# PLAN_FRONTEND.md — план работ по frontend / UI / UX

Зафиксированный план бесконечного итеративного цикла улучшения интерфейса
quiz-app. Работаем как senior frontend engineer + product-minded UI/UX reviewer +
accessibility reviewer. **Хирург, а не экскаватор:** маленькие безопасные порции,
каждая с причиной, без хаотичного редизайна и слома бизнес-логики.

Журнал выполненного — `docs/ui-ux-improvement-log.md`. Этот файл — карта
территории и приоритизированный бэклог; журнал — история сделанного.

---

## 1. Стек и жёсткие ограничения

- **Стек:** Spring Boot + **Thymeleaf**-шаблоны + **vanilla CSS/JS**. НЕ npm/React.
  Поэтому `npm run lint/typecheck/test/build`, Storybook, Cypress, Playwright-CI —
  **N/A**. Проверки = Gradle-static (когда уместно) + живой `chrome-devtools`.
- **CSS-архитектура:** `tokens.css` (токены 10 дизайнов) + `base.css` (структура).
  `editorial.css` — мёртвый код, не подключён.
- **Дизайн-система:** 10 переключаемых дизайнов (editorial=дефолт, linear, swiss,
  notion, mintlify, broadsheet, superhuman, stripe, claude, theverge) × 2 темы.
  Персонализация — атрибуты `data-*` на `<html>`; дефолт = отсутствие атрибута.
- **Версионирование ассетов:** правка CSS → бампать `?v=N` у обеих ссылок в
  `fragments/head.html`; правка JS → `app.js ?v=N` в `result.html` / `settings.html` /
  `focus-training.html`, `stats.js` — в `stats.html`. Чистые правки текста шаблона
  бампа НЕ требуют (сервер рендерит свежим на каждый запрос).
- **Живой прогон:** правки `static/`/`templates/` нужно `cp` в
  `build/resources/main/...`, чтобы попали в работающий bootRun (LiveReload).
  Не запускать gradle build при живом bootRun (wedge). Postgres-контейнер
  `quiz-postgres` слушает на хост-порту **5433**.

## 3. Методология приоритизации

Каждое улучшение оценивается по 4 осям:

```
Impact:     high / medium / low   — насколько улучшает опыт
Risk:       high / medium / low   — шанс что-то сломать
Effort:     high / medium / low   — объём работы
Confidence: high / medium / low   — уверенность, что это реальная проблема
```

Берём сначала **high impact + low/medium risk + high confidence**. Каждое
изменение обязано иметь причину из списка: читаемость / сценарий / консистентность /
a11y / responsive / меньше дублирования / ближе к дизайн-системе / понятнее
состояние / меньше когнитивной нагрузки. Не «покрасивее».

Порядок приоритетов (от важного к косметике):

1. Явные UX-баги, мешающие пользователю.
2. Accessibility-проблемы.
3. Broken/responsive layout, overflow.
4. Некорректные loading/error/empty states.
5. Непонятные формы и validation-сообщения.
6. Непоследовательные кнопки/поля/spacing/typography.
7. Дублирующиеся компоненты.
8. Плохая декомпозиция frontend-кода.
9. Визуальная полировка.
10. Микрокопирайтинг.

## 4. Аудит-области (чеклист, проходим по кругу)

- **Layout / иерархия:** одна явная цель экрана, единые отступы, визуальный ритм.
- **Компоненты:** кнопки/инпуты/селекты/чекбоксы/табы/карточки/таблицы/бэйджи/
  алерты/модалки/тултипы/пагинация — консистентность и переиспользование.
- **Формы:** labels, required, validation-сообщения по делу, disabled/loading на
  submit, сохранение ввода при ошибке, success-state, tab-order, autofocus.
- **Empty/loading/error:** что видит пользователь, есть ли recovery/retry, понятный
  текст на языке проекта, не выглядит сломанным.
- **A11y:** семантический HTML, button vs div, labels, aria только по делу,
  keyboard-навигация, focus-states, focus-trap в модалках, контраст, table headers,
  ассоциация ошибок с полями, screen-reader текст, отсутствие keyboard-ловушек.
- **Responsive:** mobile / tablet / desktop / wide; overflow, обрезанные кнопки,
  сломанные гриды, переносы, touch-targets ≥44px.
- **Навигация / сценарии:** где я нахожусь, primary/secondary actions, back/cancel,
  не теряются ли данные, минимум кликов до цели.
- **Таблицы:** названия колонок, сортировка/фильтрация, overflow длинных значений,
  empty/loading/error, понятные actions.
- **Микрокопирайтинг:** заголовки/подсказки/ошибки/кнопки — конкретно, коротко,
  без канцелярита, без абстрактного «произошла ошибка».
- **Frontend-архитектура:** большие шаблоны, дублирование, нечитаемые условия,
  хаотичные стили, несогласованные имена.

## 5. Текущий бэклог (worst-first, поддерживается живым)

Лёгкие победы за ~15 раундов уже выбраны (см. журнал). Остаток делится на:

- **recompile-gated** — требует правки Java MAIN → recompile-wedge живого bootRun
  (jacoco/label-задачи). Откладываем до отдельного цикла без живого bootRun.
- **decision-gated** — ждёт решения пользователя (favorite-флоу; «акцент-линейка»
  `border-left 3px` — A/B impeccable-ban vs editorial-идентичность — DEFERRED).
- **polish-проходы** — адресные хирургические улучшения по областям §4, которые
  можно делать без recompile и без решений: микрокопирайтинг, a11y-атрибуты,
  empty/error-state тексты, консистентность кнопок, print-паритет, responsive-краевые.

**Не трогать (осознанные решения пользователя, НЕ баги):**
prose `--measure` full-width; `.focus-question` 48px; `body` 18px/1.7; stats
cold-start вид; `role=rowheader` на summary `<td>` (share-text JS читает `td`);
💡-подсказка и 🎲🤔💪-уверенность (намеренные эмодзи); монохромный Lucide-спрайт
вместо эмодзи в остальном UI.

## 6. Цикл одной итерации

1. Выбрать одну область (§4), worst-first.
2. Понять текущий UX и код (graphify-first для навигации).
3. Сформулировать конкретную правку + оценка Impact/Risk/Effort/Confidence.
4. Внести минимальную правку (source).
5. Live-sync: `cp` source → `build/resources/main/...`.
6. Live-verify через chrome-devtools (CSSOM/DOM), оба видимых состояния.
7. При видимой дельте — пересобрать полный скриншот-набор (§7), старый удалить.
8. Запись в `docs/ui-ux-improvement-log.md`.
9. Commit source-only пер-pathspec (без push).
10. Следующая область.
