## Исправленная теория

**Q2:** роли mock/stub не объявлены несовместимыми Java-типами. Один обычный Mockito mock может одновременно предоставлять настроенные ответы и записывать взаимодействия для verify. Spy определён в контексте API Mockito; общая терминология Test Spy не сводится к частичному вызову реального кода. Fake — рабочее упрощение контракта, а не обязательно хранение в памяти. Map-репозиторий не обещает семантику транзакций production-БД.

**Q6:** различие ограничено ответами по умолчанию, а не формулой «пустышка против настоящего исходного объекта». У mock можно явно вызвать реальную реализацию; у spy не возникает тело абстрактного метода. Полный пример с MockitoExtension показывает default answers, verify и doReturn. Второй тест показывает независимость примитивного поля spy от original. Текст отдельно оговаривает общие ссылочные поля поверхностной копии и риск реального вызова при when на незаглушённом методе.

**Q31:** разделены spy(instance), spy(Class) и обработанное поле @Spy. Готовый экземпляр не обязателен; generic-параметр не требует initializer. Полный пример показывает созданный ArrayList<String>, заданную List-реализацию, обе фабрики и поле-интерфейс с default-методом. Само наличие аннотации не запускает обработчик. @Spy интерфейса не превращается в скрытую бизнес-реализацию: у List без заданной реализации add не получает хранилище ArrayList. Обычное поле класса только с аргументным конструктором требует подходящего способа создания; сочетание Spy/InjectMocks имеет отдельный путь.

## Документация и версия

Сверялись первичные исходники **Mockito v5.11.0**: [Mockito.java](https://github.com/mockito/mockito/blob/v5.11.0/src/main/java/org/mockito/Mockito.java) для копирования существующего экземпляра, фабрики по типу и реального вызова при настройке; [Spy.java](https://github.com/mockito/mockito/blob/v5.11.0/src/main/java/org/mockito/Spy.java) для аннотации; [SpyAnnotationEngine](https://github.com/mockito/mockito/blob/v5.11.0/src/main/java/org/mockito/internal/configuration/SpyAnnotationEngine.java) для готовых/null полей, interface/abstract путей, no-arg конструктора и отдельной обработки InjectMocks. После первоначального чтения javadoc.io начал возвращать 403; необходимые факты дополнительно сверены по raw-исходникам того же тега и локальным runtime.

Роли двойников и отличие терминологии Test Spy от Mockito partial spy сверены с авторским текстом [Martin Fowler, Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html), 2007. Это источник терминологии, а не руководство по текущему API Mockito и не результат исполнения его примеров.

Один support test ожидает MockitoException через assertThrows и проверяет сообщение о no-arg конструкторе — это явно проверенный отрицательный сценарий, не скрытое падение набора.

Подтверждено:

- spy(original) — другая ссылка. Изменение его int-поля не меняет int original, но List-поле остаётся общей ссылкой; вызов метода original не появляется в verify-истории spy.
- То же копирование при обработке готового @Spy поля. Без обработки поле остаётся исходным обычным объектом.
- @Spy ArrayList<String> без initializer создаётся и действительно хранит добавленный элемент.
- @Spy интерфейса без initializer создаётся: default-метод выполняется, абстрактный int-метод возвращает 0 до stubbing.
- @Spy List<String> без реализации создаётся, но add возвращает false и size остаётся 0: скрытого ArrayList нет.
- spy(AbstractType.class) и создаваемое @Spy abstract поле исполняют конкретный метод с конструкторно инициализированным полем; абстрактный String-метод возвращает null.
- Обычный @Spy класс только с аргументным конструктором без заданного экземпляра отклоняется; готовое значение с аргументом работает.
- when на незаглушённом spy Reader.read выполняет реальный метод при настройке, doReturn — нет. Обычный mock допускает явный thenCallRealMethod.
- Один Mockito mock даёт stubbed answer и проходит verify по тому же обращению.

Применён только startup `-javaagent` в отдельном завершаемом JVM-процессе. Приложение, Docker и Gradle integration tests не запускались. Проверка относится к указанной версии и стандартной локальной конфигурации; custom MockMaker и другие версии этим запуском не проверены.

## Замечания владельцу MCQ

Ключи **Q2 B / Q6 D / Q31 D** сохраняют правильную основную модель, но есть ложные пояснения в wrong sections:

1. **Q6 A, if_it_were_true:** «spy требует реального экземпляра» — чрезмерное требование готового original. Фабрика по Class и поле-интерфейс работают без ранее переданного экземпляра. Разницу default answers следует объяснять непосредственно.
2. **Q31 A, what_actually/how_it_should_be:** обязательная оболочка «поверх реального объекта» и «разница чисто синтаксическая, поведение идентично» скрывают копирование состояния, создание по типу и обработку аннотации. Основная ошибка A — подмена spy обычным mock; для её опровержения не нужны эти дополнительные неверные обещания.
3. **Q31 C, what_actually:** «нужен создаваемый конкретный тип» исключает поддержанные в 5.11 interface и создаваемые abstract поля. Runtime подтвердил оба. Совету явно передать ArrayList для реального хранения нужен именно такой смысл, а не запрет любого interface spy.
4. **Q2:** точный visible stem без backticks отличается от question_text с backticks. Заголовок теории сохранён; JSON можно согласовать с ним владельцу MCQ без смены Q-number. Роль fake не стоит определять обязательным отсутствием Mockito: существенна упрощённая рабочая логика.
