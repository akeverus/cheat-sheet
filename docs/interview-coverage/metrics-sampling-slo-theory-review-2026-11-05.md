## Подготовленные группы

**Sampling Q9/Q24.** В Q9 разделены момент решения head/tail и политика отбора; убрана классификация rate-limiting как третьего взаимоисключающего момента. Вместо неполной Spring-конфигурации — фрагмент Java SDK **1.37.0** с ParentBased для решения родителя и примером доли для root. Объяснены отсутствие точной квоты 10% и отличие создания sampler от подключения SDK. Отдельно отмечено состояние TraceIdRatioBased в спецификации **OTel 1.62.0**; это не объявлено состоянием всех старых Java SDK. [Sampling](https://opentelemetry.io/docs/concepts/sampling/), [Sampler API 1.37.0](https://github.com/open-telemetry/opentelemetry-java/blob/v1.37.0/sdk/trace/src/main/java/io/opentelemetry/sdk/trace/samplers/Sampler.java), [SDK spec](https://opentelemetry.io/docs/specs/otel/trace/sdk/#traceidratiobased).

Q24 YAML назван фрагментом processors, который нужно включить в pipeline. Уточнены независимые обычные policies: выбор по ERROR/latency или вероятности, а не глобальный лимит 5%. expected_new_traces_per_sec — подсказка выделения структур; нижний latency threshold без upper_threshold_ms включителен в прочитанном evaluator. Источники Collector — ветка main на дату чтения, не проверенная локальная поставка. [README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/tailsamplingprocessor/README.md), [latency.go](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/tailsamplingprocessor/internal/sampling/latency.go).

**SLO Q36/Q41.** Q36 теперь различает бюджет запросов и времени, рассчитывает burn rate как bad_fraction/(1-s), описывает цель вместе с окном/областью. SLA/SLO нельзя сравнивать одной универсальной процентной формулой; release policy не обязана запрещать изменения до календарного месяца. Числа 14.4 и окна 1h/5m названы примером, не обязательным порогом. [SRE definitions](https://sre.google/sre-book/service-level-objectives/), [alerting](https://sre.google/workbook/alerting-on-slos/), [example policy](https://sre.google/workbook/error-budget-policy/).

В Q41 latency SLI показан как доля ниже определённого histogram bucket. Удалены ложные равенства freshness=последний poll, durability=доля успешных write-ответов и throughput=процент успешных записей; для jobs объяснена согласованная группа с deadline и учёт retry. Убраны универсальные числовые SLO, жёсткий предел 3–5 SLI и запрет blackbox как реализации SLI. Вывод о poll следует из API, допускающего пустой результат и отдельную обработку данных. [Kafka API 3.7.2](https://kafka.apache.org/37/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html), [pipeline SLOs](https://sre.google/workbook/data-processing/), [SLI implementations](https://sre.google/workbook/implementing-slos/), [classic histogram buckets](https://prometheus.io/docs/practices/histograms/).
