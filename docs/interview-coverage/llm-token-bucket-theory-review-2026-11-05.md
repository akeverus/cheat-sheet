## Источниковая проверка

Прежний набросок с `token_bucket.TokenBucket` заменён
описанием алгоритма без обещания готовой реализации. Rate задаёт
пополнение, capacity ограничивает накопленный запас и burst. Контроль
допуска приложения не гарантирует отсутствие provider 429.

Открыты первичные страницы:

- [OpenAI Rate limits](https://developers.openai.com/api/docs/guides/rate-limits):
  RPM/TPM и другие применимые лимиты, scope организации/проекта,
  различия и общие группы моделей. Неуспешные запросы также входят
  в поминутный лимит, поэтому повторные попытки проходят тот же
  локальный контроль допуска. Конкретные числа квот не зафиксированы.
- [Claude API Rate limits](https://platform.claude.com/docs/en/api/rate-limits):
  Messages API разделяет RPM, ITPM и OTPM. Для большинства моделей
  чтение prompt cache исключено из ITPM; запись cache учитывается.
  OTPM оценивается по фактически создаваемому выводу. Правила и
  модельные группы берутся из текущего контракта провайдера.

Резервирование входа/выхода и последующая сверка с доступным usage —
предлагаемая локальная схема допуска, а не утверждение, что провайдер
использует именно такой алгоритм. При неизвестном расходе прерванного
вызова весь резерв нельзя освобождать безусловно.

## Исправленная граница: координация общей квоты

Прежняя теория требовала общего атомарного состояния во всех случаях.
Это чрезмерно: можно заранее распределить безопасные доли каждого
бюджета между репликами. Два инстанса с половиной общей квоты каждый
не удваивают суммарный допуск. Превышение создают независимые ведра,
каждое из которых настроено на полный лимит провайдера.

Это инженерный вывод о сумме выделенных бюджетов, а не цитата из
документации OpenAI или Claude. Теория теперь называет оба подхода;
Q16 остаётся ссылкой на реализацию с общим состоянием.

## Finding парного MCQ — первоначальная находка

**F-Q14-QUOTA-PARTITIONING**:

- `options[label=A].sections.edge_cases` утверждает: «Общий лимит
  требует общего атомарно обновляемого состояния». Не оговорён вариант
  заранее выделенных долей квоты.
- `options[label=D].text` предлагает проверять бюджеты каждого
  инстанса до вызова и сверять суммарный расход после ответа.
  Без условия, что каждому выдан полный общий лимит, это описание
  допускает безопасную интерпретацию с заранее распределёнными долями.
  В `D.sections.what_actually` условие «свой полный лимит» уже есть,
  но в видимой опции оно не закреплено; `D.sections.how_it_should_be`
  также подаёт централизованное состояние как единственное решение.

Владельцу MCQ нужно ограничить ошибочную модель D независимыми ведрами
на полный лимит и согласовать sections A/D с этой границей; затем
перечитать весь блок. Ключ A соответствует основному вопросу о
согласованном учёте применимых бюджетов; B игнорирует токенный бюджет,
C откладывает учёт входа. Текущая неоднозначность D не закрыта этой
авторской проверкой. JSON не редактировался.
