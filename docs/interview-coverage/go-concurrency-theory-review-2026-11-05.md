## Ручная проверка кода/гарантий

**Q3.** Изменённые утверждения снимают прежние чрезмерные гарантии: `GOMAXPROCS` — текущий уровень параллельного исполнения, может меняться; `~10 ms` не выдан за deadline вытеснения; work stealing описан как возможный механизм. Preemption версии 1.14+ сформулировано как возможность прервать многие вычисления, а не безусловная гарантия. Один упрощённый M↔P↔CPU рисунок разумно читать как snapshot, не постоянную affinity.

**Q4.** В обоих примерах close(done)/cancel посылает сигнал и отдельный `finished` канал доказывает завершение. При раннем сигнале до старта receiver закрытый done/context уже читается; ожидание finished остаётся корректным. Вызов cancel не принудителен и не ждёт. Замечание про пустой `default` предотвращает занятие CPU в busy loop.

**Q5.** Официальный runtime reference перечисляет logical CPU count, process affinity и cgroup CPU throughput quota; уточняет min 2, если logical CPUs/affinity допускают, и округление нецелой quota вверх. Updater периодически пересчитывает runtime default; явный GOMAXPROCS/positive `runtime.GOMAXPROCS` выключает это, `SetDefaultGOMAXPROCS()` восстанавливает. В релизных заметках и reference GODEBUG compatibility flags применяются для module language version 1.24 и ниже. Формулировка «для версии главного модуля до 1.25» соответствует этой границе.

**Q14.** Упоминание `time.After` в цикле не называет его утечкой для современной semantics: Go 1.23 может GC-collect недостижимый таймер. `NewTimer`/`Reset` рекомендованы при нужде в контроле/измеренной цене. Пояснение про legacy stop-and-drain ограничено старой семантикой, а не советует безусловно читать канал в новом режиме.

**Q23–Q25.** Пример Q23 собирается по импортам как main-file. Тело теперь прямо уточняет: если результат и `ctx.Done()` готовы одновременно, `select` не приоритизирует отмену и выбирает любой готовый case; контракт принятия результата после deadline задаётся явно. Это соответствует Go spec, где один готовый communication выбирается псевдослучайно. При 5s context и независимом 10s timer возможны оба готовых case, например после долгой паузы scheduler; пример не должен подразумевать обязательное предпочтение context. Q24 child deadline не может продлить более ранний parent deadline. Q25 после `cancelParent()` закрывается `child.Done()`, а `Err()` возвращает `context.Canceled`; обе CancelFunc defer безопасны после ручной отмены.

**Q26.** Для текущих фиксированных 5 jobs схема с незабуференными jobs/results не образует цикл ожидания: producer шлёт задания, три workers отправляют результат, main range читает их, все workers заканчивают после close(jobs), Wait завершается, closer закрывает results и range завершает main. При раннем прекращении чтения worker может застрять на `results <- ...`, producer — на `jobs <- ...`; текст уже называет общий cancellation сигнал, который должен участвовать в обеих отправках/приёме. Открытый Go pipelines материал подтверждает, что ранний downstream return требует разблокировать upstream senders сигналом отмены. Новые WaitGroup, close(results) после Wait и передача `id` параметром исправляют прежнее замечание об отсутствии явного worker join.
