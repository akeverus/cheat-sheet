## components-table-e01 · components-table.css:1

**Контекст:** `@layer components {`

@layer components — ТАБЛИЦА ДАННЫХ: один компонент и ОДИН ответ на нехватку ширины.
 *
 * До iter-76 на пять таблиц приложения приходилось пять разных ответов на вопрос
 * «что делать, когда таблица шире своей полосы»:
 *   1. .summary-table  — table-layout:fixed + фикс. ширины колонок, скролла нет;
 *   2. .topic-table    — обёртка .topic-table-wrap с overflow-x:auto;
 *   3. .data-table     — ничего;
 *   4. .chart-adjacent-table — ничего (только width:100%);
 *   5. .markdown-content table — display:block + overflow-x:auto на самой таблице.
 * Четыре из пяти вдобавок независимо переобъявляли один и тот же скелет (ширина,
 * border-collapse, паддинг ячейки, mono-uppercase шапка). Это ровно то, что §24
 * запрещает — несколько конкурирующих систем на одну задачу.
 *
 * ЗАМЕР, из-за которого ответ пришлось выбирать, а не оставлять как есть:
 * `width: 100%` на table-layout:auto — это ПРЕДПОЧТИТЕЛЬНАЯ ширина, а не предел.
 * Таблица всё равно раздувается до min-content. На /stats при увеличенном тексте
 * (root=25px — это MacBook при зуме 125%) .chart-adjacent-table занимала 441px в
 * карточке шириной 315px, а у карточки overflow-x:visible → выпирание доезжало до
 * документа и страница ехала вбок (WCAG 1.4.10 Reflow, 1.4.4 Resize text).
 *
 * ПОЧЕМУ ОБЁРТКА, А НЕ display:block НА ТАБЛИЦЕ (контролируемый опыт, WebKit@2):
 *   • дерево доступности у обоих приёмов ОДИНАКОВОЕ (table=1 row=3 cell=8
 *     columnheader=9 rowheader=4) — то есть довод «display:block ломает семантику»
 *     в этом движке не воспроизвёлся и решающим не был;
 *   • а вот заполнение — расходится радикально. Хост 600px, короткое содержимое:
 *     display:block → правый край последней ячейки 223px, СПРАВА 377px мёртвой
 *     пустоты внутри карточки (§6); обёртка → 599px, недобор 1px.
 *     display:block делает из таблицы блок с анонимным табличным боксом внутри, и
 *     этот бокс — shrink-to-fit. Прижатая вправо колонка «Действие» и центрированные
 *     числовые колонки при этом повисают посреди карточки.
 * Обёртка выигрывает по заполнению и не проигрывает по семантике → она и есть
 * единственный ответ. Ровно этот вывод уже был получен на .summary-table (см.
 * pages-summary.css) — там display:block сняли, но вместе с ним потеряли и саму
 * гарантию; здесь гарантия возвращается без мёртвой пустоты.
 *
 * Таблицы данных стандарт из требования «никакой прокрутки в двух измерениях»
 * (1.4.10) явно ИСКЛЮЧАЕТ, поэтому локальный скролл-контейнер — не обход правила,
 * а предусмотренный им приём. Условие — контейнер должен быть доступен с клавиатуры
 * и виден глазом; это и делает .is-scrollable ниже.
