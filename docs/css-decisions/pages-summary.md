# pages-summary.css — досье решений (ARCH-02)

Полные доводы и история правил, вынесенные из комментариев `pages-summary.css`
(REF-009): эссе читают при ПЕРЕСМОТРЕ решения, а не при каждом чтении файла.
У правила в CSS остаётся указатель с тезисом; якоря ниже — цель указателей.
Рабочие инварианты («НЕ менять», пороги) остаются в CSS.

## pages-summary-e01 · pages-summary.css:6

**Контекст:** `только вертикальный ритм между блоками итога. */`

Своей ширины у страницы итогов больше нет — она берёт общую `.ed-page`
   (--max-width-page, reset-layout.css), как /stats и /bookmarks.

   Здесь стояло `max-width: var(--max-width-reading)` (896px). Мера чтения — для
   сплошного текста, а итог сессии текстом не является: это счёт, полоса KPI,
   пятиколоночная таблица тем и список ошибок. Замер (iter-63, WebKit@2): полоса
   контента росла 1060 → 2340px от 1280 до 2560, а `.ed-page` оставалась 896 —
   мимо уходило 384px на 1280 и 1444px на 2560. Хуже того, таблица тем при этом
   СУЖАЛАСЬ с ростом окна (380 → 347px): её колонка — 7fr фиксированной полосы,
   из которой растущий --page-gutter вычитает всё больше. Две ширины для двух
   страниц с одинаковым содержимым — ровно тот дубль, который запрещено
   оставлять; ширина теперь одна на все экраны данных.

<a id="pages-summary-e04"></a>
## pages-summary-e04 · pages-summary.css:226

**Контекст:** `html[data-design] .summary-page .summary-table { table-layout: fixed; }`

Таблица тем — настоящая таблица во всю ширину секции.
   ИСТОРИЯ РЕШЕНИЯ. Сначала здесь было `display:block; overflow-x:auto` — приём
   «обёртка со скроллом», применённый к самой таблице. display:block делает из неё
   блок с анонимным табличным боксом внутри, а тот shrink-to-fit: замер давал бокс
   1041px при сумме колонок 406px, то есть 635px пустоты справа внутри рамки (§7).
   Приём сняли — вместе с ним пропала и защита от переполнения, потому что
   `table-layout:fixed` её НЕ даёт: фиксированные колонки 5.5rem×3 + 11rem = 27.5rem
   при увеличенном тексте (root=25px это 687px) шире полосы, и таблица снова поехала
   бы вбок. iter-76 вернул защиту правильным приёмом — внешней обёрткой .table-scroll
   в разметке: она ограничивает ширину, не превращая таблицу в блок, поэтому мёртвой
   пустоты справа не даёт (замер: недобор 1px против 377px у display:block).
   table-layout:fixed остаётся — но уже как решение про РАСПРЕДЕЛЕНИЕ ширины
   (остаток забирает «Тема», а не все колонки пропорционально), а не про переполнение.
   Скелет (ширина/линейки/шапка/паддинги) — из компонента .data-table.

## pages-summary-e05 · pages-summary.css:266

**Контекст:** `html[data-design] .summary-page .summary-mistakes {`

Ошибки — сетка карточек по доступной ширине, а не одна колонка.
   Колонка была следствием двухстолбцовой раскладки страницы (таблица слева,
   ошибки справа), которая разъезжалась на замере: высота левого столбца задаётся
   числом ТЕМ (обычно 1–3 строки), правого — числом ОШИБОК (до сотен). На 1280…2560
   левый столбец кончался на 1037–1067px выше правого — постоянная дыра, не
   зависящая от ширины экрана. Столбцы убраны, обе секции полноширинные (§6, §7).
   auto-fill без медиазапросов: число колонок выбирает контент. Замер (WebKit@2):
   3 колонки на 1440…2560, 2 на 768…1280, 1 на ≤430 — ни одного breakpoint.
   min(100%, 300px) держит карточку уже 300px, когда контейнер меньше, иначе на
   360px (полоса 264px) появился бы горизонтальный скролл.

## pages-summary-e06 · pages-summary.css:434

**Контекст:** `}`

Двухстолбцовая раскладка страницы (`.ed-page:has(> section .summary-mistakes)`
     → 7fr/5fr, таблица слева, ошибки справа) удалена. Причина замером: столбцы
     наполняются разными сущностями — левый растёт по числу тем, правый по числу
     ошибок, и на 1280/1440/1920/2560 левый заканчивался на 1067/1067/1037/1067px
     выше правого. Дыра была постоянной, а не краевым случаем редких данных.
     Вдобавок таблица получала лишь 7fr от полосы: 476…593px из 1280 (§7 — таблица
     не должна занимать малую часть доступной ширины).
     Теперь обе секции полноширинные, а ширину использует сетка карточек ошибок
     (`.summary-mistakes`, auto-fill) — см. базовое правило выше.

## pages-summary-e07 · pages-summary.css:446

**Контекст:** `Замер 2560×1440: `.summary-seal` — прямой ребёнок сетки разбора (`804px 804px`),`

===========================================================================
   СЦЕНА ЗАВЕРШЕНИЯ И РЯД РАЗБОРА.

   Замер 2560×1440 (без JS, экзамен с одним ответом): содержимое кончалось на 1025,
   ниже оставалось 415px фона — почти треть экрана, и это ровно «страница кончилась
   на середине» из §37. Внутри карточек «Результаты по темам» и «Ошибки» контент при
   этом жался к левому краю: таблица в одну строку занимала половину ширины.

   Две правки на одну причину — «содержимого меньше, чем места»:
   1) сцена завершения занимает верхнюю зону там, где она есть (от 1200px), и
      исчезает с узких экранов, где место дорого;
   2) разбор («Результаты по темам» + «Ошибки») с 1200px идёт РЯДОМ, а не этажами.

   Масштаб сцены целочисленный к сетке 40×25 (×8 = 320×200, ×4 = 160×100) — тот же,
   что у сцен пустых состояний: нецелый растянул бы пиксель.
   ===========================================================================
