# Журнал улучшений Frontend / UI / UX

Лог бесконечного итеративного цикла улучшения интерфейса quiz-app. Каждая
итерация — небольшая хирургическая порция изменений, не ломающая бизнес-логику
и дизайн-систему. Работаем как senior frontend + product UI/UX + accessibility
reviewer.

## Стек и ограничения (важно для каждой итерации)

- **Стек:** Spring Boot + **Thymeleaf** шаблоны + **vanilla CSS/JS**. НЕ npm/React.
  Поэтому шаги `npm run lint/typecheck/test/build`, Storybook, Cypress из общего
  workflow — **N/A**. Проверки = Gradle-static (когда нужно) + живой chrome-devtools.
- **CSS-архитектура:** `tokens.css` (токены 10 дизайнов) + `base.css` (структура).
  `editorial.css` — мёртвый код, не подключён. Бампать `?v=N` в `fragments/head.html`
  (2 ссылки) при правке CSS; `app.js ?v=N` в `result.html` / `settings.html` /
  `focus-training.html`; `stats.js` в `stats.html`.
- **Дизайн-система:** 10 переключаемых дизайнов (editorial=дефолт, linear, swiss,
  notion, mintlify, broadsheet, superhuman, stripe, claude, theverge) × 2 темы.
  Персонализация — атрибуты `data-*` на `<html>`. Дефолт = отсутствие атрибута.
- **Живой прогон:** правки `static/`/`templates/` нужно `cp` в
  `build/resources/main/...` чтобы попали в работающий bootRun (LiveReload).
- **Запрещено:** менять бизнес-логику/API ради фронта; новые зависимости; трогать
  MCQ JSON-сидеры (их ведёт внешний auto-improve); трогать mermaid; добавлять
  контролы в минималистичный focus-режим; commit/push без явного разрешения
  (пользователь пушит сам). Деструктивные действия в живом приложении (отправка
  ответа, старт/финиш сессии) — НЕ выполнять, проверять статически.

## Методология приоритизации

Каждое улучшение оценивается по 4 осям:

```
Impact:     high / medium / low   — насколько улучшает опыт
Risk:       high / medium / low   — шанс что-то сломать
Effort:     high / medium / low   — объём работы
Confidence: high / medium / low   — уверенность что это реальная проблема
```

Берём сначала **high impact + low/medium risk + high confidence**. Каждое
изменение должно иметь причину (читаемость / сценарий / консистентность / a11y /
responsive / меньше дублирования / ближе к дизайн-системе / понятнее состояние /
меньше когнитивной нагрузки), а не «покрасивее».
