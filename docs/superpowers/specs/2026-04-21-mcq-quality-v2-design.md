# MCQ Quality v2 Design

**Дата:** 2026-04-21  
**Проблема:** Правильный ответ слишком легко угадывается — длинее других, содержит больше деталей, дистракторы из другой области знаний.

## Диагностика текущих проблем

| Проблема | Пример из БД | Почему плохо |
|---|---|---|
| Длина correct в 14-21× больше дистракторов | Q708: correct=422 симв., avg wrong=20 симв. | Выбирается без знания темы |
| Дистракторы из чужой области | Q1 (ES): «Графовая БД с Cypher», «RocksDB OLTP» | Решаются без знания ES |
| Низкий когнитивный уровень | «Что такое X?» → recall definition | Application/Analysis дискриминируют лучше |
| 1 предложение = слишком мало для сложных тем | Нельзя передать нюанс поведения | Shallow options |

## Дизайн v2 (Hybrid по категориям)

### Категория A — Концептуальные / архитектурные

**Формат вопроса:** текстовый, с inline-кодом `` `ClassName` ``  
**Формат опций:** 2-3 предложения; inline-код обязателен при упоминании конкретных API

### Категория B — Поведенческие / имплементационные

**Формат вопроса:** код-блок в stem (Java, SQL, Python...) + поведенческий вопрос  
**Формат опций:** конкретный вывод / exception / описание поведения  
Пример stem:
```java
ExecutorService pool = Executors.newFixedThreadPool(2);
pool.submit(() -> { throw new RuntimeException("boom"); });
System.out.println(pool.isTerminated());
```
_Что выведет код и почему?_

### Категория C — Выбор реализации

**Формат вопроса:** постановка задачи + несколько code-вариантов в options  
**Формат опций:** каждый вариант — короткий code snippet (~3-5 строк)

## Новые правила качества (замена старых)

### 1. Информационная глубина (заменяет character ratio)

Каждая опция содержит **одинаковое количество технических утверждений (1-3)**. Если correct называет 3 факта — каждый дистрактор тоже называет 3 факта (пусть один из них ложный).

Запрещено: correct с 3 claims + distractor с 1 claim.

### 2. Строгая доменная изоляция

АБСОЛЮТНОЕ правило: все 4 опции — **только про тот же класс/API/технологию**, что в вопросе.  
- Вопрос про Elasticsearch → все 4 опции про Elasticsearch  
- Вопрос про `HashMap` → все 4 опции про `HashMap` (не TreeMap, не LinkedHashMap, если не тема сравнения)  
- НИКОГДА: ES вопрос + дистракторы про Redis, RocksDB, Cassandra, «графовая БД с Cypher»

### 3. Когнитивный уровень ≥ Application

Предпочтительные форматы вопросов:
- «Что произойдёт если...»
- «Найди ошибку в коде»
- «Выбери правильную реализацию для задачи X»
- «Какое поведение нарушает/обеспечивает...»

Минимизировать: «Что такое X?» (только если без этого нельзя)

### 4. Код в вопросах — когда обязателен

| Тема | Код в stem? |
|---|---|
| Java (concurrency, collections, streams, exceptions, generics) | Да, всегда |
| SQL (поведение запроса, план, результат) | Да |
| Алгоритмы и структуры данных | Да |
| ES/Redis/K8s/Kafka (конфигурация, DSL) | Inline-фрагмент JSON/YAML/DSL когда уместен |
| Архитектурные паттерны, принципы (SOLID, CAP) | Нет |

### 5. Типология дистракторов v2 (7 типов)

Оставить 5 из v1 + 2 новых:
1. Partial truth — большая часть верна, одна деталь сломана
2. Common misconception — реальное заблуждение middle-dev
3. Adjacent API mix-up — правильные факты про соседний класс/метод
4. Outdated fact — верно до Java N, Redis 6, ES 7, ...
5. Scope confusion — правильный механизм, неправильный уровень
6. **Plausible implementation mistake** — для code options: почти правильный код с одним тонким багом
7. **Correct mechanics, wrong condition** — правило верно, но в другом сценарии, не в описанном

### 6. Explanation v2

- 2-4 предложения (больше места → больше учебной ценности)
- Обязательно назвать **почему distractor правдоподобен** для middle-dev
- Обязательно указать **точный knowledge gap**: «путает `shutdown()` и `shutdownNow()`», «не знает что Segment-лок убрали в Java 8»

## Примеры нового уровня (по 1 на категорию)

### Category A — Концептуальный

Q: В чём разница между `primary shard` и `replica shard` в Elasticsearch и что происходит при потере primary?

Options (2-3 предложения каждый):
- ✅ Correct: Primary shard — единственный, на котором ES принимает операции записи; replica — синхронная копия, доступная для чтения и автоматически промоутируемая в primary при отказе узла через master election. Количество primary фиксируется при создании индекса, число реплик меняется динамически.
- D1 (scope confusion): Replica shard принимает операции записи параллельно с primary через multi-master протокол, что обеспечивает горизонтальное масштабирование записи.
- D2 (partial truth): При потере primary-узла ES помечает шард `UNASSIGNED` и ждёт возврата того же узла; промоут replica в primary не происходит автоматически.
- D3 (outdated): До ES 7.x replica могла обслуживать только чтение через round-robin; начиная с 7.x она участвует в записи наравне с primary.

### Category B — Поведенческий с кодом

Q:
```java
CompletableFuture<String> f = CompletableFuture.supplyAsync(() -> {
    throw new RuntimeException("fail");
});
f.exceptionally(e -> "recovered")
 .thenAccept(System.out::println);
```
Что выведет программа?

Options:
- A: `recovered` — `exceptionally` перехватывает исключение и возвращает значение, которое передаётся в `thenAccept`.
- B: Программа завершается без вывода; `RuntimeException` в `supplyAsync` подавляется компилятором JVM и никогда не доходит до `exceptionally`.
- C: `null` — `exceptionally` возвращает `CompletableFuture<Void>` при обработке исключения, игнорируя возвращаемое значение лямбды.
- D: `java.lang.RuntimeException: fail` — `exceptionally` только логирует исключение, но всё равно пробрасывает его в `thenAccept`.
