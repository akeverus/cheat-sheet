# MCQ Quality Standard — единый стандарт банка вопросов

**Статус:** действующий. Заменяет собой разрозненные правила из
`docs/mcq-structure-parity-plan.md` (автогенерируемый план, не стандарт) и
`docs/mcq-quality-improvement-plan.md` (эпоха `.md`-callout'ов, устарел).
Включает целиком `docs/mcq-quality/surface-parity-rules.md` (R1–R6 + `ANSC`) — тот
документ остаётся нормативным, здесь он дополнен измеримыми порогами и метриками.

**Уровень банка:** профессиональный вопросник технического интервью Senior / Senior+.
Качество важнее скорости, числа строк и формального прохождения валидатора.

---

## 1. Структурный контракт (что вообще есть в файле)

Источник правды — `modules/quiz-app/src/main/resources/seed/mcq-schema.json`.

```
{ topic_slug, questions[ { q_number, blocks[ { block_idx, question_text,
    options[4]{ order, label, text, correct, sections } } ] } ] }
```

`additionalProperties: false` на каждом уровне. **В seed-JSON нет полей
title / description / categories / tags / difficulty** — они живут в `.md`-файлах
интервью и в import-слое (`Question.difficulty` — enum, назначается при импорте).
Переработка этих полей — отдельная согласованная миграция, вне периметра seed-файлов.

`sections` дискриминированы ролью (`oneOf`):

| Роль | Обязательные ключи |
|---|---|
| `correct: true` | `explanation`, `example`, `when_to_apply`, `edge_cases`, `related` |
| `correct: false` | `what_actually`, `source_of_confusion`, `if_it_were_true`, `how_it_should_be` |

Инварианты, которые схема **не** проверяет, но валидатор обязан (см. §7):
ровно один `correct: true` на блок; `label` — полный набор `A,B,C,D` без повторов;
`order` — полный набор `0,1,2,3` без повторов и **отсортирован по возрастанию**;
`q_number` уникален внутри файла; тексты опций попарно различны.

**Инвариант выравнивания:** `q_number` в JSON обязан совпадать с `## Q<N>` в парном
`.md`. `question_text` не отображается пользователю; опции привязываются по номеру.

**Рендеринг:** текст опции проходит через inline-markdown (`toInlineHtml`).
`` `code` `` и `**bold**` работают. Стрипать markdown из seed нельзя.

---

## 2. Главный тезис (one-line test)

> Убери поле `correct` — правильный ответ обязан быть **неотличим по форме** от трёх
> остальных. Отличается только истинность.

Это критерий №1. Системный дефект банка, ради которого затеяна переработка:
**правильный ответ статистически сам себя выдаёт** — он длиннее, полнее,
структурнее, единственный содержит перечисление / версию / код-спан / пример.

**Направление правки — всегда ВВЕРХ.** Паритет достигается подъёмом дистракторов до
формы correct (полная правдоподобная ментальная модель с одной подменённой деталью),
а НЕ ужиманием correct до заглушек и НЕ штамповкой карбон-копий.

---

## 3. Требования к вопросу (стем)

* Проверяет понимание механизма, а не узнавание термина.
* Самодостаточен: не зависит от соседних вопросов, не отсылает к «предыдущему».
* Не содержит подсказки в формулировке (не повторяет лексику correct дословно).
* Не «какое из утверждений неверно» без крайней нужды — двойное отрицание.
* Уровень Senior+: сценарий из production, компромисс, граничный случай, а не
  определение из первого абзаца документации.

## 4. Требования к правильному ответу

* Фактически точен по §6 (иерархия источников).
* Полон: содержит механизм / условие / обоснование, достаточное для ответа.
* Не категоричнее, чем требует истина (нет искусственных «всегда», если факт мягче).
* Не единственный носитель какого-либо формального признака (см. §5).

## 5. Требования к дистракторам

Дистрактор — **полный правдоподобный ответ поверхностно знающего кандидата**, внутри
которого спрятана ровно **одна** содержательная ошибка. Не заглушка, не абсурд,
не смежная тема, не набор неточностей.

Допустимые виды ошибки (одна основная на вариант):
неверно назван принцип/механизм; перепутаны условия применения; пропущено важное
ограничение; слишком широкое обобщение частично верного тезиса; механизм описан
верно, но сделан неверный вывод; смешаны похожие понятия, версии API, уровни абстракции.

**Дистрактор = инверсия факта, а не хедж.** «Может быть, иногда, при определённых
условиях» — не дистрактор, а размытие.

**Ось заблуждения дистрактора неприкосновенна при правке формы.** Если поднимаешь
дистрактор по длине/структуре — его `sections` (`what_actually` и др.) должны
остаться валидными. Рассинхрон текста и секций — дефект класса 3 (см. §9).

## 5a. Дискурсивный паритет — главный гейт (v4)

**Как получен этот раздел.** 2026-08-05 файл `databases/database-sharding-interview.json`
прошёл все метрики `validate_v3` (risk 58, 0 format-tells) и все 12 классов
`leak_scan` — и был решён двумя независимыми слепыми ревьюерами **34/34**, без
предметных знаний, по одной только форме. Вывод: статистический паритет (§7) —
условие необходимое, но далеко не достаточное. Ключ выдавал себя **регистром речи**.

Хуже того: часть правил прежней редакции сама производила утечку. Требование
«ключ обязан признавать хотя бы одно ограничение» даёт машинно-читаемую подпись
(«Плата — …», «зато …», «но за это платят …»), по которой блок решается за секунду.
**Это требование отменено и заменено на паритет.**

### Определение дистрактора (v4)

> Дистрактор — это **правильный по форме и тону инженерный ответ, в котором неверен факт**.
> Не уверенная ложь, не переопределение термина, не отрицание посылки вопроса.

Читатель без знаний должен видеть четыре одинаково компетентно написанных абзаца.
Единственное различие — истинность утверждений.

### Правила паритета (каждое проверяется `leak_scan`)

| # | Правило | Класс детектора |
|---|---------|-----------------|
| 1 | **Паритет цены.** Если ключ называет плату за своё решение — минимум два дистрактора обязаны называть свою (правдоподобную, но неверную) плату. Ключ не может быть единственным «честным». | `COST` |
| 2 | **Паритет рубрикации.** «Плюсы: … Минусы: …» — либо у всех четырёх, либо ни у кого. | `RUBRIC` |
| 3 | **Паритет рамки.** Все четыре опции принимают рамку вопроса. Стем говорит «три драйвера» — все четыре дают три драйвера, расходясь в том, *какие* и *почему*. Ни одна опция не спорит с самим вопросом («драйвер на самом деле один»). | `DISMISSAL`, `STEMORDER` |
| 4 | **Паритет порядка.** Если стем перечисляет сущности, все четыре разбирают их в одном и том же порядке. Ключ не может быть единственным, кто «идёт ровно по заголовку». | `STEMORDER`, `ENTITY` |
| 5 | **Паритет захода.** Первое предложение построено одинаково у всех четырёх. Дистрактор не открывается переопределением термина из стема («`Vindex` — это binlog-механизм»), если ключ так не открывается. | `DEFOPEN` |
| 6 | **Паритет хеджирования.** Осторожные кванторы («и более», «как правило», «зависит от») распределены по опциям. Ключ не может быть единственным осторожным, дистракторы — единственными категоричными. | `HEDGEQ`, `ABSOLUT` |
| 7 | **Никакой «магии движка».** «Система сделает сама», «прозрачно для приложения», «без переноса данных» — это отпечаток дистрактора. Либо убрать везде, либо дать и ключу. | `MAGIC` |
| 8 | **Ключ — не надмножество.** Ключ не содержит объединения содержания дистракторов. У каждой из четырёх опций есть минимум один содержательный элемент, которого нет у остальных трёх. | `SUPERSET`, `MAJORITY`, `CLONE` |
| 9 | **Никаких клон-семейств.** Дистрактор не получается из ключа порчей одной клаузы. Расхождение — минимум по двум осям. Иначе поклаузное голосование восстанавливает ключ без предмета. | `CLAUSEMAJ`, `CONSENSUS` |
| 10 | **Никаких кросс-вопросных шаблонов.** Один и тот же шаблон дистрактора («X и Y — два названия одного механизма») не повторяется в соседних вопросах. Дистрактор не пересказывает ключ другого вопроса файла. | ручная сверка |

### Приёмка

Дискурсивный паритет считается достигнутым, когда **слепой ревьюер, получивший
только стем и четыре опции и прямо проинструктированный атаковать форму,
набирает не выше случайного уровня + 20 п.п.** (то есть ≤45% на четырёх вариантах).
Метрики `validate_v3` и `leak_scan` — дешёвый предфильтр, а не приёмка.

### 5b. Предел правил §5a: жанр стема (измерено 2026-08-05)

`database-sharding-interview.json` доведён до `34/34 clean` по всем 21 классу
`leak_scan` и `0 ERROR` в `validate_v3`; сверх гейтов вручную вычищены самодонос-лексика,
мета-отрицания, кросс-вопросные шаблоны, enum-максимум ключа и «ключ — самая длинная
опция». После этого **два независимых слепых ревью дали 17/17 и 17/17, оба отчитались
`FORM` на всех 34 вопросах** — то есть решаемо без знания предмета.

Названные ими признаки в порядке частоты **не лексические**:

1. **Покрытие стема (11/17 и 8/17).** Стем экспозиционный («X: плюсы, минусы, hot spots»,
   «причины / диагностика / лечение», «три критерия»). Полный правильный разбор физически
   один; любой неверный разбор неизбежно читается как односторонний или усечённый.
2. **«Одно яркое утверждение» у дистрактора (11/17).** Раз дистрактор обязан быть неверным,
   а стем требует экспозиции, его неверность концентрируется в одном заметном тезисе.
3. Признание цены у ключа — **цитируется даже после раздачи цены дистракторам** (путь B §2.1).

**Вывод для стандарта.** Правила §5a лечат лексику и форму опций; они не лечат жанр стема.
Пока стем экспозиционный, ключ обречён быть единственной полной экспозицией. Правки на
уровне опций здесь исчерпаны — дальше только редизайн вопроса: сценарный/диагностический
стем, где все четыре опции — трезвые инженерные позиции, а различает их один конкретный
факт, а не полнота охвата.

**Это упирается в BLK-003** (`docs/mcq-refactoring-state.md`): отображаемый стем — заголовок
`## Q<N>` шпаргалки, `question_text` из seed загрузчиком не читается. Редизайн стемов требует
миграции модели данных, а не патча seed-файла.

### 5c. Приёмы авторинга, проверенные численно

* `correct_ratio` = `correct_words / mean(три неверных)` — среднее **только по неверным**,
  не по всем четырём. Целиться в длину ключа по этой формуле, иначе итерации холостые.
* `char_parity` = `min(chars)/max(chars)`. Чинится **без изменения числа слов** — заменой
  слов на более длинные синонимы («термин» → «терминологию»). Это единственный способ,
  когда `word_parity` и `ratio` уже на месте.
* `MAJORITY` — строгий максимум практически без пола (срабатывал на `0.345 > 0.333`).
  Чинится **удалением дословного эха ключа у дистрактора**, а не правкой ключа.
* `COST` срабатывает только при `key > 0 and all(wrong == 0)` — добавить цену дистрактору
  всегда безопасно.
* `SENTS` — сделать число предложений неуникальным у ключа: делить/сливать предложения
  **у дистрактора**.
* **Таблично-сравнительные блоки: раскладка 2-2.** Каждая строка сравнения неверна ровно
  у двух опций из четырёх. Тогда поклаузное голосование не даёт сигнала, а у каждой опции
  сохраняется своя основная ошибка — секции остаются валидными.
* Ключ не должен быть строгим максимумом ни по числу `;`-пунктов, ни по длине: разница
  даже в 1–3 слова цитируется слепым ревьюером как «самый полный вариант».
* **Правка текста опции молча ломает её секции.** Ни один гейт этого не ловит. После любой
  правки перечитывать все 4–5 секций опции и приводить их в соответствие.

### 5d. Насыщение регулярных гейтов (измерено 2026-08-05, S3+S4)

Тот же файл доведён до **34/34 clean по всем трём сканерам** (`validate_v3` 0 ERROR,
tell_pct 0.0; `leak_scan` 0 утечек по 21 классу; `form_scan` 0 HARD по 12 классам),
risk 1540 → 40. Два новых независимых слепых ревью дали **34/34 и 34/34** — против
планки ≤ 45 %. Ревьюер A: `FORM_COUNT=33`, единственный `GUESS` — Q13. Ревьюер B:
`SIGNAL_COUNT=34`, «эталон» — Q10 и Q28.

Гейты насыщены: остаточные утечки семантические и прагматические, а не лексические.

**Шесть классов формальной решаемости, не ловимых регулярками:**

1. **Многочастный стем.** Ключ — единственная опция, отвечающая на все части; дистракторы
   усечены или сливают части. Q3, 5, 6, 11, 15, 17, 19, 21, 24, 26, 32.
2. **«Слишком хорошо, чтобы быть правдой».** Дистрактор, полученный инверсией факта, обещает
   отсутствие цены («почти бесплатны», «лага не бывает», «Saga атомарна»). ~20 вопросов.
3. **Отрицание посылки стема.** Стем спрашивает «почему X — anti-pattern» → опция «ничего
   не ломается» неверна по построению. Q4, 5, 6, 17, 32, 33.
4. **Ядовитый хвост.** Дистрактор на ~80 % лексически совпадает с ключом плюс одно
   абсурдное последнее предложение. Q29 D, Q30 C/D, Q14 D, Q34 A.
5. **Кросс-вопросная согласованность.** Сводные/табличные вопросы бесплатны после ответа
   на предыдущие. Q12 решается из Q7 и Q8.
6. **Длина и перечислимость** на вопросах-списках: «бери самый длинный» даёт 3/3 на Q4, Q14, Q34.

**Уточнённая корневая причина.** «Асимметрия авторской инвестиции» — симптом. Причина в том,
что **дистракторы строятся как отрицание или усечение ключа, а не как самостоятельные
правдоподобные инженерные позиции**, а экспозиционный стем делает ключ единственной полной
экспозицией по построению.

**Проверенное лекарство — сценарный шаблон Q13.** Все четыре опции в строго параллельной
форме: `Это <термин>: <механизм>. Полку держит <X>. Лечат <рецепт>.` Различает их один
конкретный факт, а не полнота охвата. Именно эти блоки (Q10, Q13, Q28) ревьюеры назвали
единственными нерешаемыми.

**`audit/mcq/form_scan.py` — обязательный гейт наравне с `validate_v3` и `leak_scan`.**
Приёмка: ноль HARD-классов (`SOFT_CLASSES = {"SENTODD"}` не блокируют).

## 5e. Механика гейтов и правила авторинга, выведенные на волнах C1–C6

Раздел фиксирует то, что многократно стоило переделок. Всё проверено численно
на `databases/cockroachdb-interview.json` (24 блока, итог: tell 0.0, anti-tell 0.0,
masked form-blind 33.3 % при потолке 45 %).

### 5e.1. Правило «платы» — главный содержательный дефект дистрактора

У ключа «плата» почти всегда настоящий инженерный компромисс. У слабого дистрактора
она вырождается в шаблон: «ручное сопровождение», «ещё одно звено», «ещё одна точка
отказа», «риск незавершённого изменения», затасканный «перерыв в обслуживании».

Вырожденная плата — **содержательная подсказка, которую не ловит ни один сканер**:
кандидат отбрасывает вариант, не разбираясь в механизме. Требование: у каждого
дистрактора плата должна быть таким же честным компромиссом, как у ключа, и не
должна опровергать сам предлагаемый рецепт.

### 5e.2. Заимствованный механизм — сильнейший вид дистрактора

Лучший дистрактор описывает **реальный механизм другого продукта**, приложенный к
этой системе: 2PL с разделяемыми блокировками чтения, внешний XA-координатор,
TrueTime commit-wait, централизованный оракул отметок, MVCC-раздувание, undo-log
откат, сброс грязных страниц, тайм-аут простоя в пуле соединений, флаги возможностей
на каждом узле, перестроение системного каталога, кворум версии по большинству узлов.

Правило: **один заимствованный механизм — один раз на файл**. Повтор превращается
в узнаваемый штамп.

### 5e.3. Где что живёт (иначе `AttributeError`)

| Функция | Модуль |
|---|---|
| `_arity`, `_stems` | `audit/mcq/form_scan.py` |
| `_entities`, `_mentions`, `_enum_score` | `audit/mcq/leak_scan.py` |
| `analyze_block` | `audit/mcq/validate_v3.py` |

`analyze_block(opts)` принимает **список словарей-опций, отсортированный по `order`**,
а не блок: `analyze_block(sorted(b['options'], key=lambda x: x['order']))`.

`validate_v3.py --file` принимает путь **относительно `seed/mcq/`**
(`databases/cockroachdb-interview.json`), а не от корня репозитория.

Обёртки `/tmp/mcqwork/{check,leakcheck,formcheck}.py` резолвят `audit/mcq/*` относительно
CWD → запускать только из корня репозитория, **без префикса `cd` в том же вызове**.

`grep` по `audit/mcq/` обязан исключать `audit/mcq/out/` (там генерируемый
`validator_v3.json` на 5.3 МБ).

### 5e.4. Формулы, которые надо знать до, а не после правки

**Anti-tell** (`validate_v3.py:176-179`):

```python
tells = [k for k in TELL_KEYS if cf[k] > 0 and all(o[k] == 0 for o in of)]
anti  = [k for k in TELL_KEYS if cf[k] == 0 and all(o[k] > 0 for o in of)]
```

Ловушка, реально сработавшая на Q5 волны C5: переформулировка ключа сняла его
единственное отрицание («не меняется» → «остаётся неизменным»), у всех трёх
дистракторов отрицание было — мгновенный `anti_tells: ['NEGATION_COUNT']`.
**После любой правки ключа пересчитывать anti-tell, а не только tell.**

**`ENTITY`, `STEMCOVER`, `ARITY` срабатывают по строгому `>`.** Значит, чинить их надо
**подъёмом дистрактора до ничьей**, а не ослаблением ключа: ничья гейт проходит.

* `_stems` — слова `≥5` символов, обрезанные до **первых 5 букв**; `scov` считается
  **только по тексту опции, секции не участвуют**. `STEMCOVER` требует ещё и `scov[key] >= 3`.
* `_mentions(opt, ent)` — **простое вхождение подстроки**: словоформы не совпадают
  («возможностей» не содержит «возможности», «прежнее» не содержит «прежнюю»).
  Развести сущность можно синонимом («возможности» → «свойства»), не трогая длину.
* `_arity` — предложения + `;` + `,\s+а\s+` + `\bи\s+(?=[а-яё])`. То есть `", и <кириллица>"`
  стоит 1, `", а "` стоит 1. Замена `«сходятся …, и владелец»` → `«приходят …, поэтому
  владелец»` снимает единицу арности.
* `_enum_score` — `;` + `:` + `\b\d\)` + ENUM_HINT. **Одно двоеточие в ключе валит
  сразу `TELL:COLON_COUNT` и `ENUM:1>0`.** В секциях двоеточия безопасны — секции
  меряются только числом слов.
* `REDUCTIVE` срабатывает, лишь когда у ключа 0 и у **всех** дистракторов >0 — ключ
  со словом «лишь» безопасен.

**Ловушки словарей и счётчиков, стоившие отдельного круга правок (волна S5):**

* `HEDGEQ` (`leak_scan.py:91`) сопоставляется **вхождением подстроки**, а не по границе
  слова, и элемент `"порядка "` ложно срабатывает на родительном падеже слова «порядок»
  («порядок сложения» безопасен, «порядка редукции» — уже хедж). Родственный набор
  `HEDGES` меряется по границе слова и включает `только`, `всегда`, `никогда`, `может`,
  `явно`, `обычно`, `напрямую`, `любой`. **Ключ не имеет права нести эти слова, даже если
  формулировка дословно взята из существующего дистрактора** — при перестановке механизмов
  между метками это самый частый источник свежего `LEAK`.
* `«и потому»` попадает под `\bи\s+(?=[а-яё])` и **молча добавляет +1 к `_arity`**.
  Замена на `«поэтому она»` снимает единицу, не меняя числа слов.
* Слова считаются `split()` по `\S+`, поэтому **тире `—` — самостоятельный токен**.
  Его добавление или снятие сдвигает `word_parity` и `correct_ratio`.

**Списки-словари** (`validate_v3.py:48-55`) сопоставляются по границе слова:
«явным» ≠ «явно»; «всё» / «всей» / «весь» / «полного» **не** ABSOLUTES, а «все» / «всех» —
да, в том числе с заглавной в начале предложения; в NEGATIONS элементы с хвостовым
пробелом («не ») — слово целиком, без пробела («невозмож») — префикс основы.

### 5e.6. Процедурные правила волны

1. **До проектирования волны выгрузить существующие заголовки `## Q` файла** — иначе
   новый вопрос дублирует уже имеющийся (так родились DUP-кластеры Q3/Q18 и Q13/Q14).
2. **Перед правкой запустить диагностику**, импортирующую `leak_scan` / `form_scan` и
   печатающую по-полевые счётчики. Не оценивать на глаз: пороги флипают ровно на границе
   (`cp=0.7849` при пороге `0.79`), нужен буфер.
3. **Правки шипнутого генератора делать keyed-патчем `(q, label, field) → text`**, а не
   текстовым якорем по исходнику: якорь молча промахивается.
4. Заголовок `## Q<N>` в `.md` — **это и есть видимый пользователю вопрос**;
   `question_text` в JSON не отображается. Менять оба (`apply2.py` делает это сам).
5. Сценарный критерий заголовка: `"?" in title and len(title.split()) >= 12`.
6. **Перенос ключа на другую метку делается перестановкой механизмов, а не флагов.**
   `check.py` и `apply2.py` адресуют записи парой `(q_number, label)` и требуют
   `assert f in o["sections"]`, поэтому переставить сам `correct` они не могут. Метка,
   на которой стоит `correct`, получает истинный механизм и 5 полей роли «верный»;
   вторая метка получает ложный механизм и 4 поля роли «неверный». `answer_dist` при этом
   не меняется, хирургия по схеме не нужна.
7. **После правки ключа обязателен ручной прогон по секциям нетронутых соседних опций.**
   Регулярные гейты не видят содержательного противоречия. На волне S5 так найдены два
   дефекта, которые иначе уехали бы молча: `how_it_should_be` соседа предлагал проверку,
   которая при новом ключе не работает, и `example` ключа в одном предложении утверждал
   и правку на стороне библиотеки, и её отсутствие.
8. Временные файлы волны — только в `/tmp/mcqwork` и с уникальным префиксом волны.
   Имена `mk_s5.py` / `s5.json` заняты старой волной `database-sharding`; совпадение имени
   молча подсовывает чужой патч.

### 5e.7. Валидность form-blind замера

**Просить сильную модель «представь, что не знаешь эту технологию» — сломанный прибор.**
Замер на cockroachdb дал `24/24 = 100 %`, и обоснования агента прямо выдавали
содержательное рассуждение («совместим с премисой "без остановки записи"»).
Модель не может «разузнать» домен по инструкции.

Единственный валидный инструмент — форм-слепок `audit/mcq/blindform.py` (постоянный
инструмент репозитория, не временный скрипт):

```
python3 audit/mcq/blindform.py --file <category>/<topic>-interview.json > /tmp/mcqwork/bf.txt
python3 audit/mcq/blindform.py --file <category>/<topic>-interview.json --keys | tail -1
```

Содержательные слова заменяются на псевдослова **детерминированно по 5-буквенной основе
и с сохранением длины слова**, отдельной маской на каждый блок. Сохраняются ровно те
признаки, по которым ключ вычисляться не должен: число слов и символов, число предложений
и запятых, сочинительные связки, оговорки, абсолюты и отрицания (список `KEEP` оставляет
их дословно), лексическое эхо между стемом и вариантом. Стем берётся из заголовка
`## Q<N>` парного `.md` — то есть ровно тот текст, который видит пользователь.

Ревьюеру отдаётся файл **без** строки `KEYS=`; ключи держатся отдельно и сверяются после.

Уровень случайного угадывания — **25 %**, потолок приёмки — **≤ 45 %**. Замеренные
значения: cockroachdb 33.3 %, mlops 28.6 %, scala 27.5 %. Смотреть надо не только на общую
долю, но и на самоотчёт ревьюера: подвыборка «где был сигнал» с долей заметно выше общей
означает остаточную формальную подсказку, даже если общий процент в норме.

## 5f. Регистр «чистой прозы» и механический form-blind (волны S1–S5, service-discovery)

Раздел выведен на `architecture/service-discovery-interview.json` (30 блоков,
risk 1373 → 45, `passed 30/30`, `secp_med 0.7778`, `answer_skew 1.14`, механический
form-blind **9.3 %** при потолке 45 %). Каждый пункт стоил отдельного круга правок.

### 5f.1. Регистр опции

Все четыре опции блока пишутся **одинаково и без исключений**:

- чистая русская проза: ни названий продуктов, ни кодовых спанов, ни цифр, ни версий;
- ровно **два предложения**;
- предложение 1 — утверждение о механизме;
- предложение 2 — `«<Средство> <делают> настройкой, платой станет <цена>.»`

Регистр снимает разом целый класс `TELL` (`CODE_TOKEN_COUNT`, `NUMBER_COUNT`,
`VERSION_MARKER_COUNT`, `ARROW_COUNT`, `QUOTE_COUNT`) — ни один из них не может сработать,
если ни в одной опции нет ни кода, ни цифр. Побочный эффект: `char_parity` держится
сам собой, потому что опции перестают различаться длиной идентификаторов.

Бюджет этого регистра **короче**, чем в §5e.5: опция 30–33 слова, ключ 88–97 слов
секций на 5 полей, каждый дистрактор 72–80 на 4 поля → `secp 0.75–0.82`.
Ключ, уехавший к 100 при дистракторах под 72, роняет `secp` до 0.68–0.70.
По-полевые цели ключа: `explanation` 30–33, `example` 16–18, `when_to_apply` 18,
`edge_cases` 16–17, `related` 12–14. Поля дистрактора — по 18–20.

### 5f.2. STEMCOVER и ARITY: измерять, а не угадывать

`form_scan` сообщает `STEMCOVER` и `ARITY` **только при строгом единственном максимуме**.
Отсюда универсальное лекарство: **поднимать дистрактор, а не срезать ключ** — ключу
достаточно перестать быть единственным максимумом, ничья гейт не зажигает.

`form_scan._stems` усекает значимые слова **до 5 букв, но только те, что длиннее пяти**.
Слова короче не усекаются, поэтому словоформы не схлопываются: слово стема «сеть»
**не** совпадёт с «сети» в опции. Три правки `STEMCOVER` подряд, сделанные по догадке,
дали два попадания и один промах ценой целого круга. Обязательная процедура — до правки
напечатать множество основ и пересечения по каждой опции:

```python
import sys; sys.path.insert(0, "audit/mcq"); import form_scan as fs
S = set(fs._stems(stem))
for lab, t in opts: print(lab, sorted(S & set(fs._stems(t))))
```

Контраст: `leak_scan._entities` **не** делает стемминга вовсе — там сравниваются точные
словоформы.

`_arity` считает предложения плюс `;`, `,\s+а\s+` и `\bи\s+(?=[а-яё])`. Союзы «но»,
«поэтому», а также двоеточие и голая запятая — бесплатны. Замена «но» → «, а» или
«поэтому» → «и» поднимает арность на единицу при нулевой цене в словах.

### 5f.3. Отсеивание даром — дефект, невидимый всем гейтам

Дистрактор, который **прямо противоречит факту, названному в самом стеме**, отсеивается
чтением одного предложения: кандидат сокращает выбор с четырёх до трёх, ничего не зная
о предмете. На волне S5 так вышел вариант «правило заведено лишь на входном узле» при
стеме «…хотя правило заведено на обе одинаково». Механизм заменён на обход разбирающего
слоя прямым адресом — стему это не противоречит, а проверяется он тем же журналом.

Проверка: прочитать стем и каждый дистрактор подряд, спрашивая «отсеивается ли он
без знания предмета». Ни один регулярный гейт этого не ловит.

### 5f.4. Гигиена оговорок и абсолютов

`HEDGES` и `ABSOLUTES` сверяются **по границам слов**, поэтому `только`, `при этом`
и `напрямую` считаются оговорками, а `все` и `всех` — абсолютами (но `всеми`, `каждого`,
`любому`, `всё` — нет). Замены, сохраняющие число слов:
`все → каждый`, `всех → каждого`, `только → лишь / зато`, `при этом → в ходе / заодно`,
`любой → каждый`, `напрямую → в обход <чего-то> / мимо него`.

Отдельный дефект: оговорки и абсолюты, сосредоточенные **в одних дистракторах**, дают
подсказку на выбывание; оговорка, стоящая в тексте **единственной** из четырёх опций, —
тоже. Скан гоняется по всему патчу разом, ключом `(q, label, field)`, и заодно ловит
CJK, латиницу и цифры, случайно занесённые ручным `Edit`.

### 5f.5. Механический form-blind вместо «представь, что не знаешь»

К форм-слепку `blindform.py` (§5e.7) добавляется **детерминированный ансамбль
эвристик по форме**: для каждого блока считаются `longest_words`, `longest_chars`,
`shortest_words`, `most_commas`, `most_clauses`, `most_hedges`, `most_stemcover`,
`most_negations` и две позиционные (`B`, `C`). Эвристика «попадает», только если её
максимум единственный и совпал с ключом.

Прибор объективен, воспроизводим и не требует второй модели. Уровень случайного
угадывания — 25 %, потолок — 45 %. Замер на service-discovery: все содержательные
эвристики 0–16.7 %, позиционные 23.3–26.7 %, среднее по ансамблю **9.3 %**.
Позиционные обязаны сидеть возле 25 % — это контроль корректности самого прибора.

### 5f.6. Форм-решатель — главный дефект корпуса (измерено 2026-08-07)

Решатель, который **не читает текст**, а только меряет его, берёт ключ в
**58.3 % корпуса** (6769 блоков, случайность 25 %). Правило решателя: взять опцию
с наибольшим числом слов, при равенстве — с наименьшим числом символов. Двенадцать
нетронутых файлов `ai-ml` решаются им на **100 %**. Это ровно тот дефект, который
задан в цели как недопустимый: «заметить самый длинный вариант».

Причина не в небрежности, а в жанре: ключ описывает настоящий механизм простыми
короткими словами, дистрактор — сложными составными оборотами, поэтому по словам
ключ выходит длиннее, а по символам короче. `word_parity ≥ 0.81` этого не ловит:
при опции в 35 слов порог допускает разброс до 6 слов, чего решателю хватает.

`validate_v3.analyze_block` считает поле `formsolve` — список из пяти решателей,
попавших в ключ: `maxw_minc`, `maxw_maxc`, `minw_minc`, `maxc`, `minc`. Блок проходит
гейт только при **пустом** `formsolve`; файловые агрегаты — `formsolve_pct` (головной
решатель) и `formsolve_any_pct`; в `risk` вклад `300 × доля блоков с непустым списком`.

Правило авторинга, которое закрывает все пять решателей разом:

> **Равное число слов у всех четырёх опций, ключ — второй или третий по символам.**

При равенстве слов словесные решатели вырождаются в символьные, и объединение всех
пяти сжимается до двух опций — самой длинной и самой короткой по символам. Ключу
достаточно не быть ни той, ни другой. Побочно это даёт `word_parity = 1.0` и
`correct_ratio = 1.0`, то есть три гейта закрываются одной правкой.

Порядок подгонки: сперва выровнять слова (добавлять их дистрактору, а не резать
ключ — иначе едет `correct_ratio`), затем двигать символы ключа внутрь коридора
заменой слов на синонимы другой длины **без изменения их числа**.

### 5f.7. Двойной `(!)` — ловушка `apply2.py`

Маркер сложности `(!)` живёт **только** в заголовке `## Q<N>` в `.md`; в JSON
`question_text` его быть не должно. `apply2.py` сам сохраняет префикс заголовка, поэтому
запись `mdhead`/`stem`, в тексте которой уже стоит `(!)`, даёт в заголовке `(!) (!)`.
Писать стем без маркера; после применения волны проверять `grep -n '(!) (!)'` по `.md`
и `question_text.startswith('(!)')` по JSON.

### 5f.8. Приёмы «почини не ключ, а дистрактор» (волна CT, 2026-08-09)

Гейты `ENTITY`, `STEMCOVER`, `ARITY` срабатывают по строгому `>`, то есть **ничья
проходит**. Отсюда правило: если ключ вырвался вперёд на единицу, дешевле поднять
дистрактор до ничьей, чем резать ключ, — правка ключа тянет за собой символьную
лестницу и `correct_ratio`, правка дистрактора почти всегда локальна.

| Гейт | Приём | Цена |
|---|---|---|
| `STEMCOVER` | заменить в ключе слово, дающее совпадение основы, равнодлинным синонимом без совпадения (`читаемых` → `надобных`) | 0 слов, 0 символов |
| `STEMCOVER` | добавить недостающую основу в дистрактор подменой клаузы, подобранной символ-в-символ (`и в сводку у посредника он не попал` → `и поверка у посредника его же не берёт`, обе 8 слов / 36 символов) | 0 слов, 0 символов |
| `ENTITY` | склонить упоминание в ключе прочь от точной формы стема: `_mentions` — сырой поиск подстроки, поэтому `на окружении` из стема не находится в `на окружениях` ключа | +1 символ |
| `CLONE` | заменить в **дистракторе** общее с ключом слово на слово ≤ 3 символов (`мимо` → `вне`): `_content` берёт только слова от 4 символов, поэтому токен исчезает из пересечения целиком | −2 символа |
| `CLONE` | заменить в ключе общий токен на уникальный синоним (`правкой` → `переписью`, `особом` → `отдельном`): снижает `|K ∩ D|`, не трогая `|K|` | +2 / +3 символа |

Обратная зависимость `CLAUSEMAJ`: `_jac = |∩| / (|A| + |B| − |∩|)`, поэтому
**сжатие сегмента ключа поднимает жаккар**. Лечится не сокращением, а удалением
одного общего токена из нулевого сегмента ключа, чтобы сегмент совпадал не более
чем с одним чужим.

### 5f.9. Длина секций ключа — стилевой, а не решательный дефект

Метрика `sec_correct_longest_pct` (доля блоков, где блок секций ключа — самый
длинный) на всех проверенных ранее принятых файлах равна **100.0 %**
(scala, cockroachdb, mlops, ansible, serverless). Это системная норма корпуса,
а не регресс отдельного файла.

Эксплуатировать её на решении **нельзя**: секции рендерятся только на `result.html`,
то есть после отправки ответа (`explanation-panel`, `distractor-panel`). Решатель их
не видит. Поэтому связывающий гейт — `sec_parity ≥ 0.70` (равномерность разбора,
§8), а не «ключ не самый длинный».

Тем не менее при переработке файла стоит держать блок секций ключа не длиннее
самого длинного дистрактора: это признак того, что разбор неверных вариантов
написан так же содержательно, как разбор верного, а не отпиской. Рабочие рычаги —
снять из `explanation`/`example` ключа предложные группы, чей референт уже задан
стемом, и добавить в `what_actually` самого короткого дистрактора вставки
`самими` / `самой` / `того`.

## 6. Фактическая точность — иерархия источников

Спецификация → официальная документация → Javadoc / API reference → исходный код →
release notes → migration guide → design doc → материалы создателей.

Запрещено выдумывать версии, таймауты, размеры, гарантии, исключения, результаты
бенчмарков. Если факт не подтверждён — вопрос переписывается на подтверждаемый.

* **Версии.** Указывать мажор, если поведение введено в мажоре (`Spring Security 7`,
  не «7.1»). Не приписывать фичу более ранней версии.
* **Числа.** Любое число в тексте опции должно быть проверяемым и осмысленным.
* **Код.** Примеры должны компилироваться концептуально: реальные имена классов,
  методов, аннотаций, свойств.
* **Knowledge cutoff.** Не сочинять факты о релизах после известного среза; при
  сомнении — проверять через `context7` (MCP) по официальной доке.

## 7. Измеримые пороги (метрики §32)

Считает `audit/mcq/validate_v3.py` (весь корпус, 318 файлов). Метрики per-block по 4 опциям:

`CHAR_COUNT`, `WORD_COUNT`, `SENTENCE_COUNT`, `COMMA_COUNT`, `COLON_COUNT`,
`SEMICOLON_COUNT`, `DASH_COUNT`, `PAREN_COUNT`, `QUOTE_COUNT`, `CODE_TOKEN_COUNT`,
`NUMBER_COUNT`, `VERSION_MARKER_COUNT`, `ABSOLUTE_MARKER_COUNT`, `HEDGE_MARKER_COUNT`,
`NEGATION_COUNT`, `LIST_MARKER_COUNT`, `METHOD_COUNT`, `ANNOTATION_COUNT`,
`GENERIC_COUNT`, `ARROW_COUNT`, `TECH_TERM_DENSITY`, `LEN_AVG`, `LEN_SPREAD`,
`COMMA_GAP`, `UNIQ_MARKER`.

| Гейт | Порог | Смысл |
|---|---|---|
| `word_parity` = min/max слов | **≥ 0.81** | ни одна опция не выбивается по длине |
| `char_parity` = min/max символов | **≥ 0.79** | то же в символах (ловит backtick-спаны) |
| `correct_ratio` = correct / mean(3 других) | **0.95 – 1.05** | correct не длиннее и не короче |
| длина опции | **22–65 слов**, целевой коридор **28–48** | ниже 22 — заглушка, выше 65 — конспект |
| `format_tells` | **пусто** | correct — не единственный носитель признака |
| `anti_tells` | **пусто** | признак есть у всех дистракторов и нет у correct |
| `sec_parity` (сумма слов секций) | **≥ 0.70** | секции correct не заметно богаче |
| обрыв текста | **0** | `«…; CapWord.»` и прочие усечения |
| шаблонные фразы | **0** | см. §8 |
| распределение A/B/C/D по файлу | перекос **≤ 1.6×** | правильный не «всегда B» |

**Пороги не ослабляются.** Исторический блокер BLK-001 («абсолютные пороги
недостижимы, эталон batch-01 сам их не проходит») закрыт в пользу переписи контента:
слабый контент не сохраняется ради минимизации diff, batch-01 перерабатывается наравне
со всеми.

### Две зеркальные ловушки

1. **Tell** — correct длиннее/полнее (`uniq_longest`, `correct_ratio > 1.05`).
   Лечится подъёмом дистракторов.
2. **Anti-tell** — correct КОРОЧЕ дистракторов (`correct_ratio < 0.95`,
   `uniq_shortest`). Встречается реже, но огульная эвристика «сократить correct»
   делает такие файлы хуже. Всегда смотреть направление до правки.

**Подсказка по длине в символах — третья, отдельная.** Паритет слов бывает чистым
(`uniq_longest_pct` низкий), а ключ при этом остаётся самым длинным на глаз: слова
у него длиннее. Метрика — `uniq_char_longest_pct`. Уровень случая для четырёх
опций — 25 %; приёмка файла требует ≤ 28 %. Лечится подъёмом дистрактора-претендента
**при неизменном числе слов** — тогда `word_parity` и `correct_ratio` не трогаются.

### Практические приёмы (проверены на корпусе)

* Измерять слова/символы Python'ом, не на глаз.
* `correct_ratio` на границе → поднять **самый короткий дистрактор** на +2 слова:
  чинит и ratio, и `word_parity` разом.
* `char_parity` = min/max → поднимать char-min дистрактор так же важно, как срезать
  char-max correct.
* `format_tell` по код-спанам → раздать спаны дистракторам заменой слов **без смены
  word-count**.
* Длинные имена классов/DSL из `explanation` не тащить в текст опции.
* Пороги 0.81/0.79 флипают ровно на границе — целиться в 0.82+/0.80+.
* Хедж-скан строго по границе слова: «возможно» ⊂ «невозможно» даёт ложные срабатывания.
* Перед завершением файла — скан на CJK/иероглифы и англ. «here» во всём блобе.

## 8. Секции

Правильный ответ (5 полей):
* `explanation` — механизм, почему это верно. Не пересказ текста опции.
* `example` — конкретный сценарий/фрагмент, а не «например, в проекте».
* `when_to_apply` — когда знание применяется на практике / на интервью.
* `edge_cases` — граница, исключение, цена решения.
* `related` — вики-ссылки `[[<topic>#Q<N>]]` на **существующие** номера этого файла.

Неправильный ответ (4 поля):
* `what_actually` — как на самом деле, с явным называнием подменённого факта.
* `source_of_confusion` — откуда взялось заблуждение (какая похожая вещь спутана).
* `if_it_were_true` — следствие, если бы утверждение было верным.
* `how_it_should_be` — корректная формулировка.

**Запрещённые шаблонные фразы** (auto-reject): «Это распространённое заблуждение»,
«На самом деле механизм работает иначе», «Правильный ответ описывает основную
концепцию», «Это смежное, но отличное понятие», «Частая ошибка в реальном коде»,
«Неправильный вариант 1/2/3».

**Паритет секций.** Секции correct не должны быть заметно длиннее, точнее,
структурнее; correct не должен быть единственным, у кого есть пример / версия /
граничный случай.

## 9. Таксономия дефектов (классы, найденные на корпусе)

1. **dual-correct by near-copy** — дистрактор почти дословно повторяет correct.
2. **dual-correct by over-correct distractor** — дистрактор фактически полностью верен.
3. **dual-correct via section-desync** — текст опции когда-то починили до фактически
   верного, а её wrong-секции продолжают опровергать СТАРЫЙ миф.
4. **factual error в самом correct**.
5. **truncation / corruption текста** (обрыв, осиротевший хвост `«; Word.»`).
6. **lone-complete (доминирующий)** — correct полное определение, дистракторы
   однострочники. Самый частый визуальный tell корпуса.
7. **anti-tell** — correct короче дистракторов.
8. **DUPSEC — совпадающие значения секций между вопросами файла** (найден на файле 15,
   5 случаев). Один и тот же миф законно повторяется дистрактором в разных вопросах,
   и обобщённо написанная секция становится побайтово одинаковой. Ни `validate_v3`,
   ни `leak_scan`, ни `form_scan` этого не видят — гейты поблочные. Ловится только
   файловой батареей: собрать все значения `sections` по файлу и потребовать
   уникальности каждой пары «поле → значение».
   **Лечение:** переписать ПОЗДНЕЕ вхождение под сюжет именно его вопроса,
   **сохранив точное число слов**, иначе поедет `sec_parity` блока.
   Прямое следствие требования §4 задания: секция не должна содержать
   «универсальный текст, пригодный для соседнего вопроса».

**Приём устранения dual-correct:** внести в переусердствовавший дистрактор
**решающую объективную ошибку** и переписать его wrong-секции под неё. НЕ смягчать
correct. Длину по возможности сохранять, чтобы паритет блока не поехал.

**Ложные срабатывания сканов:**
* русские родительные окончания `-а/-и` ловятся регуляркой обрыва — читать предложение
  целиком, регулярке не верить;
* блоки «выбери значение параметра» (`acks=X`, `auto.offset.reset=X`) имеют 4 почти
  одинаковые опции **by design** — в whitelist.

## 10. Цикл обработки одного файла

Один файл закрывается ПОЛНОСТЬЮ за проход; дробить файл по вопросам между проходами
нельзя, переключаться между файлами на середине — нельзя.

1. Анализ — прогон `validate_v3.py --file <rel>`, чтение файла целиком.
2. Проект нового набора вопросов (покрытие темы, дубликаты, перегруз, порядок).
3. Полная перепись — тексты опций, секции, при необходимости стем и состав вопросов.
4. Автопроверки — схема, структура, метрики §7.
5. Fact-check всех correct (§6), при нужде через `context7`.
6. Ручной контент-аудит.
7. Ручной визуальный аудит (one-line test §2).
8. Слепое ревью: два независимых прохода без поля `correct`; расхождение с ключом или
   между проходами = дефект.
9. Adversarial review — попытка сломать: два верных, ни одного верного,
   противоречие текста и секций, устаревший факт.
10. Приёмка: все гейты §7 зелёные, blind сходится, fact-check без открытых вопросов.
11. Файловая батарея (то, чего не видят поблочные гейты): схема `mcq-schema.json`,
    непрерывность `q_number`, сортировка `options` по `order`, ровно один `correct`,
    ролевой набор ключей секций, выравнивание с `## Q<N>` шпаргалки,
    **DUPTEXT / DUPSTEM / DUPSEC** (§9.8), распределение меток по файлу.

**После ЛЮБОЙ правки — полная переверификация файла**, а не только тронутого блока.

**Фан-ауты > ~10 агентов запрещены** (session limit): подтверждено эмпирически —
массовый workflow на 214 агентов завершил 24. Полный аудит файла делает главный цикл.

## 11. Приёмка батча и банка

* Файл считается готовым только в статусе `AUDITED` (см. `docs/mcq-refactoring-state.md`).
* Эталон качества — не «batch-01» как таковой: замеры показали, что **batch-02
  доминирует batch-01 по всем четырём метрикам** (wp 0.850 против 0.818, cratio 0.952
  против 1.062, uniq-long 14.6% против 38.3%, tell 27.2% против 44.3%). batch-01 узок
  тематически (9 Spring + 1 Java) и несёт собственный однородный tell-стиль.
  Дефекты эталона не воспроизводятся, эталон дорабатывается наравне с остальными.
* Кросс-файловый аудит банка: дубликаты вопросов между файлами, противоречия фактов
  между темами, единообразие терминологии и оформления версий.
