# Стандарт качества MCQ

Действующий контракт содержания и приёмки, актуализирован 2026-09-14.
Процесс для любой LLM: [PROMPT_PLAN_INTERVIEW](../PROMPT_PLAN_INTERVIEW.md).
Состояние и результаты аудита: [mcq-refactoring-state](mcq-refactoring-state.md).

## Приоритет правил

Фактическая точность → единственный защитимый ответ → связь с видимым вопросом и
прочитанной теорией → согласованность объяснений → правдоподобие дистракторов →
естественный язык → сопоставимая форма → числовые метрики.

Код определяет, что видит пользователь; первичные технические источники определяют,
что верно. Ошибка в теории не становится истиной из-за того, что её повторяет MCQ.
Старые журналы, номера ROUND и результаты сканеров не переопределяют этот контракт.

## Структура и фактическая поверхность

Варианты и объяснения находятся в `modules/quiz-app/src/main/resources/seed/mcq/`,
теория — в `cheatsheets/interview/`. Пара имеет одинаковый относительный путь.
Ключ блока: относительный путь темы + `q_number` + `block_idx`.
`topic_slug` совпадает с именем JSON без расширения.

Пользователь получает вопрос из заголовка `## Q<N>` Markdown. `question_text` JSON
десериализуется, но `McqJsonLoader.buildDesiredOptions` не записывает его в БД.
Он не может содержать единственное условие, оправдывающее правильный вариант.

Схема `mcq-schema.json` определяет разрешённые поля и типы. Дополнительные инварианты:

- последовательности `q_number` JSON и реальных заголовков Markdown совпадают;
- номера вопросов уникальны; существующие номера не перенумеровываются ради заполнения пробелов;
- индексы блоков внутри вопроса уникальны, упорядочены и начинаются с нуля;
- в каждом блоке четыре варианта, ровно один `correct: true`;
- `order` равен `[0,1,2,3]`, `label` равен `[A,B,C,D]` в том же порядке;
- тексты вариантов различаются; пустые и состоящие из пробелов значения запрещены;
- дубли ключей JSON, не-JSON числа и NUL в тексте отклоняются;
- строку Java `\u0000` записывают в JSON как `\\u0000`, чтобы показать обозначение, а не NUL;
- inline MCQ в Markdown не создаются; inline Markdown в текстах вариантов сохраняется.

`mcq_validation.py` проверяет эти инварианты и игнорирует заголовки-примеры внутри
fenced-блоков так же, как Java-парсер. Для внешних fixtures без production-пути связь
с теорией явно `NOT_RUN`, а не подтверждена автоматически.

## Смысл вопроса и локальная обучающая связь

MCQ закрепляет материал соответствующего Q. Правильный ответ и опровержения всех
дистракторов должны выводиться из его вопроса и тела, без скрытого знания соседнего Q.
Технические факты теории проверяются по первоисточникам. Если требуется исправить
теорию, перечитываются зависимые варианты и объяснения.

Шкала связи сохраняется: L4 — прямое следствие материала; L3 — корректный парафраз;
L2 — необходим внешний факт; L1 — совпадает только тема; L0 — другой вопрос.
L3/L4 подтверждает рецензент. Лексическое пересечение не доказывает этот уровень.

Не превращать все вопросы в искусственные диагностические сценарии, не удалять
имена API и не заменять технические термины архаизмами. Сложность должна соответствовать
материалу и проверяемому навыку. Число слов в заголовке не является критерием качества.

## Все четыре варианта

По каждому варианту рецензент определяет: верен, неверен, неоднозначен или зависит
от неуказанного условия. Нужно попытаться защитить каждый wrong в условиях вопроса.
Второй защитимый ответ, отсутствие верного ответа и неверный ключ блокируют приёмку.

Дистрактор — правдоподобная ошибочная модель с одним основным заблуждением. Он может
заимствовать реальный механизм соседней системы, но не должен требовать узнавания
необъяснённого названия. Single-Delta относится к смыслу, а не к числу заменённых слов.
Неверность wrong сама по себе НЕ finding. Замена его на истинное утверждение может
создать второй correct. Объяснение должно опровергать именно текущий текст wrong.

Все четыре текста имеют сопоставимый смысловой скелет и формат: одинаковый предмет,
уровень детализации, порядок утверждения/условия/обоснования. Correct не выделяется
единственным полным ответом на все части, единственным кодом, примером или оговоркой.

Это два самостоятельных результата приёмки: **SFPL** (форма/каркас) и **ANSC**
(полнота каждого ответа). Обязателен сравнительный разбор A/B/C/D по
[протоколу формы и полноты](mcq-quality/surface-parity-rules.md). Общая содержательная
вычитка и SKEL PASS не заменяют этого результата. Один полный correct против трёх
поверхностных wrong блокирует приёмку даже при одинаковой пунктуации и числе слов.

Проверять одновременно длину, перечисления, код, числа, версии, скобки, отрицания,
категоричность, причинные связи и качество языка. Подсказкой может быть и самый короткий
ответ. Слабые дистракторы улучшаются содержательно; лишняя лекция из варианта переносится
в объяснение. Не набивать варианты пустыми фразами ради счётчиков.

Запрещена подгонка под известные решатели: специально ставить correct вторым по длине,
склонять слово ради обхода regex, удалять API ради нулевого code-count, копировать
число слов или навязывать всем блокам ровно два предложения. Это создаёт новые признаки
ключа и ухудшает язык. Ничья метрик не доказывает неразличимость по форме.

## Человекочитаемость на русском языке — RU

Отдельный обязательный критерий для видимого вопроса, теории, всех A/B/C/D и всех
объяснений. Текст должен быть понятен человеку при первом последовательном чтении:
естественная техническая терминология, ясные условия и связи, корректная грамматика,
отсутствие канцелярита, искусственных метафор и машинных цепочек. Имена API, код и
общепринятые термины сохраняются. Хороший русский язык обязателен и для correct, и для wrong.

Применяется [протокол RU](mcq-quality/russian-readability-rules.md). RU получает свой
вердикт и покрытие по Q/B, независимо от SFPL, ANSC и фактической корректности.
`readability_precheck: NO_SIGNALS` не даёт RU PASS. Редакторское упрощение сохраняет
технический смысл, ошибочную модель wrong и согласованность sections.

## Объяснения и факты

Correct: `explanation`, `example`, `when_to_apply`, `edge_cases`, `related`.
Wrong: `what_actually`, `source_of_confusion`, `if_it_were_true`, `how_it_should_be`.

Поля раскрывают механизм, пример, границы применимости и конкретное заблуждение.
Контрфактическое объяснение должно быть логически согласованным. Недостающие условия
нельзя вводить только после ответа. Универсальные заглушки и противоречащие друг другу
text/sections блокируют приёмку. После изменения опции перечитываются все её sections
и объяснения остальных вариантов этого блока.

Разные ролевые ключи и число sections допустимы: обучающие объяснения показываются
после ответа. Равенство их длины не требуется для скрытия ключа до выбора.
Ссылки в related должны вести к существующим темам/номерам; пояснение без ссылки
нельзя автоматически объявлять битой ссылкой.

Версии, дефолты, ограничения API, лицензии, рекомендации и примеры сверяются с
официальной документацией, спецификациями или исходным кодом нужной версии.
Для спорного утверждения сохраняются само утверждение, источник, версия и дата.
Отсутствие слова «актуальный» не означает отсутствие зависимости от версии.
Список URL в freshness-sidecar подтверждает наличие записи, а не фактическую проверку.

## Проверки и интерпретация результатов

| Инструмент | Роль | Значение результата |
|---|---|---|
| `bash scripts/verify-mcq-json.sh --all` | Schema + cross-field + Markdown linkage | PASS — структурные инварианты, не содержание |
| `scripts/mcq-tools/gates.sh <seed.json>` | Предпроверки одной темы | 1 — нужны исправления/разбор сигналов; 2 — ошибка выполнения |
| `scripts/mcq-answer-parity-gate.py` | Метрики формы/позиции, наличие freshness | PASS не заменяет чтение вариантов |
| `scripts/mcq-skel-gate.py` | Формальные признаки скелета | Только pre-check; LLM проверяет смысловую структуру |
| `scripts/mcq-linkage-scan.py` | Лексические сигналы drift/coverage | Каждый сигнал исследовать по тексту |
| `scripts/mcq-struct-scan.py` | Статистика формальных решателей | Ничья всех четырёх учитывается как 1/4; порог диагностический |
| `scripts/mcq-struct-report.py`, stamp/surface/structure scans | Дополнительная диагностика | Нулевой exit у отчётного инструмента не равен приёмке |
| `audit/mcq/validate_v3.py`, validate_a/b, leak_scan, form_scan | Исторические измерители | Не обязательный современный gate и не реестр готовности |
| `scripts/mcq-audit.py` | Инвентарь, хеши, привязка заявлений, очередь | COMMIT_MATCH доказывает совпадение файлов, не полноту ревью |
| `readability_precheck` в `mcq-audit.py` | Русская проза: видимый Q, теория, все варианты/sections; эвристики из `audit-mcq-parity.py` | SIGNALS/NO_SIGNALS — диагностика; отдельный RU-вердикт обязателен |

Абсолютные коридоры слов/символов старых волн и потолок blind 45% больше не являются
общими критериями приёмки. Они были подогнаны под отдельные файлы и противоречили
действующим локальным требованиям и качеству языка. Значения старых валидаторов
сохраняются для сравнения; их FAIL не стирается и не превращается в PASS.

Для эвристического false positive сохраняется конкретный блок, правило, объяснение
и результат содержательной проверки. Молчаливые исключения и снижение порогов ради
зелёной таблицы запрещены. Структурные ошибки не допускают редакторского исключения.

## Независимость и слепое ревью

Различаются обычное ревью с ключом, независимое ревью с ключом, слепое содержательное
решение и проверка угадываемости по форме. Модель, уже видевшая ключ, не становится
слепой после инструкции «забудь». Другой провайдер сам по себе не гарантирует независимость.

Экспорт без correct/sections строится от видимого Markdown-заголовка. Ключ держится
в исходниках у принимающей стороны; ревьюеру даётся только экспорт в новом контексте.
Предсказания фиксируются до сравнения с ключом. Старые экспорты с correct_label
не являются пригодными пакетами слепого ревью.

`blindform.py` сохраняет часть слов и кода: это частичная маска, не доказательство
незнания предмета. Для статистики учитывать размер выборки, ничьи, зависимость внутри
темы, число перебранных эвристик и независимую проверочную выборку. Высокая точность
содержательного решения и низкая угадываемость формы — разные показатели.

## Приёмка и инвалидирование

AUDITED означает полный проход всех блоков и четырёх вариантов, фактов, объяснений,
формы, человекочитаемости RU и независимого ревью без открытых блокирующих находок. Автор не присваивает
себе независимый проход. Наличие поля AUDITED или фразы «два чистых круга» не доказательство.

Доказательства привязываются к хешам JSON и Markdown, правилам и охваченным блокам.
Изменение text, key, sections или видимого вопроса инвалидирует зависимые проверки.
Правка unrelated README или смена модели не обнуляет корпус. Изменение стандарта
требует оценки применимости затронутых правил, а не автоматического полного reset.

Один блок/небольшой пакет можно передавать между моделями. Завершение файла требует
покрытия всех его блоков; прерывание оставляет checkpoint, а не выдуманный DONE.
NOT_RUN, FAIL, ERROR, STALE и UNVERIFIED сохраняются отдельно.
