# Состояние продукта

Документ описывает продукт **в текущем виде** — не хронику работ. Если код и документ
разошлись, прав код: обнови документ.

## 1. Что это за продукт

Тренажёр подготовки к техническому собеседованию. Локальное веб-приложение на Spring
Boot + Thymeleaf: банк вопросов (~9.8 тыс.) с разбором, интервальным повторением (SM-2)
и статистикой освоенности тем.

Ключевое отличие от «обычного квиза»: вопрос — не только тест с вариантами. Один и тот
же банк обслуживает восемь режимов работы (см. §3), включая active recall с самооценкой,
свободный ввод ответа и код-челлендж. Варианты ответа поставляются JSON-сидерами
(`seed/mcq/<category>/<topic>.json`); у вопроса без сидера MCQ-путь вырождается во
флешкарту автоматически — это штатное, а не аварийное поведение.

Продукт однопользовательский по умолчанию (`app.security.mode=local`). Multi-режим с
OAuth2 и owner-скоупингом существует, но выключен и в этой переработке не трогался.

## 2. Экраны

| Адрес | Шаблон | Роль |
|---|---|---|
| `/` | `focus-training.html` | Главный рабочий экран: один вопрос за раз. Всё обучение происходит здесь. |
| `/review` | `focus-training.html` | Тот же экран с фильтром «где раньше ошибался». |
| `/stats` | `stats.html` | Аналитика: освоенность тем, серия, активность, слабые темы. Якорь `#topics` — список тем. |
| `/bookmarks` | `bookmarks.html` | Закладки с заметками. |
| `/settings` | `settings.html` | Вкладки Сессия / Оформление; третья, Данные, — только при открытом admin-гейте (см. ниже). |
| `/session-summary` | `session-summary.html` | Итоги завершённой сессии. Переживают перезагрузку и «назад»; стираются стартом новой сессии. |
| `/login` | `login.html` | Только в multi-режиме. |
| `/error` | `error.html` | Единый экран ошибки. |

`/training` — легаси-адрес, редиректит на `/` с переносом whitelisted query-параметров.
Канонический адрес тренировки один.

## 3. Режимы сессии

`InterviewMode`: `TRAINING`, `EXAM`, `MARATHON`, `STUDY`, `FLASHCARD`, `TYPED_RECALL`,
`INTERVIEW`, `CODE_CHALLENGE`.

Разделение, которое важно понимать при правках фокус-экрана:

- **MCQ-путь** — форма `#interview-form` с радиогруппой. Ответ уходит AJAX-ом в
  `/api/answer`, разбор рисует `interview.js`, он же подставляет ссылку «Следующий
  вопрос». Без JS работает серверный `POST /answer` → `result.html`. Оба рендерера
  дают одну разметку и один текст: формулировки собирает сервер (`AnswerCopy`),
  классы разбора общие (см. `frontend-architecture.md` §4).
- **Recall-путь** (`isRecallMode()`) — ответ скрыт, раскрывается по действию, затем
  самооценка 1-4 (`POST /flashcard-grade`) двигает SM-2. Требует **активной сессии**.
- **Browse-флешкарта** — тот же вопрос без активной recall-сессии. Раскрытие делает
  нативный `<details>` (работает без JS), самооценки нет (некуда писать), выход
  дальше — серверная ссылка «Следующий вопрос» (`focusBrowseNextHref`).
- **STUDY** — две подфазы: LEARN (читаем эталон) → `POST /study-confirm` → QUIZ (MCQ).

`TRAINING` сессии не создаёт. Дойти до `/session-summary` можно только из EXAM /
MARATHON / STUDY.

Подпись режима у пользователя **зависит от места**: `STUDY` в конструкторе сессии —
«Изучение», а на рабочем экране в бейдже фазы — «Проверка». Это не рассинхрон, а
причина, по которой подписи режимов живут не в домене, а в `ModeUtils` (критерий —
`backend-architecture.md` §3b). Все они, вместе с подписью кнопки старта и дефолтным
числом вопросов, приезжают на фронт одним списком `${sessionModes}`; своих копий
таблицы режимов ни разметка, ни JS не держат.

## 4. Решения и допущения, принятые в этой переработке

Записаны, потому что не выводятся из кода — это выбор из нескольких допустимых вариантов.

**Навигация — одна.** Топбар раньше дублировал разделы сайдбара icon-only ссылками:
пять пунктов (`/`, `/stats`, `/review`, `/bookmarks`, `/settings`) плюс шестая кнопка
«Выйти» под `th:if="${multiSecurityMode}"`. Две параллельные навигации по одним
адресам: непонятно, какая главная, скринридер объявляет каждый раздел дважды,
клавиатура тратит шесть табов до контента.
Осталась одна — сайдбар, подписанный, с `aria-current`. В топбаре — только прогресс
сессии и тоггл темы (переключатель отображения, а не пункт назначения).

**Тоггл темы — один, в топбаре.** Раньше был и в футере сайдбара, и в топбаре, оба с
`aria-pressed`. Контракт зафиксирован тестом `TemplateFragmentContractTest`: в сайдбаре
его быть не должно.

**Мета вопроса вложена от общего к частному, а не выложена списком.** Перед
заголовком стояло пять строк серой меты: чипы вопроса → очередь сессии → тема →
причина → и лишь потом `h1`. Статус сессии вклинивался между чипами вопроса и его
темой, разрывая одну группу фактов другой, а тема — лучший ориентир, когда вопросы
идут вперемешку по 320 темам, — оказывалась четвёртой и самой мелкой. Ранние правки
выравнивали отбивки внутри этой стопки, но не саму группировку. Теперь порядок
читается как один спуск: **сессия** (где я вообще) → **этот вопрос** (тема ·
режим, и сложность — когда ей есть что сказать) → **почему именно он** → сам
вопрос. Пять строк
стали двумя плюс условная третья, заголовок поднялся на ~50px на 1440 и ~48px на
390 — на мобильном это прямо решает, виден ли вопрос без скролла.

**На экзамене тренер не объясняет себя.** Строка «почему именно он» —
explainable-причина планировщика: «Недавно была ошибка (14.07)», «Повторение
просрочено на 3 дня», «Тема пока слабая (точность 33%)». В тренировке это и есть
смысл экрана. На экзамене она печатала «Часть экзаменационной сессии» — факт про
сессию, а не про этот вопрос, одинаковый на всех десяти: тот же экран уже сообщал
про экзамен чипом режима строкой выше и рельсом «ПРОГРЕСС СЕССИИ 1/10» рядом, то
есть трижды об одном. Хуже того, эта заглушка была коротким замыканием: пока шёл
экзамен, ни одна настоящая причина не вычислялась вовсе. Теперь на экзамене строки
нет — и не потому, что нечего сказать, а потому что говорить нельзя: «тема пока
слабая» и «недавно была ошибка» перед вопросом подсказывают ответ и обесценивают
итоговый балл. Решение «показывать ли повод» — это решение режима, и живёт оно на
странице, а не в классификаторе (`backend-architecture.md`, `ReviewReasonService`).

**Сложность показывается, только когда различает вопросы.** Тот же критерий, что у
строки выше, применён к бейджу уровня. Замер по банку: `MEDIUM` — **9818 из 9818**,
то есть подпись «Средний» стояла в шапке каждого вопроса и не сообщала ничего.
Причём `MEDIUM` — ещё и значение по умолчанию: в него сводятся пустое поле и любой
нераспознанный уровень, так что «Средний» буквально неотличим от «уровень
неизвестен». Продукт уже отвечал на этот вопрос дважды в одну сторону — донат
сложности на `/stats` скрывается, когда уровень в банке ровно один, — а экран
вопроса утверждал обратное. Теперь бейдж появляется только на `EASY`/`HARD`, в той
же гамме, которой `/stats` красит секторы, и остаётся честным сигналом на день,
когда в банке будет больше одного уровня. Критерий живёт в домене
(`Difficulty.informative()`), а не в разметке: подпись раньше собиралась тернарником
в шаблоне и на новом уровне не падала, а молча печатала «Средний».

**Инструкция стоит там, где действие, и уходит вместе с ним.** «Выбери один
вариант…» жила в шапке вопроса — за ~300px и целый заголовок до первого варианта.
Переехала внутрь формы вплотную над радиогруппой, оставшись целью её
`aria-describedby`. И снимается в момент блокировки радиокнопок: подсказка к
действию, которое кончилось, — шум, а список после ответа читается как разбор,
а не как форма.

**У материала к вопросу одна подпись и ограниченная высота.** Код и схема лежат в
одинаковых `.content-box` с полосой-тулбаром, и подпись блока — ровно одна: заголовок
тулбара. У кода она долго дублировалась: под тулбаром оставался `<details>` эпохи до
content-box со своим `<summary>`, и «Код к вопросу» печаталось дважды подряд одинаковым
mono/uppercase. Сворачивать код смысла не было (он нужен, чтобы ответить), а цена дубля
была реальной — лишний tab-stop перед вариантами и два спец-правила, гасивших summary во
вкладках и в печати. Высоту теперь держит `.code-viewport` — та же прокручиваемая рамка,
что у диаграммы: длинный листинг больше не выдавливает варианты за экран (первый вариант
поднялся с 1150px до 924px на 1440 и с 1003px до 837px на 500 — то есть на телефоне
въехал в первый экран). Прокрутка получает `tabindex` только когда она реально есть:
клавиатура обязана доставать спрятанный контент (WCAG 2.1.1), но короткому сниппету
лишний tab-stop не нужен.

**Прогресс сессии печатается в одном месте.** В топбаре стоял второй индикатор — эйбрау
«Прогресс в сессии», мини-трек и счётчик «N / M», — повторявший рельс сессии на том же
экране, причём в других единицах (проценты против вопросов) и без `aria-label`:
скринридер объявлял безымянный прогрессбар на 20%, а следом именованный «1 из 5». За
пределами экрана фокуса крамб не работал и напоминанием — `interviewSession` в модель
других страниц не кладётся, так что на `/stats` он оставался пустым `<div>` даже посреди
сессии. Место сессионного статуса — рельс, рядом с паузой и завершением.

**`--focus-question-lines: 2` оставлен намеренно.** Заголовок вопроса резервирует две
строки, поэтому под коротким вопросом видна пустота. Это не дефект: без резерва зона
ответа прыгает по вертикали между вопросами разной длины. Резерв дороже пустоты.

**Правый рельс — только внутри сессии.** `.focus-training` становится двухколоночным при
`min-width: 1080px` и только при `:has(.session-progress-track)`. Вне сессии колонке
нечем наполниться, и одна колонка 960px — правильный ответ, а не недоделка.

**Пустая область под флешкартой не заполняется.** Контент прижат к верху; заполнять
низ пришлось бы декором, который спорит с фокусом на вопросе.

**Ссылка «Следующий вопрос» в browse-флешкарте — вторичная.** Пока ответ скрыт, главное
действие — раскрыть его. После раскрытия ссылка получает акцентную рамку, но не заливку:
полноценный primary перетянул бы внимание с самого ответа.

**Итоги сессии живут до следующего захода, а не до первого рендера.** Раньше
`/session-summary` стирала сводку прямо на рендере: перезагрузка, «назад» из
закладок или случайный повторный переход выбрасывали на экран фокуса, и
результат только что законченной сессии исчезал безвозвратно. Тупик на основном
сценарии — разбор итогов как раз то, к чему возвращаются. Теперь инвалидация
привязана к событиям, которые действительно обесценивают данные: старт новой
сессии и возобновление приостановленной. При «возобновлении», когда паузы не
было, сводка не трогается — стирать нечего и незачем. Контракт закреплён в
`InterviewFlowMvcServiceTest` (двойной заход сохраняет сводку; старт и реальный
resume её чистят).

**Экран результата отвечает на один вопрос и начинается с ответа на него.** Над
вердиктом стояла полоса из шести глобальных плиток банка вопросов («Карточек 9818 /
К повтору / Освоено / Верных попыток / Ошибочных / Точность») и плоский бар сессии со
счётом и кнопкой «Завершить сессию» в один клик. Человек только что нажал «Ответить»,
и первым, что он видел, была сводка за всё время; собственно «верно или нет» —
третьим экраном сверху. Совокупные метрики принадлежат аналитике и вкладке «Прогресс»,
прогресс сессии уже показывает топбар (`role="progressbar"` + «N / M», один источник),
счёт сессии — итоги. Полоса удалена целиком, вместе с фрагментом-обёрткой
`stats-grid(stats)`, который звал только этот экран. Завершение сессии осталось —
но как вторичная кнопка рядом с «Следующим вопросом», там, где решение и принимается,
и с тем же `data-confirm`, что на экране вопроса: промах по кнопке в шапке обрывал
сессию без подтверждения.

**У банка появился обзорный вход — каталог разделов.** Тем около 320, и до этого
единственным способом окинуть их взглядом был `<select>` в фильтре плюс таблица
детализации. Таблица отвечает на вопрос «как дела с темой X», но не на вопрос
«с чего начать» — а именно он возникает у того, кто пришёл не за конкретной темой.
Раздел — единственный уровень, на котором список умещается в один экран: десять
карточек вместо трёхсот строк. Поэтому каталог стоит на `/stats#topics` **перед**
фильтрами: сперва выбираешь область, потом уточняешь.

Существенная деталь реализации: каталог считается по **двум** источникам. Охват берётся
из банка (`QuestionRepository.countQuestionsByTopic`), прогресс — из потемной статистики
(`findTopicStats`, INNER JOIN с `review_state`). Посчитать его по одному прогрессу
означало бы показывать только начатые разделы — ровно те, ради выхода за пределы которых
каталог и существует; при первом заходе он и выводил три раздела из десяти, пока
источник был один. Раздел без ответов показывает «нет ответов», а не «0% точности»:
ноль означал бы «отвечал и всё неверно».

**«К повтору» и «новых» — разные обещания, и они разведены везде.** Очередь тренажёра
(`due`) по построению включает вопросы без расписания, поэтому на пустом прогрессе весь
банк оказывался «к повтору»: 9818 повторений у человека, который не ответил ещё ни на
один вопрос, а раздел из 626 вопросов подписывался «626 к повтору · нет ответов» —
две части подписи противоречили друг другу. Теперь `fresh` считается тем же запросом,
что и `due` (`docs/backend-architecture.md` §3b), и текст выбирается по факту:

| Место | Долг есть | Долга нет |
|---|---|---|
| Герой «Сегодня» (`/settings`) | «N из M вопросов к повтору», CTA «Начать повторение» | «N из M ещё не открывали», CTA «Учить новое»; если и новых нет — «Ничего не ждёт повторения», CTA «Открыть тренажёр» |
| Чип «Сегодня» (экран вопроса) | «N из M к повтору» | «N из M новых» |
| Карточка набора (конструктор сессии) | «Повторение» + «карточки ждут повтора» | «Новое» + «ещё ни разу не открывались — повторять пока нечего» |
| Плитка KPI | «К повтору» = только долг | 0 |

Плитку «К повтору» не разделили на две: сетка KPI выверена ровно под шесть плиток в
трёх файлах (`pages-stats.css`, `pages-settings.css`, `pages-result.css`), седьмая
осиротела бы во всех трёх. Вместо этого существующая плитка стала честной, а `fresh`
и без того виден в трёх других местах.

Подпись границ тоже перестала врать: без фильтра чип пишет «Очередь · весь банк», а не
«Очередь · фильтр». Что считается сужением, решает домен (`InterviewFilter.isNarrowed()`),
а не выражение в шаблоне; порядок (`shuffle`, `ordered`) в сужение не входит — он меняет
последовательность, а не состав.

**Тон плитки описывает то самое число, которое на ней напечатано.** «Освоено» округляет
долю один раз (`th:with`) и по этому же округлённому значению решает, зажигать ли
`good`, — раньше округление и проверка жили порознь, и доля вроде 0,3 % печаталась как
«0 %», но подсвечивалась зелёным: плитка хвалила за ничто. «Очередь» же красила
тревогой `.metric-value`, то есть весь банк (9802) за две просроченные карточки —
цифра под обвинением была не той, о которой шла речь. Тревога переехала на сам
фрагмент долга и несёт три канала сразу: цвет, полужирное начертание и слово
«просрочено» (WCAG 1.4.1 — состояние не должно читаться только цветом).

**Карточка «что делать дальше» обещает ровно то, что потом произойдёт.** «Тренировать
слабые темы» называет конкретную тему с точностью и ведёт по ссылке с `topic=`;
режим `weakTopics` этой ссылкой и руководствуется. Пока правило слабейшей темы было
записано трижды — в SQL для режима, в Java для страницы и в JS для подписи — эти три
могли разойтись, и экран обещал бы одну тему, а тренировка давала другую, ничего при
этом не сломав. Определение осталось одно, серверное
(`docs/backend-architecture.md` §3c). Счётчик на карточке — число слабых тем, а не
всех тем в аналитике: соседние карточки показывают объём работы, и «320 тем» рядом с
ними читалось бы как такой же backlog.

**Вкладка «Данные» не рендерится вхолостую.** Экспорт (`GET /export`) и сброс банка
закрыты одним гейтом — `X-Admin-Token`/`adminToken` либо `ROLE_ADMIN`. В дефолтной
однопользовательской конфигурации гейт закрыт, `/export` отдаёт `403`
`application/problem+json`, и вкладка вместе со своей панелью не выводится вовсе
(`th:if="${optionsBankResetAllowed or multiSecurityMode}"`). Это согласовано намеренно:
кнопка, которая гарантированно вернёт 403, хуже отсутствующей кнопки. Проверено живьём —
на `/settings` в дефолте видно ровно две вкладки.

**Тема называется так, как названа в своём файле, и по-русски.** Раньше подпись темы
собиралась из slug-а (`cockroachdb-interview` → «Cockroachdb»), а исключения держались в
хардкод-словаре на 24 записи, из которых половина не соответствовала ни одной реальной
теме. Теперь имя берётся из frontmatter файла темы при импорте
(`docs/backend-architecture.md` §6a), поэтому в интерфейсе читаются «CockroachDB»,
«ClickHouse», «jOOQ», «ArchUnit», «AWS Lambda» — без единой строки исключений.

Когда источником стал файл, стало видно и содержательную проблему: 227 тем из 319 были
подписаны по-английски («Java Collections», «Memory Management», «Unit Testing») — в
русскоязычном продукте это выглядело как два разных каталога, склеенных вместе. 108
названий переведены прямо в корпусе (frontmatter + H1 + подписи ссылок в `TOC.md`).
Граница перевода — не язык, а природа названия: продукты, стандарты и имена API остаются
как есть (Redis, Spring Kafka, gRPC, OWASP Top 10), переводятся только описательные
названия концепций («Разделяй и властвуй», «Многопоточность в Java», «Векторные базы
данных»). Перевод «Kubernetes» дал бы не русский интерфейс, а неузнаваемый.

Правки не потребовали ни строки Java — это и есть проверка того, что реестр названий
устроен верно.

**Схема к вопросу наконец видна — и это была не фича, а починка.** Вкладки «Пример
кода / Схема» на фокус-экране выглядели мёртвым кодом: подходящих вопросов в базе было
ровно ноль. Оказалось наоборот — материал есть, его не показывали. Диаграмма лежала в
markdown у 1231 вопроса, а в колонке `diagram_mermaid` — у одного: импорт пропускал
вопрос, если не изменился текст, а поменялся не текст, а парсер, который его разбирает
(`docs/backend-architecture.md` §6b). После правки схема есть у 1231 вопроса, оба
материала сразу — у 604.

Вторая половина отказа была во фронте: функция активации вкладок лежала в модуле
настроек и грузилась только на `/settings`, где `.question-materials` не бывает
(`docs/frontend-architecture.md`, «Загрузка по страницам»). Пока обе половины не
сошлись, пользователь видел корректный запасной вид — две развёрнутые панели подряд —
и не имел ни одного признака, что что-то сломано. Отсюда правило, закреплённое тестом:
блок прогрессивного улучшения и его модуль обязаны встречаться на одной и той же
странице.

**Показав 1231 диаграмму, мы увидели, что треть из них не по палитре.** 177 диаграмм
несли захардкоженные цвета — 510 операторов `style`, больше тридцати hex-значений,
подобранных «на глаз» под дефолтную светлую тему Mermaid. Пока схему не показывали,
этого никто не видел; после починки корпус выглядел так, будто экраны собраны из разных
продуктов, а в тёмной теме светлая пастельная заливка оставалась светлой под подписью,
которая цвет берёт из токенов.

Цвет тут не украшение: красный, зелёный и жёлтый в этих графах означают «ошибка»,
«успех», «предупреждение». Поэтому диаграммы не обесцвечены — оттенок переводится в
семантический класс на импорте, а красит его тема (`docs/design-system.md` §5). Схема
теперь переключается вместе со светлой/тёмной, как и весь остальной интерфейс. Правка
поехала по всему банку сама, без миграции: механизм переразбора уже существовал со
времён предыдущего пункта — `↻177 переразобрано` на первом же старте.

Попутно удалён `MermaidSanitizer` — санитайзер диаграмм, «сгенерированных AI», у
которого после выпиливания AI не осталось ни одного вызова из продакшн-кода, вместе с
его константами и двумя дублирующими тест-классами.

**Починив показ схем, мы стали платить за них на каждой странице.** `mermaid.min.js` —
2,7 МБ, самый тяжёлый ассет продукта, и он грузился блокирующим тегом до первого
пикселя вопроса. При этом схема лежит во вкладке «Схема», а открыта по умолчанию
соседняя — «Пример кода»: типичный визит не смотрел схему ни разу. Теперь библиотека
едет по видимости самой схемы, а не по факту её наличия в разметке; вкладку открыли —
показывается спокойная строка «Готовим схему…», затем график. Экран вопроса стартует
без мегабайтного ожидания, а тот, кому схема нужна, теряет доли секунды один раз
(`docs/frontend-architecture.md`, «Mermaid грузится по видимости схемы»).

**Убрав мегабайт с критического пути, мы увидели, что мешает не он.** Замер на Slow 4G
дал FCP 4,4 с при том, что весь CSS продукта — 130 КБ. Плату брали не байты: шапка
перечисляла 33 `<link rel="stylesheet">`, HTTP/1.1 держит шесть соединений, и очередь
сериализовалась в шесть волн — первый пиксель ждал последнюю. Теперь браузер получает
одну ленту на страницу, собранную из тех же файлов в том же порядке; порядок и
постраничные гейты переехали из шапки в `css-bundle-manifest.txt`.

Вторая половина выигрыша — комментарии. CSS проекта на 52% состоит из прозы,
объясняющей правила: почему такой порядок слоёв, какие селекторы удалены и по какому
замеру. В исходнике этому место, браузеру она доставалась зря и после gzip составляла
три четверти трафика. Из ленты она вырезается, из файлов — нет. Итог: FCP 4436 → 1732 мс,
33 запроса → 1, 94 → 26 КБ по сети (`docs/frontend-architecture.md` §2).

**Тот же дефект нашёлся у JavaScript, и снова не в байтах.** После CSS первый пиксель
приходил за 1,7 с, а страница дособиралась к 4,9 с. Критическая цепочка — 5,2 с при
181 КБ кода: браузер узнаёт о модуле, только распарсив импортёра, и 39 ES-модулей
разворачивались шестью последовательными поездками. Теперь все модули страницы
объявлены в первом ответе через `<link rel="modulepreload">` и качаются параллельно;
цепочка — 1,7 с, и JS в ней больше нет вовсе. Список не ведётся руками: в манифесте
только точки входа, зависимости считаются обходом реальных `import`, а совпадение
динамических `import()` с гейтами манифеста проверяет тест — забытая строка иначе
не проявляется ничем, кроме медленной страницы.

**Вкладка врала о содержимом.** «Пример кода» на 230 вопросах показывала не код, а
схему, нарисованную псевдографикой прямо в шпаргалке: на 79 из них она дословно
дублировала соседнюю mermaid-вкладку, на 151 была единственной схемой вопроса под
чужим ярлыком. Причина — в `code_snippet` импортёр складывает любой не-mermaid блок,
а шаблон считал «есть код» синонимом «поле не пустое». Теперь тип и заголовок
назначает только бэкенд, шаблон читает готовые блоки, а у текстовой схемы нет ни
зума, ни фоллбэка рендера, ни «Исходника» — там нечего зумить и нечему падать
(`docs/backend-architecture.md` §6d).

**Итоги сессии показывают результат и один следующий ход.** Экран числился зрелым, и всё
же три его дефекта имели общую причину: у контейнера фиксированного размера нигде не был
записан бюджет содержимого. Идеальный результат печатался как «00,0%» — «100,0%» не
влезало во внутренний просвет кольца (`0.8 × размер`), а совпадение цвета текста с цветом
дуги превращало переполнение в правдоподобное другое число. Полоса KPI сжималась по
собственному содержимому и делила строку с кольцом, поэтому увеличение кольца молча
крало место у тайлов, а «12 мин 30 сек» не помещалось туда вовсе. И «короткий план»
предлагал два пункта, ведущих в одно место, плюс тот же пункт третий раз в меню
«Подробнее».

Решения: доля округляется до целых (но никогда не до 100 % при наличии ошибки и не до
0 % при верном ответе), длительность в тайле — таймерная `м:сс` (полная форма осталась в
свободной строке метрик, где ширина не зажата), полоса KPI получила собственную строку во
всю ширину карточки — тем самым её размер развязан с кольцом, — а назначение шага стало
свойством `NextActionType`, чтобы дубликаты снимались до отрисовки. Бюджеты записаны
комментариями у правил и закреплены тестами (`docs/design-system.md` §5,
`docs/quality-report.md` §4.3).

**Графики `/stats` рисуют столько, сколько помещается.** Тот же класс дефекта на
поверхности, где его нельзя увидеть: канвас невидим для DOM-гейтов, а Chart.js по
умолчанию удаляет непомещающиеся подписи молча. «Темы» давали 25 столбцов при 13
подписях, «Динамика точности» держала жёсткую константу в семь дат — лишнее выбрасывание
на 1440 и почти столкновение на 390. Оба предела теперь выводятся из коробки и ширины
фактической подписи, а пересчёт сверяет бюджет применённый с бюджетом текущим — прежняя
подписка сравнивала со снимком, снятым уже после того, как конструктор Chart.js изменил
коробку, и потому не срабатывала ни разу (`docs/frontend-architecture.md`,
`docs/quality-report.md` §4.4).

**Системная настройка «меньше движения» действует сразу, а не со следующей загрузки.**
Ось «движение» в режиме `auto` спрашивала `prefers-reduced-motion` однократно при старте
страницы. Анимации при этом гасли — за них отвечает CSS-медиа, — и ось выглядела рабочей;
молчала JS-половина, которая снимает декоративные слои и след курсора. То есть человек,
включивший настройку **потому что** ему плохо от движения, продолжал видеть движущийся
декор до перезагрузки. Теперь ось подписана на смену системного флага так же, как тема, и
рассылает то же событие, что переключатель в настройках (`docs/accessibility.md` §5,
`docs/quality-report.md` §4.5).

## 5. Известные ограничения

- Multi-режим (OAuth2, owner-скоупинг) выключен и не покрыт живой проверкой.
- **`master` ещё не полностью собран из приземлённых кусков.** На чистом checkout
  `:quiz-app:test` даёт 1150 тестов и 3 падения: часть правки (~36 файлов под
  `modules/`) не приземлена, а контракты на неё в `HEAD` уже объявлены. В авторском
  дереве обе половины лежат рядом и дыра не видна — см. `docs/quality-report.md` §2.
- Интеграционные тесты требуют Docker и переменных окружения — см.
  `docs/quality-report.md` §1.
- Полноэкранный `pixel-fx` проверяется вручную. Автоматически закрыт **состав**:
  карта спрайтов, палитра растра (`PixelSpriteContractTest`) и палитра стилей
  (`PixelCssPaletteTest`) — цвет мимо рампы `tokens.css` и HEX в точке потребления
  теперь красят сборку. Не закрыто то, **как слой выглядит в движении**: плотность
  декора, тайминги, попадание частиц в кадр — это ревью глазами.

## 6. Как запустить

```bash
docker compose up -d postgres          # PostgreSQL на 5432
./gradlew bootRun                      # http://localhost:8080
```

Ключи AI не нужны и не бывают нужны: AI-кода в проекте нет, включить его флагом
нельзя (см. `docs/backend-architecture.md` §6). Варианты ответов — только из JSON-сидеров.

Правки шаблонов и статики при уже запущенном `bootRun` подхватываются без рестарта:

```bash
cp -R modules/quiz-app/src/main/resources/{templates,static} \
      modules/quiz-app/build/resources/main/
```

Правки Java требуют перезапуска. Не запускай Gradle при живом `bootRun` — сборка
встаёт; сначала останови процесс.

**Уже применённые Flyway-миграции не редактируются — даже комментарии.** Flyway
считает checksum по всему файлу, поэтому правка одного слова в комментарии
`V21` роняет старт: `checksum mismatch, applied 952680921 / resolved -1162670325`.
Это проверено на живой базе в ходе переработки: правка была откачена, а не
«починена» через `flyway repair`, потому что repair прячет расхождение вместо
того, чтобы его устранить. Нужна поправка в тексте миграции — заводи новую
версию либо оставляй как есть.
