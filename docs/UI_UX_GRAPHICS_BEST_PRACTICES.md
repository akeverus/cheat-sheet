# Контракт эталонного UI/UX, графики, цвета и анимаций

Используй этот документ как обязательный набор требований при любом изменении интерфейса.

Он применяется ко всем:

* страницам;
* компонентам;
* состояниям;
* формам;
* графикам;
* pixel-art элементам;
* иконкам;
* иллюстрациям;
* анимациям;
* переходам;
* темам;
* desktop-композициям;
* mobile-композициям;
* frontend-изменениям;
* backend-изменениям, влияющим на интерфейс.

Главная задача — добиться не просто красивого интерфейса, а целостного продукта, который соответствует лучшим практикам UI/UX, accessibility, motion design, информационной архитектуры и frontend-разработки.

Интерфейс должен быть:

```text
красивым
+
уникальным
+
понятным
+
системным
+
быстрым
+
доступным
+
предсказуемым
+
адаптивным
+
визуально спокойным
+
технически качественным
```

---

# 1. Основное правило

Не добавляй элемент только потому, что он красиво выглядит.

Каждый элемент обязан выполнять хотя бы одну функцию:

* помогать принять решение;
* объяснять состояние;
* направлять внимание;
* ускорять действие;
* показывать прогресс;
* снижать когнитивную нагрузку;
* улучшать ориентацию;
* усиливать узнаваемость продукта;
* давать полезную обратную связь.

Если элемент не выполняет ни одну из этих функций, его следует:

* удалить;
* скрыть;
* ослабить;
* перенести;
* объединить с другим элементом.

---

# 2. Иерархия качества

При принятии решений используй такой приоритет:

```text
корректность и безопасность
→ понятность
→ доступность
→ удобство
→ скорость
→ визуальная иерархия
→ уникальность
→ декоративность
```

Красота не может компенсировать:

* непонятное действие;
* ложную метрику;
* плохой контраст;
* недоступность с клавиатуры;
* неправильную мобильную композицию;
* потерю данных;
* медленную загрузку;
* отсутствие состояния ошибки;
* нестабильную бизнес-логику.

---

# 3. Не копируй шаблонные интерфейсы

Не создавай интерфейс, похожий на:

* стандартный Bootstrap dashboard;
* типовой Tailwind admin panel;
* набор одинаковых SaaS-карточек;
* дешёвую мобильную игру;
* лендинг криптопроекта;
* ретро-игру с чрезмерным pixel-art;
* IDE, перегруженную техническими панелями;
* интерфейс с неоновым glow на каждом элементе;
* Dribbble-концепт, непригодный для реального использования.

Продукт должен иметь собственный визуальный язык.

Он должен узнаваться по:

* нижней pixel-art панели;
* системе pixel-art иконок;
* характерной геометрии;
* цветовым акцентам;
* типографике;
* состояниям;
* анимациям;
* композиции учебного сценария.

---

# 4. Единая дизайн-система

Любое новое решение должно быть частью системы, а не локальным исключением.

Обязательно используй дизайн-токены для:

* цветов;
* фонов;
* поверхностей;
* текста;
* границ;
* теней;
* spacing;
* размеров;
* радиусов;
* typography;
* z-index;
* motion duration;
* easing;
* breakpoints;
* focus ring;
* icon sizes;
* pixel-art sizes.

Не добавляй произвольные значения прямо в компонент, если для них должен существовать токен.

Запрещено бесконтрольно создавать:

```css
color: #23d6c4;
margin: 13px;
border-radius: 11px;
transition: 237ms;
z-index: 999999;
```

Вместо этого используй системные переменные.

Пример:

```css
var(--color-accent-primary)
var(--space-3)
var(--radius-md)
var(--motion-fast)
var(--layer-overlay)
```

# 5. Цветовая система

## 5.1 Общий характер

Палитра должна выглядеть:

* спокойной;
* технологичной;
* глубокой;
* современной;
* профессиональной;
* контрастной;
* но не агрессивной.

Основу интерфейса должны составлять:

* глубокий нейтральный фон;
* немного более светлые поверхности;
* мягкие границы;
* комфортный основной текст;
* приглушённый дополнительный текст;
* ограниченное число ярких акцентов.

## 5.2 Семантика цветов

Каждый цвет должен иметь стабильное значение.

Примерная семантика:

```text
teal / cyan — бренд, primary action, focus
green — успех, завершённость, положительный результат
amber — предупреждение, внимание, ожидающее действие
red — ошибка, опасное действие, неуспешный результат
purple — специальные режимы, достижения, дополнительная ценность
blue — информация, аналитика, нейтральное состояние
```

Не используй один и тот же цвет одновременно для:

* primary action;
* ошибки;
* декоративного эффекта;
* выбранного элемента;
* информационного статуса.

## 5.3 Ограничение насыщенности

Яркие цвета должны занимать малую часть экрана.

Не допускай:

* пяти ярких карточек рядом;
* цветных границ вокруг каждого блока;
* постоянного glow;
* разноцветных кнопок одинаковой важности;
* градиентов на всех поверхностях;
* кислотных цветов в длинных учебных сценариях.

Главный цветовой акцент должен показывать главное действие.

## 5.4 Светлая и тёмная темы

Светлая тема не должна быть простой инверсией тёмной.

Для каждой темы отдельно проверь:

* фон;
* поверхности;
* границы;
* тени;
* основной текст;
* muted text;
* ссылки;
* focus ring;
* code blocks;
* diagrams;
* charts;
* pixel-art;
* hover;
* active;
* disabled;
* success;
* warning;
* error.

Не используй чистый белый и чистый чёрный на больших поверхностях без объективной причины.

## 5.5 Контраст

Проверяй фактический контраст всех:

* текстов;
* иконок;
* кнопок;
* ссылок;
* меток;
* badges;
* chart labels;
* placeholder;
* disabled states;
* focus states.

Muted text не должен становиться нечитаемым.

Disabled state должен оставаться различимым, даже если он менее контрастен.

---

# 6. Типографика

## 6.1 Главный принцип

Типографика должна быть спокойной и легко читаемой в длинных сессиях.

Запрещено использовать pixel-font для:

* основного текста;
* вопросов;
* вариантов ответа;
* объяснений;
* таблиц;
* аналитики;
* настроек;
* длинных заголовков;
* сообщений об ошибках.

Pixel-font допустим только в небольших декоративных или брендовых элементах.

## 6.2 Роли

Определи и используй ограниченный набор ролей:

```text
display
page title
section title
card title
body
body compact
label
caption
code
numeric metric
```

Не создавай новый размер шрифта для каждого компонента.

## 6.3 Читаемость

Проверяй:

* комфортный line-height;
* достаточную ширину строки;
* отсутствие слишком длинных строк;
* отсутствие слишком узких колонок;
* корректную русскую типографику;
* правильные переносы;
* отсутствие висячих предлогов, где это возможно;
* отсутствие автоматических переносов технических терминов.

Не допускай переносов вроде:

```text
консистент-
ность

кон-
текст
```

Для основного учебного текста отключай агрессивную автоматическую расстановку переносов.

## 6.4 Размеры

Не используй текст 9–10 px для постоянных интерактивных элементов.

Особенно это касается:

* нижней навигации;
* кнопок;
* tab labels;
* form labels;
* chart legends;
* secondary actions.

Текст должен оставаться читаемым:

* на mobile;
* при масштабировании;
* на экранах с высокой плотностью;
* при плохом зрении;
* при ярком внешнем освещении.

---

# 7. Spacing и композиция

## 7.1 Системная шкала

Используй единую spacing-шкалу.

Например:

```text
4
8
12
16
24
32
48
64
```

Не используй случайные промежуточные отступы без причины.

## 7.2 Группировка

Связанные элементы должны располагаться ближе друг к другу, чем несвязанные.

Используй расстояние для обозначения:

* принадлежности;
* иерархии;
* разделения;
* последовательности;
* смены контекста.

Не используй рамку там, где достаточно отступа.

## 7.3 Вертикальный ритм

Все страницы должны иметь устойчивый вертикальный ритм.

Проверяй:

* расстояние между заголовком и описанием;
* расстояние между секциями;
* расстояние между label и control;
* расстояние между вариантами ответа;
* положение основного CTA;
* отступ перед нижней pixel-art панелью.

## 7.4 Пустое пространство

Пустое пространство является частью дизайна.

Не заполняй свободную область декоративными элементами только потому, что она существует.

На больших экранах свободное место можно использовать для:

* контекстной информации;
* навигации;
* прогресса;
* shortcuts;
* полезного secondary rail.

Но основной текст не должен растягиваться на всю ширину 1920–2560 px.

---

# 8. Сетки и адаптивность

## 8.1 Не масштабируй desktop до mobile

Mobile — это отдельная композиция, а не уменьшенный desktop.

Для mobile пересматривай:

* порядок блоков;
* количество колонок;
* закреплённые действия;
* размер нижней панели;
* длину labels;
* поведение таблиц;
* расположение графиков;
* code blocks;
* diagram viewer;
* filter controls;
* analytics;
* settings.

## 8.2 Контрольные размеры

Проверяй минимум:

```text
320 × 568
375 × 812
390 × 844
768 × 1024
1024 × 768
1280 × 800
1440 × 900
1920 × 1080
2560 × 1440
```

## 8.3 Breakpoints

Не создавай большое количество близких breakpoint:

```text
539
540
560
600
601
640
```

Используй небольшое число осмысленных layout-breakpoints.

Breakpoint должен появляться только тогда, когда композиция действительно перестаёт работать.

## 8.4 Safe areas

Для mobile учитывай:

```css
env(safe-area-inset-top)
env(safe-area-inset-right)
env(safe-area-inset-bottom)
env(safe-area-inset-left)
```

Особенно для нижней pixel-art панели и закреплённых CTA.

---

# 9. Визуальная иерархия

Каждый экран должен отвечать на вопросы:

```text
Что здесь главное?
Что пользователь должен сделать?
Что он должен понять?
Что является вторичным?
Что можно скрыть?
```

На одном экране не должно быть пяти элементов одинаковой визуальной важности.

Используй иерархию через:

* размер;
* weight;
* цвет;
* spacing;
* положение;
* контраст;
* плотность;
* форму;
* движение.

Не используй яркий цвет как единственный способ показать важность.

---

# 10. Кнопки и действия

## 10.1 Уровни действий

Используй ограниченную систему:

```text
primary
secondary
tertiary
danger
icon-only
```

На экране должен быть только один очевидный primary action.

Если одновременно отображаются несколько primary-кнопок, необходимо пересмотреть иерархию.

## 10.2 Состояния

Каждая кнопка должна иметь:

* default;
* hover;
* focus-visible;
* active;
* loading;
* disabled;
* success, если применимо;
* error, если применимо.

Loading-состояние не должно менять ширину кнопки.

## 10.3 Icon-only buttons

Icon-only кнопки обязаны иметь:

* accessible name;
* tooltip;
* достаточную область нажатия;
* понятную иконку;
* focus state.

## 10.4 Опасные действия

Danger-действие не должно выглядеть как primary action до момента, когда пользователь действительно подтверждает опасную операцию.

---

# 11. Формы

Каждое поле должно иметь:

* видимый label;
* понятное описание, если требуется;
* placeholder только как пример;
* error message;
* success state, если это полезно;
* disabled state;
* keyboard support;
* autofill support;
* корректный тип input;
* понятную причину ошибки.

Не используй placeholder вместо label.

Ошибку размещай рядом с полем, а не только в верхнем toast.

Не сбрасывай введённые данные после ошибки.

---

# 12. Карточки и поверхности

Не превращай весь интерфейс в сетку одинаковых карточек.

Карточка оправдана, если элемент:

* является самостоятельной сущностью;
* имеет собственные действия;
* может быть перемещён;
* может быть выбран;
* имеет отдельное состояние;
* визуально отделён по смыслу.

Не помещай каждый текстовый блок в карточку.

Обычный контент лучше группировать через:

* spacing;
* section headers;
* subtle dividers;
* background hierarchy.

---

# 13. Pixel-art система

Pixel-art является обязательной частью продукта, но должен использоваться дисциплинированно.

## 13.1 Раздельное хранение

Все элементы должны существовать отдельно:

* каждая иконка — отдельный SVG;
* каждый арт — отдельный PNG, SVG или WebP;
* каждый кадр анимации — отдельный PNG;
* каждый sprite sheet — отдельный файл;
* metadata — отдельный JSON;
* лицензия внешнего ассета — отдельный файл;
* preview — отдельный файл.

Не допускай существования элемента только внутри:

* большого sprite sheet;
* CSS background;
* встроенного base64;
* общего canvas;
* HTML-фрагмента;
* JavaScript-кода.

## 13.2 Сетка

Используй стабильные размеры:

```text
8 × 8 — micro details
16 × 16 — controls и statuses
24 × 24 — navigation и toolbar
32 × 32 — badges и небольшие арты
48 × 48 — empty-state details
64 × 64 и больше — иллюстрации и mascot
```

Масштабирование должно быть целочисленным.

Не растягивай:

```text
16 → 28
24 → 40
32 → 45
```

Используй:

```text
16 → 32
24 → 48
32 → 64
```

или отдельный размер ассета.

## 13.3 Optical consistency

Все pixel-art иконки должны иметь:

* одинаковую визуальную массу;
* одинаковую толщину;
* общую сетку;
* одинаковую степень детализации;
* одинаковый уровень скругления;
* одинаковую перспективу;
* совместимую палитру.

Не смешивай:

* outline;
* solid;
* изометрические;
* гладкие vector icons;
* pixel icons;
* emoji,

в одной группе навигации.

## 13.4 Pixel-art и контент

Pixel-art должен концентрироваться в:

* нижней панели;
* навигации;
* toolbar;
* active states;
* empty states;
* достижениях;
* summary;
* onboarding;
* специальных callout;
* mascot;
* status feedback.

Ослабляй pixel-art в:

* длинных объяснениях;
* таблицах;
* аналитике;
* формах;
* документации;
* больших текстовых блоках.

---

# 14. Графика и иллюстрации

Каждая иллюстрация должна иметь конкретный сценарий.

Обязательно подготовь отдельные арты для:

* пустого состояния;
* отсутствия результатов поиска;
* offline;
* reconnect;
* ошибки загрузки;
* ошибки диаграммы;
* ошибки кода;
* конфликта ревизии вопроса;
* сохранения;
* синхронизации;
* завершения сессии;
* достижения;
* слабой темы;
* отсутствия статистики;
* onboarding;
* технического обслуживания.

Не используй один и тот же mascot для всех состояний без изменения позы, эмоции или окружения.

Декоративные изображения должны использовать:

```html
aria-hidden="true"
```

Функциональная иллюстрация должна иметь альтернативное текстовое описание.

---

# 15. Иконки

## 15.1 Семантика

Иконка должна быть однозначной без длительного угадывания.

Проверяй иконки отдельно в размерах:

```text
16 px
20 px
24 px
32 px
```

Если иконка не считывается в 16–20 px, её следует упростить.

## 15.2 Консистентность

Все иконки одной группы должны иметь:

* одинаковую сетку;
* одинаковый padding;
* одинаковую толщину;
* одинаковую визуальную массу;
* одинаковый стиль.

## 15.3 Иконка и подпись

Не убирай текстовую подпись, если иконка может быть непонятной.

На mobile navigation используй подписи для главных разделов.

## 15.4 Дублирование

Не поддерживай вручную несколько копий одного icon set.

Должен существовать один источник истины, из которого при необходимости генерируются:

* individual SVG;
* inline sprite;
* external sprite;
* PNG preview;
* documentation gallery.

---

# 16. Нижняя pixel-art панель

Нижняя панель должна стать визуальной подписью продукта.

Она должна быть:

* уникальной;
* компактной;
* хорошо читаемой;
* полезной;
* доступной;
* responsive;
* визуально выразительной;
* но не отвлекающей.

## 16.1 Desktop

На desktop панель может объединять:

* главную навигацию;
* контекст текущей сессии;
* прогресс;
* shortcuts;
* sync status;
* быстрые действия.

Она не должна превращаться в перегруженный HUD.

## 16.2 Mobile

На mobile:

* максимум 4–5 основных разделов;
* secondary actions в overflow;
* подписи не мельче комфортного читаемого размера;
* достаточные touch targets;
* учёт safe area;
* отсутствие перекрытия контента;
* основной contextual CTA располагается над панелью.

## 16.3 Active state

Активный пункт должен отличаться через:

* pixel socket;
* фон;
* контраст;
* небольшое смещение;
* понятный label;
* optional short animation.

Не используй бесконечную пульсацию активного пункта.

---

# 17. Анимации и motion design

## 17.1 Цель движения

Любая анимация должна:

* объяснять переход;
* подтверждать действие;
* показывать связь;
* помогать ориентации;
* отображать загрузку;
* показывать прогресс;
* привлекать внимание к важному изменению.

Если анимация существует только ради декоративности, она должна быть редкой и отключаемой.

## 17.2 Длительности

Используй системную шкалу:

```text
быстрое состояние: 100–180 ms
обычный переход: 180–280 ms
перестройка layout: 250–400 ms
короткий feedback effect: 300–700 ms
celebration: до 1200 ms
```

Не делай интерфейс медленным ради «плавности».

## 17.3 Easing

Используй спокойные easing-функции.

Избегай:

* чрезмерного bounce;
* elastic;
* резких overshoot;
* бесконечной пульсации;
* постоянного floating;
* движения каждого hover-элемента.

## 17.4 Одновременное движение

В одном viewport не должно одновременно происходить несколько заметных анимаций.

Запрещено одновременно запускать:

* confetti;
* coin rain;
* mascot reaction;
* screen flash;
* XP fly;
* achievement;
* level-up;
* portal transition.

Выбирай один главный эффект.

## 17.5 Loading animation

Loading должен:

* показывать, что система работает;
* не создавать иллюзию прогресса, которого нет;
* иметь fallback;
* не блокировать интерфейс дольше необходимого.

Не используй бесконечный spinner для долгой операции без пояснения.

## 17.6 Reduced motion

При отключённом motion:

* sprite sheets показывают статический кадр;
* looping GIF останавливается;
* transform-анимации отключаются;
* параллакс отключается;
* smooth scroll отключается;
* screen transition упрощается;
* функциональность сохраняется.

---

# 18. Feedback и микровзаимодействия

Каждое действие пользователя должно иметь понятную реакцию.

Примеры:

```text
выбор ответа → выбранное состояние
submit → loading без повторного нажатия
успех → короткое подтверждение
ошибка → понятная причина и действие
сохранение → saved status
offline → offline status
reconnect → sync status
копирование → copied status
изменение темы → мгновенное обновление
```

Не показывай toast для каждого незначительного действия.

Используй inline feedback там, где он относится к конкретному компоненту.

---

# 19. Учебный сценарий

Основной контент должен всегда быть важнее игровых эффектов.

Приоритет после ответа:

```text
вердикт
→ правильный ответ
→ ключевое различие
→ объяснение ошибки
→ что запомнить
→ следующее действие
→ дополнительный материал
→ награды
```

Награда не должна появляться раньше объяснения.

Неправильный ответ не должен вызывать:

* сильную тряску;
* красную вспышку;
* mockery;
* потерю fake lives;
* черепа;
* надписи `MISS`, `NOPE`, `OUCH`.

---

# 20. Аналитика и графики

Графики должны помогать принимать решения.

Каждый график должен иметь:

* заголовок;
* краткое объяснение;
* период;
* единицы измерения;
* denominator;
* legend;
* tooltip;
* accessible summary;
* tabular fallback;
* loading state;
* empty state;
* error state.

Не используй:

* 3D charts;
* декоративные pie charts с большим количеством сегментов;
* скрытые оси;
* неразличимые близкие цвета;
* gradient area только ради красоты;
* график, если число или таблица объясняет данные лучше.

Не показывай метрику без возможности понять, как она рассчитана.

---

# 21. Состояния компонентов

Каждый интерактивный компонент должен быть проверен в состояниях:

```text
default
hover
focus-visible
active
selected
disabled
loading
success
warning
error
empty
offline
long content
overflow
```

Не считай компонент готовым, если реализовано только его default-состояние.

---

# 22. Ошибки и пустые состояния

Ошибка должна отвечать на вопросы:

```text
Что произошло?
Почему это могло произойти?
Потеряны ли данные?
Что можно сделать сейчас?
Можно ли повторить действие?
Как получить correlation ID?
```

Empty state должен:

* объяснять причину;
* показывать следующий шаг;
* не выглядеть как ошибка;
* не занимать весь экран без необходимости;
* использовать подходящий отдельный pixel-art арт.

---

# 23. Accessibility

Каждое изменение должно сохранять или улучшать:

* keyboard navigation;
* logical focus order;
* focus-visible;
* screen reader support;
* labels;
* descriptions;
* status announcements;
* dialogs;
* focus trap;
* focus restore;
* touch target size;
* text resize;
* zoom;
* contrast;
* reduced motion;
* semantic HTML;
* chart fallback;
* diagram fallback.

Не используй ARIA для исправления неправильной HTML-структуры.

Не помещай большие текстовые блоки целиком в `aria-live`.

После динамического изменения объявляй только краткий результат.

---

# 24. Производительность графики

Для каждого ассета оцени:

* размер файла;
* формат;
* разрешение;
* прозрачность;
* количество кадров;
* частоту кадров;
* необходимость preload;
* возможность lazy loading;
* reduced-motion fallback;
* повторное использование.

Используй:

* SVG для функциональных иконок;
* PNG для строгого pixel-art;
* WebP или AVIF для больших растровых иллюстраций, если pixel-grid не страдает;
* sprite sheets для коротких управляемых анимаций;
* GIF только для preview или когда он объективно оправдан.

Не загружай все декоративные ассеты на каждой странице.

---

# 25. Не допускай визуального долга

Во время каждой итерации проверяй:

* дубли токенов;
* hardcoded colors;
* `!important`;
* повторяющиеся media queries;
* разные варианты одной кнопки;
* несколько modal systems;
* несколько icon systems;
* несколько toast systems;
* случайные z-index;
* локальные CSS-хаки;
* устаревшие классы;
* неиспользуемые ассеты;
* broken image references;
* растровое масштабирование;
* повторяющиеся SVG.

Новое изменение не должно увеличивать системный долг.

---

# 26. Проверка перед завершением итерации

После каждой итерации обязательно выполни проверку.

## Визуальная проверка

Проверь:

* композицию;
* иерархию;
* баланс;
* плотность;
* читаемость;
* контраст;
* количество pixel-art;
* количество движения;
* главный CTA;
* mobile;
* desktop;
* большие экраны;
* dark;

## Графическая проверка

* качество pixel scaling;
* соответствие иконок;

## UX-проверка

Проверь:

* понятность действия;

* количество шагов;
* error recovery;
* loading;
* empty;
* offline;
* keyboard;

## Техническая проверка

Запусти:

* performance checks.

# 27. Вопросы, которые LLM должна задавать себе

Перед добавлением любого элемента:

```text
Нужен ли он пользователю?
Какую проблему он решает?
Можно ли решить её проще?
Не конкурирует ли он с основным действием?
Не создаёт ли он визуальный шум?
Доступен ли он с клавиатуры?
Понятен ли он без цвета?
Работает ли он на mobile?
Есть ли loading/error/empty state?
Не ухудшает ли он производительность?
Соответствует ли он pixel-art системе?
Хранится ли ассет отдельным файлом?
Есть ли reduced-motion fallback?
```

Перед завершением экрана:

```text
Очевидно ли главное действие?

Не слишком ли много рамок?
Не слишком ли много ярких цветов?
Не слишком ли много анимаций?
Читается ли текст?
Не выглядит ли это как шаблон?
Уникален ли экран без ущерба удобству?
```

# 28. Антипаттерны, которые нужно автоматически исправлять

Автоматически находи и исправляй:

* несколько primary CTA;
* текст меньше комфортного размера;
* слабый контраст;
* placeholder вместо label;
* icon-only control без accessible name;
* hover без keyboard focus;
* fixed element, перекрывающий контент;
* mobile layout как сжатый desktop;
* бесконечные декоративные animations;
* несколько focal effects одновременно;
* fake metrics;
* слишком много badges;
* слишком много nested cards;
* каждый блок в рамке;
* inconsistent icon styles;
* fractional pixel scaling;
* несистемные цвета;
* несистемные spacing;
* layout shift;
* отсутствующие изображения;
* общий sprite без отдельных исходников;
* тяжёлый GIF без fallback;
* motion без reduced-motion;
* экран ошибки без recovery action;
* аналитика без denominator;
* график без fallback;
* длинная форма без группировки;
* settings на несколько тысяч пикселей без разделения;
* CTA, находящийся ниже длинного контента на mobile.

---

# 29. Итоговый критерий

Интерфейс можно считать соответствующим требованиям только тогда, когда:

* он понятен без объяснений;
* главный CTA очевиден;
* pixel-art создаёт характер, а не усталость;
* нижняя панель уникальна и функциональна;
* цветовая система последовательна;
* типографика комфортна для длинной работы;
* анимации имеют цель;
* motion можно отключить;
* все состояния реализованы;
* desktop и mobile имеют самостоятельную композицию;
* тёмная и светлая темы полноценны;
* графика хранится отдельно;
* все ассеты доступны и не создают 404;
* иконки единообразны;
* UI доступен с клавиатуры;
* экран работает со screen reader;
* графики имеют альтернативное представление;
* производительность не ухудшена;
* backend поддерживает отображаемые состояния;
* дальнейшие изменения были бы только субъективными вкусовыми перестановками.

---

# 30. Поведение внутри loop

Этот контракт должен выполняться на каждой loop-итерации.

LLM не должна:

* переписывать качественные компоненты без причины;
* бесконечно менять цвета;
* передвигать элементы только ради diff;
* добавлять новый визуальный стиль поверх старого;
* создавать ещё одну параллельную дизайн-систему;
* добавлять ассеты без реального сценария;
* считать задачу завершённой без проверки.

Каждая итерация должна выбрать одну наиболее значимую проблему и полностью закрыть её:

```text
исследование
→ решение
→ дизайн
→ frontend
→ backend при необходимости
→ states
→ accessibility
→ responsive
→ tests
→ screenshots
→ documentation
```

После итерации зафиксируй:

```text
Какое best-practice нарушение было найдено
Почему оно важно
Как оно исправлено
Какие альтернативы рассматривались
Как изменился пользовательский сценарий
Как изменился визуальный баланс
Как проверена доступность
Как проверен mobile
Как проверены цвета и контраст
Как проверены анимации
Как проверены ассеты
Какие тесты выполнены
Какая проблема является следующей
```

Не спрашивай разрешения продолжить.

Следующий запуск loop должен самостоятельно выбрать следующую наиболее важную проблему.
