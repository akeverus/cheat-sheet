# Проверка формы и полноты вариантов: SFPL и ANSC

Детализация [единого стандарта](../mcq-quality-standard.md), актуализирована 2026-09-14.
[План работ](../../PLAN_INTERVIEW.md) выделяет это в самостоятельный этап приёмки.

Проблема: правильный ответ выглядит профессиональным и полным, а три неверных —
короткими, примитивными или иначе построенными. Ответ угадывается по качеству текста
даже при достаточном паритете слов и успешном содержательном ревью.

**SFPL** — сопоставимость структуры, формата, пунктуации и длины.
**ANSC** — полноценный ответ на вопрос со стороны каждого из четырёх вариантов.
Оба измерения обязательны; ни одно не выводится автоматически из другого.

## Сравнение четырёх вариантов

| Измерение | Что фиксирует рецензент по A/B/C/D | Пример подозрительного отличия |
|---|---|---|
| Тип ответа | Определение, сравнение, механизм, результат, рекомендация или перечень | Correct объясняет механизм, wrong только называет термин |
| Смысловой каркас | Порядок результата, условия, причины, ограничения | Correct «результат → причина → оговорка», wrong только «результат» |
| Покрытие вопроса | На какие части видимого вопроса отвечает вариант | Вопрос спрашивает «что и почему», лишь correct содержит «почему» |
| Полнота перечня | Равнозначные по объёму и роли списки | Полный каталог в correct против одного пункта у wrong |
| Конкретность | API, примеры, числа, версии и границы применимости | Только correct содержит точный API и исключение |
| Язык и правдоподобие | Естественность, самодостаточность, основное заблуждение wrong | Грамотный correct против абсурдных или неуклюжих wrong |
| Видимая форма | Длина в словах/символах, код, списки, пунктуация, начало фразы | Единственный длинный/короткий ответ или уникальный кодовый пример |

Рецензент возвращает краткую таблицу по всем четырём опциям, затем два отдельных
вердикта SFPL/ANSC и находки. Нужны проверяемые наблюдения, не внутренняя цепочка рассуждений.
Равное число предложений или знаков само по себе не подтверждает одинаковый каркас.

## Автоматические проверки и известная слепая зона

```bash
python3 scripts/mcq-skel-gate.py --verbose <seed.json>
python3 scripts/mcq-anti-tell-scan.py <seed.json>
python3 scripts/mcq-answer-parity-gate.py <seed.json>
python3 scripts/mcq-struct-scan.py <seed.json>
```

Перед ними выполняется `bash scripts/verify-mcq-json.sh <seed.json>`; общая обёртка —
`scripts/mcq-tools/gates.sh`. `mcq-audit.py` собирает SKEL/anti-tell сигналы по Q/B
в `form_precheck` и приоритизированный скоуп `form_review_queue`.

SKEL сравнивает главным образом начало фразы, предложения, `;` и грубые категории кода.
**Он может вернуть PASS для одного развёрнутого ответа и трёх коротких фраз**, если все
начинаются прозой и имеют по одному предложению. Контрпример закреплён в тестах.
Остальные сканеры могут заметить длину, но не доказывают полноту механизма/условий.

Автосигнал требует разбора; отсутствие сигнала не закрывает формальное ревью. Блоки без
сигналов также остаются в скоупе. Коридоры 1.25×, CV≈0.12 и запрет любого lone-longest
из старой редакции — исторические эвристики, а не универсальные критерии качества.
Пороги инструментов не меняются ради зелёного отчёта; обоснованный false positive
документируется отдельно от фактического устранения дефекта.

## Как исправлять

1. Сохранить видимый вопрос, проверяемую мысль и единственный корректный ответ.
2. Довести каждый слабый wrong до полноценной правдоподобной ошибочной модели.
3. Сопоставить каркасы, части вопроса, конкретность и видимое оформление всех четырёх.
4. Избыточную лекцию из correct перенести в sections; необходимые для выбора условия
   оставить в вопросе/вариантах. Правильный ответ не обязан оставаться самым длинным.
5. После правки перечитать все варианты и связанные sections: объяснения должны
   опровергать новые wrong, а не их прежнюю версию.
6. Повторить проверки и независимое сравнительное ревью затронутых блоков.

Запрещены пустое удлинение, карбоновые копии, удаление backticks/API ради счётчика,
фиксированная позиция correct «второй по длине» и искусственное выравнивание всех
блоков под одно число предложений. Сопоставимость не означает буквальную идентичность.
Категоричное слово допустимо, если оно технически уместно; важно распределение таких
признаков и правдоподобие ответа в контексте.

## Независимое ревью и доказательство результата

Первый проход — сравнение формы без поля correct и без sections. Передаются видимый
вопрос и четыре текста в новом контексте. Ревьюер фиксирует отличающиеся варианты
и наблюдаемые признаки до раскрытия ключа. Не требовать «забыть технологию»: правильный
выбор по знанию предмета не является доказательством утечки формы.

После фиксации наблюдений принимающая сторона сопоставляет их с ключом. Затем ревьюер
с доступом к теории/ключу проверяет ANSC, правдоподобие wrong и сохранность семантики.
Если отдельный контекст недоступен, вид прохода помечается честно; слепота не приписывается.

Запись по блоку содержит:

- путь темы, Q/B, SHA-256 JSON/Markdown и версию стандарта;
- вид прохода, ревьюера и то, был ли ключ доступен;
- характеристики A/B/C/D по таблице выше;
- `sfpl` и `ansc`: PASS / FAIL / UNVERIFIED с коротким обоснованием;
- признаки выделения и конкретные находки по label/полю;
- автосигналы и результат их разбора;
- изменения и повторные проверки после ремонта.

Отдельной схемы автоматического зачёта таких записей пока нет: текущий машинный снимок
показывает весь непринимавшийся отдельно скоуп формы и его приоритеты. При первом
фактическом пакете ревью нужно подключить его coverage к расчёту актуального покрытия,
проверяя поля, хеши и изменения стандарта; одна вручную поставленная галочка не подходит.

SFPL PASS требует отсутствия необъяснённых признаков, выдающих correct сравнительной
формой. ANSC PASS требует полноценности всех четырёх ответов и конкретного правдоподобного
заблуждения каждого wrong. «Это просто единственный полный ответ» не является исключением
для принятия несопоставимых вариантов. Истинность correct оценивается отдельно.
