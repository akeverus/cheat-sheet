# Полная перегенерация production MCQ одной моделью

Действующий процесс с 21 ноября 2026. Он заменяет пакеты Q/B, структурные и
эвристические гейты и обязательные фазы A/B. Исторические evidence и старые статусы
остаются справкой, но не служат руководством к запуску старых инструментов.

1. Координатор выбирает одну тему в [плане](../../PLAN_INTERVIEW.md) и передаёт
   MCQ-чату заполненный [шаблон поручения](#шаблон-поручения-mcq-чату).
   Указанные снимки должны быть доступны автору целиком.
2. Одна LLM генерирует заново всю тему одной задачей и возвращает один полный
   JSON для прямой замены. Ориентир по подробности и оформлению — полная версия
   темы из Git до перегенерации. Каждый вариант получает все секции для своей
   роли: пять у ключа и по четыре у каждого дистрактора. В блоке ровно один
   ключ. Вопрос сохраняет существенные условия и получает контекст там, где
   он нужен. Код и схемы условия берутся из парного Markdown. Код для
   разбора может быть частью `example`. Автор при записи разворачивает
   объекты и массивы JSON с отступом в два пробела.
3. Автор передаёт путь к одному полному файлу. Координатор переносит его
   побайтно. `LLM_READY` означает, что автор передал полный файл. Перенос
   в production, коммит и публикация имеют отдельные фактические статусы.
   Редакционные проверки, валидаторы и повторную вычитку после записи
   не запускают. Сборка и приложение не служат этапами приёмки MCQ.

Для восстановления партии из 55 тем бери исходные JSON из `b28a1c807` и
актуальную согласованную теорию. Сначала доведи одну тему до передачи полного
файла. Затем продолжай по подтверждённым дефектам из плана. Повторное назначение
готовой темы требует конкретного замечания или существенного изменения входа.
Если Markdown мешает получить один корректный ответ, передай собранный возврат
автору теории и продолжай независимую тему. Большую пару читай частями в той
же задаче.

Роли: координатор ведёт очередь и переносит результаты, автор шпаргалок
владеет Markdown, автор MCQ генерирует JSON, инженер отвечает за UI и код.
Используй существующие чаты.

## Шаблон поручения MCQ-чату

Заполни все поля перед отправкой. Для обоих входов укажи Git-ревизию и путь
либо путь к снимку, который сохраняется до завершения задачи.
Если специальных вводных нет, укажи «нет». Выходной путь должен быть свободен.

```text
Полностью сгенерируй MCQ одной темы по указанным входам.

Репозиторий: <абсолютный путь>
Тема и topic_slug: <название и slug>
Правила генерации: прочитай весь PROMPT_PLAN_INTERVIEW.md.
Дорегенерационный JSON этой темы: <Git SHA и путь в дереве или абсолютный путь к закреплённому снимку>
Полный согласованный Markdown: <Git SHA и путь в дереве или абсолютный путь к согласованному снимку>
Production-путь: <точный путь назначения в репозитории. Только для идентификации, запись делает координатор>
Уже известные дефекты и замечания Сергея: <конкретные Q/B и требуемый результат либо «нет»>
Особые вводные: <явно согласованная версия, материалы или сопоставление Q/B либо «нет»>
Единственный итоговый файл: <абсолютный выходной путь вне отслеживаемых файлов>

Прочитай оба входа до конца. При обрезке дочитай окнами в той же задаче.
Перегенерируй весь JSON, включая все Q/B, даже если замечания касаются одного
блока. Соблюдай полный промпт для всех A–D и их секций. Используй
дорегенерационный JSON этой темы как образец глубины и формата.

Запиши один полный файл по выходному пути. Разрешены только этот путь и
внутренний черновик задачи. Подготовь развёрнутое оформление при записи.
После записи сразу верни только абсолютный путь к результату. Отдельные
проверки и повторное чтение исключены. Markdown, production, Git-индекс
и история доступны только для чтения.
Если вход не годится или нужна правка видимого вопроса либо его материалов,
передай один собранный возврат с причиной и нужным изменением. Если работа
не закончена, укажи точку продолжения. В обоих случаях готовый путь не выдавай.
```

## Цель для существующего координатора

> /goal Координируй существующие чаты Cheat Sheet. Сначала доведи до передачи
> исправленные MCQ из партии в 55 тем. Назначай по одной теме на задачу по
> шаблону поручения MCQ-чату из этого workflow.
> Записывай путь к полному
> результату и переноси файл побайтно, когда целевой путь и Git-слот доступны.
> Генерация, перенос, коммит и публикация имеют разные статусы. После записи
> автором не проверяй JSON и не назначай вычитку. Ошибку видимого вопроса или
> теории направляй владельцу Markdown. Наблюдай за независимыми потоками,
> сохраняй чужие изменения и соблюдай согласованный порог лимита. Для Git
> назначай одного владельца, коммить и публикуй только с разрешения Сергея.

## Цель для автора MCQ

> /goal Генерируй полные production JSON тем для тренажёра самообучения по
> PROMPT_PLAN_INTERVIEW.md и заполненному шаблону поручения из этого workflow.
> Одна задача получает полный исходный JSON и весь парный Markdown, один результат
> покрывает всю тему. Вопрос задаёт условия
> и проверяет применение знания. Каждый из A–D отвечает на все части вопроса.
> Веди ученика от основ к сложным senior-сценариям. Простой вопрос проверяет
> одну мысль. Сложный кейс может связывать несколько условий одного решения.
> Бери актуальную стабильную версию и поясняй существенные различия. При
> замене сценария сохраняй исходное проверяемое понятие и привязку к Markdown.
> Ключ объясняет механизм, показывает пример, условия применения, граничное
> поведение и связь с соседней темой. Каждый дистрактор разбирает отдельное
> правдоподобное заблуждение, его источник, гипотетическое следствие и верный
> подход. Разбирай случаи, в которых похожее правило действительно работает.
> Для ложной гарантии объясни, чем её можно получить. Используй код в примере,
> когда он проясняет механизм, иначе дай конкретный сценарий словами.
> Сохраняй полезную детализацию дорегенерационного JSON этой темы. Создавай
> сразу все 17 секций блока: пять у единственного ключа и по четыре у трёх
> дистракторов. Код, данные и схемы, необходимые до ответа, бери из материалов
> Markdown. Возвращай владельцу теории недостающие входные данные и блоки.
> Записывай развёрнутый JSON с отступом в два пробела и возвращай
> путь к одному полному файлу. После записи не проверяй и не вычитывай файл.
> Если без изменения видимого вопроса невозможно дать единственный корректный
> ответ, передай координатору собранный возврат. Markdown и код не меняй.

## Цель для автора шпаргалок

> /goal Улучшай только Markdown шпаргалок по действующему плану и поручениям
> координатора. Устраняй существенные ошибки по первоисточнику для нужной
> версии. Сохраняй номера и структуру вопросов. Если для однозначного ответа
> нужны версия, сценарий или ограничения, вынеси их в видимый заголовок.
> Если для решения нужен код, SQL, лог или Mermaid-схема, помести его в
> извлекаемый блок соответствующего Q. Учти, что тренажёр показывает первый
> подходящий блок кода и первую Mermaid-схему. В обоих материалах оставляй
> вводные задачи и убирай подсказки, раскрывающие ключ до ответа.
> Передавай полный Markdown с путём, исходной версией, изменёнными Q и
> источниками. При занятом файле готовь отдельный снимок. JSON и код вне
> зоны этой цели.

## Цель для инженера тренажёра

> /goal Развивай UI и код тренажёра по действующей инженерной очереди и
> поручениям координатора. Перед правкой сопоставь задачу с текущим кодом,
> критерием воспроизведения и занятостью файлов. Проводя адресные тесты,
> проверь затронутый пользовательский сценарий. В handoff укажи изменения,
> выполненные проверки и открытый остаток. Если ход повторяется без результата,
> установи причину и продолжай следующий доступный инженерный пакет.
> Шпаргалки, production MCQ и контентные гейты вне зоны этой цели.

## Правило для всех этапов

Требования к обучающему содержанию, контракту и форматированию применяются
при генерации и записи. После записи готовый файл передаётся и переносится
целиком, без проверки, вычитки или валидаторов. Сборка, CI и приложение
обходятся без специальных проверок MCQ-файлов. Обычная десериализация JSON
нужна приложению для чтения данных.

Снятие существующих проверок в сборке и загрузчике — отдельная инженерная
задача. Этот документ задаёт правило и не подтверждает, что код уже изменён.
