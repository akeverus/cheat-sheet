# Запуск и передача MCQ другой LLM

Полный промпт: [PROMPT_PLAN_INTERVIEW](../../PROMPT_PLAN_INTERVIEW.md).
План: [PLAN_INTERVIEW](../../PLAN_INTERVIEW.md).
Проверки всех файлов: [file-checklist](file-checklist.md).
Последняя точка продолжения: [checkpoint.json](checkpoint.json).
Контракт evidence: [reviews/README](reviews/README.md).

## Экзаменационная проверка и повторный аудит

Применяй [режим экзаменатора](examiner-review.md): каждый вариант должен быть
полноценным ответом на все части видимого вопроса, даже если его модель неверна.
В текущем запрошенном LLM re-audit включены все существующие production-файлы,
в том числе готовые и ранее принятые. Это основание повторного прохода, а не
требование бесконечно перепроверять неизменённые блоки после каждого шага.

Файл можно передать LLM целиком; дробление допустимо только с явным полным покрытием
всех Q/B и A/B/C/D. В раскрытом проходе читаются все sections и нужная теория.
Сохраняй сравнительную таблицу четырёх вариантов и отдельные SFPL/ANSC/RU, факты,
связь с вопросом и объяснения. Re-audit и строгая FINAL — разные результаты;
историческое evidence не удаляется и не становится новым PASS автоматически.

## Сообщение для запуска другой LLM

Передай исполнителю **текущий рабочий каталог** и следующее короткое поручение.
Оно является точкой входа; подробные критерии остаются в полном промпте:

> Продолжи проверку и улучшение всего production MCQ в этом рабочем каталоге.
> Прочитай применимые инструкции репозитория, `PROMPT_PLAN_INTERVIEW.md`,
> `PLAN_INTERVIEW.md` и `docs/mcq-quality/workflow.md`. Сохрани все существующие
> staged, unstaged и untracked изменения. Проверь `git status --short`, затем запусти
> `doctor`, `status` и `next --size 4` через `scripts/mcq-workflow.py`.
> Действительные статусы выводи из текущего содержимого и evidence; checkpoint —
> подсказка, а не источник PASS. Продолжай следующий пакет полным циклом, включая
> CONTENT, FACTS, LINKAGE, SECTIONS, SFPL, ANSC, RU, независимые фазы A/B и FINAL.
> Сохраняй результаты и точный остаток после каждого законченного пакета. Экономь
> лимит на повторном чтении, но не сокращай обязательное покрытие. Дополнительные
> агенты допустимы только с явно выбранной дешёвой моделью. Не делай commit/push.

Если передан только чистый clone без текущих изменений, сначала восстанови полный
рабочий каталог; продолжать по числам старого checkpoint в таком clone нельзя.

## Установка и проверка

Требуются Git, Python 3.10+ и зависимости `scripts/requirements-mcq.txt`.
Для shell gates нужен Bash. Node, конкретный провайдер LLM и его платные API
для инфраструктуры не требуются. Java нужна только при изменении приложения.

Из корня репозитория:

```bash
python3 -m venv work/mcq-venv
work/mcq-venv/bin/python -m pip install -r scripts/requirements-mcq.txt
source work/mcq-venv/bin/activate
python3 scripts/mcq-workflow.py doctor
python3 -m unittest discover -s scripts/tests -p 'test_mcq*.py'
python3 scripts/mcq-workflow.py status
python3 scripts/mcq-workflow.py next --size 4
```

Перед запуском на другой машине или в новой сессии проверь, что передан именно
**текущий рабочий каталог**, а не только коммит HEAD. На момент подготовки процесса
скрипт, workflow, checkpoint и часть evidence были незакоммиченными; отдельно
скопированный чистый clone не воспроизводит достигнутую приёмку. Сохраняй staged,
unstaged и untracked файлы, включая `docs/mcq-quality/runs/` незавершённых проходов.
Сначала зафиксируй исходный `git status --short`, ветку и HEAD; не очищай рабочее дерево.
Сравни живые `status`/`next` с checkpoint: при расхождении разберись, что изменилось,
вместо ручного исправления производных статусов. При неоконченном run сначала проверь
его `manifest.json`, phase A и disclosure, затем продолжи допустимую фазу или создай
новый run; не считай частичный run принятым evidence.

Если подходящее окружение уже есть, переиспользовать его. Скрипты находят репозиторий
по своему пути, а не по текущему каталогу. Все передаваемые относительные пути
отсчитываются от корня. `status` пересчитывает структуру и evidence текущего дерева,
не доверяет сохранённому `audit-state.json` и не запускает дорогие эвристики.
Ошибка структуры останавливает этот быстрый путь: подробности выдаёт structural gate.

Коды возврата: 0 — операция выполнена, 1 — обнаружены нарушения в gates либо не выполнен
`sync --require-complete`, 2 — ошибка запуска/аргументов/доказательства. READY и exit 0
не означают, что корпус принят. `doctor` проверяет доступность, формат записей и пути;
актуальность блоков проверяют `status`, `next`, `record` и полный audit.

## Один пакет от начала до конца

Команда `next` выдаёт точную тему, Q/B и незакрытые проверки. Ниже переменные — пример;
подставить реальные значения из вывода. Диапазоны вроде Q1–Q4 не поддерживаются:
каждый B перечисляется отдельно, включая B1 и следующие.

```bash
MCQ_TOPIC='ai-ml/agentic-patterns-interview.json'
MCQ_BLOCKS='Q1:B0,Q2:B0,Q3:B0,Q4:B0'
MCQ_RUN="$(date -u +%Y%m%dT%H%M%SZ)-agentic-q1-q4-r1"
python3 scripts/mcq-workflow.py packet --topic "$MCQ_TOPIC" --blocks "$MCQ_BLOCKS" --output work/mcq-author-packet.json
```

Автор читает пакет, нужные правила, проверяет источники, исправляет только указанные
seed/Markdown и запускает gates. Пакет содержит ключ: слепому ревьюеру его не передавать.
Теория дана один раз на Q, общий пролог включён. При смысловой зависимости от другого Q
или файла автор добавляет нужный контекст и объявляет `coverage[].dependencies`.
Скрипт не выводит смысловые зависимости самостоятельно.

После завершения правок заморозить пакет для ревью:

```bash
python3 scripts/mcq-workflow.py prepare --topic "$MCQ_TOPIC" --blocks "$MCQ_BLOCKS" --run "$MCQ_RUN"
```

В `docs/mcq-quality/runs/<run>/` создаются `manifest.json` и `blind-input.jsonl`.
Ключ и теория ещё не экспортированы. Независимому ревьюеру в свежем контексте
передать **только** blind-input и короткое задание фазы A из полного промпта.
Доступ к общему диску не обеспечивает изоляцию сам по себе: ревьюеру запрещено
читать seed, теорию, старые ответы, evidence и историю координатора до фиксации выбора.

Ревьюер возвращает JSON-массив, один элемент на каждый Q/B:

```json
[
  {
    "q_number": 1,
    "block_idx": 0,
    "choice": "B",
    "reason": "Короткая проверяемая причина выбора без внутренней цепочки рассуждений.",
    "form_signals": []
  }
]
```

Кроме A/B/C/D допустимы `AMBIGUOUS`, `NO_VALID_OPTION`, `UNSURE`. Не заставлять ревьюера
угадывать, если он видит два ответа или не знает. Массив сохранить, например,
в `work/mcq-phase-a-answers.json`, затем:

```bash
python3 scripts/mcq-workflow.py phase-a --run "$MCQ_RUN" --answers work/mcq-phase-a-answers.json --reviewer reviewer-context-01
python3 scripts/mcq-workflow.py reveal --run "$MCQ_RUN" --author author-context-01 --reviewer reviewer-context-01
```

`--model` в reveal необязателен. Это запись фактически использованной модели, **не выбор
модели и не запуск агента**. Неизвестную модель оставить null. Reviewer/author — реальные
различимые контексты или люди, а не две придуманные подписи одного прохода.

Фаза A сохраняется с фактическим временем и SHA; повторная запись запрещена.
`reveal` атомарно создаёт каталог `disclosure/` с квитанцией раскрытия,
`review-input.json` и `evidence-draft.json`. При сбое публикации раскрытие можно повторить.
Тот же независимый ревьюер продолжает фазу B по раскрытому пакету и источникам.
В черновике намеренно нет PASS и checks пустые. До заполнения он не является evidence.

## Результат и исправления

Заполнить `coverage[].checks` только выполненными проверками: `{status, reason}`.
Список технических имён приведён в reviews/README и полном промпте. Добавить источники
с проверенными утверждениями/версиями/датой, findings, реальные ограничения и дату
завершения. Ненужные NOT_RUN не записывать: отсутствие проверки сохраняет прежний
результат либо оставляет NOT_RUN. Хеши не выдумывать и не подгонять под новую версию.

Для полного разбора можно сохранить отдельный артефакт в каталоге run и привязать его
через `review_artifact: {path, sha256}`. В `automatic_review` сохранить ссылки на разбор
сигналов. Инструмент проверяет привязку review_artifact, но не понимает содержание
редакторских выводов и не доказывает честность независимости. Это ответственность
исполнителя и координатора.

```bash
python3 scripts/mcq-workflow.py record --input "docs/mcq-quality/runs/$MCQ_RUN/disclosure/evidence-draft.json"
python3 scripts/mcq-workflow.py status --topic "$MCQ_TOPIC"
python3 scripts/mcq-workflow.py checkpoint --next-action 'Следующая тема и точные блоки; конкретный незакрытый вопрос, если есть.'
```

`record` добавляет новый `reviews/checks/<review_id>.json` без перезаписи. Проверяет
метаданные, текущие полные и блочные хеши, правила, артефакты, последовательность фаз,
непротиворечивость PASS и выполненность предусловий FINAL. Повторный review_id запрещён.
FAIL допустим и необходим для сохранения находок; BLOCKED требует поля `blocker`.
Неполный FINAL PASS, пустые FACTS-источники, поддельная слепота и STALE отклоняются.

Подтверждённый дефект оформить как OPEN с устойчивым id/check/blocks/reason. Новое PASS
само по себе его не закрывает: требуется RESOLVED того же finding и актуальная проверка.
Один finding id нельзя переиспользовать для другой проверки или другого набора блоков.
Неуспешный проход сохраняется; новая попытка получает новый run/review_id.

После правок выполнить новый `prepare`. Даже если изменились только sections, текущий
консервативный контракт инвалидирует результаты этого блока; неизменённые другие блоки
сохраняются. Если изменился общий пролог, инвалидируется тема. Общие правила также входят
в SHA; редактура этих трёх файлов без нужды расходует повторный review. Перед импортом
требуется совпадение полных хешей: если параллельно менялась другая часть темы, сначала
явно сверить изменения и пересобрать metadata. Уже зарегистрированные результаты
применяются по блочным хешам, без обнуления всей темы.

## Контрольные точки и передача

```bash
python3 scripts/mcq-workflow.py sync
```

Команда пересчитывает все диагностики, производные `audit-state.json`, `file-checklist.md`
и `checkpoint.json`. Выполнять после законченной темы или группы пакетов, после изменения
общих валидаторов и перед передачей. На промежуточных пакетах достаточно topic status
и checkpoint. `sync --require-complete` дополнительно возвращает 1 при незавершённом
корпусе, включая BLOCKED. Обычный sync не требует искусственного зелёного backlog.

Checkpoint — компактный указатель, не второй источник истинности. Evidence и current
контент остаются источниками результата. `next` вычисляет очередь заново, обходит
полностью BLOCKED-темы и показывает их отдельно. Новый запуск использует checkpoint,
doctor и next; без новой причины повторный смысловой аудит принятых неизменённых
блоков не нужен. Явное поручение свежего полного LLM-аудита является такой причиной.

Одновременно один автор изменяет тему, один координатор регистрирует результаты.
Скрипт защищает файлы от случайной перезаписи, но не заменяет распределённую систему
блокировок. При нескольких машинах синхронизировать Git и владение пакетами до правок.
Артефакты принятого ревью хранятся в `docs/mcq-quality`, не только в игнорируемом work/.
Копирование репозитория с текущими изменениями переносит процесс без истории чата.
Commit/push выполняются только по отдельному поручению; скрипты их не вызывают.

Перед передачей выполни `sync` на контрольной точке, затем сохрани краткий
`checkpoint --next-action` с конкретной темой, Q/B, незавершённой фазой и существенным
блокером. `sync` сам перезаписывает checkpoint стандартным следующим действием,
поэтому пользовательское `next-action` записывается последним.
Передай план, промпт, workflow и каталог с текущими изменениями. Получатель сначала
читает checkpoint и сверяет его с живым `status`/`next`; сохранённые цифры не имеют
приоритета над текущим содержимым и evidence. Если остался открытый finding, его id,
проверка и блоки должны быть в сохранённом evidence, а не только в сообщении чата.

## Устаревшие сценарии

Удалены отслеживаемые Git адаптеры старого orchestration runtime:

- `scripts/mcq-tools/author_wf.js` — принуждал к 12–15 словам, одинаковым запятым и
  позиции correct в середине ранжирования длины; схема теряла второй блок вопроса.
- `scripts/mcq-tools/verify_wf.js` — выдавал материал теории в «слепую» фазу;
  отсутствие block_idx допускалось схемой.
- `scripts/mcq-tools/struct_fix_wf.js` — подгонял символы и пунктуацию под фиксированные
  коридоры; противоречил содержательной проверке полноты.
- `scripts/mcq-struct/struct_fix_wf.js` — старый вариант с идентификацией только по Q,
  запрещавший исправлять correct даже при подтверждённом дефекте.
- `.claude/wf-mcq-gen.js` и `.claude/wf-security-mcq.js` — generate-only сценарии:
  требовали жёсткой ротации ключа и фиксированных соотношений длины sections,
  завершая работу без отдельной приёмки CONTENT, SFPL/ANSC и RU.

Замена: `packet` → точечная авторская правка → `prepare/phase-a/reveal/record`.
CLI не генерирует ответы сам. Прямых активных исполняемых потребителей удалённых
адаптеров не найдено; упоминания в исторических reviews сохранены как происхождение.
Последняя проверенная версия для восстановления: Git commit
`fc30b686daa9c9deb5d2e8565e77fa9e02545c15`. Просмотр:
`git show fc30b686daa9c9deb5d2e8565e77fa9e02545c15:<relative_path>`.
Текущая очистка не удаляет Git-историю и не создаёт commit автоматически.

Оставлены production gates, самостоятельные диагностические утилиты, все доказательства
пройденных и неудачных ревью и уникальные архивные материалы. Наличие старой даты само
по себе не основание для удаления. Старые инструкции внутри archive/reviews не являются
действующими правилами процесса.
