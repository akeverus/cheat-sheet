## Блокирующие находки

1. **Q3 C — неверный способ создания мока.** Вызов `mock(Class)` без квалификации требует видимого метода: например, static import или наследования. Mockito 4.10/Java 21 не отменяют разрешение имён Java. Type-inferred `Mockito.mock()` — другая возможность. Нельзя считать две записи одного фабричного метода третьим новым механизмом с обещанием «без static import».
2. **Q5 B/C — InjectMocks.** Выбирается самый большой конструктор, а не самый большой полностью удовлетворимый; недостающие ссылочные аргументы могут получить null. После успешного конструктора нет обязательного прохода по остальным сеттерам/полям. Best effort не означает, что любая ошибка инициализации игнорируется: исключение из конструктора реально приводит к InjectMocksException. B обещает внедрение всех моков; C требует более точного ложного тезиса вместо широкого отрицания initialization errors. [InjectMocks 5.11.0](https://github.com/mockito/mockito/blob/v5.11.0/src/main/java/org/mockito/InjectMocks.java).
3. **Q9/Q28/Q29 — strict stubbing.** Несовпадение аргументов не всегда возвращает default: STRICT_STUBS может бросить **PotentialStubbingProblem**. В материале смешаны предупреждение WARN и ошибка строгого режима, встречаются выдуманные названия исключений. Lenient снимает проверки и unused, и argument mismatch для стаба; verify остаётся независимым. Реализация 5.11.0 учитывает, в частности, source-file heuristic — не любой новый аргумент обязательно даст эту ошибку. [DefaultStubbingLookupListener](https://github.com/mockito/mockito/blob/v5.11.0/src/main/java/org/mockito/internal/junit/DefaultStubbingLookupListener.java).
4. **Q10 D — doReturn не для void.** `doReturn(value).when(mock).voidMethod()` компилируется, но настройка отклоняется CannotStubVoidMethodWithReturnValue. Это отличается от `when(voidMethod())`, которое не компилируется. Для void применяют doNothing/doThrow/doAnswer. В Q32 нельзя приписывать реальный запуск коду, который не компилируется.
5. **Q23 — lifecycle и сохранённые ссылки.** AfterEach расширения завершает сессию, освобождает ресурсы и проверяет strictness; это не эквивалент reset всех сохранённых объектов. Воспроизведён PER_CLASS: новое поле Mock во втором тесте и старый constructor-injected mock внутри уже созданного InjectMocks SUT, включая прежний stub. Новый field reference не гарантирует отсутствие протечек во всём графе. [MockitoExtension 5.11.0](https://github.com/mockito/mockito/blob/v5.11.0/subprojects/junit-jupiter/src/main/java/org/mockito/junit/jupiter/MockitoExtension.java).
6. **Q25 — неработающий UUID-пример.** `UUID.fromString(...)` вызывается уже внутри активного MockedStatic<UUID>. Незастабленный статический вызов получает default null; fixedId становится null. Создать значение следует до открытия scope. Попутно нужны ограничения потока и явное закрытие; try-with-resources — рекомендуемый способ закрыть control, не единственный синтаксис.
7. **Q26 A — String и enum.** Даже inline maker не позволяет mock(String.class), а enum в обычном inline-сценарии мокируется. Q26 прямо противоречит Q36. Нужен пример своего final-класса, разграничение String/Class/wrappers/private/native и возможностей выбранного maker. Универсальное утверждение, что inline всегда медленнее, этим аудитом не измерено. [InlineDelegateByteBuddyMockMaker 5.11.0](https://github.com/mockito/mockito/blob/v5.11.0/src/main/java/org/mockito/internal/creation/bytebuddy/InlineDelegateByteBuddyMockMaker.java).
8. **Q27 — deep stubs и альтернативы.** Теория говорит о новом моке при каждом промежуточном вызове, а sections правильно опровергают это: совместимые повторные вызовы переиспользуют промежуточный мок. Не следует гарантировать ненулевой ответ для любой цепочки/типа. Wrong D может быть разумной рекомендацией для неизменяемого чужого fluent API; нужен однозначный ошибочный механизм вместо спорной общей рекомендации.
9. **Q30 B — последнее значение и последний Answer.** Постоянный thenReturn в конце повторяет значение; оставшийся последним динамический Answer вызывается снова и может возвращать новое значение счётчика. Корректный ответ сейчас объединяет эти случаи с неверной общей формулой.
10. **Q34 C — выдуманный числовой критерий дизайна.** Пять моков не доказывают нарушение SRP. Value objects могут иметь поведение; реальные экземпляры обычно выбирают из-за простоты и соответствия цели теста. Mock репозитория уместен для unit-теста, но не проверяет реальный SQL. Нужно решение по проверяемому контракту, а не запрет Mockito по количеству зависимостей.
11. **Q37/Q39 — defaultAnswer и captor.** Custom defaultAnswer получает InvocationOnMock и может выбирать результат по методу/аргументам, поэтому широкое отрицание этого в Q37 A допускает второе разумное прочтение. Captor технически работает в stubbing: это не рекомендуемый обычный приём, но sections Q7/Q39 неправильно объявляют его невозможным. Captor хранит ссылку, не снимок состояния на момент вызова. Диагностику даёт последующее assertion, а matcher можно снабдить описанием.
12. **Q41 B.sections/C — неверная модель потоков.** Два потока могут одновременно иметь отдельные статические моки одного класса. Ошибка duplicate registration возникает при повторном активном scope того же класса в **одном** потоке. Утверждение, что разные потоки автоматически конфликтуют, опровергнуто ограниченным конкурентным тестом.
13. **Q42 A — объект и конструктор.** Mock является Java-объектом; по умолчанию конструктор часто обходится, но useConstructor позволяет инициализировать состояние. thenCallRealMethod сам конструктор не вызывает. Spy также может иметь null-зависимости: нельзя обещать ему общую безопасность, а mock описывать как «нет экземпляра».
14. **Q44 C — Kotlin.** Kotlin поддерживает inline reified type parameters; wrapper как раз использует их для mock<T>(). mockito-kotlin не включает inline mock maker вместо настройки Mockito. Java matcher dummy-null и адаптация Kotlin нуждаются в точных границах; данный пример verify(save) не содержит предшествующего save. Нужны явный Act и версия API. [Kotlin reified](https://kotlinlang.org/docs/inline-functions.html#reified-type-parameters), [Mocking.kt 5.4.0](https://github.com/mockito/mockito-kotlin/blob/5.4.0/mockito-kotlin/src/main/kotlin/org/mockito/kotlin/Mocking.kt), [Matchers.kt 5.4.0](https://github.com/mockito/mockito-kotlin/blob/5.4.0/mockito-kotlin/src/main/kotlin/org/mockito/kotlin/Matchers.kt).
15. **Q45 sections — выдуманная настройка.** `mockito.strictness` в junit-platform.properties не является прочитанным параметром MockitoExtension 5.11.0. Передача его через Launcher не выключила unused-stub failure. Следует описать MockitoSettings, наследование и приоритет per-stub/per-mock/session. LENIENT не отключает verify и ошибки типов.

Дополнительные уточнения: Q1 C ошибочно называет Testcontainers in-memory БД; Q2/Q6/Q31 spy копирует состояние вместо гарантированного делегирования исходному объекту, причём ссылки могут быть общими; Q7 generic declaration не означает глубокую runtime-проверку типов элементов; Q8 openMocks применим и в JUnit 5, возвращает AutoCloseable; Q11 нельзя обещать вызов конструктора exception-class; Q16 учитывает историю, включая setup, а STRICT_STUBS помечает использованные stubs проверенными; Q19 matcher должен безопасно обрабатывать null, для primitives нужны соответствующие matchers; Q20 InOrder не требует смежности, но не отменяет проверку числа совпадающих вызовов, а ordered noMore не запрещает все пропущенные ранние вызовы; Q22 различие cache key не означает обязательное пересоздание уже кешированного контекста; Q24 reset сохраняет mock settings и real fields spy; Q35 scope construction ограничен потоком и временем жизни control; Q38 SMART_NULLS сначала возвращает стандартные пустые значения, а не всегда SmartNull; Q40 синхронный callback не проверяет реальное планирование асинхронности; Q43 parameter mocks отличаются от полей и не питают автоматически InjectMocks. Подробные локальные notes охватывают каждый вопрос.
