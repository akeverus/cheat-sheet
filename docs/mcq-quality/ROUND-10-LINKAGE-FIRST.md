# ROUND-10 — LINKAGE-FIRST

**Статус:** активный авторитетный документ методологии MCQ.
**Заменяет:** ROUND-8 и ROUND-9 целиком. Все документы этих раундов — исторические.
**Дата принятия:** 2026-08-11.

---

## 0. Одно предложение

MCQ в этом проекте — не банк вопросов для собеседования, а **инструмент закрепления того материала,
который пользователь только что прочитал в конкретном `## Q<N>` шпаргалки**.

---

## 1. Реальная механика приложения (проверено в коде)

В UI пользователь видит ровно две вещи:

```
заголовок "## Q<N> <вопрос>" из cheatsheets/interview/**/<topic>.md
+
варианты A/B/C/D из seed/mcq/**/<topic>.json
```

`question_text` пользователю **не показывается**. Это проверяется по коду, а не по договорённости:

- `McqJsonLoader.buildDesiredOptions()` собирает строки для БД только из
  `opt.label()`, `opt.text()`, `opt.correct()`, `opt.order()`, `opt.sections()` и `block.blockIdx()`.
- `question_text` десериализуется в DTO `McqSeedBlock`, но никуда не пишется и никуда не рендерится.
- Единственная связь блока с вопросом — `questionRepository.findIdByTopicAndQuestionNumber(topic, q_number)`.

Отсюда главный вывод раунда:

> **Настоящий stem — visible-заголовок `## Q<N>`. `question_text` — служебное поле.**

Проектировать варианты вокруг `question_text` — значит проектировать их вокруг текста, которого пользователь
никогда не увидит. Именно это и породило дефект, из-за которого запущен ROUND-10.

Контракт закреплён тестом `McqVisibleLinkageContractTest`, чтобы будущий раунд снова не начал считать
`question_text` видимым stem'ом.

---

## 2. Source of truth

Для блока с `q_number = N` содержательный источник — только:

```
## Q<N> <видимый вопрос>
<весь ответ этого Q в шпаргалке>
```

Внутрь входит всё, что есть в теле Q: код, таблицы, перечисления, диаграммы, оговорки, рекомендации.

Соседние `Q<N±1>` читать можно **только чтобы не дублировать их**. Использовать их материал для ответа
на текущий Q запрещено: блок обязан быть локально решаемым.

---

## 3. Шкала LINKAGE

| Уровень | Смысл | Приёмка |
|---|---|---|
| **L4** | Правильность correct и ложность всех трёх wrong прямо следуют из Q<N> | PASS |
| **L3** | То же самое, но формулировки сильно перефразированы | PASS после подтверждения рецензентом |
| **L2** | Тема связана, но нужен факт извне | FAIL |
| **L1** | Совпадает только технология/раздел | FAIL |
| **L0** | MCQ фактически проверяет другой вопрос | FAIL |

Целевой корпус — преимущественно L4.

---

## 4. Восемь обязательных полей блока

Для статуса FINAL все восемь обязаны быть ✅:

| Код | Проверка |
|---|---|
| `VIS` | `question_text` совпадает по намерению с visible-заголовком |
| `SRC` | проверяемый тезис существует в материале Q<N> |
| `ANS` | правильный вариант выводится из Q<N> |
| `D-A` `D-B` `D-C` | каждый неправильный вариант **опровержим** материалом Q<N> (нужна дословная цитата) |
| `NOV` | ни один вариант не требует факта вне Q<N> |
| `AXIS` | все четыре варианта отвечают на один и тот же видимый вопрос |

`D-*` — самое частое место провала. Недостаточно, чтобы correct поддерживался материалом:
если пользователь не может отбросить дистрактор по прочитанному тексту, блок не работает как закрепление.

## 5. Иерархия приоритетов

1. Прямая связь с visible Q и его материалом
2. Фактическая корректность
3. Answerable from source
4. Ровно один защитимый ответ
5. Все wrong refutable from source
6. Согласованность `text` ↔ `sections`
7. Правдоподобность дистракторов
8. Естественный русский язык
9. Anti-guessability
10. Баланс A/B/C/D
11. Метрики длины и формата
12. Косметическая симметрия

**Пунктом 1 нельзя жертвовать ради пункта 9 или 11.** Это главное отличие от ROUND-8/9.

## 6. Что изменилось относительно ROUND-8/9

| Правило | Было | Стало |
|---|---|---|
| `SKEL` (единый surface skeleton всех 4 опций) | **HARD gate** | **SOFT / диагностика.** Ищет очевидную форму-подсказку, но не заставляет переписывать честный короткий MCQ в четыре искусственных абзаца |
| Минимальная длина опции (≥22 слова) | HARD | **Отменена.** Опция настолько коротка, насколько возможно, и настолько полна, насколько необходимо |
| Бюджет прозы секций (correct 102–109 слов, wrong ≥86) | целевая метрика | **Отменён.** Это была статистика старого корпуса, а не продуктовый контракт |
| Заимствованный механизм другого продукта как сильный дистрактор | default-стратегия | **Только если механизм явно упомянут в Q<N>** |
| Production-сценарий | средство поднять сложность | **Только если сценарий есть в самом Q<N>** |
| Главная метрика корпуса | `tell_pct = 0` | **100% блоков answerable from their own Q material.** Anti-tell остаётся обязательным, но вторичным |

Anti-tell (§9) сохранён полностью: correct не должен быть систематически длиннее, единственным
с backticks/числом/версией/двоеточием, единственным без hedging. Но чинить tell нужно **минимальной
смысловой правкой**, а не переписыванием source-bound блока в новый сюжет.

---

## 7. Модель сложности

Сложность повышается **различением изученных фактов**, а не добавлением нового материала:

- близкие понятия из самого Q;
- тонкие различия scope (все ↔ только одна категория);
- значения по умолчанию;
- порядок и жизненный цикл;
- точное распределение ответственности;
- исключения и ограничения;
- следствия.

Правило: `сложность MCQ <= сложности материала`. Если Q объясняет базовое различие API — MCQ честно
проверяет это различие. Если материал объективно слаб — сначала улучшить шпаргалку через `interview-writer`,
и только потом строить более глубокий MCQ.

---

## 8. Типовые контролируемые мутации дистрактора

Дистрактор — искажение **одной оси того же тезиса**, внутри лексической вселенной Q:

- **инверсия классификации** — синхронный ↔ реактивный;
- **инверсия ответственности** — кто обрабатывает статус: `retrieve()` ↔ `exchange()`;
- **инверсия default** — `@OneToMany` LAZY ↔ EAGER;
- **инверсия жизненного цикла** — до ↔ после;
- **ошибка scope** — все ↔ только одна категория;
- **перепутанная принадлежность** — свойство одного клиента приписано другому;
- **перепутанный модуль/зависимость** — `spring-web` ↔ `spring-webflux`.

Запрещено: вводить новый API, неизвестный внутренний механизм, другой фреймворк, production-инцидент,
которого не было, и любой факт, требующий знания вне Q.

Дистракторы обязаны оставаться правдоподобными и профессионально сформулированными. Linkage-first
**не означает**, что дистракторы должны быть глупыми, — только что их ошибка строится внутри изученного материала.

---

## 9. Порядок гейтов

Строго в этом порядке; провал гейта 1 останавливает работу над блоком:

1. **LINKAGE** — visible Q, source, claim map, answerability, refutability, AXIS, novel facts
2. **FACTS** — фактическая корректность source и MCQ
3. **UNIQUE ANSWER** — ровно один защитимый вариант
4. **DISTRACTOR QUALITY** — правдоподобность, Single-Delta
5. **SECTIONS** — согласованность `text` ↔ `sections`
6. **NATURAL RUSSIAN**
7. **ANTI-TELL** — длина, форма, стилистические подсказки
8. **POSITION BALANCE** — распределение correct по A/B/C/D

### Два жёстких правила пост-редактуры

- **§51.** После **любой** смысловой правки `option.text` ради parity/anti-tell — заново прогнать LINKAGE.
  Именно поздняя редактура ради формы исторически и уводила корпус от источника.
- **§77.** После любой правки `option.text` — перечитать и переписать его секции.
  Старые секции после смысловой правки считаются недействительными по умолчанию.

## 10. Что проверяется машинно, а что — нет

`scripts/mcq-linkage-scan.py` даёт **детерминированные risk-сигналы**, а не приёмку.

**ERROR** (структурные факты, проверяются точно):

- `ORPHAN-Q` — `q_number` из JSON отсутствует в шпаргалке;
- `STEM-DRIFT` — `question_text` ушёл от visible-заголовка (containment < 0.34);
- `NOVEL-TERM` — в вариантах есть технические идентификаторы, которых нет в материале своего Q;
- `NEIGHBOR-LEAK` — варианты лексически ближе к соседнему Q, чем к своему.

**WARN**:

- `MISSING-Q` — Q шпаргалки не покрыт MCQ;
- `LOW-COVERAGE` — лексическое пересечение варианта с материалом < 0.20.

### Лексическая метрика — сигнал, а не приёмка

Нельзя сказать «coverage 0.40 — хорошо, 0.39 — плохо». Честный парафраз может иметь низкое лексическое
пересечение и при этом быть L4. Поэтому:

```
lexical metric  → risk signal
semantic review → acceptance gate
```

Но экстремально низкая coverage (порядка 0.03–0.07) **обязана** уходить на ручной/LLM linkage review:
принимать такие блоки без доказанного source mapping запрещено.

### Запрет на metric gaming

Повышать `coverage` копированием предложений источника, повторением терминов, укорачиванием опций
или отказом от полезной терминологии — **дефект**, а не улучшение. Linkage семантическая.
Естественный парафраз разрешён и полезен для retrieval practice: он не меняет смысл, не расширяет scope,
не добавляет требование и не вводит новый механизм.

### Чего машина не умеет

Ни schema, ни `validate_a`, ни `form_scan`, ни parity, ни SKEL, ни leak-скан не способны сказать
«этот MCQ проверяет материал Q<N>». `LINKAGE PASS` требует source-aware семантического ревью.

---

## 11. Обязательные ревьюеры

**Source-blind reviewer** получает: visible Q<N>, полный материал Q<N>, четыре варианта.
Не получает: `question_text`, `correct`, секции.
Обязан: выбрать ответ только по материалу; для каждого варианта привести **дословную цитату**,
подтверждающую или опровергающую его; отметить факты, которых в материале нет; оценить L0–L4.
Если цитаты нет — вердикт `undecidable_from_source`, и это FAIL.

**Adversarial linkage reviewer** пытается забраковать каждый блок вопросом:
«Какой конкретный фрагмент Q<N> позволяет пользователю понять, почему этот вариант верен или неверен?»
Не может показать фрагмент — FAIL.

**Student simulation** — главный user acceptance test: пользователь не знает тему, читает только Q<N>,
закрывает ответ, видит visible Q + A/B/C/D. Сможет ли внимательный человек ответить?

---

## 12. Приёмка

**Блок PASS:** VIS/SRC/ANS/D-A/D-B/D-C/NOV/AXIS ✅, L3 или L4, факты верны, ровно один защитимый ответ,
дистракторы правдоподобны и различны, секции согласованы, русский естественный, correct не угадывается
по форме, схема и loader валидны.

**Файл AUDITED:** все Q source-mapped; L2 = L1 = L0 = 0; novel required facts = 0; все дистракторы
refutable; factual/unique/sections/anti-tell пройдены; распределение A/B/C/D приемлемо; schema и тесты
зелёные; sidecar заполнен.

---

## 13. Процесс

**Одна итерация = один topic JSON, пересобранный целиком.** Не один вопрос, не несколько файлов поверхностно.

Полная пересборка означает полную пересборку: файл не считается пересобранным, если сохранено большинство
старых вариантов, поправлен `question_text` и заменена пара дистракторов. Каждый блок проектируется заново
от source claim. Старая формулировка сохраняется только если после source-first ревью она объективно лучшая, —
это исключение, а не режим по умолчанию.

Порядок: git → прочитать шпаргалку целиком → инвентарь visible Q → claim map → старый MCQ **только как
anti-baseline** → пересборка JSON → `question_text` из visible title → source-bound опции → секции →
LINKAGE → факты → уникальность ответа → anti-tell → **повторный LINKAGE** → валидаторы → loader/тесты →
sidecar → сверка файла с источником → пометить AUDITED.

Артефакты:

- манифест и курсор — `docs/mcq-quality/linkage-reset-manifest.json`;
- sidecar на тему — `docs/mcq-quality/reviews/<topic_slug>.json`;
- эталоны — `docs/mcq-quality/golden-linkage-examples.md`;
- анти-эталоны — там же, раздел «Anti-golden».

Резервные копии рядом с файлом (`*-old.json`, `*-backup.json`) **не создавать** — история хранится в git.
`git reset --hard` и `git clean -fd` в этом процессе запрещены: сбрасывается приёмка, а не история.

## 14. Reset приёмки

Корпус, созданный методологией ROUND-8/9, считается **UNTRUSTED FOR LINKAGE**. Ни один старый `FINAL ✅`
не переносится. Старые файлы разрешено использовать как анти-примеры, как источник правдоподобных
заблуждений и для сверки фактов — но финальный текст каждого файла строится заново от шпаргалки.

Каждый раунд самостоятельно пересчитывает свои цифры (число файлов, блоков, распределение L0–L4,
coverage). Цифры из старых README не копируются; при расхождении приоритет у свежесгенерированного отчёта.

7026 ошибок и 7627 блоков на ревью — эти числа завышены и не используются.

## 15. Условие остановки раунда

Раунд останавливается, когда все целевые файлы `AUDITED`, все блоки L3/L4, L0/L1/L2 отсутствуют,
каждый correct source-supported, каждый wrong source-refutable, нет требуемого нового знания,
нет hidden-stem drift, факты проверены, секции синхронизированы, anti-tell пройден, schema/тесты/сборка
зелёные, и методология соответствует реальной механике UI.

Косметические правила после этого не добавляются. Правило добавляется только если отвечает на вопрос
«какой конкретный дефект оно предотвращает»; иначе оно не добавляется. Слои «правило → уточнение →
исключение → коррекция коррекции» не накапливаются: при смене методологии авторитетный документ
переписывается целиком.

## 16. Заметки, добытые на первом файле

Первый файл раунда — `spring-rest-client-interview` — доведён до `AUDITED` и служит эталоном принципа
(не образцом длины и пунктуации). Что он показал:

**Враждебное ревью находит дефекты в теории, а не в вариантах.** Из 13 блоков первого прохода ни один
не имел второго защитимого ответа, но нашлось 11 правок в самой шпаргалке: внутреннее противоречие про
статус `RestTemplate`, ребро диаграммы, которое прямо подкрепляло ложный вариант, невалидный Java-код
и три устаревших факта. Порядок «verify source → fix source → rebuild claims» — не формальность.

**Правило перепроверки после anti-tell правки подтвердилось на практике.** Правка «наследуются целиком»
→ «наследуется всё», сделанная ради снятия формальной подсказки, внесла фактическое переобобщение,
которое поймал следующий рецензент. Точность выше формы: если выбор стоит между корректной
формулировкой и снятием слабого tell — побеждает формулировка.

**Ролевая схема секций не является подсказкой.** У правильного варианта 5 секций (включая `example`
с кодом), у неправильных — 4. Рецензент отметил это как возможный tell, но `renderExplanation()`
кладёт секции в поле, которое показывается ПОСЛЕ ответа: на момент выбора пользователь видит только
тексты вариантов. Гоняться за этим не нужно.

**Дефект источника бывает шире одного файла.** Устаревшее «`RestTemplate` НЕ помечен `@Deprecated`»
нашлось ещё и в `spring-webflux-interview.md`. Найдя ошибку в теории, стоит прогнать её формулировку
по всему корпусу, а не чинить точечно.

**Инструмент проверки нужно проверять.** Закрывающая граница слова в детекторе подсказок оказалась
литеральным байтом `0x08` вместо `\b` — регулярка не совпадала ни с чем, проверка абсолютных маркеров
молча не работала, а гейт при этом рапортовал «0 подсказок». Зелёный вывод гейта не является
доказательством, пока не проверено, что гейт вообще что-то проверяет.

|---|---|---|
| Второй защитимый ответ | **0** | **0** |

| Замечания к самой шпаргалке | 11 (все исправлены) | 94 |

Вывод, который стоит держать в голове весь раунд:

> **Linkage-контракт не ломается. Ломается точность.**

На 43 блока не нашлось ни одного случая, где по материалу можно было бы защитить не тот вариант,
и почти не нашлось дистракторов, которые нечем отбросить. То есть source-first проектирование
даёт ровно то, ради чего затевалось. Зато фактические ошибки и рассогласованные пояснения
исчисляются десятками.

### Практические следствия

**1. Зелёные гейты ничего не говорят о фактах.** Оба файла проходили schema, linkage-скан и
anti-tell **полностью зелёными** ровно в тот момент, когда враждебное ревью находило в них
десятки фактических ошибок. Ни один детерминированный скрипт не способен заметить, что
`14:30:00Z` и `14:30:00+02:00` — разные моменты, что `ETag` показан заголовком запроса,
что `426` отдан без обязательного `Upgrade` или что процитирован несуществующий эндпоинт
чужого API. Файл без враждебного прохода принимать нельзя, каким бы зелёным ни был отчёт.

**2. Основной улов — в шпаргалке, а не в вариантах.** 105 замечаний к теории против 25
блокирующих к MCQ. Это ожидаемо: MCQ пишется от материала, поэтому наследует его ошибки и
заодно делает их видимыми. Работая над MCQ, вы фактически проводите фактчек теории — и
порядок «verify source → fix source → rebuild claims» надо соблюдать, а не считать формальностью.

**3. Дефект теории обычно шире одного файла.** Устаревший статус `RestTemplate` нашёлся ещё
в одном файле, а RFC 7807 без упоминания заменившего его RFC 9457 — в одиннадцати. Найдя
ошибку в теории, прогоняйте её формулировку по всему корпусу, а не чините точечно.

**4. Правка ради формы вносит ошибки в смысл.** Замена «наследуются целиком» на «наследуется всё»,
сделанная ради снятия слабой формальной подсказки, породила фактическое переобобщение, которое
поймал следующий рецензент. Это и есть тот случай, ради которого написано правило перепроверки
после anti-tell правки. Точность выше формы: между корректной формулировкой и снятием слабого
tell побеждает формулировка.

**5. Агент выдумывает внешние факты охотнее, чем заимствует соседний Q.** Neighbor leakage за два
файла не встретился ни разу, а вот сослаться на несуществующий эндпоинт Stripe или приписать
заголовкам несуществующий RFC — встретилось. Инструкция «не добавляй фактов вне Q» должна явно
покрывать и внешние примеры: безопаснее обобщённая формулировка, чем выдуманная конкретика.

### Что это меняет в приёмке

Враждебный проход — не финальная формальность, а **основной** гейт качества; детерминированные
проверки лишь отсеивают структурный мусор перед ним. Поэтому:

- статус `AUDITED` ставится только после враждебного прохода, подтвердившего закрытие находок;
- промежуточный статус `LINKAGE_DONE` означает «связь с материалом закрыта и измерена, факты — нет»;
- при невозможности провести проход (недоступность агентов) файл остаётся `LINKAGE_DONE`,
  и это записывается в манифест с причиной — а не выдаётся за приёмку.

## 18. Ремонт сам порождает дефекты: сходимость и как её добиться

На втором файле раунда (`api-design-best-practices`, 30 блоков) враждебная проверка запускалась
четыре раза, с ремонтом между проходами.

| Проход | Проверено блоков | Блокирующих находок |
|---|---|---|
| 1 | 30 | 25 |
| 2 | 16 | 4 |
| 3 | 14 | 10 |
| 4 (только 11 отремонтированных) | 11 | 11 |

Четвёртый проход нашёл в **отремонтированных** блоках столько же дефектов, сколько было до ремонта.
Процесс не сходился.

### Механизм

Ремонт переписывал секции целиком. Каждая переписанная секция — это новая проза, новая проза — это
новые утверждения, а часть новых утверждений оказывается неверной. Один блок несёт 17 секций
(5 у правильного варианта и по 4 у трёх неправильных); при ориентире 2–4 предложения это порядка
сорока-пятидесяти предложений на блок, и каждое — самостоятельный фактический риск.

Показательно, что **три из одиннадцати находок четвёртого прохода внёс не агент, а правка источника,
сделанная между проходами**: формулировка «для собственных исключений тело в любом случае собирают
руками» (ложно: наследник `ErrorResponseException` рендерится инфраструктурой), приписывание
Boot-свойств «Spring Framework 6», где их нет, и переусердствовавшее «звёздочка тут вообще не
сработает» (верно только для `credentials: include`, но не для `Authorization: Bearer`).
Правка ради исправления ошибки внесла три новые — ровно тот же механизм, только у человека.

### Что из этого следует

**1. Ремонт — минимальная хирургия, а не переписывание.** Чинить нужно ровно то предложение,
на которое указала находка, не трогая соседние. Инструкция ремонтному агенту должна это требовать
явно и запрещать переписывать секции, к которым претензий не было.

**2. Объём прозы — фактор качества, а не только читаемости.** Чем длиннее секции, тем больше
утверждений, тем больше из них ошибочно. Ориентир 2–4 предложения на секцию — это потолок, а не цель;
секция, которой хватает одного предложения, должна остаться одним предложением.

**3. Абсолютные формулировки в пояснениях — источник ложности.** «В любом случае», «вообще не
сработает», «всегда», «единственный» почти всегда оказываются опровержимы краевым случаем.
В секциях их следует избегать так же, как в вариантах, — но по другой причине: не ради anti-tell,
а потому что они чаще всего просто неверны.

**4. Правка источника обесценивает блоки, собранные по старой версии.** После любой правки шпаргалки
нужно перечитывать блоки затронутого Q — включая `question_text`, который может остаться со старой
формулировкой. Для дословного расхождения `question_text` с заголовком в сканер добавлена проверка
`STEM-MISMATCH`; смысловые расхождения ловятся только чтением.

**5. Число проходов ограничено.** Если после двух ремонтов файл продолжает давать находки того же
порядка, дело не в файле, а в способе ремонта. Продолжать в том же режиме — тратить проходы впустую;
нужно менять контракт ремонта, а не добавлять раунды.
