## Q1. Что такое RESTful Web Services?

**RESTful Web Services** — это архитектурный стиль разработки веб-приложений, основанный на принципах **REST (Representational State Transfer)**. **RESTful** сервисы используют стандартные **HTTP** методы (GET, POST, PUT, DELETE), чтобы выполнять операции с ресурсами, представленными через уникальные **URL**-адреса. Они не хранят состояние, масштабируемы и позволяют передавать данные в разных форматах, таких как **XML** или **JSON**. **RESTful Web Services** позволяют разработчикам построить распределенные системы, которые связывают между собой разные платформы и устройства. Это позволяет строить гибкие и масштабируемые приложения.



## Q2. Что такое ресурс REST?


Ресурс **REST** представляет собой идентифицируемый объект или информацию, доступ к которой осуществляется через **URL**-адрес. Ресурс может быть представлен любым объектом, например, пользователями, книгами, заказами и т. д. Ресурсы должны быть персистентными и обладать семантикой изменения состояния через **HTTP** методы (GET, POST, PUT, DELETE). Каждый ресурс имеет уникальный идентификатор (URI), который позволяет клиентам взаимодействовать с ним. **RESTful** сервисы предоставляют операции для работы с ресурсами, такие как создание, чтение, обновление или удаление, что делает их гибкими и удобными в использовании.



## Q3. Что такое URI?

**URI (Uniform Resource Identifier)** — это строка символов, которая идентифицирует уникальный ресурс или его локацию в сети. **URI** представляет собой стандартизированный способ указать, где находится определенный ресурс и как к нему можно обратиться. **URI** может быть представлен в виде **URL (Uniform Resource Locator)**, который указывает на конкретное местоположение ресурса в сети, или в виде **URN (Uniform Resource Name)**, который предоставляет уникальное имя ресурса, но не указывает его точное расположение. **URI** позволяет клиентам обращаться к различным ресурсам веб-сервисов и осуществлять операции с ними с помощью стандартных **HTTP** методов.



## Q4. (ВАЖНО) - Какие особенности RESTful Web Services?

**RESTful Web Services** имеют несколько особенностей:

1. Архитектурный стиль: **RESTful Web Services** следуют принципам **REST (Representational State Transfer)**. Они строятся вокруг ресурсов, которые представляются через уникальные **URI**, и используют стандартные **HTTP** методы для выполнения операций над этими ресурсами.
2. Клиент-серверная архитектура: **RESTful Web Services** основаны на принципе разделения клиентского и серверного кода. Сервер предоставляет ресурсы, а клиент взаимодействует с ними, отправляя запросы и получая ответы.
3. Кэширование: **RESTful Web Services** поддерживают кэширование, что позволяет клиентам сохранять локальную копию ресурсов и использовать ее для повторных запросов, если ресурсы не изменились.
4. Поддержка различных форматов данных: **RESTful Web Services** могут передавать данные в разных форматах, таких как **XML** или **JSON**. Это позволяет клиентам легко взаимодействовать со службами и использовать данные в формате, удобном для них.
5. **Stateless (без сохранения состояния)**: **RESTful** сервисы не хранят информацию о состоянии клиента между запросами. Каждый запрос считается изолированным и автономным, и работа сервиса не зависит от состояния клиента.

Все эти особенности делают **RESTful Web Services** гибкими, масштабируемыми и удобными в использовании для разработки распределенных систем и взаимодействия между разными платформами и устройствами.



## Q9. (ВАЖНО) - Какие недостатки RESTful Web Services?


Веб-сервисы, построенные на архитектуре **RESTful**, обладают рядом преимуществ, таких как простота в использовании, масштабируемость и поддержка кэширования. Однако они также имеют некоторые недостатки:

1. Слабая стандартизация: **RESTful** не предоставляет строгих стандартов и рекомендаций для реализации веб-сервисов. Это может привести к разнородности в подходах и сложностям в интеграции между различными сервисами.
2. Ограниченный функционал: **RESTful** ориентирован на работу с **CRUD**-операциями (Create, Read, Update, Delete) над ресурсами. Это означает, что некоторые более сложные операции могут быть труднее реализовать или требуют дополнительного усилия.
3. Отсутствие формального описания: **RESTful** не предоставляет явного формального описания для веб-сервисов, который может помочь разработчикам в понимании и использовании сервисов. Это может затруднить работу с сервисами, особенно при интеграции со сторонними системами.
4. Слабая безопасность: **RESTful** не предоставляет встроенных механизмов безопасности, и разработчики должны самостоятельно обеспечивать механизмы аутентификации и авторизации для своих сервисов.
5. Производительность: **RESTful Web Services** часто используются по протоколу **HTTP**, который может быть неэффективным при передаче большого объема данных или в ситуациях с низкой пропускной способностью сети.

Несмотря на эти недостатки, **RESTful** остается одним из наиболее популярных подходов для разработки веб-сервисов, благодаря своей простоте, гибкости и поддержке широкого круга разработчиков и инструментов.

## Q10. (ВАЖНО) - Как происходит обмен сообщениями с точки зрения RESTful Web Services?

Обмен сообщениями в веб-сервисах, построенных на архитектуре **RESTful**, основан на использовании протокола **HTTP (Hypertext Transfer Protocol)**. В **RESTful** взаимодействии информация передается между клиентом и сервером в виде **HTTP** запросов и ответов. Вот основные этапы обмена сообщениями в **RESTful Web Services**:

1. Клиент отправляет **HTTP** запрос на сервер. Запрос включает метод (GET, POST, PUT, DELETE и т. д.), **URL**-адрес ресурса, с которым клиент хочет выполнить операцию, и дополнительные заголовки, которые могут указывать на желаемый формат ответа, аутентификацию и другие детали.
2. Сервер получает **HTTP** запрос и анализирует его для определения запрашиваемого действия и ресурса. Он обрабатывает запрос и генерирует **HTTP** ответ.
3. Сервер отправляет **HTTP** ответ обратно клиенту. Ответ включает статусный код (например, 200 OK, 404 Not Found), заголовки (например, Content-Type для указания типа содержимого) и, возможно, тело ответа с данными, запрошенными клиентом.
4. Клиент получает **HTTP** ответ и анализирует его. Заголовки могут указывать на результат операции (например, успешная или неудачная операция), а тело ответа содержит данные, которые клиент может использовать.
5. При необходимости клиент может повторить этот процесс, отправляя новые запросы или выполняя дополнительные операции над ресурсами.

Обмен сообщениями в веб-сервисах **RESTful** основан на простоте протокола **HTTP** и взаимодействии по схеме "клиент-сервер". Клиент отправляет запросы на сервер, а сервер отвечает на эти запросы с помощью **HTTP** ответов. Этот обмен позволяет клиентам и серверам взаимодействовать и обмениваться данными и командами в единообразном формате.



## Q5. (ВАЖНО) - Что такое Stateless?

**Stateless (без сохранения состояния)** — один из основных принципов архитектуры **RESTful**. Он означает, что каждый запрос к **RESTful Web Service** должен содержать все необходимые данные для обработки запроса, и сервер не должен хранить информацию о состоянии клиента между запросами.

В контексте **RESTful Web Services** состояние клиента относится к любой информации, которую сервер должен хранить о клиенте для обработки последующих запросов. Принцип без сохранения состояния требует, чтобы сервер не хранил состояние клиента и каждый запрос рассматривался как отдельный, изолированный запрос. Это означает, что клиент должен предоставить все необходимые данные, такие как токены аутентификации, параметры запроса и информацию о состоянии, с каждым запросом. Сервер должен обрабатывать запрос, используя только предоставленные данные в этом запросе и не зависеть от предыдущих запросов или состояния клиента.

Принцип без сохранения состояния упрощает масштабирование серверов, позволяет кэшировать ответы и обеспечивает независимость клиента от сервера. Клиент может быть реализован на любой платформе и взаимодействовать с разными серверами без необходимости следить за состоянием клиента. **Состояние клиента** — это информация, которая характеризует текущее положение и контекст клиента во взаимодействии с веб-сервисом. Это может быть любая информация, которую клиент передает или получает от сервера и которая остается актуальной в рамках сеанса работы с веб-сервисом.

Примеры состояния клиента включают:

1. Аутентификационные данные: Информация о логине и пароле или токен аутентификации, используемые для идентификации клиента и подтверждения его прав доступа. Эта информация может быть сохранена в состоянии клиента и передаваться в каждом запросе для аутентификации на сервере.
2. Сессионные данные: Информация, связанная с текущей сессией работы пользователя с веб-сервисом. Например, идентификатор сессии, который позволяет серверу связать последующие запросы с определенным пользователем или сохранить прогресс пользователя в рамках сеанса работы.
3. Контекст данных: Любая другая информация, которая может быть передана или сохранена на клиентской стороне и использоваться в последующих взаимодействиях с веб-сервисом. Например, фильтры, настройки, предпочтения пользователя и т.д.

Состояние клиента часто используется для поддержки связанных операций во время взаимодействия с веб-сервисом, где каждый запрос может быть зависим от предыдущих операций или требовать дополнительной информации, полученной в рамках предыдущих запросов. Однако, в RESTful веб-сервисах состояние клиента должно быть сохранено на стороне клиента, а не на сервере, в соответствии с принципом без состояния.



## Q6. Что вы понимаете под JAX-RS?

**JAX-RS (Java API for RESTful Web Services)** — это набор спецификаций для разработки и реализации веб-служб с использованием архитектуры **RESTful** в **Java**. **JAX-RS** предоставляет стандартизированный подход для создания **RESTful Web Services**, упрощая процесс разработки и интеграции таких служб. **JAX-RS** определяет аннотации и классы, которые позволяют разработчикам создавать ресурсы, определять методы **HTTP**, обрабатывать запросы и генерировать ответы в различных форматах данных. Он предлагает гибкую модель программирования, которая позволяет быстро создавать **RESTful Web Services** на основе классов **Java**. **JAX-RS** обеспечивает удобный способ связать методы **Java** с **HTTP**-запросами, обрабатывать параметры запроса и генерировать ответы в формате **JSON**, **XML** и других поддерживаемых форматах данных. Он также поддерживает возможность валидации запросов, управления ошибками и настройки путей доступа к ресурсам. **JAX-RS** является частью **Java EE (Enterprise Edition)** и может быть использован в любых сервлетах и контейнерах приложений **Java EE**. Он позволяет разработчикам быстро создавать мощные и масштабируемые **RESTful Web Services**, следуя стандартам и лучшим практикам.



## Q7. (ВАЖНО) - Что такое коды состояния HTTP?


Коды состояния **HTTP (HTTP status codes)** это числовые значения, которые возвращаются сервером в ответ на запросы клиента в протоколе **HTTP (Hypertext Transfer Protocol). Коды состояния сообщают клиенту информацию о процессе обработки его запроса и состоянии ответа сервера.

Коды состояния **HTTP** разделены на несколько категорий:

1.1xx: Информационные коды состояния, которые указывают, что запрос клиента был успешно получен и сервер продолжает обработку.
2.2xx: Коды состояния успеха, которые указывают, что запрос клиента был успешно получен, понят и принят сервером.
3.3xx: Коды состояния перенаправления, которые указывают, что для выполнения запроса клиента требуется дополнительная обработка или перенаправление.
4.4xx: Коды состояния ошибок клиента, которые указывают на ошибки в запросе клиента, например, некорректный запрос или отсутствие доступа к ресурсу.
5.5xx: Коды состояния ошибок сервера, которые указывают на ошибки сервера при обработке запроса клиента, например, внутренняя ошибка сервера.

Некоторые из наиболее распространенных кодов состояния **HTTP** включают:

1.200 OK: Запрос успешно обработан.
2.404 Not Found: Запрашиваемый ресурс не найден на сервере.
3.500 Internal Server Error: Внутренняя ошибка сервера.

Знание кодов состояния **HTTP** важно при разработке и отладке веб-служб, поскольку они помогают понять результат выполнения запроса и принять соответствующие действия на стороне клиента или сервера.



## Q8. (ВАЖНО) - Что такое методы HTTP?


Методы **HTTP (HTTP methods), также известные как глаголы **HTTP, определяют тип операции или действие, которое требуется выполнить с ресурсом на сервере. Каждый запрос **HTTP** должен содержать определенный метод, который указывает серверу, какое действие нужно выполнить.

Наиболее распространенные методы **HTTP** включают:

1. GET: Запросить данные или ресурс с сервера. Используется для получения информации.
2. POST: Отправить данные на сервер для обработки. Используется для создания нового ресурса или выполнения изменений на сервере.
3. PUT: Заменить ресурс на сервере данными, которые отправляются с запросом. Используется для обновления существующего ресурса.
4. DELETE: Удаление ресурса на сервере. Используется для удаления существующего ресурса.
5. PATCH: Изменение существующего ресурса на сервере. Используется для частичного обновления ресурса.
6. HEAD: Получение только заголовков ответа без тела сообщения. Используется для получения метаданных о ресурсе.

Кроме указанных выше методов, существуют и другие, такие как **OPTIONS, TRACE** и **CONNECT, но они менее распространены.

Выбор правильного метода **HTTP** зависит от типа операции, которую вы хотите выполнить с ресурсом на сервере. Использование соответствующего метода важно для соблюдения принципов архитектуры **RESTful** и обеспечения правильного взаимодействия между клиентом и сервером.



## Q9. (ВАЖНО) - Что такое заголовки HTTP?


Заголовки **HTTP (HTTP headers)** это часть сообщения, которая передается между клиентом и сервером в протоколе **HTTP (Hypertext Transfer Protocol). Заголовки представляют собой метаданные, которые содержат информацию о запросе или ответе, включая дополнительные инструкции или метки для обработки сообщения.

Заголовки **HTTP** состоят из имени и значения. Имя заголовка указывает на тип информации, предоставляемой значением заголовка. Значение заголовка представляет собой собственно данные или инструкции, связанные с данным заголовком.

Некоторые из наиболее распространенных заголовков **HTTP** включают:

1. Content-Type: Определяет тип контента или данные, которые отправляются или принимаются. Например, text/html** для **HTML-**содержимого или **Application/json** для **JSON-**данных.
2. User-Agent: Позволяет серверу идентифицировать пользовательский агент **(например, браузер или клиентское приложение), который сделал запрос.
3. Authorization: Используется для передачи данных аутентификации или авторизации, например, токена авторизации.
4. Accept: Указывает на тип контента, который клиент может принять.
5. Loсation: Используется для указания нового **URL-**адреса в случае перенаправления.
6. Cookie: Содержит информацию о сохраненных файлах **cookie** и передается между клиентом и сервером.

Заголовки **HTTP** позволяют клиенту и серверу обмениваться дополнительной информацией, которая помогает правильно обрабатывать запросы и управлять ответами. Они играют важную роль в протоколе **HTTP** и используются для различных целей, включая управление сеансами, аутентификацию, кэширование и дополнительную обработку сообщений.



## Q11. (ВАЖНО) - В чём разница SOAP от REST?

**SOAP (Simple Object Access Protocol)** и **REST (Representational State Transfer)** — это два различных подхода к созданию веб-сервисов. Они имеют ряд ключевых различий:

1. Архитектура:
 1. SOAP** основан на **XML** и использует строго типизированные сообщения для обмена данными. Он оперирует на уровне операций над удаленными объектами.
 2. REST** основан на архитектурных принципах веба, таких как использование **URL-**адресов для идентификации ресурсов и использование **HTTP** методов для выполнения операций над ними. REST** ориентирован на работу с ресурсами.
2. Протоколы:
 1. SOAP** может использовать различные протоколы для передачи сообщений, включая **HTTP, SMTP, FTP** и другие. Он обеспечивает независимость от протокола обмена сообщениями.
 2. REST** основан на протоколе **HTTP** и использует его методы **(GET,POST,PUT,DELETE** и т. д.)** для операций над ресурсами. REST** полностью соответствует протоколу **HTTP.
3. Формат данных:
 1. **SOAP** сообщения обычно сериализуются в **XML** и могут содержать комплексные структуры данных, определенные в **XML** схеме. Они могут быть более громоздкими и менее читабельными.
 2. **REST** может использовать различные форматы данных для представления ресурсов, такие как **JSON**, **XML**, **HTML** и другие. **JSON** обычно является наиболее распространенным выбором, благодаря его простоте и компактности.
4. Состояние:
 1. **SOAP**-сервисы могут хранить состояние клиента между запросами (stateful).
 2. **REST** является без сохранения состояния (stateless): каждый запрос от клиента должен содержать все необходимые данные для выполнения операции, и сервер не хранит информацию о состоянии клиента.

**SOAP** и **REST** предлагают различные подходы к созданию веб-сервисов, и выбор между ними зависит от требований проекта, предпочтений разработчиков и особенностей среды внедрения. **SOAP** обладает большей гибкостью и мощными возможностями для работы с объектами, в то время как **REST** более прост в использовании и широко принят в веб-разработке.



## Q21. (ВАЖНО) - Что выбрать SOAP или REST?


Определение того, какой тип веб-сервисов (**SOAP** или **REST**) использовать, зависит от ряда факторов:

1. Сложность и гибкость: Если вам требуется большая гибкость в определении структуры сообщений и поддержке сложных операций, то **SOAP** может быть предпочтительным выбором. **SOAP** поддерживает более формальную спецификацию и определение интерфейсов с использованием языка **WSDL (Web Services Description Language)**.
2. Производительность: Если вам важна скорость и производительность, **REST** может быть предпочтительным выбором. **RESTful Web Services** работают на базе протокола **HTTP** и используют его методы, такие как **GET**, **POST**, **PUT** и **DELETE**. **REST** также поддерживает кеширование, что может улучшить производительность.
3. Использование ресурсов: Если вашей основной задачей является доступ к ресурсам и управление ими, то **REST** может быть более подходящим вариантом. **RESTful** архитектура опирается на ресурсно-ориентированную модель и работу с **URL**-адресами, что делает доступ и управление ресурсами более естественным.
4. Экосистема: Рассмотрите экосистему, окружающую ваши приложения и инфраструктуру. Если у вас уже есть существующая инфраструктура, которая хорошо поддерживает один из типов, это может повлиять на ваш выбор. Например, если ваша команда имеет опыт работы с **SOAP**-сервисами или использует инструменты, которые хорошо интегрируются с **SOAP**, это может быть преимуществом.
5. Поддержка клиентов: Учтите, какие клиентские приложения будут использовать ваш веб-сервис. **SOAP** и **REST** могут иметь различную поддержку в разных клиентских библиотеках или платформах. Убедитесь, что ваш выбранный тип веб-сервиса поддерживается вашими клиентами.

Это лишь некоторые факторы, которые следует учесть при выборе типа веб-сервисов. В конечном итоге, выбор будет зависеть от ваших конкретных требований и условий проекта.



## Q12. Рекомендации по создание URI


При создании **URI (Uniform Resource Identifier)** для веб-служб существуют некоторые рекомендации и практики, которые следует соблюдать:

1. Используйте существительные: **URI** должен содержать существительные, которые ясно и однозначно описывают ресурс или коллекцию ресурсов. Используйте их во множественном числе для представления коллекций.
2. Избегайте глаголов: **URI** не должен содержать глаголов, так как они соответствуют операциям, выполняемым с ресурсом, и могут быть переданы в **HTTP** методах (например, GET, POST, PUT, DELETE).
3. Используйте маленькие буквы: Рекомендуется использовать только строчные буквы в **URI**, чтобы избежать путаницы и возможных ошибок при регистре.
4. Используйте дефисы для разделения слов: Для улучшения читабельности, можно использовать дефисы для разделения слов в **URI** вместо пробелов или подчеркиваний.
5. Будьте организованы и последовательны: **URI** должен быть логически организован и последователен в своей структуре. Используйте иерархическую структуру, отображающую иерархию ресурсов.
6. Будьте консистентны: Следуйте одному стилю написания **URI** в рамках всего приложения или **API**, чтобы обеспечить консистентность.
7. Избегайте длинных URI: Старайтесь создавать **URI**, которые не являются слишком длинными и сложными. Более длинные **URI** могут быть менее читаемыми и создавать проблемы с безопасностью и переносимостью.
8. Поддерживайте стабильность: При выборе **URI** для ресурсов, старайтесь сохранять их стабильность, чтобы клиенты могли надежно ссылаться на них без необходимости сортировки нескольких местоположений.
9. Используйте понятные и информативные имена: **URI** должен использовать понятные и информативные имена, которые ясно отражают суть ресурса или операции, выполняемые над ним.

Соблюдение этих рекомендаций поможет создать понятные и удобочитаемые **URI** для веб-служб, что в свою очередь улучшит понимание и использование сервиса клиентами.



## Q13. Какие передовые методы разработки RESTful Web Services?


Существует несколько передовых методов разработки **RESTful Web Services**, которые позволяют создавать эффективные и гибкие системы:

1. Использование HTTP-методов: **RESTful API** должно полностью использовать возможности **HTTP** протокола. Основные методы **HTTP**, такие как **GET**, **POST**, **PUT** и **DELETE**, используются для выполнения различных операций с ресурсами.
2. Назначение правильных URI: Хорошо спроектированные **URI** должны быть информативными, уникальными и отображать иерархию ресурсов. Они должны быть логическими и однозначными, чтобы их использование было интуитивно понятно для клиентов.
3. Использование статуса HTTP: **RESTful API** должно активно использовать коды состояния **HTTP** для уведомления клиентов о результатах выполнения запросов. Например, коды **200 (OK)**, **201 (Created)**, **204 (No Content)** и др. сигнализируют о успешном выполнении операции.
4. Предоставление репрезентаций данных: Результаты запросов должны быть представлены в удобочитаемом формате, например, в **JSON** или **XML**. **RESTful API** должно поддерживать возможность выбора клиентом предпочитаемого формата.
5. Аутентификация и авторизация: Для защиты и контроля доступа к ресурсам **RESTful API** должно предоставлять механизмы аутентификации и авторизации, такие как токены доступа, OAuth и другие стандартные методы.
6. Версионирование API: Если **API** изменяется со временем, запланируйте различные версии **API**, чтобы сохранить обратную совместимость с клиентами, которые все еще используют предыдущие версии.
7. Кэширование: Используйте механизмы кэширования **HTTP** для эффективного использования ресурсов и ускорения обработки запросов.
8. Гибкость: **RESTful API** должно быть гибким и способным приспосабливаться к изменяющимся требованиям. Разделение ресурсов на независимые компоненты с помощью правильного проектирования позволяет легко изменять и масштабировать систему.

Эти методы являются передовыми при разработке **RESTful Web Services**, и их использование поможет создать эффективные и гибкие сервисы, которые будут легко взаимодействовать с клиентами.



## Q14. Что такое идемпотентные методы?


Идемпотентные методы — это методы, которые могут быть безопасно вызваны несколько раз без изменения состояния сервера. Это означает, что если вы вызовете идемпотентный метод один или несколько раз, результат будет таким же, как если бы вы вызывали его только один раз.

В контексте **RESTful Web Services** идемпотентность крайне важна. Веб-сервис **RESTful** должен быть спроектирован таким образом, чтобы клиентское приложение могло выполнять операции, такие как создание, обновление или удаление ресурсов, безопасно и повторно.

Преимущества использования идемпотентных методов в веб-сервисах **RESTful**:

1. Повторяемость: Когда клиентское приложение должно отправить запрос повторно, идемпотентные методы гарантируют, что состояние сервера не изменится. Это позволяет клиенту точно повторить операцию, не беспокоясь о нежелательных побочных эффектах.
2. Отказоустойчивость: В случае сбоя или потери соединения, идемпотентные методы позволяют клиентскому приложению снова отправить запрос без необходимости беспокоиться о состоянии сервера или возможном дублировании операции.
3. Продолжительность: Идемпотентные методы позволяют выполнять длительные операции в состоянии "атомарности". Клиентское приложение может повторять такие запросы с определенной периодичностью, пока не получит результат.
4. Кэширование: Идемпотентные методы соответствуют принципам кэширования **HTTP**. Клиент может кэшировать результаты запросов и повторно использовать их при необходимости, без необходимости повторного выполнения операции на сервере.

В заключение, использование идемпотентных методов в веб-сервисах **RESTful** имеет ключевое значение для обеспечения надежной и безопасной работы с ресурсами. Это обеспечивает повторяемость, отказоустойчивость, продолжительность и допускает кэширование результатов запросов, что становится незаменимым при разработке масштабируемых и надежных систем.



## Q15. В чем разница между REST и AJAX?

**REST (Representational State Transfer)** и **AJAX (Asynchronous JavaScript and XML)** — это два разных подхода к веб-разработке, которые, хотя и используются вместе, имеют разные цели и функции. **REST** — это архитектурный стиль, который определяет принципы, по которым веб-сервисы могут быть построены для обеспечения стандартизированного и эффективного взаимодействия между клиентскими и серверными системами. Ресурсы **REST** представляются в формате **URL (Uniform Resource Locator)**, и клиенты могут получать, создавать, обновлять и удалять ресурсы с помощью стандартных **HTTP** методов, таких как **GET**, **POST**, **PUT** и **DELETE**. **AJAX**, с другой стороны, это подход, который позволяет клиентскому приложению общаться с сервером асинхронно, без необходимости перезагрузки всей веб-страницы. **AJAX** использует **JavaScript** для отправки асинхронных запросов на сервер, а затем разбирает данные, полученные в ответе, обновляя только нужные части веб-страницы.

Таким образом, основная разница между **REST** и **AJAX** заключается в следующем: **REST** — это архитектурный стиль, определяющий принципы для построения веб-сервисов, где клиенты могут получать, создавать, обновлять и удалять ресурсы с помощью стандартных **HTTP** методов. **AJAX** — это подход, который позволяет асинхронно обновлять определенные части веб-страницы, отправляя асинхронные запросы на сервер и обновляя страницу без ее полной перезагрузки.

Вместе они часто используются для создания более интерактивных и отзывчивых веб-приложений, где клиентский интерфейс может общаться с сервером без задержек и без перезагрузки всей веб-страницы.



## Q16. (ВАЖНО) - Какие основные компоненты HTTP-Request?


Основные компоненты **HTTP**-запроса включают:

1. Метод (Method): Метод указывает, какое действие должно быть выполнено над ресурсом на сервере. Некоторые из часто используемых методов включают **GET**, **POST**, **PUT** и **DELETE**.
2. **URI (Uniform Resource Identifier)**: **URI** представляет целевой ресурс на сервере, с которым клиентская сторона хочет взаимодействовать. Он может быть абсолютным **URL** или относительным путем к ресурсу на сервере.
3. Заголовки (Headers): Заголовки предоставляют дополнительную информацию о запросе. Они включают заголовки, такие как **Content-Type** (тип содержимого запроса), **Authorization** (авторизация), **User-Agent** (информация о клиенте) и многие другие.
4. Параметры запроса (Query Parameters): Параметры запроса предоставляют данные, которые могут быть добавлены к **URI** для передачи серверу. Они добавляются после символа "?" в **URI** и имеют формат "ключ=значение", разделенные амперсандом "**&**".
5. Тело запроса (Request Body): Тело запроса содержит данные, которые могут быть отправлены на сервер. Оно используется обычно для методов **POST** и **PUT**, где нужно передать данные для создания или обновления ресурса.

Вместе эти компоненты формируют полноценный **HTTP**-запрос, который отправляется на сервер для выполнения соответствующего действия на ресурсе.



## Q17. (ВАЖНО) - Какие основные компоненты HTTP-Response?


Основные компоненты ответа **HTTP** включают:

1. Статусный код (Status Code): Статусный код представляет результат выполнения запроса и указывает на успешность или ошибку. Некоторые из распространенных статусных кодов включают **200** (Успешный), **404** (Не найдено) и **500** (Внутренняя ошибка сервера).
2. Заголовки (Headers): Заголовки в ответе содержат дополнительную информацию о ресурсе или о самом ответе. Некоторые из часто используемых заголовков включают **Content-Type** (тип содержимого ответа), **Set-Cookie** (установка куки), **Cache-Control** (управление кэшированием) и другие.
3. Тело ответа (Response Body): Тело ответа содержит основное содержимое, передаваемое от сервера клиентской стороне. Это может быть **HTML**-код, **JSON**-данные, файлы, изображения и другие форматы данных.

Вместе эти компоненты формируют полноценный **HTTP**-ответ, который содержит информацию о статусе выполнения запроса и данные, которые клиентская сторона может использовать для отображения или выполнения дальнейших операций.



## Q18. Что такое адрессация?


Адресация в контексте **RESTful Web Services** описывает способ идентификации и обращения к ресурсам на сервере с использованием системы **URI (Uniform Resource Identifier)**.

В **RESTful Web Services, каждый ресурс представлен уникальным **URI, который указывает на местонахождение ресурса на сервере. URI** состоит из двух основных частей: базового адреса службы и пути к конкретному ресурсу.

Базовый адрес службы (**Base Service URL**) обычно указывает на корневую точку веб-службы и может выглядеть так: `http://example.com/api/`. Это первая часть **URI**, которая определяет общий адрес для всех ресурсов, связанных с данной веб-службой.

Путь к ресурсу **(Resource Path)** добавляется к базовому адресу службы и определяет конкретный ресурс, с которым клиентская сторона хочет взаимодействовать. Например, http://example.com/api/users/1** указывает на ресурс "пользователь" с идентификатором "**1**".

Таким образом, адресация веб-служб **RESTful** основывается на системе **URI**, где каждый ресурс имеет уникальный адрес, состоящий из базового адреса службы и пути к ресурсу. Это позволяет клиентской стороне легко идентифицировать и обращаться к конкретным ресурсам на сервере.



## Q19. В чем разница между PUT и POST?


Главная разница между методами **PUT** и **POST** в архитектуре **REST** заключается в их назначении и семантике.

Метод **POST (создание)** используется для создания нового ресурса на сервере. Когда клиентская сторона отправляет запрос методом **POST, сервер обрабатывает запрос и создает новый ресурс под уникальным идентификатором. Повторные запросы с теми же данными могут привести к созданию дубликатов ресурса.

Метод **PUT (обновление)** используется для обновления или замены существующего ресурса на сервере. Когда клиентская сторона отправляет запрос методом **PUT, сервер выполняет обновление ресурса с использованием предоставленных данных. Если ресурс еще не существует, то он может быть создан с использованием предоставленных данных.

Важно отметить, что метод **PUT** обычно предполагает полное замещение ресурса на сервере, то есть все данные, включая неизмененные поля, должны быть отправлены вместе с запросом **PUT. В то время как метод **POST** предназначен для создания новых ресурсов и может принимать только частичные данные.

Определение использования методов `PUT` и `POST` зависит от контекста конкретной веб-службы и требований приложения. Однако, обычно, если клиентская сторона хочет создать новый ресурс, следует использовать метод `POST`, а если необходимо выполнить обновление ресурса, то метод `PUT` может быть предпочтительным выбором.



## Q20. (ВАЖНО) - Что делает RESTful Web Services легко масштабируемыми?

RESTful Web Services** обладают рядом характеристик, которые способствуют их легкой масштабируемости:

1. Отсутствие состояния (Stateless): RESTful Web Servicesful** не хранят состояния клиента на сервере. Каждый запрос от клиента содержит всю необходимую информацию для обработки запроса. Это позволяет распределить нагрузку между несколькими серверами и масштабировать службу горизонтально, добавляя новые экземпляры серверов без необходимости общего состояния.
2. Ресурсно-ориентированная архитектура: RESTful Web Services** организуются вокруг ресурсов, которые представляют собой сущности, которые клиентская сторона может использовать или модифицировать. Это позволяет гибко масштабировать индивидуальные ресурсы, например, по горизонтальному разделению баз данных или кэшированию на разных серверах.
3. Кеширование: RESTful Web Services** поддерживают кеширование, что позволяет клиентам сохранять копии ответов сервера и повторно использовать их для уменьшения нагрузки на сервер. Кеширование улучшает производительность и масштабируемость путем уменьшения количества запросов, которые сервер должен обрабатывать.
4. Ориентация на HTTP: RESTful Web Services** полагаются на стандартные протоколы и методы **HTTP, такие как **GET, POST, PUT, DELETE** и другие, для взаимодействия между клиентом и сервером. Это позволяет использовать функции, предоставляемые самим протоколом **HTTP, такие как балансировка нагрузки, кеширование и шаринг сессий, для легкой масштабируемости.

Комбинация этих характеристик позволяет **RESTful Web Services** быть легко масштабируемыми. Они позволяют гибко масштабировать индивидуальные ресурсы, использовать **Cache** для снижения нагрузки на сервер, а также добавлять и удалять экземпляры серверов для распределения нагрузки.



## Q22. (ВАЖНО) - В чём разница между WebSockets и RESTful Web Services?


Основные различия между **WebSockets** и **RESTful Web Services:

1. **Протокол**: **WebSockets** используют протокол **WebSocket**, который позволяет би-ди (двунаправленную) связь между клиентом и сервером. **RESTful Web Services**, с другой стороны, основаны на протоколе **HTTP** со своеобразным способом взаимодействия клиента и сервера.
2. **Тип связи**: **WebSockets** обеспечивают постоянное соединение между клиентом и сервером, позволяя отправлять данные в режиме реального времени. **RESTful Web Services** используют принцип «запрос-ответ», клиент посылает запрос на сервер, а сервер возвращает ответ.
3. Производительность:WebSockets** могут быть более производительными для реального времени и поточных приложений, так как устраняют накладные расходы связанные с протоколом **HTTP, такие как установка и разрыв соединения для каждого запроса. RESTful Web Services** считаются более подходящими для обмена данными, когда требуется точная контроль и защита доступа к ресурсам.
4. Гибкость:WebSockets** позволяют серверу отправлять данные клиентам в любой момент времени, независимо от запроса от клиента. RESTful Web Services** позволяют клиенту указать, какую информацию требуется получить при отправке запроса на сервер.
5. Клиентская поддержка:WebSockets** поддерживаются браузерами и большинством современных программных платформ. RESTful Web Services** также широко поддерживаются браузерами и платформами, но некоторые старые клиенты могут иметь ограниченную или отсутствующую поддержку для них.

Выбор между **WebSockets** и **RESTful Web Services** зависит от конкретных требований, типа приложения и ожидаемой работой с данными. Иногда лучшим решением может быть комбинированное использование обоих подходов в зависимости от потребностей проекта.



## Q23. (ВАЖНО) - Что такое безопасность транспортного уровня (TLS)?


Да, безопасность транспортного уровня **(TLS)** может быть реализована в **RESTful Web Services. TLS** предоставляет шифрование и аутентификацию данных, передаваемых между клиентом и сервером, защищая их от прослушивания и подделки.

Для реализации **TLS** в **RESTful Web Services, вы можете использовать **HTTPS (HTTP over TLS). При использовании **HTTPS, вся коммуникация между клиентом и сервером будет шифроваться, обеспечивая конфиденциальность данных.

Вам необходимо установить **SSL**-сертификат на ваш сервер, чтобы клиенты могли установить безопасное соединение с вашим веб-сервисом. **SSL**-сертификаты обеспечивают аутентификацию сервера и защиту от подмены или подделки.

Клиенты, в свою очередь, должны обращаться к веб-сервису по **URL**, начинающемуся с `https://` вместо `http://`, чтобы использовать защищенное соединение. **TLS** также позволяет проверить подлинность клиента перед установкой соединения. Это может быть полезно в случаях, когда веб-сервис требует аутентификации клиента перед предоставлением доступа к защищенным ресурсам.

Короче говоря, реализация безопасности транспортного уровня (**TLS**) в **RESTful Web Services** позволяет обеспечить конфиденциальность, целостность и аутентификацию данных, повышая уровень безопасности вашего веб-сервиса.



## Q24. (ВАЖНО) - Необходима ли потокобезопасность для совместного использования?


Да, если ваши ресурсы предназначены для совместного использования несколькими клиентами, важно обеспечить потокобезопасность этих ресурсов.

Потокобезопасность в контексте многопоточности означает, что ваши ресурсы могут быть безопасно доступны и изменяемы несколькими клиентами одновременно, и при этом сохраняют свою целостность и согласованное состояние.

Несколько клиентов могут пытаться получить доступ к ресурсам одновременно, и без правильного обеспечения потокобезопасности это может привести к состоянию гонки, проблемам с синхронизацией данных или непредсказуемому поведению приложения.

Существуют различные подходы для обеспечения потокобезопасности ресурсов, в зависимости от языка программирования и фреймворков, которые вы используете. Некоторые из этих подходов включают использование **блокировок (locks), мьютексов (mutexes), семафоров (semaphores)** или других механизмов синхронизации для управления доступом к ресурсам.

Важно также разработать вашу архитектуру таким образом, чтобы минимизировать возможность состояний гонки и проблем с синхронизацией. Это может включать правильное управление временем жизни ресурсов, использование транзакций или других механизмов, которые помогают согласовать доступ к ресурсам.

В целом, обеспечение потокобезопасности ресурсов является важным аспектом при разработке многопользовательских приложений, и рекомендуется провести необходимую работу по определению и реализации стратегии потокобезопасности для ваших ресурсов.



## Q25. Что такое Payload?


Полезная нагрузка **(payload)** в контексте **RESTful Web Services** представляет собой данные, которые передаются между клиентом и сервером в запросах и ответах.

В **RESTful Web Services** данные могут быть представлены в различных форматах, таких как **JSON**, **XML** или другие. Полезная нагрузка включает в себя информацию, которую клиенты передают в запросе (например, параметры запроса или тело запроса), а также данные, которые сервер возвращает в ответе.

Например, если вы отправляете запрос на получение информации о пользователе через **RESTful API**, полезная нагрузка может содержать данные просимого пользователя, такие как его имя, адрес электронной почты и другую связанную информацию.

Полезная нагрузка может также включать дополнительные данные, такие как метаданные запроса или ответа, которые могут быть полезными для клиента или сервера. Например, метаданные могут содержать информацию о версии **API**, времени создания или обновления ресурса, статус операции и др.

Эффективная работа с полезной нагрузкой является одним из ключевых аспектов при разработке **RESTful Web Services**. Оптимальный формат и структура данных помогут улучшить производительность, эффективность передачи данных между клиентом и сервером, а также лучше соответствовать потребностям клиентов и целям бизнеса.



## Q26. Можно ли отправить Payload методами GET и DELETE?


Технически, в протоколе **HTTP** методы **GET** и **DELETE** не предназначены для отправки полезной нагрузки (payload).

Метод **GET** используется для получения ресурса от сервера, и все параметры запроса обычно передаются в **URL**. Поэтому полезная нагрузка в методе **GET** обычно отсутствует и не рекомендуется передавать данные через тело запроса.

С другой стороны, метод **DELETE** используется для удаления ресурса на сервере, и аналогично, полезная нагрузка обычно не предусмотрена и не должна быть передана через тело запроса.

Вместо этого данные, связанные с **GET** и **DELETE** запросами, обычно передаются в виде параметров запроса или пути **URL**. Например, для запроса **GET** можно сделать что-то вроде: `/users?id=123`, где "id" — параметр запроса, а "123" — идентификатор ресурса, который вы хотите получить.

Если вам все же необходимо передать полезную нагрузку с использованием методов **GET** или **DELETE**, вы можете использовать вспомогательные заголовки, такие как заголовки запроса (request headers) или заголовки ответа (response headers), чтобы передавать данные, хотя это нестандартный подход и не рекомендуется в большинстве случаев.

В целом рекомендуется использовать методы **POST**, **PUT** или **PATCH** для отправки полезной нагрузки через тело запроса в **RESTful Web Services**, поскольку они предназначены для изменения или обновления ресурсов на сервере.

## Q28. Каков максимальный размер полезной нагрузки, которую можно отправить методами POST?


Максимальный размер полезной нагрузки, который можно отправить методом **POST, зависит от нескольких факторов, включая ограничения на стороне сервера и настройки клиента. Ниже приведены несколько факторов, которые могут влиять на максимальный размер полезной нагрузки:

1. **Ограничения на стороне сервера**: Веб-сервер может иметь ограничения на максимальный размер принимаемых запросов. Это может быть ограничение, установленное веб-сервером по умолчанию или настроенное администратором. Часто используется ограничение, связанное с максимальным размером запроса **HTTP**, который по умолчанию составляет около 2 МБ.
2. **Ограничения сети и промежуточного программного обеспечения**: В некоторых случаях между клиентом и сервером могут быть промежуточные сетевые устройства или программные компоненты, которые также ограничивают максимальный размер полезной нагрузки. Например, прокси-серверы или брандмауэры могут иметь свои собственные ограничения на размер запросов.
3. **Настройки клиента**: Дополнительно к ограничениям сервера, клиентские инструменты или библиотеки могут иметь собственные ограничения на размер запросов. Например, веб-браузеры могут иметь ограничение на размер заголовков или отправляемых данных.

Обычно рекомендуется отправлять полезную нагрузку, которая укладывается в пределы нескольких мегабайт. Если вам необходимо передать большие объемы данных, вы можете рассмотреть альтернативные способы, такие как передача файлов с использованием механизмов загрузки и скачивания файлов, или разделение данных на несколько запросов.

В случае необходимости передачи больших объемов данных рекомендуется рассмотреть использование метода **POST** в сочетании с механизмом передачи данных, таким как форматы мультипартного содержимого **(multipart content)** или потоковая передача данных **(streaming data). Это может позволить вам передавать полезную нагрузку поблочно, разбивая ее на маленькие части для более эффективной передачи и обработки на сервере.



## Q29. (ВАЖНО) - Что такое Basic HTTP Authentication?


Базовая **HTTP**-аутентификация (**Basic HTTP Authentication**) представляет собой простой механизм аутентификации, который используется для защиты доступа к веб-ресурсам. Она основана на отправке учетных данных (имя пользователя и пароль) в заголовке запроса.

Вот как работает базовая **HTTP-**аутентификация:

1. Клиент отправляет запрос на доступ к защищенному ресурсу, например, отправляет **GET-**запрос по **URL-**адресу защищенной страницы.
2. Сервер, которым защищен ресурс, отвечает с **HTTP-**статусом **401 Unauthorized (Неавторизован)** и заголовком **WWW-Authentiсate. В заголовке **WWW-Authentiсate** указано, что требуется базовая аутентификация. Пример заголовка: WWW-Authentiсate: Basic realm=**"**Restricted Area**".
3. Клиент получает ответ с кодом **401** и реагирует, создавая заголовок **Authorization** в следующем запросе.
4. В заголовке **Authorization** клиент кодирует имя пользователя и пароль, разделенные двоеточием, в кодировке **base64. Пример заголовка **Authorization: Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==.
5. Клиент повторно отправляет запрос с заголовком **Authorization, содержащим закодированные учетные данные.
6. Сервер проверяет учетные данные, сравнивая их с сохраненными данными. Если учетные данные совпадают, сервер возвращает запрошенный ресурс с кодом состояния **200 OK (**все в порядке**). Если учетные данные неверны, сервер возвращает код состояния **401 Unauthorized.

Заголовок **Authorization** используется для каждого последующего запроса, пока сессия не истечет или клиент не выйдет из системы.

Обратите внимание, что базовая **HTTP-**аутентификация не шифрует учетные данные, поэтому не рекомендуется использовать ее без передачи данных по защищенному соединению **(HTTP over SSL/TLS).



## Q30. (ВАЖНО) - В чем разница между идемпотентными и безопасными HTTP методами?


Разница между идемпотентными и безопасными методами **HTTP** заключается в их поведении и последствиях при повторении одного и того же запроса.

1. Идемпотентные методы HTTP:
 1. Идемпотентные методы означают, что повторное выполнение одного и того же запроса не приведет к изменению состояния сервера.
 2. Независимо от количества повторений запроса, результат будет одинаковым.
 3. Примеры идемпотентных методов: GET, HEAD, PUT, DELETE, OPTIONS.

1. Безопасные методы HTTP:
 1. Безопасные методы означают, что повторное выполнение одного и того же запроса не приведет к изменению состояния сервера, а также не должно иметь побочных эффектов.
 2. Они не изменяют данных на сервере, а только получают информацию.
 3. Примеры безопасных методов: GET, HEAD, OPTIONS.

Отличия между идемпотентными и безопасными методами заключаются в их назначении и предназначении. Идемпотентные методы позволяют повторять запросы без нежелательных побочных эффектов или неоднозначных изменений, в то время как безопасные методы гарантируют, что запрос не будет менять данные и не будет иметь побочных эффектов, независимо от повторения.

Однако следует отметить, что серверная реализация может не всегда соответствовать ожидаемому поведению идемпотентных и безопасных методов. Поэтому при разработке и использовании **API** необходимо обращать внимание на соответствие методов их стандартной семантике.



## Q38. Что такое @RequestMapping?


Аннотация **@RequestMapping** является одной из основных аннотаций в **Spring MVC, и она используется для отображения запросов клиента на методы контроллера.

Основная польза от использования **@RequestMapping:

1. Определение URL-адресов: Аннотация **@RequestMapping** позволяет определить **URL-**адрес или путь, по которому клиент может обратиться к методу контроллера. Например:

@RequestMapping("/users")

public String getUsers() {

}

1. Поддержка различных типов HTTP-запросов: @RequestMapping** позволяет указывать не только путь, но и типы **HTTP-**запросов, с помощью которых клиент может обратиться к методу. Например:

@RequestMapping(value = "/users", method = RequestMethod.GET)

public String getUsers() {

}

1. Шаблоны путей: @RequestMapping** поддерживает использование шаблонов путей, чтобы сделать **URL-**адрес более гибким. Например:

@RequestMapping("/users/{id}")

public String getUserById(@PathVariable("id") int id) {

}

1. Параметры запроса: @RequestMapping** позволяет указывать параметры запроса, которые должны присутствовать или отсутствовать, чтобы метод был вызван. Например:

@RequestMapping(value = "/users", params = "page=1")

public String getUsers() {

}

1. **Поддержка медиа-типов**: `@RequestMapping` позволяет указывать медиа-типы, которые метод контроллера может обрабатывать или производить. Например:

@RequestMapping(value = "/users", consumes = MediaType.APPLICATION_JSON_VALUE)

public String addUser(@RequestBody User user) {

}

1. Маршрутизация на основе условий: @RequestMapping** позволяет выполнять маршрутизацию на основе различных условий, таких как заголовки, заголовки **Cookie, а также другие атрибуты запроса или сеанса.
2. Поддержка версионирования API: @RequestMapping** также может использоваться для версионирования **API, чтобы управлять различными версиями методов контроллеров.@RequestMapping** является мощным инструментом для настройки маршрута и методов контроллера в **Spring MVC, и его использование обеспечивает гибкость и контроль над точками входа в приложении.



## Q39. В чем разница между @Controller и @RestController?


Разница между аннотациями **@Controller** и **@RestController** заключается в том, как они обрабатывают **HTTP-**запросы и формируют **HTTP-**ответы.

1.@Controller: Аннотация **@Controller** используется в **Spring MVC** для обозначения класса контроллера, который обрабатывает **HTTP-**запросы. Классы, помеченные этой аннотацией, выполняют обработку запросов и возвращают модели представления или строковые представления **HTML-**шаблонов. Обычно в этом случае используются представления **JSP** или **Thymeleaf** для формирования **HTML-**страниц.Пример:

@Controller

public class UserController {

@RequestMapping("/users")

public String getUsers(Model model) {

List&lt;User&gt; users = userService.getUsers();

model.addAttribute("users", users);

return "usersPage";

}

}

1.@RestController: Аннотация **@RestController** представляет новый функционал, добавленный в **Spring 4.0, и объединяет в себе аннотации **@Controller** и **@ResponseBody. Классы, помеченные этой аннотацией, работают как контроллеры, но возвращают данные напрямую в формате **JSON** или **XML, а не модели представлений или **HTML-**страницы.Пример:

@RestController

public class UserController {

@RequestMapping("/users")

public List&lt;User&gt; getUsers() {

return userService.getUsers();

}

}

Результатом работы метода, помеченного как **@RestController, будет сериализованный ответ в формате **JSON** или **XML, в зависимости от конфигурации. Это удобно для создания **RESTful-**сервисов, которые возвращают данные вместо представлений.

Таким образом, основное отличие между **@Controller** и **@RestController** заключается в том, что первый используется для обработки запросов и генерации представлений **HTML, в то время как второй используется для создания **RESTful-**сервисов и возврата данных в формате **JSON** или **XML.



## Q40. Что делает аннотация @PathVariable?


Аннотация **@PathVariable** используется в **Spring MVC** для привязки переменных пути **(части URL)** к параметрам метода контроллера.

Когда вы задаете переменные в **URL**-адресе, такие как `/users/{id}`, где `{id}` — это переменная пути, вы можете использовать **@PathVariable** для получения значения этой переменной и использовать ее в методе контроллера. Пример:

```java
@Controller
@RequestMapping("/users")
public class UserController {
    @RequestMapping("/{id}")
    public String getUserById(@PathVariable("id") int id, Model model) {
        User user = userService.getUserById(id);
        model.addAttribute("user", user);
        return "userPage";
    }
}
```

В этом примере, когда клиент делает запрос на **URL**-адрес типа `/users/123`, значение `123` будет автоматически привязано к параметру `id` метода `getUserById`. Затем вы можете использовать это значение для выполнения требуемой логики, например, для поиска пользователя с заданным идентификатором.

Аннотация **@PathVariable** также поддерживает внедрение переменных пути в качестве параметров метода без явного указания имени переменной пути:

```java
@RequestMapping("/{id}")
public String getUserById(@PathVariable int id, Model model) {
    // ...
}
```

Таким образом, **@PathVariable** позволяет получать значения переменных пути из **URL**-адреса и использовать их в методе контроллера для выполнения требуемых действий на основе этих значений.
