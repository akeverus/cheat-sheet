## Q1. (ВАЖНО) - Что такое Docker Containers?


Проще говоря, Docker Containers** состоят из приложений и всех их зависимостей.

Они совместно используют ресурсы ядра и системы с другими контейнерами и работают как изолированные системы в основной операционной системе.

Основная цель **Docker Containers** избавиться от зависимости от инфраструктуры при развертывании и запуске приложений. Это означает, что любое контейнерное приложение может работать на любой платформе независимо от используемой инфраструктуры.

Технически это просто экземпляры **Docker Images** во время выполнения.



## Q2. (ВАЖНО) - Что такое Docker Images?


Это исполняемые пакеты **(в комплекте с кодом приложения и зависимостями, программными пакетами и т. д.)** для создания **Containers.Docker Images** можно развернуть в любой среде **Docker, а **Containers** можно развернуть там для запуска приложения.



## Q3. (ВАЖНО) - Что такое DockerFile?


Это текстовый файл, содержащий все команды, которые необходимо выполнить для создания данного изображения.



## Q4. (ВАЖНО) - Что такое Docker Hypervisor?

**Docker Hypervisor** — это программное обеспечение, обеспечивающее виртуализацию, из-за которого его иногда называют монитором виртуальной машины. Это разделяет ресурсы хост-системы и выделяет их каждой установленной гостевой среде.

Это означает, что на одну хост-систему можно установить несколько ОС. **Docker Hypervisors** бывают двух типов: 

1. **Native Hypervisor**: этот тип также называется гипервизором без операционной системы и работает непосредственно на базовой хост-системе, что также обеспечивает прямой доступ к аппаратному обеспечению хоста, поэтому для него не требуется базовая ОС.

2. **Hosted Hypervisor**: этот тип использует базовую операционную систему хоста, на которой установлена ​​существующая ОС.



## Q5. (ВАЖНО) - Что вы можете сказать о Docker Compose?


Это файл **YAML, содержащий все сведения о различных службах, сетях и томах, которые необходимы для настройки приложения на основе **Docker. Итак, docker-compose** используется для создания нескольких **Containers, их размещения и установления связи между ними. Для связи между контейнерами порты открываются каждым контейнером.



## Q6. (ВАЖНО) - Что такое Docker Namespace?

Docker Namespace** это, по сути, функция **Linux, которая обеспечивает взаимоисключающее разделение ресурсов ОС. Это формирует основную концепцию контейнеризации, поскольку пространства имен вводят слой изоляции между контейнерами. В **Docker**е пространства имен обеспечивают переносимость **Containers** и не влияют на базовый хост. Примеры типов пространств имен, которые в настоящее время поддерживаются **Docker PID, Mount, User, Network, IPC.

## Q9. Что такое Docker Images Registry?


Проще говоря, Docker Images Registry** это область, в которой хранятся **Docker Images. Вместо того, чтобы каждый раз преобразовывать приложения в **Containers, разработчик может напрямую использовать **Images, хранящиеся в **Registry.

Этот **Registry** может быть общедоступным или частным, а **Docker Hub** является самым популярным и известным общедоступным **Registry.



## Q10. Сколько существует компонентов Docker?

Есть три компонента:

1. Docker Client: этот компонент выполняет операции **«**сборки**»** и **«**запуска**»** с целью установления связи с хостом **Docker.
2. Docker Host: этот компонент содержит основной демон **Docker** и хост**\-Containers, а также связанные с ними **Images. Демон устанавливает соединение с реестром **Docker.
3. Docker Registry: этот компонент хранит **Docker Images.Registry** может быть публичным или частным. Самые известные публичные реестры **Docker Hub** и **Docker Cloud.



## Q11. Что такое Docker Hub?


Это общедоступный облачный реестр, предоставляемый **Docker** для хранения общедоступных **Images Containers, а также для обеспечения их поиска и обмена ими.Images** можно отправить в **Docker Hub** с помощью команды:

docker push

## Q17. В чем разница между командами COPY и ADD, используемыми в Dockerfile?


Обе команды имеют схожую функциональность, но **COPY** предпочтительнее из-за более высокого уровня прозрачности, чем у **ADD.COPY** обеспечивает только базовую поддержку копирования локальных файлов в **Container, в то время как **ADD** предоставляет дополнительные функции, такие как поддержка удаленного **URL-**адреса и извлечения **tar.



## Q18. (ВАЖНО) - Может ли Container перезапускаться сам по себе?


Да, это возможно только при использовании определенных политик, определенных **Docker**ом, при использовании команды запуска **Docker. Ниже приведены доступные политики: 
<br/>**1. Off: в этом случае **Container** не будет перезапущен в случае его остановки или сбоя.2. On-failure: здесь **Container** перезапускается сам по себе только тогда, когда возникают сбои, не связанные с пользователем.3. Unless-stopped: использование этой политики гарантирует, что **Container** может быть перезапущен только тогда, когда пользователь выполнит команду для его остановки.4. Always: независимо от сбоя или остановки **Container** всегда перезапускается в этом типе политики. 
<br/>Эти политики могут использоваться как:

 
docker run -dit restart \[restart-policy-value\] \[container_name\]



## Q19. (ВАЖНО) - В чём разница между Docker Image и Docker Layer?

Docker Image: это построено из серии **Docker Layer.Image** соответствует **Docker-**контейнеру и используется для быстрой работы за счет механизма кэширования каждого шага. 
<br/>**Docker Layer: каждый уровень соответствует инструкции файла **DockerFile Image. Проще говоря, слой это тоже **Image, но это **Image** выполняемых инструкций. 
<br/>Рассмотрим пример **Dockerfile** ниже.

 
FROM ubuntu:18.04

COPY. /myapp

RUN make /myapp

CMD python /myapp/app.py Importantly, each layer is only a set of differences from the layer before it.  
<br/>Результатом сборки этого файла **Docker** является **Image. Принимая во внимание, что инструкции, присутствующие в этом файле, добавляют **Docker Layer** к **Docker Image.Docker Layer** можно рассматривать как промежуточные **Docker Image. В приведенном выше примере есть **4** инструкции, поэтому к результирующему **Docker Image** добавляются **4 Docker Layer.



## Q20. Каково назначение в команде запуска Docker параметра -v?


Синтаксис запуска **Docker** при использовании **volumes:

docker run -v host_path:docker_path &lt;container_name&gt;

Параметр **volume** используется для синхронизации каталога контейнера с любым из каталогов хоста. Рассмотрим приведенную ниже команду в качестве примера: 

docker run -v /data/app:usr/src/app myapp

 
Приведенная выше команда монтирует каталог **/data/app** на хосте в **usr/src/app** каталог. Мы можем синхронизировать **Container** с файлами данных с хоста без необходимости его перезапуска.

Это также обеспечивает безопасность данных в случае удаления контейнера. Это гарантирует, что даже если **Container** удален, данные контейнера существуют в расположении хоста, сопоставленного с **volume, что делает его самым простым способом хранения данных контейнера.



## Q21. Где в Docker хранятся Docker Volumes?

Docker Volumes** создаются и управляются **Docker, и к ним не могут получить доступ объекты, не относящиеся к **Docker. Они хранятся в файловой системе хоста **Docker** по адресу:

/var/lib/docker/volumes/

## Q23. Что делают команды up, run и start в Docker Compose?


1. Используя команду **up** для поддержания работоспособности `docker-compose` (в идеале всегда), мы можем запускать или перезапускать все сети, службы и драйверы, связанные с приложением, которые указаны в файле **docker-compose.yml. Теперь, если мы запускаем **docker-compose up** в **«**прикрепленном**»** режиме, нам будут доступны все логи из **Containers. Если **docker-compose** запускается в **«**отключенном**»** режиме, то после запуска **Containers** он просто завершает работу и не показывает журналы.
2. Используя команду **run, docker-compose** может запускать разовые или специальные задачи в зависимости от бизнес-требований. Здесь необходимо указать имя службы, и **Docker** запускает только эту конкретную службу, а также другие службы, от которых зависит целевая служба **(если есть). Эта команда полезна для тестирования **Containers, а также для выполнения таких задач, как добавление или удаление данных в томах **Containers** и т. д.
3. С помощью команды **start** можно перезапустить только те **Containers, которые уже были созданы, а затем остановлены. Это бесполезно для создания новых **Containers** само по себе.



## Q24. Каковы основные требования для работы Docker в любой системе?

Docker** может работать как на платформах **Windows, так и на **Linux.

Для платформы **Windows Docker** требуется как минимум **64-**разрядная версия **Windows 10** с **2** ГБ оперативной памяти. Для более низких версий **Docker** можно установить с помощью панели инструментов.Docker** можно загрузить с веб-сайта [**https://docs.docker.com/docker-for-windows/**](https://docs.docker.com/docker-for-windows/).

Для платформ **Linux Docker** может работать на различных версиях **Linux, таких как **Ubuntu >= 12.04, Fedora >= 19, RHEL >= 6.5, CentOS >= 6** и т. д.

## Q26. (ВАЖНО) - Перечислите наиболее часто используемые инструкции в Dockerfile?


1. FROM: используется для установки базового изображения для предстоящих инструкций. Файл **Docker** считается допустимым, если он начинается с инструкции **FROM.
2. LABEL: используется для организации **Image** на основе проектов, модулей или лицензирования. Это также помогает в автоматизации, поскольку мы указываем пару ключ-значение при определении метки, к которой позже можно обращаться и обрабатывать ее программно.
3. RUN: эта команда используется для выполнения следующих за ней инструкций в верхней части текущего изображения на новом слое. Обратите внимание, что при каждом выполнении команды **RUN** мы добавляем слои поверх изображения, а затем используем их в последующих шагах.
4. CMD: эта команда используется для предоставления значений по умолчанию для исполняемого контейнера. В случае нескольких команд **CMD** будет учитываться последняя инструкция.



## Q27. В чём разница между Daemon Logging и Container Logging?


В **Docker** ведение журнала поддерживается на **2** уровнях: ведение журнала на уровне демона или ведение журнала на уровне контейнера.Daemon Level: этот тип ведения журнала имеет четыре уровня: Debug, Info, Error** и **Fatal:

1. Debug** имеет все данные, которые произошли во время выполнения процесса демона.
2. Info** содержит всю информацию вместе с информацией об ошибках во время выполнения процесса демона.
3. Error** имеют те ошибки, которые произошли во время выполнения процесса демона.
4. Fatal** содержит фатальные ошибки, возникшие во время выполнения.Container Level:

1. Ведение журнала уровня контейнера можно выполнить с помощью команды: 

sudo docker run -it &lt;container_name&gt; /bin/bash

1. Чтобы проверить наличие **logs** уровня контейнера, мы можем запустить команду:

sudo docker logs &lt;container_id&gt;

## Q30. Можете ли вы отличить CMD от ENTRYPOINT?


1. Команда **CMD** предоставляет исполняемые значения по умолчанию для исполняемого контейнера. В случае, если исполняемый файл должен быть опущен, необходимо включить использование инструкции **ENTRYPOINT** вместе с форматом массива **JSON.
2. ENTRYPOINT** указывает, что инструкция внутри него всегда будет выполняться при запуске контейнера.  
 Эта команда предоставляет возможность настроить параметры и исполняемые файлы. Если в **DockerFile** нет этой команды, он все равно будет унаследован от базового **Image, упомянутого в инструкции **FROM. Наиболее часто используемой **ENTRYPOINT** является **/bin/sh** или **/bin/bash** для большинства базовых **Images.
3. В соответствии с передовой практикой каждый файл **DockerFile** должен иметь хотя бы одну из этих двух команд.

## Q32. Сколько Containers можно запустить в Docker и какие факторы влияют на это ограничение?


Нет четко определенного ограничения на количество **Containers, которые можно запускать в **Docker**е. Но все зависит от ограничений точнее аппаратных ограничений. Размер приложения и доступные ресурсы ЦП два важных фактора, влияющих на это ограничение. Если ваше приложение не очень большое и у вас достаточно ресурсов процессора, мы можем запустить огромное количество **Containers.



## Q33. (ВАЖНО) - Опишите жизненный цикл контейнера Docker?


Различные этапы **Docker Container** от начала его создания до конца называются жизненным циклом **Docker Container.Наиболее важными этапами являются:

1. Created: это состояние, когда **Container** только что создан, но еще не запущен.
2. Running: в этом состоянии **Container** будет работать со всеми связанными с ним процессами.
3. Paused: это состояние возникает, когда работающий **Container** был приостановлен.
4. Stopped: это состояние возникает, когда работающий **Container** был остановлен.
5. Deleted: в этом **Container** находится в мертвом состоянии.



## Q34. Как использовать Docker для Multiple Application Environments?


Здесь на помощь придет функция **docker-compose. В файле **docker-compose** мы можем определить несколько **services, networks** и **containers** вместе с сопоставлением **volumes** в чистом виде, а затем мы можем просто вызвать команду:

docker-compose up

Когда задействовано несколько сред мы хотели бы определить зависимости и процессы для конкретного сервера для запуска приложения. В этом случае мы можем продолжить создание файлов **docker-compose** для конкретной среды с именем **«docker-compose.{**environment**}.yml», а затем в зависимости от среды мы можем настроить и запустить приложение.



## Q35. Как гарантировать, что Container 1 запускается перед контейнером 2 при использовании Docker Compose?

Docker-compose** не ждет, пока какой-либо **Container** будет **«**готов**», прежде чем переходить к следующему контейнеру. Чтобы добиться порядка выполнения, мы можем использовать:«depends_on», как показано в образце файла **docker-compose.yml** ниже:

version: "2.4"

services:

backend:

build:.

depends_on:

db

db:

image: postgres

Внедрение сервисных зависимостей имеет различные причины и следствия:

1. Команда **docker-compose up** запускает службы в указанном порядке зависимости. В приведенном выше примере **Container db** запускается перед серверной частью.
2. docker-compose up SERVICE_NAME** по умолчанию включает зависимости, связанные со службой. В данном примере запуск **docker-compose up backend** создает и запускает БД **(зависимость от бэкенда).
3. Наконец, команда **docker-compose stop** также останавливает службы в порядке указанной зависимости. В данном примере серверная служба останавливается перед службой БД.
