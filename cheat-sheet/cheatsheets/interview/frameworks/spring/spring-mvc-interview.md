## Q1. (ВАЖНО) - Что такое Front Controller?

**Front Controller** — это архитектурный шаблон, который используется для обработки всех запросов в веб-приложении. Он выполняет централизованную обработку входящих запросов от клиента и координирует различные компоненты для выполнения запроса.

Основные компоненты шаблона **Front Controller:

1. Front Controller: Является единой точкой входа для всех запросов клиента. Он принимает запросы от клиента, инициирует необходимые действия и принимает решения о том, какой компонент обрабатывает запрос.
2. **Dispatcher**: Осуществляет маршрутизацию запросов на основе информации в запросе (например, URL или параметры запроса). Он определяет, какой компонент или контроллер будет вызван для обработки запроса.
3. **Controllers**: Контроллеры представляют собой компоненты, которые обрабатывают конкретные типы запросов или выполняют конкретные операции. Они получают запросы от диспетчера, осуществляют необходимые действия и генерируют ответы для клиента.
4. **Views**: Представления отвечают за генерацию и отображение данных или шаблонов в форме, понятной для клиента (например, HTML, XML, JSON и т. д.). Они получают данные от контроллера и создают выходной контент.

Преимущества использования шаблона **Front Controller:

1. Централизованная обработка запросов, что облегчает управление и одновременное изменение логики обработки.
2. Улучшение переиспользуемости и модульности, поскольку логика запроса разделена на различные контроллеры.
3. Улучшение безопасности: все запросы проходят через **Front Controller, что позволяет применять централизованное логирование, аутентификацию, авторизацию и другие меры безопасности.
4. Улучшение поддерживаемости и расширяемости приложения.

**Front Controller** используется во многих фреймворках, таких как **Spring MVC**, **JavaServer Faces (JSF)** и **Struts**. Он помогает создать более организованное и гибкое веб-приложение, разделяя обработку запроса на отдельные компоненты.



## Q2. (ВАЖНО) - Что такое Spring MVC?

**Spring MVC (Model-View-Controller)** — это архитектурный шаблон разработки веб-приложений, предоставляемый **Spring Framework**. Он предлагает разделение приложения на три основных компонента: модель (**Model**), представление (**View**) и контроллер (**Controller**).

1. **Модель (Model)**: Модель представляет данные и логику бизнес-процессов приложения. Она может быть представлена классами или объектами, которые могут содержать состояние и методы работы с данными. Как правило, модель представляет собой объекты, полученные из базы данных или от других источников данных.
2. **Представление (View)**: Представление отвечает за отображение данных пользователю. Это может быть **HTML**-шаблон, **JSP**-страница, **XML**-файл или любой другой формат отображения пользовательского интерфейса. Представление получает данные из модели для отображения пользователю и может использовать различные технологии для этой цели, например, **JSP**, **Thymeleaf** или **AngularJS**.
3. **Контроллер (Controller)**: Контроллер обрабатывает запросы от пользователя и выполняет логику обработки этих запросов. Он получает данные от пользователя, передает их в модель для обработки и выбора соответствующего представления для отображения. Контроллер также обрабатывает взаимодействие пользователя с приложением, такое как отправка форм, навигация по страницам и т. д.

**Spring MVC** предоставляет механизмы для маршрутизации запросов, связывания данных, валидации, управления состоянием приложения и других функций, необходимых для разработки эффективных веб-приложений. Он также интегрируется с другими компонентами **Spring Framework**, такими как **Dependency Injection (DI)** и **AOP (Aspect-Oriented Programming)**, что делает его мощным инструментом для разработки веб-приложений.

## Q4. Что такое локализация?


Локализация — это процесс адаптации веб-приложения к различным языкам и региональным настройкам пользователей. **Spring MVC** предоставляет механизмы для локализации сообщений, форматирования чисел, дат и других данных.

Вот несколько шагов, которые нужно выполнить для реализации локализации в приложениях **Spring MVC:

1. Конфигурация международных ресурсов **(Internationalization, i18n): Сначала необходимо настроить международные ресурсы, которые будут содержать все переводы и локализованные сообщения для различных языков. Для этого можно использовать файлы свойств **(.properties).
2. **Определение переводов и сообщений**: Создайте файлы свойств для каждого языка, который вы планируете поддерживать. Например, `messages_en.properties` для английского, `messages_fr.properties` для французского и т. д. В этих файлах свойств определите ключи и соответствующие значения сообщений на соответствующем языке.

Например, для английского языка:

welcome.message=Welcome to our Application!

error.message=An error occurred while processing your request.Для французского языка:

welcome.message=Bienvenue dans notre Application!

error.message=Une erreur est survenue lors du traitement de votre demande.

1. Использование **MessageSource: MessageSource** это интерфейс, который предоставляет способ получить сообщения на выбранном языке из международных ресурсов. В **Spring MVC** вы можете использовать **ReloadableResourceBundleMessageSource** или **ResourceBundleMessageSource** для реализации **MessageSource.
2. Маркировка сообщений для локализации: Вместо жесткого кодирования текста на определенном языке прямо в представлении или контроллере, маркируйте текстовые сообщения с использованием специальных ключей сообщений. Например, в представлении **Thymeleaf** это может выглядеть следующим образом:

&lt;h1 th:text="#{welcome.message}"&gt;&lt;/h1&gt;

&lt;p th:text="#{error.message}"&gt;&lt;/p&gt;

В результате система будет искать соответствующие локализованные значения в международных ресурсах и подставлять их вместо ключей сообщений.

1. Конфигурация локали: Определите стратегию выбора локали, которую ваше приложение будет использовать для локализации. В **Spring MVC** можно использовать **LocaleResolver, чтобы определить текущую локаль пользователя.Например, использование AcceptHeaderLocaleResolver:

@Configuration

public class WebConfig implements WebMvcConfigurer {

@Bean

public LocaleResolver localeResolver() {

AcceptHeaderLocaleResolver resolver = new AcceptHeaderLocaleResolver();

resolver.setDefaultLocale(Locale.ENGLISH);

return resolver;

}

}

1. Тестирование локализации: Для проверки локализации в приложении установите нужную локаль в запросе и убедитесь, что сообщения выводятся на соответствующем языке.

Таким образом, путем настройки международных ресурсов, использования **MessageSource** и разметки текстовых сообщений в представлениях ваше приложение на **Spring MVC** будет готово для локализации на различные языки и регионы.



## Q5. (ВАЖНО) - Что такое Intercepter?

**Interceptor (перехватчик)** позволяет добавить общую функциональность (логирование, проверку аутентификации, обработку исключений и т. д.) к запросам и ответам в приложении **Spring MVC**. Он выполняет операции до и после обработки запроса контроллером.

Вот некоторые основные моменты работы с перехватчиками в **Spring MVC:

1. Создание класса перехватчика: Создайте класс, реализующий интерфейс **HandlerInterceptor** или расширяющий класс **HandlerInterceptorAdapter. Эти классы предоставляют методы, которые можно переопределить для определенных операций, например, preHandle, postHandle** и **afterCompletion.
2. Регистрация перехватчика: Чтобы перехватчик заработал в вашем приложении, вам необходимо зарегистрировать его. В **Spring MVC** это можно сделать с помощью метода **addInterceptor** у класса **WebMvcConfigurer.

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new MyInterceptor());
    }
}
```

1. Настройка пути URL: Если вы хотите, чтобы перехватчик применялся только к определенным **URL-**адресам, вы можете использовать метод **addPathPatterns** перед вызовом **addInterceptor.

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new MyInterceptor())
            .addPathPatterns("/secured/");
    }
}
```

1. Определение операций перехватчика: Переопределите методы **preHandle, postHandle** и **afterCompletion** для реализации операций, которые должны быть выполнены перед и после обработки запроса контроллером.

```java
public class MyInterceptor extends HandlerInterceptorAdapter {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        // Здесь можно выполнить операции перед обработкой запроса контроллером
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler, ModelAndView modelAndView) throws Exception {
        // Здесь можно выполнить операции после обработки запроса контроллером, но перед возвратом представления
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) throws Exception {
        // Здесь можно выполнить операции после завершения обработки запроса, включая обработку исключений
    }
}
```

1. Указание порядка выполнения перехватчиков: Если в вашем приложении есть несколько перехватчиков, вы можете указать их порядок выполнения с помощью метода **order.

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new MyInterceptor()).order(1);
        registry.addInterceptor(new AnotherInterceptor()).order(2);
    }
}
```

1. Тестирование перехватчика: Запустите ваше приложение и убедитесь, что перехватчик работает корректно, выполняя операции, определенные в методах перехватчика.

Перехватчики в **Spring MVC** предоставляют эффективный способ добавления общей функциональности к вашим контроллерам. Они позволяют отделить определенные задачи от основной бизнес-логики контроллера и обеспечивают централизованную обработку повторяющихся операций.



## Q6. Что такое @ModelAttribute?


Аннотация `@ModelAttribute` — одна из самых важных аннотаций в **Spring MVC**. Она связывает параметр метода или возвращаемое значение метода с именованным атрибутом модели, а затем предоставляет его веб-представлению.

Если мы используем его на уровне метода, это указывает на то, что целью этого метода является добавление одного или нескольких атрибутов модели.

С другой стороны, при использовании в качестве аргумента метода это указывает на то, что аргумент должен быть получен из модели. Если он отсутствует, мы должны сначала создать его экземпляр, а затем добавить его в модель. После присутствия в модели мы должны заполнить поля аргументов из всех параметров запроса, имеющих совпадающие имена.



## Q7. В чём разница между Model, ModelMap и ModelAndView?

Model, ModelMap** и **ModelAndView** представляют различные способы передачи данных и моделей представления в **Spring MVC.

1. **Model**:
   - **Model** представляет собой простой интерфейс, который используется для передачи данных между контроллером и представлением.
   - Он предоставляет методы для добавления атрибутов, которые будут доступны в представлении.
   - Контроллер может принять **Model** в качестве параметра метода или вернуть его в качестве результата.
   - Пример: `model.addAttribute("attributeName", attributeValue);`

2. **ModelMap**:
   - **ModelMap** — это реализация интерфейса **Model**, которая также предоставляет дополнительные методы для работы с моделью.
   - Он расширяет функциональность **Model**, позволяя методы, которые позволяют добавлять, удалять и извлекать атрибуты из модели.
   - **ModelMap** также может использоваться для передачи аргументов в представление.
   - Он обеспечивает дополнительные возможности для работы с моделью, но его использование не является обязательным.

3. **ModelAndView**:
   - **ModelAndView** — это класс, который объединяет модель и имя представления в один объект.
   - Он позволяет возвращать модель и имя представления из контроллера вместе, упрощая возврат данных и выбор представления.
   - Контроллер может настроить **ModelAndView** и вернуть его в качестве результата.
   - Пример: `return new ModelAndView("viewName", "modelName", modelObject);`

В целом, **Model**, **ModelMap** и **ModelAndView** предоставляют разные подходы к передаче модели и данных между контроллером и представлением. Использование конкретной стратегии зависит от предпочтений разработчика и требований проекта. **Model** и **ModelMap** более просты и основные, в то время как **ModelAndView** предоставляет больше возможностей для управления моделью и представлением.



## Q8. В чем разница между model.put() и model.addAttribute()?


В рамках **Spring MVC** разница между **model.put()** и **model.addAttribute()** связана с тем, как они добавляют атрибуты в модель.

1. **model.put(String key, Object value)**:
   - Метод `put()` является частью интерфейса **Map**, который расширяется интерфейсами **Model** и **ModelMap** в **Spring MVC**.
   - Он используется для добавления атрибутов в модель путем указания ключа и значения.
   - Пример: `model.put("attributeName", attributeValue);`
   - `put()` позволяет добавлять атрибуты в модель с помощью простого синтаксиса **Map**, и никаких дополнительных методов не требуется.

2. **model.addAttribute(String attributeName, Object attributeValue)**:
   - Метод `addAttribute()` является частью интерфейса **Model**, который также используется в **Spring MVC**.
   - Он предоставляет более специализированный и удобный способ для добавления атрибутов в модель.
   - Пример: `model.addAttribute("attributeName", attributeValue);`
   - `addAttribute()` автоматически использует имя переменной атрибута как ключ, а значение переменной как значение.
   - Метод `addAttribute()` также возвращает объект самой модели, что позволяет выполнять цепочку вызовов методов (method chaining).

Оба метода, `put()` и `addAttribute()`, выполняют аналогичную функцию — добавление атрибутов в модель. Однако использование `addAttribute()` предпочтительнее благодаря более высокому уровню абстракции и удобству. Он позволяет указывать атрибуты с помощью их имен и значений, а также предоставляет возможность для более легкого цепочного добавления атрибутов.



## Q9. Что такое связывание форм?


Связывание форм **(форм-биндинг)** это процесс автоматического привязывания данных, полученных из формы пользователем, к объекту модели данных. Это позволяет упростить обработку и валидацию данных, полученных от пользователя.

Веб-фреймворки и библиотеки, такие как **Spring MVC** (с использованием аннотаций `@ModelAttribute`), **JavaServer Faces (JSF)** и **Thymeleaf**, предоставляют механизмы связывания форм для обработки данных.

Основные преимущества связывания форм:

1. Упрощение кода: Связывание форм позволяет уменьшить код, который необходим для получения данных из запроса и привязки их к объекту модели данных.
2. Улучшение безопасности: При использовании связывания форм можно проверять и валидировать данные на стороне сервера, что позволяет предотвращать атаки типа **XSS (межсайтовый скриптинг)** и другие уязвимости.
3. Удобство использования: Связывание форм упрощает работу с данными, полученными от пользователя, так как они могут быть напрямую привязаны к объекту модели данных и использованы в логике приложения без необходимости явного извлечения и преобразования.
4. Улучшение тестируемости: Использование связывания форм упрощает тестирование, так как можно легко создавать фейковые или тестовые данные и привязывать их к объекту модели данных для проверки логики приложения.

Пример использования связывания форм в **Spring MVC** с помощью аннотации **@ModelAttribute:

```java
@Controller
public class UserController {
    @PostMapping("/register")
    public String registerUser(@ModelAttribute("user") User user) {
        // Обработка данных пользователя
        //...
        return "success";
    }

    // Другие методы контроллера
    //...
}
```

В приведенном примере данные, отправленные из формы, автоматически связываются с объектом модели **User, что позволяет легко получить доступ к данным пользователя и обработать их в соответствии с логикой приложения.

## Q14. (ВАЖНО) - В чём разница между @Controller и @RestController?


Аннотации `@Controller` и `@RestController` являются частями **Spring Framework** и используются для организации обработки **HTTP**-запросов в веб-приложениях. Они имеют некоторые различия в контексте и предназначении.

1. **@Controller**:
   - `@Controller` используется для пометки класса как контроллера в паттерне проектирования **MVC (Model-View-Controller)**.
   - Она работает с моделью, представлением и обрабатывает **HTTP**-запросы.
   - `@Controller` обычно возвращает представления (**View**) в ответ на запросы и используется для создания динамических веб-страниц.
   - Это может быть полезно, если вы хотите использовать шаблонизаторы представлений, такие как **Thymeleaf** или **JSP**, для создания **HTML**-страниц.

2. **@RestController**:
   - `@RestController` является специализацией `@Controller` и используется для создания **RESTful Web Services** в **Spring**.
   - Она комбинирует функциональность `@Controller` и `@ResponseBody`, что означает, что каждый метод в классе будет возвращать данные, а не представление.
   - `@RestController` преобразует возвращаемые данные в **JSON** или **XML** и отправляет их клиенту в ответ на запросы.
   - Это удобно, если вы хотите создать **HTTP API** для обмена данными между клиентскими приложениями и сервером.

Таким образом, `@Controller` используется для создания веб-страниц с использованием шаблонизаторов представлений, а `@RestController` — для создания **RESTful Web Services** и предоставления данных в формате **JSON** или **XML**. Выбор между ними зависит от ваших потребностей в вашем веб-приложении.

## Q20. (ВАЖНО) - Что такое DispatcherServlet и ContextLoaderListener?

**DispatcherServlet** и **ContextLoaderListener** являются важными компонентами в **Spring MVC**:

1. **DispatcherServlet**:
   - **DispatcherServlet** является главным контроллером в **Spring MVC** приложении. Он обрабатывает все **HTTP**-запросы и управляет обработкой и передачей запросов соответствующим контроллерам.
   - **DispatcherServlet** также управляет жизненным циклом контроллеров, регистрирует их, передает им запросы и обрабатывает возвращаемые ими модели и представления.

2. **ContextLoaderListener**:
   - **ContextLoaderListener** обрабатывает создание и загрузку корневого контекста **Spring**. Корневой контекст создает и управляет инфраструктурой приложения, такой как сервисы, бины доступа к данным и т. д.
   - **ContextLoaderListener** загружает корневой контекст при запуске приложения и устанавливает его в области видимости для всех сервлетов, включая **DispatcherServlet**.

Если рассмотреть последовательность действий, то **ContextLoaderListener** загружает корневой контекст до инициализации **DispatcherServlet**. **DispatcherServlet** использует корневой контекст для получения бинов и настройки в соответствии с правилами обработки запросов.

Совместное использование этих двух компонентов позволяет более гибко настраивать и управлять **Spring MVC** приложением, разграничивать обязанности контроллера и инфраструктуры, а также обеспечивать легкую масштабируемость приложения.

## Q23. (ВАЖНО) - Как происходит обработка исключений в веб-приложениях?


У нас есть три варианта обработки исключений в **Spring MVC:

1. Обрабокта в исключении**
2. Обработка в контроллере**
3. Глобально**

Если во время обработки веб-запроса возникнет необработанное исключение, сервер вернет ответ **HTTP 500**. Чтобы предотвратить это, мы должны аннотировать любое из наших пользовательских исключений аннотацией `@ResponseStatus`. Этот тип исключений разрешается **HandlerExceptionResolver**.

Это приведет к тому, что сервер вернет соответствующий **HTTP**-ответ с указанным кодом состояния, когда метод контроллера выдаст наше исключение. Мы должны помнить, что мы не должны обрабатывать наше исключение где-то еще, чтобы этот подход работал.

Другой способ обработки исключений использование аннотации **@ExceptionHandler. Мы добавляем методы **@ExceptionHandler** к любому контроллеру и используем их для обработки исключений, создаваемых внутри этого контроллера. Эти методы могут обрабатывать исключения без аннотации **@ResponseStatus, перенаправлять пользователя в специальное представление ошибок или создавать полностью настраиваемый ответ на ошибку.

Мы также можем передать объекты, связанные с сервлетом **(HttpServletRequest, HttpServletResponse, HttpSession и Principal)** в качестве параметров методов обработчика. Но мы должны помнить, что мы не можем напрямую указать объект **Model** в качестве параметра.

Третий вариант обработки ошибок классы **@ControllerAdvice. Это позволит нам применять те же методы, только на этот раз на уровне приложения, а не только к конкретному контроллеру. Чтобы включить это, нам нужно использовать **@ControllerAdvice** и **@ExceptionHandler** вместе. Таким образом, обработчики исключений будут обрабатывать исключения, генерируемые любым контроллером.



## Q24. (ВАЖНО) - Что такое @ExceptionHandler?


Аннотация **@ExceptionHandler** позволяет нам определить метод, который будет обрабатывать исключения. Мы можем использовать аннотацию независимо, но гораздо лучше использовать ее вместе с **@ControllerAdvice. Таким образом, мы можем настроить глобальный механизм обработки ошибок. Таким образом, нам не нужно писать код для обработки исключений в каждом контроллере.

Давайте посмотрим на пример из нашей статьи об обработке ошибок для **REST** с помощью **Spring:

@ControllerAdvice

public class RestResponseEntityExceptionHandler extends ResponseEntityExceptionHandler {

@ExceptionHandler (value = {IllegalArgumentException.class, IllegalStateException.class})

protected ResponseEntity&lt;Object&gt; handleConflict (RuntimeException ex, WebRequest request) {

String bodyOfResponse = "This should be application specific";

return handleExceptionInternal (ex, bodyOfResponse, new HttpHeaders(), HttpStatus.CONFLICT, request);

}

}

Мы также должны отметить, что это предоставит методы **@ExceptionHandler** всем контроллерам, которые выдают **IllegalArgumentException** или **IllegalStateException. Исключения, объявленные с помощью **@ExceptionHandler, должны соответствовать исключению, используемому в качестве аргумента метода. В противном случае механизм разрешения исключений выйдет из строя во время выполнения.

Здесь следует иметь в виду, что для одного и того же исключения можно определить более одного **@ExceptionHandler. Однако мы не можем сделать это в том же классе, поскольку **Spring** будет жаловаться, вызывая исключение и завершаясь ошибкой при запуске.

С другой стороны, если мы определим их в двух отдельных классах, приложение запустится, но будет использовать первый найденный обработчик, возможно, неправильный.



## Q25. (ВАЖНО) - Что такое @ControllerAdvice?


Аннотация **@ControllerAdvice** позволяет нам писать глобальный код, применимый к широкому спектру контроллеров. Мы можем привязать диапазон контроллеров к выбранному пакету или конкретной аннотации.

По умолчанию **@ControllerAdvice** применяется к классам, аннотированным с помощью **@Controller (или @RestController). У нас также есть несколько свойств, которые мы используем, если хотим быть более конкретными.

Если мы хотим ограничить применимые классы пакетом, мы должны добавить имя пакета в аннотацию:

@ControllerAdvice("my.package")

@ControllerAdvice(value = "my.package")

@ControllerAdvice(basePackages = "my.package")

Также можно использовать несколько пакетов, но на этот раз нам нужно использовать массив вместо **String.

Помимо ограничения пакета по его имени, мы можем сделать это, используя один из классов или интерфейсов из этого пакета:

@ControllerAdvice(basePackageClasses = MyClass.class)

Элемент **assignableTypes** применяет **@ControllerAdvice** к определенным классам, а элемент **Annotations** к конкретным аннотациям.

Следует помнить, что мы должны использовать его вместе с **@ExceptionHandler. Эта комбинация позволит нам настроить глобальный и более конкретный механизм обработки ошибок без необходимости реализовывать его каждый раз для каждого класса контроллера.

```java
/**
 * Глобальный обработчик исключений для REST API
 * Демонстрирует использование @ControllerAdvice и @ExceptionHandler
 */
@ControllerAdvice
@RestController
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {
 
 private static final Logger logger = LoggerFactory.getLogger(GlobalExceptionHandler.class);
 
 /**
 * Обработка ошибок валидации
 */
 @ExceptionHandler(MethodArgumentNotValidException.class)
 public ResponseEntity<ErrorResponse> handleValidationExceptions(
 MethodArgumentNotValidException ex) {
 
 Map<String, String> errors = new HashMap<>();
 ex.getBindingResult().getAllErrors().forEach(error -> {
 String fieldName = ((FieldError) error).getField();
 String errorMessage = error.getDefaultMessage();
 errors.put(fieldName, errorMessage);
 });
 
 ErrorResponse errorResponse = ErrorResponse.builder().status(HttpStatus.BAD_REQUEST.value()).message("Ошибка валидации").errors(errors).timestamp(LocalDateTime.now()).build();
 
 return ResponseEntity.badRequest().body(errorResponse);
 }
 
 /**
 * Обработка пользовательских исключений
 */
 @ExceptionHandler(UserNotFoundException.class)
 public ResponseEntity<ErrorResponse> handleUserNotFound(
 UserNotFoundException ex) {
 
 ErrorResponse errorResponse = ErrorResponse.builder().status(HttpStatus.NOT_FOUND.value()).message(ex.getMessage()).timestamp(LocalDateTime.now()).build();
 
 return ResponseEntity.status(HttpStatus.NOT_FOUND).body(errorResponse);
 }
 
 /**
 * Обработка всех остальных исключений
 */
 @ExceptionHandler(Exception.class)
 public ResponseEntity<ErrorResponse> handleGenericException(Exception ex) {
 logger.error("Необработанное исключение", ex);
 
 ErrorResponse errorResponse = ErrorResponse.builder().status(HttpStatus.INTERNAL_SERVER_ERROR.value()).message("Внутренняя ошибка сервера").timestamp(LocalDateTime.now()).build();
 
 return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(errorResponse);
 }
}
```

### Пример 3: Использование Interceptors для логирования и безопасности

```java
/**
 * Interceptor для логирования запросов
 */
@Component
public class LoggingInterceptor implements HandlerInterceptor {
 
 private static final Logger logger = LoggerFactory.getLogger(LoggingInterceptor.class);
 
 @Override
 public boolean preHandle(HttpServletRequest request, 
 HttpServletResponse response, 
 Object handler) throws Exception {
 
 long startTime = System.currentTimeMillis();
 request.setAttribute("startTime", startTime);
 
 logger.info("Входящий запрос: {} {}", 
 request.getMethod(), 
 request.getRequestURI());
 
 return true;
 }
 
 @Override
 public void postHandle(HttpServletRequest request, 
 HttpServletResponse response, 
 Object handler, 
 ModelAndView modelAndView) throws Exception {
 
 long startTime = (Long) request.getAttribute("startTime");
 long endTime = System.currentTimeMillis();
 long executeTime = endTime - startTime;
 
 logger.info("Запрос обработан за {} мс: {} {}", 
 executeTime,
 request.getMethod(), 
 request.getRequestURI());
 }
 
 @Override
 public void afterCompletion(HttpServletRequest request, 
 HttpServletResponse response, 
 Object handler, 
 Exception ex) throws Exception {
 
 if (ex!= null) {
 logger.error("Ошибка при обработке запроса: {} {}", 
 request.getMethod(), 
 request.getRequestURI(), 
 ex);
 }
 }
}

/**
 * Interceptor для проверки аутентификации
 */
@Component
public class AuthenticationInterceptor implements HandlerInterceptor {
 
 @Autowired
 private AuthenticationService authenticationService;
 
 @Override
 public boolean preHandle(HttpServletRequest request, 
 HttpServletResponse response, 
 Object handler) throws Exception {
 
 // Пропускаем статические ресурсы
 if (handler instanceof ResourceHttpRequestHandler) {
 return true;
 }
 
 // Проверка аутентификации
 String token = request.getHeader("Authorization");
 if (token == null ||!authenticationService.isValidToken(token)) {
 response.setStatus(HttpStatus.UNAUTHORIZED.value());
 response.getWriter().write("{\"error\": \"Unauthorized\"}");
 return false;
 }
 
 return true;
 }
}

/**
 * Конфигурация Interceptors
 */
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {
 
 @Autowired
 private LoggingInterceptor loggingInterceptor;
 
 @Autowired
 private AuthenticationInterceptor authenticationInterceptor;
 
 @Override
 public void addInterceptors(InterceptorRegistry registry) {
 // Логирование для всех запросов
 registry.addInterceptor(loggingInterceptor);
 
 // Аутентификация только для /api/**
 registry.addInterceptor(authenticationInterceptor).addPathPatterns("/api/**").excludePathPatterns("/api/public/**");
 }
}
```

```java
@RestController
@RequestMapping("/api/files")

 return ResponseEntity.ok(response);

 /**
 * Загрузка нескольких файлов
 */

 String fileName = fileStorageService.storeFile(file);
 return FileUploadResponse.builder().fileName(fileName).fileType(file.getContentType()).size(file.getSize()).uploadDate(LocalDateTime.now()).build();
 }).collect(Collectors.toList());
 
 return ResponseEntity.ok(responses);
 }
}
```

## Best Practices для Spring MVC

### 1. Использование @RestController для REST API

**✅ Правильно:
```java

@RequestMapping("/api/users")
public class UserRestController {
 
 @GetMapping("/{id}")
 public UserDTO getUser(@PathVariable Long id) {
 // Автоматически возвращается как JSON
 return userService.findById(id);
 }
}
```

**❌ Неправильно:
```java

 @GetMapping("/{id}")
 @ResponseBody // ❌ Избыточно, если использовать @RestController
 public UserDTO getUser(@PathVariable Long id) {
 return userService.findById(id);
 }
}
```
