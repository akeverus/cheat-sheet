# Промт для автоматического разбиения шпаргалок на темы

## Контекст
Есть крупные монолитные шпаргалки в Markdown:
- `Шпаргалка - DevOps.md` — общие основы программирования/безопасности/OS, Docker, Kubernetes и др.
- `Шпаргалка - Linux.md` — процессы, файловые системы, Bash, администрирование.
- `Шпаргалка - Patterns_Alghoritms.md` — паттерны проектирования и алгоритмы (массивы, деревья, графы, строки, математика, ML/AI).
- `Шпаргалка - Review.md` — вопросы для собеседований по Java/OOP/Collections/Streams и др.
- `Шпаргалка - Java_Kotlin_Spring.md` — Java core, Concurrency, Collections, IO/NIO, и т.п. (очень большой файл).
- `Шпаргалка - Database_SQL.md` — PostgreSQL (основы, нормализация, индексы, запросы).
- `Полезные ссылки.md` — сборник внешних ссылок.

Цель: разрезать эти файлы на мелкие тематические Markdown, разложить по папкам/подпапкам, привести форматирование к единому виду, исправить ошибки и при необходимости дополнить или добавить недостающие темы. Файлы очень большие, поэтому обработку нужно делать по частям (чанк за чанком) с контролем качества и логом прогресса.

## Куда складывать результат
Создай корневую папку `cheatsheets/` с подпапками по доменам. Имёна файлов и папок — в `kebab-case`, названия секций — в русском (как в исходниках). Пример целевой структуры:
- `cheatsheets/devops/` — `programming-basics.md`, `security.md`, `os.md`, `docker-basics.md`, `docker-containers.md`, `docker-spring-boot.md`, `kubernetes-basics.md`.
- `cheatsheets/linux/` — `process-basics.md`, `process-search.md`, `process-control.md`, `process-monitoring.md`, `filesystem-basics.md`, `filesystem-catalogs.md`, `filesystem-files.md`, `filesystem-links.md`, `bash-basics.md`, `bash-advanced.md`, `admin-basics.md`.
- `cheatsheets/patterns/` — `design-creational.md`, `design-structural.md`, `design-behavioral.md`.
- `cheatsheets/algorithms/` — `sorting.md`, `arrays.md`, `trees.md`, `graphs.md`, `strings.md`, `math.md`, `collections.md`, `exercises.md`, `nn-ai.md`, `other.md`.
- `cheatsheets/java/` — `java-basics.md`, `java-concurrency-basics.md`, `java-concurrency-advanced.md`, `java-collections.md`, `java-io-nio.md`, `java-strings.md`, `java-annotations-and-reflection.md`, `java-streams-and-fp.md`, `java-exceptions.md`, `java-misc.md`.
- `cheatsheets/interview/` — `oop-and-java-core.md`, `java8.md`, `java-types.md`, `java-collections.md`, `java-conditionals.md`, `java-exceptions.md`, `strings.md`, `concurrency.md` (раскинь вопросы из `Шпаргалка - Review.md` по смыслу; дубли с Java-файлами сверни и сошли ссылками).
- `cheatsheets/databases/` — `postgres-basics.md`, `postgres-design.md`, `postgres-structure.md`, `postgres-data-ops.md`, `postgres-queries.md`, `postgres-types.md`, `postgres-joins.md`, `postgres-indexes.md`.
- `cheatsheets/links.md` — консолидированные полезные ссылки.

Разрешается добавлять подпапки/файлы, если контент явно просит более мелкой гранулярности.
Обязательные дополнительные файлы для PostgreSQL (если темы встречаются в исходнике или нужны как базовые):
- `postgres-transactions.md` — ACID, MVCC, уровни изоляции, SAVEPOINT, советы по блокировкам.
- `postgres-admin.md` — роли/права, pg_dump/pg_restore, VACUUM/ANALYZE, autovacuum, базовые настройки, psql-команды.
- `postgres-partitioning.md` — range/list/hash партиционирование, индексы на партициях, attach/detach.

## Правила переноса и слияния
- Сохраняй язык (русский). Сохраняй технические примеры и команды.
- Дубликаты и пересечения (например, Java basics, Collections, Streams, Concurrency, String/IO) вынеси в одну цельную статью, в остальных местах оставь краткие ссылки/см. также.
- Сохраняй порядок внутри темы по смыслу (от базовых к продвинутым).
- Там, где в исходниках есть длинные оглавления/нумерация вида `1.1`/`1.2`, замени на обычные Markdown-заголовки `# / ## / ###`.
- Вырежи лишние HTML-артефакты, мусорные символы, невалидные разрывы строк, двойные запятые и т.п. Исправляй опечатки (особенно в английских терминах и именах файлов/команд).
- Если тема явно пробелами (например, Spring, Kotlin или разделы, которые упомянуты, но не раскрыты), добавь краткие каркасы с TODO-блоками.

## Требования к оформлению
- Заголовки: `#` для названия статьи, `##` для крупных блоков, `###` для подтем.
- Код/команды: fenced code blocks с языком (`bash`, `sql`, `java`, `kotlin`, `yaml` и т.д.).
- Списки: используйте маркеры `-` или упорядоченные списки, без лишних пробелов и случайных номеров.
- Таблицы: если уместно, делай компактные таблицы (например, сравнения `==` vs `equals`, `INNER JOIN` vs `LEFT JOIN`).
- Вставляй краткие пояснения/итоги в начале файла (2–3 предложения).
- Вставляй блок `См. также` для ссылок на родственные файлы/темы.
- Для команд Linux/SQL добавляй короткое описание, что делает команда.
- Для алгоритмов указывай сложность (O-нотация), если известна.
- Для вопросов собеседований — только вопросы/краткие подсказки, без лишней воды; группируй по темам.
- Убери зашумленные shebang/скрипты, если они не несут ценности; если важны, оформи как код с минимальным комментарием.

## Стратегия построчной/поштучной обработки больших файлов
- Работай итеративно небольшими окнами (например, 500–1500 строк), чтобы не терять контекст и не упираться в лимиты.
- Для каждого окна: сначала извлеки/распознай структуру (подзаголовки), потом вынеси блок в целевой файл/папку, сразу нормализуя формат.
- Веди журнал прогресса: фиксируй, какие диапазоны строк обработаны и в какие целевые файлы отправлены.
- После обработки окна обновляй локальное оглавление целевого файла, чтобы позже не потерять ссылки.
- Если попались куски с явными повторами или пересечениями с уже перенесённым материалом — не копируй, а вставь в целевом месте краткий «См. также …» с относительной ссылкой.
- Если встречаются незакрытые списки/код-блоки, закрывай их корректно, не теряя содержимого.
- При нехватке контекста для термина или кода — ставь `TODO` с коротким описанием пробела.
- Каждую новую статью открывай коротким резюме (2–3 предложения), а в конце добавляй блок «См. также» со ссылками на родственные статьи.

## Контроль качества на каждом шаге
- Проверяй, что в результирующем файле: один `#`-заголовок, далее иерархия `##/###`; нет дублей заголовков на одном уровне.
- Код-блоки имеют язык и закрыты; списки не ломаются переносами; нет двойных запятых и мусорных символов.
- Ссылки относительные и валидные, путь соответствует предложенной структуре.
- При завершении обработки исходного большого файла оставь в нём предупреждение и ссылки на новые файлы (или очисти по согласованию).

## Что дополнить
- Добавь недостающие базовые определения в местах, где сразу идут команды/примеры без вступления.
- В DevOps/Docker/K8s — дай минимальные примеры `Dockerfile`, `docker-compose.yml`, базовые манифесты `Deployment/Service`, и ссылки на лучшие практики (ресурсы, probes, rollout).
- В Linux — добавить советы по безопасной работе с `sudo`, логированию, проверке ресурсов.
- В Java — кратко про модули (Java 9+), GC-обзор, record/sealed классы (если ещё не описаны), базовые паттерны обработки ошибок.
- В PostgreSQL — примеры индексов с пояснением, когда использовать, и типовые EXPLAIN-анализы.

## Выход
- Набор новых Markdown-файлов в предложенной структуре.
- Чистое, единообразное форматирование.
- Без гигантских оглавлений; максимум компактное локальное содержание в начале файла.
- Все ссылки внутри репо относительные (например, `../java/java-concurrency-basics.md`).
- Удали или оставь пустыми исходные громоздкие файлы — по согласованию; если оставляешь, добавь в них предупреждение и ссылку на новую структуру.
- Минимальный объём для финальных MD-файлов: **не менее 300 строк** при полном раскрытии темы; включай все основные кейсы (locks/MVCC/transactions/admin/partitioning/monitoring/queries/indexes/types и др. для PostgreSQL).
- **Сохранение контента:** переносить весь материал из исходных файлов (docx/md), ничего не выбрасывать.

## Пошаговый план обработки каждого исходного файла
1) Определи исходный файл и его объём. Если >1500 строк — обрабатывай чанками по 500–1500 строк.
2) Сделай снимок текущего прогресса: диапазон строк, дата/время.
3) Сними оглавление чанка (по заголовкам `# / ## / ###`) и реши, в какие целевые файлы пойдёт контент.
4) Для каждого блока внутри чанка:
   - Нормализуй заголовок до `# / ## / ###`.
   - Перепиши списки в единый формат.
   - Код и команды заверни в fenced code blocks с языком.
   - Исправь опечатки, лишние пробелы, двойные запятые, мусорные символы.
   - Если блок дублирует уже перенесённое — замени на «См. также …» с относительной ссылкой.
   - Если блок неполный — добавь `TODO: …` с одним предложением, что нужно дополнить.
5) Перенеси блок в целевой файл, сохраняя порядок (от базовых к продвинутым).
6) Обнови локальное мини-оглавление целевого файла (если оно есть) или добавь краткий «См. также».
7) Задокументируй прогресс: какой диапазон строк исходника обработан, куда положен контент, какие TODO оставлены.
8) После завершения всего исходника — поставь в нём предупреждение и ссылки на новые файлы либо очисти по согласованию.

## Оформление код-блоков и команд
- Используй fenced code blocks: три бэктика + язык.
- Языки: `bash`, `sh`, `sql`, `java`, `kotlin`, `yaml`, `json`.
- Не вставляй shebang без необходимости; если оставляешь — помести в код-блок.
- Перед кодом короткое описание, что он делает.
- Пример:
```bash
docker run --rm -it nginx:latest
```
- Для SQL:
```sql
SELECT * FROM table LIMIT 10;
```

## Оформление списков и таблиц
- Маркеры списков: `-` или нумерация `1.` без лишних пробелов.
- Не допускай разрывов между пунктами без причины.
- Таблицы использовать только когда сравнение компактно (например, `==` vs `equals`).
- В таблицах избегай длинных текстов; максимум 1–2 предложения в ячейке.

## Правила для ссылок
- Внутренние — относительные пути (../...).
- Внешние — обычные URL, по возможности с меткой.
- Если раздел перенесён — оставь ссылку в исходнике на новый файл.

## Обработка дубликатов и пересечений
- Если два файла покрывают одну тему:
  - Выбери основной (где больше контента) и собери туда материал.
  - В остальных местах: `См. также: ../path/to/main.md`.
- Не копируй текст дословно в несколько файлов.
- Если блок повторяется с небольшими отличиями — сведите различия в один список или таблицу.

## Политика логирования прогресса
- Для каждого исходного файла веди краткий лог (можно в отдельном `progress.md` или в комментарии к задаче):
  - Файл: `Шпаргалка - DevOps.md`
  - Обработано: строки 1–1200 → `devops/programming-basics.md`, `devops/security.md`
  - TODO: дописать про GC (если найден пробел), проверить ссылки.
- По завершении файла зафиксируй: все диапазоны покрыты, остаточных блоков нет.

## Детальный пайплайн для чанка (500–1500 строк)
1) Считать диапазон строк исходного файла.
2) Выделить заголовки в чанке.
3) Разбить на логические блоки (по заголовкам или очевидным темам).
4) На каждый блок:
   - Решить целевой файл.
   - Нормализовать заголовок и текст.
   - Оформить код-блоки.
   - Исправить опечатки.
   - Добавить TODO при нехватке контекста.
   - Проверить, не является ли блок дубликатом.
5) Вставить блок в целевой файл в нужное место (сохраняя порядок).
6) Обновить мини-оглавление/`См. также`.
7) Задокументировать, что этот блок перенесён.
