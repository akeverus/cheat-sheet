## Решение

Прогнать сборку в этом worktree, распарсить машинные артефакты прогона
(`build/test-results/**/*.xml`, `jacocoTestReport.xml`) и написать
`.sdlc/CS-20260828-020/report.md`; затем привести к снятым числам два места в
репозитории, где живёт устаревший замер.

**Порядок работ.**

1. **Замер времени + вердикт гейта.** Один холодный прогон:
   `time ./gradlew check --no-daemon` из корня worktree (wall-clock засечь
   явно: `s=$(date +%s); … ; e=$(date +%s)`). Вывод целиком сохранить в
   `/tmp/CS-20260828-020-check.log` (в репозиторий не класть). Красный прогон —
   **валидный результат задачи**: его фиксируют, а не чинят.
2. **Покрытие `quiz-app`.** `./gradlew :quiz-app:jacocoTestReport --no-daemon`
   → `modules/quiz-app/build/reports/jacoco/test/jacocoTestReport.xml`. Числа
   брать из XML (`<counter>` на уровне report и на каждом `<package>`), не из HTML.
3. **Покрытие остальных двух модулей.** Штатной конфигурацией не измеряется.
   Мерить временным init-скриптом **вне репозитория** (`/tmp/…-jacoco-all.gradle`),
   чтобы не трогать build-файлы:

   ```groovy
   allprojects {
       plugins.withId('java') {
           apply plugin: 'jacoco'
           tasks.withType(JacocoReport).configureEach { reports { xml.required = true } }
       }
   }
   ```

   Прогон: `./gradlew -I /tmp/…-jacoco-all.gradle :quiz-domain:jacocoTestReport
   :quiz-persistence:jacocoTestReport --no-daemon`. Тесты перезапустятся под
   агентом — время этого прогона в замер §5 **не идёт**. Если способ не сработал,
   строки модулей помечаются `не измерено` с причиной и точной командой (см. AC-4);
   выдумывать числа запрещено.
4. **Отчёт** `.sdlc/CS-20260828-020/report.md` — структура зафиксирована в AC-2.
5. **Синхронизация репозитория с замером** — ровно два файла:
   - `modules/quiz-app/build.gradle.kts:117` и `:137-138` — комментарии
     переписываются под новую дату и новые числа. **Пороги, `element`,
     `includes`/`excludes` не трогаются** (AC-9): смена политики порогов —
     отдельное решение, follow-up.
   - `docs/quality-report.md` §2 (таблица тестов + строка `failures/errors/skipped`)
     и §3 (обе таблицы) — числа заменяются на измеренные, добавляется маркер
     `Измерено <дата>, SHA <sha>`. Исторический абзац про декоративный гейт
     «До 2026-08-04 …» (`docs/quality-report.md:127-134`) сохраняется дословно:
     это правдивая история, а не устаревшее число.

**Почему `docs/quality-report.md` в скоупе, хотя задача называет только
`build.gradle.kts`:** это тот же самый замер 2026-08-04, просто второй его дом
(`docs/quality-report.md:112-126`). Обновить одну копию и оставить вторую —
значит создать расхождение там, где сейчас его нет. Правка механическая:
подстановка чисел, уже посчитанных для отчёта.

**Отвергнутые альтернативы.**

- Поднять пороги гейта под свежий замер — нет: порог, выставленный вплотную к
  факту, начинает падать от шума; смена политики требует отдельного обоснования → follow-up.
- Завести `jacoco` в `quiz-domain`/`quiz-persistence` насовсем — нет: это правка
  build-файлов и новые гейты, шире задачи-замера → follow-up.
- Взять числа из HTML-отчёта JaCoCo глазами — нет: XML машиночитаем и даёт
  пакеты и счётчики без округления.
- Класть парсеры в `scripts/` — нет: разовые команды живут в приложении отчёта,
  новый файл в репозитории под разовый пересчёт не нужен (YAGNI).
- Чинить упавшие тесты/гейт, если прогон красный — нет: задача измерительная,
  диагноз → follow-up.

## Acceptance Criteria

Проверки исполняются из корня worktree; `R=.sdlc/CS-20260828-020/report.md`,
`X=modules/quiz-app/build/reports/jacoco/test/jacocoTestReport.xml`.

1. **AC-1. Отчёт существует и непуст** — `test -s $R` (DoD-гейт).
2. **AC-2. Структура.** Присутствуют все девять заголовков (проверка:
   `for h in "## 0. Условия прогона" "## 1. Итог прогона" "## 2. Тесты"
   "## 3. Покрытие по модулям" "## 4. Покрытие по пакетам" "## 5. Время прогона"
   "## 6. Дельта к замеру 2026-08-04" "## 7. Что обновлено в репозитории"
   "## Приложение A"; do grep -qF "$h" $R || echo MISS "$h"; done` — пусто).
3. **AC-3. Условия прогона самодостаточны.** §0 содержит: полный 40-символьный SHA
   прогона (`git cat-file -t $(grep -oE '[0-9a-f]{40}' $R | head -1)` → `commit`),
   версию JVM, версию Gradle, версию Docker-сервера, дословные командные строки
   всех прогонов и признак «холодный `build/`». Плюс явная оговорка, что JVM
   локального замера (22, arm64) не совпадает с CI (17, ubuntu) — иначе время
   несопоставимо.
4. **AC-4. Покрытие по модулям.** В §3 таблица ровно с тремя строками —
   `quiz-domain`, `quiz-persistence`, `quiz-app` (проверка:
   `grep -cE '^\| *`?quiz-(domain|persistence|app)' $R` = 3). Для каждой строки
   либо четыре счётчика (INSTRUCTION, LINE, BRANCH, CLASS — покрыто/всего/%) с
   указанием пути XML-источника, либо дословный маркер `не измерено` + причина +
   команда, на которой споткнулись.
5. **AC-5. Покрытие по пакетам.** В §4 строка на каждый `<package>` XML-отчёта
   `quiz-app`; число строк совпадает с
   `python3 -c "import re,sys;print(len(re.findall(r'<package name=',open('$X').read())))"`.
   У каждой строки: LINE покрыто/всего/%, BRANCH %, и колонка «в PACKAGE-гейте:
   да/нет» согласно `includes`/`excludes` из `build.gradle.kts:139-157`. Отдельной
   строкой назван минимум по гейтуемым пакетам (имя пакета + ratio + покрыто/всего)
   — это число идёт в комментарий `build.gradle.kts:137`.
6. **AC-6. Тесты, падения, пропуски.** §2 даёт на каждый модуль
   `tests/failures/errors/skipped`, сумма сходится с
   `python3 - <<'PY'`-пересчётом по `modules/*/build/test-results/test/*.xml`
   (команда — в Приложении A). Полный список падений и пропусков в виде
   `FQCN.method` + причина (текст `<failure>`/`message` у `<skipped>`); число
   перечисленных FQCN равно сумме соответствующих элементов XML. Пустой список
   оформляется явной строкой `падений нет` / `пропусков нет`, а не отсутствием
   раздела.
7. **AC-7. Время.** §5 содержит: wall-clock всего `check` (сек и мм:сс), сумму
   `time`-атрибутов `<testsuite>` по каждому модулю, топ-10 самых долгих
   тест-классов с временем, и сопоставление с `timeout-minutes: 25`
   (`.github/workflows/ci.yml:31`) с оговоркой о разном железе/JVM.
8. **AC-8. Дельта.** §6 — таблица «замер 2026-08-04 → замер сейчас → изменение →
   запас до порога» минимум по трём величинам: BUNDLE LINE (было 0.915, порог 0.85),
   BUNDLE BRANCH (было 0.764, порог 0.70), минимум по гейтуемым пакетам
   (было 0.600 у `feature.interview.service.facade` 9/15, порог 0.55). Каждое
   «было» — из комментариев `build.gradle.kts`, каждое «стало» — из §3/§4.
9. **AC-9. `build.gradle.kts` обновлён и только в комментариях.** База сравнения —
   `B=$(git merge-base master HEAD)` (сейчас `3b1d70dc`); `git diff $B` берёт и
   закоммиченное, и рабочее дерево, поэтому проверки не зависят от того, коммитил
   ли исполнитель. `grep -c "Замер 2026-08-04" modules/quiz-app/build.gradle.kts` = 0;
   `grep -c "Замер 2026-09" modules/quiz-app/build.gradle.kts` ≥ 2;
   `git diff $B -- modules/quiz-app/build.gradle.kts | grep -E '^[-+][^-+]' |
   grep -vE '^[-+] *//'` — пусто (изменены исключительно строки-комментарии).
   Каждое число из новых комментариев встречается в отчёте дословно (проверка:
   `for n in $(git diff $B -- modules/quiz-app/build.gradle.kts | grep '^+.*//' |
   grep -oE '[0-9]+/[0-9]+|0\.[0-9]+'); do grep -qF "$n" $R || echo MISS $n; done`
   — пусто).
10. **AC-10. `docs/quality-report.md` сведён с замером.** В блоке §2–§3
    (строки 44–139 на HEAD) нет ни одного старого числа:
    `sed -n '44,139p' docs/quality-report.md | grep -nE '3633|3970|17985|19667|1366|1788|246|1211'`
    → пусто (вне этого диапазона `1366` — ширина вьюпорта в `:688`, её не трогать).
    Абзац `:55-58` про «двадцать два ещё не закоммиченных гейта редизайна» либо
    пересчитан по факту, либо удалён как отработавший — устаревшего утверждения
    в файле не остаётся. Каждое число из таблиц §2–§3 встречается в отчёте
    (та же проверка, что в AC-9); историческая проза сохранена
    (`grep -c "До 2026-08-04 гейт был декоративным" docs/quality-report.md` = 1);
    добавлена строка вида `Измерено 2026-09-…, SHA …` с тем же SHA, что в §0 отчёта.
11. **AC-11. Приложение A воспроизводит.** На каждую таблицу отчёта (§2, §3, §4, §5) —
    минимум одна команда, читающая артефакты прогона и печатающая те же числа;
    команды исполнимы из корня worktree без повторной сборки. Реревьюер прогоняет
    их и сверяет.
12. **AC-12. Дельта задачи ровно из четырёх файлов.**
    `{ git diff --name-only $B; git status --porcelain -uall | cut -c4-; } | sort -u`

    `modules/quiz-app/build.gradle.kts`, `docs/quality-report.md`. Никаких `build/`,

## Риски

- **Прогон долгий и может упереться в таймаут харнеса.** 1500+ тестов на
  Testcontainers, холодный кэш Gradle + скачивание образа `postgres:16-alpine`.
  Смягчение: запускать `check` в фоне с длинным таймаутом и логом в `/tmp`,
  не дробить на модули (иначе wall-clock §5 потеряет смысл).
- **JDK 22 против CI JDK 17.** Сборка может упасть на несовместимости
  (Lombok 1.18.34 / Gradle 8.9 формально поддерживают 22, но это не CI-конфигурация).
  Если упало — второй попыткой `JAVA_HOME` на Corretto 17 (x86_64, Rosetta) и в §0
  явная пометка, что время под эмуляцией и как ориентир для CI не годится.
- **Testcontainers и Docker API.** Симптом — массовое падение интеграционных
  тестов на согласовании версии API; лечение `JAVA_TOOL_OPTIONS=-Dapi.version=1.41`
  (`docs/quality-report.md:38-42`). Факт применения обязателен в §0.
- **Init-скрипт для двух модулей может не сработать** (порядок применения плагина,
  отсутствие `jacocoTestReport`). Тогда — честное `не измерено` (AC-4), а не
  подстановка правдоподобных чисел.
- **Параллельные агенты.** В репозитории работают чужие loop'ы: перед правкой
  `docs/quality-report.md` перечитать файл (он менялся 2026-09-01), редактировать
  точечно и не откатывать чужое.
- **Соблазн «починить красное».** Любое падение — материал отчёта и follow-up,
  не работа этой задачи; иначе замер перестаёт быть замером текущего состояния.
