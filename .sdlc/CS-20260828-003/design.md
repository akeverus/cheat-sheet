# CS-20260828-003: Закрыть «белые пятна» §18 фронт-разведки живым наблюдением

## Контекст

Задача — follow-up к CS-20260827-001 (Phase 0 фронт-разведка, статическое
чтение кода). Её отчёт `.sdlc/CS-20260827-001/report.md:560-591` честно
перечисляет 6 вопросов, на которые статическое чтение принципиально не
отвечает. Дословно (сжато):

1. **Визуальное состояние обеих тем на реальных вьюпортах** — отчёт «не видел
   ни одного отрендеренного пикселя» (`report.md:565-568`).
2. **Живое состояние БД** — число вопросов, optionless-вопросов, распределение
   MCQ (`report.md:569-572`).
3. **Реальный порядок каскада в браузере** — манифест декларирует порядок, но
   вычисленный стиль в DOM не проверялся; названы спорные места
   `components-pending`, `components-filter-bar` (`report.md:573-577`).
4. **Дублирование палитры вне `tokens.css`** — §12 заявлено, но не выполнено
   (`report.md:578-582`).
5. **«Слой pixel ничего структурного не меняет»** — заявлено манифестом, не
   проверено вычислением `position`/`display` в DOM (`report.md:583-585`).
6. **`/review` как режим, а не раздел** — подсветка активного раздела и
   счётчик ошибок в рельсе прогресса не проверены живьём
   (`report.md:586-590`).

## Решение

Поднять изолированный стенд, снять с него измерения шестью блоками (по одному
на каждое белое пятно) и написать `report.md`, где у каждого пятна есть
вердикт, числа/пиксели и команда воспроизведения.

### 1. Стенд (изолированный, чужое состояние не трогаем)

```bash
docker compose up -d postgres                      # если контейнер не поднят
docker exec quiz-postgres psql -U interview -d postgres \
  -c "CREATE DATABASE interview_recon OWNER interview"
SERVER_PORT=8091 SPRING_PROFILES_ACTIVE=qa \
SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/interview_recon \
  ./gradlew :quiz-app:bootRun --no-daemon          # фоном, лог → .sdlc/<id>/data/boot.log
```

Отдельная БД обязательна: профиль `qa` труncate'ит таблицы прогресса
(`QaFixtureRunner.java:68`), и на общей `interview` это стёрло бы прогресс
пользователя. Flyway накатит схему, `StartupRunner` импортирует банк из
репозитория — то есть числа §18.2 будут числами HEAD, а не чьей-то истории.
До и после прогона снимается **read-only** страж по пользовательской БД
(`SELECT count(*) FROM review_state` в `interview`) — два одинаковых числа
доказывают, что чужое состояние не задето. По завершении
`DROP DATABASE interview_recon`.

### 2. Драйвер браузера

`ln -s ~/IdeaProjects/cheat-sheet/e2e/node_modules e2e/node_modules` (путь
gitignored → дельты нет; чужой чекаут используется только на чтение). Скрипты
разведки живут в `.sdlc/CS-20260828-003/recon/` и запускаются как обычный node
из каталога `e2e` (`E2E_BASE_URL=http://localhost:8091`). Файлы `e2e/*.spec.js`
не трогаем — это продуктовые тесты, а не инструмент разовой разведки.
Фолбэки при неудаче, в порядке: `npm ci` в `e2e/` → MCP `chrome-devtools`.
Использованный способ фиксируется в отчёте.

### 3. Блок A — визуальная матрица (§18.1) и мёртвое пространство (§17)

`recon/shots.js`: тема ставится как в `visual-matrix.spec.js:92-102`
(`localStorage.theme`), `screenPreset` НЕ выставляется — наблюдаем поведение по
умолчанию, которое видит человек с первого захода; фактический `data-pixel`
пишется в метаданные снимка. Волатильные блоки скрываются тем же приёмом
(`VOLATILE_PRESENCE`, `visual-matrix.spec.js:56-58`), `/` пиннится
`PINNED_HOME` (`visual-matrix.spec.js:33-36`), чтобы снимок был воспроизводим.

Обязательная матрица (42 файла, `shots/<screen>-<theme>-<W>x<H>.png`):

- экраны Tier A: `home` (`/`), `train`, `stats`, `topics`;
- вьюпорты: `1280x800`, `1440x900`, `1680x1050`, `1920x1080`, `2560x1440`
  (список миссии §18: MACOS/DESKTOP/RESOLUTION);
- темы: `dark`, `light` → 4 × 5 × 2 = 40;
- плюс Retina: `home-dark-1440x900-dpr2.png`, `stats-dark-1440x900-dpr2.png`.

Tier B (по одному вьюпорту 1440×900, обе темы): `bookmarks`, `settings`,
`review`, `summary` (`/session-summary`). Экран может быть недостижим по
конструкции (сводка одноразова и требует POST `/finish` с `_csrf`) — тогда
вместо снимка в отчёте строка `НЕДОСТИЖИМО: <screen>/<theme> — <HTTP/шаги>`.

`recon/space.js` считает для Tier A на 1920 и 2560 (обе темы): ширину вьюпорта,
`getBoundingClientRect()` у `#main-content` и у самой широкой карточки внутри,
долю полезной ширины, крупнейший горизонтальный жёлоб → `data/space-metrics.json`.
Это переводит §17 «беспощадный аудит пустоты» из впечатления в числа.

### 4. Блок B — живое состояние БД (§18.2)

`recon/db.sh` гоняет через `docker exec … psql` набор запросов по
`interview_recon` (полный текст каждого — в отчёте рядом с числом): всего
вопросов; вопросов без единого варианта (`NOT EXISTS` по `answer_options`);
распределение вопросов по числу вариантов (0/2/3/4/5+); распределение
правильного варианта по позициям; число тем и категорий. Сырой вывод →
`data/db-counts.txt`. Плюс `GET http://localhost:8091/api/stats` →
`data/api-stats.json`. Плюс те же три счётчика банка **read-only** по
пользовательской БД `interview` — чтобы сказать, совпадает ли живой банк
пользователя с HEAD. Все числа сверяются с 9818/42 из аудита
(`docs/frontend-refoundation-audit.md:19,24`), расхождение объясняется.
Счётчики прогресса на recon-БД равны фикстурам qa (due=2, learned=1) — отчёт
обязан это назвать, а не выдать за «живой прогресс».

### 5. Блок C — реальный каскад (§18.3) и pixel-слой (§18.5)

`recon/cascade.js`, основной способ — CDP: `CSS.enable` +
`CSS.getMatchedStylesForNode` даёт упорядоченный список матчнутых правил с
слоем и позицией в ленте. Фолбэк (если CDP-ответ окажется без разметки слоёв):
скачать текст ленты по `href` единственного `<link>` (`head.html:333`), разобрать
её на `@layer`-блоки с балансировкой скобок и сматчить селекторы через
`document.querySelectorAll` — это тоже вычисление на живом DOM, а не чтение
исходников. Способ фиксируется в отчёте.

Проверяем:

- порядок слоёв в отданной ленте равен `tokens, reset, shell, components,
  pages, utilities, pixel` (`tokens.css:4`);
- на `/` живому узлу кнопки выставляется `data-pending="action"`, затем
  снимается упорядоченный список матчнутых правил и победитель по каждому
  спорному свойству — подтверждается ли обоснование манифеста, что
  `components-pending.css` обязана идти после `components-controls.css`
  (`css-bundle-manifest.txt:39` vs `:25`, `components-pending.css:10,39`);
- гейт ленты работает: правила `.filter-bar` есть на `/stats` и отсутствуют на
  `/` (`css-bundle-manifest.txt:94`);
- демонстрируется реальная пара правил равной специфичности, где `pixel` бьёт
  `components` — то есть порядок слоёв в браузере именно объявленный.

`recon/pixel-layer.js` (§18.5): на `/` и `/stats`, тёмная тема, 1440×900, с
`screenPreset=wide` (худший случай `data-pixel=high`) обходит до 400 узлов
внутри `#main-content`, для каждого собирает матчнутые правила слоя `pixel` и
список объявленных в них свойств. Нарушением заявления считается любое из
`position, display, float, grid*, flex*, inset/top/right/bottom/left`;
отдельной строкой «расширенная проверка» — `width/height/min-*/max-*/margin*`
(там находка не опровергает буквальное заявление §11, но идёт в «Находки»).
Результат → `data/pixel-layer-scan.json`. Статическим дополнением — grep тех же
свойств по 9 файлам `pixel-*.css`, расхождение live/static объясняется.

### 6. Блок D — палитра вне токенов (§18.4)

`recon/hex.sh` собирает инвентарь всех цветовых литералов корпуса
`static/css/*.css`: hex (`#[0-9a-fA-F]{3,8}`), `rgb()/rgba()`, `hsl()/hsla()`.
Результат → `data/hex-inventory.tsv` c колонками
`literal, kind, occurrences, files, class, note`, где `class` — ручная
классификация каждой уникальной записи:

- `T` — точный дубль значения токена из `tokens.css` (настоящий дубль палитры);
- `P` — палитровый цвет без токена вовсе;
- `N` — не-палитровое употребление (тень/градиент/маска/data-uri/`transparent`);
- `S` — литерал внутри самого `tokens.css` (легитимный источник);
- `C` — попал из комментария (grep их не отличает).

Отчёт даёт агрегат по классам и файлам, полный список классов `T` и `P`
(именно они — ответ на белое пятно), и фиксирует найденную дыру:
`scripts/design-token-audit.py:206-213` проверяет хардкоды только в `base.css`
(829 B из корпуса), pre-commit-гейт `.pre-commit-config.yaml:43-48` при этом
называется «хардкоды в base.css» честно, но покрытие корпуса нулевое.

### 7. Блок E — `/review` как режим (§18.6)

`recon/review-mode.js` проходит живой путь: `GET /review` → 200 и тот же
шаблон, что `/`, но с форсированным `onlyWrong` (маркер в DOM); ровно один
активный пункт навигации, и это `FOCUS`, а не отдельный раздел (проверяется
`aria-current`/активный класс в `fragments/sidebar.html` и
`fragments/mobile-nav.html`, ожидание — `NavSection.java:29-35`); затем сессия
TRAINING, ответ заведомо неверным вариантом, и сверка счётчика ошибок в рельсе
прогресса до/после (числа + два снимка `shots/review-*`). Реальные селекторы
разрешаются на живом DOM; если поведение не совпало с javadoc — это находка, а
не повод править код в этой задаче.

### Отвергнутые альтернативы

- Прогон по общей БД `interview` — отвергнут: `QaFixtureRunner` труncate'ит
  прогресс пользователя.
- Второй контейнер postgres на своём порту — отвергнут: лишняя инфраструктура,
  отдельная БД в уже поднятом контейнере даёт ту же изоляцию (YAGNI).
- Новый `e2e/*.spec.js` под разведку — отвергнут: разовый инструмент не должен
  оседать в продуктовом наборе тестов и в его гейтах.
- Голден-сравнение (`VISUAL_GOLDEN=1`) — отвергнуто: задача «увидеть, как
  есть», а не «проверить отсутствие регрессии»; голдены живут в 3 вьюпортах.
- `sheet.disabled` для отключения слоя `pixel` — невозможно: CSS едет одной
  склеенной лентой (`head.html:333`, `CssBundleService`).
- Правка `scripts/design-token-audit.py` в этой задаче — отвергнута: задача
  артефактная, расширение аудитора уходит в Follow-ups.

## Риски

- **Сборка/старт приложения падает** (gradle-wedge, Java 22 vs toolchain 17,
  занятый порт). Митигация: `--no-daemon`, отдельный порт 8091, лог в
  `data/boot.log`. Если старт невозможен после документированных попыток — это
  blocker, а НЕ повод сдать отчёт по чтению кода (AC-11).
- **Playwright не разрешается по симлинку** (несовпадение версии пакета и кэша
  браузеров). Митигация: фолбэк `npm ci` в `e2e/`, затем MCP `chrome-devtools`.
- **Импорт банка на пустой БД долгий** (9818 вопросов + MCQ). Ожидание — минуты;
  таймауты старта поднять, прогрев уже выключен профилем `qa`.
- **CDP `getMatchedStylesForNode` не размечает слои** в текущем Chromium →
  фолбэк на разбор текста ленты (описан в решении); способ обязателен к
  указанию в отчёте.
- **`/session-summary` недостижим** без POST `/finish` с `_csrf` и одноразов.
  Митигация: строка `НЕДОСТИЖИМО:` вместо снимка (AC-5).
- **Параллельные агенты меняют репо во время прогона** (хартия §4). Митигация:
  SHA фиксируется до прогона и сверяется после; при расхождении измерения
  пересняты на новом SHA.
- **Раздувание отчёта** полным hex-инвентарём. Митигация: полная таблица — в
  `data/hex-inventory.tsv`, в отчёте агрегат + классы `T`/`P`.
