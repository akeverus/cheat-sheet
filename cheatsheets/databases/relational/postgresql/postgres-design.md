## Этапы проектирования
- Выделить сущности (по смыслу предметной области) и атрибуты; атомизировать составные атрибуты.
- Определить уникальные идентификаторы (первичные ключи) и связи между сущностями.
- Нормализовать структуру, убрав избыточность и аномалии вставки/удаления/обновления.
- Привязать атрибуты к доменам (тип, диапазон, допускает ли NULL).

## Ключи и их типы
- `Superkey`: любой набор атрибутов, однозначно идентифицирующий строку.
- `Candidate key`: минимальный **superkey** без **NULL**, с гарантией уникальности.
- `Primary key`: выбранный **candidate key** (часто surrogate `id`), уникален, не меняется.
- `Alternate key`: **candidate key**, не выбранный основным.

## Внешние ключи и связи
- Внешний ключ (FK) указывает на ключ в родительской таблице (обычно PK).
- Типы связей: `1:1`, `1:N`, `M:N` (через промежуточную таблицу с составным `PK` из двух FK).
- Пример `M:N`: `articles` ↔ `tags` через `**article_tags(article_id, tag_id)`.

## Ссылочная целостность
- **Аномалии:**
  - Удаление: `FK` остаётся после удаления родителя.
  - Вставка: `FK` указывает в никуда.
  - Обновление: несогласованные дубли значений.
- **Стратегии:**
  - `ON **DELETE CASCADE**` — жёстко удалять дочерние строки.
  - `ON **DELETE SET NULL**` — допускать отсутствие связи, если `FK` **nullable**.
  - Вставки в дочерние таблицы — либо с валидным `FK`, либо с `NULL` (если разрешено).

## Нормализация и функциональные зависимости
- Функциональная зависимость: `A → B` если значение `A` однозначно задаёт `B`; детерминант — атрибут слева.
- 1NF: нет повторяющихся групп, атрибуты атомарны, одна сущность на таблицу.
- 2NF: таблица в 1NF, все неключевые атрибуты полностью зависят от полного составного `PK` (нет частичных зависимостей).
- 3NF (BCNF): таблица в 2NF, нет транзитивных зависимостей неключевых атрибутов от `PK` (**A→B** и **B→C** ⇒ вынести **B** и **C** в отдельную таблицу).
- 4NF: убрать многозначные зависимости (скрытые M:N внутри одной таблицы).
- 5NF: дальнейшее декомпозиция для устранения избыточности, когда таблицу можно собрать из более мелких без потерь.
- Практика: при обнаружении частичных/транзитивных зависимостей вынести атрибуты в отдельные таблицы с `FK` на детерминант. Если данных много — добавьте индексы на `FK` и часто фильтруемые поля.

## Домены и ограничения
- Домены задают допустимые значения: тип, диапазон, **NULL**/**NOT NULL**, **CHECK**.
- **Пример домена и использования:**
```sql
-- Домен email с проверкой формата и использование в таблице users
CREATE DOMAIN email_addr AS TEXT
  CHECK (VALUE ~* '^[^@]+@[^@]+\\.[^@]+$');

CREATE TABLE users (
  id    SERIAL PRIMARY KEY,
  email email_addr NOT NULL UNIQUE
);
```
- **CHECK**‑ограничения полезны для бизнес-правил (**например, `amount > 0`, `status `IN` (...**)`).

## Практические советы по моделированию
- Минимизируйте широкие таблицы: группируйте редко используемые поля в отдельные сущности.
- Не бойтесь **surrogate** ключей (`BIGSERIAL`, `UUID`) для стабильности связей; естественные ключи делайте **UNIQUE**.
- Добавляйте `created_at`, `updated_at` на изменяемых сущностях; используйте `**DEFAULT now**()` где нужно.
- Для связей M:N создавайте промежуточную таблицу с `PK` из двух `FK` и индексами на оба.
- Храните истории/аудит отдельно (append-only), не смешивайте с актуальными данными.
- Планируйте индексы под частые фильтры и **JOIN**; для статусов/дат — составные `(status, `created_at` DESC)`.
- Помните о партиционировании по дате/тенанту для очень больших таблиц.

## Пример разбиения сущностей
- Сущности: `users`, `orders`, `order_items`, `products`.
- **Ключи:**
  - `**users(id bigserial pk, email unique)`.
  - `**products(**id bigserial pk, sku unique, price numeric(12,2**))`.
  - `**orders(id bigserial pk, `user_id` fk users, status, created_at)`.
  - `**order_items(**order_id fk orders, `product_id` fk products, qty int, price numeric(12,2**), pk (order_id, product_id))`.
- **Интеграция:**
  - Внешние ключи с `ON **DELETE CASCADE**` на `order_items`.
  - Индексы: `**orders(user_id, created_at)`, `**order_items(product_id)`.

## Мультиарендность и RLS
- **Подходы:**
  - Отдельные базы/схемы на арендатора — сильная изоляция, но сложнее эксплуатация.
  - Одна БД, общий набор таблиц с колонкой `tenant_id` — проще, требуется строгий контроль доступа.
- **Row Level Security** (RLS):**
```sql
-- Включение RLS и политика изоляции по tenant_id
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY orders_tenant_isolation ON orders
USING (tenant_id = current_setting('app.tenant_id')::int);
```
- Устанавливайте `app.tenant_id` при подключении через `SET LOCAL`.

## Софт-делит, аудит и версионирование
- Софт-делит: колонка `deleted_at` + частичные индексы `**WHERE deleted_at** `IS` **NULL**`.
- Аудит: отдельная таблица `*_audit` с `changed_by`, `changed_at`.
- Версионирование записей: стратегия **SCD2** — таблица истории с `valid_from`, `valid_to`, `is_current`.

## Конвенции именования и ERD
- Имена таблиц — множественное, **snake_case** (`order_items`), `PK` — `id`, `FK` — `<**table**>_id`.
- Ограничения: `pk_<**table**>`, `fk_<**table**>__<**ref**>`, `chk_<**table**>__<**field**>`.
- Делайте **ERD** (dbdiagram.io, sqldbm) и держите в репо; обновляйте при изменениях схемы.

## Денормализация осознанно
- Причины: отчётность, **precomputed** агрегаты, быстрые фильтры по редко меняющимся данным.
- Инструменты: материализованные представления (`REFRESH `MATERIALIZED VIEW` CONCURRENTLY`), таблицы-агрегаты, кэширующие таблицы.
- Риски: сложнее инкрементальное обновление, риск расхождения; добавляйте фоновые задачи/триггеры для актуализации.

## Подробное описание нормализации

### Восходящий и нисходящий подходы проектирования

При проектировании базы данных на этапе выделения сущностей и их атрибутов мы можем использовать два подхода: восходящий и нисходящий.

**Восходящий подход** предусматривает выделение необходимых атрибутов, которые надо сохранить в бд. Затем выделенные атрибуты группируются в сущности, для которых впоследствии создается таблицы. Такой подход больше подходит для проектирования небольших баз данных с небольшим количеством атрибутов.

**Пример восходящего подхода:**

**Нам дана следующая информация:**
1. Том посещает курс по математике, который преподает профессор Смит.
2. Сэм посещает курс по математике, которые преподает профессор Смит.
3. Том посещает курс по языку **JavaScript**, который преподает ассистент Адамс.
4. Боб посещает курс по алгоритмам, который преподает ассистент Адамс.
5. Сэм имеет следующие электронный адрес **sam**@**gmail.com** и телефон +1235768789.

Какие данные из этой информации мы можем сохранить: имя студента, название курса, учебная должность преподавателя, имя преподавателя, электронный адрес студента.

**Затем мы можем выполнить группировку по сущностям, к которым относятся эти данные:**
1. Студент
2. Преподаватель
3. Курс

Так, те данные, которые имеются, позволяют выделить три сущности: студент, преподаватель и курс. При этом мы вполне можем добавлять какие-то недостающие данные. Также следует отметить, что какие-то данные могут иметь отношение к разным сущностям. Например, курс хранит информацию о студенте, которые его посещает. А студент хранит информацию о посещаемом курсе. Подобная избыточность данных решается на последующих шагах проектирования в процессе нормализации базы данных.

**Нисходящий подход** подразумевает выявление сущностей. Затем происходит анализ сущностей, выявляются связи между ними, а потом и атрибуты сущностей.

Но подобных атрибутов может оказаться очень много: сотни и даже тысячи. И в этом случае более оптимальным будет нисходящий подход. Данный подход подразумевает выявление сущностей. Затем происходит анализ сущностей, выявляются связи между ними, а потом и атрибуты сущностей.

То есть в данном случае мы могли бы сразу определить, что нам надо хранить данные по студентам, курсам и преподавателям. Затем в рамках каждой сущности выявить атрибуты.

Например, у сущности «Студент» мы могли бы выделить такие атрибуты, как имя студента, его адрес, телефон, рост, вес, год его рождения. В тоже время нам надо учитывать не вообще все свойства, которые в принципе могут быть у сущности «Студент», а только те, которые имеют значение в рамках описываемой системы. Вряд ли в данном случае играют роль такие свойства как рост или вес студента, поэтому мы можем их вычеркнуть из списка атрибутов при проектировании таблицы.

**Иногда подходы комбинируются.** Для описания разных частей системы могут использоваться разные подходы. А затем их результаты объединяются.

### Атомизация атрибутов

При определении атрибутов происходит разделение сложных комплексных элементов на более простые. Так, в случае с именем студента мы можем его разбить на собственно имя и фамилию. Это позволит впоследствии выполнять операции с этими подэлементами отдельно, например, сортировать студентов только по фамилии.

То же самое касается адреса — мы можем сохранить весь адрес целиком, а можем разбить его на части — дом, улицу, город и т.д.

В то же время возможность разделения одного элемента на подэлементы не всегда может быть востребованной. В ряде задач это может быть просто не нужно. Выделять необходимо только те элементы, которые действительно нужны.

**Пример атомизации:**
В соответствии с этим аспектом мы можем выделить у сущности «Студент» следующие атрибуты: имя студента, фамилия студента, год рождения, город, улица, дом, телефон.

### Домены (Domains)

Каждый атрибут имеет домен (domain). Домен представляет набор допустимых значений для одного или нескольких атрибутов. По сути домен определяет смысл и источник значений, которые могут иметь атрибуты.

Домены могут отличаться для разных атрибутов, но также несколько атрибутов могут иметь один домен.

**Пример определения доменов:**

**Для сущности Студент были определены атрибуты. Определим используемые домены:**

1. Имя. Домен представляет все возможные имена, которые могут использоваться. Каждое имя представляет строку длиной максимум 20 символов (маловероятно, что нам могут встретиться имена свыше 20 символов).

2. Фамилия. Домен представляет все возможные фамилии, которые могут использоваться. Каждая фамилия представляет строку длиной максимум 20 символов.

3. Год рождения. Домен представляет все года рождения. Каждый год является числовым значением от `1950` до `2017`.

4. Город. Домен представляет все города текущей страны. Каждый город представляет строку длиной максимум 50 символов.

5. Улица. Домен представляет все улицы текущей страны. Каждая улица представляет строку длиной максимум 50 символов.

6. Дом. Домен представляет все возможные номера домов. Каждый номер дома является числом от 1 до, скажем, `10000`.

7. Телефон. Домен представляет все возможные телефонные номера. Каждый номер является строкой длиной в 11 символов.

Определяя домен, мы сразу видим, какие данные и каких типов будут хранить атрибуты. Какое-то другое значение, которое не соответствует домену, атрибут иметь не может.

В примере выше каждый атрибут имеет свой домен. Но домены могут совпадать. Например, если бы сущность содержала бы следующие два атрибута: город рождения и город проживания, то домен бы совпадал и был бы одним и тем же для обоих атрибутов.

**Использование доменов в `PostgreSQL`:**
```sql
-- Создание домена
CREATE DOMAIN email_address AS TEXT
  CHECK (VALUE ~* '^[^@]+@[^@]+\.[^@]+$');

CREATE DOMAIN phone_number AS VARCHAR(11)
  CHECK (VALUE ~ '^\+?[0-9]{10,11}$');

CREATE DOMAIN year_birth AS INTEGER
  CHECK (VALUE >= 1950 AND VALUE <= 2017);

-- Использование доменов
CREATE TABLE Students (
    Id SERIAL PRIMARY KEY,
    FirstName VARCHAR(20) NOT NULL,
    LastName VARCHAR(20) NOT NULL,
    BirthYear year_birth,
    City VARCHAR(50),
    Street VARCHAR(50),
    House INTEGER CHECK (House >= 1 AND House <= 10000),
    Phone phone_number,
    Email email_address
);
```

### Определитель NULL

При определении атрибутов и их домена необходимо проанализировать, а может ли у атрибута отсутствовать значение. Определитель **NULL** позволяет задать отсутствие значения.

Например, в примере выше у студента обязательно должно быть какое-либо имя, поэтому недопустима ситуация, когда у атрибута, который представляет имя, отсутствует значение.

В то же время студент может не иметь телефонного номера или в рамках системы телефон не обязателен. Поэтому на этапе проектирования таблицы можно указать, что данный атрибут позволяет значение **NULL**.

Как правило, большинство современных реляционных СУБД поддерживают определитель **NULL** и позволяют задать его допустимость для столбца таблицы.

## Подробное описание нормальных форм

### Первая нормальная форма (1NF)

Первая нормальная форма предполагает, что таблица не должна содержать повторяющихся столбцов или таких столбцов, которые содержат наборы значений. Ненормализованная таблица в этом случае может содержать одну или несколько повторяющихся групп данных. Повторяющаяся группа — это группа из одного или нескольких атрибутов таблицы, в которой возможно наличие нескольких значений для ключевого атрибута таблицы.

**Итогом применения первой формы должно стать наличие для одного атрибута сущности только одного столбца в таблице, который при этом должен содержать скалярное значение.**

**Два подхода к переходу к первой нормальной форме:**

1. **Flattening (выравнивание)** — предполагает декомпозицию строки с повторяющимися группами данных, при котором для каждой повторяющейся группы создается своя строка. Полученная в результате таблица будет содержать атомарные значения для каждого из атрибутов. Хотя в то же время этот подход увеличит избыточность данных.

2. **Вынесение повторяющихся групп** — предполагает, что один атрибут или группа атрибутов назначаются ключом ненормализованной таблицы, а затем повторяющиеся группы удаляются из таблицы и помещаются в отдельную таблицу вместе с копиями ключа из исходной таблицы.

**Пример применения 1NF:**

**Пусть у нас есть система, которая описывается следующей информацией:**
1. Том посещает курс по математике, который преподает Смит. Дата записи 01/2017.
2. Сэм посещает курс по алгоритмам, которые преподает Адамс. Дата записи 01/2017.
3. Боб посещает курс по математике, который преподает Смит. Дата записи 01/2017.
4. Том посещает курс по языку **JavaScript**, который преподает Адамс. Дата записи 01/2017.
5. Сэм имеет два электронных адреса: **sam**@**gmail.com** и **sam**@**hotmail.com**.

**Ненормализованная таблица:**
Для каждого студента определен уникальный идентификатор **StudentId**, а также атрибут **Name** (имя), **Emails** (все электронные адреса), **Course1**/**Course2** (курс), **Date1**/**Date2** (дата поступления), **Teacher1**/**Teacher2** (преподаватель).

Эта таблица представляет прекрасный пример отклонения от первой нормальной формы. В первую очередь мы видим группу повторяющихся атрибутов, которые представляют данные по одному курсу: **Course**, **Date**, **TeacherId**, **Teacher**. Эти атрибуты представляют повторяющуюся группу, которую можно условно назвать **StudentCourse**.

Вторая проблема — атрибут **Emails** содержит набор электронных адресов. Фактически этот атрибут также образует повторяющуюся группу.

**Решение:**

Для избавления от первой повторяющейся группы атрибутов применим первый подход: создадим для каждой повторяющейся группы отдельную строку. Теперь у нас нет повторяющихся столбцов, но увеличилась избыточность данных, так как для студента Том определено уже две строки в таблице, и соответственно Id повторяется. Но тем не менее 1-я нормальная форма применена.

Для избавления от второй повторяющейся группы — атрибута **Emails** применим второй подход: вынесем эту группу с копией ключа в отдельную таблицу:

```sql
-- Вынос повторяющейся группы в отдельную таблицу (нормализация)
CREATE TABLE Emails (
    Email VARCHAR(255) PRIMARY KEY,
    StudentId INTEGER REFERENCES Students(Id)
);
```

### Вторая нормальная форма (2NF)

Во второй нормальной форме каждый столбец в таблице, который не является ключом, должен зависеть от ключа.

**Ключевой момент второй нормальной формы — полная функциональная зависимость.** Она предполагает, что атрибут В полностью функционально зависим от атрибута А, если атрибут В функционально зависит от полного значения атрибута А, а не от какого-либо подмножества значений из атрибута А. То есть, если атрибут А составляют несколько значений, скажем, А1 и А2, то атрибут В полностью функционально зависит от А, если он зависит и от А1 и от А2 (А1, А2 → В).

Если атрибут В зависит только от какого-либо подмножества из атрибута А, например, только от А1, то имеет место частичная функциональная зависимость.

Эта форма применяется к тем таблицам, которые имеют составной первичный ключ, то есть где первичный ключ состоит из нескольких атрибутов. Если в таблице несоставной первичный ключ, то в этом случае считается, что все остальные атрибуты автоматически находятся в полной функциональной зависимости от первичного ключа.

**Пример применения 2NF:**

**Возьмем таблицу **StudentCourses** после применения первой нормальной формы:**

**StudentId | `Name` | `CourseId` | `Course` | `Date` | `TeacherId` | Teacher**

**На данный момент эта таблица имеет составной первичный ключ **StudentId** + **CourseId**. Какие функциональные зависимости от ключевых атрибутов здесь можно выделить:**

- **StudentId**, **CourseId** → **Date**
- **StudentId** → **Name**
- **CourseId** → **Course**, **TeacherId**, **Teacher**

От обоих частей составного ключа **StudentId** + **CourseId** зависит только атрибут **Date** — дата, в которую студент с идентификатором **StudentId** поступил на курс с идентификатором **CourseId**.

Атрибут **Name** зависит только от части составного ключа — от атрибута **StudentId**, так как зная идентификатор студента, можно сказать, какое у него имя. В данном случае имеет факт частичной зависимости.

Атрибуты **Course**, **TeacherId**, **Teacher** зависят от другой части ключа — от атрибута **CourseId**. Зная значение **CourseId**, можно сказать, как называется курс, какой у курса преподаватель, какую должность он занимает. Опять же здесь частичная зависимость.

Наличие частичных зависимостей говорит о том, что таблица не находится во второй нормальной форме. И для перехода к этой форме необходимо переместить атрибуты, которые не входят в первичный ключ, в новую таблицу вместе с копией части первичного ключа, от которой они функционально зависят.

**Решение:**

**В нашем случае из одной таблицы получатся три таблицы:**

1. **Таблица `Students`:**
   - **StudentId** (PK)
   - **Name**

2. **Таблица `Courses`:**
   - **CourseId** (PK)
   - **Course**
   - **TeacherId** (FK)
   - **Teacher**

3. **Таблица `StudentCourses`:**
   - **StudentId** (PK, FK)
   - **CourseId** (PK, FK)
   - **Date**

Итогом стало образование связи многие ко многим (много студентов — много курсов) между таблицами **Students** и **Courses** через таблицу **StudentCourses**.

Таким образом, база данных перешла во вторую нормальную форму.

### Третья нормальная форма (3NF)

Третья нормальная форма предполагает, что каждый столбец, не являющийся ключом, должен зависеть только от столбца, который является ключом, то есть должна отсутствовать транзитивная функциональная зависимость (transitive functional dependency).

**Транзитивная функциональная зависимость** выражается следующим образом: А → В и В → С. То есть атрибут С транзитивно зависит от атрибута А, если атрибут С зависит от атрибута В, а атрибут В зависит от атрибута А (при условии, что атрибут А функционально не зависит ни от атрибута В, ни от атрибута С).

Если столбец зависит не только от первичного ключа, то данный столбец находится не в той таблице, в которой он должен находиться, либо же является производным от других столбцов.

Для нормализации из исходной таблицы те атрибуты, которые находятся в транзитивной зависимости от ключа, выносятся в отдельную таблицу с копией того атрибута, от которого они непосредственно зависят.

При применении третьей нормальной формы таблица должна находиться во второй нормальной форме. 3NF позволяет значительно снизить избыточность данных.

**Пример применения 3NF:**

**Для примера возьмем сформированную таблицу **Courses**, которая содержит информацию о курсах и которая находится во второй нормальной форме:**

**CourseId | `Course` | `TeacherId` | Teacher**

**Какие функциональные зависимости здесь можно выделить:**

- **CourseId** → **Course**, **TeacherId**, **Teacher**
- **Course** → **CourseId**, **TeacherId**, **Teacher**
- **TeacherId** → **Teacher**

Вторая зависимость фактически аналогична первой и говорит о том, что атрибут **Course** является потенциальным ключом.

Третья зависимость говорит о том, что, зная идентификатор преподавателя, мы можем узнать его фамилию и должность. То есть через атрибут **TeacherId** атрибут **Teacher** зависит от **CourseId** (CourseId → `TeacherId` и `TeacherId` → Teacher). И в данном случае мы можем говорить о транзитивной зависимости **Teacher** от **CourseId**.

**Решение:**

**Для нормализации необходимо вынести в отдельную таблицу атрибуты **TeacherId** и **Teacher**. Для этого пусть будет отдельная таблица **Teachers**:**

1. **Таблица `Teachers`:**
   - **TeacherId** (PK)
   - **Teacher**

2. **Таблица `Courses`:**
   - **CourseId** (PK)
   - **Course**
   - **TeacherId** (FK)

**А таблица **Courses** сократится следующим образом:**

**CourseId | `Course` | TeacherId**

### Нормальная форма Бойса-Кодда (BCNF)

Нормальная форма Бойса-Кодда (BCNF) является немного более строгой версией третьей нормальной формы. **BCNF** требует, чтобы каждая детерминант (атрибут или группа атрибутов, от которых зависят другие атрибуты) была потенциальным ключом.

**Различие между 3NF и `BCNF`:**

В 3NF разрешается зависимость неключевого атрибута от другого неключевого атрибута, если это не транзитивная зависимость от первичного ключа.

В **BCNF** все детерминанты должны быть потенциальными ключами (candidate keys).

**Пример различия:**

**Рассмотрим таблицу:**
- **StudentId** (PK)
- **CourseId** (PK)
- **TeacherId**
- **TeacherName**

**Если **TeacherId** → **TeacherName**, то:**
- В 3NF это допустимо (если `TeacherId` не является частью ключа).
- В **BCNF** это требует вынесения **TeacherName** в отдельную таблицу, если **TeacherId** не является потенциальным ключом.

### Четвертая нормальная форма (4NF)

Четвертая нормальная форма (4NF) применяется для устранения многозначных зависимостей (multivalued dependencies) — таких зависимостей, где столбец с первичным ключом имеет связь один-ко-многим со столбцом, который не является ключом. Эта нормальная форма устраняет некорректные отношения многие-ко-многим.

**Многозначная зависимость** существует, когда для одного значения атрибута А существует несколько значений атрибута В, и эти множества значений независимы друг от друга.

**Пример:**

**Рассмотрим таблицу:**
- **StudentId** (PK)
- **CourseId**
- **HobbyId**

**Если один студент может иметь несколько курсов и несколько хобби, и они независимы друг от друга, то это многозначная зависимость. Таблицу следует разделить на:**
- **StudentCourses(StudentId, CourseId)
- **StudentHobbies(StudentId, HobbyId)

### Пятая нормальная форма (5NF)

Пятая нормальная форма (5NF) разделяет таблицы на более малые таблицы для устранения избыточности данных. Разбиение идет до тех пор, пока нельзя будет воссоздать оригинальную таблицу путем объединения малых таблиц.

**Критерий 5NF:**
Таблица находится в 5NF, если и только если каждая зависимость соединения (join dependency) является следствием ее ключей.

**Применение:**
5NF применяется редко на практике, так как она может привести к излишней декомпозиции и усложнению запросов.

### Шестая нормальная форма (6NF)

Шестая нормальная форма (domain key normal form/6NF). Каждое ограничение в связях между таблицами должно зависеть только от ограничений ключа и ограничений домена, где домен представляет набор допустимых значений для столбца. Эта форма предотвращает добавление недопустимых данных путем установки ограничения на уровне отношений между таблицами, но не на уровне таблиц или столбцов. Данная форма, как правило, не применима на уровне СУБД, в том числе и в **PostgreSQL**.

## Практические рекомендации по нормализации

### Когда применять нормализацию

**Применяйте нормализацию для:**
- Онлайн-транзакционных систем (OLTP), где важна целостность данных.
- Систем с частыми обновлениями данных.
- Систем, где важна минимизация избыточности.

**Не применяйте излишнюю нормализацию для:**
- Систем отчетности (OLAP), где важна скорость чтения.
- Систем с редкими обновлениями и частыми сложными запросами.
- Денормализованные схемы для аналитики.

### Денормализация с умом

**Когда денормализовать:**
1. **Отчетность и аналитика** — денормализованные данные для быстрого чтения.
2. **Precomputed агрегаты** — предвычисленные суммы, средние и т.д.
3. **Редко изменяющиеся данные** — денормализация безопасна, если данные стабильны.
4. **Партиционированные таблицы** — некоторые данные можно денормализовать внутри партиций.

**Инструменты денормализации:**
- **Материализованные представления:**
```sql
CREATE MATERIALIZED VIEW mv_order_stats AS
SELECT
    user_id,
    COUNT(*) AS order_count,
    SUM(total_amount) AS total_spent,
    AVG(total_amount) AS avg_order
FROM orders
GROUP BY user_id;

-- Обновление
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_order_stats;
```

- **Триггеры для автоматического обновления:**
```sql
CREATE OR REPLACE FUNCTION update_user_stats()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE users
    SET
        order_count = (SELECT COUNT(*) FROM orders WHERE user_id = NEW.user_id),
        total_spent = (SELECT SUM(total_amount) FROM orders WHERE user_id = NEW.user_id)
    WHERE id = NEW.user_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_update_user_stats
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW
EXECUTE FUNCTION update_user_stats();
```

- **Таблицы-агрегаты:**
```sql
CREATE TABLE daily_order_stats (
    date DATE PRIMARY KEY,
    order_count INTEGER,
    total_amount NUMERIC,
    avg_amount NUMERIC
);

-- Обновление через cron или триггеры
```

### Компромиссы нормализации

**Преимущества нормализации:**
- Минимизация избыточности данных.
- Упрощение обновлений (изменение в одном месте).
- Предотвращение аномалий вставки, обновления и удаления.
- Меньший размер базы данных.

**Недостатки нормализации:**
- Больше **JOIN** в запросах (может замедлить чтение).
- Сложнее запросы для получения связанных данных.
- Может потребоваться больше таблиц.

**Когда идти на компромисс:**
- Нормализуйте до 3NF для **OLTP** систем.
- Денормализуйте для **OLAP** систем.
- Используйте материализованные представления для баланса.
- Рассмотрите партиционирование для больших таблиц.

### Процесс нормализации на практике

**Шаги нормализации:**
1. **Собрать требования** — определить все сущности и атрибуты.
2. **Создать `ER`-диаграмму** — визуализировать сущности и связи.
3. **Применить 1NF** — устранить повторяющиеся группы.
4. **Применить 2NF** — устранить частичные зависимости.
5. **Применить 3NF** — устранить транзитивные зависимости.
6. **Проверить BCNF** — для строгих требований.
7. **Тестировать** — проверить производительность и целостность.

**Инструменты для моделирования:**
- **dbdiagram.io** — онлайн инструмент для создания `ER`-диаграмм.
- **sqldbm.com** — профессиональное моделирование баз данных.
- **pgModeler** — открытый инструмент для **PostgreSQL**.
- **DBeaver** — встроенные инструменты для визуализации схем.

### Примеры реальных схем

**E-commerce система (нормализованная):**
```sql
-- Пользователи
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    name VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now()
);

-- Товары
CREATE TABLE products (

```sql
-- `OLTP` таблицы для транзакций

    id `SERIAL PRIMARY KEY`,
    `date_key INTEGER NOT NULL`,
    `customer_key INTEGER NOT NULL`,
    `product_key INTEGER NOT NULL`,
    `store_key INTEGER NOT NULL`,
    quantity `INTEGER NOT NULL`,
    `unit_price DECIMAL`(10,2) `NOT NULL`,
    `total_amount DECIMAL`(10,2) `NOT NULL`
);

-- Измерения для `OLAP`
`CREATE TABLE dim_date` (
    `date_key SERIAL PRIMARY KEY`,
    `date_actual DATE NOT NULL`,
    year `INTEGER NOT NULL`,
    quarter `INTEGER NOT NULL`,
    month `INTEGER NOT NULL`,
    day `INTEGER NOT NULL`,
    `day_of_week INTEGER NOT NULL`,
    `is_weekend BOOLEAN NOT NULL`
);

`CREATE TABLE dim_customer` (
    `customer_key SERIAL PRIMARY KEY`,
    `customer_id INTEGER NOT NULL`, — ссылка на `OLTP`
    name `VARCHAR`(`100`) `NOT NULL`,
    email `VARCHAR`(`100`),
    segment `VARCHAR`(50),
    `registration_date DATE`,
    `is_active BOOLEAN DEFAULT TRUE`
);

-- `ETL` процесс для загрузки данных
`CREATE OR REPLACE FUNCTION etl_load_sales`()
`RETURNS` void `AS` $$
`DECLARE`
    `current_date DATE` := CURRENT_DATE;
    `date_key INTEGER`;
`BEGIN`
    — Получаем или создаем ключ даты
    `INSERT INTO dim_date` (`date_actual`, year, quarter, month, day, `day_of_week`, `is_weekend`)
    `VALUES` (`current_date`,
            `EXTRACT`(`YEAR FROM current_date`),
            `EXTRACT`(`QUARTER FROM current_date`),
            `EXTRACT`(`MONTH FROM current_date`),
            `EXTRACT`(`DAY FROM current_date`),
            `EXTRACT`(`DOW FROM current_date`),
            `EXTRACT`(`DOW FROM current_date`) `IN` (0, 6))
    `ON CONFLICT` (`date_actual`) `DO NOTHING`;

    `SELECT date_key INTO date_key FROM dim_date WHERE date_actual` = `current_date`;

    — Загружаем продажи
    `INSERT INTO fact_sales` (`date_key`, `customer_key`, `product_key`, `store_key`,
                           quantity, `unit_price`, `total_amount`)
    `SELECT`
        `date_key`,
        dc.`customer_key`,
        dp.`product_key`,
        ds.`store_key`,
        `oi.quantity`,
        oi.`unit_price`,
        `oi.quantity` * oi.`unit_price`
    `FROM` orders o
    `JOIN order_items` oi `ON o.id` = oi.`order_id`
    `JOIN dim_customer` dc `ON` o.`customer_id` = dc.`customer_id`
    `JOIN dim_product` dp `ON` oi.`product_id` = dp.`product_id`
    `JOIN dim_store` ds `ON` o.`store_id` = ds.`store_id`
    `WHERE DATE`(o.`order_date`) = `current_date`;
`END`;
$$ `LANGUAGE` plpgsql;
```text

#### Saga Pattern в базе данных

```sql
-- Таблица для отслеживания саги
`CREATE TABLE order_saga` (
    id `UUID PRIMARY KEY DEFAULT gen_random_uuid`(),
    `order_id UUID NOT NULL`,
    `user_id UUID NOT NULL`,
    `total_amount DECIMAL`(10,2) `NOT NULL`,
    status `VARCHAR`(50) `DEFAULT` 'started',
    `current_step VARCHAR`(50) `DEFAULT` '`reserve_inventory`',
    `compensation_data JSONB`,
    `created_at TIMESTAMP DEFAULT` CURRENT_TIMESTAMP,
    `updated_at TIMESTAMP DEFAULT` CURRENT_TIMESTAMP
);

-- Таблица для шагов саги
`CREATE TABLE saga_steps` (
    id `UUID PRIMARY KEY DEFAULT gen_random_uuid`(),
    `saga_id UUID REFERENCES order_saga`(id),
    `step_name VARCHAR`(`100`) `NOT NULL`,
    status `VARCHAR`(50) `DEFAULT` 'pending', — pending, completed, failed, compensated
    `executed_at TIMESTAMP`,
    `compensated_at TIMESTAMP`,
    `error_message TEXT`,
    `step_data JSONB`
);

-- Функция для выполнения шага саги
`CREATE OR REPLACE FUNCTION execute_saga_step`(
    `p_saga_id UUID`,
    `p_step_name VARCHAR`,
    `p_step_function TEXT`
) `RETURNS BOOLEAN AS` $$
`DECLARE`
    `step_record RECORD`;
    success `BOOLEAN` := `FALSE`;
`BEGIN`
    — Находим или создаем шаг
    `INSERT INTO saga_steps` (`saga_id`, `step_name`)
    `VALUES` (`p_saga_id`, `p_step_name`)
    `ON CONFLICT` (`saga_id`, `step_name`) `DO NOTHING`;

    — Выполняем шаг
    `BEGIN`
        `EXECUTE p_step_function INTO` success;

        `IF` success `THEN`
            `UPDATE saga_steps`
            `SET` status = 'completed', `executed_at` = CURRENT_TIMESTAMP
            `WHERE saga_id` = `p_saga_id AND step_name` = `p_step_name`;
        `ELSE`
            `UPDATE saga_steps`
            `SET` status = 'failed', `executed_at` = CURRENT_TIMESTAMP
            `WHERE saga_id` = `p_saga_id AND step_name` = `p_step_name`;

            — Запускаем компенсацию
            `PERFORM compensate_saga`(`p_saga_id`);
            `RETURN FALSE`;
        `END IF`;

    `EXCEPTION WHEN OTHERS THEN`
        `UPDATE saga_steps`
        `SET` status = 'failed', `executed_at` = CURRENT_TIMESTAMP,
            `error_message` = `SQLERRM`
        `WHERE saga_id` = `p_saga_id AND step_name` = `p_step_name`;

        `PERFORM compensate_saga`(`p_saga_id`);
        `RETURN FALSE`;
    `END`;

    `RETURN TRUE`;
`END`;
$$ `LANGUAGE` plpgsql;

-- Функция компенсации
`CREATE OR REPLACE FUNCTION compensate_saga`(`p_saga_id UUID`)
`RETURNS` void `AS` $$
`DECLARE`
    `step_record RECORD`;
`BEGIN`
    — Компенсируем выполненные шаги в обратном порядке
    `FOR step_record IN`
        `SELECT` * `FROM saga_steps`
        `WHERE saga_id` = `p_saga_id AND` status = 'completed'
        `ORDER BY executed_at DESC`
    `LOOP`
        — Выполняем компенсацию (здесь должна быть логика для каждого шага)
        `CASE step_record`.`step_name`
            `WHEN` '`reserve_inventory`' `THEN`
                — Освободить зарезервированный инвентарь
                `PERFORM release_inventory`(`step_record`.`step_data`);
            `WHEN` '`charge_payment`' `THEN`
                — Отменить платеж
                `PERFORM refund_payment`(`step_record`.`step_data`);
            — Другие шаги...
        `END CASE`;

        `UPDATE saga_steps`
        `SET` status = 'compensated', `compensated_at` = CURRENT_TIMESTAMP
        `WHERE` id = `step_record`.id;
    `END LOOP`;

    — Обновляем статус саги
    `UPDATE order_saga`
    `SET` status = 'compensated', `updated_at` = CURRENT_TIMESTAMP
    `WHERE` id = `p_saga_id`;
`END`;
$$ `LANGUAGE` plpgsql;
```text

#### Система версионирования

```sql
-- Таблица для версионирования
`CREATE TABLE product_versions` (
    `product_id INTEGER NOT NULL`,
    `version_number INTEGER NOT NULL`,
    name `VARCHAR`(`255`),
    description `TEXT`,
    price `DECIMAL`(10,2),
    `changed_by INTEGER REFERENCES` users(id),
    `changed_at TIMESTAMP DEFAULT` CURRENT_TIMESTAMP,
    `change_reason TEXT`,

    `PRIMARY KEY` (`product_id`, `version_number`)
);

-- Триггер для автоматического версионирования
`CREATE OR REPLACE FUNCTION version_product`()
`RETURNS TRIGGER AS` $$
`DECLARE`
    `next_version INTEGER`;
`BEGIN`
    — Получаем следующий номер версии
    `SELECT COALESCE`(`MAX`(`version_number`), 0) + 1
    `INTO next_version`
    `FROM product_versions`
    `WHERE product_id` = `COALESCE`(`NEW`.id, `OLD`.id);

    — Сохраняем старую версию
    `IF` TG_OP = '`UPDATE`' `THEN`
        `INSERT INTO product_versions` (
            `product_id`, `version_number`, name, description, price,
            `changed_by`, `change_reason`
        )
        `SELECT`
            `OLD`.id, `next_version`, `OLD`.name, `OLD`.description, `OLD`.price,
            `NEW`.`updated_by`, '`Updated via application`';
    `END IF`;

    `RETURN COALESCE`(`NEW`, `OLD`);
`END`;
$$ `LANGUAGE` plpgsql;

-- Применяем триггер
`CREATE TRIGGER product_versioning_trigger`
    `AFTER UPDATE ON` products
    `FOR EACH ROW EXECUTE FUNCTION version_product`();

-- Функция для получения версии продукта
`CREATE OR REPLACE FUNCTION get_product_version`(`p_product_id INTEGER`, `p_version INTEGER`)
`RETURNS TABLE` (
    name `VARCHAR`(`255`),
    description `TEXT`,
    price `DECIMAL`(10,2),
    `changed_by INTEGER`,
    `changed_at TIMESTAMP`
) `AS` $$
`BEGIN`
    `RETURN QUERY`
    `SELECT`
        `pv.name`, `pv.description`, `pv.price`,
        pv.`changed_by`, pv.`changed_at`
    `FROM product_versions` pv
    `WHERE` pv.`product_id` = `p_product_id`
      `AND` pv.`version_number` = `p_version`;
`END`;
$$ `LANGUAGE` plpgsql;

-- Функция для сравнения версий
`CREATE OR REPLACE FUNCTION compare_product_versions`(`p_product_id INTEGER`, `p_version1 INTEGER`, `p_version2 INTEGER`)
`RETURNS TABLE` (
    `field_name TEXT`,
    `old_value TEXT`,
    `new_value TEXT`
) `AS` $$
`BEGIN`
    `RETURN QUERY`
    `SELECT`
        'name'::`TEXT`,
        `v1.name::TEXT`,
        `v2.name::TEXT`
    `FROM product_versions` v1, `product_versions` v2
    `WHERE` v1.`product_id` = `p_product_id AND` v1.`version_number` = `p_version1`
      `AND` v2.`product_id` = `p_product_id AND` v2.`version_number` = `p_version2`
      `AND v1.name IS DISTINCT FROM v2.name`

    `UNION ALL`

    `SELECT`
        'description'::`TEXT`,
        `v1.description::TEXT`,
        `v2.description::TEXT`
    `FROM product_versions` v1, `product_versions` v2
    `WHERE` v1.`product_id` = `p_product_id AND` v1.`version_number` = `p_version1`
      `AND` v2.`product_id` = `p_product_id AND` v2.`version_number` = `p_version2`
      `AND v1.description IS DISTINCT FROM v2.description`

    `UNION ALL`

    `SELECT`
        'price'::`TEXT`,
        `v1.price::TEXT`,
        `v2.price::TEXT`
    `FROM product_versions` v1, `product_versions` v2
    `WHERE` v1.`product_id` = `p_product_id AND` v1.`version_number` = `p_version1`
      `AND` v2.`product_id` = `p_product_id AND` v2.`version_number` = `p_version2`
      `AND v1.price IS DISTINCT FROM v2.price`;
`END`;
$$ `LANGUAGE` plpgsql;

        `c.id`,
        `c.name`,

        `SUM`(o.`total_amount`) as `total_spent`,
        `AVG`(o.`total_amount`) as `avg_order_value`
    `FROM` customers c
    `LEFT JOIN` orders o `ON c.id` = o.`customer_id`
    `WHERE` o.`order_date` >= CURRENT_DATE - `INTERVAL` '30 days'
    `GROUP BY c.id`, `c.name`
),

    `SELECT`
        `p.id`,
        `p.name`,
        `SUM`(`oi.quantity`) as `total_sold`,
        `SUM`(`oi.quantity` * oi.`unit_price`) as revenue
    `FROM` products p
    `JOIN order_items` oi `ON p.id` = oi.`product_id`
    `JOIN` orders o `ON` oi.`order_id` = `o.id`
    `WHERE` o.`order_date` >= CURRENT_DATE - `INTERVAL` '30 days'
    `GROUP BY p.id`, `p.name`

    cs.`avg_order_value`,
    `ps.name` as `top_product`,
    ps.`total_sold`,
    `ps.revenue`
`FROM customer_stats` cs
`CROSS JOIN LATERAL` (
    `SELECT` name, `total_sold`, revenue
    `FROM product_stats` ps
    `ORDER BY ps.revenue DESC`
    `LIMIT 1`
) ps
`ORDER BY` cs.`total_spent DESC`;

`CREATE TABLE audit_log` (
    id `SERIAL PRIMARY KEY`,
    `table_name TEXT NOT NULL`,
    operation `TEXT NOT NULL CHECK` (operation `IN` ('`INSERT`', '`UPDATE`', '`DELETE`')),
    `old_values JSONB`,
    `new_values JSONB`,
    `user_id INTEGER`,
    `session_id TEXT`,
    `client_ip INET`,
    `changed_at TIMESTAMP DEFAULT` CURRENT_TIMESTAMP
);

-- Функция аудита
`CREATE OR REPLACE FUNCTION audit_trigger_function`()
`RETURNS TRIGGER AS` $$
`DECLARE`
    `old_row JSONB`;
    `new_row JSONB`;
`BEGIN`
    — Преобразуем строки в `JSON`
    `IF` TG_OP != '`INSERT`' `THEN`
        `old_row` := `row_to_json`(`OLD`)::`JSONB`;
    `END IF`;

    `IF` TG_OP != '`DELETE`' `THEN`
        `new_row` := `row_to_json`(`NEW`)::`JSONB`;
    `END IF`;

    — Вставляем запись аудита
    `INSERT INTO audit_log` (
        `table_name`, operation, `old_values`, `new_values`,
        `user_id`, `session_id`, `client_ip`
    ) `VALUES` (
        TG_TABLE_NAME, TG_OP, `old_row`, `new_row`,
        `current_user_id()`,
        `current_setting`('app.`session_id`', `TRUE`),
        `inet_client_addr()`
    );

    `RETURN COALESCE`(`NEW`, `OLD`);
`END`;
$$ `LANGUAGE` plpgsql;

-- Применяем триггеры аудита
`CREATE TRIGGER audit_orders_trigger`
    `AFTER INSERT OR UPDATE OR DELETE ON` orders
    `FOR EACH ROW EXECUTE FUNCTION audit_trigger_function`();

`CREATE TRIGGER audit_customers_trigger`
    `AFTER INSERT OR UPDATE OR DELETE ON` customers
    `FOR EACH ROW EXECUTE FUNCTION audit_trigger_function`();

-- Функция для получения истории изменений
`CREATE OR REPLACE FUNCTION get_audit_history`(
    `p_table_name TEXT`,
    `p_record_id INTEGER`,
    `p_limit INTEGER DEFAULT 100`
)
`RETURNS TABLE` (
    operation `TEXT`,
    `old_values JSONB`,
    `new_values JSONB`,
    `user_id INTEGER`,
    `changed_at TIMESTAMP`
) `AS` $$
`BEGIN`
    `RETURN QUERY`
    `EXECUTE` format('
        `SELECT` operation, `old_values`, `new_values`, `user_id`, `changed_at`
        `FROM audit_log`
        `WHERE table_name` = $1
          `AND` (`old_values`->>''id'' = $2 `OR new_values`->>''id'' = $2)
        `ORDER BY changed_at DESC`
        `LIMIT` $3
    ')
    `USING p_table_name`, `p_record_id::TEXT`, `p_limit`;
`END`;
$$ `LANGUAGE` plpgsql `SECURITY DEFINER`;

```sql
-- Функция для проверки ссылочной целостности
`CREATE OR REPLACE FUNCTION validate_foreign_keys`()
`RETURNS TABLE` (
    `table_name TEXT`,
    `column_name TEXT`,
    `invalid_count BIGINT`
) `AS` $$
`DECLARE`
    `fk_record RECORD`;
    query `TEXT`;
`BEGIN`
    `FOR fk_record IN`
        `SELECT`
            tc.`table_name`,
            kcu.`column_name`,
            ccu.`table_name AS foreign_table_name`,
            ccu.`column_name AS foreign_column_name`
        `FROM information_schema`.`table_constraints AS` tc
        `JOIN information_schema`.`key_column_usage AS` kcu
          `ON` tc.`constraint_name` = kcu.`constraint_name`
        `JOIN information_schema`.`constraint_column_usage AS` ccu
          `ON` ccu.`constraint_name` = tc.`constraint_name`
        `WHERE constraint_type` = '`FOREIGN KEY`'
    `LOOP`
        query := format('
            `SELECT COUNT`(*) `FROM` %I t1
            `LEFT JOIN` %I t2 `ON` t1.%I = t2.%I
            `WHERE` t2.%I `IS NULL`',
            `fk_record`.`table_name`,
            `fk_record`.`foreign_table_name`,
            `fk_record`.`column_name`,
            `fk_record`.`foreign_column_name`,
            `fk_record`.`foreign_column_name`
        );

        `RETURN QUERY EXECUTE` query
        `USING fk_record`.`table_name`, `fk_record`.`column_name`;
    `END LOOP`;
`END`;
$$ `LANGUAGE` plpgsql;

-- Проверка ограничений `NOT NULL`
`CREATE OR REPLACE FUNCTION check_not_null_constraints`()
`RETURNS TABLE` (
    `table_name TEXT`,
    `column_name TEXT`,
    `null_count BIGINT`
) `AS` $$
`DECLARE`
    `col_record RECORD`;
    query `TEXT`;
`BEGIN`
    `FOR col_record IN`
        `SELECT table_name`, `column_name`
        `FROM information_schema`.columns
        `WHERE table_schema` = 'public'
          `AND is_nullable` = '`NO`'
          `AND column_name` != 'id'  — Обычно `ID` имеет `DEFAULT`
    `LOOP`
        query := format('`SELECT COUNT`() `FROM` %I `WHERE` %I `IS NULL`',
                       `col_record`.`table_name`, `col_record`.`column_name`);

        `RETURN QUERY EXECUTE` query
        `USING col_record`.`table_name`, `col_record`.`column_name`;
    `END LOOP`;
`END`;
$$ `LANGUAGE` plpgsql;

-- Комплексная проверка схемы
`CREATE OR REPLACE FUNCTION validate_database_schema`()
`RETURNS TABLE` (
    `check_type TEXT`,
    `table_name TEXT`,
    issue `TEXT`,
    severity `TEXT`
) `AS` $$
`DECLARE`
    `fk_result RECORD`;
    `nn_result RECORD`;
`BEGIN`
    — Проверка внешних ключей
    `FOR fk_result IN SELECT` * `FROM validate_foreign_keys`() `LOOP`
        `IF fk_result`.`invalid_count` > 0 `THEN`
            `RETURN QUERY SELECT`
                '`FOREIGN KEY`'::`TEXT`,
                `fk_result`.`table_name`,
                format('`Found` %s orphaned records in column %s',
                      `fk_result`.`invalid_count`, `fk_result`.`column_name`),
                '`ERROR`'::`TEXT`;
        `END IF`;
    `END LOOP`;

    — Проверка `NOT NULL` ограничений
    `FOR nn_result IN SELECT` * `FROM check_not_null_constraints`() `LOOP`
        `IF nn_result`.`null_count` > 0 `THEN`
            `RETURN QUERY SELECT`
                '`NOT NULL`'::`TEXT`,
                `nn_result`.`table_name`,
                format('`Found` %s `NULL` values in `NOT NULL` column %s',
                      `nn_result`.`null_count`, `nn_result`.`column_name`),
                '`WARNING`'::`TEXT`;
        `END IF`;
    `END LOOP`;

    — Проверка индексов на внешних ключах
    `FOR fk_result IN`
        `SELECT DISTINCT`
            ccu.`table_name`,
            ccu.`column_name`
        `FROM information_schema`.`table_constraints AS` tc
        `JOIN information_schema`.`constraint_column_usage AS` ccu
          `ON` ccu.`constraint_name` = tc.`constraint_name`
        `WHERE constraint_type` = '`FOREIGN KEY`'
    `LOOP`
        `IF NOT EXISTS` (
            `SELECT 1 FROM pg_indexes`
            `WHERE` tablename = `fk_result`.`table_name`
              `AND` (indexdef `LIKE` '%' || `fk_result`.`column_name` || '%')
        ) `THEN`
            `RETURN QUERY SELECT`
                '`INDEX`'::`TEXT`,
                `fk_result`.`table_name`,
                format('`Missing index on foreign` key column %s', `fk_result`.`column_name`),
                '`WARNING`'::`TEXT`;
        `END IF`;
    `END LOOP`;
`END`;
$$ `LANGUAGE` plpgsql;

-- Запуск валидации
`SELECT` * `FROM validate_database_schema`();
```text

```sql
-- Функция для генерации описания таблиц в формате `PlantUML`
`CREATE OR REPLACE FUNCTION generate_erd_plantuml`()
`RETURNS TEXT AS` $$
`DECLARE`
    result `TEXT` := '`@startuml ERD`\n';
    `table_record RECORD`;
    `column_record RECORD`;
    `fk_record RECORD`;
`BEGIN`
    — Генерируем классы для таблиц
    `FOR table_record IN`
        `SELECT table_name`
        `FROM information_schema`.tables
        `WHERE table_schema` = 'public' `AND table_type` = '`BASE TABLE`'
        `ORDER BY table_name`
    `LOOP`
        result := result || 'class ' || `table_record`.`table_name` || ' {\n';

        — Добавляем столбцы
        `FOR column_record IN`
            `SELECT column_name`, `data_type`, `is_nullable`,
                   `CASE WHEN column_default IS NOT NULL THEN` '`DEFAULT`' `ELSE` '' `END` as `has_default`
            `FROM information_schema`.columns
            `WHERE table_name` = `table_record`.`table_name AND table_schema` = 'public'
            `ORDER BY ordinal_position`
        `LOOP`
            result := result || '  ' || `column_record`.`column_name` || ': ' || `column_record`.`data_type`;
            `IF column_record`.`is_nullable` = '`NO`' `THEN`
                result := result || ' `NOT NULL`';
            `END IF`;
            `IF column_record`.`has_default` = '`DEFAULT`' `THEN`
                result := result || ' `DEFAULT`';
            `END IF`;
            result := result || '\n';
        `END LOOP`;

        result := result || '}\n\n';
    `END LOOP`;

    — Генерируем связи
    `FOR fk_record IN`
        `SELECT`
            tc.`table_name` as `child_table`,
            ccu.`table_name` as `parent_table`,
            kcu.`column_name` as `child_column`
        `FROM information_schema`.`table_constraints AS` tc
        `JOIN information_schema`.`key_column_usage AS` kcu
          `ON` tc.`constraint_name` = kcu.`constraint_name`
        `JOIN information_schema`.`constraint_column_usage AS` ccu
          `ON` ccu.`constraint_name` = tc.`constraint_name`
        `WHERE constraint_type` = '`FOREIGN KEY`'
        `ORDER BY` tc.`table_name`, kcu.`column_name`
    `LOOP`
        result := result || `fk_record`.`parent_table` || ' ||--o{ ' || `fk_record`.`child_table` ||
                  ' : ' || `fk_record`.`child_column` || '\n';
    `END LOOP`;

    result := result || '`@enduml`';

    `RETURN` result;
`END`;
$$ `LANGUAGE` plpgsql;

-- Генерация документации в формате `Markdown`
`CREATE OR REPLACE FUNCTION generate_schema_documentation`()
`RETURNS TEXT AS` $$
`DECLARE`
    result `TEXT` := '# `Database Schema Documentation`\n\n';
    `table_record RECORD`;
    `column_record RECORD`;
    `constraint_record RECORD`;
`BEGIN`
    result := result || '`Generated`: ' || CURRENT_TIMESTAMP || '\n\n';

    `FOR table_record IN`
        `SELECT table_name`, `table_comment`
        `FROM information_schema`.tables t
        `LEFT JOIN` (
            `SELECT` objoid::regclass::text as `table_name`, description as `table_comment`
            `FROM pg_description`
            `WHERE` objsubid = 0
        ) c `ON` t.`table_name` = c.`table_name`
        `WHERE` t.`table_schema` = 'public' `AND` t.`table_type` = '`BASE TABLE`'
        `ORDER BY` t.`table_name`
    `LOOP`
        result := result || '## `Table`: ' || `table_record`.`table_name` || '\n\n';

        `IF table_record`.`table_comment IS NOT NULL THEN`
            result := result || `table_record`.`table_comment` || '\n\n';
        `END IF`;

        — Столбцы
        result := result || '### `Columns`\n\n';
        result := result || '| `Column` | `Type` | `Nullable` | `Default` | `Description` |\n';
        result := result || '|--------|------|----------|---------|-------------|\n';

        `FOR column_record IN`
            `SELECT` c.`column_name`, c.`data_type`, c.`is_nullable`, c.`column_default`,
                   `d.description`
            `FROM information_schema`.columns c
            `LEFT JOIN pg_description` d `ON`
                `d.objoid` = (`table_record`.`table_name`)::regclass::oid
                `AND d.objsubid` = c.`ordinal_position`
            `WHERE` c.`table_name` = `table_record`.`table_name`
              `AND` c.`table_schema` = 'public'
            `ORDER BY` c.`ordinal_position`
        `LOOP`
            result := result || '| ' || `column_record`.`column_name` || ' | ' ||
                     `column_record`.`data_type` || ' | ' ||
                     `column_record`.`is_nullable` || ' | ' ||
                     `COALESCE`(`column_record`.`column_default`, '') || ' | ' ||
                     `COALESCE`(`column_record`.description, '') || ' |\n';
        `END LOOP`;

        result := result || '\n';

        — Ограничения
        result := result || '### `Constraints`\n\n';
        `FOR constraint_record IN`
            `SELECT` conname, contype, condef
            `FROM pg_constraint` c
            `WHERE` conrelid = (`table_record`.`table_name`)::regclass::oid
            `ORDER BY` conname
        `LOOP`
            result := result || '- ' || `constraint_record`.conname || ': ';

            `CASE constraint_record`.contype
                `WHEN` 'p' `THEN` result := result || '`PRIMARY KEY` ';
                `WHEN` 'f' `THEN` result := result || '`FOREIGN KEY` ';
                `WHEN` 'u' `THEN` result := result || '`UNIQUE` ';
                `WHEN` 'c' `THEN` result := result || '`CHECK` ';
                `ELSE` result := result || '`OTHER` ';
            `END CASE`;

            `IF constraint_record`.condef `IS NOT NULL THEN`
                result := result || `constraint_record`.condef;
            `END IF`;

            result := result || '\n';
        `END LOOP`;

        — Индексы
        result := result || '\n### `Indexes`\n\n';
        `FOR constraint_record IN`
            `SELECT` indexname, indexdef
            `FROM pg_indexes`
            `WHERE` tablename = `table_record`.`table_name`
              `AND` schemaname = 'public'
            `ORDER BY` indexname
        `LOOP`
            result := result || '- `' || `constraint_record`.indexname || '`: ' ||
                     `constraint_record`.indexdef || '\n';
        `END LOOP`;

        result := result || '\n---\n\n';
    `END LOOP`;

    `RETURN` result;
`END`;
$$ `LANGUAGE` plpgsql;

- Тестируйте схему - валидация данных и ограничений

### PostgreSQL-специфичные возможности:

- Наследование таблиц - для иерархических структур
- Массивы и JSONB - для гибких данных
- Generated columns - для вычисляемых полей
- Domains и Enum - для ограничения значений
- Table partitioning - для больших таблиц
- Row Level Security - для безопасности

### Производительность:

- Правильные индексы - B-tree, Hash, GiST, GIN, BRIN
- Партиционирование - для больших таблиц
- Оптимизация запросов - использование CTE, оконных функций
- Кэширование - materialized views, prepared statements
- Мониторинг - pg_stat_statements, pg_buffercache

### Безопасность:

- Row Level Security - ограничение доступа к строкам
- Аудит - отслеживание изменений
- Валидация данных - constraints и triggers
- Шифрование - pgcrypto для чувствительных данных

## Решение проблем

**Медленные запросы из-за отсутствия индексов:** анализируйте планы через `EXPLAIN (ANALYZE, BUFFERS)`, добавляйте индексы по предикатам `WHERE`, `ORDER BY`, `GROUP BY`. Избегайте лишних индексов — они замедляют вставки и обновления.

**Блокировки и дедлоки:** сокращайте время транзакций, придерживайтесь единого порядка блокировки таблиц в приложении. Используйте `SELECT ... FOR UPDATE SKIP LOCKED` для очередей. Анализ дедлоков — через логи и `pg_locks`/`pg_stat_activity`.

**Аномалии и дубликаты при денормализации:** храните версию или дату обновления денормализованных полей и обновляйте их в одной транзакции с основной таблицей. Используйте триггеры для синхронизации только при явной необходимости.

**Сложная миграция схемы:** делайте изменения по шагам (добавление колонок с default, заполнение, добавление ограничений), используйте downtime только там, где нужна блокировка. Инструменты: **pg_dump**/restore, **Flyway**, **Liquibase**.

Эффективное проектирование базы данных требует баланса между нормализацией, производительностью и удобством использования. PostgreSQL предоставляет богатый набор инструментов для создания надежных, эффективных и безопасных схем данных.
