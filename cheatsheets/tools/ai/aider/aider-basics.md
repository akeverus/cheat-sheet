# Aider: основы

Aider — это **CLI-инструмент**, который работает как pair programmer в терминале:

- вы общаетесь с моделью (GPT/Claude/другие) в консоли;
- Aider **редактирует файлы в репозитории**;
- изменения применяются через **git-патчи**, что упрощает ревью.

В отличие от IDE-ассистентов, Aider:

- не навязывает конкретный редактор;
- вписывается в консольный/`tmux`/`vim`-ориентированный рабочий процесс;
- хорошо подходит для работы с удалёнными окружениями и сервер-сайдом.

> Замечание: детали команд и флагов могут меняться; всегда сверяйтесь с актуальной документацией Aider.

## Введение

Главная идея Aider:

- **вы управляете** контекстом и командами;
- Aider отвечает за:
  - генерацию изменений;
  - формирование патчей;
  - минимальное изменение кода.

Типичные сценарии:

- рефакторинг в существующем репозитории;
- добавление небольшой фичи;
- генерация тестов;
- исправление багов по логам и трейсам.


## Установка и базовая настройка

Чаще всего Aider устанавливают через `pip` (подробности см. в официальной документации).

Общий подход:

- установить Aider (например, в виртуальное окружение);
- задать ключи API для моделей (OpenAI, Anthropic и т.п.);
- запустить Aider в корне git-репозитория.

Пример (условный):

```bash
pip install aider-chat

export OPENAI_API_KEY=...
# или другой провайдер

aider .
```

После запуска вы попадаете в интерактивную консоль Aider.


## Основной рабочий процесс

Типичный цикл:

1. Запустить Aider в корне репозитория.
2. Добавить файлы в контекст (через команды Aider).
3. Описывать задачи на естественном языке:
   - «Добавь логирование в этот сервис»;
   - «Перепиши эту функцию на более идиоматичный Go»;
   - «Сгенерируй тесты для этого файла».
4. Просматривать предложенные изменения (diff).
5. Принимать/отклонять изменения.

Важно:

- вы всегда видите **конкретные патчи**, а не «магически изменённый» код;
- можно легко откатить изменения через git, если что-то пошло не так.


## Пример типичной сессии

Разберём упрощённый, но показательный сценарий.

**Задача:** в сервисе `orders-service`:

- добавить логирование в `OrderService`;
- написать тесты для новой ветки логики;
- всё сделать через Aider в отдельной ветке.

### Шаг 1. Подготовка ветки

```bash
git checkout -b feature/order-logging
```

### Шаг 2. Запуск Aider

```bash
aider .
```

После запуска в интерактивной консоли:

1. Добавляем целевые файлы в контекст (примерная команда, см. актуальную доку Aider):

```text
/add src/orders/OrderService.java
/add src/orders/OrderServiceTest.java
```

2. Формулируем задачу:

```text
Нужно добавить structured-логирование в OrderService:
- логировать создание, обновление и отмену заказа;
- включать в логах orderId, userId и итоговый статус;
- использовать уже существующий логгер LoggerFactory из этого проекта;
- не менять сигнатуры публичных методов.

Сначала покажи план изменений, потом предложи патч.
```

3. Aider:

- строит план (список шагов: где добавить логи, какие методы затронуть);
- предлагает diff с изменениями в `OrderService.java`.

4. Мы просматриваем diff:

- убеждаемся, что:
  - формат логов согласован со стилем проекта;
  - не изменены бизнес‑правила;
  - не добавлены лишние зависимости.

5. Принимаем изменения командой Aider (подробности синтаксиса — в доке инструмента).

### Шаг 3. Генерация тестов

Дальше просим Aider:

```text
Теперь сгенерируй unit-тесты для новой логики логирования в OrderServiceTest:
- используй JUnit 5 и Mockito;
- проверь, что логгер вызывается с ожидаемыми параметрами;
- не ломай существующие тесты.
```

После генерации:

- просматриваем тесты;
- при необходимости просим Aider их упростить/переписать;
- запускаем `mvn test`/`gradle test` (уже вне Aider).

### Шаг 4. Завершение

Выходим из Aider и:

```bash
git status
git diff
git commit -am "Add structured logging to OrderService and tests"
```

Таким образом:

- Aider помогает с генерацией и правками;
- контроль над git‑историей и финальным качеством остаётся за разработчиком.


## Работа с git и патчами

Сильная сторона Aider:

- тесная интеграция с git:
  - понимает статус репозитория;
  - формирует патчи;
  - может работать с ветками.

Практический смысл:

- можно просматривать изменения как обычные git-диффы;
- удобно делать **маленькие коммиты**:
 - один запрос один коммит (или несколько логических пачек);
- легко откатывать неудачные правки.

Рекомендации:

- работать в отдельной ветке;
- коммитить небольшими порциями;
- не смешивать в одном запросе много разнотипных изменений.


## Примеры промптов

### Рефакторинг

```text
Посмотри на класс PaymentService и:
- опиши, какие у него обязанности сейчас;
- предложи план рефакторинга, чтобы:
  - разделить работу с внешним API и бизнес-правила;
  - упростить тестирование;
- не меняй публичный API сервиса.

После плана предложи патч только для выделенного метода processPayment.
```

```text
Перепиши этот метод в более идиоматичном стиле для Go:
- избегай глобальных переменных;
- используй контекст ctx для таймаутов;
- обработку ошибок сделай более явной.
```

### Тесты

```text
Сгенерируй unit-тесты для метода calculateDiscount:
- язык: Kotlin, JUnit 5;
- покрыть сценарии:
  - без скидки;
  - максимальная скидка;
  - некорректные входные данные (ожидаемое исключение);
- стиль тестов как в существующем классе DiscountServiceTest.
```

### Миграции и правки по проекту

```text
Нужно перевести все устаревшие вызовы RestTemplate на WebClient в модуле payments.

Сделай:
- найди все места использования RestTemplate в каталоге src/payments;
- предложи план миграции;
- покажи патч только для одного файла PaymentClient как примера;
- не меняй публичные контракты сервисов.
```


## Подключение разных моделей

Aider может работать с разными провайдерами LLM (точный список см. в официальной документации):

- OpenAI (GPT‑модели);
- Anthropic (Claude);
- другие совместимые модели.

Типовой подход:

- задать переменные окружения:

```bash
export OPENAI_API_KEY=...
export ANTHROPIC_API_KEY=...
```

- указать в конфигурации Aider, какую модель использовать по умолчанию и для каких задач:
  - более дешёвую/быструю — для черновой генерации;
  - более дорогую/мощную — для сложного анализа/рефакторинга.


## Типичные ошибки и грабли

- Давать Aider слишком размытую задачу:
  - «сделай код лучше» вместо конкретного запроса.
- Одним промптом пытаться изменить слишком много файлов:
  - сложнее ревьюить;
  - выше риск поломок.
- Не смотреть diff внимательно:
  - особенно в местах с бизнес‑логикой и безопасностью.
- Смешивать в одном запросе:
  - рефакторинг;
  - добавление фичи;
  - правки формата/стиля.

Лучший подход:

- один запрос одна логическая задача;
- отдельные запросы для:
  - рефакторинга;
  - тестов;
  - документации.


## Лучшие практики

- Формулировать задачи чётко и по шагам:
  - сначала объяснить цель;
  - затем попросить план;
  - потом — реализацию по шагам.
- Явно перечислять файлы, которые можно менять.
- Следить за размером патчей:
  - чем меньше, тем легче ревью и откат;
- использовать Aider как **инструмент для ускорения**, а не как единственный источник архитектурных решений.


## Частые вопросы

**Q: Можно ли использовать Aider без интернет‑доступа?**
A: Основные функции Aider зависят от облачных моделей. Если использовать только локальные модели (если это поддерживается версией), возможна частичная работа, но в целом рассчитывайте на необходимость доступа к LLM‑провайдерам.

**Q: Чем Aider отличается от IDE‑ассистента?**
A: Aider:
- работает в терминале и не зависит от конкретной IDE;
- глубоко завязан на git‑поток и патчи;
- удобен для headless/SSH‑окружений и тех, кто живёт в vim/tmux.

**Q: Насколько безопасно запускать Aider на продакшен‑репозиториях?**
A: Безопасность зависит от:
- выбранных моделей (куда уходит код);
- внутренней политики компании;
- того, какие файлы вы добавляете в контекст.

Рекомендуется:
- не отправлять секреты и чувствительные данные;
- работать в отдельных ветках;
- не коммитить изменения без ревью.


## Чек-листы

### Перед первой работой с Aider в репозитории

- [ ] Репозиторий привязан к git и чистый (`git status` без незакоммиченных мусорных правок).
- [ ] Есть отдельная ветка для экспериментов.
- [ ] Настроены ключи API для моделей.
- [ ] Понимаю, какие части кода можно показывать AI с точки зрения политики компании.

### Для каждой сессии

- [ ] Сформулирована конкретная цель.
- [ ] Добавлены только нужные файлы в контекст.
- [ ] Изменения просматриваются в diff перед коммитом.
- [ ] Коммиты разбиты на логические части.
