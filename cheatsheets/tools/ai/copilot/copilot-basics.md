# GitHub Copilot: основы

GitHub Copilot — это AI-ассистент разработки от GitHub, который встраивается прямо в IDE и помогает писать, объяснять и рефакторить код. Он использует данные из открытых файлов, репозитория и дополнительных инструкций, чтобы выдавать релевантные подсказки.

**Цель этого документа** — показать, как настроить Copilot и как использовать его в повседневной работе так, чтобы он реально ускорял разработку, а не мешал.

## Введение

Copilot помогает:

- генерировать код по комментариям и коротким подсказкам;
- дописывать повторяющиеся паттерны (циклы, маппинги, boilerplate);
- объяснять существующий код и предлагать альтернативы;
- создавать юнит-тесты и базовую документацию.

При этом:

- Copilot **не знает требований вашего бизнеса** — он опирается на паттерны, найденные в коде и обучающих данных;
- результат всегда нужно **перепроверять**;
- особенно важно контролировать **безопасность, перформанс и корректность алгоритмов**.


## Установка и активация

### Требования

Для использования Copilot вам понадобится:

- аккаунт GitHub с активной подпиской на Copilot;
- поддерживаемая IDE:
  - VS Code (рекомендуемая версия — актуальная stable);
  - JetBrains IDE (IntelliJ IDEA, WebStorm, PyCharm и т.п.);
  - Visual Studio (для .NET);
- доступ в интернет к серверам GitHub.

### Установка в VS Code

1. Откройте VS Code.
2. Перейдите в раздел Extensions.
3. Найдите `GitHub Copilot` и `GitHub Copilot Chat`.
4. Установите оба расширения.
5. После установки перезапустите редактор.

При первом использовании:

- VS Code предложит войти в GitHub-аккаунт;
- откроется окно браузера с подтверждением прав;
- после успешной авторизации Copilot станет доступен в статус-баре и в боковой панели.

### Установка в JetBrains IDE

1. Откройте `Settings` `Plugins`.
2. Найдите `GitHub Copilot` и установите плагин.
3. Перезапустите IDE.
4. При необходимости авторизуйтесь в GitHub внутри IDE.

### Авторизация GitHub и лицензия

Copilot работает только при наличии:

- **активной подписки пользователя** (личная лицензия);
- или **лицензии через организацию** (Copilot for Business/Enterprise).

Убедитесь, что:

- вы вошли в правильный GitHub-аккаунт (особенно, если у вас несколько);
- ваша организация разрешает использование Copilot для репозиториев компании.


## Основные режимы работы

### Inline suggestions (автодополнение)

Это самый базовый и часто используемый режим Copilot.

- Вы начинаете писать код или комментарий.
- Copilot предлагает продолжение (сероватый текст).
- Принять предложение:
  - `Tab` (VS Code/JetBrains по умолчанию);
  - или соответствующая комбинация, если вы её переназначили.
- Отклонить:
  - продолжить печатать;
  - или нажать `Esc`.

Практические советы:

- сначала **опишите цель в комментарии** (на английском или русском, но английский обычно даёт лучший результат);
- не принимайте огромные вставки «как есть» — просматривайте их и редактируйте;
- для сложных задач лучше использовать Copilot Chat, а не надеяться на одно автодополнение.

### Copilot Chat в IDE

Copilot Chat — отдельная панель/вкладка, где можно:

- задавать вопросы о коде;
- просить рефакторинг;
- генерировать тесты;
- объяснять ошибки.

Особенности:

- Chat автоматически подхватывает контекст:
  - активный файл;
  - выделенный фрагмент;
  - иногда — структуру репозитория.
- Можно **упоминать контекст** через `@`:
  - `@workspace` — весь рабочий каталог;
  - `@file` — текущий файл;
  - специальные участники/эксперты (в зависимости от IDE).

Примеры запросов:

- `Объясни, что делает эта функция и какие у неё граничные случаи.`
- `Перепиши этот фрагмент кода в более функциональном стиле, избегая мутабельности.`
- `Сгенерируй тесты для метода validatePayment с использованием JUnit5 и Mockito.`

### Copilot Spaces

Copilot Spaces — это **контекстные рабочие области**, которые позволяют:

- собрать вместе релевантный контекст (репозитории, файлы, документацию);
- вести диалог с Copilot в рамках конкретной задачи/темы;
- переиспользовать одно и то же пространство для длительных инициатив.

Особенности (по документации GitHub):

- Spaces можно создавать в веб-интерфейсе GitHub или интегрировать с IDE;
- IDE получает доступ к этим пространствам через GitHub MCP-сервер и специальные настройки;
- контекст в Space обновляется по мере развития проекта.

Идея:

- вместо того чтобы каждый раз объяснять Copilot весь проект, вы создаёте Space с:
  - ключевыми файлами;
  - описанием архитектуры;
  - ADR и RFC по данной задаче;
  - ссылками на тикеты/эпики.

### Copilot CLI (кратко)

Copilot CLI (отдельный продукт/режим) позволяет:

- взаимодействовать с Copilot из терминала;
- генерировать команды, скрипты, Dockerfile и т.п.

Базовая идея:

- вы описываете задачу текстом;
- Copilot предлагает одну или несколько команд;
- вы просматриваете и вручную запускаете то, что считаете корректным.


## Работа с контекстом

### Какие данные Copilot использует как контекст

Copilot может учитывать:

- содержимое **открытого файла**;
- другие файлы в том же проекте/репозитории;
- историю правок в текущей сессии;
- настройки репозитория и `.github/copilot-instructions.md`.

Чем лучше структурирован ваш проект:

- понятные имена файлов и директорий;
- единый кодстайл;
- наличие документации;

тем проще Copilot ориентироваться и выдавать адекватные предложения.

### Использование `.github/copilot-instructions.md`

Этот файл позволяет задать **кастомные инструкции для Copilot** на уровне репозитория.

Пример минимального содержания:

```markdown
# GitHub Copilot Instructions

## Project context

- This is a backend service written in Kotlin using Spring Boot.
- We use hexagonal architecture and DDD terminology.

## Coding guidelines

- Prefer Kotlin coroutines over blocking calls.
- All public REST APIs must be documented in OpenAPI.
- Use our Result type for error handling instead of throwing exceptions.
```

Рекомендации:

- описывайте **архитектуру, ограничения и code style**;
- добавляйте примеры «хорошего» кода (short snippets);
- не дублируйте общедоступные вещи (например, базовый синтаксис языка) — фокус на специфике проекта.

### Режимы приватности и ограничения

Copilot может работать:

- с **публичными репозиториями**;
- с **приватными репозиториями** (при наличии доступа и настроек организации).

Проверьте политику компании:

- какие репозитории можно подключать к Copilot;
- можно ли отправлять в Copilot код с платной/закрытой логикой;
- разрешено ли использовать Copilot для кода, содержащего персональные данные.


## Типовые сценарии использования

### Написание нового кода

1. Описать свою цель в комментарии:
   - `// Implement a function that validates JWT tokens and returns user roles.`
2. Начать писать сигнатуру функции.
3. Принять или скорректировать предложенное автодополнение.
4. Попросить Copilot Chat:

```text
Посмотри на эту функцию и предложи улучшения по безопасности и обработке ошибок.
Учти, что библиотека X уже используется в проекте.
```

### Рефакторинг и объяснение кода

1. Выделить участок кода.
2. Открыть Copilot Chat и задать вопрос:

```text
Объясни, что делает этот код, какие у него недостатки и как можно упростить без изменения поведения.
```

3. Попросить вариант рефакторинга:

```text
Предложи переписать этот код в более читаемом виде, но:
- не меняй публичный API класса;
- не добавляй новые зависимости;
- сохрани существующий контракт по ошибкам.
```

### Генерация тестов

1. Открыть файл с целевым кодом.
2. Создать или открыть тестовый файл рядом.
3. Попросить Copilot Chat:

```text
Сгенерируй unit-тесты для метода processOrder в стиле существующих тестов в этом файле.
Покрой следующие случаи:
- валидный заказ;
- недостаточно средств;
- ошибка внешнего сервиса.
```

4. Проверить:
   - читабельность тестов;
   - соответствие naming-конвенциям;
   - отсутствие «магических» значений, не привязанных к бизнес-логике.

### Работа с документацией

Copilot может:

- помогать писать README и ADR;
- предлагать краткие описания модулей;
- формировать bullet-поинты из свободного текста.

Пример запроса:

```text
Сформируй краткое описание модуля payments для README:
- что он делает;
- какие внешние системы использует;
- какие есть ограничения и важные особенности.
```


## Настройка Copilot в VS Code

### Ключевые параметры настроек

В VS Code (Settings Extensions GitHub Copilot) можно настроить:

- **Включение/выключение** Copilot по умолчанию;
- **Показывать ли предложения автоматически**, или только по запросу;
- Максимальную длину подсказок;
- Поведение при работе с определёнными языками/файлами.

Практические советы:

- отключить Copilot для файлов, где он мешает (например, больших JSON/логов);
- включить для основных рабочих языков (Java, Kotlin, Go, TypeScript и т.д.);
- при желании ограничить автодополнение только по горячей клавише.

### Горячие клавиши

По умолчанию (может отличаться в зависимости от IDE):

- Принять предложение: `Tab`.
- Показать следующие варианты (если есть несколько подсказок): `Alt+]` / `Alt+[`.
- Открыть Copilot Chat:
  - иконка в боковой панели;
  - или комбинация из настроек (например, `Ctrl+Alt+Shift+C`).

Проверьте:

- чтобы горячие клавиши не конфликтовали с уже используемыми в проекте сочетаниями;
- чтобы доступ к чату и переключению предложений был удобен под вашу раскладку клавиатуры.


## Лучшие практики

- Использовать Copilot как **ускоритель**, а не как источник финальной истины.
- Формулировать запросы в Chat **чётко и с контекстом**, а не «сделай красиво».
- Не позволять Copilot изменять архитектурные решения без явного контроля.
- Задавать ограничения:
  - «не менять публичный API»;
  - «не добавлять новые зависимости»;
  - «соблюдать существующий кодстайл».


## Распространённые ошибки и анти-паттерны

- Принимать длинные автодополнения **без чтения**.
- Генерировать код для критичных участков (безопасность, криптография) и не ревьюить его.
- Использовать Copilot для генерации SQL-запросов без дальнейшей оптимизации и анализа планов.
- Считать, что наличие тестов, сгенерированных Copilot, автоматически гарантирует качество.


## Частые вопросы

**Q: Может ли Copilot «унести» закрытый код в обучающие данные?**
A: GitHub документирует политику неиспользования приватного кода для обучения новых моделей. Но фактические гарантии и допустимость использования нужно проверять по политике вашей компании.

**Q: Copilot иногда пишет странный или устаревший код. Почему?**
A: Модели обучены на большом количестве кода разного качества и возраста. Поэтому важно самостоятельно фильтровать предложения и ориентироваться на текущие практики/версии библиотек.

**Q: Нужно ли писать промпты на английском?**
A: Copilot понимает и русский, и английский, но часто английский даёт более точные и богатые подсказки, особенно по названиям API и библиотек.


## Чек-листы

### Для включения Copilot в проект

- [ ] Проверены юридические и безопасностные ограничения использования Copilot.
- [ ] Настроен `.github/copilot-instructions.md` с базовой информацией о проекте.
- [ ] Определены сценарии, где Copilot **разрешён** (например, черновой код, тесты).
- [ ] Определены сценарии, где Copilot **запрещён** (криптография, секьюрити-критичные модули).

### Для использования Copilot в ежедневной работе

- [ ] Перед генерацией кода я описываю цель задачи (комментарием или в чате).
- [ ] Я просматриваю каждое предложение Copilot перед принятием.
- [ ] Я не полагаюсь на Copilot в вопросах архитектуры без обсуждения с командой.
- [ ] Я не вставляю в промпты секреты и чувствительные данные.

## Подробные примеры промптов

Ниже — примеры промптов для Copilot Chat, которые можно адаптировать под ваш проект.

### Пример 1. Объяснение сложного метода

```text
Объясни, что делает этот метод и какие есть edge-cases.
Сфокусируйся на:
- валидации входных данных;
- ветках обработки ошибок;
- возможных проблемах с производительностью.

В конце предложи 3–5 идей по улучшению читаемости, не меняя поведение.
```

### Пример 2. Генерация тестов с учётом стиля проекта

```text
Сгенерируй unit-тесты для метода processInvoice.

Контекст:
- проект на Java 21;
- используем JUnit 5 и AssertJ;
- моки через Mockito.

Покрой следующие сценарии:
- успешная обработка счета;
- ошибка валидации входных данных;
- таймаут внешнего сервиса.

Соблюдай стиль именования тестов как в существующем классе тестов.
```

### Пример 3. Предложение рефакторинга без изменения API

```text
Посмотри на этот класс и предложи рефакторинг:
- не меняй публичный API;
- не добавляй новых зависимостей;
- сохрани семантику логов и ошибок.

Сначала опиши план изменений списком, потом покажи пример переписанного кода.
```

### Пример 4. Быстрая сводка по изменениям

```text
Сделай краткое резюме изменений в текущем PR:
- какие модули затронуты;
- что изменилось в публичных API;
- какие потенциальные риски ты видишь.

Формат ответа:
- 3–5 bullet-поинтов с фактами;
- 3 потенциальных риска;
- 2–3 вопроса, которые стоит задать автору PR.
```


## Расширенный раздел: использование Copilot в командах

Чтобы Copilot приносил пользу всей команде, а не только отдельным разработчикам:

- договоритесь, **где и как** его использовать:
  - генерация чернового кода;
  - помощь в тестах;
  - подготовка документации;
  - объяснение legacy-модулей;
- определите, **что нельзя** поручать Copilot:
  - генерировать криптографические алгоритмы;
  - писать security-критичный код без ревью эксперта;
  - модифицировать юридически значимые документы.

Хорошая практика:

- оформить внутренний документ «Как мы используем Copilot»;
- привести примеры удачных и неудачных кейсов;
- зафиксировать ожидания:
  - «любой код от Copilot проходит то же ревью, что и код от человека»;
  - «Copilot не отменяет code review и тестирование».


## Расширенный раздел: безопасность и соответствие требованиям

При использовании Copilot в компаниях с жёсткими требованиями безопасности:

- проверьте официальную документацию GitHub по:
  - хранению и использованию данных;
  - политике обучения моделей;
  - логированию запросов;
- согласуйте использование Copilot с:
  - отделом безопасности;
  - юридическим отделом;
  - ответственными за комплаенс (GDPR, PCI DSS и др., если релевантно).

Рекомендации:

- не отправлять в Copilot:
  - реальные данные пользователей;
  - ключи, пароли, токены;
  - внутренние секретные алгоритмы;
- по возможности работать на анонимизированных/обезличенных данных;
- использовать GitHub Copilot for Business/Enterprise, если нужны дополнительные гарантии и управление политиками.


## Расширенный раздел: настройка `.github/copilot-instructions.md`

Хорошо оформленный файл инструкций задаёт тон ответов Copilot:

- описывает **доменные термины**;
- фиксирует **архитектурные решения**;
- указывает **предпочтительные библиотеки и подходы**.

Пример структуры:

```markdown
# Project context
- Short description of the system
- Main modules and their responsibilities

## Domain terminology
- Term1: short explanation
- Term2: short explanation

## Coding guidelines
- Language level and frameworks
- Error handling patterns
- Logging and observability

## Do and Don't
- Do: use Result type for errors
- Don't: throw raw exceptions from controller layer
```

Лучшие практики:

- держать файл **коротким и по существу**;
- обновлять его при изменении архитектуры;
- ссылаться из него на более подробные внутренние гайды.


## Расширенный раздел: интеграция Copilot с процессом ревью

Copilot может помочь:

- сформулировать описание PR;
- предложить список рисков;
- подсветить нетривиальные места.

Паттерн использования:

1. Перед созданием PR:
   - попросить Copilot сделать краткий summary изменений;
   - использовать этот текст как основу для описания PR.
2. Перед ревью чужого PR:

```text
Посмотри на изменения в этом PR и:
- опиши основные изменения простым языком;
- укажи возможные риски;
- предложи 3–5 вопросов автору.
```

3. После ревью:
   - не полагаться только на вывод Copilot;
   - использовать его как **вспомогательный инструмент**, а не замену человеческого анализа.

## Расширенный раздел: отладка «плохих» подсказок

Иногда Copilot:

- предлагает устаревший код;
- использует неподходящие библиотеки;
- игнорирует архитектурные ограничения.

Как реагировать:

- **не сердиться на инструмент** — воспринимать это как подсказку, а не как обязаловку;
- уточнить промпт:
  - «не используй библиотеку X, мы используем Y»;
  - «не добавляй глобальные синглтоны, у нас DI-контейнер».
- показать пример «правильного» кода:
  - «ориентируйся на стиль из @path/to/file».

Если подсказки систематически плохие:

- проверить `.github/copilot-instructions.md` — возможно, там нет контекста или он устарел;
- переиндексировать проект (перезапустить IDE, обновить расширения);
- убедиться, что в проекте нет большого количества legacy-примеров, которые сбивают Copilot.


## Расширенный раздел: Copilot и обучение разработчиков

Copilot может быть полезен:

- джунам — как источник примеров и объяснений;
- мидлам — как ускоритель рутинных задач;
- сеньорам — как инструмент для быстрых черновиков и проверки идей.

Но важно:

- не заменять Copilot полноценное обучение основам языка и архитектуры;
- использовать его как **интерактивный учебник**, задавая вопросы:
  - «объясни, как работает эта конструкция»;
  - «покажи разницу между подходами А и Б»;
- поощрять разработчиков **критически оценивать** ответы.


## Дополнительные вопросы и ответы

**Q: Можно ли настроить Copilot так, чтобы он не предлагал код в определённых файлах?**
A: Да, в настройках IDE можно отключить Copilot для отдельных языков или использовать ignore-правила. В VS Code можно настроить это через settings.json.

**Q: Copilot генерирует код с лицензиями, несовместимыми с нашим проектом.**
A: Современные версии Copilot стремятся избегать этого, но на 100% исключить нельзя. Для проектов с жёсткими лицензионными требованиями важно проводить дополнительную проверку и, при необходимости, отключать Copilot для таких модулей.

**Q: Можно ли использовать Copilot офлайн?**
A: Нет, Copilot требует подключения к серверам GitHub для работы моделей. Без интернета он не сможет генерировать подсказки и ответы в чате.


## Итоги

GitHub Copilot — инструмент, который:

- ускоряет повседневную разработку;
- помогает разбираться в чужом и legacy-коде;
- снижает порог входа в новые технологии.

Но:

- он не заменяет архитектурное мышление и опыт команды;
- его предложения нужно проверять и адаптировать;
- важно правильно настроить инструкции и политики использования.

Используйте Copilot как **сильного, но всё же виртуального напарника**, а не как автогенератор, которому доверено всё.
