# Cursor: основы

Cursor — это **AI-first IDE**, форк VS Code с глубокой интеграцией моделей искусственного интеллекта. Он объединяет классический редактор, чат с моделью, интеллектуальные правки кода и автономных агентов, которые могут изменять несколько файлов и вызывать команды.

**Цель этого документа** — дать практическое, человекочитаемое руководство по использованию Cursor в реальной разработке: от первого запуска до настройки правил проекта и безопасного использования агентов.

## Введение

Cursor фокусируется не на том, чтобы «просто встроить чат в IDE», а на том, чтобы **перенастроить весь процесс разработки под работу в паре с AI**:

- большая часть изменений в коде делается через **описания задач на естественном языке**;
- IDE умеет **сама находить и редактировать связанные файлы**, а не только текущий буфер;
- есть **агентный режим**, который может выполнять последовательность шагов: читать код, править несколько файлов, запускать команды;
- все это максимально интегрировано с привычным UI VS Code.

Важно понимать: Cursor **не заменяет понимание кода разработчиком**. Он:

- ускоряет рутинные задачи;
- помогает держать в голове большие коды и контексты;
- снижает порог входа в новые репозитории.

Но **ответственность за архитектуру, качество и безопасность** остаётся на человеке.


## Установка и первый запуск

### Поддерживаемые платформы

На момент 2026 года Cursor официально поддерживает:

- **macOS** (активно развивается, есть поддержка Apple Silicon);
- **Windows 10+**;
- **Linux** (Ubuntu и совместимые дистрибутивы).

### Установка

1. Перейти на `https://cursor.com/` и скачать установщик под свою платформу.
2. Установить как обычное приложение (drag-and-drop в `Applications` на macOS или стандартный инсталлятор на Windows).
3. При первом запуске IDE предложит:
   - импортировать настройки из VS Code (темы, шрифты, плагины, keybindings);
   - войти в аккаунт или создать новый.

Рекомендуется импортировать только то, что действительно нужно:

- тему оформления и шрифты;
- основные расширения (GitLens, Docker и т.д.);
- ключевые сочетания клавиш.

### Первый запуск и авторизация

- При старте Cursor попросит авторизоваться (через GitHub / Google / email).
- После авторизации IDE подтянет доступные модели и включит AI-функции.
- Важно убедиться, что:
  - рабочий каталог находится в **git-репозитории** (так контекст богаче);
  - нет лишних огромных директорий в корне (build-артефакты, кэш), которые будут мешать индексированию.


## Основные режимы работы

### Tab Completion (автодополнение кода)

Cursor расширяет классическое автодополнение до **многострочных, контекстно-зависимых подсказок**:

- учитывается содержимое **текущего файла**, открытых вкладок и иногда связанных модулей;
- подсказки могут включать **целые функции, классы, тесты**;
- качество сильно зависит от того, насколько хорошо IDE понимает текущую задачу.

Рекомендации:

- перед тем как начать писать новый код, **объясните в комментарии**, что вы хотите сделать — это часто улучшает подсказки;
- используйте автодополнение не как «замену головы», а как быстрый способ получить черновик, который вы потом доработаете.

### Inline Edit / Cmd+K

Inline Edit — это режим трансформации **выделенного фрагмента кода** по текстовому описанию.

Обычно это:

- на macOS: `Cmd+K`;
- на Windows/Linux: аналогичное сочетание (смотрите настройки keybindings в Cursor).

Типичные запросы:

- «Сделай эту функцию чистой и без побочных эффектов»;
- «Добавь логирование на уровне debug с контекстом requestId»;
- «Перепиши на async/await»;
- «Заменить ручную валидацию на библиотеку XYZ».

Поведение:

- Cursor строит diff для выделенного блока;
- предлагает предварительный просмотр изменений;
- вы можете **принять, отклонить или частично отредактировать** предложенный вариант.

### Chat-панель

Chat-панель — это привычный чат с моделью, но сильно завязанный на контекст IDE:

- вы можете **ссылаться на файлы и их фрагменты**;
- можно просить «найти все места, где...», «объяснить, как работает...», «предложить рефакторинг...».

Примеры запросов:

- `Объясни, что делает функция processOrder в @modules/orders/src/order-service.ts`;
- `Найди все места, где используется интерфейс PaymentProvider, и предложи общий адаптер`;
- `Подскажи, как покрыть тестами пограничные случаи для метода validateToken`.

Важно:

- чем более **конкретен** запрос и чем лучше вы указываете контекст (`@файлы`, строки, функции), тем полезнее ответы;
- чат не «всевидящий» — он работает с тем, что вы ему явно показали и что входит в допустимый объём контекста.

### Agent Mode / Cmd+I

Agent Mode — это режим, в котором Cursor может:

- сам искать нужные файлы;
- строить план изменений;
- модифицировать несколько файлов подряд;
- иногда запускать команды (в зависимости от конфигурации).

Используйте его для задач вида:

- «Добавь фичу X во всём сервисе Y»;
- «Мигрируй HTTP-клиент на новую библиотеку»;
- «Вынеси дублирующийся код в общий модуль».

Рекомендуемый паттерн работы:

1. В запросе к агенту **опишите цель и ограничения**:
   - что именно нужно сделать;
   - где нельзя трогать код;
   - какие стили и паттерны нужно соблюдать.
2. Попросите агента **сначала показать план**, затем одобрите или откорректируйте его.
3. Следите за тем, какие файлы агент редактирует, и ревьюйте итоговый diff.

### Background Agent

Background Agent — облачный агент, который может:

- работать дольше, чем одна сессия IDE;
- выполнять объёмные задачи (поиск по проекту, генерация отчётов, анализ архитектуры).

Используйте его, когда:

- локальный контекст слишком мал;
- требуется **продолжительный анализ** большого репозитория;
- вы готовы подождать и получить результат позже.


## Работа с контекстом

### Открытые файлы и выделение

Базовый уровень контекста для Cursor:

- активный файл;
- соседние открытые вкладки;
- явно выделенный код.

Практические рекомендации:

- перед запросом к чат/агенту **откройте ключевые файлы**, которые должны попасть в контекст;
- при объяснении бага выделите **конкретный фрагмент**, а не весь файл целиком;
- если задача затрагивает несколько модулей, дайте короткое текстовое резюме в начале промпта.

### Упоминание файлов и директорий через @

Cursor поддерживает ссылки на файлы и директории в духе:

- `@src/services/payment/PaymentService.ts`;
- `@modules/orders/`;
- `@README.md`.

Внутри запроса это означает:

- «обрати внимание на содержимое этого файла/директории»;
- модель сможет цитировать и анализировать именно эти ресурсы.

Лучшие практики:

- всегда явно указывайте ключевые файлы: `Посмотри @X и @Y и предложи...`;
- для больших директорий лучше давать **частями**, а не целиком (`@modules/orders/api`, а не весь `@modules`).

### Репозиторий и git-контекст

Cursor может использовать:

- историю коммитов;
- текущие изменения (staged/unstaged);
- состояние веток.

Полезные сценарии:

- «Объясни изменения в этом PR» (когда вы работаете над ревью);
- «Сгенерируй осмысленный commit message для текущих изменений»;
- «Составь changelog по последним N коммитам».


## Правила проекта и инструкции

### `.cursorrules` и `.cursor/rules/`

Cursor поддерживает **правила проекта**, которые помогают:

- задать **тон и стиль** ответов;
- зафиксировать **архитектурные ограничения**;
- описать **кодстайл** и форматы.

Часто используются два уровня:

- файл `.cursorrules` в корне репозитория с общими инструкциями;
- папка `.cursor/rules/` с более детальными правилами (по каталогам, языкам, модулям).

Примеры вещей, которые стоит туда вынести:

- «Проект на Kotlin, используем Coroutines вместо RxJava»;
- «REST API документируем через OpenAPI, не придумывать собственные форматы»;
- «Все SQL-запросы должны быть параметризованными, без конкатенации строк».

### Правила для конкретных файлов и директорий

Вы можете задавать правила **на уровень поддиректории**:

- отдельные инструкции для `backend/` и `frontend/`;
- ограничения для `infra/` (Terraform, Ansible);
- особые требования к `security/`-модулям.

Паттерн:

- для каждой крупной области создать собственный rules-файл;
- в нём описать:
  - цель модуля;
  - важные инварианты;
  - запрещённые анти-паттерны;
  - примеры «хороших» решений.

### Примеры полезных правил

- «Не генерировать огромные файлы, а при необходимости предлагать декомпозицию на модули».
- «Для новых эндпоинтов API обязательно писать тесты и обновлять OpenAPI-схему».
- «Все логи проходят через общий логгер, прямой `System.out.println` запрещён».


## Типовые сценарии использования

### Рефакторинг функции / класса

1. Откройте файл с целевым кодом.
2. Выделите функцию или класс.
3. Вызовите `Cmd+K` (Inline Edit) и опишите цель:
   - «Разбей на более мелкие функции, чтобы каждая отвечала за одну задачу»;
   - «Убери дублирование с методом X»;
   - «Сделай код чище и читабельнее, не меняя поведение».
4. Просмотрите diff. Обратите внимание:
   - не нарушены ли бизнес-правила;
   - не появились ли скрытые изменения (например, изменение логики ошибок).

### Добавление новой фичи по описанию

1. В текстовом файле (например, `feature-notes.md`) кратко опишите задачу:
   - цель;
   - сценарии использования;
   - ограничения.
2. В чат Cursor:
   - «Вот описание фичи в @docs/feature-notes.md. Предложи план изменений и файлы, которые нужно затронуть».
3. После получения плана:
   - скорректируйте его;
   - попросите агента по шагам реализовать каждую часть.

### Написание и улучшение тестов

1. Откройте файл с тестируемым кодом.
2. Сформулируйте в чате:
   - «Сгенерируй unit-тесты для функции X на JUnit5/pytest, покрывая edge-cases: A, B, C».
3. Попросите:
   - использовать уже существующие test-утилиты;
   - не ломать текущую структуру каталогов тестов.

### Объяснение legacy-кода

1. Откройте несколько ключевых файлов legacy-модуля.
2. В запросе:
   - «Объясни общую архитектуру модуля @modules/legacy-orders/ и как через него проходит заказ».
3. Попросите вывести:
   - краткий обзор;
   - список основных сущностей и их связи;
   - места для потенциального рефакторинга.

### Подготовка кода к ревью

1. После локальных изменений:
   - «Посмотри текущие изменения в репозитории и сформулируй краткое описание (PR description)».
2. Дополнительно:
   - «Подскажи, какие части могут вызвать вопросы у ревьюера и что лучше пояснить в комментариях к PR».


## Агенты и автоматизация

### Когда использовать Agent Mode

Используйте Agent Mode для:

- задач, затрагивающих **много файлов**;
- миграций и больших рефакторингов;
- создания инфраструктурного кода (конфиги, CI, Helm-чарты).

Не стоит запускать агента:

- на незнакомом вам проекте без минимального понимания архитектуры;
- без чёткого запроса и ограничений;
- в ветке, где много незакоммиченных критичных изменений.

### Запросы к агенту с явным планом

Хороший запрос:

- описывает **конечную цель**;
- задаёт **ограничения**;
- просит сначала **показать план**, потом выполнять.

Пример:

```text
Нужно добавить метрики latency для всех HTTP-эндпоинтов в сервисе orders-service.

Ограничения:
- используем Micrometer и Prometheus, как в payments-service;
- не трогаем legacy-модуль legacy-api;
- не меняем формат логов.

Сначала предложи план шагов и список файлов, которые будешь трогать.
После моего подтверждения выполняй изменения по шагам, показывая diff.
```

### Ограничения и контроль действий агента

- всегда следите за **списком файлов**, которые агент хочет изменить;
- не принимайте массовые изменения без просмотра хотя бы по выборке;
- для рискованных изменений:
  - создайте отдельную ветку;
  - ограничьте область (директория, модуль);
  - прогоните тесты и линтеры.


## CLI и продвинутая конфигурация

### Основные команды Cursor CLI

Cursor CLI позволяет:

- запускать IDE с определёнными параметрами;
- управлять моделями и MCP-серверами;
- иногда запускать headless-задачи.

Примеры (синтаксис может меняться, см. актуальную документацию):

```bash
cursor --help
cursor --project /path/to/project
cursor mcp list
cursor mcp add my-server --url http://localhost:8080
```

### Работа с MCP (Model Context Protocol)

MCP позволяет:

- подключать внешние сервисы как источники контекста;
- предоставлять инструменты (tools), которые модель может вызывать;
- организовывать более сложные сценарии (поиск по документации, работа с БД и т.д.).

Общие рекомендации:

- подключайте только те MCP-сервера, которые реально нужны;
- документируйте, **какие инструменты доступны**, чтобы команда понимала, что модель может делать;
- следите за безопасностью: не давайте модели полномочий, которые вы сами бы не дали junior-разработчику.


## Лучшие практики

- Формулировать запросы **как задачи для коллеги**, а не как магические заклинания.
- Явно указывать **ограничения** (архитектура, перформанс, безопасность).
- Сначала просить **план**, потом — реализацию.
- Не пытаться «загнать» в один запрос огромную задачу; делить работу на шаги.
- Сохранять и переиспользовать удачные промпты (в документации проекта или `.cursorrules`).


## Распространённые ошибки и анти-паттерны

- Давать Cursor полный контроль над проектом без ревью.
- Просить «сгенерировать целый сервис» без чёткого ТЗ.
- Игнорировать тесты и логику ошибок в сгенерированном коде.
- Считать, что успешный запуск — гарантия отсутствия багов.


## Частые вопросы

**Q: Заменит ли Cursor ревью со стороны человека?**
A: Нет. Он может подготовить код, подсказать улучшения, но финальное решение остаётся за командой.

**Q: Можно ли использовать Cursor без интернета?**
A: Основные AI-функции требуют доступа к облачным моделям. Без интернета Cursor работает как обычный редактор (форк VS Code).

**Q: Какие модели использует Cursor?**
A: Конкретный список зависит от настроек и тарифов, но обычно доступны современные GPT/Claude и другие модели. Подробности — в официальной документации.

## Подробные примеры промптов

Ниже — примеры промптов для типичных задач. Их можно копировать и адаптировать под свои проекты.

### Пример 1. Быстрое понимание модуля

```text
Контекст:
- работаю над сервисом orders-service;
- хочу понять, как проходит полный цикл обработки заказа.

Задача:
- посмотри файлы @modules/orders/src/order-service.ts,
  @modules/orders/src/order-controller.ts и связанные DTO;
- кратко опиши основной поток: от входящего HTTP-запроса до записи в БД;
- выдели ключевые точки валидации и бизнес-правил;
- укажи, где лучше всего ставить дополнительные метрики/логи.
```

### Пример 2. Миграция на новый HTTP-клиент

```text
Нужно мигрировать с RestTemplate на WebClient в модуле payments.

Ограничения:
- не трогаем пакеты legacy и экспериментальные фичи;
- новые вызовы должны поддерживать timeout и retry, как в сервисе billing;
- логирование ошибок через общий логгер LoggingUtils.

Сделай, пожалуйста:
1) Найди все места, где используется RestTemplate в @modules/payments.
2) Предложи план миграции.
3) Для начала перепиши только один класс с минимальными, но корректными изменениями.
4) Покажи diff и объясни ключевые места.
```

### Пример 3. Улучшение тестового покрытия

```text
Задача: улучшить покрытие тестами модуля discounts.

Контекст:
- основная логика в @modules/discounts/src/discount-service.ts;
- текущие юнит-тесты в @modules/discounts/test/discount-service.spec.ts.

Сделай:
1) Проанализируй существующие тесты и перечисли сценарии, которые уже покрыты.
2) Предложи дополнительные edge-cases (0, пограничные значения, некорректные данные).
3) Сгенерируй недостающие тесты в стиле существующих.
4) Объясни, почему каждый новый тест полезен.
```

### Пример 4. Помощь в ревью PR

```text
Я готовлю ревью для ветки feature/new-pricing.

Нужно:
1) Посмотри изменения между main и feature/new-pricing.
2) Составь краткое резюме изменений по модулям:
   - что изменилось в API;
   - что поменялось в бизнес-логике;
   - какие новые зависимости появились.
3) Предложи 5–7 вопросов, которые стоит задать автору PR.
4) Укажи потенциальные риски (перформанс, совместимость, безопасность).
```


## Расширенный раздел: безопасность и приватность

При работе с AI-инструментами, в том числе Cursor, важно учитывать:

- **куда уходит код** (какие сервера, какие провайдеры моделей);
- **что именно вы пересылаете** (секреты, персональные данные, внутренние алгоритмы);
- **какие политики компании действуют** (NDA, требования безопасности, отраслевые стандарты).

Рекомендации:

- хранить токены и ключи в безопасных хранилищах (не в коде, не в `.cursorrules`);
- не отправлять в промптах значения секретов (пароли, ключи, токены), только их имена и контракты;
- документировать в проекте, какие директории **нельзя** использовать в промптах (например, с конфиденциальными моделями ML);
- по возможности выбирать конфигурации, где данные обрабатываются с минимальными рисками (self-hosted, ограниченный набор провайдеров и т.п.).


## Расширенный раздел: интеграция Cursor в командный процесс

Чтобы Cursor не был «игрушкой одного энтузиаста», а стал частью общего процесса:

- договоритесь на уровне команды:
  - в каких задачах его использовать (рефакторинг, черновой код, тесты);
  - какие ограничения действуют (что нельзя поручать AI);
  - как оформлять результаты (PR-описания, комментарии).
- заведите в репозитории раздел документации про AI-инструменты:
  - как настроен Cursor под проект;
  - какие правила записаны в `.cursorrules`;
  - какие есть удачные промпты и сценарии;
  - как относиться к сгенерированному коду (например, «всегда ревьюит человек»).

Полезный паттерн:

- завести отдельный ADR или README вроде `docs/ai-tools-guidelines.md`;
- кратко описать:
  - цели использования AI;
  - anti-patterns («не используем AI для генерации юридических текстов», «не даём доступ к прод-данным»);
  - примеры «хорошего» использования.


## Расширенный раздел: отладка промптов (prompt engineering)

Чтобы Cursor давал более предсказуемые и полезные ответы:

- **контекст задача ограничения формат ответа**:
  - сначала кратко описать проект и модуль;
  - затем сформулировать цель;
  - указать строгие ограничения;
  - описать желаемый формат (список, таблица, код).
- избегать двусмысленности:
  - вместо «сделай лучше» — «уменьши количество вложенных if, сохрани поведение, добавь ранний выход, не меняй публичный API».
- использовать **few-shot**-подход:
  - показать пример «как надо»;
  - попросить повторить стиль или структуру.

Пример:

```text
Вот пример того, как в нашем проекте оформляются сервисы и интерфейсы:

@modules/example/src/good-service.ts

Сгенерируй новый сервис для модуля users в таком же стиле, с учётом:
- dependency injection через конструктор;
- именование методов в формате verbObject;
- логирование ошибок через ErrorLogger.
```


## Расширенный раздел: сравнение Cursor с другими AI-инструментами

Кратко о позиционировании:

- **GitHub Copilot**:
  - сильнее интегрирован с экосистемой GitHub;
  - фокус на автодополнении и чат-режиме;
  - хорошо подходит, если основной хостинг кода — GitHub.
- **Claude Code**:
  - сильный в длинном контексте и анализе больших файлов;
  - удобные диффы и план изменений;
  - может использоваться как отдельное расширение в VS Code/JetBrains.
- **Windsurf**:
  - отдельная IDE с упором на агентов и web-search;
  - тесная интеграция с Codeium.

Cursor, в свою очередь:

- даёт **глубокую интеграцию всего пайплайна разработки** (редактор, агенты, MCP, CLI);
- ориентирован на сценарий, когда **основной рабочий инструмент разработчика — именно Cursor**;
- хорошо подходит для проектов, где:
  - много кода и сложная архитектура;
  - важна скорость итераций;
  - команда готова стандартизировать использование AI.
