# Веб‑безопасность (`Web Security`)

## Основные классы атак

| Класс | Суть | Последствия |
|-------|------|-------------|
| **Инъекции** (`SQL`, `NoSQL`, `OS`, `LDAP`) | Вредоносный код через непроверенный ввод попадает в интерпретатор | Кража/модификация данных, полный доступ к системе |
| **`XSS`** (Cross‑Site Scripting) | Вредоносный `JavaScript` выполняется в браузере жертвы | Кража сессий, подмена интерфейса, действия от имени пользователя |
| **`CSRF`** (Cross‑Site Request Forgery) | Браузер залогиненного пользователя отправляет запрос без его ведома | Несанкционированные действия (перевод денег, смена email) |
| **Broken Authentication** | Самописный логин без защиты от перебора, вечные `remember-me` токены | Подбор учётных данных, угон сессий |
| **Broken Access Control** (`IDOR`) | Нет проверки прав — пользователь обращается к чужим ресурсам | Доступ к чужим данным через подмену `id` в `URL` |
| **Security Misconfiguration** | Дефолтные пароли, открытые порты, стектрейсы в ответах | Раскрытие внутренней структуры, помощь атакующему |
| **Data Exposure** | Лишние поля в ответах, нет `TLS`, слабые шифры | Утечка `PII`, перехват трафика |

## `XSS` (Cross‑Site Scripting)

Суть: злоумышленник добивается выполнения своего `JavaScript` в браузере жертвы через непроверенный пользовательский ввод.

### Три типа

- **Reflected** — вредоносный ввод сразу возвращается в ответе (через `GET`/`POST` параметры).
- **Stored** — данные сохраняются в БД и отдаются другим пользователям (комментарии, профили).
- **DOM‑based** — уязвимость только во фронтенд-коде (`innerHTML` и т.п.).

### Защита

- **Экранирование вывода** (`output encoding`) — для каждого контекста (`HTML`, `JS`, `URL`, атрибуты) свои методы.
- **Безопасные шаблонизаторы** — `Thymeleaf` (`th:text`), `React` (экранирует JSX по умолчанию). Избегать `th:utext`, `dangerouslySetInnerHTML`.
- **`CSP`** (`Content-Security-Policy`) — ограничивает источники скриптов и стилей, усложняет эксплуатацию `XSS`.
- На фронтенде — **запретить** `innerHTML` с непроверенным вводом, использовать безопасные API фреймворка.

### Серверный рендеринг

- Валидировать длину и формат пользовательских полей на входе.
- При выводе — `escapeHtml` или аналоги шаблонизатора.
- Для атрибутов `HTML` (`value`, `title`) — отдельные функции экранирования.

## `CSRF` (Cross‑Site Request Forgery)

Суть: браузер автоматически отправляет `cookie` с сессией → злоумышленник заставляет браузер жертвы отправить запрос к целевому сайту.

### Защита

- **`CSRF`-токены** для всех опасных запросов (`POST`, `PUT`, `DELETE`) при `cookie`-аутентификации.
- **`SameSite`** для `cookie` (`Lax` или `Strict`) — браузер не отправляет `cookie` при кросс-сайтовых запросах.
- Проверка `Origin`/`Referer` — дополнительная мера (не основная).
- `Authorization: Bearer` + правильный `CORS` вместо `cookie` снижает риск `CSRF`, но повышает важность защиты от `XSS`.

### Типовой паттерн для `cookie`-based приложений

1. Сервер генерирует `CSRF`-токен → скрытое поле формы или заголовок ответа.
2. При отправке формы — `cookie` + значение токена в теле или заголовке.
3. Сервер проверяет совпадение.
4. Без валидного токена — запрос отклоняется.

## `SQL Injection` и другие инъекции

Суть: непроверенный ввод попадает в команду интерпретатора (`SQL`, `shell`, `LDAP`, `NoSQL`).

### Защита

- **Только параметризованные запросы** — `PreparedStatement` в `JDBC`, параметры `ORM`. Конкатенация строк **запрещена**.
- **Валидация ввода** — типы, диапазоны, белые списки допустимых значений.
- **Минимальные права** учётной записи БД — без `DROP`, `ALTER`.

### При работе с `ORM`

- `JPQL`/`HQL` — именованные параметры (`:id`, `:name`).
- Имена таблиц/полей **не подставлять** из пользовательского ввода.
- Сортировка по полю — через **белый список** допустимых полей.

## Слабая аутентификация и авторизация

Типичные проблемы:

- Самописный логин без защиты от перебора.
- `Remember-me` токены без срока действия и возможности отзыва.
- Доступ к ресурсам по `URL` без проверки владельца (`IDOR`).
- Админка доступна любому аутентифицированному пользователю.

### Защита

- Использовать проверенные фреймворки (`Spring Security` и аналоги).
- Правила доступа — явно через механизмы фреймворка (`antMatchers`, `authorizeHttpRequests`).
- В каждом эндпоинте — сверять `userId` из токена с владельцем ресурса.
- Админка — отключить в проде или защитить дополнительной авторизацией + `VPN`/`IP`-фильтрация.

Подробнее — в [Application Security](application-security.md).

## Ошибки конфигурации и утечка данных

Что ведёт к утечкам:

- Стектрейсы в ответах → версии библиотек, структура БД, пути.
- Открытые `actuator`/`admin`/`debug` эндпоинты без авторизации.
- `Directory listing` на веб-сервере.
- Отключённый `TLS` или устаревшие шифры.
- Лишние поля в ответах `API` (`passwordHash`, `debugInfo`).

### Защита

- Продакшен-конфигурации — только необходимые модули. `debug`/`auto-config` — выключить.
- Разные профили для `dev` и `prod`.
- Фильтрация ответов `API` — клиент получает только нужные поля.
- `TLS` на всех соединениях, проверка сертификатов.
- Стандартные страницы ошибок без стектрейсов.
- Админка — по `IP`/`VPN`.
- Регулярное сканирование: `CIS`-бенчмарки, `SSL Labs`.

## Минимальный чек‑лист по веб‑безопасности

- [ ] Все входные данные валидируются по типу/формату/диапазону.
- [ ] Весь вывод, полученный от пользователя, экранируется перед вставкой в HTML/JS/`URL`.
- [ ] Для `cookie` установлены `HttpOnly`, `Secure`, `SameSite` (минимум `Lax`).
- [ ] Для опасных запросов с `cookie` включена защита `CSRF`.
- [ ] Для `API` не используется конкатенация строк в `SQL`/`shell`/`LDAP` запросах.
- [ ] Детальные стектрейсы и конфигурации не утекают в ответы.
- [ ] Админка и служебные эндпоинты защищены аутентификацией и авторизацией.

Дополнительно:

- [ ] Для основного домена настроен `Content-Security-Policy` и базовый набор security‑заголовков (`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`).
- [ ] `TLS` настроен с актуальными протоколами и шифрами, нет самоподписанных сертификатов в продакшене.
- [ ] Проведена базовая проверка по `OWASP Top 10` (ручная или через чек‑лист).

## Решение проблем

| Симптом | Причина | Решение |
|---------|---------|---------|
| Пользователь видит чужие данные | Нет проверки владельца ресурса или неправильный кэш | Проверка `userId` в каждом эндпоинте, ключ кэша с учётом пользователя |
| После логина запросы отклоняются как `CSRF` | Неправильная работа `CSRF`-токенов, конфликт `SameSite` | Проверить генерацию токена, настройки `SameSite`, `CORS` |
| Сканер находит `XSS` | Неэкранированный вывод пользовательских данных | Включить `output encoding`, запретить `innerHTML` с непроверенным вводом |
| Сканер находит `SQL Injection` | Конкатенация строк в запросах | Параметризованные запросы, белые списки для сортировки/фильтрации |
| «Сломанный» интерфейс после включения `CSP` | Слишком строгая политика блокирует легитимные ресурсы | Начать с `report-only`, постепенно ужесточать, добавлять нужные источники |
| Рост 401/403 после изменения безопасности | Ошибка в правилах авторизации или `CORS` | Анализ логов, сравнение старых/новых правил, временное ослабление с планом |
| Ошибки за обратным прокси | Неверная обработка `X-Forwarded-*`, смешение `HTTP`/`HTTPS` | Настроить доверенные прокси, корректное определение `scheme`/`host` |

## Практические сценарии веб‑безопасности

### Традиционное сервер‑рендер приложение

Шаблоны (`Thymeleaf`, `Freemarker`, `JSP`), сессии через `cookie`, минимум `JavaScript`.

**Основные угрозы:** `XSS` через плохо экранированные поля, `CSRF` для `POST`/`PUT`/`DELETE`, утечка сессионных `cookie`.

**Защита:**

- `th:text` / `@Html.Encode` по умолчанию. `th:utext` / `@Html.Raw` — **запретить** без обоснования.
- Флаги `HttpOnly`, `Secure`, `SameSite` (`Lax`/`Strict`) для всех сессионных `cookie`.
- Регенерация идентификатора сессии после логина.
- `CSRF`-токены во всех изменяющих запросах.

### SPA + backend API

Фронтенд на `React`/`Angular`/`Vue`, бэкенд — `REST`/`GraphQL`, данные в `JSON`.

**Основные угрозы:** `XSS` через `innerHTML`, `CSRF` при `cookie`-авторизации, проблемы с `CORS`.

**Защита:**

- Безопасные методы рендеринга фреймворка. `dangerouslySetInnerHTML` — **запретить**.
- `cookie`-авторизация → `SameSite` + `HttpOnly` + `Secure` + `CSRF`-защита.
- `Bearer`-авторизация → внимательно к месту хранения токена.
- `CORS` — только доверенные `origin`, не `*`.
- Вся валидация дублируется на бэкенде.

### Публичный маркетинговый сайт

Статический контент, формы подписки/контактов, `CDN`.

**Защита:**

- Строгая фильтрация пользовательского контента (комментарии, отзывы).
- Редиректы — только по белому списку доменов.
- `X-Frame-Options: DENY` или `SAMEORIGIN` на страницах входа.

### Внутренний админский интерфейс

Доступен сотрудникам / через `VPN`, широкие полномочия.

**Защита:**

- `MFA` для входа.
- Аудит всех критичных действий (кто, что, когда).
- Отдельный домен/поддомен + `VPN` или `IP`-фильтрация.

## Частые вопросы

**Достаточно ли `HTTPS` для безопасности?**
Нет. `HTTPS` защищает только канал (шифрование, подлинность сервера). Не защищает от `XSS`, `CSRF`, ошибок авторизации, утечек данных в ответах. Поверх `HTTPS` нужна валидация ввода, экранирование вывода, правильные `cookie`-флаги и контроль доступа.

**Что опаснее: `XSS` или `CSRF`?**
Оба опасны, но по‑разному. `XSS` даёт полный контроль над сессией: кража `cookie`, подмена интерфейса, запросы от имени жертвы. `CSRF` выполняет конкретное действие (перевод денег, смена email), используя существующую сессию. На практике `XSS` даёт более широкий контроль.

**Нужна ли `CSRF`-защита для `SPA`?**
Да, если авторизация через `cookie`. Если через `Bearer`-токен в `Authorization` — риск `CSRF` минимален, но возрастает важность защиты от `XSS` (токен могут украсть из `localStorage`).

**Какие поля нельзя отдавать клиенту?**
Всё, что не нужно для интерфейса: `passwordHash`, секретные ключи, внутренние заметки, технические `id`. Используйте `DTO` (`UserView`, `OrderView`) вместо прямой отдачи сущностей БД.

**Нужно ли включать `CSP`?**
Желательно для всех веб-приложений. Начать с `report-only`, собрать данные, поэтапно ужесточать. `CSP` значительно усложняет эксплуатацию `XSS`, ограничивая источники скриптов и стилей.

**Поможет ли `WAF` от `SQL Injection`/`XSS`?**
`WAF` смягчает атаки, но не заменяет защиту в коде. Сигнатуры не покрывают все векторы, настройка без ложных срабатываний сложна. Основа — параметризованные запросы, экранирование вывода, валидация ввода. `WAF` — дополнительный слой.

**Отчёты сканеров завалены подозрениями на `XSS`/инъекции?**
Выделить критичные находки, проверить вручную несколько примеров, скорректировать правила сканера (убавить шум), постепенно закрывать реальные уязвимости. Не игнорировать все отчёты целиком из-за шума.

**Как тестировать веб-безопасность локально?**
Минимум: ручной ввод `<script>alert('xss')</script>` в поля, подмена `id` в URL, сканирование через `Burp Suite`/`OWASP ZAP`, проверка обработки ошибок (нет ли стектрейсов).

**Можно ли доверять только фронтенд-валидации?**
Нет. Фронтенд-валидация — для удобства пользователя. Злоумышленник всегда может обойти фронтенд. Сервер обязан валидировать все данные повторно.

**Нужен ли `SameSite=None`?**
Только если `cookie` должно передаваться кросс-сайтово (`SSO`, `iframe`-интеграции). Иначе — `Lax` или `Strict` для снижения риска `CSRF`.
