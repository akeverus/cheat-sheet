## Модели аутентификации API

Три основных модели:

| Модель | Как работает | Когда использовать |
|--------|--------------|--------------------|
| `JWT` Bearer | Заголовок `Authorization: Bearer <token>`, содержит `claims` | Мобильные, `SPA`, сервис-сервис |
| `API Keys` | Ключ в заголовке или параметре | Внутренние сервисы, простые интеграции |
| `mTLS` | Клиентские сертификаты | Высокодоверенные внутренние взаимодействия |

Общие правила:

- Всегда `TLS` — секреты не передаются по незащищённому `HTTP`.
- `API Key` — с минимальными правами и возможностью отзыва.
- Токены и ключи **не логировать целиком** — маскировать.


## Авторизация и дизайн ресурсов

Самая частая проблема — `Broken Access Control` и `IDOR`. Наличие правильного `id` в `URL` **не равно** праву доступа.

Каждый запрос должен проверять:

1. **Кто пользователь** — `sub`/`userId` из токена.
2. **К какому ресурсу** — `/users/{id}`, `/accounts/{id}`.
3. **Какие операции разрешены** — по роли или политике.

Практические правила:

- Сверять владельца ресурса с `userId` из токена.
- Не принимать `userId` из тела запроса без сверки с токеном.
- Для админских операций — отдельные роли и отдельные `endpoint`-ы.


## Rate Limiting и защита от злоупотреблений

Две цели: защита от перебора (логины, `OTP`, `password reset`) и ограничение нагрузки от одного клиента.

### Алгоритмы

| Алгоритм | Суть | Особенность |
|----------|------|-------------|
| `Fixed window` | Фиксированные окна времени | Просто, но всплески на границах |
| `Sliding window` | Скользящее окно | Более плавное распределение |
| `Token bucket` | Токены выдаются с фиксированной скоростью | Допускает короткие всплески |

### Рекомендации

- Лимиты по `IP`, по пользователю или по `API Key` — в зависимости от сценария.
- Использовать готовые решения: `API Gateway`, `Envoy`, `Kong`, модули `NGINX`.
- Логировать все срабатывания лимитов и строить алерты.


## Валидация, схема и контракты

Для любого `API` (`REST`, `GraphQL`, `gRPC`) — описывать контракты: `OpenAPI`, `GraphQL schema`, `proto`.

Все входные данные проверять по размерам, форматам, диапазонам и обязательности **до** обработки.

**Анти-паттерны:**

- Принимать произвольный `JSON` и надеяться на валидацию в БД.
- Возвращать лишние поля (внутренние `id`, отладочную информацию).
- Один контракт для внешних и внутренних клиентов без фильтрации.


## Защита от типовых атак в API

**Инъекции** — только параметризованные запросы (`PreparedStatement`, параметры `ORM`). Конкатенация строк в `SQL`/`NoSQL`/`shell` запрещена.

**`XSS`** — `API` сам по себе редко уязвим (возвращает `JSON`, не `HTML`), но данные должны экранироваться на фронтенде. Подробнее — в `web-security.md`.

**`IDOR`** — всегда сверять владельца ресурса с `userId` из токена перед отдачей данных.

**Информация об ошибках** — не раскрывать стектрейсы, детали БД, имена серверов. Формат: `errorCode` + `message` + `traceId`.


## Практические сценарии и паттерны

### Публичный REST‑API для мобильного приложения

- `HTTPS` везде.
- `OAuth2`/`OIDC` с `Authorization Code` + `PKCE` или проверенный `Identity Provider`.
- `Access token` в `Authorization: Bearer ...`.
- Отдельные роли для пользователей и администраторов.
- `Rate limiting` по `IP` и по `userId`.
- Строгая схема `OpenAPI` + валидация.
- Каждое обращение к `/users/{id}` или `/orders/{id}` сверяет владельца с `sub` из токена.
- Ошибки — в едином формате: `errorCode`, `message`, `traceId`.

### Внутренний сервис‑сервис API

- `mTLS` + `client credentials` (`OAuth2`) для взаимной аутентификации.
- `API Key` — только для простых интеграций.
- Привязка ключа/клиента к конкретному сервису и окружению (`service-A@prod`).
- Ограничить разрешённые `endpoint`-ы для каждого ключа.
- Логировать попытки вызова неразрешённых методов.

### Версионирование и устаревание

- Новые поля — добавлять в схему, старые помечать `deprecated`.
- Поля не удалять внезапно — назначить срок и предупредить клиентов.
- Контракт-тесты для проверки обратной совместимости.


## Минимальный чек‑лист

- [ ] Каждый защищённый `endpoint` проверяет права (нет «дыр» по `URL`).
- [ ] Для чувствительных ресурсов проверяется владение (`IDOR` исключён).
- [ ] Все токены/ключи передаются только по `HTTPS`, не логируются целиком.
- [ ] Входные данные валидируются по схеме (`OpenAPI`/`JSON Schema`/`proto`).
- [ ] В ответах не отдаются внутренние идентификаторы и секреты.
- [ ] Для публичных `API` включены лимиты запросов и алерты.

Дополнительно:

- [ ] Определён формат ошибок (`errorCode`, `message`, `traceId`) и он стабилен.
- [ ] Есть контракт‑тесты для критичных клиентов/интеграций.
- [ ] Для внутренних `API` определены политики `mTLS`/`API Key`/`OAuth2` и зафиксированы в документации.


## Решение проблем

| Симптом | Причина | Решение |
|---------|---------|---------|
| Клиент видит чужие данные | Нет проверки владельца ресурса (`IDOR`) | Добавить проверку `userId`/`tenantId` из токена vs владелец ресурса |
| Частые 5xx при нагрузке | Нет `rate limiting`, тяжёлые запросы, `N+1` | Ввести лимиты, оптимизировать запросы, добавить кэширование |
| Утечка секретов в логах | Логируются заголовки/тела с токенами | Маскировать чувствительные поля, пересмотреть формат логов |
| Сканер находит инъекции | Конкатенация строк в `SQL`/`NoSQL`/`shell` | Переписать на параметризованные запросы, добавить валидацию ввода |
| «Ломка» клиентов после релиза | Изменение контракта без обратной совместимости | Версионирование (`/v1`, `/v2`), контракт-тесты, время на миграцию |
| Легко угадать `id` ресурсов | Последовательные `id` без проверки доступа | Использовать `UUID`, всегда проверять права доступа |
| Много 401/403 в логах | Ошибки в `access control` или подбор токенов | Пересмотреть правила, алерты на аномалии, ужесточить `rate limiting` |


## Расширенные паттерны проектирования API

### Идентификаторы и мультитенантность

Варианты передачи `tenantId`:

- `claim` в `JWT` (предпочтительно — нельзя подменить клиентом).
- В пути: `/tenant/{tenantId}/orders`.
- Отдельный домен: `tenant.example.com`.

Правила:

- Истинный `tenantId` — **только из токена**, даже если он есть в пути или теле.
- Проверять привязку всех запросов/ответов к `tenantId` из контекста безопасности.
- Не смешивать данные разных арендаторов в одном запросе.

### Идемпотентность и повторные запросы

Сетевые запросы могут повторяться. Многократное выполнение опасного действия (списание, перевод) — финансовые потери.

- `PUT` с устойчивыми `id` — идемпотентен по своей природе.
- Для создающих операций — заголовок `Idempotency-Key` + хранение результата по ключу.
- В логах и аудите фиксировать `Idempotency-Key` и `traceId`.

### Пагинация, фильтрация и сортировка

- Ограничить максимальный `pageSize` (например, 100-1000).
- Валидировать параметры сортировки и фильтров по **белому списку полей**.
- Для сложных фильтров — заранее определённые пресеты, а не произвольные выражения.

### Обработка ошибок и коды статусов

Единый формат: `errorCode` + `message` + `traceId`.

- Из `message` исключить детали реализации (таблицы, серверы, пути).
- Всегда возвращать `traceId` для связи с логами.
- `HTTP`-коды: `400` — некорректный запрос, `401` — нет аутентификации, `403` — нет прав, `404` — ресурс не найден, `409` — конфликт, `429` — превышен лимит, `5xx` — ошибка сервера.


## Частые вопросы по безопасности API

**`JWT` или `API Key`?**
`JWT` + `OAuth2`/`OIDC` — для пользовательских сессий (`SPA`, мобильные). `API Key` или `client credentials` + `mTLS` — для сервис-сервис. `JWT` удобен, когда нужны `claims` (роли, `userId`). `API Key` — когда важна простота и нет сложной модели пользователей.

**Нужно ли шифровать `JWT`?**
Обычно нет. `JWT` подписывается (целостность), но содержимое читаемо. Не кладите секреты, пароли или `PII` в `claims`. Если нужно скрыть содержимое — есть `JWE`, но проще хранить в токене только `userId` и читать данные из БД.

**Один `JWT` для веба и мобильного?**
Лучше разделять: разные `clientId`/`audience`, разный TTL токенов. Это упрощает управление доступом, отзыв токенов и анализ аномалий.

**Где хранить `access token` на фронтенде?**
`cookie` (`HttpOnly` + `Secure` + `SameSite`) — защищает от `XSS`, но требует `CSRF`-защиты. `localStorage` — уязвим к `XSS`, но не требует `CSRF`-защиты. Нет идеального решения — выбор зависит от архитектуры.

**Логировать ли тела запросов/ответов?**
Осторожно. Маскировать пароли, токены, `PII`. В проде — только метаданные (`traceId`, коды ошибок). Подробное логирование — только на тестовых стендах.

**Как защитить `GraphQL`-API?**
Ограничить глубину и сложность запросов (`depth`/`complexity limiting`). Контролировать доступ к полям по ролям. Валидация ввода — как для `REST`. `GraphQL` даёт гибкость клиентам, но увеличивает риск тяжёлых запросов и утечки лишних полей.

**Всегда ли нужен `rate limiting`?**
Для публичных `API` — практически всегда (защита от перебора, ограничение нагрузки). Для внутренних — лимиты мягче, но полезны для обнаружения аномалий.

**Почему плохо возвращать «сырые» ошибки из БД?**
В них могут быть имена таблиц, колонок, путей — это помогает атакующему. Логировать полную ошибку внутренне, наружу отдавать только обобщённый `errorCode` + `message`.

**Как версионировать `API` без поломки клиентов?**
Заранее определять `breaking changes`. Версии через пути (`/v1`, `/v2`) или заголовки. Параллельная работа старой и новой версий на время миграции. Документировать и давать клиентам время.

**Как тестировать безопасность `API`?**
Минимум: `OWASP ZAP`/`Burp Suite` для базового сканирования. Негативные тесты: запрос без токена → 401, с чужой ролью → 403, чтение чужого ресурса → отказ. Проверять, что ответы не содержат лишних полей.
