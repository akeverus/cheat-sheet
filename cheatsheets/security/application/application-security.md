# Безопасность приложений (Application Security)

`AppSec` — практики защиты приложений на уровне кода и бизнес-логики:

## Введение

В прикладной разработке безопасность чаще всего сводится к трём вопросам:

1. **Кто это?** — аутентификация (пароль, `MFA`, `OAuth2`, `OIDC`, `mTLS`).
2. **Что ему можно?** — авторизация и контроль доступа.
3. **Как защитить данные и логику?** — инъекции, `XSS`/`CSRF`, перебор паролей, утечка секретов.

Конкретные атаки и криптография разбираются в других файлах раздела `security/`.
Здесь — только то, что должен держать в голове разработчик прикладного кода.


## Аутентификация

**Аутентификация** — проверка того, что субъект действительно тот, за кого себя выдаёт.

### Основные варианты

| Подход | Суть | Где используется |
|--------|------|------------------|
| Пароль + хеш | Логин/пароль, храним только хеш (`bcrypt`, `Argon2`) | Классические веб-приложения, `SPA` с формой логина |
| `MFA` | Пароль + второй фактор (`TOTP`, push, `WebAuthn`) | Админка, кабинет с чувствительными данными |
| Федеративная (`OAuth2`/`OIDC`) | Аутентификация через внешний `Identity Provider` | `SSO` в компаниях, логин через Google/GitHub |
| Сертификаты (`mTLS`) | Клиент предъявляет сертификат | Взаимодействие сервис-сервис |

### Требования к паролям

- Хранить **только хеш** (`bcrypt`, `Argon2`, `scrypt`) с достаточной стоимостью вычисления.
- Парольная политика: разумная длина (12+ символов), не запрещать длинные пароли.
- Защита от перебора: `rate limiting`, временная блокировка аккаунта, `CAPTCHA`.
- **Никогда** не логировать пароли и коды `MFA`.

### Анти-паттерны

- Хранение пароля в открытом виде или хеширование через `MD5`/`SHA1`.
- Один и тот же пароль между системами.
- Отправка паролей по почте.
- Самописная криптография вместо проверенных библиотек.


## Авторизация и контроль доступа

**Авторизация** — что конкретному субъекту разрешено делать.

### Уровни контроля доступа

- **Ресурс** — может ли пользователь вообще получить доступ к объекту (`/orders/123`)?
- **Операция** — какие действия разрешены (`GET`, `POST`, `PUT`, `DELETE`)?
- **Атрибуты** — какие поля видны? Маскирование `PII`, запрет изменения `role`/`balance`.

### Модели

| Модель | Суть | Когда подходит |
|--------|------|----------------|
| `RBAC` | Права привязаны к ролям (`USER`, `ADMIN`) | Простая структура ролей |
| `ABAC` | Решение по атрибутам (страна, время, отдел) | Сложные правила доступа |
| `ACL` | Список доступа на уровне объектов | Детальный контроль |

### Принципы

- **Наименьшие привилегии** — только те права, что реально нужны.
- **Запрет по умолчанию** — доступ явно предоставляется, а не отнимается.
- Чётко разделять **аутентификацию** (кто?) и **авторизацию** (что можно?).


## OAuth2 и OpenID Connect

`OAuth2` — протокол делегированной авторизации: приложение получает доступ к ресурсам через `access token`.
`OIDC` — надстройка для аутентификации: позволяет узнать, кто пользователь.

### Ключевые роли

- **Resource Owner** — пользователь (владелец данных).
- **Client** — наше приложение.
- **Authorization Server** (`IdP`) — выдаёт токены.
- **Resource Server** — защищённый `API`.

### Потоки

- **Authorization Code + PKCE** — рекомендуется для `SPA` и мобильных приложений.
- **Client Credentials** — сервис-сервис без участия пользователя.
- **Implicit Flow** — **устаревший**, не использовать.

### Что важно разработчику

- Не реализовывать `OAuth2` с нуля — использовать `Spring Security`, `Keycloak`, `Auth0`.
- Белый список `redirect_uri`.
- `PKCE` обязателен для публичных клиентов.


## JWT и управление токенами

`JWT` — компактный токен с заголовком, полезной нагрузкой (`claims`) и подписью.

### Типы токенов

| Токен | Срок жизни | Назначение |
|-------|-----------|------------|
| `access token` | Минуты — часы | Доступ к `API` |
| `refresh token` | Дни — недели | Обновление `access token` |

### Рекомендации

- Минимум `claims` в токене. **Никаких** паролей, данных карт, `PII`.
- Алгоритмы подписи: `RS256` или `ES256`. Запретить `alg=none`.
- `access token` — короткоживущий (минуты). `refresh token` — с возможностью отзыва.
- Хранение на клиенте: `cookie` с `HttpOnly` + `SameSite` предпочтительнее `localStorage`.

### Анти-паттерны

- Вечные токены без истечения.
- `refresh token` в `localStorage` без защиты.
- Токен без привязки к устройству/сессии.


## Управление сессиями

### Сессии при использовании JWT

Даже с `JWT` часто нужен уровень «сессии»:

- Привязка к устройству и `User-Agent` для обнаружения подозрительной активности.
- Список активных сессий в профиле — пользователь видит, где залогинен.
- Принудительное завершение всех сессий при подозрении на компрометацию.

### Cookie-based сессии

- Флаги: `HttpOnly`, `Secure`, `SameSite` (`Lax` или `Strict`).
- Идентификатор сессии — криптографически стойкий генератор.
- Регенерация идентификатора **после логина** (защита от session fixation).
- В сессии — минимум данных (только идентификаторы).


## Решение проблем

| Симптом | Причина | Решение |
|---------|---------|---------|
| Пользователь «слетает» из сессии | Слишком короткий срок `access token` или некорректная регенерация | Проверить логику обновления токена, настроить баланс TTL |
| Видны чужие данные | Нет проверки владельца ресурса (`IDOR`) | Сверять `userId` из токена с владельцем объекта |
| `JWT` не принимается `API` | Несовпадение ключей, `audience` или `issuer` | Синхронизировать настройки `IdP` и `Resource Server` |
| Не работает `logout` при `JWT` | Нет отзыва `refresh token`, фронтенд не чистит хранилище | Хранить статус `refresh token` (активен/отозван), чистить `cookie` |
| Частые подозрительные логины | Нет защиты от перебора | Добавить `rate limiting`, алерты, `MFA` |


## Минимальный чек-лист для прикладного кода

**Аутентификация и пароли**

- [ ] Пароли — только хеш (`bcrypt`/`Argon2`), нет `MD5`/`SHA1`.
- [ ] Защита от перебора (`rate limiting`, блокировка, алерты).
- [ ] `MFA` для критичных действий (вход в админку, смена почты).

**Авторизация**

- [ ] Все защищённые эндпоинты проверяют права.
- [ ] Проверка владения ресурсом (`userId` из токена сравнивается с ресурсом).
- [ ] Принцип наименьших привилегий для ролей и технических учёток.

**Токены и сессии**

- [ ] `access token` с ограниченным сроком, `refresh token` можно отозвать.
- [ ] Для веб-клиентов токены в `cookie` с `HttpOnly` и `SameSite`.
- [ ] Есть страница просмотра активных сессий и их завершения.
