## Карта категорий

| Категория | Что делает | Когда работает | Ключевые инструменты |
|-----------|-----------|---------------|---------------------|
| `SAST` | Анализ исходного кода без запуска | На этапе разработки / в `CI` | `SonarQube`, `Semgrep`, `CodeQL` |
| `DAST` | Тестирование работающего приложения «снаружи» | На `staging` / в `CI` | `OWASP ZAP`, `Burp Suite` |
| `SCA` | Поиск `CVE` в зависимостях | В `CI` при каждой сборке | `Snyk`, `Dependabot`, `Renovate`, `OWASP Dependency-Check` |
| Сканеры образов | Проверка контейнеров на `CVE` и мисконфигурации | В `CI` при сборке образа | `Trivy`, `Clair`, `Anchore` |
| Сканеры `IaC` | Проверка `Terraform`/`K8s` манифестов | `pre-commit` / `CI` | `tfsec`, `Checkov` |
| Сканеры секретов | Поиск паролей/токенов в репозитории | `pre-commit` / `CI` | `gitleaks`, `truffleHog`, `git-secrets` |
| `SIEM` | Сбор и корреляция логов, обнаружение атак | Постоянно в рантайме | `ELK Stack`, `Splunk`, `CloudWatch` + `GuardDuty` |


## SAST — статический анализ кода

`SAST` находит уязвимости **в исходном коде** без запуска приложения — инъекции, небезопасная десериализация, утечки данных.

**Когда полезен:** на каждый коммит или `pull request` в `CI`. Чем раньше найдена проблема, тем дешевле исправление.

### Инструменты

- `SonarQube` — широкий набор правил для множества языков. Есть «качественные ворота» (`Quality Gates`) — можно блокировать `merge` при критичных уязвимостях.
- `Semgrep` — лёгкий, с простым синтаксисом для создания собственных правил. Хорош для поиска специфичных паттернов.
- `CodeQL` — семантический анализ: умеет отслеживать поток данных от пользовательского ввода до опасных операций.
- **Коммерческие** (`Checkmarx`, `Veracode`, `Fortify`) — более глубокий анализ, но дорого.

### Совет

Для небольшой команды хватит одного `SAST`-инструмента в `CI`. Для крупного проекта — комбинация нескольких с централизованной агрегацией отчётов.


## DAST — динамическое тестирование

`DAST` тестирует **работающее приложение** извне, имитируя действия атакующего — отправляет запросы и анализирует ответы.

**Когда полезен:** после деплоя на `staging`. Находит проблемы, которые `SAST` не видит: неправильные заголовки безопасности, ошибки конфигурации сервера, `XSS` в рендеринге.

### Инструменты

- `OWASP ZAP` — открытый, хорошо автоматизируется в `CI/CD`. Подходит для регулярных сканов.
- `Burp Suite` — продвинутый: перехват и модификация запросов, расширения, ручной пентест. Лучший выбор для глубокого анализа.

### Нюанс

Для `SPA` и `GraphQL API` может потребоваться дополнительная настройка — не все сканеры «из коробки» корректно работают с клиентским роутингом и нестандартными запросами.


## SCA — анализ зависимостей

`SCA` ищет **известные уязвимости** (`CVE`) в используемых библиотеках. Это критически важно: большинство уязвимостей — в сторонних компонентах.

### Инструменты

- `Snyk` — детальный анализ + рекомендации по исправлению + автоматические `PR` с фиксами.
- **`Dependabot` / `Renovate`** — автоматические `PR` с обновлениями зависимостей.
- `OWASP Dependency-Check` — открытый, поддерживает множество языков.

### Практический паттерн

1. Включить автоматические `PR` с обновлениями (`Dependabot` / `Renovate`).
2. Завести политику: критичные `CVE` (`CVSS` ≥ 7.0) — обновлять немедленно, остальные — в плановом порядке.
3. Настроить фильтрацию, чтобы «шум» не заставлял команду игнорировать уведомления.


## Сканирование образов и IaC

### Контейнерные образы

Уязвимости в базовых образах — частая причина компрометации. Сканеры проверяют все пакеты во всех слоях образа.

- `Trivy` — быстрый и простой, идеален для `CI`.
- `Clair` — детальный анализ по слоям.
- `Anchore` — политики безопасности и автоматизация.

**Рекомендация:** сканировать при каждой сборке, блокировать деплой при критичных `CVE`. Регулярно обновлять базовые образы.

### Infrastructure as Code

`IaC`-сканеры находят ошибки безопасности в `Terraform`, `CloudFormation` и `Kubernetes`-манифестах до их применения: открытые порты, небезопасные настройки доступа, устаревшие компоненты.

- `tfsec` — для `Terraform`.
- `Checkov` — мультиплатформенный.

**Рекомендация:** встроить в `pre-commit` хуки или `CI`. Блокировать применение при критичных ошибках.


## Сканирование секретов

Сканеры ищут случайно закоммиченные пароли, ключи и токены.

### Инструменты

- `gitleaks` — быстрый и точный.
- `truffleHog` — энтропийный анализ (находит даже нестандартные форматы).
- `git-secrets` — настраиваемые паттерны.
- Встроенные сканеры `GitHub` / `GitLab` — автоматически проверяют коммиты.

### Что делать при обнаружении секрета

1. **Немедленно ротировать** скомпрометированный секрет (новый ключ в `AWS`, новый токен).
2. При необходимости — почистить историю репозитория (`git filter-branch` / `BFG`).
3. Разобрать инцидент: почему секрет попал в код, как предотвратить повторение.

### Рекомендация

- `pre-commit` хук — ловит секреты **до** попадания в историю.
- Сканер в `CI` — страховочная сеть для того, что прошло мимо хука.


## SIEM и мониторинг

`SIEM` собирает логи со всей инфраструктуры (приложения, балансировщики, БД, ОС), ищет корреляции между событиями и поднимает алерты при подозрительной активности.

### Решения

| Тип | Пример | Подходит для |
|-----|--------|-------------|
| Открытый | `ELK Stack` (`Elasticsearch` + `Logstash` + `Kibana`) | Небольшие команды, ограниченный бюджет |
| Облачный | `CloudWatch` + `GuardDuty` (`AWS`) | Инфраструктура уже в облаке |
| Коммерческий | `Splunk`, `IBM QRadar` | Крупные организации, сложная корреляция |

### Минимум для старта

1. Определить источники логов (приложения, `LB`, БД, `WAF`).
2. Настроить базовые правила: подбор паролей (N неудачных логинов за M минут), вход с необычного `IP`, массовые ошибки авторизации.
3. Назначить ответственных за разбор алертов, наладить процесс отчётности.


## Интеграция в CI/CD

Общая схема размещения инструментов по этапам пайплайна:

| Этап | Инструменты | Действие при находке |
|------|------------|---------------------|
| `pre-commit` | Сканеры секретов, `IaC`-линтеры | Блокировать коммит |
| Сборка (`build`) | `SAST`, `SCA` | Блокировать `merge` при критичных `CVE` |
| Сборка образа | Сканеры образов (`Trivy`) | Блокировать публикацию образа |
| `Staging` | `DAST` (`ZAP`) | Блокировать деплой в прод |
| Прод | `SIEM`, мониторинг | Алерты, автоматическое реагирование |

**Принцип:** критичные уязвимости блокируют продвижение по пайплайну. Уязвимости низкой серьёзности — задача в бэклог со сроком.


## Решение проблем

| Проблема | Причина | Решение |
|----------|---------|---------|
| Слишком много ложных срабатываний | Слишком широкие правила, не настроена фильтрация | Настроить исключения (тестовые данные, примеры кода), регулярно пересматривать правила |
| Инструмент замедляет сборку | Полное сканирование при каждом коммите | Инкрементальный анализ (только изменённые файлы), кэширование результатов |
| Команда игнорирует отчёты | Много шума, непонятные сообщения | Поднять порог (блокировать только `Critical`/`High`), обучить команду интерпретации |
| Секрет попал в историю `git` | Нет `pre-commit` хука, нет сканера в `CI` | Ротировать секрет, почистить историю, внедрить `pre-commit` + `CI` сканер |
| `DAST` не находит уязвимости в `SPA` | Сканер не умеет работать с клиентским роутингом | Настроить аутентификацию и навигацию в сканере, использовать `API`-режим |


## Чек-лист

- [ ] `SAST` встроен в `CI` и проверяет код при каждом `PR`.
- [ ] `SCA` проверяет зависимости, есть политика по критичным `CVE`.
- [ ] Автоматические `PR` с обновлениями зависимостей (`Dependabot`/`Renovate`).
- [ ] Контейнерные образы сканируются при сборке (`Trivy`/`Clair`).
- [ ] `IaC`-шаблоны проверяются до применения (`tfsec`/`Checkov`).
- [ ] Сканер секретов работает в `pre-commit` и в `CI`.
- [ ] Есть процедура реагирования на обнаружение секрета в коде.
- [ ] `DAST` запускается на `staging` перед деплоем в прод.
- [ ] Логи собираются централизованно, базовые правила корреляции настроены.
- [ ] Критичные уязвимости блокируют продвижение по пайплайну.
