## Обзор подходов

Четыре подхода дополняют друг друга — каждый находит свой тип уязвимостей:

| Подход | Что делает | Когда |
|--------|-----------|-------|
| `SAST` | Анализ исходного кода без запуска | Рано — на этапе разработки |
| `DAST` | Тестирование работающего приложения через `HTTP` | На `staging` — имитация реальных атак |
| `SCA` | Поиск `CVE` в зависимостях | Постоянно — большинство уязвимостей в чужих библиотеках |
| Пентесты | Ручная имитация атак по методологии | Периодически — находит проблемы бизнес-логики |

Все четыре нужны в комплексе. Автоматические инструменты пропускают логические уязвимости, пентестеры не покрывают каждый коммит.


## `SAST` — статический анализ кода

Анализ исходного кода без запуска — находит инъекции, небезопасную работу с вводом, проблемы с шифрованием и конфигурацией.

**Инструменты:** `SonarQube`, `Semgrep`, `CodeQL`, коммерческие (`Checkmarx`, `Veracode`).

### Как внедрять

1. **Старт** — включить только критичные правила, чтобы отчёты были читаемыми.
2. **Расширение** — постепенно добавлять правила, договориться о пороге «провала» сборки.
3. **Интеграция в ревью** — ссылки на находки `SAST` в `pull request`.

### Практические правила

- Запускать на каждый `PR` или хотя бы по расписанию.
- Настраивать правила под проект — выключить нерелевантные, добавить свои.
- Отделять «шум» от реальных проблем — это требует обучения команды.


## `DAST` — динамическое тестирование

Тестирование работающего приложения «снаружи» — как видит его атакующий. Находит проблемы, которые `SAST` не видит: ошибки конфигурации сервера, неправильные заголовки, `XSS` при рендеринге.

**Инструменты:** `OWASP ZAP` (открытый, автоматизируется в `CI`), `Burp Suite` (продвинутый ручной анализ).

### Практические правила

- Запускать против тестового стенда, максимально похожего на прод.
- Начинать со «сканирования» (`spider`/`crawl`), затем — полные проверки.
- Для защищённых зон — аутентификация через `login`-скрипты.

### Важно

- Держать **отдельное окружение** для агрессивных `DAST`-проверок.
- Заранее договориться о `rules of engagement` (нельзя удалять данные, отправлять платежи).
- Сохранять отчёты и привязывать находки к задачам в трекере.


## `SCA` — анализ зависимостей

Поиск `CVE` в используемых библиотеках. Большинство уязвимостей — в сторонних зависимостях.

**Инструменты:** `OWASP Dependency-Check`, `Snyk`, `Dependabot`, `Renovate`, `Trivy`.

### Практический паттерн

1. Включить автоматические `PR` с обновлениями (`Dependabot`/`Renovate`).
2. Определить политику: критичные `CVE` блокируют сборку или релиз.
3. Регулярный «слот» в спринте на обновление зависимостей.

### Что решить заранее

- Какие `CVE` блокируют релиз автоматически (обычно критичные + высокие с известными эксплойтами).
- Какие требуют ручной оценки риска.
- Правила автоматического слияния `PR` с обновлениями.


## Пентесты и ручное тестирование

Покрывают сложные сценарии, которые автоматика пропускает: бизнес-логика, цепочки атак, социальная инженерия.

Проводятся по методологиям: `OWASP` Testing Guide, `NIST` Cybersecurity Framework, внутренние стандарты.

### Формат

1. **Определить зону охвата** — какие приложения, сервисы, окружения.
2. **Договориться о правилах** (`rules of engagement`) — что разрешено, что запрещено.
3. **Получить отчёт** с приоритизацией находок и рекомендациями.
4. **Превратить находки в задачи** с ответственными и сроками.
5. **Провести `post-test`** после исправлений — убедиться, что критичные проблемы закрыты.


## Как встроить в CI/CD

### Базовый пайплайн

| Этап | Что запускать | Блокировать при |
|------|--------------|-----------------|
| `pull request` | Быстрый `SAST` + `SCA` | Критичные уязвимости |
| `merge` в `main` / перед релизом | `DAST` на стенде + ручные проверки по чек-листу | Критичные находки |

### Расширенный (по расписанию)

- Полный `SAST` по всему коду.
- Глубокий `SCA` по всем модулям и образам.
- `DAST` по приоритетным внешним интерфейсам.

Результаты — на дашбордах. Критичные проблемы блокировка релиза или явный «approve с риском».

### Пример шага `SAST` в `GitHub Actions`

```yaml
- name: Run SAST
  uses: SonarSource/sonarcloud-github-action@master
  env:
    SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
  with:
    args: >
      -Dsonar.qualitygate.wait=true
```


## Минимальный чек‑лист

- [ ] Есть хотя бы один `SAST`‑инструмент, запускаемый автоматически.
- [ ] Зависимости проходят `SCA`, есть процесс обновления.
- [ ] На ключевые сервисы периодически прогоняется `DAST`.
- [ ] Критичные релизы сопровождаются пентестом или расширенным ручным тестированием.
- [ ] Результаты тестирования не «теряются», а превращаются в задачи с приоритизацией.

Дополнительно:

- [ ] Для каждого типа тестов определены пороги (что считается «провалом»).
- [ ] Есть базовые security‑чек‑листы для ручного тестирования функционала.
- [ ] Команда разработки понимает, как интерпретировать отчёты инструментов.


## Решение проблем

| Симптом | Причина | Решение |
|---------|---------|---------|
| В `SAST`-отчётах слишком много «красного» | Включены нерелевантные правила, нет настройки под проект | Сузить до критичных категорий, поэтапно расширять |
| `SCA` постоянно блокирует сборку | Много старых зависимостей, нет процесса обновлений | Регулярные обновления, план миграций, временное ослабление политик с планом исправлений |
| `DAST` находит `XSS`/`SQLi`/`CSRF` | Базовые меры защиты не реализованы | Исправить корневые проблемы по чек-листам [Web Security](../application/web-security.md) и [Application Security](../application/application-security.md) |
| Отчёты по безопасности никто не читает | Нет ответственного, результаты не интегрированы в процесс | Назначить владельца процесса, регулярный разбор отчётов, привязка к `KPI`/`OKR` |
| Невозможно воспроизвести уязвимость | Разные версии окружений, нет шагов воспроизведения | Требовать чёткие шаги и описание окружения, стандартизировать тестовые стенды |
