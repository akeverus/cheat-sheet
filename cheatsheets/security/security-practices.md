## Secure SDLC

Суть `Secure SDLC` — думать о безопасности **на каждом этапе**, а не добавлять проверки «в конце».

### Безопасность по этапам

| Этап | Что делать | Кто отвечает |
|------|-----------|-------------|
| **Требования** | Моделирование угроз для критичных фич (платежи, экспорт данных, управление доступом) | Продукт-менеджер, аналитик |
| **Дизайн** | Выбор схемы аутентификации/авторизации, определение границ доверия между сервисами | Архитектор |
| **Разработка** | Следование гайдлайнам безопасности, параметризованные запросы, тесты на негативные сценарии | Разработчик |
| **Тестирование** | `SAST`/`DAST`/`SCA` в `CI`, ручные проверки по чек-листу | QA, специалист по безопасности |
| **Деплой и эксплуатация** | Безопасная конфигурация, мониторинг, алерты | DevOps, SRE |

### Ключевой принцип

Чем раньше найдена проблема, тем дешевле исправление. Уязвимость, пойманная на ревью, стоит часы. В продакшене — дни и репутацию.

## Моделирование угроз

Моделирование угроз — анализ «что может пойти не так» **до** написания кода.

### Процесс

1. **Определить границы** — что защищаем (данные, сервисы, API).
2. **Идентифицировать угрозы** — кто может атаковать и зачем (внешний атакующий, инсайдер).
3. **Проанализировать векторы атак** — как именно можно эксплуатировать уязвимости.
4. **Определить контрмеры** — шифрование, контроль доступа, мониторинг.
5. **Документировать** — результаты используются при архитектурных решениях.

### Методологии

- **`STRIDE`** (Microsoft) — классифицирует угрозы по типам: подмена, изменение, отказ от авторства, раскрытие информации, отказ в обслуживании, повышение привилегий.
- **`PASTA`** — процесс симуляции атак и анализа угроз, ориентированный на бизнес-риски.

### Когда проводить

- При добавлении чувствительных фич (платежи, авторизация, экспорт данных).
- При серьёзных изменениях архитектуры.
- Формат: короткая сессия (30-60 мин) с командой.

## Код-ревью с фокусом на безопасность

Безопасное ревью дополняет обычное — ревьюер проверяет не только логику, но и типичные уязвимости.

### Мини-чек-лист для ревьюера

**Новые точки входа** (`controller`, `handler`):
- [ ] Требуют аутентификации?
- [ ] Проверяют права доступа (авторизацию)?
- [ ] Защищены от `CSRF`?

**Обращения к БД, файлам, командам ОС:**
- [ ] Параметризованные запросы / безопасные API (не конкатенация строк)?

**Логирование:**
- [ ] Не логируются пароли, токены, `PII`?

**Конфигурация:**
- [ ] Изменения `CORS`/`CSP`/`security config` не ослабляют защиту?

**Ввод/вывод:**
- [ ] Пользовательский ввод валидируется?
- [ ] Вывод экранируется (защита от `XSS`)?

### Типичные ошибки, которые ищем

| Ошибка | Пример | Правильно |
|--------|--------|-----------|
| `SQL`-инъекция | `"SELECT * FROM users WHERE id = " + userId` | Параметризованный запрос: `WHERE id = ?` |
| Обход авторизации | `@PermitAll` без обоснования, доступ к `Repository` напрямую | Проверка `userId` из токена vs владелец ресурса |
| Утечка секретов в логи | `logger.info("password: " + password)` | Логировать только `userId`, время, событие |
| Слабый `CORS` | `Access-Control-Allow-Origin: *` | Белый список доменов |

## Управление уязвимостями

Цель — чтобы найденные проблемы **не терялись** и исправлялись по приоритету.

### Источники уязвимостей

- Результаты `SAST`/`DAST`/`SCA` (автоматические).
- Результаты пентестов (ручные).
- Сообщения от пользователей / исследователей.

### Процесс

1. **Триаж** — отсеять ложные срабатывания, сгруппировать похожие находки, определить реальную серьёзность.
2. **Регистрация** — каждая реальная уязвимость → задача в трекере (`Jira` и т.п.) с приоритетом и меткой `security`.
3. **Планирование** — закладывать время на исправление в спринт.
4. **Исправление и проверка** — привязать коммит к задаче, провести повторную проверку.

### SLA по серьёзности

| Серьёзность | Срок исправления | Пример |
|-------------|-----------------|--------|
| `Critical` | Немедленно (часы) | `SQL`-инъекция в публичном `API` |
| `High` | 1-2 спринта | Обход авторизации, требующий определённых условий |
| `Medium` | 3-4 спринта | Информационная утечка во внутреннем сервисе |
| `Low` | При следующем рефакторинге | Использование устаревшей, но не уязвимой библиотеки |

### Анти-паттерны

- «Складировать» отчёты без разбора.
- Игнорировать уведомления из-за «шумности» — вместо этого настроить инструменты.

## Реагирование на инциденты

### Цикл реагирования

```text
Обнаружение → Классификация → Сдерживание → Устранение → Восстановление → Разбор (post-mortem)
```

| Этап | Действия |
|------|---------|
| **Обнаружение** | Алерты мониторинга, внешние сигналы, сообщения пользователей |
| **Классификация** | Определить масштаб: какие данные затронуты, сколько пользователей, насколько срочно |
| **Сдерживание** | Отключить уязвимую фичу, заблокировать скомпрометированные аккаунты, изолировать систему |
| **Устранение** | Применить патч, сменить секреты, провести дополнительные проверки |
| **Восстановление** | Вернуть сервис в нормальный режим, проверить все системы |
| **Post-mortem** | Выделить **корневые причины** (не симптомы), запланировать изменения |

### Организация команды

- **Заранее** определить состав: `on-call`, представитель бизнеса, специалист по безопасности.
- Каналы связи: основной (`Slack`) + резервный (телефон).
- **Журнал действий** — фиксировать кто, что и когда сделал. Пригодится для `post-mortem`.

### Post-mortem: что важно

- Провести **в течение нескольких дней**, пока всё свежо.
- Искать **корневые причины**, а не только «потушить пожар».
- Результат — конкретные задачи на улучшение процессов/инфраструктуры.
- Документировать и сделать доступным для всей команды.

## Решение проблем

| Проблема | Причина | Решение |
|----------|---------|---------|
| Команда сопротивляется практикам безопасности | Воспринимают как замедление | Показать примеры реальных инцидентов и их стоимость, начать с малого |
| Отчёты инструментов «шумят» | Много ложных срабатываний | Настроить фильтры, отключить нерелевантные правила, обучить команду триажу |
| Уязвимости не исправляются | Нет времени в спринте | Зафиксировать `SLA`, закладывать время на `security`-задачи при планировании |
| `Post-mortem` превращается в обвинения | Культура «кто виноват» | Перейти к «что пошло не так и как предотвратить», без персональных обвинений |
| Нет понимания, что проверять на ревью | Нет чек-листа | Внедрить мини-чек-лист из раздела выше, регулярно обновлять |

## Минимальный чек-лист

**Процессы:**

- [ ] Есть понятные гайдлайны по безопасности для разработчиков.
- [ ] Код-ревью включает проверки на инъекции, авторизацию и утечки секретов.
- [ ] Результаты `SAST`/`DAST`/`SCA`/пентестов → задачи в трекере (не «лежат в отчётах»).

**Управление уязвимостями:**

- [ ] Определены `SLA` по серьёзности (Critical — часы, High — 1-2 спринта).
- [ ] Есть процесс триажа: ложные срабатывания отсеиваются, реальные — приоритизируются.
- [ ] Время на исправление закладывается в спринт.

**Инциденты:**

- [ ] Есть базовый сценарий реагирования и ответственное лицо/роль.
- [ ] Определены каналы связи для инцидентов.
- [ ] `Post-mortem` проводится после каждого значимого инцидента.

**Дополнительно:**

- [ ] Моделирование угроз для критичных фич.
- [ ] Метрики: время реакции, количество открытых критичных уязвимостей.
- [ ] Безопасность учитывается при планировании фич, а не только «в конце».
