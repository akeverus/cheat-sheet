## Основные концепции

| Понятие | Описание |
|---------|----------|
| **Test Plan** | Документ: цели, объём, подход, ресурсы, расписание, критерии входа/выхода |
| **Test Case** | Сценарий: предусловия, шаги, ожидаемый результат, приоритет, связь с требованием |
| **Test Suite** | Набор тест-кейсов (smoke, regression, по модулю) |
| **Test Run** | Прогон: набор кейсов + результаты (Pass/Fail/Blocked/Skip) + билд + окружение |
| **Milestone** | Веха (релиз, спринт); к ней привязывают Test Run |
| **Defect** | Связь падающего теста с задачей/багом в трекере |
| **Traceability** | Связь: требование тест-кейсы результаты дефекты |

### Роли

- **Test Manager** — планирование, ресурсы, отчётность, критерии выхода
- **Test Lead** — распределение кейсов, ревью результатов, эскалация
- **QA Engineer** — создание/выполнение тестов, фиксация результатов, создание багов
- **Automation Engineer** — автоматизация и маппинг тестов на тест-кейсы в инструменте


## Планирование тестирования

### Что включает Test Plan

1. **Scope** — что тестируем и что нет
2. **Цели** — функциональность, регрессия, производительность, безопасность
3. **Подход** — ручное/автоматическое; уровни (unit, integration, system, UAT)
4. **Расписание** — даты прогонов, ключевые вехи (feature freeze, релиз)
5. **Ресурсы** — команда, окружения (dev, staging, pre-prod), инструменты
6. **Риски** — нехватка окружений, зависимость от внешних API; митигация
7. **Критерии входа** — билд стабилен, окружение доступно, кейсы готовы
8. **Критерии выхода** — все Critical/High тесты пройдены, критичные дефекты закрыты

### Приоритизация

| Уровень риска | Критичность | Действие |
|---------------|-------------|----------|
| Высокий | Critical | Обязательно в smoke и regression; падение = блокировка релиза |
| Высокий | High | В regression; при падении — эскалация |
| Средний | Medium | В regression по возможности |
| Низкий | Low | По времени; можно отложить |

Области высокого риска: недавно изменённый код, интеграции с внешними системами, платёжные и персональные данные.


## Тест-кейсы и тест-сьюты

### Структура тест-кейса

| Поле | Описание |
|------|----------|
| ID | Уникальный идентификатор |
| Title | Название (что проверяем) |
| Preconditions | Предусловия |
| Steps | Шаги: действие + ожидаемый результат |
| Priority | Critical / High / Medium / Low |
| Type | Functional, API, UI, Performance |
| Requirement ID | Связь с требованием (Story в Jira) |
| Automation | Ручной / авто; ссылка на скрипт |

### Пример шагов

| Шаг | Действие | Ожидаемый результат |
|-----|----------|----------------------|
| 1 | Открыть страницу логина | Форма «Логин» и «Пароль» |
| 2 | Ввести валидные данные | Поля заполнены |
| 3 | Нажать «Войти» | Перенаправление на главную; имя пользователя отображается |

### Тест-сьюты

- **Smoke** — критичные сценарии после деплоя (5-15% от всех кейсов)
- **Regression** — полная проверка перед релизом (50-100%)
- **Module Suite** — тесты по модулю («Платежи», «Авторизация»)

### Жизненный цикл тест-кейса

`Draft` `Ready for Review` `Approved` (при изменении требования) `Deprecated`

При изменении требования связанные кейсы помечают на обновление или устаревание. Перед релизом ревьюируют Critical и High кейсы на актуальность.


## Выполнение тестов и отчёты

### Test Run

Создаётся с привязкой к milestone (релиз/спринт), build (версия билда), environment (окружение). Тестировщик или CI выполняет тесты и проставляет результат:

| Статус | Значение |
|--------|----------|
| Pass | Тест пройден |
| Fail | Тест провален (создаётся дефект) |
| Blocked | Невозможно выполнить (зависимый баг, недоступное окружение) |
| Skip | Пропущен (с комментарием) |

### Отчёты

- **Test Run Summary** — сколько Pass/Fail/Blocked/Skip
- **Coverage** — % требований, покрытых тестами
- **Defects** — список дефектов по прогону
- **Trends** — тренд % Pass по прогонам

### Критерии завершения (Exit Criteria)

Типичные: все Critical/High тесты пройдены, % Pass выше порога (95%), критичные дефекты закрыты. Если не выполнены — эскалация (перенос релиза или принятие риска).


## Инструменты

| Инструмент | Назначение | Плюсы | Минусы |
|------------|------------|-------|--------|
| **Jira + Zephyr** | Тест-кейсы и прогоны в Jira | Всё в Jira, связь с задачами | Доплата за дополнение |
| **Jira + Xray** | Тест-планы, исполнения, BDD | Трассируемость, Cucumber-импорт | Доплата |
| **TestRail** | Специализированный TM | Удобные отчёты, API | Отдельный инструмент, подписка |
| **Allure** | Отчёты из автотестов | Красивые отчёты, open source | Нет ручных кейсов |
| **Excel** | Ручное ведение | Бесплатно | Нет интеграции с CI |

### Когда что выбирать

- **Уже в Jira, нужны тест-кейсы** Jira + Zephyr/Xray
- **Нужны мощные отчёты без привязки к Jira** TestRail
- **Только автотесты** Allure + отправка результатов в Jira/TestRail через API
- **Минимальный бюджет** Excel + Allure; при росте — миграция в TestRail или Jira


## Интеграция с CI/CD

### Отправка результатов

После прогона автотестов в CI вызывают API инструмента для добавления результатов. Связь «автотест тест-кейс» задаётся через:
- **Маркер/аннотацию** — `@pytest.mark.testrail('C123')`, `@Test(description = "C123")`
- **Маппинг-файл** — `имя_теста Case ID`

### Пример: pytest + TestRail

```python
# Установка: pip install pytest-testrail
# В тесте:
@pytest.mark.testrail('C123')
def test_login_success():
    ...
```

```ini
# testrail.cfg
[pytest]
testrail = true
testrail_url = https://your-domain.testrail.com
testrail_user = user@example.com
testrail_password = API_KEY
testrail_project_id = 1
testrail_run_id = 123
```

### Пример: GitHub Actions

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: pip install -r requirements.txt pytest pytest-testrail
      - run: pytest --testrail --tr-config=testrail.cfg
        env:
          TESTRAIL_URL: ${{ secrets.TESTRAIL_URL }}
          TESTRAIL_USER: ${{ secrets.TESTRAIL_USER }}
          TESTRAIL_API_KEY: ${{ secrets.TESTRAIL_API_KEY }}
```

### TestRail API (основные эндпоинты)

| Действие | Метод | Эндпоинт |
|----------|-------|----------|
| Получить тест-кейсы | GET | `get_cases/{project_id}&suite_id={id}` |
| Создать Test Run | POST | `add_run/{project_id}` |
| Добавить результат | POST | `add_result_for_case/{run_id}/{case_id}` |
| Массовые результаты | POST | `add_results_for_cases/{run_id}` |

Аутентификация: Basic Auth (email + API key). Статусы: 1=Pass, 2=Blocked, 3=Untested, 4=Retest, 5=Fail.

### Расписание прогонов

- **Smoke** — после каждого деплоя на dev/staging (авто в CI)
- **Regression (ночной)** — каждую ночь на staging
- **Regression (релизный)** — перед релизом на pre-prod
- **UAT** — по запросу заказчика


## Метрики и трассируемость

### Ключевые метрики

| Метрика | Описание |
|---------|----------|
| % Pass / Fail | Доля пройденных/проваленных тестов в прогоне |
| Requirements Coverage | % требований, покрытых тест-кейсами |
| Passed Requirements | % требований, по которым все тесты пройдены |
| Open Defects | Число открытых дефектов по приоритету |
| Test Execution Trend | Тренд % Pass по прогонам |
| Velocity | Число кейсов, выполненных за спринт |
| Flaky Rate | Доля нестабильных тестов |

### Трассируемость

Связь: **Requirements** (Story/Epic в Jira) **Test Cases** **Test Run Results** **Defects**. Позволяет ответить на вопрос: «все ли требования покрыты тестами и прошли проверку?». Необходима для аудита (ISO, FDA, SOC 2).

Инструменты: в Jira связь Story Test через issue links (Zephyr/Xray). В TestRail — поле Requirement ID. Экспорт матрицы трассируемости в PDF/Excel для стейкхолдеров.


## Лучшие практики

1. **Единый источник правды** — тест-кейсы и результаты в одном инструменте; не дублировать в Excel.
2. **Трассируемость** — связывать кейсы с требованиями; при изменении требования — обновлять или помечать устаревшие.
3. **Приоритизация** — Critical/High выполнять первыми; при нехватке времени — smoke + high priority.
4. **Маппинг автотестов** — ID тест-кейса в маркере/аннотации для единой отчётности.
5. **Exit criteria** — явно фиксировать в Test Plan; проверять перед релизом.
6. **Один Test Run = один Build** — фиксировать версию билда и окружение.
7. **Обработка flaky** — помечать нестабильные тесты; не блокировать релиз по одному flaky-падению при повторном прохождении.


## Решение проблем

| Проблема | Решение |
|----------|---------|
| Результаты из CI не попадают в TestRail/Jira | Проверить API key, URL, маппинг тест Case ID |
| Тест-кейсы дублируются в Excel и в инструменте | Вести только в инструменте; Excel — для экспорта |
| Трассируемость неполная | Заполнить Requirement ID; настроить связь Story Test в Jira |
| Exit criteria не проверяются | Чек-лист перед релизом; автоматические правила в инструменте |
| Автотесты не совпадают с тест-кейсами | Конвенция имён: ID или название кейса; маппинг-файл |
| Отчёты не актуальны | Пост-шаг в CI для отправки результатов в API |
| Ошибка 401 при вызове TestRail API | Проверить API key и email; перегенерировать key |


## Частые вопросы

**Какой инструмент выбрать?**
Зависит от контекста. Уже в Jira Zephyr/Xray. Нужны мощные отчёты TestRail. Только автотесты Allure + API-интеграция. Маленькая команда Excel + Allure.

**Как маппить автотесты на тест-кейсы?**
Через маркеры (`@pytest.mark.testrail('C123')`) или маппинг-файл (имя теста Case ID). После прогона плагин/скрипт отправляет результат в API.

**Нужны ли ручные тест-кейсы, если есть автотесты?**
Да, для сценариев, которые сложно/невозможно автоматизировать (UX, визуальная проверка, exploratory testing). Ручные и автоматические кейсы живут в одном инструменте для единой отчётности.

**Как часто запускать regression?**
Smoke — после каждого деплоя. Полная регрессия — перед релизом или ночной прогон. Баланс: стоимость прогона vs. риск пропустить регрессию.


## Итоговые таблицы

### Основные артефакты

| Артефакт | Описание |
|----------|----------|
| **Test Plan** | Цели, объём, подход, ресурсы, критерии |
| **Test Case** | Сценарий: шаги + ожидаемый результат |
| **Test Suite** | Набор кейсов (smoke, regression, модуль) |

### Чек-лист перед релизом

- [ ] Test Plan утверждён; scope и exit criteria зафиксированы
- [ ] Critical и High кейсы актуальны (ревью выполнено)
- [ ] Test Run создан с привязкой к билду и окружению
- [ ] Smoke-сьют пройден после деплоя
- [ ] Регрессионный сьют выполнен
- [ ] Результаты синхронизированы с TestRail/Jira
- [ ] Exit criteria проверены: % Pass выше порога, критичные дефекты закрыты
- [ ] Test Summary Report сформирован и доступен стейкхолдерам

### Конвенция имён тест-кейсов

```text
TC_LOGIN_001 — Успешный вход с валидными данными
TC_LOGIN_002 — Ошибка при неверном пароле
TC_PAYMENT_001 — Оплата картой (успех)
```

Префикс TC, модуль, номер, краткое описание. Упрощает поиск и маппинг с автотестами.
