## Введение в Spring AOP

**AOP (Aspect-Oriented Programming)** — это парадигма программирования, которая помогает разделить сквозные задачи (cross-cutting concerns) от бизнес-логики.

**Spring AOP** стремится предоставить простую реализацию **AOP** в **Spring IoC** для решения наиболее распространенных проблем, с которыми сталкиваются программисты. Оно не задумано как полное решение АОП — его можно применять только к компонентам, управляемым контейнером **Spring**.

### Основные понятия

**Прежде чем мы начнем, давайте сделаем быстрый общий обзор терминов и основных понятий:**

1. **Aspect** — стандартный код**/**функция, которая разбросана по нескольким местам приложения и обычно отличается от фактической бизнес-логики (например, управления транзакциями).** Каждый аспект фокусируется на конкретной сквозной функциональности**.
2. **JoinPoint** — это определенная точка во время выполнения программ, таких как выполнение метода, вызов конструктора или назначение полей**.
3. **Advice** — действие, выполняемое аспектом в определенной точке соединения**.
4. **Pointcut** — регулярное выражение, соответствующее точке соединения. Каждый раз, когда какая-либо точка соединения соответствует срезу, выполняется указанный совет, связанный с этим срезом**.
5. **Weaving** — процесс связывания аспектов с целевыми объектами для создания рекомендуемого объекта**.

### Точка соединения и Pointcut

**Точка** соединения **- это точка во время выполнения программы, например выполнение метода или обработка исключения.**

В **Spring AOP** интерфейс **JoinPoint** всегда представляет выполнение метода.

**Pointcut** — это предикат, который помогает сопоставить Совет, который будет применен Аспектом в определенной точке соединения**.

Мы часто связываем **Advice** с выражением **Pointcut,** и он выполняется в любой точке соединения, соответствующей **Pointcut.**

**Advice** — это действие, выполняемое аспектом в определенной точке соединения. Различные типы советов включают «вокруг», «до» и «после».

В **Spring** тип **Advice** моделируется как перехватчик, поддерживающий цепочку перехватчиков вокруг точки соединения.

## Как получить информацию о методе?

В этой статье мы увидим, как получить всю доступную информацию о методе, используя аспект **Spring AOP**.

Для этого мы определим простой аспект, который перехватывает выполнение метода, а затем мы извлечем информацию о методе через **JoinPoint.**

**Пример аспекта для получения информации о методе (JoinPoint):**

```java
// Аспект для логирования информации о методе перед выполнением (JoinPoint)
@Aspect
@Component
public class MethodInfoAspect {
    private Logger logger = LoggerFactory.getLogger(getClass());

    @Pointcut("execution(* com.baeldung.service.*.*(..))")
    public void serviceMethods() {}

    @Before("serviceMethods()")
    public void logMethodInfo(JoinPoint joinPoint) {
        MethodSignature signature = (MethodSignature) joinPoint.getSignature();

        logger.info("Method: " + signature.getName());
        logger.info("Declaring Type: " + signature.getDeclaringTypeName());
        logger.info("Return Type: " + signature.getReturnType().getName());
        logger.info("Parameter Types: " + Arrays.toString(signature.getParameterTypes()));
        logger.info("Parameter Names: " + Arrays.toString(signature.getParameterNames()));
        logger.info("Arguments: " + Arrays.toString(joinPoint.getArgs()));

        // Получение аннотаций метода
        Method method = signature.getMethod();
        Annotation[] annotations = method.getAnnotations();
        for (Annotation annotation : annotations) {
            logger.info("Annotation: " + annotation.annotationType().getName());
        }
    }
}
```

В приведенном выше примере мы определили простой аспект, который логирует информацию о методе перед его выполнением**.

## Введение в типы Advice

В этой статье мы обсудим различные типы рекомендаций АОП, которые можно создать в **Spring.**

**Совет** — это действие, выполняемое аспектом в определенной точке соединения. **Различные типы советов включают советы «вокруг», «до» и «после».** Основная цель аспектов — поддержка сквозных задач, таких как ведение журнала, профилирование, кэширование и управление транзакциями**.

В **Spring** вы можете объявлять рекомендации с помощью аннотаций **AspectJ**, но сначала вы должны применить аннотацию **@EnableAspectJAutoProxy** к своему классу конфигурации, что обеспечит поддержку обработки компонентов, отмеченных аннотацией **@Aspect** (AspectJ).

```java
// Конфигурация для включения поддержки AspectJ
@Configuration
@EnableAspectJAutoProxy
public class AopConfiguration {
    // Бины аспектов
}
```

### @Before Advice

**До совета** выполняется перед точкой соединения**. Он не может предотвратить выполнение потока к точке соединения, если только не выбросит исключение**.

```java
// Аспект с советом @Before - выполняется перед методом
@Aspect
@Component
public class BeforeAspect {
    private Logger logger = Logger.getLogger(getClass().getName());

    // Совет выполняется до любого метода в пакете service
    @Before("execution(* com.baeldung.service.*.*(..))")
    public void logBeforeMethod(JoinPoint joinPoint) {
        String methodName = joinPoint.getSignature().getName();
        logger.info("Before executing method: " + methodName);
    }
}
```

### @After Advice

**После совета** выполняется независимо от результата выполнения метода**. Это означает, что выполнение происходит даже при выбросе исключения**.

```java
// Аспект с советом @After - выполняется после метода (всегда)
@Aspect
@Component
public class AfterAspect {
    private Logger logger = Logger.getLogger(getClass().getName());

    // Совет выполняется после метода, даже при исключении
    @After("execution(* com.baeldung.service.*.*(..))")
    public void logAfterMethod(JoinPoint joinPoint) {
        String methodName = joinPoint.getSignature().getName();
        logger.info("After executing method: " + methodName);
    }
}
```

### @AfterReturning Advice

**После возврата совета** выполняется только при нормальном завершении метода**. Если метод выбрасывает исключение, этот совет не выполняется**.

Во-первых, обратите внимание**: используя аннотацию возврата **@**AfterReturning**,** мы можем получить доступ к возвращаемому значению целевого метода**. Во-вторых, объявив параметр типа **JoinPoint,** мы можем получить доступ к аргументам вызова целевого метода**.

```java
// Аспект с советом @AfterReturning - при успешном завершении метода
@Aspect
@Component
public class AfterReturningAspect {
    private Logger logger = Logger.getLogger(getClass().getName());

    // Получение возвращаемого значения через параметр returning
    @AfterReturning(pointcut = "execution(* com.baeldung.service.*.*(..))", returning = "returnValue")
    public void logAfterReturning(JoinPoint joinPoint, Object returnValue) {
        String methodName = joinPoint.getSignature().getName();
        logger.info("Method: " + methodName + " returned: " + returnValue);
    }
}
```

### @AfterThrowing Advice

**После исключения совета** выполняется только при выбрасывании исключения методом**.

```java
// Аспект с советом @AfterThrowing - при выбросе исключения
@Aspect
@Component
public class AfterThrowingAspect {
    private Logger logger = Logger.getLogger(getClass().getName());

    // Получение исключения через параметр throwing
    @AfterThrowing(pointcut = "execution(* com.baeldung.service.*.*(..))", throwing = "exception")
    public void logAfterThrowing(JoinPoint joinPoint, Exception exception) {
        String methodName = joinPoint.getSignature().getName();
        logger.error("Method: " + methodName + " threw exception: " + exception.getMessage());
    }
}
```

### @Around Advice

**Вокруг совета** окружает точку соединения, такую как вызов метода**.

Это самый действенный совет**. **Вокруг совета может выполняться индивидуальное поведение как до, так и после вызова метода.** Он также отвечает за выбор, следует ли перейти к точке соединения или сократить выполнение рекомендованного метода, предоставив собственное возвращаемое значение или выдав исключение**.

**Чтобы продемонстрировать его использование, предположим, что мы хотим измерить время выполнения метода**. Давайте создадим для этого аспект:**

```java
// Аспект с советом @Around для измерения времени выполнения
@Aspect
@Component
public class PerformanceAspect {
    private Logger logger = Logger.getLogger(getClass().getName());

    // Pointcut для всех методов в классах @Repository
    @Pointcut("within(@org.springframework.stereotype.Repository *)")
    public void repositoryClassMethods() {}

    // Измерение времени выполнения метода
    @Around("repositoryClassMethods()")
    public Object measureMethodExecutionTime(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        Object retval = pjp.proceed();  // Выполнение целевого метода
        long end = System.nanoTime();
        String methodName = pjp.getSignature().getName();
        logger.info("Execution of " + methodName + " took " +
            TimeUnit.NANOSECONDS.toMillis(end - start) + " ms");
        return retval;
    }
}
```

Этот совет срабатывает, когда выполняется любая из точек соединения, соответствующих **pointcut** репозитория**ClassMethods.**

Этот совет принимает один параметр типа **ProceedingJointPoint. Параметр дает нам возможность выполнить действие до вызова целевого метода. В** этом случае мы просто сохраняем время запуска метода.

Во-вторых, тип возвращаемого значения рекомендации — **Object,** поскольку целевой метод может возвращать результат любого типа**. Если целевой метод недействителен, будет возвращено значение **null**.** После вызова целевого метода мы можем измерить время, записать его и вернуть значение результата метода вызывающему объекту**.

## Введение в выражения Pointcut

В этом уроке мы обсудим язык выражений **pointcut** в **Spring AOP**.

Сначала мы познакомимся с некоторой терминологией, используемой в аспектно-ориентированном программировании. Точка соединения — это этап выполнения программы, например выполнение метода или обработка исключения. В **Spring AOP** точка соединения всегда представляет собой выполнение метода.

**Pointcut** — это предикат, который соответствует точкам соединения, а язык выражений **pointcut** — это способ программного описания **pointcut.**

Выражение **pointcut** может отображаться как значение аннотации **`@Pointcut`:**

```java
// Определение именованного pointcut для методов @Repository
@Pointcut("within(@org.springframework.stereotype.Repository *)")
public void repositoryClassMethods() {}
```

**Объявление метода называется **подписью pointcut.** Он предоставляет имя, которое аннотации советов могут использовать для ссылки на этот вырез:**

```java
// Использование именованного pointcut в совете @Around
@Around("repositoryClassMethods()")
public Object measureMethodExecutionTime(ProceedingJoinPoint pjp) throws Throwable {
    // Логика измерения времени
}
```

Выражение **pointcut** также может отображаться как значение свойства выражения тега **aop:pointcut:**

```xml
<aop:config>
    <aop:pointcut id="anyDaoMethod" expression="@target(org.springframework.stereotype.Repository)"/>
</aop:config>
```

Выражение **pointcut** начинается с **указателя pointcut (PCD)** — ключевого слова, указывающего **Spring AOP**, что сопоставлять. Существует несколько указателей **pointcut**, например выполнение метода, типа, аргументов метода или аннотаций.

### execution PCD

**Первичным **PCD** в **Spring** является выполнение, которое соответствует точкам соединения выполнения метода:**

```java
// Точное совпадение: конкретный метод с указанием типов
@Pointcut("execution(public String com.baeldung.pointcutadvice.dao.FooDao.findById(Long))")
```

**Этот пример **pointcut** точно соответствует выполнению метода **findById** класса **FooDao.** Это работает, но не очень гибко**. Предположим, мы хотим сопоставить все методы класса **FooDao**,** которые могут иметь разные сигнатуры, типы возвращаемых значений и аргументы**. Для этого мы можем использовать подстановочные знаки:**

```java
// Wildcards: * - любой тип возврата, (..) - любые параметры
@Pointcut("execution(* com.baeldung.pointcutadvice.dao.FooDao.*(..))")
```

Здесь первый подстановочный знак соответствует любому возвращаемому значению, второй соответствует любому имени метода, а шаблон **(..)** соответствует любому количеству параметров (ноль или более).**

### within PCD

**Другой способ добиться того же результата, что и в предыдущем разделе, — использовать внутренний **PCD,** который ограничивает сопоставление точками соединения определенных типов:**

```java
// within - ограничение по типу класса
@Pointcut("within(com.baeldung.pointcutadvice.dao.FooDao)")
```

**Мы также можем сопоставить любой тип в пакете **com.baeldung** или его подпакете:**

```java
// .. означает любой подпакет
@Pointcut("within(com.baeldung..*)")
```

### this и target PCD

это ограничивает сопоставление точками соединения, где ссылка на компонент является экземпляром данного типа, тогда как цель ограничивает сопоставление точками соединения, где целевой объект является экземпляром данного типа. Первый работает, когда **Spring AOP** создает прокси на основе **CGLIB**, а второй используется при создании прокси на основе **JDK**.

**Предположим, что целевой класс реализует интерфейс:**

```java
// Класс реализует интерфейс - будет JDK прокси
public class FooDao implements BarDao {
}
```

**В этом случае **Spring AOP** будет использовать прокси на основе **JDK**, и нам следует использовать целевой **PCD**, поскольку проксируемый объект будет экземпляром класса **Proxy** и реализует интерфейс **BarDao**:**

```java
// target - для JDK прокси (целевой объект)
@Pointcut("target(com.baeldung.pointcutadvice.dao.BarDao)")
```

С другой стороны, если **FooDao** не реализует какой-либо интерфейс или для свойства **proxyTargetClass** установлено значение **true,** то проксируемый объект будет подклассом **FooDao,** и мы можем использовать этот **PCD:**

```java
// this - для CGLIB прокси (прокси-объект)
@Pointcut("this(com.baeldung.pointcutadvice.dao.FooDao)")
```

### args PCD

**Мы можем использовать этот **PCD** для сопоставления определенных аргументов метода:**

```java
// args - сопоставление по типу аргумента Long
@Pointcut("execution(* *..find*(Long))")
```

**Этот **pointcut** соответствует любому методу, который начинается с **find** и имеет только один параметр типа **Long.** Если мы хотим сопоставить метод с любым количеством параметров, но при этом иметь первый параметр типа **Long,** мы можем использовать следующее выражение:**

```java
// Long первый, затем любые другие параметры
@Pointcut("execution(* *..find*(Long,..))")
```

### @target PCD

**@target PCD** (не путать с целевым PCD, описанным выше) ограничивает сопоставление точками соединения, где класс исполняемого объекта имеет аннотацию заданного типа:**

```java
// @target - класс помечен аннотацией @Repository
@Pointcut("@target(org.springframework.stereotype.Repository)")
```

### @args PCD

Этот **PCD** ограничивает сопоставление точками соединения, где тип времени выполнения фактических переданных аргументов имеет аннотации данного типа(ов).** Предположим, что мы хотим отследить все методы, принимающие **bean-**компоненты, помеченные аннотацией **`@Entity`:**

```java
// @args - аргументы помечены указанной аннотацией
@Pointcut("@args(com.baeldung.pointcutadvice.annotations.Entity)")
public void methodsAcceptingEntities() {}
```

Чтобы получить доступ к аргументу, мы должны предоставить совету аргумент **JoinPoint:**

```java
// Получение аргументов через JoinPoint
@Before("methodsAcceptingEntities()")
public void logMethodAcceptionEntityAnnotatedBean(JoinPoint jp) {
    logger.info("Accepting beans with @Entity annotation: " + jp.getArgs()[0]);
}
```

### @within PCD

**Этот **PCD** ограничивает сопоставление точками соединения внутри типов, имеющих данную аннотацию:**

```java
// @within - внутри типа с указанной аннотацией
@Pointcut("@within(org.springframework.stereotype.Repository)")
```

**Что эквивалентно:**

```java
// Альтернативная запись через within
@Pointcut("within(@org.springframework.stereotype.Repository *)")
```

### @annotation PCD

Этот **PCD** ограничивает сопоставление точками соединения, где субъект точки соединения имеет заданную аннотацию. Например, мы можем создать аннотацию **`@Loggable`:**

```java
// @annotation - метод помечен указанной аннотацией
@Pointcut("@annotation(com.baeldung.pointcutadvice.annotations.Loggable)")
public void loggableMethods() {}
```

**Затем мы можем зарегистрировать выполнение методов, отмеченных этой аннотацией:**

```java
// Логирование методов с @Loggable
@Before("loggableMethods()")
public void logMethod(JoinPoint jp) {
    String methodName = jp.getSignature().getName();
    logger.info("Executing method: " + methodName);
}
```

### Комбинирование выражений Pointcut

**Выражения **Pointcut** можно комбинировать с помощью операторов **&&**, **||** и **!**:**

```java
// Pointcut для методов @Repository
@Pointcut("@target(org.springframework.stereotype.Repository)")
public void repositoryMethods() {}

// Pointcut для методов create* с Long первым параметром
@Pointcut("execution(* *..create*(Long,..))")
public void firstLongParamMethods() {}

// Комбинация: && (AND), || (OR), ! (NOT)
@Pointcut("repositoryMethods() && firstLongParamMethods()")
public void entityCreationMethods() {}
```

В этой краткой статье о **Spring AOP** и **pointcuts** мы проиллюстрировали несколько примеров выражений **pointcut**.

## Введение в AspectJ

Это руководство представляет собой **быстрое и практическое введение в `AspectJ`.**

Сначала мы продемонстрируем, как включить аспектно-ориентированное программирование, а затем сосредоточимся на разнице между встраиванием во время компиляции, после компиляции и во время загрузки**.

### Основы AspectJ

Начнем с краткого введения в аспектно-ориентированное программирование (АОП)** и основы **AspectJ.**

АОП — это парадигма программирования, целью которой является повышение модульности за счет разделения сквозных задач. Это достигается путем добавления дополнительного поведения к существующему коду без изменения самого кода. Вместо этого мы отдельно объявляем, какой код нужно изменить**.

**AspectJ** реализует как задачи, так и объединение сквозных задач, используя расширения языка программирования **Java.**

**AspectJ** предлагает разные библиотеки в зависимости от использования**. Мы можем найти зависимости **Maven** в группе **org.aspectj** в центральном репозитории **Maven**.**

### Зависимости

**При запуске программы **AspectJ** путь к классам должен содержать классы и аспекты, а также библиотеку времени выполнения **AspectJ** (aspectjrt.jar):**

```xml
<dependency>
    <groupId>org.aspectj</groupId>
    <artifactId>aspectjrt</artifactId>
    <version>1.9.20.1</version>
</dependency>
```

Эта зависимость доступна на **Maven Central**.

**В дополнение к зависимости времени выполнения **AspectJ** нам также необходимо включить аспект**jweaver.jar,** чтобы представить рекомендации классу **Java** во время загрузки:**

```xml
<dependency>
    <groupId>org.aspectj</groupId>
    <artifactId>aspectjweaver</artifactId>
    <version>1.9.20.1</version>
</dependency>
```

**AspectJ** обеспечивает реализацию АОП и имеет **три основные концепции:**

1. **Joinpoint**
2. **Pointcut**
3. **Advice**

### Пример использования AspectJ

Мы продемонстрируем эти концепции, создав простую программу для проверки баланса учетной записи пользователя**.

**Сначала давайте создадим класс **Account** с заданным балансом и методом вывода средств:**

```java
// Класс банковского счёта
public class Account {
    int balance = 20;  // Начальный баланс

    // Метод снятия средств
    public boolean withdraw(int amount) {
        if (balance < amount) {
            return false;  // Недостаточно средств
        }
        balance = balance - amount;
        return true;
    }
}
```

Мы создадим файл **AccountAspect.aj** для регистрации информации об учетной записи и проверки баланса учетной записи **(обратите внимание, что файлы AspectJ заканчиваются расширением «.aj»):**

```java
// AspectJ аспект для банковских операций (файл .aj)
public aspect AccountAspect {
    final int MIN_BALANCE = 10;  // Минимальный баланс

    // Определение pointcut для метода withdraw
    pointcut callWithDraw(int amount, Account acc):
        call(boolean Account.withdraw(int)) && args(amount) && target(acc);

    // Before: логирование перед снятием
    before(int amount, Account acc): callWithDraw(amount, acc) {
        System.out.println("Balance before withdrawal: " + acc.balance);
        System.out.println("Withdraw amount: " + amount);
    }

    // Around: проверка баланса и возможный отказ
    boolean around(int amount, Account acc):
        callWithDraw(amount, acc) {
        if (acc.balance < amount) {
            System.out.println("Withdrawal Rejected!");
            return false;
        }
        return proceed(amount, acc);  // Продолжить выполнение
    }

    // After: логирование после снятия
    after(int amount, Account balance): callWithDraw(amount, balance) {
        System.out.println("Balance after withdrawal: " + balance.balance);
    }
}
```

### Типы встраивания (Weaving)

Далее нам нужно будет встроить аспекты в наш код**. В разделах ниже рассматриваются три различных типа встраивания: встраивание во время компиляции, встраивание после компиляции и встраивание во время загрузки в **AspectJ**.**

#### Встраивание во время компиляции

Самый простой подход к встраиванию — это встраивание во время компиляции**. Когда у нас есть исходный код аспекта и код, в котором мы используем аспекты, компилятор **AspectJ** выполнит компиляцию из исходного кода и создаст на выходе файлы встраиваемых классов**. После выполнения нашего кода выходной класс процесса встраивания загружается в **JVM** как обычный класс **Java.**

Мы можем скачать **AspectJ Development Tools**, так как в комплект входит компилятор **AspectJ**. Одной из наиболее важных функций **AJDT** является инструмент для визуализации сквозных проблем, который полезен при отладке спецификации точечного разреза. Мы можем визуализировать совокупный эффект еще до развертывания кода.

**Мы будем использовать плагин **AspectJ Maven** от **Mojo**, чтобы встроить аспекты **AspectJ** в наши классы с помощью компилятора **AspectJ**:**

```xml
<plugin>
    <groupId>org.codehaus.mojo</groupId>
    <artifactId>aspectj-maven-plugin</artifactId>
    <version>1.14.0</version>
    <configuration>
        <complianceLevel>1.8</complianceLevel>
        <source>1.8</source>
        <target>1.8</target>
        <showWeaveInfo>true</showWeaveInfo>
        <verbose>true</verbose>
        <Xlint>ignore</Xlint>
        <encoding>UTF-8</encoding>
    </configuration>
    <executions>
        <execution>
            <goals>
                <goal>compile</goal>
                <goal>test-compile</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

#### Встраивание после компиляции

Встраивание после компиляции (также иногда называемое двоичным встраиванием)** используется для объединения существующих файлов классов и файлов **JAR.** Как и в случае со встраиванием во время компиляции, аспекты, используемые для встраивания, могут быть в исходной или двоичной форме и сами могут быть составлены из аспектов**.

**Чтобы сделать это с помощью плагина **AspectJ Maven** от **Mojo**, нам нужно настроить все файлы **JAR**, которые мы хотели бы включить в конфигурацию плагина:**

```xml
<configuration>
    <weaveDependencies>
        <weaveDependency>
            <groupId>org.agroup</groupId>
            <artifactId>to-weave</artifactId>
        </weaveDependency>
        <weaveDependency>
            <groupId>org.anothergroup</groupId>
            <artifactId>gen</artifactId>
        </weaveDependency>
    </weaveDependencies>
</configuration>
```

Файлы **JAR**, содержащие классы для встраивания, должны быть указаны как **<dependencies/>** в проекте **Maven**, так и в **<`weaveDependencies`/>** списке **<configuration>** подключаемого модуля **AspectJ Maven**.

#### Встраивание во время загрузки (Load-Time Weaving)

Встраивание во время загрузки (LTW)** — это процесс встраивания несовместимых классов **Java** во время загрузки классов в **JVM.** Для этого требуется агент загрузки классов **AspectJ** для выполнения встраивания**.

Чтобы включить **LTW,** нам нужно запустить **JVM** с параметром **\-javaagent** и указать путь к **aspectjweaver.jar:**

```bash
-javaagent:/path/to/aspectjweaver.jar
```

## JoinPoint против ProceedingJoinPoint

**JoinPoint** — это интерфейс, который предоставляет статическую информацию о точке соединения**. С помощью **JoinPoint** мы можем получить доступ к информации о методе, аргументах, целевом объекте и т**. д.**

**ProceedingJoinPoint** расширяет **JoinPoint** и предоставляет метод **proceed()** для вызова целевого метода**. **ProceedingJoinPoint** используется только в **@**Around** советах**.

```java
@Around("execution(* com.baeldung.service.*.*(..))")
public Object aroundAdvice(ProceedingJoinPoint pjp) throws Throwable {
    // Действия до вызова метода
    Object result = pjp.proceed(); // Вызов целевого метода
    // Действия после вызова метода
    return result;
}
```

В отличие от **ProceedingJoinPoint**, **JoinPoint** не предоставляет метод **proceed()**, поэтому его нельзя использовать для вызова целевого метода**. Однако его можно использовать для получения информации о точке соединения**.

```java
@Before("execution(* com.baeldung.service.*.*(..))")
public void beforeAdvice(JoinPoint jp) {
    String methodName = jp.getSignature().getName();
    Object[] args = jp.getArgs();
    // Логирование информации о методе
}
```

## Сравнение Spring AOP и AspectJ

**Сегодня существует множество доступных библиотек АОП, и они должны отвечать на ряд вопросов:**

1. Совместимо ли оно с моим существующим или новым приложением?
2. Где я могу реализовать АОП?
3. Как быстро он интегрируется с моим приложением?
4. Каковы издержки производительности?

В этой статье мы рассмотрим ответы на эти вопросы и представим **Spring AOP** и **AspectJ** — две самые популярные платформы **AOP** для **Java**.

### Цели и возможности

Проще говоря, **Spring AOP** и **AspectJ** преследуют разные цели.

**Spring AOP** стремится предоставить простую реализацию **AOP** в **Spring IoC** для решения наиболее распространенных проблем, с которыми сталкиваются программисты. Оно не задумано как полное решение АОП — его можно применять только к компонентам, управляемым контейнером **Spring**.

С другой стороны, **AspectJ** — это оригинальная технология АОП, целью которой является предоставление комплексного решения АОП. Он более надежен, но и значительно сложнее, чем **Spring AOP**. Также стоит отметить, что **AspectJ** можно применять ко всем объектам домена.

### Типы встраивания

И **AspectJ**, и **Spring AOP** используют разные типы переплетения, что влияет на их поведение в отношении производительности и простоты использования.

**AspectJ** использует три различных типа плетения:**

- **Встраивание во время компиляции:** компилятор **AspectJ** принимает в качестве входных данных как исходный код нашего аспекта, так и нашего приложения, а на выходе создает файлы связанных классов**.
- **Встраивание после компиляции:** это также известно как двоичное встраивание**. Он используется для объединения существующих файлов классов и файлов **JAR** с нашими аспектами**.
- **Встраивание во время загрузки:** это точно так же, как прежнее двоичное встраивание, с той разницей, что встраивание откладывается до тех пор, пока загрузчик классов не загрузит файлы классов в **JVM.**

Поскольку **AspectJ** использует встраивание времени компиляции и времени загрузки классов, **Spring `AOP` использует встраивание времени выполнения.**

При переплетении во время выполнения аспекты переплетаются во время выполнения приложения с использованием прокси целевого объекта — с использованием либо динамического прокси **JDK,** либо прокси **CGLIB**.

### Внутренняя структура

**Spring AOP** — это платформа АОП на основе прокси. Это означает, что для реализации аспектов целевых объектов будут созданы прокси этого объекта. Это достигается одним из двух способов:**

1. Динамический прокси **JDK** — предпочтительный способ для **Spring AOP**. Всякий раз, когда целевой объект реализует хотя бы один интерфейс, будет использоваться динамический прокси **JDK**.
2. Прокси-сервер **CGLIB** — если целевой объект не реализует интерфейс, можно использовать прокси-сервер **CGLIB.**

**AspectJ, с другой стороны, ничего не делает во время выполнения, поскольку классы компилируются непосредственно с аспектами.**

И поэтому, в отличие от **Spring AOP**, он не требует каких-либо шаблонов проектирования. Чтобы объединить аспекты в коде, он вводит свой компилятор, известный как компилятор **AspectJ** (ajc), с помощью которого мы компилируем нашу программу, а затем запускаем ее, предоставляя небольшую (< `100` КБ) библиотеку времени выполнения.

### Поддерживаемые точки соединения

В разделе **3.3** мы показали, что **Spring AOP** основан на шаблонах прокси. По этой причине ему необходимо создать подкласс целевого класса **Java** и соответствующим образом применить сквозные проблемы.

Но это имеет ограничение**. Мы не можем применять сквозные проблемы (или аспекты) к классам, которые являются «окончательными», потому что их нельзя переопределить, и, следовательно, это приведет к исключению во время выполнения.**

То же самое относится к статическим и финальным методам. К ним нельзя применить аспекты **Spring**, поскольку их нельзя переопределить. Следовательно, **Spring AOP** из-за этих ограничений поддерживает только точки соединения выполнения метода.

**Однако **AspectJ** вплетает сквозные проблемы непосредственно в реальный код перед его выполнением. В отличие от **Spring AOP**, он не требует создания подкласса целевого объекта и, следовательно, поддерживает многие другие точки соединения. Ниже приводится сводка поддерживаемых точек соединения:**

| Точка соединения | Поддержка **Spring AOP** | Поддержка **AspectJ** |
| --- | --- | --- |
| Вызов метода | Нет | Да  |
| Выполнение метода | Да  | Да  |
| Вызов конструктора | Нет | Да  |
| Выполнение конструктора | Нет | Да  |
| Выполнение статического инициализатора | Нет | Да  |
| Инициализация объекта | Нет | Да  |
| Ссылка на поле | Нет | Да  |
| Назначение поля | Нет | Да  |
| Выполнение обработчика | Нет | Да  |
| Выполнение рекомендаций | Нет | Да  |

Также стоит отметить, что в **Spring AOP** аспекты не применяются к методу, вызываемому внутри того же класса.

Это очевидно, потому что когда мы вызываем метод внутри того же класса, мы не вызываем метод прокси, который предоставляет **Spring AOP**. Если нам нужна эта функциональность, нам нужно определить отдельный метод в разных **bean**-компонентах или использовать **AspectJ**.

### Простота использования

**Spring AOP**, очевидно, проще, поскольку между процессом сборки не требуется никакого дополнительного компилятора или программы **Weaver**. Он использует плетение во время выполнения и поэтому легко интегрируется с нашим обычным процессом сборки. Хотя это выглядит просто, оно работает только с **bean**-компонентами, управляемыми **Spring**.

Однако, чтобы использовать **AspectJ**, нам необходимо ввести компилятор **AspectJ** (ajc) и переупаковать все наши библиотеки (если мы не переключимся на посткомпиляцию или встраивание во время загрузки).

Это, конечно, сложнее предыдущего, поскольку в нем представлены **Java**-инструменты **AspectJ** (которые включают в себя компилятор **(ajc)**, отладчик (ajdb)**, генератор документации (ajdoc)**, браузер структуры программы (ajbrowser)**), которые нам необходимо интегрировать либо с нашей **IDE**, либо с инструментом сборки.

### Производительность

Что касается производительности, плетение во время компиляции происходит намного быстрее, чем плетение во время выполнения. **Spring AOP** — это платформа на основе прокси, поэтому прокси создаются во время запуска приложения. Кроме того, на каждый аспект приходится еще несколько вызовов методов, что отрицательно влияет на производительность.

С другой стороны, **AspectJ** встраивает аспекты в основной код перед выполнением приложения, и, таким образом, в отличие от **Spring AOP**, дополнительных накладных расходов во время выполнения не возникает.

По этим причинам тесты показывают, что **AspectJ** почти в **8–35** раз быстрее, чем **Spring AOP**.

### Сравнительная таблица

**В этой краткой таблице суммированы ключевые различия между **Spring AOP** и **AspectJ**:**

| **Spring AOP** | **AspectJ** |
| --- | --- |
| Реализовано на чистой **Java** | Реализовано с использованием расширений языка программирования **Java.** |
| Нет необходимости в отдельном процессе компиляции | Требуется компилятор **AspectJ** (ajc), если не настроен **LTW**. |
| Доступно только плетение во время выполнения | Во время выполнения плетение недоступно**. Поддерживает плетение во время компиляции, после компиляции и во время загрузки. |
| Менее мощный — поддерживает только встраивание на уровне метода. | Более мощный — можно объединять поля, методы, конструкторы, статические инициализаторы, финальные классы**/**методы и т. д. |
| Может быть реализовано только в **bean-**компонентах, управляемых контейнером **Spring.** | Может быть реализован на всех объектах домена. |
| Поддерживает только точки выполнения метода. | Поддержка всех точек |
| Прокси создаются из целевых объектов, и к этим прокси применяются аспекты. | Аспекты вплетаются непосредственно в код перед выполнением приложения (до выполнения).** |
| Гораздо медленнее, чем **AspectJ** | Лучшая производительность |
| Легко учиться и применять | Сравнительно сложнее, чем **Spring AOP**. |

### Выбор между Spring AOP и AspectJ

Если мы проанализируем все аргументы, приведенные в этом разделе, мы начнем понимать, что дело вовсе не в том, что один фреймворк лучше другого**.

**Проще говоря, выбор сильно зависит от наших требований:**

1. **Фреймворк.** Если приложение не использует среду **Spring**, у нас нет другого выбора, кроме как отказаться от идеи использования **Spring AOP**, поскольку оно не может управлять ничем, что находится за пределами контейнера **Spring**. Однако, если наше приложение создано полностью с использованием среды **Spring**, мы можем использовать **Spring AOP**, поскольку его легко изучить и применить.
2. **Гибкость.** Учитывая ограниченную поддержку точек соединения, **Spring AOP** не является полным решением АОП, но решает наиболее распространенные проблемы, с которыми сталкиваются программисты. Хотя если мы хотим копнуть глубже и максимально использовать возможности АОП и хотим получить поддержку широкого спектра доступных точек соединения, тогда **AspectJ** — это выбор.
3. **Производительность.** Если мы используем ограниченные аспекты, то различия в производительности будут незначительными. Но иногда бывают случаи, когда приложение имеет более десятков тысяч аспектов. В таких случаях мы бы не хотели использовать встраивание во время выполнения, поэтому лучше выбрать **AspectJ**. Известно, что **AspectJ** работает в **8–35** раз быстрее, чем **Spring AOP**.
4. **Лучшее из обоих:** обе эти платформы полностью совместимы друг с другом. Мы всегда можем воспользоваться преимуществами **Spring AOP**, когда это возможно, и по-прежнему использовать **AspectJ** для получения поддержки точек соединения, которые не поддерживаются первым.

## Сравнение Interceptor CDI и Spring AspectJ

Шаблон **Interceptor** обычно используется для добавления новых, сквозных функций или логики в приложение и имеет надежную поддержку в большом количестве библиотек**.

В этой статье мы рассмотрим и сравним две основные библиотеки: перехватчики **CDI** и **Spring AspectJ**.

**CDI** официально поддерживается для **Jakarta EE**, но некоторые реализации обеспечивают поддержку использования **CDI** в среде **Java SE**. **Weld** можно рассматривать как один из примеров реализации **CDI**, который поддерживается в **Java SE**.

### Перехватчики CDI

Чтобы использовать **CDI,** нам нужно импортировать библиотеку **Weld** в наш **POM:**

```xml
<dependency>
    <groupId>org.jboss.weld.se</groupId>
    <artifactId>weld-se-core</artifactId>
    <version>3.1.6.Final</version>
</dependency>
```

**Чтобы обозначить классы, которые нам нужно перехватить, давайте создадим привязку перехватчика:**

```java
// CDI привязка перехватчика - маркерная аннотация
@InterceptorBinding
@Target({ METHOD, TYPE })
@Retention(RUNTIME)
public @interface Audited {
}
```

**После того, как мы определили привязку перехватчика, нам нужно определить фактическую реализацию перехватчика:**

```java
// CDI перехватчик для аудита вызовов методов
@Audited
@Interceptor
public class AuditedInterceptor {
    public static boolean calledBefore = false;
    public static boolean calledAfter = false;

    // Метод перехвата - выполняется вокруг целевого метода
    @AroundInvoke
    public Object auditMethod(InvocationContext ctx) throws Exception {
        calledBefore = true;
        Object result = ctx.proceed();  // Вызов целевого метода
        calledAfter = true;
        return result;
    }
}
```

Каждый метод **@AroundInvoke** принимает аргумент **javax.interceptor.`InvocationContext`,** возвращает **java.lang.Object** и может выдать исключение**.

Итак, когда мы аннотируем метод новым интерфейсом **`@Audit`,** сначала будет вызываться **AuditMethod,** и только затем будет запущен целевой метод**.

**Давайте применим созданный перехватчик к некоторой бизнес-логике:**

```java
// Сервис с применением CDI перехватчика
public class SuperService {
    @Audited  // Метод будет перехвачен AuditedInterceptor
    public String deliverService(String uid) {
        return uid;
    }
}
```

Чтобы включить перехватчик **CDI,** необходимо указать полное имя класса в файле **beans.xml,** расположенном в каталоге **META-`INF`:**

```xml
<beans xmlns="http://java.sun.com/xml/ns/javaee"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xsi:schemaLocation="http://java.sun.com/xml/ns/javaee
    http://java.sun.com/xml/ns/javaee/beans_1_2.xsd">
    <interceptors>
        <class>com.baeldung.interceptor.AuditedInterceptor</class>
    </interceptors>
</beans>
```

### Преимущества и недостатки CDI Interceptors

Можно отметить следующие преимущества перехватчиков **CDI:**

1. Это стандартная функция спецификации **Jakarta EE**.
2. Некоторые библиотеки реализаций **CDI** можно использовать в **Java SE**.
3. Может использоваться, когда наш проект имеет серьезные ограничения на сторонние библиотеки**.

**Недостатками перехватчиков **CDI** являются следующие:**

1. Тесная связь между классом, бизнес-логикой и перехватчиком**.
2. Трудно увидеть, какие классы перехватываются в проекте**.
3. Отсутствие гибкого механизма применения перехватчиков к группе методов**.

### Spring AspectJ

**Spring** также поддерживает аналогичную реализацию функций перехватчика с использованием синтаксиса **AspectJ.**

Сначала нам нужно добавить в **POM** следующие зависимости **Spring** и **AspectJ:**

```xml
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context</artifactId>
    <version>5.2.8.RELEASE</version>
</dependency>
<dependency>
    <groupId>org.aspectj</groupId>
    <artifactId>aspectjweaver</artifactId>
    <version>1.9.6</version>
</dependency>
```

Затем мы можем использовать аннотации **AspectJ** для определения аспектов, что обеспечивает большую гибкость, чем перехватчики **CDI.**

### Сравнение

**Основные различия между перехватчиками **CDI** и **Spring AspectJ**:**

1. **Гибкость:** — **Spring AspectJ** предоставляет более гибкий механизм применения аспектов к группам методов через выражения **pointcut**.
2. **Стандартизация:** перехватчики **CDI** являются частью стандарта **Jakarta EE**, тогда как **Spring AspectJ** — частью экосистемы **Spring**.
3. **Производительность:** — **AspectJ** может быть быстрее, так как использует встраивание во время компиляции, тогда как перехватчики **CDI** используют динамическое проксирование во время выполнения.
4. **Сложность:** — **Spring AspectJ** требует более сложной настройки, но предоставляет больше возможностей.

### Аспект-ориентированное кэширование

```java
// Аспект для кэширования результатов методов
@Aspect
@Component
public class CacheAspect {

    private final CacheManager cacheManager;

    public CacheAspect(CacheManager cacheManager) {
        this.cacheManager = cacheManager;
    }

    // Pointcut для методов с @Cacheable
    @Pointcut("@annotation(com.example.Cacheable)")
    public void cacheableMethods() {}

    // Кэширование: проверка кэша перед вызовом метода
    @Around("cacheableMethods() && @annotation(cacheable)")
    public Object handleCaching(ProceedingJoinPoint joinPoint, Cacheable cacheable) throws Throwable {
        String cacheName = cacheable.cacheName();
        String key = generateCacheKey(joinPoint);

        Cache cache = cacheManager.getCache(cacheName);
        Cache.ValueWrapper cachedValue = cache.get(key);

        if (cachedValue != null) {
            return cachedValue.get();  // Возврат из кэша
        }

        Object result = joinPoint.proceed();  // Вызов метода
        cache.put(key, result);  // Сохранение в кэш

        return result;
    }

    // Pointcut для методов очистки кэша
    @Pointcut("@annotation(com.example.CacheEvict)")
    public void cacheEvictMethods() {}

    // Очистка кэша после вызова метода
    @After("cacheEvictMethods() && @annotation(cacheEvict)")
    public void handleCacheEviction(CacheEvict cacheEvict) {
        String cacheName = cacheEvict.cacheName();
        Cache cache = cacheManager.getCache(cacheName);
        cache.clear();
    }

    // Генерация ключа кэша на основе метода и аргументов
    private String generateCacheKey(ProceedingJoinPoint joinPoint) {
        StringBuilder key = new StringBuilder();
        key.append(joinPoint.getTarget().getClass().getSimpleName())
           .append(".")
           .append(joinPoint.getSignature().getName())
           .append("(");

        Object[] args = joinPoint.getArgs();
        for (int i = 0; i < args.length; i++) {
            if (i > 0) key.append(",");
            key.append(args[i] != null ? args[i].toString() : "null");
        }
        key.append(")");

        return key.toString();
    }
}
```

### Аспект для логирования производительности

```java
// Аспект для мониторинга производительности с интеграцией Micrometer
@Aspect
@Component
@Slf4j
public class PerformanceMonitoringAspect {

    private final MeterRegistry meterRegistry;

    public PerformanceMonitoringAspect(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
    }

    // Pointcut для всех методов сервисов
    @Pointcut("execution(* com.example.service.*.*(..))")
    public void serviceMethods() {}

    // Измерение времени выполнения и отправка метрик
    @Around("serviceMethods()")
    public Object monitorPerformance(ProceedingJoinPoint joinPoint) throws Throwable {
        String className = joinPoint.getTarget().getClass().getSimpleName();
        String methodName = joinPoint.getSignature().getName();

        Timer.Sample sample = Timer.start(meterRegistry);  // Старт таймера
        long startTime = System.nanoTime();

        try {
            Object result = joinPoint.proceed();

            long endTime = System.nanoTime();
            long durationMs = (endTime - startTime) / 1_000_000;

            sample.stop(Timer.builder("method.execution.time")
                    .tag("class", className)
                    .tag("method", methodName)
                    .register(meterRegistry));

            if (durationMs > 1000) {
                log.warn("Method {} took {} ms", className + "." + methodName, durationMs);
            } else if (durationMs > 100) {
                log.info("Method {} took {} ms", className + "." + methodName, durationMs);
            }

            return result;

        } catch (Exception e) {
            sample.stop(Timer.builder("method.execution.error")
                    .tag("class", className)
                    .tag("method", methodName)
                    .tag("exception", e.getClass().getSimpleName())
                    .register(meterRegistry));

            throw e;
        }
    }
}
```

### Аспект для валидации

```java
// Аспект для автоматической валидации параметров методов
@Aspect
@Component
public class ValidationAspect {

    private final Validator validator;  // JSR-380 валидатор

    public ValidationAspect(Validator validator) {
        this.validator = validator;
    }

    // Pointcut для методов create* и update*
    @Pointcut("execution(* com.example.service.*.create*(..)) || " +
              "execution(* com.example.service.*.update*(..))")
    public void createOrUpdateMethods() {}

    // Валидация аргументов перед выполнением метода
    @Before("createOrUpdateMethods()")
    public void validateParameters(JoinPoint joinPoint) {
        Object[] args = joinPoint.getArgs();

        for (Object arg : args) {
            if (arg != null) {
                // Проверка на нарушения ограничений
                Set<ConstraintViolation<Object>> violations = validator.validate(arg);
                if (!violations.isEmpty()) {
                    StringBuilder message = new StringBuilder("Validation failed for ")
                            .append(arg.getClass().getSimpleName())
                            .append(": ");

                    for (ConstraintViolation<Object> violation : violations) {
                        message.append(violation.getPropertyPath())
                               .append(" ")
                               .append(violation.getMessage())
                               .append("; ");
                    }

                    throw new ValidationException(message.toString());
                }
            }
        }
    }
}
```

// Аспект для проверки авторизации через кастомную аннотацию
@Aspect
@Component
public class AuthorizationAspect {

    // Pointcut для методов с @RequiresRole
    @Pointcut("@annotation(com.example.RequiresRole)")
    public void securedMethods() {}

    // Проверка наличия требуемой роли у пользователя
    @Before("securedMethods() && @annotation(requiresRole)")
    public void checkAuthorization(RequiresRole requiresRole) {
        Authentication authentication = SecurityContextHolder.getContext().getAuthentication();

        if (authentication == null) {
            throw new AccessDeniedException("Authentication required");
        }

        // Проверка наличия роли
        boolean hasRequiredRole = authentication.getAuthorities().stream()
                .anyMatch(authority -> authority.getAuthority().equals("ROLE_" + requiresRole.value()));

        if (!hasRequiredRole) {
            throw new AccessDeniedException("Required role: " + requiresRole.value());
        }
    }
}

## Решение проблем

### Распространенные проблемы

1. **Аспект не применяется**: Проверьте @**Component** аннотацию
2. **Pointcut не соответствует**: Тестируйте выражения
3. **Циклические зависимости**: Используйте @**Lazy**
4. **Проблемы с прокси**: Вызовы внутри класса не перехватываются

```java
// Аспект для автоматических повторных попыток при ошибках
@Aspect
@Component
@Slf4j
public class RetryAspect {

    // Перехват методов с аннотацией @Retryable
    @Around("@annotation(retryable)")
    public Object retryOnFailure(ProceedingJoinPoint joinPoint, Retryable retryable) throws Throwable {
        int attempts = 0;
        Throwable lastException;

        do {
            try {
                return joinPoint.proceed();  // Попытка выполнения
            } catch (Throwable e) {
                attempts++;
                lastException = e;

                // Проверка на повторную попытку
                if (attempts <= retryable.maxAttempts() &&
                    shouldRetry(e, retryable.retryFor())) {

                    long delay = calculateDelay(attempts, retryable.backoff());
                    log.warn("Attempt {} failed for method {}. Retrying in {} ms",
                            attempts, joinPoint.getSignature(), delay);

                    Thread.sleep(delay);  // Ожидание перед повтором
                } else {
                    break;
                }
            }
        } while (attempts <= retryable.maxAttempts());

        throw lastException;  // Все попытки исчерпаны
    }

    // Проверка: нужно ли повторять для данного исключения
    private boolean shouldRetry(Throwable exception, Class<? extends Throwable>[] retryFor) {
        for (Class<? extends Throwable> retryClass : retryFor) {
            if (retryClass.isAssignableFrom(exception.getClass())) {
                return true;
            }
        }
        return false;
    }

    // Вычисление задержки: exponential backoff + jitter
    private long calculateDelay(int attempt, Backoff backoff) {
        long baseDelay = backoff.multiplier() * (long) Math.pow(2, attempt - 1);
        long jitter = (long) (Math.random() * backoff.maxJitter());
        return Math.min(baseDelay + jitter, backoff.maxDelay());
    }
}

// Аспект Circuit Breaker для защиты от каскадных отказов
@Aspect
@Component
public class CircuitBreakerAspect {

    // Состояния circuit breaker для каждого метода
    private final Map<String, CircuitBreakerState> circuitBreakers = new ConcurrentHashMap<>();

    @Around("@annotation(circuitBreakable)")
    public Object executeWithCircuitBreaker(ProceedingJoinPoint joinPoint,
                                           CircuitBreakable circuitBreakable) throws Throwable {

        String methodKey = joinPoint.getSignature().toString();
        CircuitBreakerState state = circuitBreakers.computeIfAbsent(methodKey,
            k -> new CircuitBreakerState(circuitBreakable));

        // Если circuit breaker открыт - сразу отказ
        if (state.isOpen()) {
            throw new CircuitBreakerOpenException("Circuit breaker is open for " + methodKey);
        }

        try {
            Object result = joinPoint.proceed();
            state.recordSuccess();  // Успех - сбрасываем счётчик
            return result;

        } catch (Exception e) {
            state.recordFailure();  // Ошибка - увеличиваем счётчик
            throw e;
        }
    }

    // Внутренний класс: состояние Circuit Breaker
    static class CircuitBreakerState {
        private final CircuitBreakable config;
        private State currentState = State.CLOSED;  // Начальное состояние
        private int failureCount = 0;
        private long lastFailureTime = 0;

        // Три состояния: CLOSED -> OPEN -> HALF_OPEN -> CLOSED
        enum State { CLOSED, OPEN, HALF_OPEN }

        public CircuitBreakerState(CircuitBreakable config) {
            this.config = config;
        }

        // Проверка состояния с автопереходом в HALF_OPEN
        public synchronized boolean isOpen() {
            switch (currentState) {
                case CLOSED:
                    return false;
                case OPEN:
                    // Проверка таймаута для перехода в HALF_OPEN
                    if (System.currentTimeMillis() - lastFailureTime > config.timeout()) {
                        currentState = State.HALF_OPEN;
                        return false;
                    }
                    return true;
                case HALF_OPEN:
                    return false;
                default:
                    return false;
            }
        }

        // Успешный вызов: сброс в CLOSED
        public synchronized void recordSuccess() {
            failureCount = 0;
            currentState = State.CLOSED;
        }

        // Неуспешный вызов: возможный переход в OPEN
        public synchronized void recordFailure() {
            failureCount++;
            lastFailureTime = System.currentTimeMillis();

            if (failureCount >= config.failureThreshold()) {
                currentState = State.OPEN;
            }
        }
    }
}

@Aspect
@Component
public class EventSourcingAspect {

    private final EventStore eventStore;
    private final ObjectMapper objectMapper;

    // Сохранение событий после успешного выполнения метода @Aggregate
    @AfterReturning(pointcut = "@annotation(com.example.Aggregate)", returning = "result")
    public void storeEvent(JoinPoint joinPoint, Object result) {

                    event.getClass().getName(),
                    objectMapper.writeValueAsString(event),
                    aggregate.getVersion()
                );

                eventStore.append(descriptor);  // Запись в Event Store
            }

            aggregate.markEventsAsCommitted();  // Пометка как зафиксированные
        }
    }

    // Восстановление состояния агрегата из событий
    @Around("@annotation(com.example.ReplayEvents)")
    public Object replayEvents(ProceedingJoinPoint joinPoint) throws Throwable {
        ReplayEvents annotation = getAnnotation(joinPoint, ReplayEvents.class);
        UUID aggregateId = (UUID) joinPoint.getArgs()[0];

        // Получение всех событий для агрегата
        List<EventDescriptor> events = eventStore.getEventsForAggregate(aggregateId);

        // Создание агрегата из событий (Event Replay)
        Object aggregate = reconstructAggregate(events);

        // Вызов метода на восстановленном агрегате
        return joinPoint.getSignature().getName().equals("replay") ?
               aggregate : joinPoint.proceed();
    }

    // Восстановление агрегата путём последовательного применения событий
    private Object reconstructAggregate(List<EventDescriptor> events) throws Exception {
        Object aggregate = null;

        for (EventDescriptor event : events) {
            DomainEvent domainEvent = (DomainEvent) objectMapper.readValue(
                event.getData(), Class.forName(event.getEventType()));

            if (aggregate == null) {
                // Создание начального состояния из первого события
                aggregate = domainEvent.getAggregateType().newInstance();
            }

            // Применение события через рефлексию
            aggregate.getClass()
                .getMethod("apply", domainEvent.getClass())
                .invoke(aggregate, domainEvent);
        }

        return aggregate;
    }
}

@Component
public class MemoryLeakDetectionAspect {

    private final Map<String, WeakHashMap<Object, String>> objectTracker = new ConcurrentHashMap<>();

    // Отслеживание создания крупных объектов

        if (objects.size() > 100) { // Порог: 100 больших объектов
            log.warn("Potential memory leak detected in method: {}. " +
                    "Large objects created: {}", methodKey, objects.size());

            analyzeCreationPattern(objects);  // Детальный анализ
        }

    // Анализ паттерна создания объектов по времени

        // Группировка по минутам
        Map<String, Long> creationTimes = objects.values().stream()

                time -> time.substring(0, 16),
                Collectors.counting()
            ));

        // Предупреждение при высокой частоте создания
        creationTimes.entrySet().stream()
            .filter(entry -> entry.getValue() > 10)
            .forEach(entry -> log.warn("High object creation rate: {} objects/minute at {}",

                metrics.incrementCounter("reactive.stream.error"))
            .doOnComplete(() ->
                metrics.incrementCounter("reactive.stream.completed"));
    }
}
```

### AOP с gRPC

```java
// Аспект для gRPC вызовов: retry, timeout, метрики
@Aspect
@Component
public class GrpcAspect {

    // Перехват клиентских gRPC вызовов
    @Around("execution(* io.grpc.stub.AbstractStub.*(..))")
    public Object grpcClientCall(ProceedingJoinPoint joinPoint) throws Throwable {
        String methodName = joinPoint.getSignature().getName();

        // Обёртка в Mono для retry и timeout
        return Mono.fromCallable(() -> {
            long startTime = System.nanoTime();
            try {
                Object result = joinPoint.proceed();
                recordGrpcCall(methodName, System.nanoTime() - startTime, "SUCCESS");
                return result;
            } catch (Exception e) {
                recordGrpcCall(methodName, System.nanoTime() - startTime, "ERROR");
                throw e;
            }
        })
        .retryWhen(Retry.backoff(3, Duration.ofMillis(100)))  // 3 попытки с backoff
        .timeout(Duration.ofSeconds(30));  // Таймаут 30 секунд
    }

    // Перехват серверных gRPC методов с @GrpcService
    @Around("@annotation(com.example.GrpcService)")
    public Object grpcServiceMethod(ProceedingJoinPoint joinPoint) throws Throwable {
        // Добавление метаданных в gRPC Context
        GrpcService annotation = getAnnotation(joinPoint, GrpcService.class);

        Context.current()
            .withValue(SERVICE_NAME_KEY, annotation.serviceName())
            .withValue(METHOD_NAME_KEY, joinPoint.getSignature().getName())
            .attach();  // Привязка контекста

        try {
            return joinPoint.proceed();
        } finally {
            Context.current().detach();  // Отвязка контекста
        }
    }
}
```

## Заключение и рекомендации

### Когда использовать AOP

✅ **Использовать для:**
- **Cross-cutting concerns** (логирование, безопасность, транзакции)
- Код, который повторяется в нескольких местах
- Функциональность, которую нужно добавить без изменения существующего кода
- Мониторинг и метрики
- Кэширование
- Валидация

❌ **Не использовать для:**
- Бизнес-логики
- Код, специфичный для одного метода
- Сложных алгоритмов
- Когда можно решить через наследование или композицию

### Лучшие практики

1. **Делайте аспекты тестируемыми** — используйте интерфейсы для зависимостей
2. **Избегайте сложных pointcut выражений** — разбивайте на простые
3. **Мониторьте производительность** — аспекты могут добавить **overhead**
4. **Документируйте аспекты** — объясняйте, что и где они перехватывают
5. **Используйте аннотации** — для более декларативного подхода
6. **Тестируйте аспекты** — интеграционные тесты обязательны
7. **Будьте осторожны с транзакциями** — аспекты могут влиять на границы транзакций

### Производительность

- Аспекты добавляют небольшой **overhead** (~10-20% для простых случаев)
- Используйте `@Order` для контроля порядка выполнения аспектов
- Кэшируйте результаты **expensive** проверок в аспектах
- Избегайте создания объектов в **advice** методах
- Используйте **async** аспекты для тяжелых операций
