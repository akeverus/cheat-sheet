## Назначение документа

- Зафиксировать, как должен быть устроен каталог `cheatsheets/`.
- Дать единый стандарт оформления, чтобы не было конфликтующих правил.
- Снизить хаос в навигации, терминологии и структуре документов.
- Сформировать жесткие требования к читаемости и сопровождению.

## Жесткая критика текущего состояния

### 1) Перегруженный системный контур

- Исторически было слишком много служебных `.md` с пересекающимися правилами.
- Один и тот же стандарт описывался в нескольких файлах разными формулировками.
- Это ломало доверие к регламентам: команда не понимала, какой документ главный.

### 2) Историческая несогласованность стандартов

- TOC-формат менялся волнами (нумерованный, смешанный, plain-links), что оставило много технического долга.
- В отчетах долго сохранялись старые формулировки после смены стандарта.
- Обновления делались точечно, а не как единая миграция правил.

### 3) Избыточные монолиты

- Многие документы раздуты и плохо читаются как рабочие шпаргалки.
- В одном файле смешаны обзор, референс, runbook, FAQ и длинные листинги.
- Такой формат ухудшает поддерживаемость: правки сложны, якоря нестабильны, обзор теряется.

### 4) Слабая управляемость жизненного цикла документации

- Нет жесткого SLA на проверку битых ссылок и устаревших секций.
- Нет автоматического quality gate на уровне CI для markdown-качества.
- Нет формального владельца у многих поддеревьев документации.

### 5) Непрозрачная эволюция структуры

- Было много legacy-редиректов и переходных схем.
- Каталог эволюционировал правильно, но процесс был реактивным, а не архитектурным.
- Слишком много ручных pass-ов вместо автоматизируемых проверок.

### 6) Риски для читаемости

- Исторические артефакты кодировки и неравномерный стиль секций снижали качество восприятия.
- В части файлов полезная плотность текста ниже из-за шаблонных или повторяющихся блоков.

## Целевая архитектура репозитория

Архитектура строится вокруг тематических доменов и единых правил качества:

```text
cheatsheets/
├── algorithms/
├── architecture/
├── basics/
├── databases/
├── development/
├── frameworks/
├── interview/
├── languages/
├── libraries/
├── monitoring/
├── patterns/
├── platform/
├── security/
├── testing/
├── tools/
└── CHEATSHEETS_ARCHITECTURE_AND_RULES.md  # единственный системный файл в корне
```

### Принципы организации

- Доменная структура важнее исторических путей.
- Каждый раздел имеет `README.md` как локальную точку входа.
- Внутри разделов не допускаются бессмысленные дубли темы.
- Legacy-папки допустимы только как редирект-контейнеры с явным указанием целевого пути.

## Связь с архитектурными каталогами проекта

Архитектура `cheatsheets/` теперь синхронизируется с остальными базовыми каталогами репозитория:

- `modules/` — код приложения разделен на `quiz-domain`, `quiz-persistence`, `quiz-app`; документация должна отражать фактическую модульную границу.
- `src/` — корневой `src` больше не является источником кода; все ссылки в документации должны вести на `modules/*/src`.
- `gradle/` — версии зависимостей централизованы через `gradle/libs.versions.toml`; при обновлении технологического стека сначала обновляется catalog, затем документация.
- `data/` — runtime-контур стандартизован (`data/db`, `data/cache`, `data/snapshots`, `data/export`, `data/import`); operational-разделы должны использовать эту структуру.
- `prompts/` — вынесен в отдельный контур с `prompts/index.yaml` и `prompts/PROMPTS_RULES.md`; interview-документы должны быть терминологически согласованы с этими промптами.
- `cheatsheets/sheets-pdf/` — PDF-слой формализован через `cheatsheets/sheets-pdf/INDEX.yaml`; каждый PDF должен иметь связку с соответствующим разделом `cheatsheets`.

Любое архитектурное изменение в этих каталогах считается незавершенным без синхронизации этого master-документа.

## Модель документа и типы контента

Каждый документ должен иметь явный тип (по смыслу):

- `overview` — обзор темы и карта переходов.
- `reference` — справочник команд, API, параметров.
- `how-to` — пошаговая инструкция с проверяемым результатом.
- `troubleshooting` — симптомы, диагностика, решение.
- `interview` — Q&A для собеседований (только в `interview/`).

Если файл пытается быть всем сразу, он должен быть разделен.

## Единые правила оформления Markdown

### 1) Frontmatter обязателен

Минимальный контракт:

```yaml
---
title: "Название документа"
description: "Краткое описание назначения документа."
tags:
  - section
  - topic
updated: "YYYY-MM-DD"
---
```

Поле `tags` должно быть YAML-списком, а не JSON-массивом (`tags: [a, b]`) — это требование Obsidian Properties и единый стандарт репозитория.

Допустимы дополнительные поля (`difficulty`, `prerequisites`, `next`, `type`), если они реально используются.

### 2) Обязательный порядок секций (кроме коротких и index-файлов)

1. `# H1`
2. Короткое описание (1-3 абзаца)
3. `## Полезные ссылки`
4. `## Содержание`
5. Тематические разделы (`##` / `###`)
6. `## Лучшие практики` (для крупных тем)
7. `## Решение проблем` (для крупных тем)

### 3) Стандарт TOC (для всех, кроме `interview/`)

- Заголовок TOC: строго `## Содержание`
- Формат строки уровня H2: `- [Раздел](#якорь)`
- Формат строки уровня H3: `  - [Подраздел](#якорь)` (2 пробела + тире)
- Формат строки уровня H4: `    - [Подподраздел](#якорь)` (4 пробела + тире)
- Маркер — строго тире (`-`), без `*`, `1.`, `1.1.`
- TOC строится только по реальным заголовкам, не по комментариям в code-блоках

### 4) Стандарт TOC в `interview/`

- Допускается отдельный формат вопросных оглавлений.
- Общая навигация интервью-кластера ведется через `interview/TOC.md`.

### 5) Код и терминология

- Каждый code-block обязан иметь язык (`bash`, `java`, `yaml`, `sql`, `json`, `text` и т.д.).
- Английские идентификаторы и команды оформляются через обратные кавычки.
- Недопустимы поврежденные маркеры кодировки и мусорные символы.

### 6) Ссылки

- Только относительные внутренние ссылки.
- В `См. также` указывать реальную полезную связь, а не формальные ссылки ради количества.
- Битые внутренние ссылки считаются критическим дефектом.

## Правила читаемости и поддерживаемости

### Читаемость

- Один абзац = одна мысль.
- Таблицы только там, где они улучшают сравнение, а не заменяют объяснение.
- Никакой "воды ради объема"; приоритет у плотности пользы.
- Большие документы должны иметь явные "маршруты чтения" (junior/mid/senior, quick-start, prod-runbook).

### Поддерживаемость

- Изменения в заголовках автоматически требуют пересборки TOC.
- Любая правка должна синхронизировать `updated`.
- Документ >1200 строк проверяется на декомпозицию в дочерние темы.
- Для каждого раздела должен быть владелец (owner) и период ревизии.

## Качество и автоматические проверки

Обязательные проверки в CI:

- markdownlint / style check;
- проверка парности и тегов code-block;
- проверка внутренних ссылок;
- проверка TOC-валидности (якоря совпадают с заголовками);
- проверка фронтматтера (наличие `title`, `description`, `updated`);
- проверка на артефакты кодировки.

Без прохождения quality gate изменения не должны попадать в основную ветку.

## План улучшения архитектуры

### Фаза A — стабилизация структуры

- Удалять системные дубли.
- Держать единый регламент только в этом файле.
- Поддерживать актуальные локальные `README.md` в каждом разделе.

### Фаза B — декомпозиция монолитов

- Разбить чрезмерно большие файлы на обзор + специализированные документы.
- Вынести длинные справочники в `reference`-документы.
- Сократить повторяющийся контент между соседними файлами.

### Фаза C — повышение читаемости

- Ввести единый шаблон "короткого маршрута" в крупных документах.
- Добавить четкие decision guides вместо разрозненных советов.
- Убрать исторические вводные, не дающие практической ценности.

### Фаза D — эксплуатационная поддержка

- Закрепить ownership по каталогам.
- Ввести регулярный аудит качества раз в спринт.
- Вести changelog уровня раздела, а не десятки технических отчетов.

## Definition of Done для любого документа

Документ считается завершенным только если:

- валиден frontmatter и актуальна дата `updated`;
- есть `Полезные ссылки` и `Содержание` в правильном формате;
- TOC соответствует фактическим заголовкам;
- нет битых внутренних ссылок;
- нет артефактов кодировки;
- нет шаблонных пустых блоков;
- контент полезен для практического применения, а не формально "набран".

## Антипаттерны, которые запрещены

- Размножение системных файлов с противоречащими правилами.
- Хранение в репозитории "отчетов ради отчетов", которые не управляют качеством.
- Массовые правки без финальной автоматической валидации.
- Раздутие документов ради формального порога строк.
- Дубли тем между соседними файлами без добавленной ценности.
