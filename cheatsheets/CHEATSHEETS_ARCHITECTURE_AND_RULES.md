## Назначение документа

- Зафиксировать, как должен быть устроен каталог `cheatsheets/`.
- Дать единый стандарт оформления, чтобы не было конфликтующих правил.
- Снизить хаос в навигации, терминологии и структуре документов.
- Сформировать жесткие требования к читаемости и сопровождению.

## Жесткая критика текущего состояния

### 1) Перегруженный системный контур

- Исторически было слишком много служебных `.md` с пересекающимися правилами.
- Один и тот же стандарт описывался в нескольких файлах разными формулировками.
- Это ломало доверие к регламентам: команда не понимала, какой документ главный.

### 2) Историческая несогласованность стандартов

- TOC-формат менялся волнами (нумерованный, смешанный, plain-links), что оставило много технического долга.
- В отчетах долго сохранялись старые формулировки после смены стандарта.
- Обновления делались точечно, а не как единая миграция правил.

### 3) Избыточные монолиты

- Многие документы раздуты и плохо читаются как рабочие шпаргалки.
- В одном файле смешаны обзор, референс, runbook, FAQ и длинные листинги.
- Такой формат ухудшает поддерживаемость: правки сложны, якоря нестабильны, обзор теряется.

### 4) Слабая управляемость жизненного цикла документации

- Нет жесткого SLA на проверку битых ссылок и устаревших секций.
- Нет автоматического quality gate на уровне CI для markdown-качества.
- Нет формального владельца у многих поддеревьев документации.

### 5) Непрозрачная эволюция структуры

- Было много legacy-редиректов и переходных схем.
- Каталог эволюционировал правильно, но процесс был реактивным, а не архитектурным.
- Слишком много ручных pass-ов вместо автоматизируемых проверок.

### 6) Риски для читаемости

- Исторические артефакты кодировки и неравномерный стиль секций снижали качество восприятия.
- В части файлов полезная плотность текста ниже из-за шаблонных или повторяющихся блоков.

## Целевая архитектура репозитория

Архитектура строится вокруг тематических доменов и единых правил качества:

```text
cheatsheets/
├── algorithms/
├── architecture/
├── basics/
├── databases/
├── development/
├── frameworks/
├── interview/
├── languages/
├── libraries/
├── monitoring/
├── patterns/
├── platform/
├── security/
├── testing/
├── tools/
└── CHEATSHEETS_ARCHITECTURE_AND_RULES.md  # единственный системный файл в корне
```

### Принципы организации

- Доменная структура важнее исторических путей.
- Каждый раздел имеет `README.md` как локальную точку входа.
- Внутри разделов не допускаются бессмысленные дубли темы.
- Legacy-папки допустимы только как редирект-контейнеры с явным указанием целевого пути.

## Связь с архитектурными каталогами проекта

Архитектура `cheatsheets/` теперь синхронизируется с остальными базовыми каталогами репозитория:

- `modules/` — код приложения разделен на `quiz-domain`, `quiz-persistence`, `quiz-app`; документация должна отражать фактическую модульную границу.
- `src/` — корневой `src` больше не является источником кода; все ссылки в документации должны вести на `modules/*/src`.
- `gradle/` — версии зависимостей централизованы через `gradle/libs.versions.toml`; при обновлении технологического стека сначала обновляется catalog, затем документация.
- `data/` — runtime-контур стандартизован (`data/db`, `data/cache`, `data/snapshots`, `data/export`, `data/import`); operational-разделы должны использовать эту структуру.
- `prompts/` — вынесен в отдельный контур с `prompts/index.yaml` и `prompts/PROMPTS_RULES.md`; interview-документы должны быть терминологически согласованы с этими промптами.
- `cheatsheets/sheets-pdf/` — PDF-слой формализован через `cheatsheets/sheets-pdf/INDEX.yaml`; каждый PDF должен иметь связку с соответствующим разделом `cheatsheets`.

Любое архитектурное изменение в этих каталогах считается незавершенным без синхронизации этого master-документа.

## Модель документа и типы контента

Каждый документ должен иметь явный тип (по смыслу):

- `overview` — обзор темы и карта переходов.
- `reference` — справочник команд, API, параметров.
- `how-to` — пошаговая инструкция с проверяемым результатом.
- `troubleshooting` — симптомы, диагностика, решение.
- `interview` — Q&A для собеседований (только в `interview/`).

Если файл пытается быть всем сразу, он должен быть разделен.

## Единые правила оформления Markdown

### 1) Frontmatter обязателен

Минимальный контракт:

```yaml
---
title: "Название документа"
description: "Краткое описание назначения документа."
tags:
  - section
  - topic
updated: "YYYY-MM-DD"
---
```

Поле `tags` должно быть YAML-списком, а не JSON-массивом (`tags: [a, b]`) — это требование Obsidian Properties и единый стандарт репозитория.

Допустимы дополнительные поля (`difficulty`, `prerequisites`, `next`, `type`), если они реально используются.

### 2) Обязательный порядок секций (кроме коротких и index-файлов)

1. `# H1`
2. Короткое описание (1-3 абзаца)
3. `## Полезные ссылки`
4. `## Содержание`
5. Тематические разделы (`##` / `###`)
6. `## Лучшие практики` (для крупных тем)
7. `## Решение проблем` (для крупных тем)

### 3) Стандарт TOC (для всех, кроме `interview/`)

- Заголовок TOC: строго `## Содержание`
- Формат строки уровня H2: `- [Раздел](#якорь)`
- Формат строки уровня H3: `  - [Подраздел](#якорь)` (2 пробела + тире)
- Формат строки уровня H4: `    - [Подподраздел](#якорь)` (4 пробела + тире)
- Маркер — строго тире (`-`), без `*`, `1.`, `1.1.`
- TOC строится только по реальным заголовкам, не по комментариям в code-блоках

### 4) Стандарт TOC в `interview/`

- Допускается отдельный формат вопросных оглавлений.
- Общая навигация интервью-кластера ведется через `interview/TOC.md`.

### 5) Код и терминология

- Каждый code-block обязан иметь язык (`bash`, `java`, `yaml`, `sql`, `json`, `text` и т.д.).
- Английские идентификаторы и команды оформляются через обратные кавычки.
- Недопустимы поврежденные маркеры кодировки и мусорные символы.

### 6) Ссылки

- Только относительные внутренние ссылки.
- В `См. также` указывать реальную полезную связь, а не формальные ссылки ради количества.
- Битые внутренние ссылки считаются критическим дефектом.

### 7) Инлайн-форматирование — единые правила

Цель раздела — устранить визуальный шум и обеспечить, чтобы средства выделения реально несли смысл. Эти правила — приоритетный стандарт для всех файлов `cheatsheets/` (кроме `interview/`, где разрешён особый формат Q&A).

#### Иерархия выделения

Средства упорядочены по силе — **используй самое слабое, которое решает задачу**:

| Приём | Когда | Частота |
|-------|-------|---------|
| Обычный текст | По умолчанию | 95% контента |
| `` `код` `` (backticks) | Технический идентификатор | Часто, по необходимости |
| `жирный` | Ключевой термин или вывод абзаца | Макс. 1–2 на абзац |
| `> цитата` | Важное предупреждение / нетривиальный вывод | Макс. 1–2 на документ |
| `*курсив*` | Короткая пометка / подпись | Редко, по необходимости |

Правило: **никогда не комбинируй приёмы на одной фразе**. Нет `` `HashMap` ``, нет `[ссылка](...)`, нет `*`курсив+backticks`*`.

#### Заголовки (`#`, `##`, `###`, `####`)

- **Никакого** жирного внутри заголовков: заголовок уже выделен визуально и логически. `` в заголовке ломает якоря и смотрится шумно.
- Backticks допустимы только если имя — код/идентификатор, и это повышает понимание:
  - Хорошо: `## Аннотация @Transactional`, `## Метод equals()`, `## Конфигурация application.yml`
  - Не нужно: `## `PostgreSQL`: типы индексов` → `## PostgreSQL: типы индексов`
- Не вставляй в заголовки ссылки, эмодзи, нумерацию `1)` или смайлы.
- H1 — название темы из frontmatter-`title`, строка в строку. Не дублируй его жирным в первом абзаце.

**Плохо:**
```markdown
# **PostgreSQL**: типы индексов
## **B-Tree**
## **ORDER** BY
### **1. Constructor Injection** (Рекомендуемый)
```

**Хорошо:**
```markdown
# PostgreSQL: типы индексов
## B-Tree
## ORDER BY
### Constructor Injection
```

#### Жирный — `слово`

Назначение: ключевой термин или ключевой вывод абзаца. Жирный должен быть редким, чтобы работать.

Правила:
- Максимум **1–2 выделения на абзац**. Если выделяешь каждую вторую фразу — читатель перестаёт их видеть.
- **Не выделяй жирным имена продуктов/технологий в потоке текста.** `Java`, `Spring`, `PostgreSQL`, `Kafka`, `Docker` — это просто слова. Имя технологии — термин только при первом определении.
- **Не дублируй с backticks.** Либо термин на русском жирным (`неблокирующий I/O`), либо идентификатор в backticks (`` `CompletableFuture` ``). Формы `` `CompletableFuture` `` и ``CompletableFuture`` запрещены.
- **Не выделяй жирным целый абзац или фразу-предложение.** Если весь абзац нужно выделить — это подзаголовок `###`, а не жирный.
- **Не выделяй жирным часть скобок** (`(проще говоря, ...)` — запрещено).
- Жирный на лейблах-маркерах в начале абзаца поощряется: `Итог:`, `Когда использовать:`, `Правило:`, `Исключение:`, `Внимание:`.
- В определениях терминов допустима форма `- Термин — объяснение.` — она упорядочивает список понятий.

**Плохо:**
```markdown
**PostgreSQL** — это реляционная БД. **MVCC** позволяет **читающим** транзакциям
не блокировать **пишущие**. Виртуальные потоки в **Java 21** блокируют **carrier thread**
при **`synchronized`** — это называется **pinning**.
```

**Хорошо:**
```markdown
PostgreSQL — реляционная БД с MVCC: читающие транзакции не блокируют пишущие.

Виртуальные потоки Java 21 блокируют carrier-поток на `synchronized`-секциях.
Это называется **pinning** — главный подводный камень миграции на Loom.
```

#### Backticks — `` `код` ``

Назначение: код, идентификатор, команда, путь, имя файла, значение.

Когда **уместны**:
- Имена классов, методов, полей, переменных: `HashMap`, `equals()`, `user_id`
- Ключевые слова и модификаторы: `synchronized`, `volatile`, `final`, `sealed`
- Команды и флаги CLI: `git rebase`, `docker run`, `--no-cache`
- SQL-ключевые слова в тексте: `SELECT`, `WHERE`, `JOIN`, `GROUP BY`
- Значения и литералы: `null`, `0`, `'PAID'`, `"UTF-8"`
- Пути, имена файлов и каталогов: `src/main/java`, `application.yml`, `~/.ssh`
- HTTP-статусы, коды: `200 OK`, `429`, `EXIT_CODE`

Когда **не нужны**:
- На упоминании продукта/технологии: `PostgreSQL`, `Spring`, `Kafka` — без backticks
- На общих русских словах: ~~`ответ`~~ → ответ
- На целых фразах, которые не являются кодом: ~~`очень важно`~~ → очень важно
- Внутри ссылок (см. ниже)
- Внутри заголовков, если это не идентификатор

**Плохо:**
```markdown
`PostgreSQL` — это реляционная `БД`. В ней есть `индексы` и `таблицы`.
Оператор `WHERE` работает с `условиями`.
```

**Хорошо:**
```markdown
PostgreSQL — реляционная БД. Индексы строятся командой `CREATE INDEX`,
применяются планировщиком в предикатах `WHERE` и `JOIN`.
```

#### Курсив — `*слово*`

Назначение: лёгкая пометка или подпись. Если не уверен — не используй.

Допустимые случаи:
- Пометка в скобках: *прим.*, *см. ниже*, *здесь и далее*, *не рекомендуется*
- Подпись к схеме/таблице: *Таблица 1. Сравнение алгоритмов*
- Тонкий семантический акцент: «важно *когда*, а не *что*»
- Псевдо-код или имя спецификации, когда backticks не уместны: *RFC 7231*

Правила:
- Синтаксис — звёздочки `*...*`, не подчёркивания `_..._`. Underscore ломается в идентификаторах (`some_var_name`).
- Не используй курсив для английских технических терминов — для них есть backticks.
- Не используй курсив для названий продуктов — это просто текст.

#### Ссылки

Три вида ссылок, каждая со своей ролью.

**1) Внешние ссылки** (документация, книги, статьи):

```markdown
- [PostgreSQL Documentation](https://www.postgresql.org/docs/) — официальная документация
- [Baeldung: Mockito Series](https://www.baeldung.com/mockito-series) — туториалы
```

- Текст ссылки — человекочитаемое имя ресурса.
- Без `backticks`, `жирного`, `*курсива*` внутри `[...]`.
- После закрытия ссылки — тире и короткое пояснение (что читатель там найдёт).

**2) Wikilinks** (связи между файлами внутри `cheatsheets/`):

```markdown
[[postgres-indexes]]
[[postgres-indexes|типы индексов PostgreSQL]]
```

- Использовать для всех внутренних переходов — они формируют граф Obsidian.
- Только имя файла, без пути и расширения.
- Альтернативный текст через `|` — когда нужна другая подпись.
- В секции `См. также` — только wikilinks, без относительных путей.

**3) Относительные markdown-ссылки** — только когда wikilink неприменим:

```markdown
[README проекта](../../README.md)
[файл за пределами cheatsheets/](../../src/main/README.md)
```

**Плохо:**
```markdown
- [`postgres-basics`](postgres-basics.md) — backticks + путь вместо wikilink
- [**Spring** Documentation](https://spring.io) — жирный внутри ссылки
- См. также: [a](a.md) — [b](b.md).  # через тире, не список
```

**Хорошо:**
```markdown
### См. также

- [[postgres-basics]] — установка и базовые команды
- [[postgres-indexes]] — типы индексов и их выбор
- [[postgres-queries]] — выборки, агрегаты, подзапросы
```

#### Блочные цитаты `> `

Назначение: вынесенное предупреждение / исключение из общего правила / важный факт, который нельзя пропустить.

Правила:
- **Максимум 1–2 цитаты на документ.** Если больше — теряется эффект.
- Формат: `> ` + короткая мысль (1–3 предложения).
- Не используй цитаты как «красивую рамку» для очевидного.
- Не используй цитаты для цитирования людей (в технических шпаргалках это редко нужно).

Пример:
```markdown
> `DROP INDEX CONCURRENTLY` не блокирует чтения, но нельзя запускать внутри транзакции — получишь ошибку `cannot run inside a transaction block`.
```

Obsidian callouts (`> [!note]`, `> [!warning]`, `> [!tip]`) допустимы, но не обязательны. Если используешь — держись одного стиля в пределах раздела.

#### Код-блоки

- **Язык обязателен**: ```` ```java ````, ```` ```sql ````, ```` ```bash ````, ```` ```yaml ````, ```` ```json ````, ```` ```text ```` (для ASCII-диаграмм), ```` ```kotlin ````, ```` ```python ````, ```` ```go ````, ```` ```xml ````.
- Без заголовочных «рамочных» комментариев вроде `// Пример использования` в начале — контекст уже дан в абзаце перед блоком.
- Комментарии в коде — только когда объясняют неочевидное.
- Не дублируй в тексте то, что читается в коде: нет «а теперь на 10-й строке вызываем метод X».
- Не вкладывай код-блоки в таблицы (ломают рендер) — выноси до/после таблицы.

#### Таблицы

- Любое сравнение 2+ вариантов = таблица, а не bullet-список.
- Заголовки — 1–2 слова.
- Ячейки — короткие, 1 предложение или 3–5 слов.
- `` `inline code` `` в ячейках — ок; многострочный код — нельзя.
- Жирный в ячейках — не нужен, таблица уже структурирована. Исключение: первая колонка, если это «имя варианта».

#### Списки

- Маркер — только тире `-`. Не `*`, не `+`, не `•`.
- Нумерованные `1.` — только для шагов, где порядок важен.
- Не выделяй жирным первое слово каждого пункта — если все пункты равнозначны, жирный обесценивается.
- Исключение: список определений, где формат «термин — расшифровка»: `- Stateless — состояние не хранится между вызовами.`

#### Лейблы-маркеры перед ответом

Формат `Лейбл:` в начале абзаца. Допустимые и полезные лейблы:

- `Итог:` — короткий вывод после сравнения/анализа.
- `Когда использовать:` — рекомендация.
- `Когда не использовать:` / `Антипаттерн:` — антирекомендация.
- `Правило:` — формулировка обязательного требования.
- `Исключение:` — случай, когда правило не работает.
- `Внимание:` / `Осторожно:` — блокер, подводный камень.
- `Пример:` — когда следом не сразу код-блок, а развёрнутый сценарий.

Без эмодзи и восклицательных знаков.

#### Горизонтальные разделители `---`

- Не используй `---` между разделами — заголовки `##` уже их разделяют.
- Допустимо: между описанием и TOC; в `interview/` между вопросами.

#### Что запрещено явно

- Жирный на заголовках любого уровня (`# Title`, `## Section`).
- Backticks на названиях технологий вне кода (`` `PostgreSQL` `` в потоке текста).
- Жирный внутри ссылок (`[text](url)`).
- Backticks внутри ссылок на wikilinks / внутренние файлы (`[[file]]`).
- Комбинация жирного и backticks на одной фразе (`` `CREATE INDEX` ``).
- Жирный или backticks внутри скобок на часть фразы (`(только PostgreSQL)`, `(`important`)`).
- Курсив через `_..._` (ломается на идентификаторах с подчёркиванием).
- Разделы в `## Полезные ссылки` с названием продукта/сайта (`### Baeldung`, `### Oracle`) — используй `### Официальная документация`, `### Обучающие материалы`, `### Книги`, `### См. также`.

#### Русская типографика

Шпаргалки читают русскоязычные инженеры — типографика должна соответствовать нормам русского языка, а не копировать стиль английских источников.

**Тире и дефис.** Три разных знака, у каждого своя роль:

| Символ | Имя | Где использовать | Пример |
|--------|-----|------------------|--------|
| `-` | дефис | Внутри слов и составных терминов | `client-server`, `B-Tree`, `read-through` |
| `–` (U+2013) | короткое тире | В диапазонах чисел и дат, без пробелов | `2020–2025`, `pp. 10–14` |
| `—` (U+2014) | длинное тире | В прозе между частями предложения, с пробелами | `PostgreSQL — реляционная БД.` |

Правила:
- В русском тексте между словами ставь длинное тире `—` с пробелами с обеих сторон: `Индекс — это структура…`. Никогда не используй `--` или одиночный дефис с пробелами (`слово — слово`).
- В bullet-списках вида `- Термин — расшифровка` — тоже длинное тире.
- В заголовках и подписях длинное тире допустимо, но не обязательно.
- В коде, путях, URL и идентификаторах — только дефис `-`. Длинное тире ломает команды и имена файлов.
- Короткое тире `–` — только в диапазонах: `5–10 мс`, `Java 11–21`, `2020–2025`.

**Плохо:**
```markdown
Индекс - это структура данных.
Размер пула - 5-10 соединений.
Версии Java 11 - 21 поддерживаются.
Ответ - ждать таймаут 30 - 60 секунд.
```

**Хорошо:**
```markdown
Индекс — это структура данных.
Размер пула — 5–10 соединений.
Версии Java 11–21 поддерживаются.
Ответ — ждать таймаут 30–60 секунд.
```

**Кавычки.** Для русского текста — «ёлочки», для внутренних — „лапки". Прямые `"..."` — только в коде, путях, строковых литералах.

| Тип | Символы | Где | Пример |
|-----|---------|-----|--------|
| Внешние русские | `«»` | Русская проза | «паттерн Strategy», «горячий путь» |
| Внутренние русские | `„"` | Цитата внутри цитаты | «он сказал „всё работает", но нет» |
| Прямые двойные | `"..."` | Код, пути, JSON, YAML | `"application/json"` |
| Прямые одинарные | `'...'` | SQL-литералы, shell | `WHERE status = 'PAID'` |

Правила:
- Не используй прямые `"..."` для русского текста — это шум, оставшийся от английских источников.
- Не смешивай `"..."` и `«...»` в одном документе.
- Английские слова в русском тексте всё равно берутся в «ёлочки»: «паттерн `Observer`».

**Плохо:**
```markdown
Паттерн "Стратегия" применяется для "подмены" алгоритмов.
В терминах DDD это называется "Aggregate Root".
```

**Хорошо:**
```markdown
Паттерн «Стратегия» применяется для подмены алгоритмов.
В терминах DDD это называется «Aggregate Root».
```

**Прочие типографические знаки.** Явный стандарт:

- Многоточие — три точки `...`, не символ `…` (U+2026). Три точки проще редактировать и надёжнее в diff.
- Знак умножения в размерах — `×` (U+00D7), не `x`: `1920×1080`, `3×CPU`.
- Неразрывный пробел — не используй без необходимости (ломает переносы в рендерах).
- Стрелки — только в диаграммах Mermaid / ASCII-таблицах, не в прозе. В тексте пиши словами («ведёт к», «превращается в», «→» только в именах потоков: `Parser → Optimizer`).

#### Эмодзи и спец-символы

**Полный запрет на эмодзи и декоративные символы во всём контенте `cheatsheets/`**, кроме случаев, когда они — часть самой темы (например, файл про эмодзи-реакции или спецификацию Unicode).

Запрещены в заголовках, тексте, списках, таблицах, код-комментариях:

- Эмодзи: 🚀 🎯 ✅ ❌ ⚠️ 💡 📌 🔥 ⭐ и любые другие.
- Галочки и крестики: ✓ ✔ ✗ ✘ (используй `- [x]` / `- [ ]` для чек-листов).
- Декоративные символы: ➤ ▶ ★ ◆ ● ■ ♦ ❯.
- Стрелки в прозе: → ← ↑ ↓ ⇒ ⇐ (в диаграммах — можно).
- «Красивые» скобки: 【 】 〔 〕 ⟨ ⟩.

Почему:
- Эмодзи плохо отображаются в терминале, логах, diff-инструментах.
- Они не добавляют информации, только визуальный шум.
- Скринридеры читают их полными именами («красный круг», «галочка») — это мешает.
- Фильтры на «маркетинговый тон» часто срабатывают на `🚀` и `💡`.

**Разрешено** и поощряется:
- `- [ ]` и `- [x]` в чек-листах (GitHub Flavored Markdown).
- Символы в коде, если они часть синтаксиса (`→` в Scala/Haskell, `λ` в лямбда-выражениях).
- Символы в Mermaid-диаграммах.
- Математические символы в формулах: `O(n log n)`, `±`, `≈`, `≤`, `≥`.

**Лейблы-маркеры без эмодзи** — используй текст: `Внимание:`, `Осторожно:`, `Важно:`, а не `⚠️ Внимание!`.

#### Диаграммы — Mermaid vs ASCII

**Стандарт: Mermaid.** ASCII-«ящики» (`┌─┐`, `│ │`, `└─┘`) — запрещены в новых файлах и должны переводиться в Mermaid при редактировании старых.

Почему Mermaid:
- Рендерится в GitHub, Obsidian, большинстве Markdown-просмотрщиков.
- Работает на мобильных без горизонтального скролла.
- Доступен для скринридеров (описание через `accTitle` / `accDescr`).
- Легко редактируется, не ломается от одного лишнего пробела.
- ASCII-диаграммы с моноширинными рамками шире 80 символов ломают вёрстку в узких рендерах.

**Типы Mermaid-диаграмм и когда какой:**

| Тип | Когда | Пример темы |
|-----|-------|-------------|
| `flowchart` | Поток данных, архитектурные связи | Запрос от клиента до БД |
| `sequenceDiagram` | Взаимодействие сервисов во времени | OAuth2 flow, SAGA |
| `stateDiagram-v2` | Жизненный цикл объекта | Статусы заказа, TCP-состояния |
| `classDiagram` | Доменная модель, иерархия классов | DDD-агрегаты, паттерны GoF |
| `erDiagram` | Схема БД | Связи таблиц |
| `gantt` | Последовательность работ / фаз | Roadmap раздела |

Правила оформления:
- Каждая диаграмма имеет подпись (обычный абзац до или подпись `*Рис. 1: поток запроса*` под ней).
- 1–3 диаграммы на крупный файл; больше — визуальный шум.
- Не дублируй в диаграмме то, что уже ясно из текста.
- Подписи нод — короткие (1–3 слова), без эмодзи, без жирного.
- Для длинных диаграмм — разбей на несколько небольших.

**Плохо** (ASCII-диаграмма):
```text
┌─────────────┐     ┌──────────┐     ┌──────────┐
│   Client    │ ──> │  Server  │ ──> │ Database │
└─────────────┘     └──────────┘     └──────────┘
```

**Хорошо** (Mermaid):
````markdown
```
flowchart LR
    Client --> Server --> Database
```text
```

**Исключение.** Очень простые ASCII-структуры (дерево каталогов, план файла) — допустимы в блоке ```` ```text ```` и только если они **реально** нужны:

````markdown
```
cheatsheets/
├── algorithms/
├── databases/
└── CHEATSHEETS_ARCHITECTURE_AND_RULES.md
```text
```

#### Длина строки и пробелы

**Мягкий лимит — 120 символов** для строк markdown-текста. Помогает читаемости в diff-инструментах и на узких экранах.

Правила:
- Прозаические абзацы пиши с переносом на ~100 символах — облегчает ревью diff.
- Длинные URL в markdown-ссылках `[текст](url)` — не обязаны укладываться в лимит.
- Таблицы и код-блоки — не обязаны.
- Frontmatter поле `description` — одна строка, без принудительных переносов.
- Заголовки — не длиннее 80 символов; если не влезает — упрощай формулировку.

**Пробелы:**
- Один пробел после `-` в списках, одна пустая строка между секциями.
- **Не используй два пробела в конце строки** для принудительного `<br>`. Если нужен перенос — начни новый абзац.
- Trailing whitespace запрещён (убирается по сохранению).
- Между заголовком `##` и следующим блоком — одна пустая строка.
- Между блоками одного раздела — одна пустая строка. Две пустых строки — не нужны.

**Горизонтальные разделители `---`.** Дополнение к правилу выше: не используй их между секциями, между заголовком и текстом, в конце файла. В `interview/` — допустимо между вопросами.

#### Изображения

Если используешь изображение:

- **Путь.** В `cheatsheets/assets/<раздел>/<имя>.png` (или `.svg`, `.jpg`). Не размещай картинки рядом с `.md`-файлом — это загрязняет тематические папки.
- **Alt-текст.** Обязателен: `![краткое описание того, что на картинке](../../assets/databases/pg-architecture.png)`. Не дублируй заголовок соседнего абзаца.
- **Размер.** Ширина — не больше 1200 px. Больше — бессмысленно в рендере и раздувает репозиторий.
- **Формат.** Для схем и диаграмм — `.svg` (масштабируется). Для скриншотов — `.png`. `.jpg` — только для фото.
- **Скриншоты.** Без аннотаций жёлтыми стрелками и кружочками — такие быстро устаревают. Если нужно указать элемент — сделай это текстом рядом.
- **Диаграммы.** Предпочтительно Mermaid inline, а не экспорт в PNG. Исключение — редкие случаи, когда Mermaid не тянет (сложные инфографики).

**Плохо:**
```markdown
![](pg-architecture.png)  <!-- пустой alt -->
![Картинка](./pg.png)      <!-- путь рядом с .md, неинформативный alt -->
```

**Хорошо:**
```markdown
![PostgreSQL: компоненты сервера от connection pool до WAL](../../assets/databases/postgres/pg-architecture.svg)
```

#### Чек-лист инлайн-форматирования

Перед коммитом пройди по файлу:

- [ ] В заголовках нет ``, есть только текст и, при необходимости, `` `идентификаторы` ``.
- [ ] Жирный в абзаце — 0, 1 или 2 раза. Не больше.
- [ ] Имена технологий (`PostgreSQL`, `Spring`, `Kafka`) в потоке текста — без backticks и без жирного.
- [ ] Нет `` `...` `` и ``...`` — комбинаций выделений.
- [ ] Внутри `[...]` нет `` / `*` / `` ` ``.
- [ ] Ссылки между файлами `cheatsheets/` оформлены как `[[wikilinks]]`, а не как `[text](path.md)`.
- [ ] Секция `См. также` — список (`-`), а не фраза через тире.
- [ ] Каждый код-блок начинается с языка (```` ```java ````), ни одного ```` ``` ```` без тега.
- [ ] Таблицы используются везде, где есть сравнение / выбор.
- [ ] Курсив используется 0–3 раза на файл и только для пометок.
- [ ] Блочных цитат `> ` не больше 1–2 на файл.
- [ ] В `## Полезные ссылки` разделы названы по роли ресурса (`Официальная документация`, `Обучающие материалы`, `Книги`, `См. также`), а не по имени сайта (`Baeldung`).
- [ ] В русском тексте — длинное тире `—` с пробелами, не `-` и не `--`. В диапазонах — короткое `–` без пробелов.
- [ ] Русские кавычки — «ёлочки», не `"..."`. Прямые `"..."` только в коде/путях.
- [ ] Нет эмодзи, декоративных символов (✅ ⚠️ 🚀 → ★ и т. п.) — ни в заголовках, ни в тексте.
- [ ] Нет ASCII-диаграмм `┌─┐ │ │ └─┘` — переведены в Mermaid.
- [ ] Mermaid-диаграмм — 0–3 на файл, каждая с подписью.
- [ ] Длинные прозаические строки разбиты на ~100–120 символов для читаемости diff.
- [ ] Нет trailing whitespace, нет двух пробелов в конце строки для `<br>`, нет тройных пустых строк.
- [ ] Нет `---` между секциями (за исключением `interview/`).
- [ ] Изображения лежат в `cheatsheets/assets/<раздел>/`, имеют осмысленный alt-текст.

## Правила читаемости и поддерживаемости

### Читаемость

- Один абзац = одна мысль.
- Таблицы только там, где они улучшают сравнение, а не заменяют объяснение.
- Никакой «воды ради объема»; приоритет у плотности пользы.
- Большие документы должны иметь явные «маршруты чтения» (junior/mid/senior, quick-start, prod-runbook).

### Поддерживаемость

- Изменения в заголовках автоматически требуют пересборки TOC.
- Любая правка должна синхронизировать `updated`.
- Документ >1200 строк проверяется на декомпозицию в дочерние темы.
- Для каждого раздела должен быть владелец (owner) и период ревизии.

## Качество и автоматические проверки

Обязательные проверки в CI:

- markdownlint / style check;
- проверка парности и тегов code-block;
- проверка внутренних ссылок;
- проверка TOC-валидности (якоря совпадают с заголовками);
- проверка фронтматтера (наличие `title`, `description`, `updated`);
- проверка на артефакты кодировки.

Без прохождения quality gate изменения не должны попадать в основную ветку.

## План улучшения архитектуры

### Фаза A — стабилизация структуры

- Удалять системные дубли.
- Держать единый регламент только в этом файле.
- Поддерживать актуальные локальные `README.md` в каждом разделе.

### Фаза B — декомпозиция монолитов

- Разбить чрезмерно большие файлы на обзор + специализированные документы.
- Вынести длинные справочники в `reference`-документы.
- Сократить повторяющийся контент между соседними файлами.

### Фаза C — повышение читаемости

- Ввести единый шаблон «короткого маршрута» в крупных документах.
- Добавить четкие decision guides вместо разрозненных советов.
- Убрать исторические вводные, не дающие практической ценности.

### Фаза D — эксплуатационная поддержка

- Закрепить ownership по каталогам.
- Ввести регулярный аудит качества раз в спринт.
- Вести changelog уровня раздела, а не десятки технических отчетов.

## Definition of Done для любого документа

Документ считается завершенным только если:

- валиден frontmatter и актуальна дата `updated`;
- есть `Полезные ссылки` и `Содержание` в правильном формате;
- TOC соответствует фактическим заголовкам;
- нет битых внутренних ссылок;
- нет артефактов кодировки;
- нет шаблонных пустых блоков;
- контент полезен для практического применения, а не формально «набран».

## Антипаттерны, которые запрещены

- Размножение системных файлов с противоречащими правилами.
- Хранение в репозитории «отчетов ради отчетов», которые не управляют качеством.
- Массовые правки без финальной автоматической валидации.
- Раздутие документов ради формального порога строк.
- Дубли тем между соседними файлами без добавленной ценности.
