# Вопросы на собеседовании: ИИ-агенты

**AI agent** — система, в которой модель выбирает следующие шаги задачи с учётом результатов предыдущих действий. Ниже разобраны ReAct, использование инструментов, память, взаимодействие нескольких агентов, проверка качества и границы конкретных фреймворков. Версии API и доступные возможности нужно сверять с документацией выбранного провайдера.

## Q1. (!) Что такое AI agent?

**AI agent** в контексте LLM-приложений — система, где модель выбирает следующий шаг по текущей задаче и результатам предыдущих шагов. Шагом может быть вызов инструмента, обращение к данным, изменение плана или финальный ответ. Приложение исполняет выбранные действия и возвращает наблюдения модели.

Агенту не обязателен заранее составленный полный план. Важен управляемый цикл принятия решений: модель может менять маршрут в зависимости от наблюдений, а приложение задаёт инструменты, разрешения и условия остановки. Один вызов модели с инструментом ещё не обязательно делает всю систему агентом.

Агентный подход полезен, когда последовательность действий заранее неизвестна, например при исследовании темы или решении задачи в меняющейся среде. Для известной последовательности шагов обычно достаточно workflow.

## Q2. (!) Workflows vs Agents — классификация Anthropic

Anthropic различает **workflow** и **agent** по тому, кто задаёт маршрут работы. В workflow вызовы модели и инструментов организует код по заранее определённой схеме. Схема может включать ветвления, параллельные шаги и проверки; она не обязана быть одной линейной цепочкой. В agent-маршруте модель сама динамически решает, какой шаг сделать следующим.

```text
Workflow: код выбирает узел → модель выполняет ограниченную задачу → код выбирает следующий узел
Agent: модель выбирает действие → приложение исполняет → модель учитывает результат и выбирает снова
```

Anthropic советует начинать с простого решения и добавлять автономный цикл, если он даёт измеримый выигрыш на целевой задаче. Разница не определяется размером модели или самим наличием инструментов.

Источник: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).

## Q3. (!) Когда нужен agent, а когда хватает простого LLM?

Выбор зависит от того, сколько решений о маршруте действительно нужно отдать модели.

- **Один вызов LLM** подходит для перевода, классификации, суммаризации или генерации, если нужный контекст уже доступен.
- **Workflow** подходит, когда порядок действий и развилки можно описать кодом: извлечь данные, проверить условия, вызвать модель и записать результат.
- **Agent** нужен, когда следующий шаг зависит от непредсказуемого результата предыдущего и заранее не удаётся задать все ветви.

Доступ к поиску, БД или другому инструменту сам по себе не требует агента: workflow тоже может вызывать инструменты. Сравнивают качество, стоимость, задержку и сложность отладки на реальных задачах, начиная с простого варианта.

## Q4. (!) Как работает паттерн ReAct (Reasoning + Acting)?

**ReAct** — предложенный Yao и соавторами способ чередовать рассуждение, действие и наблюдение. После результата действия модель может скорректировать следующий шаг вместо исполнения неизменного плана.

```text
Нужно узнать статус заказа → запросить заказ → получить статус
Нужно уточнить доставку → запросить данные доставки → подготовить ответ
```

В современных API этот цикл может быть выражен структурированными вызовами инструментов: приложение получает tool call, исполняет его и возвращает результат модели. Внутренние рассуждения модели при этом могут быть скрыты; формат `Thought` из статьи не обязан появляться в пользовательском логе. Цикл ограничивают числом шагов, временем и разрешениями на действия.

Источник: [ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629).

## Q5. Как устроен паттерн Plan-and-Execute?

**Plan-and-Execute** разделяет планирование и выполнение: сначала составляют план подзадач, затем исполняют шаги и собирают результат. В отличие от ReAct, явный план появляется до первого действия. Исполнитель может использовать модель или обычный код; отдельная «дорогая» модель не является обязательной частью паттерна.

План помогает контролировать порядок и видеть прогресс. Если наблюдения меняют исходные предпосылки, реализация может перепланировать оставшиеся шаги. Полностью фиксированный план проще, но может привести к неверному результату после неожиданного ответа инструмента. Выбор между этим паттерном и ReAct зависит от задачи, а не от гарантированной разницы в цене или качестве.

## Q6. (!) Что такое tool use (function calling)?

**Tool use / function calling** связывает модель с функциями приложения. Разработчик описывает доступные вызовы и параметры, модель возвращает выбранный вызов с аргументами, приложение проверяет их и исполняет действие, затем передаёт результат модели. Модель не выполняет клиентскую функцию сама.

Для OpenAI function tools вход описывается JSON Schema; `tool_choice` управляет выбором инструмента. Помимо function tools существуют другие типы инструментов, в том числе custom tools со свободным текстовым вводом. Строгое соответствие схеме требует совместимой схемы и настройки `strict`; даже при ней приложение проверяет полномочия и смысл аргументов перед действием. Точный формат запроса зависит от API и версии модели.

Источник: [OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling).

## Q7. (!) Какие tools предоставляют агентам?

Инструмент даёт агенту доступ к данным или действию за пределами текстового ответа модели. Это могут быть поиск по документам, web, чтение БД, вызов API, выполнение кода, работа с файлами, отправка сообщения или управление интерфейсом. Набор выбирают по задаче и полномочиям пользователя, а не по максимальному числу доступных интеграций.

Для каждого инструмента описывают назначение, вход, выход и ошибки. Приложение проверяет аргументы и разрешения, ограничивает ресурсы опасных операций и логирует результат. Возвращаемые данные могут быть структурированными или текстовыми; важно, чтобы формат был понятен и проверяем. Содержимое документа или web-страницы остаётся недоверенными данными даже после чтения через инструмент.

## Q8. (!) Как использовать выполнение кода как tool?

**Code execution** как инструмент позволяет приложению запустить код, предложенный моделью, и вернуть результат вычисления. Это полезно для расчётов, анализа таблиц, построения графиков и проверки небольших алгоритмов. Исполнение происходит вне модели, в выбранной среде.

Недоверенный код запускают с границами: ограничивают время, память, файловый доступ и сеть по потребностям задачи. Полный запрет сети подходит для многих вычислений, но не является частью определения инструмента. Изоляция должна учитывать доступ к секретам, файловой системе и последствия вызова; один таймаут не обеспечивает безопасность.

Источник: [AutoGen Code Execution](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/code-execution-groupchat.html).

## Q9. Как использовать web-поиск как tool?

Web-поиск нужен, когда ответ зависит от меняющихся фактов или от источника, которого нет в переданном контексте. Инструмент может вернуть ссылки, фрагменты страниц или подготовленный ответ — точный формат зависит от провайдера.

Для проверяемого вывода агенту нужны первичные страницы и дата публикации или изменения факта. Сниппет помогает выбрать источник, но не всегда содержит нужный контекст; страницу открывают, когда требуется точная формулировка, число или ограничение. Результат поиска и текст страницы считаются внешними данными и могут содержать попытку prompt injection.

## Q10. (!) Что такое MCP (Model Context Protocol)?

**Model Context Protocol (MCP)** — открытый протокол обмена между AI-клиентом и сервером, предоставляющим инструменты, ресурсы и промпты. Это позволяет реализовать интеграцию с сервисом через общий протокол и подключать её к совместимым клиентам. Совместимость зависит от версии протокола, поддерживаемых возможностей, аутентификации и настроек доступа.

В спецификации **2025-11-25** сообщения кодируются JSON-RPC; стандартные транспорты — `stdio` и `Streamable HTTP`. Старый HTTP+SSE транспорт относится к более ранней версии и сохраняется как вариант совместимости. MCP не выполняет действия за модель: клиент выбирает и вызывает доступный инструмент, а сервер обрабатывает запрос по своим полномочиям.

Источник: [MCP specification, transports 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

## Q11. (!) Чем отличается short-term память от long-term?

**Краткосрочная память** — состояние, доступное агенту в текущем выполнении: сообщения, промежуточные результаты и рабочие заметки. Часть этого состояния может храниться вне запроса и снова подгружаться; оно не обязано полностью находиться в одном prompt. **Долгосрочная память** — записи, которые система сохраняет для следующих запусков: факты, предпочтения или результаты прошлой работы.

Различие задаёт срок и способ использования данных, а не размер context window. Увеличение окна не превращает историю в надёжную долгосрочную память. При сохранении учитывают источник факта, срок актуальности, доступ пользователя и возможность удалить запись.

Источник: [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents).

## Q12. Как обрезать историю разговора при заполнении контекста?

Когда история превышает бюджет контекста, можно сохранить последние сообщения, сжать старые в резюме, извлечь релевантные фрагменты из хранилища или сочетать эти способы. Метод выбирают по тому, какие детали нужны для продолжения задачи.

Обрезка должна сохранять действующие инструкции, ограничения, незавершённые действия и идентификаторы, необходимые для ответа инструментов. Резюме может потерять важный факт, а семантический поиск — не найти нужную запись. После сжатия проверяют реальное число токенов; повторять суммаризацию без гарантии уменьшения размера нельзя.

## Q13. Что такое vector memory (RAG для памяти)?

**Vector memory** хранит записи прошлых взаимодействий вместе с эмбеддингами и ищет близкие по смыслу записи к новому запросу. Извлечённые фрагменты добавляют в контекст по принципу RAG. Это один из способов долгосрочного хранения, а не обязательная форма памяти любого агента.

Семантическая близость не доказывает истинность и актуальность записи. Поэтому поиск ограничивают областью доступа пользователя, сохраняют исходный текст и метаданные, проверяют устаревание и при необходимости дают исправить или удалить запись. Для точных идентификаторов и дат может быть полезнее обычный фильтр или полнотекстовый поиск.

## Q14. (!) Что такое multi-agent system?

**Multi-agent system** использует нескольких агентов или специализированных исполнителей для одной задачи. Они могут работать последовательно, параллельно, через координатора или общее состояние. Специализация помогает, если подзадачи действительно независимы либо требуют разных инструментов и контекстов.

Цена — дополнительные вызовы модели, передача контекста, согласование результатов и более сложная отладка. Параллельность может уменьшить общее время только у независимых шагов; последовательные шаги увеличивают задержку. Несколько агентов не гарантируют повышение качества: сравнивать нужно с простым workflow или одним агентом на измеримых задачах.

## Q15. Как работает паттерн Supervisor?

В **supervisor pattern** координатор выбирает подходящего исполнителя для подзадачи, передаёт ему вход и принимает результат. Он может повторить маршрутизацию, проверить результат или собрать итоговый ответ; роль не сводится только к первому выбору worker.

Маршрутизация полезна при разных навыках и инструментах исполнителей. Для фиксированного правила выбора можно использовать обычный код без отдельного LLM-супервизора. Если координатор ошибается, нужен способ заметить неверный маршрут и исправить его, иначе добавленный уровень лишь увеличит стоимость и задержку.

## Q16. Что такое иерархические агенты (hierarchical agents)?

**Иерархическая система агентов** делит работу на несколько уровней: верхний координатор распределяет крупные части, нижние координаторы разбивают их дальше, исполнители возвращают результаты вверх. Это подходит для задач с настоящей многоуровневой структурой и контролируемыми интерфейсами между частями.

Каждый уровень требует передать ограничения, исходные данные и критерии приёмки. Ошибка или потеря контекста при делегировании может размножиться по ветвям. Глубину и число исполнителей выбирают по измеренной пользе; ни универсальной схемы, ни подтверждённой общей доли таких систем в production нет.

## Q17. (!) Какие бывают паттерны коммуникации между агентами?

Агенты могут обмениваться сообщениями напрямую, читать и обновлять общее состояние, реагировать на события или собирать несколько предложений для выбора. Эти схемы можно сочетать: например, координатор передаёт подзадачу сообщением, а результаты сохраняются в общем состоянии.

Для общего состояния нужны правила конкурентной записи и права доступа. Для событийного обмена — трассировка причин и повторов. Голосование и debate дают дополнительную проверку только при независимых подходах и подходящем критерии выбора; согласие нескольких агентов само по себе не доказывает правильность.

LangGraph строит процесс вокруг графа состояния. AutoGen поддерживает сообщения между агентами и runtime для их обработки; сводить любую реализацию каждого фреймворка к одной схеме общения нельзя.

## Q18. (!) Что такое LangGraph (от LangChain)?

**LangGraph** — фреймворк оркестрации долгоживущих процессов с явным состоянием. В `StateGraph` узлы выполняют шаги, рёбра задают переходы, а условные рёбра позволяют выбрать следующий узел. В одном графе можно сочетать обычный код и вызовы LLM. Для цикла агента после вызова модели переходят к инструментам только при наличии tool call; иначе завершают граф.

```text
START → agent
agent -- есть tool call --> tools → agent
agent -- готов ответ ----> END
```

Граф полезен, когда нужны управляемые ветвления, восстановление состояния, наблюдаемость и пауза перед действием. Само использование графа не делает агента лучше: простую цепочку из нескольких шагов можно реализовать без фреймворка.

Источник: [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview).

## Q19. Что такое AutoGen (от Microsoft)?

**AutoGen** — фреймворк Microsoft для приложений с агентами. В актуальном интерфейсе `AgentChat` есть `AssistantAgent`, команды агентов и условия остановки. Обмен сообщениями — один из способов координации; отдельно существует более низкоуровневый `Core` с агентным runtime.

Выполнение кода и участие человека подключаются отдельными агентами и настройками, а не возникают автоматически у каждого `AssistantAgent`. Например, `CodeExecutorAgent` исполняет код через выбранный исполнитель. Для недоверенного кода документация показывает Docker и не рекомендует локальное выполнение без изоляции.

Примеры из AutoGen 0.2 с `from autogen import AssistantAgent, UserProxyAgent`, `llm_config` и `initiate_chat` относятся к старому API. При переносе проекта нужно сверять версию и руководство по миграции.

Источники: [AutoGen AgentChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/index.html), [агенты AgentChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/agents.html), [выполнение кода](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/code-execution-groupchat.html).

## Q20. Что такое CrewAI?

**CrewAI** описывает агентов с ролями и целями, задачи и команду (`Crew`). `crew.kickoff()` запускает выбранный процесс. У команды есть последовательный и иерархический режимы; помимо команд фреймворк предоставляет `Flows` для управления состоянием и маршрутом выполнения.

```python
# Схема; agent1, agent2, task1, task2 задаются отдельно.
crew = Crew(agents=[agent1, agent2], tasks=[task1, task2])
result = crew.kickoff()
```

Команда с чёткими ролями удобна, когда работу можно распределить между исполнителями. Для сложных ветвлений оценивают средства `Flows` и нужную степень контроля; считать CrewAI только линейным конвейером неверно.

Источник: [CrewAI Crews](https://docs.crewai.com/en/concepts/crews).

## Q21. Свой код или фреймворк для агента?

Фреймворк помогает, когда нужны готовые механизмы состояния, восстановления, маршрутизации и наблюдаемости. Собственный цикл подходит, когда задача проста и команда готова поддерживать лимиты, ошибки, разрешения и журнал действий самостоятельно.

Anthropic рекомендует начинать с простых компонентов и добавлять абстракции по измеримой необходимости. Это не запрет на фреймворки: выбор проверяют на реальной задаче и в конкретной версии библиотеки. Утверждение, что один подход всегда надёжнее или дешевле другого, требует собственных измерений.

Источник: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).

## Q22. (!) Как тестировать агентов?

Агент может прийти к одному результату разными путями, поэтому тестируют и **результат**, и **действия**. Там, где ответ формально определён, обычная точная проверка остаётся лучшим вариантом. Для открытых задач используют набор эталонных кейсов, проверки фактов и ограничений, оценку человеком или LLM-судьёй с выборочной калибровкой человеком.

Трейс помогает увидеть вызовы инструментов, аргументы, ошибки и повторные попытки. Отдельно проверяют разрешения на действия, лимиты шагов, стоимость и поведение при недоступности инструмента. Эталонная траектория полезна для строго заданного процесса; для гибкой задачи нельзя требовать один единственный путь, если несколько путей дают корректный ответ.

Результаты проверяют на повторных запусках и после изменений модели, инструментов или промпта. Один удачный запуск не доказывает надёжность.

## Q23. Что такое оценка по трейсу (trace evaluation)?

**Trace evaluation** — оценка записанной последовательности выполнения: вызовов модели и инструментов, их аргументов, результатов, ошибок, переходов состояния и финального ответа. Такой разбор выявляет лишние вызовы, ошибочные аргументы и нарушение разрешений даже тогда, когда итоговый текст выглядит верным.

Трейс не обязан содержать внутренние мысли модели. Воспроизводимый журнал действий лучше отделять от недоступного или скрытого reasoning. Критерии задают по задаче: достигнут ли результат, использованы ли допустимые инструменты, есть ли опора на данные, соблюдены ли лимиты. Оценивать можно правилами, человеком или LLM-судьёй; спорные случаи требуют проверки по исходным данным.

## Q24. (!) Какие основные риски и подводные камни у агентов?

Агент сам выбирает часть следующих шагов и может повторять цикл работы. Поэтому важно ограничивать его полномочия, число шагов и расход ресурсов, а также проверять результат и наблюдаемые действия. Риски зависят от инструментов и среды исполнения.

**Потеря контроля над выполнением:**
1. **Бесконечные циклы** — агент раз за разом повторяет одно и то же действие.
2. **Взрыв контекста** — история растёт с каждым шагом, а вместе с ней и расходы.
3. **Непредсказуемое поведение** — разные запуски дают разные результаты.
4. **Сложность отладки** — длинные трейсы и запутанное состояние.

**Ошибки в действиях:**
5. **Неправильное использование tools** — неверные аргументы ломают поведение.
6. **Галлюцинации при планировании** — агент строит план под несуществующие tools.

**Безопасность:**
7. **Разрушительные действия** — агент удаляет файлы, переводит деньги и т.п.
8. **Prompt injection через tools** — tool возвращает вредоносные инструкции, которые агент принимает за команду.

**Стоимость и скорость:**
9. **Неконтролируемые расходы** — много итераций обходятся дорого.
10. **Задержка** — каждый дополнительный вызов модели или инструмента увеличивает общее время; величина зависит от конкретной задачи.

Лимиты времени, шагов и бюджета останавливают зацикливание. Исполнитель инструмента проверяет разрешения и аргументы, а внешние данные не получают статус инструкции. Для действий с высокой ценой ошибки устанавливают подтверждение человека по правилам операции.


## Q25. (!) Что такое human-in-the-loop (HITL)?

**Human-in-the-loop (HITL)** — пауза процесса перед действием, после которой человек может подтвердить, изменить или отклонить предложенный шаг. Это полезно для операций с высокой ценой ошибки: отправки сообщения от имени пользователя, публикации, удаления данных, платежа или изменения production-системы.

Нужен ли обязательный запрос подтверждения, определяется разрешениями пользователя, правилами организации и свойствами конкретной операции. Чтение данных и повторяемые безопасные действия обычно не требуют одинакового контроля с необратимой записью. Одобрение показывают для конкретного действия и его параметров, а исполнитель проверяет разрешение перед вызовом инструмента.

Выборочная проверка результатов и порог уверенности полезны для мониторинга качества, но не заменяют обязательное подтверждение там, где оно установлено правилами. Система должна уметь остановиться без действия, если человек отказал или не ответил.

## Q26. Как контролировать стоимость агентов?

Стоимость агентного запуска зависит от числа вызовов, входных и выходных токенов, инструментов и повторов. Поэтому процессу задают лимиты по шагам, времени, токенам, вызовам инструментов и бюджету. При достижении порога агент останавливается с понятным частичным результатом или запросом следующего решения.

Счёт провайдера может приходить после запроса, а цена зависит от модели и условий тарифа. Значит, проверка накопленной стоимости после ответа не создаёт точного жёсткого предоплатного потолка: перед дорогим шагом оценивают возможный расход и оставляют запас. Более дешёвую модель применяют только там, где качество на проверочных задачах остаётся приемлемым.

## Q27. Откуда берётся высокая latency у агентов и как её снизить?

Задержка складывается из последовательных вызовов модели, ожидания инструментов, сети и повторных попыток. Её нельзя оценить постоянными «секундами на один вызов»: время зависит от модели, длины контекста, объёма вывода и конкретного инструмента.

Сначала измеряют трейс и находят долгие шаги. Независимые чтения можно выполнять параллельно; зависимые действия выполняют по порядку. Сокращение контекста, кэширование пригодных результатов и более быстрые модели на подходящих этапах снижают время после проверки качества. Потоковая выдача и показ прогресса улучшают ожидание пользователя, но сами по себе не уменьшают время завершения задачи. Для долгих процессов нужны отмена и понятный статус.

## Q28. (!) Что такое computer use у Claude (с 2024)?

**Computer use** позволяет Claude получать снимки экрана и через инструмент предлагать действия мышью и клавиатурой. Приложение исполняет эти действия и возвращает новый результат модели. Anthropic объявила публичную бета-версию этой возможности 22 октября 2024 года для Claude 3.5 Sonnet.

Формат инструмента зависит от версии. Ранние примеры с `computer_20241022` и полем `input.action` не являются примером текущего интерфейса. В документации Claude Platform описан `computer_toolset_20260801`: действие приходит как имя отдельного `tool_use`, например `left_click`, вместе с `toolset_name="computer"`; размеры экрана не передают в запись toolset. При обновлении интеграции нужно сверять совместимость модели и версии инструмента.

Computer use полезен для интерфейсов, где прямой API не покрывает нужное действие. Его надёжность зависит от качества скриншотов, координат и изменений UI. Прямой API часто проще проверить и быстрее выполнить, если он подходит задаче. Для действий с последствиями сохраняют проверки разрешений и результата.

Источники: [анонс Anthropic](https://www.anthropic.com/news/3-5-models-and-computer-use), [документация computer use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool).
