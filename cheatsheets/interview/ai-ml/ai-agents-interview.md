# Вопросы на собеседовании: `AI Agents`

**AI Agent** — LLM, которая умеет **планировать** + **использовать tools** + **наблюдать результаты** + **итерировать** для решения задач. От простого ReAct-цикла до сложных multi-agent-систем. В 2024–2025 — горячая тема. Стандарты: **MCP** (Model Context Protocol). Фреймворки: LangGraph, AutoGen, CrewAI, Anthropic SDK.

## Q1. (!) Что такое AI agent?

**AI agent** — это LLM, которой дали цель, набор инструментов и право самой решать, что делать дальше. В отличие от обычного промпта («ответь на вопрос»), агент крутится в цикле: думает → действует → смотрит на результат → корректирует план — пока не достигнет цели.

Ключевые элементы цикла:
1. **Принимает цель** от пользователя — формулировку задачи, а не пошаговую инструкцию.
2. **Планирует** последовательность шагов сам.
3. **Использует tools** (HTTP, БД, выполнение кода, ...), чтобы действовать во внешнем мире, а не только генерировать текст.
4. **Наблюдает** результат каждого действия.
5. **Итерирует**: на основе наблюдения решает следующий шаг и повторяет, пока цель не достигнута.

Именно автономность («сам решает следующий шаг») отличает агента от заранее прописанного скрипта. Цена этой автономности — непредсказуемость и стоимость.

**Простейший agent-цикл:**

```python
def agent(goal):
    state = {"messages": [{"role": "user", "content": goal}]}
    while not is_done(state):
        action = llm.decide(state, tools=available_tools)
        if action.type == "tool_call":
            result = execute_tool(action)
            state.append(result)
        elif action.type == "answer":
            return action.content
```

**Где применяют:**
- Поддержка клиентов — с доступом к CRM и базе знаний.
- Ассистенты для кода (Cursor, Cline).
- Research-агенты (Deep Research, GPT Researcher).
- Автоматизация рабочих процессов.
- Computer-use-агенты — управляют экраном там, где нет API.


## Q2. (!) Workflows vs Agents — классификация Anthropic

Граница проходит по одному вопросу: **кто решает, какой будет следующий шаг — разработчик или LLM**. В статье «Building Effective Agents» (2024) Anthropic называет первое workflows, второе — agents.

**Workflows** — последовательность шагов задаёт разработчик, LLM лишь выполняет работу внутри каждого шага. Маршрут известен заранее.
```
Step 1: Extract entities
Step 2: Classify intent
Step 3: Generate response
```

**Agents** — LLM **сама динамически решает**, что делать дальше, на каждой итерации. Маршрут заранее не известен.
```
Loop: LLM decides next action → execute → check result → continue
```

**Компромисс:**
- **Workflows** — предсказуемы, проще отлаживать, дешевле, но не справятся с тем, чего не предусмотрел автор.
- **Agents** — гибкие, справляются с неизвестными задачами, но дороже и менее предсказуемы.

**Рекомендация:** начинать с workflows и переходить к agent только тогда, когда задача действительно требует гибкости — то есть когда шаги нельзя прописать заранее.


## Q3. (!) Когда нужен agent, а когда хватает простого LLM?

Выбирай самый простой вариант, который решает задачу: агент — это не цель, а последнее средство, когда дешёвые подходы не справляются. Шкала от простого к сложному: один вызов LLM → детерминированный workflow → агент.

**Один вызов LLM** — когда ответ получается за один проход, без внешних действий:
- однократные вопросы-ответы (single-turn QA);
- классификация;
- генерация текста или кода;
- перевод, суммаризация.

**Workflow (детерминированный)** — когда шагов несколько, но их **последовательность известна заранее**:
- многошаговые задачи с фиксированным маршрутом;
- ETL-подобные pipelines;
- структурированный вывод.

**Agent** — когда заранее не знаешь, сколько и каких шагов понадобится:
- открытые задачи с **неизвестным** числом шагов;
- нужны tools (база данных, web, выполнение кода);
- адаптивное поведение — разные пути для разных входных данных.

**Правило:** не делай agent, если хватает workflow. Агенты дороже, медленнее и менее надёжны — каждый лишний вызов LLM добавляет стоимость, задержку и шанс ошибки.


## Q4. (!) Как работает паттерн ReAct (Reasoning + Acting)?

**ReAct** (Yao et al., 2022) — базовый паттерн работы агента: модель чередует **рассуждение** (Thought) и **действие** (Action), а между ними получает **наблюдение** (Observation) — результат действия. Рассуждение вслух помогает модели выбрать следующий шаг, а наблюдение заземляет её на реальных данных вместо галлюцинаций.

Цикл повторяется, пока модель не решит, что собрала достаточно, и не выдаст Final Answer:

```
Thought: I need to find the user's order status
Action: query_database(order_id=12345)
Observation: {"status": "shipped", "tracking": "ABC123"}
Thought: Let me check delivery date
Action: get_delivery_estimate(tracking="ABC123")
Observation: {"estimated_delivery": "2025-04-20"}
Final Answer: Your order has been shipped (ABC123) and will arrive by April 20.
```

На практике в API с function calling роль Thought/Action берёт на себя сам формат tool-вызовов: пока модель возвращает `tool_calls` — выполняем их и кладём результат обратно в историю; как только вернулся обычный ответ без вызовов — это финальный ответ.

```python
def react_agent(query, tools):
    history = [{"role": "user", "content": query}]
    while True:
        response = llm.chat.completions.create(
            messages=history,
            tools=tools
        )
        msg = response.choices[0].message
        history.append(msg)
        if not msg.tool_calls:
            return msg.content  # Final answer
        for call in msg.tool_calls:
            result = execute_tool(call)
            history.append({"role": "tool", "content": result, "tool_call_id": call.id})
```


## Q5. Как устроен паттерн Plan-and-Execute?

**Plan-and-Execute** — агент сначала строит **полный план** целиком, а потом просто выполняет шаги один за другим. Планирование и исполнение разнесены: дорогая «умная» модель один раз продумывает маршрут, дешёвая — исполняет.

```
1. Planner: "To answer X, I need to do A, then B, then C"
2. Executor: do A → result_a
3. Executor: do B(result_a) → result_b
4. Executor: do C(result_b) → result_c
5. Final answer
```

**Сравнение с ReAct:** ReAct решает, что делать дальше, на каждой итерации — это гибче, но он может «забуксовать». Plan-and-Execute фиксирует план заранее — это предсказуемее и дешевле (меньше вызовов планировщика), но если план изначально плох, агент пойдёт по нему до конца и провалится.

**Сценарий применения:** сложные задачи, где важна структура и видимый заранее маршрут, — исследования, анализ данных.


## Q6. (!) Что такое tool use (function calling)?

**Function calling** — механизм, через который LLM вызывает внешние функции. Разработчик описывает доступные tools в виде JSON-схемы (имя, описание, параметры), модель по запросу пользователя выбирает нужный tool и возвращает аргументы. Сама модель код **не выполняет** — она лишь говорит, *что* вызвать; выполнение и возврат результата — на стороне приложения.

Качество описания tool напрямую влияет на то, угадает ли модель, когда его звать: `description` — это, по сути, промпт для выбора инструмента.

**Определение tool:**

```python
tools = [{
    "type": "function",
    "function": {
        "name": "search_documents",
        "description": "Search company knowledge base for documents matching query",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string"},
                "max_results": {"type": "integer", "default": 5}
            },
            "required": ["query"]
        }
    }
}]
```

**LLM выбирает** tool и аргументы:

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[...],
    tools=tools,
    tool_choice="auto"  # или "required" чтобы заставить
)

# response.choices[0].message.tool_calls
# [{"function": {"name": "search_documents", "arguments": '{"query": "vacation policy"}'}}]
```

Подробнее — в [Prompt Engineering](prompt-engineering-interview.md).


## Q7. (!) Какие tools предоставляют агентам?

Любой tool — это мост между текстовой моделью и внешним миром: чтение данных, действие или вычисление, которое LLM не может сделать «в голове».

**Типичные tools:**
1. **Поиск** — внутренние документы, web-поиск (Tavily, Perplexity, Brave).
2. **Запросы к БД** — SQL, NoSQL.
3. **HTTP-запросы** — API (REST, GraphQL).
4. **Выполнение кода** — Python-sandbox (например, E2B, Modal).
5. **Файловые операции** — чтение/запись.
6. **Email / уведомления** — отправка сообщений.
7. **Календарь / планирование**.
8. **Генерация изображений** (DALL-E, Imagen).
9. **Web scraping**.
10. **Computer-use** (Claude — клавиатура/мышь, экран).

**Рекомендации:**
- **Чётко описывайте tool** — по описанию модель решает, когда его вызывать; расплывчатое описание ведёт к лишним или пропущенным вызовам.
- **Валидируйте входные данные** — LLM может передать некорректные аргументы, и слепо доверять им нельзя.
- **Изолируйте опасные tools в sandbox** — выполнение кода и файловые операции должны быть отрезаны от боевой инфраструктуры.
- **Возвращайте структурированный результат** — JSON/dict, а не свободный текст: так модели проще разобрать ответ, а вам — отлаживать.


## Q8. (!) Как использовать выполнение кода как tool?

LLM пишет код на Python (или другом языке), приложение выполняет его в **sandbox** и возвращает вывод обратно в диалог. Это превращает модель из «генератора текста» в калькулятор и интерпретатор: вместо того чтобы угадывать ответ, она его *вычисляет*.

```python
def execute_python(code: str) -> str:
    result = sandbox.run(code, timeout=10, network=False)
    return result.stdout
```

**Сценарии применения:**
- Математика и статистика — точный расчёт вместо ненадёжной «арифметики в уме» самой LLM.
- Анализ данных в CSV.
- Генерация графиков.
- Произвольная пользовательская логика.

**Sandbox-окружения:**
- **E2B** — управляемый sandbox-API.
- **Modal** — serverless-вычисления.
- **Self-hosted Docker** — ради приватности данных.
- **Pyodide** — Python на стороне браузера.

**Безопасность критична:** модель может сгенерировать вредоносный код, поэтому выполнять его без изоляции (с доступом к сети и файловой системе) нельзя — отсюда `network=False` и `timeout` в примере.


## Q9. Как использовать web-поиск как tool?

Web-поиск даёт агенту доступ к **актуальной** информации: обучающие данные LLM фиксированы на дате cutoff и устаревают на месяцы, поэтому без поиска модель не знает о свежих событиях, ценах, версиях. Это «глаза» агента во внешнем интернете.

**API для поиска:**
- **Tavily** — заточен под AI-агентов, популярен.
- **Perplexity Online**.
- **Brave Search API**.
- **Bing Search API**.
- **SerpAPI** — результаты Google.
- **You.com**.

```python
def web_search(query: str, max_results: int = 5):
    results = tavily.search(query, max_results=max_results)
    return [{
        "url": r.url,
        "title": r.title,
        "content": r.content[:500]
    } for r in results]
```

**Типичный паттерн:** агент сначала делает поиск (получает список ссылок со сниппетами), а затем подгружает полное содержимое релевантных страниц для деталей — двухступенчатый подход экономит токены, потому что грузятся только нужные страницы.


## Q10. (!) Что такое MCP (Model Context Protocol)?

**Model Context Protocol (MCP)** — открытый стандарт от Anthropic (ноябрь 2024), задающий **единый протокол** подключения LLM-клиентов к инструментам и источникам данных. Это «USB для AI-инструментов»: один разъём вместо своего коннектора под каждую пару клиент-сервис.

**Проблема, которую он решает:** до MCP каждый клиент (Claude Desktop, Cursor, ...) интегрировался с каждым сервисом по-своему — получалась матрица M×N интеграций. MCP сводит её к M+N: сервис реализует протокол один раз, клиент реализует его один раз — и они совместимы.

```
Client (Claude Desktop, IDE)
    ↓ MCP protocol (JSON-RPC over stdio/HTTP)
MCP Server (Github, PostgreSQL, Slack, ...)
```

**MCP-серверы** уже есть для:
- файловой системы, Git, GitHub;
- PostgreSQL, SQLite, MongoDB;
- Slack, Linear, Notion;
- веб-браузеров (Puppeteer);
- Google Drive, Confluence.

**Главное преимущество:** разработчик пишет MCP-сервер один раз — и он работает с любым MCP-совместимым клиентом, без переписывания интеграции под каждый.

В **2025** стандарт принимается быстро: OpenAI анонсировал поддержку, многие IDE — тоже.


## Q11. (!) Чем отличается short-term память от long-term?

Разница — в том, переживает ли информация конец сессии. Short-term живёт внутри одного диалога, long-term — между диалогами.

**Short-term memory** — контекст текущего разговора:
- хранится прямо в истории сообщений (в prompt);
- ограничена размером context window;
- забывается, как только сессия закончилась.

**Long-term memory** — то, что сохраняется во внешнем хранилище и подгружается в новых сессиях:
- предпочтения пользователя;
- прошлые взаимодействия;
- усвоенные факты.

Short-term получается «бесплатно» (это просто история), а long-term нужно явно сохранять и извлекать — потому что в context window всю историю не уместить.

**Реализация long-term:**

```python
# At end of session
memory_summary = llm("Summarize key facts about user from this conversation")
db.save(user_id, memory_summary)

# At start of next session
context = db.get(user_id)
prompt = f"User context: {context}\n\nMessage: {new_message}"
```

**Tools:** Mem0, MemGPT, custom Postgres/Redis.


## Q12. Как обрезать историю разговора при заполнении контекста?

При длинном диалоге история перестаёт помещаться в context window, и старые сообщения нужно как-то убирать — но так, чтобы не потерять важное. Стратегии различаются балансом «простота против сохранности смысла».

**Стратегии:**
1. **Sliding window** — хранить только последние N сообщений. Просто, но раннее теряется полностью.
2. **Summarization** — старую часть истории сжать в краткое резюме (summary). Сохраняет смысл, но стоит дополнительных вызовов LLM.
3. **Hybrid** — свежие сообщения дословно плюс резюме старых. Компромисс между точностью и объёмом.
4. **Semantic** — по текущему запросу доставать из истории только релевантные прошлые сообщения через vector search.

```python
def truncate_history(history, max_tokens=8000):
    while count_tokens(history) > max_tokens:
        # Summarize oldest 10 messages
        old = history[:10]
        summary = llm(f"Summarize: {old}")
        history = [{"role": "system", "content": f"Earlier: {summary}"}] + history[10:]
    return history
```


## Q13. Что такое vector memory (RAG для памяти)?

Vector memory — это применение механики RAG не к документам, а к **истории разговора**. Каждое сообщение векторизуется и кладётся в vector DB; по новому запросу из неё извлекаются семантически близкие прошлые реплики и подмешиваются в контекст. Так агент «вспоминает» именно то, что относится к делу, не таская всю историю целиком.

**Память как vector DB:**

```python
# Store
memory_emb = embed(message)
vector_db.upsert({"user_id": user_id, "embedding": memory_emb, "text": message, "timestamp": ...})

# Retrieve relevant past
relevant = vector_db.search(embed(current_query), filter={"user_id": user_id}, top_k=5)
```

**Сценарии применения:**
- «Что я тебе говорил про свои предпочтения?» — точечное извлечение из прошлого.
- Долгосрочная персонализация.
- Непрерывность между сессиями.

Суть: **RAG над историей разговора** вместо RAG над документами.


## Q14. (!) Что такое multi-agent system?

**Multi-agent system** — задачу решают **несколько LLM-агентов**, каждый со своей ролью, координируясь между собой. Идея — декомпозиция: разбить большую задачу на части и поручить каждую специализированному агенту, как команде из исследователя, писателя и ревьюера.

Пример топологии вокруг координатора:

- `User` → `Coordinator` (координатор принимает запрос пользователя).
- `Coordinator` → раздаёт задачи трём специализированным агентам: `Researcher Agent`, `Writer Agent`, `Reviewer Agent`.
- `Researcher Agent` → `Web Search` (исследователь обращается к tool веб-поиска).
- `Writer Agent` → `Coordinator` и `Reviewer Agent` → `Coordinator` (писатель и ревьюер возвращают результаты обратно координатору).

**Типы организации:**
- **Specialist agents** — каждый эксперт в своей области.
- **Pipeline** — последовательная обработка: выход одного агента — вход следующего.
- **Debate** — два агента спорят, третий судит (повышает качество за счёт критики).
- **Hierarchical** — менеджер раздаёт подзадачи работникам.

**Минусы:**
- **Очень дорого** — каждый агент это отдельные вызовы LLM, и они складываются.
- **Медленно** — шаги идут последовательно, задержки суммируются.
- **Сложно отлаживать** — переплетённые диалоги нескольких агентов.
- **Риск зацикливания** — агенты могут гонять задачу по кругу.

В **2025** большинство production-систем — это всё ещё **один агент**: multi-agent оправдан в основном для сложных research- и creative-задач, где выигрыш в качестве перекрывает рост стоимости и сложности.


## Q15. Как работает паттерн Supervisor?

**Supervisor** (агент-супервизор) — это маршрутизатор: он не решает задачу сам, а смотрит на запрос и делегирует его подходящему **worker-агенту**. Получается централизованная схема — все запросы проходят через одну точку принятия решения, что упрощает контроль и логирование.

```python
def supervisor(query):
    decision = supervisor_llm(f"Which agent for: {query}? Options: researcher, coder, writer")
    if decision == "researcher":
        return research_agent(query)
    elif decision == "coder":
        return code_agent(query)
    elif decision == "writer":
        return writing_agent(query)
```

**Сценарий применения:** маршрутизация разнородных запросов к нужному специализированному агенту — например, технический вопрос к coder-агенту, фактологический к researcher-агенту.


## Q16. Что такое иерархические агенты (hierarchical agents)?

Иерархия агентов — это supervisor, развёрнутый на несколько уровней: менеджер дробит задачу на подзадачи и отдаёт их суб-менеджерам, те — своим работникам. Получается дерево делегирования, повторяющее организационную структуру.

```
Manager Agent
├── Sub-task to Sub-Manager 1
│   ├── Worker 1.1
│   └── Worker 1.2
└── Sub-task to Sub-Manager 2
    ├── Worker 2.1
    └── Worker 2.2
```

Многоуровневая декомпозиция полезна для очень больших задач, которые не помещаются в один контекст и требуют разбиения, — например, рефакторинг целого codebase.

В **2025** тема остаётся продвинутой, но экспериментальной: стоимость и сложность отладки растут с каждым уровнем иерархии и ограничивают распространение в проде.


## Q17. (!) Какие бывают паттерны коммуникации между агентами?

Вопрос сводится к тому, *как* агенты обмениваются информацией — напрямую или через общее хранилище, и кто инициирует обмен. От этого зависит связанность системы и сложность отладки.

**Паттерны:**

1. **Direct messaging** — агент A пишет агенту B напрямую. Просто, но связывает агентов жёстко.
2. **Shared blackboard** — все читают и пишут в общее состояние («доску»). Развязывает агентов, но за состоянием нужно следить.
3. **Pub/sub** — событие порождает реакцию у всех подписавшихся агентов. Хорошо масштабируется.
4. **Voting / consensus** — несколько агентов предлагают варианты, итог выбирается голосованием. Повышает надёжность.
5. **Debate** — агенты спорят, отдельный судья выбирает лучший ответ.

Фреймворки выбирают разную базовую модель: **LangGraph** строится вокруг **общего состояния-графа** (агенты — узлы, читающие и пишущие в общее состояние), а **AutoGen** — вокруг **диалога** (агенты буквально разговаривают друг с другом сообщениями).


## Q18. (!) Что такое LangGraph (от LangChain)?

**LangGraph** — agent-фреймворк, в котором логика агента описана как **граф**: узлы — это шаги (вызов модели, вызов tools), рёбра задают переходы между ними, а через граф протекает общее **состояние**. Цикл «модель → tools → модель» выражается явным ребром-петлёй, а не неявным `while`.

```python
from langgraph.graph import StateGraph

class State(TypedDict):
    messages: list

def agent_node(state: State):
    response = llm.invoke(state["messages"])
    return {"messages": state["messages"] + [response]}

def tool_node(state: State):
    tool_calls = state["messages"][-1].tool_calls
    results = [execute_tool(tc) for tc in tool_calls]
    return {"messages": state["messages"] + results}

graph = StateGraph(State)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.add_edge("agent", "tools")
graph.add_edge("tools", "agent")  # loop
graph.set_entry_point("agent")
```

**Преимущества:** состояние явное (его видно и можно инспектировать), отладка удобнее, чем в неявном цикле, и легко выражаются сложные потоки с ветвлениями и циклами.

В **2025** — самый популярный agent-фреймворк.


## Q19. Что такое AutoGen (от Microsoft)?

**AutoGen** (Microsoft) — фреймворк, где multi-agent-система строится как **диалог** между агентами: они обмениваются сообщениями, как участники чата. Один из агентов обычно умеет выполнять код, поэтому AutoGen силён в задачах генерации и запуска кода.

```python
from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent("assistant", llm_config={"model": "gpt-4o"})
user_proxy = UserProxyAgent("user", code_execution_config={"work_dir": "coding"})

user_proxy.initiate_chat(assistant, message="Solve this: ...")
```

**Особенности:**
- Multi-agent-диалоги как способ координации.
- Встроенное выполнение кода прямо у агента.
- Поддержка human-in-the-loop — человек может вмешаться в диалог.

В **2025** популярен в research и генерации кода.


## Q20. Что такое CrewAI?

**CrewAI** — фреймворк, в котором команда агентов («crew») описывается **декларативно** через роли, цели и задачи: вы задаёте, *кто* агент и *что* он должен сделать, а фреймворк сам организует выполнение. Это ближе к настройке команды людей, чем к программированию цикла.

```python
researcher = Agent(role="Researcher", goal="Find info", tools=[web_search])
writer = Agent(role="Writer", goal="Write articles", tools=[])
crew = Crew(agents=[researcher, writer], tasks=[task1, task2])
result = crew.kickoff()
```

**Когда подходит:** линейные pipelines с чётко разделёнными ролями (нашёл — написал — проверил). За простоту платишь меньшей гибкостью, чем у графовых фреймворков.


## Q21. Свой код или фреймворк для агента?

Решающий фактор — сложность задачи. Фреймворк ускоряет старт, но прячет логику за абстракциями; свой код многословнее, зато прозрачен и полностью под контролем. Для простого цикла «модель → tools → модель» абстракции фреймворка часто только мешают отладке.

**Плюсы фреймворков:**
- Быстрый старт.
- Готовые реализации типовых паттернов.
- Сообщество и примеры.

**Минусы фреймворков:**
- **Тяжёлые абстракции** — труднее понять и отладить, что происходит внутри.
- Частые ломающие изменения (LangChain этим печально известен).
- Иногда мешают реализовать нестандартный паттерн.

**Рекомендация Anthropic (2024):**
> «Не используйте фреймворки, пока они вам действительно не понадобятся. Большинство агентов — это простые циклы.»

```python
# Simple custom agent — может быть лучше LangGraph
def agent(query, tools, max_iterations=10):
    messages = [{"role": "user", "content": query}]
    for _ in range(max_iterations):
        response = client.chat.completions.create(messages=messages, tools=tools)
        messages.append(response.choices[0].message)
        if not response.choices[0].message.tool_calls:
            return response.choices[0].message.content
        for tc in response.choices[0].message.tool_calls:
            result = execute_tool(tc)
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
    raise TimeoutError("Agent exceeded max iterations")
```

**В 2025** всё чаще сходятся на том, что для агентов **свой код часто лучше фреймворка** — особенно когда логика проста и важна предсказуемость.


## Q22. (!) Как тестировать агентов?

Главная сложность: агенты **недетерминированы** — один и тот же запрос даёт разные траектории, и к правильному ответу ведёт множество путей. Поэтому привычный assert «выход == ожидание» не работает, и проверяют сразу несколько аспектов: и *что* агент ответил, и *как* он к этому шёл.

**Подходы:**

1. **Trace evaluation** — логировать каждый шаг агента и разбирать траекторию (вручную или автоматически).
2. **Outcome evaluation** — корректен ли финальный ответ; обычно оценивает LLM-as-judge, раз эталона дословно нет.
3. **Tool call evaluation** — правильные ли tools вызваны и с правильными ли аргументами.
4. **Cost / step count** — агент не должен раздувать число шагов и стоимость (например, делать 100 вызовов вместо трёх).
5. **Golden trajectories** — сравнение реального пути агента с заранее заданным «правильным».

**Фреймворки для трейсинга и оценки:** LangSmith, Langfuse, Phoenix Arize, Weights & Biases.

```python
# Pseudo eval
for case in test_cases:
    trace = run_agent(case.input)
    assert trace.tool_calls_count < case.max_calls
    assert llm_judge(trace.final_answer, case.expected) > 0.8
```


## Q23. Что такое оценка по трейсу (trace evaluation)?

**Trace** — это полная запись работы агента: последовательность его мыслей (Thought), действий (Action) и наблюдений (Observation). Оценка по трейсу смотрит не только на финальный ответ, но и на **процесс**: правильно ли агент рассуждал и не делал ли лишних действий — даже верный ответ может быть получен неэффективным или случайным путём.

```
Step 1: Thought "I need order status"
Step 2: Action search_orders(...)
Step 3: Observation {...}
Step 4: Thought "Found order"
Step 5: Final Answer "..."
```

**Критерии оценки:**
- Решил ли агент задачу?
- Эффективны ли вызовы tools — нет ли лишних и повторяющихся?
- Здравые ли рассуждения, без галлюцинаций?
- Разумна ли итоговая стоимость?

**LLM-as-judge:** разбирать трейсы вручную дорого, поэтому часто их анализирует и оценивает другая LLM.


## Q24. (!) Какие основные риски и подводные камни у агентов?

Все проблемы вытекают из двух свойств агентов — **автономности** (сами решают, что делать) и **цикличности** (повторяют шаги). Отсюда — риски потери контроля, неуправляемого роста стоимости и опасных действий.

**Потеря контроля над выполнением:**
1. **Бесконечные циклы** — агент раз за разом повторяет одно и то же действие.
2. **Взрыв контекста** — история растёт с каждым шагом, а вместе с ней и расходы.
3. **Непредсказуемое поведение** — разные запуски дают разные результаты.
4. **Сложность отладки** — длинные трейсы и запутанное состояние.

**Ошибки в действиях:**
5. **Неправильное использование tools** — неверные аргументы ломают поведение.
6. **Галлюцинации при планировании** — агент строит план под несуществующие tools.

**Безопасность:**
7. **Разрушительные действия** — агент удаляет файлы, переводит деньги и т.п.
8. **Prompt injection через tools** — tool возвращает вредоносные инструкции, которые агент принимает за команду.

**Стоимость и скорость:**
9. **Неконтролируемые расходы** — много итераций обходятся дорого.
10. **Высокая latency** — многошаговое выполнение растягивается на минуты.


## Q25. (!) Что такое human-in-the-loop (HITL)?

**Human-in-the-loop (HITL)** — встраивание человека в цикл агента: перед необратимыми или дорогими действиями агент останавливается и просит подтверждение. Это страховка от автономности — мы соглашаемся на чуть меньшую скорость ради защиты от разрушительной ошибки там, где её цена высока.

```python
def execute_tool_with_approval(tool_call):
    if tool_call.tool in DANGEROUS_TOOLS:
        approval = ask_human(f"Agent wants to {tool_call.tool} with {tool_call.args}. Approve?")
        if not approval:
            return "User declined"
    return execute(tool_call)
```

**Когда HITL обязателен** — там, где действие необратимо или его последствия дороги:
- **Финансовые транзакции** — перевод денег, размещение заказов.
- **Разрушительные операции** — удаление данных, drop таблиц.
- **Внешние коммуникации** — отправка писем, звонки от лица компании.
- **Деплои в production**.

**Паттерны** — от строгого к экономному:
- **Ручное подтверждение** — человек одобряет каждое опасное действие. Максимум контроля, минимум скорости.
- **Выборочный контроль** — вручную проверяется 10% случайных действий. Компромисс «контроль/скорость».
- **Порог уверенности** — при высокой уверенности агент действует сам, при низкой — спрашивает.


## Q26. Как контролировать стоимость агентов?

У агента нет встроенного «стоп-крана»: цикл может крутиться, пока не достигнет цели, — а каждый шаг это деньги. Поэтому в коде задают жёсткие лимиты-предохранители, при достижении которых выполнение принудительно останавливается. Самый прямой — бюджет в долларах на один запуск:

```python
def agent_with_budget(query, max_cost_usd=0.50):
    total_cost = 0
    while ...:
        response = llm(...)
        total_cost += calculate_cost(response)
        if total_cost > max_cost_usd:
            return f"Budget exceeded ({total_cost})"
        ...
```

**Стратегии:**
- **Лимит итераций** — максимум, например, 10 шагов: защищает от зацикливания.
- **Лимит токенов** — потолок на суммарные токены за запуск.
- **Лимит стоимости** — бюджет в долларах на один запуск (как в коде выше).
- **Лимит времени** — обрывать через, например, 5 минут.
- **Лимит вызовов tools** — не больше N вызовов.
- **Дешёвая модель для рутины** — маленькая модель планирует и делает простые шаги, большая включается только для критичной генерации.


## Q27. Откуда берётся высокая latency у агентов и как её снизить?

Корень проблемы — **последовательность вызовов LLM**: один вызов занимает 1–5 секунд, а агент делает их по цепочке, поэтому задержки складываются. 10 шагов по 1–5 сек — это уже 10–50 секунд ожидания.

**Технические оптимизации:**
- **Параллельные вызовы tools** — если tools независимы, запускать их разом (`parallel_tool_calls: true` в OpenAI), а не по очереди.
- **Маленькие быстрые модели** для простых шагов (Haiku, GPT-4o-mini).
- **Кэширование** промежуточных результатов, чтобы не пересчитывать одно и то же.
- **Стриминг** финального ответа сразу, как только он готов.
- **Фоновое выполнение** с асинхронным уведомлением по завершении.

**Что делать с UX**, раз убрать задержку полностью нельзя — сделать её переносимой:
- показывать прогресс («Агент ищет документы... проверяет...»);
- давать оценку времени завершения;
- позволять отменить выполнение на полпути.

- QA-тестирование;
- легаси-приложения без API.

**Подводный камень:** работает очень медленно и дорого — каждый шаг это скриншот плюс рассуждение модели. Если у системы есть API, почти всегда лучше использовать его; computer use оправдан именно там, где **API не существует**.

В **2025** распространение растёт в RPA (Robotic Process Automation).
