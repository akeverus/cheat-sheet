# Вопросы на собеседовании: `Model Serving`

**Model serving** — развёртывание ML/LLM-моделей в production. Когда **API не подходит** (приватность, масштаб, стоимость) — нужно **разворачивать у себя** (self-host). Стек: **vLLM**, **TGI**, **Triton**, **TorchServe**, **BentoML**, **Ollama**. Главные оптимизации: **continuous batching**, **quantization**, **KV cache**, **GPU sharing**.

## Q1. (!) Что такое model serving?

**Model serving** — это превращение обученной ML/LLM-модели в работающий сервис: модель отдаётся клиентам через API, который на каждый запрос возвращает предсказание (inference). Обучение даёт файл с весами; serving — это всё, что нужно, чтобы по этим весам отвечать на реальный трафик: загрузка в память, приём запросов, выполнение прогона, возврат результата.

**Путь одного запроса** проходит через четыре стадии:
1. **Загрузка модели** — веса загружаются в RAM или GPU один раз при старте (это дорого, поэтому держим модель в памяти, а не читаем с диска на каждый запрос).
2. **Приём запроса** — сервис принимает входные данные по HTTP или gRPC.
3. **Inference** — модель прогоняет вход и считает предсказание.
4. **Ответ** — результат сериализуется и возвращается клиенту.

**Где разместить модель** — четыре подхода, от простого к промышленному:
- **Embedded** — модель живёт прямо внутри приложения (`model.predict()` в том же процессе). Просто, но модель не масштабируется отдельно от приложения.
- **Sidecar** — модель в отдельном процессе на той же машине; приложение ходит к ней по localhost.
- **Microservice** — модель вынесена в самостоятельный API-сервис, масштабируется и обновляется независимо.
- **Managed** — облако берёт инфраструктуру на себя (SageMaker, Vertex AI).

**Рекомендация:** для серьёзного production используют выделенные inference-серверы (vLLM, Triton) — они дают батчинг, управление GPU-памятью и метрики «из коробки», которых нет у самописного `model.predict()`.


## Q2. (!) Когда выбрать self-host, а когда чужой API?

Коротко: **API — пока вы маленькие и важна скорость запуска; self-host — когда масштаб, приватность или кастомизация перевешивают сложность инфраструктуры.** Это решение упирается в три оси — деньги на масштабе, контроль над данными, качество доступных моделей.

**Чужой API (OpenAI, Anthropic):**
- Плюсы: быстрый старт, доступ к самым сильным (state-of-the-art) моделям, ноль инфраструктуры.
- Минусы: платите за каждый токен, данные уходят за пределы вашего контура, есть rate limits и привязка к вендору.

**Self-host (своя инфраструктура):**
- Плюсы: данные не покидают контур (важно для PII и комплаенса); на большом объёме дешевле; можно дообучать (fine-tuning) под себя; нет привязки к вендору.
- Минусы: нужна GPU-инфраструктура и команда MLOps; открытые модели часто уступают топовым проприетарным по качеству.

**Эмпирическое правило:** self-host начинает окупаться примерно с **10M–100M токенов в месяц** — ниже этого порога стоимость своих GPU и MLOps-работы обычно превышает счёт за API. Поэтому типичный путь: начать на API, мигрировать на self-host, когда объём вырос настолько, что экономия покрывает накладные расходы.


## Q3. (!) GPU или CPU для inference — что выбрать?

Главная причина, по которой LLM просят GPU, — параллелизм: inference это огромные матричные умножения, а GPU делает тысячи таких операций одновременно, тогда как CPU считает почти последовательно. Отсюда разница в скорости в десятки раз. Выбор сводится к балансу скорость/стоимость/память:

| Критерий | GPU | CPU |
|----------|-----|-----|
| Скорость (LLM) | в 10–100 раз быстрее | Медленно (но реально через llama.cpp) |
| Стоимость | $$$ | $ |
| Память | Ограничена (24–80 ГБ на GPU) | До терабайтов RAM |
| Latency | Низкая | Высокая |
| Embedding-модели | Нормально на CPU (они небольшие) | Нормально |
| Простая классификация | CPU достаточно | Нормально |

**Эмпирическое правило:** LLM крупнее 7B параметров фактически требуют GPU; модели меньше 1B спокойно крутятся на CPU. Промежуток между ними — зона компромисса: на CPU можно запустить и большую модель (через квантизацию и llama.cpp), но latency будет высокой, что годится для офлайн-задач, но не для интерактивного чата.


## Q4. В чём компромисс между latency и throughput?

**Latency** — время ответа на один запрос; **throughput** — сколько запросов система обслуживает в секунду. Между ними прямой конфликт, и причина — батчинг: чтобы загрузить GPU и поднять throughput, запросы собирают в пачку (batch) и считают вместе, но тогда каждый запрос ждёт, пока пачка наберётся, — latency растёт.

**Оптимизация под latency:**
- Маленький batch (часто batch=1) — запрос не ждёт соседей.
- Одиночный запрос обрабатывается быстро.
- Платой за это идёт неполная загрузка GPU.

**Оптимизация под throughput:**
- Большой batch и много параллельных запросов.
- Выше утилизация GPU, больше ответов в секунду.
- Платой идёт более высокая latency на отдельный запрос.

**Continuous batching** (vLLM) частично снимает этот компромисс: запросы не ждут формирования пачки, а добавляются в общий батч на лету, поэтому GPU остаётся загруженным без штрафа к latency. Подробнее — в Q14.


## Q5. (!) Что такое TorchServe и для чего он?

**TorchServe** — официальный inference-сервер для PyTorch. Он берёт обученную PyTorch-модель, упаковывает её вместе с кодом препроцессинга в архив `.mar` и поднимает поверх HTTP/gRPC-эндпоинт — вам не нужно писать веб-сервер вручную.

```python
# Define handler
class MyHandler:
    def initialize(self, ctx): ...
    def preprocess(self, data): ...
    def inference(self, model_input): ...
    def postprocess(self, inference_output): ...

# Serve
torchserve --start --model-store . --models my_model=my_model.mar
```

Handler с четырьмя методами (`initialize` → `preprocess` → `inference` → `postprocess`) — это точка, куда вы вставляете свой Python-код вокруг модели: разобрать вход, прогнать модель, оформить выход.

**Сценарии применения:**
- Классические PyTorch-модели (классификация, детекция, эмбеддинги).
- Кастомный препроцессинг на Python (нестандартная подготовка входа).
- Несколько версий модели одновременно.

**Подводный камень:** TorchServe не годится для LLM — в нём нет специфичных для генеративных моделей оптимизаций (continuous batching, PagedAttention), которые даёт vLLM. Для LLM берите vLLM или TGI.


## Q6. Что такое TensorFlow Serving?

**TF Serving** — production-сервер для моделей TensorFlow и Keras, разработанный и обкатанный внутри Google. Модель кладут в каталог, монтируют в контейнер — и она доступна по REST и gRPC, без написания серверного кода.

```bash
docker run -p 8501:8501 \
  -v /path/to/model:/models/my_model \
  -e MODEL_NAME=my_model \
  tensorflow/serving
```

**Чем полезен:**
- Production-grade — проверен на нагрузке внутри Google.
- Два интерфейса: gRPC (быстрый, для сервис-сервис) и REST.
- Горячая замена модели без рестарта — новая версия подхватывается на лету, трафик не прерывается.
- Встроенное версионирование моделей.

**Контекст на 2025:** TensorFlow теряет долю в пользу PyTorch, поэтому новые проекты редко стартуют на TF Serving, но в legacy-системах он остаётся рабочим и поддерживаемым выбором.


## Q7. (!) Что такое NVIDIA Triton Inference Server?

**Triton** (NVIDIA) — универсальный inference-сервер, главная фишка которого в том, что он не привязан к одному фреймворку: один сервер обслуживает модели из PyTorch, TensorFlow, ONNX и других стеков. Это удобно, когда в продакшене зоопарк моделей разного происхождения и не хочется поднимать под каждую свой сервер.

**Что умеет:**
- **Multi-framework** — PyTorch, TensorFlow, ONNX, TensorRT, OpenVINO, vLLM (через TensorRT-LLM) под одной крышей.
- **Dynamic batching** — сам собирает приходящие запросы в батч ради загрузки GPU.
- **Model ensembles** — конвейер из нескольких моделей (например, препроцессинг → модель → постпроцессинг) описывается декларативно.
- **Multi-GPU** — планирует выполнение по нескольким GPU.
- **gRPC + HTTP** одновременно.

```python
# Model repository structure
model_repository/
  my_model/
    config.pbtxt
    1/
      model.onnx
```

```protobuf
# config.pbtxt
name: "my_model"
platform: "onnxruntime_onnx"
max_batch_size: 32
input [{ name: "input", data_type: TYPE_FP32, dims: [3, 224, 224] }]
output [{ name: "output", data_type: TYPE_FP32, dims: [1000] }]
```

**Когда брать:** Triton — выбор по умолчанию, когда нужен один общий сервер общего назначения под разнородные модели в production ML.


## Q8. (!) Что такое BentoML?

**BentoML** — Python-first фреймворк для serving: вы описываете сервис обычным Python-классом с декораторами, а BentoML сам генерирует REST/gRPC API, собирает контейнер и деплоит его. Это закрывает разрыв между «у меня есть модель и кусок кода вокруг неё» и «у меня есть задеплоенный сервис», не заставляя вручную писать веб-слой и Dockerfile.

```python
import bentoml

@bentoml.service
class MyModel:
    def __init__(self):
        self.model = load_model()

    @bentoml.api
    def predict(self, input: str) -> dict:
        return self.model.predict(input)
```

```bash
bentoml serve service.py:MyModel
bentoml build  # build container
bentoml deploy  # to BentoCloud / K8s
```

**Чем хорош:**
- Pythonic — описание сервиса близко к обычному коду, низкий порог входа.
- Автогенерация REST + gRPC.
- Сборка контейнера встроена (`bentoml build`).
- Деплой через Yatai / BentoCloud / Kubernetes.

**Когда брать:** BentoML силён, когда вокруг модели много кастомного Python-кода (классический ML, своя бизнес-логика в препроцессинге). Под LLM он сам по себе не оптимизирован, но умеет интегрироваться с vLLM, если генеративная модель нужна именно внутри BentoML-сервиса.


## Q9. (!) Почему vLLM — главный инструмент для LLM serving?

**vLLM** (UC Berkeley) — самое популярное решение для self-hosted LLM в **2024–2025**, и причина одна — пропускная способность. За счёт PagedAttention и continuous batching он выжимает из той же GPU в разы больше токенов в секунду, чем «наивный» запуск модели через HuggingFace `generate()`.

```python
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-3-8B-Instruct")
outputs = llm.generate(["Hello"], SamplingParams(temperature=0.7))
```

**Или OpenAI-совместимый API:**

```bash
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3-8B-Instruct \
  --port 8000
```

**Ключевые оптимизации:**
- **PagedAttention** — управляет KV cache как страницами памяти, почти без потерь на фрагментацию (см. Q14).
- **Continuous batching** — добавляет новые запросы в идущий батч на лету, GPU не простаивает.
- **Tensor parallelism** — разносит большую модель по нескольким GPU.
- **Quantization** — поддерживает AWQ, GPTQ, FP8, чтобы уместить модель в меньшую память.
- **Prefix caching** — переиспользует уже посчитанный общий префикс промпта между запросами.

**Throughput:** в 5–20 раз выше, чем у наивного HuggingFace, — это и есть причина, по которой vLLM стал выбором по умолчанию для self-hosted LLM.


## Q10. (!) Что такое Hugging Face TGI?

**Text Generation Inference (TGI)** — собственный LLM-сервер Hugging Face и прямой конкурент vLLM. Это тот движок, на котором работают платные Inference Endpoints HF, поэтому он хорошо интегрирован с экосистемой Hub.


```bash
docker run --gpus all -p 8080:80 \
  ghcr.io/huggingface/text-generation-inference:latest \
  --model-id meta-llama/Llama-3-8B-Instruct
```

**Что умеет** (набор почти как у vLLM):
- OpenAI-совместимый API.
- Continuous batching.
- Quantization (bitsandbytes, GPTQ, AWQ).
- Tensor parallelism.
- Production-ready — лежит в основе Hugging Face Inference Endpoints.

**TGI против vLLM:** функционально они очень близки. На практике TGI чуть проще поднять, vLLM обычно чуть быстрее по throughput. Разница невелика, поэтому выбор чаще диктуется тем, в чьей экосистеме вы уже находитесь, а не цифрами бенчмарка.


## Q11. Что такое TensorRT-LLM от NVIDIA?

**TensorRT-LLM** — движок LLM-inference от NVIDIA, выжимающий максимум из их же железа. Под капотом он компилирует модель в TensorRT-движок, заточенный под конкретную GPU, и использует низкоуровневые kernels (FP8, FlashAttention-2). Цена этой скорости — потеря гибкости.

**Плюсы:**
- Самый высокий throughput на NVIDIA GPU.
- Кастомные kernels (FP8, FA-2 и т. д.).
- Тесная интеграция с Triton.

**Минусы (и почему его берут не все):**
- Заметно сложнее в настройке.
- Только NVIDIA — никакого AMD/Apple.
- Модель приходится **компилировать под каждую архитектуру GPU**: собрали под H100 — на A100 артефакт не поедет.

**Когда брать:** когда критична максимальная производительность на NVIDIA и в команде есть экспертиза, чтобы пройти сложную настройку. В остальных случаях vLLM/TGI дают близкий результат с куда меньшими усилиями.


## Q12. Что такое Ollama и для чего он?

**Ollama** — простейший способ запустить LLM локально: одна команда `ollama run llama3` скачивает модель и поднимает её с OpenAI-совместимым API. Это «Docker для LLM» — вся возня с весами, форматами и зависимостями спрятана.

```bash
ollama pull llama3
ollama run llama3
```

**Чем удобен:**
- Установка одной командой, кроссплатформенность (Mac, Linux, Windows).
- OpenAI-совместимый API на `http://localhost:11434` — код, написанный под OpenAI, работает без изменений.
- Под капотом — **llama.cpp**, поэтому быстро на Apple Silicon и умеет CPU.
- Библиотека готовых моделей (Llama, Mistral, Qwen, ...) ставится в одно действие.

**Сценарии применения:**
- Локальная разработка и эксперименты.
- POC, где данные нельзя отдавать наружу (приватность).
- Edge-развёртывания.

**Подводный камень:** Ollama — это один инстанс без оптимизаций под многопользовательскую нагрузку. Для production-масштаба с параллельными пользователями он не предназначен — там нужен vLLM/TGI с continuous batching.


## Q13. Что такое llama.cpp и зачем CPU-inference?

**llama.cpp** — реализация инференса LLM на C++, которая позволяет запускать модели **на обычном CPU** (с опциональным GPU-ускорением). Это база, на которой стоят Ollama и LM Studio: именно она делает возможным запуск больших моделей без дорогой видеокарты — за счёт агрессивной квантизации.

```bash
./llama-cli -m models/llama-3-8b.gguf -p "Hello"
```

**Чем характерен:**
- Inference на CPU реально работает (медленно, но работает).
- Свой формат **GGUF** — это уже квантованные веса модели.
- Низкое потребление памяти за счёт квантизации (4-bit, 5-bit, 8-bit).
- Быстро на Apple Silicon (бэкенд Metal).
- Лежит в основе Ollama и LM Studio.

**Уровни квантизации** — выбор между размером и качеством:
- `Q4_K_M` — 4-bit, сбалансированный вариант по умолчанию.
- `Q8_0` — 8-bit, качество почти как у оригинала, но больше памяти.
- `Q2_K` — 2-bit, самый компактный и быстрый, но качество заметно проседает.

**Практический итог:** благодаря этой квантизации llama.cpp в 2025 позволяет запустить **70B-модель прямо на MacBook** — то, что без квантизации потребовало бы серверной GPU.


## Q14. (!) Как работает continuous batching и PagedAttention?

Проблема, которую это решает: генерация — пошаговый процесс, разные запросы заканчиваются в разное время, и при наивном батчинге короткие запросы простаивают, ожидая самый длинный в пачке. GPU при этом недозагружен.

**Наивный (статический) батчинг:** ждём, пока batch заполнится, обрабатываем его целиком, пока не закончится самая длинная последовательность. Latency и утилизация страдают.

**Continuous batching (vLLM):**
- Последовательности (sequences) разной длины крутятся в общем батче вместе.
- Как только последовательность сгенерировала свой конец, она «выходит» из батча, а на освободившееся место сразу заходит новый запрос.
- За счёт этого **GPU всегда занят** — нет простоя в ожидании самого медленного.

```
Time 1: batch = [seq1 (token 1), seq2 (token 1), seq3 (token 1)]
Time 2: seq1 finished. batch = [seq4 (token 1), seq2 (token 2), seq3 (token 2)]
Time 3: ...
```

**PagedAttention** — техника vLLM для управления памятью, которая делает continuous batching возможным. KV cache хранится **постранично** (по аналогии с виртуальной памятью в ОС), а не одним непрерывным блоком на запрос. Это убирает фрагментацию: память под кэш выделяется маленькими страницами по мере необходимости, поэтому в GPU помещается заметно больше параллельных запросов.

**Эффект:** связка continuous batching + PagedAttention даёт в 5–10 раз более высокий throughput по сравнению с наивным батчингом.


## Q15. (!) Что такое KV cache и зачем он нужен?

**KV cache** — это кэш промежуточных значений attention (**K**ey и **V**alue) для уже обработанных токенов. Зачем он: при авторегрессионной генерации каждый новый токен в attention «смотрит» на все предыдущие; без кэша их Key/Value пришлось бы пересчитывать на каждом шаге заново. KV cache сохраняет эти значения один раз и переиспользует — это превращает квадратичную работу в линейную.

```
Generate token 1: process tokens 0
Generate token 2: process tokens 0, 1 (но 0 уже cached)
Generate token 3: process tokens 0, 1, 2 (но 0, 1 cached)
```

**Цена — память.** KV cache растёт линейно с длиной последовательности и числом одновременных запросов. На длинных контекстах он может занимать **больше, чем сами веса модели**, и именно он, а не веса, чаще всего упирается в потолок GPU-памяти при serving.

**Оптимизации** (все нацелены на то, чтобы кэш занимал меньше):
- **PagedAttention** (vLLM) — постраничное хранение без фрагментации (см. Q14).
- **Квантизация KV cache** (FP8) — хранить значения в меньшей точности.
- **GQA (Grouped Query Attention)** — несколько attention-голов делят одни K/V, голов в кэше меньше.
- **MQA (Multi-Query Attention)** — крайний случай GQA: все головы делят одну K/V-голову.

**Контекст на 2025:** современные модели (Llama 3, GPT-4) штатно используют GQA именно ради экономии KV cache.


## Q16. (!) Что такое квантизация и какие форматы бывают (FP16, INT8, INT4, GPTQ, AWQ)?

**Квантизация** — хранение весов модели в меньшей разрядности (например, INT4 вместо FP16), чтобы модель занимала меньше памяти и работала быстрее. Суть компромисса: меньше бит на вес → меньше памяти, но и точность чисел грубее, поэтому качество немного падает. Главная выгода — вместить большую модель в доступную GPU.

| Формат | Биты | Память | Качество |
|--------|------|--------|----------|
| FP32 | 32 | 1x (база) | Лучшее |
| FP16 / BF16 | 16 | 0.5x | Минимальная потеря |
| INT8 | 8 | 0.25x | Заметная потеря |
| INT4 | 4 | 0.125x | Существенная потеря (но пригодно) |

**Современные методы квантизации** (отличаются тем, насколько умно они выбирают, где терять точность):
- **GPTQ** — post-training квантизация в 4-bit (применяется к уже обученной модели).
- **AWQ (Activation-aware Weight Quantization)** — учитывает значимость весов по активациям и обычно даёт качество выше, чем GPTQ.
- **FP8** — нативно поддерживается на NVIDIA H100+, почти без потери качества.
- **BitsAndBytes** — библиотека квантизации от Hugging Face, удобна для быстрого старта.

**Зачем это на практике:** 70B-модель в FP16 весит **140 ГБ** и не влезает в одну GPU; в INT4 — **35 ГБ**, и помещается в одну A100/H100. То есть квантизация напрямую решает, нужен вам один GPU или кластер.

**Компромисс:** обычно качество падает на ~1–3% — для большинства задач это приемлемая цена за кратное сокращение памяти.


## Q17. Как работает speculative decoding?

**Speculative decoding** — приём ускорения генерации: маленькая «черновая» модель быстро **предлагает** сразу N токенов вперёд, а большая «целевая» модель **проверяет** их все за один forward pass. Идея в том, что проверить N кандидатов одним прогоном дешевле, чем сгенерировать те же N токенов по одному большой моделью.

```
Small model: "The cat sat on the [mat, dog, sofa, ...]"
Big model: verify these candidates → accept "The cat sat on the mat", reject rest
```

**Почему качество не страдает:** финальное слово всегда за большой моделью — она принимает только те предложенные токены, которые совпали бы с её собственным выбором, и отбрасывает остальные. Поэтому результат идентичен обычной генерации, меняется только скорость.

**Эффект:** ускорение в 2–3 раза без потери качества.

**Поддержка:** реализовано в vLLM, TGI, TensorRT-LLM.


## Q18. Чем различаются tensor parallelism и pipeline parallelism?

Оба способа распределяют одну модель по нескольким GPU, но режут её по-разному.

**Tensor parallelism (TP):** разрезает каждый слой **поперёк** — разные части одного слоя (например, половины attention-голов) считаются на разных GPU параллельно. GPU работают одновременно над одним слоем, поэтому нужен быстрый обмен между ними (NVLink).
```
GPU 1: half of attention heads
GPU 2: other half
```

**Pipeline parallelism (PP):** разрезает модель **вдоль** — разные слои живут на разных GPU и работают по конвейеру (один отдал результат — другой подхватил). Обмена меньше, но GPU частично простаивают в ожидании предыдущей стадии («пузырь» конвейера).
```
GPU 1: layers 1-10
GPU 2: layers 11-20
```

**Когда это нужно:** когда модель **не помещается** в память одной GPU. TP — основной выбор внутри одного узла с NVLink; PP — когда надо растянуть модель ещё и между узлами.

```bash
# vLLM с TP=4 (4 GPUs)
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3-70B \
  --tensor-parallel-size 4
```

**Пример расчёта:** 70B в FP16 = 140 ГБ — в одну GPU не влезает; TP=2 разносит её на две H100 по 80 ГБ (около 70 ГБ весов на каждую), и модель стартует.


## Q19. (!) Как горизонтально масштабировать LLM serving?

**Топология:** `Load Balancer` раскидывает входящий трафик на несколько одинаковых реплик, каждая из которых сидит на своей GPU:

- `Load Balancer` → `vLLM Pod 1` (GPU)
- `Load Balancer` → `vLLM Pod 2` (GPU)
- `Load Balancer` → `vLLM Pod 3` (GPU)

Принцип тот же, что у любого stateless-сервиса: ставим несколько реплик за балансировщиком. Особенность LLM — реплика тяжёлая (целая GPU) и долго стартует.

**Развёртывание в K8s:**
- Каждый pod — vLLM/TGI с одной или несколькими GPU.
- Балансировщик раскидывает запросы (round-robin или least-connection).
- Автомасштабирование по глубине очереди (queue depth), а не по CPU — для LLM именно очередь отражает перегрузку (см. Q21).

**Подводные камни:** GPU-поды дорогие даже в простое, поэтому держать много «про запас» накладно. При этом холодный старт медленный — загрузка весов в GPU занимает минуты, и реактивное автомасштабирование не успевает за всплесками. Поэтому масштабировать нужно с прогревом и запасом, а не «впритык».


## Q20. Что такое GPU sharing (MIG, MPS)?

Проблема: маленькая модель занимает пару гигабайт, а GPU у вас на 80 ГБ — отдавать ей целиком одну видеокарту расточительно. GPU sharing позволяет разделить один физический GPU между несколькими нагрузками. Есть два механизма.

**MIG (Multi-Instance GPU)** — аппаратное разбиение: A100 и H100 можно нарезать на меньшие изолированные «виртуальные GPU», каждый со своей памятью и вычислителями.

```
A100 (80GB) → 7× MIG (10GB each)
```

Каждый такой MIG-слайс — изолированный GPU: соседи не влияют друг на друга по памяти и не мешают по производительности.

**MPS (Multi-Process Service)** — программный механизм: несколько процессов делят один GPU без жёсткой изоляции. Гибче MIG, но процессы конкурируют за ресурсы и могут влиять друг на друга.

**Когда применять:** когда модели маленькие (< 10 ГБ) и занимать под каждую целый A100 расточительно. MIG, например, позволяет разместить до 7 моделей на одной GPU вместо семи отдельных видеокарт.


## Q21. Зачем масштабировать LLM по queue depth (глубине очереди)?

Привычная метрика автоскейлинга — загрузка CPU — для LLM-сервера обманчива: GPU может быть занят на 100%, а CPU при этом почти спит. Куда честнее отражает перегрузку **глубина очереди** — сколько запросов ждёт обработки. Поэтому HPA настраивают на неё.

```yaml
# K8s HPA
metrics:
  - type: External
    external:
      metric:
        name: queue_depth
      target:
        type: AverageValue
        averageValue: 10
```

**Триггер:** если в очереди в среднем больше 10 запросов — добавить pod.

**Подводный камень:** холодный старт GPU-пода — это 1–3 минуты на загрузку весов. Пока новый pod поднимается, всплеск нагрузки уже прошёл, и реактивное масштабирование за ним не успевает.

**Как обойти:**
- **Прогрев (pre-warm)** — всегда держать запасной поднятый pod, чтобы не ждать холодного старта.
- **Предиктивное масштабирование** — поднимать реплики заранее по известному паттерну нагрузки (например, к пиковым часам).
- **Каскад по размеру модели** — на пике обслуживать дешёвой моделью поменьше, эскалируя к крупной только когда без неё не обойтись.


## Q22. (!) Что такое OpenAI-совместимый API и зачем он?

vLLM, TGI, Ollama и почти все остальные сервера реализуют **OpenAI-совместимый API** — те же эндпоинты и формат запросов/ответов, что у OpenAI. Это де-факто стандарт индустрии, и держатся его ради одного: совместимости с уже написанным кодом.

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://my-vllm:8000/v1",
    api_key="dummy"  # vLLM не требует auth по default
)

response = client.chat.completions.create(
    model="meta-llama/Llama-3-8B",
    messages=[{"role": "user", "content": "Hello"}]
)
```

**Зачем это нужно:** это **drop-in замена** OpenAI — весь существующий клиентский код (включая официальный SDK) работает без переписывания, меняется только `base_url`, указывающий на ваш сервер вместо api.openai.com.

**Практическая выгода — плавная миграция:** можно стартовать на OpenAI API, а когда масштаб дорастёт до окупаемости self-host (см. Q2), переключиться на свой vLLM сменой одной строки конфигурации, не трогая логику приложения.


## Q23. Как работает потоковая отдача ответа (streaming)?

При генерации модель выдаёт токены по одному, и стриминг отдаёт их клиенту по мере готовности, а не ждёт, пока соберётся весь ответ. Включается флагом `stream=True`, после чего ответ читается как поток кусочков (chunks).

```python
stream = client.chat.completions.create(
    model="...",
    messages=[...],
    stream=True
)

for chunk in stream:
    print(chunk.choices[0].delta.content, end="")
```

Технически vLLM и TGI отдают поток через SSE (Server-Sent Events) — тот же транспорт, что использует OpenAI.

**Зачем это нужно:** стриминг критичен для UX. Без него пользователь смотрит на пустой экран все 30 секунд генерации; со стримингом текст начинает появляться почти сразу, и воспринимаемая задержка резко падает, хотя полное время ответа то же.


## Q24. (!) Какой GPU выбрать (A100, H100, RTX 4090, ...)?

**Главный критерий выбора — объём памяти**, потому что именно он определяет, влезет ли модель (вместе с KV cache) в GPU. Производительность вторична: если модель не помещается, никакая скорость не поможет. Дальше всё упирается в баланс памяти, цены и того, datacenter-карта это или потребительская.

| GPU | Память | Стоимость | Лучше всего для |
|-----|--------|-----------|-----------------|
| **H100** (80 ГБ) | 80 ГБ HBM3 | ~$30K | Production, лучшая производительность |
| **A100** (40/80 ГБ) | 40–80 ГБ | ~$15–20K | Рабочая лошадка |
| **L40s** (48 ГБ) | 48 ГБ | ~$8–10K | Бюджетный production |
| **RTX 4090** (24 ГБ) | 24 ГБ | ~$2K | Разработка, небольшие модели |
| **RTX A6000** (48 ГБ) | 48 ГБ | ~$5K | Разработка с моделями покрупнее |
| **MacBook M-серии** | unified memory | $$ | Локальная разработка (Apple Silicon) |

**Где арендовать в облаке:**
- **AWS p4d/p5** — A100/H100.
- **GCP A3** — H100.
- **Azure ND H100v5**.
- **CoreWeave, Lambda Labs** — специализированные провайдеры, обычно дешевле гиперскейлеров.

**Быстрый подбор под размер модели** (это следствие правила «память решает»):
- **7B** — хватает RTX 4090 (24 ГБ).
- **70B** — A100/H100, как правило с квантизацией.
- **405B** — один GPU не справится, нужен мульти-GPU кластер из H100.


## Q25. (!) On-prem или облачные GPU — что выгоднее?

Развилка та же, что и аренда против покупки: **облако дешевле на старте и при неравномерной нагрузке, своё железо — при стабильной нагрузке 24/7 на горизонте года.** Решает утилизация: GPU дорог, и если он работает почти всегда, своя карта окупает разовую покупку; если простаивает — выгоднее платить за часы аренды.

**Облако:**
- Плюсы: нулевые затраты на старте, автомасштабирование, несколько регионов.
- Минусы: очень дорого на масштабе ($3–10/час за A100); сами H100 в дефиците, мощностей может банально не быть.

**On-prem (своё железо):**
- Плюсы: дешевле на масштабе (окупаемость 3–12 месяцев), полный контроль над данными и конфигурацией.
- Минусы: крупные вложения на старте ($30K+ за H100); своя забота о датацентре, питании и охлаждении; вся сложность MLOps на вас.

**Гибрид** (частый компромисс): своё железо держит базовую постоянную нагрузку, облако подхватывает всплески — так не переплачиваешь за пики и не простаиваешь дорогим железом.

**Эмпирическое правило:** при утилизации 24/7 on-prem окупается за 6–12 месяцев.


## Q26. Когда использовать spot-инстансы для inference?

**Spot/Preemptible** — это незадействованные мощности облака за полцены и дешевле, но с условием: провайдер может **забрать** инстанс в любой момент, дав лишь ~2 минуты предупреждения. Поэтому ключевой вопрос — переживёт ли ваша нагрузка внезапное отключение.

**Что это значит для inference:**
- Плюс: на 50–90% дешевле обычных инстансов.
- Минусы: при отзыве пропадает состояние в памяти и текущие запросы падают; для критичного realtime это неприемлемо.

**Где подходит** (везде, где прерывание не фатально и работу можно перезапустить):
- **Batch inference** — прервали, перезапустили батч.
- **Генерация эмбеддингов** — идемпотентна, повтор не вредит.
- **Фоновая обработка** без жёстких дедлайнов.
- **Окружения dev/staging**.

**Где не подходит:** realtime-трафик с пользователями, где надёжность и предсказуемая latency важнее экономии.


## Q27. (!) Какие частые проблемы в model serving?

Большинство этих проблем сводятся к двум первопричинам: GPU-память конечна, а GPU дорог, поэтому любой простой или раздувание памяти бьёт по бюджету. Список — по сути карта рисков:

1. **OOM (нехватка памяти)** — модель не влезает в GPU. Лечится квантизацией или раскладкой на несколько GPU.
2. **Медленный холодный старт** — загрузка весов занимает минуты. Прогревать инстансы заранее.
3. **Рост очереди** — автомасштабирование отстаёт, копится backpressure. Скейлить по queue depth с запасом (см. Q21).
4. **Недозагрузка GPU** — наивный батчинг и одиночные запросы оставляют GPU полупустым. Лечится continuous batching.
5. **Узкое место в сети** — большие запросы/ответы при длинном контексте упираются в пропускную способность.
6. **Сложность версионирования** — обновить модель без простоя (downtime) нетривиально; нужна горячая замена/канарейка.
7. **Неконтролируемый рост затрат** — GPU дорогие, и каждый час простоя — это прямые потери.
8. **Регресс качества** — после квантизации ответы становятся хуже; нужно мерить, а не верить «на глаз».
9. **Расхождение с API** — self-hosted модель ведёт себя иначе, чем привычный OpenAI (мелкие отличия в обработке промптов и шаблонах).
10. **Отсутствие мониторинга** — без метрик latency/throughput/ошибок непонятно, что вообще происходит, и проблемы из списка выше ловятся уже постфактум.


## Q28. (!) Как выбрать serving-стек под свою задачу?

Сначала разделите два мира: **LLM** (генеративные модели — тут нужен continuous batching и KV cache) и **классический ML** (классификация, эмбеддинги — тут важнее multi-framework и удобство деплоя). Внутри каждого мира выбор сужают экосистема и приоритет (throughput, простота, максимум перформанса). Дерево ниже формализует эту логику.

**Дерево решений:**

```
LLM serving в production?
├── Open-source LLM, max throughput?
│   → vLLM (default 2025)
├── Hugging Face ecosystem, want managed?
│   → TGI или HF Inference Endpoints
├── NVIDIA, want max perf?
│   → TensorRT-LLM + Triton
├── Local dev / edge?
│   → Ollama (under the hood llama.cpp)
└── Multi-framework, classical ML?
    → Triton (general-purpose)

Classical ML?
├── PyTorch?
│   → TorchServe или BentoML
├── TensorFlow?
│   → TF Serving
└── Multi-framework?
    → Triton

Custom code, easy deploy?
└── BentoML или FastAPI + Pydantic
```

**Если запоминать одно правило (2025):** для LLM в production — **vLLM**, для локальной разработки — **Ollama**. Остальные ветки дерева — это уже частные случаи под конкретную экосистему или приоритет.
