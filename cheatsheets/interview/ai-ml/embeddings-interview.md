## Q1. (!) Что такое embedding?

**Embedding** — это числовое представление данных (текст, изображение, аудио) в виде **вектора** в многомерном пространстве. Каждое число вектора — координата объекта по одному из «смысловых измерений», а само положение в пространстве кодирует смысл объекта.

```
"кошка"    → [0.12, -0.45, 0.78, ..., 0.03]  (1536 чисел)
"котёнок"  → [0.14, -0.43, 0.76, ..., 0.05]  (близкий к "кошка")
"автомобиль" → [-0.33, 0.51, 0.02, ..., 0.91] (далёкий от "кошка")
```

**Ключевое свойство:** семантически похожие объекты получают близкие векторы. Именно поэтому смысл можно сравнивать арифметикой — измеряя расстояние между векторами, а не сопоставляя слова.

**Где применяется:**
- Семантический поиск (semantic search)
- RAG retrieval
- Кластеризация
- Рекомендации
- Поиск аномалий (anomaly detection)
- Классификация (embeddings + linear layer)


## Q2. (!) Зачем нужны embeddings — что они дают по сравнению с поиском по словам?

Embeddings решают главную проблему классического поиска: он находит только **совпадения слов**, а не **совпадения смысла**. Релевантный документ, в котором нет ни одного слова из запроса, лексический поиск пропускает.

**Без embeddings** (BM25, поиск по ключевым словам):
```
Query: "горячий напиток"
Doc: "кофе бодрит"
Match: 0 (нет общих слов)
```

**С embeddings:**
```
emb("горячий напиток") близко к emb("кофе бодрит")
Match: 0.85
```

Embeddings улавливают **семантику**, а не только совпадение токенов: «горячий напиток» и «кофе бодрит» оказываются рядом в пространстве, потому что близки по смыслу. Это и сделало возможными semantic search, RAG и рекомендации «по похожести».


## Q3. (!) Как устроена и обучается embedding-модель?

Embedding-модель — это **transformer (обычно encoder-only)**, который обучают так, чтобы похожие тексты он отображал в близкие векторы, а непохожие — в далёкие. Само пространство выстраивается не вручную, а **контрастным обучением**: модель буквально «притягивает» правильные пары и «расталкивает» неправильные.

**Логика обучения:**
1. Берут пары семантически похожих текстов (или triplets).
2. Обучают модель так, чтобы их embeddings были близки.
3. Negative samples (несвязанные тексты) — наоборот, отталкивают друг от друга.

За счёт миллионов таких примеров пространство постепенно «раскладывает» смысл по координатам.

**Loss-функции** (как именно формулируется «притянуть/оттолкнуть»):
- **Contrastive loss** — пары (похожие/непохожие)
- **Triplet loss** — anchor + positive + negative
- **InfoNCE** — multi-class contrastive (один positive против многих negatives)

**Выход:** вектор нужного размера. Его получают из последнего hidden state с помощью pooling — усреднением по токенам (mean) либо взяв вектор служебного токена `[CLS]`.


## Q4. Чем отличаются sparse и dense embeddings?

Разница — в том, сколько измерений вектора заполнено и что они кодируют.

- **Dense embeddings** — небольшая размерность (сотни-тысячи), все измерения значимы и заполнены (`[0.1, -0.5, 0.3, ...]`). Каждое измерение — абстрактный «смысловой» признак.
- **Sparse embeddings** — размерность равна размеру словаря, но большинство измерений = 0 (`[0, 0, 0.7, 0, 0.3, ...]`). Ненулевые позиции соответствуют конкретным словам.

**Примеры sparse:** TF-IDF, веса BM25, SPLADE (современный обучаемый sparse).

**Когда что лучше:**
- **Dense** точнее передаёт семантику (синонимы, перефразы), но спотыкается на точных терминах — артикулах, кодах, редких именах, которых не было в обучении.
- **Sparse** наоборот: безошибочно ловит точные термины (коды, имена), но плохо понимает смысл и синонимы.

**Hybrid** объединяет оба подхода, чтобы закрыть слабые стороны каждого: dense даёт семантику, sparse — точные совпадения.


## Q5. (!) Что представляют собой модели OpenAI text-embedding-3?

`text-embedding-3` (2024) — линейка embedding-моделей OpenAI из двух вариантов: дешёвого `small` и более качественного `large`.

| Модель | Размерность | Стоимость |
|-------|------|------|
| `text-embedding-3-small` | 1536 (можно truncate) | $0.02 / 1M tokens |
| `text-embedding-3-large` | 3072 (можно truncate) | $0.13 / 1M tokens |

**Чем выделяется:**
- **Matryoshka** — размерность можно обрезать без сильной потери качества (1536 → 512 проходит нормально), экономя память и стоимость хранения.
- **Низкая цена** по сравнению с LLM API.
- **Multilingual** — хорошо работает на популярных языках, хуже на низкоресурсных.
- Контекст 8K токенов на входе.

```python
response = client.embeddings.create(
    model="text-embedding-3-small",
    input="Hello, world!",
    dimensions=512  # truncate (matryoshka)
)
```

В 2025 — **выбор по умолчанию** для большинства случаев: лучший баланс цены, качества и простоты.


## Q6. (!) Что особенного в Cohere Embed v3?

Cohere Embed v3 (2023+) — embedding-модель, заточенная под retrieval, с сильным multilingual-вариантом.

| Модель | Размерность | Языки |
|-------|------|-----------|
| `embed-english-v3.0` | 1024 | английский |
| `embed-multilingual-v3.0` | 1024 | 100+ языков |

**Главная фишка — `input_type`.** Модель различает, что именно эмбеддится: документ для индекса (`search_document`), поисковый запрос (`search_query`), либо вход для `classification`/`clustering`. Запрос и документ оптимизируют под разные распределения, поэтому асимметричный поиск (короткий запрос против длинного документа) работает заметно лучше, чем у симметричных моделей.

```python
response = co.embed(
    texts=["Hello"],
    model="embed-english-v3.0",
    input_type="search_document"  # vs "search_query"
)
```

**Итог:** отличный multilingual и часто **лучше OpenAI** на retrieval-бенчмарках.


## Q7. (!) Что такое Voyage AI и чем он интересен?

Voyage AI — стартап, который делает только embeddings и потому держит верх по качеству; именно его embeddings рекомендует Anthropic.

**Модели — упор на специализацию под домен:**
- `voyage-large-2-instruct` — лучшее общее качество
- `voyage-code-2` — для кода
- `voyage-multilingual-2` — для многих языков
- `voyage-finance-2` — под финансовый домен

**Почему его выбирают:**
- Часто **state-of-the-art** на MTEB.
- Доменные модели бьют общие на своих данных (код, финансы) без необходимости fine-tuning.
- Интеграция с экосистемой Anthropic.

В **2025** — топовый выбор для production RAG, когда нужно выжать максимум качества.


## Q8. (!) Что даёт библиотека Sentence Transformers?

`sentence-transformers` (UKP Lab) — Python-библиотека, которая позволяет запускать сотни open-source embedding-моделей **локально, без обращения к API**.

```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('sentence-transformers/all-MiniLM-L6-v2')

embeddings = model.encode(["Hello", "World"])
# numpy array shape (2, 384)
```

**Популярные модели — от компактных к более качественным:**
- `all-MiniLM-L6-v2` (384d) — компактная, быстрая, на CPU
- `all-mpnet-base-v2` (768d) — выше качество, медленнее
- `multi-qa-mpnet-base-cos-v1` — заточена под Q&A
- `paraphrase-multilingual-MiniLM-L12-v2` — multilingual

**Плюсы:** self-host (приватность данных и отсутствие платы за API), огромный выбор моделей на Hugging Face, простой fine-tuning.

**Минусы:** качество ниже топовых проприетарных (OpenAI/Cohere/Voyage), а для приемлемой пропускной способности нужен GPU — то есть бесплатность API оборачивается затратами на железо и эксплуатацию.


## Q9. Что такое модели BGE и E5?

BGE и E5 — два семейства сильнейших open-source embedding-моделей, которые конкурируют с проприетарными.

**BGE (BAAI General Embedding)** — от Beijing Academy of AI:
- `BAAI/bge-large-en-v1.5` (1024d) — одна из лучших open-source моделей для английского
- `BAAI/bge-m3` — multilingual и многофункциональная: выдаёт сразу dense + sparse + colbert-представления, то есть одна модель закрывает и семантику, и точные термины

**E5** — от Microsoft:
- `intfloat/multilingual-e5-large` — multilingual
- `intfloat/e5-mistral-7b-instruct` — крупная (7B), лучшее качество среди open-source ценой ресурсов на инференс

В **2025** качество open-source вплотную подтянулось к проприетарным решениям — для многих задач разрыв стал несущественным.


## Q10. (!) Как выбрать embedding-модель под задачу?

Универсального ответа нет — выбор сводится к взвешиванию нескольких ограничений. На собеседовании важно показать, что вы думаете не только о качестве, но и о приватности, стоимости и языке.

**Факторы выбора:**

1. **Качество:** отправная точка — **MTEB leaderboard**, но финальную проверку делать на своих данных.
2. **Стоимость:** API с оплатой за токены против self-host (плата за GPU).
3. **Latency:** локальный инференс против сетевого вызова API.
4. **Приватность:** при отправке в API данные покидают периметр → для PII нужен self-host.
5. **Языки:** нужен ли multilingual?
6. **Домен:** общий контент против специализированного (код, финансы, медицина).
7. **Размерность:** баланс между качеством и стоимостью хранения векторов.
8. **Длина контекста:** 512 токенов (BERT) против 8K (OpenAI) — определяет, как резать документы.

**Готовые рецепты на 2025:**
- **Production RAG без требований к приватности:** Voyage / OpenAI text-embedding-3-large
- **Жёсткая приватность (PII, on-prem):** BGE-M3, E5-large
- **Чувствительно к стоимости:** OpenAI text-embedding-3-small
- **Multilingual:** Cohere embed-multilingual-v3 / BGE-M3


## Q11. (!) Что такое бенчмарк MTEB и как им пользоваться?

MTEB (Massive Text Embedding Benchmark) — стандартный бенчмарк для embedding-моделей; его leaderboard на Hugging Face де-факто служит главной точкой сравнения.

**Почему ему доверяют:** он измеряет модель не на одной задаче, а на широком наборе — **56 датасетов, 8 типов задач**:
- Retrieval (релевантность поиска)
- Классификация
- Кластеризация
- Reranking
- Pair classification
- STS (semantic textual similarity)

**Топ моделей на 2025:**
1. NV-Embed (NVIDIA)
2. Voyage 3
3. BGE-EN-ICL
4. E5-mistral-7b
5. text-embedding-3-large

**Подвох:** MTEB — это усреднённое качество на публичных данных. Лидер таблицы не обязан быть лучшим на ваших задаче и домене, а под бенчмарк можно переобучиться. Поэтому MTEB — для шортлиста, а финальный выбор — по замеру на **своих данных**.


## Q12. (!) Какую размерность вектора выбрать?

Размерность — это **компромисс между качеством и стоимостью хранения/поиска**: больше измерений дают чуть выше качество, но линейно растят память и замедляют поиск.

**Ориентиры:**
- **Малые (256-512):** быстро, дёшево по хранению, качество чуть ниже.
- **Средние (768-1024):** стандарт для большинства open-source моделей.
- **Большие (1536-3072):** OpenAI, Cohere; больше места и медленнее поиск, качество чуть выше.

**Matryoshka embeddings (OpenAI v3, Nomic) снимают остроту выбора** — модель обучена так, что вектор можно укоротить постфактум:
```
Train на 3072d → truncate в любой меньший size без сильной потери
```

**Почему размерность бьёт по бюджету** — память растёт пропорционально:
```
1M vectors × 1536 dims × 4 bytes = 6 GB
1M vectors × 384 dims × 4 bytes  = 1.5 GB
```

**Рекомендация:** начинать с 512-1024d и увеличивать только тогда, когда замер показывает реальную нехватку качества.


## Q13. (!) Нужна ли нормализация embeddings?

Нормализация — это приведение вектора к единичной длине (`||v|| = 1`), то есть сохраняется только направление, а «длина» отбрасывается. Для семантического поиска важно именно направление, поэтому нормализация почти всегда уместна.

```python
import numpy as np
normalized = vector / np.linalg.norm(vector)
```

**Кто нормализует сам:** OpenAI и Cohere возвращают **уже нормализованные** векторы. Sentence Transformers — обычно нет, нужно явно передать `normalize_embeddings=True`.

**Зачем это нужно:**
- На нормализованных векторах **cosine similarity сводится к dot product** — а его считать быстрее (см. Q14).
- Vector DB умеют оптимизировать индекс под нормализованные векторы.

**Главный подвох — согласованность.** Если часть базы нормализована, а часть нет, расстояния станут несопоставимыми и поиск поедет. Нормализовать нужно либо всё, либо ничего.


## Q14. (!) В чём разница между cosine similarity и dot product?

Cosine similarity измеряет **угол** между векторами (только направление), а dot product учитывает ещё и **длину**. Формула связывает их напрямую:

```
cos(A, B) = (A · B) / (|A| × |B|)
```

Если **оба вектора нормализованы** (`|A| = |B| = 1`), знаменатель равен 1 и обе метрики совпадают:
```
cos(A, B) = A · B
```

**Практический вывод:** на нормализованных векторах dot product даёт тот же результат, но без деления на нормы — поэтому в production выбирают метрику `dot` (выигрыш ~10-30% по latency). Cosine оставляют, когда нормализацию гарантировать нельзя.

```python
# В Pinecone, Weaviate, Qdrant
metric = "dot"  # вместо "cosine" если уже normalized
```


## Q15. Какой лимит токенов на входе у embedding-моделей?

У каждой embedding-модели есть максимальная длина входа — всё, что сверх лимита, модель проигнорирует или отвергнет. Разброс между моделями огромный:

| Модель | Макс. токенов |
|-------|-----------|
| OpenAI text-embedding-3 | 8191 |
| Cohere embed-v3 | 512 (!) |
| BGE-large | 512 |
| Voyage-large-2 | 16000 |
| Sentence Transformers (на базе BERT) | 512 (обычно) |

**Почему это важно:** у Cohere и BGE лимит всего **512 токенов** = ~400 английских слов — короткий абзац. Целый документ туда не влезет, поэтому его обязательно разбивают на чанки до эмбеддинга. Иначе хвост текста просто не попадёт в вектор.


## Q16. Что делать с текстами длиннее лимита модели?

Когда текст превышает `max_tokens`, есть четыре стратегии — от простой и теряющей информацию до более качественных:

1. **Truncate** — просто обрезать до максимума (быстро, но теряете хвост текста).
2. **Chunk** — разбить на кусочки и эмбеддить каждый отдельно (ничего не теряется).
3. **Сначала суммаризировать** (LLM) → эмбеддить summary (сжимает смысл, но добавляет стоимость и риск потерять детали).
4. **Embedding pooling** — объединить векторы чанков (mean / max / первый чанк).

**Рекомендация для RAG:** не полагаться на truncation, а делать **правильный chunking** на стадии препроцессинга (см. [RAG](rag-interview.md)) — так, чтобы каждый чанк гарантированно влезал в лимит модели, и эмбеддить каждый чанк отдельно. Это сохраняет полный текст и даёт более точный retrieval.


## Q17. (!) Как работают multilingual embeddings?

Multilingual-модель обучена сразу на множестве языков и помещает их в **одно общее пространство**: одинаковая по смыслу фраза на разных языках получает почти одинаковый вектор.

```
emb("hello") ≈ emb("привет") ≈ emb("你好")
```

Именно это общее пространство и делает возможным поиск через языковую границу — язык запроса перестаёт иметь значение.

**Модели:**
- **Cohere embed-multilingual-v3** — 100+ языков
- **BGE-M3** — multilingual + многофункциональная
- **OpenAI text-embedding-3** — хорошо для популярных языков, хуже для низкоресурсных
- **paraphrase-multilingual-MiniLM** (sentence-transformers)

**Где применяется:**
- международные продукты
- cross-lingual search
- документы на корейском ↔ запрос на английском


## Q18. Что такое cross-lingual search?

Cross-lingual search — поиск, при котором запрос **на одном языке** находит документы **на другом**. Это прямое следствие общего пространства multilingual-моделей (Q17): вектор запроса и вектор релевантного документа оказываются рядом независимо от языка.

```
Indexed: documents на русском
Query: на английском
Result: relevant Russian docs
```

```python
# Index Russian docs
docs_emb = model.encode(russian_docs)
vector_db.upsert(docs_emb, ...)

# Search with English query
query_emb = model.encode("How to login?")
results = vector_db.search(query_emb)
# Returns Russian docs about login
```

**Качество:** multilingual-модели обычно **немного хуже** монолингвальных на конкретном языке, но **намного лучше** в cross-lingual-задачах.


## Q19. (!) Как устроены image embeddings и при чём тут CLIP?

CLIP (Contrastive Language-Image Pre-training) от OpenAI помещает **изображения и текст в одно общее пространство**. Ключевая идея: картинку и её текстовое описание модель обучали сближать, поэтому вектор фото кошки оказывается рядом с вектором фразы «a photo of a cat». Это и позволяет сравнивать текст с изображением напрямую.

```python
import clip
model, preprocess = clip.load("ViT-B/32")

image_features = model.encode_image(image)  # 512d
text_features = model.encode_text(["a photo of a cat"])

similarity = (image_features @ text_features.T)
```

**Что это даёт:**
- **поиск изображений по тексту** («найди фото кошки») — текст-запрос ищется среди image-векторов;
- **zero-shot классификация** — картинку относят к классу, чьё текстовое описание ближе, без отдельного обучения классификатора;
- **multi-modal RAG** (изображения + текст в одном индексе).

**Альтернативы:** SigLIP (качество выше), BLIP-2, OpenCLIP (open-source).


## Q20. Что такое audio embeddings?

Audio embeddings — векторное представление звука (речи, музыки, шумов), позволяющее сравнивать аудио по сходству так же, как тексты. Выбор модели зависит от того, что вы эмбеддите:

- **Whisper embeddings** — для речи
- **CLAP** (Contrastive Language-Audio Pretraining) — общее пространство text + audio, по аналогии с CLIP для картинок
- **Wav2Vec 2.0** — для произвольного аудио
- **VGGish** — для музыкальных тегов

**Где применяется:** поиск/рекомендации похожей музыки, признаки для распознавания речи, классификация аудио.

Направление менее зрелое, чем текстовые embeddings, — меньше готовых моделей и бенчмарков.


## Q21. Что такое multimodal embeddings?

Multimodal embeddings — это единое векторное пространство сразу для **нескольких модальностей** (текст + изображение + видео + аудио). Раз все типы данных лежат в одном пространстве, их можно сравнивать между собой напрямую — искать видео по тексту, картинку по звуку и т.д.

**Модели на 2025:**
- **CLIP** — текст + изображение
- **ImageBind** (Meta) — 6 модальностей сразу (текст, изображение, аудио, видео, IMU, depth)
- **LanguageBind** — расширение ImageBind
- **Cohere Embed v3 multimodal** — текст + изображение (2024)

**Где применяется:**
- cross-modal search («найди видео, похожее на этот текст»)
- multimodal RAG

В **2025** — растущая, но всё ещё менее зрелая область, чем text-only embeddings.


## Q22. (!) Как снизить стоимость embeddings?

Стоимость складывается из двух статей — оплата вызовов API и хранение векторов; оптимизируют обе. Рычаги, от самых эффективных:

1. **Выбрать правильную модель** — нужна ли large? Часто small достаточно при кратно меньшей цене.
2. **Уменьшить размерность** (Matryoshka) — 1536 → 512 экономит ~3x на хранении.
3. **Кешировать embeddings** — тот же текст не эмбеддить дважды (см. Q23).
4. **Batch-запросы** — embedding API часто дешевле и быстрее в batch.
5. **Self-host** на больших объёмах (>10M embeddings/месяц) — фиксированная плата за GPU обгоняет поток оплаты за токены.
6. **Асинхронная обработка** — эмбеддить пакетами ночью, а не в realtime.
7. **Избегать повторного эмбеддинга** — если документ не изменился, не пересчитывать вектор.

**Масштаб расходов:**
```
1M docs × avg 500 tokens × $0.02/1M tokens = $10
с text-embedding-3-small
```

То есть embeddings — копеечная статья по сравнению с генерацией через LLM API.



## Q23. (!) Как кешировать embeddings?

Embedding для конкретного текста **детерминирован** — одна и та же строка всегда даёт один вектор. Значит, результат можно закешировать по хешу текста и не платить за повторный вызов API.

```python
import hashlib

def get_embedding(text):
    cache_key = hashlib.md5(text.encode()).hexdigest()
    if cached := redis.get(f"emb:{cache_key}"):
        return cached
    embedding = openai.embeddings.create(input=text, model="...")
    redis.set(f"emb:{cache_key}", embedding, ex=86400)
    return embedding
```

**Когда кеш окупается:**
- повторяющиеся запросы (популярные поиски);
- A/B-тестирование разных моделей на одних и тех же запросах;
- dev / staging окружения, где гоняют один и тот же набор данных.

**Когда не стоит:**
- embeddings часто обновляются (кеш протухает быстрее, чем пригождается);
- стоимость хранения кеша выше стоимости API — на практике редкость, кеш обычно дешёвый.


## Q24. Что такое Matryoshka embeddings и как они обрезаются?

Matryoshka representation learning (MRL) — приём обучения, при котором важная информация концентрируется в **начале** вектора. Поэтому любой **префикс** вектора остаётся осмысленным embedding-ом меньшей размерности — как вложенные матрёшки.

```
3072-dim embedding → truncate первые 512 dims → still useful (5-10% quality loss)
```

**Зачем это нужно:**
- **многоуровневый поиск (tiered search)** — грубый и быстрый отбор кандидатов по 256d, затем точный rerank top-k по полным 1536d;
- **экономия хранения** — урезанный вектор занимает в 3-5 раз меньше места.

**Модели:** OpenAI text-embedding-3, Nomic embed.

```python
emb_full = openai.embeddings.create(model="text-embedding-3-large", input=text).data[0].embedding
# 3072 dims

emb_truncated = emb_full[:512]
# Можно использовать! Quality чуть ниже
```


## Q25. Что такое quantization embeddings (binary, int8)?

Quantization — это хранение каждого измерения вектора в меньшем числе байт ценой небольшой потери точности. Базовый `float32` занимает 4 байта на измерение; его сжимают:
- **fp16** — 2 байта на измерение (экономия 2x)
- **int8** — 1 байт на измерение (экономия 4x)
- **Binary** — 1 бит на измерение (экономия 32x)

**Binary quantization** — самый радикальный вариант: оставляем только знак каждого измерения.
```python
binary_vec = (vec > 0).astype(np.uint8)  # 1 bit per dim
# Compare через Hamming distance — XOR + popcount, очень быстро
```
Сравнение бинарных векторов идёт через Hamming distance (XOR + popcount) — это процессорные инструкции, поэтому поиск не только дешевле по памяти, но и кратно быстрее.

**Компромисс точность/экономия:**
- Binary: ~5-10% потери recall, но в 32x меньше памяти и быстрее.
- int8: ~1-2% потери, экономия 4x — почти бесплатный выигрыш.

В **2025** binary quantization стала стандартом для **гигантских масштабов** (100M+ векторов), где хранить float32 уже непрактично.


## Q26. (!) Когда стоит дообучать embedding-модель?

Короткий ответ: fine-tuning оправдан, только когда **готовая модель уже даёт плохой recall на ваших данных**, а причина — в специфике домена. Это не первый шаг, а крайняя мера после смены модели и улучшения chunking.

**Когда оправдан:**
- **доменная лексика**, которую общие модели плохо понимают (медицина, юриспруденция, код);
- **узкие задачи** (например, сопоставление тикетов поддержки);
- замеры показывают низкий recall на ваших запросах.

**Когда не нужен:**
- типовой контент (новости, блоги, общие документы) — общие модели и так хороши;
- маленький датасет (< 1000 примеров) — не на чем учиться;
- нет ML-экспертизы для подготовки данных и валидации.

**Компромисс:** fine-tuning стоит ~$500-5000 на обучение плюс постоянная поддержка (переобучение при дрейфе данных), тогда как готовая модель обходится в $0 сверх обычных вызовов.


## Q27. (!) Как дообучить модель в sentence-transformers?

Суть та же, что и при обучении с нуля (Q3): подаём пары/тройки и дообучаем модель сближать релевантные тексты. Достаточно собрать пары `(query, relevant_doc)` и запустить `model.fit`.

```python
from sentence_transformers import SentenceTransformer, InputExample, losses
from torch.utils.data import DataLoader

# Pairs: (query, positive_doc) или triplets (query, positive, negative)
train_examples = [
    InputExample(texts=["query1", "relevant doc1"]),
    InputExample(texts=["query2", "relevant doc2"]),
    ...
]

model = SentenceTransformer('sentence-transformers/all-MiniLM-L6-v2')
train_loss = losses.MultipleNegativesRankingLoss(model)

train_dataloader = DataLoader(train_examples, batch_size=16, shuffle=True)
model.fit(train_objectives=[(train_dataloader, train_loss)], epochs=3)
model.save("my-fine-tuned-model")
```

**Какой loss выбрать** — зависит от формата данных:
- **MultipleNegativesRankingLoss** — самая частая; берёт остальные примеры в батче как negatives, поэтому достаточно только положительных пар;
- **TripletLoss** — когда есть явные тройки anchor + positive + negative;
- **CosineSimilarityLoss** — когда у пар есть числовая оценка похожести.

**Где основная работа:** не в коде, а в сборе **golden pairs** `(query, relevant_doc)` — качество дообучения упирается именно в качество и объём этих пар.


## Q28. (!) Где применяются embeddings помимо RAG?

RAG — лишь одно из применений. По сути любая задача, сводящаяся к «насколько эти объекты похожи», решается через embeddings:

1. **Семантический поиск** — по смыслу, а не по ключевым словам.
2. **Рекомендации** — «похожие объекты» (Netflix, Amazon).
3. **Кластеризация** — группировка документов без разметки.
4. **Поиск аномалий** — выбросы (outliers) в векторном пространстве.
5. **Классификация** — embedding + linear classifier поверх него.
6. **Дедупликация** — поиск почти дублирующихся документов.
7. **Персонализация** — профиль пользователя как embedding (среднее по понравившимся объектам).
8. **Сопоставление A/B-вариантов.**
9. **Обнаружение плагиата.**
10. **Построение графа знаний** — entity linking.


## Q29. Какие частые ошибки и проблемы с embeddings?

Почти все проблемы сводятся к одному правилу: **запрос и документы должны жить в одном согласованном пространстве**. Нарушите согласованность — и поиск тихо деградирует, без явных ошибок.

1. **Embedding drift** — модель обновили, векторы стали другими → нужно re-embed всю базу, иначе старые и новые несопоставимы.
2. **Несовпадение моделей query/doc** — запрос и документы эмбеддены разными моделями (или разными `input_type`).
3. **Неверная метрика расстояния** — например, Euclidean для нормализованных векторов.
4. **Плохой chunking** — эмбеддят целые документы вместо чанков, размывая смысл.
5. **Нет нормализации там, где она нужна** (см. Q13).
6. **Короткие тексты** (1-2 слова) — слишком мало контекста, embedding получается шумным.
7. **Неконтролируемые затраты** — эмбеддят всё подряд без кеша.
8. **Деградация качества на узком домене** без fine-tuning.
9. **Multilingual-контент в монолингвальной модели** — плохое качество на других языках.
10. **Восприятие embedding как сжатия текста** — из вектора нельзя восстановить исходный текст, это представление смысла, а не архив.
