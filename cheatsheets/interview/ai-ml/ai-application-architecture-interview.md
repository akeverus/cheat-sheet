# Вопросы на собеседовании: `AI Application Architecture Patterns`

Архитектура AI-приложений — это не выбор «модной» технологии, а **инженерная задача**: подобрать комбинацию `prompt + RAG + fine-tune + agents` под конкретные требования (свежесть знаний, latency, cost, compliance). На senior-интервью спрашивают про фреймворк выбора, гибридные паттерны, сквозную референсную архитектуру, бюджеты latency/cost, антипаттерны и производственные стадии.

## Q1. (!) Какие 4 базовых паттерна AI-приложений?

Любое production-AI-приложение собирается из четырёх кирпичей: **Prompt Engineering, RAG, Fine-tuning и Agents**. Их редко используют по отдельности — но без понимания сильных и слабых сторон каждого нельзя осознанно собрать гибрид. Ключевое различие между ними — *где* живёт знание и поведение модели: в промпте, во внешнем индексе, в весах или в цепочке шагов.

| Паттерн | Что делает | Стоимость настройки | Стоимость запроса | Когда выбрать |
|---|---|---|---|---|
| **Prompt Engineering** | Zero/few-shot, system prompt, structured output (JSON schema) | $0 | низкая | Простые задачи, быстрое прототипирование, когда задача укладывается в context |
| **RAG** | Достаёт релевантный контекст из vector/keyword-индекса → LLM генерирует обоснованный (grounded) ответ | средняя (embedding-pipeline + индекс) | средняя (`embedding + LLM`) | Часто обновляемые знания, упор на факты, нужна атрибуция источников |
| **Fine-tuning** | Подгоняет веса модели под domain/стиль/формат | высокая (датасет + обучение) | как у базовой модели + амортизация обучения | Стабильный стиль/формат, узкий domain, нужна низкая latency на маленькой модели |
| **Agents** | Multi-step с tool use, планированием, рефлексией | средняя (проектирование инструментов) | высокая (5-15 вызовов LLM) | Open-ended задачи: код, ресёрч, автоматизация браузера, computer use |

Один и тот же `User Query` можно направить в любой из четырёх паттернов, и каждый даёт свой тип результата:

- `Prompt Engineering` → прямой ответ (Direct answer).
- `RAG` → обоснованный ответ с источниками (Grounded answer + sources).
- `Fine-tuning` → стилизованный ответ (Stylized answer).
- `Agents` → результат из нескольких шагов (Multi-step result).

**Ключевая идея:** это не «или-или». Каждый паттерн закрывает свою ось требований — свежесть знаний (RAG), стиль/формат (Fine-tune), сложность задачи (Agents), скорость старта (Prompt). Поэтому в production почти всегда получается **гибрид** (см. Q4-Q7), где паттерны компенсируют слабости друг друга.

## Q2. (!) Когда выбрать Prompt Engineering vs RAG vs Fine-tune vs Agents?

Выбор сводится к нескольким бинарным вопросам о задаче, которые отсекают неподходящие паттерны. Главные развилки: меняется ли знание часто, нужен ли особый стиль, и сколько шагов требует задача. Дерево решений ведёт по этим развилкам сверху вниз, начиная с новой AI-фичи:

- **Knowledge часто меняется?**
  - **Да** → **Сложная multi-step задача?**
    - **Да** → `Agents + RAG`.
    - **Нет** → `RAG`.
  - **Нет** → **Нужен специфический стиль/формат?**
    - **Да** → **Достаточно 2-3 few-shot?**
      - **Да** → `Prompt Engineering`.
      - **Нет** → `Fine-tuning`.
    - **Нет** → **Задача укладывается в context?**
      - **Да** → `Prompt Engineering`.
      - **Нет** → `Fine-tuning`.

**Как распознать паттерн по сигналу в требованиях:**

- «У нас 100k документов, обновляются каждый день» → **RAG**: факты живут вне модели, retrain на каждое обновление нереален.
- «Хотим всегда отвечать в нашем corporate-стиле» → **Fine-tune** (или system prompt + few-shot, если стиль простой и стабильный).
- «Пользователь говорит "сделай рефакторинг репозитория"» → **Agents**: задача open-ended, нужны планирование и tool use.
- «5 категорий, FAQ» → **Prompt Engineering** + structured output: задача фиксированная и помещается в context.

**Эмпирическое правило:** начинай с самого дешёвого (Prompt) и эскалируй на следующий паттерн только тогда, когда увидел конкретный, воспроизводимый провал качества — а не «на всякий случай». Каждый шаг вверх по сложности удваивает стоимость поддержки стека.

## Q3. Как выбрать паттерн по матрице требований?

Дерево из Q2 даёт быстрый ответ, но реальная фича имеет сразу несколько требований (latency, cost, privacy, свежесть). Матрица показывает, как каждый паттерн ведёт себя по каждой оси — чтобы найти тот, что не проваливается ни в одном критичном для вас пункте:

| Требование | Prompt | RAG | Fine-tune | Agent |
|---|---|---|---|---|
| **Свежесть знаний** (часто меняются) | плохо | отлично | плохо (нужен retrain) | отлично (через RAG-tool) |
| **Адаптация стиля/формата** | средне | плохо | отлично | средне |
| **Latency < 500ms** | отлично | хорошо | отлично (малая модель) | плохо |
| **Cost < $0.01/request** | хорошо | средне | отлично (FT малая) | плохо |
| **Data privacy / on-prem** | через self-hosted | через self-hosted | отлично (свой weights) | сложнее (tools) |
| **Compliance / audit trail** | средне | отлично (источники) | средне | отлично (trace steps) |
| **Open-ended задачи** | плохо | средне | плохо | отлично |
| **Холодный старт (нет данных)** | отлично | средне (нужен корпус) | плохо | средне |

**Как пользоваться:** выпиши требования своей фичи как строки матрицы, отбрось паттерны с «плохо» в критичных для тебя строках — и из оставшихся выбери самый дешёвый. Часто ни один паттерн не покрывает все оси, и тогда матрица прямо указывает на гибрид (например, RAG для свежести + Fine-tune для стиля).

## Q4. (!) RAG + Fine-tune — зачем комбинировать?

Их комбинируют, потому что они отвечают на разные вопросы — *что* сказать и *как* сказать, — и пытаться закрыть оба одним паттерном бесполезно. Классическая ошибка ровно в этом: учить стилю через **RAG** (контекст не меняет манеру речи модели) или зашивать факты в **Fine-tune** (веса быстро устаревают, а переобучение дорогое).

**Правильное разделение ответственности:**

- **Fine-tune** учит модель, **как отвечать**: стиль, формат, тон, терминология, структура вывода. Это стабильные вещи — их и стоит «зашить» в веса.
- **RAG** даёт модели, **что отвечать**: актуальные факты, документы, политики. Это меняющиеся вещи — их держат снаружи, чтобы обновлять без переобучения.

Поток связки выглядит так:

- `Query` → `Vector Search` (Retriever), куда знания поставляет `Knowledge Base` (Docs).
- `Vector Search` передаёт найденный context в `Fine-tuned LLM` (модель знает domain style).
- `Fine-tuned LLM` → `Stylized grounded answer` (стилизованный обоснованный ответ).

**Пример — медицинский ассистент.** Fine-tune учит модель медицинской терминологии и формату SOAP-notes (стабильное «как»), RAG подтягивает свежие guidelines и карту конкретного пациента (меняющееся «что»). На выходе — ответ в правильном клиническом стиле и с актуальными фактами.

**Когда не комбинировать:**
- Маленькое приложение — один паттерн дешевле в разработке и поддержке.
- Если fine-tune не даёт измеримого прироста качества над связкой prompt + RAG, он не нужен: лишний слой обучения без выигрыша.

## Q5. (!) Agents + RAG — retrieval как tool?

Здесь retrieval перестаёт быть жёстким первым шагом pipeline (`retrieve → generate`) и становится **одним из инструментов агента** — наравне с web-поиском, SQL и вычислениями. Разница принципиальная: в обычном RAG поиск выполняется всегда, а агент сам решает, нужен ли он вообще.

```python
tools = [
    {"name": "search_docs", "description": "Search internal knowledge base"},
    {"name": "search_web", "description": "Search the web"},
    {"name": "query_sql", "description": "Run SQL on analytics DB"},
    {"name": "calculate", "description": "Run Python expression"},
]
```

**Плюсы:**
- Агент **сам решает**, когда нужен поиск, а когда хватит знаний из весов — лишние запросы к индексу не делаются.
- Может **итеративно уточнять** запрос, если первый результат нерелевантен (`search_docs("policy") → search_docs("policy 2024 amendment")`).
- Может **комбинировать источники** в одном ответе: документы из RAG + цифры из SQL + свежие данные из web.

**Минусы:**
- Дороже: каждый шаг агента — отдельный вызов LLM.
- Риск зацикливания: без ограничителя агент может бесконечно делать retrieve.
- Качество труднее оценивать — нет фиксированного pipeline, путь к ответу каждый раз разный.

**Сценарий применения:** сложный ресёрч, customer support с разнородными источниками, code-агенты.
**Когда не стоит:** простой Q&A по одному источнику — обычный RAG дешевле, быстрее и предсказуемее.

## Q6. Как работает каскадирование промптов (дешёвая → дорогая модель)?

Суть каскада: **дешёвая модель** обрабатывает запрос первой, а **дорогая** подключается только тогда, когда дешёвой не хватило. Это экономит деньги, потому что большинство запросов в реальном трафике простые и не требуют флагманской модели.

Поток каскада по шагам:

1. `Query` идёт в дешёвую модель (`Haiku`/`Mini`).
2. Проверяем уверенность ответа (Confidence high?):
   - **Да** → возвращаем ответ дешёвой модели (Return answer).
   - **Нет** → передаём в дорогую модель (`Sonnet`/`Opus`) и возвращаем её ответ (Return answer).

**Варианты каскадирования:**
- **Router-модель** — маленький LLM классифицирует intent и направляет запрос в специализированный pipeline.
- **Сначала дешёвый ответ** — генерируем им, и если confidence низкий, переспрашиваем дорогую модель.
- **Набросок + доводка** — маленькая модель пишет черновик, большая критикует и правит. Дорогих токенов тратится меньше, чем при генерации с нуля.

**Почему это выгодно:** если 70% запросов решает Haiku ($0.001), а оставшиеся 30% эскалируются к Sonnet ($0.03), усреднённая стоимость = `0.7*0.001 + 0.3*0.03 = $0.0097` — втрое дешевле, чем гнать все запросы через Sonnet за $0.03. Чем больше доля простых запросов, тем сильнее экономия.

## Q7. Как сделать fallback с RAG на fine-tuned при низкой уверенности?

Идея гибрида: RAG отвечает, пока находит релевантный контекст, а когда не находит — управление передаётся fine-tuned-модели, которая знает domain «по умолчанию», из весов. Это страхует случаи, которые корпус ещё не покрывает.

1. Сначала пробуем **RAG** (retrieve + generate).
2. Оцениваем уверенность: relevance-score ретривера плюс неуверенность самой модели.
3. Если **уверенность низкая** (retrieval-score ниже порога или модель ответила «не знаю»):
   - Fallback к **fine-tuned-модели**, которая отвечает из domain-знаний в весах.
   - Или эскалация к **человеку** (human-in-the-loop).

```python
result = rag_pipeline(query)
if result.retrieval_score < 0.5 or "I don't know" in result.answer:
    result = fine_tuned_model.answer(query)
    if result.confidence < 0.7:
        escalate_to_human(query)
return result
```

**Сценарий применения:** customer support, где RAG покрывает не все вопросы, но fine-tuned-baseline даёт приемлемый ответ там, где корпус молчит.

## Q8. (!) Какая референсная архитектура у production AI-приложения?

Канонический скелет, который масштабируется от MVP до enterprise без переписывания. Запрос проходит по слоям: вход и защита → выбор модели → вызов LLM и инструментов → стриминг ответа, и параллельно всё трассируется. Каждый слой решает одну задачу, поэтому его можно менять независимо от остальных.

Поток запроса по слоям:

- `Client` (Web/Mobile) → `API Gateway`.
- `API Gateway` → `Rate Limiter + Auth`.
- `Rate Limiter + Auth` → `Model Router` (cheap vs expensive).
- `Model Router` → `LLM Service`.
- `LLM Service` → `Tool Executor`, который обращается к трём хранилищам: `Vector DB`, `SQL DB` и `Redis Cache`.
- `LLM Service` → `Streaming` (SSE/WebSocket) → обратно в `Client`.

Параллельные (служебные) связи:

- `LLM Service` пишет трассы (trace) в `Observability` (Langfuse/LangSmith).
- `Model Router` берёт конфиг (config) из `Prompt Registry` и из `Model Registry`.

**Слои:**

| Слой | Назначение | Технологии |
|---|---|---|
| **API Gateway** | Маршрутизация, TLS, публичная точка входа | Kong, Envoy, NGINX, AWS ALB |
| **Rate Limiter + Auth** | JWT, лимиты на пользователя/тенанта | Redis token bucket, Auth0, Keycloak |
| **Model Router** | Выбор `model` по запросу/тенанту | Custom + LiteLLM/Portkey |
| **LLM Service** | Вызов модели (OpenAI/Anthropic/локальной) | LangChain, Spring AI, LiteLLM |
| **Tool Executor** | Выполнение function calls (RAG, SQL, web) | Custom + sandbox |
| **Vector DB** | Индекс эмбеддингов | Pinecone, Weaviate, pgvector, Qdrant |
| **Cache** | Embedding/semantic/exact-match кеш | Redis, Mem0 |
| **Streaming** | SSE/WebSocket для TTFT UX | Spring WebFlux, FastAPI, Vercel AI SDK |
| **Observability** | Трейсы, evals, версии промптов | Langfuse, LangSmith, Helicone |
| **Prompt/Model Registry** | Версионирование промптов/моделей | Promptlayer, Langfuse, GitOps |

**Принципы, на которых это держится:**
- **Stateless service-слой** — состояние не хранится в сервисе, поэтому он масштабируется горизонтально простым добавлением реплик.
- **Модель и промпт берутся из конфига** — менять их можно без деплоя кода.
- **Async-friendly** — SSE отдаёт первый токен быстро (TTFT), долгие задачи уходят в jobs.
- **Трассируется всё** — каждый вызов LLM пишется в Langfuse, иначе отлаживать проблемы в проде невозможно.

## Q9. (!) Как работает router-слой (выбор модели по запросу)?

Router — слой, который для каждого входящего запроса решает, **какую модель вызвать**. Решение принимается по приоритетам: сначала жёсткие переопределения (тенант), потом смысл запроса (intent), потом раскатка фич и бюджет. Порядок проверок важен — более специфичные правила должны срабатывать раньше общих.

```python
def route(request: Request) -> Model:
    # 1. Tenant override
    if request.tenant.preferred_model:
        return request.tenant.preferred_model
    # 2. Intent-based routing
    if request.intent == "code":
        return "claude-sonnet-4.5"
    if request.intent == "simple_faq":
        return "haiku"
    # 3. Feature flag (canary)
    if feature_flags.enabled("opus-rollout", request.user_id):
        return "claude-opus-4"
    # 4. Budget-based
    if request.tenant.budget_left < 0.10:
        return "haiku"  # degraded
    return DEFAULT_MODEL
```

**Стратегии маршрутизации:**

| Стратегия | Когда | Плюсы | Минусы |
|---|---|---|---|
| **Статическая (по фиче)** | разным фичам — разные модели | просто | негибко |
| **Intent-классификатор** | router-LLM выбирает | оптимально по cost | +latency, +cost самого классификатора |
| **Каскадирование** | дешёвая → дорогая | экономия | сложная eval |
| **A/B-тестирование** | сравнение моделей | data-driven | накладные расходы на сплит трафика |
| **Tenant-config** | enterprise/BYOK | контроль на стороне тенанта | сложность эксплуатации |

**В production** обычно используют гибрид всех стратегий: статические дефолты как база, tenant override поверх них, и раскатка новых моделей через feature flag.

## Q10. Что такое Tool Executor и как изолировать инструменты?

Tool Executor — компонент, который выполняет function calls агента (`search_web`, `run_sql`, `execute_python`, `send_email`). Поскольку аргументы этих вызовов генерирует LLM, а не человек, executor нельзя считать доверенным: к нему относятся как к выполнению недоверенного кода и оборачивают защитой.

**Меры безопасности:**
- **Sandbox** для исполнения кода — Docker, gVisor, Firecracker, браузер в Chrome sandbox. Сбежавший из песочницы код не дотянется до хоста.
- **Allowlist доменов** для web-запросов, чтобы агента нельзя было заставить ходить куда попало.
- **Read-only DB user** по умолчанию для SQL-инструмента — даже ошибочный запрос ничего не сломает.
- **Human-in-the-loop** для деструктивных действий (отправить email, списать с карты) — необратимое действие требует подтверждения человека.

**Архитектура (поток tool call):**

- `LLM` отправляет `tool_call` в `Tool Executor`.
- `Tool Executor` проверяет разрешение (Allowed?):
  - **No** → возвращает ошибку модели (Error to LLM).
  - **Yes** → исполняет в `Sandbox`.
- `Sandbox` → `Result`, который возвращается обратно в `LLM`.
- Параллельно `Sandbox` пишет audit-запись в `Audit Log`.

**Что нужно в реализации (Spring/Python):** реестр инструментов, валидация аргументов по схеме (Pydantic / JSON Schema), таймаут на каждый tool call (иначе зависший инструмент держит весь запрос), retry с idempotency-ключами (чтобы повтор не выполнил действие дважды).

## Q11. (!) Как разложить latency-бюджет (цель < 2s)?

Цель — **TTFT < 1s** (первый токен) и полный ответ < 2s. Чтобы уложиться, общий бюджет режут на этапы и каждому назначают свой лимит — тогда видно, какой этап «съедает» время и что оптимизировать в первую очередь.

Пример раскладки бюджета end-to-end (~2s), последовательно по этапам, сгруппированным по секциям:

- **Edge:** Auth + rate limit — ~10 ms.
- **Retrieve:** Embedding query — ~30 ms; Vector search — ~100 ms; Rerank (optional) — ~50 ms.
- **LLM:** Prompt assembly — ~20 ms; LLM prefill (TTFT) — ~500 ms; Token streaming — ~1000 ms.
- **Tools:** Optional tool call — ~500 ms (после стриминга).

**Разбивка:**

| Этап | Бюджет |
|---|---|
| Auth + rate limit | ~10ms |
| Embedding-запрос | 20-50ms |
| Vector search | 50-200ms |
| Rerank (cross-encoder) | 30-150ms |
| Сборка промпта | <20ms |
| LLM prefill (TTFT) | 300-800ms (зависит от длины context) |
| Token streaming (полный) | 500-2000ms (зависит от output) |
| Tool call (каждый) | 500-3000ms |

**Где сокращать время:**
- **Streaming** — пользователь видит первый токен через TTFT, а не ждёт ответ целиком; воспринимаемая задержка падает в разы.
- **Параллелизм** — retrieve и подготовку промпта запускать одновременно, а не последовательно.
- **Кеш эмбеддингов** для часто повторяющихся запросов — экономит embedding-вызов целиком.
- **Меньше context** — каждый лишний токен в промпте удлиняет prefill (TTFT).
- **Меньшая или специализированная модель** для быстрых ответов — она и дешевле, и быстрее на простых задачах.

## Q12. (!) Сколько стоит запрос: prompt vs RAG vs agent?

Порядок стоимости зависит от паттерна и растёт на порядки от чистого промпта к агенту. Цифры для grounded-диалогов (цены Q4 2025, USD):

| Паттерн | Расчёт | Стоимость запроса |
|---|---|---|
| **Чистый prompt (GPT-4o/Sonnet)** | 1k in + 500 out токенов | $0.01 — $0.10 |
| **RAG** | embedding ($0.0001) + 3k context + 500 out | $0.02 — $0.15 |
| **Agent (5-15 вызовов LLM)** | каждый шаг 2k in + 1k out × N | $0.10 — $2.00 |
| **Fine-tuned base** | как base + амортизированная стоимость обучения (разовая ~$100-10000) | базовая цена + амортизация |
| **Каскадирование (70% Haiku, 30% Sonnet)** | усреднённо | $0.005 — $0.015 |

**Почему агент дороже всех:** его стоимость линейно растёт с числом шагов, а каждый шаг — это полный вызов LLM с in- и out-токенами:
```
cost_agent ≈ N_steps × (avg_in_tokens × price_in + avg_out_tokens × price_out)
```
Например, 10 шагов × (3000 × $3/1M + 500 × $15/1M) = $0.165 — на порядок дороже одиночного промпта.

**Чек-лист снижения стоимости:**
- Кеширование (см. Q17) — повторные запросы бесплатны.
- Prompt caching (Anthropic / OpenAI prompt-cache) — скидка на неизменный префикс промпта.
- Меньше context — класть только релевантные chunks, а не весь документ.
- Каскадирование (Q6) — дешёвая модель закрывает простые запросы.
- Batch API — скидка 50% при SLA < 24ч.
- Self-hosted — выгоден при высоких объёмах и стабильной нагрузке.

## Q13. Какие метрики качества у каждого паттерна?

| Паттерн | Сильные стороны | Слабые стороны | Метрики |
|---|---|---|---|
| **Prompt Engineering** | гибкость, скорость итераций | нестабильное качество, дрейф промптов | exact-match, BLEU, LLM-as-judge |
| **RAG** | меньше галлюцинаций (если grounded) | узкое место — качество retrieval | groundedness, recall@k, MRR |
| **Fine-tune** | следование стилю/формату | факты устаревают, качество генерации стагнирует | task-specific accuracy, format-conformance |
| **Agents** | open-ended задачи, tool use | failure rate накапливается по шагам | task success rate, число шагов, $ за задачу |

Ключевая мысль: у каждого паттерна своя «уязвимая» метрика. У RAG это качество retrieval (groundedness, recall@k) — если ретривер промахнулся, дальше уже неважно, насколько хороша модель. У агентов — накопление ошибок: вероятность провала всей цепочки растёт с числом шагов.

**Eval-инфраструктура:** датасеты в Langfuse / LangSmith + автоматический LLM-judge + регрессионные тесты на CI, чтобы ловить просадку качества до релиза.

## Q14. (!) Что такое TTFT, TPOT и зачем streaming для UX?

Это две latency-метрики, которые по-разному влияют на восприятие:

- **TTFT (Time To First Token)** — время от запроса до первого токена. Главная **UX-метрика**: пользователь воспринимает её как «отзывчивость» системы.
- **TPOT (Time Per Output Token)** — сколько ms уходит на каждый следующий токен. Задаёт «скорость печати» ответа.

**Зачем streaming:** он бьёт именно по TTFT. Без streaming пользователь ждёт ~2s до **первого** символа (нужно сгенерировать весь ответ). Со streaming он видит первый токен через ~500ms — воспринимаемая задержка падает примерно вчетверо, хотя полное время генерации не меняется.

**Стек:**
- **Backend:** SSE (Server-Sent Events) — простой однонаправленный поток поверх HTTP/1.1, легко проходит через прокси (в отличие от WebSocket).
- **Frontend:** `EventSource` API или Vercel AI SDK `useChat`.

**Подводные камни:**
- Посреди стрима **нельзя просто сделать retry** — часть токенов уже ушла пользователю; нужна стратегия возобновления (resumability) либо честный старт заново.
- Tool calls обычно не стримятся: объект `tool_call` нужен целиком, прежде чем его выполнять.
- Логирование стрима: дописывать токены в trace по мере их прихода, а не одним блоком в конце.

## Q15. (!) Что строить на стадиях PoC → MVP → Production?

Главное — на каждой стадии своя цель и свой объём работ. Опасность в том, чтобы строить production-grade инфраструктуру до того, как доказана сама решаемость задачи. Поэтому на ранних стадиях намеренно срезают углы, а добавляют надёжность только тогда, когда понятно, что фича нужна.

| Стадия | Цель | Что строим | Что НЕ строим |
|---|---|---|---|
| **PoC (1-2 недели)** | Доказать, что задача решаема | Jupyter notebook, захардкоженный prompt, OpenAI API, ручная eval на 20 примерах | Не строим: UI, auth, observability, масштабирование |
| **MVP (1-2 месяца)** | Реальные пользователи на dogfood | обёртка LangChain/LlamaIndex, простой UI, базовый auth, минимальное логирование, eval-датасет 100-500 примеров | Не строим: multi-tenant, BYOK, продвинутый routing, FT |
| **Production (3+ месяца)** | Надёжно, масштабируемо, наблюдаемо | референсная архитектура (Q8), полноценные evals, CI/CD промптов, observability, fallback-и, multi-tenancy, compliance | Перестаём срезать углы |

**Подводный камень:** прыгать через стадии. «Сразу production-grade» без PoC — это месяцы, вложенные в фичу, которая в итоге может вообще не работать.

## Q16. Каков путь эволюции: prompt → RAG → fine-tune → agent?

Это естественный порядок усложнения стека: каждый следующий шаг добавляют только тогда, когда предыдущий упёрся в потолок. Двигаться по нему стоит снизу вверх, а не выбирать сразу верхний уровень.

1. **Prompt** — пока его хватает, ничего больше не нужно.
2. **Prompt + Few-shot** — если разброс качества слишком высокий.
3. **RAG** — когда нужны актуальные или объёмные знания, не помещающиеся в промпт.
4. **Улучшенный RAG** (rerank, hybrid search, query rewriting) — когда базовый retrieval промахивается.
5. **Fine-tune** — когда стиль/формат не вытягиваются промптом или нужны скорость и низкий cost.
6. **Agents** — когда задача стала multi-step / open-ended.
7. **Multi-agent** — когда одиночный агент тонет в сложности задачи.

**Сигнал к переходу:** виден систематический, воспроизводимый failure mode — тогда добавляют следующий уровень. Переходить «потому что модно» нельзя: каждый шаг увеличивает сложность стека в 2-3 раза.

## Q17. (!) Какие слои кеширования у AI-приложений?

Кеш в AI-приложении — не один слой, а несколько на разных этапах pipeline: от детерминированных эмбеддингов (можно держать почти вечно) до точных ответов модели (живут недолго). Каждый слой ловит свой класс повторов и экономит свой ресурс — embedding-вызов, поиск, токены LLM.

| Слой | Что кешируется | TTL | Технологии |
|---|---|---|---|
| **Embedding cache** | text → embedding-вектор | долгий (текст детерминирован) | Redis, file cache |
| **Semantic cache** | похожий запрос → закешированный ответ (по cosine similarity) | средний | Redis Vector, Mem0, GPTCache |
| **Prompt cache** | переиспользование префикса у провайдера (system prompt, RAG context) | 5мин-1ч | Anthropic prompt cache, OpenAI prompt caching |
| **LLM response cache** | точное совпадение запроса → ответ | короткий (или инвалидация по событию) | Redis, Memcached |
| **Tool result cache** | аргументы tool call → результат | зависит от инструмента | Redis |

Порядок проверки кешей для запроса (`Query`):

1. **Semantic cache hit?**
   - **Yes** → возвращаем закешированный ответ (Return cached) — на этом всё.
   - **No** → переходим к проверке embedding-кеша.
2. **Embedding cache hit?**
   - **Yes** → пропускаем embedding-вызов (Skip embedding call).
   - **No** → считаем эмбеддинг запроса (Embed query).
3. Обе ветки (с готовым эмбеддингом и со свежесчитанным) сходятся в `Vector search`.
4. **Prompt cache prefix hit?**
   - **Yes** → вызов LLM с закешированным префиксом (LLM with cached prefix).
   - **No** → обычный вызов LLM (Normal LLM call).

**Эффект:** на «горячем» трафике кеш срабатывает в 30-60% случаев, и на этой доле запросов cost и latency падают примерно вдвое.

## Q18. Semantic cache или exact match — когда что выбрать?

Разница в том, по чему сопоставляются запросы — по точному совпадению строки или по близости смысла. Это определяет и hit rate, и риск отдать неверный ответ.

**Exact match cache** — `key = hash(query)`, срабатывает только на дословном повторе.
- Плюс: нулевой риск false positive — ключи совпали, значит запросы идентичны.
- Минус: низкий hit rate (1-5%) — малейшая разница в формулировке промахивается мимо кеша.

**Semantic cache** — `key = embedding(query)`, попадание, если cosine_similarity выше порога.
- Плюс: hit rate 20-40% — ловит перефразировки одного и того же вопроса.
- Минус: **риск false positive** — два запроса похожи по эмбеддингу, но различаются по смыслу, и пользователь получает чужой ответ.

**Какой когда:**

| Сценарий | Кеш |
|---|---|
| Финансы, медицина, юр. данные | Exact match |
| FAQ, базовый support | Semantic (порог ≥ 0.95) |
| Брейншторм / open-ended | Без кеша (нужна вариативность) |

**Рекомендация:** для semantic cache обязательно подключи **инвалидацию** при изменении knowledge base — иначе модель будет отдавать закешированные ответы, которые уже устарели после обновления данных.

## Q19. (!) Sync, async, streaming, batch — какие паттерны потока данных?

Это четыре способа доставить ответ клиенту, и выбор диктуется временем генерации и тем, ждёт ли пользователь у экрана. Короткие запросы — синхронно, долгие — асинхронно, чат — стримингом, не-realtime массив — батчем.

| Паттерн | Описание | Когда | Latency |
|---|---|---|---|
| **Synchronous** | `POST /ask → 200 OK { answer }` | короткие задачи (< 2s) | низкая |
| **Async с колбэком** | `POST /ask → 202 Accepted { job_id }` → webhook | долгие генерации, batch | высокая |
| **Streaming** | `POST /ask → SSE-поток токенов` | chat UX, codegen | TTFT низкий, полный — средний |
| **Batch** | загрузить файл → выходной файл (Anthropic/OpenAI batch API) | не realtime: ночное обогащение, evals | 0-24ч (на 50% дешевле) |

Async-паттерн по шагам (участники: `Client`, `Service`, `Queue`, `Worker`):

1. `Client` → `Service`: `POST /ask`.
2. `Service` → `Queue`: enqueue (ставит задачу в очередь).
3. `Service` → `Client`: `202 { job_id }` (немедленный ответ с идентификатором задачи).
4. `Queue` → `Worker`: process (воркер забирает задачу на обработку).
5. `Worker` → `Client`: `webhook { result }` (готовый результат уходит колбэком).

## Q20. Webhook или SSE для долгих генераций?

Выбор зависит от того, остаётся ли клиент на связи всё время генерации. Когда она занимает 10 с — 10 мин (deep research, coding-агент), держать открытое соединение не всегда возможно:

- **SSE** хорош, когда задача привязана к UI и пользователь смотрит на экран — соединение живёт, пока открыта вкладка.
- **Webhook** хорош, когда клиент может уйти и вернуться: интеграции backend → backend, где никто не ждёт у экрана.
- **Polling** — запасной вариант для сервисов без поддержки webhook.

**Рекомендация (гибрид):** SSE для UI плюс сохранение прогресса в БД. Если клиент отвалился, он сможет вернуться и **переподписаться** (resubscribe) на текущее состояние — генерация не теряется.

## Q21. (!) Какие бывают режимы отказа AI-системы и стратегии fallback?

Главный принцип: у каждого внешнего вызова должен быть явный путь отступления. Любой из них может отказать (провайдер, лимиты, контекст, бюджет), и без fallback такой вызов превращается в единую точку отказа. Ниже — типичные режимы отказа и реакция на каждый:

| Режим отказа | Симптом | Fallback |
|---|---|---|
| **Провайдер недоступен** | 5xx, таймауты | резервный провайдер (Anthropic ↔ OpenAI ↔ self-hosted) через gateway |
| **Rate limit (429)** | отказы | очередь + retry с jitter + переход на более дешёвую модель |
| **Превышена длина контекста** | ошибка API | сжатие контекста, summarize, меньше chunks |
| **Галлюцинация / неверный ответ** | плохой ответ | проверка groundedness → эскалация на человека |
| **Превышен бюджет по cost** | внутренний alert | graceful degradation (дешёвая модель / кеш / «недоступно») |
| **Медленный ответ (всплеск latency)** | > p95 | таймаут → fallback к кешу / более дешёвой модели |
| **Сбой инструмента** | инструмент вернул ошибку | повтор инструмента / альтернативный инструмент / сообщить LLM |
| **Prompt injection** | вредоносный ввод | input rails + sanitize + reject |

**Закрепление принципа:** проектируя fallback, идите по таблице — для каждого внешнего вызова заранее ответьте, что система сделает при его отказе. Если на какой-то строке ответа нет, это и есть будущая точка отказа.

## Q22. Что такое паттерн Inference Gateway (LiteLLM / Portkey / OpenRouter)?

**Inference Gateway** — единый API-слой над несколькими провайдерами, который централизует retry, fallback, кеширование, observability и RBAC. Вместо того чтобы хардкодить эту логику в каждом сервисе, её выносят в один шлюз — и все обращения к моделям идут через него.

Схема обращений: приложение (`App`) ходит не напрямую к провайдерам, а через `Inference Gateway` (LiteLLM/Portkey). Шлюз маршрутизирует запрос к одному из провайдеров — `OpenAI`, `Anthropic`, self-hosted `vLLM` или `OpenRouter` — и параллельно использует общий `Cache` и пишет `Logs`.

**Что это даёт:**
- Единый формат (OpenAI-compatible) для всех провайдеров — код приложения не знает, к кому реально идёт запрос.
- Централизованные fallback / retry / circuit breaker — пишутся один раз в шлюзе, а не в каждом сервисе.
- Rate limits на тенанта и трекинг cost «из коробки».
- Observability подключается одним местом, а не размазана по сервисам.
- A/B-тестирование моделей без изменений в коде приложения.

**LiteLLM proxy config (выдержка):**

```yaml
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
  - model_name: claude-sonnet
    litellm_params:
      model: anthropic/claude-sonnet-4-5
      api_key: os.environ/ANTHROPIC_API_KEY

router_settings:
  fallbacks:
    - gpt-4o: [claude-sonnet]
  retry_policy:
    num_retries: 3
    timeout: 30
```

**Когда не нужен:** один провайдер и < 1k запросов в день — накладные расходы на лишний слой не окупаются.

## Q23. (!) Как устроена multi-tenancy: промпты, индексы, лимиты на тенанта?

Корпоративный AI-app обслуживает несколько **тенантов** (организаций), и каждому нужны свои промпты, RAG-индекс, лимиты и бюджет. Главное здесь — изоляция: данные и ресурсы одного тенанта не должны протекать к другому. Ниже — что разделяют и как:

| Ресурс | Реализация |
|---|---|
| **Промпты** | prompt registry с namespace по tenant_id |
| **RAG-индекс** | отдельный namespace в Pinecone/Weaviate на каждого тенанта (или фильтр по tenant_id) |
| **Модели** | конфиг на тенанта: BYOK (bring-your-own-key) или общая модель с виртуальным бюджетом |
| **Rate limits** | token bucket на тенанта (Redis с ключом `rl:{tenant}:{user}`) |
| **Бюджеты по cost** | месячный лимит на тенанта, alert на 80%, жёсткое отсечение на 100% |
| **Fine-tuned-модели** | FT под конкретного тенанта (если кейс позволяет: enterprise) |
| **Изоляция данных** | row-level security в БД, шифрование ключом тенанта |

**Подводные камни — все про утечку изоляции:**
- **Утечка между тенантами в RAG** — забыли фильтр по tenant_id, и ретривер вернул чужие документы. Фильтр в ретривере должен быть строгим и обязательным.
- **Отравление общего кеша** — semantic cache без tenant_id в ключе отдаёт ответ, сгенерированный для другого тенанта.
- **BYOK-ключи** — хранить только в Vault, никогда в БД в открытом виде.

## Q24. (!) Как устроена security-архитектура: prompt injection, секреты, sandboxing?

Базовый принцип: всё, что приходит снаружи и всё, что выдаёт LLM, считается недоверенным. Поэтому вход фильтруют на «рельсах» до модели, а выход — после неё; секреты держат отдельно от промптов, а инструменты исполняют в песочнице. Модель угроз и контрмеры:

| Угроза | Защита |
|---|---|
| **Prompt injection (прямая)** | input rails (классификатор вредоносного ввода), строгое разделение ролей, ограничение набора доступных инструментов |
| **Непрямая prompt injection** (через RAG / web-инструмент) | sanitize полученного контента, content-filter LLM, относиться к выводу инструмента как к недоверенному |
| **Output rails** | проверка ответа: PII, признаки jailbreak, нарушение политик |
| **Утечка секретов** | API-ключи в Vault/AWS Secrets Manager, никогда в промптах/логах; redact PII перед логированием |
| **Sandboxing инструментов** | исполнение в Docker/gVisor, network allowlist, read-only FS, без креденшелов внутри |
| **Audit trails** | каждый LLM call + tool call + решение → audit log с user/tenant/timestamp |
| **Управление API-ключами** | ротация, скоупы на тенанта, отдельные ключи под каждое окружение |
| **Rate limiting** | защита от abuse и DoS по бюджету |

Поток через рельсы безопасности:

- `User input` → `Input Rails` (классификатор):
  - **safe** → передаём в `LLM`.
  - **unsafe** → отклоняем (Reject).
- Выход `LLM` → `Output Rails` (PII redact + проверка политик):
  - **safe** → отдаём ответ пользователю (Response).
  - **unsafe** → санитизируем или блокируем (Sanitize/Block).

**Дополнительно по compliance:** в регулируемых отраслях (фин, мед) перед отправкой клиенту все ответы проходят ревью человеком.

## Q25. Как спроектировать архитектуру под compliance (PII, GDPR, residency)?

При работе с PII и регулируемыми данными compliance — это не отдельный модуль, а набор требований, пронизывающих весь pipeline: от того, что мы вообще отправляем в LLM, до того, где физически лежат данные и как долго хранятся логи.

- **Слой PII-редактирования** перед отправкой в LLM (regex + ML-детектор) — провайдер не должен видеть персональные данные.
- **Data residency** — выбор региона для API через region-aware endpoints (Anthropic / Azure OpenAI), чтобы данные не покидали юрисдикцию.
- **No-training agreement** — API Anthropic / OpenAI по умолчанию не обучается на переданных данных.
- **Audit logging** — кто, что, когда и зачем; срок хранения задаётся compliance-окном.
- **GDPR consent** — явное согласие на использование AI-фич; право на забвение распространяется и на эмбеддинги.
- **Шифрование** — at-rest и in-transit; ключи на тенанта, где это возможно.
- **DPA / BAA** — Data Processing Agreement с провайдером (для HIPAA — только compliant-endpoints).
- **On-prem-вариант** — для самых строгих кейсов self-hosted (Llama 3, Mistral, vLLM), когда данные нельзя выпускать наружу вообще.

## Q26. Как мониторить стоимость и задавать бюджеты на тенанта/фичу?

Идея — сделать стоимость наблюдаемой и управляемой: сначала измерить расход с точностью до тенанта, пользователя и фичи, затем поставить лимиты, которые сработают до того, как счёт убежит вверх.

**Что трекать:**
- Токены in/out в разрезе `tenant`, `user`, `feature`, `model`.
- Потраченные $ на запрос (по прайс-листу провайдера).
- Аномалии: запрос с cost > p99 или резкий всплеск расхода.

**Где хранить:** time-series-БД (VictoriaMetrics, Prometheus) + дашборды в Grafana.

**Контроли (от мягких к жёстким):**
- **Бюджет на тенанта** — месячный лимит: мягкий alert на 80%, жёсткое отсечение на 100%.
- **Бюджет на фичу** — отдельный лимит для экспериментальных фич, чтобы эксперимент не съел весь бюджет.
- **Авто-throttle** — если расход за час превысил норму в 10 раз, временно ограничиваем (ловит runaway-сценарии вроде цикла в агенте).
- **Атрибуция cost в trace** — каждый Langfuse-span несёт `cost_usd`, чтобы видеть, какой именно вызов дорогой.

**Пример формулы:** `cost = (in_tokens × price_in + out_tokens × price_out) / 1_000_000`. Для GPT-4o (Q4 2025): in $2.5/1M, out $10/1M.

## Q27. (!) Какие архитектурные антипаттерны встречаются в AI-проектах?

Большинство этих ошибок объединяет одно: усложнение там, где оно не нужно, и отсутствие базовых инженерных практик (fallback, observability, evals). Самые частые находки на ревью:

| Антипаттерн | Симптом | Лечение |
|---|---|---|
| **Преждевременные агенты** | сложные multi-step pipelines там, где хватит workflow | Простой chain/workflow; агенты только если задача open-ended |
| **RAG вместо fine-tune для стиля** | пытаемся учить стилю через context — плохо работает | Fine-tune для стиля, RAG для фактов |
| **Захардкоженная модель** | `openai.chat.completions.create("gpt-4")` повсюду | model registry + config |
| **Нет стратегии fallback** | один провайдер → сбой = простой | inference gateway + резервный провайдер |
| **Нет observability** | «оно сломалось, не знаю почему» | Langfuse / LangSmith с первого дня MVP |
| **Только синхронность** | блокирующие 30-секундные запросы без streaming | SSE для UX, async для долгих задач |
| **Промпты прямо в коде** | промпты разбросаны по исходникам | prompt registry + version control |
| **Нет evals** | регрессия качества незаметна | golden dataset + CI eval |
| **Доверять всему, что выдаёт LLM** | injection / галлюцинации проскакивают | input + output rails |
| **«Чем больше context, тем лучше»** | заливка 100k токенов — дорого, качество падает | курируемый context (top-k + rerank) |

## Q28. Зачем feature flags и A/B-тестирование для AI-фич?

Поведение AI-фичи нельзя надёжно предсказать офлайн, поэтому новые модели и промпты выкатывают под контролем и проверяют на реальном трафике. Флаги дают безопасную раскатку, A/B — доказательство, что изменение реально лучше.

**Feature flags для AI:**
- Постепенная раскатка новой модели или промпта (1% → 10% → 50% → 100%) — проблему ловишь на 1%, а не на всех.
- Kill switch при инциденте — мгновенный откат без деплоя.
- Override на конкретного пользователя или тенанта.

**Инструменты:** LaunchDarkly, Unleash, Flagsmith, кастомные.

**A/B-тестирование:**
- Делим трафик между вариантами (модель A vs B, prompt v1 vs v2).
- Измеряем продуктовые метрики: удовлетворённость (thumbs up/down), конверсию, выполнение задачи.
- Проверяем статистическую значимость: набрать минимальный размер выборки, p-value < 0.05 — иначе разница может быть шумом.
- **Онлайн- и офлайн-evals** синхронизируют: онлайн-метрики сверяют с результатами на golden dataset.

**Пример:** новый prompt → 10% трафика → через 2 недели сравниваем thumbs-up rate. +5% — раскатываем, иначе откат.

## Q29. Что такое Edge AI: маленькая модель на устройстве + тяжёлая в облаке?

Это гибрид, где лёгкая модель на устройстве отвечает на простое и быстрое, а тяжёлую в облаке вызывают только для сложного. Так выигрывают по latency, приватности, офлайну и стоимости, не жертвуя качеством на трудных запросах.

- **На устройстве:** Apple Intelligence (3B), Phi-3-mini, Gemma 2B, ONNX runtime, WebGPU + WebLLM в браузере, MLC LLM на мобильных.
- **В облаке:** тяжёлые модели для сложных задач.

Поток маршрутизации запроса:

- `User device` → маленькая модель на устройстве (`Small model on-device`).
- Маленькая модель оценивает сложность запроса (Сложно?):
  - **Нет** → отдаёт локальный ответ (Локальный ответ).
  - **Да** → эскалирует в облачную модель (`Cloud LLM`), которая возвращает облачный ответ (Cloud response).

**Сценарии применения:**
- **Чувствительные к latency** — автодополнение, голос: круговая поездка в облако слишком медленная.
- **Приватность** — данные не покидают устройство.
- **Офлайн** — mobile, embedded без стабильной сети.
- **Стоимость** — инференс на устройстве пользователя бесплатен для вас.

**Компромисс:** маленькие модели слабее, поэтому критична логика маршрутизации — надёжно распознать «сложный» запрос и вовремя эскалировать в облако.

## Q30. Архитектура голосового агента: STT → LLM → TTS или Realtime API?

Выбор между двумя подходами — это компромисс «контроль против задержки». Классический pipeline собирается из отдельных моделей (гибко, но latency складывается), Realtime API делает всё одной multimodal-моделью (быстро, но контроля меньше).

**Pipeline-архитектура (классика):** звук проходит по цепочке `Mic` → `Speech-to-Text` (Whisper/Deepgram) → `LLM` → `Text-to-Speech` (ElevenLabs/OpenAI) → `Speaker`.

Плюсы: гибкость — можно выбрать любую LLM/STT/TTS; есть явный текстовый trace на каждом шаге.
Минусы: задержки складываются (STT 200ms + LLM 800ms + TTS 300ms = 1.3s+); barge-in (перебить агента голосом) сложно реализовать.

**Realtime API (OpenAI Realtime, Gemini Live):**
- Audio → Audio в одной multimodal-модели, без промежуточного текста.
- Latency ~300-500ms, нативный barge-in — модель сама понимает, что пользователь начал говорить.
- Минусы: меньше контроля, выше поминутная стоимость, vendor lock-in.

**Оптимизации (применимы к pipeline):**
- **Streaming STT** — начинаем LLM, не дожидаясь конца фразы.
- **Streaming LLM** — TTS озвучивает первые токены, пока генерируются остальные.
- **VAD (voice activity detection)** — детектор активности голоса для barge-in.

## Q31. Build или buy: своё решение или hosted, OSS или commercial?

Решение упирается в два фактора — масштаб (QPS) и уникальность требований. На старте и при малых объёмах выгоднее buy (фокус на продукте), при больших объёмах и нестандартных требованиях — build (экономика и контроль). Покомпонентная разбивка:

| Компонент | Build (своё) | Buy (hosted) |
|---|---|---|
| **Vector DB** | pgvector в существующей PG | Pinecone, Weaviate Cloud |
| **LLM Gateway** | свой proxy на FastAPI | Portkey, LiteLLM, OpenRouter |
| **Observability** | логи + Grafana | Langfuse Cloud, LangSmith |
| **Инфра для fine-tuning** | свой кластер H100 | OpenAI/Together/Anyscale FT API |
| **Prompt registry** | git + сервис | Promptlayer, Langfuse |

**Build выбирают, когда:** уникальные требования (compliance, кастомный retrieval, on-prem), есть инженерные ресурсы и нагрузка > 1k QPS — на таком объёме своё решение дешевле hosted.

**Buy выбирают, когда:** старт, эксперименты, небольшая команда, нужен фокус на продукте, нагрузка < 1k QPS.

**OSS или commercial:** OSS даёт больше контроля и дешевле на длинной дистанции, но требует своих ops; commercial — быстрее на старте, с SLA и поддержкой, но дороже и менее гибок.

## Q32. Реальные примеры: какие паттерны у Notion AI, Cursor, Perplexity, Devin?

Разбор показывает главное: ни один серьёзный продукт не построен на одном паттерне — все они гибриды. Высокоуровневая карта:

| Продукт | Базовая архитектура | Ключевые паттерны |
|---|---|---|
| **Notion AI** | RAG поверх документов workspace | индекс на каждый workspace, semantic search, structured output для action items |
| **Cursor** | Гибрид: длинный context (весь файл) + embedding-поиск (по кодовой базе) + tool use | speculative decoding, FT под код, multi-file context |
| **Perplexity** | RAG + агент: инструмент web-поиска + генерация цитат | онлайн-retrieval на каждый запрос, атрибуция источников в UI, streaming с inline-цитатами |
| **Devin** (Cognition) | Автономный coding-агент с долгоживущим исполнением | multi-step-планирование, sandboxed VM, self-reflection, human-checkpoint |
| **Claude apps (Artifacts, Projects)** | Workflow + инструменты: исполнение кода, анализ файлов, MCP | tool use, Projects = постоянный context (RAG-lite), Artifacts = structured output |
| **GitHub Copilot** | Edge (маленькая модель для автодополнения) + cloud (тяжёлая модель для чата) | каскадирование, FT под код, интеграция с IDE как поверхность инструментов |
| **ChatGPT Search** | Prompt + RAG + инструменты-агенты (browser, python) | маршрутизация инструментов, цитирование источников |

**Общий паттерн на 2025-2026:** все серьёзные продукты — **гибрид** (RAG + инструменты + немного FT + аккуратный prompt engineering), а не «чистый» один паттерн.
