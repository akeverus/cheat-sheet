# Вопросы на собеседовании: `Code Agents`

**Code agent** — это LLM-приложение, которое читает, навигирует и **редактирует кодовую базу** через набор tools (file ops, shell, git, search) и **итерирует** до прохождения тестов. Спектр огромен — от inline-автокомплита (Copilot) до полностью автономных SWE-агентов в VM (Devin, OpenHands). В 2025-2026 они стали мейнстримом: SWE-Bench Verified превратился из академического бенчмарка в маркетинговое поле, а связка Claude Code + Cursor + Aider — стандартом ежедневного workflow многих команд.

## Q1. (!) Что такое code agent и какие категории существуют?

**Code agent** — это система на базе LLM, которая не просто отвечает текстом, а **действует** в репозитории: читает файлы, ищет по коду, редактирует, запускает тесты, делает git-коммиты.

От обычного chat-ассистента его отличают две вещи:

- **Tools** — инструменты, которыми модель меняет состояние мира (файлы, шелл, git), а не только генерирует текст.
- **Loop** — цикл обратной связи «подумал → вызвал tool → посмотрел результат → подумал ещё раз». Именно цикл превращает разовый ответ в способность доводить задачу до прохождения тестов.

Условный спектр зрелости — от пассивных подсказок к полной автономии:

- `in-editor inline` — `GitHub Copilot`, `Tabnine`, `Codeium`. Подсказки в редакторе по контексту вокруг курсора. Tools нет, агентности почти нет.
- `chat-in-editor` — `Cursor Chat`, `Continue`, `Cody`. Диалог с моделью, она знает про открытые файлы, может предложить правку, но применяет её человек.
- `agentic in-editor` — `Cursor Composer`, `Cline`, `Windsurf Cascade`. Многошаговые задачи, многофайловые правки, запуск команд с подтверждением.
- `agentic CLI` — `Aider`, `Claude Code`. Терминал, git-first, длинные автономные сессии, MCP-интеграции.
- `autonomous SWE` — `Devin`, `OpenHands`, `SWE-agent`, `Cognition`. Получают задачу типа «реши issue», работают часами в VM, выдают PR.
- `IDE-like нового поколения` — `Cursor`, `Windsurf`, `Zed AI`. Это уже не плагины, а отдельные редакторы вокруг агентов.

## Q2. (!) Чем различаются inline, chat-in-editor, agentic и autonomous SWE?

Различие — в **степени автономии** и, как следствие, в трёх связанных параметрах: сколько контроля остаётся у человека, какими tools владеет агент и как долго длится одна задача. Чем агент автономнее, тем больше прав и тем дольше он работает без вмешательства.

| Категория | Пример | Контроль человека | Tools | Длительность задачи |
|---|---|---|---|---|
| Inline | `Copilot`, `Tabnine` | каждая клавиша | нет | секунды |
| Chat-in-editor | `Cursor Chat`, `Continue` | принять каждый ответ | read-only | минуты |
| Agentic in-editor | `Cursor Composer`, `Cline` | подтверждение действий | read/write/shell | десятки минут |
| Agentic CLI | `Aider`, `Claude Code` | git-коммит как чекпоинт | read/write/shell/git/web | часы |
| Autonomous SWE | `Devin`, `OpenHands` | review финального PR | full VM | часы-дни |

Граница между категориями размыта: `Cursor` совмещает inline-Tab, чат и Composer; `Claude Code` работает и как «короткий ответ», и как многочасовой агент. Поэтому на собеседовании важнее не зазубрить таблицу, а понимать: **какой режим вы запускаете прямо сейчас**. От этого напрямую зависят стоимость, риски и то, где находится human-in-the-loop.

## Q3. Как устроена архитектура типичного code agent (LLM + tools + sandbox)?

Любой code agent сводится к трём слоям: **оркестратор** крутит цикл, **LLM** принимает решения, **sandbox** безопасно исполняет действия над файлами и шеллом. LLM сам ничего не трогает — он лишь генерирует tool-call, а реальные изменения выполняет tool-слой внутри песочницы и возвращает результат обратно в цикл.

Поток управления по шагам:

- `User prompt / issue` → **Agent loop** (оркестратор) → **LLM** (`Claude` / `GPT` / `DeepSeek`).
- LLM принимает решение «tool call?»:
  - **yes** → **Tool layer**, который раскрывается на конкретные инструменты:
    - `File system` — read / write / edit;
    - `Shell exec` — tests, build;
    - `Code search` — grep / AST / symbols;
    - `git` — diff / log / commit;
    - `Web fetch`.
  - **no** → `Final answer / PR` (выход из цикла).
- Все tool-вызовы (`File system`, `Shell exec`, `Code search`, `git`, `Web fetch`) исполняются внутри **Sandbox** (`Docker` / `VM` / local).
- Sandbox возвращает `Observation` обратно в **Agent loop** — и цикл повторяется.

Разберём три уровня подробнее:

1. **Orchestrator** — управляет циклом: считает токены, держит scratchpad с планом, ловит ошибки tool-вызовов и решает, когда остановиться. Это код, а не модель, поэтому именно здесь живут лимиты, ретраи и логика безопасности.
2. **LLM** — генератор решений: что прочитать, что изменить, какую команду запустить. Формат tool-call зависит от провайдера — Anthropic tool_use, OpenAI function calling, у некоторых агентов кастомный XML.
3. **Sandbox** — место, где физически живут файлы и шелл. Локальный FS (Aider, Claude Code), Docker-контейнер per task (OpenHands) или удалённая VM с браузером (Devin). Выбор песочницы — это компромисс между изоляцией и удобством (подробнее в Q24).

## Q4. (!) Что такое SWE-Bench и зачем он нужен?

**SWE-Bench** (Princeton, 2023) — бенчмарк, который проверяет способность модели **закрывать реальные GitHub issues** в популярных Python-репозиториях (`django`, `sympy`, `scikit-learn`, `astropy`, …). Это основной отраслевой способ сравнивать code-агентов между собой.

Как устроена одна задача. Для каждого issue заранее известно:

- описание issue и ссылка на PR-фикс;
- набор изменённых файлов;
- набор тестов, который **проваливался до фикса и проходит после**.

Агенту дают только issue + полный репозиторий — без подсказки, где именно править. Патч засчитывается, если он **проходит «fail-to-pass» тесты** (то, что чинит issue) и не ломает «pass-to-pass» (существующую функциональность).

**Почему это честная проверка.** В отличие от задачек вида «угадай функцию по docstring», SWE-Bench близок к реальной работе инженера:

- код разбросан по большой кодовой базе — агенту нужно сначала **найти место** для правки, а не только написать её;
- тесты — реальные регрессии, написанные мейнтейнерами проекта, а не синтетика;
- успех означает «такой PR прошёл бы CI», а не «код выглядит правдоподобно».

## Q5. (!) SWE-Bench Verified — чем отличается от Full?

Verified — это **очищенное подмножество** оригинального SWE-Bench. Изначальный набор (~2294 задачи) оказался шумным, и шум искажал цифры в обе стороны: часть проблем нерешаема без приватных данных (агент не виноват, что провалился), часть тестов flaky, часть issue двусмысленны. OpenAI вместе с авторами провели human-валидацию и опубликовали **SWE-Bench Verified — 500 задач**, где каждая:

- однозначно сформулирована;
- решаема в пределах данного контекста;
- покрыта стабильными тестами, проверяющими именно описанную проблему.

Поэтому к 2025-2026 индустрия меряется почти всегда **на Verified** — на нём цифры отражают реальную способность агента, а не дефекты датасета. Грубая шкала (показатели плавают и стареют, не доверяйте маркетингу буквально):

- 2023, base GPT-4 + RAG: единицы процентов.
- 2024, SWE-agent, Devin (демо): 10-15%.
- 2025, Claude 3.5 Sonnet + Claude Code: ~50%.
- начало 2026, Claude 3.7 Sonnet + Claude Code, агенты следующего поколения: ~65-70%.

Тренд важнее точной цифры: за два года прирост в разы — но потолок «100% без помощи человека» вряд ли реально достижим, потому что часть PR требует контекста, которого нет в репо.

## Q6. Как читать лидерборд SWE-Bench и где подвохи?

Главная мысль: **одна цифра процента почти ничего не значит без контекста**, в котором её получили. Пять вещей, которые надо проверить, прежде чем сравнивать результаты:

- **Verified vs Full vs Lite** — всегда смотрите, какая редакция. На Lite (300 задач) числа выше, и сравнивать «Lite одного агента» с «Verified другого» нельзя.
- **Agent vs model** — лидерборд оценивает не модель, а **связку «модель + agent harness»**. Один и тот же Claude в `SWE-agent` и в `Claude Code` даст разные цифры.
- **Pass@k vs Pass@1** — иногда заявляют «лучший из N запусков» (Pass@k). Это завышает реальную полезность: в проде вы получаете один прогон, а не право выбрать удачный.
- **Внутренний vs воспроизводимый запуск** — у Cognition (Devin) долго не было воспроизводимого harness, и маркетинговые цифры расходились с независимыми проверками.
- **Утечка в обучении** — задачи публичны, и часть фиксов могла попасть в pretraining модели. Это объясняет долю «магии», которая не воспроизводится на свежем коде.

**Эмпирическое правило.** SWE-Bench — **не предсказатель** того, как агент справится с вашим легаси. Это нижняя оценка узкой способности: «закрывать описанные issue в Python OSS». Высокий балл не гарантирует, что агент разберётся в вашем недокументированном монолите.

## Q7. (!) Какие tools обычно есть у code agent?

К 2025 сложился минимальный «джентльменский набор» — он повторяет то, что инженер делает в терминале и IDE руками:

- **File ops**: `read_file`, `write_file`, `edit_file` (search/replace или diff), `list_dir`, `glob`.
- **Code search**: `grep`, `ripgrep`-based, иногда AST/symbol-search через tree-sitter или LSP.
- **Shell exec**: запуск произвольных команд (`pytest`, `npm test`, `gradle build`, `psql`, …), обычно с таймаутом.
- **VCS**: `git status/diff/log`, авто-commit, иногда `git blame`.
- **Navigation**: «go to definition», «find references» — через LSP или tree-sitter.
- **Web fetch / search**: подтянуть документацию, прочитать issue, посмотреть Stack Overflow.
- **Task management**: TODO-лист, чекпоинты (в Claude Code/Cursor Composer есть встроенный «план»).
- **MCP-серверы**: универсальный мост к внешним системам (Postgres, Slack, GitHub API).

**Принцип хорошего дизайна tools** — узкие и явные, по-юниксовому: каждый инструмент делает одно (`read_file` только читает). Это важно, потому что модель выбирает tool по его описанию; чем уже и понятнее инструмент, тем реже модель ошибается. **Антипаттерн** — один универсальный `execute_action` с гигантской схемой, в которой LLM путается и подбирает не те параметры.

## Q8. (!) Стратегии редактирования файла: full replace, unified diff, search/replace, AST, apply-model?

Главная боль агента — **как технически выразить «измени файл»**. Это нетривиально: полная замена файла дорога по токенам, а генерация diff хрупка (модель путается в номерах строк). Поэтому сложился целый спектр стратегий, у каждой свой компромисс между ценой и надёжностью:

| Стратегия | Кто использует | Плюсы | Минусы |
|---|---|---|---|
| **Full replace** (выдать весь файл заново) | базовые ассистенты | просто, ноль парсинга | дорого по токенам, рискует переписать чужие правки |
| **Unified diff** (`---/+++`, `@@`-hunks) | ранний Aider | компактно, привычно | LLM путается в номерах строк и whitespace |
| **Search/Replace blocks** (`<<<<<<< SEARCH ... ======= ... >>>>>>> REPLACE`) | Aider, Claude Code, Cline | дёшево, легко проверить, легко применить | требует уникального SEARCH-блока |
| **AST-aware edits** (через tree-sitter) | продвинутые refactor-tools | понимает структуру, не ломает синтаксис | сложно реализовать на каждый язык |
| **Apply-model** (отдельная маленькая модель превращает «intent» в diff) | Cursor | большая модель не тратит токены на точное форматирование | вторая модель = ещё одна точка отказа |

**Что победило на практике.** В современных агентах доминирует **search/replace**, и причина в том, как устроена LLM: модель надёжно воспроизводит локальный фрагмент кода целиком, но плохо считает позиции и метаданные. Стратегия проста: модель пишет «найди вот этот блок, замени на вот этот», система ищет точное совпадение и применяет. Если SEARCH-блок не уникален или не найден — агент получает понятную ошибку и пробует снова, вместо того чтобы молча испортить файл.

По шагам это выглядит так:

- `Намерение модели` → выбор **edit strategy**, одна из пяти веток:
  - **Full** → `Полный файл`;
  - **Diff** → `Unified diff`;
  - **S/R** → `Search/Replace block`;
  - **AST** → `Структурный патч`;
  - **Apply** → `Intent → small model → diff`.
- Результат любой ветки → `Применить к файлу`.
- Дальше проверка «успех?»:
  - **да** → `Файл обновлён`;
  - **нет** → `Tool error` → возврат к `Намерению модели` (новая попытка).

## Q9. (!) Почему unified diff часто ломается у LLM?

Коротко: unified diff придуман для **людей и утилиты `patch`**, а не для генерации языковой моделью. Он требует точной позиционной мета-информации, а это ровно то, что LLM делает хуже всего. Конкретные точки отказа:

- **Номера строк.** Модель плохо считает `@@ -120,7 +120,9 @@`, особенно после нескольких прошлых правок, когда строки уже сместились.
- **Чувствительность к whitespace.** Один лишний или недостающий пробел в context-строке — и `patch` отказывается применять hunk целиком.
- **Большие файлы.** Модель «забывает», что было выше, и придумывает hunk, не подходящий ни к одному месту файла.
- **Несколько hunks подряд.** Ошибки коррелируют: один сломанный hunk заваливает применение всего патча.

Aider специально перешёл на **search/replace blocks**, потому что LLM гораздо точнее воспроизводит **локальный фрагмент** (несколько строк целиком), чем правильную позицию. Эту проблему подробно описал Paul Gauthier в постах про Aider — после смены формата процент успешно применённых правок вырос значительно.

## Q10. Apply-model в Cursor — что это и зачем?

Apply-model — это **разделение труда между двумя моделями**. В Cursor большая модель (Claude / GPT) **не пишет точный патч**: она набрасывает фрагмент «как должно стать», иногда с маркерами `// …existing code…`. Затем отдельная **специализированная маленькая модель** (apply model, дообученная именно на edit-задачах) аккуратно вклеивает этот фрагмент в реальный файл и выдаёт точный diff.

Зачем так делать:

- Большая модель **не тратит токены и внимание** на дотошное копирование неизменного контекста — она думает над логикой правки.
- Маленькая модель **дешёвая и быстрая**, её можно гонять часто без заметных затрат.
- **Качество применения растёт**: склейку фрагмента с файлом можно прицельно обучить, и она почти не ошибается.

Аналогично работает кнопка «apply» в Continue и в части open-source-форков. **Минус** — apply-model в Cursor проприетарна и серверная; локально её не воспроизвести.

## Q11. (!) Cursor: устройство и killer-фичи?

`Cursor` — это **форк VS Code, целиком выстроенный вокруг агентов**: не плагин поверх редактора, а редактор, где AI встроен в каждое действие. Ключевые компоненты:

- **Cursor Tab** — собственная маленькая модель для inline-предсказаний; умнее Copilot, особенно на крупных правках и перемещениях кода (предсказывает не следующее слово, а следующую правку).
- **Cursor Chat** — chat-in-editor с контекстом из открытых файлов и `@`-меншенов файлов, папок и документов.
- **Composer** — многофайловый агент: даёшь задачу, он показывает план, правит сразу несколько файлов и прогоняет тесты.
- **Bug Finder / PR review** — отдельные режимы для поиска багов и автокомментирования PR.
- **Embeddings index** репозитория — для быстрого retrieval по большим кодовым базам (см. Q22).

```bash
# Типичный layout проекта с Cursor
project/
  .cursor/
    rules/
      backend.mdc      # правила для backend-файлов (glob: src/backend/**)
      frontend.mdc     # правила для frontend-файлов (glob: src/frontend/**)
  .cursorrules         # legacy single-file правила
  src/
    ...
```

**Модель оплаты** — bundled tokens: фиксированная подписка, а под капотом крутятся разные модели. Удобно как «один кошелёк», но на больших агентских сессиях упираешься в потолки тарифа.

## Q12. `.cursorrules` и project-level контекст?

`.cursorrules` (и новые `.cursor/rules/*.mdc`) — это **системный промпт уровня проекта**: инструкции, которые автоматически подмешиваются в контекст при каждом запросе. Туда кладут то, что модель должна знать всегда, чтобы не выдавать generic-код:

- стек (Kotlin + Spring Boot 3, React + TypeScript, …);
- стилевые правила (no `var` в Java, prefer `record` в DTO);
- запреты (никогда не править файлы в `generated/`, не трогать миграции старше N);
- workflow (всегда запускать `./gradlew test` перед коммитом).

```text
# .cursorrules (пример)

Ты пишешь код для Kotlin/Spring Boot 3 backend и React/TS frontend.

Правила:
- Не используй мокa Mockito в новых тестах; используй Mockk + JUnit 5.
- Контроллеры — только тонкие, бизнес-логика в сервисах.
- Миграции в `src/main/resources/db/migration/` нумеруются V{дата}__описание.sql.
- Не редактируй файлы в `generated/`, `build/`, `node_modules/`.
- После любой правки кода предлагай команду для запуска тестов.
```

Аналогичные механизмы:

- `Aider` — `CONVENTIONS.md` и `--read` файлы.
- `Claude Code` — `CLAUDE.md` (project + user), скиллы, hooks.
- `Cline` — `.clinerules`.

Это критично: **без проектного контекста** агент выдаёт generic-код, который не вписывается в кодовую базу.

## Q13. (!) Aider: git-first CLI и repo map?

`Aider` — CLI-агент на Python, главная идея которого — **git как ядро рабочего процесса**. Особенности:

- **Auto-commit.** Каждое успешное изменение становится git-коммитом с осмысленным сообщением. Откат — обычный `git reset`, без отдельной «истории агента».
- **Repo map.** При старте Aider сканирует репозиторий через tree-sitter и строит **сжатую карту** структуры: какие символы где определены и кто их вызывает — имена классов/функций/публичного API без тел. LLM сразу видит скелет проекта, не тратя контекст на полный код.
- **`/add file.py`** — явно добавить файл в режим read/write. Без этого Aider файл читает, но не редактирует (защита от случайных правок).
- **`--read file.md`** — read-only-контекст (например, спецификация или CONVENTIONS).
- Поддерживает любые модели через LiteLLM, включая локальные.

```yaml
# .aider.conf.yml
model: anthropic/claude-3-7-sonnet-latest
auto-commits: true
dirty-commits: true
gitignore: true
test-cmd: "./gradlew test"
auto-test: true
read:
  - CONVENTIONS.md
  - docs/architecture.md
```

**Почему git-first — это сильно.** Вся работа агента превращается в обычную историю коммитов: её видно в `git log`, ревьюят привычными инструментами, откатывают штатным `git reset`. Не нужно учить отдельный механизм истории — она и есть git.

## Q14. Architect + Editor mode в Aider?

Architect+Editor — это **разделение «думать» и «оформлять» между двумя моделями**. В режиме Architect умная, но дорогая модель играет архитектора: пишет **план и указания** на естественном языке, не заботясь о точном формате. Вторая, быстрая и дешёвая модель в роли Editor превращает эти указания в конкретные search/replace-блоки.

Зачем разделять:

- **Архитектором** ставят `o1` / `Claude Opus` — дорогих, но сильных в reasoning.
- **Editor** — `Sonnet` / `Haiku` / `DeepSeek`: дёшевый и аккуратный в форматировании правок.
- В сумме выходит **дешевле и часто качественнее**, чем гонять одну большую модель и на reasoning, и на дотошное форматирование.

Это частный случай общего паттерна **разделения ответственности** (separation of concerns): одна модель думает, другая исполняет. Та же идея лежит в apply-model у Cursor (Q10) и в reasoning-agent-фреймворках.

## Q15. (!) Claude Code: terminal-first agent и набор tools?

`Claude Code` — официальный CLI от Anthropic, ориентированный на терминал, а не на IDE. Из чего он состоит:

- **Tools** на базе Anthropic tool_use: `Bash`, `Read`, `Edit`, `Write`, `Glob`, `Grep`, `WebFetch`, `WebSearch`.
- **Длительные agentic-сессии** с планом и scratchpad. Чтобы не упереться в окно контекста, история периодически «компактится» (сжимается).
- **MCP-интеграция «из коробки»** — подключение к Postgres, GitHub, кастомным серверам через `~/.claude.json` и `.mcp.json` (см. Q29).
- **`CLAUDE.md`** — иерархия системных инструкций: global (`~/.claude/CLAUDE.md`) + project (`./CLAUDE.md`) + локальная папка; ближний уровень уточняет дальний.
- **Skills** — пакеты инструкций, которые подключаются по триггеру (например, «пишу тесты в kratos — следую conventions»).
- **Hooks** (PreToolUse / PostToolUse / Stop) — программные перехваты вокруг tool-вызовов: ими делают, например, автообновление графа знаний или линтинг после каждого edit.

```bash
# Регистрация MCP-сервера локально
claude mcp add postgres -- npx -y @modelcontextprotocol/server-postgres \
  "postgresql://localhost/mydb"

# Запуск задачи (агентская сессия)
claude "Реши issue #1234: добавь поле lastLoginAt в Customer и миграцию"
```

**Модель оплаты** — pay-per-token через Anthropic API, без bundled-подписки. Плюс — видна честная картина расхода; минус (и одновременно дисциплина) — длинные сессии стоят дорого, и это сразу чувствуешь.

## Q16. Чем Claude Code отличается от Cursor/Aider?

Если в одной фразе: **Cursor — это IDE вокруг агента, Aider — git-дисциплина в CLI, Claude Code — терминальный агент для длинных автономных задач**. Подробное сравнение по осям:

| Свойство | Cursor | Aider | Claude Code |
|---|---|---|---|
| UI | свой IDE (форк VS Code) | CLI | CLI/terminal |
| Платформа | macOS/Win/Linux GUI | где есть Python | где есть Node |
| Модель | bundled (multiple) | любая через LiteLLM | Anthropic only |
| Git | optional | **встроен**, авто-commit | optional, обычно через bash-tool |
| Контекст | embeddings index | tree-sitter repo map | on-demand read + CLAUDE.md |
| Edit-стратегия | apply-model | search/replace | search/replace + Edit tool |
| MCP | да | через расширения | первоклассный |
| Скиллы/hooks | rules + правила | conventions | CLAUDE.md + skills + hooks |
| Лучшее применение | живая разработка в IDE | git-чёткие пошаговые правки | длинные автономные задачи, ops |

Эти инструменты не конкурируют 1:1 — многие команды используют **связку**: Cursor для интерактивной работы в IDE, Aider/Claude Code для агентских сессий «закрой задачу целиком».

## Q17. Cline (Claude Dev): Plan/Act и auto-approve?

`Cline` (раньше Claude Dev) — open-source VS Code-расширение. Его фишка — **явный тоггл Plan/Act**, который разделяет «обдумывание» и «исполнение»:

- **Plan mode** — модель только обсуждает план и ничего не трогает. Здесь безопасно согласовать подход, пока не поздно.
- **Act mode** — выполняет tools: пишет файлы, гоняет команды.

Ключ к балансу — **auto-approve**: каждое действие требует подтверждения, кроме того, что вы заранее разрешили автоматически (read-only команды, edit без удаления и т.п.). Получается удобный middle-ground — рутина идёт сама, а опасные шаги остаются под контролем человека.

Из той же ниши — `Roo Code`, `Continue Agent`, `Cody Agentic Chat`. Все они дают похожий цикл «план → подтверждение → действие → следующий шаг».

## Q18. (!) Devin: устройство, демо и реальные результаты?

`Devin` от **Cognition Labs** (март 2024) — первый громкий «autonomous SWE», который и задал этот жанр. Дизайн:

- Живёт **полностью в браузерной VM**: у Devin своя план-панель, редактор кода, шелл и браузер — фактически рабочее место разработчика в облаке.
- Получает задачу формата «возьми bug из issue tracker и почини» и работает часами автономно.
- Умеет **искать в интернете**, ставить зависимости, запускать сервисы и дебажить.

**Демо vs реальность.** Маркетинг заявлял «решает SWE-Bench Verified лучше всех», но независимые проверки (включая reproduction от Princeton/Stanford) дали куда скромнее — около 14% на SWE-Bench в первой публичной оценке. Это классический пример расхождения внутренних и воспроизводимых цифр (см. Q6). К 2026 показатели подросли, но Devin остаётся **закрытым SaaS** и стоит дорого.

**Главный вклад Devin** — не процент, а **формат**: «full-VM autonomous SWE» стал отдельным жанром, который затем подхватили open-source-решения (OpenHands и др.).

## Q19. OpenHands — open-source альтернатива Devin?

`OpenHands` (изначально `OpenDevin`) — **open-source-ответ на Devin**: тот же жанр autonomous SWE, но открытый и self-hostable. Особенности:

- Каждая задача исполняется в собственном **Docker-контейнере** — изоляция от хоста (легче и быстрее полной VM).
- **Multi-agent**: можно собрать конвейер «coder + reviewer + tester» из разных ролей.
- Backend-LLM любой: Claude, GPT, Gemini, DeepSeek, локальные через Ollama — вы не привязаны к одному провайдеру.
- Web UI в духе Devin: чат + редактор + терминал + браузер.
- Активно публикует **воспроизводимые** SWE-Bench-результаты и benchmark suite.

Похожие проекты:

- **SWE-agent** (Princeton) — ACI (Agent-Computer Interface), оптимизированный под SWE-Bench.
- **AutoCodeRover** — упор на структурированный поиск по AST.
- **Magenta**, **Aider в roo-mode**, **Plandex** — каждый со своими акцентами.

**Главный плюс open-source-подхода** — контроль: можно запускать локально, подключать свои tools и аудитить все логи. Для enterprise это часто решающий аргумент против закрытого SaaS.

## Q20. GitHub Copilot Workspace и Continue?

Это два разных по духу инструмента: Copilot Workspace встраивает agentic-flow прямо в GitHub, а Continue — это открытый и настраиваемый аналог Cursor/Cline.

**GitHub Copilot Workspace** (анонс 2024) — попытка GitHub сделать end-to-end-флоу на базе issue, не выходя из платформы:

- Цепочка: issue → план → спецификация → правки → PR.
- Всё интегрировано в GitHub UI; модель — GPT-семейство.
- **Human-in-the-loop на каждом шаге**: «вот план — поправь его — теперь поехали править файлы». Контроль не финальный, а пошаговый.

**Continue** (`continue.dev`) — open-source-аналог Cursor/Cline, расширение для VS Code и JetBrains:

- Подключаешь любую модель: Claude, GPT, локальную через Ollama, кастомные провайдеры.
- Поддерживает edit-actions, чат и agent-mode.
- По сути бесплатная и гибко настраиваемая альтернатива Copilot.

`Cody` (Sourcegraph) — давний игрок с фокусом на поиск по **очень большим** кодовым базам; тоже движется в сторону agentic.

Пять инструментов закрывают разные точки спектра: от интерактивной работы в IDE до «реши задачу, пока я сплю». Главные различающие оси — открытость кода, длительность задачи, тип песочницы и модель оплаты.

|---|---|---|---|---|---|

| Длительность задачи | минуты-часы | минуты-часы | часы | минуты-часы | часы-дни |
| Sandbox | локальный FS | локальный FS | локальный FS + bash | локальный FS | full VM |

## Q22. (!) Как code agent выбирает релевантный контекст (repo map / embeddings / LSP)?

Корень проблемы: большой репозиторий не влезает в контекст ни одной модели, поэтому агент должен выбрать **минимально нужный** срез кода. Сложилось пять подходов, и у каждого свой профиль «точность vs стоимость»:

- **Embeddings index** (Cursor, Cody, Continue) — каждый файл/чанк превращают в vector, ищут по cosine similarity. Хорошо ловит семантику («где у нас про X»), но слабо — точные имена API.
- **AST/tree-sitter repo map** (Aider) — структурное «оглавление» репо: символы и их связи без тел функций. Быстро, не нужен embedding-API; отлично отвечает на «к какому файлу относится этот класс».
- **LSP symbol index** — `go to definition`, `find references`. Самый точный способ, но дорого поднимать для всех языков сразу.
- **On-demand read** (Claude Code) — модель сама вызывает `Glob`, `Grep`, `Read`, опираясь на CLAUDE.md и предыдущие шаги. Никакого пре-индекса — навигация «по ходу».
- **Граф знаний** (например, `graphify` в этом проекте) — заранее построенный структурный + semantic-граф, по которому агент навигирует прежде, чем читать сырые файлы.

**На практике стратегии сочетают**, потому что ни одна не покрывает всё: грубый поиск через embeddings/repo map → точное чтение найденных файлов → повторный поиск по тому, что выяснилось. Этот трёхшаговый цикл и есть рабочий retrieval в code-агенте.

## Q23. Почему long context (200K+) не отменяет indexing?

Короткий ответ: большое окно убирает *жёсткий лимит*, но не убирает причин делать retrieval — цену, скорость и качество. С появлением Claude 200K / Gemini 1M возникла иллюзия «засунем весь проект и забудем про поиск», но на практике это **не работает** по четырём причинам:

- **Стоимость.** Цена растёт линейно (или хуже) от длины контекста. 1M токенов на каждый запрос — это разорение.
- **Latency.** «Время до первого токена» при больших контекстах ощутимо растёт.
- **«Lost in the middle».** Модели хуже находят факт, который лежит в середине длинного контекста, — качество ответа падает.
- **Шум.** Много нерелевантного кода рядом с нужным сбивает модель и провоцирует ошибки.

Поэтому даже на моделях с гигантским окном агенты всё равно делают retrieval: грузят **минимально необходимый** контекст и подтягивают новый только когда он реально понадобился. Большое окно — это страховка на крайний случай, а не замена поиску.

## Q24. (!) Sandboxing: Docker / VM / local shell с confirmation?

Раз агент умеет запускать произвольные команды, он способен и навредить — стереть файлы, утащить секрет, сходить наружу. Поэтому **sandbox обязателен**, а его выбор — это всегда **компромисс «изоляция vs удобство»**: чем сильнее изоляция, тем дороже и медленнее запуск.

| Подход | Кто использует | Изоляция | Удобство |
|---|---|---|---|
| Локальный shell без ограничений | базовые ассистенты | **никакой** | максимум |
| Локальный shell с confirmation | `Claude Code`, `Cline`, `Cursor Composer` | человек как гард | средний |
| Read-only по умолчанию + allowlist команд | продвинутые setup | средняя | средний |
| Docker-контейнер per task | `OpenHands`, серверные сценарии | хорошая | средний |
| Полная VM (microVM/Firecracker/QEMU) | `Devin`, enterprise | максимальная | сложно |

**Разумный минимум** независимо от выбранного уровня:

- Не давать агенту `rm -rf` (и подобное деструктивное) без подтверждения.
- Запретить чтение секретов (`.env`, `~/.ssh`, `~/.aws`) — через ignore-листы инструмента или прокси.
- Логировать все shell-команды (audit log).
- Использовать git как **дешёвый revert**: даже плохая правка отменяется одним коммитом назад.

Развязка решений по порядку:

- `Code agent` → **Confirmation policy**, которая разводит действие по трём веткам:
  - **safe allowlist** → `Exec` (выполнить);
  - **ask user** → `Human-in-the-loop` (спросить человека);
  - **deny** → `Block + log` (заблокировать и записать).
- Если дошло до `Exec`, команда исполняется внутри **Sandbox layer**, и это один из уровней:
  - `Local FS`;
  - `Docker container`;
  - `Full VM / microVM`.
- Любой из уровней песочницы пишет всё в `Audit log`.

## Q25. (!) Как работает цикл на тестах: правка → запуск → исправление → повтор?

Ключевая идея: тесты — это **внешний источник истины**, по которому агент сам понимает, верна правка или нет, и итерирует без человека. Хороший code agent прогоняет тесты сам и крутит цикл «правка → запуск → исправление», пока не станет зелено. Базовый порядок шагов:

- `План правки` → `Edit файлов` → `Запуск тестов` → `Парсинг вывода`.
- Проверка «все зелёные?»:
  - **да** → `Commit + следующая задача`;
  - **нет** → `Диагностика по stack trace` → возврат к `Плану правки` (новая итерация).

Ключевые практики:

- **Test gating** — нельзя коммитить, пока тесты красные.
- **Tight tests first** — агент пишет/обновляет тест, потом меняет код (TDD-lite), чтобы по выводу было понятно, что ломается.
- **Reflexion / самокоррекция** — после неудачи модель явно записывает «что я думал → что произошло → что попробую дальше».
- **Bounded retries** — например, 3-5 итераций; иначе агент уходит в петлю, тратит токены, и качество падает.

Reflexion и подобные паттерны — отдельная исследовательская тема (`Reflexion: Language Agents with Verbal Reinforcement Learning`, NeurIPS 2023), но в реальных code-agent они реализованы простыми эвристиками: «если тест упал — добавь в сообщение модели его вывод и попроси предложить другую правку».

## Q26. (!) Стоимость code agent: за задачу, за сессию, за месяц?

Главное правило стоимости: **платишь за токены, а в агентском цикле токены растут с каждым шагом** — поэтому цена задачи нелинейна по её сложности. Грубые порядки (Claude 3.7 Sonnet, начало 2026, цены меняются):

- **Inline-автокомплит** (Copilot, Cursor Tab) — фиксированная подписка $10-20/мес.
- **Chat-in-editor** — единицы центов за вопрос.
- **Agentic короткая задача** ($0.05-$1) — почистить функцию, написать тест, поправить bug в одном файле.
- **Agentic длинная задача** ($1-5) — многофайловая фича с прогоном тестов.
- **Autonomous SWE** (Devin/OpenHands на сложной задаче) — $5-30+ за задачу.
- **Активный месяц heavy user** — $200-1000+ при интенсивном использовании Claude Code / Cursor Pro+.

**Что разоряет** (понимание этого = понимание, как устроен счёт):

- Длинные сессии **без компакции истории** — контекст растёт, и за каждый следующий шаг платишь за весь накопленный контекст.
- Циклы **без bounded retries** — агент бесконечно «поправляет тесты», сжигая токены.
- Сложные tools, **возвращающие много данных** (полные логи, большие файлы), — весь вывод попадает в контекст и оплачивается.

Что экономит:

- Prompt caching (Anthropic, OpenAI) — повторяющиеся system prompt / CLAUDE.md / repo map.
- Подбор модели под задачу: апликатор/линтер — на маленькой модели.
- Чёткие задачи и хорошие тесты (меньше итераций).

## Q27. Production-практики: ограниченный бюджет, checkpoints, diff review?

Когда code agent встроен в реальный workflow, его нельзя пускать «как есть» — нужны страховочные слои. Их объединяет общий принцип: **агент не доверенный участник, а ускоритель, чьи результаты обязательно проверяются машиной и человеком.**

- **Ограниченный бюджет на задачу.** Лимит токенов/$ и hard stop, иначе одна зацикленная сессия выжжет бюджет.
- **Checkpoints.** Git-коммит после каждого осмысленного шага — чтобы откатить частично, а не всё сразу.
- **Diff review перед merge.** Даже если агент уверен, финальный PR смотрит человек.
- **Test gating в CI.** Никакого «агент сказал зелёное» без подтверждения от CI — CI остаётся единственным источником истины.
- **Static analysis + linters.** Стандартные gates никуда не деваются, агент для них не исключение.
- **Audit log.** Что агент читал, какие команды запускал, какие edit делал.
- **Роль с минимальными правами.** Отдельный API-ключ с урезанным доступом (например, без production-БД).
- **Поэтапный rollout.** Сначала пилотная команда, потом масштабирование на всех.

## Q28. (!) Anti-patterns: vibe coding, auto-merge, утечка ключей?

Большинство грабель первой волны массового использования агентов сводятся к одному: **человек снимает с себя контроль там, где снимать его нельзя**. Конкретные антипаттерны:

- **«Vibe coding»** — accept-all, не читая. На хобби-проекте сходит с рук, в командной кодовой базе ломает прод.
- **Auto-merge без CI** — фатально. CI обязан оставаться единственным источником истины.
- **Чтение `.env`, `~/.ssh`, ключей** — агент может «утащить» секрет в логи провайдера. Sandbox и ignore-листы обязательны.
- **Запуск миграций/деплоя tool'ом без подтверждения** — катастрофично; такие действия всегда через human-in-the-loop.
- **Долгие автономные сессии без бюджета** — деньги и токены сгорают, а качество к концу сессии падает.
- **Слепая вера в SWE-Bench** — реальный легаси сложнее, и цифры не переносятся 1:1 (см. Q6).
- **Отсутствие проектного контекста** (`CLAUDE.md`, `.cursorrules`, `CONVENTIONS.md`) — агент стабильно выдаёт «среднеинтернетный» код, не вписанный в проект.
- **Pin to latest для модели** — после обновления провайдера поведение резко меняется и ломает отлаженный workflow; разумнее фиксировать конкретные версии моделей.

## Q29. MCP servers как универсальный tool layer для code agents?

`MCP (Model Context Protocol)` решает **«N×M-проблему» интеграций**. Без него каждый из N агентов пришлось бы отдельно учить работе с каждым из M инструментов — это N×M реализаций. MCP вводит **один стандартный протокол** между host (агент) и server (Postgres, GitHub, Slack, Jira, файловая система, …), и тогда любой агент работает с любым сервером «из коробки» — N+M вместо N×M.

Типовые MCP-серверы, полезные code-агенту:

- `filesystem` — расширенные файловые операции.
- `github` — issues, PRs, comments, releases.
- `postgres`/`sqlite` — SQL-запросы к dev-БД.
- `playwright`/`chrome-devtools` — браузерные сценарии и e2e.
- `atlassian` — Jira/Confluence для контекста задачи.
- кастомные: внутренний поиск по коду, мониторинг, фиче-флаги.

Code agent (Claude Code, Cursor, Cline) подключает MCP-серверы декларативно, и они становятся **общим набором tools**. Это разделяет «что умеет инструмент» и «какая модель его использует».

## Q30. AI code review (CodeRabbit, Codacy AI, Cursor PR review) — отдельный класс?

Да, это **отдельный класс — узкоспециализированный code-agent под одну задачу**: получить diff/PR и выдать комментарии «потенциальный bug / стиль / производительность / безопасность». Он не пишет код, а оценивает чужой.

Игроки и подходы:

- `CodeRabbit` — глубокий PR-ревью, контекст из истории PR, авто-summary, conversation в комментариях.
- `Codacy AI`, `Sonar AI` — поверх классических линтеров, добавляют LLM-объяснения и предложения фикса.
- `Cursor BugBot / Cursor PR review` — расширение Cursor на GitHub.
- `GitHub Copilot for PR` — авто-summary, автоответы на review-комментарии.

Чем AI code review отличается от agentic-coding:

- **Короткий цикл.** Один прогон по diff, без длинной автономии и итераций.
- **Минимум tools.** Чтение файлов в окрестности правки, иногда запуск тестов — и всё.
- **Главная метрика — сигнал-шум.** Слишком много false-positives, и люди просто перестают читать комментарии бота; тогда инструмент бесполезен, даже если иногда находит реальные баги.

Важно: это **дополнение** к code-агенту, а не замена. Полная цепочка такая: агент пишет код → CI прогоняет тесты + AI-ревью → человек смотрит сводку.

## Q31. (!) Куда идут code agents: full SDLC и 24/7 коллаборация?

Общий вектор: агенты выходят за рамки «написать код» и захватывают **весь цикл разработки**, а человек смещается к постановке задач и ревью. Прогнозы на 2026-2027:

- **Full SDLC-агенты** — от issue до deploy: спецификация → план → реализация → тесты → PR → ревью → деплой. Уже частично реализовано (Devin, Copilot Workspace, Plandex).
- **24/7 коллаборация** — агент работает «ночью», на утро у команды стопка PR; задача людей сдвигается в **спецификацию и ревью**.
- **Multi-agent в команде** — coder, reviewer, tester, ops — разные специализации, общая память через MCP.
- **Глубокая интеграция с LSP/IDE-семантикой** — отказ от «текстовых» правок в пользу AST-операций и рефакторинг-engine.
- **Локальные модели для рутины** — апплай, форматирование, поиск — на маленьких локальных моделях; большие модели только для тяжёлого reasoning.
- **Регуляторика** — компании добавят политики «AI-generated code маркируется, проходит отдельный gate». Аудит-логи станут обязательными.
- **Skill-based agents** — портативные пакеты инструкций (как Claude Skills, Cursor Rules, Aider conventions) станут переносимыми между инструментами.
- **Стандартизация tool-layer через MCP** — как HTTP в своё время для веба: один протокол, много реализаций.

Главный сдвиг — **роль человека**. Меньше «писать код руками», больше «формулировать задачу + ревью + отвечать за продукт». Команды, которые научатся работать в этом режиме раньше, получат большое преимущество в скорости.
