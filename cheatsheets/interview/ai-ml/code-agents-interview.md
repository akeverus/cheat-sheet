# Вопросы на собеседовании: Кодовые агенты

**Code agent** — программа, которая по заданию читает код, вызывает разрешённые инструменты, меняет файлы и использует результат действий для следующего шага. Подсказка следующей строки и обычный чат помогают писать код, но сами по себе не образуют агентный цикл.

Продукты быстро меняют интерфейсы, модели и тарифы. Сравнение ниже фиксирует проверенные свойства на 9 ноября 2026 года; исторические анонсы и прогнозы помечены отдельно.

## Q1. (!) Что такое code agent и какие категории существуют?

Code agent выполняет действия через инструменты и оценивает их результат в цикле. Inline-подсказки и чат — соседние режимы coding assistants; агентный режим читает, меняет и проверяет код, а автономный может вести целую задачу.

**Граница агентности** — цикл наблюдения и действия. Inline-комплит предлагает текст у курсора, chat обсуждает решение, а агентный режим вызывает инструменты и видит их ответ. Автономность растёт вместе с объёмом задачи и разрешёнными действиями; она не определяется названием продукта. Cursor и Continue совмещают несколько режимов.

**Пример.** Inline-подсказка предлагает текст; агент с разрешёнными инструментами может найти файл, изменить его и запустить тест.

**Граница.** Inline-подсказки и чат сами по себе не означают агентный цикл.

## Q2. (!) Чем различаются inline, chat-in-editor, agentic и autonomous SWE?

Различаются степень самостоятельности, доступные инструменты, среда исполнения и точки контроля. Inline предлагает правку, чат обсуждает код, агент выполняет несколько шагов, а автономный режим может довести issue до PR.

Удобно сравнивать четыре оси: доступ к чтению/записи/командам, длительность работы, среду и момент подтверждения. Inline обычно требует принять конкретную подсказку. Chat может только обсуждать. Агентный режим проводит несколько шагов. Удалённый агент может подготовить PR, но правила merge и review остаются у команды. Один продукт часто поддерживает несколько режимов.

**Пример.** В Ask обсуждают изменение без записи, а в Agent разрешают поиск, правку и тесты.

**Граница.** Граница определяется включёнными инструментами и правами, а не названием продукта.

## Q3. Как устроена архитектура типичного code agent (LLM + tools + sandbox)?

Оркестратор ведёт цикл и политики доступа; модель выбирает действия; инструменты читают и меняют код, запускают команды и возвращают результат. Среда может быть локальной, контейнерной или удалённой; отдельный sandbox не универсален.

Оркестратор хранит состояние задачи, передаёт модели наблюдения и применяет политики доступа. Модель выбирает следующий вызов, а инструмент выполняет чтение, запись или команду. Результат возвращается в цикл. Песочница — возможный уровень изоляции, а не обязательный компонент каждого агента: локальный shell с подтверждением видит пользовательскую файловую систему.

**Пример.** Локальный агент вызывает файл и shell через свой host; наличие sandbox и сетевых ограничений проверяют отдельно.

**Граница.** Локальная работа с подтверждением команды не равна изоляции процесса от хоста.

## Q4. (!) Что такое SWE-Bench и зачем он нужен?

SWE-bench проверяет, может ли система подготовить патч для реального GitHub issue в Python-репозитории. Оценка запускает тесты: ранее падавшие должны пройти, ранее проходившие — сохраниться.

В задаче SWE-bench агент получает описание GitHub issue и снимок Python-репозитория. После правки harness проверяет тесты, которые должны перейти из fail в pass, и сохранение прежних pass-тестов. Это измеряет выполнение конкретных задач в заданной среде, но не доказывает качество произвольного кода или готовность патча к production.

**Пример.** Исправление issue в Django засчитывается, если нужные тесты стали зелёными и прежние проходящие не сломались.

**Граница.** Прохождение публичных тестов не доказывает отсутствие иных дефектов в патче.

## Q5. (!) SWE-Bench Verified — чем отличается от Full?

SWE-bench Verified — вручную проверенное подмножество из 500 задач исходного набора около 2294. Отбор уменьшает неоднозначность условий и ошибок тестов, но не делает результат показателем качества на любом проекте.

[SWE-bench Verified](https://www.swebench.com/verified) — 500 задач, отобранных человеком из исходного набора. По данным проекта, исходный Full содержит около 2294 задач; Lite — 300. Ручная проверка уменьшила неоднозначность описаний и проблем с тестами, но Verified остаётся публичным набором Python issues. Для сравнения нужны одинаковые split и методика.

**Пример.** На сайте SWE-bench Full содержит около 2294 задач, Verified — 500 проверенных экспертами.

**Граница.** На другом наборе и в другом harness процент resolved может отличаться.

## Q6. Как читать лидерборд SWE-Bench и где подвохи?

Сравнивают один и тот же набор задач, метод подсчёта, число попыток, модель, агентный harness, бюджет и условия проверки. Балл связки «модель + агент» не переносится напрямую на другую кодовую базу.

Процент resolved относится к связке модели, агентного harness, инструментов, бюджету и числу попыток. Pass@k с несколькими пробами нельзя выдавать за одноразовый pass@1. Смотрите, выполняла ли прогон команда бенчмарка и воспроизводимы ли конфигурация и патчи. Публичность задач создаёт риск попадания решений в обучение. Балл не даёт нижней или верхней оценки успеха на вашем монолите.

**Пример.** Сравнивают две записи Verified только после проверки harness, бюджета и числа попыток.

**Граница.** Публичные issue могут попасть в обучение, а тесты не покрывают всё поведение.

## Q7. (!) Какие tools обычно есть у code agent?

Обычно агенту доступны чтение и правка файлов, поиск по коду, запуск команд и проверка diff; VCS, браузер, MCP и планирование зависят от продукта и прав. Нужен понятный контракт каждого инструмента.

Обычный цикл требует чтения файлов, поиска, внесения правки, запуска доступных проверок и просмотра результата. Git, браузер, MCP и планировщик добавляют по задаче и правам. Контракт инструмента должен объяснять, что он меняет, какие данные читает и какой результат возвращает. Возможность выполнить shell-команду не означает разрешения на любой доступ или деплой.

**Пример.** Для задачи агент использует поиск, чтение файла, правку, запуск узкого теста и просмотр diff.

**Граница.** Не каждый агент имеет браузер, MCP или право коммитить.

## Q8. (!) Стратегии редактирования файла: full replace, unified diff, search/replace, AST, apply-model?

Full replace прост, но дорог и может затронуть лишнее; unified diff компактен, но хрупок к контексту; search/replace требует точного совпадения; AST-правки учитывают структуру. Отдельная apply-модель — ещё один возможный слой.

**Full replace** воспроизводит целый файл и рискует задеть соседние изменения. **Unified diff** компактен, но чувствителен к контексту и hunk. **Search/replace** задаёт фрагмент и замену; совпадение должно быть однозначным. **AST-правка** требует языка и парсера, зато может опираться на структуру. Историческая **apply-модель** — отдельный этап превращения намерения в точную правку. Продукты могут сочетать методы; единственного доминирующего формата нет.

**Пример.** Поиск и замена нескольких строк уменьшает объём текста, но не применяется при неоднозначном SEARCH.

**Граница.** Инструменты могут сочетать форматы; универсального победителя для всех файлов нет.

## Q9. (!) Почему unified diff часто ломается у LLM?

Для применения diff должны совпасть контекст, границы hunk и пробелы. LLM может ошибиться в метаданных или опереться на устаревшую версию файла; проверка патча и повторное чтение файла уменьшают риск.

У unified diff есть контекст, строки удаления/добавления и границы hunk. Если файл изменился, контекст больше не совпадает; модель также может ошибиться в пробелах или метаданных. Надёжный инструмент проверяет применимость патча, показывает diff и сообщает об ошибке для повторного чтения. Aider поддерживает несколько edit-форматов; утверждение, что он целиком отказался от diff, неверно.

**Пример.** После чужой правки исходный hunk может больше не совпадать с текущим файлом.

**Граница.** Ошибку может вызвать и устаревший контекст, даже когда синтаксис diff верен.

## Q10. Apply-model в Cursor — что это и зачем?

Cursor описал в 2024 году fast apply: сильная модель формулировала изменение, специализированная модель применяла его к текущему файлу. Это разделяло планирование и точное редактирование; нынешний Agent может править через tool calls.

[Cursor описал fast apply в 2024 году](https://cursor.com/blog/instant-apply): мощная модель задаёт направление правки, специализированная модель быстро накладывает её на текущий файл. Это пример разделения планирования и точного edit. Текущий Cursor Agent редактирует через вызовы инструментов и показывает diff; историческое описание apply нельзя переносить на все его нынешние режимы.

**Пример.** В статье Cursor 2024 года мощная модель задаёт edit intent, fast-apply модель накладывает изменение на файл.

**Граница.** Описание относится к опубликованной архитектуре 2024 года; нынешний Agent редактирует через tools.

## Q11. (!) Cursor: устройство и killer-фичи?

Cursor совмещает редактор кода, Tab-подсказки, Agent с поиском по репозиторию, многофайловыми правками и командами, а также режимы Ask/Plan и Bugbot для PR. Возможности и оплата зависят от плана и версии.

Cursor объединяет Tab-подсказки, Agent для поиска, многофайловых правок и команд, режимы Ask/Plan и Bugbot для PR. Редактор остаётся центральной поверхностью, но есть и cloud agents. Названия прежних режимов Composer/Chat и схема оплаты менялись. Поэтому при выборе проверяют актуальный план, доступные модели, разрешения и способ просмотра diff.

**Пример.** Cursor Agent ищет файлы, меняет несколько файлов и запускает команды; Tab предлагает локальные правки.

**Граница.** Названия режимов, модели и тарифы зависят от версии и плана.

## Q12. `.cursorrules` и project-level контекст?

`.cursorrules` — старый формат проектных инструкций Cursor; актуальные Project Rules лежат в `.cursor/rules`, также поддерживается `AGENTS.md`. Правила задают контекст и ограничения для Agent, но не заменяют проверку кода.

`.cursorrules` — старый единый файл инструкций. Текущие Project Rules лежат в `.cursor/rules`; поддерживается и `AGENTS.md`. Правило может быть постоянным или применяться к файлам по шаблону. В него кладут архитектурные договорённости, стиль и команды проверки, но не секреты. Инструкции влияют на контекст модели и не заменяют тесты или ревью.

**Пример.** Правило для backend кладут в `.cursor/rules` с областью применения по путям.

**Граница.** `.cursorrules` остаётся legacy; правило не запускает тесты само по себе.

## Q13. (!) Aider: git-first CLI и repo map?

Aider — CLI-инструмент, который использует git и по умолчанию коммитит свои правки; автокоммит отключаем. Repo map показывает отобранные файлы и ключевые символы в рамках бюджета контекста, а не весь код.

Aider работает из терминала с локальным репозиторием. По умолчанию он коммитит свои правки, но `--no-auto-commits` отключает это. Repo map через tree-sitter показывает отобранные символы, типы и сигнатуры в пределах бюджета токенов, а не полный текст всех файлов. `/add` управляет файлами в контексте правки; `/read-only` даёт справочный материал.

**Пример.** Aider добавляет нужные файлы в чат, использует краткую repo map и может зафиксировать правку коммитом.

**Граница.** Автокоммит можно выключить; карта не содержит весь репозиторий дословно.

## Q14. Architect + Editor mode в Aider?

В режиме Architect/Editor одна модель формулирует решение, другая переводит его в формат правки. Модели могут быть разными или одинаковыми; польза зависит от их качества, формата edit и цены.

Architect формулирует подход на обычном языке, Editor превращает его в конкретную правку. [Документация Aider](https://aider.chat/docs/usage/modes.html) допускает разные модели или одну и ту же модель для обеих ролей; edit-формат настраивается. Выигрыш в цене и качестве зависит от модели и задачи, поэтому его проверяют, а не предполагают автоматически.

**Пример.** Architect описывает решение, Editor вносит правки выбранным edit-форматом.

**Граница.** Одна модель может выполнять обе роли; экономия и качество не гарантированы.

## Q15. (!) Claude Code: terminal-first agent и набор tools?

Claude Code читает и меняет файлы, запускает команды, работает с правилами, MCP и разрешениями. У него есть CLI, IDE, desktop и web-поверхности; доступность инструментов и среда исполнения зависят от поверхности.

Claude Code начинался как терминальный агент, но [текущая документация](https://code.claude.com/docs/en/overview) описывает CLI, IDE, desktop и web. Он читает файлы, меняет код, запускает команды и поддерживает project instructions, skills, hooks и MCP. Место исполнения и доступ к локальным файлам различаются по поверхности; разрешения и способы оплаты зависят от конфигурации.

**Пример.** Сессию Claude Code можно запустить в CLI или IDE; доступ к локальным файлам и cloud-среде различается.

**Граница.** Разрешения, компакция и поддержка инструментов зависят от настройки и поверхности.

## Q16. Чем Claude Code отличается от Cursor/Aider?

Cursor ориентирован на собственный редактор и облачные/локальные Agent-сессии; Aider — CLI с repo map и автокоммитом по умолчанию; Claude Code доступен в CLI, IDE, desktop и web. Git, модель и права зависят от настроек.

Cursor ориентирован на редактор и связанную облачную работу; Aider — CLI с repo map и автокоммитом по умолчанию; Claude Code — агент Claude в терминале, IDE, desktop и web. Все три способны редактировать файлы. Git-операции, режимы и стоимость проверяют по конкретной настройке, а не по старой таблице «IDE против CLI».

**Пример.** Aider по умолчанию коммитит изменения, тогда как Cursor и Claude Code не следует считать системами автокоммита.

**Граница.** Текущие продукты имеют дополнительные поверхности и режимы; таблица не исчерпывает функции.

## Q17. Cline (Claude Dev): Plan/Act и auto-approve?

Cline — открытый агент для редактора и терминала. В Plan он исследует и предлагает план, в Act меняет файлы и запускает команды; разрешения можно задавать по типам действий. Нельзя считать auto-approve безусловным.

Cline — открытый агент с IDE, CLI и desktop-поверхностями. Режим Plan помогает исследовать задачу, Act получает доступ к действиям. Разрешения на действия можно настраивать; auto-approve не означает безусловного доступа ко всем файлам и командам. Разница между режимами определяется доступными инструментами и политикой.

**Пример.** В Plan агент исследует задачу, в Act получает право на правку; auto-approve настраивается отдельно.

**Граница.** Возможности Cline уже не ограничены только VS Code.

**Пример.** В исходном демо Cognition показала shell, редактор и браузер в своей среде и опубликовала собственную оценку SWE-bench.

## Q19. OpenHands — open-source альтернатива Devin?

OpenHands развивает открытые компоненты для agentic-разработки: Canvas, SDK и Agent Server. Можно выбрать собственную инфраструктуру и модель. Среда может быть локальной, self-hosted или облачной; нельзя утверждать, что каждая задача всегда исполняется в одном Docker-контейнере или аппаратной VM. Открытость облегчает аудит, но безопасность всё равно зависит от конфигурации.

**Пример.** OpenHands можно запустить с локальным backend и выбранной моделью.

**Граница.** Контейнеры, удалённая среда и серверная конфигурация различаются; не всё запускается одинаково.

## Q22. (!) Как code agent выбирает релевантный контекст (repo map / embeddings / LSP)?

Агент сочетает поиск по тексту, карту символов, LSP, семантический индекс и чтение нужных файлов. Подход зависит от вопроса: точное имя ищут иначе, чем описание поведения; полный репозиторий в контекст не копируют.

Для точного имени файла или символа подходят grep и LSP. Repo map даёт краткое структурное оглавление. Семантический индекс помогает искать по описанию поведения. После грубого поиска агент читает исходный файл и его потребителей; при новых данных повторяет поиск. Embeddings не заменяют точный поиск, а LSP не гарантирует покрытие каждого языка.

**Пример.** Точное имя функции ищут текстом или LSP, описание поведения — семантическим поиском; затем читают найденный файл.

**Граница.** Один метод retrieval может пропустить связь, найденную другим.

## Q23. Почему long context (200K+) не отменяет indexing?

Большое контекстное окно помогает разбирать найденные файлы, но не делает весь репозиторий релевантным. Retrieval снижает объём, задержку и шум; качество поиска в длинном контексте зависит от модели и задачи.

Большое окно позволяет держать больше найденных файлов одновременно, но каждый токен влияет на стоимость и может повышать задержку. Нерелевантный код мешает выделять нужную связь. Исследования long-context показывают позиционные эффекты вроде lost in the middle, но их сила зависит от модели и задачи. Retrieval подбирает нужные файлы; длинный контекст помогает затем разобрать их вместе.

**Пример.** Агент сначала находит нужные файлы и передаёт их модели вместе с зависимостями.

**Граница.** Большой контекст полезен после отбора, а не автоматически вреден.

## Q24. (!) Sandboxing: Docker / VM / local shell с confirmation?

Локальный shell работает с правами пользователя; подтверждения ограничивают действия, но не дают изоляции. Контейнер и VM изолируют среду в разной степени, если правильно настроены сеть, файловые монтирования и секреты.

**Подтверждение** ограничивает разрешённые операции, но локальный процесс всё равно видит хост в рамках прав пользователя. **Контейнер** создаёт отдельную среду, если ограничены mount и сеть. **VM** обычно даёт более сильную границу, но дороже в запуске и обслуживании. Для любого варианта проверяют доступ к секретам, сети, изменению файлов и журнал действий. Git помогает откатить код, но не возвращает удалённые данные и не отменяет отправленный секрет.

**Пример.** Локальный shell с подтверждением команды всё ещё видит хост; контейнер без ограничений сети и mount не даёт полной защиты.

**Граница.** Изоляция зависит от конфигурации, а не только от ярлыка Docker или VM.

## Q25. (!) Как работает цикл на тестах: правка → запуск → исправление → повтор?

Агент меняет код, запускает подходящие тесты, читает сбой и уточняет правку в ограниченном числе итераций. Зелёные тесты подтверждают только проверенные сценарии; перед передачей результата нужны diff и сообщение о непроверенном.

Цикл начинается с понятной цели и подходящих тестов. Агент меняет код, запускает проверку, читает конкретный сбой и делает следующую правку. Число попыток ограничивают бюджетом и причиной повторения. Зелёный тест — свидетельство проверенного сценария, а не гарантия отсутствия дефектов. Перед передачей результата нужны diff и перечень проверенных и непроверенных частей.

**Пример.** После сбоя теста агент читает его причину, меняет код и повторно запускает нужный тест в пределах бюджета.

**Граница.** Зелёные локальные тесты не заменяют остальные обязательные проверки проекта.

## Q26. (!) Стоимость code agent: за задачу, за сессию, за месяц?

Стоимость зависит от модели, объёма входа и выхода, числа шагов, инструментов, кеширования и цены среды. Подписка и API тарифицируются по-разному; цену задачи, сессии и месяца оценивают по фактическому usage.

У API важны входные и выходные токены, кеш, число вызовов и стоимость внешних инструментов или среды. У подписки важны включённый usage, ограничения и дополнительные списания. Длинная сессия может повторно подавать историю; компакция и кеш помогают по-разному. Цена задачи и месяца зависит от модели, глубины исследования и числа повторов, поэтому старые универсальные суммы быстро устаревают.

**Пример.** Длинный лог инструмента увеличивает входной контекст на следующих шагах; кеширование может снизить цену повторного префикса.

**Граница.** Подписка может ограничивать usage иначе, чем API; универсальной цены задачи нет.

## Q27. Production-практики: ограниченный бюджет, checkpoints, diff review?

Работу агента ограничивают временем, бюджетом и правами; сохраняют промежуточный diff или checkpoint; запускают подходящие проверки и проводят ревью перед merge по правилам команды. Доступ к production контролируют отдельно.

Ограничивают бюджет, время и права; передают агенту только нужные данные. Для долгой работы сохраняют промежуточный diff или другой восстанавливаемый checkpoint. Проверки выбирают по характеру изменения и правилам репозитория, а перед merge просматривают diff и обязательные CI-статусы. Отдельный коммит после каждого шага не универсальная норма.

**Пример.** Перед merge команда проверяет diff и необходимые CI-статусы; агенту дают только нужные права.

**Граница.** Не всегда нужен отдельный коммит после каждого шага; достаточно восстанавливаемого checkpoint.

## Q28. (!) Anti-patterns: vibe coding, auto-merge, утечка ключей?

Риски создают принятие правок без просмотра, merge в обход обязательных проверок, передача секретов, опасные действия без нужного контроля и бесконечные циклы. Политика подтверждений и проверки зависит от риска операции.

Принятие правок без чтения скрывает ошибки в конкретном проекте. Merge в обход обязательных checks, передача секретов в tool output и бесконечный цикл создают отдельные риски. Для миграции и деплоя политика подтверждения зависит от обратимости и полномочий; не всякая автоматизация обязана ждать человека. Ограничения доступа и версии модели выбирают по процессу команды.

**Пример.** Агент может прочитать секрет через file-tool и передать его дальше, даже без shell.

**Граница.** Не все операции требуют ручного подтверждения: правило зависит от обратимости и полномочий.

## Q29. MCP servers как универсальный tool layer для code agents?

MCP стандартизирует обмен между host и внешним server с инструментами и ресурсами. Совместимый сервер может переиспользоваться несколькими агентами, но нужны настройки, разрешения и проверка доверия; MCP не заменяет tool calling модели.

MCP задаёт протокол между host и server: сервер предоставляет инструменты или ресурсы, host решает, какие из них показать модели и какие действия разрешить. Повторное использование сервера уменьшает число отдельных интеграций, но каждый клиент требует настройки и доверия. MCP не заменяет provider-specific tool calling и сам по себе не делает внешний сервер безопасным.

**Пример.** Один MCP-сервер предоставляет инструменты нескольким совместимым клиентам при раздельной настройке доступа.

**Граница.** Совместимость протокола не гарантирует одинаковые права и поведение hosts.

## Q30. AI code review (CodeRabbit, Codacy AI, Cursor PR review) — отдельный класс?

AI code review анализирует diff и контекст, возвращает замечания и иногда предлагает правки. Агент написания кода меняет файлы и проверяет реализацию; возможности пересекаются, поэтому различают роль в процессе и качество сигнала.

Review-агент читает PR или diff, ищет возможные ошибки и объясняет замечания. Coding agent обычно вносит правки и запускает проверки. Граница не жёсткая: современные review-продукты могут предлагать и применять исправления. Важны точность замечаний, контекст и возможность проверить вывод; большой поток ложных комментариев снижает доверие.

**Пример.** Bugbot анализирует PR; coding agent меняет файлы. Современные review-продукты могут предлагать и применять исправления.

**Граница.** Количество комментариев не равно качеству; нужна проверка ложных срабатываний.

## Q31. (!) Куда идут code agents: full SDLC и 24/7 коллаборация?

Уже существуют агенты для многошаговой реализации, PR-ревью, облачной работы и MCP-интеграций. Полностью автономный SDLC, обязательная маркировка AI-кода и универсальная multi-agent-команда остаются прогнозами, а не общим правилом.

Подтверждённые возможности уже включают многошаговую реализацию, удалённые сессии, PR-ревью и MCP. Отдельные продукты соединяют часть шагов SDLC, но полный автоматический путь от issue до production не стал универсальным или обязательным. Multi-agent-команды, круглосуточная работа и маркировка AI-кода — варианты развития, которые нужно проверять по реальным требованиям и результатам, а не подавать как факт.

**Пример.** Облачный агент уже может подготовить PR; его merge и deploy зависят от прав и процесса команды.

**Граница.** Переход к полному SDLC и новые обязанности по маркировке кода — гипотезы, не текущая универсальная норма.
