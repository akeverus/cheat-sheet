# Вопросы на собеседовании: `API Versioning`

API versioning — стратегия развития API без поломки существующих клиентов. Главные подходы: **URI versioning** (`/v1/`), **header versioning**, **query parameter**, **content negotiation**. Также сюда входят: обратная совместимость, политики устаревания (deprecation), sunset, semantic versioning. Критично для публичных API и систем с несколькими командами.

## Q1. (!) Зачем нужен API versioning?

Versioning позволяет менять API, не ломая уже работающих клиентов: старые продолжают жить на старой версии контракта, новые — на новой, а миграция идёт в темпе самих клиентов.

**Корень проблемы:** потребители API (мобильные приложения, сторонние интеграции) обновляются **несинхронно**. Сервер вы релизите за минуты, а клиент над собой не властны — апдейт мобильного приложения доезжает до всех пользователей неделями, и часть никогда не обновится. Любое несовместимое изменение контракта тут же роняет тех, кто остался на старом коде.

**Без versioning:**
- Сервер меняет контракт → существующие клиенты падают прямо в проде.
- Мобильные клиенты особенно болезненны: цикл обновления долгий, а у части аудитории старая версия живёт годами.
- Каждый breaking change превращается в шквал обращений в поддержку.

**С versioning:**
- Несколько версий живут параллельно.
- Старые клиенты остаются на старой версии и продолжают работать.
- Новые клиенты сразу берут новую.
- Миграция плавная, без «дня X», когда всё ломается разом.

**Где обязательно, а где нет:** публичные API версионируют всегда — внешних клиентов нельзя заставить обновиться по команде. Внутренние API иногда обходятся без версий: если клиент и сервер катятся одним релиз-циклом, проще менять контракт и клиента вместе и не платить за поддержку нескольких версий.

## Q2. (!) Что такое breaking change?

**Breaking change** — изменение контракта, после которого существующему клиенту нужно что-то поправить у себя, иначе он сломается. Ключ — не «сервер поменялся», а «клиент без правок перестаёт работать». Поэтому критерий всегда смотрят со стороны видимого клиенту контракта (запрос/ответ), а не внутренней реализации.

**Типичные breaking changes:**
- **Удаление поля** из ответа — клиент читает то, чего больше нет.
- **Переименование поля** — старый ключ исчезает, клиент получает `null`.
- **Смена типа поля** (string → number) — ломается десериализация, особенно в строго типизированных языках.
- **Опциональное поле запроса становится обязательным** — прежде валидные запросы начинают отклоняться.
- **Добавление нового обязательного поля** в запрос — старые клиенты его не шлют и получают ошибку валидации.
- **Смена структуры ответа** (object → array) — клиент разбирает другую форму.
- **Смена семантики кодов ошибок** — клиент трактует ошибку не так, как раньше.
- **Смена схемы аутентификации** — старые ключи/токены перестают работать.
- **Смена URL** без редиректа — клиент стучится в несуществующий адрес.

Общий знаменатель: любое из этого требует от клиента ответных правок. **Поэтому breaking change нельзя катить в той же версии — он требует новой.**


## Q3. (!) Какие изменения backwards-compatible? Примеры.

Backwards-compatible — изменение, которое только **расширяет** контракт, не нарушая ожиданий существующих клиентов: они продолжают слать прежние запросы и читать прежние поля ответа. Такие правки безопасно катить в той же версии — новая не нужна.

**Безопасно в той же версии:**
- **Новое опциональное поле в запросе** — клиенты его просто не шлют.
- **Новое поле в ответе** — старые клиенты игнорируют лишнее, новые начинают использовать.
- **Новый эндпоинт** — на существующие никак не влияет.
- **Новый опциональный query-параметр** — по умолчанию ведёт себя как раньше.
- **Обязательное поле запроса становится опциональным** — прежние запросы остаются валидными (обратное — уже breaking).
- **Новые коды ошибок** — при условии, что клиенты умеют разумно реагировать на незнакомый код.

Почему это работает — **паттерн Tolerant Reader** (закон Постела):
> "Be conservative in what you send, liberal in what you accept."

Чтобы расширения контракта не ломали клиента, он должен:
- игнорировать неизвестные поля, а не падать на них;
- корректно работать, когда опционального поля нет;
- аккуратно обрабатывать незнакомые коды ошибок, а не считать их фатальными.

Именно толерантность клиента и делает добавление полей безопасным — без неё даже «безобидное» расширение ответа могло бы ронять интеграцию.


## Q4. (!) Что такое URI versioning?

URI versioning кодирует версию прямо в пути URL — номер версии становится частью адреса:

```
https://api.example.com/v1/users/123
https://api.example.com/v2/users/123
```

Раз версия в адресе, маршрутизация и отладка тривиальны: шлюз направляет `/v1/` и `/v2/` на разные деплои, а любой запрос можно открыть прямой ссылкой.

**Плюсы:**
- **Просто и видно** прямо в URL.
- Легко маршрутизировать: разные версии → разные сервисы/деплои.
- Удобно тестировать — дружелюбно к браузеру (открыл ссылку и проверил).
- Понятно пользователям с первого взгляда.

**Минусы:**
- **Идентичность ресурса формально меняется** с версией: с точки зрения REST `/v1/users/123` и `/v2/users/123` — «разные ресурсы», хотя физически это один пользователь.
- Нарушает чистоту REST: URI должен идентифицировать ресурс, а не его версию.
- Один ресурс получает несколько URL.

На практике REST-пуризм здесь обычно несущественен. **Это самый распространённый подход** — использовался в Twitter, раньше в GitHub и Stripe.


## Q5. (!) Что такое header versioning?

Header versioning передаёт версию в HTTP-заголовке, а путь URL оставляет неизменным. Один и тот же `/users/123` отдаёт разные представления в зависимости от запрошенной версии — через стандартный `Accept`:

```http
GET /users/123
Accept: application/vnd.example.v2+json
```

или через кастомный заголовок:
```http
GET /users/123
X-API-Version: 2
```

Раз версия не в адресе, концептуально это ближе к REST (URI продолжает идентифицировать ресурс), но менее наглядно.

**Плюсы:**
- **URI не меняется** — чистый REST.
- Идентичность ресурса сохраняется.
- Проще добавлять новые версии: новый адрес не плодится.

**Минусы:**
- **Версия менее заметна** — её не видно в URL, тяжело тестировать в браузере без расширений.
- Сложнее документировать.
- Усложняется кэширование: нужен заголовок `Vary` по версионному заголовку, иначе CDN отдаст ответ не той версии.

**Где применяется:** в более новом API GitHub.


## Q6. (!) Что такое query parameter versioning?

Версия передаётся как параметр строки запроса — путь к ресурсу не меняется, версия просто дописывается к query:

```
https://api.example.com/users/123?version=2
https://api.example.com/users/123?api-version=2024-01-15
```

Это компромисс между URI- и header-подходом: версию видно в URL (как у URI versioning), но структуру пути менять не нужно.

**Плюсы:**
- Видно в URL — наглядно.
- Удобно тестировать: ссылку легко скопировать и открыть.

**Минусы:**
- Засоряет query string — версия смешивается с фильтрами и пагинацией (`?page=2&version=2`) и её легко случайно потерять при формировании ссылок.
- Менее устоявшаяся практика, чем URI versioning.

**Где применяется:** часто в Azure API; Stripe передаёт date-based версию в виде параметра.


## Q7. Что такое content negotiation (версия через заголовок Accept)?

Версия зашита в кастомный MIME-тип, а нужное представление сервер выбирает штатным механизмом HTTP content negotiation — по содержимому заголовка `Accept`, при неизменном пути:

```http
GET /users/123
Accept: application/vnd.example.user.v2+json
```

По сути это частный случай header versioning: версию несёт не отдельный заголовок `X-API-Version`, а сам медиатип (`vnd.*`).

**Плюсы:**
- Это механизм из стандарта HTTP, а не самодельная схема.
- Идентичность ресурса сохраняется — URL не меняется.

**Минусы:**
- Громоздкие MIME-типы (`application/vnd.company.resource.v2+json`) трудно набирать и документировать.
- Тяжело воспринимается людьми.
- Встречается редко.

**Нишевый подход** — в основном академический; для массовых публичных API по умолчанию берут URI versioning.


## Q8. Что такое hostname-based версионирование?

Версия кодируется в имени хоста — каждая версия живёт на своём поддомене:

```
https://api-v1.example.com/users/123
https://api-v2.example.com/users/123
```

Это даёт полную физическую изоляцию деплоев: поддомены могут указывать на разные кластеры, а миграция версии = переключение клиента на другой хост.

**Плюсы:**
- Отдельные деплои под каждую версию.
- Простое инфраструктурное разделение (вплоть до разных регионов и сетей).

**Минусы:**
- Накладные расходы на DNS — каждый версионный поддомен надо завести и сопровождать.
- Сложности с CORS: разные поддомены — это разные origin для браузера, поэтому нужны CORS-заголовки и аккуратная настройка cookies (`SameSite`/`domain`).

**Применяется редко** — когда версиям действительно нужна раздельная инфраструктура, а не просто разный контракт.


## Q9. (!) Какой подход к версионированию выбрать?

Единственно правильного подхода нет — он определяется типом API и аудиторией. Публичному REST нужна простота и видимость, GraphQL версионируется иначе по своей природе, gRPC — через пакеты:

| Сценарий | Подход |
|----------|----------|
| Публичный API | **URI versioning** (`/v1/`) — просто, наглядно |
| Внутренний API | URI или header (важна консистентность) |
| Стабильность в стиле Stripe | Date-версии через заголовок |
| GraphQL | **Без версий** (только deprecation) |
| gRPC | Версионирование пакетов (`MyServiceV2`) |

**Когда решать:** стратегию выбирают рано, в начале жизни контракта — менять подход позже болезненно.

**Дефолт на 2025:** для большинства публичных REST-API — URI versioning (`/v1/`, `/v2/`) как самый прагматичный. GraphQL же не версионируют URL'ом (`/graphql/v2` противоречит модели единой эволюционирующей схемы), а gRPC версионируют через имя пакета/сервиса (`package.v2`, `MyServiceV2`), потому что привычного REST-URI у него нет.


## Q10. Что такое semantic versioning (SemVer)?

SemVer — конвенция нумерации, кодирующая характер изменений прямо в номере версии `MAJOR.MINOR.PATCH` (например, `2.5.3`):

- **MAJOR** — breaking changes (несовместимые изменения).
- **MINOR** — новые фичи, обратно совместимые.
- **PATCH** — исправления багов.

Так по номеру сразу видно, можно ли обновляться безопасно: смена MAJOR сигналит «осторожно, сломается», MINOR/PATCH — «совместимо».

**Версионирование HTTP-API обычно ≠ полный SemVer:**
- В URL выносят только MAJOR (`/v1/`): менять адрес на каждый минорный апдейт непрактично, а `/v2.5.3/` не нужен — минорные и патч-изменения по определению совместимы.
- MINOR/PATCH отслеживают в документации и changelog.

**А вот к SDK и клиентским библиотекам** полный SemVer применяют целиком — там номер `2.5.3` несёт реальный смысл (например, в пакетах npm/Maven).


## Q11. (!) Что такое date-based versioning (подход Stripe)?

Вместо мажорных номеров версии именуются датами — каждая дата фиксирует точное поведение API на момент выпуска:

```
2024-04-19, 2024-06-30, ...
```

Версию клиент передаёт заголовком (путь к ресурсу при этом не версионируется):
```http
Stripe-Version: 2024-04-19
```

Каждая дата — снимок поведения API; breaking change рождает новую дату, а клиент остаётся на своей, пока сам не обновится.

**Плюсы:**
- Гранулярность: любая несовместимая мелочь = новая дата, без выкатки целого «v3».
- Нет споров про номер мажорной версии — просто даты.

**Минусы:**
- Накапливается много версий, которые приходится поддерживать.
- Клиентам путано, какая дата самая свежая.

**Ключевая гарантия:** Stripe хранит **все когда-либо опубликованные версии**. Клиент пинится (pin) к конкретной дате и не ломается принудительно — старые даты живут вечно, до явного апгрейда самим клиентом.


## Q12. (!) Что такое per-account version pinning (модель Stripe)?

В модели Stripe версия — это **атрибут аккаунта, а не отдельного запроса**: каждый клиент закреплён (pinned) за конкретной версией API, и после фиксации поведение API для него застывает.

```
Account X: pinned к 2024-04-19
Account Y: pinned к 2024-06-30
Account Z: latest (auto-upgrade)
```

**Как это работает:**
- Версия фиксируется при первом вызове API (или выставляется вручную).
- Аккаунт остаётся на ней навсегда — до явного апгрейда.
- Новые клиенты по умолчанию стартуют на последней версии.

**Webhooks тоже пинятся к версии аккаунта:** сервер пушит payload в формате версии конкретного аккаунта. Это важно именно потому, что в push-модели клиент не может «запросить» версию — закрепление за аккаунтом обеспечивает стабильный формат событий там, где content negotiation невозможен.

**Итог:** благодаря pinning Stripe может постоянно вносить breaking changes, **никого при этом не ломая** — новые несовместимые изменения просто не касаются уже закреплённых аккаунтов, и миграционные кампании не нужны.


## Q13. Как версионировать webhooks?

Webhooks сложнее версионировать, чем обычное API. **Причина:** в обычном запросе версию выбирает клиент (через путь или заголовок), а вебхуки инициирует сервер — он сам пушит событие, и согласовать версию в ответ на запрос клиента нельзя. Значит, версию приходится закреплять заранее или держать формат строго совместимым.

**Подходы:**
1. **Версия, закреплённая за клиентом** (per-account pinning, как в Stripe) — сервер шлёт payload в версии аккаунта.
2. **Несколько вебхук-эндпоинтов** под разные версии (например, отдельный `/webhooks/v2`).
3. **Заголовок в payload вебхука**, указывающий версию.
4. **Только обратно совместимые изменения** — всегда добавлять поля, никогда не удалять.

**Частый паттерн** (самый дешёвый): payload вебхуков заморожен навсегда, со временем только добавляются новые поля и новые типы событий. Так существующие обработчики не ломаются — что критично для платёжных и интеграционных событий, которые клиент не может «перезапросить» в другой версии.


## Q14. (!) Почему GraphQL обходится без версий?

Философия GraphQL — **эволюция единой схемы без версионирования**. Это возможно из-за самой модели запросов: клиент сам перечисляет нужные поля, поэтому добавление новых полей в схему его не затрагивает — он их просто не запрашивает.

**Вместо версий:**
- **Добавлять поля** — клиент запрашивает только то, что ему нужно, так что добавления ничего не ломают.
- **Помечать поля устаревшими** через `@deprecated`.
- **Никогда не удалять** сразу — только очень нескоро после депрекейта.

```graphql
type User {
  id: ID!
  name: String!
  email: String!
  username: String @deprecated(reason: "Use 'handle' instead")
  handle: String!  # new field
}
```

Здесь старое поле `username` остаётся рабочим, рядом добавлено новое `handle`, а директива `@deprecated` подталкивает клиентов мигрировать. Клиенты продолжают использовать `username`, пока не перейдут.

**Со временем** (через годы) `username` удаляют — но потрясений минимум: большинство клиентов уже переехало на `handle`.


## Q15. Как работает field deprecation в GraphQL?

Поле помечают директивой `@deprecated` с причиной — оно остаётся рабочим, но схема явно сигналит, что им пользоваться не стоит, и указывает на замену:

```graphql
type Query {
  user(id: ID!): User
}

type User {
  id: ID!
  fullName: String @deprecated(reason: "Use firstName + lastName")
  firstName: String
  lastName: String
}
```

Сила подхода в том, что депрекейт виден инструментам и доходит до разработчика-потребителя автоматически:
- IDE показывает зачёркивание на устаревших полях.
- Линтеры выдают предупреждения при их использовании.
- В документации API отображаются пометки об устаревании.

Так клиентов мягко подталкивают мигрировать, не ломая их код прямо сейчас.


## Q16. (!) Как выглядит политика устаревания (deprecation policy)?

Смысл политики — не «выключить старое», а **дать клиентам предсказуемое время и понятный путь миграции**, чтобы удаление не стало для них сюрпризом. Типичная последовательность для публичного API:

1. **Объявить об устаревании** — release notes, email, блог.
2. **Проставить заголовок Sunset** в ответах устаревших эндпоинтов.
3. **Выдержать период устаревания** — обычно 6–24 месяца.
4. **Напоминать** клиентам по мере приближения даты.
5. **Дать гайды по миграции** и инструменты.
6. **Окончательно удалить.**

**Как это делают на практике:**
- **Stripe:** не удаляет вовсе — версии живут вечно (благодаря per-account pinning).
- **GitHub:** период депрекейта ~12–18 месяцев.
- **Twitter:** ~6 месяцев.


## Q17. Что такое HTTP-заголовок Sunset?

`Sunset` (**RFC 8594**) — стандартный HTTP-заголовок, который машиночитаемо сообщает: ресурс будет удалён к указанной дате. Это превращает депрекейт из текста в release notes в сигнал, который клиент может перехватить программно:

```http
HTTP/1.1 200 OK
Sunset: Sat, 31 Dec 2025 23:59:59 GMT
Deprecation: Mon, 01 Jan 2024 00:00:00 GMT
Link: <https://api.example.com/v3/users/123>; rel="successor-version"
```

Здесь `Deprecation` отмечает момент устаревания, `Sunset` — крайний срок, а `Link` с `rel="successor-version"` указывает на замену. Инструменты могут отлавливать `Sunset` и автоматически уведомлять разработчиков.

**Рекомендация:** включать заголовок в каждый ответ устаревшего эндпоинта, а не только при первом обращении — так клиент гарантированно его увидит.


## Q18. (!) Как корректно вывести API из эксплуатации (graceful deprecation)?

Главный принцип — **не удивлять пользователей**: дать замену, заранее предупредить несколько раз и убедиться по аналитике, что почти все ушли, прежде чем выключать. Практические шаги:

1. **Определить замену** — новый эндпоинт или новая версия.
2. **Задокументировать устаревание** — release notes, docs.
3. **Добавить заголовок Sunset** в ответы.
4. **Написать потребителям API** — несколько раз, а не один.
5. **Отслеживать использование** — аналитика по устаревшему эндпоинту показывает, кто ещё на нём.
6. **Дать инструменты миграции** — скрипт, примеры кода.
7. **Напоминать** ближе к sunset-дате.
8. **Отключить** — отдавать `410 Gone`.
9. **Вычистить серверный код** — в самом конце.

Шаги 5 и 8 связаны: отключать стоит только когда аналитика подтверждает, что трафик на старом эндпоинте упал до незначимого. Резюме: коммуницируйте, коммуницируйте и ещё раз коммуницируйте.


## Q19. (!) Рекомендации по версионированию API

Свод правил, который сводит развитие API к одной идее — **менять контракт дёшево и предсказуемо, а версии плодить только при реальной необходимости**:

1. **По умолчанию делайте обратно совместимые изменения** — пока правка совместима, новая версия не нужна.
2. **Стратегию версионирования выбирайте рано** — менять её позже болезненно.
3. **URI versioning** — самое простое для большинства случаев.
4. **Документируйте политику breaking changes** — клиенты должны знать правила игры.
5. **Анонсы Sunset** — минимум за 6 месяцев.
6. **Отдельная OpenAPI-спека на каждую версию.**
7. **API gateway** для маршрутизации к нужной версии.
8. **Тесты на всех версиях** — ловят регрессии в старых контрактах.
9. **Ограничивайте число поддерживаемых версий** — максимум 3–4.
10. **Отслеживайте переход** на новые версии — без этого не понять, когда можно гасить старые.
11. **Паттерн Tolerant Reader** на стороне клиента — чтобы добавления полей его не ломали.
12. **Не версионируйте внутренние API**, если возможно — это даёт более быструю итерацию.


## Q20. Сколько стоит держать несколько версий параллельно?

Каждая живая версия — это не только дополнительный код, но и умножение всей сопутствующей работы: тестов, багфиксов, документации, деплоя. Отсюда правило — версий должно быть мало.

**Из чего складывается стоимость:**
- **Сложность кода** — ветвления под каждую версию.
- **Матрица тестирования** — проверять приходится все версии.
- **Багфиксы в нескольких ветках** — одну и ту же ошибку чинить многократно.
- **Поддержка документации** — отдельная на каждую версию.
- **Сложность деплоя.**
- **Накладные расходы на производительность** — слой трансляции запросов.

**Как снижать:**
- **Трансляция в API Gateway** — в бэкенде живёт самая свежая версия, а gateway транслирует старые запросы к ней, не размазывая версионную логику по всему коду.
- **Паттерн Adapter** — изолировать версионные различия в отдельных адаптерах.
- **Ограничивать число версий** — агрессивно выводить старые из эксплуатации.

**Подход Stripe «все версии навсегда»** — исключение: он удобен клиентам, но требует существенных инженерных вложений, которые большинство команд позволить себе не может.
