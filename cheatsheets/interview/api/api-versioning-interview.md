# Вопросы на собеседовании: Версионирование API

API versioning — стратегия развития API без поломки существующих клиентов. Главные подходы: **URI versioning** (`/v1/`), **header versioning**, **query parameter**, **content negotiation**. Также сюда входят: обратная совместимость, политики устаревания (deprecation), sunset, semantic versioning. Критично для публичных API и систем с несколькими командами.

## Q1. Зачем нужен API versioning?

Версионирование позволяет одновременно обслуживать старый и новый контракт во время миграции клиентов. Это особенно полезно, когда мобильные приложения и сторонние интеграции обновляются не одновременно с сервером.

Версия сама по себе не гарантирует, что старый контракт будет доступен вечно. Опубликуйте срок поддержки и порядок вывода версии. Если клиенты и сервер развёртываются вместе, команда может выбрать совместимое развитие одного контракта без отдельной версии.

<a id="q2"></a>

## Q2. Что такое breaking change?

**Breaking change** — изменение контракта, после которого существующему клиенту нужно что-то поправить у себя, иначе он сломается. Ключ — не «сервер поменялся», а «клиент без правок перестаёт работать». Поэтому критерий всегда смотрят со стороны видимого клиенту контракта (запрос/ответ), а не внутренней реализации.

**Типичные breaking changes:**
- **Удаление поля** из ответа — клиент читает то, чего больше нет.
- **Переименование поля** — старый ключ исчезает, клиент получает `null`.
- **Смена типа поля** (string → number) — ломается десериализация, особенно в строго типизированных языках.
- **Опциональное поле запроса становится обязательным** — прежде валидные запросы начинают отклоняться.
- **Добавление нового обязательного поля** в запрос — старые клиенты его не шлют и получают ошибку валидации.
- **Смена структуры ответа** (object → array) — клиент разбирает другую форму.
- **Смена семантики кодов ошибок** — клиент трактует ошибку не так, как раньше.
- **Смена схемы аутентификации** — старые ключи/токены перестают работать.
- **Смена URL** без редиректа — клиент стучится в несуществующий адрес.

Общий знаменатель: любое из этого требует от клиента ответных правок. **Поэтому breaking change нельзя катить в той же версии — он требует новой.**


<a id="q3"></a>

## Q3. Какие изменения backwards-compatible? Примеры.

Обратная совместимость означает, что прежние корректные запросы продолжают работать, а существующие клиенты правильно обрабатывают ответы. Смотрите на наблюдаемое поведение, а не только на форму схемы.

Обычно совместимы новый опциональный параметр с прежним поведением по умолчанию, новый эндпоинт и ослабление обязательности поля запроса. Добавление поля ответа безопасно для клиента, который допускает неизвестные поля, но может сломать строгую десериализацию. Удаление поля или появление нового обязательного параметра обычно несовместимо.

Проверяйте совместимость на потребителях и контрактных тестах. `Tolerant Reader` помогает пережить расширения ответа, но не служит доказательством совместимости сам по себе.

<a id="q4"></a>

## Q4. Что такое URI versioning?

URI versioning кодирует версию прямо в пути URL — номер версии становится частью адреса:

```
https://api.example.com/v1/users/123
https://api.example.com/v2/users/123
```

Раз версия в адресе, маршрутизация и отладка тривиальны: шлюз направляет `/v1/` и `/v2/` на разные деплои, а любой запрос можно открыть прямой ссылкой.

**Плюсы:**
- **Просто и видно** прямо в URL.
- Легко маршрутизировать: разные версии → разные сервисы/деплои.
- Удобно тестировать — дружелюбно к браузеру (открыл ссылку и проверил).
- Понятно пользователям с первого взгляда.

**Минусы:**
- **Идентичность ресурса формально меняется** с версией: с точки зрения REST `/v1/users/123` и `/v2/users/123` — «разные ресурсы», хотя физически это один пользователь.
- Нарушает чистоту REST: URI должен идентифицировать ресурс, а не его версию.
- Один ресурс получает несколько URL.

На практике REST-пуризм здесь обычно несущественен. Это один из распространённых подходов. Stripe использует другой механизм выбора версии — заголовок `Stripe-Version` (см. Q11).


<a id="q5"></a>

## Q5. Что такое header versioning?

Header versioning передаёт версию в HTTP-заголовке, а путь URL оставляет неизменным. Один и тот же `/users/123` отдаёт разные представления в зависимости от запрошенной версии — через стандартный `Accept`:

```http
GET /users/123
Accept: application/vnd.example.v2+json
```

или через кастомный заголовок:
```http
GET /users/123
X-API-Version: 2
```

Раз версия не в адресе, концептуально это ближе к REST (URI продолжает идентифицировать ресурс), но менее наглядно.

**Плюсы:**
- **URI не меняется** — чистый REST.
- Идентичность ресурса сохраняется.
- Проще добавлять новые версии: новый адрес не плодится.

**Минусы:**
- **Версия менее заметна** — её не видно в URL, тяжело тестировать в браузере без расширений.
- Сложнее документировать.
- Усложняется кэширование: нужен заголовок `Vary` по версионному заголовку, иначе CDN отдаст ответ не той версии.

**Где применяется:** в более новом API GitHub.


<a id="q6"></a>

## Q6. Что такое query parameter versioning?

Версия передаётся как параметр строки запроса — путь к ресурсу не меняется, версия просто дописывается к query:

```
https://api.example.com/users/123?version=2
https://api.example.com/users/123?api-version=2024-01-15
```

Это компромисс между URI- и header-подходом: версию видно в URL (как у URI versioning), но структуру пути менять не нужно.

**Плюсы:**
- Видно в URL — наглядно.
- Удобно тестировать: ссылку легко скопировать и открыть.

**Минусы:**
- Засоряет query string — версия смешивается с фильтрами и пагинацией (`?page=2&version=2`) и её легко случайно потерять при формировании ссылок.
- Менее устоявшаяся практика, чем URI versioning.

**Где применяется:** некоторые API принимают версию в query-параметре; конкретный механизм нужно сверять с документацией сервиса. Stripe использует заголовок `Stripe-Version`.


<a id="q7"></a>

## Q7. Что такое content negotiation (версия через заголовок Accept)?

Версия зашита в кастомный MIME-тип, а нужное представление сервер выбирает штатным механизмом HTTP content negotiation — по содержимому заголовка `Accept`, при неизменном пути:

```http
GET /users/123
Accept: application/vnd.example.user.v2+json
```

По сути это частный случай header versioning: версию несёт не отдельный заголовок `X-API-Version`, а сам медиатип (`vnd.*`).

**Плюсы:**
- Это механизм из стандарта HTTP, а не самодельная схема.
- Идентичность ресурса сохраняется — URL не меняется.

**Минусы:**
- Громоздкие MIME-типы (`application/vnd.company.resource.v2+json`) трудно набирать и документировать.
- Тяжело воспринимается людьми.
- Встречается редко.

Выбирайте этот способ, когда клиентам удобно управлять представлением через `Accept`, а инфраструктура корректно обрабатывает разные варианты ответа.


<a id="q8"></a>

## Q8. Что такое hostname-based версионирование?

Hostname-based versioning размещает версии на разных именах хостов:

```text
v1.api.example.com/users/123
v2.api.example.com/users/123
```

Это позволяет маршрутизировать версии независимо, в том числе на разные деплои. Однако отдельный хост сам по себе не означает отдельный кластер: оба имени могут вести в одну систему. Нужно сопровождать DNS и сертификаты. Для браузера разные поддомены — разные origin, поэтому при кросс-origin доступе учитывают CORS и cookies.

<a id="q9"></a>

## Q9. Какой подход к версионированию выбрать?

Выбор зависит от аудитории, инфраструктуры и срока поддержки версий. У публичного REST путь `/v1/` прост для диагностики и маршрутизации; заголовок сохраняет один путь ресурса, но требует явной обработки на клиентах и в кэше.

GraphQL обычно развивает единую схему совместимыми изменениями и пометками `@deprecated`. Это распространённый подход, а не технический запрет на версионирование схемы. В gRPC версию можно отражать в имени пакета, например `example.user.v2`.

Зафиксируйте стратегию до публикации контракта и сообщите, какие изменения требуют новой версии.

<a id="q10"></a>

## Q10. Что такое semantic versioning (SemVer)?

SemVer — конвенция нумерации, кодирующая характер изменений прямо в номере версии `MAJOR.MINOR.PATCH` (например, `2.5.3`):

- **MAJOR** — breaking changes (несовместимые изменения).
- **MINOR** — новые фичи, обратно совместимые.
- **PATCH** — исправления багов.

Так по номеру сразу видно, можно ли обновляться безопасно: смена MAJOR сигналит «осторожно, сломается», MINOR/PATCH — «совместимо».

**Версионирование HTTP-API обычно ≠ полный SemVer:**
- В URL выносят только MAJOR (`/v1/`): менять адрес на каждый минорный апдейт непрактично, а `/v2.5.3/` не нужен — минорные и патч-изменения по определению совместимы.
- MINOR/PATCH отслеживают в документации и changelog.

**А вот к SDK и клиентским библиотекам** полный SemVer применяют целиком — там номер `2.5.3` несёт реальный смысл (например, в пакетах npm/Maven).


<a id="q11"></a>

## Q11. Что такое date-based versioning (подход Stripe)?

Date-based versioning использует дату в идентификаторе выпуска. Например, Stripe позволяет выбрать версию API заголовком `Stripe-Version`, сохраняя путь `/v1/...`.

```http
Stripe-Version: 2025-03-31.basil
```

Текущая схема Stripe различает крупные выпуски, которые могут содержать несовместимые изменения, и ежемесячные совместимые выпуски в пределах крупной серии. Дата указывает версию поведения, но сама по себе не обещает бессрочную поддержку и не означает, что каждая дата содержит breaking change. Для обновления сверяют changelog, версию SDK и вебхуков.

<a id="q12"></a>

## Q12. Что такое per-account version pinning (модель Stripe)?

У Stripe версия аккаунта служит настройкой по умолчанию. Для отдельного API-запроса версию можно выбрать через `Stripe-Version`; SDK тоже может закреплять версию, соответствующую его выпуску.

Webhook endpoint может получить отдельную версию при создании. Если она не задана, используется версия аккаунта по умолчанию. Поэтому обновление API-запросов и формата вебхуков проверяют отдельно. Версия уже созданного события не меняется от последующего запроса на его чтение.

<a id="q13"></a>

## Q13. Как версионировать webhooks?

Вебхук инициирует сервер, поэтому получатель не выбирает формат заголовком в момент доставки. Версию и схему события согласуют заранее: в настройке webhook endpoint, контракте события или в явном поле версии payload.

При обновлении получателей сохраняют старый формат на срок миграции и тестируют его отдельно от ответов обычного API. Например, Stripe позволяет закрепить версию webhook endpoint; некоторые события API v2 передают тонкий payload со ссылкой на ресурс, а не снимок объекта.

<a id="q14"></a>

## Q14. Почему GraphQL обходится без версий?

Философия GraphQL — **эволюция единой схемы без версионирования**. Это возможно из-за самой модели запросов: клиент сам перечисляет нужные поля, поэтому добавление новых полей в схему его не затрагивает — он их просто не запрашивает.

**Вместо версий:**
- **Добавлять поля** — клиент запрашивает только то, что ему нужно, так что добавления ничего не ломают.
- **Помечать поля устаревшими** через `@deprecated`.
- **Не удалять сразу:** сначала узнать об использовании поля, предупредить клиентов и дать время на переход.

```graphql
type User {
  id: ID!
  name: String!
  email: String!
  username: String @deprecated(reason: "Use 'handle' instead")
  handle: String!  # new field
}
```

Здесь старое поле `username` остаётся рабочим, рядом добавлено новое `handle`, а директива `@deprecated` подталкивает клиентов мигрировать. Клиенты продолжают использовать `username`, пока не перейдут.

Перед удалением `username` проверяют его использование и миграцию клиентов; одна пометка `@deprecated` не делает удаление безопасным.


<a id="q15"></a>

## Q15. Как работает field deprecation в GraphQL?

Поле помечают директивой `@deprecated` с причиной — оно остаётся рабочим, но схема явно сигналит, что им пользоваться не стоит, и указывает на замену:

```graphql
type Query {
  user(id: ID!): User
}

type User {
  id: ID!
  fullName: String @deprecated(reason: "Use firstName + lastName")
  firstName: String
  lastName: String
}
```

Сила подхода в том, что депрекейт виден инструментам и доходит до разработчика-потребителя автоматически:
- IDE показывает зачёркивание на устаревших полях.
- Линтеры выдают предупреждения при их использовании.
- В документации API отображаются пометки об устаревании.

Так клиентов мягко подталкивают мигрировать, не ломая их код прямо сейчас.


<a id="q16"></a>

## Q16. Как выглядит политика устаревания (deprecation policy)?

Политика устаревания даёт клиентам понятный срок и путь миграции. Опубликуйте замену, дату начала устаревания и планируемый срок вывода. Предупредите потребителей через документацию и доступные каналы; машинный сигнал можно передать заголовками `Deprecation` и `Sunset`.

Длительность перехода выбирают по реальному циклу обновления клиентов и условиям поддержки. Следите за трафиком старой версии и повторяйте уведомления перед отключением. Нельзя выводить универсальный срок из практики одного сервиса или обещать вечную доступность без такой политики.

<a id="q17"></a>

## Q17. Что такое HTTP-заголовок Sunset?

`Sunset` по [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html) передаёт HTTP-дату, когда ресурс, предположительно, перестанет отвечать:

```http
Sunset: Sun, 31 Dec 2028 23:59:59 GMT
Deprecation: @1851292800
```

Это подсказка о планируемом выводе, а не гарантия точного момента удаления. Заголовок `Deprecation` по [RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html) сообщает об устаревании; его дата имеет другой формат. Переход на замену объясняют в документации и могут указать через `Link`.

<a id="q18"></a>

## Q18. Как корректно вывести API из эксплуатации (graceful deprecation)?

Плавный вывод начинается с опубликованной замены и срока миграции. Предупредите потребителей через документацию и доступные каналы, добавьте машинные сигналы `Deprecation` и `Sunset`, затем отслеживайте оставшийся трафик по старому контракту.

Перед отключением проверьте, кто ещё использует старую версию, и дайте достаточно времени на переход. После вывода можно отвечать `410 Gone`, если сервер знает, что ресурс существовал и удалён, либо выбрать другой ответ по контракту. Отключение не должно быть неожиданным для клиентов.

<a id="q19"></a>

## Q19. Рекомендации по версионированию API

Развивайте контракт совместимыми изменениями, когда это возможно. Для несовместимых изменений публикуйте новую версию и правила миграции. Стратегию выбора версии, срок поддержки и способ уведомления клиентов согласуйте до появления зависимых потребителей.

Поддерживайте документацию и проверки для каждой живой версии. Сколько версий держать одновременно, решают по реальным клиентам и стоимости сопровождения; универсального предела в три или четыре версии нет.

<a id="q20"></a>

## Q20. Сколько стоит держать несколько версий параллельно?

Каждая поддерживаемая версия требует проверок, документации, анализа ошибок и работы с потребителями. Общая реализация может уменьшить дублирование кода, но не отменяет различия контрактов.

Изолируйте версионные преобразования там, где они нужны, и проверяйте старые сценарии контрактными тестами. Сроки поддержки и число одновременно живых версий задавайте по потребностям клиентов и возможностям команды; не обещайте бессрочную поддержку без явной политики.
