# Вопросы на собеседовании: `Richardson Maturity Model (REST)`

`Richardson Maturity Model` (Leonard Richardson, 2008) — модель оценки **степени соответствия REST** для API, 4 уровня (0-3). Уровень 3 (HATEOAS) — «truly RESTful» по Roy Fielding. На практике большинство «REST API» застревают на Level 2.

Модель помогает понять, что значит REST глубже, чем просто «JSON поверх HTTP».

## Q1. (!) Что такое Richardson Maturity Model?

**Richardson Maturity Model (RMM)** — шкала из 4 уровней (0-3), которая измеряет, насколько API использует возможности HTTP и приближается к REST. Каждый следующий уровень добавляет одно новое требование поверх предыдущего, поэтому это именно «лестница зрелости»: пропустить ступень нельзя.

**Уровни** (каждый строится на предыдущем):

| Level | Название | Что добавляет |
|-------|----------|---------------|
| **0** | The Swamp of POX | HTTP только как транспорт (RPC-стиль) |
| **1** | Resources | Отдельный URI на каждый ресурс |
| **2** | HTTP Verbs | Семантика HTTP (GET, POST, коды статусов) |
| **3** | Hypermedia Controls (HATEOAS) | Ссылки для навигации прямо в ответах |

Идея проста: чем выше уровень, тем больше работы перекладывается с тела сообщения на сам протокол HTTP. На Level 0 HTTP — просто труба, на Level 3 он несёт и адресацию ресурсов, и семантику операций, и навигацию по API.

**Автор:** Leonard Richardson (доклад на QCon, 2008), популяризировал Martin Fowler в статье 2010 года.

## Q2. (!) Зачем нужна Richardson Maturity Model?

Главная польза модели — общий язык для разговора об API. Слово «REST» все понимают по-разному, и RMM даёт точную точку отсчёта: можно сказать «мы на Level 2» вместо расплывчатого «у нас REST».

**Разводит разные смыслы слова «REST API»:**

- многие называют REST даже Level 0-1 (JSON поверх POST);
- **Level 2** — типичный прагматичный REST, к которому относится большинство API;
- **Level 3** — академически «truly RESTful» (с HATEOAS).

**Помогает понять предмет глубже**, отвечая на вопросы:

- что вообще значит «RESTful» и почему JSON-over-HTTP — это ещё не REST;
- почему важны HTTP-глаголы и коды статусов (а не один POST на всё);
- какие следствия даёт HATEOAS и зачем он нужен.

**Важный нюанс:** модель ничего не предписывает — она **описательная, а не нормативная**. Level 2 не «провал» и не «недоделанный REST»: для большинства задач это осознанный и правильный выбор. Лестница показывает структуру, но не обязывает лезть на самый верх.

## Q3. (!) Level 0 — что такое «The Swamp of POX»?

Level 0 — это RPC-стиль поверх HTTP: вызов удалённой процедуры, где HTTP служит лишь транспортом. **POX = Plain Old XML** (старый добрый XML), отсюда и название «болото POX». Суть в том, что от REST здесь нет ничего, кроме того, что данные летят по HTTP.

```http
POST /endpoint HTTP/1.1

<request>
  <method>getUser</method>
  <id>123</id>
</request>
```

**Ключевые признаки** (по ним узнаётся Level 0):
- **один URL** (endpoint) — все вызовы туннелируются через него;
- **все запросы — POST**, GET/PUT/DELETE не используются;
- HTTP выступает только транспортом, его семантика игнорируется;
- какое действие выполнять, сервер узнаёт **из тела запроса** (`<method>getUser</method>`), а не из URL и метода.

**Примеры:** SOAP, XML-RPC, JSON-RPC.

**Почему это не REST:** адресуемых ресурсов нет, глаголы HTTP не несут смысла, кэширование и стандартные инструменты не работают. Технически HTTP используется, но как «глупая труба» — отсюда и «болото».

## Q4. (!) Level 1 — что даёт переход к ресурсам (Resources)?

На Level 1 появляется главное понятие REST — **ресурс с собственным URI**. Вместо одного endpoint у каждой сущности теперь свой адрес: `/users`, `/orders`, `/products`. Это первый шаг «делим и властвуем»: огромный единый сервис разбивается на адресуемые части.

```http
POST /users          # не /endpoint
POST /orders         # не /endpoint
POST /products       # не /endpoint
```

**Что НЕ изменилось:** по-прежнему всё идёт через POST, а семантика операции всё ещё прячется в теле. Меняется только адресация — но и это уже много.

**Что это даёт:**
- **структура** — API становится понятной картой сущностей, а не одной чёрной дырой;
- **кэшируемость** — у ресурса есть URL, значит, его в принципе можно адресовать и кэшировать;
- **исследуемость** — по URI видно, какие сущности есть в системе.

Относительно Level 0 это большой шаг: система перестаёт быть монолитным вызовом и обретает «карту» ресурсов.

## Q5. (!) Level 2 — зачем нужны HTTP-глаголы и коды статусов?

На Level 2 семантика операции переезжает из тела запроса в сам протокол: **глагол говорит, что делаем, а код ответа — чем закончилось**. Именно здесь API начинает «играть по правилам HTTP», а не просто пользоваться им как транспортом.

```http
GET    /users/123     # получить
POST   /users         # создать
PUT    /users/123     # полное обновление / создание
PATCH  /users/123     # частичное обновление
DELETE /users/123     # удалить

# Status codes
200 OK
201 Created
204 No Content
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
500 Internal Server Error
```

**Почему это важно** — стандартная семантика бесплатно включает всю инфраструктуру вокруг HTTP:
- **кэширование** работает само — GET объявлен безопасным, поэтому прокси и CDN могут его кэшировать;
- **идемпотентность** — клиент и сети знают, что PUT/DELETE можно безопасно повторить при таймауте;
- **готовый инструментарий** — браузеры, прокси, CDN, шлюзы понимают глаголы и коды без специального обучения.

**Главный вывод:** большинство «REST API» на практике — это именно **Level 2**. Он даёт почти все выгоды HTTP при низкой сложности, поэтому считается разумным балансом прагматики и идеологии REST.

## Q6. (!) Level 3 — что такое Hypermedia Controls (HATEOAS)?

Level 3 добавляет последнее: **в ответы встраиваются ссылки на доступные действия**. Клиент не хранит у себя список URL, а обнаруживает следующие шаги прямо в полученном ресурсе. **HATEOAS** расшифровывается как *Hypermedia as the Engine of Application State* — «гипермедиа как движок состояния приложения»: именно ссылки в ответах ведут клиента по состояниям.

```json
{
  "id": 123,
  "name": "Alice",
  "_links": {
    "self": { "href": "/users/123" },
    "orders": { "href": "/users/123/orders" },
    "update": { "href": "/users/123", "method": "PUT" },
    "delete": { "href": "/users/123", "method": "DELETE" }
  }
}
```

**Как клиент работает с таким API:**
1. стартует с одной известной точки входа (`/`);
2. переходит по ссылкам из ответов к нужным ресурсам;
3. выполняет действия по ссылкам, которые сервер сам разрешил.

**Чем это отличается от хардкода URL:** навигацией управляет не клиент, а сервер. Он может переименовать URL или перестроить структуру ресурсов — и пока ссылки отдаются под прежними именами (`self`, `orders`), клиенты продолжают работать. Связанность между клиентом и сервером падает до минимума — это и есть смысл «truly RESTful».

## Q7. (!) Что такое HATEOAS и зачем он нужен?

**HATEOAS** — это принцип, по которому клиент перемещается по состояниям приложения, переходя по гипермедиа-ссылкам, которые в каждом ответе отдаёт сам сервер. Клиент не строит URL по своим правилам — он берёт готовые ссылки из тела ответа.

**Аналогия — обычный веб-сёрфинг:** вы не набираете каждый адрес руками, а кликаете по ссылкам на странице. Сайт сам ведёт вас дальше. HATEOAS делает то же самое для машинного клиента: сервер подсказывает, что можно сделать прямо сейчас.

Главная цель — **снизить связанность** между клиентом и сервером. Сравним два подхода:

**Без HATEOAS (обычный API):**
- клиент заранее зашивает у себя ВСЕ URL (`/users/{id}`, `/users/{id}/orders`, …);
- сильная связанность: знание структуры API живёт в коде клиента;
- любое изменение URL на сервере ломает клиентов.

**С HATEOAS:**
- клиент знает только одну точку входа (`/`);
- все остальные адреса и действия он обнаруживает по ссылкам в ответах;
- сервер может менять URL и структуру, не ломая клиентов, — контракт держится на именах связей (`orders`, `self`), а не на конкретных путях.

## Q8. (!) Какие бывают форматы hypermedia (HAL, JSON:API, Siren)?

Чтобы класть ссылки в ответ единообразно, придумали стандартные медиатипы. Они различаются тем, как описывают ссылки и насколько богато выражают действия. Кратко: **HAL** — минималистичный (только ссылки и вложенные ресурсы), **JSON:API** — строгий, с типами и связями, **Siren** — самый богатый, описывает ещё и действия с методами и полями форм.

**HAL (Hypertext Application Language)** — простой: блок `_links` для ссылок, `_embedded` для вложенных ресурсов:
```json
{
  "id": 123,
  "name": "Alice",
  "_links": {
    "self": { "href": "/users/123" },
    "orders": { "href": "/users/123/orders" }
  },
  "_embedded": {
    "address": { ... }
  }
}
```

**JSON:API** — строгая спецификация: данные с явным `type` и `id`, отдельный блок `relationships` для связей:
```json
{
  "data": {
    "type": "user",
    "id": "123",
    "attributes": { "name": "Alice" },
    "relationships": {
      "orders": {
        "links": { "related": "/users/123/orders" }
      }
    }
  }
}
```

**Siren** — самый выразительный: помимо данных и ссылок описывает `actions` с методом и (опционально) полями, то есть полноценные «формы» для клиента:
```json
{
  "class": ["user"],
  "properties": { "name": "Alice" },
  "actions": [
    { "name": "update", "method": "PUT", "href": "/users/123" }
  ],
  "links": [...]
}
```

**Реализации на Java:** Spring HATEOAS, RestEasy. **Практический совет:** выбирать формат стоит один раз на весь API — смешивать HAL и JSON:API в одном сервисе нельзя, иначе клиентам придётся уметь оба.

## Q9. В чём преимущества HATEOAS?

Все плюсы HATEOAS вытекают из одной идеи — сервер сам сообщает клиенту, что и где можно сделать:

1. **Слабая связанность** — клиенты знают только точку входа, остальное берут из ссылок.
2. **Эволюция сервера** — URL и структуру можно менять, не ломая клиентов.
3. **Обнаруживаемость** — API самодокументируется: доступные переходы видны прямо в ответе.
4. **Машина состояний прямо в ссылках** — сервер кладёт в ответ только те действия, которые допустимы в текущем состоянии ресурса; клиенту не нужно знать бизнес-правила.
5. **Проще версионирование** — ссылки могут нести информацию о версии, так что клиент идёт туда, куда указал сервер.

Самый сильный из этих пунктов — четвёртый. Логика «что можно сделать с заказом сейчас» живёт на сервере и приезжает клиенту в виде набора ссылок:

**Пример машины состояний:**
```json
// Заказ в состоянии PENDING
{
  "_links": {
    "approve": { "href": "/orders/123/approve" },
    "cancel": { "href": "/orders/123/cancel" }
  }
}

// Заказ в состоянии SHIPPED
{
  "_links": {
    "track": { "href": "/orders/123/tracking" }
    // нет approve/cancel — эти действия недопустимы
  }
}
```

Клиент просто рисует кнопки по присланным ссылкам: есть `cancel` — показываем «Отменить», нет — не показываем. **Бизнес-правила не дублируются** на клиенте и сервере — единственный источник истины остаётся на сервере.

## Q10. (!) Почему HATEOAS редко применяется на практике?

Несмотря на теоретическую красоту, в реальности доминирует **Level 2**, а HATEOAS встречается редко. Причина не одна — против него работает сразу несколько факторов, причём ключевой в том, что выгоды получает сервер, а платит за них клиент.

**Причины:**

1. **Сложность клиента** — вместо простого «дёрнуть известный URL» клиент должен парсить ссылки и переходить по ним; выгода (слабая связанность) достаётся серверу, а работа ложится на клиент.
2. **Нет единого стандарта** — HAL, JSON:API, Siren конкурируют, экосистема фрагментирована, общих инструментов мало.
3. **Версионирование** — встроенные ссылки не отменяют необходимость версионировать API при ломающих изменениях схемы.
4. **Не хватает инструментов** — фронтенд-разработчикам проще захардкодить пути, чем строить навигацию по ссылкам.
5. **Производительность** — блоки ссылок раздувают payload, особенно в коллекциях.
6. **Потребители хотят OpenAPI** — командам нужна заранее известная схема для кодогенерации, а не обнаружение API в рантайме.
7. **GraphQL** закрывает часть тех же задач (гибкая навигация по данным) другим способом.

**Итоговый консенсус индустрии:** HATEOAS академически чист, но на практике прагматичный дизайн API = **Level 2 + документация OpenAPI**. Цена внедрения почти всегда перевешивает выгоду.

## Q11. (!) HTTP-глаголы: GET, POST, PUT, PATCH, DELETE — в чём разница?

Каждый глагол несёт свой контракт: что он делает, можно ли его безопасно повторить (идемпотентность) и меняет ли он данные (безопасность). Эти три свойства определяют, как с методом обращаются клиенты, прокси и CDN.

| Метод | Семантика | Идемпотентный | Безопасный |
|-------|-----------|---------------|------------|
| `GET` | Получить | **Да** | **Да** |
| `POST` | Создать / произвольное действие | Нет | Нет |
| `PUT` | Полная замена / создание | **Да** | Нет |
| `PATCH` | Частичное обновление | Иногда | Нет |
| `DELETE` | Удалить | **Да** | Нет |
| `HEAD` | Как GET, но без тела | Да | Да |
| `OPTIONS` | Узнать разрешённые методы | Да | Да |

**Два ключевых свойства:**
- **Идемпотентный** — повторение одинакового запроса не меняет конечного результата (важно при ретраях на таймауте).
- **Безопасный** — запрос не меняет состояние на сервере (можно кэшировать и спокойно повторять).

**PUT vs PATCH** — частый вопрос на собеседовании:
- **PUT** отправляет **весь** ресурс целиком — то, чего нет в теле, обнуляется. Поэтому PUT идемпотентен: повторная отправка того же тела даёт тот же результат.
- **PATCH** отправляет **только изменения** (дельту). Идемпотентность зависит от семантики патча: замена поля идемпотентна, а операция вроде «увеличить счётчик на 1» — нет.

## Q12. (!) Как устроены HTTP-коды статусов по категориям?

Первая цифра кода — это **класс ответа**, и по ней клиент сразу понимает исход, не зная конкретного кода. Это и есть смысл категорий: `2xx` — успех, `3xx` — иди в другое место, `4xx` — ошибся клиент, `5xx` — упал сервер. Правильный код позволяет клиенту реагировать автоматически (ретраить `5xx`, не ретраить `4xx`).

**1xx — информационные** (на практике встречаются редко)

**2xx — успех:**
- 200 OK
- 201 Created (POST создал новый ресурс)
- 202 Accepted (запущена асинхронная обработка)
- 204 No Content (успех, тела нет)

**3xx — перенаправления:**
- 301 Moved Permanently
- 304 Not Modified (кэш актуален)

**4xx — ошибка клиента:**
- 400 Bad Request (не прошла валидация)
- 401 Unauthorized (нет аутентификации)
- 403 Forbidden (аутентификация есть, но доступ запрещён)
- 404 Not Found
- 405 Method Not Allowed
- 409 Conflict (например, несовпадение версии ресурса)
- 422 Unprocessable Entity (ошибки валидации)
- 429 Too Many Requests (превышен лимит)

**5xx — ошибка сервера:**
- 500 Internal Server Error
- 502 Bad Gateway
- 503 Service Unavailable
- 504 Gateway Timeout

**Главный антипаттерн — «200 на всё»:** возвращать `200 OK` даже при ошибке, спрятав её в теле (`{"error": ...}`). Так клиент, прокси и мониторинг теряют возможность реагировать автоматически. Правильный код в статус-строке — это сигнал, который понимают все участники цепочки без чтения тела.

## Q13. Идемпотентность HTTP-методов — что это и зачем?

**Идемпотентность** означает: сколько раз ни повтори один и тот же запрос, конечное состояние сервера будет таким же, как после одного вызова. Свойство критично для надёжности: при таймауте клиент не знает, дошёл запрос или нет, и идемпотентный метод можно спокойно повторить.

- **Идемпотентные методы:** GET, HEAD, OPTIONS, PUT, DELETE.
- **Неидемпотентные:** POST (и обычно PATCH).

**Почему DELETE идемпотентен** — важна не одинаковость ответа, а одинаковость конечного состояния:
```
DELETE /users/123 (первый раз → 204 No Content)
DELETE /users/123 (второй раз → 404 или 204) — конечное состояние то же
```
Пользователя `123` нет ни после первого вызова, ни после второго — цель достигнута. То, что код ответа отличается, идемпотентности не нарушает.

**Почему POST не идемпотентен:** каждый вызов создаёт новый ресурс, поэтому два повтора дадут два объекта.

**Как сделать POST идемпотентным** (нужно для платежей и заказов):
- клиент шлёт **ключ идемпотентности** в заголовке `Idempotency-Key: abc123`;
- сервер запоминает ключ и на повторный запрос с тем же ключом возвращает прежний ответ, не выполняя операцию снова.

```http
POST /payments HTTP/1.1
Idempotency-Key: 7f9c1d-...

{"amount": 100}
```

## Q14. Чем безопасные (safe) методы отличаются от небезопасных?

**Безопасный (safe)** метод по определению **не меняет состояние** на сервере — это методы только для чтения: **GET, HEAD, OPTIONS**.

**Небезопасный (unsafe)** метод состояние меняет: **POST, PUT, PATCH, DELETE**.

Это не просто формальность — на безопасности построено поведение всей веб-инфраструктуры:
- **CDN и прокси** кэшируют ответы безопасных методов (повторный вызов ничего не сломает);
- **поисковые краулеры** свободно ходят по безопасным ссылкам;
- **браузеры** заранее предзагружают безопасные URL (prefetch).

**Отсюда железное правило:** никогда не вешайте действие с побочным эффектом на GET. Если поставить «удалить» под GET, то краулер, prefetch или прокси однажды выполнят это удаление сами, без участия пользователя.

```
ПЛОХО:   GET /users/123/delete
ХОРОШО:  DELETE /users/123
```

## Q15. (!) Как критикует модель Roy Fielding и за что критикуют саму RMM?

Здесь сталкиваются две позиции — автора REST и здравого смысла.

**Позиция Roy Fielding** (создатель REST, диссертация 2000 года) — RMM мягко завышает оценку «промежуточных» уровней. По Fielding, без гипертекста REST вообще нет:
> "If the engine of application state (and hence the API) is not being driven by hypertext, then it cannot be RESTful."

То есть **настоящим REST он считает только Level 3** — Level 0-2 для него вовсе не REST, а лишь «HTTP-API».

**Критика в обратную сторону — самой RMM:**
- слово «лестница зрелости» подсказывает «выше = лучше», но это верно не всегда;
- Level 2 — это прагматичный отраслевой стандарт, а не «недозрелый» или провальный API;
- уровни не являются обязательной целью, к которой нужно стремиться любой ценой.

**Итог спора:** большинство современных API — это Level 2 + OpenAPI/Swagger. Индустрия сознательно выбрала прагматику против академической чистоты, и для большинства задач это правильный выбор.

## Q16. Прагматичный REST против идеалистичного — в чём разница?

Это два ответа на вопрос «что такое REST на практике»: остановиться на удобном Level 2 или дойти до полного Level 3 с HATEOAS.

**Прагматичный REST (RMM Level 2)** — то, что в индустрии и называют «REST»:
- HTTP-глаголы и коды статусов используются по смыслу;
- чистые URI на ресурсы;
- тела запросов и ответов в JSON;
- контракт описан в OpenAPI.

**Идеалистичный REST (RMM Level 3)** — добавляет к этому гипермедиа:
- всё перечисленное выше **плюс HATEOAS**;
- гипермедиа-формат ответов (HAL и т. п.);
- самообнаружение действий клиентом в рантайме.

**Что побеждает на практике:** доминирует прагматичный подход. Ключевая причина — **OpenAPI стал де-факто стандартом** описания API: он закрывает главную потребность (знать заранее структуру и сгенерировать клиент), ради которой задумывался HATEOAS, но дешевле и привычнее для команд.

## Q17. (!) Чем GraphQL и gRPC отличаются от REST?

Все три — способы общения между системами, но с разным акцентом. REST мыслит ресурсами и опирается на HTTP, GraphQL — гибким графом данных под запрос клиента, gRPC — быстрым типизированным вызовом процедур. Понимать различия нужно, чтобы выбирать инструмент под задачу, а не «по моде».

**REST (RMM Level 2):**
- работает поверх HTTP;
- ресурсо-ориентированный (URL = сущность);
- слабое место — лишние round-trip-ы: over-fetch (пришло больше нужного) и under-fetch (пришлось делать несколько запросов);
- кэширование получается «бесплатно» через HTTP.

**GraphQL** — решает проблему over/under-fetch:
- один эндпоинт на весь API;
- клиент сам описывает, какие именно поля ему нужны, — ни лишнего, ни недостающего;
- строгая схема как контракт;
- подписки для данных в реальном времени;
- расплата — **меньше используется семантика HTTP** (кэширование и коды статусов сложнее).

**gRPC** — заточен под скорость и типизацию:
- бинарный формат (Protobuf) вместо текстового JSON;
- работает по HTTP/2;
- строгая типизация из `.proto`-контракта;
- двунаправленный стриминг;
- ниша — **взаимодействие сервис-сервис** внутри инфраструктуры;
- минус — **не работает нативно в браузере** (нужен прокси grpc-web).

**Как выбрать — по сценарию:**
- **публичные API** — REST (привычен потребителям, кэшируется, работает везде);
- **мобильные клиенты и сложные выборки данных** — GraphQL (экономит трафик и round-trip-ы);
- **внутренние микросервисы** — gRPC (скорость и строгий контракт);
- на практике часто встречается **гибрид**: REST наружу для клиентов, gRPC внутри между сервисами.

**Итог:** RMM описывает 4 уровня зрелости REST: Level 0 — RPC поверх HTTP, Level 1 — ресурсы с отдельными URI, Level 2 — корректная семантика HTTP-глаголов и кодов, Level 3 — HATEOAS. На практике стандарт — Level 2 + OpenAPI; HATEOAS академически «чист», но в индустрии редок.
