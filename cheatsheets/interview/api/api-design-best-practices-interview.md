# Вопросы на собеседовании: Практики проектирования API

Проектирование API — критический навык. Хороший API: **интуитивный, консистентный, расширяемый, безопасный**. Плохой API — вечная боль. На интервью спрашивают: соглашения об именовании, пагинацию, фильтрацию, формат ошибок, идемпотентность, rate limiting, аутентификацию. Коллекция лучших практик от Google, Microsoft, Stripe, GitHub.

## Q1. Как называть ресурсы в REST API (существительные, множественное число)?

Ресурс — это **сущность** («пользователь», «заказ»), а не действие. Поэтому в URL должны быть существительные во множественном числе, а что именно с ресурсом сделать — определяет HTTP-метод. URL отвечает на вопрос «над чем», метод — «что делаем».

**Существительные во множественном числе:**

```
✓ /users
✓ /orders
✓ /products
✗ /getUsers       # verb
✗ /user           # singular
```

Почему множественное, а не единственное: коллекция `/users` и элемент `/users/123` образуют единообразную пару — не нужно гадать, где `user`, а где `users`.

**Иерархия** выражается через путь:
```
✓ /users/123/orders/456
```

**Глаголы в URL не нужны** — их роль играют HTTP-методы:
```
✓ DELETE /users/123     # not POST /users/123/delete
✓ PUT /users/123        # not POST /users/123/update
```

**Исключение:** действия, которые не укладываются в CRUD (например, «опубликовать», «отменить») — см. Q8.

## Q2. Как разделить идентификатор ресурса и параметры выборки в URL?

Полный URL содержит схему, хост, путь и необязательную query-строку. В примере ниже версия размещена в пути — это выбор данного API, а не обязательное требование REST. Идентификатор элемента указывает адрес ресурса, query-параметры меняют выборку коллекции.

```
https://api.example.com/v1/users/123/orders?status=pending&limit=10
└──────┘└─────────────┘└─┘└───────────────┘└──────────────────────┘
 scheme      host      ver  resource path        query string
```

**Рекомендации:**
- **Поддомен для API** (`api.example.com`) — отделяет API от веб-сайта, упрощает маршрутизацию и масштабирование.
- **Версия в пути** (`/v1/`) — позволяет ломать контракт в новой версии, не трогая старых клиентов.
- **URL в нижнем регистре** (`/users`, а не `/Users`) — регистр в пути чувствителен, разнобой ведёт к ошибкам.
- **Дефисы, а не подчёркивания** (`/order-items`, а не `/order_items`) — дефис не теряется при подчёркнутом тексте в документации.
- **Существительные во множественном числе** для коллекций.
- **Идентификаторы — в пути** (`/users/123`): они адресуют ресурс.
- **Фильтры — в query string** (`?status=active`): они уточняют выборку, а не адресуют ресурс.

## Q3. snake_case или camelCase для имён полей в JSON?

Главное правило: **выберите одно соглашение и применяйте его ко всему API**. Сам выбор менее важен, чем консистентность — смешение `first_name` и `lastName` в одном ответе путает клиентов и ломает кодогенерацию.

**snake_case** — чаще встречается в публичных API:
```json
{"first_name": "Alice", "created_at": "2025-04-19T10:00:00Z"}
```

**camelCase** — ближе к JavaScript:
```json
{"firstName": "Alice", "createdAt": "2025-04-19T10:00:00Z"}
```

**Кто что выбрал:**
- snake_case: Stripe, Slack, Twitter, экосистема Python.
- camelCase: Google, Microsoft, экосистема JavaScript.

**В Java-бэкенде** поля внутри пишут в `camelCase` (`firstName`), а на границе сериализации разводят имена через Jackson — `@JsonProperty("first_name")`, если наружу API отдаёт snake_case. Так внутренний код остаётся идиоматичным, а контракт — стабильным.

## Q4. Как передавать в API конкретный момент времени?

Используйте **ISO 8601** — международный стандарт, который понимают все языки и библиотеки. Для конкретного момента времени укажите `Z` или смещение; локальное время без него неоднозначно.

```json
"created_at": "2025-04-19T14:30:00Z"           // UTC
"created_at": "2025-04-19T14:30:00+02:00"       // with timezone
```

**Чего избегать и почему:**
- Unix-таймстампов в публичном API — они нечитаемы для человека и провоцируют ошибки с секундами/миллисекундами; для людей отдавайте ISO.
- Кастомных форматов («April 19, 2025») — их нельзя надёжно распарсить и они зависят от локали.
- Локального времени без таймзоны — без смещения момент времени неоднозначен.

**В Java** работайте с `Instant`, `OffsetDateTime` или `ZonedDateTime` (но не с устаревшим `Date`): их собственная текстовая форма и есть ISO 8601. А вот уйдёт ли поле в JSON строкой или числом секунд, решает настройка сериализатора (`WRITE_DATES_AS_TIMESTAMPS` у Jackson) — её стоит задать явно, а не считать верной по умолчанию.

## Q5. Как адресовать связанные ресурсы без избыточной вложенности?

Отношение «принадлежит» выражают вложенностью в URL: путь от родителя к потомку. Это сразу показывает, чьим является ресурс, и встроенно ограничивает выборку (scoping).

```
/users/123/orders          # all orders для user 123
/users/123/orders/456      # specific order
/orders/456                # also valid (independent access)
```

**Плюсы вложенности:**
- Понятная принадлежность (ownership) — видно, что заказ относится к пользователю 123.
- Скоупинг встроен «из коробки» — `/users/123/orders` уже отфильтрован по владельцу.

**Минусы вложенности:**
- Глубокая вложенность нечитаема: `/users/123/orders/456/items/789/refunds/...` — длинно и хрупко.
- Универсального предела в два уровня нет: оценивайте длину и устойчивость конкретного адреса.

**Рекомендация:** не переносите в путь всю цепочку владения автоматически. Оставляйте вложенность, если она объясняет контекст или скоупинг; самостоятельному ресурсу можно дать прямой адрес, а коллекции — фильтр.

<a id="q6"></a>

## Q6. Под-ресурсы или плоская структура с фильтром?

Это два способа выразить связь между сущностями. Выбор зависит от того, насколько сильно потомок «привязан» к родителю.

**Под-ресурсы** (вложенные) — связь жёсткая, потомок не существует без родителя:
```
GET /users/123/orders     # orders for this user
POST /users/123/orders    # create order для user
```

**Плоская структура** — сущность самостоятельна, родитель лишь один из её атрибутов:
```
GET /orders?user_id=123
POST /orders {"user_id": 123, ...}
```

**Как выбрать:**
- **Сильная принадлежность** (элемент имеет смысл только в контексте пользователя) → вложенные ресурсы.
- **Независимая** сущность → плоская структура с фильтром.

**Оба варианта могут сосуществовать.** Stripe предоставляет и `/customers/cus_123/charges`, и `/charges?customer=cus_123` — вложенный путь удобен для навигации, плоский — для общих выборок.

## Q7. Как проектировать массовые (bulk) операции?

Bulk-операция позволяет создать, обновить или удалить несколько ресурсов одним вызовом — это снижает число round-trip'ов и нагрузку, когда элементов много.

**Способы оформить запрос:**

**1. Передать массив:**
```http
POST /users/batch
[
  {"name": "Alice"},
  {"name": "Bob"}
]
```

**2. Обернуть в объект** (удобнее расширять метаданными):
```http
POST /users
{"users": [{"name": "Alice"}, ...]}
```

**3. Выделить под-ресурс действия:**
```http
POST /users/bulk-create
{"users": [...]}
```

**Ключевые решения, которые надо принять заранее:**
- **Атомарность** — всё-или-ничего (одна ошибка откатывает весь батч) или частичный успех (partial success, что прошло — сохраняется)? Это меняет и реализацию, и формат ответа.
- **Формат ответа** — при частичном успехе нужен массив результатов с индивидуальным статусом и ошибкой по каждому элементу, иначе клиент не поймёт, что именно не прошло.
- **Лимиты** — задайте максимум элементов на запрос, чтобы батч не вырос в неуправляемую транзакцию.

**Готового отраслевого стандарта на bulk почти нет.** Базовая спецификация JSON:API bulk-операций не описывает вовсе. Для нескольких операций в одном запросе у неё есть отдельное официальное расширение Atomic Operations, но оно по определению строго атомарно: либо применяются все операции, либо ни одна — поэлементного результата с частичным успехом там нет. Контракт с частичным успехом приходится описывать самому.

<a id="q8"></a>

## Q8. Как оформлять действия-глаголы, не укладывающиеся в CRUD?

Некоторые операции — «опубликовать статью», «заархивировать заказ» — это не создание/чтение/обновление/удаление, а переход состояния. Загнать их в чистый CRUD неестественно, поэтому есть несколько компромиссов.

**Варианты:**

**1. Действие как под-ресурс** (чаще всего):
```
POST /articles/123/publish
POST /orders/456/cancel
```

**2. Смена состояния через PATCH** — если действие сводится к смене поля статуса:
```
PATCH /orders/456
{"status": "cancelled"}
```

**3. Отдельный эндпоинт-действие:**
```
POST /actions/cancel-order
{"order_id": 456}
```

**Рекомендация:** под-ресурс (`POST /orders/456/cancel`) обычно ложится естественнее всего — он остаётся в рамках ресурса. Применяйте такие глаголы экономно, для редких случаев: если действий-эндпоинтов становится много, API скатывается в RPC-стиль и теряет преимущества REST.

## Q9. Чем различаются offset, page и keyset-пагинация?

Для коллекций, размер которых может расти, задают предел страницы и устойчивый порядок сортировки. Основные способы указать продолжение:

- **Offset/limit:** `GET /users?offset=20&limit=10` — пропустить 20 строк и взять 10.
- **Page/per_page:** `GET /users?page=3&per_page=10` — та же числовая позиция в виде номера страницы.
- **Keyset:** продолжить после последнего значения ключа сортировки. Если сортировка идёт по времени, добавьте уникальный ID для записей с одинаковой меткой: `?after_time=...&after_id=...`.

Непрозрачный `cursor` может кодировать keyset, offset или другое состояние сервера: сам формат токена не определяет алгоритм. Параметр `since` бывает фильтром диапазона либо границей страницы — это задаёт контракт. Максимальный размер страницы защищает сервер; конкретное число выбирают по данным и нагрузке.

<a id="q10"></a>

## Q10. Чем keyset-пагинация отличается от offset-пагинации?

**Offset** задаёт число пропущенных строк. Он прост и позволяет перейти к номеру страницы, но большой OFFSET может дорого обходиться в БД. Изменения данных между запросами способны сдвинуть границы страниц.

**Keyset** задаёт продолжение после последнего значения устойчивой сортировки, например пары `(created_at, id)`. При подходящем индексе сервер ищет следующую границу без пересчёта большого смещения. Этот способ удобен для длинных лент, но переход на произвольный номер страницы сложнее.

Keyset не даёт автоматической гарантии отсутствия пропусков или дублей при любых изменениях: нужны стабильный порядок, уникальный tie-breaker и согласованная фильтрация. Непрозрачный курсор сам по себе не доказывает, что внутри реализован keyset.

<a id="q11"></a>

## Q11. Как реализовать фильтрацию и сортировку?

И фильтры, и сортировка идут через query-параметры коллекции — это то, что уточняет выборку, не меняя адрес ресурса.

**Фильтрация** — каждый параметр сужает результат, несколько комбинируются по И:
```
GET /users?status=active
GET /users?created_after=2025-01-01
GET /users?role=admin&country=US
```

**Сортировка** — поле задаёт ключ, префикс `-` меняет направление, запятая задаёт несколько ключей по приоритету:
```
GET /users?sort=created_at         # ascending
GET /users?sort=-created_at         # descending (- prefix)
GET /users?sort=name,-created_at   # multiple fields
```

**Продвинутая фильтрация** (RSQL, OData) — когда нужны операторы сравнения и логика:
```
GET /users?filter=age=gt=18;status==active
```

**Рекомендация:**
- Простые фильтры — через query-параметры: их легко читать, кэшировать и логировать.
- Сложные фильтры (вложенная логика, длинные условия) выносите в `POST /search` с JSON-телом: query-строка для них слишком тесная и плохо читается.

<a id="q12"></a>

## Q12. Что такое выборка полей (sparse fieldsets)?

Это возможность клиента запросить только нужные поля ресурса, а не весь объект. Клиент перечисляет поля, сервер возвращает урезанный ответ.

```
GET /users/123?fields=id,name,email
```

**Ответ** содержит только запрошенное:
```json
{
  "id": 123,
  "name": "Alice",
  "email": "alice@example.com"
}
```

**Зачем:** меньше трафика и быстрее ответ — особенно для мобильных и других клиентов, чувствительных к ширине канала.

**В JSON:API для этого есть стандарт** (поля задаются по типу ресурса):
```
GET /users?fields[user]=name,email
```

**GraphQL** решает ту же задачу на уровне языка запросов: клиент всегда указывает нужные поля, отдельный механизм не требуется.

<a id="q13"></a>

## Q13. Каким должен быть формат ответа об ошибке?

Главное — **единый формат для всех ошибок API**. Если каждый эндпоинт возвращает ошибку по-своему, клиенту приходится писать разбор под каждый случай; общий контракт позволяет обрабатывать ошибки централизованно.

**Распространённый паттерн:**
```json
{
  "error": {
    "code": "INVALID_PARAMETER",
    "message": "The 'email' parameter is invalid",
    "details": {
      "field": "email",
      "reason": "Not a valid email address"
    },
    "documentation_url": "https://docs.example.com/errors/invalid-parameter"
  }
}
```

**Что должно быть в ошибке и зачем:**
- **HTTP-статус** (4xx — ошибка клиента, 5xx — сервера) — клиент сразу понимает класс проблемы.
- **Машиночитаемый код** (`INVALID_PARAMETER`) — по нему ветвится логика; в отличие от текста, он стабилен.
- **Человекочитаемое сообщение** (`message`) — для разработчика и логов.
- **`details`** — структурированные данные для программной обработки (какое поле, почему).
- **Ссылка на документацию** — куда идти за подробностями.
- **Request ID** — чтобы по обращению в поддержку найти конкретный запрос в логах.

**Никаких stack trace** в продакшен-ответах: они раскрывают внутреннее устройство и пути — это риск безопасности.

<a id="q14"></a>

## Q14. Что такое Problem Details (RFC 9457)?

Это стандартизированный формат тела ошибки от IETF. RFC 9457 задаёт смысл стандартных полей `type`, `title`, `status`, `detail` и `instance`, но не требует, чтобы все пять присутствовали в каждом ответе. Стандарт заменил RFC 7807.

```json
{
  "type": "https://example.com/probs/out-of-credit",
  "title": "You do not have enough credit.",
  "status": 403,
  "detail": "Your current balance is 30, but that costs 50.",
  "instance": "/account/12345/msgs/abc"
}
```

Поля по смыслу: `type` — URI типа ошибки (машиночитаемый идентификатор), `title` — краткое название, `status` — HTTP-код, `detail` — пояснение для конкретного случая, `instance` — URI этого конкретного происшествия.

**Content-Type:** `application/problem+json` — по нему клиент понимает, что тело в формате Problem Details.

**Spring Framework 6** даёт типы `ProblemDetail` и `ErrorResponse`, но сам по себе ничего не включает: там обработку подключают `@ControllerAdvice`, унаследованным от `ResponseEntityExceptionHandler`. **В Spring Boot 3** для этого есть свойство — `spring.mvc.problemdetails.enabled=true` (для WebFlux `spring.webflux.problemdetails.enabled=true`); без него приложение отдаёт обычное boot-тело ошибки. Собственные исключения удобно наследовать от `ErrorResponseException` — такие рендерятся в `application/problem+json` без ручного `@ExceptionHandler`.

Преимущество стандарта — общий инструментарий (клиенты, прокси, логи) умеет разбирать ошибки без кастомного кода. Учтите: все пять полей необязательны, а спецификация разрешает добавлять свои, поэтому клиент обязан переживать и отсутствие `instance`, и незнакомое поле.

<a id="q15"></a>

## Q15. Как вернуть все найденные ошибки полей формы за один ответ?

Если форма требует показать пользователю все независимые ошибки сразу, собирайте их в массив с указанием поля. Некоторые проверки зависят от предыдущих и не могут безопасно продолжаться после первой ошибки; политика валидации должна быть частью контракта.

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Request validation failed",
    "errors": [
      {"field": "email", "reason": "Invalid format"},
      {"field": "age", "reason": "Must be >= 18"},
      {"field": "country", "reason": "Required"}
    ]
  }
}
```

Каждый элемент массива `errors` привязан к конкретному полю — фронтенд легко покажет ошибку рядом с нужным input'ом.

**Статус:** 400 Bad Request или 422 Unprocessable Content; выберите и задокументируйте правило для ошибок валидации.

<a id="q16"></a>

## Q16. Как ключ идемпотентности помогает повторить POST после таймаута?

`POST` не обязан быть идемпотентным. После таймаута клиент может не знать, выполнил ли сервер операцию, поэтому повторяет запрос с тем же `Idempotency-Key`.

```http
POST /payments HTTP/1.1
Idempotency-Key: 7f9c1d-...
{"amount": 100}
```

Сервер атомарно связывает ключ с параметрами и состоянием операции. Повтор с тем же ключом не запускает тот же эффект снова: клиент получает сохранённый результат или согласованный статус ещё выполняющейся операции. Повтор ключа с другим телом нужно отклонять по контракту.

Срок хранения ключа задаёт API; после истечения окна прежний ключ может рассматриваться как новый. Для внешних побочных эффектов нужна согласованная запись результата и защита на стороне интеграции. Ключ снижает риск дубля в пределах этих условий, а не обещает глобальное exactly-once навсегда.

<a id="q17"></a>

## Q17. Как реализовать оптимистичную блокировку через ETag?

**ETag** — идентификатор текущей версии ресурса. При обновлении клиент присылает ETag, который он прочитал, в заголовке `If-Match`; сервер сравнивает его с актуальным и отклоняет запись, если ресурс уже успел измениться. Это и есть оптимистичная блокировка: конфликт не предотвращают локом, а обнаруживают в момент записи.

```http
# Read
GET /users/123
ETag: "abc123"

# Modify
PUT /users/123
If-Match: "abc123"
{...}

# If resource changed → 412 Precondition Failed
```

**Зачем:** предотвращает потерянные обновления (lost update), когда два клиента правят один ресурс и второй молча затирает изменения первого.

**Как это выглядит по шагам:**
- Клиент A читает (ETag `"abc123"`).
- Клиент B читает (тот же ETag `"abc123"`).
- Клиент A обновляет — успех, версия становится `"def456"`.
- Клиент B обновляет со старым `"abc123"` — `412 Precondition Failed`. Он понимает, что данные устарели, перечитывает и повторяет.

**Альтернатива:** хранить версию полем в теле (`{"version": 1, ...}`) и сверять её — та же идея без HTTP-заголовков.

<a id="q18"></a>

## Q18. Как различать API-ключ, JWT, OAuth 2.0 и OIDC?

API-ключ, JWT, OAuth 2.0 и OIDC относятся к разным слоям:

- **API-ключ** — учётные данные приложения или интеграции. Ограничьте права, предусмотрите ротацию и отзыв.
- **JWT** — формат токена с утверждениями. Формат сам по себе не определяет выдачу, срок сессии или отзыв; подпись зависит от способа применения.
- **OAuth 2.0** — протокол делегированного доступа; также определяет потоки для machine-to-machine, например Client Credentials.
- **OpenID Connect (OIDC)** — слой аутентификации пользователя поверх OAuth 2.0. Для входа может использовать Authorization Code flow.

Эти механизмы сочетаются: OIDC может выдать токен формата JWT. Для внутреннего service-to-service доступа рассматривают и mTLS. Выбор зависит от того, кто вызывает API, от имени кого действует и какие права нужно делегировать.

Подробнее — в [OAuth2](../security/oauth2-interview.md), [JWT](../security/jwt-interview.md).

<a id="q19"></a>

## Q19. Какие практики безопасности для API-ключей?

Каждый пункт закрывает конкретный риск — от утечки до невозможности отозвать скомпрометированный ключ.

1. **Префиксы в ключах** (`sk_live_`, `pk_test_`) — тип ключа виден с первого взгляда, в том числе при случайном попадании в логи.
2. **Длинные случайные** (32+ байт) — чтобы ключ нельзя было подобрать.
3. **Скоупированные права** (read-only, конкретные ресурсы) — утёкший ключ нанесёт меньше вреда.
4. **Отзываемые** — должна быть возможность мгновенно инвалидировать скомпрометированный ключ.
5. **Ротируемые** — обновление без простоя (старый и новый ключ какое-то время валидны).
6. **На каждое окружение** (test, live) — ключ из теста не должен открывать прод.
7. **Аудит-логирование** — кто и когда пользовался ключом, чтобы расследовать инциденты.
8. **Хеш в БД** — хранить хеш, а не сам ключ; утечка базы не раскроет ключи.
9. **Показывать один раз** — только при создании, дальше только хеш.
10. **Rate limiting на каждый ключ** — ограничивает ущерб от злоупотребления.

**Паттерн Stripe:** `sk_live_abc123...` — по префиксу сразу понятно secret/publishable и test/live, что снижает риск перепутать ключи.

## Q20. Какие заголовки используют для rate limiting?

Статус `429` и заголовок `Retry-After` определены RFC. Для публикации остатка квоты API используют разные поля; рабочая группа IETF разрабатывает общий формат `RateLimit` и `RateLimit-Policy`, который на дату редакции остаётся Internet-Draft. Конкретные имена и единицы узнавайте из документации сервиса.

### Что стандартизовано

Статус `429 Too Many Requests` определён RFC 6585, а заголовок `Retry-After` — RFC 9110 §10.2.3. У `Retry-After` две разрешённые формы: число секунд ожидания либо HTTP-дата.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

```http
HTTP/1.1 429 Too Many Requests
Retry-After: Wed, 12 Aug 2026 09:00:00 GMT
```

### Поля остатка квоты и проект стандарта

Единого RFC на них нет. Есть два семейства имён с разной судьбой.

**Вендорские `X-RateLimit-*`.** В стандартизацию не попадали, у каждого API свои соглашения — и по написанию, и по единицам:

| API | имена | что в `Reset` |
|---|---|---|
| GitHub | `x-ratelimit-limit`, `-remaining`, `-reset` | Unix-метка |
| Reddit | `x-ratelimit-remaining`, `-reset` | секунды до сброса |
| Discord | `x-ratelimit-reset` и отдельно `x-ratelimit-reset-after` | метка и дельта в разных полях |
| X (Twitter) | `x-rate-limit-*` — с дефисом после `rate` | Unix-метка |

Ответ в стиле GitHub (числа условные):

```http
HTTP/1.1 200 OK
x-ratelimit-limit: 5000
x-ratelimit-remaining: 4953
x-ratelimit-reset: 1786469137
```

Метка указывает на конец текущего окна, а окно отсчитывается от первого запроса в нём — не от круглого часа. Длина окна тоже не универсальна даже внутри одного API: у GitHub для REST это час, а для Search — минута.

Смысл полей везде схожий: `limit` — потолок за окно, `remaining` — сколько запросов осталось, `reset` — когда счётчик обнулится. А вот **в каких единицах записан `reset`, из имени заголовка не следует** — это и показывает таблица выше.

**Беспрефиксные `RateLimit-*`.** Пришли из черновика `draft-polli-ratelimit-headers`, который затем приняла рабочая группа IETF httpapi под именем `draft-ietf-httpapi-ratelimit-headers`. В ранних редакциях `RateLimit-Reset` — секунды до сброса:

```http
RateLimit-Limit: 100
RateLimit-Remaining: 47
RateLimit-Reset: 60
```

Черновик до сих пор не опубликован как RFC, а в его актуальной редакции эта тройка заменена на два поля — `RateLimit` и `RateLimit-Policy`, где публикуются и остаток, и параметры окна.

На собеседовании про эту часть корректно говорить «распространённая практика», а не «стандарт».

### Что должен делать клиент

- Следить за остатком квоты, не дожидаясь 429.
- Снижать темп (backoff) по мере приближения к лимиту.
- Прочитать в документации API, в каких единицах он отдаёт `reset`, и не выводить это из имени заголовка.
- После 429 — уважать `Retry-After` и не долбить сервер раньше срока.

<a id="q21"></a>

## Q21. Чем задержка запроса отличается от отказа 429 при превышении лимита?

При превышении лимита сервер может **задержать** запрос до появления квоты или быстро **отказать** с `429 Too Many Requests`. Это различие в поведении конкретного API; слова «throttling» и «rate limiting» команды используют по-разному.

Задержка сглаживает краткий всплеск, но число ожидающих запросов и время ожидания нужно ограничить. Отказ освобождает ресурсы сервера, а клиент может повторить запрос после `Retry-After`. Алгоритм подсчёта квоты — token bucket, sliding window или fixed window — выбирают отдельно от реакции на превышение.

Лимит считают на ключ, пользователя, IP или эндпоинт по выбранной политике. Эффект и справедливость проверяют на реальной нагрузке.

<a id="q22"></a>

## Q22. Что такое OpenAPI / Swagger и зачем они нужны?

**OpenAPI** (прежнее название спецификации — Swagger) — машиночитаемое описание HTTP API: операции, параметры, схемы запросов и ответов в YAML или JSON. Описание можно хранить в одном файле либо разбивать на связанные файлы.

```yaml
openapi: 3.0.0
info:
  title: My API
  version: 1.0
paths:
  /users/{id}:
    get:
      summary: Get user
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: User found
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/User'
```

Один файл-описание даёт сразу несколько артефактов:

**Инструменты:**
- **Swagger UI** — интерактивная документация, где можно сразу дёрнуть эндпоинт.
- **Redoc** — альтернативный UI для документации.
- **Кодогенераторы** — клиентские SDK прямо из спецификации.
- **Валидаторы** — проверка запросов/ответов на соответствие схеме.

**Рекомендация:** проектируйте **сначала спецификацию, потом реализацию** (design-first). OpenAPI становится единым источником истины: документация, SDK и валидация генерируются из него и не расходятся с кодом.

Подробнее — в [OpenAPI / Swagger](openapi-swagger-interview.md).

<a id="q23"></a>

## Q23. Зачем к API нужны примеры и SDK?

Документация спецификацией — необходимый минимум, но интеграцию сильно ускоряют готовые примеры и SDK: разработчик копирует рабочий код, а не разбирается со схемой с нуля.

**Что стоит предоставить:**
- **Примеры кода** на разных языках (curl, Python, JavaScript, Java, …) — их можно скопировать и запустить.
- **Коллекцию Postman** или экспорты Insomnia — чтобы попробовать API без написания кода.
- **SDK** для основных языков (автогенерация из OpenAPI).

**SDK снижают порог входа:** разработчику не нужно вручную писать HTTP-вызовы, сериализацию и обработку ошибок — всё уже в библиотеке.

**Инструменты автогенерации SDK:** OpenAPI Generator, Speakeasy, Stainless.

<a id="q24"></a>

## Q24. Почему API должен работать только по HTTPS?

**Всегда HTTPS, никакого HTTP в продакшене.** По открытому HTTP токены, ключи и данные идут в открытом виде — их перехватывают и подменяют (man-in-the-middle). TLS шифрует канал и подтверждает подлинность сервера.

```
HTTP/1.1 308 Permanent Redirect
Location: https://api.example.com/...
```

Тонкость: для API часто лучше **не редиректить** с HTTP на HTTPS, а отвечать 400/426. При редиректе клиент уже успел отправить секрет по незащищённому каналу — то есть он мог утечь ещё до перенаправления.

**Заголовок HSTS** заставляет браузер всегда ходить по HTTPS:
```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

**TLS 1.2 — минимум**, рекомендуется 1.3 (быстрее и без устаревших шифров).

<a id="q25"></a>

## Q25. Как сочетаются валидация входа, параметризация запросов и кодирование вывода?

Защита зависит от контекста использования данных. Валидация ограничивает допустимый ввод, параметризованный запрос отделяет данные от SQL, а кодирование при выводе в HTML не даёт строке стать разметкой или скриптом. Ни одна мера не заменяет остальные.

**Валидация входных данных:**
- Проверка по схеме (OpenAPI или JSON Schema).
- Проверка типов.
- Проверка диапазонов.
- Проверка формата (email, URL, UUID).
- Ограничения длины.
- Для SQL используйте параметры вместо конкатенации строки запроса; это отдельная мера от валидации.
- Санация имён файлов и путей из запроса — защита от path traversal. Проверять нужно до обращения к файлу: иначе `../` уведёт за пределы разрешённого каталога.

**Кодирование вывода:**
- Экранируйте HTML/JS, если ответ может попасть в HTML-рендеринг (защита от XSS).
- Кодируйте значения, которые подставляются в URL ответа, чтобы спецсимволы не ломали адрес.

Подробнее — в [Application Security](../security/application-security-interview.md).

## Q26. Что такое CORS и как его настраивать?

**Cross-Origin Resource Sharing** — механизм браузера, который ограничивает доступ скрипта с одного origin (схема+домен+порт) к ответу другого origin. Сервер заголовками объявляет, каким источникам разрешено читать ответ. Простой кросс-origin запрос может быть отправлен даже тогда, когда браузер не даст скрипту прочитать ответ; CORS не заменяет аутентификацию.

```http
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 3600
```

**Preflight-запрос OPTIONS** браузер шлёт перед «непростым» запросом, чтобы заранее узнать, разрешён ли метод и заголовки.

**Рекомендация:** для API, работающего с куками, перечисляйте точные origin. Со звёздочкой такой сценарий просто не заработает: при запросе с учётными данными (`credentials: include`) браузер требует, чтобы `Access-Control-Allow-Origin` точно совпадал с `Origin`, и ответ с `*` отвергает. Для API на `Authorization: Bearer` это ограничение не действует — там `*` допустим, и так живут многие публичные API.

**Важно про сам заголовок:** `Access-Control-Allow-Origin` несёт ровно одно значение — конкретный origin или `*`. Список через запятую браузеры не принимают, поэтому белый список держат на сервере и в ответ отдают тот origin, который совпал, добавляя `Vary: Origin`. Настоящая дыра — отражать пришедший `Origin` без проверки по списку, да ещё с `Access-Control-Allow-Credentials: true`: формально это не wildcard, а фактически доступ открыт любому сайту.

<a id="q27"></a>

## Q27. Какие HTTP-заголовки управляют кэшированием?

Кэширование экономит трафик и нагрузку двумя путями: `Cache-Control` говорит, сколько ответ можно хранить без перезапроса, а `ETag`/`Last-Modified` позволяют сделать условный запрос и получить пустой `304`, если данные не менялись.

```http
# Tell client/CDN how long к cache
Cache-Control: public, max-age=3600

# ETag для conditional requests
ETag: "abc123"

# Last modified
Last-Modified: Sat, 19 Apr 2025 14:30:00 GMT

# Conditional GET
GET /users/123
If-None-Match: "abc123"
# → 304 Not Modified (если unchanged)
```

Связка работает так: клиент сохраняет `ETag`, а при следующем запросе шлёт его в `If-None-Match`; если ресурс не изменился, сервер отвечает `304 Not Modified` без тела — данные берутся из кэша, канал не нагружается.

**Где кэшируется ответ (уровни):**
- Кэш браузера.
- CDN.
- API gateway.
- Кэш приложения (Redis).

**Когда применять:** для условно статичных данных — профиль пользователя, каталог товаров, которые меняются редко.

<a id="q28"></a>

## Q28. Как работает сжатие ответов (gzip, brotli)?

Сжатие тела ответа резко уменьшает объём передаваемых данных. Стороны договариваются о нём через заголовки: клиент сообщает, какие алгоритмы понимает, сервер выбирает один и помечает им ответ.

**Клиент сообщает, что умеет распаковывать:**
```http
Accept-Encoding: gzip, br
```

**Сервер указывает, чем сжал:**
```http
Content-Encoding: gzip
```

**Эффект:** для JSON и текста объём сокращается на 60–90% — они хорошо сжимаются из-за повторяющихся ключей и структуры.

**Brotli против gzip:** brotli сжимает плотнее, но требует чуть больше CPU.

**Включение:** сжатие не появляется само по себе — его нужно явно включить в конфигурации сервера, фреймворка или обратного прокси. По умолчанию оно чаще выключено, и без этого шага ответы уходят несжатыми, сколько бы алгоритмов клиент ни перечислил.

**Кэширование:** сжатый ответ обязан нести `Vary: Accept-Encoding`. Без этого заголовка общий кэш (CDN, прокси) отдаст сжатое тело клиенту, который такой алгоритм не заявлял, и тот получит нераспаковываемый мусор.

<a id="q29"></a>

## Q29. Нужен ли HATEOAS на практике?

Для большинства API — **нет**. HATEOAS (сервер возвращает в ответе ссылки на доступные действия, и клиент «ходит» по ним) — это вершина REST по Ричардсону, но на практике она редко окупает свою сложность.

Для простого CRUD API документированный стабильный контракт часто достаточен. OpenAPI описывает доступные операции, но не заменяет ссылки на действия, разрешённые конкретным состоянием ресурса.

**Где HATEOAS всё же полезен:**
- Workflow-API с конечным автоматом — сервер подсказывает, какие переходы доступны из текущего состояния.
- Самообнаруживающиеся гипермедиа-клиенты, которые не хотят зашивать URL.
- Строгое соответствие REST уровня 3 (требуется редко).

См. [REST Maturity](rest-maturity-interview.md).

<a id="q30"></a>

## Q30. Как проектировать вебхуки (webhooks)?

**Webhook** — обратный механизм: вместо того чтобы клиент опрашивал API, сервер сам шлёт HTTP-запрос с событием на URL, заданный клиентом. Это push вместо polling.

Поскольку доставка идёт по сети к чужому, не всегда надёжному получателю, дизайн должен закрывать подлинность, повторы и дубли:
- **Подписывайте payload** (HMAC) — получатель проверяет, что событие действительно от вас, а не подделка.
- **Повторяйте при сбоях** с экспоненциальным backoff — endpoint получателя может временно лежать.
- **Dead letter** после исчерпания попыток — чтобы недоставленные события не терялись.
- **Идемпотентность** — из-за повторов одно событие может прийти дважды; получатель должен это переживать (например, по `event_id`).
- **Типы событий** (`order.created`, `order.cancelled`) — получатель подписывается только на нужные.
- **Версионированные payload**, закреплённые за клиентом — смена схемы не ломает существующих подписчиков.
- **API управления вебхуками** (subscribe, unsubscribe, list).
- **Документация** с примерами payload.
- **Инструменты тестирования** (webhook tester, ngrok) — чтобы отлаживать локально.

**Вебхуки Stripe** — эталонный пример, на их дизайн стоит ориентироваться.
