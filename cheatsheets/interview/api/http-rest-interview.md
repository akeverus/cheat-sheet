## Как отвечать про HTTP/REST (короткий шаблон)

На интервью обычно ждут один и тот же каркас: сначала вы задаете контекст, то есть тип API, профиль нагрузки, SLA/SLO и требования безопасности, затем объясняете семантику решения через методы, статусы и контракт, после этого проговариваете trade-off и возможные альтернативы вроде `GraphQL`, `WebSocket`, `gRPC` или `SOAP`, и в конце показываете, как решение валидируется через тесты, метрики и наблюдаемость.

## Q1. Как коротко объяснить REST и его ограничения?

`REST` — это архитектурный стиль для сетевых систем: ресурсная модель, единый интерфейс `HTTP`, stateless-взаимодействие, кэширование и самоописательные сообщения.  
Ключевая идея: клиент работает с **ресурсами**, а не с RPC-методами.

Ограничения тоже важно проговорить явно: `REST` неудобен для сложных графов данных из-за over/under-fetching, не оптимален для двунаправленного real-time обмена и хуже подходит для длинных stateful workflow с явным протоколом состояния. Сильный ответ звучит не как "REST всегда лучший", а как "REST хорош как базовый стиль, пока требования не уводят в другой протокол".

## Q2. Что такое ресурс и как проектировать URI?

Ресурс — это адресуемая бизнес-сущность (`/users`, `/orders/{orderId}`), а не операция (`/createUser`).  
`URI` должен описывать **что это**, а не **что сделать**.

Базовые правила такие: используем существительные и множественное число для коллекций, строим иерархию только когда есть реальная вложенность вроде `/orders/{id}/items`, держим `URI` стабильными и развиваем API через версионирование и контракт, а фильтрацию, сортировку и пагинацию выносим в query-параметры. Антипаттерн здесь один и тот же: "глагольные" endpoint-ы вроде `/approveOrder` для обычных CRUD-сценариев.

## Q3. Как правильно выбирать HTTP-методы?

Метод выбирают по семантике операции, а не по удобству клиента: `GET` остается методом чтения без изменения состояния, `POST` подходит для создания подчиненного ресурса или неидемпотентной команды, `PUT` означает полную замену состояния ресурса, `PATCH` применяется для частичного изменения, а `DELETE` — для удаления. Практический критерий простой: если повтор запроса после network timeout меняет итог непредсказуемо, то метод или контракт, скорее всего, выбраны неверно.

## Q4. В чем разница между безопасностью и идемпотентностью методов?

`Safe` означает, что запрос не должен менять состояние сервера, поэтому сюда относятся `GET`, `HEAD` и `OPTIONS`. `Idempotent` означает другое: повтор одинакового запроса приводит к тому же итоговому состоянию, как у `PUT` и `DELETE`, а также safe-методов. Эти свойства не совпадают автоматически: запрос может быть idempotent, но не safe, как `DELETE`, и может быть одновременно safe и idempotent, как `GET`. Ключевой момент в том, что идемпотентность задается не названием метода, а реальной реализацией, включая retry и дедупликацию команд.

## Q5. В чем реальная разница между PUT, PATCH и POST?

`PUT` используют, когда клиент передает полное представление ресурса и заменяет им текущее состояние. `PATCH` применяют для передачи только изменений и частичного обновления. `POST` подходит для создания ресурса в коллекции или для командной операции с побочным эффектом. На практике `PUT` проще поддерживать для идемпотентных retry, `PATCH` экономит трафик, но усложняет валидацию конфликтов, а `POST` опасно превращать в универсальный метод, потому что теряется предсказуемость контракта.

## Q6. Как выбирать HTTP status code без хаоса?

Нужна короткая и стабильная политика, где `2xx` покрывает успешные операции, `4xx` указывает на ошибки клиента, а `5xx` сигнализирует о сбоях сервера. В реальном проекте важно не количество кодов, а консистентность: один и тот же тип ошибки всегда должен маппиться в один и тот же status code и error code. Самый вредный антипаттерн — возвращать `200 OK` и прятать ошибку в теле ответа.

## Q7. Как должен выглядеть хороший error response?

Хороший error response одновременно полезен машине и человеку: он содержит стабильный машинный `code`, короткий человекочитаемый `message`, структурированные `details` для валидации и доменных нарушений, `traceId` или `requestId` для связи с логами и трейсингом, и всегда сопровождается корректным HTTP-статусом. Для production-контуров обязательно исключают утечку внутренних деталей вроде `stacktrace`, SQL-текста и внутренних имен сервисов.

## Q8. Зачем API-контракт и как его поддерживать?

Контракт в формате `OpenAPI` — это источник истины о поведении API, который синхронизирует backend, frontend и внешних интеграторов, упрощает генерацию SDK и документации, а также делает contract testing и релизы безопаснее. Рабочая модель обычно выглядит так: изменения контракта проходят review, CI проверяет схему и backward compatibility, а breaking changes выпускают через версионирование и заранее оговоренный миграционный период.

## Q9. Когда REST лучше SOAP, а когда наоборот?

`REST` обычно лучше, когда важны простая интеграция, скорость разработки и web/mobile-экосистема.  
`SOAP` разумен, когда требуется строгий формальный контракт, enterprise governance и специфичные WS-* требования.

Критерий выбора упирается в контекст. Если нужен легкий публичный API с быстрой интеграцией, чаще выбирают `REST`. Если критичны формальные enterprise-процессы, интеграции с legacy и жесткий governance, часто уместнее `SOAP`. Сильный ответ здесь всегда привязан к требованиям, ограничениям и стоимости сопровождения.

## Q10. Когда REST хуже GraphQL/WebSocket?

`GraphQL` обычно выигрывает в сложных read-сценариях, когда клиентам нужен гибкий выбор полей, а `WebSocket` лучше подходит для событий в реальном времени и двунаправленного обмена. При этом `REST` остается оптимальным вариантом для большинства CRUD и командных API с понятной ресурсной моделью. Зрелый trade-off здесь в том, чтобы не заменять `REST` везде, а комбинировать протоколы по типу нагрузки.

## Q11. Что делает REST API масштабируемым на практике?

Масштабируемость в `REST` не сводится к horizontal scaling. Она строится на stateless-обработке без server session affinity, корректном кэшировании через `Cache-Control`, `ETag` и conditional requests, разумной пагинации и фильтрации вместо попытки "отдать все", а также на идемпотентных retry с контролем timeout/retry budget. На границе системы обязательно нужны rate limiting, quotas и backpressure. Эксплуатационная часть не менее важна: метрики `RPS`, error rate и latency p95/p99, трассировка и SLO-алерты.

## Q12. Как защищать REST API в production?

Минимальный production baseline начинается с `TLS` на всех участках и запрета слабых cipher/protocol версий, продолжается корректной authN/authZ-моделью на базе `OAuth2`, JWT/introspection или mTLS по контексту, затем требует least privilege, короткоживущих токенов, строгой server-side валидации входа и безопасной обработки данных. Отдельно важны секреты в `vault` или `secret manager`, ротация ключей и аудит доступа. Зрелый подход отличается тем, что безопасность встроена в SDLC через threat modeling, SAST/DAST, regression-проверки и incident runbooks.

## Q13. Какие anti-patterns в безопасности API встречаются чаще всего?

Чаще всего встречаются долгоживущие токены без rotation/revocation, слишком широкие scopes и roles, отсутствие `429` и защиты от abuse, утечки персональных данных и токенов в логах, доверие клиентскому input без server-side валидации и чрезмерно "разговорчивые" ошибки, которые раскрывают внутреннюю архитектуру. На интервью сильнее звучит не просто список проблем, а связка "риск плюс конкретная контрмера".

## Q14. Как тестировать REST API системно?

Системное тестирование REST API строится как пирамида: unit-тесты покрывают бизнес-правила и валидацию, contract tests проверяют API-границу, integration tests валидируют связки с БД, брокерами и внешними сервисами, а e2e/smoke контролируют критические пользовательские потоки. Дополняют это нагрузочные и стресс-тесты для `latency`, saturation и деградации, security tests для auth bypass и injection, а также resilience-тесты для timeout, retry storm и partial outage. Критерий зрелости в том, что тесты привязаны к SLO и к реальным рискам инцидентов, а не только к happy path.

## Q15. Как отвечать на HTTP/REST вопросы сильно на senior-раунде?

Рабочий шаблон senior-ответа звучит как короткая история: сначала вы обозначаете контекст, например публичный API с нагрузкой 6k RPS и p99 ниже 250 ms в multi-tenant среде, затем объясняете решение через resource-oriented endpoints, единую error model и `OpenAPI` с contract tests в CI, после этого честно проговариваете trade-off, например почему для real-time событий оставили `WebSocket`, а для чтения справочников выбрали `REST` с кэшированием, и завершаете измеримым результатом вроде снижения интеграционных дефектов, MTTR и стабилизации p99. Сильный senior-ответ всегда сочетает корректную семантику `HTTP`, осознанные trade-offs и операционно проверяемый эффект.
