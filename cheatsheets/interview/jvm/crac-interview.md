# Вопросы на собеседовании: `CRaC`

`CRaC` (Coordinated Restore at Checkpoint) — проект OpenJDK и API, который решает главную боль JVM в облаке: медленный холодный старт. Идея — сделать снимок (checkpoint) уже прогретого, проинициализированного процесса JVM и потом мгновенно восстанавливать (restore) его из этого снимка за десятки миллисекунд.

`CRaC` особенно важен для serverless и автоскейлинга, где время старта напрямую влияет на стоимость и латентность. На нём построен, в частности, `AWS Lambda SnapStart` для Java.

## Q1. (!) Что такое CRaC и какую проблему он решает?

`CRaC` (Coordinated Restore at Checkpoint) — это API и реализация в OpenJDK, позволяющие сохранить состояние работающего процесса JVM в снимок на диске (**checkpoint**) и затем восстановить процесс из этого снимка (**restore**).

Решаемая проблема — **медленный старт JVM**. Запуск Java-приложения включает:

- инициализацию самой JVM и загрузку классов;
- инициализацию фреймворка (`Spring`-контекст, пулы соединений, кэши);
- прогрев `JIT` до пиковой производительности.

В долгоживущем сервисе это не страшно — старт амортизируется за месяцы аптайма. Но в serverless и автоскейлинге, где инстансы создаются и убиваются постоянно, секунды старта становятся прямой стоимостью и латентностью.

`CRaC` делает снимок процесса, который уже прошёл всю инициализацию и прогрет, и восстанавливает его за десятки миллисекунд — вместо нескольких секунд холодного старта.

**Итог:** `CRaC` превращает дорогой старт JVM в дешёвое восстановление из снимка. Это не про скорость работы кода, а про скорость выхода на готовность.

## Q2. (!) Как CRaC связан с холодным стартом и JIT-прогревом?

Холодный старт — это не только инициализация, но и **прогрев `JIT`**. Сразу после запуска JVM исполняет байткод в интерпретаторе; «горячие» методы компилируются в нативный код только после тысяч вызовов. До этого приложение работает в разы медленнее пиковой производительности.

`CRaC` бьёт по обеим частям сразу: снимок снимают с **уже прогретого** процесса. После restore приложение получает не только готовый контекст, но и накопленные `JIT`-оптимизации — пиковая производительность доступна почти сразу.

```mermaid
graph LR
    A[Старт JVM] --> B[Инициализация]
    B --> C[Прогрев JIT]
    C --> D[Пиковая производительность]
    C -.checkpoint.-> E[Снимок на диске]
    E -.restore ~десятки мс.-> D
```

**Итог:** обычный старт = инициализация + прогрев (секунды). `CRaC`-restore пропускает оба этапа — отсюда выигрыш не только во времени готовности, но и в производительности первых запросов.

## Q3. (!) Как технически работает checkpoint/restore?

На Linux `CRaC` опирается на **`CRIU`** (Checkpoint/Restore In Userspace) — механизм, который умеет «заморозить» процесс и сохранить его полное состояние: память, потоки, открытые дескрипторы.

1. **Checkpoint.** Приложение получает сигнал подготовиться (см. Resource API, Q5). После этого `CRIU` сериализует образ процесса (страницы памяти, состояние потоков) на диск.
2. **Restore.** `CRIU` воссоздаёт процесс из образа: восстанавливает память и потоки, после чего приложение получает сигнал «довосстановить» внешние ресурсы.

Поскольку восстанавливается уже существующая память (а не строится заново), это на порядки быстрее полной инициализации.

**Итог:** `CRaC` = `CRIU` (системный механизм снимка процесса) + JVM-координация (чтобы приложение корректно закрыло и заново открыло внешние ресурсы вокруг снимка).

## Q4. Как сделать checkpoint и restore на практике?

Нужен JDK со сборкой `CRaC` (например, `Azul Zulu` с поддержкой CRaC или `Liberica` NIK). Базовый сценарий:

```bash
# 1. Запускаем приложение, указывая, куда положить снимок
java -XX:CRaCCheckpointTo=/app/checkpoint -jar app.jar

# 2. Когда приложение прогрето — делаем checkpoint извне
jcmd app.jar JDK.checkpoint
# процесс завершается, снимок лежит в /app/checkpoint

# 3. Восстанавливаем из снимка
java -XX:CRaCRestoreFrom=/app/checkpoint
```

В CI/CD снимок обычно делают на этапе сборки образа: прогрели приложение синтетическими запросами, сняли checkpoint, упаковали снимок в Docker-образ. В рантайме контейнер стартует сразу из restore.

**Итог:** ключевые флаги — `-XX:CRaCCheckpointTo` (куда писать) и `-XX:CRaCRestoreFrom` (откуда читать); сам checkpoint инициируется командой `jcmd ... JDK.checkpoint` или программно.

## Q5. (!) Что такое Resource API и коллбэки beforeCheckpoint/afterRestore?

Не всё состояние можно «заморозить»: открытый сокет или файловый дескриптор после restore станет невалидным. Чтобы приложение управляло этим, есть интерфейс `jdk.crac.Resource` с двумя коллбэками.

```java
import jdk.crac.*;

public class DbConnectionResource implements Resource {
    public DbConnectionResource() {
        Core.getGlobalContext().register(this); // подписываемся на события
    }

    @Override
    public void beforeCheckpoint(Context<? extends Resource> ctx) {
        // перед снимком: закрыть соединения, остановить пулы
        connectionPool.close();
    }

    @Override
    public void afterRestore(Context<? extends Resource> ctx) {
        // после восстановления: заново открыть ресурсы
        connectionPool.reopen();
    }
}
```

- **`beforeCheckpoint`** вызывается перед снятием снимка — здесь закрывают то, что нельзя «заморозить».
- **`afterRestore`** вызывается сразу после восстановления — здесь заново открывают ресурсы (часто уже в новом окружении: другой IP, другие секреты).

**Итог:** Resource API — это контракт между приложением и `CRaC`. Любой внешний ресурс (пулы БД, HTTP-клиенты, таймеры) должен корректно закрываться в `beforeCheckpoint` и переоткрываться в `afterRestore`.

## Q6. Почему restore называется «coordinated»?

«Coordinated» (координированный) — потому что снимок снимается не «насильно» в произвольный момент, а **в согласии с приложением**. Перед checkpoint JVM проходит по всем зарегистрированным `Resource` и вызывает `beforeCheckpoint`, давая каждому шанс привести себя в «снимаемое» состояние. После restore — симметрично вызывает `afterRestore`.

Это принципиальное отличие от «слепого» снимка процесса средствами ОС: без координации в снимок попали бы открытые сокеты, протухшие соединения и устаревшие данные (например, закэшированное время), и приложение после restore вело бы себя некорректно.

**Итог:** координация = приложение участвует в процессе снимка. Именно это делает `CRaC` пригодным для реальных сервисов, а не только для stateless-вычислений.

## Q7. (!) Какое состояние ломается при checkpoint/restore?

Опасно всё, что завязано на внешний мир или на момент времени снимка:

- **Сетевые соединения** — открытые сокеты, пулы соединений к БД, HTTP keep-alive. После restore они «протухли».
- **Файловые дескрипторы** — открытые файлы, временные файлы, блокировки.
- **Закэшированное время** — `System.currentTimeMillis()`, сохранённое до снимка, после restore устарело; таймеры и расписания нужно пересчитать.
- **Случайность и секреты** — `SecureRandom`-состояние и одноразовые секреты, «зашитые» в память, могут повторно использоваться (риск, см. Q8).
- **Переменные окружения** — снимок снят в одном окружении, restore — в другом; конфигурацию часто нужно перечитать в `afterRestore`.

```java
@Override
public void afterRestore(Context<? extends Resource> ctx) {
    this.startTime = System.currentTimeMillis(); // пересчитать время
    this.config = reloadFromEnvironment();        // перечитать окружение
}
```

**Итог:** проверяйте всё, что «помнит» внешний мир или время. Хорошие фреймворки (`Spring`) обрабатывают типовые ресурсы автоматически, но кастомные пулы и таймеры — ваша ответственность.

## Q8. (!) Какие риски безопасности у снимка процесса?

Снимок — это полный дамп памяти процесса на диск. Если в памяти были секреты (пароли БД, токены, ключи шифрования, содержимое `SecureRandom`), они **физически лежат в файле снимка**.

Риски:

- **Утечка через снимок** — файл checkpoint содержит секреты в открытом виде; если он попал в Docker-образ или в незащищённое хранилище, секреты скомпрометированы.
- **Повторное использование случайности** — состояние `SecureRandom`/`SSLContext`, восстановленное из снимка, может выдавать предсказуемые значения; криптопримитивы нужно ре-инициализировать в `afterRestore`.
- **Утечка сессионных данных** — если снимок сняли после реальных запросов, в памяти могут остаться чужие данные.

Меры: не класть секреты в память до checkpoint (подгружать в `afterRestore`), хранить файл снимка в защищённом месте, ре-сеять `SecureRandom` после restore, снимать checkpoint на «чистом» прогреве без реальных пользовательских данных.

**Итог:** относитесь к файлу снимка как к дампу памяти с секретами. Это главный аргумент против бездумного `CRaC` — безопасность снимка нужно проектировать.

## Q9. (!) Как Spring Boot поддерживает CRaC?

`Spring Framework 6.1+` / `Spring Boot 3.2+` имеют встроенную поддержку `CRaC`. Если в classpath есть зависимость `org.crac:crac`, Spring сам регистрирует `Lifecycle`-бины как `CRaC`-ресурсы: перед checkpoint он останавливает (`stop()`) бины со `SmartLifecycle`/`Lifecycle` (пулы, listener-контейнеры, веб-сервер), а после restore — запускает заново (`start()`).

Это значит, что для большинства приложений не нужно вручную реализовывать `Resource` — Spring закрывает и переоткрывает соединения, веб-сервер и брокерные подписки за вас.

```mermaid
graph LR
    A[checkpoint signal] --> B[Spring: stop Lifecycle beans]
    B --> C[CRIU snapshot]
    C --> D[restore]
    D --> E[Spring: start Lifecycle beans]
```

**Итог:** на `Spring Boot 3.2+` `CRaC` работает почти «из коробки» — добавили зависимость `org.crac`, и фреймворк сам координирует жизненный цикл бинов вокруг снимка.

## Q10. Чем automatic checkpoint отличается от on-demand?

Spring поддерживает два режима снятия checkpoint.

| Режим | Как включается | Когда снимается checkpoint |
|-------|----------------|----------------------------|
| Automatic (on refresh) | `-Dspring.context.checkpoint=onRefresh` | автоматически после инициализации контекста, на этапе старта |
| On-demand | без флага, внешне через `jcmd ... JDK.checkpoint` | в произвольный момент, когда приложение прогрето |

- **Automatic (`onRefresh`)** удобен для сборки образа: контекст поднялся → сразу снимок. Но снимок снят до прогрева `JIT` и до открытия веб-порта (соединения ещё не приняты).
- **On-demand** даёт больше контроля: можно прогреть приложение синтетической нагрузкой, и только потом снять checkpoint с уже оптимизированным `JIT`.

**Итог:** `onRefresh` проще и хорош для быстрого старта; on-demand с предварительным прогревом даёт лучшую производительность первых запросов ценой более сложного пайплайна.

## Q11. Как бины реагируют на checkpoint и restore?

Spring отображает события `CRaC` на `Lifecycle`-контракт:

- Бины, реализующие `SmartLifecycle`, получают `stop(Runnable)` перед checkpoint и `start()` после restore.
- Для тонкого контроля можно реализовать `org.springframework.context.Lifecycle` или напрямую `jdk.crac.Resource`.
- Порядок остановки/запуска управляется через `getPhase()` (как и при обычном shutdown/startup) — ресурсы останавливаются в обратном порядке относительно запуска.

```java
@Component
public class CacheWarmer implements SmartLifecycle {
    public void start() { warmUpCache(); }   // вызовется и при старте, и при afterRestore
    public void stop()  { clearVolatile(); } // вызовется перед checkpoint
    public boolean isRunning() { return running; }
}
```

**Итог:** если ваш бин уже корректно реализует `Lifecycle`/`SmartLifecycle` для обычного старта/останова, он, скорее всего, корректно отработает и `CRaC` — это тот же контракт.

## Q12. (!) CRaC vs GraalVM Native Image — что выбрать?

Оба ускоряют старт, но разными путями и с разными компромиссами.

| Критерий | `CRaC` | `GraalVM Native Image` |
|----------|--------|------------------------|
| Подход | снимок прогретой JVM | AOT-компиляция в нативный бинарь |
| Время старта | десятки мс | десятки мс |
| Пиковая производительность | как у обычной JVM (полный `JIT`) | обычно ниже (нет рантайм-`JIT`) |
| Потребление памяти | как у JVM | существенно ниже |
| Размер артефакта | образ + снимок памяти | компактный бинарь |
| Reflection/dynamic | работает как обычно | требует конфигурации (`reachability metadata`) |
| Платформа | Linux (через `CRIU`) | кроссплатформенно |
| Сложность сборки | прогрев + checkpoint в пайплайне | AOT-сборка, ограничения на динамику |

- **`CRaC`** сохраняет полноценную JVM — пиковая производительность и совместимость с reflection/динамикой не страдают. Цена — Linux-only, большой снимок, безопасность снимка.
- **`Native Image`** даёт минимальную память и компактный бинарь, но «замораживает» динамику на этапе сборки и обычно проигрывает в пиковой пропускной способности.

**Итог:** нужен быстрый старт + пиковая производительность + динамика без переписывания → `CRaC`. Нужны минимальная память и компактный бинарь, готовы платить настройкой reflection → `Native Image`.

## Q13. Как связаны CRaC и AWS Lambda SnapStart?

`AWS Lambda SnapStart` для Java — это, по сути, управляемая облаком реализация той же идеи checkpoint/restore. AWS снимает снимок инициализированной функции на этапе публикации версии и при холодном старте восстанавливает из снимка вместо полной инициализации.

Связь:

- Концептуально SnapStart = checkpoint/restore (как `CRaC`); ранние версии и Java-рантаймы используют схожие механизмы (Firecracker MicroVM-снимки).
- В современных рантаймах появились **runtime hooks** (`CRaC`-совместимые `beforeCheckpoint`/`afterRestore`), чтобы функция корректно пересоздавала соединения и секреты после restore.
- Те же риски: устаревшие соединения, повторное использование `SecureRandom` (AWS специально предупреждает про уникальность случайности после restore).

**Итог:** SnapStart — это «CRaC как сервис» от AWS: вам не надо управлять `CRIU`, но та же дисциплина (переоткрытие ресурсов, ре-сев случайности в hooks) обязательна.

## Q14. (!) Какие ограничения и требования у CRaC?

- **Платформа.** Реализация опирается на `CRIU`, поэтому checkpoint/restore работает на **Linux**. Под Windows/macOS — только через Linux-контейнер/VM.
- **Специальный JDK.** Нужен дистрибутив с поддержкой `CRaC` (`Azul Zulu` CRaC-сборки, `BellSoft Liberica`), обычный OpenJDK не подойдёт.
- **Привилегии.** `CRIU` требует определённых Linux-capabilities (например, для работы с пространствами имён процессов) — в контейнерах это нужно настраивать.
- **Координация ресурсов.** Любой кастомный внешний ресурс должен корректно реализовать `Resource` (или быть `Lifecycle`-бином в Spring), иначе после restore — невалидные дескрипторы.
- **Безопасность снимка.** Файл снимка содержит память с секретами — нужна защита (см. Q8).
- **Идентичность окружения.** Restore лучше выполнять в окружении, совместимом с тем, где снят checkpoint (та же архитектура, совместимое ядро).

**Итог:** `CRaC` мощный, но не бесплатный: Linux + специальный JDK + дисциплина по ресурсам и безопасности. Это осознанный инфраструктурный выбор, а не «флаг включил и забыл».

## Q15. В каких сценариях CRaC даёт наибольший выигрыш?

- **Serverless / FaaS** — где холодный старт напрямую бьёт по латентности и стоимости (основной кейс, ср. SnapStart).
- **Автоскейлинг** — когда поды/инстансы поднимаются под всплеск нагрузки и должны быть готовы за миллисекунды, а не секунды.
- **Частые деплои / rolling restart** — быстрый ввод инстанса в строй сокращает окно деградации.
- **Тяжёлые на старте приложения** — большой `Spring`-контекст, много автоконфигураций, прогрев кэшей: чем дольше обычный старт, тем больше выигрыш от restore.

Где выигрыш мал: долгоживущие монолиты с редкими рестартами — там старт амортизируется, и сложность `CRaC` не окупается.

**Итог:** `CRaC` окупается там, где старт происходит часто и его время критично. Для «запустил и работает годами» он избыточен.

## Q16. Как тестировать и эксплуатировать CRaC в проде?

**Тестирование:**

- Проверяйте, что после restore все соединения валидны: интеграционный тест, который делает checkpoint, restore и затем реальный запрос к БД/внешнему API.
- Тестируйте на **Linux-окружении**, идентичном проду (контейнер с CRaC-JDK), — локальная macOS не покажет реальное поведение.
- Отдельно проверяйте корректность `afterRestore`: переоткрытие пулов, пересчёт времени, ре-сев `SecureRandom`.

**Эксплуатация:**

- Снимайте checkpoint в CI/CD на этапе сборки образа после прогрева, а не в рантайме.
- Защищайте файл снимка (он содержит память с секретами) и/или подгружайте секреты только в `afterRestore`.
- Мониторьте время restore и долю «первых» запросов с деградацией — если `afterRestore` тяжёлый, выигрыш от снимка частично теряется.

**Итог:** относитесь к restore как к особому виду старта со своими инвариантами. Главные проверки — валидность внешних ресурсов и безопасность снимка; всё это нужно гонять в Linux-окружении, идентичном проду.
