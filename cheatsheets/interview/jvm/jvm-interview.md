## Q1. (!) Что такое `JVM` и зачем она нужна?

**`JVM`** (`Java Virtual Machine`) — виртуальная машина, которая выполняет `Java`-байткод. Она работает как прослойка между скомпилированной программой и операционной системой: код пишут под `JVM`, а уже `JVM` переводит его в инструкции конкретного процессора и ОС. Отсюда главный принцип — **Write Once, Run Anywhere**: один и тот же `.class`-файл запускается на любой платформе, где есть `JVM`, без перекомпиляции.

Что `JVM` делает за разработчика:
- **Загрузка классов** — `ClassLoader` находит и подгружает `.class`-файлы по мере необходимости, лениво
- **Верификация байткода** — проверяет, что байткод корректен и безопасен (нет переполнения стека операндов, некорректных переходов), прежде чем его выполнить
- **Исполнение** — сначала интерпретирует байткод, а «горячие» участки `JIT`-компилирует в нативный код
- **Управление памятью** — сама выделяет память под объекты и освобождает её через `GC`; ручного `free`, как в C, нет
- **Управление потоками** — отображает `Java`-потоки на потоки ОС и синхронизацию

Полный конвейер от исходника до исполнения:

- `Java Source` (`.java`) → компилятор `javac` → `Bytecode` (`.class`)
- `Bytecode` поступает в `JVM`, где проходит три стадии:
  - `ClassLoader` → **Загрузка**
  - `Verifier` → **Верификация**
  - `Interpreter` / `JIT` → **Исполнение**

**Ключевой акцент для собеседования:** `JVM` — это **спецификация** (документ, описывающий поведение), а `HotSpot`, `OpenJ9`, `GraalVM` — её конкретные **реализации**. Поэтому «JVM от Oracle» и «JVM от IBM» ведут себя одинаково по контракту, но различаются деталями GC и JIT.

## Q2. (!) Из каких компонентов состоит `JVM`?

`JVM` состоит из трёх крупных блоков: **`ClassLoader Subsystem`** (загружает классы), **`Runtime Data Areas`** (области памяти, где живут классы, объекты и стеки) и **`Execution Engine`** (исполняет байткод — интерпретатор + `JIT` + `GC`). Связывает их с нативным миром **`JNI`** (`Native Interface`).

Структура `Java Virtual Machine` по блокам:

- **`ClassLoader Subsystem`** — подсистема загрузки классов
- **`Runtime Data Areas`** (области памяти):
  - `Method Area` / `Metaspace`
  - `Heap`
  - `Stack` (per thread)
  - `PC Register` (per thread)
  - `Native Method Stack`
- **`Execution Engine`**:
  - `Interpreter`
  - `JIT Compiler` (`C1` + `C2`)
  - `Garbage Collector`
- **`Native Interface (JNI)`** — мост к нативному коду

Поток данных между блоками: `ClassLoader Subsystem` → `Runtime Data Areas` → `Execution Engine` → `Native Interface (JNI)`.

| Компонент | Назначение |
|-----------|-----------|
| `ClassLoader` | Загрузка, линковка и инициализация классов |
| `Method Area` / `Metaspace` | Метаданные классов, таблицы методов, `constant pool` |
| `Heap` | Хранение всех объектов; область работы `GC` |
| `Stack` | Фреймы вызовов: локальные переменные, операнды, адреса возврата |
| `PC Register` | Адрес текущей выполняемой инструкции для каждого потока |
| `Interpreter` | Построчное выполнение байткода |
| `JIT Compiler` | Компиляция «горячих» методов в нативный код |
| `GC` | Автоматическое освобождение памяти от недостижимых объектов |

Логика потока данных: классы загружаются (`ClassLoader`) → их метаданные и объекты ложатся в области памяти (`Runtime Data Areas`) → байткод исполняется (`Execution Engine`) → при необходимости вызывается нативный код через `JNI`.

## Q3. Что такое байткод и как `JVM` его выполняет?

**Байткод** — промежуточное представление программы в виде инструкций для `JVM` (не для процессора). Компилятор `javac` переводит исходный код `.java` в файлы `.class`, а уже `JVM` исполняет эти инструкции. Именно этот промежуточный слой делает Java платформонезависимой: байткод одинаков на всех ОС, а в нативный код его транслирует конкретная `JVM`.

Байткод — **стековый**: операнды кладутся на стек операндов, инструкция их забирает и кладёт результат обратно. В примере ниже `iload_1`/`iload_2` загружают аргументы на стек, `iadd` складывает, `ireturn` возвращает результат:

```java
// Исходный код
public int add(int a, int b) {
    return a + b;
}

// Байткод (вывод javap -c):
// 0: iload_1
// 1: iload_2
// 2: iadd
// 3: ireturn
```

Просмотр байткода:

```java
// Команда для дизассемблирования
// javap -c -p MyClass.class
// javap -v MyClass.class  — подробный вывод с constant pool
```

Полный путь исполнения: `ClassLoader` загружает байткод → `Verifier` проверяет его корректность → `Interpreter` начинает выполнять инструкции построчно → `JIT` дожидается, пока метод станет «горячим» (по счётчику вызовов, обычно ~10 000 для `C2`), и компилирует его в нативный код. Поэтому первые вызовы метода медленнее последующих — это и есть эффект «прогрева» (warm-up).

## Q4. Чем отличаются `JVM`, `JRE` и `JDK`?

Это три вложенных уровня: `JDK` ⊃ `JRE` ⊃ `JVM`. Каждый следующий добавляет инструменты поверх предыдущего.

| Компонент | Что включает | Для чего |
|-----------|-------------|----------|
| **`JVM`** | Виртуальная машина: `ClassLoader`, `GC`, `JIT` | Исполняет байткод |
| **`JRE`** | `JVM` + стандартная библиотека (`rt.jar`) | Запуск готовых приложений |
| **`JDK`** | `JRE` + `javac`, `javap`, `jcmd`, `jstack`, `jmap`, `jfr` | Разработка: компиляция + диагностика |

Проще говоря: чтобы **запустить** Java-приложение, нужен `JRE`; чтобы его **собрать и отлаживать** — `JDK`; `JVM` — это «движок» внутри обоих.

С `Java 11` Oracle поставляет только `JDK` — отдельной поставки `JRE` больше нет. Если нужен компактный runtime для запуска, его собирают самостоятельно через `jlink` из модулей `JPMS` (`Java 9+`), включая только реально используемые модули.

## Q5. (!) Что такое `JIT`-компиляция и как она работает?

**`JIT`** (`Just-In-Time`) — компиляция байткода в нативный машинный код **во время выполнения** программы. Идея в компромиссе: интерпретатор стартует мгновенно, но работает медленно; нативный код работает быстро, но его дорого получать. Поэтому `JVM` начинает с интерпретации и компилирует только те методы, что вызываются часто (hot spots) — на них окупается стоимость компиляции.

В `HotSpot JVM` два компилятора, и они дополняют друг друга:
- **`C1`** (Client) — компилирует быстро, но с базовыми оптимизациями; даёт ранний прирост скорости на старте
- **`C2`** (Server) — компилирует дольше и агрессивнее (инлайнинг, escape analysis, loop unrolling); выжимает максимум производительности на действительно горячем коде

Основные оптимизации `JIT`:
- **Инлайнинг** (method inlining) — встраивание тела метода в вызывающий код
- **Escape Analysis** — определение, выходит ли объект за пределы метода
- **Loop unrolling** — развёртывание циклов
- **Dead code elimination** — удаление недостижимого кода
- **Branch prediction** — оптимизация условных переходов

```java
// JIT-оптимизация: инлайнинг
// До:
public int calculate(int x) {
    return multiply(x, 2);  // вызов метода
}
private int multiply(int a, int b) {
    return a * b;
}

// После инлайнинга JIT-компилятором:
// calculate(x) → x * 2  (прямая операция, без вызова)
```

Флаги для наблюдения за `JIT`:

```java
// Логирование компиляции
// -XX:+PrintCompilation
// -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining
```

## Q6. Что такое `Tiered Compilation`?

**Tiered Compilation** (многоуровневая компиляция) — стратегия, при которой `JVM` использует оба компилятора (`C1` и `C2`) последовательно, а не выбирает один из них. Смысл: `C1` быстро даёт «средне-оптимизированный» код и попутно собирает профиль выполнения, а `C2` позже использует этот профиль, чтобы скомпилировать метод максимально агрессивно. Включена по умолчанию с `Java 8`.

5 уровней компиляции — от чистой интерпретации до полностью оптимизированного `C2`:
- **Level 0** — интерпретация (метод ещё не горячий)
- **Level 1** — `C1` без профилирования (для простых методов, которым профиль не нужен)
- **Level 2** — `C1` с лёгким профилированием
- **Level 3** — `C1` с полным профилированием (собирает данные для `C2`)
- **Level 4** — `C2` с агрессивными оптимизациями (итоговое состояние горячего метода)

```java
// Типичный путь: Level 0 → Level 3 → Level 4
// Отключение tiered compilation:
// -XX:-TieredCompilation
// Порог компиляции C2:
// -XX:CompileThreshold=10000
```

**Практический эффект:** быстрый старт (за счёт `C1`) и максимальная производительность после прогрева (за счёт `C2`) — лучшее из двух миров. Это особенно важно для микросервисов, где и холодный старт, и пиковая нагрузка одинаково чувствительны.

## Q7. Что такое `GraalVM` и `AOT`-компиляция?

**`GraalVM`** — универсальная виртуальная машина от Oracle. В контексте JVM она интересна двумя ролями:
- **Graal JIT** — замена `C2`-компилятора в `HotSpot` (написан на Java, даёт сравнимые или лучшие оптимизации)
- **Native Image** — платформа для `AOT`-компиляции в самостоятельный бинарник без JVM

**`AOT`** (`Ahead-of-Time`) — компиляция в нативный код **до запуска** (на этапе сборки), в противоположность `JIT`, который компилирует во время работы. Это меняет баланс: вся работа по компиляции делается заранее, поэтому старт мгновенный, но `JVM` не может адаптировать код под реальный профиль нагрузки.

| Характеристика | `JIT` | `AOT` (Native Image) |
|---------------|-------|---------------------|
| Время старта | Медленнее (прогрев) | Быстрый (~50 мс) |
| Пиковая производительность | Выше (адаптивные оптимизации) | Ниже |
| Потребление памяти | Выше | Ниже (нет JIT, метаданных) |
| Применение | Долгоживущие сервисы | Serverless, CLI-утилиты |

```java
// Сборка native image (GraalVM)
// native-image -jar myapp.jar
// Spring Boot + GraalVM:
// ./mvnw -Pnative native:compile
```

Подробнее о применении в Spring Boot — в [вопросах по Spring Boot](../frameworks/spring/spring-boot-interview.md).

## Q8. (!) Как работает иерархия `ClassLoader` в `JVM`?

`ClassLoader` отвечает за загрузку `.class`-файлов в `JVM` по требованию (лениво, когда класс впервые понадобился). Загрузчики выстроены в иерархию «родитель-потомок» и работают по принципу делегирования (parent-first): прежде чем загрузить класс самому, загрузчик сначала просит это сделать родителя.

Иерархия загрузчиков выстроена сверху вниз (каждый — родитель следующего):

- **`Bootstrap ClassLoader`** (`C++` / JVM internal) — `java.lang`, `java.util`
  - → **`Platform ClassLoader`** (`Java 9+`, ранее `Extension`) — `javax.*`, `java.sql`
    - → **`Application ClassLoader`** (`System ClassLoader`) — classpath приложения
      - → **`Custom ClassLoader 1`** (плагины, `OSGi`)
      - → **`Custom ClassLoader 2`** (hot reload)

| `ClassLoader` | Что загружает | Путь |
|--------------|--------------|------|
| `Bootstrap` | Ядро `Java` (`java.lang.*`, `java.util.*`) | `$JAVA_HOME/lib` |
| `Platform` | Модули платформы (`java.sql`, `javax.crypto`) | `$JAVA_HOME/lib` |
| `Application` | Классы приложения и зависимости | `-classpath` / `-cp` |

Каждый класс проходит три этапа:
1. **Loading** — поиск `.class`-файла и чтение его байтов в память
2. **Linking** — верификация байткода, preparation (выделение памяти под `static`-поля со значениями по умолчанию) и resolution (разрешение символьных ссылок на другие классы)
3. **Initialization** — выполнение `static`-блоков и присваивание реальных значений `static`-полям

Класс инициализируется лениво — только при первом активном использовании (создание экземпляра, обращение к `static`-члену), а не в момент загрузки.

## Q9. Что такое принцип делегирования `ClassLoader`?

**Parent-first delegation** — перед тем как загрузить класс, `ClassLoader` сначала передаёт запрос родителю, тот — своему родителю, и так до самого верхнего (`Bootstrap`). Класс грузит тот загрузчик, который смог его найти первым, идя сверху вниз. Сам же текущий загрузчик берётся за дело только если никто из предков класс не нашёл.

```java
// Упрощённая логика ClassLoader.loadClass()
protected Class<?> loadClass(String name) throws ClassNotFoundException {
    // 1. Проверяем кэш — уже загружен?
    Class<?> c = findLoadedClass(name);
    if (c == null) {
        try {
            // 2. Делегируем родителю
            c = parent.loadClass(name);
        } catch (ClassNotFoundException e) {
            // 3. Родитель не нашёл — грузим сами
            c = findClass(name);
        }
    }
    return c;
}
```

Зачем нужна именно такая схема:
- **Безопасность** — системные классы всегда грузит `Bootstrap`, поэтому подменить `java.lang.String` своим вредоносным классом через пользовательский загрузчик невозможно
- **Единственность** — поскольку родитель проверяется первым, один класс не загрузится дважды разными загрузчиками в одной цепочке
- **Изоляция** — при этом разные ветки загрузчиков могут держать разные версии одного класса (так application-серверы изолируют приложения друг от друга)

**Подводные камни.** Важно различать три похожих исключения:
- `ClassNotFoundException` — класс не найден при явном поиске (`Class.forName`, `loadClass`)
- `NoClassDefFoundError` — класс присутствовал при компиляции, но отсутствует в runtime (несовпадение classpath)
- `ClassCastException` между «одинаковыми» классами — два класса с одним именем, загруженные **разными** загрузчиками, для `JVM` различны и несовместимы при касте

## Q10. Когда нужен кастомный `ClassLoader`?

Кастомный загрузчик нужен, когда стандартного «загрузить класс из classpath» недостаточно — то есть когда классы появляются динамически или должны быть изолированы. Типичные сценарии:
- **Плагин-системы** — загрузка кода из внешних JAR без перезапуска приложения (например, `OSGi`)
- **Hot reload** — перезагрузка изменённых классов в dev-среде на лету (Spring DevTools)
- **Изоляция зависимостей** — параллельное использование разных версий одной библиотеки разными модулями
- **Загрузка из нестандартных источников** — байты класса лежат в сети, БД или шифрованном архиве, а не в `.class`-файле на диске

В кастомном загрузчике переопределяют `findClass` (а не `loadClass`!) — так сохраняется parent-first делегирование, а собственная логика подключается только тогда, когда родитель класс не нашёл.

```java
public class PluginClassLoader extends ClassLoader {
    private final Path pluginDir;

    public PluginClassLoader(Path pluginDir, ClassLoader parent) {
        super(parent);
        this.pluginDir = pluginDir;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        Path classFile = pluginDir.resolve(
            name.replace('.', '/') + ".class"
        );
        try {
            byte[] bytes = Files.readAllBytes(classFile);
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}
```

**Подводный камень:** кастомный `ClassLoader` — частый источник утечки `Metaspace`. Загруженные им классы выгружаются только тогда, когда сам загрузчик становится недостижимым и собирается `GC`. Если на загрузчик где-то остаётся ссылка (например, кэш или `ThreadLocal`), классы висят в `Metaspace` вечно — это типичная утечка при многократном hot deploy.

## Q11. (!) Какие области памяти существуют в `JVM`?

Память `JVM` делится по принципу «что общее, а что приватно для потока». **Общие** области (`Heap`, `Metaspace`, `Code Cache`) видны всем потокам, и доступ к ним требует синхронизации. **Приватные** области (`Stack`, `PC Register`, `Native Method Stack`) создаются для каждого потока отдельно и не нуждаются в синхронизации.

| Область | Scope | Содержимое | Ключевые флаги |
|---------|-------|-----------|----------------|
| `Heap` | Общая | Объекты, массивы | `-Xms`, `-Xmx` |
| `Metaspace` | Общая | Метаданные классов | `-XX:MaxMetaspaceSize` |
| `Code Cache` | Общая | Нативный код от `JIT` | `-XX:ReservedCodeCacheSize` |
| `Stack` | Per-thread | Фреймы вызовов | `-Xss` (по умолчанию 512KB-1MB) |
| `PC Register` | Per-thread | Адрес текущей инструкции | — |
| `Direct Memory` | Off-heap | `ByteBuffer.allocateDirect()` | `-XX:MaxDirectMemorySize` |

Подробнее об анализе потребления памяти — в [вопросах по управлению памятью](../performance/memory-management-interview.md).

## Q12. (!) Что такое `Stack` и `Heap` и чем они отличаются?

Коротко: **`Stack`** хранит «контекст выполнения» (где мы в коде, какие локальные переменные и ссылки), **`Heap`** хранит сами объекты. `Stack` свой у каждого потока и управляется автоматически по принципу LIFO; `Heap` один на всю `JVM` и его убирает `GC`.

| Характеристика | `Stack` | `Heap` |
|---------------|---------|--------|
| Что хранит | Примитивы, ссылки, фреймы вызовов | Объекты, массивы |
| Scope | Per-thread (приватный) | Общий для всех потоков |
| Размер | Фиксированный (`-Xss`) | Динамический (`-Xms` / `-Xmx`) |
| Скорость доступа | Быстрый (LIFO) | Медленнее (поиск по ссылке) |
| Ошибка переполнения | `StackOverflowError` | `OutOfMemoryError` |
| Управление | Автоматическое (LIFO) | `Garbage Collector` |

```java
public void example() {
    int x = 42;               // x — в Stack (примитив)
    String s = "hello";        // s (ссылка) — в Stack, объект String — в Heap
    List<String> list = new ArrayList<>(); // list (ссылка) — Stack, ArrayList — Heap
    list.add(s);               // внутри ArrayList ссылка на тот же String в Heap
}
// При выходе из метода — фрейм Stack удаляется,
// объекты в Heap живут, пока на них есть ссылки
```

**Граничные случаи.** Ключ к разнице между ошибками — где кончилась память. `StackOverflowError` возникает, когда переполнен стек потока — почти всегда из-за бесконечной (или слишком глубокой) рекурсии: каждый вызов добавляет фрейм, а они не освобождаются. `OutOfMemoryError: Java heap space` — когда в `Heap` накопилось слишком много живых объектов и `GC` не может ничего освободить.

## Q13. Что такое `Metaspace` и чем он заменил `PermGen`?

**`PermGen`** (Permanent Generation, до `Java 8`) — фиксированная область **внутри** `Heap` для метаданных классов. Её главная беда — заранее заданный лимит: при частом `hot deploy` старые классы накапливались, и приложение падало с `OutOfMemoryError: PermGen space`, хотя обычной heap-памяти было сколько угодно.

**`Metaspace`** (с `Java 8`) — пришёл на замену и хранит те же метаданные, но уже в **нативной памяти** ОС, а не внутри `Heap`. Главное отличие — он растёт по требованию, поэтому жёсткого `PermGen`-лимита больше нет (но при утечке `Metaspace` теперь может «съесть» всю память машины, если не задан `-XX:MaxMetaspaceSize`).

| Свойство | `PermGen` | `Metaspace` |
|----------|----------|------------|
| Расположение | Часть `Heap` | Нативная память ОС |
| Размер | Фиксированный (`-XX:MaxPermSize`) | Динамический, растёт по запросу |
| Лимит | Обязателен | Опциональный (`-XX:MaxMetaspaceSize`) |
| `GC` | `Full GC` | `Metadata GC Threshold` |

```java
// Настройка Metaspace
// -XX:MetaspaceSize=128m        — порог для срабатывания GC метаданных
// -XX:MaxMetaspaceSize=512m     — жёсткий лимит (рекомендуется в production)

// Мониторинг Metaspace
// jcmd <pid> VM.metaspace
```

Утечка `Metaspace` возникает при многократном `hot deploy` (например, в `Tomcat`), когда старые `ClassLoader` не выгружаются из-за удержания ссылок.

## Q14. Что происходит при нехватке памяти в `Heap`?

`JVM` не сдаётся сразу — она сначала пытается освободить место и только после этого падает. Когда не удаётся выделить память под новый объект, шаги такие:

1. Запускается `Minor GC` — сборка `Young Generation` (дешёвая, чистит короткоживущие объекты)
2. Если места всё ещё нет — запускается `Full GC` — сборка всего `Heap` (дорогая, со `Stop-The-World`)
3. Если и после `Full GC` свободной памяти недостаточно — выбрасывается `OutOfMemoryError`

То есть `OOM` — это не «память сразу кончилась», а «`GC` уже всё убрал, что мог, и этого не хватило».

Типы `OutOfMemoryError` (важно различать — каждый указывает на свою область):

```java
// Недостаточно Heap
java.lang.OutOfMemoryError: Java heap space

// GC работает слишком долго (>98% времени — GC, <2% освобождается)
java.lang.OutOfMemoryError: GC overhead limit exceeded

// Не хватает Metaspace
java.lang.OutOfMemoryError: Metaspace

// Не хватает нативной памяти для потоков
java.lang.OutOfMemoryError: unable to create new native thread

// Не хватает direct memory
java.lang.OutOfMemoryError: Direct buffer memory
```

**Рекомендация:** в production всегда включайте `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/heapdump.hprof`. Тогда в момент падения `JVM` автоматически сохранит heap dump — без него причину утечки придётся искать вслепую, ведь воспроизвести `OOM` повторно часто невозможно.

## Q15. (!) Что такое `Garbage Collection` и зачем он нужен?

**`Garbage Collection`** (`GC`) — автоматическое освобождение памяти от объектов, до которых больше нельзя «дотянуться» из живой части программы. Ключевой критерий — не «используется ли объект», а **достижим ли он** по цепочке ссылок от корневых объектов (`GC Roots`). Если нет ни одного пути от `GC Roots` к объекту, его память можно забрать.

**`GC Roots`** — стартовые точки обхода графа объектов (то, что заведомо живо):
- Локальные переменные и параметры методов в стеках потоков
- Активные потоки (`Thread` objects)
- Статические переменные загруженных классов
- Ссылки из `JNI`

Базовый алгоритм — **Mark-and-Sweep** (с опциональной компактацией):
1. **Mark** — обход графа от `GC Roots`, все достижимые объекты помечаются как живые
2. **Sweep** — память непомеченных (недостижимых) объектов освобождается
3. **Compact** (опционально) — живые объекты сдвигаются вплотную, чтобы убрать «дыры» (фрагментацию) и ускорить будущее выделение памяти

**Компромисс.** Плюсы: не нужны ручные `malloc`/`free`, нет висячих указателей (`dangling pointer`) и двойного освобождения, меньше класс утечек. Минусы: за это платим `STW`-паузами, непредсказуемостью момента сборки и накладными расходами `CPU`/памяти на работу самого `GC`.

## Q16. (!) Что такое `Generational Garbage Collection`?

**`Generational GC`** — стратегия, основанная на **гипотезе поколений**: подавляющее большинство объектов умирает молодыми (infant mortality), и лишь немногие живут долго. Раз так, выгодно не сканировать весь `Heap` каждый раз, а разделить его на поколения и часто/дёшево чистить «молодую» область, где почти всё уже мусор, и редко трогать «старую», где живут долгожители.

`Heap` делится на поколения:

| Область | Назначение | Тип GC | Характеристика |
|---------|-----------|--------|---------------|
| `Eden` | Создание новых объектов | `Minor GC` | Быстрый, частый |
| `Survivor` (S0, S1) | Промежуточное хранение | `Minor GC` | Copy-collection |
| `Old Generation` | Долгоживущие объекты | `Major/Full GC` | Редкий, долгий |

Жизненный цикл объекта: рождается в `Eden` → при `Minor GC` (срабатывает, когда `Eden` заполнен) выжившие копируются в `Survivor` → переживая каждый следующий `Minor GC`, объект увеличивает «возраст» и кочует между `Survivor 0` и `Survivor 1` → когда возраст достигает порога (по умолчанию 15, настраивается `-XX:MaxTenuringThreshold`), объект промотируется (promotion) в `Old Generation` как долгожитель. Чем дольше объект задержался в Young, тем дороже потом обойдётся его сборка в Old.

## Q17. (!) Что означает `Stop-The-World`?

**`Stop-The-World`** (`STW`) — пауза, на время которой `JVM` останавливает **все** потоки приложения, чтобы `GC` мог безопасно работать с графом объектов. Останавливать приходится потому, что иначе приложение меняло бы ссылки прямо во время обхода — и `GC` не мог бы получить согласованную картину достижимости. Как это происходит:

- Потоки приложения доводятся до ближайшего **safepoint** (безопасной точки) и замораживаются
- `GC` выполняет маркировку / копирование / компактирование над «застывшим» снимком кучи
- После завершения потоки возобновляются

**Влияние на приложение:** всплески latency, таймауты, «фризы» UI. Для latency-критичных систем (цель `<10 мс p99`) именно `STW`-паузы — главный враг, поэтому современные сборщики стремятся делать как можно больше работы конкурентно, не останавливая приложение.

Способы минимизации:
- Использование `ZGC` или `Shenandoah` (паузы `<1 мс`)
- Настройка `-XX:MaxGCPauseMillis` для `G1`
- Уменьшение количества живых объектов в `Old Generation`
- Мониторинг: `GC`-логи (`-Xlog:gc*`), [инструменты наблюдаемости](../monitoring/observability-interview.md)

## Q18. Когда объект становится пригодным для `GC`?

Объект пригоден для `GC`, когда он **недостижим** из `GC Roots` — то есть оборвана последняя цепочка ссылок, ведущая к нему от живых корней. Важно: дело именно в достижимости, а не в том, «обнулили ли мы переменную». Объект может оставаться в памяти, даже если локальная ссылка ушла, — пока на него ссылается что-то достижимое.

Типичные сценарии, после которых объект становится недостижим:

```java
// 1. Обнуление ссылки
Object obj = new Object();
obj = null;  // объект пригоден для GC

// 2. Выход из области видимости
void method() {
    Object local = new Object();
}  // local выходит из scope — объект пригоден для GC

// 3. Переназначение ссылки
Object obj = new Object();  // первый объект
obj = new Object();          // первый объект пригоден для GC

// 4. Изоляция (island of isolation)
class Node { Node next; }
Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;
a = null;
b = null;  // циклическая структура недостижима — оба пригодны для GC
```

**Ключевой момент:** `GC` в JVM определяет жизнь объекта через достижимость от `GC Roots`, а не подсчётом ссылок (reference counting). Именно поэтому циклические ссылки (последний пример выше) **не** мешают сборке: если весь «островок» из ссылающихся друг на друга объектов отрезан от корней, он будет собран целиком.

## Q19. (!) В чём разница между `Strong`, `Weak`, `Soft` и `Phantom` ссылками?

Эти четыре типа задают разную «силу удержания» объекта: от `Strong` (GC не тронет, пока ссылка жива) до `Phantom` (объект почти не живёт, ссылка нужна лишь для уведомления об уже состоявшейся сборке). Чем «слабее» ссылка, тем легче `GC` забирает объект.

| Тип ссылки | Класс | Когда собирается GC | Типичное применение |
|-----------|-------|-------------------|-------------------|
| `Strong` | прямая ссылка | Никогда (пока достижима) | Обычный код |
| `Soft` | `SoftReference<T>` | При нехватке памяти | Кэши |
| `Weak` | `WeakReference<T>` | При следующем `GC` | `WeakHashMap`, listeners |
| `Phantom` | `PhantomReference<T>` | После `finalize` | Очистка ресурсов, `Cleaner` |

```java
// Soft — кэширование: объект живёт, пока хватает памяти
SoftReference<byte[]> cache = new SoftReference<>(new byte[1024 * 1024]);
byte[] data = cache.get(); // может вернуть null, если GC собрал

// Weak — не мешает GC
WeakReference<Object> weak = new WeakReference<>(new Object());
// После GC: weak.get() == null

// WeakHashMap — ключи на weak-ссылках
WeakHashMap<Object, String> map = new WeakHashMap<>();
Object key = new Object();
map.put(key, "value");
key = null;  // после GC запись удалится из map

// Phantom — для finalization-замены (через ReferenceQueue)
ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<Object> phantom = new PhantomReference<>(new Object(), queue);
// phantom.get() всегда возвращает null
// объект появится в queue после finalize
```

**Главное для собеседования** — разница между `Soft` и `Weak`. `SoftReference` `JVM` держит как можно дольше и гарантированно очищает только **перед** тем, как бросить `OutOfMemoryError` (поэтому годится для кэшей: данные живут, пока есть память). `WeakReference` же очищается при **любом** ближайшем `GC`, как только не осталось strong-ссылок (поэтому годится для `WeakHashMap` и слушателей — записи исчезают, как только ключ перестал использоваться).

## Q20. Можно ли запустить `GC` из кода? Стоит ли?

```java
System.gc();             // «подсказка» JVM запустить GC
Runtime.getRuntime().gc(); // эквивалент
```

**Можно, но не нужно.** `System.gc()` — это лишь **рекомендация** запустить сборку, а не команда: `JVM` вправе её проигнорировать. Полагаться на него для управления памятью нельзя. В production его обычно **отключают** флагом, чтобы случайный вызов из библиотеки не запустил дорогой `Full GC`:

```java
// Отключение System.gc()
// -XX:+DisableExplicitGC
```

Редкие случаи, где `System.gc()` оправдан:
- В бенчмарках — привести память к предсказуемому состоянию между замерами
- При работе с `DirectByteBuffer` — спровоцировать освобождение off-heap памяти, привязанной к собранным объектам
- В тестах — проверить, что объект действительно стал недостижим

**Антипаттерн:** вызывать `System.gc()` в обычном production-коде. Он почти всегда запускает `Full GC` с длинной `STW`-паузой, бьющей по latency, и при этом не гарантирует, что память реально освободится.

## Q21. Пригодны ли циклические ссылки для `GC`?

Да, циклические ссылки собираются без проблем. Причина — в самом алгоритме: `GC` в `JVM` использует **tracing** (обход графа от `GC Roots`), а не **reference counting** (подсчёт входящих ссылок). При подсчёте ссылок объекты в цикле держали бы счётчик друг друга ненулевым и никогда не освободились бы. Но tracing на это не смотрит: он проверяет лишь, есть ли путь от корня. Если вся циклическая структура отрезана от `GC Roots`, она собирается целиком, сколько бы ссылок объекты ни держали друг на друга.

```java
// node1 → node2 → node3 → node1 (цикл)
node1 = null;
node2 = null;
node3 = null;
// Все три объекта недостижимы из GC Roots — будут собраны
```

Именно поэтому в языках с reference counting (например, `CPython`) приходится держать отдельный детектор циклов — в `JVM` он не нужен.

## Q22. (!) Какие сборщики мусора доступны в `HotSpot JVM`?

Все они решают одну задачу, но с разным компромиссом между **паузами** и **throughput** (пропускной способностью), и под разный размер `Heap`. Грубо: `Serial`/`Parallel` жертвуют паузами ради простоты и throughput, `G1` ищет баланс, а `ZGC`/`Shenandoah` минимизируют паузы ценой большего overhead.

| Сборщик | Флаг | Паузы | `Heap` | Доступность |
|---------|------|-------|--------|------------|
| **Serial** | `-XX:+UseSerialGC` | Длинные, STW | Малый | Все версии |
| **Parallel** | `-XX:+UseParallelGC` | Средние, STW | Средний | Все, default до Java 8 |
| **G1** | `-XX:+UseG1GC` | Управляемые | Большой | Java 7+, default с Java 9 |
| **ZGC** | `-XX:+UseZGC` | `<1 мс` | До 16 TB | Java 15+ (production) |
| **Shenandoah** | `-XX:+UseShenandoahGC` | `<10 мс` | Большой | Java 12+ (OpenJDK) |

`CMS` (`Concurrent Mark-Sweep`) удалён в `Java 14`.

```java
// Определить текущий GC:
// java -XX:+PrintFlagsFinal -version 2>&1 | grep UseGC
// или: jcmd <pid> VM.flags
```

## Q23. (!) Как работает `G1 Garbage Collector`?

**`G1`** (Garbage First) — сборщик по умолчанию с `Java 9`, рассчитанный на большой `Heap` и предсказуемые паузы. Ключевая идея в самом названии: он делит `Heap` не на две большие области, а на множество равных **регионов** (обычно 2048 штук, размер 1-32 MB) и сначала собирает те, где **больше всего мусора** (Garbage First) — так за фиксированное время паузы освобождается максимум памяти. Поколения (`Eden`/`Survivor`/`Old`) тут логические: любой регион может играть любую роль.

`Heap` в `G1` — это набор регионов, каждый из которых отмаркирован одной из ролей:

- `E` — `Eden` (выжившие при `Young GC` копируются в `Survivor`: `E` → `S`)
- `S` — `Survivor`
- `O` — `Old`
- `H` — `Humongous` (крупные объекты)
- `Free` — свободные, пока ни под что не выделенные регионы

Каждый регион в любой момент играет одну из ролей: `Eden`, `Survivor`, `Old` или `Humongous` — особый случай для крупных объектов, занимающих > 50% региона (они выделяются напрямую в Old-регионы и дороги в сборке).

Фазы работы `G1`:
1. **Young GC** — собирает заполненные `Eden`/`Survivor` регионы, копируя выживших (короткий `STW`)
2. **Concurrent Marking** — параллельно с приложением размечает, в каких Old-регионах сколько живых объектов
3. **Mixed GC** — собирает `Young` плюс те `Old`-регионы, где мусора больше всего; именно здесь реализуется принцип «Garbage First»

```java
// Ключевые флаги G1
// -XX:+UseG1GC
// -XX:MaxGCPauseMillis=200         — целевая пауза (мс)
// -XX:G1HeapRegionSize=16m         — размер региона
// -XX:InitiatingHeapOccupancyPercent=45  — порог запуска concurrent marking
```

## Q24. (!) Как работает `ZGC`?

**`ZGC`** — сборщик со сверхнизкими паузами (обычно `<1 мс`), причём длительность пауз **не растёт** с размером `Heap`. Поддерживает `Heap` до **16 TB**. Главный приём: почти всю работу, включая перемещение объектов, `ZGC` делает **конкурентно** — приложение продолжает работать, а не стоит в `STW`.

Чтобы перемещать объекты прямо под работающим приложением, `ZGC` использует:
- **Colored pointers** — служебные метаданные `GC` (например, «объект перемещён») хранятся прямо в неиспользуемых битах указателя, а не в заголовке объекта
- **Load barriers** — на каждом чтении ссылки вставлен барьер, который проверяет цвет указателя и при необходимости «чинит» его на актуальный адрес
- **Concurrent relocation** — объекты переносятся в новые регионы без остановки приложения; барьеры гарантируют, что код всегда видит корректный адрес

С `Java 21` появился **Generational `ZGC`** (`-XX:+UseZGC -XX:+ZGenerational`) — он добавляет поколения поверх этой схемы, отдельно и чаще собирая молодые объекты, что заметно повышает эффективность на типичных нагрузках.

```java
// Включение ZGC
// -XX:+UseZGC

// Generational ZGC (Java 21+)
// -XX:+UseZGC -XX:+ZGenerational

// ZGC автоматически определяет Heap — можно задать:
// -Xmx16g
// -XX:SoftMaxHeapSize=8g  — мягкий лимит (ZGC попытается не превышать)
```

**Сценарий применения:** `ZGC` — лучший выбор для latency-критичных приложений (торговые платформы, real-time системы) на `Java 17+`, где даже редкие десятки миллисекунд паузы недопустимы. Платой служит чуть меньший throughput и небольшой overhead от load barriers.

## Q25. Как работает `Shenandoah`?

**`Shenandoah`** — регионарный сборщик с низкими паузами от Red Hat, доступен в `OpenJDK` с `Java 12`. Как и `ZGC`, ставит во главу угла короткие паузы и делает большую часть работы конкурентно с приложением.

**Отличие от `G1`:** `Shenandoah` выполняет **конкурентную компактацию** — перемещает живые объекты без `STW`. Чтобы приложение не «теряло» переезжающий объект, в заголовок каждого объекта добавлено дополнительное слово — **forwarding pointer**, указывающее на актуальное местоположение.

**Отличие от `ZGC`:** другой механизм — Shenandoah работает с обычными указателями (без colored pointers), а актуальный адрес хранит в forwarding pointer внутри объекта. Платой за это служит небольшой overhead памяти на каждый объект. Важная организационная деталь: Shenandoah есть в `OpenJDK`, но **отсутствует в Oracle JDK**.

```java
// Включение Shenandoah
// -XX:+UseShenandoahGC

// Режим работы:
// -XX:ShenandoahGCMode=normal    — конкурентный (default)
// -XX:ShenandoahGCMode=iu        — incremental update
// -XX:ShenandoahGCMode=passive   — STW (для отладки)
```

## Q26. Как выбрать сборщик мусора для production?

Выбор сводится к одному вопросу: что важнее — **низкие паузы** (latency) или **максимальная пропускная способность** (throughput)? Под это и подбирается сборщик с учётом размера `Heap`.

| Критерий | Рекомендация |
|----------|-------------|
| Latency `<10 мс` p99 | `ZGC` или `Shenandoah` |
| Throughput (batch, ETL) | `Parallel GC` |
| Универсальный (API, web) | `G1` (default) |
| Малый `Heap` (`<256 MB`) | `Serial GC` |
| Контейнеры с малой памятью | `Serial` или `G1` с настройкой |

**Эмпирическое правило** — не угадывать, а идти от измерений:
1. Начать с `G1` (default) — он закрывает ~80% задач без тюнинга
2. Снять `GC`-логи и измерить реальные паузы и throughput под нагрузкой
3. Если паузы не укладываются в SLA — перейти на `ZGC` (или `Shenandoah`)
4. Если это batch/ETL и важна именно пропускная способность — попробовать `Parallel GC`

Подробнее о настройке производительности — в [вопросах по JVM Performance Tuning](../performance/jvm-performance-tuning-interview.md).

## Q27. (!) Какие флаги `JVM` наиболее важны для production?

Минимально необходимый набор закрывает четыре зоны: фиксация памяти, выбор и настройка `GC`, поведение при `OOM` и наблюдаемость (`GC`-логи). Ниже — типовой production-набор с пояснениями в комментариях.

```java
// === Память ===
-Xms4g -Xmx4g                        // Heap: начальный = максимальный (избежать resize)
-XX:MaxMetaspaceSize=512m             // Лимит Metaspace
-XX:MaxDirectMemorySize=256m          // Лимит direct memory (NIO)

// === Garbage Collector ===
-XX:+UseG1GC                          // или -XX:+UseZGC
-XX:MaxGCPauseMillis=200              // Целевая пауза (G1)

// === Диагностика OOM ===
-XX:+HeapDumpOnOutOfMemoryError       // Дамп при OOM
-XX:HeapDumpPath=/var/log/app/heapdump.hprof
-XX:+ExitOnOutOfMemoryError           // Завершить процесс при OOM

// === GC-логирование (Java 9+) ===
-Xlog:gc*:file=/var/log/app/gc.log:time,level,tags:filecount=5,filesize=50m

// === Кодировка ===
-Dfile.encoding=UTF-8

// === Контейнеры ===
-XX:+UseContainerSupport              // Учитывать cgroup-лимиты (default с Java 10)
-XX:MaxRAMPercentage=75.0             // % от RAM контейнера вместо -Xmx
```

**Подводный камень:** задать `-Xmx` больше memory limit контейнера. Тогда `JVM` будет считать память «своей» и спокойно её занимать, а ОС/`cgroup` убьёт процесс через `OOM Killer` ещё до того, как сработает heap-`OOM` внутри `JVM`. В контейнерах вместо жёсткого `-Xmx` обычно задают `-XX:MaxRAMPercentage`.

## Q28. Как настроить размер `Heap`?

Настройка сводится к двум решениям: задать границы `Heap` (`-Xms`/`-Xmx`) и оставить запас под всё, что лежит **вне** `Heap` (`Metaspace`, `Code Cache`, стеки потоков, direct memory, сама ОС).

Основные флаги:

```java
-Xms2g    // Начальный размер Heap
-Xmx2g    // Максимальный размер Heap (рекомендуется = -Xms)
-Xmn512m  // Размер Young Generation (обычно 1/4 - 1/3 от -Xmx)
```

**Рекомендации:**
- **`-Xms` = `-Xmx`** — фиксируем размер, чтобы избежать дорогого расширения/сжатия `Heap` в runtime и связанных с ним пауз
- **Не более 75%** RAM хоста/контейнера — оставшаяся четверть нужна под `Metaspace`, `Code Cache`, direct memory, стеки потоков и саму ОС; иначе процесс убьёт `OOM Killer`
- **Мониторинг:** если `GC` съедает >5-10% процессорного времени (`GC overhead`) — это сигнал, что `Heap` мал или аллокаций слишком много

```java
// Пример для контейнера с 4 GB RAM:
-XX:MaxRAMPercentage=75.0    // JVM возьмёт ~3 GB под Heap
// или явно:
-Xms3g -Xmx3g
```

Когда увеличивать `Heap`:
- Частые `OutOfMemoryError: Java heap space`
- `GC overhead limit exceeded`
- Высокая доля `Full GC` в логах

Когда **уменьшать**: слишком длинные `GC`-паузы (особенно при `Parallel`/`G1`).

## Q29. (!) Как уменьшить `GC`-паузы?

Паузы уменьшают с двух сторон: сменой сборщика на более «тихий» и снижением нагрузки на `GC` (меньше аллокаций — меньше работы). Шаги от самого результативного к точечным:

1. **Выбор сборщика** — `ZGC` / `Shenandoah` дают субмиллисекундные паузы там, где `G1` не укладывается в SLA
2. **Настройка `G1`** — `-XX:MaxGCPauseMillis=100` снижает целевую паузу (но ценой более частых сборок и меньшего throughput)
3. **Уменьшение аллокаций** — самый универсальный рычаг: меньше создаём объектов → меньше работы для `GC`
4. **Object pooling** — переиспользование тяжёлых объектов (соединения, буферы), но осторожно: для лёгких объектов пул чаще вредит, чем помогает
5. **Избегать `Humongous` объектов** в `G1` (> 50% региона) — они дороги в выделении и сборке
6. **Настройка поколений** — `-XX:MaxTenuringThreshold` регулирует, как быстро объекты уходят в `Old Gen` (преждевременная промоция перегружает дорогую сборку Old)

```java
// Пример: минимизация пауз с G1
-XX:+UseG1GC
-XX:MaxGCPauseMillis=100
-XX:G1HeapRegionSize=16m
-XX:ParallelGCThreads=8
-XX:ConcGCThreads=4
-XX:InitiatingHeapOccupancyPercent=35

// Пример: ZGC для субмиллисекундных пауз
-XX:+UseZGC
-Xmx8g
```

Мониторинг пауз: анализ `GC`-логов через [GCEasy](https://gceasy.io/) или [GCViewer](https://github.com/chewiebug/GCViewer).

## Q30. Как `JVM` работает в контейнерах `Docker`/`Kubernetes`?

Главная сложность контейнеров в том, что до `Java 10` `JVM` смотрела на ресурсы **всего хоста**, а не контейнера: видела 64 GB и 32 ядра физической машины, хотя контейнеру выделили 512 MB и 1 CPU. С `Java 10+` это исправлено — `JVM` учитывает `cgroup`-лимиты контейнера (флаг `-XX:+UseContainerSupport` включён по умолчанию).

Основные проблемы и решения:

| Проблема | Решение |
|----------|---------|
| `JVM` не видит лимит памяти | Обновить `Java` >= 10; `-XX:+UseContainerSupport` |
| `OOM Killer` от ОС | `-XX:MaxRAMPercentage=75.0` вместо `-Xmx` больше лимита |
| Неправильное количество CPU | `-XX:ActiveProcessorCount=N` при необходимости |
| Долгий старт | `CDS` (Class Data Sharing), `AppCDS`, или `GraalVM` native image |

```java
// Dockerfile — пример
// ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0 \
//   -XX:+UseZGC \
//   -XX:+HeapDumpOnOutOfMemoryError \
//   -XX:HeapDumpPath=/tmp/heapdump.hprof \
//   -Xlog:gc*:file=/tmp/gc.log:time"
// ENTRYPOINT ["java", "$JAVA_OPTS", "-jar", "app.jar"]
```

Подробнее о контейнеризации — в [вопросах по Docker](../devops/docker-interview.md) и [Kubernetes](../devops/kubernetes-interview.md).

## Q32. Что такое `Heap Dump` и `Thread Dump`?

Оба — это «фотографии» состояния `JVM` в момент снятия, но снимают разные срезы: один — память, другой — потоки.

**`Heap Dump`** — снимок всех объектов в `Heap`: что лежит в памяти, сколько занимает и кто на это ссылается. Отвечает на вопрос **«что съело память»** — отсюда его используют для поиска утечек.

**`Thread Dump`** — снимок состояния всех потоков: стек вызовов, статус (`RUNNABLE`/`BLOCKED`/`WAITING`), удерживаемые и ожидаемые блокировки. Отвечает на вопрос **«почему висит или грузит CPU»** — отсюда его используют для диагностики deadlock, зависаний и высокой загрузки процессора.

```java
// Heap Dump
// jcmd <pid> GC.heap_dump /tmp/heapdump.hprof
// jmap -dump:format=b,file=/tmp/heapdump.hprof <pid>
// Автоматически при OOM: -XX:+HeapDumpOnOutOfMemoryError

// Thread Dump
// jcmd <pid> Thread.print
// jstack <pid>
// kill -3 <pid>   (SIGQUIT — не убивает процесс, выводит dump в stdout)
```

Инструменты анализа:
- **`Eclipse MAT`** — анализ `Heap Dump` (Dominator Tree, Leak Suspects)
- **`fastthread.io`** — онлайн-анализ `Thread Dump`
- **`Java Mission Control`** — анализ записей `JFR`

## Q33. Как диагностировать утечку памяти в `Java`?

Суть утечки в `Java` коварна: это не «потерянная» память (как в C), а объекты, которые **остаются достижимыми** из `GC Roots`, хотя приложению уже не нужны. `GC` не может их собрать — ведь формально ссылка есть, — и `Old Gen` медленно, но неотвратимо растёт. Поэтому диагностика — это всегда поиск того, **кто** держит лишнюю ссылку.

Типичные причины (почти всегда — забытая ссылка в чём-то долгоживущем):
- Коллекции, растущие без ограничения (кэш без `eviction`)
- Статические коллекции / `static Map`
- Listener-ы и callback-и без deregistration
- Незакрытые ресурсы (`Connection`, `InputStream`)
- Утечки `ClassLoader` (hot deploy)
- `ThreadLocal` без `remove()`

Алгоритм диагностики:
1. Включить `-XX:+HeapDumpOnOutOfMemoryError` — чтобы дамп снялся автоматически в момент падения
2. Мониторить `Old Gen`: характерный признак утечки — пилообразный график, у которого **нижние точки после Full GC постоянно ползут вверх** (память не возвращается)
3. Снять `Heap Dump` через `jcmd` (или взять автоматический после `OOM`)
4. Открыть в `Eclipse MAT` → «Leak Suspects» или «Dominator Tree»
5. Найти объекты с аномально большим **retained size** (сколько памяти освободится, если их убрать)
6. Проследить цепочку ссылок до `GC Root` — это и укажет, кто держит утечку

```java
// Пример утечки: ThreadLocal без remove()
private static final ThreadLocal<List<byte[]>> cache = new ThreadLocal<>();

public void process() {
    cache.set(new ArrayList<>());
    cache.get().add(new byte[1024 * 1024]); // 1 MB
    // cache.remove() не вызван!
    // В thread pool поток переиспользуется — данные копятся
}
```

## Q34. Что такое `Java Flight Recorder` и `JFR Events`?

**`Java Flight Recorder`** (`JFR`) — встроенный прямо в `JVM` механизм профилирования. Его ключевое достоинство — **минимальный overhead** (обычно `<2%`): он использует данные, которые `JVM` и так собирает внутри себя, поэтому его не страшно держать включённым в production постоянно (в отличие от внешних агентов-профайлеров). Доступен бесплатно с `Java 11` (OpenJDK).

`JFR` непрерывно пишет **события** (events) о происходящем в `JVM`: `GC`-паузы, аллокации объектов, загрузку классов, блокировки на мониторах, `I/O`, компиляцию `JIT` и многое другое — а потом всё это можно проанализировать постфактум.

```java
// Запуск записи JFR
// При старте:
// -XX:StartFlightRecording=duration=300s,filename=app.jfr
//
// На работающем процессе:
// jcmd <pid> JFR.start duration=60s filename=recording.jfr
// jcmd <pid> JFR.dump filename=recording.jfr
// jcmd <pid> JFR.stop

// Анализ: открыть .jfr в Java Mission Control (JMC)
```

Программный API `JFR` (`Java 9+`):

```java
// Создание пользовательского JFR-события
@jdk.jfr.Label("Order Processing")
@jdk.jfr.Category("Business")
public class OrderEvent extends jdk.jfr.Event {
    @jdk.jfr.Label("Order ID")
    long orderId;
    @jdk.jfr.Label("Duration ms")
    long durationMs;
}

// Использование:
OrderEvent event = new OrderEvent();
event.begin();
processOrder(orderId);
event.orderId = orderId;
event.durationMs = elapsed;
event.commit();
```

`JFR` — рекомендуемый инструмент для production-мониторинга, поскольку он встроен в `JVM` и не требует агентов. Подробнее — в [вопросах по метрикам и трейсингу](../monitoring/metrics-tracing-interview.md).

## Q35. Есть ли деструктор в `Java`?

Нет. В `Java` **нет деструкторов** в стиле `C++`, и это сознательное решение: память освобождает `GC`, а момент сборки недетерминирован — поэтому надёжно «выполнить код при уничтожении объекта» язык не обещает. Освобождение ресурсов отвязано от освобождения памяти.

Для детерминированного освобождения ресурсов (файлы, соединения, сокеты) используют паттерн `try-with-resources` с `AutoCloseable` — он гарантирует вызов `close()` при выходе из блока, независимо от `GC`:

```java
// Правильный подход (Java 7+)
try (var conn = dataSource.getConnection();
     var stmt = conn.prepareStatement(sql);
     var rs = stmt.executeQuery()) {
    while (rs.next()) {
        process(rs);
    }
}  // conn, stmt, rs закрываются автоматически

// Устаревший подход
public class LegacyResource {
    @Override
    protected void finalize() throws Throwable {
        // НЕ рекомендуется! Deprecated с Java 9
        // Нет гарантии вызова; проблемы с производительностью
        cleanup();
    }
}
```

Замена `finalize` (с `Java 9`) — `java.lang.ref.Cleaner`: безопаснее (выполняется в отдельном потоке, не тормозит `GC`), но тоже **без гарантий своевременного вызова** — годится лишь как страховка от утечки, а не как основной механизм. **Рекомендация:** для освобождения ресурсов всегда использовать `try-with-resources`, а `Cleaner` — только как подстраховку на случай, если `close()` забыли вызвать.

## Q36. Можно ли воскресить объект после `finalize`?

Да, технически объект можно «воскресить». Перед сборкой `JVM` вызывает у него `finalize()`, и если внутри этого метода присвоить `this` какому-нибудь достижимому полю (например, статическому), объект снова станет достижимым из `GC Roots` — и `GC` его не заберёт:

```java
public class Zombie {
    static Zombie instance;

    @Override
    protected void finalize() {
        instance = this;  // «воскрешение»
    }
}

// Zombie z = new Zombie();
// z = null; System.gc();
// Zombie.instance != null — объект «воскрес»
// Повторное обнуление: Zombie.instance = null; System.gc();
// finalize() НЕ вызовется повторно — объект собран окончательно
```

Но воскресить объект можно только **один раз**: `JVM` помечает, что `finalize()` для него уже отработал, и при повторной недостижимости объект собирается без вызова `finalize()`. Этот трюк — чистый антипаттерн (непредсказуемое поведение, путаница в жизненном цикле); сам `finalize()` deprecated с `Java 9`.

## Q37. Что такое `Escape Analysis` и скалярная замена?

**`Escape Analysis`** — анализ `JIT`-компилятора `C2`, который определяет, «убегает» ли объект за пределы создавшего его метода или потока (сохраняется ли он в поле, возвращается ли наружу, передаётся ли в другой поток). Если объект **никуда не убегает**, его жизнь полностью ограничена методом — а значит, его необязательно вообще размещать в `Heap`.

В этом случае `JIT` может применить:
- **Scalar replacement** — разложить объект на отдельные поля в регистрах/стеке (без аллокации в `Heap`)
- **Stack allocation** — разместить объект на стеке (фактически через scalar replacement)
- **Lock elision** — убрать синхронизацию, если объект не разделяется между потоками

```java
// Пример: объект Point не убегает из метода
public int sumCoordinates() {
    Point p = new Point(3, 4);  // JIT может НЕ создавать объект в Heap
    return p.x + p.y;           // scalar replacement: просто 3 + 4
}

// Результат: нет аллокации → нет нагрузки на GC → быстрее
```

```java
// Флаги (включены по умолчанию):
// -XX:+DoEscapeAnalysis
// -XX:+EliminateAllocations
// -XX:+EliminateLocks
```

**Практическое значение:** короткоживущие объекты-обёртки (`Optional`, `Iterator`, маленькие `DTO`), не покидающие метод, часто полностью элиминируются `JIT`-компилятором. Поэтому распространённый страх «много мелких объектов = нагрузка на GC» на горячем коде нередко беспочвен — `Escape Analysis` убирает аллокацию вовсе. Подробнее о концепциях оптимизации — в [вопросах по Java Concurrency](../programming-languages/java/java-concurrency-interview.md).

## Q38. (!) Как работает GraalVM Native Image и каковы ограничения?

**GraalVM Native Image** — инструмент, который компилирует Java-приложение в самостоятельный нативный бинарник заранее (AOT — Ahead-Of-Time). Результат — исполняемый файл, который не нуждается в установленной `JVM` и запускается за миллисекунды вместо секунд. Цена за это — потеря рантайм-адаптивности `JIT` и жёсткие ограничения на динамику (рефлексия, прокси), о которых ниже.

**Как это работает** — конвейер сборки и запуска:

- `Java Source` (`.java`) → компилятор `javac` → `Bytecode` (`.class`)
- `Bytecode` → `GraalVM` `native-image` → `Native Binary` (`./app`)
- `Native Binary` запускается мгновенно (~50 ms против ~5 s у обычной `JVM`) → `Running Process`

В основе лежит **closed-world analysis** («анализ замкнутого мира»): на этапе сборки `native-image` статически прослеживает весь граф достижимых классов и методов от точки входа и компилирует **только** их. Всё, что нельзя увидеть статически, в бинарник не попадает — и именно отсюда растут все ограничения native image. Динамика, которую анализатор не может предсказать (рефлексия, прокси, загрузка классов в runtime), для него невидима, поэтому её нужно описывать заранее через конфигурацию и hints.

**Запуск native image:**
```bash
# Сборка (требует GraalVM JDK)
./gradlew nativeCompile

# Результат
./build/native/nativeCompile/app   # ~50-100 MB, запускается за ~50ms
```

**Spring Boot 3 + GraalVM Native:**
```xml
<!-- pom.xml -->
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.2.0</version>
</parent>

<plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
</plugin>
```

**Ограничения Native Image** (все вытекают из closed-world analysis — то, чего нет в статическом графе, нужно объявить вручную):
| Ограничение | Причина | Решение |
|-------------|---------|---------|
| Рефлексия | Закрытый мир не знает runtime-типов | `@RegisterForReflection`, hints |
| Dynamic proxies | Proxy создаётся в runtime | GraalVM proxy configuration |
| Classloading | Нельзя загрузить классы в runtime | Переписать код |
| JNI | Нативные вызовы требуют конфигурации | JNI configuration file |
| Serialization | `ObjectInputStream` читает произвольные классы | `@RegisterForSerialization` |

**Spring AOT и hints:**
```java
// Регистрация класса для рефлексии в native image
@Configuration
@ImportRuntimeHints(MyRuntimeHints.class)
public class AppConfig { }

class MyRuntimeHints implements RuntimeHintsRegistrar {
    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.reflection()
            .registerType(MyDto.class, MemberCategory.INVOKE_DECLARED_CONSTRUCTORS,
                MemberCategory.DECLARED_FIELDS);
        hints.resources().registerPattern("templates/*.html");
    }
}
```

**Когда использовать Native Image** (там, где важен старт, а не пиковый throughput):
- Serverless / Lambda — холодный старт оплачивается напрямую, и тут native выигрывает на порядки
- CLI-инструменты — пользователь ждёт мгновенного запуска, прогрев JIT недопустим
- Микросервисы с частым масштабированием — новые поды поднимаются быстрее и едят меньше памяти

**Когда НЕ использовать** (там, где сервис живёт долго и важна пиковая скорость):
- Долгоживущие сервисы с высоким throughput — прогретый `JIT C2` адаптируется под реальную нагрузку и даёт более высокий пиковый throughput, чем статичный AOT-код
- Код с активной динамикой — сложная рефлексия, динамическая генерация классов, Groovy-скрипты: их трудно или невозможно описать для closed-world analysis

## Q39. Как JIT-компилятор обнаруживает "горячие" методы?

«Горячий» — значит часто исполняемый. `HotSpot JVM` определяет это не эвристически, а буквально считая выполнение двумя счётчиками на каждый метод: **invocation counter** (сколько раз метод вызвали) и **backedge counter** (сколько раз выполнился «обратный переход» цикла — то есть как долго крутятся циклы внутри метода). Когда сумма переходит порог, метод признаётся горячим и ставится в очередь на компиляцию:

```
Порог компиляции C1 (клиентский): -XX:CompileThreshold=1500 (Tiered: ~2000)
Порог компиляции C2 (серверный):  -XX:CompileThreshold=10000 (Tiered: ~15000)
```

**Tiered Compilation (5 уровней):**

| Уровень | Режим | Порог | Когда |
|---------|-------|-------|-------|
| 0 | Интерпретация | — | Первые вызовы |
| 1 | C1 без профилирования | ~2000 | Быстрая компиляция |
| 2 | C1 с частичным профилем | — | Переходный |
| 3 | C1 с полным профилем | ~15000 | Сбор данных для C2 |
| 4 | C2 (агрессивные оптимизации) | — | Горячие методы в prod |

```java
// Диагностика: какие методы скомпилировал JIT
// Флаг: -XX:+PrintCompilation
// Вывод:
// 71    1       3       java.lang.String::hashCode (55 bytes)
// 73    2       4       com.app.OrderService::process (120 bytes)
//        ^tier  ^method

// async-profiler покажет flame graph JIT-компиляции:
// ./profiler.sh -e cpu -d 30 -f profile.html <PID>
```

**Деоптимизация (deoptimization).** `C2` оптимизирует агрессивно, опираясь на спекулятивные допущения из профиля (например, «в этой точке всегда приходит один и тот же тип»). Если в runtime допущение нарушается, `JVM` откатывает скомпилированный код обратно к интерпретатору — это и есть деоптимизация. Частые деоптимизации означают, что профиль «врёт», и стоят производительности:
```bash
# JIT может отменить оптимизацию если допущение нарушено
# Например: мономорфный вызов стал полиморфным → C2 деоптимизирует
# Диагностика:
-XX:+TraceDeoptimization     # логировать деоптимизации
-XX:+PrintDeoptimizationDetails
```

**Практика:** прогрев (warm-up) в prod критичен. Первые 10-30 секунд после деплоя p99 latency заметно хуже: код ещё интерпретируется или скомпилирован только `C1`, горячие пути не вышли на `C2`. Отсюда типичная ошибка — пускать полный трафик сразу после старта. Решение: либо `readiness probe` в Kubernetes откладывает приём трафика до прогрева, либо приложение само «прогоняет» горячие пути синтетическими запросами на старте.

## Q40. Что такое AOT-компиляция в контексте Spring Boot 3?

**Spring AOT** (Ahead-Of-Time) — фаза сборки в Spring Boot 3, которая выполняет «тяжёлую» работу по разбору конфигурации заранее. Обычно Spring при каждом старте сканирует classpath, разбирает аннотации, вычисляет `@Conditional` и строит `BeanDefinition` через рефлексию — всё это в runtime и небесплатно. AOT делает это **на этапе сборки** и генерирует готовый Java-код инициализации контекста, который при запуске остаётся просто выполнить.

**Два режима использования:**

1. **AOT для JVM** — ускоряет старт на обычной `JVM`: меньше рефлексии и сканирования при запуске (native не требуется)
2. **AOT для Native Image** — **обязателен** для GraalVM Native: именно AOT регистрирует hints, без которых closed-world analysis не «увидит» бины и рефлексию Spring

```bash
# Сборка с AOT
./mvnw spring-boot:process-aot

# Что генерируется:
# target/spring-aot/main/sources/
#   com/app/AppContextInitializer.java   ← сгенерированный код инициализации
#   com/app/BeanDefinitions.java         ← статические bean definitions
```

**Что AOT делает автоматически:**
- Вычисляет `@Conditional` условия во время сборки
- Генерирует proxy-классы статически (не через `java.lang.reflect.Proxy`)
- Регистрирует hints для рефлексии и ресурсов
- Вычисляет `@Value` placeholder types

**Подводный камень:** AOT исходит из того, что окружение на сборке и в runtime одинаковое. Условия вроде `@Profile` и `@ConditionalOnProperty` вычисляются **один раз при сборке** и «зашиваются» в сгенерированный код. Поэтому переключить профиль или включить условный бин через переменную окружения уже после сборки нельзя — набор бинов зафиксирован. Это меняет привычную для Spring модель «настрою профилями при деплое».

```java
// Проверить корректность AOT-сборки:
./mvnw -Pnative spring-boot:build-image   // через Buildpacks
./mvnw -Pnative native:compile            // напрямую
```

**Итог:** Spring AOT + GraalVM Native — сильная связка для serverless и быстрого масштабирования, где решают старт и память. Но для классических долгоживущих enterprise-сервисов обычный `JIT` на `JVM` по-прежнему выигрывает по пиковому throughput и не требует возни с hints и потери рантайм-гибкости.
