## Q1. Что такое статический анализ кода и зачем он нужен?

**Статический анализ — это проверка кода без его выполнения.** Инструмент читает исходник, строит модель программы (AST — Abstract Syntax Tree, байткод или промежуточное представление IR) и ищет в ней подозрительные паттерны.

**Зачем он нужен.** Идея в том, чтобы поймать дефект как можно раньше — пока он стоит дёшево. Чем позже найден баг (запуск, тесты, прод), тем дороже его исправить. Статический анализатор работает ещё до запуска и до того, как ревьюер откроет PR.

Что он даёт на практике:
- **Раннее обнаружение багов** — NullPointerException, утечки ресурсов, бесконечные циклы видны до первого запуска.
- **Единый стиль в команде** — форматирование и именование проверяет машина, а не люди на ревью.
- **Метрики качества в динамике** — видно, растёт технический долг или падает.
- **Уязвимости безопасности** — SQL injection, XSS, null dereference находятся автоматически.

**Важный нюанс.** Статический анализ **не заменяет тесты**: он не знает, делает ли код то, что нужно бизнесу. Но он дёшево закрывает целые классы технических дефектов, до которых тесты могут и не дойти.

## Q2. Чем статический анализ отличается от динамического?

**Главное отличие: статический анализ читает код, динамический — наблюдает за его выполнением.** Поэтому статический видит весь код целиком, но рассуждает о нём приблизительно (отсюда больше ложных срабатываний); динамический видит только то, что реально выполнилось, зато с фактами на руках.

| Аспект | Статический | Динамический |
|--------|------------|--------------|
| Когда | Без запуска кода | Во время выполнения |
| Покрытие | Весь код | Только исполняемые пути |
| Скорость | Быстро | Медленно (нужны тесты) |
| Ложные срабатывания | Выше | Ниже |
| Примеры | SonarQube, PMD, SpotBugs | JaCoCo, VisualVM, Java Flight Recorder |

**Почему так.** Статический анализатор рассуждает о всех возможных путях, не запуская ни одного, — поэтому покрывает весь код, но иногда ошибается («а вдруг сюда придёт null»). Динамический инструмент видит только то, что реально отработало на конкретных входных данных, — он точнее, но пропустит непокрытые ветки.

**Вывод:** инструменты не конкурируют, а дополняют друг друга. Статический ловит дефекты на всех путях дёшево, динамический подтверждает поведение на реальных сценариях.

## Q3. Какие классы проблем находит статический анализ?

Статический анализ покрывает пять разных уровней — от «код сломается в проде» до «код некрасивый». Их полезно различать, потому что реакция на них разная: баги чинят немедленно, стиль — автоматическим форматтером.

- **Потенциальные баги** — код скомпилируется, но поведёт себя неверно: NullPointerException, утечка ресурса (resource leak), бесконечный цикл.
- **Уязвимости безопасности** — дыры, которыми может воспользоваться атакующий: SQL injection, hardcoded passwords, небезопасная сериализация.
- **Code smells** — работает, но плохо поддерживается: длинные методы, god classes, дублирование.
- **Стилистические нарушения** — форматирование и соглашения об именовании; на работоспособность не влияют, но мешают читать.
- **Нарушения метрик** — превышение порогов: высокая цикломатическая сложность, слишком глубокое наследование.

**Эмпирическое правило:** первые две категории блокируют релиз, остальные — повод для рефакторинга, но не для остановки сборки.

## Q4. Что такое false positive и false negative в статическом анализе?

Это два типа ошибок самого анализатора — он ведь тоже может ошибаться.

- **False positive (ложная тревога)** — инструмент сообщает о проблеме, которой на самом деле нет. Прямого вреда коду нет, но это «шум»: чем его больше, тем быстрее команда перестаёт читать отчёты вообще.
- **False negative (пропуск)** — реальная проблема есть, но инструмент её не нашёл. Опаснее, потому что создаёт **ложное чувство безопасности**: «анализ зелёный, значит всё хорошо» — а баг в проде.

**Компромисс.** Снизить один тип ошибок обычно можно только ценой роста другого. Большинство инструментов осознанно жертвуют точностью ради полноты — минимизируют false negatives, мирясь с некоторым количеством false positives (лучше лишний раз предупредить, чем пропустить). Задача команды — донастроить правила под свой контекст: отключить шумные правила, чтобы вернуть доверие к отчётам.

## Q5. Что такое SonarQube и из каких компонентов состоит?

**SonarQube — платформа непрерывного контроля качества кода.** Её идея: один центральный сервер собирает результаты анализа со всех проектов, копит историю и показывает, как качество меняется со временем.

Система состоит из четырёх рабочих частей и двух конфигурационных. Полезно понимать, кто что делает:

- **SonarQube Server** — мозг системы: принимает отчёты, считает метрики, отдаёт веб-интерфейс. Внутри это несколько процессов: web server (UI и API), compute engine (обработка отчётов сканера) и встроенный Elasticsearch (поиск).
- **База данных** — обязательный компонент: хранит конфигурацию, правила, issues, метрики и всю историю анализов. Поддерживаются PostgreSQL (рекомендуемая), Oracle и Microsoft SQL Server; встроенная H2 годится только для демо. Без БД сервер не работает — потеря базы означает потерю всей истории качества.
- **SonarScanner** — запускается в CI на каждой сборке: анализирует проект и отправляет результат на сервер. Сам ничего не хранит.
- **SonarLint** — плагин для IDE: подсвечивает проблемы «на лету», прямо при наборе кода, без обращения к серверу. Закрывает дефекты до коммита.

Две настройки определяют, *что* считать проблемой и *что* считать провалом:
- **Quality Profile** — набор активных правил для языка (какие проверки включены).
- **Quality Gate** — пороговые условия; если хоть одно не выполнено, сборка помечается как провалившаяся.

**Связь компонентов:** Scanner и SonarLint находят issues по правилам из Quality Profile → Server применяет к ним Quality Gate и сохраняет результаты в базу данных → команда видит вердикт в UI или прямо в PR.

## Q6. Что такое Quality Gate в SonarQube?

**Quality Gate — это набор пороговых условий, которые решают, прошёл код проверку или нет.** Логика жёсткая: достаточно нарушить **одно** условие — и статус всего gate становится `FAILED`. Это «светофор» на пути в прод: красный блокирует merge.

Ключевой принцип стандартного **Sonar Way** — проверять только **новый код** (new code period), а не весь проект. Почему: на легаси-кодовой базе старых нарушений могут быть тысячи, и требовать их немедленного исправления нереально. Поэтому gate смотрит на то, что вы добавили или изменили, — это называется **Clean as You Code**: не даём ухудшать качество новыми коммитами, а старое чиним постепенно.

Типичные условия Sonar Way (всё — про новый код):
- **Coverage** ≥ 80% — новый код покрыт тестами.
- **Duplicated lines** < 3% — не копипастим.
- **Maintainability Rating = A** — нет тяжёлых code smells.
- **Reliability Rating = A** — нет новых багов.
- **Security Rating = A** — нет новых уязвимостей.

```yaml
# Пример условий в CI (через SonarQube API check)
- name: SonarQube Quality Gate check
  uses: sonarsource/sonarqube-quality-gate-action@master
  env:
    SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

## Q7. Какие метрики отслеживает SonarQube?

SonarQube группирует метрики по трём «осям качества» — надёжность, безопасность, поддерживаемость — плюс отдельно покрытие, дублирование и сложность. Каждой оси соответствует свой рейтинг A–E, чтобы можно было оценить проект одним взглядом.

| Метрика | Описание |
|---------|----------|
| **Bugs** | Потенциальные ошибки, влияющие на поведение |
| **Vulnerabilities** | Уязвимости безопасности |
| **Code Smells** | Проблемы поддерживаемости |
| **Coverage** | Покрытие тестами (из отчёта JaCoCo) |
| **Duplications** | % дублированных строк |
| **Cyclomatic Complexity** | Сложность кода |
| **Cognitive Complexity** | Читаемость кода |
| **Technical Debt** | Расчётное время на исправление всех Code Smells |
| **Reliability/Security/Maintainability Rating** | Рейтинг A–E |

**Как читать рейтинги:** Reliability считается по багам, Security — по уязвимостям, Maintainability — по техническому долгу. Сам SonarQube своих тестов не запускает: Coverage он берёт из готового отчёта JaCoCo, который вы сформировали на этапе тестов.

## Q8. Что такое Technical Debt Ratio в SonarQube?

**Technical Debt Ratio показывает, какую долю от стоимости разработки составляет стоимость уборки за собой.** Формула:

**Technical Debt Ratio = (Technical Debt / Development Cost) × 100%**

Из чего складываются две части дроби:
- **Technical Debt** (числитель) — суммарное время на исправление всех Code Smells. SonarQube берёт его не с потолка: у каждого правила есть «remediation cost» (например, «разбить длинный метод — 20 минут»), и они суммируются.
- **Development Cost** (знаменатель) — оценочное время написания всего кода. SonarQube считает его грубо, по количеству строк (по умолчанию около 30 минут на строку).

**Зачем нужно отношение, а не абсолютное число.** 10 часов долга — это много или мало? Зависит от размера проекта. Ratio нормирует долг на масштаб: 10 часов на крошечный модуль — катастрофа, на огромную систему — мелочь. По нему SonarQube и выставляет Maintainability Rating:

- **A** ≤ 5% — долг под контролем
- **B** 6–10%
- **C** 11–20%
- **D** 21–50%
- **E** > 50% — на уборку уйдёт больше, чем ушло на написание

## Q9. Что такое SonarQube issues: Bug, Vulnerability, Code Smell, Security Hotspot?

SonarQube делит находки на четыре типа по тому, **на что они влияют** — а значит, кто и как должен на них реагировать.

| Тип | Описание |
|-----|----------|
| **Bug** | Дефект, который, вероятно, вызовет некорректное поведение во время выполнения |
| **Vulnerability** | Слабое место, которое может быть использовано злоумышленником |
| **Code Smell** | Проблема поддерживаемости, не влияющая напрямую на работоспособность |
| **Security Hotspot** | Код, требующий ручной проверки на предмет безопасности (не обязательно уязвимость) |

**Ключевое различие — Vulnerability vs Security Hotspot.** Vulnerability — это уже найденная дыра, её надо чинить. Hotspot — лишь «чувствительное место» (работа с криптографией, файлами, вводом), которое **может** быть безопасным, а может и нет: машина не уверена и просит человека посмотреть глазами.

**Практическое следствие.** Каждый Security Hotspot нужно вручную пометить как `Reviewed` — выбрать `Safe` (всё в порядке), `Fixed` (исправлено) или `Acknowledged` (приняли риск). Пока hotspots не разобраны, Quality Gate может не пройти. Это сделано намеренно: вопросы безопасности нельзя замолчать автоматически.

## Q10. Как интегрировать SonarQube в Maven/Gradle-сборку?

Подключение в обоих сборщиках сводится к одному: указать адрес сервера, ключ проекта и токен авторизации, после чего запустить анализ отдельной командой/таском.

**Важный момент про порядок.** Сначала идёт `verify` (или `build`) — компиляция, тесты, генерация отчёта о покрытии, — и только потом `sonar`. Если запустить sonar до тестов, SonarQube не увидит coverage и покажет 0%.

**Maven:**
```xml
<!-- pom.xml properties -->
<properties>
    <sonar.host.url>https://sonarqube.example.com</sonar.host.url>
    <sonar.projectKey>my-project</sonar.projectKey>
</properties>
```
```bash
mvn verify sonar:sonar -Dsonar.token=$SONAR_TOKEN
```

**Gradle:**
```groovy
// build.gradle
plugins {
    id "org.sonarqube" version "4.4.1.3373"
}
sonar {
    properties {
        property "sonar.projectKey", "my-project"
        property "sonar.host.url", "https://sonarqube.example.com"
        property "sonar.token", System.getenv("SONAR_TOKEN")
    }
}
```
```bash
./gradlew sonar
```

## Q11. Что такое SpotBugs и чем он отличается от FindBugs?

**SpotBugs — это форк и преемник FindBugs.** Последний релиз FindBugs (3.0.1) вышел в 2015 году, после чего разработка остановилась; в 2016–2017 проект был официально объявлен мёртвым, и в 2017 году сообщество продолжило его под новым именем SpotBugs. По сути это тот же инструмент, но с живой разработкой.

**Как он работает.** SpotBugs анализирует **байткод**, а не исходник. Это его принципиальная особенность: ему не нужны исходные файлы, достаточно скомпилированных `.class`. Он сопоставляет байткод с базой «bug patterns» — известных шаблонов ошибок (разыменование null, неверный `equals`/`hashCode` и т.д.).

Чем он отличается от мёртвого FindBugs:
- **Активно поддерживается** — выходят новые версии и детекторы.
- **Понимает современную Java** — Java 11+ (FindBugs на новых версиях просто падал).
- **Расширяется плагинами** — Find Security Bugs (безопасность), fb-contrib (дополнительные детекторы).
- **Встраивается в SonarQube** через отдельный плагин.

**Следствие из «анализа байткода»:** SpotBugs можно запускать только после компиляции — на исходник без сборки он не работает (в отличие от PMD и Checkstyle).

## Q12. Какие категории багов находит SpotBugs?

SpotBugs раскладывает находки по категориям, которые отличаются **уверенностью и серьёзностью**: от «это почти наверняка баг» (Correctness) до «выглядит подозрительно, посмотри» (Dodgy code).

| Категория | Примеры |
|-----------|---------|
| **Correctness** | Null dereference, infinite loops, wrong comparisons |
| **Bad practice** | Ignored exceptions, equals/hashCode inconsistency |
| **Performance** | Использование String вместо StringBuilder в цикле |
| **Security** | SQL injection, HTTP response splitting |
| **Multithreaded correctness** | Deadlocks, race conditions |
| **Dodgy code** | Потенциально опасные приведения типов |

**На что смотреть в первую очередь:** Correctness и Multithreaded correctness — это почти всегда настоящие баги, их чинят сразу. Dodgy code и часть Bad practice дают больше ложных срабатываний — их стоит просматривать критически.

**Подключение в Maven:**

```xml
<!-- Maven интеграция -->
<plugin>
    <groupId>com.github.spotbugs</groupId>
    <artifactId>spotbugs-maven-plugin</artifactId>
    <version>4.8.3.0</version>
    <executions>
        <execution>
            <goals><goal>check</goal></goals>
        </execution>
    </executions>
</plugin>
```

## Q13. Что такое SpotBugs плагин Find Security Bugs?

**Find Security Bugs — это плагин к SpotBugs, специализированный на безопасности.** Базовый SpotBugs ищет общие баги, а этот плагин добавляет детекторы под уязвимости из OWASP Top 10 для Java-приложений. По сути превращает SpotBugs в простой SAST-инструмент (Static Application Security Testing).

Что находит — типичные веб-уязвимости и ошибки работы с данными:
- **Инъекции:** SQL injection, command injection, path traversal.
- **Веб:** XSS.
- **Криптография и секреты:** insecure random, weak crypto, hardcoded credentials.
- **Сериализация:** небезопасная десериализация (классический вектор RCE в Java).

**Сценарий применения:** ставится в дополнение к SpotBugs одной строчкой зависимости — дешёвый способ закрыть базовый уровень security-проверок, не покупая отдельный SAST.

```xml
<plugin>
    <groupId>com.github.spotbugs</groupId>
    <artifactId>spotbugs-maven-plugin</artifactId>
    <dependencies>
        <dependency>
            <groupId>com.h3xstream.findsecbugs</groupId>
            <artifactId>findsecbugs-plugin</artifactId>
            <version>1.12.0</version>
        </dependency>
    </dependencies>
</plugin>
```

## Q14. Что такое PMD и чем он отличается от SpotBugs?

**Главное отличие: PMD читает исходный код (строит AST), а SpotBugs — байткод.** Из этого вытекает всё остальное.

| | PMD | SpotBugs |
|--|-----|----------|
| Анализ | AST (исходник) | Байткод |
| Фокус | Стиль, design, code smells | Потенциальные баги |
| Настройка | Правила в XML ruleset | Детекторы |
| CPD | Да (поиск дублей) | Нет |

**Почему это важно на практике.** Раз PMD работает с исходником, ему доступны вещи, которых нет в байткоде, — имена локальных переменных, форматирование, структура кода как её видит человек. Поэтому он силён в «человеческих» проблемах: стиль, дизайн классов, code smells. SpotBugs же видит, что *реально* делает скомпилированный код, — отсюда его сила в логических багах (null, конкуренция потоков), которые на уровне исходника не очевидны.

**Вывод:** они не конкуренты, а взаимодополняющие. На практике их часто ставят вместе: PMD ловит «некрасиво написано», SpotBugs — «сломается в рантайме».

## Q15. Какие наборы правил есть в PMD для Java?

Правила PMD сгруппированы в **rulesets** по категориям — это удобно, потому что в конфиге обычно подключают не отдельные правила, а целые наборы и точечно отключают лишнее.

| Ruleset | Что проверяет |
|---------|--------------|
| `bestpractices` | Рекомендуемые практики Java (switch без default, etc.) |
| `codestyle` | Форматирование, именование |
| `design` | God classes, coupling, закон Деметры |
| `errorprone` | Потенциальные ошибки (clone, equals, etc.) |
| `multithreading` | Проблемы многопоточности |
| `performance` | Неэффективное использование коллекций, String |
| `security` | Базовые проверки безопасности |

**С чего начать:** разумный стартовый набор — `bestpractices` + `errorprone` (самые полезные и наименее спорные). `codestyle` часто конфликтует с Checkstyle/форматтером, поэтому его включают выборочно, чтобы не получать дублирующие замечания об одном и том же.

## Q16. Что такое CPD в PMD?

**CPD (Copy-Paste Detector) — встроенный в PMD инструмент поиска дублированного кода.** Это отдельная утилита внутри PMD, не связанная с обычными правилами.

**Почему он умнее простого diff.** CPD работает не по тексту, а по **токенам**: сначала превращает код в поток лексем (ключевые слова, операторы, литералы), а уже потом ищет совпадающие участки. Поэтому он **нечувствителен к переименованиям** — если скопировать метод и переименовать в нём все переменные, CPD всё равно увидит дубликат, хотя текстуально файлы различаются.

**Порог чувствительности** задаётся в токенах (`minimumTokens`). Чем ниже порог, тем больше мелких совпадений находится — и тем больше шума; стандартные 100 токенов отсекают случайные похожие конструкции.

```bash
# Запуск CPD
mvn pmd:cpd

# Порог минимального количества токенов (по умолчанию 100)
<configuration>
    <minimumTokens>50</minimumTokens>
</configuration>
```

## Q17. Что такое Checkstyle и какова его основная задача?

**Checkstyle проверяет, что код написан по принятому стилю** — и больше ничего. Это узкоспециализированный инструмент: работает с исходником, конфигурируется одним XML-файлом с описанием правил.

**Основная задача — устранить споры о стиле.** Он следит за форматированием, именованием, структурой файлов и документацией (Javadoc). Смысл в том, чтобы весь код в репозитории выглядел так, будто его писал один человек: это снижает когнитивную нагрузку на ревью и убирает с него бесполезные споры о пробелах и скобках — за этим теперь следит машина.

**Чёткая граница ответственности.** Checkstyle **намеренно не ищет баги** — он не понимает семантику программы, только её форму. Поиск дефектов — задача SpotBugs (баги) и PMD (code smells, дизайн). Их часто ставят вместе: каждый закрывает свой слой.

## Q18. Чем Sun Checks отличается от Google Checks в Checkstyle?

Это два готовых набора правил, которые поставляются с Checkstyle «из коробки». Разница между ними — это, по сути, разница между двумя историческими стилями оформления Java-кода.

| Аспект | Sun Checks | Google Checks |
|--------|-----------|---------------|
| Отступы | 4 пробела | 2 пробела |
| Длина строки | 80 символов | 100 символов |
| Фигурные скобки | Обязательны | Обязательны |
| Импорты | Strict ordering | Группировки |
| Происхождение | Java Coding Conventions | Google Java Style Guide |

**Откуда взялась разница.** Sun Checks восходят к оригинальным Java Coding Conventions от Sun Microsystems конца 90-х (4 пробела, 80 символов — наследие узких терминалов). Google Checks отражают более современный Google Java Style Guide: компактные 2 пробела и 100 символов под широкие мониторы.

**Что выбрать.** Сегодня для новых проектов чаще берут Google Checks как более актуальный и распространённый. Но конкретные цифры менее важны, чем сам факт: команда должна выбрать **один** стандарт и придерживаться его — единообразие важнее, чем 2 против 4 пробелов.

## Q19. Что такое цикломатическая сложность (Cyclomatic Complexity)?

**Цикломатическая сложность (McCabe, 1976) считает число линейно-независимых путей через код** — то есть сколько разных маршрутов выполнения есть в методе.

Формальная формула — через граф потока управления: **CC = E − N + 2P**, где E — рёбра графа, N — узлы, P — связные компоненты.

**Как считать в уме.** На собеседовании формулу с графами разворачивать не нужно — есть простое правило: **CC = 1 + количество точек ветвления**. Точки ветвления — это `if`, `while`, `for`, `case`, `&&`, `||`, `?:`, `catch`. Начинаем с 1 (один путь сквозь метод) и прибавляем по единице за каждое место, где поток может разойтись.

**Зачем метрика нужна.** Она напрямую связана с тестируемостью: CC — это нижняя граница числа тест-кейсов, нужных для покрытия всех путей. Чем выше сложность, тем больше веток надо протестировать и тем труднее держать метод в голове.

| CC | Интерпретация |
|----|--------------|
| 1–10 | Простой, хорошо тестируемый метод |
| 11–20 | Умеренная сложность, требует внимания |
| 21–50 | Высокая сложность, трудно тестировать |
| > 50 | Нетестируемый код, обязательный рефакторинг |

```java
// CC = 4: if + while + if + else
void process(List<Integer> items) {
    if (items == null) return;  // +1
    int i = 0;
    while (i < items.size()) {  // +1
        if (items.get(i) > 0) { // +1
            System.out.println(items.get(i));
        } else {                 // +1
            System.out.println("negative");
        }
        i++;
    }
}
```

**Нюанс про комментарии в примере.** Пометка `+1` напротив `else` неточна: `else` — не точка ветвления и по правилу выше ничего не добавляет (альтернативный путь уже учтён единицей за `if`). Корректный подсчёт для этого метода: 1 (база) + `if` + `while` + `if` = **4** — итог совпадает с подписью в примере, но методика именно такая. Если считать «+1 за else», на другом коде вы получите завышенный результат.

## Q20. Что такое Cognitive Complexity (SonarQube)?

**Cognitive Complexity — метрика SonarSource, измеряющая, насколько трудно человеку прочитать код.** Её автор — Дж. Энн Кэмпбелл (G. Ann Campbell, SonarSource); white paper «Cognitive Complexity: A New Way of Measuring Understandability» опубликован в 2016 году и доработан в 2017-м. Это сознательная попытка исправить главный недостаток цикломатической сложности: та считает пути, но не отражает, насколько код тяжёл для понимания.

**Проблема, которую она решает.** Для McCabe плоский `switch` на 10 веток и метод с тройной вложенностью могут дать одинаковый CC — хотя читаются они совершенно по-разному. Cognitive Complexity штрафует именно за то, что реально ломает понимание:

- **Вложенность наказывается прогрессивно** — каждый уровень вложения добавляет всё больший штраф. Условие внутри цикла внутри условия «стоит» дороже, чем три условия подряд.
- **Прыжки в потоке** — `break`/`continue` с меткой увеличивают сложность, потому что заставляют читателя «перепрыгивать».
- **Линейные цепочки `&&`/`||` считаются как 1** — в отличие от McCabe, который штрафует за каждый оператор; читать `a && b && c` не сложнее, чем одно условие.

**Когда что использовать:** цикломатическая отвечает на вопрос «сколько тестов нужно», когнитивная — «насколько больно это сопровождать». В SonarQube для порогов поддерживаемости обычно ориентируются именно на cognitive.

```java
// Cyclomatic CC = 4, но Cognitive CC выше из-за вложенности
void process(List<Item> items) {
    for (Item item : items) {          // +1
        if (item.isActive()) {         // +2 (вложено)
            if (item.hasDiscount()) {  // +3 (вложено глубже)
                applyDiscount(item);
            }
        }
    }
}
```

## Q21. Что такое метрики связности (LCOM, CBO, DIT)?

Это метрики из набора CK (Chidamber & Kemerer), оценивающие качество **дизайна классов**, а не отдельных методов. Все они формализуют один и тот же идеал ООП — **высокая связность (cohesion) внутри класса, низкое зацепление (coupling) между классами**.

| Метрика | Расшифровка | Что показывает |
|---------|-------------|---------------|
| **LCOM** | Lack of Cohesion of Methods | Насколько методы класса связаны через общие поля. Высокий LCOM → God Class или Data Class |
| **CBO** | Coupling Between Objects | Количество других классов, с которыми класс взаимодействует. Высокий CBO → хрупкость к изменениям |
| **DIT** | Depth of Inheritance Tree | Глубина иерархии наследования. DIT > 4 — признак over-engineering |
| **RFC** | Response for a Class | Количество методов, которые могут быть вызваны в ответ на сообщение классу |

**Как читать значения.** LCOM и CBO — это «чем меньше, тем лучше»: высокий LCOM означает, что класс делает несколько несвязанных вещей и его пора разбить; высокий CBO — что класс слишком от всего зависит и сломается при любом изменении соседей. DIT и RFC — про управляемость иерархии: глубокое наследование и большой отклик класса труднее тестировать и понимать.

**Оговорка для собеседования.** Это сигналы, а не приговор: высокая метрика — повод присмотреться к классу, но иногда оправдана. Слепо гнать LCOM в ноль не нужно.

## Q22. Как встроить статический анализ в CI/CD пайплайн?

**Базовый принцип — fail fast: анализ должен падать сразу и блокировать плохой код, а не висеть отчётом, который никто не читает.** Поэтому статический анализ встраивают как обязательный шаг пайплайна, а не как опциональный отчёт постфактум.

**Порядок шагов важен.** Сначала сборка и тесты с генерацией отчёта о покрытии (`jacocoTestReport`), и только потом анализаторы, — иначе SonarQube не увидит coverage. Отдельный нюанс — `fetch-depth: 0` при checkout: SonarQube нужна полная история git, чтобы по `blame` понять, какие строки относятся к «новому коду».

```yaml
# GitHub Actions пример
name: Quality Check
on: [push, pull_request]
jobs:
  analyze:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # нужно для SonarQube blame info
      - name: Build and test
        run: ./gradlew build jacocoTestReport
      - name: SonarQube Scan
        run: ./gradlew sonar
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
      - name: SpotBugs
        run: ./gradlew spotbugsMain
      - name: PMD
        run: ./gradlew pmdMain
```

**Рекомендация:** настроить merge PR так, чтобы он был заблокирован при падении Quality Gate (branch protection rule). Тогда проверка не «информирует», а реально не пускает деградацию в основную ветку — в этом и смысл fail fast.

## Q23. Что такое SonarQube PR Decoration?

**PR Decoration — это когда SonarQube пишет результаты анализа прямо в Pull Request**, как обычный комментарий, на GitHub/GitLab/Bitbucket. Анализируется только новый код PR.

**Зачем это нужно.** Без декорации разработчику пришлось бы уходить из PR в отдельный веб-интерфейс SonarQube, искать там свой анализ и сопоставлять с диффом. Decoration убирает этот разрыв контекста: замечания появляются ровно там, где идёт ревью, рядом с изменёнными строками. Обратная связь становится мгновенной и не теряется.

Что показывает прямо в PR:
- **Новые issues** — список проблем в изменённых файлах, с привязкой к строкам.
- **Статус Quality Gate** — прошёл PR проверку или нет (часто как required check, блокирующий merge).
- **Покрытие новых строк** — какие добавленные строки не покрыты тестами.

**Что требуется для настройки:** сконфигурировать ALM Integration в SonarQube (ALM — Application Lifecycle Management, то есть привязку к GitHub/GitLab) и выдать токены доступа, чтобы SonarQube мог оставлять комментарии от своего имени.

## Q24. Как обработать унаследованный код с тысячами warnings?

**Главная ошибка — пытаться исправить всё сразу.** Это нереально: остановит разработку на месяцы и сгенерирует огромные рискованные PR. Правильный подход — провести черту во времени и не давать долгу расти, разгребая старое постепенно. Ниже стратегии от системной к точечной.

1. **New Code Focus (основная)** — настроить SonarQube на анализ только нового кода (since previous version / since X days). Quality Gate применяется только к новому коду — это и есть принцип Clean as You Code: старое не трогаем, но и хуже не делаем.
2. **Baseline + ratchet («храповик»)** — зафиксировать текущее число нарушений как базовую линию (baseline) и не допускать новых сверх неё. Ratchet — это ужесточение по принципу храповика: порог двигается только вниз — как только число warnings уменьшилось, новый минимум становится новым лимитом, и откатиться назад уже нельзя.
3. **Boy Scout Rule** («оставь стоянку чище, чем нашёл») — чинить старые нарушения в тех файлах, которые и так трогаешь по текущей задаче. Долг рассасывается естественно, без отдельных «недель рефакторинга».
4. **Suppress + Document** — то, что осознанно решили не чинить, явно подавить с комментарием-обоснованием, чтобы не висело в отчётах как шум.

```java
// Осознанное подавление с пояснением
@SuppressWarnings("squid:S2095")  // SonarQube: resource leak
// Ресурс закрывается в другом месте (lifecycle управляется Spring)
private Connection connection;
```

## Q25. Как настроить suppression для false positives?

У каждого инструмента свой способ сказать «я знаю про это предупреждение и сознательно его игнорирую». Подавление делается аннотацией прямо в коде — рядом с тем местом, к которому относится.

**SonarQube** — стандартная аннотация `@SuppressWarnings` с ключом правила (`java:S...`):
```java
@SuppressWarnings("java:S1135")  // «TODO» комментарии — игнорируем намеренно
// TODO: удалить после релиза 2.0
```

**PMD** — тот же `@SuppressWarnings`, но с префиксом `PMD.` и именем правила:
```java
@SuppressWarnings("PMD.AvoidCatchingGenericException")
void process() throws Exception { ... }
```

**SpotBugs** — своя аннотация `@SuppressFBWarnings` с обязательным по смыслу полем `justification`:
```java
@SuppressFBWarnings(value = "NP_NULL_ON_SOME_PATH",
                    justification = "null проверяется выше по стеку")
void handle(String value) { ... }
```

**Главное правило — никогда не подавлять молча.** Suppression всегда сопровождается обоснованием (`justification` или комментарий): *почему* это осознанное решение, а не «лишь бы билд позеленел». Иначе через полгода никто не вспомнит, безопасно ли убрать подавление, и оно навсегда останется дырой в анализе. Подавление по-широкому (на класс или весь модуль) — антипаттерн: точечно, по одному правилу, рядом со строкой.

## Q26. Какой стек статического анализа вы бы выбрали для нового Java-проекта?

**Ключевая мысль для ответа: ни один инструмент не закрывает всё, поэтому собирают стек из взаимодополняющих слоёв.** Каждый отвечает за свой класс проблем, а SonarQube агрегирует результаты и выносит вердикт.

| Инструмент | Роль |
|------------|------|
| **SonarQube / SonarCloud** | Центральная платформа: метрики, Quality Gate, история |
| **SpotBugs + Find Security Bugs** | Поиск потенциальных багов и уязвимостей в байткоде |
| **Checkstyle** | Единый стиль кода (Google Java Style или своя конфигурация) |
| **SonarLint** (IDE) | Мгновенная обратная связь при написании кода |

Как эти слои складываются: Checkstyle закрывает стиль, SpotBugs + Find Security Bugs — рантайм-баги и уязвимости, SonarQube собирает всё вместе и держит историю/Quality Gate, а SonarLint двигает обратную связь к самому раннему моменту — в IDE, до коммита. **PMD** добавляют опционально — если нужен CPD (поиск дублей) и расширенный набор design-правил.

**Стратегия внедрения (то, что отличает хороший ответ от перечисления тулов):**
- Все анализаторы — в CI как обязательный шаг, а не ручной запуск.
- Блокировка merge при падении Quality Gate (иначе проверка декоративная).
- SonarLint у каждого в IDE — сдвиг проблем «влево», к моменту написания.
- Для легаси — Clean as You Code: gate только на новый код, старое не блокирует разработку.
