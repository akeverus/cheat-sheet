## Q1. Что такое «чистый код»? Как его определяют известные авторы?

**Чистый код** — это код, который легко читать, понимать и безопасно изменять. Не «красивый» сам по себе, а такой, что следующий разработчик (часто — ты сам через полгода) разберётся в нём без археологических раскопок.

У классиков нет единого определения, но все они сходятся на читаемости как главном критерии:

- **Роберт Мартин (Uncle Bob):** код заботится о деталях и читается как хорошо написанная проза.
- **Bjarne Stroustrup:** чистый код делает одно дело хорошо — то есть имеет чёткую, узкую ответственность.
- **Ward Cunningham:** прочитав чистый код, вы улыбаетесь и думаете: «именно так я бы и написал» — он не удивляет, не прячет логику, делает ровно то, что от него ждёшь.

**Ключевая мысль для собеседования:** код пишется один раз, а читается десятки раз — при ревью, отладке, доработке. Поэтому оптимизировать надо под чтение, а не под скорость набора. Чистота — это не перфекционизм, а инвестиция в будущую скорость команды.

## Q2. Почему чистый код важен с практической точки зрения?

Главный аргумент — деньги и скорость: грязный код не «некрасивый», он дорого обходится команде на каждой итерации. Стоимость владения кодом определяется не тем, как быстро его написали, а тем, как часто его читают и меняют.

Конкретные выгоды:

- **Скорость разработки.** Грязный код замедляет команду с каждым месяцем: чтобы внести изменение, сначала нужно потратить время на то, чтобы понять, что вообще происходит.
- **Меньше багов.** Запутанный код прячет дефекты в шуме, чистый — делает их очевидными, потому что отклонение от понятной структуры сразу бросается в глаза.
- **Быстрый onboarding.** Новый человек вникает в чистый код за дни, а не за недели — меньше «племенных знаний» нужно держать в голове.
- **Тестируемость.** Функции с одной чёткой ответственностью легко покрыть тестами изолированно, без хрупких моков половины системы.
- **Безопасный рефакторинг.** Чистый код можно менять без страха сломать что-то на другом конце системы — связность контролируема.

## Q3. Какие правила именования переменных и методов?

Главный принцип: имя должно само объяснять, что хранит переменная или что делает метод, — чтобы не приходилось искать ответ в реализации или комментариях. Хорошее имя экономит чтение десятков строк ниже.

**Переменные:**
- Имя отвечает на три вопроса: зачем существует, что хранит, как используется.
- Избегать однобуквенных имён — исключение лишь счётчики циклов `i`, `j`, где область видимости в одну строку.
- Не использовать сокращения, кроме общепринятых и однозначных (`id`, `url`, `dto`).

**Методы:**
- Метод выполняет действие, поэтому имя — глагол или глагольная фраза: `getUserById`, `calculateTax`, `isValid`.
- Длинное описательное имя всегда лучше короткого непонятного: его читают, а не печатают, а IDE дописывает автодополнением.

```java
// Плохо
int d;  // elapsed time in days?
List<int[]> theList;

// Хорошо
int elapsedTimeInDays;
List<Cell> gameBoard;
```

## Q4. Что такое «говорящие имена» и почему важно избегать сокращений?

**Говорящее имя** (intention-revealing name) — имя, из которого сразу ясно намерение, без необходимости лезть в реализацию или соседний код. Сокращения вредны, потому что переносят работу по расшифровке на каждого читателя: автор экономит несколько символов один раз, а все остальные тратят внимание каждый раз при чтении.

```java
// Сокращения создают когнитивную нагрузку
int cnt;  // count чего? заказов? ошибок?
String addr; // address? adder? admin?

// Говорящие имена — читаются как документация
int activeOrderCount;
String userEmailAddress;

// Разница в реальном коде
// Непонятно:
if (emp.seniority() > 5 && emp.type() == 1) { ... }
// Понятно:
if (employee.hasSufficientExperience() && employee.isFullTime()) { ... }
```

## Q5. Как именовать булевы переменные и методы?

Булево имя должно читаться как утверждение, которое в коде проверяют на истинность: `if (user.isActive())` звучит как естественная фраза, а `if (user.flag())` — нет. Достигается это префиксами `is`, `has`, `can`, `was`, `should` — они сразу сообщают, что значение логическое, и задают вопрос, на который true/false даёт осмысленный ответ.

- Переменные: `isActive`, `hasPermission`, `canEdit`, `wasProcessed`.
- Методы: `isEmpty()`, `isValid()`, `hasErrors()`, `canAccess()`.

Избегать отрицаний в имени (`isNotEmpty`): двойное отрицание `if (!isNotEmpty())` нечитаемо.

```java
// Плохо: неясно что значит true/false
boolean flag;
boolean status;
boolean check();

// Хорошо
boolean isEmailVerified;
boolean hasActiveSubscription;
boolean isEligibleForDiscount();
```

## Q6. Какие антипаттерны именования встречаются чаще всего?

Все они объединены одним: имя не сообщает правды о сущности либо не добавляет смысла. Читатель вынужден держать поправку в голове («тут написано List, но на самом деле Map») — это лишняя когнитивная нагрузка и источник ошибок.

| Антипаттерн | Пример | Проблема |
|-------------|--------|---------|
| Дезинформирующее имя | `accountList` (а это `Map`) | Несоответствие типу |
| Шум-слова | `theData`, `aVariable`, `InfoData` | Пустые слова не добавляют смысла |
| Числовые суффиксы | `getUser1()`, `getUser2()` | Сигнал о дублировании |
| Венгерская нотация | `strName`, `iCount` | IDE и так знает тип |
| Слишком общие | `Manager`, `Processor`, `Helper` | Нет конкретики |
| Аббревиатуры | `CustMgr`, `SvcFct` | Трудночитаемы |

## Q7. Какими должны быть функции по Роберту Мартину?

Главное правило у Мартина — **функция должна делать одно дело, делать его хорошо и только его**. Всё остальное (размер, число аргументов) — следствия этого: если функция делает ровно одну вещь, она и получается короткой, и легко называется одним глаголом.

1. **Маленькие** — умещаются на экране (ориентир: 10–20 строк). Маленькую функцию видно целиком, без прокрутки и удержания контекста в голове.
2. **Делают одно** — если метод можно осмысленно разбить на более мелкие с говорящими именами, значит он делал несколько вещей.
3. **Один уровень абстракции** — не мешать «что делаем» (высокий уровень) с «как именно» (детали реализации) в одном теле.
4. **Минимум аргументов** — идеал 0–2; три — нежелательно; четыре и больше — сигнал собрать их в Parameter Object.
5. **Без неожиданных side effects** — функция `checkPassword` не должна попутно инициализировать сессию: скрытый эффект ломает ожидания вызывающего кода.
6. **Не повторяют себя** — общая логика выносится, а не копируется (DRY).

```java
// Нарушение: один метод делает несколько вещей
void processUserRegistration(String email, String password) {
    // валидация
    if (!email.contains("@")) throw new InvalidEmailException();
    if (password.length() < 8) throw new WeakPasswordException();
    // сохранение
    User user = new User(email, hashPassword(password));
    userRepo.save(user);
    // уведомление
    emailService.sendWelcome(email);
    // аудит
    auditLog.record("User registered: " + email);
}

// Лучше: разбить на шаги
void processUserRegistration(String email, String password) {
    validateCredentials(email, password);
    User user = createUser(email, password);
    notifyUser(user);
    auditRegistration(user);
}
```

## Q8. Что такое уровень абстракции метода и почему его нужно выдерживать?

**Уровень абстракции** — это «высота полёта» кода: высокий уровень отвечает на вопрос *что* делаем (`getCompletedOrders()`), низкий — *как именно* (фильтр по статусу через stream, форматирование строки). Внутри одной функции все операции должны быть примерно на одной высоте.

Почему это важно: смешав уровни, мы заставляем читателя постоянно прыгать между «бизнес-смыслом» и «технической мелочью». Глаз спотыкается, общую логику метода уже не видно за деталями. Когда уровни выдержаны, тело функции читается как оглавление: список шагов одного масштаба, а детали спрятаны в методах-помощниках.

```java
// Нарушение: смешение уровней
void prepareReport() {
    // Высокий уровень
    List<Order> orders = getOrders();
    // Низкий уровень (детали SQL-like логики)
    orders.stream()
          .filter(o -> o.getStatus().equals("COMPLETED") && o.getTotal().compareTo(BigDecimal.ZERO) > 0)
          .forEach(o -> System.out.println(o.getId() + "," + o.getTotal()));
}

// Хорошо: единый уровень абстракции
void prepareReport() {
    List<Order> completedOrders = getCompletedOrders();
    printOrdersCsv(completedOrders);
}
```

## Q9. Что такое Command Query Separation (CQS)?

**CQS** (принцип Бертрана Мейера): метод должен быть либо **командой**, либо **запросом**, но не тем и другим сразу.

- **Команда** изменяет состояние и ничего не возвращает (`void`).
- **Запрос** возвращает данные и не имеет побочных эффектов — его можно вызвать сколько угодно раз без последствий.

Зачем разделять: если запрос незаметно меняет состояние, вызывающий код перестаёт быть предсказуемым. Строка `if (getValue())` выглядит безобидной проверкой, но если `getValue` ещё и инкрементирует счётчик — вы получаете баги, которые «не должны были случиться». Чистое разделение делает запросы безопасными для свободного использования (в логах, ассертах, отладчике).

```java
// Нарушение CQS: метод одновременно изменяет и возвращает
int incrementAndGet(Counter counter) {
    counter.increment();  // side effect
    return counter.getValue();  // query
}

// Соблюдение CQS
void increment(Counter counter) { counter.increment(); }  // command
int getValue(Counter counter) { return counter.getValue(); }  // query
```

**Компромисс:** `Stack.pop()` и `Queue.poll()` намеренно нарушают CQS (изменяют структуру и возвращают элемент) — здесь атомарность «достать и удалить» важнее чистоты принципа. CQS — ориентир, а не догма.

## Q10. Почему флаги-параметры (boolean flag) — плохая практика?

Булев параметр почти всегда означает, что внутри функции стоит `if (flag) { ... } else { ... }` — то есть функция делает два разных дела в зависимости от значения. Это прямое нарушение правила «одна функция — одна задача».

Вторая беда — читаемость места вызова. В строке `render(true)` непонятно, что значит `true`: чтобы узнать, нужно открыть сигнатуру метода. Имя параметра видит автор, но не читатель вызова. Лекарство — два метода с говорящими именами либо `enum`, который проговаривает смысл прямо в точке вызова.

```java
// Плохо: что значит true/false без контекста?
render(true);
renderHtml(false);

// Хорошо: два разных метода
renderForMobile();
renderForDesktop();

// Или через enum
render(RenderMode.MOBILE);
render(RenderMode.DESKTOP);
```

## Q11. Что такое принцип единственной ответственности (SRP)?

**SRP (Single Responsibility Principle):** у класса должна быть только **одна причина для изменения**.

«Ответственность» здесь — это не «делает одно дело», а «обслуживает одного заказчика изменений». Мартин формулирует точнее: у модуля должен быть один и только один актор (stakeholder), ради которого его меняют. В примере ниже класс `Employee` трогают трое разных людей по трём разным поводам — финансист меняет формулу зарплаты, DBA меняет схему хранения, HR меняет формат отчёта. Любая правка одного риском задевает остальных. Это и есть «несколько причин для изменения», которые SRP велит разнести.

```java
// Нарушение: класс изменяется при изменении бизнес-правил, БД-схемы, формата отчёта
class Employee {
    void calculatePay() { ... }    // финансовый отдел
    void saveToDatabase() { ... }  // DBA
    void generateReport() { ... }  // HR
}

// Соблюдение: три класса, три причины изменения
class PayrollCalculator { void calculatePay(Employee e) { ... } }
class EmployeeRepository { void save(Employee e) { ... } }
class EmployeeReportGenerator { void generate(Employee e) { ... } }
```

## Q12. Что такое принцип открытости/закрытости (OCP)?

**OCP (Open/Closed Principle):** код должен быть **открыт для расширения**, но **закрыт для модификации** — новое поведение добавляется без правки уже работающего, протестированного кода.

Идея: каждое изменение проверенного класса — это риск внести регрессию и повод перепроверять всё, что от него зависит. Если же точки роста заложены через абстракцию (интерфейс, стратегию), то новая фича — это новый класс рядом, а старый остаётся нетронутым. Практический маркёр нарушения OCP — растущий `switch`/`if-else` по типу, который правят при каждом новом варианте (см. пример). Лекарство — полиморфизм: вынести варианты за интерфейс.

```java
// Нарушение: каждый новый тип скидки требует изменения метода
BigDecimal calculateDiscount(Order order, String discountType) {
    return switch (discountType) {
        case "SEASONAL" -> order.getTotal().multiply(new BigDecimal("0.10"));
        case "LOYALTY" -> order.getTotal().multiply(new BigDecimal("0.15"));
        // при добавлении нового типа — правим этот метод
        default -> BigDecimal.ZERO;
    };
}

// Соблюдение OCP: новый тип скидки — новый класс, старый код не трогаем
interface DiscountStrategy {
    BigDecimal calculate(Order order);
}
class SeasonalDiscount implements DiscountStrategy { ... }
class LoyaltyDiscount implements DiscountStrategy { ... }
```

## Q13. Что такое принцип подстановки Лисков (LSP)?

**LSP (Liskov Substitution Principle):** объект подтипа можно подставить вместо объекта базового типа, и программа продолжит работать корректно. Иными словами, наследник обязан соблюдать контракт предка, а не просто иметь те же методы.

Подкласс нарушает LSP, когда:
- **ужесточает предусловия** — требует больше, чем базовый тип (например, не принимает значения, которые предок принимал);
- **ослабляет постусловия** — гарантирует меньше, чем обещал предок;
- **бросает исключения**, которых клиент базового типа не ожидает.

Классический контрпример — `Square extends Rectangle` (ниже). Наследование «есть-разновидность» формально верно (квадрат — это прямоугольник), но поведенчески ломается: код, рассчитанный на независимые ширину и высоту, при подстановке квадрата получает неверную площадь. Вывод: LSP про поведение, а не про иерархию классов; «is-a» в геометрии не равно «is-a» в коде.

```java
// Нарушение LSP: Square ведёт себя не как Rectangle
class Rectangle {
    void setWidth(int w) { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {
    @Override
    void setWidth(int w) { this.width = w; this.height = w; }  // неожиданный side effect
    @Override
    void setHeight(int h) { this.height = h; this.width = h; }
}

// Код, работающий с Rectangle, ломается при подстановке Square
void testArea(Rectangle r) {
    r.setWidth(5); r.setHeight(4);
    assert r.area() == 20;  // для Square вернёт 16!
}
```

## Q14. Что такое принцип разделения интерфейсов (ISP)?

**ISP (Interface Segregation Principle):** клиент не должен зависеть от методов, которыми не пользуется. Много узких, ролевых интерфейсов лучше одного «толстого».

Проблема толстого интерфейса в том, что он навязывает лишнее. Если в `Worker` входят `work()`, `eat()`, `sleep()`, то `Robot`, которому нужен только `work()`, вынужден реализовать `eat()` и `sleep()` заглушками с `UnsupportedOperationException` (см. пример). Это ложь в контракте: тип объявляет умения, которых у него нет. Плюс лишняя связность — изменение `eat()` затрагивает классы, которым еда вообще не нужна. Разбив интерфейс на роли (`Workable`, `Eatable`), каждый класс реализует ровно то, что умеет.

```java
// Нарушение ISP: интерфейс слишком широк
interface Worker {
    void work();
    void eat();
    void sleep();
}

// Робот реализует Worker, но не ест и не спит — вынужден имплементировать пустые методы
class Robot implements Worker {
    public void work() { ... }
    public void eat() { throw new UnsupportedOperationException(); }
    public void sleep() { throw new UnsupportedOperationException(); }
}

// Соблюдение ISP: разбить на роли
interface Workable { void work(); }
interface Eatable { void eat(); }
class Human implements Workable, Eatable { ... }
class Robot implements Workable { ... }
```

## Q15. Что такое принцип инверсии зависимостей (DIP)?

**DIP (Dependency Inversion Principle):**

- Модули высокого уровня не должны зависеть от модулей низкого уровня — оба зависят от **абстракций**.
- Абстракции не зависят от деталей; детали зависят от абстракций.

«Инверсия» — потому что переворачивается естественное направление зависимости. Обычно бизнес-логика напрямую тянет за собой конкретный класс (`new MySqlOrderRepository()`), и тогда смена БД заставляет переписывать саму логику. DIP вставляет между ними интерфейс: `OrderService` знает только про `OrderRepository`, а конкретную реализацию ему передают снаружи. Теперь высокоуровневая логика диктует контракт, а низкоуровневые детали подстраиваются под него.

```java
// Нарушение DIP: high-level зависит от конкретного класса
class OrderService {
    private MySqlOrderRepository repository = new MySqlOrderRepository();  // конкретика
}

// Соблюдение DIP: зависимость через интерфейс + DI
class OrderService {
    private final OrderRepository repository;  // абстракция

    OrderService(OrderRepository repository) {  // DI через конструктор
        this.repository = repository;
    }
}
```

Именно DIP делает возможными Dependency Injection и инверсию управления (IoC): контейнер подставляет нужную реализацию в конструктор, а в тестах вместо неё легко передать мок.

## Q16. Что такое DRY (Don't Repeat Yourself)?

**DRY** (Эндрю Хант, Дэвид Томас, «Pragmatic Programmer»): каждый фрагмент знания должен иметь единственное, однозначное, авторитетное представление в системе.

Ключевое слово — **знание**, а не код. DRY борется не с похожими строками, а с дублированием смысла: если одно бизнес-правило (ставка скидки, формула налога, формат даты) записано в нескольких местах, то при изменении нужно вспомнить и синхронно поправить все копии. Пропустишь одну — получишь рассогласование, которое всплывёт багом в проде. Лекарство — единственный источник истины (single source of truth): правило живёт в одном месте, остальные на него ссылаются.

```java
// Нарушение DRY: константа скидки задублирована
class OrderService {
    BigDecimal discount = order.getTotal().multiply(new BigDecimal("0.10"));
}
class CartService {
    BigDecimal discount = price.multiply(new BigDecimal("0.10")); // дублирование знания
}

// DRY: единственный источник истины
class DiscountPolicy {
    static final BigDecimal STANDARD_RATE = new BigDecimal("0.10");
}
```

## Q17. Что такое KISS (Keep It Simple, Stupid)?

**KISS:** из двух решающих задачу вариантов выбирай более простой. Сложность вводят только тогда, когда она оправдана реальной потребностью, а не «на всякий случай» или ради демонстрации навыков.

Почему: сложность не бесплатна — её сопровождают, отлаживают и объясняют новичкам. Лишний паттерн или хитрый однострочник экономят пару строк автору, но добавляют работы всем, кто потом будет это читать. Простой код проще проверить на корректность глазами.

**Подводные камни** (типичные нарушения KISS):
- Паттерны там, где хватило бы прямого кода.
- Преждевременные абстракции «под будущее, которое не наступит».
- «Умные» однострочники, экономящие строки ценой читаемости.

```java
// Нарушение KISS: «умно», но нечитаемо
int result = IntStream.range(0, n)
    .reduce(1, (acc, i) -> acc * (i + 1));

// KISS: просто и понятно
int factorial = 1;
for (int i = 2; i <= n; i++) {
    factorial *= i;
}
```

## Q18. Что такое YAGNI (You Aren't Gonna Need It)?

**YAGNI** (из экстремального программирования, Кент Бек): не добавляй функциональность, пока она реально не понадобилась. Не «может пригодится», а «нужна прямо сейчас под текущую задачу».

Идея в том, что предсказания о будущем чаще всего не сбываются. Код, написанный «на вырост», обычно либо никогда не используется, либо к моменту нужды требования оказываются другими — и заготовку всё равно переписывают. А пока она просто висит мёртвым грузом: её нужно поддерживать, тестировать и понимать при чтении.

**Подводные камни** (типичные нарушения YAGNI):
- «Сделаю параметром на случай будущего» — параметр, у которого всегда одно значение.
- Абстрактный базовый класс с единственным наследником.
- Флаги конфигурации, которые никто никогда не переключит.

**Связь с XP:** в agile с короткими итерациями дешевле добавить функцию ровно тогда, когда она потребуется, чем годами тащить и поддерживать ненужную.

## Q19. Когда DRY нарушается оправданно?

DRY — принцип, а не закон: иногда небольшое дублирование дешевле, чем неправильная абстракция. Главный критерий — дублируется ли *знание* или только внешняя форма кода. Если два фрагмента похожи случайно и меняются по разным причинам, объединять их вредно.

**Когда дублирование оправдано:**

- **Случайное сходство (false DRY).** Два фрагмента выглядят одинаково сейчас, но завязаны на разные требования. Слияние создаст ложную связность — правка под один контекст сломает другой.
- **Разные ограниченные контексты.** Валидация в domain-слое и в UI похожа, но живёт раздельно намеренно: у них разные причины меняться (бизнес-правила vs UX).
- **Читаемость.** Иногда инлайн-код понятнее, чем вызов утилиты ради единственной строки, спрятанной за абстракцией.

**Эмпирическое правило (Rule of Three, Мартин Фаулер):** первое дублирование — терпим, второе — берём на заметку, третье — пора выносить общий код. К третьему разу уже видно, что́ действительно общее, а что совпало случайно.

## Q20. Когда комментарии в коде уместны, а когда вредны?

Базовый принцип Мартина: комментарий — это признак того, что код не сумел объяснить себя сам. Хороший комментарий говорит **почему**, а не **что**: «что» должно быть видно из самого кода. Главная же опасность комментариев — они не компилируются и не тестируются, поэтому со временем расходятся с кодом и начинают врать.

**Уместные комментарии** — объясняют то, чего в коде не видно:
- **«Почему»** — бизнес-ограничение, причина нестандартного решения, ссылка на тикет.
- **TODO** с конкретным контекстом (что и почему отложено).
- **Javadoc** для публичного API — контракт для внешних потребителей.
- **Предупреждение** о неочевидных последствиях изменения.

**Вредные комментарии** — шум или ложь:
- Пересказ «что» делает очевидный код (`i++; // increment i`).
- Закомментированный код — для истории есть git, а мёртвый блок только путает.
- Устаревшие комментарии, противоречащие коду, — хуже отсутствия.
- Шум-метки: `// constructor`, `// getters`.

```java
// Вредный комментарий: объясняет очевидное
i++; // increment i

// Вредный: закомментированный код
// oldMethod(param1, param2);

// Полезный: объясняет «почему»
// Округляем вниз — требование банка, см. ticket JIRA-1234
BigDecimal amount = total.setScale(2, RoundingMode.FLOOR);
```

## Q21. Что такое «самодокументируемый код»?

Это код, написанный настолько выразительно, что пояснительные комментарии не нужны: намерение читается прямо из имён и структуры. Идея напрямую продолжает Q20 — вместо того чтобы комментарием объяснять непонятный код, лучше сделать сам код понятным. Тогда нечему устаревать и расходиться с реализацией.

**Инструменты самодокументирования:**
- Говорящие имена переменных и методов — имя несёт смысл вместо комментария.
- Выделение намерения в отдельный метод с говорящим именем (`hasEnoughPointsForPurchase()` вместо голого условия).
- Именованные константы вместо магических чисел — `MIN_POINTS_FOR_PURCHASE` объясняет, откуда взялось `100`.
- Value Objects вместо примитивов — тип `Email` сам гарантирует и документирует смысл значения.

```java
// Требует комментария
// Проверяем, достаточно ли у пользователя баллов для покупки (нужно >= 100)
if (user.points >= 100) { ... }

// Самодокументируется
if (user.hasEnoughPointsForPurchase()) { ... }
// или
static final int MIN_POINTS_FOR_PURCHASE = 100;
if (user.getPoints() >= MIN_POINTS_FOR_PURCHASE) { ... }
```

## Q22. Почему форматирование кода важно для читаемости?

Как формулирует Мартин Фаулер, форматирование — это коммуникация: визуальная структура кода передаёт смысл ещё до того, как читатель вник в логику. Пустая строка говорит «здесь заканчивается одна мысль», отступ — «это вложено в то». Глаз считывает форму быстрее, чем разбирает текст.

- **Консистентность снижает когнитивную нагрузку.** Если стиль одинаков во всём проекте, не нужно подстраиваться под каждый файл — мозг тратит силы на логику, а не на формат.
- **Форматирование = структура.** Пустые строки разделяют смысловые блоки, отступы показывают вложенность; код, слепленный в одну строку, нечитаем именно потому, что структура спрятана.
- **Это автоматизируется.** Google Java Format, Checkstyle, форматтеры IDE приводят код к единому виду машинально — и тогда стиль перестаёт быть темой для споров на code review.

```java
// Плохо: всё слеплено
class OrderProcessor{void process(Order o){validate(o);save(o);notify(o);}}

// Хорошо: пространство делает структуру очевидной
class OrderProcessor {

    void process(Order order) {
        validate(order);
        save(order);
        notify(order);
    }
}
```

## Q23. Что такое «вертикальная плотность» и «вертикальное расстояние» в Clean Code?

Оба понятия — про размещение кода *по вертикали*: близость на экране Мартин использует как сигнал о связи. Чем теснее строки, тем сильнее читатель воспринимает их как одну мысль.

- **Вертикальная плотность:** тесно связанные строки держат рядом. Объявление переменной не отрывают от её использования посторонним кодом — иначе читателю приходится держать значение в голове и сканировать вверх-вниз.
- **Вертикальное расстояние:** наоборот, несвязанные концепции разделяют пустыми строками, а функции разного уровня располагают в разных частях класса. Пустая строка здесь — граница смыслового блока.

Короче: близко = связано, далеко = разное. Расположение кода должно подтверждать эту интуицию, а не противоречить ей.

```java
// Плохо: объявление и использование разделены несвязанным кодом
int timeout = 5000;
String endpoint = buildEndpoint();
log.debug("Connecting...");
int retries = 3;
connect(endpoint, timeout, retries);  // timeout и retries далеко от connect

// Хорошо: связанное — рядом
String endpoint = buildEndpoint();
int timeout = 5000;
int retries = 3;
connect(endpoint, timeout, retries);
```

## Q24. Как правильно обрабатывать ошибки в духе Clean Code?

Главная мысль Мартина: обработка ошибок не должна загораживать основную логику. Когда успешный путь утопает в проверках `if (result == -1)`, читать код невозможно — поэтому ошибки выносят на отдельный «канал» исключений, а happy path остаётся чистым.

- **Исключения вместо кодов ошибок.** Коды ошибок заставляют проверять результат после каждого вызова и плодят if-else; исключение поднимается само и не засоряет основной поток.
- **Не подавлять исключения.** Пустой `catch` хуже падения: программа продолжает работать в сломанном состоянии, а причину уже не найти. Минимум — залогировать.
- **Не возвращать null.** Вместо null — `Optional`, исключение или пустая коллекция (подробно в Q25).
- **Информативные сообщения.** Исключение должно нести контекст операции (что, над чем, с каким ID не получилось), иначе по логу невозможно понять, что произошло.

```java
// Плохо: подавление исключения
try {
    processOrder(order);
} catch (Exception e) {
    // игнорируем
}

// Плохо: код ошибки
int result = processOrder(order);
if (result == -1) { ... }

// Хорошо: специфическое исключение с контекстом
try {
    processOrder(order);
} catch (PaymentFailedException e) {
    log.error("Payment failed for order {}: {}", order.getId(), e.getMessage());
    throw new OrderProcessingException("Cannot process order " + order.getId(), e);
}
```

## Q25. Почему возврат null — плохая практика?

Коротко: null перекладывает ответственность за обработку «пустого» случая на вызывающего и ничего не сообщает о его смысле. Сигнатура `User findUser(Long id)` молчит о том, что результат может отсутствовать, — компилятор не напомнит, и проверку легко забыть.

Конкретные проблемы:

- **Заражает вызывающий код.** Каждый, кто пользуется методом, обязан вставлять `!= null` — забыл хоть раз, и ловишь `NullPointerException` в рантайме, а не на компиляции.
- **Не несёт семантики.** Что значит вернувшийся null — «не найдено», «ошибка», «ещё не инициализировано»? Тип `User` об этом молчит.

**Альтернативы — выбирай по смыслу отсутствия:**
- `Optional<T>` — когда «может не быть» это нормальный исход; тип в сигнатуре сам заставляет обработать пустой случай.
- Пустая коллекция (`Collections.emptyList()`) вместо null-коллекции — по ней безопасно итерироваться без проверок.
- Null Object Pattern — объект-заглушка с безопасным поведением по умолчанию.
- Специфическое исключение — когда отсутствие это нештатная ситуация, а не ожидаемый результат.

```java
// Плохо
User findUser(Long id) {
    return userMap.get(id);  // null если не найдено
}

// Хорошо: явная семантика
Optional<User> findUser(Long id) {
    return Optional.ofNullable(userMap.get(id));
}

// Использование
findUser(id)
    .map(User::getEmail)
    .orElse("unknown@example.com");
```

## Q26. Что такое Boy Scout Rule в контексте Clean Code?

**Boy Scout Rule** (Роберт Мартин, по аналогии с правилом бойскаутов): «оставь лагерь чище, чем нашёл». Применительно к коду — каждый раз, когда трогаешь файл, оставляй его чуть лучше, чем он был.

Суть приёма — в том, что качество поддерживается непрерывно и малыми порциями, а не разовым героическим рефакторингом. Достаточно мелочи в рамках текущей задачи: переименовать невнятную переменную, вынести разросшийся метод, удалить мёртвый код. Каждое улучшение крошечное и почти не несёт риска, но если так делает вся команда на каждом PR, кодовая база со временем деградирует не вниз, а вверх — энтропия не накапливается.

## Q27. Как балансировать чистоту кода и сроки (deadline)?

Честный ответ для собеседования: **грязный код под дедлайном — ложная экономия**. Время, выигранное на спешке, возвращается с процентами на следующих итерациях.

Почему это так:
- Грязный код замедляет каждую следующую задачу — команда платит «процентами» по техническому долгу, и платёж растёт.
- С опытом писать чисто почти не дольше, чем грязно: это привычка, а не отдельный этап «уборки».
- Если давление реальное — оформить долг явно: завести задачу и положить в бэклог, а не делать вид, что долга нет. Осознанный долг управляем, скрытый — нет.

**Практический баланс** — соизмерять усилия с ценностью:
- Не доводить до идеала то, что достаточно сделать хорошо.
- Не делать хорошо то, что вообще не нужно делать (YAGNI).
- Применять Boy Scout Rule — дешёвые улучшения без риска прямо по ходу работы.
- На серьёзный накопленный долг — отдельная задача на рефакторинг после дедлайна.
