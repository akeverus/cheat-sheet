## Q1. Что такое code coverage и зачем его измерять?

**Code coverage** — метрика, которая показывает, какой процент кода был фактически выполнен во время прогона тестов. Инструмент следит, какие строки, ветки и методы «затронул» хоть один тест, и считает их долю от общего объёма.

Зачем измерять:
- **Находит слепые пятна.** Непокрытые ветки — это код, который ни один тест ни разу не выполнил, то есть потенциально незащищённый от регрессий.
- **Даёт обратную связь о полноте тестов.** Видно, дописал ли разработчик тесты к новой логике или забыл.
- **Задаёт порог качества в CI.** Можно блокировать merge, если покрытие упало ниже установленной планки.

**Главный нюанс.** Coverage отвечает только на вопрос «был ли код выполнен», но не «работает ли он правильно». Тест может прогнать строку без единого `assert` — покрытие вырастет, а проверки поведения не появится. Поэтому высокий coverage ≠ хорошие тесты: это необходимое, но не достаточное условие.

## Q2. Какие виды coverage существуют?

Виды coverage отличаются тем, насколько мелкую единицу кода они считают «покрытой» — от грубой (строка) до самой строгой (все пути выполнения). Чем мельче единица, тем точнее метрика отражает реальную проверку логики.

| Вид | Что считается | Строгость |
|-----|--------------|-----------|
| **Statement/Line** | Выполненные строки или инструкции | низкая |
| **Branch** | Обе ветви каждого условного оператора (true/false для `if`) | средняя |
| **Condition** | Каждое булево подвыражение внутри условия | высокая |
| **Path** | Все возможные пути выполнения (число растёт экспоненциально) | максимальная, на практике недостижима |
| **Method** | Вызванные методы | низкая |
| **Class** | Инстанцированные классы | низкая |
| **Mutation** | Доля «убитых» мутаций (требует mutation testing) | проверяет качество, а не объём |

**На практике.** JaCoCo по умолчанию считает instruction, branch, line, method, class и cyclomatic complexity. Большинство команд ориентируются на line и branch coverage: первый — для быстрого обзора, второй — как более честный показатель, что условия действительно проверены.

## Q3. Что такое line coverage?

**Line coverage** (покрытие строк) — доля строк, которые выполнил хотя бы один тест: `выполненные строки / общее число строк × 100%`.

Это самая понятная метрика, но и самая слабая. Слабость в том, что одна строка может скрывать несколько ветвлений, а line coverage засчитает её целиком, как только она выполнилась хоть раз — даже если проверена лишь одна из веток:

```java
// Одна строка — но две ветки: true и false
String result = value != null ? value.toUpperCase() : "default";
// line coverage = 100%, если строка выполнена хоть раз
// branch coverage = 50%, если value всегда != null
```

## Q4. Что такое branch coverage и чем он важнее line coverage?

**Branch coverage** проверяет, выполнены ли обе ветки каждого условного оператора — и true, и false. Именно поэтому он строже line coverage: чтобы засчитать `if`, недостаточно один раз войти в него, нужно прогнать оба исхода.

```java
void process(Order order) {
    if (order.isPaid()) {      // две ветки: paid и not paid
        ship(order);
    } else {
        notifyUnpaid(order);
    }
}

// Тест только с paid=true: line coverage = 100%, branch coverage = 50%
```

**Почему это важнее.** Один тест с `order.isPaid() == true` выполнит все строки метода (line coverage = 100%), но ветка `else` с `notifyUnpaid` останется непроверенной (branch coverage = 50%). Именно в таких пропущенных ветках чаще всего и живут баги. SonarQube и JaCoCo показывают branch coverage отдельной колонкой — смотреть стоит в первую очередь на него.

## Q5. Что такое statement coverage vs line coverage?

Разница между ними проявляется только тогда, когда на одной строке стоит несколько инструкций.

- **Statement coverage** — единица измерения это инструкция (statement); покрытие достигнуто, когда каждая инструкция выполнена хотя бы раз.
- **Line coverage** — единица это строка исходника; покрытие достигнуто, когда каждая строка выполнена хотя бы раз.

Если на строке три инструкции, а тест дошёл только до первой (например, вторая бросила исключение), line coverage засчитает строку как покрытую, а statement coverage — только треть. Поэтому statement точнее:

```java
int a = 1; int b = 2; int c = a + b;  // 3 statements, 1 line
```

**На практике.** JaCoCo не считает строки и инструкции исходника напрямую — он работает с байткодом и оперирует понятием **instruction coverage** (одна JVM-инструкция), что по смыслу близко к statement coverage и точнее, чем line coverage.

## Q6. Какой процент coverage считается хорошим?

Универсального числа нет — всё зависит от контекста. Гнаться за единой цифрой по всему проекту бессмысленно: критическая бизнес-логика и DTO-классы требуют совершенно разного уровня внимания. Разумнее задавать планку по типу кода:

| Контекст | Рекомендуемый coverage |
|----------|----------------------|
| Критическая бизнес-логика | 90%+ branch coverage |
| Обычный сервисный код | 70–80% |
| Утилиты, helper-классы | 80%+ |
| DTO, конфигурация | исключить из подсчёта |
| Интеграционный слой (контроллеры) | важнее интеграционные тесты, чем процент |

**Ориентир.** Quality Gate Sonar Way в SonarQube требует ≥ 80% coverage на **новом** коде. Это удачный компромисс: вы не заставляете команду покрывать унаследованный код задним числом, но новый код приходит уже с тестами.

## Q7. Что такое JaCoCo и как он работает?

**JaCoCo** (Java Code Coverage) — де-факто стандарт измерения покрытия в Java-проектах.

В основе лежит **инструментация байткода**: JaCoCo не анализирует исходники, а вставляет в скомпилированные классы счётчики-«пробы» и по ним понимает, какой код выполнился. Полный цикл:

1. JaCoCo инструментирует байткод — вставляет probe-инструкции в каждую ветку.
2. Во время прогона тестов эти пробы фиксируют, какие участки выполнились.
3. По завершении собранные данные сбрасываются в бинарный файл `.exec`.
4. Из `.exec` генерируются человекочитаемые отчёты — XML (для SonarQube), HTML (для людей), CSV.

**Два режима инструментирования:**
- **On-the-fly** (через Java Agent) — пробы добавляются в момент загрузки классов, файлы на диске не меняются. Режим по умолчанию, ничего настраивать не нужно.
- **Offline** — классы инструментируются заранее, до запуска. Нужен в нестандартных окружениях, где Java Agent не подключить (например, особые контейнеры или фреймворки со своим загрузчиком классов).

## Q8. Как настроить JaCoCo в Maven/Gradle?

Идея одинакова в обоих сборщиках: сначала подключить агент JaCoCo к запуску тестов (он соберёт данные покрытия), затем сгенерировать отчёт.

**Maven.** Цель `prepare-agent` подключает Java Agent к тестам, а `report` на фазе `verify` строит отчёт из `.exec`:
```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.11</version>
    <executions>
        <execution>
            <id>prepare-agent</id>
            <goals><goal>prepare-agent</goal></goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>verify</phase>
            <goals><goal>report</goal></goals>
        </execution>
    </executions>
</plugin>
```

**Gradle.** Плагин `jacoco` подключается одной строкой; `finalizedBy` гарантирует, что отчёт строится сразу после тестов. XML-отчёт обязателен, если данные пойдут в SonarQube:
```groovy
plugins {
    id 'jacoco'
}
test {
    finalizedBy jacocoTestReport
}
jacocoTestReport {
    dependsOn test
    reports {
        xml.required = true  // нужен для SonarQube
        html.required = true
    }
}
```

## Q9. Как настроить minimum coverage threshold в JaCoCo?

Порог задаётся через цель `check`: если покрытие опустится ниже минимума, сборка падает — это и превращает coverage в обязательное условие, а не просто справочную цифру. Можно задавать отдельные лимиты на разные счётчики (`LINE`, `BRANCH`) и разный уровень агрегации (`BUNDLE` — весь проект, `CLASS`, `METHOD`).

```xml
<!-- Maven: check goal с правилами -->
<execution>
    <id>check</id>
    <goals><goal>check</goal></goals>
    <configuration>
        <rules>
            <rule>
                <element>BUNDLE</element>
                <limits>
                    <limit>
                        <counter>LINE</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.80</minimum>
                    </limit>
                    <limit>
                        <counter>BRANCH</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.70</minimum>
                    </limit>
                </limits>
            </rule>
        </rules>
    </configuration>
</execution>
```

**Gradle:**
```groovy
jacocoTestCoverageVerification {
    violationRules {
        rule {
            limit {
                counter = 'LINE'
                value = 'COVEREDRATIO'
                minimum = 0.80
            }
        }
    }
}
```

## Q10. Как исключить классы из подсчёта coverage в JaCoCo?

Исключения задаются паттернами путей к классам. Из подсчёта обычно убирают код, который тестировать бессмысленно: DTO без логики, сгенерированный код, конфигурационные классы, `main`-методы. Если их оставить, метрика искусственно занижается, и команда тратит силы на «покрытие» геттеров вместо реальной логики.

```xml
<!-- Maven exclusions -->
<configuration>
    <excludes>
        <exclude>**/dto/**</exclude>
        <exclude>**/config/**</exclude>
        <exclude>**/*Application.class</exclude>
        <exclude>**/generated/**</exclude>
    </excludes>
</configuration>
```

```groovy
// Gradle
jacocoTestReport {
    afterEvaluate {
        classDirectories.setFrom(files(classDirectories.files.collect {
            fileTree(dir: it, exclude: [
                '**/dto/**',
                '**/config/**',
                '**/*Application*'
            ])
        }))
    }
}
```

## Q11. Как JaCoCo интегрируется с SonarQube?

SonarQube сам coverage не считает — он читает готовый XML-отчёт JaCoCo. Поэтому интеграция сводится к двум шагам:

1. Настроить JaCoCo на генерацию отчёта именно в формате XML (HTML SonarQube не понимает).
2. Передать путь к этому XML через свойство `sonar.coverage.jacoco.xmlReportPaths`.

```xml
<!-- Maven: путь по умолчанию - target/site/jacoco/jacoco.xml -->
<sonar.coverage.jacoco.xmlReportPaths>
    ${project.build.directory}/site/jacoco/jacoco.xml
</sonar.coverage.jacoco.xmlReportPaths>
```

**Подводный камень.** В многомодульном проекте одного XML мало: SonarQube увидит покрытие только того модуля, чей отчёт ему дали. Нужно либо собрать агрегированный отчёт (`report-aggregate`), либо перечислить пути к отчётам каждого модуля.

## Q12. Что такое mutation testing?

**Mutation testing** — методика проверки качества самих тестов: инструмент намеренно вносит в код мелкие ошибки (мутации) и смотрит, заметят ли их тесты. Идея простая: если в код внести баг, а тесты остаются зелёными — значит, эти тесты бесполезны.

Как это работает:
1. Инструмент создаёт «мутанты» — копии кода с одним маленьким изменением (например, `>` заменён на `>=`).
2. Прогоняет существующие тесты против каждого мутанта.
3. Если хотя бы один тест упал — мутант **«убит»**, тесты заметили подмену (это хорошо).
4. Если все тесты прошли — мутант **«выжил»**, тесты не отличили испорченный код от исходного (это плохо).

**В чём ценность.** Обычный coverage отвечает «был ли код выполнен», а mutation testing — «а проверяет ли тест поведение этого кода». Это единственная метрика, которая ловит тесты без осмысленных assertions: строка покрыта, но мутант выживает.

## Q13. Как работает PIT (Pitest)?

**PIT (Pitest)** — самый популярный инструмент mutation testing для Java. Он работает быстрее наивной реализации за счёт двух оптимизаций: мутирует байткод (не нужно перекомпилировать исходники) и для каждого мутанта запускает только те тесты, что покрывают изменённую строку.

В конфигурации указывают, какие классы мутировать (`targetClasses`), какими тестами их проверять (`targetTests`) и минимальный порог mutation score (`mutationThreshold`), ниже которого сборка падает:

```xml
<!-- Maven -->
<plugin>
    <groupId>org.pitest</groupId>
    <artifactId>pitest-maven</artifactId>
    <version>1.15.3</version>
    <configuration>
        <targetClasses>
            <param>com.example.service.*</param>
        </targetClasses>
        <targetTests>
            <param>com.example.service.*Test</param>
        </targetTests>
        <mutationThreshold>70</mutationThreshold>
    </configuration>
</plugin>
```
```bash
mvn test-compile pitest:mutationCoverage
```

На выходе — HTML-отчёт, где для каждого класса видно, какие мутанты выжили и в какой строке. Выжившие мутанты — это и есть точные адреса, куда стоит дописать assertions.

## Q14. Что такое mutation score?

**Mutation score** — доля мутантов, которые тесты сумели поймать: `убитые мутанты / всего мутантов × 100%`. По сути это процент намеренно внесённых багов, которые тесты заметили.

Как читать цифру:
- **90%+** — превосходное качество: тесты ловят почти любое искажение логики.
- **70–90%** — хороший уровень для большинства проектов.
- **< 50%** — тревожный сигнал: тесты вроде есть, но они выполняют код, не проверяя его поведение.

**Почему это честнее line coverage.** Line coverage растёт от любого вызова метода, даже без assertions. Mutation score растёт только тогда, когда тест реально отличает правильный код от испорченного. Поэтому именно он показывает настоящее качество тестов, а не их объём.

## Q15. Какие мутации создаёт Pitest?

Каждый мутатор — это правило точечной порчи кода, имитирующее типичную ошибку программиста: сдвиг границы, инверсию условия, перепутанный знак. Базовый набор мутаторов:

| Мутатор | Пример мутации | Какую ошибку имитирует |
|---------|---------------|------------------------|
| **Conditionals Boundary** | `>` → `>=`, `<` → `<=` | off-by-one на границе |
| **Negate Conditionals** | `==` → `!=`, `>` → `<=` | перепутанное условие |
| **Math** | `+` → `-`, `*` → `/` | ошибка в арифметике |
| **Return Values** | `return true` → `return false` | неверный результат |
| **Void Method Calls** | удаление вызова `void`-метода | забытый побочный эффект |
| **Increments** | `i++` → `i--` | неверное направление счётчика |
| **Invert Negatives** | `-x` → `x` | потерянный знак |

```java
// Оригинал
boolean isAdult(int age) {
    return age >= 18;
}

// Мутант: Conditionals Boundary
boolean isAdult(int age) {
    return age > 18;  // граничный случай 18 теперь false
}
// Если тест не проверяет age=18 отдельно — мутант выживет
```

## Q16. Что такое «coverage theater»?

**Coverage theater** («театр покрытия») — ситуация, когда команда добивается красивой цифры coverage, но тесты при этом не проверяют реальное поведение. Метрика растёт, защита от багов — нет: это спектакль ради отчёта.

Типичные проявления:
- **Тесты без assertions** — метод просто вызывают, ничего не утверждая. Строки покрыты, поведение не проверено.
- **Только happy path** — гоняют сценарий «всё хорошо», а граничные случаи и ошибки игнорируют. А именно там и живут баги.
- **Тесты ради цифр** — пишут, чтобы поднять процент к дедлайну, а не чтобы поймать регрессию.
- **Тотальное мокирование** — замокано всё подряд, и тест проверяет поведение моков, а не реального кода.

**Чем опасен.** Высокий процент создаёт ложное чувство безопасности: команда думает, что код защищён, спокойно его меняет — а регрессии проходят сквозь тесты незамеченными. Иногда отсутствие тестов честнее, чем такой «театр».

---

## Q17. Как написать тест, который увеличивает coverage, но не проверяет ничего?

Достаточно вызвать метод и не написать ни одного `assert` — coverage вырастет, потому что строки выполнились, но тест ничего не утверждает и не упадёт при любой поломке логики. Сравните «театр» и осмысленный тест:

```java
// Coverage theater: метод вызван, строки покрыты, но тест ничего не утверждает
@Test
void testCalculate() {
    Calculator calc = new Calculator();
    calc.calculate(10, 5, Operation.ADD);  // coverage есть, assertion нет
}

// Правильно: проверяем результат
@Test
void testCalculate_addition() {
    Calculator calc = new Calculator();
    int result = calc.calculate(10, 5, Operation.ADD);
    assertThat(result).isEqualTo(15);
}
```

**Как ловить такое на ревью.** Оба теста дают одинаковый coverage, но первый не упадёт, даже если `calculate` начнёт возвращать мусор. Признак «театра» — тест, в котором нет `assert`/`verify`, а есть только вызов метода.

## Q18. Как отличить осмысленный coverage от формального?

Ключевая мысль: осмысленный тест проверяет **поведение** кода, а формальный лишь **прогоняет** его. Различить их можно по таким признакам:

- **Есть assertions по делу.** Каждый тест проверяет конкретный ожидаемый результат, а не просто вызывает метод.
- **Покрыты граничные случаи.** Тесты идут дальше happy path: null, пустые коллекции, лимиты, ошибки.
- **Mutation score близок к coverage.** Если покрытие высокое, а mutation score тоже высокий — assertions реально работают.
- **Тест падает на подсаженном баге.** Внесите ошибку в код вручную — осмысленный тест сразу покраснеет, формальный останется зелёным.

**Инструментальная проверка.** Запустите Pitest. Если mutation score заметно ниже line coverage — значит, строки выполняются, но поведение не проверяется. Это и есть формальное покрытие.

## Q19. Стоит ли гнаться за 100% coverage?

В общем случае — нет. Стопроцентное покрытие почти всегда стоит дороже, чем приносит пользы, и часто подменяет цель: вместо «писать хорошие тесты» команда начинает «закрывать последние строки любой ценой». Конкретные причины:

- **Закон убывающей отдачи.** Первые проценты покрывают основную логику дёшево, а последние 10% требуют непропорциональных усилий ради малозначимых веток.
- **Есть код, который тестировать незачем.** `main`-методы, конфигурация, обработка инфраструктурных исключений, которые на практике не воспроизвести.
- **Отвлекает от качества.** Команда начинает оптимизировать метрику, а не реальную защищённость кода — растёт риск coverage theater.
- **Мёртвый код тоже можно покрыть.** Писать тест на код, который никогда не вызывается в проде, — пустая трата времени.

**Исключение.** Safety-critical системы (авиация, медицина, автомобильный софт) требуют 100% MC/DC coverage. Но это не «гонка за цифрой», а осознанное требование отраслевых стандартов, где цена пропущенного бага — человеческие жизни.

## Q20. Что не покрывает обычный code coverage?

Главное ограничение coverage в том, что он измеряет факт выполнения, а не правильность, и видит только то, что воспроизводится в тестовом окружении. Вне его зоны охвата остаётся целый класс проблем:

- **Корректность** — код выполнен, но возвращает неверный результат. Без assertions coverage этого не заметит.
- **Многопоточность** — гонки данных и deadlock проявляются по таймингу, а не по факту прохождения строк.
- **Интеграция** — реальное взаимодействие компонентов в боевом окружении (сеть, БД, очереди) тесты с моками не проверяют.
- **Производительность** — покрытая строка может быть выполнена, но при этом работать недопустимо медленно.
- **Безопасность** — SQL-инъекция спокойно живёт в «покрытом» коде, ведь уязвимость — это свойство логики, а не факт выполнения.
- **Обработка ошибок** — исключения от внешних систем (таймауты, отказы) сложно воспроизвести, поэтому их ветки часто остаются непокрытыми.

## Q21. Как измерять coverage в многомодульном проекте?

Проблема в том, что каждый модуль собирает свой `.exec` и видит только свой код. Если тесты из модуля A проверяют код модуля B, по отдельности покрытие B будет занижено. Решение — собрать данные всех модулей в один агрегированный отчёт.

**Maven: агрегированный отчёт.** Заводят отдельный report-модуль, который через `report-aggregate` объединяет покрытие всех зависимостей:
```xml
<!-- В отдельном report-модуле -->
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <executions>
        <execution>
            <id>report-aggregate</id>
            <phase>verify</phase>
            <goals><goal>report-aggregate</goal></goals>
        </execution>
    </executions>
</plugin>
```

**Gradle multi-project.** В корневом build-скрипте собирают все `.exec`-файлы из подпроектов в общий отчёт:
```groovy
// В корневом build.gradle
task jacocoMergedReport(type: JacocoReport) {
    executionData fileTree(project.rootDir.absolutePath).include("**/build/jacoco/*.exec")
    subprojects.each {
        sourceSets it.sourceSets.main
    }
}
```

## Q22. Как использовать coverage в code review?

Coverage в ревью полезен не как самоцель, а как навигатор: он подсвечивает места, где новая логика осталась без тестов, и превращает абстрактное «надо больше тестов» в конкретный вопрос по конкретной ветке. Рабочие практики:

- **PR не должен ронять покрытие.** Минимум — сохранять текущий уровень, лучше — улучшать. SonarQube PR Decoration показывает дельту прямо в PR.
- **Новая функциональность — с тестами.** Появился новый код — к нему должны прийти тесты в том же PR.
- **Непокрытая ветка — повод для вопроса.** Увидели в diff красную строку — спросите «почему здесь нет теста?». Часто это вскрывает забытый сценарий.
- **Не требуйте 100%, требуйте тесты на критику.** Геттеры можно простить, бизнес-логику без тестов — нет.

**Инструментально.** Настройте Quality Gate «coverage on new code ≥ 80%» — это автоматически блокирует merge кода без тестов, не полагаясь на бдительность ревьюера.

## Q23. Какие компоненты не имеет смысла покрывать тестами?

Общий критерий простой: если в коде нет собственной логики и ветвлений, тест на него ничего не проверит, а лишь искусственно нарисует покрытие. Под это попадают:

- **DTO / Record / POJO** — если там только геттеры и сеттеры без логики. Тестировать `return this.name;` бессмысленно.
- **Конфигурационные классы** — `@Configuration`, биндинг `application.yml`. Их «проверяет» сам запуск приложения.
- **`main()`-методы** Spring Boot приложений — точка входа без логики.
- **Сгенерированный код** — MapStruct, QueryDSL, Lombok. Его корректность гарантирует генератор, а не ваши тесты.
- **Методы только с логированием** без бизнес-логики.

**Важно.** Эти классы стоит явно вынести в excludes JaCoCo (см. Q10). Иначе они либо занижают метрику (числятся непокрытыми), либо подталкивают команду писать на них пустые тесты ради процента — то есть провоцируют coverage theater.

## Q24. Как внедрить coverage в legacy-проект?

Главная ошибка с legacy — пытаться разом покрыть всё. Это нереалистично и демотивирует. Правильная стратегия — зафиксировать текущий уровень как «дно», не дать ему упасть и наращивать покрытие постепенно, сосредоточившись на новом и критическом коде. Пошагово:

1. **Замерить baseline.** Запустить JaCoCo и зафиксировать текущее состояние (например, 20%). Это отправная точка, а не приговор.
2. **Запретить регресс.** Установить threshold = текущему уровню. CI не должен пропускать изменения, которые роняют покрытие ниже зафиксированного.
3. **Постепенный рост.** Поднимать порог на 1–2% за спринт, покрывая в первую очередь новый и критический код.
4. **Фокус на новом коде.** Через SonarQube New Code Period требовать 80% покрытия только для свежих изменений — старый код это правило не затрагивает.
5. **Правило бойскаута.** Касаетесь файла по задаче — заодно дописываете на него тесты. Так покрытие растёт там, где код и так меняется.

## Q25. Что такое differential coverage?

**Differential coverage** (он же diff coverage, coverage on new code) — измерение покрытия только изменённого кода в PR, а не всего проекта целиком. Метрика отвечает на вопрос «покрыты ли строки, которые вы добавили или изменили именно в этом PR», игнорируя унаследованный код.

**Как применяют.** В каждом PR/MR анализируют только строки из diff. Это снимает главный конфликт с legacy: общий процент по проекту может быть низким, но к новым строкам можно предъявлять строгие требования.

**Инструменты:**
- **SonarQube New Code** — встроенная поддержка через настройку New Code Period.
- **Codecov / Coveralls** — внешние сервисы с дифференциальным анализом, удобно интегрируются с GitHub.

**В чём выигрыш.** Можно поставить строгий порог (например, 90%) для нового кода, не требуя при этом мгновенно покрыть весь старый. Покрытие проекта растёт органично — с каждым PR, без масштабной разовой кампании по дописыванию тестов.
