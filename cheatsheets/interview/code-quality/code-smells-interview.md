## Q1. Что такое code smell и чем он отличается от бага?

**Code smell** (запах кода) — поверхностный признак того, что с дизайном кода что-то не так, хотя сам код при этом работает корректно. Это не ошибка, а намёк на скрытую проблему в структуре.

Ключевое различие — в том, что именно сломано:

| | Что не так | Что страдает |
|---|---|---|
| **Баг** | код работает неправильно, нарушено ожидаемое поведение | пользователь и корректность |
| **Code smell** | код работает правильно, но плохо устроен | понимание, изменение, тестирование, развитие |

Смысл понятия — дать команде общий язык: смелл не требует немедленных действий, а служит сигналом «остановись и присмотрись». Решение, рефакторить или нет, зависит от контекста: смелл в коде, который никто не трогает годами, можно оставить, а тот же смелл в часто меняемом модуле — повод вмешаться.

**Главное:** баг ловят тесты, смелл ловит человек при чтении кода.

## Q2. Откуда взялся термин «запах кода»? Кто ввёл классификацию?

Авторство — за двумя людьми. Сам термин «code smell» предложил и популяризировал **Кент Бек** (Kent Beck), а развёрнутый каталог смеллов систематизировал **Мартин Фаулер** в книге «Refactoring: Improving the Design of Existing Code» (1-е изд. 1999, 2-е изд. 2018).

Почему это важно для собеседования: смеллы — не абстрактная теория, а практический инструмент.

- Каталог содержит около 22 базовых смеллов в 1-м издании и расширен во 2-м.
- Главная идея Фаулера: **каждый смелл связан с конкретным рефакторингом**, который его устраняет. Распознал смелл — знаешь, какое лекарство применить.

Поэтому смеллы и рефакторинги изучают в паре: одно без другого бесполезно.

## Q3. Как code smells соотносятся с техническим долгом?

Смелл — это симптом, технический долг — его цена. Одно описывает «что не так», другое — «сколько это будет стоить».

- **Code smell** — конкретный, видимый симптом плохого дизайна: длинный метод, дублирование, god class.
- **Технический долг** — накопленная стоимость этих симптомов: дополнительное время, которое команда будет тратить на каждое изменение, пока долг не погашен.

Связь между ними удобно представить как цепочку:

> смелл (симптом) → накапливает технический долг (цена) → гасится рефакторингом (выплата)

**Аналогия с финансами** (её и ввёл Уорд Каннингем): смеллы — это «проценты» по долгу. Чем дольше не рефакторишь, тем дороже обходится каждая новая фича в этом коде. Поэтому смеллы важно не просто фиксировать, а оценивать по тому, насколько дорого они обходятся при изменениях.

## Q4. Какие основные категории code smells выделяет Мартин Фаулер?

Каталог смеллов принято группировать в пять категорий — это удобно тем, что у каждой группы своя причина и свой типичный набор рефакторингов. На собеседовании достаточно назвать категории и по одному-два примера.

| Категория | В чём суть проблемы | Примеры |
|-----------|---------|---------|
| **Bloaters** (раздутый код) | сущности разрослись до неуправляемых размеров | Long Method, Large Class, Long Parameter List, Data Clumps, Primitive Obsession |
| **Object-Orientation Abusers** | ООП применяется неполно или неправильно | Switch Statements, Refused Bequest, Temporary Field |
| **Change Preventers** | одно изменение тянет за собой множество правок | Divergent Change, Shotgun Surgery, Parallel Inheritance Hierarchies |
| **Dispensables** (лишнее) | код, который можно безболезненно убрать | Comments, Duplicate Code, Lazy Class, Dead Code, Speculative Generality |
| **Couplers** (связность) | классы знают друг о друге слишком много | Feature Envy, Inappropriate Intimacy, Message Chains, Middle Man |

**Зачем категории:** они подсказывают направление лечения. Bloaters лечат разбиением, Change Preventers — перегруппировкой ответственности, Couplers — снижением связности.

## Q5. Что такое Long Method и почему он вреден?

**Long Method** — метод, который делает слишком много и потому не охватывается взглядом за один присест. Главный критерий не строки, а понятность: если метод нельзя понять с первого прочтения, он длинный. На практике порогом часто называют 20–30 строк, но это лишь ориентир — зависит от контекста.

Почему длинный метод вреден — все три проблемы растут из одного корня, «метод делает много вещей»:

- **Трудно тестировать изолированно** — нельзя проверить один шаг, не прогнав весь метод целиком.
- **Невозможно нормально назвать** — имя должно отражать одно действие, а тут их десяток.
- **Хрупкость** — правка одной части рискует задеть другую, потому что всё перемешано в общем теле и делит локальные переменные.

**Рекомендация:** длина метода — обратная сторона хорошего именования. Каждый осмысленный фрагмент стоит вынести в метод с говорящим именем; тогда верхний метод читается как оглавление.

**Рефакторинг: Extract Method**

```java
// До: один метод на всё
public void processOrder(Order order) {
    // валидация — 20 строк
    // расчёт скидки — 15 строк
    // формирование счёта — 25 строк
    // отправка уведомления — 10 строк
}

// После: каждый шаг — отдельный метод
public void processOrder(Order order) {
    validateOrder(order);
    applyDiscount(order);
    generateInvoice(order);
    sendNotification(order);
}
```

## Q6. Что такое Long Parameter List и как его устранить?

**Long Parameter List** — метод принимает столько параметров, что вызов становится трудно читать и легко ошибиться. Тревожным сигналом обычно считают 4 параметра и больше.

Чем длинный список параметров плох:

- Вызов нечитаем — на месте вызова видно лишь набор значений без имён, легко перепутать порядок (особенно у параметров одного типа).
- Список разрастается при каждом новом требовании, и сигнатура постоянно меняется.
- Часто это маскированный смелл **Data Clumps** (см. Q11): параметры всегда ходят вместе и просятся в отдельный объект.

**Рефакторинги:**
- **Introduce Parameter Object** — сгруппировать связанные параметры в один объект.
- **Preserve Whole Object** — если параметры берутся из полей одного объекта, передавать сам объект, а не вытаскивать поля по отдельности.

```java
// До
void createUser(String firstName, String lastName, String email,
                String phone, String city, String zipCode) { ... }

// После: Parameter Object
record UserRegistrationRequest(
    String firstName, String lastName,
    String email, String phone,
    Address address
) {}

void createUser(UserRegistrationRequest request) { ... }
```

## Q7. Что такое Duplicate Code и какие техники рефакторинга применяются?

**Duplicate Code** — один и тот же (или почти одинаковый) фрагмент кода живёт в нескольких местах. Это самый частый и самый коварный смелл: пока логика не меняется, дубли молчат, но при первой же правке нужно найти и обновить все копии — а одну почти наверняка пропустят, и поведение разъедется.

Выбор рефакторинга зависит от того, где лежат дубли:

- **Extract Method** — фрагменты в одном классе: вынести в общий приватный метод.
- **Pull Up Method** — одинаковые методы в классах-братьях: поднять в общего родителя.
- **Form Template Method** — структура алгоритма одна, а отдельные шаги различаются: зафиксировать каркас в базовом классе, оставив шаги для переопределения.

**Эмпирическое правило:** «правило трёх» — два повтора терпимы, на третьем устраняй дублирование.

```java
// До: дублирование в двух классах
class OrderReport {
    String formatHeader() {
        return "=== Report ===\nDate: " + LocalDate.now();
    }
}
class InvoiceReport {
    String formatHeader() {
        return "=== Report ===\nDate: " + LocalDate.now();
    }
}

// После: общий базовый класс или утилита
abstract class BaseReport {
    protected String formatHeader() {
        return "=== Report ===\nDate: " + LocalDate.now();
    }
}
```

## Q8. Что такое Dead Code и как его обнаружить?

**Dead Code** — код, который никогда не выполняется или результат которого нигде не используется: неиспользуемые методы, переменные, недостижимые ветки условий, осиротевшие константы. Он создаёт иллюзию, будто что-то делает, и заставляет читателя тратить время на разбор бесполезных строк.

**Как обнаружить** — от дешёвого к глубокому:

- **IDE-предупреждения** — IntelliJ IDEA помечает неиспользуемое серым прямо при наборе. Самый быстрый путь.
- **SonarQube** — правила `squid:S1172` (неиспользуемый параметр), `squid:S1481` (неиспользуемая локальная переменная).
- **JaCoCo** — непокрытые строки в отчёте о покрытии часто и есть мёртвый код (его не достигают даже тесты).

```java
// Примеры dead code
private void unusedMethod() { ... }  // никто не вызывает

if (false) {  // никогда не выполнится
    doSomething();
}

int result = compute();  // результат не используется
```

Удаление dead code снижает когнитивную нагрузку и уменьшает поверхность для ошибок.

## Q9. Что такое God Class / Large Class?

**God Class** (God Object, божественный объект) — класс, который знает и делает слишком много, стянув на себя логику, которой место в нескольких отдельных классах. Это крайняя форма смелла Large Class.

Как распознать:

- сотни методов или тысячи строк в одном классе;
- много полей, относящихся к разным, не связанным между собой концепциям;
- класс нарушает **принцип единственной ответственности (SRP)** — у него больше одной причины для изменения.

Почему это дорого: такой класс становится узким местом разработки. Любая фича задевает его, отсюда постоянные merge-конфликты, а покрыть его тестами почти невозможно из-за сцепленности всего со всем.

**Рефакторинг:** Extract Class — выделить группы связанных методов и полей в отдельные классы; Move Method / Move Field — растащить ответственности по этим классам.

```java
// До: God Class
class UserService {
    // Аутентификация
    boolean authenticate(String login, String password) { ... }
    // Уведомления
    void sendWelcomeEmail(User user) { ... }
    // Отчёты
    List<UserStats> generateReport(DateRange range) { ... }
    // Платёжная логика
    void processPayment(User user, Order order) { ... }
}

// После: разделение по ответственностям
class AuthService { boolean authenticate(...) { ... } }
class NotificationService { void sendWelcomeEmail(...) { ... } }
class UserReportService { List<UserStats> generateReport(...) { ... } }
class PaymentService { void processPayment(...) { ... } }
```

## Q10. Что такое Feature Envy?

**Feature Envy** («завистливый метод») — метод в классе A обращается к данным класса B чаще, чем к собственным. Он как будто завидует чужому классу: дёргает его геттеры, считает что-то на основе его полей. Это верный сигнал, что метод оказался не в том классе.

Логика лечения проста: **поведение должно жить рядом с данными, которыми оно оперирует**. Если метод работает в основном с полями Order — пусть он и будет методом Order. Это снижает связность между классами и заодно убирает цепочки геттеров.

```java
// Feature Envy: метод OrderPrinter работает только с Order
class OrderPrinter {
    void print(Order order) {
        System.out.println(order.getCustomer().getName());
        System.out.println(order.getItems().size());
        System.out.println(order.getTotalPrice());
        // почти нет обращений к self
    }
}

// После рефакторинга: метод переезжает в Order
class Order {
    void print() {
        System.out.println(customer.getName());
        System.out.println(items.size());
        System.out.println(getTotalPrice());
    }
}
```

**Рефакторинг:** Move Method.

## Q11. Что такое Data Clumps?

**Data Clumps** («группы данных») — несколько полей или параметров, которые постоянно появляются вместе: в полях разных классов, в сигнатурах методов, в списках аргументов. Если три значения всюду ходят парой-тройкой, это не случайность — они описывают одну самостоятельную концепцию, у которой просто нет своего типа.

Как заметить: эмпирическое правило Фаулера — удали одно из значений и спроси, имеют ли остальные смысл по отдельности. Если нет — перед тобой clump, который просится в отдельный класс.

```java
// До: city, street, zip везде ходят вместе
void deliver(String city, String street, String zip) { ... }
class Customer { String city; String street; String zip; }

// После: Address как отдельный класс
record Address(String city, String street, String zip) {}
void deliver(Address address) { ... }
class Customer { Address address; }
```

**Рефакторинг:** Extract Class, Introduce Parameter Object.

## Q12. Что такое Primitive Obsession?

**Primitive Obsession** («одержимость примитивами») — привычка моделировать понятия предметной области голыми примитивами (`String`, `int`, `boolean`) вместо собственных типов. Email хранится как `String`, деньги как `BigDecimal`, статус как `int`-код.

Почему это смелл: у примитива нет правил. Раз тип ничего не гарантирует, логика валидации и форматирования расползается по всему коду — и в каждой точке её легко забыть или сделать по-разному. Заводя **Value Object**, эти правила собирают в одном месте, а тип сам не даёт создать некорректное значение.

```java
// До: Email как String
class User {
    String email;  // валидация где-то снаружи, или нигде
}

// После: Email как Value Object
record Email(String value) {
    Email {
        if (!value.contains("@")) throw new IllegalArgumentException("Invalid email");
    }
}
class User {
    Email email;
}
```

## Q13. Что такое Lazy Class и когда класс считается лишним?

**Lazy Class** («ленивый класс») — класс, который не делает достаточно, чтобы оправдать своё существование. Каждый класс стоит денег: его нужно понимать, поддерживать, держать в голове при навигации. Если отдачи от него меньше, чем этих издержек, он лишний.

Когда класс попадает под подозрение:

- содержит лишь 1–2 тривиальных метода;
- только делегирует вызовы другому классу, не добавляя смысла;
- остался «огрызком» после агрессивного рефакторинга или появился как Speculative Generality (задел на будущее, которое не наступило).

**Рефакторинг:** Inline Class — влить содержимое в класс, который им пользуется; Collapse Hierarchy — слить почти пустой подкласс с родителем.

## Q14. Что такое Data Class и почему она проблематична?

**Data Class** — класс из одних полей с геттерами/сеттерами и без поведения, «мешок данных». Сама по себе пассивная структура не криминал — проблема в том, что логика работы с этими данными неизбежно расползается по другим классам.

Чем это плохо: нарушается инкапсуляция. Раз класс не охраняет свои данные, любой может читать и менять их как угодно, а одни и те же вычисления (например, расчёт суммы строки заказа) дублируются везде, где эти данные используются. Лечится переносом поведения внутрь класса — туда, где живут данные (см. Feature Envy, Q10).

**Оговорка:** не всякий объект без поведения — смелл. DTO, record-параметры, immutable value-объекты на границах системы вполне законны; смелл возникает, когда поведение есть, но живёт не там.

```java
// Data Class — только данные, нет поведения
class OrderItem {
    private int quantity;
    private BigDecimal price;
    public int getQuantity() { return quantity; }
    public BigDecimal getPrice() { return price; }
}

// Лучше: добавить поведение туда, где оно должно жить
class OrderItem {
    private int quantity;
    private BigDecimal price;

    public BigDecimal subtotal() {
        return price.multiply(BigDecimal.valueOf(quantity));
    }
}
```

## Q15. Что такое Shotgun Surgery?

**Shotgun Surgery** («стрельба дробью») — одно изменение требует множества мелких правок в разных, не связанных между собой классах. Название образное: чтобы поразить одну цель, приходится попадать сразу по многим местам.

Это зеркальный двойник Divergent Change (Q16) — оба относятся к Change Preventers, но разнонаправлены:

- **Divergent Change** — один класс меняется по многим разным причинам (ответственность скучена в одном месте).
- **Shotgun Surgery** — одна причина изменения размазана по многим классам (ответственность рассыпана).

**Типичный признак:** «хочу поменять логику логирования — а трогать надо 15 файлов». Логика, которая должна быть в одном месте, разбросана повсюду.

**Рефакторинг:** Move Method, Move Field, Inline Class — собрать разбросанную логику в один класс, чтобы будущие изменения происходили в одной точке.

## Q16. Что такое Divergent Change?

**Divergent Change** («расходящееся изменение») — один класс приходится менять по нескольким не связанным между собой причинам. Это прямое нарушение **SRP**: у класса должна быть ровно одна причина для изменения, а здесь их несколько.

**Пример:** `UserService` правят и когда меняется логика аутентификации, и когда меняются правила уведомлений, и когда переделывают схему отчётов. Три разные команды/задачи постоянно толкаются в одном файле.

Как отличить от Shotgun Surgery (Q15): смотри на направление. Здесь много причин сходятся в один класс; там одна причина расходится по многим классам.

**Рефакторинг:** Extract Class — разнести несвязанные группы методов по отдельным классам, у каждого из которых будет своя единственная ответственность.

## Q17. Что такое Inappropriate Intimacy?

**Inappropriate Intimacy** («неуместная близость») — два класса знают друг о друге слишком много: лезут во внутренние поля, через reflection обходят инкапсуляцию, опираются на детали чужой реализации. В итоге их нельзя менять по отдельности — это высокая связность (coupling).

Опасность в том, что граница между классами фактически стёрта: правка в одном почти гарантированно ломает другой, и тестировать их изолированно невозможно.

**Рефакторинг:**
- **Move Method / Move Field** — перенести логику и данные туда, где они действительно используются.
- **Extract Class** — выделить то общее, ради чего классы лезут друг к другу, в третий класс.
- **Change Bidirectional Association to Unidirectional** — убрать лишнюю двунаправленную ссылку, если зависимость на деле односторонняя.

## Q18. Что такое Message Chains?

**Message Chains** («цепочки сообщений») — длинная цепочка навигации по объектам: `a.getB().getC().getD().doSomething()`. Клиент пробирается через несколько объектов, чтобы добраться до нужного.

Чем это плохо: код привязывается к структуре связей между объектами. Поменялась любая ссылка в середине цепочки — и все вызывающие ломаются. Это нарушает **Закон Деметры** (Law of Demeter, «не разговаривай с незнакомцами»): объект должен общаться только с ближайшими соседями, а не дёргать соседей своих соседей.

```java
// Message chain — хрупко к изменениям структуры
String city = order.getCustomer().getAddress().getCity().getName();

// Лучше: делегирующий метод
String city = order.getCustomerCity();  // скрывает структуру
```

**Рефакторинг:** Hide Delegate.

## Q19. Что такое Middle Man?

**Middle Man** («посредник») — класс, который почти все вызовы просто перенаправляет другому классу, не добавляя ничего своего. Лишнее звено: чтобы понять, что происходит, всё равно приходится идти к тому, кому он делегирует.

Откуда берётся: чаще всего это перегиб с **Hide Delegate** (Q18). Прячешь делегата за обёрткой, дальше прячешь ещё и ещё — и однажды обёртка не делает уже ничего, кроме проброса. Это зеркало Message Chains: там навигации слишком много, тут посредничества слишком много, и оба крайности.

```java
// Middle Man — PersonFacade ничего не делает сам
class PersonFacade {
    private Person person;
    String getName() { return person.getName(); }
    int getAge() { return person.getAge(); }
    String getAddress() { return person.getAddress(); }
}
```

**Рефакторинг:** Remove Middle Man — обращаться к Person напрямую.

## Q20. Что такое Parallel Inheritance Hierarchies?

**Parallel Inheritance Hierarchies** («параллельные иерархии наследования») — частный, особо неприятный случай Shotgun Surgery: создаёшь подкласс в одной иерархии — обязан создать парный подкласс в другой. Два дерева классов растут синхронно и связаны невидимой нитью.

**Как узнать:** имена классов из двух иерархий повторяют друг друга по префиксу. Появился `Dog` — рядом обязаны появиться `DogRenderer` и `DogExporter`; добавили `Cat` — снова `CatRenderer`, `CatExporter`. Каждый новый тип требует правок в двух местах.

**Рефакторинг:** перенести ответственность так, чтобы одна из иерархий стала ненужной — например, сделать так, чтобы экземпляры одной иерархии ссылались на экземпляры другой, и второе дерево схлопнулось.

## Q21. Что такое Switch Statements как code smell?

Смелл не в самом `switch`, а в **повторяющемся `switch`/`if-else` по типу объекта**. Если один и тот же разбор «что это за фигура / что за тип» встречается в нескольких методах, это сигнал, что просится полиморфизм.

Почему повтор опасен: добавляешь новый тип — и надо не забыть дописать ветку в каждый такой `switch` по всему коду (это Shotgun Surgery в миниатюре). Полиморфизм переворачивает ситуацию: новый тип — это новый класс, реализующий интерфейс, и ни один существующий `switch` трогать не нужно (принцип открытости/закрытости, OCP).

```java
// До: switch по типу фигуры в нескольких методах
double area(Shape shape) {
    return switch (shape.type()) {
        case CIRCLE -> Math.PI * shape.radius() * shape.radius();
        case RECTANGLE -> shape.width() * shape.height();
        case TRIANGLE -> 0.5 * shape.base() * shape.height();
    };
}

// После: полиморфизм
interface Shape { double area(); }
class Circle implements Shape { public double area() { return Math.PI * r * r; } }
class Rectangle implements Shape { public double area() { return w * h; } }
```

**Рефакторинг:** Replace Conditional with Polymorphism, Replace Type Code with Subclasses.

## Q22. Что такое Speculative Generality?

**Speculative Generality** («умозрительная общность») — код, написанный «на будущее»: обобщения, абстракции и параметры, которые добавили в расчёте на гипотетические требования, но которыми сейчас никто не пользуется. Прямое нарушение **YAGNI** (You Aren't Gonna Need It — «тебе это не понадобится»).

Чем это вредит: лишняя гибкость не бесплатна. Она усложняет код, который и так нужно читать и поддерживать, а предугаданное будущее обычно так и не наступает — либо наступает, но иначе, чем заложили.

**Признаки:**
- абстрактные классы и интерфейсы с единственной реализацией;
- параметры методов, которым всегда передают одно и то же значение;
- хуки и точки расширения, которые ничего не расширяют.

**Рефакторинг:** Collapse Hierarchy, Inline Class, Remove Parameter — убрать неиспользуемую гибкость, оставив код ровно под текущие нужды.

## Q23. Что такое Refused Bequest?

**Refused Bequest** («отказ от наследства») — подкласс наследует от родителя, но игнорирует или переопределяет-в-пустоту большую часть унаследованных методов и полей. Он берёт фамилию, но отказывается от наследства.

Почему это смелл: наследование объявляет отношение «является» (is-a). Если подкласс не хочет половину того, что предлагает родитель, значит, он на самом деле им не является — иерархия построена ради переиспользования кода, а не ради общего поведения. Это ломает принцип подстановки Лисков (LSP) и сбивает с толку: тип обещает контракт родителя, которого не выполняет.

**Сигнал:** связь наследования выбрана неверно — чаще здесь нужна композиция, при которой класс берёт лишь то, что ему действительно нужно.

```java
// Refused Bequest: Stack наследует Vector, но не хочет большинство его методов
class Stack<T> extends Vector<T> {  // проблема в стандартной Java
    // push/pop используются, но add(index, element) нарушает инварианты стека
}
```

**Рефакторинг:** Replace Inheritance with Delegation.

## Q24. Что такое Comments как code smell (по Фаулеру)?

Комментарий сам по себе не зло. Смелл — это **комментарий-дезодорант**: им часто пытаются заглушить запах непонятного кода вместо того, чтобы переписать сам код. Если комментарий объясняет, **что** делает строка, — это сигнал, что код недостаточно выразителен, и комментарий стоило бы заменить хорошим именем или вынесенным методом.

**Правило:** хороший комментарий объясняет **почему** (бизнес-причину, неочевидное решение, обход известного бага), а не «что» — потому что «что» должен говорить сам код. Когда тянет написать комментарий-«что», сперва попробуй сделать код понятным без него.

```java
// Плохо: объясняет «что» — код должен говорить сам
// Умножаем цену на 1.2, потому что добавляем 20% наценку
double finalPrice = price * 1.2;

// Хорошо: выразительный код без комментария
double finalPrice = price.withMarkup(STANDARD_MARKUP);

// Хорошо: комментарий объясняет «почему» (бизнес-ограничение)
// Округляем вниз, т.к. банк не принимает дробные копейки
BigDecimal rounded = amount.setScale(2, RoundingMode.FLOOR);
```

## Q25. Как автоматически обнаруживать code smells в Java-проекте?

Автоматика хорошо ловит измеримые смеллы (длина, сложность, дублирование, неиспользуемый код), но бессильна против структурных (Feature Envy, Shotgun Surgery) — их по-прежнему распознаёт человек на ревью. На практике инструменты дополняют друг друга.

| Инструмент | Что находит |
|------------|-------------|
| **SonarQube** | God classes, long methods, cyclomatic complexity, duplicate code |
| **PMD** | Long methods, data clumps, switch complexity, unused variables |
| **SpotBugs** | Потенциальные баги, связанные с плохим дизайном |
| **Checkstyle** | Нарушения стиля, которые часто коррелируют со смеллами |
| **IntelliJ IDEA** | Code inspections: dead code, feature envy, duplicate fragments |
| **JaCoCo** | Dead code через незакрытые ветки |

Конфигурация PMD в Maven:
```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-pmd-plugin</artifactId>
    <configuration>
        <rulesets>
            <ruleset>/rulesets/java/design.xml</ruleset>
            <ruleset>/rulesets/java/codesize.xml</ruleset>
        </rulesets>
    </configuration>
</plugin>
```

## Q26. Какие метрики кода связаны с code smells?

Метрики — это числовые «датчики» смеллов: их легко считать автоматически и ставить порогом в CI. Важно помнить, что превышение порога — повод присмотреться, а не приговор: метрика указывает на запах, но решение принимает человек.

| Метрика | Связанный смелл |
|---------|----------------|
| **Cyclomatic Complexity** > 10 | Long Method, Switch Statements |
| **Lines of Code** (LOC) метода > 30 | Long Method |
| **Number of Parameters** > 4 | Long Parameter List |
| **Coupling Between Objects** (CBO) | Inappropriate Intimacy, Shotgun Surgery |
| **Lack of Cohesion of Methods** (LCOM) | God Class, Divergent Change |
| **Depth of Inheritance Tree** (DIT) > 4 | Refused Bequest, Parallel Hierarchies |
| **Code Duplication** % | Duplicate Code |

## Q27. Как приоритизировать устранение code smells?

Не все смеллы одинаково вредны, поэтому чинить подряд бессмысленно. Главный критерий — **частота изменений**: смелл болит ровно настолько, насколько часто его трогают. Смелл в коде, который никто не открывает, не стоит ничего.

Приоритет устранения — от самого болезненного к терпимому:

1. **Смеллы в часто меняемом коде** — где команда работает каждый день. Такие места (hotspots) находят через историю изменений, например `git log --stat`.
2. **Смеллы, блокирующие тестируемость** — длинные методы с кучей ветвлений: пока их не разобьёшь, код не покрыть тестами.
3. **Дублирование в критической бизнес-логике** — один баг, размноженный по копиям, бьёт сразу в нескольких местах.
4. **God Classes** — узкие места разработки: тормозят параллельную работу и плодят merge-конфликты.
5. **Смеллы в стабильном, нетрогаемом коде** — низкий приоритет: не болит — не лечим.

**Эмпирическое правило:** не устраивать отдельных «рефакторинг-спринтов», а чинить смелл при следующем касании файла — **Boy Scout Rule** («оставь место стоянки чище, чем нашёл»).
