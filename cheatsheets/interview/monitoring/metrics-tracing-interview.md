## Метрики

## Q1. Чем метрики отличаются от логов и трейсов?

**Метрики** — агрегированные числа во времени (счётчики, gauge, гистограммы); малый объём; подходят для алертов и дашбордов. **Логи** — события с текстом и контекстом; большой объём; для отладки и аудита. **Трейсы** — цепочка операций (spans) одного запроса; показывают задержки по узлам и зависимостям. Вместе образуют observability: метрики — «что происходит в целом», трейсы — «где время ушло в одном запросе», логи — детали по запросу (по `traceId`).

При инциденте: алерт по метрике (например, рост ошибок) → открыть трейсы за период → найти медленные/ошибочные запросы по `traceId` → по `traceId` отфильтровать логи и локализовать причину. Метрики не заменяют логи и трейсы — они дополняют друг друга.

## Q2. Что такое Prometheus и как он собирает метрики?

**Prometheus** — система мониторинга с **pull-моделью**: `Prometheus` периодически запрашивает (scrape) `HTTP`-эндпоинты приложений (обычно `/actuator/prometheus` в `Spring Boot`). Метрики в текстовом формате; хранятся в локальной БД с временными рядами; запросы — `PromQL`. Плюсы: простой формат; мощный `PromQL`; интеграция с `Grafana` и `Alertmanager`. Минусы: pull не всегда удобен в динамических средах (`Kubernetes Service Discovery` решает это).

**Практика:** конфигурация scrape в `prometheus.yml`: перечень `targets` (`URL` приложений) и `scrape_interval`. В `Kubernetes` используют `ServiceMonitor` (`Prometheus Operator`) или аннотации на `Pods / Service` для автообнаружения целей. Приложение только отдаёт `HTTP`-страницу с метриками; сбор и хранение — на стороне `Prometheus`. Пример `scrape_configs`: `targets: ['app:8080']`, `scrape_interval: 15s`.

## Q3. Что такое Micrometer и как он связан с Prometheus?

`Micrometer` — фасад для метрик в `Java` (аналог `SLF4J` для логов). Приложение регистрирует счётчики, gauge, таймеры через `Micrometer`; биндинг к `Prometheus` экспортирует их в формате, который `Prometheus` scrape’ит. В `Spring Boot Micrometer` включён по умолчанию; зависимость `micrometer-registry-prometheus` и эндпоинт `/actuator/prometheus` дают готовый экспорт для `Prometheus`.

**Практика:** в `Spring Boot` добавить `micrometer-registry-prometheus`, в `application.properties`: `management.endpoints.web.exposure.include=prometheus,health`. Метрики `JVM`, `HTTP`, пулы появятся автоматически. Свои метрики — инжектировать `MeterRegistry`, создавать `Counter`, `Timer`, `Gauge`. Не создавать метрики с высоким cardinality (уникальные лейблы по `user_id` и т.п.).

## Q4. Какие типы метрик бывают (counter, gauge, histogram, summary)?

`Counter` — монотонно растущее значение (число запросов, ошибок). `Gauge` — текущее значение (размер очереди, использование памяти). `Histogram` — распределение значений (латентность); хранит счётчики по корзинам и суммарную сумму; в `Prometheus` даёт квантили через `PromQL`. `Summary` — квантили считаются на стороне приложения (редко в `Prometheus` из-за невозможности агрегации). В `Micrometer`: `Counter`, `Gauge`, `Timer` (гистограмма времени), `DistributionSummary` (размеры, не время).

Практическая ценность ответа обычно повышается, если дополнить определение операционным контекстом: как решение ведёт себя под нагрузкой, при сбоях и в процессе сопровождения. На интервью ожидают, что вы назовёте критерии выбора и способ валидации решения через метрики и проверяемый сценарий.

## Q5. Что такое распределённая трассировка и зачем она нужна?

Распределённая трассировка — запись цепочки операций (spans) одного запроса при прохождении через несколько сервисов. Позволяет увидеть, где запрос провёл время (какой сервис или БД медленный), и выявить узкие места. Без трассировки в микросервисах видно только латентность на границе; внутри цепочки вызовов — «чёрный ящик».

**Практика:** инструменты: `Jaeger`, `Zipkin`, `Tempo`; стандарт инструментирования — `OpenTelemetry`. При инциденте по высокой латентности: открыть трейсы за период → отфильтровать по `traceId` медленные запросы → по дереву spans увидеть, какой сервис или БД даёт задержку.

## Q6. Что такое OpenTelemetry и как он связан с трассировкой?

`OpenTelemetry` — открытый стандарт и набор `SDK / API` для трассировки, метрик и логов. Единая инструментация кода; экспорт в разные бэкенды (`Jaeger`, `Zipkin`, облачные сервисы). Связь с трассировкой: `OpenTelemetry` генерирует spans и trace context (`traceId`, `spanId`), передаёт контекст между сервисами (`HTTP`-заголовки, `gRPC` metadata), экспортирует в `Jaeger / Zipkin`.

**Практика:** рекомендуемый способ добавить трассировку в новое приложение — `OpenTelemetry Java Agent` или `Spring Boot` starter; автоинструментация для `HTTP`, `JDBC`, `Kafka`; кастомные spans через `Tracer API`.

## Q7. Что такое span и trace в трассировке?

`Span` — одна операция (например, `HTTP / Trace` — дерево spans, объединённых общим `traceId`; один запрос от клиента до ответа может породить десятки spans в разных сервисах. `Span` может иметь дочерние spans (вложенный вызов). По дереву spans видно полный путь запроса и время на каждом уровне.

**Практика:** в `Jaeger / Zipkin` по `traceId` открывают дерево spans: корневой span — входящий `HTTP`; дочерние — вызовы к БД, другим сервисам. Время на каждом span показывает узкое место. Атрибуты (`http.method`, `db.statement`) помогают фильтровать и искать. При инциденте: по метрике «высокий p99» найти exemplar → перейти к trace → по дереву spans увидеть, какой сервис или БД медленный.

## Q8. Как передать контекст трассировки между микросервисами?

Контекст (`traceId`, `spanId`, флаги sampling) передаётся в `HTTP`-заголовках (например, `W3C Trace Context`: `traceparent`, `tracestate`) или в `gRPC` metadata. Клиент (или шлюз) создаёт корневой span и инжектирует контекст в заголовки; следующий сервис извлекает контекст и создаёт дочерний span. `OpenTelemetry / RestTemplate`, `WebClient`, `Feign`, `gRPC`).

Практическая ценность ответа обычно повышается, если дополнить определение операционным контекстом: как решение ведёт себя под нагрузкой, при сбоях и в процессе сопровождения. На интервью ожидают, что вы назовёте критерии выбора и способ валидации решения через метрики и проверяемый сценарий.

## Q9. Что такое sampling в трассировке и когда его применять?

`Sampling` — решение, записывать ли trace целиком (при высокой нагрузке нельзя сохранять все трейсы). Типы: `head-based` (решение в начале trace); `tail-based` (решение в конце по результату — например, записывать только медленные или с ошибками).

**Практика:** применять в prod при большом `RPS / OpenTelemetry` настраивают `Sampler` (например, `ParentBased` с `RateLimiting` или `tail-based` в бэкенде).

## Q10. Как интегрировать Micrometer с Spring Boot?

В `Spring Boot` Micrometer уже включён (`spring-boot-starter-actuator`); добавить зависимость `micrometer-registry-prometheus` и включить эндпоинт: `management.endpoints.web.exposure.include=prometheus,health`. Метрики `JVM`, `HTTP`, пулы и т.д. появятся автоматически. Свои метрики: инжектировать `MeterRegistry` и создавать `Counter`, `Timer`, `Gauge`. Для `Prometheus` важен контроль cardinality (число уникальных комбинаций лейблов).

**Пример кастомной метрики:**
```java
@RequiredArgsConstructor
public class OrderService {
    private final MeterRegistry registry;
    public void createOrder(Order o) {
        Counter.builder("orders.created").register(registry).increment();
        Timer.builder("orders.create.duration").register(registry)
            .record(() -> doCreate(o));
    }
}
```
Эндпоинт `/actuator/prometheus` отдаёт метрики в формате, который `Prometheus` scrape'ит.

## Q11. Что такое экспоненциальные гистограммы в метриках?

Экспоненциальная гистограмма — бакеты (корзины) распределены по экспоненте (1, 2, 4, 8, …); подходит для латентности с большим разбросом. В `Prometheus` и `OpenTelemetry` используются для эффективного хранения и агрегации.

**Практика:** альтернатива — фиксированные бакеты; экспоненциальные дают хорошую точность при малом числе бакетов для широкого диапазона. В `Micrometer Timer` по умолчанию использует подходящее распределение бакетов; при кастомных гистограммах указывать границы вручную или использовать готовые пресеты.

## Q12. Как настроить метрики JVM (память, потоки, GC)?

В `Spring Boot` с `Micrometer` метрики `JVM` включаются автоматически (память, потоки, загрузка классов). Для `GC` нужна регистрация `GcMetrics` (в новых версиях `Micrometer` может быть автоматически). Эндпоинт `/actuator/prometheus` отдаёт `jvm_memory_used_bytes`, `jvm_threads_live_threads`, `jvm_gc_*` и др.

**Практика:** в `Grafana` используют готовые дашборды (`JVM Micrometer`) для визуализации. Алерты: рост `jvm_memory_used_bytes` выше порога; рост числа потоков; частые или длинные `GC`-паузы по `jvm_gc_*`.

## Q13. Что такое custom metrics и когда их добавлять?

`Custom` metrics — метрики, определённые приложением (счётчик заказов, размер очереди, бизнес-события). Добавлять когда стандартных метрик недостаточно для алертинга или анализа (например, число обработанных сообщений в consumer, число ошибок валидации). Через `MeterRegistry`: `Counter`, `Timer`, `Gauge`.

**Практика:** важно не создавать высокую cardinality (уникальные лейблы по пользователю/запросу — избегать). Лейблы — с малым множеством значений: `status`, `endpoint`, `error_type`. Пример: `Counter.builder("orders.created").tag("region", region).register(registry).increment();`.

## Q14. Как связать метрики и трейсы (например, в Grafana)?

Связь по времени и лейблам: в `Grafana` на одном дашборде запросы к `Prometheus` (метрики) и к `Jaeger / Tempo` (трейсы). `Exemplars` — ссылки от точки метрики к конкретному trace (в `Prometheus` 2.26+ и `OpenTelemetry`); по клику переходят к трейсу. Так можно от метрики «высокий p99» перейти к конкретному медленному запросу.

**Практика:** в `Spring Boot` с `OpenTelemetry` и `Micrometer` exemplars включаются при наличии `micrometer-registry-prometheus` и трассировки; в `Grafana` на панели с гистограммой латентности включить опцию «`Exemplars`» и указать источник трейсов (`Jaeger / Tempo`). При расследовании: открыть дашборд → клик по пику на графике p99 → переход к трейсу по exemplar → по `traceId` отфильтровать логи в `Loki / ELK`.

## Q15. Что такое Jaeger и Zipkin и чем они отличаются?

`Jaeger` и `Zipkin` — бэкенды для хранения и отображения трейсов. `Zipkin` — проще, меньше функций; `Jaeger` — полнофункциональный (интерфейс, запросы, интеграция с `Kubernetes`). Оба поддерживают `OpenTelemetry` как источник данных.

**Практика:** выбор часто по экосистеме (`Kubernetes` — `Jaeger`; легковесный вариант — `Zipkin`) или по облаку (`Tempo`, `Datadog`, `AWS X-Ray`). Экспорт из приложения — один формат (`OTLP` или `Zipkin`); бэкенд можно менять без смены инструментации.

## Q16. Как настроить трассировку в Spring Boot (OpenTelemetry)?

Добавить зависимости `OpenTelemetry` для `Spring Boot` (например, `opentelemetry-javaagent` или `Spring OpenTelemetry` starter). Настроить экспорт в `Jaeger / Zipkin` (`endpoint`, sampling). Автоинструментация для `HTTP`, `JDBC`, `Kafka` и др. включается агентом или стартером.

**Практика:** для кастомных spans — `Tracer` из `OpenTelemetry API`; вставить в критичные участки кода (бизнес-операции, вызовы внешних `API`). В `application.properties`: `endpoint` экспорта, sampling rate; в `Kubernetes` — переменные окружения или `ConfigMap`.

## Q17. Что такое cardinality метрик и почему она важна?

`Cardinality` — число уникальных комбинаций значений лейблов метрики. Высокая cardinality (например, лейбл `user_id` с миллионами значений) приводит к взрывному росту рядов в `Prometheus` и проблемам с памятью и производительностью.

**Практика:** ограничивать лейблы небольшим множеством значений (env, service, `endpoint`); не использовать идентификаторы пользователей или запросов в лейблах метрик. При добавлении новой метрики проверять: сколько уникальных комбинаций лейблов возможно; если растёт неограниченно — убрать или агрегировать лейбл.

## Q18. Как метрики и трейсы помогают при инцидентах?

Метрики: алерты срабатывают при аномалии (рост ошибок, латентности); дашборды показывают, какой сервис или эндпоинт деградировал. Трейсы: показывают конкретный путь запроса и где задержка или ошибка; по `traceId` связать с логами.

**Практика:** последовательность при инциденте: алерт по метрике → открыть трейсы за период → найти медленные/ошибочные трейсы → по `traceId` отфильтровать логи и локализовать причину. `Exemplars` в `Grafana` позволяют от точки на графике метрики перейти к конкретному трейсу.

## Q19. Что такое RED и USE методологии для метрик?

**RED** (`Rate`, `Errors`, `Duration / Utilization`, `Saturation`, `Errors`) — для ресурсов (`CPU`, диск, сеть): загрузка, насыщенность (очереди), ошибки. Методологии задают минимальный набор метрик для мониторинга сервисов и ресурсов; по ним строят дашборды и алерты.

**Практика:** для `HTTP`-сервиса в `Micrometer`: `Rate` — `Timer` или счётчик запросов; `Errors` — счётчик с лейблом `status=5xx` или `outcome=SERVER_ERROR`; `Duration` — гистограмма латентности (`Timer`). Для `USE` по `JVM`: `Utilization` — загрузка CPU/памяти; `Saturation` — длина очереди пула; `Errors` — исключения. В `Prometheus` алерты: например `rate(http_requests_total{status=~"5.."})/rate(http_requests_total) > 0.01` — доля 5xx выше 1%.

## Q20. Как экспортировать метрики в Prometheus из Java?

Приложение открывает `HTTP`-эндпоинт с метриками в формате `Prometheus` (текст). В `Spring Boot`: зависимость `micrometer-registry-prometheus`, эндпоинт `/actuator/prometheus`. `Prometheus` настроен на scrape этого `URL` (статически или через `Service Discovery` в `Kubernetes`).

**Практика:** альтернатива — `Pushgateway` для `short-lived` jobs (push вместо pull). В `Kubernetes` — `ServiceMonitor` (`Prometheus Operator / Service` для автообнаружения целей. `Scrape` interval обычно 15–30 с; для латентных метрик достаточно.

## Q21. Что такое exemplars и зачем они нужны?

`Exemplars` — связь точки на графике метрики с конкретным trace (например, exemplar хранит `traceId` и `spanId`). При просмотре скачка метрики можно перейти к конкретному трейсу и понять причину. Нужны для перехода от «что выросло» (метрика) к «какой запрос виноват» (трейс).

**Практика:** поддержка в `Prometheus` 2.26+, `OpenTelemetry`, `Grafana`. В `Spring Boot` с `Micrometer` и `OpenTelemetry` exemplars включаются при наличии трассировки; в `Grafana` на панели с гистограммой включить «`Exemplars`» и указать источник трейсов (`Jaeger / Tempo`).

## Q22. Как настроить алерты по метрикам (Prometheus, Alertmanager)?

В `Prometheus` задают правила алертов (`PromQL`): при выполнении условия алерт переходит в состояние firing. `Alertmanager` получает алерты, группирует, дедуплицирует и отправляет в каналы (email, `Slack`, `PagerDuty`).

**Практика:** пример правила: `rate(`http_requests_total`{status=~"5.."}[5m]) > 0.01` — доля 5xx выше 1%. Настройка `Alertmanager`: маршруты (routing), приёмники (receivers), шаблоны сообщений. Группировка по `alertname` и лейблам снижает шум; inhibition и silence для плановых работ.

## Q23. Что такое traceId и spanId и как они связаны?

`traceId` — уникальный идентификатор всего trace (одного запроса через систему); один для всех spans в trace. `spanId` — идентификатор одной операции (span); у каждого span свой `spanId`. Связь: span может ссылаться на родительский `spanId` (parent `spanId`); корневой span не имеет родителя.

**Практика:** по `traceId` выбирают все spans одного запроса; по `spanId` — конкретную операцию и её дочерние spans. В логах добавлять `traceId` (и при необходимости `spanId`) в `MDC` или в структурированный лог; тогда по `traceId` можно отфильтровать логи одного запроса в `ELK / Loki`.

## Q24. Как уменьшить объём данных трассировки в prod?

Меры: (1) `Sampling` — записывать только часть трейсов (процент или `tail-based` по ошибкам/латентности). (2) Ограничить атрибуты и размер событий (не логировать большие payload в span). (3) Сократить retention в хранилище трейсов. (4) Отключать инструментацию для неважных компонентов.

**Практика:** баланс между полнотой для отладки и затратами на хранение и передачу. В prod часто достаточно 1–10% `head-based` или `tail-based` (только ошибки и медленные); при инциденте временно повысить sampling. Атрибуты — только нужные для фильтрации (`endpoint`, status); не писать тело запроса в span.

## Q25. Как выбрать между метриками и трейсами для отладки?

Метрики — для выявления «где проблема» (какой сервис, эндпоинт, период): алерты, дашборды, агрегаты. Трейсы — для понимания «почему» в конкретном запросе: цепочка вызовов, задержки по узлам, ошибки по span.

**Практика:** типичный поток: метрики показывают рост латентности на сервисе A → открываем трейсы за период → смотрим медленные трейсы и видим, что задержка в вызове к БД или к сервису B. `Exemplars` позволяют от точки на графике перейти к конкретному трейсу.

## Q26. Что такое RED-метрики и USE-метрики?

`RED` (`Rate`, `Errors`, `Duration`) — для сервисов и запросов: количество запросов в секунду, доля ошибок, задержка (например, p50, p99). `USE` (`Utilization`, `Saturation`, `Errors`) — для ресурсов (`CPU`, диск, сеть): утилизация, насыщенность (очереди), ошибки. `RED` — для мониторинга `API` и микросервисов; `USE` — для инфраструктуры и узких мест.

**Практика:** оба подхода дополняют golden signals. В `Micrometer`: `Rate` и `Errors` — через `Timer` и счётчики с лейблом outcome; `Duration` — гистограмма латентности. Для `USE` по `JVM` — метрики памяти, потоков, `GC`; по инфраструктуре — `node_exporter`, `cAdvisor`.

## Q27. Как уменьшить объём и стоимость хранения трейсов в production?

`Sampling`: сохранять только часть трейсов (например, 1% или 100% ошибок + 0.1% успешных). `Tail-based` sampling: решение по полному трейсу (например, сохранять трейсы с ошибками или с высокой латентностью). Сокращение срока хранения; агрегация старых трейсов в метрики.

**Практика:** `OpenTelemetry` и бэкенды (`Jaeger`, `Tempo`) поддерживают sampling на коллекторе. Стоимость снижается при сохранении возможности расследования инцидентов. `Tail-based` предпочтителен в prod: ошибки и выбросы по латентности сохраняются; успешные «нормальные» трейсы отбрасываются.

## Q28. Что такое sampling в трассировке и когда его применять?

`Sampling` — решение, какие трейсы сохранять (все, доля, по правилам). `Head-based`: решение в начале трейса (например, 10% запросов). `Tail-based`: решение в конце (сохранять трейсы с ошибками или медленные). Применять при высокой нагрузке для снижения объёма и стоимости; `tail-based` предпочтителен для отладки (ошибки и выбросы сохраняются).

**Практика:** в dev можно 100% для отладки; в prod — долевой или `tail-based`. В `OpenTelemetry` настраивают `Sampler` (`ParentBased`, `RateLimiting`); в `Jaeger / Tempo` — `tail-based` sampling на коллекторе по атрибутам (status=error, duration>threshold).

## Q29. Как связать метрики приложения с бизнес-метриками?

Метрики приложения (`RPS`, latency, ошибки) дополняют бизнес-метрики (конверсия, заказы, отказы). Связь: общие теги (`user_segment`, `product_id`); дашборды с панелями «технические + бизнес»; алерты по бизнес-метрикам при падении конверсии и расследование по техническим (какой эндпоинт упал, latency).

**Практика:** экспорт бизнес-событий в `Prometheus / orders_created_total`, `payments_failed_total` с лейблами segment/region; на одном дашборде с техническими метриками (latency, error rate) по тем же сервисам.

## Q30. Как организовать алертинг по метрикам и трейсам?

Алерты в основном по метрикам (пороги по latency, error rate, доступности); по трейсам — реже (например, рост доли медленных трейсов). Каналы: `Alertmanager`, `PagerDuty`, `Slack`, email. Рутинг по severity и командам.

**Практика:** в алерте указывать ссылку на дашборд и пример трейса (exemplar). `Runbook` в описании алерта. Избегать шума: мало порогов, агрегация, подтверждение (например, 2 из 3 точек). Группировка в `Alertmanager` по `alertname` и лейблам; inhibition и silence для плановых работ.
