# Вопросы на собеседовании: `Data Lake и Lakehouse`

**Data Lake** — хранилище **сырых** данных любого формата на cheap storage (S3, ADLS, HDFS). **Lakehouse** — комбинация: lake-простота + warehouse-фичи (ACID, schema, indexing). Реализуется через **Delta Lake** (Databricks), **Apache Iceberg** (Netflix → Apache), **Apache Hudi** (Uber → Apache).

## Q1. (!) Что такое Data Lake?

**Data Lake** — централизованное хранилище для **сырых** данных в любом формате на дешёвом object storage. Главная идея: ничего не выкидывать на входе и не навязывать схему заранее — кладём как есть, разбираемся при чтении.

Что отсюда следует:

- **Schema-on-read** — структуру навешиваем в момент чтения, а не при записи. В DWH наоборот (schema-on-write): без подходящей схемы данные просто не загрузить. Озеро принимает всё, а цена этому — порядок наводит уже потребитель.
- **Любые форматы** — структурированные, полуструктурированные и неструктурированные: JSON, CSV, Parquet, Avro, изображения, видео.
- **Дешёвое хранилище** — S3 ~$0.023/GB в месяц против ~$23/TB у Snowflake. Поэтому держать большие архивы «на всякий случай» не разорительно.
- **Разделение хранения и вычислений** — данные лежат сами по себе, кластер поднимаем только на время обработки. Храним долго и дёшево, платим за compute лишь когда считаем.

**Сценарии применения:**

- **Архив сырых данных** — сохранить на случай, если структура понадобится позже.
- **Обучение ML** — большие неструктурированные датасеты, которым DWH-схема не нужна.
- **Исследование данных** — площадка для data scientists.
- **Staging для ETL** — промежуточный слой перед загрузкой в warehouse.

## Q2. (!) Чем Data Lake отличается от Data Warehouse?

Коротко: **Lake** хранит сырьё дёшево и навязывает схему при чтении, **Warehouse** хранит вычищенные структурированные данные с жёсткой схемой и быстрыми запросами. Lake оптимизирован под гибкость и объём, Warehouse — под скорость и управляемость.

| Критерий | Data Lake | Data Warehouse |
|----------|-----------|----------------|
| Схема | При чтении | При записи |
| Данные | Сырые, любые форматы | Структурированные, преобразованные |
| Стоимость хранения | Очень дёшево ($/TB) | Дорого ($/TB) |
| Скорость запросов | Медленно без оптимизации | Быстро (оптимизировано) |
| Пользователи | Data scientists, ML-инженеры | Аналитики, BI |
| Обновления | Чаще append-only | INSERT/UPDATE/DELETE |
| Управление (governance) | Сложно | Легко |
| Инструменты | Spark, Trino, Athena | Snowflake, BQ, Redshift |
| Эволюция схемы | Гибко | Жёстко структурно |

**Тренд — сближение.** Граница размывается: Lake получает свойства DWH через Lakehouse, а DWH учится читать external tables прямо с S3. На собеседовании важно показать, что это не «или-или», а две точки на одном спектре.

## Q3. (!) Что такое Lakehouse?

**Lakehouse** (термин от Databricks, 2020) — это попытка взять лучшее от обоих миров: хранить данные дёшево, как в озере, но работать с ними как в warehouse. Технически это:

- **Хранилище** — дешёвый object storage, как у Data Lake.
- **Возможности** — ACID, схема, индексы, как у DWH.

**Как это работает.** Поверх обычных Parquet-файлов кладётся **table format** — слой метаданных с транзакционным логом, который и даёт ACID, time travel и эволюцию схемы. Сами данные остаются открытыми Parquet-файлами на S3, меняется только то, как движок их «видит». Три основные реализации:

- **Delta Lake** (Databricks)
- **Apache Iceberg** (Netflix)
- **Apache Hudi** (Uber)

**Плюсы:**

- Одно хранилище для всего — не нужно гонять данные из lake в DWH и держать две копии.
- Дешёвое хранение, как у озера.
- ACID, time travel, эволюция схемы — то, чего в «голом» Parquet нет.
- Streaming и batch в одной системе.

**Минусы:**

- Зрелость ниже, чем у проверенного годами DWH.
- Производительность пока чуть уступает максимально оптимизированному DWH, хотя разрыв небольшой.

## Q4. (!) Где физически лежат данные Data Lake: S3, ADLS, GCS, HDFS?

Данные озера лежат в **object storage** — у каждого облака свой, плюс есть on-prem и self-hosted варианты. Все они дают одно и то же: дешёвое масштабируемое хранилище с REST-доступом, на которое движки кладут Parquet-файлы.

| Хранилище | Провайдер | Особенности |
|---------|----------|-------------|
| **S3** | AWS | Самое популярное, eventual consistency (с 2020 — strong) |
| **ADLS Gen2** | Azure | Иерархическое пространство имён (hierarchical namespace) |
| **GCS** | Google | Strong consistency |
| **HDFS** | On-prem (Hadoop) | Legacy, требует кластер |
| **MinIO** | Self-hosted (S3-совместимое) | Open-source альтернатива |

**Главное.** Облачный object storage доминирует с 2010-х и вытеснил HDFS почти везде. HDFS остаётся только в legacy on-prem инсталляциях, потому что требует обслуживать собственный кластер. MinIO выбирают, когда нужен S3-совместимый API на своём железе.

## Q5. Чем object storage отличается от HDFS?

Ключевое различие: **object storage — это key-value хранилище объектов с REST-доступом и безграничным managed-масштабированием**, а HDFS — настоящая распределённая файловая система с директориями и data locality, которую нужно держать на собственных серверах.

| Критерий | Object Storage (S3) | HDFS |
|----------|---------------------|------|
| Тип | Key-value (объекты) | Файловая система |
| Иерархия | Эмулируется через ключи | Настоящие директории |
| API | REST | POSIX-подобный |
| Масштабирование | Безграничное (managed) | Через HDFS DataNodes |
| Стоимость | Низкая ($0.023/GB) | Высокая (серверы + обслуживание) |
| Операции | Стиль append-only (кладём новую версию) | Полный набор файловых операций |
| Связь с вычислениями | Разделены | Часто связаны (data locality) |

**Итог.** Object storage победил за счёт цены и managed-масштабирования: не нужно администрировать кластер, а ёмкость практически безгранична. Historic-преимущество HDFS — data locality (вычисления рядом с данными) — перестало быть решающим, когда сеть в облаке стала быстрой. Сегодня HDFS встречается только в legacy-системах.

## Q6. (!) Parquet — что это и зачем?

**Apache Parquet** — колоночный (columnar) формат хранения, заточенный под аналитику. Суть колоночности: значения одной колонки лежат вместе, а не вперемешку по строкам. Из этого вытекают почти все его преимущества.

**Особенности и почему они работают:**

- **Колоночная организация** — однотипные значения рядом сжимаются лучше, а аналитический запрос обычно читает 2-3 колонки из сотни, поэтому остальные просто не сканируются.
- **Схема встроена** в файл — не нужен внешний реестр, чтобы прочитать данные.
- **Predicate pushdown** — в footer лежит min/max-статистика по блокам, и движок пропускает блоки, которые заведомо не попадают под фильтр (`WHERE date = ...`).
- **Сжатие** — Snappy (по умолчанию), Gzip, Zstd, Brotli.
- **Вложенные типы** — structs, arrays, maps.

```python
import pyarrow.parquet as pq
table = pq.read_table('data.parquet', columns=['id', 'name'])
# читает только эти колонки → быстро
```

**Итог.** Parquet — de facto стандарт для аналитических файлов в Lake; именно поверх него строятся все три table format (Delta, Iceberg, Hudi).

## Q7. Что такое ORC и чем он отличается от Parquet?

**Apache ORC** (Optimized Row Columnar) — колоночный формат, созданный под **Hive**. По устройству и идеям он почти близнец Parquet, поэтому на собеседовании главное — объяснить, чем они различаются на практике, а не пересказывать одинаковые свойства.

**Общее с Parquet:** колоночная раскладка, сжатие, predicate pushdown, встроенная схема.

**В чём разница:**

- В отдельных случаях ORC даёт чуть лучшее сжатие и производительность.
- Но он заметно менее популярен — Parquet выиграл гонку за узнаваемость и поддержку в инструментах.

**Эмпирическое правило:** в экосистеме Hive — ORC, во всём остальном — Parquet.

## Q8. Что такое Avro и для чего его применяют?

**Apache Avro** — **строчно-ориентированный** (row-oriented) бинарный формат, главная фишка которого — гибкая эволюция схемы. В отличие от Parquet/ORC он хранит данные построчно, поэтому подходит не для аналитики, а для передачи сообщений.

**Особенности:**

- **Строчная организация** — вся строка лежит вместе, в отличие от колоночных Parquet/ORC.
- **Схема** встроена в файл или хранится отдельно в Schema Registry.
- **Эволюция схемы** — можно добавлять/удалять поля без перекомпиляции читателей и писателей; читатель и писатель могут работать с разными версиями схемы.
- **Компактное бинарное** представление.

**Сценарии применения:**

- **Сообщения Kafka** (с Confluent Schema Registry) — основное применение.
- Потоковые данные.
- RPC (Avro IDL).

**Не для аналитики.** Чтобы прочитать одну колонку, строчному формату приходится поднимать всю строку — для сканирования колонок это неэффективно. Поэтому для запросов в озере берут Parquet, а Avro оставляют транспорту.

## Q9. (!) Как выбрать между Parquet, ORC и Avro?

Главное различие — раскладка данных: **Parquet и ORC колоночные** (хороши для аналитики), **Avro строчный** (хорош для передачи и streaming). Отсюда и распределение ролей.

| Критерий | Parquet | ORC | Avro |
|----------|---------|-----|------|
| Раскладка | Колоночная | Колоночная | Строчная |
| Сценарий | Аналитика | Аналитика в Hive | Streaming, RPC |
| Сжатие | Отличное | Отличное | Хорошее |
| Эволюция схемы | Ограничена | Ограничена | **Отличная** |
| Скорость чтения (колонка) | Быстро | Быстро | Медленно (нужна вся строка) |
| Скорость чтения (строка) | Медленно | Медленно | Быстро |
| Экосистема | Spark, Pandas, Trino, ... | Hive, Pig | Kafka, Flink |

**Эмпирическое правило:**

- **Parquet** — аналитика в Lake (выбор по умолчанию).
- **Avro** — Kafka и streaming, где важна эволюция схемы.
- **ORC** — проекты, завязанные на Hive.

## Q10. (!) Delta Lake — что это?

**Delta Lake** — open-source table format от Databricks. Он превращает обычные Parquet-файлы на S3/ADLS в **транзакционную таблицу** за счёт одного приёма: рядом с данными ведётся transaction log, и именно лог, а не список файлов, определяет, что входит в таблицу.

**Что это даёт поверх голого Parquet:**

- **ACID-транзакции** на object storage.
- **Time travel** — запросы к прошлым версиям таблицы.
- **Эволюция схемы** плюс её проверка (enforcement) — несовместимые записи отклоняются.
- **MERGE / UPSERT** — обновления и слияния, которых в обычном Parquet нет.
- **Streaming и batch** в единой модели.

**Структура на диске:**
```
table/
  ├── _delta_log/             ← transaction log
  │   ├── 00000000.json       ← версия 0
  │   ├── 00000001.json       ← версия 1
  │   └── 00000010.checkpoint.parquet
  └── part-00000.parquet     ← actual data files
```

**Как это читается.** `_delta_log` — это серия JSON-файлов, каждый описывает одну операцию (добавлены/удалены такие-то файлы). Чтобы получить актуальную таблицу, движок проигрывает лог и берёт только relevant Parquet-файлы. Периодические `.checkpoint.parquet` сворачивают историю, чтобы не перечитывать весь лог с нуля.

## Q11. (!) Что такое Apache Iceberg и чем он отличается от Delta?

**Apache Iceberg** (от Netflix, top-level в Apache с 2020) — прямой конкурент Delta Lake. Решает ту же задачу (ACID-таблицы поверх Parquet), но делает ставку на **открытость** и **скрытое партиционирование**.

**Чем выделяется:**

- **Скрытое партиционирование (hidden partitioning)** — Iceberg сам отслеживает связь «значение → партиция» (например, по `day`), и физическую колонку партиционирования в данные класть не нужно. Пользователь пишет фильтр по обычной колонке, а Iceberg сам отсекает ненужные партиции. В Hive-стиле приходилось вручную писать `WHERE dt=...`, иначе partition pruning не срабатывал.
- **Snapshot isolation** — каждое изменение порождает новый snapshot, читатели видят согласованное состояние.
- **Богатые метаданные** — множество Avro-файлов со статистикой, что ускоряет планирование запросов.
- **Эволюция схемы** — лучшая в классе (переименование, удаление, изменение порядка и типов колонок).
- **Множество движков** — Spark, Trino, Flink, Snowflake (с 2024).

**Где используют:** Apple, Netflix, Stripe, Adobe, Pinterest.

**Итог.** Iceberg — лидер по внедрению вне экосистемы Databricks именно за счёт vendor-neutrality: его одинаково хорошо читают разные движки.

## Q12. (!) Что такое Apache Hudi и в чём его специализация?

**Apache Hudi** (от Uber, в Apache с 2017) — самый старый из трёх table format. Его отличает заточенность под **частые upsert'ы и streaming**: там, где Delta и Iceberg в первую очередь про аналитические таблицы, Hudi с самого начала строился вокруг обновлений отдельных записей.

**Особенности:**

- **Оптимизирован под streaming inserts/updates** — UPSERT здесь первоклассная операция, а не надстройка.
- **Два режима хранения** — выбор компромисса между скоростью записи и скоростью чтения:
  - **Copy-on-Write (CoW)** — переписывает Parquet-файлы целиком (как Delta/Iceberg); чтение быстрое, запись дороже.
  - **Merge-on-Read (MoR)** — пишет дельты в log-файлы поверх base-файлов; запись быстрая, но чтение должно слить base + log, поэтому медленнее.
- **Индексирование** — Hudi ведёт индекс «ключ → файл», чтобы при upsert быстро находить нужный файл и не сканировать всю таблицу.

**Сценарии применения:** там, где много обновлений — CDC-пайплайны, потоковые агрегации.

**Итог.** Hudi менее популярен, чем Delta/Iceberg, но остаётся сильным выбором в нише streaming с upserts.

## Q13. (!) Как выбрать между Delta Lake, Iceberg и Hudi?

Все три дают ACID и time travel поверх Parquet, поэтому выбор сводится к контексту: **Delta — если вы в Databricks**, **Iceberg — если нужна совместимость с разными движками**, **Hudi — если в центре streaming-upserts**. Таблица — для деталей.

| Критерий | Delta Lake | Apache Iceberg | Apache Hudi |
|----------|------------|----------------|-------------|
| Создатель | Databricks | Netflix | Uber |
| Тип | Open-source | Apache | Apache |
| Главный движок | Spark / Databricks | Trino, Spark, Flink | Spark, Flink |
| ACID | Да | Да | Да |
| Time travel | Да | Да (snapshots) | Да |
| Эволюция схемы | Хорошая | **Лучшая** | Хорошая |
| Скрытое партиционирование | Нет | **Да** | — |
| Streaming inserts | Хорошо | Хорошо | **Лучше** |
| Поддержка многих движков | Растёт | **Отличная** | Хорошая |
| Внедрение | Огромное (Databricks) | Сильно растёт (Netflix, Apple) | Среднее (стек Uber) |

**Как выбирать:**

- Работаете в Databricks — **Delta** (нативная поддержка).
- Нужно много движков (Trino, Snowflake, Spark) — **Iceberg** (максимальная открытость).
- Упор на стриминг с upserts — **Hudi** (его профильная задача).

## Q14. (!) ACID transactions на S3 — как?

У object storage нет транзакций — он умеет только класть и читать объекты (а до 2020 S3 был ещё и eventually consistent). ACID на S3 даёт table format: он реализует свойства транзакций средствами самого лога, без блокировок на стороне хранилища.

**Как набираются свойства ACID:**

1. **Атомарность** — данные пишутся в новые файлы, а «коммитом» становится одна атомарная запись в `_delta_log`; пока её нет, изменений как будто не было.
2. **Изоляция** — snapshot isolation: каждый читатель видит таблицу на момент конкретной версии и не замечает чужих незавершённых записей.
3. **Согласованность** — все читатели видят один и тот же snapshot, а не половину обновления.
4. **Конкурентность** — параллельные писатели разруливаются оптимистично через номера версий в логах.
5. **Долговечность** — обеспечивает сам S3 (11 девяток надёжности).

**Что происходит при конфликте двух писателей:**
```
Writer A: читает версию 5, вносит изменения → пытается записать версию 6
Writer B: читает версию 5, вносит изменения → пытается записать версию 6
Коммитит только один; проигравший делает retry с новой версией.
```

Это **optimistic concurrency control**: писатели не берут блокировок заранее, а проверяют конфликт в момент коммита. Дёшево, когда параллельных записей в одну таблицу немного; при высокой конкуренции растёт число retry.

## Q15. (!) Что такое time travel и как он работает?

**Time travel** — возможность запросить таблицу в том виде, в каком она была на конкретную версию или момент времени. Работает «бесплатно» как побочный эффект transaction log: старые версии файлов не удаляются сразу, а лог хранит, какие файлы относились к каждой версии — поэтому движок может восстановить любое прошлое состояние.

```sql
-- Delta Lake / Iceberg
SELECT * FROM my_table VERSION AS OF 5;
SELECT * FROM my_table TIMESTAMP AS OF '2025-04-15 10:00:00';

-- Spark
spark.read.format("delta").option("versionAsOf", 5).load(path)
```

**Сценарии применения:**

- **Аудит** — посмотреть, как таблица выглядела вчера.
- **Откат** — восстановить данные после случайного удаления или сбойного пайплайна.
- **Воспроизводимость** — переобучить ML-модель ровно на той же версии данных.
- **A/B-сравнение** — сопоставить текущую версию с предыдущей.

**Компромисс.** За time travel платят местом: старые версии файлов занимают хранилище, пока их не очистит `VACUUM`. Поэтому настраивают retention period — баланс между глубиной истории и стоимостью.

## Q16. Что такое schema evolution и как она устроена?

**Schema evolution** — возможность менять схему таблицы (добавлять, удалять, переименовывать колонки, повышать тип) без перезаписи всех данных. В table format схема — это метаданные в логе, поэтому изменить её можно одной DDL-командой, не трогая старые Parquet-файлы.

```sql
-- Add column
ALTER TABLE my_table ADD COLUMN new_field STRING;

-- Rename
ALTER TABLE my_table RENAME COLUMN old TO new;

-- Drop
ALTER TABLE my_table DROP COLUMN deprecated;

-- Type change
ALTER TABLE my_table ALTER COLUMN amount TYPE DECIMAL(20, 4);
```

**Где полнее.** В Iceberg поддержка самая полная — включая переупорядочивание, удаление и повышение типа колонок. В Delta эти возможности добавлялись постепенно.

**Schema enforcement — обратная сторона.** Эволюция не означает «принимаем что угодно»: enforcement отклоняет запись, если её схема несовместима с таблицей. Это защищает от случайной порчи данных:

```python
df.write.mode("append").save("table")
# Если schema df ≠ table schema → error
```

## Q17. (!) Что такое Z-Order и зачем нужна кластеризация данных?

**Z-Order** — многомерная кластеризация: данные перекладываются так, чтобы близкие значения сразу по нескольким колонкам попадали в одни файлы. Обычная сортировка хорошо группирует по одной колонке, а Z-Order — компромисс, который держит локальность по нескольким сразу.

```sql
OPTIMIZE my_table ZORDER BY (user_id, country);
```

**Почему это ускоряет запросы.** Если значения сгруппированы, нужные строки лежат в немногих файлах, и data skipping по min/max-статистике отбрасывает больше нерелевантных файлов. Запросы по `user_id` и/или `country` начинают читать меньше данных.

**Как называется в разных форматах:** в Delta Lake это Z-Order, в Iceberg — sort orders (та же идея кластеризации при записи).

**Когда применять.** Для высокоселективных запросов с фильтрами по нескольким колонкам. Если запросы всегда по одной колонке, хватит обычной сортировки или партиционирования.

## Q18. Что такое compaction и зачем она нужна?

**Compaction (уплотнение)** — слияние множества мелких файлов в небольшое число крупных. Нужна потому, что streaming inserts постоянно плодят маленькие файлы, а каждый файл — это накладные расходы на открытие/закрытие, чтение метаданных и отдельную таску. Из-за этого запросы деградируют, даже если данных немного.

**Как запускают:**

```sql
OPTIMIZE my_table
WHERE date >= '2025-04-01';

-- Compact + Z-Order
OPTIMIZE my_table
WHERE date >= '2025-04-01'
ZORDER BY (user_id);
```

`OPTIMIZE` собирает из множества мелких файлов меньшее число крупных, а добавив `ZORDER BY`, уплотнение можно совместить с кластеризацией.

**Не путать с VACUUM.** Compaction уменьшает число файлов в текущей версии, но старые версии файлов остаются (нужны для time travel). Их физически удаляет `VACUUM` после истечения `retention period`.

## Q19. (!) Что такое medallion-архитектура (Bronze, Silver, Gold)?

**Medallion** (от Databricks) — типовой способ организовать данные в Lakehouse в три слоя нарастающего качества. Идея: данные проходят путь от сырья к готовым витринам ступенчато, и на каждой ступени становятся чище и пригоднее для бизнеса. Так проще отлаживать пайплайн и переиспользовать промежуточные результаты.

```
[Source] → Bronze (raw, append-only)
           ↓ cleaning, dedupe
           Silver (validated, deduplicated)
           ↓ business logic, joins
           Gold (aggregated, BI-ready)
```

| Слой | Содержание |
|-------|-----------|
| **Bronze** | Сырые данные как есть. Минимум преобразований. |
| **Silver** | Очищенные, дедуплицированные, объединённые. Атомарные сущности. |
| **Gold** | Бизнес-агрегаты, витрины для BI. |

**Аналогия.** Это та же идея, что staging/intermediate/marts в dbt, только сформулированная в терминах Lakehouse.

## Q20. (!) Data Mesh — что это?

**Data Mesh** (Zhamak Dehghani, 2019) — социотехническая парадигма, которая предлагает не централизовать все данные в одной команде, а раздать владение бизнес-доменам. Это ответ на узкое место монолитного озера: центральная data-команда не успевает за десятками доменов и становится бутылочным горлышком.

**4 принципа:**

1. **Владение доменом** — каждый бизнес-домен владеет своими данными и отвечает за них.
2. **Данные как продукт** — доменная команда обеспечивает качество, документацию и SLA, как у настоящего продукта.
3. **Self-serve data platform** — централизованная инфраструктура, чтобы доменам не приходилось строить пайплайны с нуля.
4. **Федеративное управление (governance)** — общие стандарты задаются централизованно, но контроль локальный.

**В чём контраст:**

- **Монолитный Data Lake** — всё делает одна центральная команда (плохо масштабируется по людям).
- **Data Mesh** — владение распределено по доменам, а платформа остаётся общей.

**Плюсы:** масштабируемость по командам, доменная экспертиза рядом с данными, понятная ответственность.
**Минусы:** сложно внедрить, требует организационной зрелости; без дисциплины распределённое владение легко превращается в data swamp.

**Реальность.** Это модный термин, но на практике внедряется тяжело — мешают чаще организационные, чем технические причины.

## Q21. Как оптимизировать стоимость хранения по тирам (hot/warm/cold)?

Главная идея: данные обращаются неравномерно — свежие читают часто, старые почти никогда. Поэтому S3 предлагает **storage classes** с компромиссом «цена против скорости доступа»: чем реже нужны данные, тем дешевле хранение, но тем дольше и дороже извлечение.

**S3 storage classes:**

| Класс | Задержка | Стоимость (за GB/месяц) | Сценарий |
|-------|---------|---------------------|----------|
| **S3 Standard** | мс | $0.023 | Горячие данные |
| **S3 Standard-IA** | мс | $0.0125 | Менее частый доступ |
| **S3 Glacier Instant** | мс | $0.004 | Архив с быстрым извлечением |
| **S3 Glacier Flexible** | мин-часы | $0.0036 | Архив |
| **S3 Glacier Deep Archive** | 12 ч | $0.00099 | Комплаенс, доступ крайне редко |

**Lifecycle policies — автоматизация.** Вручную переносить объекты между классами не нужно: правило по возрасту объекта само сдвигает его в более холодный тир.

```json
{
  "Rules": [
    {"Days": 30, "StorageClass": "STANDARD_IA"},
    {"Days": 90, "StorageClass": "GLACIER_IR"},
    {"Days": 365, "StorageClass": "DEEP_ARCHIVE"}
  ]
}
```

**Эффект.** На редко используемых данных тиринг экономит до 80% стоимости хранения. Подвох — за извлечение из Glacier-классов платят отдельно и ждут, поэтому в холодные тиры отправляют только то, что почти наверняка не понадобится скоро.

## Q22. (!) Какие движки умеют работать с Lakehouse?

Поскольку table format лежит поверх открытых Parquet-файлов, читать одну и ту же таблицу могут разные движки. Степень поддержки зависит от формата: Iceberg читают почти все, Delta — растущий круг, Hudi — поуже.

**Spark** — поддерживает все три (Delta, Iceberg, Hudi)
**Databricks** — нативно Delta
**Snowflake** — внешние таблицы Iceberg (с 2023+)
**BigQuery** — external tables на Iceberg
**Trino / Presto** — Iceberg, Delta, Hudi
**Flink** — Iceberg, Hudi (для стриминга)
**Athena** (AWS) — Iceberg, Delta
**ClickHouse** — Iceberg (с 2024)
**DuckDB** — Iceberg, Delta

**Вывод.** Возможность подключить много движков к одной таблице — главный аргумент в пользу Iceberg: он самый «открытый» из трёх, и данные не оказываются заперты в одном вендоре.

## Q23. Зачем нужны Trino / Presto для запросов к озеру?

**Trino** (бывший PrestoSQL) — распределённый SQL-движок, который не хранит данные сам, а исполняет запросы прямо там, где они лежат. Его суперсила — **федеративные запросы**: одним SQL-запросом джойнить данные из разных источников (S3, PostgreSQL, Kafka), не перегружая их предварительно в одно место.

```sql
-- Один query через несколько data sources
SELECT u.name, COUNT(o.id)
FROM postgres.public.users u
JOIN s3.warehouse.orders o ON u.id = o.user_id
GROUP BY u.name;
```

**Сценарии применения:**

- Запросы к Lake (Iceberg, Delta, Hudi, обычный Parquet).
- Федеративные запросы поверх смеси источников (БД, S3, Kafka).
- Ad-hoc анализ на огромных датасетах без отдельного ETL.

**Где используют:** Netflix, LinkedIn, Pinterest, Slack.

**На заметку:** Starburst — managed-версия Trino, если не хочется поднимать кластер самостоятельно.

## Q24. (!) В чём суть small files problem?

**Small files problem** — деградация производительности из-за множества мелких файлов (1-10 KB) вместо немногих крупных. Корень проблемы в том, что у движка есть фиксированные накладные расходы на каждый файл, и при тысячах крошечных файлов они начинают доминировать над полезной работой:

- на каждый файл — чтение метаданных и footer;
- на каждый файл — отдельная Spark-таска (планирование, запуск);
- на каталог — дорогие S3 LIST-операции.

**Откуда берутся мелкие файлы:**

- стриминг с короткими интервалами (каждый микробатч — новый файл);
- слишком детальное партиционирование (например, по часу × user_id);
- удаления и обновления, порождающие мелкие файлы.

**Как лечить:**

- **Compaction** — слить мелкие в крупные (`OPTIMIZE` в Delta, `rewrite_data_files` в Iceberg).
- **Адекватное партиционирование** — не дробить слишком мелко.
- **Буферизация при стриминге** — накапливать данные пакетами (например, ~по часу), а не писать на каждое событие.

## Q25. Что такое data swamp и как его избежать?

**Data swamp** («болото данных») — это Data Lake, оставшийся без governance и превратившийся в свалку, из которой нельзя достать ничего полезного. Гибкость озера (schema-on-read, любые форматы) без дисциплины оборачивается хаосом — это обратная сторона его главного достоинства.

**Симптомы:**

- никто не знает, что лежит в каких файлах;
- схемы меняются бесконтрольно и ломают потребителей;
- копятся дубли, мусор и сломанные пайплайны;
- нет lineage и документации — непонятно, откуда взялись данные;
- проблемы с комплаенсом: где лежат персональные данные, никто не отвечает.

**Профилактика:**

- **Каталог** (Hive Metastore, AWS Glue, Unity Catalog) — единый реестр таблиц и схем.
- **Проверки качества данных** (Great Expectations, dbt tests) — ловить мусор на входе.
- **Отслеживание lineage** (OpenLineage, Marquez, Datahub) — видеть, откуда и куда текут данные.
- **Контракты данных** между производителями и потребителями — чтобы схема не менялась внезапно.
- **Документация** — не опция, а обязательная часть.

## Q26. (!) Зачем нужны каталоги метаданных (AWS Glue, Hive Metastore, Unity)?

**Каталог** — реестр, который связывает имя таблицы с её схемой, расположением файлов и партициями. Без него движок видит на S3 лишь набор Parquet-файлов и не знает, что это «таблица `orders`». Каталог — это то, что превращает кучу файлов в осмысленную таблицу, к которой можно обратиться по имени из SQL.

| Каталог | Вендор | Особенности |
|---------|--------|-------------|
| **Hive Metastore** | Apache | Старый стандарт, Java |
| **AWS Glue** | AWS | Managed, интеграция с S3 |
| **Unity Catalog** | Databricks | Современный, governance, lineage |
| **Iceberg REST Catalog** | Apache | Vendor-neutral спецификация |
| **Apache Polaris** | Snowflake | Каталог Iceberg (с 2024) |
| **Nessie** | Project Nessie | Git-подобный для данных |

```sql
-- Через catalog query
SELECT * FROM glue_catalog.my_db.my_table;
```

**Тренд.** Индустрия сходится вокруг Iceberg REST Catalog как открытого, vendor-neutral стандарта — чтобы каталог не привязывал данные к конкретному облаку или вендору.

## Q27. (!) Какой table format выбрать в 2026 году?

Короткий ответ: **по умолчанию Iceberg, если вы не в Databricks**. Выбор зависит от двух факторов — вендора, на котором вы работаете, и характера нагрузки (batch против streaming-upserts). Дерево решений помогает не перебирать всё подряд.

**Дерево решений:**

```
Используешь Databricks?
  → Delta Lake

Хочешь max vendor-neutrality (Trino, Snowflake, Spark, Flink)?
  → Iceberg

Сильный focus на streaming upserts (CDC pipelines)?
  → Hudi

Pure batch analytics, simple use case?
  → Plain Parquet (ещё актуален!)
```

**Главный тренд.** Iceberg становится de facto стандартом в мульти-вендорном мире: Snowflake, BigQuery, AWS Athena и даже Databricks добавили его поддержку. Когда все крупные вендоры читают один формат, выбор в его пользу снижает риск vendor lock-in.

## Q28. Как сочетаются streaming и Lakehouse?

Lakehouse позволяет писать потоковые данные прямо в транзакционную таблицу: stream-движок коммитит микробатчи в table format, и те же данные сразу доступны для batch-запросов и аналитики. Это убирает классическое разделение «отдельная система для стрима, отдельная для аналитики».

```python
# Spark Structured Streaming → Delta Lake
spark.readStream.format("kafka")...load() \
     .writeStream \
     .format("delta") \
     .option("checkpointLocation", "...") \
     .outputMode("append") \
     .start("delta://my_table")
```

**Типовые связки:**

- **Delta Live Tables** (Databricks) — декларативные потоковые пайплайны.
- **Iceberg + Flink** — сильная пара для стриминга.
- **Hudi + Flink** — самый зрелый вариант для CDC.

**Что это даёт:**

- одно хранилище и для streaming, и для batch — не нужно дублировать инфраструктуру;
- низколатентное чтение из потоковых таблиц;
- time travel работает и для потоковых данных.

**Итог.** Конвергенция стрима и аналитики в одном хранилище — главное направление развития Lakehouse.
