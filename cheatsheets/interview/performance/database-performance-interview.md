# Вопросы на собеседовании: `Database Performance`

`Database Performance` — **топ-1 причина медленных приложений**. В 90% случаев медленные ответы = плохой запрос, отсутствующий индекс, N+1, исчерпанный connection pool. Знание EXPLAIN, pg_stat_statements, execution plan — обязательный навык senior-backend.

## Q1. (!) Как диагностировать slow query?

Действуйте по воронке: сначала **найти** проблемный запрос, затем **воспроизвести** его, разобрать через `EXPLAIN ANALYZE`, выдвинуть гипотезу фикса, проверить и выкатить. Главная ошибка новичка — сразу «добавить индекс наугад» без замера. Ниже — пошаговый процесс.

**1. Найти проблемный запрос.** Виновника ищем сверху вниз — от пользовательской боли к конкретному SQL:
- APM-инструмент (DataDog, New Relic) показывает медленный endpoint — отсюда видно, в какой запрос упирается время
- `pg_stat_statements` — топ-N запросов по суммарному / среднему времени (нормализованные по форме запроса)
- Slow query log (порог, например 1 с) ловит всё, что превышает лимит

**2. Воспроизвести.** Без воспроизведения нельзя проверить фикс:
- Получить запрос + параметры
- Прогнать в тестовом окружении на объёме данных, близком к прод (на пустой таблице любой план «быстрый»)

**3. EXPLAIN ANALYZE:**
```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE user_id = 123 AND status = 'PAID';
```

**4. Найти узкое место** в плане. Типичные сигнатуры проблем:
- **Seq Scan** большой таблицы → отсутствует индекс?
- **Sort** с уходом на диск → слишком маленький work_mem?
- **Nested Loop** на многомиллионных таблицах → неверный план; ошибся порядок join?
- **Высокий Buffers: read** → промах кэша, холодные данные с диска

**5. Сформулировать гипотезу фикса** под найденное узкое место:
- Добавить индекс
- Переписать запрос
- Подкрутить work_mem / конфиг
- Партицировать таблицу

**6. Проверить.** EXPLAIN ANALYZE после изменения и сравнить с базой: planning time, execution time, фактические rows, buffers. Если стало не лучше — гипотеза неверна, возвращаемся к шагу 4.

**7. Выкатить и мониторить.** В прод, затем следить за метриками (latency, время запроса) — на проде распределение данных и кэш отличаются от теста.

**Чек-лист на первом касании** (быстрые подозреваемые до глубокого анализа):
- Есть индекс на колонках WHERE?
- Статистика актуальна (`ANALYZE`)?
- Запрос возвращает вменяемое число строк (не SELECT *)?
- Нет ли несовпадения типов или функции на индексируемой колонке (`WHERE LOWER(email) =` ломает обычный индекс)?

## Q2. (!) Чем EXPLAIN отличается от EXPLAIN ANALYZE?

Коротко: `EXPLAIN` показывает план, который планировщик **собирается** выполнить (только оценки, запрос не запускается), а `EXPLAIN ANALYZE` **реально выполняет** запрос и добавляет фактические тайминги и число строк. Главная ценность ANALYZE — увидеть, где оценка планировщика расходится с реальностью.

**EXPLAIN** — планируемый план (оценки):
- Быстро, без реального выполнения
- Оценочные costs / rows
- Гипотетический — годится, когда запрос слишком тяжёлый, чтобы его реально гонять

**EXPLAIN ANALYZE** — реально выполняет запрос и замеряет:
- Реальные тайминги, реальное число строк рядом с оценками
- Выявляет **расхождение оценки и факта** — главный признак плохой статистики
- Медленный запрос выполняется столько же (ANALYZE не сокращает выполнение, а добавляет к нему замер)
- **Внимание:** для DML запрос выполняется по-настоящему! Чтобы не изменить данные, оберните: `BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;`

**Полезные опции:**
```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT JSON)
SELECT ...;
```

- **BUFFERS:** shared buffers hit / read — показывает эффективность кэша (сколько прочитано из памяти, сколько с диска)
- **VERBOSE:** выводит списки колонок
- **FORMAT JSON/YAML/XML:** машиночитаемый вывод для инструментов (например, визуализатор pev2)
- **SETTINGS:** показывает не-дефолтные значения конфига, повлиявшие на план
- **WAL:** число записанных WAL-записей (PG 13+)

**Как читать вывод:**
- `actual rows=100` против `rows=10000` → оценка ошибается в 100× → статистика устарела, нужен `ANALYZE`
- `Buffers: shared hit=X read=Y` — read = диск, hit = кэш; высокий read = холодные данные
- `Execution Time: 234 ms` — реальная длительность

**Визуализаторы** (для больших планов читать текст тяжело):
- **pev2** / **explain.depesz.com** — подсвечивают узкие места цветом
- **Dalibo Visual Explain**

**Подводный камень:** холодный прогон не равен тёплому. Прогоните 2 раза — первый бьёт по диску, второй идёт из кэша. Чтобы отличить одно от другого, всегда добавляйте `BUFFERS`.

## Q3. (!) Как читать execution plan?

**План — это дерево операций**, которое выполняется снизу вверх и изнутри наружу: самые глубоко вложенные (с наибольшим отступом) узлы дают строки родительским. Читая план, идите от листьев к корню и ищите узел, где время или число строк резко выросло — там узкое место.

```
Nested Loop  (cost=0.42..8.46 rows=1 width=128) (actual time=0.05..0.12 rows=1 loops=1)
  -> Index Scan using users_pkey on users  (cost=0.28..8.29 rows=1 width=64)
       Index Cond: (id = 123)
  -> Index Scan using orders_user_id_idx on orders  (cost=0.14..0.16 rows=1 width=64)
       Index Cond: (user_id = users.id)
       Filter: (status = 'PAID')
```

**Как читать каждый узел:**
- **Отступ:** глубже = выполняется раньше (сначала листья)
- В строке узла: операция, cost, rows, width, actual time
- `cost=startup..total` — не миллисекунды, а абстрактные единицы планировщика; важно соотношение между узлами, а не абсолютное число
- `rows` — оценка планировщика; `actual time` — реальный замер (сравнивайте эти две величины: расхождение = плохая статистика)
- `loops` — сколько раз узел выполнился; реальный вклад узла = `actual time × loops` (легко недооценить узел внутри Nested Loop)

**Ключевые типы узлов:**
- **Seq Scan:** полное сканирование таблицы
- **Index Scan:** идёт по указателям индекса к строкам
- **Index Only Scan:** индекс содержит все нужные колонки (быстро)
- **Bitmap Heap Scan + Bitmap Index Scan:** пакетное чтение, отсортированное по страницам диска
- **Hash Join:** строит хэш меньшей таблицы
- **Merge Join:** обе стороны отсортированы; сливает их
- **Nested Loop:** для каждой строки внешней таблицы сканирует внутреннюю
- **Sort:** сортирует результат; уход на диск — плохо
- **Aggregate / HashAggregate:** GROUP BY
- **Gather / Gather Merge:** объединение результатов параллельных воркеров

**Тревожные признаки** (что искать в первую очередь):
- `rows=1 (actual rows=1000)` — грубый просчёт оценки, планировщик мог выбрать неверную стратегию
- `Sort Method: external merge Disk: 500MB` — сортировка ушла на диск, мал work_mem
- `Seq Scan` большой таблицы без фильтра → отсутствует индекс
- `Nested Loop` с большой внешней таблицей → плохо: каждая строка запускает внутренний скан, ожидался Hash Join
- Высокий `Rows Removed by Filter` — много строк прочитано и отброшено; условие лучше затащить в index condition

## Q4. Чем различаются Seq Scan, Index Scan и Bitmap Scan?

Это три способа достать строки, и планировщик выбирает между ними по **селективности**: сколько строк вернёт запрос. Грубое правило: мало строк → Index Scan, средне → Bitmap Scan, много (или таблица мала) → Seq Scan. Причина — соотношение случайного и последовательного I/O.

**Seq Scan (Sequential Scan):**
- Читает таблицу страница за страницей от начала до конца — это последовательный I/O, для диска он дёшев
- **Быстро для:** маленькой таблицы или выборки ≥ ~30% строк (когда индекс всё равно прочитал бы почти всё)
- **Медленно для:** большой таблицы при поиске иголки в стоге сена
- Оптимален для `COUNT(*)` без WHERE

**Index Scan:**
- Проходит по индексу → достаёт каждую найденную строку из таблицы (случайный I/O — он дороже)
- **Быстро для:** селективных запросов (мало строк)
- **Медленно для:** неселективных (много случайных чтений страниц перевешивает выгоду индекса)
- Возвращает строки **в порядке индекса** — даром даёт ORDER BY по ключу

**Index Only Scan:**
- Все нужные колонки есть в индексе → к таблице вообще не обращаемся
- Дополнительно проверяется visibility map (нужна из-за MVCC в PostgreSQL)
- Самый быстрый вариант

**Bitmap Index Scan + Bitmap Heap Scan** — гибрид, закрывающий «среднюю зону»:
- Шаг 1: сканирует индекс → строит bitmap из TID (адресов строк)
- Шаг 2: сортирует bitmap по страницам и читает heap **последовательно** — так случайный I/O превращается в последовательный
- **Быстро для:** средней селективности (10-30% строк)
- Результат не упорядочен (порядок индекса теряется)

**Как планировщик выбирает между ними:**
- По селективности из статистики прикидывает число строк
- Сравнивает стоимость случайного и последовательного I/O (`random_page_cost`, `seq_page_cost`)
- По умолчанию `random_page_cost=4` — расчёт на HDD, где случайное чтение в 4 раза дороже; для SSD ставьте `=1.1`, иначе планировщик зря избегает индексов (большой прирост производительности!)

**Пример:**
```sql
-- 1M rows, returning 100 rows → Index Scan
EXPLAIN SELECT * FROM orders WHERE user_id = 42;

-- 1M rows, returning 500K → Seq Scan
EXPLAIN SELECT * FROM orders WHERE amount > 10;
```

## Q5. (!) Когда индекс помогает, а когда нет?

B-tree-индекс хранит значения **упорядоченно**, поэтому он ускоряет всё, что опирается на порядок или на точное совпадение префикса. Как только запрос ломает этот порядок (функция над колонкой, wildcard в начале, неявный каст) или выбирает слишком много строк — индекс становится бесполезен, и планировщик уходит в Seq Scan.

**Индекс помогает:**
- `WHERE col = value` (равенство)
- `WHERE col > X` (диапазон) — B-tree упорядочен, можно встать на границу и идти дальше
- `ORDER BY col` — избегаем отдельной сортировки (читаем уже в порядке)
- `GROUP BY col` — соседние одинаковые значения идут подряд
- `JOIN ON a.col = b.col`

**Индекс НЕ помогает:**

**1. Функция над колонкой:**
```sql
WHERE LOWER(email) = 'x@y.com'  -- normal index не используется!
```
Решение: функциональный индекс: `CREATE INDEX ON t (LOWER(email));`

**2. Wildcard в начале:**
```sql
WHERE name LIKE '%john%'  -- no index (B-tree prefix only)
```
Решение: триграммный индекс (`pg_trgm`) или full-text search

**3. Несовпадение типов:**
```sql
-- col is VARCHAR, passing INT
WHERE phone = 123456  -- implicit cast breaks index
```

**4. Неселективный запрос:**
- Возвращает > 30% строк → дешевле просто прочитать таблицу, выигрывает Seq Scan
- Например, `WHERE active = true`, когда 90% строк активны — индекс бесполезен

**5. OR без индексов на обе колонки:**
```sql
WHERE a = 1 OR b = 2  -- if only a indexed, partial
```
Решение: индекс на обе колонки ИЛИ запросы через UNION

**6. NOT IN / != (в некоторых случаях):**
- Планировщик может выбрать seq scan

**7. Перекос распределения данных:**
- 99% `status='ACTIVE'`, 1% `status='DELETED'`
- Запросу `WHERE status='DELETED'` нужен индекс
- Запросу `WHERE status='ACTIVE'` нужен seq scan
- Решение: **partial index** для `WHERE status='DELETED'`

**Проверить использование индексов:**
```sql
SELECT * FROM pg_stat_user_indexes WHERE idx_scan = 0;  -- unused indexes
```

## Q6. (!) Как выбрать порядок колонок в составном индексе?

Порядок колонок в составном индексе определяет, какие запросы он сможет ускорить. Популярный совет «самую селективную колонку — первой» — миф; **реальный критерий — паттерн доступа запросов** и правило левого префикса.

**Правило левого префикса.**
Индекс `(a, b, c)` может использоваться для:
- `WHERE a = ?`
- `WHERE a = ? AND b = ?`
- `WHERE a = ? AND b = ? AND c = ?`
- НЕ для `WHERE b = ?` (пропущена ведущая колонка `a` — индекс не подойдёт)
- частично для `WHERE a = ? AND c = ?` (по индексу отработает только `a`, `c` отфильтруется после)

**Порядок по паттерну запроса:**
1. **Сначала колонки равенства** (слева) — они сужают диапазон поиска
2. **Колонка диапазона — в конце:** range (`>`, `<`, `BETWEEN`) останавливает использование индекса для всех колонок правее
3. **Колонки сортировки** — сразу после колонок равенства, чтобы ORDER BY шёл по индексу

**Пример.**
Запросы:
- `WHERE user_id = ? AND created_at > ?`
- `WHERE user_id = ? ORDER BY created_at DESC`

Индекс: `(user_id, created_at)` — помогает обоим запросам: равенство по `user_id`, затем диапазон/сортировка по `created_at`.

**Плохо:** `(created_at, user_id)` — первый запрос вынужден сканировать весь диапазон по `created_at`, второй не может опереться на сортировку без дополнительного шага.

**Несколько нагрузок.**
Если разные запросы затрагивают разные колонки, может понадобиться несколько индексов. Но за это платим:
- Накладные расходы на запись (каждый INSERT/UPDATE обновляет все индексы)
- Место на диске
- Сопровождение

**Эмпирическое правило:** < 10 индексов на таблицу; больше — пересмотрите паттерны запросов, часть индексов наверняка лишние.

**Бонус — index-only scan.**
Включите часто выбираемые колонки в INCLUDE, чтобы не ходить в таблицу:
```sql
CREATE INDEX idx ON orders (user_id, created_at) INCLUDE (amount, status);
```

## Q7. Что такое covering index (INCLUDE) и зачем он нужен?

**Covering index** — индекс, который содержит все колонки, нужные запросу (и в SELECT, и в WHERE). Тогда движок берёт всё прямо из индекса и не ходит в таблицу — это **Index Only Scan**, самый дешёвый способ чтения.

**Старый способ (до PG 11):**
```sql
CREATE INDEX ON orders (user_id, amount, status);
```
- Все колонки попадают в ключ B-tree → индекс крупнее и навязывает порядок по `amount, status`, который зачастую не нужен

**Современный способ (PG 11+):**
```sql
CREATE INDEX ON orders (user_id) INCLUDE (amount, status);
```
- `user_id` остаётся в ключе (отсортирован, по нему ищут)
- `amount, status` лежат только в **листовых страницах** (не участвуют в сортировке, просто хранятся для выдачи)
- Индекс получается меньше, чем полный многоколоночный
- Index Only Scan по-прежнему работает

**Выгода:** не обращаемся к heap (телу таблицы) → меньше I/O → быстрее.

**Запрос:**
```sql
SELECT amount, status FROM orders WHERE user_id = 42;
```
Plan:
```
Index Only Scan using idx on orders
  Index Cond: (user_id = 42)
  Heap Fetches: 0
```

**Подводный камень с MVCC:**
- Index Only Scan работает только если visibility map считает страницу all-visible (это ставит VACUUM)
- Если строки недавно обновлялись → в плане появится `Heap Fetches: N` → движок всё-таки лазает в таблицу, и «index-only» уже не чистый

**Компромисс:**
- Индекс растёт в размере
- Дополнительные накладные расходы на запись
- Оправдан прежде всего на горячих путях чтения

## Q8. Что такое partial index и когда он полезен?

**Partial index** — индекс, который покрывает не всю таблицу, а только подмножество строк, заданное условием `WHERE` в самом `CREATE INDEX`. Смысл: индексировать только те строки, по которым реально идут запросы, и не тратить место и запись на остальные.

```sql
CREATE INDEX idx_pending_orders ON orders (created_at)
WHERE status = 'PENDING';
```

**Сценарии:**
- Перекошенные данные (99% строк имеют одно значение) → индексируем только редкие значения, которые и ищут
- Soft delete: `WHERE deleted_at IS NULL` — индексируем только активные строки
- Горячий, часто повторяющийся паттерн запросов

**Выгоды:**
- **Меньше размер** — в индексе только нужное подмножество строк
- **Быстрее запись** — индекс обновляется только когда строка попадает под условие
- **Быстрее чтение** — меньше данных для обхода

**Пример экономии:**
- Таблица 100M строк, 99M завершённых, 1M в ожидании
- Полный индекс: 100M записей
- Частичный (`WHERE status='PENDING'`): 1M записей — в 100× меньше

**Важный нюанс: запрос должен попадать под предикат индекса.**
```sql
-- Works (matches WHERE)
SELECT ... FROM orders WHERE status='PENDING' AND created_at > ...;

-- Doesn't use index (no status filter)
SELECT ... FROM orders WHERE created_at > ...;
```

**Как планировщик решает:** он использует partial index, только если из условия запроса логически следует предикат индекса. Нет фильтра по `status='PENDING'` — нет гарантии, что нужные строки в индексе, поэтому он не подойдёт.

**Частые паттерны:**
- `WHERE enabled = true`
- `WHERE deleted_at IS NULL`
- `WHERE region = 'US'` для запросов по конкретному региону

## Q9. Что такое index bloat и как с ним бороться через REINDEX?

**Index bloat (раздувание индекса)** — это когда страницы индекса заполнены частично, потому что UPDATE/DELETE оставляют после себя мёртвые версии строк (dead tuples). Индекс занимает больше места, чем нужно под актуальные данные → сканирование медленнее, больше I/O.

**Причины** (всё растёт из MVCC):
- UPDATE = вставка новой версии строки + пометка старой как мёртвой (а индекс получает новую запись)
- DELETE помечает строку мёртвой; физически её убирает VACUUM позже
- Длинные транзакции держат старые версии и мешают VACUUM их вычистить

**Как обнаружить:**
```sql
SELECT schemaname, tablename, indexname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;
```

Или расширение `pgstattuple`:
```sql
SELECT * FROM pgstatindex('idx_name');
-- leaf_fragmentation, avg_leaf_density
```

Низкий `avg_leaf_density` (< 50%) → bloat.

**Исправление:**

**REINDEX:**
```sql
REINDEX INDEX idx_name;          -- locks writes (PG <12)
REINDEX INDEX CONCURRENTLY ...;  -- non-blocking (PG 12+)
```

**CREATE + DROP (до 12):**
```sql
CREATE INDEX CONCURRENTLY idx_new ON t (...);
DROP INDEX idx_old;
ALTER INDEX idx_new RENAME TO idx_old;
```

**pg_repack / pg_squeeze:** онлайн-перестроение таблицы и индексов без долгого lock на запись.

**Профилактика** (дешевле, чем лечение):
- Регулярный, правильно настроенный autovacuum
- Избегайте очень длинных транзакций — они держат xmin horizon и блокируют очистку
- **HOT-обновления** (UPDATE, не затрагивающий индексируемые колонки) не создают новых записей в индексе и потому не раздувают его

## Q10. (!) Что такое N+1 problem, как её обнаружить и исправить?

**N+1** — антипаттерн, когда вместо одного-двух запросов приложение делает 1 запрос на список + ещё N запросов (по одному на каждый элемент) для подгрузки связанной сущности. Чаще всего возникает в ORM при ленивой загрузке: достали список, в цикле трогаем связь — каждое обращение порождает отдельный SQL.

**Пример (JPA/Hibernate):**
```java
List<Order> orders = orderRepo.findAll();  // 1 query
for (Order o : orders) {
    System.out.println(o.getUser().getName());  // N queries lazy load!
}
```
→ 1 + 100 = 101 обращений к БД для 100 заказов. На проде это легко превращается в тормозящий endpoint.

**Как обнаружить:**
- **APM** (трассировка DataDog) — на спане видна пачка однотипных запросов подряд
- **Статистика Hibernate:** `hibernate.generate_statistics=true`; смотрим `queryExecutionCount`
- **p6spy** — логирует весь реальный SQL, сразу видно лавину запросов
- **JPA Buddy / QuickPerf** — тестом утверждаем отсутствие N+1 (ловим регрессию заранее)

**Исправления.** Все они сводятся к тому, чтобы подтянуть связь заранее одним-двумя запросами:

**JOIN FETCH** — жадно подгружает связь в одном запросе:
```java
@Query("SELECT o FROM Order o JOIN FETCH o.user WHERE ...")
```
Один запрос с JOIN → 1 запрос вместо 101.

**EntityGraph:**
```java
@EntityGraph(attributePaths = {"user", "items"})
List<Order> findAll();
```

**Batch fetch size:**
```properties
spring.jpa.properties.hibernate.default_batch_fetch_size=20
```
Группирует N запросов в пачки IN (...) по 20.

**DTO-проекция:**
```java
@Query("SELECT new com.OrderDto(o.id, u.name) FROM Order o JOIN o.user u")
```
Прямой плоский запрос, без графа сущностей.

**Что выбрать:**
- Маленькая коллекция → JOIN FETCH
- Пагинация / many-to-many → batch fetch (JOIN FETCH здесь даёт дубликаты и ломает пагинацию)
- Только чтение → DTO-проекция (самый быстрый вариант, не строим граф сущностей)

**Не только Hibernate:** так ведёт себя любой ORM, если дёргать связь в цикле, — паттерн универсален.

## Q11. Чем различаются JOIN FETCH, subselect и batch size?

Это три стратегии Hibernate, чтобы подтянуть связь и не словить N+1. Различаются числом запросов и тем, как ведут себя при коллекциях и пагинации. **Сценарий:** загрузить `Order` вместе с `OrderItems`.

**JOIN FETCH** — всё одним JOIN:
```sql
SELECT o.*, i.*
FROM orders o
LEFT JOIN order_items i ON i.order_id = o.id
```
- **1 запрос** — минимум обращений
- Декартов взрыв при двух и более коллекциях (строки перемножаются)
- **Пагинация ломается:** Hibernate не может применить LIMIT к JOIN с коллекцией, грузит всё и режет страницу в памяти (выдаёт предупреждение в логе)

**Batch (subselect) fetching:**
```properties
hibernate.batch_fetch_style=dynamic
hibernate.default_batch_fetch_size=16
```
Hibernate выполняет:
```sql
SELECT * FROM orders WHERE id IN (1, 2, ..., 16);
SELECT * FROM order_items WHERE order_id IN (1, 2, ..., 16);
```
- Несколько запросов вместо N — связи грузятся пачками по `batch_fetch_size`
- Без декартова произведения
- Работает с пагинацией (LIMIT применяется к корневому запросу)

**Subselect fetch:**
```java
@OneToMany(fetch = FetchType.LAZY)
@Fetch(FetchMode.SUBSELECT)
Collection<Item> items;
```
Выполняет исходный запрос как подзапрос:
```sql
SELECT * FROM order_items WHERE order_id IN (SELECT id FROM orders WHERE ...)
```

**Сравнение:**

| Стратегия | Запросов | Декартово произведение | Пагинация |
|----------|---------|-----------|------------|
| JOIN FETCH | 1 | Да (плохо для нескольких коллекций) | Ломается для коллекций |
| Batch | ~N/batch_size | Нет | OK |
| Subselect | 2 | Нет | OK, но переигрывает исходный фильтр в подзапросе |

**Эмпирическое правило:**
- Одна коллекция, мало родителей → JOIN FETCH
- Несколько коллекций → batch_fetch_size (типично 20)
- Очень большой объём / только чтение → DTO-проекция

## Q12. (!) Зачем нужен connection pooling?

Пул соединений нужен, потому что **открыть новое соединение к БД дорого**, а PostgreSQL ещё и ограничивает их общее число. Пул держит набор уже открытых соединений и переиспользует их между запросами — так мы убираем цену установки соединения из каждого запроса и не даём приложению задавить базу числом коннектов.

**Открытие соединения** — дорого, потому что это целая цепочка шагов:
- TCP handshake
- TLS handshake (~100+ мс по WAN)
- Аутентификация в БД
- Форк backend-процесса (в PostgreSQL на каждое соединение — отдельный процесс, `connection_pid`)

**Без пула:** каждый запрос открывает и закрывает соединение — это **последовательное узкое место**, плюс БД ограничивает общее число соединений и при всплеске начинает их отвергать.

**Что делает пул:**
- Держит N открытых соединений наготове
- Запрос берёт соединение из пула и возвращает по завершении
- Если все заняты — ставит запрос в очередь (а не открывает новое сверх лимита)

**Выгоды:**
- Убираем накладные расходы на соединение (экономия мс)
- Ограничиваем число одновременных соединений к БД (стабильность бэкенда)
- Быстрее (latency подключения = 0)
- Контроль ресурсов

**Типичные пулы:**
- **HikariCP** (Java) — самый быстрый, дефолт в Spring Boot
- **pgbouncer** (отдельный) — перед PostgreSQL
- **RDS Proxy** (AWS) — управляемый
- **Node pg-pool**, **Python psycopg2 pool**

**Архитектурное решение:**
- **Пул на стороне приложения:** просто, in-process
- **Внешний пул (pgbouncer, RDS Proxy):** между приложением и БД; можно делить пул между несколькими приложениями/инстансами
- **Оба:** пул приложения → внешний пул → БД (типично для serverless)

**Размер пула:**
- Старая формула: `pool = cores × 2 + spindles`
- Современный подход: подбирать бенчмарком — слишком большой пул вредит из-за переключения контекста и конкуренции за ресурсы БД
- Типичный бэкенд: 10-30 соединений на инстанс

**Подводный камень:** serverless (Lambda) без пулинга = взрыв числа соединений к БД (каждый инстанс открывает свои); всегда ставьте перед БД RDS Proxy или внешний пул.

## Q13. (!) Какие настройки HikariCP важны и как их подбирать?

**HikariCP** — пул соединений по умолчанию в Spring Boot: быстрый и требует минимум конфигурации. Знать стоит несколько ключевых параметров — размер пула, тайминги жизни соединений и защиту от утечек.

**Ключевые свойства (`spring.datasource.hikari.*`):**

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000    # 30s wait for connection
      idle-timeout: 600000         # 10 min evict idle
      max-lifetime: 1800000        # 30 min recycle connections
      keepalive-time: 120000       # 2 min ping idle conn (Hikari 4.0+)
      leak-detection-threshold: 60000  # 60s — warn if not returned
```

**Рекомендации по размеру:**
- **maximum-pool-size:** начните с 10, подкручивайте по нагрузке + DB max_connections
- **minimum-idle:** обычно = max (держать прогретым) для стабильного latency
- **Формула:** суммарное число соединений по всем инстансам ≤ DB `max_connections × 0.8`

**Частая проблема — суммарный лимит соединений:**
- Приложение из 10 инстансов × пул 20 = 200 соединений
- DB max = 100 → база отвергает коннекты, приложение падает
- Поэтому считайте пул по всем инстансам, а не по одному

**connection-timeout:** приложение не виснет в бесконечном ожидании свободного соединения — по истечении быстро падает и возвращает 503 (fail fast лучше зависания).

**max-lifetime:** важно — принудительно пересоздаёт соединения, не давая им «протухнуть» (фаерволы убивают idle-коннекты, БД могла рестартовать).

**leak-detection-threshold:** если соединение держат дольше порога, в лог пишется stack trace — так находят пропущенный `try-with-resources` или незакрытую сессию.

**Метрики:** экспонируем через Micrometer:
```
hikaricp.connections.active
hikaricp.connections.idle
hikaricp.connections.pending
hikaricp.connections.acquire  # time histogram
```

**Алерты:** устойчивое `pending > 0` означает, что запросы постоянно ждут соединение → пул мал (или запросы держат соединения слишком долго).

## Q14. Чем различаются режимы transaction и session pooling в PgBouncer?

**PgBouncer** — лёгкий внешний пулер соединений для PostgreSQL (работает как прокси перед базой). Главное различие режимов — **когда соединение к БД возвращается в пул**: после disconnect клиента (session) или после каждой транзакции (transaction). Чем раньше возвращается, тем выше переиспользование, но тем больше ограничений.

**Режимы:**

**Session pooling (по умолчанию):**
- Клиент держит соединение с БД на **всю сессию** (от connect до disconnect)
- Почти как без пулинга — соединение переиспользуется только после того, как клиент отключился
- Безопасен для всех возможностей (prepared statements, temp tables, listen/notify)
- Прирост эффективности небольшой

**Transaction pooling:**
- Соединение выдаётся **на одну транзакцию** и возвращается в пул на COMMIT/ROLLBACK
- **Огромная эффективность:** между транзакциями соединение свободно, поэтому 1000 клиентов могут делить 20 соединений к БД
- **Ограничения** (всё, что живёт дольше транзакции, ломается):
  - Нет prepared statements (привязаны к сессии) — кроме PG 14+ и PgBouncer 1.22+ с поддержкой на уровне протокола
  - Нет `SET` (привязан к сессии)
  - Нет temp tables
  - Нет `LISTEN/NOTIFY`
  - Ограничения по курсорам

**Statement pooling:**
- Соединение возвращается после каждого statement (применяется редко — крайне жёсткие ограничения, нельзя даже многооператорных транзакций)

**Что выбрать:**
- **Session:** легаси-приложения, которым нужны session-привязанные возможности
- **Transaction:** современные приложения с высоким throughput и stateless-обработчиками — основной выбор ради экономии соединений
- **ORM:** Hibernate по умолчанию использует prepared statements, что конфликтует с transaction pooling — отключите их (`prepareThreshold=0`) или используйте PG 14+ с PgBouncer 1.22+

**Spring Boot + PgBouncer в режиме transaction:**
```yaml
spring:
  datasource:
    hikari:
      # Critical! Disable prepared statements
      data-source-properties:
        prepareThreshold: 0
    # Or use PgBouncer 1.22+ with PG 14+
```

**Схема развёртывания:**
```
[App instances × N] → [PgBouncer pool: 500 client conns / 30 DB conns] → [PostgreSQL]
```

## Q15. (!) Когда применять партиционирование таблиц?

**Партиционирование** — это разбиение одной большой логической таблицы на меньшие физические части (партиции) по ключу (range, list или hash). Главная выгода — **partition pruning**: планировщик читает только релевантные партиции, а не всю таблицу. Партиционирование оправдано на больших таблицах с понятным ключом (чаще всего — дата); для маленьких таблиц это лишняя сложность.

**Когда применять:**

**1. Очень большие таблицы (> 100M строк / > 100GB):**
- Запросы сканируют свежие данные → партицируем по дате, запрос отсекает старые партиции
- Индекс помещается в память (меньше на партицию)

**2. Временные ряды:**
- Логи, события, метрики — range-партицирование по месяцу/неделе
- Дроп старой партиции = быстро (против DELETE миллионов строк)

**3. Нагрузка с большим числом удалений:**
- Дроп партиции = мгновенно; DELETE + VACUUM = медленно

**4. Изоляция арендаторов:**
- Hash/list-партицирование по tenant_id

**Когда НЕ применять:**
- Маленькие таблицы (< 10M строк) — обычный индекс справится лучше
- Запросы не дают отсечения (нет фильтра по ключу партиционирования)
- Сложность не окупается выгодой
- Внешние ключи и уникальность между партициями реализуются непросто

**Выгоды:**
- Отсечение партиций (сканируем только релевантные)
- Параллельные операции по партициям
- Обслуживание по партициям (VACUUM, REINDEX)
- DROP партиции для retention

**Издержки:**
- Сложность (миграции, ограничения)
- Кросс-партиционные запросы медленнее
- Ключ партиционирования должен быть во всех уникальных индексах (или обходной путь)

**Партицирование в PostgreSQL (10+):**
```sql
CREATE TABLE logs (ts TIMESTAMP, msg TEXT)
PARTITION BY RANGE (ts);

CREATE TABLE logs_2024_01 PARTITION OF logs
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
```

**Автоматизация:** расширение `pg_partman` для авто-создания партиций.

## Q16. Чем различаются range-, list- и hash-партиционирование?

Три способа отличаются тем, как значение ключа отображается в партицию: диапазоном (range), точным значением из набора (list) или хэшем (hash). Выбор зависит от природы ключа и от того, какие запросы должны выигрывать от отсечения.

**Range (по диапазону):**
- Значение попадает в партицию, в чей диапазон укладывается
- Лучше для: меток времени, последовательных ID — естественно растут вперёд
```sql
PARTITION BY RANGE (created_at);
-- partitions: 2024_01, 2024_02, ...
```

**List (по списку значений):**
- Каждое дискретное значение (или их набор) → своя партиция
- Лучше для: региона, категории, статуса — конечный набор значений
```sql
PARTITION BY LIST (country);
-- partitions: us, eu, apac, other
```

**Hash (по хэшу):**
- `hash(key) % N` → партиция, значения раскидываются равномерно
- Лучше для: равномерного распределения нагрузки, когда нет естественного ключа диапазона
- Не умеет отсекать партиции для range-запросов (по хэшу диапазон не сгруппирован)
```sql
PARTITION BY HASH (user_id);
-- 16 partitions
```

**Composite:**
- Range → List суб-партиции: сначала по дате, затем по региону

**Сравнение:**

| Тип | Отсечение | Сценарий | Рост |
|------|---------|----------|--------|
| Range | Range-запросы | Временные ряды | Добавляем новую партицию на период |
| List | Равенство | Регион/арендатор | Добавляем на каждое новое значение |
| Hash | Равенство по ключу | Равномерное распределение | Фиксированное число, планируйте заранее |

**Отсечение:** планировщик исключает партиции, когда WHERE запроса совпадает с ключом партиционирования.

**Hash: нелегко перепартицировать** — выбирайте число партиций аккуратно (степень 2 для удобного удвоения в будущем).

## Q17. (!) Зачем нужны ANALYZE и статистика оптимизатора?

Планировщик PostgreSQL — cost-based: он выбирает план не по «правилам», а по оценке стоимости, и эта оценка целиком опирается на **статистику** о данных. `ANALYZE` собирает и обновляет эту статистику. Если статистика устарела, планировщик ошибается в оценке числа строк и выбирает плохой план (Seq Scan вместо Index, Nested Loop вместо Hash Join).

**Статистика** — сводные данные о распределении таблицы и колонок, которые планировщик использует для оценок:
- Число строк
- Число уникальных значений на колонку
- Наиболее частые значения + их частоты
- Гистограмма распределения значений
- Доля NULL
- Средняя ширина

**Хранилище:** view `pg_stats`.

**ANALYZE:**
```sql
ANALYZE orders;        -- update stats
ANALYZE;              -- all tables
```

- Сэмплирует строки (по умолчанию 30000 * `default_statistics_target`)
- Обновляет `pg_statistic`

**Auto-analyze (autovacuum):**
- Срабатывает, когда изменилось > `autovacuum_analyze_scale_factor * rows` (по умолчанию 10%)

**Когда статистика устаревает:**
- Массовый INSERT/UPDATE
- Сдвиги распределения данных
- Новая неделя/месяц (временные ряды)

**Как обнаружить устаревшую статистику:**
- `EXPLAIN ANALYZE` показывает грубое расхождение `rows=X` против `actual rows=Y`

**default_statistics_target:**
- 100 по умолчанию (подходит в большинстве случаев)
- Поднимите до 1000 для колонки со сложным распределением
- `ALTER TABLE t ALTER COLUMN c SET STATISTICS 1000;`

**Расширенная статистика (PG 10+):**
```sql
CREATE STATISTICS s_name (dependencies, ndistinct)
  ON col_a, col_b FROM t;
ANALYZE t;
```
По умолчанию планировщик считает колонки независимыми и перемножает селективности. Для **коррелированных колонок** (city + zip — город однозначно задаёт индекс) это даёт грубую недооценку строк; расширенная статистика учит планировщик их зависимости.

**Сценарий из прода:** после крупного изменения данных (миграция, восстановление из дампа) статистики ещё нет — сразу выполните `ANALYZE`. Planning time снижается, запросы перестают выбирать плохой план.

## Q18. Что делают VACUUM, autovacuum и как возникает bloat?

В PostgreSQL из-за MVCC любой UPDATE/DELETE не стирает строку, а оставляет её мёртвую версию (dead tuple). **VACUUM** убирает этот мусор: помечает место под повторное использование и «замораживает» старые транзакции. Без VACUUM таблицы раздуваются (bloat) и в пределе наступает transaction ID wraparound.

**VACUUM** освобождает dead tuples после UPDATE/DELETE.

**Зачем он нужен:**
- UPDATE = пометить старую версию мёртвой + вставить новую → накапливается мусор
- Dead tuples занимают место впустую и замедляют сканирование
- Предотвращает transaction ID wraparound (критично — иначе БД встанет!)

**Типы:**

**VACUUM (стандартный):**
- Помечает мёртвое место для повторного использования
- Не отдаёт место ОС (размер таблицы остаётся)
- Не блокирует (кроме VACUUM FULL)

**VACUUM FULL:**
- Переписывает всю таблицу (перестраивает)
- Отдаёт место ОС
- **Блокирует запись** — только для экстренных случаев
- Вместо него используйте `pg_repack` (онлайн)

**Autovacuum:**
- Фоновый воркер, запускается автоматически
- Конфиг: `autovacuum_vacuum_scale_factor` (по умолчанию 20%)
- Агрессивные настройки для таблиц с большим числом записей:
```sql
ALTER TABLE t SET (autovacuum_vacuum_scale_factor = 0.05);
```

**Bloat:**
- Dead tuples вычищаются недостаточно быстро
- Или долгая транзакция мешает очистке (`xmin horizon`)
- Обнаружить: `pgstattuple`, `pg_stat_user_tables`

**Длинные транзакции = враг bloat:**
- Работающая транзакция мешает VACUUM удалять более новые удалённые строки
- Проверка: `SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction';`

**TXID wraparound** (почему VACUUM нельзя отключать):
- ID транзакций в PostgreSQL — 32-битные, то есть конечны и зацикливаются
- У каждой строки есть `xmin`/`xmax` — кем создана и удалена
- При зацикливании старые транзакции «уезжают в будущее» → строки внезапно становятся невидимыми = повреждение данных
- VACUUM «замораживает» старые строки (помечает как заведомо видимые) и предотвращает это
- Если игнорировать — на отметке ~2 млрд транзакций **БД принудительно останавливается** ради защиты данных

**Мониторинг:**
- `pg_stat_user_tables.n_dead_tup`
- `age(relfrozenxid)` по таблице — предупреждение при > 1 млрд

**Тюнинг:** `autovacuum_max_workers=6`, `autovacuum_naptime=10s` для нагруженных БД.

## Q19. Как настраивать shared_buffers, work_mem и effective_cache_size?

Это три ключевых параметра памяти в PostgreSQL, и их легко перепутать. Коротко: `shared_buffers` — это **реально выделяемый** общий кэш страниц; `work_mem` — лимит памяти **на каждую операцию сортировки/хэша** (и потому очень опасен при умножении на соединения); `effective_cache_size` — **ничего не выделяет**, это лишь подсказка планировщику, сколько памяти под кэш доступно в системе.

**shared_buffers** — блочный кэш PostgreSQL (разделяемая память):
- По умолчанию: 128MB (намного меньше нужного!)
- Рекомендация: **25% RAM** (до 8-16GB — дальше отдача падает)
- Большие значения выгодны OLAP; для OLTP начинается дублирование с кэшем ОС, выгода уменьшается

**work_mem** — память на одну операцию (sort, hash):
- По умолчанию: 4MB
- Самое опасное: лимит действует **на каждую операцию и на каждое соединение**, а не на сервер целиком
- 10 соединений × 3 операции × work_mem = до 30× этого значения сразу → риск OOM
- Рекомендация: типично 16-64MB; больше — только для аналитики
- Можно поднять точечно на тяжёлый запрос: `SET LOCAL work_mem = '256MB';`

**maintenance_work_mem:** для CREATE INDEX, VACUUM.
- По умолчанию: 64MB
- Поднимите до 1GB для быстрого построения индексов
- На сессию, но maintenance-сессии редки

**effective_cache_size:** подсказка планировщику об общем доступном кэше (ОС + shared_buffers).
- По умолчанию: 4GB
- Рекомендация: **50-75% RAM**
- Ничего не выделяет, только влияет на планировщик (он предпочитает index scan при высоком effective_cache_size)

**wal_buffers:** буфер для записи WAL.
- По умолчанию: auto (минимум 1/32 shared_buffers, максимум 16MB)
- Обычно подходит как есть

**пример (сервер с 32GB RAM):**
```
shared_buffers = 8GB
effective_cache_size = 24GB
work_mem = 32MB
maintenance_work_mem = 1GB
```

**Инструмент:** `pgtune` — калькулятор конфига по типу нагрузки.

## Q20. Как тюнить WAL и checkpoint?

**WAL (Write-Ahead Log)** — журнал, куда любое изменение пишется **раньше**, чем в файлы данных; благодаря этому БД восстанавливается после сбоя. **Checkpoint** периодически сбрасывает грязные буферы в файлы данных, после чего WAL до этой точки можно переиспользовать. Тюнинг сводится к компромиссу: реже checkpoint → выше throughput записи, но дольше восстановление после падения.

**Ключевые параметры:**

**wal_level:** `replica` (по умолчанию) / `logical` (для логической репликации).

**max_wal_size:** целевой объём WAL между checkpoint. По умолчанию 1GB.
- Больше = меньше checkpoint = выше throughput записи, но дольше восстановление
- Нагруженная БД: 8-16GB

**checkpoint_timeout:** максимум времени между checkpoint. По умолчанию 5 мин.
- Больше = лучше throughput, дольше восстановление
- 15-30 мин для нагрузки с большим числом записей

**checkpoint_completion_target:** размазывает I/O checkpoint по этой доле интервала. По умолчанию 0.9.
- Выше = более плавный I/O; менять нужно редко

**min_wal_size:** держать переработанным как минимум столько. По умолчанию 80MB.

**Синхронный commit** (`synchronous_commit`) — ждать ли подтверждения записи WAL перед ответом клиенту:
- **on (по умолчанию):** ACK только после fsync WAL на диск — максимальная долговечность, но commit ждёт диск
- **off:** ACK до fsync — при падении можно потерять последние несколько мс транзакций, зато заметно быстрее
- **remote_apply / remote_write:** ждать подтверждения от реплики — для синхронной репликации

**Для пакетных загрузок:** поставьте `synchronous_commit = off` в рамках сессии → bulk-импорт идёт быстрее, а риск потери последних мс при таком импорте приемлем.

**Репликация:**
- `wal_keep_size` (PG 13+): хранить WAL для реплик
- `archive_mode + archive_command`: для PITR
- Слоты репликации: гарантируют, что WAL сохранится для подписчика

**Мониторинг:**
- `pg_stat_bgwriter`: checkpoints, buffers
- Высокий `checkpoints_req` против `checkpoints_timed` → max_wal_size слишком мал

## Q21. (!) В чём проблема пагинации через LIMIT + OFFSET?

Беда `OFFSET` в том, что БД не умеет «перепрыгнуть» N строк — она вынуждена прочитать и отбросить их все, прежде чем вернуть нужную страницу. Поэтому глубокие страницы линейно деградируют. Решение — keyset-пагинация (seek-метод): вместо смещения двигаемся по индексу от «закладки» последней показанной строки.

**Проблема:**
```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 10000;
```
- Приходится прочитать 10020 строк, отбросить 10000 и вернуть 20
- **Чем дальше страница, тем медленнее** — стоимость растёт с offset
- Страница 500 (offset 10000) → примерно в 100 раз медленнее первой

**Решение: keyset-пагинация (метод seek):**

```sql
-- Page 1
SELECT * FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- Last row returns (created_at='2024-01-15 10:00', id=1234)

-- Page 2 (using last row as bookmark)
SELECT * FROM orders
WHERE (created_at, id) < ('2024-01-15 10:00', 1234)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

**Выгоды:**
- Константное время **на каждую страницу** — это index seek, а не сканирование с отбрасыванием
- Нет несогласованности «строка сдвинулась»: при OFFSET вставка новых строк сдвигает окно и часть данных дублируется/пропускается, а keyset двигается от стабильной закладки

**Нужен индекс** под порядок сортировки: `(created_at DESC, id DESC)`.

**Оговорка:**
- Нельзя прыгнуть на произвольную страницу — только next/prev
- Для UX это обычно ок: бесконечная прокрутка, кнопка «load more»

**Альтернатива — посчитать строки один раз, затем OFFSET:**
- Полный подсчёт `SELECT COUNT(*)` медленный на больших таблицах
- Для оценки используйте приблизительный подсчёт: `pg_class.reltuples`

**Рекомендация:**
- Бесконечная прокрутка / «next» → keyset
- «Перейти сразу на страницу 500» → либо смиритесь с медленностью OFFSET, либо переосмыслите UX

## Q22. Что выбрать: JOIN, подзапрос или EXISTS?

Современный планировщик PostgreSQL обычно сводит все три формы к одному плану, поэтому различие чаще в **семантике и читаемости**, чем в скорости. Важные практические отличия — поведение при дубликатах (JOIN), при NULL (`IN`/`NOT IN`) и короткое замыкание (`EXISTS`). Ниже — семантически эквивалентные варианты одного запроса.

**JOIN:**
```sql
SELECT o.* FROM orders o
JOIN users u ON u.id = o.user_id
WHERE u.country = 'US';
```

**Подзапрос IN:**
```sql
SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE country = 'US');
```

**EXISTS:**
```sql
SELECT * FROM orders o
WHERE EXISTS (SELECT 1 FROM users u WHERE u.id = o.user_id AND u.country = 'US');
```

**Что делает планировщик PostgreSQL:**
- Обычно переписывает все три варианта в эквивалентный план
- Различия проявляются лишь в граничных случаях

**Где формы реально различаются:**
- **JOIN** с `SELECT *` из orders может **продублировать** заказы, если строке соответствует несколько пользователей — JOIN размножает строки по совпадениям
- **EXISTS** возвращает внешнюю строку один раз независимо от числа внутренних совпадений (короткое замыкание на первом) → часто оптимален для semi-join
- **IN** опасен NULL-семантикой: NULL в списке даёт UNKNOWN вместо ожидаемого результата

**Советы по производительности:**
- `NOT IN` с подзапросом, который может вернуть NULL, ломается (условие всегда не-истинно) — используйте `NOT EXISTS` или `LEFT JOIN ... WHERE ... IS NULL`
- `EXISTS` часто быстрее на большой внутренней таблице за счёт короткого замыкания
- `JOIN` нужен, когда требуются колонки из обеих таблиц (подзапрос/EXISTS их не отдают)

**Проверяйте план через EXPLAIN ANALYZE:**
- Часто планировщик сам превращает `IN` в `Semi Hash Join`, эквивалентный `EXISTS`
- Берите вариант, который читается яснее, и подтверждайте выбор замером, а не интуицией

## Q23. Что важно знать про производительность window functions?

**Оконные функции (window functions)** вычисляют значение для каждой строки по её «окну» соседних строк и, в отличие от обычного агрегата, не схлопывают результат в одну строку. Главная цена производительности — почти всегда требуется сортировка набора по `PARTITION BY ... ORDER BY`, и если она не покрыта индексом и не помещается в work_mem, то уходит на диск.

**Примеры:**
```sql
SELECT user_id, amount,
  ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn,
  SUM(amount) OVER (PARTITION BY user_id) AS total
FROM orders;
```

**Производительность:**

- **Нужна сортировка**, если индекс не совпадает с `PARTITION BY ... ORDER BY`
- Индекс `(user_id, created_at)` → в примере выше сортировка не нужна, читаем уже в порядке

**Стоимость:**
- Обычно требуется сортировка всего набора данных
- Если сортировка не влезла в work_mem и ушла на диск → медленно
- При этом оконная функция почти всегда быстрее эквивалентного коррелированного подзапроса (тот пересчитывает агрегат на каждую строку)

**Frame clause (рамка окна):**
```sql
SUM(amount) OVER (ORDER BY dt ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
```
- По умолчанию: `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — нарастающий итог
- Кастомные frame могут быть дорогими

**Советы:**
- Поддержка индекса для ORDER BY
- Избегайте оконной функции поверх огромного агрегата (материализуйте промежуточный результат)
- `DISTINCT ON` (специфично для PostgreSQL) — часто более быстрая альтернатива для «первая запись в группе»:
```sql
SELECT DISTINCT ON (user_id) *
FROM orders
ORDER BY user_id, created_at DESC;
```

**Materialized CTE (PG 12+):**
```sql
WITH aggregated AS MATERIALIZED (...)
SELECT ... FROM aggregated;
```

## Q24. Чем materialized view отличается от обычного view?

Различие в том, **где живёт результат**. Обычный view — это просто сохранённый текст запроса: при каждом обращении он выполняется заново (всегда свежие данные, но платим за пересчёт). Materialized view хранит **уже посчитанный результат** как таблицу: читается мгновенно, но данные устаревают до следующего REFRESH. Выбор — это компромисс свежесть против скорости чтения.

**View** — сохранённый запрос, выполняется при каждом обращении:
```sql
CREATE VIEW user_summary AS
SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id;
```
- Плюс: данные всегда актуальны
- Минус: пересчитывает запрос на каждое обращение → медленно для сложных агрегатов

**Materialized view** — **результат запроса сохранён** как таблица:
```sql
CREATE MATERIALIZED VIEW user_summary_mv AS
SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id;

CREATE UNIQUE INDEX ON user_summary_mv (user_id);
```
- Плюс: чтение быстрое — это просто SELECT из готовой таблицы
- Минус: данные **устаревают** между обновлениями, пока не сделан REFRESH

**REFRESH:**
```sql
REFRESH MATERIALIZED VIEW user_summary_mv;  -- locks reads
REFRESH MATERIALIZED VIEW CONCURRENTLY user_summary_mv;  -- needs unique index
```

**Инкрементальный refresh:** нет в ядре PostgreSQL; расширения (`pg_ivm`) или решения на уровне логики (CDC → обновление).

**Сценарии:**
- Дашборды (ночной refresh)
- Отчётность (сложные join)
- Денормализация для пути чтения
- Поисковые индексы

**Альтернативы:**
- **Кэш** (Redis): на уровне приложения; похожий компромисс
- **Read replica**: запросы к реплике со слегка устаревшими данными

**Подводный камень:** время refresh само может стать узким местом — если materialized view строится 10 минут, его физически нельзя обновлять каждую минуту. В таких случаях нужен инкрементальный пересчёт (например, по партициям), а не полный REFRESH.

## Q25. (!) Когда и как применять read replicas?

**Read replica** — копия БД, которая проигрывает WAL мастера (primary) и обслуживает только запросы на чтение. Применяют, чтобы масштабировать чтение горизонтально, но за это платят eventual consistency: реплика всегда чуть-чуть отстаёт от мастера (лаг), поэтому главная сложность — корректно решить, какие запросы можно отправлять на реплику, а какие обязаны идти на primary.

**Зачем:**
- Масштабировать throughput чтения — в большинстве приложений 80%+ нагрузки это чтения
- Изолировать тяжёлую аналитику от OLTP, чтобы отчёты не мешали транзакциям
- HA-failover в некоторых конфигурациях (реплика может стать новым мастером)

**PostgreSQL:**
- **Streaming replication** (физическая) — побайтовая копия; только чтение
- **Logical replication** — изменения на уровне строк; выборочные таблицы; доступна для записи (но осторожно)

**Лаг:**
- Типично: миллисекунды-секунды
- Массовые операции на primary дают всплеск лага
- Мониторинг: `pg_replication_slots`, дельта `replay_lsn`

**Проблема read-your-writes** (главная ловушка реплик):
- Пользователь обновляет запись и тут же читает её
- Запрос может попасть на реплику, которая ещё не догнала мастер → пользователь видит старые данные
- Решения (все сводятся к «свежие чтения — на primary»):
  - Маршрутизировать запись и немедленное чтение после неё на primary
  - Sticky-сессия: прибить пользователя к primary на X секунд после записи
  - Читать с primary в течение всего «окна после записи»

**Архитектурные паттерны:**
- Приложение маршрутизирует запросы: `@Transactional(readOnly=true)` → реплика; иначе → primary
- Spring `AbstractRoutingDataSource` для динамической маршрутизации
- **На основе прокси:** ProxySQL, pgpool, RDS Proxy

**Компромиссы:**
- Eventual consistency (лаг)
- Сложность failover
- Число соединений удваивается (приложение подключается к обоим)

**Режимы согласованности:**
- Асинхронная репликация (по умолчанию, быстро, может потерять данные при падении)
- Синхронная репликация (`synchronous_standby_names`) — медленнее запись, нулевая потеря данных

**Облако:** RDS/Aurora делают реплики тривиальными; Aurora — общее хранилище, минимальный лаг.

## Q26. (!) Как находить slow queries в prod?

Базовый ответ: начинайте с `pg_stat_statements` — оно агрегирует все запросы по их форме и сразу показывает топ по суммарному времени, где обычно прячется 80% нагрузки. Дальше по ситуации подключаются slow query log (для конкретных медленных вызовов), `pg_stat_activity` (что тормозит прямо сейчас), APM и `auto_explain`.

**PostgreSQL:**

**pg_stat_statements (обязательное расширение, начинать отсюда):**
```sql
CREATE EXTENSION pg_stat_statements;

SELECT query,
       calls,
       total_exec_time / 1000 AS total_sec,
       mean_exec_time AS mean_ms,
       rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```
- Учитывает по нормализованному запросу (параметры заменяются на `$1`)
- Суммарное время, среднее, число вызовов
- **Всегда начинайте отсюда** — топ-10 обычно объясняет 80% нагрузки

**Slow query log:**
```sql
log_min_duration_statement = 1000  -- log queries > 1s
```
- Пишет в лог-файл PostgreSQL
- Grep / отправка в ELK / Loki

**Запросы, активные прямо сейчас:**
```sql
SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state != 'idle' AND now() - query_start > interval '5 seconds'
ORDER BY duration DESC;
```
Используйте для «что тормозит прямо сейчас».

**APM (DataDog, New Relic):**
- Автоматически захватывает SQL из трейсов
- Размечает по сервису/endpoint
- Latency P95/P99 на запрос

**auto_explain:**
```sql
LOAD 'auto_explain';
SET auto_explain.log_min_duration = 1000;
SET auto_explain.log_analyze = true;  -- adds runtime overhead!
```
Логирует полный EXPLAIN для медленных запросов → подробная диагностика.

**pganalyze / pgwatch2:** дашборды поверх pg_stat_statements.

**Рабочий процесс:**
1. pg_stat_statements → топ-N
2. Выбрать самый влиятельный запрос (total_exec_time)
3. Взять пример аргументов из лога
4. EXPLAIN ANALYZE в тесте
5. Исправить (индекс, переписать, конфиг)
6. Выкатить, замерить

## Q27. Как нагрузочно тестировать БД (pgbench, sysbench)?

Цель нагрузочного теста БД — измерить TPS и latency (особенно P99) под реалистичной нагрузкой и проверить, выдержит ли база ожидаемый трафик. Ключ к достоверности — воспроизвести прод: объём данных, конфиг, сеть. Два основных инструмента — pgbench (идёт с PostgreSQL) и sysbench (мультиСУБД).

**pgbench** (идёт в комплекте с PostgreSQL):
- Встроенный бенчмарк в стиле TPC-B
- Поддерживает собственные сценарии
```bash
pgbench -i -s 100 testdb   # init scale 100 (~1.5GB)
pgbench -c 50 -j 4 -T 60 testdb  # 50 clients, 4 threads, 60s
```

Вывод: TPS (транзакций в секунду) и latency.

**Свой сценарий:**
```sql
-- my_bench.sql
\set uid random(1, 10000)
SELECT * FROM users WHERE id = :uid;
```
```bash
pgbench -c 50 -T 60 -f my_bench.sql testdb
```

**sysbench:**
- Несколько СУБД (MySQL, PostgreSQL)
- Стандартные OLTP-нагрузки
```bash
sysbench --db-driver=pgsql oltp_read_write prepare
sysbench --db-driver=pgsql oltp_read_write run --threads=64 --time=60
```

**Целевые сценарии:**
- С упором на запись (нагрузка INSERT)
- С упором на чтение (нагрузка SELECT)
- Смешанный (70/30)
- Чувствительный к latency (P99)

**Рекомендации** (чтобы результат был достоверным):
- Объём данных как в прод (scale factor ~ размер прода) — иначе всё влезает в кэш и тест врёт
- Конфиг как в прод (shared_buffers, work_mem)
- Сеть как в прод — латентность сети сама может стать узким местом теста
- Прогрев: несколько минут разогрева, чтобы заполнить кэши перед замером
- Замеряйте не только среднее: TPS, latency P50, P95, P99 (хвосты важнее среднего)
- Итерируйте по одному параметру за раз, иначе непонятно, что повлияло

**Прочие инструменты:**
- **HammerDB** — OLTP/TPC-C, TPC-H
- **jmeter** / **k6** — на уровне приложения (end-to-end, не чистая БД)
- **pg_bench_tools** (community-скрипты)

**Планирование ёмкости:** экстраполируйте «при нагрузке 5k TPS p99 = 50 мс» — сравните с SLO.
