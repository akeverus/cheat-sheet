## Q1. (!) Какие ключевые метрики кэша нужно мониторить?

Минимальный набор для любого кэша в проде — это **hit ratio, eviction rate, latency, throughput, использование памяти, число соединений, сетевой трафик и error rate**. Главная из них — hit ratio: пока он высок, кэш разгружает backend; остальные показывают, упирается ли узел в память, CPU или сеть.

**Hit ratio (доля попаданий) — король метрик:**
```
hit_ratio = hits / (hits + misses)
```
- Целевое значение зависит от workload (80-99%).
- Низкое значение означает, что кэш не разгружает backend и фактически бесполезен.

**Eviction rate (частота вытеснения):**
- Сколько ключей вытесняется в секунду (LRU/LFU).
- Высокая частота = память под давлением → увеличить размер или подстроить TTL.

**Latency (задержка):**
- Время GET / SET по перцентилям p50/p95/p99.
- Для Redis норма — единицы миллисекунд; > 10ms сигнализирует о проблеме (сеть, big keys).

**Throughput (пропускная способность, ops/sec):**
- Число GET/SET в секунду — нужно для планирования ёмкости.

**Использование памяти:**
- `used_memory` относительно `maxmemory`.
- Выше 80% — кэш начинает активно вытеснять.

**Число соединений:**
- Открытые соединения упираются в лимит на стороне сервера.
- Слишком много — исчерпание пула соединений.

**Пропускная способность сети:**
- В лимиты NIC можно упереться раньше, чем в CPU.

**Error rate (доля ошибок):**
- Сбойные операции: connection refused, timeout, OOM.

**Специфика Redis:**
- `instantaneous_ops_per_sec`
- `keyspace_hits` / `keyspace_misses`
- `evicted_keys`
- `expired_keys`
- `blocked_clients`

**Memcached:**
- `get_hits` / `get_misses`
- `bytes` / `limit_maxbytes`
- `evictions`

**Экспорт метрик:** `redis_exporter` / `memcached_exporter` → Prometheus → Grafana.

## Q2. (!) Hit ratio — что считается "хорошо"?

Универсального числа нет — «хороший» hit ratio зависит от природы данных. Чем сильнее ключи повторяются, тем выше планка; для long-tail данных даже 50-80% — нормальный результат. Ориентиры по типам данных:

| Уровень | Данные | Целевой hit ratio | Почему |
|---------|--------|-------------------|--------|
| Tier 1 | hot data: сессии, конфиг | **99%+** | почти всё закэшировано, miss редок; короткий TTL и прогрев заранее |
| Tier 2 | кэш DB-запросов, ответы API | **90-95%** | большинство запросов из кэша, есть инвалидация; типичное веб-приложение |
| Tier 3 | CDN, статика | **95-99%** | статика меняется редко |
| Tier 4 | long-tail (пользовательский контент) | **50-80%** | много уникальных ключей, мало повторов (распределение Zipf); кэш полезен, но не доминирует |

**На каком окне считать.** Мгновенное значение скачет, поэтому окно подбирают под задачу:
- **За 1 минуту** — волатильно, для дашборда в реальном времени.
- **Среднее за 5-15 мин** — стабильно, годится для алертинга.
- **За сутки** — анализ тренда.

**Причины низкого hit ratio:**
- TTL слишком короткий — ключ вытесняется до повторного использования.
- Размер кэша слишком мал — вытеснение по LRU.
- Много уникальных ключей (long tail) — кэшировать почти нечего.
- Слишком агрессивная инвалидация.
- Cold start после деплоя или рестарта.

**Порядок устранения:**
1. Измерить текущий hit ratio по каждому кэшу.
2. Если ниже целевого — разбираться дальше.
3. Посмотреть top-N промахов (если доступно) и искать паттерны.
4. Подстроить размер, TTL или реструктурировать ключи.

**Подводный камень: выше не всегда лучше.** 100% попаданий легко получить, вечно кэшируя мусор. Нужен баланс со свежестью данных, иначе кэш будет уверенно отдавать устаревшее.

## Q3. (!) Как измерить влияние кэша на latency?

Цель — понять, насколько кэш реально ускоряет запросы и сколько накладных расходов добавляет сам. Самый честный способ — A/B-сравнение с выключенным кэшем; самый наглядный — формула среднего времени через hit ratio. На практике сочетают несколько подходов.

**Метод 1: прямое измерение каждого пути.**
```java
long start = System.nanoTime();
Value v = cache.get(key);
long cacheLatency = System.nanoTime() - start;

if (v == null) {
    start = System.nanoTime();
    v = db.query(key);  // slow path
    long dbLatency = System.nanoTime() - start;
    cache.put(key, v);
}
```

Логируем метрики по быстрому (кэш) и медленному (DB) путям отдельно.

**Метод 2: A/B через feature flag.** Отключить кэш для части трафика и сравнить end-to-end latency. Показывает «реальный» эффект, включая накладные расходы самого кэша.

**Метод 3: анализ p99.** Отсортировать запросы по latency: p99 — самый медленный 1%, и это часто именно промахи кэша. Дельта между p99 и p50 косвенно показывает эффективность кэша.

**Расчёт теоретического эффекта.** Среднее время — взвешенная сумма быстрого и медленного путей:
```
avg_latency = hit_ratio × cache_lat + (1 - hit_ratio) × miss_lat
```

Пример (попадание = 1ms, DB = 100ms):
- Hit ratio 95% → avg = 0.95×1 + 0.05×100 = 5.95ms
- Hit ratio 90% → avg = 10.9ms — почти вдвое медленнее

Падение hit ratio всего на 5 пунктов почти удвоило среднюю latency. Эффект нелинейный, потому что доля дорогих промахов выросла вдвое (с 5% до 10%) — поэтому hit ratio и считают главной метрикой.

**Инструментирование.** Спаны OpenTelemetry с атрибутом `cache.hit=true/false`; разбивка p99 по этому атрибуту сразу показывает вклад промахов.

**Подводный камень: кэш сам добавляет latency.**
- Сетевой RTT до Redis — 1-2ms.
- Сериализация и десериализация.
- In-proc кэш (Caffeine) — микросекунды, по сути бесплатно.

## Q4. (!) LRU / LFU / TinyLFU — в чём разница по производительности?

Это три политики вытеснения, и разница в том, что считать «ненужным». LRU смотрит на давность обращения, LFU — на частоту, а TinyLFU объединяет оба сигнала и почти всегда выигрывает по hit ratio. Логика проста: давность ловит свежесть, но пропускает «однодневки»; частота ловит популярность, но цепляется за устаревшее; TinyLFU балансирует и то, и другое.

**LRU (Least Recently Used):**
- Вытесняет давно не использованное.
- **Плюсы:** простота, хорош для последовательных workload-ов.
- **Минусы:** «однодневки» (one-hit wonders) засоряют кэш — свежие, но малоценные записи занимают место.

**LFU (Least Frequently Used):**
- Вытесняет запись с наименьшим счётчиком обращений.
- **Плюсы:** удерживает популярные элементы.
- **Минусы:** классический LFU ничего не забывает, поэтому когда-то популярные, но устаревшие записи вытесняют новые.

**TinyLFU (Caffeine, современный Redis `allkeys-lfu`):**
- Оценщик частоты (Count-Min Sketch) плюс оконный LRU.
- Аппроксимирует LFU при малом расходе памяти.
- Учитывает и свежесть, и частоту — лучшее из двух подходов.
- Победитель в бенчмарках на реалистичных workload-ах.

**Сравнение hit ratio** (реалистичный workload, например база или поиск):
- LRU: ~70-80%
- LFU: ~75-82%
- **TinyLFU: 85-95%** — заметно лучше

**Admission filter (фильтр допуска)** — ключевая идея TinyLFU: новый элемент вытесняет текущего жильца только если его оценочная частота выше. Это не даёт случайному холодному попаданию вымыть прогретый кэш.

**Режимы Redis:**
- `allkeys-lru` — дефолт во многих конфигах.
- `allkeys-lfu` (с 4.0) — приближённый LFU.
- Настраивается через `maxmemory-samples` (дефолт 5; больше = точнее приближение ценой CPU).

**Caffeine** использует TinyLFU — обычно верный выбор для in-proc кэша на JVM.

**Вердикт.** На типичном веб-workload с распределением Zipf TinyLFU превосходит LRU на 5-15% по hit ratio.

## Q5. (!) Redis `maxmemory-policy` — как выбрать?

`maxmemory-policy` определяет, что Redis делает при достижении лимита памяти: вытеснять записи или возвращать ошибку. Выбор зависит от того, чистый ли это кэш, смешанная нагрузка (кэш + сессии) или хранилище. Семейство `allkeys-*` трогает все ключи, `volatile-*` — только ключи с выставленным TTL.

**Политики:**

- **`noeviction`** — возвращать ошибку при OOM (дефолт в некоторых конфигах).
- **`allkeys-lru`** — вытеснять по LRU среди всех ключей.
- **`allkeys-lfu`** — вытеснять по LFU среди всех ключей (4.0+).
- **`allkeys-random`** — случайное вытеснение.
- **`volatile-lru`** — LRU только среди ключей с TTL.
- **`volatile-lfu`** — LFU среди ключей с TTL.
- **`volatile-random`** — случайное среди ключей с TTL.
- **`volatile-ttl`** — первым выбывает ключ с наименьшим остаточным TTL.

**Как выбрать под сценарий:**

**Чистый кэш** (все данные кэшируемы, без различий):
- `allkeys-lfu` — обычно лучший hit ratio.
- `allkeys-lru` — проще, примерно так же хорош.

**Кэш + хранилище сессий** (смешанная нагрузка):
- `volatile-lru` или `volatile-lfu` — у сессий есть TTL, поэтому вытесняем кэш, но сохраняем сессии.
- Подвох: постоянные ключи без TTL никогда не вытесняются и могут заполнить память — следить за этим.

**Write-through с персистентностью** (Redis как хранилище, а не кэш):
- `noeviction` — приложение само управляет объёмом; приходится мириться с ошибками OOM.

**Настройка:**
```
maxmemory 10gb
maxmemory-policy allkeys-lfu
maxmemory-samples 10  # default 5; higher = better approximation
```

**Антипаттерн:** `noeviction` с неограниченным TTL — растёт до OOM → падение.

**Мониторинг:** счётчик `evicted_keys`; всплески указывают на нехватку ресурсов.

## Q6. Что такое фрагментация памяти Redis и как с ней бороться?

Фрагментация — это разрыв между памятью, которую Redis реально использует под данные, и памятью, которую под него выделила ОС. Измеряется коэффициентом: значение около 1.0 идеально, выше 1.5 — память расходуется впустую, а меньше 1.0 сигнализирует о свопе (худший случай).

**Коэффициент фрагментации:**
```
mem_fragmentation_ratio = used_memory_rss / used_memory
```

- 1.0 — фрагментации нет.
- 1.0-1.5 — норма.
- больше 1.5 — высокая фрагментация, память расходуется впустую.
- меньше 1.0 — своп: ОС выгрузила память Redis на диск, latency становится ужасной.

**Причины:**
- Ключи и значения переменного размера (арены jemalloc).
- Удаления оставляют «дыры» в памяти.
- Долгоживущий процесс с большим числом записей.

**Как исправить:**

**Активная дефрагментация (Redis 4.0+):**
```
activedefrag yes
active-defrag-ignore-bytes 100mb
active-defrag-threshold-lower 10
active-defrag-threshold-upper 100
active-defrag-cycle-min 5
active-defrag-cycle-max 75
```
- Фоновый процесс перемещает значения, уплотняя память.
- Накладные расходы по CPU регулируются через `active-defrag-cycle-max`.

**Рестарт** — крайняя мера: очищает кэш. Чтобы не терять трафик, делают failover на реплику и перезапускают primary.

**Аллокатор:** jemalloc (дефолт Redis) даёт наименьшую фрагментацию — не используйте libc malloc.

**Мониторинг:** алерт, если `mem_fragmentation_ratio > 1.5` держится продолжительное время.

## Q7. (!) Что такое thundering herd / cache stampede?

Cache stampede (он же thundering herd) — это лавина одновременных промахов, когда у популярного ключа истекает TTL. Пока кэш держал значение, он принимал, например, 1000 RPS вместо backend. Как только ключ исчезает, все эти запросы промахиваются разом и одновременно бьют в DB, перестраивая одно и то же значение.

**Сценарий:**
1. Истекает hot key.
2. 1000 одновременных запросов промахиваются мимо кэша.
3. Все 1000 перестраивают значение — бьют в DB или пересчитывают.
4. DB раздавлена, latency взлетает.

Суть проблемы: кэш экранировал backend от 1000 RPS, и в момент промаха эти 1000 RPS целиком обрушиваются на DB.

**Последствия:**
- Перегрузка DB.
- Каскадный отказ.
- Всплеск latency.
- Тем хуже, чем дольше перестройка (секунды — критично).

**Защита** (детальнее в Q8):

**1. Распределённый лок (mutex).** Первый промах берёт лок и перестраивает значение, остальные ждут и затем читают свежий результат:
```java
if (cache.get(key) == null) {
    if (lock.tryLock(key, 5s)) {
        try {
            val = db.load();
            cache.put(key, val);
        } finally { lock.unlock(); }
    } else {
        waitAndRetry();
    }
}
```

**2. Вероятностное досрочное истечение.** Перестраивать значение вероятностно ещё до формального истечения: чем ближе к expiry, тем выше шанс. Так перестройку делает один случайный запрос, а не вся толпа сразу. Формула (Vattani et al. 2015):
```
now - (delta × β × ln(random())) >= expiry
```
**Плюс:** нет лока, нагрузка на перестройку размазана по времени.

**3. Stale-while-revalidate.** Отдавать устаревшее значение и асинхронно запускать перестройку. Подходит, когда допустима лёгкая несвежесть (обычно так и есть).

**4. Request coalescing (в пределах процесса).** Single-flight дедуплицирует одновременные запросы: в Go — `singleflight`, в Java — кэш на `CompletableFuture`.

**5. Прогрев (warmup).** Заполнить кэш заранее, до подачи трафика.

## Q8. (!) Защита от stampede: mutex и probabilistic early expiration?

Это два главных способа не дать толпе запросов одновременно перестраивать значение. Mutex пускает к backend ровно одного, остальные ждут — просто, но ждущие блокируются. Вероятностный алгоритм (XFetch) обновляет значение чуть раньше истечения силами одного случайного запроса — никто не блокируется, но реализация сложнее.

**Распределённый mutex (Redis):**

```python
def get_with_lock(key):
    val = redis.get(key)
    if val:
        return val
    
    lock_key = f"lock:{key}"
    if redis.set(lock_key, 1, nx=True, ex=10):  # 10s lock
        try:
            val = db.query(key)
            redis.set(key, val, ex=300)
            return val
        finally:
            redis.delete(lock_key)
    else:
        # Another is rebuilding; wait or serve stale
        time.sleep(0.1)
        return redis.get(key) or get_with_lock(key)  # recursion limit
```

**Плюсы:** просто, гарантирует единственного перестраивающего.
**Минусы:** ждущие блокируются; критично гарантированно освобождать лок (помогает короткий TTL на самом локе).

**Redlock (Redis multi-master)** — более надёжный распределённый лок, но для большинства кэш-сценариев избыточен.

**Вероятностный алгоритм (XFetch):**
```python
def xfetch(key, ttl, compute_fn):
    data, expiry, delta = redis.get_with_meta(key)
    now = time.time()
    if data and now - delta * BETA * math.log(random.random()) < expiry:
        return data  # serve cached
    
    # Probabilistically refresh early
    start = time.time()
    data = compute_fn()
    delta = time.time() - start
    redis.set_with_meta(key, data, ttl, delta)
    return data
```

- `delta` — время на пересчёт, хранится рядом со значением.
- `BETA` — настроечная константа (обычно 1.0): больше → раньше начинаются обновления.
- Чем ближе к истечению, тем выше вероятность перестройки (стремится к 1).
- «Стада» нет: запросы размазаны по окну перестройки.

**Caffeine** (Java in-proc) даёт это из коробки через `refreshAfterWrite`: асинхронное обновление с одновременной отдачей закэшированного значения.

**Сравнение подходов:**

| Подход | Простота | Эффективность | Latency |
|----------|-----------|---------------|---------|
| Mutex | Средняя | Высокая | Ждущие заблокированы |
| Вероятностный | Сложно | Высокая | Никто не блокируется |
| Stale-while-revalidate | Легко | Высокая (для толерантных приложений) | Никто не блокируется |
| Прогрев | Легко | Высокая (если реализуемо) | Разовый |

## Q9. Что такое request coalescing?

Request coalescing (он же single-flight) — дедупликация одновременных идентичных запросов внутри одного процесса. Если несколько потоков промахнулись по одному ключу, к backend уходит ровно один запрос, а все остальные ждут его результат. Это локальный аналог mutex из Q8, но без распределённого лока.

**Без coalescing:**
- Запрос A промахивается и запускает DB-запрос.
- Запрос B (через 1ms) тоже промахивается и запускает ещё один такой же DB-запрос.
- Два DB-запроса ради одного результата.

**С coalescing:**
- Запрос A запускает задачу.
- Запрос B видит уже выполняющуюся задачу A и ждёт тот же future.
- Один DB-запрос, оба получают результат.

**Go `singleflight`:**
```go
var group singleflight.Group
result, _, _ := group.Do(key, func() (interface{}, error) {
    return db.Query(key)
})
```

**Java (CompletableFuture):**
```java
ConcurrentHashMap<String, CompletableFuture<Value>> inflight = new ConcurrentHashMap<>();

public Value get(String key) {
    Value v = cache.get(key);
    if (v != null) return v;
    
    return inflight.computeIfAbsent(key, k -> 
        CompletableFuture.supplyAsync(() -> {
            Value val = db.query(k);
            cache.put(k, val);
            inflight.remove(k);
            return val;
        })
    ).join();
}
```

**Caffeine** делает coalescing автоматически при использовании `.build(CacheLoader)`.

**Ограничения.** Работает только в пределах процесса и не спасёт, если 100 подов промахиваются одновременно — для межпроцессного случая комбинируют с распределённым mutex (Q8).

**Подвох:** исключение в общем future уронит все ждущие запросы, которые его разделяют. Часто это приемлемо, но об этом нужно помнить.

## Q10. (!) Как выбрать TTL?

TTL — это компромисс между свежестью и hit ratio: чем он короче, тем актуальнее данные, но тем чаще промахи. Отправная точка — допустимая несвежесть данных, дальше TTL корректируют с учётом стоимости промаха, частоты изменений и возможности явной инвалидации.

**Факторы:**

**1. Требование к свежести** (главный фактор):
- Реальное время (биржевые котировки) → секунды.
- Детали товара → минуты-часы.
- Профиль пользователя → часы-дни.
- Конфиг → часы-сутки.

**2. Стоимость промаха на backend:**
- Дёшево (in-memory вычисление) → короткий TTL допустим.
- Дорого (DB-запрос с кучей join-ов, 500ms) → длинный TTL.

**3. Частота изменений:**
- Меняется редко → длинный TTL (дни).
- Меняется часто → короткий TTL или event-driven инвалидация.

**4. Возможность инвалидации:**
- Есть механизм (pub/sub, шина событий) → длинный TTL допустим, свежесть обеспечит инвалидация.
- Нет инвалидации → TTL равен максимально допустимой несвежести.

**Прагматичные дефолты:**
- Ответы API: 5-60 секунд
- Кэш DB-запросов: 1-5 мин
- Конфиг / справочные данные: 1ч
- Сессии: 24ч

**Расчёт:**
```
hit_ratio = TTL_length / (TTL_length + request_interval)
```

Пример (ключ запрашивается каждые 100ms):
- TTL = 5s → ratio = 5 / 5.1 ≈ 98%
- TTL = 1s → ratio = 1 / 1.1 ≈ 91%
- Увеличение TTL в 5 раз даёт +7 пунктов hit ratio — отдача от роста TTL быстро падает.

**Подстройка под workload.** Измерить hit ratio при нескольких TTL, построить график и найти точку перегиба, где дальнейший рост TTL почти не помогает.

**Подвох:** слишком длинный TTL без инвалидации — пользователь видит устаревшее. Контрольный вопрос: нормально ли, что данные устарели, например, на час?

## Q11. Что такое jittered TTL и зачем он нужен?

Jittered TTL — добавление случайного разброса к времени жизни, чтобы ключи истекали не одновременно, а в окне. Это защита от массового истечения: если множество ключей выставлено с одинаковым TTL, они истекут в одну секунду и устроят stampede по DB. Джиттер размазывает истечения во времени.

**Проблема:**
- 10 000 ключей выставлены одновременно с TTL=60s.
- Все истекают разом.
- 10 000 промахов → stampede по DB.

**Решение:** добавить случайный джиттер к TTL, чтобы истечения распределились по окну.

**Реализация:**
```python
TTL_BASE = 60
TTL_JITTER = 10  # ±10s
ttl = TTL_BASE + random.randint(-TTL_JITTER, TTL_JITTER)
redis.set(key, val, ex=ttl)
```

- Теперь ключи истекают в окне 50-70s.
- Нагрузка плавная вместо всплеска.

**Когда особенно важно** (TTL синхронизируются сами собой):
- Пакетный прогрев или построение кэша.
- Ежедневный дамп или почасовое обновление.
- Событие деплоя — все поды прогревают кэш одновременно.

**Caffeine:**
- Интерфейс `Expiry` в `expireAfterWrite` может возвращать случайную длительность.
- Или добавить джиттер вручную: `Duration.ofSeconds(60 + random())`.

**Родственный паттерн — обновление до истечения.** Обновлять значение асинхронно на 80% TTL: работает как естественный джиттер и заодно избавляет от массового промаха.

**Эффект:** график нагрузки на DB превращается из «пилы» в ровную линию — перестройка идёт плавным темпом, без всплесков.

## Q12. (!) Cold start — какие есть стратегии прогрева кэша?

Холодный кэш (cold start) — это пустой кэш, который пропускает все запросы в DB и даёт всплеск latency. Задача прогрева — заполнить кэш до того, как на инстанс пойдёт реальный трафик, либо нарастить трафик плавно, чтобы кэш успел заполниться сам.

**Когда кэш оказывается холодным:**
- Деплой или рестарт.
- Failover кэш-кластера.
- Масштабирование — поднялся новый инстанс.
- Массовое истечение TTL.

**Эффект:** часть или все запросы бьют в DB → всплеск latency, возможна перегрузка.

**Стратегии:**

**1. Жадный прогрев (предзагрузка).** До подачи трафика заполнить кэш самыми запрашиваемыми ключами (top-N из логов доступа). Readiness probe проходит только после завершения прогрева.

**2. Постепенный набор трафика.** Балансировщик отдаёт новому инстансу 1%, 5%, 10% трафика за несколько минут — кэш заполняется естественно, без перегрузки backend.

**3. Репликация.** Реплика кэша рядом с primary (Redis replica): при рестарте primary промоутим уже прогретую реплику. Связка L2 (Redis) + L1 (Caffeine) тоже помогает — L2 переживает рестарт процесса с L1.

**4. Персистентный кэш.** Redis с AOF/RDB переживает рестарт (загрузка снапшота занимает время). Memcached непостоянен и всегда стартует холодным.

**5. Фоновое обновление из источника истины.** ETL/batch-задача или поток событий (Kafka) пишет в кэш, поддерживая его горячим.

**6. Не прогревать вовсе.** Смириться с медленным первым запросом — если SLO это допускает, отдельный прогрев не нужен.

**Измерение прогрева.** Метрика — время достижения целевого hit ratio (например, 95%). Это «время прогрева» должно быть меньше максимально допустимого холодного периода.

**K8s:** readiness probe должна возвращать healthy только после прогрева, иначе балансировщик начнёт слать трафик на ещё холодный под.

## Q13. Какие есть паттерны инвалидации и как они влияют на производительность?

Инвалидация — это компромисс между согласованностью и стоимостью. Чем сильнее гарантия свежести, тем дороже и сложнее механизм: TTL почти бесплатен, но отдаёт устаревшее; CDC даёт near-realtime, но требует сложной инфраструктуры. Как пошутил Phil Karlton, «в Computer Science есть только две сложные вещи: инвалидация кэша и придумывание имён».

**Паттерны (от дешёвых к строгим):**

**1. На основе TTL.** Простейший вариант без явной инвалидации — миримся с несвежестью в пределах TTL.
- **Стоимость:** нулевая. **Рассогласование:** в пределах окна TTL.

**2. Write-through.** При записи в DB синхронно обновляем кэш.
- **Стоимость:** latency записи = max(DB, кэш), сбой если кэш недоступен. **Согласованность:** строгая.

**3. Write-behind.** Обновляем кэш, а запись в DB идёт асинхронно.
- **Стоимость:** дёшево. **Риск:** потеря данных при падении до записи в DB.

**4. Событийная (pub/sub).** Изменение в DB порождает событие, подписчики инвалидируют свои кэши.
- **Стоимость:** инфраструктура (Kafka / Redis pub/sub). **Согласованность:** секунды. Хорошо ложится на CQRS и event sourcing.

**5. CDC (Change Data Capture).** Debezium читает WAL базы → топик → консьюмер инвалидации.
- **Стоимость:** сложно. **Согласованность:** почти в реальном времени. Хорошо масштабируется.

**6. По тегам (Varnish, Fastly).** Группируем ключи тегом; инвалидация тега сбрасывает все связанные ключи.
- Пример: тег `user:42` на всех страницах пользователя 42 — запись инвалидирует тег, все эти кэши очищаются разом.

**7. По версии.** Версия зашита в ключ: `product:v5:123`. Обновление DB инкрементит версию — это фактически новая запись в кэше, а старые ключи со временем истекают по TTL.

**Что учесть по производительности:**
- Broadcast-инвалидация — это N×M сообщений (N кэшей × M ключей); проверить, масштабируется ли.
- Лаг инвалидации = окно отдачи устаревшего.
- Слишком агрессивная инвалидация роняет hit ratio.

**Рекомендация:** начинать с TTL (просто), добавлять явную инвалидацию только там, где несвежесть недопустима, и действовать прицельно — не «инвалидировать всё при любой записи».

## Q14. (!) Зачем нужна связка L1 (in-proc) + L2 (Redis)?

Двухуровневый кэш сочетает скорость локального кэша со ёмкостью и общностью распределённого. L1 в памяти процесса отдаёт hot keys за микросекунды без сети; L2 (Redis) — общий для всех инстансов, переживает рестарт процесса и вмещает гораздо больше. Запрос сначала идёт в L1, при промахе — в L2, и лишь затем в DB.

**L1: внутрипроцессный** (Caffeine, Guava, локальный HashMap):
- Latency: наносекунды-микросекунды.
- Ёмкость: ограничена heap JVM (обычно 100MB-1GB).
- Без сети.

**L2: распределённый** (Redis, Memcached):
- Latency: 0.5-2ms (сеть).
- Ёмкость: терабайты.
- Общий для всех инстансов приложения.

**Иерархия:**
```
Request → L1 (check in-proc) → L2 (check Redis) → DB
         hit → return (μs)    hit → return (ms)    miss → rebuild
```

**Преимущества:**
- **Сверхбыстро** для hot keys — попадания обслуживаются из L1.
- **Разгрузка Redis** — освобождается его CPU.
- **Экономия сети** — меньше GET-ов уходит в Redis.
- **Устойчивость** к отказу Redis — L1 продолжает отдавать данные.

**Компромисс: согласованность.** L1 и L2 могут рассинхронизироваться: L2 уже обновлён, а L1 ещё держит старое значение до своего TTL. Для большинства сценариев это приемлемо, если TTL у L1 короткий.

**TTL для L1** держат короче, чем у L2 (например, L1=1мин, L2=10мин) — чтобы быстро сходиться к актуальному значению.

**Инвалидация.** Либо публиковать событие инвалидации (Redis pub/sub), чтобы все L1 сбросили ключ, либо просто мириться с кратковременной несвежестью L1.

**Когда применять:**
- Read-heavy нагрузка (10 000+ RPS на один ключ) — L1 критичен.
- Hot keys по распределению Парето: 20% ключей дают 80% запросов.
- Чувствительность к latency (SLO в долях миллисекунды).

**Когда не стоит:**
- Низкий RPS — накладные расходы L1 превышают выгоду.
- Каждое чтение обязано отдавать строго последнее значение.

## Q15. Как настраивать Caffeine?

Caffeine — высокопроизводительная in-proc библиотека кэширования для Java (использует TinyLFU из Q4). Настройка сводится к трём решениям: ограничение размера (`maximumSize`/`maximumWeight`), политика истечения (`expireAfterWrite`/`expireAfterAccess`) и асинхронное обновление (`refreshAfterWrite`) — плюс обязательный сбор статистики.

**Конфигурация:**
```java
Cache<K, V> cache = Caffeine.newBuilder()
    .maximumSize(10_000)         // LFU-based eviction
    .expireAfterWrite(5, MINUTES) // TTL
    .expireAfterAccess(10, MINUTES) // TTI (time-to-idle)
    .refreshAfterWrite(1, MINUTES)  // async refresh for freshness
    .recordStats()                  // enable metrics
    .build(key -> db.load(key));
```

**`maximumSize` vs `maximumWeight`:**
- Size считает число записей.
- Weight использует свою функцию-весовщик (`entry.size()` в байтах).
- Выбор зависит от того, сильно ли различаются размеры значений: при разнородных значениях точнее ограничивать по весу.

**`expireAfterWrite` vs `expireAfterAccess`:**
- Write — фиксированный TTL от момента создания.
- Access — TTL сбрасывается при каждом чтении, поэтому hot keys остаются в кэше.
- Для своей логики комбинируется с `expireAfter(Expiry)`.

**`refreshAfterWrite`** — асинхронная фоновая перезагрузка спустя заданное время. Пока идёт обновление, отдаётся устаревшее значение, поэтому штрафа за промах нет. Критично для защиты от stampede.

**Статистика:**
```java
CacheStats stats = cache.stats();
stats.hitRate();       // e.g., 0.94
stats.evictionCount();
stats.missRate();
```

Экспорт через Micrometer в Prometheus:
```java
CaffeineCacheMetrics.monitor(registry, cache, "user_cache");
```

**Подбор размера:**
- Начать с 10x от ожидаемого числа уникальных ключей.
- Следить за hit ratio и корректировать.
- Слишком большой кэш давит на GC — заполняется old-gen.

**Загрузка кэша:**
- `CacheLoader` — синхронная загрузка при промахе.
- `AsyncCacheLoader` — неблокирующая.
- Оба объединяют одновременные запросы по одному ключу, защищая от «стада».

**Spring Boot:**
```yaml
spring.cache.type: caffeine
spring.cache.caffeine.spec: maximumSize=1000,expireAfterWrite=10m
```

## Q16. (!) Какие накладные расходы у Redis Cluster по сравнению с одним узлом?

Кластер даёт горизонтальное масштабирование (данные + записи распределены по N мастерам), но платит за это сложностью: cross-slot операции ломаются, появляются MOVED-редиректы, транзакции через слоты невозможны. По latency cluster-aware клиент с кэшированной картой слотов почти не уступает одному узлу — основная цена не в скорости, а в ограничениях на операции с несколькими ключами.

**Одноузловой Redis:**
- Минимальная latency, простота.
- Лимит — в основном 1 ядро CPU и RAM одной машины.

**Redis Cluster:**
- Шардирование по N мастерам, 16384 хэш-слота.
- Горизонтальное масштабирование данных и записей.

**Где появляются накладные расходы:**

**1. Сетевые хопы.** Если клиент попал не на тот узел, он получает редирект (MOVED) на нужный. Умный (cluster-aware) клиент кэширует карту слотов, и редиректов нет.

**2. Кросс-слотовые операции.** `MGET key1 key2` падает, если ключи в разных слотах. Решения: **hash tags** (`{user:42}:session`, `{user:42}:orders` попадают в один слот) либо Lua/пакетирование по слотам через pipeline.

**3. Решардинг.** Перенос слотов вызывает кратковременные MOVED-редиректы — cluster-aware клиенты (Lettuce, Jedis JedisCluster) обрабатывают это прозрачно.

**4. Многоключевые транзакции (MULTI/EXEC).** Через слоты невозможны — данные нужно заранее колоцировать в одном слоте.

**Измерение latency:**
- p99 одного узла: ~1ms (localhost) / 2-3ms (внутри VPC).
- p99 кластера: сопоставимо при закэшированной карте слотов, хуже без неё.

**Sentinel (HA, не шардирование).** Даёт авто-failover на реплику и высокую доступность одного мастера, но ёмкость остаётся в пределах одного узла.

**Кластер не поможет, когда:**
- Один hot key — один слот живёт на одном узле, разделить нельзя.
- Малый объём данных, помещающийся на одну машину.

**Кластер помогает, когда:**
- Весь датасет больше лимита RAM.
- Пропускная способность записи упирается в CPU одного узла.
- Нужно распределить нагрузку.

**Альтернативы:** партиционирование на уровне приложения (consistent hashing по инстансам Redis) или Redis Enterprise (коммерческий) с прозрачным шардированием.

## Q17. Что даёт батчинг через Pipeline / MGET?

Батчинг устраняет главную беду множества мелких операций — повторяющийся RTT. 100 отдельных GET-ов = 100 round-trip к Redis, и latency определяется не работой сервера, а сетью. Pipeline отправляет все команды одним пакетом (1 RTT), MGET делает то же для нескольких GET одной командой. Эффект особенно велик на cross-region, где RTT десятки миллисекунд.

**Проблема:** 100 GET-ов в Redis = 100 RTT (500ms+ при cross-region).

**Решение через Pipeline:**
```python
p = redis.pipeline()
for key in keys:
    p.get(key)
results = p.execute()  # 1 RTT for all
```

**Решение через MGET:**
```python
results = redis.mget(keys)  # single command, 1 RTT
```

**Различия:**

| Аспект | Pipeline | MGET |
|--------|----------|------|
| RTT | 1 (все команды пакетом) | 1 |
| Типы команд | Любые (GET, SET, ...) | Только GET |
| Атомарность | Нет (если не обёрнуто в MULTI) | Одна команда |
| Поддержка кластера | Нужен cluster-aware клиент | Ключи в одном слоте |

**Pipeline для смешанных команд:**
```python
p = redis.pipeline()
p.get(key1)
p.set(key2, val)
p.incr(counter)
res1, _, counter = p.execute()
```

**Pipeline в кластере:**
- Ключи распределяются по узлам согласно слотам
- Lettuce: `RedisClusterAsyncCommands.mget(keys...)` разбивает автоматически
- Jedis: разбивать вручную

**Выигрыш в производительности:**
- 100 операций при RTT 1ms: 100ms последовательно против 2ms через pipeline — **в 50 раз быстрее**.
- На cross-region (RTT 20+ ms) выигрыш ещё больше.

**Эмпирическое правило:** пакетировать всегда, когда несколько ключей известны заранее и latency определяется RTT.

**Ограничение:** большие pipeline потребляют память на клиенте и сервере — держать разумный размер пакета (100-1000 команд).

## Q18. Каковы накладные расходы сериализации (JSON vs MessagePack vs protobuf)?

Формат сериализации влияет на две вещи: размер значения (трафик и память) и скорость кодирования/декодирования (CPU). JSON удобен и читаем, но самый крупный и медленный; бинарные форматы (MessagePack, Protobuf, Kryo, Fury) компактнее и быстрее ценой читаемости. Выбор зависит от размера значений и от того, что в кэше дороже — сеть или CPU.

**Замеры** (объект 1KB):

| Формат | Размер | Скорость сериализации | Скорость десериализации | Человекочитаемость |
|--------|------|-----------|-------------|----------------|
| JSON | 1000B | Быстро | Быстро | Да |
| MessagePack | 700B | Быстро | Быстро | Нет |
| Protobuf | 600B | Быстро | Быстро | Нет |
| Kryo (Java) | 550B | Быстрее всех на JVM | Быстрее всех на JVM | Нет |
| Avro | 600B | Средне | Средне | Нет (схема) |
| Fury (Apache) | 500B | Быстрее всех | Быстрее всех | Нет |
| Gzip(JSON) | 400B | Медленно | Медленно | Нет |
| Java Serialization | 1500B | Медленно | Медленно | Нет |

**Компромиссы:**
- JSON: универсален и читаем, но самый большой и медленный.
- MessagePack: бинарный JSON, легко внедрить.
- Protobuf: схема заранее даёт безопасность версий и компактность.
- Kryo: только для JVM, быстрый, но есть вопросы к обратной совместимости.
- Fury: лидер бенчмарков 2020-х.
- **Избегать:** Java Serialization — медленная, раздутая и подвержена CVE.

**Что важно именно для кэша:**
- Маленькое значение (< 1KB) — доминируют накладные расходы сериализации (CPU).
- Большое значение (> 10KB) — доминирует передача по сети, помогает сжатие.
- Hot key — сериализовать один раз и кэшировать готовые байты.

**Специфика Redis:**
- Хранить значения в бинарном виде (байты).
- Сжатие при сериализации (gzip, lz4, zstd) — обмен CPU на сеть.
- LZ4 — быстрая распаковка, Zstd — лучший коэффициент сжатия.

**Бенчмарк своего workload:**
```java
// ~ 5k ops/sec JSON vs 15k ops/sec protobuf типично
```

**Не переоптимизируйте.** Если кэш занимает 0.5% времени запроса, ускорение сериализации в 2× даёт выигрыш всего 0.25%. Сначала профилировать, потом менять формат.

## Q19. (!) Как CDN hit ratio зависит от cache-заголовков?

CDN hit ratio — доля запросов, отданных с edge, а не с origin (цель обычно 90%+, для статики >98%). Управляют им HTTP-заголовки ответа: `Cache-Control` задаёт TTL и кэшируемость, `Vary` определяет, на сколько копий дробится кэш, `ETag`/`Last-Modified` — ревалидацию. Большинство провалов hit ratio объясняется неправильными заголовками (например, `private`, `Set-Cookie` или `Vary: User-Agent`).

**Влияющие заголовки:**

**`Cache-Control`:**
- `max-age=3600` — кэшировать 1 час
- `s-maxage=7200` — TTL именно для CDN (отдельно от браузера)
- `public` / `private` — кэшируется CDN или нет
- `no-cache` — ревалидировать каждый раз
- `no-store` — не кэшировать вовсе
- `must-revalidate` — строго после истечения
- `stale-while-revalidate=60` — отдавать устаревшее 60s, пока идёт ревалидация

**`Vary`:**
- Перечисляет заголовки, от которых зависит кэшированный ответ
- `Vary: Accept-Encoding` — отдельный кэш для gzip/br
- `Vary: User-Agent` — катастрофа (по записи на каждый UA) — избегать!
- `Vary: Cookie` — тоже часто катастрофа

**`ETag` / `Last-Modified`:**
- Ревалидация: `If-None-Match: "etag"` → 304 Not Modified (без тела)
- Экономит трафик, но не latency

**Частые ошибки, убивающие hit ratio:**
- `Set-Cookie` — большинство CDN по умолчанию не кэшируют такие ответы.
- Query-строки — CDN может считать `?ts=1` и `?ts=2` разными объектами.
- `Cache-Control: private` — CDN пропускает ответ мимо кэша; для кэшируемого контента нужен `public`.

**Оптимизации:**
- **Нормализация query-строк** — убирать аналитические параметры (`utm_*`), чтобы не плодить копии.
- **Проектирование ключа кэша** — включать только значимые параметры.
- **Многоуровневое кэширование** — см. следующий вопрос.

**Измерение.** Дашборд CDN (CloudFront, Fastly) показывает hit ratio; при низком значении проверяют заголовки, конфигурацию ключа кэша и истечение.

**Рекомендации по Cache-Control:**
- Статика (JS/CSS/изображения): `max-age=31536000, immutable` плюс имя файла с фингерпринтом.
- HTML: `max-age=0, s-maxage=60` — клиенты всегда перезапрашивают, CDN кэширует ненадолго.
- API: настраивать по эндпоинтам, часто `private, max-age=0`.

## Q20. Что такое tiered caching в CDN?

Tiered caching ставит промежуточный уровень (shield POP) между сотней edge-узлов и origin. Без него каждый edge при промахе идёт прямо в origin, и популярный объект может вызвать сотню одновременных запросов к источнику. Со shield первый промах идёт к нему, shield забирает объект из origin ровно один раз, а остальные edge берут его уже у прогретого shield — origin защищён.

**Без многоуровневого:**
```
100 edge POPs → origin
All 100 miss same object → origin slammed with 100 requests
```

**Многоуровневое / shield POP:**
```
Edge POPs → shield POP (regional) → origin
First edge miss fetches from shield; shield fetches from origin ONCE
Other edges hit shield (shield pre-populated)
```

**Преимущества:**
- **Разгрузка origin** — снижение нагрузки в 9-100 раз.
- Промах разрешается быстрее для последующих edge: shield ближе, чем origin.

**Вендоры:**
- **Fastly:** shielding — назначить POP как shield.
- **CloudFront:** Origin Shield — включается на distribution.
- **Cloudflare:** Argo Tiered Cache — авто-выбор лучшего shield.

**Конфигурация:** shield обычно ставят ближе к origin, чем edge (origin в us-east-1 → shield в us-east-1), либо ближе к пользователям — зависит от паттерна трафика.

**Когда помогает:**
- Большое число edge POPs (100+).
- Long-tail контент — популярно не всё.
- Большие счета за нагрузку на origin.

**Когда не помогает:**
- Малый охват CDN (мало POPs).
- Очень короткий TTL кэша — shield тоже часто промахивается.

**Стоимость:** включение чуть дороже (запрос к shield тарифицируется), но окупается экономией на origin.

## Q21. (!) В чём проблема hot key и как её решать?

Hot key — один ключ, получающий непропорционально большую долю нагрузки (например, 80% GET-ов на один товар). Беда в том, что один ключ всегда живёт в одном слоте на одном узле, поэтому шардирование кластера не помогает: упирается CPU и NIC именно этого узла. Главное решение — снять нагрузку с Redis локальным L1-кэшем, чтобы hot key отдавался из памяти процесса.

**Почему это проблема:**
- Узел Redis с этим ключом упирается в CPU.
- Сетевой NIC к этому узлу становится бутылочным горлышком.
- Ребалансировка кластера не помогает — ключ нельзя разделить.

**Обнаружение:**
- `redis-cli --hotkeys` — на основе сэмплинга.
- `MONITOR` — захват всех команд (осторожно: высокие накладные расходы).
- Метрики приложения — счётчик попаданий по ключу.

**Решения:**

**1. Внутрипроцессный L1-кэш (Caffeine)** — главный приём. Hot key отдаётся в основном из памяти процесса, и нагрузка на Redis резко падает.

**2. Read-реплики.** Маршрутизировать чтения этого ключа на реплику; чтение с реплик в Redis Cluster (только RE) приложение включает явно.

**3. Шардирование ключа (multi-key).** Дублировать ключ по N экземплярам: `product:123:shard0`...`product:123:shard9`. Приложение читает случайный shard, запись обновляет все. Хорошо для read-heavy статики.

**4. Предрасчёт / денормализация.** Если hot key — это дорогой запрос, материализовать результат в другом месте.

**5. Сэмплинг на стороне клиента.** 1% чтений идёт в Redis, 99% отдаётся из L1-кэша в процессе; L1 инвалидируется через Redis pub/sub.

**Мониторинг:** алерт, если один ключ забирает > 5% всех операций.

**Из практики:** «проблема Джастина Бибера» у Twitter — таймлайн одного пользователя создавал горячий шард; решением стало кастомное шардирование.

## Q22. (!) В чём проблема big keys и как её решать?

Big key — это одно очень большое значение (> 100KB, тем более мегабайты). Основная опасность в том, что Redis однопоточный: операция над big key монополизирует единственный поток и блокирует все остальные команды. Плюс каждый GET тянет мегабайты по сети, раздувается репликация и фрагментация. Лечится дроблением значения на части и использованием коллекций с поэлементным/постраничным доступом.

**Чем вреден:**
- **Всплеск latency** — GET на ключ 10MB передаёт 10MB по сети на каждый запрос.
- **Блокировка** — Redis однопоточный, чтение big key тормозит все другие операции.
- **Фрагментация памяти** — боль при выделении и освобождении.
- **Лаг репликации** — запись big key отправляет 10MB на реплики.
- **Дисбаланс хэш-слотов** — узел с большим ключом становится «толще» остальных.

**Обнаружение:**
- `redis-cli --bigkeys` — сэмплинг.
- `MEMORY USAGE key` — точный размер.
- `DEBUG OBJECT key` — детальная информация.

**Частые причины:** большой list (миллионы элементов), большой hash (тысячи полей), большой set, большой сериализованный blob.

**Решения:**

**1. Разбить на меньшие части.** Вместо `SET user:42 {big_json}` использовать `HSET user:42 field1 val1` (заодно улучшаются паттерны доступа) либо шардировать вручную: `chunk1`, `chunk2`...

**2. Использовать коллекции вместо blob-ов.** Вместо JSON-списка — Redis List (RPUSH/LRANGE) с O(1) на элемент.

**3. Пагинация.** `LRANGE list 0 99` вместо `LRANGE list 0 -1` на весь список.

**4. Сжатие.** Хранить сжатый blob, распаковывать на стороне клиента.

**5. Вынести в настоящую БД / объектное хранилище.** Redis не хранилище для больших blob-ов — держать их в S3 или DB, а в кэше только указатель.

**6. Сканировать вместо MEMBERS.** `SMEMBERS huge_set` блокирует — использовать курсор `SSCAN`.

**Мониторинг:** алерт на `MEMORY USAGE > 1MB` для любого ключа.

## Q23. Кэш не масштабируется — что проверять?

Симптомы — latency растёт с нагрузкой, hit ratio падает, насыщаются CPU или память. Поскольку Redis однопоточный, чаще всего упирается одно ядро одного узла; дальше по списку идут сеть, лимиты соединений, отдельные «тяжёлые» ключи и команды, а также накладные расходы персистентности и клиента. Чек-лист — по порядку:

**1. Бутылочное горлышко одного узла.** Redis однопоточный — ядро CPU насыщается на ~100k ops/sec. Решение: кластер или чтения с реплик.

**2. Сетевой NIC.** 1 Gbps насыщен — есть ли 10 Gbps? Потребность в полосе = RPS × размер значения, поэтому большие значения упираются в сеть.

**3. Лимит соединений.** `CONFIG GET maxclients` — упёрлись в лимит? Слишком маленький пул на стороне приложения создаёт очереди.

**4. Hot key (Q21).** Один ключ перегружает узел — размазать через L1.

**5. Big keys (Q22).** Блокирующие операции над крупными значениями.

**6. Медленные команды.** `SLOWLOG GET 10` показывает недавние. Виновники: `KEYS *` (никогда не использовать в проде!), `HGETALL` на большом hash, `SMEMBERS`.

**7. Персистентность.** Всплеск `BGSAVE`, синхронизация `RDB`, перезапись `AOF`? `fork()` на большом heap создаёт давление Copy-on-Write. На чистом кэше персистентность лучше отключить.

**8. Фрагментация памяти.** `mem_fragmentation_ratio > 1.5` — см. Q6.

**9. Swap.** `mem_fragmentation_ratio < 1` означает выгрузку в swap — это плохо, swap нужно отключить.

**10. Проблема на стороне клиента.** Слишком маленький пул соединений, сериализация упирается в CPU, паузы GC в приложении блокируют обращения к кэшу.

**Инструменты:** `redis-cli --latency`, `redis-cli --latency-history`, дашборд Grafana для Redis.

**Варианты масштабирования:**
- **Вертикальное** — машина мощнее (ограничено однопоточностью Redis).
- **Горизонтальное** — кластер (шардирование данных) или репликация (масштабирование чтений).
- **Больше слоёв кэширования** — L1, CDN и т.д.
