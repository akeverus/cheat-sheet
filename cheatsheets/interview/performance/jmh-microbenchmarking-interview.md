# Вопросы на собеседовании: `JMH (Java Microbenchmark Harness)`

JMH (Java Microbenchmark Harness) — это библиотека от команды OpenJDK для корректного замера производительности небольших фрагментов JVM-кода (микробенчмарков). На собеседовании по performance её спрашивают, чтобы проверить, понимает ли кандидат, почему «наивные» замеры через `System.nanoTime()` врут, и умеет ли он бороться с оптимизациями JIT, прогревом и эффектами изоляции JVM.

## Q1. (!) Почему нельзя замерять производительность Java-кода просто через `System.nanoTime()`?

Потому что JVM — это не «честный исполнитель байткода по строчкам», а адаптивная среда с JIT-компилятором, который агрессивно оптимизирует код во время выполнения. Наивный замер ловит не то, что вы думаете, по нескольким причинам сразу.

- **Прогрев (warmup).** Первые тысячи вызовов код работает в интерпретаторе или под C1, и только потом C2 компилирует «горячий» метод. Если замерить первые вызовы — получите скорость интерпретатора, а не оптимизированного кода.
- **Dead-code elimination.** Если результат вычисления никуда не используется, JIT просто выкинет вычисление целиком. Вы измерите «как быстро Java умеет ничего не делать».
- **Constant folding.** Если на вход идут константы/литералы, JIT посчитает результат на этапе компиляции и заменит весь метод на возврат готовой константы.
- **On-stack replacement, инлайнинг, branch prediction**, эффекты GC, динамика частоты CPU — всё это искажает «ручной» замер в цикле.

Пример наивного замера, который почти наверняка соврёт:

```java
long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) {
    Math.log(42);            // результат не используется -> dead code
}
long elapsed = System.nanoTime() - start; // близко к нулю
```

JMH решает все эти проблемы системно: автоматический прогрев, форк отдельной JVM, `Blackhole` против dead-code elimination, передача входных данных через `@State` против constant folding.

**Итог:** ручной замер на JVM измеряет артефакты JIT, а не алгоритм. JMH — это инструмент, который делает замер воспроизводимым и честным.

## Q2. Как подключить JMH к проекту и из чего он состоит?

JMH состоит из двух артефактов, и нужны оба:

- `jmh-core` — рантайм-движок (раннер, аннотации, `Blackhole`, профилировщики).
- `jmh-generator-annprocess` — annotation processor, который на этапе компиляции генерирует обвязку (синтетические классы-раннеры вокруг ваших `@Benchmark`-методов). Без него бенчмарки просто не соберутся в исполняемый вид.

Актуальная стабильная версия на момент написания — `1.37`.

```xml
<dependency>
    <groupId>org.openjdk.jmh</groupId>
    <artifactId>jmh-core</artifactId>
    <version>1.37</version>
</dependency>
<dependency>
    <groupId>org.openjdk.jmh</groupId>
    <artifactId>jmh-generator-annprocess</artifactId>
    <version>1.37</version>
    <scope>provided</scope>
</dependency>
```

Рекомендованный способ старта — Maven-архетип `org.openjdk.jmh:jmh-java-benchmark-archetype`: он создаёт отдельный модуль, настраивает `maven-shade-plugin` для сборки fat-jar с `Main-Class: org.openjdk.jmh.Main`, и вы запускаете `java -jar target/benchmarks.jar`.

Важная практика: **бенчмарки держат в отдельном модуле**, который зависит от вашего основного кода, а не подмешивают их в `src/test`. Так annotation processor и shade-плагин не конфликтуют с обычной сборкой, а fat-jar получается изолированным и воспроизводимым.

## Q3. Как написать и запустить простейший бенчмарк?

Метод помечается `@Benchmark`, кладётся в публичный класс. Запустить можно двумя способами — через fat-jar или программно через `Runner`.

```java
public class StringBenchmark {

    @Benchmark
    public String concat() {
        return "a" + "b" + System.currentTimeMillis();
    }

    public static void main(String[] args) throws Exception {
        Options opt = new OptionsBuilder()
                .include(StringBenchmark.class.getSimpleName())
                .warmupIterations(5)
                .measurementIterations(5)
                .forks(1)
                .build();
        new Runner(opt).run();
    }
}
```

- **Через jar:** `java -jar target/benchmarks.jar StringBenchmark` (плюс флаги `-wi 5 -i 5 -f 1 -bm avgt`).
- **Программно:** `Runner` + `OptionsBuilder` — удобно для запуска из IDE и для CI.

`include(...)` принимает регулярное выражение по именам бенчмарков, так что можно гонять подмножество.

## Q4. (!) Что делает `@State` и зачем нужны Scope `Thread`/`Benchmark`/`Group`?

`@State` объявляет класс-носитель данных, которые нужны бенчмарку, но **не должны попадать в измеряемый код** (инициализация коллекций, входные числа, мок-объекты). JMH создаёт экземпляр state-класса и передаёт его в метод `@Benchmark` как параметр. State-класс должен быть `public` и иметь публичный no-arg конструктор (если это вложенный класс — он должен быть `static`).

`Scope` управляет тем, как экземпляр state шарится между потоками при многопоточном прогоне (`-t N`):

| Scope | Сколько экземпляров | Когда использовать |
|---|---|---|
| `Scope.Thread` | по одному на каждый поток | у каждого потока своё изолированное состояние; нет гонок и contention на самих данных |
| `Scope.Benchmark` | один на весь бенчмарк, общий для всех потоков | замер shared-структур (конкурентные коллекции, общий счётчик) — contention входит в замер |
| `Scope.Group` | один на каждую группу потоков (`@Group`) | асимметричные сценарии producer/consumer внутри одной группы |

```java
@State(Scope.Benchmark)
public static class SharedState {
    final Map<Integer, Integer> map = new ConcurrentHashMap<>();
}

@Benchmark
public void put(SharedState s) {
    s.map.put(ThreadLocalRandom.current().nextInt(), 1);
}
```

**Подвох:** выбор Scope меняет смысл замера. `Scope.Benchmark` для `HashMap` под нагрузкой нескольких потоков измерит ещё и contention/false sharing, а `Scope.Thread` — только однопоточную стоимость операции.

## Q5. Чем отличаются `@Setup`/`@TearDown` с разными `Level` (Trial/Iteration/Invocation)?

Это fixture-методы внутри `@State`-класса: `@Setup` готовит состояние перед замерами, `@TearDown` — прибирает после. `Level` определяет частоту вызова:

| Level | Когда вызывается | Назначение |
|---|---|---|
| `Level.Trial` (по умолчанию) | один раз на весь форк (до всего прогрева и измерений) | дорогая разовая подготовка: построить большой массив, прогреть кэш |
| `Level.Iteration` | перед/после каждой итерации | сбросить состояние между итерациями |
| `Level.Invocation` | перед/после **каждого** вызова `@Benchmark` | редкий случай: подготовить per-call вход |

```java
@State(Scope.Thread)
public static class Data {
    int[] arr;

    @Setup(Level.Trial)
    public void setUp() {
        arr = ThreadLocalRandom.current().ints(10_000).toArray();
    }
}
```

**Серьёзный подвох с `Level.Invocation`:** документация JMH прямо предупреждает, что он опасен. Сам вызов setup попадает в тайминг-окно итерации, и если работа в `@Setup` сопоставима по длительности с замеряемым методом (а для микробенчмарков это типично — наносекунды), вы измеряете в основном setup, а не сам метод. Использовать только когда вызов реально дорогой (миллисекунды) и состояние нельзя переиспользовать.

## Q6. Зачем нужен `@Param` и как он работает?

`@Param` параметризует бенчмарк: JMH прогонит его отдельно для каждого значения и выдаст отдельную строку результата. Это позволяет одним кодом снять зависимость производительности от размера входа или варианта реализации.

```java
@State(Scope.Benchmark)
public static class P {
    @Param({"10", "1000", "100000"})
    public int size;

    List<Integer> list;

    @Setup(Level.Trial)
    public void init() {
        list = IntStream.range(0, size).boxed().collect(Collectors.toList());
    }
}

@Benchmark
public int sum(P p) {
    return p.list.stream().mapToInt(Integer::intValue).sum();
}
```

- Поле под `@Param` должно быть `public` и неконстантным; JMH присваивает значения через рефлексию.
- Можно несколько `@Param` сразу — JMH сделает декартово произведение всех комбинаций.
- Значения — строки, JMH сам парсит их в тип поля (`int`, `enum`, `boolean` и т.д.).

**Польза на собеседовании:** показать, что вы снимаете не одну точку, а кривую — например, что преимущество стримов над циклом проявляется только на больших объёмах.

## Q7. (!) Какие есть `@BenchmarkMode` и чем они отличаются?

`@BenchmarkMode` задаёт, что именно измеряется. Поддерживается несколько режимов (можно указать массив или `Mode.All`):

| Режим | Что меряет | Единица (типично) | Когда брать |
|---|---|---|---|
| `Throughput` (по умолчанию) | сколько операций в единицу времени | ops/s | пропускная способность; «больше — лучше» |
| `AverageTime` | среднее время одного вызова | ns/op, us/op | стоимость операции; «меньше — лучше» |
| `SampleTime` | сэмплирует время вызовов, строит распределение | даёт перцентили (p50/p99/p999) | когда важны хвосты латентности, а не среднее |
| `SingleShotTime` | время одного-единственного вызова | время/op | cold-start, разовые операции (классовая инициализация), без непрерывного прогона |
| `All` | все режимы по очереди | — | разведка |

```java
@BenchmarkMode({Mode.Throughput, Mode.AverageTime})
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Benchmark
public long work() { ... }
```

**Подвохи:**

- `Throughput` и `AverageTime` — это, по сути, обратные величины, но считаются по-разному; для разных целей читаются удобнее в своих единицах.
- `SampleTime` ценен тем, что показывает p99/p999 — для latency-критичных систем среднее почти бесполезно.
- `SingleShotTime` сознательно **не прогревает** код многократно — он именно про холодный запуск; путать его с обычными режимами нельзя.

## Q8. Что делает `@OutputTimeUnit` и почему важно его указывать?

`@OutputTimeUnit` задаёт единицу времени, в которой JMH печатает результат (`TimeUnit.NANOSECONDS`, `MICROSECONDS`, `MILLISECONDS`, `SECONDS`). На сам замер это не влияет — только на читаемость вывода.

```java
@OutputTimeUnit(TimeUnit.NANOSECONDS)  // ns/op для AverageTime
```

Зачем указывать явно: дефолт (секунды) для микробенчмарков даёт нечитаемые числа вроде `0.0000000234 s/op`. Для операций уровня наносекунд берут `NANOSECONDS`, для I/O или крупных операций — `MICRO/MILLISECONDS`. Согласованная единица также упрощает сравнение строк в одном отчёте.

**Вывод:** косметическая, но важная аннотация — без неё легко промахнуться на три порядка при чтении результата.

## Q9. (!) Зачем нужен warmup и чем `@Warmup` отличается от `@Measurement`?

Warmup (прогрев) — это итерации, которые JMH прогоняет **до** замера и результаты которых выбрасывает. Их цель — довести код до steady-state: дать C2 скомпилировать горячие методы, прогреть кэши процессора, стабилизировать профиль ветвлений и привести GC в установившийся режим. Без прогрева вы измерите интерпретатор и переходные эффекты компиляции.

- `@Warmup(iterations = N, time = T)` — сколько прогревочных итераций и какой длительности (по умолчанию обычно 5 итераций по 10 с в архетипе, исторический дефолт ядра — больше).
- `@Measurement(iterations = N, time = T)` — собственно замеряемые итерации, чьи цифры идут в отчёт.

```java
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 5, time = 1)
@Benchmark
public int hot() { ... }
```

**Подвохи:**

- Слишком мало warmup-итераций — рискуете замерить ещё не дошедший до C2 код (бимодальное распределение, гигантский разброс).
- У обеих аннотаций общий набор опций: `iterations`, `time`, `timeUnit`, `batchSize`.
- Если видите, что измерения «гуляют» — обычно мало прогрева либо мешает другой бенчмарк (см. `@Fork`).

## Q10. (!) Что делает `@Fork` и почему форков должно быть хотя бы один?

`@Fork` задаёт, сколько раз бенчмарк запускается в **отдельном свежем процессе JVM**. Это критично: JMH по умолчанию форкает, потому что без изоляции один бенчмарк «отравляет» профиль JIT для следующего.

Что чинит форк:

- **Изоляцию profile pollution.** Если в одной JVM прогнать бенчмарки `A` и `B`, C2 мог заинлайнить/спрофилировать вызовы под `A`, и `B` унаследует чужие оптимизации (или деоптимизации). Свежая JVM на каждый бенчмарк сбрасывает профиль.
- **Воспроизводимость.** Несколько форков (`@Fork(3)`) показывают межпроцессную дисперсию — иногда разные запуски JVM выходят на разные стабильные состояния.

```java
@Fork(value = 2, jvmArgs = {"-Xms2g", "-Xmx2g"})
@Benchmark
public void m() { ... }
```

- `@Fork(0)` отключает форк — гонять **в той же JVM**. Это допустимо только для отладки самого бенчмарка (например, чтобы поставить брейкпойнт), результаты в этом режиме доверять нельзя.
- Через `jvmArgs`/`jvmArgsAppend` можно зафиксировать heap, GC, флаги — чтобы замер был стабилен.

**Итог:** `@Fork ≥ 1` — это не перестраховка, а условие корректности. `@Fork(0)` = «я отлаживаю, цифрам не верю».

## Q11. (!) Что такое dead-code elimination и как от него защищает `Blackhole`?

Dead-code elimination — оптимизация компилятора: если результат вычисления нигде не наблюдается (не используется), C2 имеет право выкинуть всё вычисление целиком. В микробенчмарке это катастрофа — вы измерите пустоту.

Два штатных способа «потребить» результат, чтобы JIT считал его наблюдаемым:

1. **Вернуть значение из метода** — JMH-обвязка сама прогонит возвращённое значение через `Blackhole` и не даст его соптимизировать (см. Q13).
2. **Явный `Blackhole.consume(...)`** — когда внутри метода вычисляется несколько значений и вернуть можно только одно.

```java
@Benchmark
public void multiple(Blackhole bh) {
    bh.consume(compute1());
    bh.consume(compute2());   // оба «потреблены», ни одно не выкинут
}
```

`Blackhole` спроектирован так, чтобы компилятор не мог доказать, что потребление бесполезно (нетривиальная логика внутри `consume`). В современных JDK есть ещё и компиляторные blackholes на уровне C1/C2 (`-XX:+UnlockExperimentalVMOptions -XX:+UseCompilerBlackhole`), которые JMH задействует, делая потребление практически бесплатным и более надёжным.

**Антипаттерн:** молча присваивать результат локальной переменной и думать, что этого хватит — не хватит, переменная тоже мёртвая.

## Q12. Что такое constant folding и почему входные данные передают через `@State`, а не литералами?

Constant folding — JIT вычисляет выражение над константами **на этапе компиляции** и заменяет его готовым результатом. Если на вход бенчмарка идут литералы или `final`-константы, компилятор посчитает ответ один раз и подставит его — вы измерите скорость возврата константы, а не работу алгоритма.

Плохо (результат свернётся):

```java
@Benchmark
public double bad() {
    return Math.sqrt(42.0);   // 42.0 — литерал -> const fold
}
```

Хорошо (вход из `@State`, нефинальное поле):

```java
@State(Scope.Thread)
public static class In {
    public double x = 42.0;   // не final, JIT не докажет константность
}

@Benchmark
public double good(In in) {
    return Math.sqrt(in.x);
}
```

Ключевые правила: входы хранить в `@State`-объекте как **нефинальные** поля; не хардкодить литералы в тело метода. Тогда JIT не может доказать, что значение константно, и честно компилирует вычисление.

**Связь с Q11:** dead-code elimination убирает «выход» бенчмарка (результат не используется), а constant folding убирает «вход» (значение известно заранее). Защищаться надо от обоих: `Blackhole`/return — от первого, `@State` без `final` — от второго.

## Q13. Нужно ли возвращать значение из метода `@Benchmark`?

Да, это самый простой и идиоматичный способ защититься от dead-code elimination. Если метод возвращает результат вычисления, генерируемая JMH обвязка сама прогоняет это значение через `Blackhole`, и компилятор не вправе выкинуть вычисление.

```java
@Benchmark
public long compute(State s) {
    return s.a * 31 + s.b;   // возвращаем -> JMH потребит за нас
}
```

- Если значение **одно** — просто `return`, ничего больше не нужно.
- Если значений **несколько** — вернуть можно лишь одно, остальные пропустить через `Blackhole.consume(...)` (см. Q11).
- Метод `void` без `Blackhole` и без побочных эффектов — почти всегда баг: измеряете пустоту.

**Вывод:** «есть результат — верни его». Это нулевая стоимость в коде и максимальная защита от самой частой ошибки микробенчмаркинга.

## Q14. Зачем нужен `@CompilerControl`?

`@CompilerControl` управляет тем, как JIT обращается с конкретным методом: запретить/принудить инлайнинг или вообще исключить из компиляции. Нужен в тонких сценариях, когда инлайнинг искажает то, что вы хотите измерить.

```java
@CompilerControl(CompilerControl.Mode.DONT_INLINE)
private int hotPath() { ... }
```

Режимы:

- `DONT_INLINE` — запретить инлайн (например, чтобы метод был виден в профиле как отдельный фрейм, или чтобы воспроизвести реальную ситуацию вызова через границу).
- `INLINE` — наоборот, форсировать.
- `EXCLUDE` — вовсе не компилировать (оставить в интерпретаторе) — для крайних диагностических случаев.

**Подвох:** это инструмент тонкой настройки. В большинстве бенчмарков его трогать не надо — по умолчанию JMH измеряет код так, как его реально оптимизирует JVM, и это правильно. `@CompilerControl` достают, когда инлайнинг конкретно мешает разделить вклад частей или исследовать поведение JIT.

## Q15. Как читать вывод JMH: что такое `score`, `± error` и единицы?

JMH печатает таблицу, где для каждого бенчмарка (и каждой комбинации `@Param`) есть:

- **`Score`** — точечная оценка метрики. Для `Throughput` — операций в единицу времени (больше лучше), для `AverageTime` — время на операцию (меньше лучше).
- **`Error` (после `±`)** — половина доверительного интервала (по умолчанию 99.9% confidence). Это разброс между итерациями/форками, а не «ошибка измерения прибора».
- **`Units`** — единицы из `@OutputTimeUnit`/режима (`ops/s`, `ns/op` и т.д.).

```
Benchmark            Mode  Cnt    Score    Error  Units
StringBench.concat   avgt    5   42.318 ±  1.204  ns/op
```

Как интерпретировать:

- Сравнивая два бенчмарка, смотрите, **перекрываются ли интервалы** `score ± error`. Если перекрываются — разница статистически незначима, нельзя говорить «A быстрее B».
- Большой `error` относительно `score` (например, ±50%) — сигнал, что замер нестабилен: мало прогрева, мешает GC, бимодальное поведение JIT. Цифрам верить рано.
- Для `SampleTime` в выводе будут ещё перцентили (`p0.50`, `p0.99`, `p0.999`) — для latency читать именно их.

**Итог:** одно число без интервала бессмысленно. Всегда читать `score` вместе с `± error` и проверять перекрытие, прежде чем делать выводы.

## Q16. Какие профилировщики встроены в JMH (`-prof`) и зачем нужен async-profiler?

JMH умеет навешивать профилировщики прямо на прогон через флаг `-prof`. Они дают понять не только «сколько», но и «почему столько».

Встроенные (примеры):

- `-prof gc` — статистика аллокаций и GC: `gc.alloc.rate`, `B/op` (байт на операцию). Бесценно, чтобы поймать скрытые аллокации (autoboxing, лишние объекты).
- `-prof stack` — простой sampling стэка по safepoint'ам (грубый, со safepoint bias).
- `-prof perfasm` (Linux) — показывает горячий ассемблер с аннотациями, видно сам сгенерированный JIT-код.
- `-prof comp` / `-prof cl` — статистика JIT-компиляции и загрузки классов.

**async-profiler** подключается как внешний профилировщик: `-prof async:libPath=/path/libasyncProfiler.so;output=flamegraph;event=cpu`. Он сэмплирует через `AsyncGetCallTrace`, обходит проблему safepoint bias обычных sampling-профайлеров, имеет низкий overhead и умеет cpu/alloc/lock-профилирование с выводом во flame-graph или JFR.

```bash
java -jar benchmarks.jar MyBench -prof gc \
  -prof async:libPath=/opt/async-profiler/libasyncProfiler.so';'output=flamegraph
```

**Польза на собеседовании:** показать, что вы не просто получаете число, а через `-prof gc` объясняете аллокации, а через async-profiler — где именно горит CPU.

## Q17. Какие типичные ошибки микробенчмаркинга вы знаете?

Это любимый «контрольный» вопрос — он показывает, понимает ли кандидат, что мешает честному замеру.

- **Замер без прогрева** — ловите интерпретатор/C1 вместо C2 (см. Q9).
- **Dead-code elimination** — не потребили результат, измерили пустоту (Q11, Q13).
- **Constant folding** — подали литералы вместо `@State`, измерили возврат константы (Q12).
- **`@Fork(0)` / общая JVM** — profile pollution между бенчмарками (Q10).
- **`Level.Invocation` для наносекундных методов** — setup доминирует над замером (Q5).
- **Игнор `± error`** — делают вывод «A быстрее B», когда интервалы перекрываются (Q15).
- **Запуск под нагрузкой/на ноутбуке** — turbo boost, thermal throttling, фоновые процессы, виртуализация дают огромный разброс; нужна тихая, зафиксированная по частоте машина.
- **Микробенчмарк вместо реального профиля** — оптимизируют то, что в проде вообще не горячее. JMH отвечает на вопрос «что из двух быстрее», а не «что тормозит в моём приложении».

**Вывод:** список ошибок симметричен фичам JMH — каждая аннотация (`@Warmup`, `@Fork`, `@State`, `Blackhole`) закрывает конкретную ловушку. Хороший ответ связывает ошибку с механизмом защиты.

## Q18. Чем JMH отличается от JMC/JFR и когда что использовать?

Это разные инструменты для разных вопросов, и их часто путают.

| | JMH | JFR + JMC |
|---|---|---|
| Вопрос | «что из двух вариантов быстрее, на сколько» | «что тормозит в моём реальном приложении» |
| Уровень | микро: отдельный метод/фрагмент | макро: вся работающая JVM/сервис |
| Подход | синтетический бенчмарк, изоляция, прогрев | low-overhead запись событий рантайма в проде |
| Что даёт | `score ± error`, сравнение вариантов | timeline аллокаций, GC, lock contention, hot methods, I/O |
| Где гоняют | отдельный модуль/CI, тихая машина | прямо на проде/стейдже, постоянно или по триггеру |

- **JFR (Java Flight Recorder)** — встроенный в JVM механизм записи событий с минимальными накладными; **JMC (JDK Mission Control)** — GUI для анализа этих записей.
- **JMH** не заменяет профилировщик: он не скажет, какой метод в вашем сервисе горячий. Он отвечает на узкий вопрос сравнения реализаций.

**Правильный порядок на практике:** сначала JFR/JMC (или async-profiler) на реальном приложении находит горячую точку → затем JMH микробенчмарком сравнивает варианты её оптимизации → решение валидируется снова на реальной нагрузке. Начинать с JMH, не зная, что тормозит, — это преждевременная оптимизация.
