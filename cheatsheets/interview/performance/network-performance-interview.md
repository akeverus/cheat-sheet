## Q1. (!) Latency vs Bandwidth — разница?

Это две **независимые** характеристики канала. **Latency (задержка)** — сколько времени пакет летит из точки A в точку B; **bandwidth (пропускная способность)** — сколько данных канал прокачивает в секунду. Толстый канал не уменьшает задержку, а низкий ping не увеличивает объём данных в секунду.

- **Latency** измеряется в ms. На практике обычно считают **RTT (round-trip time)** — время туда-обратно, оно равно удвоенной задержке в одну сторону.
- **Bandwidth** измеряется в bps / Gbps.

**Аналогия — грузовик из Лос-Анджелеса в Нью-Йорк.** Bandwidth — это вместимость кузова (сколько груза увезёшь за рейс); latency — время доехать через всю страну. Можно поставить огромный грузовик (высокий bandwidth), но ехать он всё равно будет столько же.

**Почему это разные оси:**
- **Bandwidth** улучшается технологиями: апгрейд оптики / NIC, больше параллельных линков. Поэтому он и растёт год от года (10 Gbps → 100 Gbps).
- **Latency** упирается в физику: скорость света в оптике ~20 км/мс — её не обойти. Единственное реальное лекарство — географическая близость, то есть размещать edge (CDN) ближе к пользователю. Поэтому задержка по сути уперлась в **физический предел**.

**Что доминирует в вашем приложении:**
- Болтливые протоколы (много мелких запросов друг за другом) упираются в latency: каждый запрос платит свой RTT.
- Массовая передача больших данных упирается в bandwidth.
- Загрузка веб-страницы — это куча мелких запросов, поэтому почти всегда доминирует latency, а не ширина канала.

**Пример LA ↔ NY.** Скорость света даёт ~20 ms в одну сторону, то есть RTT ≥ 40 ms; на практике с маршрутизацией и очередями выходит ~70 ms. Если сделать 100 запросов последовательно — это 7 секунд только на сеть. Если те же запросы распараллелить (мультиплексирование HTTP/2), всё укладывается в 1 RTT + время передачи. Отсюда вывод: с latency борются не «толщиной трубы», а уменьшением числа последовательных round-trip-ов.

## Q2. (!) Типичные RTT-значения?

Эти числа полезно держать в голове: они задают «бюджет» задержки и сразу подсказывают, реалистична ли заявленная latency. Порядок величины меняется на каждом уровне — от микросекунд внутри машины до сотен миллисекунд через океан.

| Уровень | RTT |
|---------|-----|
| Localhost | 0.05–0.2 ms |
| Внутри дата-центра (intra-DC) | 0.5–2 ms |
| Внутри региона (intra-region) | 2–10 ms |
| US east ↔ west (один континент) | ~70 ms |
| Europe west ↔ east | ~30 ms |
| US ↔ Europe (межконтинентально) | ~80–100 ms |
| US ↔ Asia | ~120–180 ms |
| Подводный кабель ↔ peer | ~150–250 ms |
| Спутник (геостационарный) | 500+ ms |
| Starlink (LEO) | ~50 ms |

Первый хоп беспроводных сетей добавляет своё: **Mobile 4G** — 20–50 ms, **5G** — 5–15 ms, **Wi-Fi** до роутера — 2–10 ms. Это плата ещё до выхода в магистраль.

**Почему это критично — RTT умножается на число round-trip-ов.** Пять последовательных запросов = 5× RTT:
- Локально: 0.5 ms × 5 ≈ 2.5 ms — незаметно.
- Между регионами: 70 ms × 5 = 350 ms — уже ощутимо.
- Межконтинентально: 180 ms × 5 = 900 ms — почти секунда на ровном месте.

**Что из этого следует для дизайна:**
- Батчить запросы — меньше отдельных round-trip-ов.
- Распараллеливать независимые вызовы, чтобы их RTT накладывались, а не складывались.
- Деплоить multi-region, если сервис user-facing: приблизить сервер к пользователю — единственный способ сократить RTT.

**Чем мерить:**
- `ping <host>` — ICMP RTT.
- `traceroute <host>` — задержка по хопам (видно, где растёт).
- `mtr <host>` — непрерывный замер (ловит джиттер и потери во времени).

## Q3. (!) Что такое bandwidth-delay product?

**BDP = bandwidth × round-trip time** — это объём данных, который может «лететь» по каналу одновременно, то есть сколько влезает в «трубу» между отправкой и приходом подтверждения. Цифра нужна, чтобы понять, какого размера окно/буфер требуется TCP, иначе канал не наполнится.

**Пример.** Линк 1 Gbps, RTT 50 ms: BDP = 1e9 bit/s × 0.05 s = 5e7 бит = 6.25 MB. Значит, в любой момент в канале может находиться до 6.25 MB неподтверждённых данных.

**Почему это упирается в receive window.** TCP не отправит больше, чем влезает в окно получателя (rwnd), пока не дождётся ACK. Если **rwnd < BDP**, отправитель упирается в потолок и простаивает в ожидании подтверждений — реальный throughput оказывается ниже доступной пропускной способности. Канал толстый, а вы его не наполняете.

**Откуда брался лимит.** Поле окна в TCP — 16-битное, то есть максимум 64KB. Этого хватало в 1980-х, но не на современных каналах. Расширение **window scaling (RFC 1323)** снимает потолок — окно масштабируется вплоть до гигабайт.

**TCP-буферы по умолчанию** в Linux обычно 4MB с авто-масштабированием. Для **long fat networks** (большой BDP) этого мало — буферы тюнят:
```
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216
```

**Long Fat Networks (LFN)** — это каналы с высоким bandwidth И высокой latency одновременно (спутник, скоростные межконтинентальные линки). У них BDP огромный, поэтому нужны крупные буферы; без тюнинга throughput ограничен размером буфера, а не реальной пропускной способностью канала.

**Чем проверить:**
- `ss -ti` — показывает текущее congestion window (cwnd) и размеры send/recv-буферов.
- `iperf3 -c server -w <window>` — прогон с конкретным окном, видно эффект от его размера.

**Эмпирическое правило:** для 10 Gbps межконтинентально receive buffer должен быть ≥ 10MB.

## Q4. (!) TCP slow start и congestion control?

**TCP стартует медленно и наращивает скорость постепенно**, а не шлёт сразу на полной пропускной способности. Причина — отправитель не знает реальную ёмкость канала и не хочет его моментально перегрузить. Поэтому он «прощупывает» сеть, увеличивая congestion window (cwnd) до первой потери пакета.

**Slow start (фаза разгона):**
- Начальный cwnd = 10 MSS (~14KB) по умолчанию в Linux.
- На каждый ACK cwnd += 1 MSS — фактически окно удваивается каждый RTT, рост экспоненциальный.
- Продолжается до первой потери пакета или достижения порога ssthresh.

**Congestion avoidance (осторожная фаза):**
- После ssthresh рост становится линейным: cwnd += 1 MSS за RTT.
- При потере пакета cwnd делится пополам (multiplicative decrease) — резко отступить, чтобы разгрузить сеть.

**Главное следствие — короткоживущее соединение никогда не доходит до полной скорости.** Пример: линк 1 Gbps, RTT 50 ms:
- После 1 RTT cwnd = 20 MSS = 28KB → реально всего 4.5 Mbps.
- После 5 RTT cwnd = 320 MSS = 450KB → всё ещё лишь 70 Mbps.
- Чтобы насытить гигабит, нужны секунды разгона.

**Алгоритмы congestion control:**
- **Reno / CUBIC** (дефолт Linux с 2.6+): loss-based, ориентируются на потери; cwnd растёт по кубической функции.
- **BBR** (Google 2016): model-based — оценивает bandwidth × RTT, а не ждёт потерь.
- **Westwood, Veno, HSTCP** — альтернативы под специфичные сети.

**Что это значит для приложений:**
- **Переиспользуйте соединения** (HTTP keep-alive): на уже «разогретом» соединении cwnd остаётся высоким, и следующий запрос летит на полной скорости.
- Каждое новое соединение начинает slow start с нуля.
- Cross-region + короткий запрос = большой «налог» на разгон: соединение закрывается раньше, чем успевает раскачаться.

**Поднять стартовый cwnd** (быстрее отдать первый экран):
```
ip route change default via <gw> initcwnd 30
```
В Linux 3.10+ дефолт 10; иногда поднимают до 20–40 ради ускорения загрузки страницы.

## Q5. (!) Какова цена TCP handshake?

Прежде чем отправить хоть байт данных, TCP тратит **1 RTT** на трёхстороннее рукопожатие. Это «мёртвое время» — соединение ещё устанавливается, полезного трафика нет.

**3-way handshake:**
```
Client → SYN → Server     (0.5 RTT)
Client ← SYN-ACK ← Server (1 RTT)
Client → ACK → Server     (1.5 RTT; но data piggyback возможно)
```

**Во что обходится этот 1 RTT:**
- Локально: 1–2 ms — пренебрежимо.
- Cross-region: 70 ms чистого простоя на каждое соединение.
- Mobile: плюс латентность сотовой сети сверху.

**Боль начинается без keep-alive:** каждый запрос открывает новое соединение, значит новый handshake. Загрузка 50 картинок на странице = 50 рукопожатий, то есть 50× RTT впустую.

**Как сократить:**

1. **Keep-alive (Q12)** — переиспользовать соединение, тогда handshake платится один раз на много запросов. Это первое и главное средство.
2. **TCP Fast Open (TFO)** — второе и последующие соединения экономят 1 RTT, отправляя данные прямо в SYN (RFC 7413). Нужна поддержка клиента и сервера плюс cookie; распространён слабо, потому что middleboxes часто его ломают.
3. **QUIC (HTTP/3)** — 0-RTT при переподключении (см. Q14).
4. **Connection pooling** — на стороне сервера переиспользуем исходящие соединения к зависимостям, чтобы не платить handshake на каждый внутренний вызов.

**TLS усугубляет.** Поверх TCP-рукопожатия идёт TLS-рукопожатие (1–2 RTT), итого 2–3 RTT до первого байта данных. Cross-region это 200–300 ms чистого простоя — для мелких запросов это уже доминирует над самим запросом.

**SO_REUSEPORT** — распределяет входящие соединения между несколькими процессами/потоками, повышая throughput на стадии accept.

## Q6. Nagle algorithm и delayed ACK?

Это две оптимизации TCP, которые по отдельности полезны, но вместе дают неприятную паузу в ~200 ms. Понимать их связку важно, потому что это классическая причина «загадочных» задержек в RPC и интерактивных протоколах.

**Алгоритм Нейгла (Nagle, 1984)** копит мелкие записи и не отправляет их, пока не придёт ACK на предыдущие данные или не наберётся полный сегмент. Цель — не плодить крошечные пакеты у болтливых приложений (меньше overhead на заголовки). Включён по умолчанию (TCP_NODELAY=0).

**Delayed ACK (дефолт в Linux)** работает с другой стороны: получатель не подтверждает сразу, а ждёт ~200 ms — вдруг придут ещё данные или свой ответ, и тогда ACK можно отправить вместе с ними. Цель — уменьшить «спам» из чистых ACK.

**Nagle + delayed ACK = почти deadlock.** Каждый ждёт другого:
- Отправитель сделал мелкую запись → Nagle держит её, ожидая ACK на прошлые данные.
- Получатель → delayed ACK, ждёт ещё данных, чтобы подтвердить пакетом побольше.
- Никто не двигается → пауза ~200 ms буквально на ровном месте.

**Фикс — отключить Nagle** для latency-чувствительных протоколов:

```c
int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(int));
```

В Java:
```java
socket.setTcpNoDelay(true);
```

**Когда отключать, а когда оставить:**
- Отключить Nagle (TCP_NODELAY=true) — интерактивные нагрузки (SSH, игры, RPC) и любые мелкие latency-чувствительные записи: важнее мгновенная отправка, чем экономия пакетов.
- Оставить Nagle (дефолт) — массовая передача (загрузка файла): здесь склейка мелких записей экономит bandwidth и не вредит.

Поэтому большинство RPC-фреймворков (gRPC, Netty по умолчанию) Nagle отключают. HTTP-клиенты тоже обычно отключают его ради низкой латентности — для bulk download разница уже непринципиальна.

## Q7. Чем BBR отличается от CUBIC (congestion control)?

Это два разных подхода к одному вопросу — «с какой скоростью можно слать, не перегружая сеть». CUBIC ждёт потерь как сигнала, BBR строит модель канала и не доводит до потерь. Отсюда вся разница в поведении.

**CUBIC** (дефолт Linux с 2.6.19) — **loss-based**: разгоняется по кубической функции (агрессивно, затем плато) и замедляется только когда теряет пакет. Он честный и десятилетиями обкатан, но у него есть слабость: на bufferbloated-линках он заполняет сетевые буферы под завязку, прежде чем увидит потерю, — а полные буферы это высокая queueing latency.

**BBR** (Bottleneck Bandwidth and RTT, Google 2016) — **model-based**: вместо ожидания потерь он оценивает реальную пропускную способность узкого места и минимальный RTT, и шлёт со скоростью bandwidth × (1 − buffer_fill). За счёт этого он **не забивает буферы** (избегает bufferbloat) и даёт **лучший throughput на lossy-линках** (сотовая связь, WiFi), где случайная потеря не означает реальной перегрузки — а CUBIC бы на неё зря затормозил.

**Включить BBR:**
```bash
sudo sysctl net.core.default_qdisc=fq
sudo sysctl net.ipv4.tcp_congestion_control=bbr
```

**Плюсы BBR:**
- Внедрён в масштабе — YouTube и сервисы Google работают на нём.
- Google сообщал о росте throughput **до 2700%** на некоторых путях (сотовая связь).
- Ниже queueing latency — лучше для видео и игр.

**Минусы:**
- BBRv1 агрессивен и может «зажимать» CUBIC-потоки — в смешанном трафике он нечестен.
- BBRv2 (2019+) исправляет честность.
- Требует аккуратного внедрения, а не «включил везде».

**Когда применять:** высокий bandwidth на lossy или bufferbloated сетях — сотовая связь, спутник, cross-region с джиттером.

**Когда не стоит:** low-bandwidth, low-loss локалка (CUBIC там и так хорош), или там, где критична честность к соседним CUBIC-отправителям — это нужно планировать заранее.

**Проверить:**
```bash
sysctl net.ipv4.tcp_congestion_control
ss -ti  # shows per-connection congestion info
```

## Q8. (!) Какова цена TLS handshake?

TLS добавляет свои round-trip-ы поверх TCP-рукопожатия — и именно версия TLS определяет, сколько именно. Версия — главный рычаг: переход на TLS 1.3 убирает целый RTT из каждого нового соединения.

- **TLS 1.2** — handshake занимает 2 RTT, итого с TCP получается **3 RTT** до данных.
- **TLS 1.3** (2018) — handshake за 1 RTT, итого **2 RTT**. Плюс обязательная forward secrecy и более безопасные cipher suites по умолчанию.

**Разбивка по стоимости** наглядно показывает выигрыш:
- TCP: 1 RTT.
- TLS 1.2: +2 RTT → 3 RTT суммарно.
- TLS 1.3: +1 RTT → 2 RTT суммарно.

На cross-region при RTT 100 ms это разница между **300 ms** (TLS 1.2) и **200 ms** (TLS 1.3) мёртвого времени до первого байта.

**Что с CPU.** Дорогая часть — асимметричная криптография (RSA/ECDSA), но она платится один раз за handshake. Симметричное шифрование самого трафика после рукопожатия на современных CPU с AES-NI почти бесплатно (несколько % оверхеда). ECDSA дешевле RSA по CPU. А session tickets / IDs позволяют при следующем соединении вообще пропустить асимметрику.

**0-RTT (TLS 1.3)** — крайний случай: на возобновлённом соединении данные летят прямо в первом пакете, то есть 0 RTT до данных. Расплата — **риск replay-атаки**: пакет могут перехватить и переотправить, поэтому 0-RTT допустим только для идемпотентных GET-ов.

**Чем тюнить latency рукопожатия:**
- **Session resumption** (tickets/IDs) — переиспользовать предыдущую сессию без повторной асимметрики.
- **OCSP stapling** — сервер сам прикладывает OCSP-ответ к рукопожатию, чтобы клиент не ходил за ним отдельным запросом.
- **Короткая цепочка сертификатов** — меньше байт = меньше TCP-сегментов на handshake = быстрее.

**Измерить:**
```bash
curl -o /dev/null -s -w "%{time_connect} %{time_appconnect} %{time_starttransfer}\n" https://site.com
# time_connect — TCP handshake; time_appconnect — TLS handshake; time_starttransfer — first byte
```

## Q9. Как работают TLS session resumption и 0-RTT?

Resumption — это способ при повторном подключении пропустить дорогую часть TLS-рукопожатия (асимметричную криптографию), переиспользовав состояние прошлой сессии. Ключевой выбор между механизмами — где хранится это состояние: на сервере или у клиента.

**Механизмы TLS 1.2:**
- **Session ID** — состояние хранит сервер, клиент при переподключении присылает только ID, сервер находит сессию и возобновляет её. Проблема в масштабировании: состояние живёт на конкретном сервере, поэтому нужен sticky LB.
- **Session Tickets (RFC 5077)** — сервер шифрует состояние сессии своим ключом и отдаёт клиенту «тикет»; клиент возвращает тикет при переподключении, сервер расшифровывает и возобновляет. Это **stateless** — сервер ничего не хранит, поэтому работает за любым LB.

**TLS 1.3 PSK (Pre-Shared Key)** заменяет оба механизма: возобновление идёт через «resumption key», выведенный из прошлой сессии.

**0-RTT** — следующий шаг: клиент кладёт данные прямо в первый пакет вместе с тикетом, и сервер принимает их сразу, если тикет валиден. Это **экономит целый RTT**.

**Чем опасен 0-RTT.** Главный риск — **replay-атака**: атакующий записывает первый пакет и переотправляет его, и действие выполняется повторно. Поэтому 0-RTT допустим только для идемпотентных запросов (GET) и никогда для `POST /payment`. На практике большинство браузеров сами ограничивают 0-RTT только GET-ами.

**Поддержка:** Chrome и Safari поддерживают 0-RTT; на серверах включается через `ssl_early_data on` (Nginx/Envoy/Apache).

**Как проверить, что resumption работает:**
- DevTools Network: «Resumed TLS connection: yes».
- Лог Nginx: переменная `$ssl_session_reused`.

**Практический эффект:** на cross-region API-вызовах resumption экономит 50–100 ms на запрос — этого достаточно, чтобы держать latency статики под 100 ms по всему миру.

## Q10. (!) Чем различаются HTTP/1.1, HTTP/2 и HTTP/3?

Каждая версия решала главное узкое место предыдущей: HTTP/2 убрал ограничение «один запрос за раз», а HTTP/3 ушёл с TCP на QUIC, чтобы убрать оставшийся head-of-line blocking на транспорте.

**HTTP/1.1 (1997):**
- Текстовый протокол.
- **1 запрос за раз на соединение** — pipelining на практике почти не поддержан.
- Keep-alive по умолчанию.
- Чтобы хоть как-то распараллелить, браузеры открывают **6 параллельных соединений** на origin.

**HTTP/2 (2015):**
- **Бинарный** фрейминг вместо текста.
- **Мультиплексирование** — много запросов в одном соединении одновременно, конец «6 соединениям-костылю».
- **Сжатие заголовков** (HPACK) — заголовки повторяются от запроса к запросу, сжатие экономит трафик.
- Server Push (по большей части deprecated).
- Транспорт тот же: TCP + TLS.

**HTTP/3 (2022):**
- Транспорт **QUIC** — поверх UDP, а не TCP.
- TLS 1.3 встроен в транспорт.
- **Нет head-of-line blocking** на транспорте: стримы по-настоящему независимы.
- **Возобновление соединения за 0-RTT** нативно в QUIC.
- Миграция между сетями без разрыва соединения (ноутбук WiFi → mobile).

**Сравнение:**

| Аспект | 1.1 | 2 | 3 |
|--------|-----|---|---|
| Протокол | TCP | TCP | UDP (QUIC) |
| Формат | Текст | Бинарный | Бинарный |
| Мультиплексирование | Нет | Да | Да |
| HoL blocking | Да | Да (на уровне TCP) | Нет |
| Handshake | TCP+TLS (3 RTT) | TCP+TLS (3 RTT) | 1 RTT (или 0-RTT) |
| Сжатие заголовков | Нет | HPACK | QPACK |
| Server Push | Нет | Да (deprecated) | Да |
| Мобильность | Нет | Нет | Да |

**Когда применять:**
- HTTP/1.1 — legacy и фоллбэк.
- HTTP/2 — мейнстрим, поддержан большинством бэкендов и клиентов.
- HTTP/3 — мобильные клиенты и latency-чувствительные сценарии; Cloudflare, Google, Meta внедряют широко.

**Подводные камни:**
- HTTP/2 живёт на одном соединении — если оно упало, упало всё сразу (у HTTP/1.1 было 6 независимых).
- UDP заблокирован в части сетей → HTTP/3 откатывается на HTTP/2.
- Server Push браузеры отключили к 2022 году: много сложности при незначительном выигрыше.

## Q11. (!) Head-of-line blocking в HTTP/1.1 и HTTP/2?

Head-of-line (HoL) blocking — это когда один «застрявший» элемент в очереди держит за собой все остальные, даже готовые. Ключевой нюанс собеседования: HTTP/2 решил HoL **на уровне приложения**, но оставил его **на уровне TCP** — и убрал его полностью только HTTP/3.

**HTTP/1.1.** Запросы строго сериализованы: следующий запрос в соединении нельзя начать, пока не получен ответ на текущий. Pipelining (теоретическая очередь из нескольких запросов) на практике сломан. Обходной путь — 6 параллельных соединений на origin, то есть 6 независимых очередей.

**HTTP/2.** Мультиплексирование позволяет гнать много стримов в одном соединении, поэтому **HoL на уровне приложения решён** — ответы не ждут друг друга логически. НО остаётся **HoL на уровне TCP**: все стримы лежат в одном TCP-соединении, и потеря одного пакета заставляет TCP придержать доставку *всех* стримов, пока пакет не ретрансмитнут. Парадокс: при ~5% потерь пакетов HTTP/2 оказывается **медленнее** HTTP/1.1, у которого было 6 независимых TCP-соединений и потеря била только по одному из них.

**HTTP/3 (QUIC).** Стримы независимы уже на транспортном уровне, поэтому потерянный пакет в стриме A НЕ блокирует стрим B — это **по-настоящему без HoL**.

**Когда HoL реально кусается:**
- Lossy-сети — mobile, перегруженный WiFi.
- Много мелких ресурсов — страница со 100 картинками, где потеря бьёт по всем сразу.

**Когда неважно:**
- Сеть с малыми потерями — DC, хорошая оптика.
- Один большой поток — стриминг видео, где стрим и так один.

**Практический вывод:**
- HTTP/2 работает нормально, пока потери пакетов < 2%.
- HTTP/3 выгоден там, где потери > 2%, с фоллбэком на HTTP/2, если UDP заблокирован.
- Подтверждается на практике: Google измеримо улучшил мобильный опыт search/YouTube на HTTP/3, Cloudflare включает его по умолчанию везде, где он поддерживается.

## Q12. (!) Keep-alive и connection reuse?

**Keep-alive** — это удержание соединения открытым после ответа, чтобы следующий запрос пошёл по нему же. Смысл — не платить заново за установку соединения, которая стоит дорого (см. Q5, Q8). Это самая дешёвая и самая важная сетевая оптимизация для клиента.

**Поведение по умолчанию:**
- HTTP/1.1 — keep-alive включён по умолчанию (`Connection: keep-alive`).
- HTTP/2 — одно постоянное мультиплексированное соединение.
- HTTP/3 — одно постоянное QUIC-соединение.

**Почему это даёт такой выигрыш:**
- Не платим TCP + TLS handshake (2–3 RTT) на каждом запросе.
- TCP cwnd уже раскачан — нет повторного slow start (Q4), соединение сразу на скорости.
- За счёт обоих факторов последующие запросы заметно быстрее первого.

**Пример выигрыша.** RTT 100 ms, 10 запросов:
- Новое соединение каждый раз: 10 × (TCP + TLS + req) ≈ 10 × 200 ms = 2000 ms.
- С переиспользованием: 10 × 100 ms = 1000 ms — **вдвое быстрее**, и это без учёта slow start, с которым разрыв ещё больше.

**Управляющие заголовки:**
- `Connection: keep-alive` — дефолт HTTP/1.1.
- `Keep-Alive: timeout=60, max=100` — таймаут простоя и максимум запросов на соединение.
- `Connection: close` — явный отказ от переиспользования.

**Настройки клиента (HTTP-клиентской библиотеки):**
```java
// Apache HttpClient
HttpClientBuilder.create()
    .setConnectionManagerShared(true)
    .setMaxConnTotal(200)
    .setMaxConnPerRoute(50)
    .setConnectionTimeToLive(60, TimeUnit.SECONDS)
    .build();
```

**На стороне сервера** keep-alive тоже настраивается (Nginx `keepalive_timeout 65s;`) и тюнится под профиль трафика. Тут компромисс: больший таймаут эффективнее переиспользует соединения, но дольше держит занятыми файловые дескрипторы и сокеты.

**За чем следить:** когда пул соединений исчерпан, новые запросы ждут свободного слота и latency растёт. Ключевые метрики — `connections_active` и `connections_reused`.

**Антипаттерн** (классическая ловушка для синьора в Java): создавать новый `HttpClient` на каждый запрос. При этом пулинг теряется, и каждый запрос платит полный TCP + TLS заново. `HttpClient` нужно создавать один раз и переиспользовать.

## Q13. HTTP/2 server push (и почему deprecated)?

**Server Push** позволял серверу проактивно отдать ресурс до того, как клиент его запросил: например, странице нужен `style.css` — сервер пушит его сразу вместе с HTML. В теории это экономит RTT, потому что клиенту не нужно делать отдельный запрос.

**Почему на практике не взлетело.** Главная проблема — сервер не знает состояние кэша клиента, а из этого вытекает всё остальное:
- **Over-pushing** — ресурс уже лежит в кэше браузера, а его пушат снова, расходуя bandwidth впустую.
- **Сложность настройки** — нужно аккуратно подбирать пары «что пушить и когда».
- **Конфликт приоритетов** — запушенный стрим конкурирует за пропускную способность с тем, что действительно нужно прямо сейчас.
- **Итог** — на реальных сайтах эффект оказался незначительным или даже отрицательным.

Поэтому **Chrome убрал server push в 2022 году**.

**Чем заменили:**
- **Early Hints (HTTP 103)** — отправить preload-подсказки ещё до основного ответа 200:
  ```
  103 Early Hints
  Link: </style.css>; rel=preload
  ```
- **HTML `<link rel=preload>`** — клиентская preload-директива, где про кэш решает сам клиент.

Подход Early Hints выигрывает именно тем, что устранял корневую проблему push: решение «грузить или нет» остаётся за клиентом, который знает свой кэш. Сейчас 103 широко поддержан (Chrome, Fastly, Cloudflare, Vercel), проще HTTP/2 push и работает и с HTTP/2, и с HTTP/3; Cloudflare сообщает об ускорении LCP на 20–30%.

**Вывод:** на HTTP/2 Push не полагаться (deprecated) — использовать Early Hints или `<link rel=preload>`.

## Q14. QUIC — почему быстрее TCP?

**QUIC (Quick UDP Internet Connections) — транспорт HTTP/3.** Он построен поверх UDP именно потому, что TCP «застыл» (его сложно менять из-за middleboxes), а QUIC реализуется в userland и закрывает сразу несколько слабых мест TCP+TLS.

1. **Handshake за 1 RTT** против 3 RTT у TCP+TLS — QUIC объединяет транспорт и TLS в одно рукопожатие. При возобновлении вообще 0-RTT (данные в первом пакете).
2. **Нет TCP HoL blocking** — стримы независимы на транспорте, потерянный пакет в стриме A не задерживает стрим B (см. Q11). Огромный выигрыш на lossy-сетях вроде mobile.
3. **Миграция соединения** — соединение идентифицируется по Connection ID, а не по паре IP/port. Когда ноутбук роумится с WiFi на mobile, то же QUIC-соединение продолжает жить; TCP бы при смене IP порвалось и пришлось бы переустанавливать.
4. **Гибкий congestion control** — BBR, CUBIC живут в userland, поэтому новые алгоритмы выкатываются быстро, без правок ядра у всех пользователей.
5. **Обязательное шифрование** — зашифрован каждый пакет (payload и частично заголовки). Middleboxes не могут вмешиваться в трафик, что защищает протокол от оссификации (застывания).
6. **Точнее восстановление после потерь** — номера пакетов монотонно растут, тогда как в TCP sequence numbers переиспользуются при ретрансмитах и создают неоднозначность; за счёт этого QUIC точнее оценивает RTT.

**Чем расплачиваемся:**
- UDP заблокирован в части сетей (обычно 0.5–2%) → фоллбэк на HTTP/2.
- Выше нагрузка на CPU — крипто в userland и обработка по отдельным пакетам; сглаживается hardware offload.
- Менее зрелый тулинг по сравнению с TCP.

**Насколько распространён (2024):** ~28% веб-трафика (статистика Cloudflare); работает в Gmail, YouTube, Meta, Instagram, Spotify; включён по умолчанию у большинства крупных CDN.

**Поддержка клиентами:** Chrome, Firefox, Safari — включён; curl и браузеры — стандарт; в мобильных приложениях зависит от используемой библиотеки.

## Q15. (!) DNS lookup как latency source?

DNS-резолв (`api.example.com` → IP) выполняется *до* установки соединения, поэтому его задержка добавляется к самому первому запросу — и про неё часто забывают, когда раскладывают end-to-end latency.

**Сколько стоит:**
- Попадание в кэш (локальный или кэш ОС) — практически 0 ms.
- Промах кэша — 20–200 ms на запрос к рекурсивному резолверу.

**Почему холодный lookup такой дорогой.** Запрос проходит цепочку: браузер → DNS-клиент ОС → настроенный резолвер (1.1.1.1, 8.8.8.8, ISP) → root → TLD → authoritative. Это потенциально 3–4 последовательных запроса, и каждый платит свой RTT.

**Роль TTL.** TTL записи задаёт время кэширования: 300s — пять минут, и тут компромисс. Короткий TTL (30s) даёт частые lookup-ы (больше latency), но позволяет быстро переключиться при failover; длинный TTL (1h+) экономит lookup-ы, но делает failover менее гибким.

**Как сократить:**

**1. DNS prefetch** — HTML-подсказка резолвить заранее, ещё до реального запроса:
```html
<link rel="dns-prefetch" href="//api.example.com">
```
Браузер делает резолв заблаговременно, экономя RTT в нужный момент.

**2. Preconnect** (ещё лучше) — заранее делает не только DNS, но и TCP + TLS:
```html
<link rel="preconnect" href="//api.example.com">
```

**3. DNS over HTTPS (DoH) / DNS over TLS (DoT)** — шифруют DNS ради приватности, но могут добавить latency (TLS-рукопожатие с резолвером); поэтому держите резолвер/прокси рядом с пользователем (Cloudflare 1.1.1.1 быстрый).

**4. Кэширование на уровне приложения** — многие HTTP-клиенты кэшируют резолвнутые IP; следите, чтобы кэш не устарел при failover (настройте соблюдение TTL).

**5. Anycast DNS** — резолверы географически распределены, отвечает ближайший POP (Cloudflare DNS, Google DNS), что сокращает RTT самого DNS-запроса.

**Ловушка в Java:** старые JVM кэшировали DNS навсегда и поэтому пропускали failover-ы. Свойство `networkaddress.cache.ttl` нужно выставить не в `-1`, а в конечное значение (например, 30s); в современных JVM дефолт уже 30s.

**Мониторинг.** Разбивка end-to-end latency обязана включать время DNS; например, через `curl -w`:
```bash
curl -o /dev/null -s -w "dns:%{time_namelookup} connect:%{time_connect} start:%{time_starttransfer}\n" https://api.site.com
```

## Q16. (!) Чем отличаются gzip, brotli и zstd?

Все три сжимают HTTP-ответы, но балансируют по-разному между степенью сжатия, скоростью и совместимостью. Короткий ответ: gzip — универсальный дефолт, brotli — лучший вариант для веба, zstd — отличный, но пока почти не используется в HTTP.

- **gzip** — повсеместный с 1990-х. Быстрое сжатие и распаковка, низкая нагрузка на CPU, дефолтное качество 6 из 9. Степень так себе, но на текстовых данных результат всё равно солиден (на JSON — до 80%). Его сила — что его понимают абсолютно все.
- **brotli** (Google 2013) — сжимает на ~15–25% плотнее gzip при такой же быстрой распаковке; платит за это более медленным сжатием на высоких уровнях. Поддержан всеми современными браузерами и широко включён на CDN. Уровни качества 0–11: типично 4–6 для динамики и 11 для статики (которую сжимают заранее).
- **zstd** (Facebook 2016) — быстрый и с хорошей степенью (часто бьёт gzip, близок к brotli). Но **для HTTP `Content-Encoding` он почти не используется**: RFC 8878 (2021) есть, а распространение ограничено. Зато он популярен внутри приложений — сжатие в Kafka, файловые системы.

**Согласование** идёт через заголовки: клиент шлёт `Accept-Encoding: gzip, br, zstd`, сервер выбирает лучший поддерживаемый (подробнее в Q17).

**Рекомендация по применению:**
- Статика — сжать заранее brotli level 11 + gzip level 9 и отдавать готовое: высокая цена сжатия платится один раз.
- Динамика — brotli level 4–6: баланс между нагрузкой на CPU и степенью сжатия в реальном времени.
- Не сжимать совсем мелкое (< 1KB) — overhead превысит выигрыш.
- Не сжимать уже сжатое (JPEG, PNG, MP4) — CPU тратится впустую, размер не падает.

**Подводный камень — атака BREACH.** Связка «сжатие + HTTPS + секрет в ответе + пользовательский ввод в том же ответе» позволяет атакующему по изменению размера ответа постепенно угадать секрет. Защита: не сжимать чувствительные ответы либо гарантировать, что пользовательский ввод не попадает в ответ с секретом.

**На CDN** контент часто отдаётся предварительно сжатым (сжатие оплачено один раз при деплое); некоторые CDN сжимают ответ origin-а на лету автоматически.

**Как измерить** эффект: отношение `Content-Length` к сырому размеру и есть коэффициент сжатия.

## Q17. Как работает согласование Content-Encoding?

Это механизм, которым клиент и сервер договариваются о кодировке ответа. Клиент перечисляет, что умеет распаковывать, а сервер выбирает один вариант из поддерживаемых — выбор не навязывается, а согласуется.

Клиент объявляет поддержку:
```
Accept-Encoding: gzip, deflate, br, zstd
```

Можно задать предпочтения через значения качества `q`:
```
Accept-Encoding: gzip;q=0.5, br;q=1.0
```

Сервер выбирает одну кодировку и сообщает её в ответе:
```
Content-Encoding: br
```

Сжимать можно и тело запроса (`Content-Encoding: gzip` — редко, при POST сжатых данных), и тело ответа (типичный случай). Кодировка `identity` означает «несжатое»: `Accept-Encoding: identity` явно просит без сжатия, и по умолчанию identity разрешён, если его не исключили.

**Подводные камни:**
- **`Vary: Accept-Encoding` обязателен на CDN.** Без него CDN может закэшировать brotli-ответ и отдать его клиенту, понимающему только gzip, — ответ сломается. С ним CDN держит отдельный закэшированный вариант на каждую кодировку.
- **Middleboxes.** Старые прокси вырезают заголовок `Accept-Encoding`, и сервер не видит поддержки сжатия (отдаёт несжатое). HTTPS это предотвращает, потому что заголовки зашифрованы.
- **`Content-Length`** должен отражать именно сжатый размер и быть выставлен корректно.
- **brotli — только по HTTPS:** браузеры не примут brotli поверх обычного HTTP.

**Проверка инструментами:**
```bash
curl -H "Accept-Encoding: br, gzip" -I https://site.com/page
# check Content-Encoding header
```

## Q18. (!) Зачем CDN — latency math?

CDN приближает контент к пользователю географически, а значит сокращает RTT — единственный реальный способ уменьшить latency (см. Q1). Посчитаем выигрыш на конкретных числах.

**Без CDN.** Origin в us-east-1, пользователь в Токио, RTT ~130 ms. Каждый запрос ассета стоит минимум 130 ms + время передачи.

**С CDN.** Edge стоит в Токио, ~5 ms от пользователя:
- Первый запрос (cache miss): пользователь → edge → origin → ответ ≈ 140 ms.
- Последующие (cache hit): пользователь → edge → ответ ≈ 5–10 ms.

**Для типичной веб-страницы (50 запросов)** разница драматична:
- Без CDN: 130 ms на каждый round-trip в цепочке → 3–5 секунд.
- С CDN (95% из кэша): в основном по 5–10 ms → 0.5–1 секунда.

**Что CDN даёт помимо latency:**
1. **Разгрузка origin-а** — при 95% cache hit до origin не доходит 95% трафика: ниже счёт за bandwidth и меньше нужен origin-кластер.
2. **Поглощение DDoS** — у CDN глобальная ёмкость, атака размазывается по множеству POP вместо одного origin.
3. **Терминация TLS на edge** — рукопожатие происходит рядом с пользователем (несколько ms) вместо origin (150 ms). Это огромный выигрыш по latency даже для контента, который вообще не кэшируется.
4. **Edge compute** (Workers, Lambda@Edge) — логику можно выполнять рядом с пользователем, ускоряя даже динамические ответы.
5. **Отказоустойчивость** — если origin лёг, CDN отдаёт stale-копию; поддерживается multi-region failover origin-а.

**По деньгам** CDN часто ещё и дешевле: CDN egress ~$0.03–0.08 за GB против origin egress (AWS us-east-1 в интернет) $0.09/GB. То есть лучше и UX, и счёт.

**Где выигрыш меньше:** сильно персонализированный контент (уникальный на каждого пользователя) — это всегда cache miss; real-time с низким TTL тоже выигрывает меньше. Но даже там терминация TLS на edge продолжает помогать.

## Q19. (!) Чем gRPC производительнее REST?

**gRPC** — RPC-фреймворк на protobuf + HTTP/2; **REST** — JSON поверх HTTP (1.1 или 2). gRPC быстрее в основном по двум причинам: компактная бинарная сериализация и обязательный HTTP/2 с мультиплексированием. Но «быстрее» не значит «всегда лучше» — разберём оси.

**Откуда берётся разница в производительности:**
- **Сериализация** — protobuf компактнее (на 30–50% меньше байт) и быстрее парсится; JSON универсальнее и человекочитаем, но дороже.
- **Транспорт** — gRPC всегда HTTP/2 (мультиплексирование, бинарь); REST часто остаётся на HTTP/1.1.
- **Стриминг** — у gRPC двунаправленный стриминг нативно; REST для стриминга вынужден использовать SSE или WebSocket.
- **Паттерн соединений** — gRPC держит несколько долгоживущих HTTP/2-соединений (пул 1–2); REST либо плодит соединения, либо тоже пулит HTTP/2.
- **Контракт** — gRPC генерирует типобезопасные stub-ы из `.proto`; в REST клиенты пишут руками или генерируют из OpenAPI.

**Порядок цифр (грубо):** gRPC часто в 2–5 раз быстрее на запрос при высоком throughput за счёт меньших payload-ов и скорости парсинга. На одной машине (Java) встречается gRPC ~10k req/s против REST-JSON ~3k req/s.

**Когда REST лучше:** публичные API (браузеры зовут напрямую), приоритет простоты и тулинга (curl, Postman), нужно HTTP-кэширование.

**Когда gRPC лучше:** внутренние микросервисы, высокий throughput, стриминг, важна строгая типизация и кодогенерация.

**Минусы gRPC:** плохая поддержка браузерами (нужен gRPC-Web прокси), сложнее отладка (бинарный формат), беднее экосистема тулинга, L7-фичи middleware и балансировщиков бывают ограничены. **gRPC-Web** — это урезанное подмножество для браузеров (только unary + server streaming), которому нужен Envoy-прокси для трансляции.

**Про миграцию REST → gRPC:** сначала замерьте — часто REST вообще не настоящий bottleneck. Внутренние горячие пути дают высокий ROI; публичное API ломать ради gRPC обычно не стоит.

## Q20. WebSockets — накладные расходы и сценарии применения?

**WebSocket (RFC 6455)** — полнодуплексное постоянное соединение поверх TCP. Оно открывается через апгрейд из HTTP/1.1-рукопожатия, а дальше живёт как двунаправленный канал с минимальным оверхедом на фрейминг (~2–14 байт на сообщение). Главная ценность — после установки нет handshake на каждое сообщение, поэтому оно идеально для частого двустороннего обмена.

**Где применять:**
- **Двунаправленный real-time** — чат, совместное редактирование, игры.
- **Server push** — уведомления, биржевые тикеры.
- **Стриминг обновлений** — дашборды, live-спорт.

**Overhead.** Установка стоит 1 RTT (HTTP/1.1-запрос + Upgrade-ответ); дальше handshake не платится, а накладные расходы на каждый фрейм минимальны.

**Чем отличается от альтернатив:**
- **vs SSE** — WebSocket двунаправленный, SSE только сервер→клиент (зато проще: поверх HTTP, дружелюбнее к прокси, переподключение встроено).
- **vs long polling** — long polling открывает новый запрос на каждое событие (большой оверхед); WebSocket держит одно соединение на множество событий — гораздо эффективнее.
- **vs gRPC bidi streaming** — WebSocket дружелюбнее к браузеру и проще; gRPC-стриминг типизирован, но требует gRPC-Web.

**Чем сложен.** Основная боль — состояние привязано к соединению:
- Stateful — нужна sticky-сессия, чтобы LB всегда направлял пользователя на тот же WS-сервер.
- Из-за этой привязки сложно масштабировать горизонтально.
- Прокси и файрволы могут дропнуть простаивающее соединение — нужны ping/keepalive.
- Нет HTTP-кэширования: после upgrade это семантически уже не HTTP.

**Как масштабируют:** Redis pub/sub для рассылки сообщений между инстансами сервера или централизованный брокер соединений (EMQX, Centrifugo, MQTT).

**По производительности** современные серверы держат 100K+ одновременных WS на инстанс (Netty, Node.js, Go). Ключевой ресурс — память на соединение, поэтому тюнят socket-буферы.

## Q21. Что такое Server-Sent Events (SSE) и когда их применять?

**SSE — однонаправленный поток сервер→клиент поверх обычного HTTP.** Это его суть и одновременно главное преимущество: раз это просто долгоиграющий HTTP-ответ, работают все привычные вещи — заголовки, авторизация, прокси, а переподключение браузер делает сам.

**Формат** — текстовый, с полями `event`/`data`:
```
Content-Type: text/event-stream

event: update
data: {"price": 100}

event: heartbeat
data: ok
```

**Клиент (браузер):**
```js
const es = new EventSource('/events');
es.onmessage = (e) => console.log(e.data);
```

**Против WebSocket:**

| Аспект | SSE | WebSocket |
|--------|-----|-----------|
| Направление | Сервер → Клиент | Двунаправленный |
| Протокол | HTTP | WebSocket (после upgrade) |
| Переподключение | Автоматическое | Ручное |
| Event ID | Нативно (Last-Event-ID) | Вручную |
| Бинарные данные | Только текст | Текст + бинарь |
| Дружелюбность к прокси | Да (просто HTTP) | Может быть дропнут |
| Сложность | Проще | Гибче |

**Когда выбирать SSE:** односторонние обновления (дашборды, уведомления, стриминг логов), нужна HTTP-семантика (заголовки, авторизация, прокси), важна простота деплоя.

**Когда WebSocket:** настоящий двунаправленный обмен (чат, игры), бинарные данные, чуть ниже оверхед на сообщение (хотя разница незначительная).

**SSE заметно выигрывает от новых версий HTTP.** На HTTP/1.1 каждый SSE-стрим занимает отдельное соединение, и их число упирается в лимит на origin. HTTP/2 за счёт мультиплексирования позволяет многим SSE-стримам делить одно соединение — масштабируется лучше. HTTP/3 вдобавок убирает HoL blocking (Q11), так что один зависший стрим не тормозит остальные.

**Частая ошибка** — считать, что «WebSocket всегда лучше». Для односторонних обновлений SSE часто идеально подходит и даёт более простой код.

## Q22. (!) Tail latency — причины и борьба?

**Tail latency** — это «хвост» распределения, задержки p99 и p99.9, то есть худшие несколько процентов запросов. На собеседовании главное — объяснить, почему именно хвост, а не медиана, определяет реальный пользовательский опыт.

**Почему хвост так важен — fan-out умножает редкие задержки.** Допустим, одна страница делает 50 вызовов бэкенда, у каждого p50 = 20 ms, p99 = 100 ms. Тогда вероятность, что *хотя бы один* из 50 вызовов попадёт в свой медленный p99, очень высока — поэтому **p99 страницы ≈ 100 ms почти всегда**. Страница так же медленна, как её самый медленный компонент: доминирует худший, а не средний.

**Откуда берётся хвост:**
- **Паузы GC** — сборка старого поколения даёт паузы 100 ms+. Лечится тюнингом (G1, ZGC, Shenandoah) и снижением аллокаций.
- **Очереди** — очередь пула потоков забивается, и часть запросов ждёт (закон Литтла: L = λ × W).
- **Сеть** — потеря пакета и ретрансмит добавляют ~300 ms, плюс TCP congestion backoff.
- **Дисковый I/O** — сброс из БД, всплеск fsync при записи лога.
- **Борьба за CPU** — шумный сосед (соседняя VM на той же машине) или фоновая задача выедает ядра.
- **Bufferbloat** — глубокие сетевые буферы дают queueing latency.
- **Промах кэша** — промах L1/L2 заставляет идти в БД, что в 10–100 раз медленнее.

**Чем бороться:**
- **Hedged requests** — отправить запрос на 2 реплики и взять ту, что ответит первой (паттерны Google Spanner, MapReduce). Тратит ~5–10% лишних ресурсов, но заметно срезает p99: маловероятно, что обе реплики затормозят одновременно.
- **Tied requests** — как только быстрая реплика ответила, отменить медленную; так меньше работы тратится впустую.
- **Circuit breaking** — быстро отказывать на нездоровом бэкенде, чтобы его медленные ответы не попадали в хвост.
- **Load shedding** — отклонять часть запросов у порога насыщения, чтобы перегрузка не каскадировала и не растягивала хвост у всех.

**Что мониторить.** Снимайте p50, p90, p95, p99, p99.9 и ставьте алерты на рост p99 — **нельзя смотреть только на p50**: именно он скрывает проблему, которую чувствуют пользователи.

## Q23. (!) Linux sysctl tuning для high-throughput?

Под высокий throughput дефолтные лимиты ядра становятся узким местом раньше, чем железо: маленькие буферы не дают наполнить канал (Q3), короткие очереди дропают всплески соединений, заканчиваются ephemeral-порты. Ниже — типовой набор, но важнее принцип: каждую настройку проверять замером, а не копировать вслепую.

**Сетевой стек:**

```bash
# Larger socket buffers
net.core.rmem_max = 134217728  # 128MB
net.core.wmem_max = 134217728
net.ipv4.tcp_rmem = 4096 87380 134217728
net.ipv4.tcp_wmem = 4096 65536 134217728

# Higher connection backlog
net.core.somaxconn = 65535
net.core.netdev_max_backlog = 30000

# More ephemeral ports
net.ipv4.ip_local_port_range = 1024 65535

# TIME_WAIT reuse (client side)
net.ipv4.tcp_tw_reuse = 1

# FIN timeout
net.ipv4.tcp_fin_timeout = 15

# SYN backlog
net.ipv4.tcp_max_syn_backlog = 65535

# TCP fast open
net.ipv4.tcp_fastopen = 3

# Congestion control
net.ipv4.tcp_congestion_control = bbr
net.core.default_qdisc = fq
```

**Лимиты файловых дескрипторов:**
```bash
# /etc/security/limits.conf
* soft nofile 1000000
* hard nofile 1000000
```

**Connection tracking (если используется netfilter/iptables):**
```
net.netfilter.nf_conntrack_max = 1000000
```

**Не копируйте вслепую:** замеряйте до и после — часть настроек помогает только конкретным нагрузкам, а где-то и навредит.

**Опасная ловушка — `tcp_tw_recycle`:** он **удалён в Linux 4.12+** и его нельзя использовать никогда, потому что он ломает соединения через NAT.

**Чем смотреть эффект:**
- `ss -s` — сводка по сокетам.
- `netstat -s` — статистика (ретрансмиты, дропы — растущие счётчики указывают на проблему).
- `nstat` — сетевая статистика.

**Не забывайте уровень приложения** — sysctl бесполезен, если приложение само себя ограничивает: число воркеров / event loop-ов HTTP-сервера под количество CPU, размер пула потоков, лимиты пула соединений.

## Q24. Чем диагностировать медленную сеть (инструменты)?

Главный приём — не гадать, а изолировать стадию: каждый инструмент отвечает за свой слой (RTT, соединение, TLS, HTTP, DNS), и поочерёдный замер сразу показывает, где именно теряется время.

**Latency и throughput:**
- `ping <host>` — RTT и потери пакетов.
- `traceroute` / `mtr` — задержка по хопам (видно, на каком участке растёт).
- `iperf3` — измерение пропускной способности.
- `tcpdump` / `wireshark` — захват пакетов для детального разбора.

**Состояние соединений:**
- `ss -tn` — TCP-соединения.
- `ss -ti` — с информацией о congestion (cwnd, rtt, ретрансмиты).
- `ss -ltn` — слушающие сокеты.

**Статистика:**
- `netstat -s` / `nstat` — накопительные счётчики; смотрите аномалии в `tcpExtTCPRcvCoalesce`, `tcpExtTCPRetransFail`.
- `ip -s link` — статистика интерфейса (дропы, ошибки).

**Специфично для HTTP:**
```bash
curl -o /dev/null -s -w "dns:%{time_namelookup} conn:%{time_connect} tls:%{time_appconnect} first:%{time_starttransfer} total:%{time_total}\n" https://site.com
```

**DNS:**
- `dig example.com` — DNS-запрос.
- `dig +trace` — полная трассировка резолва от корня.

**Низкоуровневое:**
- `bpftrace` / `eBPF` — трассировка на уровне ядра.
- `tcpdump -i eth0 port 443 -w capture.pcap` → разбор в Wireshark.

**Service mesh:** в Envoy / Istio поле access-лога `%RESPONSE_FLAGS%` показывает таймауты upstream и подобные проблемы.

**Синтетический мониторинг:** Pingdom, Datadog Synthetics — непрерывные проверки из локаций по всему миру (ловят региональные деградации до жалоб пользователей).

**Порядок разбора «сервис X тормозит»** — идти по стадиям и на каждой смотреть свой таймер:
1. Быстро ли резолвится DNS? (время `dig`)
2. Быстрый ли TCP handshake? (`curl -w time_connect`)
3. Быстрый ли TLS handshake? (`curl -w time_appconnect`)
4. Быстро ли отвечает сервер? (`curl -w time_starttransfer`)
5. Медленно ли передаётся payload? (тогда это проблема bandwidth)

Каждый шаг изолирует свою причину, и первая стадия, где время «прыгнуло», и есть виновник.
