## Q1. (!) Что такое рекурсия?

**Рекурсия** — это когда функция вызывает сама себя, сводя задачу к более простой версии той же задачи. Решение «большого» случая выражается через решение «меньшего», и так до элементарного случая, который считается напрямую.

```java
int factorial(int n) {
    if (n <= 1) return 1;          // base case
    return n * factorial(n - 1);   // recursive step
}
```

Здесь `factorial(n)` не считает результат сам — он делегирует подзадачу `factorial(n - 1)` и достраивает ответ умножением на `n`. Так задача спускается до `n <= 1`, где ответ известен сразу.

Рекурсия естественна там, где сама **структура данных или задача определена рекурсивно** — дерево состоит из поддеревьев, а задача разбивается на подзадачи того же вида:

- Обходы деревьев и графов
- Divide and Conquer (Merge Sort, Quick Sort)
- Backtracking (N-Queens, Sudoku)
- Парсеры (recursive descent)
- Файловая система (директория содержит директории)

## Q2. (!) Базовый случай и рекурсивный шаг?

Любая корректная рекурсивная функция состоит из двух обязательных частей — без одной из них она либо не остановится, либо не продвинется к ответу.

1. **Базовый случай (base case)** — условие останова: самый простой вход, ответ для которого известен сразу, без рекурсии. Без него рекурсия уходит в бесконечность и падает с `StackOverflowError`.
2. **Рекурсивный шаг (recursive step)** — вызов самой себя с **меньшей** подзадачей, который постепенно приближает вход к базовому случаю.

```java
int fact(int n) {
    if (n <= 1) return 1;       // base case — must!
    return n * fact(n - 1);     // recursive step — приближаемся к base
}
```

**Правило:** на каждом вызове аргумент должен **двигаться** в сторону базового случая (здесь `n` уменьшается). Если этого не происходит — рекурсия не сойдётся и переполнит стек. Частая ошибка на интервью — забыть базовый случай или сделать шаг, который не приближает к нему (например, `fact(n)` вместо `fact(n - 1)`).

## Q3. (!) Что такое recursion call stack?

Стек вызовов — это структура, в которой среда исполнения хранит «незавершённые» вызовы функций. Каждый новый вызов кладёт сверху отдельный **stack frame** (кадр стека) с локальными переменными, параметрами и адресом возврата. При рекурсии эти кадры накапливаются: вызов `factorial(4)` не может завершиться, пока не вернётся `factorial(3)`, тот ждёт `factorial(2)` и так далее.

```
factorial(4) call stack:
┌─────────────────────┐
│ factorial(1) → 1    │ ← base case
├─────────────────────┤
│ factorial(2) → 2*1  │
├─────────────────────┤
│ factorial(3) → 3*2  │
├─────────────────────┤
│ factorial(4) → 4*6  │ ← начало
└─────────────────────┘
```

Стек растёт вглубь, пока не достигнут базовый случай (самый верхний кадр), а затем «схлопывается» снизу вверх: после каждого `return` верхний кадр удаляется, и его результат подставляется в ожидающий кадр под ним. Поэтому **максимальная глубина стека равна глубине рекурсии**, и именно она определяет расход памяти.

**В JVM** размер стека потока ограничен и составляет примерно `512KB-1MB` (настраивается флагом `-Xss`). Когда кадров накапливается больше, чем влезает, поток падает с `StackOverflowError` — это плата за глубокую рекурсию.

## Q4. (!) Чем рекурсия отличается от итерации?

Оба подхода решают задачу повторением, но повторение организовано по-разному: рекурсия использует **стек вызовов** (неявную память), итерация — **цикл и переменные** (явное состояние). Отсюда и все различия:

| Критерий | Рекурсия | Итерация |
|----------|----------|----------|
| Читаемость | Часто проще для деревьев, графов | Проще для линейных задач |
| Память | `O(n)` стек | `O(1)` обычно |
| Производительность | Overhead на вызовы | Быстрее |
| Риск StackOverflow | Да | Нет |
| Применимость | Естественна для D&C, рекурсивных структур | Универсальна |

**Главный компромисс:** рекурсия выигрывает в читаемости на рекурсивных структурах (деревья, графы, divide-and-conquer), но платит за это памятью на стек и риском его переполнения. Итерация дешевле по ресурсам, но для древовидных задач код становится громоздким (приходится вручную вести стек).

**Любую** рекурсию можно переписать итеративно (теоретически — через явный стек), но не всегда это получается **просто и читаемо**. Ниже одна и та же задача — сумма дерева — в двух стилях:

```java
// Рекурсия — естественно для дерева
int sumTree(TreeNode node) {
    if (node == null) return 0;
    return node.val + sumTree(node.left) + sumTree(node.right);
}

// Итеративно — через явный стек
int sumTreeIter(TreeNode root) {
    if (root == null) return 0;
    Deque<TreeNode> stack = new ArrayDeque<>();
    stack.push(root);
    int sum = 0;
    while (!stack.isEmpty()) {
        TreeNode node = stack.pop();
        sum += node.val;
        if (node.left != null) stack.push(node.left);
        if (node.right != null) stack.push(node.right);
    }
    return sum;
}
```

Память у обоих вариантов — `O(h)` (высота дерева): рекурсия держит её в кадрах JVM-стека, итерация — в явном `Deque`. Разница в том, что у явного стека можно контролировать размер и он живёт в куче, а рекурсия упирается в фиксированный лимит потока и рискует `StackOverflowError` на глубоких деревьях.

## Q5. (!) Что такое tail recursion?

**Хвостовая рекурсия (tail recursion)** — это случай, когда рекурсивный вызов является **самой последней** операцией функции: его результат сразу возвращается, без каких-либо вычислений после него. Ключевой признак — после возврата из рекурсивного вызова делать больше **нечего**, поэтому текущий кадр стека уже не нужен.

```java
// Tail recursive
int sum(int n, int acc) {
    if (n == 0) return acc;
    return sum(n - 1, acc + n); // последнее действие — вызов
}

// НЕ tail recursive — после вызова мы умножаем
int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1); // вызов, потом *
}
```

Во втором примере после `factorial(n - 1)` остаётся незавершённое умножение на `n` — значит, кадр нужно сохранить, и это уже не хвостовой вызов.

**Зачем это нужно:** раз текущий кадр после хвостового вызова бесполезен, компилятор может **переиспользовать** его вместо создания нового. Это превращает рекурсию в обычный цикл — стек не растёт, и `StackOverflowError` исключён даже при миллионах вызовов. Такую оптимизацию называют tail call optimization (TCO).

## Q6. (!) Поддерживает ли JVM tail call optimization?

**Нет.** JVM не выполняет TCO (Tail Call Optimization) — даже идеально хвостовой метод на Java всё равно создаёт по кадру на каждый вызов.

**Почему — исторические причины:** оптимизация ломала бы то, что в JVM завязано на реальные кадры стека:

- **Stack traces.** Переиспользование кадров «съедало» бы промежуточные вызовы — интроспекция и отладка стали бы недостоверными.
- **Security manager.** Проверки прав исторически привязаны к конкретным кадрам стека (кто кого вызвал), а TCO эти кадры убирает.
- **Project Loom.** Виртуальные потоки частично снимают остроту проблемы другим способом (растущий стек), поэтому отдельный приоритет на TCO стал ниже.

**Практическое следствие:** на Java хвостовая рекурсия не даёт никакого выигрыша по стеку. Для большой глубины нужно явно переписывать в итерацию или вести стек руками.

**В Scala / Kotlin** ограничение JVM обходится на уровне компилятора: аннотация `@tailrec` заставляет его развернуть хвостовую рекурсию в цикл (и выдать ошибку компиляции, если вызов на деле не хвостовой).

```kotlin
tailrec fun sum(n: Int, acc: Int = 0): Int =
    if (n == 0) acc else sum(n - 1, acc + n) // компилируется в while-loop
```

## Q7. Как обойти отсутствие TCO в Java?

Раз JVM не сворачивает хвостовую рекурсию сама, глубину приходится снимать вручную. Способы — от радикального до паллиативного:

1. **Переписать итеративно** — самый надёжный вариант: цикл вообще не использует стек вызовов, поэтому глубина перестаёт быть проблемой.

```java
int sumIter(int n) {
    int sum = 0;
    for (int i = 1; i <= n; i++) sum += i;
    return sum;
}
```

2. **Trampolining (батут)** — функция не вызывает себя напрямую, а **возвращает описание следующего шага** (`Supplier<Result>` или объект-продолжение). Внешний цикл крутит эти шаги, пока не дойдёт до результата. Кадры стека при этом не накапливаются, потому что каждый шаг завершается возвратом:

```java
interface TailCall<T> {
    TailCall<T> apply();
    boolean isComplete();
    T result();

    default T invoke() {
        TailCall<T> tc = this;
        while (!tc.isComplete()) tc = tc.apply();
        return tc.result();
    }
}
```

3. **Увеличить размер стека** — флаг `-Xss4m` поднимает лимит потока с ~512K до 4MB и даёт примерно 80K уровней рекурсии. Это паллиатив: вы лишь отодвигаете предел, а не убираете его, и платите памятью за каждый поток.

4. **Project Loom (виртуальные потоки)** — у виртуального потока стек растёт по мере надобности, поэтому глубокая рекурсия не упирается в фиксированный лимит. Это не настоящий TCO (кадры всё ещё создаются), но практическое ограничение по глубине снимается.

## Q8. (!) Factorial — рекурсивно?

Факториал — каноничный пример: `n! = n · (n-1)!`, базовый случай `0! = 1! = 1`. Рекурсивная версия буквально повторяет эту формулу, но на интервью важно показать и итеративную (без расхода стека), и переполнение типа.

```java
// O(n) время, O(n) стек
long factorial(int n) {
    if (n < 0) throw new IllegalArgumentException("n must be >= 0");
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}

// Итеративно — O(n) время, O(1) память
long factorialIter(int n) {
    long result = 1;
    for (int i = 2; i <= n; i++) result *= i;
    return result;
}

// BigInteger для больших n
BigInteger factorialBig(int n) {
    BigInteger result = BigInteger.ONE;
    for (int i = 2; i <= n; i++) result = result.multiply(BigInteger.valueOf(i));
    return result;
}
```

**Подводный камень — переполнение.** `long` хватает только до `n = 20`: уже `21!` не влезает (`20! = 2,432,902,008,176,640,000` — последнее значение, помещающееся в `long`). Для бо́льших `n` нужен `BigInteger`, который растёт без ограничения. Рекурсивный и итеративный варианты по времени одинаковы — `O(n)`, но рекурсия дополнительно тратит `O(n)` стека, поэтому на практике предпочтительнее итеративная или `BigInteger`-версия.

## Q9. (!) Fibonacci — рекурсивно?

Числа Фибоначчи (`F(n) = F(n-1) + F(n-2)`) — классическая ловушка: наивная рекурсия выглядит красиво, но работает за `O(2^n)`, потому что одни и те же подзадачи пересчитываются заново. Три варианта показывают эволюцию от провального к оптимальному:

```java
// Naive — O(2^n) — НЕПРИГОДНО для n > 30
int fibNaive(int n) {
    if (n <= 1) return n;
    return fibNaive(n - 1) + fibNaive(n - 2);
}

// Memoization — O(n) время и память
int fibMemo(int n, int[] memo) {
    if (n <= 1) return n;
    if (memo[n] != 0) return memo[n];
    return memo[n] = fibMemo(n - 1, memo) + fibMemo(n - 2, memo);
}

// Итеративно — O(n) время, O(1) память
int fibIter(int n) {
    if (n <= 1) return n;
    int prev2 = 0, prev1 = 1;
    for (int i = 2; i <= n; i++) {
        int curr = prev1 + prev2;
        prev2 = prev1; prev1 = curr;
    }
    return prev1;
}
```

Дерево вызовов для `fib(5)` (часть, до второго уровня):

- `fib(5)` → `fib(4)` и `fib(3)`
- `fib(4)` → `fib(3)` и `fib(2)`

`fib(3)` уже на этом фрагменте встречается **дважды** (в ветке `fib(5)` напрямую и внутри `fib(4)`).

Это наглядно показывает проблему: `fib(3)` встречается дважды (и для бо́льших `n` дублирований лавинообразно больше). Именно эти **перекрывающиеся подзадачи** дают экспоненту. Memoization кеширует уже посчитанные значения и убирает повторы, сводя время к `O(n)`; а итеративная версия достигает того же за `O(n)` времени и `O(1)` памяти, храня лишь два последних числа.

## Q10. Как рекурсивно посчитать сумму элементов массива?

Идея: сумма всего массива = первый элемент + сумма оставшегося «хвоста». Базовый случай — пустой остаток (индекс дошёл до конца), его сумма равна нулю.

```java
int sum(int[] arr, int index) {
    if (index == arr.length) return 0;
    return arr[index] + sum(arr, index + 1);
}

// Tail recursive (но JVM не оптимизирует!)
int sumTail(int[] arr, int index, int acc) {
    if (index == arr.length) return acc;
    return sumTail(arr, index + 1, acc + arr[index]);
}
```

Второй вариант — хвостовой (аккумулятор `acc` копит сумму, после вызова делать нечего), но на JVM это не помогает: TCO отсутствует, и оба варианта тратят `O(n)` стека. Поэтому для больших массивов рекурсия здесь — антипаттерн: простой `for`-цикл даёт `O(1)` памяти и не рискует `StackOverflowError`.

## Q11. (!) Как решить задачу о Ханойских башнях (Tower of Hanoi)?

**Задача:** перенести `n` дисков со стержня `from` на `to`, используя `via` как вспомогательный. Правила: за раз двигаем один диск и нельзя класть больший диск на меньший.

**Рекурсивная идея** разбивает задачу на три шага: чтобы перенести `n` дисков, сначала перенесём верхние `n-1` диска в сторону (на `via`), затем переложим самый большой диск на место (`to`), и наконец перенесём те `n-1` диска поверх него. Перенос `n-1` дисков — та же задача меньшего размера, отсюда рекурсия.

```java
void hanoi(int n, char from, char to, char via) {
    if (n == 0) return;
    hanoi(n - 1, from, via, to);
    System.out.printf("Move disk %d from %c to %c%n", n, from, to);
    hanoi(n - 1, via, to, from);
}

hanoi(3, 'A', 'C', 'B');
// Move 1 from A to C
// Move 2 from A to B
// Move 1 from C to B
// Move 3 from A to C
// Move 1 from B to A
// Move 2 from B to C
// Move 1 from A to C
```

Из структуры решения сразу выводится число ходов: рекуррентное соотношение `T(n) = 2·T(n-1) + 1` (два переноса по `n-1` диска плюс один ход большого диска) даёт `2^n - 1`. Это `O(2^n)` — экспоненциально, но при этом **минимально возможное** число ходов: меньше задачу не решить.

Это классическая задача-демонстрация рекурсии: короткое и элегантное решение там, где итеративный аналог куда менее очевиден.

## Q12. Как рекурсивно перевести число в другую систему счисления?

Перевод строится на разложении: последняя цифра в системе с основанием `base` — это остаток `n % base`, а оставшиеся старшие цифры получаются переводом `n / base`. Рекурсия как раз и обрабатывает «оставшуюся часть», а базовый случай — `n == 0` (переводить больше нечего).

```java
String decimalToBase(int number, int base) {
    if (number == 0) return "0";
    return decimalToBaseHelper(number, base, new StringBuilder()).reverse().toString();
}

StringBuilder decimalToBaseHelper(int n, int base, StringBuilder sb) {
    if (n == 0) return sb;
    int digit = n % base;
    sb.append(digit < 10 ? (char)('0' + digit) : (char)('A' + digit - 10));
    return decimalToBaseHelper(n / base, base, sb);
}
```

Цифры извлекаются от младшей к старшей, поэтому в конце результат разворачивается через `reverse()`. Глубина рекурсии (и расход стека) — `O(log_base n)`, то есть число цифр результата. Та же логика тривиально переписывается итеративно через `while (n > 0)` без расхода стека.

## Q13. (!) Как реализовать быстрое возведение в степень Power(x, n)?

Наивный способ умножает `x` сам на себя `n` раз — `O(n)`. Быстрое возведение (exponentiation by squaring) опирается на тождество `x^n = (x^(n/2))^2`: посчитав `x^(n/2)` **один раз**, мы получаем `x^n` всего одним умножением. Так показатель уменьшается вдвое на каждом шаге.

```java
double power(double x, int n) {
    if (n == 0) return 1;
    if (n < 0) return 1.0 / power(x, -n);
    if (n % 2 == 0) {
        double half = power(x, n / 2);
        return half * half; // ОДНО умножение вместо n/2
    }
    return x * power(x, n - 1);
}
```

Поскольку показатель делится пополам, число шагов — `O(log n)` вместо `O(n)`. Это видно из рекуррентного соотношения `T(n) = T(n/2) + O(1)`. Отдельные ветки в коде обрабатывают граничные случаи: `n == 0` (база), `n < 0` (берём обратное) и нечётный `n` (снимаем один множитель и переходим к чётному).

**Где применяется:** RSA-шифрование (возведение по модулю в огромную степень), быстрое возведение матриц в степень — например, чтобы считать числа Фибоначчи за `O(log n)`.

## Q14. Как развернуть строку рекурсивно?

Идея: развёрнутая строка = развёрнутый «хвост» (всё, кроме первого символа) + первый символ в конце. Базовый случай — строка из 0–1 символа, она уже «развёрнута».

```java
String reverseRec(String s) {
    if (s.length() <= 1) return s;
    return reverseRec(s.substring(1)) + s.charAt(0);
}
```

**Подводный камень — скрытая `O(n²)`.** Кроме `O(n)` времени и `O(n)` стека, эта версия на каждом шаге создаёт новую подстроку через `substring(1)` и конкатенирует строки — обе операции линейны, а делаются `n` раз, поэтому суммарно `O(n²)` по времени и мусору. Это учебный пример, но **для production не годится** — `StringBuilder.reverse()` делает то же за `O(n)` без рекурсии.

## Q15. Как рекурсивно обойти файловую систему?

Файловая система рекурсивна по своей природе: директория содержит файлы и другие директории. Поэтому обход естественно пишется рекурсией — для каждого элемента: файл печатаем, директорию печатаем и спускаемся в неё тем же методом.

```java
void traverse(File dir, int depth) {
    File[] files = dir.listFiles();
    if (files == null) return;
    for (File f : files) {
        String indent = "  ".repeat(depth);
        if (f.isDirectory()) {
            System.out.println(indent + "[DIR]  " + f.getName());
            traverse(f, depth + 1);
        } else {
            System.out.println(indent + "[FILE] " + f.getName());
        }
    }
}

// Современный вариант через NIO Stream
void traverseNio(Path root) throws IOException {
    try (Stream<Path> stream = Files.walk(root)) {
        stream.forEach(p -> {
            String type = Files.isDirectory(p) ? "[DIR] " : "[FILE]";
            System.out.println(type + root.relativize(p));
        });
    }
}
```

Современный вариант через NIO предпочтительнее: `Files.walk()` внутри реализует **итеративный DFS** через явный стек, поэтому даже очень глубокая иерархия не вызовет `StackOverflowError`, в отличие от наивной рекурсии. Дополнительный плюс — обход возвращает ленивый `Stream<Path>`, который нужно закрывать (отсюда `try-with-resources`).

## Q16. (!) Как рекурсивно реализовать все обходы дерева?

Все три обхода — это одна и та же рекурсия по поддеревьям; различается только **момент, когда мы обрабатываем сам узел** относительно спуска влево и вправо. Базовый случай везде один — `node == null` (пустое поддерево, делать нечего).

- **Preorder** (`root → L → R`): обрабатываем узел до спуска — удобно копировать/сериализовать дерево.
- **Inorder** (`L → root → R`): для BST даёт элементы в отсортированном порядке.
- **Postorder** (`L → R → root`): обрабатываем узел после детей — удобно удалять дерево или считать значения снизу вверх.

```java
// Preorder: root → L → R
void preorder(TreeNode node) {
    if (node == null) return;
    process(node);
    preorder(node.left);
    preorder(node.right);
}

// Inorder: L → root → R
void inorder(TreeNode node) {
    if (node == null) return;
    inorder(node.left);
    process(node);
    inorder(node.right);
}

// Postorder: L → R → root
void postorder(TreeNode node) {
    if (node == null) return;
    postorder(node.left);
    postorder(node.right);
    process(node);
}
```

Каждый узел посещается ровно один раз — `O(n)` по времени, а память — `O(h)` (высота дерева) на кадры стека: на сбалансированном дереве это `O(log n)`, на вырожденном (список) — `O(n)`.

Подробнее — в [Деревья](../data-structures/trees-interview.md).

## Q17. (!) Как рекурсивно найти высоту дерева?

Высота дерева = `1 + максимум из высот левого и правого поддеревьев`. Рекурсия спускается до листьев, а базовый случай — пустое поддерево (`root == null`) высотой `0`, от которого высоты «собираются» обратно вверх.

```java
int height(TreeNode root) {
    if (root == null) return 0;
    return 1 + Math.max(height(root.left), height(root.right));
}
```

Это постфиксный (postorder) обход: значение узла нельзя посчитать, пока не известны высоты обоих детей. Сложность — `O(n)` по времени (каждый узел один раз) и `O(h)` по стеку.

## Q18. (!) Как зеркально отразить (инвертировать) дерево?

Инвертировать дерево — значит в каждом узле поменять местами левое и правое поддерево. Рекурсия делает это снизу вверх: сначала инвертирует оба поддерева, затем переставляет их у текущего узла. Базовый случай — `root == null`.

```java
TreeNode invertTree(TreeNode root) {
    if (root == null) return null;
    TreeNode left = invertTree(root.left);
    TreeNode right = invertTree(root.right);
    root.left = right;
    root.right = left;
    return root;
}
```

Сложность — `O(n)` по времени и `O(h)` по стеку. Задача знаменита байкой: Max Howell, автор Homebrew, не смог решить её на интервью в Google — хороший повод довести этот короткий рекурсивный паттерн до автоматизма.

## Q19. Как реализовать DFS на графе рекурсивно?

DFS (поиск в глубину) на графе — почти то же, что обход дерева, с одним важным отличием: в графе возможны циклы, поэтому нужен массив `visited`, иначе обход зациклится. Из текущей вершины рекурсивно заходим во всех непосещённых соседей.

```java
void dfs(List<List<Integer>> adj, int u, boolean[] visited) {
    visited[u] = true;
    process(u);
    for (int v : adj.get(u)) {
        if (!visited[v]) dfs(adj, v, visited);
    }
}
```

Сложность — `O(V + E)` по времени (каждую вершину и каждое ребро смотрим один раз) и `O(V)` по стеку в худшем случае (длинная цепочка вершин). Для графов с миллионами вершин рекурсия рискует переполнить стек, поэтому DFS переписывают итеративно через явный стек.

## Q20. (!) Что такое recursion tree (дерево рекурсии)?

**Дерево рекурсии** — это схема, на которой нарисованы **все** рекурсивные вызовы и их вложенность. Она превращает абстрактную рекурсию в наглядную структуру, по которой удобно рассуждать о сложности и корректности.

- **Корень** — исходный вызов.
- **Дети узла** — вызовы, которые он порождает.
- **Листья** — базовые случаи (рекурсия дальше не идёт).

Зачем строят дерево рекурсии:

- **Анализ сложности по времени** — общее число узлов равно числу вызовов, а сумма работы во всех узлах и есть итоговая сложность.
- **Поиск повторных вычислений** — если одинаковые подзадачи встречаются в разных узлах (как `fib(3)` в Q9), значит, помогут memoization / DP.
- **Оценка глубины стека** — высота дерева равна максимальной глубине рекурсии, то есть пиковому расходу стека.

Например, дерево рекурсии для `mergeSort(0..7)`:

- `mergeSort(0..7)` → `mergeSort(0..3)` и `mergeSort(4..7)`
- `mergeSort(0..3)` → `mergeSort(0..1)` и `mergeSort(2..3)`
- `mergeSort(4..7)` → `mergeSort(4..5)` и `mergeSort(6..7)`

Такое дерево сразу даёт оценку для Merge Sort: вход делится пополам, поэтому уровней `log n`, а на каждом уровне суммарно `O(n)` работы на слияние — итого `O(n log n)`.

## Q21. Как анализировать сложность рекурсии?

Сложность рекурсии нельзя оценить «на глаз» — её выражают через рекуррентное соотношение, а затем решают одним из методов. Общий порядок действий:

1. **Записать рекуррентное соотношение (recurrence relation)** — выразить время `T(n)` через время на подзадачах, например `T(n) = a · T(n/b) + f(n)`, где `a` — число подзадач, `n/b` — их размер, `f(n)` — работа вне рекурсии.
2. **Master theorem** — если соотношение имеет вид выше, теорема сразу даёт ответ по соотношению `f(n)` и `n^(log_b a)`.
3. **Дерево рекурсии** — нарисовать вызовы и просуммировать работу по уровням (как в Q20); работает и там, где master theorem неприменима.
4. **Метод подстановки (substitution method)** — угадать оценку и доказать её индукцией.

Подробнее — в [Анализ сложности](../complexity/complexity-analysis-interview.md) и [Divide and Conquer](divide-and-conquer-interview.md).

## Q22. (!) Когда рекурсия даёт StackOverflowError?

`StackOverflowError` возникает, когда глубина рекурсии превышает размер стека потока. В JVM стек — примерно `512KB-1MB`, один кадр занимает `~50-100 байт`, поэтому предел — порядка `5K-20K` вложенных вызовов. Всё, что делает рекурсию слишком глубокой, ведёт к ошибке.

**Типичные причины:**

1. **Глубокая линейная рекурсия** — глубина растёт линейно с входом: `factorial(100000)`, `sum(arr)` на большом массиве.
2. **Бесконечная рекурсия** — забыли базовый случай или шаг не приближает к нему, глубина не ограничена.
3. **Глубокие структуры данных** — обход вырожденного дерева или связного списка из `10⁶` узлов (каждый узел = кадр).
4. **Взаимная рекурсия (mutual recursion)** без базового случая — две функции бесконечно зовут друг друга.

**Как защититься** (по убыванию надёжности):

- **Преобразовать в итерацию** — стек вызовов вообще не используется.
- **Использовать явный стек** в куче — глубина ограничена только памятью кучи.
- **Увеличить `-Xss`** — отодвигает лимит, но не убирает его.
- **Project Loom (виртуальные потоки)** — растущий стек снимает практическое ограничение по глубине.

## Q23. (!) Memoization — что это и зачем?

**Memoization** — это кеширование результатов рекурсивных вызовов: первый раз подзадача считается и её ответ сохраняется (обычно в `Map` или массив), а при повторном обращении берётся готовое значение вместо пересчёта. Приём имеет смысл, когда рекурсия многократно решает **одни и те же** подзадачи.

```java
Map<Integer, Integer> memo = new HashMap<>();

int fib(int n) {
    if (n <= 1) return n;
    if (memo.containsKey(n)) return memo.get(n);
    int result = fib(n - 1) + fib(n - 2);
    memo.put(n, result);
    return result;
}
```

Эффект драматичен: каждая подзадача теперь считается **ровно один раз**, поэтому экспоненциальная рекурсия Фибоначчи (`O(2^n)`) превращается в полиномиальную (`O(n)`). По сути это и есть динамическое программирование сверху вниз (**DP top-down**) — та же идея, что и bottom-up DP, только подзадачи решаются по требованию через рекурсию.

**Условие применимости:** подзадачи должны **перекрываться**. Если каждый вызов уникален (как в простом обходе дерева), кеш бесполезен. Подробнее — [DP](dynamic-programming-interview.md).

## Q24. Как преобразовать рекурсию в итерацию?

Способ зависит от **формы** рекурсии — есть несколько типовых преобразований, от тривиального цикла до явной структуры данных, заменяющей стек вызовов:

1. **Линейная рекурсия → цикл** — один рекурсивный вызов на шаге легко разворачивается в `for`/`while` (factorial, sum).
2. **Хвостовая рекурсия → while-loop** — аккумулятор из параметра становится переменной цикла (sum с `acc`).
3. **DFS на дереве/графе → явный stack** — кадры вызовов заменяет `Deque`, куда вручную кладём узлы.
4. **BFS на дереве → queue** — обход по уровням реализуется очередью вместо рекурсии.
5. **Memoized recursion → таблица bottom-up DP** — вместо вызовов по требованию заполняем таблицу в правильном порядке.

```java
// Рекурсия
int fact(int n) {
    if (n <= 1) return 1;
    return n * fact(n - 1);
}

// Итерация
int factIter(int n) {
    int result = 1;
    for (int i = 2; i <= n; i++) result *= i;
    return result;
}
```

**Когда не стоит:** для сложных обходов (Sudoku Solver, деревья) итеративный код с ручным стеком получается заметно менее читаемым, чем рекурсия. Если глубина заведомо невелика и `StackOverflowError` не грозит — оставляют рекурсию ради ясности.

## Q25. (!) Чем рекурсия отличается от backtracking?

**Backtracking — это частный случай рекурсии с откатом (undo).** Обычная рекурсия просто спускается по подзадачам и собирает ответ. В backtracking мы на каждом шаге **меняем общее состояние** (выбираем вариант), рекурсивно идём вглубь, а затем **откатываем изменение** и пробуем следующий вариант. Откат после вызова — ключевое отличие, которое позволяет перебирать все возможные конфигурации, не плодя их копий.

```java
// Чистая рекурсия (без backtracking)
int sumTree(TreeNode node) {
    if (node == null) return 0;
    return node.val + sumTree(node.left) + sumTree(node.right);
}

// Backtracking
void permute(int[] nums, List<Integer> current, ...) {
    if (current.size() == nums.length) { result.add(new ArrayList<>(current)); return; }
    for (int i = 0; i < nums.length; i++) {
        if (used[i]) continue;
        used[i] = true; current.add(nums[i]);
        permute(nums, current, ...);
        used[i] = false; current.remove(current.size() - 1); // ← BACKTRACK
    }
}
```

Подробнее — в [Backtracking](backtracking-interview.md).

## Q26. Что такое взаимная рекурсия (mutual recursion)?

**Взаимная (mutual) рекурсия** — это когда две или больше функций вызывают друг друга по кругу, а не напрямую самих себя. Задача всё так же сводится к меньшей версии, просто «эстафету» подхватывает другая функция. Базовый случай по-прежнему обязателен — иначе цикл вызовов не остановится.

```java
boolean isEven(int n) {
    if (n == 0) return true;
    return isOdd(n - 1);
}

boolean isOdd(int n) {
    if (n == 0) return false;
    return isEven(n - 1);
}
```

В примере `isEven` и `isOdd` определены друг через друга: чётность `n` сводится к нечётности `n-1` и наоборот. Где это встречается на практике:

- **Парсеры** — recursive descent, где правила грамматики ссылаются друг на друга (выражение → терм → множитель → выражение).
- **State machines** — переходы между состояниями как взаимные вызовы.
- **Game AI** — minimax, где ход максимизирующего игрока чередуется с ходом минимизирующего (`maximizer` ↔ `minimizer`).

## Q27. (!) Где рекурсия применяется в production?

Закономерность одна: рекурсия появляется везде, где данные имеют **древовидную или вложенную структуру**, потому что обход такой структуры естественно выражается через обход её частей.

1. **Парсеры** — recursive descent для JSON, XML, арифметических выражений.
2. **Файловая система** — обходы директорий (директория содержит директории).
3. **JSON/XML traversal** — Jackson, Gson рекурсивно обходят дерево узлов.
4. **Spring DI** — разрешение зависимостей бинов (bean зависит от других бинов).
5. **Компиляторы** — обход AST, проверка типов.
6. **Планы запросов БД** — оптимизатор рекурсивно перебирает варианты планов.
7. **Алгоритмы GC** — обход графа достижимых объектов по ссылкам.
8. **Игровые движки** — обход scene graph.
9. **Маршрутизация HTTP-запросов** — цепочка middleware (в некоторых реализациях).
10. **Обходчики файловой системы** — `Files.walk`, `File.listFiles`.
