# Вопросы на собеседовании: `Жадные алгоритмы (Greedy)`

Жадные алгоритмы делают **локально оптимальный выбор** на каждом шаге, надеясь на глобальный оптимум. Когда работают — изящны и быстры (`O(n log n)` обычно). Когда нет — нужен DP. На интервью важно отличать «когда greedy работает» и **доказывать** корректность через **exchange argument**.

## Q1. (!) Что такое жадный алгоритм?

**Greedy algorithm** на каждом шаге делает **локально оптимальный** выбор — берёт то, что выглядит лучшим прямо сейчас, — и больше к этому выбору не возвращается, надеясь, что цепочка локальных оптимумов сложится в глобальный.

Ключевое отличие от других парадигм: нет ни перебора альтернатив, ни отката назад. Greedy идёт «вперёд и без оглядки», поэтому он быстрый — но именно поэтому работает не всегда.

**Как выглядит жадное решение на практике:**
- Сначала часто **сортируем** вход по ключевому критерию (по концу интервала, по ratio, по частоте).
- Идём по элементам один раз и на каждом делаем **жадный выбор**.
- Уже принятые решения не пересматриваем.

**Каркас рассуждения** (его и ждут на собеседовании):
1. Сформулировать **жадный выбор** — что брать первым и почему.
2. Доказать, что этот выбор **не противоречит** какому-нибудь оптимуму (обычно через exchange argument).
3. Показать, что после выбора остаётся **подзадача того же типа** меньшего размера — и к ней применима та же стратегия.

## Q2. (!) Что такое greedy choice property?

**Greedy choice property** — свойство задачи, при котором глобальный оптимум можно собрать из **локально оптимальных** выборов: на каждом шаге берём «лучший по критерию» элемент, и итог гарантированно оптимален.

Это **необходимое условие** применимости greedy. Если его нет — жадный алгоритм может промахнуться мимо оптимума, и нужен перебор (DP). DP это свойство не требует именно потому, что честно рассматривает все варианты, а не доверяет одному «лучшему» шагу.

Содержательно property означает: оптимальное решение **всегда можно начать** с жадного выбора. Если же оптимум иногда вынужден отказаться от «лучшего сейчас» ради выгоды позже — property не выполняется.

**Есть greedy choice property** (greedy даёт оптимум):
- Activity Selection — выбор активности с минимальным концом
- Huffman — слияние пары наименьших частот
- Fractional Knapsack — выбор по убыванию value/weight ratio
- Dijkstra — выбор непосещённой вершины с минимальным расстоянием
- Kruskal — добавление минимального безопасного ребра

**Нет greedy choice property** (нужен DP):
- 0/1 Knapsack — оптимум может не содержать самый выгодный предмет
- Longest Common Subsequence — локальное совпадение не предсказывает глобальное
- TSP — нужен DP с битмаской

## Q3. (!) Чем Greedy отличается от DP?

Коротко: **обе парадигмы требуют optimal substructure**, но greedy дополнительно полагается на greedy choice property — что один локально лучший шаг никогда не закрывает дорогу к оптимуму. Там, где это неверно, greedy ошибается, и приходится перебирать варианты через DP.

| Критерий | Greedy | DP |
|----------|--------|-----|
| Выбор | Локально оптимальный, без отката | Перебор всех вариантов |
| Оптимальность | Не всегда гарантирует | Всегда оптимум (если применим) |
| Сложность | `O(n log n)` или `O(n)` обычно | Полиномиальная (часто `O(n²)` или больше) |
| Память | `O(1)` или `O(n)` | `O(n)` или `O(n·k)` |
| Компромисс | Скорость в обмен на риск промаха | Гарантия в обмен на время и память |
| Применимость | Greedy choice property | Optimal substructure + overlapping subproblems |

**Когда выбирать greedy:**
- Корректность доказана (или это известная классическая задача).
- Нужна максимальная скорость и/или минимум памяти.
- DP-таблица не помещается в память.

**Эмпирическое правило:** если сомневаешься в корректности greedy — ищи контрпример. Не нашёл и смог обосновать exchange argument'ом → greedy; нашёл → DP.

## Q4. Как доказать корректность жадного алгоритма?

Самый частый метод — **exchange argument** (аргумент обмена). Идея: берём любой оптимум и шаг за шагом «переделываем» его в жадное решение, не теряя оптимальности. Раз так можно — жадное решение тоже оптимально.

**Схема exchange argument:**
1. Предположим, какой-то оптимум `OPT` отличается от жадного `G`.
2. Найдём **первое** место, где они расходятся.
3. Покажем, что заменив здесь выбор `OPT` на выбор `G`, мы **не ухудшаем** решение (получаем не менее хороший оптимум).
4. Повторяя обмены, превращаем `OPT` в `G` → значит, `G` тоже оптимален.

**Пример (Activity Selection):** greedy берёт активность с минимальным временем конца. Если `OPT` начал с другой — её можно заменить на жадную: та завершается **не позже**, значит освобождает не меньше места для оставшихся активностей. Обмен не уменьшает их число → оптимум сохраняется.

**Альтернатива — индукция:** доказываем, что после каждого шага «уже сделанный жадный выбор + оптимальное решение остатка» по-прежнему даёт глобальный оптимум.

## Q5. (!) Как решить Activity Selection (выбор максимума неперекрывающихся активностей)?

**Задача:** дано `n` активностей с интервалами `[start, end]`; нужно выбрать **максимальное число** таких, что они **попарно не пересекаются**.

**Жадная стратегия:** сортируем активности по времени **конца** и идём по порядку, добавляя активность, если она начинается не раньше конца последней выбранной.

**Почему именно по концу:** активность, которая заканчивается раньше всех, освобождает максимум времени для остальных — это и есть жадный выбор, который никогда не мешает оптимуму (доказательство — exchange argument из Q4).

```java
record Activity(int start, int end) {}

List<Activity> selectActivities(List<Activity> activities) {
    activities.sort(Comparator.comparingInt(Activity::end));

    List<Activity> selected = new ArrayList<>();
    int lastEnd = Integer.MIN_VALUE;

    for (Activity a : activities) {
        if (a.start() >= lastEnd) {
            selected.add(a);
            lastEnd = a.end();
        }
    }
    return selected;
}
```

**Сложность:** `O(n log n)` — доминирует сортировка; сам проход линеен.

**Типичная ошибка:** сортировать по времени **начала** или по длительности. Оба варианта дают контрпримеры — оптимален именно критерий «минимальный конец».

## Q6. (!) Fractional Knapsack — почему здесь greedy работает?

**Задача:** рюкзак вместимости `capacity`, предметы с весом и ценностью; можно брать **долю** предмета. Цель — максимум суммарной ценности.

**Решение:** сортируем предметы по убыванию **удельной ценности** `value/weight` (ratio) и набираем их подряд; последний предмет добиваем дробной долей до заполнения рюкзака. Этот жадный выбор по ratio даёт **гарантированный оптимум**.

```java
record Item(double weight, double value) {
    double ratio() { return value / weight; }
}

double fractionalKnapsack(Item[] items, double capacity) {
    Arrays.sort(items, (a, b) -> Double.compare(b.ratio(), a.ratio()));

    double totalValue = 0, remaining = capacity;
    for (Item item : items) {
        if (remaining <= 0) break;
        if (item.weight() <= remaining) {
            totalValue += item.value();
            remaining -= item.weight();
        } else {
            totalValue += item.ratio() * remaining;
            remaining = 0;
        }
    }
    return totalValue;
}
```

**Почему работает:** каждая единица веса самого «выгодного» предмета приносит максимум ценности — значит, заполнять рюкзак выгодно именно в порядке убывания ratio. Возможность **дробить** снимает ограничение «целиком или ничего»: если предмет не помещается полностью, мы берём его лучшую долю, не теряя ни единицы вместимости впустую. Поэтому greedy choice property тут выполняется.

**Контраст с 0/1:** именно дробление и делает задачу жадной. В целочисленной версии (Q7) этого рычага нет — и greedy ломается.

**Сложность:** `O(n log n)`.

## Q7. (!) 0/1 Knapsack — почему здесь greedy НЕ работает?

В **целочисленной** задаче каждый предмет берётся **целиком или никак** — дробить нельзя. Из-за этого жадный выбор по `value/weight` **перестаёт давать оптимум**. Контрпример:

```
Items: A (weight=10, value=60),  B (weight=20, value=100), C (weight=30, value=120)
Capacity: 50

Greedy (по ratio):
  A ratio = 6, B ratio = 5, C ratio = 4
  Берём A → 10, B → 30, C не помещается → total = 60 + 100 = 160

Optimum (DP):
  Берём B + C → 20 + 30 = 50, value = 100 + 120 = 220
```

Здесь **greedy choice property не выполняется**: оптимум (`B + C = 220`) вообще не содержит самый выгодный по ratio предмет `A`. Взять `A` означает «забить» 10 единиц веса так, что оставшихся 40 не хватает на по-настоящему ценную пару. Жадность смотрит только на удельную выгоду и не видит этой ловушки — поэтому нужен **DP**, который перебирает «брать / не брать» для каждого предмета (см. [Динамическое программирование](dynamic-programming-interview.md)).

## Q8. (!) Coin Change — когда greedy даёт минимум монет?

**Greedy (бери самый крупный подходящий номинал) гарантированно оптимален только для канонических систем монет.** Для произвольных номиналов он может выдать больше монет, чем нужно.

```
Канонические (greedy работает):
  USD: [1, 5, 10, 25] — для 30: 25 + 5 = 2 монеты
  EUR: [1, 2, 5, 10, 20, 50, 100, 200]

Неканонические (greedy НЕ работает):
  [1, 3, 4] — для 6: greedy = 4 + 1 + 1 = 3 монеты, optimum = 3 + 3 = 2 монеты
```

**Теорема Pearson** даёт точный критерий каноничности. Для `[1, 5, 10, 25]` он выполняется → greedy верен. Для произвольных номиналов гарантий нет → нужен DP (см. [Динамическое программирование](dynamic-programming-interview.md)).

**На собеседовании:** если система монет дана и нестандартна — не доверяй greedy, сразу думай про DP либо проверь её на маленьком контрпримере вроде `[1, 3, 4]` для суммы 6.

```java
// Greedy (работает для US coins)
int coinChangeGreedy(int amount) {
    int[] coins = {25, 10, 5, 1};
    int count = 0;
    for (int c : coins) {
        count += amount / c;
        amount %= c;
    }
    return count;
}
```

## Q9. (!) Как работает Huffman Coding?

Huffman — жадный алгоритм **сжатия без потерь** (lossless). Он строит **префиксный код** (ни одно кодовое слово не является префиксом другого, поэтому декодирование однозначно) с **минимальной средней длиной** при данных частотах символов: частым буквам — короткие коды, редким — длинные.

**Жадная стратегия:** на каждом шаге берём **две наименее частые** буквы (или поддерева) и объединяем их в новый узел с суммарной частотой. Повторяем, пока не останется один узел — корень дерева. Жадный выбор «слить самую редкую пару» оптимален, потому что эти символы заведомо окажутся на самой глубине дерева, то есть получат самые длинные коды.

```java
record Node(char ch, int freq, Node left, Node right) {}

Node buildHuffman(Map<Character, Integer> freqs) {
    PriorityQueue<Node> pq = new PriorityQueue<>(Comparator.comparingInt(Node::freq));
    freqs.forEach((ch, f) -> pq.offer(new Node(ch, f, null, null)));

    while (pq.size() > 1) {
        Node a = pq.poll();
        Node b = pq.poll();
        pq.offer(new Node('\0', a.freq + b.freq, a, b));
    }
    return pq.poll();
}

// Кодируем: левое = 0, правое = 1
Map<Character, String> buildCodes(Node root) {
    Map<Character, String> codes = new HashMap<>();
    dfs(root, "", codes);
    return codes;
}

void dfs(Node node, String code, Map<Character, String> codes) {
    if (node == null) return;
    if (node.ch != '\0') codes.put(node.ch, code);
    dfs(node.left, code + "0", codes);
    dfs(node.right, code + "1", codes);
}
```

**Сложность:** `O(n log n)` — каждое из `n` слияний работает с priority queue за `O(log n)`. Применяется в **gzip, JPEG, MP3, Brotli**.

## Q10. (!) Алгоритм Дейкстры — это greedy?

**Да, Дейкстра — классический жадный алгоритм.** На каждом шаге он «фиксирует» непосещённую вершину с **минимальным** текущим расстоянием от источника — это и есть жадный выбор.

**Почему работает (при неотрицательных весах):** когда вершина выбрана как ближайшая из оставшихся, её расстояние уже **финальное**. Любой другой путь к ней идёт через ещё не обработанную вершину, которая дальше, а значит добавление неотрицательных рёбер сделает обходной путь только длиннее — короче не станет.

**Почему ломается на отрицательных рёбрах:** жадность опирается ровно на это «добавление ребра не уменьшает длину». Отрицательное ребро нарушает гарантию: уже зафиксированное расстояние может оказаться завышенным, ведь позже найдётся более короткий путь через отрицательное ребро. Для таких графов берут Bellman-Ford.

Подробнее — в [Графы](../data-structures/graphs-interview.md).

## Q11. (!) Как алгоритмы Краскала и Прима строят MST и почему они жадные?

Оба строят **минимальное остовное дерево** (MST) жадно, добавляя рёбра по возрастанию веса, но по-разному организуют выбор:

- **Kruskal:** сортируем все рёбра по весу и добавляем очередное минимальное, **если оно не образует цикл** (проверка через Union-Find). Растим лес, который сливается в одно дерево.
- **Prim:** растим **одно связное** дерево из стартовой вершины, на каждом шаге добавляя самое лёгкое ребро, выходящее наружу из уже построенной части.

**Почему оба корректны — cut property:** для любого разреза графа (разбиения вершин на две части) **минимальное ребро, пересекающее разрез, принадлежит некоторому MST**. И Kruskal, и Prim на каждом шаге добавляют именно такое безопасное ребро, поэтому их жадный выбор никогда не противоречит оптимуму.

Подробнее — в [Графы](../data-structures/graphs-interview.md).

## Q12. (!) Как решить Job Sequencing с дедлайнами?

**Задача:** `n` задач, у каждой дедлайн и profit; каждая занимает 1 единицу времени, одновременно выполняется одна. Нужно выбрать подмножество и порядок, максимизирующие суммарный profit.

**Жадная стратегия:** сортируем задачи по **убыванию profit** и для каждой ставим её в **самый поздний свободный слот** не позже её дедлайна. Поздний слот выбираем намеренно — он оставляет ранние слоты свободными для будущих (менее прибыльных) задач с жёсткими дедлайнами.

```java
record Job(int id, int deadline, int profit) {}

int maxProfit(Job[] jobs) {
    Arrays.sort(jobs, (a, b) -> b.profit() - a.profit()); // по убыванию profit

    int maxDeadline = Arrays.stream(jobs).mapToInt(Job::deadline).max().getAsInt();
    boolean[] slot = new boolean[maxDeadline + 1];
    int totalProfit = 0;

    for (Job j : jobs) {
        for (int t = j.deadline(); t > 0; t--) { // ищем свободный слот <= deadline
            if (!slot[t]) {
                slot[t] = true;
                totalProfit += j.profit();
                break;
            }
        }
    }
    return totalProfit;
}
```

**Сложность:** `O(n²)` — для каждой задачи в худшем случае линейный поиск слота. Через Union-Find (быстрый переход к ближайшему свободному слоту) ускоряется до `O(n log n)`.

## Q13. Как найти минимальное число переговорных (Minimum Meeting Rooms)?

**Задача:** `n` встреч с интервалами `[start, end]`; нужно минимальное число комнат, чтобы провести все, ни разу не наложив две встречи на одну комнату. Ответ равен **максимальному числу одновременно идущих встреч**.

**Жадная идея:** разделяем все начала и концы, сортируем их и идём по оси времени. Каждое начало занимает комнату, каждый конец — освобождает. Достаточно отслеживать пиковое число занятых комнат.

```java
int minMeetingRooms(int[][] intervals) {
    int n = intervals.length;
    int[] starts = new int[n], ends = new int[n];
    for (int i = 0; i < n; i++) {
        starts[i] = intervals[i][0];
        ends[i] = intervals[i][1];
    }
    Arrays.sort(starts);
    Arrays.sort(ends);

    int rooms = 0, endIdx = 0;
    for (int i = 0; i < n; i++) {
        if (starts[i] < ends[endIdx]) rooms++;
        else                           endIdx++;
    }
    return rooms;
}
```

**Сложность:** `O(n log n)` — доминирует сортировка начал и концов. Альтернатива: **min-heap** по времени конца текущих встреч (размер кучи и есть число комнат).

## Q14. Как решить Task Scheduler с cooldown?

**Задача:** дан список задач; между двумя выполнениями **одинаковой** задачи должен пройти cooldown в `n` тактов (иначе — простой). Нужно минимальное время выполнения всех задач.

**Жадная идея:** в каждый такт запускаем **самую частую из доступных** задач (max-heap по оставшемуся количеству) — так мы быстрее «разреживаем» самые проблемные задачи и сокращаем простои. Реализация — в [Кучи](../data-structures/heaps-interview.md).

## Q16. (!) Как объединить пересекающиеся интервалы (Merge Intervals)?

**Задача:** дан набор интервалов `[start, end]`; объединить все пересекающиеся в максимальные непрерывные.

**Жадная идея:** сортируем по **началу** и идём слева направо. Если очередной интервал начинается не позже конца текущего — они пересекаются, расширяем текущий до максимального конца. Иначе закрываем текущий и начинаем новый. Сортировка по началу гарантирует, что все «соседи» по перекрытию идут подряд.

```java
int[][] merge(int[][] intervals) {
    if (intervals.length == 0) return intervals;
    Arrays.sort(intervals, (a, b) -> a[0] - b[0]);

    List<int[]> result = new ArrayList<>();
    int[] current = intervals[0];
    result.add(current);

    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] <= current[1]) {
            current[1] = Math.max(current[1], intervals[i][1]); // merge
        } else {
            current = intervals[i];
            result.add(current);
        }
    }
    return result.toArray(new int[result.size()][]);
}
```

`O(n log n)` — доминирует сортировка.

## Q17. (!) Как вставить интервал в отсортированный набор (Insert Interval)?

**Задача:** дан **уже отсортированный** по началу набор непересекающихся интервалов и новый интервал; вставить его, слив с пересекающимися.

**Жадная идея (три фазы за один проход):**
1. Копируем все интервалы, целиком лежащие **левее** нового.
2. Все **пересекающиеся** с новым сливаем в него (расширяем границы по min/max).
3. Копируем оставшийся «хвост» правее.

Так как вход уже отсортирован, **сортировка не нужна** — отсюда `O(n)`.

```java
int[][] insert(int[][] intervals, int[] newInterval) {
    List<int[]> result = new ArrayList<>();
    int i = 0;

    // 1. До newInterval
    while (i < intervals.length && intervals[i][1] < newInterval[0]) {
        result.add(intervals[i++]);
    }
    // 2. Слияние с newInterval
    while (i < intervals.length && intervals[i][0] <= newInterval[1]) {
        newInterval[0] = Math.min(newInterval[0], intervals[i][0]);
        newInterval[1] = Math.max(newInterval[1], intervals[i][1]);
        i++;
    }
    result.add(newInterval);
    // 3. После
    while (i < intervals.length) result.add(intervals[i++]);

    return result.toArray(new int[result.size()][]);
}
```

`O(n)` — без сортировки, intervals уже отсортированы.

## Q18. Как найти минимум интервалов для удаления (Non-overlapping Intervals)?

**Задача:** дан набор интервалов; удалить **минимальное** их число так, чтобы оставшиеся не пересекались.

**Жадная идея:** это Activity Selection наизнанку. Сортируем по **концу** и жадно оставляем максимум совместимых интервалов (как в Q5); всё, что не влезло, и есть удалённые. Сортировка по концу гарантирует, что мы сохраняем интервалы, освобождающие максимум места.

```java
int eraseOverlapIntervals(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> a[1] - b[1]); // по концу

    int end = Integer.MIN_VALUE, removed = 0;
    for (int[] i : intervals) {
        if (i[0] >= end) end = i[1];
        else              removed++;
    }
    return removed;
}
```

Та же логика, что и Activity Selection, только считаем «лишние», а не «выбранные». **Сложность:** `O(n log n)`.

## Q19. Как найти минимум стрел, чтобы лопнуть все шары (Minimum Arrows)?

**Задача:** каждый шар задан горизонтальным отрезком `[xstart, xend]`; вертикальная стрела в координате `x` лопает все шары, чьи отрезки её пересекают. Нужно минимальное число стрел.

**Жадная идея:** сортируем шары по **правому концу** и стреляем по концу первого ещё не лопнутого шара — эта стрела заодно лопает все шары, что пересекают эту координату. Стрелять по самому раннему концу оптимально: он гарантированно входит в максимум перекрывающихся шаров.

```java
int findMinArrowShots(int[][] points) {
    Arrays.sort(points, (a, b) -> Integer.compare(a[1], b[1])); // по концу

    int arrows = 1, end = points[0][1];
    for (int i = 1; i < points.length; i++) {
        if (points[i][0] > end) {
            arrows++;
            end = points[i][1];
        }
    }
    return arrows;
}
```

**Связь с Q18:** та же жадная схема на интервалах — сортировка по концу и минимизация числа «точек», покрывающих все интервалы. Разница только в том, что касание концами здесь считается пересечением (`>` вместо `>=`).

## Q20. (!) Как решить Jump Game (достижим ли конец массива)?

**Задача:** массив `nums`, где `nums[i]` — максимальная длина прыжка из позиции `i`. Можно ли допрыгать с начала до последнего индекса?

**Жадная идея:** идём слева направо и держим `maxReach` — самый дальний достижимый индекс. На каждой позиции, если она вообще достижима (`i <= maxReach`), обновляем `maxReach`. Как только текущий индекс обгоняет `maxReach` — дальше пути нет, возвращаем false. Это работает, потому что достаточно знать **самый дальний** охват, а не конкретный путь.

```java
boolean canJump(int[] nums) {
    int maxReach = 0;
    for (int i = 0; i < nums.length; i++) {
        if (i > maxReach) return false;
        maxReach = Math.max(maxReach, i + nums[i]);
    }
    return true;
}
```

**Сложность:** `O(n)`, память `O(1)` — один проход с единственной переменной `maxReach`.

## Q21. Как найти минимум прыжков в Jump Game II?

**Задача:** тот же массив прыжков, но конец **точно достижим**; нужно **минимальное число прыжков**, чтобы дойти до него.

**Жадная идея (BFS по уровням за один проход):** считаем массив «уровнями». `currentEnd` — граница текущего уровня (докуда дойдём за `jumps` прыжков), `farthest` — куда дотянемся, если прыгнем из любой точки этого уровня. Дойдя до конца уровня (`i == currentEnd`), делаем прыжок и расширяем границу до `farthest`. Каждый прыжок выбирает максимальный охват — потому это и есть минимум прыжков.

```java
int jump(int[] nums) {
    int jumps = 0, currentEnd = 0, farthest = 0;
    for (int i = 0; i < nums.length - 1; i++) {
        farthest = Math.max(farthest, i + nums[i]);
        if (i == currentEnd) {
            jumps++;
            currentEnd = farthest;
        }
    }
    return jumps;
}
```

**Сложность:** `O(n)`. Ключ — не отслеживать конкретные позиции прыжков, а только границу текущего и следующего «уровня охвата».

## Q22. (!) Gas Station — с какой станции можно объехать круг?

**Задача:** кольцо станций; на станции `i` заправляешься на `gas[i]`, а до следующей тратишь `cost[i]`. С какой станции начать, чтобы объехать круг целиком (или вернуть `-1`, если нельзя)?

**Жадная идея (две проверки за один проход):**
- **Существование решения:** маршрут возможен тогда и только тогда, когда суммарный `gas` ≥ суммарного `cost`. Иначе топлива физически не хватит.
- **Где старт:** ведём текущий бак `currTank`. Если на каком-то участке он ушёл в минус — ни одна станция от прежнего старта до этой точки не годится (на любой из них бак опустеет ещё раньше). Значит сбрасываем бак и пробуем начать со **следующей** станции.

```java
int canCompleteCircuit(int[] gas, int[] cost) {
    int totalTank = 0, currTank = 0, start = 0;
    for (int i = 0; i < gas.length; i++) {
        int diff = gas[i] - cost[i];
        totalTank += diff;
        currTank += diff;
        if (currTank < 0) {
            start = i + 1; // не можем доехать — пробуем со следующей
            currTank = 0;
        }
    }
    return totalTank >= 0 ? start : -1;
}
```

**Сложность:** `O(n)`, память `O(1)`. Гарантия корректности: если итоговый `totalTank ≥ 0`, то старт после последнего «провала» обязательно доезжает до круга.

## Q23. Candy — как раздать минимум конфет детям?

**Задача:** дети в ряд, у каждого рейтинг. Правила: каждому хотя бы 1 конфета; если рейтинг ребёнка **выше соседа**, у него конфет должно быть **строго больше**. Минимизировать суммарное число конфет.

**Жадная идея (два прохода):** одно правило нельзя удовлетворить за один проход, потому что у ребёнка два соседа. Поэтому проходим дважды:
- **Слева направо** — учитываем только левого соседа: если рейтинг растёт, даём на одну конфету больше.
- **Справа налево** — учитываем правого соседа, беря `max` с уже посчитанным, чтобы не сломать первое правило.

Так каждый ребёнок получает минимум, удовлетворяющий **обоим** соседям сразу.

```java
int candy(int[] ratings) {
    int n = ratings.length;
    int[] candies = new int[n];
    Arrays.fill(candies, 1);

    // Слева направо
    for (int i = 1; i < n; i++) {
        if (ratings[i] > ratings[i - 1]) candies[i] = candies[i - 1] + 1;
    }
    // Справа налево
    for (int i = n - 2; i >= 0; i--) {
        if (ratings[i] > ratings[i + 1]) candies[i] = Math.max(candies[i], candies[i + 1] + 1);
    }

    return Arrays.stream(candies).sum();
}
```

**Сложность:** `O(n)` — два линейных прохода. Память `O(n)` под массив конфет (есть вариант `O(1)` через анализ «холмов» — длин возрастающих и убывающих участков).

## Q24. Как решить Partition Labels?

**Задача:** разбить строку на **максимально возможное число** частей так, чтобы каждая буква встречалась только в одной части.

**Жадная идея:** сначала для каждой буквы запоминаем индекс её **последнего** вхождения. Затем идём по строке, поддерживая границу текущего блока `end` = самый поздний «последний индекс» среди уже встреченных букв. Как только текущая позиция достигла `end`, все буквы этого блока больше нигде не появятся — здесь можно резать. Жадно резать при первой возможности и даёт максимум частей.

```java
List<Integer> partitionLabels(String s) {
    int[] lastIndex = new int[26];
    for (int i = 0; i < s.length(); i++) {
        lastIndex[s.charAt(i) - 'a'] = i;
    }

    List<Integer> result = new ArrayList<>();
    int start = 0, end = 0;
    for (int i = 0; i < s.length(); i++) {
        end = Math.max(end, lastIndex[s.charAt(i) - 'a']);
        if (i == end) {
            result.add(end - start + 1);
            start = i + 1;
        }
    }
    return result;
}
```

**Сложность:** `O(n)` плюс `O(1)` на алфавит из 26 букв. Суть — расширять блок до самого позднего вхождения любой буквы внутри и резать в этой точке.

## Q25. (!) Как максимизировать прибыль в Best Time to Buy and Sell Stock II?

**Задача:** массив цен по дням; разрешено **неограниченное** число сделок (но держать не более одной акции одновременно). Максимизировать суммарную прибыль.

**Жадная идея:** суммируем все **положительные** разности соседних дней. Каждый участок роста цены равносилен одной сделке «купил перед ростом — продал после»; разбивать длинный рост на отдельные дни и собирать ровно те же приращения — то же самое, что одна крупная сделка. Падения просто пропускаем (сделок в них нет).

```java
int maxProfit(int[] prices) {
    int profit = 0;
    for (int i = 1; i < prices.length; i++) {
        if (prices[i] > prices[i - 1]) profit += prices[i] - prices[i - 1];
    }
    return profit;
}
```

**Сложность:** `O(n)`, память `O(1)`. Каждый локальный рост = одна сделка «купил вчера — продал сегодня».

## Q26. (!) Как распознать, что задача решается жадно?

Жадный подход стоит подозревать, когда сходятся несколько признаков:

1. Это задача **оптимизации** — что-то максимизировать или минимизировать.
2. На каждом шаге есть **очевидный «локально лучший»** выбор по понятному критерию.
3. Вход можно осмысленно **отсортировать** и обработать в одном порядке.
4. Подзадачи **не перекрываются** — после выбора остаётся независимый «остаток» (если перекрываются — это сигнал в сторону DP).
5. Часто встречается на **интервалах, расписаниях, графах**.

**Как проверить за минуту на собеседовании:**
1. Сформулируй жадный выбор словами.
2. Прогони на двух-трёх маленьких примерах.
3. **Активно ищи контрпример** — это самое важное.
4. Нашёл контрпример → переходи на DP.
5. Не нашёл и можешь обосновать exchange argument'ом → greedy.

## Q27. Какие типичные ошибки делают в greedy?

**Подводные камни:**
1. **Применяют там, где property нет** — например, жадный `0/1 Knapsack` даёт не оптимум; здесь нужен DP.
2. **Берут неверный критерий сортировки** — сортируют по value вместо value/weight, по началу интервала вместо конца. Критерий — половина решения.
3. **Забывают граничные случаи** — пустой вход, один элемент, все элементы равны, нулевые/отрицательные значения.
4. **Не доказывают корректность** — жадный выбор локально хорош, а глобально проигрывает, но это замечают только на скрытых тестах.
5. **«Чинят» решение задним числом** — откатывают и пересматривают прежние выборы. Это уже не greedy, а псевдо-DP без таблицы; либо честный DP, либо корректный greedy.

## Q28. (!) Где жадные алгоритмы применяются в production?

Greedy и его приближённые версии встречаются повсюду, где важна скорость, а точный оптимум либо гарантирован, либо не критичен:

- **Сжатие** — Huffman в gzip/zlib/Brotli.
- **Маршрутизация** — Dijkstra в протоколах OSPF, IS-IS.
- **Сети** — Token bucket для rate limiting.
- **Планирование** — Earliest Deadline First (EDF), планировщики задач в ОС.
- **MST** — проектирование телеком-сетей и электросетей (Kruskal/Prim).
- **Приближённые алгоритмы для NP-hard** — Set Cover, Vertex Cover (greedy даёт гарантированное приближение).
- **Кеширование** — стратегии вытеснения LRU/LFU.
