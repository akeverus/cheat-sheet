# Вопросы на собеседовании: `Графы`

Графы — основа социальных сетей, маршрутизации, зависимостей сборки, рекомендаций. На интервью спрашивают BFS/DFS, Dijkstra, топологическую сортировку, MST, обнаружение циклов и компонент связности. Всё это — `O(V + E)` или `O(E log V)`, и важно понимать когда какой подход применять.

## Q1. (!) Что такое граф и какие виды бывают?

**Граф** `G = (V, E)` — множество **вершин** (V) и **рёбер** (E), соединяющих пары вершин.

**Виды:**

| Тип | Описание |
|-----|----------|
| **Ориентированный (directed)** | Рёбра имеют направление |
| **Неориентированный (undirected)** | Рёбра двунаправленные |
| **Взвешенный (weighted)** | Каждое ребро имеет вес |
| **Невзвешенный** | Все рёбра одинаковы |
| **Циклический** | Содержит хотя бы один цикл |
| **Ациклический (DAG)** | Нет циклов, ориентированный |
| **Связный** | Между любыми двумя вершинами есть путь |
| **Полный** | Все вершины попарно соединены |
| **Bipartite (двудольный)** | Вершины разбиваются на 2 группы, рёбра только между группами |
| **Tree** | Связный, ациклический, с `V - 1` рёбрами |

**Применения:**
- Социальные сети (друзья, подписки)
- Маршрутизация (карты, интернет)
- Зависимости (Maven/Gradle, Spring beans)
- Рекомендации (e-commerce)


> [!mcq] Какое определение графа и классификация его видов корректны?
>
> - [ ] A. DAG — это граф вообще без рёбер (empty graph), в котором есть только изолированные вершины.
>
>     **Что на самом деле.** DAG = Directed Acyclic Graph — ориентированный граф с рёбрами, но без циклов. У DAG могут быть тысячи рёбер; «ацикличность» означает только отсутствие пути, возвращающегося в исходную вершину. Пустой граф — это частный (вырожденный) случай DAG, а не его определение.
>
>     **Откуда путаница.** Слово «ациклический» иногда воспринимают буквально как «нет связей вообще», смешивая с понятием «empty graph». В теории графов «acyclic» относится только к циклам, а не к рёбрам в целом.
>
>     **Если бы это было правдой.** Тогда Maven/Gradle dependency tree (где модули зависят друг от друга через рёбра) нельзя было бы называть DAG — но именно это название используется в документации Gradle, Apache Airflow и Spring. Build-системы развалились бы как концепция.
>
>     **Как было бы правильно.** Сказать «DAG — ориентированный граф с рёбрами, но без циклов; пустой граф — лишь вырожденный частный случай».
>
> - [x] B. Граф `G = (V, E)` бывает directed/undirected, weighted/unweighted, циклическим/ациклическим (DAG), bipartite (рёбра только между двумя множествами вершин), tree (связный, ациклический, ровно `V-1` рёбер).
>
>     **Развёрнутое объяснение.** Граф формально — пара множеств: вершины V и рёбра E ⊆ V × V. Ключевые осыпи классификации: направленность (directed имеет упорядоченные пары, undirected — неупорядоченные); вес (weighted задаёт функцию `w: E → ℝ`); цикличность (DAG — directed без циклов); двудольность (bipartite: V = A ⊔ B, рёбра только между A и B); дерево (tree: связный undirected без циклов, всегда `|E| = |V| - 1`). Эти атрибуты ортогональны: можно иметь weighted directed DAG (например, граф сборки с временем компиляции).
>
>     **Пример.** Apache Airflow моделирует workflow как weighted DAG: вершины — задачи (`PythonOperator`, `BashOperator`), рёбра — `t1 >> t2` (зависимость), вес — ожидаемое время выполнения. Spring DI bean container — directed DAG зависимостей: `UserController → UserService → UserRepository`. Граф друзей VK — undirected unweighted (дружба симметрична).
>
>     **Когда применять.** На собеседовании по data structures от вас ожидают свободное оперирование терминами: «directed/undirected», «weighted/unweighted», «cyclic/acyclic», «connected/disconnected», «bipartite», «tree». Эти атрибуты определяют, какой алгоритм применим (Dijkstra — weighted без негативных весов, BFS — unweighted, topo sort — DAG).
>
>     **Подводные камни.** Tree должен быть связным — иначе это «forest». Bipartite ⟺ нет нечётных циклов (теорема Кёнига): даже если визуально кажется, что вершины разделены на две группы, треугольник внутри одной группы делает граф не bipartite. Multigraph (несколько рёбер между парой вершин) и self-loop в классическом определении часто исключают — уточняйте на интервью.
>
>     **Связанные вопросы.** [[graphs-interview#Q2]] представление графов; [[graphs-interview#Q4]] dense vs sparse; [[graphs-interview#Q23]] проверка двудольности через BFS.
>
> - [ ] C. Tree — это связный граф с `V+1` рёбрами; добавление одного ребра к остовному дереву ещё не образует цикла.
>
>     **Что на самом деле.** Дерево по определению имеет ровно `V-1` рёбер. Связный граф с `V` рёбрами уже содержит ровно один цикл (это так называемый «pseudotree» или unicyclic graph). `V+1` рёбер означает ≥ 2 цикла — граф заведомо не дерево.
>
>     **Откуда путаница.** Формула путается с «n+1 fence-post» аналогиями. Корни путаницы: интуитивно кажется, что «дерево с N узлами имеет N рёбер» (на самом деле N-1 — на одно меньше, потому что корень не имеет родителя).
>
>     **Если бы это было правдой.** Тогда BST с 1000 узлов имел бы 1001 ребро, что противоречит инвариантам Red-Black Tree и AVL Tree: каждый узел указывает на ≤ 2 потомка, итого ≤ N-1 родительских рёбер.
>
>     **Как было бы правильно.** Сформулировать так: «tree — связный ациклический граф с `V-1` рёбрами; добавление любого ребра неизбежно создаёт цикл».
>
> - [ ] D. Bipartite граф может содержать нечётные циклы — это лишь характеристика, а не строгий критерий.
>
>     **Что на самом деле.** Теорема Кёнига гласит: граф bipartite ⟺ в нём нет нечётных циклов. Это эквивалентность, а не свойство. Алгоритм 2-coloring (BFS с чередующимися цветами) даёт false при первом же ребре между одноцветными вершинами — и это именно случай нечётного цикла.
>
>     **Откуда путаница.** «Bipartite» путают с произвольным разделением вершин на две группы. Если разделить случайно — нечётные циклы внутри одной группы возможны. Но bipartite требует, чтобы такое разделение существовало одновременно с условием «все рёбра между группами».
>
>     **Если бы это было правдой.** Задача LeetCode «Is Graph Bipartite?» (785) допускала бы false positive: треугольник `A-B-C-A` определялся бы как двудольный, что ломает применение к проблемам matching (хобольшинство, scheduling on bipartite).
>
>     **Как было бы правильно.** Признать строгую эквивалентность: bipartite ⟺ нет нечётных циклов ⟺ граф 2-раскрашиваемый ⟺ BFS-coloring не натыкается на конфликт.

## Q2. (!) Как представляют графы в коде?

**1. Матрица смежности — `boolean[V][V]` или `int[V][V]`:**

```java
int[][] matrix = new int[V][V];
matrix[u][v] = weight; // ребро u → v с весом
matrix[v][u] = weight; // для неориентированного
```

**2. Список смежности — `List<List<Integer>>` или `Map<V, List<V>>`:**

```java
List<List<int[]>> adj = new ArrayList<>(); // список пар {to, weight}
for (int i = 0; i < V; i++) adj.add(new ArrayList<>());
adj.get(u).add(new int[]{v, weight});
```

**3. Список рёбер — `List<Edge>`:**

```java
record Edge(int from, int to, int weight) {}
List<Edge> edges = new ArrayList<>();
```

В Java для production рекомендуется библиотека **JGraphT**.


> [!mcq] Как сравнить три представления графа (матрица смежности / список смежности / список рёбер) по памяти и операциям?
>
> - [ ] A. Матрица смежности — всегда лучший выбор, потому что даёт `O(1)` проверку наличия ребра.
>
>     **Что на самом деле.** Матрица `boolean[V][V]` действительно даёт `O(1)` на проверку `hasEdge(u,v)`, но это лишь одна из множества операций. На разреженном графе она расходует `O(V²)` памяти при содержательной информации в `O(V+E) ≈ O(V)` и заставляет перебирать соседей за `O(V)` вместо `O(deg(u))` — это ломает BFS/DFS на больших графах.
>
>     **Откуда путаница.** «O(1) lookup» звучит как универсальное преимущество, как в HashMap. В реальности матрица оптимальна только для dense графов или когда `hasEdge` доминирует над обходом.
>
>     **Если бы это было правдой.** Facebook (3 млрд пользователей, средняя степень ~200) использовал бы матрицу — это `9·10¹⁸` ячеек, около 10²⁰ байт. Невозможно физически — все дата-центры мира столько не дадут. Реально соцграф хранится в TAO (LinkedIn — Liquid), оба — на adjacency list.
>
>     **Как было бы правильно.** Сказать «матрица оптимальна для dense графов и операций `hasEdge`; для sparse — список смежности».
>
> - [ ] B. Edge list (`List<Edge>`) — оптимальное представление для обхода BFS/DFS на любых графах.
>
>     **Что на самом деле.** Edge list хорош для алгоритмов, работающих со всеми рёбрами сразу (Kruskal MST с сортировкой по весу, Bellman-Ford с `V-1` проходом по всем рёбрам). Для BFS/DFS нужны соседи конкретной вершины, и edge list заставляет сканировать весь список за `O(E)` на каждом шаге — итого `O(V·E)` вместо `O(V+E)`.
>
>     **Откуда путаница.** Edge list — простейшая форма (`List<int[]>`), и кажется универсальной. Но «универсально простое» ≠ «универсально оптимальное».
>
>     **Если бы это было правдой.** BFS на графе с 10⁶ вершин и 10⁷ рёбер занимал бы 10¹³ операций (часы), вместо `10⁷` (секунды) на adjacency list. Дорожные графы и соцсети были бы неюзабельны.
>
>     **Как было бы правильно.** Уточнить: edge list — для алгоритмов, итерирующих рёбра целиком (Kruskal, Bellman-Ford); для BFS/DFS — adjacency list.
>
> - [x] C. Adjacency list `O(V+E)` памяти — стандарт для разреженных графов; матрица `O(V²)` — когда `E ≈ V²` и нужно `O(1)` `hasEdge`; edge list — для алгоритмов поверх всех рёбер сразу.
>
>     **Развёрнутое объяснение.** Три представления решают разные задачи. **Adjacency list** хранит для каждой вершины список соседей: память `O(V+E)`, проверка ребра `O(deg(u))`, перебор соседей `O(deg(u))` — оптимально для BFS/DFS на sparse графах. **Adjacency matrix** — двумерный массив `V×V`: память `O(V²)`, `hasEdge` за `O(1)`, перебор соседей `O(V)` — оптимально для dense графов и алгоритмов с частыми проверками рёбер (Floyd-Warshall работает с матрицей нативно). **Edge list** хранит `List<{from, to, weight}>`: память `O(E)`, не поддерживает быстрого поиска соседей, но идеален для Kruskal (сортировка по весу) и Bellman-Ford (V-1 проход по всем рёбрам).
>
>     **Пример.** В Spring Framework `DefaultListableBeanFactory` хранит зависимости beans как adjacency list (`Map<String, Set<String> dependenciesForBean>`) — это позволяет за `O(deg)` найти зависимости конкретного бина при инициализации. JGraphT по умолчанию использует `DefaultDirectedGraph` с adjacency list (`Map<V, Set<E>>`); матричную форму даёт `SparseIntDirectedGraph` для специальных нужд. Apache Spark GraphX хранит граф как edge list (`RDD[Edge]`) + vertex RDD — это позволяет шардить по рёбрам в распределённой среде.
>
>     **Когда применять.** Adjacency list — дефолт для всех graph-задач на собеседовании; используется в Java коде LinkedList/ArrayList, в Python — `defaultdict(list)`. Матрица — если требование задачи `O(1) hasEdge` или граф dense (`E ≈ V²/2`), также для маленьких графов ≤ 100 вершин, где `O(V²)` нерелевантно. Edge list — Kruskal, Bellman-Ford, кросс-агрегации.
>
>     **Подводные камни.** В Java `List<List<Integer>>` нужно инициализировать каждый внутренний список явно (`for (int i = 0; i < V; i++) adj.add(new ArrayList<>())`) — иначе NPE при `adj.get(u)`. Adjacency list для weighted граф'ов — `List<List<int[]>>` или собственный класс `Edge` (более читаемо). Для production используют JGraphT — там уже учтены edge cases типа multigraph, self-loop.
>
>     **Связанные вопросы.** [[graphs-interview#Q3]] критерий выбора матрица vs список; [[graphs-interview#Q4]] dense vs sparse классификация; [[graphs-interview#Q16]] Kruskal использует edge list.
>
> - [ ] D. Adjacency list и matrix потребляют одинаковую память для любого графа — выбор зависит только от стиля кода.
>
>     **Что на самом деле.** Для sparse графа (`E ≈ V`) матрица тратит `O(V²)`, список — `O(V+E) ≈ O(V)`. Разница на графе 10⁶ вершин: матрица — 10¹² бит ≈ 125 GB, список — несколько MB. Это решающее различие, не «стиль».
>
>     **Откуда путаница.** Оба представления хранят «ту же информацию», и можно ошибочно подумать, что асимптотика одинакова. На самом деле представление кодирует one and the same информацию в разных формах с разной эффективностью по памяти.
>
>     **Если бы это было правдой.** AWS Neptune (graph DB на 10⁹ вершин) использовал бы матрицу — это `10¹⁸` бит ≈ 125 PB только на структуру. Реально Neptune хранит данные как property graph с adjacency list плюс secondary indexes.
>
>     **Как было бы правильно.** Признать: матрица — `O(V²)`, список — `O(V+E)`; на sparse графе разница в `V/E` раз, иногда — гигабайты.

## Q3. Когда матрица, а когда список смежности?

| Критерий | Матрица | Список смежности |
|----------|---------|-------------------|
| Память | `O(V²)` | `O(V + E)` |
| Проверка ребра `(u, v)` | `O(1)` | `O(degree(u))` |
| Перебор соседей `u` | `O(V)` | `O(degree(u))` |
| Добавление ребра | `O(1)` | `O(1)` |
| Удаление ребра | `O(1)` | `O(degree(u))` |
| Лучше для | Плотных графов | Разреженных графов |

**Правило:** если `E ≈ V²` — матрица, если `E ≈ V` — список.

В соцсетях (миллионы пользователей, средний фолловинг ~100) — список. В картах (~10 связей на перекрёсток) — список.


> [!mcq] По какому критерию выбирают между матрицей и списком смежности?
>
> - [ ] A. Матрица всегда выгоднее для алгоритмов типа Dijkstra — `O(1)` доступ к ребру всегда даёт прирост.
>
>     **Что на самом деле.** Dijkstra с adjacency list и binary heap работает за `O((V+E) log V)` — на sparse графе это `O(V log V)`. Матричный Dijkstra (без heap) — `O(V²)` независимо от E. На sparse `V log V << V²`, поэтому список выигрывает; матрица лучше только на dense.
>
>     **Откуда путаница.** «O(1) на одну операцию выгоднее `O(deg)`» — поверхностно логично. Но Dijkstra использует не отдельные `hasEdge` queries, а полный обход соседей каждой вершины — там работает суммарная асимптотика.
>
>     **Если бы это было правдой.** GPS-навигатор (граф дорог: 10⁷ вершин, 3·10⁷ рёбер) на матрице потребовал бы 10¹⁴ бит ≈ 12.5 TB только на структуру. Реально OSRM и Yandex Maps хранят дорожный граф в виде adjacency list (плюс specialized contraction hierarchies).
>
>     **Как было бы правильно.** Признать: матрица выигрывает только на dense графах; на sparse список + heap-Dijkstra быстрее.
>
> - [ ] B. Adjacency list всегда быстрее матрицы — матрицу в современных задачах вообще не используют.
>
>     **Что на самом деле.** На dense графе `E ≈ V²` матрица показывает себя лучше: Floyd-Warshall (`O(V³)`) работает с матрицей нативно — три вложенных цикла. Dijkstra с матрицей — `O(V²)`, на dense это даже быстрее heap-варианта `O(V² log V)`. Также матрица обязательна для алгоритмов с матричной арифметикой (PageRank через power iteration, spectral clustering).
>
>     **Откуда путаница.** Преобладание sparse графов в реальных задачах (соцсети, дороги) создаёт иллюзию универсальности списка. Но в физике, химии (молекулярные графы), маленьких комбинаторных задачах матрица оптимальна.
>
>     **Если бы это было правдой.** Pixar/DreamWorks отказались бы от использования матричных представлений в графах смежности полигональных мешей (где плотность связей высокая на маленьком графе). На самом деле они используют именно матричные структуры для быстрых subdivision-операций.
>
>     **Как было бы правильно.** Сказать: на dense графе `E ≈ V²` матрица оптимальнее списка по константе и по локальности кэша.
>
> - [ ] C. Выбор зависит исключительно от числа вершин V — больше вершин, обязательно матрица; меньше — список.
>
>     **Что на самом деле.** Решающий фактор — плотность `E/V²`, а не одно V. При 10⁶ вершин и `E = 2·10⁶` (sparse) матрица — 125 GB, список — несколько MB. При 100 вершин и `E = 5000` (dense) матрица — 10 KB, список — 20+ KB (с overhead на pointer).
>
>     **Откуда путаница.** Кажется, что «большой граф = матрица не помещается, поэтому маленький = матрица». Но истинный критерий — отношение `E/V²`, а не абсолютная величина V.
>
>     **Если бы это было правдой.** Twitter (300M пользователей, sparse) использовал бы матрицу — это `9·10¹⁶` бит ≈ 11 PB. Реально соц-граф хранится в адаптированной FlockDB (custom sharded adjacency list).
>
>     **Как было бы правильно.** Использовать пороговое отношение `E/V² > 0.5` (rule of thumb): >0.5 → матрица, <0.1 → список, между — зависит от operations mix.
>
> - [x] D. `E ≈ V²` → матрица (dense, `O(1)` edge lookup выгоден); `E << V²` → список (sparse, экономия памяти `O(V+E)`); большинство реальных графов — sparse.
>
>     **Развёрнутое объяснение.** Критерий — плотность графа `E/V²`. Если ребра почти все возможные (полные графы, маленькие комбинаторные графы, регулярные графы алгоритмов matrix multiplication) — выбираем матрицу: лучшая локальность кэша, простой код, `O(1)` `hasEdge`. Если ребра разрежены (большинство реальных графов: соцсети, дороги, веб) — выбираем adjacency list: память `O(V+E) ≈ O(V)`, обход соседей `O(deg)`. Пороговое отношение `E/V² > 0.5` — rule of thumb от Cormen et al.: выше — матрица, ниже — список.
>
>     **Пример.** Google PageRank (web graph: 50B страниц, средняя степень ~40 — крайне sparse) — adjacency list (точнее, специализированное column-store представление для распределённой обработки в MapReduce). Floyd-Warshall на routing tables маленькой сети из 50 маршрутизаторов — матрица `50×50` (всего 20 KB, в кэше L1). Wikipedia article graph (~6M статей, average outdegree ~25) — adjacency list в Pet Scan tooling. JGraphT — выбирает adjacency list по умолчанию, потому что 95% production-графов sparse.
>
>     **Когда применять.** Routing tables (dense, маленькие) → матрица; соцсети, веб, дороги (sparse, миллионы вершин) → список; PageRank power iteration над миллиардами страниц → специализированный column-oriented edge list для распределённости. На собеседовании по умолчанию говорите «adjacency list `Map<V, List<V>>`» — это правильный default.
>
>     **Подводные камни.** Граф может «менять плотность» при росте: дерево организации с 100 сотрудниками — sparse (~100 рёбер), но если добавить рёбра «коллеги по проекту» — dense на маленьком масштабе. Hybrid-представления (CSR — Compressed Sparse Row) дают компромисс — sparse-friendly память + `O(1)` лookup за счёт сложного построения. Также для multigraph (несколько рёбер между парой вершин) матрица не подходит без счётчиков.
>
>     **Связанные вопросы.** [[graphs-interview#Q2]] три представления графа; [[graphs-interview#Q4]] dense vs sparse классификация; [[graphs-interview#Q13]] Floyd-Warshall работает с матрицей.

## Q4. Что такое плотный и разреженный граф?

- **Плотный (dense):** `E ≈ V²` (близко к максимуму `V·(V-1)/2`)
- **Разреженный (sparse):** `E << V²` (часто `E = O(V)`)

Большинство реальных графов **разреженные** (соцсети, дорожные карты, граф зависимостей).

| Алгоритм | Sparse `E ≈ V` | Dense `E ≈ V²` |
|----------|----------------|-----------------|
| BFS/DFS | `O(V)` | `O(V²)` |
| Dijkstra (с heap) | `O(V log V)` | `O(V² log V)` |
| Dijkstra (с массивом) | `O(V²)` | `O(V²)` |
| Floyd-Warshall | `O(V³)` | `O(V³)` |

Для плотных графов матрица + Dijkstra на массиве может оказаться быстрее.


> [!mcq] Чем плотный граф отличается от разреженного и какие реальные графы относятся к какой категории?
>
> - [x] A. Sparse: `E = O(V) << V²` (большинство реальных графов: соцсети, дороги, зависимости); dense: `E ≈ V²` (полный/почти полный граф, маленькие комбинаторные графы).
>
>     **Развёрнутое объяснение.** Плотность определяется отношением `E/V²`, а не абсолютным числом рёбер. Sparse граф имеет `E = O(V)` (часто `E ≈ k·V` с малым k=5..200), что асимптотически намного меньше `V² ≈ V·V`. Dense граф приближается к максимуму `V·(V-1)/2 = O(V²)` рёбер. От классификации зависит выбор алгоритмов: на sparse графах Dijkstra с heap (`O(V log V)`) быстрее матричного (`O(V²)`), а на dense — наоборот. Floyd-Warshall (`O(V³)`) применим только на маленьких графах ≤ 500 вершин независимо от плотности.
>
>     **Пример.** Facebook (2025): 3 млрд пользователей, средняя степень ~338 друзей → `E ≈ 5·10¹¹`, `V² ≈ 9·10¹⁸`. Плотность ~`6·10⁻⁸` — крайне sparse. Spring DI bean graph типичного приложения: 500 beans, средние 3 зависимости → `E ≈ 1500`, `V² = 250000`. Плотность ~`0.6%` — sparse. Граф взаимодействий 5 микросервисов с full mesh: V=5, E=20 (directed), `V² = 25` — плотность 80%, dense.
>
>     **Когда применять.** Классификация — первый шаг перед выбором алгоритма и представления. Sparse → adjacency list + Dijkstra/BFS/DFS на `O(V+E)`; dense → matrix + Floyd-Warshall / matrix-Dijkstra на `O(V²..V³)`. Большинство задач на собеседовании и в production — sparse: соцсети (Facebook, LinkedIn, TikTok), дорожные графы (OSM), зависимости (Maven, npm), graph DB queries (Neo4j).
>
>     **Подводные камни.** Граф может менять плотность при evolution: tree → DAG → cyclic graph при росте features. На маленьких dense графах матрица в L1-кэше дешевле списка (cache locality). Не путать «много вершин» с «плотный»: 10⁹ вершин и 10¹⁰ рёбер — это sparse (`E/V² = 10⁻⁸`), но физически большой граф; нужны distributed-системы (Pregel, GraphX). Bipartite графы часто sparse: вершин одной из двух частей много, рёбер между частями мало.
>
>     **Связанные вопросы.** [[graphs-interview#Q3]] критерий выбора матрицы vs списка; [[graphs-interview#Q10]] Dijkstra на sparse и dense; [[graphs-interview#Q13]] Floyd-Warshall для dense small graphs.
>
> - [ ] B. Разреженный граф — это граф с менее чем 100 рёбер; плотный — с более чем 100 рёбер.
>
>     **Что на самом деле.** Плотность относительна, а не абсолютна. Граф с `V=1000`, `E=1000` — sparse (`E ≈ V`). Граф с `V=10`, `E=45` (полный неориентированный) — dense (`E = V(V-1)/2`). Абсолютное число рёбер бессмысленно без учёта V.
>
>     **Откуда путаница.** Числа кажутся понятнее, чем асимптотика. Но «100 рёбер» на графе из 10 вершин — это полный граф (dense); на графе из 10⁶ вершин — это даже не связный граф.
>
>     **Если бы это было правдой.** Алгоритм выбора структуры выглядел бы как `if (edges < 100) sparse else dense` — это игнорировало бы реальную плотность. Все Twitter / VK графы были бы «dense» (миллиарды рёбер) и пытались бы построить матрицу — невозможно.
>
>     **Как было бы правильно.** Использовать относительную меру: `E/V² < 0.1` → sparse, `> 0.5` → dense.
>
> - [ ] C. Соцсети — плотные графы, потому что в современном мире каждый связан почти с каждым.
>
>     **Что на самом деле.** Соцграф Facebook (2025): средняя степень ~338, что много по человеческим меркам, но `338 / 3·10⁹ ≈ 10⁻⁷` — крайне sparse. Даже шесть рукопожатий (small-world phenomenon) подразумевает sparse-граф с короткими путями, не dense.
>
>     **Откуда путаница.** Феномен «six degrees of separation» создаёт ощущение, что граф «плотный» — короткие пути между любыми двумя людьми. На самом деле это свойство small-world графов, ортогональное плотности (короткие пути возникают за счёт hub-узлов и кластеризации, а не плотности).
>
>     **Если бы это было правдой.** Facebook хранил бы свой граф в матрице — `9·10¹⁸` бит ≈ 1 ZB. Реально TAO (Facebook backend) хранит граф в распределённой adjacency list поверх MySQL.
>
>     **Как было бы правильно.** Признать: соцсети — sparse small-world графы со степенным распределением степеней (power-law).
>
> - [ ] D. Floyd-Warshall быстрее Dijkstra на разреженных графах, поэтому для sparse предпочитают Floyd.
>
>     **Что на самом деле.** Floyd-Warshall работает за `O(V³)` независимо от плотности. На sparse графе Dijkstra с heap — `O((V+E) log V) ≈ O(V log V)`. Запуск Dijkstra от каждой вершины (если нужен all-pairs) — `O(V·(V+E) log V) = O(V² log V)`, что асимптотически быстрее `V³` на sparse графе.
>
>     **Откуда путаница.** Floyd-Warshall иногда называют «универсальным», и кажется, что он быстрее во всех случаях. На самом деле он удобен только когда нужны все пары на маленьком dense графе.
>
>     **Если бы это было правдой.** Google Maps использовал бы Floyd-Warshall для дорожного графа (10⁷ вершин) — это `10²¹` операций, нереализуемо. Реально используются contraction hierarchies (Geisberger et al., 2008) — preprocessing + Dijkstra-подобный query.
>
>     **Как было бы правильно.** Признать: Floyd-Warshall — `O(V³)`, выгоден только на маленьких dense графах; на sparse — Dijkstra от каждой вершины (Johnson's algorithm).

## Q5. (!) BFS — Breadth First Search?

Обход графа **по уровням**: посещаем все вершины на расстоянии 1, потом 2, и т.д. Использует **очередь**.

```java
void bfs(List<List<Integer>> adj, int start) {
    boolean[] visited = new boolean[adj.size()];
    Queue<Integer> queue = new ArrayDeque<>();
    queue.offer(start);
    visited[start] = true;

    while (!queue.isEmpty()) {
        int u = queue.poll();
        process(u);
        for (int v : adj.get(u)) {
            if (!visited[v]) {
                visited[v] = true;
                queue.offer(v);
            }
        }
    }
}
```

`O(V + E)` время, `O(V)` память.

**Применения:**
- Кратчайший путь в невзвешенном графе
- Найти все вершины на расстоянии K
- Двудольная проверка
- Web crawling, social network friends-of-friends


> [!mcq] Что характеризует BFS и какие у него гарантии?
>
> - [x] A. BFS = Queue (FIFO), обход по уровням, кратчайший путь в невзвешенном графе; `O(V+E)` время, `O(w)` память (w — ширина уровня).
>
>     **Развёрнутое объяснение.** Breadth-First Search использует очередь (FIFO): вершина извлекается из головы, её непосещённые соседи добавляются в хвост. Это создаёт строгий level-by-level порядок: сначала все вершины на расстоянии 1, потом 2, и т.д. **Ключевая гарантия**: BFS находит кратчайший путь по числу рёбер в **невзвешенном** графе. Доказательство — индукция по уровням: вершина впервые посещается на минимальном уровне, потому что любой более короткий путь означал бы посещение на более раннем уровне. Сложность по времени — `O(V+E)` (каждая вершина и ребро посещаются один раз), по памяти — `O(V)` на visited array плюс `O(w)` на очередь, где `w` — максимальная ширина уровня.
>
>     **Пример.** LinkedIn «You are connected through Alice and Bob» — BFS глубиной 2 от пользователя в графе друзей. Web crawler Googlebot — BFS по ссылкам с приоритетом на «свежие» страницы; глубина обхода ограничивается per-domain. Garbage Collector mark phase в G1GC использует BFS-подобный mark от GC roots для определения reachable objects. Solver Lights Out / Rubik's cube — BFS по конфигурациям с предикатом «отличается на 1 ход».
>
>     **Когда применять.** Кратчайший путь в невзвешенном графе (число рёбер); level-order traversal в trees; обход на расстоянии ≤ K (social network degrees, peer discovery в P2P); bipartite check через 2-coloring; web crawling; serialization деревьев в level-order формате; флудинг (Number of Islands).
>
>     **Подводные камни.** Память может вырасти до `O(V)` на широком уровне (полное двоичное дерево последнего уровня — `V/2` вершин в очереди). На глубоких деревьях BFS использует больше памяти, чем DFS (`O(h)`). `visited[v] = true` нужно ставить **при добавлении в очередь**, а не при извлечении — иначе одна вершина попадёт в очередь несколько раз. Для bidirectional BFS требуется граф с обратимыми рёбрами.
>
>     **Связанные вопросы.** [[graphs-interview#Q6]] DFS как контрастный обход; [[graphs-interview#Q7]] BFS vs DFS сравнение; [[graphs-interview#Q8]] кратчайший путь через BFS.
>
> - [ ] B. BFS использует стек, DFS использует очередь — обе структуры данных, разница только в порядке доступа.
>
>     **Что на самом деле.** Ровно наоборот: BFS использует Queue (FIFO для level-by-level), DFS — Stack/recursion (LIFO для углубления). Перепутать = получить неправильный обход и неверные гарантии (BFS на стеке вырождается в обход в обратном порядке, DFS на очереди превратится в BFS).
>
>     **Откуда путаница.** Обе структуры — линейные коллекции, начинающиеся на букву Q или S — легко перепутать без понимания семантики «извлекаем спереди» vs «извлекаем сверху».
>
>     **Если бы это было правдой.** Реализация LeetCode 102 «Binary Tree Level Order Traversal» с stack дала бы вывод не по уровням, а в DFS-обратном порядке — WA на любых тестах. Spring DI с DFS-инициализацией могла бы инициализировать `@Configuration` до его зависимостей — `BeanCurrentlyInCreationException`.
>
>     **Как было бы правильно.** Запомнить: «BFS = Queue = Wide = по слоям»; «DFS = Stack = Deep = в глубину». Расширение `B`/`D` помогает: Breadth — широкая очередь, Depth — глубокий стек.
>
> - [ ] C. BFS находит кратчайший путь и в взвешенных графах — алгоритм универсальный.
>
>     **Что на самом деле.** BFS минимизирует **число рёбер** в пути, не сумму весов. На взвешенном графе он может проигнорировать дешёвый длинный путь и выбрать дорогой короткий по числу шагов. Для взвешенных графов используют Dijkstra (неотрицательные веса) или Bellman-Ford (с отрицательными).
>
>     **Откуда путаница.** «Кратчайший путь» — фраза, под которой понимают разное. В контексте BFS подразумевается «минимальное число рёбер», а в общем — «минимальная сумма весов».
>
>     **Если бы это было правдой.** GPS-навигатор использовал бы BFS для поиска маршрута и предлагал бы пройти по трём километрам широкого шоссе вместо двух километров узкой дороги — потому что число рёбер было бы меньше, но не время в пути. Google Maps реально использует contraction hierarchies + Dijkstra-like queries.
>
>     **Как было бы правильно.** Уточнить: BFS — кратчайший по числу рёбер, только в невзвешенном графе. Для взвешенного → Dijkstra/Bellman-Ford.
>
> - [ ] D. BFS не находит все вершины, связанные с источником — нужно дополнительно запускать DFS для оставшихся.
>
>     **Что на самом деле.** BFS гарантированно обходит **все достижимые** из источника вершины. Если граф не связный, недостижимые вершины — действительно остаются за пределами одного запуска, но это поведение не специфично для BFS: DFS тоже не достигнет другой компоненты. Чтобы посетить все вершины — нужен внешний цикл с запуском BFS/DFS от каждой непосещённой.
>
>     **Откуда путаница.** На несвязном графе кажется, что «BFS не полный». На самом деле BFS полный в рамках своей компоненты связности.
>
>     **Если бы это было правдой.** Java GC mark phase (BFS-подобный) пропустил бы достижимые объекты — это привело бы к освобождению памяти живых объектов, segfault. Spring DI пропустил бы beans из той же компоненты зависимостей — ApplicationContext не стартовал бы корректно.
>
>     **Как было бы правильно.** Признать: BFS обходит **всю компоненту связности**, в которой стартовал; для несвязных графов нужен внешний цикл по всем вершинам.

## Q6. (!) DFS — Depth First Search?

Идём «вглубь» сколько можем, потом возвращаемся. Использует **стек** (рекурсия или явный).

```java
// Рекурсивный
void dfs(List<List<Integer>> adj, int u, boolean[] visited) {
    visited[u] = true;
    process(u);
    for (int v : adj.get(u)) {
        if (!visited[v]) dfs(adj, v, visited);
    }
}

// Итеративный через стек
void dfsIterative(List<List<Integer>> adj, int start) {
    boolean[] visited = new boolean[adj.size()];
    Deque<Integer> stack = new ArrayDeque<>();
    stack.push(start);
    while (!stack.isEmpty()) {
        int u = stack.pop();
        if (visited[u]) continue;
        visited[u] = true;
        process(u);
        for (int v : adj.get(u)) {
            if (!visited[v]) stack.push(v);
        }
    }
}
```

`O(V + E)` время, `O(V)` память (стек/visited). Стек вызовов до `O(V)` — для больших графов используй итеративный.

**Применения:**
- Топологическая сортировка
- Обнаружение циклов
- Поиск SCC (Tarjan, Kosaraju)
- Backtracking, генерация перестановок
- Maze solving


> [!mcq] Какие свойства имеет DFS и где он применяется?
>
> - [ ] A. DFS находит кратчайший путь лучше, чем BFS — идёт глубже, поэтому быстрее доходит до цели.
>
>     **Что на самом деле.** DFS вообще не гарантирует кратчайший путь даже в невзвешенном графе: он спускается по одной ветке до конца, прежде чем перейти к другой, и может найти длинный путь к цели первым. Кратчайший путь даёт только BFS (по числу рёбер) или Dijkstra (по сумме весов).
>
>     **Откуда путаница.** «Глубже = быстрее» — интуиция из физики (пробить стенку, чтобы дойти быстрее). В графах глубина ортогональна длине пути: можно уйти глубоко в неправильном направлении.
>
>     **Если бы это было правдой.** LeetCode 102 «Shortest Path in Binary Matrix» решался бы DFS — но canonical-решение использует BFS, потому что DFS даёт WA на тестах с несколькими путями разной длины.
>
>     **Как было бы правильно.** Признать: DFS находит **любой** путь, но не обязательно кратчайший. Для shortest path — BFS (unweighted) или Dijkstra (weighted).
>
> - [ ] B. DFS не может обнаружить циклы — для этого нужны специальные алгоритмы вроде Tarjan.
>
>     **Что на самом деле.** DFS с трёхцветной разметкой (WHITE/GRAY/BLACK) — стандартный алгоритм обнаружения циклов в directed графе. Если из GRAY-вершины приходим в GRAY — обнаружен back edge = цикл. Tarjan строится на DFS, не заменяет его. Для undirected — DFS с parent[]: если visited-сосед не parent, это back edge.
>
>     **Откуда путаница.** Tarjan SCC algorithm включает дополнительные структуры (low-link, stack), и кажется, что cycle detection — отдельная задача. На самом деле базовая cycle detection — это просто DFS + colors, доступна на 10 строк кода.
>
>     **Если бы это было правдой.** Maven/Gradle не могли бы определить циклическую зависимость между модулями — build блокировался бы с infinite recursion вместо понятного error «Circular dependency between :moduleA and :moduleB». На практике Gradle использует именно DFS с visited tracking.
>
>     **Как было бы правильно.** Признать: DFS — естественный и базовый инструмент cycle detection через back edges; Tarjan/Kosaraju — расширения для SCC.
>
> - [ ] C. DFS всегда быстрее BFS, потому что использует меньше памяти `O(h)` против `O(w)`.
>
>     **Что на самом деле.** Оба алгоритма работают за `O(V+E)` по времени. Память зависит от формы графа: на сбалансированном дереве `h = log V`, `w = V/2` — DFS выигрывает; на «линейке» (V вершин подряд) `h = V`, `w = 1` — BFS выигрывает. Универсального превосходства нет.
>
>     **Откуда путаница.** В большинстве «учебных» задач (balanced trees) DFS экономит память, и это становится общим правилом. На реальных графах разница может быть в противоположную сторону.
>
>     **Если бы это было правдой.** Все реализации BFS заменили бы на DFS — но Spring framework инициализирует beans через топологическую сортировку Kahn (BFS-based), а не DFS, именно потому что BFS даёт level-by-level evaluation, нужное для bean lifecycle phases.
>
>     **Как было бы правильно.** Сказать: «время — одинаковое `O(V+E)`; память зависит от формы графа; DFS лучше на глубоких, BFS — на широких».
>
> - [x] D. DFS = Stack/рекурсия, идёт в глубину; `O(V+E)` время, `O(h)` память (h — глубина рекурсии); применяется для топологической сортировки, SCC, обнаружения циклов, backtracking, maze solving.
>
>     **Развёрнутое объяснение.** Depth-First Search углубляется насколько может, потом возвращается (backtrack). Используется явный стек или рекурсия (call stack играет роль стека). Алгоритм состоит из трёх фаз для каждой вершины: discovery (вход в DFS), processing (обработка соседей рекурсивно), finish (выход из DFS). Сложность по времени — `O(V+E)` (каждая вершина и ребро посещается раз). Память — `O(V)` на visited + `O(h)` на стек, где h — глубина рекурсии (худшем случае h = V на «линейке»). На большом V (10⁵+) рекурсия может пробить стандартный JVM-stack 512KB — поэтому используют итеративный DFS на `Deque`.
>
>     **Пример.** Java compiler dependency analysis — DFS по import-графу для обнаружения циклических импортов. Apache Maven `effective-pom` собирает граф наследования POM через DFS с post-order разрешением properties. Tarjan SCC algorithm (используется в LLVM для оптимизации) — single-pass DFS с low-link values. Tetris bot, Sudoku solver — backtracking DFS с проверкой каждой возможной комбинации. JDK `Object.toString()` для циклических структур использует DFS с visited identity-set.
>
>     **Когда применять.** Топологическая сортировка через post-order (Q26); обнаружение циклов (3-color DFS для directed, parent-tracking для undirected); SCC (Tarjan single-pass); backtracking (N-Queens, Sudoku); maze solving с любым путём; обход по структурным свойствам (find articulation points, bridges). Когда задача требует «структуру графа», а не «короткие пути» — DFS.
>
>     **Подводные камни.** Stack overflow на глубоких графах (`h > 10000` ломает JVM-default 512KB stack) — решение `-Xss` или итеративный DFS. Recursion даёт неявный backtrack — удобно для backtracking задач, но трудно прервать середине. Iterative DFS со стеком не даёт «post-order» бесплатно — нужны явные маркеры «in/out». В Python `sys.setrecursionlimit(10000)` обязателен для глубоких графов. При параллелизации DFS теряет преимущества — обычно параллелится BFS (для каждого уровня независимо).
>
>     **Связанные вопросы.** [[graphs-interview#Q5]] BFS как контрастный обход; [[graphs-interview#Q7]] BFS vs DFS сравнение; [[graphs-interview#Q20]] DFS с 3 цветами для cycle detection; [[graphs-interview#Q22]] Tarjan/Kosaraju SCC на DFS.

## Q7. (!) Чем BFS отличается от DFS?

| Критерий | BFS | DFS |
|----------|-----|-----|
| Структура данных | Queue (FIFO) | Stack (LIFO) или рекурсия |
| Память | `O(w)`, w = ширина уровня | `O(h)`, h = глубина |
| Кратчайший путь | Невзвешенный — да | Не находит |
| Топологическая сортировка | Да (Кан) | Да |
| Обнаружение цикла | Да (с осторожностью) | Естественно |
| Поиск SCC | Не подходит | Tarjan/Kosaraju |
| Память для очень глубоких | Хуже (широкий слой) | Хуже (deep recursion) |
| Память для очень широких | Хуже | Лучше |

**BFS** — для shortest path, level-based.
**DFS** — для топологии, циклов, backtracking.


> [!mcq] Как выбрать между BFS и DFS для конкретной задачи?
>
> - [ ] A. BFS и DFS одинаково подходят для shortest path — выбор зависит только от стиля разработчика.
>
>     **Что на самом деле.** DFS не гарантирует кратчайший путь: он спускается по одной ветке до конца и может найти длинный путь первым. Только BFS гарантирует минимальное число рёбер в невзвешенном графе по математической индукции (вершина впервые посещается на минимальном уровне).
>
>     **Откуда путаница.** Оба алгоритма «находят путь», и кажется, что они эквивалентны. На самом деле они оптимизируют разные метрики — BFS минимизирует число шагов, DFS не минимизирует ничего конкретного.
>
>     **Если бы это было правдой.** LeetCode 1091 «Shortest Path in Binary Matrix» решался бы DFS — но это даёт WA, потому что DFS может найти путь длиной 100, когда BFS — длиной 10. На production-системе (Google Maps) пользователь получал бы случайный маршрут.
>
>     **Как было бы правильно.** Сказать: «BFS — для shortest path; DFS — для структурных задач (cycles, topo sort, SCC)».
>
> - [x] B. BFS — кратчайший путь в невзвешенном графе, level-order, bipartite check; DFS — topological sort, cycle detection, SCC, backtracking; оба `O(V+E)` по времени.
>
>     **Развёрнутое объяснение.** Выбор между BFS и DFS зависит от того, что нужно от обхода: «кратчайший путь» или «структуру графа». BFS гарантирует level-by-level порядок и минимальное число рёбер до цели — это даёт shortest path в невзвешенном, level-order traversal деревьев, bipartite check через 2-coloring. DFS даёт natural recursion и post-order — это идеально для топологической сортировки, cycle detection через back edges, SCC через low-link values, backtracking задач. По времени оба `O(V+E)`, по памяти BFS — `O(w)` (ширина уровня), DFS — `O(h)` (глубина).
>
>     **Пример.** Spring DI инициализирует beans через топологическую сортировку Kahn — BFS-based, потому что нужно level-by-level выполнение. Java GC mark phase (G1, ZGC) — BFS-подобный mark от GC roots. Apache Maven dependency resolution — DFS с post-order (childparent → resolve children first → resolve parent). Tarjan SCC algorithm в LLVM — single-pass DFS с low-link. LeetCode «Number of Islands» решается обоими — выбирают по предпочтению, оба `O(R·C)`.
>
>     **Когда применять.** Нужен shortest path в невзвешенном → BFS. Нужны degrees of separation (соцсети 1st/2nd/3rd connection) → BFS. Топологическая сортировка → BFS (Kahn) или DFS (post-order). Cycle detection → DFS с цветами. SCC → DFS (Tarjan/Kosaraju). Backtracking (Sudoku, N-Queens) → DFS. Web crawler — обычно BFS с приоритетом «новые URL сначала».
>
>     **Подводные камни.** BFS требует `O(w)` памяти — на широком уровне (полное двоичное дерево последнего уровня — V/2 вершин) это `O(V)`. DFS требует `O(h)` стека — на «линейке» это `O(V)`, риск StackOverflow при `h > 10⁴` (JVM default stack 512KB). На больших графах с `V > 10⁶` нужен итеративный DFS на `Deque`. Lazy initialization beans в Spring смешивает BFS-инициализацию с DFS-резолвом, что вызывает сложные edge cases с `@Lazy` proxy.
>
>     **Связанные вопросы.** [[graphs-interview#Q5]] BFS подробно; [[graphs-interview#Q6]] DFS подробно; [[graphs-interview#Q8]] shortest path через BFS.
>
> - [ ] C. DFS всегда лучше BFS для нахождения пути в лабиринтах — нужно всегда использовать DFS.
>
>     **Что на самом деле.** DFS находит **какой-то** путь, но не обязательно кратчайший. BFS гарантирует минимальное число шагов. A* с эвристикой Manhattan/Euclidean даёт ещё лучшую производительность для grid-pathfinding. Выбор зависит от требования: «любой путь как можно быстрее» → DFS, «кратчайший путь» → BFS/A*.
>
>     **Откуда путаница.** В классических визуализациях DFS «бежит по стенке» (left-hand rule), и кажется, что он эффективен в лабиринтах. На самом деле он находит путь, но обычно не оптимальный.
>
>     **Если бы это было правдой.** Pacman-AI в Google's pacman pathfinding tutorial использовал бы DFS — но canonical-решение использует A* с Manhattan distance, потому что DFS даёт subobtimal пути (призраки делают петли вокруг heroя).
>
>     **Как было бы правильно.** Признать: DFS — для «найти любой путь быстро»; BFS — для shortest; A* — для shortest с эвристикой.
>
> - [ ] D. BFS подходит только для деревьев, а не для произвольных графов — там нужны более сложные алгоритмы.
>
>     **Что на самом деле.** BFS работает на любом графе при условии правильного `visited[]` — для дерева это особый случай (нет циклов, поэтому visited не нужен). На графе без visited алгоритм может зациклиться.
>
>     **Откуда путаница.** В учебниках BFS чаще объясняют на деревьях (level-order traversal binary tree), и кажется, что это его «правильная» область. На самом деле BFS изначально проектировался для произвольных графов; деревья — частный случай.
>
>     **Если бы это было правдой.** LinkedIn не мог бы предложить «You are connected through Alice» — это BFS на графе friendships (не дерево, есть треугольники друзей). Реально LinkedIn использует BFS-вариант с глубиной 1-2-3.
>
>     **Как было бы правильно.** Признать: BFS работает на любом графе с `visited[]`; для дерева visited не обязателен (нет циклов).

## Q8. (!) Кратчайший путь в невзвешенном графе?

**BFS** даёт кратчайший путь в невзвешенном графе:

```java
int bfsShortestPath(List<List<Integer>> adj, int start, int end) {
    boolean[] visited = new boolean[adj.size()];
    Queue<int[]> queue = new ArrayDeque<>(); // {вершина, расстояние}
    queue.offer(new int[]{start, 0});
    visited[start] = true;

    while (!queue.isEmpty()) {
        int[] curr = queue.poll();
        int u = curr[0], dist = curr[1];
        if (u == end) return dist;

        for (int v : adj.get(u)) {
            if (!visited[v]) {
                visited[v] = true;
                queue.offer(new int[]{v, dist + 1});
            }
        }
    }
    return -1;
}
```

Чтобы восстановить **сам путь** — храни `parent[v] = u` при посещении и пройдись от end до start.

`O(V + E)` время, `O(V)` память.


> [!mcq] Как BFS находит кратчайший путь в невзвешенном графе и как восстановить сам путь?
>
> - [ ] A. BFS автоматически восстанавливает путь — отдельная структура данных не нужна.
>
>     **Что на самом деле.** BFS находит **расстояние** (число рёбер) до каждой вершины, но не сохраняет сам путь. Чтобы восстановить путь, нужен дополнительный массив `parent[v] = u` — устанавливается, когда `v` посещается через `u`. Восстановление: идти от end к start через `parent[]` и реверсировать список.
>
>     **Откуда путаница.** В простых учебных версиях BFS возвращают только дистанцию (`int distance`), и кажется, что путь «получается само собой». На самом деле информация о пути теряется, если её не сохранять явно.
>
>     **Если бы это было правдой.** Google Maps выдавал бы маршрут «20 минут» без визуализации самого пути на карте — потому что путь не сохранён. Реально BFS-вариант пути требует именно parent-tracking.
>
>     **Как было бы правильно.** Сказать: «BFS считает расстояние; путь — отдельный шаг через `parent[]`».
>
> - [ ] B. BFS находит кратчайший путь только если граф ациклический — циклы ломают алгоритм.
>
>     **Что на самом деле.** BFS работает на любом графе с `visited[]`. Visited предотвращает бесконечные циклы — вершина не добавляется в очередь повторно. Гарантия кратчайшего пути (по числу рёбер) сохраняется на любом невзвешенном графе, циклическом или нет.
>
>     **Откуда путаница.** «Циклы ломают алгоритм» — частая мысль из других контекстов (DAG topological sort). В BFS циклы безвредны, потому что visited блокирует повторное посещение.
>
>     **Если бы это было правдой.** BFS не работал бы на соцсетях (там много циклов — треугольники друзей) — но реально LinkedIn успешно использует BFS для feature «1st/2nd/3rd connection» в графе с циклами.
>
>     **Как было бы правильно.** Признать: BFS работает на любом графе с visited; ациклические — частный случай (без необходимости в visited).
>
> - [x] C. BFS находит кратчайший путь в невзвешенном графе за `O(V+E)`; путь восстанавливается через `parent[]` массив, проходя от end к start в обратном направлении.
>
>     **Развёрнутое объяснение.** BFS на невзвешенном графе посещает вершины level-by-level: при первом посещении вершины `v` гарантированно набирается минимальное число рёбер из start. Чтобы восстановить путь, при добавлении `v` в очередь сохраняем `parent[v] = u` (тот, кто привёл к `v`). Когда дошли до `end`, восстанавливаем путь: `path = [end, parent[end], parent[parent[end]], ..., start]`, потом реверсируем. Сложность по времени — `O(V+E)`, по памяти — `O(V)` на `visited` + `O(V)` на `parent`. Метод универсален для unweighted graphs: directed/undirected, cyclic/acyclic.
>
>     **Пример.** LeetCode 127 «Word Ladder» — BFS на графе слов с рёбрами «отличаются на 1 букву», ищем минимальное число трансформаций. LinkedIn degrees of separation — BFS от user до искомого человека, выводит «3-я степень знакомства». В P2P-сетях (Kademlia DHT) кратчайший путь к узлу через XOR-distance — BFS-вариант. Backend для онлайн-игр (Pokémon GO route planning) — BFS на graph spawn points с парент-tracking для отображения route на map.
>
>     **Когда применять.** Любая задача «минимум шагов» на невзвешенном графе: word transformations, social degrees, грид-pathfinding без весов, dependency depth analysis. Обязательно сохранять `parent[]`, если нужен сам путь, а не только длина.
>
>     **Подводные камни.** Off-by-one error: `parent[start] = -1` (нет родителя) — иначе бесконечный цикл при восстановлении. На больших графах `parent[]` занимает `O(V)` памяти — заметно при V = 10⁹. Если граф взвешенный, BFS даст неверный ответ (минимизирует число рёбер, не сумму) — нужен Dijkstra. При мульти-source BFS (старт от нескольких вершин) parent должен быть `Map<v, u>` или `int[]` с инициализацией `-2` (sentinel «source»).
>
>     **Связанные вопросы.** [[graphs-interview#Q5]] BFS базовый алгоритм; [[graphs-interview#Q9]] bidirectional BFS для ускорения; [[graphs-interview#Q29]] Word Ladder как пример path reconstruction.
>
> - [ ] D. Для взвешенного графа BFS даёт минимальный вес пути — алгоритм универсален.
>
>     **Что на самом деле.** BFS минимизирует число рёбер, не сумму весов. На графе с рёбрами `A→B = 100`, `A→C = 1, C→D = 1, D→B = 1` BFS найдёт путь `A→B` длиной 100 (1 ребро), а оптимальный путь — `A→C→D→B` длиной 3 (3 ребра). Для взвешенных нужен Dijkstra (неотрицательные веса) или Bellman-Ford (с отрицательными).
>
>     **Откуда путаница.** «Кратчайший путь» — фраза без точного смысла без контекста. В BFS — кратчайший по числу шагов; в Dijkstra — по сумме весов; разные определения.
>
>     **Если бы это было правдой.** GPS-навигатор использовал бы BFS — пользователь получил бы маршрут с 1 ребром (одно шоссе на 500 км) вместо 3 быстрых дорог на 50 км. Реально Google Maps использует Dijkstra-like алгоритмы (contraction hierarchies).
>
>     **Как было бы правильно.** Признать: BFS — для невзвешенного; для взвешенного → Dijkstra (non-negative) или Bellman-Ford (general).

## Q9. Bidirectional BFS — двунаправленный поиск?

**Bidirectional BFS** — запускаем BFS одновременно от start и end, останавливаемся когда фронты встретятся.

```java
int bidirBFS(List<List<Integer>> adj, int start, int end) {
    if (start == end) return 0;

    Set<Integer> visitedFromStart = new HashSet<>(Set.of(start));
    Set<Integer> visitedFromEnd = new HashSet<>(Set.of(end));
    int distance = 0;

    while (!visitedFromStart.isEmpty() && !visitedFromEnd.isEmpty()) {
        // Расширяем меньший фронт
        if (visitedFromStart.size() > visitedFromEnd.size()) {
            Set<Integer> tmp = visitedFromStart;
            visitedFromStart = visitedFromEnd;
            visitedFromEnd = tmp;
        }

        Set<Integer> next = new HashSet<>();
        for (int u : visitedFromStart) {
            for (int v : adj.get(u)) {
                if (visitedFromEnd.contains(v)) return distance + 1;
                next.add(v);
            }
        }
        visitedFromStart = next;
        distance++;
    }
    return -1;
}
```

**Сложность:** в среднем `O(b^(d/2))` вместо `O(b^d)` — где `b` — branching factor, `d` — расстояние. На practice экспоненциально быстрее обычного BFS.


> [!mcq] Как работает Bidirectional BFS и какие у него преимущества?
>
> - [ ] A. Bidirectional BFS всегда быстрее обычного BFS на любом графе — потому что идёт сразу с двух сторон.
>
>     **Что на самом деле.** Выигрыш bidirectional BFS зависит от branching factor `b`. На графе с высоким `b` (соцсети с avg degree 200) BFS исследует `O(b^d)`, biBFS — `O(b^(d/2)) = √(b^d)` — экспоненциальный выигрыш. На линейном графе (`b = 1`) оба — `O(V)`, разницы нет; biBFS даже хуже из-за overhead двух фронтов.
>
>     **Откуда путаница.** «Два процесса быстрее одного» — поверхностная интуиция parallelism. На самом деле выигрыш достигается за счёт меньшего объёма исследуемого пространства, а это даётся только на графах с branching.
>
>     **Если бы это было правдой.** Все реализации BFS заменили бы на biBFS — но Apache Spark GraphX оставил обычный BFS для большинства задач (linear chains, narrow graphs), потому что overhead двух фронтов на низкобранчинговых графах перевешивает выигрыш.
>
>     **Как было бы правильно.** Признать: biBFS даёт выигрыш на графах с высоким branching factor (b > 5); на линейных графах overhead не оправдан.
>
> - [ ] B. Bidirectional BFS работает только на невзвешенных ориентированных графах — это ключевое ограничение.
>
>     **Что на самом деле.** biBFS требует возможности **обратного обхода** от `end`. На undirected графе это тривиально (рёбра двунаправленные). На directed нужен `reverse graph` (часто хранится отдельно). На взвешенном графе biBFS можно адаптировать (NBA*, bidirectional Dijkstra), но это сложнее, потому что фронты должны встретиться оптимально — нужно условие остановки `top_f + top_b ≥ best_so_far`.
>
>     **Откуда путаница.** Базовый biBFS показывают на undirected без весов, и кажется, что это его «единственная область». На самом деле он обобщается на directed (с reverse graph) и weighted (bidirectional Dijkstra в OSRM).
>
>     **Если бы это было правдой.** OSRM (open-source routing на дорожных графах — directed weighted) не мог бы использовать biDijkstra — но он использует, потому что на directed работает через precomputed reverse graph.
>
>     **Как было бы правильно.** Сказать: «biBFS работает на любом графе с обратимыми рёбрами (undirected или directed с reverse graph)».
>
> - [ ] C. Bidirectional BFS не даёт точный кратчайший путь — для точности всегда нужен обычный BFS.
>
>     **Что на самом деле.** При корректной реализации biBFS даёт точный кратчайший путь. Условие остановки: когда фронт от start посетит вершину, уже исследованную фронтом от end, проверяем `dist_start + dist_end + 1` (для конкретного ребра между ними). Тонкость — нужно завершить **слой** перед остановкой, иначе можно пропустить более короткий путь через другую вершину того же уровня.
>
>     **Откуда путаница.** Наивная реализация biBFS «останавливается на первой встрече» может пропустить оптимальное пересечение в том же слое — отсюда миф «biBFS неточный». На самом деле проблема в наивной реализации, не в алгоритме.
>
>     **Если бы это было правдой.** LeetCode 127 «Word Ladder» решения с biBFS получали бы WA — но canonical bidirectional-решение принимается на 100% тестов.
>
>     **Как было бы правильно.** Признать: biBFS даёт точный shortest path при корректной обработке слоёв; ошибка только в наивной реализации.
>
> - [x] D. Два BFS-фронта одновременно от start и end; останавливаемся при пересечении фронтов; `O(b^(d/2))` против `O(b^d)` — экспоненциальный выигрыш на графах с branching.
>
>     **Развёрнутое объяснение.** Идея — запустить BFS параллельно с двух сторон: один фронт от `start`, другой от `end`. Когда фронты встречаются (общая вершина или ребро между ними), складываем расстояния → получаем кратчайший путь. Математика выигрыша: обычный BFS исследует `b^d` вершин (where b — branching factor, d — depth); biBFS — `2 · b^(d/2) = 2√(b^d)`. На `b=10, d=6` обычный BFS — `10⁶ = 1M`, biBFS — `2·10³ = 2K` — в 500 раз быстрее. Реализация: альтернируем расширение фронтов; для оптимума всегда расширяем меньший фронт (минимизирует общее число вершин).
>
>     **Пример.** OSRM (Open Source Routing Machine) использует bidirectional Dijkstra для маршрутизации между двумя точками карты — это даёт ms-латентность на графе всей Европы (40M вершин). Google's Pacman pathfinding tutorial использует biBFS для NPC navigation — экспоненциально быстрее обычного BFS. LeetCode «Word Ladder II» с длинными цепочками (15+ слов) — biBFS обязателен для AC, обычный BFS получает TLE. LinkedIn для feature «How you know X» — biBFS от обоих пользователей навстречу.
>
>     **Когда применять.** Когда branching factor высокий (b ≥ 5) и расстояние большое (d ≥ 4); graph allows reverse traversal (undirected или directed с reverse); требуется кратчайший путь между **конкретной парой** start/end (не shortest-paths-from-source). Игровая навигация, social network shortest path, dictionary word transformation, Rubik's cube solver.
>
>     **Подводные камни.** Условие остановки сложнее, чем кажется: первая встреча фронтов — НЕ всегда оптимум; нужно завершить слой и проверить все возможные пересечения. На directed графе требуется хранить reverse-граф — двойная память. Реализация багует на single-edge графах (start = end через одно ребро) — нужны guards `if (start == end) return 0`. Memory остаётся `O(b^(d/2))` — на очень больших графах может не помещаться.
>
>     **Связанные вопросы.** [[graphs-interview#Q5]] BFS базовый алгоритм; [[graphs-interview#Q8]] shortest path в невзвешенном; [[graphs-interview#Q29]] Word Ladder выигрывает от bidirectional.

## Q10. (!) Алгоритм Дейкстры?

Кратчайшие пути от одной вершины до всех в графе с **неотрицательными весами**.

```java
int[] dijkstra(List<List<int[]>> graph, int start) {
    int n = graph.size();
    int[] dist = new int[n];
    Arrays.fill(dist, Integer.MAX_VALUE);
    dist[start] = 0;

    // {distance, vertex}
    PriorityQueue<int[]> pq = new PriorityQueue<>(Comparator.comparingInt(a -> a[0]));
    pq.offer(new int[]{0, start});

    while (!pq.isEmpty()) {
        int[] curr = pq.poll();
        int d = curr[0], u = curr[1];
        if (d > dist[u]) continue; // устаревшая запись

        for (int[] edge : graph.get(u)) {
            int v = edge[0], w = edge[1];
            int newDist = dist[u] + w;
            if (newDist < dist[v]) {
                dist[v] = newDist;
                pq.offer(new int[]{newDist, v});
            }
        }
    }
    return dist;
}
```

| Реализация | Сложность |
|------------|-----------|
| С массивом | `O(V²)` |
| С бинарной кучей | `O((V + E) log V)` |
| С Fibonacci heap | `O(V log V + E)` |

**Применение:** GPS-навигация, IP-маршрутизация (OSPF), сетевая задержка.


> [!mcq] Как работает алгоритм Дейкстры и какие у него ограничения?
>
> - [x] A. Dijkstra: PriorityQueue + relaxation, `O((V+E) log V)` с heap; только неотрицательные веса; применяется в GPS-навигации (Google Maps), IP-маршрутизации (OSPF).
>
>     **Развёрнутое объяснение.** Алгоритм Дейкстры — greedy single-source shortest path для графа с неотрицательными весами. Поддерживает массив `dist[]` (текущие минимальные расстояния от source) и приоритетную очередь по `dist[v]`. На каждом шаге: извлекаем вершину `u` с минимальным `dist[u]` (greedy invariant); для каждого ребра `(u, v, w)` выполняем relaxation: `if dist[u] + w < dist[v]: dist[v] = dist[u] + w; pq.offer(v)`. Greedy invariant работает только при неотрицательных весах: вершина, извлечённая первой, имеет окончательное минимальное расстояние. Сложность с binary heap — `O((V+E) log V)`; с Fibonacci heap — `O(V log V + E)` (теоретически быстрее, на практике константа большая).
>
>     **Пример.** Google Maps использует Dijkstra-подобный алгоритм (точнее, contraction hierarchies — preprocessing-based variant) для маршрутизации. OSPF (Open Shortest Path First) — стандартный IGP-протокол в IP-сетях, где каждый маршрутизатор запускает Dijkstra на link-state database для построения routing table. Yandex Such (поиск маршрутов между остановками) — Dijkstra на multimodal графе (пешеход + транспорт). LeetCode 743 «Network Delay Time» — прямое применение Dijkstra с измерением максимального расстояния от source.
>
>     **Когда применять.** Граф с неотрицательными весами, single-source shortest path; роуминг, network routing (OSPF), доставка (ETA расчёт в Uber), graph queries в Neo4j (`apoc.algo.dijkstra`). Если веса отрицательные → Bellman-Ford; если нужны все пары → Floyd-Warshall на маленьких графах или Johnson's algorithm на больших sparse.
>
>     **Подводные камни.** Lazy deletion в Java PriorityQueue — стандартный workaround отсутствия `decrease-key`: добавляем новую запись с обновлённой дистанцией, старую игнорируем при `poll()` через проверку `if (d > dist[u]) continue`. Память PQ может вырасти до `O(E)` из-за дубликатов. Overflow `Integer.MAX_VALUE + w`: используйте `long` или проверку `if (dist[u] != Integer.MAX_VALUE)`. На очень больших графах (10⁹ вершин) обычный Dijkstra недоступен — применяют contraction hierarchies или distributed graph processing.
>
>     **Связанные вопросы.** [[graphs-interview#Q11]] Bellman-Ford для отрицательных весов; [[graphs-interview#Q12]] почему Dijkstra не работает с negative weights; [[graphs-interview#Q14]] A* как Dijkstra + эвристика.
>
> - [ ] B. Dijkstra работает с отрицательными весами рёбер — алгоритм просто всегда берёт минимальное в каждой итерации.
>
>     **Что на самом деле.** Greedy invariant Dijkstra **ломается** на отрицательных весах: вершина, извлечённая с минимальным `dist[u]`, может быть позже улучшена через путь с отрицательным ребром. Алгоритм даёт некорректные результаты даже без отрицательных циклов. Для negative weights — Bellman-Ford или SPFA.
>
>     **Откуда путаница.** «Берёт минимальное» звучит как универсальное правило, но greedy strategy работает только при условии «лучше уже не станет», которое выполняется только при `w ≥ 0`.
>
>     **Если бы это было правдой.** Forex arbitrage detection (поиск отрицательных циклов в графе валютных пар через log of exchange rates) использовал бы Dijkstra — но реально торговые алгоритмы (HFT-системы Citadel, Jane Street) применяют Bellman-Ford именно для negative cycle detection.
>
>     **Как было бы правильно.** Признать: Dijkstra корректен только на неотрицательных весах; для отрицательных — Bellman-Ford `O(VE)`.
>
> - [ ] C. Dijkstra с отрицательными весами работает, если граф ациклический (DAG).
>
>     **Что на самом деле.** Даже на DAG с negative weights Dijkstra может ошибиться: greedy фиксирует вершину с минимальным `dist[]`, но потом через отрицательное ребро может появиться более короткий путь. Для DAG с любыми (включая отрицательные) весами оптимальный алгоритм — topological sort + relaxation за `O(V+E)`.
>
>     **Откуда путаница.** «На DAG нет циклов, значит negative weight не вызовет проблем» — но проблема Dijkstra не в циклах, а в greedy фиксации. Negative-weight edge может улучшить уже «зафиксированный» dist.
>
>     **Если бы это было правдой.** На LeetCode-подобной задаче с DAG + negative edges использовали бы Dijkstra — но canonical-решение всегда topo sort + relaxation, потому что Dijkstra даёт WA.
>
>     **Как было бы правильно.** Сказать: «на DAG с любыми весами — topological sort + relaxation `O(V+E)`; Dijkstra только при `w ≥ 0`».
>
> - [ ] D. Dijkstra требует `O(V²)` памяти для PriorityQueue, поэтому не масштабируется на большие графы.
>
>     **Что на самом деле.** PriorityQueue в Dijkstra хранит максимум `O(E)` записей (каждое ребро может породить одну запись при relaxation), не `O(V²)`. С lazy deletion общая память — `O(V + E)` = линейная от размера графа. Dijkstra масштабируется до миллионов вершин на одной машине (GPS navigation: 10⁷ вершин дорожной сети).
>
>     **Откуда путаница.** «Может добавить много записей» иногда обобщают до `V²`, но дубликаты в PQ ограничены числом улучшений `dist[v]` — это `O(E)` в худшем случае.
>
>     **Если бы это было правдой.** GPS-системы (Yandex Maps на графе 10⁷ дорог) тратили бы `10¹⁴` бит ≈ 12 TB памяти — нереализуемо. Реально Yandex Maps работает на серверах с обычными 64-128 GB RAM, используя contraction hierarchies + Dijkstra-queries.
>
>     **Как было бы правильно.** Признать: PQ хранит `O(E)` записей; общая память — `O(V+E)`, линейная.

## Q11. (!) Алгоритм Беллмана-Форда?

Кратчайшие пути от одной вершины **с отрицательными весами**. Может обнаружить **отрицательный цикл**.

```java
int[] bellmanFord(int n, List<int[]> edges, int start) {
    int[] dist = new int[n];
    Arrays.fill(dist, Integer.MAX_VALUE);
    dist[start] = 0;

    // V-1 итераций релаксации всех рёбер
    for (int i = 0; i < n - 1; i++) {
        for (int[] edge : edges) {
            int u = edge[0], v = edge[1], w = edge[2];
            if (dist[u] != Integer.MAX_VALUE && dist[u] + w < dist[v]) {
                dist[v] = dist[u] + w;
            }
        }
    }

    // Проверка отрицательного цикла
    for (int[] edge : edges) {
        int u = edge[0], v = edge[1], w = edge[2];
        if (dist[u] != Integer.MAX_VALUE && dist[u] + w < dist[v]) {
            throw new IllegalStateException("Negative cycle detected!");
        }
    }
    return dist;
}
```

`O(V · E)` время. Медленнее Dijkstra, но универсальнее. Применение: forex arbitrage detection, общая маршрутизация с возможными «доплатами».


> [!mcq] Какие особенности отличают Bellman-Ford от Dijkstra и где он применяется?
>
> - [ ] A. Bellman-Ford медленнее Dijkstra и не имеет преимуществ — его сохранили в учебниках только из исторических соображений.
>
>     **Что на самом деле.** Bellman-Ford медленнее по асимптотике (`O(VE)` vs `O((V+E) log V)`), но имеет два уникальных преимущества: (1) поддерживает отрицательные веса рёбер; (2) обнаруживает отрицательные циклы (вторая итерация после V-1 шагов даёт улучшение → есть negative cycle). Это незаменимо для forex arbitrage detection, RIP routing protocol, общих графов с возможными «доплатами».
>
>     **Откуда путаница.** «Медленнее = хуже» — упрощённая логика. На самом деле выбор алгоритма зависит не от скорости, а от поддержки требований (negative weights).
>
>     **Если бы это было правдой.** HFT-системы Jane Street не использовали бы Bellman-Ford для arbitrage detection — но они используют именно его, потому что Dijkstra не умеет detect negative cycles.
>
>     **Как было бы правильно.** Признать: Bellman-Ford медленнее, но единственный практичный general-purpose алгоритм с поддержкой negative weights.
>
> - [x] B. Bellman-Ford: V-1 итераций релаксации всех рёбер; `O(VE)` время; поддерживает отрицательные веса + обнаружение отрицательных циклов; применяется в RIP, forex arbitrage.
>
>     **Развёрнутое объяснение.** Bellman-Ford выполняет `V-1` проходов по всем рёбрам: на каждом проходе релаксирует все рёбра (`if dist[u] + w < dist[v]: dist[v] = dist[u] + w`). Через V-1 итераций все кратчайшие пути найдены (любой simple path в графе из V вершин содержит ≤ V-1 рёбер). Дополнительная V-я итерация: если хоть одно ребро ещё можно релаксировать — есть negative cycle (path можно бесконечно улучшать). Сложность по времени — `O(V·E)`, по памяти — `O(V)` на `dist[]`. Ключевое отличие от Dijkstra: не нужен greedy выбор минимума — все рёбра релаксируются одинаково в каждой итерации.
>
>     **Пример.** RIP (Routing Information Protocol) — distance-vector routing в IP-сетях с метрикой «hop count» — каждый маршрутизатор периодически обновляет таблицу маршрутов через Bellman-Ford-like распространение. Forex arbitrage detection: представляем валюты как вершины, обменные курсы как рёбра с весами `-log(rate)` — отрицательный цикл означает arbitrage opportunity (купить EUR на USD, продать на GBP, обратно в USD с прибылью). LeetCode 787 «Cheapest Flights Within K Stops» — модифицированный Bellman-Ford с ограничением на число итераций (K+1 проходов).
>
>     **Когда применять.** Граф с отрицательными весами (forex, экономические модели), требуется detect negative cycles, distance-vector routing protocols (RIP), задачи с «отрицательными доплатами» (промокоды, скидки в маршрутах доставки). Если веса неотрицательные → Dijkstra (быстрее); если DAG → topological sort + relaxation (`O(V+E)`).
>
>     **Подводные камни.** `Integer.MAX_VALUE + w` → overflow: используйте `long` или явный guard `if (dist[u] != Integer.MAX_VALUE)`. Order of edges в edge list влияет на скорость сходимости (но не на корректность за V-1 итераций) — early termination: если на итерации не было релаксации — можно остановиться. На очень больших графах (10⁸+ рёбер) Bellman-Ford непрактичен; SPFA (Shortest Path Faster Algorithm) — оптимизация, в среднем работает быстрее, хотя worst case тот же `O(VE)`.
>
>     **Связанные вопросы.** [[graphs-interview#Q10]] Dijkstra для неотрицательных весов; [[graphs-interview#Q12]] почему Dijkstra ломается на negative weights; [[graphs-interview#Q13]] Floyd-Warshall для всех пар.
>
> - [ ] C. Bellman-Ford требует сортировки рёбер по весу перед запуском — иначе порядок релаксации даст неверный результат.
>
>     **Что на самом деле.** Bellman-Ford работает корректно при **любом** порядке релаксации рёбер. Гарантия алгоритма: после V-1 проходов по всем рёбрам в любом порядке все shortest paths найдены. Сортировка по весу — это Kruskal MST, не Bellman-Ford.
>
>     **Откуда путаница.** Алгоритмы графов часто путают между собой (Kruskal сортирует рёбра, Bellman-Ford итерирует по ним). Но сортировка в Bellman-Ford избыточна и только добавила бы `O(E log E)` overhead.
>
>     **Если бы это было правдой.** На больших графах с 10⁷ рёбер Bellman-Ford занимал бы дополнительные секунды на сортировку — недопустимо в real-time протоколах вроде OSPF/RIP. Реально RIP сортировку не делает.
>
>     **Как было бы правильно.** Признать: порядок рёбер свободный; гарантия — V-1 проход в любом порядке.
>
> - [ ] D. Bellman-Ford работает только на DAG (ациклических) графах, как и topological sort.
>
>     **Что на самом деле.** Bellman-Ford работает на любом графе: directed/undirected, cyclic/acyclic, с положительными или отрицательными весами. Его сила именно в применимости к cyclic графам (включая обнаружение negative cycles). На DAG используется специализированный алгоритм `topological sort + relaxation` за `O(V+E)`, что быстрее Bellman-Ford `O(VE)`.
>
>     **Откуда путаница.** Слово «cycle» в названии «negative cycle detection» создаёт впечатление, что алгоритм специализирован на циклах. На самом деле он работает с любыми графами, а detection — это побочный бонус.
>
>     **Если бы это было правдой.** Forex arbitrage detection (где циклы — суть задачи) не мог бы работать через Bellman-Ford — но именно через него работает.
>
>     **Как было бы правильно.** Признать: Bellman-Ford работает на любом графе; для DAG быстрее `topological sort + relaxation`.

## Q12. Когда Dijkstra не работает?

**Dijkstra не работает с отрицательными весами.** Жадный выбор минимума может «зафиксировать» вершину с дистанцией, которая позже окажется ошибочной из-за отрицательного ребра.

Пример:
```
A → B: 5
A → C: 4
C → B: -2
```
От A: правильно `dist[B] = 4 + (-2) = 2`. Dijkstra зафиксирует `dist[C] = 4` первым (минимум), потом проверит B через C → 2. Это работает только если **граф не имеет negative cycles** и Dijkstra **не зафиксирует** вершину рано.

На практике — для отрицательных весов используем **Bellman-Ford** или **SPFA**.

Также **Dijkstra медленнее** на плотных графах с heap → лучше использовать массивную реализацию.


> [!mcq] В каких случаях Dijkstra даёт неверный результат?
>
> - [ ] A. Dijkstra ломается только при наличии отрицательного **цикла** — отдельные отрицательные рёбра без цикла обрабатывает корректно.
>
>     **Что на самом деле.** Dijkstra даёт неверный результат при **любых** отрицательных весах, даже без цикла. Греди фиксация вершины может произойти до оптимальной релаксации через отрицательное ребро. Пример: `A→B = 5, A→C = 4, C→B = -2`. Dijkstra зафиксирует `dist[C] = 4` первым (минимум), не учитывая, что через C можно улучшить `dist[B]` до 2. На некоторых графах это даёт правильный результат случайно — но гарантии нет.
>
>     **Откуда путаница.** Negative cycle делает задачу нерешаемой (`dist[v] = -∞`), и кажется, что без цикла всё OK. На самом деле проблема глубже: greedy invariant требует `w ≥ 0`.
>
>     **Если бы это было правдой.** На LeetCode 787 «Cheapest Flights» с отрицательными промокодами (discount edges) использовали бы Dijkstra — но canonical-решение всегда Bellman-Ford-вариант с K шагами, потому что Dijkstra даёт WA на тестах с negative edges.
>
>     **Как было бы правильно.** Признать: Dijkstra корректен только при `w ≥ 0` на всех рёбрах; даже один отрицательный — потенциальная ошибка.
>
> - [ ] B. Dijkstra не работает на направленных графах (digraph) — там нужны другие алгоритмы.
>
>     **Что на самом деле.** Dijkstra работает одинаково корректно на directed и undirected графах с неотрицательными весами. Direction не влияет на алгоритм — он просто следует исходящим рёбрам. На directed reachability может быть несимметричной (`dist[A→B] ≠ dist[B→A]`), но сам алгоритм работает.
>
>     **Откуда путаница.** Некоторые расширения (например, all-pairs Johnson's algorithm) требуют specific графовых свойств, и кажется, что Dijkstra тоже. На самом деле базовый Dijkstra универсален.
>
>     **Если бы это было правдой.** OSPF (link-state routing protocol на directed IP-сетях) не мог бы использовать Dijkstra — но он использует именно Dijkstra. Google Maps на directed дорожной сети (one-way streets) тоже Dijkstra-based.
>
>     **Как было бы правильно.** Признать: Dijkstra работает на directed и undirected; единственное ограничение — `w ≥ 0`.
>
> - [x] C. Dijkstra даёт неверный результат с отрицательными весами (greedy fix ломается); для negative weights используйте Bellman-Ford `O(VE)` или SPFA; для DAG с neg edges — `topological sort + relaxation`.
>
>     **Развёрнутое объяснение.** Корень проблемы — greedy invariant Dijkstra: «вершина с минимальным текущим `dist[u]` имеет окончательное минимальное расстояние». Это верно только при `w ≥ 0`, потому что добавление ребра не может уменьшить путь. При negative edges greedy фиксация может произойти раньше, чем найден оптимальный путь через отрицательное ребро. Пример: `A→B = 5, A→C = 4, C→B = -2`. Dijkstra извлекает C первой (`dist=4`), фиксирует, потом обрабатывает B через C (`dist=2`) — в этом конкретном случае получится правильно, но если бы B был извлечён раньше C (например, при `A→B = 3`), Dijkstra зафиксировал бы `dist[B] = 3`, не заметив улучшения до 2.
>
>     **Пример.** Yandex.Доставка проектирует ETA с учётом промокодов: некоторые рестораны дают -10 минут (отрицательное ребро) для «приоритетной обработки». Если использовать Dijkstra — получают неверные ETA для пользователей с активными промокодами. Реально используют Bellman-Ford-вариант. Forex arbitrage: представить курсы как `-log(rate)` — отрицательные веса означают «выгодная позиция»; Dijkstra пропустил бы arbitrage opportunities, Bellman-Ford находит их через detection negative cycles. LeetCode 787 «Cheapest Flights Within K Stops» — Bellman-Ford с K итерациями вместо Dijkstra.
>
>     **Когда применять.** Если веса могут быть отрицательными (промокоды, скидки, экономические модели) — Bellman-Ford `O(VE)` или SPFA (faster average). Если DAG с любыми весами — topological sort + relaxation за `O(V+E)`. Если ВСЕ веса неотрицательные — Dijkstra `O((V+E) log V)`. Johnson's algorithm — для all-pairs shortest path на больших sparse графах с negative weights (reweight через Bellman-Ford, потом Dijkstra от каждой вершины).
>
>     **Подводные камни.** «Все веса неотрицательные» может быть ложным предположением — проверять на edge cases (промокоды, отрицательные таймауты, оптимизации). На некоторых тестах Dijkstra даёт правильный ответ случайно — но это не гарантия. SPFA (Bellman-Ford с queue) популярен на competitive programming, но имеет worst case `O(VE)` — на adversarial graphs deteriorate. Для distributed systems Bellman-Ford лучше — каждый узел может работать независимо.
>
>     **Связанные вопросы.** [[graphs-interview#Q10]] Dijkstra правила и алгоритм; [[graphs-interview#Q11]] Bellman-Ford как альтернатива; [[graphs-interview#Q24]] DAG topological sort + relaxation.
>
> - [ ] D. Dijkstra перестаёт работать на графах более 10K вершин — слишком медленный.
>
>     **Что на самом деле.** Dijkstra с binary heap масштабируется до миллионов вершин: `O((V+E) log V)` на графе 10⁶ вершин и 10⁷ рёбер — это `10⁸` операций ≈ 1 секунда. Google Maps работает на графе 10⁷ дорог; Yandex Maps — 10⁸. На очень больших графах (10⁹+) применяют contraction hierarchies + Dijkstra-подобный query.
>
>     **Откуда путаница.** Производительность зависит от V и E, не только от V; на dense графе с V=10K и E=10⁸ Dijkstra медленный, на sparse с теми же V — быстрый.
>
>     **Если бы это было правдой.** Yandex Maps работал бы только на маленьких городах (10K дорог) — но он работает на всей России с миллионами дорог.
>
>     **Как было бы правильно.** Сказать: «Dijkstra масштабируется до миллионов вершин; на 10⁹+ нужны specialized techniques (CH, ALT)».

## Q13. (!) Floyd-Warshall — все пары?

Кратчайшие пути **между всеми парами** вершин. Работает с любыми весами (без отрицательных циклов).

```java
int[][] floydWarshall(int[][] graph) {
    int n = graph.length;
    int[][] dist = new int[n][n];
    for (int i = 0; i < n; i++) dist[i] = graph[i].clone();

    for (int k = 0; k < n; k++) {
        for (int i = 0; i < n; i++) {
            for (int j = 0; j < n; j++) {
                if (dist[i][k] != Integer.MAX_VALUE
                    && dist[k][j] != Integer.MAX_VALUE
                    && dist[i][k] + dist[k][j] < dist[i][j]) {
                    dist[i][j] = dist[i][k] + dist[k][j];
                }
            }
        }
    }
    return dist;
}
```

`O(V³)` время, `O(V²)` память. Идеален для **малых плотных графов** (до 500 вершин). Для большего — все пары через Dijkstra/Bellman-Ford от каждой вершины.


> [!mcq] Что вычисляет Floyd-Warshall и каковы его границы применимости?
>
> - [ ] A. Floyd-Warshall работает только для пути между двумя конкретными вершинами — это специализированный алгоритм.
>
>     **Что на самом деле.** Floyd-Warshall вычисляет **все пары** кратчайших путей одновременно: на выходе матрица `dist[i][j]` для всех i, j. Это его killer feature и оправдывает `O(V³)`. Для одной пары лучше Dijkstra `O((V+E) log V)` — не тратить cube на ненужные пары.
>
>     **Откуда путаница.** Можно знать только базовое название «shortest path algorithm» и думать, что это всё то же самое. На самом деле Floyd-Warshall — единственный из «учебной троицы» (BFS, Dijkstra, Floyd), который даёт all-pairs.
>
>     **Если бы это было правдой.** Telecom-сети для расчёта матрицы latency между всеми pairs дата-центров не могли бы использовать Floyd — но именно его используют для small dense networks (50 узлов).
>
>     **Как было бы правильно.** Сказать: «Floyd-Warshall — all-pairs; для single source/pair → Dijkstra/Bellman-Ford».
>
> - [ ] B. Floyd-Warshall быстрее Dijkstra для разреженных графов — три цикла эффективнее heap.
>
>     **Что на самом деле.** Floyd-Warshall — `O(V³)` независимо от плотности. На sparse графе запуск Dijkstra от каждой вершины — `O(V·(V+E) log V) ≈ O(V² log V)`, что быстрее `V³` при `E ≪ V²`. Например, для V=1000, E=5000 (sparse): Floyd — `10⁹`, Dijkstra×V — `5·10⁶·10 = 5·10⁷` — в 20 раз быстрее.
>
>     **Откуда путаница.** Простота кода (три вложенных цикла) создаёт впечатление efficiency. На самом деле простота ≠ скорость; cube остаётся cube.
>
>     **Если бы это было правдой.** Yandex.Маршруты использовали бы Floyd на сети дорог России (10⁸ дорог) — это `10²⁴` операций, физически невозможно. Реально используют contraction hierarchies.
>
>     **Как было бы правильно.** Признать: Floyd — `O(V³)` всегда; на sparse выгоден Dijkstra от каждой вершины или Johnson's algorithm.
>
> - [ ] C. Floyd-Warshall не работает с отрицательными весами рёбер — это фундаментальное ограничение.
>
>     **Что на самом деле.** Floyd-Warshall **поддерживает** отрицательные веса (это его преимущество перед all-pairs Dijkstra). Не работает только при наличии отрицательного **цикла** — тогда `dist[i][i]` становится отрицательным (бесконечно уменьшающийся путь). Обнаружение neg cycle: после алгоритма проверить `dist[i][i] < 0` для какого-то i.
>
>     **Откуда путаница.** Путают Floyd с Dijkstra: Dijkstra не работает с negative weights, Floyd — работает. Названия похожи (оба shortest path), ограничения разные.
>
>     **Если бы это было правдой.** Forex arbitrage detection (где negative weights — суть) не использовал бы Floyd — но реально применяют Floyd-Warshall именно для cross-currency arbitrage matrix (small dense graph валютных пар).
>
>     **Как было бы правильно.** Признать: Floyd поддерживает negative weights; не работает только при negative cycles.
>
> - [x] D. Floyd-Warshall: `O(V³)` время, `O(V²)` память; вычисляет кратчайшие пути между всеми парами вершин; поддерживает отрицательные веса (но не отрицательные циклы); применяется на dense графах V ≤ 500.
>
>     **Развёрнутое объяснение.** Floyd-Warshall — dynamic programming алгоритм для all-pairs shortest paths. Идея: `dist[i][j]` через промежуточные вершины `0..k` вычисляется через `dist[i][j] = min(dist[i][j], dist[i][k] + dist[k][j])`. Внешний цикл по `k`, внутренние по `i, j` — три вложенных цикла, `O(V³)`. Память — `O(V²)` на матрицу. Базовая инициализация: `dist[i][i] = 0`, `dist[i][j] = weight(i,j)` если есть ребро, иначе `∞`. Поддерживает negative weights благодаря отсутствию greedy invariant (как у Dijkstra). Negative cycle detection: после алгоритма проверить `dist[i][i] < 0` — означает, что i достижим сам через отрицательный цикл.
>
>     **Пример.** Cisco IOS использует Floyd-Warshall на маленьких маршрутизаторах для backup routing table calculations (50 узлов на отдельном свитче). Telecom-операторы рассчитывают latency matrix между 200 дата-центрами через Floyd — на современном CPU 200³ = `8·10⁶` операций ≈ 100 мс. LeetCode 1334 «Find the City With the Smallest Number of Neighbors at a Threshold Distance» — прямое применение Floyd-Warshall (V ≤ 100). Compiler optimization: transitive closure of dependencies — частный случай Floyd с `min → and`/`max → or`.
>
>     **Когда применять.** Маленький dense граф (V ≤ 500), нужны все пары shortest paths, возможны отрицательные веса. Граф маршрутизации внутри одного дата-центра, decision-making с матрицей переходов между состояниями, latency planning между сервисами в Service Mesh, anomaly detection в small graphs (transitive reachability). Если V > 500 на sparse → Johnson's algorithm; если нужна только одна пара → Dijkstra/Bellman-Ford.
>
>     **Подводные камни.** Overflow `dist[i][k] + dist[k][j]` при `Integer.MAX_VALUE` — нужна явная проверка `if (dist[i][k] != INF && dist[k][j] != INF)`. Negative cycle ломает алгоритм без явного detection — `dist[i][i]` становится `-∞` после нескольких итераций. Для path reconstruction нужна дополнительная матрица `next[i][j] = k` (через какую вершину идти). Memory `O(V²)` — на V=1000 это 4 MB (int) или 8 MB (long); на V=5000 — 100 MB, может не помещаться в L3-кэш.
>
>     **Связанные вопросы.** [[graphs-interview#Q10]] Dijkstra для single-source; [[graphs-interview#Q11]] Bellman-Ford для negative weights; [[graphs-interview#Q4]] dense vs sparse как критерий выбора.

## Q14. A* поиск — что это?

**A* (A-star)** — расширение Dijkstra с **эвристикой** для ускорения.

```
f(n) = g(n) + h(n)
g(n) — фактическое расстояние от start до n
h(n) — эвристическая оценка от n до end (admissible — не переоценивает)
```

Если `h(n) ≡ 0` — это Dijkstra. Если `h` точная — A* идёт прямо к цели.

**Применения:** игровая навигация (NPC patfinding), GPS, robotics.

```java
// Эвристика для grid: Manhattan / Euclidean distance
int manhattan(int[] a, int[] b) {
    return Math.abs(a[0] - b[0]) + Math.abs(a[1] - b[1]);
}
```


> [!mcq] Что такое A* и как он отличается от Dijkstra?
>
> - [x] A. A* = Dijkstra + эвристика `h(n)`; `f(n) = g(n) + h(n)`, где g — фактическое расстояние, h — оценка до цели; admissible h гарантирует оптимальность; быстрее Dijkstra для точечного поиска (start → end).
>
>     **Развёрнутое объяснение.** A* обобщает Dijkstra, добавляя heuristic-функцию `h(n)`, оценивающую расстояние от `n` до цели. Алгоритм извлекает из priority queue вершину с минимальным `f(n) = g(n) + h(n)`, где `g(n)` — фактическая стоимость пути от start до n. Условие корректности — **admissible heuristic**: `h(n) ≤ actual distance from n to goal` (никогда не переоценивает). Если h admissible, A* гарантированно находит оптимальный путь, посещая обычно меньше вершин, чем Dijkstra. При `h ≡ 0` A* идентичен Dijkstra; при идеальной h (равной точному расстоянию) A* идёт прямо к цели, посещая `O(d)` вершин (где d — длина пути).
>
>     **Пример.** Видеоигры (Unity, Unreal Engine) используют A* для NPC pathfinding на навигационной сетке (NavMesh). Эвристика — Euclidean distance на 2D/3D. StarCraft II AI бот навигирует юнитов через A* с обновлением весов при изменениях terrain. OSRM (Open Source Routing Machine) для веломаршрутов использует A* с эвристикой «расстояние по прямой × коэффициент извилистости». ChessBot/AlphaGo используют A*-варианты для search через game tree (на самом деле — Monte Carlo Tree Search, но идея похожа).
>
>     **Когда применять.** Известна geometric структура графа (grid, 2D/3D space), есть естественная эвристика (Manhattan distance для 4-связной сетки, Euclidean для 8-связной или непрерывного пространства, Haversine для географии). Игровая навигация, GPS-маршрутизация, robotics (motion planning), procedural generation. Если эвристики нет — обычный Dijkstra.
>
>     **Подводные камни.** **Admissibility** легко нарушить — overestimating эвристика даёт неоптимальный путь (но обычно быстрее работает — trade-off). **Consistent** (monotonic) эвристика — сильнее admissibility: `h(u) ≤ cost(u, v) + h(v)` для всех соседей. Consistent гарантирует, что вершина больше не пересматривается после первого extract — нет необходимости в lazy deletion. На многих задачах admissible+consistent эвристики не существует — приходится compromise. Memory consumption A* ≈ Dijkstra на worst case — оба `O(V)`.
>
>     **Связанные вопросы.** [[graphs-interview#Q10]] Dijkstra как частный случай A* (h=0); [[graphs-interview#Q5]] BFS как Dijkstra с unit weights; [[graphs-interview#Q30]] Network Delay как пример Dijkstra-задачи.
>
> - [ ] B. A* с эвристикой `h(n) = 0` быстрее Dijkstra — не вычисляет лишнего на эвристике.
>
>     **Что на самом деле.** A* с `h ≡ 0` **идентичен** Dijkstra по поведению — `f(n) = g(n) + 0 = g(n)`, то есть PQ ранжирует по `g(n)`, ровно как Dijkstra. Никакого выигрыша от «отсутствия эвристики» нет. Смысл A* в **ненулевой** эвристике, которая направляет поиск к цели.
>
>     **Откуда путаница.** «Меньше вычислений = быстрее» — обычно верно, но в A* эвристика — это **компас**, без которого алгоритм не отличается от Dijkstra.
>
>     **Если бы это было правдой.** Game engine Unity использовал бы A* с h=0 для NPC pathfinding — и получал бы те же характеристики, что Dijkstra. На практике эвристика Manhattan/Euclidean даёт 5-100× ускорение на типичных levels.
>
>     **Как было бы правильно.** Признать: A* без эвристики = Dijkstra; смысл A* — в ненулевой informed heuristic.
>
> - [ ] C. A* с admissible эвристикой может не найти оптимальный путь — admissibility не гарантирует optimality.
>
>     **Что на самом деле.** Admissible эвристика **гарантирует** optimality A* по теореме Hart-Nilsson-Raphael (1968). Доказательство: вершина с минимальным `f` извлекается первой; admissibility означает, что `g(goal) ≤ f(n)` для всех ещё не извлечённых n; первая extracted goal — оптимальная. Inadmissible эвристика (over-estimating) ломает гарантию optimality, но обычно ускоряет.
>
>     **Откуда путаница.** Существуют edge cases (consistency != admissibility), и кажется, что admissible недостаточно. На самом деле admissible — достаточное условие для optimality (но не для эффективности без re-opening).
>
>     **Если бы это было правдой.** OSRM bidirectional A* не мог бы гарантировать optimal routes — но именно гарантирует благодаря admissible Haversine эвристике.
>
>     **Как было бы правильно.** Признать: admissible → optimality гарантирована; inadmissible — может быть suboptimal но обычно быстрее.
>
> - [ ] D. A* не работает в 3D-пространстве, только в 2D grid.
>
>     **Что на самом деле.** A* работает в любом пространстве с подходящей эвристикой. Для 3D — Euclidean distance `sqrt(dx² + dy² + dz²)` или Manhattan distance `|dx| + |dy| + |dz|` (для 6-связной сетки). Robotics motion planning (manipulator arm в 7-мерном configuration space) тоже использует A*.
>
>     **Откуда путаница.** Базовые туториалы A* показывают на 2D grid (LeetCode-стиль задачи), и кажется, что это его область. На самом деле A* размерно-независим.
>
>     **Если бы это было правдой.** Boston Dynamics Spot robot не мог бы планировать пути через 3D-пространство — но он использует A* варианты для motion planning.
>
>     **Как было бы правильно.** Признать: A* работает в N-мерном пространстве с подходящей эвристикой.

## Q15. (!) Что такое MST?

**Minimum Spanning Tree (MST)** — подмножество рёбер, образующее **дерево** на всех вершинах с минимальной суммой весов.

Применения:
- Прокладка кабельной сети
- Организация коммуникаций (telecom)
- Кластеризация
- Approximation algorithms (TSP)

Существует два классических алгоритма: **Краскала** и **Прима**.


> [!mcq] Что такое Minimum Spanning Tree и какие задачи он решает?
>
> - [ ] A. MST находит кратчайший путь между двумя вершинами в графе — это разновидность shortest path.
>
>     **Что на самом деле.** MST — дерево, **покрывающее ВСЕ вершины** с минимальной **суммой весов рёбер**. Это глобальная оптимизация, не задача «между парой». Shortest path (Dijkstra/BFS) минимизирует расстояние от source до конкретной target, MST минимизирует общую стоимость соединения всех вершин. На одном и том же графе MST и shortest path могут включать совершенно разные рёбра.
>
>     **Откуда путаница.** Оба алгоритма минимизируют «что-то с весами», и кажется, что они эквивалентны. На самом деле они оптимизируют разные метрики: shortest path — длина одного пути, MST — общая стоимость.
>
>     **Если бы это было правдой.** Прокладка телефонного кабеля между офисами компании выбиралась бы через shortest path от штаб-квартиры — но реально это MST-задача (объединить все офисы с минимальным расходом кабеля).
>
>     **Как было бы правильно.** Признать: MST — глобальная (все вершины); shortest path — локальная (между парой).
>
> - [x] B. MST = подмножество ровно `V-1` рёбер, покрывающее все V вершин (без циклов) с минимальной суммой весов; алгоритмы — Kruskal (sort + Union-Find) и Prim (PriorityQueue).
>
>     **Развёрнутое объяснение.** MST для weighted undirected connected graph — это spanning tree (связное подмножество, включающее все V вершин с V-1 рёбрами без циклов) с минимальной суммой весов. Существование: для любого связного weighted графа MST существует, но может быть не единственным. Два классических алгоритма: **Kruskal** — сортируем рёбра по весу, добавляем по одному в MST если не образуют цикл (Union-Find для cycle check); `O(E log E)`. **Prim** — растим MST из одной вершины, добавляя минимальное outgoing edge; PriorityQueue для выбора минимального ребра; `O(E log V)`. Оба алгоритма greedy и корректны благодаря cut property: для любого cut графа (разбиение на две части) минимальное cross-edge принадлежит MST.
>
>     **Пример.** Прокладка оптоволоконной сети между городами: МТС/Билайн строят MST дерево, минимизируя общую длину кабеля. Telecom backbone-планирование: Cisco IOS использует Prim's algorithm для построения spanning tree на маршрутизаторах (STP — Spanning Tree Protocol). Кластеризация в ML: single-linkage clustering = MST + cut k-1 longest edges → k clusters. Boruvka algorithm (parallel MST) используется в Apache Spark GraphX для больших графов. TSP (Traveling Salesman) approximation: 2-approximation алгоритм основан на MST + DFS traversal.
>
>     **Когда применять.** Соединить все вершины с минимальной общей стоимостью: networking (telecom, internet backbone, LAN cabling), кластеризация (single-linkage в ML), image segmentation (MST cut), approximation algorithms (TSP, Steiner tree). На undirected weighted графах — все классические MST алгоритмы. Для directed используют specialized variants (arborescence minimum spanning).
>
>     **Подводные камни.** MST уникален **только если все веса различны** — при равных весах возможны разные MST с одинаковой общей стоимостью. На несвязном графе MST не существует; Kruskal естественно даёт MSF (Minimum Spanning Forest), Prim требует запуска от каждой компоненты. Для directed графов нужны spanning arborescence (Chu-Liu/Edmonds algorithm) — намного сложнее. На очень больших графах (10⁹+ рёбер) обычные алгоритмы непрактичны; распределённый Boruvka в Spark GraphX.
>
>     **Связанные вопросы.** [[graphs-interview#Q16]] Kruskal детально; [[graphs-interview#Q17]] Prim детально; [[graphs-interview#Q18]] Kruskal vs Prim сравнение.
>
> - [ ] C. MST уникален — существует ровно один MST для любого weighted графа.
>
>     **Что на самом деле.** MST уникален **только** если все веса рёбер различны. При равных весах могут существовать несколько MST с одинаковой минимальной суммой. Theorem: MST уникален ⟺ для любого cycle в графе максимальный вес ребра в цикле уникален.
>
>     **Откуда путаница.** Слово «minimum» подразумевает «единственный наименьший» по аналогии с числами. Но MST — это структура, а не число; разные структуры могут давать одинаковую сумму.
>
>     **Если бы это было правдой.** Алгоритмы Kruskal и Prim давали бы всегда одинаковое дерево — но это верно только при уникальных весах. На графах с равными весами они могут вернуть разные MST.
>
>     **Как было бы правильно.** Признать: MST уникален только при попарно различных весах; иначе — несколько MST с одинаковой суммой.
>
> - [ ] D. MST применяется только к невзвешенным графам — где все рёбра одинаковы.
>
>     **Что на самом деле.** MST по определению — оптимизация **суммы весов**. На невзвешенном графе (все веса 1) любое spanning tree — MST (сумма = V-1). Задача MST становится тривиальной (BFS/DFS даёт результат). MST имеет смысл только на weighted графах.
>
>     **Откуда путаница.** Слово «minimum» можно интерпретировать как «минимальное число рёбер» — но V-1 фиксировано для любого spanning tree. «Minimum» относится именно к сумме весов.
>
>     **Если бы это было правдой.** Telecom backbone planning (выбор маршрутов с разной длиной кабеля) не использовал бы MST — но именно использует, потому что длина кабеля = вес ребра.
>
>     **Как было бы правильно.** Признать: MST — для weighted graphs; на невзвешенном тривиально (любое spanning tree).

## Q16. (!) Алгоритм Краскала?

**Идея:** сортируем рёбра по весу, добавляем по одному, если не образуют цикл (используем **Union-Find**).

```java
int kruskalMST(int n, List<int[]> edges) {
    edges.sort(Comparator.comparingInt(e -> e[2])); // по весу
    UnionFind uf = new UnionFind(n);
    int totalWeight = 0, edgesUsed = 0;

    for (int[] e : edges) {
        int u = e[0], v = e[1], w = e[2];
        if (uf.union(u, v)) {
            totalWeight += w;
            if (++edgesUsed == n - 1) break;
        }
    }
    return totalWeight;
}
```

`O(E log E)` — доминирует сортировка. С Union-Find и path compression — почти `O(E α(V))` для остальной работы.

**Лучше для разреженных графов** (когда `E` маленькое).


> [!mcq] Как работает алгоритм Краскала?
>
> - [ ] A. Kruskal требует хранить весь граф в матрице смежности — без неё невозможна работа.
>
>     **Что на самом деле.** Kruskal работает с **edge list** — простым `List<Edge>`. Матрица смежности не нужна, даже мешает (требует `O(V²)` памяти при обычно sparse-графах). Алгоритм только сортирует рёбра и проверяет цикл через Union-Find — обе операции совместимы с edge list.
>
>     **Откуда путаница.** Учебники иногда показывают graph как матрицу для наглядности, и кажется, что это требование. На самом деле edge list — естественное представление для Kruskal.
>
>     **Если бы это было правдой.** На графе 10⁹ вершин и 10¹⁰ рёбер (telecom backbone planning) Kruskal требовал бы `10¹⁸` бит памяти на матрицу — невозможно. Реально работает на edge list: `10¹⁰ × 12 bytes ≈ 120 GB` (помещается на cluster).
>
>     **Как было бы правильно.** Признать: Kruskal — edge list; сортировка по весу + Union-Find для cycle detection.
>
> - [ ] B. Kruskal лучше Prim во всех случаях — нужно всегда выбирать его как более простой.
>
>     **Что на самом деле.** Kruskal `O(E log E)` лучше для **sparse** графов (E маленькое, `log E ≈ log V`). Prim `O(E log V)` с binary heap лучше для **dense** графов (где сортировка всех рёбер дорогая). Prim с Fibonacci heap — `O(E + V log V)`, асимптотически лучший. На dense графе Prim с матрицей — `O(V²)`, что лучше Kruskal `O(E log E) = O(V² log V)` на dense.
>
>     **Откуда путаница.** «Простой = лучше» — поверхностно. На самом деле выбор зависит от плотности графа.
>
>     **Если бы это было правдой.** На dense графе 1000 вершин и 500K рёбер: Kruskal — `5·10⁵·log(5·10⁵) = 10⁷`, Prim с матрицей — `10⁶` — в 10 раз быстрее. Telecom backbone с full mesh использует Prim.
>
>     **Как было бы правильно.** Сказать: «Kruskal — для sparse; Prim — для dense; выбор зависит от `E/V²`».
>
> - [x] C. Kruskal: сортируем рёбра по весу `O(E log E)`, добавляем по одному в MST если не образуют цикл (Union-Find для cycle check); `O(E log E)`; лучше для sparse графов.
>
>     **Развёрнутое объяснение.** Идея — глобально greedy: сортируем все рёбра по весу, идём от меньшего к большему, добавляем ребро в MST если его концы ещё не в одной компоненте (Union-Find проверка). Корректность по cut property: при добавлении ребра `(u, v)` с минимальным весом, не образующего цикл, для любого cut, отделяющего u и v, это ребро минимально среди cross-edges → принадлежит MST. Сложность: сортировка — `O(E log E)`, V-1 union/find операций — `O(E α(V))` с path compression + union by rank (`α` — обратная Аккермана, практически константа). Суммарно `O(E log E) = O(E log V)` (так как `E ≤ V²`).
>
>     **Пример.** Apache Hadoop MR-job для построения backbone сети из 10⁶ городов и 10⁷ дорог: Kruskal с distributed sort + Union-Find. Bouncy Castle library в Java использует Kruskal-like algorithm для optimal certificate chain selection. Yandex.Маршруты: построение зон доставки через MST по граф'у складов. LeetCode 1135 «Connecting Cities With Minimum Cost» — прямое применение Kruskal с UF.
>
>     **Когда применять.** Sparse граф `E << V²` (большинство telecom-сетей, road networks); рёбра уже отсортированы (например, после streaming-сортировки в Spark) — экономия на sorting step; нужен minimum spanning forest на несвязном графе (Kruskal естественно его даёт). Если граф dense → Prim; если ультра-большой → distributed Boruvka.
>
>     **Подводные камни.** Union-Find без path compression и union by rank — `O(V)` на одну операцию, общее `O(V·E)` — катастрофично. Без правильной UF Kruskal асимптотически медленный. Сортировка стабильна — это важно для воспроизводимости MST на графах с равными весами. На несвязном графе Kruskal даёт MSF (forest); MST не существует — нужно явно проверить `edgesUsed == V - 1` после алгоритма.
>
>     **Связанные вопросы.** [[graphs-interview#Q15]] MST определение; [[graphs-interview#Q17]] Prim как альтернатива; [[graphs-interview#Q18]] Kruskal vs Prim сравнение.
>
> - [ ] D. Kruskal не работает для несвязных графов — алгоритм падает с ошибкой.
>
>     **Что на самом деле.** Kruskal естественно обрабатывает несвязные графы: для каждой connected компоненты строит MST, результат — minimum spanning forest (MSF). Алгоритм не падает; просто `edgesUsed < V-1` означает, что граф несвязный.
>
>     **Откуда путаница.** MST по строгому определению требует, чтобы граф был связным. На несвязном MST не существует. Но Kruskal даёт MSF без всяких изменений — он не различает «связный» и «несвязный» case.
>
>     **Если бы это было правдой.** Telecom-планирование для двух изолированных регионов (без связей между ними) не могло бы использовать Kruskal — пришлось бы строить отдельные MST вручную. Реально Kruskal даёт MSF на одном проходе.
>
>     **Как было бы правильно.** Признать: Kruskal даёт MSF (forest) на несвязных графах; Prim требует связного графа или явного запуска от каждой компоненты.

## Q17. (!) Алгоритм Прима?

**Идея:** растим MST из одной вершины, добавляя минимальное ребро, выходящее из текущего дерева.

```java
int primMST(List<List<int[]>> adj) {
    int n = adj.size();
    boolean[] inMST = new boolean[n];
    PriorityQueue<int[]> pq = new PriorityQueue<>(Comparator.comparingInt(a -> a[1]));
    pq.offer(new int[]{0, 0}); // {vertex, weight}
    int totalWeight = 0, edgesUsed = 0;

    while (!pq.isEmpty() && edgesUsed < n) {
        int[] curr = pq.poll();
        int u = curr[0], w = curr[1];
        if (inMST[u]) continue;
        inMST[u] = true;
        totalWeight += w;
        edgesUsed++;
        for (int[] edge : adj.get(u)) {
            if (!inMST[edge[0]]) pq.offer(new int[]{edge[0], edge[1]});
        }
    }
    return totalWeight;
}
```

`O(E log V)` с binary heap. **Лучше для плотных графов**.


> [!mcq] Как работает алгоритм Прима?
>
> - [ ] A. Prim не работает для несвязных графов — приходится использовать только Kruskal.
>
>     **Что на самом деле.** Prim требует связного графа для построения полного MST. Но на несвязном графе можно запустить Prim **от каждой компоненты** — результат тот же MSF, что Kruskal даёт естественно. Kruskal удобнее на несвязных, но Prim не «не работает» — нужны лишь дополнительные шаги.
>
>     **Откуда путаница.** Базовая реализация Prim начинается от одной вершины и не выходит за пределы её компоненты. Кажется, что алгоритм фундаментально ограничен. На самом деле это implementation detail — обертка с внешним циклом по непосещённым вершинам решает проблему.
>
>     **Если бы это было правдой.** Распределённая система с двумя изолированными регионами (без связей) не могла бы использовать Prim — но при добавлении внешнего цикла работает.
>
>     **Как было бы правильно.** Сказать: «Prim требует связности; на несвязном — запускать от каждой компоненты или использовать Kruskal».
>
> - [ ] B. Prim и Kruskal всегда возвращают **разные** MST-деревья — это особенность алгоритмов.
>
>     **Что на самом деле.** При **уникальных** весах MST единственный — оба алгоритма возвращают **одно и то же** дерево. При равных весах могут вернуться разные MST с одинаковой суммой (рёбра с равным весом выбираются в разном порядке).
>
>     **Откуда путаница.** Алгоритмы работают по разному принципу (global edges vs local growth), и кажется, что результаты должны отличаться. На самом деле MST как объект однозначен, если веса уникальны.
>
>     **Если бы это было правдой.** Тесты, сравнивающие выход Prim и Kruskal, всегда падали бы — на практике они проходят на графах с уникальными весами.
>
>     **Как было бы правильно.** Признать: при уникальных весах MST единственный и оба алгоритма дают одинаковое дерево; различия только на ties.
>
> - [ ] C. Prim медленнее Kruskal на sparse графах — Prim — это только для dense.
>
>     **Что на самом деле.** На sparse графе оба алгоритма имеют близкую асимптотику: Prim — `O(E log V)`, Kruskal — `O(E log E) = O(E log V)`. Разница в константах: Kruskal требует одного большого sort step, Prim — много heap-операций. На очень малых sparse графах Kruskal часто немного быстрее (sort cache-friendly). На dense Prim выигрывает значительно.
>
>     **Откуда путаница.** «Prim для dense» — упрощённое правило. На sparse оба применимы.
>
>     **Если бы это было правдой.** Только Kruskal использовали бы на дорожных сетях — но Prim тоже корректен, просто чуть медленнее на ультра-sparse.
>
>     **Как было бы правильно.** Признать: на sparse оба `O(E log V)`; на dense Prim с матрицей `O(V²)` лучше.
>
> - [x] D. Prim: PriorityQueue + растим MST из выбранной вершины, добавляя минимальное outgoing edge; `O(E log V)` с heap; лучше для dense графов; Kruskal — `O(E log E)`, лучше для sparse.
>
>     **Развёрнутое объяснение.** Prim — локально greedy: начинаем с одной вершины (MST = {v}), на каждом шаге добавляем ребро минимального веса, выходящее из MST (соединяющее MST с не-MST вершиной). Реализация: priority queue с элементами `(weight, vertex)`; извлекаем минимальное; если vertex ещё не в MST — добавляем; релаксируем outgoing edges (как в Dijkstra). Корректность по cut property: для cut (MST, not-MST) минимальное cross-edge принадлежит MST. Сложность с binary heap — `O(E log V)`, с Fibonacci heap — `O(E + V log V)`, с матрицей (для dense) — `O(V²)` без heap (просто linear scan).
>
>     **Пример.** Cisco STP (Spanning Tree Protocol) на switches использует Prim-like algorithm для построения loop-free L2 топологии — каждый switch выбирает root port (минимальный path cost). Apache Spark GraphX `runMST` использует distributed Boruvka (родственник Prim) для больших графов. Network design: Booking.com проектирует backbone между data centers через Prim на dense графе (full mesh кандидатов) с весами = latency + cost. LeetCode 1584 «Min Cost to Connect All Points» — Prim на dense complete graph (V² рёбер) даёт лучшее решение, чем Kruskal с явной сортировкой.
>
>     **Когда применять.** Dense граф `E ≈ V²` (full mesh networks, complete graphs с N²); рёбра не упорядочены и в потоковом виде (computing edges on demand); инкрементальное добавление вершин (online MST). Если граф sparse → Kruskal часто проще; если несвязный → Kruskal естественно даёт MSF.
>
>     **Подводные камни.** PriorityQueue без `decrease-key` (Java `java.util.PriorityQueue`) → lazy deletion: добавляем новые записи, старые игнорируем — память может вырасти до `O(E)`. Worst case на adversarial graphs. Параллелизация Prim сложна — последовательный growth tree; параллельный Kruskal реализуется через distributed sort. Cache locality на Prim хуже Kruskal — random access к соседним spisкам vs последовательный scan отсортированного списка.
>
>     **Связанные вопросы.** [[graphs-interview#Q15]] MST определение; [[graphs-interview#Q16]] Kruskal как альтернатива; [[graphs-interview#Q18]] Kruskal vs Prim детальное сравнение.

## Q18. Чем Краскал отличается от Прима?

| Критерий | Kruskal | Prim |
|----------|---------|------|
| Структура | Сортировка + Union-Find | Priority queue |
| Сложность | `O(E log E)` | `O(E log V)` |
| Подход | Глобальный (по всем рёбрам) | Локальный (растёт из вершины) |
| Лучше для | Разреженных | Плотных |
| Параллелизация | Сложно | Легко |
| Связан ли граф | Не требуется | Требуется (или возвращает MST компоненты) |

Оба дают одинаковый MST по весу (если веса уникальны — и идентичные деревья).


> [!mcq] Чем Kruskal отличается от Prim по подходу и применимости?
>
> - [x] A. Kruskal: глобально-greedy по рёбрам (sort + Union-Find), `O(E log E)`, лучше для sparse; Prim: локально-greedy от вершины (PQ + grow), `O(E log V)`, лучше для dense; оба дают одинаковый MST по весу (при уникальных весах — то же дерево).
>
>     **Развёрнутое объяснение.** Принципиальное различие — strategy. Kruskal смотрит на **всё множество рёбер глобально**: сортирует по весу и добавляет минимальное не образующее цикл. Prim смотрит **локально из текущего MST**: добавляет минимальное outgoing edge. Оба greedy и корректны по cut property, но конкретная реализация и performance различаются. Kruskal естественно даёт minimum spanning **forest** на несвязном графе; Prim строит дерево одной компоненты, требуя внешний цикл для несвязных. Параллелизация: Kruskal легко через distributed sort + Union-Find (Boruvka algorithm); Prim сложнее — последовательный growth.
>
>     **Пример.** Cisco STP на свитчах использует Prim-like (root switch → grow tree через минимальные path costs) — потому что MST строится локально из root. Telecom planning между 10⁶ городов — Kruskal с distributed sort (Apache Spark + Union-Find). Image segmentation Felzenszwalb-Huttenlocher algorithm — Kruskal вариант с adaptive threshold на каждом шаге union. Google's Chubby cluster использует Prim-like leader election для построения spanning tree на dense overlay.
>
>     **Когда применять.** Sparse network → Kruskal (`E log E ≈ E log V` на sparse + cache-friendly sort). Dense complete graph → Prim (`O(V²)` с матрицей лучше `O(V² log V²)` у Kruskal). Несвязный граф → Kruskal (естественно forest). Streaming edges → Kruskal с online sort. Incremental MST (добавляем вершины) → Prim natural fit.
>
>     **Подводные камни.** На графах с равными весами Kruskal и Prim могут вернуть разные MST с одинаковой суммой — это не баг, не нужно тратить время на «исправление». Параллельный Kruskal требует careful Union-Find synchronization — обычные UF не thread-safe; lock-free UF существует (Anderson 1994), но сложнее. Prim implementation детали: lazy vs eager deletion в PQ — lazy memory `O(E)`, eager — `O(V)` через index-based heap. Cache locality: Kruskal — sequential scan sorted list (cache hit); Prim — random access adjacency list (cache miss).
>
>     **Связанные вопросы.** [[graphs-interview#Q15]] MST определение; [[graphs-interview#Q16]] Kruskal детально; [[graphs-interview#Q17]] Prim детально.
>
> - [ ] B. Prim не работает для несвязных графов; Kruskal работает для обоих — это главное различие.
>
>     **Что на самом деле.** Несвязные графы — лишь одно из различий. Основные отличия — подход (global vs local greedy), performance на dense/sparse (`O(E log E)` vs `O(E log V)` vs `O(V²)` с матрицей), параллелизуемость. Prim адаптируется к несвязным через внешний цикл от каждой компоненты — это не фундаментальное ограничение.
>
>     **Откуда путаница.** Несвязный case часто обсуждают как «специфика Kruskal», но это не главное в выборе алгоритма на практике.
>
>     **Если бы это было правдой.** Telecom-планирование выбирал бы Kruskal только из-за несвязности — но реально на 99% графов связные, и выбор делается по плотности.
>
>     **Как было бы правильно.** Признать: разница в подходе (global/local), производительности (sparse/dense), и параллельности; несвязный case — частный.
>
> - [ ] C. Prim медленнее на графах с отрицательными весами рёбер — алгоритм greedy не справляется.
>
>     **Что на самом деле.** Ни Prim, ни Kruskal не чувствительны к знаку весов. Они выбирают **минимальное** ребро — отрицательное даже предпочтительнее. MST на графе с отрицательными весами корректно вычисляется обоими. Greedy invariant (минимальное cross-edge принадлежит MST) работает независимо от знака.
>
>     **Откуда путаница.** Dijkstra ломается на отрицательных весах, и эту особенность некорректно проецируют на MST алгоритмы. Разница: Dijkstra зависит от «пути уже не станет короче», а MST просто берёт минимальное ребро.
>
>     **Если бы это было правдой.** Forex network planning (где курсы могут давать «отрицательные веса» через `-log(rate)`) не работало бы с MST — но работает.
>
>     **Как было бы правильно.** Признать: и Prim, и Kruskal корректны на любых весах (включая отрицательные); MST не требует positivity.
>
> - [ ] D. Kruskal всегда быстрее Prim, потому что не использует PriorityQueue.
>
>     **Что на самом деле.** Производительность зависит от плотности. На sparse Kruskal `O(E log E) ≈ O(V log V)` и Prim `O(E log V) ≈ O(V log V)` — похожи. На dense Prim с матрицей `O(V²)` обгоняет Kruskal `O(V² log V²)` — Prim быстрее. PriorityQueue — деталь имплементации, не критерий скорости.
>
>     **Откуда путаница.** «Меньше структур = быстрее» — поверхностная интуиция. На самом деле скорость зависит от асимптотики и константы для конкретного графа.
>
>     **Если бы это было правдой.** Cisco STP не использовал бы Prim-like algorithm для full-mesh L2 сетей — но именно использует.
>
>     **Как было бы правильно.** Сказать: «Kruskal быстрее на sparse, Prim — на dense; PriorityQueue — инструмент Prim, не недостаток».

## Q19. (!) Как обнаружить цикл в неориентированном графе?

**DFS:** если встретили посещённую вершину, не являющуюся родителем в DFS-дереве — цикл.

```java
boolean hasCycle(List<List<Integer>> adj) {
    boolean[] visited = new boolean[adj.size()];
    for (int i = 0; i < adj.size(); i++) {
        if (!visited[i] && dfsCycle(adj, i, -1, visited)) return true;
    }
    return false;
}

boolean dfsCycle(List<List<Integer>> adj, int u, int parent, boolean[] visited) {
    visited[u] = true;
    for (int v : adj.get(u)) {
        if (!visited[v]) {
            if (dfsCycle(adj, v, u, visited)) return true;
        } else if (v != parent) {
            return true; // back edge — цикл!
        }
    }
    return false;
}
```

Альтернатива — **Union-Find**: для каждого ребра проверяем, не в одной ли группе уже его концы.

`O(V + E)`.


> [!mcq] Как обнаружить цикл в неориентированном графе?
>
> - [ ] A. В неориентированном графе достаточно простого `visited[]` (boolean) — как и в любом DFS.
>
>     **Что на самом деле.** Простой `visited[]` без parent даёт false positive: каждое ребро `(u, v)` при возврате `v → u` ведёт к уже посещённой вершине (u) — будет считаться циклом, хотя это родительское ребро. Корректная реализация: передавать `parent` в рекурсию и проверять `visited[v] && v != parent` → цикл.
>
>     **Откуда путаница.** В directed DFS visited без parent работает, и кажется, что undirected такой же. На самом деле undirected требует учёта parent edge (back edge to parent — нормально, не цикл).
>
>     **Если бы это было правдой.** Цикл обнаруживался бы на любом дереве, даже на двух вершинах с одним ребром — но дерево не имеет циклов. Алгоритм был бы бесполезен.
>
>     **Как было бы правильно.** Признать: в undirected нужен parent-tracking; «visited && != parent → цикл».
>
> - [x] B. DFS с `parent[]`: если встретили посещённую вершину ≠ parent → цикл; или Union-Find: `union(u, v) = false` означает, что концы уже в одной компоненте → цикл; обе техники `O(V+E)`.
>
>     **Развёрнутое объяснение.** Два стандартных метода. **DFS с parent**: для каждой вершины в DFS передаём `parent` (через которого пришли). Для соседа `v`: если не посещён — рекурсивно DFS(v, current); если посещён и `v != parent` — back edge → цикл. Каждое ребро обходится один раз. **Union-Find**: для каждого ребра `(u, v)` пытаемся `union(u, v)` — если concepts уже в одной компоненте (find(u) == find(v)), это означает, что между ними уже есть путь, и текущее ребро замыкает цикл. С path compression + union by rank — `O(E α(V)) ≈ O(E)`. Оба метода работают за `O(V+E)`.
>
>     **Пример.** Spring Framework BeanDependencyInjector проверяет `dependsOn` цепочки на циклы через DFS с parent — иначе `BeanCurrentlyInCreationException`. Maven/Gradle dependency-cycle detection — DFS на module graph. LeetCode 261 «Graph Valid Tree» проверяет: связный + нет циклов = `E = V - 1` и Union-Find не находит цикла. CSS Grid layout engine в браузерах проверяет циклические зависимости grid items через Union-Find. Linux's `dependency-cycle` check в systemd для service units.
>
>     **Когда применять.** Dependency graph (Spring beans, Maven modules, систы init); network topology validation (нет циклов в L2 сетях после Spanning Tree); proof of tree-ness (LeetCode «Valid Tree»); image segmentation (avoid splitting regions through cycles). Если граф directed → специальный 3-color DFS (Q20). Если нужно посчитать число циклов → специализированные алгоритмы (cycle space).
>
>     **Подводные камни.** В DFS параметр `parent` — это вершина, не индекс ребра. На multigraph (несколько рёбер между парой) parent по вершине даст false negative — нужно tracking по edge id. Iterative DFS требует явного stack с parent: `stack.push({u, parent})`. Union-Find без path compression и union by rank — `O(V·E)` worst case. На несвязном графе нужно проверять для каждой компоненты отдельно (внешний цикл).
>
>     **Связанные вопросы.** [[graphs-interview#Q20]] cycle detection в directed (3 цвета); [[graphs-interview#Q21]] компоненты связности через DFS/UF; [[graphs-interview#Q22]] SCC для directed.
>
> - [ ] C. Union-Find не может обнаружить цикл в неориентированном графе — это специализированная техника только для directed.
>
>     **Что на самом деле.** Union-Find — стандартный и часто **предпочтительный** метод для cycle detection в undirected графах. Логика: `union(u, v)` возвращает false (или уже в одной компоненте через `find(u) == find(v)`), если u и v уже соединены — текущее ребро образует цикл. Сложность `O(E α(V)) ≈ O(E)` — асимптотически быстрее DFS на некоторых сценариях.
>
>     **Откуда путаница.** Union-Find часто ассоциируется с MST (Kruskal) — это создаёт впечатление, что UF только для MST. На самом деле UF универсален для задач, где «нужно отслеживать компоненты связности при добавлении рёбер».
>
>     **Если бы это было правдой.** Kruskal MST не мог бы строить дерево (потому что использует UF для отказа от ребра, образующего цикл) — но Kruskal работает корректно.
>
>     **Как было бы правильно.** Признать: UF — стандартный инструмент cycle detection в undirected, наряду с DFS+parent.
>
> - [ ] D. DFS cycle detection одинаков для undirected и directed графов — те же 3 цвета.
>
>     **Что на самом деле.** Алгоритмы разные. **Undirected**: DFS с `parent[]` — back edge к `non-parent` означает цикл; визиты простые boolean. **Directed**: 3 цвета (WHITE/GRAY/BLACK) — back edge из GRAY в GRAY означает цикл; обычный `visited[]` (boolean) дал бы false positive на forward/cross edges.
>
>     **Откуда путаница.** Оба алгоритма используют DFS как базовый обход, и кажется, что детали одинаковые. На самом деле направленность графа требует разной техники определения back edge.
>
>     **Если бы это было правдой.** Maven dependency-cycle detection (directed) использовал бы parent-tracking из undirected — это давало бы false negative на forward edges, циклы пропускались бы, build падал бы непредсказуемо.
>
>     **Как было бы правильно.** Признать: undirected — DFS + parent; directed — DFS + 3 цвета (WHITE/GRAY/BLACK).

## Q20. (!) Как обнаружить цикл в ориентированном графе?

**DFS с тремя состояниями:**
- WHITE — не посещена
- GRAY — в текущем DFS-стеке
- BLACK — полностью обработана

Если из GRAY попадаем в GRAY — цикл (back edge).

```java
boolean hasCycleDirected(List<List<Integer>> adj) {
    int n = adj.size();
    int[] color = new int[n]; // 0=WHITE, 1=GRAY, 2=BLACK
    for (int i = 0; i < n; i++) {
        if (color[i] == 0 && dfsDirected(adj, i, color)) return true;
    }
    return false;
}

boolean dfsDirected(List<List<Integer>> adj, int u, int[] color) {
    color[u] = 1; // GRAY
    for (int v : adj.get(u)) {
        if (color[v] == 1) return true; // back edge
        if (color[v] == 0 && dfsDirected(adj, v, color)) return true;
    }
    color[u] = 2; // BLACK
    return false;
}
```

`O(V + E)`. Альтернатива — **алгоритм Кана**: если после топологической сортировки осталось < V вершин в результате — цикл.


> [!mcq] Как обнаружить цикл в ориентированном графе?
>
> - [ ] A. Union-Find подходит для cycle detection в directed graph — техника универсальна.
>
>     **Что на самом деле.** Union-Find **не различает направление рёбер** — union(u, v) и union(v, u) дают одинаковый результат. В directed графе ребро `A → B` не означает, что B и A в одной компоненте по semantics directed graph (нет пути B → A). UF даёт false positive: `A → B` и `B → C` не образуют цикл в directed, но UF засчитал бы их как одну компоненту, и `A → C` (нет цикла) выглядело бы как цикл.
>
>     **Откуда путаница.** Union-Find универсален для undirected — кажется, что и для directed подойдёт. На самом деле для directed нужна специальная техника (3-color DFS), учитывающая направление.
>
>     **Если бы это было правдой.** CI/CD pipeline build dependency check (directed graph) использовал бы UF — и блокировал бы корректные конфигурации (например, два независимых модуля, делящих общий dependency).
>
>     **Как было бы правильно.** Признать: UF — для undirected; для directed → DFS с 3 цветами или Kahn's algorithm.
>
> - [ ] B. Для directed cycle detection достаточно `visited[]` (boolean), как в undirected DFS — без специальных цветов.
>
>     **Что на самом деле.** Простой `visited[]` без 3 цветов не различает три типа back-edges. **Back edge** (текущая вершина → её предок в DFS tree) = цикл. **Forward edge** (предок → потомок, уже посещённый) = НЕ цикл. **Cross edge** (между ветвями DFS tree) = НЕ цикл. Без 3 цветов forward и cross edges дают false positive «цикл».
>
>     **Откуда путаница.** В undirected DFS с parent ребро к non-parent visited = цикл. В directed это не так — direction edge различает back/forward/cross.
>
>     **Если бы это было правдой.** Maven dependency check выдавал бы false positive «circular dependency» на корректных конфигурациях с diamond inheritance (A → B, A → C, B → D, C → D) — но это корректный DAG.
>
>     **Как было бы правильно.** Признать: directed cycle detection требует 3 цвета (WHITE/GRAY/BLACK) для различения back/forward/cross edges.
>
> - [x] C. DFS с 3 цветами: WHITE → GRAY при входе в вершину, GRAY → BLACK при выходе; если из GRAY попадаем в GRAY — back edge → цикл; `O(V+E)`.
>
>     **Развёрнутое объяснение.** 3 состояния вершины: **WHITE** — не посещена; **GRAY** — в текущем DFS-стеке (зашли, ещё не вышли); **BLACK** — полностью обработана (вышли). При входе в DFS(u) меняем `color[u] = GRAY`; при выходе — `BLACK`. Для соседа v: если `WHITE` — рекурсивный DFS; если `GRAY` — back edge → цикл; если `BLACK` — forward/cross edge, не цикл. Сложность — `O(V+E)`, каждая вершина и ребро посещаются раз. Альтернатива — алгоритм Кана: BFS с in-degree=0; если после алгоритма `order.size() < V` — некоторые вершины никогда не получили in-degree=0 → есть цикл.
>
>     **Пример.** Maven dependency check валидирует POM-файлы при `mvn validate` — DFS с 3 цветами на module graph. Gradle build cycle detection использует ту же технику с разделением «configuration» и «task» phases. Apache Airflow DAG validator — если пользователь добавил cycle в DAG, при `airflow dags validate` блокирует deploy. JaCoCo coverage analysis на CFG (control flow graph) использует cycle detection для определения loops. CI/CD pipeline tools (Jenkins, GitLab CI) валидируют workflow graphs.
>
>     **Когда применять.** Любой directed graph, требующий cycle detection: build system dependencies (Maven, Gradle, Bazel), workflow orchestrators (Airflow, Argo), service init dependencies (systemd, Spring), compiler call graph analysis. Для CI/CD systems, dependency injection frameworks. Если нужно topological order + cycle check одновременно → Kahn's algorithm более удобен.
>
>     **Подводные камни.** Iterative DFS (для глубоких графов) требует явного stack с tracking цветов; при pop'е вершины нужно ставить BLACK, при push — GRAY. На очень глубоких графах (`V > 10⁴`) рекурсивный DFS пробивает JVM stack 512KB — обязательно итеративный. 3 цвета можно закодировать как `int color[]` (0/1/2) или `enum` — производительность одинакова. На multigraph self-loop `v → v` сразу же даёт цикл при первом же обходе — корректно обрабатывается.
>
>     **Связанные вопросы.** [[graphs-interview#Q19]] cycle detection в undirected; [[graphs-interview#Q25]] Kahn's algorithm как альтернатива; [[graphs-interview#Q24]] topological sort требует acyclicity.
>
> - [ ] D. Алгоритм Кана (topological sort) не может обнаружить циклы — это отдельная техника.
>
>     **Что на самом деле.** Алгоритм Кана **естественно обнаруживает циклы**: если после алгоритма `order.size() < V`, то некоторые вершины никогда не получили `in-degree = 0` — они в цикле. Это бесплатная side-feature, делающая Kahn популярным для CI/CD validators.
>
>     **Откуда путаница.** Kahn описан как «topological sort algorithm» — звучит как «упорядочивание», не «detection». На самом деле в DAG он даёт topo order, на cyclic — детектирует cycle.
>
>     **Если бы это было правдой.** Apache Airflow использовал бы отдельный 3-color DFS для cycle detection + Kahn для ordering — но реально использует **Kahn для обоих** одновременно через проверку size().
>
>     **Как было бы правильно.** Признать: Kahn — двойного назначения; topo sort + cycle detection в одном проходе через `order.size() < V`.

## Q21. Найти компоненты связности?

В неориентированном графе. Запускаем DFS/BFS от каждой непосещённой вершины — это и есть отдельный компонент.

```java
int countComponents(int n, List<List<Integer>> adj) {
    boolean[] visited = new boolean[n];
    int count = 0;
    for (int i = 0; i < n; i++) {
        if (!visited[i]) {
            dfs(adj, i, visited);
            count++;
        }
    }
    return count;
}
```

Альтернатива — **Union-Find**: для каждого ребра делаем union, потом считаем число уникальных корней.

`O(V + E)`.


> [!mcq] Как найти количество компонент связности в графе?
>
> - [ ] A. Компоненты связности можно найти только Union-Find — DFS не подходит для этой задачи.
>
>     **Что на самом деле.** DFS и BFS — каноничные методы для подсчёта компонент: запускаем обход от каждой непосещённой вершины, каждый запуск = одна компонента. Сложность `O(V+E)`. Union-Find — равноценная альтернатива (особенно для online сценариев, где рёбра добавляются динамически), но не единственный метод.
>
>     **Откуда путаница.** Union-Find часто используется в Kruskal MST и кажется специализированным для «компонентов». На самом деле он один из инструментов; DFS/BFS не уступают.
>
>     **Если бы это было правдой.** LeetCode 547 «Number of Provinces» решался бы только UF — но canonical-решения часто DFS, потому что код проще читается.
>
>     **Как было бы правильно.** Признать: DFS/BFS и UF — три равноценные техники для connected components.
>
> - [ ] B. Компоненты связности существуют только в неориентированных графах.
>
>     **Что на самом деле.** В directed графах есть **два понятия**: **strongly connected components (SCC)** — взаимная достижимость (путь A→B и B→A); **weakly connected components (WCC)** — связность при игнорировании направлений (как если граф undirected). DFS/BFS на directed даёт WCC через игнорирование направления, SCC требует Tarjan/Kosaraju.
>
>     **Откуда путаница.** «Connected components» часто учат на undirected, и слово «strongly/weakly» забывается. На самом деле для directed нужны более тонкие определения.
>
>     **Если бы это было правдой.** Spring framework не мог бы анализировать SCC в bean dependency graph — но это полезный feature для cycle detection.
>
>     **Как было бы правильно.** Признать: undirected → CC; directed → SCC (взаимная достижимость) или WCC (как undirected).
>
> - [ ] C. Компоненты связности требуют `O(V²)` памяти на adjacency matrix.
>
>     **Что на самом деле.** Алгоритм работает с adjacency list (`O(V+E)` памяти) — матрица не нужна. На больших sparse графах (соцсети 10⁹ вершин) только adjacency list возможен.
>
>     **Откуда путаница.** Учебники иногда показывают graph как матрицу для наглядности, и кажется, что это требование.
>
>     **Если бы это было правдой.** Detection «изолированных» групп в Facebook (10⁹ users, sparse) был бы невозможен — `10¹⁸` бит матрицы. Реально работает на adjacency list.
>
>     **Как было бы правильно.** Признать: adjacency list `O(V+E)` достаточно; matrix не нужна.
>
> - [x] D. DFS/BFS от каждой непосещённой вершины — каждый запуск = одна компонента; альтернатива — Union-Find с `union` по всем рёбрам, в конце число уникальных корней = число компонент; `O(V+E)` для обоих.
>
>     **Развёрнутое объяснение.** Два классических подхода. **DFS/BFS**: внешний цикл по всем вершинам; для каждой непосещённой вершины — запускаем DFS/BFS, помечающий всю компоненту как visited; инкрементируем счётчик. Сложность `O(V+E)`. **Union-Find**: для каждого ребра `(u, v)` делаем `union(u, v)`; в конце число различных корней (`find(v)`) = число компонент. С path compression + union by rank — `O((V+E) α(V)) ≈ O(V+E)`. UF преимущества: online алгоритм (можно динамически добавлять рёбра), легко параллелится через distributed UF. DFS преимущества: проще код, явно даёт сами компоненты (не только число).
>
>     **Пример.** Facebook Newsfeed clustering: группировка пользователей в «семейные» круги через UF на friendship graph + similarity threshold. Image segmentation (computer vision): UF для группировки пикселей с одинаковыми свойствами (color, intensity) в regions. Social network analysis: detection «isolated» communities в LinkedIn через DFS на graph of mutual connections. LeetCode 200 «Number of Islands» — DFS counting на implicit graph где соседи — 4-connected '1'-cells.
>
>     **Когда применять.** Network partitioning (где разрывы в сети — где разделение на dataset shards); image segmentation (Photoshop magic wand, segmentation в medical imaging); social community detection (LinkedIn groups, Facebook friend circles); fraud detection (isolated transaction networks); detection orphan nodes в graph databases (Neo4j `apoc.refactor.detachDelete` для unconnected). Если граф directed → SCC через Tarjan/Kosaraju.
>
>     **Подводные камни.** Iterative DFS на больших компонентах требует `O(V)` стек памяти. На очень больших графах UF с distribution challenges — обычные path compression не concurrent-safe; нужны specialized concurrent UF. Для weighted графов с порогом similarity (image segmentation) нужен Kruskal-like sort + UF. Не путать с biconnected components (отделение по articulation points) — это отдельная задача.
>
>     **Связанные вопросы.** [[graphs-interview#Q22]] strongly connected components в directed; [[graphs-interview#Q19]] cycle detection через UF; [[graphs-interview#Q27]] Number of Islands как пример DFS на implicit graph.

## Q22. (!) Найти strongly connected components (SCC)?

В **ориентированном** графе. SCC — максимальные подграфы, где между любыми двумя вершинами есть путь в обе стороны.

**Алгоритм Косараджу (Kosaraju):**
1. DFS на исходном графе, записываем порядок завершения (postorder)
2. Транспонируем граф
3. DFS на транспонированном в обратном порядке завершения — каждое DFS-дерево = SCC

```java
List<List<Integer>> kosaraju(List<List<Integer>> adj) {
    int n = adj.size();
    boolean[] visited = new boolean[n];
    Deque<Integer> stack = new ArrayDeque<>();

    // Шаг 1: DFS, заполняем стек по postorder
    for (int i = 0; i < n; i++) {
        if (!visited[i]) fillOrder(adj, i, visited, stack);
    }

    // Шаг 2: транспонировать
    List<List<Integer>> trans = transpose(adj, n);

    // Шаг 3: DFS на транспонированном
    Arrays.fill(visited, false);
    List<List<Integer>> sccs = new ArrayList<>();
    while (!stack.isEmpty()) {
        int u = stack.pop();
        if (!visited[u]) {
            List<Integer> scc = new ArrayList<>();
            dfsCollect(trans, u, visited, scc);
            sccs.add(scc);
        }
    }
    return sccs;
}
```

**Алгоритм Тарьяна** делает то же за один DFS, используя low-link значения. Сложнее в реализации, но эффективнее на практике.

`O(V + E)` оба.


> [!mcq] Как найти strongly connected components в directed графе?
>
> - [x] A. Kosaraju: 2 DFS (на прямом графе для postorder + на реверсированном); Tarjan: 1 DFS с low-link values; оба `O(V+E)`; SCC = максимальное множество вершин с взаимной достижимостью.
>
>     **Развёрнутое объяснение.** **SCC** (Strongly Connected Component) — максимальное подмножество directed graph, где между любыми двумя вершинами есть путь в обе стороны (A → B и B → A). Два классических алгоритма. **Kosaraju**: (1) DFS на оригинальном графе, записываем порядок завершения вершин в stack; (2) транспонируем граф (реверс всех рёбер); (3) DFS на транспонированном графе, начиная с вершин из stack в обратном порядке — каждое DFS-дерево = одна SCC. Сложность `O(V+E)`, простой код. **Tarjan**: один DFS-проход; для каждой вершины поддерживаем `disc[v]` (порядок discovery) и `low[v]` (минимальный disc, достижимый из поддерева). Когда `low[v] == disc[v]` — v корень SCC; выводим всё, что в стеке выше v. Сложность `O(V+E)`, сложнее код, но **один проход** и меньше памяти.
>
>     **Пример.** Maven dependency analyzer (`mvn dependency:tree`) использует Tarjan SCC для detection circular module dependencies — `BUILD FAILED` с указанием на цикл. LLVM compiler optimization: SCC на call graph для inlining decisions (recursive functions = SCC, не inlining'ятся). Deadlock detection в БД (Postgres, MySQL): waits-for graph между транзакциями; SCC = deadlock. Compiler call graph analysis (Java's `javac`, Go's `go build`) — Tarjan SCC для определения mutually recursive functions. Apache Spark Catalyst optimizer использует SCC на query graph для определения reusable subqueries.
>
>     **Когда применять.** Detection circular dependencies в модулях (Maven, npm, Cargo); deadlock detection в transactional systems (Postgres, MySQL); compiler optimization для recursive call analysis; condensation graph (SCC-quotient) — преобразование directed graph в DAG (каждая SCC становится одной вершиной condensation). Если граф undirected → обычные CC через DFS (Q21).
>
>     **Подводные камни.** Reversed graph в Kosaraju — отдельная структура памяти `O(V+E)`. На больших графах может быть проблемой. Tarjan экономит память, но сложнее в реализации (легко сделать off-by-one в low-link обновлениях). Iterative Tarjan ещё сложнее — нужны explicit phases (pre/in/post). Для distributed graphs (10⁹+ вершин) обычные SCC не работают; используются distributed algorithms (DCSC — Divide and Conquer Strong Connectivity). Self-loop `v → v` — SCC из одной вершины; isolated vertex (без рёбер) — тоже SCC из одной.
>
>     **Связанные вопросы.** [[graphs-interview#Q20]] cycle detection как basics; [[graphs-interview#Q21]] CC в undirected; [[graphs-interview#Q26]] DFS post-order используется в Kosaraju.
>
> - [ ] B. SCC можно найти через обычный BFS без реверса графа — алгоритм универсален.
>
>     **Что на самом деле.** Обычный BFS/DFS на directed графе даёт **weakly connected components** (вершины, связанные если игнорировать направление). SCC требует **взаимной достижимости** — это сильнее. Kosaraju требует реверс графа именно для проверки достижимости в обе стороны.
>
>     **Откуда путаница.** «BFS обходит граф» обобщают до «BFS находит компоненты». На directed semantically разные виды компонент.
>
>     **Если бы это было правдой.** Maven dependency analyzer находил бы false positive «circular dependencies» в любых tightly-coupled модулях (Spring, Hibernate ecosystems) — но Maven корректно различает strong vs weak connectivity.
>
>     **Как было бы правильно.** Признать: BFS на directed → WCC; SCC требует Tarjan/Kosaraju.
>
> - [ ] C. Алгоритм Tarjan требует двух DFS-проходов, как Kosaraju — особой разницы нет.
>
>     **Что на самом деле.** Tarjan — **один** DFS-проход с использованием low-link values; Kosaraju — **два** DFS-прохода (на оригинале и transposed). Tarjan сложнее в реализации, но экономит память (нет transposed graph) и одного scan.
>
>     **Откуда путаница.** Оба алгоритма решают одну задачу за `O(V+E)`, и кажется, что они эквивалентны. На самом деле детали реализации существенно различаются.
>
>     **Если бы это было правдой.** Embedded systems (низкая память) не имели бы выбора между алгоритмами — оба «двухпроходные». Реально для memory-constrained systems выбирают Tarjan.
>
>     **Как было бы правильно.** Признать: Kosaraju — 2 DFS, Tarjan — 1 DFS с low-link; оба `O(V+E)` по времени, разные trade-offs по памяти и сложности кода.
>
> - [ ] D. SCC существуют только в undirected графах — там, где «связность» имеет смысл.
>
>     **Что на самом деле.** SCC — концепция **только для directed** графов. В undirected все рёбра двунаправленные, поэтому любая компонента связности автоматически «strongly connected» — нет смысла в специальном термине. Для undirected используют просто «connected components» (CC).
>
>     **Откуда путаница.** «Strong» звучит как «более строгое условие», и кажется, что оно может применяться везде. На самом деле strong/weak различение имеет смысл только в directed graphs.
>
>     **Если бы это было правдой.** Compiler dependency analysis (always directed) не имел бы SCC — но это базовый инструмент в `javac`/`gcc`.
>
>     **Как было бы правильно.** Признать: SCC — только для directed; для undirected — обычные CC через DFS.

## Q23. Bipartite graph — проверка двудольности?

**BFS с двумя цветами:** красим start — 0, соседей — 1, их соседей — 0, и т.д. Если встретим ребро между одинаково окрашенными — НЕ двудольный.

```java
boolean isBipartite(List<List<Integer>> adj) {
    int n = adj.size();
    int[] color = new int[n];
    Arrays.fill(color, -1);

    for (int i = 0; i < n; i++) {
        if (color[i] == -1) {
            Queue<Integer> queue = new ArrayDeque<>();
            queue.offer(i);
            color[i] = 0;
            while (!queue.isEmpty()) {
                int u = queue.poll();
                for (int v : adj.get(u)) {
                    if (color[v] == -1) {
                        color[v] = 1 - color[u];
                        queue.offer(v);
                    } else if (color[v] == color[u]) {
                        return false;
                    }
                }
            }
        }
    }
    return true;
}
```

`O(V + E)`. Применения: matching, scheduling.


> [!mcq] Как проверить, является ли граф двудольным?
>
> - [ ] A. Двудольный граф — это граф с чётным числом вершин, как следует из названия.
>
>     **Что на самом деле.** Bipartite означает, что вершины можно разбить на **два множества** A и B так, что **все рёбра идут только между** A и B (нет рёбер внутри A или внутри B). Число вершин может быть любым. Граф с 5 вершин может быть bipartite (A={1, 3}, B={2, 4, 5}), 100 вершин может быть не bipartite (треугольник внутри).
>
>     **Откуда путаница.** Слово «bi» (два) интерпретируют как «чётное». На самом деле «bi» относится к разделению на 2 группы, не к числу элементов.
>
>     **Если бы это было правдой.** Проверка двудольности была бы тривиальной (`V % 2 == 0`) — но это не так. LeetCode 785 «Is Graph Bipartite?» с V=3 (треугольник) ожидает ответ `false`, не `true`.
>
>     **Как было бы правильно.** Признать: bipartite — про разделение на 2 группы; число вершин не критерий.
>
> - [x] B. BFS с 2 цветами: окрашиваем стартовую вершину 0, её соседей — 1, их соседей — 0, и т.д.; если встретим ребро между одноцветными вершинами — не bipartite; `O(V+E)`.
>
>     **Развёрнутое объяснение.** Алгоритм 2-coloring основан на theorem König (1936): bipartite ⟺ нет нечётных циклов ⟺ 2-раскрашиваем. BFS обходит граф уровнями: красим start цветом 0, всех его соседей — цветом 1, их соседей — 0, и т.д. Если при обходе встречаем ребро между вершинами одного цвета — нашли нечётный цикл → граф не bipartite. Если обход завершился без конфликта — bipartite, и цвета дают валидное разделение. Сложность `O(V+E)`. DFS-вариант работает идентично с теми же гарантиями.
>
>     **Пример.** Job scheduling между двумя группами worker и tasks — bipartite matching через Hungarian algorithm. Stable marriage problem (Gale-Shapley) на bipartite graph men-women. Network flow задачи: maximum matching через Ford-Fulkerson на bipartite graph. Course-student assignment в университетах — Hungarian algorithm на bipartite preference graph. LeetCode 785 «Is Graph Bipartite?» — прямое применение BFS 2-coloring.
>
>     **Когда применять.** Любая задача с разделением на 2 группы и связями только между ними: matching (job assignment, stable marriage), scheduling (resource allocation), proof structure (2-SAT через implication graph). Bipartite check как preprocessing для специализированных алгоритмов (Hopcroft-Karp matching, König theorem). Если граф не bipartite — нужны более общие алгоритмы (general matching через Edmonds).
>
>     **Подводные камни.** На несвязном графе bipartite check должен запускаться от каждой непосещённой вершины — иначе пропустит компоненту с нечётным циклом. `color[start] = 0` — конвенция; можно `1`. Self-loop `v → v` автоматически делает граф не bipartite (вершина соединена сама с собой того же цвета). На multigraph несколько рёбер между парой не меняют результат. Bipartite ≠ tree: дерево всегда bipartite (нет циклов), но bipartite не обязательно tree (даже простой 4-cycle — bipartite не tree).
>
>     **Связанные вопросы.** [[graphs-interview#Q1]] bipartite в классификации графов; [[graphs-interview#Q5]] BFS как базовый обход; [[graphs-interview#Q21]] обход компонент связности.
>
> - [ ] C. Граф с нечётным циклом может быть двудольным — это лишь свойство, а не критерий.
>
>     **Что на самом деле.** Theorem König: bipartite ⟺ **нет** нечётных циклов. Это эквивалентность. Нечётный цикл (треугольник, пятиугольник) делает граф **не** bipartite. Доказательство: при попытке 2-раскрасить нечётный цикл, обходя по очереди, последняя вершина получает тот же цвет, что и первая → конфликт.
>
>     **Откуда путаница.** «Свойство, а не критерий» — частая формулировка про необязательные условия. Но König — именно строгая эквивалентность.
>
>     **Если бы это было правдой.** LeetCode 785 на графе `[1,2,3,1]` (треугольник) принимал бы `true` — но ожидает `false`. Hungarian algorithm применялся бы на графах с треугольниками — даёт некорректное matching.
>
>     **Как было бы правильно.** Признать: bipartite ⟺ нет нечётных циклов; одна — точная эквивалентность.
>
> - [ ] D. Проверка двудольности требует `O(V²)` — перебираем все пары вершин на конфликт.
>
>     **Что на самом деле.** BFS/DFS 2-coloring работает за `O(V+E)` — линейное от размера графа. Цвета расставляются при обходе, конфликты проверяются на каждом ребре (всего E проверок). Перебор пар избыточен.
>
>     **Откуда путаница.** «Проверить все пары» — наивный подход на любую задачу. На самом деле граф уже даёт informacja через рёбра — не нужно перебирать.
>
>     **Если бы это было правдой.** На графе 10⁶ вершин bipartite check занимал бы `10¹²` операций ≈ часы — нереально для real-time job scheduling в Booking.com (где сотрудники назначаются на смены).
>
>     **Как было бы правильно.** Признать: `O(V+E)` через BFS/DFS coloring; перебор пар избыточен.

## Q24. (!) Топологическая сортировка — что и зачем?

**Топологическая сортировка** — линейный порядок вершин **DAG** (Directed Acyclic Graph), при котором для каждого ребра `u → v` вершина `u` стоит **перед** `v`.

**Применения:**
- Сборка зависимостей (Maven/Gradle)
- Порядок задач с предусловиями
- Spring bean dependency graph
- Парсинг конфигов с зависимостями
- Course scheduling

Существует, **только если граф DAG** (без циклов).


> [!mcq] Что такое топологическая сортировка и где она применяется?
>
> - [ ] A. Topological sort работает на любом directed графе, включая графы с циклами.
>
>     **Что на самом деле.** Topo sort работает **только на DAG** (Directed Acyclic Graph). При наличии цикла линейный порядок принципиально невозможен: если `A → B → C → A`, нельзя поставить A раньше B, B раньше C и C раньше A одновременно. Алгоритм Кана обнаруживает цикл через `order.size() < V` после обхода (некоторые вершины не получили `in-degree = 0`).
>
>     **Откуда путаница.** «Sort» обычно работает на любом input — кажется, что topo sort универсален. На самом деле его semantics зависят от ацикличности.
>
>     **Если бы это было правдой.** Maven мог бы строить cycling module dependencies — но build падает с понятной ошибкой «circular dependency between A and B».
>
>     **Как было бы правильно.** Признать: topo sort требует DAG; на cyclic — детектирует цикл через `order.size() < V`.
>
> - [ ] B. Topological sort уникальна — существует ровно один правильный порядок для любого DAG.
>
>     **Что на самом деле.** При независимых вершинах (множество вершин с `in-degree = 0` одновременно) возможны несколько валидных topo orders. Алгоритм Кана выбирает произвольный (depends on insertion order in queue). Лексикографически минимальный — отдельная задача, требует PriorityQueue вместо queue.
>
>     **Откуда путаница.** «Sort» обычно даёт unique result. В topo sort единственность не гарантирована — это структурное свойство DAG.
>
>     **Если бы это было правдой.** Тесты, сравнивающие Kahn vs DFS-варианты, всегда падали бы — но они проходят, потому что оба валидны (просто разные допустимые порядки).
>
>     **Как было бы правильно.** Признать: topo sort даёт any valid order; для уникального лексикографически минимального — отдельная задача с PriorityQueue.
>
> - [x] C. Линейный порядок вершин DAG, при котором для каждого ребра `u → v` вершина u стоит раньше v; применяется в build dependencies (Gradle/Maven), Spring bean initialization, task scheduling; `O(V+E)`.
>
>     **Развёрнутое объяснение.** Топологическая сортировка — линеаризация вершин DAG, соблюдающая partial order, заданный рёбрами. Формально: для каждого ребра `u → v` в выходном порядке `u` идёт раньше `v`. Существует ⟺ граф DAG (нет циклов). Два классических алгоритма: **Kahn's algorithm** (BFS-based) — поддерживаем queue вершин с `in-degree = 0`, извлекаем их по очереди, декрементируем in-degree соседей, добавляем новые с `in-degree = 0`; `O(V+E)`. **DFS-based** — post-order DFS, push в стек при выходе; результат в обратном порядке; `O(V+E)`.
>
>     **Пример.** Gradle при `./gradlew build` строит DAG модулей по `dependencies { implementation project(':module-a') }`, выполняет Kahn's algorithm, билдит модули в правильном порядке. Spring DI контейнер инициализирует beans через топологическую сортировку DI graph (`UserController` после `UserService` после `UserRepository`). Apache Airflow DAG — само название отсылает к этому: tasks выполняются в topo order с учётом upstream/downstream зависимостей. Flyway/Liquibase migration: V1 → V2 → V3 — topo sort скриптов с зависимостями. NPM/Yarn install: topo sort packages по `dependencies`.
>
>     **Когда применять.** Любая задача с partial order на зависимостях: build systems (Maven, Gradle, Bazel, Cargo), workflow orchestrators (Airflow, Argo Workflows, Camunda), DI frameworks (Spring, Guice), database migrations (Flyway, Liquibase), package managers (npm, pip), course scheduling (prerequisites), task scheduling (precedence-constrained jobs).
>
>     **Подводные камни.** Циклы фатальны — алгоритмы детектируют, но не «исправляют». В Spring `BeanCurrentlyInCreationException` при цикле в конструкторах; workaround — setter injection с `@Lazy`, но это code smell. Несколько валидных orderings — при отладке гонок в multi-threaded init может удивить. Параллелизация: вершины с одинаковым topo level можно выполнять параллельно (Airflow это использует через `task_concurrency`). На очень больших DAG (10⁹ вершин) обычные алгоритмы непрактичны; distributed topo sort через Apache Giraph/Pregel.
>
>     **Связанные вопросы.** [[graphs-interview#Q25]] Kahn's algorithm детально; [[graphs-interview#Q26]] DFS-based topo sort; [[graphs-interview#Q28]] Course Schedule как практика.
>
> - [ ] D. Topo sort не работает для несвязных компонент — граф должен быть связным.
>
>     **Что на самом деле.** Topo sort прекрасно работает на disconnected DAG. Несвязные вершины (`in-degree = 0` изначально и независимые компоненты) добавляются первыми в queue. Алгоритм Кана корректно обрабатывает любой DAG: связный или нет. Реальные dependency graphs часто disconnected (независимые модули в monorepo).
>
>     **Откуда путаница.** «Топологический порядок ВСЕХ вершин» звучит как «должен охватывать все из одного starting point». На самом деле topo sort — это просто упорядочивание, не обязательно с единого корня.
>
>     **Если бы это было правдой.** Gradle multi-project build с несколькими независимыми модулями не работал бы — но это стандартный workflow в monorepo.
>
>     **Как было бы правильно.** Признать: topo sort корректен на любом DAG, включая несвязные.

```java
List<Integer> kahnTopologicalSort(int n, List<List<Integer>> adj) {
    int[] inDegree = new int[n];
    for (int u = 0; u < n; u++)
        for (int v : adj.get(u)) inDegree[v]++;

    Queue<Integer> queue = new ArrayDeque<>();
    for (int i = 0; i < n; i++)
        if (inDegree[i] == 0) queue.offer(i);

    List<Integer> order = new ArrayList<>();
    while (!queue.isEmpty()) {
        int u = queue.poll();
        order.add(u);
        for (int v : adj.get(u)) {
            if (--inDegree[v] == 0) queue.offer(v);
        }
    }

    if (order.size() != n) throw new IllegalStateException("Cycle!");
    return order;
}
```

`O(V + E)`. Алгоритм Кана **обнаруживает цикл**: если `order.size() < n` — есть цикл. Естественно поддерживает обработку рёбер по слоям.


> [!mcq] Как работает алгоритм Кана и какие у него преимущества?
>
> - [ ] A. Алгоритм Кана работает только на деревьях, не на произвольных DAG.
>
>     **Что на самом деле.** Алгоритм Кана разработан именно для произвольных DAG, не только для деревьев. Он работает на любом directed acyclic graph: диамант-shape, многослойная DAG, disconnected DAG. Деревья — частный случай DAG (с условием уникального родителя).
>
>     **Откуда путаница.** Алгоритм объясняют на простых примерах в виде деревьев. На самом деле он генерализуется на произвольные DAG без изменений.
>
>     **Если бы это было правдой.** Gradle multi-project build с diamond-зависимостями (`A → B, A → C, B → D, C → D`) не работал бы — но это базовый pattern в Maven/Gradle.
>
>     **Как было бы правильно.** Признать: Kahn — универсальный для DAG; деревья — частный случай.
>
> - [ ] B. Алгоритм Кана не обнаруживает циклы — для этого нужен отдельный DFS-проход.
>
>     **Что на самом деле.** Kahn **сам обнаруживает** циклы: если `order.size() < V` после алгоритма, некоторые вершины никогда не получили `in-degree = 0` — они в цикле. Это бесплатная side-feature.
>
>     **Откуда путаница.** Kahn описывают как «topo sort algorithm» — звучит как «упорядочивание», не «detection». Но на cyclic графе он естественно отмечает наличие цикла через неполный output.
>
>     **Если бы это было правдой.** Apache Airflow проверял бы DAGs дважды (отдельный DFS + Kahn) — но реально использует только Kahn.
>
>     **Как было бы правильно.** Признать: Kahn — двойного назначения; topo sort + cycle detection одновременно.
>
> - [ ] C. Топологическая сортировка требует `O(V²)` для сортировки in-degree.
>
>     **Что на самом деле.** Подсчёт in-degree — `O(V+E)` (проход по всем рёбрам). Обработка queue — `O(V+E)` (каждая вершина в queue один раз, каждое ребро декрементирует in-degree один раз). Итого `O(V+E)` — линейное время, не quadratic.
>
>     **Откуда путаница.** Слово «sort» в названии создаёт иллюзию `O(V log V)` или `O(V²)`. На самом деле topo sort через Kahn — линейный.
>
>     **Если бы это было правдой.** Gradle build на 10⁵ модулях занимал бы `10¹⁰` операций — недопустимо. Реально работает за `10⁵+10⁶ ≈ 10⁶` операций.
>
>     **Как было бы правильно.** Признать: Kahn — `O(V+E)`, линейный.
>
> - [x] D. Kahn's algorithm: BFS с очередью вершин с `in-degree = 0`; извлекаем, декрементируем in-degree соседей, добавляем новые с in-degree=0; обнаруживает циклы через `order.size() < V`; `O(V+E)`; естественен для level-by-level обработки.
>
>     **Развёрнутое объяснение.** Kahn's algorithm — BFS-based topological sort с естественной cycle detection. Сначала вычисляем `in-degree` для каждой вершины. Помещаем в queue все вершины с `in-degree = 0` (нет зависимостей). Цикл: извлекаем `u` из queue, добавляем в `order`; для каждого outgoing edge `u → v` декрементируем `in-degree[v]`; если стало 0 — добавляем в queue. После завершения: если `order.size() == V` — DAG, успех; иначе — есть цикл (вершины с `in-degree > 0` после обхода). Сложность по времени — `O(V+E)`, по памяти — `O(V)`. Преимущество над DFS-based topo sort: естественная level-by-level обработка (все вершины с одинаковым «depth in DAG» обрабатываются вместе), что удобно для parallel execution.
>
>     **Пример.** Apache Airflow scheduler использует Kahn для определения, какие tasks готовы к выполнению (`in-degree = 0` = все upstream завершены); `task_concurrency` использует level-by-level group для параллельного запуска. Gradle build dependency resolution — Kahn для определения порядка компиляции модулей. Make/Bazel parallel build — same approach. Apache Camel route execution — Kahn для определения, какие steps можно выполнить параллельно. LeetCode 207 «Course Schedule» и 210 «Course Schedule II» — прямые применения Kahn.
>
>     **Когда применять.** Build systems (Makefile, Bazel, Gradle); package managers (NPM, Cargo); workflow orchestrators (Airflow, Argo); CI pipeline ordering (Jenkins, GitLab CI); curriculum planning (course prerequisites); resource allocation с зависимостями. Когда нужна параллельная обработка по levels — Kahn выгоднее DFS (level-by-level natural).
>
>     **Подводные камни.** Initial queue должен содержать **все** вершины с `in-degree = 0`, не только одну (иначе пропустим disconnected components). На multigraph несколько рёбер `u → v` должны декрементировать in-degree[v] раз за каждое — обычно in-degree подсчитывается с multiplicities. PriorityQueue вместо обычной queue даёт лексикографически минимальный topo order — некоторые задачи требуют именно его. Изменение order при `addAll`/`pollFirst` operations — `ArrayDeque` в Java оптимален.
>
>     **Связанные вопросы.** [[graphs-interview#Q24]] topo sort definition; [[graphs-interview#Q26]] DFS-based topo sort; [[graphs-interview#Q28]] Course Schedule как практический пример Kahn.

## Q26. Топологическая сортировка через DFS?

```java
List<Integer> topologicalSortDFS(int n, List<List<Integer>> adj) {
    boolean[] visited = new boolean[n];
    Deque<Integer> stack = new ArrayDeque<>();

    for (int i = 0; i < n; i++) {
        if (!visited[i]) dfs(i, adj, visited, stack);
    }

    List<Integer> order = new ArrayList<>();
    while (!stack.isEmpty()) order.add(stack.pop());
    return order;
}

void dfs(int u, List<List<Integer>> adj, boolean[] visited, Deque<Integer> stack) {
    visited[u] = true;
    for (int v : adj.get(u))
        if (!visited[v]) dfs(v, adj, visited, stack);
    stack.push(u); // post-order
}
```

`O(V + E)`. Не обнаруживает циклы напрямую — нужно дополнить трёхцветной схемой.


> [!mcq] Как работает DFS-based топологическая сортировка?
>
> - [x] A. DFS post-order: push вершину в стек **после** обработки всех её соседей; результат = стек сверху вниз; `O(V+E)`; не обнаруживает циклы сам по себе (нужна 3-цветная схема).
>
>     **Развёрнутое объяснение.** Идея — пройти DFS по всем вершинам и при выходе из рекурсии (post-order) положить вершину в стек. Логика: когда DFS возвращается из v, все вершины, достижимые из v (т.е. зависящие от v) уже обработаны и в стеке выше v. Чтобы получить topo order, читаем стек сверху вниз (pop). Альтернатива — `List` с reverse в конце. Сложность `O(V+E)` (стандарт DFS). Cycle detection НЕ встроена — нужна дополнительная 3-цветная схема (WHITE/GRAY/BLACK), иначе на cyclic графе алгоритм даёт некорректный «topo order» без сигнала о цикле.
>
>     **Пример.** Kosaraju SCC algorithm использует DFS-topo для первого прохода (заполняет стек по post-order на оригинальном графе). Tarjan articulation points algorithm — DFS с low-link на пост-обработке. Compiler dataflow analysis (LLVM) использует DFS post-order для определения порядка обработки basic blocks. Clojure compiler — DFS post-order для namespace dependency resolution. Linux `make` (рекурсивный mode) — DFS post-order для resolution Makefile dependencies.
>
>     **Когда применять.** Когда нужен DFS-native порядок (для последующих операций типа Kosaraju); когда параллелизация не нужна (DFS sequential); когда нужно простое решение без queue management; embedded systems с ограниченной памятью (DFS recursion uses stack, no extra data structures). Если нужна параллелизация или level-by-level — Kahn's algorithm удобнее.
>
>     **Подводные камни.** Без 3-цветной схемы алгоритм даст некорректный «topo order» на cyclic graph — нужно добавить colors или явный cycle check (отдельный DFS). На глубоких графах (`V > 10⁴`) рекурсивный DFS пробивает JVM stack 512KB — обязательно итеративный (но iterative post-order сложнее: нужны markers). Push в стек — может быть `Deque.push(v)` или `List.add(v) + reverse в конце`. Stack vs ArrayDeque в Java: ArrayDeque быстрее (нет synchronization overhead).
>
>     **Связанные вопросы.** [[graphs-interview#Q24]] topo sort definition; [[graphs-interview#Q25]] Kahn's algorithm как альтернатива; [[graphs-interview#Q22]] Kosaraju использует DFS-topo.
>
> - [ ] B. DFS topological sort ставит вершины в стек **при входе** (pre-order), а не при выходе.
>
>     **Что на самом деле.** Pre-order push даёт **обратный** topo order — то есть вершины ставятся в стек **до** обработки их зависимостей. Это нарушает invariant «зависимости перед зависимой вершиной». Корректный topo sort требует post-order push (после рекурсии).
>
>     **Откуда путаница.** Pre-order естественен в DFS (push при входе) — это default DFS behavior. Для topo sort нужно специально откладывать push до выхода.
>
>     **Если бы это было правдой.** Maven module build выполнялся бы в обратном порядке зависимостей: сначала root project, потом его dependencies — что приводит к compile errors (`cannot find symbol`).
>
>     **Как было бы правильно.** Признать: только post-order push корректен; pre-order даёт reverse order.
>
> - [ ] C. DFS topological sort возвращает результат в порядке добавления в стек (pop в том же порядке).
>
>     **Что на самом деле.** Stack — LIFO. Вершины добавляются в post-order, но pop происходит в обратном порядке добавления — то есть top of stack первая. Правильный topo order = читать stack сверху вниз (через pop). Если читать в порядке добавления (FIFO), получится reverse topo order.
>
>     **Откуда путаница.** Список и стек путают в semantics: список — FIFO read, стек — LIFO. Для topo sort нужен LIFO (post-order push, top-down pop).
>
>     **Если бы это было правдой.** Spring DI инициализировал бы beans в reverse dependency order — root bean раньше своих dependencies, NullPointerException на startup.
>
>     **Как было бы правильно.** Признать: stack — LIFO; правильный topo order — pop сверху (последний push = первый pop = начало topo).
>
> - [ ] D. DFS topological sort не работает если граф несвязный — нужно специальное обхождение.
>
>     **Что на самом деле.** DFS topo sort корректен на disconnected DAG. Внешний цикл `for (int i = 0; i < n; i++) if (!visited[i]) dfs(i, ...)` обрабатывает все компоненты последовательно. Post-order push в общий стек даёт корректный topo order, объединяющий все компоненты.
>
>     **Откуда путаница.** «DFS обходит одну компоненту за один запуск» обобщают до «топ-sort не работает на несвязных». На самом деле внешний цикл с visited tracking решает проблему.
>
>     **Если бы это было правдой.** Multi-project Gradle build с независимыми модулями не работал бы — но это базовый workflow в monorepo.
>
>     **Как было бы правильно.** Признать: внешний цикл по непосещённым обеспечивает корректность на несвязных DAG.

## Q27. (!) Number of Islands — задача с матрицей?

Дана grid из `1` (земля) и `0` (вода). Найти количество островов (4-связные регионы из `1`).

```java
int numIslands(char[][] grid) {
    int rows = grid.length, cols = grid[0].length;
    int count = 0;
    for (int r = 0; r < rows; r++) {
        for (int c = 0; c < cols; c++) {
            if (grid[r][c] == '1') {
                count++;
                dfsIsland(grid, r, c);
            }
        }
    }
    return count;
}

void dfsIsland(char[][] grid, int r, int c) {
    if (r < 0 || r >= grid.length || c < 0 || c >= grid[0].length
        || grid[r][c] != '1') return;
    grid[r][c] = '#'; // mark visited
    dfsIsland(grid, r + 1, c);
    dfsIsland(grid, r - 1, c);
    dfsIsland(grid, r, c + 1);
    dfsIsland(grid, r, c - 1);
}
```

`O(R · C)` время. Альтернатива — Union-Find (полезно если нужно динамически добавлять землю).


> [!mcq] Number of Islands — какая сложность алгоритма и какие ключевые шаги?
>
> - [ ] A. `O(R + C)`, потому что обходим строки и столбцы независимо.
>
>     **Что на самом деле.** Алгоритм посещает **каждую клетку матрицы один раз** — это `O(R · C)`, не `O(R + C)`. Каждая клетка либо стартует новый DFS (`grid[r][c] == '1'`), либо посещается соседним DFS. В обоих случаях трогается ровно один раз благодаря пометке `grid[r][c] = '#'`.
>
>     **Откуда путаница.** `O(R + C)` звучит знакомо по `O(V + E)` для BFS/DFS на графе. Но в задаче на матрице V — это все клетки (R·C), а E — соседние пары (4 на клетку, тоже O(R·C)).
>
>     **Если бы это было правдой.** На матрице 1000×1000 алгоритм работал бы за 2000 операций вместо миллиона. Такая оценка на собеседовании показала бы непонимание — типичный отказ.
>
>     **Как было бы правильно.** Сказать: «`O(R · C)` — каждая клетка посещается один раз; всего R·C клеток».
>
> - [ ] B. Нужно создать отдельный `boolean[][] visited` массив — без него алгоритм некорректен.
>
>     **Что на самом деле.** В каноничной in-place реализации помечаем `grid[r][c] = '#'` прямо в исходной матрице. Это экономит `R · C` байт памяти и упрощает код. Отдельный visited нужен только если требование «не модифицировать вход».
>
>     **Откуда путаница.** В учебных DFS на графе массив `visited[V]` обязателен — нельзя «портить» структуру графа. Матрица — особый случай, где мутация клетки эквивалентна пометке.
>
>     **Если бы это было правдой.** На матрице 10⁹ клеток (streaming картa местности) `visited` занял бы 1 GB — OOM на typical serverless runner (AWS Lambda 512 MB).
>
>     **Как было бы правильно.** Признать: in-place mutation — стандарт для Number of Islands; отдельный `visited` — опционально (если grid `final`).
>
> - [ ] C. Union-Find не подходит для Number of Islands — это исключительно DFS/BFS задача.
>
>     **Что на самом деле.** Union-Find — полноценная альтернатива. Каждая `'1'`-клетка — узел, соседние объединяются через `union(r·cols+c, r'·cols+c')`. В конце число островов = число уникальных корней. Время `O(R · C · α(R · C))`, где α — обратная Аккермана (практически константа). UF выигрывает у DFS в Number of Islands II (LeetCode 305), где острова появляются динамически.
>
>     **Откуда путаница.** DFS-решение проще для базовой задачи, поэтому UF кажется избыточным. На самом деле UF — стандартный инструмент для streaming/dynamic версий.
>
>     **Если бы это было правдой.** Streaming-карта (вода поднимается/спадает в реальном времени) требовала бы полного пересчёта O(R·C) вместо инкрементального O(α) — деградация на порядки.
>
>     **Как было бы правильно.** Признать: UF — равноценная альтернатива DFS; обязательна в Number of Islands II.
>
> - [x] D. Сложность `O(R · C)`; DFS из каждой `'1'`-клетки помечает связную область заменой на `'#'`; счётчик инкрементируется при каждой новой стартовой `'1'`-клетке.
>
>     **Развёрнутое объяснение.** Алгоритм имеет два уровня. **Внешний цикл по всем клеткам** — `O(R · C)`. Для каждой клетки проверяем: если `'1'` и не пройдена (не `'#'`) — увеличиваем счётчик и запускаем DFS. **DFS из стартовой клетки** — помечает все 4-связные `'1'`-соседи как `'#'` рекурсивно. Каждая клетка попадает в DFS ровно один раз. Суммарно: каждая клетка трогается O(1) раз → общее время `O(R · C)`. Память — `O(R · C)` в worst case на стек рекурсии (одна гигантская спираль из `'1'`).
>
>     **Пример.** Подсчёт связных областей на 2D-сетке: количество комнат на плане здания, изолированные кластеры в клеточном автомате (Conway's Game of Life). Google Maps определяет «изолированные» участки дорог (без выхода на магистраль) через подобный DFS на graph дорог. Datadog cluster monitoring выделяет «острова» инстансов с одинаковой ошибкой по топологии. Photoshop magic wand tool — DFS/BFS на pixels с similarity threshold. LeetCode 200 — каноничный пример этой техники.
>
>     **Когда применять.** Любая задача «количество связных областей на grid» с 4- или 8-связностью: image segmentation, terrain analysis (terra/sea regions), maze-like разбиения. На 8-связности добавляются 4 диагональных направления. Для streaming-добавления клеток (Number of Islands II) → Union-Find. Для огромных grids (`R · C > 10⁹`) → итеративный DFS / BFS на Deque (избегаем stack overflow).
>
>     **Подводные камни.** **Stack overflow** при больших матрицах: DFS-рекурсия для 10⁴×10⁴ пробивает default JVM stack (512 KB ≈ 10⁴ кадров). Решение — iterative DFS на `Deque` или BFS на `Queue`. **8-связность vs 4-связность**: задача обычно про 4 (up/down/left/right), но иногда требуется 8 (с диагоналями) — внимательно читать условие. **In-place мутация** ломает повторный запуск на той же матрице — если grid `final` или shared, нужен `boolean[][] visited`.
>
>     **Связанные вопросы.** [[graphs-interview#Q6]] DFS как базовый алгоритм; [[graphs-interview#Q21]] компоненты связности (общая идея); [[graphs-interview#Q28]] Course Schedule использует тот же подход на DAG.

## Q28. (!) Course Schedule — обнаружение цикла в зависимостях?

Дано `numCourses` и список prerequisites `[[a, b], ...]` (b → a). Можно ли пройти все курсы?

```java
boolean canFinish(int numCourses, int[][] prerequisites) {
    List<List<Integer>> adj = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) adj.add(new ArrayList<>());
    int[] inDegree = new int[numCourses];

    for (int[] p : prerequisites) {
        adj.get(p[1]).add(p[0]);
        inDegree[p[0]]++;
    }

    Queue<Integer> queue = new ArrayDeque<>();
    for (int i = 0; i < numCourses; i++)
        if (inDegree[i] == 0) queue.offer(i);

    int taken = 0;
    while (!queue.isEmpty()) {
        int u = queue.poll();
        taken++;
        for (int v : adj.get(u)) {
            if (--inDegree[v] == 0) queue.offer(v);
        }
    }
    return taken == numCourses;
}
```

Если можно завершить — топологический порядок существует (нет циклов). `O(V + E)`.


> [!mcq] Как решается LeetCode Course Schedule (cycle detection в prerequisites)?
>
> - [ ] A. Course Schedule решается **только** через DFS — BFS не подходит для cycle detection.
>
>     **Что на самом деле.** Course Schedule решается обоими методами. **DFS с 3 цветами** (WHITE/GRAY/BLACK) — back edge GRAY → GRAY означает cycle. **Kahn's algorithm (BFS)** — в очередь добавляются курсы с `in-degree = 0`; если итоговый `taken < numCourses`, есть cycle. Оба подхода `O(V+E)`. Kahn часто предпочитают за читаемость кода.
>
>     **Откуда путаница.** Cycle detection часто учат на DFS с 3 цветами как «канонический» — BFS-вариант менее популярен в учебниках, но не менее корректен.
>
>     **Если бы это было правдой.** LeetCode 207 имел бы одно canonical решение — но editorial показывает оба (DFS и Kahn), оба принимаются.
>
>     **Как было бы правильно.** Признать: оба подхода работают; выбор по стилю и читаемости.
>
> - [x] B. Kahn's algorithm: курсы с `in-degree = 0` в queue → берём курс → декрементируем in-degree соседей; цикл если `taken < numCourses`; `O(V+E)`; применяется в dependency resolution.
>
>     **Развёрнутое объяснение.** Course Schedule — прямое применение Kahn's algorithm для topo sort + cycle detection. Строим граф: ребро `b → a` для каждой пары `[a, b]` в prerequisites (b — prerequisite для a, поэтому b должен идти раньше). Подсчитываем `in-degree` для каждого курса. Стартовая queue — курсы с `in-degree = 0` (нет prerequisites). На каждом шаге: извлекаем `u`, инкрементируем `taken`, для каждого `u → v` декрементируем `in-degree[v]`; если стало 0 — добавляем в queue. Если в конце `taken == numCourses` — все курсы можно пройти (graph DAG); иначе — есть cycle.
>
>     **Пример.** Coursera/Stepik используют похожие алгоритмы для prerequisite checking — нельзя enroll в advanced course без completion базового. Maven dependency analyzer проверяет circular dependencies через эту же технику. Apache Airflow DAG validation — Kahn для проверки, что workflow можно выполнить. CI/CD pipeline validation (Jenkins, GitLab CI) — проверка отсутствия циклов между jobs. Compiler dependency resolution для multi-file проектов (TypeScript, Rust).
>
>     **Когда применять.** Любая задача «может ли быть выполнено всё с учётом зависимостей»: course planning, build systems, workflow orchestrators, package install order, database migration sequencing. Если нужен сам порядок курсов (а не только yes/no) — Course Schedule II (LeetCode 210), та же логика + collecting order. Альтернатива — DFS с 3 цветами, более компактный код, но менее «параллелизуемый» по уровням.
>
>     **Подводные камни.** Off-by-one в построении графа: convention в LeetCode — `prerequisites[i] = [a, b]` означает «b нужен для a», то есть ребро `b → a`. Легко спутать направление, что инвертирует результат. Multi-edge (одна prerequisite указана дважды) — нужно увеличить in-degree кратно. Single-vertex graph (один курс без prerequisites) — корректно обрабатывается (queue стартует с него). Cycle на self-loop `[a, a]` (курс — prerequisite сам себе) даёт cycle.
>
>     **Связанные вопросы.** [[graphs-interview#Q24]] topological sort definition; [[graphs-interview#Q25]] Kahn's algorithm детально; [[graphs-interview#Q20]] cycle detection в directed.
>
> - [ ] C. Если граф содержит цикл — Course Schedule невозможно решить алгоритмом, нужно специальное обращение.
>
>     **Что на самом деле.** Если есть цикл → вернуть `false` (нельзя пройти все курсы из-за бесконечной зависимости). Алгоритм Kahn корректно обрабатывает этот случай — не падает, просто `taken < numCourses` после обхода. Это и есть «решение» — детектируем impossibility.
>
>     **Откуда путаница.** Слово «невозможно решить» путают с «алгоритм падает». На самом деле «невозможно завершить все курсы» — это и есть валидный ответ.
>
>     **Если бы это было правдой.** LeetCode 207 не имел бы тестов с cycles — но именно такие тесты основные (ожидаемый output `false`).
>
>     **Как было бы правильно.** Признать: цикл → return `false`; алгоритм не падает, корректно определяет impossibility.
>
> - [ ] D. Course Schedule требует хранить сам порядок курсов (II версия) для проверки возможности — без порядка нельзя определить.
>
>     **Что на самом деле.** Для **Course Schedule I** (проверка возможности) достаточно `taken == numCourses` — boolean check. Порядок курсов нужен только в **Course Schedule II** (LeetCode 210). Это две разные задачи на одной idea (Kahn): I — yes/no, II — конкретный order.
>
>     **Откуда путаница.** Обе задачи на одной странице LeetCode, легко спутать требования. На самом деле I проще — только counting.
>
>     **Если бы это было правдой.** LeetCode 207 требовал бы output list courses — но output `bool canFinish`.
>
>     **Как было бы правильно.** Признать: Schedule I — `boolean canFinish` (taken count); Schedule II — `List<Integer> findOrder` (сам order).

## Q29. Word Ladder — кратчайшая трансформация слов?

Из `beginWord` в `endWord`, изменяя по 1 букве, через слова из словаря. Минимальная длина пути.

```java
int ladderLength(String begin, String end, List<String> wordList) {
    Set<String> dict = new HashSet<>(wordList);
    if (!dict.contains(end)) return 0;

    Queue<String> queue = new ArrayDeque<>();
    queue.offer(begin);
    int level = 1;

    while (!queue.isEmpty()) {
        int size = queue.size();
        for (int i = 0; i < size; i++) {
            String word = queue.poll();
            if (word.equals(end)) return level;
            for (int j = 0; j < word.length(); j++) {
                char[] arr = word.toCharArray();
                for (char c = 'a'; c <= 'z'; c++) {
                    arr[j] = c;
                    String next = new String(arr);
                    if (dict.contains(next)) {
                        queue.offer(next);
                        dict.remove(next); // mark visited
                    }
                }
            }
        }
        level++;
    }
    return 0;
}
```

`O(N · L · 26)`, где N — слов, L — длина слова. Bidirectional BFS даёт ещё ускорение.


> [!mcq] Word Ladder — почему BFS, а не DFS, и что делает `dict.remove(next)` ключевым?
>
> - [ ] A. BFS используется потому, что DFS вообще не работает на словарных задачах.
>
>     **Что на самом деле.** DFS работает — но возвращает **любой** путь, а Word Ladder требует **минимальный** (кратчайший). BFS гарантирует кратчайший путь в невзвешенном графе по построению: на уровне `level` все слова достижимы ровно за `level - 1` трансформаций.
>
>     **Откуда путаница.** DFS легко представить как «рекурсивный поиск», и кажется, что с `if (path.size() < min) min = path.size()` получим кратчайший путь. Так и есть — но цена `O(N!)` в worst case (все перестановки) вместо `O(N · L · 26)` у BFS.
>
>     **Если бы это было правдой.** На тестах LeetCode 127 (словарь 5000 слов, длина пути 10) DFS-решение получает TLE за 30+ секунд; BFS — проходит за 200ms.
>
>     **Как было бы правильно.** Признать: DFS работает, но даёт any path, не shortest; BFS обеспечивает shortest by construction.
>
> - [ ] B. `dict.remove(next)` нужен для экономии памяти словаря — иначе heap переполнится.
>
>     **Что на самом деле.** `dict.remove(next)` работает как **mark visited** — предотвращает повторное добавление того же слова в queue. Без него BFS не завершится: A → B → A → B → ... зацикливание. Экономия памяти — побочный эффект, не основная цель.
>
>     **Откуда путаница.** В Java/Python привычка освобождать неиспользуемые ресурсы. `remove` действительно освобождает память, но это побочный эффект — основная задача в том, чтобы пометить слово как «уже было в queue».
>
>     **Если бы это было правдой.** Можно было бы заменить `dict.remove(next)` на `Set<String> visited = new HashSet<>()` с такой же корректностью — но это сделало бы код многословнее без выгоды.
>
>     **Как было бы правильно.** Признать: `dict.remove(next)` — mark visited; экономия памяти — побочный эффект.
>
> - [ ] C. Сложность `O(N²)`, потому что для каждого слова проверяем все остальные на «отличие в 1 букву».
>
>     **Что на самом деле.** Сложность `O(N · L · 26)`. Для каждого слова длиной `L` мы **не сравниваем** его с другими словами в словаре, а **генерируем** соседей — для каждой позиции (L) пробуем все 26 букв (a..z). Получаем `26 · L` кандидатов, проверяем `dict.contains(next)` за `O(1)` (HashSet).
>
>     **Откуда путаница.** Наивный подход — для каждого слова проходить весь словарь и считать символы — `O(N² · L)`. Уловка задачи: не сравнивать пары, а генерировать соседей и проверять `contains` в HashSet.
>
>     **Если бы это было правдой.** На словаре 10K слов length=5 наивный подход — `5·10⁸` операций (~5 секунд); правильный — `5·10⁶·26 = 1.3·10⁸` операций. На LeetCode с большим словарём наивный не пройдёт.
>
>     **Как было бы правильно.** Признать: `O(N · L · 26)` через generation + HashSet lookup; не O(N²) сравнение пар.
>
> - [x] D. BFS даёт кратчайший путь по построению; `dict.remove(next)` помечает слово как visited (предотвращает зацикливание); сложность `O(N · L · 26)`, где L — длина слова, 26 — генерация соседей по букве.
>
>     **Развёрнутое объяснение.** Идея — представить трансформации как граф: узлы — слова из словаря; рёбра — между словами, отличающимися ровно в одной букве; найти кратчайший путь от `begin` до `end`. Главный трюк: рёбра не хранятся явно. Соседи вычисляются на лету заменой каждой буквы на `a..z` — `26 · L` кандидатов вместо `O(N)` сравнений со всем словарём. BFS обходит граф по уровням: на k-м уровне все слова достижимы за k шагов от `begin`; первое достижение `end` даёт ответ. `dict.remove(next)` совмещает «проверить наличие в словаре» и «пометить как visited» в одной операции.
>
>     **Пример.** Spell-check корректоры (Microsoft Word, Grammarly) — поиск ближайшего слова по edit distance; BFS даёт shortest path в графе слов. DNA sequencing — мутации с минимальным числом замен между двумя последовательностями. Game state graphs (Rubik's cube, 15-puzzle solver) — кратчайший путь между конфигурациями. Compiler refactoring tools (IntelliJ rename) — поиск minimum rename transformation между symbol names.
>
>     **Когда применять.** Любая задача «минимум трансформаций между состояниями» с дискретными переходами: spell correction, DNA mutations, puzzle solvers, configuration migration. Если переходов много (большой alphabet) — нужны wildcards для индексирования; если путь очень длинный — bidirectional BFS даёт `√`-ускорение.
>
>     **Подводные камни.** **`begin` не должен быть в словаре** — иначе `dict.remove(begin)` теряет starting word (для алгоритма OK, начало уже в queue). **Bidirectional BFS даёт √-ускорение** — одновременно идти из `begin` и `end` навстречу. **Длина `L = 1`** — edge case, для `begin = end` ответ 1, не 0. **Большой alphabet** (Unicode strings) — `26` становится `~10⁶`, алгоритм непрактичен; нужно индексирование по wildcard-паттернам `c_t` → все 3-letter words.
>
>     **Связанные вопросы.** [[graphs-interview#Q5]] BFS как основа для кратчайшего пути; [[graphs-interview#Q8]] кратчайший путь в невзвешенном; [[graphs-interview#Q9]] bidirectional BFS для ускорения.

## Q30. Network Delay Time — Dijkstra-задача?

Дано `times = [[u, v, w], ...]`, n узлов. Найти время, за которое сигнал достигнет всех узлов из `k`.

```java
int networkDelayTime(int[][] times, int n, int k) {
    List<List<int[]>> adj = new ArrayList<>();
    for (int i = 0; i <= n; i++) adj.add(new ArrayList<>());
    for (int[] t : times) adj.get(t[0]).add(new int[]{t[1], t[2]});

    int[] dist = new int[n + 1];
    Arrays.fill(dist, Integer.MAX_VALUE);
    dist[k] = 0;

    PriorityQueue<int[]> pq = new PriorityQueue<>(Comparator.comparingInt(a -> a[0]));
    pq.offer(new int[]{0, k});

    while (!pq.isEmpty()) {
        int[] curr = pq.poll();
        int d = curr[0], u = curr[1];
        if (d > dist[u]) continue;
        for (int[] e : adj.get(u)) {
            int v = e[0], w = e[1];
            if (dist[u] + w < dist[v]) {
                dist[v] = dist[u] + w;
                pq.offer(new int[]{dist[v], v});
            }
        }
    }

    int max = 0;
    for (int i = 1; i <= n; i++) {
        if (dist[i] == Integer.MAX_VALUE) return -1;
        max = Math.max(max, dist[i]);
    }
    return max;
}
```

Классический Dijkstra. Ответ — максимальная дистанция (последний достигнутый узел).


> [!mcq] Network Delay Time — что считается ответом и почему `if (d > dist[u]) continue;` критичен?
>
> - [ ] A. Ответ — **сумма** всех `dist[i]` (общее время сигнала по сети).
>
>     **Что на самом деле.** Ответ — **максимальная** `dist[i]` из всех достижимых вершин. Это время, когда **последний** узел получит сигнал. Сумма не имеет физического смысла: сигнал распространяется параллельно, узлы получают его в разные моменты времени.
>
>     **Откуда путаница.** В задачах на «общее время» (cumulative wait time, work scheduling) ответ часто сумма. Network Delay — задача про **самое долгое ожидание**, не суммарная нагрузка.
>
>     **Если бы это было правдой.** Для сети из 1000 узлов сумма всех `dist` может достигать `10⁹`, что overflowит `int` и даёт неверный ответ. На LeetCode 743 это автоматический WA (Wrong Answer).
>
>     **Как было бы правильно.** Признать: ответ — `max(dist[i])` (latency до последнего узла); сумма не релевантна.
>
> - [ ] B. `if (d > dist[u]) continue;` — это оптимизация для отказа от тупиков; без неё алгоритм работает, просто медленнее.
>
>     **Что на самом деле.** Это **обязательная** проверка для корректности с lazy deletion в PriorityQueue. Когда находим более короткий путь к `u`, делаем `pq.offer({newDist, u})`, но НЕ удаляем старую запись. При `poll()` можем получить устаревший (более длинный) путь, который игнорируем через `d > dist[u]`. Без этой проверки алгоритм даёт **неверный** результат — обновляет соседей через устаревшие dist.
>
>     **Откуда путаница.** Строка похожа на «оптимизацию» — «если уже нашли путь короче, пропустим». Без неё алгоритм идёт по stale data, порождая incorrect updates.
>
>     **Если бы это было правдой.** В production-имплементации Google Maps кратчайший путь к точке стал бы случайно длиннее оптимального — пользователь увидел бы маршрут «через всю Москву» вместо прямой улицы.
>
>     **Как было бы правильно.** Признать: `d > dist[u]` — корректность с lazy deletion, не оптимизация; без неё — bug.
>
> - [ ] C. Можно использовать BFS вместо Dijkstra — граф невзвешенный, BFS быстрее.
>
>     **Что на самом деле.** Граф **взвешенный** — каждое ребро `[u, v, w]` имеет вес `w` (время передачи). BFS даёт минимальное **число рёбер**, не минимальное **суммарное время**. Путь `A→B→C` через рёбра 1+1=2 короче, чем `A→C` через ребро 5, хотя в BFS второй был бы выбран (меньше рёбер).
>
>     **Откуда путаница.** «Время передачи сигнала» звучит похоже на BFS-задачу о level. Но веса разные — BFS даёт WA на тестах с w > 1.
>
>     **Если бы это было правдой.** Network Delay Time прошёл бы на маленьких тестах, но на тестах с весами > 1 (они там точно есть) — WA на 50%+ кейсов.
>
>     **Как было бы правильно.** Признать: граф взвешенный → Dijkstra; BFS — только для unit weights.
>
> - [x] D. Ответ — `max(dist[i])`; если хоть одна вершина недостижима — `-1`; lazy deletion через `d > dist[u]` гарантирует корректность при множественных offers в pq.
>
>     **Развёрнутое объяснение.** Network Delay Time — прямая обёртка над Dijkstra. После запуска Dijkstra из узла `k` имеем `dist[]` — кратчайшее время от `k` до каждой вершины. Ответ — `max(dist[i])` (время до самой удалённой вершины — последний достигнутый узел). Если хоть одна вершина имеет `dist == Integer.MAX_VALUE` (недостижима из k) — return `-1`. Реализация на PriorityQueue использует ленивое удаление: при найденной более короткой дистанции добавляем новую запись в pq, старую не удаляем (она будет проигнорирована при poll через guard `if (d > dist[u]) continue`).
>
>     **Пример.** Routing protocols (OSPF в IP-сетях) — поиск кратчайшего пути; PageRank-подобные алгоритмы используют тот же подход. Yandex.Доставка и Uber — расчёт ETA через граф дорог. Service mesh latency analysis: Istio metrics + Dijkstra-вариант для определения «дальнего» сервиса от entry-point. На LeetCode 743 — каноничный пример Dijkstra-задачи.
>
>     **Когда применять.** Любая задача «время до самого удалённого узла» на weighted графе: network propagation, signal delay, latency analysis, broadcast time estimation. Если граф unweighted — BFS быстрее. Если веса отрицательные — Bellman-Ford. Для очень больших графов (10⁶+) — Dijkstra с binary heap + lazy deletion.
>
>     **Подводные камни.** **Decrease-key vs lazy deletion**: учебный Dijkstra использует decrease-key (Fibonacci heap), но `java.util.PriorityQueue` не поддерживает — lazy deletion стандарт, цена `O(E log E)` vs `O(E log V)`. **Отрицательные веса** — задача гарантирует положительные, иначе Bellman-Ford. **Overflow** `Integer.MAX_VALUE + w` — нужна проверка `if (dist[u] != Integer.MAX_VALUE)`. **Граф 1-индексированный** (узлы 1..n) — `adj` размером `n+1`, частая off-by-one ошибка.
>
>     **Связанные вопросы.** [[graphs-interview#Q10]] Dijkstra с детальным разбором; [[graphs-interview#Q11]] Bellman-Ford для отрицательных весов; [[graphs-interview#Q13]] Floyd-Warshall для all-pairs.

## Q31. (!) Clone Graph — глубокое копирование?

Глубокое копирование графа с задаными вершинами и рёбрами.

```java
class Node { int val; List<Node> neighbors; }

Node cloneGraph(Node node) {
    if (node == null) return null;
    Map<Node, Node> visited = new HashMap<>();
    return dfs(node, visited);
}

Node dfs(Node node, Map<Node, Node> visited) {
    if (visited.containsKey(node)) return visited.get(node);
    Node copy = new Node();
    copy.val = node.val;
    copy.neighbors = new ArrayList<>();
    visited.put(node, copy);
    for (Node n : node.neighbors) {
        copy.neighbors.add(dfs(n, visited));
    }
    return copy;
}
```

`O(V + E)`. HashMap нужен, чтобы не клонировать одну вершину дважды.


> [!mcq] Clone Graph — зачем нужен `Map<Node, Node>` и что произойдёт без него?
>
> - [ ] A. `Map<Node, Node>` нужен только как visited set — простая проверка «посещён или нет».
>
>     **Что на самом деле.** Map хранит **отображение оригинал → копия**, не просто «посещён». Это критично: при повторном проходе через уже клонированный узел через другое ребро нужно вернуть **тот же экземпляр копии**, не создавать новый. `Set<Node> visited` дал бы только информацию «был там», но не «куда я положил клон».
>
>     **Откуда путаница.** В обычных DFS/BFS `visited` — это `Set<Node>`. В Clone Graph нужна именно `Map<orig, clone>` — композитная роль (visited + mapping).
>
>     **Если бы это было правдой.** При `Set` мы знали бы, что узел посещён, но в `copy.neighbors.add(...)` не могли бы добавить правильный клон (нет ссылки) — алгоритм не компилировался бы.
>
>     **Как было бы правильно.** Признать: Map — это и visited, и mapping; Set был бы недостаточен.
>
> - [ ] B. Без `visited` алгоритм работает медленнее, но даёт правильный результат.
>
>     **Что на самом деле.** Без `visited` алгоритм **зацикливается** на циклах в графе. Пример: A↔B (взаимная связь): `clone(A)` вызовет `clone(B)`, который вызовет `clone(A)`, и так бесконечно → `StackOverflowError`.
>
>     **Откуда путаница.** «Оптимизация для скорости» — частая мысль про `visited` в линейных алгоритмах. В Clone Graph это **корректность**, не оптимизация.
>
>     **Если бы это было правдой.** На тесте `[[2],[1]]` (A↔B) — простой циклический граф — мы получили бы SO. На production (копирование DOM с back-references) — crash сервера.
>
>     **Как было бы правильно.** Признать: visited критичен для корректности на циклических графах; без него — infinite recursion.
>
> - [ ] C. Алгоритм работает только для деревьев, не для произвольных графов.
>
>     **Что на самом деле.** Алгоритм работает для **произвольных** графов, включая циклические и с back-edges. Map хранит уже скопированные узлы, поэтому циклы корректно замыкаются: `copy_A.neighbors` будет содержать `copy_B`, у которого в neighbors — `copy_A`.
>
>     **Откуда путаница.** «Глубокое копирование» в обычном объектном мире (Object.clone, Jackson serialization) часто работает только на деревьях — циклы вызывают SO или infinite JSON. Граф специально проектируется для циклов, поэтому нужен HashMap.
>
>     **Если бы это было правдой.** Clone Graph не имел бы смысла как задача — деревья клонируются тривиально через рекурсию без map.
>
>     **Как было бы правильно.** Признать: алгоритм с Map работает для любого графа, включая циклы.
>
> - [x] D. Map хранит mapping `original → clone`; при повторном попадании на узел возвращаем уже созданную копию; это решает циклы и shared neighbors; `O(V+E)` время, `O(V)` память.
>
>     **Развёрнутое объяснение.** Deep copy графа должен сохранить структуру: если у оригинала A→B и B→A (цикл), у копии должно быть A'→B' и B'→A'. Без map наивный DFS на A → B → A → ... → SO. Решение — map `original → clone`. Первый раз при виде узла создаём копию и сразу кладём в map (до рекурсии по соседям). Когда DFS возвращается к этому узлу через цикл или другое ребро, видим его в map и возвращаем существующую копию. Сложность — `O(V+E)` время (каждый узел и ребро обрабатываются раз), `O(V)` память на map. Это оптимум.
>
>     **Пример.** Snapshot изменяемой структуры (текущее состояние графа зависимостей пакетов перед операцией over). Immutable replicas в reactive системах (RxJava graph snapshots). DOM-cloning в браузерных движках с back-references (parent ↔ child). IntelliJ IDEA — копирование AST с cross-references при refactoring (rename, extract method). Spring's `BeanDefinition` cloning во время configuration phase.
>
>     **Когда применять.** Любая задача deep copy структуры с возможными циклами или shared references: graph snapshots, immutable replicas в reactive systems, копирование AST в compiler tooling, transactions snapshots в graph databases. Если структура — дерево (без cycles, без shared), достаточно простой рекурсии без map.
>
>     **Подводные камни.** **`visited.put(node, copy)` ДО рекурсии** — иначе цикл не закроется (мы пометим узел уже после возврата из соседей, и при возврате через цикл сноваса создадим). **Многопоточность**: если граф модифицируется параллельно с клонированием — нужен snapshot или lock; `ConcurrentHashMap` для visited не помогает (проблема в самом графе). **BFS-альтернатива**: безопаснее от stack overflow на очень глубоких графах. **Custom Node** с метаданными — нужно копировать все поля, иначе клон «лысый». **equals/hashCode**: HashMap использует identity (если не переопределены) — правильно для clone graph; переопределение по `val` сломает на графах с дубликатами values.
>
>     **Связанные вопросы.** [[graphs-interview#Q6]] DFS как базовый алгоритм; [[graphs-interview#Q19]] cycle detection через visited; [[graphs-interview#Q21]] компоненты связности.

## Q32. (!) Где графы встречаются в реальной разработке?

1. **Spring DI** — bean dependency graph (тополог. сорт. для определения порядка инициализации)
2. **Maven/Gradle** — модули и их зависимости
3. **Compilers** — control flow graph (CFG), data flow analysis
4. **Социальные сети** — friends, followers, recommendations
5. **Routing protocols** — OSPF (Dijkstra), BGP
6. **Knowledge graphs** — Google Knowledge Graph, Wikipedia
7. **Code analysis** — call graphs, import graphs (детектор циклов)
8. **Recommender systems** — collaborative filtering
9. **Network topology** — datacenter design, mesh networks
10. **Workflow orchestration** — Airflow DAGs, Argo Workflows


> [!mcq] Какая конкретная задача из реальной разработки требует именно топологической сортировки в графе?
>
> - [ ] A. Поиск кратчайшего маршрута между офисами компании на карте.
>
>     **Что на самом деле.** Маршрутизация по карте — это задача про weighted graph с весами = расстояние/время. Решается Dijkstra (или A* для оптимизации), не топологической сортировкой. Topo sort применима только к **DAG** и упорядочивает узлы так, что рёбра идут «вперёд».
>
>     **Откуда путаница.** «Маршрут от A до B» интуитивно звучит как «порядок шагов». Но маршрут — последовательность вершин в пути, topo order — глобальное расписание вершин по зависимостям.
>
>     **Если бы это было правдой.** Google Maps выдавал бы маршрут с противоречиями («поверните налево, но сначала направо») — topo sort не учитывает физические расстояния и циклы (а в дорожной сети есть круговые движения).
>
>     **Как было бы правильно.** Сказать: «маршрут по карте → Dijkstra/A*; topo sort → для DAG зависимостей».
>
> - [ ] B. Поиск кратчайшей цепочки знакомств в социальной сети (six degrees of Kevin Bacon).
>
>     **Что на самом деле.** Это задача BFS на **невзвешенном** графе друзей. Социальные сети — undirected (A друг B ⟺ B друг A) и обычно с **циклами** (треугольники друзей). Topological sort требует DAG — соц-граф им не является.
>
>     **Откуда путаница.** «Цепочка знакомств» звучит как «упорядочить людей по связям». Но в соц-графе нет иерархии (X не «выше» Y), и BFS даёт кратчайший путь без необходимости упорядочивать всех.
>
>     **Если бы это было правдой.** LinkedIn отказался бы от feature «как вы знаете этого человека» при наличии треугольников друзей — topo sort падал бы на циклах. Реально LinkedIn использует BFS глубиной 1-2-3 («1st/2nd/3rd connection»).
>
>     **Как было бы правильно.** Признать: соц-сеть → BFS; topo sort требует ациклический directed.
>
> - [x] C. Spring Boot определяет порядок инициализации beans с учётом `@DependsOn` и конструкторных зависимостей через топологическую сортировку bean dependency graph.
>
>     **Развёрнутое объяснение.** Spring контейнер строит **граф зависимостей beans**: ребро `B → A` означает «B зависит от A» (A создаётся раньше). Граф должен быть ациклическим (DAG) — иначе `BeanCurrentlyInCreationException`. Spring выполняет топологическую сортировку (Kahn's algorithm) и инициализирует beans от leaves (без зависимостей) к roots: `@Repository` → `@Service` → `@Controller`. Это classical use case topo sort на directed acyclic dependency graph.
>
>     **Пример.** Типичная конфигурация: `DataSource → UserRepository → UserService → UserController`. Spring собирает граф через сканирование `@Component`/`@Bean` методов и их parameter types, запускает Kahn для определения порядка. Если есть цикл `A ↔ B` через конструкторы — fail-fast с ясным сообщением. Workaround — setter injection с `@Lazy` (создание прокси, отложенный resolution).
>
>     **Когда применять.** Любая система с DAG-зависимостями: build systems (Maven/Gradle topo sort модулей), Apache Airflow (DAG в названии), database migrations (Flyway/Liquibase V1 → V2 → V3), Make/Bazel/Buck (топосорт targets), NPM/Yarn package install. Где есть «X должен быть готов до Y» — там topo sort.
>
>     **Подводные камни.** **Циклы фатальны** — в Spring `BeanCurrentlyInCreationException`; workaround через `@Lazy` setter injection — code smell. **Несколько валидных порядков** — Spring выбирает любой допустимый; на воспроизводимости влияет редко, но debug гонок удивляет. **`@DependsOn`** — explicit override для зависимостей, не выражаемых через конструктор (side effects от инициализации другого bean).
>
>     **Связанные вопросы.** [[graphs-interview#Q24]] topo sort definition; [[graphs-interview#Q25]] Kahn's algorithm; [[graphs-interview#Q26]] DFS-вариант через post-order.
>
> - [ ] D. Recommendation engine рекомендует фильмы на основе похожих пользователей — это типичная topo sort задача.
>
>     **Что на самом деле.** Recommendation engines используют **collaborative filtering** на bipartite графе (users ↔ items) и матричную факторизацию (SVD, ALS), не топологическую сортировку. Граф user-item не ациклический и не имеет порядка обхода — нужна оценка similarity (cosine).
>
>     **Откуда путаница.** «Граф похожих» звучит как «упорядочить по похожести». Но это сортировка по числовой метрике (cosine similarity), не topo sort по структурным зависимостям.
>
>     **Если бы это было правдой.** Netflix не показывал бы рекомендации в персонализированном порядке — только в общем «topo-sorted» (что бессмысленно для разных users). Реально Netflix использует matrix factorization + reinforcement learning.
>
>     **Как было бы правильно.** Признать: recommendations → collaborative filtering, matrix factorization; topo sort — для строгих dependency orderings.

## Q33. Что такое graph database? Когда выбирать?

**Graph database** — БД с нативной моделью узлов и рёбер, оптимизированная для traversal-запросов.

Примеры: **Neo4j**, ArangoDB, Amazon Neptune, JanusGraph.

**Когда выбирать:**
- Запросы с **множественными join'ами** (соц. сети — «друзья друзей друзей»)
- Граф знаний и онтологии
- Fraud detection (поиск подозрительных паттернов)
- Recommendation engines
- Network topology analysis

**Когда НЕ выбирать:**
- Простые CRUD-операции — relational БД проще
- Аналитика по агрегатам — column store (ClickHouse)

Запросы пишут на **Cypher** (Neo4j), Gremlin, SPARQL.


> [!mcq]
>
> **Вопрос:** Когда выбор Neo4j (graph database) **оправдан** против PostgreSQL с обычным relational подходом?
>
> ---
>
> #### A) Когда у нас 10M строк в одной таблице — Neo4j быстрее обрабатывает большие данные — ❌ Неверно
>
> **Что на самом деле:** Neo4j НЕ оптимизирован для агрегаций по большим однородным данным. Для счётов, средних, group-by по 10M строк PostgreSQL и тем более ClickHouse (column store) значительно быстрее. Neo4j выигрывает на **multi-hop traversals**, не на масштабе записей.
>
> **Откуда путаница:** маркетинг graph DB говорит про «big data», но в контексте графов это «много связей», не «много строк одного типа».
>
> **Если бы это было правдой:** инжерия Booking.com или Yandex выбрала бы Neo4j для общих метрик (revenue per region), что было бы катастрофой по производительности. Реально они используют ClickHouse для агрегатов и Neo4j для специфичных recommendation queries.
>
> ---
>
> #### B) Когда мы делаем 5+ JOIN'ов уровней «друзья друзей друзей» и они стали слишком медленными в SQL — ✓ Верно
>
> **Развёрнутое объяснение:**
>
> Ключевое преимущество graph DB — **index-free adjacency**: связь между узлами хранится как прямой указатель, а не как foreign key, который надо JOIN'ить. Это даёт `O(N)` обход цепочки длиной N независимо от размера базы.
>
> В PostgreSQL «friends of friends of friends» — это 3 JOIN'а с self-таблицей `friendships`. На графе друзей соц. сети из 100M пользователей с avg 200 друзьями:
> - SQL: каждый JOIN сканирует/индексирует 200^N комбинаций. На 4 уровнях — 200^4 = 1.6 миллиарда, минуты.
> - Neo4j: переходы по указателям, ~200^4 операций по `O(1)` каждая = миллисекунды.
>
> **Пример (Cypher):**
> ```cypher
> // 4 уровня вглубь от Alice — кого знаем через 3 рукопожатия
> MATCH (alice:Person {name: 'Alice'})-[:FRIEND*1..4]-(person)
> WHERE alice <> person
> RETURN DISTINCT person.name, length((alice)-[:FRIEND*]-(person)) AS distance
> ORDER BY distance LIMIT 50
> ```
>
> Тот же запрос в SQL потребовал бы рекурсивного CTE (`WITH RECURSIVE`) и плохо оптимизируется на больших графах.
>
> **Когда применять:**
> - **LinkedIn** — «How you know X», degree of connection (1st/2nd/3rd) — Neo4j-подобный движок (внутренний LIquid).
> - **Fraud detection** — обнаружение колец из 5+ участников, которые перемещают деньги по кругу. Banks (HSBC, ING) используют Neo4j для AML compliance.
> - **Recommendation engines** на основе знаний (knowledge graph): «люди, которые купили Х и Y, также купили Z» через multi-hop.
> - **Network topology analysis** — мониторинг service dependencies (Istio service mesh + Neo4j для визуализации цепочек вызовов).
> - **Identity & access management** — кто имеет доступ к каким ресурсам через какие группы (transitive permissions).
>
> **Подводные камни:**
> - **Цена**: Neo4j Enterprise дорогой ($, в 5-10× выше PostgreSQL VM). Open-source Community version имеет ограничения (1 GB DB store до v5).
> - **Слабая аналитика**: для агрегатов и BI нужно ETL'ить данные из Neo4j в OLAP-хранилище. Это сложный pipeline.
> - **Memory-heavy**: graph DB держит граф в памяти для быстрого traversal. На графе 100M узлов нужны 64+GB RAM.
> - **Транзакции** в Neo4j ACID, но кросс-cluster (causal cluster) — eventual; не подходит для финансовых транзакций.
>
> **Связанные вопросы:** [[graphs-interview#Q1]] — типы графов и базовая терминология; [[graphs-interview#Q32]] — где графы встречаются в реальной разработке; [[graphs-interview#Q34]] — PageRank как пример graph algorithm в production.
>
> ---
>
> #### C) Когда наши данные хорошо структурированы и нам нужен strict schema — ❌ Неверно
>
> **Что на самом деле:** Neo4j использует **schema-flexible** модель — у узлов могут быть произвольные properties, и schema-проверки опциональны (можно настроить `CREATE CONSTRAINT`, но не обязательно). Strict schema — преимущество **relational** БД, а не graph.
>
> **Откуда путаница:** «labeled property graph» звучит структурированно, и Neo4j действительно даёт типы рёбер (`[:FRIEND]`, `[:FOLLOWS]`). Но это не то же самое что строгая схема с NOT NULL, foreign keys, check constraints.
>
> **Если бы это было правдой:** мы бы выбрали Neo4j вместо PostgreSQL для типичного банкоского приложения (account, transaction, customer). На практике банки используют PostgreSQL/Oracle для core data, а Neo4j — только для fraud detection layer поверх.
>
> ---
>
> #### D) Когда мы хотим уменьшить нагрузку на CPU за счёт хранения данных в формате column store — ❌ Неверно
>
> **Что на самом деле:** Neo4j — НЕ column store. Это object/property storage, оптимизированный для быстрого traversal по указателям. Column store — это ClickHouse, Apache Parquet, BigQuery — для OLAP-аналитики.
>
> **Откуда путаница:** «не SQL» иногда обобщают в «современная альтернатива RDBMS», смешивая graph DB и column store. На самом деле это разные классы — graph для связей, column для агрегатов.
>
> **Если бы это было правдой:** для отчёта «средний revenue per customer category за квартал» мы выбрали бы Neo4j, и запрос выполнялся бы минутами вместо секунд в ClickHouse. Для агрегаций — column store, не graph.

## Q34. (!) PageRank — как работает?

**PageRank** (Page-Brin, 1998) — алгоритм оценки важности веб-страницы по ссылкам.

**Идея:** «случайный сёрфер» с вероятностью `d` (=0.85) переходит по ссылке, с вероятностью `1-d` — на случайную страницу.

```
PR(p) = (1-d)/N + d · Σ (PR(q) / L(q))   для q → p
```

Итеративный алгоритм:
1. Инициализировать PR всех страниц = 1/N
2. Обновлять PR по формуле
3. Повторять до сходимости

```java
double[] pageRank(int n, List<List<Integer>> adj, int iterations) {
    double[] pr = new double[n];
    Arrays.fill(pr, 1.0 / n);
    double damp = 0.85;

    for (int iter = 0; iter < iterations; iter++) {
        double[] next = new double[n];
        for (int u = 0; u < n; u++) {
            int outDegree = adj.get(u).size();
            if (outDegree == 0) continue;
            double share = damp * pr[u] / outDegree;
            for (int v : adj.get(u)) next[v] += share;
        }
        for (int i = 0; i < n; i++) next[i] += (1 - damp) / n;
        pr = next;
    }
    return pr;
}
```

Применения: Google search ranking, citation networks, social influence detection.

> [!mcq]
>
> **Вопрос:** PageRank — какой параметр `d=0.85` означает и что делает «damping factor»?
>
> ---
>
> #### A) `d=0.85` — это доля памяти, выделяемой алгоритму (85%) — ❌ Неверно
>
> **Что на самом деле:** `d` — это **вероятность** того, что random surfer перейдёт по ссылке с текущей страницы (продолжит блуждание), а `1-d=0.15` — вероятность телепортации на случайную страницу. Память тут ни при чём.
>
> **Откуда путаница:** «85%» звучит как «много», и можно представить это как «лимит ресурса». В алгоритмическом контексте это вероятностный параметр Markov chain.
>
> **Если бы это было правдой:** алгоритм бы вылетал по OOM или работал на 85% мощности — но никакой связи между PR результатами и `d` тогда бы не было. По факту PR без damping factor (`d=1`) расходится (не сходится) для графов с тупиками и циклами.
>
> ---
>
> #### B) `d` определяет порядок итераций — сколько раз обновлять PR — ❌ Неверно
>
> **Что на самом деле:** число итераций — отдельный параметр (обычно 20-100). Damping factor `d` определяет **вероятностное поведение** random surfer, не количество циклов.
>
> **Откуда путаница:** в коде `for (iter = 0; iter < iterations; iter++)` и `damp = 0.85` стоят рядом, и можно их перепутать как «параметры итераций». Но они разные.
>
> **Если бы это было правдой:** при `d=0.85` мы бы делали 85 итераций (или 850?), но PR не зависел бы от структуры графа правильно — был бы лишь функцией числа итераций.
>
> ---
>
> #### C) Damping factor `d` — вероятность что random surfer продолжит идти по ссылкам; `(1-d)/N` — равномерная telepor­tation вероятность; без damping PageRank не сходится для графов с тупиками — ✓ Верно
>
> **Развёрнутое объяснение:**
>
> Идея PageRank — моделировать «случайного сёрфера», который кликает по случайным ссылкам. PR страницы — вероятность что сёрфер окажется на ней в стационарном состоянии (после бесконечно долгого блуждания).
>
> **Проблема 1**: страницы-тупики (нет исходящих ссылок) — сёрфер «застревает». Решение — telepor­tation: с вероятностью `1-d` он телепортируется на случайную страницу.
>
> **Проблема 2**: spider-trap (циклы, ведущие в петлю) — без teleport PageRank накапливается в петле. Telepor­tation размывает PR равномерно.
>
> **Проблема 3**: гарантия сходимости. Цепь Маркова с teleport — irreducible и aperiodic → сходится к уникальному стационарному распределению.
>
> Значение `d=0.85` — экспериментально подобрано в оригинальной статье Page-Brin (1998). Дисбаланс: высокий `d` ближе к структуре ссылок (но медленнее сходится), низкий — больше teleport (быстрее сходится, но размывает).
>
> **Пример:**
> ```java
> double[] pageRank(int n, List<List<Integer>> adj, int iterations) {
>     double[] pr = new double[n];
>     Arrays.fill(pr, 1.0 / n);              // init: равномерное распределение
>     double damp = 0.85;
>     for (int iter = 0; iter < iterations; iter++) {
>         double[] next = new double[n];
>         double dangling = 0;                // сумма PR тупиковых страниц
>         for (int u = 0; u < n; u++) {
>             int out = adj.get(u).size();
>             if (out == 0) {
>                 dangling += pr[u];          // dangling node — распределим равномерно
>                 continue;
>             }
>             double share = damp * pr[u] / out;
>             for (int v : adj.get(u)) next[v] += share;
>         }
>         double teleport = (1 - damp) / n + damp * dangling / n;
>         for (int i = 0; i < n; i++) next[i] += teleport;
>         pr = next;
>     }
>     return pr;
> }
> ```
>
> **Когда применять:**
> - **Google Search Ranking** (исторический пример) — оценка важности страниц в Web.
> - **Twitter «Who to follow»** — graph of mentions/retweets с PR-вариантом (Personalized PageRank).
> - **Citation analysis** в академии (Microsoft Academic Graph) — важность научных статей по ссылкам других статей.
> - **Fraud detection** — узлы (счета) с высоким PR в transaction graph могут быть hub'ами money-laundering.
> - **Recommendation systems** — Personalized PageRank как baseline для item-item recommendations.
>
> **Подводные камни:**
> - **Dangling nodes** (без исходящих рёбер) — наивный алгоритм теряет вероятность каждую итерацию. Решение — раздавать их PR равномерно (см. `dangling` в примере).
> - **Сходимость**: на больших графах нужно 50-100 итераций. Критерий остановки — `|pr_new - pr_old| < eps` вместо фиксированного числа итераций.
> - **Sensitivity к спаму**: можно манипулировать PR через link farms. Google добавил TrustRank и алгоритмы anti-spam, чтобы compensate.
> - **Personalized PageRank** меняет вектор телепортации с равномерного `1/N` на user-specific — теперь PR центрирован на пользователе, не на всех страницах одинаково.
>
> **Связанные вопросы:** [[graphs-interview#Q1]] — определение графа (PageRank — directed, weighted); [[graphs-interview#Q33]] — graph DB (Neo4j имеет встроенный PR procedure `gds.pageRank`); [[graphs-interview#Q32]] — реальные применения графов в продукте.
>
> ---
>
> #### D) Damping factor предотвращает зависание программы (deadlock protection) — ❌ Неверно
>
> **Что на самом деле:** алгоритм PageRank — итеративный детерминированный, в нём нет concurrent access или locks. Deadlock к нему неприменим. Damping factor — про математическую сходимость Markov chain, не про runtime.
>
> **Откуда путаница:** «защита от чего-то плохого» (зависания/нерасчёта) — частая интерпретация любой страховочной константы. В контексте PR это страховка от математической дивергенции, не от system-level deadlock.
>
> **Если бы это было правдой:** мы бы могли отключить damping factor в однопоточной среде «потому что deadlock невозможен» — но тогда PR не сошёлся бы вообще или дал бы неверные значения. PR требует teleport на математическом уровне, а не на инфраструктурном.
