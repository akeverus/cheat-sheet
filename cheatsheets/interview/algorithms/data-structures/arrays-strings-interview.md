## Q1. (!) Какие отличия между Array и ArrayList?

| Характеристика | Array | ArrayList |
|---------------|-------|-----------|
| Размер | Фиксированный | Динамический (1.5x при росте) |
| Тип | Любые (включая примитивы `int[]`) | Только объекты (`Integer`, не `int`) |
| Доступ | `arr[i]` — `O(1)` | `list.get(i)` — `O(1)` |
| Вставка в конец | — | `O(1)` амортиз. |
| Память | Меньше (нет overhead) | Больше (объекты + capacity) |
| Generics | Нет (массивы reified) | Да (`ArrayList<T>` erasure) |

```java
// Массив примитивов — компактно, быстро
int[] arr = new int[1000];

// ArrayList — гибче, но boxing для примитивов
List<Integer> list = new ArrayList<>(1000); // initial capacity!

// Конвертация
Integer[] boxed = list.toArray(new Integer[0]);
List<Integer> back = Arrays.asList(boxed); // фиксированный размер!
```

**Подводный камень:** `Arrays.asList(int[])` вернёт `List<int[]>` размером 1, а не `List<Integer>`. Для примитивов — `Arrays.stream(arr).boxed().toList()`.


> [!mcq] В чём ключевое отличие `int[]` от `ArrayList<Integer>` в Java?
>
> - [x] A. `int[]` хранит примитивы без boxing и имеет фиксированный размер; `ArrayList<Integer>` хранит объекты-обёртки и растёт динамически.
>
>     **Развёрнутое объяснение.** `int[]` — reified-структура JVM: элементы лежат в непрерывном блоке памяти как 4-байтовые `int`, тип компонента известен в рантайме. `ArrayList<Integer>` внутри держит `Object[] elementData`, каждый элемент — ссылка на heap-объект `Integer` (16+ байт overhead на заголовок + поле). Размер массива фиксируется при `new int[n]`, а `ArrayList` расширяет внутренний буфер в 1.5 раза при переполнении через `Arrays.copyOf` (амортизированный `O(1)` на `add`).
>
>     **Пример.** `int[] arr = new int[1_000_000]` занимает ≈ 4 МБ непрерывной памяти; `ArrayList<Integer>` на миллион элементов — 20+ МБ из-за заголовков объектов и ссылок. В Twitter timeline-расчётах счётчики лайков держат как `long[]`, а не `List<Long>` — это снижает heap-pressure и GC-паузы.
>
>     **Когда применять.** `int[]`/`long[]` — алгоритмы, hot-path, парсинг больших файлов, low-latency сервисы (Aeron, LMAX Disruptor). `ArrayList` — бизнес-код, где нужны дженерики, динамический размер, методы `add/remove/contains` и совместимость с Collections API.
>
>     **Подводные камни.** `Arrays.asList(intArr)` вернёт `List<int[]>` размером 1, а не `List<Integer>` — массив примитивов не unboxится. Для boxing: `Arrays.stream(arr).boxed().toList()`. Массивы дженерик-типов создать нельзя: `new T[10]` не скомпилируется (reified vs erased конфликт).
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q2]] реверс `int[]`; [[arrays-strings-interview#Q33]] String pool и `==`; [[arrays-strings-interview#Q35]] StringBuilder vs конкатенация.
>
> - [ ] B. Оба используют динамический рост, но `ArrayList` быстрее на чтении из-за внутренней индексации.
>
>     **Что на самом деле.** Скорость `O(1)` random access у обоих, но `int[]` быстрее: прямое чтение из памяти без method-call и unboxing. `ArrayList.get(i)` делает `elementData[i]` + cast + unboxing к `int`. Массивы примитивов НЕ растут — для расширения нужно явно вызывать `Arrays.copyOf`.
>
>     **Откуда путаница.** Оба дают `O(1)` доступ по индексу, поэтому кажется, что они эквивалентны. Но JIT оптимизирует чтение из `int[]` через bounds-check elimination и SIMD-инструкции, а `ArrayList<Integer>.get(i)` упирается в indirection через heap-ссылку.
>
>     **Если бы это было правдой.** Не было бы смысла держать массивы примитивов в языке, и проекты типа LMAX Disruptor / Aeron не показывали бы 10x speedup на `long[]` против `List<Long>` в low-latency бенчмарках.
>
>     **Как было бы правильно.** Сказать, что `int[]` фиксирован и быстрее благодаря отсутствию boxing/indirection, а `ArrayList<Integer>` гибче за счёт динамического роста — но платит overhead на обёртках.
>
> - [ ] C. `ArrayList` поддерживает дженерики через reification, а массивы используют type erasure.
>
>     **Что на самом деле.** Наоборот — **массивы** в Java reified (знают свой компонентный тип в рантайме, бросают `ArrayStoreException` при попытке положить чужой тип), а **дженерики** `ArrayList<T>` стираются: в рантайме это просто `ArrayList` без `T`.
>
>     **Откуда путаница.** Слова «reified» и «erased» звучат экзотично, и студенты помнят, что что-то одно — устаревшее/новое, путая направление. Reified array vs erased generic — древний дизайн-конфликт Java 5.
>
>     **Если бы это было правдой.** `new T[10]` компилировался бы без проблем, а `Object[] arr = new Integer[5]; arr[0] = "x"` падал бы только в `ArrayList`, но не в массиве. На практике первое запрещено компилятором, второе ловится массивом.
>
>     **Как было бы правильно.** Указать, что массивы — reified (помнят тип) и ковариантны (`Integer[]` это `Object[]`), а generics — erased и инвариантны (`ArrayList<Integer>` не `ArrayList<Object>`).
>
> - [ ] D. Массивы и ArrayList идентичны по семантике, разница только в синтаксисе `arr[i]` vs `list.get(i)`.
>
>     **Что на самом деле.** Они различаются по памяти (примитивы vs heap-объекты), росту (фиксированный vs динамический), API (нет методов vs `add/remove/contains/iterator`), дженерикам (нет vs erasure) и вариантности (массивы ковариантны, generics инвариантны).
>
>     **Откуда путаница.** Оба «индексируемые контейнеры», и в туториалах часто показывают взаимозаменяемые примеры `for (int i = 0; i < n; i++)`.
>
>     **Если бы это было правдой.** Не было бы причин держать в JDK обе абстракции, и API `Collection.toArray(T[])` не существовал бы как мост между мирами.
>
>     **Как было бы правильно.** Признать, что синтаксис — лишь верхушка: разные данные (`int` vs `Integer`), разная память, разные API, разная вариантность типов — это две принципиально разные структуры.

## Q2. Как реверсировать массив?

```java
// In-place через two pointers — O(n) время, O(1) память
void reverse(int[] arr) {
    int left = 0, right = arr.length - 1;
    while (left < right) {
        int tmp = arr[left];
        arr[left++] = arr[right];
        arr[right--] = tmp;
    }
}

// Через стандартную библиотеку для объектов
Collections.reverse(list);

// Reverse Stream
int[] reversed = IntStream.rangeClosed(1, arr.length)
                          .map(i -> arr[arr.length - i])
                          .toArray();
```

Для примитивов в стандартной библиотеке нет прямого `Arrays.reverse()` — пишут вручную или через `Collections.reverse(Arrays.asList(boxedArr))`.


> [!mcq] Какой способ реверса `int[]` массива оптимален по времени и памяти?
>
> - [ ] A. `Collections.reverse(Arrays.asList(arr))` — самое короткое и идиоматичное решение.
>
>     **Что на самом деле.** Для `int[]` это НЕ сработает: `Arrays.asList(intArr)` вернёт `List<int[]>` из одного элемента (сам массив целиком), и `Collections.reverse` развернёт список длиной 1, оставив исходные данные нетронутыми. Работает только для `Integer[]` (массива обёрток).
>
>     **Откуда путаница.** Для object-массивов (`String[]`, `Integer[]`) рецепт действительно одна строка, и его механически переносят на примитивы, не глядя на дженерик-сигнатуру `asList(T...)`.
>
>     **Если бы это было правдой.** В JDK не появились бы постоянные просьбы добавить `Arrays.reverse(int[])` (есть открытый JEP-запрос), и StackOverflow не имел бы тысяч вопросов «почему мой `int[]` не реверснулся после `Collections.reverse`».
>
>     **Как было бы правильно.** Сказать, что метод подходит только для `Integer[]`/`String[]`, а для `int[]` нужен ручной two-pointers цикл — и тогда формулировка становится корректной.
>
> - [x] B. Two pointers in-place: `left=0`, `right=n-1`, swap и двигаемся навстречу — `O(n)` время, `O(1)` память.
>
>     **Развёрнутое объяснение.** Два индекса идут навстречу друг другу. На каждом шаге обмениваем `arr[left]` и `arr[right]`, инкрементируем `left` и декрементируем `right`. Цикл завершается при `left >= right`. Делается ровно `n/2` обменов, без дополнительных аллокаций — работаем прямо в исходном массиве. Шаблон стабильно ловится JIT и оптимизируется через bounds-check elimination.
>
>     **Пример.** `[1,2,3,4,5]` → swap(0,4) → `[5,2,3,4,1]` → swap(1,3) → `[5,4,3,2,1]` → left=2, right=2 → стоп за 2 итерации. На массиве в миллион элементов это ≈ 1 мс на современном CPU vs ~10 мс при `IntStream`-варианте.
>
>     **Когда применять.** Любой реверс массива или `char[]`-строки, разворот сегмента (`reverse(arr, l, r)`), часть алгоритма rotate через тройной реверс (см. Q3), Manacher pre-processing, обращение порядка байт в network-протоколах.
>
>     **Подводные камни.** Условие должно быть `left < right` (не `<=` — иначе средний элемент свопнется сам с собой). Для `n=0` цикл не выполнится — OK. При swap через XOR (`a^=b; b^=a; a^=b`) обязательно проверить `left != right`, иначе элемент обнулится. Для `String` нужен `toCharArray` (immutable), а для unicode surrogate pairs — `StringBuilder.reverse()`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q3]] циклический сдвиг через тройной реверс; [[arrays-strings-interview#Q21]] реверс строки и surrogates; [[arrays-strings-interview#Q22]] палиндромы.
>
> - [ ] C. Создать новый массив того же размера и копировать `arr[n-1-i]` в `result[i]` — самый понятный способ.
>
>     **Что на самом деле.** Работает корректно, но тратит `O(n)` дополнительной памяти, тогда как in-place two-pointers даёт `O(1)`. Для миллиона int-ов это 4 МБ лишних аллокаций и нагрузка на GC; для встроенных типов в low-latency-сервисе — недопустимо.
>
>     **Откуда путаница.** На собеседовании этот вариант проще написать без ошибок, и для маленьких массивов разница в памяти неощутима. Преподаватели часто показывают именно его как первый шаг.
>
>     **Если бы это было правдой.** Интервьюер не задавал бы follow-up «а можно ли без дополнительной памяти», и in-place реверс не был бы каноничной техникой two-pointers в LeetCode top-100.
>
>     **Как было бы правильно.** Признать, что копирование — рабочий, но субоптимальный путь; для требования `O(1)` памяти нужен встречный two-pointers in-place.
>
> - [ ] D. `IntStream.range(0, n).map(i -> arr[n-1-i]).toArray()` — функциональный одностроечник, оптимальный на современных JVM.
>
>     **Что на самом деле.** Stream создаёт новый массив (`O(n)` память), плюс overhead на pipeline-инфраструктуру и lambda capture. JIT не разворачивает это в SIMD-цикл; на JMH в горячем пути проигрывает 2–5x обычному `for`-циклу.
>
>     **Откуда путаница.** «Современный Java = stream» — карго-культ из туториалов. На простых трансформациях разница незаметна, но на массивных операциях обычный цикл стабильно выигрывает.
>
>     **Если бы это было правдой.** Apache Commons и Guava не предоставляли бы императивные хелперы для работы с `int[]`, и JMH-бенчмарки `IntStream` vs `for` не показывали бы стабильный отрыв в пользу цикла.
>
>     **Как было бы правильно.** Сказать, что Stream-вариант читаемый и pure (без mutation), но для оптимума по памяти и скорости нужен in-place two-pointers.

## Q3. (!) Как реализовать циклический сдвиг массива?

Поворот массива на `k` позиций вправо. Наивный — `O(n·k)`, оптимальный — `O(n)` через **тройной реверс**.

```java
// Метод тройного реверса — O(n) время, O(1) память
void rotate(int[] arr, int k) {
    int n = arr.length;
    k = k % n; // нормализуем k

    reverse(arr, 0, n - 1);       // [1,2,3,4,5] → [5,4,3,2,1]
    reverse(arr, 0, k - 1);       // → [4,5,3,2,1] для k=2
    reverse(arr, k, n - 1);       // → [4,5,1,2,3]
}

void reverse(int[] arr, int left, int right) {
    while (left < right) {
        int tmp = arr[left];
        arr[left++] = arr[right];
        arr[right--] = tmp;
    }
}
```

**Альтернативы:**
- Скопировать в новый массив со сдвигом — `O(n)` время и память
- Циклический алгоритм со счётчиком — `O(n)` время, `O(1)` память, но сложнее в реализации


> [!mcq] Как сделать циклический сдвиг массива на `k` позиций вправо за `O(n)` время и `O(1)` память?
>
> - [ ] A. Скопировать в новый массив со сдвинутыми индексами: `result[(i+k) % n] = arr[i]`.
>
>     **Что на самом деле.** Работает корректно и тоже `O(n)` по времени, но требует `O(n)` дополнительной памяти. Для большого массива (миллион элементов) — 4 МБ лишних аллокаций, нагрузка на GC и потеря cache-locality между записью в new и чтением из old.
>
>     **Откуда путаница.** Этот вариант проще объяснить и реализовать без off-by-one ошибок, поэтому его часто предлагают первым на собеседовании.
>
>     **Если бы это было правдой.** Не существовало бы фольклорной задачи «rotate in-place» как одной из топ-50 интервью-вопросов LeetCode (189. Rotate Array), и follow-up «а можно ли без доп. памяти?» никогда бы не задавался.
>
>     **Как было бы правильно.** Признать, что это `O(n)` по памяти и не отвечает требованию `O(1)`; для in-place нужен тройной реверс или цикл по cycle-detection.
>
> - [ ] B. Использовать `Collections.rotate(Arrays.asList(arr), k)` — стандартное решение из JDK.
>
>     **Что на самом деле.** Для `int[]` это снова не сработает: `Arrays.asList(intArr)` даёт `List<int[]>` размера 1. А для `Integer[]` `Collections.rotate` внутри использует именно тройной реверс — то есть это обёртка над правильным решением, а не самостоятельная альтернатива.
>
>     **Откуда путаница.** «Есть готовый метод в Collections» звучит профессионально, но в контексте `int[]` это просто не работает, а в контексте `Integer[]` это и есть ответ C под капотом.
>
>     **Если бы это было правдой.** Интервьюер был бы удовлетворён ответом «есть в JDK», но он явно спрашивает реализацию — иначе зачем задавать вопрос.
>
>     **Как было бы правильно.** Уточнить, что `Collections.rotate` работает на `List<T>` (не `int[]`) и сам реализован через тройной реверс — то есть знание алгоритма всё равно нужно.
>
> - [x] C. Тройной реверс: `reverse(arr, 0, n-1)` → `reverse(arr, 0, k-1)` → `reverse(arr, k, n-1)`.
>
>     **Развёрнутое объяснение.** Трюк основан на наблюдении: если развернуть весь массив, последние `k` элементов окажутся в начале (но в обратном порядке), а первые `n-k` — в конце (тоже в обратном). Два дополнительных реверса восстанавливают правильный порядок внутри каждой из двух частей. Всего три прохода, каждый `O(n)` с in-place two-pointers, итого `O(n)` времени и `O(1)` памяти — никаких аллокаций.
>
>     **Пример.** `arr=[1,2,3,4,5]`, `k=2`. Шаг 1: reverse(0,4) → `[5,4,3,2,1]`. Шаг 2: reverse(0,1) → `[4,5,3,2,1]`. Шаг 3: reverse(2,4) → `[4,5,1,2,3]`. Получили сдвиг вправо на 2 позиции — последние 2 элемента в начале.
>
>     **Когда применять.** LeetCode 189 Rotate Array, циклические сдвиги в задачах со строками (rotation check), реализация ring-buffer операций без modulo, перестановка сегментов в редакторах текста (move line up/down), палиндромная подстрока через rotation.
>
>     **Подводные камни.** Обязательно `k = k % n` до реверсов — для `k >= n` сегменты выйдут за границы. Для пустого массива `n=0` `%` бросит `ArithmeticException`, нужен ранний return. Для сдвига влево порядок тот же, но границы — `n-k` вместо `k`. Отрицательное `k` можно нормализовать как `((k % n) + n) % n`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q2]] реверс через two-pointers; [[arrays-strings-interview#Q20]] next permutation (тоже использует partial reverse); [[arrays-strings-interview#Q21]] реверс строки.
>
> - [ ] D. Перемещать элементы по одному `k` раз: `for k раз { last = arr[n-1]; for i = n-1..1 { arr[i] = arr[i-1] }; arr[0] = last }`.
>
>     **Что на самом деле.** Это `O(n·k)` — для `k = n/2` получаем `O(n²)`. На массиве в миллион элементов со сдвигом 500k это полтриллиона операций — несколько часов работы вместо миллисекунд при тройном реверсе.
>
>     **Откуда путаница.** Это самый интуитивный способ, который приходит в голову первым, и на маленьких массивах (n < 100) разница незаметна; неопытные кодеры считают, что «работает же» — значит OK.
>
>     **Если бы это было правдой.** Оптимизация через тройной реверс не давала бы измеримой разницы, и интервьюеры не использовали бы этот вопрос как фильтр для проверки понимания сложности алгоритмов на массивах.
>
>     **Как было бы правильно.** Признать, что это `O(n·k)` и для больших `k` неприемлемо; для оптимума нужен один из `O(n)` подходов — тройной реверс или cycle-detection.

## Q4. Как удалить дубликаты из отсортированного массива in-place?

```java
// Two pointers: slow = граница уникальных, fast = идёт вперёд
int removeDuplicates(int[] arr) {
    if (arr.length == 0) return 0;

    int slow = 0;
    for (int fast = 1; fast < arr.length; fast++) {
        if (arr[fast] != arr[slow]) {
            arr[++slow] = arr[fast];
        }
    }
    return slow + 1; // длина уникальной части
}
```

После работы алгоритма первые `k` элементов содержат уникальные значения. Остальное — мусор. Время `O(n)`, память `O(1)`.

Для **неотсортированного** массива требуется `HashSet` — `O(n)` время и память.


> [!mcq] Как удалить дубликаты из отсортированного массива in-place за `O(n)` время и `O(1)` память?
>
> - [ ] A. Создать `HashSet<Integer>` и собрать уникальные, потом записать обратно в массив.
>
>     **Что на самом деле.** `HashSet` даёт `O(n)` время, но `O(n)` память на хеш-таблицу — нарушает условие `O(1)` память. Плюс теряется свойство «отсортированный»: `HashSet` не сохраняет порядок, нужен дополнительный `sort` или `LinkedHashSet`.
>
>     **Откуда путаница.** Универсальный приём для неотсортированных массивов («дубликаты → HashSet») механически переносится на отсортированный случай, хотя там есть локальная two-pointers оптимизация.
>
>     **Если бы это было правдой.** LeetCode 26 не была бы помечена как Easy с конкретным требованием `O(1)` памяти, и follow-up «без доп. структур» терял бы смысл.
>
>     **Как было бы правильно.** Сказать, что HashSet нужен для неотсортированного массива, а для отсортированного дубликаты идут подряд — достаточно two-pointers.
>
> - [x] B. Two pointers: `slow` указывает на границу уникальных, `fast` идёт вперёд; при `arr[fast] != arr[slow]` пишем `arr[++slow] = arr[fast]`.
>
>     **Развёрнутое объяснение.** В отсортированном массиве дубликаты лежат подряд, поэтому достаточно сравнивать соседей. `slow` держит позицию последнего уникального значения, `fast` сканирует. Когда `arr[fast]` отличается от `arr[slow]` — это новое уникальное значение, продвигаем `slow` и записываем. Один проход, `O(n)` время, `O(1)` память; «мусор» за `slow+1` остаётся, но не мешает — длина уникальной части возвращается из функции.
>
>     **Пример.** `[1,1,2,2,3]` → slow=0, fast=1: `arr[1]=1=arr[0]`, пропуск. fast=2: `arr[2]=2 != 1`, `arr[++slow=1]=2` → `[1,2,2,2,3]`. fast=3: `2 == 2`, пропуск. fast=4: `3 != 2`, `arr[++slow=2]=3` → `[1,2,3,2,3]`. Длина уникальной = `slow+1 = 3`, первые 3 элемента — `[1,2,3]`.
>
>     **Когда применять.** LeetCode 26 Remove Duplicates from Sorted Array, удаление повторов в логах после сортировки по timestamp, schema-evolution миграция (удалить дубликаты по PK после `ORDER BY`), in-place dedup в memory-mapped файлах.
>
>     **Подводные камни.** Для пустого массива нужен early return `0` (иначе `slow=0` соответствует длине 1, что неверно). Если переменные перепутаны (`++slow` vs `slow++`), получается off-by-one. «Мусор» в хвосте остаётся валидным `int`, поэтому если читать `arr.length`, увидишь дубликаты — всегда работай с возвращённой длиной.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q5]] merge двух отсортированных; [[arrays-strings-interview#Q18]] Dutch National Flag (тоже two/three pointers); [[arrays-strings-interview#Q19]] Move Zeroes.
>
> - [ ] C. Сделать `Arrays.stream(arr).distinct().toArray()` — функциональный и краткий способ.
>
>     **Что на самом деле.** `distinct()` использует внутренний `LinkedHashSet`, что даёт `O(n)` память. Плюс `Arrays.stream(int[]).distinct()` возвращает `IntStream`, и `.toArray()` создаёт новый массив — не in-place. Для миллиона элементов — ~4 МБ overhead.
>
>     **Откуда путаница.** Stream API делает код красивым, но многие забывают, что `distinct` использует промежуточное хранилище. На отсортированном массиве это избыточно — соседняя дедупликация выгоднее.
>
>     **Если бы это было правдой.** JDK содержал бы оптимизацию `IntStream.distinct()` под отсортированный input через `sorted()` flag — но этой fast-path нет, реализация одинакова для любого порядка.
>
>     **Как было бы правильно.** Признать, что Stream-вариант создаёт новый массив (`O(n)` память) и подходит для удобства, но не для требования `O(1)` in-place.
>
> - [ ] D. Пройти массив, при встрече дубликата сдвигать оставшиеся элементы влево через `System.arraycopy` — это in-place.
>
>     **Что на самом деле.** Это `O(n²)`: каждый дубликат вызывает сдвиг хвоста длиной до `n`. На массиве с k дубликатами получится `O(n·k)`. `System.arraycopy` быстро в native, но количество операций всё равно квадратичное.
>
>     **Откуда путаница.** Звучит как in-place решение, и `arraycopy` действительно работает в памяти без аллокаций — но сложность по времени деградирует. Похоже на `ArrayList.remove(i)` в цикле.
>
>     **Если бы это было правдой.** Two-pointers решение не было бы каноничным, и интервьюеры считали бы любое in-place решение эквивалентным по сложности — но это не так.
>
>     **Как было бы правильно.** Сказать, что для in-place нужен two-pointers без сдвигов: запись напрямую через индекс `slow`, не двигая хвост.

## Q5. (!) Как реализовать слияние двух отсортированных массивов?

```java
// Out-of-place — O(n+m) время и память
int[] mergeSorted(int[] a, int[] b) {
    int[] result = new int[a.length + b.length];
    int i = 0, j = 0, k = 0;

    while (i < a.length && j < b.length) {
        if (a[i] <= b[j]) result[k++] = a[i++];
        else               result[k++] = b[j++];
    }
    while (i < a.length) result[k++] = a[i++];
    while (j < b.length) result[k++] = b[j++];

    return result;
}

// In-place в первый массив, если в нём есть место в конце (LeetCode 88)
// Идём с конца — чтобы не затирать ещё не обработанные элементы
void mergeInPlace(int[] a, int m, int[] b, int n) {
    int i = m - 1, j = n - 1, k = m + n - 1;
    while (i >= 0 && j >= 0) {
        a[k--] = (a[i] > b[j]) ? a[i--] : b[j--];
    }
    while (j >= 0) a[k--] = b[j--];
}
```

Этот же паттерн — основа `Merge Sort`. Для слияния `k` массивов используют `PriorityQueue` — `O(N log k)`, где `N` — суммарное число элементов.


> [!mcq] Почему при in-place merge двух отсортированных массивов (LeetCode 88) обход ведут с конца, а не с начала?
>
> - [ ] A. С конца итерация всегда быстрее благодаря CPU prefetcher, который оптимизирован под обратный обход.
>
>     **Что на самом деле.** Современные CPU-префетчеры одинаково хорошо работают и forward, и backward, и причина обратного обхода — НЕ производительность, а корректность: запись с конца не затирает ещё непрочитанные элементы исходного `nums1`.
>
>     **Откуда путаница.** Миф «backward iteration быстрее» возник в эпоху, когда некоторые компиляторы лучше оптимизировали циклы `for (i = n; i > 0; i--)`. Современные JIT и AOT нивелируют разницу.
>
>     **Если бы это было правдой.** JMH-бенчмарки `forward vs backward` показывали бы стабильный win backward на современных JVM (Java 17+), но они показывают разницу в пределах шума измерений.
>
>     **Как было бы правильно.** Сказать, что обратный обход выбран ради корректности in-place: запись в хвост не затирает голову `nums1`, ещё не обработанную.
>
> - [x] B. Запись в `nums1[k]` с конца не затирает пока не прочитанные элементы `nums1`, так как они лежат в первых `m` ячейках, а свободное место — в хвосте.
>
>     **Развёрнутое объяснение.** В LeetCode 88 `nums1` имеет длину `m+n`: первые `m` ячеек — данные, последние `n` — свободные слоты. Если идти с начала, запись `nums1[0] = max(nums1[0], nums2[0])` могла бы затереть `nums1[0]`, который ещё нужен. Идя с конца, кладём максимум в `nums1[m+n-1]`, потом `m+n-2` и т.д. — хвост заполняется в обратном порядке убывания, голова `nums1` остаётся нетронутой до момента её прочтения.
>
>     **Пример.** `nums1=[1,3,5,0,0,0]` (m=3), `nums2=[2,4,6]` (n=3). i=2, j=2, k=5: `6>5`, `nums1[5]=6`, j=1. k=4: `5>4`, `nums1[4]=5`, i=1. k=3: `4>3`, `nums1[3]=4`, j=0. k=2: `3>2`, `nums1[2]=3`, i=0. k=1: `2>1`, `nums1[1]=2`, j=-1. k=0: остаток `nums1[0]=1` уже на месте. Итого `[1,2,3,4,5,6]`, ни одно `nums1[i]` не затёрто до прочтения.
>
>     **Когда применять.** LeetCode 88 Merge Sorted Array, фаза merge в merge-sort внешней сортировки (когда финальный буфер физически тот же), in-place компактация двух segment files в LSM-Tree, объединение sparse-индексов в Lucene.
>
>     **Подводные камни.** После основного цикла нужен второй цикл `while (j >= 0)` для оставшихся `nums2` (если `nums1` исчерпался первым). Обратное — для `nums1` остатки не нужны: они уже на нужных позициях. Если перепутать `>` и `>=` в сравнении — теряется стабильность сортировки.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q4]] remove duplicates two-pointers; [[arrays-strings-interview#Q19]] move zeroes; [[arrays-strings-interview#Q18]] Dutch National Flag.
>
> - [ ] C. Это требование `nums1.length == m` — массив фиксированной длины не позволяет идти с начала.
>
>     **Что на самом деле.** Наоборот: в LeetCode 88 `nums1.length == m + n` (есть свободное место в хвосте). Если бы массив был длины `m`, in-place merge был бы невозможен без сдвигов — пришлось бы использовать out-of-place решение.
>
>     **Откуда путаница.** Студенты путают `m` (значимая длина) и `nums1.length` (физическая ёмкость). В Java они различимы; в задаче чётко прописано наличие padding для значений из `nums2`.
>
>     **Если бы это было правдой.** Условие задачи звучало бы как «дан `int[m]`», но в LeetCode 88 явно указано «`nums1` has length `m + n`, with last n cells being 0».
>
>     **Как было бы правильно.** Признать, что массив именно `m+n` длины, и обратный обход использует свободный хвост — без этого in-place не получился бы.
>
> - [ ] D. Обратный обход нужен потому, что отсортированные массивы хранятся в обратном порядке внутренне, и forward работает только после `reverse`.
>
>     **Что на самом деле.** Массивы хранятся в естественном порядке (`arr[0]` — первый элемент). Никакого «внутреннего обратного порядка» нет. Forward merge работает корректно — но требует дополнительного буфера `O(n+m)`.
>
>     **Откуда путаница.** Возможно перепутали с LIFO-стеками или с RTL-кодировкой строк (`right-to-left` в некоторых языках интерфейса). К сортированным массивам это не относится.
>
>     **Если бы это было правдой.** `arr[0]` возвращал бы максимум вместо минимума в отсортированном по возрастанию массиве, и сортировка по возрастанию ломала бы Comparator-контракт.
>
>     **Как было бы правильно.** Сказать, что forward merge тоже корректен, но требует `O(n+m)` доп. памяти; backward работает in-place благодаря свободному хвосту в `nums1`.

## Q6. (!) Как найти максимальную сумму подмассива (алгоритм Кадана)?

**Kadane's algorithm** — один проход, `O(n)` по времени, `O(1)` по памяти. Идея: на каждом шаге решаем «продолжать текущий подмассив или начать новый».

```java
int maxSubarraySum(int[] arr) {
    int currentSum = arr[0];
    int maxSum = arr[0];

    for (int i = 1; i < arr.length; i++) {
        currentSum = Math.max(arr[i], currentSum + arr[i]);
        maxSum = Math.max(maxSum, currentSum);
    }
    return maxSum;
}

// Расширенная версия: возвращает индексы подмассива
int[] maxSubarrayWithIndices(int[] arr) {
    int currentSum = arr[0], maxSum = arr[0];
    int start = 0, end = 0, tempStart = 0;

    for (int i = 1; i < arr.length; i++) {
        if (arr[i] > currentSum + arr[i]) {
            currentSum = arr[i];
            tempStart = i;
        } else {
            currentSum += arr[i];
        }
        if (currentSum > maxSum) {
            maxSum = currentSum;
            start = tempStart;
            end = i;
        }
    }
    return new int[]{maxSum, start, end};
}
```

Пример: для `[-2, 1, -3, 4, -1, 2, 1, -5, 4]` ответ `6` (подмассив `[4, -1, 2, 1]`).

**Если все числа отрицательные** — возвращается максимальный элемент. Если разрешён пустой подмассив (сумма `0`), нужна корректировка: `currentSum = Math.max(0, ...)`.


> [!mcq] В чём ключевая идея алгоритма Кадана для максимальной суммы подмассива?
>
> - [x] A. На каждом шаге решаем «продолжать текущий подмассив или начать новый с `arr[i]`»: `currentSum = max(arr[i], currentSum + arr[i])`.
>
>     **Развёрнутое объяснение.** Это классический DP с состоянием размера `O(1)`: `currentSum` = максимальная сумма подмассива, заканчивающегося на `arr[i]`. Решение «продолжить или начать заново» сводится к сравнению `arr[i]` и `currentSum + arr[i]`. Если `currentSum < 0`, его прибавление только уменьшит результат — значит, начать с нуля и взять `arr[i]`. Глобальный максимум обновляем отдельной переменной `maxSum`. Один проход, `O(n)` время, `O(1)` память.
>
>     **Пример.** `[-2, 1, -3, 4, -1, 2, 1, -5, 4]`: на индексе 3 `currentSum=4` (начинаем заново после `-3`), далее `4 + (-1) = 3`, `3 + 2 = 5`, `5 + 1 = 6` — глобальный максимум, дальше `6 - 5 = 1` (продолжаем, так как ещё положительно), потом `1 + 4 = 5`. Ответ `6` для подмассива `[4,-1,2,1]`.
>
>     **Когда применять.** Stock prediction (max profit за один buy/sell), maximum subarray в data-stream аналитике, максимальная подпоследовательность в DSP-сигналах, скользящие финансовые метрики (drawdown, recovery), max-sum rectangle в 2D расширении алгоритма.
>
>     **Подводные камни.** Если все числа отрицательные — алгоритм вернёт максимальный элемент (а не 0). Если задача допускает пустой подмассив (сумма 0), нужна корректировка `currentSum = max(0, currentSum + arr[i])`. Для возврата индексов нужны дополнительные переменные `start, end, tempStart`. Overflow: на массиве из больших `int` суммы могут превысить `Integer.MAX_VALUE` — используй `long`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q7]] Two Sum (другой паттерн scan); [[arrays-strings-interview#Q12]] prefix sums; [[arrays-strings-interview#Q13]] подмассивы с заданной суммой.
>
> - [ ] B. Перебрать все возможные пары `(i, j)` и для каждой посчитать сумму `arr[i..j]` — это `O(n²)`, но оптимально.
>
>     **Что на самом деле.** `O(n²)` это лучшее **brute force**, но не оптимум: Kadane даёт `O(n)`, что строго лучше. На массиве в миллион элементов разница между `10¹²` и `10⁶` операций — это разница в часы vs миллисекунды.
>
>     **Откуда путаница.** Это первое решение, которое приходит в голову, и оно правильное по результату. Многие не знают о существовании одно-проходного алгоритма Кадана.
>
>     **Если бы это было правдой.** Kadane не упоминался бы в учебниках Cormen / Sedgewick как фундаментальный пример DP, и LeetCode 53 не относилась бы к Easy с критерием `O(n)`.
>
>     **Как было бы правильно.** Сказать, что `O(n²)` — наивный baseline, но за `O(n)` решает Kadane через локальный DP.
>
> - [ ] C. Сортировать массив и взять сумму всех положительных элементов — отрицательные нам не нужны.
>
>     **Что на самом деле.** Сортировка ломает порядок, а задача требует **непрерывный** подмассив. Сумма всех положительных корректна для задачи «max сумма подпоследовательности», но не подмассива. Также `O(n log n)` хуже `O(n)`.
>
>     **Откуда путаница.** Слова «подмассив» и «подпоследовательность» в русском похожи, а в LeetCode постановках разница принципиальна: subarray = contiguous, subsequence = sparse.
>
>     **Если бы это было правдой.** Тест-кейс `[-2, 1, -3, 4, -1, 2, 1, -5, 4]` дал бы ответ `1+4+2+1+4 = 12`, а не `6`. Реальный максимум подмассива — `6`, и LeetCode 53 ловит подобные ошибки.
>
>     **Как было бы правильно.** Не сортировать, не выбирать «все положительные»: алгоритм Кадана уважает порядок и выбирает оптимальный непрерывный сегмент.
>
> - [ ] D. Использовать divide-and-conquer: делим массив пополам, рекурсивно ищем максимум в обеих половинах и через границу. Сложность `O(n)`.
>
>     **Что на самом деле.** Divide-and-conquer для этой задачи существует (классическое упражнение из Cormen), но даёт `O(n log n)` — рекурсия глубиной `log n`, на каждом уровне `O(n)` для cross-border merge. Это хуже `O(n)` Kadane.
>
>     **Откуда путаница.** Maximum subarray часто упоминается как первый пример divide-and-conquer в учебниках, что создаёт иллюзию, будто это и есть оптимальный алгоритм.
>
>     **Если бы это было правдой.** Cormen / Sedgewick не упоминали бы алгоритм Кадана отдельно как улучшение до `O(n)` через DP.
>
>     **Как было бы правильно.** Признать, что divide-and-conquer даёт `O(n log n)`, а Kadane улучшает до `O(n)` через одно-проходное DP.

## Q7. (!) Two Sum — поиск пары с заданной суммой?

**Вариант 1 — отсортированный массив (two pointers):** `O(n)` время, `O(1)` память.

```java
int[] twoSumSorted(int[] arr, int target) {
    int left = 0, right = arr.length - 1;
    while (left < right) {
        int sum = arr[left] + arr[right];
        if (sum == target) return new int[]{left, right};
        if (sum < target) left++;
        else              right--;
    }
    return new int[]{-1, -1};
}
```

**Вариант 2 — неотсортированный массив (HashMap):** `O(n)` время и память.

```java
int[] twoSum(int[] arr, int target) {
    Map<Integer, Integer> seen = new HashMap<>();
    for (int i = 0; i < arr.length; i++) {
        int complement = target - arr[i];
        if (seen.containsKey(complement)) {
            return new int[]{seen.get(complement), i};
        }
        seen.put(arr[i], i);
    }
    return new int[]{-1, -1};
}
```

Если массив можно сортировать — first sort + two pointers (`O(n log n)`, `O(1)` доп. памяти, но теряются исходные индексы).


> [!mcq] Какое решение Two Sum даёт `O(n)` время на неотсортированном массиве?
>
> - [ ] A. Два вложенных цикла: для каждого `i` пробовать все `j > i` — `O(n²)`, зато `O(1)` память.
>
>     **Что на самом деле.** `O(n²)` — это brute force, не оптимум. Для миллиона элементов это `10¹²` операций. LeetCode 1 (Easy) явно требует лучше — иначе на массивах длины 10⁵ упрётся в time limit.
>
>     **Откуда путаница.** Это первое решение, которое приходит в голову, и оно действительно `O(1)` по памяти. На маленьких массивах работает, и в junior-собеседованиях иногда принимается как стартовая точка с follow-up «а как ускорить».
>
>     **Если бы это было правдой.** LeetCode 1 не была бы Easy, а закрывалась бы как «достаточно brute force». Но критерий именно `O(n)` через HashMap.
>
>     **Как было бы правильно.** Признать, что brute force `O(n²)` корректен, но для `O(n)` нужен HashMap с complement-lookup.
>
> - [x] B. HashMap `value → index`: для каждого `arr[i]` проверяем `complement = target - arr[i]` в карте; если есть — нашли пару.
>
>     **Развёрнутое объяснение.** Идём по массиву один раз. Для текущего элемента вычисляем `complement = target - arr[i]` и смотрим в HashMap: видели ли мы его раньше? Если да — пара найдена, возвращаем `(map.get(complement), i)`. Если нет — добавляем `arr[i] → i` в карту и идём дальше. Каждая операция `get`/`put` — амортизированный `O(1)`, итого `O(n)` время и `O(n)` память.
>
>     **Пример.** `arr=[2,7,11,15]`, `target=9`. i=0: `complement=7`, карта пуста, пишем `{2→0}`. i=1: `arr[1]=7`, `complement=2`, в карте есть! Возвращаем `(0,1)`. Один проход, две операции с HashMap, готово.
>
>     **Когда применять.** LeetCode 1 Two Sum, поиск пар в финансовых данных (matching buy/sell orders), детекция reciprocal events в Kafka stream, deduplication по сумме хешей, lookup pairs в access-логах для security-аналитики.
>
>     **Подводные камни.** Если один индекс может использоваться дважды (`arr[i]+arr[i]=target`) — это запрещено в LeetCode 1, и решение естественно ловит: complement ищется до записи текущего `i`. Дубликаты значений: `arr=[3,3], target=6` — корректно вернёт `(0,1)`, потому что второе `3` найдёт первое в карте. Overflow: `target - arr[i]` для `Integer.MIN_VALUE` лучше считать как `long`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q8]] Three Sum; [[arrays-strings-interview#Q13]] subarrays с заданной суммой (тот же паттерн с prefix-sum); [[arrays-strings-interview#Q23]] анаграммы (HashMap для подсчёта).
>
> - [ ] C. Отсортировать массив и применить two-pointers: `left=0`, `right=n-1`, двигать к центру. Это `O(n)`.
>
>     **Что на самом деле.** Сам two-pointers — `O(n)`, но сортировка — `O(n log n)`, итого общая сложность `O(n log n)`. Кроме того, сортировка теряет исходные индексы, а LeetCode 1 требует именно их вернуть.
>
>     **Откуда путаница.** Two-pointers на отсортированном массиве — частый приём (Two Sum II, LeetCode 167), и его путают с задачей на неотсортированном.
>
>     **Если бы это было правдой.** Sort + two-pointers давал бы `O(n)` без оговорок, и интервьюер бы не различал Two Sum I (HashMap) и Two Sum II (two-pointers на sorted).
>
>     **Как было бы правильно.** Сказать, что для **отсортированного** массива two-pointers даёт `O(n)` + `O(1)` память без учёта сортировки, а для неотсортированного с возвратом индексов лучше HashMap.
>
> - [ ] D. Через `Arrays.binarySearch`: для каждого `arr[i]` искать `target - arr[i]` бинарным поиском. Сложность `O(n log n)`.
>
>     **Что на самом деле.** `Arrays.binarySearch` требует отсортированный массив. На неотсортированном вернёт undefined-результат. Если сначала сортировать — теряются индексы, как в варианте C, и общее `O(n log n)` хуже `O(n)`.
>
>     **Откуда путаница.** Binary search — стандартный приём ускорения lookup до `O(log n)`, и его пытаются применить везде, где видят «найти элемент».
>
>     **Если бы это было правдой.** Не существовало бы оптимизации до `O(n)` через HashMap, и LeetCode 1 имел бы threshold по времени `O(n log n)` — но реально он требует строгий `O(n)`.
>
>     **Как было бы правильно.** Сказать, что binary search даёт `O(log n)` lookup только на отсортированном; для `O(n)` на любом массиве нужен HashMap с `O(1)` lookup.

## Q8. Three Sum — все тройки с нулевой суммой?

Для каждого `i` зафиксировать `arr[i]` и решать `Two Sum` на оставшейся части. После сортировки — `O(n²)`.

```java
List<List<Integer>> threeSum(int[] arr) {
    Arrays.sort(arr); // O(n log n)
    List<List<Integer>> result = new ArrayList<>();

    for (int i = 0; i < arr.length - 2; i++) {
        if (i > 0 && arr[i] == arr[i - 1]) continue; // пропускаем дубликаты i
        int left = i + 1, right = arr.length - 1;

        while (left < right) {
            int sum = arr[i] + arr[left] + arr[right];
            if (sum == 0) {
                result.add(List.of(arr[i], arr[left], arr[right]));
                while (left < right && arr[left] == arr[left + 1]) left++;
                while (left < right && arr[right] == arr[right - 1]) right--;
                left++; right--;
            } else if (sum < 0) {
                left++;
            } else {
                right--;
            }
        }
    }
    return result;
}
```

Сложность `O(n²)`. Скип дубликатов — критичная деталь, без него получаются повторяющиеся тройки.


> [!mcq] Какая сложность у оптимального решения Three Sum (все уникальные тройки с нулевой суммой)?
>
> - [ ] A. `O(n³)` — три вложенных цикла, по-другому никак, потому что нужно проверить все тройки.
>
>     **Что на самом деле.** `O(n³)` — наивный brute force. После сортировки `O(n log n)` и применения two-pointers на оставшихся двух индексах для зафиксированного `i` сложность снижается до `O(n²)`. Это значительное улучшение: на `n=3000` разница `9·10⁹` vs `9·10⁶` — секунды vs миллисекунды.
>
>     **Откуда путаница.** «Раз нужно проверить тройки — значит `n³`» — интуитивно правильно, но игнорирует комбинаторный трюк: фиксируем один индекс и сводим к Two Sum.
>
>     **Если бы это было правдой.** LeetCode 15 имел бы time limit, разрешающий `O(n³)`, но реально `n` до 3000 требует `O(n²)`.
>
>     **Как было бы правильно.** Признать, что оптимум — `O(n²)` через sort + two-pointers, а `n³` — наивный baseline.
>
> - [x] B. `O(n²)` — сортировка `O(n log n)` + внешний цикл по `i` и two-pointers на оставшейся части.
>
>     **Развёрнутое объяснение.** Сортируем массив. Для каждого `i` фиксируем `arr[i]` и ищем пару `(left, right)` с суммой `-arr[i]` через two-pointers на `arr[i+1..n-1]`. Внутренний поиск — `O(n)`, внешний цикл — `O(n)`, итого `O(n²)`. Сортировка `O(n log n)` поглощается. Важная деталь: при нахождении тройки и при изменении `i` пропускаем дубликаты, чтобы тройки были уникальны.
>
>     **Пример.** `arr=[-1,0,1,2,-1,-4]` → sorted `[-4,-1,-1,0,1,2]`. i=0 (`-4`): target `4`, two-pointers не находят. i=1 (`-1`): target `1`, `left=2, right=5`. `arr[2]+arr[5] = -1+2 = 1`, нашли тройку `(-1,-1,2)`. Дальше скипаем дубликат `-1`. i=2 пропускаем (дубликат `-1`). i=3 (`0`): `left=4, right=5`. `1+2=3`, не подходит, right--. left=4, right=4, стоп. Итог: `[[-1,-1,2], [-1,0,1]]`.
>
>     **Когда применять.** LeetCode 15 Three Sum, поиск тройки точек на коллинеарной прямой (geometry), детекция triangle inequalities в network latency, скоринг ML-фич через сочетания трёх признаков.
>
>     **Подводные камни.** Скип дубликатов **обязателен** в трёх местах: для `i` (внешний), для `left` после нахождения тройки, для `right`. Без скипов получаются повторяющиеся тройки. Сортировка изменяет исходный массив — если он нужен — клонируйте через `arr.clone()`. Overflow: `arr[i] + arr[left] + arr[right]` для крайних int — лучше `long`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q7]] Two Sum; [[arrays-strings-interview#Q18]] Dutch National Flag; [[arrays-strings-interview#Q20]] next permutation.
>
> - [ ] C. `O(n log n)` через сортировку и бинарный поиск пары — лучшее достижимое.
>
>     **Что на самом деле.** Бинарный поиск пары даёт `O(log n)` на одну операцию, но для каждой из `O(n²)` пар (i, j) нужно искать третий элемент — итого `O(n² log n)`. Хуже, чем `O(n²)` через two-pointers. Чистого `O(n log n)` для Three Sum не существует — есть доказанный нижний предел `Ω(n²)`.
>
>     **Откуда путаница.** Кажется, что любую задачу можно ускорить через бинарный поиск, и `O(n log n)` звучит «как sort, значит хорошо».
>
>     **Если бы это было правдой.** Существовал бы алгоритм Three Sum за `O(n log n)`, и это был бы серьёзный результат в complexity theory — но известная нижняя граница `Ω(n²)`.
>
>     **Как было бы правильно.** Признать, что best known для Three Sum — `O(n²)`, и улучшить общую асимптотику без quantum-computing нельзя.
>
> - [ ] D. `O(n)` через хеш-таблицу всех сумм пар, потом проверка третьего элемента.
>
>     **Что на самом деле.** Хеш-таблица всех пар содержит `O(n²)` записей и строится за `O(n²)`. Lookup третьего — `O(n)`, общая сложность всё равно `O(n²)`, а память деградирует до `O(n²)`. Это не улучшение, а ухудшение по памяти.
>
>     **Откуда путаница.** HashMap-приём из Two Sum (`O(n)` lookup) механически переносится на Three Sum, без учёта что для одного индекса остальные пары — это `O(n²)` пространство.
>
>     **Если бы это было правдой.** Three Sum имел бы решение `O(n)`, и это нарушало бы доказанный нижний предел `Ω(n²)` для problems с трёхэлементной комбинацией.
>
>     **Как было бы правильно.** Сказать, что HashMap-подход работает на Two Sum (`O(n)`), но для Three Sum переход через все пары даёт `O(n²)` и не лучше two-pointers.

## Q9. Поиск элемента, встречающегося один раз?

В массиве каждый элемент встречается **дважды**, кроме одного. Найти его за `O(n)` без доп. памяти.

```java
// Через XOR: a ^ a = 0, a ^ 0 = a
int singleNumber(int[] arr) {
    int result = 0;
    for (int x : arr) result ^= x;
    return result;
}
```

XOR коммутативен и ассоциативен, парные числа сократятся до `0`, останется только одиночка. Память `O(1)`, время `O(n)`.

Если каждый встречается **трижды**, кроме одного — алгоритм через подсчёт битов (`ones`, `twos`).


> [!mcq] Почему XOR-проход даёт `O(1)` память для поиска одиночки среди парных элементов?
>
> - [ ] A. XOR использует битовые операции, которые JIT компилирует в одну ASM-инструкцию — это быстрее любого цикла.
>
>     **Что на самом деле.** Скорость инструкции не относится к памяти. Алгоритм даёт `O(1)` память благодаря свойствам XOR (коммутативность, ассоциативность, `a^a=0`, `a^0=a`), а не за счёт ASM. JIT действительно генерирует `XOR EAX, EBX` — но это влияет на cycles per op, не на space complexity.
>
>     **Откуда путаница.** Низкоуровневое мышление: «битовая операция = эффективная» механически переносится в анализ сложности по памяти.
>
>     **Если бы это было правдой.** Любая битовая операция автоматически давала бы `O(1)` память — но это не так: `Long.bitCount(arr[i])` в HashMap для подсчёта оставит `O(n)` память.
>
>     **Как было бы правильно.** Сказать, что `O(1)` память достигается за счёт алгебраических свойств XOR, а не за счёт компиляции в одну ASM-инструкцию.
>
> - [x] B. XOR коммутативен и ассоциативен, `a^a=0`, `a^0=a`: парные числа взаимно гасятся независимо от порядка, остаётся только одиночка в одной переменной-аккумуляторе.
>
>     **Развёрнутое объяснение.** Свойства XOR позволяют переупорядочить выражение `a^b^c^d^...` как `(a^a)^(b^b)^...^single = 0^0^...^single = single`. Парные элементы сократятся независимо от порядка ввода. Нужен один `int`-аккумулятор `result`, цикл по массиву с `result ^= arr[i]`. После прохода в `result` останется значение одиночки. Память — одна переменная (`O(1)`), время — `O(n)` один проход.
>
>     **Пример.** `[4,1,2,1,2]` → `0^4=4`, `4^1=5`, `5^2=7`, `7^1=6`, `6^2=4`. Итог `4` — единственный одиночка. Для проверки: `1^1=0` и `2^2=0` сократились, остался `4^0=4`.
>
>     **Когда применять.** LeetCode 136 Single Number, поиск повреждённой записи в дублированном backup, контрольная сумма в network-протоколах (XOR-checksum), детекция одного flipped бита в RAID, hash-based set membership при больших датасетах.
>
>     **Подводные камни.** Работает только если все остальные числа встречаются **ровно дважды**. Для тройных дубликатов нужен другой алгоритм: счётчики `ones` и `twos` по битам (LeetCode 137 Single Number II). Если есть два одиночки — XOR даёт их XOR (тоже LeetCode 260, требует расщепления по битам). Overflow невозможен — XOR работает побитно без переноса.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q11]] missing number через XOR; [[arrays-strings-interview#Q30]] swap через XOR; [[arrays-strings-interview#Q32]] проверка степени двойки.
>
> - [ ] C. Используется HashMap для подсчёта частот, потом фильтрация по `count == 1` — это и есть `O(1)` память.
>
>     **Что на самом деле.** HashMap-подход требует `O(n/2)` память на словарь (≈ половина уникальных ключей), что не `O(1)`, а `O(n)`. XOR-подход именно тем и хорош, что не нуждается в HashMap.
>
>     **Откуда путаница.** HashMap — стандартный приём для «подсчёта вхождений», и его инстинктивно применяют, не учитывая память.
>
>     **Если бы это было правдой.** HashMap не считался бы overhead-структурой, и LeetCode 136 не требовал бы решение с constant extra space.
>
>     **Как было бы правильно.** Признать, что HashMap даёт `O(n)` память, а для `O(1)` нужен XOR или сортировка + два указателя.
>
> - [ ] D. Сортировка массива и проверка соседей за один проход даёт `O(1)` памяти, потому что сортировка in-place.
>
>     **Что на самом деле.** Сортировка `O(n log n)` хуже `O(n)` XOR. In-place sort (Java `Arrays.sort` для примитивов использует Dual-Pivot Quicksort) действительно `O(log n)` память на стек рекурсии — формально не `O(1)`. Плюс модификация исходного массива может быть нежелательна.
>
>     **Откуда путаница.** Сортировка часто упоминается как универсальный pre-step, и `O(log n)` на стек считают «как бы константой».
>
>     **Если бы это было правдой.** XOR-решение не имело бы преимущества, и LeetCode 136 не отмечал бы его как идиоматичное.
>
>     **Как было бы правильно.** Сказать, что sort + scan даёт `O(n log n)` время и `O(log n)` память на стек — это хуже XOR по обоим параметрам.

## Q10. (!) Поиск элемента большинства (>n/2)?

**Алгоритм Бойера-Мура (Boyer-Moore Voting):** `O(n)` время, `O(1)` память.

```java
int majorityElement(int[] arr) {
    int candidate = 0, count = 0;
    for (int x : arr) {
        if (count == 0) candidate = x;
        count += (x == candidate) ? 1 : -1;
    }
    return candidate; // гарантия — если majority существует
}
```

**Идея:** парные «голоса» за разных кандидатов гасят друг друга. Если majority element существует (>n/2) — он останется.

Для подтверждения, что элемент действительно majority — сделать второй проход и посчитать.


> [!mcq] Как работает алгоритм Бойера-Мура для поиска majority element (`>n/2`)?
>
> - [x] A. Парные «голоса» за разных кандидатов гасят друг друга: если `count==0` — новый candidate, иначе `count += (x==candidate ? 1 : -1)`.
>
>     **Развёрнутое объяснение.** Идея: представь, что элементы — голосующие, и одинаковые «поддерживают» друг друга, а разные «дерутся 1-к-1». Если есть majority (> n/2), его голосов больше, чем всех остальных вместе — в финале он останется кандидатом. Алгоритм: ходим по массиву, при `count == 0` назначаем `candidate = x`, инкрементируем `count` если `x == candidate`, иначе декрементируем. Один проход, `O(1)` память — одна переменная-кандидат и счётчик.
>
>     **Пример.** `[2,2,1,1,1,2,2]`: count=0→candidate=2, count=1. `2==2`: count=2. `1≠2`: count=1. `1≠2`: count=0. `1≠2`: candidate=1, count=1. `2≠1`: count=0. `2≠1`: candidate=2, count=1. Финал — `candidate=2` (встречается 4 раза > 3.5).
>
>     **Когда применять.** LeetCode 169 Majority Element, поиск преобладающего класса в стримах ML-фич, детекция доминирующей версии в Raft/Paxos consensus при оценке majority quorum, аналитика преобладающего IP в DDoS-логах, выбор default-значения в A/B-тестах.
>
>     **Подводные камни.** Алгоритм гарантирует кандидата **только если majority существует**. Если majority нет — возвращённый элемент произвольный, нужен второй проход для верификации `count > n/2`. Для поиска элементов с частотой `> n/k` есть расширение — Бойер-Мур-Мур с `k-1` кандидатами. Подсчёт частоты через HashMap даёт `O(n)` память — хуже по space.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q9]] single number через XOR; [[arrays-strings-interview#Q13]] subarray sum equals K; [[arrays-strings-interview#Q11]] missing number.
>
> - [ ] B. Сортируем массив и берём элемент в середине: `arr[n/2]` — это majority по определению, если он существует.
>
>     **Что на самом деле.** Это работает, но даёт `O(n log n)` время, что хуже `O(n)` Бойера-Мура. Идея корректна: если элемент встречается > n/2 раз, после сортировки он обязательно будет в середине. Но это медленнее оптимума.
>
>     **Откуда путаница.** Sort + median — классический приём в статистике, и для majority он действительно работает. Просто не оптимален.
>
>     **Если бы это было правдой.** Бойер-Мура не считался бы каноничным `O(n)` решением, и LeetCode 169 не выделял бы его в follow-up «Could you solve in O(1) space?».
>
>     **Как было бы правильно.** Признать, что sort + arr[n/2] корректен, но `O(n log n)`, а Бойер-Мура даёт `O(n)` за один проход.
>
> - [ ] C. HashMap счётчиков: для каждого элемента инкрементировать частоту; majority — тот, у кого `count > n/2`.
>
>     **Что на самом деле.** Работает, `O(n)` время, но `O(n)` память на HashMap. Уступает Бойеру-Муру именно по памяти: тот делает `O(1)`.
>
>     **Откуда путаница.** HashMap — универсальный приём для частотного анализа, и его инстинктивно выбирают.
>
>     **Если бы это было правдой.** Не было бы causes for separate algorithm Бойера-Мура, и его не упоминали бы в учебниках как пример streaming-алгоритма.
>
>     **Как было бы правильно.** Признать `O(n)`/`O(n)` для HashMap и улучшить до `O(n)`/`O(1)` через voting Бойера-Мура.
>
> - [ ] D. Случайный sampling: 10 раз выбираем случайный элемент и проверяем — majority с вероятностью > 99.9%.
>
>     **Что на самом деле.** Это рандомизированный probabilistic подход, который действительно работает с высокой вероятностью для majority (по определению > 50%, ловится за ~10 samples). Но это не **детерминированный** алгоритм; в production-критичных системах нужен гарантированный ответ.
>
>     **Откуда путаница.** Randomized algorithms — модная техника (Monte Carlo, QuickSelect), и для majority она имеет правильную статистическую базу.
>
>     **Если бы это было правдой.** LeetCode 169 принимал бы probabilistic решение с failure probability — но тестовый фреймворк требует строгого ответа.
>
>     **Как было бы правильно.** Сказать, что probabilistic sampling работает для majority с высокой вероятностью, но Бойер-Мура даёт детерминированный `O(n)`/`O(1)`.

## Q11. Найти недостающее число в массиве 0..n?

В массиве из `n` чисел все значения от `0` до `n`, кроме одного. Найти пропущенное.

```java
// Метод 1: сумма арифметической прогрессии
int missingNumberSum(int[] arr) {
    int n = arr.length;
    int expected = n * (n + 1) / 2;
    int actual = 0;
    for (int x : arr) actual += x;
    return expected - actual;
}

// Метод 2: XOR — без переполнения
int missingNumberXor(int[] arr) {
    int xor = arr.length; // включаем n
    for (int i = 0; i < arr.length; i++) {
        xor ^= i ^ arr[i];
    }
    return xor;
}
```

Оба `O(n)` время и `O(1)` память. XOR безопаснее для больших массивов (нет риска переполнения).


> [!mcq] Чем XOR-метод поиска пропущенного числа в `0..n` безопаснее метода с суммой арифметической прогрессии?
>
> - [ ] A. XOR быстрее: одна битовая операция вместо умножения `n*(n+1)/2`.
>
>     **Что на самом деле.** Оба метода `O(n)` по времени; разница в одной арифметической операции для подсчёта ожидаемого значения. Скорость не аргумент: на современном CPU и умножение, и XOR — несколько наносекунд. Реальное преимущество XOR — отсутствие риска переполнения.
>
>     **Откуда путаница.** «Битовые операции = быстро» — мем из low-level программирования, к этому case не применим.
>
>     **Если бы это было правдой.** Разница в производительности была бы заметна на JMH-бенчмарках, но `n*(n+1)/2` и XOR-цикл показывают идентичные результаты.
>
>     **Как было бы правильно.** Сказать, что XOR безопаснее не по скорости, а по отсутствию overflow при больших `n`.
>
> - [x] B. XOR не переполняется: для `n ≈ 2·10⁹` сумма `n*(n+1)/2 > Integer.MAX_VALUE`, а XOR работает побитно без переноса.
>
>     **Развёрнутое объяснение.** `int` в Java 32-битный, `Integer.MAX_VALUE ≈ 2.1·10⁹`. Для `n = 65536` уже `n*(n+1)/2 = 2.15·10⁹` — переполнение. Можно перейти на `long`, но это требует осознанного выбора. XOR работает поэлементно: `result ^= i ^ arr[i]`, переноса нет, размер аккумулятора всегда 32 бита и хранит реальное значение пропущенного числа. Алгебраически: `(0^1^...^n) ^ (arr[0]^...^arr[n-1]) = пропущенное`, потому что все остальные взаимно сократятся.
>
>     **Пример.** `[3,0,1]`, `n=3`. XOR: `3 ^ (0^3) ^ (1^0) ^ (2^1) = 3 ^ 3 ^ 1 ^ 3 = 2`. Пропущено `2`. Если использовать sum: `expected = 3*4/2 = 6`, `actual = 3+0+1 = 4`, `6-4 = 2`. Оба ответа верны, но XOR не зависит от размера `n`.
>
>     **Когда применять.** LeetCode 268 Missing Number, поиск пропущенной записи в нумерованной серии (transaction IDs, sequence numbers), детекция gap в кафкаобразных offset-последовательностях, RAID-like recovery при выпавшем диске, debug log gap analysis.
>
>     **Подводные камни.** XOR работает только когда массив содержит каждый элемент `0..n` ровно один раз с одним пропуском. Если есть дубликаты или пропусков несколько — нужен другой алгоритм (HashSet или sort). Если массив **отсортирован** — можно бинарным поиском за `O(log n)`. Алгоритм с XOR коммутативен — порядок чтения значения не имеет.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q9]] single number через XOR; [[arrays-strings-interview#Q30]] swap через XOR; [[arrays-strings-interview#Q32]] степень двойки через bitwise.
>
> - [ ] C. XOR работает и для отсортированных, и для неотсортированных массивов, а sum — только для отсортированных.
>
>     **Что на самом деле.** Оба метода НЕ требуют сортировки: и сумма (коммутативна), и XOR (коммутативен и ассоциативен) дают одинаковый результат при любом порядке элементов.
>
>     **Откуда путаница.** Некоторые алгоритмы (бинпоиск, two-pointers) требуют sorted input, и это свойство ошибочно переносится на missing number.
>
>     **Если бы это было правдой.** Метод с суммой работал бы только на части тест-кейсов LeetCode 268, но он проходит все.
>
>     **Как было бы правильно.** Признать, что оба метода работают на любом порядке; преимущество XOR — отсутствие overflow.
>
> - [ ] D. XOR использует меньше памяти — sum требует двух переменных (`expected`, `actual`), а XOR — одной.
>
>     **Что на самом деле.** Оба используют `O(1)` память. XOR может обойтись одной переменной (`xor ^= i ^ arr[i]`), sum использует две (`expected`, `actual`). Разница в одну `int` переменную — это шум, не критерий.
>
>     **Откуда путаница.** На уровне литературы о space complexity иногда раздувают разницу в константный множитель.
>
>     **Если бы это было правдой.** При больших `n` оптимизация sum до одной переменной не существовала бы (`int total = (n*(n+1))/2 - sum(arr)` тоже работает с одной переменной).
>
>     **Как было бы правильно.** Признать, что обе схемы — `O(1)` память; настоящее различие — overflow safety.

## Q12. (!) Что такое prefix sum?

**Prefix sum** — массив `prefix[i]` = сумма `arr[0..i]`. Позволяет за `O(1)` получить сумму любого подмассива:

```java
int[] buildPrefix(int[] arr) {
    int[] prefix = new int[arr.length + 1];
    for (int i = 0; i < arr.length; i++) {
        prefix[i + 1] = prefix[i] + arr[i];
    }
    return prefix;
}

// Сумма arr[i..j] (включительно) — O(1)
int rangeSum(int[] prefix, int i, int j) {
    return prefix[j + 1] - prefix[i];
}
```

**Применение:** range queries, поиск подмассива с суммой K, сложность `O(1)` на запрос после `O(n)` препроцессинга.


> [!mcq] Что даёт техника prefix sum при range-queries по массиву?
>
> - [x] A. После `O(n)` препроцессинга в массив `prefix[i+1] = prefix[i] + arr[i]`, сумма любого подмассива `arr[i..j]` достаётся за `O(1)` как `prefix[j+1] - prefix[i]`.
>
>     **Развёрнутое объяснение.** Идея: запомнить накопительные суммы префиксов. `prefix[k]` хранит сумму первых `k` элементов. Тогда сумма любого диапазона — разность двух префиксов: `sum(i..j) = prefix[j+1] - prefix[i]`. Препроцессинг — один проход `O(n)`, каждый запрос — две операции, `O(1)`. При `m` запросах общая стоимость `O(n + m)` против `O(n·m)` без оптимизации. Память — дополнительный массив `O(n)`.
>
>     **Пример.** `arr=[2,4,6,8,10]`, `prefix=[0,2,6,12,20,30]`. Сумма `arr[1..3] = 4+6+8 = 18`. Через prefix: `prefix[4] - prefix[1] = 20 - 2 = 18`. Один subtract вместо трёх сложений.
>
>     **Когда применять.** LeetCode 303 Range Sum Query Immutable, оконные индикаторы в финансах (moving sum за период), агрегаты в OLAP-кубах после precompute, prefix-counts для статистики (`P(X<x)`), скользящие алгоритмы в DSP, fast range query в иммутабельных immutable datasets.
>
>     **Подводные камни.** Если массив изменяемый — после каждого изменения нужно пересчитывать prefix (или использовать Fenwick Tree / Segment Tree, `O(log n)` на update и query). Off-by-one: `prefix[0] = 0`, длина `n+1`; для `arr[i..j]` нужен `prefix[j+1] - prefix[i]`. Для 2D расширения — формула включения-исключения: `sum(r1,c1,r2,c2) = P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1]`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q13]] subarray sum equals K через prefix+HashMap; [[arrays-strings-interview#Q14]] equilibrium index; [[arrays-strings-interview#Q6]] Kadane.
>
> - [ ] B. Prefix sum — это сортировка массива, после которой запросы можно делать бинарным поиском.
>
>     **Что на самом деле.** Prefix sum НЕ сортирует исходный массив, наоборот — порядок принципиален: `prefix[k]` — это сумма **первых** `k` элементов в исходном порядке. Сортировка ломает индексы, и range-query «сумма arr[i..j]» теряет смысл.
>
>     **Откуда путаница.** Любая precompute-техника воспринимается как «pre-sort», но prefix sum — другой класс предобработки.
>
>     **Если бы это было правдой.** LeetCode 303 принимала бы input as sorted, что нарушает task description.
>
>     **Как было бы правильно.** Сказать, что prefix sum сохраняет исходный порядок и накапливает суммы; сортировка тут не применяется.
>
> - [ ] C. Prefix sum — это binary indexed tree (Fenwick), требующая `O(n log n)` препроцессинга.
>
>     **Что на самом деле.** Это разные структуры. Prefix sum — массив с `O(n)` препроцессинга и `O(1)` запросом, но не поддерживает обновления (точнее, обновление = пересчёт всего, `O(n)`). Fenwick Tree — отдельная структура с `O(n log n)` препроцессингом, `O(log n)` query и `O(log n)` update.
>
>     **Откуда путаница.** Обе структуры решают range-sum, и Fenwick часто упоминается как «улучшенный prefix sum». Но базовый prefix sum — массив, не дерево.
>
>     **Если бы это было правдой.** Простейший prefix-sum trick не существовал бы как отдельная техника, и его не упоминали бы в учебниках до Fenwick.
>
>     **Как было бы правильно.** Признать, что prefix sum — массив с `O(n)` препроцессинга и `O(1)` query (без update), а для mutable массивов нужен Fenwick.
>
> - [ ] D. Prefix sum даёт `O(log n)` на каждый range-query через бинарный поиск по накопительным суммам.
>
>     **Что на самом деле.** Запрос — это одна разность `prefix[j+1] - prefix[i]`, `O(1)`, не `O(log n)`. Бинарный поиск тут не нужен. `O(log n)` появляется в Fenwick/Segment Tree, но не в plain prefix sum.
>
>     **Откуда путаница.** `O(log n)` — стандартный «улучшенный» time complexity для range-структур, и его инстинктивно приписывают prefix sum.
>
>     **Если бы это было правдой.** Не существовало бы преимущества `O(1)` query, и Fenwick/Segment Tree не отличались бы по асимптотике query.
>
>     **Как было бы правильно.** Сказать, что prefix sum даёт `O(1)` query без обновлений, а `O(log n)` query — это уже Fenwick/Segment Tree.

## Q13. (!) Подсчёт подмассивов с заданной суммой?

**Идея:** prefix sums + HashMap. Если `prefix[j] - prefix[i] = k`, то подмассив `arr[i..j-1]` суммируется в `k`.

```java
int subarraySum(int[] arr, int k) {
    Map<Integer, Integer> prefixCount = new HashMap<>();
    prefixCount.put(0, 1); // пустой префикс

    int sum = 0, count = 0;
    for (int x : arr) {
        sum += x;
        // Сколько раз встречали prefix sum = (sum - k)?
        count += prefixCount.getOrDefault(sum - k, 0);
        prefixCount.merge(sum, 1, Integer::sum);
    }
    return count;
}
```

Сложность `O(n)` время и память. Работает с отрицательными числами и нулями.


> [!mcq] Почему sliding window не работает напрямую для «подмассивов с суммой K» при наличии отрицательных чисел?
>
> - [ ] A. Sliding window работает для отрицательных, просто нужно использовать `long` вместо `int` для overflow safety.
>
>     **Что на самом деле.** Проблема не в overflow, а в монотонности окна. Sliding window предполагает, что при сдвиге `right` сумма растёт, при сдвиге `left` — падает. Отрицательные числа ломают эту монотонность: добавление `right` может **уменьшить** сумму, а удаление `left` — увеличить. Алгоритм перестаёт быть корректным.
>
>     **Откуда путаница.** Overflow — частая проблема в задачах на суммы, и её механически приписывают всем сложностям.
>
>     **Если бы это было правдой.** LeetCode 560 Subarray Sum Equals K имел бы решение через простой two-pointer sliding window, но реально требует HashMap+prefix.
>
>     **Как было бы правильно.** Сказать, что sliding window требует монотонности (только положительные числа), а для смешанных значений нужен prefix-sum + HashMap.
>
> - [x] B. Sliding window предполагает монотонность суммы; отрицательные числа делают сумму немонотонной, поэтому используют prefix sum + HashMap счётчиков префиксов.
>
>     **Развёрнутое объяснение.** Корректный алгоритм: ходим по массиву, поддерживаем running `sum` и HashMap `prefixCount[prefix → количество встреченных]`. Для каждой позиции `j` искомых подмассивов с суммой `k` ровно столько, сколько раз ранее встречался prefix-sum `sum - k` (потому что `prefix[j+1] - prefix[i] = k` ⇔ `prefix[i] = sum - k`). Инициализируем `prefixCount.put(0, 1)` (пустой префикс). Время `O(n)`, память `O(n)`.
>
>     **Пример.** `arr=[1,-1,1,1,1]`, `k=2`. sum=1: prefixCount={0:1}, нет 1-2=-1, добавляем 1. sum=0: ищем 0-2=-2, нет, добавляем 0:1. sum=1: ищем -1, нет, count(1)=2. sum=2: ищем 0, есть! count=1. sum=3: ищем 1, есть `2 раза`! count=3. Итого 3 подмассива с суммой 2: `[1,-1,1,1]`, `[1,1]` (между -1 и третьим 1), `[1,1]` (последние два).
>
>     **Когда применять.** LeetCode 560 Subarray Sum Equals K, поиск periods of zero net flow в банковских транзакциях, детекция balanced subwindows в time-series данных, contiguous segments с заданным aggregate в IoT-телеметрии.
>
>     **Подводные камни.** Обязательно начальная запись `prefixCount.put(0, 1)` — без неё пропадут подмассивы, начинающиеся с индекса 0. Использовать `HashMap.merge(sum, 1, Integer::sum)` для idiomatic increment. Overflow: при больших суммах `long`. Для **положительных** чисел можно использовать sliding window (`O(n)` + `O(1)` память), что эффективнее.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q12]] prefix sum; [[arrays-strings-interview#Q7]] Two Sum (тот же HashMap-трюк); [[arrays-strings-interview#Q25]] longest substring without repeating (sliding window).
>
> - [ ] C. Sliding window работает идеально, проблема только в том, что нужно использовать deque вместо одной переменной для трекинга окна.
>
>     **Что на самом деле.** Deque-вариант (monotonic deque) применяется для max/min в окне (LeetCode 239), а не для суммы. Для sum монотонность нужна на самом окне, чего нельзя достичь deque-структурой.
>
>     **Откуда путаница.** Monotonic deque — мощная техника, и её путают с проблемой суммы окна.
>
>     **Если бы это было правдой.** LeetCode 560 имел бы решение через deque, но реально требует HashMap.
>
>     **Как было бы правильно.** Признать, что deque нужен для max/min, а для sum с отрицательными — prefix + HashMap.
>
> - [ ] D. Sliding window не работает потому, что массив должен быть отсортирован для двух указателей.
>
>     **Что на самом деле.** Sliding window НЕ требует сортировки — он работает на **непрерывных** подмассивах, а сортировка ломает непрерывность. Two pointers на отсортированном — другой паттерн (Two Sum II).
>
>     **Откуда путаница.** Two pointers и sliding window часто путают: оба используют пару индексов, но семантика разная.
>
>     **Если бы это было правдой.** LeetCode 209 Minimum Size Subarray Sum принимал бы только sorted input, но реально работает на любом массиве с положительными числами через sliding window.
>
>     **Как было бы правильно.** Сказать, что sliding window работает на любом неотсортированном массиве, если сумма монотонна; для отрицательных монотонность ломается — используем prefix + HashMap.

## Q14. Найти equilibrium index?

**Equilibrium index** — индекс `i`, где сумма слева равна сумме справа.

```java
int equilibriumIndex(int[] arr) {
    int total = 0;
    for (int x : arr) total += x;

    int leftSum = 0;
    for (int i = 0; i < arr.length; i++) {
        int rightSum = total - leftSum - arr[i];
        if (leftSum == rightSum) return i;
        leftSum += arr[i];
    }
    return -1;
}
```

Сложность `O(n)` время, `O(1)` память. Один проход после подсчёта общей суммы.


> [!mcq] Как найти equilibrium index (где sum слева == sum справа) за `O(n)`?
>
> - [ ] A. Для каждого `i` посчитать `sum(0..i-1)` и `sum(i+1..n-1)` — `O(n²)`, иначе не получится.
>
>     **Что на самом деле.** Brute force даёт `O(n²)`, но оптимум — `O(n)` через предвычисление общей суммы и поддержание `leftSum` в одном проходе. Для миллиона элементов разница `10¹²` vs `10⁶`.
>
>     **Откуда путаница.** Первое решение — «для каждого i пересчитать»; идея running `leftSum` появляется не сразу.
>
>     **Если бы это было правдой.** LeetCode 724 Find Pivot Index не имел бы решения за `O(n)`, но в условии явно требуется linear time.
>
>     **Как было бы правильно.** Признать, что `O(n²)` это baseline, а через total - leftSum - arr[i] можно за `O(n)` без квадратичного пересчёта.
>
> - [x] B. Считаем `total = sum(arr)`. В одном проходе поддерживаем `leftSum`, и для каждого `i`: `rightSum = total - leftSum - arr[i]`; если равны — нашли.
>
>     **Развёрнутое объяснение.** Идея: вместо квадратичных пересчётов используем алгебру. Пусть `total` — сумма всего массива. Для индекса `i`: `leftSum = sum(0..i-1)`, `rightSum = total - leftSum - arr[i]`. Если равны — equilibrium. После проверки добавляем `arr[i]` в `leftSum` и переходим к `i+1`. Один проход для подсчёта `total`, один — для поиска, итого `O(n)`, память `O(1)`.
>
>     **Пример.** `arr=[1,7,3,6,5,6]`, `total=28`. i=0: leftSum=0, rightSum=28-0-1=27, не равны, leftSum=1. i=1: rightSum=28-1-7=20, не равны, leftSum=8. i=2: rightSum=28-8-3=17, не равны, leftSum=11. i=3: rightSum=28-11-6=11 = leftSum! Equilibrium index = 3.
>
>     **Когда применять.** LeetCode 724 Find Pivot Index, поиск балансовой точки в распределённой нагрузке, partition load в распределённых хранилищах (Cassandra), balanced split в финансовых портфелях, центр масс в массиве весов.
>
>     **Подводные камни.** Может быть несколько equilibrium indices — обычно возвращают первый (LeetCode требует именно first occurrence). Для пустого массива или `n=1` нужны edge cases (n=1 → index 0 если разрешено `rightSum=leftSum=0`). Для отрицательных чисел алгоритм работает без изменений. Overflow: `total` может быть большим, используй `long`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q12]] prefix sum; [[arrays-strings-interview#Q11]] missing number (тоже sum-arithmetic); [[arrays-strings-interview#Q13]] subarray sum equals K.
>
> - [ ] C. Использовать двумерный prefix sum для `O(1)` запросов к каждому диапазону.
>
>     **Что на самом деле.** Двумерный prefix sum нужен для 2D-матриц, не для 1D-массива. Здесь хватает одномерного prefix или вообще running `leftSum`. Применение 2D — оверкилл и не даёт лучшей асимптотики.
>
>     **Откуда путаница.** Студенты, выучившие 2D-trick, применяют его всюду; для equilibrium это избыточно.
>
>     **Если бы это было правдой.** Алгоритм был бы сложнее необходимого, и LeetCode не упоминал бы простое running-sum решение.
>
>     **Как было бы правильно.** Сказать, что для 1D достаточно `total` + running `leftSum`; 2D-prefix — другая задача.
>
> - [ ] D. Это задача требует Segment Tree для дин-запросов sum в диапазоне.
>
>     **Что на самом деле.** Segment Tree (`O(n log n)` build, `O(log n)` query) применяется при многих изменяемых запросах. Для one-shot static equilibrium это оверинженеринг — running `leftSum` за `O(n)` намного проще.
>
>     **Откуда путаница.** Segment Tree — мощная универсальная структура, и её предлагают как панацею.
>
>     **Если бы это было правдой.** Задача в Easy не имела бы простого решения, и она бы не входила в LeetCode 724 Easy.
>
>     **Как было бы правильно.** Признать, что Segment Tree избыточен; для one-pass equilibrium хватит running sum.

## Q15. (!) Как повернуть матрицу на 90 градусов in-place?

**Поворот по часовой стрелке** = транспонирование + реверс каждой строки.

```java
void rotate(int[][] matrix) {
    int n = matrix.length;

    // Транспонирование (отражение по главной диагонали)
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            int tmp = matrix[i][j];
            matrix[i][j] = matrix[j][i];
            matrix[j][i] = tmp;
        }
    }

    // Реверс каждой строки
    for (int[] row : matrix) {
        int left = 0, right = n - 1;
        while (left < right) {
            int tmp = row[left];
            row[left++] = row[right];
            row[right--] = tmp;
        }
    }
}
```

Сложность `O(n²)` (по числу элементов), память `O(1)`. Для **поворота против часовой** — транспонирование + реверс столбцов (или реверс строк + транспонирование).


> [!mcq] Какая комбинация операций даёт поворот квадратной матрицы на 90° по часовой стрелке in-place?
>
> - [ ] A. Только реверс каждой строки — этого достаточно для поворота 90° CW.
>
>     **Что на самом деле.** Только реверс строк даёт **отражение по вертикальной оси** (mirroring), не поворот. Пример: `[[1,2,3],[4,5,6]]` → `[[3,2,1],[6,5,4]]` — строки те же, перевёрнутые. Это не поворот.
>
>     **Откуда путаница.** Реверс строк часто упоминается как часть rotation-комбинации, и его принимают за весь алгоритм.
>
>     **Если бы это было правдой.** LeetCode 48 принимал бы решение из одного реверса, но тест-кейсы это не пропускают.
>
>     **Как было бы правильно.** Признать, что нужны два шага: транспонирование + реверс строк; одного реверса недостаточно.
>
> - [ ] B. Транспонирование без реверса даёт поворот на 90° по часовой.
>
>     **Что на самом деле.** Транспонирование — это отражение по главной диагонали, не поворот. Чтобы получить полноценный поворот 90° CW, нужно ещё реверсить строки. Без реверса получится «зеркало» матрицы, не её поворот.
>
>     **Откуда путаница.** Транспонирование визуально похоже на поворот в простых случаях, и его путают.
>
>     **Если бы это было правдой.** Композиция трансформ из linear algebra нарушалась бы: поворот ≠ отражению.
>
>     **Как было бы правильно.** Признать, что транспонирование — это reflection along diagonal, для full rotation требуется второй reflection (вдоль вертикали).
>
> - [x] C. Транспонирование (отражение по главной диагонали) + реверс каждой строки.
>
>     **Развёрнутое объяснение.** Транспонирование меняет местами `m[i][j]` и `m[j][i]` — это отражение по главной диагонали (NW-SE). После этого реверс каждой строки даёт поворот на 90° по часовой. Альтернативное доказательство через композицию: поворот на 90° CW = транспонирование (отражение по NW-SE диагонали) ∘ реверс по горизонтали. Оба шага in-place: транспонирование требует обхода верхнего треугольника (`j > i`), реверс строк — стандартный two-pointers. Время `O(n²)`, память `O(1)`.
>
>     **Пример.** `[[1,2,3],[4,5,6],[7,8,9]]`. Транспонирование: `[[1,4,7],[2,5,8],[3,6,9]]`. Реверс каждой строки: `[[7,4,1],[8,5,2],[9,6,3]]`. Это и есть поворот 90° CW: первый столбец `[1,4,7]` стал верхней строкой `[7,4,1]`.
>
>     **Когда применять.** LeetCode 48 Rotate Image, поворот спрайтов в 2D-играх без allocate, обработка изображений в memory-mapped raster файлах (PGM/PPM), повороты тайлов в HDR-обработке, layout-rotations в CSS-движках браузеров.
>
>     **Подводные камни.** Транспонирование требует `j > i` (только верхний треугольник), иначе сделаешь два обмена и вернёшься к исходному. Для прямоугольной матрицы (`m ≠ n`) in-place rotation невозможна без `O(m*n)` буфера — размеры меняются местами. Поворот на 90° против часовой = транспонирование + реверс **столбцов** (или реверс строк + транспонирование). Поворот на 180° = реверс всех строк и реверс всех столбцов.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q2]] реверс через two-pointers; [[arrays-strings-interview#Q16]] spiral order; [[arrays-strings-interview#Q17]] set zeroes.
>
> - [ ] D. Создать новый массив `result[i][j] = matrix[n-1-j][i]` и вернуть его — это и есть in-place поворот.
>
>     **Что на самом деле.** Создание нового массива — это **out-of-place** решение с `O(n²)` доп. памяти. In-place значит «в той же матрице, без дополнительного буфера». Формула корректна, но решение не in-place.
>
>     **Откуда путаница.** Формула `matrix[n-1-j][i]` — math definition для rotation, и её применяют как алгоритм, не замечая аллокацию.
>
>     **Если бы это было правдой.** LeetCode 48 не имел бы follow-up «Could you do this in-place?», но реально такой follow-up есть.
>
>     **Как было бы правильно.** Сказать, что копирование работает (`O(n²)` память), но для in-place нужны transpose + row reverse в той же матрице.

## Q16. Spiral order — обход матрицы по спирали?

```java
List<Integer> spiralOrder(int[][] matrix) {
    List<Integer> result = new ArrayList<>();
    if (matrix.length == 0) return result;

    int top = 0, bottom = matrix.length - 1;
    int left = 0, right = matrix[0].length - 1;

    while (top <= bottom && left <= right) {
        // → вправо
        for (int j = left; j <= right; j++) result.add(matrix[top][j]);
        top++;
        // ↓ вниз
        for (int i = top; i <= bottom; i++) result.add(matrix[i][right]);
        right--;
        if (top <= bottom) {
            // ← влево
            for (int j = right; j >= left; j--) result.add(matrix[bottom][j]);
            bottom--;
        }
        if (left <= right) {
            // ↑ вверх
            for (int i = bottom; i >= top; i--) result.add(matrix[i][left]);
            left++;
        }
    }
    return result;
}
```

Сложность `O(m·n)`. Важна правильная проверка границ перед движением назад — иначе будет дублирование строк/столбцов.


> [!mcq] Почему в spiral traversal матрицы нужны проверки `top <= bottom` и `left <= right` перед обходом в обратных направлениях?
>
> - [x] A. Для матриц нечётной размерности (или прямоугольных) последний слой может иметь только одну строку или один столбец, и без проверки получится дублирование элементов.
>
>     **Развёрнутое объяснение.** Spiral traversal обходит границы прямоугольника: вправо по верхнему краю → вниз по правому → влево по нижнему → вверх по левому, потом сужает rectangle. Когда матрица не квадратная или нечётная, после первых двух обходов (вправо + вниз) может остаться один слой (одна строка/столбец). Без проверки `top <= bottom` обход «влево по нижнему» повторит уже пройденные элементы. Проверки исключают такие случаи.
>
>     **Пример.** Матрица `[[1,2,3]]` (1×3): top=0, bottom=0, left=0, right=2. Вправо: добавляем 1,2,3. top++=1 → top > bottom. Без проверки на «влево по нижнему» — алгоритм добавит `[3,2,1]` повторно, итог `[1,2,3,3,2,1]` (ошибка). С проверкой `top <= bottom`: ветка пропускается, итог `[1,2,3]`.
>
>     **Когда применять.** LeetCode 54 Spiral Matrix, LeetCode 59 Spiral Matrix II (генерация), визуализация heat-map в специфическом порядке, шифрование/декодирование по спирали (Caesar variants), пайплайн обработки 2D-датасетов в нестандартном порядке.
>
>     **Подводные камни.** Четыре направления требуют **двух** дополнительных проверок (`top <= bottom` для «влево», `left <= right` для «вверх»), потому что rectangular shrink происходит после каждой пары направлений. Если использовать direction-array `[(0,1),(1,0),(0,-1),(-1,0)]` и visited-матрицу, кода больше, но логика проще. Для бесконечной матрицы (spiral indexing) — другой алгоритм.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q15]] rotate matrix; [[arrays-strings-interview#Q17]] set zeroes; [[arrays-strings-interview#Q19]] move zeroes.
>
> - [ ] B. Проверки нужны только для пустой матрицы; для непустой алгоритм корректен без них.
>
>     **Что на самом деле.** Проверка на пустую матрицу — отдельный early return (`if (matrix.length == 0) return result`). Внутренние проверки `top <= bottom` нужны для нестандартных размеров (нечётных, прямоугольных), не только для empty.
>
>     **Откуда путаница.** Пустая матрица — типичный edge case, и его иногда считают единственным проблемным.
>
>     **Если бы это было правдой.** Алгоритм ломался бы только на empty input, но реально он ломается на любой нечётной/прямоугольной матрице без проверок.
>
>     **Как было бы правильно.** Признать, что проверки решают проблему дублирования в последнем слое, а пустая матрица — отдельный edge case.
>
> - [ ] C. Это оптимизация для производительности — без проверок алгоритм медленнее, но всё равно корректен.
>
>     **Что на самом деле.** Без проверок алгоритм **некорректен** — добавляет дубликаты в результат. Это вопрос правильности, не скорости.
>
>     **Откуда путаница.** В привычке программистов «проверки = оптимизация» (early exit), хотя здесь они принципиальны.
>
>     **Если бы это было правдой.** LeetCode 54 проходил бы тесты с предупреждением о медленности, но реально валится с wrong answer.
>
>     **Как было бы правильно.** Сказать, что проверки нужны для корректности, не для скорости; без них дубликаты в результате.
>
> - [ ] D. Это нужно для thread safety при concurrent обходе несколькими worker-thread-ами.
>
>     **Что на самом деле.** Spiral traversal — single-threaded алгоритм; thread safety и concurrent доступ — не его проблема. Проверки `top <= bottom` — про границы итерации, не про concurrency.
>
>     **Откуда путаница.** Java-разработчики часто думают о thread-safety, но в этом алгоритме нет shared state.
>
>     **Если бы это было правдой.** Параллельный spiral traversal требовал бы синхронизации rectangle-границ, но это не часть стандартной задачи.
>
>     **Как было бы правильно.** Признать, что проверки — про корректность single-threaded итерации, не про concurrency.

## Q17. Set zeroes — обнуление строк и столбцов?

Если в матрице есть `0`, обнулить всю строку и столбец. **Подвох:** обнуление в процессе обхода исказит результат.

```java
// O(1) дополнительной памяти — используем первую строку/столбец как маркеры
void setZeroes(int[][] matrix) {
    int rows = matrix.length, cols = matrix[0].length;
    boolean firstRowZero = false, firstColZero = false;

    // Проверяем первую строку и столбец
    for (int j = 0; j < cols; j++) if (matrix[0][j] == 0) firstRowZero = true;
    for (int i = 0; i < rows; i++) if (matrix[i][0] == 0) firstColZero = true;

    // Используем 1-ю строку/столбец как маркеры
    for (int i = 1; i < rows; i++)
        for (int j = 1; j < cols; j++)
            if (matrix[i][j] == 0) {
                matrix[i][0] = 0;
                matrix[0][j] = 0;
            }

    // Обнуляем по маркерам
    for (int i = 1; i < rows; i++)
        for (int j = 1; j < cols; j++)
            if (matrix[i][0] == 0 || matrix[0][j] == 0) matrix[i][j] = 0;

    // Обнуляем 1-ю строку/столбец, если нужно
    if (firstRowZero) for (int j = 0; j < cols; j++) matrix[0][j] = 0;
    if (firstColZero) for (int i = 0; i < rows; i++) matrix[i][0] = 0;
}
```

Сложность `O(m·n)` время, `O(1)` память. Альтернатива с `O(m+n)` памяти — два массива маркеров.


> [!mcq] Какая идея даёт `O(1)` дополнительной памяти для задачи Set Matrix Zeroes (обнулить строки и столбцы по найденным нулям)?
>
> - [ ] A. Идти по матрице и сразу обнулять строки/столбцы при встрече нуля — `O(1)` память.
>
>     **Что на самом деле.** Это сломает алгоритм: обнулённый элемент при дальнейшем обходе будет принят за «исходный ноль», и каскадно занулится вся матрица. Нужно сначала **найти** все нули, потом обнулять.
>
>     **Откуда путаница.** «Обнулить in-place» = «в той же матрице» — но это не значит «по ходу первого прохода». Нужны два прохода: detection + mutation.
>
>     **Если бы это было правдой.** На матрице с одним нулём в центре всё заполнялось бы нулями — но тест-кейсы LeetCode 73 это ловят.
>
>     **Как было бы правильно.** Признать, что нужны два прохода: сначала пометить, потом обнулить, иначе каскад.
>
> - [x] B. Использовать первую строку и первый столбец как маркеры; отдельно запомнить, нужно ли обнулять саму первую строку/столбец.
>
>     **Развёрнутое объяснение.** Идея: первая строка хранит, какие **столбцы** обнулять (если `matrix[0][j] = 0`, столбец `j` к обнулению). Первый столбец — какие **строки** обнулять. Но сама первая строка/столбец могут содержать исходные нули, поэтому отдельно фиксируем два булевых флага `firstRowZero`, `firstColZero` перед использованием маркеров. Затем три фазы: (1) пометить маркеры по нулям в `matrix[1..][1..]`, (2) обнулить по маркерам, (3) обнулить первую строку/столбец, если флаги установлены. `O(m*n)` время, `O(1)` память.
>
>     **Пример.** `[[1,1,1],[1,0,1],[1,1,1]]`. firstRowZero=false, firstColZero=false. Маркеры: `matrix[1][1]=0` → пометили `matrix[1][0]=0`, `matrix[0][1]=0`. Теперь матрица: `[[1,0,1],[0,0,1],[1,1,1]]`. Обнуляем по маркерам внутреннее `[1..][1..]`: для i=1 `matrix[1][0]=0` → строка 1 → `[0,0,0]`. Для i=2 строка 2 не помечена. Для j=1 `matrix[0][1]=0` → столбец 1 → `matrix[2][1]=0`. Итог: `[[1,0,1],[0,0,0],[1,0,1]]`.
>
>     **Когда применять.** LeetCode 73 Set Matrix Zeroes, очистка строк/столбцов в spreadsheet после detection NaN, в sparse-matrix transformations при обработке missing data, ETL-pipelines при обнаружении corrupted cells.
>
>     **Подводные камни.** Порядок обнуления критичен — сначала внутренние (`[1..][1..]`), потом первая строка/столбец (по флагам). Если перепутать — потеряются маркеры. Альтернатива: использовать `Boolean[m]` + `Boolean[n]` массивы (`O(m+n)` память, проще читать). Для **multi-thread** обновления нужны барьеры или версионирование.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q15]] rotate matrix; [[arrays-strings-interview#Q16]] spiral traversal; [[arrays-strings-interview#Q19]] move zeroes (тоже две прохода).
>
> - [ ] C. Создать копию матрицы и работать в ней — `O(m*n)` память приемлемо, иначе никак.
>
>     **Что на самом деле.** Это работает, но даёт `O(m*n)` память. LeetCode 73 явно ставит follow-up «Could you use O(m+n) or O(1) extra space?» — копия не отвечает на оба.
>
>     **Откуда путаница.** Копия — самый прямой способ избежать каскада, и его часто используют как baseline.
>
>     **Если бы это было правдой.** Не существовало бы оптимизации до `O(1)`, и follow-up не имел бы смысла.
>
>     **Как было бы правильно.** Признать, что копия — baseline `O(m*n)`, а для `O(1)` нужны marker-rows в исходной матрице.
>
> - [ ] D. Использовать `HashSet<Integer>` для строк и `HashSet<Integer>` для столбцов с нулями — `O(m+n)` память.
>
>     **Что на самом деле.** Это работает, `O(m+n)` память; это улучшение над `O(m*n)`, но всё ещё не `O(1)`. LeetCode 73 принимает это как удовлетворительное решение для middle-tier, но для O(1) нужны in-matrix маркеры.
>
>     **Откуда путаница.** HashSet — стандартный приём для «запомнить найденные», и его инстинктивно применяют.
>
>     **Если бы это было правдой.** LeetCode не упоминал бы `O(1)` follow-up, но он есть.
>
>     **Как было бы правильно.** Признать, что HashSet даёт `O(m+n)` память; для `O(1)` нужны in-place маркеры в первой строке/столбце.

## Q18. (!) Dutch National Flag — сортировка трёх значений за один проход?

Задача Эдсгера Дейкстры: отсортировать массив из `0`, `1`, `2` за `O(n)`, `O(1)`.

```java
void sortColors(int[] arr) {
    int low = 0, mid = 0, high = arr.length - 1;

    while (mid <= high) {
        if (arr[mid] == 0) {
            swap(arr, low++, mid++);
        } else if (arr[mid] == 1) {
            mid++;
        } else { // arr[mid] == 2
            swap(arr, mid, high--);
            // mid не двигаем — пришедший элемент ещё не обработан
        }
    }
}

void swap(int[] arr, int i, int j) {
    int tmp = arr[i]; arr[i] = arr[j]; arr[j] = tmp;
}
```

Идея: три указателя делят массив на 4 зоны: `[0..low)` — нули, `[low..mid)` — единицы, `[mid..high]` — необработанные, `(high..end]` — двойки.

Применяется в `Quick Sort` с дублирующимися значениями (3-way partition).


> [!mcq] Зачем в Dutch National Flag (sort colors `0/1/2`) после swap с `high` указатель `mid` не двигают?
>
> - [x] A. Элемент, пришедший из позиции `high`, ещё не обработан — может быть `0` или `1`, и его нужно проверить в следующей итерации.
>
>     **Развёрнутое объяснение.** В Dutch National Flag три указателя: `low` — граница нулей, `mid` — текущий элемент, `high` — граница двоек. Когда `arr[mid] == 2`, мы swap с `arr[high]` и декрементируем `high`. Но что было в `arr[high]` до swap? Мы не знаем — это мог быть `0`, `1` или `2`. После swap новый `arr[mid]` нужно проверить заново, поэтому `mid` не инкрементируем. В отличие от случая `arr[mid] == 0`: swap с `arr[low]` гарантирует, что туда придёт `1` (так как `low` всегда указывает на граничный `1` или `arr[low] == 0`), и `mid` можно безопасно увеличить.
>
>     **Пример.** `arr=[2,0,1]`, low=0, mid=0, high=2. arr[mid]=2: swap(mid, high) → `[1,0,2]`, high=1, mid не меняем. arr[mid]=1: mid++. arr[mid]=0: swap(low, mid) → `[0,1,2]`, low=1, mid=2. mid > high, стоп. Итог `[0,1,2]`.
>
>     **Когда применять.** LeetCode 75 Sort Colors, 3-way partition в QuickSort при большом количестве дубликатов (избегает quadratic deterioration), DSP-classification trinary signals, RGB-channel bucketing, threshold-based image segmentation.
>
>     **Подводные камни.** Условие цикла `mid <= high` (НЕ `<` — иначе пропустишь последний элемент). При `arr[mid] == 0` важно инкрементировать **и** `low`, **и** `mid` (потому что `arr[low]` до swap гарантировано `<= 1`, и новый `arr[mid]` обработан). Для расширения на 4 значения (Dutch flag для `0/1/2/3`) — добавь четвёртый указатель или сделай 2 прохода. Время `O(n)`, память `O(1)`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q4]] remove duplicates two-pointers; [[arrays-strings-interview#Q19]] move zeroes; [[arrays-strings-interview#Q20]] next permutation.
>
> - [ ] B. Инкремент `mid` после swap с `high` — это off-by-one bug, который никто не замечает, но он создаёт «правильный» результат случайно.
>
>     **Что на самом деле.** Если двигать `mid` после swap с `high`, алгоритм **пропустит** элемент, пришедший из `high`, и не отсортирует его. Это не «случайно правильно» — это явный bug, который видно на тест-кейсе типа `[1,2,0]`.
>
>     **Откуда путаница.** Некоторые off-by-one ошибки в JS/Python проявляются только на edge cases, и студенты думают, что «работает» — значит OK.
>
>     **Если бы это было правдой.** LeetCode 75 проходился бы любым вариантом, но реально без правильной обработки `mid` не движется на `2`-случае — некоторые тесты падают.
>
>     **Как было бы правильно.** Признать, что `mid` намеренно не двигают после swap с `high`, потому что новый элемент в позиции `mid` ещё не обработан.
>
> - [ ] C. Так требует стандарт Dijkstra; без этого свойство 3-way partition не сохраняется.
>
>     **Что на самом деле.** Дийкстра действительно сформулировал задачу Dutch National Flag, но не как «стандарт» — это математически обоснованное требование инварианта, не догма. Инвариант: после каждой итерации `[0..low) == 0`, `[low..mid) == 1`, `[mid..high]` — необработано, `(high..n-1] == 2`. Если двигать mid после swap с high — нарушается «`[mid..high]` необработано».
>
>     **Откуда путаница.** «Дийкстра придумал — значит сакрально» — попытка обосновать через авторитет, а не через инвариант.
>
>     **Если бы это было правдой.** Алгоритм был бы догматическим; на самом деле он математически выведен из требования one-pass и поддержания инварианта.
>
>     **Как было бы правильно.** Сказать, что фиксация `mid` после swap-with-high — следствие инварианта, а не догма; новый элемент в `mid` нужен для проверки.
>
> - [ ] D. Для thread-safety: если другой поток модифицирует массив, инкремент `mid` приведёт к race condition.
>
>     **Что на самом деле.** Dutch National Flag — single-threaded алгоритм. Concurrent модификации массива не входят в спецификацию задачи; thread-safety не аргумент.
>
>     **Откуда путаница.** Привычка думать о concurrency накладывается на алгоритмическую задачу.
>
>     **Если бы это было правдой.** При single-threaded запуске не было бы смысла фиксировать `mid`, но он фиксируется и в single-threaded случае.
>
>     **Как было бы правильно.** Признать, что фиксация `mid` нужна для корректности single-threaded алгоритма, а concurrency — отдельная тема.

## Q19. Move Zeroes — переместить нули в конец?

Сохранить порядок ненулевых элементов.

```java
void moveZeroes(int[] arr) {
    int slow = 0;
    for (int fast = 0; fast < arr.length; fast++) {
        if (arr[fast] != 0) {
            arr[slow++] = arr[fast];
        }
    }
    while (slow < arr.length) arr[slow++] = 0;
}
```

Two pointers, `O(n)` время, `O(1)` память. Альтернатива со swap — также `O(n)`, но больше операций.


> [!mcq] Как переместить все нули в конец массива с сохранением порядка ненулевых за один проход и `O(1)` память?
>
> - [x] A. Two pointers: `slow` указывает на позицию записи, `fast` — на чтение; копируем ненулевые в `arr[slow++]`, в конце заполняем нулями.
>
>     **Развёрнутое объяснение.** Идея: первая фаза собирает ненулевые элементы в начале массива через single-write pointer `slow`. `fast` сканирует весь массив; когда `arr[fast] != 0`, записываем `arr[slow++] = arr[fast]`. После цикла `slow` показывает количество ненулевых, оставшиеся слоты `[slow..n-1]` заполняем нулями. Порядок сохраняется, потому что `fast` идёт линейно слева направо, а `slow` записывает по мере встречи ненулевых. Время `O(n)`, память `O(1)`.
>
>     **Пример.** `[0,1,0,3,12]`. slow=0, fast=0: arr[0]=0, skip. fast=1: arr[1]=1, arr[0]=1, slow=1 → `[1,1,0,3,12]`. fast=2: arr[2]=0, skip. fast=3: arr[3]=3, arr[1]=3, slow=2 → `[1,3,0,3,12]`. fast=4: arr[4]=12, arr[2]=12, slow=3 → `[1,3,12,3,12]`. Заполняем `[3..4]` нулями: `[1,3,12,0,0]`.
>
>     **Когда применять.** LeetCode 283 Move Zeroes, очистка sparse-векторов в memory-mapped массивах, компактация после soft-delete в файловых хранилищах, page-compaction в databases, скрытие missing значений в timeseries для отображения.
>
>     **Подводные камни.** Альтернатива со swap (`if (arr[fast] != 0) swap(arr[slow++], arr[fast])`) тоже `O(n)`, но делает в 2 раза больше операций обмена. Если порядок ненулевых не важен — можно two-pointers навстречу: `left` ищет ноль, `right` ищет ненулевое, swap, продвигаемся. Для сохранения **относительного порядка нулей** — это уже сортировка stable, требующая других алгоритмов.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q4]] remove duplicates two-pointers; [[arrays-strings-interview#Q18]] Dutch National Flag; [[arrays-strings-interview#Q3]] rotate array.
>
> - [ ] B. Создать новый массив, скопировать ненулевые в начало, нули в конец, потом скопировать обратно. `O(n)` память.
>
>     **Что на самом деле.** Это работает, но даёт `O(n)` дополнительную память. LeetCode 283 явно ставит follow-up «minimize the number of operations» и in-place требование.
>
>     **Откуда путаница.** «Скопировать в новый массив» — простой и понятный способ для junior-уровня.
>
>     **Если бы это было правдой.** Не существовало бы in-place решения через two-pointers, и оно не входило бы в LeetCode Easy.
>
>     **Как было бы правильно.** Признать, что новый массив даёт `O(n)` память; для `O(1)` нужен two-pointers in-place.
>
> - [ ] C. Использовать `Arrays.sort` с custom Comparator, который ставит нули в конец. `O(n log n)`.
>
>     **Что на самом деле.** `O(n log n)` хуже `O(n)`. Плюс `Comparator` не работает на `int[]` — нужно конвертировать в `Integer[]` или `List<Integer>` (boxing, `O(n)` память). И стабильная сортировка не гарантирована для всех реализаций.
>
>     **Откуда путаница.** Sort с custom comparator — мощный приём, и его пытаются применить везде, где «нужно переставить».
>
>     **Если бы это было правдой.** LeetCode 283 имел бы решение через `Arrays.sort`, но time complexity не позволяет.
>
>     **Как было бы правильно.** Признать, что sort даёт `O(n log n)` + overhead на boxing, а two-pointers даёт `O(n)`/`O(1)`.
>
> - [ ] D. Через `Stream.filter(x -> x != 0)` собрать ненулевые, потом дополнить нулями.
>
>     **Что на самом деле.** Stream создаёт промежуточный массив (`O(n)` память), и копирование обратно делает `O(n)` дополнительный проход. Это не in-place и проигрывает two-pointers.
>
>     **Откуда путаница.** Stream-стиль для функциональной читаемости, и его применяют без анализа аллокаций.
>
>     **Если бы это было правдой.** Не было бы преимущества two-pointers in-place, и JMH-бенчмарки показали бы одинаковую производительность — но они показывают разницу.
>
>     **Как было бы правильно.** Сказать, что Stream выразителен, но даёт `O(n)` доп. память; для in-place — two-pointers.

## Q20. Next Permutation — следующая лексикографическая перестановка?

```java
void nextPermutation(int[] arr) {
    int n = arr.length;

    // 1. Найти первый i справа, где arr[i] < arr[i+1]
    int i = n - 2;
    while (i >= 0 && arr[i] >= arr[i + 1]) i--;

    if (i >= 0) {
        // 2. Найти первый j справа, где arr[j] > arr[i]
        int j = n - 1;
        while (arr[j] <= arr[i]) j--;
        // 3. Swap
        int tmp = arr[i]; arr[i] = arr[j]; arr[j] = tmp;
    }

    // 4. Реверс правой части
    int left = i + 1, right = n - 1;
    while (left < right) {
        int tmp = arr[left];
        arr[left++] = arr[right];
        arr[right--] = tmp;
    }
}
```

Сложность `O(n)` время, `O(1)` память. Для последней перестановки в лексикографическом порядке вернёт первую (отсортированный массив).


> [!mcq] Какие три шага составляют алгоритм Next Permutation за `O(n)` in-place?
>
> - [x] A. Найти первый справа `i` где `arr[i] < arr[i+1]`; найти первый справа `j` где `arr[j] > arr[i]`; swap `i,j`; реверс суффикса `[i+1..n-1]`.
>
>     **Развёрнутое объяснение.** Идея: чтобы получить следующую перестановку в лексикографическом порядке, нужно минимально увеличить число. (1) Находим pivot — первый справа индекс `i`, где последовательность ещё не отсортирована по убыванию (`arr[i] < arr[i+1]`). Все индексы > i образуют убывающий хвост (последняя перестановка для этого суффикса). (2) В этом хвосте находим минимальное число, большее `arr[i]` — это первый справа `j` с `arr[j] > arr[i]`. (3) Swap делает префикс [0..i] на 1 «больше» в лексикопорядке. (4) После swap хвост всё ещё убывающий — реверс делает его возрастающим (минимальный лексикопорядок). Если pivot не найден — массив уже последняя перестановка, реверсим весь.
>
>     **Пример.** `[1,2,3]` → pivot i=1 (`2<3`), j=2 (`3>2`), swap → `[1,3,2]`, реверс суффикса [2..2] → `[1,3,2]`. Следующая: `[1,3,2]` → pivot i=0 (`1<3`), j=2 (`2>1`), swap → `[2,3,1]`, реверс [1..2] → `[2,1,3]`. Так последовательно получаем все перестановки.
>
>     **Когда применять.** LeetCode 31 Next Permutation, генерация всех перестановок без рекурсии (итеративный обход), последовательность permutations в STL `next_permutation`, поиск best/worst-case input для тестов, обход состояний в combinatorial generative algorithms.
>
>     **Подводные камни.** Если pivot не найден (массив отсортирован по убыванию) — это последняя перестановка, нужно реверсить весь массив (вернуться к первой). Дубликаты обрабатываются корректно благодаря строгим неравенствам `<` (не `<=`). Off-by-one: `i = n-2` стартует, не `n-1`. Реверс суффикса критичен — без него получится правильный pivot, но не минимальный suffix.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q2]] реверс через two-pointers; [[arrays-strings-interview#Q3]] rotate array (тоже использует reverse); [[arrays-strings-interview#Q18]] Dutch National Flag.
>
> - [ ] B. Генерировать все перестановки рекурсивно, отсортировать их и взять следующую — это `O(n! · n log n)`.
>
>     **Что на самом деле.** Генерация всех перестановок — `O(n!)`, что катастрофично: для n=12 это 479 миллионов. Для next-permutation хватает `O(n)`.
>
>     **Откуда путаница.** «Чтобы найти следующую — нужны все» — наивная идея, без понимания locality алгоритма.
>
>     **Если бы это было правдой.** LeetCode 31 не было бы Medium, а закрывалось бы как computationally infeasible для n > 10.
>
>     **Как было бы правильно.** Признать, что existing relations between adjacent permutations позволяют найти next за `O(n)`, не генерируя все.
>
> - [ ] C. Поделить на половины, рекурсивно найти next в правой, потом «переложить» — divide and conquer.
>
>     **Что на самом деле.** Next permutation не структурируется как divide-and-conquer; pivot может быть в любой позиции, и разделение на половины не помогает. Алгоритм линейный по природе.
>
>     **Откуда путаница.** D&C — универсальная техника, и её пытаются применить к любой задаче на массивах.
>
>     **Если бы это было правдой.** Существовал бы `O(log n)` алгоритм — но известная нижняя граница `Ω(n)` для one-shot next-permutation.
>
>     **Как было бы правильно.** Сказать, что алгоритм линейный по природе и не разлагается на D&C; сложность `O(n)`.
>
> - [ ] D. Сделать `Arrays.sort` от конца к началу — последняя половина становится отсортированной.
>
>     **Что на самом деле.** Полная сортировка теряет понятие «следующая перестановка». Например, `[1,3,2]` после полной sort → `[1,2,3]`, это **первая** перестановка, не следующая.
>
>     **Откуда путаница.** Sort — лёгкий способ упорядочивания, и студенты не различают «отсортировать суффикс» и «полная sort».
>
>     **Если бы это было правдой.** LeetCode 31 принимал бы решение через `Arrays.sort`, но реально это даёт wrong answer на большинстве тестов.
>
>     **Как было бы правильно.** Сказать, что сортируем (или реверсим) **только суффикс после pivot**, не весь массив.

## Q21. (!) String — алгоритм реверса строки?

```java
// 1. Через StringBuilder — O(n)
String reverse1(String s) {
    return new StringBuilder(s).reverse().toString();
}

// 2. Two pointers in-place в char[] — O(n)
String reverse2(String s) {
    char[] arr = s.toCharArray();
    int left = 0, right = arr.length - 1;
    while (left < right) {
        char tmp = arr[left];
        arr[left++] = arr[right];
        arr[right--] = tmp;
    }
    return new String(arr);
}

// 3. Рекурсия — O(n) по времени и стеку — НЕ рекомендуется
String reverse3(String s) {
    if (s.length() <= 1) return s;
    return reverse3(s.substring(1)) + s.charAt(0);
}
```

`String` в Java **immutable** — прямой in-place реверс невозможен, нужен `char[]` или `StringBuilder`. На собеседовании ожидают вариант 2 (показывает понимание two-pointers).

**Особый случай:** **юникодные surrogate pairs** (эмодзи, китайские иероглифы). Простой `char[]` реверс сломает их. Корректно — через `StringBuilder.reverse()`, который учитывает surrogates.

Подробнее — в [Java String](../../programming-languages/java/java-string-interview.md).


> [!mcq] Почему `s.toCharArray()` + two-pointers swap может сломать строку с эмодзи (surrogate pairs)?
>
> - [ ] A. `toCharArray()` теряет данные на не-ASCII символах из-за encoding mismatch.
>
>     **Что на самом деле.** `toCharArray()` корректно копирует все UTF-16 code units без потери данных. Проблема не в копировании, а в swap'е: surrogate pair состоит из 2 `char` (high + low surrogate), и при простом swap они меняются местами в неправильном порядке, образуя невалидный Unicode.
>
>     **Откуда путаница.** «Эмодзи ломаются» часто сводят к проблеме encoding, хотя реальная причина — split surrogate pair при reverse.
>
>     **Если бы это было правдой.** `new String(s.toCharArray()).equals(s)` иногда был бы `false` — но он всегда `true`, потому что copy корректный.
>
>     **Как было бы правильно.** Сказать, что копия корректна, но операция reverse split'ит surrogate pair и создаёт невалидный Unicode.
>
> - [x] B. Эмодзи (например, 😀 U+1F600) в Java хранится как 2 `char` (high + low surrogate). Простой swap меняет их местами, образуя невалидный Unicode `[low, high]` вместо `[high, low]`.
>
>     **Развёрнутое объяснение.** Unicode supplementary planes (`U+10000` и выше) кодируются в UTF-16 двумя 16-битными `char`: high surrogate (`U+D800-U+DBFF`) и low surrogate (`U+DC00-U+DFFF`). Java `String.length()` возвращает количество UTF-16 code units, не code points. Простой two-pointers swap по `char[]` рассматривает каждый surrogate как независимый, переставляет high и low в обратном порядке — получается невалидная пара. Корректные подходы: `StringBuilder.reverse()` (учитывает surrogate pairs), либо ручной обход через `codePointAt(i)` + `Character.charCount(cp)`.
>
>     **Пример.** `"a😀b"` имеет `length() == 4` (a, high-surrogate, low-surrogate, b). Простой reverse: `[b, low, high, a]` — невалидно. `StringBuilder.reverse()`: `"b😀a"` — корректно, потому что внутри ловит surrogate pairs.
>
>     **Когда применять.** Реверс строки в i18n-приложениях, обработка эмодзи в Twitter/мессенджерах, korean/chinese/арабский текст с extended characters, мобильные клиенты с локализацией, поиск и replace в Unicode-aware тексте.
>
>     **Подводные камни.** Грейфем-кластеры (например, эмодзи семьи 👨‍👩‍👧 — это `man + ZWJ + woman + ZWJ + girl`, 8 code points!) даже `StringBuilder.reverse()` обрабатывает некорректно с точки зрения user-perceived character. Для true grapheme reverse нужна библиотека ICU4J `BreakIterator.getCharacterInstance()`. Combining characters (например, `é = e + ́`) — отдельная боль.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q2]] реверс массива two-pointers; [[arrays-strings-interview#Q33]] string pool и `==`; [[arrays-strings-interview#Q35]] StringBuilder.
>
> - [ ] C. `toCharArray()` создаёт копию, и swap по копии не виден в исходной строке — это просто no-op.
>
>     **Что на самом деле.** `String` immutable, копия `toCharArray()` действительно отдельная, но потом из неё создаётся новая String `new String(arr)` — она и есть результат. Это не no-op, изменения видны.
>
>     **Откуда путаница.** «Immutable String» переоценивают как защиту от любых модификаций, забывая, что результат можно вернуть как новую String.
>
>     **Если бы это было правдой.** Реверс через `toCharArray` + swap всегда возвращал бы исходную строку без изменений, что противоречит реальности.
>
>     **Как было бы правильно.** Признать, что копия отдельная, но новая String корректно создаётся из неё; проблема — в семантике swap surrogate pairs.
>
> - [ ] D. Java не поддерживает Unicode в `char[]`, нужно использовать `int[]` для code points.
>
>     **Что на самом деле.** Java `char` — это 16-битное UTF-16 code unit, и Unicode поддерживается полностью через surrogate pairs. Использование `int[]` для code points — один из путей корректного reverse, но это не из-за «отсутствия поддержки», а из-за конкретики UTF-16.
>
>     **Откуда путаница.** Многие думают, что Java `char` — это «один символ», и удивляются surrogate pairs.
>
>     **Если бы это было правдой.** Java не имел бы `String.codePointAt()` и `Character.charCount()` — но они есть именно для работы с Unicode supplementary planes.
>
>     **Как было бы правильно.** Сказать, что `char` — это UTF-16 code unit; для code-point-aware reverse используют `int[]` или `StringBuilder`.

## Q22. (!) Проверка палиндрома?

```java
// Простой случай — без учёта регистра и спецсимволов
boolean isPalindrome(String s) {
    int left = 0, right = s.length() - 1;
    while (left < right) {
        if (s.charAt(left) != s.charAt(right)) return false;
        left++;
        right--;
    }
    return true;
}

// LeetCode-вариант: только alphanumeric, ignore case
boolean isPalindromeLeet(String s) {
    int left = 0, right = s.length() - 1;
    while (left < right) {
        while (left < right && !Character.isLetterOrDigit(s.charAt(left))) left++;
        while (left < right && !Character.isLetterOrDigit(s.charAt(right))) right--;
        if (Character.toLowerCase(s.charAt(left)) !=
            Character.toLowerCase(s.charAt(right))) return false;
        left++;
        right--;
    }
    return true;
}
```

`O(n)` время, `O(1)` память. Альтернатива — реверс и сравнение, но это `O(n)` доп. памяти.


> [!mcq] Какой способ проверки палиндрома даёт `O(n)` время и `O(1)` память (без alphanumeric-фильтра)?
>
> - [ ] A. Реверсировать строку и сравнить с исходной через `equals` — `O(n)` память на новую String.
>
>     **Что на самом деле.** Работает, но создаёт новую String (`O(n)` память на копию). Two-pointers даёт `O(1)`. Кроме того, реверс делает полный проход, а two-pointers может exit early на первом несовпадении.
>
>     **Откуда путаница.** «Палиндром = строка равна реверсу» — определение, и его буквально кодируют, не задумываясь об оптимизации.
>
>     **Если бы это было правдой.** LeetCode 125 не имел бы критерия `O(1)` памяти, но обычно ожидается именно two-pointers.
>
>     **Как было бы правильно.** Признать, что reverse + equals корректен, но `O(n)` памяти; для `O(1)` нужны two-pointers.
>
> - [ ] B. Хеш-сравнение: посчитать hash первой и второй половины, сравнить. `O(n)` время, `O(1)` память.
>
>     **Что на самом деле.** Hash collisions возможны: разные строки могут дать одинаковый хеш. Для строгого ответа нужна проверка посимвольно, и хеш не даёт преимущества. Плюс, для палиндрома hash первой половины не равен hash зеркальной второй (палиндром не означает «hash совпадают»).
>
>     **Откуда путаница.** Хеширование — частый speedup, но для O(n) сравнений двух половин оно не помогает (та же асимптотика, плюс false positive).
>
>     **Если бы это было правдой.** Rabin-Karp применялся бы для палиндромов, но он решает задачу string-matching, не palindrome-check.
>
>     **Как было бы правильно.** Признать, что хеш не упрощает palindrome-check; two-pointers достаточно.
>
> - [ ] C. Сортировать символы строки — если после sort строка равна реверсу sorted, это палиндром.
>
>     **Что на самом деле.** Sorted string == sorted reversed string всегда (sort коммутативен), это не критерий палиндрома. Например, `"aabb"` после sort `"aabb"`, его reverse `"bbaa"`, тоже sorted в `"aabb"` — но `"aabb"` не палиндром.
>
>     **Откуда путаница.** Студенты путают anagram (использует sort) и palindrome (использует two-pointers).
>
>     **Если бы это было правдой.** Все anagram'ы были бы палиндромами, что абсурдно.
>
>     **Как было бы правильно.** Признать, что sort применяется для anagram, а для palindrome — two-pointers без sort.
>
> - [x] D. Two pointers `left=0`, `right=n-1`: сравнивать `s.charAt(left)` и `s.charAt(right)`, двигаться к центру до `left >= right`.
>
>     **Развёрнутое объяснение.** Палиндром — строка, читающаяся одинаково слева направо и справа налево. Two pointers идут навстречу: `left` стартует с начала, `right` — с конца. На каждом шаге сравниваем символы; если разные — не палиндром. Если равны — `left++`, `right--`. Если дошли до `left >= right` без расхождений — палиндром. Память — две int переменные, время — `n/2` сравнений (`O(n)`).
>
>     **Пример.** `"radar"`: left=0(r), right=4(r), равны → left=1(a), right=3(a) → left=2(d), right=2(d) → left ≥ right, палиндром. `"hello"`: left=0(h), right=4(o), `h≠o` → не палиндром.
>
>     **Когда применять.** LeetCode 125 Valid Palindrome, проверка palindromic substrings в DNA-анализе (поиск палиндромных последовательностей), валидация номеров с зеркальной структурой (некоторые сертификаты), Manacher's algorithm preprocessing, кэш-friendly palindrome check для long strings.
>
>     **Подводные камни.** Для LeetCode 125 (только alphanumeric, ignore case) нужны `while`-фильтры для skip non-letter-or-digit: `while (left < right && !Character.isLetterOrDigit(s.charAt(left))) left++;`. `Character.toLowerCase()` нужно применить перед сравнением. Для surrogate pairs (эмодзи) — корректнее использовать `codePointAt` и `Character.charCount`. Для пустой строки — палиндром по определению (цикл не выполняется).
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q2]] реверс через two-pointers; [[arrays-strings-interview#Q21]] string reverse; [[arrays-strings-interview#Q26]] longest palindromic substring.

## Q23. (!) Проверка анаграммы?

Две строки — анаграммы, если одна получается перестановкой символов другой.

```java
// Метод 1: сортировка — O(n log n) время, O(n) память (toCharArray)
boolean isAnagramSort(String a, String b) {
    if (a.length() != b.length()) return false;
    char[] aArr = a.toCharArray();
    char[] bArr = b.toCharArray();
    Arrays.sort(aArr);
    Arrays.sort(bArr);
    return Arrays.equals(aArr, bArr);
}

// Метод 2: подсчёт частот — O(n) время, O(1) память для ASCII
boolean isAnagram(String a, String b) {
    if (a.length() != b.length()) return false;
    int[] count = new int[26]; // только английский lowercase
    for (int i = 0; i < a.length(); i++) {
        count[a.charAt(i) - 'a']++;
        count[b.charAt(i) - 'a']--;
    }
    for (int c : count) if (c != 0) return false;
    return true;
}

// Универсальный для unicode — HashMap
boolean isAnagramUnicode(String a, String b) {
    if (a.length() != b.length()) return false;
    Map<Integer, Integer> freq = new HashMap<>();
    a.codePoints().forEach(c -> freq.merge(c, 1, Integer::sum));
    b.codePoints().forEach(c -> freq.merge(c, -1, Integer::sum));
    return freq.values().stream().allMatch(v -> v == 0);
}
```


> [!mcq] Какой алгоритм проверки анаграмм даёт `O(n)` время и `O(1)` память для строк из ASCII lowercase?
>
> - [x] A. Массив счётчиков `int[26]`: для каждого `i` инкрементируем `count[a.charAt(i)-'a']++` и декрементируем `count[b.charAt(i)-'a']--`; в конце проверяем, что все `count[i] == 0`.
>
>     **Развёрнутое объяснение.** Идея: анаграммы имеют одинаковую частоту каждого символа. Для ASCII lowercase (26 букв) используем фиксированный массив `int[26]` — это `O(1)` память (константный размер не зависит от `n`). Один проход по обеим строкам параллельно: инкрементируем счётчик для символа из `a`, декрементируем для символа из `b`. Если строки — анаграммы, все счётчики обнулятся. Время `O(n)`, проверка финального массива `O(26) = O(1)`.
>
>     **Пример.** `a="anagram"`, `b="nagaram"`. Длины равны. Проходим: count[a]=+1,count[n]=+1,count[a]=+2,count[g]=+1,count[r]=+1,count[a]=+3,count[m]=+1 (всего из a). Параллельно: count[n]=0,count[a]=+2,count[g]=0,count[a]=+1,count[r]=0,count[a]=0,count[m]=0. Все нули → анаграммы.
>
>     **Когда применять.** LeetCode 242 Valid Anagram, проверка перестановок в DNA-секвенциях, сравнение word lists в spell-checker, нормализация slug'ов, кэширование canonical forms.
>
>     **Подводные камни.** Размер массива `26` подходит только для ASCII lowercase. Для general Unicode используй `HashMap<Integer, Integer>` через `codePoints()` — память становится `O(min(n, unique chars))`. Если длины строк отличаются — early return `false` (анаграммы одинаковой длины). Регистр: для case-insensitive вызывай `toLowerCase` (учитывая Locale!). Для surrogate pairs нужен code-point подход.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q24]] group anagrams; [[arrays-strings-interview#Q25]] longest substring without repeats (тоже частотные счётчики); [[arrays-strings-interview#Q12]] prefix sum.
>
> - [ ] B. Сортировка обеих строк и сравнение через `Arrays.equals` — это `O(n)` после сортировки.
>
>     **Что на самом деле.** Сортировка `O(n log n)`, не `O(n)`. Плюс `toCharArray()` создаёт две копии (`O(n)` память). Подход работает, но проигрывает счётчикам по обоим критериям.
>
>     **Откуда путаница.** Sort + equals — идиоматичный приём для «нормализации» и сравнения; забывают про `n log n`.
>
>     **Если бы это было правдой.** LeetCode 242 не имел бы follow-up «What if the inputs contain unicode characters? How would you adapt?», но он есть, и оптимальный — HashMap частот.
>
>     **Как было бы правильно.** Признать, что sort даёт `O(n log n)`, и счётчики — `O(n)` оптимум.
>
> - [ ] C. Перемножить простые числа, кодирующие каждый символ — анаграммы дают одинаковое произведение.
>
>     **Что на самом деле.** Этот трюк работает математически (Gödel-numbering), но произведение быстро переполняется: для строки длиной 30 произведение простых > 2^64 даже с `BigInteger`. Производительность хуже счётчиков, и есть риск collision при модулярной арифметике.
>
>     **Откуда путаница.** «Уникальные простые → уникальное произведение» — элегантный трюк из теории чисел, и его иногда показывают на собеседовании как curiosity.
>
>     **Если бы это было правдой.** Production-код использовал бы prime-product для anagram check, но реально используются счётчики из-за overflow.
>
>     **Как было бы правильно.** Признать, что prime-product — теоретический трюк с overflow-проблемами; для production — счётчики.
>
> - [ ] D. Если `a.hashCode() == b.hashCode()` — это анаграмма; иначе — нет.
>
>     **Что на самом деле.** `hashCode` для String зависит от порядка символов: `"abc"` и `"cba"` имеют разные хеши. Анаграммы — это перестановки, не одинаковые строки, и hashCode их не объединяет.
>
>     **Откуда путаница.** «Хеш = uniqueness» — миф; hash работает на equality, не на anagram-equivalence.
>
>     **Если бы это было правдой.** `"silent".hashCode() == "listen".hashCode()` всегда бы выполнялось, но это не так.
>
>     **Как было бы правильно.** Сказать, что hashCode не инвариантен относительно перестановок; для anagram нужен sort или счётчики.

## Q24. Группировка анаграмм?

```java
List<List<String>> groupAnagrams(String[] strs) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String s : strs) {
        char[] arr = s.toCharArray();
        Arrays.sort(arr);
        String key = new String(arr);
        groups.computeIfAbsent(key, k -> new ArrayList<>()).add(s);
    }
    return new ArrayList<>(groups.values());
}
```

Сложность `O(n · k log k)`, где `n` — число строк, `k` — макс. длина. Альтернативный ключ — частотный массив, преобразованный в строку: `O(n · k)`, но больше memory overhead на ключи.


> [!mcq] Какой ключ HashMap для группировки анаграмм даёт `O(n · k)` (где `k` — длина строки) без сортировки?
>
> - [ ] A. `String.hashCode()` исходной строки — анаграммы дают одинаковый хеш.
>
>     **Что на самом деле.** `hashCode` зависит от порядка символов: `"abc"` и `"cba"` дают разные значения. Группировка по hashCode не объединит анаграммы.
>
>     **Откуда путаница.** Hash часто используется как универсальный «отпечаток», без учёта order-dependence.
>
>     **Если бы это было правдой.** Можно было бы группировать словарные анаграммы простой group-by по `s.hashCode()`, но это не работает.
>
>     **Как было бы правильно.** Признать, что String.hashCode не инвариантен относительно перестановок; нужен другой канонический ключ.
>
> - [ ] B. Сортированная строка как ключ — `O(n · k log k)`, единственный возможный подход.
>
>     **Что на самом деле.** Sorted key работает (`"act"` для `"cat"/"tac"/"act"`), но даёт `O(n · k log k)`. Альтернатива через частотные счётчики (`int[26]` → String или Tuple) даёт `O(n · k)` без log-фактора.
>
>     **Откуда путаница.** Sorted key — самый простой и популярный приём, и его часто называют «единственным».
>
>     **Если бы это было правдой.** LeetCode 49 не имел бы follow-up «What if we want O(n·k)?», но он подразумевается как улучшение.
>
>     **Как было бы правильно.** Признать, что sorted key даёт `O(n·k log k)`, а частотные счётчики — `O(n·k)`.
>
> - [x] C. Частотный массив `int[26]`, сериализованный в String (например, `"a2b1c0..."`) или представленный как `String.valueOf(count)` — даёт `O(k)` на ключ.
>
>     **Развёрнутое объяснение.** Для ASCII lowercase создаём массив `int[26]`: для каждой строки `s` считаем частоты символов за `O(k)`, превращаем массив в строку-ключ (например, `Arrays.toString(count)` или конкатенация `"a"+count[0]+"b"+count[1]+...`). Этот ключ инвариантен относительно перестановок: все анаграммы дают одинаковую строку. HashMap группирует. Итого `O(n · k)` время и `O(n · k)` память на ключи. Без log-фактора от сортировки.
>
>     **Пример.** `["eat","tea","tan","ate","nat","bat"]`. Для `"eat"`: count = `[1,0,...,1(e),...,1(t)]`, key = `"1,0,...,1,...,1"`. То же для `"tea"`, `"ate"` → одна группа. `"tan"`, `"nat"` → другая. `"bat"` → отдельная. Итог: `[["eat","tea","ate"], ["tan","nat"], ["bat"]]`.
>
>     **Когда применять.** LeetCode 49 Group Anagrams, кластеризация документов по bag-of-words без TF-IDF, поиск дубликатов в spell-checker dictionaries, объединение synonyms по freq-signature, дедупликация перестановок в combinatorial enumeration.
>
>     **Подводные камни.** Для unicode `int[26]` не работает — нужен `HashMap<Integer, Integer>` частот и его сериализация. Хеш-collision: если использовать обычный `int` hash от count-массива, разные массивы могут дать одинаковый хеш — лучше String-key. Память на ключи может быть значительной для длинных слов; trade-off с sorted-key (`O(k)` ключ против `O(k)` ключа, но без log на построение).
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q23]] is anagram; [[arrays-strings-interview#Q25]] longest substring без повторов; [[arrays-strings-interview#Q33]] string pool.
>
> - [ ] D. Простой `String.length()` — анаграммы одинаковой длины.
>
>     **Что на самом деле.** Длина — необходимое, но не достаточное условие. `"abc"` и `"def"` обе длины 3, но не анаграммы. Группировка по длине даст слишком крупные группы с false positives.
>
>     **Откуда путаница.** «Анаграммы одинаковой длины» — верное наблюдение, и его принимают за полный критерий.
>
>     **Если бы это было правдой.** LeetCode 49 принимал бы решение через `Collectors.groupingBy(String::length)`, но это даёт wrong answer.
>
>     **Как было бы правильно.** Признать, что длина — preliminary check; для полного group-by нужны частоты или sorted.

## Q25. (!) Самая длинная подстрока без повторов?

**Sliding window** + `HashMap` для отслеживания последнего вхождения.

```java
int lengthOfLongestSubstring(String s) {
    Map<Character, Integer> lastSeen = new HashMap<>();
    int maxLen = 0, left = 0;

    for (int right = 0; right < s.length(); right++) {
        char c = s.charAt(right);
        if (lastSeen.containsKey(c) && lastSeen.get(c) >= left) {
            left = lastSeen.get(c) + 1; // сдвигаем левую границу
        }
        lastSeen.put(c, right);
        maxLen = Math.max(maxLen, right - left + 1);
    }
    return maxLen;
}
```

Сложность `O(n)` время, `O(min(n, alphabet))` память. Для ASCII — `O(1)` память (массив 128).


> [!mcq] Как sliding window + HashMap даёт `O(n)` для «longest substring without repeating characters»?
>
> - [x] A. `right` расширяет окно; при дубликате прыгаем `left = max(left, lastSeen[c]+1)`; обновляем `lastSeen[c]=right` и `maxLen`.
>
>     **Развёрнутое объяснение.** Поддерживаем окно `[left, right]` с уникальными символами. `right` идёт вперёд, добавляя `s[right]`. Если `s[right]` уже встречался в текущем окне (`lastSeen[s[right]] >= left`), сдвигаем `left` до `lastSeen[s[right]] + 1` (за позицию предыдущего вхождения). После каждого шага обновляем `maxLen = max(maxLen, right - left + 1)` и записываем `lastSeen[s[right]] = right`. Каждый символ обрабатывается ≤ 2 раз (right movement + потенциальный left jump), общая `O(n)`. Память `O(min(n, alphabet))`.
>
>     **Пример.** `"abcabcbb"`: right=0(a), lastSeen={a:0}, max=1. right=1(b), {a:0,b:1}, max=2. right=2(c), {a:0,b:1,c:2}, max=3. right=3(a), lastSeen[a]=0≥left=0, left=1, {a:3,b:1,c:2}, max=3. right=4(b), lastSeen[b]=1≥1, left=2, {a:3,b:4,c:2}, max=3. right=5(c), lastSeen[c]=2≥2, left=3, max=3. right=6(b), lastSeen[b]=4≥3, left=5, max=3. right=7(b), lastSeen[b]=6≥5, left=7, max=3. Итог: 3 (`"abc"`).
>
>     **Когда применять.** LeetCode 3 Longest Substring Without Repeating, обработка stream-сессий без duplicate event types, longest unique-prefix в DNA sequencing, поиск longest unique URL-pattern в access-логах, deduplication windows в Kafka Streams.
>
>     **Подводные камни.** Условие `lastSeen[c] >= left` критично: символ мог встретиться **до** `left`, и он уже не в окне — игнорируем. Без проверки получится преждевременный сдвиг left и неверный ответ. Использовать массив `int[128]` (`int[]`-array, не HashMap) для ASCII даёт строго `O(1)` память + быстрее без autoboxing. Инициализация: `int[128]` заполнен нулями, что для empty string ассоциируется с `right=0` — лучше инициализировать `-1` для ясности.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q13]] subarray sum equals K; [[arrays-strings-interview#Q14]] sliding window technique; [[arrays-strings-interview#Q26]] longest palindromic substring.
>
> - [ ] B. Перебрать все подстроки через два вложенных цикла, для каждой проверить уникальность — `O(n²)`.
>
>     **Что на самом деле.** Brute force даёт `O(n²)` подстрок, плюс `O(n)` на проверку каждой — итого `O(n³)`. С HashSet проверка ускоряется до `O(1)` на символ, но число подстрок остаётся `O(n²)`.
>
>     **Откуда путаница.** Первое решение, которое приходит в голову; не понимают, что sliding window даёт линейность за счёт амортизации.
>
>     **Если бы это было правдой.** LeetCode 3 не относился бы к Medium с критерием линейности, но он именно такой.
>
>     **Как было бы правильно.** Признать, что brute force — `O(n²)` или хуже; sliding window — `O(n)` оптимум.
>
> - [ ] C. Динамическое программирование с `dp[i] = max длина unique-substring заканчивающейся на i`, переход через сравнение со всеми j<i.
>
>     **Что на самом деле.** DP-формулировка возможна, но прямолинейный переход `dp[i] = ...` требует look-back на все предыдущие, что даёт `O(n²)`. Можно оптимизировать через массив last positions — это и есть sliding window с другой нотацией.
>
>     **Откуда путаница.** DP — мощная техника, и студенты пытаются применить её даже там, где sliding window проще.
>
>     **Если бы это было правдой.** LeetCode 3 не имел бы решения без DP, но sliding window даёт линейность напрямую.
>
>     **Как было бы правильно.** Признать, что DP-формулировка существует, но оптимизация сводится к sliding window.
>
> - [ ] D. Trie дерево всех суффиксов: longest path без дубликатов — это ответ.
>
>     **Что на самом деле.** Trie построение для всех суффиксов даёт `O(n²)` память и время. Suffix Tree (Ukkonen) даёт `O(n)`, но overkill для этой задачи и сложен в реализации.
>
>     **Откуда путаница.** «Подстроки → Trie» — стандартная ассоциация для string-задач, но для unique-substring sliding window проще и эффективнее.
>
>     **Если бы это было правдой.** LeetCode 3 не входил бы в стандартный набор «sliding window» задач, но он именно там.
>
>     **Как было бы правильно.** Признать, что Trie/Suffix Tree — overkill; sliding window решает за `O(n)` без сложных структур.

## Q26. Самый длинный палиндром в строке?

**Expand around center** — для каждого индекса считаем максимальный палиндром с центром в нём (для чётных и нечётных длин). `O(n²)`.

```java
String longestPalindrome(String s) {
    int start = 0, end = 0;

    for (int i = 0; i < s.length(); i++) {
        int len1 = expand(s, i, i);     // нечётная длина
        int len2 = expand(s, i, i + 1); // чётная длина
        int len = Math.max(len1, len2);

        if (len > end - start) {
            start = i - (len - 1) / 2;
            end = i + len / 2;
        }
    }
    return s.substring(start, end + 1);
}

int expand(String s, int left, int right) {
    while (left >= 0 && right < s.length() && s.charAt(left) == s.charAt(right)) {
        left--;
        right++;
    }
    return right - left - 1;
}
```

Альтернатива — **алгоритм Манакера** — `O(n)`, но сложен в реализации. На собеседовании обычно ожидают `expand around center`.


> [!mcq] Почему в «expand around center» для longest palindromic substring нужно пробовать **два** разных центра на каждой позиции?
>
> - [x] A. Палиндромы бывают нечётной длины (центр — один символ, `aba`) и чётной (центр — два символа, `abba`); один индекс не покрывает оба случая.
>
>     **Развёрнутое объяснение.** Палиндром длины L с центром в позиции `i` для нечётного L начинается и кончается в той же букве `s[i-k..i+k]`. Для чётного L «центр» лежит между двумя одинаковыми буквами `s[i..i+1]`. Поэтому для каждого индекса `i` пробуем оба: `expand(i, i)` (odd-length, начало one symbol) и `expand(i, i+1)` (even-length, начало two symbols). Из двух берём максимум. Время `O(n²)` worst case (каждый `expand` — `O(n)`), память `O(1)`.
>
>     **Пример.** `"abba"`. i=0: expand(0,0) → `"a"` len=1, expand(0,1) → `a≠b`, len=0. i=1: expand(1,1) → `"b"` len=1, expand(1,2) → `s[1]=b, s[2]=b`, расширяемся → `s[0]=a, s[3]=a`, расширяемся → за пределы, len=4! i=2: expand(2,2) → `"b"` len=1, expand(2,3) → `b≠a`, len=0. i=3: expand(3,3) → `"a"` len=1. Максимум: 4 (`"abba"`).
>
>     **Когда применять.** LeetCode 5 Longest Palindromic Substring, поиск palindromic regions в DNA (восстанавливающие последовательности), валидация palindrome-rules в crypto (хеш-функции, не считающие палиндромы), парсинг symmetric tokens, обнаружение мирror-структур в логах.
>
>     **Подводные камни.** `expand` возвращает `right - left - 1`, потому что после цикла `left` и `right` указывают за границы палиндрома. Расчёт `start = i - (len - 1) / 2` и `end = i + len / 2` — для odd `(len-1)/2 = len/2`, для even — асимметрично. Алгоритм Manacher даёт `O(n)`, но сложнее: добавляет separator-символы (`#a#b#a#`), потом single expand с reuse предыдущих радиусов. Empty string — палиндром длины 0 по соглашению.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q22]] is palindrome two-pointers; [[arrays-strings-interview#Q21]] string reverse; [[arrays-strings-interview#Q25]] longest substring без повторов.
>
> - [ ] B. Это для thread-safety: два expand могут выполняться параллельно.
>
>     **Что на самом деле.** Алгоритм single-threaded; два `expand` выполняются последовательно для каждого `i`. Concurrency — не аргумент.
>
>     **Откуда путаница.** Java-разработчики думают о parallelism, но в стандартном expand-around-center нет shared state.
>
>     **Если бы это было правдой.** Без второго expand параллельность была бы недостижима, но реально и single-thread требует двух вызовов.
>
>     **Как было бы правильно.** Признать, что два expand — для покрытия odd/even длин, а не для concurrency.
>
> - [ ] C. Один из expand используется для верификации, а другой — для поиска; это защита от off-by-one.
>
>     **Что на самом деле.** Оба expand'а равноценны и оба ищут палиндром, просто с разными центрами. Один — для odd-length, другой — для even-length. Никакой «верификации» нет.
>
>     **Откуда путаница.** Студенты, не понимая логики odd/even, придумывают объяснение через «дублирование для надёжности».
>
>     **Если бы это было правдой.** Можно было бы обойтись одним expand, но это пропускало бы все палиндромы чётной длины.
>
>     **Как было бы правильно.** Сказать, что оба expand равноценны: один ловит odd, другой even; пропуск любого = потеря части палиндромов.
>
> - [ ] D. Второй expand нужен только для не-ASCII строк (Unicode); для ASCII достаточно первого.
>
>     **Что на самом деле.** Логика odd/even палиндромов не зависит от кодировки. `"abba"` (ASCII) и `"абба"` (Unicode) оба требуют even-length expand. Encoding тут не аргумент.
>
>     **Откуда путаница.** Unicode часто всплывает как «особый случай», и его инстинктивно приписывают любым string-задачам.
>
>     **Если бы это было правдой.** ASCII-only `"abba"` не находился бы — но он находится `[expand(1,2) и расширяемся]`.
>
>     **Как было бы правильно.** Признать, что два expand нужны для любых строк (ASCII и Unicode) — это про odd/even длину, не про кодировку.

## Q27. (!) Поиск подстроки — алгоритм KMP?

**KMP (Knuth-Morris-Pratt)** — поиск подстроки длины `m` в тексте длины `n` за `O(n + m)`. Использует **префиксную функцию** для пропуска повторных сравнений.

```java
int kmpSearch(String text, String pattern) {
    if (pattern.isEmpty()) return 0;

    int[] lps = computeLPS(pattern);
    int i = 0, j = 0;

    while (i < text.length()) {
        if (text.charAt(i) == pattern.charAt(j)) {
            i++; j++;
            if (j == pattern.length()) return i - j;
        } else if (j > 0) {
            j = lps[j - 1]; // используем префикс-функцию
        } else {
            i++;
        }
    }
    return -1;
}

int[] computeLPS(String pattern) {
    int[] lps = new int[pattern.length()];
    int len = 0, i = 1;

    while (i < pattern.length()) {
        if (pattern.charAt(i) == pattern.charAt(len)) {
            lps[i++] = ++len;
        } else if (len > 0) {
            len = lps[len - 1];
        } else {
            lps[i++] = 0;
        }
    }
    return lps;
}
```

`lps[i]` — длина наибольшего префикса, который также является суффиксом для `pattern[0..i]`. Препроцессинг `O(m)`, поиск `O(n)`.

В стандартной библиотеке `String.indexOf()` использует **наивный алгоритм** `O(n·m)`. Для частых поисков по большим текстам — KMP или Aho-Corasick (поиск множества образцов).


> [!mcq] Что хранит массив `lps` (longest prefix that is also suffix) в алгоритме KMP?
>
> - [x] A. `lps[i]` — длина наибольшего собственного префикса `pattern[0..i]`, который также является суффиксом этого подобразца; используется для пропуска повторных сравнений при mismatch.
>
>     **Развёрнутое объяснение.** При несовпадении символа в позиции `j` паттерна (где-то посередине match-а) наивный поиск откатывает `i` на `i - j + 1` и `j` на `0` — теряет всю проделанную работу. KMP знает, что префикс `pattern[0..j-1]` уже совпал в тексте; внутри этого префикса есть «зеркало»: суффикс длины `lps[j-1]` равен префиксу той же длины. Значит, можно перепрыгнуть на `j = lps[j-1]` без отката `i`. Препроцессинг массива `lps` — `O(m)`, поиск — `O(n+m)`.
>
>     **Пример.** `pattern = "ABABAC"`, lps = `[0,0,1,2,3,0]`. lps[0]=0 (нет собственного префикса). lps[1]=0 (`AB` — нет общего). lps[2]=1 (`ABA` → `A`). lps[3]=2 (`ABAB` → `AB`). lps[4]=3 (`ABABA` → `ABA`). lps[5]=0 (`ABABAC` → C ломает). При поиске в тексте `"ABABABAC"`: совпадение до `j=5`, mismatch (`A` ≠ `C`); `j = lps[4] = 3`, продолжаем сравнение `pattern[3]=B` с текущим `text[5]=A` — снова mismatch, `j = lps[2] = 1`, и т.д. Без отката `i`.
>
>     **Когда применять.** LeetCode 28 Find First Occurrence, мульти-pattern search (Aho-Corasick расширение KMP), DNA-секвенции (motif search), grep на больших файлах с одним pattern, антивирусные сигнатуры (хотя в проде чаще Boyer-Moore), text editors search-and-replace.
>
>     **Подводные камни.** Префикс должен быть **собственным** (не равным всей строке), иначе lps[i] = i+1 для строки `"aaaa"` всегда — алгоритм зациклится. Правильно: `lps[3] = 3` для `"aaaa"` (префикс `"aaa"` суффикс `"aaa"`). Computing lps — задача с двумя указателями: `len` для длины current match, `i` для позиции. Standard implementation: при mismatch `len = lps[len-1]` (рекурсивный отступ).
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q28]] Rabin-Karp; [[arrays-strings-interview#Q22]] is palindrome; [[arrays-strings-interview#Q26]] longest palindromic substring.
>
> - [ ] B. `lps[i]` — индекс последнего вхождения символа `pattern[i]` в pattern.
>
>     **Что на самом деле.** Last-occurrence таблица — это часть Boyer-Moore (bad character heuristic), не KMP. У KMP принципиально другая структура: запоминает префикс-суффикс соотношения внутри pattern.
>
>     **Откуда путаница.** Boyer-Moore и KMP — оба string-matching, и студенты путают их таблицы.
>
>     **Если бы это было правдой.** KMP не работал бы быстрее brute force, но он именно `O(n+m)` благодаря prefix-function.
>
>     **Как было бы правильно.** Признать, что Boyer-Moore использует last-occurrence, KMP — prefix function (lps).
>
> - [ ] C. `lps[i]` — количество вхождений pattern в text до позиции `i`.
>
>     **Что на самом деле.** `lps` строится **только из pattern**, без участия text. Это свойство pattern, не результат matching.
>
>     **Откуда путаница.** Студенты, не понимающие preprocessing-vs-search divide, путают input для каждого этапа.
>
>     **Если бы это было правдой.** Препроцессинг требовал бы text, что противоречит идее «подготовить pattern один раз, искать в разных текстах».
>
>     **Как было бы правильно.** Сказать, что lps строится из pattern (preprocessing), и потом используется для search в любом text.
>
> - [ ] D. `lps[i]` — длина паттерна для подстроки, hashCode которой совпадает с pattern.
>
>     **Что на самом деле.** Хеш-сравнение — это Rabin-Karp, не KMP. KMP не использует хеши, работает напрямую с префиксной функцией.
>
>     **Откуда путаница.** Rabin-Karp и KMP — оба `O(n+m)`-алгоритмы (в среднем), их часто упоминают вместе.
>
>     **Если бы это было правдой.** lps зависел бы от hashCode, что давало бы collisions и false positives — но KMP детерминирован.
>
>     **Как было бы правильно.** Признать, что хеши — это Rabin-Karp; KMP использует собственную функцию префикса без хеширования.

## Q28. (!) Алгоритм Рабина-Карпа?

**Rabin-Karp** — поиск подстроки через хеширование. Использует **rolling hash** для быстрого пересчёта при сдвиге окна. Среднее `O(n + m)`, худшее `O(n·m)`.

```java
int rabinKarp(String text, String pattern) {
    int n = text.length(), m = pattern.length();
    if (m > n) return -1;

    long base = 256, mod = 1_000_000_007L;
    long patternHash = 0, windowHash = 0, h = 1;

    for (int i = 0; i < m - 1; i++) h = (h * base) % mod;

    for (int i = 0; i < m; i++) {
        patternHash = (patternHash * base + pattern.charAt(i)) % mod;
        windowHash  = (windowHash  * base + text.charAt(i))    % mod;
    }

    for (int i = 0; i <= n - m; i++) {
        if (patternHash == windowHash && text.regionMatches(i, pattern, 0, m)) {
            return i; // hash match + verify
        }
        if (i < n - m) {
            windowHash = (base * (windowHash - text.charAt(i) * h)
                          + text.charAt(i + m)) % mod;
            if (windowHash < 0) windowHash += mod;
        }
    }
    return -1;
}
```

**Применение:** поиск нескольких образцов одной длины (хеши хранятся в `HashSet`), плагиат-детекторы, поиск дубликатов в файлах.


> [!mcq] Почему Rabin-Karp в среднем `O(n+m)`, но в худшем случае деградирует до `O(n·m)`?
>
> - [x] A. Среднее `O(n+m)` достигается благодаря rolling hash (`O(1)` пересчёт); худший случай — когда хеши часто совпадают, требуя посимвольной верификации (`O(m)` на каждое окно).
>
>     **Развёрнутое объяснение.** Rolling hash считает хеш окна длины `m` за `O(1)` через формулу `hash = (hash - text[i]*base^(m-1)) * base + text[i+m]`. Это даёт `O(n)` для сканирования всех окон + `O(m)` для preprocessing pattern. Если хеши не совпадают — пропускаем без проверки. Если совпали — проверяем посимвольно (`O(m)`) для защиты от collision. На «хорошем» хеше (mod большое простое, base ≥ alphabet) collisions редки, среднее `O(n+m)`. Но при искусственном паттерне (например, все символы одинаковые в специально подобранной строке) collisions могут случаться на каждом окне — `O(n·m)`.
>
>     **Пример.** `text="aaaaa"`, `pattern="aaa"`. Хеши всех окон одинаковы (потому что все символы `a`), на каждом окне делаем verification — `O(n·m)`. На случайных текстах с разнообразным алфавитом collisions редки, и почти все окна skip'аются за `O(1)`.
>
>     **Когда применять.** Multi-pattern search (несколько паттернов одной длины, хеши хранятся в HashSet), плагиат-детекторы (поиск дубликатов абзацев в корпусе), find similar files через chunked hashes (rsync), детекция repeated substrings в DNA с known length, Aho-Corasick alternative для специальных случаев.
>
>     **Подводные камни.** Mod должен быть большим простым (например, `10^9+7`) для уменьшения collisions, но `(hash * base) % mod` всё ещё в `long` — overflow возможен на `int`. Negative values после mod операции: добавь `mod` для нормализации. Для multi-pattern Rabin-Karp с разными длинами — нужно разное preprocessing. Hash bias: некоторые base/mod комбинации дают плохое распределение — выбирай тщательно.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q27]] KMP; [[arrays-strings-interview#Q24]] group anagrams (тоже использует хеш-ключи); [[arrays-strings-interview#Q33]] string pool.
>
> - [ ] B. Rabin-Karp всегда `O(n)`, потому что hash сравнения занимают константное время.
>
>     **Что на самом деле.** Hash сравнение `O(1)`, но verification после hash match — `O(m)`. Без verification получишь wrong answer на collision. С verification — worst case `O(n·m)` при патологических входах.
>
>     **Откуда путаница.** «Hash = O(1)» — мем; забывают про collision verification.
>
>     **Если бы это было правдой.** Не нужна была бы verification, но без неё false positives = wrong answer.
>
>     **Как было бы правильно.** Признать, что hash compare — `O(1)`, но verification — `O(m)`; средний `O(n+m)`, худший `O(n·m)`.
>
> - [ ] C. Сложность всегда зависит от длины алфавита `Σ`, и для большого Σ становится `O(n·Σ)`.
>
>     **Что на самом деле.** Σ влияет на качество хеша (большой base = редкие collisions), но не на time complexity напрямую. Сложность характеризуется через collision frequency, не размер алфавита.
>
>     **Откуда путаница.** «Длина алфавита» — параметр в некоторых string-алгоритмах (Aho-Corasick, KMP), и его инстинктивно прилагают везде.
>
>     **Если бы это было правдой.** Rabin-Karp для Unicode (Σ = 65536) был бы непригоден, но он работает на любом алфавите.
>
>     **Как было бы правильно.** Признать, что Σ влияет на качество хеша, а не на time complexity напрямую.
>
> - [ ] D. Худший случай возникает только когда pattern длиннее text — в этом случае ответ всегда `-1`.
>
>     **Что на самом деле.** Если `m > n`, ответ `-1` определяется за `O(1)` early check. Худший случай Rabin-Karp возникает при `m <= n` с patological collisions на каждом окне.
>
>     **Откуда путаница.** Edge case `m > n` иногда называют «худшим», хотя он тривиален.
>
>     **Если бы это было правдой.** Не было бы патологических инпутов для случая `m < n`, но они есть (`"aaaa..."` с `"aaa"`).
>
>     **Как было бы правильно.** Сказать, что `m > n` — тривиальный edge case; худший случай — collision-heavy внутри `m <= n`.

## Q29. Сравнение двух строк с учётом backspace?

`#` — обозначает backspace. Сравнить строки после применения backspaces.

```java
// O(n+m) время, O(1) память — идём с конца
boolean backspaceCompare(String s, String t) {
    int i = s.length() - 1, j = t.length() - 1;

    while (i >= 0 || j >= 0) {
        i = nextValidChar(s, i);
        j = nextValidChar(t, j);

        if (i < 0 && j < 0) return true;
        if (i < 0 || j < 0) return false;
        if (s.charAt(i) != t.charAt(j)) return false;
        i--; j--;
    }
    return true;
}

int nextValidChar(String s, int i) {
    int skip = 0;
    while (i >= 0) {
        if (s.charAt(i) == '#') { skip++; i--; }
        else if (skip > 0) { skip--; i--; }
        else return i;
    }
    return -1;
}
```

Альтернатива — построить итоговые строки через `StringBuilder` или стек: `O(n+m)` память.


> [!mcq] Почему сравнение строк с backspace-символами через два указателя с конца даёт `O(1)` память (вместо стека)?
>
> - [x] A. Идём с конца: на каждом шаге skip-pattern (`# → pop`) обрабатывается локально через счётчик, не требуя стека для хранения «отменённых» символов.
>
>     **Развёрнутое объяснение.** Backspace `#` отменяет предыдущий символ. Прямой подход — построить итоговые строки через `StringBuilder` (стек pop при `#`), `O(n+m)` память. Оптимум: идти с конца, поддерживая счётчик `skip`. При встрече `#` инкрементируем skip. При обычном символе — если skip > 0, декрементируем (это символ, который будет удалён); иначе это валидный символ. Helper `nextValidChar` находит следующий valid index. На главном уровне сравниваем `s[i]` и `t[j]` через эти helpers. Память — две int переменные на каждую строку, итого `O(1)`.
>
>     **Пример.** `s="ab#c"`, `t="ad#c"`. i=3(`c`), j=3(`c`), совпали, i=2, j=2. i=2(`#`), skip=1, i=1, skip=0, i=0 (`a` пропускаем не, skip=0). Нет, нюанс: `s="ab#c"` → idx 3 `c`, 2 `#`, 1 `b`, 0 `a`. Идём: i=3, nextValid(3) → `c`. j=3, nextValid(3) → `c`. Равны, i=2, j=2. nextValid(2): `s[2]=#`, skip=1, i=1, skip=0, i=0 → `a`. nextValid(2) для t: `t[2]=#`, skip=1, j=1, skip=0, j=0 → `a`. Равны, i=-1, j=-1, return true.
>
>     **Когда применять.** LeetCode 844 Backspace String Compare, сравнение пользовательского ввода в text-editor с undo-операциями, валидация diff-операций в Git, симуляция redo/undo в command pattern, IDE auto-completion при typo correction.
>
>     **Подводные камни.** Условия цикла: `while (i >= 0 || j >= 0)` (не `&&`, иначе пропустишь хвост одной строки). При выходе из `nextValidChar` — возвращай `-1`, если строка кончилась. Сравнение должно быть **внутри** цикла, после вычисления `i` и `j`. Multi-character backspace (например, `##`) обрабатывается естественно через накопление `skip`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q4]] remove duplicates two-pointers; [[arrays-strings-interview#Q23]] is anagram; [[arrays-strings-interview#Q36]] avoid IOOB in two-pointers.
>
> - [ ] B. Используется один указатель и одна переменная — `s.charAt(i)` достаточно для всего.
>
>     **Что на самом деле.** Один указатель не позволяет двигаться по двум строкам параллельно; нужны минимум два (по одному на строку). Плюс счётчик skip на каждую.
>
>     **Откуда путаница.** «Минимизировать переменные» — благое намерение, но недостаточное условие корректности.
>
>     **Если бы это было правдой.** Алгоритм не различал бы s и t, что некорректно для compare-задачи.
>
>     **Как было бы правильно.** Сказать, что нужны два указателя (`i, j`) + два skip-счётчика; всего 4 int — это `O(1)`.
>
> - [ ] C. Применяется regex `\\w#` для удаления символов перед `#`; результат сравнивается через `equals`.
>
>     **Что на самом деле.** Regex работает, но даёт `O(n)` память на промежуточные String (новые объекты от replace). Плюс regex engine добавляет overhead в 5-10x против двух указателей.
>
>     **Откуда путаница.** Regex — выразительный приём, и его пытаются применять для всех string-преобразований.
>
>     **Если бы это было правдой.** LeetCode 844 не имел бы follow-up «Could you solve in O(n) time AND O(1) space?», но он есть.
>
>     **Как было бы правильно.** Признать, что regex даёт `O(n)` память на новые String; для `O(1)` нужен two-pointers from end.
>
> - [ ] D. Используется HashMap для хранения позиций `#` и применения backspace в lookup-фазе.
>
>     **Что на самом деле.** HashMap `O(n)` память. Альтернативный подход через stack даёт `O(n)`. Two-pointers from end — единственный `O(1)`.
>
>     **Откуда путаница.** HashMap — универсальный инструмент, и его инстинктивно выбирают для трекинга «состояний».
>
>     **Если бы это было правдой.** Не было бы преимущества two-pointers from end, но в LeetCode именно он считается optimal.
>
>     **Как было бы правильно.** Сказать, что HashMap/stack дают `O(n)` память; для `O(1)` нужно scanning с конца с локальным skip-счётчиком.

## Q30. (!) Поменять два числа без временной переменной?

```java
// Через XOR — без переполнения, работает для целых
void swapXor(int[] arr, int i, int j) {
    if (i == j) return; // важно! XOR с собой даёт 0
    arr[i] = arr[i] ^ arr[j];
    arr[j] = arr[i] ^ arr[j];
    arr[i] = arr[i] ^ arr[j];
}

// Через арифметику — риск переполнения
void swapArith(int[] arr, int i, int j) {
    arr[i] = arr[i] + arr[j];
    arr[j] = arr[i] - arr[j];
    arr[i] = arr[i] - arr[j];
}
```

В реальном коде используют временную переменную — это читабельнее. XOR-трюк показывает понимание побитовых операций. Подробнее — в [Java Types](../../programming-languages/java/java-types-interview.md).


> [!mcq] Почему XOR-swap (`a^=b; b^=a; a^=b`) безопаснее арифметического (`a=a+b; b=a-b; a=a-b`) для произвольных integer?
>
> - [x] A. XOR работает побитно без переноса — нет риска переполнения; арифметика на `Integer.MAX_VALUE + 1` даёт overflow и неверный результат.
>
>     **Развёрнутое объяснение.** Арифметический swap основан на свойстве суммы: `(a+b) - b = a`. Но `a + b` может превысить `Integer.MAX_VALUE` (2^31 - 1), вызывая wrap-around в Java (silent overflow). После `b = a - b` получим неверное значение. XOR работает побитно: каждый бит результата зависит только от соответствующих битов входов, без переноса в соседние. `a^b^b = a` всегда математически точно, независимо от значений. Это делает XOR-swap безопасным для любых `int`.
>
>     **Пример.** `a=Integer.MAX_VALUE, b=1`. Арифметика: `a = MAX + 1 = Integer.MIN_VALUE` (overflow). `b = MIN - 1 = MAX` (ещё overflow, но математически правильно). `a = MIN - MAX = MIN - MAX = 1` (третья операция). Случайно сработало, но опасно. XOR: `a^b^b = MAX, b^a = 1` — гарантировано правильно без overflow.
>
>     **Когда применять.** Низкоуровневые алгоритмы с жёсткими memory constraints (embedded), битовые операции в graphics (XOR-cursor), демонстрация на интервью знания bitwise. В production-коде Java чаще используют `int tmp = a; a = b; b = tmp;` — читаемее и без edge cases (`i == j` для XOR-swap обнуляет элемент).
>
>     **Подводные камни.** Если `a` и `b` — **одна и та же** переменная (одинаковый адрес/индекс), XOR-swap обнулит её: `a ^= a → 0`, потом `a ^= 0 → 0`. Это критично при `swap(arr, i, i)`. Производительность: на современных CPU обычный swap через регистр быстрее (XOR требует 3 операции vs 3 mov + tmp register). Java JIT обычно оптимизирует обычный swap лучше.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q9]] single number через XOR; [[arrays-strings-interview#Q11]] missing number XOR; [[arrays-strings-interview#Q32]] степень двойки.
>
> - [ ] B. XOR работает быстрее, потому что на CPU выполняется за 1 cycle, а арифметика — за 3-4.
>
>     **Что на самом деле.** Современный x86 CPU выполняет и XOR, и ADD за 1 cycle. Скорость не является преимуществом XOR-swap. Реальное преимущество — отсутствие overflow.
>
>     **Откуда путаница.** «Битовые операции = быстро» — миф из времён, когда CPU действительно различались по сложности операций.
>
>     **Если бы это было правдой.** Бенчмарки показывали бы win XOR-swap, но реальные JMH-тесты показывают разницу в пределах шума.
>
>     **Как было бы правильно.** Признать, что разница в скорости минимальна; преимущество — overflow safety.
>
> - [ ] C. XOR-swap единственный способ обмена без временной переменной — арифметический невозможен.
>
>     **Что на самом деле.** Арифметический swap **возможен**, но имеет overflow-проблему. Это два эквивалентных по математике подхода, оба без tmp; различаются по безопасности и читаемости.
>
>     **Откуда путаница.** На лекциях часто показывают XOR-swap как «уникальный трюк», забывая арифметический аналог.
>
>     **Если бы это было правдой.** Учебники не упоминали бы арифметический swap, но он часто приводится как первый вариант.
>
>     **Как было бы правильно.** Признать, что оба варианта существуют; XOR безопаснее по overflow.
>
> - [ ] D. XOR-swap работает только для целых, а арифметический — для любых типов, включая `float`.
>
>     **Что на самом деле.** XOR работает на любых fixed-bit-width типах: `int`, `long`, `byte`, `short`. Для `float`/`double` XOR-swap технически возможен через `Float.floatToIntBits`, но это нестандартно. Арифметический swap для `float` имеет проблемы precision: `(a+b) - b ≠ a` для floating-point из-за потери mantissa-битов.
>
>     **Откуда путаница.** Студенты ассоциируют XOR только с целыми, забывая, что арифметика на float'ах тоже имеет свои подводные камни.
>
>     **Если бы это было правдой.** XOR-swap был бы неприменим для `long`, но он применим (`long` поддерживает `^=`).
>
>     **Как было бы правильно.** Сказать, что XOR работает на integer-типах; для float ни один из этих swap'ов не идеален из-за precision/overflow.

## Q31. Перевод числа в произвольную систему счисления?

```java
String decimalToBase(int number, int base) {
    if (number == 0) return "0";
    StringBuilder sb = new StringBuilder();
    boolean negative = number < 0;
    number = Math.abs(number);

    while (number > 0) {
        int remainder = number % base;
        sb.append(remainder < 10 ? (char)('0' + remainder)
                                  : (char)('A' + remainder - 10));
        number /= base;
    }
    if (negative) sb.append('-');
    return sb.reverse().toString();
}

// Встроенные методы Java:
String binary = Integer.toString(42, 2);   // "101010"
String hex    = Integer.toString(42, 16);  // "2a"
int back      = Integer.parseInt("101010", 2); // 42
```

Минимальная база — 2, максимальная для `Integer.toString` — 36 (`Character.MAX_RADIX`).


> [!mcq] Какие границы поддерживает встроенный `Integer.toString(int, radix)` для основания счисления?
>
> - [x] A. От 2 (`Character.MIN_RADIX`) до 36 (`Character.MAX_RADIX`); 36 потому что 10 цифр + 26 латинских букв.
>
>     **Развёрнутое объяснение.** `Integer.toString(num, radix)` использует цифровое представление: 0-9 для значений 0-9, и A-Z (или a-z в lowercase) для значений 10-35. Итого 10+26=36 символов. Минимум 2 — это binary; меньше 2 не имеет смысла (унарная система требует другого подхода). Если radix вне `[2, 36]`, Java fallback'ит на radix 10 (silently!) без exception, что может скрыть баги.
>
>     **Пример.** `Integer.toString(255, 16)` → `"ff"` (hex). `Integer.toString(255, 2)` → `"11111111"` (binary). `Integer.toString(255, 36)` → `"73"` (3*36 + 7*1 + ... фактически `73` означает `7*36 + 3 = 255`). `Integer.toString(255, 50)` → `"255"` (silent fallback на radix 10!).
>
>     **Когда применять.** Конвертация для отображения (hex для memory dumps, binary для битовых масок), URL-shortening (base 62: 0-9, a-z, A-Z через ручную реализацию), encoding для compact representation чисел в строки (base 36 для коротких ID), debug numbers в нестандартных системах.
>
>     **Подводные камни.** Silent fallback при `radix < 2 || radix > 36` — Java не бросает exception, использует 10. Для base > 36 нужен custom код (например, base 62 для URL-short). Отрицательные числа: `Integer.toString(-1, 2)` → `"-1"` (с минусом), не two's-complement representation. Для работы с two's-complement bit pattern используй `Integer.toBinaryString(num)`, которая возвращает 32-битное представление без минуса.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q32]] is power of two; [[arrays-strings-interview#Q33]] string equality; [[arrays-strings-interview#Q35]] StringBuilder.
>
> - [ ] B. От 2 до 16 — максимум hex, потому что выше слишком сложно для людей читать.
>
>     **Что на самом деле.** Hex (16) — частая система, но не максимальная. Java поддерживает до 36, что используется в base36 encoding (короткие URL-short ID).
>
>     **Откуда путаница.** Hex часто упоминается как «верхняя граница в практике», но JDK даёт больше.
>
>     **Если бы это было правдой.** `Integer.toString(num, 36)` бросало бы exception, но оно работает корректно для 36.
>
>     **Как было бы правильно.** Признать, что JDK поддерживает 2-36; 16 — частая, но не максимум.
>
> - [ ] C. От 0 до 64 — максимум определяется `Long.SIZE` для 64-битных систем.
>
>     **Что на самом деле.** Radix не имеет отношения к bit-size типа. 64 — это длина `long`, не основание системы счисления. Максимум 36 определяется количеством стандартных символов (0-9 + A-Z = 36).
>
>     **Откуда путаница.** Студенты путают «количество битов» и «основание счисления».
>
>     **Если бы это было правдой.** Можно было бы записать число в base 50, используя символы за пределами A-Z, но стандарт ограничивает 36.
>
>     **Как было бы правильно.** Сказать, что radix 2-36 ограничен буквенно-цифровым алфавитом; bit-size типа здесь не аргумент.
>
> - [ ] D. От 10 до 16 — основания, которые человек может читать естественно.
>
>     **Что на самом деле.** Java поддерживает от 2 (binary), что меньше 10. Бинарные представления критичны для битовых операций и debugging.
>
>     **Откуда путаница.** «Естественные системы» — субъективное представление; JDK ориентирован на технические потребности, включая binary.
>
>     **Если бы это было правдой.** `Integer.toBinaryString` не существовал бы, но он часто используется.
>
>     **Как было бы правильно.** Признать, что binary (radix 2) полностью поддерживается; диапазон 2-36 покрывает все технические нужды.

## Q32. Проверка степени двойки?

```java
boolean isPowerOfTwo(int n) {
    return n > 0 && (n & (n - 1)) == 0;
}
```

**Идея:** степень двойки в двоичной записи имеет ровно один бит. `n - 1` инвертирует все биты после младшего единичного, поэтому `n & (n - 1) = 0` только для степеней двойки (и для `n = 0`, поэтому проверяем `n > 0`).

Для `n = 0` нужно явно вернуть `false`. Для отрицательных тоже `false`.


> [!mcq] Почему трюк `n > 0 && (n & (n - 1)) == 0` корректно определяет степени двойки?
>
> - [ ] A. `n & (n - 1)` удваивает `n`; для степени двойки удвоение даёт ноль из-за специфики битовой арифметики.
>
>     **Что на самом деле.** `n & (n-1)` НЕ удваивает; AND — побитовая операция «и», она зануляет биты. Удвоение — это сдвиг влево (`n << 1`) или умножение на 2.
>
>     **Откуда путаница.** Студенты, не знакомые с битовой логикой, придумывают арифметические объяснения.
>
>     **Если бы это было правдой.** `(n & (n-1))` для `n=4` давало бы `8`, но реально даёт `0`.
>
>     **Как было бы правильно.** Признать, что AND зануляет биты; для степени двойки это даёт `0`.
>
> - [ ] B. Это проверка через `log2(n) == floor(log2(n))` — алгебраическое определение степени двойки.
>
>     **Что на самом деле.** Алгебраическая проверка через `log2` работает математически, но требует float-операции, что медленнее и имеет precision-проблемы. Битовый трюк — целочисленный и точный.
>
>     **Откуда путаница.** Математическое определение «степень двойки = `n = 2^k` для целого `k`» подразумевает log2, и его пытаются применить в коде.
>
>     **Если бы это было правдой.** Решение через `Math.log` было бы канонично, но bit trick предпочитается из-за integer-арифметики.
>
>     **Как было бы правильно.** Признать, что log-проверка возможна, но имеет precision-issues; bit-trick точнее.
>
> - [ ] C. Проверка через `Integer.bitCount(n) == 1` — это и есть тот же алгоритм, просто в другой нотации.
>
>     **Что на самом деле.** `Integer.bitCount(n) == 1` — корректная альтернатива, но это **другая** реализация (popcount instruction), не «тот же алгоритм». `bitCount` внутри использует SWAR-трюки или native `POPCNT` инструкцию.
>
>     **Откуда путаница.** Оба решения дают одинаковый результат, и их часто называют «эквивалентными» вместо «разных».
>
>     **Если бы это было правдой.** Метод `Integer.bitCount` был бы реализован через `n & (n-1)`, но реально использует hardware POPCNT.
>
>     **Как было бы правильно.** Признать, что `bitCount == 1` — альтернативная реализация той же проверки, но через другую механику.
>
> - [x] D. Степень двойки в двоичной записи — ровно один установленный бит; `n - 1` инвертирует все биты после младшего единичного, поэтому `n & (n - 1)` обнулит все биты, давая 0.
>
>     **Развёрнутое объяснение.** Любая степень двойки имеет вид `2^k = 100...0` в двоичной записи (один единичный бит в позиции `k`). Вычитание единицы: для `2^k` получаем `2^k - 1 = 011...1` (нули до позиции `k`, единицы до позиции 0). Побитовое AND: `100...0 & 011...1 = 000...0`. Для любого другого числа есть хотя бы два единичных бита; вычитание изменит только младший единичный, остальные сохранятся, и AND даст ненулевое значение. Проверка `n > 0` нужна, потому что `0` тоже даст `0 & -1 = 0`, но `0` не считается степенью двойки.
>
>     **Пример.** `n=8`: `1000 & 0111 = 0000` → true. `n=7`: `0111 & 0110 = 0110 ≠ 0` → false. `n=1`: `0001 & 0000 = 0` → true (`2^0 = 1`). `n=0`: `0 & -1` (`-1` это все единицы в two's complement) = `0`, но `n > 0` отсекает.
>
>     **Когда применять.** Проверка hash-table capacity (Java HashMap требует степень двойки для бит-маски в `tab[(n-1) & hash]`), validate buffer sizes (ring buffers с modulo через AND), проверка power-of-two alignment в memory allocators, оптимизация в bit-shifting кодеках (видео-encoding).
>
>     **Подводные камни.** Для отрицательных чисел: в Java `int` 32-битный signed, `n=-2147483648` (`MIN_VALUE`) представлен как `10000000_00000000_00000000_00000000` — один установленный бит. Без `n > 0` алгоритм скажет «степень двойки», что неверно (отрицательные не степени двойки в стандартном понимании). Также не работает для `long` без замены `(n-1)` на `(n-1L)` — overflow при `Long.MIN_VALUE`.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q9]] single number через XOR; [[arrays-strings-interview#Q30]] XOR-swap; [[arrays-strings-interview#Q11]] missing number.

## Q33. (!) Почему == для строк работает не как ожидается?

`==` сравнивает **ссылки**, а не содержимое. У строк это работает только для **interned** строк (литералов в string pool):

```java
String a = "hello";
String b = "hello";
a == b;  // true — обе ссылаются на pool

String c = new String("hello");
a == c;  // false — c в куче, не в pool

a.equals(c);  // true — содержимое одинаковое

c.intern() == a;  // true — intern возвращает ссылку из pool
```

**Правильно:** всегда использовать `.equals()` или `Objects.equals()` для строк (защита от NPE).

Подробнее — в [Java String](../../programming-languages/java/java-string-interview.md).


> [!mcq] Почему `"hello" == "hello"` в Java возвращает `true`, а `new String("hello") == "hello"` — `false`?
>
> - [x] A. Литералы `"hello"` берутся из String pool (одинаковая ссылка), а `new String("hello")` создаёт **новый** объект в куче — ссылки разные. `==` сравнивает ссылки, не содержимое.
>
>     **Развёрнутое объяснение.** Java String pool — это специальная область кучи (PermGen → Metaspace с Java 8, теперь в обычной куче), где хранятся уникальные интернированные строки. При компиляции литерал `"hello"` проверяется в pool: если есть — возвращается существующая ссылка, иначе добавляется. Поэтому `String a = "hello"; String b = "hello";` дают одну ссылку (`a == b` true). `new String("hello")` явно создаёт новый объект в куче, ссылка отличается от pool'а (`a == new String("hello")` false). `equals` сравнивает содержимое по символам и всегда даёт `true` для одинакового текста.
>
>     **Пример.** `String a = "hello"; String b = "hello"; String c = new String("hello"); a == b` → true (оба из pool). `a == c` → false (c в куче). `a.equals(c)` → true (содержимое одинаковое). `c.intern() == a` → true (intern возвращает pool-ссылку).
>
>     **Когда применять.** Понимание для debug NPE при `null.equals(...)` (используй `Objects.equals` или `"literal".equals(var)` чтобы избежать NPE при `var == null`), оптимизация памяти через `intern()` для повторяющихся ключей (lookup keys, enum-like patterns), JIT-оптимизация compile-time string concatenation (`"a" + "b"` → `"ab"` в pool).
>
>     **Подводные камни.** `intern()` помещает строку в pool, но если pool заполнен мусором, это GC pressure. С Java 7+ pool в обычной куче, размер настраиваемый через `-XX:StringTableSize`. Compile-time concatenation литералов идёт в pool: `"he" + "llo" == "hello"` true; runtime concat — нет: `String s="he"; s + "llo" == "hello"` false. `String.valueOf(null)` возвращает `"null"`, а не throws NPE.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q34]] char[] vs String; [[arrays-strings-interview#Q35]] StringBuilder; [[arrays-strings-interview#Q1]] Array vs ArrayList.
>
> - [ ] B. `==` сравнивает строки по содержимому, но `new String` создаёт unicode-копию, отличающуюся encoding'ом.
>
>     **Что на самом деле.** `==` сравнивает **ссылки** для всех объектов в Java, включая String. Encoding не играет роли — String внутри хранится одинаково (`byte[]` с флагом LATIN1/UTF-16 в Java 9+, или `char[]` в Java 8-).
>
>     **Откуда путаница.** В C/C++ `==` для `char*` сравнивает указатели (то же поведение). В JavaScript `==` для строк сравнивает содержимое — этот опыт переносят на Java.
>
>     **Если бы это было правдой.** `new String("hello") == "hello"` всегда давало бы true, но реально false.
>
>     **Как было бы правильно.** Сказать, что `==` сравнивает ссылки в Java; для content-сравнения нужен `equals`.
>
> - [ ] C. Это баг JVM, который исправлен в Java 17 — в новых версиях `==` работает корректно.
>
>     **Что на самом деле.** Это не баг, а намеренный design Java с самого начала. Поведение стабильно от Java 1.0 до текущих версий и не будет меняться (нарушит миллионы существующих кодов).
>
>     **Откуда путаница.** Студенты, попавшие на этот «странный» результат, ищут объяснение через «возможно это исправят».
>
>     **Если бы это было правдой.** Java 17 release notes упоминали бы изменение `==` semantics, но никакого такого изменения нет.
>
>     **Как было бы правильно.** Признать, что поведение by design стабильно; использовать `equals` для content-сравнения.
>
> - [ ] D. Литералы хранятся в read-only memory сегменте, и любое сравнение с ними возвращает true благодаря immutability.
>
>     **Что на самом деле.** Литералы хранятся в pool (часть heap), не в read-only memory. Immutability защищает от мутаций, но не делает `==` равенство по содержимому.
>
>     **Откуда путаница.** Immutability часто упоминается как «специальная» характеристика String, и её приписывают всему поведению.
>
>     **Если бы это было правдой.** `new String("hello") == "hello"` всегда true, но это не так.
>
>     **Как было бы правильно.** Сказать, что immutability и pool — две разные характеристики; `==` сравнивает ссылки независимо от immutability.

## Q34. Когда использовать char[] вместо String для алгоритмов?

1. **In-place модификация** — `String` immutable, `char[]` можно менять
2. **Безопасность** — пароли держат в `char[]`, чтобы можно было «затереть» (`Arrays.fill(arr, '\0')`); `String` остаётся в куче до GC
3. **Производительность** — для тяжёлых алгоритмов на строках `char[]` обходит `String.charAt()` (в Java 9+ String хранится как `byte[]` с compact strings)

```java
// Работа с паролем
char[] password = readPassword();
try {
    authenticate(password);
} finally {
    Arrays.fill(password, '\0'); // затираем
}
```

С Java 9+ строки хранятся как `byte[]` с флагом кодировки (LATIN1 или UTF-16) — `String.charAt()` для LATIN1 вернёт значение быстро, но для алгоритмов всё ещё может быть выгоднее `toCharArray()`.


> [!mcq] Почему пароли в Java рекомендуют хранить в `char[]`, а не в `String`?
>
> - [ ] A. `char[]` быстрее в обработке — JIT оптимизирует bit-level операции лучше, чем String API.
>
>     **Что на самом деле.** В Java 9+ String внутри использует `byte[]` (compact strings для LATIN1, UTF-16 для остальных). Скорость доступа сопоставима с `char[]`. Производительность — не главный аргумент для паролей; security — главный.
>
>     **Откуда путаница.** «Char[] быстрее» — миф из старой Java (до 8); сейчас разница минимальна.
>
>     **Если бы это было правдой.** Best practice была бы «char[] для performance», но реально это «char[] для security».
>
>     **Как было бы правильно.** Признать, что security (возможность затирания), а не speed — главное преимущество.
>
> - [ ] B. `String` нельзя передавать через JNI, поэтому для интеграции с native crypto нужен `char[]`.
>
>     **Что на самом деле.** JNI поддерживает и String, и char[] (`GetStringUTFChars`, `GetCharArrayElements`). Native crypto-libraries (OpenSSL bindings) принимают любые типы. JNI — не аргумент для выбора.
>
>     **Откуда путаница.** «Native = особый случай» — миф; JNI работает с любыми Java типами.
>
>     **Если бы это было правдой.** BouncyCastle и подобные библиотеки требовали бы `char[]`, но они принимают и String тоже.
>
>     **Как было бы правильно.** Признать, что JNI работает с обоими; security (gc-controllability) — настоящий критерий.
>
> - [x] C. `String` immutable и остаётся в куче до GC; `char[]` можно затереть `Arrays.fill(arr, '\0')`, минимизируя окно, когда секрет лежит в памяти.
>
>     **Развёрнутое объяснение.** При утечке памяти (heap dump в случае инцидента, debugging, attacker с физическим доступом) данные в String остаются читаемыми до момента, пока GC не освободит и не перезапишет регион. Поскольку String immutable, нельзя обнулить содержимое программно — JIT-оптимизация даже может сохранить String в pool. `char[]` — mutable, и после использования можно явно `Arrays.fill(password, '\0')`, что гарантированно затрёт байты в памяти. Окно «время от чтения до затирания» минимизируется до нескольких миллисекунд.
>
>     **Пример.** В Spring Security PasswordEncoder API `matches(CharSequence rawPassword, String encodedPassword)` принимает `CharSequence` для raw — намёк на использование `char[]`. JDBC `PreparedStatement.setObject(idx, password)` для пароля — `setString` оставляет String в pool, `setCharStream(new CharArrayReader(arr))` чище. После аутентификации: `Arrays.fill(password, '\0')`. В `JPasswordField.getPassword()` возвращается именно `char[]`, не String — Sun design intentional.
>
>     **Когда применять.** Все pure-Java sensitive data в памяти: пароли, API tokens, JWT secrets, encryption keys. Banking apps (Sberbank's password handlers), security middleware (Keycloak login flow), CLI tools принимающие credentials через `System.console().readPassword()` (возвращает `char[]`).
>
>     **Подводные камни.** `String.valueOf(password)` копирует в новый String, который опять навсегда в куче — не используй `valueOf`. Логирование (`log.info("Pwd: " + password)` через `+` создаёт String → утечка). Heap dump может попасть на disk через системные crash logs; помимо `char[]` нужен disabled HeapDumpOnOutOfMemoryError для production. SecurityManager + Sealed Objects дают дополнительную защиту, но это тема глубже базового вопроса.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q21]] string reverse; [[arrays-strings-interview#Q33]] string pool и `==`; [[arrays-strings-interview#Q35]] StringBuilder.
>
> - [ ] D. В `char[]` можно сохранить пароль с null-байтами, а String — нельзя.
>
>     **Что на самом деле.** Java String поддерживает любые `char`, включая ` `. `"foo bar"` — валидная String длины 7. Null-byte preservation — не разница между типами.
>
>     **Откуда путаница.** В C `char*` строки null-terminated, и сохранение null-байта обрывает строку. Этот опыт переносят на Java.
>
>     **Если бы это было правдой.** Java String имел бы C-like null termination, но он сохраняет точную длину через field `count`.
>
>     **Как было бы правильно.** Признать, что и String, и char[] поддерживают null-байты; разница в mutability и GC-control.

## Q35. (!) StringBuilder vs String конкатенация — где разница?

```java
// O(n²) — каждая конкатенация создаёт новую строку
String result = "";
for (String s : list) result += s; // ужасно для большого list

// O(n) — StringBuilder
StringBuilder sb = new StringBuilder();
for (String s : list) sb.append(s);
String result = sb.toString();

// O(n) — String.join, лаконично
String result = String.join("", list);

// O(n) — Collectors.joining
String result = list.stream().collect(Collectors.joining(", "));
```

С Java 9+ компилятор использует **invokedynamic** + `StringConcatFactory` для `+` — для **простой** конкатенации это эффективно. Но в **цикле** `+=` всё равно проигрывает — компилятор не может объединить итерации в одну операцию.

Для тред-сейф случая — `StringBuffer` (синхронизирован, медленнее).


> [!mcq] Почему `String result = ""; for (String s : list) result += s;` имеет сложность `O(n²)` для списка длины `n`?
>
> - [ ] A. Каждая `+=` вызывает `intern()`, добавляя String в pool — `O(log n)` на поиск + `O(n)` на копирование.
>
>     **Что на самом деле.** `+=` НЕ вызывает `intern` автоматически. Конкатенированные runtime-строки идут в обычную кучу, не в pool. `intern` нужно вызывать явно.
>
>     **Откуда путаница.** String pool часто упоминается как «магия» Java, и студенты приписывают ей всё необъяснимое.
>
>     **Если бы это было правдой.** String pool раздувался бы до миллионов записей при любом цикле конкатенации, что давно вызвало бы OOM в production.
>
>     **Как было бы правильно.** Признать, что pool не вовлечён в runtime `+=`; деградация из-за copy-overhead.
>
> - [ ] B. JIT не может оптимизировать loop body, потому что String immutable; каждый `+=` — это `synchronized` block, добавляющий контеншн.
>
>     **Что на самом деле.** Конкатенация String не использует `synchronized` (нет shared state). JIT может оптимизировать loop, но не может объединить independent `+=` операции в один `StringBuilder` — это требует escape-analysis уровня смены семантики.
>
>     **Откуда путаница.** «Synchronized» иногда упоминается в контексте `StringBuffer` (который sync), и его путают с `String`.
>
>     **Если бы это было правдой.** В multi-thread разница была бы заметна, но в single-thread тоже `O(n²)` — concurrency не причина.
>
>     **Как было бы правильно.** Признать, что причина — copy при каждой новой String, не synchronized.
>
> - [ ] C. `+=` создаёт new String с pre-allocated capacity = `Integer.MAX_VALUE`, что вызывает GC pressure.
>
>     **Что на самом деле.** Created String имеет precise size = `result.length() + s.length()`, не overallocated. Compiler оптимизирует через `StringBuilder` (default capacity 16 + growth doubling), но **внутри одной expression `a+b+c`**, не через итерации цикла.
>
>     **Откуда путаница.** ArrayList использует doubling capacity, и это правило ошибочно переносят на String.
>
>     **Если бы это было правдой.** Каждая `+=` потребляла бы 2 ГБ heap, что мгновенно вызывало бы OOM на первой же итерации.
>
>     **Как было бы правильно.** Признать, что size precise; деградация из-за repeated full copy, не из-за overallocation.
>
> - [x] D. Каждая `+=` создаёт **новую** String (`String` immutable), и копирование накапливающегося `result` после k итераций — `O(k)`; суммарно `Σ k = n(n+1)/2 = O(n²)`.
>
>     **Развёрнутое объяснение.** Конкатенация `result += s` транслируется в `result = new StringBuilder(result).append(s).toString()` (или `StringConcatFactory.makeConcatWithConstants` в Java 9+). Каждый раз создаётся новый билдер, копируется накопленный `result`, добавляется `s`, возвращается новая String. Если средняя длина строки — константа, после `k` итераций `result` имеет длину `k`, и копирование `O(k)`. Суммирование `1+2+...+n = n(n+1)/2 = O(n²)` копирований. `StringBuilder.append` вне цикла даёт `O(n)`: накапливает в один буфер с doubling capacity, никаких промежуточных String.
>
>     **Пример.** Конкатенация 10000 строк по 10 символов через `+=`: ~50М операций копирования, ~5-10 секунд. Через `StringBuilder`: ~100K операций, ~10 мс. На реальных бенчмарках разница 3-4 порядка для n > 1000.
>
>     **Когда применять.** Сборка ответа в HTTP-handler из частей (template rendering, JSON streaming), генерация SQL queries (хотя для безопасности — PreparedStatement), composing log lines, форматирование CSV-export, генерация HTML в Spring MVC controller. Альтернативы: `String.join`, `Collectors.joining`, `String.format` (последний медленнее по причине parsing).
>
>     **Подводные камни.** В Java 9+ компилятор использует `invokedynamic` + `StringConcatFactory` для `+` — для **простой** конкатенации (одна строка) это эффективно. Но в **цикле** компилятор не может объединить итерации в одну операцию: каждый `+=` — отдельный bytecode `INVOKEDYNAMIC`. `StringBuffer` (synchronized) медленнее `StringBuilder` из-за monitor enter/exit на каждом методе; используй только в multi-thread сценариях. `String.join(",", list)` идиоматичнее `StringBuilder`-цикла для simple cases.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q33]] string pool; [[arrays-strings-interview#Q34]] char[] vs String; [[arrays-strings-interview#Q1]] Array vs ArrayList (тоже про immutability и copy).

## Q36. Как избежать ArrayIndexOutOfBoundsException в two-pointers?

1. **Условие в цикле перед чтением** — проверяй `left < arr.length`, `right >= 0`
2. **Учитывай Deque/PriorityQueue null** — `pollFirst()` возвращает `null`, не кидает исключение
3. **Используй `<=` vs `<`** аккуратно — частая ошибка в `binarySearch`
4. **При работе со строкой:** `s.charAt(i)` кидает `StringIndexOutOfBoundsException`, проверяй границы

```java
// Опасно — проверяй с короткого замыкания
while (i < n && j < m && arr[i] == brr[j]) { ... }

// Безопаснее: явный break
while (i < n) {
    if (j >= m || arr[i] != brr[j]) break;
    ...
}
```

При работе с `char` помни про **surrogate pairs**: `String.length()` считает UTF-16 кодовые единицы, а не code points.


> [!mcq] Почему `while (i < n && j < m && arr[i] == brr[j])` безопаснее, чем `while (arr[i] == brr[j] && i < n && j < m)`?
>
> - [x] A. Java вычисляет логическое AND слева направо с short-circuit: первый вариант сначала проверяет границы, и `arr[i]`/`brr[j]` читаются только когда индексы валидны.
>
>     **Развёрнутое объяснение.** Логические `&&` и `||` в Java имеют семантику short-circuit evaluation: при `false && X` правая часть не вычисляется. В первой формулировке проверки границ идут **до** чтения массива, поэтому при `i >= n` массив `arr[i]` никогда не читается — нет IOOBE. Во второй формулировке `arr[i] == brr[j]` вычисляется **первым**, и при `i == n` это уже IOOBE до проверки границы. Порядок условий в `&&` критичен для безопасности.
>
>     **Пример.** `arr=[1,2,3]`, `brr=[1,2]`, `i=2`, `j=2`. Безопасный вариант: `i<3 → true, j<2 → false, short-circuit, exit`. Опасный: `arr[2]==brr[2]` → `brr[2]` это IOOBE до проверки `j<2`. Throws `ArrayIndexOutOfBoundsException`.
>
>     **Когда применять.** Любые two-pointer/sliding-window/merge алгоритмы, где индекс может выйти за границу при последнем шаге. Особенно при работе с **двумя** массивами разной длины: merge sorted arrays, longest common subsequence, edit distance. В Java Streams `filter(x -> x != null && x.length() > 0)` — тот же принцип защиты от NPE.
>
>     **Подводные камни.** Short-circuit работает только для логических `&&` и `||`, не для побитовых `&` и `|`. Случайная замена `&&` на `&` ломает безопасность (`x != null & x.length() > 0` всё ещё бросит NPE при null). Для `||` тоже важен порядок: `x == null || x.isEmpty()` — корректно; `x.isEmpty() || x == null` — NPE при null. С `Optional.ofNullable(...).filter(...)` короче и безопаснее, но требует boxing.
>
>     **Связанные вопросы.** [[arrays-strings-interview#Q4]] two pointers; [[arrays-strings-interview#Q5]] merge sorted arrays; [[arrays-strings-interview#Q29]] backspace string compare.
>
> - [ ] B. Java вычисляет всё условие целиком, а потом решает; порядок не имеет значения, главное — `try-catch`.
>
>     **Что на самом деле.** Java компилируется в JVM bytecode с конкретными инструкциями `IFEQ`/`IFNE` после каждого подвыражения `&&`/`||`. Short-circuit — часть language specification (JLS §15.23-24), не «implementation detail».
>
>     **Откуда путаница.** Студенты из C-like языков думают, что compiler reordering меняет порядок; но в Java seq-cst в boolean operators сохраняется.
>
>     **Если бы это было правдой.** `if (obj != null && obj.method())` бросал бы NPE для `obj==null`, но он гарантированно безопасен по JLS.
>
>     **Как было бы правильно.** Признать, что Java гарантирует short-circuit; порядок условий принципиален.
>
> - [ ] C. JIT может изменить порядок проверок ради cache-locality, поэтому полагаться на порядок ненадёжно.
>
>     **Что на самом деле.** JIT может reorder некоторые операции (memory loads in non-volatile fields), но **не** реорганизует side-effects логических операторов — это нарушение JLS. Boolean short-circuit гарантирован независимо от JIT.
>
>     **Откуда путаница.** JIT оптимизации звучат как «magic», и им приписывают всё «странное» поведение.
>
>     **Если бы это было правдой.** Любая null-check before deref переставала бы работать в production после warmup, что катастрофично.
>
>     **Как было бы правильно.** Сказать, что short-circuit — часть language semantics, гарантированно соблюдается JIT.
>
> - [ ] D. Разницы нет — оба варианта эквивалентны; для безопасности нужен только `try-catch (ArrayIndexOutOfBoundsException)`.
>
>     **Что на самом деле.** Разница принципиальна: первая формулировка не бросит IOOBE, вторая бросит. `try-catch` для IOOBE — антипаттерн, скрывающий логические ошибки. Правильный bounds check — дешевле и явнее, чем exception handling.
>
>     **Откуда путаница.** `try-catch` — универсальный safety net, и им компенсируют слабую логику.
>
>     **Если бы это было правдой.** Все Java-коды содержали бы `try-catch(IOOBE)` вокруг array access, но это считается code smell.
>
>     **Как было бы правильно.** Признать, что order matters в `&&`; bounds check first — это идиоматичный safety, не `try-catch`.
