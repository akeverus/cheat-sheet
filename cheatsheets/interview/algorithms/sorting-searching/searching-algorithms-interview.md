## Q1. (!) Что такое поисковый алгоритм?

Поисковый алгоритм находит нужный элемент или решение в структуре данных либо в пространстве состояний. Ключевая характеристика любого такого алгоритма — что он эксплуатирует: если данные упорядочены, поиск можно сократить с `O(n)` до `O(log n)`; если порядка нет, остаётся только перебор.

Поиск бывает разных типов — и это не просто перечисление, а разные постановки задачи:

- **Точечный** — найти конкретный элемент по значению (классический Binary Search).
- **Range (диапазонный)** — найти все элементы, попадающие в заданный интервал.
- **Граничный** — найти первый или последний элемент, удовлетворяющий условию (часто сводится к Binary Search по предикату).
- **Минимум/максимум** — поиск экстремума (в том числе на унимодальной функции — Ternary Search).
- **Граф/дерево** — поиск пути или вершины обходом структуры: BFS, DFS, A*.

**Главный вопрос на собеседовании:** прежде чем выбирать алгоритм, спроси, отсортированы ли данные и какова стоимость доступа к произвольному элементу — от этого зависит, доступен ли `O(log n)`.

## Q2. (!) Сводная таблица поисковых алгоритмов?

Шпаргалка для выбора алгоритма: смотри, какие требования к данным выполнены, и бери самый быстрый из подходящих. Главное правило — `O(log n)` и быстрее доступны только на отсортированных (а для interpolation — ещё и равномерно распределённых) данных.

| Алгоритм | Где работает | Сложность | Требования |
|----------|-------------|-----------|------------|
| Linear Search | Любой массив/список | `O(n)` | Нет |
| Binary Search | Отсортированный массив | `O(log n)` | Сортировка |
| Exponential Search | Отсортированный массив (unbounded) | `O(log n)` | Сортировка |
| Interpolation Search | Равномерно распределённый | `O(log log n)` среднее | Равномерность + сортировка |
| Jump Search | Отсортированный массив | `O(√n)` | Сортировка |
| Ternary Search | Унимодальный массив | `O(log₃ n)` | Унимодальность |
| BFS | Графы, деревья | `O(V + E)` | Нет |
| DFS | Графы, деревья | `O(V + E)` | Нет |
| Dijkstra | Взвешенные графы | `O((V+E) log V)` | Неотрицательные веса |
| A* | Графы с эвристикой | Зависит от h | Допустимая эвристика |
| Hash lookup | HashMap/HashSet | `O(1)` среднее | Хорошая хеш-функция |

## Q3. (!) Как работает Linear Search?

Linear Search (линейный поиск) последовательно сравнивает каждый элемент с искомым, пока не найдёт совпадение или не дойдёт до конца. Это самый простой и универсальный поиск: он не требует ни сортировки, ни случайного доступа — достаточно уметь перебирать элементы по одному.

```java
int linearSearch(int[] arr, int target) {
    for (int i = 0; i < arr.length; i++) {
        if (arr[i] == target) return i;
    }
    return -1;
}

// Generic вариант с Predicate
<T> int linearSearch(T[] arr, Predicate<T> condition) {
    for (int i = 0; i < arr.length; i++) {
        if (condition.test(arr[i])) return i;
    }
    return -1;
}
```

**Сложность:** `O(n)` в среднем и худшем случае (искомого нет или он в конце), `O(1)` в лучшем (элемент первый). Память — `O(1)`.

**Когда применять:**
- **Малые массивы (< 50–100 элементов)** — последовательный проход кеш-дружелюбен (CPU читает память подряд), поэтому на коротких данных линейный поиск нередко обгоняет Binary Search с его «прыжками» по памяти.
- **Неотсортированные данные** — Binary Search тут просто неприменим, а сортировать ради одного поиска дороже самого поиска.
- **Поиск всех вхождений** — раз всё равно нужно обойти массив целиком, преимущество логарифмических методов теряется.

## Q4. Что такое Sentinel Linear Search и зачем он нужен?

Sentinel Linear Search — это микрооптимизация линейного поиска, убирающая одно из двух сравнений в цикле. В обычном варианте на каждой итерации проверяются **два** условия: не вышли ли за границу (`i < length`) и совпал ли элемент (`element == target`).

**Идея «часового» (sentinel):** записываем искомое значение в последнюю ячейку массива. Теперь цикл гарантированно найдёт совпадение и не выйдет за границу — значит, проверку индекса можно убрать, оставив только сравнение с target:

```java
int sentinelSearch(int[] arr, int target) {
    int n = arr.length;
    int last = arr[n - 1];
    arr[n - 1] = target;

    int i = 0;
    while (arr[i] != target) i++;

    arr[n - 1] = last; // restore
    if (i < n - 1 || last == target) return i;
    return -1;
}
```

После цикла восстанавливаем исходное значение и отдельно проверяем, было ли реальное совпадение или мы остановились на «часовом».

**Компромисс:** число сравнений в цикле падает примерно вдвое, но на современных CPU выигрыш почти незаметен — предсказатель переходов (branch prediction) и так делает проверку границы практически бесплатной. Плюс приём требует модифицировать массив, что не подходит для иммутабельных или конкурентно читаемых данных. Это скорее классическая иллюстрация оптимизации, чем рабочий приём для продакшена.

## Q5. (!) Как реализовать итеративный Binary Search?

Binary Search ищет элемент в **отсортированном** массиве, на каждом шаге вдвое сокращая зону поиска: берём средний элемент, сравниваем с target и отбрасываем ту половину, где искомого заведомо нет. Отсюда логарифмическая сложность.

```java
int binarySearch(int[] arr, int target) {
    int low = 0, high = arr.length - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2; // избегаем переполнения!
        if (arr[mid] == target) return mid;
        if (arr[mid] < target) low = mid + 1;
        else                    high = mid - 1;
    }
    return -1;
}
```

**Сложность:** `O(log n)` по времени, `O(1)` по памяти. Обязательное условие — массив отсортирован.

**Три детали, на которых чаще всего ошибаются:**
- **`low <= high` (со знаком равенства)** — когда `low == high`, остаётся ровно один непроверенный элемент; без `=` цикл завершится, не сравнив его, и поиск пропустит ответ.
- **`low + (high - low) / 2` вместо `(low + high) / 2`** — защита от переполнения int: при больших индексах сумма `low + high` может вылезти за `Integer.MAX_VALUE` (подробнее в Q29).
- **`mid + 1` и `mid - 1`** — сдвигаем границу за уже проверенный `mid`. Если оставить `low = mid` или `high = mid`, при `low == high` зона перестанет сужаться и получится бесконечный цикл.

## Q6. Как выглядит рекурсивный Binary Search и чем он отличается от итеративного?

Та же логика «отбрось половину», но границы передаются параметрами рекурсии, а не меняются в цикле:

```java
int binarySearchRec(int[] arr, int target, int low, int high) {
    if (low > high) return -1;
    int mid = low + (high - low) / 2;
    if (arr[mid] == target) return mid;
    if (arr[mid] < target) return binarySearchRec(arr, target, mid + 1, high);
    return binarySearchRec(arr, target, low, mid - 1);
}
```

**Сложность:** `O(log n)` по времени, но `O(log n)` по памяти — на каждый уровень рекурсии тратится кадр стека. Итеративный вариант (`O(1)` памяти) в Java предпочтительнее: JVM не делает оптимизацию хвостовой рекурсии (TCO), так что рекурсия здесь — это лишний расход стека без выигрыша в читаемости.

## Q7. (!) Какие подводные камни у Binary Search?

Binary Search прост по идее, но печально знаменит ошибками на границах — алгоритм «почти работает», и баг проявляется только на краевых входах. Шесть классических ловушек:

1. **Integer overflow.** `mid = (low + high) / 2` переполняется, когда `low + high > Integer.MAX_VALUE`, давая отрицательный `mid` и выход за границы. Решение — считать смещение от `low`: `mid = low + (high - low) / 2`.
2. **Бесконечный цикл.** Если забыть `mid + 1` / `mid - 1` и написать `low = mid`, то при `low == high` зона поиска перестаёт сужаться и цикл не завершится.
3. **`<` vs `<=`.** `while (low < high)` останавливается, когда остался один элемент, и не проверяет его. Для классического поиска нужно `<=`; `<` используют только в специальных инвариантах (поиск границы, как в Q11).
4. **Off-by-one в границах.** `high = arr.length` или `high = arr.length - 1` — выбор зависит от того, полуоткрытый у вас интервал `[low, high)` или закрытый `[low, high]`. Смешивать инварианты нельзя — это источник ошибок «на один».
5. **Дубликаты.** Обычный Binary Search вернёт **любое** из совпадающих вхождений, а не первое/последнее. Для границ нужна модификация (Q8).
6. **Пустой массив.** При `arr.length == 0` границы `low=0, high=-1` дадут пустой цикл и корректный `-1` — но это стоит подтвердить тестом, а не надеяться на удачу.

**Эмпирическое правило:** фиксируй инвариант (что именно означают `low` и `high`) до написания кода и держи его неизменным во всех ветках — большинство багов рождается из смешения двух инвариантов.

## Q8. (!) Как найти первое и последнее вхождение элемента (Find First and Last Position)?

Задача: в отсортированном массиве с дубликатами найти индексы первого и последнего вхождения target — за `O(log n)`. Обычный Binary Search не годится: найдя совпадение, он сразу возвращается, а нам нужно проверить, нет ли такого же значения левее (для первого) или правее (для последнего).

**Приём:** при совпадении не останавливаемся, а запоминаем индекс в `result` и продолжаем поиск в нужную сторону, двигая границу через `mid`.

```java
int[] searchRange(int[] arr, int target) {
    return new int[]{firstPosition(arr, target), lastPosition(arr, target)};
}

int firstPosition(int[] arr, int target) {
    int low = 0, high = arr.length - 1, result = -1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (arr[mid] == target) {
            result = mid;
            high = mid - 1; // ищем дальше слева
        } else if (arr[mid] < target) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }
    return result;
}

int lastPosition(int[] arr, int target) {
    int low = 0, high = arr.length - 1, result = -1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (arr[mid] == target) {
            result = mid;
            low = mid + 1; // ищем дальше справа
        } else if (arr[mid] < target) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }
    return result;
}
```

**Сложность:** `O(log n)` на каждый из двух проходов. Ключевое отличие от обычного поиска: совпадение не завершает цикл — для первого вхождения после находки сужаем правую границу (`high = mid - 1`), для последнего сдвигаем левую (`low = mid + 1`), пока не упрёмся в край серии дубликатов.

## Q9. (!) Как искать в повёрнутом отсортированном массиве (Search in Rotated Sorted Array)?

Массив был отсортирован, а затем циклически сдвинут вокруг неизвестной точки (например, `[4,5,6,7,0,1,2]`). Нужно найти элемент за `O(log n)` — то есть всё ещё бинарным поиском, несмотря на «слом» порядка.

**Ключевое наблюдение:** как бы массив ни повернули, на любом шаге хотя бы одна из двух половин (`[low..mid]` или `[mid..high]`) гарантированно остаётся полностью отсортированной. Мы определяем, какая именно, и проверяем, попадает ли target в её отсортированный диапазон: если да — идём туда, если нет — в другую половину.

```java
int searchRotated(int[] arr, int target) {
    int low = 0, high = arr.length - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (arr[mid] == target) return mid;

        // Какая половина отсортирована?
        if (arr[low] <= arr[mid]) {
            // Левая половина отсортирована
            if (arr[low] <= target && target < arr[mid]) {
                high = mid - 1; // ищем слева
            } else {
                low = mid + 1; // ищем справа
            }
        } else {
            // Правая половина отсортирована
            if (arr[mid] < target && target <= arr[high]) {
                low = mid + 1;
            } else {
                high = mid - 1;
            }
        }
    }
    return -1;
}
```

**Сложность:** `O(log n)`. Условие `arr[low] <= arr[mid]` отличает отсортированную левую половину от случая, когда точка слома попала в неё. Знак `<=` важен: при двух элементах `mid == low`, и без равенства логика сломается.

## Q10. (!) Как найти позицию вставки (Search Insert Position)?

Задача: вернуть индекс target, если он есть, иначе — индекс, куда его нужно вставить, чтобы массив остался отсортированным. Это обычный Binary Search с одним изменением в концовке: вместо `-1` при отсутствии возвращаем `low`.

```java
int searchInsert(int[] arr, int target) {
    int low = 0, high = arr.length - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (arr[mid] == target) return mid;
        if (arr[mid] < target) low = mid + 1;
        else                    high = mid - 1;
    }
    return low; // позиция вставки
}
```

**Сложность:** `O(log n)`. **Почему именно `low`:** когда цикл завершается, `low` и `high` «перекрещиваются» (`low = high + 1`), и инвариант гарантирует, что все элементы левее `low` строго меньше target, а все справа — больше. Значит, `low` — ровно та позиция, на которую встанет target (возможно, `arr.length`, если target больше всех). Это та же логика, что лежит в основе `Arrays.binarySearch` (Q27).

## Q11. (!) Как найти пик-элемент (Find Peak Element) за O(log n)?

**Пик** — элемент, который строго больше обоих соседей (края считаются «уходящими в `-∞`»). Пиков может быть несколько; задача — найти любой за `O(log n)`.

Удивительно, что бинарный поиск работает на **неотсортированном** массиве. Причина — в монотонности направления подъёма: если `arr[mid] < arr[mid+1]`, склон идёт вверх вправо, и справа гарантированно есть пик. Если `arr[mid] > arr[mid+1]` — склон идёт вниз, пик в `mid` или левее. Так мы каждый раз отбрасываем половину, двигаясь «в гору».

```java
int findPeakElement(int[] arr) {
    int low = 0, high = arr.length - 1;
    while (low < high) {
        int mid = low + (high - low) / 2;
        if (arr[mid] > arr[mid + 1]) {
            high = mid; // peak слева или mid
        } else {
            low = mid + 1; // peak справа
        }
    }
    return low;
}
```

**Сложность:** `O(log n)`. Обрати внимание на `while (low < high)` (а не `<=`) и `high = mid` (а не `mid - 1`): здесь мы ищем не точное значение, а границу, поэтому `mid` нельзя исключать из зоны поиска — он сам может оказаться пиком. Это типичный «инвариант границы», отличный от классического поиска из Q5.

## Q12. (!) Как найти медиану двух отсортированных массивов за O(log(min(m, n)))?

Задача-легенда (LeetCode Hard): по двум отсортированным массивам найти медиану их объединения, не сливая их (`O(m+n)` слияние было бы слишком медленным).

**Идея — бинарный поиск по точке разреза.** Медиана делит объединённый массив пополам так, что слева ровно половина элементов и каждый из них не больше любого справа. Мы перебираем бинарным поиском, сколько элементов из меньшего массива (`a`) уходит в левую половину; остаток добирается из `b`. Корректный разрез — тот, где `aLeft <= bRight && bLeft <= aRight` (всё слева не превосходит всё справа). `Integer.MIN/MAX_VALUE` подставляются на краях, чтобы не городить отдельные проверки на выход за границу.

```java
double findMedianSortedArrays(int[] a, int[] b) {
    if (a.length > b.length) return findMedianSortedArrays(b, a);
    int m = a.length, n = b.length, total = m + n;
    int half = (total + 1) / 2;

    int low = 0, high = m;
    while (low <= high) {
        int i = low + (high - low) / 2;
        int j = half - i;

        int aLeft = (i == 0) ? Integer.MIN_VALUE : a[i - 1];
        int aRight = (i == m) ? Integer.MAX_VALUE : a[i];
        int bLeft = (j == 0) ? Integer.MIN_VALUE : b[j - 1];
        int bRight = (j == n) ? Integer.MAX_VALUE : b[j];

        if (aLeft <= bRight && bLeft <= aRight) {
            if (total % 2 == 1) return Math.max(aLeft, bLeft);
            return (Math.max(aLeft, bLeft) + Math.min(aRight, bRight)) / 2.0;
        } else if (aLeft > bRight) {
            high = i - 1;
        } else {
            low = i + 1;
        }
    }
    throw new IllegalStateException();
}
```

**Сложность:** `O(log(min(m, n)))` — бинарный поиск идёт по меньшему массиву (поэтому в начале `a` и `b` при необходимости меняются местами). Это одна из самых каверзных задач на Binary Search: ошибиться в индексах разреза легко, поэтому на собеседовании важно вслух проговорить инвариант «всё слева ≤ всё справа» и обработку чётной/нечётной суммарной длины.

## Q13. (!) Можно ли применять Binary Search к LinkedList?

**Формально — да, но это бессмысленно.** Binary Search экономит время за счёт мгновенного прыжка к середине, а у связного списка нет произвольного доступа: чтобы добраться до `mid`, нужно пройти `O(n/2)` узлов по ссылкам. В итоге каждый из `log n` шагов стоит `O(n)`, и общая сложность вырождается в `O(n log n)` — **хуже**, чем обычный линейный обход `O(n)`.

```java
// Это работает, но медленно для длинных списков
int idx = Collections.binarySearch(linkedList, key);
```

`Collections.binarySearch(LinkedList, key)` это подтверждает: для коллекций без `RandomAccess` он переключается на доступ через итератор и теряет логарифмическое преимущество.

**Чем заменить, если нужен быстрый поиск по упорядоченным данным:**
- **Skip list** — структура поверх связного списка с «экспресс-уровнями», даёт `O(log n)` поиск без массива.
- **Скопировать в массив и искать в нём** — `O(n)` на копирование плюс `O(log n)` на поиск; оправдано, если поисков будет много.
- **TreeMap/TreeSet** — сбалансированное дерево с гарантированным `O(log n)`.

Подробнее — в [Связные списки](../data-structures/linked-lists-interview.md).

## Q14. Что такое Exponential Search и когда он полезен?

Exponential Search (экспоненциальный, он же «галопирующий» поиск) сначала **находит диапазон**, в котором может лежать target, удваивая индекс (1, 2, 4, 8, …), а затем запускает обычный Binary Search внутри найденного промежутка. Он выигрывает в двух ситуациях: когда длина массива неизвестна (**unbounded** / бесконечный поток) или когда target скорее всего близок к началу — тогда удвоения находят его за единицы шагов.

```java
int exponentialSearch(int[] arr, int target) {
    if (arr[0] == target) return 0;
    int i = 1;
    while (i < arr.length && arr[i] < target) i *= 2;
    return Arrays.binarySearch(arr, i / 2, Math.min(i + 1, arr.length), target);
}
```

**Сложность:** `O(log n)`. Если target стоит на позиции `i`, фаза удвоения делает `O(log i)` шагов и находит диапазон шириной не больше `i`, после чего Binary Search добавляет ещё `O(log i)` — обе фазы логарифмические.

**Сценарии применения:** поиск в потоке без известной длины, задача «infinite/unbounded sorted array», случаи, когда искомое обычно недалеко от начала.

## Q15. Что такое Interpolation Search?

Interpolation Search — «умный» Binary Search для **равномерно распределённых** отсортированных данных. Вместо того чтобы всегда брать середину, он угадывает позицию пропорционально значению target — так же, как мы листаем телефонную книгу: имя на «Я» ищем ближе к концу, а не в центре. Оценка позиции:

```
pos = low + ((target - arr[low]) * (high - low)) / (arr[high] - arr[low])
```

```java
int interpolationSearch(int[] arr, int target) {
    int low = 0, high = arr.length - 1;
    while (low <= high && target >= arr[low] && target <= arr[high]) {
        if (low == high) {
            if (arr[low] == target) return low;
            return -1;
        }
        int pos = low + ((target - arr[low]) * (high - low)) / (arr[high] - arr[low]);
        if (arr[pos] == target) return pos;
        if (arr[pos] < target) low = pos + 1;
        else                    high = pos - 1;
    }
    return -1;
}
```

**Сложность:** `O(log log n)` в среднем на равномерных данных — резко быстрее Binary Search. **Но** на неравномерном распределении (скажем, значения экспоненциально скучены) формула систематически промахивается, и поиск деградирует до `O(n)`. Именно поэтому Interpolation Search применяют там, где распределение предсказуемо равномерно — например, в индексных поисках СУБД.

## Q16. Что такое Jump Search?

Jump Search (поиск прыжками) идёт по отсортированному массиву блоками фиксированного размера `√n`, перепрыгивая вперёд, пока не «перешагнёт» target, а затем делает линейный поиск внутри последнего блока. Размер шага `√n` не случаен — это значение, минимизирующее сумму прыжков (`√n`) и линейного добора внутри блока (тоже до `√n`).

```java
int jumpSearch(int[] arr, int target) {
    int n = arr.length;
    int step = (int) Math.sqrt(n);
    int prev = 0;

    while (arr[Math.min(step, n) - 1] < target) {
        prev = step;
        step += (int) Math.sqrt(n);
        if (prev >= n) return -1;
    }

    while (arr[prev] < target) {
        prev++;
        if (prev == Math.min(step, n)) return -1;
    }
    return arr[prev] == target ? prev : -1;
}
```

**Сложность:** `O(√n)` — медленнее Binary Search (`O(log n)`), но Jump Search делает только прыжки вперёд и линейные шаги. Поэтому он выигрывает там, где **возврат назад дорог, а движение вперёд дёшево**: например, при последовательном чтении с диска или ленты, где «прыгнуть назад» гораздо дороже, чем «прочитать следующий».

## Q17. Что такое Ternary Search?

Ternary Search делит интервал не на две, а на **три** части двумя точками `m1` и `m2`. Это инструмент не для поиска значения в массиве, а для поиска **экстремума унимодальной функции** — такой, что у неё ровно один максимум (или минимум): значения сначала только растут, потом только падают.

**Почему именно три части:** сравнив `f(m1)` и `f(m2)`, мы понимаем, по какую сторону от экстремум, и отбрасываем треть интервала, где его заведомо нет. Если `f(m1) < f(m2)` — максимум правее `m1`, поэтому отрезаем левую треть.

```java
double ternarySearchMax(double low, double high, Function<Double, Double> f) {
    while (high - low > 1e-9) {
        double m1 = low + (high - low) / 3;
        double m2 = high - (high - low) / 3;
        if (f.apply(m1) < f.apply(m2)) low = m1;
        else                            high = m2;
    }
    return (low + high) / 2;
}
```

**Сложность:** `O(log₃ n)`. **Нюанс:** хотя основание логарифма 3, на каждой итерации делается **два** вычисления функции против одного у Binary Search, так что для поиска значения в отсортированном массиве тернарный поиск проигрывает. Его ниша — численная оптимизация и поиск экстремумов унимодальных функций, где бинарный поиск неприменим.

## Q18. (!) Что значит «binary search на ответе»?

**Binary search on answer** — техника, где бинарным поиском перебирают не индекс в массиве, а само **значение ответа** в диапазоне `[low, high]` его возможных величин. Мы не ищем элемент — мы угадываем число и проверяем, годится ли оно.

Приём применим, когда выполнены два условия:

1. **Есть быстрая проверка `canDo(X)`** — функция, отвечающая «достижим ли результат при кандидате X?» за полиномиальное время (обычно линейным проходом).
2. **Свойство монотонно** — если `X` подходит, то и любое `Y ≥ X` тоже (или наоборот, `≤ X`). Именно монотонность превращает «ось ответов» в отсортированную последовательность `да/нет`, по которой и работает бинарный поиск, находя точку перелома.

Распознать такую задачу можно по формулировке «минимизируй максимум» или «максимизируй минимум» при заданном ограничении.

```java
int binarySearchAnswer(int low, int high, Predicate<Integer> canDo) {
    while (low < high) {
        int mid = low + (high - low) / 2;
        if (canDo.test(mid)) high = mid;
        else                  low = mid + 1;
    }
    return low;
}
```

**Задачи на этот приём:** Koko Eating Bananas, Split Array Largest Sum, Capacity to Ship Packages, Aggressive Cows — все они разобраны или однотипны с Q19–Q21.

## Q19. (!) Как решить Koko Eating Bananas?

Условие: есть кучи бананов `piles[]`, за час Коко съедает `k` бананов из одной кучи (если в куче меньше — доедает её и на этом час заканчивается). Нужно минимальное `k`, при котором она управится за `h` часов. Это эталонный пример «binary search на ответе» (Q18).

**Почему здесь применим бинарный поиск:** скорость `k` монотонна — чем больше ешь в час, тем меньше часов нужно. Значит, на оси `k` есть точка перелома: левее неё не успеваем, правее (включая саму точку) успеваем. Бинарным поиском ищем эту минимальную подходящую `k`. Диапазон: от `1` до `max(piles)` (есть быстрее самой большой кучи смысла нет). Проверка для конкретного `k` — посчитать суммарные часы `ceil(p/k)` по всем кучам.

```java
int minEatingSpeed(int[] piles, int h) {
    int low = 1, high = Arrays.stream(piles).max().getAsInt();
    while (low < high) {
        int mid = low + (high - low) / 2;
        long hours = 0;
        for (int p : piles) hours += (p + mid - 1) / mid; // ceil(p/mid)
        if (hours <= h) high = mid;
        else            low = mid + 1;
    }
    return low;
}
```

**Сложность:** `O(n log m)`, где `n` — число куч, `m = max(piles)`: бинарный поиск даёт `log m` итераций, на каждой линейный проход по кучам стоит `O(n)`. Деталь: `hours` объявлен `long` — при больших `piles` сумма часов может переполнить `int`. Выражение `(p + mid - 1) / mid` — это целочисленный `ceil(p/mid)` без перехода во float.

## Q20. Как решить Capacity to Ship Packages within D Days?

Условие: посылки `weights[]` нужно отгрузить **по порядку** за `D` дней; найти минимальную грузоподъёмность корабля, при которой это возможно. Та же схема «binary search на ответе», что и Koko (Q19) — меняется только смысл переменной и проверка.

```java
int shipWithinDays(int[] weights, int D) {
    int low = Arrays.stream(weights).max().getAsInt();
    int high = Arrays.stream(weights).sum();
    while (low < high) {
        int mid = low + (high - low) / 2;
        if (canShip(weights, D, mid)) high = mid;
        else                           low = mid + 1;
    }
    return low;
}

boolean canShip(int[] weights, int D, int capacity) {
    int days = 1, current = 0;
    for (int w : weights) {
        if (current + w > capacity) {
            days++;
            current = 0;
        }
        current += w;
    }
    return days <= D;
}
```

**Границы диапазона здесь логичны и важны:** нижняя — `max(weights)` (корабль обязан вместить хотя бы самую тяжёлую посылку), верхняя — `sum(weights)` (грузоподъёмности на всё сразу заведомо хватит за один день). Внутри них бинарным поиском ищем минимальную capacity, при которой `canShip` укладывается в `D` дней. Сложность — `O(n log(sum))`.

## Q21. Как решить Split Array Largest Sum?

Условие: массив `arr[]` разбить на `k` непрерывных подмассивов так, чтобы **максимальная** из их сумм была **минимальной**. Формулировка «минимизировать максимум» — прямой признак «binary search на ответе»; по сути это та же задача, что Q20, только «дни» называются «подмассивами».

```java
int splitArray(int[] arr, int k) {
    int low = Arrays.stream(arr).max().getAsInt();
    int high = Arrays.stream(arr).sum();
    while (low < high) {
        int mid = low + (high - low) / 2;
        if (canSplit(arr, k, mid)) high = mid;
        else                        low = mid + 1;
    }
    return low;
}

boolean canSplit(int[] arr, int k, int maxSum) {
    int parts = 1, current = 0;
    for (int x : arr) {
        if (current + x > maxSum) {
            parts++;
            current = 0;
        }
        current += x;
    }
    return parts <= k;
}
```

**Что искать:** минимальную «крышку» суммы `maxSum`, при которой массив жадно делится не более чем на `k` частей. Диапазон — `[max(arr), sum(arr)]`, как в Q20. Эту же задачу можно решить динамическим программированием за `O(n² · k)`, но бинарный поиск даёт `O(n log(sum))` — на больших данных он на порядки быстрее, и это хороший аргумент озвучить интервьюеру.

## Q22. (!) Как BFS работает как алгоритм поиска?

**Breadth-First Search (поиск в ширину)** обходит граф «кольцами»: сначала все вершины на расстоянии 1 от старта, затем на расстоянии 2 и так далее. Именно поэтому BFS находит **кратчайший путь в невзвешенном графе** — вершина впервые достигается по минимальному числу рёбер. Очередь (FIFO) обеспечивает этот послойный порядок, а массив `visited` не даёт зайти в вершину дважды.

```java
int bfsShortestPath(List<List<Integer>> adj, int start, int end) {
    boolean[] visited = new boolean[adj.size()];
    Queue<int[]> queue = new ArrayDeque<>();
    queue.offer(new int[]{start, 0});
    visited[start] = true;

    while (!queue.isEmpty()) {
        int[] curr = queue.poll();
        if (curr[0] == end) return curr[1];
        for (int v : adj.get(curr[0])) {
            if (!visited[v]) {
                visited[v] = true;
                queue.offer(new int[]{v, curr[1] + 1});
            }
        }
    }
    return -1;
}
```

**Сложность:** `O(V + E)` — каждую вершину кладём в очередь один раз, каждое ребро просматриваем один раз. Важная деталь: вершину помечают `visited` **в момент добавления в очередь**, а не извлечения — иначе одна вершина успеет попасть в очередь несколько раз. Подробнее — в [Графы](../data-structures/graphs-interview.md).

## Q23. (!) Как DFS работает как алгоритм поиска?

**Depth-First Search (поиск в глубину)** идёт вглубь по одной ветке до упора, а упёршись — откатывается (backtracking) и пробует следующую. Это инструмент задач, где важен сам факт достижимости или структура связей, а не длина пути: проверка существования пути, обнаружение циклов, поиск компонент связности, топологическая сортировка. Реализуется рекурсией (стек вызовов) или явным стеком.

```java
boolean dfs(List<List<Integer>> adj, int u, int target, boolean[] visited) {
    if (u == target) return true;
    visited[u] = true;
    for (int v : adj.get(u)) {
        if (!visited[v] && dfs(adj, v, target, visited)) return true;
    }
    return false;
}
```

**Сложность:** `O(V + E)`. **Главное отличие от BFS:** DFS в общем случае **не** находит кратчайший путь — он возвращает первый попавшийся, который может быть сколь угодно длинным. Зато он естественно ложится на задачи с возвратом (backtracking) и рекурсивную структуру графа. Если нужен кратчайший путь в невзвешенном графе — берут BFS (Q22), если важна глубина и перебор вариантов — DFS.

## Q24. Поиск в HashMap — действительно O(1)?

**В среднем — да, `O(1)`**, но это «амортизированная» гарантия, а не безусловная. Хеш мгновенно указывает на корзину (bucket), и при равномерном распределении в корзине лежит один-два элемента. Однако в худшем случае всё иначе:

- **`O(n)`** — до Java 8 или при катастрофически плохом `hashCode()`: все ключи падают в одну корзину и вырождаются в связный список, который приходится обходить целиком.
- **`O(log n)`** — с Java 8+ длинные корзины автоматически превращаются (treeify) в красно-чёрное дерево, и даже коллизионная корзина ищется за логарифм, а не линейно.

**Условия, при которых поиск остаётся `O(1)`:**
- **Хорошая хеш-функция** — равномерно «размазывает» ключи по корзинам, минимизируя коллизии.
- **Разумный load factor** (по умолчанию `0.75`) — таблица не переполнена, поэтому корзины короткие; при превышении происходит resize.
- **Быстрый `equals()`** — внутри корзины ключи всё равно сравниваются через `equals()`, и его медленность бьёт по каждому поиску.

**Вывод:** `O(1)` у HashMap держится на качестве `hashCode()`. Подробнее — в [Хеш-таблицы](../data-structures/hash-tables-interview.md).

## Q25. Поиск в TreeMap — O(log n)?

**Да, и эта гарантия безусловна** (в отличие от HashMap из Q24). `TreeMap` основан на красно-чёрном дереве — самобалансирующемся BST, который не даёт дереву выродиться в список. Поэтому `get/put/remove` всегда `O(log n)`, без оговорок про хеш-функцию и худший случай.

**За что платим этим логарифмом:** TreeMap хранит ключи **в отсортированном порядке**, что открывает операции, которых у HashMap в принципе нет:

```java
TreeMap<String, Integer> map = new TreeMap<>();
map.get("key");      // O(log n)
map.floorKey("k");   // O(log n) — наибольший ключ ≤ "k"
map.ceilingKey("k"); // O(log n) — наименьший ключ ≥ "k"
```

`floorKey`/`ceilingKey`/`headMap`/`subMap` — это поиск по диапазону и по ближайшему ключу. HashMap их не умеет, потому что не хранит порядок. **Эмпирическое правило:** нужен только быстрый «есть/нет» по ключу — бери HashMap (`O(1)`); нужны диапазоны, ближайшие ключи или отсортированный обход — TreeMap (`O(log n)`).

## Q26. (!) Чем различаются Arrays.binarySearch и Collections.binarySearch?

Это две готовые реализации Binary Search в JDK — не нужно писать поиск руками (и спотыкаться о ловушки из Q7). `Arrays.binarySearch` работает с массивами, `Collections.binarySearch` — со `List`. Обе требуют, чтобы данные были **заранее отсортированы**: на неотсортированном входе результат не определён.

```java
// Arrays.binarySearch — для массивов
int[] arr = {1, 3, 5, 7, 9};
int idx = Arrays.binarySearch(arr, 5);   // 2
int notFound = Arrays.binarySearch(arr, 6); // -4 (= -(insertionPoint+1))

// Collections.binarySearch — для List
List<Integer> list = List.of(1, 3, 5, 7, 9);
int idx2 = Collections.binarySearch(list, 5); // 2
```

**Подводный камень:** `Collections.binarySearch(linkedList, key)` вырождается в `O(n log n)` — у LinkedList нет произвольного доступа, и каждый прыжок к середине стоит линейного обхода (см. Q13). Метод применяй только к коллекциям с `RandomAccess` — на практике это `ArrayList`. Не найдя элемент, оба метода возвращают не `-1`, а закодированную позицию вставки (разбор — в Q27).

## Q27. (!) Что возвращает binarySearch при отсутствии элемента?

Не `-1`, а `-(insertionPoint + 1)`, где `insertionPoint` — индекс, на который встал бы искомый элемент, чтобы массив остался отсортированным. Так JDK в одном `int` упаковывает сразу два ответа: «нашли» (неотрицательный индекс) и «не нашли, но вот куда вставлять».

**Почему `+1`, а не просто `-insertionPoint`:** если точка вставки равна `0`, то `-0 == 0` неотличимо от «нашли на позиции 0». Сдвиг на единицу гарантирует, что любой результат «не найдено» строго отрицателен.

```java
int[] arr = {1, 3, 5, 7, 9};
int result = Arrays.binarySearch(arr, 4);
// result = -3 → insertionPoint = -result - 1 = 2
// 4 нужно вставить на позицию 2: [1, 3, 4, 5, 7, 9]

if (result < 0) {
    int insertAt = -result - 1;
    // используй insertAt
}
```

**Зачем это нужно:** за один вызов получаешь и факт наличия, и позицию вставки. Это идеально для поддержания отсортированного списка: если результат отрицательный, декодируешь `insertAt = -result - 1` и вставляешь туда — структура остаётся упорядоченной без повторного поиска.

## Q28. Какая сложность у List.indexOf?

`List.indexOf(o)` — это `O(n)` **линейный** поиск: метод последовательно сравнивает элементы через `equals()` и возвращает индекс первого совпадения или `-1`. Никакого Binary Search тут нет, даже если список отсортирован — `indexOf` об этом не знает и сортировки не требует.

```java
List<String> list = List.of("apple", "banana", "apple");
list.indexOf("apple");      // 0
list.lastIndexOf("apple");  // 2
list.contains("cherry");    // false (тоже O(n))
```

`contains()` устроен так же — внутри он зовёт `indexOf` и тоже стоит `O(n)`.

**Рекомендация:** если проверки `contains`/поиск идут часто, переложи данные в `HashSet` — там lookup амортизированно `O(1)`. Линейный `indexOf` оправдан только для разовых поисков или совсем коротких списков.

## Q29. (!) Почему mid = (low + high) / 2 опасно?

Потому что при больших индексах сумма `low + high` может превысить `Integer.MAX_VALUE` и переполнить `int`. В Java переполнение «заворачивается» в отрицательное число — `mid` становится отрицательным, и следующий же `arr[mid]` бросает `ArrayIndexOutOfBoundsException`:

```java
int low = Integer.MAX_VALUE - 100;
int high = Integer.MAX_VALUE - 50;
int mid = (low + high) / 2; // overflow! результат отрицательный
```

**Правильно:**

```java
int mid = low + (high - low) / 2; // safe
// или
int mid = (low + high) >>> 1; // unsigned right shift — Joshua Bloch's trick
```

Оба варианта считают тот же индекс, но без промежуточной суммы, способной переполниться: `low + (high - low) / 2` прибавляет к `low` лишь половину **разности** (которая всегда влезает в int), а `>>> 1` — беззнаковый сдвиг, корректно делящий на 2 даже «отрицательную» после переполнения сумму (приём Джошуа Блоха).

**Почему это не теоретическая придирка:** ровно эта ошибка жила в `Arrays.binarySearch` самого JDK девять лет и всплыла лишь в 2006-м. Баг проявляется только на массивах больше ~1 млрд элементов, поэтому проходит все «обычные» тесты — классический пример, почему граничные случаи надо проверять осознанно (Q31).

## Q30. Когда Binary Search работает неправильно?

Binary Search молчаливо выдаёт мусор (а не падает) в нескольких случаях — все они нарушают предпосылки алгоритма:

1. **Неотсортированный массив** — фундаментальное нарушение: без порядка решение «искомое слева или справа» бессмысленно, результат не определён.
2. **Дубликаты** — формально корректно, но вернётся **любое** из совпадений, а не первое/последнее; для границ нужна модификация (Q8).
3. **Сравнение `double` через `==`** — из-за погрешности представления `arr[mid] == target` почти никогда не сработает для дробных; сравнивай с допуском: `Math.abs(arr[mid] - target) < epsilon`.
4. **Изменение массива во время поиска** — если другой поток правит массив между шагами, инвариант «отсортировано» ломается, и результат непредсказуем; нужна внешняя синхронизация или иммутабельная копия.
5. **`NaN` в `double[]`** — `NaN` несравним ни с чем (`NaN < x`, `NaN > x` и `NaN == x` все ложны), поэтому любая ветка сравнения ведёт себя неверно.

## Q31. (!) Как протестировать корректность Binary Search?

Поскольку баги Binary Search прячутся именно на краях (Q7, Q29), тесты строят вокруг граничных случаев, а не «среднего» входа. Минимальный чек-лист:

1. **Пустой массив** — должен вернуть `-1`, а не упасть на `arr[mid]`.
2. **Один элемент** — обе ветки: элемент найден и элемент отсутствует.
3. **Target в начале и в конце** — крайние позиции чаще всего ловят off-by-one в границах.
4. **Target между двумя элементами** — отсутствующее значение должно дать `-1` (или закодированную позицию вставки), а не зациклить поиск.
5. **Все элементы одинаковые** — проверка поведения на дубликатах.
6. **Очень большой массив** — выявляет overflow в `mid` (Q29), который на малых данных не виден.
7. **`null` на входе** — должен бросить `NullPointerException`, а не вернуть случайный результат.

```java
@Test
void testBinarySearchEdgeCases() {
    assertEquals(-1, search(new int[]{}, 5));
    assertEquals(0, search(new int[]{5}, 5));
    assertEquals(-1, search(new int[]{5}, 6));
    assertEquals(0, search(new int[]{1, 2, 3}, 1));
    assertEquals(2, search(new int[]{1, 2, 3}, 3));
    // и т.д.
}
```
