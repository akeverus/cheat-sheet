# Вопросы на собеседовании: `Property-based Testing`

`Property-based testing (PBT)` — подход к тестированию, где тесты описывают **свойства** (properties), которым код должен удовлетворять, а фреймворк **генерирует входные данные автоматически**. Зародился в **QuickCheck** (Haskell, 2000). Современные инструменты: **Hypothesis** (Python), **jqwik** (Java), **fast-check** (JS), **PropEr** (Erlang). Дополняет example-based-тестирование.

## Q1. (!) Что такое property-based testing?

**Property-based testing (PBT)** — подход, при котором ты описываешь не конкретные пары «вход → ожидаемый выход», а **общее свойство** (property), которое должно выполняться для *любого* входа, а фреймворк сам генерирует входные данные и проверяет это свойство сотни раз.

Цикл работы:

1. **Определяешь свойство** — инвариант, который код обязан соблюдать для всех допустимых входов (например, «развернуть список дважды = исходный список»).
2. Фреймворк **генерирует много входов** случайным образом (с уклоном в граничные значения: пустые, нули, огромные, unicode).
3. Свойство проверяется на каждом сгенерированном входе.
4. Если хоть один вход свойство нарушил — фреймворк **сжимает (shrink)** его до минимального контрпримера, чтобы причину было легко увидеть.

**Пример:**
```python
@given(st.lists(st.integers()))
def test_reverse_twice_returns_original(lst):
    assert reverse(reverse(lst)) == lst
```

Hypothesis (Python) сам подставит сотни разных списков и проверит, что двойной разворот всегда возвращает исходный.

**Если свойство падает,** Hypothesis не показывает огромный случайный список, на котором споткнулся, а сжимает его до минимального падающего случая (например, `[1, 0]`) — так баг видно сразу.

## Q2. (!) Чем property-based отличается от example-based?

Разница в том, *что* ты задаёшь руками. В example-based ты сам перечисляешь входы и ожидаемые выходы; в property-based ты задаёшь правило, а входы подбирает фреймворк.

**Example-based** (традиционный) — конкретные примеры:
```python
def test_reverse():
    assert reverse([1, 2, 3]) == [3, 2, 1]
    assert reverse([]) == []
    assert reverse([1]) == [1]
```

Ты пишешь **конкретные входы и ожидаемые выходы**. Тест проверяет ровно те случаи, которые ты придумал, — и ничего сверх них.

**Property-based** — общее правило:
```python
@given(st.lists(st.integers()))
def test_reverse_idempotent(lst):
    assert reverse(reverse(lst)) == lst  # property
```

Ты описываешь, **что должно быть истинно всегда**, а фреймворк сам подбирает десятки и сотни входов, включая те, о которых ты бы не подумал.

**Компромисс:** примеры точны и читаются как документация, но покрывают только перечисленные случаи; свойства покрывают огромное пространство входов, но сформулировать их сложнее. Поэтому подходы дополняют друг друга: примеры — для известных и граничных случаев, свойства — для общих инвариантов.

## Q3. (!) Зачем нужен property-based testing?

Главная ценность PBT в том, что он находит входы, которые ты сам не догадался бы проверить, — и делает это автоматически, на каждом прогоне.

**Что он даёт:**

1. **Находит граничные случаи**, о которых ты не подумал — пустой список, очень большие числа, unicode, спецсимволы. Это самый частый источник «неожиданных» багов.
2. **Больше покрытия при меньшем коде** — один property-тест эквивалентен сотням примеров, потому что входы генерируются, а не пишутся руками.
3. **Заставляет думать в терминах свойств** — чтобы сформулировать инвариант, нужно понять, что код вообще гарантирует. Это побочно улучшает дизайн.
4. **Ловит регрессии** — падающий вход сохраняется в базу примеров и автоматически проверяется при каждом следующем запуске.
5. **Сильнее fuzz-тестирования** — fuzzer просто скармливает мусор и ловит падения, а PBT при этом ещё и проверяет содержательные assertions, то есть ловит не только краши, но и неверные результаты.

**Известные находки** через PBT:
- Баги в стандартных библиотеках (Java Collections)
- Уязвимости в криптографии
- Несогласованности в файловых системах

## Q4. (!) Какие свойства можно проверять через PBT?

Самая сложная часть PBT — придумать свойство. Помогает держать в голове несколько типовых шаблонов: почти под любую функцию подойдёт один из них.

**Типовые категории свойств:**

1. **Round-trip (туда-обратно):** `decode(encode(x)) == x` — после кодирования и обратного декодирования данные не меняются.
2. **Идемпотентность:** `f(f(x)) == f(x)` — повторное применение ничего не меняет.
3. **Инварианты:** то, что обязано сохраняться, — размер, сумма элементов, отсортированность.
4. **Сравнение с эталоном (oracle):** `optimized(x) == naive(x)` — быстрая реализация должна совпадать с заведомо корректной медленной.
5. **Математические свойства:** коммутативность, ассоциативность, дистрибутивность операции.
6. **Известные ответы:** `f(empty) == empty` — частный случай с заранее известным результатом.
7. **Стабильность:** результат не меняется при повторном применении (например, при повторной сортировке порядок равных элементов сохраняется).

**Практически для любой функции** найдётся хотя бы одно из этих свойств.

## Q5. Что такое round-trip property и где она применима?

**Round-trip («туда и обратно»)** — свойство `decode(encode(x)) == x`: если данные закодировать, а потом раскодировать, должен получиться исходный объект. Это одно из самых сильных и при этом простых для формулировки свойств — оно сразу ловит потерю информации при преобразовании.

```python
@given(st.dictionaries(st.text(), st.integers()))
def test_json_roundtrip(d):
    assert json.loads(json.dumps(d)) == d
```

**Сценарии применения** — везде, где есть пара «прямое и обратное преобразование»:
- Сериализация (JSON, Protobuf, XML)
- Кодирование (Base64, URL encoding)
- Сжатие (`decompress(compress(x)) == x`)
- Шифрование (`decrypt(encrypt(x, key), key) == x`)

**Что ловит на практике:** именно round-trip-тесты вскрывают JSON-библиотеки, которые спотыкаются на unicode и специальных float-значениях (`NaN`, `Infinity`) — на «нормальных» примерах такие баги обычно не видны.

## Q6. Что такое property идемпотентности?

**Идемпотентность** — свойство `f(f(x)) == f(x)`: повторный вызов функции на уже обработанном результате ничего не меняет. Один вызов и два вызова подряд дают одинаковый итог — функция приводит вход к «устойчивому» состоянию, дальше которого изменений нет.

```python
@given(st.lists(st.integers()))
def test_sort_idempotent(lst):
    assert sorted(sorted(lst)) == sorted(lst)
```

**Сценарии применения** — операции, которые должны «доводить до нормы» и не накапливать эффект:
- Сортировка (уже отсортированный список сортировкой не меняется)
- Нормализация (приведение к канонической форме)
- Операции очистки (cleanup)

## Q7. Что такое свойства-инварианты?

**Инвариант** — условие, которое должно сохраняться для всех входов независимо от того, что именно делает функция. Для сортировки, например, неважно, в каком порядке оказались элементы, — важно, что их количество и сумма не изменились.

```python
@given(st.lists(st.integers()))
def test_sort_preserves_size(lst):
    assert len(sorted(lst)) == len(lst)

@given(st.lists(st.integers()))
def test_sort_preserves_sum(lst):
    assert sum(sorted(lst)) == sum(lst)
```

**Зачем несколько инвариантов:** один инвариант проверяет лишь один аспект поведения. Сохранение размера не поймает потерю элемента с дублированием другого, а сохранение суммы — нет. Набор взаимодополняющих инвариантов вместе описывает корректность гораздо точнее, чем любой по отдельности.

## Q8. (!) Что такое QuickCheck — родоначальник PBT?

**QuickCheck** — первый PBT-фреймворк (Haskell, 2000, Koen Claessen и John Hughes). Именно он ввёл саму идею «опиши свойство — фреймворк сгенерирует входы» и задал шаблон, по которому устроены все последующие инструменты.

```haskell
prop_reverse :: [Int] -> Bool
prop_reverse xs = reverse (reverse xs) == xs

main = quickCheck prop_reverse
-- +++ OK, passed 100 tests.
```

**Значение:** повлиял на каждый современный PBT-фреймворк, а основополагающая статья до сих пор широко цитируется.

**Порты и наследники на других языках** — все они переносят модель QuickCheck в свою экосистему:
- ScalaCheck (Scala)
- ScalaCheck для Java
- jqwik (Java, осовременённый)
- Hypothesis (Python)
- fast-check (JS)
- proptest (Rust)
- gopter (Go)

## Q9. (!) Что такое Hypothesis (Python)?

**Hypothesis** — самый популярный и зрелый PBT-фреймворк для Python.

```python
from hypothesis import given, strategies as st

@given(st.text())
def test_uppercase_lowercase_inverse(s):
    assert s == s.upper().lower() or contains_special(s)

@given(st.integers(min_value=1, max_value=100))
def test_factorial_positive(n):
    assert factorial(n) > 0

@given(st.dictionaries(
    keys=st.text(min_size=1),
    values=st.integers()
))
def test_dict_operations(d):
    assert len(d) >= 0
    assert all(isinstance(k, str) for k in d.keys())
```

**Стратегии (`st.*`)** — встроенные генераторы для распространённых типов (`integers`, `text`, `lists`, `dictionaries` и т.д.), которые комбинируются между собой.

**База примеров (examples database)** — ключевая фишка Hypothesis: найденный падающий вход сохраняется на диск и при следующем запуске проверяется первым. Поэтому однажды найденный баг не «теряется» между прогонами и работает как защита от регрессий.

## Q10. (!) Что такое jqwik (Java)?

**jqwik** — современный PBT-фреймворк для Java, пришедший на смену старому QuickCheck-Java.

```java
@Property
boolean concatenationLength(@ForAll List<Integer> a, @ForAll List<Integer> b) {
    return concat(a, b).size() == a.size() + b.size();
}

@Property
@StatisticsReport
void sortIsIdempotent(@ForAll @Size(max = 100) List<Integer> list) {
    List<Integer> sorted = new ArrayList<>(list);
    Collections.sort(sorted);
    List<Integer> sortedTwice = new ArrayList<>(sorted);
    Collections.sort(sortedTwice);

    Assertions.assertThat(sortedTwice).isEqualTo(sorted);
}
```

**Ключевые аннотации** (свойство описывается декларативно):
- `@Property` — помечает метод как свойство (вместо `@Test`)
- `@ForAll` — параметр, значение которого генерирует фреймворк
- `@Size`, `@IntRange` — ограничивают диапазон генерации (размер коллекции, границы чисел)

**Совместим с JUnit 5** — property-методы живут в тех же классах, что и обычные `@Test`, поэтому PBT можно вводить постепенно, не переписывая существующие тесты.

## Q11. Что такое fast-check (JavaScript)?

**fast-check** — основной PBT-фреймворк для JavaScript/TypeScript. Свойство задаётся через `fc.property(...генераторы, предикат)`, а `fc.assert` прогоняет его на множестве входов.

```javascript
import fc from 'fast-check';

test('reverse is involutive', () => {
  fc.assert(
    fc.property(fc.array(fc.integer()), (data) => {
      return reverse(reverse(data)).join(',') === data.join(',');
    })
  );
});
```

**Зрелость:** проверено крупными проектами — fast-check используют ESLint, Babel, Apollo и другие. Для собеседования это аргумент, что PBT в JS — не экзотика, а production-практика.

## Q12. (!) Что такое генератор (generator) в PBT?

**Генератор** — это рецепт, по которому фреймворк производит случайные входные значения нужного типа. В Hypothesis генераторы называются *стратегиями*; именно они определяют, какое пространство входов будет исследовать тест.

**Встроенные генераторы (Hypothesis):**
- `st.integers()`, `st.floats()`
- `st.text()`, `st.binary()`
- `st.booleans()`
- `st.lists(elements_strategy)`
- `st.dictionaries(keys_strategy, values_strategy)`
- `st.tuples(strat1, strat2)`
- `st.dates()`, `st.datetimes()`
- `st.from_regex("[a-z]{3,5}")`

**Сужение диапазона** — генератор можно ограничить, чтобы он выдавал только валидные для домена значения:
```python
st.integers(min_value=0, max_value=100)
st.lists(st.integers(), min_size=1, max_size=10)
st.text(alphabet="abc", max_size=5)
```

## Q13. Как комбинировать генераторы?

Простые генераторы складываются в сложные — так из `integers`, `text` и `emails` собирается генератор целых доменных объектов. Это позволяет тестировать функции, которые принимают не примитивы, а структуры.

```python
# Generate User objects
user_strategy = st.builds(
    User,
    name=st.text(min_size=1, max_size=50),
    age=st.integers(min_value=0, max_value=150),
    email=st.emails()
)

@given(user_strategy)
def test_user_validation(user):
    assert validate(user)

# Lists of users
@given(st.lists(user_strategy, min_size=1, max_size=100))
def test_user_collection(users):
    ...
```

**`flatmap`** — когда один генератор зависит от значения другого. Здесь сначала генерируется число `n`, а затем список ровно такой длины:
```python
st.integers().flatmap(lambda n: st.lists(st.integers(), min_size=n, max_size=n))
# Lists of randomly chosen size
```

## Q14. Когда и как писать кастомные генераторы?

Когда встроенных стратегий не хватает, генератор пишут вручную через `@st.composite`: внутри функции вызовы `draw(...)` тянут случайные значения, а ты собираешь из них валидный по бизнес-правилам объект. В примере ниже генерируются 12 цифр, к ним вычисляется контрольная цифра — на выходе всегда корректный ISBN.

```python
@st.composite
def valid_isbn(draw):
    digits = draw(st.lists(st.integers(0, 9), min_size=12, max_size=12))
    check_digit = compute_isbn_check(digits)
    return ''.join(map(str, digits)) + str(check_digit)

@given(valid_isbn())
def test_isbn_validates(isbn):
    assert is_valid_isbn(isbn)
```

**Свои генераторы нужны**, когда вход обязан удовлетворять правилам, которые встроенные стратегии не знают:
- Доменно-специфичные строки с контрольными суммами (UUID, ISBN)
- Сложные объекты, валидные только при согласованных полях
- Машины состояний (для stateful PBT)

## Q15. (!) Что такое shrinking (сжатие контрпримера)?

**Shrinking** — это автоматическое упрощение падающего входа: найдя пример, который ломает свойство, фреймворк ищет минимальный вход, который ломает его так же. Случайный генератор обычно выдаёт большой и «грязный» контрпример, а отлаживать гораздо проще минимальный.

**Пример:**
```python
@given(st.lists(st.integers()))
def test_sort_property(lst):
    assert sorted(lst)[-1] >= sorted(lst)[0]  # max >= min
```

**Баг:** падает на пустом списке (`IndexError`, потому что у `[]` нет ни `[-1]`, ни `[0]`).

- **Без shrinking** в отчёте о падении видно что-то вроде `[42, -7, 100, 13, ...]` — случайный список, по которому неочевидно, в чём именно дело.
- **С shrinking** Hypothesis упрощает его и сообщает о падении на `[]` — причина становится очевидной.

**Как это работает:**
1. Найден падающий вход.
2. Фреймворк пробует уменьшенные версии (короче список, меньше по модулю числа) и проверяет, падают ли они тоже.
3. Процесс продолжается, пока упрощать дальше нельзя без того, чтобы тест перестал падать.
4. На выходе — **минимальный контрпример**.

## Q16. Почему shrinking так важен?

Без shrinking PBT терял бы половину пользы: тест бы падал, но разобраться в случайном «мусорном» входе было бы тяжело.

- **Без shrinking** отладка мучительна: «почему падает `[42, -7, 100, ...]`?» — приходится вручную выяснять, какая часть входа критична.
- **С shrinking** причина видна сразу: минимальный контрпример вроде `[]` прямо указывает на необработанный случай.

**Качество shrinking — важный критерий выбора фреймворка.** Современные PBT используют продвинутые алгоритмы сжатия, и Hypothesis здесь особенно силён: он умеет сжимать не только числа и списки, но и сложные структуры — словари и кастомные объекты.

## Q17. (!) Примеры свойств: разворот списка, сортировка, парсинг

Три классических примера, на которых удобно показывать PBT на собеседовании. Обрати внимание: для каждой функции свойств несколько, и вместе они описывают корректность куда полнее, чем один пример.

**Reverse (разворот):**
```python
@given(st.lists(st.integers()))
def test_reverse(lst):
    assert reverse(reverse(lst)) == lst
    assert len(reverse(lst)) == len(lst)
    if lst:
        assert reverse(lst)[0] == lst[-1]
```

**Sorting (сортировка):**
```python
@given(st.lists(st.integers()))
def test_sort(lst):
    sorted_lst = sorted(lst)
    # Properties
    assert len(sorted_lst) == len(lst)
    assert set(sorted_lst) == set(lst)  # same elements
    assert all(sorted_lst[i] <= sorted_lst[i+1] for i in range(len(sorted_lst)-1))
```

**Parsing (round-trip):**
```python
@given(st.dictionaries(st.text(), st.integers()))
def test_json(d):
    assert json.loads(json.dumps(d)) == d
```

## Q18. Как сочетать PBT с обычными тестами?

PBT не вытесняет example-тесты, а живёт рядом с ними — обычно прямо в одном тестовом классе. Example-тесты фиксируют конкретные известные случаи, property-тест проверяет общие инварианты.

```python
class TestSort:
    # Example tests (specific known cases)
    def test_empty(self):
        assert sort([]) == []

    def test_already_sorted(self):
        assert sort([1, 2, 3]) == [1, 2, 3]

    # Property test (general invariants)
    @given(st.lists(st.integers()))
    def test_invariants(self, lst):
        result = sort(lst)
        assert sorted(lst) == result
```

**Рекомендация** — разделяй роли:
- **Примеры** — для известных граничных случаев; заодно служат конкретной документацией поведения
- **Свойства** — для общих инвариантов, которые должны держаться на любом входе

## Q19. Что такое stateful (model-based) PBT?

**Stateful PBT** проверяет не отдельные функции, а объект с состоянием, генерируя случайные *последовательности операций*. Рядом с настоящей реализацией держат простую эталонную «модель» (в примере — обычный список вместо стека), выполняют над обеими одни и те же операции и проверяют, что они ведут себя одинаково. Так находят баги, которые проявляются только в определённом порядке вызовов.

```python
from hypothesis.stateful import RuleBasedStateMachine, rule

class StackMachine(RuleBasedStateMachine):
    def __init__(self):
        super().__init__()
        self.stack = Stack()
        self.model = []

    @rule(value=st.integers())
    def push(self, value):
        self.stack.push(value)
        self.model.append(value)

    @rule()
    def pop(self):
        if self.model:
            assert self.stack.pop() == self.model.pop()

    @invariant()
    def size_matches(self):
        assert self.stack.size() == len(self.model)
```

**Hypothesis** сам генерирует последовательности вроде (push, push, pop, pop, push, …) и на каждом шаге сверяет реальный объект с моделью, в том числе через `@invariant()` (здесь — совпадение размеров).

**Где это особенно ценно:** именно stateful PBT находит баги в базах данных, распределённых системах и сложных машинах состояний — там, где ошибка возникает лишь при конкретной комбинации операций.

## Q20. (!) Когда стоит применять PBT?

Общее правило: PBT тем полезнее, чем «чище» функция и чем легче сформулировать инвариант. Чем больше сайд-эффектов и внешних зависимостей — тем сложнее придумать свойство и тем меньше отдача.

**Хорошо подходит** — там, где вход и выход связаны проверяемым правилом:
- **Чистые функции** (сортировка, парсинг, кодирование)
- **Операции над структурами данных**
- **Математика, алгоритмы**
- **Сериализация**
- **Машины состояний**
- **Код библиотек** (которым пользуются многие — цена бага высока)

**Хуже подходит** — там, где свойство трудно выразить:
- **UI-код** — тяжело сформулировать, что именно «всегда верно»
- **Код, жёстко завязанный на внешнее** (БД, сеть)
- **Код с большим числом сайд-эффектов** — требует аккуратного дизайна, чтобы вообще стать тестируемым

**Главное:** PBT не заменяет example-тесты, а дополняет их — комбинируй оба подхода.

## Q21. (!) В чём ограничения и за что критикуют PBT?

Полезно знать слабые места — на собеседовании это показывает, что ты понимаешь границы инструмента, а не повторяешь рекламу.

**Подводные камни:**

1. **Сложно проектировать свойства** — труднее придумать инвариант, чем написать пример; это главный барьер.
2. **Ложное ощущение покрытия** — свойства проверяют лишь то, что в них заложено, и могут пропустить целый класс проблем.
3. **Медленно для сложных генераторов** — генерация и shrinking стоят времени.
4. **Генераторы несовершенны** — случайное распределение может не совпадать с реальным распределением данных, и важные случаи редко попадают в выборку.
5. **Падения иногда тяжело отлаживать** — даже после shrinking минимальный пример бывает неочевидным.
6. **Подходит не для всего кода** — UI, интеграционные тесты.
7. **Порог входа** — требует иного образа мышления, чем привычные example-тесты.
8. **Поддержка** — свойства приходится развивать вместе с кодом.

**Не серебряная пуля** — PBT дополняет другие виды тестирования, но не отменяет их.

По состоянию на **2025** PBT набирает популярность в командах, ориентированных на качество; в мире Python **Hypothesis** уже фактически мейнстрим.
