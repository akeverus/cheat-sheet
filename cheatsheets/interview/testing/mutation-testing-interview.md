# Вопросы на собеседовании: Мутационное тестирование

`Mutation testing` — техника оценки **качества тестов** (а не качества кода). Идея: модифицировать ("**mutate**") код, прогнать тесты и проверить, **сколько мутаций поймано** (killed). Выжившие мутанты (surviving mutants) = слабые тесты. Главные инструменты: **PIT** (Java), **Stryker** (JS/TS/.NET/Scala), **mutmut** (Python). Дополняет (но не заменяет) coverage.

## Q1. (!) Что такое mutation testing?

`Mutation testing` тестирует не код, а **сами тесты**: оно отвечает на вопрос «а действительно ли мои тесты что-то проверяют, или просто гоняют код вхолостую?».

Идея простая: инструмент намеренно вносит в рабочий код мелкие поломки (мутации) и смотрит, заметят ли это ваши тесты. Если хоть один тест краснеет — мутацию «убили», тесты сторожат этот участок. Если все тесты остаются зелёными — мутант выжил, значит этот код тестами фактически не защищён.

**Как идёт цикл:**
1. **Вносим мутацию** — одно мелкое изменение в коде: `if (x > 5)` → `if (x >= 5)`.
2. **Прогоняем весь набор тестов** на мутированной версии.
3. Тесты **упали** → мутант **killed** (хорошо: тесты поймали поломку).
4. Тесты **прошли** → мутант **survived** (плохо: поломку никто не заметил).
5. Повторяем для каждой возможной мутации.

**Итоговая метрика** — mutation score (kill rate) = убитые мутанты / все мутанты. Чем он выше, тем надёжнее тесты ловят регрессии.

**Главная мысль:** если тесты не реагируют на маленькое искажение логики, то на собеседовании это формулируют так — высокое покрытие без убитых мутантов означает, что код *исполняется* тестами, но не *проверяется* ими.

## Q2. (!) Зачем mutation testing, если уже есть code coverage?

Потому что покрытие и качество тестов — это разные вещи. Coverage отвечает на вопрос «какие строки выполнились при прогоне тестов», но ничего не говорит о том, *проверил* ли тест результат. Mutation testing закрывает именно эту дыру.

**Классическая ловушка покрытия** — 100% coverage при бесполезном ассерте:
```java
// Coverage: 100%
@Test
void test() {
    int result = calculate(5);
    assertNotNull(result);  // weak assertion
}
```

Строка `calculate(5)` выполнилась — покрытие зелёное. Но `assertNotNull` проверяет лишь то, что вернулось *хоть что-то*. Верни `calculate` совершенно неверное число — тест всё равно пройдёт.

**Mutation testing это вскрывает.** Инструмент подменяет тело метода:
```java
// Mutant: change return value
int calculate(int x) {
    return 999; // mutation
}
```

Тест снова зелёный (`assertNotNull(999)` → true), значит мутант **выжил** — и это сигнал: тест есть, покрытие есть, а реальной проверки нет.

**Вывод для собеседования:** coverage измеряет, что код *исполнен*, а mutation score — что код *проверен ассертами*. Поэтому mutation testing дополняет покрытие, а не заменяет его.

## Q3. Что значат термины mutant, killed, survived, equivalent?

Эти слова описывают разные вещи: изменённый вариант программы, результат его проверки и семантическое свойство. Их нельзя считать четырьмя взаимоисключающими статусами одного отчёта.

| Термин | Значение | Чего из него не следует |
|---|---|---|
| **Mutant** | Вариант программы с внесённым изменением; в обычном first-order анализе проверяют одну активную мутацию | Инструмент не обязан создавать отдельную копию исходников для каждого варианта |
| **Killed** | Активная мутация вызвала падение хотя бы одного теста | Не требуется падение всех тестов; причиной может быть и неожиданное исключение, а не только явное сравнение результата |
| **Survived** | Выполненные проверки не обнаружили активную мутацию | Это не доказательство эквивалентности и не автоматический приговор всем тестам |
| **Equivalent** | Изменение сохраняет наблюдаемое поведение на всей объявленной области входов и условий | Это семантическая характеристика, а не автоматически известный движку статус; различающего теста в этой области нет |

Например, `age >= 18` → `age > 18` создаёт мутант. Если тест проверяет требуемый допуск при `age = 18`, изменение может быть обнаружено. Если выбранные проверки его пропустили, это ещё не делает пару эквивалентной: различающий вход существует. Подробности — в Q5/Q9/Q10. [PIT: basic concepts](https://pitest.org/quickstart/basic_concepts/).

Отдельно читайте категории конкретного отчёта. `No coverage` означает отсутствие покрытия изменённого места, а не выполненные проверки, успешно подтвердившие его поведение. В Stryker возможность отличить эту категорию от `Survived` зависит и от режима анализа покрытия. `Timeout` означает превышение допустимого времени; в документированной модели Stryker он входит в `detected`, но остаётся отдельным от `Killed` статусом. Он не доказывает эквивалентность. [Stryker: states and metrics](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/), [coverage analysis](https://stryker-mutator.io/docs/stryker-js/configuration/#coverageanalysis-string).

Ошибку самого прогона или раннера нужно отличать от падения обычного теста. Например, отдельный `Runtime error` в модели Stryker не включается в score; это не правило «любое прикладное исключение означает invalid». Неожиданное исключение из мутированной программы может уронить тест и тем самым обнаружить изменение. Статусы и формулу метрики проверяют по выбранному инструменту, как в Q8.

## Q4. (!) Какие мутации типичны?

Mutation operator — это правило, по которому инструмент вносит одну поломку. Все типовые операторы бьют в одно и то же: в места, где легко ошибиться и где слабый тест ничего не заметит — границы сравнений, арифметику, возвращаемые значения, побочные эффекты.

| Оператор | Оригинал | Мутация |
|----------|----------|----------|
| **Conditional Boundary** | `<` | `<=` |
| **Conditional Boundary** | `>` | `>=` |
| **Negate Conditional** | `==` | `!=` |
| **Math** | `+` | `-` |
| **Math** | `*` | `/` |
| **Increment** | `++` | `--` |
| **Boolean Return** | `return true` | `return false` |
| **Void Method Call** | `methodCall();` | (удалён) |
| **Constant** | `42` | `0` или `1` |

**Важный нюанс масштаба:** каждая строка может попасть сразу под несколько операторов, поэтому одна строка с условием или арифметикой порождает несколько мутантов. Отсюда и взрывной рост их числа — на проекте легко набираются тысячи (см. Q15 про производительность).

## Q5. Как работает Conditional Boundary Mutator?

В **PIT 1.30.2** оператор `CONDITIONALS_BOUNDARY` меняет включение точки равенства, сохраняя операнды сравнения:

| Исходное сравнение | Граничная подмена |
|---|---|
| `<` | `<=` |
| `<=` | `<` |
| `>` | `>=` |
| `>=` | `>` |

Для подходящей инструкции байт-кода в этой таблице задана одна подмена. Одна строка исходника может содержать несколько инструкций или подходить другим операторам, но это не превращает `>=` в набор `>`, `==` и `!=` в рамках одного boundary-оператора. Изменение константы `18` на `19` — тоже другой механизм. [Таблица подмен PIT 1.30.2](https://github.com/hcoles/pitest/blob/1.30.2/pitest/src/main/java/org/pitest/mutationtest/engine/gregor/mutators/ConditionalsBoundaryMutator.java).

Для исходного условия `age >= 18` и мутанта `age > 18` результаты таковы:

| `age` | Оригинал `>= 18` | Мутант `> 18` | Различает эту пару? |
|---|---|---|---|
| 17 | false | false | Нет |
| 18 | true | false | Да |
| 19 | true | true | Нет |

Нужно не только выполнить условие на `18`, но и проверить наблюдаемый результат: например, что доступ разрешён. Если изменённая ветка не влияет на проверяемое поведение, само посещение границы мутанта не обнаружит. Значения по обе стороны полезны для проверки требования в целом, но не заменяют точку равенства для этой подмены. [PIT: basic concepts](https://pitest.org/quickstart/basic_concepts/).

Если отдельно рассматривают ошибочную замену `>= 18` на `== 18`, их различает `19`, а не `17`: на `17` оба условия ложны. Это другая подмена, которую нельзя приписывать `CONDITIONALS_BOUNDARY`.

## Q6. Как работает Math Mutator?

В **PIT 1.30.2** семейство `MATH` заменяет подходящую инструкцию байт-кода по своей таблице. Например, целочисленное умножение `IMUL` заменяется делением `IDIV`: из `price * quantity` получается поведение `price / quantity`, а не одновременно сложение, вычитание и деление. Другие семейства и настройки могут иметь другую таблицу подмен. [Исходник MATH 1.30.2](https://github.com/hcoles/pitest/blob/1.30.2/pitest/src/main/java/org/pitest/mutationtest/engine/gregor/mutators/MathMutator.java).

Различать нужно **конкретные вычисления на выбранных данных**, а не только знаки операций:

| Входы `int` | Умножение | Деление | Что может заметить тест |
|---|---|---|---|
| `(5, 4)` | 20 | 1 | Проверка ожидаемого 20 различает результаты |
| `(0, 2)` | 0 | 0 | Даже точная проверка 0 не различает эту пару на этих входах |
| `(5, 0)` | 0 | `ArithmeticException` | Тест, ожидающий нормального завершения, может упасть и без сравнения результата |

Один вызов метода без наблюдения результата или значимого эффекта может пройти и на мутанте. Поэтому выбирают различающие данные и проверку требования. Исключение тоже способно обнаружить изменение; неверно утверждать, что мутанта убивает только явный `assertEquals`. Указанное исключение относится к **целочисленному** делению на ноль, а не к любому числовому типу. [JLS 21: integer division](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.17.2).

## Q7. Какие ещё бывают операторы мутаций?

Помимо границ и арифметики (Q5–Q6), инструменты применяют целый набор операторов. Каждый бьёт в свой класс типичных ошибок — перечислим основные с примерами и тем, что должен проверять тест.

**Increment/Decrement** — путаница инкремента и декремента (например, в счётчиках и циклах):
```java
i++  →  i--
```

**Negate Conditional** — инверсия условия; убивается тестом, который проходит обе ветки if/else:
```java
if (x == 5)  →  if (x != 5)
```

**Remove Conditional** — условие всегда истинно (тело выполняется безусловно); ловится тестом на ветку, где код выполняться *не должен*:
```java
if (condition) {  →  // removed
```

**Return Values** — подмена возвращаемого значения; вскрывает слабые ассерты, которые не сверяют результат:
```java
return true   →  return false
return 0      →  return 1
```

**Void Method Call** — удаление вызова метода без возвращаемого значения; проверяет, что тест верифицирует *побочный эффект* (например, через mock):
```java
log.info("Processing");  →  // removed
```

**Масштаб.** Поскольку каждый оператор применяется ко всем подходящим местам, мутантов набирается много — на реальном проекте счёт идёт на сотни и тысячи. Это напрямую объясняет, почему mutation testing медленный (Q15).

## Q8. (!) Что такое mutation score (kill rate) и как его считают?

Mutation score показывает долю обнаруженных мутантов **в выбранной модели отчёта**. Перед сравнением процентов нужно проверить состав числителя и знаменателя: формула «убитые / все» скрывает правила учёта статусов.

Например, в документированной модели **Stryker**:

| Величина | Состав |
|---|---|
| Обнаруженные (`detected`) | `killed + timeout` |
| Необнаруженные (`undetected`) | `survived + no coverage` |
| Учитываемые в score (`valid`) | `detected + undetected` |
| Mutation score | `100 × detected / valid` |

`Timeout` учитывается как обнаружение, но остаётся отдельным статусом, а не переименовывается в `killed`. Ошибки компиляции, ошибки выполнения и `ignored` не входят в `valid`; временный статус `pending` также не включают в этот расчёт. [Stryker: states and metrics](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/).

**Пример:** 6 `killed`, 1 `timeout`, 2 `survived` и 1 `no coverage` дают 7 обнаруженных из 10 учитываемых мутантов, то есть **70%**. Это расчёт по заданным статусам, а не результат запуска движка. Отдельная метрика Stryker по покрытому коду исключает `no coverage` из знаменателя и потому здесь составит `100 × 7 / 9 ≈ 77,8%`; эти два показателя нельзя смешивать.

Эквивалентные мутанты не распознаются и не вычитаются автоматически: они могут остаться среди `survived`. Теоретическую поправку на доказанную эквивалентность нужно отделять от фактического score и явно описывать исключения. **100% возможны** для конкретного набора мутаций и тестов, но не доказывают правильность требований или реализации. [Stryker: equivalent mutants](https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/).

Универсальных оценок «80% — отлично» или обязательной цели 70–85% нет. Порог согласуют по риску и стоимости разбора, а динамику сравнивают при сопоставимых операторах, области анализа и правилах расчёта.

## Q9. Как анализировать выживших мутантов (surviving mutants)?

Выживший мутант не был обнаружен выбранными тестами; это повод для разбора, а не автоматическое доказательство слабого assertion. Сначала уточняют статус отчёта: `survived` и `no coverage` могут быть отдельными категориями. Затем читают конкретное изменение, покрывающие тесты и проверяемое ими поведение.

1. **Найдите различающий сценарий.** Для подмены `age >= 18` на `age > 18` таким входом будет 18. Если требование разрешает доступ с 18 лет, проверять нужно и допуск, а не только выполнение строки.
2. **Проверьте причину пропуска.** Нужного входа могло не быть; эффект мог остаться без проверки; выбранный набор тестов мог не охватить нужный сценарий. Добавляйте проверку значимого требования, а не любой тест ради роста процента.
3. **Обоснуйте эквивалентность, если подозреваете её.** Совпадение на нескольких проверенных входах не доказывает одинаковое поведение на всей рассматриваемой области. У действительно эквивалентной пары различающего теста в этой области нет.
4. **Зафиксируйте решение.** Реальный пробел устраняют тестом; эквивалентность или принятый риск описывают явно. Принятие риска не превращает мутант в `killed`.

Само ручное решение «equivalent» не меняет исходный знаменатель отчёта. Если инструмент или команда применяют исключение, нужно указать его способ и отдельно показать, что изменился состав анализа. Иначе рост score может отражать исключённые мутации, а не улучшенные тесты. [PIT: результаты и эквивалентность](https://pitest.org/quickstart/basic_concepts/), [Stryker: статусы и формулы](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/).

## Q10. Что такое эквивалентные мутанты (equivalent mutants)?

Эквивалентный мутант меняет программу синтаксически, но сохраняет её **наблюдаемое поведение на всей объявленной области входов и условий**. Поэтому в этой области нет теста, который отличит его от оригинала. Совпадение на текущих тестовых данных само по себе эквивалентность не доказывает.

Простой пример для Java `int`: выражения `x + 0` и `x - 0` возвращают то же значение `x` для любого значения этого типа. Здесь основание — правило целочисленной арифметики, а не только несколько зелёных запусков. Это не утверждение о произвольных типах или выражениях с побочными эффектами. [JLS 21: numeric addition and subtraction](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.18.2).

В примере цикла с начальным `i = 0` и телом `i++` нужно различать две подмены:

| Условие цикла | Число выполнений тела | Что изменено относительно `i < 10` |
|---|---|---|
| `i < 10` | 10 | Оригинал |
| `i <= 9` | 10 | Знак **и** константа; показанная пара эквивалентна |
| `i <= 10` | 11 | Только знак; это одиночная boundary-подмена, она меняет поведение |

Нельзя выдавать `i < 10` → `i <= 9` за результат одной замены знака оператором `CONDITIONALS_BOUNDARY`.

Инструменты могут отфильтровывать известные случаи, но обычный список `survived` не является полной автоматической классификацией эквивалентности. Обоснование и решение по каждому спорному случаю остаются частью разбора. Если equivalent остаётся среди учитываемых необнаруженных мутантов, он снижает фактический score; автоматического вычитания всех таких мутантов из знаменателя нет. Ручную корректировку отделяют от исходного отчёта, как в Q8–Q9. [PIT: equivalent mutations](https://pitest.org/quickstart/basic_concepts/), [Stryker: equivalent mutants](https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/).

## Q11. (!) Как использовать PIT для Java?

PIT (Pitest) — стандарт де-факто для mutation testing в Java. Он мутирует не исходники, а байт-код, что заметно ускоряет работу, и интегрируется с Maven и Gradle.

**Подключение в Maven** — добавляем плагин:
```xml
<plugin>
    <groupId>org.pitest</groupId>
    <artifactId>pitest-maven</artifactId>
    <version>1.15.0</version>
</plugin>
```

И запускаем анализ одной командой:
```bash
mvn org.pitest:pitest-maven:mutationCoverage
```

**Что на выходе.** PIT генерирует HTML-отчёт, где по каждому файлу видно:
- mutation score;
- сколько мутантов убито, а сколько выжило;
- тип мутации для каждого выжившего — чтобы сразу понимать, какого теста не хватает.

**Чем PIT удобен:**
- **инкрементальный анализ** (`withHistory`) — прогоняет мутации только по изменённому коду;
- встроенная поддержка JUnit 5;
- **coverage-based** отбор — не тратит время на непокрытые строки, где мутант всё равно выживет «по отсутствию покрытия».

**Производительность.** Начиная с PIT 1.6+ есть fast mode, который ускоряет анализ на порядки за счёт умного отбора тестов под каждый мутант (Q16) — без него mutation testing на крупной кодовой базе непрактичен.

## Q12. (!) Как использовать Stryker для JavaScript/TypeScript?

Stryker — основной инструмент mutation testing в экосистеме JS/TS (а также .NET и Scala). Это аналог PIT для фронтенда и Node.js: подключается к привычным раннерам (Jest, Mocha, Vitest) и мутирует исходный код.

**Установка и запуск:**
```bash
npm install --save-dev @stryker-mutator/core @stryker-mutator/jest-runner
npx stryker init
npx stryker run
```

**Конфигурация** задаётся в `stryker.conf.json` — указываем раннер, что мутировать и пороги:
```json
{
  "testRunner": "jest",
  "mutate": ["src/**/*.ts"],
  "thresholds": {
    "high": 80,
    "low": 60,
    "break": 50
  }
}
```

**Как читать thresholds** — это и есть гейт для CI: `high`/`low` лишь раскрашивают отчёт (зелёный/жёлтый/красный), а `break: 50` ломает сборку, если mutation score опустится ниже 50%.

**Stryker Dashboard** позволяет публиковать score и отслеживать его тренд во времени — а тренд (Q18) на практике важнее абсолютного числа.

## Q13. Как использовать mutmut для Python?

mutmut — популярный инструмент mutation testing для Python: он вносит мутации в исходники и прогоняет ваш тестовый набор (обычно pytest), отмечая, какие мутанты выжили.

**Базовый сценарий:**
```bash
pip install mutmut
mutmut run
mutmut html  # report
```

`mutmut run` запускает анализ, `mutmut html` генерирует отчёт с выжившими мутантами.

**Главный подводный камень — скорость.** В Python нет компиляции и байт-кода, который можно было бы дёшево пропатчить (как делает PIT в Java), поэтому каждый мутант фактически требует отдельного прогона тестов через интерпретатор. На сколько-нибудь крупном проекте mutmut работает медленно, и его обычно гоняют ночными прогонами или точечно по изменённым модулям.

## Q14. Какие ещё есть инструменты mutation testing?

Помимо PIT, Stryker и mutmut, у большинства экосистем есть свои инструменты — полезно знать пару имён под каждый язык:

- **Gremlins** (Go) — mutation testing для Go (также go-mutesting).
- **Cosmic Ray** (Python) — альтернатива mutmut с другим подходом к запуску.
- **Infection** (PHP) — фактический стандарт в PHP-проектах.
- **Pitest** (Scala через плагин) — переиспользует движок PIT для Scala.

**Что важно понимать про зрелость.** Инструменты сильно различаются по проработанности и поддержке. Наиболее зрелые и широко применяемые — PIT (Java) и Stryker (JS/TS); их и стоит называть на собеседовании как референсные.

## Q15. (!) Почему mutation testing медленный?

Корень проблемы — мультипликативная стоимость. Чтобы вынести вердикт по *одному* мутанту, нужно прогнать на нём тесты; а мутантов — сотни и тысячи (Q4, Q7). Иногда к этому добавляется перекомпиляция мутированного кода.

Формула простая:

**N мутантов × время прогона набора тестов = общее время.**

**Числовой пример** показывает, насколько это больно в лоб:
- 1000 мутантов;
- тесты идут 30 секунд;
- итого: 1000 × 30 = **8.3 часа** (наивный подход «каждый мутант × весь набор тестов»).

Восемь часов на один прогон неприемлемы для CI — и именно поэтому весь инструментарий построен вокруг оптимизаций (Q16), которые отбрасывают лишние комбинации мутант×тест и сводят эти часы к минутам.

## Q16. Как ускоряют mutation testing (incremental, in-process)?

Все приёмы сводятся к одной идее: не прогонять лишние комбинации мутант×тест и не платить за лишние перезапуски. Вот основные оптимизации и что именно каждая срезает:

1. **Coverage-based selection** — мутировать только покрытый код: для непокрытых строк мутант всё равно выживет «по отсутствию покрытия», так что считать там нечего.
2. **Per-mutant test selection** — для каждого мутанта запускать только те тесты, которые покрывают мутированную строку, а не весь набор. Это убирает основную часть множителя из формулы Q15.
3. **Incremental** — перепрогонять только код, изменившийся с прошлого запуска (история результатов кэшируется).
4. **In-process** — выполнять мутантов без перезапуска JVM на каждого: запуск виртуальной машины дорогой, и амортизация его экономит уйму времени.
5. **Parallel** — раскидывать мутантов по нескольким потокам/ядрам.
6. **Мутация байт-кода вместо исходников** (Java) — не нужно перекомпилировать на каждого мутанта.

**Итог.** Современный PIT с инкрементальным режимом укладывается в минуты даже на крупных кодовых базах — те самые «8 часов» из Q15 превращаются в практичный CI-шаг.

## Q17. (!) Когда mutation testing оправдан?

Поскольку mutation testing стоит дорого (время CI + ручной разбор выживших), применять его имеет смысл там, где цена ошибки и сомнения в тестах высоки. Логика выбора — «много ли я выиграю от *доказательства*, что тесты действительно проверяют этот код».

**Оправдано, когда:**
- **критичный код** — финансы, биллинг, safety-critical: тут баг дорого стоит, и важно убедиться, что тесты не формальные;
- **есть сомнения в качестве тестов** — покрытие высокое, но баги всё равно проскакивают (типичный симптом слабых ассертов из Q2);
- **код библиотеки или фреймворка**, которым пользуются многие: цена регрессии умножается на число потребителей;
- **проверка внедрения TDD** — объективное доказательство, что тесты действительно ведут разработку, а не дописываются для галочки.

**Менее ценно** там, где код нестабилен или тривиален:
- прототипы (быстро меняются — анализ устаревает раньше, чем окупится);
- связующий (glue) код;
- сгенерированный код;
- простые data-классы (геттеры/сеттеры — проверять там нечего).

**Главный компромисс:** mutation testing требует времени CI и инженерного внимания на разбор результатов — поэтому его наводят точечно на ценный код, а не на весь проект сразу.

## Q18. Какой mutation score ставить целевым?

Универсального обязательного процента нет. Цель согласуют для конкретной области кода по цене пропущенной ошибки, стоимости анализа и разбора surviving. Само название «бизнес-логика», «glue» или «data-класс» не задаёт ни нужный процент, ни запрет мутационного анализа: важно, какое поведение и риск за ним стоят.

Сначала зафиксируйте смысл числа: инструмент и версию, набор операторов, область кода и тестов, исключения, статусы числителя и знаменателя. Затем разберите важные выжившие мутанты и выберите достижимый порог с понятной реакцией на нарушение. Порог CI и тренд решают разные задачи: первый задаёт согласованное ограничение, второй помогает заметить изменение при сопоставимых условиях.

**Рост score сам по себе не доказывает улучшение тестов.** Условный пример по формуле Stryker:

| Состав отчёта | Detected | Valid | Score |
|---|---|---|---|
| Исходный набор | 63 | 90 | 70% |
| Исключили 20 необнаруженных мутантов; тесты не менялись | 63 | 70 | 90% |

Это арифметическая иллюстрация смены знаменателя, а не результат запуска движка. Процент вырос без нового теста. Поэтому при сравнении запусков проверяют состав анализа и конкретные surviving; смена версии, операторов или исключений может изменить смысл тренда. [Stryker: формулы](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/).

Не превращайте настройки отображения в универсальную норму качества. В StrykerJS `high`/`low` задают цветовые зоны, а `break` — отдельное условие отказа при score ниже настроенного порога. Эти параметры позволяют реализовать политику команды, но сами не обосновывают обязательные «90% для платежей». Даже 100% относятся к выбранным мутациям и тестам и не доказывают правильность требований. [StrykerJS: thresholds](https://stryker-mutator.io/docs/stryker-js/configuration/#thresholds-object).

## Q19. (!) В чём ограничения и за что критикуют mutation testing?

При всей пользе у метода есть существенные ограничения — на собеседовании важно показать, что вы понимаете не только плюсы, но и где он буксует:

1. **Медленный** даже с оптимизациями — на больших проектах полный прогон остаётся тяжёлым.
2. **Эквивалентные мутанты** создают шум: их нельзя убить, и они засоряют отчёт (Q10).
3. **Ложное ощущение качества** — высокий score говорит, что тесты *реагируют* на изменения, но не гарантирует, что сам код *корректен*.
4. **Сложно интерпретировать** — выживший мутант не всегда очевидно переводится в нужный тест.
5. **Не проверяет интеграцию** — работает на уровне путей в коде (по сути unit), а не на стыках компонентов.
6. **Не серебряная пуля** — это дополнение к другим видам тестирования, а не замена им.
7. **Неочевидный ROI** — для части команд соотношение цены и выгоды спорно.
8. **Накладные расходы на поддержку** — кто-то должен регулярно разбирать выживших мутантов.

**Вывод:** применять вдумчиво и точечно. Mutation testing не заменяет code review, exploratory-тестирование и интеграционные тесты — он усиливает их, проверяя именно строгость unit-проверок.

## Q20. Как встроить mutation testing в CI/CD?

Ключ к встраиванию — разделить дорогой полный прогон и дешёвый быстрый. На каждый PR гоняют только инкрементальный анализ изменённых файлов, а полный mutation testing уносят в ночные/еженедельные сборки, где время не критично.

**На pull request — инкрементально** (по истории, только изменённый код):
```bash
# PIT incremental — only changed files
mvn org.pitest:pitest-maven:mutationCoverage -DwithHistory
```

**Пороговый гейт** ломает сборку, если качество тестов проседает:
```
If mutation score < 60% → fail build
```

**Отчётность** делает результат видимым команде:
- комментарий прямо в PR (у Stryker есть готовый GitHub Action);
- публикация score в dashboard для истории;
- алерт при просадках.

**Рекомендации по режимам запуска:**
- **полный mutation testing** — еженедельно или по ночам (дорого, но исчерпывающе);
- **инкрементальный** — на каждом PR (быстро, не тормозит разработку);
- **отслеживать тренд** во времени — он информативнее разовой цифры (Q18).

**Статус практики.** На 2025 год mutation testing остаётся нишевым, но набирающим обороты подходом; его берут на вооружение команды, серьёзно относящиеся к качеству (например, Google и финансовый сектор).
