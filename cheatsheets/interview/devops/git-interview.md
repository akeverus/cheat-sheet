## Q1. (!) Что такое `Version Control System` (`VCS`)?

Система контроля версий (`Version Control System`, `VCS`) — это инструмент, который используется для управления изменениями в файлах и проектах различных типов. `VCS` позволяет фиксировать и отслеживать изменения, хранить и восстанавливать предыдущие версии файлов, а также объединять изменения, внесенные разными людьми одновременно. Это помогает улучшить сотрудничество в команде разработчиков, отслеживать причины возникновения ошибок и решать конфликты при внесении изменений. Одной из наиболее популярных систем контроля версий является Git.

При обсуждении архитектуры важно дополнить ответ явными trade-offs: что выигрываем, чем платим и как контролируем риски в production. Хорошей практикой считается привязка решения к измеримым SLO/SLI и плану эволюции при росте нагрузки.

## Q2. (!) Что такое Git `Repository`?

Git `Repository` представляет собой место, где хранятся все файлы, история изменений и метаданные проекта, контролируемого с помощью системы контроля версий Git. В нем содержится полная история изменений файлов, сделанных разными разработчиками, а также информация о ветвлениях и слияниях проекта. Git `Repository` может быть локальным (на вашем компьютере) или удаленным (на сервере). Локальный репозиторий содержит полную копию проекта и может быть использован для работы без подключения к сети. Удаленный репозиторий, наоборот, расположен на сервере и служит для хранения и совместной работы над проектом нескольких разработчиков. Git использует репозиторий для сохранения всех изменений, сделанных в проекте, и предоставляет возможность переключаться между разными версиями проекта, запрашивать и добавлять изменения, а также сотрудничать с другими разработчиками над проектом.

Практическая ценность ответа обычно повышается, если дополнить определение операционным контекстом: как решение ведёт себя под нагрузкой, при сбоях и в процессе сопровождения. На интервью ожидают, что вы назовёте критерии выбора и способ валидации решения через метрики и проверяемый сценарий.

## Q3. (!) Как создать Git `Repository`?

Для создания Git `Repository` вы можете следовать следующим шагам:

1. Откройте командную строку или терминал в папке, где хотите создать репозиторий Git.
2. Используйте команду git init, чтобы инициализировать новый репозиторий:

```bash
git init
```

3. После выполнения команды, Git создаст пустой репозиторий в текущей папке. Вы увидите сообщение о успешной инициализации.
4. Опционально: создайте файл.gitignore, чтобы указать Git'у, какие файлы и папки должны быть проигнорированы при добавлении в репозиторий. Файлы, перечисленные в.gitignore, будут игнорироваться при выполнении команды git add.
5. Добавьте файлы в индекс репозитория Git с помощью команды git add. Например, чтобы добавить все файлы в текущем каталоге, используйте:

```bash
git add .
```

6. Выполните команду git commit, чтобы создать коммит с добавленными файлами в вашем репозитории:

```bash
git commit -m "Initial commit"
```

Теперь у вас есть созданный Git `Repository` с первым коммитом. Вы можете продолжить работу с репозиторием, добавлять новые файлы, создавать ветви, выполнять слияния и т. д.

## Q4. (!) Что такое `HEAD`?

В Git термин `HEAD` используется для обозначения текущей указанной версии вашего репозитория. `HEAD` указывает на последний коммит в текущей ветке. Он представляет собой указатель на конкретную версию вашего проекта. `HEAD` может иметь несколько состояний:

1. Ссылка на конкретный коммит (например, указывает на последний коммит в текущей ветке).
2. Имя ветки (например, master), что означает, что `HEAD` указывает на последний коммит в ветке с этим именем.
3. Хешированный идентификатор коммита, непосредственно указывающий на конкретный коммит.

Относительно количества `HEAD`-ов, в репозитории может присутствовать только один `HEAD`. Однако могут существовать разные ветви, и при переключении между ветками, `HEAD` будет указывать на последний коммит в выбранной ветке. Таким образом, несколько ветвей в репозитории могут иметь свои собственные `HEAD`-ы, которые указывают на разные коммиты в каждой ветке.

## Q5. (!) Что такое `Detached HEAD`?

`Detached HEAD` — это состояние репозитория Git, когда текущая ветка не указывает на последний коммит, а указатель `HEAD` напрямую указывает на определенный коммит. В результате, все новые коммиты создаются с новыми хешами и ветка не продвигается вперед. `Detached HEAD` может произойти по нескольким причинам:

1. Выполнение команды git checkout с указанием конкретного коммита или тега вместо ветки.
2. Слияние конфликтующих коммитов веток без создания нового коммита.
3. Проверка отмеченного коммита, не привязанного к ветке.

Чтобы избежать `Detached HEAD`, рекомендуется:

1. Переключаться на конкретную ветку командой `git checkout <branch_name>`, вместо указания коммита или тега.
2. При слиянии веток, всегда создавать новый коммит, который содержит объединенные изменения.
3. Использовать ветки и теги для организации работы и идентификации коммитов.

Если вы оказались в состоянии `Detached HEAD`, есть несколько способов исправить ситуацию:

1. Создайте новую ветку, указывающую на текущий коммит, командой `git branch <branch_name>`.
2. Переключитесь на существующую ветку, командой `git checkout <branch_name>`.
3. Если вам необходимо сохранить изменения с `Detached HEAD`, создайте временную ветку и переключитесь на нее.
4. Используйте git stash для временного сохранения изменений перед переключением на другую ветку или коммит.

Важно понимать, что `Detached HEAD` является нормальным состоянием в Git, например, при работе со специфическими командами или при проверке конкретных коммитов. Однако, для обычных рабочих процессов, рекомендуется стараться избегать `Detached HEAD` и следовать указанным рекомендациям для сохранения стабильности вашего репозитория и истории изменений.

## Q6. (!) Что такое `Commit`?

`Commit` в Git представляет собой фиксацию изменений в репозитории. Когда вы делаете коммит, вы создаете точку сохранения состояния вашего проекта. Коммиты в Git являются основным механизмом отслеживания истории изменений в репозитории. `Commit` в Git состоит из нескольких компонентов:

1. Хеш коммита (commit hash): Уникальный идентификатор каждого коммита, который является шестнадцатеричным значением и используется для идентификации коммита в системе контроля версий Git.
2. Автор (author): Имя и электронная почта человека, который создал коммит.
3. Коммиттер (committer): Имя и электронная почта человека, который выполнил коммит в репозиторий.
4. Дата и время (date and time): Метка времени, указывающая, когда был создан коммит.
5. Сообщение коммита (commit message): Описание изменений, внесенных в данном коммите.
6. Родительский коммит (parent commit): Хеш коммита, который является родителем данного коммита. Каждый коммит может иметь одного или нескольких родителей (например, при слиянии веток).
7. Данные (tree): Указатель на дерево (tree) объекта, который содержит информацию о состоянии файлов в данном коммите.

Кроме того, в объекте фиксации также хранятся другие метаданные, такие как подпись, ссылка на предыдущий коммит для создания истории изменений, а также прочие вспомогательные данные.

Объект фиксации является основным строительным блоком в Git и используется для отслеживания истории изменений в репозитории.

## Q7. (!) Что такое `Index`?

`Index` (также известный как стейджинг-область или просто стейдж) — это промежуточное состояние в Git, где вы можете подготовить свои изменения перед коммитом.

Когда вы вносите изменения в файлы в вашем рабочем каталоге, Git отслеживает эти изменения, но они еще не готовы к коммиту. Вместо этого вы можете использовать команду git add для добавления измененных файлов или новых файлов в индекс. Когда файлы добавлены в индекс, Git сохраняет их текущее состояние и готов их записать в следующий коммит.

Индекс позволяет вам точно контролировать, какие изменения будут включены в следующий коммит. Вы можете создавать множество коммитов с разными наборами изменений, добавляя и удаляя файлы из индекса.

Когда вы готовы зафиксировать изменения, вы используете команду git commit, которая создает коммит на основе файлов, находящихся в индексе. Индекс позволяет вам сформировать логические единицы изменений и делает коммиты более модульными и управляемыми.

Индекс является важной концепцией в Git и позволяет вам контролировать содержимое следующего коммита и организовывать вашу работу в проекте.

## Q8. Что делает git clone?

Команда git clone используется для создания локальной копии удаленного репозитория Git на вашем компьютере. Эта команда копирует все файлы, историю изменений и метаданные проекта, находящиеся в удаленном репозитории, и создает точную копию на вашем локальном компьютере.

Чтобы использовать команду git clone, вам нужно знать `URL` удаленного репозитория, который вы хотите склонировать. Затем вы можете выполнить следующую команду:

```bash
git clone <URL>
```

Git создаст новую папку с названием репозитория и скопирует все содержимое удаленного репозитория в эту папку на вашем компьютере. После успешного выполнения команды git clone у вас будет локальная копия репозитория, с которой вы можете работать, внести изменения, коммитить и синхронизировать с удаленным репозиторием.

## Q9. Что делает git config?

Команда git config используется для настройки параметров Git на вашем локальном компьютере. Она позволяет установить и получить значение различных настроек Git, таких как имя пользователя, электронная почта, редактор по умолчанию и другие.

Вот несколько примеров использования команды git config:

1. Установка имени пользователя:

```bash
git config --global user.name "Your Name"
```

2. Установка электронной почты:

```bash
git config --global user.email "youremail@example.com"
```

3. Просмотр текущих настроек Git:

```bash
git config --list
```

Команда git config имеет два уровня настроек: локальный (для конкретного репозитория) и глобальный (глобально для вашего компьютера). Флаг --global используется для установки глобальных настроек, а без него настройки будут применяться только к текущему репозиторию.

Настройки Git позволяют вам устанавливать предпочтения для своей работы с Git и корректно идентифицировать ваши коммиты.

## Q10. Что делает git `ls-tree`?

Команда git `ls-tree` предоставляет функциональность для просмотра содержимого объектов дерева в Git-репозитории. Она позволяет просматривать метаданные файлов и директорий внутри указанного дерева или коммита.

Синтаксис команды git `ls-tree` выглядит следующим образом:

```bash
git ls-tree [<commit-ish>] [<path>]
```

1. `<commit-ish>` — опциональный параметр, позволяющий указать коммит или ветку, в котором следует искать дерево. По умолчанию используется текущий коммит `HEAD`.
2. `<path>` — опциональный параметр, позволяющий ограничить вывод только на выбранный путь внутри дерева.

Примеры использования команды git `ls-tree`:

1. Вывести содержимое дерева текущего коммита `HEAD`:

```bash
git ls-tree HEAD
```

2. Вывести содержимое дерева для данного коммита:

```bash
git ls-tree c3f2a72
```

3. Вывести только содержимое дерева в указанном пути:

```bash
git ls-tree HEAD src/
```

Команда git `ls-tree` вернет список путей, режимов доступа, хешей объектов и типов объектов для всех файлов и директорий в указанном дереве или коммите. Используя эту команду, вы можете получить полезную информацию о содержимом вашего репозитория.

## Q11. Что делает git status?

Команда git status используется в Git для отображения текущего состояния вашего рабочего каталога и репозитория. Она предоставляет информацию о файлах с изменениями, новых файлах, удаленных файлах и текущей ветке.

При запуске команды git status вы получаете следующую информацию:

1. Выводит ветку, на которой вы находитесь, и указывает, что ветка установлена.
2. Сообщает об изменениях, которые были внесены в вашем рабочем каталоге и не добавлены в индекс.
3. Выводит информацию о файлах, которые находятся в индексе и готовы для коммита.
4. Показывает новые файлы, которые не были отслеживаемы ранее.
5. Сообщает о файле, который был удален из вашего рабочего каталога, но еще не был удален из репозитория.

Команда git status является одной из наиболее используемых команд в Git, так как она позволяет вам получить обзор состояния вашего рабочего каталога и репозитория, а также помогает вам принимать решения о том, какие изменения добавить в индекс для последующего коммита.

## Q12. Что делает git add?

Команда git add используется в Git для добавления изменений в индекс (стейджинг-область) перед коммитом.

Когда вы вносите изменения в файлы в вашем рабочем каталоге, с помощью команды git add вы можете добавить эти изменения в индекс, чтобы они были готовы к коммиту. Команда git add имеет несколько вариантов выполнения:

1. Добавить изменения конкретных файлов:

```bash
git add <file1> <file2>...
```

Вы можете указать конкретные файлы, которые вы хотите добавить в индекс.

2. Добавить все измененные и новые файлы:

```bash
git add .
```

Точка (.) позволяет добавить все измененные и новые файлы в текущем каталоге и его подкаталогах.

3. Добавить определенные изменения в файле:

```bash
git add -p <file>
```

Опция -p позволяет вам взаимодействовать с изменениями в файле, разделяя их на логические части, и добавлять только нужные части.

После выполнения команды git add, изменения будут помещены в индекс, и они будут готовы к коммиту. Вы можете использовать команду git status, чтобы увидеть, какие файлы были добавлены в индекс. Затем вы можете выполнить команду git commit, чтобы создать коммит на основе изменений, находящихся в индексе.

## Q13. Что делают git diff и git status?

Команды git diff и git status являются часто используемыми в Git для работы с изменениями в репозитории. Вот их основные функции:

1. git diff:

Команда git diff используется для отображения различий между текущим состоянием рабочей директории и последним коммитом в репозитории. Это позволяет вам просмотреть, какие файлы были изменены, какие строки были добавлены или удалены. git diff также может быть использован с различными параметрами для сравнения разных коммитов и веток.

2. git status:

Команда git status выводит информацию о текущем состоянии репозитория. Она показывает, какие файлы были изменены, которые еще не были добавлены в индекс, и какие уже были добавлены и готовы к коммиту. git status также покажет ветку, с которой вы работаете, и сообщит о наличии незакоммиченных изменений или новых файлов в рабочей директории.

Команды git diff и git status очень полезны при работе с Git, они позволяют вам просматривать изменения в рабочей директории и иметь обзор текущего состояния вашего репозитория.

## Q14. Что делает git reflog?

Конечно! git reflog это инструмент в Git, который записывает историю всех `HEAD`-указателей (указателей на текущий коммит) в вашем репозитории. Рефлог позволяет вам просматривать и восстанавливать коммиты, которые больше не отображаются в обычных графах коммитов, таких как логи или история ветки.

Некоторые основные сценарии использования `Git reflog` включают:

1. Восстановление удаленных коммитов: Если вы случайно удалите коммит, используя команду reset или revert, вы можете использовать git reflog для нахождения коммита и вернуться к нему.
2. Восстановление удаленных веток: Если вы удалите ветку с помощью команды branch -D, вы можете использовать git reflog, чтобы найти последний коммит на этой ветке и восстановить ветку.
3. Отслеживание изменений `HEAD`: `Git reflog` отображает историю изменений `HEAD`-указателя, позволяя вам просматривать изменения текущей позиции и переходить между ними.
4. Отслеживание операций переключения веток: `Git reflog` запоминает операции переключения веток, позволяя вам вернуться к предыдущей ветке, если вы случайно переключились на другую ветку.

Чтобы просмотреть рефлог, выполните команду git reflog в терминале или командной строке Git. Вы увидите список коммитов и действий `HEAD`-указателя. Каждая запись в рефлоге содержит хеш коммита, действие, дату и время.`Git reflog` это мощный инструмент, который помогает отслеживать и восстанавливать коммиты и ветки, которые иначе могли быть потеряны. Однако он также может занимать много места в вашем репозитории, поэтому рекомендуется время от времени очищать рефлог с помощью команды git reflog expire --`expire-unreachable`=несколько_месяцев.

## Q15. Что делает git annotate?

Команда git annotate, также известная как git blame, используется для отображения аннотаций (построчной истории изменений) для файла в Git. Она позволяет узнать, кто и когда внес определенные изменения в каждую строку файла.

При выполнении команды `git annotate <file>`, Git выводит содержимое указанного файла, а рядом с каждой строкой добавляет информацию об авторе последнего изменения этой строки и коммите, в котором это изменение было сделано. Обычно вывод информации выглядит как таблица или список, где каждая строка представляет собой одно изменение.

Пример вывода команды git annotate:

```text
1e5a6b72 (John Doe 2021-01-01 10:00:00) This is line 1
34f9e8d4 (Jane Smith 2021-01-02 12:00:00) This is line 2
e9d7b5f2 (John Doe 2021-01-03 14:30:00) This is line 3
```

В этом примере каждая строка представляет собой информацию об изменении вместе с хешем коммита, именем автора, датой и временем изменения, а также содержимым самой строки.git annotate полезна для исследования истории изменений файла, задачи отслеживания авторства и определения, кто отвечает за конкретный код или строку. Многие разработчики используют команду git annotate для обзора истории файла перед внесением своих изменений или для понимания контекста кода.

Помимо команды git annotate, существует аналогичная команда git blame с теми же возможностями. Отличие заключается только в названии команды, в остальном они идентичны.

## Q16. Какие уровни есть в git config?

В Git существуют три уровня настройки: локальный (local), глобальный (global) и системный (system). Каждый уровень имеет свою область действия и определяет, где будут применяться установленные значения.

1. Локальный уровень настройки (local): Используется для конфигурации конкретного репозитория. Значения, установленные на этом уровне, применяются только в данном репозитории и сохраняются в файле `.git/config`. Чтобы настроить значение на локальном уровне, выполните команду git config --local <ключ> <значение> внутри директории репозитория.
2. Глобальный уровень настройки (global): Используется для конфигурации Git на уровне пользователя. Значения, установленные на этом уровне, применяются для всех репозиториев на данной машине и сохраняются в файле ~/.gitconfig. Чтобы настроить значение на глобальном уровне, выполните команду git config --global <ключ> <значение>.
3. Системный уровень настройки (system): Используется для конфигурации Git на уровне всей системы. Значения, установленные на этом уровне, применяются для всех пользователей и сохраняются в файле /etc/gitconfig или /usr/local/etc/gitconfig. Чтобы настроить значение на системном уровне, выполните команду git config --system <ключ> <значение>. Обратите внимание, что для доступа к системным настройкам может потребоваться права администратора.

Чтобы просмотреть текущие настройки, используйте команду git config --list. Она отобразит все ключи и значения настроек на каждом уровне. Чтобы изменить или удалить значение на определенном уровне, используйте git config --unset <ключ> или git config --unset --global <ключ> / git config --unset --local <ключ>.

Настройки `Git config` позволяют устанавливать различные параметры, такие как имя пользователя, электронная почта, редактор по умолчанию, ветка по умолчанию и др. Это полезно для настройки и персонализации вашего рабочего процесса в Git.

## Q17. Что делает git stash?

`Git stash` это мощная функция Git, которая позволяет вам временно сохранить незавершенные изменения в отдельном стэше (stash), чтобы вы могли переключиться на другую ветку или применить другие изменения. Вот некоторые важные аспекты использования git stash:

1. Создание stash: Вы можете создать stash с помощью команды git stash save или просто git stash. Это создаст новый stash, который содержит все незавершенные изменения в вашем рабочем каталоге.
2. Применение stash: Чтобы применить stash и вернуть сохраненные изменения, используйте команду git stash apply. По умолчанию Git применяет последний stash, но вы можете указать номер конкретного stash, чтобы применить его. При применении stash они не удаляются, и вы можете применить их снова позже.
3. Применение stash с удалением: Вы можете использовать команду git stash pop, чтобы применить stash и удалить его из списка stash. Это удобно, если вы больше не нуждаетесь в сохраненных изменениях и хотите удалить их из stash.
4. Просмотр списка stash: Чтобы увидеть список stash, используйте команду git stash list. Он покажет вам все сохраненные stash с их идентификаторами и сообщениями.
5. Применение stash на другой ветке: Вы можете легко переключиться на другую ветку и применить stash на этой ветке с помощью команды `git stash branch <new-branch-name>`. Git создаст новую ветку с указанным именем и автоматически применит stash к этой ветке.

`Git stash` очень полезен, когда вам нужно временно сохранить изменения, чтобы переключить ветку, внести другие изменения или протестировать что-то, а затем вернуться к сохраненным изменениям. Он помогает избежать потери работы и облегчает управление незавершенными задачами в Git.

## Q18. Что делает git branch -d?

Для удаления ветки в Git вы можете использовать команду git branch -d или git branch -D. Вот как работает каждая из них:

```bash
git branch -d <branch_name>
```

Эта команда используется для удаления ветки, которая уже была объединена в другую ветку. Если ветка, которую вы пытаетесь удалить, имеет незамердженные изменения, Git выдаст ошибку и не удалит ветку, защищая вас от потери незафиксированных изменений. Если вы уверены, что хотите удалить ветку, несмотря на незамердженные изменения, вы можете использовать вместо -d флаг -D, вот так: `git branch -D <branch_name>`. Примеры использования:

Удалить ветку, которая уже была объединена:

```bash
git branch -d feature/my-feature-branch
```

Удалить ветку с незамердженными изменениями:

```bash
git branch -D feature/my-feature-branch
```

Пожалуйста, обратите внимание, что удаление ветки является постоянной операцией и она не может быть отменена. Поэтому будьте осторожны при удалении веток и убедитесь, что вы сохранили все необходимые изменения перед удалением ветки.

## Q19. Что делает git branch --merged?

Чтобы узнать список веток, которые были слиты с веткой master, вы можете использовать команду git branch --merged master.

При выполнении этой команды Git покажет список локальных веток, которые были слиты с веткой master. Версии git после `2.18`.0 также отображают удаленные ветки, которые были слиты с master. Кроме того, вам также будут показаны текущая ветка и те ветки, которые еще не были слиты.

Вот пример вывода команды git branch --merged master:

```text
feature-branch-1
feature-branch-2
master
* develop
```

В этом примере `feature-branch-1` и `feature-branch-2` являются ветками, которые были слиты с master. master и develop это текущая ветка и ветка, которая еще не была слита с master.

Эта команда полезна, когда вы хотите увидеть список веток, которые успешно были слиты в ветку master или другую ветку. Она может помочь вам отслеживать прогресс интеграции изменений из разных веток в основную ветку вашего проекта.

## Q20. Что делает git stash apply?

Команда git stash apply используется для применения сохраненных изменений, которые были сохранены в стэше (stash), к текущей ветке в Git. Вот как работает эта команда:

1. Когда вы выполняете git stash apply, Git применяет наилучший (latest) stash к вашей текущей ветке, включая все изменения, которые были сохранены в нем.
2. Если вы сохраняли изменения в стэше с сообщениями коммитов, эти сообщения также будут применены к вашей текущей ветке вместе с изменениями.
3. Обратите внимание, что git stash apply не удаляет сохраненные изменения из стэша. Они остаются доступными в стеке стэшей, и вы можете применить их снова, если нужно.

Пример использования git stash apply:

```bash
git stash apply
```

Команда git stash apply особенно полезна, когда вам нужно вернуть сохраненные изменения в стэше обратно в вашу текущую рабочую ветку, но вы также хотите оставить сохраненные изменения в стэше для будущего использования.

## Q21. В чем разница между git stash apply и git stash pop?

Команды git stash apply и git stash pop используются для возврата ранее сохраненных изменений из стэша в вашу рабочую копию, но есть небольшая разница между ними.

1. git stash apply: Эта команда применяет верхний стэш, сохраняя его изменения в вашей рабочей копии, но не удаляет его из стэша. То есть стэш сохраняется, и вы можете применить его снова в будущем или удалить его вручную с помощью git stash drop. Команда git stash apply применяет изменения из стэша и пытается объединить их с текущим состоянием вашего рабочего дерева. Если возникают конфликты, вам придется разрешить их вручную.

2. git stash pop: Эта команда также применяет верхний стэш и сохраняет его изменения в вашей рабочей копии, но в отличие от git stash apply, она также удаляет примененный стэш из стэша. Это означает, что после применения изменений стэш будет полностью удален. Команда git stash pop также может столкнуться с конфликтами, и вам придется разрешить их вручную.

Обе команды очень полезны для временного сохранения изменений в хранилище, чтобы переключиться на другую ветку или отладить проблему, а затем вернуться к изменениям со стэша. Однако, если у вас возникают конфликты при применении стэша, git stash apply дает вам больше контроля, так как стэш остается в хранилище, и вы можете снова применить его позднее или удалить вручную. В то же время, git stash pop может быть удобнее, когда вы уверены, что больше не нуждаетесь в примененных изменениях и хотите удалить стэш сразу после применения.

## Q22. Как восстановить удаленную ветку?

Если ветка была удалена с локальных компьютеров каждого члена команды, но изменения были уже отправлены в центральный репозиторий, можно восстановить ветку, следуя этим шагам:

1. Убедитесь, что информация о удаленной ветке еще есть в центральном репозитории. Для этого вы можете выполнить команду git branch -r, чтобы просмотреть удаленные ветки. Если ветка отображается в списке удаленных веток, перейдите к следующему шагу.
2. Создайте новую локальную ветку, основанную на удаленной ветке. Используйте команду git checkout -b <имя_ветки> <имя_удаленной_ветки>, где <имя_ветки> это имя новой ветки, которую вы хотите создать, и <имя_удаленной_ветки> это имя удаленной ветки из центрального репозитория. Например, git checkout -b `restored-branch` origin/удаленная_ветка.
3. Проверьте, что восстановленная ветка содержит все необходимые изменения. Используйте команду git log, чтобы просмотреть историю коммитов на восстановленной ветке. Убедитесь, что все изменения, которые вы ожидали, присутствуют.
4. Если у вас есть локальные изменения, которые были сделаны перед случайным удалением ветки, вы можете применить их на восстановленную ветку. Воспользуйтесь командой git `cherry-pick`, чтобы применить выбранные коммиты на восстановленную ветку.
5. После завершения восстановления ветки, убедитесь, что все члены команды получат обновления с центрального репозитория. Используйте команду git pull origin <имя_ветки>, чтобы получить последние изменения с сервера.

Теперь ветка должна быть восстановлена и доступна для работы на локальных компьютерах каждого члена команды.

## Q23. (!) Что такое `Conflict`?

`Conflict` в Git возникает, когда система не может автоматически объединить изменения, сделанные в разных ветках, при попытке выполнить операцию слияния (merge) или переноса (rebase). `Conflict` возникает, когда две или более ветки вносят изменения в одну и ту же область кода, и Git не может самостоятельно понять, какое из изменений следует принять. `Conflict` возникает, когда две или более веток имеют разные изменения в одном и том же месте кода. Это может произойти, например, когда два разработчика параллельно вносят изменения в один и тот же файл или когда происходит слияние веток с разными изменениями. Git пытается автоматически объединить изменения, но если он обнаруживает конфликт, он объявляет это состояние как конфликт слияния (merge conflict) и отмечает проблематические места в файлах с помощью специальных маркеров.

Разрешение конфликта требует вмешательства разработчика. Вы должны вручную редактировать соответствующие файлы, разрешая конфликты путем выбора, какую версию кода сохранить или комбинировать эти изменения. После разрешения конфликта вы должны выполнить команду git add для отметки файлов как разрешенные, а затем выполнить команду git commit для завершения слияния или коммита.

Корректное разрешение конфликтов важно для поддержания целостности кодовой базы и согласованности изменений, вносимых несколькими разработчиками.

## Q24. (!) Как решить `Conflict`?

Чтобы разрешить конфликт в Git, вам понадобится выполнить следующие шаги:

1. Сначала вам нужно определить, в каком файле или файлах возник конфликт. Это можно увидеть при выполнении команды `git status` или при попытке выполнить операцию слияния (merge) или переноса (rebase).
2. Откройте файлы с конфликтами в текстовом редакторе. Внутри файла вы обнаружите маркеры, показывающие места конфликта. Обычно они выглядят следующим образом:

```text
<<<<<<< HEAD
... код, внесенный в текущей ветке (HEAD)
=======
... код, внесенный в другой ветке (например, при слиянии)
>>>>>>> branch_name
```

3. Внесите изменения в коде, чтобы разрешить конфликт. Решение конфликта может включать удаление ненужных частей кода, редактирование или объединение изменений. После внесения изменений удалите маркеры конфликта.
4. Сохраните файлы после внесения изменений и разрешения конфликта.
5. После разрешения конфликта выполните команду `git add` для добавления измененных файлов в индекс.
6. Затем выполните команду `git commit`, чтобы закрепить изменения в виде нового коммита.
7. Если вы выполняли операцию слияния (merge) или переноса (rebase), возможно, вам придется выполнить команду `git push`, чтобы отправить изменения на удаленный сервер.

Эти шаги позволят вам разрешить конфликт в Git, сохранить и зафиксировать изменения и продолжить работу с вашим проектом.

## Q25. Что делает git revert?

Если вы уже отправили неверный коммит и хотите его отменить, вам нужно использовать команду git revert. Данная команда создает новый коммит, который обратно отменяет изменения, внесенные указанным коммитом. Это предпочтительный способ отмены изменений в уже отправленном коммите, поскольку он сохраняет историю изменений и предоставляет ясную документацию о том, что было изменено и отменено.

Вот как использовать git revert для отмены коммита:

1. Откройте терминал и перейдите в рабочую директорию вашего проекта.
2. Выполните команду git log, чтобы получить список коммитов. Скопируйте идентификатор (хэш) коммита, который вы хотите отменить.
3. Выполните команду `git revert <commit_id>`, где `<commit_id>` — это идентификатор коммита, который нужно отменить. Git создаст новый коммит, который отменяет изменения указанного коммита.
4. Введите сообщение коммита, чтобы описать, что именно вы отменили.
5. Нажмите `Enter`, чтобы завершить процесс создания нового коммита отмены.

Обратите внимание, что git revert может создавать конфликты слияния, если коммит, который вы хотите отменить, вносит изменения, которые конфликтуют с другими коммитами в истории. В этом случае вам нужно будет разрешить конфликты слияния вручную.

Помните, что после использования git revert изменения не будут удалены из истории коммитов, они просто будут отменены в новом коммите.

## Q26. Что делает git `cherry-pick`?

Команда git `cherry-pick` в Git позволяет применять конкретные коммиты из одной ветки в другую. Функциональность git `cherry-pick` заключается в том, чтобы выбирать коммиты из одной ветки и применять их изменения в текущую ветку, создавая новый коммит с этими изменениями.

Вот как работает git `cherry-pick`:

1. Откройте терминал и перейдите в рабочую директорию вашего проекта.
2. Убедитесь, что вы находитесь в ветке, в которую вы хотите применить изменения из другой ветки.
3. Выполните команду git log в ветке, из которой вы хотите взять коммиты, чтобы получить список коммитов.
4. Скопируйте идентификатор (хэш) коммита, который вы хотите применить.
5. Выполните команду `git cherry-pick <commit_id>`, где `<commit_id>` — это идентификатор коммита, который вы хотите применить. Git создаст новый коммит с изменениями этого коммита и применит его к текущей ветке.
6. Введите сообщение коммита, чтобы описать примененные изменения.
7. Нажмите `Enter`, чтобы завершить процесс создания нового коммита с примененными изменениями.

Команда git `cherry-pick` полезна, когда вы хотите применить определенные изменения, внесенные в другую ветку, к текущей ветке, без необходимости слияния всей ветки. Она позволяет выбирать конкретные коммиты и применять их изменения отдельно.

Однако, следует быть осторожным, применяя git `cherry-pick`, особенно при работе с конфликтующими изменениями. В таких случаях может потребоваться разрешение конфликтов слияния вручную.

## Q27. В чём разница между git revert и git reset?

Команды git revert и git reset предоставляют различные способы отмены изменений в Git. Вот основные различия между ними:

1. git revert: Команда git revert используется для создания нового коммита, который отменяет изменения, внесенные определенным коммитом или серией коммитов. Она не меняет историю коммитов, а создает новый коммит, который отменяет эффекты выбранных коммитов. Каждый коммит отменяется в отдельном коммите отката, что делает операцию безопасной для работы с общим репозиторием, чтобы не внести конфликты при слиянии. git revert может быть использована для отмены любого коммита в истории.

2. git reset: Команда git reset используется для перемещения указателя коммитов, обычно головки ветки, по различным режимам: --soft, --mixed и --hard.
   1. git reset --soft перемещает указатель коммита без изменения индекса и рабочей копии. Все изменения, внесенные в коммиты, остаются в индексе и рабочей копии.
   2. git reset --mixed (по умолчанию) перемещает указатель коммита и сбрасывает индекс на указанный коммит. Рабочая копия будет оставаться неизменной.
   3. git reset --hard перемещает указатель коммита и полностью сбрасывает и индекс, и рабочую копию на указанный коммит, удаляя все изменения после него.

Важно помнить, что git reset изменяет историю коммитов, и тем самым может быть опасным для совместной работы с другими разработчиками, если использование некорректно. В отличие от этого, git revert создает новые коммиты, которые отменяют выбранные изменения, и является безопасным для работы в общей среде.

## Q28. В чём разница между git reset --mixed и git merge --abort?

Команда git reset --mixed и флаг git merge --abort предоставляют различные функциональные возможности в Git.

1. git reset --mixed: Эта команда используется для изменения состояния индекса (staging area) и рабочего каталога на определенном коммите, отменяя коммиты после этого коммита, но сохраняя изменения в вашем рабочем каталоге как немаркированные.

Если передать команде git reset --mixed <commit> указатель коммита, Git отменит все коммиты, начиная с указанного коммита, причем осуществит мягкий откат изменений в индексе и рабочем каталоге.

Если передать команде git reset --mixed `HEAD`~<number>, она отменит несколько последних коммитов, где <number> количество коммитов, которые нужно отменить.

2. git merge --abort: Эта команда используется для отмены операции слияния, ее можно использовать, когда есть конфликты при слиянии веток и вы хотите вернуться к состоянию до начала операции слияния.

Если вызвать команду git merge --abort, то Git попытается вернуть рабочую копию и индекс к состоянию, которое было до начала операции слияния, удаляя все изменения, выполненные в ходе слияния.

В целом, `git reset --mixed` используется для отмены коммитов и изменения состояния индекса, тогда как `git merge --abort` используется для отмены операции слияния при возникновении конфликтов.

## Q29. В чём разница между git merge и git rebase?

При выборе между командами git merge и git rebase в Git необходимо учитывать несколько факторов:

1. История коммитов: Если важно сохранить историю коммитов, особенно если ветка была создана для работы над специфической функцией или задачей в виде отдельного коммита, то лучше использовать git merge. Он сохраняет исторический контекст слияния, создавая коммит с объединенными изменениями из другой ветки.
2. Чистота истории коммитов: Если важно получить чистую и линейную историю коммитов без дополнительных коммитов слияния, то лучше использовать git rebase. Он переписывает историю коммитов, применяя их в новой ветке на последнюю точку разветвления, создавая новые коммиты на основе изменений с другой ветки.
3. Соответствие общим правилам: Если работаете в команде, которая согласовала использование определенного подхода по слиянию или перебазированию, то важно учесть эти правила и следовать им.
4. Взаимодействие с историей коммитов других разработчиков: Если работаете с общим репозиторием и другие разработчики уже склонировали этот репозиторий, то использование git rebase может стать проблемой, так как он изменяет историю коммитов. В этом случае лучше использовать git merge, чтобы сохранить историю коммитов для всех.
5. Размер коммитов и изменений: Если ветка содержит большие коммиты или много изменений, то слияние (git merge) может быть более предпочтительным, так как он сохраняет контекст и объединяет все изменения. В случае с перебазированием (git rebase) может быть сложнее обработать конфликты и сохранить порядок изменений.

В целом, правильный выбор между git merge и git rebase зависит от конкретной ситуации и предпочтений разработчика или команды.

## Q30. Как объединить несколько коммитов в один?

Для объединения нескольких коммитов в один коммит можно использовать команду git rebase -i. Вот как это сделать:

1. Откройте терминал или командную строку и перейдите в корневую директорию вашего репозитория Git.
2. Запустите команду git rebase -i `HEAD`~N, где N это количество последних коммитов, которые вы хотите объединить. Например, если вы хотите объединить последние 3 коммита, команда будет выглядеть как git rebase -i `HEAD`~3.
3. Git откроет интерактивный режим перебазирования в вашем текстовом редакторе по умолчанию (обычно это Vim или `Nano`). В этом режиме отображается список коммитов, которые будут объединены вместе.
4. Измените команды перед каждым коммитом, который вы хотите объединить, с помощью слова pick на squash или s (это означает объединение коммита с предыдущим коммитом). Вы также можете использовать fixup или f, чтобы объединить коммит без сохранения его сообщения коммита.
5. Сохраните и закройте файл редактора. Git объединит выбранные коммиты в один.
6. Git может предложить вам изменить сообщение коммита после объединения. Исправьте сообщение коммита по вашему усмотрению и сохраните его.
7. Git завершит перебазирование и создаст новый коммит, включающий объединенные изменения. Он также оставит оригинальные коммиты в истории, но пометит их как устаревшие.

Важно отметить, что перебазирование (rebase) может изменить историю коммитов, поэтому использование этой команды следует осуществлять с осторожностью, особенно при работе с общим репозиторием, где есть другие разработчики.

## Q31. В чём разница между git remote и git clone?

Команды git remote и git clone выполняют разные задачи. Вот их отличия:

1. git remote:

Эта команда используется для управления удаленными репозиториями в Git. Она позволяет просматривать, добавлять, переименовывать и удалять удаленные репозитории. Вот несколько примеров использования:

- `git remote -v` — показывает список удаленных репозиториев и их `URL`.
- `git remote add <remote_name> <remote_url>` — добавляет новый удаленный репозиторий с указанным именем и `URL`.
- `git remote rename <old_name> <new_name>` — переименовывает удаленный репозиторий с указанным старым именем на новое имя.
- `git remote remove <remote_name>` — удаляет удаленный репозиторий с указанным именем.

2. git clone:

Эта команда используется для клонирования удаленного репозитория на локальную машину. Команда git clone <remote_url> создает локальную копию удаленного репозитория с историей коммитов, ветками и файлами. Вот пример использования: git clone <remote_url> [<directory_name>] - клонирует удаленный репозиторий с указанным `URL` в новую локальную директорию.

Таким образом, команда git remote позволяет управлять удаленными репозиториями, в то время как команда git clone используется для создания локальной копии удаленного репозитория.

## Q32. В чём разница между `git pull` и `git fetch`?

`git pull` и `git fetch` — две разные команды, используемые для обновления локальной копии репозитория в `Git`. Вот их различия:

1. `git fetch`:

Команда `git fetch` извлекает все изменения из удаленного репозитория на вашу локальную машину, не объединяя их с текущей веткой. Это позволяет вам просмотреть изменения, внесенные в удаленный репозиторий, без перезаписи ваших локальных файлов. Все извлеченные ветки и коммиты сохраняются в удаленных отслеживаемых ветках, но не влияют на вашу рабочую ветку.

2. `git pull`:

Команда `git pull` выполняет две операции: `git fetch`, чтобы обновить удаленный репозиторий, и `git merge`, чтобы объединить извлеченные изменения с текущей веткой. Она извлекает изменения из удаленного репозитория и автоматически пытается объединить их с вашей рабочей копией. Если ваша текущая ветка имеет локальные изменения, `git pull` автоматически попытается объединить удаленные изменения с вашими локальными изменениями, возможно, создавая конфликты слияния.

Примеры использования: `git fetch origin` извлекает все изменения из удаленного репозитория `origin`, но не объединяет их с текущей веткой. `git pull origin main` извлекает изменения из удаленной ветки `main` в удаленном репозитории `origin` и объединяет их с текущей веткой.

В целом, если вам нужно только обновить локальную копию репозитория без автоматического объединения изменений, используйте `git fetch`. Если вы хотите обновить и объединить извлеченные изменения автоматически, используйте `git pull`.

## Q33. В чём разница между pull `request` и branch?

Вот разница между pull `request` и веткой:

1. Ветка (branch):

Ветка в Git представляет собой версию кодовой базы, которая может быть создана для работы над определенной функциональностью, исправлением ошибки или любым другим набором изменений. Ветка используется для изоляции работ, чтобы они не влияли на главную ветку или другие ветки до тех пор, пока они не будут готовы быть включенными в общий код. Ветка дает возможность параллельной разработки разных функций или исправлений, прежде чем они будут объединены в основную ветку проекта.

2. Запрос на включение изменений (pull `request`): `Pull request` — это механизм, предоставляемый хостинг-платформами для систем контроля версий (таких как `GitHub`, `GitLab`), позволяющий разработчикам запросить рассмотрение и включение своих изменений из одной ветки в другую. Обычно это означает запрос на включение изменений из ветки фичи или исправления ошибки в основную ветку проекта. `Pull request` предоставляет комментарии, обсуждения и возможность провести код-ревью перед тем, как изменения будут слиты (merged) в основную ветку проекта.

Таким образом, ветка представляет собой изолированную линию разработки, которая может содержать изменения и новую функциональность, в то время как pull `request` — это механизм, позволяющий предложить и обсудить включение этих изменений в целевую ветку проекта после проведения код-ревью и обсуждений. `Pull request` обычно осуществляется на хостинг-платформе и предоставляет более гибкий процесс сотрудничества и интеграции изменений между ветками.

## Q34. Почему мы не называем git pull `request` как push `request`?

Термин pull `request` используется в Git и других системах контроля версий для обозначения механизма запроса на включение изменений из одной ветки в другую. Вот несколько причин, почему используется pull `request`, а не push `request`:

1. Отражение действия на стороне вытягивания (pull):

Когда вы создаете pull `request`, вы фактически вытягиваете (pull) изменения из своей ветки в целевую ветку. Термин pull `request` логично отражает это действие, в отличие от push `request`, который может создать путаницу, так как push обычно ассоциируется с отправкой изменений из локальной копии в удаленный репозиторий.

2. Отражение намерения включения изменений:

Термин pull `request` более ясно отражает намерение разработчика включить свои изменения в целевую ветку. Это сообщение, что вы просите команду проекта или владельца репозитория вытащить (pull) ваши изменения и рассмотреть их в целях включения. `Push request` может быть менее понятным в этом контексте, так как он не ясно описывает желание включить изменения.

3. Предотвращение путаницы с существующими терминами:

Термин push `request` может привести к путанице с уже установленным термином push, который в Git используется для отправки изменений в удаленный репозиторий. Использование pull `request` и push в разных контекстах помогает избежать путаницы и понимать, что два термина относятся к разным функциям и действиям.

Следовательно, pull `request` был выбран как более удобочитаемый, описательный и логичный термин для обозначения механизма запроса на включение изменений в системах контроля версий.

## Q35. Что делает git bisect?

Чтобы найти коммит, который привел к проблеме или сломал что-то после операции слияния в Git, вы можете использовать команду `git bisect`.

Вот шаги, которые помогут вам найти проблемный коммит с использованием git bisect:

1. Отметьте текущую точку в истории коммитов, где проблема еще не существует, с помощью команды git bisect start.
2. Укажите точку, где проблема возникла, используя команду git bisect bad. Git автоматически перейдет к коммиту, который содержит эту проблему.
3. Теперь вам нужно указать коммит, в котором проблема еще не существует. Это может быть предыдущий коммит или любой другой коммит, который вы считаете рабочим состоянием. С помощью команды `git bisect good <commit>` вы определяете, что коммит хороший.
4. Git автоматически перейдет к другому коммиту между плохим и хорошим коммитами.
5. На каждой итерации проверяйте, есть ли проблема или нет. Если проблема существует, используйте команду git bisect bad. Если проблемы нет, используйте команду git bisect good.
6. Git будет продолжать делить диапазон коммитов пополам и перемещаться в загадочный коммит до тех пор, пока не найдет причину проблемы.
7. Когда Git находит проблемный коммит, вы получаете сообщение, а bisect может быть остановлен с помощью команды git bisect reset.

Таким образом, git bisect помогает вам эффективно перебирать коммиты до тех пор, пока вы не найдете тот, который привел к проблеме после операции слияния.

## Q36. В чём разница между Git от `GitHub`?

Да, конечно! Вот основное отличие между Git и `GitHub`:

1. Git: Git — это система контроля версий с распределенной архитектурой. Она разработана Линусом Торвальдсом и предоставляет возможность отслеживать изменения в исходном коде и координировать работу между различными разработчиками или командами. Git позволяет создавать репозитории с кодовой базой, которые могут быть клонированы и синхронизированы с различными участниками проекта. Он предоставляет мощные средства для управления версиями файлов и слияния изменений между ветвями кода. Git работает локально на компьютере разработчика и позволяет сохранять изменения в локальном репозитории, а также взаимодействовать с удаленными репозиториями.

2. `GitHub`: `GitHub` — это хостинг-платформа для Git, которая предоставляет инфраструктуру для удаленного хранения, совместной работы и управления репозиториями Git. `GitHub` обеспечивает централизованное хранение репозиториев и предоставляет различные функциональные возможности для совместной работы над проектами. Это веб-платформа, где разработчики и команды могут публиковать свои репозитории, делать и контролировать изменения с помощью pull `request`, проводить код-ревью, отслеживать ошибки, вести обсуждения и многое другое. `GitHub` также предоставляет возможности для автоматической сборки и развертывания программного обеспечения с помощью интеграции с инструментами `Continuous Integration / Continuous Deployment` (`CI / CD`).

Таким образом, Git является системой контроля версий, позволяющей управлять изменениями и координировать работу, а `GitHub` — это хостинг-платформа для Git, которая предоставляет дополнительные возможности для совместной разработки и управления репозиториями.
