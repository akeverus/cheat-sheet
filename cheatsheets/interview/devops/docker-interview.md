## Q1. (!) Что такое `Docker Containers`?

Проще говоря, `Docker Containers` состоят из приложений и всех их зависимостей. Они совместно используют ресурсы ядра и системы с другими контейнерами и работают как изолированные системы в основной операционной системе. Основная цель `Docker Containers` избавиться от зависимости от инфраструктуры при развертывании и запуске приложений. Это означает, что любое контейнерное приложение может работать на любой платформе независимо от используемой инфраструктуры. Технически это просто экземпляры `Docker Images` во время выполнения.

Практическая ценность ответа обычно повышается, если дополнить определение операционным контекстом: как решение ведёт себя под нагрузкой, при сбоях и в процессе сопровождения. На интервью ожидают, что вы назовёте критерии выбора и способ валидации решения через метрики и проверяемый сценарий.

## Q2. (!) Что такое `Docker Images`?

**Docker Image** — неизменяемый шаблон для создания контейнеров: код приложения, зависимости, runtime, метаданные. Образ идентифицируется репозиторием и тегом (например, `nginx:1.24`). Развернуть можно в любой среде `Docker`; из одного образа можно запустить много контейнеров.

Образ строится из слоёв (layers): каждый слой — результат одной инструкции в `Dockerfile` (`RUN`, `COPY`, `ADD`). Слои кэшируются и переиспользуются между образами. Образ идентифицируется репозиторием и тегом (например, `nginx:1.24`). Базовый образ задаётся в `FROM` (alpine, `eclipse-temurin` и т.д.). Команда `docker build -t myapp:1.0 .` создаёт образ из `Dockerfile` в текущем каталоге.

**Практика:** для продакшена использовать конкретный тег (например, `eclipse-temurin:17-jre-alpine`), не `latest`. `Multi-stage` сборка уменьшает размер образа: в первой стадии — сборка (`Maven / Gradle`), во второй — только `JAR` и `JRE. Образы хранить в registry (`Docker` Hub, `Harbor`, `ECR`) и подписывать по версии приложения.

## Q3. (!) Что такое `DockerFile`?

**Dockerfile** — текстовый файл с инструкциями для сборки образа: `FROM` (базовый образ), `COPY / ADD`, `RUN`, `ENV`, `EXPOSE`, `CMD / ENTRYPOINT`. Имя по умолчанию — `Dockerfile`; контекст сборки — каталог, передаваемый в `docker build` (например, `docker build -t myapp:1.0 .`). Каждая инструкция создаёт слой образа; слои кэшируются.

Типичные инструкции: `FROM` (базовый образ), `WORKDIR` (рабочий каталог), `COPY / ADD` (копирование файлов), `RUN` (выполнение команд при сборке), `ENV` (переменные окружения), `EXPOSE` (порты), `CMD / ENTRYPOINT` (команда запуска контейнера). Каждая инструкция создаёт слой образа. Многоступенчатая сборка (`multi-stage`): несколько `FROM` — финальный образ содержит только артефакты последней стадии, без инструментов сборки. Пример: `FROM maven AS build ... FROM eclipse-temurin:17-jre` — итоговый образ только с `JAR` и `JRE`.

**Порядок слоёв:** редко меняющиеся инструкции (`FROM`, `ENV`) — в начале; `COPY` зависимостей (`pom.xml`, `package.json`) и `RUN` установки — перед `COPY` кода, чтобы кэш слоёв переиспользовался при изменении только кода. Итоговый образ меньше: в последней стадии только `COPY / CMD`, без `Maven` и исходников. Для `Java`: `multi-stage / JRE` во второй — типичный размер образа 200–400 `MB` вместо 600+ `MB` с полным `JDK`.

## Q4. (!) Что такое `Docker Hypervisor`?

`Docker Hypervisor` — это программное обеспечение, обеспечивающее виртуализацию, из-за которого его иногда называют монитором виртуальной машины. Это разделяет ресурсы хост-системы и выделяет их каждой установленной гостевой среде. Это означает, что на одну хост-систему можно установить несколько ОС. `Docker Hypervisors` бывают двух типов:

1. `Native Hypervisor`: этот тип также называется гипервизором без операционной системы и работает непосредственно на базовой хост-системе, что также обеспечивает прямой доступ к аппаратному обеспечению хоста, поэтому для него не требуется базовая ОС. 2. `Hosted Hypervisor`: этот тип использует базовую операционную систему хоста, на которой установлена существующая ОС.

## Q5. (!) Что вы можете сказать о `Docker Compose`?

**Docker Compose** — инструмент для описания и запуска мультиконтейнерного приложения в одном файле (обычно `docker-compose.yml`): сервисы, сети, тома, зависимости. Команды: `docker compose up` — запуск, `docker compose down` — остановка. Сервисы обращаются друг к другу по имени (например, `db:5432`).

Это файл `YAML`, содержащий все сведения о различных службах, сетях и томах, которые необходимы для настройки приложения на основе `Docker`. Итак, `docker-compose` используется для создания нескольких `Containers`, их размещения и установления связи между ними. Для связи между контейнерами порты открываются каждым контейнером.

**Практика:** в `docker-compose.yml` задают сервисы (image или build), порты, volumes, environment, `depends_on. Команды: `docker compose up -d` — запуск в фоне; `docker compose down` — остановка и удаление контейнеров; `docker compose ps` — статус. Сеть по умолчанию общая — сервисы обращаются друг к другу по имени сервиса (например, `db:5432`). Для продакшена образы тегировать по версии; секреты — через env-файл или внешнее хранилище, не в репо.

## Q6. (!) Что такое `Docker Namespace`?

`Docker Namespace` — это, по сути, функция `Linux`, которая обеспечивает взаимоисключающее разделение ресурсов ОС. Это формирует основную концепцию контейнеризации, поскольку пространства имен вводят слой изоляции между контейнерами. В `Docker` пространства имен обеспечивают переносимость `Containers` и не влияют на базовый хост. Примеры типов пространств имен, которые в настоящее время поддерживаются `Docker`: `PID`, `Mount`, `User`, `Network`, `IPC`.

**Практика:** `PID` namespace — изоляция процессов (контейнер видит только свои процессы); `Network` — отдельный сетевой стек; `Mount` — изолированная файловая система; `IPC` — изоляция очередей и семафоров; `UTS` — изолированное hostname. Без namespace контейнер бы видел все процессы и сеть хоста. `Cgroups` дополняют namespace ограничением ресурсов (`CPU`, память). В `Kubernetes` каждый под имеет свои namespace; изоляция между подами обеспечивается на уровне сети и файловой системы.

## Q7. Какая команда отображает состояние всех `Containers`?

Команда **`docker ps -a`** показывает все контейнеры (запущенные и остановленные). Без `-a` выводятся только запущенные. Дополнительно: `-q` — только `ID`, `--filter "status=exited"` — фильтр по статусу, `--format` — свой формат вывода.

```bash
docker ps -a
```

**Практика:** `docker ps` без `-a` показывает только запущенные контейнеры; `-a` (--all) — все контейнеры, включая остановленные. Фильтры: `--filter "status=exited"`, `--filter "name=myapp"`. Формат вывода: `--format "table {{.ID}}\t{{.Image}}\t{{.Status}}"`. Для скриптов: `-q` — только `ID` контейнеров. Статусы: created, running, paused, exited (с кодом выхода).

## Q8. При каких обстоятельствах вы потеряете данные, хранящиеся в `Container`?

Данные теряются при **удалении контейнера** (`docker rm`) или **пересоздании** контейнера без примонтированного тома или volume. Файловая система контейнера эфемерна: всё, что записано внутри контейнера без volume, исчезает при удалении. Чтобы сохранить данные — использовать **volumes** (named volume или bind mount).

Данные внутри контейнера (файловая система контейнера) теряются при: `docker rm container_id` (удаление контейнера); пересоздании контейнера без примонтированного тома. Чтобы сохранить данные: использовать volumes (`docker volume create`, монтирование в контейнер) или bind mount (`-v /host/path:/container/path`). `Volume` переживает удаление контейнера; при следующем запуске можно примонтировать тот же volume. Без volume все изменения внутри контейнера (записанные файлы, БД) исчезают при удалении контейнера.

**Практика:** для БД и состояний всегда использовать named volume: `docker run -v mydata:/data .... В `docker-compose`: `volumes: - dbdata:/var/lib/postgresql/data` в сервисе и объявление `volumes: dbdata:` в корне. При `docker compose down -v` тома удаляются — для продакшена не использовать `-v` при down или делать бэкапы перед удалением. Bind mount для конфигов: `-v ./config:/app/config` — изменения на хосте видны в контейнере.

## Q9. Что такое `Docker Images Registry`?

Проще говоря, `Docker Images Registry` — это область, в которой хранятся `Docker Images`. Вместо того, чтобы каждый раз преобразовывать приложения в `Containers`, разработчик может напрямую использовать `Images`, хранящиеся в `Registry`. Этот `Registry` может быть общедоступным или частным, а `Docker` Hub является самым популярным и известным общедоступным `Registry`.

**Практика:** `docker push myregistry.io/myimage:tag` — публикация образа; `docker pull myregistry.io/myimage:tag` — загрузка. Для приватного registry — `docker login myregistry.io. В CI/CD образ собирают и пушат в registry (`Harbor`, `ECR`, `GCR`); в `Kubernetes` в манифесте указывают image из registry. Для продакшена использовать приватный registry и конкретные теги (не `latest`); образы сканировать на уязвимости (`Trivy`) перед деплоем.

## Q10. Сколько существует компонентов `Docker`?

Есть три компонента:

1. `Docker Client`: этот компонент выполняет операции «сборки» и «запуска» с целью установления связи с хостом `Docker`.
2. `Docker Host`: этот компонент содержит основной демон `Docker` и хост-`Containers`, а также связанные с ними `Images`. Демон устанавливает соединение с реестром `Docker`.
3. `Docker Registry`: этот компонент хранит `Docker Images`. `Registry` может быть публичным или частным. Самые известные публичные реестры `Docker` Hub и `Docker Cloud`.

## Q11. Что такое `Docker` Hub?

Это общедоступный облачный реестр, предоставляемый `Docker` для хранения общедоступных `Images`, `Containers`, а также для обеспечения их поиска и обмена ими. `Images` можно отправить в `Docker` Hub с помощью команды:

```bash
docker push
```

## Q12. Какая команда экспортирует `Image Docker` в виде архива?

Это можно сделать с помощью команды docker save, синтаксис которой следующий:

```bash
docker save -o <exported_name>.tar <image_name>:<tag>
```

Используется имя образа и тег (например, `myapp:1.0`), не имя контейнера. Результат — tar-архив со всеми слоями образа. Импорт на другом хосте: `docker load -i <`exported_name`>.tar. Отличие от `docker export` (экспорт файловой системы контейнера в tar): save сохраняет образ со всеми слоями и метаданными; export — снимок файловой системы одного контейнера, без истории слоёв.

## Q13. Какая команда импортует `Image Docker` на другой хост `Docker`?

Это можно сделать с помощью команды docker load, а синтаксис такой:

```bash
docker load -i <export_image_name>.tar
```

`docker load` читает tar-архив, созданный `docker save`, и загружает образ(ы) в локальное хранилище `Docker. После загрузки образ доступен как обычно (`docker run <image>:<tag>`). Для импорта контейнера, экспортированного через `docker export`, используют `docker import file.tar [repo:tag]` — создаётся образ из содержимого tar (без слоёв образа). В `CI / CD` чаще используют registry: push на один хост, pull на другом.

## Q14. (!) Можно ли удалить `PAUSED Container` из `Docker`?

Нет. Контейнер в состоянии **PAUSED** нельзя удалить командой `docker rm` — сначала нужно остановить: `docker unpause container_id`, затем `docker stop container_id` (переход в `EXITED`), после чего `docker rm container_id. Принудительное удаление без остановки: `docker rm -f container_id`.

Сначала контейнер нужно остановить: `docker unpause container_id` (если был paused), затем `docker stop container_id` — контейнер перейдёт в статус exited. После этого `docker rm container_id` удалит контейнер. Принудительное удаление без остановки: `docker rm -f container_id` — контейнер будет убит и удалён. Для удаления всех остановленных контейнеров: `docker container prune`.

## Q15. Какая команда используется для проверки версии клиента и сервера `Docker`?

## Q18. (!) Может ли `Container` перезапускаться сам по себе?

Да, это возможно только при использовании определенных политик, определенных Dockerом, при использовании команды запуска `Docker`. Ниже приведены доступные политики:
<br/>1. Off: в этом случае `Container` не будет перезапущен в случае его остановки или сбоя.2. `On-failure`: здесь `Container` перезапускается сам по себе только тогда, когда возникают сбои, не связанные с пользователем.3. `Unless-stopped`: использование этой политики гарантирует, что `Container` может быть перезапущен только тогда, когда пользователь выполнит команду для его остановки.4. `Always`: независимо от сбоя или остановки `Container` всегда перезапускается в этом типе политики. <br/>Эти политики могут использоваться как:

```bash

```

## Q19. (!) В чём разница между `Docker Image` и `Docker Layer`?

**Docker Image** строится из серии **Docker Layer**. Каждый слой соответствует инструкции в `Dockerfile`. Проще говоря, слой — это тоже образ; см. пример `Dockerfile` ниже:

```dockerfile
FROM ubuntu:18.04

COPY . /myapp

RUN make /myapp

CMD python /myapp/app.py
```

**Важно:** в `Docker` каждый слой по сути является образом. Инструкции в `Dockerfile` добавляют `Docker Layer` к образу; каждый слой можно рассматривать как промежуточный образ. В примере выше 4 инструкции — 4 слоя в результирующем образе.

## Q20. Каково назначение в команде запуска `Docker` параметра -v?

Синтаксис запуска `Docker` при использовании volumes:

```bash

```

Параметр volume используется для синхронизации каталога контейнера с любым из каталогов хоста. Рассмотрим приведенную ниже команду в качестве примера:


Приведенная выше команда монтирует каталог /data/app на хосте в usr/src/app каталог. Мы можем синхронизировать `Container` с файлами данных с хоста без необходимости его перезапуска. Это также обеспечивает безопасность данных в случае удаления контейнера. Это гарантирует, что даже если `Container` удален, данные контейнера существуют в расположении хоста, сопоставленного с volume, что делает его самым простым способом хранения данных контейнера.

## Q21. Где в `Docker` хранятся `Docker Volumes`?

**Краткий ответ:** именованные и анонимные тома хранятся на хосте (например, `/var/lib/docker/volumes/`). Каждый том — подкаталог с именем тома, внутри `_data` с файлами. На `Windows` (`Docker Desktop`) путь виртуализирован (`WSL2`).

`Docker Volumes` создаются и управляются `Docker`, и к ним не могут получить доступ объекты, не относящиеся к `Docker. Они хранятся в файловой системе хоста `Docker` по адресу:

```text
/var/lib/docker/volumes/
```

**Практика:** именованные тома — подкаталог с именем тома, внутри `_data` с файлами. На `Windows` (`Docker Desktop`) путь виртуализирован (`WSL2`). Для бэкапа: `docker run --rm -v volname:/data -v $(pwd):/backup alpine tar cvf /backup/vol.tar /data`.

Именованные тома: подкаталог с именем тома, внутри — `_data` с файлами. Анонимные тома — случайное имя в том же каталоге. На `Windows` (`Docker Desktop`) путь виртуализирован (например, `\\wsl$\docker-desktop-data\data\docker\volumes\` в WSL2). Прямое редактирование файлов в `_data` возможно, но предпочтительнее монтировать в контейнер и менять изнутри или через `docker cp`. Для бэкапа: копирование из тома в tar или `docker run ... tar cvf`.

## Q27. В чём разница между `Daemon Logging` и `Container Logging`?

В `Docker` ведение журнала поддерживается на 2 уровнях: ведение журнала на уровне демона или ведение журнала на уровне контейнера. **Daemon Level:** этот тип ведения журнала имеет четыре уровня: `Debug`, `Info`, `Error` и `Fatal`:

1. `Debug`: имеет все данные, которые произошли во время выполнения процесса демона.
2. `Info`: содержит всю информацию вместе с информацией об ошибках во время выполнения процесса демона.
3. `Error`: имеют те ошибки, которые произошли во время выполнения процесса демона.
4. `Fatal`: содержит фатальные ошибки, возникшие во время выполнения. **Container Level:**

1. Ведение журнала уровня контейнера можно выполнить с помощью команды:

```bash
sudo docker run -it <container_name> /bin/bash
```

2. Чтобы проверить наличие logs уровня контейнера, мы можем запустить команду:

```bash
sudo docker logs <container_id>
```

## Q28. Как установить связь между `Docker Host` и `Linux Host`?

Связь обеспечивается сетью `Docker`: по умолчанию создаётся мост **`docker0`**; контейнеры получают `IP` из подсети моста. С хоста к контейнеру — по `IP` контейнера или через проброс порта `-p 8080:80. С контейнера к хосту — gateway моста (`172.17.0.1`) или **`host.docker.internal`** (`Docker Desktop`). Контейнеры между собой — общая сеть (`docker network create mynet`, `--network mynet`); по имени сервиса резолвится `DNS`.

**Практика:** `Docker` создаёт мост docker0 и сетевые пространства имён. С хоста к контейнеру — по `IP` контейнера или через `-p 8080:80` (проброс порта). С контейнера к хосту — gateway сети (`172.17.0.1` по умолчанию) или `host.docker.internal` (`Docker Desktop`). Режим `--network host` использует сетевой стек хоста напрямую — контейнер видит те же порты и интерфейсы, что и хост; изоляции по сети нет. Для связи контейнеров между собой — общая пользовательская сеть (`docker network create mynet`, `--network mynet` при run); по имени сервиса резолвится `DNS` внутри сети. На Linux `ip addr show docker0` покажет адрес моста; контейнеры получают адреса из подсети моста (например `172.17.0.0/16`).

## Q29. Как лучше всего удалить `Container`?

Рекомендуемый порядок: сначала остановить контейнер (**`docker stop container_id`**), затем удалить (**`docker rm container_id`**). Для остановленного контейнера можно сразу `docker rm container_id`. Для принудительного удаления запущенного: **`docker rm -f container_id`** — контейнер будет убит и удалён без ожидания остановки. Удаление всех остановленных: `docker container prune`.

```bash
# Остановка контейнера, затем удаление
docker stop <container_id>
docker rm <container_id>
# Или одной командой: docker rm -f <container_id>
```

Рекомендуемый порядок: сначала `docker stop` (graceful shutdown по `SIGTERM`, затем `SIGKILL` по истечении timeout), затем `docker rm` — так приложение успевает завершить соединения и сохранить состояние. `docker rm -f` принудительно останавливает и удаляет контейнер без ожидания; использовать при зависших контейнерах. Для удаления с томами: `docker rm -v container_id` (анонимные тома, привязанные к контейнеру, удаляются). Именованные тома (созданные через `docker volume create`) не удаляются при rm контейнера. Массовая очистка остановленных контейнеров: `docker container prune`; с неиспользуемыми томами: `docker system prune -a --volumes` (осторожно — удалит все неиспользуемые тома).

## Q33. (!) Опишите жизненный цикл контейнера `Docker`?

Различные этапы `Docker Container` от начала его создания до конца называются жизненным циклом `Docker Container`. Наиболее важными этапами являются:

1. `Created`: это состояние, когда `Container` только что создан, но еще не запущен.
2. `Running`: в этом состоянии `Container` будет работать со всеми связанными с ним процессами.
3. `Paused`: это состояние возникает, когда работающий `Container` был приостановлен.
4. `Stopped`: это состояние возникает, когда работающий `Container` был остановлен.
5. `Deleted`: в этом `Container` находится в мертвом состоянии.

## Q34. Как использовать `Docker` для `Multiple Application Environments`?

Здесь на помощь придет функция `docker-compose`. В файле `docker-compose` мы можем определить несколько services, networks и containers вместе с сопоставлением volumes в чистом виде, а затем мы можем просто вызвать команду:

`docker-compose` up

Когда задействовано несколько сред мы хотели бы определить зависимости и процессы для конкретного сервера для запуска приложения. В этом случае мы можем продолжить создание файлов `docker-compose` для конкретной среды с именем «`docker-compose`.{environment}.yml», а затем в зависимости от среды мы можем настроить и запустить приложение.

## Q35. Как гарантировать, что `Container` 1 запускается перед контейнером 2 при использовании `Docker Compose`?

Docker Compose не ждёт, пока какой-либо `Container` будет «готов», прежде чем переходить к следующему контейнеру. Чтобы добиться порядка выполнения, мы можем использовать `depends_on`, как показано в образце файла `docker-compose.yml` ниже:

version: "2.4"

services:

`backend`:

  build: .
  `depends_on`:
    - db

db:

image: postgres

Внедрение сервисных зависимостей имеет различные причины и следствия:

1. Команда `docker-compose` up запускает службы в указанном порядке зависимости. В приведенном выше примере `Container` db запускается перед серверной частью.
2. `docker-compose` up SERVICE_NAME по умолчанию включает зависимости, связанные со службой. В данном примере запуск `docker-compose` up `backend` создает и запускает БД (зависимость от бэкенда).
3. Наконец, команда `docker-compose` stop также останавливает службы в порядке указанной зависимости. В данном примере серверная служба останавливается перед службой БД.
