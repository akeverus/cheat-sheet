## Q1. (!) Что такое inode и что он хранит?

`inode` — это структура данных файловой системы, которая хранит все метаданные файла, кроме его имени. Каждому файлу и директории соответствует ровно **один inode** со своим номером; посмотреть номер можно через `ls -i`.

Что хранит inode:

- Тип файла (`regular`, `directory`, `symlink`, `device`).
- Права доступа и владельца (uid/gid).
- Размер и timestamps (`atime`, `mtime`, `ctime`).
- Счётчик жёстких ссылок.
- Указатели на блоки данных на диске.

**Где же имя?** Имени файла в inode нет — оно лежит в directory entry, которая связывает имя с inode-номером. Именно эта развязка «имя ↔ inode» делает возможными hard-link-и: несколько записей в разных директориях указывают на один и тот же inode, то есть на один и тот же файл.

```bash
stat /etc/hostname       # покажет inode, размер, права, timestamps
df -i                    # мониторинг inode usage (inode могут кончиться при живом диске)
```

**Подводный камень:** ошибка «No space left on device» возникает не только при заполненном диске. Если создать миллионы мелких файлов, inode могут закончиться раньше, чем место — и запись упадёт, хотя `df -h` покажет свободные гигабайты. Проверять надо обе вещи: `df -h` и `df -i`.

## Q2. В чём разница между hard link и symlink?

Коротко: **hard link** — это второе равноправное имя того же файла (та же inode), а **symlink** — отдельный файл-указатель, внутри которого хранится путь к цели. Отсюда и все различия:

| Свойство | Hard link | Symlink (soft link) |
|---|---|---|
| Указывает на | inode файла | путь (строка) |
| Можно на директорию | нет (кроме root в некоторых FS) | да |
| Через точки монтирования | нет | да |
| Переживёт удаление оригинала | да, данные живут до последней ссылки | станет битой ссылкой |
| `ls -l` | не видно что это link | `->` и путь |
| Команда создания | `ln target link` | `ln -s target link` |

```bash
ln   /data/file.txt  hard.txt       # hard
ln -s /data/file.txt soft.txt       # soft
```

**Почему так:** hard-link разделяет с оригиналом ту же inode, поэтому при удалении исходного имени данные не пропадают — файл живёт, пока счётчик ссылок не упадёт до нуля. Symlink хранит лишь строку-путь и ничего не знает о цели: удалили оригинал — ссылка «повисла» (битый symlink). Поэтому symlink умеет то, что hard-link не может: указывать на директории и пересекать границы файловых систем.

## Q3. (!) Как устроены права доступа в Linux и как их читать?

В Linux у каждого файла три категории субъектов — **владелец (User), группа (Group), все остальные (Others)** — и для каждой категории три права: **читать (r), писать (w), исполнять (x)**. Это и есть классическая модель UGO + rwx. В выводе `ls -l` она читается слева направо:

```text
-rwxr-x--- 1 app devops 1024 Apr 20 12:00 run.sh
 │└┬┘└┬┘└┬┘
 │ │  │  └── Others: ---
 │ │  └───── Group:  r-x
 │ └──────── User:   rwx
 └────────── Type: - файл, d директория, l symlink, b/c device, s socket, p pipe
```

Значения для файлов и директорий:

Ключевой нюанс: на директории те же буквы `rwx` означают совсем другое, чем на файле.

| Бит | Для файла | Для директории |
|---|---|---|
| `r` | читать содержимое | листинг `ls` |
| `w` | писать/менять | создавать/удалять файлы внутри |
| `x` | исполнять | входить (`cd`) и обращаться к файлам по имени |

Численное представление (octal) — каждый бит это степень двойки, права складываются:

```text
r=4, w=2, x=1
rwx = 7, rw- = 6, r-x = 5, r-- = 4
```

**Пример:** `chmod 750 run.sh` → `rwxr-x---` (владелец — всё, группа — читать и запускать, остальные — ничего).

**Частая ловушка:** на директории без бита `x` нельзя зайти (`cd`) и нельзя обратиться к файлам внутри по имени — даже если у самого файла права открыты. Поэтому `r` без `x` на каталоге почти бесполезен: имена увидите, а содержимое файлов — нет.

## Q4. Что такое `chmod`, `chown`, `chgrp`?

Три команды, которые меняют разные части метаданных доступа: `chmod` — сами права (rwx), `chown` — владельца (и при желании группу), `chgrp` — только группу.

| Команда | Назначение | Пример |
|---|---|---|
| `chmod` | изменить права | `chmod 640 file` / `chmod u+x,go-w file` |
| `chown` | изменить владельца | `chown app:devops file` |
| `chgrp` | изменить группу | `chgrp devops file` |

`chmod` принимает два формата: octal (`640`) задаёт права целиком, символьный (`u+x,go-w`) меняет их точечно — добавить/убрать бит конкретной категории. Опция `-R` — рекурсивно по дереву. Опция `--reference=other` — скопировать права с другого файла, не вычисляя их вручную.

```bash
chmod -R g+w /var/log/myapp     # дать группе запись в логи
chown -R app:app /opt/app       # все файлы приложения под app:app
```

## Q5. Что такое SUID, SGID и sticky bit?

Это три специальных бита поверх обычных `rwx`, которые меняют поведение при запуске или внутри директории. В выводе `ls` они занимают место бита `x` соответствующей категории.

| Бит | Символ | На файле | На директории |
|---|---|---|---|
| SUID | `s` в user-x | запуск от имени владельца (`passwd` работает root'ом) | — |
| SGID | `s` в group-x | запуск от имени группы | новые файлы наследуют группу директории |
| Sticky | `t` в other-x | — | удалять/переименовывать может только владелец (`/tmp`) |

Зачем они нужны на практике: **SUID** позволяет обычному пользователю выполнить программу с правами владельца — классика — `passwd`, которому нужен root, чтобы записать в `/etc/shadow`. **SGID** на каталоге удобен для общих папок: всё созданное внутри автоматически попадает в нужную группу. **Sticky bit** защищает общие на запись директории вроде `/tmp`: писать туда могут все, но удалять чужие файлы — нет.

```bash
ls -l /usr/bin/passwd
# -rwsr-xr-x 1 root root ...   # s = SUID

ls -ld /tmp
# drwxrwxrwt ...               # t = sticky
```

**Подводный камень:** SUID-бит — лакомая цель для эскалации привилегий. Любая дыра в SUID-программе даёт атакующему права её владельца (часто root). Поэтому SUID на собственных скриптах ставить нельзя, а аудит SUID-файлов (`find / -perm -u+s`) — стандартный шаг при проверке безопасности хоста.

## Q6. (!) Что такое `umask` и как он влияет на права новых файлов?

`umask` — это маска, которая определяет, какие биты прав **снимаются** у каждого нового файла и каталога. Сам процесс создаёт файл с «желаемыми» правами, а ядро гасит в них биты, указанные в umask.

- Базовые права при создании: `0666` для файлов, `0777` для директорий (бит `x` файлам по умолчанию не даётся — это защита от случайного запуска).
- Итоговые права считаются как `default & ~umask` — то есть из базовых убираются биты, выставленные в маске.

| umask | Новый файл | Новая директория |
|---|---|---|
| `022` | `644` (rw-r--r--) | `755` |
| `027` | `640` | `750` |
| `077` | `600` | `700` |

```bash
umask                  # показать текущее значение
umask 027              # задать для текущего shell
```

**Рекомендация:** для сервисов, которые пишут чувствительные файлы (логи с PII, ключи, конфиги с секретами), ставьте `umask 027` (закрыть запись от группы и всё — от остальных) или `077` (доступ только владельцу). Так новые файлы изначально создаются с безопасными правами, и не нужно потом гоняться за ними `chmod`-ом.

## Q7. (!) Через какие состояния проходит процесс в Linux?

Процесс за свою жизнь переходит между несколькими состояниями планировщика: то выполняется на CPU, то спит в ожидании события или IO, может быть остановлен сигналом, а после завершения ненадолго становится zombie. Текущее состояние видно в `ps` в колонке `STAT`:

| Код | Состояние | Описание |
|---|---|---|
| `R` | Running / Runnable | выполняется или готов к запуску на CPU |
| `S` | Sleeping (interruptible) | ждёт события, можно разбудить сигналом |
| `D` | Uninterruptible sleep | ждёт IO, сигналом не разбудить (опасное состояние) |
| `T` | Stopped | остановлен `SIGSTOP` / точкой останова |
| `Z` | Zombie | завершён, но родитель ещё не забрал exit-code |
| `X` | Dead | kernel-видимое, недолго |

Переходы между состояниями по жизненному циклу процесса:

- Старт: процесс появляется через `fork + exec` и попадает в `Running`.
- `Running` → `Sleeping`: процесс уходит в ожидание IO (`wait IO`).
- `Sleeping` → `Running`: IO готово или пришёл сигнал (`IO ready / signal`).
- `Running` → `Stopped`: получен `SIGSTOP`.
- `Stopped` → `Running`: получен `SIGCONT`.
- `Running` → `Zombie`: процесс завершился (`exit`).
- `Zombie` → завершение: родитель забрал exit-code через `parent wait()`, и запись о процессе исчезает.

**Подводный камень — состояние `D`.** Это непрерываемый сон: процесс заблокирован внутри системного вызова в ожидании IO, и его нельзя разбудить даже сигналом. Поэтому `kill -9` на него не действует — ядро не доставит сигнал, пока IO не завершится. Висящий в `D` процесс почти всегда указывает на проблему с диском, контроллером или зависший NFS-маунт; лечить нужно причину (storage), а не сам процесс.

## Q8. Что такое zombie и orphan процессы?

Оба термина описывают разрыв связи «родитель ↔ ребёнок», но в противоположных направлениях: zombie — ребёнок завершился, но родитель его не «похоронил»; orphan — родитель умер, а ребёнок ещё жив.

- **Zombie (`Z`)** — процесс уже завершился, но в таблице процессов осталась запись с его exit-кодом, потому что родитель ещё не вызвал `wait()`/`waitpid()`, чтобы его забрать. Сам zombie ресурсов не ест — только удерживает PID. Множество zombie — это симптом бага в родителе: он порождает детей, но не «жнёт» их.
- **Orphan** — родитель умер раньше ребёнка. Такой осиротевший процесс автоматически усыновляется `init` (PID 1, обычно `systemd`), который и заберёт его `wait()`-ом после завершения. Это штатный, безопасный механизм — именно поэтому orphan, в отличие от zombie, обычно не проблема.

```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'     # найти zombies
```

**Как чинить zombie:** убить или перезапустить родителя — тогда дети-zombie достаются `init`, который их и забирает. Сам zombie `kill`-ом не убрать: он уже мёртв. Если не вмешаться, PID будут утекать и в пределе исчерпают лимит процессов.

## Q9. (!) Какие команды для просмотра процессов и ресурсов?

Инструменты делятся по уровню детализации: `ps`/`pgrep`/`pstree` дают статичный снимок и поиск процессов; `top`/`htop` — живую интерактивную картину; `lsof`/`strace`/`/proc` — глубокую отладку одного конкретного процесса; `iotop`/`vmstat`/`mpstat` — нагрузку по ресурсам (IO, CPU, память).

| Команда | Назначение |
|---|---|
| `ps aux` / `ps -ef` | снимок всех процессов |
| `top` | интерактивный top |
| `htop` | удобнее top, нужно ставить отдельно |
| `pgrep -af nginx` | найти процессы по имени/cmdline |
| `pidof nginx` | получить PID |
| `pstree -p` | дерево процессов с PID |
| `lsof -p PID` | открытые файлы/сокеты процесса |
| `strace -p PID` | системные вызовы в реальном времени |
| `iotop`, `iostat` | IO per process / диск |
| `vmstat 1`, `mpstat -P ALL 1` | CPU / память |
| `/proc/<pid>/` | вся инфа о процессе (fd, maps, status) |

На собеседовании достаточно показать ход мысли: «найти процесс (`pgrep`/`ps`) → посмотреть нагрузку (`top`) → копнуть вглубь (`strace`/`lsof`/`/proc`)». Типовой старт — отсортировать процессы по памяти:

```bash
ps -eo pid,ppid,%cpu,%mem,cmd --sort=-%mem | head   # топ по памяти
```

## Q10. (!) Что такое сигнал и какие самые важные?

Сигнал — это асинхронное уведомление, которое ядро или другой процесс посылает процессу, чтобы прервать его и сообщить о событии (нажат `Ctrl+C`, упал child, пора завершаться). Это самый базовый механизм IPC в Unix.

Получив сигнал, процесс может повести себя тремя способами:

1. **Проигнорировать** — если сигнал игнорируемый (`SIGKILL` и `SIGSTOP` игнорировать нельзя).
2. **Поймать и обработать** — назначить свой handler через `signal()`/`sigaction()` (так делают graceful shutdown).
3. **Выполнить действие по умолчанию** — у каждого сигнала оно своё (завершиться, сделать core dump, остановиться и т.д.).

Важнейшие сигналы:

| № | Имя | Default | Можно поймать? | Когда использовать |
|---|---|---|---|---|
| 1 | `SIGHUP` | terminate | да | перечитать конфиг (nginx, rsyslog) |
| 2 | `SIGINT` | terminate | да | `Ctrl+C` |
| 3 | `SIGQUIT` | core dump | да | `Ctrl+\`, для дампа JVM thread dump |
| 9 | `SIGKILL` | kill | ❌ нельзя | жёсткий kill |
| 15 | `SIGTERM` | terminate | да | graceful shutdown (`kill PID`) |
| 17 | `SIGCHLD` | ignore | да | умер child-процесс |
| 19 | `SIGSTOP` | stop | ❌ нельзя | пауза |
| 18 | `SIGCONT` | resume | да | возобновить |

## Q11. В чём разница между `SIGTERM`, `SIGKILL` и `SIGHUP`?

Главное различие — в том, **даёт ли сигнал процессу шанс среагировать**. `SIGTERM` — вежливая просьба завершиться, её можно поймать и прибраться. `SIGKILL` ловить нельзя — ядро убивает процесс мгновенно. `SIGHUP` исторически про обрыв терминала, а на практике — это «перечитай конфиг».

| Сигнал | Можно поймать | Graceful | Применение |
|---|---|---|---|
| `SIGTERM` (15) | да | да | вежливое завершение, процесс может закрыть файлы, завершить запросы |
| `SIGKILL` (9) | ❌ нет | ❌ нет | kernel убивает мгновенно, файлы не закрыты, данные могут потеряться |
| `SIGHUP` (1) | да | — | раньше — «оторвался терминал», сейчас — перечитать конфиг (`nginx -s reload`) |

**Эмпирическое правило:** сначала `kill` (это `SIGTERM`) — пусть процесс закроет соединения, дозапишет буферы, освободит ресурсы. Дай ему 10–30 секунд. Только если он завис — `kill -9` (`SIGKILL`). Сразу `kill -9` бить не стоит: рискуете потерять незаписанные данные и оставить файлы/сокеты в неконсистентном состоянии.

## Q12. Что такое file descriptor?

`File descriptor (fd)` — это небольшое неотрицательное целое-«хэндл», которое ядро возвращает при открытии ресурса (`open()`, `socket()`, `pipe()`). По сути это индекс в таблице открытых файлов процесса: дальше процесс работает с ресурсом через этот номер — `read`/`write`/`close`. Благодаря такой абстракции файл, сокет и pipe выглядят для программы одинаково.

Три fd открыты у каждого процесса по умолчанию:

| fd | Назначение |
|---|---|
| 0 | stdin |
| 1 | stdout |
| 2 | stderr |

```bash
ls /proc/$$/fd            # все открытые fd текущего shell
lsof -p PID | wc -l       # сколько fd открыто процессом
ulimit -n                 # лимит на fd (RLIMIT_NOFILE)
```

**Боль в production:** ошибка «Too many open files» означает, что процесс упёрся в лимит fd (`RLIMIT_NOFILE`). Частые причины — много соединений или утечка fd (открыли и не закрыли). Лечение: проверить, не течёт ли что-то (`lsof -p PID | wc -l`), и поднять лимит — `ulimit -n` для пользователя или `LimitNOFILE=65536` в systemd-юните.

## Q13. Что такое fork/exec и как они связаны?

Это два разных системных вызова, на которых в Unix построен запуск любой программы: `fork()` создаёт процесс, `exec()` загружает в него нужный код. Поодиночке они почти бесполезны — работают в паре.

- `fork()` — создаёт **копию** текущего процесса. Child получает новый PID, а память сначала делится с родителем и копируется только при записи (copy-on-write), поэтому fork дёшев.
- `exec()` — заменяет образ процесса новым бинарником: код, стек и heap становятся новыми, а PID **сохраняется**. Никакого нового процесса не возникает — меняется «начинка» текущего.

Стандартный флоу запуска программы в shell:

```text
shell --fork()--> child (копия shell)
       child --exec("ls")--> running ls
       shell --wait()--> ждёт exit child
```

```c
pid_t pid = fork();
if (pid == 0) {
    execvp("ls", args);          // в child
} else {
    waitpid(pid, &status, 0);    // в parent
}
```

**Итог:** в `bash` каждый вызов внешней команды — это fork + exec. Встроенные команды (`cd`, `echo`) выполняются без fork.

## Q14. (!) Чем отличаются `.bashrc` и `.bash_profile`?

Разница — в типе shell, который читает файл: `~/.bash_profile` подхватывается **login**-сессией (вход по SSH, `su -`, консоль), а `~/.bashrc` — **interactive non-login** сессией (каждый новый терминал в GUI, запуск `bash` вручную). Грубо: «логинишься на машину» против «открываешь ещё одну вкладку терминала».

| Файл | Когда читается |
|---|---|
| `/etc/profile`, `~/.bash_profile`, `~/.profile` | **login shell** (SSH, `su -`, tty) |
| `~/.bashrc` | **interactive non-login shell** (новый терминал в GUI, `bash` вручную) |
| `/etc/bash.bashrc` | system-wide bashrc |
| `~/.bash_logout` | при выходе из login shell |

Обычно `~/.bash_profile` подключает `~/.bashrc`:

```bash
# ~/.bash_profile
[[ -f ~/.bashrc ]] && . ~/.bashrc
```

Поэтому почти всегда `~/.bash_profile` просто подключает `~/.bashrc` (см. сниппет выше) — чтобы настройки работали и в login-, и в non-login-сессии, и их не приходилось дублировать.

**Эмпирическое правило, что куда класть:** переменные окружения (`PATH`, `JAVA_HOME`) — в `~/.bash_profile` (или `~/.profile` — он login-agnostic и подходит для zsh): они наследуются дочерними процессами, и одного выставления при логине достаточно. А алиасы и функции — в `~/.bashrc`: они не наследуются, поэтому нужны в каждом новом интерактивном shell.

## Q15. (!) Как устроены pipe и редиректы?

И pipe, и редиректы — это перенаправление потоков ввода-вывода (stdin/stdout/stderr), только pipe соединяет два процесса, а редирект связывает поток с файлом.

Пайп `|` подключает stdout левой команды к stdin правой, и так можно собирать конвейер: каждая команда делает одну вещь, а данные текут сквозь них:

```bash
grep ERROR /var/log/app.log | awk '{print $4}' | sort | uniq -c | sort -rn | head
```

Здесь логи фильтруются по `ERROR`, из строк берётся 4-е поле, оно сортируется, считаются уникальные значения и выводится топ — классический «Unix-way».

Редиректы перенаправляют поток в файл (или между потоками):

| Синтаксис | Что делает |
|---|---|
| `>` | перезаписать stdout в файл |
| `>>` | дописать stdout в файл |
| `<` | читать stdin из файла |
| `2>` | перезаписать stderr |
| `2>&1` | stderr перенаправить туда же, куда stdout |
| `&>` или `>&` | и stdout и stderr в одно место (bash) |
| `<<EOF ... EOF` | heredoc (многострочный вход) |
| `<<<"string"` | here-string |

**Подводный камень — порядок редиректов.** `2>&1` означает «направь stderr туда же, куда сейчас указывает stdout», а не «свяжи их навсегда». Поэтому редиректы применяются строго слева направо:

- `cmd > out.log 2>&1` — правильно: сначала stdout уходит в файл, затем stderr копирует это назначение — оба в файле.
- `cmd 2>&1 > out.log` — ошибка: stderr копирует stdout, пока тот ещё указывает на терминал, и только потом stdout переключается в файл. В итоге stderr остаётся в терминале.

## Q16. Что такое `$?`, `$$`, `$!`, `$@`, `$#` в bash?

Это специальные переменные bash, которые shell заполняет автоматически. Они делятся на две группы: про *состояние* (`$?` — код возврата, `$$`/`$!` — PID-ы) и про *аргументы скрипта* (`$0`, `$1…`, `$#`, `$@`, `$*`).

| Переменная | Значение |
|---|---|
| `$?` | exit-code последней команды (0 = success) |
| `$$` | PID текущего shell |
| `$!` | PID последнего фонового процесса (`cmd &`) |
| `$0` | имя скрипта |
| `$1`, `$2` ... `$9` | позиционные аргументы |
| `$#` | количество аргументов |
| `$@` | все аргументы как список (`"$@"` — корректно сохраняет кавычки) |
| `$*` | все аргументы как одна строка |
| `$_` | последний аргумент предыдущей команды |

Главное, что любят спрашивать: разница `"$@"` и `"$*"`. `"$@"` разворачивается в список отдельных аргументов (каждый — своё слово, пробелы внутри сохраняются), а `"$*"` склеивает всё в одну строку. В скриптах почти всегда нужен именно `"$@"`.

```bash
./script.sh foo bar
# $#=2, $1=foo, $2=bar, $@="foo bar"
```

## Q17. (!) Разница между `'строкой'`, `"строкой"` и `` `команда` ``?

Разница в том, что shell делает *внутри* кавычек: одинарные сохраняют текст буквально, двойные раскрывают переменные и подстановки команд, а обратные кавычки — это вообще не кавычки, а сама подстановка команды.

| Кавычки | Подстановка переменных `$var` | Подстановка команд `$(...)` | Экранирование `\` |
|---|---|---|---|
| `'одинарные'` | ❌ нет | ❌ нет | только для `'` |
| `"двойные"` | ✅ да | ✅ да | ограниченное |
| `` `...` `` | — | сама есть подстановка команд (устаревший синтаксис) | — |
| `$(...)` | — | подстановка команд, современный вариант | — |

```bash
name=World
echo 'hello $name'     # hello $name
echo "hello $name"     # hello World
echo `date`            # выполнит date
echo $(date +%F)       # 2026-04-20 (предпочтительная форма)
```

**Правило:** `$()` лучше backticks — проще вкладывать: `echo $(basename $(dirname "$PWD"))`.

## Q18. Что делает `set -euo pipefail` в начале скрипта?

Это «строгий режим» bash: одна строка, которая заставляет скрипт падать на ошибках вместо того, чтобы молча продолжать с битыми данными. По умолчанию shell прощает слишком многое — эти три флага закрывают самые опасные дыры.

| Флаг | Эффект |
|---|---|
| `-e` | падать на первой ошибке (ненулевой exit-code) |
| `-u` | падать при обращении к необъявленной переменной |
| `-o pipefail` | pipe возвращает ненулевой код, если **любая** команда в пайпе упала (без него — только код последней) |

Зачем каждый: без `-e` скрипт после провалившейся команды бежит дальше (например, `cd /nonexistent` упал — а `rm -rf *` отработал не там). Без `-u` опечатка в имени переменной даёт пустую строку, а не ошибку (опасно в `rm -rf "$DIR/"`). Без `pipefail` конвейер `cmd | tee log` считается успешным, даже если `cmd` упал, — потому что код берётся от последней команды.

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'       # безопасный IFS
```

**Хороший тон:** начинать каждый production-скрипт с этой строки — ловит классические баги.

## Q19. Что такое subshell и чем он отличается от source?

Разница в том, **где** выполняется код: subshell — это отдельный дочерний процесс с собственной средой, а `source` исполняет скрипт прямо в текущем shell. Поэтому всё, что меняет среду, ведёт себя по-разному.

- `bash script.sh` / `./script.sh` / `(cmd)` / `$(cmd)` — **subshell**, отдельный процесс. Он наследует копию окружения, но любые его изменения (`cd`, новые переменные, функции) **не возвращаются** в родителя — процесс завершился, копия исчезла.
- `source script.sh` / `. script.sh` — выполнение в **текущем** shell. Никакого нового процесса нет, поэтому переменные, функции и смена каталога остаются в вашей сессии. Именно так подключают конфиги окружения (`source ~/.bashrc`, `source venv/bin/activate`).

```bash
# set-env.sh
export JAVA_HOME=/opt/java17

./set-env.sh            # JAVA_HOME не виден после
source ./set-env.sh     # JAVA_HOME доступен в текущей сессии
```

## Q20. Что такое `trap` в bash?

`trap` назначает команду-обработчик, которая выполнится, когда скрипт получит указанный сигнал или дойдёт до события shell. Это аналог `try/finally` в bash: главный сценарий — гарантированный cleanup (удалить временные файлы, снять lock, остановить фоновый процесс) при любом завершении, в том числе аварийном.

```bash
#!/usr/bin/env bash
set -euo pipefail

tmp=$(mktemp -d)
trap "rm -rf '$tmp'" EXIT    # удалить temp при любом выходе

cleanup_and_exit() { echo "interrupted"; exit 130; }
trap cleanup_and_exit INT TERM
```

Полезные события: `EXIT` (любой выход из скрипта — самый надёжный для cleanup), `ERR` (любая упавшая команда), `INT` (SIGINT, `Ctrl+C`), `TERM` (SIGTERM, штатная остановка). Ставить cleanup на `EXIT` удобнее всего: он сработает и при нормальном завершении, и при ошибке, и после `INT`/`TERM`.

## Q21. (!) В чём разница `$(...)` и backticks `` `...` ``?

Делают они одно и то же — подставляют вывод команды в строку. Но `$(...)` — современная замена backticks, у которой нет их проблем с вложенностью и экранированием.

| Свойство | `` `...` `` | `$(...)` |
|---|---|---|
| Возраст | исходный POSIX | современный (Bourne Again) |
| Вложенность | неудобно (нужно экранировать) | легко: `$(cmd $(other))` |
| Парсинг обратных слэшей | непрост | обычный |
| Рекомендация | ❌ не использовать | ✅ использовать |

Ключевая боль backticks — вложенность: внутренние обратные кавычки приходится экранировать (`` \` ``), и при двух-трёх уровнях код становится нечитаемым. `$(...)` вкладывается естественно, скобка к скобке, без единого слэша.

```bash
# неудобно
echo `echo \`date\``

# удобно
echo $(echo $(date))
```

## Q22. Как эффективно искать файлы и содержимое?

Здесь два разных инструмента под две задачи: `find` ищет файлы **по метаданным** (имя, дата, размер, права), а `grep`/`rg` ищут **внутри** файлов по содержимому.

**Файлы (по имени, времени, размеру, правам):**

```bash
find /var/log -name '*.log' -mtime -1 -size +1M
find / -type f -perm -u+s 2>/dev/null          # SUID-файлы
```

`find` хорош тем, что условия комбинируются: пример выше находит `.log`-файлы, изменённые за последние сутки (`-mtime -1`) и больше 1 МБ (`-size +1M`) — одним запросом.

**Содержимое (по тексту/регулярке):**

```bash
grep -rni 'ERROR' /var/log --include='*.log'
rg -n 'ERROR' /var/log                         # ripgrep — быстрее grep
```

**По расширению/регулярке через fd (современный find):**

```bash
fd -e log -d 3 /var/log
```

## Q23. (!) Что такое `systemd` и зачем он заменил `init.d`?

`systemd` — это первый процесс системы (PID 1) и менеджер сервисов. Он стартует при загрузке и отвечает за запуск, остановку и контроль всех остальных служб. Пришёл на смену `SysV init` (`init.d`), и заменил его не косметически, а концептуально: вместо последовательного запуска bash-скриптов по номерам — декларативная модель с зависимостями.

Что это даёт по сравнению с `init.d`:

- **Параллельный старт.** Unit-ы описывают зависимости (`After=`, `Requires=`), а не жёсткий порядок (`S10`, `S20`), поэтому независимые сервисы поднимаются одновременно — загрузка быстрее.
- **Активация по событию.** Socket- и timer-activation позволяют запускать сервис только когда он понадобился (пришёл коннект, наступило время) — это же заменяет cron для многих задач.
- **Единые логи** через `journald` — структурированный журнал вместо разрозненных файлов.
- **Контроль ресурсов** каждого сервиса через cgroups (CPU, память, лимиты).
- **Декларативные unit-файлы** вместо императивных стартовых скриптов — меньше копипасты и ошибок.

Ключевые команды:

```bash
systemctl start|stop|restart|reload nginx
systemctl enable|disable nginx           # автозапуск
systemctl status nginx
systemctl list-units --type=service --state=failed
journalctl -u nginx -f --since '10 min ago'
```

## Q24. Как написать unit-файл для приложения?

Unit-файл — это декларативное описание сервиса в INI-формате с тремя секциями: `[Unit]` (метаданные и зависимости), `[Service]` (как запускать и перезапускать процесс) и `[Install]` (в какой target включить при `enable`). Кладётся в `/etc/systemd/system/myapp.service`:

```ini
[Unit]
Description=My Spring Boot app
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=app
Group=app
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/java -jar /opt/myapp/app.jar
Restart=on-failure
RestartSec=5s
LimitNOFILE=65536
Environment=SPRING_PROFILES_ACTIVE=prod

[Install]
WantedBy=multi-user.target
```

Применить:

```bash
systemctl daemon-reload
systemctl enable --now myapp
```

Ключевой параметр здесь — `Type=`: он говорит systemd, как понять, что сервис «запустился», и от этого зависит порядок старта зависимых юнитов. Для большинства современных приложений (включая Spring Boot, как в примере) подходит `simple`.

| `Type=` | Когда использовать |
|---|---|
| `simple` | процесс не демонизируется, сам systemd его «охраняет» |
| `forking` | классический daemon с fork |
| `oneshot` | скрипт-однострочник, быстро выходит |
| `notify` | процесс сообщает готовность через `sd_notify` |
| `exec` | как simple, но ждёт `exec()` перед тем как считать стартовавшим |

Разница важна для зависимостей: при `simple` systemd считает сервис запущенным сразу после `fork`+`exec`, ещё до того как приложение реально готово. Если другим юнитам нужна именно готовность (порт открыт, инициализация прошла), используют `notify` — тогда сервис сам сообщает «я готов» через `sd_notify`.

## Q25. Что такое cron и в чём отличие от `systemd timer`?

Оба запускают задачи по расписанию, но `cron` — простой классический планировщик из таблицы строк, а `systemd timer` — более мощная пара unit-файлов, интегрированная в systemd (логи, контроль ресурсов, учёт пропусков).

`cron` задаёт расписание в текстовых файлах `/etc/crontab`, `~/crontab`:

```text
# m  h  dom mon dow command
  0  3  *   *   *   /opt/backup.sh
  */5 * *   *   *   /opt/collect-metrics.sh
```

Формат: `минуты часы день-месяца месяц день-недели команда`.

`systemd timer` — альтернатива: пара `.timer` + `.service`:

```ini
# /etc/systemd/system/backup.timer
[Unit]
Description=Daily backup

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

**Когда брать `systemd timer` вместо cron:**

- **Пропущенные запуски не теряются.** С `Persistent=true` задача, не выполненная из-за выключенной машины, отработает сразу после загрузки — cron такой запуск просто пропустит.
- **Логи из коробки** — `journalctl -u backup` показывает вывод и историю; в cron вывод по умолчанию уходит в почту root и часто теряется.
- **Контроль ресурсов** — таймер запускает обычный `.service`, которому можно задать лимиты CPU/памяти.
- **Гибкие триггеры** — не только календарь, но и события вроде `OnBootSec` (через N после загрузки) и `OnUnitActiveSec` (через N после прошлого запуска).

## Q26. (!) Какие команды использовать для диагностики сети?

Сильный ответ — идти по слоям сети сверху вниз, локализуя, где рвётся: свой интерфейс и маршрут (`ip addr`/`ip route`) → разрешается ли имя (`dig`) → доходит ли пакет до хоста (`ping`/`mtr`) → открыт ли нужный порт (`nc`) → что реально летит по сети (`tcpdump`).

| Задача | Команда |
|---|---|
| Список интерфейсов и адресов | `ip addr` / `ip a` (новая), `ifconfig` (устаревшая) |
| Таблица маршрутизации | `ip route` / `route -n` |
| DNS-резолвинг | `dig example.com`, `getent hosts example.com`, `nslookup` |
| Ping / trace | `ping`, `traceroute`, `mtr` |
| Проверить порт | `nc -zv host 443`, `curl -v telnet://host:443` |
| Слушаемые порты | `ss -tlnp` (новая), `netstat -tlnp` (устаревшая) |
| Сетевая статистика | `ss -s`, `nstat`, `sar -n DEV 1` |
| Перехват пакетов | `tcpdump -i any -n port 80` |

Так вы не гадаете, а сужаете проблему: «DNS резолвится, ping идёт, но порт закрыт» сразу указывает на firewall или упавший сервис, а не на сеть в целом.

## Q27. Что такое порты, сокеты и как посмотреть слушаемые порты?

- **Порт** — 16-битное число (0–65535), которое идентифицирует конкретный endpoint (приложение) на хосте. По IP пакет приходит на машину, по порту — попадает в нужный процесс.
- **Сокет** — это endpoint соединения. Конкретное TCP-соединение однозначно задаётся 5-кортежем `(protocol, src_ip, src_port, dst_ip, dst_port)` — поэтому к одному слушающему порту сервера могут одновременно подключаться тысячи клиентов: каждое соединение отличается парой «адрес+порт клиента».
- Порты **<1024** — привилегированные («well-known»): открыть их на прослушивание может только root. Это защита от того, чтобы непривилегированный процесс не притворился, скажем, системным SSH или HTTP.

```bash
ss -tlnp           # TCP, listening, numeric, с процессами
ss -tunap          # TCP+UDP, all, numeric, with PIDs
lsof -i :8080      # кто слушает порт 8080
```

**Типичные порты:** 22 (SSH), 80 (HTTP), 443 (HTTPS), 5432 (PostgreSQL), 6379 (Redis), 3306 (MySQL), 9092 (Kafka), 27017 (MongoDB).

## Q28. В чём разница между `iptables`, `nftables` и `ufw`?

Все они в итоге управляют одним и тем же ядерным фреймворком — **netfilter**, но находятся на разных уровнях абстракции. `iptables` и `nftables` — это низкоуровневые «движки» правил (`nftables` пришёл на смену `iptables`), а `ufw` и `firewalld` — удобные обёртки поверх них для человека.

| Инструмент | Уровень | Современность |
|---|---|---|
| `iptables` | netfilter, legacy | устаревает, на многих дистрах — alias к `iptables-nft` |
| `nftables` | netfilter, новое поколение | рекомендуется |
| `ufw` | wrapper над iptables/nftables | удобно для простых задач (Ubuntu) |
| `firewalld` | daemon + zones | по умолчанию на RHEL/Fedora |

На практике: для сервера руками пишут правила в `nftables`; на десктопе/простом хосте под Ubuntu хватает `ufw` (`ufw allow 22`); на RHEL/Fedora из коробки стоит `firewalld` с концепцией зон. Голый `iptables` на новых системах чаще всего уже не настоящий — это alias на `iptables-nft`, который транслирует старый синтаксис в nftables.

```bash
ufw allow 22/tcp                 # разрешить SSH
ufw enable

nft list ruleset                 # показать все правила nftables
```

## Q29. (!) Как диагностировать, что «диск забит»?

Алгоритм — от общего к частному: сначала понять, *какой* раздел и *что* в нём забилось (место или inode), потом найти конкретных виновников, и в конце проверить хитрый случай с «удалёнными, но открытыми» файлами.

1. **Какой раздел полон:** `df -h` — покажет заполненность по разделам в процентах.
2. **Место или inode:** `df -i` — место может быть свободным, но кончились inode (см. Q1). Если виноваты inode, шаги ниже про крупные файлы не помогут — искать надо много мелких.
3. **Крупные каталоги:** `du -h --max-depth=1 /var | sort -h` — спускаемся по дереву туда, где «тяжело».
4. **Крупные файлы:** `find / -xdev -type f -size +500M 2>/dev/null` (`-xdev` не выходит за пределы раздела).
5. **Удалённые, но открытые:** `lsof +L1` — файл удалён (`nlink=0`), но процесс держит на него fd, и место не освобождается до закрытия дескриптора или рестарта.

**Подводный камень:** логи, которые ротируются, но приложение держит старый fd, продолжают занимать место до рестарта.

```bash
df -h /var
du -sh /var/log/* | sort -h | tail
lsof +L1 /var            # файлы с nlink=0
```

## Q30. (!) Как посмотреть, что процесс делает в реальном времени?

Инструмент выбирают по тому, *что именно* хочется увидеть: общение процесса с ядром (`strace`), с библиотеками (`ltrace`), куда уходит CPU (`perf`), где он застрял (`gdb`, `/proc/.../stack`) или что делают треды JVM (`jstack`). Начинать стоит с гипотезы «процесс висит / жрёт CPU / много IO» и брать соответствующий инструмент.

| Инструмент | Что показывает |
|---|---|
| `strace -p PID` | системные вызовы |
| `strace -f -e trace=network -p PID` | только сетевые вызовы |
| `ltrace -p PID` | библиотечные вызовы |
| `perf top -p PID` | hot-методы по CPU |
| `perf record -p PID ... && perf report` | профилирование |
| `gdb -p PID` | backtrace, дамп |
| `pidstat -t 1 -p PID` | CPU / IO per thread |
| `tail -f` по `/proc/<pid>/status` | состояние, память, threads |
| `cat /proc/<pid>/stack` | kernel-стек (если завис в D) |
| `jstack PID` / `jcmd PID Thread.print` | для JVM — thread dump |

Типичный пример: процесс «висит» и ест 0% CPU — `strace -p PID` покажет, на каком системном вызове он заблокирован (часто `read`/`futex`); если он завис в состоянии `D`, обычный `strace` не подцепится, и смотреть надо `cat /proc/<pid>/stack`.

## Q31. Что делать, если приложение съедает память?

Сначала убедиться, что памяти действительно мало (а не просто заполнен кэш), затем найти процесс-виновника и разобрать, куда у него уходит память. Порядок действий:

1. **Кто ест:** `top` / `htop` — сортировка по `RES`/`%MEM`.
2. **Разбивка по процессу:** `pmap -x PID` / `cat /proc/<pid>/status` — `VmRSS` (реально в RAM) против `VmSize` (виртуальная — она обычно сильно больше и сама по себе не страшна).
3. **Картина с учётом shared:** `smem -r -k` — честно делит общую память между процессами (важно, когда несколько процессов шарят библиотеки).
4. **Реально ли мало:** `cat /proc/meminfo` — смотреть `MemAvailable` (а не `MemFree`), `Cached`, `Buffers`.
5. **Для JVM:** `jcmd PID GC.heap_info`, при необходимости heap dump через `jcmd PID GC.heap_dump` — отдельно от RSS, потому что JVM-память живёт в куче.
6. **Не сработал ли OOM:** `dmesg -T` — нет ли следов OOM killer (см. Q32).

**Частая ошибка новичка:** смотрят на `top` и путают `free` с `available`. `free` маленький — это нормально: Linux кэширует файлы. Смотрят на `MemAvailable`.

## Q32. (!) Что такое `OOM killer` и как понять, что он убил процесс?

`OOM killer` (Out-Of-Memory killer) — это подсистема ядра, которая включается, когда память кончилась и выделить новую невозможно. Чтобы система не зависла намертво, ядро выбирает «худший» процесс по эвристике `oom_score` (учитывает потребление памяти и `oom_score_adj`) и убивает его, освобождая RAM. То есть это аварийный механизм выживания, а не штатное управление памятью.

Как узнать, что OOM killer сработал:

```bash
dmesg -T | grep -i 'killed process'
journalctl -k --since 'today' | grep -i oom
# Out of memory: Killed process 12345 (java) total-vm:8388608kB, anon-rss:6291456kB
```

Управление:

- `/proc/<pid>/oom_score_adj` — -1000..1000, -1000 = неубиваемый.
- В systemd: `OOMScoreAdjust=-500` в unit-файле.
- Кастомный OOM в cgroup v2 (`memory.max`) — убивает только процессы в этой группе (важно для контейнеров).

**Итог:** если под в Kubernetes получает `OOMKilled`, это тот же механизм — лимит памяти cgroup исчерпан.

## Q33. Как посмотреть лимиты процесса (`ulimit`)?

`ulimit` — это встроенная команда shell для просмотра и изменения ресурсных лимитов процесса (за ними стоят ядерные ограничения `RLIMIT_*`). Лимиты не дают одному процессу или пользователю исчерпать ресурсы всей системы — например, открыть бесконечно много файлов или наплодить процессы.

| Лимит | Значение |
|---|---|
| `ulimit -n` / `nofile` | макс file descriptors |
| `ulimit -u` / `nproc` | макс процессов/тредов пользователя |
| `ulimit -s` / `stack` | размер стека в KB |
| `ulimit -v` / `as` | макс virtual memory |
| `ulimit -l` / `memlock` | `mlock`ed память |
| `ulimit -c` / `core` | размер core dump |

Важно: у каждого лимита есть **soft** и **hard** значения. Soft — текущий действующий лимит, его пользователь может поднять сам, но не выше hard. Hard — потолок, поднять который может только root.

Посмотреть лимиты конкретного процесса:

```bash
cat /proc/<pid>/limits
```

Изменить для сервиса в systemd:

```ini
LimitNOFILE=65536
LimitNPROC=4096
```

Изменить для пользователя:

```text
# /etc/security/limits.conf
app    soft    nofile    65536
app    hard    nofile    65536
```

**Вывод:** лимиты — первая причина проблем у долгоживущих сервисов; проверь сразу, если видишь «resource temporarily unavailable».
