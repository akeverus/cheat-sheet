# Вопросы на собеседовании: `Ansible`

`Ansible` — agentless-система управления конфигурацией и автоматизации. Создана Michael DeHaan (2012), куплена Red Hat (2015). Использует **SSH** (без агентов), **YAML-плейбуки**, **идемпотентные** модули. Доминирует на рынке config management. Альтернативы: Puppet, Chef, SaltStack.

## Q1. (!) Что такое Ansible?

**Ansible** — open-source инструмент IT-автоматизации, который описывает желаемое состояние серверов в YAML и приводит их к нему через SSH, без установки агентов. Создан Michael DeHaan (автор Cobbler) в 2012, куплен Red Hat в 2015.

Главная идея: вы описываете «как должна выглядеть система» в текстовых файлах, а Ansible подключается к машинам и доводит их до этого состояния. Один и тот же плейбук можно безопасно запускать снова — уже настроенное он не трогает.

**Где применяют:**
- **Управление конфигурацией** — установка и настройка ПО на серверах. Основной сценарий.
- **Деплой приложений** — выкатка новой версии на парк машин.
- **Оркестрация** — многошаговые workflow, где порядок и зависимости важны.
- **Provisioning** — создание облачных ресурсов (чаще в паре с Terraform, который делает это лучше).
- **Continuous delivery** — деплой как шаг CI/CD-пайплайна.
- **Сетевая автоматизация** — конфигурация Cisco, Juniper и других устройств.
- **Автоматизация безопасности** — приведение хостов к требованиям compliance.

**Что отличает Ansible (ключевые характеристики):**
- **Agentless** — работает поверх SSH (Linux) и WinRM (Windows), ничего ставить на хосты не нужно.
- **YAML-плейбуки** — конфигурация читается как обычный текст, порог входа низкий.
- **Идемпотентные модули** — повторный запуск не ломает уже настроенное.
- **Push-модель** — control node инициирует подключение к managed nodes и «толкает» изменения (в отличие от pull-модели Puppet/Chef, где агент сам тянет конфиг).

## Q2. (!) Чем agentless-подход лучше агентного?

**Agentless** означает, что на управляемых машинах не нужно ничего устанавливать — Ansible подключается по уже имеющемуся SSH. Это убирает целый класс работ, который есть у агентных систем.

**Что приходится терпеть с агентными системами (Puppet, Chef):**
- Нужно ставить и обслуживать агента на каждой managed node.
- Обновления агента — отдельная регулярная задача по всему парку.
- Постоянно работающий агент — это дополнительный демон, то есть лишняя поверхность атаки и риск безопасности.

**Что даёт agentless-подход Ansible:**
- Достаточно SSH, который и так есть на любом Linux-сервере — стартовать можно сразу.
- Не нужно устанавливать и обновлять агента.
- Проще начать: один control node и доступ по ключу — больше ничего.
- Меньше поверхность атаки: нет постоянного демона на хостах.

**Компромисс** — за простоту платят на масштабе:
- SSH-подключение поднимается на каждую задачу, поэтому на огромных парках машин Ansible медленнее агентных систем.
- Сложнее **отслеживать состояние** — нет агента, который сам шлёт отчёты обратно, так что централизованного мониторинга «дрейфа» из коробки нет.

agentless-подход доминирует в новых инструментах — даже у Salt, изначально агентного, есть agentless-режим (`salt-ssh`).

## Q3. (!) Что такое идемпотентность и зачем она нужна?

**Идемпотентность** — свойство задачи давать один и тот же результат при любом числе запусков. Первый прогон приводит систему к нужному состоянию, а все последующие ничего не меняют, потому что менять уже нечего.

Достигается это так: идемпотентный модуль сначала **проверяет текущее состояние** и действует только при расхождении. Например, `package` с `state: present` ставит пакет, только если его нет; если он уже стоит — задача завершается со статусом `ok`, а не `changed`.

**Пример:**
```yaml
# Idempotent — install only if not present
- name: Install nginx
  package:
    name: nginx
    state: present

# NOT idempotent — runs every time
- name: Run setup script
  command: /opt/setup.sh  # always executes
```

**Зачем это нужно:**
- **Безопасный перезапуск.** Плейбук можно гонять сколько угодно раз — лишних действий не будет.
- **Сходимость (convergence).** Сколько бы раз ни запустили, система сходится к одному желаемому состоянию.
- **Восстановление после частичного сбоя.** Если плейбук упал на середине, его просто запускают заново: уже сделанные шаги пропускаются, выполняются только оставшиеся.

**Подводный камень:** большинство модулей Ansible идемпотентны, но `command` и `shell` — нет, они выполняют команду каждый раз. Чтобы вернуть им идемпотентность, добавляют условия `creates`/`removes` или `changed_when`/`when`, которые говорят Ansible, при каких условиях команду можно пропустить.

## Q4. (!) Чем статический inventory отличается от динамического?

**Inventory** — это список хостов, которыми управляет Ansible, разбитый на группы. Он бывает двух видов в зависимости от того, откуда берётся список.

**Статический inventory** — список хостов прописан вручную в файле (INI или YAML):
```ini
# inventory.ini
[webservers]
web1.example.com
web2.example.com

[databases]
db1.example.com

[production:children]
webservers
databases
```

Группа `[production:children]` объединяет другие группы — так строят иерархию. Удобно, когда хостов немного и они стабильны.

**Динамический inventory** — список не пишут руками, а генерируют на лету из внешнего источника правды:
- AWS EC2 (автообнаружение инстансов)
- Azure
- GCP
- Kubernetes
- Consul, Vault
- Самописные скрипты под свой источник

```yaml
# aws_ec2.yml
plugin: aws_ec2
regions:
  - us-east-1
keyed_groups:
  - key: tags.Environment
```

```bash
ansible-inventory -i aws_ec2.yml --list
```

**Когда что выбирать.** В облаке инстансы эфемерны — поднимаются и гаснут автоскейлингом, IP меняются. Вести такой список вручную бессмысленно, поэтому в облачных окружениях почти всегда берут динамический inventory: он спрашивает актуальный список прямо у провайдера. Статический хорош для небольшого, редко меняющегося парка железа.

## Q5. (!) Из чего состоит playbook?

**Playbook** — YAML-файл, описывающий, что и на каких хостах выполнить. Состоит из одного или нескольких **play**, а каждый play связывает группу хостов с набором задач.

Ключевые элементы play:
- **`hosts`** — на какую группу из inventory применять.
- **`become`** — повышение прав (sudo).
- **`vars`** — переменные для этого play.
- **`tasks`** — задачи, выполняются строго по порядку сверху вниз.
- **`handlers`** — задачи-реакции, срабатывают только по `notify` и один раз в конце play (см. Q8).

```yaml
# deploy.yml
---
- name: Deploy web servers
  hosts: webservers
  become: yes  # use sudo
  vars:
    nginx_port: 80

  tasks:
    - name: Install nginx
      package:
        name: nginx
        state: present

    - name: Copy config
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: Restart nginx

    - name: Ensure nginx running
      service:
        name: nginx
        state: started
        enabled: yes

  handlers:
    - name: Restart nginx
      service:
        name: nginx
        state: restarted
```

**Запуск:**
```bash
ansible-playbook -i inventory deploy.yml
```

## Q6. (!) Что такое roles и зачем они нужны?

**Роль (role)** — это способ упаковать связанную автоматизацию (задачи, переменные, файлы, шаблоны, обработчики) в стандартную структуру каталогов. Роль решает проблему разрастания: когда весь плейбук — это одна длинная простыня задач, его невозможно переиспользовать и тяжело сопровождать. Роль выносит «как настроить nginx» в отдельный самодостаточный модуль, который подключается одной строкой.

Сила в **соглашении об именах**: Ansible сам знает, что искать в каждом подкаталоге, поэтому связывать файлы вручную не нужно.

```
roles/
  nginx/
    tasks/
      main.yml
    handlers/
      main.yml
    templates/
      nginx.conf.j2
    defaults/
      main.yml      # default variables
    vars/
      main.yml      # higher-precedence variables
    files/
      static-asset.html
    meta/
      main.yml      # dependencies
```

**Использование в плейбуке:**
```yaml
- hosts: webservers
  roles:
    - nginx
    - app-deploy
```

Подкаталоги по назначению: `tasks/` — что делать, `handlers/` — реакции, `templates/` и `files/` — содержимое для копирования, `defaults/` — переменные с низшим приоритетом (легко переопределяются), `vars/` — переменные с высоким приоритетом, `meta/` — зависимости от других ролей.

**Главная выгода:** роль пишут один раз, а используют во многих плейбуках и проектах. Готовые роли распространяются через Ansible Galaxy (см. Q18) — не нужно изобретать настройку nginx с нуля.

## Q7. Что такое modules?

**Модули (modules)** — это исполняемые единицы работы, которые вызываются в задачах. По сути каждый модуль — функция «сделай X с нужным состоянием»: он принимает параметры, выполняет действие на хосте и возвращает результат. Именно модули реализуют идемпотентность — сами проверяют текущее состояние и меняют его только при расхождении. Встроенных модулей 3000+.

**Категории (что бывает):**
- **Система** — file, service, user, package
- **Облако** — ec2, gcp_compute, azure_rm
- **Сетевые утилиты** — uri, get_url
- **БД** — postgresql_db, mysql_user
- **Контроль версий** — git, github
- **Файлы** — copy, template, lineinfile
- **Контейнеры** — docker_container, k8s

```yaml
# Examples
- file:
    path: /etc/myapp.conf
    state: touch

- service:
    name: nginx
    state: restarted

- ec2_instance:
    name: my-instance
    instance_type: t3.micro
    image: ami-...
```

**Расширяемость:** если подходящего модуля нет, свой можно написать на Python.

## Q8. Чем handlers отличаются от обычных tasks?

**Tasks** — обычные задачи, выполняются по порядку сверху вниз на каждом запуске.

**Handlers** — особые задачи-реакции. Отличия два: они запускаются **только** если их кто-то вызвал через `notify`, и срабатывают **один раз** в конце play, даже если их вызвали несколько раз. Вызов происходит лишь когда задача что-то реально изменила (статус `changed`); если задача вернула `ok`, `notify` не срабатывает.

Зачем такая механика: дорогие побочные действия вроде рестарта сервиса нужно делать один раз и только при реальных изменениях. Если два разных таска поправили конфиг, нет смысла рестартовать nginx дважды — handler сделает это однократно в конце.

```yaml
tasks:
  - name: Update nginx config
    template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: Restart nginx  # marks handler

  - name: Update SSL cert
    copy:
      src: cert.pem
      dest: /etc/nginx/cert.pem
    notify: Restart nginx  # same handler — fires once

handlers:
  - name: Restart nginx
    service:
      name: nginx
      state: restarted
```

**Итог:** если хоть одна из этих задач что-то изменила, handler сработает **один раз** в конце — без двойного рестарта.

## Q9. (!) Как устроен приоритет переменных (group_vars, host_vars, playbook)?

Переменную в Ansible можно задать в десятке мест, и одну и ту же переменную нередко определяют сразу в нескольких. Какое значение победит, решает **приоритет**: чем «ближе» к конкретному запуску и хосту источник, тем он сильнее. Поэтому defaults роли легко переопределить, а `-e` из командной строки перебивает всё.

**Приоритет (от низкого к высокому):**

1. **Role defaults** (`roles/*/defaults/main.yml`)
2. **Переменные из inventory-файла**
3. **`group_vars/all.yml`** (применяются ко всем хостам)
4. **`group_vars/<group>.yml`** (конкретная группа)
5. **`host_vars/<host>.yml`** (конкретный хост)
6. **`vars` плейбука**
7. **`vars` роли**
8. **extra vars `-e`** (наивысший приоритет)

```
inventory/
  group_vars/
    all.yml         # для всех
    webservers.yml  # для webservers группы
  host_vars/
    web1.yml        # для web1
```

**Логика проста:** `defaults` роли — это «разумные значения по умолчанию», их и задумано переопределять. `group_vars`/`host_vars` уточняют значения для конкретных групп и хостов. А `-e` в командной строке — это явное ручное переопределение «здесь и сейчас», поэтому оно сильнее всего.

**Переопределение через CLI** (extra vars, наивысший приоритет):
```bash
ansible-playbook deploy.yml -e "version=2.0"
```

## Q10. Что такое facts?

**Facts** — это переменные с данными о хосте, которые Ansible автоматически собирает перед выполнением задач (модулем `setup`). По сути это «паспорт машины»: ОС, версия, объём памяти, число CPU, IP-адреса, hostname. Их используют, чтобы плейбук подстраивался под конкретный хост — например, ставил пакет через `apt` на Ubuntu и через `yum` на RHEL.

```yaml
- debug:
    msg: "OS is {{ ansible_facts['distribution'] }}"
- debug:
    msg: "Memory: {{ ansible_facts['memtotal_mb'] }} MB"
```

**Примеры:**
- `ansible_distribution` (Ubuntu, RHEL)
- `ansible_distribution_version`
- `ansible_memtotal_mb`
- `ansible_processor_count`
- `ansible_default_ipv4.address`
- `ansible_hostname`

**Тонкость со скоростью:** сбор facts — это отдельный заход на каждый хост, и на большом парке он заметно тормозит старт. Если facts в плейбуке не нужны, его отключают: `gather_facts: no`.

**Свои facts (custom facts):** можно положить файлы в `/etc/ansible/facts.d/` на managed node — их значения попадут в `ansible_local` и будут доступны как обычные facts.

## Q11. Как работают шаблоны (Jinja2)?

**Шаблон** — это файл с подстановками, который модуль `template` рендерит на лету: подставляет переменные и facts, выполняет циклы и условия, а готовый результат кладёт на хост. Так из одного `.j2`-файла получают конфиги, адаптированные под каждый хост (свой порт, свой hostname, свой список бэкендов). Движок — Jinja2, переменные в нём заключают в `{{ }}`, а управляющие конструкции — в `{% %}`.

```yaml
- template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
```

`nginx.conf.j2`:
```jinja2
worker_processes {{ ansible_processor_count }};

server {
    listen {{ nginx_port }};
    server_name {{ inventory_hostname }};

    {% for backend in backend_servers %}
    upstream {{ backend.name }} {
        server {{ backend.host }}:{{ backend.port }};
    }
    {% endfor %}
}
```

В шаблоне выше `{{ nginx_port }}` и `{{ inventory_hostname }}` — подстановка переменных, а блок `{% for %}` генерирует по одному `upstream` на каждый бэкенд из списка. Jinja2 поддерживает переменные, циклы, условия и фильтры (`| default`, `| upper` и т.д.) — этого хватает, чтобы собирать конфиги любой сложности.

## Q12. (!) Что такое Ansible Vault?

**Ansible Vault** — встроенный механизм шифрования чувствительных данных (паролей, ключей, токенов), чтобы их можно было безопасно хранить в git вместе с плейбуками. Решает базовую проблему: секреты нельзя класть в репозиторий в открытом виде, но и держать отдельно от кода неудобно. Vault шифрует файл (или отдельную строку) под общим паролем, а Ansible расшифровывает его на лету при запуске — нужно лишь передать этот vault-пароль.

```bash
# Encrypt file
ansible-vault encrypt secrets.yml

# Edit
ansible-vault edit secrets.yml

# Decrypt
ansible-vault decrypt secrets.yml

# Encrypt single string
ansible-vault encrypt_string 'mypassword' --name 'db_password'
```

**Использование в плейбуке:**
```yaml
vars_files:
  - secrets.yml
```

```bash
ansible-playbook deploy.yml --ask-vault-pass
# or
ansible-playbook deploy.yml --vault-password-file ~/.vault_pass
```

**Рекомендация:** для разных окружений используют отдельные vault-файлы и `vault-id` — так у dev и prod свои пароли, и компрометация одного не открывает остальные.

**Когда Vault недостаточно:** для крупной инфраструктуры с ротацией и аудитом секретов вместо файлов берут централизованное хранилище — **Vault** (HashiCorp), к которому Ansible подключается за секретами в рантайме.

## Q13. Какие best practices по SSH в Ansible?

Поскольку Ansible весь работает поверх SSH, его безопасность и скорость прямо зависят от того, как настроены соединения. Основное настраивают в `ansible.cfg`:

```ini
# ansible.cfg
[defaults]
host_key_checking = False  # for dev (NOT production!)
forks = 50  # parallel connections
pipelining = True  # speed up

[ssh_connection]
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
```

Здесь `pipelining` и `ControlMaster`/`ControlPersist` переиспользуют SSH-соединения вместо переподключения на каждую задачу — это главный рычаг ускорения. `host_key_checking = False` удобен в dev, но в production его оставлять нельзя: отключённая проверка ключа хоста открывает MITM.

**Рекомендации по безопасности:**
- **SSH-ключи вместо паролей** — пароли нельзя автоматизировать безопасно и они подбираются.
- **Bastion / jump-хосты** — единая точка входа в приватные сети, через которую Ansible достаёт внутренние машины.
- **Отдельный пользователь** под Ansible (не root) — меньше прав по умолчанию, понятнее аудит.
- **Повышение прав через `become: yes`** (sudo) только там, где оно реально нужно.
- Режим **`ansible-pull`** — для pull-сценариев, когда хост сам тянет и применяет плейбук (полезно при автоскейлинге, где push на эфемерные машины неудобен).

## Q14. (!) Чем ad-hoc команды отличаются от playbooks?

Разница в назначении: **ad-hoc** — это одна команда «здесь и сейчас» прямо из терминала, а **playbook** — записанный и переиспользуемый сценарий. Грубо: ad-hoc — как набрать команду в shell, playbook — как написать скрипт.

**Ad-hoc** — разовая команда без файла плейбука:
```bash
ansible all -m ping
ansible webservers -m service -a "name=nginx state=restarted" --become
ansible all -a "uname -r"  # shell command
```

**Плейбук** — много задач в YAML-файле, который коммитят в git и запускают повторно.

**Ad-hoc уместен, когда** действие одноразовое и записывать его незачем:
- быстрые проверки (`ping`, «жив ли хост»);
- разовые операции (перезапустить сервис, выполнить команду на парке);
- разведка inventory.

**Плейбуки — когда** сценарий нужно повторять и хранить:
- повторяемые задачи;
- многошаговые workflow с порядком и зависимостями;
- любая автоматизация в составе CI/CD.

## Q15. Что такое check mode (dry-run)?

**Check mode** — режим «прогона вхолостую»: Ansible проходит весь плейбук и сообщает, что бы он изменил, но реально ничего не трогает. Это безопасный способ увидеть последствия до того, как они случатся.

```bash
ansible-playbook deploy.yml --check
```

**Эффект:** показывает, какие задачи дали бы статус `changed`, без реальных изменений на хостах.

**Ограничение:** работает корректно, только если модули умеют check mode (большинство умеют). `command`/`shell` в этом режиме просто пропускаются — Ansible не может предсказать результат произвольной команды, не запустив её.

**Связка с `--diff`:** `--diff` дополнительно показывает построчный diff файлов — что именно поменялось бы в конфигах.

```bash
ansible-playbook deploy.yml --check --diff
```

**Рекомендация:** перед деплоем в production прогонять `--check --diff` — это даёт предпросмотр изменений и ловит ошибки до того, как они доедут до прода.

## Q16. Зачем нужны tags?

**Tags (теги)** — это метки на задачах, позволяющие запустить не весь плейбук, а только нужную его часть. Когда плейбук большой (установка + конфиг + сертификаты + сервисы), а поправить надо только одно, теги избавляют от прогона всего сценария.

```yaml
tasks:
  - name: Install nginx
    package: name=nginx state=present
    tags: nginx, install

  - name: Copy SSL certs
    copy: src=cert.pem dest=/etc/ssl/
    tags: ssl, security
```

**Управление через теги:** `--tags` запускает только помеченные задачи, `--skip-tags` — наоборот, пропускает их:
```bash
ansible-playbook deploy.yml --tags ssl
ansible-playbook deploy.yml --skip-tags install
```

**Типичный сценарий:** быстро передеплоить только конфиг (`--tags config`), пропустив долгие шаги установки пакетов.

## Q17. Как устроено параллельное выполнение (forks)?

`forks` задаёт, на скольких хостах Ansible выполняет текущую задачу **одновременно**. Модель такая: Ansible идёт по задачам по порядку, но каждую отдельную задачу запускает параллельно сразу на пачке хостов размером `forks`. По умолчанию это всего 5 — поэтому на большом парке выполнение тормозит, и значение поднимают.

```ini
# ansible.cfg
[defaults]
forks = 50  # default 5
```

Или для конкретного запуска:
```bash
ansible-playbook deploy.yml --forks 100
```

**Тюнинг — компромисс между скоростью и ресурсами:**
- Больше парк машин — больше forks, но с оглядкой на лимит одновременных SSH-соединений и нагрузку на control node.
- Если control node упирается в память (каждый fork — это процесс), forks снижают.

## Q18. (!) Что такое Ansible Galaxy?

**Ansible Galaxy** — публичный community-хаб готовых **ролей** и **коллекций**, по сути «package manager» для Ansible. Вместо того чтобы писать настройку nginx, postgres или docker с нуля, нужную роль скачивают из Galaxy и подключают. Утилита `ansible-galaxy` ставит роли и коллекции локально.

```bash
# Install role
ansible-galaxy install geerlingguy.nginx

# Install from requirements file
ansible-galaxy install -r requirements.yml
```

`requirements.yml`:
```yaml
roles:
  - name: geerlingguy.nginx
    version: 3.1.4
collections:
  - name: community.general
```

Файл `requirements.yml` фиксирует зависимости с версиями — так сборка воспроизводима. **Подводный камень:** ролей на Galaxy 40K+, но качество разное и никто его не гарантирует. Перед использованием смотрите на звёзды, свежесть обновлений и активность автора (роли `geerlingguy.*` — известный надёжный пример).

## Q19. Что такое collections (появились в Ansible 2.10)?

**Collections** — современная единица упаковки, появившаяся в Ansible 2.10. Если роль упаковывает одну единицу автоматизации, то коллекция — это целый комплект: модули, роли, плагины и документацию в одном пакете. Так появилась модульность: в 2.10 монолитный Ansible разбили на ядро (`ansible-core`) и набор коллекций, которые версионируются и распространяются независимо.

```bash
ansible-galaxy collection install community.kubernetes
```

**Использование в плейбуке:**
```yaml
- hosts: all
  tasks:
    - community.kubernetes.k8s:
        name: my-pod
        ...
```

Модули вызывают по полному имени `namespace.collection.module` — отсюда `community.kubernetes.k8s` в примере. Базовые модули живут во встроенной коллекции **`ansible.builtin`** (`copy`, `template`, `service` и т.д.), которая идёт в комплекте.

**Облачные коллекции** ставят отдельно: `amazon.aws`, `google.cloud`, `azure.azcollection`.

## Q20. (!) Чем различаются AWX, Ansible Tower и Automation Platform?

Это три «слоя» одного и того же продукта — веб-платформы для управления запуском Ansible. Голый Ansible — это CLI; перечисленные продукты добавляют поверх него UI, RBAC, расписания и API. Различаются они лицензией и зрелостью:

- **AWX** — бесплатный open-source upstream. На нём «обкатывают» функции; это тот же движок, что и в платных версиях, но без поддержки и гарантий стабильности.
- **Ansible Tower** — историческое платное издание Red Hat: тот же продукт, но со стабильными релизами и коммерческой поддержкой.
- **Ansible Automation Platform (AAP)** — текущее коммерческое предложение Red Hat, пришедшее на смену Tower: Tower плюс расширения (automation hub, аналитика и т.д.).

Связь простая: AWX → стабилизируется и продаётся как Tower → развивается в AAP.

**Что они дают сверх CLI:**
- Web-интерфейс
- Планирование задач (job scheduling)
- Workflow (цепочки плейбуков)
- RBAC
- API
- Уведомления
- Дашборд, логи

**Self-host AWX** (в Kubernetes через оператор):
```bash
helm install awx awx-operator/awx
```

**Когда это нужно:** когда Ansible запускает целая команда, а не один инженер с ноутбука. Платформа даёт общий аудируемый запуск, права по ролям и историю — то, чего нет у голого CLI.

## Q21. Что такое workflows и schedules в AWX/Tower?

**Workflow** — это граф из нескольких плейбуков (job templates) с ветвлением по результату: следующий шаг выбирается в зависимости от того, успешен ли предыдущий. Так из отдельных плейбуков собирают сквозной процесс «провижининг → конфигурация → деплой» с откатом при сбое.

```
Stage 1: Provision EC2 (Terraform call)
  ↓ on success
Stage 2: Configure servers (Ansible playbook)
  ↓ on success
Stage 3: Deploy app
  ↓ on failure
Stage 4 (cleanup): Rollback
```

В примере выше каждый шаг ветвится по `on success` / `on failure`: при провале конкретного этапа управление уходит на cleanup/rollback вместо продолжения.

**Schedules** — cron-подобные расписания для периодического запуска плейбуков без участия человека: регулярные проверки compliance, бэкапы, сбор инвентаря.

## Q22. (!) Ansible vs Terraform — в чём разница и что когда?

Коротко: они решают разные задачи и чаще дополняют друг друга, чем конкурируют. **Terraform** создаёт инфраструктуру (provisioning) — VM, сети, балансировщики, БД. **Ansible** настраивает то, что уже создано (configuration management) — ставит и конфигурирует ПО внутри машин. Главное архитектурное различие — состояние: Terraform хранит state-файл и знает, что уже создано, поэтому умеет находить дрейф и удалять лишнее; Ansible stateless — каждый запуск независим и опирается только на проверку текущего состояния задачей.

| Аспект | Ansible | Terraform |
|--------|---------|-----------|
| Тип | Управление конфигурацией | Провижининг инфраструктуры |
| Состояние | **Stateless** (каждый запуск независим) | **Stateful** (файл состояния) |
| Подход | Процедурный (задачи по порядку) | Декларативный (желаемое состояние) |
| Идемпотентность | На уровне задачи | На уровне всей инфраструктуры |
| Провижининг в облаке | Нормально | **Отлично** |
| Управление конфигурацией | **Отлично** | Ограниченно |
| Обнаружение дрейфа | Ограниченно | Встроено |

**На практике их связывают в цепочку:**
- **Terraform** провижинит инфраструктуру (VM, сети, БД).
- **Ansible** настраивает ПО на созданных VM.

```
Terraform creates EC2 → Ansible installs nginx, copies config
```

То есть Terraform отвечает за «железо», Ansible — за то, что на нём работает.

## Q23. (!) Ansible vs Puppet vs Chef — чем отличаются?

Все трое — системы управления конфигурацией, и различает их в первую очередь архитектура и модель применения. **Ansible** agentless и push: control node по SSH толкает изменения, ставить ничего не нужно, конфиг — YAML. **Puppet и Chef** agent-based и pull: на каждом хосте крутится агент, который сам периодически тянет конфиг с сервера; язык — Puppet DSL (декларативный) и Ruby (процедурный) соответственно. Именно низкий порог входа и отсутствие агентов вывели Ansible вперёд.

| Критерий | Ansible | Puppet | Chef |
|-----------|---------|--------|------|
| Архитектура | **Agentless** (SSH) | Agent-based | Agent-based |
| Язык | YAML | Puppet DSL (похож на Ruby) | Ruby |
| Подход | Процедурный | Декларативный | Процедурный |
| Push / Pull | Push | Pull | Pull |
| Порог входа | Низкий | Средний | Высокий |
| Распространённость (2025) | **Наибольшая** | Снижается | Снижается |
| Экосистема | Galaxy | Forge | Supermarket |

**Итог:** Ansible выиграл рынок в 2010–2020-х за счёт связки «простота + agentless» — стартовать можно без инфраструктуры агентов. Puppet и Chef в большинстве организаций перешли в разряд legacy.

**Четвёртый игрок — SaltStack:** работает и в agent-, и в agentless-режиме, известен высокой скоростью на больших парках.

## Q24. (!) Какие best practices в Ansible?

Большинство практик сводятся к трём идеям: держать плейбуки идемпотентными, модульными и под контролем версий, а в прод выкатывать только после предпросмотра.

1. **Идемпотентность** — всегда проверяйте, что повторный запуск ничего лишнего не делает.
2. **Роли** — разбивайте большие плейбуки на переиспользуемые модули, не плодите монолит.
3. **Иерархия переменных** — defaults → group_vars → host_vars; не дублируйте значения.
4. **Vault** для секретов (или интеграция с HashiCorp Vault) — никаких паролей в открытом виде.
5. **Контроль версий** — плейбуки в git, чтобы видеть историю и катать через PR.
6. **Inventory в git** (иногда) — версионируйте и список хостов, если он статический.
7. **`check --diff` перед production** — предпросмотр изменений ловит ошибки до прода.
8. **Теги** — для точечных перезапусков без прогона всего плейбука.
9. **Тестируйте плейбуки** фреймворком Molecule — автотесты ролей в чистом окружении.
10. **Интеграция с CI/CD** — автозапуск по git push, чтобы изменения катились единообразно.
11. **Никаких `command` / `shell`**, если есть подходящий модуль — иначе теряете идемпотентность.
12. **Документируйте через `name:`** в каждой задаче — это и читаемый вывод, и адресация по тегам.
13. **Избегайте `latest`** для версий пакетов — фиксируйте версию ради воспроизводимости.
14. **Handlers** для рестартов — чтобы рестарт случался один раз и только при изменениях.

## Q25. Какие частые проблемы и как они проявляются?

Большая часть «болей» Ansible — не в самом инструменте, а в окружении (SSH, sudo) и в дисциплине (переменные, идемпотентность, тесты).

1. **Проблемы с SSH-соединением** — firewall режет порт или не подходят ключи; плейбук просто не достучится до хоста.
2. **Права `become`** — sudo на хосте не настроен, и задачи с повышением прав падают.
3. **Путаница с приоритетом переменных** — значение берётся «не из того файла», и поведение неожиданное (см. Q9).
4. **Нарушения идемпотентности** — `command`/`shell` без условий делают изменения на каждом прогоне.
5. **Медленное выполнение** — мало forks и/или сбор facts на огромном парке машин (см. Q10, Q17).
6. **Управление паролем Vault** — как безопасно раздать vault-пароль команде, не утопив его в чате.
7. **Дрейф inventory** — статические списки хостов устаревают, плейбук бьёт по несуществующим машинам.
8. **Сложность плейбуков** — монолитные простыни задач невозможно сопровождать (лечится ролями).
9. **Различия окружений** — плейбук, отлаженный в dev, падает в prod из-за расхождений конфигурации.
10. **Отсутствие тестов** — непротестированное изменение ломает production (лечится Molecule + check/diff).

**Вывод:** Ansible — де-факто стандарт управления конфигурацией, и чаще всего его ставят в пару с Terraform: Terraform создаёт инфраструктуру, Ansible её настраивает.
