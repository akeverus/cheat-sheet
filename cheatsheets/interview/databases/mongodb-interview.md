## Q1. (!) Что такое `MongoDB` и когда её выбирать?

MongoDB — документоориентированная БД. Она хранит BSON-документы в коллекциях. Документ может содержать вложенные документы и массивы. Связанные данные удобно хранить вместе, если их обычно читают и меняют одной операцией и размер документа ограничен.

Например, в карточке товара можно хранить характеристики конкретной категории. У документов разных категорий могут различаться поля. Правила валидации позволяют закрепить обязательные поля и типы. При добавлении поля нужно решить, как приложение читает старые документы, в которых его ещё нет.

Replica set обеспечивает выборы нового primary, если доступно большинство голосующих участников и есть подходящий кандидат. Шардирование позволяет распределить запись и объём данных, если ключ соответствует запросам и распределению нагрузки. Горячее значение ключа может перегрузить отдельный шард.

При выборе посмотрите, какие данные читаются вместе, какие операции должны быть атомарными и как растут вложенные коллекции. Если бизнес-операция регулярно меняет несколько документов или использует связи многие-ко-многим, сравните цену транзакций и соединений с реляционной схемой. Подробнее — в [архитектуре баз данных](database-architecture-interview.md).

## Q2. В чём отличие `MongoDB` от реляционных баз данных?

Главное различие — единица моделирования. В MongoDB это документ, а в реляционной схеме — строки отношений. Например, ограниченный набор адресов пользователя можно вложить в документ. Заказы с отдельным жизненным циклом удобнее хранить отдельно и связывать идентификатором.

| Аспект | MongoDB | Реляционная БД |
|--------|---------|----------------|
| Структура | BSON-документы с вложенными полями, при необходимости валидируемые правилами коллекции | Таблицы с типами столбцов, ограничениями и миграциями схемы |
| Связи | Вложение, отдельные документы со ссылками, соединение через `$lookup` | Отдельные отношения, внешние ключи и `JOIN` |
| Транзакции | Операция над документом атомарна. Многодокументные транзакции доступны на replica sets с 4.0, в шардированных кластерах с 4.2 | Транзакции могут охватывать несколько таблиц, а гарантии зависят от движка и настроек |
| Доступ | MQL и aggregation pipeline | SQL и возможности конкретного диалекта |

Вложение уменьшает число обращений для чтения агрегата. Ссылки уместны при независимых обновлениях или неограниченном росте связанных данных. MongoDB поддерживает обе модели. Подробнее о реляционных операциях — в [вопросах по SQL](sql-interview.md).

## Q3. (!) Что такое `BSON` и чем он отличается от `JSON`?

BSON — бинарный формат BSON-документов с типизированными значениями. В нём есть отдельные типы для 32- и 64-битных целых, `Decimal128`, даты, двоичных данных и `ObjectId`. BSON Date хранит миллисекунды с начала Unix-эпохи. `Decimal128` хранит десятичные числа с конечной точностью, поэтому подходит для денежных величин при явно заданных правилах округления.

Документ начинается с общей длины. Элемент содержит байт типа, имя и закодированное значение. Строки и вложенные документы включают длины, а целые числа имеют фиксированный размер. Например, запись `{"name":"John","age":30}` с `age` типа Int32 занимает 29 байт:

```text
1d 00 00 00                     общая длина
02 6e 61 6d 65 00               строковое поле name
05 00 00 00 4a 6f 68 6e 00      строка John с нулевым завершением
10 61 67 65 00 1e 00 00 00      поле age со значением Int32 30
00                              конец документа
```

Размер и скорость относительно текстового JSON зависят от данных и реализации. Для представления BSON-типов в JSON используют Extended JSON.

`ObjectId` занимает 12 байт: 4 байта времени в секундах, 5 байт случайного значения процесса и 3 байта счётчика. Его можно сгенерировать на клиенте. Порядок по `ObjectId` приближённо отражает время создания. В пределах одной секунды и между клиентами со сдвинутыми часами строгого временного порядка нет.

## Q4. Что такое коллекция и документ?

Документ — набор типизированных полей BSON, включая вложенные документы и массивы. Коллекция объединяет документы. У документов могут отличаться поля, а правила валидации коллекции позволяют требовать обязательные поля и типы.

В обычной коллекции документ имеет неизменяемый `_id`. Если его не передать, при вставке обычно генерируется `ObjectId`. В шардированной коллекции, где ключ шардирования отличается от `_id`, встроенный индекс `_id` сам по себе обеспечивает уникальность только внутри шарда. Глобальную уникальность в такой схеме обеспечивает приложение.

Предел размера обычного BSON-документа — 16 MiB. Для больших двоичных объектов можно использовать GridFS. Capped collection ограничивает объём данных и при заполнении освобождает место, удаляя старые документы. В MongoDB 8.0 capped collection нельзя шардировать.

```javascript
db.createCollection("logs", { capped: true, size: 10485760, max: 5000 })
```

Здесь ограничены и объём, и число документов. Для выборки в заданном порядке указывайте сортировку явно, особенно если в capped collection пишут параллельно.

## Q5. Какие типы данных поддерживает `MongoDB`?

MongoDB хранит значения в BSON. Тип влияет на сравнение, условия запросов и точность вычислений. Например, денежные значения можно передавать строкой в конструктор `Decimal128`, чтобы сначала не округлить их через двоичный `Double`.

| Тип | Пример в mongosh | Особенность |
|-----|-------------------|-------------|
| String / Boolean | `"paid"`, `true` | Строка UTF-8 и логическое значение |
| Int32 / Int64 | `Int32(42)`, `Long("9007199254740993")` | Целые разной разрядности. Строка в конструкторе Long позволяет избежать потери точности числа JavaScript. |
| Double / Decimal128 | `Double(0.1)`, `Decimal128("0.10")` | Двоичная и десятичная арифметика с конечной точностью |
| Date | `ISODate("2026-01-01T00:00:00Z")` | Миллисекунды с Unix-эпохи |
| ObjectId | `ObjectId("507f1f77bcf86cd799439011")` | 12 байт, распространённый тип `_id` |
| Array / Object | `[1, 2]`, `{ city: "Москва" }` | Массив и вложенный документ |
| Null | `null` | Значение поля. Отсутствие поля можно отдельно проверить через `$exists`. |
| Timestamp | Специальный тип BSON | Используется, например, в oplog. Отличается от Date. |

BSON также поддерживает двоичные значения и регулярные выражения. Подробнее о представлении — Q3.

## Q6. (!) Как моделировать связи: `embedding` vs `referencing`?

**Embedding** подходит, когда связанные данные обычно нужны вместе и их объём ограничен. Например, позиции заказа можно хранить внутри заказа, а сумму и позиции обновлять одним атомарным обновлением документа:

```javascript
{
    orderNumber: "A-42",
    items: [{ sku: "MOUSE", qty: 2, unitPrice: Decimal128("2500.00") }],
    total: Decimal128("5000.00")
}
```

**Referencing** подходит, когда связанные записи растут независимо, используются многими документами или читаются отдельно. Например, профиль покупателя можно хранить отдельно, а в заказе оставить `customerId` и значения, нужные для исторического снимка заказа. Ссылка сама по себе не проверяет существование документа. Чтение через дополнительный запрос или `$lookup` имеет свою стоимость. Многодокументная транзакция нужна, если изменения нескольких документов должны фиксироваться атомарно.

Для десятков тысяч комментариев под одним постом заведите отдельную коллекцию и индекс по идентификатору поста и порядку выдачи. Хранить все комментарии одним массивом рискованно: он растёт к пределу 16 MiB и концентрирует конкурентные обновления в одном документе.

## Q7. Какие ограничения есть в `MongoDB`?

Основные ограничения MongoDB 8.0:

| Объект | Лимит или условие |
|--------|-------------------|
| BSON-документ | До 16 MiB. Каждый вложенный объект или массив добавляет уровень вложенности. Максимум 100 уровней. |
| Индексы | До 64 на коллекцию и до 32 полей в составном индексе. |
| Namespace | До 255 байт для нешардированной коллекции и 235 байт для шардированной. Считаются имя БД, точка и имя коллекции. |
| Имена полей | С MongoDB 5.0 сервер допускает точки и начальный знак доллара в именах с ограничениями. Такие имена, например, нельзя индексировать или использовать в ключе шардирования. |
| Память агрегации | Для этапов, которые могут писать временные файлы, превышение 100 MB приводит к сбросу на диск или ошибке в зависимости от настроек. С MongoDB 6.0 поведение по умолчанию задаёт `allowDiskUseByDefault`, а опция `allowDiskUse` переопределяет его для запроса. |
| Многодокументная транзакция | Доступна на replica set и в шардированном кластере. `transactionLifetimeLimitSeconds` по умолчанию равен 60 секундам. Это настраиваемое время жизни транзакции. |

## Q8. Какие основные `CRUD`-операции есть в `MongoDB`?

```javascript
// CREATE
db.users.insertOne({ name: "Иван", age: 28 })
db.users.insertMany([
    { name: "Мария", age: 25 },
    { name: "Алексей", age: 32 }
])

// READ
db.users.find({ age: { $gte: 25 } })            // все с age >= 25
db.users.findOne({ name: "Иван" })               // один документ
db.users.find({ age: { $gte: 25 } }, { name: 1 }) // проекция: name и _id

// UPDATE
db.users.updateOne(
    { name: "Иван" },
    { $set: { age: 29 }, $push: { tags: "senior" } }
)
db.users.updateMany(
    { age: { $lt: 30 } },
    { $inc: { age: 1 } }
)
db.users.replaceOne(
    { name: "Иван" },
    { name: "Иван", age: 30, role: "developer" }
)

// DELETE
db.users.deleteOne({ name: "Алексей" })
db.users.deleteMany({ age: { $lt: 20 } })
```

**Найти и изменить за один шаг:** `findOneAndUpdate` / `findOneAndDelete` совмещают выбор и изменение одного документа. В mongosh `findOneAndUpdate` по умолчанию возвращает старую версию, а `returnDocument: "after"` возвращает обновлённую. `findOneAndDelete` возвращает удалённый документ.

Чтобы два воркера не забрали одну задачу, в фильтре укажите ожидаемый статус `pending`, а обновлением смените его на `running`. Атомарность относится к одному документу: `updateMany` обновляет каждый документ атомарно, но другие операции могут вклиниться между изменениями разных документов.

## Q9. Как работают операторы сравнения и логические операторы?

В `MQL` условия описываются документом-фильтром: ключ — поле, значение — либо точное совпадение, либо документ с оператором (`{ age: { $gt: 25 } }`). Несколько полей на одном уровне неявно соединяются логикой И.

**Операторы сравнения:**
- `$eq`, `$ne` — равно / не равно
- `$gt`, `$gte`, `$lt`, `$lte` — больше / больше-равно / меньше / меньше-равно
- `$in`, `$nin` — в списке / не в списке
- `$exists` — поле существует (полезно из-за гибкой схемы — поля может не быть)
- `$type` — поле имеет указанный `BSON`-тип

**Логические операторы:** `$and`, `$or`, `$not`, `$nor` — для явного комбинирования условий, когда неявного И недостаточно.

```javascript
// Пользователи из Москвы или Петербурга старше 25
db.users.find({
    "address.city": { $in: ["Москва", "Санкт-Петербург"] },
    age: { $gt: 25 }
})

// Поиск по вложенному полю (dot notation)
db.users.find({ "address.city": "Москва" })

// Поиск по элементу массива
db.users.find({ interests: "Java" })

// $elemMatch — элемент массива удовлетворяет нескольким условиям
db.orders.find({
    items: { $elemMatch: { product: "Ноутбук", qty: { $gte: 2 } } }
})
```

Условие `{ email: null }` находит документы с `null` и документы без поля. `{ email: { $exists: true } }` включает поля со значением `null`. Отрицательные операторы вроде `$nin` могут совпасть с отсутствующим полем. Если оба условия должны относиться к одному элементу массива, используйте `$elemMatch`: отдельные предикаты по путям могут совпасть с разными элементами.

## Q10. (!) Как обновлять документы: операторы `$set`, `$inc`, `$push`, `$pull`?

Основные операторы обновления:

```javascript
// $set — установить значение поля
db.users.updateOne({ _id: id }, { $set: { status: "active" } })

// $unset — удалить поле
db.users.updateOne({ _id: id }, { $unset: { tempField: "" } })

// $inc — инкремент числового поля
db.users.updateOne({ _id: id }, { $inc: { loginCount: 1, score: -5 } })

// $push — добавить элемент в массив
db.users.updateOne({ _id: id }, { $push: { tags: "mongodb" } })

// $addToSet — добавить, если ещё нет в массиве
db.users.updateOne({ _id: id }, { $addToSet: { tags: "mongodb" } })

// $pull — удалить элемент из массива
db.users.updateOne({ _id: id }, { $pull: { tags: "deprecated" } })

// $push с $each и $sort — добавить несколько, отсортировать
db.users.updateOne({ _id: id }, {
    $push: {
        scores: { $each: [85, 92], $sort: -1, $slice: 10 }
    }
})

// Upsert — вставить, если не найден
db.users.updateOne(
    { email: "new@example.com" },
    { $set: { name: "Новый" }, $setOnInsert: { createdAt: new Date() } },
    { upsert: true }
)
```

**Граничные случаи.** `$inc` создаёт отсутствующее поле со значением приращения, а для `null` возвращает ошибку. `$push` и `$addToSet` создают массив, если поля нет, и завершаются ошибкой, если существующее поле имеет другой тип. `$addToSet` не удаляет уже имеющиеся дубли, а `$pull` удаляет все элементы, удовлетворяющие условию.

Запись одного документа атомарна. Для конкурентных upsert по email закрепите инвариант уникальным индексом, если схема шардирования допускает такой индекс. Обработку повторов и конфликтов определяет приложение.

## Q11. В чём разница между `find` и `aggregate`?

Используйте `find` для выборки с фильтром, проекцией, сортировкой и ограничением числа документов. `aggregate` задаёт последовательность этапов, например для группировки, вычисляемых полей и `$lookup`.

```javascript
db.orders.find({ status: "paid" }, { total: 1, _id: 0 }).limit(20)

db.orders.aggregate([
    { $match: { status: "paid" } },
    { $group: { _id: "$customerId", total: { $sum: "$total" } } }
])
```

Оба интерфейса могут использовать индексы. Для pipeline важен фактический план: `$match` в начале может использовать индекс, а оптимизатор может переместить независимый фильтр перед преобразованием полей. Поздняя сортировка после группировки может потребовать отдельной работы. Сравнивайте планы и число обработанных документов, а не скорость интерфейсов в отрыве от запроса.

## Q12. (!) Что такое индексы в `MongoDB` и какие типы существуют?

Индекс хранит ключи для поиска и может помочь с фильтром или сортировкой. Без выгодного пути через индекс планировщик может выбрать `COLLSCAN`. Однопольный и составной индексы описывают число ключей, а unique, partial и TTL задают свойства индекса. Один индекс может сочетать несколько свойств.

Примеры независимы. Выбирайте индекс под запрос и ограничения коллекции:

```javascript
// 1. Single field — одно поле
db.users.createIndex({ email: 1 })

// 2. Compound — составной (несколько полей)
db.orders.createIndex({ status: 1, createdAt: -1 })

// 3. Unique — уникальный
db.users.createIndex({ email: 1 }, { unique: true })

// 4. Text — полнотекстовый
db.articles.createIndex({ title: "text", body: "text" })

// 5. Hashed — хеш ключа для равенства и хешированного шардирования
db.users.createIndex({ userId: "hashed" })

// 6. TTL — фоновое удаление после истечения срока
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })

// 7. Geospatial — геоиндекс
db.places.createIndex({ location: "2dsphere" })

// 8. Partial — индекс с условием (экономия места)
db.orders.createIndex(
    { status: 1 },
    { partialFilterExpression: { status: "ACTIVE" } }
)

// 9. Wildcard — для документов с динамической структурой
db.products.createIndex({ "attributes.$**": 1 })

// 10. Multikey — автоматически для массивов
db.posts.createIndex({ tags: 1 })
```

**Компромисс:** индексы ускоряют чтение, но замедляют запись — вставки и изменения ключей требуют обслуживания затронутых индексов, которые занимают место на диске и используют кэш. Поэтому создавайте индексы под реальные паттерны запросов, а не «на всякий случай». Подробнее об индексах реляционных БД — в [вопросах по SQL](sql-interview.md).

## Q13. (!) Как работает составной индекс и правило `ESR`?

Составной индекс упорядочен по полям ключа. Для `{ a: 1, b: 1, c: 1 }` фильтр по `a` или паре `a, b` использует ведущий префикс. С фильтром по `a, c` индекс может учитывать `c`, но отсутствие ограничения на `b` может потребовать просмотра многих ключей с тем же `a`. Фильтр только по `b` не даёт эффективного поиска по этому префиксу.

Для запроса `status = "ACTIVE"`, `price > 1000` с сортировкой по `createdAt` сравните два порядка:

- **ESR** — равенство, сортировка, диапазон. `{ status: 1, createdAt: -1, price: 1 }` помогает сохранить порядок выдачи без отдельной сортировки.
- **ERS** — равенство, диапазон, сортировка. `{ status: 1, price: 1, createdAt: -1 }` может сократить просмотр ключей при очень селективном условии по цене. Для выдачи по времени может понадобиться отдельная сортировка.

Для сортировки по части ключа после префикса предыдущие поля должны быть зафиксированы равенствами. Поведение `$in` с сортировкой зависит от размера списка и версии сервера. В `explain("executionStats")` сравнивайте наличие SORT, число просмотренных ключей и документов.

## Q14. Что такое `covered query`?

Покрывающий индекс позволяет ответить на запрос без чтения документов. Все поля, нужные для фильтра, проекции и внутренних условий, должны быть доступны в индексе. Например, при запросе через `mongos` индекс должен содержать ключ шардирования. Наличие всех полей — необходимое условие, но есть исключения: предикат на равенство `null` не покрывается, а multikey-индекс не возвращает само индексированное поле-массив без чтения документа.

```javascript
db.users.createIndex({ email: 1, name: 1 })

db.users.find(
    { email: "ivan@example.com" },
    { email: 1, name: 1, _id: 0 }
).explain("executionStats")
```

Здесь `_id: 0` убирает поле, которого нет в индексе. Для подтверждения покрытия смотрите индексный путь без FETCH и `totalDocsExamined: 0` на запросе, который действительно вернул строки. Число просмотренных ключей зависит от данных и границ поиска.

## Q15. (!) Как реализовать полнотекстовый поиск?

Встроенный поиск `$text` использует текстовый индекс. Например, для русскоязычных статей можно настроить язык анализа и вес заголовка:

```javascript
// Создание текстового индекса (один на коллекцию)
db.articles.createIndex(
    { title: "text", body: "text" },
    { weights: { title: 10, body: 5 }, default_language: "russian" }
)

// Поиск
db.articles.find({ $text: { $search: "MongoDB индексы" } })

// С ранжированием по релевантности
db.articles.find(
    { $text: { $search: "MongoDB индексы" } },
    { score: { $meta: "textScore" } }
).sort({ score: { $meta: "textScore" } })

// Фразовый поиск для выбранного языка анализа
db.articles.find({ $text: { $search: "\"replica set\"" } })

// Исключение слова
db.articles.find({ $text: { $search: "MongoDB -deprecated" } })
```

**Ограничения:** один текстовый индекс на коллекцию; не поддерживает fuzzy-поиск, нет синонимов (есть в `Atlas Search`). При нескольких словах обычный запрос ищет совпадение по любому из терминов. Кавычки требуют совпадения фразы. Для поиска с опечатками или синонимами можно использовать отдельный поисковый интерфейс, например Atlas Search или [Elasticsearch](elasticsearch-interview.md).

## Q16. Что такое `TTL`-индекс?

TTL-индекс отмечает документы, которые можно удалить после истечения срока. Для поля с датой срок вычисляется как дата плюс `expireAfterSeconds`. При массиве дат используется самая ранняя. Если поле отсутствует или не содержит даты, этот индекс не удалит документ.

```javascript
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })
db.notifications.createIndex({ expireAt: 1 }, { expireAfterSeconds: 0 })
```

В первом примере документ становится доступен для удаления через час после `createdAt`, во втором — начиная с `expireAt`. Удаление фоновое. Проход обычно запускается раз в 60 секунд, а под нагрузкой просроченные документы могут оставаться дольше. В replica set удаляет primary, а остальные участники применяют изменения через репликацию. TTL задаётся на однопольном индексе.

Если приложению важно перестать принимать сессию точно по сроку, оно должно проверять срок при чтении и использовать TTL для последующей уборки.

## Q17. (!) Как устроен агрегационный `pipeline`?

Pipeline — последовательность этапов. Каждый этап получает результат предыдущего. Например, можно отобрать оплаченные заказы, посчитать сумму по категориям и вывести десять категорий с наибольшей выручкой:

```javascript
db.orders.aggregate([
    { $match: {
        status: "COMPLETED",
        createdAt: { $gte: ISODate("2026-01-01T00:00:00Z") }
    }},
    { $group: {
        _id: "$category",
        totalRevenue: { $sum: "$amount" },
        orderCount: { $sum: 1 }
    }},
    { $sort: { totalRevenue: -1, _id: 1 } },
    { $limit: 10 },
    { $project: { category: "$_id", totalRevenue: 1, orderCount: 1, _id: 0 } }
])
```

Подходящий индекс может помочь начальному `$match`. Сортировка по вычисленной сумме выполняется после группировки. Оптимизатор может объединить `$sort` и `$limit`, чтобы удерживать только лучшие результаты. Ранний `$project` обычно не нужен только для сокращения набора полей: сервер умеет определять используемые поля. Для этапов, поддерживающих временные файлы, проверьте настройки spill (Q7) и показатели плана.

## Q18. Как работает `$lookup` (аналог `JOIN`)?

Этап `$lookup` добавляет к каждому исходному документу массив совпавших документов. Если совпадений нет, массив пуст, а исходный документ остаётся в потоке. Это соответствует семантике левого внешнего соединения до разворачивания массива.

```javascript
db.orders.aggregate([
    { $lookup: {
        from: "users",
        localField: "userId",
        foreignField: "_id",
        as: "user"
    }},
    { $unwind: { path: "$user", preserveNullAndEmptyArrays: true } },
    { $project: { orderNumber: 1, "user.name": 1, amount: 1 } }
])
```

Обычный `$unwind: "$user"` отбросит заказ без совпадения. Здесь `preserveNullAndEmptyArrays` сохраняет его. Для соединения по равенству проверьте индекс на `foreignField`. В варианте с подконвейером возможности использования индекса зависят от выражений и ограничений плана.

С MongoDB 5.1 коллекция `from` может быть шардированной. Это не гарантирует обращение к одному шарду. Смотрите фактический план и объём обмена, прежде чем решать, хранить ли данные вместе (Q6).

## Q19. Как использовать `$group`, `$unwind`, `$project`?

- **`$unwind`** выдаёт отдельный документ на каждый элемент массива. По умолчанию пустой массив, `null` и отсутствующее поле не дают выходной записи. Для сохранения таких документов используйте `preserveNullAndEmptyArrays`.
- **`$group`** объединяет документы по выражению `_id` и считает накопители. Порядок групп задаёт отдельный `$sort`.
- **`$project`** выбирает поля ответа и вычисляет новые. `_id` включается по умолчанию, если его явно не исключить.

Этот запрос считает число публикаций для каждого тега, даже если в одной публикации тег повторился:

```javascript
db.posts.aggregate([
    { $unwind: "$tags" },
    { $group: { _id: { postId: "$_id", tag: "$tags" } } },
    { $group: { _id: "$_id.tag", postCount: { $sum: 1 } } },
    { $sort: { postCount: -1, _id: 1 } },
    { $project: { _id: 0, tag: "$_id", postCount: 1 } }
])
```

Первая группировка оставляет одну запись на пару «публикация и тег». Если нужно считать каждое вхождение, её можно убрать и группировать непосредственно по `$tags`.

## Q20. (!) Что такое `Replica Set` и как происходит выбор `primary`?

Replica set — группа участников, поддерживающих копии данных через oplog. Primary принимает запись, а secondary применяют изменения и могут обслуживать чтения при подходящей настройке. Arbiter участвует в голосовании, но не хранит данные и не подтверждает их запись.

Если участники теряют связь с primary, подходящий secondary может начать выборы. Для победы нужно большинство голосующих участников. `priority: 0` исключает избрание этого участника. Пока нет primary, запись недоступна. Временной предел зависит от настроек выборов, сети и состояния участников.

Сетевой разрыв может оставить прежний primary доступным отдельным клиентам до того, как он уйдёт с роли. Записи без подтверждения большинства могут откатиться при восстановлении. В конфигурации из трёх голосующих узлов большинство — два. Четыре голосующих узла требуют трёх голосов и сами по себе не позволяют пережить больше отказов голосующих узлов, чем три.

## Q21. (!) Что такое `Write Concern` и `Read Concern`?

**Write concern** определяет, какого подтверждения ждёт клиент:

- `w: 0` не запрашивает подтверждение записи.
- `w: 1` ждёт подтверждения primary. Запись может отсутствовать на новом primary после переключения.
- `w: "majority"` ждёт записи на рассчитанном большинстве голосующих участников, хранящих данные. Arbiter не подтверждает данные.
- `j: true` требует записи в журнал для подтверждающих узлов. Для `w: "majority"` при обычной настройке `writeConcernMajorityJournalDefault: true` ожидание журнала уже входит в подтверждение.

**Read concern** задаёт требования к видимому состоянию:

- `local` читает доступное состояние выбранного узла. Изменения могут ещё не быть подтверждены большинством.
- `majority` читает состояние, подтверждённое большинством. Оно может отставать от последних записей.
- `linearizable` доступен на primary для подходящих чтений одного документа и учитывает успешные записи с majority, завершившиеся до начала чтения.
- `snapshot` читает согласованный снимок. С MongoDB 5.0 он доступен вне транзакций для ряда операций. В транзакции гарантию чтения majority-committed снимка связывают с фиксацией с `w: "majority"`.

Таймаут ожидания write concern не означает, что сервер отменил сделанные изменения. При повторе учитывайте неопределённый исход операции.

## Q22. Что такое `Read Preference` и когда читать из реплик?

Read preference выбирает, какой участник replica set обслуживает чтение. Read concern задаёт требования к видимости данных (Q21).

| Режим | Выбор узла |
|-------|------------|
| `primary` (по умолчанию) | Только primary. |
| `primaryPreferred` | Primary, при его недоступности — подходящий secondary. |
| `secondary` | Только подходящий secondary. |
| `secondaryPreferred` | Подходящий secondary, при его отсутствии — primary. |
| `nearest` | Подходящий primary или secondary из допустимого окна задержек. |

Отчёт, который допускает отставание, можно читать с secondary. При `secondaryPreferred` учтите, что отказ реплик может вернуть нагрузку на primary. `maxStalenessSeconds` отсекает слишком отставшие secondary по оценке драйвера. Эта настройка не гарантирует видимость конкретной записи.

Для read-your-writes на разных участниках можно использовать causally consistent session с read concern и write concern `majority`. Одна настройка read preference не обеспечивает такую гарантию. Транзакции с чтением используют `primary`.

## Q23. Что такое `Oplog`?

Oplog — журнал операций репликации в коллекции `local.oplog.rs`. Primary добавляет записи о выполненных изменениях, а secondary получают их от источника синхронизации и применяют локально. Источником может быть другой secondary. На истории oplog также опираются change streams.

Размер oplog определяет доступное окно истории в байтах, а его длительность зависит от интенсивности изменений. Oplog может превысить настроенный размер, чтобы сохранить majority commit point. Если вторичный узел отстал за доступное окно у всех возможных источников, ему нужна повторная синхронизация. Оценивайте окно времени на фоне пиков записи, а не только размер файла.

```javascript
db.getSiblingDB("local").getCollection("oplog.rs")
    .find().sort({ $natural: -1 }).limit(5)
```

## Q24. (!) Как работает шардирование в `MongoDB`?

Шардирование распределяет документы одной коллекции по шардам. Каждый шард — replica set. Config servers хранят карту распределения, а `mongos` кэширует её и направляет запросы. Chunk описывает диапазон значений ключа. Balancer переносит диапазоны, учитывая объём данных и зоны (Database Sharding Q24).

При равенстве по полному ключу `mongos` обычно может выбрать нужный шард. Фильтр по префиксу составного ключа или по диапазону может сузить запрос до нескольких шардов. Если по предикату и карте размещения нельзя исключить ни одного, запрос рассылается всем. Поэтому наличие поля ключа в фильтре само по себе не обещает один маршрут.

Для частых запросов смотрите в `explain`, какие шарды участвовали и сколько данных прочитал каждый. При запросе ко всем шардам оцените время самого медленного участника, пересылку промежуточных данных и работу по объединению результатов.

## Q25. (!) Как выбрать `shard key`?

Выбирайте ключ по распределению данных и форме запросов. Высокая кардинальность даёт больше значений для разбиения. Частое значение ключа всё равно может создать неделимый горячий диапазон. Монотонный ведущий ключ при разбиении по диапазонам направляет последовательные вставки в крайний диапазон.

Например, ключ `{ userId: 1, createdAt: 1 }` подходит для чтения истории конкретного пользователя. Фильтр только по `userId` может затронуть несколько шардов, а монотонная запись одного очень активного пользователя всё ещё может перегреть его текущий диапазон. Ключ `{ _id: "hashed" }` распределяет различные идентификаторы, но фильтр по интервалу исходных `_id` обычно нельзя эффективно направить на небольшой набор шардов.

С MongoDB 7.0 команда `analyzeShardKey` помогает оценить характеристики ключа и распределение запросов по собранной выборке. С MongoDB 5.0 `reshardCollection` позволяет сменить ключ, а `refineCollectionShardKey` добавляет поля в конец существующего ключа. Это разные операции: уточнение ключа само по себе не означает немедленный перенос данных.

## Q26. В чём разница между `range-based` и `hash-based` sharding?

Range-based sharding делит исходные значения ключа на диапазоны. Это сохраняет возможность исключить шарды, чьи диапазоны не пересекаются с условием. Один запрос по широкому интервалу может затронуть несколько или все шарды. Монотонные вставки могут перегрузить крайний диапазон.

Hashed sharding делит пространство хешей ключа. По точному значению можно вычислить хеш, но близкие исходные значения могут лежать на разных шардах. Хеш помогает распределять разные значения. Повторяющееся горячее значение всё равно получает тот же хеш.

В составном ключе `{ country: 1, orderId: "hashed" }` условие по стране может ограничить маршрутизацию, если заказы страны занимают только часть шардов. Условие по стране и точному ID даёт полный ключ. Запросы по одному диапазону исходных ID сохраняют цену обращения к нескольким диапазонам хеша.

## Q27. (!) Как работают транзакции в `MongoDB`?

Многодокументные транзакции доступны на replica sets с MongoDB 4.0 и на шардированных кластерах с 4.2. Они позволяют зафиксировать изменения нескольких документов вместе. В примере перевод использует целочисленные денежные единицы, проверяет достаточность средств и требует, чтобы оба счёта существовали:

```javascript
const session = db.getMongo().startSession()
try {
    const accounts = session.getDatabase("bank").accounts
    session.withTransaction(() => {
        const debit = accounts.updateOne(
            { _id: "from", balance: { $gte: 100 } },
            { $inc: { balance: -100 } }
        )
        if (debit.matchedCount !== 1) {
            throw new Error("Исходный счёт отсутствует или недостаточно средств")
        }
        const credit = accounts.updateOne(
            { _id: "to" },
            { $inc: { balance: 100 } }
        )
        if (credit.matchedCount !== 1) {
            throw new Error("Счёт назначения отсутствует")
        }
    }, {
        readConcern: { level: "snapshot" },
        writeConcern: { w: "majority" }
    })
} finally {
    session.endSession()
}
```

Callback может быть повторно вызван при временной ошибке транзакции. Внешние побочные эффекты следует вынести из него или обеспечить идемпотентность. Неопределённый результат commit требует проверки или повторения commit согласно API драйвера.

В MongoDB 8.0 лимит 16 MiB применяется к отдельной записи oplog, а транзакция может состоять из нескольких записей. Ограничение времени жизни по умолчанию — 60 секунд. Создание коллекций и индексов внутри транзакции допускается при определённых условиях. Например, создание запрещено в транзакции с записью на нескольких шардах. Параметры и команды проверяйте для конкретной топологии.

## Q28. Как работает оптимистическая блокировка?

Оптимистическая блокировка решает проблему «потерянного обновления»: два потока читают один документ, оба меняют его и записывают — и одно изменение молча затирает другое. MongoDB атомарно проверяет фильтр и обновляет один документ. Приложение добавляет в фильтр ожидаемое значение **поля версии**. Идея: при записи проверяем, что версия не изменилась с момента чтения, и только тогда применяем апдейт, увеличивая версию.

```javascript
// 1. Прочитать документ с версией
const doc = db.products.findOne({ _id: productId });
if (doc === null) {
    throw new Error("Product not found");
}

// 2. Обновить с проверкой версии
const result = db.products.updateOne(
    { _id: productId, version: doc.version },
    { $set: { price: newPrice }, $inc: { version: 1 } }
);

// 3. Проверить, было ли обновление
if (result.matchedCount === 0) {
    throw new Error("Product deleted or concurrently modified");
}
```

В `Spring Data MongoDB` — аннотация `@Version`:

```java
@Document(collection = "products")
public class Product {
    @Id private String id;
    @Version private Long version; // автоматическая оптимистическая блокировка
    private String name;
    private BigDecimal price;
}
```

При сохранении существующей сущности через `repository.save(product)` Spring Data учитывает версию и сообщает о конфликте через `OptimisticLockingFailureException`. Нужен подтверждаемый write concern: при записи без подтверждения приложение может не увидеть конфликт. Для произвольного `updateFirst` задавайте ожидаемую версию в фильтре явно, когда операция должна выполнять ту же проверку. При повторе сначала перечитайте данные и пересчитайте изменение.

## Q29. Что такое `Schema Validation`?

**Schema Validation** — правила, которыми БД проверяет документы при вставке и обновлении. Гибкая схема `MongoDB` удобна, но иногда нужна гарантия, что в коллекции не появится мусорных или неполных документов — даже если в приложении есть баг или данные пишет несколько сервисов. Validation добавляет такой барьер на уровне БД, обычно через `$jsonSchema`:

```javascript
db.createCollection("users", {
    validator: {
        $jsonSchema: {
            bsonType: "object",
            required: ["email", "name", "role"],
            properties: {
                email: {
                    bsonType: "string",
                    pattern: "^.+@.+\\..+$",
                    description: "должен соответствовать указанному шаблону"
                },
                name: { bsonType: "string", minLength: 1 },
                age: { bsonType: "int", minimum: 0, maximum: 150 },
                role: { enum: ["admin", "user", "moderator"] }
            }
        }
    },
    validationLevel: "strict",       // strict | moderate | off
    validationAction: "error"        // error | warn
})
```

- **`strict`** — проверяет вставки и итоговое состояние при обновлениях. Добавление правила не сканирует и не исправляет старые документы автоматически.
- **`moderate`** — проверяет только новые документы и те старые, что уже соответствовали схеме; удобно при постепенном внедрении валидации на существующую коллекцию, где есть «исторические» невалидные записи.
- **`off`** — отключает проверку.
- **`error`** — отклоняет невалидный документ (`WriteError` с кодом 121).
- **`warn`** — пишет предупреждение в лог, но документ сохраняет; полезно, чтобы сначала оценить масштаб нарушений, не ломая запись.

Для существующей коллекции правила можно изменить через `collMod`. При переходе на строгую проверку заранее оцените, какие старые документы не пройдут новые правила при обновлении. Валидация отдельного документа не заменяет уникальный индекс.

## Q30. (!) Как использовать `Spring Data MongoDB`: `MongoRepository` и `MongoTemplate`?

`Spring Data MongoDB` даёт два уровня работы с БД, и выбор между ними — частый вопрос на собеседовании. `MongoRepository` — декларативный, высокоуровневый: вы описываете интерфейс, а реализацию генерирует Spring. `MongoTemplate` — программный: вы сами собираете запрос и получаете полный контроль. На практике их сочетают.

**`MongoRepository`** — декларативный подход, аналогичный `Spring Data JPA`. Запрос выводится из имени метода или задаётся аннотацией `@Query`:

```java
@Document(collection = "users")
public class User {
    @Id private String id;
    @Indexed(unique = true) private String email;
    private String name;
    private Integer age;
    private String status;
    private Instant createdAt;
    private long loginCount;
    private Instant lastLogin;
    private Address address; // вложенный объект
}

public interface UserRepository extends MongoRepository<User, String> {
    // Автогенерация запроса по имени метода
    List<User> findByName(String name);
    List<User> findByAgeBetween(int min, int max);
    List<User> findByAddress_City(String city); // dot notation

    // Кастомный запрос MQL
    @Query("{ 'age': { $gte: ?0 }, 'address.city': ?1 }")
    List<User> findByMinAgeAndCity(int minAge, String city);

    // Проекция в отдельный интерфейс
    @Query(value = "{ 'status': 'ACTIVE' }", fields = "{ 'name': 1, 'email': 1 }")
    List<UserSummary> findActiveUsersProjected();

    interface UserSummary {
        String getName();
        String getEmail();
    }

    // Пагинация
    Page<User> findByStatus(String status, Pageable pageable);
}
```

**`MongoTemplate`** — программный подход для сложных запросов:

```java
@Service
@RequiredArgsConstructor
public class UserService {
    private final MongoTemplate mongoTemplate;

    public List<User> findByComplexCriteria(String city, int minAge) {
        Query query = new Query();
        query.addCriteria(Criteria.where("address.city").is(city)
                .and("age").gte(minAge));
        query.with(Sort.by(Sort.Direction.DESC, "createdAt"));
        query.limit(20);
        return mongoTemplate.find(query, User.class);
    }

    public UpdateResult incrementLoginCount(String userId) {
        Query query = Query.query(Criteria.where("id").is(userId));
        Update update = new Update()
                .inc("loginCount", 1)
                .set("lastLogin", Instant.now());
        return mongoTemplate.updateFirst(query, update, User.class);
    }
}
```

Аннотация `@Indexed` описывает индекс. Проверьте способ создания индексов: автоматическое создание по аннотациям по умолчанию отключено начиная со Spring Data MongoDB 3.0. Проекции с частью полей удобно возвращать отдельно от сохраняемой сущности.

**Когда что использовать:**
- `MongoRepository` — `CRUD`, простые запросы, пагинация
- `MongoTemplate` — агрегации, `bulkOps`, сложные update, `upsert`, программная логика

Подробнее о `Spring Data` — в [вопросах по Spring Data JPA](../frameworks/spring/spring-data-jpa-interview.md) (аналогичный подход для РСУБД).

## Q31. Какие аннотации используются в `Spring Data MongoDB`?

| Аннотация | Назначение | Пример |
|-----------|-----------|--------|
| `@Document` | Маркер документа, привязка к коллекции | `@Document(collection = "orders")` |
| `@Id` | Поле `_id` | `@Id private String id;` |
| `@Field` | Маппинг на имя поля в `BSON` | `@Field("user_name") private String name;` |
| `@Indexed` | Описание индекса | `@Indexed(unique = true)` |
| `@CompoundIndex` | Составной индекс | `@CompoundIndex(def = "{'status': 1, 'createdAt': -1}")` |
| `@TextIndexed` | Текстовый индекс | `@TextIndexed(weight = 2)` |
| `@DBRef` | Ссылка на документ в другой коллекции | `@DBRef private User author;` |
| `@Version` | Оптимистическая блокировка | `@Version private Long version;` |
| `@Transient` | Не сохранять в БД | `@Transient private String computed;` |
| `@CreatedDate` | Дата создания (auditing) | Требует `@EnableMongoAuditing` |
| `@LastModifiedDate` | Дата последнего обновления | Требует `@EnableMongoAuditing` |

```java
@Document(collection = "orders")
@CompoundIndex(def = "{'status': 1, 'createdAt': -1}", name = "status_date_idx")
public class Order {
    @Id private String id;
    @Field("user_id") private String userId;
    private String status;
    @Version private Long version;
    @CreatedDate private Instant createdAt;
    @LastModifiedDate private Instant updatedAt;
    private List<OrderItem> items; // embedded
    @Field(targetType = FieldType.DECIMAL128)
    private BigDecimal total;
}
```

Начиная со Spring Data MongoDB 3.0 автоматическое создание индексов по аннотациям требует явного включения. При управлении схемой через миграции проверяйте фактические индексы в БД. `@DBRef` описывает ссылку и её разрешение при чтении. Она не создаёт внешний ключ и не сохраняет связанную сущность каскадно.

## Q32. (!) Как выполнять агрегации в `Spring Data MongoDB`?

Для программного pipeline используйте `MongoTemplate.aggregate`. Пример считает выручку по категориям. После `unwind` входом для группировки становится позиция заказа, поэтому `count()` считает позиции. Сумма берётся из `lineTotal`, где цена уже умножена на количество.

```java
record CategoryStats(String category, BigDecimal revenue, long itemCount) {}

public List<CategoryStats> getCategoryStats(Instant from) {
    Aggregation aggregation = Aggregation.newAggregation(
        Aggregation.match(Criteria.where("status").is("COMPLETED")
            .and("createdAt").gte(Date.from(from))),
        Aggregation.unwind("items"),
        Aggregation.group("items.category")
            .sum("items.lineTotal").as("revenue")
            .count().as("itemCount"),
        Aggregation.sort(Sort.Direction.DESC, "revenue"),
        Aggregation.project("revenue", "itemCount")
            .and("_id").as("category")
            .andExclude("_id")
    );
    return mongoTemplate.aggregate(aggregation, "orders", CategoryStats.class)
        .getMappedResults();
}
```

В нетипизированном pipeline для имени коллекции используйте имена полей BSON. Например, ссылка `userId` из Q31 хранится как `user_id`. Типизированная агрегация учитывает метаданные отображения. Для статического pipeline можно описать этапы в `@Aggregation` на методе репозитория.

## Q33. Как использовать транзакции в `Spring Data MongoDB`?

Для императивной декларативной транзакции настройте `MongoTransactionManager` и используйте `MongoTemplate` с той же `MongoDatabaseFactory`. MongoDB должна работать как replica set или шардированный кластер. В приложении с несколькими transaction manager явно укажите нужный менеджер.

```java
@Bean
MongoTransactionManager mongoTransactionManager(MongoDatabaseFactory factory) {
    return new MongoTransactionManager(factory);
}
```

Пример использует баланс в целых минимальных денежных единицах и проверяет совпадения обоих обновлений:

```java
@Transactional(transactionManager = "mongoTransactionManager")
public void transfer(String fromId, String toId, long amountInCents) {
    if (amountInCents <= 0 || fromId.equals(toId)) {
        throw new IllegalArgumentException("Invalid transfer");
    }
    Query debitQuery = Query.query(Criteria.where("id").is(fromId)
        .and("balanceInCents").gte(amountInCents));
    UpdateResult debit = mongoTemplate.updateFirst(debitQuery,
        new Update().inc("balanceInCents", -amountInCents), Account.class);
    if (debit.getMatchedCount() != 1) {
        throw new IllegalStateException("Source account missing or insufficient funds");
    }
    UpdateResult credit = mongoTemplate.updateFirst(
        Query.query(Criteria.where("id").is(toId)),
        new Update().inc("balanceInCents", amountInCents), Account.class);
    if (credit.getMatchedCount() != 1) {
        throw new IllegalStateException("Destination account missing");
    }
}
```

В стандартном proxy-режиме метод должен вызываться через Spring proxy. Непроверяемые исключения по умолчанию ведут к rollback. Для программного варианта передайте тот же MongoTransactionManager в `TransactionTemplate`. Повтор после конфликтов и обработка неопределённого результата commit требуют отдельной политики (Q27).

## Q34. Как настроить подключение к `MongoDB` в `Spring Boot`?

В Spring Boot 4.0 URI задаётся через `spring.mongodb.uri`. В Spring Boot 3.x используется `spring.data.mongodb.uri`. Свойство `spring.data.mongodb.auto-index-creation` в Boot 4.0 сохраняет прежний префикс, поскольку относится к Spring Data.

```yaml
# Spring Boot 4.0
spring:
  mongodb:
    uri: ${MONGODB_URI}
```

В URI указывают базу, параметры топологии и при необходимости базу аутентификации. Например, для replica set задают адреса участников и `replicaSet=rs0`. Учетные данные передавайте через секрет окружения, не сохраняйте их в YAML. Не смешивайте URI с альтернативной конфигурацией host/port без проверки правил привязки свойств вашей версии.

Для настройки пула и таймаутов при автоконфигурации можно зарегистрировать `MongoClientSettingsBuilderCustomizer`. Один `MongoClient` может обслуживать несколько баз. Если нужны отдельные `MongoTemplate`, настройте для них соответствующие фабрики и явно укажите, какой шаблон используют репозитории. Для транзакций шаблон и менеджер должны разделять фабрику (Q33).

## Q35. (!) Как оптимизировать запросы в `MongoDB`?

Сначала найдите запрос, который создаёт нагрузку, и воспроизведите его с характерными параметрами. Сравните выбранный план и фактические объёмы работы:

```javascript
db.orders.find({ status: "ACTIVE" })
    .sort({ createdAt: -1, _id: -1 })
    .limit(20)
    .explain("executionStats")
```

Смотрите `nReturned`, `totalKeysExamined`, `totalDocsExamined`, отдельную сортировку и участие шардов. `IXSCAN` сам по себе не означает хороший план. `explain` не использует кэш планов, поэтому сопоставляйте результат с метриками обычных запросов.

- Подбирайте составной индекс по фильтру и порядку (Q13). Проекция уменьшает передачу данных и при подходящем индексе может избежать FETCH (Q14).
- Для глубокой пагинации используйте условие после последнего ключа. Например, при сортировке по `createdAt` и `_id` сохраняйте оба значения, чтобы страницы имели однозначную границу и при одинаковых датах.
- В pipeline уменьшайте входной набор подходящим фильтром. Spill позволяет отдельным этапам продолжать работу при превышении лимита памяти, но добавляет I/O (Q7, Q17).
- Для боевой диагностики используйте логи медленных операций и метрики. Если включаете profiler, учитывайте его накладные расходы и хранение текста запросов.

## Q36. Что такое `Change Streams`?

Change streams читают изменения коллекции, базы или развёртывания на replica set и в шардированном кластере. Они опираются на oplog и сообщают об изменениях после подтверждения большинством. Через `mongos` один поток сохраняет общий порядок между шардами. Это может добавить задержку при объединении событий.

Для update событие обычно несёт описание изменения. Опция `fullDocument: "updateLookup"` может вернуть текущую версию документа, видимую после записи большинством. Между обновлением и lookup документ мог измениться повторно, поэтому это не обязательно его состояние сразу после исходного события.

Возобновляйте поток с сохранённого resume token через `resumeAfter` при том же pipeline и тех же опциях. Токен сохраняйте после того, как потребитель надёжно применил событие. Если процесс упадёт между применением и сохранением токена, событие может прийти повторно. Если нужная позиция больше не доступна в oplog, потребуется восстановить исходное состояние потребителя и открыть поток с доступной точки.

Пример применения — поддержание поисковой проекции в [Elasticsearch](elasticsearch-interview.md). Запись в индекс должна выдерживать повторную обработку события.

## Q37. Как мониторить производительность `MongoDB`?

Сопоставьте задержку приложения с метриками конкретного `mongod` или `mongos`. В шардированном кластере проверяйте отдельные шарды: среднее по кластеру может скрывать перегрузку одного узла.

| Сигнал | Что проверить |
|--------|---------------|
| Пропускная способность | `opcounters` — накопительные счётчики. Скорость считают по разности за интервал. |
| Соединения и очередь | `connections.current` показывает входящие соединения, включая простаивающие. Ожидание выдачи соединения смотрите отдельно в пуле драйвера. |
| Кэш и диск | Сопоставьте eviction WiredTiger, грязные страницы, задержку I/O и ожидания операций. Eviction сам по себе является нормальной работой кэша. |
| Репликация | Сравните позиции и отставание участников с допустимой давностью чтения и окном oplog. |
| Медленные запросы | Найдите форму запроса в логах или profiler и проверьте план (Q35). |

`serverStatus` даёт снимок счётчиков узла, `mongostat` помогает наблюдать изменения, `mongotop` показывает время чтения и записи по коллекциям. Database profiler записывает данные на `mongod` в `system.profile`. У `mongos` такого profiler нет. При включении учитывайте нагрузку и доступ к содержимому операций.

## Q38. Как выполнять миграции данных?

Изменения формата документов лучше выпускать поэтапно. Например, при добавлении обязательного `status`:

1. Выпустите код, который читает старые документы без `status` и записывает новые со статусом.
2. Запустите версионированный backfill небольшими пакетами. Обновляйте только записи, у которых поле ещё отсутствует. Сохраните прогресс и повторяйте прерванный пакет безопасно.
3. Сверьте число документов без поля и корректность присвоенных статусов. Когда все активные писатели поддерживают новое поле, включите нужную валидацию и уберите временную совместимость.

```javascript
db.users.updateMany(
    { _id: { $in: batchIds }, status: { $exists: false } },
    { $set: { status: "ACTIVE" } }
)
```

Здесь `batchIds` — текущий пакет идентификаторов, а `ACTIVE` подходит только если это корректный статус для исторических данных. Условие на отсутствие поля защищает статус, уже выставленный приложением. `updateMany` атомарен для каждого документа отдельно, поэтому после сбоя возможен частичный прогресс.

Для отката формата используйте совместимый код или адресную обратную миграцию, если можно точно определить изменённые записи. Массовый `$unset` удалит и значения, которые создало приложение. Восстановление на момент времени полезно для аварийного восстановления, но может отбросить более поздние записи.

## Q39. Как обеспечить безопасность `MongoDB`?

Защитите MongoDB на трёх уровнях: доступ к сети, аутентификация клиента и минимальные привилегии.

- **Сеть и TLS.** Разрешайте подключения только доверенным приложениям и административным точкам. Используйте приватную сеть или списки доступа и проверку сертификата сервера. `bindIp` управляет интерфейсами прослушивания.
- **Аутентификация.** Включите контроль доступа. Выберите поддерживаемый механизм, например SCRAM-SHA-256 или X.509, и задайте ротацию учётных данных.
- **Авторизация.** Разделите сервисные, миграционные и административные учётные записи. Сервису, который только читает справочник, достаточно права чтения этой коллекции. Учитывайте, что встроенная `readWrite` выдаёт права шире одного сценария записи.
- **Аудит и обновления.** Проверяйте версии сервера и драйвера, права и изменения конфигурации. Возможности встроенного аудита зависят от редакции и развёртывания.

Подробнее — [безопасность приложений](../security/application-security-interview.md).

## Q40. Когда `MongoDB` -- плохой выбор?

MongoDB может оказаться неудобной, если частые операции пересекают границы документов, а модель приходится подстраивать под множество меняющихся запросов.

- **Связи и ограничения.** Если нужно регулярно соединять много сущностей и проверять ссылочную целостность при записи, сравните с реляционной схемой и внешними ключами.
- **Запись в несколько документов.** Транзакции доступны. Если почти каждая запись охватывает несколько коллекций или шардов, измерьте цену координации на целевой топологии.
- **Поиск и аналитика.** Для больших сканирований, сложного ранжирования или отдельных требований к свежести оцените специализированный движок либо проекцию (Database Architecture Q28/Q36).
- **Растущие агрегаты.** Если историю нельзя ограничить, один вложенный массив ухудшает модель. Проверьте, сохраняется ли преимущество документного доступа при выделении истории в отдельную коллекцию.

На собеседовании приведите конкретный запрос, требуемый инвариант и измерение, которое определило выбор.

## Q41. (!) Как работает `$lookup` с вложенным `pipeline` и `$unwind`?

Вложенный pipeline в `$lookup` позволяет фильтровать совпадения во второй коллекции. Ниже условие использует `let`, доступный для этого синтаксиса с MongoDB 3.6:

```javascript
db.orders.aggregate([
    { $lookup: {
        from: "products",
        let: { productId: "$product_id", minPrice: "$min_price" },
        pipeline: [
            { $match: { $expr: { $and: [
                { $eq: ["$_id", "$$productId"] },
                { $gte: ["$price", "$$minPrice"] }
            ] } } },
            { $project: { name: 1, price: 1 } }
        ],
        as: "product_info"
    } },
    { $unwind: { path: "$product_info", preserveNullAndEmptyArrays: true } }
])
```

`$lookup` оставляет исходный заказ и помещает совпадения в массив. `$unwind` делает по записи на совпадение. Здесь заказ без совпадения сохранится. Обычный `$unwind` без опции его отбросит.

Внутри `$expr` сравнение поля с константой может использовать индекс второй коллекции. Для сравнения с `let` значение должно разрешаться в константу для данного поиска. Сравнение двух полей и multikey-индекс в таком сравнении не дают того же индексного пути. Учитывайте размер входного набора и проверяйте план.

## Q42. (!) Что такое `Change Streams` и как использовать в `Spring`?

Spring Data MongoDB предоставляет поток `ChangeStreamEvent` через `ReactiveMongoTemplate`. Ниже метод строит поток вставок. Подпиской управляет вызывающий компонент, который также обрабатывает ошибки, завершение и повторное подключение.

```java
Flux<ChangeStreamEvent<Order>> watchInserts(ReactiveMongoTemplate template) {
    return template.changeStream(Order.class)
        .watchCollection("orders")
        .filter(Aggregation.newAggregation(
            Aggregation.match(Criteria.where("operationType").is("insert"))))
        .listen();
}
```

Из события можно получить тело и resume token. После успешной записи в целевое хранилище сохраните токен, а при возобновлении используйте те же фильтры и опции. Если запись и сохранение токена выполняются раздельно, обработчик должен выдерживать повтор события (Q36).

При использовании синхронного Java Driver чтение курсора блокирует поток. Закрывайте курсор при остановке обработчика. Если нужная позиция исчезла из oplog, одного повторного подключения недостаточно: требуется восстановить состояние проекции.

## Q43. (!) Как работают транзакции на нескольких документах и коллекциях?

В Java Driver передайте один `ClientSession` каждой операции, которая должна войти в транзакцию. Например, заказ и резерв остатка должны либо зафиксироваться вместе, либо быть отменены:

```java
TransactionOptions options = TransactionOptions.builder()
    .readPreference(ReadPreference.primary())
    .readConcern(ReadConcern.SNAPSHOT)
    .writeConcern(WriteConcern.MAJORITY)
    .build();

try (ClientSession session = mongoClient.startSession()) {
    session.withTransaction(() -> {
        UpdateResult reserved = inventoryCollection.updateOne(session,
            and(eq("_id", productId), gte("quantity", quantity)),
            inc("quantity", -quantity));
        if (reserved.getMatchedCount() != 1) {
            throw new IllegalStateException("Insufficient stock");
        }
        ordersCollection.insertOne(session, newOrder);
        return null;
    }, options);
}
```

Пример предполагает положительное `quantity` и заранее подготовленный ID заказа. Без проверки числа совпадений заказ может сохраниться без резерва. Callback может выполняться повторно. Отправку внешних событий включайте в согласованный протокол доставки (например, сохраняйте outbox в той же транзакции), а ошибки фиксации передавайте вызывающему коду. При неопределённом исходе проверяйте состояние по стабильному идентификатору заказа.

Для Spring Data используйте менеджер и общую фабрику из Q33. Ограничения oplog, времени работы и DDL разобраны в Q27. Издержки зависят от размера операции и числа затронутых шардов.

## Q44. Что такое `Time Series Collections` в `MongoDB`?

`Time Series Collections` — специальный тип коллекции в MongoDB 5.0+, оптимизированный для хранения временных рядов (метрики, IoT-данные, логи с временными метками).

**Создание:**

```javascript
db.createCollection("sensor_readings", {
  timeseries: {
    timeField: "timestamp",     // обязательное поле с временной меткой
    metaField: "metadata",      // поле для группировки (sensor_id, region)
    granularity: "seconds"      // seconds | minutes | hours
  },
  expireAfterSeconds: 2592000   // Хранить измерения примерно 30 дней
})
```

**Запись данных:**

```javascript
db.sensor_readings.insertMany([
  {
    timestamp: new Date("2026-04-13T10:00:00Z"),
    metadata: { sensor_id: "sensor_01", region: "Moscow" },
    temperature: 22.5,
    humidity: 65
  },
  {
    timestamp: new Date("2026-04-13T10:01:00Z"),
    metadata: { sensor_id: "sensor_01", region: "Moscow" },
    temperature: 22.7,
    humidity: 64
  }
])
```

**Агрегация по времени:**

```javascript
db.sensor_readings.aggregate([
  {
    $match: {
      "metadata.sensor_id": "sensor_01",
      timestamp: { $gte: ISODate("2026-04-13T00:00:00Z") }
    }
  },
  {
    $group: {
      _id: { $dateTrunc: { date: "$timestamp", unit: "hour" } },
      avgTemp: { $avg: "$temperature" },
      maxTemp: { $max: "$temperature" }
    }
  },
  { $sort: { "_id": 1 } }
])
```

MongoDB группирует близкие по времени измерения с одинаковым `metaField` в бакеты. Это помогает сжимать повторяющиеся данные и исключать нерелевантные бакеты при чтении диапазона. Выбирайте стабильные метаданные серии и гранулярность по частоте измерений. Эффект проверяйте на своём наборе данных.

В MongoDB 8.0 для документа time series действует отдельный предел 4 MB. Обновления ограничены: фильтровать и менять можно только `metaField`, обновление должно допускать несколько документов и не может быть upsert. Удаления поддерживаются, но имеют ограничения в зависимости от версии и топологии. TTL удаляет бакет после истечения срока всех его измерений, поэтому отдельное измерение может оставаться дольше номинального срока.

## Q45. Как выбрать стратегию шардирования: зональное vs хэш-шардирование?

Диапазонное и хешированное шардирование определяют координаты ключа. Зоны задают, на каких шардах балансировщик может размещать определённые диапазоны. Например, можно выделить зону для региона и распределять заказы внутри неё по хешу ID.

Пример для уже шардированной коллекции `mydb.orders` с ключом `{ regionCode: 1, orderId: "hashed" }` и двумя существующими шардами. В этой схеме целочисленные коды 1 и 2 обозначают EU и US соответственно. Границы включают все поля ключа. Нижняя граница включена, верхняя исключена:

```javascript
sh.addShardToZone("shard0001", "EU")
sh.addShardToZone("shard0002", "US")

sh.updateZoneKeyRange("mydb.orders",
    { regionCode: 1, orderId: MinKey },
    { regionCode: 2, orderId: MinKey },
    "EU"
)
sh.updateZoneKeyRange("mydb.orders",
    { regionCode: 2, orderId: MinKey },
    { regionCode: 3, orderId: MinKey },
    "US"
)
```

Один шард на зону ограничивает доступную ёмкость региона. Хеширование распределяет разные значения по доступным диапазонам, но одно горячее значение сохраняет один хеш. После изменения зон проверьте фактическое размещение: переносы выполняются балансировщиком. Диапазоны, которым зона не назначена, могут размещаться вне этих зон.

## Q46. Что такое `Atlas Search` и как он отличается от встроенного `text`-индекса?

Atlas Search использует отдельный поисковый индекс на базе Lucene. На нём доступны поиск с опечатками, автодополнение, анализаторы, ранжирование и фасеты. Встроенный `$text` использует текстовый индекс MongoDB (Q15). При выборе учитывайте и свежесть: изменения коллекции могут появляться в поисковом индексе с задержкой.

Пример определения Search Index в Atlas. Назовите индекс `products_search`:

```json
{
  "mappings": {
    "dynamic": false,
    "fields": {
      "name": { "type": "string", "analyzer": "lucene.russian" },
      "category": { "type": "token" }
    }
  }
}
```

Для фасетов отдельно запросите метаданные поиска. `$searchMeta` должен быть первым этапом pipeline:

```javascript
db.products.aggregate([
    { $searchMeta: {
        index: "products_search",
        facet: {
            operator: { text: { query: "детское кресло", path: "name" } },
            facets: { categories: { type: "string", path: "category" } }
        }
    } }
])
```

Для списка совпадений используйте отдельный pipeline с `$search` и соответствующим критерием. Если поиск обслуживает Elasticsearch, отдельно настройте доставку изменений и восстановление поисковой проекции (Q36).
