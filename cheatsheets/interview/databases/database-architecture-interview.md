## Q1. (!) Что такое нормализация?

Нормализация строит схему на основе зависимостей между атрибутами. Она уменьшает дублирование фактов и устраняет аномалии вставки, изменения и удаления. Например, если город отдела хранится в строке каждого сотрудника, при переезде отдела придётся обновить несколько строк, а удаление последнего сотрудника может уничтожить сведения об отделе.

- **1NF** предполагает одно значение домена в ячейке вместо повторяющейся группы.
- **2NF** исключает зависимость неключевого атрибута от части любого кандидатного ключа.
- **3NF** требует для каждой нетривиальной функциональной зависимости `X → A`, чтобы `X` был суперключом или `A` входил хотя бы в один кандидатный ключ.
- **BCNF** требует, чтобы детерминант каждой нетривиальной функциональной зависимости был суперключом.

Пример: в отношении `employees(id, name, dept_id, dept_city)` с ключом `id` город зависит от `dept_id`. Вынесите `departments(id, city)`, а в `employees` оставьте внешний ключ `dept_id`. Простой ключ сотрудника здесь не создаёт частичной зависимости. При разложении проверяйте соединение без потерь и возможность контролировать зависимости.

Денормализация может ускорить конкретное чтение. Например, сохранённая сумма заказа позволяет не пересчитывать позиции при каждом запросе, но при изменении позиций сумму нужно обновлять согласованно. Подробнее о формах — в [вопросах по SQL](sql-interview.md).

## Q2. (!) Что такое BASE?

BASE описывает подход, в котором система допускает временное расхождение состояния ради доступности в выбранных сценариях.

- **Basically Available.** Архитектура стремится обслуживать запросы при части отказов. Точные гарантии зависят от операции и отказа.
- **Soft State.** Наблюдаемое состояние может меняться без новых клиентских записей, например при применении задержавшихся обновлений.
- **Eventually Consistent.** Если новых изменений нет и реплики смогли обменяться обновлениями и разрешить конфликты, их состояние сходится. Фиксированный срок сходимости из этого свойства не следует.

Например, новый комментарий записан, а одна из реплик ещё отдаёт старую версию страницы. После доставки изменений реплики сходятся. Подробнее о границах при сетевом разделении — в [вопросах по CAP](../architecture/cap-theorem-interview.md).

## Q3. (!) Что такое ACID?

ACID описывает четыре свойства транзакции:

- **Atomicity.** Изменения фиксируются вместе или отменяются вместе.
- **Consistency.** Корректная транзакция переводит данные в состояние, которое удовлетворяет инвариантам. Ограничения БД защищают заданные правила, а остальные правила должна соблюдать логика операции.
- **Isolation.** Уровень изоляции определяет видимость изменений и допустимые аномалии при конкуренции (Q5).
- **Durability.** Зафиксированный результат переживает сбой в пределах гарантий конфигурации. В PostgreSQL асинхронный commit может вернуть успех до записи WAL на устойчивый носитель. При сбое недавно подтверждённые изменения могут потеряться.

При переводе денег списание и зачисление выполняются в одной транзакции. Сама операция проверяет оба счёта и результат обоих обновлений. Если счёт назначения отсутствует, `UPDATE` может затронуть ноль строк без ошибки, и приложение должно отменить перевод.

## Q4. (!) В чём разница ACID от BASE?

ACID задаёт свойства транзакции, а BASE описывает подход к доступности и сходимости распределённого состояния. Эти свойства могут сочетаться в одной системе. Например, заказ и событие в outbox фиксируются одной локальной транзакцией, а витрина заказов обновляется по событию с задержкой.

При проектировании отдельно определите, какие изменения должны фиксироваться атомарно, какие чтения допускают устаревшее значение и что видит клиент, пока обновление распространяется. Согласованность в ACID относится к инвариантам данных. В CAP согласованность означает линеаризуемость, то есть согласованное с реальным временем наблюдение операций над распределёнными данными.

Подробнее — [паттерны согласованности](../architecture/consistency-patterns-interview.md).

## Q5. (!) Какие есть типы изоляции транзакций?

Уровень изоляции определяет, какие результаты конкурентного выполнения допустимы. Стандарт SQL задаёт минимальные гарантии, а конкретная БД может обеспечить больше.

| Уровень | Dirty read | Non-repeatable read | Phantom read | Аномалия сериализации |
|---------|------------|---------------------|--------------|-----------------------|
| `READ UNCOMMITTED` | Возможен | Возможен | Возможен | Возможна |
| `READ COMMITTED` | Исключён | Возможен | Возможен | Возможна |
| `REPEATABLE READ` | Исключён | Исключён | Возможен | Возможна |
| `SERIALIZABLE` | Исключён | Исключён | Исключён | Исключена |

В PostgreSQL `READ UNCOMMITTED` работает как `READ COMMITTED`, уровень по умолчанию. `REPEATABLE READ` использует snapshot isolation и исключает фантомы, но допускает аномалии сериализации. `SERIALIZABLE` использует SSI: проверяет зависимости между транзакциями и может отменить одну из них, чтобы зафиксированные результаты были эквивалентны последовательному выполнению.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;
COMMIT;
```

Обычный SELECT не блокирует конкурентный UPDATE этой строки. Если текущая транзакция затем попытается изменить строку, изменённую конкурентом после создания снимка, PostgreSQL может вернуть ошибку сериализации. При SQLSTATE `40001` повторяют всю транзакцию, включая чтения и расчёты.

## Q6. (!) Какие проблемы при одновременном доступе несколькими транзакциями?

- **Dirty read.** Чтение изменений, которые другая транзакция ещё не зафиксировала.
- **Non-repeatable read.** Повторное чтение строки даёт другой результат после чужого commit.
- **Phantom read.** Повторный запрос по тому же предикату возвращает другой набор подходящих строк после чужого commit.
- **Lost update.** Два клиента читают остаток 10, вычисляют новое значение отдельно и записывают 9. Вторая запись затирает эффект первой.
- **Write skew.** Две транзакции читают общее условие и изменяют разные строки, вместе нарушая инвариант. Например, два дежурных одновременно снимают себя с дежурства, каждый видит второго на месте. В PostgreSQL такое возможно при `REPEATABLE READ`.

Для простого списания в PostgreSQL можно вычислять изменение в одном операторе и проверять число обновлённых строк:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

При чтении с последующим расчётом можно блокировать нужную строку через `SELECT … FOR UPDATE` или обновлять её с условием по версии. Ноль обновлённых строк означает, что условие не выполнилось. Причиной может быть новая версия или отсутствие записи. Для инварианта между несколькими строками нужны блокировки, охватывающие этот инвариант, либо `SERIALIZABLE` с повтором транзакции.

## Q7. В чем разница между блокировкой строки и таблицы?

Гранулярность описывает, на что берётся блокировка. Режим определяет, какие операции с ней конфликтуют. В PostgreSQL одна команда может брать блокировки обоих уровней.

- Обычный `SELECT` берёт табличную `ACCESS SHARE`. Она конфликтует только с `ACCESS EXCLUSIVE`.
- `UPDATE` берёт табличную `ROW EXCLUSIVE` и блокировки изменяемых строк. Слово ROW в названии `ROW EXCLUSIVE` не меняет уровень этой блокировки.
- `SELECT … FOR UPDATE` берёт табличную `ROW SHARE` и блокирует выбранные строки для конкурирующих изменений и конфликтующих блокировок строк. Обычный SELECT может прочитать видимую ему версию.
- `LOCK TABLE … IN ACCESS EXCLUSIVE MODE` конфликтует даже с обычным SELECT. Такой же режим нужен, например, для `TRUNCATE`.

Блокировки обычно удерживаются до конца транзакции. Взаимная блокировка возможна на обоих уровнях, если транзакции захватывают конфликтующие ресурсы в разном порядке.

## Q8. (!) Что такое MVCC и как он работает в PostgreSQL?

MVCC хранит несколько версий строки и выбирает видимую версию по снимку. Обычное чтение может видеть старую версию, пока конкурентная транзакция пишет новую.

В PostgreSQL `UPDATE` создаёт новую версию. Поле `xmin` указывает на транзакцию, создавшую версию. Поле `xmax` участвует в учёте удаления или обновления и может отражать блокировку. По ненулевому `xmax` нельзя самостоятельно заключить, что версия удалена. Видимость зависит от снимка, статуса транзакций и собственных изменений читающей транзакции.

В `READ COMMITTED` обычный SELECT получает снимок на начало команды. В `REPEATABLE READ` снимок берётся на первой команде, которая не управляет транзакцией. Например, если первый SELECT видит сумму 500, а другая транзакция затем фиксирует 700, следующий SELECT в той же `REPEATABLE READ` продолжает видеть 500. В `READ COMMITTED` новый SELECT увидит 700, если больше ничего не изменилось.

MVCC не устраняет конфликт между писателями и ожидание табличных блокировок. Старые версии остаются, пока могут понадобиться какому-либо снимку. Когда версии больше не нужны, `VACUUM` может освободить место для повторного использования. Долгая транзакция со старым снимком задерживает очистку. Подробнее — [Q10](#q10-как-работает-vacuum-в-postgresql).

## Q9. (!) Что такое WAL (Write-Ahead Log)?

WAL — журнал упреждающей записи. PostgreSQL может изменить страницу в памяти сразу. Перед сохранением изменённой страницы в файл данных соответствующие записи WAL должны быть сброшены на устойчивый носитель. При синхронном commit достаточно сохранить WAL до записи о фиксации, даже если страницы данных ещё в памяти. При асинхронном commit часть недавно подтверждённых транзакций может потеряться при сбое (Q3).

- **Crash recovery.** PostgreSQL воспроизводит WAL с позиции redo контрольной точки (Q11).
- **Физическая репликация.** Реплика получает поток WAL и воспроизводит изменения. Получение, сброс на диск и применение — разные этапы.
- **PITR.** Для восстановления на выбранный момент нужен подходящий базовый бэкап и непрерывная цепочка WAL до цели.

Чтобы оценить объём WAL за пять минут, снимите `pg_current_wal_insert_lsn()` в начале и конце интервала на одном primary и вычислите разницу через `pg_wal_lsn_diff(end_lsn, start_lsn)`. Разность с `0/0` не измеряет заданный интервал и не показывает размер файлов в `pg_wal`.

## Q10. (!) Как работает VACUUM в PostgreSQL?

Обычный `VACUUM` очищает версии строк, которые больше не нужны снимкам, и делает место доступным для повторного использования. Он также обновляет карту видимости и замораживает старые идентификаторы транзакций для защиты от wraparound. Статистику распределения значений для планировщика собирает `ANALYZE`. Команда `VACUUM ANALYZE` совмещает обе операции.

- **Обычный VACUUM** совместим с чтением и обычным DML. Он конфликтует с некоторыми DDL, а для усечения свободных страниц в конце файла может кратко брать `ACCESS EXCLUSIVE`. Обычно свободное место остаётся внутри файла.
- **VACUUM FULL** переписывает таблицу, возвращает место файловой системе и удерживает `ACCESS EXCLUSIVE`.
- **Autovacuum** запускает обычный VACUUM и ANALYZE по своим условиям. Старые снимки могут удерживать версии даже при работающем autovacuum.

```sql
SELECT relname, n_dead_tup, n_live_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```

`n_dead_tup` — оценка числа мёртвых версий. Для диагноза учитывайте возраст удерживаемых снимков и размер таблицы и индексов.

## Q11. Что такое checkpoint в PostgreSQL?

Контрольная точка создаёт позицию redo, с которой можно начать восстановление. PostgreSQL постепенно записывает и синхронизирует страницы, нужные для этой точки. Запись продолжается параллельно, поэтому к завершению могут существовать новые грязные страницы.

Сервер может переработать или удалить WAL, когда он больше не нужен для восстановления и других целей, например архивации или слотов репликации. `max_wal_size` — мягкий ориентир для запуска checkpoint, а не жёсткий предел размера каталога. Плановые контрольные точки также ограничивает `checkpoint_timeout`. Параметр `checkpoint_completion_target` распределяет запись по интервалу. Слишком частые точки увеличивают нагрузку на диск и при включённом `full_page_writes` могут увеличивать объём WAL.

```sql
-- PostgreSQL 17 и новее
SELECT * FROM pg_stat_checkpointer;
```

До PostgreSQL 17 счётчики checkpoint входили в `pg_stat_bgwriter`.

## Q12. (!) Что такое индекс и какие типы индексов существуют?

Индекс хранит вспомогательную структуру доступа к строкам. Для B-tree логарифмической является навигация к началу диапазона. Полная стоимость зависит от числа совпадений, обращений к таблице и ввода-вывода. Планировщик может выбрать последовательное сканирование даже при наличии подходящего индекса. Индексы занимают место и добавляют работу при изменении данных. Например, HOT-обновление при выполнении его условий обходится без новых записей в обычных индексах.

Типы индексов в `PostgreSQL`:

| Тип | Структура | Операции | Когда использовать |
|-----|-----------|----------|-------------------|
| **B-tree** | Сбалансированное дерево | `=`, `<`, `>`, `BETWEEN`, `ORDER BY` | Тип по умолчанию |
| **Hash** | Хеш-таблица | Только `=` | Точечный поиск (редко лучше B-tree) |
| **GiST** | Обобщённое дерево поиска | Пространственные, полнотекстовые | Геоданные (`PostGIS`), `tsvector` |
| **GIN** | Инвертированный индекс | `@>`, `&&`, полнотекст | Массивы, `JSONB`, `tsvector` |
| **BRIN** | Блочный диапазонный | `<`, `>`, `BETWEEN` | Огромные таблицы с естественным порядком |
| **SP-GiST** | Пространственное разбиение | Диапазоны, точки | Неравномерно распределённые данные |

```sql
-- B-tree (по умолчанию)
CREATE INDEX idx_orders_customer ON orders (customer_id);

-- Составной индекс (порядок столбцов важен!)
CREATE INDEX idx_orders_status_date ON orders (status, created_at DESC);

-- Частичный индекс (только активные заказы)
CREATE INDEX idx_orders_active ON orders (customer_id)
WHERE status = 'ACTIVE';

-- GIN для JSONB
CREATE INDEX idx_products_attrs ON products USING GIN (attributes);

-- BRIN для временных рядов (огромная таблица, данные добавляются по порядку)
CREATE INDEX idx_logs_created ON logs USING BRIN (created_at);

-- Покрывающий индекс (INCLUDE добавляет поля результата, пропуск heap зависит от карты видимости)
CREATE INDEX idx_orders_covering ON orders (customer_id)
INCLUDE (status, total_amount);
```

Подробнее про оптимизацию запросов с индексами — [вопросы по SQL](sql-interview.md).

## Q13. Что будет если два одинаковых индекса в БД?

Полный дубль занимает место и добавляет работу при обслуживании индексов. Это не означает удвоения стоимости всей записи.

Совпадения списка столбцов недостаточно. Сравните метод доступа, выражения, порядок и параметры сортировки, классы операторов, collation, INCLUDE, предикат, уникальность и обработку NULL. Для кандидатов посмотрите определения и проверьте зависимости, включая ограничения:

```sql
SELECT indexrelid::regclass AS index_name,
       pg_get_indexdef(indexrelid) AS definition,
       indisvalid, indisprimary, indisunique, indisreplident
FROM pg_index
WHERE indrelid = 'public.orders'::regclass;
```

`idx_scan = 0` описывает наблюдавшееся использование в пределах статистики. Индекс может обеспечивать ограничение или быть нужен редким запросам. Для самостоятельного дубликата в PostgreSQL можно рассмотреть `DROP INDEX CONCURRENTLY`. Он выполняется вне транзакционного блока и не подходит для индекса секционированной таблицы или индекса, обеспечивающего PK/UNIQUE.

## Q14. (!) Что такое кластерный и некластерные индексы?

В InnoDB строки хранятся в листьях кластерного индекса. Обычно это первичный ключ. Если его нет, движок выбирает первый подходящий уникальный индекс со всеми столбцами NOT NULL, а при его отсутствии создаёт скрытый кластерный индекс. Вторичный индекс хранит свой ключ и идентификатор строки на основе кластерного ключа. Если нужных полей нет во вторичном индексе, движок обращается к кластерному.

В PostgreSQL строки обычной heap-таблицы хранятся отдельно от индексов. `CLUSTER orders USING idx_orders_created_at` переписывает таблицу в порядке индекса. Последующие записи этот порядок не поддерживают. Команда берёт `ACCESS EXCLUSIVE`. В PostgreSQL 19 она эквивалентна `REPACK` с `USING INDEX`.

Физическая локальность может снизить стоимость чтения диапазона. Порядок строк в результате SQL задаёт `ORDER BY`.

## Q15. (!) Как БД определяет какой индекс использовать?

PostgreSQL сравнивает стоимость доступных планов. Среди них могут быть последовательное сканирование, Index Scan, Bitmap Heap Scan и Index Only Scan. Вариант с индексом должен поддерживать операции запроса, например условие отбора или нужный порядок.

На выбор влияют оценки числа строк и страниц, корреляция порядка ключа с порядком строк в таблице, стоимость доступа к страницам, сортировка и возможность остановиться после `LIMIT`. При большой доле совпадений последовательный проход может оказаться дешевле обращений к таблице через индекс.

```sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;
```

Для диагностики можно сравнить альтернативный план с `SET LOCAL enable_seqscan = off` внутри транзакции. Это делает последовательное сканирование менее предпочтительным, но не запрещает его полностью.

## Q16. (!) Что такое EXPLAIN ANALYZE и как читать план запроса?

Обычный `EXPLAIN` показывает выбранный план и оценки. `EXPLAIN ANALYZE` выполняет запрос и добавляет фактические измерения. Для изменяющих запросов транзакция с `ROLLBACK` отменяет транзакционные изменения, но вызов `nextval()` и внешние побочные эффекты могут сохраниться.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total_amount
FROM orders
WHERE status = 'SHIPPED'
ORDER BY created_at DESC
LIMIT 20;
```

- **`cost=start..total`** — оценки в условных единицах. Полная стоимость узла предполагает выполнение до конца.
- **`rows` и `actual rows`** — оценка и факт числа строк на выполнение узла. При нескольких `loops` фактические строки и время в текстовом плане усреднены по выполнениям. Под `LIMIT` родитель может остановить дочерний узел раньше.
- **`shared hit/read`** — обращения к блокам в shared buffers и чтения блоков, которых там не было. `read` может обслужить кэш ОС. Показатели родительского узла включают дочерние, поэтому их не складывают по всему дереву.
- **Расхождение оценки и факта** требует проверки причин. Помимо устаревшей статистики возможны корреляция предикатов или досрочная остановка. Сортировка на диске показывает сброс на временное хранилище, но менять `work_mem` стоит с учётом объёма данных и числа параллельных операций.

## Q17. (!) Какое значение имеет статистика в работе с индексами?

Планировщик оценивает число строк после фильтров и соединений. Ошибка оценки может изменить выбор сканирования, порядок соединений и их алгоритмы.

- `pg_class.reltuples` и `relpages` содержат приблизительные размеры отношений.
- `pg_stats` показывает частые значения, их частоты, границы гистограмм, долю NULL и корреляцию логического порядка значений с физическим порядком строк. Это помогает оценить селективность и стоимость чтения через индекс.
- Одноколоночная статистика может дать плохую оценку, если условия связаны. Например, точная пара «страна и город» встречается чаще, чем предсказывает произведение независимых вероятностей.

```sql
CREATE STATISTICS orders_country_city_stats (mcv)
ON country, city FROM orders;

ANALYZE orders;
```

`CREATE STATISTICS` задаёт, какие данные собрать при `ANALYZE`. Многоколоночный список MCV помогает оценивать совместные фильтры по одной таблице. Сам объект статистики не создаёт индекс и не ускоряет поиск строк напрямую. После массового изменения данных проверьте оценки через `EXPLAIN ANALYZE` и при необходимости запустите `ANALYZE` раньше автоматического сбора.

## Q18. (!) Что такое проблема фрагментации индексов?

В PostgreSQL B-tree может занимать больше страниц, чем нужно для текущих записей. Обновления и удаления создают устаревшие записи, а разбиение страниц может оставлять свободное место. Очистка позволяет повторно использовать место, но обычно не уменьшает файл индекса. Лишние страницы увеличивают размер индекса и могут повышать стоимость сканирования.

Для B-tree можно посмотреть плотность листьев и показатели фрагментации через установленное расширение `pgstattuple`:

```sql
SELECT index_size, leaf_pages, deleted_pages, avg_leaf_density, leaf_fragmentation
FROM pgstatindex('public.idx_orders_customer'::regclass);
```

`avg_leaf_density` описывает заполненность листьев, а `leaf_fragmentation` — их расположение. Оценивайте их вместе с размером, `fillfactor`, профилем записи и стоимостью реальных запросов. Универсального порога плотности для перестройки нет.

## Q19. (!) Как решить проблему фрагментации индексов в PostgreSQL?

Если индекс разросся и это заметно по размеру или планам запросов, `REINDEX` строит его заново. Обычная перестройка блокирует запись в родительскую таблицу и берёт эксклюзивную блокировку перестраиваемого индекса. Чтения, которым нужен этот индекс, тоже могут ждать.

```sql
-- PostgreSQL 12+, вне транзакционного блока.
REINDEX INDEX CONCURRENTLY public.idx_orders_customer;
```

`CONCURRENTLY` оставляет обычные чтения и записи доступными, но делает дополнительные проходы, ждёт подходящих границ транзакций и требует место для новой копии. При сбое может остаться невалидный индекс, который нужно учесть перед повтором. Есть ограничения, например для индексов ограничений исключения.

Обычный `VACUUM` может очистить устаревшие записи индекса и подготовить место для повторного использования. Если этого хватает для рабочей нагрузки, перестройка по расписанию не нужна. Если разрослась сама heap-таблица, её размер оценивают отдельно (Q10).

## Q20. (!) Подходы для повышения производительности запросов с индексами?

- **Составной B-tree.** Равенства по ведущим столбцам и ограничение по первому следующему столбцу обычно сужают сканируемый диапазон. Индекс `(a, b)` может использоваться и для `WHERE b = 5`. В PostgreSQL 18+ skip scan иногда позволяет пропускать части индекса, особенно если разных значений `a` мало. При большом числе значений отдельный индекс по `b` может оказаться выгоднее.
- **Покрывающий индекс.** `INCLUDE` позволяет хранить поля результата в индексе. Index Only Scan всё равно обращается к heap, если карта видимости не подтверждает видимость страницы.
- **Частичный индекс.** Планировщик должен вывести предикат индекса из условий запроса при построении плана. Например, частичный индекс по активным заказам может быть полезен, если активных заказов мало даже при небольшом числе значений статуса.
- **Сортировка.** B-tree может избежать отдельной сортировки, когда направление сканирования, ключи и порядок NULL соответствуют `ORDER BY`. При `LIMIT` это иногда позволяет остановить сканирование раньше.
- **Выражение.** Для поиска по `lower(email)` рассмотрите индекс на выражение `lower(email)`.

```sql
CREATE INDEX idx_orders_active_date ON orders (created_at DESC)
WHERE status = 'ACTIVE';

EXPLAIN SELECT id, created_at
FROM orders
WHERE status = 'ACTIVE'
ORDER BY created_at DESC
LIMIT 20;
```

Сверьте выбранный план и измерения до и после. Каждый дополнительный индекс занимает место и добавляет издержки записи.

## Q21. (!) Что такое партиционирование таблиц?

Секционирование делит одну логическую таблицу на физические секции. В PostgreSQL родительская таблица не хранит строки сама. При вставке PostgreSQL выбирает секцию по ключу. При чтении partition pruning исключает секции, границы которых несовместимы с условием запроса. Это возможно при планировании и в некоторых случаях при выполнении. Наличие индекса для pruning не требуется.

Поддерживаются `RANGE` (нижняя граница включена, верхняя исключена), `LIST` (явные значения) и `HASH` (остаток от деления хеша ключа).

```sql
CREATE TABLE events (
    event_id BIGINT NOT NULL,
    created_on DATE NOT NULL,
    PRIMARY KEY (created_on, event_id)
) PARTITION BY RANGE (created_on);

CREATE TABLE events_2026_q2 PARTITION OF events
FOR VALUES FROM ('2026-04-01') TO ('2026-07-01');

SELECT event_id FROM events
WHERE created_on >= DATE '2026-04-01'
  AND created_on < DATE '2026-07-01';
```

В PostgreSQL PK или UNIQUE на секционированной таблице должен включать все столбцы ключа секционирования, и ключ секционирования для такого ограничения не должен содержать выражений. В примере уникальна пара, поэтому одинаковый `event_id` с разными датами допускается.

При хранении истории `DETACH PARTITION` убирает секцию из логической таблицы, сохраняя её как отдельную таблицу. `DROP TABLE` удаляет секцию. Эти операции обходятся без построчного DELETE, но требуют подходящих блокировок. Выгода зависит от запросов и обслуживания. Слишком много секций увеличивает работу планировщика.

## Q22. (!) Что такое репликация БД и какие виды бывают?

Репликация поддерживает копии данных на нескольких узлах. Она может повысить отказоустойчивость, обслуживать чтения и размещать копии ближе к клиентам. Свойства зависят от того, кто принимает запись, что передаётся и какого подтверждения ждёт транзакция.

- **Топология.** В single-leader запись принимает один лидер. В multi-leader изменения могут принимать несколько лидеров. В leaderless-модели операции могут координировать разные узлы. Для вариантов с конкурентными записями важны правила конфликтов.
- **Содержимое потока.** Физическая репликация PostgreSQL воспроизводит WAL. Логическая передаёт изменения строк выбранных таблиц.
- **Подтверждение.** При асинхронной репликации commit не ждёт подтверждения реплики. При синхронной точка ожидания зависит от настройки. Например, в PostgreSQL при настроенной синхронной реплике `synchronous_commit = on` ждёт её устойчивой записи WAL, а `remote_apply` — применения изменений.

Асинхронная реплика может отставать. При аварийном переключении часть подтверждённых на primary изменений может отсутствовать на новой primary. Репликация также может перенести ошибочное удаление. Для восстановления нужен независимый бэкап. Подробнее — [репликация БД](database-replication-interview.md).

## Q23. (!) Что такое шардирование и как выбрать ключ шардирования?

Шардирование распределяет разные части набора данных по узлам. Репликация создаёт копии этих частей. Например, заказы клиента могут храниться на одном шарде, а внутри шарда иметь несколько реплик.

- **Хеш по модулю.** Подходит для стабильного числа шардов и равномерного распределения ключей. Изменение модуля меняет маршруты многих ключей.
- **Диапазоны.** Сохраняют локальность запросов по интервалам. Новый монотонный ключ может концентрировать запись в крайнем диапазоне.
- **Каталог.** Хранит соответствие ключа или диапазона владельцу. Перемещение требует согласованного обновления маршрутов.
- **Consistent hashing.** При изменении состава кластера обычно переносится часть ключей. Один горячий ключ всё равно может перегружать своего владельца.

Ключ выбирают по частым запросам, распределению данных и нагрузке на самые популярные значения. Равенство по полному ключу часто даёт один маршрут. Предикат по диапазону или части составного ключа может затронуть несколько шардов. Для запросов и транзакций между шардами оценивают сетевой обмен и требуемые гарантии отдельно. Подробнее — [шардирование БД](database-sharding-interview.md).

## Q24. (!) Что такое connection pooling и зачем он нужен?

Пул переиспользует соединения и ограничивает число одновременных обращений к БД. При исчерпании пула клиент ждёт или получает ошибку по таймауту. HikariCP выдаёт JDBC-соединения приложению. PgBouncer может дополнительно переиспользовать серверные соединения между клиентами.

| Режим PgBouncer | Когда серверное соединение возвращается в пул | Последствия |
|-----------------|-----------------------------------------------|-------------|
| **Session** | При отключении клиента | Состояние сессии доступно до отключения. |
| **Transaction** | По завершении транзакции | Следующая транзакция может попасть на другой backend. Произвольное состояние сессии между транзакциями не сохраняется. |
| **Statement** | После оператора | Многооператорные транзакции запрещены. |

С PgBouncer 1.21 именованные prepared statements на уровне протокола поддерживаются в transaction pooling при `max_prepared_statements > 0`. SQL-команды `PREPARE` и `DEALLOCATE` для отдельных именованных запросов PgBouncer таким способом не переносит между backend-соединениями.

При прямом подключении десять экземпляров приложения с `maximumPoolSize=20` могут открыть до 200 соединений. В PgBouncer `max_client_conn` ограничивает клиентов прокси, а `default_pool_size` задаёт размер серверного пула для пары «БД и пользователь». В бюджет соединений входят все пулы, экземпляры прокси, резервные и прямые подключения. Размер выбирают по этому бюджету, нагрузке и времени ожидания пула.

## Q25. (!) Чем SQL база данных отличается от NoSQL?

Реляционная БД моделирует данные отношениями и обычно предоставляет SQL, ограничения и соединения таблиц. NoSQL объединяет разные модели, например документы, ключи и значения, wide-column и графы. Они по-разному задают структуру, связи и способы доступа.

- **Данные и запросы.** Заказы и позиции можно хранить в связанных таблицах. Документная БД позволяет хранить позиции внутри заказа, если их обычно читают вместе и размер массива ограничен.
- **Валидация.** PostgreSQL проверяет ограничения таблицы. У документов могут различаться поля, а MongoDB позволяет задать правила проверки.
- **Транзакции.** Гарантии зависят от движка и настроек. MongoDB 8.0 поддерживает многодокументные ACID-транзакции, в том числе в шардированном кластере.
- **Масштабирование.** PostgreSQL можно распределить через Citus (Database Sharding Q27). Шардированная MongoDB может перегреть узел на неудачном ключе. В обоих случаях стоимость определяется раскладкой и профилем нагрузки.

При выборе перечислите основные запросы, инварианты и требования к задержке. Затем проверьте, какие операции выполняются локально и какие требуют связи между узлами.

## Q26. (!) Какие есть типы NoSQL баз данных?

Модели NoSQL удобно различать по тому, как приложение адресует данные и какие операции выполняет чаще всего.

| Модель | Пример | Запрос, под который она подходит |
|--------|--------|----------------------------------|
| **Key-value** | [Redis](redis-interview.md), [DynamoDB](dynamodb-interview.md) | Получить сессию по идентификатору. В DynamoDB составной первичный ключ также позволяет читать диапазон sort key в пределах одного значения partition key. |
| **Документная** | [MongoDB](mongodb-interview.md) | Найти товар по вложенному атрибуту и прочитать документ целиком. |
| **Wide-column** | [Cassandra](cassandra-interview.md) | Прочитать события устройства за период по ключу партиции и диапазону clustering key. |
| **Графовая** | Neo4j | Найти цепочки связей между аккаунтами. |
| **Поисковый движок** | [Elasticsearch](elasticsearch-interview.md) | Найти документы по словам и отсортировать по релевантности. |

Категории могут пересекаться. Например, DynamoDB хранит вложенные атрибуты, но выбор partition key остаётся важен для маршрутизации и стоимости чтения.

## Q27. Можно ли использовать SQL язык запросов с NoSQL?

Да. Возможности зависят от конкретного API. Знакомый синтаксис помогает выразить запрос, а его стоимость определяется моделью хранения и путём доступа.

| Система | Интерфейс | Что проверить |
|---------|-----------|---------------|
| **Cassandra 5.0** | CQL | `SELECT` читает одну таблицу. Возможности отбора и порядка связаны с первичным ключом и индексами. `GROUP BY` ограничен столбцами первичного ключа в их порядке. |
| **DynamoDB** | PartiQL | `SELECT` с равенством или `IN` по partition key может адресовать нужные значения. Без такого условия возможен полный scan. |
| **Elasticsearch** | SQL API | Поддерживает отбор и агрегации. Ограничения вложенных полей и отдельных выражений нужно сверять с документацией. |
| **MongoDB 8.0** | MQL и aggregation pipeline | Нативный интерфейс имеет собственный синтаксис. Этап `$lookup` позволяет соединять документы с другой коллекцией. |

Например, `SELECT` по статусу в DynamoDB без подходящего ключа таблицы или индекса может прочитать всю таблицу. Смена языка запроса сама по себе этот путь доступа не меняет.

## Q28. (!) Преимущества и недостатки SQL в сравнении с NoSQL?

Реляционная модель удобна, когда бизнес-правила заданы между сущностями и нужны разные способы соединять данные. Например, схема заказов может проверять внешний ключ на клиента и атомарно менять заказ и позиции. При распределении таблиц часть таких операций потребует согласованной раскладки или обмена между узлами.

Хранилище со специализированным доступом может лучше обслуживать конкретную операцию. Например, документ товара удобно читать целиком, а поисковый индекс позволяет ранжировать результаты полнотекстового поиска. Цену оценивайте по запросам, которые выходят за пределы основного пути доступа, и по способу поддержания инвариантов.

При сочетании PostgreSQL как источника заказов и Elasticsearch как поисковой проекции появляются задержка обновления, обработка повторов и процедура пересборки индекса. В требованиях стоит указать, какие экраны могут показать старое состояние и куда обращаться за подтверждённым статусом заказа.

## Q29. (!) Критерии выбора между SQL и NoSQL для проекта?

Начните с ключевых операций и инвариантов, затем сравните конкретные движки на характерной нагрузке.

1. **Запросы.** Выпишите частые чтения и записи, фильтры, сортировку и нужные связи. Например, проверка заказа по ID и полнотекстовый поиск по каталогу требуют разных путей доступа.
2. **Гарантии.** Укажите, какие изменения нужно фиксировать вместе, где нужна уникальность и где допустимо устаревшее чтение. Проверьте гарантии для выбранной конфигурации, включая переключение после сбоя.
3. **Рост.** Измерьте задержку и пропускную способность с реалистичными размерами записей, распределением ключей и индексами. Одинаковое число операций в секунду может давать разную нагрузку.
4. **Эксплуатация.** Сравните миграции, резервное копирование, восстановление и стоимость поддержки дополнительного хранилища.

Например, для заказов с позициями, внешними ключами и отчётами можно начать с PostgreSQL. Изменяемые атрибуты товара могут храниться в `jsonb` и индексироваться под нужные запросы. Если поисковые требования выходят за возможности выбранной схемы, оцените отдельную поисковую проекцию и допустимую задержку её обновления (Q28).

## Q30. (!) Что такое горизонтальное и вертикальное масштабирование БД?

**Scale up** увеличивает ресурсы одного узла. Он полезен, если ограничение связано с CPU, памятью или вводом-выводом и нагрузка использует добавленную ёмкость. Способ обновления и возможный простой зависят от платформы и конфигурации.

**Scale out** добавляет узлы и распределяет работу. Для PostgreSQL hot standby может обслуживать чтения. Это разгружает primary по чтению, но запись к нему по-прежнему идёт через один узел. Чтобы распределить запись и объём данных, можно разделить независимые наборы данных по шардам (Q23).

Пример: если память не вмещает рабочий набор, проверьте эффект добавления памяти. Если задержку создают независимые запросы на чтение, оцените вынос части чтений на реплики с учётом отставания. Если один узел упёрся в запись, сначала проверьте возможность разделить нагрузку по ключу, в том числе самый горячий диапазон. Координация, сетевой обмен и перекос нагрузки ограничивают выигрыш от дополнительных узлов.

Подробнее — [паттерны масштабирования](../architecture/scalability-patterns-interview.md).

## Q31. Какие виды индексов поддерживаются SQL и NoSQL?

Сравнивайте индекс по операции, которую он ускоряет, и по ограничениям конкретного движка. Например, поиск равенства, диапазон, полнотекстовый отбор и маршрутизация по ключу требуют разных структур.

| Система | Пример | Что проверить |
|---------|--------|---------------|
| **PostgreSQL** | B-tree для диапазонов, GIN для ряда операций с `jsonb` и полнотекстового поиска | Поддерживаемый оператор и его класс, селективность и стоимость обращения к heap. |
| **MySQL/InnoDB** | Кластерный и вторичные индексы, полнотекстовые и пространственные | Содержит ли вторичный индекс нужные поля или понадобится обращение к кластерному (Q14). |
| **MongoDB** | Составной, hashed, текстовый, пространственный | Соответствие индекса фильтру и сортировке. Хеш поля не сохраняет его порядок для поиска по диапазону. |
| **Cassandra 5.0** | Первичный ключ для прямого доступа к партиции, SAI для индексируемых условий | Запрос через вторичный индекс может затронуть несколько партиций. |
| **Elasticsearch** | Инвертированный индекс для поиска | Mapping определяет, как хранится и индексируется поле. Поле может быть исключено из индекса с помощью `index: false`. |

Подробнее — [вопросы по SQL](sql-interview.md).

## Q32. (!) Обработка транзакций в SQL и NoSQL?

Сравнивайте границы операции и поведение при сбое. У разных движков слово «транзакция» может означать разные гарантии.

| Система | Границы и гарантии |
|---------|---------------------|
| **PostgreSQL** | Транзакция может менять несколько таблиц. Доступны уровни изоляции и откат транзакционных изменений. Например, выданное значение последовательности при откате не возвращается. |
| **MongoDB** | Операция над одним документом атомарна. Многодокументные транзакции появились для replica sets в 4.0, для шардированных кластеров — в 4.2. Гарантии чтения и подтверждения зависят от read concern и write concern. |
| **Cassandra 5.0** | Lightweight transaction с `IF` поддерживает условное изменение через Paxos. CQL batch имеет свои гарантии атомарности и изоляции. Изоляция batch действует в пределах одной партиции. |
| **Redis** | `MULTI/EXEC` выполняет очередь без вклинивания команд других клиентов. Ошибка отдельной команды при выполнении не отменяет успешные команды. `WATCH` позволяет отказаться от исполнения очереди, если отслеживаемый ключ изменился до `EXEC`. |

В сценарии с несколькими сервисами сначала определите, требуется ли единое решение о фиксации или допустимы промежуточные состояния. Например, Saga может создать ожидающий заказ, запросить резерв и при отказе отменить заказ отдельной операцией. Компенсация видима как новая операция и может требовать повторов (Database Sharding Q19).

## Q33. (!) Разница между PostgreSQL, MongoDB, Elasticsearch, Redis и Cassandra?

Различия проще увидеть на пяти запросах одного продукта:

| Система | Пример операции | Что проверить |
|---------|-----------------|---------------|
| **PostgreSQL** | Зафиксировать заказ и позиции, проверить ссылку на покупателя | Границы транзакции, ограничения и план SQL. |
| **MongoDB** | Прочитать карточку товара с вложенными атрибутами | Размер документа, индексы по полям и ключ шардирования. |
| **Elasticsearch** | Найти товары по описанию и ранжировать выдачу | Mapping, анализ текста и время до появления изменений в поиске. |
| **Redis** | Получить значение сессии по ключу с TTL | Лимит памяти, правила вытеснения и нужная устойчивость данных. В Redis Cluster 16 384 хеш-слота распределяются между узлами. |
| **Cassandra** | Прочитать события устройства за период | Размер партиций, горячие ключи и выбранный уровень согласованности. |

Сравнивайте задержку, объём работы и поведение при отказе для одинакового функционального сценария. Например, для поиска важны и p99 запроса, и время появления новой записи в выдаче.

Подробнее — [PostgreSQL](postgresql-interview.md), [MongoDB](mongodb-interview.md), [Elasticsearch](elasticsearch-interview.md), [Redis](redis-interview.md) и [Cassandra](cassandra-interview.md).

## Q34. (!) Какие ключевые параметры конфигурации PostgreSQL влияют на производительность?

Начните с того, что ограничивает запросы: активные соединения, сброс промежуточных данных на диск, чтение страниц, контрольные точки или обслуживание таблиц. Меняйте параметры по измерениям на характерной нагрузке.

| Параметры | Что меняют | Что измерять |
|-----------|------------|--------------|
| `shared_buffers` | Размер кэша страниц PostgreSQL | Память процесса и нагрузку на ввод-вывод вместе с кэшем ОС. |
| `work_mem`, `hash_mem_multiplier` | Базовый бюджет отдельной операции сортировки или хеширования; для хеша применяется множитель | Сброс во временные файлы и пиковую память при конкурентных запросах. |
| `maintenance_work_mem`, `autovacuum_work_mem` | Память ручного обслуживания и отдельных воркеров autovacuum | Длительность обслуживания и суммарную память при одновременных workers. |
| `effective_cache_size`, `random_page_cost` | Оценки для планировщика. Первый параметр не выделяет память | Планы и фактическое время при конкретной раскладке и хранилище. |
| `max_connections` | Верхний предел серверных соединений | Конкуренцию, очередь пула и общий бюджет подключений (Q24). |
| `max_wal_size`, `checkpoint_timeout`, `checkpoint_completion_target` | Условия и темп сброса страниц в контрольных точках | Частоту checkpoint, пики I/O, размер WAL и время восстановления (Q11). |

`work_mem` нельзя оценивать только по числу соединений: один план может одновременно выполнять несколько сортировок и хешей, в том числе в параллельных воркерах. Смотрите фактические узлы плана и число одновременно активных запросов.

## Q35. (!) Как мониторить производительность PostgreSQL?

Начните с симптома: задержка, рост очереди, блокировки или отставание реплики. Сопоставьте момент ухудшения с нагрузкой и сравнивайте приращения счётчиков за одинаковые интервалы.

- `pg_stat_statements` группирует статистику запросов. `total_exec_time` помогает найти запросы с наибольшим суммарным временем, а `mean_exec_time` показывает среднее, из которого нельзя получить p99. Для подключения модуля нужны `shared_preload_libraries`, перезапуск при изменении списка и расчёт query ID. Для доступа к представлению в нужной БД создают расширение.
- `pg_stat_activity` показывает текущие состояния и ожидания. Для открытой транзакции используйте `xact_start`, для активного запроса — `query_start`. Блокирующие процессы определяет `pg_blocking_pids`.
- `pg_stat_database` и `pg_stat_io` помогают оценить обращения к блокам. `blks_hit` учитывает попадания в буферы PostgreSQL, а `blks_read` может обслуживаться кэшем ОС. Доля попаданий оценивается в контексте профиля запросов.
- `pg_stat_replication` на primary показывает состояние, позиции WAL и задержки стадий для подключённых реплик. Сопоставляйте их с допустимой давностью данных и потерей при переключении.

```sql
SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start AS transaction_age,
       pg_blocking_pids(pid) AS blocking_pids
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
   OR state = 'idle in transaction';
```

Для найденного запроса проверьте план и фактическую работу через `EXPLAIN ANALYZE` в подходящих условиях (Q16).

## Q36. (!) Что такое `HTAP` и как совместить `OLTP` и `OLAP`?

HTAP объединяет транзакционную и аналитическую обработку на одной платформе. Обычно цель — дать аналитике достаточно свежие данные и сохранить задержку транзакций при тяжёлых сканированиях.

Например, в TiDB строковые данные обслуживает TiKV, а TiFlash хранит колоночные реплики для аналитики. SQL-слой может направлять подходящие операции в TiFlash. Колоночная реплика поддерживается асинхронно. При чтении важна её способность обслужить требуемый снимок: отставание может добавить ожидание. Копии также требуют места и ресурсов на обновление.

Вариант с отдельной аналитической БД и CDC даёт независимое масштабирование. Его свежесть зависит от доставки событий, скорости применения и нагрузки на приёмник. При выборе измеряйте задержку транзакций во время отчёта, давность данных, время выполнения отчёта и поведение при отставании.

## Q37. (!) Что такое `NewSQL` (`CockroachDB`, `Google Spanner`)?

NewSQL — исторический термин для реляционных систем, которые предоставляют SQL и транзакционные гарантии при горизонтальном распределении данных. Пример современного класса — distributed SQL.

- **CockroachDB** автоматически делит пространство ключей на диапазоны и реплицирует их через Raft. По умолчанию транзакции работают на уровне `SERIALIZABLE`. При конфликте приложение может получить ошибку с требованием повторить транзакцию. Мультирегиональное размещение задаётся конфигурацией БД и локальностью таблицы.
- **Spanner** использует TrueTime, который предоставляет интервал с границами неопределённости времени. В режиме с внешней согласованностью порядок транзакций учитывает реальное время: если первая завершилась до начала второй, она предшествует второй и в наблюдаемой истории.

Такие системы полезны, если нужны распределённые реляционные данные и транзакции через части набора. Измеряйте цену координации: запись через удалённые реплики или диапазоны может ждать сетевые обмены. Выбор региона, локальности и запросов влияет на задержку и поведение при отказе.

## Q38. Что такое `Polyglot Persistence` и `Database Federation`?

**Polyglot persistence** — выбор разных хранилищ для разных операций. Например, PostgreSQL хранит исходные заказы, а Elasticsearch обслуживает поисковую проекцию. Команда определяет владельца данных, способ доставки изменений, допустимое отставание и порядок пересборки проекции.

**Database federation** даёт единый интерфейс запросов к автономным источникам. Например, Trino может соединить выгрузку заказов из объектного хранилища с таблицей клиентов из PostgreSQL. Коннекторы могут передавать поддерживаемые фильтры и другие операции источнику. Для передачи всего соединения источнику Trino требует, чтобы таблицы принадлежали одному каталогу и все предикаты соединения поддерживали pushdown. В примере с двумя каталогами соединение выполняет Trino. По `EXPLAIN` можно проверить, остался ли оператор `Join` в плане. Объём фактически прочитанных данных проверяют по метрикам выполнения.

Один SQL-запрос к двум источникам сам по себе не гарантирует общего снимка или атомарной записи. Например, PostgreSQL 19 `postgres_fdw` открывает транзакцию на удалённом сервере при первом обращении к нему. Удалённый уровень — `SERIALIZABLE` при локальном `SERIALIZABLE`, в остальных случаях — `REPEATABLE READ`. Поэтому при локальном `READ COMMITTED` два запроса в одной транзакции могут увидеть новую версию строки локальной таблицы и прежнюю версию строки удалённой таблицы. Снимки разных серверов формируются независимо. Модуль также не поддерживает подготовку удалённых транзакций для двухфазной фиксации. Если операции должны сохранять общий инвариант, выбирайте механизм фиксации отдельно (Database Sharding Q19).

## Q39. (!) Как работает `HikariCP` и что важно настроить?

HikariCP выдаёт приложению JDBC-соединение из пула. `close()` на выданном соединении возвращает его в пул для повторного использования, если физическое соединение пригодно. Если пул достиг лимита и свободных соединений нет, `getConnection()` ждёт выдачи. По истечении `connectionTimeout` вызов завершается с `SQLException`. Таймаут возможен и при числе соединений ниже лимита, если пул не успевает открыть пригодное соединение.

- **`maximumPoolSize`** ограничивает общее число соединений пула. При расчёте учитывайте все экземпляры приложения и другие клиенты БД (Q24).
- **`connectionTimeout`** ограничивает ожидание выдачи соединения, а не время SQL-запроса. Долгая транзакция может удерживать соединение даже в паузах между запросами.
- **`maxLifetime`** ограничивает срок жизни соединения в пуле. Используемое соединение выводится из пула после возврата. Учитывайте более короткие лимиты на стороне инфраструктуры.
- **`idleTimeout`** применяется к лишним простаивающим соединениям, если `minimumIdle < maximumPoolSize`.

**Пример диагностики.** После релиза выросли задержки заказа и появились ошибки получения соединения. Включите JMX через `registerMbeans` и сопоставьте динамику `ActiveConnections`, `TotalConnections` и `ThreadsAwaitingConnection` с временем удержания соединений и состоянием БД.

- Если `TotalConnections` устойчиво ниже лимита, а запросы ждут, проверьте ошибки открытия и проверки соединений. Поднятие лимита не поможет, если БД уже отклоняет подключения.
- Если все соединения заняты и транзакции стали длиннее, проверьте ожидания блокировок и работу приложения внутри транзакции. Например, перенос медленного вызова внешнего сервиса за её границу, если это допустимо по инвариантам, сокращает время удержания соединения.
- Если операции короткие, а БД имеет запас ресурсов, оцените увеличение пула нагрузочным тестом. Учитывайте суммарный лимит при максимальном числе экземпляров приложения.

[Настройки HikariCP](https://github.com/brettwooldridge/HikariCP#configuration-knobs-baby) · [Метрики HikariCP через JMX](https://github.com/brettwooldridge/HikariCP/wiki/MBean-(JMX)-Monitoring-and-Management)

## Q40. (!) Как использовать `Read Replicas` для масштабирования чтения?

Запись направляют на primary. Чтения, для которых допустимо отставание, можно направлять на standby. Например, на реплике формируют отчёт, а подтверждение нового заказа читают с primary.

В Spring решение о маршруте принимается при получении соединения. `@Transactional(readOnly = true)` задаёт признак транзакции, а не выбирает DataSource. Если маршрут зависит от этого признака, физическое соединение нужно получать после установки транзакционного контекста. В Spring Framework 6.1.2+ можно настроить `LazyConnectionDataSourceProxy` с отдельным `readOnlyDataSource`. Запрос внутри уже открытой транзакции обычно продолжает использовать её соединение.

Для read-your-writes используйте primary или убедитесь, что выбранная реплика применила нужную позицию WAL. Синхронное подтверждение сброса WAL на реплику не гарантирует, что данные доступны для чтения. `remote_apply` ждёт применения на нужных синхронных репликах, но не делает свежей произвольную реплику.

```sql
-- На primary: сколько байтов WAL отправлено, но ещё не воспроизведено.
SELECT application_name, state,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS sent_not_replayed_bytes
FROM pg_stat_replication;
```

Этот запрос показывает разницу между последней отправленной и последней подтверждённой позицией replay. Ноль возможен, даже если primary уже сформировал WAL, который ещё не отправил. Возраст последней воспроизведённой транзакции растёт и при простое догнавшей реплики. Для проверки видимости конкретного заказа сравнивайте replay с целевой позицией WAL, полученной на primary после его коммита.

В PostgreSQL 19 на выбранной физической реплике можно выполнить `WAIT FOR LSN '0/12345678' WITH (MODE 'standby_replay', TIMEOUT '200ms')`, подставив целевую позицию. Запустите ожидание до получения снимка, затем прочитайте заказ с новым снимком на том же узле. В PostgreSQL 18 ту же позицию проверяют ограниченным по времени опросом `pg_last_wal_replay_lsn()`. Если ожидание истекло, прочитайте с узла, на котором коммит подтверждён. После переключения primary сначала проверьте, что нужный коммит сохранился в новой истории WAL. Одинаковое числовое значение LSN на другой ветке само по себе этого не гарантирует. См. [WAIT в PostgreSQL 19](https://www.postgresql.org/docs/19/sql-wait.html) и [Database Replication](database-replication-interview.md).

## Q41. Что такое `Database Federation` и горизонтальное партиционирование на уровне приложения?

Федерация даёт общий интерфейс запросов к разным источникам (Q38). При делении по доменам сервисы владеют разными наборами данных, например заказами и каталогом. При горизонтальном шардировании один набор строк делят на части по ключу. Эти решения можно сочетать.

При маршрутизации в приложении ключ должен быть известен до получения соединения и начала транзакции. Например, сервис по `tenant_id` находит владельца диапазона и использует его DataSource. Если ключ отсутствует либо карта не содержит владельца, операция должна завершиться явной ошибкой или идти по предусмотренному маршруту для запросов ко многим шардам. Случайный маршрут на шард по умолчанию может записать строку не туда.

**Пример со Spring Framework 6.2 и JDBC.** Внешний обработчик определяет шард по `tenant_id` до вызова транзакционного сервиса. `AbstractRoutingDataSource` выбирает целевой пул при запросе соединения. `DataSourceTransactionManager` привязывает полученное соединение к потоку, а `JdbcTemplate` на том же `DataSource` использует его для запросов текущей транзакции. Если внутри сервиса поменять ключ с A на B после получения соединения, следующий запрос через `JdbcTemplate` продолжит работу на A. Для независимой операции на B нужна отдельная транзакционная граница с выбором B до получения соединения. Две локальные транзакции фиксируются независимо. Если ключ хранится в `ThreadLocal`, обработчик восстанавливает предыдущее значение или очищает его в `finally`, чтобы повторно используемый поток не сохранил маршрут прошлого запроса. [Spring JDBC Connections](https://docs.spring.io/spring-framework/reference/6.2/data-access/jdbc/connections.html) · [AbstractRoutingDataSource](https://docs.spring.io/spring-framework/docs/6.2.14/javadoc-api/org/springframework/jdbc/datasource/lookup/AbstractRoutingDataSource.html)

При росте кластера можно переносить логические диапазоны между узлами, сохраняя правило вычисления диапазона. Перенос требует догона изменений и согласованного переключения карты (Database Sharding Q22/Q30). Если запрос затрагивает несколько шардов, отдельно решите, как собрать результат и какие гарантии нужны для записи.
