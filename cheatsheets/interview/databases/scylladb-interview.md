# Вопросы на собеседовании: `ScyllaDB`

`ScyllaDB` — open-source NoSQL wide-column база данных. **Drop-in замена Cassandra**, написана на **C++** (в отличие от Cassandra на Java) с архитектурой **shard-per-core**. Обещает **в 10 раз меньшую задержку** и более высокую пропускную способность. Использует фреймворк **Seastar** для асинхронного I/O. Создана в 2014 году выходцами из Cloudius (KVM).

## Q1. (!) Что такое ScyllaDB?

**ScyllaDB** — open-source NoSQL wide-column база данных, переписанная с нуля на **C++**, чтобы дать ту же модель данных и тот же интерфейс, что у Apache Cassandra, но в разы быстрее. Ключевая идея: взять проверенную распределённую архитектуру Cassandra и убрать главный тормоз — JVM с её паузами GC и неоптимальной утилизацией CPU.

Поэтому Scylla **API-совместима с Cassandra**: тот же CQL, та же репликация, те же уровни согласованности. Приложение, написанное под Cassandra, в большинстве случаев работает с Scylla без изменения кода — меняется только движок под капотом.

**Заявленные метрики против Cassandra** (на том же железе):
- **В 10 раз меньшая задержка** — за счёт отсутствия пауз GC.
- **В 3-5 раз выше пропускная способность** — за счёт shard-per-core и эффективной работы с CPU.
- **Та же модель данных** — CQL, репликация, согласованность.

**История:** создана в 2014 году выходцами из проекта KVM (компания Cloudius Systems, позже — ScyllaDB Inc.). Команда применила опыт системного программирования из гипервизоров к базе данных.

**Сценарии применения** — те же, что у Cassandra, то есть высоконагруженные write-heavy задачи:
- Временные ряды (time-series).
- IoT.
- Ad-tech (ставки в реальном времени, где важна задержка в единицы миллисекунд).
- Платформы обмена сообщениями (Discord перешёл на Scylla именно ради предсказуемой задержки).
- Высокопроизводительное логирование.

## Q2. (!) ScyllaDB vs Cassandra — основные отличия?

| Критерий | Apache Cassandra | ScyllaDB |
|----------|------------------|----------|
| Язык | Java (JVM) | C++ |
| Архитектура | Пул потоков | **Shard-per-core (Seastar)** |
| GC | Да (паузы JVM GC) | Нет GC |
| Задержка p99 | ~5-50 мс | ~1-5 мс |
| Пропускная способность | Высокая | **В 3-5 раз выше** |
| Потребление памяти | Высокое | Ниже |
| Эффективность CPU | Ниже | **Существенно выше** |
| Совместимость | Оригинал | API-совместима |
| Зрелость | с 2008 | с 2014 |
| Распространённость | Шире | Растёт |

**Суть отличия в одной фразе:** модель данных и протокол одинаковые, расходится реализация движка. Cassandra исполняется на JVM с пулом потоков, разделяемой памяти и блокировками между ядрами; Scylla на C++ закрепляет один shard за каждым ядром, убирает GC и конкуренцию за блокировки.

Практический итог: на **том же железе** Scylla обычно в 3-10 раз быстрее и держит ту же нагрузку меньшим числом узлов. Платой служит меньшая зрелость и более узкая экосистема, чем у Cassandra с 2008 года.

## Q3. (!) Что такое shard-per-core архитектура?

**Shard-per-core** — это когда за каждым ядром CPU закреплён один shard, который владеет своим подмножеством данных и работает с ним полностью независимо от других ядер. По сути shared-nothing, перенесённый с уровня узлов на уровень ядер внутри узла.

**Чем это отличается от Cassandra.** В Cassandra ядра работают через общий пул потоков (work-stealing) и общую память. Поток может выполняться на любом ядре, поэтому при доступе к данным нужны блокировки, а ядра конкурируют за разделяемые структуры. Это даёт переключения контекста, промахи кэша и накладные расходы JVM.

**Как устроено в ScyllaDB:**
- **Один shard на ядро** — поток жёстко прибит к ядру (pinned), миграции между ядрами нет.
- Каждый shard владеет своим срезом данных — это его и только его собственность.
- **Нет блокировок между ядрами** — раз данные не разделяются, конкурировать не за что.
- **Нет разделяемой памяти** — каждое ядро держит свою область памяти, что бережёт CPU-кэш.
- Сетевой запрос маршрутизируется сразу на то ядро, которое владеет нужными данными.

```
8-core node:
  Core 0 → shard 0 (range A-D)
  Core 1 → shard 1 (range E-H)
  Core 2 → shard 2 (range I-L)
  ...
```

**Что это даёт:**
- **Линейное масштабирование с числом ядер** — добавили ядра, пропорционально выросла производительность. У Cassandra из-за конкуренции за блокировки рост рано выходит на плато.
- Нет пауз GC — память управляется вручную в C++.
- Предсказуемая задержка — нет случайных простоев на синхронизацию между ядрами.

**Подводный камень:** клиенты должны знать про shard-per-core. Драйвер, осведомлённый о shard-aware (shard-aware driver), бьёт запросом сразу в нужное ядро. Обычный driver попадёт на случайное ядро, и запрос придётся перенаправлять — отсюда требование к тюнингу пула соединений (см. Q23).

## Q4. Что такое фреймворк Seastar?

**Seastar** — C++ фреймворк для асинхронных приложений, созданный авторами ScyllaDB. Именно он реализует ту самую shard-per-core модель из Q3; Scylla — это, по сути, база данных, построенная поверх Seastar. Фреймворк спроектирован под современное железо: многоядерные CPU и быстрые сетевые карты, где главный враг производительности — не нехватка ресурсов, а накладные расходы на синхронизацию и переключения контекста.

**Ключевые принципы:**
- **Shared-nothing на каждое ядро** — каждое ядро работает со своими данными без блокировок (см. Q3).
- **Полностью асинхронный I/O** — поток никогда не блокируется в ожидании диска или сети, вместо этого переключается на другую готовую работу.
- **Сеть в user-space** — опционально через DPDK, в обход TCP-стека ядра, чтобы убрать лишние копирования и системные вызовы.
- **Future/Promise** — программная модель для асинхронного кода: операция возвращает Future, а её результат приходит позже через Promise, без явных колбэков-лапши.

Seastar используется не только в ScyllaDB, но и в других высокопроизводительных сетевых приложениях и Redis-подобных проектах — то есть это самостоятельная инфраструктура, а не закрытая часть базы.

## Q5. (!) Как устроена wide-column модель данных?

Модель данных Scylla **полностью совпадает с Cassandra** — отличается только скорость движка под капотом. Wide-column означает, что данные раскладываются по партициям: строки, у которых одинаковый partition key, физически живут вместе на одном узле и сортируются внутри партиции по clustering key. Это не «таблица с фиксированными колонками» в SQL-смысле, а вложенная структура «партиция → отсортированные строки → колонки».

```sql
CREATE TABLE users (
    user_id UUID,
    timestamp TIMESTAMP,
    event_type TEXT,
    data TEXT,
    PRIMARY KEY (user_id, timestamp)
) WITH CLUSTERING ORDER BY (timestamp DESC);
```

**Понятия:**
- **Keyspace** — аналог базы данных / схемы; в нём задаётся стратегия репликации.
- **Table** — набор строк с общей схемой.
- **Partition key** — определяет, на каком узле физически лежит строка (хешируется в токен).
- **Clustering key** — порядок сортировки строк внутри одной партиции.
- **Columns** — колонки, объявленные в схеме.

В примере выше `user_id` — partition key (все события одного пользователя на одном узле), `timestamp` — clustering key с убывающей сортировкой (свежие события первыми). Так читать ленту событий пользователя можно одним эффективным запросом по партиции.

Подробнее про общую модель — в [Apache Cassandra](cassandra-interview.md).

## Q6. Чем отличаются partition key и clustering key?

Оба входят в PRIMARY KEY, но отвечают за разное: partition key решает, **где** хранится строка (на каком узле), а clustering key — **в каком порядке** строки лежат внутри партиции.

```sql
PRIMARY KEY ((partition_key), clustering_key1, clustering_key2)
```

- **Partition key** — хешируется в токен и определяет узел-владелец строки. Запросы, которые знают partition key, бьют точно в один узел и работают быстро.
- **Clustering key** — задаёт сортировку строк внутри партиции и позволяет эффективно читать диапазоны (например, события за период) без полного сканирования.

**Составной partition key** объединяет несколько полей в один ключ — так дробят слишком большие партиции:
```sql
PRIMARY KEY ((user_id, date), timestamp)
-- partition by combination, ordered by timestamp
```
Здесь партиция — это пара «пользователь + день», а внутри строки отсортированы по `timestamp`. Без `date` все события активного пользователя за всё время собрались бы в одну гигантскую партицию.

**Рекомендации по проектированию ключей:**
- Брать partition key **высокой кардинальности**, чтобы нагрузка равномерно размазалась по узлам и не возникало горячих партиций (одна партиция = один узел = одно ядро).
- Держать размер партиции **меньше 100 МБ**: огромные партиции бьют по задержке чтения и compaction.
- Подбирать порядок clustering keys под реальные паттерны запросов — данные физически лежат в этом порядке, и чтение «по сортировке» бесплатно.

## Q7. Что такое CQL (Cassandra Query Language)?

**CQL** — язык запросов Cassandra и Scylla. Синтаксис намеренно сделан похожим на SQL (CREATE, INSERT, SELECT, UPDATE, DELETE), чтобы снизить порог входа, но это не реляционный язык: за привычным фасадом стоит wide-column модель, и многих привычных по SQL операций здесь нет.

```sql
-- DDL
CREATE KEYSPACE mykeyspace WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 3};

CREATE TABLE users (
    user_id UUID PRIMARY KEY,
    name TEXT,
    email TEXT
);

-- DML
INSERT INTO users (user_id, name, email) VALUES (uuid(), 'Alice', 'alice@example.com');

SELECT * FROM users WHERE user_id = uuid_value;

UPDATE users SET email = 'new@example.com' WHERE user_id = uuid_value;

DELETE FROM users WHERE user_id = uuid_value;
```

**Ограничения по сравнению с SQL** (и почему они есть):
- **Нет JOIN-ов** — данные намеренно денормализуют, дублируя их под нужные запросы. Соединять партиции с разных узлов было бы дорого.
- **Агрегации между партициями ограничены** — движок заточен под чтение конкретной партиции, а не под аналитику по всей таблице.
- **WHERE только по partition key + clustering key** (или по вторичному индексу) — без них пришлось бы сканировать весь кластер, что запрещено по умолчанию.
- **Нет подзапросов** — каждый запрос самостоятелен.

Главный принцип: **схему проектируют от запросов**, а не наоборот. Сначала решают, какие запросы нужны, потом под них раскладывают данные.

**Расширения ScyllaDB** поверх базового CQL:
- **CDC (Change Data Capture)** — поток изменений таблицы, удобен для репликации и интеграций.
- **Materialized Views** — автоматически поддерживаемые представления с другим primary key (запрос тех же данных под другим углом).

## Q8. (!) Что такое shared-nothing распределённая архитектура?

**Shared-nothing** — каждый узел полностью самостоятелен: владеет своими данными, CPU, памятью и диском и ничего не делит с соседями. Нет общего хранилища, нет мастера-координатора, нет единой точки, через которую проходят все запросы.

```
Node 1: own data, own CPU, own memory, own disk
Node 2: same
Node 3: same
```

**Как узлы договариваются без мастера.** Координация идёт через **gossip-протокол**: узлы периодически обмениваются информацией о состоянии кластера друг с другом (peer-to-peer), и знание о том, кто жив и кто чем владеет, расходится по кластеру эпидемически. Любой узел может принять запрос и стать координатором для него.

**Что это даёт:**
- **Линейное масштабирование** — добавили узел, пропорционально выросли ёмкость и пропускная способность, потому что узлы не упираются в общий ресурс.
- **Нет единой точки отказа** — все узлы равноправны, выпадение одного не роняет кластер.
- **Простое добавление и вывод узлов** — кластер сам перераспределяет данные.

**Компромисс:** ценой этой устойчивости и масштабируемости становится согласованность — по умолчанию модель eventual consistency. Но её можно подкрутить per-запрос через уровни согласованности (см. Q9–Q10), вплоть до строгой.

## Q9. Как работают репликация и уровни согласованности?

Здесь две независимые настройки, которые легко спутать. **Replication factor (RF)** задаётся один раз на keyspace и говорит, **сколько копий** данных хранить. **Consistency level (CL)** задаётся на каждый отдельный запрос и говорит, **со сколькими копиями** должен синхронно поговорить координатор, прежде чем ответить.

**Replication factor (RF)** — сколько реплик данных держать; с `NetworkTopologyStrategy` можно задать своё число на каждый дата-центр:
```sql
CREATE KEYSPACE mykeyspace WITH replication = {'class': 'NetworkTopologyStrategy', 'dc1': 3, 'dc2': 3};
```

**Уровни согласованности (per-запрос)** — от слабого к строгому:
- `ANY` — хватит одной записи, в том числе через hinted handoff (когда реплика временно недоступна, координатор сохраняет подсказку); самый слабый для записи.
- `ONE`, `TWO`, `THREE` — подтверждение от соответствующего числа реплик.
- `QUORUM` — большинство, то есть N/2 + 1 реплик.
- `ALL` — все реплики; максимальная согласованность, но падает доступность (любая недоступная реплика рушит запрос).
- `LOCAL_QUORUM` — кворум только внутри локального дата-центра (не ждём другие DC через WAN).
- `EACH_QUORUM` — кворум в каждом дата-центре.

```sql
SELECT * FROM users WHERE user_id = ? USING CONSISTENCY QUORUM;
```

Логика простая: чем больше реплик участвует, тем свежее и согласованнее ответ, но тем выше задержка и тем чувствительнее запрос к падению узлов. Как из RF и CL собрать строгую согласованность — в Q10.

## Q10. Как работает настраиваемая согласованность (R + W > N)?

Это правило, по которому из уровней чтения и записи можно собрать строгую согласованность, не жертвуя на запись полным `ALL`.

```
R + W > N
```
- R — число реплик, которые читаются (consistency level чтения).
- W — число реплик, в которые подтверждается запись (consistency level записи).
- N — replication factor.

**Почему оно работает.** Если множества реплик для записи и для чтения **гарантированно пересекаются**, то любое чтение обязательно зацепит хотя бы одну реплику с последней записью — и вернёт свежее значение. Условие пересечения и есть `R + W > N`.

**Пример** для RF=3:
- W=QUORUM (2) + R=QUORUM (2): 2 + 2 > 3 — множества пересекаются, чтение всегда видит последнюю запись (строгая согласованность).
- W=ONE (1) + R=ONE (1): 1 + 1 < 3 — пересечения может не быть, чтение рискует попасть на устаревшую реплику (eventual consistency).

**Компромисс:**
- Выше R и W → строже согласованность, но больше задержка и ниже доступность (ждём больше узлов).
- Ниже R и W → быстрее и устойчивее к падениям, но согласованность лишь eventual.

**Эмпирическое правило:** `LOCAL_QUORUM` для чтения и записи. При RF=3 это даёт строгую согласованность внутри дата-центра (2 + 2 > 3) и при этом не ходит через WAN в другие DC — хороший баланс для большинства задач.

## Q11. Что такое tokens и virtual nodes (vnodes)?

Это механизм, который решает, какой узел владеет какими данными, — без центрального справочника.

**Token ring** — кольцо всех возможных значений хеша (от `-2^63` до `2^63-1`). Partition key каждой строки хешируется в **токен**, а каждый узел отвечает за свой диапазон токенов на кольце. Чтобы найти владельца строки, достаточно посчитать хеш ключа — никакого запроса к мастеру не нужно.

**Проблема без vnodes.** Если на узел приходится один сплошной диапазон токенов, кольцо балансируется плохо: узлы получают неравные объёмы данных, а при добавлении/выходе узла перетряхивать приходится большие смежные куски.

**vnodes (virtual nodes)** — решение: каждый физический узел владеет не одним, а множеством мелких **случайных** диапазонов токенов (обычно 256 на узел).

```
Without vnodes:
  Node 1: tokens 0-1000
  Node 2: tokens 1001-2000

With 256 vnodes per node:
  Node 1: 256 random ranges
  Node 2: 256 random ranges
```

**Почему это лучше:**
- **Равномернее балансировка** — много мелких случайных диапазонов в среднем дают узлам близкие объёмы данных.
- **Быстрее восстановление** — данные упавшего узла лежат кусочками на многих соседях, поэтому при ребилде их тянут параллельно со всех сразу, а не последовательно с одного.
- **Проще масштабирование** — новый узел забирает по чуть-чуть со всех остальных, нагрузка на отдачу размазывается по кластеру.

ScyllaDB поддерживает vnodes (а также режим с обычными едиными токенами).

## Q12. (!) Как устроено хранение на LSM-tree?

**LSM-tree (Log-Structured Merge-tree)** — движок хранения, оптимизированный под запись. Та же идея, что в Cassandra, RocksDB, ClickHouse: вместо того чтобы править данные на месте на диске (дорогие случайные записи), все изменения сначала копятся в памяти, а на диск сбрасываются крупными последовательными блоками.

**Как идёт запись и чтение:**
```
Write → MemTable (in-memory sorted)
       ↓ flush when full
       SSTable (immutable on-disk file)
       ↓ background compaction
       Larger SSTables
```
1. Запись попадает в **MemTable** — отсортированную структуру в памяти (плюс запись в commit log на случай сбоя).
2. Когда MemTable наполняется, она целиком сбрасывается на диск как **SSTable** — неизменяемый файл. Раз файлы неизменяемы, запись на диск всегда последовательная.
3. Старые SSTable периодически сливаются фоновым **compaction** в более крупные, попутно выкидывая перезаписанные значения и tombstone-ы.

**Плюсы:**
- **Очень быстрые записи** — только последовательный ввод-вывод, без случайных правок на месте.
- **Быстрые чтения при попадании в кэш** — свежие данные в MemTable, а Bloom filter позволяет не трогать SSTable, в которых ключа заведомо нет.

**Компромисс:**
- **Усиление чтения (read amplification)** — одно значение может быть размазано по нескольким SSTable, и при чтении их приходится проверять и сливать на лету.
- **Накладные расходы на compaction** — фоновое слияние ест CPU и диск; если оно отстаёт, чтения деградируют (см. Q23).

**Стратегии compaction под разные нагрузки:**
- **STCS (SizeTieredCompactionStrategy)** — по умолчанию; сливает SSTable близкого размера, дёшево по записи, но read amplification выше.
- **LCS (LeveledCompactionStrategy)** — раскладывает данные по уровням, минимизирует read amplification — лучше для read-heavy нагрузок ценой большего объёма compaction.
- **TWCS (TimeWindowCompactionStrategy)** — группирует SSTable по временным окнам — оптимальна для временных рядов (см. Q19).

## Q13. (!) Почему Scylla быстрее Cassandra?

Коротко: Scylla убирает три главных источника накладных расходов Cassandra — JVM, конкуренцию между ядрами и неэффективную работу с ядром ОС. Все причины ниже сводятся к этим трём.

**Уход от JVM:**
1. **C++ вместо Java** — нет накладных расходов рантайма JVM.
2. **Нет пауз GC** — память управляется вручную, поэтому исчезают stop-the-world паузы, которые рвут задержку p99 (см. Q14).
3. **Более плотное управление памятью** — нет издержек на Java heap и его служебные структуры.

**Устранение конкуренции между ядрами:**
4. **Shard-per-core** — каждое ядро работает со своими данными без блокировок, нет конкуренции за общие структуры (см. Q3).
5. **Лучшая утилизация CPU** — архитектура спроектирована под современные многоядерные процессоры и масштабируется с числом ядер.

**Эффективная работа с I/O и ОС:**
6. **Асинхронный I/O Seastar** — поток не блокируется в ожидании диска/сети, а переключается на готовую работу.
7. **Прямой дисковый I/O** — в части конфигураций в обход буферов ядра, без лишних копирований.
8. **Своя сетевая реализация** (опционально DPDK) — в обход TCP-стека ядра, меньше системных вызовов.

**Итог:** на том же железе Scylla часто в 3-10 раз быстрее Cassandra — и тем самым держит ту же нагрузку меньшим числом узлов.

## Q14. Нет JVM — значит нет пауз GC?

Да. Cassandra работает на JVM, а значит подвержена сборке мусора; Scylla написана на C++ и управляет памятью вручную, поэтому пауз GC у неё нет в принципе. Для базы данных под нагрузкой это не мелочь, а ключевой фактор предсказуемости задержки.

**Чем плохи паузы GC в Cassandra:**
- **Stop-the-world паузы** на 10-500 мс — в этот момент узел не отвечает вообще.
- Из-за них скачет **задержка p99**: средняя может быть хорошей, но хвост распределения портят именно паузы GC.
- **Сложный тюнинг** — приходится подбирать сборщик и его параметры (G1GC, ZGC), и это постоянная эксплуатационная головная боль.

**Что у Scylla:**
- **Нет GC** — ручное управление памятью в C++, никаких stop-the-world пауз.
- **Предсказуемая задержка** — нет случайных простоев, хвост распределения ровный.
- **Задержка p99 в 5-10 раз ниже** — выигрыш именно в хвосте, а не в среднем.

Именно предсказуемость хвоста задержки — **главная причина**, по которой Discord, Comcast и другие мигрировали с Cassandra на Scylla: для интерактивных систем важно не «обычно быстро», а «никогда не залипает».

## Q15. Что такое приоритизация нагрузок (workload prioritization)?

**Workload prioritization** — фича ScyllaDB Enterprise, которая позволяет разным типам нагрузки на одном кластере выделять разные доли CPU и I/O. Проблема, которую она решает: на общем кластере тяжёлый аналитический запрос может «съесть» ресурсы и просадить задержку критичных OLTP-запросов. Приоритизация ставит между ними жёсткую границу.

```
Critical OLTP queries: 80% resources
Background analytics: 20% resources
```

**Сценарий применения:** смешанная нагрузка — быстрые транзакционные запросы плюс фоновая отчётность/аналитика — на одном кластере, но без того, чтобы одна нагрузка деградировала другую.

В Cassandra встроенного аналога нет: чтобы изолировать нагрузки, обычно приходится поднимать **отдельные кластеры**, что дороже по железу и эксплуатации.

## Q16. (!) Насколько Scylla — настоящая drop-in замена Cassandra?

На уровне приложения — почти полностью, на уровне эксплуатации — нет. То есть код приложения чаще всего переезжает без изменений, а вот процессы DevOps придётся пересобрать.

**Что совпадает (поэтому приложение не трогаем):**
- Тот же **CQL**.
- Тот же **wire-протокол** — существующие драйверы Cassandra подключаются к Scylla как есть.
- Та же модель данных, та же репликация, те же уровни согласованности.

В итоге **миграция приложения обычно не требует правок кода**.

**Что расходится (поэтому это не 100% drop-in):**
- Часть продвинутых фич Cassandra отсутствует или реализована иначе.
- **Эксплуатация и мониторинг другие** — у Scylla свой стек метрик и свои операционные команды.
- **Параметры тюнинга свои** — настройки Cassandra напрямую не переносятся (например, всё, что связано с shard-per-core).
- Версии и набор фич двух продуктов со временем расходятся.

**Рекомендация:** относиться к Scylla как к совместимой, но самостоятельной системе — тщательно тестировать на своей нагрузке и использовать **Scylla Migration Tools** для переноса данных (см. Q22).

## Q17. (!) Что такое DynamoDB API (Alternator)?

**Scylla Alternator** — реализация API DynamoDB поверх ScyllaDB. То есть, помимо родного CQL, Scylla умеет отвечать на запросы по протоколу DynamoDB: приложение, написанное под AWS DynamoDB, может ходить в Scylla без переписывания — достаточно подменить endpoint.

```python
# Standard boto3 DynamoDB client works
import boto3
dynamodb = boto3.resource('dynamodb', endpoint_url='http://scylla:8000')
table = dynamodb.Table('users')
table.put_item(Item={'PK': 'user#123', 'name': 'Alice'})
```

**Зачем это нужно:**
- **Уход от vendor lock-in на AWS** — DynamoDB-совместимое хранилище, которое можно держать у себя.
- **DynamoDB-нагрузки on-premise или multi-cloud** — не привязываясь к одному облаку.
- **Дешевле DynamoDB на больших масштабах** — на больших объёмах модель оплаты DynamoDB становится дорогой, а self-hosted Scylla — нет.

В **2025 году** Alternator — жизнеспособная альтернатива для приложений, уже спроектированных под DynamoDB: можно сменить хранилище без переписывания слоя доступа к данным.

## Q18. (!) Когда выбрать Scylla?

Короткий критерий: Scylla оправдана там, где нужны масштаб и предсказуемо низкая задержка write-heavy NoSQL, а реляционные возможности не требуются. Если задача — обычный бизнес-CRUD на умеренных объёмах, это перебор.

**Выбирай Scylla, когда:**
- Уже работаешь на **Cassandra** и упёрся в её производительность — это самый прямой сценарий.
- Нужна **предсказуемо низкая задержка** (p99 < 10 мс), в том числе в хвосте распределения.
- Высокая **пропускная способность записи** (10K+ записей/сек на узел).
- Важна **экономия на железе** — та же нагрузка держится меньшим числом узлов.
- Смешанным нагрузкам нужна **изоляция** на одном кластере (workload prioritization, см. Q15).
- Это типичные сценарии Cassandra: IoT, временные ряды, ad-tech.

**Не выбирай, когда:**
- Нужен **полноценный SQL** — джойны, агрегации, транзакции (тогда смотри в сторону реляционных БД).
- **Небольшой масштаб** — для умеренных объёмов хватит PostgreSQL, и он проще в эксплуатации.
- Нужны **строгие ACID-гарантии** — это не про eventual-consistency NoSQL.
- У команды **нет опыта с NoSQL** — проектирование схемы «от запросов» и эксплуатация распределённого кластера требуют экспертизы.

## Q19. Как Scylla работает с time-series нагрузками?

Временные ряды — едва ли не идеальная нагрузка для Scylla, потому что их природа точно ложится на сильные стороны LSM-tree. Данные пишутся **только на добавление** (append-only) — а LSM как раз оптимизирован под последовательную запись. Нагрузка по записи **высокая и равномерная**, а читают обычно **по временным окнам** (например, «последний час по датчику»), что прекрасно ложится на сортировку по clustering key.

**Схема:**
```sql
CREATE TABLE sensor_data (
    sensor_id UUID,
    bucket DATE,  -- partition by day to limit partition size
    timestamp TIMESTAMP,
    value DOUBLE,
    PRIMARY KEY ((sensor_id, bucket), timestamp)
) WITH CLUSTERING ORDER BY (timestamp DESC)
  AND compaction = {'class': 'TimeWindowCompactionStrategy', 'compaction_window_size': '1', 'compaction_window_unit': 'DAYS'};
```

Здесь partition key — пара «датчик + день» (`bucket` ограничивает размер партиции, чтобы один датчик за всё время не разросся в одну гигантскую партицию), а строки внутри отсортированы по времени.

**TWCS** группирует SSTable по временным окнам, поэтому compaction старых данных идёт эффективно и не перемешивает свежие записи со старыми. А когда срок жизни данных истекает по **TTL**, целые SSTable старых окон удаляются разом — без дорогого построчного удаления и без шлейфа tombstone-ов.

## Q20. Чем Scylla хороша для IoT?

IoT — это миллионы устройств, непрерывно льющих телеметрию. Профиль нагрузки тот же, что у временных рядов (Q19), только в экстремальном масштабе: запись доминирует, объёмы огромны, а география распределённая.

**Почему Scylla здесь к месту:**
- **Высокая пропускная способность записи** — миллионы записей/сек на кластер, как раз чтобы поглотить поток от множества устройств.
- **Хранение временных рядов** — телеметрия по своей сути и есть time-series (см. Q19).
- **Геораспределённость (multi-DC)** — устройства разбросаны по миру, а multi-DC репликация держит данные близко к ним.
- **Автоматическое истечение по TTL** — старая телеметрия удаляется сама, без отдельных задач очистки.

**Кто использует:** Comcast, Tubi, Discord, Numberly.

## Q21. (!) Чем различаются Open Source, Enterprise и ScyllaDB Cloud?

Три редакции отличаются не столько ядром, сколько тем, что вокруг него: набором enterprise-фич и тем, кто отвечает за эксплуатацию.

**Open Source (бесплатно):** само ядро.
- Лицензия Apache 2.0 — очень либеральная, можно использовать в коммерции без ограничений.
- Базовые возможности базы.
- Self-managed — кластер поднимаешь и обслуживаешь сам.

**ScyllaDB Enterprise (платно):** то же ядро плюс «корпоративная» обвязка.
- Приоритизация нагрузок (workload prioritization, см. Q15).
- Безопасность и compliance — LDAP, шифрование.
- Более быстрые стратегии compaction.
- Поддержка 24/7.

**ScyllaDB Cloud (managed):** Scylla как сервис — снимает с команды эксплуатацию.
- Полностью управляемый сервис на AWS, GCP, Azure.
- Multi-region из коробки.
- Автоматические бэкапы.
- Оплата по факту (pay-as-you-go).

**Как выбирать (на 2025 год):** Open Source закрывает большинство нагрузок. Enterprise берут там, где критичны безопасность и compliance или нужна изоляция нагрузок. Cloud — когда не хочется держать команду эксплуатации распределённой БД.

## Q22. (!) Как мигрировать с Cassandra на Scylla?

Идея миграции — **постепенное переключение без даунтайма**: новый кластер какое-то время живёт параллельно со старым, данные синхронизируются, а трафик переводится плавно и обратимо. Совместимость по CQL (Q16) делает это возможным без правки кода.

**Порядок шагов:**
1. **Проверка совместимости** — убедиться, что используемые возможности версии Cassandra поддержаны в Scylla.
2. **Поднять кластер Scylla** параллельно действующему.
3. **Включить dual-write** — приложение пишет одновременно в оба кластера (либо новый питается из CDC-потока старого). С этого момента свежие данные есть в обоих.
4. **Залить исторические данные** массово — Scylla Migrator (на базе Spark) или sstableloader.
5. **Проверить паритет данных** — что в Scylla оказалось ровно то же, что в Cassandra.
6. **Переключить чтения** на Scylla постепенно, наблюдая за метриками; при проблеме легко откатиться на старый кластер.
7. **Остановить dual-write**, когда Scylla стала источником истины.
8. **Вывести Cassandra из эксплуатации**.

Для приложения переход **обычно прозрачен** — тот же CQL и тот же протокол.

**Инструменты:** Scylla Migrator, sstableloader, собственный CDC.

## Q23. Какие частые проблемы Scylla в production?

Большинство граблей не уникальны для Scylla — это типичные ошибки моделирования данных и эксплуатации Cassandra-подобных систем. Сгруппируем их по природе.

**Ошибки моделирования данных:**
1. **Горячие партиции** — неудачный partition key с низкой кардинальностью загоняет нагрузку на один узел/ядро (помним: партиция = один shard).
2. **Tombstones** — обилие удалений оставляет «надгробия», которые приходится перебирать при чтении, и это перегружает чтения.

**Перекосы нагрузки и ресурсов:**
3. **Отставание compaction** — когда скорость записи стабильно выше скорости фонового слияния, SSTable копятся и чтения деградируют (см. Q12).
4. **Узкое место по дисковому I/O** — медленные диски не вытягивают поток записи и compaction.
5. **Слишком мало узлов** — попытка масштабироваться за пределами доступной ёмкости кластера.

**Неверные настройки:**
6. **Неверный уровень согласованности** — слишком строгий замедляет и снижает доступность, слишком слабый даёт рассогласования (см. Q10).
7. **Непонимание shard-per-core** — без shard-aware драйвера и правильного тюнинга пула соединений запросы попадают не на то ядро и теряют производительность (см. Q3).

**Пробелы в эксплуатации:**
8. **Нет бэкапов** — нужны Scylla Manager или снапшоты, иначе потеря данных невосстановима.
9. **Недостаточный мониторинг** — без стека Scylla Monitoring проблемы (то же отставание compaction) замечают слишком поздно.
10. **Миграции схемы** — на больших таблицах идут медленно, это надо закладывать в план.

**Рекомендация:** использовать **Scylla Manager** — он закрывает сразу несколько пунктов: автоматизирует бэкапы, repair-ы и управление схемой.
