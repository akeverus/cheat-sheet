# Вопросы на собеседовании: `PostgreSQL`

Подробные ответы по `PostgreSQL`: архитектура, типы данных, индексы, `EXPLAIN`, транзакции, `MVCC`, `VACUUM`, партиционирование, оконные функции, `CTE`, репликация, `full-text search`, `JSONB`, `PgBouncer`, блокировки, производительность, расширения.

Краткое введение: **PostgreSQL** — объектно-реляционная СУБД с открытым кодом, известная надёжностью, расширяемостью и полным соответствием стандарту `SQL`. Отличается богатой системой типов (`JSONB`, массивы, `UUID`, `enum`, пользовательские типы), мощным планировщиком запросов, `MVCC`-изоляцией и развитой инфраструктурой для репликации и горизонтального масштабирования. На собеседованиях проверяют понимание внутреннего устройства (процессы, `WAL`, `shared buffers`), умение читать планы запросов (`EXPLAIN ANALYZE`), знание индексов, уровней изоляции и типичных приёмов оптимизации.

## Q1. (!) Какова архитектура процессов PostgreSQL?

PostgreSQL использует **мультипроцессную архитектуру** (а не многопоточную): каждое клиентское соединение обслуживается отдельным процессом ОС — `backend`. На запросы клиента работает именно этот процесс, а вокруг крутится набор фоновых процессов, которые делят общую память.

Из этого вытекает ключевое практическое следствие: каждое соединение стоит памяти и `fork()`, поэтому тысячи прямых соединений деградируют сервер — отсюда потребность в пуле (`PgBouncer`).

Главные процессы:

| Процесс | Назначение |
|---------|-----------|
| `postmaster` | Главный процесс, принимает входящие соединения, порождает дочерние процессы |
| `backend` | Один на соединение, выполняет запросы клиента |
| `checkpointer` | Записывает грязные страницы из `shared_buffers` на диск при `checkpoint` |
| `background writer` | Упреждающая запись грязных страниц, снижает нагрузку на `checkpoint` |
| `WAL writer` | Сбрасывает буферы `WAL` на диск |
| `autovacuum launcher` | Запускает рабочие процессы `autovacuum` |
| `stats collector` | Собирает статистику использования таблиц и индексов |
| `wal sender/receiver` | Репликация: отправка/приём WAL на реплику |

Процессы общаются не через переменные, а через **разделяемую память** (`shared memory`). В ней лежат: `shared_buffers` (кэш страниц данных), `WAL buffers`, `lock table` (таблица блокировок), кэш планов и другое.

```sql
-- Посмотреть активные серверные процессы
SELECT pid, usename, application_name, state, query
FROM pg_stat_activity
WHERE state <> 'idle';
```

## Q2. Что такое `shared_buffers` и как он влияет на производительность?

**`shared_buffers`** — общий кэш страниц данных в памяти, разделяемый между всеми процессами. Прежде чем читать данные с диска, PostgreSQL ищет нужную страницу здесь; диск трогается, только если в кэше её нет. Чем больше попаданий в кэш, тем меньше дискового ввода-вывода и тем быстрее запросы.

Тонкость, которую часто спрашивают: PostgreSQL опирается не только на свой кэш, но и на **кэш файловой системы ОС** (`page cache`). Поэтому отдавать `shared_buffers` слишком много памяти контрпродуктивно — данные будут дублироваться в двух кэшах.

**Рекомендации по настройке:**
- Типичное значение: **25% RAM** для выделенного сервера (но не более 8–16 GB — остальное оставляют ОС-кэшу).
- Увеличение `shared_buffers` снижает число операций дискового ввода-вывода до определённого предела.
- В паре с `shared_buffers` настраивают `effective_cache_size` — это не выделение памяти, а **подсказка планировщику** о суммарном размере доступного кэша (свой + ОС). Завышенный `effective_cache_size` склоняет планировщик чаще выбирать индексы.

```sql
-- Посмотреть текущие значения
SHOW shared_buffers;
SHOW effective_cache_size;

-- Статистика попаданий в кэш (должна быть > 99%)
SELECT sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) AS cache_hit_ratio
FROM pg_statio_user_tables;
```

## Q3. (!) Что такое `WAL` и зачем он нужен?

**`WAL` (Write-Ahead Log)** — журнал предзаписи. Главное правило: любое изменение сначала фиксируется записью в `WAL` на диск и лишь потом применяется к страницам данных в памяти. Сами страницы данных на диск пишутся позже и пачкой (при `checkpoint`).

Зачем такой обходной путь? Если просто писать изменённые страницы напрямую, при сбое посреди записи база останется в несогласованном состоянии. `WAL` решает это: фиксируем намерение в журнал, а после сбоя проигрываем журнал и восстанавливаем согласованность.

**Что это даёт:**
- **Надёжность (durability):** после сбоя базу восстанавливают, проиграв `WAL` с последнего `checkpoint` (`crash recovery`).
- **Производительность:** журнал пишется **последовательно** — это намного быстрее, чем россыпь случайных записей по страницам данных. Запись страниц откладывается и группируется.
- **Репликация:** те же `WAL`-записи потоком уходят на реплики (`streaming replication`).
- **Point-in-Time Recovery (PITR):** архив `WAL`-файлов позволяет откатить базу на любой момент времени.

**Ключевые параметры:**
| Параметр | Описание |
|---------|---------|
| `wal_level` | Уровень детализации: `minimal`, `replica`, `logical` |
| `synchronous_commit` | Синхронная/асинхронная запись: `on`, `off`, `local`, `remote_write`, `remote_apply` |
| `wal_compression` | Сжатие WAL-сегментов |
| `archive_mode` | Включить архивирование WAL |

```sql
SHOW wal_level;
SHOW synchronous_commit;
```

## Q4. Как работает `checkpoint` в PostgreSQL?

**`Checkpoint`** — точка согласованности, в которой PostgreSQL гарантированно сбрасывает все «грязные» страницы (`dirty pages`) из `shared_buffers` на диск и ставит отметку в `WAL`. С этого момента всё, что было до отметки, уже на диске, поэтому при восстановлении после сбоя журнал нужно проигрывать только начиная с последнего `checkpoint` — а не с самого начала.

Отсюда компромисс: частые `checkpoint` ускоряют восстановление, но создают пиковую нагрузку на диск (надо разом записать много страниц); редкие — наоборот, удлиняют восстановление, но сглаживают запись. Настройка как раз балансирует между этими крайностями.

**Параметры:**
- `checkpoint_timeout` (по умолчанию `5min`) — максимальный интервал между `checkpoint` по времени.
- `max_wal_size` — порог накопленного `WAL`: при превышении `checkpoint` запускается принудительно, не дожидаясь таймаута.
- `checkpoint_completion_target` (по умолчанию `0.9`) — на какую долю интервала «размазать» запись грязных страниц. Значение `0.9` означает: растянуть запись на 90% периода, чтобы не было резкого пика ввода-вывода в один момент.

## Q5. Что такое `pg_hba.conf` и для чего он используется?

**`pg_hba.conf`** (`host-based authentication`) — файл, который решает, **кому и как разрешено подключаться**: ещё до проверки пароля сервер сверяет соединение с правилами в этом файле. Каждая строка — одно правило: тип соединения, база, пользователь, адрес клиента и метод аутентификации.

Правила читаются сверху вниз, и применяется **первое совпавшее** — порядок строк важен. Если ни одно правило не подошло, в подключении отказывают.

```
# TYPE  DATABASE  USER    ADDRESS         METHOD
host    mydb      myuser  192.168.1.0/24  md5
local   all       all                     peer
host    all       all     0.0.0.0/0       scram-sha-256
```

**Методы аутентификации:** `trust`, `peer`, `md5`, `scram-sha-256`, `ldap`, `cert`, `radius`.

## Q6. (!) Какие специальные типы данных поддерживает PostgreSQL?

Богатая система типов — одна из визитных карточек PostgreSQL: кроме привычных чисел и строк есть типы, которые в других СУБД пришлось бы эмулировать таблицами или текстом. Это позволяет хранить полуструктурированные и доменные данные «как есть», с индексами и операторами под них.

| Тип | Описание |
|-----|---------|
| `JSONB` | Бинарный `JSON` с индексированием |
| `JSON` | Текстовый `JSON`, сохраняет порядок ключей |
| `UUID` | 128-битный универсальный идентификатор |
| `ARRAY` | Массив любого типа (`int[]`, `text[]`, ...) |
| `HSTORE` | Хранилище пар ключ-значение |
| `ENUM` | Перечислимый тип |
| `INET`, `CIDR` | IP-адреса и подсети |
| `TSRANGE`, `DATERANGE` | Диапазоны дат/временных меток |
| `TSVECTOR` | Full-text search вектор |
| `BYTEA` | Бинарные данные |
| `XML` | XML-данные |
| `POINT`, `LINE`, `POLYGON` | Геометрические типы |
| `MONEY` | Денежная сумма |

## Q7. В чём разница между `JSON` и `JSONB`?

Коротко: `JSON` хранит исходный текст как есть, а `JSONB` — разобранную бинарную структуру. Отсюда вытекают все различия в таблице.

| Характеристика | `JSON` | `JSONB` |
|---------------|--------|---------|
| Хранение | Текст (оригинальная строка) | Бинарный формат |
| Порядок ключей | Сохраняется | Не гарантируется |
| Дубли ключей | Сохраняются | Последнее значение |
| Индексирование | Нет (только функциональный) | `GIN`-индекс |
| Производительность записи | Быстрее | Медленнее (парсинг при вставке) |
| Производительность чтения | Медленнее (парсинг при выборке) | Быстрее |

Логика проста: `JSONB` платит разбором один раз при вставке, зато потом читает и ищет по уже готовой структуре. `JSON` дешевле пишет, но каждый раз парсит заново при чтении и не умеет индексироваться.

**Что выбирать:** в 99% случаев — `JSONB`: только он поддерживает `GIN`-индексы, операторы `@>`, `?` и быстрый поиск по содержимому. `JSON` оправдан, лишь когда важно дословно сохранить исходный текст (порядок ключей, дубли, форматирование), а поиск по полям не нужен.

```sql
CREATE TABLE events (
    id SERIAL PRIMARY KEY,
    payload JSONB
);

-- GIN-индекс для JSONB
CREATE INDEX idx_events_payload ON events USING GIN (payload);
```

## Q8. Как работают массивы (`arrays`) в PostgreSQL?

Массивы позволяют хранить несколько значений одного типа прямо в одном поле — без отдельной таблицы-связки. Удобно для простых перечислений (теги, роли), где не нужны отдельные строки и `JOIN`.

Ключевые операторы для работы с массивами: `ANY` (содержит элемент), `@>` (содержит все перечисленные), `&&` (пересекается), `unnest` (разворачивает массив в строки).

```sql
-- Создание таблицы с массивом
CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    tags TEXT[]
);

-- Вставка
INSERT INTO articles (tags) VALUES ('{"postgresql","database","sql"}');
INSERT INTO articles (tags) VALUES (ARRAY['performance', 'indexing']);

-- Запрос: содержит ли массив элемент
SELECT * FROM articles WHERE 'postgresql' = ANY(tags);

-- Запрос: все элементы массива присутствуют
SELECT * FROM articles WHERE tags @> ARRAY['postgresql', 'sql'];

-- unnest: развернуть массив в строки
SELECT id, unnest(tags) AS tag FROM articles;
```

Поиск вида `'x' = ANY(tags)` или `tags @> ARRAY[...]` без индекса приводит к `Seq Scan`. Чтобы такие запросы шли по индексу, на колонку-массив вешают `GIN`:

```sql
CREATE INDEX idx_articles_tags ON articles USING GIN (tags);
```

## Q9. Что такое `hstore` и когда его использовать?

**`hstore`** — расширение для хранения плоского набора пар `ключ => значение` в одном поле, где и ключ, и значение — строки. По сути это «словарь без вложенности»: идеально для разреженных атрибутов, набор которых заранее неизвестен и меняется от записи к записи.

```sql
CREATE EXTENSION IF NOT EXISTS hstore;

CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT,
    attributes HSTORE
);

INSERT INTO products (name, attributes)
VALUES ('Shirt', 'color => "red", size => "L", material => "cotton"');

-- Получить значение по ключу
SELECT attributes -> 'color' FROM products;

-- Фильтр по ключу-значению
SELECT * FROM products WHERE attributes @> 'color => "red"';
```

**Когда использовать:** только если данные плоские (нет вложенности и массивов) и нужен максимально лёгкий формат. В современных проектах `hstore` почти вытеснен `JSONB` — тот умеет вложенность, типы помимо строк и богаче по операторам. Знать `hstore` стоит в основном для поддержки legacy-баз.

## Q10. Как работают пользовательские типы (`enum`, `composite`, `domain`)?

PostgreSQL позволяет объявлять собственные типы — это делает схему выразительнее и переносит часть проверок с уровня приложения на уровень БД.

**`ENUM`** — перечислимый тип с фиксированным набором значений, заданным при создании. Хранится компактно (как небольшое целое), но добавить новое значение можно только через `ALTER TYPE`:

```sql
CREATE TYPE mood AS ENUM ('happy', 'sad', 'neutral');

CREATE TABLE persons (
    name TEXT,
    current_mood mood
);
```

**Composite type** — составной тип, объединяющий несколько полей в одно (аналог структуры/записи):

```sql
CREATE TYPE address AS (
    street TEXT,
    city TEXT,
    zip_code VARCHAR(10)
);

CREATE TABLE customers (
    id SERIAL PRIMARY KEY,
    addr address
);

SELECT (addr).city FROM customers;
```

**`DOMAIN`** — существующий тип плюс ограничения (`CHECK`, `NOT NULL`). Объявив правило один раз, его переиспользуют в любых таблицах — например, «положительное целое» или «email по маске» в единственном месте:

```sql
CREATE DOMAIN positive_int AS INTEGER
    CHECK (VALUE > 0);

CREATE TABLE items (
    id SERIAL PRIMARY KEY,
    quantity positive_int
);
```

## Q11. (!) Какие типы индексов существуют в PostgreSQL?

В PostgreSQL индекс — это не «один на всё», а семейство структур под разные задачи. Выбор типа определяется не столько колонкой, сколько **операторами в запросе**: равенство и диапазоны — это `B-tree`, поиск элемента внутри составного значения (`JSONB`, массив, текст) — `GIN`, геометрия и диапазоны — `GiST`, огромные упорядоченные таблицы — `BRIN`.

| Тип | Структура | Применение |
|-----|-----------|-----------|
| `B-tree` | Сбалансированное дерево | По умолчанию. Равенство, диапазон, `IS NULL`, сортировка |
| `Hash` | Хэш-таблица | Только проверка равенства (`=`) |
| `GIN` | Inverted index | `JSONB`, массивы, `full-text search`, `hstore` |
| `GiST` | Обобщённое дерево поиска | Геометрические типы, `full-text`, диапазоны, `pg_trgm` |
| `SP-GiST` | Space-partitioned GiST | IP-адреса, телефонные номера, точки |
| `BRIN` | Block Range Index | Монотонные данные (временные метки, последовательности) |

В подавляющем большинстве случаев используется `B-tree` — остальные типы берут под конкретные специализированные сценарии.

## Q12. (!) Как работает `B-tree` индекс и когда он применяется?

**`B-tree`** (Balanced Tree) — индекс по умолчанию. Хранит ключи в отсортированном сбалансированном дереве, поэтому поиск любого значения занимает логарифмическое число шагов, а соседние значения лежат рядом — это и даёт эффективные диапазоны и сортировку.

Именно из-за упорядоченности `B-tree` так универсален: дерево умеет и точное равенство, и «больше/меньше», и `ORDER BY` без отдельной сортировки.

**Применяется при:**
- Операторах `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`
- `ORDER BY` (может устранить сортировку)
- `IS NULL` / `IS NOT NULL`
- Операциях `LIKE 'prefix%'` (только с префиксом, не `'%suffix'`)

```sql
-- Обычный B-tree
CREATE INDEX idx_orders_created_at ON orders (created_at);

-- Составной B-tree
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- Descending
CREATE INDEX idx_orders_created_desc ON orders (created_at DESC);
```

**Составной индекс** работает по правилу «левого префикса»: индекс `(a, b, c)` помогает запросам по `a`, по `a, b` и по `a, b, c`, но **не** запросу только по `b` или `c`. Поэтому порядок столбцов критичен — первым ставят столбец, по которому фильтруют чаще всего (обычно через равенство), а столбцы для диапазонов — ближе к концу.

## Q13. Что такое `GIN` индекс и для каких данных он нужен?

**`GIN` (Generalized Inverted Index)** — инвертированный индекс, устроенный «наоборот» обычному: ключом выступает не строка таблицы, а отдельный элемент внутри значения (слово, элемент массива, ключ `JSONB`), а значением — список строк, где этот элемент встречается. Та же идея, что в поисковых системах: по слову сразу находим все документы.

Поэтому `GIN` незаменим там, где одно поле содержит **много элементов**, и искать надо «по элементу внутри», а не по полю целиком.

**Применяется для:**
- `JSONB` (операторы `@>`, `?`, `?|`, `?&`)
- Массивов (`@>`, `<@`, `&&`)
- `full-text search` (`@@`)
- `hstore`
- `pg_trgm` (поиск по подстроке)

```sql
-- GIN для JSONB
CREATE INDEX idx_events_payload ON events USING GIN (payload);

-- GIN для full-text search
CREATE INDEX idx_articles_tsv ON articles USING GIN (to_tsvector('russian', body));

-- GIN для pg_trgm (поиск LIKE '%term%')
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING GIN (name gin_trgm_ops);
```

**Подводные камни:** при вставке/обновлении приходится трогать индекс по каждому элементу значения, поэтому запись в `GIN` заметно дороже, чем в `B-tree`. Смягчает это опция `fastupdate` — она копит изменения в отложенном списке и применяет их пачкой, ценой небольшого замедления чтения.

---

## Q14. Что такое `GiST` индекс и чем он отличается от `GIN`?

**`GiST` (Generalized Search Tree)** — это не один индекс, а каркас для деревьев поиска: сама структура общая, а как сравнивать значения и определять «пересечение/вложенность», задаёт класс операторов под конкретный тип. Благодаря этому `GiST` умеет то, что недоступно `B-tree`: индексировать диапазоны, геометрию, расстояния.

**Чем отличается от `GIN`:** `GIN` заточен под точный поиск отдельных элементов («есть такой ключ/слово»), а `GiST` — под пространственные и приближённые запросы («пересекается с диапазоном», «ближайшие точки»). Цена универсальности `GiST` — возможные ложные срабатывания: индекс отбирает кандидатов, а движок затем перепроверяет их по самой таблице.

| Характеристика | `GIN` | `GiST` |
|---------------|-------|--------|
| Оптимален для | Точный поиск элементов | Приближённые запросы, диапазоны |
| Размер | Обычно больше | Меньше |
| Обновление | Медленнее | Быстрее |
| Ложные срабатывания | Нет | Возможны (требует перепроверки) |

**Сценарий применения:** геометрические данные (`PostGIS`), диапазоны (`tsrange`), `full-text search`, `pg_trgm`.

```sql
-- GiST для диапазонов дат
CREATE INDEX idx_reservations_period ON reservations USING GiST (period);

-- GiST для PostGIS
CREATE INDEX idx_locations_geom ON locations USING GiST (geom);
```

## Q15. Что такое `BRIN` индекс и когда его выгодно использовать?

**`BRIN` (Block Range Index)** — самый компактный индекс. Вместо ссылки на каждую строку он хранит лишь мин/макс значения для группы физических блоков (по умолчанию 128 блоков на диапазон). При запросе `BRIN` отсекает целые диапазоны блоков, чьи мин/макс не подходят под условие, а оставшиеся досматривает напрямую.

Отсюда два следствия: индекс занимает крошечный объём (метаданные на сотни мегабайт данных), но эффективен **только если значения столбца коррелируют с физическим порядком строк** — иначе в каждый диапазон попадёт всё подряд, и отсекать будет нечего.

**Сценарий применения:**
- Данные физически упорядочены по индексируемому столбцу (монотонные `id`, временные метки вставки — записи ложатся в конец таблицы по возрастанию).
- Таблица очень большая, и полноценный `B-tree` занял бы неприемлемо много места.

```sql
CREATE INDEX idx_logs_created_brin ON logs USING BRIN (created_at);
```

**Подводные камни:** если данные перемешаны (низкая корреляция с физическим порядком), `BRIN` бесполезен — придётся читать почти всю таблицу. В таких случаях нужен `B-tree`.

## Q16. Что такое частичный (`partial`) индекс?

**Частичный индекс** включает не все строки таблицы, а только те, что удовлетворяют условию `WHERE` в определении индекса. Идея: если запросы всегда фильтруют узкое подмножество (например, только активные заказы), нет смысла индексировать остальные миллионы строк.

Выгода двойная: индекс меньше (меньше места и быстрее по нему искать) и дешевле обновляется — строки вне условия его вообще не трогают.

```sql
-- Индексировать только незакрытые заказы
CREATE INDEX idx_orders_open ON orders (user_id)
WHERE status = 'open';

-- Индексировать только ненулевые значения
CREATE INDEX idx_users_email ON users (email)
WHERE email IS NOT NULL;
```

**Когда использовать:** запросы всегда содержат один и тот же предикат (`WHERE status = 'active'`, `WHERE deleted_at IS NULL`), а интересующее подмножество — малая часть таблицы. Важно: чтобы планировщик задействовал индекс, условие запроса должно совпадать с условием индекса (или быть его частным случаем).

## Q17. Что такое функциональный (`expression`) индекс?

**Функциональный индекс** строится не по самому столбцу, а по **результату выражения** над ним. Это решает частую проблему: если в запросе колонка обёрнута в функцию (`LOWER(email)`, `payload->>'type'`), обычный индекс по голой колонке не сработает — планировщик не знает, что `LOWER(email)` связан с индексом по `email`.

Решение — заранее проиндексировать ровно то выражение, которое стоит в `WHERE`. Тогда планировщик увидит совпадение и пойдёт по индексу.

```sql
-- Поиск без учёта регистра
CREATE INDEX idx_users_lower_email ON users (LOWER(email));

-- Запрос, использующий этот индекс
SELECT * FROM users WHERE LOWER(email) = 'user@example.com';

-- Индекс по extracted части JSONB
CREATE INDEX idx_events_type ON events ((payload->>'event_type'));

-- Индекс по части даты
CREATE INDEX idx_orders_year ON orders (EXTRACT(YEAR FROM created_at));
```

## Q18. (!) Что такое покрывающий (`covering`) индекс и как его создать в PostgreSQL?

**Покрывающий индекс** содержит все столбцы, которые нужны запросу, прямо в самом индексе. Тогда движок отвечает на запрос **только из индекса** (`Index Only Scan`), не делая дорогих случайных обращений к основной таблице за каждой строкой. Это устраняет шаг «нашли в индексе → сходили в таблицу за остальными колонками» (`heap fetch`).

В PostgreSQL (с версии 11) для этого есть `INCLUDE`: ключевые столбцы участвуют в поиске и сортировке, а перечисленные в `INCLUDE` просто «довешиваются» в листья индекса как полезная нагрузка:

```sql
-- Основной индекс по user_id, дополнительно хранит status и total
CREATE INDEX idx_orders_covering ON orders (user_id) INCLUDE (status, total);

-- Запрос использует Index Only Scan
SELECT status, total FROM orders WHERE user_id = 42;
```

**До PostgreSQL 11** того же эффекта добивались составным индексом — просто включали нужные столбцы прямо в ключ. Разница в том, что `INCLUDE`-столбцы не раздувают ключ и не участвуют в сортировке, поэтому такой индекс компактнее и эффективнее.

**Компромисс:** меньше обращений к таблице и ввода-вывода при чтении — ценой большего размера индекса и более дорогих вставок/обновлений. Не стоит складывать в `INCLUDE` всё подряд: покрывают только реально востребованные столбцы.

## Q19. Что такое `CONCURRENTLY` при создании индекса?

Обычный `CREATE INDEX` берёт на таблицу блокировку `SHARE`, которая запрещает любые `INSERT`/`UPDATE`/`DELETE` на всё время построения. На большой «живой» таблице это означает простой записи на минуты — недопустимо в продакшене. `CONCURRENTLY` строит индекс **без блокировки записи**: приложение продолжает работать.

```sql
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id);
```

Цена за отсутствие блокировки — индекс строится в несколько проходов и медленнее.

**Подводные камни:**
- Дольше обычного построения (минимум два прохода по таблице).
- Нельзя выполнять внутри транзакционного блока (`BEGIN ... COMMIT`).
- Если построение прервётся (ошибка, конфликт), останется нерабочий `invalid`-индекс — его надо найти и удалить вручную, иначе он будет занимать место и сбивать планировщик.
- Симметричный безопасный вариант при удалении — `DROP INDEX CONCURRENTLY`.

## Q20. (!) Как читать вывод `EXPLAIN`?

`EXPLAIN` показывает **план выполнения** — как именно PostgreSQL собирается выполнить запрос: какими сканами, в каком порядке, какими соединениями. Вывод — дерево узлов-операций. Читать его удобнее **изнутри наружу / снизу вверх**: самые вложенные узлы (листья) выполняются первыми, а их результаты поднимаются к корню.

Главное при чтении — найти узел, где оценка строк (`rows`) или стоимость резко расходится с реальностью или с ожиданием: именно там обычно прячется проблема (`Seq Scan` по большой таблице, неверная оценка, лишняя сортировка).

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```

```
Index Scan using idx_orders_user_id on orders  (cost=0.43..8.45 rows=5 width=128)
  Index Cond: (user_id = 42)
```

**Основные поля:**
- `cost=X..Y` — оценочная стоимость в условных единицах: `X` — до выдачи первой строки (startup), `Y` — до выдачи последней (total). Это **оценка планировщика**, а не время.
- `rows=N` — **оценочное** число строк, которое узел вернёт. Сравнение этой оценки с реальностью — первое, что проверяют.
- `width=N` — средний размер строки в байтах.
- `actual time=X..Y` (только `EXPLAIN ANALYZE`) — реальное время в миллисекундах.
- `actual rows=N loops=N` — реальное число строк и сколько раз узел запускался. Реальное число строк = `actual rows × loops`; сильное расхождение с `rows` — сигнал устаревшей статистики.

**Типичные узлы:**
| Узел | Описание |
|------|---------|
| `Seq Scan` | Полное сканирование таблицы |
| `Index Scan` | Сканирование по индексу с возвратом в таблицу |
| `Index Only Scan` | Сканирование только по индексу (покрывающий) |
| `Bitmap Index Scan` | Построение битовой карты по индексу |
| `Bitmap Heap Scan` | Чтение строк по битовой карте |
| `Hash Join` | Соединение хэш-таблицей |
| `Nested Loop` | Вложенные циклы |
| `Merge Join` | Соединение слиянием |
| `Sort` | Сортировка |
| `Aggregate` | Агрегация |

## Q21. (!) В чём разница между `EXPLAIN` и `EXPLAIN ANALYZE`?

Разница в одном: `EXPLAIN` только **прогнозирует** план (запрос не выполняется), а `EXPLAIN ANALYZE` реально **выполняет** запрос и показывает фактические цифры рядом с оценочными. Именно сопоставление «оценка vs факт» и делает `ANALYZE` главным инструментом диагностики: если планировщик ждал 10 строк, а пришло 10 миллионов — статистика врёт и план выбран плохо.

| Команда | Описание |
|---------|---------|
| `EXPLAIN` | Показывает **оценочный** план без выполнения запроса |
| `EXPLAIN ANALYZE` | **Выполняет** запрос и показывает реальное время и число строк |
| `EXPLAIN (ANALYZE, BUFFERS)` | Добавляет информацию о попаданиях в кэш (`shared hit`, `read`) |
| `EXPLAIN (ANALYZE, FORMAT JSON)` | Вывод в формате `JSON` |

```sql
-- Полный анализ с информацией о буферах
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 'open';
```

**Подводный камень:** раз `ANALYZE` действительно выполняет запрос, он реально изменит данные в `INSERT`/`UPDATE`/`DELETE`. Чтобы посмотреть план деструктивного запроса, не меняя данные, его оборачивают в `BEGIN` ... `ROLLBACK`:

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM old_logs WHERE created_at < NOW() - INTERVAL '1 year';
ROLLBACK;
```

## Q22. (!) Что такое `Seq Scan` и `Index Scan` и когда планировщик выбирает каждый?

Это два способа добраться до строк, и планировщик выбирает между ними по стоимости. Ключевая интуиция: **последовательное чтение диска дёшево, а случайные прыжки по индексу — дороги**. Поэтому всё зависит от того, какую долю таблицы вернёт запрос.

**`Seq Scan` (Sequential Scan)** — читает таблицу подряд, страница за страницей:
- Выгоден, когда нужно вернуть **большую долю строк**: проще прочитать всё последовательно, чем тысячи раз прыгать по индексу к разбросанным строкам.
- Единственный вариант, если подходящего **индекса нет**.
- На маленьких таблицах часто дешевле индекса — накладные расходы на обход индекса не окупаются.

**`Index Scan`** — находит подходящие записи в индексе, затем по каждой идёт в таблицу за полной строкой:
- Выгоден при **высокой селективности** — когда условие отсекает почти всё и остаётся мало строк.
- Стоимость растёт с числом `heap fetch` (случайных обращений к таблице); поэтому при большом числе совпадений `Index Scan` проигрывает `Seq Scan`.

**`Index Only Scan`** — если покрывающий индекс уже содержит все нужные столбцы, в таблицу ходить не нужно вовсе — это самый быстрый вариант.

**Когда планировщик предпочитает `Seq Scan`:**
- Условие возвращает большую долю строк (порог зависит от соотношения `random_page_cost` / `seq_page_cost`).
- Статистика устарела и планировщик ошибся в оценке — лечится `ANALYZE`.
- Принудительный запрет индексов для эксперимента: `SET enable_indexscan = off;`

## Q23. Что такое `Bitmap Index Scan` и `Index Only Scan`?

**`Bitmap Index Scan`** — промежуточный режим между `Index Scan` и `Seq Scan`, который убирает главный минус `Index Scan` — хаотичные случайные обращения к таблице:

1. Сканирует индекс и строит **битовую карту** (bitmap) страниц, где лежат подходящие строки.
2. `Bitmap Heap Scan` читает эти страницы **в порядке их физического расположения** на диске — то есть почти последовательно, а не вразнобой. Это превращает дорогой случайный ввод-вывод в дешёвый последовательный.

Применяется при **умеренной селективности** — когда строк слишком много для обычного `Index Scan`, но слишком мало, чтобы оправдать чтение всей таблицы. Бонус: bitmap-карты от нескольких индексов можно комбинировать (`BitmapAnd`, `BitmapOr`) — так PostgreSQL использует сразу два индекса в одном запросе.

```
Bitmap Heap Scan on orders
  Recheck Cond: (status = 'open')
  ->  Bitmap Index Scan on idx_orders_status
        Index Cond: (status = 'open')
```

**`Index Only Scan`** читает данные **только из индекса**, минуя таблицу — возможно лишь когда индекс покрывает все нужные столбцы. Но есть нюанс с `MVCC`: индекс не хранит признак видимости версии строки. Чтобы не ходить в таблицу за этим признаком, PostgreSQL сверяется с **visibility map** — если она помечает страницу как «полностью видимую», обращения к таблице не будет. Если же таблица недавно менялась и `VACUUM` не успел обновить map, движок всё-таки заглянет в таблицу — поэтому свежий `VACUUM` важен для эффективности `Index Only Scan`.

## Q24. Что такое `cost` в плане запроса?

**`cost`** — это не время и не байты, а **абстрактная оценка трудозатрат** в условных единицах. За единицу принята стоимость последовательного чтения одной страницы (`seq_page_cost = 1.0`), а всё остальное (случайное чтение, обработка строки, вычисление оператора) выражено относительно неё. Планировщик считает `cost` для каждого варианта плана и выбирает самый дешёвый.

Поэтому `cost` нужен не для абсолютных выводов («медленно/быстро»), а для **сравнения планов между собой** и для понимания, почему планировщик предпочёл один путь другому.

**Параметры, влияющие на стоимость:**
| Параметр | По умолчанию | Описание |
|---------|------------|---------|
| `seq_page_cost` | `1.0` | Стоимость последовательного чтения страницы |
| `random_page_cost` | `4.0` | Стоимость случайного чтения страницы |
| `cpu_tuple_cost` | `0.01` | Стоимость обработки одной строки |
| `cpu_index_tuple_cost` | `0.005` | Стоимость обработки записи индекса |
| `cpu_operator_cost` | `0.0025` | Стоимость вычисления оператора |

Дефолт `random_page_cost = 4.0` рассчитан на HDD, где случайное чтение действительно вчетверо дороже последовательного. На SSD разрыв почти исчезает, поэтому значение снижают до `1.1–2.0` — иначе планировщик переоценивает стоимость индексов и зря выбирает `Seq Scan`.

```sql
SET random_page_cost = 1.1;
```

## Q25. Как работает статистика в PostgreSQL (`pg_statistics`)?

Планировщик не сканирует таблицу, чтобы узнать, сколько строк вернёт условие, — он **оценивает** это по статистике о распределении данных. Хорошая оценка строк → хороший выбор плана; устаревшая статистика → ошибочный план (например, `Seq Scan` вместо индекса). Поэтому свежесть статистики напрямую влияет на производительность.

Статистика обновляется командой `ANALYZE` (вручную) или автоматически процессом `autovacuum`.

```sql
-- Ручной запуск анализа
ANALYZE orders;

-- Посмотреть статистику столбца
SELECT * FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';
```

**Ключевые поля `pg_stats`:**
- `n_distinct` — число уникальных значений (по нему планировщик прикидывает селективность `=`).
- `most_common_vals` — самые частые значения, и `most_common_freqs` — их доли. Нужны для перекошенных распределений: оценка строк для частого значения и для редкого будет разной.
- `histogram_bounds` — границы равночастотной гистограммы для остальных значений; по ним оцениваются диапазонные условия (`>`, `BETWEEN`).

Параметр `default_statistics_target` (по умолчанию `100`) задаёт, насколько детальной будет статистика — сколько частых значений и корзин гистограммы хранить. Для столбцов с большим разнообразием значений и сложными запросами детализацию повышают:

```sql
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
```

## Q26. (!) Какие уровни изоляции транзакций поддерживает PostgreSQL?

PostgreSQL поддерживает все 4 стандартных уровня изоляции `SQL`. Уровень изоляции определяет, какие аномалии параллельных транзакций он допускает: чем строже уровень, тем меньше аномалий, но тем выше шанс конфликтов и откатов. Особенность PostgreSQL — благодаря `MVCC` он защищает строже, чем требует стандарт.

| Уровень | Dirty Read | Non-Repeatable Read | Phantom Read |
|---------|-----------|--------------------|-|
| `READ UNCOMMITTED` | Невозможен¹ | Возможен | Возможен |
| `READ COMMITTED` (по умолч.) | Невозможен | Возможен | Возможен |
| `REPEATABLE READ` | Невозможен | Невозможен | Невозможен² |
| `SERIALIZABLE` | Невозможен | Невозможен | Невозможен |

¹ PostgreSQL не реализует `dirty read` даже на `READ UNCOMMITTED`.  
² За счёт `MVCC` `REPEATABLE READ` в PostgreSQL также предотвращает `phantom read`.

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- ... операции ...
COMMIT;

-- Или через SET
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

**`SERIALIZABLE`** даёт гарантию, что результат параллельных транзакций будет таким же, как при каком-то их последовательном выполнении. Реализован он не через блокировки, а через `SSI` (Serializable Snapshot Isolation): транзакции работают по снимкам, а на коммите PostgreSQL проверяет, не возник ли опасный конфликт. Если возник — одну из транзакций откатывают с ошибкой `SQLSTATE 40001`. Поэтому приложение, работающее на `SERIALIZABLE`, обязано уметь **повторять** транзакцию при таком откате.

## Q27. (!) Как работает `MVCC` в PostgreSQL?

**`MVCC` (Multi-Version Concurrency Control)** решает классическую проблему: как дать читателям и писателям работать одновременно, не мешая друг другу. Ответ PostgreSQL — **не перезаписывать строку на месте, а хранить её версии**. Пока один пишет новую версию, остальные спокойно читают старую.

**Принцип:**
- `UPDATE` не меняет строку in-place: старая версия остаётся и помечается «удалённой» (в `xmax` пишется номер транзакции), а рядом создаётся **новая** версия с новым `xmin`. То же с `DELETE` — версия не стирается, а помечается удалённой.
- Каждая транзакция работает со **снимком** (snapshot): видит только те версии, что были зафиксированы к нужному моменту. За счёт этого читателю не нужны блокировки — он просто смотрит «свою» версию.

**Плюсы:**
- Читатели не блокируют писателей и наоборот → высокий параллелизм.
- Снимок даёт согласованное чтение без блокировок.

**Минусы (обратная сторона версионности):**
- Старые версии накапливаются как **мёртвые кортежи** (`dead tuples`) и занимают место — их периодически убирает `VACUUM`.
- Индексы тоже ссылаются на мёртвые версии, поэтому раздуваются вместе с таблицей.

```sql
-- Посмотреть xmin/xmax
SELECT xmin, xmax, * FROM orders WHERE id = 1;
```

## Q28. Что такое `xmin` и `xmax` в кортежах PostgreSQL?

Это служебные поля, которые `MVCC` хранит в каждой версии строки. Через них PostgreSQL и определяет, какую версию видит конкретная транзакция — по сути это «срок жизни» версии: `xmin` — когда она появилась, `xmax` — когда исчезла.

| Поле | Описание |
|------|---------|
| `xmin` | `XID` транзакции, создавшей кортеж (`INSERT` или `UPDATE`) |
| `xmax` | `XID` транзакции, удалившей или заменившей кортеж (`DELETE` или `UPDATE`) |
| `ctid` | Физический адрес кортежа (`блок`, `смещение`) |

**Как решается видимость версии для транзакции:** версия видна, если она «уже родилась, но ещё не умерла» с точки зрения снимка:
- `xmin` должен быть зафиксирован и попадать в снимок (версия создана видимой транзакцией).
- `xmax` либо пуст/незафиксирован, либо относится к транзакции, не видимой снимку (то есть версия ещё не удалена с точки зрения наблюдателя).

```sql
SELECT xmin, xmax, ctid, id, status FROM orders WHERE id = 1;
```

## Q29. Что такое `phantom read`, `non-repeatable read` и `dirty read`?

Это аномалии, которые могут возникнуть при параллельных транзакциях. Разница между тремя «read»-аномалиями — в том, **что именно** меняется между двумя чтениями одной транзакции:

| Аномалия | Описание |
|----------|---------|
| **Dirty read** | Транзакция читает **незафиксированные** изменения другой — те могут откатиться, и прочитанное окажется «призраком» |
| **Non-repeatable read** | Повторный `SELECT` той же строки даёт другое значение — её успел изменить/удалить чужой зафиксированный `UPDATE`/`DELETE` |
| **Phantom read** | Повторный `SELECT` по тому же условию возвращает **новые строки** — чужой зафиксированный `INSERT` добавил подходящие записи |
| **Serialization anomaly** | Итог параллельных транзакций таков, что его нельзя получить ни при каком их последовательном порядке |

Память: non-repeatable — изменилась **существующая** строка; phantom — появились/исчезли **строки в выборке**.

Защита в PostgreSQL построже стандарта: благодаря `MVCC` даже `READ COMMITTED` полностью исключает `dirty read`, а `REPEATABLE READ` снимает заодно и `phantom read` (по стандарту он там ещё допустим). `SERIALIZABLE` убирает и serialization anomaly.

## Q30. Как работает `SAVEPOINT`?

**`SAVEPOINT`** — это «закладка» внутри транзакции: к ней можно откатиться через `ROLLBACK TO SAVEPOINT`, отменив только то, что сделано после неё, и при этом **не теряя** всю транзакцию целиком. Удобно, когда часть шагов может безопасно провалиться (попытка вставки, расчёт скидки), а остальную работу хочется сохранить.

```sql
BEGIN;

INSERT INTO orders (user_id, total) VALUES (1, 100);

SAVEPOINT before_discount;

UPDATE orders SET total = total * 0.9 WHERE user_id = 1;

-- Отменить только операцию после SAVEPOINT
ROLLBACK TO SAVEPOINT before_discount;

-- Первый INSERT сохранён, UPDATE отменён
COMMIT;
```

Удалить `SAVEPOINT`: `RELEASE SAVEPOINT before_discount;`

## Q31. (!) Зачем нужен `VACUUM` и что такое `dead tuples`?

`VACUUM` нужен как прямое следствие `MVCC`. Поскольку `UPDATE`/`DELETE` не стирают строки, а оставляют старые версии, со временем таблица заполняется **мёртвыми кортежами** (`dead tuples`) — версиями, которые уже не видны ни одной транзакции. `VACUUM` — это уборщик, освобождающий занятое ими место.

**Чем плохо накопление `dead tuples`:**
- Таблица и индексы пухнут (`table bloat`) — занимают больше диска.
- Замедляется `Seq Scan`: чтобы прочитать живые строки, движок вынужден перелопачивать ещё и мёртвые.
- Замедляется `Index Scan`: индексы тоже ссылаются на мёртвые версии.

Важный нюанс: обычный **`VACUUM` не возвращает место операционной системе**. Он лишь помечает пространство мёртвых кортежей как свободное **внутри файла таблицы**, чтобы туда легли новые строки. Файл на диске при этом не уменьшается.

```sql
-- Ручной запуск
VACUUM orders;

-- Посмотреть статистику dead tuples
SELECT relname, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

## Q32. В чём разница между `VACUUM` и `VACUUM FULL`?

Главное различие — что происходит с местом на диске и с блокировками:

| Команда | Поведение |
|---------|---------|
| `VACUUM` | Помечает пространство мёртвых кортежей как свободное внутри таблицы. Не блокирует читателей/писателей |
| `VACUUM FULL` | Переписывает всю таблицу в новый файл, **реально возвращая** место ОС. Устанавливает эксклюзивную блокировку на таблицу |
| `VACUUM ANALYZE` | Выполняет `VACUUM` + обновляет статистику (`ANALYZE`) |

Итог: обычный `VACUUM` лёгкий и неблокирующий, но место ОС не возвращает — он для регулярной уборки. `VACUUM FULL` физически ужимает файл, но берёт `ACCESS EXCLUSIVE`-блокировку, то есть **полностью останавливает работу с таблицей** на всё время перезаписи — на проде так в рабочие часы не делают.

```sql
VACUUM ANALYZE orders;
VACUUM FULL orders;  -- осторожно: блокирует таблицу!
```

**Рекомендация:** когда нужно вернуть место без простоя, вместо `VACUUM FULL` берут расширение `pg_repack` — оно перепаковывает таблицу почти без блокировки.

## Q33. Как работает `AUTOVACUUM` и как его настроить?

**`AUTOVACUUM`** — фоновый процесс, который сам решает, когда запустить `VACUUM` и `ANALYZE`, чтобы вручную это не отслеживать. Он срабатывает по таблице, когда та накопила достаточно мёртвых кортежей относительно своего размера.

Порог не фиксированный, а пропорциональный размеру таблицы: он равен `autovacuum_vacuum_threshold` плюс `autovacuum_vacuum_scale_factor`, умноженный на число живых строк (см. формулу в комментарии к коду ниже).

Из-за множителя `scale_factor` (по умолчанию 0.2 = 20%) большие таблицы убираются слишком редко: 20% от миллиарда строк — это огромный bloat, прежде чем autovacuum проснётся. Поэтому для крупных таблиц `scale_factor` снижают, а `threshold` повышают.

**Ключевые параметры:**

```sql
-- Порог запуска VACUUM = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * n_live_tup
autovacuum_vacuum_threshold = 50       -- минимум dead tuples
autovacuum_vacuum_scale_factor = 0.2   -- 20% от числа живых строк

-- Для больших таблиц лучше снижать scale_factor
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 1000
);
```

**Мониторинг:**
```sql
SELECT relname, last_autovacuum, last_autoanalyze, n_dead_tup,
       autovacuum_count, autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

## Q34. Что такое `table bloat` и как его измерить?

**`Table bloat`** (раздувание) — разрыв между физическим размером таблицы/индекса на диске и объёмом реально нужных, живых данных. Грубо: «таблица занимает 10 GB, а полезных данных в ней на 3 GB — остальное мусор». Причина — те же `dead tuples` и неполностью заполненные страницы, которые `VACUUM` помечает свободными, но файл не сжимает.

Bloat вреден тем, что лишние страницы всё равно читаются с диска и попадают в кэш, вытесняя полезные данные, — отсюда замедление запросов.

```sql
-- Размер таблицы и индексов
SELECT
    relname,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    pg_size_pretty(pg_relation_size(relid)) AS table_size,
    pg_size_pretty(pg_indexes_size(relid)) AS indexes_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

Для детального анализа `bloat` используют расширение `pgstattuple` или запросы из набора `check_postgres`.

## Q35. (!) Какие виды партиционирования поддерживает PostgreSQL?

Партиционирование разбивает одну логическую таблицу на несколько физических кусков (партиций) по значению ключа. Цель — чтобы запросы и обслуживание (`VACUUM`, удаление старых данных) работали с маленькой партицией, а не с гигантской таблицей целиком. Старые данные можно удалять мгновенно — простым `DROP` партиции вместо долгого `DELETE`.

PostgreSQL (с версии 10+) поддерживает **декларативное партиционирование** трёх видов — выбор зависит от природы ключа:

| Тип | Описание | Пример использования |
|-----|---------|---------------------|
| `RANGE` | По диапазону значений | Партиционирование по дате (`created_at`) |
| `LIST` | По списку значений | По стране, статусу, категории |
| `HASH` | По хэшу значения | Равномерное распределение по модулю |

Интуиция выбора: `RANGE` — для непрерывных величин (даты, числовые диапазоны); `LIST` — для дискретного перечня значений (регион, статус); `HASH` — когда естественного разбиения нет, но нужно ровно распределить нагрузку.

```sql
-- RANGE партиционирование по дате
CREATE TABLE orders (
    id BIGSERIAL,
    user_id INT,
    total NUMERIC,
    created_at TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2025 PARTITION OF orders
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

CREATE TABLE orders_2026 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

-- LIST партиционирование
CREATE TABLE orders_by_region (
    id BIGSERIAL,
    region TEXT NOT NULL,
    total NUMERIC
) PARTITION BY LIST (region);

CREATE TABLE orders_ru PARTITION OF orders_by_region FOR VALUES IN ('RU');
CREATE TABLE orders_kz PARTITION OF orders_by_region FOR VALUES IN ('KZ');
```

**Подпартиционирование** (вложенное) также поддерживается: `RANGE + HASH`, `RANGE + LIST` и т. д.

## Q36. Как работает `partition pruning`?

**`Partition pruning`** (отсечение партиций) — это та самая оптимизация, ради которой партиционирование вообще имеет смысл. Если в запросе есть условие на ключ партиционирования, планировщик заранее понимает, что искомые строки физически могут лежать только в некоторых партициях, и **исключает остальные** из плана — их даже не открывают.

```sql
-- Планировщик прочитает только orders_2026
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';
```

**Динамический `pruning`** (PostgreSQL 11+): исключает партиции даже при параметризованных запросах или на этапе выполнения.

Проверить в плане: если партиция не упоминается в `EXPLAIN`, она была отсечена.

## Q37. Когда партиционирование не даёт выигрыша?

Партиционирование помогает не всегда — а при неправильном применении даже вредит. Типичные случаи, когда выигрыша нет:

- **Запрос не фильтрует по ключу партиционирования** — отсечение не срабатывает, и сканируются все партиции (часто медленнее, чем одна большая таблица).
- **Таблица небольшая** — накладные расходы на маршрутизацию строк по партициям перевешивают любую выгоду.
- **Слишком много партиций** (тысячи и больше) — раздувается время планирования каждого запроса.
- **`JOIN`** партиционированной таблицы с обычной без условия по ключу — отсечение опять не работает.
- **Нет глобальных индексов:** уникальный индекс/первичный ключ обязан включать ключ партиционирования; индексы существуют только локально на каждой партиции.

## Q38. (!) Что такое оконные функции и как они работают?

**Оконные функции** считают агрегат по группе строк (окну), но, в отличие от `GROUP BY`, **не схлопывают строки** — каждая исходная строка остаётся в результате, рядом просто появляется вычисленное значение. Это ключевое отличие: `GROUP BY` отдаёт одну строку на группу, а оконная функция — все строки плюс «нарастающий итог», «ранг», «среднее по группе» в дополнительном столбце.

Окно задаётся через `OVER (...)`: `PARTITION BY` делит строки на группы, `ORDER BY` упорядочивает внутри группы, а рамка (`ROWS`/`RANGE`) ограничивает, какие соседние строки участвуют в расчёте.

```sql
SELECT
    user_id,
    order_date,
    total,
    SUM(total) OVER (PARTITION BY user_id ORDER BY order_date) AS running_total,
    AVG(total) OVER (PARTITION BY user_id) AS avg_per_user,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_date DESC) AS rn
FROM orders;
```

**Синтаксис:**
```sql
function_name(...) OVER (
    [PARTITION BY col1, col2]
    [ORDER BY col3 [ASC|DESC]]
    [ROWS|RANGE BETWEEN ... AND ...]
)
```

**Виды функций:**
- **Ранжирование:** `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `NTILE(n)`
- **Смещение:** `LAG()`, `LEAD()`, `FIRST_VALUE()`, `LAST_VALUE()`, `NTH_VALUE()`
- **Агрегатные:** `SUM()`, `AVG()`, `COUNT()`, `MIN()`, `MAX()`

## Q39. Как работают `ROW_NUMBER`, `RANK` и `DENSE_RANK`?

Все три нумеруют строки по `ORDER BY`, но по-разному ведут себя при **одинаковых значениях** — именно это и спрашивают на собеседовании:

| Функция | Описание | Поведение при дублях |
|---------|---------|---------------------|
| `ROW_NUMBER()` | Уникальный порядковый номер | Всегда уникален (произвольный порядок дублей) |
| `RANK()` | Ранг с пропуском при дублях | 1, 2, 2, 4 |
| `DENSE_RANK()` | Ранг без пропуска | 1, 2, 2, 3 |

Запомнить просто: `ROW_NUMBER` дублей «не замечает» и всегда даёт разные номера; `RANK` даёт одинаковым значениям один ранг, но затем **пропускает** следующие (после двух вторых сразу четвёртый); `DENSE_RANK` тоже объединяет дубли, но **не пропускает** номера (после двух вторых — третий).

```sql
SELECT
    name,
    score,
    ROW_NUMBER() OVER (ORDER BY score DESC) AS row_num,
    RANK()       OVER (ORDER BY score DESC) AS rnk,
    DENSE_RANK() OVER (ORDER BY score DESC) AS dense_rnk
FROM leaderboard;
```

**Распространённый паттерн:** топ-N записей на группу:

```sql
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
    FROM orders
) t
WHERE rn = 1; -- последний заказ каждого пользователя
```

## Q40. Как работают `LAG` и `LEAD`?

`LAG` и `LEAD` дают доступ к значению из **соседней строки** окна, не прибегая к самосоединению таблицы саму с собой. Это основной инструмент для сравнения «текущее vs предыдущее»: разница с прошлым периодом, изменение статуса, дельта между замерами.

- **`LAG(col, offset, default)`** — значение из строки **выше** на `offset` позиций (по умолчанию `offset = 1`); `default` подставляется, когда такой строки нет (первая строка окна).
- **`LEAD(col, offset, default)`** — то же, но из строки **ниже** на `offset` позиций.

```sql
SELECT
    order_date,
    total,
    LAG(total, 1, 0)  OVER (PARTITION BY user_id ORDER BY order_date) AS prev_total,
    LEAD(total, 1, 0) OVER (PARTITION BY user_id ORDER BY order_date) AS next_total,
    total - LAG(total) OVER (PARTITION BY user_id ORDER BY order_date) AS diff_from_prev
FROM orders;
```

## Q41. Как использовать `SUM OVER` и скользящие агрегаты?

Оконные агрегаты (`SUM`, `AVG` с `OVER`) дают то, чего не умеет обычный `GROUP BY`: считать накопительные и скользящие значения, сохраняя при этом каждую строку. Поведение определяет **рамка окна** (`frame`):

- **Без `ORDER BY`** агрегат берётся по всей партиции — одно значение для всей группы.
- **С `ORDER BY`** по умолчанию рамка — «от начала окна до текущей строки», что и даёт **нарастающий итог**.
- **Явная рамка** `ROWS BETWEEN N PRECEDING AND CURRENT ROW` ограничивает расчёт фиксированным числом последних строк — это **скользящее окно**.

```sql
-- Нарастающий итог (running total)
SELECT
    order_date,
    total,
    SUM(total) OVER (ORDER BY order_date) AS running_total
FROM orders;

-- Скользящее среднее за 7 дней
SELECT
    order_date,
    total,
    AVG(total) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS moving_avg_7d
FROM daily_revenue;

-- Итог в рамках группы (без ORDER BY — агрегат по всей группе)
SELECT
    user_id,
    total,
    SUM(total) OVER (PARTITION BY user_id) AS user_total
FROM orders;
```

**Разница `ROWS` и `RANGE`** (частый вопрос):
- `ROWS BETWEEN N PRECEDING AND CURRENT ROW` — фиксированное **число строк** (ровно `N` соседей по позиции).
- `RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW` — диапазон **по значению** ключа сортировки (все строки в пределах 7 дней); число строк при этом может быть любым.

## Q42. (!) Что такое `CTE` и чем он отличается от подзапроса?

**`CTE` (Common Table Expression)** — это именованный промежуточный результат, объявленный в блоке `WITH` и доступный в основном запросе по имени. По сути «временная вьюшка на один запрос»: сложную логику разбивают на читаемые именованные шаги вместо вложенных подзапросов-«матрёшек».

```sql
WITH active_users AS (
    SELECT id, name FROM users WHERE status = 'active'
),
recent_orders AS (
    SELECT user_id, SUM(total) AS total_spent
    FROM orders
    WHERE created_at > NOW() - INTERVAL '30 days'
    GROUP BY user_id
)
SELECT u.name, ro.total_spent
FROM active_users u
JOIN recent_orders ro ON u.id = ro.user_id
ORDER BY ro.total_spent DESC;
```

**`CTE` против подзапроса.** Главное различие — не в читаемости, а в том, как ведёт себя оптимизатор, и это любимый «версионный» вопрос:

| Характеристика | `CTE` | Подзапрос |
|---------------|-------|-----------|
| Читаемость | Высокая, можно именовать | Может быть сложным при вложении |
| Повторное использование | Да (одно определение — несколько ссылок) | Нет |
| Оптимизация (PostgreSQL < 12) | `CTE` — «забор оптимизации» (materializes) | Встраивается в план |
| Оптимизация (PostgreSQL 12+) | По умолчанию встраивается, если не рекурсивный и без побочных эффектов | Встраивается |
| `MATERIALIZED` / `NOT MATERIALIZED` | Явное управление материализацией | Нет |

Суть версионного нюанса: **до PostgreSQL 12** `CTE` всегда материализовался — выполнялся отдельно, результат складывался во временную структуру, и планировщик не мог «протолкнуть» внешние условия внутрь `CTE`. Это работало как «оптимизационный забор» и иногда замедляло запросы. **С версии 12** обычный `CTE` по умолчанию **встраивается** в план (как подзапрос), а старое поведение при необходимости включают вручную через `MATERIALIZED`.

```sql
-- Принудительная материализация (PostgreSQL 12+)
WITH stats AS MATERIALIZED (
    SELECT AVG(total) AS avg_total FROM orders
)
SELECT * FROM orders, stats WHERE total > stats.avg_total;
```

## Q43. (!) Как работают рекурсивные `CTE`?

**Рекурсивный `CTE`** (`WITH RECURSIVE`) — единственный способ в обычном `SQL` обойти данные неизвестной глубины: дерево категорий, цепочку подчинённости, граф связей. Запрос ссылается сам на себя и шагает по уровням, пока не упрётся в конец.

```sql
-- Обход иерархии сотрудников
WITH RECURSIVE emp_hierarchy AS (
    -- Базовый случай: корневые узлы
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Рекурсивный шаг
    SELECT e.id, e.name, e.manager_id, eh.depth + 1
    FROM employees e
    JOIN emp_hierarchy eh ON e.manager_id = eh.id
)
SELECT id, name, depth FROM emp_hierarchy ORDER BY depth, name;
```

**Как это работает по шагам:**
1. **Базовый запрос** — стартовые строки (корни дерева), выполняется один раз без рекурсии.
2. **`UNION ALL`** соединяет базовую часть с рекурсивной.
3. **Рекурсивный запрос** ссылается на имя самого `CTE` и на каждой итерации берёт строки, найденные на предыдущем шаге, добавляя их «детей».

Движок повторяет шаг 3 снова и снова, пока рекурсивная часть не вернёт пустой результат, — тогда обход завершён.

**Подводный камень:** если в данных есть цикл (например, сотрудник косвенно числится своим же руководителем), `WITH RECURSIVE` зациклится. Защита — ограничить глубину или отслеживать пройденный путь:

```sql
WHERE eh.depth < 10
```

## Q44. (!) Что такое `streaming replication` в PostgreSQL?

**`Streaming replication`** — физическая репликация, при которой первичный сервер (`primary`) практически в реальном времени передаёт поток `WAL`-записей на реплики (`standby`) по TCP. Реплика проигрывает у себя те же `WAL`-записи и получает побайтовую копию `primary`. Поскольку передаётся уже существующий журнал, накладные расходы минимальны.

**Режимы синхронизации (`synchronous_commit`)** определяют, как далеко должна «доехать» запись, прежде чем клиент получит подтверждение коммита. Это прямой компромисс между задержкой и риском потери данных — от полностью асинхронного до подтверждения применения на реплике:

| Режим `synchronous_commit` | Описание |
|--------------------------|---------|
| `off` | Возврат клиенту до записи `WAL` на диск (риск потери данных) |
| `local` | Запись на диск `primary`, без ожидания реплики |
| `remote_write` | Ожидание записи `WAL` на диск реплики (без `fsync`) |
| `remote_apply` | Ожидание применения изменений на реплике |
| `on` | Синхронный: ожидание `fsync` на реплике |

Чем строже режим, тем выше гарантия сохранности (после коммита данные точно на реплике), но тем больше задержка каждой записи — на `remote_apply` коммит ждёт, пока реплика реально применит изменение.

**Настройка на `primary`:**

```sql
-- postgresql.conf
wal_level = replica
max_wal_senders = 5
```

**Настройка на `standby`:**

```
# recovery.conf / postgresql.conf (PG 12+)
primary_conninfo = 'host=primary-host port=5432 user=replication_user'
```

Дополнительный бонус: пока реплика принимает `WAL`, её можно использовать для **read-only** запросов (`hot standby`) — так разгружают `primary`, отправляя отчёты и аналитику на реплику.

## Q45. В чём разница между физической и логической репликацией?

Разница в **уровне абстракции, что передаётся**. Физическая репликация копирует низкоуровневые изменения блоков (через `WAL`) — получается точный двойник всей базы. Логическая передаёт изменения как **логические операции над строками** (`INSERT`/`UPDATE`/`DELETE`) по выбранным таблицам — то есть «что произошло» вместо «какие байты поменялись».

Из этого следует всё остальное: точная копия требует одинаковой версии и платформы и реплицирует базу целиком (физическая), тогда как логическая гибче — работает между разными версиями, выборочно по таблицам, и потому годится для миграций и `CDC`, но не даёт побайтового дубля.

| Характеристика | Физическая репликация | Логическая репликация |
|---------------|----------------------|----------------------|
| Единица | Блоки данных (`WAL`) | Строки (`INSERT`/`UPDATE`/`DELETE`) |
| Версия PostgreSQL | Должна совпадать | Может отличаться |
| Платформа | Должна совпадать | Может отличаться |
| Избирательность | Вся база данных | Выбранные таблицы |
| Применение | DR, read-реплики | Миграции, разнородные БД, CDC |

**Логическая репликация** (PostgreSQL 10+): работает через **Publication** (на primary) и **Subscription** (на replica).

```sql
-- На primary
CREATE PUBLICATION my_pub FOR TABLE orders, users;

-- На standby
CREATE SUBSCRIPTION my_sub
CONNECTION 'host=primary dbname=mydb user=repuser'
PUBLICATION my_pub;
```

## Q46. Что такое `replication slot` и зачем он нужен?

**`Replication slot`** решает конкретную проблему отстающей реплики. Обычно `primary` свободно удаляет старые `WAL`-сегменты после `checkpoint`. Но если реплика на момент удаления ещё не успела их получить, она безнадёжно отстанет и потребует полного пересоздания. Слот заставляет `primary` **придерживать** `WAL` до тех пор, пока конкретная реплика (или подписчик логической репликации) их не подтвердит.

```sql
-- Посмотреть слоты
SELECT * FROM pg_replication_slots;

-- Создать физический слот
SELECT pg_create_physical_replication_slot('standby1_slot');

-- Создать логический слот
SELECT pg_create_logical_replication_slot('my_slot', 'pgoutput');
```

**Подводный камень (обратная сторона):** раз слот не даёт удалять `WAL`, то «мёртвый» слот опаснее всего. Если реплика навсегда отключилась, а слот забыли удалить, `WAL` будет накапливаться без предела и **заполнит диск** `primary` — частая причина инцидентов. Поэтому слоты обязательно мониторят:

```sql
SELECT slot_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots;
```

## Q47. Как работает `full-text search` в PostgreSQL?

PostgreSQL умеет полноценный полнотекстовый поиск «из коробки», без внешнего движка вроде Elasticsearch. В его основе два типа: `TSVECTOR` — нормализованное представление текста (слова приведены к основам, удалены стоп-слова), а `TSQUERY` — поисковый запрос. Оператор `@@` проверяет, удовлетворяет ли документ запросу.

Ключевая идея — нормализация: текст и запрос приводятся к одной форме (леммы), поэтому «прыгает», «прыгал», «прыгать» совпадают. За правила нормализации отвечает указанная конфигурация языка (`'russian'`).

```sql
-- TSVECTOR: нормализованный вектор слов
SELECT to_tsvector('russian', 'Быстрая коричневая лиса прыгает');

-- TSQUERY: запрос
SELECT to_tsquery('russian', 'лиса & прыгает');

-- Поиск
SELECT title FROM articles
WHERE to_tsvector('russian', body) @@ to_tsquery('russian', 'postgresql & индексы');

-- Ранжирование результатов
SELECT title, ts_rank(to_tsvector('russian', body), query) AS rank
FROM articles, to_tsquery('russian', 'postgresql') query
WHERE to_tsvector('russian', body) @@ query
ORDER BY rank DESC;
```

**Рекомендация:** вычислять `to_tsvector` на лету при каждом запросе дорого. На практике `TSVECTOR` материализуют в отдельном (часто генерируемом) столбце и вешают на него `GIN`-индекс — тогда поиск идёт по индексу, а не сканирует таблицу:

```sql
ALTER TABLE articles ADD COLUMN tsv TSVECTOR
    GENERATED ALWAYS AS (to_tsvector('russian', title || ' ' || body)) STORED;

CREATE INDEX idx_articles_tsv ON articles USING GIN (tsv);
```

## Q48. (!) Какие операторы и функции доступны для `JSONB`?

Операторы `JSONB` делятся на две группы, и их легко перепутать на собеседовании: одни **извлекают** данные, другие **ищут/фильтруют**.

**Операторы доступа (извлечение).** Ключевое — разница между «стрелками»: одинарная (`->`, `#>`) возвращает `JSON`, двойная (`->>`, `#>>`) — `TEXT`. Двойная нужна, когда значение сравнивают со строкой или приводят к числу:

| Оператор | Описание | Пример |
|----------|---------|--------|
| `->` | Получить поле как `JSON` | `payload->'name'` |
| `->>` | Получить поле как `TEXT` | `payload->>'name'` |
| `#>` | Путь как `JSON` | `payload#>'{address,city}'` |
| `#>>` | Путь как `TEXT` | `payload#>>'{address,city}'` |

**Операторы поиска (фильтрация).** Именно они умеют использовать `GIN`-индекс, поэтому для быстрых запросов по `JSONB` фильтруют через `@>`/`?`, а не через `->>` со сравнением:

| Оператор | Описание |
|----------|---------|
| `@>` | Содержит (правый в левом) |
| `<@` | Содержится (левый в правом) |
| `?` | Ключ существует |
| `?\|` | Хотя бы один ключ из массива существует |
| `?&` | Все ключи из массива существуют |

```sql
-- Поиск по вложенному полю
SELECT * FROM events WHERE payload @> '{"event_type": "purchase"}';

-- Проверка существования ключа
SELECT * FROM events WHERE payload ? 'discount_code';

-- Модификация JSONB
UPDATE events
SET payload = payload || '{"processed": true}'
WHERE id = 1;

-- Удаление ключа
UPDATE events SET payload = payload - 'temp_field' WHERE id = 1;

-- jsonb_set: обновить вложенное поле
UPDATE events
SET payload = jsonb_set(payload, '{user,name}', '"Alice"')
WHERE id = 1;
```

## Q49. (!) Что такое `PgBouncer` и зачем он нужен?

**`PgBouncer`** — лёгкий пул соединений-посредник между приложением и PostgreSQL. Он нужен из-за самой архитектуры PostgreSQL: на каждое соединение создаётся отдельный процесс ОС (~5–10 MB памяти плюс `fork()`). Поэтому несколько тысяч прямых соединений съедают память и деградируют сервер, даже если большинство из них простаивает.

**Проблема без пула:**
- Каждое соединение — отдельный тяжёлый `backend`-процесс.
- Установка соединения стоит времени (~1–5 мс) и `fork()` на каждом подключении.
- Веб-приложения держат сотни «полуспящих» соединений — память тратится, а работа почти не идёт.

**Как помогает `PgBouncer`:** приложения подключаются не к базе напрямую, а к `PgBouncer`, который держит небольшой пул реальных соединений к PostgreSQL и **мультиплексирует** на него тысячи клиентских. Так тысячи клиентов делят десятки реальных backend-процессов.

```ini
# pgbouncer.ini
[databases]
mydb = host=localhost port=5432 dbname=mydb

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
```

## Q50. Какие режимы пулинга поддерживает `PgBouncer`?

Режимы отличаются тем, **как часто реальное соединение возвращается в пул** — а значит, насколько агрессивно оно переиспользуется. Чем агрессивнее, тем выше экономия, но тем больше ограничений на то, что можно держать «привязанным» к соединению:

| Режим | Описание | Ограничения |
|-------|---------|------------|
| `session` | Соединение держится на время сессии клиента | Минимальная экономия |
| `transaction` | Соединение возвращается в пул после каждой транзакции | Нельзя использовать `SET`, `LISTEN`, `PREPARE` между транзакциями |
| `statement` | Соединение возвращается после каждого оператора | Нельзя использовать многооператорные транзакции |

Логика ограничений проста: если соединение уходит в пул после транзакции, нельзя рассчитывать, что заданный ранее `SET` или подготовленный `PREPARE` «доживёт» до следующей транзакции — её обслужит уже другое физическое соединение.

**Рекомендация:** в большинстве случаев — `transaction`: лучший баланс экономии и совместимости. `session` берут, только если приложению критичны настройки уровня сессии или `LISTEN/NOTIFY`. `statement` — нишевый, в основном для пула под одиночные запросы.

## Q51. (!) Какие типы блокировок существуют в PostgreSQL?

Блокировки в PostgreSQL работают на двух уровнях, и важно понимать, зачем нужен каждый. Их редко берут вручную — обычно их неявно ставят сами команды (`SELECT`, `UPDATE`, `DDL`), а смысл системы в том, чтобы несовместимые операции не выполнялись одновременно над одним объектом.

**Блокировки таблиц (`table-level locks`)** защищают саму структуру таблицы. Ключевая идея таблицы конфликтов: «слабые» блокировки от `SELECT`/`DML` совместимы между собой (поэтому много запросов идут параллельно), а `DDL` берёт `ACCESS EXCLUSIVE`, который конфликтует со всем, — поэтому `ALTER TABLE` или `DROP` ждут завершения активных запросов и блокируют новые.

| Блокировка | Команды | Конфликтует с |
|-----------|---------|--------------|
| `ACCESS SHARE` | `SELECT` | `ACCESS EXCLUSIVE` |
| `ROW SHARE` | `SELECT FOR UPDATE/SHARE` | `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE` | `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY` | — |
| `SHARE` | `CREATE INDEX` | `ROW EXCLUSIVE` и выше |
| `SHARE ROW EXCLUSIVE` | — | `ROW EXCLUSIVE` и выше |
| `EXCLUSIVE` | — | Всё кроме `ACCESS SHARE` |
| `ACCESS EXCLUSIVE` | `DROP TABLE`, `TRUNCATE`, `ALTER TABLE` | Всё |

**Блокировки строк (`row-level locks`)** защищают отдельные строки при изменении, не мешая работе с остальными строками таблицы. Их явно запрашивают через `SELECT ... FOR ...`, и они идут от самой строгой к самой мягкой:
- `FOR UPDATE` — эксклюзивная блокировка строки (для «прочитать и тут же изменить»).
- `FOR NO KEY UPDATE` — слабее `FOR UPDATE`: не конфликтует с `FOR KEY SHARE`, используется при изменении неключевых полей.
- `FOR SHARE` — разделяемая: несколько транзакций могут читать строку, но никто не изменит, пока блокировки держатся.
- `FOR KEY SHARE` — самая мягкая, нужна в основном для проверки внешних ключей.

Важно: благодаря `MVCC` эти блокировки **не мешают читателям** — обычный `SELECT` без `FOR ...` видит свою версию строки независимо от того, кто её заблокировал.

```sql
-- Посмотреть активные блокировки
SELECT pid, locktype, relation::regclass, mode, granted
FROM pg_locks
WHERE NOT granted;
```

## Q52. Что такое `deadlock` и как PostgreSQL его обнаруживает?

**`Deadlock`** (взаимоблокировка) — циклическое ожидание: транзакция A ждёт блокировку, которую держит B, а B ждёт ту, что держит A. Ни одна не отпустит своё и не дождётся чужого — без вмешательства они зависнут навсегда.

```
Транзакция A: держит блокировку строки 1, ждёт строку 2
Транзакция B: держит блокировку строки 2, ждёт строку 1
```

PostgreSQL не предотвращает deadlock заранее, а **обнаруживает** его постфактум. Транзакция, прождавшая блокировку дольше `deadlock_timeout` (по умолчанию `1s`), запускает проверку графа ожидания. Если в графе нашёлся цикл — PostgreSQL разрывает его, принудительно откатывая одну из транзакций-участниц с ошибкой `ERROR: deadlock detected`. Остальные после этого продолжают работу.

**Как предотвращать (это во многом задача приложения):**
- **Брать блокировки в едином порядке** во всех транзакциях — главное правило: если все блокируют строки в одинаковой последовательности, цикл невозможен.
- Явно и последовательно использовать `SELECT ... FOR UPDATE`.
- Держать транзакции короткими — чем меньше блокировок одновременно, тем ниже шанс пересечения.
- Где уместно — `NOWAIT` (упасть сразу вместо ожидания) или `SKIP LOCKED` (пропустить занятые строки, паттерн очередей задач).

```sql
-- Попытка захватить блокировку без ожидания
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;

-- Пропустить заблокированные строки
SELECT * FROM jobs WHERE status = 'pending' FOR UPDATE SKIP LOCKED LIMIT 1;
```

## Q53. Какие ключевые параметры конфигурации влияют на производительность?

Эти параметры удобно сгруппировать по тому, на что они влияют: память, оценки планировщика, фоновые процессы и логирование. Самые важные — настройки памяти, потому что они напрямую решают, сколько работы пойдёт в RAM, а сколько уйдёт на диск.

| Параметр | Рекомендация | Описание |
|---------|-------------|---------|
| `shared_buffers` | 25% RAM | Кэш страниц данных |
| `effective_cache_size` | 75% RAM | Подсказка планировщику об ОС-кэше |
| `work_mem` | 4–64 MB | Память для сортировки/хэш-операций на запрос |
| `maintenance_work_mem` | 256–1024 MB | Память для `VACUUM`, `CREATE INDEX` |
| `max_connections` | 100–200 | Максимум соединений (лучше с `PgBouncer`) |
| `wal_buffers` | 16–64 MB | Буфер `WAL` в памяти |
| `random_page_cost` | 1.1–2.0 для SSD | Относительная стоимость случайного чтения |
| `effective_io_concurrency` | 200 для SSD | Параллелизм ввода-вывода |
| `checkpoint_completion_target` | 0.9 | Сглаживание нагрузки `checkpoint` |
| `autovacuum_vacuum_cost_delay` | 2ms | Задержка `autovacuum` для снижения нагрузки |
| `log_min_duration_statement` | 1000 (мс) | Логировать медленные запросы |

Главный подвох — `work_mem`: это лимит **на каждую сортировку/хэш в каждом запросе**, а не на всю систему. Сложный запрос с несколькими сортировками да помноженный на сотни соединений может суммарно затребовать память кратно больше указанного значения — поэтому его не задирают бездумно. Превышение `work_mem` означает, что сортировка «проливается» на диск (медленно).

## Q54. Как анализировать медленные запросы?

Подход двухуровневый: сперва найти **какие** запросы медленные, затем понять **почему** конкретный из них тормозит. Для первого служат логи и `pg_stat_statements`, для второго — `EXPLAIN ANALYZE`.

**1. Включить логирование медленных запросов** — самый простой способ поймать «долгоиграющие» запросы по факту:

```sql
-- postgresql.conf
log_min_duration_statement = 1000  -- запросы дольше 1 секунды
log_line_prefix = '%t [%p] %d %u '
```

**2. Использовать `pg_stat_statements`** — расширение агрегирует статистику по нормализованным запросам. Незаменимо, чтобы найти не разовый тормоз, а запрос, который сам по себе быстрый, но выполняется так часто, что даёт основную нагрузку:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Топ-10 запросов по суммарному времени
SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- Сбросить статистику
SELECT pg_stat_statements_reset();
```

**3. Анализировать конкретный запрос** через `EXPLAIN ANALYZE` — теперь, найдя проблемный запрос, разбираем его план: где `Seq Scan` вместо индекса, где ошибка в оценке строк, где лишняя сортировка:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT ...;
```

**4. Проверить `pg_stat_activity`** — посмотреть, что происходит **прямо сейчас**: какие запросы выполняются долго и не ждут ли они блокировку (`wait_event`):

```sql
SELECT pid, query, state, wait_event_type, wait_event, now() - query_start AS duration
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY duration DESC;
```

## Q55. Какие популярные расширения PostgreSQL стоит знать?

Одна из сильных сторон PostgreSQL — расширяемость: функциональность добавляют расширениями (`CREATE EXTENSION`) без патчинга ядра. На собеседовании достаточно знать назначение самых ходовых — особенно `pg_stat_statements` (диагностика) и `pg_trgm` (поиск по подстроке).

| Расширение | Назначение |
|-----------|-----------|
| `pg_stat_statements` | Статистика выполнения SQL-запросов |
| `pg_trgm` | Поиск по подстроке (`LIKE '%term%'`), `GIN`/`GiST` |
| `PostGIS` | Геопространственные данные и функции |
| `uuid-ossp` / `gen_random_uuid()` | Генерация `UUID` (встроена с PG 13) |
| `hstore` | Хранилище пар ключ-значение |
| `pgcrypto` | Функции шифрования и хэширования |
| `tablefunc` | `crosstab` — сводные таблицы |
| `pg_partman` | Автоматическое управление партиционированием |
| `timescaledb` | Time-series данные на основе PostgreSQL |
| `pg_repack` | Перепаковка таблиц без длительной блокировки (альтернатива `VACUUM FULL`) |
| `pgaudit` | Аудит SQL-операций |
| `pg_bouncer` | Пул соединений (отдельный процесс, не расширение) |

```sql
-- Установить расширение
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Посмотреть установленные расширения
SELECT name, default_version, installed_version, comment
FROM pg_available_extensions
WHERE installed_version IS NOT NULL;
```
