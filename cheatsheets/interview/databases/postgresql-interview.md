# Вопросы на собеседовании: `PostgreSQL`

Подробные ответы по `PostgreSQL`: архитектура, типы данных, индексы, `EXPLAIN`, транзакции, `MVCC`, `VACUUM`, партиционирование, оконные функции, `CTE`, репликация, `full-text search`, `JSONB`, `PgBouncer`, блокировки, производительность, расширения.

Краткое введение: **PostgreSQL** — объектно-реляционная СУБД с открытым кодом, известная надёжностью, расширяемостью и полным соответствием стандарту `SQL`. На собеседованиях проверяют понимание внутреннего устройства (процессы, `WAL`, `shared buffers`), умение читать планы запросов (`EXPLAIN ANALYZE`), знание индексов, уровней изоляции и типичных приёмов оптимизации.

## Q1. (!) Какова архитектура процессов PostgreSQL?

PostgreSQL использует **мультипроцессную архитектуру**: каждое клиентское соединение обслуживается отдельным серверным процессом (`backend process`). Главные компоненты:

| Процесс | Назначение |
|---------|-----------|
| `postmaster` | Главный процесс, принимает входящие соединения, порождает дочерние процессы |
| `backend` | Один на соединение, выполняет запросы клиента |
| `checkpointer` | Записывает грязные страницы из `shared_buffers` на диск при `checkpoint` |
| `background writer` | Упреждающая запись грязных страниц, снижает нагрузку на `checkpoint` |
| `WAL writer` | Сбрасывает буферы `WAL` на диск |
| `autovacuum launcher` | Запускает рабочие процессы `autovacuum` |
| `stats collector` | Собирает статистику использования таблиц и индексов |
| `wal sender/receiver` | Репликация: отправка/приём WAL на реплику |

**Shared memory** содержит: `shared_buffers` (кэш страниц данных), `WAL buffers`, `lock table`, кэш планов и другое.

```sql
-- Посмотреть активные серверные процессы
SELECT pid, usename, application_name, state, query
FROM pg_stat_activity
WHERE state <> 'idle';
```

> [!mcq]
> - [ ] PostgreSQL использует многопоточную архитектуру: все соединения обслуживаются потоками одного процесса `postmaster`. | PostgreSQL использует именно мультипроцессную архитектуру — каждое соединение порождает отдельный `backend`-процесс через `fork()`. Многопоточная модель применяется в других СУБД, например MySQL.
> - [x] PostgreSQL использует мультипроцессную архитектуру: каждое клиентское соединение обслуживается отдельным серверным процессом `backend`. | Верно. `postmaster` принимает соединения и порождает дочерние `backend`-процессы. Кроме `backend` работают вспомогательные процессы: `checkpointer`, `background writer`, `WAL writer`, `autovacuum launcher`.
> - [ ] PostgreSQL использует мультипроцессную архитектуру: все соединения обслуживаются одним процессом `backend` через мультиплексирование. | Один `backend`-процесс обслуживает ровно одно клиентское соединение. Мультиплексирование нескольких соединений одним процессом — это задача пул-менеджеров вроде PgBouncer, но не самого PostgreSQL.
> - [ ] PostgreSQL использует мультипроцессную архитектуру: `postmaster` сам обрабатывает запросы, а `backend` процессы нужны только для репликации. | `postmaster` только принимает входящие соединения и управляет жизненным циклом дочерних процессов. Выполнение запросов клиентов — исключительно задача `backend`-процессов.

## Q2. Что такое `shared_buffers` и как он влияет на производительность?

**`shared_buffers`** — общий кэш страниц данных в памяти, разделяемый между всеми серверными процессами. Прежде чем читать данные с диска, PostgreSQL проверяет, есть ли нужная страница в `shared_buffers`.

**Рекомендации по настройке:**
- Типичное значение: **25% RAM** для выделенного сервера (но не более 8–16 GB, так как ОС-кэш (`page cache`) тоже важен).
- Увеличение `shared_buffers` снижает число операций дискового ввода-вывода.
- Совместно работает с `effective_cache_size` (подсказка планировщику о размере ОС-кэша).

```sql
-- Посмотреть текущие значения
SHOW shared_buffers;
SHOW effective_cache_size;

-- Статистика попаданий в кэш (должна быть > 99%)
SELECT sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) AS cache_hit_ratio
FROM pg_statio_user_tables;
```

> [!mcq]
> - [ ] Типичное рекомендуемое значение `shared_buffers` для выделенного PostgreSQL-сервера составляет 75% RAM. | 75% RAM — слишком много для `shared_buffers`. ОС-кэш (`page cache`) тоже важен для производительности, и при таком соотношении на него останется слишком мало памяти.
> - [x] Типичное рекомендуемое значение `shared_buffers` для выделенного PostgreSQL-сервера составляет 25% RAM. | Верно. Значение 25% RAM — стандартная рекомендация. Остальная память используется ОС-кэшем, `work_mem` и другими нуждами. `effective_cache_size` (подсказка планировщику) обычно выставляют в ~75% RAM.
> - [ ] Типичное рекомендуемое значение `shared_buffers` для выделенного PostgreSQL-сервера составляет 10% RAM. | 10% RAM занижено и не даст достаточного кэширования для большинства рабочих нагрузок. Стандартная рекомендация — 25% RAM для выделенного сервера.
> - [ ] Типичное рекомендуемое значение `shared_buffers` для выделенного PostgreSQL-сервера составляет 50% RAM. | 50% RAM избыточно для `shared_buffers`. При таком значении ОС-кэш получает меньше памяти, что снижает эффективность кэширования на уровне операционной системы.

## Q3. (!) Что такое `WAL` и зачем он нужен?

**`WAL` (Write-Ahead Log)** — журнал предзаписи: все изменения данных сначала записываются в `WAL`-файлы на диск, и только потом применяются к страницам данных.

**Зачем:**
- **Надёжность (durability):** при сбое базу можно восстановить из `WAL`, проиграв журнал с последнего `checkpoint`.
- **Производительность:** последовательная запись в журнал быстрее случайных операций записи страниц данных.
- **Репликация:** `WAL`-сегменты отправляются на реплики (`streaming replication`).
- **Point-in-Time Recovery (PITR):** архивированные `WAL`-файлы позволяют восстановить базу на произвольный момент времени.

**Ключевые параметры:**
| Параметр | Описание |
|---------|---------|
| `wal_level` | Уровень детализации: `minimal`, `replica`, `logical` |
| `synchronous_commit` | Синхронная/асинхронная запись: `on`, `off`, `local`, `remote_write`, `remote_apply` |
| `wal_compression` | Сжатие WAL-сегментов |
| `archive_mode` | Включить архивирование WAL |

```sql
SHOW wal_level;
SHOW synchronous_commit;
```

> [!mcq]
> - [x] `WAL` обеспечивает durability: изменения сначала пишутся в журнал, и при сбое база восстанавливается проигрыванием журнала с последнего checkpoint. | Верно. Это классический Write-Ahead Logging: журнал фиксируется до применения изменений в data-файлы. Также используется для репликации и PITR.
> - [ ] `WAL` обеспечивает durability: изменения сначала пишутся в data-файлы, а затем дублируются в журнал для архивации. | Порядок обратный: сначала `WAL`, потом data-файлы. Иначе при сбое между записью данных и журнала восстановление было бы невозможно.
> - [ ] `WAL` обеспечивает durability: изменения пишутся напрямую в data-файлы, а журнал ведётся только для репликации на standby. | Репликация — лишь одна из задач `WAL`. Главная — надёжность: без `WAL` crash recovery невозможен.
> - [ ] `WAL` обеспечивает durability: изменения пишутся в `shared_buffers` и флашатся на диск при каждом commit без отдельного журнала. | Без отдельного журнала случайная запись страниц данных была бы слишком дорогой и не гарантировала бы консистентность при частичной записи блока.

## Q4. Как работает `checkpoint` в PostgreSQL?

**`Checkpoint`** — точка согласованности: PostgreSQL сбрасывает все «грязные» страницы (`dirty pages`) из `shared_buffers` на диск и записывает отметку в `WAL`. При восстановлении после сбоя достаточно воспроизвести `WAL` только начиная с последнего `checkpoint`.

**Параметры:**
- `checkpoint_timeout` (по умолчанию `5min`) — максимальный интервал между `checkpoint`.
- `max_wal_size` — размер накопленного `WAL`, при превышении которого принудительно инициируется `checkpoint`.
- `checkpoint_completion_target` (по умолчанию `0.9`) — доля периода `checkpoint_timeout`, в течение которой допускается размазывать запись, чтобы снизить пиковую нагрузку на ввод-вывод.

> [!mcq]
> - [ ] Во время `checkpoint` PostgreSQL сбрасывает все грязные страницы из `WAL`-буферов в data-файлы и удаляет `WAL`-сегменты до checkpoint. | Грязные страницы сбрасываются из `shared_buffers`, а не из `WAL`-буферов. `WAL`-сегменты до чекпойнта могут удаляться, но это побочный эффект, а не суть операции.
> - [x] Во время `checkpoint` PostgreSQL сбрасывает все грязные страницы из `shared_buffers` на диск и записывает отметку в `WAL`. | Верно. После чекпойнта для восстановления достаточно проиграть `WAL` начиная от отметки. Параметр `checkpoint_completion_target` размазывает нагрузку во времени.
> - [ ] Во время `checkpoint` PostgreSQL переписывает все таблицы, возвращая ОС освобождённое место от dead tuples. | Это описание `VACUUM FULL`. `Checkpoint` не трогает dead tuples и не переписывает таблицы.
> - [ ] Во время `checkpoint` PostgreSQL блокирует все транзакции до завершения сброса страниц на диск. | `Checkpoint` не блокирует транзакции. Благодаря `checkpoint_completion_target` запись размазывается во времени и выполняется в фоне.

## Q5. Что такое `pg_hba.conf` и для чего он используется?

**`pg_hba.conf`** (`host-based authentication`) — файл конфигурации аутентификации клиентов. Каждая строка описывает правило: тип соединения, база данных, пользователь, адрес клиента и метод аутентификации.

```
# TYPE  DATABASE  USER    ADDRESS         METHOD
host    mydb      myuser  192.168.1.0/24  md5
local   all       all                     peer
host    all       all     0.0.0.0/0       scram-sha-256
```

**Методы аутентификации:** `trust`, `peer`, `md5`, `scram-sha-256`, `ldap`, `cert`, `radius`.

> [!mcq]
> - [ ] `pg_hba.conf` описывает размещение табличных пространств на дисках и их квоты. | Табличные пространства настраиваются через SQL-команды `CREATE TABLESPACE` и представление `pg_tablespace`. `pg_hba.conf` к этому не имеет отношения.
> - [ ] `pg_hba.conf` содержит список зарегистрированных пользователей и их хэши паролей. | Пользователи и их пароли хранятся в системном каталоге `pg_authid`. `pg_hba.conf` лишь указывает, какой метод аутентификации применять.
> - [x] `pg_hba.conf` задаёт правила аутентификации клиентов: тип соединения, базу, пользователя, адрес клиента и метод аутентификации. | Верно. Это host-based authentication: каждая строка определяет, как подключающийся клиент должен доказать свою личность (`trust`, `md5`, `scram-sha-256`, `peer`, `ldap` и т.д.).
> - [ ] `pg_hba.conf` перечисляет настройки репликации: список реплик, их адреса и параметры `synchronous_commit`. | Реплики настраиваются параметрами `primary_conninfo`, `synchronous_standby_names` в `postgresql.conf`. `pg_hba.conf` может лишь разрешить replication-соединения, но не хранит их конфигурацию.

## Q7. В чём разница между `JSON` и `JSONB`?

| Характеристика | `JSON` | `JSONB` |
|---------------|--------|---------|
| Хранение | Текст (оригинальная строка) | Бинарный формат |
| Порядок ключей | Сохраняется | Не гарантируется |
| Дубли ключей | Сохраняются | Последнее значение |
| Индексирование | Нет (только функциональный) | `GIN`-индекс |
| Производительность записи | Быстрее | Медленнее (парсинг при вставке) |
| Производительность чтения | Медленнее (парсинг при выборке) | Быстрее |

**Вывод:** для большинства задач следует использовать `JSONB` — он поддерживает индексирование и эффективный поиск.

```sql
CREATE TABLE events (
    id SERIAL PRIMARY KEY,
    payload JSONB
);

-- GIN-индекс для JSONB
CREATE INDEX idx_events_payload ON events USING GIN (payload);
```

> [!mcq]
> - [ ] `JSON` хранится в бинарном формате с потерей пробелов, а `JSONB` — в текстовом с сохранением оригинала. | Всё наоборот: `JSON` хранится как текст и сохраняет оригинал, а `JSONB` — бинарный и не сохраняет пробелы/порядок ключей.
> - [ ] `JSON` поддерживает `GIN`-индексы, а `JSONB` — только `B-tree`. | Ровно наоборот: `JSONB` — основной тип для `GIN`-индексов. `JSON` индексируется только функционально.
> - [x] `JSON` хранится как текст и сохраняет порядок ключей/дубли, а `JSONB` — бинарный, не сохраняет дубли и поддерживает `GIN`-индекс. | Верно. `JSON` — быстрее вставка, медленнее чтение, нет индексов. `JSONB` — медленнее вставка (парсинг), быстрее чтение, поддерживает индексы.
> - [ ] `JSON` и `JSONB` идентичны на уровне хранения, но различаются только именем типа в схеме. | Они различаются принципиально: форматом хранения, производительностью и возможностями индексирования.

## Q8. Как работают массивы (`arrays`) в PostgreSQL?

Массивы позволяют хранить несколько значений одного типа в одном поле.

```sql
-- Создание таблицы с массивом
CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    tags TEXT[]
);

-- Вставка
INSERT INTO articles (tags) VALUES ('{"postgresql","database","sql"}');
INSERT INTO articles (tags) VALUES (ARRAY['performance', 'indexing']);

-- Запрос: содержит ли массив элемент
SELECT * FROM articles WHERE 'postgresql' = ANY(tags);

-- Запрос: все элементы массива присутствуют
SELECT * FROM articles WHERE tags @> ARRAY['postgresql', 'sql'];

-- unnest: развернуть массив в строки
SELECT id, unnest(tags) AS tag FROM articles;
```

Для ускорения поиска по массиву используется `GIN`-индекс:

```sql
CREATE INDEX idx_articles_tags ON articles USING GIN (tags);
```

> [!mcq]
> - [ ] Для поиска элемента в массиве `tags` следует использовать оператор `=` и `B-tree`-индекс. | Оператор `=` сравнивает массивы целиком. Для поиска элемента используют `ANY(tags)` или оператор содержания `@>`; индекс — `GIN`.
> - [x] Для поиска элемента в массиве `tags` следует использовать `ANY(tags)` или оператор `@>`, а для ускорения — `GIN`-индекс. | Верно. `ANY`/`@>`/`<@`/`&&` — стандартные массивные операторы, все они ускоряются `GIN`-индексом.
> - [ ] Для поиска элемента в массиве `tags` следует использовать оператор `LIKE` и `GiST`-индекс. | `LIKE` работает со строками, а не с массивами. Для массивов нужны операторы `ANY`/`@>` и индекс `GIN`.
> - [ ] Для поиска элемента в массиве `tags` следует использовать `unnest()` без индекса. | `unnest()` разворачивает массив в строки, что полезно, но не ускоряет поиск — выполняется seq scan. Для поиска нужен `GIN`-индекс на массиве.

## Q9. Что такое `hstore` и когда его использовать?

**`hstore`** — расширение PostgreSQL для хранения пар `ключ => значение` в одном поле (оба — строки). Подходит для разреженных атрибутов объектов с непредсказуемым набором свойств.

```sql
CREATE EXTENSION IF NOT EXISTS hstore;

CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT,
    attributes HSTORE
);

INSERT INTO products (name, attributes)
VALUES ('Shirt', 'color => "red", size => "L", material => "cotton"');

-- Получить значение по ключу
SELECT attributes -> 'color' FROM products;

-- Фильтр по ключу-значению
SELECT * FROM products WHERE attributes @> 'color => "red"';
```

**Когда использовать:** если набор атрибутов непредсказуем и не требует вложенных структур. Для сложных структур предпочтителен `JSONB`.

> [!mcq]
> - [x] `hstore` хранит плоские пары ключ-значение типа `text => text` и подходит для разреженных атрибутов без вложенности. | Верно. Оба — ключ и значение — строки. Для вложенных структур или типизированных значений лучше использовать `JSONB`.
> - [ ] `hstore` хранит произвольные вложенные JSON-структуры с поддержкой числовых и булевых значений. | Это описание `JSONB`, а не `hstore`. В `hstore` только строки и нет вложенности.
> - [ ] `hstore` хранит массивы значений одного типа с поддержкой `GIN`-индекса. | Массивы — отдельный тип (`int[]`, `text[]`), а не `hstore`. `hstore` — это map ключ→значение.
> - [ ] `hstore` хранит бинарные данные и шифрует их на диске. | Для бинарных данных есть `BYTEA`, для шифрования — `pgcrypto`. `hstore` — просто key-value.

## Q10. Как работают пользовательские типы (`enum`, `composite`, `domain`)?

**`ENUM`** — перечислимый тип, значения фиксированы при создании:

```sql
CREATE TYPE mood AS ENUM ('happy', 'sad', 'neutral');

CREATE TABLE persons (
    name TEXT,
    current_mood mood
);
```

**Composite type** — составной тип (аналог структуры):

```sql
CREATE TYPE address AS (
    street TEXT,
    city TEXT,
    zip_code VARCHAR(10)
);

CREATE TABLE customers (
    id SERIAL PRIMARY KEY,
    addr address
);

SELECT (addr).city FROM customers;
```

**`DOMAIN`** — тип на основе существующего с дополнительными ограничениями:

```sql
CREATE DOMAIN positive_int AS INTEGER
    CHECK (VALUE > 0);

CREATE TABLE items (
    id SERIAL PRIMARY KEY,
    quantity positive_int
);
```

> [!mcq]
> - [ ] `DOMAIN` — это именованный составной тип с несколькими полями разного типа. | Составной тип с полями — это `composite type`. `DOMAIN` добавляет только ограничения к существующему типу.
> - [ ] `DOMAIN` — это перечислимый тип с фиксированным набором значений. | Это `ENUM`. `DOMAIN` — другое: базовый тип плюс `CHECK` или `NOT NULL`. Частая ошибка — неправильное понимание этого момента в production коде.
> - [x] `DOMAIN` — тип на основе существующего с дополнительными ограничениями (`CHECK`, `NOT NULL`). | Верно. Удобен для переиспользования валидации: например, `positive_int AS INTEGER CHECK (VALUE > 0)`.
> - [ ] `DOMAIN` — тип для хранения доменных имён и IP-адресов с автоматической валидацией. | Для сетевых адресов есть `INET`/`CIDR`. `DOMAIN` — общий механизм создания ограниченных пользовательских типов поверх любых базовых.

## Q11. (!) Какие типы индексов существуют в PostgreSQL?

| Тип | Структура | Применение |
|-----|-----------|-----------|
| `B-tree` | Сбалансированное дерево | По умолчанию. Равенство, диапазон, `IS NULL`, сортировка |
| `Hash` | Хэш-таблица | Только проверка равенства (`=`) |
| `GIN` | Inverted index | `JSONB`, массивы, `full-text search`, `hstore` |
| `GiST` | Обобщённое дерево поиска | Геометрические типы, `full-text`, диапазоны, `pg_trgm` |
| `SP-GiST` | Space-partitioned GiST | IP-адреса, телефонные номера, точки |
| `BRIN` | Block Range Index | Монотонные данные (временные метки, последовательности) |

> [!mcq]
> - [x] Для поиска по `JSONB` с оператором `@>` оптимален `GIN`-индекс. | Верно. `GIN` — инвертированный индекс, оптимален для типов с множеством ключей/элементов в одном значении: `JSONB`, массивы, `tsvector`.
> - [ ] Для поиска по `JSONB` с оператором `@>` оптимален `B-tree`-индекс. | `B-tree` не работает с составными типами вроде `JSONB` по операторам `@>`/`?`. Он поддерживает только равенство/диапазоны по скалярам.
> - [ ] Для поиска по `JSONB` с оператором `@>` оптимален `Hash`-индекс. | `Hash` поддерживает только оператор `=`. Для containment-запросов в `JSONB` он не применим.
> - [ ] Для поиска по `JSONB` с оператором `@>` оптимален `BRIN`-индекс. | `BRIN` хранит min/max по блокам и подходит только для монотонных скалярных данных. Для `JSONB` неприменим.

## Q12. (!) Как работает `B-tree` индекс и когда он применяется?

**`B-tree`** (Balanced Tree) — индекс по умолчанию в PostgreSQL. Хранит данные в отсортированном дереве, поддерживает эффективный поиск по значению или диапазону.

**Применяется при:**
- Операторах `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`
- `ORDER BY` (может устранить сортировку)
- `IS NULL` / `IS NOT NULL`
- Операциях `LIKE 'prefix%'` (только с префиксом, не `'%suffix'`)

```sql
-- Обычный B-tree
CREATE INDEX idx_orders_created_at ON orders (created_at);

-- Составной B-tree
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- Descending
CREATE INDEX idx_orders_created_desc ON orders (created_at DESC);
```

**Составной индекс:** оптимизирует запросы с фильтром по первому (или первым нескольким) столбцам. Порядок столбцов важен — наиболее селективный или часто фильтруемый ставят первым.

> [!mcq]
> - [ ] `B-tree`-индекс эффективен для `LIKE '%suffix'` — достаточно обратной сортировки дерева. | `B-tree` ускоряет только `LIKE 'prefix%'`. Для `%suffix` или `%middle%` нужен `GIN`/`GiST` с `pg_trgm` или reverse-индекс.
> - [x] `B-tree`-индекс эффективен для операторов `=`, `<`, `>`, `BETWEEN`, `ORDER BY` и `LIKE 'prefix%'`. | Верно. Данные в `B-tree` отсортированы, поэтому доступны диапазонные запросы, сортировка без пересортировки и поиск по префиксу.
> - [ ] `B-tree`-индекс эффективен для полнотекстового поиска `@@` по `tsvector`. | Для `@@` по `tsvector`/`tsquery` используется `GIN` или `GiST`. `B-tree` не поддерживает эти операторы.
> - [ ] `B-tree`-индекс эффективен для containment-запросов `@>` по массивам. | Для containment по массивам используется `GIN`. `B-tree` проверяет только равенство массивов целиком.

## Q13. Что такое `GIN` индекс и для каких данных он нужен?

**`GIN` (Generalized Inverted Index)** — инвертированный индекс: для каждого элемента хранится список строк, его содержащих. Оптимален для типов, где одно поле содержит несколько ключей.

**Применяется для:**
- `JSONB` (операторы `@>`, `?`, `?|`, `?&`)
- Массивов (`@>`, `<@`, `&&`)
- `full-text search` (`@@`)
- `hstore`
- `pg_trgm` (поиск по подстроке)

```sql
-- GIN для JSONB
CREATE INDEX idx_events_payload ON events USING GIN (payload);

-- GIN для full-text search
CREATE INDEX idx_articles_tsv ON articles USING GIN (to_tsvector('russian', body));

-- GIN для pg_trgm (поиск LIKE '%term%')
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING GIN (name gin_trgm_ops);
```

**Недостатки:** `GIN` медленнее обновляется по сравнению с `B-tree`. Для ускорения обновлений используется `fastupdate`.

> [!mcq]
> - [ ] `GIN` быстрее обновляется, чем `B-tree`, за счёт компактной структуры. | Наоборот: при INSERT/UPDATE `GIN` разбивает значение на элементы и для каждого обновляет posting list — это медленнее, чем `B-tree`.
> - [x] `GIN` медленнее обновляется, чем `B-tree`, но даёт точный поиск по элементам составных типов (`JSONB`, массивы, `tsvector`). | Верно. Для снижения стоимости обновлений есть параметр `fastupdate`, откладывающий вставки в pending list.
> - [ ] `GIN` не поддерживает `tsvector` — для full-text search используется только `GiST`. | `GIN` — основной индекс для `tsvector`, причём более быстрый на чтении, чем `GiST`.
> - [ ] `GIN` даёт ложные срабатывания и требует recheck в `Bitmap Heap Scan`. | Ложные срабатывания характерны для `GiST` (lossy индекс). `GIN` — точный.

## Q14. Что такое `GiST` индекс и чем он отличается от `GIN`?

**`GiST` (Generalized Search Tree)** — обобщённое дерево поиска, расширяемое: логика индексирования выносится в классы операторов.

| Характеристика | `GIN` | `GiST` |
|---------------|-------|--------|
| Оптимален для | Точный поиск элементов | Приближённые запросы, диапазоны |
| Размер | Обычно больше | Меньше |
| Обновление | Медленнее | Быстрее |
| Ложные срабатывания | Нет | Возможны (требует перепроверки) |

**Применяется для:** геометрических данных (`PostGIS`), диапазонов (`tsrange`), `full-text search`, `pg_trgm`.

```sql
-- GiST для диапазонов дат
CREATE INDEX idx_reservations_period ON reservations USING GiST (period);

-- GiST для PostGIS
CREATE INDEX idx_locations_geom ON locations USING GiST (geom);
```

> [!mcq]
> - [x] `GiST` меньше по размеру и быстрее обновляется, но допускает ложные срабатывания (нужен recheck). | Верно. `GiST` — lossy-индекс: после поиска по индексу таблица перепроверяется. Оптимален для приближённых запросов и диапазонов.
> - [ ] `GiST` больше по размеру и медленнее обновляется, но даёт точный результат без recheck. | Это характеристики `GIN`, а не `GiST`. `GiST`, наоборот, меньше и быстрее обновляется.
> - [ ] `GiST` применяется только к `JSONB` и массивам, а `GIN` — к геометрии. | Ровно наоборот: `GIN` — для `JSONB`/массивов, `GiST` — для геометрии, диапазонов и `pg_trgm`.
> - [ ] `GiST` не поддерживает `pg_trgm` — триграммы индексируются только `B-tree`. | `pg_trgm` поддерживает и `GIN`, и `GiST`. `B-tree` для триграмм не применим.

## Q15. Что такое `BRIN` индекс и когда его выгодно использовать?

**`BRIN` (Block Range Index)** — индекс на основе диапазонов блоков. Хранит мин/макс значения для каждого диапазона физических блоков таблицы (по умолчанию 128 блоков на диапазон).

**Применяется, когда:**
- Данные физически упорядочены по индексируемому столбцу (монотонные `id`, временные метки вставки).
- Таблица очень большая, а `B-tree` индекс занял бы неприемлемо много места.

```sql
CREATE INDEX idx_logs_created_brin ON logs USING BRIN (created_at);
```

**Ограничения:** подходит только для коррелированных данных (высокая корреляция значений с физическим порядком строк). Для неупорядоченных данных эффективность стремится к нулю.

> [!mcq]
> - [ ] `BRIN` эффективен на случайно распределённых данных благодаря хэш-функции. | `BRIN` не использует хэш — он хранит min/max по диапазонам блоков. На случайных данных min/max каждого блока покрывают весь диапазон значений, и индекс становится бесполезен.
> - [x] `BRIN` эффективен, когда данные физически упорядочены по индексируемому столбцу (например, монотонный timestamp). | Верно. При высокой корреляции значений с физическим порядком `BRIN` резко сокращает число сканируемых блоков, занимая минимум места.
> - [ ] `BRIN` эффективен для точечных lookup'ов по уникальному ключу. | Для точечного lookup нужны `B-tree` или `Hash`. `BRIN` — грубый индекс (диапазонный), всегда требует recheck страниц.
> - [ ] `BRIN` эффективен для полнотекстового поиска и containment по `JSONB`. | Для full-text и `JSONB` используется `GIN`/`GiST`. `BRIN` не поддерживает эти операторы.

## Q16. Что такое частичный (`partial`) индекс?

**Частичный индекс** строится только по подмножеству строк, удовлетворяющих условию `WHERE`. Меньший размер и быстрое обновление, так как не все строки индексируются.

```sql
-- Индексировать только незакрытые заказы
CREATE INDEX idx_orders_open ON orders (user_id)
WHERE status = 'open';

-- Индексировать только ненулевые значения
CREATE INDEX idx_users_email ON users (email)
WHERE email IS NOT NULL;
```

**Когда использовать:** для запросов с фиксированным фильтром (`WHERE status = 'active'`), когда нужна выборка из небольшого подмножества строк.

> [!mcq]
> - [x] Частичный индекс строится только по строкам, удовлетворяющим `WHERE`-условию в определении индекса. | Верно. Это уменьшает размер индекса и ускоряет обновления. Планировщик использует такой индекс, если условие запроса покрывается условием индекса.
> - [ ] Частичный индекс строится по всем строкам, но хранит только часть столбцов через `INCLUDE`. | Это описание покрывающего (covering) индекса с `INCLUDE`, а не частичного. Частичный — про отбор строк, covering — про дополнительные столбцы.
> - [ ] Частичный индекс — это индекс, который создаётся на партиции и автоматически продвигается на родительскую таблицу. | Речь идёт о partitioned indexes. Частичный индекс (`partial index`) — независимая концепция, связанная с условием `WHERE` в определении индекса. Частая ошибка — неправильное понимание этого момента в production коде.
> - [ ] Частичный индекс — это индекс, который автоматически перестраивается после каждого `VACUUM`. | Индексы не перестраиваются после `VACUUM`. Частичный — про `WHERE`-фильтр в определении.

## Q17. Что такое функциональный (`expression`) индекс?

**Функциональный индекс** строится по результату выражения или функции, применённой к столбцу.

```sql
-- Поиск без учёта регистра
CREATE INDEX idx_users_lower_email ON users (LOWER(email));

-- Запрос, использующий этот индекс
SELECT * FROM users WHERE LOWER(email) = 'user@example.com';

-- Индекс по extracted части JSONB
CREATE INDEX idx_events_type ON events ((payload->>'event_type'));

-- Индекс по части даты
CREATE INDEX idx_orders_year ON orders (EXTRACT(YEAR FROM created_at));
```

> [!mcq]
> - [ ] Функциональный индекс ускоряет запрос `WHERE LOWER(email) = ?` только если в запросе явно переписать `LOWER` на оригинал. | Наоборот: запрос должен содержать ровно то же выражение, что и индекс (`LOWER(email)`). Именно функциональный индекс для этого и создаётся.
> - [x] Функциональный индекс строится по результату выражения или функции (`LOWER(email)`, `payload->>'type'`) и ускоряет запросы с тем же выражением. | Верно. PostgreSQL хранит уже вычисленные значения; функция должна быть `IMMUTABLE`.
> - [ ] Функциональный индекс — это индекс с триггером, который пересчитывает значения при каждом UPDATE. | PostgreSQL не требует триггера: значение выражения вычисляется автоматически при вставке/обновлении строки.
> - [ ] Функциональный индекс хранит исходные значения столбцов, а функция применяется только при поиске. | Всё наоборот: индекс хранит именно результат функции. Это позволяет избежать её вычисления при каждом запросе.

## Q18. (!) Что такое покрывающий (`covering`) индекс и как его создать в PostgreSQL?

**Покрывающий индекс** содержит все столбцы, необходимые для выполнения запроса, — планировщик может использовать `Index Only Scan` без обращения к основной таблице.

В PostgreSQL (с версии 11) покрывающий индекс создаётся с помощью `INCLUDE`:

```sql
-- Основной индекс по user_id, дополнительно хранит status и total
CREATE INDEX idx_orders_covering ON orders (user_id) INCLUDE (status, total);

-- Запрос использует Index Only Scan
SELECT status, total FROM orders WHERE user_id = 42;
```

**До PostgreSQL 11** покрывающий эффект достигался составным индексом (все нужные столбцы включались в ключ).

**Преимущества:** устраняет обращение к основной таблице (`heap fetch`), снижает ввод-вывод. **Недостатки:** увеличивает размер индекса.

> [!mcq]
> - [x] Покрывающий индекс в PostgreSQL создаётся через `CREATE INDEX ... INCLUDE (cols)` и позволяет `Index Only Scan` без обращения к таблице. | Верно. Столбцы из `INCLUDE` хранятся в листьях индекса, но не участвуют в сортировке/ключе. Доступно с PG 11.
> - [ ] Покрывающий индекс в PostgreSQL создаётся через `CREATE COVERING INDEX ...`. | Такого синтаксиса в PostgreSQL нет. Используется `INCLUDE` в обычном `CREATE INDEX`. Частая ошибка — неправильное понимание этого момента в production коде.
> - [ ] Покрывающий индекс в PostgreSQL создаётся автоматически для всех таблиц размером более 1 ГБ. | Автоматическое создание индексов в PostgreSQL не существует. Любой индекс создаётся явно.
> - [ ] Покрывающий индекс в PostgreSQL создаётся через `CLUSTER` на `B-tree`. | `CLUSTER` физически переупорядочивает строки таблицы по индексу. Это не покрывающий индекс — он не устраняет heap fetch.

## Q19. Что такое `CONCURRENTLY` при создании индекса?

При обычном `CREATE INDEX` таблица блокируется на запись на время построения индекса. `CONCURRENTLY` позволяет строить индекс без блокировки записи:

```sql
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id);
```

**Особенности:**
- Занимает больше времени (два прохода по таблице).
- Нельзя использовать внутри транзакции.
- Если прервать, оставит «неправильный» (`invalid`) индекс — его нужно удалить вручную.
- Аналог при удалении: `DROP INDEX CONCURRENTLY`.

> [!mcq]
> - [ ] `CREATE INDEX CONCURRENTLY` блокирует таблицу на запись, но позволяет читать. | Обычный `CREATE INDEX` блокирует на запись. `CONCURRENTLY`, наоборот, снимает эту блокировку и позволяет INSERT/UPDATE/DELETE. Частая ошибка — неправильное понимание этого момента в production коде.
> - [x] `CREATE INDEX CONCURRENTLY` строит индекс без блокировки записи, но занимает больше времени и не работает внутри транзакции. | Верно. Делает два прохода по таблице. Если прерван — оставляет `invalid`-индекс, который нужно вручную дропнуть.
> - [ ] `CREATE INDEX CONCURRENTLY` создаёт индекс параллельно несколькими воркерами, полностью снимая блокировки. | Параллельное построение индекса — отдельная фича (`max_parallel_maintenance_workers`). `CONCURRENTLY` — про отсутствие блокировки записи, а не про параллелизм.
> - [ ] `CREATE INDEX CONCURRENTLY` разрешено внутри транзакции и автоматически откатывается при сбое. | `CONCURRENTLY` запрещён внутри транзакции. При сбое остаётся `invalid`-индекс.

## Q20. (!) Как читать вывод `EXPLAIN`?

`EXPLAIN` показывает **план выполнения** запроса. Вывод — дерево узлов, каждый из которых описывает операцию. Читается **снизу вверх** (листья выполняются первыми).

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```

```
Index Scan using idx_orders_user_id on orders  (cost=0.43..8.45 rows=5 width=128)
  Index Cond: (user_id = 42)
```

**Основные поля:**
- `cost=X..Y` — стоимость запуска узла (`X`) и общая стоимость (`Y`) в условных единицах.
- `rows=N` — оценочное число строк.
- `width=N` — средний размер строки в байтах.
- `actual time=X..Y` (только `EXPLAIN ANALYZE`) — реальное время.
- `actual rows=N loops=N` — реальное число строк и число запусков узла.

**Типичные узлы:**
| Узел | Описание |
|------|---------|
| `Seq Scan` | Полное сканирование таблицы |
| `Index Scan` | Сканирование по индексу с возвратом в таблицу |
| `Index Only Scan` | Сканирование только по индексу (покрывающий) |
| `Bitmap Index Scan` | Построение битовой карты по индексу |
| `Bitmap Heap Scan` | Чтение строк по битовой карте |
| `Hash Join` | Соединение хэш-таблицей |
| `Nested Loop` | Вложенные циклы |
| `Merge Join` | Соединение слиянием |
| `Sort` | Сортировка |
| `Aggregate` | Агрегация |

> [!mcq]
> - [x] Дерево плана `EXPLAIN` читается снизу вверх: листья (сканирования таблиц) выполняются первыми, а верхний узел — последним. | Верно. Поля `cost=X..Y` — startup cost и total cost; `rows` — оценочное число строк; `width` — средний размер строки.
> - [ ] Дерево плана `EXPLAIN` читается сверху вниз: верхний узел — самая первая операция, дальше идут зависимые. | Иерархия обратная: верхний узел получает строки от дочерних. Чтобы понять, откуда они берутся, нужно читать снизу.
> - [ ] Поле `cost` в `EXPLAIN` показывает реальное время выполнения запроса в миллисекундах. | `cost` — условные единицы планировщика, а не миллисекунды. Реальное время показывает `EXPLAIN ANALYZE` в поле `actual time`.
> - [ ] Поле `rows` в `EXPLAIN` — точное число возвращённых строк, полученное после выполнения запроса. | В обычном `EXPLAIN` это оценка. Реальное число строк показывает `EXPLAIN ANALYZE` в поле `actual rows`.

## Q21. (!) В чём разница между `EXPLAIN` и `EXPLAIN ANALYZE`?

| Команда | Описание |
|---------|---------|
| `EXPLAIN` | Показывает **оценочный** план без выполнения запроса |
| `EXPLAIN ANALYZE` | **Выполняет** запрос и показывает реальное время и число строк |
| `EXPLAIN (ANALYZE, BUFFERS)` | Добавляет информацию о попаданиях в кэш (`shared hit`, `read`) |
| `EXPLAIN (ANALYZE, FORMAT JSON)` | Вывод в формате `JSON` |

```sql
-- Полный анализ с информацией о буферах
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 'open';
```

**Важно:** `EXPLAIN ANALYZE` реально выполняет запрос, включая `INSERT`/`UPDATE`/`DELETE`. Для деструктивных запросов оборачивать в `BEGIN`/`ROLLBACK`:

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM old_logs WHERE created_at < NOW() - INTERVAL '1 year';
ROLLBACK;
```

> [!mcq]
> - [ ] `EXPLAIN` реально выполняет запрос и возвращает фактическое время, а `EXPLAIN ANALYZE` — только оценку. | Наоборот: `EXPLAIN` только строит план без выполнения, а `EXPLAIN ANALYZE` реально выполняет запрос и собирает `actual time`/`actual rows`.
> - [x] `EXPLAIN` показывает только оценочный план без выполнения, а `EXPLAIN ANALYZE` выполняет запрос и показывает реальное время и строки. | Верно. Поэтому `EXPLAIN ANALYZE` нужно оборачивать в `BEGIN`/`ROLLBACK` для `INSERT`/`UPDATE`/`DELETE`.
> - [ ] `EXPLAIN` и `EXPLAIN ANALYZE` идентичны — различаются только форматом вывода. | Принципиальное различие: первое только планирует, второе реально выполняет запрос.
> - [ ] `EXPLAIN ANALYZE` откатывает все изменения автоматически, поэтому безопасен для `DELETE`. | Автоматического отката нет: изменения применяются. Для деструктивных запросов нужно явно `BEGIN`/`ROLLBACK`.

## Q22. (!) Что такое `Seq Scan` и `Index Scan` и когда планировщик выбирает каждый?

**`Seq Scan` (Sequential Scan):**
- Читает все страницы таблицы последовательно.
- Выбирается, когда нужно прочитать **большую долю строк** (нет смысла прыгать по индексу).
- Выбирается, если **индекса нет** для данного условия.
- Иногда выгоднее `Index Scan` для маленьких таблиц (накладные расходы на индекс не окупаются).

**`Index Scan`:**
- Сначала находит значения в индексе, затем обращается к основной таблице за строкой.
- Выбирается при **высокой селективности** условия (фильтрует большую часть строк).
- Стоимость зависит от числа `heap fetch` (случайных обращений к таблице).

**`Index Only Scan`:**
- Если покрывающий индекс содержит все нужные столбцы, обращение к таблице не нужно.

**Планировщик переключается на `Seq Scan`, если:**
- Условие фильтрует < 5–10% строк (зависит от `random_page_cost` / `seq_page_cost`).
- Статистика устарела.
- Принудительно: `SET enable_indexscan = off;`

> [!mcq]
> - [x] `Seq Scan` выбирается, когда нужно прочитать большую долю строк таблицы или индекса нет — последовательное чтение дешевле случайного. | Верно. Также выбирается для маленьких таблиц, где накладные расходы на индекс не окупаются. Планировщик сравнивает стоимость с учётом `seq_page_cost`/`random_page_cost`.
> - [ ] `Seq Scan` выбирается, когда условие запроса очень селективно и возвращает малую долю строк. | При высокой селективности (мало строк) выгоднее `Index Scan`, а не `Seq Scan`. Seq Scan выгоден при обратной ситуации. Частая ошибка — неправильное понимание этого момента в production коде.
> - [ ] `Seq Scan` выбирается только тогда, когда отключены все остальные методы доступа через `enable_*` параметры. | Планировщик выбирает `Seq Scan` по стоимости в штатном режиме. Принудительное отключение индексов — лишь один из сценариев, не основной.
> - [ ] `Seq Scan` выбирается только для партиционированных таблиц, независимо от индексов. | На партиционированных таблицах индексы тоже используются (локальные на партициях). Выбор метода зависит от стоимости.

## Q23. Что такое `Bitmap Index Scan` и `Index Only Scan`?

**`Bitmap Index Scan`:**

1. Сканирует индекс и строит **битовую карту** (bitmap) страниц, содержащих подходящие строки.
2. `Bitmap Heap Scan` читает эти страницы в порядке физического расположения, снижая случайный ввод-вывод.

Применяется при умеренной селективности (больше строк, чем при `Index Scan`, но меньше, чем при `Seq Scan`). Позволяет объединять несколько индексов (`BitmapAnd`, `BitmapOr`).

```
Bitmap Heap Scan on orders
  Recheck Cond: (status = 'open')
  ->  Bitmap Index Scan on idx_orders_status
        Index Cond: (status = 'open')
```

**`Index Only Scan`:** читает данные **только из индекса**, не обращаясь к таблице. Возможен только при использовании покрывающего индекса. Требует, чтобы visibility map показывала, что страницы таблицы не содержат «видимых» мёртвых кортежей — иначе PostgreSQL вынужден проверить таблицу.

> [!mcq]
> - [ ] `Index Only Scan` возможен всегда, когда индекс содержит нужные столбцы, независимо от visibility map. | Для `Index Only Scan` необходим «чистый» visibility map: если страница содержит видимые dead tuples, планировщик вынужден перепроверить таблицу. Помогает `VACUUM`.
> - [x] `Index Only Scan` использует только индекс и visibility map, избегая обращения к таблице, если страница отмечена как all-visible. | Верно. Устраняет heap fetch и резко снижает ввод-вывод. Требует, чтобы все нужные столбцы были в индексе (покрывающий) и страницы помечены как all-visible.
> - [ ] `Index Only Scan` использует хэш-индекс для поиска и всегда обращается к таблице за актуальной версией строки. | `Hash`-индексы не поддерживают `Index Only Scan`. Более того, обращение к таблице как раз и отсутствует — это суть «Only Scan». Частая ошибка — неправильное понимание этого момента в production коде.
> - [ ] `Index Only Scan` работает только с `BRIN`-индексами и не поддерживает `B-tree`. | Наоборот: `Index Only Scan` наиболее применим с `B-tree` + `INCLUDE`. `BRIN` — грубый индекс и не даёт такого эффекта. Частая ошибка — неправильное понимание этого момента в production коде.

## Q24. Что такое `cost` в плане запроса?

**`cost`** — условная оценка стоимости выполнения, выраженная в единицах, соответствующих стоимости чтения одной дисковой страницы последовательно.

**Параметры, влияющие на стоимость:**
| Параметр | По умолчанию | Описание |
|---------|------------|---------|
| `seq_page_cost` | `1.0` | Стоимость последовательного чтения страницы |
| `random_page_cost` | `4.0` | Стоимость случайного чтения страницы |
| `cpu_tuple_cost` | `0.01` | Стоимость обработки одной строки |
| `cpu_index_tuple_cost` | `0.005` | Стоимость обработки записи индекса |
| `cpu_operator_cost` | `0.0025` | Стоимость вычисления оператора |

Для SSD рекомендуется снизить `random_page_cost` до `1.1–2.0`, так как случайное чтение на SSD дешевле.

```sql
SET random_page_cost = 1.1;
```

> [!mcq]
> - [x] Для SSD имеет смысл снизить `random_page_cost` до `1.1–2.0`, так как случайное чтение на SSD почти не дороже последовательного. | Верно. По умолчанию `random_page_cost=4.0` рассчитан на HDD. На SSD это завышено и уводит планировщик от индексных сканирований.
> - [ ] Для SSD имеет смысл увеличить `random_page_cost` до `8.0`, чтобы планировщик чаще выбирал `Seq Scan`. | Наоборот: на SSD `random_page_cost` снижают, чтобы чаще выбирались `Index Scan`. Частая ошибка — неправильное понимание этого момента в production коде.
> - [ ] `cost` измеряется в миллисекундах и напрямую отражает время выполнения. | `cost` — условные единицы относительно стоимости последовательного чтения страницы. Для реального времени нужен `EXPLAIN ANALYZE` с `actual time`.
> - [ ] `seq_page_cost` всегда выше `random_page_cost`, так как последовательное чтение требует больше ресурсов. | В реальности наоборот: последовательное чтение дешевле случайного, поэтому `seq_page_cost=1.0`, а `random_page_cost=4.0` (HDD) или ~1.1 (SSD).

## Q25. Как работает статистика в PostgreSQL (`pg_statistics`)?

Планировщик PostgreSQL использует **статистику** о распределении данных для оценки количества строк. Статистика обновляется командой `ANALYZE` (или автоматически `autovacuum`).

```sql
-- Ручной запуск анализа
ANALYZE orders;

-- Посмотреть статистику столбца
SELECT * FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';
```

**Ключевые поля `pg_stats`:**
- `n_distinct` — число уникальных значений
- `most_common_vals` — наиболее частые значения
- `most_common_freqs` — их частоты
- `histogram_bounds` — границы гистограммы равночастотного распределения

Параметр `default_statistics_target` (по умолчанию `100`) определяет детализацию. Для столбцов с высокой кардинальностью можно увеличить:

```sql
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
```

> [!mcq]
> - [ ] Статистика в PostgreSQL автоматически обновляется после каждого `INSERT`/`UPDATE`/`DELETE`. | Статистика обновляется командой `ANALYZE`, которую запускает `autovacuum` по порогу (`autovacuum_analyze_scale_factor`), а не на каждую DML-операцию.
> - [x] Статистика обновляется командой `ANALYZE` (вручную или через `autovacuum`) и хранится в `pg_statistic`; `pg_stats` — view-обёртка над ней. | Верно. Планировщик использует `n_distinct`, `most_common_vals`, `histogram_bounds` для оценки числа строк. `default_statistics_target` регулирует детализацию.
> - [ ] Статистика генерируется только при `VACUUM FULL`, а обычный `VACUUM` её не трогает. | Статистика обновляется командой `ANALYZE` (или `VACUUM ANALYZE`). Обычный `VACUUM` без `ANALYZE` статистику не трогает, но она не требует именно `VACUUM FULL`.
> - [ ] Статистика хранится в `WAL`-журнале и передаётся на реплики для согласованного планирования. | Статистика хранится в системном каталоге `pg_statistic`. На physical-реплике она доступна через обычную репликацию каталогов, но не через специальный механизм.

## Q26. (!) Какие уровни изоляции транзакций поддерживает PostgreSQL?

PostgreSQL поддерживает 4 стандартных уровня изоляции `SQL`:

| Уровень | Dirty Read | Non-Repeatable Read | Phantom Read |
|---------|-----------|--------------------|-|
| `READ UNCOMMITTED` | Невозможен¹ | Возможен | Возможен |
| `READ COMMITTED` (по умолч.) | Невозможен | Возможен | Возможен |
| `REPEATABLE READ` | Невозможен | Невозможен | Невозможен² |
| `SERIALIZABLE` | Невозможен | Невозможен | Невозможен |

¹ PostgreSQL не реализует `dirty read` даже на `READ UNCOMMITTED`.  
² За счёт `MVCC` `REPEATABLE READ` в PostgreSQL также предотвращает `phantom read`.

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- ... операции ...
COMMIT;

-- Или через SET
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

**`SERIALIZABLE`** использует `SSI` (Serializable Snapshot Isolation) — обнаруживает конфликты сериализации и откатывает транзакцию с `SQLSTATE 40001`.

> [!mcq]
> - [ ] PostgreSQL реализует `dirty read` на уровне `READ UNCOMMITTED`, как по стандарту SQL. | В PostgreSQL `READ UNCOMMITTED` ведёт себя как `READ COMMITTED` — dirty read невозможен даже на самом слабом уровне.
> - [x] PostgreSQL на `REPEATABLE READ` предотвращает и non-repeatable, и phantom read благодаря `MVCC`-снимку. | Верно. Стандарт SQL этого не требует, но PostgreSQL-реализация строже: снимок фиксируется на старт транзакции.
> - [ ] PostgreSQL по умолчанию использует уровень `SERIALIZABLE`. | По умолчанию — `READ COMMITTED`. `SERIALIZABLE` нужно включать явно через `SET TRANSACTION ISOLATION LEVEL`. Частая ошибка — неправильное понимание этого момента в production коде.
> - [ ] PostgreSQL на уровне `SERIALIZABLE` блокирует все конфликтующие транзакции до завершения первой. | PostgreSQL использует SSI (Serializable Snapshot Isolation) — не блокировки, а обнаружение конфликтов сериализации и откат с `SQLSTATE 40001`.

## Q27. (!) Как работает `MVCC` в PostgreSQL?

**`MVCC` (Multi-Version Concurrency Control)** — механизм изоляции транзакций: вместо блокировок читателей и писателей PostgreSQL хранит несколько версий одной и той же строки.

**Принцип:**
- При `UPDATE` старая версия строки не удаляется сразу — помечается как «удалённая» в поле `xmax`.
- Создаётся новая версия строки с новым `xmin`.
- Каждая транзакция видит **снимок** (snapshot) данных: набор версий строк, зафиксированных до начала транзакции.

**Преимущества:**
- Читатели не блокируют писателей, писатели не блокируют читателей.
- Высокий параллелизм.

**Недостатки:**
- Накапливаются мёртвые кортежи (`dead tuples`), которые нужно периодически убирать (`VACUUM`).
- Индексы также накапливают мёртвые записи.

```sql
-- Посмотреть xmin/xmax
SELECT xmin, xmax, * FROM orders WHERE id = 1;
```

> [!mcq]
> - [x] При `UPDATE` старая версия строки не удаляется сразу, а помечается `xmax` — новая версия создаётся с новым `xmin`. | Верно. Так обеспечивается параллельное чтение: каждая транзакция видит подходящий снимок. Старые версии убирает `VACUUM`.
> - [ ] При `UPDATE` старая версия перезаписывается in-place новой, а `xmin`/`xmax` хранят только факт блокировки. | PostgreSQL не делает in-place update: всегда создаётся новая версия строки. Это ключевое отличие от InnoDB/Oracle undo-based MVCC.
> - [ ] MVCC использует блокировки читателей для обеспечения консистентности снимка. | Наоборот: MVCC спроектирован так, чтобы читатели не блокировали писателей и наоборот. Каждая транзакция видит свой снимок.
> - [ ] MVCC не порождает dead tuples, поэтому `VACUUM` в PostgreSQL не нужен. | Именно MVCC и порождает dead tuples (устаревшие версии строк). `VACUUM` нужен регулярно, иначе возникает bloat.

## Q28. Что такое `xmin` и `xmax` в кортежах PostgreSQL?

Каждый кортеж (строка) содержит системные поля:

| Поле | Описание |
|------|---------|
| `xmin` | `XID` транзакции, создавшей кортеж (`INSERT` или `UPDATE`) |
| `xmax` | `XID` транзакции, удалившей или заменившей кортеж (`DELETE` или `UPDATE`) |
| `ctid` | Физический адрес кортежа (`блок`, `смещение`) |

**Видимость кортежа для транзакции T:**
- `xmin` должен быть зафиксирован и входить в снимок.
- `xmax` не должен быть зафиксирован или должен быть больше XID снимка (кортеж не удалён в видимом диапазоне).

```sql
SELECT xmin, xmax, ctid, id, status FROM orders WHERE id = 1;
```

> [!mcq]
> - [ ] `xmin` — это физический адрес строки (блок, смещение). | Физический адрес строки — это `ctid`, а не `xmin`. `xmin` — XID транзакции, создавшей кортеж.
> - [x] `xmin` — XID транзакции, создавшей кортеж; `xmax` — XID транзакции, удалившей или заменившей его. | Верно. Комбинация `xmin`/`xmax` и снимка транзакции определяет видимость версии строки.
> - [ ] `xmin` — уникальный идентификатор строки в пределах таблицы, аналог primary key. | Это не уникальный ключ строки: `xmin` совпадает у всех строк, вставленных одной транзакцией. Уникальный PK — отдельная пользовательская колонка.
> - [ ] `xmin` — контрольная сумма (checksum) страницы для защиты от повреждения данных. | Контрольные суммы — отдельный механизм (`data_checksums`). `xmin` относится к MVCC-видимости.

## Q29. Что такое `phantom read`, `non-repeatable read` и `dirty read`?

| Аномалия | Описание |
|----------|---------|
| **Dirty read** | Транзакция читает незафиксированные изменения другой транзакции |
| **Non-repeatable read** | Повторный `SELECT` возвращает другой результат из-за зафиксированного `UPDATE`/`DELETE` |
| **Phantom read** | Повторный `SELECT` возвращает новые строки из-за зафиксированного `INSERT` |
| **Serialization anomaly** | Результат параллельных транзакций невозможен ни при каком последовательном порядке их выполнения |

В PostgreSQL благодаря `MVCC` даже `READ COMMITTED` исключает `dirty read`. `REPEATABLE READ` исключает `non-repeatable` и `phantom read`. `SERIALIZABLE` исключает все аномалии.

> [!mcq]
> - [x] Phantom read — это появление новых строк при повторном `SELECT` из-за зафиксированного `INSERT` другой транзакции. | Верно. Non-repeatable read — про изменение уже прочитанных строк (`UPDATE`/`DELETE`), а phantom — про появление новых.
> - [ ] Phantom read — это изменение уже прочитанной строки из-за зафиксированного `UPDATE`. | Это описание non-repeatable read, а не phantom. Phantom касается именно новых строк.
> - [ ] Phantom read — это чтение незафиксированных изменений другой транзакции. | Это dirty read. Phantom возникает только после commit вставки в другой транзакции.
> - [ ] Phantom read невозможен в любой СУБД, реализующей MVCC. | В общем случае возможен (стандарт SQL допускает его на `REPEATABLE READ`). Конкретно PostgreSQL на `REPEATABLE READ` его предотвращает, но это особенность реализации.

## Q30. Как работает `SAVEPOINT`?

**`SAVEPOINT`** позволяет создать точку внутри транзакции, к которой можно откатиться без отмены всей транзакции.

```sql
BEGIN;

INSERT INTO orders (user_id, total) VALUES (1, 100);

SAVEPOINT before_discount;

UPDATE orders SET total = total * 0.9 WHERE user_id = 1;

-- Отменить только операцию после SAVEPOINT
ROLLBACK TO SAVEPOINT before_discount;

-- Первый INSERT сохранён, UPDATE отменён
COMMIT;
```

Удалить `SAVEPOINT`: `RELEASE SAVEPOINT before_discount;`

> [!mcq]
> - [ ] `SAVEPOINT` автоматически создаётся в начале каждой транзакции и откатывает всю транзакцию при ошибке. | `SAVEPOINT` всегда создаётся явно командой `SAVEPOINT name`. Всю транзакцию откатывает `ROLLBACK` без имени.
> - [x] `SAVEPOINT` создаёт именованную точку внутри транзакции, к которой можно откатиться через `ROLLBACK TO SAVEPOINT`, сохранив остальные изменения. | Верно. После `ROLLBACK TO` транзакция продолжает жить, и можно продолжить работу или сделать `COMMIT`.
> - [ ] `SAVEPOINT` создаёт отдельную независимую транзакцию, которая коммитится независимо от основной. | Независимые вложенные транзакции в PostgreSQL эмулируются через dblink/FDW или pg_savepoints в процедурах — это не механизм `SAVEPOINT`.
> - [ ] После `ROLLBACK TO SAVEPOINT` вся транзакция завершается, и нужен новый `BEGIN`. | Транзакция остаётся активной после `ROLLBACK TO`. Новый `BEGIN` требуется только после полного `ROLLBACK`/`COMMIT`.

## Q31. (!) Зачем нужен `VACUUM` и что такое `dead tuples`?

**`Dead tuples`** — устаревшие версии строк, оставшиеся после `UPDATE`/`DELETE` из-за `MVCC`. Физически строки не удаляются сразу — они остаются в таблице до тех пор, пока ни одна активная транзакция их не видит.

**Проблемы от накопления `dead tuples`:**
- Увеличение размера таблицы (`table bloat`).
- Замедление `Seq Scan` (больше страниц для чтения).
- Замедление `Index Scan` (больше записей в индексах).

**`VACUUM`** помечает пространство `dead tuples` как доступное для повторного использования (но **не возвращает** его ОС — лишь делает доступным для новых строк внутри таблицы).

```sql
-- Ручной запуск
VACUUM orders;

-- Посмотреть статистику dead tuples
SELECT relname, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

> [!mcq]
> - [x] `VACUUM` помечает место dead tuples как свободное для повторного использования внутри таблицы, но не возвращает его ОС. | Верно. Таблица остаётся того же физического размера, но новые строки смогут заполнить освобождённое место. Для возврата ОС нужен `VACUUM FULL` или `pg_repack`.
> - [ ] `VACUUM` физически удаляет dead tuples и сразу возвращает освобождённое место ОС. | Освобождение ОС — задача `VACUUM FULL` (или `pg_repack`). Обычный `VACUUM` только помечает место как свободное.
> - [ ] `VACUUM` перестраивает все индексы таблицы с нуля при каждом запуске. | Полная перестройка индексов — отдельная операция (`REINDEX`). Обычный `VACUUM` только чистит dead-записи внутри существующих. Частая ошибка — неправильное понимание этого момента в production коде.
> - [ ] `VACUUM` создаёт read-only копию таблицы, не затрагивая оригинал. | `VACUUM` работает in-place с оригинальной таблицей. Копию создаёт `VACUUM FULL` (во временный файл) или `pg_repack`.

## Q32. В чём разница между `VACUUM` и `VACUUM FULL`?

| Команда | Поведение |
|---------|---------|
| `VACUUM` | Помечает пространство мёртвых кортежей как свободное внутри таблицы. Не блокирует читателей/писателей |
| `VACUUM FULL` | Переписывает всю таблицу в новый файл, **реально возвращая** место ОС. Устанавливает эксклюзивную блокировку на таблицу |
| `VACUUM ANALYZE` | Выполняет `VACUUM` + обновляет статистику (`ANALYZE`) |

```sql
VACUUM ANALYZE orders;
VACUUM FULL orders;  -- осторожно: блокирует таблицу!
```

Альтернатива `VACUUM FULL` без длительной блокировки — расширение `pg_repack`.

> [!mcq]
> - [ ] `VACUUM FULL` работает без блокировок, как обычный `VACUUM`, но медленнее. | `VACUUM FULL` берёт `ACCESS EXCLUSIVE` lock — на таблице нельзя ни читать, ни писать, пока она переписывается в новый файл.
> - [x] `VACUUM FULL` переписывает всю таблицу в новый файл и реально возвращает место ОС, но требует `ACCESS EXCLUSIVE` lock. | Верно. Из-за блокировки на продакшене его почти не используют — предпочтительнее `pg_repack`, дающее тот же эффект без длительной блокировки.
> - [ ] `VACUUM FULL` переносит данные на другую файловую систему и обновляет путь tablespace. | Tablespace не меняется. `VACUUM FULL` лишь перезаписывает файлы в пределах текущего tablespace таблицы.
> - [ ] `VACUUM FULL` работает только на партиционированных таблицах. | Работает на любых таблицах. Для партиционированных выполняется отдельно на каждой партиции.

## Q33. Как работает `AUTOVACUUM` и как его настроить?

**`AUTOVACUUM`** — фоновый процесс, автоматически запускающий `VACUUM` и `ANALYZE` на таблицах, накопивших достаточно `dead tuples`.

**Ключевые параметры:**

```sql
-- Порог запуска VACUUM = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * n_live_tup
autovacuum_vacuum_threshold = 50       -- минимум dead tuples
autovacuum_vacuum_scale_factor = 0.2   -- 20% от числа живых строк

-- Для больших таблиц лучше снижать scale_factor
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 1000
);
```

**Мониторинг:**
```sql
SELECT relname, last_autovacuum, last_autoanalyze, n_dead_tup,
       autovacuum_count, autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

> [!mcq]
> - [x] `AUTOVACUUM` срабатывает, когда число dead tuples превышает `autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * n_live_tup`. | Верно. Для больших таблиц `scale_factor` часто снижают до 0.01–0.05, чтобы autovacuum запускался чаще, а не ждал 20% мертвых строк.
> - [ ] `AUTOVACUUM` срабатывает строго каждые 60 секунд и обрабатывает все таблицы подряд. | Интервал проверки — `autovacuum_naptime` (по умолчанию 1 минута), но это лишь период запуска launcher. Обрабатываются только таблицы, превысившие порог.
> - [ ] `AUTOVACUUM` запускается только вручную через `VACUUM` и не имеет автоматического планировщика. | `AUTOVACUUM` — фоновый процесс, запускаемый autovacuum launcher автоматически. Ручной запуск — это просто `VACUUM`.
> - [ ] `AUTOVACUUM` настраивается только глобально в `postgresql.conf` — для отдельной таблицы параметры задать нельзя. | Параметры можно задавать на уровне таблицы через `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.01)`.

## Q34. Что такое `table bloat` и как его измерить?

**`Table bloat`** — разница между реальным физическим размером таблицы/индекса и объёмом, фактически занятым живыми данными. Возникает из-за накопления `dead tuples` и незаполненных страниц.

```sql
-- Размер таблицы и индексов
SELECT
    relname,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    pg_size_pretty(pg_relation_size(relid)) AS table_size,
    pg_size_pretty(pg_indexes_size(relid)) AS indexes_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

Для детального анализа `bloat` используют расширение `pgstattuple` или запросы из набора `check_postgres`.

> [!mcq]
> - [ ] `Table bloat` — это разница между числом строк в таблице и числом записей в индексах. | Речь идёт о физическом размере: сколько места занимает таблица против того, сколько нужно живым данным. Разница в числе записей — другое явление.
> - [x] `Table bloat` — разница между физическим размером таблицы/индекса и реальным объёмом живых данных, возникающая из-за dead tuples и незаполненных страниц. | Верно. Для детального анализа используется расширение `pgstattuple` или запросы из `check_postgres`.
> - [ ] `Table bloat` — замедление запросов из-за устаревшей статистики планировщика. | Устаревшая статистика — отдельная проблема, решаемая `ANALYZE`. Bloat — про физический размер.
> - [ ] `Table bloat` устраняется автоматически через `ANALYZE` и не требует `VACUUM`. | `ANALYZE` обновляет статистику, но не чистит dead tuples. Для устранения bloat нужен `VACUUM` (или `VACUUM FULL`/`pg_repack` для возврата места).

## Q35. (!) Какие виды партиционирования поддерживает PostgreSQL?

PostgreSQL (с версии 10+) поддерживает **декларативное партиционирование**:

| Тип | Описание | Пример использования |
|-----|---------|---------------------|
| `RANGE` | По диапазону значений | Партиционирование по дате (`created_at`) |
| `LIST` | По списку значений | По стране, статусу, категории |
| `HASH` | По хэшу значения | Равномерное распределение по модулю |

```sql
-- RANGE партиционирование по дате
CREATE TABLE orders (
    id BIGSERIAL,
    user_id INT,
    total NUMERIC,
    created_at TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2025 PARTITION OF orders
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

CREATE TABLE orders_2026 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

-- LIST партиционирование
CREATE TABLE orders_by_region (
    id BIGSERIAL,
    region TEXT NOT NULL,
    total NUMERIC
) PARTITION BY LIST (region);

CREATE TABLE orders_ru PARTITION OF orders_by_region FOR VALUES IN ('RU');
CREATE TABLE orders_kz PARTITION OF orders_by_region FOR VALUES IN ('KZ');
```

**Подпартиционирование** (вложенное) также поддерживается: `RANGE + HASH`, `RANGE + LIST` и т. д.

> [!mcq]
> - [x] PostgreSQL поддерживает декларативное партиционирование по `RANGE`, `LIST` и `HASH` начиная с версии 10. | Верно. До PG 10 использовалось inheritance-партиционирование с триггерами/`CHECK`-констрейнтами. Декларативный синтаксис проще и поддерживает подпартиционирование.
> - [ ] PostgreSQL поддерживает только `RANGE`-партиционирование; `LIST` и `HASH` — удел других СУБД. | Все три типа поддерживаются с PG 10 (`HASH` — с PG 11).
> - [ ] PostgreSQL поддерживает партиционирование только через inheritance и триггеры, без декларативного синтаксиса. | Inheritance-партиционирование существует исторически, но с PG 10 есть декларативный синтаксис `PARTITION BY RANGE/LIST/HASH`.
> - [ ] PostgreSQL поддерживает только партиционирование по первичному ключу. | Партиционировать можно по любому выражению от столбцов. Первичный ключ лишь обязан включать ключ партиционирования (ограничение декларативного партиционирования).

## Q36. Как работает `partition pruning`?

**`Partition pruning`** — оптимизация планировщика: при наличии условия на ключ партиционирования PostgreSQL исключает нерелевантные партиции из плана запроса.

```sql
-- Планировщик прочитает только orders_2026
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';
```

**Динамический `pruning`** (PostgreSQL 11+): исключает партиции даже при параметризованных запросах или на этапе выполнения.

Проверить в плане: если партиция не упоминается в `EXPLAIN`, она была отсечена.

> [!mcq]
> - [ ] `Partition pruning` работает только на этапе планирования и не применяется к параметризованным запросам. | С PG 11 поддерживается динамический pruning на этапе выполнения — он умеет отсекать партиции даже для параметров из prepared statements.
> - [x] `Partition pruning` — оптимизация планировщика: при фильтре по ключу партиционирования нерелевантные партиции исключаются из плана. | Верно. С PG 11 работает и на этапе выполнения (runtime pruning) для параметризованных запросов.
> - [ ] `Partition pruning` — это механизм физического удаления старых партиций через `DROP PARTITION`. | Удаление партиций (`DETACH`/`DROP`) — отдельная операция. Pruning — про исключение партиций из плана запроса.
> - [ ] `Partition pruning` эффективен, только если включён параметр `enable_seqscan = off`. | Pruning работает независимо от `enable_seqscan`. Этот параметр влияет на выбор между Seq Scan и Index Scan внутри выбранных партиций. Частая ошибка — неправильное понимание этого момента в production коде.

## Q37. Когда партиционирование не даёт выигрыша?

- Запрос не фильтрует по ключу партиционирования — все партиции сканируются.
- Таблица небольшая — накладные расходы на `partition routing` перевешивают выгоду.
- Большое количество партиций (>1000) может замедлить планирование.
- `JOIN` между партиционированными и обычными таблицами без фильтра по ключу.
- Глобальные индексы не поддерживаются (только локальные — на каждой партиции).

> [!mcq]
> - [x] Партиционирование не даёт выигрыша, когда запрос не фильтрует по ключу партиционирования — сканируются все партиции. | Верно. Без partition pruning получаем накладные расходы на множество таблиц без выгоды. Также слишком много партиций (>1000) замедляет планирование.
> - [ ] Партиционирование всегда ускоряет любые запросы за счёт параллелизации. | Без фильтра по ключу партиционирования запрос пробежит по всем партициям — суммарно медленнее, чем одна непартиционированная таблица.
> - [ ] Партиционирование помогает только для INSERT, не для SELECT. | Партиционирование помогает и SELECT (через pruning), и массовому удалению (`DROP PARTITION`). Просто требует правильного ключа.
> - [ ] Партиционирование не работает с `JOIN` — PostgreSQL не поддерживает partition-wise join. | `partition-wise join` поддерживается (параметр `enable_partitionwise_join`, с PG 11). Проблема — в отсутствии фильтра по ключу, а не в JOIN как таковом.

## Q38. (!) Что такое оконные функции и как они работают?

**Оконные функции** выполняют вычисления по **набору строк, связанных с текущей строкой** (окну), не сворачивая результат в одну строку, как `GROUP BY`.

```sql
SELECT
    user_id,
    order_date,
    total,
    SUM(total) OVER (PARTITION BY user_id ORDER BY order_date) AS running_total,
    AVG(total) OVER (PARTITION BY user_id) AS avg_per_user,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_date DESC) AS rn
FROM orders;
```

**Синтаксис:**
```sql
function_name(...) OVER (
    [PARTITION BY col1, col2]
    [ORDER BY col3 [ASC|DESC]]
    [ROWS|RANGE BETWEEN ... AND ...]
)
```

**Виды функций:**
- **Ранжирование:** `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `NTILE(n)`
- **Смещение:** `LAG()`, `LEAD()`, `FIRST_VALUE()`, `LAST_VALUE()`, `NTH_VALUE()`
- **Агрегатные:** `SUM()`, `AVG()`, `COUNT()`, `MIN()`, `MAX()`

> [!mcq]
> - [ ] Оконные функции сворачивают набор строк в одну строку, как `GROUP BY`. | Наоборот: оконные функции возвращают результат для каждой строки, не сворачивая набор. Это ключевое отличие от `GROUP BY`.
> - [x] Оконные функции возвращают результат для каждой строки, используя набор связанных строк (окно), заданный через `PARTITION BY`/`ORDER BY`/фрейм. | Верно. `PARTITION BY` разбивает набор на группы, `ORDER BY` упорядочивает в группе, `ROWS/RANGE BETWEEN` задаёт фрейм внутри окна.
> - [ ] Оконные функции работают только с числовыми столбцами и применимы только для `SUM`/`AVG`. | Работают с любыми типами и включают ранжирование (`ROW_NUMBER`), смещение (`LAG`/`LEAD`), агрегаты и пользовательские агрегаты.
> - [ ] Оконные функции требуют создания временной таблицы через `WITH` перед применением. | Оконные функции вычисляются на лету и не требуют CTE/временной таблицы.

## Q39. Как работают `ROW_NUMBER`, `RANK` и `DENSE_RANK`?

| Функция | Описание | Поведение при дублях |
|---------|---------|---------------------|
| `ROW_NUMBER()` | Уникальный порядковый номер | Всегда уникален (произвольный порядок дублей) |
| `RANK()` | Ранг с пропуском при дублях | 1, 2, 2, 4 |
| `DENSE_RANK()` | Ранг без пропуска | 1, 2, 2, 3 |

```sql
SELECT
    name,
    score,
    ROW_NUMBER() OVER (ORDER BY score DESC) AS row_num,
    RANK()       OVER (ORDER BY score DESC) AS rnk,
    DENSE_RANK() OVER (ORDER BY score DESC) AS dense_rnk
FROM leaderboard;
```

**Распространённый паттерн:** топ-N записей на группу:

```sql
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
    FROM orders
) t
WHERE rn = 1; -- последний заказ каждого пользователя
```

> [!mcq]
> - [x] При дублях значения `RANK` оставляет пропуски (1, 2, 2, 4), а `DENSE_RANK` — нет (1, 2, 2, 3). | Верно. `ROW_NUMBER` всегда даёт уникальные номера (1, 2, 3, 4), произвольно разрешая дубли.
> - [ ] При дублях значения `RANK` и `DENSE_RANK` ведут себя одинаково и дают подряд идущие номера. | Они отличаются именно на дублях: `RANK` пропускает следующие номера, `DENSE_RANK` — нет.
> - [ ] `ROW_NUMBER` всегда совпадает с `RANK` при `ORDER BY` по уникальному ключу. | Только при отсутствии дублей по ключу сортировки. Тогда все три функции совпадают.
> - [ ] `RANK` и `DENSE_RANK` возвращают одинаковые значения для всех строк в окне. | Возвращают одинаковое значение только для равных по `ORDER BY` строк, а не для всех.

## Q40. Как работают `LAG` и `LEAD`?

- **`LAG(col, offset, default)`** — значение столбца из строки **выше** в окне на `offset` строк.
- **`LEAD(col, offset, default)`** — значение столбца из строки **ниже** в окне на `offset` строк.

```sql
SELECT
    order_date,
    total,
    LAG(total, 1, 0)  OVER (PARTITION BY user_id ORDER BY order_date) AS prev_total,
    LEAD(total, 1, 0) OVER (PARTITION BY user_id ORDER BY order_date) AS next_total,
    total - LAG(total) OVER (PARTITION BY user_id ORDER BY order_date) AS diff_from_prev
FROM orders;
```

Полезны для расчёта дельт, разниц между соседними строками, определения «предыдущего статуса».

> [!mcq]
> - [ ] `LAG(col)` возвращает значение столбца из следующей строки окна. | `LAG` — это значение из предыдущей строки. Значение из следующей возвращает `LEAD`.
> - [x] `LAG(col, offset, default)` возвращает значение столбца из строки на `offset` позиций выше в окне, `default` — при отсутствии такой строки. | Верно. `LEAD` работает симметрично в сторону следующих строк. Обе функции требуют `ORDER BY` в окне.
> - [ ] `LAG` и `LEAD` работают только внутри `GROUP BY` и не требуют `OVER`. | Они обязательно требуют `OVER (...)` — это оконные функции. В `GROUP BY` они не применимы.
> - [ ] `LAG(col)` возвращает сумму значений всех строк до текущей. | Сумма до текущей — это running total через `SUM(col) OVER (ORDER BY ...)`. `LAG` возвращает значение одной конкретной строки (на `offset` позиций назад).

## Q41. Как использовать `SUM OVER` и скользящие агрегаты?

```sql
-- Нарастающий итог (running total)
SELECT
    order_date,
    total,
    SUM(total) OVER (ORDER BY order_date) AS running_total
FROM orders;

-- Скользящее среднее за 7 дней
SELECT
    order_date,
    total,
    AVG(total) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS moving_avg_7d
FROM daily_revenue;

-- Итог в рамках группы (без ORDER BY — агрегат по всей группе)
SELECT
    user_id,
    total,
    SUM(total) OVER (PARTITION BY user_id) AS user_total
FROM orders;
```

**Фреймы:**
- `ROWS BETWEEN N PRECEDING AND CURRENT ROW` — фиксированное число строк.
- `RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW` — диапазон значений.

> [!mcq]
> - [x] `AVG(total) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` вычисляет скользящее среднее по текущей и 6 предыдущим строкам. | Верно. `ROWS` задаёт фрейм в строках. Для задания фрейма в логических единицах (например, 7 дней) используется `RANGE BETWEEN INTERVAL '7 days' PRECEDING`.
> - [ ] `AVG(total) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` вычисляет среднее по всем строкам окна, игнорируя фрейм. | Фрейм `ROWS BETWEEN ...` как раз ограничивает расчёт окном из 7 строк; игнорировать его нельзя.
> - [ ] Для running total нужен фрейм `ROWS BETWEEN UNBOUNDED FOLLOWING AND CURRENT ROW`. | Running total требует `UNBOUNDED PRECEDING AND CURRENT ROW` — от начала окна до текущей строки. `FOLLOWING` — будущие строки.
> - [ ] Без `ORDER BY` в окне `SUM(col) OVER ()` возвращает значение только текущей строки. | Без `ORDER BY` агрегат считается по всему окну (или партиции, если есть `PARTITION BY`) — для каждой строки одно и то же значение.

## Q42. (!) Что такое `CTE` и чем он отличается от подзапроса?

**`CTE` (Common Table Expression)** — именованный временный результат, объявляемый в `WITH`-блоке и используемый в основном запросе.

```sql
WITH active_users AS (
    SELECT id, name FROM users WHERE status = 'active'
),
recent_orders AS (
    SELECT user_id, SUM(total) AS total_spent
    FROM orders
    WHERE created_at > NOW() - INTERVAL '30 days'
    GROUP BY user_id
)
SELECT u.name, ro.total_spent
FROM active_users u
JOIN recent_orders ro ON u.id = ro.user_id
ORDER BY ro.total_spent DESC;
```

**`CTE` vs подзапрос:**
| Характеристика | `CTE` | Подзапрос |
|---------------|-------|-----------|
| Читаемость | Высокая, можно именовать | Может быть сложным при вложении |
| Повторное использование | Да (одно определение — несколько ссылок) | Нет |
| Оптимизация (PostgreSQL < 12) | `CTE` — «забор оптимизации» (materializes) | Встраивается в план |
| Оптимизация (PostgreSQL 12+) | По умолчанию встраивается, если не рекурсивный и без побочных эффектов | Встраивается |
| `MATERIALIZED` / `NOT MATERIALIZED` | Явное управление материализацией | Нет |

```sql
-- Принудительная материализация (PostgreSQL 12+)
WITH stats AS MATERIALIZED (
    SELECT AVG(total) AS avg_total FROM orders
)
SELECT * FROM orders, stats WHERE total > stats.avg_total;
```

> [!mcq]
> - [ ] В PostgreSQL 11 `CTE` всегда встраивается в основной запрос, как подзапрос. | В PG ≤ 11 `CTE` всегда материализовался («забор оптимизации»). Встраивание по умолчанию появилось с PG 12.
> - [x] В PostgreSQL 12+ `CTE` по умолчанию встраивается в основной запрос, если он не рекурсивный и без side-effects; можно форсировать через `MATERIALIZED`/`NOT MATERIALIZED`. | Верно. До PG 12 CTE всегда материализовался, что часто мешало оптимизации.
> - [ ] `CTE` всегда материализуется во временную таблицу на диске, независимо от версии. | В современных версиях PG материализация — частный случай, а не правило. CTE чаще встраивается напрямую в план.
> - [ ] `CTE` нельзя использовать несколько раз в одном запросе — только одна ссылка. | CTE можно ссылаться несколько раз; это одно из его ключевых преимуществ над подзапросами.

## Q43. (!) Как работают рекурсивные `CTE`?

**Рекурсивный `CTE`** позволяет выполнять иерархические или графовые запросы (обход дерева, поиск путей).

```sql
-- Обход иерархии сотрудников
WITH RECURSIVE emp_hierarchy AS (
    -- Базовый случай: корневые узлы
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Рекурсивный шаг
    SELECT e.id, e.name, e.manager_id, eh.depth + 1
    FROM employees e
    JOIN emp_hierarchy eh ON e.manager_id = eh.id
)
SELECT id, name, depth FROM emp_hierarchy ORDER BY depth, name;
```

**Структура:**
1. **Базовый запрос** — начальные строки (без рекурсии).
2. **`UNION ALL`** — объединение с рекурсивной частью.
3. **Рекурсивный запрос** — ссылается на имя `CTE`.

Итерации продолжаются, пока рекурсивный запрос не вернёт пустой результат. Для предотвращения бесконечных циклов можно ограничить глубину:

```sql
WHERE eh.depth < 10
```

> [!mcq]
> - [x] Рекурсивный CTE состоит из базового запроса и рекурсивной части, объединённых `UNION ALL`; итерации продолжаются, пока рекурсивный запрос возвращает строки. | Верно. Базовый случай — стартовый набор, рекурсивный — ссылается на имя CTE. Для защиты от циклов добавляют ограничение по глубине или `UNION` (дедупликация).
> - [ ] Рекурсивный CTE состоит из одного блока и автоматически обходит иерархию благодаря ключевому слову `RECURSIVE`. | Ключевое слово лишь разрешает самоссылку; сам запрос обязательно включает базовую и рекурсивную части через `UNION ALL`/`UNION`.
> - [ ] Рекурсивный CTE использует `JOIN LATERAL` вместо `UNION ALL`. | `LATERAL` — другой механизм (коррелированные подзапросы). Рекурсия в CTE всегда через `UNION ALL` или `UNION`.
> - [ ] Рекурсивный CTE работает только для строго двоичных деревьев. | Работает для произвольных иерархий и графов (с защитой от циклов). Не ограничен бинарными деревьями.

## Q44. (!) Что такое `streaming replication` в PostgreSQL?

**`Streaming replication`** — механизм физической репликации: первичный сервер (`primary`) передаёт `WAL`-записи на реплики (`standby`) в режиме реального времени через TCP-соединение.

**Режимы синхронизации:**
| Режим `synchronous_commit` | Описание |
|--------------------------|---------|
| `off` | Возврат клиенту до записи `WAL` на диск (риск потери данных) |
| `local` | Запись на диск `primary`, без ожидания реплики |
| `remote_write` | Ожидание записи `WAL` на диск реплики (без `fsync`) |
| `remote_apply` | Ожидание применения изменений на реплике |
| `on` | Синхронный: ожидание `fsync` на реплике |

**Настройка на `primary`:**

```sql
-- postgresql.conf
wal_level = replica
max_wal_senders = 5
```

**Настройка на `standby`:**

```
# recovery.conf / postgresql.conf (PG 12+)
primary_conninfo = 'host=primary-host port=5432 user=replication_user'
```

Реплика может использоваться для **read-only** запросов (`hot standby`).

> [!mcq]
> - [ ] `Streaming replication` передаёт на реплику только зафиксированные строки в логическом формате (INSERT/UPDATE/DELETE). | Это описание логической репликации. Streaming — физическая: передаются WAL-записи на уровне блоков данных.
> - [x] `Streaming replication` передаёт WAL-записи с primary на standby по TCP в режиме реального времени; реплика может быть read-only (`hot standby`). | Верно. Режимы синхронизации задаются `synchronous_commit` (`off`/`local`/`remote_write`/`remote_apply`/`on`).
> - [ ] `Streaming replication` поддерживает репликацию между разными major-версиями PostgreSQL. | Физическая репликация требует совпадения major-версии и платформы. Между разными версиями работает только логическая.
> - [ ] `Streaming replication` работает только в режиме async и не поддерживает синхронные коммиты. | Поддерживаются и async, и синхронные режимы через `synchronous_standby_names` и `synchronous_commit`.

## Q45. В чём разница между физической и логической репликацией?

| Характеристика | Физическая репликация | Логическая репликация |
|---------------|----------------------|----------------------|
| Единица | Блоки данных (`WAL`) | Строки (`INSERT`/`UPDATE`/`DELETE`) |
| Версия PostgreSQL | Должна совпадать | Может отличаться |
| Платформа | Должна совпадать | Может отличаться |
| Избирательность | Вся база данных | Выбранные таблицы |
| Применение | DR, read-реплики | Миграции, разнородные БД, CDC |

**Логическая репликация** (PostgreSQL 10+): работает через **Publication** (на primary) и **Subscription** (на replica).

```sql
-- На primary
CREATE PUBLICATION my_pub FOR TABLE orders, users;

-- На standby
CREATE SUBSCRIPTION my_sub
CONNECTION 'host=primary dbname=mydb user=repuser'
PUBLICATION my_pub;
```

> [!mcq]
> - [x] Логическая репликация работает построчно (`INSERT`/`UPDATE`/`DELETE`), допускает разные major-версии и выборочные таблицы через `PUBLICATION`/`SUBSCRIPTION`. | Верно. Удобна для миграций, CDC, частичной репликации. Физическая быстрее, но требует идентичных версий и реплицирует всё.
> - [ ] Логическая репликация работает блоками WAL, требует совпадения версий и реплицирует всю базу целиком. | Это характеристики физической репликации. Логическая строится поверх logical decoding и позволяет выборочность.
> - [ ] Логическая репликация невозможна в PostgreSQL — для неё нужны внешние инструменты вроде Debezium. | Нативная логическая репликация доступна с PostgreSQL 10 через `CREATE PUBLICATION`/`CREATE SUBSCRIPTION`. Внешние CDC-инструменты — это альтернатива, не замена.
> - [ ] Логическая репликация не поддерживает DDL-изменения. | Верное замечание (DDL автоматически не реплицируется), но суть различия не в DDL, а в том, что она работает с логическими операциями над строками, а не WAL-блоками.

## Q46. Что такое `replication slot` и зачем он нужен?

**`Replication slot`** — механизм, гарантирующий, что `primary` не удалит `WAL`-сегменты, пока реплика (или клиент логической репликации) их не получила.

```sql
-- Посмотреть слоты
SELECT * FROM pg_replication_slots;

-- Создать физический слот
SELECT pg_create_physical_replication_slot('standby1_slot');

-- Создать логический слот
SELECT pg_create_logical_replication_slot('my_slot', 'pgoutput');
```

**Риск:** если реплика надолго отстанет или отключится, `WAL`-сегменты будут накапливаться, что может привести к исчерпанию дискового пространства. Для мониторинга:

```sql
SELECT slot_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots;
```

> [!mcq]
> - [ ] `Replication slot` ускоряет передачу WAL на реплику за счёт сжатия и приоритетного канала. | Слот не занимается сжатием или приоритизацией. Его функция — гарантировать, что WAL не удалят до потребления репликой.
> - [x] `Replication slot` гарантирует, что primary не удалит WAL-сегменты, пока их не получит реплика или клиент логической репликации. | Верно. Это защищает от потери данных при отставании реплики, но даёт риск накопления WAL, если реплика надолго отключилась.
> - [ ] `Replication slot` автоматически переключает master и реплики при сбое. | Автоматическое переключение — задача failover-инструментов (Patroni, repmgr). Слот лишь удерживает WAL.
> - [ ] `Replication slot` предназначен только для логической репликации и не применяется к физической. | Существуют и физические, и логические слоты. Для физической репликации используется `pg_create_physical_replication_slot`.

## Q47. Как работает `full-text search` в PostgreSQL?

PostgreSQL поддерживает встроенный полнотекстовый поиск через типы `TSVECTOR` и `TSQUERY`.

```sql
-- TSVECTOR: нормализованный вектор слов
SELECT to_tsvector('russian', 'Быстрая коричневая лиса прыгает');

-- TSQUERY: запрос
SELECT to_tsquery('russian', 'лиса & прыгает');

-- Поиск
SELECT title FROM articles
WHERE to_tsvector('russian', body) @@ to_tsquery('russian', 'postgresql & индексы');

-- Ранжирование результатов
SELECT title, ts_rank(to_tsvector('russian', body), query) AS rank
FROM articles, to_tsquery('russian', 'postgresql') query
WHERE to_tsvector('russian', body) @@ query
ORDER BY rank DESC;
```

**Оптимизация:** хранить `TSVECTOR` в отдельном столбце и индексировать `GIN`:

```sql
ALTER TABLE articles ADD COLUMN tsv TSVECTOR
    GENERATED ALWAYS AS (to_tsvector('russian', title || ' ' || body)) STORED;

CREATE INDEX idx_articles_tsv ON articles USING GIN (tsv);
```

> [!mcq]
> - [x] Full-text search использует `tsvector` (нормализованный вектор лексем) и `tsquery` (запрос), сопоставляемые оператором `@@`; ускоряется `GIN`-индексом. | Верно. `to_tsvector('russian', ...)` выполняет токенизацию, стемминг и удаление стоп-слов согласно словарю.
> - [ ] Full-text search работает через стандартный оператор `LIKE` и `B-tree`-индекс по столбцу текста. | `LIKE` не учитывает стемминг, морфологию и ранжирование. Для полноценного поиска нужны `tsvector`/`tsquery`/`@@`.
> - [ ] Full-text search не поддерживает русскую морфологию. | PostgreSQL поддерживает русский словарь (`russian`) со стеммингом. Можно подключить `ispell`/`myspell`/`snowball`-словари для улучшения.
> - [ ] Full-text search не поддерживает ранжирование результатов. | Для ранжирования есть функции `ts_rank` и `ts_rank_cd` — по TF и позициям совпадений.

## Q48. (!) Какие операторы и функции доступны для `JSONB`?

**Операторы доступа:**
| Оператор | Описание | Пример |
|----------|---------|--------|
| `->` | Получить поле как `JSON` | `payload->'name'` |
| `->>` | Получить поле как `TEXT` | `payload->>'name'` |
| `#>` | Путь как `JSON` | `payload#>'{address,city}'` |
| `#>>` | Путь как `TEXT` | `payload#>>'{address,city}'` |

**Операторы поиска:**
| Оператор | Описание |
|----------|---------|
| `@>` | Содержит (правый в левом) |
| `<@` | Содержится (левый в правом) |
| `?` | Ключ существует |
| `?\|` | Хотя бы один ключ из массива существует |
| `?&` | Все ключи из массива существуют |

```sql
-- Поиск по вложенному полю
SELECT * FROM events WHERE payload @> '{"event_type": "purchase"}';

-- Проверка существования ключа
SELECT * FROM events WHERE payload ? 'discount_code';

-- Модификация JSONB
UPDATE events
SET payload = payload || '{"processed": true}'
WHERE id = 1;

-- Удаление ключа
UPDATE events SET payload = payload - 'temp_field' WHERE id = 1;

-- jsonb_set: обновить вложенное поле
UPDATE events
SET payload = jsonb_set(payload, '{user,name}', '"Alice"')
WHERE id = 1;
```

> [!mcq]
> - [ ] Оператор `->>` возвращает значение поля JSONB как `JSONB`, а `->` — как `TEXT`. | Всё наоборот: `->` возвращает `JSON`/`JSONB`, а `->>` — `TEXT`. Ошибка в операторах часто приводит к проблемам с кастингом.
> - [x] Оператор `@>` проверяет содержание (левый JSONB содержит правый), а `?` — существование ключа верхнего уровня. | Верно. `@>` — containment, идеален для фильтра по вложенному объекту; `?` — проверка ключа, `?|`/`?&` — OR/AND по списку ключей. Все ускоряются `GIN`.
> - [ ] Оператор `@>` проверяет равенство JSONB-значений, аналогично `=`. | `@>` проверяет именно вхождение, а не равенство. Равенство — оператор `=`.
> - [ ] Оператор `?` проверяет вхождение значения, аналогично `IN` для массивов. | `?` проверяет существование ключа верхнего уровня, а не значения. Для поиска значения используют `@>` или `->>`.

## Q49. (!) Что такое `PgBouncer` и зачем он нужен?

**`PgBouncer`** — легковесный пул соединений для PostgreSQL. PostgreSQL создаёт отдельный процесс на каждое соединение (~5–10 MB памяти), поэтому тысячи одновременных соединений приводят к деградации производительности.

**Проблема без пула:**
- Каждое соединение — отдельный `backend` процесс.
- Затраты на установку соединения: ~1–5 мс.
- `fork()` при каждом новом соединении.

**Решение с `PgBouncer`:**
- Приложения подключаются к `PgBouncer`, а не напрямую к PostgreSQL.
- `PgBouncer` поддерживает пул из N реальных соединений с `PostgreSQL`.
- Тысячи клиентских соединений → десятки реальных соединений.

```ini
# pgbouncer.ini
[databases]
mydb = host=localhost port=5432 dbname=mydb

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
```

> [!mcq]
> - [x] `PgBouncer` — лёгкий пул соединений: тысячи клиентских коннектов мультиплексируются в десятки реальных к PostgreSQL. | Верно. Решает проблему стоимости forking и памяти на backend-процесс (~5–10 MB). Особенно важен для кратковременных соединений web-приложений.
> - [ ] `PgBouncer` — репликационное middleware, передающее WAL между узлами кластера. | PgBouncer к репликации не относится. Это исключительно пул соединений.
> - [ ] `PgBouncer` — встроенный в PostgreSQL механизм, включаемый параметром `enable_pgbouncer`. | PgBouncer — отдельный процесс/сервис, устанавливается независимо от PostgreSQL.
> - [ ] `PgBouncer` — расширение для sharding: автоматически распределяет запросы по нескольким primary. | Шардинг — задача других инструментов (Citus, pgpool-II в некоторых конфигурациях). PgBouncer не маршрутизирует запросы между primaries.

## Q50. Какие режимы пулинга поддерживает `PgBouncer`?

| Режим | Описание | Ограничения |
|-------|---------|------------|
| `session` | Соединение держится на время сессии клиента | Минимальная экономия |
| `transaction` | Соединение возвращается в пул после каждой транзакции | Нельзя использовать `SET`, `LISTEN`, `PREPARE` между транзакциями |
| `statement` | Соединение возвращается после каждого оператора | Нельзя использовать многооператорные транзакции |

**Рекомендация:** `transaction` — оптимальный баланс между экономией соединений и совместимостью. `session` — если приложение активно использует `SESSION`-уровня настройки.

> [!mcq]
> - [ ] Режим `session` даёт максимальную экономию соединений и подходит для всех приложений. | Экономия в `session` минимальная — соединение держится всю клиентскую сессию. Максимум даёт `transaction` или `statement`. Частая ошибка — неправильное понимание этого момента в production коде.
> - [x] Режим `transaction` возвращает соединение в пул после каждой транзакции, что запрещает использовать `SET`/`LISTEN`/`PREPARE` между транзакциями. | Верно. Оптимальный баланс: существенная экономия соединений при разумных ограничениях. Это стандартный режим в большинстве продакшенов.
> - [ ] Режим `statement` требует обязательного использования multi-statement транзакций. | Наоборот: `statement` запрещает multi-statement транзакции, возвращая соединение после каждого оператора.
> - [ ] В режиме `transaction` prepared statements полностью поддерживаются без ограничений. | Server-side prepared statements не переживают смену соединения. В `transaction`-пуле их нельзя использовать напрямую (или нужны специальные обходные пути).

## Q51. (!) Какие типы блокировок существуют в PostgreSQL?

PostgreSQL использует многоуровневую систему блокировок:

**Блокировки таблиц (`table-level locks`):**

| Блокировка | Команды | Конфликтует с |
|-----------|---------|--------------|
| `ACCESS SHARE` | `SELECT` | `ACCESS EXCLUSIVE` |
| `ROW SHARE` | `SELECT FOR UPDATE/SHARE` | `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE` | `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY` | — |
| `SHARE` | `CREATE INDEX` | `ROW EXCLUSIVE` и выше |
| `SHARE ROW EXCLUSIVE` | — | `ROW EXCLUSIVE` и выше |
| `EXCLUSIVE` | — | Всё кроме `ACCESS SHARE` |
| `ACCESS EXCLUSIVE` | `DROP TABLE`, `TRUNCATE`, `ALTER TABLE` | Всё |

**Блокировки строк (`row-level locks`):**
- `FOR UPDATE` — эксклюзивная блокировка строки.
- `FOR NO KEY UPDATE` — не блокирует `SELECT FOR KEY SHARE`.
- `FOR SHARE` — разделяемая блокировка.
- `FOR KEY SHARE` — минимальная блокировка (для внешних ключей).

```sql
-- Посмотреть активные блокировки
SELECT pid, locktype, relation::regclass, mode, granted
FROM pg_locks
WHERE NOT granted;
```

> [!mcq]
> - [x] `ALTER TABLE` и `DROP TABLE` берут `ACCESS EXCLUSIVE` lock, который конфликтует даже с `SELECT`. | Верно. Поэтому DDL часто нужно запускать с `lock_timeout` и в короткие интервалы. Для безопасного `CREATE INDEX` существует `CONCURRENTLY`.
> - [ ] `ALTER TABLE` и `DROP TABLE` берут `SHARE UPDATE EXCLUSIVE`, не конфликтующий с `SELECT`. | `SHARE UPDATE EXCLUSIVE` — блокировка более слабых операций (`VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY`). DDL берёт `ACCESS EXCLUSIVE`. Частая ошибка — неправильное понимание этого момента в production коде.
> - [ ] `ALTER TABLE` и `DROP TABLE` работают без блокировок благодаря MVCC. | MVCC избавляет от блокировок между читателями и писателями строк, но DDL — это всегда эксклюзивная блокировка уровня объекта.
> - [ ] `ALTER TABLE` берёт `ROW EXCLUSIVE`, как `UPDATE`. | `ROW EXCLUSIVE` берут DML (`INSERT`/`UPDATE`/`DELETE`). DDL всегда требует более сильной блокировки, обычно `ACCESS EXCLUSIVE`.

## Q52. Что такое `deadlock` и как PostgreSQL его обнаруживает?

**`Deadlock`** — ситуация, когда две (или более) транзакции ожидают блокировки, удерживаемые друг другом, и ни одна не может продолжить выполнение.

```
Транзакция A: держит блокировку строки 1, ждёт строку 2
Транзакция B: держит блокировку строки 2, ждёт строку 1
```

PostgreSQL автоматически обнаруживает `deadlock` через периодический анализ графа ожидания (раз в `deadlock_timeout`, по умолчанию `1s`). При обнаружении одна из транзакций откатывается с ошибкой `ERROR: deadlock detected`.

**Предотвращение:**
- Всегда обновлять/блокировать строки в одном порядке.
- Использовать `SELECT ... FOR UPDATE` явно и последовательно.
- Минимизировать время жизни транзакций.
- Использовать `NOWAIT` или `SKIP LOCKED` для неблокирующих операций.

```sql
-- Попытка захватить блокировку без ожидания
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;

-- Пропустить заблокированные строки
SELECT * FROM jobs WHERE status = 'pending' FOR UPDATE SKIP LOCKED LIMIT 1;
```

> [!mcq]
> - [x] PostgreSQL обнаруживает deadlock через периодический анализ графа ожиданий (`deadlock_timeout` = 1 сек) и откатывает одну из транзакций с `ERROR: deadlock detected`. | Верно. `SKIP LOCKED` и `NOWAIT` позволяют избежать ожидания блокировок в очередях задач и при конкурентных выборках.
> - [ ] PostgreSQL предотвращает deadlock путём упорядочивания всех блокировок на уровне движка. | Автоматического упорядочивания нет. Приложение само должно блокировать объекты в согласованном порядке.
> - [ ] PostgreSQL зависает в deadlock до вмешательства администратора и ручного отмены запроса. | PostgreSQL сам обнаруживает deadlock и откатывает одну из транзакций — вмешательство не требуется.
> - [ ] PostgreSQL вообще не допускает deadlock благодаря MVCC. | MVCC решает проблему блокировок чтения/записи на уровне строк, но deadlock между разными блокировками всё равно возможен.

| Параметр | Рекомендация | Описание |

> [!mcq]
> - [ ] `work_mem` задаёт общий объём памяти на все соединения сервера. | `work_mem` — это память **на каждую операцию сортировки/хэширования в каждом запросе**. При большом числе соединений общий расход может многократно превысить номинал.
> - [x] `work_mem` — память на каждую операцию сортировки/хэш-соединения в одном запросе; увеличение помогает сложным запросам, но общий расход кратен числу параллельных сортировок. | Верно. Типично 4–64 MB. Для тяжёлых аналитических запросов можно временно повысить локально через `SET LOCAL work_mem = '256MB'`.
> - [ ] `work_mem` влияет только на `VACUUM` и `CREATE INDEX`. | На эти операции влияет `maintenance_work_mem`. `work_mem` — про сортировку и хэши в обычных запросах.
> - [ ] `work_mem` должен быть равен `shared_buffers`. | Это независимые параметры с разным назначением. `shared_buffers` — кэш страниц (25% RAM), `work_mem` — память на операцию запроса (мегабайты).

## Q54. Как анализировать медленные запросы?

**1. Включить логирование медленных запросов:**

```sql
-- postgresql.conf
log_min_duration_statement = 1000  -- запросы дольше 1 секунды
log_line_prefix = '%t [%p] %d %u '
```

**2. Использовать `pg_stat_statements`:**

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Топ-10 запросов по суммарному времени
SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- Сбросить статистику
SELECT pg_stat_statements_reset();
```

**3. Анализировать конкретный запрос:**

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT ...;
```

**4. Проверить `pg_stat_activity`:**

```sql
SELECT pid, query, state, wait_event_type, wait_event, now() - query_start AS duration
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY duration DESC;
```

> [!mcq]
> - [x] `pg_stat_statements` агрегирует нормализованные запросы (без литералов) с суммарным и средним временем — идеально для поиска топ-нагружающих запросов. | Верно. Параметры заменяются на `$1`, `$2`, так что похожие запросы группируются. Для деталей конкретного случая — логи `log_min_duration_statement` и `EXPLAIN ANALYZE`.
> - [ ] `pg_stat_statements` логирует каждый запрос в отдельный файл на диск. | Данные собираются в памяти и периодически сохраняются в служебный файл, но не в отдельный файл на запрос.
> - [ ] `pg_stat_statements` требует отдельной лицензии Enterprise. | Это стандартное расширение PostgreSQL, устанавливается через `CREATE EXTENSION`.
> - [ ] `pg_stat_statements` показывает только DDL-запросы, пропуская SELECT/INSERT. | Показывает любые SQL-запросы. Именно аналитика DML — его основной use case.

## Q55. Какие популярные расширения PostgreSQL стоит знать?

| Расширение | Назначение |
|-----------|-----------|
| `pg_stat_statements` | Статистика выполнения SQL-запросов |
| `pg_trgm` | Поиск по подстроке (`LIKE '%term%'`), `GIN`/`GiST` |
| `PostGIS` | Геопространственные данные и функции |
| `uuid-ossp` / `gen_random_uuid()` | Генерация `UUID` (встроена с PG 13) |
| `hstore` | Хранилище пар ключ-значение |
| `pgcrypto` | Функции шифрования и хэширования |
| `tablefunc` | `crosstab` — сводные таблицы |
| `pg_partman` | Автоматическое управление партиционированием |
| `timescaledb` | Time-series данные на основе PostgreSQL |
| `pg_repack` | Перепаковка таблиц без длительной блокировки (альтернатива `VACUUM FULL`) |
| `pgaudit` | Аудит SQL-операций |
| `pg_bouncer` | Пул соединений (отдельный процесс, не расширение) |

```sql
-- Установить расширение
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Посмотреть установленные расширения
SELECT name, default_version, installed_version, comment
FROM pg_available_extensions
WHERE installed_version IS NOT NULL;
```

> [!mcq]
> - [ ] `pg_trgm` предназначен для геопространственных данных и работы с координатами. | Геопространство — это `PostGIS`. `pg_trgm` работает с триграммами (трёхбуквенными подстроками) для fuzzy-поиска текста.
> - [x] `pg_trgm` ускоряет поиск `LIKE '%term%'` и подобный поиск через триграммы и `GIN`/`GiST`-индексы. | Верно. Также поддерживает операторы похожести (`%`, `<->`) и `similarity()`. Классическое решение для автодополнения и поиска с опечатками.
> - [ ] `pg_trgm` шифрует хранимые строки для защиты от утечек данных. | Шифрование — это `pgcrypto`. `pg_trgm` работает с fuzzy-поиском и похожестью строк.
> - [ ] `pg_trgm` автоматически включает партиционирование текстовых столбцов. | Автоматического партиционирования в PostgreSQL нет. `pg_trgm` — про поиск по подстроке и похожести.
