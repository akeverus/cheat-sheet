# Вопросы на собеседовании: `PostgreSQL`

Подробные ответы по `PostgreSQL`: архитектура, типы данных, индексы, `EXPLAIN`, транзакции, `MVCC`, `VACUUM`, партиционирование, оконные функции, `CTE`, репликация, `full-text search`, `JSONB`, `PgBouncer`, блокировки, производительность, расширения.

Краткое введение: **PostgreSQL** — объектно-реляционная СУБД с открытым кодом, известная надёжностью, расширяемостью и полным соответствием стандарту `SQL`. Отличается богатой системой типов (`JSONB`, массивы, `UUID`, `enum`, пользовательские типы), мощным планировщиком запросов, `MVCC`-изоляцией и развитой инфраструктурой для репликации и горизонтального масштабирования. На собеседованиях проверяют понимание внутреннего устройства (процессы, `WAL`, `shared buffers`), умение читать планы запросов (`EXPLAIN ANALYZE`), знание индексов, уровней изоляции и типичных приёмов оптимизации.

## Q1. (!) Какова архитектура процессов PostgreSQL?

PostgreSQL использует **мультипроцессную архитектуру**: каждое клиентское соединение обслуживается отдельным процессом ОС — `backend`. На запросы клиента работает этот процесс, а вспомогательные процессы отвечают за запись страниц, WAL и обслуживание сервера.

Из этого вытекает практическое следствие: каждое соединение требует отдельного процесса и памяти. При большой конкуренции соединений оценивают накладные расходы и при необходимости ставят пул (`PgBouncer`). [How Connections Are Established](https://www.postgresql.org/docs/18/connect-estab.html).

Главные процессы:

| Процесс | Назначение |
|---------|-----------|
| `postmaster` | Главный процесс, принимает входящие соединения, порождает дочерние процессы |
| `backend` | Один на соединение, выполняет запросы клиента |
| `checkpointer` | Записывает грязные страницы из `shared_buffers` на диск при `checkpoint` |
| `background writer` | Упреждающая запись грязных страниц, снижает нагрузку на `checkpoint` |
| `WAL writer` | Сбрасывает буферы `WAL` на диск |
| `autovacuum launcher` | Запускает рабочие процессы `autovacuum` |
| `wal sender/receiver` | Репликация: отправка/приём WAL на реплику |

Отдельного процесса `stats collector` нет с PostgreSQL 15: накопленная статистика хранится в разделяемой памяти. Процессы используют **разделяемую память** (`shared memory`) и семафоры. В общей памяти находятся `shared_buffers` (кэш страниц данных), `WAL buffers` и данные о блокировках. Подготовленные запросы и их планы относятся к сеансу, а не к общему кэшу планов для всех подключений. [PostgreSQL 15 Release Notes](https://www.postgresql.org/docs/15/release-15.html), [Protocol Overview](https://www.postgresql.org/docs/18/protocol-overview.html).

```sql
-- Посмотреть активные клиентские сессии, а не фоновые процессы
SELECT pid, usename, application_name, state, query
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND state <> 'idle';
```

## Q2. Что такое `shared_buffers` и как он влияет на производительность?

**`shared_buffers`** — общий кэш страниц данных в памяти, разделяемый между процессами PostgreSQL. Если страницы там нет, сервер запрашивает её у ОС; та может вернуть страницу из собственного файлового кэша без физического чтения с диска. Высокая доля попаданий полезна, но сама по себе не доказывает низкую задержку запросов.

PostgreSQL опирается и на **кэш файловой системы ОС** (`page cache`). Размер `shared_buffers` выбирают с учётом памяти для ОС, сортировок, соединений и реальной нагрузки, а не по одной доле попаданий.

**Рекомендации по настройке:**
- Для выделенного сервера с **не менее 1 GB RAM** документация называет **25% RAM** разумной стартовой точкой, а не обязательной целью. Жёсткого потолка 8–16 GB нет; увеличение проверяют на своей нагрузке. Обычно доля выше 40% RAM не даёт выигрыша из-за роли кэша ОС.
- Увеличение `shared_buffers` может сократить промахи общего кэша, но требует памяти и нередко пересмотра `max_wal_size`.
- Изменение `shared_buffers` требует перезапуска сервера; сначала измеряют нагрузку и проверяют, хватит ли памяти остальным потребителям.
- В паре с `shared_buffers` настраивают `effective_cache_size` — это не выделение памяти, а **подсказка планировщику** о суммарном размере доступного кэша (свой + ОС). Завышенный `effective_cache_size` склоняет планировщик чаще выбирать индексы.

```sql
-- Посмотреть текущие значения
SHOW shared_buffers;
SHOW effective_cache_size;

-- Доля попаданий в shared buffers для страниц таблиц; это не доля физических чтений с диска
SELECT sum(heap_blks_hit)::numeric /
       NULLIF(sum(heap_blks_hit) + sum(heap_blks_read), 0) AS cache_hit_ratio
FROM pg_statio_user_tables;
```

Универсального порога вроде «выше 99%» нет. Этот запрос не учитывает индексные блоки и не различает чтение из кэша ОС и с устройства. Счётчики накопительные с момента сброса статистики, поэтому сравнивайте интервалы под нагрузкой, а результат сопоставляйте с задержками, `EXPLAIN (ANALYZE, BUFFERS)` и статистикой ввода-вывода. [Resource Consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html), [Cumulative Statistics](https://www.postgresql.org/docs/18/monitoring-stats.html).

## Q3. (!) Что такое `WAL` и зачем он нужен?

**`WAL` (Write-Ahead Log)** — журнал предзаписи. Его правило касается **записи на постоянное хранилище**: запись WAL об изменении должна быть сброшена до записи соответствующей страницы данных на диск. Страницу можно изменить в памяти раньше сброса WAL; её запись на диск откладывается. Сброс грязных страниц происходит не только при `checkpoint`.

Если страница не успела попасть на диск до сбоя, PostgreSQL повторяет нужные изменения из сохранённого WAL при восстановлении. При обычном синхронном коммите запись журнала сохраняют до ответа клиенту; `synchronous_commit=off` ослабляет гарантию сохранения последних подтверждённых транзакций при сбое. [Write-Ahead Logging](https://www.postgresql.org/docs/18/wal-intro.html).

**Что это даёт:**
- **Восстановление после сбоя:** изменения повторяют из `WAL` начиная с redo-позиции последнего `checkpoint`.
- **Производительность:** последовательная запись журнала позволяет не сбрасывать каждую изменённую страницу при каждом коммите; страницы записываются позже.
- **Репликация:** те же `WAL`-записи потоком уходят на реплики (`streaming replication`).
- **Point-in-Time Recovery (PITR):** базовая копия и непрерывная последовательность архивных `WAL` позволяют восстановиться на выбранную точку после начала этой копии. Для архивирования нужны `wal_level=replica` или выше, `archive_mode` и рабочий `archive_command` либо `archive_library`; одного локального каталога `pg_wal` недостаточно. [Continuous Archiving and PITR](https://www.postgresql.org/docs/18/continuous-archiving.html).

**Ключевые параметры:**
| Параметр | Описание |
|---------|---------|
| `wal_level` | Уровень детализации: `minimal`, `replica`, `logical` |
| `synchronous_commit` | Уровень ожидания локального сброса WAL или подтверждения синхронной standby: `on`, `off`, `local`, `remote_write`, `remote_apply` (см. Q44) |
| `wal_compression` | Сжатие полных образов страниц, записываемых в WAL, а не целых сегментов |
| `archive_mode` | Включить архивирование WAL |

```sql
SHOW wal_level;
SHOW effective_wal_level; -- PostgreSQL 19+
SHOW synchronous_commit;
```

С PostgreSQL 19 `wal_level` показывает настройку сервера, а `effective_wal_level` — фактический уровень детализации WAL. Например, на издателе с настройкой `replica` создание первого логического слота поднимает фактический уровень до `logical`. После удаления или инвалидирования последнего логического слота уровень возвращается к `replica`. [Параметры WAL PostgreSQL 19](https://www.postgresql.org/docs/19/runtime-config-wal.html#GUC-WAL-LEVEL).
**Сжатие WAL при обновлении с 18 до 19.** В PostgreSQL 18 значение `wal_compression=on` выбирает `pglz`. В 19 оно выбирает первый доступный алгоритм в порядке `zstd`, `lz4`, `pglz`. Доступность первых двух зависит от сборки. Значение по умолчанию в обеих версиях — `off`. Если при сравнении до и после обновления важно сохранить тот же алгоритм, задайте `pglz` явно. Для оценки выигрыша сравните объём WAL и нагрузку на CPU при записи и воспроизведении на сопоставимой нагрузке. [PostgreSQL 18](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-WAL-COMPRESSION), [PostgreSQL 19](https://www.postgresql.org/docs/19/runtime-config-wal.html#GUC-WAL-COMPRESSION).

**Как измерить вклад полных образов страниц.** В PostgreSQL 19 снимите `wal_bytes`, `wal_fpi` и `wal_fpi_bytes` из `pg_stat_wal` до и после интервала нагрузки. Убедитесь, что `stats_reset` не изменился. Разность `wal_fpi_bytes` показывает объём полных образов за интервал, а её отношение к приросту `wal_bytes` — их долю в сгенерированном WAL при ненулевом приросте. В PostgreSQL 18 есть счётчик образов `wal_fpi`, но умножение их числа на размер страницы не даёт записанный объём: образ может быть сжат или записан без свободной области страницы. Счётчики общие для кластера. Чтобы проверить вклад конкретного запроса, в PostgreSQL 19 можно отдельно выполнить `EXPLAIN (ANALYZE, WAL)` на тестовых данных. `ANALYZE` действительно выполняет запрос. [Статистика WAL в 19](https://www.postgresql.org/docs/19/monitoring-stats.html#MONITORING-PG-STAT-WAL), [статистика WAL в 18](https://www.postgresql.org/docs/18/monitoring-stats.html#MONITORING-PG-STAT-WAL), [изменения PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html).

## Q4. Как работает `checkpoint` в PostgreSQL?

**`Checkpoint`** — точка в последовательности WAL, до которой изменения файлов таблиц и индексов гарантированно записаны на диск. Checkpointer записывает грязные страницы, относящиеся к этой точке, и создаёт запись checkpoint в WAL. После сбоя восстановление начинает REDO с позиции, указанной последним checkpoint, а не обязательно с начала его записи или WAL-файла. [WAL Configuration](https://www.postgresql.org/docs/18/wal-configuration.html).

Компромисс: более частые checkpoint могут сократить объём REDO после сбоя, но увеличивают число записей страниц и объём WAL из-за полных образов страниц. Запись грязных страниц распределяют по интервалу, чтобы снизить пики I/O; редкие checkpoint могут увеличить время восстановления и объём удерживаемого WAL.

**Параметры:**
- `checkpoint_timeout` (по умолчанию `5min`) — интервал планового запуска checkpoint; если после предыдущего не было новых записей WAL, очередной может быть пропущен.
- `max_wal_size` — мягкий ориентир размера WAL для автоматического запуска checkpoint: при нагрузке, архивации или слотах фактический размер может его превысить.
- `checkpoint_completion_target` (по умолчанию `0.9`) — доля интервала, к концу которой планируется завершить запись грязных страниц. Это сглаживает I/O, но не задаёт жёсткую длительность checkpoint.

**Как проверить на сервере:** в PostgreSQL 17+ `pg_stat_checkpointer` показывает число checkpoint, время записи и синхронизации страниц, число записанных буферов. Сравнивайте прирост счётчиков за одинаковые интервалы под нагрузкой, а не одно накопленное значение. В PostgreSQL 18 `num_timed` и `num_requested` учитывают и пропущенные checkpoint; `num_done` считает только выполненные. В PostgreSQL 17 колонки `num_done` ещё нет, а `num_requested` считает выполненные запрошенные checkpoint. [Statistics Views](https://www.postgresql.org/docs/18/monitoring-stats.html), [PostgreSQL 17](https://www.postgresql.org/docs/17/monitoring-stats.html), [PostgreSQL 18 Release Notes](https://www.postgresql.org/docs/18/release-18.html).

```sql
-- PostgreSQL 18: счётчики всего кластера с момента stats_reset
SELECT num_timed, num_requested, num_done,
       write_time, sync_time, buffers_written, stats_reset
FROM pg_stat_checkpointer;
```

## Q5. Что такое `pg_hba.conf` и для чего он используется?

**`pg_hba.conf`** (`host-based authentication`) — файл, который решает, **кому и как разрешено подключаться**: ещё до проверки пароля сервер сверяет соединение с правилами в этом файле. Запись аутентификации задаёт тип соединения, базу, пользователя, адрес клиента и метод. Файл может также содержать директивы включения других файлов.

Правила читаются сверху вниз, и применяется **первое совпавшее** — порядок строк важен. Если ни одно правило не подошло, в подключении отказывают.
Если аутентификация по выбранному правилу не прошла, к следующим правилам сервер уже не переходит. После изменения файла на работающем сервере конфигурацию обычно перечитывают через `pg_reload_conf()`; на Windows новые подключения видят изменения сразу. `pg_hba_file_rules` показывает ошибки в **текущем содержимом файла**, но не подтверждает, что сервер уже загрузил именно эту версию правил. [System View](https://www.postgresql.org/docs/18/view-pg-hba-file-rules.html).

```
# TYPE  DATABASE  USER    ADDRESS         METHOD
host    mydb      myuser  192.168.1.0/24  scram-sha-256
local   all       all                     peer
host    all       all     0.0.0.0/0       scram-sha-256
```

**Методы аутентификации:** `trust`, `peer`, `md5`, `scram-sha-256`, `ldap`, `cert`, `radius` и другие. `peer` применяется к локальным Unix-сокетам; `md5` ещё принимается, но поддержка MD5-хешей паролей помечена как устаревающая. Для новых парольных правил выбирайте `scram-sha-256` при поддержке его клиентом. Если между клиентом и PostgreSQL стоит PgBouncer, его собственные правила аутентификации настраивают отдельно (см. Q49).

Источник: [PostgreSQL 18 — The pg_hba.conf File](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html).

## Q6. (!) Какие специальные типы данных поддерживает PostgreSQL?

Помимо чисел и строк PostgreSQL предлагает типы под документы, адреса, интервалы, массивы и другие данные. Выбирают тип по операциям, ограничениям и нужным индексам, а не только по форме значения. Большинство типов ниже встроены; `hstore` поставляется с PostgreSQL как расширение и подключается отдельно командой `CREATE EXTENSION hstore`.

| Тип | Описание |
|-----|---------|
| `JSONB` | Разобранное двоичное представление JSON; поддерживает GIN по содержимому |
| `JSON` | Исходный текст JSON с порядком и дубликатами ключей; по извлечённому значению возможен индекс по выражению |
| `UUID` | 128-битный универсальный идентификатор |
| `ARRAY` | Массив элементов выбранного типа (`int[]`, `text[]` и др.) |
| `hstore` | Плоские пары «ключ → значение»: ключ — строка, значение — строка или SQL `NULL`; дополнительное расширение |
| `ENUM` | Перечислимый тип |
| `INET`, `CIDR` | IP-адреса и подсети |
| `daterange`, `tsrange`, `tstzrange` | Диапазоны дат и временных меток без/с часовым поясом; есть также multirange-типы для нескольких непересекающихся диапазонов |
| `TSVECTOR` | Full-text search вектор |
| `BYTEA` | Бинарные данные |
| `XML` | XML-данные |
| `POINT`, `LINE`, `POLYGON` | Геометрические типы |
| `money` | Денежная сумма с точностью и форматированием, зависящими от `lc_monetary`; для управляемой точности обычно выбирают `numeric` |

Например, для поиска по содержимому документа можно взять `jsonb` с GIN; для IP-адреса — `inet`, а для интервала дат — `daterange`. `hstore` подходит для плоских строковых атрибутов, но сначала нужно установить расширение в базе. Более подробное сравнение `json` и `jsonb` — в Q7, `hstore` — в Q9.
В сетевых типах есть тонкость: `inet` допускает адрес узла с маской, например `192.168.0.1/24`, а `cidr` требует, чтобы биты за маской были нулевыми.
Для расписания диапазон удобнее двух независимых дат: `&&` проверяет пересечение, а GiST-индекс может ускорить такой поиск. `EXCLUDE USING GIST (during WITH &&)` позволяет запретить пересекающиеся интервалы; обычный `UNIQUE` запрещает только равные значения. Если нужны несколько раздельных интервалов в одном значении, используют соответствующий multirange-тип. [Range Types](https://www.postgresql.org/docs/18/rangetypes.html).

Источники: [PostgreSQL 18 — Data Types](https://www.postgresql.org/docs/18/datatype.html), [JSON Types](https://www.postgresql.org/docs/18/datatype-json.html), [Network Address Types](https://www.postgresql.org/docs/18/datatype-net-types.html), [hstore](https://www.postgresql.org/docs/18/hstore.html), [Monetary Types](https://www.postgresql.org/docs/18/datatype-money.html).

## Q7. В чём разница между `JSON` и `JSONB`?

Коротко: `JSON` хранит исходный текст как есть, а `JSONB` — разобранную бинарную структуру. Отсюда вытекают все различия в таблице.

| Характеристика | `JSON` | `JSONB` |
|---------------|--------|---------|
| Хранение | Текст (оригинальная строка) | Бинарный формат |
| Порядок ключей | Сохраняется | Не гарантируется |
| Дубли ключей | Сохраняются | Последнее значение |
| Индексирование | Индекс по выражению для извлечённого значения | `GIN` по документу, индексы по выражениям и другие варианты |
| Производительность записи | Быстрее | Медленнее (парсинг при вставке) |
| Производительность чтения | Медленнее (парсинг при выборке) | Быстрее |

Логика проста: `JSONB` платит разбором при вставке, зато операции с документом работают по уже готовой структуре. Функциям обработки `JSON` приходится разбирать исходный текст при каждом вызове. Индекс по выражению, например по `(payload->>'status')`, возможен и для `JSON`; GIN по содержимому целого документа предназначен для `JSONB`.

**Что выбирать:** `JSONB` обычно удобнее, когда нужны поиск по содержимому и индексирование документа. `JSON` подходит, когда нужно сохранить исходную запись, включая пробелы, порядок ключей и дубликаты. Выбор индекса зависит от выражения и оператора запроса: обычный GIN по колонке `jsonb` не обязан помогать предикату по вложенному выражению `payload->'tags'`; там может понадобиться индекс по выражению.

**Граница ввода:** `jsonb` преобразует числа в PostgreSQL `numeric`, поэтому отклоняет числа вне его диапазона; `json` может сохранить такой исходный текст. `jsonb` также отклоняет escape-последовательность `\u0000` и некорректные суррогатные пары уже при вводе. `json` проверяет некоторые такие случаи только при последующей обработке, поэтому успешная вставка в `json` не гарантирует успешного преобразования в `jsonb`. [JSON Input](https://www.postgresql.org/docs/18/datatype-json.html).

```sql
CREATE TABLE events (
    id SERIAL PRIMARY KEY,
    payload JSONB
);

-- GIN-индекс для JSONB
CREATE INDEX idx_events_payload ON events USING GIN (payload);
```

Источник: [PostgreSQL 18 — JSON Types and Indexing](https://www.postgresql.org/docs/18/datatype-json.html).

## Q8. Как работают массивы (`arrays`) в PostgreSQL?

Массивы позволяют хранить несколько значений одного типа прямо в одном поле. PostgreSQL поддерживает и многомерные массивы. Для коротких списков, которые обычно читают вместе со строкой, это может быть проще отдельной таблицы; если элементам нужны собственные атрибуты, ограничения и связи, лучше моделировать их строками отдельной таблицы.

Ключевые операции: `= ANY(tags)` сравнивает значение с элементами массива; `@>` проверяет включение массива, `&&` — пересечение, `unnest` разворачивает элементы в строки. `@>` сравнивает наборы: повторы не учитываются как отдельные экземпляры (`ARRAY[1] @> ARRAY[1,1]` истинно).

```sql
-- Создание таблицы с массивом
CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    tags TEXT[]
);

-- Вставка
INSERT INTO articles (tags) VALUES ('{"postgresql","database","sql"}');
INSERT INTO articles (tags) VALUES (ARRAY['performance', 'indexing']);

-- Запрос: содержит ли массив элемент
SELECT * FROM articles WHERE 'postgresql' = ANY(tags);

-- Запрос: все элементы массива присутствуют
SELECT * FROM articles WHERE tags @> ARRAY['postgresql', 'sql'];

-- unnest: развернуть массив в строки
SELECT id, unnest(tags) AS tag FROM articles;
```

Для поиска по `@>` и `&&` можно создать GIN-индекс на массив. Стандартный класс операторов GIN для массивов поддерживает `@>`, `<@`, `&&` и равенство массивов, но не выражение `= ANY(tags)`. Даже при подходящем индексе планировщик может предпочесть последовательное сканирование на небольших таблицах или при низкой селективности; проверяйте план через `EXPLAIN`.

Объявление `integer[3]` или `integer[3][3]` **не ограничивает** длину и число измерений: PostgreSQL считает массивы одного элементного типа одним типом независимо от этих чисел. Если точная форма обязательна, задают отдельное ограничение. При `= ANY(tags)` массив с `NULL`-элементом и без совпадений даёт SQL `NULL`, а не `FALSE`; пустой массив даёт `FALSE`. [Arrays](https://www.postgresql.org/docs/18/arrays.html), [ANY/SOME](https://www.postgresql.org/docs/18/functions-comparisons.html#FUNCTIONS-COMPARISONS-ANY-SOME).

```sql
CREATE INDEX idx_articles_tags ON articles USING GIN (tags);
```

Источники: [PostgreSQL 18 — Arrays](https://www.postgresql.org/docs/18/arrays.html), [Array Functions and Operators](https://www.postgresql.org/docs/18/functions-array.html), [GIN Indexes](https://www.postgresql.org/docs/18/gin.html).

## Q9. Что такое `hstore` и когда его использовать?

**`hstore`** — поставляемое с PostgreSQL расширение для плоского набора пар `ключ => значение`. Ключи — строки, значения — строки либо SQL `NULL`. Вложенных объектов нет. Тип полезен для разреженных плоских атрибутов, когда список ключей различается между строками.

```sql
CREATE EXTENSION IF NOT EXISTS hstore;

CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT,
    attributes HSTORE
);

INSERT INTO products (name, attributes)
VALUES ('Shirt', 'color => "red", size => "L", material => "cotton"');

-- Получить значение по ключу
SELECT attributes -> 'color' FROM products;

-- Фильтр по ключу-значению
SELECT * FROM products WHERE attributes @> 'color => "red"';
```

**Когда использовать:** если схема уже использует `hstore` или нужны именно плоские строковые атрибуты и его операторы. Для вложенных структур, чисел и булевых значений обычно удобнее `jsonb` (Q7). В `hstore` одинаковые ключи не сохраняются как разные пары; если ключ повторён во входе, нельзя полагаться на выбор сохранившегося значения. SQL `NULL` как значение отличают от отсутствующего ключа через `exist(attributes, 'key')` и `defined(attributes, 'key')`.

Для частого поиска по ключам и парам `hstore` поддерживает GIN и GiST с операторами `?`, `?|`, `?&`, `@>`. Индекс нужно создать отдельно; примерный фильтр по паре выше может использовать `CREATE INDEX idx_products_attributes ON products USING GIN (attributes)`. Индекс по `hstore` не делает значения числовыми и не добавляет вложенность. [hstore Indexes](https://www.postgresql.org/docs/18/hstore.html#HSTORE-INDEXES).

Источник: [PostgreSQL 18 — hstore](https://www.postgresql.org/docs/18/hstore.html).

## Q10. Как работают пользовательские типы (`enum`, `composite`, `domain`)?

PostgreSQL позволяет объявлять собственные типы. У трёх распространённых вариантов разные задачи: `enum` ограничивает набор меток, `composite` группирует поля, `domain` добавляет ограничения к базовому типу. Ограничения в самой базе выполняют `enum` и `domain`; `composite` сам по себе проверяет типы полей, но не переносит ограничения таблицы на значения вне неё.

**`ENUM`** — упорядоченный набор меток, заданный при создании. Значение занимает четыре байта; добавить или переименовать метку можно через `ALTER TYPE`, а удалить отдельную метку без пересоздания типа нельзя:

```sql
CREATE TYPE mood AS ENUM ('happy', 'sad', 'neutral');

CREATE TABLE persons (
    name TEXT,
    current_mood mood
);
```

Если `ALTER TYPE ... ADD VALUE` выполнен внутри транзакции, использовать новую метку можно только после `COMMIT`. Это важно для миграции, которая добавляет метку и сразу обновляет строки. [ALTER TYPE](https://www.postgresql.org/docs/18/sql-altertype.html).

**Composite type** — составной тип, объединяющий несколько полей в одно значение (аналог записи). В `CREATE TYPE ... AS` задают имена и типы полей, но не `NOT NULL` или `CHECK`. Даже если тип автоматически создан из таблицы, её ограничения не действуют на значения этого типа вне таблицы:

```sql
CREATE TYPE address AS (
    street TEXT,
    city TEXT,
    zip_code VARCHAR(10)
);

CREATE TABLE customers (
    id SERIAL PRIMARY KEY,
    addr address
);

SELECT (addr).city FROM customers;
```

Если ограничения нужны для составного значения вне исходной таблицы, можно создать `DOMAIN` поверх composite-типа с `CHECK`; сам composite их не наследует. [Composite Types](https://www.postgresql.org/docs/18/rowtypes.html).

**`DOMAIN`** — базовый тип с переиспользуемыми ограничениями, например `CHECK`. В примере `CHECK (VALUE > 0)` отсекает неположительные числа, но не запрещает `NULL`: результат проверки для `NULL` неизвестен, а не ложен. Если колонка обязательна, задайте ей `NOT NULL`:

```sql
CREATE DOMAIN positive_int AS INTEGER
    CHECK (VALUE > 0);

CREATE TABLE items (
    id SERIAL PRIMARY KEY,
    quantity positive_int NOT NULL
);
```

Источники: [PostgreSQL 18 — Enumerated Types](https://www.postgresql.org/docs/18/datatype-enum.html), [Composite Types](https://www.postgresql.org/docs/18/rowtypes.html), [CREATE DOMAIN](https://www.postgresql.org/docs/18/sql-createdomain.html).

## Q11. (!) Какие типы индексов существуют в PostgreSQL?

В PostgreSQL индекс — это не «один на всё», а семейство структур под разные задачи. Выбор типа определяется не столько колонкой, сколько **операторами в запросе**: равенство и диапазоны — это `B-tree`, поиск элемента внутри составного значения (`JSONB`, массив, текст) — `GIN`, геометрия и диапазоны — `GiST`, огромные упорядоченные таблицы — `BRIN`.

| Тип | Структура | Применение |
|-----|-----------|-----------|
| `B-tree` | Сбалансированное дерево | По умолчанию. Равенство, диапазон, `IS NULL`, сортировка |
| `Hash` | Хэш-таблица | Только проверка равенства (`=`) |
| `GIN` | Инвертированный индекс | Операторы поиска по элементам `jsonb`, массивов, `tsvector`, `hstore` при подходящем классе операторов |
| `GiST` | Обобщённое дерево поиска | Геометрические типы, `full-text`, диапазоны, `pg_trgm` |
| `SP-GiST` | Деревья с разбиением пространства | Точки и другие данные при подходящем классе операторов |
| `BRIN` | Сводки по диапазонам блоков | Большие таблицы с корреляцией значения и физического порядка строк |

`B-tree` создаётся по умолчанию и покрывает многие обычные сравнения. Но даже подходящий тип индекса не гарантирует индексный план: планировщик учитывает стоимость чтения и долю подходящих строк. Для `GiST` и `GIN` применимость конкретного оператора определяется классом операторов.

Встроенные методы в таблице не исчерпывают расширения: `bloom` поставляется отдельно и становится доступен после `CREATE EXTENSION bloom`. Его не следует считать обычным встроенным индексом наравне с B-tree или GIN. [Index Types](https://www.postgresql.org/docs/18/indexes-types.html).

Источник: [PostgreSQL 18 — Index Types](https://www.postgresql.org/docs/18/indexes-types.html).

## Q12. (!) Как работает `B-tree` индекс и когда он применяется?

**`B-tree`** — индекс по умолчанию. Хранит ключи в отсортированном дереве, что позволяет искать равенство и диапазоны и иногда получать нужный порядок строк без отдельной сортировки. Выбор индекса зависит от оценки стоимости: для большой доли таблицы последовательное чтение с сортировкой может быть дешевле.

Именно из-за упорядоченности `B-tree` так универсален: дерево умеет и точное равенство, и «больше/меньше», и `ORDER BY` без отдельной сортировки.

**Применяется при:**
- Операторах `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`
- `ORDER BY` (может устранить сортировку при совпадающем порядке, особенно с `LIMIT`)
- `IS NULL` / `IS NOT NULL`
- Операциях `LIKE 'prefix%'` с постоянным префиксом; вне локали `C` для текстовых колонок может понадобиться `text_pattern_ops` или аналогичный класс операторов

```sql
-- Обычный B-tree
CREATE INDEX idx_orders_created_at ON orders (created_at);

-- Составной B-tree
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- Descending
CREATE INDEX idx_orders_created_desc ON orders (created_at DESC);
```

**Составной B-tree** обычно наиболее эффективен, если запрос ограничивает ведущие столбцы: равенства по ним и неравенство по первому столбцу без равенства сокращают просматриваемый участок индекса. Условия на последующие столбцы проверяются в индексе, но сами по себе не обязательно сокращают его обход. Поэтому порядок столбцов выбирают по реальным фильтрам, сортировке и селективности.

В PostgreSQL 18 оптимизация **skip scan** иногда позволяет использовать `(a, b)` для `WHERE b = ...`: планировщик выполняет повторные поиски по разным значениям `a`, если их немного и это дешевле полного прохода. Это не гарантия и не замена отдельному индексу по `b` при частых запросах: при множестве значений `a` планировщик обычно выберет другой путь. Проверяйте конкретный запрос через `EXPLAIN`.

Для одного столбца обратный проход по B-tree меняет `ASC NULLS LAST` на `DESC NULLS FIRST`, поэтому отдельный индекс `DESC` обычно избыточен. Для составного `(a, b)` обратный проход меняет направление **обоих** ключей; запросу `ORDER BY a ASC, b DESC` нужен индекс с соответствующим смешанным порядком, если цель — избежать отдельной сортировки. [Indexes and ORDER BY](https://www.postgresql.org/docs/18/indexes-ordering.html).

Источники: [PostgreSQL 18 — Index Types](https://www.postgresql.org/docs/18/indexes-types.html), [Multicolumn Indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html), [Indexes and ORDER BY](https://www.postgresql.org/docs/18/indexes-ordering.html), [Operator Classes](https://www.postgresql.org/docs/18/indexes-opclass.html).

## Q13. Что такое `GIN` индекс и для каких данных он нужен?

**`GIN` (Generalized Inverted Index)** — инвертированный индекс, устроенный «наоборот» обычному: ключом выступает не строка таблицы, а отдельный элемент внутри значения (слово, элемент массива, ключ `JSONB`), а значением — список строк, где этот элемент встречается. Та же идея, что в поисковых системах: по слову сразу находим все документы.

Поэтому `GIN` полезен, когда значение содержит **много элементов**, а запрос ищет внутри него. Набор доступных операторов определяется классом операторов: индекс может дать кандидатов, которым потребуется перепроверка по строке.

**Применяется для:**
- `jsonb`: стандартный `jsonb_ops` поддерживает `@>`, `?`, `?|`, `?&`, `@?`, `@@`; `jsonb_path_ops` — только `@>`, `@?`, `@@`
- Массивов (`@>`, `<@`, `&&`)
- `full-text search` (`@@`)
- `hstore`
- `pg_trgm` (поиск по подстроке)

```sql
-- GIN для JSONB
CREATE INDEX idx_events_payload ON events USING GIN (payload);

-- GIN для full-text search
CREATE INDEX idx_articles_tsv ON articles USING GIN (to_tsvector('russian', body));

-- GIN для pg_trgm (поиск LIKE '%term%')
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING GIN (name gin_trgm_ops);
```

**Подводные камни:** вставка или обновление строки может добавить много ключей в индекс. При `fastupdate` новые записи сначала попадают в pending list. Поиск читает и этот список; его очистка при достижении лимита может резко замедлить отдельную запись. Размер списка и режим `fastupdate` выбирают по нагрузке, а не из предположения, что он всегда ускоряет работу.

`VACUUM`/autovacuum и `gin_clean_pending_list(index)` переносят записи из pending list в основную структуру. Для большого пакетного импорта иногда выгоднее построить GIN после загрузки, чем поддерживать его для каждой строки; это надо проверять на своей нагрузке. У составного GIN, в отличие от составного B-tree, эффективность поиска не зависит от того, какой индексируемый столбец указан в условии. [GIN Implementation](https://www.postgresql.org/docs/18/gin.html), [Multicolumn Indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html).

Источники: [PostgreSQL 18 — GIN Indexes](https://www.postgresql.org/docs/18/gin.html), [JSON Types](https://www.postgresql.org/docs/18/datatype-json.html).

## Q14. Что такое `GiST` индекс и чем он отличается от `GIN`?

**`GiST` (Generalized Search Tree)** — каркас для деревьев поиска. Какие операторы он поддерживает, задаёт класс операторов. Это позволяет индексировать, например, пересечение диапазонов и пространственные отношения; некоторые классы поддерживают поиск ближайших значений через `ORDER BY ... <-> ... LIMIT`.

**Чем отличается от `GIN`:** `GIN` хранит ключи элементов и списки строк, где они встречаются; `GiST` использует дерево и правила конкретного класса операторов. Оба могут ускорять полнотекстовый поиск, но с разными представлениями данных. Перепроверка кандидата возможна у обоих: у `GiST` это зависит от класса операторов и его флага `recheck`, у `GIN` — от класса и запроса. Например, полнотекстовый GIN не хранит весовые метки лексем, и запрос с весами требует перепроверки строки.

| Характеристика | `GIN` | `GiST` |
|---------------|-------|--------|
| Структура | Ключ элемента → список строк | Дерево с поведением класса операторов |
| Типичные задачи | Содержимое `jsonb`, массивов, полнотекстовый поиск | Диапазоны, геометрия, поиск ближайших значений при подходящем классе |
| Перепроверка строки | Возможна в зависимости от класса и запроса | Возможна в зависимости от класса и запроса |

**Сценарий применения:** геометрические данные (`PostGIS`), диапазоны (`tsrange`), `full-text search`, `pg_trgm`.

Для встроенного геометрического типа `point` GiST может обслужить поиск ближайших точек через `ORDER BY location <-> point '(101,456)' LIMIT 10`, если создан подходящий GiST-индекс по `location`. Само имя `GiST` не гарантирует поддержку `<->`: это свойство класса операторов. В полнотекстовом поиске GiST использует сигнатуру с возможными ложными совпадениями, поэтому PostgreSQL перепроверяет строки; GIN хранит лексемы, но при запросах с весами тоже требуется перепроверка. [Index Types](https://www.postgresql.org/docs/18/indexes-types.html), [Text Search Indexes](https://www.postgresql.org/docs/18/textsearch-indexes.html).

```sql
-- GiST для диапазонов дат
CREATE INDEX idx_reservations_period ON reservations USING GiST (period);

-- GiST для PostGIS
CREATE INDEX idx_locations_geom ON locations USING GiST (geom);
```

Источники: [PostgreSQL 18 — GiST Indexes](https://www.postgresql.org/docs/18/gist.html), [GIN Indexes](https://www.postgresql.org/docs/18/gin.html), [Index Types](https://www.postgresql.org/docs/18/indexes-types.html), [Text Search Indexes](https://www.postgresql.org/docs/18/textsearch-indexes.html).

## Q15. Что такое `BRIN` индекс и когда его выгодно использовать?

**`BRIN` (Block Range Index)** хранит сводку по группе соседних физических блоков, а не запись для каждой строки. Для упорядочиваемого типа стандартный класс может хранить минимум и максимум; другие классы используют другие сводки. Размер группы задаёт `pages_per_range` (по умолчанию 128). Индекс отсекает диапазоны, сводка которых несовместима с условием, а строки в оставшихся блоках перепроверяются: это индекс с потерями.

Отсюда два следствия: индекс обычно мал, но лучше всего работает, когда значения коррелируют с физическим порядком строк. Меньший `pages_per_range` делает сводки точнее ценой большего индекса. При слабой корреляции он может отсечь мало блоков, поэтому сравнивайте план и стоимость с `B-tree` и последовательным сканированием.

**Сценарий применения:**
- Данные физически упорядочены по индексируемому столбцу (монотонные `id`, временные метки вставки — записи ложатся в конец таблицы по возрастанию).
- Таблица очень большая, и полноценный `B-tree` занял бы неприемлемо много места.

```sql
CREATE INDEX idx_logs_created_brin ON logs USING BRIN (created_at);
```

**Подводные камни:** новые диапазоны блоков могут оставаться без сводки до `VACUUM`, autovacuum или явного summarization; `autosummarize` по умолчанию выключен. Наличие BRIN не гарантирует его выбор планировщиком.

После большой загрузки можно явно создать сводки для новых диапазонов: `SELECT brin_summarize_new_values('idx_logs_created_brin');`. Пока диапазон не сводён, индекс не может отбросить его по условию; даже после сводки BRIN остаётся индексом с потерями, так что сравнивайте `EXPLAIN (ANALYZE, BUFFERS)` до и после на реальной нагрузке. [BRIN Index Maintenance](https://www.postgresql.org/docs/18/brin.html).

Источник: [PostgreSQL 18 — BRIN Indexes](https://www.postgresql.org/docs/18/brin.html).

## Q16. Что такое частичный (`partial`) индекс?

**Частичный индекс** включает не все строки таблицы, а только те, что удовлетворяют условию `WHERE` в определении индекса. Идея: если запросы всегда фильтруют узкое подмножество (например, только активные заказы), нет смысла индексировать остальные миллионы строк.

Обычно это уменьшает индекс и затраты на его поддержку: строка вне предиката не получает записи в этом индексе. Изменение строки, которое переводит её через границу предиката, всё же требует обновления индекса.

```sql
-- Индексировать только незакрытые заказы
CREATE INDEX idx_orders_open ON orders (user_id)
WHERE status = 'open';

-- Индексировать только ненулевые значения
CREATE INDEX idx_users_email ON users (email)
WHERE email IS NOT NULL;
```

**Когда использовать:** когда запросы часто обращаются к определённому подмножеству или нужна уникальность только внутри него (`CREATE UNIQUE INDEX ... WHERE ...`). Для поиска планировщик должен при планировании доказать, что условие запроса подразумевает предикат индекса. Он распознаёт простые следствия вроде `x < 1` ⇒ `x < 2`, но не произвольные эквивалентные записи. Условие с параметром, например `x < $1`, не даёт универсального доказательства для предиката `x < 2`; применимость зависит от полученного плана, поэтому проверяйте `EXPLAIN` конкретного запроса.

Для soft delete можно обеспечить уникальность только активных записей: `CREATE UNIQUE INDEX users_active_email ON users (email) WHERE deleted_at IS NULL`. Предикат может использовать колонку, которой нет в ключе индекса; запросу для использования индекса при поиске всё равно нужно явно или доказуемо ограничить строки условием `deleted_at IS NULL`. Уникальность частичного индекса действует при записи независимо от того, какой план выберет запрос. Если `email` допускает `NULL`, обычный `UNIQUE` разрешит несколько активных строк с `NULL`; задайте `NOT NULL` либо используйте `NULLS NOT DISTINCT` в PostgreSQL 15+. [Partial Indexes](https://www.postgresql.org/docs/18/indexes-partial.html), [PostgreSQL 15 Release Notes](https://www.postgresql.org/docs/15/release-15.html).

Источник: [PostgreSQL 18 — Partial Indexes](https://www.postgresql.org/docs/18/indexes-partial.html).

## Q17. Что такое функциональный (`expression`) индекс?

**Функциональный индекс** строится не по самому столбцу, а по **результату выражения** над ним. Это решает частую проблему: если в запросе колонка обёрнута в функцию (`LOWER(email)`, `payload->>'type'`), обычный индекс по голой колонке не сработает — планировщик не знает, что `LOWER(email)` связан с индексом по `email`.

Решение — проиндексировать выражение, соответствующее условию запроса. Планировщик **может** выбрать этот индекс, если оператор подходит и оценка стоимости выгодна. Результат выражения вычисляется при создании индекса и изменении строки; все функции и операторы в определении индекса, в том числе в `WHERE` частичного индекса, должны быть `IMMUTABLE`.

```sql
-- Поиск без учёта регистра
CREATE INDEX idx_users_lower_email ON users (LOWER(email));

-- Запрос, использующий этот индекс
SELECT * FROM users WHERE LOWER(email) = 'user@example.com';

-- Индекс по extracted части JSONB
CREATE INDEX idx_events_type ON events ((payload->>'event_type'));

```

Например, извлечение года из `timestamptz` зависит от часового пояса сеанса, поэтому такое выражение нельзя без проверки объявлять индексируемым как `IMMUTABLE`. Для часто используемого поиска по дате сначала определите тип столбца и конкретный предикат. Индекс по выражению можно сделать `UNIQUE`, например для запрета одинаковых email без учёта регистра.

Нельзя объявлять функцию `IMMUTABLE` только ради создания индекса, если она зависит от времени, настроек сеанса или внешних данных: сохранённое в индексе значение перестанет соответствовать новому результату функции. Уникальный индекс по `lower(email)` проверяет равенство результатов выражения при записи, но поиск всё равно зависит от совпадения выражения и подходящего плана. [CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html).

Источники: [PostgreSQL 18 — Indexes on Expressions](https://www.postgresql.org/docs/18/indexes-expressional.html), [CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html).

## Q18. (!) Что такое покрывающий (`covering`) индекс и как его создать в PostgreSQL?

**Покрывающий индекс** содержит все столбцы, нужные запросу, и позволяет рассмотреть `Index Only Scan`. Но PostgreSQL всё равно должен проверить видимость версии строки: если для страницы таблицы не установлен бит `all-visible` в visibility map, потребуется чтение heap. На часто изменяемой таблице покрытие само по себе не даёт выигрыша.

В PostgreSQL (с версии 11) для этого есть `INCLUDE`: ключевые столбцы участвуют в поиске и сортировке, а перечисленные в `INCLUDE` просто «довешиваются» в листья индекса как полезная нагрузка:

```sql
-- Основной индекс по user_id, дополнительно хранит status и total
CREATE INDEX idx_orders_covering ON orders (user_id) INCLUDE (status, total);

-- Запрос может получить Index Only Scan, если план и visibility map это позволяют
SELECT status, total FROM orders WHERE user_id = 42;
```

До появления `INCLUDE` в PostgreSQL 11 дополнительные столбцы иногда ставили в конец ключа составного индекса. `INCLUDE`-столбцы не участвуют в поиске, сортировке и проверке уникальности; их хранят как данные для чтения. Это может уменьшить верхние уровни B-tree по сравнению с дополнительными ключами, но не гарантирует меньший индекс целиком.

**Компромисс:** меньше обращений к heap на страницах `all-visible` — ценой дополнительного места и поддержки индекса при записи. Слишком широкое включённое значение может превысить лимит индексного кортежа. `INCLUDE` поддерживают B-tree, GiST и SP-GiST, но не GIN; включаемый столбец не может быть выражением.

Поддержка `INCLUDE` не означает, что любой GiST/SP-GiST-класс умеет `Index Only Scan`: он должен хранить или восстанавливать исходное значение. B-tree поддерживает такой скан всегда. Проверяйте `EXPLAIN (ANALYZE, BUFFERS)`: даже узел `Index Only Scan` может показывать ненулевые `Heap Fetches`, если нужные страницы не отмечены `all-visible`. [Index-Only Scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html), [EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html).

Источник: [PostgreSQL 18 — Index-Only Scans and Covering Indexes](https://www.postgresql.org/docs/18/indexes-index-only-scans.html).

## Q19. Что такое `CONCURRENTLY` при создании индекса?

Обычный `CREATE INDEX` блокирует запись в таблицу на время построения, хотя чтение продолжается. `CONCURRENTLY` позволяет параллельные `INSERT`/`UPDATE`/`DELETE`, но сам процесс всё же ждёт некоторые активные транзакции и создаёт дополнительную нагрузку CPU/I/O. Это способ сохранить доступность записи, а не гарантия отсутствия любых ожиданий или замедлений.

```sql
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id);
```

Цена за отсутствие блокировки — индекс строится в несколько проходов и медленнее.

**Подводные камни:**
- Дольше обычного построения (минимум два прохода по таблице).
- Нельзя выполнять внутри транзакционного блока (`BEGIN ... COMMIT`).
- При ошибке построения может остаться `INVALID` индекс: планировщик игнорирует его для запросов, но индекс занимает место и может замедлять обновления. Обычный путь восстановления — удалить его и повторить построение; возможен `REINDEX INDEX CONCURRENTLY`.
- Для `UNIQUE` ограничения могут начать проверяться до того, как индекс станет пригоден для чтения. После неудачи такой `INVALID` индекс может продолжить проверять уникальность.
- На таблице допускается лишь одно одновременное concurrent-построение; прямое `CREATE INDEX CONCURRENTLY` на партиционированной таблице не поддерживается.

Для долгого построения смотрят `pg_stat_progress_create_index`: `phase` различает сканирование и ожидание старых транзакций, а `current_locker_pid` помогает найти блокирующую сессию в фазах ожидания. Это полезнее предположения, что команда «зависла». После сбоя проверьте оставшийся индекс, прежде чем повторять миграцию. [Progress Reporting](https://www.postgresql.org/docs/18/progress-reporting.html).

`DROP INDEX CONCURRENTLY` тоже не блокирует обычную работу таблицы, но его нельзя запускать в транзакционном блоке, с `CASCADE`, для индекса ограничения `UNIQUE`/`PRIMARY KEY` или для индекса партиционированной таблицы. За один вызов указывают только один индекс. [DROP INDEX](https://www.postgresql.org/docs/18/sql-dropindex.html).

Источник: [PostgreSQL 18 — CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html).

## Q20. (!) Как читать вывод `EXPLAIN`?

`EXPLAIN` показывает выбранный план запроса: способы чтения таблиц, соединения, сортировки и другие операции. План — дерево узлов. Начните с листьев и проследите, как строки поступают в родительские узлы; затем проверьте дорогие узлы и оценки. Это порядок разбора дерева, а не обещание, что каждый дочерний узел целиком завершится до запуска родителя: например, `Nested Loop` может запускать внутренний узел много раз.

Для диагностики сопоставьте оценочное `rows` с фактическим числом строк из `EXPLAIN (ANALYZE)`, а затем изучите фильтры, условия индекса, число запусков, время и буферы. Сам по себе `Seq Scan` на большой таблице не ошибка: он может быть дешевле индексного доступа при широкой выборке.

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```

```
Index Scan using idx_orders_user_id on orders  (cost=0.43..8.45 rows=5 width=128)
  Index Cond: (user_id = 42)
```

**Основные поля:**
- `cost=X..Y` — оценочная стоимость в условных единицах: `X` — до выдачи первой строки (startup), `Y` — до выдачи последней (total). Это **оценка планировщика**, а не время.
- `rows=N` — **оценочное** число строк на один запуск узла; это число выданных строк, а не обязательно просмотренных.
- `width=N` — средний размер строки в байтах.
- `actual time=X..Y` (только `EXPLAIN ANALYZE`) — реальное время в миллисекундах.
- `actual rows=N loops=N` — среднее число выданных строк за запуск и число запусков. Для общего числа выданных строк умножьте их, учитывая округление вывода. С `rows` сравнивайте именно значение **за запуск**. Расхождение требует проверки оценок и статистики, но само по себе не доказывает, что статистика устарела.

Например, `rows=10` и `actual rows=8 loops=100` означают оценку 10 и факт около 8 строк **за запуск**, а не оценку 10 против 800 за всё время. `actual time` повторно запускаемого узла тоже усредняется за запуск. `Rows Removed by Filter` показывает отсеянные строки; `Buffers: shared hit/read` помогает отличить обращения к буферам от чтения страниц, но счётчики родителя уже включают обращения его дочерних узлов. Не складывайте их повторно. [Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html), [EXPLAIN](https://www.postgresql.org/docs/18/sql-explain.html).

Строки `Index Cond` и `Filter` — свойства узла, а не отдельные операции: первое ограничивает индексный поиск, второе проверяет оставшиеся строки. Стоимость родителя включает стоимость дочерних узлов, поэтому их нельзя просто складывать. [Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html).

**Типичные узлы:**
| Узел | Описание |
|------|---------|
| `Seq Scan` | Последовательное чтение страниц таблицы; `LIMIT` может остановить его до полного обхода |
| `Index Scan` | Сканирование по индексу с возвратом в таблицу |
| `Index Only Scan` | Чтение значений из индекса; возможны обращения к таблице для проверки видимости |
| `Bitmap Index Scan` | Построение битовой карты по индексу |
| `Bitmap Heap Scan` | Чтение строк по битовой карте |
| `Hash Join` | Соединение хэш-таблицей |
| `Nested Loop` | Вложенные циклы |
| `Merge Join` | Соединение слиянием |
| `Sort` | Сортировка |
| `Aggregate` | Агрегация |

## Q21. (!) В чём разница между `EXPLAIN` и `EXPLAIN ANALYZE`?

Обычный `EXPLAIN` строит план, но не выполняет сам запрос. `EXPLAIN (ANALYZE)` выполняет его и добавляет фактические строки и время к оценкам. Здесь `ANALYZE` — опция `EXPLAIN`, а не отдельная команда `ANALYZE`, которая обновляет статистику планировщика (Q25). Сильное расхождение — повод проверить статистику, условия и оценки планировщика; оно не доказывает единственную причину или плохой план само по себе.

| Команда | Описание |
|---------|---------|
| `EXPLAIN` | Показывает **оценочный** план без выполнения запроса |
| `EXPLAIN ANALYZE` | **Выполняет** запрос и показывает реальное время и число строк |
| `EXPLAIN (ANALYZE, BUFFERS)` | Явно запрашивает счётчики буферов (`shared hit`, `read` и другие); в PostgreSQL 18 при `ANALYZE` они уже включены по умолчанию |
| `EXPLAIN (ANALYZE, FORMAT JSON)` | Вывод в формате `JSON` |

```sql
-- Полный анализ с информацией о буферах
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 'open';
```

**Диагностика чтения в PostgreSQL 19.** Если план показывает медленное сканирование, к счётчикам буферов можно добавить данные об асинхронном вводе-выводе:

```sql
EXPLAIN (ANALYZE, BUFFERS, IO, TIMING OFF)
SELECT count(*) FROM orders WHERE status = 'open';
```

На узлах сканирования, которые собирают эти данные, `IO` показывает размер запросов в блоках, число ожиданий и среднее число запросов в работе. По этим полям можно проверить, совмещает ли сканирование несколько запросов чтения и как часто ждёт их завершения. Нулевые значения в текстовом выводе опускаются. `IO` требует `ANALYZE`, а в PostgreSQL 18 этой опции ещё нет. [EXPLAIN в PostgreSQL 19](https://www.postgresql.org/docs/19/sql-explain.html).

**Подводный камень:** `ANALYZE` действительно выполняет `INSERT`/`UPDATE`/`DELETE` и другие изменяющие команды. Для диагностики без сохранения изменений в БД используйте `BEGIN` ... `ROLLBACK`; это не исключает затрат на выполнение и побочных эффектов вне откатываемых данных. [EXPLAIN](https://www.postgresql.org/docs/18/sql-explain.html).

Измеренное `Execution Time` не равно времени ответа клиенту: обычный `EXPLAIN (ANALYZE)` не отправляет строки результата и по умолчанию не измеряет их преобразование для передачи. Сбор времени по узлам тоже добавляет накладные расходы; если нужны фактические строки без времени каждого узла, используйте `TIMING OFF`. В PostgreSQL 18 `SERIALIZE TEXT`/`BINARY` позволяет отдельно измерить преобразование результата, но сетевую передачу `EXPLAIN` всё равно не измеряет. [EXPLAIN](https://www.postgresql.org/docs/18/sql-explain.html).

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM old_logs WHERE created_at < NOW() - INTERVAL '1 year';
ROLLBACK;
```

## Q22. (!) Что такое `Seq Scan` и `Index Scan` и когда планировщик выбирает каждый?

Это два способа читать строки. Планировщик оценивает их стоимость с учётом числа подходящих строк, расположения данных, размера таблицы, кэша и настроек стоимости. При широкой выборке чтение таблицы подряд часто выгоднее множества обращений через индекс, но универсального порога селективности нет.

**`Seq Scan` (Sequential Scan)** — читает таблицу подряд, страница за страницей:
- Выгоден, когда нужно вернуть **большую долю строк**: проще прочитать всё последовательно, чем тысячи раз прыгать по индексу к разбросанным строкам.
- Возможен и без подходящего индекса; у запроса могут быть и другие способы доступа, например сканирование другого индекса для порядка строк.
- На маленьких таблицах часто дешевле индекса — накладные расходы на обход индекса не окупаются.

**`Index Scan`** — находит подходящие записи в индексе и обращается к таблице за строками и проверкой их видимости:
- Выгоден при **высокой селективности** — когда условие отсекает почти всё и остаётся мало строк.
- Множество обращений к разбросанным страницам таблицы может сделать его дороже `Seq Scan`; `Bitmap Heap Scan` — ещё одна возможная альтернатива.

**`Index Only Scan`** возможен, когда индекс поддерживает такой режим и содержит нужные значения. Если страница таблицы не помечена all-visible в visibility map, PostgreSQL всё равно обращается к таблице за проверкой видимости. Нельзя считать этот режим всегда самым быстрым. См. Q18 и Q23.

**Когда планировщик предпочитает `Seq Scan`:**
- Условие возвращает много строк или таблица мала: оценочная цена обхода индекса выше.
- Оценка числа строк ошибочна: проверьте статистику и сравните план с фактом через `EXPLAIN (ANALYZE)`; `ANALYZE` может обновить статистику, но не гарантирует нужный план.

`SET enable_indexscan = off` отключает рассмотрение `Index Scan` и `Index Only Scan`, но не `Bitmap Index Scan`: это не запрет всех видов индексного доступа. Используйте такую настройку только для диагностики и верните прежнее значение. [Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html), [Planner Method Configuration](https://www.postgresql.org/docs/18/runtime-config-query.html).

## Q23. Что такое `Bitmap Index Scan` и `Index Only Scan`?

**`Bitmap Index Scan`** строит карту расположения подходящих строк по индексу, но сам не читает строки таблицы; обычно над ним стоит `Bitmap Heap Scan`, который читает соответствующие страницы. Планировщик сравнивает цену этой пары с другими способами доступа:

1. Индексный узел формирует карту расположения кандидатов в таблице. Несколько карт можно объединить через `BitmapAnd` или `BitmapOr`.
2. `Bitmap Heap Scan` посещает страницы таблицы в физическом порядке, что уменьшает разброс обращений. Это не означает, что чтение стало полностью последовательным; порядок исходного индекса теряется, и для `ORDER BY` может понадобиться отдельная сортировка.

Такой план часто выгоден при промежуточном числе совпадений, но выбор зависит от оценок и расположения строк. При lossy bitmap `Bitmap Heap Scan` повторно проверяет условие на кандидатах; строка `Recheck Cond` в плане сама по себе не доказывает, что для каждого кандидата была повторная проверка.

В `EXPLAIN (ANALYZE)` проверяйте `Heap Blocks: exact/lossy` и `Rows Removed by Index Recheck`: первый показатель показывает точность bitmap по страницам, второй — сколько кандидатов было отсеяно повторной проверкой. `Recheck Cond` может присутствовать и при `Heap Blocks: exact`, когда повторной проверки по причине lossy-страниц не было. [Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html).

```
Bitmap Heap Scan on orders
  Recheck Cond: (status = 'open')
  ->  Bitmap Index Scan on idx_orders_status
        Index Cond: (status = 'open')
```

**`Index Only Scan`** возможен, если метод индекса поддерживает его и индекс содержит все нужные запросу значения. Для проверки MVCC-видимости PostgreSQL смотрит бит all-visible в **visibility map** соответствующей страницы таблицы. Если бит не установлен, происходит обращение к heap; число таких обращений видно как `Heap Fetches` в `EXPLAIN (ANALYZE)`. `VACUUM` помогает отмечать подходящие страницы, но частые изменения снова сбрасывают этот признак. Ненулевой `Heap Fetches` совместим с планом `Index Only Scan`: это обращения к таблице за проверкой видимости. Несколько обращений могут приходиться на одну страницу, а сама страница может быть в кеше. Физический I/O оценивайте отдельно (Q54). См. также Q18. [Combining Multiple Indexes](https://www.postgresql.org/docs/18/indexes-bitmap-scans.html), [Index-Only Scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html).
**Что изменилось в PostgreSQL 19.** Сканирование heap запросом, который не меняет эту таблицу, при очистке страницы может само выставить бит `all-visible`, если подтвердит видимость всех оставшихся версий строк для всех транзакций. Например, обычный `Seq Scan` может подготовить часть страниц для последующего `Index Only Scan`. Если следующий план действительно выберет такой узел и страницы сохранят этот признак, обращений к heap может стать меньше. Один проход не гарантирует, что все страницы получат отметку. `VACUUM` по-прежнему нужен для обслуживания таблицы и заморозки версий строк (Q31). [Заметки к PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html), [изменение в исходниках](https://github.com/postgres/postgres/commit/b46e1e54d).

## Q24. Что такое `cost` в плане запроса?

**`cost`** — оценка работы плана в условных единицах, а не время в миллисекундах или размер данных в байтах. `EXPLAIN` показывает две оценки: `startup cost` до первой строки и `total cost` при полном выполнении узла. Стоимость родительского узла включает дочерние узлы; при `LIMIT`/`EXISTS` важна стоимость получения нужных строк, а не обязательно полного выполнения. Базовая единица по умолчанию — последовательное чтение страницы (`seq_page_cost = 1.0`). [Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html), [EXPLAIN](https://www.postgresql.org/docs/18/sql-explain.html).

Сравнивайте оценки альтернативных планов **для одного запроса в сопоставимых настройках**. Большой `cost` сам по себе не доказывает медленную работу. Для диагностики сопоставьте estimated rows с actual rows и время/буферы через `EXPLAIN (ANALYZE, BUFFERS)`: `ANALYZE` действительно выполняет запрос, включая запись данных для DML.

**Параметры, влияющие на стоимость:**
| Параметр | По умолчанию | Описание |
|---------|------------|---------|
| `seq_page_cost` | `1.0` | Стоимость последовательного чтения страницы |
| `random_page_cost` | `4.0` | Стоимость случайного чтения страницы |
| `cpu_tuple_cost` | `0.01` | Стоимость обработки одной строки |
| `cpu_index_tuple_cost` | `0.005` | Стоимость обработки записи индекса |
| `cpu_operator_cost` | `0.0025` | Стоимость вычисления оператора |

`random_page_cost = 4.0` **не** означает, что диск всегда вчетверо медленнее: значение уже учитывает ожидание, что часть случайных чтений попадёт в кэш. На SSD или при другом профиле кэша снижение может быть полезно, но универсального числа нет. Сначала проверяют статистику (Q25), `effective_cache_size`, реальные `EXPLAIN (ANALYZE, BUFFERS)` и нагрузку; затем меняют параметры для нужного окружения и сравнивают планы. [Planner cost constants](https://www.postgresql.org/docs/18/runtime-config-query.html).

```sql
BEGIN;
SET LOCAL random_page_cost = 1.5; -- только для диагностики внутри транзакции
EXPLAIN SELECT * FROM orders WHERE status = 'open';
ROLLBACK;
```

## Q25. Как работает статистика в PostgreSQL (`pg_statistic` и `pg_stats`)?

Планировщик оценивает число строк и стоимость возможных планов по статистике, а не предварительно выполняет каждый запрос. Оценки приблизительны даже сразу после обновления статистики: `ANALYZE` обычно берёт выборку строк. Ошибка оценки может привести к неудачному плану, но один `Seq Scan` сам по себе её не доказывает.

`ANALYZE` собирает статистику распределения в каталоге `pg_statistic`; `pg_stats` — удобное представление, показывающее только таблицы, доступные пользователю на чтение. Оценки числа строк и страниц таблиц и индексов хранятся также в `pg_class.reltuples` и `relpages`. Автоматический `ANALYZE` запускается по отдельному порогу изменений таблицы (Q33).

```sql
-- Ручной запуск анализа
ANALYZE orders;

-- Посмотреть статистику столбца
SELECT * FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';
```

**Ключевые поля `pg_stats`:**
- `n_distinct` — оценка числа различных значений: положительное значение означает примерное число, отрицательное — отрицательную долю от числа строк (`-1` соответствует примерно одному уникальному значению на строку).
- `most_common_vals` — самые частые значения, и `most_common_freqs` — их доли. Нужны для перекошенных распределений: оценка строк для частого значения и для редкого будет разной.
- `histogram_bounds` — границы групп примерно равной численности для значений вне списка самых частых; помогают оценивать диапазонные условия (`>`, `BETWEEN`).

`default_statistics_target` (по умолчанию `100` в PostgreSQL 18) ограничивает детализацию статистики. Для конкретного столбца её можно повысить после проверки оценок и цены `ANALYZE`, но это не гарантирует нужный план:

```sql
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;
```

Если условия по нескольким столбцам связаны, обычная статистика по каждому столбцу может ошибаться даже после свежего `ANALYZE`. Для такого случая проверьте расширенную статистику через `CREATE STATISTICS` и повторный `ANALYZE`; создание объекта само по себе данных не собирает. Выбирайте тип по ошибке оценки: `dependencies` для связанных условий равенства, `mcv` для частых сочетаний значений, `ndistinct` для числа групп при `GROUP BY`.

```sql
-- Пример для двух связанных фильтров по равенству
CREATE STATISTICS orders_user_status (mcv) ON user_id, status FROM orders;
ANALYZE orders;
```

Проверьте оценку на одном и том же запросе до и после сбора статистики. Например, если у конкретного пользователя доля заказов со статусом `pending` заметно выше средней, оценка для фильтра `user_id = 42 AND status = 'pending'` может быть занижена. Список `mcv` помогает, если это сочетание достаточно часто встречается в выборке. В PostgreSQL 18 и 19 расширенная статистика может уточнить число строк после фильтра одной таблицы, но планировщик не использует её напрямую для оценки селективности условия `JOIN` между таблицами. [CREATE STATISTICS в PostgreSQL 18](https://www.postgresql.org/docs/18/sql-createstatistics.html), [CREATE STATISTICS в PostgreSQL 19](https://www.postgresql.org/docs/19/sql-createstatistics.html).

Такие объекты не создаются автоматически для всех сочетаний столбцов. `dependencies` не исправляет оценки диапазонных условий или `LIKE`; повышение `STATISTICS` увеличивает объём выборки и стоимость анализа, но не гарантирует точный план. [Statistics Used by the Planner](https://www.postgresql.org/docs/18/planner-stats.html), [pg_statistic](https://www.postgresql.org/docs/18/catalog-pg-statistic.html), [pg_stats](https://www.postgresql.org/docs/18/view-pg-stats.html).

## Q26. (!) Какие уровни изоляции транзакций поддерживает PostgreSQL?

PostgreSQL принимает названия всех четырёх стандартных уровней изоляции, но реализует три разных режима: `READ UNCOMMITTED` ведёт себя как `READ COMMITTED`. По умолчанию действует `READ COMMITTED`. Различие уровней — в допустимых аномалиях параллельных транзакций:

| Уровень | Dirty read | Non-repeatable read | Phantom read | Serialization anomaly |
|---------|------------|---------------------|--------------|-----------------------|
| `READ UNCOMMITTED` | Невозможен | Возможен | Возможен | Возможна |
| `READ COMMITTED` | Невозможен | Возможен | Возможен | Возможна |
| `REPEATABLE READ` | Невозможен | Невозможен | Невозможен | Возможна |
| `SERIALIZABLE` | Невозможен | Невозможен | Невозможен | Невозможна |

`READ COMMITTED` берёт новый снимок для каждой команды; два `SELECT` в одной транзакции могут увидеть разные зафиксированные данные. В `REPEATABLE READ` снимок устанавливается при первой содержательной команде и сохраняется до конца транзакции: фантомов нет, но возможна аномалия сериализации, например write skew. Поэтому отсутствие фантомов ещё не равно `SERIALIZABLE`.

При конкурирующем `UPDATE` поведение тоже различается: в `READ COMMITTED` после ожидания чужого `COMMIT` PostgreSQL может повторно проверить `WHERE` на обновлённой версии строки и продолжить; в `REPEATABLE READ` попытка изменить строку, которую другая транзакция обновила после начала снимка, приводит к ошибке сериализации. Повторять нужно всю транзакцию. [Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html).

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- ... операции ...
COMMIT;

-- Или через SET до первого запроса внутри другой транзакции
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- ... операции ...
COMMIT;
```

Вне `BEGIN` команда `SET TRANSACTION` выдаёт предупреждение и не меняет изоляцию следующей транзакции. После первой команды чтения или изменения данных уровень этой транзакции уже нельзя сменить. [SET TRANSACTION](https://www.postgresql.org/docs/18/sql-set-transaction.html).

**`SERIALIZABLE`** гарантирует результат, эквивалентный некоторому последовательному выполнению успешно завершившихся транзакций. PostgreSQL применяет `SSI` (Serializable Snapshot Isolation): отслеживает опасные зависимости чтения и записи, в том числе неблокирующими предикатными блокировками `SIReadLock`. При риске аномалии транзакция может получить `SQLSTATE 40001` не только на `COMMIT`. Приложение должно повторять **всю** транзакцию, включая чтения и решения на их основе. Обычные конфликты записи и явные блокировки при этом по-прежнему могут приводить к ожиданию.

Источник: [PostgreSQL 18 — Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html).

## Q27. (!) Как работает `MVCC` в PostgreSQL?

**`MVCC` (Multi-Version Concurrency Control)** решает классическую проблему: как дать читателям и писателям работать одновременно, не мешая друг другу. Ответ PostgreSQL — **не перезаписывать строку на месте, а хранить её версии**. Пока один пишет новую версию, остальные спокойно читают старую.

**Принцип:**
- `UPDATE` создаёт новую версию строки с новым `xmin`; прежняя версия сохраняется, а в её `xmax` указывается транзакция, которая её заменила. `DELETE` тоже не стирает версию немедленно. Видимость зависит от снимка и состояния транзакций, а не от одного наличия `xmax`.
- Каждый SQL-запрос читает согласованный **снимок** (snapshot). В `READ COMMITTED` последующие команды получают новые снимки; в `REPEATABLE READ` и `SERIALIZABLE` снимок фиксируется при первой содержательной команде транзакции.

**Плюсы:**
- Обычный `SELECT` не блокирует запись строки, а запись не блокирует такое чтение. `SELECT FOR UPDATE`/`FOR SHARE` и другие явные блокировки могут ждать конкурирующие операции.
- Снимок даёт согласованное чтение без блокировки читаемых строк.

**Минусы (обратная сторона версионности):**
- Версии, которые больше не нужны снимкам, могут занимать место как **мёртвые кортежи** (`dead tuples`). Их удаляет `VACUUM`; для некоторых промежуточных `HOT`-версий возможна очистка и при обычном доступе к странице.
- Обычный `UPDATE` может создать новые индексные записи и увеличить их объём. При `HOT`-обновлении, когда индексируемые значения не затронуты и на странице хватает места, новые записи в обычных индексах не нужны; промежуточные версии могут удаляться без ожидания `VACUUM`. [Heap-Only Tuples](https://www.postgresql.org/docs/18/storage-hot.html).

**Важная граница снимка:** в `READ COMMITTED` конкурирующий `UPDATE` после ожидания может примениться к новой версии строки и повторно проверить условие. Это не означает, что обычный `SELECT` увидит незавершённые чужие изменения. В `REPEATABLE READ` изменение строки, обновлённой после снимка, заканчивается ошибкой и требует повтора транзакции (Q26). [Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html).

```sql
-- Посмотреть xmin/xmax
SELECT xmin, xmax, * FROM orders WHERE id = 1;
```

Источники: [PostgreSQL 18 — MVCC](https://www.postgresql.org/docs/18/mvcc-intro.html), [Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html).

## Q28. Что такое `xmin` и `xmax` в кортежах PostgreSQL?

Это служебные поля каждой версии строки, а не время создания и удаления. `xmin` содержит идентификатор создавшей транзакции (`XID`). `xmax` участвует в отметке удаления, замены или блокировки строки; его видимое число нельзя толковать без служебных флагов кортежа и состояния транзакций.

| Поле | Описание |
|------|---------|
| `xmin` | `XID` транзакции, создавшей кортеж (`INSERT` или `UPDATE`) |
| `xmax` | Обычно `XID` транзакции, удалившей или заменившей версию; при блокировках может содержать `XID` блокирующей транзакции или идентификатор `MultiXact` нескольких участников |
| `ctid` | Физический адрес версии (`блок`, `смещение`); меняется после `UPDATE` или перемещения строки при `VACUUM FULL` |

**Упрощённая проверка видимости:** версия должна быть создана транзакцией, видимой данному снимку, и не должна быть удалена видимой ему завершённой транзакцией. Ненулевой `xmax` сам по себе не доказывает удаление: он может относиться к незавершённой или откатившейся операции либо к блокировке строки. При нескольких блокирующих транзакциях в заголовке хранится `MultiXact ID`, а не простой `XID` одной транзакции. `ctid` не подходит для постоянного идентификатора строки; для этого нужен первичный ключ. `XID` также не следует считать долговечным уникальным идентификатором: счётчик циклически переполняется. [Routine Vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html), [System Columns](https://www.postgresql.org/docs/18/ddl-system-columns.html).

```sql
SELECT xmin, xmax, ctid, id, status FROM orders WHERE id = 1;
```

Источник: [PostgreSQL 18 — System Columns](https://www.postgresql.org/docs/18/ddl-system-columns.html).

## Q29. Что такое `phantom read`, `non-repeatable read` и `dirty read`?

Это явления, которыми стандарт SQL описывает уровни изоляции. `Dirty read` касается **одного** чтения незафиксированных чужих данных; две другие аномалии обнаруживаются при повторном чтении в одной транзакции:

| Аномалия | Описание |
|----------|---------|
| **Dirty read** | Транзакция читает данные, записанные другой, ещё не зафиксированной транзакцией; та может откатиться |
| **Non-repeatable read** | Повторное чтение ранее прочитанных данных обнаруживает их изменение после фиксации другой транзакции |
| **Phantom read** | Повторный запрос с тем же условием обнаруживает иной **набор подходящих строк** после фиксации другой транзакции; набор может измениться из-за `INSERT`, `DELETE` или `UPDATE` |
| **Serialization anomaly** | Итог параллельных транзакций таков, что его нельзя получить ни при каком их последовательном порядке |

Практическое различие: при non-repeatable read смотрят на **ранее прочитанные данные**, при phantom read — на **набор строк, удовлетворяющих условию**. Изменение или удаление строки может затронуть обе формулировки, поэтому не стоит сводить фантомы только к `INSERT`. Аномалия сериализации шире: итог успешных транзакций не соответствует ни одному последовательному порядку их выполнения.

В PostgreSQL `READ UNCOMMITTED` работает как `READ COMMITTED`, поэтому dirty read здесь не возникает. При `READ COMMITTED` два запроса могут увидеть разные зафиксированные данные; `REPEATABLE READ` исключает и non-repeatable, и phantom read, но допускает аномалию сериализации. `SERIALIZABLE` исключает её для успешно завершившихся транзакций; приложение должно быть готово повторить транзакцию при ошибке сериализации. См. Q26. [Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html).

## Q30. Что происходит при `ROLLBACK TO SAVEPOINT`?

`SAVEPOINT` создаёт точку внутри **текущей транзакции**. `ROLLBACK TO SAVEPOINT` отменяет действия после неё и позволяет продолжить транзакцию; действия до точки остаются частью ещё не зафиксированной транзакции. Это полезно, когда ошибку отдельного шага можно обработать локально, не отменяя все предыдущие шаги.

```sql
BEGIN;

INSERT INTO orders (user_id, total) VALUES (1, 100);

SAVEPOINT before_discount;

UPDATE orders SET total = total * 0.9 WHERE user_id = 1;

-- Отменить только операцию после SAVEPOINT
ROLLBACK TO SAVEPOINT before_discount;

-- Первый INSERT остаётся в транзакции, UPDATE отменён
COMMIT;
```

После `ROLLBACK TO` сама точка остаётся доступной для повторного отката. Следующие за ней точки удаляются. `RELEASE SAVEPOINT` удаляет указанную точку вместе с более поздними активными точками и сохраняет выполненные после неё действия **внутри текущей транзакции**, но не делает `COMMIT`; полный `ROLLBACK` всё ещё отменит их. Если команда уже перевела транзакцию в состояние ошибки, сначала выполните `ROLLBACK TO`, а не `RELEASE`. [SAVEPOINT](https://www.postgresql.org/docs/18/sql-savepoint.html), [ROLLBACK TO SAVEPOINT](https://www.postgresql.org/docs/18/sql-rollback-to.html), [RELEASE SAVEPOINT](https://www.postgresql.org/docs/18/sql-release-savepoint.html).

Блокировки таблиц и строк, полученные **после** точки, при откате к ней освобождаются; более ранние остаются до завершения транзакции. У курсоров есть исключение: перемещение ранее открытого курсора через `FETCH` не откатывает его позицию, а курсор, открытый после точки, закрывается. [Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html), [ROLLBACK TO SAVEPOINT](https://www.postgresql.org/docs/18/sql-rollback-to.html).

## Q31. (!) Зачем нужен `VACUUM` и что такое `dead tuples`?

`VACUUM` нужен как прямое следствие `MVCC`. Поскольку `UPDATE`/`DELETE` оставляют старые версии, со временем таблица может заполняться **мёртвыми кортежами** (`dead tuples`) — версиями, которые больше не нужны ни одному снимку. `VACUUM` освобождает занятое ими место для повторного использования. Часть промежуточных `HOT`-версий может удаляться и при обычном доступе к странице (Q27), поэтому не каждую старую версию ждёт отдельный `VACUUM`.

**Чем плохо накопление `dead tuples`:**
- Таблица и индексы пухнут (`table bloat`) — занимают больше диска.
- Замедляется `Seq Scan`: чтобы прочитать живые строки, движок вынужден перелопачивать ещё и мёртвые.
- Замедляется `Index Scan`: часть индексных записей может ссылаться на устаревшие версии; при `HOT`-обновлении новые записи в обычных индексах не создаются (Q27).

Обычно `VACUUM` освобождает место мёртвых версий **для повторного использования внутри таблицы**, не уменьшая файл. Исключение: если в конце таблицы целые страницы стали свободными, `VACUUM` может обрезать хвост и вернуть место ОС; для этой короткой операции требуется `ACCESS EXCLUSIVE`. Подробнее о выборе между обычным и полным вариантом — в Q32. [Routine Vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html).

Долгая транзакция, старый snapshot или оставленный replication slot могут удерживать горизонт видимости и мешать удалению версий; повторный `VACUUM` без поиска причины не исправит это. `n_dead_tup` в `pg_stat_user_tables` — **оценка**, а не точное число. Смотрите также время последней очистки и прогресс текущей операции. [Routine Vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html), [Monitoring Statistics](https://www.postgresql.org/docs/18/monitoring-stats.html).

Если `n_dead_tup` остаётся высоким после очистки, сначала ищите **кто удерживает горизонт**, а не запускайте `VACUUM FULL`. В PostgreSQL 18 проверьте `backend_xid`/`backend_xmin` и `xact_start` в `pg_stat_activity`, `xmin`/`catalog_xmin` в `pg_replication_slots` и подготовленные двухфазные транзакции в `pg_prepared_xacts`. `age(...)` помогает увидеть старые XID; один лишь большой `xact_start` без удерживаемого XID или snapshot ещё не доказывает причину. Не удаляйте действующий slot и не завершайте чужую транзакцию по одной строке мониторинга: проверьте владельца и потребителя репликации. [Routine Vacuuming: wraparound diagnostics](https://www.postgresql.org/docs/18/routine-vacuuming.html#VACUUM-FOR-WRAPAROUND), [pg_stat_activity](https://www.postgresql.org/docs/18/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW), [pg_replication_slots](https://www.postgresql.org/docs/18/view-pg-replication-slots.html), [pg_prepared_xacts](https://www.postgresql.org/docs/18/view-pg-prepared-xacts.html).

```sql
SELECT pid, state, xact_start, age(backend_xid) AS xid_age,
       age(backend_xmin) AS xmin_age
FROM pg_stat_activity
WHERE backend_xid IS NOT NULL OR backend_xmin IS NOT NULL;

SELECT slot_name, active, age(xmin) AS xmin_age,
       age(catalog_xmin) AS catalog_xmin_age
FROM pg_replication_slots
WHERE xmin IS NOT NULL OR catalog_xmin IS NOT NULL;

SELECT gid, prepared, age("transaction") AS xid_age
FROM pg_prepared_xacts;
```

**Параллельный `VACUUM` после обновления до PostgreSQL 19.** При включённых паузах по стоимости лидер и параллельные воркеры теперь делят бюджет `vacuum_cost_limit`. В PostgreSQL 18 каждый воркер учитывал собственные затраты для расчёта пауз, поэтому суммарная работа могла расходовать бюджет быстрее. В 19 очистка может занять больше времени даже при прежнем количестве воркеров. Этот лимит выражен в условных единицах стоимости операций над страницами.

Если окно обслуживания выросло после обновления, сравните длительность фаз и задержку запросов приложения при сопоставимом объёме работы. Текущую фазу показывает `pg_stat_progress_vacuum`. Прежде чем повышать лимит, проверьте, что паузы по стоимости включены и что время уходит на фазу с параллельной обработкой индексов. [Заметки о выпуске PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html), [Параметры VACUUM](https://www.postgresql.org/docs/19/runtime-config-vacuum.html), [VACUUM](https://www.postgresql.org/docs/19/sql-vacuum.html).

В PostgreSQL 19 для текущей операции можно снять несколько показаний `pg_stat_progress_vacuum`:

```sql
SELECT pid, phase, indexes_processed, indexes_total, delay_time
FROM pg_stat_progress_vacuum
WHERE relid = 'public.orders'::regclass;
```

В фазах обработки индексов `indexes_processed` показывает прогресс текущей фазы. При включённом `track_cost_delay_timing` рост `delay_time` показывает, что процессы спали из-за ограничения по стоимости. Это сумма пауз лидера и воркеров в миллисекундах. Паузы могут перекрываться, поэтому сумму нельзя вычитать из времени операции, чтобы получить время полезной работы. При выключенном учёте поле равно нулю. [Ход выполнения VACUUM](https://www.postgresql.org/docs/19/progress-reporting.html#VACUUM-PROGRESS-REPORTING).

У `VACUUM` есть и другие задачи: он обновляет карту видимости страниц, от которой зависит возможность `Index Only Scan` (Q18/Q23), и замораживает старые идентификаторы транзакций для защиты от переполнения XID. `ANALYZE` отдельно собирает распределение значений для планировщика; совмещённая команда — `VACUUM ANALYZE` (Q25/Q32).

```sql
-- Ручной запуск
VACUUM orders;

-- Посмотреть статистику dead tuples
SELECT relname, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

## Q32. В чём разница между `VACUUM` и `VACUUM FULL`?

Главное различие — что происходит с местом на диске и с блокировками:

| Команда | Поведение |
|---------|---------|
| `VACUUM` | Освобождает место для повторного использования; обычно работает одновременно с чтением и записью. Может вернуть свободный хвост файла ОС, кратко взяв `ACCESS EXCLUSIVE` |
| `VACUUM FULL` | Переписывает таблицу в новый файл, возвращает свободное место ОС и держит `ACCESS EXCLUSIVE` на время операции; требует дополнительного диска |
| `VACUUM ANALYZE` | Выполняет `VACUUM` + обновляет статистику (`ANALYZE`) |

Итог: регулярный `VACUUM` сохраняет доступность DML, хотя создаёт I/O-нагрузку и при обрезке хвоста может кратко взять исключительную блокировку. `VACUUM FULL` подходит для редкого возврата большого объёма диска, когда допустимы длительная блокировка и место под новую копию. Если таблица скоро снова вырастет, обычный `VACUUM` с повторным использованием пространства часто полезнее. [Routine Vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html), [VACUUM](https://www.postgresql.org/docs/18/sql-vacuum.html).

Обе формы `VACUUM` запускают **вне** явного транзакционного блока. Прогресс обычного `VACUUM`, включая autovacuum, смотрят в `pg_stat_progress_vacuum`, а переписывающего `VACUUM FULL` — в `pg_stat_progress_cluster`. Обычный `VACUUM` может пропустить очистку индексов при малом числе мёртвых кортежей; одно выполнение не доказывает, что в индексах больше нет устаревших записей. [VACUUM](https://www.postgresql.org/docs/18/sql-vacuum.html), [Progress Reporting](https://www.postgresql.org/docs/18/progress-reporting.html).

```sql
VACUUM ANALYZE orders;
VACUUM FULL orders;  -- осторожно: блокирует таблицу!
```

Если длительная блокировка неприемлема, в PostgreSQL 18 можно рассмотреть стороннее расширение [`pg_repack`](https://github.com/reorg/pg_repack/blob/master/doc/pg_repack.rst). Оно допускает обычную работу большую часть времени, но требует кратких блокировок и дополнительного места на диске. Проверьте доступность и ограничения расширения в своём окружении.

В PostgreSQL 19 появилась встроенная команда `REPACK (CONCURRENTLY)`. Она переписывает таблицу и её индексы, чтобы вернуть свободное место операционной системе. Для временной копии нужно свободное место как минимум под таблицу и все её индексы. Основная фаза проходит под `SHARE UPDATE EXCLUSIVE`, который позволяет обычные чтения и записи. Для финальной подмены файлов команда запрашивает `ACCESS EXCLUSIVE`. Старая транзакция со снимком, сделанным до начала переписывания, после подмены может увидеть таблицу пустой. Для обычной журналируемой heap-таблицы с подходящим первичным ключом или индексом replica identity команда выглядит как `REPACK (CONCURRENTLY) orders;`. Запускайте её вне транзакционного блока. Для финальной фазы учитывайте время ожидания блокировки и объём изменений, которые предстоит применить под ней. Для регулярной уборки мёртвых строк используют обычный `VACUUM`. [Примечания к выпуску PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html), [REPACK](https://www.postgresql.org/docs/19/sql-repack.html).

**Почему параллельные запуски могут упереться в слоты.** Пока строится новая копия, `REPACK (CONCURRENTLY)` захватывает изменения через логическое декодирование. Для этого ему нужен слот из отдельного лимита `max_repack_replication_slots` (по умолчанию 5, меняется при старте сервера). Например, если пять операций уже заняли все пять слотов, очередная команда не сможет запуститься. Можно дождаться завершения одной операции и повторить запуск. Увеличение общего `max_replication_slots` для репликации этот лимит не меняет. При расчёте диска учитывайте ещё и данные изменений, накопленных во время переписывания. [Настройки PostgreSQL 19](https://www.postgresql.org/docs/19/runtime-config-replication.html#GUC-MAX-REPACK-REPLICATION-SLOTS), [REPACK](https://www.postgresql.org/docs/19/sql-repack.html).

**Как проверить прогресс в PostgreSQL 19.** Для обычного `VACUUM` по-прежнему используется `pg_stat_progress_vacuum`. Для `REPACK`, `CLUSTER` и `VACUUM FULL` есть `pg_stat_progress_repack`. Старое представление `pg_stat_progress_cluster` сохраняется для совместимости.

```sql
SELECT pid, command, phase, heap_tuples_scanned, heap_tuples_inserted
FROM pg_stat_progress_repack
WHERE relid = 'orders'::regclass
  AND datname = current_database();
```

Если `REPACK CONCURRENTLY` остаётся в фазе `catch-up`, проверьте по PID, ждёт ли он блокировку (см. Q51). В этой фазе команда и применяет изменения, накопленные во время переписывания, и ждёт финальный `ACCESS EXCLUSIVE`. Счётчики отражают работу в отдельных фазах. По ним нельзя вычислить процент завершения всей команды. [Мониторинг прогресса в PostgreSQL 19](https://www.postgresql.org/docs/19/progress-reporting.html#REPACK-PROGRESS-REPORTING).

## Q33. Как работает `AUTOVACUUM` и как его настроить?

`AUTOVACUUM` — launcher и рабочие процессы, которые периодически проверяют таблицы и запускают `VACUUM` **и/или** `ANALYZE`, когда выполнены соответствующие условия. Проверка происходит по расписанию launcher, но сами операции зависят от изменений таблицы и отдельных порогов. `VACUUM` повторно использует место и защищает от переполнения XID (Q31); `ANALYZE` обновляет статистику планировщика (Q25).

Для обычного `VACUUM` по устаревшим строкам порог в PostgreSQL 18 равен `min(autovacuum_vacuum_max_threshold, autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × pg_class.reltuples)`. По умолчанию это `min(100 000 000, 50 + 0.2 × reltuples)`. Отдельно есть запуск `VACUUM` по вставкам и принудительный запуск против переполнения XID, даже когда autovacuum отключён.

Автоанализ использует **другой** порог: `autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × reltuples` (по умолчанию `50 + 0.1 × reltuples`). Он учитывает `INSERT`, `UPDATE` и `DELETE` с последнего `ANALYZE`. На большой таблице стандартные доли могут задерживать обслуживание; параметры меняют по реальным метрикам и нагрузке, а не по универсальному рецепту.

**Ключевые параметры:**

```sql
-- Пример настройки конкретной таблицы после проверки нагрузки и частоты обслуживания
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 1000,
    autovacuum_analyze_scale_factor = 0.02
);
```

Эти значения — только пример: для `VACUUM` учитывайте верхний предел и порог вставок. На партиционированной родительской таблице autovacuum не запускает `ANALYZE` для статистики всей иерархии; после существенных изменений распределения данных запускайте его вручную. Временные таблицы autovacuum тоже не обслуживает. [Routine Vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html), [Vacuuming Configuration](https://www.postgresql.org/docs/18/runtime-config-vacuum.html).

**Мониторинг:**
```sql
SELECT relname, last_autovacuum, last_autoanalyze, n_dead_tup,
       n_ins_since_vacuum, autovacuum_count, autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

`n_dead_tup` и `n_ins_since_vacuum` — оценки накопительной статистики, а не точный снимок состояния таблицы. Если обслуживание уже идёт, проверяйте `pg_stat_progress_vacuum`; если счётчики растут несмотря на запуски, ищите долго живущие снимки, replication slots и причину задержки worker, прежде чем снижать пороги. [Monitoring Statistics](https://www.postgresql.org/docs/18/monitoring-stats.html), [Progress Reporting](https://www.postgresql.org/docs/18/progress-reporting.html).

**В PostgreSQL 19 порог запуска и приоритет обслуживания решают разные задачи.** Внутри выбранной базы worker ранжирует таблицы, которым уже нужен `VACUUM` или `ANALYZE`. Итоговый балл — максимум взвешенных компонентов: возраста XID и MultiXact, потребности в очистке после обновлений или удалений, обслуживания после вставок и обновления статистики. Если две таблицы превысили порог, размер таблицы или число мёртвых строк сами по себе не определяют, какую обработают раньше. Посмотрите компоненты в `pg_stat_autovacuum_scores` текущей базы и проверьте активные операции в `pg_stat_progress_vacuum`. Балл показывает текущий приоритет, а стадия и факт запуска видны в представлении прогресса. [Autovacuum Prioritization](https://www.postgresql.org/docs/19/routine-vacuuming.html#AUTOVACUUM-PRIORITIZATION).

В PostgreSQL 19 один autovacuum worker может привлекать дополнительные процессы для параллельной очистки индексов. Это относится к индексным фазам, тогда как основной обход страниц таблицы остаётся отдельной фазой. По умолчанию `autovacuum_max_parallel_workers = 0`. Ненулевое значение задаёт максимум на один autovacuum worker. Фактический параллелизм зависит от подходящих индексов, настройки таблицы `autovacuum_parallel_workers` и доступных процессов. Если задержка приходится на обход таблицы или очистку ограничивает удерживаемый снимок, увеличение этого лимита не устраняет причину. [Parallel Vacuum](https://www.postgresql.org/docs/19/routine-vacuuming.html#PARALLEL-VACUUM), [Vacuuming Configuration](https://www.postgresql.org/docs/19/runtime-config-vacuum.html#GUC-AUTOVACUUM-MAX-PARALLEL-WORKERS).

Если autovacuum **не запускается вовсе** после параллельной сборки GIN-индекса, проверьте оценку `pg_class.reltuples` для этой таблицы. В PostgreSQL 18 до исправления **18.6** такая сборка могла записать `Infinity` или `NaN`; тогда формула порога переставала выбирать таблицу, и состояние не исправлялось само. Исправление в 18.6 предотвращает новые случаи, а уже неверное значение требует ручного `ANALYZE` после проверки конкретной таблицы. Это специальная диагностика для затронутых версий, а не обычная причина каждого запаздывания autovacuum. [PostgreSQL 18.6 release notes](https://www.postgresql.org/docs/18/release-18-6.html), [анонс исправления от 13.08.2026](https://www.postgresql.org/about/news/postgresql-186-1711-1615-1519-1424-and-19-beta-3-released-3365/).

**Как понять, почему запустился текущий VACUUM.** В PostgreSQL 19 `pg_stat_progress_vacuum` показывает причину запуска в `started_by` и текущий режим в `mode`. Если миграция ждёт блокировку, которую держит процесс VACUUM, найдите его PID по Q51 и проверьте оба поля:

```sql
SELECT pid, relid::regclass AS relation, started_by, mode, phase
FROM pg_stat_progress_vacuum
WHERE datname = current_database();
```

`started_by = 'autovacuum_wraparound'` означает запуск для защиты от переполнения счётчика XID или MultiXact. PostgreSQL может автоматически прервать обычный autovacuum при конфликте блокировок, но для запуска с этой причиной такого прерывания нет. `mode = 'failsafe'` описывает текущий режим, в котором VACUUM оставляет только работу, необходимую для защиты от wraparound. Даже вручную запущенный VACUUM может перейти в этот режим. [Прогресс VACUUM в PostgreSQL 19](https://www.postgresql.org/docs/19/progress-reporting.html#VACUUM-PROGRESS-REPORTING).
**Предупреждение о wraparound.** PostgreSQL 19 начинает предупреждать клиента и писать в журнал, когда до переполнения XID или MultiXact остаётся менее 100 млн идентификаторов. Прежний порог предупреждения составлял 40 млн. Порог предупреждения и порог запуска защитного VACUUM задают разные границы. Если после обновления предупреждение появляется раньше, проверяйте возраст идентификаторов и ход защитной очистки. Изменение порога само по себе не означает, что очистка стала отставать. [Примечания к выпуску PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html).

**Журнал автоматического `ANALYZE`.** Если после массовой загрузки планировщик продолжает ошибаться в оценках, проверьте `last_autoanalyze` в `pg_stat_user_tables` и журнал сервера. С PostgreSQL 19 длительность автоматического `ANALYZE` журналирует отдельный параметр `log_autoanalyze_min_duration`, а `log_autovacuum_min_duration` относится к автоматическому `VACUUM`. Если до обновления оба вида событий собирались через `log_autovacuum_min_duration = 250ms`, для сохранения этого порога у `ANALYZE` задайте `log_autoanalyze_min_duration = 250ms` отдельно. В PostgreSQL 19 его значение по умолчанию — `10min`, поэтому короткий успешный запуск может не появиться в журнале. [Настройки журналирования PostgreSQL 19](https://www.postgresql.org/docs/19/runtime-config-logging.html#GUC-LOG-AUTOANALYZE-MIN-DURATION).

## Q34. Что такое `table bloat` и как его измерить?

**`Table bloat`** — избыточное место в таблице относительно её полезных живых строк. Оно может содержать мёртвые версии и свободное пространство после `VACUUM`; часть свободного пространства намеренно оставляют для будущих `UPDATE` через `fillfactor`. Большой файл сам по себе не доказывает bloat: в нём могут быть живые данные. Раздувание индекса оценивают отдельно от таблицы.

Лишние страницы увеличивают I/O и могут вытеснять полезные страницы из кэша. Сначала оцените размер отношений и динамику, затем измерьте доли живых/мёртвых кортежей и свободного места. `pg_relation_size` и `pg_total_relation_size` показывают размер, **не процент bloat**.

```sql
-- Размер таблицы и индексов
SELECT
    relname,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    pg_size_pretty(pg_relation_size(relid)) AS table_size,
    pg_size_pretty(pg_indexes_size(relid)) AS indexes_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple; -- при наличии права и разрешения на расширение
SELECT table_len, tuple_percent, dead_tuple_percent, free_percent
FROM pgstattuple('public.orders');

-- На большой таблице: часть живых строк и свободного места оценивается приближённо
SELECT table_len, scanned_percent, dead_tuple_percent, approx_free_percent
FROM pgstattuple_approx('public.orders');
```

`pgstattuple` полностью сканирует таблицу и даёт точные счётчики на просмотренных страницах; `pgstattuple_approx` может пропускать полностью видимые страницы, сохраняя точную статистику dead tuples, но оценивая живые строки и свободное место приближённо. При параллельных изменениях даже полный проход **не является мгновенным снимком** всей таблицы. На крупной таблице учитывайте стоимость проверки; выполнение функций по умолчанию ограничено правами роли `pg_stat_scan_tables` или суперпользователя. Для B-tree индекса есть `pgstatindex`, а для других типов — отдельные функции и ограничения. [pgstattuple](https://www.postgresql.org/docs/18/pgstattuple.html). См. Q31/Q32 о том, когда обычный `VACUUM` повторно использует место и когда нужна перезапись.

## Q35. (!) Какие виды партиционирования поддерживает PostgreSQL?

Партиционирование разбивает логическую таблицу на физические партиции по ключу. Родительская таблица при декларативном партиционировании не хранит строки: они направляются в подходящие дочерние таблицы. Это может ускорить запросы, которые читают небольшое число партиций, и удаление больших порций старых данных. `DROP TABLE` партиции или `DETACH PARTITION` обычно быстрее массового `DELETE`, но это операции DDL с блокировками; их планируют с учётом конкурирующей нагрузки.

PostgreSQL 18 поддерживает **декларативное партиционирование** трёх видов. `RANGE` и `LIST` появились в PostgreSQL 10, `HASH` — в PostgreSQL 11. Выбор зависит от природы ключа и запросов:

| Тип | Описание | Пример использования |
|-----|---------|---------------------|
| `RANGE` | По непересекающимся диапазонам: нижняя граница включается, верхняя нет | По дате (`created_at`) |
| `LIST` | По списку значений | По стране, статусу, категории |
| `HASH` | По хэшу ключа, модулю и остатку | Фиксированное число партиций без естественных диапазонов |

Интуиция выбора: `RANGE` удобен для интервалов и удаления старых периодов, `LIST` — для ограниченного набора значений, `HASH` — для распределения строк по заданному числу партиций. Хэширование не гарантирует равномерную **нагрузку запросов** и само по себе не улучшает поиск без подходящего условия. [Table Partitioning](https://www.postgresql.org/docs/18/ddl-partitioning.html).

```sql
-- RANGE партиционирование по дате
CREATE TABLE orders (
    id BIGSERIAL,
    user_id INT,
    total NUMERIC,
    created_at TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2025 PARTITION OF orders
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

CREATE TABLE orders_2026 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

-- LIST партиционирование
CREATE TABLE orders_by_region (
    id BIGSERIAL,
    region TEXT NOT NULL,
    total NUMERIC
) PARTITION BY LIST (region);

CREATE TABLE orders_ru PARTITION OF orders_by_region FOR VALUES IN ('RU');
CREATE TABLE orders_kz PARTITION OF orders_by_region FOR VALUES IN ('KZ');
```

Подпартиционирование также поддерживается: партиция может сама быть таблицей, разбитой, например, через `HASH` или `LIST`. Для `INSERT` нужна подходящая партиция; у `RANGE` и `LIST` можно добавить `DEFAULT`, а у `HASH` такой партиции нет. Если значение не попадает ни в одну партицию, вставка завершится ошибкой. При выборе числа партиций учитывайте накладные расходы на планирование и обслуживание. [PostgreSQL 10: Partitioning](https://www.postgresql.org/docs/10/ddl-partitioning.html), [PostgreSQL 11: Release Notes](https://www.postgresql.org/docs/11/release-11.html), [CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html).

При удалении старого периода `DROP TABLE` партиции берёт `ACCESS EXCLUSIVE` на родителе. Обычный `DETACH PARTITION` тоже берёт эту блокировку, а `DETACH PARTITION ... CONCURRENTLY` снижает её на родителе до `SHARE UPDATE EXCLUSIVE`, но ждёт завершения транзакций, работавших с таблицей; на самой отделяемой партиции в конце требуется `ACCESS EXCLUSIVE`. В PostgreSQL 18 форму `CONCURRENTLY` нельзя запускать внутри транзакционного блока или при наличии `DEFAULT`-партиции. [Table Partitioning](https://www.postgresql.org/docs/18/ddl-partitioning.html), [ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html).

## Q36. Как работает `partition pruning`?

`Partition pruning` исключает из чтения партиции, границы которых несовместимы с условием запроса на ключ. Это может происходить при планировании, при инициализации плана или в ходе выполнения, когда станут известны параметры. Отсечение опирается на **границы партиций**, а не на наличие индекса по ключу. Условие на ключ помогает лишь тогда, когда PostgreSQL может доказать несовместимость с границами; произвольная функция над ключом не гарантирует pruning. В PostgreSQL 18 `enable_partition_pruning` включён по умолчанию; если он выключен, планировщик и исполнитель не исключат части этим механизмом. [Partition Pruning](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITION-PRUNING).

```sql
-- При подходящих границах будет нужна только orders_2026
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';
```

При параметризованном запросе часть партиций может быть отсечена **при инициализации**: в плане появится `Subplans Removed`. При значении, известном лишь во время выполнения, некоторые узлы остаются в `EXPLAIN (ANALYZE)`, но имеют `loops=0` или отметку `(never executed)`. Партиции, отсечённые при инициализации, всё же могут быть заблокированы в начале выполнения.

**Проверка generic plan.** Пусть `orders` разбита по диапазонам `created_at` и каждый год занимает отдельную партицию. Границы запроса становятся известны при `EXECUTE`, поэтому PostgreSQL может отсечь лишние партиции при инициализации, даже если при планировании значения параметров были неизвестны:

```sql
PREPARE orders_in_period AS
SELECT * FROM orders WHERE created_at >= $1 AND created_at < $2;

BEGIN;
SET LOCAL plan_cache_mode = force_generic_plan;
EXPLAIN (ANALYZE, BUFFERS)
EXECUTE orders_in_period('2026-01-01', '2027-01-01');
ROLLBACK;

DEALLOCATE orders_in_period;
```

При успешном отсечении на этом этапе ищите `Subplans Removed` и сканирование только нужной партиции. Метка `(never executed)` говорит, что узел не запускался. Чтобы связать её с отсечением во время выполнения, проверьте контекст узла: например, вложенный `Append` может вообще не получить ни одного вызова, если внешняя сторона `Nested Loop` пуста. [Partition Pruning в PostgreSQL 19](https://www.postgresql.org/docs/19/ddl-partitioning.html#DDL-PARTITION-PRUNING).

Проверяйте `EXPLAIN` и `EXPLAIN (ANALYZE)` для конкретных параметров: отсутствие партиции в плане, `Subplans Removed` и число запусков отвечают на **разные этапы** отсечения. Если в PostgreSQL 18 подозреваете пропажу строк из `DEFAULT`-партиции при `RANGE`, проверьте минорную версию: в 18.6 исправлена ошибка, из-за которой pruning мог пропустить нужную партицию. [Partition Pruning](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITION-PRUNING), [PostgreSQL 18.6 Release Notes](https://www.postgresql.org/docs/18/release-18-6.html).

## Q37. Когда партиционирование не даёт выигрыша?

Партиционирование окупается, если выигрыш от локальности данных или обслуживания превышает накладные расходы. Перед выбором ключа проверьте реальные запросы, планы и способ удаления данных. Типичные ограничения:

- **Нет условия, ограничивающего ключ:** по одним границам партиций нельзя исключить ненужные части. В некоторых запросах нужное значение приходит при выполнении, например из очередной строки внешней стороны `Nested Loop`. Узел передаёт значение параметризованному внутреннему плану, и при повторном сканировании значение может ограничить ключ партиционирования. Поэтому отсутствие константы в SQL само по себе не исключает pruning.
- **Таблица мала или читается широко:** накладные расходы на дополнительные отношения и маршрутизацию могут перевесить выигрыш от отсечения. Сравните планы с непартиционированной схемой на реальной нагрузке.
- **Много партиций остаётся после отсечения:** растут время и память планирования, а также память сеансов, обращающихся ко многим партициям. Несколько тысяч партиций допустимы, если типовые запросы оставляют мало нужных частей; универсального порога нет.
- **Нужна уникальность по столбцу без ключа партиционирования:** виртуальный индекс родителя состоит из индексов дочерних таблиц, поэтому `PRIMARY KEY`/`UNIQUE` на родителе должен включать все столбцы ключа партиционирования; ключ с выражением для такого ограничения не подходит. Индекс, объявленный на родителе, создаёт индексы на дочерних таблицах, но не становится единым глобальным индексом. [Partitioning Limitations](https://www.postgresql.org/docs/18/ddl-partitioning.html), [Best Practices](https://www.postgresql.org/docs/18/ddl-partitioning.html).

Например, у `orders PARTITION BY RANGE (created_at)` нельзя объявить на родителе `PRIMARY KEY (id)`: один и тот же `id` мог бы попасть в разные месяцы. `PRIMARY KEY (id, created_at)` допустим, но это уже другой контракт уникальности. Если приложению нужен уникальный `id` независимо от даты, продумайте его обеспечение до выбора схемы партиционирования.

Это меняет и связи с другими таблицами. Если у `orders` первичный ключ `(id, created_at)`, то `order_items` может ссылаться на него через `FOREIGN KEY (order_id, order_created_at) REFERENCES orders (id, created_at)`. Ссылка только по `order_id` на `orders(id)` не создастся: на родителе нет допустимого `PRIMARY KEY`/`UNIQUE` по одному `id`. Даже если каждый дочерний раздел имеет собственный `UNIQUE (id)`, он не создаёт уникальность `id` на родителе. Поэтому до миграции проверьте не только запросы к `orders`, но и все таблицы, которые хранят ссылку на заказ. [Foreign Keys](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK), [Partitioning Limitations](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS).

## Q38. (!) Что такое оконные функции и как они работают?

Оконная функция вычисляет значение для каждой строки по связанным с ней строкам, **сохраняя отдельные строки результата**. Так работают и агрегаты с `OVER`, и функции ранжирования или смещения. Обычный агрегат с `GROUP BY` сворачивает группу в строку; `SUM(...) OVER (...)` может добавить итог рядом с каждой исходной строкой.

`OVER (...)` задаёт разбиение через `PARTITION BY` и порядок внутри него через `ORDER BY`. Рамка (`ROWS`, `RANGE`, `GROUPS`) ограничивает строки для функций, которые её учитывают, в частности оконных агрегатов и `FIRST_VALUE`/`LAST_VALUE`/`NTH_VALUE`; `LAG`/`LEAD` обращаются по позиции внутри всей партиции. Оконная сортировка не гарантирует порядок выдачи результата: для него нужен внешний `ORDER BY`.

```sql
SELECT
    user_id,
    order_date,
    total,
    SUM(total) OVER (PARTITION BY user_id ORDER BY order_date) AS running_total,
    AVG(total) OVER (PARTITION BY user_id) AS avg_per_user,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_date DESC) AS rn
FROM orders;
```

В этом примере `running_total` использует рамку по умолчанию: заказы с одинаковой `order_date` могут получить один накопленный итог. Если итог должен расти строго по строкам, задайте явную рамку `ROWS` и устойчивый порядок сортировки (Q41).

**Синтаксис:**
```sql
function_name(...) OVER (
    [PARTITION BY col1, col2]
    [ORDER BY col3 [ASC|DESC]]
    [ROWS|RANGE|GROUPS BETWEEN ... AND ...]
)
```

**Виды функций:**
- **Ранжирование:** `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `NTILE(n)`
- **Соседние строки:** `LAG()`, `LEAD()`
- **Значения из рамки:** `FIRST_VALUE()`, `LAST_VALUE()`, `NTH_VALUE()`
- **Агрегатные:** `SUM()`, `AVG()`, `COUNT()`, `MIN()`, `MAX()`

Ловушка: `LAST_VALUE(total) OVER (PARTITION BY user_id ORDER BY order_date)` при рамке по умолчанию смотрит лишь до последнего peer текущей строки, а не до конца партиции. Для значения из последней строки всей партиции задайте устойчивый порядок и рамку `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`. Оконные функции вычисляются после `WHERE`, группировки и `HAVING`. Результат `ROW_NUMBER()` нельзя фильтровать в `WHERE` того же уровня: используйте подзапрос или CTE. [Window Functions](https://www.postgresql.org/docs/18/functions-window.html), [Window Function Processing](https://www.postgresql.org/docs/18/queries-table-expressions.html).

## Q39. Как работают `ROW_NUMBER`, `RANK` и `DENSE_RANK`?

Все три нумеруют строки внутри партиции по `ORDER BY`, но по-разному ведут себя при одинаковых значениях ключа сортировки (*peers*):

| Функция | Описание | Поведение при дублях |
|---------|---------|---------------------|
| `ROW_NUMBER()` | Уникальный порядковый номер | У peers номера разные, но их порядок не определён без дополнительного ключа |
| `RANK()` | Ранг с пропуском при дублях | 1, 2, 2, 4 |
| `DENSE_RANK()` | Ранг без пропуска | 1, 2, 2, 3 |

`RANK` даёт peers один ранг и затем оставляет пропуск; `DENSE_RANK` даёт тот же ранг без последующего пропуска. `ROW_NUMBER` присваивает каждой строке свой номер. Если нужен воспроизводимый выбор одной строки при равенстве дат или баллов, добавьте в `ORDER BY` уникальный ключ. [Window Functions](https://www.postgresql.org/docs/18/functions-window.html).

```sql
SELECT
    name,
    score,
    ROW_NUMBER() OVER (ORDER BY score DESC) AS row_num,
    RANK()       OVER (ORDER BY score DESC) AS rnk,
    DENSE_RANK() OVER (ORDER BY score DESC) AS dense_rnk
FROM leaderboard;
```

**Распространённый паттерн:** топ-N записей на группу:

```sql
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC, id DESC) AS rn
    FROM orders
) t
WHERE rn = 1; -- последний заказ каждого пользователя
```

Если нужны все строки с ничьей на границе топа, фильтруйте вычисленный ранг во внешнем запросе: `rnk <= N` может вернуть больше `N` строк. Фильтр по `DENSE_RANK()` выбирает до `N` групп разных значений и тоже может вернуть больше строк. `ROW_NUMBER()` ограничивает число строк, но для воспроизводимого выбора среди равных значений ему нужен дополнительный уникальный ключ в оконном `ORDER BY`.

## Q40. Как работают `LAG` и `LEAD`?

`LAG` и `LEAD` возвращают значение из строки на заданном смещении **внутри партиции**, без самосоединения. Направление задаёт `ORDER BY` в `OVER`; при одинаковых ключах сортировки добавьте уникальный столбец, если сравнение должно быть воспроизводимым.

- **`LAG(col, offset, default)`** — значение из строки на `offset` позиций **раньше** (по умолчанию `offset = 1`).
- **`LEAD(col, offset, default)`** — значение из строки на `offset` позиций **позже**.

Если нужной строки нет, возвращается `default`, а при его отсутствии — `NULL`. `default` не подменяет `NULL` из **существующей** соседней строки и вычисляется для текущей строки: например, `LAG(total, 1, total)` вернёт её `total` при отсутствии предыдущей. В PostgreSQL 18 функции учитывают строки с `NULL`, а синтаксиса `IGNORE NULLS` ещё нет. PostgreSQL 19 добавил `IGNORE NULLS` для `lag`, `lead`, `first_value`, `last_value` и `nth_value`. Например, `LAG(total) IGNORE NULLS OVER (PARTITION BY user_id ORDER BY order_date, id)` ищет предыдущее ненулевое значение. Без явного указания действует `RESPECT NULLS`. Для `LAST_VALUE` пропуск `NULL` не расширяет рамку до конца партиции (Q38). [PostgreSQL 18](https://www.postgresql.org/docs/18/functions-window.html), [PostgreSQL 19](https://www.postgresql.org/docs/19/functions-window.html).

```sql
SELECT
    order_date,
    total,
    LAG(total, 1, 0)  OVER (PARTITION BY user_id ORDER BY order_date, id) AS prev_total,
    LEAD(total, 1, 0) OVER (PARTITION BY user_id ORDER BY order_date, id) AS next_total,
    total - LAG(total) OVER (PARTITION BY user_id ORDER BY order_date, id) AS diff_from_prev
FROM orders;
```

## Q41. Как использовать `SUM OVER` и скользящие агрегаты?

Оконные агрегаты (`SUM`, `AVG` с `OVER`) дают то, чего не умеет обычный `GROUP BY`: считать накопительные и скользящие значения, сохраняя при этом каждую строку. Поведение определяет **рамка окна** (`frame`):

- **Без `ORDER BY`** агрегат берётся по всей партиции — одно значение для всей группы.
- **С `ORDER BY`** рамка по умолчанию — `RANGE UNBOUNDED PRECEDING`: от начала партиции до **последнего peer текущей строки**. При одинаковом ключе сортировки сумма меняется сразу для всей группы peers.
- **Явная рамка** `ROWS BETWEEN N PRECEDING AND CURRENT ROW` берёт текущую и до `N` предыдущих **строк**. Для накопления строго по строкам задайте `ROWS UNBOUNDED PRECEDING` и устойчивый порядок.

```sql
-- Нарастающий итог (running total)
SELECT
    order_date,
    total,
    SUM(total) OVER (
        ORDER BY order_date, id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total
FROM orders;

-- Среднее по текущей и шести предыдущим строкам (не обязательно 7 дней)
SELECT
    order_date,
    total,
    AVG(total) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS moving_avg_7_rows
FROM daily_revenue;

-- Итог в рамках группы (без ORDER BY — агрегат по всей группе)
SELECT
    user_id,
    total,
    SUM(total) OVER (PARTITION BY user_id) AS user_total
FROM orders;
```

**Разница `ROWS`, `RANGE` и `GROUPS`:**
- `ROWS BETWEEN N PRECEDING AND CURRENT ROW` — текущая строка плюс до `N` предыдущих по позиции; в начале партиции их может быть меньше.
- `RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW` при сортировке по `timestamp` — диапазон значений за шесть предшествующих суток и текущую границу; строк может быть любое число. Равные значения сортировки попадают в одну рамку.
- `GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW` — текущая группа строк с одинаковым ключом сортировки и одна предыдущая такая группа; число строк в группах может различаться.

Для рамки `RANGE` со смещением PostgreSQL 18 требует ровно одно выражение в оконном `ORDER BY`; `GROUPS` требует сортировку, по которой можно выделить группы peers. Проверяйте рамку при дублирующихся датах: рамка по умолчанию не эквивалентна `ROWS ... CURRENT ROW`. [Window Function Calls](https://www.postgresql.org/docs/18/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS), [Window Functions](https://www.postgresql.org/docs/18/functions-window.html).

## Q42. (!) Что такое `CTE` и чем он отличается от подзапроса?

**`CTE` (Common Table Expression)** — это именованный вспомогательный запрос в блоке `WITH`, результат которого доступен основному запросу по имени. Его удобно использовать для читаемых шагов и нескольких ссылок на одно определение. `WITH` может содержать и изменяющие данные команды; правила встраивания ниже относятся к обычному `SELECT`.

```sql
WITH active_users AS (
    SELECT id, name FROM users WHERE status = 'active'
),
recent_orders AS (
    SELECT user_id, SUM(total) AS total_spent
    FROM orders
    WHERE created_at > NOW() - INTERVAL '30 days'
    GROUP BY user_id
)
SELECT u.name, ro.total_spent
FROM active_users u
JOIN recent_orders ro ON u.id = ro.user_id
ORDER BY ro.total_spent DESC;
```

**`CTE` против подзапроса.** Помимо имени и повторного использования, на план влияет число ссылок и свойства запроса:

| Характеристика | `CTE` | Подзапрос |
|---------------|-------|-----------|
| Читаемость | Высокая, можно именовать | Может быть сложным при вложении |
| Повторное использование | Одно определение доступно по имени для нескольких ссылок | Для независимых ссылок определение обычно приходится повторять |
| Оптимизация (PostgreSQL < 12) | `CTE` вычисляется отдельно и служит барьером для совместной оптимизации | Планировщик может преобразовать подзапрос |
| Оптимизация (PostgreSQL 12+) | `SELECT` без рекурсии и volatile-функций обычно встраивается при одной ссылке; при нескольких по умолчанию вычисляется отдельно | Планировщик может преобразовать подзапрос; результат зависит от его формы |
| `MATERIALIZED` / `NOT MATERIALIZED` (12+) | Управляют отдельным вычислением или встраиванием, если оно допустимо | К подзапросу эти указания не применяются |

**Версионный нюанс:** до PostgreSQL 12 `CTE` не встраивался в основной запрос, поэтому внешнее условие обычно нельзя было протолкнуть внутрь него. Начиная с 12 планировщик по умолчанию встраивает нерекурсивный `SELECT` без volatile-функций, если на него ссылаются один раз. При нескольких ссылках он по умолчанию вычисляется отдельно: это избегает повторного вычисления, но может помешать проталкиванию разных условий. `NOT MATERIALIZED` разрешает встраивание с риском повторной работы; `MATERIALIZED` принудительно сохраняет отдельное вычисление. Для рекурсивного или содержащего volatile-функции `CTE` `NOT MATERIALIZED` не действует. Выбор проверяют через `EXPLAIN (ANALYZE, BUFFERS)` на конкретном запросе. Например, если две ссылки на CTE читают разные небольшие диапазоны одной большой таблицы, встраивание может дать отдельный индексный доступ для каждого диапазона. Если обе ссылки используют почти весь результат дорогого вычисления, отдельное вычисление CTE может оказаться дешевле.

```sql
-- Принудительная материализация (PostgreSQL 12+)
WITH stats AS MATERIALIZED (
    SELECT AVG(total) AS avg_total FROM orders
)
SELECT * FROM orders, stats WHERE total > stats.avg_total;
```

[Документация PostgreSQL 18: материализация CTE](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-CTE-MATERIALIZATION).

**Изменяющий данные `WITH` работает иначе.** `INSERT`, `UPDATE`, `DELETE` или `MERGE` внутри `WITH` выполняется один раз и до конца, даже если основной запрос не прочитает результат. Другие части команды видят тот же снимок данных; передать им изменённые строки можно через `RETURNING`, а не повторным чтением целевой таблицы. Такие CTE допустимы только при верхнеуровневой команде; правила встраивания `SELECT` и указание `NOT MATERIALIZED` не меняют их поведение. Например:

```sql
WITH changed AS (
    UPDATE products SET price = price + 10 WHERE id = 42
    RETURNING id, price
)
SELECT id, price FROM changed;
```

[Документация PostgreSQL 18: изменяющие данные команды в WITH](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-MODIFYING).

## Q43. (!) Как работают рекурсивные `CTE`?

**Рекурсивный `CTE`** (`WITH RECURSIVE`) обходит дерево или граф неизвестной глубины. Он состоит из нерекурсивной стартовой части и части, которая ссылается на результат предыдущей итерации. PostgreSQL вычисляет такой запрос итеративно.

```sql
-- Обход иерархии сотрудников
WITH RECURSIVE emp_hierarchy AS (
    -- Базовый случай: корневые узлы
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Рекурсивный шаг
    SELECT e.id, e.name, e.manager_id, eh.depth + 1
    FROM employees e
    JOIN emp_hierarchy eh ON e.manager_id = eh.id
)
SELECT id, name, depth FROM emp_hierarchy ORDER BY depth, name;
```

**Как это работает по шагам:**
1. Нерекурсивная часть один раз создаёт стартовые строки и рабочую таблицу.
2. Рекурсивная часть читает строки рабочей таблицы, выдаёт следующий набор и заменяет им рабочую таблицу.
3. Шаг 2 повторяется, пока очередной набор не станет пустым.

`UNION ALL` сохраняет все строки. `UNION` удаляет полные дубликаты, но не гарантирует защиту от цикла: например, растущий `depth` делает строки различными. Порядок строк результата без `ORDER BY` не гарантирован. Начиная с PostgreSQL 14, `SEARCH DEPTH FIRST` и `SEARCH BREADTH FIRST` вычисляют столбец сортировки; затем по нему нужно явно сортировать результат. Это не задаёт порядок фактического посещения узлов. [PostgreSQL 14 Release Notes](https://www.postgresql.org/docs/14/release-14.html).

**Подводный камень:** при цикле `UNION ALL` может повторяться бесконечно. Условие `WHERE eh.depth < 10` внутри рекурсивного шага обрывает обход, но может скрыть допустимые глубокие узлы. Для графа лучше отслеживать посещённые ключи или использовать `CYCLE`: повтор проверяется **на текущем пути**, поэтому один узел может встречаться в разных независимых путях. Циклическая строка помечается, но из неё рекурсия дальше не продолжается.

```sql
-- edges(src bigint, dst bigint)
WITH RECURSIVE walk(node) AS (
    SELECT 1::bigint
    UNION ALL
    SELECT e.dst FROM walk w JOIN edges e ON e.src = w.node
) SEARCH BREADTH FIRST BY node SET bfs_order
  CYCLE node SET is_cycle USING path
SELECT node, is_cycle, path FROM walk ORDER BY bfs_order;
```

Если нужен порядок по глубине, `SEARCH DEPTH FIRST` вместе с `CYCLE` обычно дублирует вычисление пути: можно сортировать по добавленному `path`. Внешний `LIMIT` годится только как вспомогательная проверка: сортировка или соединение во внешнем запросе могут потребовать весь результат. [Документация PostgreSQL 18: рекурсивные запросы и циклы](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-RECURSIVE).

## Q44. (!) Что такое `streaming replication` в PostgreSQL?

**`Streaming replication`** — физическая репликация: `primary` передаёт `standby` записи `WAL` по TCP, а standby применяет их к своей копии кластера. По умолчанию передача асинхронна: `primary` может подтвердить коммит до того, как изменение станет видимым на standby. Наличие streaming само по себе не означает синхронного подтверждения коммита или немедленной видимости записи при чтении с реплики. [Standby Server Operation](https://www.postgresql.org/docs/18/warm-standby.html).

`synchronous_commit` определяет, на каком этапе можно ответить клиенту об успешном коммите. Для ожидания подтверждения от реплик задают `synchronous_standby_names` и выбирают режим `on`, `remote_write` или `remote_apply`. Если требуемого числа подходящих реплик нет, коммит продолжает ждать, пока условие синхронного подтверждения не будет выполнено или ожидание не прервут. Если список пуст, `local`, `remote_write` и `remote_apply` дают тот же локальный уровень подтверждения, что `on`. [WAL configuration](https://www.postgresql.org/docs/18/runtime-config-wal.html).

| Режим `synchronous_commit` | Описание |
|--------------------------|---------|
| `off` | Ответ без ожидания локального flush WAL; недавний подтверждённый коммит может потеряться при сбое |
| `local` | Запись на диск `primary`, без ожидания реплики |
| `remote_write` | Ожидание записи WAL в файловую систему синхронной standby, без гарантии durable flush на ней |
| `remote_apply` | Ожидание применения WAL на синхронной standby и видимости изменения её запросам |
| `on` | Локальный flush и, при синхронной standby, ожидание durable flush на ней |

После коммита с `remote_apply` запрос с новым снимком увидит запись на standby, которая подтвердила её применение. Например, при `ANY 2 (s1, s2, s3)` коммит может дождаться `s1` и `s2`, пока `s3` ещё отстаёт. Балансировщику нужна реплика с подтверждённым применением записи. После смены primary проверяйте, что новый источник чтения сохранил этот коммит. [Синхронные standby PostgreSQL 19](https://www.postgresql.org/docs/19/warm-standby.html#SYNCHRONOUS-REPLICATION).

Ожидание реплики повышает задержку и влияет на доступность записи при её отказе. `off` может потерять недавний подтверждённый коммит при сбое, но не делает данные внутренне несогласованными, в отличие от выключения `fsync`. Если приложение читает с асинхронной реплики, способы обеспечить чтение после записи разобраны в [Database Transactions Q41](database-transactions-interview.md#q41-read-your-writes-consistency--механизмы-обеспечения).

**Read-your-writes на выбранной реплике.** После успешного `COMMIT` приложение получает на primary целевую позицию через `pg_current_wal_insert_lsn()`. Начиная с PostgreSQL 19, на физической реплике той же истории WAL можно дождаться применения этой позиции:

```sql
-- Отдельная команда на выбранной реплике. Подставьте полученный LSN.
WAIT FOR LSN '0/12345678' WITH (MODE 'standby_replay', TIMEOUT '2s');
```

После успешного ожидания выполните чтение с новым снимком на том же узле. Вызывайте `WAIT` до получения снимка и блокировок, например отдельной командой перед транзакцией чтения. При таймауте заново выберите источник чтения с учётом оставшегося бюджета запроса. После смены ветки WAL проверьте, что её история содержит нужный коммит. `WAIT` сравнивает числовой LSN, поэтому достижение той же позиции на другой ветке само по себе не подтверждает применение записи. В PostgreSQL 18 это ожидание реализует приложение, опрашивая `pg_last_wal_replay_lsn()`. `remote_apply` переносит ожидание на коммит, а `WAIT FOR LSN` позволяет дождаться нужного состояния перед конкретным чтением. [WAIT в PostgreSQL 19](https://www.postgresql.org/docs/19/sql-wait.html), [функции WAL PostgreSQL 18](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-RECOVERY-INFO-TABLE).

**Как обработать результат ожидания.** В примере без `NO_THROW` таймаут завершает команду ошибкой. Если приложение добавляет `NO_THROW`, оно должно проверить статус и продолжить чтение только после `success`. При `timeout` можно направить чтение на проверенный primary, если это допускает политика приложения. При `not in recovery` перепроверьте роль узла и историю WAL. Команда сравнивает числовые LSN, поэтому даже `success` после переключения upstream не подтверждает принадлежность записи ожидаемой timeline. Если от этого зависит гарантия read-your-writes, приложение должно проверить историю WAL отдельно. [PostgreSQL 19: статусы и ограничения WAIT](https://www.postgresql.org/docs/19/sql-wait.html).

**Диагностика таймаута ожидания в PostgreSQL 19.** На выбранной standby сравните целевой LSN с `pg_stat_wal_receiver.flushed_lsn` и `pg_stat_recovery.last_replayed_end_lsn`. Сравнение имеет смысл для позиций одной истории WAL. Если receiver уже подтвердил запись до целевой позиции, а replay ещё до неё не дошёл, проверяйте применение WAL. Например, `pg_stat_recovery.pause_state = 'paused'` указывает, что воспроизведение приостановлено. Поле `replay_end_lsn` может указывать на конец записи, которая ещё применяется. Для сравнения с уже применённой позицией используйте `last_replayed_end_lsn`. Пустой результат из `pg_stat_recovery` возможен вне recovery или при недостатке прав. [WAL receiver](https://www.postgresql.org/docs/19/monitoring-stats.html#MONITORING-PG-STAT-WAL-RECEIVER), [статистика recovery](https://www.postgresql.org/docs/19/monitoring-stats.html#MONITORING-PG-STAT-RECOVERY).

**Настройка на `primary`:**

```ini
# primary: postgresql.conf
wal_level = replica
max_wal_senders = 5
```

**Настройка на `standby`:**

```ini
# PostgreSQL 12+: postgresql.conf; в data directory нужен standby.signal
primary_conninfo = 'host=primary-host port=5432 user=replication_user'
```

`recovery.conf` удалён в PostgreSQL 12: при его наличии сервер не стартует. Если используется физический слот, задают также `primary_slot_name` на standby. Для синхронного подтверждения на primary отдельно настраивают `synchronous_standby_names`. При `hot_standby=on` реплика после достижения согласованного состояния принимает read-only запросы; их результат может отставать от primary. [Recovery configuration](https://www.postgresql.org/docs/18/recovery-config.html), [Hot Standby](https://www.postgresql.org/docs/18/hot-standby.html).
**Плановая остановка отправителя WAL.** В PostgreSQL 19 параметр `wal_sender_shutdown_timeout` ограничивает ожидание, пока получатель догонит отправителя при остановке сервера. По умолчанию `-1` отключает лимит, `0` пропускает ожидание, а положительное значение задаёт его предел. Например, при `10s` медленный получатель может остаться позади после остановки. Перед повышением физической standby проверьте, что она применила WAL до контрольного LSN переключения. Сам факт остановки primary при заданном лимите этого не гарантирует. [Параметры репликации PostgreSQL 19](https://www.postgresql.org/docs/19/runtime-config-replication.html#GUC-WAL-SENDER-SHUTDOWN-TIMEOUT).

## Q45. В чём разница между физической и логической репликацией?

Разница в **уровне абстракции, что передаётся**. Физическая репликация воспроизводит низкоуровневые изменения через `WAL` — получается копия всего кластера. Логическая передаёт изменения выбранных таблиц как операции `INSERT`/`UPDATE`/`DELETE`, а также `TRUNCATE` для таблицы целиком — то есть «что произошло» вместо «какие байты поменялись».

Физическая схема воспроизводит кластер целиком и требует совместимого двоичного формата, обычно одной основной версии PostgreSQL. Логическая допускает выбор публикаций и миграцию между совместимыми версиями, но требует проверки схемы и поведения конкретных типов данных; она не даёт побайтового дубля. [Logical Replication](https://www.postgresql.org/docs/18/logical-replication.html).

| Характеристика | Физическая репликация | Логическая репликация |
|---------------|----------------------|----------------------|
| Единица | Низкоуровневые записи `WAL` | Операции над выбранными таблицами, включая `TRUNCATE` |
| Версия PostgreSQL | Совместимая двоичная версия, обычно та же основная | Возможна работа между версиями после проверки совместимости |
| Платформа | Совместимый формат данных | Не требуется побайтовая совместимость |
| Избирательность | Весь кластер | Таблицы, выбранные публикацией, и последовательности в PostgreSQL 19 |
| Применение | DR, read-реплики | Миграции, публикация изменений, CDC |

**Требования к издателю.** В PostgreSQL 18 для логической репликации в конфигурации нужен `wal_level = logical`. В PostgreSQL 19 достаточно `replica` или `logical`. При `replica` первый логический слот включает нужную детализацию WAL без перезапуска (см. Q3). Для подписки по-прежнему нужны свободные слоты и процессы отправки WAL на издателе. При расчёте лимитов учитывайте начальную синхронизацию таблиц и одновременные подключения физических реплик. [Настройки издателя PostgreSQL 18](https://www.postgresql.org/docs/18/logical-replication-config.html#LOGICAL-REPLICATION-CONFIG-PUBLISHER), [настройки издателя PostgreSQL 19](https://www.postgresql.org/docs/19/logical-replication-config.html#LOGICAL-REPLICATION-CONFIG-PUBLISHER).

**Логическая репликация** (PostgreSQL 10+): publisher создаёт `Publication`, subscriber — `Subscription`. Публикация может выбирать типы операций, в том числе `TRUNCATE`; по умолчанию включены все четыре. Таблицы на subscriber создают заранее: схема и DDL не реплицируются. Обычный `CREATE SUBSCRIPTION` сам создаёт логический слот у publisher; ручной вызов `pg_create_logical_replication_slot` для этого сценария не нужен. [Publication](https://www.postgresql.org/docs/18/logical-replication-publication.html), [Subscription](https://www.postgresql.org/docs/18/logical-replication-subscription.html), [Restrictions](https://www.postgresql.org/docs/18/logical-replication-restrictions.html).

Для передачи `UPDATE` и `DELETE` publisher должен знать, как найти ту же строку на subscriber: это задаёт `REPLICA IDENTITY` опубликованной таблицы. По умолчанию используется первичный ключ. Если его нет и оставлено `DEFAULT`, попытка такого изменения завершится ошибкой на publisher; `INSERT` при этом возможен. Можно выбрать подходящий уникальный индекс или `REPLICA IDENTITY FULL`, но поиск строки по всей записи может быть дорогим. Поэтому при настройке публикации проверьте ключи и схему таблиц на обеих сторонах. [Replica Identity](https://www.postgresql.org/docs/18/logical-replication-publication.html#LOGICAL-REPLICATION-REPLICA-IDENTITY).

```sql
-- На primary
CREATE PUBLICATION my_pub FOR TABLE orders, users;

-- На subscriber (таблицы уже созданы)
CREATE SUBSCRIPTION my_sub
CONNECTION 'host=primary dbname=mydb user=repuser'
PUBLICATION my_pub;
```

**Генерируемые столбцы.** С PostgreSQL 18 можно передавать значения столбцов `GENERATED … STORED` через `publish_generated_columns = stored` или явный список столбцов таблицы. Список имеет приоритет над настройкой публикации. По умолчанию эти значения не передаются, а виртуальные столбцы опубликовать нельзя.

Например, если `orders.total_cents` вычисляется на издателе, подписчик может пересчитывать его по своему выражению. Для этого оставьте столбец генерируемым на подписчике и исключите его из публикации. Если нужно сохранить именно рассчитанное издателем значение, включите столбец в публикацию и создайте на подписчике обычный `total_cents` совместимого типа. Применение передаваемого значения к генерируемому столбцу на подписчике завершится ошибкой. При миграции проверьте и начальную копию: подписчик младше PostgreSQL 18 не скопирует значения генерируемых столбцов на этом этапе. [PostgreSQL 18](https://www.postgresql.org/docs/18/logical-replication-gencols.html), [PostgreSQL 19](https://www.postgresql.org/docs/19/logical-replication-gencols.html).

**Последовательности при переключении записи.** Если PostgreSQL 18 переносит строки с явно записанными ID, локальная последовательность на subscriber может отстать. Перед приёмом записей её состояние нужно согласовать отдельно. В PostgreSQL 19 последовательности можно включить в публикацию через `FOR ALL SEQUENCES`. На subscriber с заранее созданными совместимыми последовательностями `copy_data = true` запускает первичную синхронизацию. Каждый следующий `nextval()` на publisher не передаётся непрерывно. Перед плановым переключением остановите записи на старом узле, дождитесь применения изменений строк, выполните `ALTER SUBSCRIPTION my_sub REFRESH SEQUENCES` для известных подписке последовательностей и проверьте, что фоновая синхронизация завершилась. Если последовательности добавили позже, сначала обновите состав подписки через `REFRESH PUBLICATION`. [PostgreSQL 19 — Replicating Sequences](https://www.postgresql.org/docs/19/logical-replication-sequences.html).

**Проверка перед открытием записи на subscriber.** Для конкретной последовательности сравните `pg_subscription_rel.srsublsn` на subscriber с `page_lsn` из `pg_get_sequence_data()` на publisher. Если LSN на publisher продвинулся, subscriber ещё не отражает это изменение. Совпадение LSN тоже требует проверки: несколько вызовов `nextval()` могут изменить состояние последовательности внутри одного блока значений, пока новый WAL для её страницы ещё не записан. В плановом переключении после остановки выдачи значений на старом узле выполните итоговый `REFRESH SEQUENCES`, дождитесь завершения фоновой работы и сверьте `last_value` и `is_called` на обеих сторонах. Если состояния расходятся, проверьте определения последовательностей и журнал рабочего процесса до открытия записи.

Это переключение роли **логического subscriber**. При повышении **физической standby издателя** и переподключении прежнего логического subscriber проверяется готовность слотов (Q46). Готовый слот позволяет продолжить поток изменений, а готовность subscriber принимать собственные записи требует отдельной проверки последовательностей. [Синхронизация последовательностей в PostgreSQL 19](https://www.postgresql.org/docs/19/logical-replication-sequences.html#LOGICAL-REPLICATION-REFRESHING-SEQUENCES).


**Как диагностировать сбой синхронизации.** На subscriber проверьте `pg_stat_subscription` для активных рабочих процессов и `pg_stat_subscription_stats` для накопленных ошибок. В PostgreSQL 19 счётчик начальной синхронизации таблиц переименован из `sync_error_count` в `sync_table_error_count`. Ошибки фоновой синхронизации последовательностей учитываются отдельно в `sync_seq_error_count`, а ошибки применения изменений — в `apply_error_count`.

Если после `REFRESH SEQUENCES` вырос `sync_seq_error_count`, откройте журнал subscriber и проверьте состояние конкретных последовательностей перед переключением записи. Одна прибавка счётчика может относиться к нескольким последовательностям. Для сравнения двух замеров проверьте, что между ними не менялся `stats_reset`. [PostgreSQL 19: статистика подписки](https://www.postgresql.org/docs/19/monitoring-stats.html#MONITORING-PG-STAT-SUBSCRIPTION-STATS).

## Q46. Что такое `replication slot` и зачем он нужен?

**`Replication slot`** хранит позицию потребителя и удерживает на publisher нужные ему сегменты `WAL`, чтобы отставшая физическая standby или логический подписчик могли продолжить чтение. Это не абсолютная гарантия сохранения WAL: при заданном `max_slot_wal_keep_size` нужные сегменты могут быть удалены на checkpoint, и слот станет непригодным. Без лимита (значение `-1` по умолчанию) заброшенный слот способен заполнить диск. [Replication configuration](https://www.postgresql.org/docs/18/runtime-config-replication.html), [pg_replication_slots](https://www.postgresql.org/docs/18/view-pg-replication-slots.html).

```sql
-- Посмотреть слоты
SELECT * FROM pg_replication_slots;

-- Создать физический слот
SELECT pg_create_physical_replication_slot('standby1_slot', true);

-- Явное создание логического слота нужно лишь при ручном управлении;
-- обычный CREATE SUBSCRIPTION создаст его сам
SELECT pg_create_logical_replication_slot('my_slot', 'pgoutput');
```

Параметр `true` у `pg_create_physical_replication_slot` резервирует WAL сразу; без него резервирование начинается при первом подключении streaming-клиента. На standby указывают `primary_slot_name = 'standby1_slot'`, иначе созданный физический слот не будет использоваться. [Replication functions](https://www.postgresql.org/docs/18/functions-admin.html).

**Мониторинг:** проверяйте не только разницу LSN, но и `active`, `wal_status`, `safe_wal_size`. Разница LSN — оценка объёма WAL от старейшей нужной позиции, а не задержка применения на реплике в секундах. При `wal_status='unreserved'` слот уже не обеспечивает удержание нужного WAL, и часть файлов может быть удалена на следующем checkpoint. Состояние ещё может измениться обратно, пока файлы доступны. При `wal_status='lost'` продолжить репликацию через этот слот уже нельзя. `safe_wal_size` показывает, сколько ещё байт WAL можно записать до риска потери слота. Значение `NULL` бывает как у потерянного слота, так и при отключённом лимите, поэтому смотрите на оба поля. Причину недействительности показывает `invalidation_reason`.

В PostgreSQL 18 и 19 можно независимо задать `idle_replication_slot_timeout`. При ненулевом значении сервер на checkpoint может признать неактивный слот недействительным даже без превышения лимита WAL. Таймаут не применяется к слотам, которые не резервируют WAL, и к синхронизируемым слотам на standby. [Настройки репликации PostgreSQL 18](https://www.postgresql.org/docs/18/runtime-config-replication.html), [настройки PostgreSQL 19](https://www.postgresql.org/docs/19/runtime-config-replication.html), [pg_replication_slots](https://www.postgresql.org/docs/18/view-pg-replication-slots.html).

```sql
SELECT slot_name, slot_type, active, wal_status, safe_wal_size, invalidation_reason,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal_estimate
FROM pg_replication_slots;
```

**Переключение логического подписчика на новый primary** требует подготовки (PostgreSQL 17+). У подписки задают `failover = true`. На физической standby включают `sync_replication_slots = true` и `hot_standby_feedback = on`, задают `primary_slot_name` для связи через физический слот и указывают действительный `dbname` в `primary_conninfo`. Синхронизации нужны WAL и версии строк системных каталогов, которые требуются для декодирования. Если нужные данные уже удалены на standby, слот не станет постоянным.

На primary рекомендуют добавить этот физический слот в `synchronized_standby_slots`. Тогда отправитель логических изменений ждёт, пока каждая указанная физическая standby подтвердит сброс нужного WAL на диск. Это защищает от ситуации, когда подписчик уже получил изменения, до которых кандидат на переключение ещё не дошёл. При отставании standby растёт задержка подписчика. Если указанный физический слот отсутствует или стал недействительным, логическая передача останавливается. [Настройки репликации PostgreSQL 19](https://www.postgresql.org/docs/19/runtime-config-replication.html#GUC-SYNCHRONIZED-STANDBY-SLOTS). Эта настройка регулирует выдачу изменений логическим потребителям. Гарантии для подтверждённых транзакций приложения определяет конфигурация физической репликации (Q44).

Перед переключением соберите имена слотов подписок с включённым failover. Для подписчика PostgreSQL дополнительно проверьте слоты синхронизации таблиц, копирование которых завершилось и ещё ожидает окончания синхронизации (`pg_subscription_rel.srsubstate = 'f'`). Слоты для остальных состояний процедура не требует: их удалят или создадут заново на новом primary. На выбранной standby для каждого нужного слота должны выполняться `synced = true`, `temporary = false` и `invalidation_reason IS NULL`. Синхронизация асинхронна, поэтому наличие слота ещё не подтверждает его готовность. При плановом переключении остановите подписки перед повышением standby, переведите подключения на новый primary и включите подписки снова. Так подписчики не продолжат чтение со старого primary, если тот остаётся доступным. [Logical Replication Failover](https://www.postgresql.org/docs/19/logical-replication-failover.html), [Replication Slot Synchronization](https://www.postgresql.org/docs/19/logicaldecoding-explanation.html#LOGICALDECODING-REPLICATION-SLOTS-SYNCHRONIZATION).

**Диагностика перед переключением в PostgreSQL 19.** Если нужный слот есть на standby, но ещё не готов, проверьте `pg_replication_slots.slotsync_skip_reason`. Например, `wal_not_flushed` означает, что standby на момент попытки ещё не сбросила WAL на диск до позиции, зарезервированной failover-слотом. В `pg_stat_replication_slots` поля `slotsync_skip_count` и `slotsync_last_skip` показывают число пропусков с момента сброса статистики и время последнего пропуска. Сравните их в свежих выборках, чтобы отличить единичный пропуск от повторяющейся проблемы. После устранения причины повторите проверку готовности всех нужных слотов. Нулевой счётчик сам по себе готовность не подтверждает. Диагностические поля о пропусках применимы на standby. [Состояние слотов](https://www.postgresql.org/docs/19/view-pg-replication-slots.html), [статистика слотов](https://www.postgresql.org/docs/19/monitoring-stats.html#MONITORING-PG-STAT-REPLICATION-SLOTS), [проверка готовности](https://www.postgresql.org/docs/19/logical-replication-failover.html).

В PostgreSQL 18.6 для logical decoding plugins появился список разрешённых библиотек `output_plugin_libraries`. По умолчанию в нём `pgoutput` и `test_decoding`; при обновлении установки с собственным плагином проверьте этот параметр до возобновления потребителя изменений. При `pg_upgrade` с кластера PostgreSQL 17+ проверьте список до `pg_upgrade --check`. [PostgreSQL 18.6 Release Notes](https://www.postgresql.org/docs/18/release-18-6.html).

## Q47. Как работает `full-text search` в PostgreSQL?

PostgreSQL поддерживает полнотекстовый поиск без внешнего поискового движка. `tsvector` хранит разобранный на лексемы документ, `tsquery` описывает условие поиска, а `@@` проверяет совпадение. Разбор, удаление стоп-слов и нормализация зависят от конфигурации поиска; это не сравнение буквальных подстрок.

**Конфигурация должна совпадать** при подготовке документа и запроса. Например, `'russian'` задаёт правила для русского текста. `to_tsquery` принимает синтаксис `tsquery` (`&`, `|`, `!`), поэтому сырую пользовательскую строку обычно передают в `websearch_to_tsquery` или `plainto_tsquery`.

```sql
-- TSVECTOR: нормализованный вектор слов
SELECT to_tsvector('russian', 'Быстрая коричневая лиса прыгает');

-- TSQUERY: запрос
SELECT to_tsquery('russian', 'лиса & прыгает');

-- Поисковая строка пользователя: без требования писать синтаксис tsquery
SELECT websearch_to_tsquery('russian', 'лиса or волк');

-- Поиск
SELECT title FROM articles
WHERE to_tsvector('russian', body) @@ to_tsquery('russian', 'postgresql & индексы');

-- Ранжирование результатов
SELECT title, ts_rank(to_tsvector('russian', body), search.q) AS rank
FROM articles
CROSS JOIN (SELECT to_tsquery('russian', 'postgresql') AS q) search
WHERE to_tsvector('russian', body) @@ search.q
ORDER BY rank DESC;
```

**Поиск фразы отличается от поиска всех слов.** `plainto_tsquery('russian', 'база данных')` соединяет лексемы через `&`: их порядок не важен. `phraseto_tsquery` соединяет их оператором следования `<->` и учитывает расстояние через стоп-слова. `websearch_to_tsquery` также понимает фразу в кавычках, но не синтаксис `tsquery` вроде `:*` для префикса. Это поиск нормализованных лексем по позициям, а не буквального фрагмента строки:

```sql
SELECT title FROM articles
WHERE to_tsvector('russian', body) @@ phraseto_tsquery('russian', 'база данных');
```

GIN хранит лексемы, а не их позиции или готовый ранг: для проверки фразы нужно обратиться к самому `tsvector`, а сортировку по релевантности вычислить отдельно. [Управление полнотекстовым поиском](https://www.postgresql.org/docs/18/textsearch-controls.html), [индексы полнотекстового поиска](https://www.postgresql.org/docs/18/textsearch-indexes.html).

**Индексирование:** для частого поиска создают `GIN`-индекс на выражении `to_tsvector` с явной конфигурацией или на сохранённом генерируемом столбце. Индекс может ускорить отбор документов, но его наличие не гарантирует индексный план и не избавляет от расчёта ранга. При объединении полей нужен `coalesce`, иначе `NULL` в одном из них обнулит всё выражение:

```sql
ALTER TABLE articles ADD COLUMN tsv TSVECTOR
    GENERATED ALWAYS AS (to_tsvector('russian', coalesce(title, '') || ' ' || coalesce(body, ''))) STORED;

CREATE INDEX idx_articles_tsv ON articles USING GIN (tsv);

SELECT title FROM articles
WHERE tsv @@ websearch_to_tsquery('russian', 'postgresql индексы');
```

Для небольшой таблицы или редких запросов индекс может не окупиться. `ts_rank` и `ts_rank_cd` помогают упорядочить найденные документы по релевантности, но итоговый порядок задаёт `ORDER BY`. Источники: [обработка текста](https://www.postgresql.org/docs/18/textsearch-intro.html), [таблицы и индексы](https://www.postgresql.org/docs/18/textsearch-tables.html), [ввод запроса и ранжирование](https://www.postgresql.org/docs/18/textsearch-controls.html), [типы индексов](https://www.postgresql.org/docs/18/textsearch-indexes.html).


**Обновление до PostgreSQL 19.** Полнотекстовый парсер и `pg_trgm` теперь классифицируют символы через провайдер локали базы. В PostgreSQL 18 для этого использовалась libc. Если база использует ICU или встроенный провайдер и его правила отличаются от правил прежнего `LC_CTYPE`, разбор текста и результаты поиска могут измениться. Для такой базы после `pg_upgrade` документация рекомендует пересчитать сохранённые `tsvector` и перестроить индексы полнотекстового поиска и `pg_trgm`.

В примере выше `REINDEX` индекса на `tsv` читает уже записанные в столбце векторы. Чтобы получить новые лексемы, сначала пересчитайте данные столбца, например обновлением исходных полей строк. Предусмотрите объём записи и WAL при таком обновлении. У индекса на выражении `to_tsvector(...)` отдельного сохранённого столбца нет, поэтому при построении индекса выражение вычисляется по исходному тексту. Проверьте на копии базы запросы с не-ASCII символами, которые реально встречаются в ваших данных. [PostgreSQL 19 — изменения при обновлении](https://www.postgresql.org/docs/19/release-19.html), [таблицы и индексы FTS](https://www.postgresql.org/docs/19/textsearch-tables.html).

## Q48. (!) Какие операторы и функции доступны для `JSONB`?

Операторы `JSONB` делятся на две группы, и их легко перепутать на собеседовании: одни **извлекают** данные, другие **ищут/фильтруют**.

**Операторы доступа (извлечение).** Одинарная стрелка (`->`, `#>`) сохраняет тип входа: из столбца `jsonb` возвращает `jsonb`, из `json` — `json`. Двойная (`->>`, `#>>`) возвращает `text`. Отсутствующий ключ даёт SQL `NULL`, поэтому его нужно отличать от значения JSON `null`:

| Оператор | Описание | Пример |
|----------|---------|--------|
| `->` | Получить поле как `jsonb` из `jsonb` | `payload->'name'` |
| `->>` | Получить поле как `TEXT` | `payload->>'name'` |
| `#>` | Путь как `jsonb` из `jsonb` | `payload#>'{address,city}'` |
| `#>>` | Путь как `TEXT` | `payload#>>'{address,city}'` |

**Операторы поиска (фильтрация).** `@>` проверяет вложенное содержание, а `?`, `?|`, `?&` ищут ключ или элемент массива только на верхнем уровне переданного значения. `@?` и `@@` проверяют `jsonpath` по разным правилам. Возможность использовать индекс зависит от выражения слева и класса операторов `GIN`:

| Оператор | Описание |
|----------|---------|
| `@>` | Содержит (правый в левом) |
| `<@` | Содержится (левый в правом) |
| `?` | Ключ объекта или строковый элемент массива существует на верхнем уровне |
| `?\|` | Хотя бы один ключ/элемент из `text[]` существует на верхнем уровне |
| `?&` | Все ключи/элементы из `text[]` существуют на верхнем уровне |
| `@?` / `@@` | Поиск элементов / проверка предиката по `jsonpath` |

```sql
-- Поиск по вложенному полю
SELECT * FROM events WHERE payload @> '{"event_type": "purchase"}';

-- Проверка существования ключа
SELECT * FROM events WHERE payload ? 'discount_code';

-- Вложенный ключ: оператор ? применён к извлечённому объекту
SELECT * FROM events WHERE payload->'user' ? 'name';

-- Модификация JSONB
UPDATE events
SET payload = payload || '{"processed": true}'
WHERE id = 1;

-- Удаление ключа
UPDATE events SET payload = payload - 'temp_field' WHERE id = 1;

-- jsonb_set: обновить вложенное поле
UPDATE events
SET payload = jsonb_set(payload, '{user,name}', '"Alice"')
WHERE id = 1;
```

**Отсутствующий ключ и JSON `null` различаются.** `payload->'status' IS NULL` истинно при отсутствии ключа, неподходящей структуре или SQL `NULL` в самом `payload`, но не при значении JSON `null`: оно остаётся значением `jsonb`. `payload->>'status' IS NULL` даст истину и для отсутствующего ключа, и для JSON `null`. Если нужно различить состояния, сочетайте `payload ? 'status'` и `jsonb_typeof(payload->'status')`: для JSON `null` функция возвращает текст `'null'`, для отсутствующего ключа — SQL `NULL`.

```sql
SELECT payload ? 'status' AS key_exists,
       jsonb_typeof(payload->'status') AS value_type
FROM events;
```

Для вложенного поиска `@?` отвечает, вернул ли путь хотя бы один элемент, а `@@` проверяет результат предиката `jsonpath`. Предикатный путь не стоит передавать в `@?`: даже `false` остаётся возвращённым элементом. Напротив, `@@` для пути без единственного логического результата может вернуть SQL `NULL`:

```sql
SELECT '{"a":[1,2,3]}'::jsonb @? '$.a[*] ? (@ > 2)';
SELECT '{"a":[1,2,3]}'::jsonb @@ '$.a[*] > 2';
```

Оба оператора подавляют часть ошибок несоответствия структуры документа пути, поэтому отсутствие поля не обязано приводить к ошибке. [JSON-функции и операторы](https://www.postgresql.org/docs/18/functions-json.html).

Стандартный `GIN (payload)` с `jsonb_ops` поддерживает `@>`, `?`, `?|`, `?&`, `@?`, `@@`, но не любое выражение с `payload`: для `payload->'user' ? 'name'` нужен подходящий индекс по выражению. `jsonb_path_ops` поддерживает `@>`, `@?`, `@@`, но не проверку существования ключа; `payload->>'event_type' = 'purchase'` можно ускорить отдельным B-tree индексом по выражению (см. Q17). Оператор `||` объединяет только верхний уровень объектов/массивов, без рекурсивного слияния. Источники: [JSON-функции и операторы](https://www.postgresql.org/docs/18/functions-json.html), [индексирование `jsonb`](https://www.postgresql.org/docs/18/datatype-json.html#JSON-INDEXING).

## Q49. (!) Что такое `PgBouncer` и зачем он нужен?

**`PgBouncer`** — отдельный пул соединений между клиентами и PostgreSQL. Каждый прямой клиентский сеанс PostgreSQL обслуживает серверный процесс. PgBouncer позволяет нескольким клиентским соединениям по очереди использовать меньшее число серверных соединений, снижая затраты на их открытие и удержание. Экономия зависит от нагрузки и выбранного режима пулинга.

**Когда помогает:** много клиентов держат подключения, но одновременно выполняют сравнительно мало запросов. Тогда ограниченный серверный пул уменьшает число процессов PostgreSQL. Если все серверные соединения заняты, остальные клиенты ждут свободное; пул не увеличивает вычислительную мощность базы и требует настройки очереди и лимитов.

Приложение подключается к порту PgBouncer как к PostgreSQL. Его собственный пул соединений при этом не исчезает: суммарные лимиты всех экземпляров приложения и PgBouncer нужно согласовать. `max_client_conn` ограничивает клиентские подключения к экземпляру PgBouncer, а `default_pool_size` — число серверных соединений **на пару пользователь/база**, если нет переопределения. Это не общий лимит всех серверных соединений.

PgBouncer **сам аутентифицирует клиентов** по своим `auth_type` и `auth_file` либо `auth_user`/`auth_query`; файл `pg_hba.conf` PostgreSQL не заменяет эту проверку. Затем PgBouncer устанавливает или переиспользует серверное соединение, для которого действуют правила PostgreSQL. Поэтому отказ на стороне PgBouncer и отказ при соединении с PostgreSQL разбирают отдельно. [PgBouncer Authentication Settings](https://www.pgbouncer.org/config.html#authentication-settings), [PostgreSQL `pg_hba.conf`](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html).

```ini
# pgbouncer.ini
[databases]
mydb = host=localhost port=5432 dbname=mydb

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
```

В этом примере `transaction` указан явно: режим PgBouncer по умолчанию — `session`; настройки аутентификации в фрагменте опущены. Числа 1000 и 20 иллюстрируют разные лимиты, а не обещают, что одновременно выполнятся 1000 запросов через 20 серверных соединений. Для проверки нагрузки смотрят `SHOW POOLS`: `cl_waiting` показывает число клиентов без серверного соединения, `maxwait` — ожидание самого старого из них. Источники: [PgBouncer Usage](https://www.pgbouncer.org/usage.html), [Configuration](https://www.pgbouncer.org/config.html).

## Q50. Какие режимы пулинга поддерживает `PgBouncer`?

Режимы отличаются тем, **как часто реальное соединение возвращается в пул** — а значит, насколько агрессивно оно переиспользуется. Чем агрессивнее, тем выше экономия, но тем больше ограничений на то, что можно держать «привязанным» к соединению:

| Режим | Описание | Ограничения |
|-------|---------|------------|
| `session` | Серверное соединение закреплено до отключения клиента; режим по умолчанию | Сессионные возможности PostgreSQL доступны, но переиспользование между активными клиентами ограничено |
| `transaction` | Серверное соединение возвращается после завершения транзакции | Нельзя рассчитывать на произвольное состояние серверной сессии между транзакциями |
| `statement` | Серверное соединение возвращается после запроса | Многооператорные транзакции запрещены |

**Граница совместимости `transaction`:** `LISTEN`, обычный SQL `PREPARE`/`DEALLOCATE`, удерживаемые курсоры и session-level advisory locks требуют привязки к сеансу и несовместимы с переиспользованием сервера между транзакциями. Протокольные именованные prepared statements — другой механизм: PgBouncer поддерживает их начиная с версии 1.21 при ненулевом `max_prepared_statements` (в 1.26.1 значение по умолчанию — 200). PgBouncer отслеживает имена таких запросов и при необходимости заново подготавливает запрос на выделенном серверном соединении. Обычные SQL-команды `PREPARE`, `EXECUTE` и `DEALLOCATE имя` он передаёт PostgreSQL напрямую. Исключения — `DEALLOCATE ALL` и `DISCARD ALL`: они очищают и подготовленные запросы, которые PgBouncer отслеживает для этого клиента. При проверке драйвера выясните, использует ли он именованные запросы на уровне протокола. [Настройка max_prepared_statements](https://www.pgbouncer.org/config.html#max_prepared_statements).

Не следует считать, что произвольный `SET` сохранится для клиента после смены серверного соединения. PgBouncer отслеживает некоторые параметры, передаваемые PostgreSQL через протокол. Начиная с PostgreSQL 18 сервер сообщает `search_path`, и PgBouncer 1.26 отслеживает его по умолчанию. На PostgreSQL до 18 PgBouncer может восстановить отслеживаемое значение `search_path` из параметров подключения, но сервер не сообщает об изменениях через `SET` после подключения. При переиспользовании соединения такое изменение может затронуть другого клиента. Начиная с PgBouncer 1.26.1 настройка `ignore_startup_parameters = search_path` имеет приоритет и отключает отслеживание этого параметра. [Настройки PgBouncer](https://www.pgbouncer.org/config.html#track_extra_parameters). [Release notes PgBouncer 1.26.1](https://www.pgbouncer.org/changelog.html) отдельно сообщают о ещё не исправленных ошибках отслеживания `search_path`. Поэтому даже для пары PgBouncer 1.26.1/PostgreSQL 18 проверяйте сценарий смены серверного соединения в приложении, не считая поддержку безусловной.

**Выбор режима:** начинайте с требований клиента. `session` сохраняет привычную семантику PostgreSQL; `transaction` даёт более частое переиспользование, если приложение не зависит от серверного состояния между транзакциями; `statement` подходит лишь при допустимости отдельных autocommit-запросов. Проверяйте реальные функции ORM/драйвера и поведение приложения, прежде чем менять `pool_mode`. Источники: [PgBouncer Features](https://www.pgbouncer.org/features.html), [Configuration](https://www.pgbouncer.org/config.html), [FAQ о prepared statements](https://www.pgbouncer.org/faq.html), [PgBouncer 1.26 changelog](https://www.pgbouncer.org/changelog.html).

## Q51. (!) Какие типы блокировок существуют в PostgreSQL?

Для прикладных запросов важнее всего различать **блокировки таблицы** и **блокировки строки**. Команды PostgreSQL обычно получают их автоматически; `LOCK TABLE` и `SELECT ... FOR ...` позволяют запросить блокировку явно. Есть также кратковременные блокировки страниц и advisory locks с заданным приложением смыслом. Предикатные блокировки при `SERIALIZABLE` решают другую задачу — обнаружение конфликтов сериализации.

**Блокировки таблиц (`table-level locks`)** регулируют совместный доступ к таблице. Названия `ROW SHARE` и `ROW EXCLUSIVE` относятся именно к табличным режимам, а не к блокировкам отдельных строк. Конфликт определяется парой режимов на одном объекте. Обычный `SELECT` берёт `ACCESS SHARE`, а `DROP TABLE` — `ACCESS EXCLUSIVE`, который конфликтует со всеми режимами. Разные формы `ALTER TABLE` запрашивают разные режимы; нельзя считать всякий `ALTER` блокировкой `ACCESS EXCLUSIVE`.

| Режим на таблице | Типичный источник | Существенные конфликты |
|------------------|------------------|-----------------------|
| `ACCESS SHARE` | Обычный `SELECT` | Только `ACCESS EXCLUSIVE` |
| `ROW SHARE` | `SELECT ... FOR UPDATE/SHARE` | `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE`, `MERGE` | `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM` без `FULL`, `ANALYZE`, `CREATE INDEX CONCURRENTLY` | Сам с собой, `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `SHARE` | `CREATE INDEX` без `CONCURRENTLY` | `ROW EXCLUSIVE`, `SHARE UPDATE EXCLUSIVE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `SHARE ROW EXCLUSIVE` | `CREATE TRIGGER`, некоторые `ALTER TABLE` | `ROW EXCLUSIVE`, `SHARE UPDATE EXCLUSIVE`, `SHARE`, сам с собой, `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `EXCLUSIVE` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` | Все, кроме `ACCESS SHARE` |
| `ACCESS EXCLUSIVE` | `DROP TABLE`, `TRUNCATE`, `VACUUM FULL` | Все режимы, включая себя |

**Блокировки строк (`row-level locks`)** возникают при изменении строк и при `SELECT ... FOR ...`. Их режимы различаются тем, какие другие изменения и захваты той же строки они задерживают:
- `FOR UPDATE` конфликтует со всеми четырьмя строковыми режимами; его получает `DELETE` и некоторые `UPDATE` ключевых столбцов.
- `FOR NO KEY UPDATE` не конфликтует с `FOR KEY SHARE`; его обычно получает `UPDATE` без изменения ключа.
- `FOR SHARE` допускает другие `FOR SHARE` и `FOR KEY SHARE`, но задерживает изменение строки.
- `FOR KEY SHARE` не даёт удалить строку или изменить ключ, но допускает `FOR NO KEY UPDATE`. Например, пока одна транзакция держит `FOR KEY SHARE` на строке заказа, другая может изменить поле комментария, если оно не относится к ключу. Удаление той же строки будет ждать. [Строковые блокировки PostgreSQL 19](https://www.postgresql.org/docs/19/explicit-locking.html#LOCKING-ROWS).

Строковые блокировки не мешают обычному `SELECT` без `FOR ...`: благодаря MVCC он читает доступную ему версию строки. Табличный `ACCESS EXCLUSIVE` при этом блокирует и такой `SELECT`. Блокировки, полученные после `SAVEPOINT`, снимаются при откате к нему; обычно они держатся до конца транзакции (см. Q30).

**Advisory locks** защищают ресурс, смысл которого задаёт приложение, а не строку таблицы. PostgreSQL не заставляет другие запросы соблюдать такой захват. `pg_advisory_xact_lock(key)` освобождается в конце транзакции, в том числе при откате; отдельной функции разблокировки для него нет. `pg_advisory_lock(key)` держится до парного `pg_advisory_unlock(key)` или конца сеанса и **переживает `ROLLBACK`**. Поэтому для краткой операции внутри транзакции обычно проще транзакционный вариант, а сеансовый требует явного контроля жизненного цикла соединения. [Advisory Locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS), [Advisory Lock Functions](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).

```sql
-- Найти ожидающие процессы и их блокирующие PID
SELECT a.pid, a.query, pg_blocking_pids(a.pid) AS blocking_pids
FROM pg_stat_activity AS a
WHERE a.wait_event_type = 'Lock';
```

`pg_locks` показывает удерживаемые и ожидаемые блокировки, но ожидание блокировки строки часто видно как ожидание `transactionid`, а не как отдельная запись о строке. Для поиска блокирующей сессии удобнее `pg_blocking_pids()`: он может вернуть не только держателя конфликтующей блокировки, но и ожидающий процесс впереди в очереди. При блокировке подготовленной транзакцией в массиве может быть PID `0`; не считайте каждый PID активным держателем блокировки. Источники: [Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html), [Viewing Locks](https://www.postgresql.org/docs/18/monitoring-locks.html), [pg_blocking_pids](https://www.postgresql.org/docs/18/functions-info.html).

**Ёмкость таблицы блокировок после обновления до PostgreSQL 19.** Транзакция, обращающаяся к родительской таблице с большим числом секций, может удерживать блокировки на множестве объектов. `max_locks_per_transaction` задаёт ёмкость общей таблицы блокировок в расчёте на серверный процесс или подготовленную транзакцию. Одна транзакция может превысить это число, пока хватает места в общей таблице. Число заблокированных строк этот параметр не ограничивает.

В PostgreSQL 19 изменилось выделение памяти для блокировок, а значение по умолчанию выросло с 64 до 128. Если в PostgreSQL 18 было задано своё значение, для сопоставимой ёмкости при обновлении ориентируйтесь на удвоение этого значения. Проверьте операции с большим числом секций на тестовом сервере при обычной конкуренции. Параметр читается при старте сервера. На standby его значение должно быть не ниже, чем на primary. [Заметки о выпуске PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html), [Lock Management](https://www.postgresql.org/docs/19/runtime-config-locks.html#GUC-MAX-LOCKS-PER-TRANSACTION).

**Серверный журнал.** С PostgreSQL 19 `log_lock_waits` включён по умолчанию. Он записывает событие, если ожидание захвата блокировки превышает `deadlock_timeout`. После обновления проверьте фактическое значение через `SHOW log_lock_waits`: ранее заданное значение может отличаться от нового умолчания. Если ожидание уже закончилось, журнал помогает привязать эпизод ко времени, а `pg_stat_lock` показывает итог по типу блокировки за интервал между замерами. Сообщение об ожидании само по себе не означает взаимоблокировку. [PostgreSQL 19: журналирование ожиданий блокировок](https://www.postgresql.org/docs/19/runtime-config-logging.html#GUC-LOG-LOCK-WAITS).

**Накопленная статистика в PostgreSQL 19.** Если жалобы на задержку уже закончились, сравните два замера `pg_stat_lock`: рост `waits` и `wait_time` по `transactionid` покажет, что за интервал были длительные ожидания блокировок этого типа. Эти счётчики общие для кластера и растут только после успешного захвата блокировки, если ожидание превысило `deadlock_timeout`. `wait_time` измеряется в миллисекундах. Перед сравнением проверьте, что `stats_reset` не изменился.

```sql
SELECT locktype, waits, wait_time, stats_reset
FROM pg_stat_lock
WHERE locktype = 'transactionid';
```

По этим счётчикам нельзя восстановить конкретную пару сессий. Пока ожидание продолжается, ищите её запросом к `pg_stat_activity` и `pg_blocking_pids()` выше. [Статистика блокировок PostgreSQL 19](https://www.postgresql.org/docs/19/monitoring-stats.html#MONITORING-PG-STAT-LOCK).

## Q52. Что такое `deadlock` и как PostgreSQL его обнаруживает?

**`Deadlock`** (взаимоблокировка) — циклическое ожидание: транзакция A ждёт блокировку, которую держит B, а B ждёт ту, что держит A. Ни одна не отпустит своё и не дождётся чужого — без вмешательства они зависнут навсегда.

```
Транзакция A: держит блокировку строки 1, ждёт строку 2
Транзакция B: держит блокировку строки 2, ждёт строку 1
```

PostgreSQL обнаруживает взаимоблокировку после начала ожидания. После `deadlock_timeout` (по умолчанию `1s`) сервер проверяет граф ожиданий; проверять его при каждом ожидании было бы дорого. Если найден цикл, PostgreSQL прерывает **одну** транзакцию с SQLSTATE `40P01` (`deadlock_detected`), позволяя остальным продолжить. Какая именно транзакция станет жертвой, не гарантируется. Если операция допускает повтор, приложение начинает новую транзакцию и заново выполняет чтения, расчёты и записи, от которых зависит результат. У повтора должен быть предел. Внешний эффект, например уже отправленное уведомление, откатом БД не отменяется: его нужно вынести за границу повторяемой операции или обеспечить идемпотентность. [Повтор транзакций в PostgreSQL 19](https://www.postgresql.org/docs/19/mvcc-serialization-failure-handling.html).

`deadlock_timeout` — **момент запуска проверки, а не предел ожидания блокировки**. Если цикла нет, запрос может ждать дальше. `lock_timeout` отменяет оператор, когда отдельная попытка получить блокировку длится дольше заданного времени; `statement_timeout` ограничивает выполнение оператора в целом. Например, `lock_timeout`, установленный короче `deadlock_timeout`, может прервать ожидание до проверки цикла. Сам по себе тайм-аут не доказывает deadlock: при разборе отличайте его от `40P01` и выясняйте, кто удерживает ресурс. [Lock Management](https://www.postgresql.org/docs/18/runtime-config-locks.html), [Client Connection Defaults](https://www.postgresql.org/docs/18/runtime-config-client.html).

**Как предотвращать (это во многом задача приложения):**
- **Брать блокировки в едином порядке** во всех транзакциях — главное правило: если все блокируют строки в одинаковой последовательности, цикл невозможен.
- Если нужен явный захват, выбирать достаточный режим сразу, а не наращивать его позже.
- Держать транзакции короткими — чем меньше блокировок одновременно, тем ниже шанс пересечения.
- Для очередей задач можно использовать `SKIP LOCKED`; `NOWAIT` сразу сообщает о занятой строке. Это способы управлять ожиданием, а не общая защита от deadlock.

```sql
-- Попытка захватить блокировку без ожидания
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;

-- Пропустить заблокированные строки
SELECT * FROM jobs WHERE status = 'pending'
ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1;
```

`NOWAIT` и `SKIP LOCKED` относятся к строковым блокировкам: нужная команде табличная блокировка всё ещё может ожидать. `SKIP LOCKED` даёт неполный срез строк и подходит для конкурирующих потребителей очереди, но не для обычного чтения всех данных. Источники: [Deadlocks](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-DEADLOCKS), [deadlock_timeout](https://www.postgresql.org/docs/18/runtime-config-locks.html), [SELECT locking clause](https://www.postgresql.org/docs/18/sql-select.html), [SQLSTATE](https://www.postgresql.org/docs/18/errcodes-appendix.html).

## Q53. Какие ключевые параметры конфигурации влияют на производительность?

Настройку PostgreSQL начинают с симптома и измерений: ожидания I/O, временные файлы, ошибки оценок плана, конкуренция за соединения, checkpoints или задержка очистки таблиц требуют разных действий. Процент RAM или значение для «любого SSD» не является готовой настройкой. Некоторые параметры требуют перезапуска, поэтому изменение проверяют на своей нагрузке и планируют откат.

| Параметр | Что меняет и что проверить |
|----------|----------------------------|
| `shared_buffers` | Реально выделенный общий кэш. Для выделенного сервера с RAM от 1 GB документация предлагает 25% как начальную оценку, не как обязательную норму; учитывают также кэш ОС. |
| `effective_cache_size` | Только оценка доступного кэша для планировщика, без выделения памяти. Учитывают `shared_buffers`, кэш ОС и параллельные запросы. |
| `work_mem` и `hash_mem_multiplier` | Базовый предел на отдельную сортировку/хэш-операцию и дополнительный множитель для хэширования. Учитывают число операций и одновременных запросов. |
| `maintenance_work_mem`, `autovacuum_work_mem` | Память обслуживания; при нескольких процессах автоочистки суммарное потребление растёт (см. Q33). |
| `max_connections` | Предел серверных соединений; увеличение повышает затраты на общие ресурсы. Сверяют с пулами приложений и PgBouncer (Q49). |
| `random_page_cost` | Относительная цена случайного чтения в модели планировщика. Изменение может повлиять на выбор плана. |
| `effective_io_concurrency`, `io_max_concurrency` | Первый параметр влияет на число I/O-операций, которые сеанс пытается инициировать параллельно. Второй ограничивает число одновременных I/O-операций на процесс и задаётся при старте сервера. |
| `checkpoint_completion_target` | Растягивает checkpoint по интервалу; значение по умолчанию в PostgreSQL 18 — `0.9`, снижать его обычно не советуют. |
| `max_wal_size` | Мягкий предел объёма WAL между checkpoints. После значительного роста `shared_buffers` документация советует проверить, не требуется ли увеличить и этот предел; длинные checkpoints и репликационные слоты разбирают отдельно. |
| `log_min_duration_statement` | Порог записи завершённых SQL-операторов в лог. Выбирают по целям диагностики и допустимому объёму логов. |

**Сценарий обновления с PostgreSQL 18 до 19.** При `io_method = worker` в 18 число I/O-воркеров задаёт `io_workers`. В 19 этот параметр удалён. Размер пула меняется по нагрузке в пределах `io_min_workers` и `io_max_workers`. `io_worker_launch_interval` ограничивает частоту запуска новых воркеров, а `io_worker_idle_timeout` позволяет сократить пул после простоя.

Если в старой конфигурации задан `io_workers`, пересмотрите его до запуска 19. Проверьте на тестовом стенде те же запросы с чтением больших объёмов данных при сопоставимой нагрузке. Сравните задержку запросов и ожидания I/O. В `EXPLAIN (ANALYZE, BUFFERS, IO)` на PostgreSQL 19 проверьте, выполнялось ли асинхронное чтение в исследуемом плане (Q21). [PostgreSQL 18 — I/O](https://www.postgresql.org/docs/18/runtime-config-resource.html#RUNTIME-CONFIG-RESOURCE-IO), [заметки о выпуске PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html), [PostgreSQL 19 — I/O](https://www.postgresql.org/docs/19/runtime-config-resource.html#RUNTIME-CONFIG-RESOURCE-IO).

**JIT после обновления до PostgreSQL 19.** В 18 параметр `jit` по умолчанию включён, в 19 — выключен. Если после обновления замедлился длинный CPU-bound отчёт, проверьте `SHOW jit` и доступность JIT-провайдера. При включённом JIT решение о компиляции зависит от оценки стоимости плана и порога `jit_above_cost`. Пороги стоимости для JIT учитываются при построении плана. Если уже используется generic plan, изменение порогов влияет на решение о компиляции после перепланирования. При этом `SET jit = off` подавляет JIT и на этапе выполнения: следующий вызов может выполнить тот же закешированный план без компиляции. Чтобы сравнить обе настройки в одинаковых условиях, задайте их до подготовки и выполнения запроса в каждой серии замеров.

На тестовом стенде сравните несколько запусков отчёта с теми же параметрами при `jit = off` и `jit = on`. В `EXPLAIN (ANALYZE, BUFFERS)` проверьте секцию `JIT`, затраты на компиляцию и полное время выполнения. Компиляция может окупиться на долгом отчёте и увеличить задержку короткого запроса. [Заметки о выпуске PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html), [When to JIT?](https://www.postgresql.org/docs/19/jit-decision.html).

**Частая ошибка с `work_mem`:** это не общий лимит памяти сервера и не предел всего запроса. Один план может иметь несколько сортировок и хэш-узлов, а несколько сеансов выполняют их одновременно. Хэш-операция может использовать до `work_mem * hash_mem_multiplier`; превышение предела операции ведёт к временным файлам. Смотрите `Sort Method`, `Disk`, временные блоки в `EXPLAIN (ANALYZE, BUFFERS)` и реальную параллельность, прежде чем повышать значение. Для плохого плана сначала проверьте статистику и оценки строк (Q20–Q25), для bloat — autovacuum (Q31–Q33). Источники: [Resource Consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html), [Query Planning](https://www.postgresql.org/docs/18/runtime-config-query.html), [Connections](https://www.postgresql.org/docs/18/runtime-config-connection.html), [WAL checkpoints](https://www.postgresql.org/docs/18/runtime-config-wal.html).

## Q54. Как анализировать медленные запросы?

Сначала выясните, **какая нагрузка и когда замедлилась**: единичный долгий запрос, частый запрос с большим суммарным временем или ожидание блокировки требуют разных проверок. Затем разбирайте выбранный SQL с его параметрами и планом. Сравнивайте измерения до и после изменения.

**1. Логи завершённых запросов.** `log_min_duration_statement` фиксирует операторы, выполнившиеся не быстрее порога; он не показывает ещё выполняющийся запрос. Порог выбирают под нагрузку и объём логов:

```sql
-- postgresql.conf
log_min_duration_statement = '1s'  -- пример порога, не универсальная настройка
log_line_prefix = '%t [%p] %d %u '
```

**2. Суммарная нагрузка.** `pg_stat_statements` агрегирует статистику по запросам и помогает найти частый SQL с большим суммарным временем. Сначала добавьте модуль в `shared_preload_libraries` и перезапустите сервер; `compute_query_id` должен быть включён (`auto` или `on`). Модуль собирает статистику по всем базам экземпляра. В базе, из которой будете её читать, создайте расширение: оно добавляет представления и функции. Один `CREATE EXTENSION` без предварительной загрузки модуль не активирует:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Самые затратные группы запросов по времени выполнения
SELECT dbid, userid, queryid, toplevel, query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

Не сбрасывайте статистику в середине расследования: `pg_stat_statements_reset()` удаляет накопленные данные. Проверьте `stats_reset` и `dealloc` в `pg_stat_statements_info`: частое вытеснение записей делает рейтинг неполным. `query` — представитель группы нормализованных запросов, а не журнал каждого вызова с его значениями параметров или планом. При воспроизведении берите параметры проблемного случая отдельно; разные значения могут дать разные планы. `total_exec_time` и `mean_exec_time` относятся к выполнению, а учёт времени планирования требует `pg_stat_statements.track_planning = on` (по умолчанию `off`, включение может добавить заметные расходы). [pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html).

**3. Текущее ожидание.** `pg_stat_activity` показывает активные запросы и `wait_event_type`; при `Lock` ищите блокирующую сессию через `pg_blocking_pids()` (Q51). Время от `query_start` для неактивного сеанса не является длительностью выполняющегося запроса:

```sql
SELECT pid, query, wait_event_type, wait_event,
       clock_timestamp() - query_start AS running_for,
       pg_blocking_pids(pid) AS blockers
FROM pg_stat_activity
WHERE state = 'active'
ORDER BY running_for DESC;
```

**Ожидания буферов после обновления с PostgreSQL 18 на 19.** Значения `wait_event_type` и `wait_event` меняются парами. В 18 ожидание исключительного pin отображается как `BufferPin / BufferPin`. В 19 оно отображается как `Buffer / BufferCleanup`. Вместо прежнего `LWLock / BufferContent` версия 19 показывает тип `Buffer` и уточняет режим ожидания: `BufferShared`, `BufferShareExclusive` или `BufferExclusive`.

Если после обновления график по `BufferContent` опустел, сначала проверьте фильтр дашборда по обеим колонкам. Затем сравните доли новых событий по режимам. Эти события отражают ожидание доступа к общему буферу. По ним нельзя определить блокирующую транзакцию через `pg_blocking_pids()` или измерить время чтения с диска. Для сравнения версий храните исходные названия событий и при необходимости объединяйте три новых режима в одну категорию дашборда. [Ожидания PostgreSQL 18](https://www.postgresql.org/docs/18/monitoring-stats.html#WAIT-EVENT-TABLE), [Ожидания PostgreSQL 19](https://www.postgresql.org/docs/19/monitoring-stats.html#WAIT-EVENT-TABLE), [Заметки о выпуске PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html).

**Ожидания WAL в PostgreSQL 19.** Если приложение сообщает о медленных фиксациях, смотрите на пару `wait_event_type / wait_event`. `Timeout / CommitDelay` означает настроенную паузу перед сбросом WAL для групповой фиксации. `IPC / SyncRep` означает ожидание подтверждения синхронной реплики. Для ожидания конкретного LSN есть отдельные события типа `IPC`: `WaitForWalFlush` на первичном сервере или реплике, `WaitForWalWrite` и `WaitForWalReplay` на реплике. Например, если чтение задержалось на барьере `WAIT FOR LSN` и видно `WaitForWalReplay`, сопоставьте целевую позицию с прогрессом применения WAL, как в Q44. Текущее событие показывает, чего ждёт процесс в момент выборки. Длительность этапа проверяйте по серии наблюдений или отдельным метрикам. [События ожидания PostgreSQL 19](https://www.postgresql.org/docs/19/monitoring-stats.html#WAIT-EVENT-TABLE), [новые события PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html).

**4. План выбранного SQL.** Начните с обычного `EXPLAIN`, если повторное выполнение запроса дорого или у него есть побочные эффекты. `EXPLAIN (ANALYZE, BUFFERS)` выполняет оператор. Даже `SELECT` может вызвать функцию с побочным эффектом. Для проверки изменяющих запросов используйте подходящую среду: `ROLLBACK` отменяет транзакционные изменения, но не возвращает, например, значение, уже выданное `nextval()` (Q21).

Сравнивайте оценку строк с `actual rows` на один проход узла. Для оценки общего числа строк умножайте фактическое среднее на `loops`. `shared read` означает, что блока не было в общих буферах PostgreSQL. Его ещё мог отдать кеш ОС, поэтому счётчик сам по себе не измеряет обращения к диску. Для времени чтения и записи используйте показатели I/O при включённом `track_io_timing`. `Seq Scan` сам по себе не ошибка. [EXPLAIN в PostgreSQL 19](https://www.postgresql.org/docs/19/sql-explain.html), [функции последовательностей](https://www.postgresql.org/docs/19/functions-sequence.html).

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42;
```

**Подготовленный запрос и перекос данных.** Если приложение медленно читает заказы крупного клиента, а ручной запрос с его ID строит быстрый план, воспроизведите вызов через `PREPARE` в отдельной тестовой сессии. Custom plan учитывает конкретное значение параметра. Generic plan можно переиспользовать для разных значений. В режиме `auto` PostgreSQL 19 сначала использует пять custom plans и сравнивает их среднюю оценочную стоимость с оценкой generic plan. Переход зависит от оценки планировщика.

```sql
PREPARE orders_by_user AS SELECT * FROM orders WHERE user_id = $1;

BEGIN;
SET LOCAL plan_cache_mode = force_generic_plan;
EXPLAIN (ANALYZE, BUFFERS) EXECUTE orders_by_user(42);
SET LOCAL plan_cache_mode = force_custom_plan;
EXPLAIN (ANALYZE, BUFFERS) EXECUTE orders_by_user(42);
ROLLBACK;

DEALLOCATE orders_by_user;
```

Подберите ID крупного и типичного клиента. В generic plan параметр отображается как `$1`, в custom plan подставляется значение. Сравните оценки и фактическое число строк, чтения и время на нескольких запусках с учётом прогрева кеша. Принудительные режимы проверяют гипотезу о влиянии параметров. Для подтверждения причины отдельно выясните, какой план выбирается в режиме `auto` на соединении приложения. [PREPARE](https://www.postgresql.org/docs/19/sql-prepare.html), [EXPLAIN](https://www.postgresql.org/docs/19/sql-explain.html).

Чтобы измерить фактический выбор, на том же серверном соединении снимите `generic_plans` и `custom_plans` из `pg_prepared_statements` до и после серии вызовов в режиме `auto`. Если приложение работает через пул, запрос из отдельной сессии покажет подготовленные операторы только этой сессии. Снимайте дельту у той же записи, без переподготовки между замерами. [pg_prepared_statements](https://www.postgresql.org/docs/19/view-pg-prepared-statements.html).

В PostgreSQL 19 `pg_stat_statements` дополнительно показывает `generic_plan_calls` и `custom_plan_calls` для выполнений с соответствующим планом. Для оценки за время инцидента сравните два замера по одному ключу `(dbid, userid, queryid, toplevel)` и проверьте, что `stats_since` совпадает. Например, прирост 980 generic и 20 custom показывает, как часто использовался каждый тип плана по этой записи. Для связи с задержкой всё ещё нужны параметры медленных вызовов и сравнение планов, поскольку статистика объединяет вызовы из разных сессий и режимов. [pg_stat_statements](https://www.postgresql.org/docs/19/pgstatstatements.html).

**5. Проверка регрессии плана в PostgreSQL 19.** Если прежний план был быстрее, модуль `pg_plan_advice` помогает проверить, какое решение планировщика повлияло на результат. После загрузки модуля `EXPLAIN (PLAN_ADVICE)` покажет описание выбранных решений, например порядка соединений. Чтобы проверить гипотезу, задайте в отдельной сессии только нужное ограничение через `pg_plan_advice.advice`. Посмотрите в выводе `EXPLAIN`, применилось ли оно, и сравните время выполнения на представительных параметрах. При изменении распределения данных тот же выбор может стать хуже. [Документация pg_plan_advice](https://www.postgresql.org/docs/19/pgplanadvice.html).

Если приложение повторно выполняет подготовленный запрос, прежний закешированный план может сохраниться после смены advice. Для сравнения заново подготовьте запрос в тестовой сессии при каждой настройке и проверьте план и параметры выполнения. [Ограничения pg_plan_advice](https://www.postgresql.org/docs/19/pgplanadvice.html#PGPLANADVICE-LIMITATIONS).

Если проверенное ограничение нужно автоматически применять к одному запросу, в PostgreSQL 19 для этого есть расширение `pg_stash_advice`. В выбранном хранилище оно сопоставляет идентификатор запроса со строкой advice и читает её при планировании. Для функций управления выполните `CREATE EXTENSION pg_stash_advice` хотя бы в одной базе. Серверную библиотеку загрузите в сессиях, где должно действовать правило, а хранилище выберите через `pg_stash_advice.stash_name`. Например, начните с одной тестовой сессии и проверьте на типичных параметрах, что ограничение применяется и ускоряет запрос. [Документация pg_stash_advice](https://www.postgresql.org/docs/19/pgstashadvice.html).

**Если запись есть, а advice не применяется.** В сессии приложения проверьте `SHOW pg_stash_advice.stash_name` и получите `Query Identifier` через `EXPLAIN (VERBOSE, PLAN_ADVICE)` для того же запроса. `compute_query_id` должен разрешать вычисление идентификаторов. При `auto` загруженный `pg_stash_advice` включает его автоматически. Сравните идентификатор с записью в `pg_get_advice_stash_contents` и повторите проверку после перепланирования. Например, запись для запроса к `orders` из тестовой БД может не сработать в production: идентификатор зависит от разобранного дерева запроса и может отличаться, если разрешились другие объекты. После обновления основной версии также определите идентификатор заново. [pg_stash_advice](https://www.postgresql.org/docs/19/pgstashadvice.html), [pg_stat_statements и границы стабильности queryid](https://www.postgresql.org/docs/19/pgstatstatements.html).

**Откат правила.** Если после включения advice задержка выросла на других значениях параметров, удалите запись вызовом `pg_set_stashed_advice(stash_name, query_id, NULL)`. Это меняет поведение при следующем планировании. Уже закешированные планы могут и дальше использовать прежнее решение. При проверке отката в затронутой сессии переподготовьте запрос или сбросьте её кеш планов командой `DISCARD PLANS`, затем сравните новый план и время выполнения на тех же параметрах. [Управление записями pg_stash_advice](https://www.postgresql.org/docs/19/pgstashadvice.html), [DISCARD](https://www.postgresql.org/docs/19/sql-discard.html).

Источники: [Logging](https://www.postgresql.org/docs/18/runtime-config-logging.html), [pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html), [Monitoring](https://www.postgresql.org/docs/18/monitoring-stats.html), [Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html).

## Q55. Какие популярные расширения PostgreSQL стоит знать?

**Расширение PostgreSQL** — пакет SQL-объектов и, при необходимости, серверной библиотеки. `CREATE EXTENSION` регистрирует его объекты в **текущей базе**, но файлы расширения сначала должны быть установлены на сервере. Для части расширений нужны права суперпользователя или предварительная загрузка библиотеки. Доступность сторонних расширений зависит от сборки и провайдера.

| Расширение | Назначение и граница |
|-----------|----------------------|
| `pg_stat_statements` | Агрегированная статистика SQL; серверный модуль собирает статистику по всем базам после предварительной загрузки и перезапуска. `CREATE EXTENSION` открывает доступ к его представлениям и функциям в текущей базе (Q54). |
| `pg_trgm` | Сходство строк по триграммам, индексируемые `LIKE`/`ILIKE` и поиск похожих строк; это не полнотекстовый поиск с лексемами (Q13/Q47). |
| `hstore` | Значения вида ключ → значение. |
| `pgcrypto` | Криптографические функции; не требуется для встроенной `gen_random_uuid()`. |
| `uuid-ossp` | Дополнительные алгоритмы UUID, например v3/v5; для обычного случайного UUID в PostgreSQL 13+ расширение не нужно. |
| `tablefunc` | Табличные функции, в том числе `crosstab`. |

Сторонние примеры: [PostGIS](https://postgis.net/) для геоданных, [pg_partman](https://github.com/pgpartman/pg_partman) для сопровождения партиций, [TimescaleDB](https://github.com/timescale/timescaledb) для временных рядов и [pg_repack](https://github.com/reorg/pg_repack) для переупаковки таблиц и индексов с минимальными блокировками. Их совместимость с версией PostgreSQL, поставку и разрешения проверяют отдельно. Встроенный `REPACK` появился в PostgreSQL 19 и не требует установки `pg_repack` (Q32). **PgBouncer не является расширением:** это внешний пул соединений (Q49).

В PostgreSQL 18 `gen_random_uuid()`/`uuidv4()` и `uuidv7()` доступны в ядре. `uuid-ossp` нужен только для алгоритмов сверх встроенных; не путайте его с `pgcrypto` или PgBouncer.

```sql
-- Какие расширения доступны серверу для установки
SELECT name, default_version, installed_version
FROM pg_available_extensions;

-- Какие расширения установлены в текущей базе
SELECT extname, extversion FROM pg_extension;

-- Включить доступное расширение в текущей базе
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- Проверить доступные версии установленного расширения
SELECT version, installed
FROM pg_available_extension_versions
WHERE name = 'pg_trgm';

-- Обновить SQL-объекты расширения в текущей базе до версии по умолчанию
ALTER EXTENSION pg_trgm UPDATE;
```

`IF NOT EXISTS` не проверяет, совпадает ли уже установленная версия с доступной. После обновления файлов расширения на сервере версия его SQL-объектов в каждой базе сама не меняется: её обновляет владелец расширения через `ALTER EXTENSION ... UPDATE`, если поставлены подходящие скрипты перехода. Без `TO` команда выбирает версию по умолчанию из control-файла; перед обновлением проверяют доступные версии и совместимость конкретного пакета. При обновлении самого сервера `pg_upgrade` может создать отдельный скрипт обновления расширений для последующего запуска.

**Проверка перед переходом на PostgreSQL 19.** Запустите `pg_upgrade --check` из поставки целевой версии до окна миграции. Например, в 19 штатным классом операторов GiST для `inet` и `cidr` стал встроенный `inet_ops`. Старые классы из `btree_gist` могли пропускать подходящие строки, поэтому `pg_upgrade` откажется обновлять кластер с индексами на этих классах. Подготовьте замену затронутых индексов до миграции. Если индекс обслуживает ограничение исключения, проверьте при замене и само ограничение. Решение касается индексов с конкретными классами операторов. Само наличие расширения `btree_gist` не означает такой блокировки. [Примечания к PostgreSQL 19](https://www.postgresql.org/docs/19/release-19.html), [pg_upgrade](https://www.postgresql.org/docs/19/pgupgrade.html).
