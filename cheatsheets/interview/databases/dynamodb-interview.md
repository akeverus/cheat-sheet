# Вопросы на собеседовании: `DynamoDB`

`AWS DynamoDB` — serverless NoSQL key-value/document-хранилище. Однозначные миллисекунды задержки при любом масштабе. Используют Amazon (Cart, Prime), Netflix, Lyft. На интервью спрашивают: partition keys, индексы (GSI/LSI), single-table design, режимы capacity, hot partitions, DynamoDB Streams, транзакции, Global Tables.

## Q1. (!) Что такое DynamoDB?

**DynamoDB** — полностью управляемое serverless NoSQL key-value/document-хранилище от AWS (доступно с 2012). Главное обещание — стабильная задержка в однозначных миллисекундах при любом объёме данных и трафика, без ручного шардинга и тюнинга.

Ключевая идея: вы не управляете серверами, репликами и партициями — AWS делает это за вас. Взамен модель данных и запросы приходится проектировать заранее под конкретные access patterns (см. Q12).

**Что важно для собеседования:**
- **Стабильная задержка** в однозначных миллисекундах — не «в среднем», а предсказуемо, при росте таблицы до терабайт.
- **Serverless** — нет инстансов, версий движка и патчей; масштабирование (on-demand) или выделенная capacity (provisioned).
- **Встроенная отказоустойчивость** — данные синхронно реплицируются по 3 зонам доступности (AZ) внутри региона.
- **Multi-region** — Global Tables дают активную репликацию в несколько регионов.
- **Оплата** — pay-per-request (on-demand) либо за выделенную capacity (provisioned).

В основе — принципы статьи Amazon Dynamo (2007). DynamoDB обкатан на собственных сервисах Amazon (Cart, Prime, ad tech) под пиковыми нагрузками.

## Q2. (!) Чем DynamoDB отличается от MongoDB и Cassandra?

| Критерий | DynamoDB | MongoDB | Cassandra |
|----------|----------|---------|-----------|
| Хостинг | Только AWS (managed) | Self-host / Atlas | Self-host / Astra |
| Тип | Key-value / Document | Document | Wide-column |
| Схема | Schemaless | Schemaless | Со схемой (CQL) |
| Joins | Нет | Ограниченно (`$lookup`) | Нет |
| Транзакции | Да (ограниченно) | Да (4.0+) | Ограниченно |
| Задержка | Однозначные мс | Переменная | Однозначные мс |
| Масштабирование | Авто | Ручной шардинг | Ручное |
| Vendor lock-in | Высокий | Низкий | Низкий |
| Стоимость | Переменная | Переменная | Self-host: низкая |

Главная разница в том, кто управляет масштабированием. У DynamoDB это полностью на стороне AWS (и отсюда vendor lock-in), у MongoDB и Cassandra — на вас (но можно вынести в любое облако). MongoDB сильнее в гибких запросах по документам, Cassandra — в линейном горизонтальном масштабировании под запись.

**Когда DynamoDB:** AWS-native приложения, заранее известные access patterns, нужен serverless без обслуживания инфраструктуры.
**Когда MongoDB:** гибкая схема, сложные и заранее неизвестные запросы, документная модель.
**Когда Cassandra:** очень большой масштаб, multi-region active-active, write-heavy нагрузка.

## Q3. (!) Когда DynamoDB не подходит?

Главное ограничение: DynamoDB эффективно отвечает только на те запросы, под которые таблица спроектирована заранее. Всё, что требует гибких или агрегирующих запросов «на лету», — против его природы.

**Не подходит, когда:**
- **Сложные запросы** (joins, агрегации) — это не аналитическая БД; считать суммы и группировки на стороне DynamoDB неудобно и дорого.
- **Ad-hoc запросы** (заранее неизвестные access patterns) — добавить новый запрос задним числом часто означает новый GSI или переразметку данных.
- **Отчётность / BI** — выгружайте данные и считайте в Athena или Redshift.
- **Полнотекстовый поиск** — для поиска по тексту используйте OpenSearch.
- **Multi-region записи в существующей таблице** — Global Tables проще включать на этапе создания таблицы; ретроспективное превращение в global-таблицу — отдельная операция.
- **Произвольные запросы по любым полям** — здесь реляционная БД с индексами удобнее.

**Подходит, когда:**
- Access patterns известны и стабильны.
- Нужна предсказуемая производительность на любом масштабе.
- Стек serverless-дружественный (Lambda, API Gateway).
- Вы уже в экосистеме AWS.

## Q4. (!) Как устроен primary key: partition key и sort key?

**Primary key** однозначно идентифицирует item и определяет, где физически лежат данные. Это не просто идентификатор, как в SQL, — от его структуры напрямую зависит, какие запросы будут быстрыми, а какие невозможными.

**Два варианта ключа:**

**1. Только partition key (ключ партиции):**
```
PK: user_id (e.g., "user#123")
```

**2. Составной (partition key + sort key):**
```
PK: user_id        (partition by user)
SK: order_date     (sort within user)
```

**Как это работает:**
- **Partition key** хешируется, и хеш определяет физическую партицию, в которой лежит item. Доступ к одному item по полному ключу — это всегда обращение к одной партиции.
- **Sort key** упорядочивает items внутри одной партиции. Благодаря этому по диапазону SK можно эффективно вытащить связанные записи.
- **Один и тот же PK** — все items попадают в одну партицию, поэтому `Query` по этому PK читает только её (быстро и дёшево).

**Рекомендации:**
- Выбирайте PK с **высокой кардинальностью** (много разных значений) — иначе трафик сконцентрируется на одной партиции и возникнет hot partition (см. Q16).
- Используйте SK, чтобы держать связь one-to-many внутри партиции (профиль пользователя + его заказы под одним PK).

## Q5. Что такое item и attribute?

**Item** — отдельная запись, аналог строки в SQL.
**Attribute** — поле внутри item, аналог колонки.

```json
{
  "user_id": "user#123",      // PK attribute
  "order_id": "order#456",     // SK attribute
  "amount": 99.99,
  "items": ["A", "B"],
  "created_at": "2025-04-19T10:00:00Z"
}
```

По сути каждый item — это JSON-документ. Схема не фиксирована: обязательны только атрибуты ключа (PK и, для составного ключа, SK), а остальные поля у разных items в одной таблице могут различаться. Именно эта гибкость делает возможным single-table design (см. Q11), где в одной таблице живут сущности разного типа.

## Q6. (!) Какие типы данных (data types) поддерживает DynamoDB?

Типы делятся на три группы: скалярные (одно значение), документные (вложенные структуры) и множества (наборы уникальных значений). Дат как отдельного типа нет — их хранят строкой в ISO-8601 (`S`) или числом-timestamp (`N`).

**Скалярные** (одно значение):
- `S` — String
- `N` — Number
- `B` — Binary
- `BOOL` — Boolean
- `NULL`

**Документные** (вложенные структуры):
- `M` — Map (вложенный объект)
- `L` — List (массив)

**Множества** (наборы уникальных значений одного типа):
- `SS` — String Set
- `NS` — Number Set
- `BS` — Binary Set

```json
{
  "user_id": {"S": "user#123"},
  "age": {"N": "30"},
  "tags": {"SS": ["premium", "verified"]},
  "address": {"M": {"city": {"S": "London"}}}
}
```

## Q7. Каков лимит размера item (400 KB)?

Жёсткий лимит — **400 KB на один item**, и в этот размер входят и имена атрибутов, и их значения. Лимит обойти нельзя — большие данные нужно либо ужать, либо вынести из таблицы.

Лимит важно учитывать на этапе проектирования: если поле может неограниченно расти (например, список вложенных элементов), его нельзя держать внутри одного item.

**Как обойти для больших данных:**
- **Сжать** значение перед записью (gzip) и хранить как `B`.
- **Разбить** одну логическую сущность на несколько items через composite key.
- **Вынести payload в S3**, а в DynamoDB держать только метаданные и ссылку — это самый частый паттерн для крупных объектов.

```python
# Pattern: large body → S3, reference в DynamoDB
{
  "PK": "doc#123",
  "metadata": {...},
  "body_s3_uri": "s3://bucket/docs/123.txt"
}
```

## Q8. (!) GSI (Global Secondary Index) — что и зачем?

**GSI** — это альтернативный первичный ключ поверх той же таблицы, который позволяет делать `Query` по другим атрибутам, а не только по основному PK. Под капотом это отдельная копия данных, переразложенная по новому ключу, которую DynamoDB обновляет асинхронно.

Зачем он нужен: основной ключ даёт ровно один способ доступа к данным. Каждый дополнительный access pattern (например, «найти заказ по его номеру» или «список заказов по статусу») закрывается отдельным GSI.

```
Main table:
  PK: user_id, SK: order_id

GSI 1:
  PK: order_id, SK: created_at
  → Query orders by order_id directly

GSI 2:
  PK: status, SK: created_at
  → Query orders by status, sorted by date
```

**Особенности:**
- **Только eventually consistent** — GSI обновляется асинхронно, поэтому свежая запись может на доли секунды отставать. Strongly consistent чтения по GSI невозможны.
- **Своя capacity** — отдельная provisioned capacity (или общий on-demand с таблицей); запись в таблицу тратит ещё и capacity GSI.
- **Дополнительное хранилище** — это физическая копия данных, переразложенная по ключу индекса.
- До **20 GSI на таблицу** (квота по умолчанию).
- **Sparse по умолчанию** — в индекс попадают только те items, у которых заданы атрибуты ключа GSI (см. Q10).

## Q9. (!) LSI (Local Secondary Index) — отличия от GSI?

**LSI** использует **тот же partition key**, что и основная таблица, но даёт **альтернативный sort key**. То есть он не меняет, по какой партиции искать, — он даёт другой порядок сортировки внутри той же партиции.

```
Main table:
  PK: user_id, SK: order_date

LSI:
  PK: user_id (same), SK: amount
  → Query user's orders sorted by amount
```

**Отличия от GSI:**

| Критерий | GSI | LSI |
|-----------|-----|-----|
| Partition key | Другой | **Такой же, как у основной** |
| Когда создаётся | В любой момент | **Только при создании таблицы** |
| Консистентность | Eventually | Есть опция strongly consistent |
| Capacity | Отдельная | Общая с основной таблицей |
| Лимит | 20 на таблицу | 5 на таблицу |

**Главные практические различия:** LSI можно создать только вместе с таблицей (потом — никак), он делит capacity с таблицей и ограничен тем же partition key. Зато он умеет strongly consistent чтения, чего GSI не может.

**На практике LSI применяют редко.** GSI гибче почти во всём. Выбирайте LSI только тогда, когда нужен альтернативный порядок сортировки в пределах того же PK и критична строгая консистентность чтения.

## Q10. Что такое sparse indexes (разреженные индексы)?

**Sparse index** (разреженный индекс) — item попадает в индекс, только если у него заданы атрибуты ключа этого индекса. Items без нужного атрибута в индекс просто не включаются. Это не отдельная настройка, а естественное свойство любого индекса в DynamoDB, которое используют намеренно.

```python
# Item 1
{"PK": "user#1", "SK": "order#1", "status": "PENDING"}

# Item 2
{"PK": "user#2", "SK": "order#2"}  # no status attribute
```

GSI по `status`:
- Item 1 → попадает в индекс
- Item 2 → **не попадает в индекс**

**Сценарий применения** — выборка только «активных» items. Атрибут-ключ GSI выставляют лишь тем items, которые должны быть в выборке, а у остальных его убирают. В результате GSI остаётся маленьким и дешёвым, а запрос по нему не приходится фильтровать.

```python
# Add "active" attribute только для active orders
{"PK": "order#1", "active": "Y", ...}  # in active GSI
{"PK": "order#2", ...}                  # closed, not in active GSI
```

Закрытому заказу достаточно удалить атрибут `active` — он автоматически выпадет из индекса. Запрос активных заказов читает только небольшой GSI вместо полного `Scan` с фильтром.

## Q11. (!) Что такое single-table design?

**Single-table design** — это паттерн, при котором **все сущности приложения хранятся в одной таблице** и различаются только структурой ключей PK/SK, а не отдельными таблицами. Пользователи, заказы, товары — всё лежит вперемешку, но так, что связанные записи оказываются под одним partition key.

Смысл в том, что в DynamoDB нет join'ов. Чтобы достать связанные данные одним запросом, их физически кладут рядом — в одну партицию. Тогда `Query` по одному PK возвращает и сущность, и всё, что с ней связано.

```
PK              | SK              | type    | data...
user#123        | profile          | USER    | {name, email}
user#123        | order#456        | ORDER   | {amount, date}
user#123        | order#789        | ORDER   | {amount, date}
order#456       | item#a           | ITEM    | {sku, qty}
order#456       | item#b           | ITEM    | {sku, qty}
product#sku-1   | metadata         | PRODUCT | {name, price}
```

**Плюсы:**
- **Один `Query` вместо нескольких запросов** — связанные items лежат в одной партиции, заменяя join'ы.
- **Атомарные транзакции внутри таблицы** — проще обеспечить согласованность связанных записей.
- **Дешевле и проще в эксплуатации** — настраивается capacity и алармы для одной таблицы, а не для десятка.

**Компромиссы:**
- **Сложнее проектировать** — нужно знать все access patterns заранее, до создания таблицы.
- **Непривычно после SQL** — данные выглядят «свалкой» разных сущностей в одной таблице.
- **Тяжелее эволюционировать** — новые паттерны и миграции данных требуют осторожности.

На 2025 год single-table остаётся рекомендуемым паттерном у экспертов по DynamoDB (Alex DeBrie), хотя для простых случаев допустимо начинать с нескольких таблиц.

## Q12. (!) Access patterns — почему важны?

Access patterns — это полный список запросов, которые приложение будет делать к данным. В DynamoDB проектирование идёт от них, а не от структуры данных. Это переворот привычного порядка: в SQL сначала нормализуют модель, а запросы пишут потом; в DynamoDB наоборот — сначала фиксируют запросы, и под них строят ключи и индексы.

**Порядок проектирования:**

1. **Сначала перечислите все access patterns** — конкретные запросы, а не сущности:
   - Получить пользователя по ID
   - Получить заказы пользователя
   - Получить заказ вместе с items
   - Получить топ-10 популярных продуктов
   ...

2. **Спроектируйте таблицу под каждый паттерн:**
   - Подберите PK/SK так, чтобы каждый запрос закрывался одним `Query` или `GetItem`.
   - Для паттернов, которые не ложатся на основной ключ, спланируйте GSI.

3. **Избегайте `Scan`** — полный скан таблицы медленный и дорогой; если запрос приводит к `Scan`, скорее всего, модель спроектирована неверно.

Причина строгости проста: добавить новый access pattern задним числом тяжело — он почти всегда тянет за собой новый GSI или переразложение данных. Без проектирования заранее DynamoDB либо упирается в `Scan`, либо требует дорогой переделки.

## Q13. Какие бывают стратегии композитных ключей (PK/SK)?

Идея всех стратегий одна: подобрать структуру SK так, чтобы нужные items оказались рядом в партиции и доставались одним `Query` по диапазону или префиксу.

**Иерархический ключ (one-to-many):** под одним PK держим разнотипные записи, а тип кодируем в префиксе SK.
```
PK: user#123 + SK: profile         → user profile
PK: user#123 + SK: order#456       → user's order
PK: user#123 + SK: order#789       → another order
```
Запрос `PK="user#123" AND begins_with(SK, "order#")` вернёт все заказы пользователя одним обращением к партиции.

**Сортировка по дате:** дату ставим в начало SK, чтобы работал диапазонный поиск по времени.
```
PK: user#123 + SK: 2025-04-19#order#456
```
Тогда `Query` с условием `BETWEEN` по SK достаёт заказы за нужный период.

**Инвертированный индекс:** GSI, в котором PK и SK меняются местами, открывает обратное направление связи (например, «по заказу найти пользователей»).
```
GSI: PK = SK, SK = PK
```

## Q14. (!) Чем отличаются режимы On-demand и Provisioned capacity?

Разница в том, кто отвечает за планирование пропускной способности. On-demand перекладывает это на AWS: платите за фактические запросы, capacity подстраивается мгновенно. Provisioned требует заранее заявить, сколько чтений и записей в секунду нужно, — зато при стабильной нагрузке выходит дешевле.

**On-demand (по запросам):**
- Оплата за фактические запросы (порядка $0.25 за миллион чтений и $1.25 за миллион записей в us-east-1 — чтения примерно в 5 раз дешевле записей; в конце 2024 AWS снизил on-demand-цены ещё примерно вдвое).
- **Мгновенное масштабирование** — нет throttling из-за нехватки заявленной capacity.
- **Не нужно планировать capacity** заранее.
- Подходит для: непредсказуемого или скачкообразного трафика, dev/test, новых сервисов.

**Provisioned (выделенная):**
- Заранее выделяете **RCU/WCU** — сколько чтений и записей в секунду гарантировано.
- **Дешевле при стабильном предсказуемом трафике**.
- Доступна скидка на reserved capacity (до 76%) за обязательство по объёму.
- **Авто-масштабирование** есть, но реактивное и с задержкой — на резкий всплеск среагирует не сразу, возможен throttling.

**Рекомендация:** on-demand — для dev и непредсказуемых паттернов. Provisioned — для production со стабильной, прогнозируемой нагрузкой ради экономии.

## Q15. RCU и WCU — что это?

RCU и WCU — единицы пропускной способности, в которых DynamoDB измеряет и тарифицирует чтения и записи. Одна единица привязана к фиксированному размеру item, и важно помнить пороги: для чтения это 4 KB, для записи — 1 KB. Item крупнее порога стоит пропорционально больше единиц (округление вверх).

**RCU (Read Capacity Unit)** — за секунду одна RCU обеспечивает:
- 1 strongly consistent чтение item до 4 KB,
- 2 eventually consistent чтения item до 4 KB (eventually вдвое дешевле),
- 0.5 транзакционного чтения (транзакции дороже).

**WCU (Write Capacity Unit)** — за секунду одна WCU обеспечивает:
- 1 запись item до 1 KB,
- 0.5 транзакционной записи (то есть транзакционная запись стоит 2 WCU).

**Примеры расчёта:**
- Чтение item 8 KB strongly consistent = 2 RCU (8 KB / 4 KB).
- Запись item 2 KB = 2 WCU (2 KB / 1 KB).

**Provisioning:**
```
RCU: 1000 = 1000 reads/sec для < 4 KB items
WCU: 500 = 500 writes/sec для < 1 KB items
```

При throttling — `ProvisionedThroughputExceededException`.

## Q16. (!) В чём проблема hot partition?

**Hot partition** — это партиция, на которую приходится непропорционально много трафика, из-за чего она упирается в свой лимит и начинает отвергать запросы (throttling), хотя суммарной capacity таблицы хватает.

Корень проблемы в том, как DynamoDB распределяет данные: partition key хешируется, и хеш определяет физическую партицию. Если значений у PK мало или одно значение очень «популярное», весь трафик стекается в одну партицию, а её пропускная способность ограничена.

```
Bad PK choice: status = "ACTIVE" → 99% of items
→ All reads hit one partition → throttle
```

**Симптомы:**
- Throttling даже при высокой суммарной provisioned capacity.
- Неравномерное распределение запросов по партициям.

**Решения:**
- **Выбирайте PK с высокой кардинальностью** — user_id или order_id, но не status, у которого мало значений.
- **Write sharding** — добавить к ключу случайный суффикс (`user_id#1`, `user_id#2`, …), чтобы «горячие» записи разъехались по разным партициям; при чтении придётся опросить все шарды.
- **Read sharding** — снять нагрузку с чтений кешем DAX (см. Q27).
- **Adaptive capacity** — автоматический механизм DynamoDB, частично сглаживающий проблему (см. Q17).

## Q17. Что такое adaptive capacity?

**Adaptive capacity** (с 2018) — встроенный механизм DynamoDB, который автоматически перераспределяет пропускную способность в пользу перегруженных партиций, не требуя действий от разработчика.

Логика проста: если таблице выделено 1000 WCU, но 90% трафика бьёт в одну партицию, DynamoDB временно поднимает её доступную capacity за счёт простаивающих партиций. Это сглаживает краткосрочные всплески и неравномерность.

**Важно понимать ограничение:** adaptive capacity лечит симптом, а не причину. Постоянная hot partition из-за плохого выбора PK всё равно требует исправления на уровне модели данных (см. Q16) — на механизм нельзя полагаться как на решение.

## Q18. (!) GetItem, Query, Scan — отличия?

Это три способа чтения, и разница между ними — в том, сколько данных они вынуждены прочитать. Чем точнее операция бьёт по ключу, тем она быстрее и дешевле: `GetItem` читает один item, `Query` — одну партицию, `Scan` — всю таблицу.

**GetItem** — достаёт ровно один item по полному ключу (PK, а для составного ключа — и SK).
- Самая быстрая операция, обращение к одному item.
- Задержка в однозначные миллисекунды.

**Query** — достаёт несколько items в пределах **одного partition key**.
- Задаёте PK и опциональное условие по SK (`=`, `BETWEEN`, `BEGINS_WITH`, …).
- Результат отсортирован по SK (ASC/DESC).
- Поддерживает пагинацию.
- Быстро, потому что читается только одна партиция, а не вся таблица.

**Scan** — читает всю таблицу целиком, item за item.
- **Медленно и дорого** — оплачивается чтение всех записей, даже отброшенных фильтром.
- Допустим только для маленьких таблиц или разовых миграций.
- **В production-коде на горячем пути его быть не должно** — это признак неверной модели данных.

```python
# GetItem — fast
table.get_item(Key={"PK": "user#123", "SK": "profile"})

# Query — fast
table.query(
    KeyConditionExpression=Key("PK").eq("user#123") & Key("SK").begins_with("order#")
)

# Scan — slow!
table.scan(FilterExpression=Attr("status").eq("ACTIVE"))
```

## Q19. PartiQL для DynamoDB?

**PartiQL** — SQL-подобный язык запросов к DynamoDB (доступен с 2020). Он даёт привычный синтаксис `SELECT` / `INSERT` / `UPDATE` / `DELETE` поверх обычного API.

```sql
SELECT * FROM "MyTable" WHERE PK = 'user#123' AND begins_with(SK, 'order#');
INSERT INTO "MyTable" VALUE {'PK': 'user#456', 'name': 'Alice'};
UPDATE "MyTable" SET status = 'ACTIVE' WHERE PK = 'user#123';
```

Это лишь удобная обёртка: каждый запрос компилируется в обычные операции `Query` / `Scan` / `PutItem` / …

**Важно не обмануться:** PartiQL — не настоящий SQL. Все ограничения DynamoDB остаются в силе. Нет join'ов; запрос без условия по ключу превратится в дорогой `Scan`, даже если внешне выглядит как безобидный `SELECT * WHERE`.

## Q20. Как работают filter expressions?

**Filter expression** отсеивает items уже **после** их чтения из таблицы операцией `Query`/`Scan`, но **до** отправки клиенту. Это ключевой момент: фильтр сужает результат, но не сужает объём прочитанных данных.

```python
table.query(
    KeyConditionExpression=Key("PK").eq("user#123"),
    FilterExpression=Attr("status").eq("ACTIVE")
)
```

**Подводный камень:** фильтр **не снижает потребление read capacity**. Если `Scan` прочитал миллион items и фильтр оставил десять — вы заплатили за чтение всего миллиона. Фильтр экономит трафик в сеть, но не деньги и не время на чтение.

**Рекомендация:** сужать выборку нужно условиями по ключу (key condition) — они работают на этапе чтения и реально экономят capacity. Если фильтрация по какому-то полю нужна часто, заведите под него GSI, а не полагайтесь на filter expression.

## Q21. Pagination в DynamoDB?

Пагинация в DynamoDB основана на курсоре, а не на смещении (offset). После запроса DynamoDB возвращает `LastEvaluatedKey` — ключ последнего обработанного item; чтобы получить следующую страницу, его передают обратно в `ExclusiveStartKey`. Если `LastEvaluatedKey` в ответе нет — данные закончились.

```python
response = table.query(
    KeyConditionExpression=Key("PK").eq("user#123"),
    Limit=20  # max 20 items per page
)

# Pagination token
last_key = response.get("LastEvaluatedKey")

# Next page
response = table.query(
    KeyConditionExpression=...,
    Limit=20,
    ExclusiveStartKey=last_key
)
```

Дополнительная причина пагинации — жёсткий лимит **1 MB на один ответ**. Даже без `Limit` DynamoDB вернёт не больше 1 MB за раз и отдаст `LastEvaluatedKey`, так что обрабатывать страницы в цикле приходится почти всегда.

## Q22. (!) Как работают DynamoDB Transactions?

DynamoDB поддерживает ACID-транзакции: группа операций применяется по принципу «всё или ничего» — либо проходят все действия, либо ни одного. Это позволяет атомарно менять сразу несколько items (и даже несколько таблиц), сохраняя согласованность.

**TransactWriteItems** — атомарная группа до **100 действий записи** (`Put`, `Update`, `Delete`, `ConditionCheck`) в одной транзакции.

```python
client.transact_write_items(
    TransactItems=[
        {"Put": {"TableName": "Orders", "Item": {...}}},
        {"Update": {"TableName": "Inventory", "Key": {...}, "UpdateExpression": "SET qty = qty - :n"}},
        {"ConditionCheck": {"TableName": "Users", "Key": {...}, "ConditionExpression": "active = :true"}}
    ]
)
```

**TransactGetItems** — атомарное чтение до 100 items в едином согласованном снимке.

**Особенности и ограничения:**
- **ACID** в пределах DynamoDB (в рамках одного региона; на Global Tables гарантии не распространяются на репликацию между регионами).
- Лимит — до 4 MB и 100 items на транзакцию.
- **Стоит вдвое дороже** обычных операций (2× WCU/RCU), потому что под капотом делается два прохода — подготовка и применение.
- Может завершиться отказом (`ConditionalCheckFailed` — не выполнилось одно из условий) — код должен обработать отказ и при необходимости сделать retry.

## Q23. Что такое conditional writes (условные записи)?

**Conditional write** — это запись, которая применяется только если выполнено заданное условие, проверяемое атомарно на стороне DynamoDB. Если условие ложно — операция отклоняется (`ConditionalCheckFailed`) и ничего не меняется. Это даёт атомарность для одного item без накладных расходов полноценной транзакции.

```python
table.put_item(
    Item={"PK": "user#123", "name": "Alice"},
    ConditionExpression="attribute_not_exists(PK)"  # Only if doesn't exist
)

table.update_item(
    Key={"PK": "order#123"},
    UpdateExpression="SET #s = :new",
    ConditionExpression="#s = :expected",  # CAS
    ExpressionAttributeNames={"#s": "status"},
    ExpressionAttributeValues={":new": "SHIPPED", ":expected": "PROCESSING"}
)
```

**Сценарии применения:**
- **Идемпотентность** — вставить item, только если его ещё нет (`attribute_not_exists`), чтобы повторная попытка не создала дубль.
- **Оптимистичная блокировка** — обновить, только если значение совпало с ожидаемым (см. Q24).
- **Атомарные счётчики и переходы статусов** — изменить поле только из конкретного предыдущего состояния.

## Q24. Как реализовать optimistic locking?

Оптимистичная блокировка предотвращает потерю обновлений (lost update), когда два процесса читают один item и пишут поверх друг друга. Идея: хранить атрибут `version`, читать его вместе с item и при записи проверять условием, что версия не изменилась с момента чтения, — это и есть CAS (compare-and-swap) поверх conditional write.

```python
# Read
item = table.get_item(...)["Item"]
version = item["version"]

# Update в коде
item["amount"] = 200

# Write с CAS
table.update_item(
    Key={"PK": item["PK"]},
    UpdateExpression="SET amount = :new, version = version + 1",
    ConditionExpression="version = :expected",
    ExpressionAttributeValues={":new": 200, ":expected": version}
)
# Если version изменилась → ConditionalCheckFailed → retry
```

При конфликте операция падает с `ConditionalCheckFailed` — обработчик должен перечитать item и повторить попытку. В DynamoDB Java SDK этот паттерн встроен: достаточно пометить поле аннотацией `@DynamoDbVersionAttribute`, и маппер сам ведёт версию и подставляет условие.

## Q25. (!) Что такое DynamoDB Streams?

**DynamoDB Streams** — это change data capture (CDC) для DynamoDB: упорядоченный поток событий обо всех изменениях данных в таблице. Каждое изменение item (INSERT / UPDATE / DELETE) попадает в stream как отдельная запись, которую можно прочитать и обработать.

Главная ценность — реакция на изменения без опроса таблицы: вместо периодического `Scan` приложение подписывается на поток и обрабатывает события по мере их появления.

**Запись stream:**
```json
{
  "eventName": "INSERT",
  "dynamodb": {
    "Keys": {"PK": {"S": "user#123"}},
    "NewImage": {...},
    "OldImage": {...}
  }
}
```

Запись содержит `Keys` всегда; а `NewImage`/`OldImage` — в зависимости от выбранного режима StreamViewType (можно хранить новое состояние, старое, оба или только ключи).

**Срок хранения:** события живут в stream 24 часа — за это время их нужно успеть обработать.

**Сценарии применения:**
- Запускать Lambda в ответ на изменения данных (см. Q26).
- Реплицировать данные в ElasticSearch / OpenSearch для поиска.
- Пересчитывать агрегаты или инвалидировать кеш.
- Отправлять уведомления и события в другие сервисы.
- Вести журнал аудита (audit log) изменений.

## Q26. Как настроить Lambda-триггеры на Streams?

Lambda можно подписать на DynamoDB Streams как event source: сервис сам опрашивает stream и вызывает функцию пакетами записей (batch). Внутри функции вы перебираете `event["Records"]` и реагируете на нужные типы событий.

```python
def handler(event, context):
    for record in event["Records"]:
        if record["eventName"] == "INSERT":
            new_item = record["dynamodb"]["NewImage"]
            # Process new order, send email, etc.
```

**Параметры подписки:**
- **Batch size** (1–10000) — сколько записей передавать в один вызов.
- **Batch window** (0–5 сек) — сколько ждать, накапливая записи, прежде чем вызвать функцию.
- **Parallelization factor** (1–10) — сколько параллельных обработчиков на один шард.
- **Filter expressions** — обрабатывать только подходящие записи, экономя вызовы Lambda.

**Подводный камень:** Lambda получает целый batch. Если упадёт обработка хотя бы одной записи, по умолчанию повторяется весь пакет — и порядок обработки в шарде застопорится. Чтобы переотправлять только сбойные записи, включают `ReportBatchItemFailures` (partial batch response).

Подробнее — в [AWS Lambda](../cloud/aws-lambda-interview.md).

## Q27. (!) Что такое DAX (DynamoDB Accelerator)?

**DAX** — управляемый in-memory кеш, который ставится перед DynamoDB и снижает задержку чтений с миллисекунд до микросекунд. По сути это read-through кеш: при попадании ответ отдаётся из памяти, при промахе DAX сам ходит в DynamoDB и кладёт результат в кеш.

Поток запроса (`graph LR`):
- Приложение (`App`) обращается к кластеру DAX (`DAX Cluster`).
- При промахе (`miss`) DAX идёт в DynamoDB (`DynamoDB`).
- DynamoDB возвращает данные обратно в DAX.
- DAX отдаёт ответ приложению (`App`).

**API-совместим** — drop-in замена для DynamoDB SDK, код приложения почти не меняется.

**Что кеширует:**
- **Item cache** — результаты `GetItem`.
- **Query cache** — результаты `Query` и `Scan`.

**Сценарий применения:** read-heavy нагрузки с частым обращением к одним и тем же items (горячие профили, каталог) — DAX снимает с DynamoDB основную массу повторных чтений.

**Когда НЕ подходит:**
- Нужна строгая консистентность — DAX отдаёт данные eventually consistent и может вернуть слегка устаревшее значение.
- Write-heavy нагрузка — кешируются только чтения, записи всё равно идут в DynamoDB напрямую.

## Q28. (!) Что такое Global Tables (multi-region)?

**Global Tables** — это автоматическая репликация одной таблицы между несколькими регионами AWS. Реплики синхронизируются в фоне, так что приложение в каждом регионе работает с локальной копией данных.

```
Region us-east-1: tables replicates ↔
Region eu-west-1: tables replicates ↔
Region ap-northeast-1: tables replicates
```

**Multi-master:** записывать можно в любом регионе, изменения автоматически расходятся по остальным. Нет «главного» региона, в который надо ходить за записью.

**Разрешение конфликтов:** если один item изменили в двух регионах почти одновременно, побеждает последняя запись по timestamp (last writer wins). Промежуточное обновление при этом теряется — это нужно учитывать в логике приложения.

**Сценарии применения:**
- Аварийное восстановление (disaster recovery) — данные доступны в другом регионе, если один откажет.
- Низкая задержка для пользователей в разных регионах — каждый читает из ближайшего.
- Соответствие требованиям к месту хранения данных (data residency).

**Подводный камень:** между регионами действует **eventual consistency** — запись в одном регионе доезжает в другой с задержкой (обычно до нескольких секунд). Сразу после записи в регионе A в регионе B можно прочитать старое значение.

## Q29. Backup и PITR?

В DynamoDB есть два механизма резервного копирования, и они дополняют друг друга. On-demand бэкапы — это ручные снимки «на сейчас» (например, перед рискованной миграцией). PITR — непрерывное копирование, позволяющее откатиться к любому моменту времени.

**On-demand бэкапы** — снимок таблицы по запросу, хранится сколько нужно:
```bash
aws dynamodb create-backup --table-name MyTable --backup-name backup-1
```

**PITR (Point-in-time recovery)** — непрерывные бэкапы для восстановления на любой момент:
- Откат до любой секунды за последние 35 дней — спасает от «случайно затёр данные».
- Работает непрерывно и прозрачно, без ручных действий.
- Стоит дополнительно ~$0.20/GB/месяц.

```bash
aws dynamodb update-continuous-backups \
  --table-name MyTable \
  --point-in-time-recovery-specification PointInTimeRecoveryEnabled=true
```

**Рекомендация:** PITR включён для production.

## Q30. (!) Какие частые ошибки в DynamoDB production?

Большинство этих ошибок — следствие переноса реляционного мышления на DynamoDB. Корень почти всех проблем один: данные спроектированы не под реальные access patterns.

1. **Неудачный выбор PK** — низкая кардинальность ведёт к hot partitions и throttling (Q16).
2. **`Scan` на горячем пути** — медленно и дорого; обычно признак неверной модели (Q18).
3. **Нет проектирования access patterns** — реляционное мышление вместо проектирования от запросов (Q12).
4. **Слишком много GSI** — каждый индекс удваивает запись и съедает capacity и хранилище (Q8).
5. **Items больше 400 KB** — упирается в лимит; нужно дробить или выносить payload в S3 (Q7).
6. **Не включён PITR** — риск безвозвратно потерять данные при ошибке (Q29).
7. **Неверная provisioned capacity** — слишком много означает переплату, слишком мало — throttling (Q14).
8. **Filter вместо key condition** — чтения всё равно оплачиваются, экономии нет (Q20).
9. **Query без `Limit`** — подгружается вся партиция, лишний трафик и capacity (Q21).
10. **Лишняя строгая консистентность** — strongly consistent чтение стоит вдвое дороже eventually consistent (Q15).
