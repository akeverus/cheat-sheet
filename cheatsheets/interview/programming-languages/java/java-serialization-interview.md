## Q1. (!) Что такое сериализация и зачем она нужна?

**Сериализация** — это преобразование объекта в поток байтов (или в другой формат), чтобы его можно было сохранить на диск, передать по сети или положить в кэш. Обратный процесс восстановления объекта из потока называется **десериализацией**. В `Java` стандартный механизм — классы `ObjectOutputStream` и `ObjectInputStream`, работающие с бинарным форматом, специфичным для `JVM`.

Такой подход используется для персистентности (сохранение состояния приложения), для RMI (удалённый вызов методов), для кэширования (например, сессий в веб-приложениях) и для передачи сообщений через очереди. Важно понимать, что бинарная Java-сериализация привязана к платформе и к версии класса; для межсистемного обмена и современных сервисов чаще применяют альтернативы: JSON, XML, Protocol Buffers — они не выполняют произвольный код при десериализации и обычно безопаснее.

## Q2. (!) Что такое маркерный интерфейс `Serializable`?

`Serializable` — это маркерный интерфейс в пакете `java.io`: у него нет методов, он лишь помечает класс как допускающий сериализацию. Класс должен реализовать `Serializable`, чтобы `JVM` разрешила записывать его экземпляры через `ObjectOutputStream`. Если попытаться сериализовать объект класса без этого интерфейса, будет выброшено `NotSerializableException` с указанием класса.

Все подклассы сериализуемого класса автоматически считаются сериализуемыми. Если в классе есть поля ссылочных типов, их классы тоже должны быть сериализуемы (или поля помечены `transient`). Несериализуемые поля либо объявляют `transient` (тогда при десериализации они получат значения по умолчанию), либо обеспечивают их инициализацию после десериализации через методы `readObject` / `readResolve`.

```java
public class User implements Serializable {
    private static final long serialVersionUID = 1L;
    private final String name;
    private final int age;

    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }
}
// Без Serializable при writeObject(obj) — NotSerializableException
```

## Q3. Что такое `serialVersionUID` и когда его задавать?

`serialVersionUID` — это число типа `long`, которое идентифицирует версию сериализованного класса. Оно используется при десериализации: если UID в потоке не совпадает с UID класса в `JVM`, выбрасывается `InvalidClassException`. Если разработчик не задаёт `serialVersionUID` явно, `JVM` вычисляет его по сигнатурам полей, методов и суперклассов; при любом совместимом или несовместимом изменении класса это значение может измениться, и старые сохранённые данные перестанут десериализоваться.

Явное объявление `private static final long serialVersionUID = 1L;` (или другое фиксированное значение) даёт контроль над совместимостью: при обратно совместимых изменениях (добавление полей с default-значениями и т.п.) UID оставляют тем же; при несовместимых (удаление поля, смена типа) UID меняют, чтобы старые данные не десериализовались по ошибке. В сериализуемых классах явно задавать `serialVersionUID` рекомендуется, чтобы поведение было предсказуемым.

## Q4. Какие поля не сериализуются (`transient`, `static`)?

Поля с модификатором **`transient`** не записываются в поток сериализации. При десериализации таким полям присваиваются значения по умолчанию: `null` для ссылок, `0` для чисел, `false` для `boolean`. Так обычно помечают кэши, временные буферы или поля, которые можно вычислить заново после загрузки объекта.

**Статические** (`static`) поля не сериализуются — они принадлежат классу, а не экземпляру, и при загрузке класса уже инициализированы. Финальные поля с примитивами или ссылками сериализуются как обычные поля; при десериализации `JVM` способна присвоить им значение из потока через внутренний механизм, несмотря на `final`. Если нужно, чтобы `transient`-поле инициализировалось не значением по умолчанию, можно реализовать приватные методы `readObject` и `writeObject` и в них вручную прочитать/записать нужные данные.

```java
public class CachedResult implements Serializable {
    private static final long serialVersionUID = 1L;
    private final String data;
    private transient volatile Object cache;  // не сериализуется, после десериализации = null

    public CachedResult(String data) {
        this.data = data;
        this.cache = compute(data);
    }
}
```

## Q5. Что такое `Externalizable` и чем отличается от `Serializable`?

`Externalizable` расширяет `Serializable` и добавляет два метода: `writeExternal(ObjectOutput out)` и `readExternal(ObjectInput in)`. Класс, реализующий `Externalizable`, сам решает, какие поля и в каком порядке записывать и читать. Это даёт полный контроль над форматом и позволяет оптимизировать размер потока и производительность; удобно, когда нужна компактность или нестандартная логика (например, сжатие, шифрование).

Важное отличие от `Serializable`: при десериализации сначала вызывается **публичный конструктор без аргументов**, а затем `readExternal`. Без no-arg конструктора десериализация невозможна. Из-за ручного поддержания совместимости при изменении полей (нужно самому следить за порядком и версиями) `Externalizable` используют реже, чем `Serializable`; его применяют там, где критичны размер или скорость.

```java
public class CompactDto implements Externalizable {
    private String name;
    private int id;

    public CompactDto() {}  // обязателен для десериализации

    @Override
    public void writeExternal(ObjectOutput out) throws IOException {
        out.writeUTF(name);
        out.writeInt(id);
    }

    @Override
    public void readExternal(ObjectInput in) throws IOException {
        name = in.readUTF();
        id = in.readInt();
    }
}
```

## Q6. Как сериализуется наследование (родитель не `Serializable`)?

Если родительский класс **не** реализует `Serializable`, при сериализации объекта-потомка в поток попадают только поля, объявленные в самом потомке. Поля родителя не сохраняются. При десериализации для создания объекта родительской части JVM вызывает конструктор по умолчанию (без аргументов) родительского класса; поэтому у такого родителя **обязан** быть доступный no-arg конструктор, иначе возникнет `InvalidClassException`.

Если же родитель сам реализует `Serializable`, его поля сериализуются вместе с полями потомка: сначала идёт «граф» от родителя, затем от потомка. Инициализация при десериализации идёт снизу вверх по иерархии (от Object к потомку), но без вызова обычных конструкторов — поля восстанавливаются из потока. Учитывая это, в несериализуемом родителе часто делают поля `transient` или обеспечивают no-arg конструктор и логику восстановления в потомке через `readObject`.

## Q7. Какие риски безопасности у `Java Serialization`?

Десериализация произвольного потока байтов может привести к выполнению произвольного кода. Атакующий формирует поток так, чтобы при чтении объектов вызывались опасные цепочки вызовов (гаджеты) в классах из classpath (например, создание `ProcessBuilder`, вызов методов через рефлексию). Известны уязвимости в старых версиях JDK и в библиотеках (в т.ч. Apache Commons Collections); даже при обновлениях риск остаётся из-за большого количества классов на classpath.

Рекомендации: не десериализовать данные из ненадёжных источников; если десериализация неизбежна — использовать `ObjectInputFilter` (`Java` 9+), задавая белый список допустимых классов и ограничения по глубине и количеству объектов. По возможности стоит переходить на форматы без исполнения кода при десериализации: JSON, Protocol Buffers и т.п., где парсинг не вызывает конструкторы и методы приложения.

## Q8. Какие альтернативы бинарной сериализации (`JSON`, protobuf)?

`JSON` (через Jackson, Gson и др.) — текстовый формат, удобный для API и логов, независимый от языка; минусы — больший объём и отсутствие строгой типизации в самом формате. **XML** — тоже текстовый, с поддержкой схем (XSD). **Protocol Buffers** (protobuf) — бинарный формат со схемой и кодогенерацией, компактный и быстрый, хорошо подходит для RPC и высоконагруженных систем; типы и совместимость версий задаются в `.proto` файлах.

Для JVM также популярны быстрые бинарные форматы вроде `Kryo` и `FST` — они не выполняют произвольный код при десериализации (в отличие от стандартной Java-сериализации), но привязаны к Java. Выбор формата зависит от требований: межязыковая совместимость, производительность, безопасность, необходимость человекочитаемого вида и инструментов (логи, отладка).

## Q9. Как сериализовать объект в файл и обратно?

Сериализация в файл выполняется через связку `FileOutputStream` и `ObjectOutputStream`. Нужно создать `FileOutputStream` по пути к файлу, обернуть его в `ObjectOutputStream`, вызвать `writeObject(obj)` для каждого объекта (или один раз для графа объектов), и обязательно закрыть поток. Удобнее всего использовать `try-with-resources`, чтобы потоки закрывались даже при исключении.

При чтении используют `FileInputStream` и `ObjectInputStream`: создают поток из файла, оборачивают в `ObjectInputStream`, вызывают `readObject()`. Возвращается `Object`, его нужно привести к нужному типу. Важно обрабатывать `IOException` (файл не найден, ошибка чтения) и `ClassNotFoundException` (класс объекта из потока отсутствует в classpath). Ресурсы следует закрывать; при использовании одного файла для нескольких объектов нужно соблюдать тот же порядок записи и чтения.

```java
// Запись
try (var fos = new FileOutputStream("data.ser");
     var oos = new ObjectOutputStream(fos)) {
    oos.writeObject(user);
}

// Чтение
try (var fis = new FileInputStream("data.ser");
     var ois = new ObjectInputStream(fis)) {
    User user = (User) ois.readObject();
}
```

## Q10. Что такое `writeReplace` и `readResolve`?

Это специальные **приватные** методы, которые позволяют подменить объект при сериализации и десериализации. **`writeReplace()`** вызывается до записи объекта в поток; объект, который он возвращает, сериализуется вместо исходного. Так можно, например, подменить синглтон или прокси на «маркерный» объект, чтобы в потоке не оказывалось лишних данных или сложного графа.

**`readResolve()`** вызывается после того, как объект десериализован; возвращаемый им объект подменяет только что созданный и возвращается вызывающему `readObject()`. Классическое применение — синглтоны: при десериализации создаётся новый экземпляр, а `readResolve()` возвращает единственный существующий экземпляр, сохраняя единственность. Оба метода дают контроль над тем, что реально уходит в поток и что возвращается при чтении, без изменения остальной логики сериализации.

```java
public class Singleton implements Serializable {
    private static final long serialVersionUID = 1L;
    public static final Singleton INSTANCE = new Singleton();

    private Singleton() {}

    private Object readResolve() {
        return INSTANCE;  // при десериализации вернуть единственный экземпляр
    }
}
```

## Q11. Что такое `ObjectInputFilter` и зачем он нужен?

`ObjectInputFilter` (интерфейс с `Java` 9) позволяет ограничить набор классов, которые разрешено десериализовать, и ограничить сложность графа объектов (глубина, число ссылок). Это снижает риск атак через вредоносные сериализованные данные: даже если в classpath есть опасные гаджеты, фильтр может запретить их загрузку.

Фильтр задаётся через `ObjectInputStream.setObjectInputFilter(filter)` или глобально через системное свойство `jdk.serialFilter`. В фильтре можно разрешать конкретные классы (белый список), запрещать известные опасные, ограничивать глубину и количество массивов/объектов. Рекомендуется задавать фильтр до первого вызова `readObject()`. Для приложений, принимающих сериализованные данные извне, использование фильтра считается обязательной мерой безопасности.

```java
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
    "com.example.dto.*;!*"  // разрешить только классы из пакета com.example.dto
);
try (var ois = new ObjectInputStream(fis)) {
    ois.setObjectInputFilter(filter);
    var obj = ois.readObject();
}
```

## Q12. Как сериализуются `enum` и `record` в `Java`?

**Enum**: константы перечислений сериализуются по **имени** (а не по полям). В поток записывается только имя константы; при десериализации вызывается `Enum.valueOf(класс, имя)`, поэтому создаётся тот же самый экземпляр константы, что и в `JVM`. Дополнительные поля у `enum` при стандартной сериализации не записываются — это сделано намеренно, чтобы гарантировать совпадение константы по идентичности. Кастомная сериализация для enum не поддерживается (методы `writeObject`/`readObject` игнорируются).

**Record** (Java 16+): по умолчанию record не реализует `Serializable`. Если объявить `record Point(int x, int y) implements Serializable {}`, то сериализуются только компоненты (как поля); механизм использует канонический конструктор при десериализации. Рекомендуется явно задавать `serialVersionUID` для record, если нужна стабильная совместимость между версиями. Record удобны для DTO и сообщений в сочетании с JSON или protobuf, но и бинарная сериализация при необходимости поддерживается.

```java
public enum Status { ACTIVE, INACTIVE }  // сериализуется по имени "ACTIVE"/"INACTIVE"

public record Point(int x, int y) implements Serializable {
    private static final long serialVersionUID = 1L;
}
```

## Q13. Что происходит с совместимостью при изменении класса между версиями?

Совместимость сериализации между версиями класса определяется в первую очередь `serialVersionUID`. Если идентификатор совпадает, JVM пытается сопоставить поля старой и новой версии: новые поля получат значения по умолчанию, удалённые поля будут проигнорированы. Если `serialVersionUID` отличается, десериализация завершается `InvalidClassException`.

Поэтому для долгоживущих форматов важно явно задавать `serialVersionUID` и осознанно управлять эволюцией модели. Критичные изменения структуры лучше делать через миграционные адаптеры, либо переходить на более управляемые форматы (JSON/Proto) с версионированием схем.

## Q14. Как использовать custom `writeObject`/`readObject` безопасно?

Кастомные методы `writeObject`/`readObject` нужны, когда требуется особая логика сериализации: шифрование части данных, вычисляемые поля, контроль инвариантов. Внутри `readObject` важно валидировать данные после чтения, иначе можно восстановить объект в некорректном или небезопасном состоянии.

Безопасная практика: вызывать `defaultWriteObject`/`defaultReadObject`, затем делать строгую проверку полей (диапазоны, nullability, бизнес-ограничения). При нарушении инвариантов бросать `InvalidObjectException` и не допускать использования частично восстановленного объекта.

## Q15. Почему в микросервисах обычно избегают Java Serialization?

Стандартная Java Serialization даёт сильную связность между сервисами на уровне JVM-моделей и версии классов. Это усложняет совместимость между языками и командами, увеличивает риск несовместимых изменений и проблем при rolling-deploy. Кроме того, формат бинарный и слабо наблюдаемый: сложнее дебажить и анализировать трафик.

С точки зрения безопасности у нативной десериализации исторически высокий риск gadget-цепочек при приёме недоверенных данных. Поэтому в микросервисах чаще выбирают JSON, Protobuf или Avro: прозрачные схемы, межъязыковая совместимость и более управляемая эволюция контрактов.
