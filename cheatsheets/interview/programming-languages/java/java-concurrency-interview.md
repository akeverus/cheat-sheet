## Q1. (!) В чем разница между `Process` и `Thread`? Что такое `Context Switching`?

Процесс (`Process`) — это экземпляр выполняющейся программы, имеющий собственное адресное пространство, файлы, память и другие системные ресурсы.

Поток (`Thread`) — это выполнение инструкций в рамках процесса. Один процесс может иметь несколько потоков, каждый с собственным счётчиком команд, стеком вызова и сведениями о состоянии.

Контекстное переключение (`Context Switching`) — это процесс переключения выполнения между различными потоками в рамках процесса. Оно происходит, когда исполнение одного потока приостанавливается в пользу выполнения другого потока. В этот момент операционная система сохраняет состояние текущего потока, а затем загружает состояние следующего потока для выполнения.

Контекстное переключение может иметь некоторую накладную нагрузку, так как требуется сохранение и восстановление состояния потоков, что может занимать время. Однако контекстное переключение необходимо для равномерного распределения процессорного времени между потоками, обеспечивая многозадачность в рамках процесса.

## Q2. Как создать `Thread` и запустить его?

Чтобы создать экземпляр потока, есть два варианта. Передайте экземпляр `Runnable` конструктору и вызовите `start()`. `Runnable` — функциональный интерфейс, поэтому его можно передать как лямбда-выражение:

```java
Thread thread1 = new Thread(() -> System.out.println("Hello World!"));
thread1.start();
```

`Thread` также реализует `Runnable`, поэтому другой способ — создать анонимный подкласс, переопределить метод `run()` и вызвать `start()`:

```java
Thread thread2 = new Thread() {
    @Override
    public void run() {
        System.out.println("Hello World from subclass!");
    }
};
thread2.start();
```

## Q3.  Как явно определить `Stack Size` для `Thread`?

Класс `Thread` определяет следующий конструктор, с помощью которого мы можем явно определить размер стека для нового потока.

Влияние параметра `stackSize`, если таковое имеется, сильно зависит от платформы. На некоторых платформах более высокое значение размера стека может позволить большую глубину [рекурсии](https://docs.oracle.com/javase/specs/jvms/se17/html/jvms-2.html#jvms-2.6) перед броском `StackOverflowError`, а на других платформах это может вообще не иметь никакого эффекта.

```java
new Thread(ThreadGroup group, Runnable target, String name, long stackSize);
```

## Q4. (!) Какие состояния есть у Thread?

В `Java` потоки имеют следующие основные состояния, определенные в перечислении `Thread.State`:

1. `NEW` (НОВЫЙ): Поток создан, но еще не запущен.
2. `RUNNABLE` (ВЫПОЛНЯЕМЫЙ): Поток готов к выполнению и может быть выбран планировщиком для исполнения.
3. `BLOCKED` (БЛОКИРОВАН): Поток ожидает блокировки для доступа к разделяемому ресурсу (например, при вызове synchronized метода, если монитор уже захвачен другим потоком).
4. `WAITING` (ОЖИДАЕТ): Поток ожидает, пока не будет вызван метод `notify()`, `notifyAll()` или `join()`. Также возникает при вызове `Object.wait()`.
5. TIMED_WAITING (ОЖИДАЕТ НА ВРЕМЯ): Аналогично `WAITING`, но с ограниченным временем ожидания (например, при вызове `Thread.sleep()` или `Object.wait(timeout)`).
6. `TERMINATED` (ЗАВЕРШЕН): Поток завершил свое выполнение.

Переходы между состояниями: `NEW` -> `RUNNABLE` при вызове start(), `RUNNABLE` -> `BLOCKED` при ожидании блокировки, `RUNNABLE` -> `WAITING / RUNNABLE` -> `TERMINATED` при завершении метода run(). Переходы осуществляются планировщиком потоков `Java` и зависят от доступности ресурсов, блокировок и ожиданий.

## Q5. (!) Можем ли мы переопределить `Thread.start()`?

Да, можно переопределить метод `Thread.start()`, но переопределенный метод будет выполняться как обычный вызов метода только основным потоком. Он не создаст новый поток, как метод start() по умолчанию.

```java
class ChildThread extends Thread {
    public void start() {
        System.out.println("Overriding start() method in ChildThread");
    }

    public void run() {
        System.out.println("ChildThread run() method");
    }
}

ChildThread childThread = new ChildThread();
childThread.start();
// Вывод: Overriding start() method in ChildThread
// Метод run() не выполняется
```

Чтобы инициализировать новый поток, нужно вызвать `super.start()` из дочернего потока:

```java
public void start() {
    System.out.println("Overriding start() method in ChildThread");
    super.start(); // Вызов родительского метода для создания потока
}
// Вывод: Overriding start() method in ChildThread
//        ChildThread run() method
```

## Q6. (!) Что, если мы не переопределим метод run()?

Если не переопределить метод run() в расширенном классе, будет выполнен метод `Thread.run()` по умолчанию с пустым телом. Будет создан и выполнен новый поток, который ничего не делает.

```java
class SubTask extends Thread { }

SubTask subtask = new SubTask();
subtask.start(); // Поток создан, но ничего не выполняется
```

## Q7. (!) Что такое `Thread Priority`? Каков `Thread Priority` по умолчанию?

Приоритет потока — целое число от 1 до 10, присваиваемое каждому потоку в `JVM`. Используется планировщиком потока при выделении процессорного времени. Потоки с более высоким приоритетом получают больше шансов на выполнение.

Приоритет по умолчанию для любого потока наследуется от родительского потока. Поскольку приоритет основного потока по умолчанию равен 5, все дочерние потоки будут иметь приоритет по умолчанию 5.

```java
System.out.println(Thread.currentThread().getPriority()); // 5

Thread.currentThread().setPriority(10);
MyThread thread = new MyThread();
thread.start();
System.out.println(thread.getPriority()); // 10 (наследуется от родителя)
```

Класс `Thread` определяет 3 константы для представления приоритетов:

```java
Thread.MIN_PRIORITY = 1;
Thread.NORM_PRIORITY = 5;
Thread.MAX_PRIORITY = 10;
```

## Q8. (!) Что такое политика справедливости?

Политика справедливости (или "fairness policy") в контексте планировщика потоков относится к способу, которым
выбираются потоки для выполнения из группы готовых к выполнению потоков.

В общем случае, планировщик может использовать разные политики справедливости для разных целей. Некоторые из
распространенных политик справедливости включают в себя:

1. Первым пришел, первым обслужен (`First-Come`, `First-Served`): В этой политике потоки выбираются для выполнения в том
   порядке, в котором они становятся готовыми к выполнению. Потоки рассматриваются в порядке их поступления и каждый
   поток продолжает выполняться до тех пор, пока не закончит свое выполнение или не будет заблокирован. Эта политика не
   гарантирует справедливое распределение ресурсов и может приводить к явлению "ограничения червя".
2. Круговой алгоритм (`Round Robin`): Эта политика работает по принципу "каждый поток получает равный квант времени для
   выполнения, по очереди". Каждый поток выбирается для выполнения последовательно, присваивается квант времени и
   продолжает выполняться до истечения этого времени или до тех пор, пока не будет заблокирован. Затем выбирается
   следующий поток и процесс повторяется. Этот подход обеспечивает более равномерную загрузку, но может негативно влиять
   на время отклика некоторых потоков.
3. Приоритетная политика (`Priority-based`): Каждому потоку назначается приоритет, который определяет порядок выполнения.
   Потоки с более высоким приоритетом получают больше времени для выполнения по сравнению с потоками с более низким
   приоритетом. Однако следует отметить, что приоритет никогда не гарантирует непрерывное выполнение и может приводить к
   голоданию потоков с более низким приоритетом.

Это лишь некоторые из возможных политик справедливости, которые могут использоваться планировщиками потоков. Выбор
конкретной политики зависит от приложения, требований к отзывчивости, приоритетов и других факторов, которые могут быть
уникальными для каждого случая использования.

## Q9. (!) В чем разница между `Runnable` и `Callable` интерфейсами? Как они используются?

Разница между интерфейсами `Runnable` и `Callable` заключается в следующем:

1. `Runnable`: Это функциональный интерфейс в `Java`, предназначенный для выполнения кода в отдельном потоке. Он
   объявляет единственный метод `run()`, который не возвращает результат и не выбрасывает исключение. Вместо этого
   код, который должен быть выполнен, должен быть помещен в метод run().

Пример использования `Runnable`:

```java
Runnable myRunnable = () -> System.out.println("Running");
Thread thread = new Thread(myRunnable);
thread.start();
```

2. `Callable`: Это также функциональный интерфейс в `Java`, который похож на `Runnable`, но имеет некоторые отличия.
   Он объявляет единственный метод `call()`, который возвращает результат вызова и может выбрасывать исключение. `Callable` предоставляет более мощный способ выполнения кода в отдельном потоке и получения результата.

Пример использования `Callable`:

```java
Callable<Integer> myCallable = new Callable<Integer>() {
    @Override
    public Integer call() throws Exception {
        return 42;
    }
};

ExecutorService executor = Executors.newSingleThreadExecutor();
Future<Integer> future = executor.submit(myCallable);
Integer result = future.get();
executor.shutdown();
```

Как видно из примеров, `Runnable` используется с помощью класса `Thread`, который выполняет код в отдельном потоке,
без возможности получения результатов. `Callable`, с другой стороны, используется с `ExecutorService` и `Future`,
что позволяет получить результат выполнения и контролировать потоки более гибко.

Использование `Runnable` или `Callable` зависит от требований вашего приложения. Если вам необходим только запуск
кода в отдельном потоке без получения результата, используйте `Runnable`. А если вам нужно получить результат
выполнения или контролировать потоки более гибко, используйте `Callable`.

## Q10. (!) Что такое `Daemon Thread`, каковы варианты его использования? Как создать `Daemon Thread`?

`Daemon Thread` (демонический поток) в `Java` — это поток, который выполняется на фоне без препятствия остановки
основного процесса. Он предназначен для обслуживания других потоков или выполнения фоновых задач, которые не должны
предотвращать завершение программы.

Особенности `Daemon Thread`:

1. Жизненный цикл демонического потока зависит от основного процесса. Когда все потоки, не являющиеся демоническими,
   завершили свое выполнение, `JVM` автоматически завершает демонический поток, не дожидаясь его завершения.
2. Демонический поток не должен выполнять важные задачи, так как его выполнение может быть прервано в любой момент. Варианты использования демонического потока:

1. Фоновая задача: Демонический поток может быть использован для выполнения фоновых задач, таких как автоматическая
   очистка, сбор статистики и т.д. Это особенно удобно в ситуациях, когда непрерывное выполнение задачи не требуется или
   она зависит от других потоков.
2. Ожидание других потоков: Демонический поток может быть использован для ожидания завершения других потоков в
   приложении. Например, если у вас есть главный поток, который должен дождаться, чтобы все дочерние потоки завершились,
   то вы можете сделать главный поток демоническим и просто запустить все дочерние потоки. Создание демонического потока:

```java
Thread daemonThread = new Thread(() -> {
    // Фоновая задача
});
daemonThread.setDaemon(true);
daemonThread.start();
```

Важно: флаг `setDaemon(true)` должен быть установлен до запуска потока `start()`.

## Q11. (!) Что такое `ThreadGroup` и его назначение? Что такое `ThreadGroup` по умолчанию?

`ThreadGroup` в `Java` — это группа связанных потоков, которые могут быть организованы в хранилища. Он представляет
собой удобный способ управления группами потоков и обеспечивает некоторые дополнительные возможности.

Назначение `ThreadGroup`:

1. Управление потоками: `ThreadGroup` позволяет логически группировать потоки и управлять ими как единую сущность.
   Например, вы можете одновременно приостановить или возобновить все потоки в группе или установить приоритет для всех
   потоков в группе.
2. Обработка исключений: `ThreadGroup` позволяет определить обработчик исключений для всех потоков в группе. Это
   позволяет централизованно обрабатывать исключения, возникающие в потоках группы.
3. Проверка активности потоков: `ThreadGroup` предоставляет методы для проверки активности потоков в группе. Это полезно
   для определения состояния и выполнения потоков в группе. `ThreadGroup` по умолчанию:

Когда поток создается без явной указанной `ThreadGroup`, он добавляется в `ThreadGroup`, связанный с потоком, вызвавшим
его создание. Этот `ThreadGroup` по умолчанию имеет имя "main". Потоки, созданные в методе main(), будут
принадлежать к этой группе, если им не была явно указана другая `ThreadGroup`.

## Q12. (!) Что такое флаг `interrupt()`, `isInterrupted()`, `InterruptedException`?

Флаг прерывания потока это булева переменная, которая указывает, должен ли поток быть прерван. Он используется для
выхода из бесконечных циклов и выполнения завершающих действий, когда поток получает сигнал о прерывании.

1. Установка флага прерывания потока:

Флаг прерывания потока можно установить с помощью метода interrupt() класса `Thread`:

```java
Thread myThread = ...;
myThread.interrupt();
```

Проверка флага прерывания потока выполняется с помощью метода `isInterrupted()` или статического метода `Thread.interrupted()`. Второй метод также сбрасывает флаг прерывания при проверке:

```java
if (Thread.currentThread().isInterrupted()) {
    // Поток был прерван
}

// или

if (Thread.interrupted()) {
    // Поток был прерван, флаг сброшен
}
```

Когда метод потока вызывает метод, который может генерировать `InterruptedException` (например, `Thread.sleep()`, `Object.wait()`, `BlockingQueue.put()`), метод должен обработать это исключение. Если во время блокировки потока поступает сигнал о прерывании, выбрасывается `InterruptedException`:

```java
Thread myThread = Thread.currentThread();
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    myThread.interrupt(); // Восстанавливаем флаг прерывания
}
```

## Q13. (!) Что такое `Java Memory Model` (`JMM`)?

`Java Memory Model` (`JMM`) — спецификация, описывающая, как виртуальная машина `Java` (`JVM`) управляет памятью и
взаимодействием между потоками в многопоточной среде. Основная цель `JMM` — обеспечить предсказуемое и корректное
выполнение многопоточных программ. Основные идеи `JMM`:

1. Гарантии примитивов синхронизации: `JMM` определяет, как потоки взаимодействуют с переменными и объектами при
   использовании примитивов синхронизации, таких как synchronized блоки, volatile переменные, атомарные операции и
   другие конструкции. Она определяет, как гарантируется порядок чтения и записи в память и какие виды взаимодействия
   между потоками являются видимыми.
2. Порядок выполнения операций: `JMM` определяет правила упорядочивания операций в разных потоках. Это обеспечивает
   последовательность операций, которая является согласованной относительно других потоков, учитывая различные
   оптимизации и переупорядочивания, выполняемые `JVM`.
3. Видимость изменений: `JMM` определяет, когда изменения, внесенные одним потоком, становятся видимыми другим потокам.
   Это включает в себя обеспечение прямой и специальной видимости для чтения и записи переменных.
4. Барьеры памяти: `JMM` предоставляет контроль над потоками через использование барьеров памяти. Барьеры памяти
   определяют точки синхронизации и влияют на операции чтения и записи, гарантируя определенное упорядочивание и
   видимость.

Вместе эти идеи `JMM` обеспечивают правильное взаимодействие между потоками и предоставляют механизмы для безопасного
и корректного выполнения многопоточных программ.

## Q14. (!) Что такое volatile поле? Что `JMM` гарантирует для volatile полей?

`Volatile` поле — это переменная, помеченная ключевым словом volatile в языке `Java`. Когда поле объявляется как
volatile, гарантируется, что все потоки будут видеть последние записанные значения этого поля.

`JMM` (`Java Memory Model`) гарантирует следующее для volatile полей:

1. Порядок записи и чтения: Когда один поток записывает значение в volatile поле, это значение будет видимо другим
   потокам, которые выполняют чтение этого поля. `JMM` гарантирует, что запись в volatile поле произойдет до
   чтения других полей после этой записи.
2. Видимость изменений: Когда поток выполняет чтение volatile поля, он гарантированно получает самое последнее
   записанное значение этого поля, даже если другие потоки записывают в это поле. Это гарантирует, что изменения,
   внесенные одним потоком, станут видимыми другим потокам.
3. Запрет переупорядочивания: `JMM` гарантирует, что операции чтения и записи volatile поля не будут
   переупорядочены с другими операциями чтения и записи вокруг него. Это гарантирует, что промежуточные значения volatile поля не будут видны другим потокам.
4. Операция "`happens-before`": Чтение volatile поля установит соответствующую связь "`happens-before`" с последующей
   записью в это поле. Это означает, что все изменения, выполненные потоком до записи в volatile поле, становятся
   видимыми после чтения этого поля другим потокам.

В целом, использование volatile полей в `Java` позволяет обеспечить более надежную и консистентную синхронизацию и
взаимодействие между потоками.

## Q15. (!) Какие специальные гарантии дает `JMM` для final полей класса?

`JMM` (`Java Memory Model`) предоставляет специальные гарантии для final полей класса. Эти гарантии характеризуются
следующими особенностями:

1. Видимость инициализации: `JMM` гарантирует, что инициализация final поля в одном потоке будет видна другим
   потокам. После инициализации значения final поля, другие потоки увидят это значение без какой-либо синхронизации.
2. Порядок инициализации: `JMM` гарантирует, что инициализация final поля произойдет до любых операций чтения и
   записи, которые появляются после инициализации final поля в том же потоке. Это гарантирует, что изменения,
   внесенные в поля перед использованием final поля, будут видны во всех потоках после его инициализации.
3. Запрет переупорядочивания: `JMM` не допускает переупорядочивания операций чтения и записи над final полем с
   другими операциями чтения и записи, которые появляются до и после его использования. Это предотвращает случайное
   чтение или запись в final поле в неправильном порядке.
   4."`Final`-перед" и "`Final`-после" отношение: `JMM` устанавливает связь "`Final`-перед" (`final-before`) и "
   `Final`-после" (`final-after`) между операциями чтения и записи, предшествующими и следующими за чтением final
   поля. Это означает, что все изменения, выполненные перед записью в final поле, становятся видимыми после чтения
   этого поля.

Эти специальные гарантии `JMM` для final полей обеспечивают безопасность и надежность использования final
полей в `Java`, особенно в многопоточных средах.

## Q16. (!) Что такое потокобезопасный класс?

Термин [безопасность потоков](https://docs.oracle.com/javase/tutorial/essential/concurrency/threadsafe.html) означает, что
разные потоки могут обращаться к одному и тому же ресурсу без выявления ошибочного поведения или получения
непредсказуемых результатов.

Чтобы сделать потокобезопасным весь класс, мы должны гарантировать, что внутреннее состояние экземпляра доступно и
изменяется только одним потоком за раз. В `Java` есть несколько классов, которые уже являются потокобезопасными.
Например:

1. `StringBuffer`
2. `Stack`
3. `Vector`
4. `Hashtable`
5. `Properties`

Мы также можем создать собственный класс потоков. Среди них есть несколько способов достижения потокобезопасности в
нашем классе, некоторые из них перечислены ниже.

1. Использование synchronized
2. Использование keyword
3. Использование `Atomic` классов
4. Использование final переменных (иммутабельных)
5. Использование `ThreadLocal` переменных
6. Использование `Reentrant Lock`

Пример: кинотеатр с 4 стойками для бронирования и 6 клиентами, каждый пытается забронировать 2 билета:

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class MovieTicketBooking {
    private final int totalSeat = 10;
    private int lastBookedSeat = 0;

    public synchronized String book(int numberOfSeats) {
        if (lastBookedSeat == totalSeat) {
            return "House Full! " + Thread.currentThread().getName();
        } else if (lastBookedSeat + numberOfSeats > totalSeat) {
            return "Enough Seats Not Available " + Thread.currentThread().getName();
        } else {
            int start = lastBookedSeat + 1;
            lastBookedSeat += numberOfSeats;
            return start + " to " + lastBookedSeat + " Seats Booked " + Thread.currentThread().getName();
        }
    }
}

ExecutorService threadPool = Executors.newFixedThreadPool(4);
MovieTicketBooking booking = new MovieTicketBooking();
for (int i = 0; i < 6; i++) {
    threadPool.submit(() -> System.out.println(booking.book(2)));
}
threadPool.shutdown();
```

Вывод (может быть разным в каждом прогоне):

1 to 2 Seats Booked pool-1-thread-1

7 to 8 Seats Booked pool-1-thread-2

5 to 6 Seats Booked pool-1-thread-3

3 to 4 Seats Booked pool-1-thread-4

9 to 10 Seats Booked pool-1-thread-4

House Full! pool-1-thread-4

В приведённом выше примере `MovieTicketBooking` — это потокобезопасный класс, поскольку каждое поле является закрытым, а метод также синхронизирован. Если мы удалим ключевое слово `synchronized` из объявления метода, мы получим непредсказуемые результаты.

## Q17. (!) Что такое `Atomic Operation`?

`Atomic Operation` — это операция, которая выполняется неделимым образом, то есть либо полностью, либо не выполняется вообще. Она представляет собой операцию, которая гарантирует, что другие потоки не смогут видеть промежуточные или неполные результаты выполнения этой операции.

`Atomic Operation` обычно используется для обеспечения безопасности и согласованности при выполнении операций над общими данными или ресурсами в многопоточной среде. Он гарантирует, что только один поток может активно выполнять операцию, и другие потоки должны ждать, пока операция не будет полностью выполнена.

В `Java` пакет `java.util.concurrent.atomic` предоставляет классы для выполнения атомарных операций, такие как `AtomicInteger`, `AtomicLong`, `AtomicBoolean` и т. д. Эти классы предлагают методы для выполнения атомарных операций, таких как инкремент, декремент, установка значения и проверка на равенство. Это позволяет гарантировать, что операции будут выполнены неделимо и без гонок данных.

Использование атомарных операций может повысить производительность и безопасность в многопоточном окружении, так как нет необходимости в явной синхронизации через блокировки или ключевое слово `synchronized`.

## Q18. (!) Что такое `Atomic Classes`?

`Atomic Classes` это классы из пакета `java.util.concurrent.atomic`, предоставляющие атомарные операции для манипуляции с общими данными в многопоточной среде. Они предлагают набор методов, которые гарантируют выполнение операций неделимо и без возникновения состояния гонки данных.

Атомарные классы обеспечивают безопасность и корректность операций, когда множество потоков пытается одновременно обновлять или читать одни и те же данные. Это достигается путем использования низкоуровневых атомарных операций (как правило, использующих **Compare-and-Swap** или **Load-Linked / Store-Conditional** инструкции процессора), которые позволяют гарантировать целостность данных во время выполнения операции.Некоторые атомарные классы включают:

1. `AtomicBoolean`: Предоставляет атомарные операции обновления и чтения для типа boolean.
2. `AtomicInteger`, `AtomicLong`: Предоставляют атомарные операции обновления и чтения для соответствующих примитивных типов int и long.
3. `AtomicReference`: Предоставляет атомарные операции обновления и чтения для ссылочных типов.
4. `AtomicIntegerArray`, `AtomicLongArray`, `AtomicReferenceArray`: Предоставляют атомарные операции обновления и чтения для соответствующих массивов примитивных типов и ссылочных типов.

Использование атомарных классов позволяет избежать явной синхронизации, такой как использование блокировок или ключевого слова synchronized, что может привести к повышению производительности и обеспечению корректной работы в многопоточной среде.

## Q19. (!) Что такое synchronized блок, метод и инструкция?

Итак, synchronized блок, метод и инструкция — это механизмы в `Java`, предназначенные для обеспечения синхронизации доступа к общим данным в многопоточной среде.

1. synchronized блок: Это конструкция, которая позволяет указать блок кода, доступ к которому одновременно может иметь только один поток. Он использует монитор объекта в качестве ключа синхронизации. При выполнении synchronized блока один поток захватывает монитор объекта, выполняет соответствующий блок кода, а затем освобождает монитор, позволяя другим потокам получить доступ к блоку кода.Пример использования synchronized блока:

```java
synchronized (monitorObject) {
    // Критическая секция
}
```

synchronized метод: Метод, объявленный с ключевым словом `synchronized`. Монитором синхронизации является текущий экземпляр объекта (для экземплярных методов) или класс (для статических методов). Только один поток может выполнять `synchronized` метод для данного объекта или класса в определенный момент времени:

```java
public synchronized void synchronizedMethod() {
    // Критическая секция
}
```

synchronized инструкция — то же самое, что и synchronized блок (синтаксически идентичны).

`synchronized` конструкции обеспечивают синхронизацию доступа к общим данным и предотвращают состояние гонки при параллельном выполнении потоков. Они обеспечивают сериализацию доступа и гарантируют, что критические секции кода будут выполняться атомарно, тем самым предотвращая некорректное состояние объектов из-за несогласованности операций в разных потоках.

## Q20. (!) В чем преимущество synchronized блока перед synchronized методом?

Преимущество synchronized блока перед synchronized методом заключается в более гибком управлении синхронизацией.

1. Гибкость: synchronized блок позволяет указать только необходимую часть кода, которая требует синхронизации. Остальная часть кода может выполняться параллельно другим потокам, что сокращает накладные расходы и улучшает производительность.

2. Гранулярность синхронизации: Можно точно контролировать, какие объекты используются в качестве мониторов синхронизации. Это позволяет синхронизировать только на минимально необходимых объектах, уменьшая вероятность блокировок и улучшая масштабируемость.

3. Взаимодействие с другими объектами: Позволяет свободно взаимодействовать с другими объектами без блокировок, так как только участок кода внутри блока синхронизирован.

synchronized метод может быть проще в использовании, когда синхронизация требуется для всего метода, и в некоторых случаях может быть немного быстрее блока.

## Q21. (!) Если два потока одновременно вызывают synchronized метод для разных экземпляров объекта, может ли один из этих потоков заблокироваться? Что делать, если метод статический?

Если два потока одновременно вызывают synchronized метод для разных экземпляров объекта, они не будут блокироваться друг другом. Каждый поток имеет свой собственный монитор объекта для синхронизации.

Когда метод является статическим (static), синхронизация происходит на уровне класса, а не на уровне объекта. synchronized статический метод использует монитор на уровне класса. Если два потока вызывают synchronized статический метод, они будут блокироваться друг другом, так как используют один и тот же монитор класса, независимо от того, для каких объектов вызывается метод.

Если синхронизированный метод (экземплярный или статический) вызывается для одного и того же объекта/класса, другие потоки будут ждать, пока текущий поток не выполнит метод и освободит монитор.

Для более гибкого управления блокировками можно использовать `ReentrantLock`.

## Q22. (!) В чем разница между блокировкой на уровне класса и блокировкой на уровне объекта?

Разница между блокировкой на уровне класса и блокировкой на уровне объекта заключается в том, как они действуют и на каком уровне происходит синхронизация.

1. Блокировка на уровне объекта:
 1. Применяется к экземплярам объектов.
 2. Обеспечивает синхронизацию только между потоками, работающими с одним и тем же экземпляром объекта.
 3. Когда поток получает блокировку на уровне объекта, он захватывает монитор данного объекта и становится единственным потоком, который может выполнять синхронизированные операции с этим объектом.
 4. Другие потоки, которые пытаются получить блокировку на уровне объекта для того же самого объекта, должны ждать, пока блокировка не будет освобождена.
2. Блокировка на уровне класса:
 1. Применяется к классу в целом, а не к конкретному экземпляру объекта.
 2. Обеспечивает синхронизацию между потоками для всех экземпляров данного класса.
 3. Когда поток получает блокировку на уровне класса, он захватывает монитор этого класса и становится единственным потоком, который может выполнять синхронизированные операции с любыми экземплярами этого класса.
 4. Другие потоки, которые пытаются получить блокировку на уровне класса для того же самого класса, должны ждать, пока блокировка не будет освобождена.

Важно отметить, что блокировка на уровне класса имеет глобальный эффект на все экземпляры данного класса, в то время как блокировка на уровне объекта ограничена конкретным экземпляром объекта.

Выбор между блокировкой на уровне класса и блокировкой на уровне объекта зависит от требований и контекста приложения. Оба подхода имеют свои сильные и слабые стороны, и правильное использование зависит от конкретной ситуации и потребностей многопоточности.

## Q23. (!) Почему мы не можем объявить synchronized метод abstract?

Мы не можем объявить synchronized метод абстрактным потому, что в интерфейсах нельзя определить реализацию метода.

Когда метод объявлен как abstract, это означает, что он не имеет реализации в самом классе или интерфейсе, в котором он объявлен. Вместо этого, классы, наследующие абстрактный класс или реализующие интерфейс, должны предоставить свою собственную реализацию для абстрактных методов.

Синхронизация с использованием ключевого слова synchronized требует наличия монитора объекта или класса, которым можно блокировать доступ к методу для параллельных потоков. Однако при объявлении абстрактного метода в интерфейсе неизвестно, какой объект или класс будет использоваться для синхронизации, так как реализация метода будет предоставлена в производном классе или интерфейсе.

Таким образом, объявление synchronized метода abstract не имеет смысла, потому что невозможно предоставить конкретную реализацию синхронизации для метода в интерфейсе, где нет доступа к монитору объекта или класса.

## Q24. (!) Какова цель методов wait(), notify() и `notifyAll()`?

Методы wait(), notify() и `notifyAll()` используются для управления потоками и обеспечения синхронизации между ними.

wait(): Вызывается на объекте, чей монитор должен быть захвачен. Поток освобождает монитор объекта и переходит в состояние ожидания до тех пор, пока другой поток не вызовет notify() или `notifyAll()` для этого объекта. Может быть вызван с параметром времени ожидания.

notify(): Будит один из потоков, находящихся в состоянии ожидания на этом объекте. Какой именно поток будет разбужен, не определено.

`notifyAll()`: Будит все потоки, находящиеся в состоянии ожидания на этом объекте. После вызова notify() или `notifyAll()` поток, освободивший монитор, продолжит работу и только потом другие потоки могут продолжить выполнение.

Используются для реализации паттерна "`Producer-Consumer`" и других многопоточных сценариев, где потокам требуется взаимодействовать и синхронизировать свои действия.

## Q25. (!) В чем разница между notify() и `notifyAll()`?

Разница между методами notify() и `notifyAll()` заключается в том, как они будят потоки, находящиеся в состоянии ожидания на объекте.

1. Метод notify():
 1. Вызов метода notify() разбужит один из потоков, находящихся в состоянии ожидания на объекте.
 2. Какой именно поток будет разбужен, не определено. Это зависит от планировщика потоков операционной системы.
 3. Если на объекте находится несколько потоков в состоянии ожидания, и метод notify() был вызван, то разбудится только один из этих потоков.
2. Метод `notifyAll()`:
 1. Вызов метода `notifyAll()` разбудит все потоки, находящиеся в состоянии ожидания на объекте.
 2. Каждый поток будет разбужен из состояния ожидания и будет конкурировать за захватить монитор объекта.
 3. Если на объекте находится несколько потоков в состоянии ожидания, и метод `notifyAll()` был вызван, то все эти потоки будут разбужены.

Таким образом, основная разница между notify() и `notifyAll()` заключается в том, сколько потоков будет разбужено из состояния ожидания. Если требуется разбудить только один поток, обычно используется notify(). Если же необходимо разбудить все потоки, находящиеся в состоянии ожидания, то следует использовать `notifyAll()`. Выбор метода зависит от специфики сценария и требований к взаимодействию потоков.

## Q26. (!) В чем разница между yield(), join() и sleep()?

Разница между методами yield(), join() и sleep() заключается в их функциях и поведении в отношении потоков.

1. Метод yield():
 1. Метод yield() вызывается потоком, чтобы предоставить возможность другим потокам с меньшим приоритетом запуститься.
 2. Если других потоков с меньшим приоритетом нет или они уже выполняются, то этот метод может быть проигнорирован.
 3. Другими словами, метод yield() указывает планировщику потоков операционной системы, что текущий поток готов уступить возможность выполнения другим потокам, имеющим более высокий приоритет.
2. Метод join():
 1. Метод join() позволяет одному потоку дождаться завершения другого потока перед тем, как продолжить свою работу.
 2. Когда поток вызывает метод join() на другом потоке, он приостанавливается до тех пор, пока другой поток не завершится.
 3. Это полезно в ситуациях, когда нужно дождаться результатов выполнения другого потока, прежде чем продолжить выполнение текущего потока.
3. Метод sleep():
 1. Метод sleep() вызывается потоком, чтобы временно приостановить свое выполнение на заданный промежуток времени.
 2. После истечения указанного времени поток возобновит свое выполнение и будет готов к выполнению.
3. Метод `sleep()` полезен, если требуется создать паузу в выполнении потока или добавить задержку перед выполнением каких-либо действий.

Таким образом, основная разница между yield(), join() и sleep() заключается в их особенностях и предназначении. Метод yield() позволяет передать возможность выполнения другим потокам, метод join() позволяет дождаться завершения потока, а метод sleep() предоставляет возможность временной задержки выполнения потока.

## Q27. (!) Что такое `Deadlock` и основная причина `Deadlock`?

`Deadlock` (взаимная блокировка) это ситуация, когда два или более потока взаимодействуют между собой и блокируют ресурсы, необходимые для продолжения своей работы. Каждый из потоков ожидает ресурс, который удерживает другой поток, тем самым вызывая блокировку или защаду ресурсов.

Основная причина `Deadlock` это нарушение порядка захвата ресурсов и возникновение циклической ситуации, в которой каждый поток ожидает того, что будет освобождено другим потоком, прежде чем сам продолжит работу.

Чтобы возникла `Deadlock`, должны быть выполнены следующие условия, называемые "четырьмя условиями необходимости":

1. Взаимная блокировка (`Mutual Exclusion`): Минимум два потока должны требовать эксклюзивного доступа к ресурсу, который не может быть одновременно использован несколькими потоками.
2. Удержание и ожидание (`Hold and Wait`): Поток удерживает какой-либо ресурс и ожидает освобождения другого ресурса, удерживаемого другим потоком.
3. Нет прерывания (No `Preemption`): Ресурсы не могут быть изымаемы или прерываться у одного потока и передаваться другому потоку.
4. Взаимная ожидание (`Circular Wait`): Существует циклическая зависимость относительно ресурсов, где один поток ожидает ресурс, который контролируется другим потоком, а последний поток ожидает ресурс, который контролируется первым потоком.

Для предотвращения `Deadlock` важно соблюдать порядок захвата ресурсов, избегать взаимной блокировки и использовать алгоритмы управления ресурсами, такие как иерархическая блокировка и выделение ресурсов по запросу (resource `alloCation` graph). Также можно применять принципы прерывания и ожидания без удержания ресурсов, чтобы избежать возникновения `Deadlock`.

## Q28. (!) В чем разница между `Deadlock`, `Livelock` и `Starvation`?

`Deadlock`, `Livelock` и `Starvation` это три различных концепции, связанных с проблемами синхронизации и планирования в многопоточном программировании. Вот их основные различия:

1. `Deadlock` (Взаимная блокировка):
 1. `Deadlock` возникает, когда два или более потока блокируют друг друга, ожидая ресурсы, которые контролируют другие потоки.
2. Это статическая ситуация, в которой ни один из потоков не может продолжить свое выполнение из-за блокировки ресурсов, на которые они ожидают обращение.
 3. Решение `Deadlock` требует снятия или предотвращения одного или нескольких условий взаимной блокировки.
2. `Livelock` (Живая блокировка):
 1. `Livelock` возникает, когда два или более потока активно выполняются, но не могут выполнить свою задачу, поскольку они генерируют действия в ответ на действия друг друга.
 2. Это динамичная ситуация, в которой потоки взаимодействуют между собой, создавая постоянный обмен сообщениями или изменяя свое состояние, чтобы обойти блокировку.
 3. Решение `Livelock` требует изменения алгоритма, чтобы избежать бесконечного обмена сообщениями или изменения состояния.
3. `Starvation` (Голодание):
 1. `Starvation` возникает, когда один или несколько потоков не получают доступ к ресурсам или возможности выполнения, которые им нужны для продолжения работы.
 2. Это могут быть вызвано приоритетами потоков или неправильным планированием, обусловленными одним или несколькими потоками, которые постоянно занимают ресурсы.
 3. Решение голодания требует справедливого распределения ресурсов, правильного управления очередью или использования приоритетов потоков.

Таким образом, различия между `Deadlock`, `Livelock` и `Starvation` связаны с их характером и последствиями. `Deadlock` это статическая блокировка потоков, `Livelock` это динамичная ситуация обмена сообщениями, а `Starvation` это блокировка ресурсов или возможности выполнения потоков.

## Q29. (!) Напишите программу для демонстрации `Deadlock`

Вот пример программы на языке `Java`, демонстрирующей `Deadlock`:

```java
public class DeadlockDemo {
    public static Object resource1 = new Object();
    public static Object resource2 = new Object();

    public static void main(String[] args) {
        Thread thread1 = new Thread(new Runnable() {
            public void run() {
                synchronized (resource1) {
                    System.out.println("Поток 1 захватил resource1");
                    try {
                        Thread.sleep(1000);
                    } catch (InterruptedException e) {}
                    synchronized (resource2) {
                        System.out.println("Поток 1 захватил resource2");
                    }
                }
            }
        });

        Thread thread2 = new Thread(new Runnable() {
            public void run() {
                synchronized (resource2) {
                    System.out.println("Поток 2 захватил resource2");
                    try {
                        Thread.sleep(1000);
                    } catch (InterruptedException e) {}
                    synchronized (resource1) {
                        System.out.println("Поток 2 захватил resource1");
                    }
                }
            }
        });

        thread1.start();
        thread2.start();
    }
}
```

В этом примере создаются два потока: thread1 и thread2. Каждый поток пытается последовательно захватить два
ресурса (resource1 и resource2). Однако порядок захвата ресурсов в каждом потоке противоположен, что приводит к
блокировке и взаимной блокировке потоков, что и является `Deadlock`.

При запуске этой программы вы увидите, что она вызывает `Deadlock` и не завершает свою работу, так как потоки
блокированы и ожидают освобождения ресурсов, удерживаемых другими потоками.

## Q30. (!) Что такое `Race Condition`? Как это найти и исправить?

`Race Condition` (состояние гонки) возникает в параллельных программных системах, когда результат выполнения программы
зависит от того, в каком порядке выполняются отдельные потоки или процессы. В результате, результат работы программы
может быть непредсказуемым или некорректным. `Race Condition` возникает, когда несколько потоков одновременно получают
доступ к общим данным и пытаются изменить их. Если эти изменения происходят без синхронизации, то результат может быть
непредсказуемым или некорректным.

Для обнаружения `Race Condition` можно использовать следующие методы:

1. Анализ кода: Анализируйте код программы в многопоточной среде и ищите места, где общие данные модифицируются без
   синхронизации. Обратите особое внимание на операции записи/чтения данных.
2. Использование инструментов исследования: Существуют различные инструменты, такие как статические анализаторы кода и
   инструменты динамической проверки, которые могут помочь обнаружить потенциальные состояния гонки в программе.
3. Тестирование: Создайте тестовые сценарии и наборы данных, которые максимально усиливают возможные состояния гонки.
   Запустите тесты и проверьте, возникают ли непредсказуемые или некорректные результаты.

Для исправления `Race Condition` следует использовать механизмы синхронизации, чтобы гарантировать правильное
выполнение параллельных операций. Некоторые из таких механизмов включают в себя:

1. Использование блокировок (мьютексов) для защиты общих данных.
2. Использование семафоров или мониторов для синхронизации доступа к общим ресурсам.
3. Использование потокобезопасных коллекций данных, если доступ к ним происходит одновременно из нескольких потоков.

Комбинирование правильно выбранных механизмов синхронизации с анализом и тестированием может помочь обнаружить и решить
проблемы состояний гонки.

## Q31. (!) Что такое `ForkJoinPool`?

`ForkJoinPool` — это реализация пула потоков в `Java`, которая оптимизирована для работы с рекурсивными задачами,
которые могут быть разделены на более мелкие задачи и выполняться параллельно. `ForkJoinPool` основан на парадигме "
разделяй и властвуй" (divide and conquer), где задача разбивается на более мелкие подзадачи, которые затем рекурсивно
решаются и объединяются в итоговый результат.

В отличие от обычного `ThreadPoolExecutor`, `ForkJoinPool` имеет дополнительные функции, которые позволяют эффективно
разделять и объединять подзадачи. Он поддерживает специальный тип задач, называемый `ForkJoinTask`, который может быть
разделен на подзадачи методом fork() и затем объединен методом join(). Кроме того, `ForkJoinPool` обладает
механизмом управления параллелизмом, который автоматически распределяет незавершенные задачи на доступные потоки в
пуле. `ForkJoinPool` предлагает высокую степень контроля над параллелизмом и распределением задач, что позволяет
эффективно выполнять рекурсивные задачи, такие как сортировка массива, расчет факториала, умножение матрицы и т. д.

Обычно `ForkJoinPool` используется там, где требуется выполнять большие объемы работы, которые могут быть разделены на
подзадачи и выполняться параллельно.

## Q32. (!)  Что такое `ThreadLocal`?

`ThreadLocal` — это класс в `Java`, который предоставляет возможность создать переменную, которая будет привязана к
каждому отдельному потоку. Это означает, что каждый поток будет иметь свою собственную копию этой переменной, и
изменения, внесенные одним потоком, не будут видны другим потокам.

Класс `ThreadLocal` позволяет обеспечить изоляцию и безопасность данных в многопоточной среде. Он полезен там, где
каждый поток должен иметь свое собственное состояние или контекст. Каждый поток может получить доступ к своей
собственной копии переменной, используя методы `get()` и `set()` объекта `ThreadLocal`.

Пример использования `ThreadLocal` может быть в приложении, где каждый поток выполняет операцию на базе данных, где
каждый поток должен иметь свое собственное подключение к базе данных. С использованием `ThreadLocal` можно хранить и
получать свою собственную копию подключения к базе данных для каждого потока, избегая конфликтов доступа и обеспечивая
безопасность данных.

Недостатком `ThreadLocal` является потенциальная опасность утечки памяти, поскольку переменные, привязанные к потокам,
могут продолжать существовать даже после завершения потока, если не будет правильно управлять их жизненным циклом или
очищать их по завершении потока. Поэтому важно правильно использовать и управлять объектами `ThreadLocal`, чтобы
избежать утечек памяти.

## Q33. (!) В чем разница между `ThreadLocal` и `InheritableThreadLocal`?

`ThreadLocal` и `InheritableThreadLocal` — это два класса в `Java`, которые предоставляют механизм хранения и
получения значений в контексте каждого потока. Они имеют разные поведения в отношении наследования значений при создании
новых потоков.

`ThreadLocal` позволяет каждому потоку иметь свою собственную копию переменной. При создании нового потока значение в
`ThreadLocal` не наследуется, и каждый поток получает свое собственное, изолированное значение. Это полезно, когда
требуется, чтобы каждый поток имел уникальное значение переменной.

`InheritableThreadLocal`, с другой стороны, позволяет наследовать значение переменной от родительского потока к
дочернему потоку. При создании нового потока значение в `InheritableThreadLocal` копируется из родительского потока в
дочерний поток. Это полезно, когда необходимо передать значение из родительского потока в дочерний поток, например, для
передачи контекстной информации.

Итак, основная разница между `ThreadLocal` и `InheritableThreadLocal` заключается в том, что `ThreadLocal` не
наследует значение от родительского потока, а `InheritableThreadLocal` позволяет наследовать и передавать значение от
родительского потока дочернему потоку. Выбор между ними зависит от требований конкретной ситуации и необходимости
передачи значений между потоками.

## Q34. (!) Что такое `Executor` и `ExecutorService`? Каковы различия между этими интерфейсами?

`Executor` и `ExecutorService` — это интерфейсы в `Java`, относящиеся к выполнению потоков. Они предоставляют
абстракцию для выполнения асинхронных задач.

Интерфейс `Executor` декларирует единственный метод `execute(Runnable)`, который принимает объект типа `Runnable` и
выполняет его в некотором потоке. `Executor` предоставляет базовую функциональность для выполнения задач, но не
предоставляет никаких средств для управления и контроля задач и пулом потоков.

Интерфейс `ExecutorService` является расширением интерфейса `Executor` и предоставляет дополнительные методы для
управления и контроля выполнения задач, а также для работы с пулом потоков. Он представляет собой простую очередь задач,
которые будут выполнены внутри пула потоков. `ExecutorService` позволяет отправлять задачи на выполнение и получать
объекты типа `Future`, которые представляют собой результат выполнения задачи и могут использоваться для контроля над
выполнением и получения результата.

Различия между `Executor` и `ExecutorService` заключаются в дополнительной функциональности, предоставленной
интерфейсом `ExecutorService`. `ExecutorService` позволяет управлять выполнением задач, такими как запуск и остановка
пула потоков, ожидание завершения задач, получение результатов выполнения и так далее. Он предлагает более высокий
уровень абстракции для работы с потоками и задачами.

## Q35. (!) Каковы доступные реализации `ExecutorService` в стандартной библиотеке?

В стандартной библиотеке `Java` доступны следующие реализации интерфейса `ExecutorService`:

1. `ThreadPoolExecutor`: Это наиболее часто используемая реализация `ExecutorService`. Позволяет создавать пул потоков с
   определенным количеством рабочих потоков и настраиваемыми параметрами, такими как размер пула, задержка перед
   запуском потоков и т. д.
2. `ScheduledThreadPoolExecutor`: Это реализация `ExecutorService` с возможностью планирования отложенного или
   периодического выполнения задач. Позволяет запускать задачи через определенные интервалы или с определенной
   задержкой.
3. `ForkJoinPool`: Это реализация `ExecutorService`, оптимизированная для задач, которые можно разделить на подзадачи и
   выполнить их параллельно. Он предоставляет механизм "разделяй и властвуй", который автоматически распределяет
   подзадачи между доступными потоками.
4. `CachedThreadPool`: Это реализация `ExecutorService`, которая динамически создает и уничтожает потоки в пуле в
   зависимости от нагрузки. Если в пуле нет свободных потоков, то он создает новые. Когда потоки не используются в
   течение определенного времени, они удаляются.
5. `SingleThreadExecutor`: Это реализация `ExecutorService`, которая запускает все задачи в единственном потоке.
   Гарантирует, что все задачи будут выполнены последовательно в порядке их поступления.

Каждая реализация `ExecutorService` имеет свои особенности и рекомендуется выбирать подходящую реализацию в
зависимости от требований и характера задач, которые требуется выполнять.

## Q36. (!) Разница между shutdown(), `shutdownNow()` и `awaitTermination`()

Все три метода `shutdown()`, `shutdownNow()` и `awaitTermination()` связаны с остановкой выполнения задач в `ExecutorService` и обеспечением корректного завершения его работы.

1. shutdown(): Этот метод запрещает принятие новых задач для выполнения, сохраняя при этом ожидающие задачи в очереди на
   выполнение. `ExecutorService` продолжает выполнять имеющиеся задачи и завершает работу, когда все задачи выполнены.
   Этот метод не останавливает выполнение немедленно, а просто предотвращает добавление новых задач.
2. `shutdownNow()`: Этот метод останавливает выполнение всех задач немедленно. Он пытается прекратить выполнение
   запущенных задач и прерывает все потоки, находящиеся в ожидании выполнения задач. Метод возвращает список задач,
   которые были запущены и еще не начали выполнение.
3. `awaitTermination(long timeout, TimeUnit unit)`: этот метод ожидает, пока все задачи `ExecutorService` не
   завершатся, либо пока не истечет указанный временной лимит. Он блокирует выполнение текущего потока до момента
   завершения всех задач или до достижения таймаута. Метод возвращает `true`, если все задачи завершились в указанный
   период времени, и `false`, если время истекло и все задачи не завершились.

Использование этих методов в сочетании позволяет корректно завершить работу `ExecutorService`. Сначала вызывается `shutdown()`, чтобы приостановить приём новых задач. Затем вызывается `awaitTermination()` с достаточно большим
временным лимитом, чтобы дождаться завершения всех задач. Если задачи не завершились за указанный таймаут, можно
вызвать `shutdownNow()`, чтобы немедленно остановить выполнение задач.

## Q37. (!) Разница между submit() и execute()

Методы submit() и execute() используются для отправки задач на выполнение в `ExecutorService`, но есть некоторые
различия в их поведении и возможностях.

1. `execute(Runnable task)`: этот метод принимает в качестве аргумента объект `Runnable` (или его подкласс) и
   немедленно отправляет его на выполнение в пул потоков `ExecutorService`. Данный метод не возвращает результат
   выполнения задачи.

```java
ExecutorService executor = Executors.newFixedThreadPool(10);
executor.execute(new MyTask());
```

1. `submit(Callable<T> task)`: этот метод принимает в качестве аргумента объект `Callable`<T> (или его подкласс),
   который представляет задачу, возвращающую результат. При отправке задачи на выполнение метод submit() возвращает
   объект типа `Future`<T>, который может быть использован для получения результата выполнения задачи.

```java
ExecutorService executor = Executors.newFixedThreadPool(10);
Future<Integer> futureResult = executor.submit(new MyTask());
```

2. `submit(Runnable task)`: этот метод является вариантом `submit()` для `Runnable` задачи, который принимает
   аргументом объект `Runnable` и возвращает объект типа `Future<?>`. Возвращаемый `Future<?>` можно использовать для
   проверки статуса выполнения задачи или для ожидания ее завершения посредством методов `isDone()` и `get()`.

```java
ExecutorService executor = Executors.newFixedThreadPool(10);
Future<?> future = executor.submit(new MyTask());
```

Несмотря на различия, оба метода предназначены для отправки задач на выполнение в `ExecutorService`. Выбор между `execute()` и `submit()` зависит от необходимости получения результата выполнения задачи и управления ее выполнением.
Если вам требуется результат выполнения, вы можете использовать submit() с `Callable`<T>. Если результат не
требуется, можно использовать submit() с `Runnable`, или просто execute().

## Q38. (!) Как запланировать выполнение задачи через определенный интервал?

Для запланирования выполнения задачи через определённый интервал в `Java` можно использовать классы `ScheduledExecutorService` и `ScheduledFuture`. Вот пример:

```java
ScheduledExecutorService executor = Executors.newSingleThreadScheduledExecutor();
ScheduledFuture<?> future = executor.scheduleAtFixedRate(new MyTask(), 0, 1, TimeUnit.SECONDS);
executor.schedule(() -> future.cancel(true), 10, TimeUnit.SECONDS);
```

Вышеуказанный пример использует `scheduleAtFixedRate()` для запуска задачи с заданным интервалом (1 секунда в данном
случае) и schedule() для отмены выполнения задачи через определенное время (10 секунд в данном случае). `MyTask` — это ваша собственная реализация интерфейса `Runnable`, которая представляет задачу, которую вы хотите выполнить. Вам нужно написать свою логику выполнения задачи внутри метода run().

Не забудьте вызвать `executor.shutdown()` после того, как все задачи будут выполнены или больше не нужны, чтобы
корректно завершить работу `ScheduledExecutorService`.

## Q39. (!) Что такое `BlockingQueue`?

`BlockingQueue` — это интерфейс в `Java`, который представляет собой расширение интерфейса `Queue`. Он
предоставляет методы для добавления и извлечения элементов из очереди, но с дополнительной функциональностью
блокирования или ожидания, если очередь пуста или полна.

Основная особенность `BlockingQueue` заключается в том, что если поток пытается добавить элемент в полную очередь или
извлечь элемент из пустой очереди, то он будет заблокирован до тех пор, пока другой поток не удалит элемент из очереди
или добавит новый элемент.

Некоторые распространенные реализации `BlockingQueue` включают:

1. `ArrayBlockingQueue`: Это класс, реализующий `BlockingQueue` с использованием массива фиксированного размера.
2. `LinkedBlockingQueue`: Это класс, реализующий `BlockingQueue` с использованием связанного списка.
3. `PriorityBlockingQueue`: Это класс, реализующий `BlockingQueue`, который поддерживает упорядоченную очередь на основе
   приоритетов.

Ниже приведены некоторые методы, предоставляемые `BlockingQueue`:

1. put(E element): Добавляет элемент в очередь, при необходимости блокируя текущий поток до освобождения места.
2. take(): Извлекает и возвращает элемент из очереди, при необходимости блокируя текущий поток до наличия элемента в
   очереди.
3. offer(E element, long timeout, `TimeUnit unit`): Добавляет элемент в очередь, блокируя текущий поток на протяжении
   заданного времени, если в очереди нет места.
4. poll(long timeout, `TimeUnit unit`): Извлекает и возвращает элемент из очереди, блокируя текущий поток на протяжении
   заданного времени, если очередь пуста. `BlockingQueue` является очень полезным инструментом в многопоточном
   программировании, где необходимо безопасно передавать данные между потоками, обеспечивая синхронизацию и ожидание при
   необходимости.

## Q40. (!) Что такое `Callable` и `Future`?

В `Java` интерфейс `Callable` и класс `Future` являются частями пакета `java.util.concurrent` и предоставляют
механизмы для выполнения задач в фоновом режиме и получения их результатов.

`Callable` — это функциональный интерфейс, похожий на `Runnable`, но в отличие от `Runnable` он может возвращать
значение и генерировать исключение. Он определяет метод call(), который является точкой входа в задачу, которая
может быть исполнена асинхронно.

`Future` представляет значение или исключение, которое будет доступно в будущем при завершении `Callable`. Когда
задача выполняется асинхронно, можно использовать `Future` для получения результата вычисления.

Вот пример использования `Callable` и `Future`:

```java
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class CallableExample {
    public static void main(String[] args) throws InterruptedException, ExecutionException {
        ExecutorService executorService = Executors.newSingleThreadExecutor();
        Callable<String> callable = () -> {
            Thread.sleep(2000);
            return "Hello from Callable!";
        };

        Future<String> future = executorService.submit(callable);
        System.out.println("Doing something in the main thread...");
        String result = future.get();
        System.out.println(result);
        executorService.shutdown();
    }
}
```

В приведенном выше примере `Callable` представляет задачу, которая возвращает строку «Hello from Callable!» через 2 секунды. Метод `submit()` класса `ExecutorService` используется для отправки задачи на выполнение, и он
возвращает `Future`, через который можно получить результат выполнения задачи с помощью метода get(). Если результат
еще не готов, метод get() блокируется, пока он не будет доступен.

При использовании `Callable` и `Future` вы можете получать результаты выполнения задач в фоновом режиме и дальше
продолжать выполнять другую работу в главном потоке.

## Q41. (!) Что такое `FutureTask`?

`FutureTask` — это конкретная реализация интерфейса `Future` и реализация интерфейса `Runnable`, которая
представляет собой асинхронную вычислительную задачу.

`FutureTask` позволяет нам запускать задачу в отдельном потоке и получать результаты вычислений. Можно использовать `FutureTask` для обёртывания объекта `Callable` и запуска его в фоновом режиме.

Преимущества использования `FutureTask`:

1. `FutureTask` может использоваться для отмены задачи с помощью метода cancel(). Это позволяет гибко управлять
   выполнением задачи и закрыть ее, если результат больше не требуется.
2. `FutureTask` позволяет получить результат выполнения задачи методом get(). Если задача ещё не выполнена, метод `get()` блокируется, пока результат не будет доступен.
3. `FutureTask` также позволяет проверить, выполнена ли задача, с помощью методов `isDone()` и `isCancelled()`.

Пример использования `FutureTask`:

```java
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.FutureTask;

public class FutureTaskExample {
    public static void main(String[] args) throws InterruptedException, ExecutionException {
        Callable<Integer> callable = () -> {
            Thread.sleep(2000);
            return 42;
        };

        FutureTask<Integer> futureTask = new FutureTask<>(callable);
        Thread thread = new Thread(futureTask);
        thread.start();

        System.out.println("Fetching result...");
        Integer result = futureTask.get();
        System.out.println("Result: " + result);
    }
}
```

В приведенном выше примере `FutureTask` используется для выполнения `Callable`, который задерживается на 2 секунды и
возвращает целое число 42. После запуска `Thread` объект `FutureTask` передается ему, а затем мы получаем результат
вызовом get(). Если результат еще не готов, метод get() блокируется до тех пор, пока результат не будет
доступен.

Использование `FutureTask` упрощает выполнение асинхронных задач и получение результатов их выполнения. Он особенно
полезен, когда нужно получить результаты из долгого вычисления, но при этом продолжить работу в главном потоке не
блокируя его.

## Q42. (!) Что такое `CompletableFuture`?

`CompletableFuture` — это класс из библиотеки `Java`, который предоставляет возможности для работы с асинхронными
операциями. Он является усовершенствованной версией интерфейса `Future` и обладает более гибкой и мощной
функциональностью.

Отличия `CompletableFuture` от `Future`:

1. `CompletableFuture` позволяет прикреплять коллбэки к выполнению асинхронных операций, что позволяет получать
   результаты операций, обрабатывать их и выполнять дополнительные действия.
2. `CompletableFuture` поддерживает цепочки операций, что позволяет выполнять несколько операций последовательно или
   параллельно, управлять их зависимостями и комбинировать результаты.
3. `CompletableFuture` позволяет манипулировать результатами операций, такими как трансформация результатов,
   комбинирование результатов операций или применение агрегационных функций.
4. `CompletableFuture` поддерживает отмену операций при необходимости.
5. `CompletableFuture` предоставляет более гибкую и удобную обработку исключений.

Пример использования `CompletableFuture`:

```java
import java.util.concurrent.CompletableFuture;

public class CompletableFutureExample {
    public static void main(String[] args) {
        CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
            try {
                Thread.sleep(2000);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
            return "Hello, world";
        });

        future.thenAccept(result -> System.out.println("Результат: " + result));
        System.out.println("Выполняется другая операция");
        future.join();
    }
}
```

В данном примере мы создаем `CompletableFuture` с использованием метода `supplyAsync`, который запускает выполнение
задачи в отдельном потоке. Прикрепляем коллбэк с помощью метода `thenAccept`, который будет вызван после завершения
асинхронной операции и выводит результаты на консоль. Затем мы выполняем другую операцию в главном потоке. В конце мы
ожидаем завершения `CompletableFuture` с помощью метода join. В результате мы получаем вывод «Результат: Hello, world» после того, как операция завершится.

## Q43. (!) Что такое `CountDownLatch` и `CyclicBarrier`?

`CountDownLatch` и `CyclicBarrier` — это два класса в `Java`, которые используются для синхронизации потоков в
многопоточной среде. Они позволяют потокам скоординированно выполнять свои задачи.

`CountDownLatch`: `CountDownLatch` предоставляет возможность ожидать завершения выполнения фиксированного количества
операций или задач, прежде чем продолжить выполнение текущего потока. Он инициализируется с определенным счетчиком, и
каждый поток, который выполняет операцию, может уменьшать этот счетчик при его завершении. Другие потоки, которые
ожидают, могут вызвать метод await(), чтобы остановиться и ждать до тех пор, пока счетчик не станет равным 0.
Пример с `CountDownLatch`:

```java
import java.util.concurrent.CountDownLatch;

public class CountdownLatchExample {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch latch = new CountDownLatch(3);
        Thread thread1 = new WorkerThread(latch);
        Thread thread2 = new WorkerThread(latch);
        Thread thread3 = new WorkerThread(latch);
        thread1.start();
        thread2.start();
        thread3.start();
        latch.await();
        System.out.println("Все потоки завершились. Продолжаем выполнение главного потока.");
    }
}

class WorkerThread extends Thread {
    private CountDownLatch latch;

    public WorkerThread(CountDownLatch latch) {
        this.latch = latch;
    }

    @Override
    public void run() {
        System.out.println("Поток выполняет задачу: " + Thread.currentThread().getName());
        latch.countDown();
    }
}
```

`CyclicBarrier`: `CyclicBarrier` позволяет группе потоков остановиться и ждать друг друга до тех пор, пока все
потоки не достигнут определенной точки синхронизации, называемой "барьером". Когда каждый поток доходит до барьера, он
вызывает метод await(), и все потоки блокируются до тех пор, пока последний поток не достигнет барьера. Только после
этого все потоки будут выпущены и продолжат свое выполнение.

Пример с `CyclicBarrier`:

```java
import java.util.concurrent.BrokenBarrierException;
import java.util.concurrent.CyclicBarrier;

public class CyclicBarrierExample {
    public static void main(String[] args) {
        CyclicBarrier barrier = new CyclicBarrier(3, () -> {
            System.out.println("Все потоки достигли барьера. Выполним действие после достижения барьера.");
        });
        Thread thread1 = new WorkerThread(barrier);
        Thread thread2 = new WorkerThread(barrier);
        Thread thread3 = new WorkerThread(barrier);
        thread1.start();
        thread2.start();
        thread3.start();
    }
}

class WorkerThread extends Thread {
    private CyclicBarrier barrier;

    public WorkerThread(CyclicBarrier barrier) {
        this.barrier = barrier;
    }

    @Override
    public void run() {
        System.out.println("Поток выполняет задачу: " + Thread.currentThread().getName());
        try {
            barrier.await();
        } catch (InterruptedException | BrokenBarrierException e) {
            e.printStackTrace();
        }
    }
}
```

В этих примерах `CountDownLatch` используется для ожидания завершения выполнения всех потоков перед продолжением
работы главного потока. `CyclicBarrier` используется для синхронизации потоков в месте барьера, где каждый поток
останавливается и ждет, пока остальные потоки также достигнут барьера.

Отличие между `CountDownLatch` и `CyclicBarrier` заключается в поведении потоков:

1. `CountDownLatch` работает только в одном направлении и не может быть сброшен после единичной инициализации, в то
   время как `CyclicBarrier` может быть переиспользован.
2. `CountDownLatch` обычно используется в ситуациях, когда главный поток ожидает выполнения нескольких задач, прежде чем
   продолжить, а `CyclicBarrier` когда все потоки должны достигнуть барьера, прежде чем продолжить дальнейшую работу.

Оба класса очень полезны для координации выполнения потоков и позволяют точно синхронизировать их работу.

## Q44. (!) Что такое `Semaphore` и `ReentrantLock`?

`Semaphore` и `ReentrantLock` — это механизмы синхронизации в `Java`, которые используются для управления доступом
к общим ресурсам в многопоточной среде. Они оба позволяют потокам конкурировать за доступ к ресурсу, но имеют некоторые
различия в своем использовании.

`Semaphore`: `Semaphore` это счетчик, который контролирует количество разрешений для доступа к общему ресурсу. У
него есть значение, заданное при создании, которое указывает на максимальное число потоков, которые могут одновременно
получить доступ к ресурсу. Каждый поток, желающий получить доступ к ресурсу, вызывает метод acquire() для получения
разрешения. Если разрешение доступно, то поток продолжает выполнение, в противном случае он блокируется до тех пор, пока
разрешение не станет доступным. После использования ресурса поток вызывает метод release(), чтобы освободить
разрешение и позволить другим потокам получить доступ.

Пример использования `Semaphore`:

```java
import java.util.concurrent.Semaphore;

public class SemaphoreExample {
    private static final Semaphore semaphore = new Semaphore(2);

    public static void main(String[] args) {
        Thread t1 = new Thread(new Worker());
        Thread t2 = new Thread(new Worker());
        Thread t3 = new Thread(new Worker());
        t1.start();
        t2.start();
        t3.start();
    }

    static class Worker implements Runnable {
        @Override
        public void run() {
            try {
                System.out.println(Thread.currentThread().getName() + " is waiting...");
                semaphore.acquire();
                System.out.println(Thread.currentThread().getName() + " is working...");
                Thread.sleep(2000);
                System.out.println(Thread.currentThread().getName() + " completed the work.");
                semaphore.release();
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }
    }
}
```

В данном примере 3 потока t1, t2 и t3 конкурируют за доступ к ресурсу (например, общему файлу или базе
данных), но не более 2 потоков могут одновременно получить доступ к ресурсу, так как используется семафор с 2-мя
разрешениями.

1. `ReentrantLock`: `ReentrantLock` — это класс, который предоставляет более гибкий механизм блокировки, чем ключевое
   слово synchronized. Он обеспечивает возможность блокировки и разблокировки ресурса вручную. Поток, желающий
   получить доступ к ресурсу, вызывает метод lock(). Если ресурс свободен, то поток получает доступ к ресурсу и
   выполняет свою задачу. Если ресурс заблокирован другим потоком, текущий поток блокируется до тех пор, пока ресурс не
   освободится. После завершения работы с ресурсом поток вызывает метод unlock(), чтобы освободить ресурс и
   разблокировать его для других потоков. `ReentrantLock` также поддерживает возможность блокировки на основе условия
   с использованием методов `newCondition()`, что добавляет гибкости при синхронизации потоков.

Пример использования `ReentrantLock`:

```java
import java.util.concurrent.locks.ReentrantLock;

public class ReentrantLockExample {
    private static final ReentrantLock lock = new ReentrantLock();

    public static void main(String[] args) {
        Thread t1 = new Thread(new Worker());
        Thread t2 = new Thread(new Worker());
        t1.start();
        t2.start();
    }

    static class Worker implements Runnable {
        @Override
        public void run() {
            lock.lock();
            try {
                System.out.println(Thread.currentThread().getName() + " is working...");
                Thread.sleep(2000);
                System.out.println(Thread.currentThread().getName() + " completed the work.");
            } catch (InterruptedException e) {
                e.printStackTrace();
            } finally {
                lock.unlock();
            }
        }
    }
}
```

В данном примере 2 потока t1 и t2 конкурируют за доступ к ресурсу при помощи `ReentrantLock`. Когда поток
получает доступ к ресурсу, он блокирует его, выполняет работу и затем разблокирует ресурс. Это позволяет контролировать
точки входа и выхода из блокировки более гибко, чем при использовании ключевого слова synchronized.

Различия между `Semaphore` и `ReentrantLock`:

1. `Semaphore` предоставляет фиксированное количество разрешений для доступа к ресурсу, в то время как `ReentrantLock`
   не задает никаких ограничений на количество потоков, которые могут одновременно получить доступ к ресурсу.
2. `Semaphore` можно использовать для решения задачи с ограниченными ресурсами, где несколько потоков могут получать
   доступ к ресурсу одновременно, но с определенными ограничениями. `ReentrantLock`, с другой стороны, является более
   общим механизмом блокировки, который может быть использован в широком спектре сценариев.

В обоих случаях `Semaphore` и `ReentrantLock` являются полезными инструментами для управления доступом к общим
ресурсам в многопоточной среде. Однако выбор между ними зависит от конкретной задачи и требуемых условий синхронизации
потоков.

## Q45. (!) Что такое `Concurrent Collection Classes`?

`Concurrent Collection Classes` это классы, предоставляемые пакетом `java.util.concurrent`, которые предназначены для
работы с коллекциями в многопоточной среде. Эти классы имеют потокобезопасную реализацию и обеспечивают безопасное
совместное использование коллекций из разных потоков без необходимости в явной синхронизации.

Некоторые из наиболее распространенных классов `Concurrent Collection` включают:

1. `ConcurrentHashMap`: Это реализация Map интерфейса, предназначенная для параллельной работы в многопоточной среде.
   Она обеспечивает высокую производительность и масштабируемость для операций чтения и записи. Позволяет множеству
   потоков безопасно обращаться к коллекции.
2. `ConcurrentLinkedQueue`: Это реализация `Queue` интерфейса, предназначенная для параллельной работы в многопоточной
   среде. Она обеспечивает быстрое и безопасное вставку и удаление элементов из очереди. Позволяет множеству потоков
   безопасно обращаться к очереди.
3. `CopyOnWriteArrayList`: Это реализация `List` интерфейса, обеспечивающая безопасность чтения для множества потоков.
   Она создает новую копию списка при любой операции записи, что делает его идеальным для сценариев, когда чтение
   намного превышает запись.
4. `ConcurrentSkipListSet`: Это реализация Set интерфейса, основанная на пропускном списке. Она предоставляет
   упорядоченное множество, которое может быть безопасно использовано из разных потоков. Поддерживает высокую
   параллельность для операций добавления, удаления и поиска.
5. `BlockingQueue`: Это интерфейс, предоставляющий блокирующие (wait/notify) операции для операций добавления и
   удаления из очереди. Реализации включают `ArrayBlockingQueue`, `LinkedBlockingQueue`, `PriorityBlockingQueue` и т. д.
   Эти классы позволяют ограничить количество элементов в очереди или установить приоритет элементов.

Эти классы позволяют безопасно работать с коллекциями в многопоточной среде и обеспечивают гарантию согласованности
данных, даже при параллельных операциях на коллекции из разных потоков.

## Q47. (!) Как передать параметр в поток?

Есть несколько способов передачи параметров в поток:

1. Через конструктор потока: Вы можете создать свой собственный класс, реализующий интерфейс `Runnable` или
   наследующий класс `Thread`, и создать конструктор, принимающий параметры, которые вы хотите передать. Затем при
   создании объекта потока вы передаете параметры через конструктор. Поток может получить доступ к этим параметрам
   внутри своего метода run(). Пример:

```java
public class MyThread extends Thread {
    private int parameter;

    public MyThread(int parameter) {
        this.parameter = parameter;
    }

    @Override
    public void run() {
        System.out.println("Параметр: " + parameter);
    }
}

MyThread thread = new MyThread(10);
thread.start();
```

2. Через метод потока: Вы можете создать свой собственный класс, реализующий интерфейс `Runnable` или наследующий
   класс `Thread`, и создать метод, принимающий параметры, которые вы хотите передать. Затем вы передаете параметры
   через этот метод, вызвав его перед запуском потока. Поток может получить доступ к этим параметрам внутри своего
   метода run(). Пример:

```java
public class MyRunnable implements Runnable {
    private int parameter;

    public void setParameter(int parameter) {
        this.parameter = parameter;
    }

    @Override
    public void run() {
        System.out.println("Параметр: " + parameter);
    }
}

MyRunnable runnable = new MyRunnable();
runnable.setParameter(10);

Thread thread = new Thread(runnable);
thread.start();
```

3. Используя лямбда-выражения: Если вы используете `Java` 8 или выше, вы можете использовать лямбда-выражения для
   передачи параметров в потоки. Пример:

```java
int parameter = 10;
Thread thread = new Thread(() -> {
    System.out.println("Параметр: " + parameter);
});
thread.start();
```

Все эти подходы позволяют передавать параметры в поток и получать к ним доступ во время выполнения потока. Выбор способа
зависит от ваших потребностей и привычек программирования.

## Q48. (!) Что такое `Java Thread Dump`?

`Java Thread Dump` — это снимок состояния всех потоков, работающих в `Java`-программе в определённый момент времени. Он представляет собой диагностический инструмент, который может
использоваться для анализа проблем, связанных с выполнением и взаимодействием потоков в приложении. `Thread Dump`
содержит информацию о каждом потоке, включая его состояние, стек вызовов и блокировки, которые он может держать или
ожидать. Это дает представление о том, какие потоки активны, что они делают и какие ресурсы они используют. `Thread Dump`
 может использоваться для выявления проблем, таких как общение потоков, состояние гонки, дедлоки или долгая
блокировка.

Создание `Thread Dump` может быть выполнено несколькими способами:

1. Используя команду jstack: Вы можете использовать утилиту jstack, поставляемую с `JDK`, для создания `Thread`
   `Dump` в командной строке. Пример: `jstack <PID>`, где `<PID>` — идентификатор процесса `Java`.
2. Используя управляющую консоль `Java`: Вы также можете создать `Thread Dump`, отправив специальный сигнал (обычно
   `SIGQUIT` или `Ctrl`+\\) на процесс `Java` с помощью управляющей консоли `Java` (jconsole, jvisualvm и т. д.).

Полученный `Thread Dump` можно анализировать с использованием различных инструментов и анализаторов, таких как `Java`
`VisualVM`, `Eclipse MAT` (`Memory Analyzer Tool`) и др. Они позволяют идентифицировать проблемные области и причины проблем
в потоках, что может помочь в отладке и оптимизации производительности приложения.

## Q49. (!) Как решить `Producer-Consumer` проблему?

`Producer-Consumer` проблема возникает при совместном использовании общего ресурса между производителями (producer)
и потребителями (`Consumer`). Производители производят данные и помещают их в общий буфер, а потребители забирают данные
из буфера и обрабатывают их. Цель состоит в том, чтобы обеспечить правильное взаимодействие между производителями и
потребителями, избегая проблем, таких как состояние гонки или дедлоки.

Вот некоторые подходы для решения проблемы `Producer-Consumer`:

1. Использование блокировок и условных переменных: Вы можете использовать механизмы синхронизации, такие как блокировки
   и условные переменные, чтобы гарантировать, что только один производитель или потребитель может получить доступ к
   общему ресурсу в определенное время. Производитель должен ждать, если буфер заполнен, а потребитель должен ждать,
   если буфер пуст. Когда производитель помещает элемент в буфер или потребитель забирает элемент из буфера, они
   уведомляют друг друга, чтобы возобновить работу. Это обеспечивает справедливость и безопасность доступа к ресурсу.
2. Использование блокирующих очередей: Блокирующие очереди, такие как `java.util.concurrent.ArrayBlockingQueue` или 
   `java.util.concurrent.LinkedBlockingQueue`, предоставляют встроенные механизмы синхронизации для решения проблемы 
   `Producer-Consumer`. Производители могут помещать элементы в очередь, а потребители могут забирать элементы из очереди.
   Если очередь заполнена, производители будут блокироваться до освобождения места, а если очередь пуста, потребители
   будут блокироваться до появления элементов в очереди.
3. Использование механизмов синхронизации и обмена данных: Вы также можете использовать механизмы синхронизации,
   такие как `synchronized`, `wait-notify` или `Lock`, в сочетании с общими объектами-буферами для решения проблемы.
   Производители и потребители должны взаимодействовать с общими объектами и объявлять свои операции как критические
   секции для предотвращения состояния гонки.

Выбор конкретного подхода зависит от ваших требований и контекста приложения. Важно гарантировать правильное
взаимодействие между производителями и потребителями, обеспечивая безопасность и эффективность работы приложения.

### Пример решения `Producer-Consumer` с `BlockingQueue`

```java
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;

public class ProducerConsumerExample {
    private static final int QUEUE_SIZE = 10;

    public static void main(String[] args) {
        BlockingQueue<Integer> queue = new LinkedBlockingQueue<>(QUEUE_SIZE);

        // Producer
        Thread producer = new Thread(() -> {
            try {
                for (int i = 0; i < 100; i++) {
                    queue.put(i); // Блокируется, если очередь полна
                    System.out.println("Produced: " + i);
                    Thread.sleep(100);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        // Consumer
        Thread consumer = new Thread(() -> {
            try {
                while (true) {
                    Integer value = queue.take(); // Блокируется, если очередь пуста
                    System.out.println("Consumed: " + value);
                    Thread.sleep(200);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
    }
}
```

## Q50. (!) Что такое Virtual Threads (Java 21) и когда их использовать?

**Virtual Threads** (виртуальные потоки) — лёгкие потоки JVM, введённые в `Java` 21 (JEP 444). Они привязаны к платформенным потокам (`carrier threads`) только на время выполнения кода на CPU; при блокирующем вызове (I/O, `Lock`) виртуальный поток освобождает носитель, а после завершения ожидания планируется снова. Создаются через `Thread.ofVirtual().start(runnable)` или `Executors.newVirtualThreadPerTaskExecutor()`.

Практический акцент в таких вопросах — показать не только синтаксис, но и эксплуатационные последствия: читаемость, совместимость и профиль производительности. На интервью это обычно усиливают примером типичной ошибки и способом её предотвращения в код-ревью или тестах.
