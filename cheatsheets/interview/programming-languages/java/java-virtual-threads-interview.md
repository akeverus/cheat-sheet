# Вопросы на собеседовании: Виртуальные потоки Java

`Virtual Threads` (Project Loom) — лёгкие потоки JVM, ставшие стандартом в Java 21. Помогают масштабировать последовательный код с блокирующим ожиданием без отдельного потока ОС на каждую задачу.

## Q1. Что такое виртуальные потоки (Virtual Threads) и зачем они нужны?

Виртуальный поток — обычный `java.lang.Thread` с реализацией, которой управляет JVM. Во время поддерживаемого блокирующего ожидания JVM снимает его с платформенного потока-носителя и запускает на нём другую задачу. Так приложение может обслуживать много одновременных запросов в понятном последовательном стиле. Выигрыш возможен в пропускной способности при большом числе ожидающих задач; отдельная задача не исполняется быстрее. Виртуальные потоки стали постоянной возможностью Java 21.

## Q2. Как создать виртуальный поток?

`Thread.ofVirtual().start(task)` запускает отдельную задачу. `Executors.newVirtualThreadPerTaskExecutor()` создаёт новый виртуальный поток на каждую отправленную задачу и ждёт их завершения при закрытии исполнителя. `Thread.currentThread().isVirtual()` проверяет тип текущего потока, но сам поток не создаёт.

```java
Thread thread = Thread.ofVirtual().name("request-1").start(task);
thread.join();

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    var future = executor.submit(task);
    future.get();
}
```

Виртуальные потоки — daemon-потоки: сами по себе они не удерживают JVM от завершения.

## Q3. Что такое carrier thread и как виртуальный поток с ним связан?

Carrier — платформенный поток, на котором сейчас исполняется виртуальный. JVM монтирует на него готовый виртуальный поток и обычно демонтирует его при поддерживаемом блокирующем ожидании. Один carrier поочерёдно обслуживает много виртуальных потоков. Целевая параллельность планировщика по умолчанию связана с числом доступных процессоров, но это не жёсткое равенство числа carrier-потоков числу ядер. Планировщик не обещает вытеснять долгую вычислительную задачу по кванту времени; CPU-нагрузка всё равно ограничена ядрами.

## Q4. Что такое pinning и как его избежать?

Pinning означает, что блокирующийся виртуальный поток не может освободить carrier. Это снижает масштабируемость при долгих и частых блокировках, но не нарушает правильность программы.

На JDK 21–23 блокировка внутри `synchronized` могла закрепить поток. Начиная с JDK 24 JEP 491 устранил эту причину: обычный монитор больше не повод заменять `synchronized` на `ReentrantLock`. Длительный вызов native/FFM-кода всё ещё может удерживать carrier. `Object.wait()` и ожидание инициализации класса также требуют внимания по данным JFR. Ищите реальные длительные события `jdk.VirtualThreadPinned`, затем меняйте конкретный проблемный участок или библиотеку. Не заменяйте все мониторы заранее.

## Q5. Для каких задач Virtual Threads подходят, а для каких нет?

Они полезны для множества независимых задач с блокирующим ожиданием: серверных запросов, сетевых вызовов и работы с JDBC. При этом количество соединений с БД, лимиты внешних сервисов, память и CPU остаются конечными. Виртуальные потоки не ускоряют вычислительный код и обычно не добавляют выигрыша уже неблокирующему конвейеру. Решение проверяют нагрузочным тестом на своём стеке, особенно если драйвер выполняет длительный native-вызов или есть другие удержания carrier.

## Q6. Как включить Virtual Threads в Spring Boot?

В Spring Boot 3.2+ на Java 21+ можно включить `spring.threads.virtual.enabled=true`. Boot настроит свои поддерживаемые исполнители задач и планировщик; конкретные интеграции зависят от веб-сервера и наличия пользовательских бинов. `@Async` и `@Scheduled` работают на виртуальных потоках, когда используют соответствующие автоконфигурированные компоненты. Собственный `Executor` не переключится одним флагом — его настройку нужно проверить отдельно.

```yaml
spring:
  threads:
    virtual:
      enabled: true
  main:
    keep-alive: true # если приложение иначе держится только на daemon-задачах
```

Виртуальные потоки — daemon-потоки. Для приложения, которое иначе завершается до выполнения расписания, подходит `spring.main.keep-alive=true`. Размеры обычных пулов не управляют числом виртуальных потоков автоконфигурации.

## Q7. Влияет ли использование ThreadLocal на Virtual Threads?

`ThreadLocal` работает и сохраняет значение для каждого виртуального потока. Контекст запроса допустим, но тяжёлый объект в каждом из множества потоков увеличивает расход памяти. Старый приём кешировать дорогой объект в `ThreadLocal` ради многократного использования одного pooled worker здесь теряет смысл.

`ScopedValue` стал постоянным API в Java 25. Он подходит для неизменяемого контекста, привязанного к времени выполнения блока, и не заменяет всякий изменяемый `ThreadLocal`. На Java 21 его форма и доступность зависят от preview-версии.

## Q8. Что такое Structured Concurrency?

`StructuredTaskScope` объединяет связанные подзадачи в область с управляемым временем жизни, ожиданием результата и отменой. По умолчанию подзадачи запускаются в виртуальных потоках. Область закрывается после завершения или отмены своих задач; детали прерывания зависят от сотрудничества задач с отменой.

На JDK 27 это **седьмая preview-версия**, требующая `--enable-preview`. API менялся: пример с `new StructuredTaskScope.ShutdownOnFailure()` из JDK 21 нельзя выдавать за актуальный. В JDK 27 используют `StructuredTaskScope.open()` и `join()`; стратегии результата задают через `Joiner`.

```java
try (var scope = StructuredTaskScope.open()) {
    var user = scope.fork(() -> fetchUser(userId));
    var orders = scope.fork(() -> fetchOrders(userId));
    scope.join();
    return new UserProfile(user.get(), orders.get());
}
```

## Q9. Чем Virtual Threads отличаются от корутин Kotlin?

Виртуальный поток — `Thread` JVM; обычный блокирующий Java-вызов может приостанавливать его на поддерживаемом ожидании. Корутина Kotlin использует `suspend`-функции, преобразование компилятора и библиотеку `kotlinx.coroutines`. Работа с блокирующей библиотекой в корутине требует выбора подходящего dispatcher или адаптера. Оба подхода помогают обслуживать ожидающие задачи; сравнение скорости зависит от кода и окружения. Виртуальные потоки наблюдают через `jcmd` и JFR, корутины — через средства Kotlin и JVM.

## Q10. Как виртуальные потоки взаимодействуют с JDBC?

Обычный JDBC остаётся блокирующим API и может выполняться в виртуальном потоке. Когда поддерживаемая операция ожидания освобождает carrier, другие задачи продолжают работу. При этом пропускную способность запросов к БД ограничивают соединения, сама БД и драйвер. Пул соединений настраивают под БД и нагрузку, а не под количество виртуальных потоков. На JDK 21–23 полезно проверить удержание carrier в коде драйвера/пула под монитором; с JDK 24 этот вид pinning устранён, но другие длительные блокировки и native-вызовы остаются предметом измерения.

## Q11. Как отлаживать Virtual Threads?

`jcmd <pid> Thread.dump_to_file -format=json <file>` или `-format=text` создаёт дамп с платформенными и виртуальными потоками. Традиционный `Thread.print` показывает платформенные и смонтированные виртуальные потоки, но не заменяет полный дамп виртуальных. `Thread.getAllStackTraces()` не даёт полного перечня виртуальных потоков. Для редкого долгого pinning используйте JFR-событие `jdk.VirtualThreadPinned`; порог и включение событий проверьте в конфигурации записи. На JDK 27 доступна и диагностика планировщика через `jcmd Thread.vthread_scheduler`.

## Q12. Каков накладной расход создания виртуального потока?

Создание и хранение виртуального потока обычно дешевле платформенного: не нужен отдельный поток ОС, а стек хранится в управляемой памяти и растёт по мере надобности. Универсального времени в микросекундах, коэффициента выигрыша или гарантии «миллион за секунду» нет. Много одновременно живущих потоков всё равно расходует память на стеки, задачи, очереди и `ThreadLocal`. Измеряйте создание и пиковую память на целевой JDK и типичной нагрузке.

## Q13. Почему не нужен пул виртуальных потоков?

Пул переиспользует дорогие платформенные потоки и часто ограничивает их число. Виртуальный поток дешевле, поэтому задача обычно получает свой поток через `newVirtualThreadPerTaskExecutor()`. Лимитировать стоит дефицитный ресурс: например, пул соединений или число одновременных вызовов внешнего сервиса через `Semaphore`. Это не разрешение безгранично принимать задачи: очередь, память и внешние лимиты тоже требуют защиты.

## Q14. Как виртуальные потоки соотносятся с Reactive Streams (WebFlux)?

Оба подхода могут обслуживать много задач, ожидающих I/O, но модель программы разная. Виртуальные потоки сохраняют последовательный блокирующий код. WebFlux использует неблокирующий конвейер и даёт операторы для потоков данных, отмены и backpressure. Универсального победителя по пропускной способности или удобству нет. Если система уже строится на реактивных API, включение виртуальных потоков само по себе мало что меняет; если нужен простой код поверх блокирующих API, их стоит измерить в своём сценарии.

## Q15. Что такое Thread.sleep() в контексте VT и чем отличается от Platform Thread?

`Thread.sleep()` приостанавливает виртуальный поток и обычно освобождает carrier для другой работы. Сон платформенного потока удерживает соответствующий поток ОС. Само ожидание всё равно занимает память и время задачи. Если виртуальный поток уже pinned, carrier может остаться занят; поэтому нельзя переносить поведение `sleep` на любой код внутри native-вызова. На JDK 21–23 блокировка внутри `synchronized` могла pinning вызвать; с JDK 24 обычный монитор больше не закрепляет carrier. Поведение `Object.wait()` проверяйте отдельно через JFR.
