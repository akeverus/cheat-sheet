## Q1. Что такое виртуальные потоки (Virtual Threads) и зачем они нужны?

**Virtual Thread** — лёгкий поток, которым управляет сама JVM, а не операционная система. Один OS-поток (его называют carrier thread) по очереди обслуживает тысячи виртуальных потоков, переключаясь между ними каждый раз, когда текущий VT блокируется.

**Какую проблему решают.** Платформенный поток (Platform Thread) — это тонкая обёртка над OS-потоком, отношение к ним один-к-одному. Поэтому платформенные потоки дорогие: ОС держит для каждого ~1 МБ стека и не даёт создать сильно больше ~10 000. В I/O-bound нагрузке (HTTP-вызовы, запросы в БД) поток почти всё время простаивает в ожидании ответа — и при модели «поток на запрос» вы упираетесь в лимит потоков задолго до того, как закончится CPU или сеть.

**Идея.** VT снимают это ограничение: пока виртуальный поток ждёт I/O, JVM снимает его с carrier thread и ставит на тот же carrier другой готовый VT. OS-поток не простаивает в блокировке, а делает полезную работу.

В итоге вы пишете привычный **blocking-style код** (последовательный, читаемый, с обычным try/catch), но получаете **non-blocking производительность** без перехода на reactive:
- carrier thread не простаивает: при блокировке одного VT он подхватывает другой;
- виртуальных потоков можно создать миллионы — стек у них маленький и не резервируется целиком, поэтому OOM не наступает.

## Q2. Как создать виртуальный поток?

Есть три типичных способа, и для собеседования важно понимать, когда какой нужен.

- **`Thread.ofVirtual()`** — билдер для одного потока: можно задать имя, обработчик исключений, запустить через `.start(...)`. Удобно для разовых задач.
- **`Executors.newVirtualThreadPerTaskExecutor()`** — основной рабочий вариант: на **каждую** задачу создаётся свой свежий VT (никакого переиспользования). Именно его используют под нагрузкой — пул здесь не нужен и даже вреден (см. Q13).
- **`Thread.currentThread().isVirtual()`** — проверка, что код реально выполняется на виртуальном потоке.

```java
// Thread factory
Thread vt = Thread.ofVirtual().name("vt-1").start(() -> {
    System.out.println("Virtual: " + Thread.currentThread().isVirtual());
});

// Executor для массового создания
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        executor.submit(() -> {
            Thread.sleep(Duration.ofMillis(100));
            return "done";
        });
    }
}

// Явная проверка
Thread t = Thread.ofVirtual().start(() -> {});
System.out.println(t.isVirtual()); // true
```

## Q3. Что такое carrier thread и как виртуальный поток с ним связан?

**Carrier thread** — это платформенный (OS) поток, на котором виртуальный поток физически исполняется. Сам VT не умеет работать «в вакууме»: чтобы выполнить его код, JVM **монтирует** (mount) его на свободный carrier; как только VT блокируется — JVM его **демонтирует** (unmount) и освобождает carrier. Ключевая мысль: один и тот же carrier за время жизни обслуживает множество VT.

Жизненный цикл при блокировке:
1. VT доходит до блокирующей операции (`I/O`, `Thread.sleep`, `LockSupport.park`) — его состояние (стек) сохраняется в куче.
2. JVM демонтирует VT с carrier, и тот сразу же подхватывает другой готовый к работе VT.
3. Когда блокировка снимается, VT снова становится готовым и встаёт в очередь планировщика на ближайший свободный carrier.

Под carrier threads используется выделенный `ForkJoinPool`. По умолчанию число carrier-потоков (его параллелизм) равно `Runtime.availableProcessors()` — то есть привязано к числу ядер, а не к числу виртуальных потоков. Именно поэтому миллионы VT спокойно живут на десятке carrier-потоков.

## Q4. Что такое pinning и как его избежать?

**Pinning** («прикрепление») — ситуация, когда виртуальный поток нельзя демонтировать с carrier во время блокировки, и carrier застревает вместе с ним. Опасность в том, что это убивает главное свойство VT: пока carrier занят заблокированным VT, он не может обслуживать другие. Если так «зависнет» сразу несколько carrier-потоков (а их всего по числу ядер), приложение начинает захлёбываться, словно VT вообще нет.

Когда возникает pinning:
1. **`synchronized`-блок или метод** — внутри монитора JVM не умеет сохранять стек VT в кучу, поэтому VT остаётся прибит к carrier. Это самая частая причина на практике.
2. **Native-метод (JNI)** — JVM не контролирует чужой нативный стек и не может его смонтировать/демонтировать.

```java
// Проблема — pinning
synchronized (lock) {
    Thread.sleep(1000);  // carrier заблокирован!
}

// Решение — ReentrantLock
private final ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    Thread.sleep(1000);  // carrier свободен
} finally {
    lock.unlock();
}
```

**Как избежать.** Замените `synchronized` вокруг блокирующих операций на `ReentrantLock` (как в примере выше) — он не вызывает pinning, потому что реализован поверх `LockSupport.park`, который JVM умеет демонтировать. Идеально — держать блокирующий I/O вообще вне любых критических секций.

**Диагностика.** Флаг JVM `-Djdk.tracePinnedThreads=full` печатает стек-трейс в момент pinning — по нему сразу видно, какой `synchronized` мешает. (В свежих версиях JDK ситуация с `synchronized` смягчена, но на собеседовании безопаснее называть его источником pinning и предлагать `ReentrantLock`.)

## Q5. Для каких задач Virtual Threads подходят, а для каких нет?

Главный критерий простой: **VT выигрывают там, где поток много ждёт, и не дают ничего там, где поток постоянно считает.** Их сила — дешёвая блокировка, а не ускорение вычислений.

**Подходят (I/O-bound, поток в основном ждёт):**
- HTTP-запросы к внешним API, чтение/запись в БД, файловые и сетевые операции — пока VT ждёт ответа, carrier обслуживает другие.
- Серверы с высоким параллелизмом и blocking I/O по модели «один поток на запрос»: можно держать десятки тысяч одновременных запросов без реактивщины.
- Замена `ThreadPoolExecutor` с большим числом потоков, который раньше создавали именно ради параллельного ожидания.

**Не подходят:**
- **CPU-bound задачи** (вычисления, кодирование, парсинг в памяти) — здесь поток не блокируется, демонтировать нечего, и упор всё равно в число ядер. Преимущества над `ForkJoinPool`/parallel stream нет.
- **Код с активным `synchronized`** вокруг блокировок — pinning сводит выигрыш на нет (см. Q4).
- **Реактивный стек (WebFlux)** — там I/O уже non-blocking, и поверх него VT просто избыточны.

## Q6. Как включить Virtual Threads в Spring Boot?

Начиная со Spring Boot 3.2 (на Java 21+) достаточно одного флага в `application.yml`:

```yaml
# application.yml — Spring Boot 3.2+
spring:
  threads:
    virtual:
      enabled: true
```

После этого Spring Boot сам переводит обработку HTTP-запросов Tomcat, выполнение `@Async` и планировщик `@Scheduled` на виртуальные потоки — менять прикладной код не нужно.

Если проект ещё на более ранней версии, те же executors можно подменить вручную через бины (executor для Tomcat и `AsyncTaskExecutor`):

```java
// Ручная настройка (до Spring Boot 3.2)
@Bean
public TomcatProtocolHandlerCustomizer<?> virtualThreadsForTomcat() {
    return handler -> handler.setExecutor(
        Executors.newVirtualThreadPerTaskExecutor());
}

@Bean
public AsyncTaskExecutor applicationTaskExecutor() {
    return new TaskExecutorAdapter(
        Executors.newVirtualThreadPerTaskExecutor());
}
```

## Q7. Влияет ли использование ThreadLocal на Virtual Threads?

Технически `ThreadLocal` с виртуальными потоками работает как раньше, но именно сценарий VT обнажает его слабые места:
- **Память.** Каждый VT имеет свой набор `ThreadLocal`-значений. На тысячах потоков это не замечали, а на миллионах VT эти значения превращаются в заметный расход памяти.
- **Утечки в пуле.** С VT пул потоков не нужен (они и так дёшевы), но если по инерции оставить пул, переиспользуемый поток сохраняет `ThreadLocal` от предыдущей задачи — и значение может «протечь» в следующую, не сбросившись.

**Java 20+: `ScopedValue` (Scoped Values)** — спроектированная под VT замена `ThreadLocal`. Значение задаётся только на время выполнения переданного блока и автоматически исчезает на выходе, поэтому оно неизменяемое, не течёт между задачами и не требует ручной очистки:

```java
ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

ScopedValue.where(CURRENT_USER, user)
    .run(() -> processRequest());

// Внутри processRequest():
User user = CURRENT_USER.get();
```

## Q8. Что такое Structured Concurrency?

**Structured Concurrency** (Java 21 — preview, Java 23 — стандарт) — подход, при котором группа параллельных задач рассматривается как один структурный блок: дочерние задачи не могут «пережить» область, в которой запущены, и гарантированно завершаются (или отменяются) до выхода из неё.

Зачем это нужно. Раньше при ручном `executor.submit(...)` легко было получить «осиротевшие» задачи: метод вернул результат, а форкнутые потоки ещё работают, текут или их некому отменить при ошибке. Structured Concurrency делает время жизни задач предсказуемым — как обычный `try`-блок задаёт область видимости переменных, `StructuredTaskScope` задаёт область жизни параллельных задач. Ошибка или отмена распространяются на всю группу.

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Future<User> user = scope.fork(() -> fetchUser(userId));
    Future<List<Order>> orders = scope.fork(() -> fetchOrders(userId));

    scope.join()           // ждём завершения всех
         .throwIfFailed(); // пробрасываем исключение если было

    return new UserProfile(user.resultNow(), orders.resultNow());
}
// При выходе из блока все задачи гарантированно завершены
```

Два готовых режима покрывают типовые сценарии:
- **`ShutdownOnFailure`** — «нужны все результаты»: как только падает любая задача, остальные отменяются, а `throwIfFailed()` пробрасывает ошибку. Подходит для fan-out, где итог собирается из нескольких источников.
- **`ShutdownOnSuccess`** — «достаточно первого»: первая успешно завершившаяся задача отменяет остальные (race-паттерн). Подходит, когда нужен любой быстрейший ответ из нескольких реплик/зеркал.

## Q9. Чем Virtual Threads отличаются от корутин Kotlin?

| Критерий | Virtual Threads | Kotlin Coroutines |
|----------|----------------|-------------------|
| Механизм | JVM-управляемые потоки | Suspend-функции + continuations |
| Синтаксис | Обычный blocking Java | `suspend`, `async`, `launch` |
| Совместимость | Все библиотеки Java | Нужны coroutine-aware библиотеки |
| Производительность | Чуть выше накладных расходов | Очень низкие overhead |
| Отладка | Обычный thread dump | Специальные инструменты |
| Реактивный стек | Не нужен | Заменяет |

**Суть различия.** И то, и другое решает задачу дешёвого ожидания, но на разных уровнях. Корутины Kotlin — это компиляторная магия: `suspend`-функция превращается в state-machine (continuation), точки приостановки расставляет компилятор, поэтому работают они только в коде, который про корутины «знает» (нужны coroutine-aware библиотеки). VT — это runtime-механизм самой JVM: приостановка происходит на обычных блокирующих вызовах, поэтому VT прозрачно ускоряют **любой** существующий blocking-код и стандартный thread dump остаётся читаемым.

**Вывод для собеседования:** VT позволяют писать Java в привычном blocking-стиле, не изучая reactive/suspend API и не переписывая библиотеки; цена — чуть больший overhead на переключение по сравнению с континуациями корутин.

## Q10. Как виртуальные потоки взаимодействуют с JDBC?

JDBC по своей природе делает blocking I/O — а это ровно тот случай, ради которого созданы VT: пока запрос выполняется в БД, carrier обслуживает другие потоки. Никаких реактивных драйверов для этого не требуется.

Главный нюанс — **узким местом становится не число потоков, а число соединений**. VT можно создать миллионы, но БД физически держит ограниченный пул соединений (HikariCP). Поэтому размер пула задаёт реальный параллелизм к базе, и раздувать его «под VT» не нужно — соединений с БД и так немного:

```yaml
# HikariCP с Virtual Threads — оптимальный размер пула
spring:
  datasource:
    hikari:
      maximum-pool-size: 20  # VT создают много потоков, но соединений с БД обычно немного
```

**Вывод:** реактивный драйвер `r2dbc` поверх VT не нужен — связка «обычный JDBC + VT» даёт сопоставимую производительность при куда более простом коде. Тонкое место одно: блокировка на свободном соединении пула, но это ограничение БД, а не потоков.

## Q11. Как отлаживать Virtual Threads?

Главная сложность — потоков очень много, поэтому ставка делается на массовые дампы и фильтрацию, а не на пошаговый просмотр. Три рабочих приёма:

- **`-Djdk.tracePinnedThreads=full`** — на запуске печатает стек в момент pinning. Первое, что включают, если VT внезапно не дают выигрыша.
- **`jstack`/VisualVM** — обычный thread dump уже понимает VT, искать виртуальные потоки в нём можно по `isVirtual()`.
- **Программный обход** через `Thread.getAllStackTraces()` с фильтром `Thread::isVirtual` — удобно, чтобы из кода посмотреть только виртуальные потоки.

```bash
# Включить трассировку pinning
java -Djdk.tracePinnedThreads=full -jar app.jar

# Thread dump (jstack, VisualVM) — показывает VT
jstack <pid>

# Просмотр всех виртуальных потоков
Thread.getAllStackTraces().keySet().stream()
    .filter(Thread::isVirtual)
    .forEach(t -> System.out.println(t.getName()));
```

Для массовых дампов под VT в JDK 21+ есть `jcmd <pid> Thread.dump_to_file -format=json file.json` — он выгружает полный снимок всех потоков (включая виртуальные) в JSON, который потом удобно разбирать инструментами.

## Q12. Каков накладной расход создания виртуального потока?

Накладной расход на порядки меньше, чем у платформенного потока — именно поэтому VT можно создавать миллионами, не задумываясь:

- **Создание:** ~1 мкс против ~100 мкс у OS-потока (примерно в 100 раз дешевле).
- **Память стека:** несколько КБ, причём стек растёт и сжимается динамически (хранится в куче) — в отличие от фиксированных ~512 КБ–8 МБ, которые OS резервирует под каждый платформенный поток.

Практический вывод: создать миллион VT и тут же раздать им задачи — нормальная операция (укладывается примерно в секунду), тогда как миллион OS-потоков положил бы и память, и ОС.

```java
// Benchmark: создание 1 000 000 VT за ~1 секунду — нормально
var futures = new ArrayList<Future<?>>();
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        futures.add(executor.submit(() -> "work"));
    }
}
```

## Q13. Почему не нужен пул виртуальных потоков?

Чтобы ответить, надо вспомнить, **зачем вообще существует пул**. Классический `ThreadPoolExecutor` решает две задачи:
1. **Ограничивает число потоков** — потому что OS-потоки дорогие, и их нельзя плодить бесконтрольно.
2. **Переиспользует потоки** — чтобы не платить за постоянное создание и уничтожение дорогих объектов.

С виртуальными потоками **обе причины исчезают**: создание VT почти бесплатно (переиспользовать нечего), а искусственно ограничивать их число — значит выкинуть главное преимущество. Поэтому правильный паттерн — `newVirtualThreadPerTaskExecutor()`: свежий VT на каждую задачу.

При этом ограничивать всё равно нужно — но **не потоки, а дефицитные ресурсы** (соединения с БД, вызовы к внешнему API). Для этого берут не пул потоков, а семафор: VT создаём сколько угодно, а одновременный доступ к ресурсу режем разрешениями.

```java
Semaphore semaphore = new Semaphore(100);
// каждый VT берёт разрешение перед запросом к БД
semaphore.acquire();
try { db.query(...); } finally { semaphore.release(); }
```

## Q14. Как виртуальные потоки соотносятся с Reactive Streams (WebFlux)?

VT и Reactive — это две конкурирующие модели для **одной и той же** проблемы: высокий параллелизм при I/O-bound нагрузке. Различаются они тем, кто и какой ценой управляет ожиданием:

- **Reactive/WebFlux** — non-blocking I/O плюс цепочки операторов/коллбэков. Даёт максимальную эффективность, но требует мыслить потоками данных, тащит свой API и усложняет отладку (stack trace размазан по операторам).
- **Virtual Threads** — обычный blocking-style код, а non-blocking JVM обеспечивает под капотом. Писать и читать проще, ценой чуть большего overhead.

**Когда что выбирать:**
- Для **нового кода** в большинстве сервисов связка Spring Boot + VT — отличный выбор по соотношению «простота/производительность».
- WebFlux оправдан, когда нужен предельный throughput или вы и так работаете с reactive-only библиотеками, где обратного пути к blocking нет.

## Q15. Что такое Thread.sleep() в контексте VT и чем отличается от Platform Thread?

Ключевое отличие: на виртуальном потоке `Thread.sleep()` **не блокирует carrier thread**. JVM воспринимает sleep как точку приостановки — демонтирует VT с carrier, и тот сразу переключается на другой готовый VT. На платформенном же потоке `sleep` честно «усыпляет» OS-поток, и тот всё это время простаивает впустую.

Поэтому код, который раньше считался антипаттерном («поток спит — поток потерян»), на VT почти бесплатен: тысячи VT могут одновременно «спать», занимая лишь горстку carrier-потоков.

```java
// C VT — carrier thread НЕ заблокирован
Thread.ofVirtual().start(() -> {
    Thread.sleep(Duration.ofSeconds(5)); // carrier свободен
});

// С Platform Thread — OS-поток заблокирован
Thread.ofPlatform().start(() -> {
    Thread.sleep(Duration.ofSeconds(5)); // OS-поток занят
});
```

То же верно для `Object.wait()`, `LockSupport.park()` и blocking I/O: все они для JVM являются точками приостановки и корректно демонтируют VT с carrier (исключение — pinning из Q4, где демонтаж невозможен).
