## Q1. (!) Что такое конструктор и чем он отличается от метода?

**Конструктор** — особый член класса, который JVM вызывает при создании объекта через `new`, чтобы перевести только что выделенную «сырую» память в валидное состояние: проинициализировать поля и установить инварианты. Это не метод — у него другая роль и другие правила.

Ключевые отличия от обычного метода:

| Свойство | Конструктор | Метод |
|---|---|---|
| Имя | совпадает с именем класса | любое |
| Тип возврата | отсутствует (даже `void` нельзя писать) | обязателен |
| Вызов | через `new` | по ссылке на объект или `ClassName.method()` |
| Наследование | не наследуется | наследуется |
| Модификатор | любой (включая `private`) | любой |

```java
public class User {
    private final String name;

    public User(String name) {   // конструктор
        this.name = name;
    }

    public String getName() {    // метод
        return name;
    }
}
```

**Главное отличие в одну фразу:** имена могут совпадать с классом, возвращаемого типа нет, и конструктор не наследуется — у каждого класса своя цепочка конструкторов через `super()`.

## Q2. (!) Что такое конструктор по умолчанию и когда он создаётся?

**Конструктор по умолчанию (default constructor)** — это безаргументный конструктор, который компилятор генерирует за вас, но только если в классе **не объявлено ни одного конструктора**. Как только вы пишете хотя бы один свой конструктор (с любыми параметрами), компилятор перестаёт добавлять default — он есть либо явно ваш, либо его нет.

```java
public class Foo {}                // компилятор создаст Foo() { super(); }

public class Bar {
    public Bar(int x) {}           // явный конструктор — default уже НЕ создастся
}

new Bar();                         // ❌ compile error: no default constructor
```

Сгенерированный default-конструктор имеет тот же модификатор доступа, что и класс, и состоит из единственного действия — вызова `super()` у родителя. Поэтому есть важное ограничение: если у родителя нет no-args конструктора (например, только `Parent(int)`), компилятору нечего вызвать в `super()` — он не сможет сгенерировать default у наследника, и код не соберётся.

**Подводный камень:** многие фреймворки (`Jackson`, `JPA`, сериализация) создают объект через рефлексию и требуют именно no-args конструктор. Как только вы добавили параметризованный конструктор, no-args исчезает — поэтому объявляйте его явно, если он нужен фреймворку.

## Q3. Что такое конструктор копирования в Java?

**Конструктор копирования** — это обычный конструктор, который принимает объект того же класса и создаёт его копию. В отличие от `C++`, в `Java` нет языковой поддержки copy-constructor — это просто соглашение, которое пишут руками:

```java
public class Point {
    private final int x, y;

    public Point(int x, int y) { this.x = x; this.y = y; }

    public Point(Point other) {          // конструктор копирования
        this(other.x, other.y);
    }
}
```

**Зачем нужен:** это предпочтительная альтернатива `clone()`. У `clone()` много подводных камней (нужен `Cloneable`, защищённый метод, нет вызова конструктора, поверхностная копия по умолчанию), а конструктор копирования прозрачен — глядя на тело, сразу видно, что и как копируется, и можно сделать глубокую копию там, где нужно.

## Q4. (!) Для чего нужны `this()` и `super()` в конструкторе?

Оба — это явные вызовы других конструкторов, которые делегируют часть инициализации:

- `this(args)` — вызывает **другой конструктор того же класса** (constructor chaining), чтобы не дублировать логику между перегрузками.
- `super(args)` — вызывает конструктор **родительского класса**, чтобы сначала проинициализировать унаследованную часть объекта.

Правила, которые любят спрашивать:

- Вызов должен стоять **первой** строкой конструктора (до `Java 22`; в Java 22+ через превью-фичу допустимы `statements before super()`). Причина — родитель обязан быть полностью построен раньше потомка.
- В одном конструкторе нельзя использовать `this()` и `super()` одновременно — каждый из них передаёт управление, и точка входа может быть только одна.
- Если ни `this()`, ни `super()` не написаны явно — компилятор сам вставляет `super()` (вызов no-args конструктора родителя).

```java
public class Rectangle extends Shape {
    public Rectangle(int w, int h) {
        super("rectangle");     // вызов Shape(String)
        this.w = w; this.h = h;
    }

    public Rectangle() {
        this(10, 10);           // делегируем своему же конструктору
    }
}
```

**Итог:** `super()` гарантирует, что родитель проинициализирован до потомка, а `this()` устраняет дублирование логики между перегрузками, сводя инициализацию к одному «главному» конструктору.

## Q5. Можно ли сделать конструктор `private` / `final` / `abstract`?

Из модификаторов доступа разрешены все, а вот специальные модификаторы методов к конструктору в основном неприменимы — потому что у конструктора другая семантика. Кратко по каждому:

| Модификатор | Можно? | Смысл |
|---|---|---|
| `private` | ✅ | Singleton, фабрики, утилитные классы |
| `public` / `protected` / package-private | ✅ | обычное использование |
| `final` | ❌ | конструктор и так не наследуется |
| `abstract` | ❌ | у конструктора нет тела без реализации, теряет смысл |
| `static` | ❌ | конструктор работает на экземпляре |
| `synchronized` | ❌ | объект ещё не опубликован, синхронизироваться не с кем |

```java
public class Holder {
    private Holder() {}                   // singleton
    public static Holder INSTANCE = new Holder();
}
```

## Q6. Что такое конструктор `record`?

У `record` конструктор устроен особым образом: компилятор автоматически создаёт **canonical constructor** — конструктор, чьи параметры один-в-один совпадают с компонентами записи, и который присваивает все поля:

```java
public record Point(int x, int y) {
    // компилятор генерирует: public Point(int x, int y) { this.x = x; this.y = y; }
}
```

Три формы конструкторов у `record`:

- **Canonical** — точно повторяет компоненты. Генерируется автоматически, но его можно переопределить вручную, если нужна своя логика присваивания.
- **Compact** — пишется без списка параметров; нужен для валидации и нормализации входных данных. Присваивания полей компилятор дописывает сам **после** тела блока:
  ```java
  public record Age(int value) {
      public Age {
          if (value < 0) throw new IllegalArgumentException();
          // this.value = value — добавит компилятор
      }
  }
  ```
- **Дополнительный** (с другими параметрами) — допустим, но обязан в первой строке делегировать в canonical через `this(...)`. Так гарантируется, что любой объект записи проходит через единый canonical-конструктор.

Подробнее в [java-17-21-interview](java-17-21-interview.md) и [java-oop-interview](java-oop-interview.md).

## Q7. (!) Что такое `static`-блок инициализации?

**`static`-блок инициализации** — это блок `static { ... }` на уровне класса, который JVM выполняет **ровно один раз при инициализации класса**, ещё до первого создания объекта, обращения к полям или вызова методов. Его задача — подготовить состояние самого класса (`static`-поля), когда одного присваивания недостаточно.

```java
public class Config {
    static final Map<String, String> DEFAULTS;

    static {
        DEFAULTS = new HashMap<>();
        DEFAULTS.put("region", "ru");
        DEFAULTS.put("tz", "UTC");
    }
}
```

Свойства:

- В классе может быть несколько `static`-блоков; они и `static`-инициализаторы полей выполняются в порядке объявления, сверху вниз.
- Запускается **до** `main()`, если класс уже загружен (точный момент — first active use, см. Q14).
- Удобен там, где присваивания мало: нужны try/catch, цикл, вычисление, reflection.

**Сценарий применения:** инициализация `static`-поля, которое нельзя задать одним выражением — например, заполнение неизменяемой `Map` константами или загрузка конфигурации с обработкой ошибок.

## Q8. (!) Что такое instance-блок инициализации?

**Instance-блок инициализации** — это блок `{ ... }` без `static` на уровне класса. В отличие от `static`-блока, он выполняется **при каждом создании экземпляра** и срабатывает после `super(...)`, но до тела конструктора.

```java
public class Cache {
    private final Map<String, Object> data;

    {
        data = new ConcurrentHashMap<>();
        System.out.println("instance block");
    }

    public Cache() {
        System.out.println("constructor");
    }
}
```

Механика: компилятор копирует instance-блоки и инициализаторы полей в **каждый** конструктор класса, сразу после `super(...)`. Именно поэтому общий для всех перегрузок код в блоке выполнится при любом `new`. В обычном коде применяется редко — логику проще держать в конструкторе. Главный реальный сценарий — анонимные классы, у которых конструктор объявить нельзя:

```java
Map<String, Integer> m = new HashMap<>() {{
    put("a", 1);   // double brace initialization — instance-блок анонимного класса
    put("b", 2);
}};
```

**Подводный камень:** double-brace initialization выглядит изящно, но за каждый такой литерал создаётся отдельный анонимный класс, а его экземпляр держит скрытую ссылку на enclosing instance — отсюда лишние классы и потенциальные утечки памяти. В production предпочтительнее `Map.of(...)`.

## Q9. Когда использовать init-блоки вместо конструктора?

Короткий ответ: почти никогда — init-блок оправдан только в узких случаях, когда у обычного присваивания или конструктора есть конкретное ограничение. Ориентир по ситуациям:

| Ситуация | Решение |
|---|---|
| Сложная инициализация `static` поля (loop, try/catch) | `static`-блок |
| Однажды-вычисляемая константа таблиц (`static final Map`) | `static`-блок |
| Одинаковый код в нескольких конструкторах | instance-блок или `this()` |
| Анонимный класс, которому нужен конструктор | instance-блок |
| Обычное присваивание поля | инициализатор поля `= ...` |

**Эмпирическое правило:** init-блок уместен, когда одну и ту же последовательность действий нужно выполнить до тела конструктора у **всех** перегрузок, и при этом нельзя обойтись инициализатором поля.

## Q10. Может ли `static`-блок бросать checked-исключение?

**Нет.** У `static`-блока нет сигнатуры, поэтому объявить `throws` негде — checked-исключение из него «выпустить» нельзя, его придётся обработать на месте. А вот unchecked-исключение или `Error` блок выбросить может, и тогда происходит следующее: JVM оборачивает его в `ExceptionInInitializerError` (это `Error`, а не `Exception`), помечает класс как **erroneous**, и любая дальнейшая попытка использовать класс будет падать.

Поэтому типичный приём — поймать checked-исключение прямо в блоке и пробросить его уже завёрнутым в `ExceptionInInitializerError`:

```java
static {
    try {
        loadConfig();
    } catch (IOException e) {
        throw new ExceptionInInitializerError(e);
    }
}
```

**Вывод:** ошибки в `static`-инициализации фатальны и необратимы — класс остаётся непригодным до перезапуска JVM, поэтому в `static`-блоках стоит избегать рискованной логики.

## Q11. (!) Какой порядок инициализации класса в JVM?

Инициализация делится на два независимых этапа: один раз готовится сам класс, и при каждом `new` — отдельный объект. Порядок такой:

**Инициализация класса (без наследования) — выполняется однократно:**

1. `static` поля получают **zero-значения** (по типу: `0`, `null`, `false`).
2. `static`-инициализаторы полей + `static`-блоки выполняются **сверху вниз** в порядке объявления.
3. Класс помечен как initialized.

**Создание экземпляра:**

4. Instance-поля получают zero-значения.
5. Выполняется `super(...)` (или `super()` неявно).
6. Instance-инициализаторы полей + instance-блоки выполняются сверху вниз.
7. Тело конструктора.

```java
class A {
    static int s = init("static field");
    static { System.out.println("static block"); }
    int i = init("instance field");
    { System.out.println("instance block"); }
    A() { System.out.println("constructor"); }

    static int init(String name) { System.out.println(name); return 0; }
}

new A();
// static field
// static block
// instance field
// instance block
// constructor
```

## Q12. (!) Какой порядок инициализации при наследовании?

Ключевой принцип: сначала полностью «снизу вверх» инициализируются классы (static), затем «сверху вниз» — родитель раньше потомка — строится объект. При `new Child()` (где `Child extends Parent`) шаги такие:

1. Загружается `Parent`, инициализируются `Parent.static` поля + `static`-блоки.
2. Загружается `Child`, инициализируются `Child.static` поля + `static`-блоки.
3. Аллоцируется объект `Child`, все instance-поля обнуляются.
4. Вызывается `Parent` конструктор: `Parent` instance-поля + instance-блоки → тело конструктора.
5. Вызывается `Child` конструктор: `Child` instance-поля + instance-блоки → тело конструктора.

**Подводный камень:** если конструктор `Parent` вызывает переопределяемый метод, сработает версия из **Child** (виртуальная диспетчеризация работает с момента аллокации объекта). Но конструктор Child ещё не отработал — его поля держат zero-значения. Это классический ловушечный interview-вопрос.

```java
class Parent {
    Parent() { print(); }         // виртуальный вызов
    void print() { System.out.println("parent"); }
}
class Child extends Parent {
    String name = "child";
    void print() { System.out.println(name); }
}
new Child();    // напечатает "null" — name ещё null
```

**Вывод:** никогда не вызывай переопределяемые методы из конструктора.

## Q13. (!) Что такое методы `<clinit>` и `<init>`?

Это два специальных метода, которые `javac` синтезирует в байт-коде — вы их не пишете руками, но именно они и реализуют весь порядок инициализации из Q11–Q12. Имена в угловых скобках выбраны намеренно невызываемыми из Java-кода:

- `<clinit>` (class initializer) — собирает в один метод все `static`-инициализаторы полей и `static`-блоки. JVM вызывает его **один раз** при инициализации класса и гарантирует потокобезопасность: если два потока одновременно триггерят инициализацию, один выполняет `<clinit>`, второй ждёт. Именно это делает `static`-инициализацию безопасной идиомой для синглтонов.
- `<init>` (instance initializer) — каждый конструктор компилируется в собственный `<init>`. В него компилятор встраивает инициализаторы instance-полей и instance-блоки, причём сразу после вызова `super()`.

Посмотреть можно через `javap -c -p ClassName`:

```text
static {};   // <clinit>
  Code: ...

public Foo(int);  // <init>
  Code:
    aload_0
    invokespecial Object.<init>
    ...
```

**Итог:** `<clinit>` отвечает за «состояние класса», `<init>` — за «состояние объекта».

## Q14. Когда именно класс загружается и инициализируется?

Важно различать два разных события, которые часто путают:

**Загрузка (load)** — момент, когда `ClassLoader` впервые нашёл и прочитал байты `.class`. Происходит при первом обращении к классу и сама по себе **не** запускает `static`-инициализацию.

**Инициализация (initialize)** — запуск `<clinit>` — JVM лениво откладывает до **first active use**, то есть до момента, когда состояние класса действительно понадобилось:

- Создание экземпляра (`new`).
- Обращение к `static` полю, **не являющемуся** `static final` константой compile-time.
- Вызов `static` метода.
- Присваивание `static` поля.
- Отражение через `Class.forName("Foo")` (с `initialize=true`, по умолчанию).
- Инициализация подкласса.
- Обращение к `main()` как entry point.

**Не триггерит** инициализацию (это любимые ловушки на собеседовании):

- Обращение к `static final` compile-time константе примитива/`String` — её значение зашито прямо в вызывающий класс (constant folding, см. Q19), читать класс-владелец не нужно.
- Литерал `Foo.class` — только ссылка на метаданные, без запуска `<clinit>`.
- `ClassLoader.loadClass()` без `initialize=true` — загружает, но не инициализирует.

Подробнее о classloader в [jvm-interview](../../jvm/jvm-interview.md).

## Q15. Что напечатает код с наследованием и init-блоками?

Это проверка на знание порядка из Q12 на конкретном примере. Классический interview-вопрос:

```java
class A {
    static { System.out.println("1"); }
    { System.out.println("2"); }
    A() { System.out.println("3"); }
}

class B extends A {
    static { System.out.println("4"); }
    { System.out.println("5"); }
    B() { System.out.println("6"); }
}

public class Main {
    public static void main(String[] args) {
        new B();
        new B();
    }
}
```

Вывод:

```text
1        ← A static
4        ← B static (B загружается из-за new B)
2        ← A instance
3        ← A constructor
5        ← B instance
6        ← B constructor
2        ← A instance (второй new)
3
5
6
```

Обратите внимание: `1` и `4` (static-блоки) печатаются только при **первом** `new B()` — класс инициализируется один раз, поэтому при втором `new` повторяются лишь instance-части (`2 3 5 6`).

**Мнемоника:** «static parent → static child → (для каждого new) instance parent → ctor parent → instance child → ctor child».

## Q16. (!) Какие отличия между `static` и instance-полями?

Коротко: `static`-поле принадлежит классу и существует в одном экземпляре, а instance-поле принадлежит конкретному объекту и существует в стольких копиях, сколько создано объектов. Отсюда вытекают все остальные различия:

| Свойство | `static` | instance |
|---|---|---|
| Живёт в | `Metaspace` (класс-метаданные) | `Heap` (объект) |
| Экземпляров | одно на `ClassLoader` | по одному на объект |
| Обращение | `ClassName.field` | `obj.field` |
| Видимость из `static`-метода | напрямую | требует ссылку на `this` |
| Инициализация | `<clinit>`, один раз | `<init>`, при каждом `new` |
| Сериализация | не включается в `Serializable` | включается |

```java
class Counter {
    static int total;     // общий счётчик
    int id;               // персональный
}
```

## Q17. (!) Что такое `final`-поле и как оно инициализируется?

**`final`-поле** — поле, которое можно присвоить ровно один раз, после чего переназначить его нельзя. Важно: `final` запрещает переприсваивание ссылки, но не делает сам объект неизменяемым (`final List` можно дополнять).

Присвоить `final`-поле обязательно нужно, и сделать это можно тремя способами:

- Инициализатор: `private final int x = 10;`
- Instance-блок: `{ this.x = computeX(); }`
- Конструктор (каждый путь через `new` должен присвоить `final` ровно один раз).

```java
class Foo {
    final int x;
    final int y;
    final int z = 3;

    Foo(int a) {
        this.x = a;
        this.y = a * 2;
        // z уже инициализирован
    }
}
```

**Определённое присваивание (definite assignment):** компилятор статически доказывает, что по **любому** пути выполнения через конструктор каждое `final`-поле присваивается ровно один раз — не остаётся ни неинициализированным, ни присвоенным дважды. Не выполнили — ошибка компиляции.

**Гарантия JMM:** если `final`-поле проинициализировано корректно и `this` не «утекает» из конструктора до его завершения, то после выхода из конструктора значение поля **видно всем потокам без какой-либо синхронизации**. Это особое свойство именно `final`-полей, на котором строится безопасная публикация immutable-объектов.

## Q18. В чём разница между `static final` и просто `final`?

Оба запрещают переприсваивание, но `final` — это неизменяемое **свойство объекта** (своё у каждого экземпляра), а `static final` — неизменяемая **константа класса** (одна на всю JVM). Разница вытекает из того, что `static` привязывает поле к классу, а не к объекту:

| Характеристика | `final` | `static final` |
|---|---|---|
| Область | поле экземпляра | поле класса |
| Когда инициализируется | в конструкторе / инициализаторе | в `static`-блоке / инициализаторе, один раз |
| Может ли отличаться у объектов | да (разные объекты — разные `final` значения) | нет, одно на JVM |
| Где хранится | `Heap` | `Metaspace` |
| Используется для | immutable поля объекта | константы |

```java
public static final int MAX = 100;   // константа
public final String id;              // immutable свойство
```

**Правило:** `static final` — для значений, которые не зависят от объекта.

## Q19. Что такое constant folding и как он связан со `static final`?

**Constant folding** — оптимизация компилятора: если `static final`-поле инициализировано **compile-time constant expression** примитива или `String`, компилятор не генерирует чтение поля, а подставляет само значение прямо в байт-код использующего класса. То есть значение «зашивается» в потребителя на этапе компиляции:

```java
// A.java
public class A {
    public static final int SIZE = 100;
}

// B.java
int x = A.SIZE;   // в байт-коде B будет `bipush 100`, а не чтение A.SIZE
```

**Следствия:**

- Доступ к такой константе **не триггерит** инициализацию класса-владельца (см. Q14) — читать класс `A` уже не нужно, значение и так в `B`.
- Если в `A` потом поменять `SIZE = 200`, но **не перекомпилировать** `B`, то `B` продолжит использовать старое `100`. Это классический коварный баг многомодульных сборок: меняешь константу, а зависимые модули «не замечают».

Чтобы значение перестало быть compile-time константой и folding не сработал, нарушают «константность» выражения — например, считают значение в рантайме:

```java
public static final int SIZE = Integer.parseInt("100");   // уже не compile-time constant
```

## Q20. (!) Какие виды вложенных классов есть в Java?

Главный водораздел — наличие модификатора `static`: статический вложенный класс не связан с экземпляром outer, а остальные три (inner-классы) держат скрытую ссылку на enclosing instance. Всего четыре вида, и они образуют такую иерархию:

- **Nested Classes** (вложенные классы) делятся на:
  - **`static nested class`** — статический вложенный класс (без ссылки на outer);
  - **Inner class** (non-static) — нестатический вложенный класс, который, в свою очередь, бывает трёх видов:
    - **Member inner** — член-класс на уровне класса;
    - **Local inner** — локальный класс внутри метода/блока;
    - **Anonymous inner** — анонимный класс в выражении `new`.

| Вид | Где объявлен | Имеет ссылку на outer? | Имя | Можно `static` члены |
|---|---|---|---|---|
| `static nested` | на уровне класса | нет | да | да |
| member inner | на уровне класса, без `static` | да (`Outer.this`) | да | `static final` compile-time с Java 16+ |
| local | внутри метода/блока | да (если нестатический контекст) | да | `static final` с Java 16+ |
| anonymous | в выражении `new` | да (если нестатический контекст) | нет | только `static final` поля |

```java
class Outer {
    static class StaticNested {}            // 1
    class Inner {}                          // 2

    void method() {
        class Local {}                      // 3
        Runnable r = new Runnable() {       // 4
            public void run() {}
        };
    }
}
```

## Q21. (!) В чём разница между `static nested` и inner-классом?

Суть в одной строке: inner-класс хранит скрытую ссылку на экземпляр outer (`Outer.this`) и потому не может существовать без него, а `static nested` такой ссылки не имеет — это, по сути, обычный класс, просто объявленный внутри другого для группировки. Из этого следует всё остальное:

| Характеристика | `static nested` | inner (non-static) |
|---|---|---|
| Ссылка на outer | нет | скрытое поле `Outer.this` |
| Создание | `new Outer.Nested()` | `outer.new Inner()` или `new Inner()` изнутри outer |
| Доступ к instance-членам outer | только через ссылку | напрямую, включая `private` |
| Может иметь `static` члены | да | до Java 16 — нет; с 16+ — да |
| Сериализация | обычная | сериализация «тянет» outer — часто ломается |
| Утечки памяти | нет | удержание outer в коллекции → утечка |

**Рекомендация:** если вложенный класс **не нуждается** в доступе к instance-полям outer — делай его `static`. Меньше памяти, нет сюрпризов с сериализацией.

## Q22. Что такое local-класс и где его используют?

**Local class** — это полноценный именованный класс, объявленный прямо внутри метода, конструктора или блока инициализации. Его область видимости ограничена окружающим блоком: снаружи на него сослаться нельзя. Как и анонимный класс, он захватывает effectively final локальные переменные окружения (см. Q24).

```java
public List<String> upper(List<String> items) {
    class Upper {
        String apply(String s) { return s.toUpperCase(); }
    }
    Upper u = new Upper();
    return items.stream().map(u::apply).toList();
}
```

**Когда применять.** В современном коде local-классы почти полностью вытеснены лямбдами и method reference. Они остаются оправданными в двух случаях:

- Нужен полноценный класс с несколькими методами и собственным состоянием — лямбда тут не подойдёт.
- На класс нужно ссылаться по имени, например для рекурсии внутри него.

## Q23. (!) Что такое анонимный класс и чем он отличается от лямбды?

**Анонимный класс** — это одноразовая реализация интерфейса или подкласс, объявленные без имени прямо в выражении `new`. Компилятор сразу создаёт класс и его единственный экземпляр:

```java
Runnable r = new Runnable() {
    @Override public void run() { System.out.println("hi"); }
};
```

Главное концептуальное отличие: лямбда — это не «короткий анонимный класс», а другой механизм. Она компилируется через `invokedynamic` и не порождает отдельный `.class`, поэтому и `this` у неё ведёт себя иначе. Сводка различий:

| Свойство | Анонимный класс | Лямбда |
|---|---|---|
| Генерация | отдельный `.class` (`Outer$1.class`) | `invokedynamic` + `LambdaMetafactory`, без отдельного класса |
| `this` | ссылается на анонимный экземпляр | ссылается на enclosing instance |
| Тип | любой класс/интерфейс (1+ абстрактных методов) | только `functional interface` (1 abstract method) |
| Поля / конструктор | может иметь | нет |
| Создание при каждом вызове | да | может быть закэширован |

**Когда что выбирать:** лямбда дешевле и читаемее — это выбор по умолчанию для функционального интерфейса. Анонимный класс нужен, когда требуется собственное состояние/поля, несколько методов, расширение класса или семантика `this`, указывающая на сам объект.

## Q24. Почему анонимный / local класс видит только `effectively final` переменные?

Потому что эти классы могут пережить метод, в котором созданы (а локальные переменные живут только на стеке этого метода). Чтобы их значения остались доступны, компилятор **захватывает копию** локальной переменной в скрытое поле класса. Будь переменная изменяемой, копия внутри класса и переменная в методе со временем разошлись бы — а молчаливое расхождение «двух истин» порождало бы неуловимые баги. Поэтому язык требует, чтобы захватываемая переменная не менялась.

```java
void method() {
    int x = 10;
    Runnable r = () -> System.out.println(x);
    // x = 20;  ❌ тогда x перестанет быть effectively final — compile error
    r.run();
}
```

**Effectively final** — переменная, которая фактически не переприсваивается после инициализации, хотя и не помечена `final`. С Java 8 компилятор разрешает захватывать такие переменные без явного ключевого слова `final`.

Если изменяемость всё же нужна, оборачивают значение в объект (массив, `AtomicReference`): захватывается неизменная **ссылка**, а меняется содержимое по ней:

```java
int[] counter = {0};
Runnable r = () -> counter[0]++;
```

## Q25. Как inner-класс ссылается на outer-экземпляр?

Через скрытое поле, которое добавляет компилятор. В inner-класс генерируется поле `this$0` с ссылкой на внешний объект, а в его конструктор компилятор первым параметром незаметно подставляет `Outer`. Поэтому inner-экземпляр в принципе нельзя создать без outer-экземпляра — связь устанавливается в момент конструирования.

```java
class Outer {
    int x = 10;
    class Inner {
        int read() { return x; }    // фактически: return Outer.this.x
    }
}
```

Декомпиляция:

```java
class Outer$Inner {
    final Outer this$0;
    Outer$Inner(Outer outer) { this$0 = outer; }
    int read() { return this$0.x; }
}
```

Явное обращение к outer — через `Outer.this` (нужно при конфликте имён):

```java
class Outer {
    int x;
    class Inner {
        int x;
        int readOuter() { return Outer.this.x; }
    }
}
```

**Подводный камень:** раз каждый inner-экземпляр держит жёсткую ссылку на свой outer, коллекция таких экземпляров не даёт собрать сборщику ни один связанный outer-объект — типичный источник утечки памяти. Если связь с outer не нужна, делайте класс `static` (см. Q21).

## Q26. Как инициализируется `record` и что такое compact constructor?

**`record`** — это immutable-класс, у которого компилятор сам генерирует всю «обвязку». Из объявления компонентов автоматически создаются:

- `private final` поля для каждого компонента.
- Canonical-конструктор, присваивающий все компоненты.
- `equals` / `hashCode` / `toString` на основе компонентов.
- Аксессоры без префикса `get` — `point.x()`, а не `point.getX()`.

**Compact constructor** — это особый вид canonical-конструктора без списка параметров. Он нужен, чтобы валидировать или нормализовать входные данные, не переписывая вручную весь список параметров и присваивания: компилятор дописывает `this.from = from; this.to = to;` сам, после тела блока.

```java
public record Range(int from, int to) {
    public Range {                                    // compact
        if (from > to) throw new IllegalArgumentException();
        // присваивание this.from / this.to выполнит компилятор
    }
}
```

Полноценный canonical-конструктор тоже допустим, но тогда присваивания делаешь сам:

```java
public record Range(int from, int to) {
    public Range(int from, int to) {                  // canonical
        if (from > to) throw new IllegalArgumentException();
        this.from = from; this.to = to;
    }
}
```

Подробнее о `record` — в [java-17-21-interview](java-17-21-interview.md).

## Q27. Как устроена инициализация `enum`?

Под капотом `enum` — это обычный `final`-класс, неявно расширяющий `Enum<T>`. Каждая константа компилируется в отдельный `public static final` экземпляр этого класса, и все они создаются в `<clinit>` в порядке объявления. То есть инициализация `enum` — это частный случай статической инициализации класса (см. Q13), что и даёт ему ключевые гарантии.

```java
public enum Status {
    ACTIVE,
    INACTIVE;

    private final String label;
    Status() { this.label = name().toLowerCase(); }
}
```

Особенности:

- Конструктор `enum` всегда фактически `private` (даже если модификатор не указан) — извне создать значение нельзя.
- Константы создаются один раз и потокобезопасно — это гарантирует `<clinit>` (см. Q13). Отсюда идиома **`enum`-синглтона** (`INSTANCE`): один экземпляр без двойной проверки и volatile.
- Оператор `new` для `enum` запрещён — все возможные значения уже перечислены в объявлении.
- `switch` по `enum` оптимизирован через таблицу по `ordinal`, поэтому работает быстро.

```java
public enum Singleton {
    INSTANCE;

    public void doWork() { /* ... */ }
}
```

**Вывод:** `enum` гарантирует ровно один экземпляр на каждую константу — идеальный lazy-free singleton.
