## Q1. (!) Что такое `JPMS` и зачем модули?

**JPMS** (Java Platform Module System), введённый в `Java` 9, — это модульная система платформы. Модуль — это именованная совокупность пакетов и ресурсов с явно объявленными зависимостями (`requires`) и экспортом пакетов (`exports`). Цель — сильная инкапсуляция: пакеты, не указанные в `exports`, недоступны извне, в отличие от классического `classpath`, где все публичные классы видны всем.

Дополнительные цели: явные зависимости (модуль не может случайно «подцепить» класс из JAR, который не объявлен в `requires`), уменьшение размера runtime за счёт `jlink` (сборка образа только с нужными модулями), предотвращение конфликтов имён и «адского» `classpath`. Сама платформа JDK разбита на модули: `java.base` (минимальный набор), `java.sql`, `java.xml` и т.д.; приложение может зависеть только от того, что реально использует.

## Q2. Что такое `module-info.java` и что в нём объявляют?

`module-info.java` — это специальный файл-описание модуля, он располагается в корне исходного кода модуля (рядом с корневым пакетом) и компилируется в `module-info.class`. В нём объявляют имя модуля в виде `module com.example.app { }` и внутри фигурных скобок — директивы.

Основные директивы: **`requires`** — от каких модулей зависит данный модуль; **`exports`** — какие пакеты видны другим модулям для компиляции и вызова; **`opens`** — какие пакеты открыты для рефлексии; **`provides`** и **`uses`** — для механизма `ServiceLoader` (сервисы и их реализации). На один модуль — один файл `module-info.java`. Имя модуля должно быть уникальным; по соглашению используют обратное доменное имя (как для пакетов).

```java
// module-info.java в корне src модуля
module com.example.app {
    requires java.sql;
    requires transitive com.example.api;   // транзитивно для клиентов
    exports com.example.app.api;
    opens com.example.app.entities;       // для Hibernate/Spring
    uses com.example.spi.MyService;
    provides com.example.spi.MyService with com.example.app.MyServiceImpl;
}
```

## Q3. В чём разница между `exports` и `opens`?

**`exports`** делает пакет публичным для компиляции и обычного вызова: другие модули могут импортировать и использовать только **публичные** типы из этого пакета. При этом рефлексивный доступ к полям и методам (в том числе приватным) по-прежнему может быть запрещён, если пакет только экспортирован, но не открыт.

**`opens`** открывает пакет именно для рефлексии: другой модуль может вызывать `setAccessible(true)`, обращаться к приватным полям и методам. Без `opens` такие вызовы приводят к `InaccessibleObjectException`. Для фреймворков вроде Spring или Hibernate, которые используют рефлексию для создания прокси, внедрения зависимостей и маппинга сущностей, в модульном приложении нужно явно указывать `opens` для пакетов с конфигурацией, сущностями и т.п. Итог: `exports` — «видно снаружи для вызова», `opens` — «разрешена рефлексия».

## Q4. Что такое `requires` и `requires transitive`?

**`requires`** объявляет прямую зависимость модуля от другого модуля: без неё нельзя использовать типы из того модуля (компилятор и runtime проверяют это). Зависимость не транзитивна: если модуль A зависит от B, а модуль C зависит от A, то C по умолчанию не «видит» B.

**`requires transitive`** делает зависимость транзитивной: модули, которые зависят от текущего, автоматически получают доступ к модулю, указанному в `requires transitive`. Типичный пример — публичный API: модуль `api` объявляет `requires transitive impl`; тогда любой модуль, который пишет `requires api`, получает доступ и к `impl`, и не обязан объявлять зависимость на `impl` отдельно. Так скрывают детали реализации, но дают клиенту всё необходимое для работы с API.

## Q5. Как модули влияют на рефлексию и доступ к внутренним API?

Модули жёстко ограничивают рефлексивный доступ: пакет должен быть либо **exports**, либо **opens** для того модуля, который выполняет рефлексию. Обращение к внутренним (non-exported) пакетам JDK (например, `sun.*`, `jdk.internal.*`) без специальных флагов приводит к `InaccessibleObjectException`. Многие библиотеки (в т.ч. Spring, Hibernate, логирование) используют рефлексию; при запуске на Java 9+ часто приходится добавлять флаги вида `--add-opens java.base/java.lang=ALL-UNNAMED`, чтобы «открыть» нужный пакет для кода из unnamed module.

В собственно модульном приложении вместо глобального `--add-opens` предпочтительно точечно указывать **`opens`** в `module-info.java` только для тех пакетов, которым действительно нужна рефлексия. Так снижается поверхность атаки и явно видно, какие части приложения открыты для фреймворков.

## Q6. Что такое `provides` и `uses` (`ServiceLoader`)?

**`uses`** объявляет, что модуль потребляет сервис (как правило, интерфейс): он будет искать реализации через `ServiceLoader`. **`provides`** объявляет реализацию сервиса: указывается интерфейс (или абстрактный класс) и конкретный класс реализации. Синтаксис: `provides MyService with MyServiceImpl;` и `uses MyService;`.

При вызове `ServiceLoader.load(MyService.class)` JVM находит все модули в modulepath, которые объявляют `provides` для этого интерфейса, загружает классы реализаций и возвращает итератор по экземплярам. Так реализуют плагины, драйверы (например, JDBC), альтернативные реализации без жёсткой зависимости от конкретного класса в коде. Модульная система делает механизм `ServiceLoader` предсказуемым: реализации видны только если модули правильно объявили `provides` и вызывающий модуль объявил `uses`.

```java
// В модуле-потребителе (uses MyService):
ServiceLoader<MyService> loader = ServiceLoader.load(MyService.class);
for (MyService impl : loader) {
    impl.doSomething();
}
```

## Q7. Можно ли запустить класс без `module-info` (классический `classpath`)?

Да. Код, загруженный с **classpath**, попадает в так называемый **unnamed module**. У него нет имени, он не объявляет `exports` и `opens`, но по правилам JPMS он неявно «читает» все именованные модули и сам считается экспортирующим и открывающим все свои пакеты. Таким образом, старые приложения и JAR без `module-info.java` продолжают работать без изменений.

Смешивание modulepath и classpath возможно: приложение может состоять из модулей (JAR с `module-info.class`) и из JAR на classpath. Модули могут зависеть от JAR на classpath, если тот помещён на **modulepath** — тогда он трактуется как **automatic module**. Постепенная миграция: сначала выносят часть кода в именованные модули, остальное остаётся на classpath в unnamed module, пока все зависимости не будут готовы к модулям.

## Q8. Что такое `unnamed module` и `automatic module`?

**Unnamed module** — это совокупность всех классов, загруженных с `classpath`. У него нет имени (поэтому «unnamed»), нет своего `module-info.class`. Он неявно читает все именованные модули и сам экспортирует и открывает все свои пакеты любому именованному модулю. Один unnamed module на загрузчик классов; разные JAR на `classpath` объединяются в один unnamed module. Так сохраняется обратная совместимость со старым способом запуска.

**Automatic module** — это обычный JAR (без `module-info.class`), помещённый на `modulepath`. JVM автоматически превращает его в модуль: имя берётся из имени JAR-файла (дефисы заменяются на точки, версия и расширение отбрасываются), автоматически подразумеваются `requires` всех остальных модулей и `exports` всех своих пакетов. Это позволяет подключать существующие JAR как модули без пересборки и использовать их в модульном приложении на этапе миграции. После появления у JAR собственного `module-info.java` он становится обычным именованным модулем.

## Q9. Что такое `jlink` и зачем собирать custom runtime image?

`jlink` — утилита из JDK, которая собирает **custom runtime image**: образ среды выполнения, содержащий только указанные модули приложения и платформы, без всего остального JDK. На выходе получается директория (или образ) с `bin/java`, библиотеками и конфигурацией — минимальный runtime для запуска конкретного приложения.

Зачем это нужно: уменьшение размера дистрибутива (вместо полного JDK — только нужные модули), упрощение развёртывания (один образ без отдельной установки JDK), возможность оптимизации под целевую платформу. Запуск: `jlink --add-modules <модули> --output <путь>`. В образ попадают указанные модули и все их транзитивные зависимости. Для приложений с модульной структурой `jlink` даёт компактный и предсказуемый runtime.

```bash
jlink --add-modules java.base,java.sql,com.example.app \
      --output runtime-image \
      --strip-debug --no-header-files --no-man-pages
./runtime-image/bin/java -m com.example.app
```

## Q10. Как мигрировать существующий проект на модули?

Миграцию делают пошагово. Сначала добавляют `module-info.java` в один или несколько корневых модулей (например, в один JAR многомодульного проекта). В `module-info` объявляют только `requires` для уже модульных зависимостей и для модулей JDK (например, `java.sql`); остальные JAR пока оставляют на `classpath` или подключают как automatic modules (положить на `modulepath` без `module-info`).

Затем по одному переходят на именованные модули: добавляют `module-info.java` в библиотеки, объявляют `exports` для публичных пакетов и `opens` для пакетов, к которым обращается рефлексия (Spring, Hibernate и т.д.). Для зависимостей, которые ещё не модульные, используют automatic modules; при необходимости добавляют `--add-opens` для совместимости со старыми библиотеками. Тестируют сборку и запуск; после стабилизации можно собирать образ через `jlink`. Документация и инструменты (IDE, Maven/Gradle) поддерживают модули, поэтому ключевое — аккуратно объявить границы модулей и зависимости.

## Q11. Что такое split package и почему это проблема в JPMS?

**Split package** возникает, когда один и тот же пакет (например, `com.example.util`) находится сразу в нескольких модулях. В JPMS это запрещено: модульная система должна однозначно понимать, из какого модуля загружать типы пакета. Если пакет «разрезан» по нескольким модулям, появляется неоднозначность разрешения зависимостей и риска конфликтов при сборке и запуске.

На практике split package часто появляется при миграции монолита на модули, когда код одного пакета разносят в разные артефакты. Исправление: переразбить пакеты так, чтобы каждый пакет принадлежал только одному модулю, либо выделить общий пакет в отдельный модуль-библиотеку.

## Q12. Чем отличается module path от classpath?

`Classpath` — старый механизм загрузки классов без строгих границ модулей: всё видимо всем, зависимости в основном проверяются только во время выполнения. `Module path` — модульный режим JPMS: зависимости явно описаны в `module-info.java`, доступ к пакетам контролируется через `exports`/`opens`, а ошибки связности можно поймать на этапе запуска или даже сборки.

При миграции часто используют гибрид: часть артефактов живёт на `module path`, часть — на `classpath` (как unnamed module). Но для предсказуемого поведения и безопасности лучше поэтапно переводить проект на чистый `module path`.

## Q13. Как в JPMS обрабатываются циклические зависимости между модулями?

JPMS не поддерживает циклические зависимости модулей в стиле `module A requires B` и одновременно `module B requires A`. Такой граф зависимостей усложняет анализ инициализации и нарушает идею чётких границ модулей. При попытке собрать или запустить такой набор модулей вы получите ошибку разрешения зависимостей.

Решение — разорвать цикл: вынести общий контракт в третий модуль (`api`), инвертировать зависимость через интерфейсы или применить `ServiceLoader` (`uses`/`provides`) для слабой связности. Это обычно улучшает архитектуру и тестируемость.

## Q14. Как тестировать модульное приложение?

Для модульного приложения важно тестировать не только логику, но и модульные границы: корректность `requires`, `exports`, `opens`, а также совместимость с рефлексией в фреймворках. Unit-тесты обычно запускают в том же модуле или в отдельном test-модуле, который явно зависит от целевого модуля.

Если тестам нужен доступ к неэкспортируемым пакетам, используют `--add-exports`/`--add-opens` в конфигурации тестового запуска (Maven Surefire/Gradle Test). Для интеграционных тестов полезно запускать приложение в модульном режиме, чтобы раннее поймать проблемы, которые на classpath не проявляются.

## Q15. Какие практики проектирования модулей считаются хорошими?

Хорошая практика — делать модули небольшими и осмысленными по домену, экспортировать только минимально необходимый API и не открывать пакеты без необходимости. Пакеты для внутренней реализации должны оставаться неэкспортируемыми, а `opens` следует использовать точечно под конкретные фреймворки.

Также полезно стабилизировать публичные контракты (API-модули), а детали реализации держать в отдельных impl-модулях. Такой подход упрощает эволюцию системы, уменьшает риски регрессий и делает зависимости между командами/подсистемами прозрачнее.
