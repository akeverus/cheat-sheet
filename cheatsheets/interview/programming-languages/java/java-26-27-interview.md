# Вопросы на собеседовании: `Java 26–27`

Здесь собраны изменения JDK 26 и 27, которые влияют на запуск и сопровождение серверного приложения. Статус фич указан для JDK 27 GA (проверено 2026-10-05). Java 25 остаётся LTS; 26 и 27 — промежуточные релизы.

## Q1. Что изменилось в настройках JVM по умолчанию в JDK 27 и как проверить миграцию?

В HotSpot JDK 27 **compact object headers включены по умолчанию** (JEP 534), а **G1 стал сборщиком по умолчанию во всех окружениях** (JEP 523), включая те, где раньше эргономика могла выбрать другой GC. В JDK 25 compact headers уже были production-фичей, но их включали флагом `-XX:+UseCompactObjectHeaders`; описание JDK 25 см. [Q14 соседней темы](java-22-25-interview.md#q14--что-дают-compact-object-headers-jep-519).

При миграции проверяют фактически выбранный GC, размер heap, паузы и потребление памяти на своей нагрузке. Для сравнения можно временно отключить compact headers через `-XX:-UseCompactObjectHeaders`; явный выбор GC продолжает иметь приоритет над умолчанием. Флаг `UseCompressedClassPointers` в JDK 27 стал obsolete: JVM выдаёт предупреждение и игнорирует его. Старые параметры запуска стоит удалить после проверки, а не считать их рабочей настройкой.

JDK 27 также добавил `jcmd <pid> VM.security_properties` для просмотра действующих security properties; `VM.info` и crash log теперь показывают число открытых файловых дескрипторов на поддерживаемых платформах. Это помогает отличить проблему конфигурации от исчерпания ресурсов, но диагностический вывод перед распространением нужно проверять на чувствительные значения.

**Итог:** сравнивайте поведение JVM на одинаковой нагрузке и проверяйте реальные флаги запуска; одно только обновление версии меняет часть умолчаний.

## Q2. Можно ли считать structured concurrency стабильным API в JDK 26–27?

Нет. `StructuredTaskScope` был **шестым preview в JDK 26** (JEP 525) и остаётся **седьмым preview в JDK 27** (JEP 533). Preview API требует `--enable-preview` при компиляции и запуске; приложение с preview-фичами следует собирать и запускать на соответствующем релизе JDK. Его контракт ещё может измениться или исчезнуть в следующем релизе.

Практический сценарий — fan-out запроса: запустить независимые подзадачи получения профиля и заказов, дождаться результата в пределах scope, а при ошибке или отмене завершить связанные задачи по выбранной политике `Joiner`. Scope ограничивает время жизни дочерних задач и делает их связи видимыми в thread dump. Это не обещание, что любой `fork()` автоматически отменит соседние задачи при первой ошибке: поведение задаёт выбранная политика и вызовы `join()`/`close()`.

Для стабильной production-базы на Java 25 можно использовать виртуальные потоки и существующие API координации; переход на preview `StructuredTaskScope` требует осознанного решения о совместимости. [Q8 про Java 25](java-22-25-interview.md#q8-какой-статус-у-structured-concurrency-в-java-25) описывает предыдущий раунд API.

**Итог:** на JDK 27 structured concurrency удобен для связанных подзадач, но ещё не финализирован.

## Q3. Какие данные JFR скрывает в JDK 27 и где граница этой защиты?

JDK 27 добавил **in-process redaction** для JFR (JEP 536). Стандартные фильтры до записи скрывают подходящие аргументы командной строки и начальные значения переменных окружения и системных свойств. Своими шаблонами можно дополнить фильтры через `-XX:FlightRecorderOptions:redact-key=+...` и `redact-argument=+...`; `-XX:FlightRecorderOptions:help` показывает действующие умолчания и синтаксис.

Это **ограниченная защита**, а не гарантия отсутствия секретов в любом событии JFR. `redact-key` применяется к `jdk.InitialSystemProperty`, `jdk.InitialEnvironmentVariable` и соответствующим аргументам `jdk.JVMInformation`; `redact-argument` также работает лишь для указанных событий и не очищает, например, `jdk.ProcessStart` дочерних процессов. Фильтры работают по ключам/аргументам и могут пропустить секрет с неожиданным именем. Отключение умолчаний через `redact-key=none,redact-argument=none` повышает риск утечки.

При диагностике инцидента проверяют конкретную запись и права доступа к ней; секреты по возможности не передают в аргументах запуска. Настройки JFR не заменяют политику хранения и передачи диагностических файлов.

**Итог:** JFR в JDK 27 безопаснее по умолчанию для нескольких источников данных, но перед отправкой записи её всё равно нужно проверить.

## Q4. Когда JDK 27 использует гибридный post-quantum обмен ключами TLS 1.3?

JDK 27 добавил гибридные группы для **TLS 1.3** (JEP 527): обмен ключами сочетает ECDHE с ML-KEM. `X25519MLKEM768` стоит первой в списке предпочтений SunJSSE по умолчанию. Гибридная группа будет согласована, **только если её поддерживает и другая сторона**; иначе стороны могут выбрать общую традиционную группу. Поэтому обновление одного клиента само по себе не доказывает, что все его соединения стали гибридными.

Кроме `X25519MLKEM768`, реализация поддерживает `SecP256r1MLKEM768` и `SecP384r1MLKEM1024`; последние две группы не включены по умолчанию. При необходимости список и порядок настраивают через `jdk.tls.namedGroups` или `SSLParameters.setNamedGroups(...)`. Для проверки миграции смотрят результат TLS handshake с реальными серверами и посредниками, а также совместимость политик криптографии.

Алгоритмы ML-KEM/ML-DSA, появившиеся в Java 24, — [другая ступень поддержки](java-22-25-interview.md#q19-какие-post-quantum-алгоритмы-добавили-в-java-24-ml-kem-ml-dsa): наличие криптографического API не означает, что TLS уже согласует гибридную группу.

**Итог:** JDK 27 предлагает гибридный обмен ключами по умолчанию, но фактический выбор зависит от peer и настроек TLS.
