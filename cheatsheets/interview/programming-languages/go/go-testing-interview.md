## Q1. (!) Как написать unit test в Go?

Unit-тест в Go — это обычная функция в файле `*_test.go`, имя которой начинается с `Test` и которая принимает один аргумент `*testing.T`. Никаких аннотаций, базовых классов и фреймворков: тестирование встроено в язык и в команду `go test`.

Минимальный пример:

```go
// math.go
package mathx

func Add(a, b int) int { return a + b }

// math_test.go
package mathx

import "testing"

func TestAdd(t *testing.T) {
    result := Add(2, 3)
    if result != 5 {
        t.Errorf("Add(2, 3) = %d; want 5", result)
    }
}
```

Тест считается провалившимся, если он вызвал любой из методов отметки об ошибке (`t.Error`, `t.Fatal` и их `*f`-варианты). Сама проверка условий — обычный `if`: фреймворк не навязывает синтаксис ассертов. Запуск — `go test`.

## Q2. (!) Где располагать тесты?

Тесты в Go лежат **рядом с кодом**, в той же директории, в файлах `*_test.go`. Отдельной папки `tests/` (как в Java или Python) не делают: `go test` ищет тестовые файлы именно в каталоге пакета, а компилятор исключает `*_test.go` из обычной сборки.

При этом у тестового файла есть выбор пакета — и это влияет на доступ к внутренностям:

```
mathx/
  ├── math.go
  ├── math_test.go      ← package mathx (white-box)
  └── math_ext_test.go  ← package mathx_test (black-box)
```

- **White-box** (`package mathx`) — тот же пакет, что и код. Виден доступ к unexported-функциям и полям. Удобно для тестов внутренней логики.
- **Black-box** (`package mathx_test`) — отдельный пакет с суффиксом `_test`. Доступен только публичный API, как у внешнего потребителя. Это заодно ловит случайные циклические импорты и заставляет тестировать контракт, а не реализацию.

**Рекомендация:** для библиотечного кода предпочтительнее black-box (`_test`) — он проверяет именно публичный API. White-box оставляйте для случаев, когда без доступа к внутренностям проверку не написать. Оба варианта могут сосуществовать в одной директории.

## Q3. (!) Как запускать тесты?

```bash
go test                        # текущий пакет
go test ./...                  # все пакеты
go test -v ./...               # verbose
go test -run TestAdd            # один тест по regex
go test -run "TestAdd|TestSub" # несколько по regex
go test -timeout 30s            # timeout
go test -race ./...             # с race detector
go test -count=1 ./...          # отключить кеш
go test -short ./...            # пропустить долгие тесты (testing.Short())
go test -count=10 ./...         # повторить 10 раз (для нестабильных)
```

**Кеширование результатов.** `go test` кеширует успешные прогоны: если исходники, тестовые файлы и аргументы запуска не менялись, повторный вызов мгновенно возвращает `ok (cached)` без реального выполнения. Это ускоряет работу, но мешает, когда тест зависит от внешнего окружения (БД, сеть, время). Сбросить кеш — `-count=1`: формально это «запустить ровно один раз», но Go трактует любой явный `-count` как запрет на использование кеша.

**Полезные флаги на собеседовании:**
- `-run <regex>` фильтрует тесты по имени (включая subtests через `/`).
- `-race` включает детектор гонок (см. Q28) — обязателен в CI для concurrent-кода.
- `-short` вместе с `testing.Short()` в коде позволяет пропускать долгие тесты.
- `-count=N` повторяет тесты N раз — способ выловить нестабильные (flaky) тесты.

## Q4. Какие основные методы у `testing.T`?

`*testing.T` — это «ручка» теста: через неё сообщают об ошибках, логируют, управляют выполнением и регистрируют очистку. Ключевые группы методов:

```go
func TestSomething(t *testing.T) {
    t.Log("info")               // вывод (только в -v или при failure)
    t.Logf("count=%d", n)

    t.Error("oops")              // mark failed, продолжить
    t.Errorf("got %v, want %v", got, want)

    t.Fatal("stop")              // mark failed + остановить test
    t.Fatalf("got %v, want %v", got, want)

    t.Skip("not implemented")    // пропустить
    t.SkipNow()

    if testing.Short() { t.Skip() } // если -short

    t.Parallel()                 // параллельный запуск
    t.Helper()                   // см. Q7

    t.Cleanup(func() {
        // выполнится при завершении теста
    })

    name := t.Name()             // имя теста
}
```

**`Error` vs `Fatal` — ключевое отличие:**
- `Error`/`Errorf` помечают тест как провалившийся, но **продолжают** выполнение — удобно, когда хочется собрать сразу несколько несоответствий.
- `Fatal`/`Fatalf` помечают провал и **немедленно останавливают** тест (через `runtime.Goexit`). Применяют, когда дальше идти бессмысленно — например, если объект не создался и проверять его поля уже нельзя.

**Важный нюанс:** `Fatal` завершает только горутину текущего теста. Поэтому его нельзя вызывать из дочерних горутин — там используйте `Error` плюс синхронизацию, иначе тест не остановится корректно.

## Q5. (!) Что такое table-driven tests?

Table-driven tests — идиоматичный для Go способ проверить одну функцию на наборе входов: тест-кейсы описывают срезом структур (`name` + входные данные + ожидаемый результат), а потом в цикле прогоняют каждый кейс, обычно оборачивая его в `t.Run` как отдельный subtest.

```go
func TestAdd(t *testing.T) {
    tests := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"positives", 2, 3, 5},
        {"negatives", -1, -2, -3},
        {"zero", 0, 5, 5},
        {"overflow boundary", math.MaxInt32, 1, math.MaxInt32 + 1},
    }

    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            if got := Add(tc.a, tc.b); got != tc.expected {
                t.Errorf("Add(%d, %d) = %d; want %d", tc.a, tc.b, got, tc.expected)
            }
        })
    }
}
```

**Зачем так делают:**
- **Лаконичность.** Логика проверки описана один раз, а кейсы — это данные, а не копипаста тела теста.
- **Расширяемость.** Новый случай — это одна строка в таблице, без дублирования кода.
- **Читаемые отчёты.** Каждый кейс получает имя через `t.Run`, поэтому в выводе видно, *какой именно* кейс упал, и его можно запустить точечно: `go test -run TestAdd/zero`.

**Подводный камень:** при выходе из строки таблицы используйте `t.Errorf` (не `t.Fatalf`), иначе первый же провал остановит весь тест и вы не увидите остальные кейсы. Этот паттерн повсеместно используется в стандартной библиотеке Go.

## Q6. (!) Что дают subtests через `t.Run`?

`t.Run(name, func)` запускает вложенный тест внутри родительского. Это группирует связанные проверки под одним `Test`-функцией и даёт каждой ветке собственное имя, изоляцию и возможность точечного запуска.

```go
func TestUser(t *testing.T) {
    t.Run("create", func(t *testing.T) {
        // ...
    })
    t.Run("update", func(t *testing.T) {
        // ...
    })
    t.Run("delete", func(t *testing.T) {
        // ...
    })
}
```

Что это даёт:
- **Иерархию в отчётах** — имена вида `TestUser/create`, по которым видно, какая ветка упала.
- **Точечный запуск** через regex: `go test -run TestUser/create`.
- **Свой `t.Parallel()`** для каждого subtest — можно распараллелить только часть веток.
- **Изоляцию провалов:** `t.Fatal` внутри subtest останавливает только этот subtest, а не весь `TestUser` — остальные ветки всё равно выполнятся.

## Q7. (!) Что делает `t.Helper()`?

`t.Helper()` помечает текущую функцию как вспомогательную (helper). После этого в сообщении о провале Go указывает строку **вызывающего** кода, а не строку внутри хелпера. Без этого все ошибки «схлопываются» в одну строку внутри ассерт-функции, и непонятно, какой именно вызов в тесте упал.

```go
func assertEqual(t *testing.T, got, want int) {
    t.Helper() // важно!
    if got != want {
        t.Errorf("got %d, want %d", got, want)
    }
}

func TestSomething(t *testing.T) {
    assertEqual(t, Add(1, 2), 4) // failure → строка с этим вызовом
    // Без t.Helper() → строка внутри assertEqual
}
```

**Когда вызывать:** в самом начале любой функции, которая принимает `*testing.T` и сама вызывает `t.Error`/`t.Fatal` — типичные ассерт-хелперы и общие setup-функции. Вызов `t.Helper()` должен стоять до первой проверки, иначе для уже выполнившихся строк он не сработает.

## Q8. Как делать setup/teardown в Go, если нет JUnit `@Before`?

В Go нет аннотаций жизненного цикла вроде `@Before`/`@After`. Подготовку и очистку оформляют **обычными функциями**, а освобождение ресурсов вешают через `t.Cleanup` (для одного теста) или `TestMain` (для всего пакета, см. Q27).

Типичный паттерн — функция `setup`, которая возвращает подготовленный объект и сама регистрирует очистку:

```go
func setupTest(t *testing.T) (*App, func()) {
    app := NewApp()
    cleanup := func() { app.Close() }
    return app, cleanup
}

func TestSomething(t *testing.T) {
    app, cleanup := setupTest(t)
    defer cleanup()
    // ... test using app
}

// Лучше — t.Cleanup
func setupTest(t *testing.T) *App {
    app := NewApp()
    t.Cleanup(func() { app.Close() })
    return app
}

func TestSomething(t *testing.T) {
    app := setupTest(t) // cleanup автоматический
}
```

**Почему `t.Cleanup` лучше `defer`:**
- Очистка срабатывает даже при `t.Fatal` (который завершает горутину через `runtime.Goexit`) — в отличие от `defer`, который при этом тоже сработает, но только если стоит в теле самого теста.
- Очистку можно зарегистрировать **внутри setup-функции** — с `defer` так нельзя, потому что `defer` отработал бы при выходе из самой setup-функции, а не из теста.
- Несколько `t.Cleanup` выполняются в порядке LIFO, как и `defer`.

## Q9. (!) Как работают параллельные тесты — `t.Parallel`?

Вызов `t.Parallel()` помечает тест как параллельный: он приостанавливается, пропускает вперёд все последовательные тесты, а затем запускается одновременно с другими параллельными. Степень параллелизма ограничена флагом `-parallel` (по умолчанию `GOMAXPROCS`).

```go
func TestA(t *testing.T) {
    t.Parallel()
    // ...
}

func TestB(t *testing.T) {
    t.Parallel()
    // ...
}
```

**Порядок выполнения:** в рамках одного `go test` сначала отрабатывают все последовательные тесты, и только потом стартуют все помеченные `t.Parallel()`. Внутри `t.Run` это работает на уровне subtests: родитель не завершится, пока не отработают его параллельные потомки.

**Классическая ловушка в table-driven с subtests** (до Go 1.22) — захват переменной цикла. Все subtests делят одну и ту же переменную `tc`, и к моменту параллельного запуска она уже указывает на последний элемент. Поэтому её копируют в локальную:

```go
for _, tc := range tests {
    tc := tc // capture range variable (до Go 1.22)
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()
        // используем tc
    })
}
```

Начиная с **Go 1.22** переменная цикла создаётся заново на каждой итерации, поэтому строку `tc := tc` можно убрать. Помните также о shared state: параллельные тесты не должны писать в общие переменные без синхронизации — иначе `-race` справедливо найдёт гонку.

## Q10. (!) Почему в стандартном пакете `testing` нет assertions?

Это сознательное решение авторов Go: они считают, что библиотека ассертов уводит от ясного кода и провоцирует «магию». Поэтому стандарт даёт только примитивы — `t.Error`/`t.Fatal` — а саму проверку условий вы пишете обычным `if`. Идея в том, что хорошее сообщение об ошибке важнее краткости, и автор теста должен сам сформулировать, *что* именно пошло не так.

**Плюсы такого подхода:**
- Сообщения об ошибках под контролем автора — пишете ровно то, что нужно для диагностики.
- Минимум зависимостей, простой и предсказуемый код.

**Минусы:**
- Многословность: на каждую проверку — `if got != want { t.Errorf(...) }`.
- Нет готовых структурных diff'ов для сложных значений.

Из-за минусов на практике многие проекты подключают `testify` (`assert`/`require`) — он даёт лаконичные ассерты и наглядные diff'ы. Это не часть стандарта, но де-факто отраслевой стандарт.

## Q11. (!) В чём разница между `assert` и `require` в testify?

`testify` даёт два пакета с одинаковым набором ассертов, но разным поведением при провале: `assert` вызывает `t.Error` и **продолжает** тест, а `require` вызывает `t.Fatal` и **останавливает** его. Правило простое: `require` — для проверок, без которых дальше идти бессмысленно (например, `err != nil` перед использованием результата); `assert` — для независимых проверок, которые хочется собрать все сразу.

```go
import (
    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/require"
)

func TestSomething(t *testing.T) {
    user, err := getUser(1)
    require.NoError(t, err)        // failed → t.Fatal
    require.NotNil(t, user)

    assert.Equal(t, "Alice", user.Name)  // failed → t.Error (продолжает)
    assert.Equal(t, 30, user.Age)

    // Diff diff diff
    assert.ElementsMatch(t, []int{1, 2, 3}, []int{3, 1, 2})
    assert.JSONEq(t, `{"a":1}`, `{"a":1}`)
    assert.WithinDuration(t, time.Now(), got, time.Second)
}
```

Помимо `Equal`/`NoError` testify даёт матчеры для нетривиальных сравнений: `ElementsMatch` — те же элементы без учёта порядка, `JSONEq` — сравнение по структуре JSON (а не побайтно), `WithinDuration` — время с допуском. Они дают понятные diff'ы, которые на голом `if` пришлось бы писать руками.

| Пакет | При провале | Когда использовать |
|--------|--------|--------|
| `assert.X` | `t.Error` — продолжает | независимые проверки, хотим увидеть все сразу |
| `require.X` | `t.Fatal` — останавливает | предусловия, без которых дальше нельзя |

**Важно:** `require` вызывает `t.Fatal`, поэтому его, как и сам `t.Fatal`, нельзя дёргать из дочерней горутины — только из горутины теста.

Помимо ассертов в testify есть `testify/mock` (фреймворк моков с ожиданиями) и `testify/suite` (объединение тестов в suite со своими setup/teardown — аналог тест-класса в JUnit).

## Q12. (!) Как делают mocking в Go?

В Go нет аннотаций вроде `@Mock` и проксирования классов. Подмена зависимостей строится на **интерфейсах** и неявной их реализации: production-код зависит от узкого интерфейса, а в тесте вы подставляете любую структуру, которая этот интерфейс реализует. Структурная типизация Go позволяет писать такой мок вручную — отдельной библиотеки для этого не требуется.

```go
// production
type UserRepo interface {
    FindByID(id int) (*User, error)
}

type UserService struct {
    repo UserRepo
}

func (s *UserService) GetUser(id int) (*User, error) {
    return s.repo.FindByID(id)
}

// test — ручной mock
type mockRepo struct {
    user *User
    err  error
}

func (m *mockRepo) FindByID(id int) (*User, error) {
    return m.user, m.err
}

func TestGetUser(t *testing.T) {
    s := &UserService{repo: &mockRepo{user: &User{Name: "Alice"}}}
    u, err := s.GetUser(1)
    assert.NoError(t, err)
    assert.Equal(t, "Alice", u.Name)
}
```

**Рекомендация:** объявляйте интерфейс **на стороне потребителя** и держите его узким (только нужные методы) — тогда ручной мок остаётся маленьким. Для простых случаев ручного мока достаточно; генераторы (gomock, mockery, см. Q13) оправданы, когда у интерфейса много методов или нужны проверки порядка и количества вызовов.

## Q13. Чем отличаются gomock, mockery и ручные моки?

Все три решают одну задачу — подменить интерфейс в тесте, — но по-разному балансируют простоту и контроль над вызовами:

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| Ручные моки | Простые, понятные, без тулинга | Boilerplate под каждый интерфейс |
| **gomock** (поддерживается Uber) | Генерация мока с ожиданиями вызовов и порядком | Сгенерированный код, нужен `mockgen` |
| **mockery** | Генерация моков с API в стиле testify | Зависимость от CLI mockery |
| **testify/mock** | Идёт в составе testify | Многословный ручной API |

```bash
# gomock
mockgen -source=repo.go -destination=mock_repo.go

# mockery
mockery --name=UserRepo
```

```go
// gomock
mockRepo := NewMockUserRepo(ctrl)
mockRepo.EXPECT().FindByID(1).Return(&User{Name: "Alice"}, nil)
```

**Эмпирическое правило:** ручные моки для простых интерфейсов; gomock/mockery — когда важны проверки ожиданий (какие методы, с какими аргументами и сколько раз вызвались) или интерфейс большой. Главный плюс генераторов — мок не «отстаёт» от интерфейса: добавили метод — перегенерировали.

## Q14. (!) Как тестировать HTTP-хендлеры через httptest?

Хендлер — это обычная функция `(http.ResponseWriter, *http.Request)`, поэтому его можно вызвать напрямую, без поднятия сервера. Пакет `net/http/httptest` даёт две вещи для этого: `httptest.NewRequest` собирает тестовый запрос, а `httptest.NewRecorder` подставляет «писатель», который запоминает статус, заголовки и тело ответа.

```go
import "net/http/httptest"

func TestHandler(t *testing.T) {
    req := httptest.NewRequest("GET", "/users/1", nil)
    w := httptest.NewRecorder()

    UserHandler(w, req) // вызываем handler напрямую

    resp := w.Result()
    body, _ := io.ReadAll(resp.Body)

    assert.Equal(t, http.StatusOK, resp.StatusCode)
    assert.Contains(t, string(body), "Alice")
}
```

**Почему так лучше:** нет реального сетевого сокета и порта — тест быстрый и детерминированный, не зависит от занятости портов. Этот подход проверяет именно логику хендлера. Если же нужно протестировать всю цепочку с роутером и middleware, тот же `NewRecorder` можно подать на вход не голому хендлеру, а собранному `http.Handler` (роутеру).

## Q15. Зачем нужен `httptest.NewServer` при тестировании клиентов?

Если `httptest.NewRecorder` (Q14) проверяет хендлер без сети, то `httptest.NewServer` решает обратную задачу — протестировать **HTTP-клиент**. Он поднимает настоящий локальный сервер на случайном порте, отдаёт его адрес через `server.URL`, и клиент ходит туда по реальному HTTP. Это позволяет проверить, как клиент формирует запрос и разбирает ответ, не завися от внешнего сервиса.

```go
func TestUserClient(t *testing.T) {
    server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.URL.Path == "/users/1" {
            json.NewEncoder(w).Encode(User{Name: "Alice"})
            return
        }
        http.NotFound(w, r)
    }))
    defer server.Close()

    client := NewUserClient(server.URL)
    user, err := client.GetUser(1)
    assert.NoError(t, err)
    assert.Equal(t, "Alice", user.Name)
}
```

**Важные детали:**
- Обязательно `defer server.Close()` — иначе сервер и его горутины утекут между тестами.
- Адрес `server.URL` нужно передать клиенту как базовый — клиент должен быть параметризуемым по URL, иначе его не подменить.
- Это «integration-style» тест: реальный TCP-стек, но всё в памяти процесса — медленнее `NewRecorder`, зато проверяет клиент целиком.

## Q16. (!) Как писать benchmarks?

Бенчмарк — функция с именем `Benchmark*` и аргументом `*testing.B`. Измеряемый код прогоняют в цикле ровно `b.N` раз; само значение `b.N` подбирает runtime, постепенно увеличивая его, пока суммарное время не станет достаточным для надёжного замера. Делить на `b.N` вручную не нужно — `go test` сам нормирует и выводит время и аллокации в расчёте на одну операцию.

```go
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(2, 3)
    }
}
```

Запуск:

```bash
go test -bench=. -benchmem
BenchmarkAdd-8   1000000000   0.30 ns/op   0 B/op   0 allocs/op
```

**Как читать вывод:** `BenchmarkAdd-8` — суффикс `-8` это `GOMAXPROCS`; дальше число итераций (`b.N`), затем `ns/op` (наносекунды на операцию), а с флагом `-benchmem` ещё `B/op` (байт аллоцировано) и `allocs/op` (число аллокаций). Runtime увеличивает `b.N`, пока общее время не достигнет порога (по умолчанию ~1 с) — поэтому у быстрого кода итераций миллиарды, а у медленного единицы.

**Подводный камень:** если результат вызова не используется, компилятор может выкинуть код целиком (dead code elimination), и бенчмарк покажет ложный «0 ns/op». Чтобы этого избежать, присваивают результат в пакетную переменную или используют `b.Loop()` (Go 1.24+, см. Q17), который защищён от такой оптимизации.

## Q17. (!) Зачем нужны `b.ResetTimer`, `b.StopTimer`, `b.ReportAllocs`?

Эти методы управляют тем, *что именно* попадает в замер. Без них в результат может затечь время подготовки данных, и бенчмарк завысит стоимость операции.

```go
func BenchmarkSomething(b *testing.B) {
    // Setup — не считаем
    data := makeBigData()
    b.ResetTimer()
    b.ReportAllocs()

    for i := 0; i < b.N; i++ {
        process(data)
    }

    b.StopTimer()
    cleanup()
}
```

- `b.ResetTimer()` — обнулить накопленное время и счётчики; вызывают **после** дорогого setup, чтобы он не вошёл в замер.
- `b.StopTimer()` / `b.StartTimer()` — приостановить и возобновить замер; полезны, если внутри цикла есть подготовка, которую измерять не нужно.
- `b.ReportAllocs()` — включить отчёт по аллокациям (`B/op`, `allocs/op`) для конкретного бенчмарка, не указывая глобальный `-benchmem`.

С Go 1.24+ есть `b.Loop()` — он сам исключает setup из замера и защищает тело цикла от dead-code elimination, поэтому `b.ResetTimer()` с ним обычно не нужен:

```go
func BenchmarkSomething(b *testing.B) {
    setup()
    for b.Loop() { // вместо for i := 0; i < b.N; i++
        process()
    }
}
```

## Q18. Что такое sub-benchmarks?

Sub-benchmarks — это бенчмарки, запущенные через `b.Run(name, func)`, по аналогии с subtests. Главный сценарий — прогнать один и тот же код на разных размерах входа и увидеть, как растёт время. Это превращает бенчмарк в инструмент проверки сложности алгоритма.

```go
func BenchmarkAdd(b *testing.B) {
    sizes := []int{10, 100, 1000, 10000}
    for _, size := range sizes {
        b.Run(fmt.Sprintf("size_%d", size), func(b *testing.B) {
            data := make([]int, size)
            b.ResetTimer()
            for i := 0; i < b.N; i++ {
                process(data)
            }
        })
    }
}
```

Output:
```
BenchmarkAdd/size_10-8       100000000   12 ns/op
BenchmarkAdd/size_100-8       10000000  120 ns/op
BenchmarkAdd/size_1000-8       1000000 1200 ns/op
```

По выводу видно масштабирование: время на операцию растёт примерно линейно с размером — это согласуется с O(n). Если бы при росте размера в 10 раз время росло в 100 раз, это сигнал о квадратичной сложности. Каждый sub-benchmark можно запустить отдельно по имени, как и subtests.

## Q19. Зачем нужен benchstat для сравнения результатов?

Один прогон бенчмарка зашумлён: на цифры влияют другие процессы, тепловой троттлинг, GC. `benchstat` решает это статистически — берёт несколько прогонов «до» и «после», считает среднее с разбросом и проверяет, значима ли разница (p-value). Без него легко принять случайный шум за «оптимизацию».

```bash
go install golang.org/x/perf/cmd/benchstat@latest

# Бейзлайн
go test -bench=. -count=10 > old.txt

# После изменений
go test -bench=. -count=10 > new.txt

benchstat old.txt new.txt
```

Output:
```
name              old time/op    new time/op    delta
Process-8           1.20µs         0.85µs       -29.17% (p=0.000)
```

**Как читать:** `delta` показывает изменение (тут −29% — ускорение), а `p=0.000` — что разница статистически значима. Если бы `benchstat` написал `~` вместо дельты, это значило бы «отличие в пределах шума, вывод делать нельзя».

**Рекомендация:** запускайте бенчмарки с `-count=10` и более, иначе микро-отличиям доверять нельзя. Для чистоты замеров полезно закрыть фоновые процессы и зафиксировать частоту CPU.

## Q20. (!) Что такое fuzzing в Go (1.18+)?

Fuzzing — это автоматическая генерация входных данных для поиска тех значений, что ломают код (panic, неверный результат, нарушение инварианта). С Go 1.18 фаззинг встроен в `testing`: пишут функцию `Fuzz*` с `*testing.F`, задают через `f.Add` стартовые примеры (seed corpus), а в `f.Fuzz` формулируют проверку, которая должна выполняться **на любом входе**. Движок мутирует seed-данные и гоняет проверку, пытаясь найти контрпример.

```go
func FuzzReverse(f *testing.F) {
    // Seed corpus — стартовые примеры
    f.Add("hello")
    f.Add("foo")
    f.Add("")

    f.Fuzz(func(t *testing.T, s string) {
        rev := Reverse(s)
        doubleRev := Reverse(rev)

        if s != doubleRev {
            t.Errorf("Reverse(Reverse(%q)) = %q; want %q", s, doubleRev, s)
        }

        if !utf8.ValidString(rev) {
            t.Errorf("Reverse produced invalid UTF-8: %q", rev)
        }
    })
}
```

Запуск:

```bash
go test -fuzz=FuzzReverse -fuzztime=10s
```

**Что происходит при находке:** когда fuzzer находит вход, ломающий проверку, он минимизирует его и **сохраняет в `testdata/fuzz/`**. С этого момента файл становится частью обычного `go test`: даже без флага `-fuzz` тест прогонит сохранённый кейс как регрессионный — баг не вернётся незамеченным.

В примере проверяется property «двойной разворот строки даёт исходную строку» плюс валидность UTF-8 — классический инвариант, который легко сформулировать и трудно нарушить вручную, но fuzzer найдёт многобайтовые символы, на которых наивная реализация ломается.

## Q21. Когда применять fuzzing?

Fuzzing окупается там, где есть **широкое пространство входов** и **проверяемое свойство, истинное для любого входа**. Если такого инварианта сформулировать нельзя, фаззинг бесполезен — ему нечего проверять.

**Хорошие кандидаты:**
- Парсеры (JSON, XML, собственные протоколы) — много пограничных и битых входов.
- Кодировщики/декодеры (URL, Base64) и любой код с round-trip-свойством `decode(encode(x)) == x`.
- Crypto-код — но осторожно: операции медленные, фаззинг идёт долго.
- Публичный API, принимающий пользовательский ввод, — туда приходит непредсказуемое.

**Плохо подходит:**
- Бизнес-логика без очевидного инварианта — нечего утверждать «для любого входа».
- Интеграционные тесты — слишком медленные для миллионов прогонов.

**Как это работает:** Go fuzzing — coverage-guided (как AFL): он отслеживает, какие новые ветки кода открыл очередной вход, и мутирует именно перспективные данные, направленно углубляясь в непокрытые пути.

## Q22. (!) Как считать coverage?

Покрытие в Go измеряется на уровне выполненных операторов (statements): `go test -cover` инструментирует код, считает, какие строки отработали, и выводит процент. Для детального анализа сохраняют профиль (`-coverprofile`), а затем смотрят его в браузере (`-html`) или текстом по функциям (`-func`).

```bash
go test -cover ./...
go test -coverprofile=cover.out ./...
go tool cover -html=cover.out  # web view
go tool cover -func=cover.out  # текстовый отчёт
```

Output:
```
PASS
coverage: 87.5% of statements
ok      example.com/myapp  0.005s
```

**Режимы счёта (`-covermode`):**
- `set` (по умолчанию) — только факт «строка выполнена/нет». Дёшево.
- `count` — сколько раз выполнилась каждая строка. Помогает находить горячие участки.
- `atomic` — то же, что `count`, но счётчики атомарные. Нужен для concurrent-кода и тестов с `-race`, иначе сами счётчики дадут гонку.

С Go 1.20+ доступно покрытие для собранных бинарников (`-test.gocoverdir=...`) — так измеряют покрытие интеграционными прогонами, а не только юнит-тестами.

## Q23. Как читать coverage profile?

Файл профиля — это текст: первая строка задаёт режим, остальные описывают «блоки» кода (последовательности операторов между ветвлениями).

```
mode: set
example.com/myapp/math.go:5.18,8.2 2 1
```

Формат строки: `файл:строкаНачала.колонка,строкаКонца.колонка количествоОператоров счётчик`. В примере блок из 2 операторов выполнился (счётчик 1). В режиме `set` счётчик — это 0/1, в `count`/`atomic` — реальное число вызовов.

Руками этот формат читать редко нужно: `go tool cover -html=cover.out` строит наглядную раскраску (зелёный — покрыто, красный — нет), а `-func` даёт процент по каждой функции.

**Рекомендация:** не гонитесь за 100% покрытия — это ложная метрика, которая поощряет тесты ради цифры. Покрытие показывает, что строка *выполнилась*, но не что её результат *проверен*. Фокусируйтесь на критичных путях, ветвлениях и граничных случаях; именно там покрытие действительно ценно.

## Q24. (!) Как build tags разделяют unit и integration тесты?

Build tags — это директивы `//go:build`, управляющие тем, попадёт ли файл в сборку. Файл с `//go:build integration` компилируется и запускается **только** при `go test -tags=integration`, а в обычном прогоне игнорируется целиком. Так медленные тесты, требующие БД, сети или Docker, отделяют от быстрых юнит-тестов, не пугая их флагами на каждом запуске.

```go
//go:build integration

package mypackage_test

func TestIntegrationDB(t *testing.T) { ... }
```

```bash
# Только unit
go test ./...

# Только integration
go test -tags=integration ./...

# И то и то
go test -tags=integration ./...
```

**Нюансы:**
- Директива `//go:build integration` должна стоять в самом верху файла, до объявления `package`, и за ней нужна пустая строка.
- Тег `integration` — произвольное имя, его придумывает команда; популярная альтернатива тегам — пропуск через `if testing.Short() { t.Skip() }` плюс флаг `-short`.
- В CI обычно гоняют оба прогона: быстрый `go test ./...` на каждый коммит и `go test -tags=integration ./...` отдельной, более тяжёлой стадией.

## Q25. Что такое Testcontainers для Go?

Testcontainers — библиотека, которая на время теста поднимает реальную зависимость (Postgres, Kafka, Redis…) в Docker-контейнере, отдаёт строку подключения, а после теста гасит контейнер. Это даёт честный интеграционный тест против настоящей БД вместо мока или хрупкого in-memory-аналога.

```go
import (
    "github.com/testcontainers/testcontainers-go"
    "github.com/testcontainers/testcontainers-go/modules/postgres"
)

func TestRepo(t *testing.T) {
    ctx := context.Background()
    container, err := postgres.Run(ctx,
        "postgres:15-alpine",
        postgres.WithDatabase("mydb"),
        postgres.WithUsername("user"),
        postgres.WithPassword("pass"),
    )
    require.NoError(t, err)
    t.Cleanup(func() { container.Terminate(ctx) })

    connStr, _ := container.ConnectionString(ctx)
    db, _ := sql.Open("postgres", connStr)

    // тестируем с реальным postgres
}
```

**Что важно помнить:**
- Очистку вешают на `t.Cleanup` (или `defer`) — `container.Terminate(ctx)`, иначе контейнеры утекут между прогонами.
- Нужен запущенный Docker-демон, поэтому такие тесты обычно прячут за build tag `integration` (Q24).
- Это аналог Java Testcontainers: реалистично, но медленно — гоняют не на каждый коммит, а отдельной стадией CI.

Подробнее — в [Testcontainers](../../testing/testcontainers-interview.md).

## Q26. (!) Где держать тесты — рядом с кодом или в отдельной директории?

Стандарт Go — **рядом с кодом**, в той же директории. Это не просто соглашение: расположение завязано на правила сборки. Тесты в каталоге пакета имеют доступ к unexported (white-box, Q2), а `go test` и IDE находят их без настройки.

**Почему рядом — лучше:**
- Доступ к unexported для white-box тестов.
- Тесты «переезжают» вместе с кодом при рефакторинге, не теряются и не устаревают.
- IDE автоматически показывает coverage прямо в файле.

**Минус** ровно один: при просмотре кода видны и тестовые файлы — но IDE умеют их сворачивать, а суффикс `_test.go` сразу отличает их от продакшена.

**Когда выносят отдельно:** только большие сквозные наборы — e2e или системные тесты, которые не привязаны к конкретному пакету и гоняют приложение целиком. Юнит-тесты в отдельную папку не уносят.

## Q27. (!) Зачем нужен `TestMain` (`testing.M`)?

`TestMain(m *testing.M)` — это точка входа всех тестов пакета: если такая функция объявлена, Go вызывает её вместо прямого запуска тестов, а сами тесты стартуют только когда вы позовёте `m.Run()`. Это даёт место для **однократного** setup/teardown на весь пакет — то, что слишком дорого делать в каждом тесте.

```go
func TestMain(m *testing.M) {
    // Setup
    setupDatabase()

    code := m.Run()

    // Teardown
    teardownDatabase()

    os.Exit(code)
}
```

**Критичный момент:** `m.Run()` возвращает код выхода, и его нужно передать в `os.Exit(code)` — иначе результат тестов потеряется и CI посчитает прогон успешным даже при провалах. Из-за `os.Exit` обычный `defer` для teardown не сработает (он не выполняется при `os.Exit`), поэтому очистку делают **до** `os.Exit`, как в примере.

**Типичные сценарии:**
- Поднять общую БД или Docker-контейнер один раз на пакет, а не на каждый тест.
- Инициализировать логгер, конфиг, глобальные фикстуры.
- Прогнать миграции перед интеграционными тестами.

Для очистки на уровне *одного* теста используйте `t.Cleanup` (Q8); `TestMain` — именно для общего на весь пакет.

## Q28. (!) Зачем запускать тесты с race detector?

Флаг `-race` включает детектор гонок: рантайм инструментирует обращения к памяти и фиксирует, когда две горутины конкурентно обращаются к одной переменной и хотя бы одна пишет, без синхронизации. Это и есть data race — источник плавающих, невоспроизводимых багов.

```bash
go test -race ./...
```

**Почему это обязательно для concurrent-кода:** гонка проявляется только при определённом порядке выполнения горутин. Тест может пройти зелёным сто раз, а на сто первый — или уже в production под нагрузкой — упасть. Детектор не ждёт «удачного» порядка: он находит потенциальную гонку по самому факту небезопасного доступа, даже если в этом прогоне она «не выстрелила».

**Компромисс по цене:** инструментирование замедляет тесты примерно в 5–10 раз и увеличивает потребление памяти. Поэтому `-race` обязательно держат в CI (особенно для concurrent-пакетов), а локально включают по необходимости. Детектор находит реальные гонки, но не доказывает их отсутствие — он видит только то, что выполнилось в этом прогоне.
