## Q1. (!) Как написать unit test в Go?

Unit-тест в Go — это обычная функция в файле `*_test.go`, имя которой начинается с `Test` и которая принимает один аргумент `*testing.T`. Никаких аннотаций, базовых классов и фреймворков: тестирование встроено в язык и в команду `go test`.

Минимальный пример:

```go
// math.go
package mathx

func Add(a, b int) int { return a + b }

// math_test.go
package mathx

import "testing"

func TestAdd(t *testing.T) {
    result := Add(2, 3)
    if result != 5 {
        t.Errorf("Add(2, 3) = %d; want 5", result)
    }
}
```

Тест считается провалившимся, если он вызвал любой из методов отметки об ошибке (`t.Error`, `t.Fatal` и их `*f`-варианты). Сама проверка условий — обычный `if`: фреймворк не навязывает синтаксис ассертов. Запуск — `go test`.

## Q2. (!) Где располагать тесты?

Пакетные тесты Go обычно лежат **рядом с кодом**, в той же директории, в файлах `*_test.go`. `go test` собирает их вместе с соответствующим пакетом, а обычная сборка исключает эти файлы. Отдельный пакет тестов в другом каталоге возможен для самостоятельного интеграционного сценария, но он не получает доступа к внутренним именам исходного пакета.

При этом у тестового файла есть выбор пакета — и это влияет на доступ к внутренностям:

```
mathx/
  ├── math.go
  ├── math_test.go      ← package mathx (white-box)
  └── math_ext_test.go  ← package mathx_test (black-box)
```

- **White-box** (`package mathx`) — тот же пакет, что и код. Виден доступ к unexported-функциям и полям. Удобно для тестов внутренней логики.
- **Black-box** (`package mathx_test`) — отдельный пакет с суффиксом `_test`. Доступен только публичный API, как у внешнего потребителя. Это заодно ловит случайные циклические импорты и заставляет тестировать контракт, а не реализацию.

**Рекомендация:** для библиотечного кода предпочтительнее black-box (`_test`) — он проверяет именно публичный API. White-box оставляйте для случаев, когда без доступа к внутренностям проверку не написать. Оба варианта могут сосуществовать в одной директории.

## Q3. (!) Как запускать тесты?

```bash
go test                        # текущий пакет
go test ./...                  # все пакеты
go test -v ./...               # verbose
go test -run TestAdd            # один тест по regex
go test -run "TestAdd|TestSub" # несколько по regex
go test -timeout 30s            # timeout
go test -race ./...             # с race detector
go test -count=1 ./...          # отключить кеш
go test -short ./...            # пропустить долгие тесты (testing.Short())
go test -count=10 ./...         # повторить 10 раз (для нестабильных)
```

**Кеширование результатов.** В режиме списка пакетов (`go test ./...` или с именем пакета) Go кеширует успешные прогоны при совпадении тестового бинарника, допустимых флагов и отслеживаемых файлов или переменных окружения. Вызов `go test` без списка пакетов запускается в локальном режиме и не использует кеш результата. Внешние БД, сеть и время не всегда отражаются в ключе кеша; для повторного запуска используйте `-count=1`.

**Полезные флаги на собеседовании:**
- `-run <regex>` фильтрует тесты по имени (включая subtests через `/`).
- `-race` включает детектор гонок (см. Q28) — обязателен в CI для concurrent-кода.
- `-short` вместе с `testing.Short()` в коде позволяет пропускать долгие тесты.
- `-count=N` повторяет тесты N раз — способ выловить нестабильные (flaky) тесты.

## Q4. Чем отличаются `t.Error` и `t.Fatal`?

`*testing.T` — это «ручка» теста: через неё сообщают об ошибках, логируют, управляют выполнением и регистрируют очистку. Ключевые группы методов:

```go
func TestSomething(t *testing.T) {
    t.Log("info")               // вывод (только в -v или при failure)
    t.Logf("count=%d", n)

    t.Error("oops")              // mark failed, продолжить
    t.Errorf("got %v, want %v", got, want)

    t.Fatal("stop")              // mark failed + остановить test
    t.Fatalf("got %v, want %v", got, want)

    t.Skip("not implemented")    // пропустить
    t.SkipNow()

    if testing.Short() { t.Skip() } // если -short

    t.Parallel()                 // параллельный запуск
    t.Helper()                   // см. Q7

    t.Cleanup(func() {
        // выполнится при завершении теста
    })

    name := t.Name()             // имя теста
}
```

**`Error` vs `Fatal` — ключевое отличие:**
- `Error`/`Errorf` помечают тест как провалившийся, но **продолжают** выполнение — удобно, когда хочется собрать сразу несколько несоответствий.
- `Fatal`/`Fatalf` помечают провал и **немедленно останавливают** тест (через `runtime.Goexit`). Применяют, когда дальше идти бессмысленно — например, если объект не создался и проверять его поля уже нельзя.

**Важный нюанс:** `Fatal` завершает только горутину текущего теста. Поэтому его нельзя вызывать из дочерних горутин — там используйте `Error` плюс синхронизацию, иначе тест не остановится корректно.

## Q5. (!) Что такое table-driven tests?

Table-driven tests — идиоматичный для Go способ проверить одну функцию на наборе входов: тест-кейсы описывают срезом структур (`name` + входные данные + ожидаемый результат), а потом в цикле прогоняют каждый кейс, обычно оборачивая его в `t.Run` как отдельный subtest.

```go
func TestAdd(t *testing.T) {
    tests := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"positives", 2, 3, 5},
        {"negatives", -1, -2, -3},
        {"zero", 0, 5, 5},
        {"larger values", 1000, 2000, 3000},
    }

    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            if got := Add(tc.a, tc.b); got != tc.expected {
                t.Errorf("Add(%d, %d) = %d; want %d", tc.a, tc.b, got, tc.expected)
            }
        })
    }
}
```

**Зачем так делают:**
- **Лаконичность.** Логика проверки описана один раз, а кейсы — это данные, а не копипаста тела теста.
- **Расширяемость.** Новый случай — это одна строка в таблице, без дублирования кода.
- **Читаемые отчёты.** Каждый кейс получает имя через `t.Run`, поэтому в выводе видно, *какой именно* кейс упал, и его можно запустить точечно: `go test -run TestAdd/zero`.

**Подводный камень:** внутри `t.Run` можно использовать и `t.Fatalf`: он остановит только текущий subtest, а остальные кейсы продолжатся. `t.Errorf` полезен, если нужно собрать несколько независимых ошибок внутри одного кейса.

## Q6. (!) Что дают subtests через `t.Run`?

`t.Run(name, func)` запускает вложенный тест внутри родительского. Это группирует связанные проверки под одним `Test`-функцией и даёт каждой ветке собственное имя, изоляцию и возможность точечного запуска.

```go
func TestUser(t *testing.T) {
    t.Run("create", func(t *testing.T) {
        // ...
    })
    t.Run("update", func(t *testing.T) {
        // ...
    })
    t.Run("delete", func(t *testing.T) {
        // ...
    })
}
```

Что это даёт:
- **Иерархию в отчётах** — имена вида `TestUser/create`, по которым видно, какая ветка упала.
- **Точечный запуск** через regex: `go test -run TestUser/create`.
- **Свой `t.Parallel()`** для каждого subtest — можно распараллелить только часть веток.
- **Изоляцию провалов:** `t.Fatal` внутри subtest останавливает только этот subtest, а не весь `TestUser` — остальные ветки всё равно выполнятся.

## Q7. (!) Что делает `t.Helper()`?

`t.Helper()` помечает текущую функцию как вспомогательную (helper). После этого в сообщении о провале Go указывает строку **вызывающего** кода, а не строку внутри хелпера. Без этого все ошибки «схлопываются» в одну строку внутри ассерт-функции, и непонятно, какой именно вызов в тесте упал.

```go
func assertEqual(t *testing.T, got, want int) {
    t.Helper() // важно!
    if got != want {
        t.Errorf("got %d, want %d", got, want)
    }
}

func TestSomething(t *testing.T) {
    assertEqual(t, Add(1, 2), 4) // failure → строка с этим вызовом
    // Без t.Helper() → строка внутри assertEqual
}
```

**Когда вызывать:** в самом начале любой функции, которая принимает `*testing.T` и сама вызывает `t.Error`/`t.Fatal` — типичные ассерт-хелперы и общие setup-функции. Вызов `t.Helper()` должен стоять до первой проверки, иначе для уже выполнившихся строк он не сработает.

## Q8. Как делать setup/teardown в Go, если нет JUnit `@Before`?

В Go нет аннотаций жизненного цикла вроде `@Before`/`@After`. Подготовку и очистку оформляют **обычными функциями**, а освобождение ресурсов вешают через `t.Cleanup` (для одного теста) или `TestMain` (для всего пакета, см. Q27).

Setup-функция может вернуть готовый объект и зарегистрировать его очистку:

```go
func setupTest(t *testing.T) *App {
    t.Helper()
    app := NewApp()
    t.Cleanup(func() { app.Close() })
    return app
}
```

`t.Cleanup` (Go 1.14+) выполняет зарегистрированные функции в обратном порядке после завершения теста и всех его подтестов. `defer` срабатывает при выходе из функции, в которой объявлен, в том числе при `t.Fatal` в той же горутине. Если родительский тест открывает общий ресурс для параллельных подтестов, его `defer` закроет ресурс до того, как подтесты продолжат работу после `t.Parallel()`. Зарегистрируйте закрытие через `t.Cleanup` родителя. [Документация T.Cleanup](https://pkg.go.dev/testing#T.Cleanup) · [Документация T.FailNow](https://pkg.go.dev/testing#T.FailNow).

## Q9. (!) Как работают параллельные тесты — `t.Parallel`?

Вызов `t.Parallel()` приостанавливает тест до возврата родительской тестовой функции. Для тестов верхнего уровня роль родителя выполняет внутренняя обёртка пакета `testing`: код до `t.Parallel()` выполняется сразу, а продолжения ждут завершения последовательных тестов верхнего уровня. Флаг `-parallel` ограничивает число одновременно выполняемых параллельных тестов внутри одного тестового процесса. По умолчанию лимит равен `GOMAXPROCS`. [Порядок выполнения подтестов](https://go.dev/blog/subtests#control-of-parallelism).

Например, родитель вызывает `t.Run("A", ...)` и `t.Run("B", ...)`. Каждый вызов `t.Run` возвращается, когда соответствующий подтест доходит до `t.Parallel()`. Когда родительская функция возвращается, оба подтеста могут продолжить работу параллельно. Сам тест считается завершённым после обоих подтестов и очистки. Если подтестам нужен общий сервер, его закрытие можно зарегистрировать в `t.Cleanup` родителя (Q8).

`t.Setenv` (Go 1.17+) и `t.Chdir` (Go 1.24+) меняют состояние процесса. Их нельзя вызывать в параллельном тесте или при наличии параллельного предка. [Документация T.Setenv](https://pkg.go.dev/testing#T.Setenv) · [Документация T.Chdir](https://pkg.go.dev/testing#T.Chdir).

**Классическая ловушка в table-driven с subtests** (до Go 1.22) — захват переменной цикла. Все subtests делят одну и ту же переменную `tc`, и к моменту параллельного запуска она уже указывает на последний элемент. Поэтому её копируют в локальную:

```go
for _, tc := range tests {
    tc := tc // capture range variable (до Go 1.22)
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()
        // используем tc
    })
}
```

Новая семантика действует для модулей с `go 1.22` или новее в `go.mod` (и файлов, для которых она включена ограничением сборки). Для старой версии языка копия всё ещё нужна даже при новом бинарнике Go. Параллельные тесты не должны писать в общие переменные без синхронизации.

## Q10. (!) Есть ли готовые assertions в стандартном пакете `testing`?

Пакет `testing` даёт управление тестом и методы сообщения об ошибках, но не содержит набора готовых проверок значений. Условие обычно пишут обычным `if`, а сообщение формулируют через `t.Error` или `t.Fatal`. Для сложных сравнений можно подключить стороннюю библиотеку. Это описание возможностей стандартного пакета, а не приписывание его авторам единственного мотива.

**Плюсы такого подхода:**
- Сообщения об ошибках под контролем автора — пишете ровно то, что нужно для диагностики.
- Минимум зависимостей, простой и предсказуемый код.

**Минусы:**
- Многословность: на каждую проверку — `if got != want { t.Errorf(...) }`.
- Нет готовых структурных diff'ов для сложных значений.

Из-за минусов на практике многие проекты подключают `testify` (`assert`/`require`) — он даёт лаконичные ассерты и наглядные diff'ы. Это не часть стандарта, но де-факто отраслевой стандарт.

## Q11. (!) В чём разница между `assert` и `require` в testify?

`testify` даёт два пакета с одинаковым набором ассертов, но разным поведением при провале: `assert` вызывает `t.Error` и **продолжает** тест, а `require` вызывает `t.Fatal` и **останавливает** его. Правило простое: `require` — для проверок, без которых дальше идти бессмысленно (например, `err != nil` перед использованием результата); `assert` — для независимых проверок, которые хочется собрать все сразу.

```go
import (
    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/require"
)

func TestSomething(t *testing.T) {
    user, err := getUser(1)
    require.NoError(t, err)        // failed → t.Fatal
    require.NotNil(t, user)

    assert.Equal(t, "Alice", user.Name)  // failed → t.Error (продолжает)
    assert.Equal(t, 30, user.Age)

    // Diff diff diff
    assert.ElementsMatch(t, []int{1, 2, 3}, []int{3, 1, 2})
    assert.JSONEq(t, `{"a":1}`, `{"a":1}`)
    assert.WithinDuration(t, time.Now(), got, time.Second)
}
```

Помимо `Equal`/`NoError` testify даёт матчеры для нетривиальных сравнений: `ElementsMatch` — те же элементы без учёта порядка, `JSONEq` — сравнение по структуре JSON (а не побайтно), `WithinDuration` — время с допуском. Они дают понятные diff'ы, которые на голом `if` пришлось бы писать руками.

| Пакет | При провале | Когда использовать |
|--------|--------|--------|
| `assert.X` | `t.Error` — продолжает | независимые проверки, хотим увидеть все сразу |
| `require.X` | `t.Fatal` — останавливает | предусловия, без которых дальше нельзя |

**Важно:** `require` вызывает `t.Fatal`, поэтому его, как и сам `t.Fatal`, нельзя дёргать из дочерней горутины — только из горутины теста.

Помимо ассертов в testify есть `testify/mock` (фреймворк моков с ожиданиями) и `testify/suite` (объединение тестов в suite со своими setup/teardown — аналог тест-класса в JUnit).

## Q12. (!) Как делают mocking в Go?

В Go нет аннотаций вроде `@Mock` и проксирования классов. Подмена зависимостей строится на **интерфейсах** и неявной их реализации: production-код зависит от узкого интерфейса, а в тесте вы подставляете любую структуру, которая этот интерфейс реализует. Структурная типизация Go позволяет писать такой мок вручную — отдельной библиотеки для этого не требуется.

```go
// production
type UserRepo interface {
    FindByID(id int) (*User, error)
}

type UserService struct {
    repo UserRepo
}

func (s *UserService) GetUser(id int) (*User, error) {
    return s.repo.FindByID(id)
}

// test — ручной mock
type mockRepo struct {
    user *User
    err  error
}

func (m *mockRepo) FindByID(id int) (*User, error) {
    return m.user, m.err
}

func TestGetUser(t *testing.T) {
    s := &UserService{repo: &mockRepo{user: &User{Name: "Alice"}}}
    u, err := s.GetUser(1)
    assert.NoError(t, err)
    assert.Equal(t, "Alice", u.Name)
}
```

**Рекомендация:** объявляйте интерфейс **на стороне потребителя** и держите его узким (только нужные методы) — тогда ручной мок остаётся маленьким. Для простых случаев ручного мока достаточно; генераторы (gomock, mockery, см. Q13) оправданы, когда у интерфейса много методов или нужны проверки порядка и количества вызовов.

## Q13. Чем отличаются gomock, mockery и ручные моки?

Все три решают одну задачу — подменить интерфейс в тесте, — но по-разному балансируют простоту и контроль над вызовами:

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| Ручные моки | Простые, понятные, без тулинга | Boilerplate под каждый интерфейс |
| **gomock** (поддерживается Uber) | Генерация мока с ожиданиями вызовов и порядком | Сгенерированный код, нужен `mockgen` |
| **mockery** | Генерация моков по настраиваемым шаблонам, включая testify-стиль | Зависимость от CLI и его конфигурации |
| **testify/mock** | Идёт в составе testify | Многословный ручной API |

```bash
# gomock
mockgen -source=repo.go -destination=mock_repo.go

# mockery v3 — интерфейсы указывают в .mockery.yaml
mockery
```

```go
// gomock
mockRepo := NewMockUserRepo(ctrl)
mockRepo.EXPECT().FindByID(1).Return(&User{Name: "Alice"}, nil)
```

**Эмпирическое правило:** ручные моки удобны для простых интерфейсов; генераторы полезны, когда нужны настройки ожиданий или интерфейс велик. После изменения интерфейса сгенерированный код нужно обновить, иначе сборка покажет расхождение.

## Q14. (!) Как тестировать HTTP-хендлеры через httptest?

Хендлер — это обычная функция `(http.ResponseWriter, *http.Request)`, поэтому его можно вызвать напрямую, без поднятия сервера. Пакет `net/http/httptest` даёт две вещи для этого: `httptest.NewRequest` собирает тестовый запрос, а `httptest.NewRecorder` подставляет «писатель», который запоминает статус, заголовки и тело ответа.

```go
import "net/http/httptest"

func TestHandler(t *testing.T) {
    req := httptest.NewRequest("GET", "/users/1", nil)
    w := httptest.NewRecorder()

    UserHandler(w, req) // вызываем handler напрямую

    resp := w.Result()
    body, _ := io.ReadAll(resp.Body)

    assert.Equal(t, http.StatusOK, resp.StatusCode)
    assert.Contains(t, string(body), "Alice")
}
```

**Почему так лучше:** нет реального сетевого сокета и порта — тест быстрый и детерминированный, не зависит от занятости портов. Этот подход проверяет именно логику хендлера. Если же нужно протестировать всю цепочку с роутером и middleware, тот же `NewRecorder` можно подать на вход не голому хендлеру, а собранному `http.Handler` (роутеру).

## Q15. Зачем нужен `httptest.NewServer` при тестировании клиентов?

Если `httptest.NewRecorder` (Q14) проверяет хендлер без сети, то `httptest.NewServer` решает обратную задачу — протестировать **HTTP-клиент**. Он поднимает настоящий локальный сервер на случайном порте, отдаёт его адрес через `server.URL`, и клиент ходит туда по реальному HTTP. Это позволяет проверить, как клиент формирует запрос и разбирает ответ, не завися от внешнего сервиса.

```go
func TestUserClient(t *testing.T) {
    server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.URL.Path == "/users/1" {
            json.NewEncoder(w).Encode(User{Name: "Alice"})
            return
        }
        http.NotFound(w, r)
    }))
    defer server.Close()

    client := NewUserClient(server.URL)
    user, err := client.GetUser(1)
    assert.NoError(t, err)
    assert.Equal(t, "Alice", user.Name)
}
```

**Важные детали:**
- Обязательно `defer server.Close()` — иначе сервер и его горутины утекут между тестами.
- Адрес `server.URL` нужно передать клиенту как базовый — клиент должен быть параметризуемым по URL, иначе его не подменить.
- Это «integration-style» тест: реальный TCP-стек, но всё в памяти процесса — медленнее `NewRecorder`, зато проверяет клиент целиком.

## Q16. (!) Как писать benchmarks?

Бенчмарк — функция с именем `Benchmark*` и аргументом `*testing.B`. Начиная с Go 1.24 для новых бенчмарков предпочтителен `for b.Loop()`: он управляет повторениями и исключает setup перед циклом из замера. Старый цикл по `b.N` тоже поддерживается, но функция с ним может вызываться несколько раз при калибровке. Делить время на число повторений вручную не нужно.

```go
func BenchmarkAdd(b *testing.B) {
    for b.Loop() {
        Add(2, 3)
    }
}
```

Запуск:

```bash
go test -run='^$' -bench='^BenchmarkAdd$' -benchmem
```

Условный вывод:

```text
BenchmarkAdd-8   1000000000   0.30 ns/op   0 B/op   0 allocs/op
```

**Как читать вывод:** `BenchmarkAdd-8` — суффикс `-8` показывает `GOMAXPROCS`; дальше число итераций, `ns/op`, а с `-benchmem` ещё `B/op` и `allocs/op`. По умолчанию `-benchtime=1s` задаёт целевое время измерения, поэтому число повторений зависит от скорости операции. Форма `-benchtime=100x` задаёт число итераций.

**Подводный камень:** при старом цикле по `b.N` неиспользуемое вычисление может быть оптимизировано; результат нужно сделать наблюдаемым. Защита от удаления измеряемой работы действует внутри цикла, записанного в форме `for b.Loop() { ... }`.

## Q17. (!) Зачем нужны `b.ResetTimer`, `b.StopTimer`, `b.ReportAllocs`?

Эти методы управляют тем, *что именно* попадает в замер. Без них в результат может затечь время подготовки данных, и бенчмарк завысит стоимость операции.

```go
func BenchmarkSomething(b *testing.B) {
    // Setup — не считаем
    data := makeBigData()
    b.ResetTimer()
    b.ReportAllocs()

    for i := 0; i < b.N; i++ {
        process(data)
    }

    b.StopTimer()
    cleanup()
}
```

- `b.ResetTimer()` — сбросить накопленное время, счётчики аллокаций и пользовательские метрики. Состояние таймера сохраняется. В примере вызов после подготовки исключает её из замера.
- `b.StopTimer()` / `b.StartTimer()` — приостановить и возобновить замер; полезны, если внутри цикла есть подготовка, которую измерять не нужно.
- `b.ReportAllocs()` — включить отчёт по аллокациям (`B/op`, `allocs/op`) для конкретного бенчмарка, не указывая глобальный `-benchmem`.

С Go 1.24+ есть `b.Loop()` — он сам исключает setup до первого вызова из замера и защищает вызовы внутри тела цикла от удаления компилятором, поэтому `b.ResetTimer()` с ним обычно не нужен. Когда `b.Loop()` возвращает `false`, он останавливает таймер, и очистка после цикла тоже исключается:

```go
func BenchmarkSomethingLoop(b *testing.B) {
    setup()
    for b.Loop() { // вместо for i := 0; i < b.N; i++
        process()
    }
    cleanup()
}
```

## Q18. Что такое sub-benchmarks?

Sub-benchmarks — это бенчмарки, запущенные через `b.Run(name, func)`, по аналогии с subtests. Главный сценарий — прогнать один и тот же код на разных размерах входа и увидеть, как растёт время. Так можно проверить, согласуются ли измерения с ожидаемым масштабированием.

```go
func BenchmarkAdd(b *testing.B) {
    sizes := []int{10, 100, 1000, 10000}
    for _, size := range sizes {
        b.Run(fmt.Sprintf("size_%d", size), func(b *testing.B) {
            data := make([]int, size)
            b.ResetTimer()
            for i := 0; i < b.N; i++ {
                process(data)
            }
        })
    }
}
```

Условный вывод для трёх размеров:

```text
BenchmarkAdd/size_10-8       100000000   12 ns/op
BenchmarkAdd/size_100-8       10000000  120 ns/op
BenchmarkAdd/size_1000-8       1000000 1200 ns/op
```

По выводу видно масштабирование: время на операцию растёт примерно линейно с размером — это согласуется с O(n). Если бы при росте размера в 10 раз время росло в 100 раз, это сигнал о квадратичной сложности. Замеры нескольких размеров сами по себе не доказывают асимптотику. На результат также влияют кеш CPU и распределение входов. Для отдельного прогона размера 100 используйте `go test -run='^$' -bench='^BenchmarkAdd$/^size_100$'`. Шаблон после косой черты ограничивает выбор дочерним именем.

## Q19. Зачем нужен benchstat для сравнения результатов?

Один прогон бенчмарка зашумлён: на цифры влияют другие процессы, тепловой троттлинг и GC. `benchstat` сравнивает группы замеров «до» и «после», для обычных замеров времени показывает медианы с доверительными интервалами, относительное изменение и результат статистического теста. Он помогает отличить устойчивый сигнал от шума, но не заменяет одинаковые условия измерения.

```bash
go install golang.org/x/perf/cmd/benchstat@latest

# Бейзлайн
go test -run='^$' -bench=. -count=10 > old.txt

# После изменений
go test -run='^$' -bench=. -count=10 > new.txt

benchstat old.txt new.txt
```

Условный пример вывода:

```text
           │   old.txt   │               new.txt               │
           │   sec/op    │   sec/op     vs base                │
Process-8    1.200µ ± 2%   0.850µ ± 3%  -29.17% (p=0.001 n=10)
```

**Как читать:** медианное время операции сократилось примерно на 29%. Значения после `±` показывают оценку неопределённости медианы каждой серии. P-value показывает, насколько необычен результат сравнения при предположении об отсутствии различия между распределениями. Размер эффекта читают по дельте. Символ `~` означает, что на этих данных тест не обнаружил статистически значимого различия. Если практическое решение зависит от небольшой дельты, важно проверить разброс и повторить измерения.

**Рекомендация:** сохраните одинаковые входные данные, версию Go, параметры запуска и условия на машине. По возможности чередуйте замеры двух версий, чтобы постепенный нагрев или фоновая нагрузка меньше влияли на сравнение. `-count=10` задаёт число повторов в примере. Достаточность выборки зависит от разброса и размера эффекта, который требуется обнаружить.

## Q20. (!) Что такое fuzzing в Go (1.18+)?

Fuzzing — это автоматическая генерация входных данных для поиска тех значений, что ломают код (panic, неверный результат, нарушение инварианта). С Go 1.18 фаззинг встроен в `testing`: пишут функцию `Fuzz*` с `*testing.F`, задают через `f.Add` стартовые примеры (seed corpus), а в `f.Fuzz` формулируют проверку, которая должна выполняться **на любом входе**. Движок мутирует seed-данные и гоняет проверку, пытаясь найти контрпример.

```go
// Reverse разворачивает руны в строке. Пример находится в *_test.go
// в том же пакете, что и Reverse. Нужны импорты testing и unicode/utf8.
func TestReverseRunes(t *testing.T) {
    if got := Reverse("aя🙂"); got != "🙂яa" {
        t.Errorf("Reverse(%q) = %q; want %q", "aя🙂", got, "🙂яa")
    }
}

func FuzzReverse(f *testing.F) {
    // Seed corpus — стартовые примеры
    f.Add("hello")
    f.Add("aя🙂")
    f.Add("")

    f.Fuzz(func(t *testing.T, s string) {
        if !utf8.ValidString(s) { return } // свойство задано для валидного UTF-8
        rev := Reverse(s)
        doubleRev := Reverse(rev)

        if s != doubleRev {
            t.Errorf("Reverse(Reverse(%q)) = %q; want %q", s, doubleRev, s)
        }

        if !utf8.ValidString(rev) {
            t.Errorf("Reverse produced invalid UTF-8: %q", rev)
        }
    })
}
```

Запуск:

```bash
go test -fuzz='^FuzzReverse$' -fuzztime=10s
```

**Что происходит при находке:** движок пытается уменьшить контрпример в пределах бюджета минимизации. Если запись удалась, новый контрпример появляется в `testdata/fuzz/FuzzReverse/`. Обычный `go test` проверяет значения из этой папки и вызовов `f.Add`. Отдельные входы, которые движок сохранил в кэше ради покрытия, используются при активном фаззинге. Если записать контрпример не удалось, автоматической регрессии из файла не будет.

Двойной разворот и валидность UTF-8 проверяют два свойства. Их выполняет и функция, возвращающая исходную строку, поэтому отдельный пример проверяет ожидаемый порядок рун. Руна соответствует кодовой точке Unicode. Для разворота пользовательских символов, состоящих из нескольких кодовых точек, нужен другой контракт.

## Q21. Когда применять fuzzing?

Fuzzing окупается там, где есть **широкое пространство входов** и проверяемое свойство: результат, round-trip или хотя бы отсутствие аварийного завершения. Условия допустимого входа нужно явно задавать в fuzz target; без полезной проверки найденные входы мало что скажут.

**Хорошие кандидаты:**
- Парсеры (JSON, XML, собственные протоколы) — много пограничных и битых входов.
- Кодировщики/декодеры (URL, Base64) и любой код с round-trip-свойством `decode(encode(x)) == x`.
- Crypto-код — но осторожно: операции медленные, фаззинг идёт долго.
- Публичный API, принимающий пользовательский ввод, — туда приходит непредсказуемое.

**Плохо подходит:**
- Бизнес-логика без очевидного инварианта — нечего утверждать «для любого входа».
- Интеграционные тесты — слишком медленные для миллионов прогонов.

**Как это работает:** Фаззинг Go использует обратную связь по покрытию. Входы, расширяющие покрытие, пополняют корпус для дальнейших мутаций. За заданное время движок исследует часть пространства входов. Успешный прогон означает, что проверенные входы не нарушили заданное свойство.

## Q22. (!) Как получить HTML-отчёт coverage Go-тестов?

Покрытие в Go измеряется на уровне выполненных операторов (statements): `go test -cover` инструментирует приближённые базовые блоки и выводит долю операторов в выполненных блоках. Одна строка может содержать несколько операторов. Для детального анализа сохраняют профиль (`-coverprofile`), а затем смотрят его в браузере (`-html`) или текстом по функциям (`-func`).

```bash
go test -cover ./...
go test -coverprofile=cover.out ./...
go tool cover -html=cover.out  # web view
go tool cover -func=cover.out  # текстовый отчёт
```

Пример строки из вывода `go test -cover`:

```text
coverage: 87.5% of statements
ok      example.com/myapp  0.005s
```

**Режимы счёта (`-covermode`):**
- `set` (по умолчанию) — фиксирует факт выполнения блока.
- `count` — считает входы в блок. Частота выполнения сама по себе не показывает время работы.
- `atomic` — то же, что `count`, но счётчики атомарные. сохраняет корректность счётчиков при конкурентных обновлениях. При `-race` это режим по умолчанию.

По умолчанию каждый тест анализирует покрытие собственного пакета. Для сценария, в котором тест пакета API вызывает код другого пакета того же модуля, используйте, например, `go test -coverpkg=./... -coverprofile=cover.out ./...`. В профиль войдут совпавшие пакеты, участвующие в сборке тестов.

С Go 1.20 можно собрать приложение через `go build -cover`, запустить интеграционные сценарии с `GOCOVERDIR`, указав уже существующий каталог и обработать данные командой `go tool covdata`. Это покрытие работающего приложения, а не только тестового бинарника.

## Q23. Как читать coverage profile?

Файл профиля — это текст: первая строка задаёт режим, остальные описывают инструментированные участки кода и число операторов в каждом.

```text
mode: set
example.com/myapp/math.go:5.18,8.2 2 1
```

Формат строки: `файл:строкаНачала.колонка,строкаКонца.колонка количествоОператоров счётчик`. В примере блок из 2 операторов выполнился (счётчик 1). В режиме `set` счётчик — это 0/1, в `count`/`atomic` — число входов в блок.

Руками этот формат читать редко нужно: `go tool cover -html=cover.out` строит наглядную раскраску (зелёный — покрыто, красный — нет), а `-func` даёт процент по каждой функции.

Высокое покрытие показывает, что тесты прошли через измеряемые участки. Например, тест может выполнить строку с `a && b` только при ложном `a`. Отчёт не покажет, что правая часть вообще вычислялась, и не оценит проверку результата. Для такого условия нужны входы, на которых проверяются обе части и их влияние на результат.

## Q24. (!) Как build tags разделяют unit и integration тесты?

Build tags — это директивы `//go:build`, управляющие тем, попадёт ли файл в сборку. Файл `*_test.go` с условием `//go:build integration` входит в тестовую сборку, когда задан тег `integration`, например через `go test -tags=integration`. Какие тестовые функции запустятся, дополнительно определяет фильтр `-run`. Так медленные тесты, требующие БД, сети или Docker, отделяют от быстрых юнит-тестов, не пугая их флагами на каждом запуске.

```go
//go:build integration

package mypackage_test

// Здесь объявляют интеграционные тесты этого пакета.
```

```bash
# Только unit
go test ./...

# Unit и integration вместе
go test -tags=integration ./...
```

**Нюансы:**
- Директива `//go:build integration` стоит до объявления `package`. Перед ней допустимы пустые строки и комментарии. После директивы оставляют пустую строку.
- Тег `integration` — произвольное имя, его придумывает команда; популярная альтернатива тегам — пропуск через `if testing.Short() { t.Skip() }` плюс флаг `-short`.
- В CI обычно гоняют оба прогона: быстрый `go test ./...` на каждый коммит и `go test -tags=integration ./...` отдельной, более тяжёлой стадией.

## Q25. Как проверить Go-код с Postgres через Testcontainers?

Testcontainers — библиотека, которая на время теста поднимает реальную зависимость (Postgres, Kafka, Redis…) в контейнере, работающем через Docker-совместимый API. Тест получает адрес подключения и регистрирует очистку контейнера. Это позволяет проверить интеграцию с настоящей БД вместо мока.

```go
package mypackage_test

import (
    "context"
    "database/sql"
    "testing"
    "time"

    _ "github.com/jackc/pgx/v5/stdlib"
    "github.com/stretchr/testify/require"
    "github.com/testcontainers/testcontainers-go"
    "github.com/testcontainers/testcontainers-go/modules/postgres"
)

func TestPostgresConnection(t *testing.T) {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Minute)
    defer cancel()

    container, err := postgres.Run(ctx, "postgres:16-alpine",
        postgres.WithDatabase("mydb"),
        postgres.WithUsername("user"),
        postgres.WithPassword("pass"),
        postgres.BasicWaitStrategies(),
    )
    testcontainers.CleanupContainer(t, container)
    require.NoError(t, err)

    dsn, err := container.ConnectionString(ctx, "sslmode=disable")
    require.NoError(t, err)

    db, err := sql.Open("pgx", dsn)
    require.NoError(t, err)
    t.Cleanup(func() { require.NoError(t, db.Close()) })
    require.NoError(t, db.PingContext(ctx))

    var database string
    require.NoError(t, db.QueryRowContext(ctx, "SELECT current_database()").Scan(&database))
    require.Equal(t, "mydb", database)
}
```

**Что важно помнить:**
- Регистрируйте очистку контейнера сразу после возврата `Run`, до проверки ошибки: запуск мог создать ресурс и завершиться ошибкой позже. Зарегистрированное следом закрытие пула выполнится первым.
- Нужен запущенный Docker-совместимый контейнерный runtime, например Docker или настроенный Podman. Такие тесты часто выделяют тегом `integration` (Q24).
- `sql.Open` создаёт дескриптор пула и может отложить сетевое соединение. `PingContext` проверяет доступность, а запрос проверяет, что соединение ведёт в ожидаемую БД. Для проверки репозитория добавьте его миграции, вызов метода и проверку результата. `sslmode=disable` здесь относится к локальному тестовому контейнеру.

Подробнее — в [Testcontainers](../../testing/testcontainers-interview.md).

## Q26. (!) Где держать тесты — рядом с кодом или в отдельной директории?

Стандарт Go — **рядом с кодом**, в той же директории. Это не просто соглашение: расположение завязано на правила сборки. Тесты в каталоге пакета имеют доступ к unexported (white-box, Q2), а `go test` и IDE находят их без настройки.

**Почему рядом — лучше:**
- Доступ к unexported для white-box тестов.
- Тесты «переезжают» вместе с кодом при рефакторинге, не теряются и не устаревают.
- IDE автоматически показывает coverage прямо в файле.

**Минус** ровно один: при просмотре кода видны и тестовые файлы — но IDE умеют их сворачивать, а суффикс `_test.go` сразу отличает их от продакшена.

**Когда выносят отдельно:** самостоятельные интеграционные или сквозные сценарии, которые проверяют приложение целиком и используют публичные границы пакетов. Для обычных unit-тестов каталог пакета проще.

## Q27. (!) Зачем нужен `TestMain` (`testing.M`)?

Если в тестовом пакете объявлена функция `TestMain(m *testing.M)`, сгенерированная обёртка вызывает её в главной горутине тестового бинарника. Внутри `TestMain` вызов `m.Run()` запускает работу, выбранную флагами. Это могут быть тесты, примеры, бенчмарки или фаззинг. Общие ресурсы удобно подготовить перед вызовом и закрыть после него.

```go
func TestMain(m *testing.M) {
    setupDatabase()
    defer teardownDatabase()

    m.Run()
}
```

При возврате из `TestMain` отложенная очистка выполняется, а тестовая обёртка использует код результата `m.Run()`. Если требуется выбрать собственный код выхода, завершите очистку до вызова `os.Exit(code)`: он прекращает процесс без выполнения отложенных вызовов.

На входе в `TestMain` флаги ещё не разобраны. Если подготовка зависит от флага, например от `testing.Short()`, сначала вызовите `flag.Parse()`. К моменту вызова тестовых функций флаги уже разобраны.

Подготовка выполняется один раз **на вызов `TestMain` в конкретном процессе**. Повторные запуски бинарника и дочерние процессы фаззинга могут вызвать её снова. Для ресурсов отдельного теста используйте `t.Cleanup` (Q8).

## Q28. (!) Зачем запускать тесты с race detector?

Флаг `-race` включает инструментирование при сборке тестового бинарника и проверку обращений к памяти при его выполнении. Data race возникает, когда обращения к одной области памяти не упорядочены синхронизацией, хотя бы одно из них записывает значение и хотя бы одно является неатомарным.

```bash
go test -race ./...
```

**Как разобрать отчёт.** Если обработчик обновляет общий счётчик, а сборщик метрик читает его без общей синхронизации, тест может пройти по своим assertions. При обнаружении гонки детектор выведет стеки конфликтующих обращений и стеки создания горутин. По ним можно найти оба пути доступа и определить, где нужен общий mutex или атомарные операции на всех путях доступа к счётчику.

**Границы проверки.** Детектор видит только обращения, выполненные в этом прогоне. Если тесты обходят нужную ветку, можно запустить бинарник, собранный с `-race`, под реалистичной нагрузкой. Оценки Go для накладных расходов составляют 2–20× по времени и 5–10× по памяти. Фактические значения зависят от программы.
