# Вопросы на собеседовании: `Go Modules`

**Modules** — система управления зависимостями в Go, появилась в Go 1.11 (2018) и заменила подход на основе `GOPATH`. Она даёт воспроизводимые сборки, точные версии зависимостей через semantic versioning и поддержку приватных и проксируемых модулей. С Go 1.18 добавился workspace mode для одновременной работы с несколькими модулями.

Эта шпаргалка разбирает, что лежит в `go.mod` и `go.sum`, как Go выбирает версии (MVS), зачем нужны `replace`, vendoring и workspaces, как настроить GOPROXY/GOPRIVATE для приватных репозиториев и какие подводные камни ждут на собеседовании.

## Q1. (!) Что такое Go module?

**Module** — это коллекция Go-пакетов, которые версионируются и распространяются как единое целое. Корень модуля — директория, в которой лежит файл `go.mod`: всё, что внутри неё (и в подпапках без своего `go.mod`), принадлежит этому модулю.

```
myapp/
  ├── go.mod         ← module path, dependencies
  ├── go.sum         ← checksums
  ├── main.go        ← package main
  ├── handler/
  │   ├── user.go    ← package handler
  │   └── order.go
  └── service/
      └── user.go    ← package service
```

Ключевое понятие — **module path** (путь модуля), он задан в первой строке `go.mod`. Он совпадает с **import path** корня модуля: если path равен `github.com/myorg/myapp`, то пакет в подпапке `handler/` импортируется как `github.com/myorg/myapp/handler`. Path обычно совпадает с URL git-репозитория — так Go понимает, откуда скачивать код.

**Итог:** module — единица версионирования и распространения; границу модуля задаёт `go.mod`, а его path служит и адресом для импортов, и адресом для загрузки.

## Q2. (!) Зачем заменили GOPATH?

Старый подход на основе `GOPATH` не умел версионировать зависимости: код жил в одной глобальной папке, версия каждой библиотеки была единственной на всю систему, а сборки невозможно было воспроизвести. Modules решают именно эти проблемы.

**Как было (GOPATH):**
- Весь Go-код лежал в `$GOPATH/src/` — проект нельзя положить в произвольную папку.
- Одна версия каждой зависимости на всю систему: два проекта не могли использовать разные версии одной библиотеки.
- Версионирования не было — `go get` всегда тянул `master`, и сборка ломалась, как только в upstream что-то менялось.
- Чтобы зафиксировать зависимости, их копировали в `vendor/` в каждом репозитории вручную.

**Что из этого ломалось:**
- Сборки невоспроизводимы — сегодня и завтра `go get` мог принести разный код.
- Конфликты версий между проектами на одной машине.
- Боль с приватными модулями — нет внятного механизма аутентификации и кеширования.

**Как стало (modules):**
- Проект — любая директория с `go.mod`, не обязательно внутри `GOPATH`.
- У каждого проекта свой граф зависимостей.
- Точные версии зафиксированы в `go.mod`.
- Целостность кода проверяется по хешам в `go.sum`.
- Для коммитов без релиза есть pseudo-versions — можно зависеть от конкретного коммита.

**Итог:** GOPATH давал «одну версию на машину» без воспроизводимости; modules дают «свой граф версий на проект» с проверкой целостности.

## Q3. (!) go.mod — что в нём?

```go
module github.com/myorg/myapp

go 1.21

require (
    github.com/gorilla/mux v1.8.0
    github.com/lib/pq v1.10.9
    github.com/stretchr/testify v1.8.4 // indirect
)

require (
    github.com/davecgh/go-spew v1.1.1 // indirect
    github.com/pmezard/go-difflib v1.0.0 // indirect
)

replace github.com/oldname/lib => github.com/newname/lib v1.2.3

exclude github.com/old/buggy v1.0.0
```

`go.mod` — манифест модуля: его имя, требуемая версия Go и список зависимостей с точными версиями. Это первый файл, который читают `go build`, `go test` и IDE.

**Директивы:**
- `module` — path модуля (адрес для импортов и загрузки).
- `go` — минимальная версия Go, нужная для сборки. Влияет и на поведение тулчейна (например, как `go mod tidy` ведёт себя с indirect-зависимостями).
- `require` — список зависимостей с версиями: прямые (используются в коде напрямую) и косвенные (помечены `// indirect`).
- `replace` — переопределение источника или версии зависимости.
- `exclude` — запрет конкретной версии.

Комментарий `// indirect` означает, что модуль не импортируется напрямую в вашем коде, а подтянут как транзитивная зависимость через другую библиотеку.

**Итог:** `go.mod` — единственный источник правды о том, какие версии нужны проекту; редактируется обычно не руками, а командами `go get` и `go mod tidy`.

## Q4. (!) go.sum — для чего?

`go.sum` фиксирует **криптографические хеши** всех зависимостей (включая транзитивные) и служит «контрольной суммой» для проверки целостности скачанного кода. Если содержимое модуля изменилось по сравнению с зафиксированным хешем — сборка падает.

```
github.com/gorilla/mux v1.8.0 h1:i40aqfkR1h2SlN9hojwV5ZA91wcXFOvkdNIeFDP5koI=
github.com/gorilla/mux v1.8.0/go.mod h1:DVbg23sWSpFRCP0SfiEN6jmj59UnW/n46BH5rLB71So=
```

На каждый модуль в `go.sum` две строки: хеш самого кода (`h1:...`) и хеш его файла `go.mod` — так проверяется и содержимое, и метаданные.

**Зачем нужен:**
- **Защита от подмены кода.** Если кто-то перепишет тег в репозитории на вредоносный код, хеш не совпадёт.
- **Воспроизводимость.** Гарантия, что у всех собирается ровно тот же байт-в-байт код зависимостей.
- **Защита от supply chain attacks** — атак через подмену звеньев в цепочке зависимостей.

`go mod download` и `go build` сверяют хеши скачанного кода с `go.sum`; при расхождении — ошибка, сборка останавливается.

**Рекомендация:** не редактируйте `go.sum` вручную — он обновляется автоматически командами `go get` и `go mod tidy`. Но коммитьте его в git вместе с `go.mod`: без него воспроизводимость теряется.

## Q5. (!) Что делают go mod init, tidy, download?

```bash
# Инициализация — создаёт go.mod
go mod init github.com/myorg/myapp

# Tidy — добавляет используемые, удаляет неиспользуемые
go mod tidy

# Download — скачивает в кеш ($GOPATH/pkg/mod)
go mod download

# Vendor — копирует зависимости в vendor/
go mod vendor

# Verify — проверяет hash'и
go mod verify

# Why — почему этот модуль в зависимостях?
go mod why github.com/davecgh/go-spew
```

Краткая шпаргалка по командам `go mod`:

| Команда | Что делает |
|---------|-----------|
| `go mod init <path>` | Создаёт `go.mod` с указанным module path |
| `go mod tidy` | Синхронизирует `go.mod`/`go.sum` с реальными импортами в коде |
| `go mod download` | Скачивает модули в кеш `$GOPATH/pkg/mod` |
| `go mod vendor` | Копирует все зависимости в `vendor/` |
| `go mod verify` | Сверяет кеш зависимостей с хешами |
| `go mod why <mod>` | Объясняет, зачем этот модуль в графе зависимостей |

**Рекомендация:** `go mod tidy` — самая частая команда; запускайте её перед каждым коммитом, чтобы `go.mod` точно отражал реальные импорты — добавил недостающие зависимости и выкинул те, которые больше не используются.

## Q6. (!) Чем go get отличается от go install?

Команды решают разные задачи: `go get` управляет **зависимостями проекта** (правит `go.mod`), а `go install` ставит **исполняемый бинарник** в `$GOPATH/bin` и `go.mod` не трогает.

| Команда | Назначение |
|---------|------------|
| `go get` | Изменяет `go.mod` (добавляет/обновляет зависимость) |
| `go install` | Устанавливает binary в `$GOPATH/bin` |

```bash
# Добавить зависимость
go get github.com/gorilla/mux

# Обновить до последней
go get -u github.com/gorilla/mux

# Конкретная версия
go get github.com/gorilla/mux@v1.8.0

# Установить tool (локально, не в проект)
go install github.com/some/tool@latest
```

**Подводный камень:** с Go 1.16+ `go install` требует явно указывать версию через `@` (`@latest`, `@v1.2.3` или хеш коммита). Просто `go install github.com/some/tool` без версии теперь не работает вне модуля — это сделано, чтобы установка тула не зависела случайно от `go.mod` текущего проекта.

**Итог:** ставите зависимость в проект — `go get`; ставите CLI-утилиту в систему — `go install ...@version`.

## Q7. go list -m all — что показывает?

`go list -m all` выводит **полный список модулей** в графе зависимостей проекта (прямых и транзитивных) с выбранными версиями. Это рабочий способ увидеть, что реально попадёт в сборку.

```bash
go list -m all       # все модули в зависимостях
go list -m -u all    # с информацией о доступных обновлениях
go list -m -versions github.com/gorilla/mux  # все версии
```

Output:
```
github.com/myorg/myapp
github.com/davecgh/go-spew v1.1.1
github.com/gorilla/mux v1.8.0
github.com/lib/pq v1.10.9
...
```

Первая строка — сам ваш модуль, дальше — зависимости с выбранными MVS-версиями.

**Сценарии применения:**
- `go list -m all` — аудит: что вообще тянется в проект.
- `go list -m -u all` — флаг `-u` дописывает к каждой строке доступное обновление, удобно перед апгрейдом.
- `go list -m -versions <mod>` — посмотреть все опубликованные версии модуля, чтобы выбрать целевую.

## Q8. (!) Semantic versioning в Go?

Go строго требует **SemVer** (Semantic Versioning) для версий модулей: `vMAJOR.MINOR.PATCH`. Это не рекомендация, а часть контракта системы модулей — на номере версии Go строит и выбор зависимостей (MVS), и правила совместимости.

Смысл каждой части номера:

| Версия | Изменение |
|--------|-----------|
| `v1.0.0` → `v1.0.1` | Bug fix, backwards compatible |
| `v1.0.0` → `v1.1.0` | New features, backwards compatible |
| `v1.0.0` → `v2.0.0` | **Breaking changes** |

**Префикс `v`** обязателен (`v1.2.3`, не `1.2.3`) — в git это означает теги вида `v1.8.0`.

```go
require github.com/gorilla/mux v1.8.0
```

**Подводный камень с `v0.x.x`:** мажор `0` означает pre-release — стабильность API не гарантируется, и автор имеет право вносить breaking changes даже в минорной версии. Поэтому к зависимостям на `v0` стоит относиться осторожнее: фиксировать точную версию и читать changelog перед обновлением.

## Q9. (!) Major versions (/v2, /v3) — особенности?

Главная особенность: начиная с major-версии 2, **module path обязан включать суффикс** `/v2`, `/v3` и т.д. Это правило называется *semantic import versioning*. Причина — major-версия по определению содержит breaking changes, и Go делает несовместимые версии буквально разными import path, а значит, разными пакетами.

```go
// v1
import "github.com/gorilla/mux"

// v2 — путь меняется!
import "github.com/gorilla/mux/v2"

// v3
import "github.com/gorilla/mux/v3"
```

Что это даёт:
- **Несколько major-версий одного модуля в одной программе** — `v1` и `v2` компилятор видит как разные пакеты и не конфликтует.
- **Плавная миграция** — можно перевести код на `v2` по частям, не ломая всё сразу.

В git мажорную версию публикуют одним из двух способов: тег `v2.0.0` в той же ветке с указанием `/v2` в module path внутри `go.mod`, либо отдельная поддиректория `/v2` со своим `go.mod` (subdirectory-based versioning).

**Итог:** в Go major-версия — это часть адреса пакета, а не просто номер; обновление с `v1` на `v2` всегда требует правки import path в коде.

## Q10. Что такое pseudo-versions (v0.0.0-yyyymmddhhmmss-...)?

**Pseudo-version** — это синтетический номер версии, который Go генерирует для конкретного коммита, когда подходящего git-тега нет. Так можно зависеть от любого коммита, даже если у модуля ещё нет ни одного релиза.

```
v0.0.0-20230401120000-abcdef123456
```

Формат: `vMAJOR.MINOR.PATCH-yyyymmddhhmmss-shortcommithash`. Дата коммита в имени нужна, чтобы pseudo-version корректно сравнивалась с обычными версиями по правилам SemVer (более свежий коммит «больше»).

```bash
go get github.com/some/repo@main  # latest commit на main
# go.mod
require github.com/some/repo v0.0.0-20230401120000-abcdef123456
```

**Сценарии применения:**
- Зависимость от bleeding-edge — нужен фикс, который уже в `main`, но ещё не вышел релизом.
- Форк без релизов — указываете конкретный коммит своего форка.

Это нормальный механизм, но временный: как только upstream выпустит тег, лучше перейти на обычную версию — её читать и поддерживать проще.

## Q11. Как работает Module Version Selection (MVS)?

**MVS (Minimal Version Selection)** — алгоритм, которым Go выбирает версию каждой зависимости в графе. Его называют «выбором минимальной версии», и это слово ключевое.

**Правило:** для каждого модуля берётся **минимальная** версия, которая удовлетворяет всем требованиям из `require` (как прямым, так и транзитивным). То есть Go берёт максимум из всех *запрошенных* версий модуля — но не более новую, чем кто-либо запросил.

```
A → B v1.2.0
A → C v1.0.0
C → B v1.5.0  // транзитивная зависимость

Результат: B v1.5.0 (минимум, удовлетворяющий обоим)
```

Здесь `B v1.5.0` — это минимальная версия, которая одновременно удовлетворяет требованию `v1.2.0` (от A) и `v1.5.0` (от C через транзитивную зависимость).

Чем MVS отличается от npm и Maven: там по умолчанию подтягивается **самая свежая** подходящая версия, поэтому сборка может незаметно «уехать» вперёд при появлении новых релизов. MVS же фиксируется на минимально достаточной версии и не двигается, пока вы явно не запросите обновление.

**Плюсы MVS:**
- **Меньше неожиданных breaking changes** — версия не растёт сама по себе.
- **Воспроизводимость** — при тех же `go.mod` результат всегда один и тот же.
- **Предсказуемость** — алгоритм простой и детерминированный, легко рассуждать о результате.

## Q12. (!) replace директива — когда использовать?

`replace` переопределяет, **откуда** или **какой версии** брать зависимость: можно подменить модуль локальной папкой, форком или зафиксировать конкретную версию. Левая часть `=>` — что заменяем, правая — на что.

```go
// Использовать локальную копию
replace github.com/myorg/lib => ../lib

// Использовать форк
replace github.com/old/lib => github.com/myfork/lib v1.0.1

// Конкретная версия
replace github.com/some/lib => github.com/some/lib v1.5.0

// Заблокировать версию
replace github.com/buggy/lib v1.0.0 => github.com/buggy/lib v1.0.1
```

**Сценарии применения:**
1. **Локальная разработка** — подменить зависимость папкой `../lib`, чтобы тестировать правки в библиотеке без публикации.
2. **Hotfix** — временно указать на форк с фиксом, пока upstream не выпустил релиз.
3. **Корпоративные форки** — в организации используется собственный форк библиотеки.
4. **Фиксация версии** — заменить проблемную версию на конкретную исправную.

**Важный нюанс:** `replace` действует **только в текущем модуле** и не транзитивен. Если вашу библиотеку подключат как зависимость, ваши `replace` к ним не применятся — downstream-проекту придётся прописать свои. Поэтому `replace` — инструмент приложения (main-модуля), а не публичной библиотеки.

## Q13. exclude директива?

`exclude` запрещает MVS выбирать конкретную версию модуля. Это «чёрный список» из одной версии: если какая-то зависимость через транзитивный граф тянет именно её, MVS пропустит её и возьмёт следующую совместимую.

```go
exclude github.com/buggy/lib v1.0.0
```

**Сценарий применения:** известный баг или security-issue ровно в одной версии, и вы хотите гарантированно её обойти.

**Подводный камень:** на практике `exclude` используют редко — обычно понятнее и надёжнее явно прописать `require`/`replace` на нужную версию, чем перечислять, какие версии запрещены.

## Q14. (!) Что такое vendoring (go mod vendor)?

**Vendoring** — копирование всех зависимостей прямо в репозиторий, в папку `vendor/`. После этого сборка идёт из локальных копий и вообще не обращается в сеть.

```bash
go mod vendor  # создаёт vendor/ с копией всех зависимостей
```

```
myapp/
  ├── go.mod
  ├── go.sum
  ├── vendor/
  │   ├── modules.txt
  │   └── github.com/gorilla/mux/...
  └── ...
```

Если папка `vendor/` есть и согласована с `go.mod`/`go.sum`, Go по умолчанию собирает из неё и не ходит в GOPROXY (это поведение можно переключить флагом `-mod=mod`).

**Плюсы:**
- **Воспроизводимость**, даже если зависимость удалили из proxy или git.
- **Air-gapped builds** — сборка без доступа в интернет (закрытый контур, CI без сети).
- **Аудит** — весь сторонний код лежит в одном месте, его видно в diff и в код-ревью.
- Закрывает корпоративные требования к контролю над зависимостями.

**Минусы:**
- Репозиторий распухает (легко десятки-сотни МБ на проект).
- Папку нужно вручную пересобирать командой `go mod vendor` после каждого изменения зависимостей.

**Когда применять:** с появлением modules + GOPROXY (immutable-кеш на стороне прокси) vendoring нужен реже — воспроизводимость даёт и сам proxy. Но он остаётся актуальным для security-sensitive проектов, закрытых контуров и команд, которым важно ревьюить сторонний код в одном PR.

## Q15. (!) Что такое go workspace mode (1.18+)?

**Workspace mode** (Go 1.18+) — режим, в котором вы одновременно разрабатываете несколько модулей и Go видит их локальные версии напрямую. Он решает старую боль: раньше, чтобы протестировать связку «приложение + соседняя библиотека», приходилось писать в `go.mod` временный `replace ... => ../lib` и следить, чтобы он случайно не попал в коммит. Workspace убирает эту необходимость — список локальных модулей живёт в отдельном файле `go.work`.

```
project/
  ├── go.work           ← workspace
  ├── module-a/
  │   ├── go.mod
  │   └── ...
  ├── module-b/
  │   ├── go.mod
  │   └── ...
  └── module-c/
      ├── go.mod
      └── ...
```

```bash
cd project
go work init ./module-a ./module-b
go work use ./module-c
```

Команды: `go work init` создаёт `go.work` со стартовым набором модулей, `go work use` добавляет ещё один. После этого при сборке любого модуля Go подставляет локальные версии остальных модулей из workspace вместо скачанных.

**Сценарий применения:** monorepo или связка «сервис + общая библиотека», которые правятся вместе. Удобно, потому что `go.mod` каждого модуля остаётся чистым — никаких временных `replace` в коммитах.

## Q16. go.work — что внутри?

```go
go 1.21

use (
    ./module-a
    ./module-b
    ./module-c
)

replace github.com/external/lib => github.com/myfork/lib v1.2.3
```

Файл `go.work` устроен похоже на `go.mod`: директива `go` с версией, блок `use` со списком локальных папок-модулей и (опционально) `replace` для внешних зависимостей.

**Рекомендация:** `go.work` обычно **не коммитят** в git (добавляют в `.gitignore`) — это локальная конфигурация конкретного разработчика, у каждого набор подключённых модулей свой. В CI собирают без него, чтобы проверка шла по реальным версиям из `go.mod`, как у конечного пользователя; либо `go.work` генерируют на лету именно под multi-module CI.

## Q17. (!) GOPROXY — что это и как работает?

`GOPROXY` — переменная окружения со списком прокси-серверов, откуда Go скачивает модули вместо прямого обращения к git. По умолчанию все публичные зависимости тянутся через `proxy.golang.org` — это слой кеширования и защиты между вами и репозиториями.

```bash
# Default
GOPROXY=https://proxy.golang.org,direct

# Возможные значения
GOPROXY=https://proxy.golang.org    # Google's official
GOPROXY=direct                       # напрямую с git
GOPROXY=off                          # запретить downloads
GOPROXY=https://my.corp.proxy        # корпоративный (Athens, Artifactory)
```

Значение читается как список через запятую: Go пробует прокси по очереди. Слово `direct` в конце — это fallback: «если ни один прокси не отдал модуль, тяни напрямую из git». Особый элемент `off` запрещает любые загрузки (полезно в CI, чтобы поймать незакоммиченные зависимости).

**Зачем нужен proxy:**
- **Доступность версий** — прокси кеширует модули как immutable-артефакты, поэтому версия остаётся доступной, даже если автор удалил репозиторий или переписал тег.
- **Защита от supply chain attacks** — однажды закешированный артефакт уже не подменить.
- **Скорость** — повторные загрузки идут из кеша, а не из исходного git.

`proxy.golang.org` — публичный бесплатный кеш от Google, используется по умолчанию.

## Q18. (!) GOPRIVATE для приватных модулей?

`GOPRIVATE` — список glob-паттернов module path, которые считаются приватными. Он нужен потому, что публичный `proxy.golang.org` и checksum-база `sum.golang.org` не имеют доступа к вашим закрытым репозиториям — и попытка пройти через них для приватного модуля просто упадёт с ошибкой.

```bash
GOPRIVATE=github.com/mycorp/*,gitlab.mycompany.com
```

Модули, попадающие под `GOPRIVATE`, Go обрабатывает иначе:
- **Не идут через публичный `GOPROXY`** — запрос напрямую к git (по сути включается `direct`).
- **Не проверяются в `GOSUMDB`** — публичная checksum-база про них всё равно ничего не знает.

Но настройки самого Go недостаточно — git тоже должен уметь авторизоваться в приватном репозитории:

```bash
git config --global url."https://${TOKEN}@github.com/".insteadOf "https://github.com/"

# или SSH
git config --global url."git@github.com:".insteadOf "https://github.com/"
```

**Итог:** `GOPRIVATE` говорит Go «эти модули не публичные, не води их через прокси и checksum-базу», а настройка git добавляет учётные данные для самой загрузки.

## Q19. Что такое GOSUMDB (checksum database)?

`GOSUMDB` указывает на публичную **checksum database** — глобальный реестр хешей всех публичных модулей. По умолчанию это `sum.golang.org`. Когда Go впервые скачивает модуль, он сверяет его хеш с этой базой и дописывает в ваш `go.sum` — так подмена кода в репозитории обнаруживается даже при самой первой загрузке, ещё до того как хеш попал в локальный `go.sum`.

```bash
GOSUMDB=off  # отключить (не рекомендуется!)
GOSUMDB=mycorp.com/sumdb  # корпоративная
```

**Подводные камни:**
- `GOSUMDB=off` отключает эту проверку целиком — небезопасно, так делать не стоит.
- Приватные модули (под `GOPRIVATE`) автоматически исключаются из проверки: публичная база про них всё равно ничего не знает, поэтому отдельно отключать GOSUMDB для них не нужно.

## Q20. Что такое Athens — private Go proxy?

[Athens](https://github.com/gomods/athens) — open-source Go proxy, который разворачивают у себя (self-hosting), чтобы получить собственный кеш модулей и контроль над зависимостями вместо публичного `proxy.golang.org`.

**Сценарии применения:**
- **Корпоративный кеш** — загрузки быстрее, чем из `proxy.golang.org`, особенно из удалённых офисов или регионов с плохой связностью.
- **Air-gapped среды** — единственный источник модулей в закрытом контуре без интернета.
- **Аудит и контроль** — централизованно решаете, какие зависимости пускать в сборки.
- **Persistence** — модуль остаётся доступным, даже если автор удалил репозиторий.

```bash
docker run -p 3000:3000 gomods/athens

# В клиенте
GOPROXY=http://athens.mycorp:3000
```

В клиенте достаточно указать адрес Athens в `GOPROXY` — дальше Go работает с ним как с обычным прокси.

**Альтернативы:** JFrog Artifactory и Sonatype Nexus с включённым Go-репозиторием (удобно, если в компании уже есть Artifactory/Nexus для Maven/npm), а также Buf — он попутно умеет и protobuf-зависимости.

## Q21. (!) Module path — соглашения?

Главное соглашение: **module path должен совпадать с URL git-репозитория** без схемы. Это не косметика — Go по этому пути физически находит, откуда скачивать код, так что `module github.com/myorg/myapp` обязан лежать именно в `github.com/myorg/myapp`.

```go
module github.com/myorg/myapp
module gitlab.mycorp.com/team/service
module example.com/internal/pkg
```

**Рекомендации:**
- Path совпадает с реальным адресом репозитория (хост + владелец + имя).
- Только нижний регистр — пути в Go регистрозависимы, разнобой ломает импорты на разных ОС.
- Слова разделяйте дефисом `-`, а не подчёркиванием `_` (нижнее подчёркивание в путях не принято и плохо читается).

## Q22. Структура multi-module проекта?

Сразу главный вывод: **в подавляющем большинстве случаев нужен один модуль с многими пакетами**, а не несколько модулей. Несколько модулей в одном репо — редкий случай для очень больших monorepos. Разберём оба варианта.

**Вариант 1: один модуль, много пакетов** (наиболее частый):

```
myapp/
  go.mod
  cmd/
    server/main.go
    cli/main.go
  internal/
    handler/
    service/
    repo/
  pkg/
    publicapi/
```

**Вариант 2: несколько модулей в одном репо** (редко):

```
mymonorepo/
  go.work
  service-a/
    go.mod
  service-b/
    go.mod
  shared-lib/
    go.mod
```

Несколько модулей оправданы, когда части репо нужно версионировать и релизить независимо. Иначе один модуль проще: одна команда `go test ./...`, один `go.mod`, никакой синхронизации версий между внутренними модулями.

**Полезный нюанс:** папка `internal/` — особенная для Go. Пакеты внутри неё доступны только коду из того же модуля (точнее, из родителя `internal/`). Это языковой механизм скрыть внутреннюю реализацию от внешних импортёров — то, что лежит в `internal/`, нельзя импортировать из чужого модуля.

## Q23. (!) Как обновить зависимости?

Базовая команда — `go get -u`: флаг `-u` («update») разрешает поднимать версию в пределах того же major, то есть до свежих minor и patch. После любого обновления стоит прогнать `go mod tidy`, чтобы подчистить `go.mod`/`go.sum`.

```bash
# Обновить ОДНУ зависимость до latest minor/patch
go get -u github.com/gorilla/mux

# До конкретной версии
go get github.com/gorilla/mux@v1.8.0

# Все зависимости до latest
go get -u ./...

# Только patch updates
go get -u=patch ./...

# Tidy после
go mod tidy
```

Разберём флаги:
- `go get -u <mod>` — поднять одну зависимость до свежих minor/patch.
- `go get <mod>@<version>` — зафиксировать ровно нужную версию (в том числе откатиться назад).
- `go get -u ./...` — обновить все зависимости до latest minor/patch.
- `go get -u=patch ./...` — только patch-обновления (консервативнее, меньше риск сломать совместимость).

**Подводный камень — обновление major (v1 → v2) не делается флагом `-u`.** Поскольку major-версия живёт в import path, Go не станет молча подставлять `/v2`. Менять путь нужно вручную в коде:

```go
// Было
import "github.com/gorilla/mux"

// Стало
import "github.com/gorilla/mux/v2"
```

## Q24. Минорная и патч-версии — auto update?

Нет — **Go никогда не обновляет зависимости сам**. Версии в `go.mod` зафиксированы, и это прямое следствие MVS: версия меняется только когда вы явно запускаете `go get`. Это и есть гарантия воспроизводимости — сборка не «уезжает» вперёд между запусками.

Если автообновление нужно, его настраивают внешними инструментами, которые открывают PR с обновлением, а решение оставляют за вами:
- **Dependabot** (GitHub) — открывает PR при выходе новых версий.
- **Renovate** — гибкий аналог Dependabot с тонкой настройкой правил.
- **`go get -u` в CI по расписанию** (например, раз в неделю) с автосозданием PR.

**Подводный камень:** даже patch-обновление может принести breaking change — SemVer лишь обещает совместимость, но не гарантирует её на 100%. Поэтому обновления всегда прогоняйте через PR с ревью и прохождением тестов, а не катите автоматически в прод.

## Q25. (!) Что такое diamond dependency problem?

«Ромбовидная» проблема возникает, когда **два разных пути в графе зависимостей ведут к разным major-версиям** одной и той же библиотеки. В Java и npm это классический источник боли, а в Go она решается за счёт того, что major-версия зашита в import path.

```
A → B v1.0.0 → D v1.0.0
A → C v1.0.0 → D v2.0.0
```

Здесь `B` тянет `D v1`, а `C` тянет `D v2`. В Java/npm это конфликт: рантайм может загрузить только одну версию класса/пакета, и кто-то останется со «своей» несовместимой. В Go конфликта нет — `v1` и `v2` имеют разные import path:

```go
import "example.com/d"        // v1
import "example.com/d/v2"      // v2
```

Для компилятора это **два разных пакета**, поэтому обе версии спокойно живут в одной программе одновременно.

**Итог:** ромбовидная проблема в Go относится только к разным major-версиям и снимается semantic import versioning. А вот разные minor/patch одной major-версии diamond не создают — там MVS просто выбирает одну версию для всех.

## Q26. Indirect зависимости — что это?

Indirect-зависимость — это модуль, который попал в ваш граф не из-за прямого импорта в коде, а через цепочку чужих зависимостей. В `go.mod` он помечен комментарием `// indirect`.

```go
require (
    github.com/gorilla/mux v1.8.0
    github.com/davecgh/go-spew v1.1.1 // indirect
)
```

Комментарий `// indirect` означает, что модуль **не импортируется в вашем коде напрямую** — он попал в `go.mod` только потому, что его требуют другие зависимости. Прямые зависимости (без `// indirect`) — те, что вы реально импортируете в своих файлах.

Indirect-запись появляется, когда:
- транзитивная зависимость требует модуль, у которого в `go.mod` не указана своя версия (например, старый модуль без `go.sum`-полноты), и Go вынужден зафиксировать выбранную версию у вас;
- модуль нужен только для тестов или непрямого использования.

**Рекомендация:** не редактируйте indirect-записи руками — ими полностью управляет `go mod tidy`. Он сам добавит нужные и удалит лишние, как только вы синхронизируете `go.mod` с кодом.

## Q27. (!) Что делать, если нужен форк зависимости?

**Сценарий:** в `github.com/some/lib` есть баг, а upstream молчит и релиз с фиксом не выходит. Ключевой инструмент здесь — `replace`: он перенаправляет import-путь оригинала на ваш форк, не требуя править все импорты в коде.

**Шаг 1.** Форкните репозиторий на `github.com/myorg/some-lib` и внесите правку.

**Шаг 2.** Перенаправьте оригинал на форк в `go.mod`:
```go
replace github.com/some/lib => github.com/myorg/some-lib v1.0.1
```
Импорты в коде остаются прежними (`github.com/some/lib/...`) — Go подставит форк под капотом.

**Шаг 3.** Зафиксируйте версию форка. Поставьте на форк **новый git-тег** и укажите его, либо сошлитесь на конкретный коммит — тогда Go запишет pseudo-version:
```bash
go get github.com/myorg/some-lib@abc1234
```

**Долгосрочно:** оформите PR в upstream. Если примут — снимаете `replace` и возвращаетесь на официальную версию; если нет — поддерживаете форк сами.

**Корпоративный нюанс:** в больших компаниях зависимости часто проксируются через Artifactory или Athens с возможностью подменять артефакты централизованно — тогда форк раздаётся всем командам через прокси, без `replace` в каждом проекте.
