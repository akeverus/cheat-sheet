# Вопросы на собеседовании: `Rust`

`Rust` — системный язык программирования (с 2010, версия 1.0 в 2015), который даёт контроль над памятью на уровне `C`/`C++`, но **гарантирует безопасность памяти без сборщика мусора** за счёт системы владения, проверяемой компилятором. Главные применения: системное и встраиваемое ПО, высоконагруженные сервисы, инструменты CLI, WebAssembly, части браузеров и ОС.

## Q1. (!) Что такое Rust и зачем он нужен?

`Rust` — системный язык, который решает давнюю дилемму: либо контроль над памятью и производительность (`C`/`C++`), либо безопасность (языки с GC вроде `Java`/`Go`). `Rust` даёт и то, и другое: ручное управление памятью без сборщика мусора, но с **гарантией безопасности памяти на этапе компиляции**.

Достигается это системой **владения** (ownership): компилятор отслеживает, кто владеет каждым значением и как долго оно живёт, и отвергает код, который мог бы привести к use-after-free, двойному освобождению или гонке данных.

Зачем его выбирают:

- **Безопасность памяти без GC** — нет пауз сборщика, но и нет целого класса ошибок памяти.
- **Производительность уровня C/C++** — компиляция в нативный код, zero-cost abstractions.
- **Бесстрашная многопоточность** — гонки данных ловятся компилятором (см. [[rust-interview#Q29]]).
- **Современный инструментарий** — `cargo` (сборка + зависимости + тесты), отличные сообщения об ошибках.
- **Сильная система типов** — алгебраические типы, `Option`/`Result` вместо `null` и исключений.

**Где применяют:** компоненты браузеров (части `Firefox`), инфраструктура (`Cloudflare`, `Discord`, `Dropbox`), CLI-инструменты (`ripgrep`, `fd`), встраиваемые системы, WebAssembly, а с 2022 года — и в ядре `Linux`.

## Q2. (!) Чем Rust отличается от C++ и от Go?

**От C++:** `Rust` решает те же задачи (системное программирование, контроль над памятью, отсутствие GC), но безопасность памяти у него **проверяется компилятором по умолчанию**, а не лежит на дисциплине программиста. Нет неопределённого поведения в безопасном коде, нет «висячих» указателей, гонок данных. Цена — строгий компилятор и кривая обучения.

**От Go:** оба современны и удобны, но цели разные. `Go` выбирает простоту и имеет сборщик мусора с рантайм-паузами; `Rust` отказывается от GC ради предсказуемой производительности и контроля, но язык заметно сложнее.

| Аспект | C++ | Go | Rust |
|---|---|---|---|
| Безопасность памяти | на программисте | GC | компилятор (ownership) |
| Сборщик мусора | нет | есть | нет |
| Скорость | очень высокая | высокая | очень высокая |
| Сложность | высокая | низкая | высокая |
| Конкурентность | вручную | goroutines + GC | ownership + Send/Sync |

Грубо: `Go` — «простота и быстрая разработка сервисов», `Rust` — «контроль и безопасность без компромисса по скорости».

## Q3. Что такое zero-cost abstractions?

**Zero-cost abstraction** — принцип: высокоуровневые конструкции языка не должны стоить дороже, чем эквивалентный написанный вручную низкоуровневый код. «За то, что не используешь, не платишь; а за то, что используешь, нельзя написать лучше вручную».

Примеры в `Rust`:

- **Итераторы** компилируются в такой же эффективный код, как ручной цикл `for` с индексами (см. [[rust-interview#Q24]]).
- **Generics** мономорфизируются — компилятор генерирует специализированный код под каждый конкретный тип, без рантайм-диспетчеризации.
- **`Option`/`Result`** не добавляют накладных расходов: `Option<&T>` занимает столько же, сколько указатель (niche-оптимизация).

Это позволяет писать выразительный, безопасный код, не жертвуя производительностью, — ключевое отличие `Rust` от языков, где абстракции тянут рантайм-цену.

## Q4. (!) Что такое ownership?

**Ownership (владение)** — центральная идея `Rust`, заменяющая и ручное `free`, и сборщик мусора. Правила:

1. У каждого значения есть ровно один **владелец** (переменная).
2. Владелец может быть только один в каждый момент.
3. Когда владелец выходит из области видимости, значение автоматически освобождается (вызывается `drop`).

```rust
fn main() {
    let s = String::from("hello"); // s владеет строкой
    // ... используем s ...
} // s вышел из scope -> память освобождена автоматически
```

Поскольку владелец один и время его жизни известно компилятору, освобождение памяти **детерминировано** и не требует ни ручного управления, ни GC. Это устраняет утечки и use-after-free на этапе компиляции. Передача значения в функцию или присваивание по умолчанию **перемещает** владение (см. [[rust-interview#Q5]]).

## Q5. (!) Что такое move-семантика?

По умолчанию присваивание или передача значения, владеющего ресурсом (например `String`, `Vec`), **перемещает** владение, а не копирует данные. После перемещения прежняя переменная становится недействительной.

```rust
let s1 = String::from("hi");
let s2 = s1;        // владение перемещено в s2
// println!("{}", s1); // ОШИБКА: s1 больше не валиден (value moved)
println!("{}", s2);    // OK
```

Зачем так: если бы `s1` и `s2` оба «владели» одной кучей, при выходе из scope память освободилась бы дважды (double free). Move гарантирует ровно одного владельца. Это дёшево — перемещается только указатель/метаданные на стеке, сами данные в куче не копируются.

Типы, реализующие трейт `Copy` (простые значения на стеке — числа, `bool`, `char`), вместо перемещения **копируются** (см. [[rust-interview#Q6]]).

## Q6. (!) Copy и Clone — в чём разница?

- **`Copy`** — маркерный трейт для типов, которые можно дублировать побитово и дёшево (целиком лежат на стеке): `i32`, `bool`, `char`, `f64`, кортежи из `Copy`-типов. Для таких типов присваивание **копирует**, а не перемещает, и старая переменная остаётся валидной.
- **`Clone`** — трейт для **явного**, возможно дорогого, глубокого копирования (например, `String`, `Vec` дублируют данные в куче). Нужно вызывать метод `.clone()` явно.

```rust
let x = 5;
let y = x;        // Copy: x всё ещё валиден
println!("{x} {y}");

let s1 = String::from("hi");
let s2 = s1.clone(); // явное глубокое копирование
println!("{s1} {s2}"); // оба валидны
```

Правило: `Copy` — неявно и дёшево для простых стековых данных; `Clone` — явно и потенциально дорого для владеющих кучей типов. Тип не может быть `Copy`, если владеет ресурсом, требующим `drop`.

## Q7. (!) Что такое borrowing и ссылки?

Чтобы дать доступ к значению, не передавая владение, используют **ссылки** (borrowing — «заимствование»). Ссылка `&T` позволяет читать значение, не становясь владельцем.

```rust
fn len(s: &String) -> usize { // заимствует, не владеет
    s.len()
}

let s = String::from("hello");
let n = len(&s); // передали ссылку
println!("{s} {n}"); // s всё ещё валиден — владение не уходило
```

Два вида ссылок:

- **`&T`** — неизменяемая (shared) ссылка: можно читать, нельзя менять; таких ссылок может быть много одновременно.
- **`&mut T`** — изменяемая (exclusive) ссылка: можно менять, но она должна быть **единственной**.

Заимствование позволяет функциям работать со значениями, не забирая владение, что и делает код эргономичным. Правила, ограничивающие ссылки, проверяет borrow checker (см. [[rust-interview#Q8]]).

## Q8. (!) Каковы правила borrow checker?

**Borrow checker** — часть компилятора, проверяющая ссылки. Главное правило (XOR-инвариант):

> В любой момент для значения может существовать **либо** любое число неизменяемых ссылок (`&T`), **либо** ровно одна изменяемая (`&mut T`) — но не то и другое одновременно.

```rust
let mut s = String::from("hi");

let r1 = &s;      // OK
let r2 = &s;      // OK: несколько shared ссылок
// let w = &mut s; // ОШИБКА: нельзя &mut, пока живы &
println!("{r1} {r2}");

let w = &mut s;   // теперь OK: shared ссылки больше не используются
w.push_str("!");
```

Дополнительно: ссылка не может «пережить» значение, на которое указывает (нет висячих ссылок). Этот единственный инвариант на этапе компиляции исключает гонки данных и большинство ошибок памяти. Современный borrow checker использует **non-lexical lifetimes**: ссылка считается живой до последнего использования, а не до конца блока, что делает правила менее болезненными.

## Q9. (!) Что такое lifetimes и зачем аннотации?

**Lifetime (время жизни)** — это область кода, в течение которой ссылка валидна. Компилятор всегда отслеживает времена жизни, чтобы гарантировать: ссылка не переживёт данные. Иногда он не может вывести связь между временами жизни сам — тогда нужны **аннотации** (`'a`).

```rust
// Какая из двух ссылок возвращается? Компилятору нужна подсказка:
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Аннотация `'a` говорит: возвращаемая ссылка живёт не дольше, чем входные. Это не меняет реальное время жизни, а лишь **описывает связь** между ссылками, чтобы borrow checker мог проверить корректность.

Важно: благодаря правилам **lifetime elision** в большинстве простых случаев аннотации можно опускать — компилятор выводит их сам. Явные lifetimes нужны в основном при возврате ссылок и в структурах, хранящих ссылки.

## Q10. Какие базовые типы в Rust?

- **Целые:** `i8`..`i128`, `u8`..`u128`, а также `isize`/`usize` (размер указателя).
- **С плавающей точкой:** `f32`, `f64`.
- **Логический:** `bool`.
- **Символ:** `char` (скалярное значение Unicode, 4 байта).
- **Кортежи:** `(i32, f64, char)` — фиксированный набор разнотипных значений.
- **Массивы:** `[i32; 5]` — фиксированная длина; динамические — `Vec<T>`.
- **Строки:** `String` (владеющая) и `&str` (срез, см. [[rust-interview#Q22]]).

```rust
let n: i64 = 42;
let pi: f64 = 3.14;
let flag: bool = true;
let tup: (i32, &str) = (1, "one");
let arr: [u8; 3] = [1, 2, 3];
```

`Rust` строго типизирован и почти не делает неявных приведений: между числовыми типами нужно конвертировать явно (`as` или `try_into`). Числовые типы по умолчанию — `i32` для целых и `f64` для дробных.

## Q11. Какие бывают struct?

`struct` — пользовательский составной тип. Три формы:

```rust
// 1. С именованными полями
struct User { name: String, age: u32 }

// 2. Кортежный (tuple struct) — поля по позиции
struct Point(i32, i32);

// 3. Единичный (unit-like) — без полей
struct Marker;
```

Методы и ассоциированные функции задаются в блоке `impl`:

```rust
impl User {
    fn new(name: String, age: u32) -> Self { User { name, age } } // ассоциированная (конструктор)
    fn greet(&self) -> String { format!("Hi, {}", self.name) }    // метод (берёт &self)
}
```

В отличие от ООП-языков, у `Rust` **нет наследования классов**: переиспользование строится на композиции и трейтах (см. [[rust-interview#Q17]]).

## Q12. (!) enum и pattern matching?

`enum` в `Rust` — это **алгебраический тип-сумма**: значение является одним из вариантов, и варианты могут нести данные. Это гораздо мощнее enum в `C`/`Java`.

```rust
enum Shape {
    Circle(f64),          // несёт радиус
    Rectangle(f64, f64),  // ширину и высоту
    Nothing,
}

fn area(s: &Shape) -> f64 {
    match s {
        Shape::Circle(r) => std::f64::consts::PI * r * r,
        Shape::Rectangle(w, h) => w * h,
        Shape::Nothing => 0.0,
    }
}
```

**`match`** — выражение сопоставления с образцом, которое **обязано быть исчерпывающим**: компилятор требует обработать все варианты (или поставить `_`). Это исключает забытые случаи. Pattern matching умеет деструктурировать структуры, кортежи, ссылки и связывать значения. `enum` + `match` — основа моделирования состояний и таких типов, как `Option` и `Result`.

## Q13. (!) Option — как Rust заменяет null?

В `Rust` **нет `null`**. Отсутствие значения выражается типом `Option<T>` — enum с двумя вариантами: `Some(значение)` или `None`.

```rust
fn find(v: &[i32], target: i32) -> Option<usize> {
    for (i, &x) in v.iter().enumerate() {
        if x == target { return Some(i); }
    }
    None
}

match find(&[1, 2, 3], 2) {
    Some(i) => println!("found at {i}"),
    None => println!("not found"),
}
```

Польза: компилятор **заставляет** обработать вариант `None` перед доступом к значению — нельзя случайно разыменовать «null». Это устраняет целый класс ошибок (null pointer exceptions). Для удобной работы есть методы: `unwrap` (паника при `None`), `unwrap_or`, `map`, `and_then`, `if let`. Тони Хоар назвал изобретение null «ошибкой на миллиард долларов» — `Option` решает её на уровне системы типов.

## Q14. (!) Result и обработка ошибок?

В `Rust` нет исключений для восстановимых ошибок. Вместо них функция возвращает `Result<T, E>` — enum: `Ok(значение)` при успехе или `Err(ошибка)` при сбое.

```rust
use std::num::ParseIntError;

fn parse(s: &str) -> Result<i32, ParseIntError> {
    s.parse::<i32>() // вернёт Ok(n) или Err(e)
}

match parse("42") {
    Ok(n) => println!("got {n}"),
    Err(e) => println!("error: {e}"),
}
```

Ключевая идея: ошибка — это **обычное значение**, которое нельзя проигнорировать незаметно (компилятор предупреждает о неиспользованном `Result`). Это делает пути ошибок явными в сигнатурах. Для краткого проброса есть оператор `?` (см. [[rust-interview#Q15]]), а для невосстановимых ситуаций — `panic!` (см. [[rust-interview#Q16]]).

## Q15. (!) Как работает оператор вопроса для проброса ошибок?

Оператор `?` — краткая форма «верни ошибку наверх, если она есть, иначе извлеки значение». Применяется к `Result` (и `Option`).

```rust
fn read_number(s: &str) -> Result<i32, std::num::ParseIntError> {
    let n = s.parse::<i32>()?; // если Err — функция сразу вернёт этот Err
    Ok(n * 2)                  // если Ok — n содержит значение, идём дальше
}
```

`expr?` разворачивается примерно в: «если `Ok(v)` — подставить `v`; если `Err(e)` — `return Err(e.into())`». Благодаря `.into()` тип ошибки автоматически конвертируется к типу ошибки функции (если есть `From`-преобразование), что удобно для агрегирования разных ошибок. `?` убирает шаблонный `match` на каждом шаге и делает «happy path» читаемым, сохраняя явную обработку ошибок. Работает только в функциях, возвращающих `Result`/`Option` (или совместимый тип).

## Q16. panic или Result — когда что?

- **`Result`** — для **восстановимых** ошибок, которые вызывающий код может осмысленно обработать: файл не найден, неверный ввод, сетевой сбой. Это часть контракта функции.
- **`panic!`** — для **невосстановимых** ошибок и нарушений инвариантов (баг в программе): выход за границы массива, недостижимая ветка, нарушенное предусловие. Паника разворачивает стек (или прерывает процесс) и обычно завершает поток.

```rust
let v = vec![1, 2, 3];
// v[10];                 // паника: выход за границы (это баг)
let x = v.get(10);        // Option: None — нормально обрабатывается

// unwrap паникует при Err/None — для прототипов/тестов или "этого не может быть"
let n: i32 = "42".parse().unwrap();
```

Правило: библиотечный код почти всегда возвращает `Result` (решение принимает вызывающий), а `panic!`/`unwrap`/`expect` уместны в тестах, прототипах и там, где нарушение действительно означает баг, а не ожидаемую ситуацию.

## Q17. (!) Что такое trait?

**Trait** — это набор методов, описывающий поведение, которое тип может реализовать. Аналог интерфейсов в `Java`/`Go`, но мощнее: трейты поддерживают дефолтные реализации, ассоциированные типы и обобщённые ограничения.

```rust
trait Animal {
    fn name(&self) -> String;
    fn sound(&self) -> String;
    fn describe(&self) -> String {           // дефолтная реализация
        format!("{} говорит {}", self.name(), self.sound())
    }
}

struct Dog;
impl Animal for Dog {
    fn name(&self) -> String { "Пёс".into() }
    fn sound(&self) -> String { "гав".into() }
}
```

Трейты — основа полиморфизма в `Rust`. Их используют двумя способами: как ограничения для generics (статическая диспетчеризация) и как trait objects `dyn Trait` (динамическая) — см. [[rust-interview#Q18]]. Важное правило когерентности (orphan rule): реализовать трейт можно, только если трейт **или** тип определён в вашем крейте.

## Q18. (!) Static vs dynamic dispatch и trait objects?

Полиморфизм через трейты в `Rust` бывает двух видов:

- **Static dispatch (generics)** — `fn f<T: Trait>(x: T)`. Компилятор **мономорфизирует**: генерирует отдельную копию кода под каждый конкретный тип. Нет рантайм-затрат на диспетчеризацию, возможен инлайнинг, но бинарник больше.
- **Dynamic dispatch (trait objects)** — `fn f(x: &dyn Trait)` или `Box<dyn Trait>`. Вызов метода идёт через **vtable** в рантайме. Одна копия кода, можно хранить разнотипные объекты в одной коллекции, но есть небольшая рантайм-цена и нет инлайнинга.

```rust
// static: тип известен на этапе компиляции
fn print_static<T: Animal>(a: &T) { println!("{}", a.describe()); }

// dynamic: разные типы за одним интерфейсом
let zoo: Vec<Box<dyn Animal>> = vec![Box::new(Dog)];
for a in &zoo { println!("{}", a.describe()); }
```

Выбор: generics — когда тип известен и важна скорость; `dyn Trait` — когда нужна гетерогенная коллекция или тип определяется в рантайме.

## Q19. (!) Generics и trait bounds?

**Generics** позволяют писать код, обобщённый по типам, без потери типобезопасности и (благодаря мономорфизации) без рантайм-затрат.

```rust
fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut max = &list[0];
    for x in list { if x > max { max = x; } }
    max
}
```

**Trait bounds** (`T: PartialOrd`) ограничивают, какие типы допустимы, и одновременно открывают доступ к методам трейта внутри функции. Без ограничения о `T` ничего не известно. Для нескольких ограничений: `T: Clone + Display`; для читаемости — `where`-клауза:

```rust
fn process<T>(item: T) where T: Clone + std::fmt::Debug { /* ... */ }
```

Generics применяются и к структурам (`struct Wrapper<T>`), и к трейтам, и к методам. Это основной механизм переиспользования кода в `Rust`.

## Q20. Что делает derive?

`#[derive(...)]` — атрибут, который автоматически генерирует реализацию некоторых стандартных трейтов, избавляя от ручного шаблонного кода.

```rust
#[derive(Debug, Clone, PartialEq)]
struct Point { x: i32, y: i32 }

let a = Point { x: 1, y: 2 };
let b = a.clone();              // Clone
println!("{a:?}");             // Debug ({:?})
assert_eq!(a, b);              // PartialEq
```

Часто выводимые трейты: `Debug` (отладочный вывод), `Clone`/`Copy`, `PartialEq`/`Eq` (сравнение), `PartialOrd`/`Ord` (упорядочивание), `Hash` (ключи в `HashMap`), `Default`. `derive` работает, если все поля типа тоже реализуют нужный трейт. Для нестандартного поведения трейт реализуют вручную.

## Q21. Какие основные коллекции в стандартной библиотеке?

- **`Vec<T>`** — динамический массив (растущий буфер в куче); самая частая коллекция.
- **`String`** — растущая UTF-8 строка (по сути `Vec<u8>` с гарантией валидного UTF-8).
- **`HashMap<K, V>`** — хеш-таблица; **`BTreeMap<K, V>`** — отсортированная по ключу.
- **`HashSet<T>` / `BTreeSet<T>`** — множества.
- **`VecDeque<T>`** — двусторонняя очередь.

```rust
let mut v = vec![1, 2, 3];
v.push(4);

use std::collections::HashMap;
let mut scores = HashMap::new();
scores.insert("Ann", 10);
if let Some(s) = scores.get("Ann") { println!("{s}"); }
```

Все коллекции подчиняются правилам владения: например, нельзя одновременно держать изменяемую ссылку на `Vec` и итерироваться по нему. Доступ по индексу `v[i]` паникует при выходе за границы; безопасный вариант — `v.get(i)`, возвращающий `Option`.

## Q22. (!) String и str — в чём разница?

Это два представления текста, и их различие — следствие системы владения:

- **`String`** — владеющая, изменяемая, растущая строка в куче. Аналог «своей» строки, которой можно управлять.
- **`&str`** (string slice) — **заимствованный** неизменяемый вид на последовательность UTF-8 байт: либо часть `String`, либо строковый литерал (который имеет тип `&'static str`).

```rust
let owned: String = String::from("hello");
let slice: &str = &owned[0..2];   // "he" — срез, заимствует
let literal: &str = "world";      // литерал — это &str

fn print_it(s: &str) { println!("{s}"); } // принимает и String (через &), и &str
print_it(&owned);
print_it(literal);
```

Правило хорошего тона: принимать `&str` в параметрах (универсальнее — подойдёт и `String`, и литерал), а `String` использовать, когда нужна владеющая, изменяемая строка. `String` относится к `&str` так же, как `Vec<T>` к срезу `&[T]` (см. [[rust-interview#Q23]]).

## Q23. (!) Что такое slices?

**Slice (срез)** — это ссылка на непрерывный участок коллекции, без владения им. Срез знает указатель на начало и длину (это «толстый указатель»).

```rust
let v = vec![1, 2, 3, 4, 5];
let middle: &[i32] = &v[1..4]; // [2, 3, 4] — срез, не копия

let s = String::from("hello");
let part: &str = &s[0..2];     // "he" — строковый срез
```

Зачем нужны: функция может работать с частью данных (или со всей коллекцией), не владея ими и не копируя. Например, `&[T]` принимает и `Vec`, и массив, и другой срез — это делает API гибким. Срез **заимствует** исходные данные, поэтому borrow checker не даст изменить или освободить коллекцию, пока срез жив. Срезы — пример zero-cost абстракции: они компилируются в простую пару «указатель + длина».

## Q24. (!) Как устроены итераторы и их ленивость?

Итераторы в `Rust` реализуют трейт `Iterator` с методом `next()`, возвращающим `Option<Item>`. Ключевое свойство — **ленивость**: адаптеры (`map`, `filter`, `take`) ничего не вычисляют, пока не запущен «потребитель» (`collect`, `sum`, `for`).

```rust
let v = vec![1, 2, 3, 4, 5];
let result: Vec<i32> = v.iter()
    .filter(|&&x| x % 2 == 0)  // ленивый адаптер
    .map(|&x| x * 10)          // ленивый адаптер
    .collect();                // потребитель -> запускает цепочку
// result == [20, 40]
```

Благодаря ленивости и мономорфизации такая цепочка компилируется в код, не уступающий ручному циклу (zero-cost). Есть три способа итерироваться: `iter()` (по `&T`), `iter_mut()` (по `&mut T`), `into_iter()` (забирает владение, по `T`). Итераторы — идиоматичный способ обработки коллекций, предпочтительнее ручных индексов.

## Q25. Замыкания и трейты Fn, FnMut, FnOnce?

**Замыкание (closure)** — анонимная функция, которая может **захватывать** переменные из окружения. В зависимости от того, как она использует захваченные данные, замыкание реализует один из трёх трейтов:

- **`Fn`** — захватывает по неизменяемой ссылке (только читает); можно вызывать многократно.
- **`FnMut`** — захватывает по изменяемой ссылке (меняет окружение); многократно.
- **`FnOnce`** — забирает владение захваченным; может быть вызвано только один раз.

```rust
let factor = 3;
let multiply = |x: i32| x * factor; // захватывает factor по ссылке (Fn)
println!("{}", multiply(5)); // 15

let mut count = 0;
let mut inc = || { count += 1; };   // меняет count -> FnMut
inc();
```

Ключевое слово `move` заставляет замыкание захватить переменные **по значению** (владением) — это часто нужно при передаче замыкания в другой поток. Эти трейты позволяют принимать замыкания как аргументы: `fn apply<F: Fn(i32) -> i32>(f: F)`.

## Q26. (!) Box, Rc и Arc — для чего?

Это **умные указатели** для случаев, когда обычного владения мало:

- **`Box<T>`** — размещает значение в куче с единственным владельцем. Нужен для рекурсивных типов (известный размер), больших данных и хранения trait objects (`Box<dyn Trait>`).
- **`Rc<T>`** (reference counting) — **разделяемое** владение в однопоточном коде: несколько `Rc` указывают на одни данные, которые освобождаются, когда счётчик ссылок дойдёт до нуля. Только для чтения (вместе с `RefCell` — для мутации).
- **`Arc<T>`** (atomic reference counting) — то же, что `Rc`, но потокобезопасно (счётчик атомарный), для разделения данных между потоками. Чуть дороже `Rc` из-за атомарных операций.

```rust
use std::rc::Rc;
let a = Rc::new(vec![1, 2, 3]);
let b = Rc::clone(&a);              // не копирует данные, +1 к счётчику
println!("count = {}", Rc::strong_count(&a)); // 2
```

Правило: `Box` — один владелец в куче; `Rc` — много владельцев в одном потоке; `Arc` — много владельцев между потоками. Циклы `Rc` могут течь — их разрывают через `Weak`.

## Q27. (!) Что такое внутренняя мутабельность?

**Interior mutability** — паттерн, позволяющий изменять данные через неизменяемую ссылку, перенося проверку правил заимствования с этапа компиляции в **рантайм**. Нужен, когда статических гарантий недостаточно (например, мутация внутри `Rc`).

- **`Cell<T>`** — для `Copy`-типов: даёт `get`/`set` значения целиком, без ссылок.
- **`RefCell<T>`** — даёт `borrow()`/`borrow_mut()`, проверяя XOR-правило в рантайме; при нарушении — **паника**.

```rust
use std::cell::RefCell;
let data = RefCell::new(5);
*data.borrow_mut() += 1;        // мутируем через неизменяемую переменную
println!("{}", data.borrow());  // 6

// let a = data.borrow_mut();
// let b = data.borrow_mut();   // паника в рантайме: двойной mut borrow
```

Частая связка — `Rc<RefCell<T>>`: разделяемое владение + возможность мутации (например, для графов и деревьев). Плата за гибкость — проверки переезжают в рантайм и могут паниковать, тогда как обычный borrow checker ловит ошибки при компиляции.

## Q28. (!) Как Rust управляет памятью без GC?

`Rust` не использует ни ручной `free`, ни сборщик мусора. Память управляется на основе **владения и времени жизни**, известных компилятору:

- Каждое значение имеет одного владельца; когда владелец выходит из области видимости, автоматически вызывается деструктор (трейт **`Drop`**) и ресурс освобождается. Это паттерн **RAII** (захват ресурса есть инициализация).
- Поскольку момент освобождения определяется статически (по scope), он **детерминирован** — без пауз GC и без «висячих» ссылок.

```rust
struct Resource { name: String }
impl Drop for Resource {
    fn drop(&mut self) { println!("освобождаю {}", self.name); }
}
fn main() {
    let _r = Resource { name: "file".into() };
} // здесь автоматически вызовется drop(_r)
```

`Drop` управляет не только памятью, но и любыми ресурсами: файлами, сокетами, блокировками (например, `MutexGuard` освобождает мьютекс в `drop`). Итог: безопасность памяти и детерминированное освобождение — без рантайм-сборщика.

## Q29. (!) Как Rust обеспечивает безопасную многопоточность?

`Rust` распространяет гарантии владения на потоки и ловит **гонки данных на этапе компиляции** через два маркерных трейта:

- **`Send`** — тип можно безопасно **переместить** в другой поток.
- **`Sync`** — на тип можно безопасно **ссылаться** из нескольких потоков (`&T` является `Send`).

Компилятор разрешает делиться данными между потоками, только если типы реализуют эти трейты. Например, `Rc` **не** `Send` (его счётчик не атомарный) — попытка отправить его в поток не скомпилируется; для этого есть `Arc`.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];
for _ in 0..10 {
    let c = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        *c.lock().unwrap() += 1; // Mutex даёт эксклюзивный доступ
    }));
}
for h in handles { h.join().unwrap(); }
println!("{}", *counter.lock().unwrap()); // 10
```

Тот же borrow checker, что предотвращает ошибки памяти, предотвращает и гонки данных: общий мутабельный доступ возможен только через синхронизацию (`Mutex`, `RwLock`, атомики).

## Q30. Что такое fearless concurrency?

**Fearless concurrency** («бесстрашная многопоточность») — лозунг `Rust`: писать конкурентный код можно смело, потому что компилятор **не пропустит гонки данных**. Целый класс самых коварных, плавающих и трудновоспроизводимых багов многопоточности отлавливается на этапе компиляции, а не в проде.

Достигается это тем же, что и безопасность памяти:

- Правило «либо много `&T`, либо одна `&mut T`» исключает одновременный незащищённый доступ на запись.
- Трейты `Send`/`Sync` (см. [[rust-interview#Q29]]) гарантируют, что между потоками передаются только безопасные для этого типы.

В результате разработчик может выбирать любую модель (потоки + `Mutex`, каналы, `async`), не боясь, что забытая синхронизация тихо приведёт к гонке: код с потенциальной гонкой данных просто не скомпилируется.

## Q31. (!) Что такое unsafe и когда он нужен?

`unsafe` — блок или функция, где разрешены операции, которые компилятор не может проверить на безопасность. Это **не** отключение borrow checker целиком, а доступ к пяти «суперспособностям», в т.ч.:

- разыменование сырых указателей (`*const T`, `*mut T`),
- вызов `unsafe`-функций (включая FFI к `C`),
- доступ к `static mut` и изменяемым глобалам,
- реализация `unsafe`-трейтов.

```rust
let mut x = 5;
let p = &mut x as *mut i32;
unsafe {
    *p = 10; // разыменование сырого указателя
}
```

Когда нужен: интеграция с `C` (FFI), низкоуровневые структуры данных, оптимизации, работа с железом. Контракт: внутри `unsafe` **программист** отвечает за соблюдение инвариантов памяти. Идиома — прятать `unsafe` за безопасной абстракцией (как делает сама стандартная библиотека). Большая часть прикладного кода `unsafe` не использует вовсе.

## Q32. Что такое cargo и crates?

**`cargo`** — официальный инструмент сборки и менеджер пакетов `Rust`. Он закрывает почти весь рабочий цикл одной командой: создание проекта (`cargo new`), сборка (`cargo build`), запуск (`cargo run`), тесты (`cargo test`), проверка (`cargo check`), публикация.

**Crate** — единица компиляции и распространения: бинарный (исполняемый) или библиотечный. Зависимости (тоже крейты) подключаются из реестра **crates.io** через файл `Cargo.toml`:

```toml
[package]
name = "myapp"
version = "0.1.0"
edition = "2021"

[dependencies]
serde = { version = "1", features = ["derive"] }
```

`Cargo.lock` фиксирует точные версии для воспроизводимых сборок. Единый стандартный тулчейн (`cargo` + `rustup` + `clippy` + `rustfmt`) — одна из причин, по которым `Rust` приятен в повседневной работе.

## Q33. (!) Какие минусы у Rust?

- **Крутая кривая обучения.** Ownership, borrowing и lifetimes требуют времени; «борьба с borrow checker» — типичный опыт новичка.
- **Медленная компиляция.** Мономорфизация generics и проверки делают сборку крупных проектов небыстрой.
- **Многословность.** Явная обработка ошибок (`Result`, `?`), аннотации времён жизни и типов делают код более громоздким, чем в языках с GC.
- **Меньшая (хоть и растущая) экосистема,** чем у `Java`/`Python`/`JS`; для некоторых ниш меньше готовых библиотек.
- **Скорость разработки.** Строгий компилятор ловит ошибки рано, но прототипировать медленнее, чем на `Python`/`Go`.
- **Сложность асинхронности.** `async`/`await` мощны, но добавляют сложности (времена жизни в футурах, выбор рантайма вроде `tokio`).

Итог: `Rust` блистает там, где критичны производительность, безопасность памяти и контроль (системное ПО, инфраструктура). Для простых CRUD-сервисов или быстрых прототипов его строгость и цена обучения часто не окупаются — там удобнее язык с GC.
