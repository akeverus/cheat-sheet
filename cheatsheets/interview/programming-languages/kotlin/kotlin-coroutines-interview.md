## Q1. (!) Что такое корутины и зачем они нужны?

**Корутины** (`Coroutines`) — легковесные единицы выполнения, которые позволяют писать асинхронный код в обычном последовательном стиле. Это не потоки ОС, а абстракция более высокого уровня поверх потоков: библиотека `kotlinx.coroutines` сама раскладывает корутины по потокам пула и управляет их приостановкой и возобновлением.

Главная идея: вместо callback-ов и реактивных цепочек код пишется линейно, а в точках ожидания (I/O, таймер) корутина не блокирует поток, а **приостанавливается** — поток в это время обслуживает другие корутины.

Почему это удобно и эффективно:
- **Легковесность** — десятки тысяч корутин не создают проблем с памятью: каждая занимает порядка сотен байт против ~1 МБ стека у потока. Поэтому корутинами можно моделировать каждую задачу/запрос отдельно, не экономя на них.
- **Последовательный стиль** — асинхронный код читается сверху вниз как синхронный, без callback hell и ручной склейки результатов.
- **Кооперативная многозадачность** — корутина уступает поток только сама, в точках `suspend`; нет вытесняющего переключения и связанных с ним накладных расходов.
- **Structured concurrency** — жизненный цикл корутин привязан к scope, поэтому «забытых» фоновых задач и утечек не возникает.

```kotlin
// 100_000 корутин — без проблем
fun main() = runBlocking {
    repeat(100_000) {
        launch {
            delay(1000)
            print(".")
        }
    }
}
// Попробуйте то же с Thread — получите OutOfMemoryError
```

Ключевая мысль для собеседования: корутина — это не поток, а задача, которая выполняется на потоке из пула. Один поток обслуживает множество корутин именно потому, что приостановка освобождает его, не блокируя.

## Q2. (!) В чём разница между потоками и корутинами?

Коротко: поток — это ресурс ОС с вытесняющим планированием, а корутина — задача, исполняемая на потоке с кооперативным планированием. Корутины дешевле создавать, дешевле переключать и они приостанавливаются вместо блокировки.

| Характеристика | `Thread` | `Coroutine` |
|---|---|---|
| Управление | ОС (preemptive) | Библиотека (cooperative) |
| Память | ~1 МБ стека | ~несколько сотен байт |
| Создание | Дорого (системный вызов) | Дёшево (объект в heap) |
| Переключение контекста | Через ОС, дорого | В user-space, дёшево |
| Масштабируемость | Тысячи — предел | Миллионы — реально |
| Блокирование | Блокирует поток ОС | Приостанавливает, освобождая поток |

Как это раскладывается на потоки: несколько корутин мультиплексируются на небольшое число потоков ОС, и каждая в точке `suspend` отдаёт свой поток другой корутине. Например, на двух потоках `Thread 1` и `Thread 2` пять корутин могут распределиться так:

- `Thread 1` обслуживает `Coroutine A`, `Coroutine B` и `Coroutine E` — каждая из них в момент `suspend` освобождает поток для следующей.
- `Thread 2` обслуживает `Coroutine C` и `Coroutine D` тем же образом.

Главное отличие на практике — поведение при ожидании I/O. Поток на время ожидания блокируется и просто простаивает, занимая память и место в пуле. Корутина в той же ситуации **приостанавливается** и отдаёт поток другой работе. Поэтому небольшим числом потоков можно обслуживать тысячи одновременных запросов — это и есть причина, по которой корутины масштабируются лучше потоков.

## Q3. (!) Что такое `suspend`-функция и как она работает под капотом?

`suspend`-функция — функция, выполнение которой можно приостановить в точке ожидания без блокировки потока и позже возобновить с того же места. Ключевое слово `suspend` — это контракт: «здесь возможна приостановка», поэтому вызвать такую функцию можно только из другой `suspend`-функции или из тела корутины, где есть кому её возобновить.

```kotlin
suspend fun fetchUser(id: Long): User {
    val response = httpClient.get("/users/$id") // приостановка на I/O
    return response.body()                       // возобновление
}

suspend fun fetchUserWithPosts(id: Long): UserWithPosts {
    val user = fetchUser(id)                     // последовательный вызов
    val posts = fetchPosts(user.id)              // ещё одна приостановка
    return UserWithPosts(user, posts)
}
```

**Под капотом** никакой магии нет — компилятор Kotlin превращает `suspend`-функцию в конечный автомат (state machine) с помощью **Continuation Passing Style (CPS)**. Каждый suspend-вызов становится отдельным состоянием (`label`): дойдя до точки приостановки, функция сохраняет своё состояние в объекте `Continuation` и возвращает управление; при возобновлении она входит заново и по сохранённому `label` прыгает на нужное состояние.

Состояния и переходы такого автомата на примере `fetchUserWithPosts`:

1. **`Label0`** — вход при вызове функции; выполняется код до первого suspend-вызова.
2. suspend-вызов `fetchUser` приводит в состояние **`Suspended1`** (точка приостановки).
3. Возобновление с результатом переводит в **`Label1`**; выполняется код до следующего suspend-вызова.
4. suspend-вызов `fetchPosts` приводит в состояние **`Suspended2`**.
5. Возобновление с результатом переводит в **`Label2`**.
6. Из `Label2` функция выполняет `return` результата и завершается.

Технически компилятор добавляет каждой `suspend`-функции скрытый параметр `Continuation<T>` — «колбэк», которым она возобновляется. На уровне JVM сигнатура `suspend fun fetchUser(id: Long): User` превращается в `fun fetchUser(id: Long, cont: Continuation<User>): Any?`. Возвращаемое значение служит сигналом: если вернулся специальный маркер `COROUTINE_SUSPENDED` — функция приостановилась и результата пока нет; иначе вернулся готовый результат. Именно поэтому suspend-вызов не блокирует поток: при приостановке управление просто возвращается наверх.

## Q4. Как определить и запустить корутину?

Чтобы запустить корутину, нужны две вещи: **scope** (где она будет жить) и **билдер корутины** — функция, которая её создаёт: `launch`, `async`, `runBlocking`. Билдеры `launch`/`async` объявлены как расширения `CoroutineScope`, поэтому их всегда вызывают на каком-то scope.

```kotlin
// 1. Через runBlocking (блокирует текущий поток — только для main/тестов)
fun main() = runBlocking {
    launch {
        delay(100)
        println("World")
    }
    println("Hello")
}

// 2. Через CoroutineScope (рекомендуемый подход)
class UserService(
    private val scope: CoroutineScope = CoroutineScope(Dispatchers.Default + SupervisorJob())
) {
    fun refreshUsers() {
        scope.launch {
            val users = fetchUsers()
            cacheUsers(users)
        }
    }

    fun close() {
        scope.cancel() // отменяем все корутины при завершении
    }
}

// 3. Через coroutineScope (suspend-функция, структурированная)
suspend fun loadData() = coroutineScope {
    val user = async { fetchUser() }
    val posts = async { fetchPosts() }
    combine(user.await(), posts.await())
}
```

Какой из трёх вариантов выбрать:
- `runBlocking` — только точка входа: `main`, тесты, скрипты. Он блокирует поток, поэтому в обычном коде неприемлем.
- `CoroutineScope(...)` + `launch` — когда корутина должна жить вместе с компонентом (сервис, ViewModel); scope потом нужно явно закрыть через `cancel()`.
- `coroutineScope { }` — внутри suspend-функции, чтобы запустить параллельные подзадачи и дождаться их.

Не используйте `GlobalScope` в production-коде — это нарушает [structured concurrency](kotlin-coroutines-interview.md) и приводит к утечкам. Подробнее в вопросе Q12.

## Q5. (!) В чём разница между `launch` и `async`?

Оба билдера запускают корутину, но различаются по тому, нужен ли результат. `launch` — fire-and-forget: запустил и забыл, возвращает `Job` для управления. `async` — для вычисления, которое вернёт значение: возвращает `Deferred<T>`, и результат забирается через `await()`.

| | `launch` | `async` |
|---|---|---|
| Возвращает | `Job` | `Deferred<T>` (наследник `Job`) |
| Результат | Нет (fire-and-forget) | Получается через `await()` |
| Исключения | Пробрасываются в scope | Хранятся в `Deferred`, пробрасываются при `await()` |
| Когда использовать | Побочные эффекты, фоновые задачи | Параллельные вычисления с результатом |

```kotlin
// launch — для задач без результата
scope.launch {
    saveToDatabase(user)
    sendNotification(user.email)
}

// async — для параллельных вычислений
suspend fun loadDashboard(): Dashboard = coroutineScope {
    val profile = async { fetchProfile() }
    val orders = async { fetchOrders() }
    val recommendations = async { fetchRecommendations() }

    Dashboard(
        profile = profile.await(),
        orders = orders.await(),
        recommendations = recommendations.await()
    )
}
```

**Различие в обработке исключений** — самый частый вопрос на собеседовании. У `launch` исключение пробрасывается сразу же в scope (и обрабатывается `CoroutineExceptionHandler`). У `async` исключение «упаковано» в `Deferred` и всплывает только при вызове `await()`.

**Подводный камень:** `async` без `await()`. Тогда исключение из такой корутины не пробросится через `await` (его никто не вызывает), но при обычном `Job` оно всё равно отменит родительский scope — и упасть может в неожиданном месте, с неочевидным stacktrace. Поэтому каждый `async` либо ожидайте через `await()`, либо не используйте `async` там, где результат не нужен.

## Q6. В чём разница между асинхронностью и параллелизмом?

Это разные понятия, которые часто путают. **Асинхронность/конкурентность** (concurrency) — про *структуру*: способность вести несколько задач сразу, переключаясь между ними. Один повар, который чередует несколько блюд, — конкурентен, но не параллелен. **Параллелизм** (parallelism) — про *исполнение*: задачи реально работают одновременно на разных ядрах. Несколько поваров на разных плитах работают параллельно.

**Конкурентность** — способность обрабатывать несколько задач, переключаясь между ними; они могут идти на одном потоке, чередуясь в точках приостановки.

**Параллелизм** — одновременное выполнение задач на разных ядрах/потоках.

```kotlin
// Асинхронность без параллелизма (один поток, Dispatchers.Main)
suspend fun loadSequential() {
    val user = fetchUser()    // приостановка → поток свободен
    val posts = fetchPosts()  // приостановка → поток свободен
    show(user, posts)
}

// Параллелизм (задачи реально выполняются одновременно)
suspend fun loadParallel() = coroutineScope {
    val user = async(Dispatchers.IO) { fetchUser() }
    val posts = async(Dispatchers.IO) { fetchPosts() }
    show(user.await(), posts.await()) // обе загрузки идут одновременно
}
```

Вывод: корутины дают **конкурентность** из коробки — она следует из приостановки и не требует нескольких потоков. А вот **параллелизм** зависит от диспетчера: на однопоточном диспетчере (`Dispatchers.Main`) корутины конкурентны, но не параллельны; `Dispatchers.Default` использует пул из числа ядер CPU и даёт настоящий параллелизм.

## Q7. (!) Что такое `CoroutineContext` и из чего он состоит?

`CoroutineContext` — неизменяемый набор данных, который определяет, как корутина исполняется. По устройству это типобезопасная ассоциативная коллекция: каждый элемент сам себе ключ (по своему типу), поэтому в контексте не может быть двух диспетчеров или двух `Job` одновременно.

Основные элементы и за что отвечают:
- `Job` — жизненный цикл, отмена, иерархия родитель-дети.
- `CoroutineDispatcher` — на каком потоке/пуле выполнять корутину.
- `CoroutineName` — имя для отладки и логов.
- `CoroutineExceptionHandler` — обработка необработанных исключений.

```kotlin
// Контексты можно складывать оператором +
val context = Dispatchers.IO + CoroutineName("data-loader") + SupervisorJob()

val scope = CoroutineScope(context)

// Каждая корутина наследует контекст родителя с переопределением
scope.launch(Dispatchers.Default) {
    // Job — дочерний от scope.coroutineContext[Job]
    // Dispatcher — Dispatchers.Default (переопределён)
    // Name — "data-loader" (унаследовано)
}
```

Как работает наследование: дочерняя корутина берёт контекст родителя, накладывает сверху явно переданные элементы и получает **новый** `Job`. Условно — `childContext = parentContext + childOverrides + Job()`. Важный нюанс: `Job` не наследуется как есть, а каждый раз создаётся новый, который становится **потомком** родительского — именно так и выстраивается иерархия для structured concurrency. Всё остальное (диспетчер, имя) наследуется, пока не переопределено явно.

## Q8. (!) Какие `Dispatchers` существуют и когда какой использовать?

Диспетчер решает, на каком потоке выполнять корутину. Выбор простой: считаете на CPU — `Default`, ждёте блокирующий I/O — `IO`, трогаете UI — `Main`.

| Диспетчер | Пул потоков | Когда использовать |
|---|---|---|
| `Dispatchers.Default` | Общий пул, размер = CPU cores | CPU-интенсивные вычисления, сортировки, парсинг |
| `Dispatchers.IO` | Эластичный пул, до 64 потоков | Блокирующий I/O: файлы, JDBC, сеть |
| `Dispatchers.Main` | Главный поток UI | Обновление UI (Android) |
| `Dispatchers.Unconfined` | Без привязки к потоку | Тесты, специфические сценарии |

```kotlin
suspend fun processData(data: List<Item>) = coroutineScope {
    // CPU-работа на Default
    val processed = withContext(Dispatchers.Default) {
        data.map { heavyComputation(it) }
    }

    // I/O-работа на IO
    withContext(Dispatchers.IO) {
        database.saveAll(processed)
    }
}
```

Полезный факт: `Dispatchers.Default` и `Dispatchers.IO` используют **общий** пул потоков. Различается лишь лимит одновременно занятых потоков (число ядер для `Default`, до 64 для `IO`). Поэтому переход `withContext(Dispatchers.IO)` из `Default` зачастую не вызывает реального переключения потока — тот же поток просто меняет «лимитную группу». Это делает такие переключения дешёвыми.

Почему `IO` допускает много потоков, а `Default` — нет: блокирующий I/O большую часть времени ждёт, поэтому потоков должно быть с запасом; CPU-работа же, наоборот, не выигрывает от потоков больше числа ядер — лишние только добавят накладные расходы на переключение.

`Dispatchers.IO` можно расширить через `limitedParallelism(n)` для изоляции:

```kotlin
// Выделенный пул из 4 потоков для тяжёлых I/O-операций
val dbDispatcher = Dispatchers.IO.limitedParallelism(4)

suspend fun queryDb() = withContext(dbDispatcher) {
    jdbc.query("SELECT * FROM users")
}
```

## Q9. Что такое `withContext` и чем отличается от `async`?

Оба меняют контекст выполнения, но `withContext` — про **последовательное** переключение, а `async` — про **параллельный** запуск. `withContext` переключает контекст текущей корутины, выполняет блок и возвращает результат напрямую (без `await`), приостанавливая вызывающего до завершения. `async` создаёт **отдельную** корутину, которая идёт параллельно, и возвращает `Deferred`.

```kotlin
// withContext — последовательное переключение
suspend fun loadUser(): User = withContext(Dispatchers.IO) {
    repository.findUser()  // переключились на IO, дождались результата
}

// async — параллельный запуск
suspend fun loadAll() = coroutineScope {
    val user = async(Dispatchers.IO) { repository.findUser() }
    val orders = async(Dispatchers.IO) { repository.findOrders() }
    Pair(user.await(), orders.await())  // оба запроса параллельно
}
```

**Эмпирическое правило:** один результат с переключением контекста — `withContext`; несколько задач параллельно — `async` + `await`. Антипаттерн — `async { ... }.await()` сразу же на одной задаче: это `withContext` с лишней аллокацией `Deferred`, без всякой выгоды.

## Q10. (!) Что такое `structured concurrency`?

**Structured concurrency** — принцип, по которому у каждой корутины есть родитель, и её жизненный цикл строго привязан к области (`scope`). Идея та же, что у блочной структуры обычного кода: как функция не возвращается, пока не отработают все вложенные вызовы, так и scope не завершается, пока живы его корутины. Это превращает асинхронность в предсказуемую иерархию вместо россыпи независимых задач.

Из этого следуют четыре гарантии:

1. **Корутина не может «утечь»** — она всегда запускается внутри какого-то scope и принадлежит ему.
2. **Родитель ждёт детей** — scope (или `coroutineScope`) не завершится, пока не завершатся все дочерние корутины.
3. **Отмена распространяется вниз** — отмена scope отменяет всех детей и внуков.
4. **Ошибки распространяются вверх** — исключение в ребёнке отменяет родителя, а через него и остальных детей (если это не `SupervisorJob`).

Иерархия выглядит как дерево: `CoroutineScope` владеет корневым `Parent Job`, а у того есть дети и внуки:

- `Parent Job`
  - `Child 1` (запущен через `launch`)
  - `Child 2` (запущен через `async`)
    - `Grandchild` (запущен через `launch` внутри `Child 2`)

Отмена идёт вниз по этому дереву: `cancel()` на `Parent Job` отменяет `Child 1` и `Child 2`, а отмена `Child 2` доходит и до его `Grandchild`.

```kotlin
suspend fun fetchAllData() = coroutineScope {
    // Если любой async упадёт — отменятся все остальные
    val users = async { fetchUsers() }
    val products = async { fetchProducts() }

    processData(users.await(), products.await())
}
// Вызывающий код гарантированно получит результат или исключение
// Никаких "забытых" корутин, работающих в фоне
```

Без structured concurrency (например, при использовании `GlobalScope`) легко получить «зомби-корутины», которые продолжают работать после уничтожения компонента.

## Q11. (!) Что такое `CoroutineScope` и зачем он нужен?

`CoroutineScope` — это интерфейс всего с одним свойством `coroutineContext`. Несмотря на минимализм, он играет ключевую роль: задаёт границу жизненного цикла группы корутин и обеспечивает structured concurrency. Привязав scope к жизни компонента (через хранящийся в его контексте `Job`), вы получаете единую «ручку» отмены: `scope.cancel()` гасит все корутины разом, и забытых фоновых задач не остаётся.

```kotlin
// Создание scope с привязкой к жизненному циклу
class OrderService : AutoCloseable {
    private val scope = CoroutineScope(
        Dispatchers.Default + SupervisorJob() + CoroutineName("order-service")
    )

    fun processOrderAsync(order: Order) {
        scope.launch {
            validateOrder(order)
            saveOrder(order)
            notifyCustomer(order)
        }
    }

    override fun close() {
        scope.cancel() // все корутины будут отменены
    }
}
```

В Android доступны готовые scopes:
- `viewModelScope` — привязан к жизненному циклу `ViewModel`
- `lifecycleScope` — привязан к `Lifecycle` компонента

В серверных приложениях scope обычно создаётся вручную и привязывается к жизненному циклу сервиса или запроса.

## Q12. В чём разница между `GlobalScope` и scope с жизненным циклом?

`GlobalScope` — глобальный scope, привязанный к жизни всего приложения. Его опасность в том, что он **ни к чему не привязан**: корутины в нём не отменятся автоматически при уничтожении компонента, который их запустил. Это прямое нарушение structured concurrency — корутина «выпадает» из иерархии и живёт сама по себе.

```kotlin
// ПЛОХО — утечка корутины
class MyViewModel {
    fun load() {
        GlobalScope.launch {
            val data = fetchData() // продолжит работу после уничтожения ViewModel
            updateUI(data)         // crash: ViewModel уже уничтожена
        }
    }
}

// ХОРОШО — корутина отменится вместе с ViewModel
class MyViewModel : ViewModel() {
    fun load() {
        viewModelScope.launch {
            val data = fetchData()
            updateUI(data)
        }
    }
}
```

**Когда применять `GlobalScope`:** только для операций, которые действительно должны жить всё время работы приложения (фоновая синхронизация, отправка метрик) и не привязаны ни к какому компоненту. Во всех остальных случаях — scope с жизненным циклом (`viewModelScope`, `lifecycleScope` или собственный). Если сомневаетесь — значит `GlobalScope` не нужен.

## Q13. Что такое `coroutineScope` (функция) и чем отличается от `CoroutineScope` (конструктор)?

Их легко спутать из-за похожих имён, но это разные инструменты с разными ролями. Разница — в регистре первой буквы и в том, suspend это или нет:

- `CoroutineScope(context)` (с большой буквы) — **фабричная функция-конструктор**. Создаёт долгоживущий scope, который существует независимо и которым вы управляете вручную (закрываете через `cancel()`). Не suspend.
- `coroutineScope { }` (с маленькой) — **suspend-функция**. Создаёт временный вложенный scope, выполняет блок и приостанавливает вызывающего, пока не завершатся все дочерние корутины. По выходе из блока scope исчезает.

```kotlin
// coroutineScope — приостанавливает до завершения всех детей
suspend fun loadAllData(): Pair<User, List<Post>> = coroutineScope {
    val user = async { fetchUser() }
    val posts = async { fetchPosts() }
    Pair(user.await(), posts.await())
}
// Вызывающая корутина продолжится только когда обе задачи завершатся

// CoroutineScope — создаёт независимый scope
val myScope = CoroutineScope(Dispatchers.IO + SupervisorJob())
myScope.launch { /* живёт независимо от вызывающего кода */ }
```

Итого: `coroutineScope` — для параллельной декомпозиции внутри одной suspend-функции (запустить подзадачи и дождаться их). `CoroutineScope` — для создания scope с собственным, явно управляемым жизненным циклом (сервис, ViewModel).

## Q14. Что такое `runBlocking` и когда его использовать?

`runBlocking` — **блокирующий** билдер корутин и мост между обычным (синхронным) кодом и миром корутин. Он запускает корутину и **блокирует** текущий поток, пока она и все её дети не завершатся. Именно блокировка отличает его от `coroutineScope`, который приостанавливает (а не блокирует) вызывающую корутину.

```kotlin
// Допустимо: main-функция
fun main() = runBlocking {
    val result = async { computeAnswer() }
    println("Answer: ${result.await()}")
}

// Допустимо: тесты
@Test
fun `test coroutine`() = runBlocking {
    val result = myService.fetchData()
    assertEquals("expected", result)
}

// НЕДОПУСТИМО: внутри корутины или на Dispatchers.Main
scope.launch {
    runBlocking { /* DEADLOCK! */ }
}
```

**Когда применять:** только `main`, тесты и пограничный код, который вызывает suspend-функции из синхронного мира. В production-серверном коде `runBlocking` не используют: он держит занятым поток (в реактивном стеке это особенно дорого) и при вызове внутри уже работающей корутины — например, на `Dispatchers.Main` — может привести к `deadlock`. Вместо него пробрасывайте `suspend` дальше по цепочке вызовов и используйте `coroutineScope`.

## Q15. (!) Что такое `Job` и каков его жизненный цикл?

`Job` — это «ручка управления» корутиной: элемент `CoroutineContext`, который представляет саму единицу работы и её состояние. Через `Job` корутину отменяют (`cancel`), ждут (`join`) и встраивают в иерархию родитель-дети. У каждой корутины свой `Job`; `launch` возвращает его напрямую, а `Deferred` от `async` — это `Job` с результатом.

Переходы между состояниями:

- старт → **New**: создание через `Job()`;
- **New** → **Active**: `start()` или запуск через `launch`;
- **Active** → **Completing**: собственный код корутины завершился;
- **Completing** → **Completed**: все дочерние корутины завершились (финальное состояние);
- **Active** → **Cancelling**: пришёл `cancel()` или исключение;
- **Cancelling** → **Cancelled**: все дети отменены (финальное состояние).

Состояния жизненного цикла:
- **New** — создан, но ещё не запущен (для лениво стартующих корутин).
- **Active** — выполняется (обычное состояние сразу после `launch`).
- **Completing** — собственный код отработал, но `Job` ждёт завершения дочерних корутин (это и есть «родитель ждёт детей»).
- **Completed** — успешно завершён со всеми детьми.
- **Cancelling** — пришла отмена или исключение, идёт сворачивание (выполняются `finally`-блоки).
- **Cancelled** — отмена завершена; это финальное состояние, при котором `isCompleted` тоже `true`.

```kotlin
val job = scope.launch {
    println("Working...")
    delay(1000)
    println("Done")
}

println(job.isActive)      // true
println(job.isCompleted)   // false
println(job.isCancelled)   // false

job.cancel()               // переход в Cancelling
job.join()                 // ожидание завершения

println(job.isCancelled)   // true
println(job.isCompleted)   // true (Cancelled — финальное состояние)
```

Разница между `Job` и `CoroutineScope`: `Job` управляет состоянием одной корутины (или иерархии), а `CoroutineScope` — контейнер контекста для запуска корутин. Scope содержит `Job` как элемент контекста.

## Q16. Как отменить корутину и почему отмена кооперативна?

Отмена в корутинах **кооперативна**: `cancel()` не прерывает корутину силой, а лишь переводит её `Job` в состояние «отменяется». Реально остановиться корутина должна сама — это происходит автоматически в любой точке приостановки. Любая стандартная suspend-функция (`delay`, `yield`, `withContext`, сетевые и файловые операции) при возобновлении проверяет флаг отмены и бросает `CancellationException`.

```kotlin
val job = scope.launch {
    repeat(1000) { i ->
        println("Processing $i")
        delay(100) // <-- проверка отмены происходит здесь
    }
}

delay(350)
job.cancel()    // устанавливает флаг
job.join()      // ждём завершения
// или job.cancelAndJoin()
```

Отсюда главный подводный камень: если корутина крутит CPU-работу без единой точки приостановки, проверять флаг негде — и она **не отменится**, продолжая жечь процессор. Решение — самому вставить проверку через `isActive`, `ensureActive()` или `yield()`:

```kotlin
// ПЛОХО — не отменяется
val job = scope.launch(Dispatchers.Default) {
    var i = 0
    while (i < 1_000_000) {
        // Тяжёлое вычисление без проверки отмены
        i++
    }
}

// ХОРОШО — проверяем отмену
val job = scope.launch(Dispatchers.Default) {
    var i = 0
    while (isActive && i < 1_000_000) { // проверяем isActive
        i++
    }
}
```

Почему отмена сделана кооперативной, а не принудительной: жёсткое прерывание потока в произвольном месте (как `Thread.stop`) оставляет данные в несогласованном состоянии и не даёт корректно освободить ресурсы. Кооперативная модель гарантирует, что отмена случится только в безопасной точке, а `finally`-блоки успеют отработать.

## Q17. Что такое `yield` и `ensureActive`?

Обе функции вставляют в код точку проверки отмены вручную — пригодятся в долгих циклах без естественных точек приостановки. Разница в том, делают ли они что-то ещё: `yield()` вдобавок уступает поток другим корутинам, а `ensureActive()` только проверяет флаг и максимально дёшев.

| | `yield()` | `ensureActive()` |
|---|---|---|
| Тип | `suspend`-функция | Обычная функция |
| Действие | Приостанавливает корутину, отдаёт поток другим, проверяет отмену | Только проверяет `isActive`, бросает `CancellationException` |
| Когда использовать | В тяжёлых циклах, когда нужно дать другим корутинам поработать | Когда нужна только проверка отмены без приостановки |

```kotlin
// yield — приостанавливает и проверяет отмену
scope.launch {
    hugeList.forEach { item ->
        processItem(item)
        yield() // даём другим корутинам шанс выполниться
    }
}

// ensureActive — только проверяет, не приостанавливает
scope.launch {
    hugeList.forEach { item ->
        ensureActive() // бросит CancellationException если отменена
        processItem(item)
    }
}
```

**Эмпирическое правило:** нужна только отмена тяжёлого цикла — берите `ensureActive()`; хотите ещё и не «голодать» остальные корутины на одном диспетчере — `yield()`.

## Q18. Как обеспечить отмену при таймауте?

Для таймаутов в kotlinx.coroutines есть две функции — `withTimeout` и `withTimeoutOrNull`. Обе ограничивают время выполнения блока и по истечении срока отменяют его как обычную корутину. Разница в реакции на превышение: `withTimeout` бросает `TimeoutCancellationException`, а `withTimeoutOrNull` молча возвращает `null` — удобно для фоллбэка.

```kotlin
// withTimeout — бросает TimeoutCancellationException
try {
    val result = withTimeout(3000) {
        fetchDataFromSlowApi()
    }
} catch (e: TimeoutCancellationException) {
    println("Запрос превысил 3 секунды")
}

// withTimeoutOrNull — возвращает null при таймауте (удобнее)
val result = withTimeoutOrNull(3000) {
    fetchDataFromSlowApi()
} ?: fallbackValue
```

**Важный нюанс:** таймаут — это та же кооперативная отмена, что и в Q16. Если внутри блока нет точек приостановки, по истечении срока ничего не прервётся — отмена сработает только когда дело дойдёт до ближайшей проверки. Поэтому в тяжёлых вычислениях под таймаутом добавляйте `ensureActive()` или `yield()`, иначе `withTimeout(3000)` может проработать гораздо дольше трёх секунд.

## Q19. (!) Как распространяются исключения в корутинах?

Это одна из самых каверзных тем на собеседовании, потому что поведение зависит от билдера и от типа `Job`. Базовый принцип structured concurrency: непойманное исключение в дочерней корутине отменяет родителя, а тот — всех остальных детей (ошибка распространяется вверх по иерархии). Но *момент* всплытия исключения различается:

- **`launch`** — исключение всплывает **немедленно**: отменяет родительский `Job` и вместе с ним всех соседних детей, после чего попадает в `CoroutineExceptionHandler`.
- **`async`** — исключение **откладывается**: сохраняется в `Deferred` и пробрасывается тому, кто вызовет `await()`. (При этом с обычным `Job` оно всё равно отменит родителя — см. Q5.)

Это можно представить так. У `Scope` есть `Parent Job` с тремя детьми, запущенными через `launch`:

- `Child 1` — работает нормально;
- `Child 2` — бросает исключение (✗);
- `Child 3` — работает нормально.

Исключение из `Child 2` распространяется вверх к `Parent Job`, и тот вызывает `cancel()` для `Child 1` и `Child 3` — то есть сбой одного ребёнка отменяет соседей.

```kotlin
// Исключение в одном ребёнке отменяет всех
scope.launch {
    launch { fetchUsers() }           // будет отменена
    launch { error("Boom!") }         // ← исключение
    launch { fetchProducts() }        // будет отменена
}
```

Чтобы сбой одного ребёнка **не** отменял соседей, нужен `SupervisorJob`/`supervisorScope` (Q20). А чтобы корректно поймать всплывающее исключение — `CoroutineExceptionHandler` для `launch` (Q21) или `try/catch` вокруг `await()` для `async`. Подробнее об обработке исключений — в [вопросах по исключениям Kotlin](kotlin-exceptions-interview.md).

## Q20. (!) Что такое `SupervisorJob` и `supervisorScope`?

`SupervisorJob` — особая разновидность `Job`, которая разрывает «горизонтальную» отмену: **сбой одного ребёнка не отменяет соседних детей**. Обычный `Job` при ошибке ребёнка отменяет родителя, а тот — всех остальных детей; `SupervisorJob` эту цепочку прерывает — ошибка идёт только вверх к самому supervisor-у, но не «в стороны». Каждый ребёнок изолирован и отвечает за свои ошибки сам.

С `SupervisorJob` картина другая. У `Scope` есть `SupervisorJob` с тремя детьми:

- `Child 1` — работает нормально;
- `Child 2` — бросает исключение (✗);
- `Child 3` — работает нормально.

Исключение из `Child 2` уходит вверх к `SupervisorJob`, но тот **не отменяет** `Child 1` и `Child 3` — они продолжают работать. Горизонтальная отмена разорвана.

```kotlin
// SupervisorJob в scope — дети независимы
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

scope.launch { fetchUsers() }         // продолжит работу
scope.launch { error("Boom!") }       // упадёт, но не отменит остальных
scope.launch { fetchProducts() }      // продолжит работу

// supervisorScope — аналог для suspend-функций
suspend fun loadDashboard() = supervisorScope {
    val users = async { fetchUsers() }
    val recommendations = async { fetchRecommendations() } // может упасть
    try {
        DashboardData(users.await(), recommendations.await())
    } catch (e: Exception) {
        DashboardData(users.await(), emptyList())
    }
}
```

**Сценарий применения:** независимые задачи, где падение одной не должна ронять остальные, — загрузка нескольких виджетов дашборда, пул фоновых обработчиков, корневой scope сервиса. `SupervisorJob` (как часть контекста scope) — для долгоживущих scope; `supervisorScope { }` — для разовой изоляции внутри suspend-функции.

**Подводный камень:** передача `SupervisorJob()` прямо в `launch` — `scope.launch(SupervisorJob()) { ... }` — **не даёт эффекта**. Причина в наследовании `Job` (Q7): билдер создаёт новый дочерний `Job`, а переданный `SupervisorJob` становится лишь его родителем — обрабатывает чужие ошибки, но не ошибки этой самой корутины. Supervisor должен быть родителем тех корутин, которые нужно изолировать, поэтому правильно — `supervisorScope { launch { } }` или `CoroutineScope(SupervisorJob())`.

## Q21. (!) Что такое `CoroutineExceptionHandler` и где его устанавливать?

`CoroutineExceptionHandler` — элемент `CoroutineContext`, играющий роль «глобального catch» последней инстанции: он ловит исключения, которые всплыли до корня иерархии и не были обработаны иначе. Это аналог `Thread.uncaughtExceptionHandler`, но для корутин. Его задача — не восстановление, а реакция на уже неизбежный сбой: залогировать, отправить метрику, уведомить.

```kotlin
val handler = CoroutineExceptionHandler { context, exception ->
    log.error("Coroutine ${context[CoroutineName]} failed", exception)
}

val scope = CoroutineScope(SupervisorJob() + handler)

scope.launch {
    error("Boom!") // обработается handler'ом
}
```

Правила, без знания которых handler «молча не срабатывает»:
- Работает **только** с `launch`. У `async` исключение — это результат, и забирать его положено через `await()`; handler его не увидит.
- Устанавливается **только на корне** иерархии — на самом scope или на корневой корутине. На дочерней корутине бесполезен: дочерние корутины не обрабатывают исключения сами, а делегируют их вверх к родителю.
- **Не перехватывает** `CancellationException` — отмена считается штатной, а не ошибкой.
- Момент вызова зависит от типа `Job`. С обычным `Job` handler срабатывает, когда вся иерархия уже отменена (исключение успело распространиться). С `SupervisorJob` — раньше, ведь соседних детей отменять не нужно, и handler обрабатывает изолированный сбой одного ребёнка.

## Q22. Чем `CancellationException` отличается от обычных исключений?

`CancellationException` — это «легальный» способ свернуть корутину: специальное исключение, которое библиотека трактует как **штатную отмену**, а не сбой. Механически отмена реализована именно через бросок этого исключения из точек приостановки, поэтому корутины устроены так, чтобы оно проходило по иерархии «бесшумно» и не запускало обработку ошибок:

| Поведение | `CancellationException` | Обычное исключение |
|---|---|---|
| Отменяет детей | Да | Да |
| Отменяет родителя | **Нет** | Да |
| Обрабатывается `CoroutineExceptionHandler` | **Нет** | Да |
| Логируется | **Нет** (по умолчанию) | Да |

```kotlin
scope.launch {
    launch {
        throw CancellationException("Отменяю себя")
        // Родитель НЕ будет отменён
    }
    launch {
        throw RuntimeException("Ошибка!")
        // Родитель БУДЕТ отменён, все дети тоже
    }
}
```

**Главный подводный камень** — проглотить `CancellationException` в широком `catch (e: Exception)`. Тогда корутина «не услышит» команду на отмену и продолжит работу, ломая кооперативную модель отмены. Если ловите широкие исключения вокруг suspend-вызовов — всегда пробрасывайте `CancellationException` отдельно:

```kotlin
// ПЛОХО — корутина не отменится
try {
    suspendFunction()
} catch (e: Exception) { // ловит и CancellationException!
    log.error("Error", e)
}

// ХОРОШО — пробрасываем CancellationException
try {
    suspendFunction()
} catch (e: CancellationException) {
    throw e // пробрасываем!
} catch (e: Exception) {
    log.error("Error", e)
}
```

## Q23. (!) Что такое `Flow` и чем он отличается от `Sequence`?

`Flow` — асинхронный холодный поток из нескольких значений во времени. Концептуально это `Sequence`, который умеет приостанавливаться: между элементами можно вызывать suspend-функции (`delay`, сетевые запросы), не блокируя поток. Если `suspend`-функция возвращает одно значение асинхронно, то `Flow` — это её обобщение на *множество* значений.

| | `Sequence` | `Flow` |
|---|---|---|
| Выполнение | Синхронное | Асинхронное (suspend) |
| Блокирует поток | Да | Нет |
| Контекст | Текущий поток | Можно переключать через `flowOn` |
| Отмена | Нет встроенной | Поддерживает отмену корутины |
| Backpressure | Автоматический (pull) | Автоматический (suspend) |

```kotlin
// Sequence — блокирует поток
fun numbersSequence(): Sequence<Int> = sequence {
    yield(1)
    Thread.sleep(1000) // блокирует!
    yield(2)
}

// Flow — не блокирует
fun numbersFlow(): Flow<Int> = flow {
    emit(1)
    delay(1000) // приостанавливает, не блокирует!
    emit(2)
}

// Сбор Flow
scope.launch {
    numbersFlow()
        .filter { it > 0 }
        .map { it * 2 }
        .collect { value ->
            println(value) // 2, 4
        }
}
```

Главное свойство — **холодность**: код внутри `flow { }` не выполняется, пока не вызван терминальный оператор (`collect`, `toList`, `first` и др.). До этого `Flow` — лишь описание того, *как* получать данные, а не сами данные. Поэтому каждый `collect` запускает поток заново и каждый коллектор получает свою порцию данных. По той же причине промежуточные операторы (`map`, `filter`) ничего не делают сразу — они лишь достраивают цепочку, которая отработает на `collect`.

## Q24. (!) Что такое cold и hot потоки?

Разница в том, кто управляет производством данных — потребитель или сам источник.

**Cold поток** (обычный `Flow`) производит данные «по требованию»: код запускается только при подписке (`collect`), и каждый коллектор получает собственный, независимый прогон с самого начала. Аналогия — функция: вызвал — посчиталось, не вызвал — ничего не происходит. Если подписчиков нет, нет и работы.

**Hot поток** (`StateFlow`, `SharedFlow`, `Channel`) производит данные сам по себе, независимо от наличия подписчиков. Аналогия — радиоэфир: вещание идёт всегда, а подписчики ловят то, что транслируется в момент их подписки. Источник один на всех, и опоздавший подписчик пропускает то, что было до него.

```kotlin
// Cold Flow — каждый collect запускает flow заново
val coldFlow = flow {
    println("Producing...") // выведется дважды
    emit(fetchFromNetwork())
}

coldFlow.collect { println(it) } // Producing... + результат
coldFlow.collect { println(it) } // Producing... + новый результат

// Hot StateFlow — одно значение для всех подписчиков
val _state = MutableStateFlow(0)
val state: StateFlow<Int> = _state.asStateFlow()

scope.launch { state.collect { println("Sub1: $it") } }
scope.launch { state.collect { println("Sub2: $it") } }

_state.value = 42 // оба подписчика получат 42
```

Разница в схеме «источник → подписчики»:

- **Cold Flow** — у каждого коллектора свой отдельный прогон источника: `collect #1` запускает свою копию `Producer` для `Collector 1`, а `collect #2` — ещё одну копию `Producer` для `Collector 2`. Источники независимы.
- **Hot Flow** — один общий `Producer` вещает на всех сразу: `Subscriber 1`, `Subscriber 2` и `Subscriber 3` получают данные от одного и того же источника.

## Q25. (!) В чём разница между `StateFlow` и `SharedFlow`?

Оба — горячие потоки. `SharedFlow` — общий и более гибкий мультикаст-источник, а `StateFlow` — его частный случай, заточенный под хранение *состояния*: это `SharedFlow` с `replay = 1`, обязательным начальным значением и дедупликацией. Проще говоря: `StateFlow` отвечает на вопрос «какое значение сейчас?», а `SharedFlow` — «какие события произошли?».

| | `StateFlow` | `SharedFlow` |
|---|---|---|
| Значение | Всегда имеет текущее (`value`) | Нет свойства `value` |
| Replay | Фиксированно `1` (последнее значение) | Настраиваемый `replay` (0, 1, N) |
| Дедупликация | Да (`distinctUntilChanged`) | Нет |
| Начальное значение | Обязательно | Не требуется |
| Use case | Состояние UI, конфигурация | События, команды, мультикаст |

```kotlin
// StateFlow — хранит текущее состояние
class UserViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(UiState.Loading)
    val uiState: StateFlow<UiState> = _uiState.asStateFlow()

    fun loadUser() {
        viewModelScope.launch {
            _uiState.value = UiState.Loading
            val user = repository.fetchUser()
            _uiState.value = UiState.Success(user)
        }
    }
}

// SharedFlow — события (одноразовые сообщения)
class EventBus {
    private val _events = MutableSharedFlow<Event>(
        replay = 0,            // не повторять старые события новым подписчикам
        extraBufferCapacity = 64,
        onBufferOverflow = BufferOverflow.DROP_OLDEST
    )
    val events: SharedFlow<Event> = _events.asSharedFlow()

    suspend fun emit(event: Event) {
        _events.emit(event)
    }
}
```

**Эмпирическое правило:** `StateFlow` — для **состояния** (всегда есть актуальное значение, новый подписчик получает его сразу; одинаковые подряд значения отсеиваются дедупликацией). `SharedFlow` с `replay = 0` — для **одноразовых событий** (навигация, уведомления, тосты): такое событие нельзя «повторять» новому подписчику, иначе при пересоздании UI оно сработает дважды. Запомнить просто: состояние повторять нужно, событие — нет.

## Q26. Какие операторы `Flow` существуют и как они работают?

Операторы `Flow` делятся на три категории, и ключевое — понимать, какие из них «ленивые», а какие запускают работу:

**Промежуточные (intermediate)** — возвращают новый `Flow` и только достраивают цепочку преобразований. Сами по себе они ничего не выполняют (как у `Sequence`) — отработают лишь когда поток соберут терминальным оператором:

```kotlin
flowOf(1, 2, 3, 4, 5)
    .filter { it % 2 == 0 }         // 2, 4
    .map { it * 10 }                 // 20, 40
    .take(1)                         // 20
    .onEach { println("Got: $it") }  // побочный эффект
    .collect { }
```

**Терминальные** — это suspend-функции, которые запускают весь поток и доводят его до результата (значение или сбор):

```kotlin
val list = flow.toList()             // собрать в список
val first = flow.first()             // первый элемент
val count = flow.count()             // количество
val sum = flow.reduce { a, b -> a + b }
flow.collect { value -> process(value) }
```

**Комбинирующие** — объединяют несколько Flow:

```kotlin
// combine — последнее значение из каждого
val combined = combine(usersFlow, settingsFlow) { users, settings ->
    UiState(users, settings)
}

// zip — попарно (ждёт оба)
val zipped = namesFlow.zip(agesFlow) { name, age -> Person(name, age) }

// flatMapLatest — при новой эмиссии отменяет предыдущую
searchQuery
    .debounce(300)
    .flatMapLatest { query -> searchApi(query) }
    .collect { results -> showResults(results) }

// flatMapConcat — последовательно
// flatMapMerge — параллельно (concurrency параметр)
```

## Q27. Как обрабатывать ошибки в `Flow`?

Ошибки в `Flow` обрабатывают декларативно — специальными операторами в цепочке, а не одним большим `try-catch` вокруг всего. Основные инструменты: `catch` (перехват), `onCompletion` (финализация) и `retry` (повтор).

```kotlin
// catch — перехватывает исключения из upstream
flow {
    emit(fetchData())
}
    .map { transform(it) }
    .catch { e ->
        // Перехватывает ошибки из flow и map (upstream)
        // НЕ перехватывает ошибки из collect (downstream)
        emit(fallbackValue)        // можно эмитировать fallback
        // или: log.error(e)       // просто залогировать
    }
    .collect { value ->
        updateUI(value) // ошибки отсюда НЕ перехватятся catch выше
    }

// onCompletion — вызывается при завершении (аналог finally)
flow
    .onCompletion { cause ->
        if (cause != null) println("Flow failed: $cause")
        else println("Flow completed normally")
    }
    .collect { }

// retry — автоматический повтор при ошибке
flow { emit(fetchFromNetwork()) }
    .retry(3) { cause ->
        cause is IOException  // повторять только для I/O ошибок
    }
    .collect { }
```

**Ключевой нюанс** — направление работы `catch`. Он перехватывает исключения только из **upstream** (всё, что *выше* него по цепочке: сам `flow { }` и операторы до `catch`). Ошибки из **downstream** — то есть из `collect` или операторов *ниже* `catch` — он не видит. Поэтому код внутри `collect` оборачивайте в `try-catch` отдельно, либо переносите логику обработки в `onEach` *перед* `catch`.

Полезные операторы под разные задачи: `catch` — перехватить и подменить/залогировать; `onCompletion` — финализация (аналог `finally`, знает причину завершения); `retry`/`retryWhen` — автоповтор с условием (например, только для сетевых ошибок).

## Q28. Как управлять backpressure в `Flow`?

Backpressure — это ситуация, когда producer (источник) эмитирует значения быстрее, чем consumer (коллектор) их обрабатывает, и нужно как-то справляться с накоплением. По умолчанию `Flow` решает это самой природой suspend: producer и consumer работают в одной корутине последовательно, поэтому `emit()` просто ждёт, пока `collect` обработает предыдущее значение, — переполнения в принципе не возникает.

Проблема в том, что при таком последовательном выполнении медленный consumer тормозит и producer. Чтобы развязать их и при этом управлять накоплением, есть несколько операторов с разными стратегиями:

```kotlin
// buffer — producer и consumer работают в разных корутинах
flow
    .buffer(capacity = 64) // буфер на 64 элемента
    .collect { slowProcess(it) }

// conflate — пропускает промежуточные значения
sensorDataFlow
    .conflate() // если collector медленный, берёт только последнее
    .collect { updateDisplay(it) }

// collectLatest — отменяет обработку при новом значении
searchQueryFlow
    .collectLatest { query ->
        // при новом query предыдущий поиск отменяется
        val results = search(query)
        showResults(results)
    }
```

Наглядно три стратегии работают так:

- **`buffer`** — быстрый `Producer` эмитирует `1, 2, 3, 4` в буфер (`capacity = N`), откуда медленный `Consumer` забирает значения по мере готовности; producer и consumer развязаны, ни одно значение не теряется (пока буфер не переполнен).
- **`conflate`** — `Producer` эмитирует `1, 2, 3`, но промежуточное `2` пропускается, и медленный `Consumer` получит только `1` и `3` (последнее на момент готовности).
- **`collectLatest`** — `Producer` эмитирует `A, B, C`; обработка `A` и `B` отменяется при поступлении следующего значения, и `Consumer` доводит до конца только обработку `C`.

Как выбрать: важны все значения — `buffer` (развязывает корутины, но при переполнении приостановит producer); важно только самое свежее — `conflate` (теряет промежуточные) или `collectLatest` (отменяет недоделанную обработку при новом значении, полезно для поиска/UI). `conflate` — это по сути `buffer(onBufferOverflow = DROP_OLDEST, capacity = 0)`.

## Q29. Как преобразовать cold `Flow` в hot (`shareIn`, `stateIn`)?

`shareIn` и `stateIn` превращают cold `Flow` в горячий и решают конкретную проблему: при cold-потоке каждый коллектор запускает источник заново (повторный сетевой запрос, повторная подписка на БД). Эти операторы запускают upstream **один раз** в переданном scope и разделяют (мультикастят) его результат между всеми подписчиками. Разница между ними — в типе результата: `stateIn` даёт `StateFlow` (нужно состояние с текущим значением), `shareIn` — `SharedFlow` (нужен поток событий).

```kotlin
class UserRepository(
    private val api: UserApi,
    private val scope: CoroutineScope
) {
    // stateIn — превращает в StateFlow
    val currentUser: StateFlow<User?> = flow {
        emit(api.fetchCurrentUser())
    }.stateIn(
        scope = scope,
        started = SharingStarted.WhileSubscribed(5000), // останавливается через 5с без подписчиков
        initialValue = null
    )

    // shareIn — превращает в SharedFlow
    val notifications: SharedFlow<Notification> = flow {
        api.notificationStream().collect { emit(it) }
    }.shareIn(
        scope = scope,
        started = SharingStarted.Lazily, // запускается при первом подписчике
        replay = 0
    )
}
```

Параметр `started` (`SharingStarted`) определяет, когда upstream запускается и останавливается:
- `Eagerly` — запускается сразу при создании, даже без подписчиков, и работает всё время.
- `Lazily` — стартует при первом подписчике и больше не останавливается.
- `WhileSubscribed(stopTimeout, replayExpiration)` — стартует при первом подписчике и останавливается через `stopTimeout` после ухода последнего. Самый практичный вариант: типичный `WhileSubscribed(5000)` не убивает поток при кратковременном пересоздании экрана (поворот устройства), но и не держит подписку на БД/сеть, когда экран реально закрыт.

## Q30. (!) Что такое `Channel` и чем он отличается от `Flow`?

`Channel` — это потокобезопасная suspend-очередь для передачи данных **между корутинами** по модели «производитель-потребитель»; концептуально это `BlockingQueue`, но вместо блокировки потока он приостанавливает корутину. Ключевое отличие от `Flow`: канал **горячий** (живёт независимо от потребителей), а каждый отправленный элемент достаётся **ровно одному** получателю — это распределение работы (fan-out), а не широковещание.

| | `Channel` | `Flow` |
|---|---|---|
| Тип | Hot | Cold (по умолчанию) |
| Получатели | Один (fan-out) | Каждый получает все данные |
| Модель | Коммуникация между корутинами | Поток данных (producer → consumer) |
| Буферизация | Настраиваемая | Через оператор `buffer` |
| Жизненный цикл | Требует явного закрытия | Завершается при окончании `flow { }` |

```kotlin
// Channel — передача между корутинами
val channel = Channel<Int>(capacity = Channel.BUFFERED)

// Producer
scope.launch {
    for (i in 1..5) {
        channel.send(i)
        println("Sent: $i")
    }
    channel.close()
}

// Consumer
scope.launch {
    for (value in channel) {
        println("Received: $value")
        delay(1000)
    }
}

// Fan-out: несколько consumer получают разные элементы
repeat(3) { consumerId ->
    scope.launch {
        for (value in channel) {
            println("Consumer $consumerId got $value")
        }
    }
}
```

**Эмпирическое правило:** `Channel` — когда корутины *общаются* между собой (очередь задач, распределение работы между воркерами, обмен сообщениями). `Flow` — когда нужен *поток данных* от источника к потребителю с операторами трансформации. На практике «голый» `Channel` редко нужен напрямую: для большинства задач хватает `Flow`, а `Channel` чаще встречается внутри `produce`/`callbackFlow` как реализация. Подробнее об аналогах в реактивном программировании — в [вопросах по RxJava](../../reactive/rxjava-interview.md).

## Q31. Какие типы `Channel` существуют?

Тип канала задаётся его ёмкостью (`capacity`) и определяет, что произойдёт с `send`, когда буфер заполнен: приостановиться, перезаписать или копить дальше. Это влияет и на синхронность отправителя с получателем.

| Тип | Capacity | Поведение `send` при полном буфере |
|---|---|---|
| `RENDEZVOUS` (0) | 0 | Приостанавливается, пока receiver не вызовет `receive` |
| `BUFFERED` | 64 (по умолчанию) | Приостанавливается при полном буфере |
| `CONFLATED` | 1 | Перезаписывает последнее значение (никогда не приостанавливается) |
| `UNLIMITED` | ∞ | Никогда не приостанавливается (риск `OutOfMemoryError`) |
| Числовое значение | N | Приостанавливается при N элементах в буфере |

```kotlin
// Rendezvous — producer ждёт consumer
val rendezvous = Channel<Int>(Channel.RENDEZVOUS)

// Buffered — стандартный буферизованный
val buffered = Channel<Int>(Channel.BUFFERED)

// Conflated — хранит только последнее значение
val conflated = Channel<Int>(Channel.CONFLATED)

// Можно указать onBufferOverflow для точной стратегии
val channel = Channel<Int>(
    capacity = 10,
    onBufferOverflow = BufferOverflow.DROP_OLDEST
)
```

**На что обратить внимание:** `RENDEZVOUS` синхронизирует отправителя и получателя — `send` ждёт `receive`, что даёт естественный backpressure. `UNLIMITED` никогда не приостанавливает `send`, но при медленном получателе очередь растёт неограниченно — прямой путь к `OutOfMemoryError`, поэтому в production его избегают.

## Q32. Что такое `produce` и `actor`?

`produce` и `actor` — высокоуровневые билдеры поверх `Channel`, которые избавляют от ручного управления его жизненным циклом. `produce` создаёт корутину-**производителя**, `actor` — корутину-**получателя**.

`produce` запускает корутину и возвращает `ReceiveChannel`, из которого можно читать. Его плюс перед ручным `Channel` — structured concurrency: канал автоматически закрывается при завершении корутины, а отмена потребителя отменяет и продюсера.

```kotlin
// produce — корутина-производитель
fun CoroutineScope.produceNumbers(): ReceiveChannel<Int> = produce {
    var x = 1
    while (true) {
        send(x++)
        delay(100)
    }
}

val numbers = produceNumbers()
repeat(5) {
    println(numbers.receive())
}
numbers.cancel()
```

`actor` (помечен deprecated) — это обратная сторона: корутина-получатель, которая последовательно обрабатывает сообщения из своего `SendChannel`. Поскольку сообщения обрабатываются по одному в одной корутине, общее изменяемое состояние внутри actor не требует синхронизации — это безопасная альтернатива блокировкам. Сейчас вместо устаревшего `actor` используют тот же паттерн вручную — `Channel` + цикл `for` (или `Flow`):

```kotlin
// Современный паттерн actor через Channel
sealed class Command {
    data class Add(val value: Int) : Command()
    object GetTotal : Command()
}

fun CoroutineScope.counterActor() = launch {
    val channel = Channel<Command>()
    var total = 0
    for (cmd in channel) {
        when (cmd) {
            is Command.Add -> total += cmd.value
            is Command.GetTotal -> println("Total: $total")
        }
    }
}
```

## Q33. Как вызывать suspend-функции из обычного кода?

Напрямую из обычного (не-suspend) кода suspend-функцию вызвать нельзя — компилятор это запретит, ведь там нет `Continuation` и некому возобновить вызов. Поэтому нужен «мост»: создать корутину одним из билдеров. Выбор зависит от того, можно ли блокировать поток и нужен ли результат синхронно.

```kotlin
// 1. runBlocking — блокирует текущий поток (main, тесты, скрипты)
fun main() {
    val result = runBlocking {
        fetchData()
    }
}

// 2. CoroutineScope.launch — fire-and-forget
class MyService {
    private val scope = CoroutineScope(Dispatchers.IO + SupervisorJob())

    fun doWork() {
        scope.launch {
            val data = fetchData()
            processData(data)
        }
    }
}

// 3. Spring suspend-контроллер — фреймворк создаёт корутину
@RestController
class UserController(private val service: UserService) {
    @GetMapping("/users/{id}")
    suspend fun getUser(@PathVariable id: Long): User {
        return service.findUser(id)  // suspend-функция
    }
}

// 4. CompletableFuture bridge (для Java-interop)
fun fetchDataFuture(): CompletableFuture<Data> =
    scope.future { fetchData() }
```

Как выбрать мост: `runBlocking` — когда результат нужен синхронно и поток блокировать допустимо (`main`, тесты, край Java-интеропа); `scope.launch` — fire-and-forget внутри живого компонента; suspend-контроллер — когда мост создаёт фреймворк (Spring, Ktor); `future { }` — когда наружу нужно отдать `CompletableFuture` для Java. Подробнее о взаимодействии с Java-кодом — в [вопросах по Kotlin-Java Interop](kotlin-interop-java-interview.md).

## Q34. (!) Распространённые ошибки при работе с корутинами

Большинство ошибок с корутинами сводятся к двум источникам: нарушению structured concurrency (утечки) и блокировке потока вместо приостановки. Вот типовые промахи, которые любят спрашивать на собеседовании.

**1. Использование `GlobalScope` вместо structured concurrency:**
```kotlin
// ПЛОХО
GlobalScope.launch { fetchData() }

// ХОРОШО
scope.launch { fetchData() }
```

**2. Глотание `CancellationException`:**
```kotlin
// ПЛОХО
try { suspendFun() } catch (e: Exception) { log(e) }

// ХОРОШО
try { suspendFun() } catch (e: CancellationException) { throw e } catch (e: Exception) { log(e) }
```

**3. `SupervisorJob` в `launch` вместо scope:**
```kotlin
// ПЛОХО — SupervisorJob не даёт эффекта
scope.launch(SupervisorJob()) { /* ... */ }

// ХОРОШО
supervisorScope { launch { /* ... */ } }
```

**4. Блокирующий код без переключения диспетчера:**
```kotlin
// ПЛОХО — блокирует Dispatchers.Default/Main
scope.launch { Thread.sleep(1000) }

// ХОРОШО
scope.launch { withContext(Dispatchers.IO) { Thread.sleep(1000) } }
```

**5. Запуск корутины в `init` или конструкторе без scope:**
```kotlin
// ПЛОХО — корутина переживёт объект
class MyClass {
    init { GlobalScope.launch { loadData() } }
}
```

**6. Неправильный сбор `Flow` в UI (Android):**
```kotlin
// ПЛОХО — не пережнвает пересоздание Activity
lifecycleScope.launch { flow.collect { } }

// ХОРОШО
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        flow.collect { }
    }
}
```

## Q35. Как тестировать корутины (`runTest`, `TestScope`)?

Тесты на корутины не должны реально ждать `delay` — иначе тест с `delay(10_000)` шёл бы 10 секунд. Библиотека `kotlinx-coroutines-test` даёт **виртуальное время**: внутри `runTest` все `delay` пропускаются мгновенно, а таймеры можно перематывать вручную (`advanceTimeBy`, `advanceUntilIdle`). Так тесты остаются быстрыми и при этом детерминированными.

```kotlin
// runTest — основной инструмент (заменяет runBlockingTest)
@Test
fun `test delay is skipped`() = runTest {
    val result = async {
        delay(10_000) // НЕ ждёт реально — виртуальное время
        42
    }
    assertEquals(42, result.await())
}

// Инжектирование TestDispatcher
class UserService(private val dispatcher: CoroutineDispatcher = Dispatchers.IO) {
    suspend fun fetchUser(): User = withContext(dispatcher) {
        repository.findUser()
    }
}

@Test
fun `test with injected dispatcher`() = runTest {
    val service = UserService(dispatcher = UnconfinedTestDispatcher(testScheduler))
    val user = service.fetchUser()
    assertEquals("John", user.name)
}

// Управление виртуальным временем
@Test
fun `test timeout behavior`() = runTest {
    val flow = flow {
        emit(1)
        delay(1000)
        emit(2)
    }

    val values = mutableListOf<Int>()
    flow.collect { values.add(it) }

    assertEquals(listOf(1, 2), values)
    assertEquals(1000, currentTime) // прошло 1000мс виртуального времени
}

// advanceTimeBy / advanceUntilIdle
@Test
fun `test periodic task`() = runTest {
    var count = 0
    val job = launch {
        while (true) {
            delay(1000)
            count++
        }
    }
    advanceTimeBy(3500)
    assertEquals(3, count)
    job.cancel()
}
```

**Рекомендация:** не хардкодьте `Dispatchers.IO`/`Default` внутри классов, а инжектируйте `CoroutineDispatcher` через конструктор. Тогда в тестах его легко подменить: `StandardTestDispatcher` (корутины ждут явной перемотки времени — точный контроль над порядком) или `UnconfinedTestDispatcher` (корутины стартуют сразу, eagerly — проще для большинства сценариев). Без такой инъекции реальные `Dispatchers.IO` не подхватят виртуальное время `runTest`, и тест может стать недетерминированным.

## Q36. Как интегрировать корутины со `Spring`?

`Spring WebFlux` (начиная с Spring 5.2) понимает корутины нативно — мост создаёт сам фреймворк, поэтому контроллеры и сервисы можно писать прямо на `suspend`-функциях и `Flow`, без ручного `runBlocking` или собственного scope.

```kotlin
// Suspend-контроллер
@RestController
class UserController(private val userService: UserService) {

    @GetMapping("/users/{id}")
    suspend fun getUser(@PathVariable id: Long): User {
        return userService.findById(id) // suspend-функция
    }

    @GetMapping("/users")
    fun getAllUsers(): Flow<User> {
        return userService.findAll() // возвращает Flow
    }
}

// Suspend-сервис
@Service
class UserService(private val repository: UserRepository) {

    suspend fun findById(id: Long): User =
        withContext(Dispatchers.IO) {
            repository.findById(id) ?: throw NotFoundException("User $id not found")
        }

    fun findAll(): Flow<User> = flow {
        repository.findAll().forEach { emit(it) }
    }.flowOn(Dispatchers.IO)
}
```

Необходимые зависимости:
```kotlin
implementation("org.springframework.boot:spring-boot-starter-webflux")
implementation("org.jetbrains.kotlinx:kotlinx-coroutines-reactor")
```

Как это работает под капотом: `kotlinx-coroutines-reactor` наводит мост между корутинами и реактором `Reactor`. Spring автоматически конвертирует возвращаемую suspend-функцию в `Mono`, а `Flow` — в `Flux`, так что наружу выходит привычный реактивный тип, а вы пишете линейный код.

**Важное ограничение:** всё это про реактивный стек WebFlux. На блокирующем стеке (`spring-boot-starter-web` + Servlet) нативной поддержки suspend-контроллеров нет — там корутины придётся запускать вручную через собственный `CoroutineScope` в сервисе, что менее удобно и теряет часть преимуществ.

## Q37. Чем `Flow` отличается от `RxJava`?

Оба решают одну задачу — реактивные/асинхронные потоки данных с операторами. Главное концептуальное различие: `Flow` построен **поверх корутин** и наследует их structured concurrency (отмена, scope, backpressure через suspend), тогда как `RxJava` — самостоятельная библиотека со своей моделью планировщиков (`Scheduler`) и ручным управлением подписками (`Disposable`).

| | `Flow` | `RxJava` |
|---|---|---|
| Зависимость | Часть `kotlinx.coroutines` | Отдельная библиотека |
| Язык | Kotlin-first | Java-first |
| Backpressure | Встроенный через suspend | `Flowable` (отдельный тип) |
| Отмена | Через structured concurrency | `Disposable` + ручное управление |
| Обработка ошибок | `catch`, `retry` + coroutine exception handling | `onError*` операторы |
| Hot streams | `StateFlow`, `SharedFlow` | `Subject`, `Processor` |
| Кривая обучения | Низкая (если знаешь корутины) | Высокая |
| Операторы | ~50 | ~400+ |

```kotlin
// RxJava
Observable.fromCallable { fetchData() }
    .subscribeOn(Schedulers.io())
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe(
        { data -> showData(data) },
        { error -> showError(error) }
    )

// Flow — эквивалент
flow { emit(fetchData()) }
    .flowOn(Dispatchers.IO)
    .catch { error -> showError(error) }
    .collect { data -> showData(data) } // уже на нужном потоке
```

**Когда что:** для новых Kotlin-проектов выбирают `Flow` — он легче (часть стандартной библиотеки корутин), безопаснее по отмене и не требует учить отдельную модель. `RxJava` остаётся актуален в крупных проектах с большим объёмом Java-кода или там, где нужна его богатая операторная база (~400 операторов против ~50 у `Flow`). Подробнее — в [вопросах по RxJava](../../reactive/rxjava-interview.md).

## Q38. Как работает `Mutex` в корутинах и когда использовать вместо `synchronized`?

`Mutex` (mutual exclusion) — это «корутино-дружелюбный» замок: он защищает критическую секцию от одновременного доступа так же, как `synchronized`, но при ожидании блокировки **не блокирует поток**, а **приостанавливает** корутину. Это принципиально для корутин: пока одна ждёт замок, поток свободен и обслуживает другие корутины.

```kotlin
import kotlinx.coroutines.sync.Mutex
import kotlinx.coroutines.sync.withLock

val mutex = Mutex()
var counter = 0

// withLock — suspend-функция: приостанавливает, не блокирует поток
suspend fun increment() {
    mutex.withLock {
        counter++
    }
}

// Пример: 100 корутин безопасно инкрементируют счётчик
fun main() = runBlocking {
    val jobs = List(100) {
        launch { repeat(1000) { increment() } }
    }
    jobs.forEach { it.join() }
    println("Counter: $counter")  // 100000
}
```

**Почему `synchronized` опасен в корутинах:** внутри `synchronized`-блока нельзя вызывать suspend-функции (компилятор это запретит). Хуже того, если бы корутина приостановилась, удерживая монитор, тот остался бы захваченным потоком, который ушёл выполнять другую работу, — прямой путь к взаимоблокировке. `Mutex` устроен иначе: блокировка привязана к корутине, а не к потоку, поэтому приостановка под замком безопасна.

```kotlin
// ПЛОХО — synchronized блокирует поток, корутина не может приостановиться внутри
suspend fun dangerousFun() {
    synchronized(lock) {
        delay(100) // IllegalStateException: suspension functions can't be called in sync blocks
    }
}

// ХОРОШО — Mutex позволяет приостановку
suspend fun safeFun() {
    mutex.withLock {
        delay(100) // OK — корутина приостановлена, поток свободен
    }
}
```

| | `synchronized` | `Mutex` |
|---|---|---|
| Блокировка | Блокирует поток ОС | Приостанавливает корутину |
| Suspend-функции внутри | Нельзя | Можно |
| Применение | Java-legacy, non-coroutine код | Корутины |

**Эмпирическое правило:** в корутинном коде синхронизируйте `Mutex`-ом (он не блокирует поток и разрешает suspend внутри); `synchronized`/`ReentrantLock` оставьте для не-корутинного и legacy-кода. А для простых счётчиков и флагов вообще не берите блокировку — атомарные типы (`AtomicInteger`, `AtomicLong`) дешевле, потому что работают на CAS без приостановки. Ещё один корутинный приём — заменить разделяемое изменяемое состояние на конфайнмент в одной корутине (паттерн actor из Q32), тогда блокировки не нужны вовсе.

## Q39. Как комбинировать несколько `Flow` — `combine`, `zip`, `merge`?

Все три объединяют несколько потоков в один, но по-разному решают, *когда* выдавать результат. Самый частый вопрос — отличие `combine` от `zip`: `combine` реагирует на каждое новое значение и берёт последние из каждого потока, а `zip` строго ждёт пары. `merge` же не комбинирует значения, а просто сливает потоки в один.

**`combine`** — реагирует на каждое новое значение от **любого** потока и пересчитывает результат из **последних** значений всех потоков. Идеален для UI: объединить несколько источников состояния так, чтобы итог обновлялся при изменении любого из них.

```kotlin
val flow1 = flow {
    emit(1); delay(300); emit(2); delay(300); emit(3)
}
val flow2 = flow {
    delay(150); emit("a"); delay(300); emit("b")
}

flow1.combine(flow2) { n, s -> "$n$s" }.collect { println(it) }
// 1a, 2a, 2b, 3b  (при каждом новом значении — пара из последних)
```

**`zip`** — строгое попарное объединение: ждёт по одному значению от каждого потока и только тогда выдаёт пару. Поэтому быстрый поток «притормаживает» и ждёт медленный. Останавливается, как только закончится более короткий поток (число результатов = длине короткого):

```kotlin
val numbers = flow { emit(1); emit(2); emit(3) }
val letters = flow { emit("A"); emit("B") }

numbers.zip(letters) { n, s -> "$n$s" }.collect { println(it) }
// 1A, 2B  (только 2 пары — по числу элементов более короткого потока)
```

**`merge`** (и `flattenMerge`) — не комбинирует значения, а сливает несколько потоков в один, пропуская значения по мере появления, не дожидаясь остальных. Подходит, когда нужно слушать несколько независимых источников событий сразу:

```kotlin
val flowA = flow { emit("A1"); delay(200); emit("A2") }
val flowB = flow { delay(100); emit("B1"); delay(200); emit("B2") }

merge(flowA, flowB).collect { println(it) }
// A1, B1, A2, B2  (в реальном времени по мере поступления)
```

**`flatMapMerge`** — конкурентная трансформация каждого элемента в Flow:

```kotlin
// Параллельная загрузка данных для каждого id
val ids = flowOf(1, 2, 3)
ids.flatMapMerge { id ->
    flow { emit(loadUser(id)) }
}.collect { user -> process(user) }
```

| Оператор | Семантика | Стоп-условие |
|---|---|---|
| `combine` | Последние значения при любом новом | Оба потока завершились |
| `zip` | Строгие пары | Более короткий поток |
| `merge` | Конкурентное слияние | Все потоки завершились |
