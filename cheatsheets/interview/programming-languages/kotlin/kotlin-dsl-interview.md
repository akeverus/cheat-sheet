## Q1. (!) Что такое DSL в Kotlin и зачем он нужен?

**Domain-Specific Language** (DSL) — язык или синтаксис, заточенный под конкретную предметную область. В Kotlin под DSL обычно имеют в виду **внутренний DSL**: тот же Kotlin, но организованный так, что код читается как декларация — конфиг, разметка, сценарий теста, маршруты. Зачем это нужно: **читаемость** (код похож на описание задачи), **типобезопасность** (компилятор и IDE проверяют структуру и подсказывают допустимые вызовы), **удобство** (меньше шаблонного кода, естественная вложенность).

Типичные примеры: **Gradle Kotlin DSL** для `build.gradle.kts`, **Ktor** — `routing` и настройка приложения через блоки, HTML-builders, конфигурация в виде `config { host = "localhost"; port = 8080 }`, BDD-тесты. Всё это — не отдельный язык, а приёмы Kotlin (lambda с receiver, extension-функции, перегрузка операторов), собранные в читаемый API.

## Q2. Что такое Type-Safe Builder и как он устроен?

**Type-Safe Builder** — приём, при котором иерархическая структура (дерево узлов) строится через вызовы функций с lambda. Каждая функция принимает lambda с receiver: внутри lambda доступны методы и свойства контекста (текущего узла). Контекст задаётся типом receiver’а, поэтому вложенность и допустимые вызовы проверяются компилятором. Устроен так: классы представляют узлы (например, `Html`, `Body`, `Div`); extension-функции с параметром типа `T.() -> Unit` создают дочерний узел, вызывают у него переданную lambda и добавляют его в структуру. В результате код выглядит как разметка, но остаётся типобезопасным Kotlin.

В реальном проекте здесь важно показать контракт API и предсказуемость поведения: `null-safety`, читаемость и совместимость с Java/корутинами. На интервью обычно ценят, когда кандидат называет типичные ошибки команды и конкретные практики предотвращения через тесты, review и статический анализ.

## Q3. Что такое lambda с receiver и как она используется в DSL?

**Lambda с receiver** — lambda, у которой при вызове неявный `this` указывает на объект-receiver. Синтаксис: `T.() -> Unit`. В DSL такая lambda передаётся в функцию builder’а; внутри блока вызывают методы и свойства типа `T` без префикса. Это создаёт контекст: «внутри этого блока мы находимся в узле типа `T` и можем вызывать только его методы». **@DslMarker** — аннотация на маркерном интерфейсе, которую вешают на классы контекстов DSL; она ограничивает видимость receiver’ов из внешних scope, чтобы нельзя было случайно вызвать метод внешнего контекста без явного указания получателя.

В реальном проекте здесь важно показать контракт API и предсказуемость поведения: `null-safety`, читаемость и совместимость с Java/корутинами. На интервью обычно ценят, когда кандидат называет типичные ошибки команды и конкретные практики предотвращения через тесты, review и статический анализ.

## Q4. Как написать простой builder (например, для HTML или конфига)?

Определяют классы для узлов (например, `Html`, `Body`, `Tag`). Для каждого узла объявляют extension-функции на соответствующем receiver’е с параметром `Tag.() -> Unit` (или аналог). Внутри функции создают дочерний узел, вызывают у него переданную lambda (`child.init()`), добавляют в список детей. Точка входа — функция верхнего уровня, принимающая lambda с receiver корневого узла. Пример: `html { body { div { +"text" } } }`. Для конфига — класс с полями и методами вида `fun host(s: String)`, `fun port(p: Int)`, вызываемые внутри lambda с receiver конфига.

Для HTML builder'а типичный паттерн: корневой класс `HTML` с методом `fun body(init: Body.() -> Unit)`, внутри которого создаётся `Body`, вызывается `body.init()`, результат добавляется в коллекцию детей. Текст добавляют через перегрузку `operator fun String.unaryPlus()`. Для конфига чаще используют `var`-свойства и присваивание в блоке: `config { host = "db"; port = 5432 }` — блок вызывается на `Config` через `apply`, поля задаются напрямую.

```kotlin
class Config {
    var host = "localhost"
    var port = 8080
    fun host(s: String) { host = s }
    fun port(p: Int) { port = p }
}

fun config(block: Config.() -> Unit): Config = Config().apply(block)
// Использование: config { host("db"); port(5432) }
```

## Q5. В чём разница между DSL и обычным fluent API?

**Fluent API** — цепочка вызовов методов одного (или сменяющих друг друга) объекта; каждый метод возвращает объект для продолжения цепочки. Вложенности контекстов нет: вся цепочка выполняется в одном «плоском» потоке. Пример: `builder.setHost("x").setPort(80).build()`.

**DSL в Kotlin** — вложенные **блоки** (lambda с receiver). Каждый блок задаёт свой контекст и вложенность; структура похожа на дерево или декларацию. Внутри блока `body { ... }` доступны только методы, допустимые для содержимого body; контекст родителя скрыт (или доступен только явно при использовании @DslMarker). DSL читается как конфигурация или разметка; fluent API — как последовательность команд. И то и другое может быть типобезопасным; различие — в структуре (цепочка vs вложенные блоки).

## Q6. Где в реальных проектах используют Kotlin DSL?

**Gradle** — Kotlin DSL для `build.gradle.kts`: конфигурация сборки в виде Kotlin-кода с автодополнением и типами. **Ktor** — `routing` и настройка приложения через блоки с receiver (`routing { get("/") { ... } }`). **Тесты** — аннотированные билдеры и BDD-стиль (описание сценариев в виде блоков). **Конфигурация** — хост, порт, флаги в виде `config { ... }`. **HTML/XML** — генерация разметки через builder'ы. **SQL** — типобезопасные построители запросов. Всё это — внутренние DSL на Kotlin: один язык, но синтаксис подобран под задачу.

В экосистеме Kotlin DSL широко используются: **Exposed** — SQL через type-safe builder'ы; **kotlinx.html** — HTML для веб-приложений; **KotlinTest**, **Kotest** — assert-билдеры вида `x shouldBe y`; **Detekt** — конфигурация правил линтера. Выбор DSL вместо обычного API оправдан, когда структура сложная, вложенная и должна читаться как декларация; для простых случаев fluent API может быть достаточно.

## Q7. Что такое @DslMarker и зачем он нужен?

**@DslMarker** — аннотация, которую применяют к маркерному интерфейсу, а затем к классам контекстов DSL (receiver’ам). Компилятор учитывает её при разрешении неявного receiver’а: из вложенной lambda можно обращаться к receiver’у только текущего (самого внутреннего) помеченного контекста. Это предотвращает случайный вызов метода внешнего контекста с тем же именем. Без маркера во вложенных блоках был бы доступен внешний receiver, и код мог бы стать неочевидным или ошибочным.

Пример: в `html { body { div { a { ... } } } }` и `Html`, и `Body`, и `Tag` могут иметь метод `classes`. Без @DslMarker вызов `classes("active")` внутри `a` мог бы неоднозначно относиться к внешнему `div` или к текущему `a`. С маркером `this` привязан только к самому внутреннему контексту (`a`), вызов однозначен. Маркер объявляют как `@DslMarker annotation class MyDsl` и вешают на все классы контекстов: `@MyDsl class Html`, `@MyDsl class Body` и т.д.

## Q8. Как в DSL передавать параметры и опции (именованные аргументы, блоки)?

Параметры в DSL передают теми же средствами Kotlin, что и в обычном API. **Именованные аргументы** удобны для опций: `div(class = "card", id = "main")` — читаемо и не зависит от порядка. **Default-аргументы** позволяют опускать редко меняемые значения. **Блоки** (lambda с receiver) задают вложенную структуру или подконфигурацию: `server { host = "0.0.0.0"; port = 8080; ssl { ... } }` — `ssl` принимает блок для настройки SSL.

Для опциональных блоков параметр может быть nullable lambda: `fun Tag.optionalBlock(block: (Tag.() -> Unit)? = null)` — если блок передан, вызываем его; иначе просто создаём узел без содержимого. Комбинация именованных аргументов, default-значений и блоков даёт гибкий и читаемый API без перегрузок с десятками параметров.

## Q9. Что такое invoke convention и как его используют в DSL?

**Invoke convention** — возможность вызывать объект как функцию: если у класса определён `operator fun invoke(...)`, то экземпляр можно «вызвать»: `obj(args)`. В DSL это даёт синтаксис без явного имени метода: например, `div("content")` вместо `div { text("content") }`, или `config("prod") { ... }` — конфиг с именем окружения. Объект-синглтон с `invoke` становится вызываемой «функцией», что упрощает API.

Пример: `object Routes { operator fun invoke(block: Routing.() -> Unit) = routing(block) }` — тогда пишут `Routes { get("/") { ... } }` вместо `routing { ... }`. Другой сценарий — builder, который вызывается с параметрами: `query("users") { where("active = true") }` — здесь `query` может быть объектом с `invoke(query: String, block: QueryBuilder.() -> Unit)`. Это делает DSL более лаконичным и похожим на декларативный язык.

## Q10. Как перегрузка операторов используется в DSL (например, + для текста)?

Перегрузка операторов в Kotlin позволяет использовать `+`, `-`, `[]`, `in` и др. для своих типов. В DSL типичный пример — **`operator fun String.unaryPlus()`** в контексте HTML builder'а: `+"text"` внутри блока `div` добавляет текстовый узел. Вызов `+ "Hello"` эквивалентен `this.plus("Hello")`, но для extension-функции `unaryPlus` синтаксис короче и читается как «добавить текст».

Для `get`/`set` оператор `[]` удобен в конфигурациях: `config["host"]` или `config["port"] = 8080`. Оператор `invoke` уже рассмотрен. Оператор `in` может использоваться для проверки принадлежности: `"admin" in roles`. Важно не перегружать операторы без смысла: `+` для добавления контента в builder — уместно; `+` для слияния конфигов — тоже; но произвольные перегрузки затрудняют чтение кода.

```kotlin
class Tag(val children: MutableList<Any> = mutableListOf()) {
    operator fun String.unaryPlus() { children.add(this) }
}
// Использование: div { +"Hello, world!" }
```

## Q11. Инфиксные функции в DSL — когда и зачем?

**Инфиксная функция** (`infix fun`) позволяет вызывать метод без точки и скобок: `a to b` вместо `a.to(b)`. В DSL это даёт читаемые конструкции: `x shouldBe y` (Kotest), `config host "localhost"`, `user hasRole "admin"`. Синтаксис выглядит как утверждение на естественном языке, что особенно уместно в тестах и конфигурациях.

Ограничения: инфиксная функция — один параметр; нельзя использовать с vararg или несколькими параметрами. Подходит для пар «субъект — значение»: `expect(result).toBe(42)`, `request method "GET"`. В BDD-тестах `scenario("login") { user should succeed }` — `should` как инфикс связывает `user` и `succeed`. Злоупотреблять не стоит: `a plus b` менее читаемо, чем `a.plus(b)` или `a + b`.

## Q12. Как в DSL реализовать опциональные и обязательные блоки?

**Обязательный блок** — параметр без default: `fun body(init: Body.() -> Unit)` — блок должен быть передан, иначе компилятор выдаст ошибку. **Опциональный блок** — nullable lambda с default `null`: `fun ssl(init: (SslConfig.() -> Unit)? = null)`. Внутри функции проверяют: `init?.invoke(sslConfig)` — если блок передан, вызываем; иначе создаём узел без дочерней конфигурации.

Для «опционального, но с default-содержимым» можно передать пустой блок: `ssl { }` — минимальная конфигурация. Или использовать перегрузки: `fun div()` и `fun div(init: Div.() -> Unit)`. В Gradle DSL часто встречается `optionalBlock { }` — вызов без блока создаёт объект с default-значениями; с блоком — применяет настройки. Комбинация `block: (T.() -> Unit)? = null` и проверки `block?.invoke(this)` — стандартный паттерн.

## Q13. Extension properties в контексте DSL — зачем и примеры?

**Extension properties** расширяют тип дополнительным свойством без изменения класса. В DSL они полезны для контекстно-зависимых значений: например, `val Tag.parent: Tag?` — доступ к родительскому узлу внутри блока. Или `val RequestContext.currentUser: User` — в контексте обработчика запроса свойство даёт текущего пользователя. Синтаксис `this.currentUser` или просто `currentUser` внутри receiver'а читается как часть DSL.

Другой пример — вычисляемые свойства: `val Routing.controllers: List<Controller>` — список зарегистрированных контроллеров в контексте routing. Extension properties работают с receiver'ом так же, как extension-функции: они «видят» контекст и могут использовать его для вычисления значения. Важно: extension property не может иметь backing field, только getter (и setter для `var` с хранилищем в другом месте).

## Q14. Как inline влияет на производительность DSL и когда его использовать?

**`inline`** для функции с lambda-параметром убирает выделение памяти под объект lambda: тело функции подставляется в место вызова (inlining), а lambda «разворачивается» в тот же код. Для DSL это важно: builder'ы вызываются часто, каждый `html { }` или `config { }` без `inline` создаёт объект анонимного класса. С `inline` накладные расходы на вызов и аллокацию снижаются.

Рекомендуется помечать `inline` функции верхнего уровня DSL, принимающие lambda с receiver: `inline fun html(block: HTML.() -> Unit)`. Ограничение: lambda не может быть сохранена или передана в другое место (например, в `runLater`), если функция inline — компилятор на это укажет. Для большинства type-safe builder'ов lambda вызывается сразу, поэтому `inline` безопасен и даёт прирост производительности. `reified` вместе с `inline` позволяет использовать `T::class` внутри generic-функций — полезно для сериализации и рефлексии в DSL.

## Q15. Как устроены DSL для тестов (expect, should) — примеры?

DSL для тестов используют **lambda с receiver** и **инфиксные функции**. Типичная структура: `expect(actual) { ... }` — блок получает receiver с методами `toEqual`, `toBe`, `toThrow` и т.д. Или `actual shouldBe expected` — инфикс связывает значение и ожидание. Фреймворки **Kotest**, **KotlinTest**, **Strikt** строят assert-билдеры: `expectThat(user) { getName() shouldBe "Alice"; getAge() shouldBe 30 }`.

BDD-стиль: `feature("login") { scenario("valid credentials") { given { user = createUser() }; when { response = login(user) }; then { response.status shouldBe 200 } } }` — блоки `feature`, `scenario`, `given`, `when`, `then` задают контекст и читаются как спецификация. Каждый блок — lambda с receiver; вложенность ограничивает видимость (например, `user` доступен в `when` и `then`). Matcher'ы вроде `shouldBe`, `shouldNotBe` реализованы как extension-функции с инфиксом на типах или обёртках.

```kotlin
// Kotest-подобный синтаксис
val result = compute()
result shouldBe 42
result shouldNotBe 0

// BDD-блоки
feature("API") {
    scenario("GET returns 200") {
        val response = get("/users")
        response.status shouldBe 200
    }
}
```
