# Вопросы на собеседовании: `Kotlin` коллекции

Краткие ответы по коллекциям в `Kotlin`: `List`, `Set`, `Map`, `Sequence`, мутабельность, операции и отличия от `Java`.

Дата последнего обновления: 2026-02-04

## Введение

В `Kotlin` коллекции разделены на **read-only** (интерфейсы `List`, `Set`, `Map`) и **mutable** (`MutableList`, `MutableSet`, `MutableMap`). Под капотом на `JVM` используются коллекции `Java`, но API и разделение по мутабельности — свои. На собеседованиях часто спрашивают про отличия от `Java`, `Sequence` и типичные операции.

## Q1. (!) В чём разница между read-only и mutable коллекциями в Kotlin?

**Read-only** интерфейсы в Kotlin — это `List`, `Set`, `Map`. У них нет методов изменения (добавление, удаление, очистка); доступны только операции чтения: получение по индексу/ключу, итерация, размер и т.д. Важно: переменная с типом `List` может на самом деле указывать на изменяемую реализацию (например, `ArrayList`), но через тип `List` менять коллекцию нельзя — контракт на уровне типа гарантирует «здесь только чтение».

**Mutable** интерфейсы — `MutableList`, `MutableSet`, `MutableMap` — наследуют соответствующие read-only интерфейсы и добавляют методы `add`, `remove`, `clear` и т.п. Если функция должна накапливать элементы или изменять коллекцию, параметр или переменная объявляются как `MutableList` (или другой mutable-тип). На JVM под капотом используются те же классы Java (`ArrayList`, `HashSet`, `HashMap`); различие только в том, какой интерфейс экспонируется в типе. Так снижается риск случайно изменить коллекцию там, где ожидается только чтение.

```kotlin
val readOnly: List<String> = listOf("a", "b")
// readOnly.add("c")  // ошибка компиляции: у List нет add

val mutable: MutableList<String> = mutableListOf("a", "b")
mutable.add("c")  // OK

fun process(items: List<Int>) { /* только чтение */ }

fun collect(items: MutableList<Int>) { items.add(1) }
```

## Q2. Как устроены List, Set и Map в Kotlin и что под капотом на JVM?

В Kotlin `List`, `Set` и `Map` — это интерфейсы из `kotlin.collections`. **List** — упорядоченная коллекция с допущением дубликатов; на JVM обычно соответствует `java.util.List`, чаще всего реализация — `ArrayList`. **Set** — коллекция уникальных элементов; порядок не гарантируется (если нужен порядок вставки, используют `LinkedHashSet`). **Map** — пары ключ–значение; на JVM это `java.util.Map`, как правило `HashMap`.

Фабрики `listOf()`, `mutableListOf()`, `setOf()`, `mapOf()` и т.д. возвращают экземпляры, которые реализуют и Kotlin-интерфейсы, и соответствующие Java-интерфейсы. Поэтому передавать коллекции в Java-код и принимать их из Java можно без явной конвертации; важно лишь учитывать платформенные типы и nullability при работе с элементами из Java.

## Q3. Как создать коллекцию: listOf(), mutableListOf(), emptyList()?

**`listOf(e1, e2, ...)`** создаёт read-only список с заданными элементами. На JVM для малого числа элементов может использоваться оптимизированное представление; тип переменной — `List<T>`. **`mutableListOf()`** создаёт пустой изменяемый список (как правило, `ArrayList`); тип — `MutableList<T>`. **`emptyList()`** возвращает синглтон пустого read-only списка — новый объект при каждом вызове не создаётся, удобно для default-значений и возврата «пустого результата».

Аналогично для множеств: `setOf()`, `mutableSetOf()`, `emptySet()`. Для отображений: `mapOf()`, `mutableMapOf()`, `emptyMap()`. В `mapOf()` пары задают через `key to value` или `Pair(key, value)`, например: `mapOf("a" to 1, "b" to 2)`.

```kotlin
val list = listOf(1, 2, 3)           // List<Int>, read-only
val mutable = mutableListOf<Int>()   // MutableList<Int>
val empty = emptyList<String>()      // синглтон
val set = setOf("x", "y")
val map = mapOf("a" to 1, "b" to 2)
```

## Q4. (!) Что такое Sequence и чем отличается от List при цепочке операций?

**Sequence** в Kotlin — это ленивая последовательность элементов. В отличие от `List`, промежуточные операции (`map`, `filter` и т.д.) не выполняются сразу и не создают промежуточные коллекции: они откладываются и выполняются по одному элементу в момент вызова **терминальной** операции (`toList()`, `first()`, `count()`, `forEach` и т.п.). Это даёт выигрыш по памяти (нет нескольких копий данных) и по количеству проходов.

При цепочке над **List** каждая операция обрабатывает всю коллекцию и создаёт новую: например, `filter` создаёт новый список, затем `map` — ещё один. При цепочке над **Sequence** один элемент «проходит» всю цепочку от начала до конца, затем следующий — получается pipeline по одному элементу. Для больших данных или длинных цепочек `Sequence` часто предпочтительнее; для маленьких коллекций и простых операций разница может быть незначительной или даже в пользу `List` из-за накладных расходов на итератор.

```kotlin
// List: создаются промежуточные списки
listOf(1, 2, 3, 4, 5).filter { it % 2 == 0 }.map { it * 2 }.toList()

// Sequence: один проход по элементам, лениво
listOf(1, 2, 3, 4, 5).asSequence().filter { it % 2 == 0 }.map { it * 2 }.toList()
```

## Q5. Какие типичные операции над коллекциями (map, filter, fold, groupBy)?

**`map`** — преобразование каждого элемента в другой (или в коллекцию; если результат — коллекция и нужна «плоская» последовательность, используют **`flatMap`**). **`filter`** — оставить только элементы, удовлетворяющие предикату. **`fold`** и **`reduce`** — свертка в одно значение (сумма, конкатенация, произведение и т.д.); `fold` принимает начальное значение, `reduce` использует первый элемент. **`groupBy`** — группировка по ключу, результат — `Map<K, List<T>>`.

Также часто используются: **`find`**, **`first`** / **`firstOrNull`**, **`any`**, **`all`**, **`none`**, **`count`**, **`partition`** (разбиение на два списка по предикату), **`zip`** (объединение двух коллекций в пары), **`flatten`** (список списков в один список). Для `Sequence` те же операции доступны, но выполняются лениво до вызова терминальной операции.

## Q6. В чём разница между map и flatMap в Kotlin?

**`map`** преобразует каждый элемент в **одно** значение (или один объект). Размер результата совпадает с размером исходной коллекции. **`flatMap`** преобразует каждый элемент в **итерируемую структуру** (список, последовательность и т.д.) и затем «склеивает» все эти структуры в одну плоскую последовательность; размер результата может быть любым.

Пример: список строк разбить на слова. Каждая строка при `split(" ")` даёт список слов. `flatMap { it.split(" ") }` даёт один общий список всех слов. Если бы использовали `map { it.split(" ") }`, получили бы `List<List<String>>` — список списков слов. Таким образом, `flatMap` удобен, когда один элемент «разворачивается» в несколько или когда нужно объединить вложенные структуры в одну.

```kotlin
val lines = listOf("hello world", "kotlin collections")
lines.map { it.split(" ") }      // [["hello", "world"], ["kotlin", "collections"]]
lines.flatMap { it.split(" ") }   // ["hello", "world", "kotlin", "collections"]
```

## Q7. Как в Kotlin работать с Java-коллекциями (взаимодействие, nullability)?

Kotlin воспринимает типы из Java как **платформенные**: для них неизвестна nullability (если в Java нет аннотаций `@Nullable` / `@NotNull`). Коллекции из Java приходят как платформенные типы; элементы внутри тоже могут трактоваться как nullable, чтобы не допустить NPE при реальном `null` из Java. Без аннотаций в Java тип элемента в Kotlin будет отображаться как nullable или платформенный (`T!`).

Использовать Java-коллекции из Kotlin можно напрямую: присвоить в `MutableList`, вызвать методы. При необходимости конвертации: **`javaList.toList()`** даёт Kotlin read-only `List`; **`javaList.toMutableList()`** — копию в виде `MutableList`. Для безопасной работы с элементами при отсутствии аннотаций в Java используют проверки на null, безопасный вызов `?.` и оператор `?:`, либо обёртки, гарантирующие non-null там, где это допустимо.

## Q8. Что такое toList(), toSet(), toMutableList() и когда что использовать?

**`toList()`** создаёт новый read-only список из коллекции или последовательности (при необходимости делается копия). **`toSet()`** — множество уникальных элементов. **`toMutableList()`** — изменяемую копию списка, которую можно дальше изменять. Эти вызовы являются **терминальными** для `Sequence`: они запускают выполнение всего pipeline и материализуют результат.

Используют их, когда нужно зафиксировать результат цепочки операций (например, после `sequence.map { ... }.filter { ... }.toList()`), получить независимую копию (чтобы изменения не затрагивали исходную коллекцию) или передать результат в API, ожидающий конкретный тип. Для read-only контракта предпочтительнее `toList()` или `toSet()`; для накопления и последующего изменения — `toMutableList()`.

## Q9. Как сортировать коллекции в Kotlin (sorted, sortedBy, sortWith)?

**`sorted()`** — сортировка по естественному порядку; элементы должны быть `Comparable`. **`sortedBy { selector }`** — сортировка по результату селектора (например, по полю: `sortedBy { it.name }`). **`sortedDescending()`** и **`sortedByDescending { ... }`** — то же, но по убыванию. **`sortWith(comparator)`** — сортировка по переданному компаратору, когда нужна сложная или кастомная логика сравнения.

Для **read-only** списков все эти методы возвращают **новый** список; исходный не меняется. Для **изменяемых** списков есть in-place варианты: **`sort()`**, **`sortBy { ... }`**, **`sortWith(...)`** — они изменяют сам список и не возвращают новую коллекцию (возвращают `Unit`). Выбор зависит от того, нужно ли сохранить исходный порядок или допустимо изменить список на месте.

```kotlin
data class User(val name: String, val age: Int)
val users = listOf(User("Bob", 30), User("Alice", 25))

users.sortedBy { it.name }              // новый список по имени
users.sortedByDescending { it.age }     // по возрасту убывание
users.sortedWith(compareBy({ it.name }, { it.age }))

val mut = mutableListOf(3, 1, 2)
mut.sort()  // изменяет mut, возвращает Unit
```

## Q10. Что такое lazy-операции в Sequence и зачем они нужны?

**Lazy** (ленивые) операции в `Sequence` не вычисляются в момент вызова: каждая промежуточная операция (`map`, `filter` и т.д.) лишь запоминает преобразование. Вычисление происходит при вызове **терминальной** операции: `toList()`, `first()`, `count()`, `forEach` и т.п. Тогда элементы по одному проходят всю цепочку от начала до конца.

Это уменьшает объём памяти (нет промежуточных коллекций) и может сократить объём работы: например, `sequence.map { ... }.filter { ... }.first()` остановится после первого элемента, прошедшего `filter`, а не обработает всю коллекцию. Для больших данных, длинных цепочек или когда нужен только первый/несколько элементов, `Sequence` часто эффективнее, чем те же операции над `List`.

## Q11. Чем отличаются associate, associateBy, associateWith и groupBy?

**`associate`** преобразует коллекцию в `Map`: для каждого элемента вычисляются ключ и значение через lambda, результат — `Map<K, V>`. Уникальность ключей должна обеспечиваться самим разработчиком; при дубликатах ключа остаётся последнее значение. **`associateBy`** — ключ вычисляется из элемента (или из селектора), значение — сам элемент; получается `Map<K, T>`. **`associateWith`** — значение вычисляется из элемента, ключ — сам элемент; получается `Map<T, V>`.

**`groupBy`** группирует элементы по ключу; результат — **`Map<K, List<T>>`**: один ключ соответствует списку всех элементов с этим ключом. В отличие от `associate*`, дубликаты ключей не перезаписываются — все элементы с одинаковым ключом собираются в один список. Итого: `associate` — «каждый элемент → одна пара ключ–значение»; `groupBy` — «каждый ключ → список всех элементов с этим ключом».

```kotlin
val list = listOf("a", "ab", "b", "bc")
list.associateBy { it.first() }  // {'a'="ab", 'b'="bc"} — последнее выигрывает
list.associateWith { it.length }  // {"a"=1, "ab"=2, "b"=1, "bc"=2}
list.groupBy { it.first() }  // {'a'=["a","ab"], 'b'=["b","bc"]}
```

## Q12. Когда использовать Sequence, а когда List (практический выбор)?

**Sequence** предпочтителен, когда: (1) данных много или цепочка операций длинная — чтобы не создавать промежуточные коллекции; (2) нужен только часть результата — например, `first()`, `take(n)`, `any()` — тогда ленивое выполнение может рано остановиться; (3) источник сам по себе потоковый (файл, сеть, бесконечная последовательность). **List** (и другие коллекции) предпочтителен, когда: (1) данных мало и операции простые — накладные расходы на `Sequence` могут не окупиться; (2) нужен многократный доступ по индексу или случайный доступ; (3) результат нужен целиком и несколько раз — один раз материализовать в список выгоднее, чем несколько раз итерировать `Sequence`.

На практике часто начинают с коллекции и цепочки над ней; если профилирование показывает проблемы с памятью или количеством аллокаций, переписывают на `Sequence` (добавляют `.asSequence()` в начале цепочки и вызывают терминальную операцию в конце). Для однократного прохода и длинных цепочек `Sequence` — безопасный и читаемый выбор.

## Q13. Какие операции с коллекциями самые частые по сложности и как это влияет на выбор типа?

При выборе коллекции важна асимптотика базовых операций. `ArrayList` обычно даёт O(1) доступ по индексу и амортизированное O(1) добавление в конец, но вставка/удаление в середине — O(n). `HashSet`/`HashMap` дают O(1) в среднем для contains/get/put, а `TreeSet`/`TreeMap` — O(log n), зато с упорядочиванием.

На практике сначала выбирают структуру под преобладающую операцию: много проверок на наличие — `Set`, частый доступ по ключу — `Map`, последовательный вывод и индексация — `List`. Такой подход обычно важнее микрооптимизаций цепочки `map/filter`.

## Q14. Когда использовать `kotlinx.collections.immutable`?

`kotlinx.collections.immutable` даёт persistent-коллекции (например, `PersistentList`, `PersistentMap`) с функциональной моделью обновлений: каждая модификация возвращает новую коллекцию, но за счёт структурного шаринга не копирует всё содержимое целиком. Это удобно, когда важны неизменяемость и безопасное совместное использование между потоками.

Библиотека особенно полезна в state-management (UI, event-sourcing, reducers), где нужно хранить версии состояния и избегать гонок. Если же коллекция локальная, короткоживущая и активно мутируется, обычные mutable-коллекции часто проще и быстрее.

## Q15. Как проектировать API: возвращать `List`, `Sequence` или `Flow`?

`List` подходит, когда результат нужен полностью и сразу, а источник уже материализован. `Sequence` уместен для ленивых синхронных вычислений и длинных pipeline без промежуточных аллокаций. `Flow` используют для асинхронных и потенциально бесконечных потоков данных (корутины, backpressure, отмена).

Хорошая практика для публичного API — выбирать самый простой контракт, который покрывает задачу: сначала `List`, затем `Sequence`, если есть явная выгода в ленивости, и `Flow`, если нужна асинхронность/стриминг. Это делает API предсказуемым и легче поддерживаемым.
