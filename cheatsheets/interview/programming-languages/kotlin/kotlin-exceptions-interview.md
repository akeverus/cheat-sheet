# Вопросы на собеседовании: исключения в `Kotlin`

Краткие ответы по обработке исключений в `Kotlin`: отсутствие проверяемых исключений, `try` как выражение, `Nothing`, `runCatching`, best practices.

Дата последнего обновления: 2026-02-04

## Введение

В `Kotlin` все исключения непроверяемые (unchecked): компилятор не обязывает объявлять или обрабатывать их. Часто спрашивают про отличие от `Java`, использование `try-catch` как выражения, тип `Nothing`, функции `runCatching`/`require`/`check` и рекомендации по обработке ошибок.

## Q1. (!) Есть ли в `Kotlin` проверяемые исключения (checked exceptions)?

Нет. В `Kotlin` **все исключения непроверяемые (unchecked)**: компилятор не требует объявлять их в сигнатуре функции (`throws`) и не обязывает вызывающий код обрабатывать или пробрасывать их. Вызов метода, который может бросить исключение, синтаксически ничем не отличается от вызова «безопасного» метода.

Это осознанное решение языка: в `Java` проверяемые исключения часто приводят к пустым блокам `catch` или к пробросу вверх по стеку без реальной обработки. В `Kotlin` ошибки обрабатывают там, где это действительно нужно; для явной передачи ошибок как значения используют тип **Result** или sealed-классы. Так контракт «может вернуть ошибку» выражается через тип, а не через объявление `throws`.

## Q2. Как использовать try-catch как выражение?

В `Kotlin` блок **try-catch** является **выражением**: его значение — это последнее выражение в выполненной ветке — либо в `try`, либо в `catch` (если было выброшено исключение). Блок `finally` не влияет на результат выражения (в нём обычно освобождают ресурсы). Тип выражения — общий супертип типов обеих веток.

Пример: `val n = try { str.toInt() } catch (e: NumberFormatException) { 0 }` — переменная `n` получит число при успешном парсинге или 0 при ошибке. Это позволяет писать компактный код без отдельной переменной и дублирования логики. Важно: в ветках должны быть именно выражения (значения); если нужны несколько действий, последняя строка блока должна быть выражением, дающим итоговое значение.

```kotlin
val n = try { "42".toInt() } catch (e: NumberFormatException) { 0 }  // 42
val m = try { "x".toInt() } catch (e: NumberFormatException) { 0 }    // 0
val result = try { parse(input) } catch (e: Exception) { default }
```

## Q3. Что такое тип Nothing и где он используется?

**Nothing** — тип, у которого нет ни одного значения. Функция с возвращаемым типом `Nothing` никогда не завершается нормально: она либо всегда бросает исключение, либо уходит в бесконечный цикл. Компилятор использует это для анализа потока управления: например, в ветке `when` выражение `else -> throw Exception()` имеет тип `Nothing`, поэтому компилятор считает все варианты исчерпанными и не требует дополнительной ветки.

Функции вида `fun fail(msg: String): Nothing { throw RuntimeException(msg) }` удобны для прерывания выполнения в местах, где тип должен совпасть (например, инициализация переменной после проверки). **Nothing?** допускает единственное значение — **null**; тип `Nothing?` часто встречается в обобщённых сигнатурах (например, пустой список имеет тип `List<Nothing?>` в некоторых контекстах).

## Q4. Что такое runCatching и чем отличается от try-catch?

**`runCatching { ... }`** — функция стандартной библиотеки Kotlin: она выполняет блок кода и возвращает **`Result<T>`**. При успешном выполнении возвращается `Result.success(value)`; при исключении — `Result.failure(exception)`. Исключение не пробрасывается дальше, а «упаковывается» в результат. Дальше можно вызывать `.getOrElse { }`, `.map { }`, `.recover { }`, `.onFailure { }` и т.д. — функциональный стиль обработки без явного try-catch.

Отличие от try-catch: результат всегда обёрнут в `Result`; ошибка передаётся как значение, а не через механизм исключений. Подходит, когда ошибку нужно обработать выше по стеку как данные (например, вернуть из функции `Result` или преобразовать в сообщение для пользователя). Для фатальных ошибок или когда не хотите упаковывать исключение в результат, по-прежнему используют try-catch или проброс исключения.

```kotlin
val result = runCatching { riskyOperation() }
result.getOrElse { e -> log(e); default }
result.onSuccess { }.onFailure { }
val value = result.getOrNull() ?: fallback
```

## Q5. Для чего нужны require, check и assert?

**`require(condition)`** — проверка **аргументов** функции. При `condition == false` бросается **IllegalArgumentException**. Семантика: «контракт входа» — вызывающий код не выполнил предусловия. Можно передать сообщение: `require(value >= 0) { "value must be non-negative" }`.

**`check(condition)`** — проверка **состояния** объекта или контекста. При false бросается **IllegalStateException**. Семантика: «инвариант состояния» — объект оказался в недопустимом состоянии. **`assert(condition)`** — проверка допущений в режиме отладки; выполняется только при включённом флаге JVM `-ea`. В релизе вызов может быть пропущен, поэтому для контрактов и валидации используют `require` и `check`, а не `assert`. Итого: `require` — входные данные, `check` — состояние, `assert` — отладочные допущения.

```kotlin
fun setRate(rate: Double) {
    require(rate >= 0 && rate <= 1) { "rate must be in [0, 1]" }
    this.rate = rate
}

fun execute() {
    check(state == State.READY) { "not ready" }
    // ...
}
```

## Q6. Как из Kotlin вызывать Java-код, объявляющий checked exception?

`Kotlin` **не различает** проверяемые и непроверяемые исключения с точки зрения синтаксиса. Java-метод с `throws IOException` из Kotlin вызывается как обычная функция; обрабатывать исключение или объявлять его в сигнатуре Kotlin-функции **не обязательно**. Если исключение будет выброшено, оно распространится как любое другое; перехватывать его можно по желанию.

Если Kotlin-функция сама вызывает такой Java-метод и нужно, чтобы из `Java` было видно, что метод может бросить исключение (для контракта или документации), на Kotlin-функцию вешают **`@Throws(IOException::class)`**. Тогда в сгенерированном байткоде появится объявление `throws IOException`, и Java-код сможет обрабатывать или объявлять его как проверяемое исключение.

```kotlin
@Throws(IOException::class)
fun readFile(path: String): String = File(path).readText()  // из Java видно throws
```

## Q7. Какие практики обработки ошибок рекомендуются в Kotlin?

Для **ожидаемых** ошибок (валидация, сетевая ошибка, «не найдено») предпочтительны типы: **null** (nullable), **Result**, **sealed class** с вариантами успех/ошибка — то есть передача ошибки как значения, а не через исключение. Для **фатальных** или неожиданных ситуаций (баги, отказ окружения) — бросать исключение.

Не глотать исключения пустым `catch`; логировать или преобразовывать в понятную ошибку и либо пробрасывать, либо возвращать Result. В **корутинах** использовать структурированную конкурентность и **CoroutineExceptionHandler**; при необходимости оборачивать вызовы в `runCatching` и возвращать Result. Для валидации аргументов — **require**, для инвариантов состояния — **check**. Так ошибки явно видны в типах и обрабатываются в нужных местах.

## Q8. Чем Result отличается от try-catch и когда что использовать?

**Result** — это тип-обёртка для значения или исключения: либо успех с данными, либо неудача с исключением. Обработка идёт через методы `.getOrElse`, `.map`, `.recover`, `.onFailure` и т.д. — то есть ошибка передаётся как значение по стеку вызовов. **try-catch** перехватывает исключение в месте возникновения (или пробрасывает дальше); обработка императивная.

**Result** уместен, когда ошибка — часть доменной логики (например, «файл не найден», «неверный формат»), её нужно передать выше, преобразовать или объединить с другими ошибками. **try-catch** уместен для неожиданных сбоев, для очистки ресурсов в `finally`, для перехвата в граничном слое (контроллер, main). В одном коде можно комбинировать: внутри функции использовать try-catch, а наружу возвращать Result; или наоборот — runCatching и дальше работать с Result.

## Q9. Как обрабатывать исключения в корутинах?

Исключения в корутинах распространяются вверх по иерархии Job: необработанное исключение в дочерней корутине отменяет родителя и может дойти до корня scope. Обработка: (1) **try-catch** внутри корутины — перехватываем в месте вызова; (2) **CoroutineExceptionHandler** на scope (например, на `SupervisorJob` или на scope, переданный в `runBlocking`/`launch`) — вызывается для необработанных исключений из дочерних корутин; (3) обёртка в **Result** через `runCatching` внутри корутины и возврат результата вызывающему.

**SupervisorJob** полезен, когда падение одной корутины не должно отменять остальные. **async** пробрасывает исключение при вызове **await()**; если нужно получать ошибку как значение, внутри async использовать try-catch или runCatching и возвращать Result. В тестах и при отладке часто вешают CoroutineExceptionHandler с логированием, чтобы видеть необработанные исключения.

```kotlin
val handler = CoroutineExceptionHandler { _, e -> println("Unhandled: $e") }
val scope = CoroutineScope(SupervisorJob() + handler)
scope.launch { throw RuntimeException("oops") }  // handler получит исключение
scope.launch { delay(100); println("OK") }      // эта корутина не отменяется
```

## Q10. Как проектировать иерархию пользовательских исключений в Kotlin?

Пользовательские исключения стоит группировать по домену: например, `DomainException` как базовый тип и конкретные наследники (`ValidationException`, `PaymentDeclinedException`, `AccessDeniedException`). Это упрощает централизованную обработку на границе приложения (контроллер, handler, API gateway).

Важно не делать слишком глубокую иерархию без практической пользы. Обычно достаточно 1-2 уровней и понятных имён, отражающих бизнес-сценарий. Для recoverable-ошибок полезно добавлять machine-readable код и контекст, а не только текст сообщения.

## Q11. Почему `CancellationException` в корутинах обрабатывают отдельно?

`CancellationException` в корутинах — часть нормального механизма отмены, а не «ошибка» в бизнес-логике. Если её перехватить и проглотить как обычное исключение, можно сломать кооперативную отмену и получить зависшие задачи или утечки ресурсов.

Поэтому в блоках `catch` обычно либо не ловят `CancellationException`, либо сразу пробрасывают дальше. Шаблон: `catch (e: CancellationException) { throw e }` и только потом обработка остальных исключений.

## Q12. Как обрабатывать исключения в Kotlin Flow?

Во `Flow` исключения обрабатываются оператором `catch`, который перехватывает ошибки upstream-части цепочки. Это удобно для fallback-логики: вернуть резервное значение, отправить событие ошибки, преобразовать исключение в Result/UiState.

Важно помнить, что `catch` не ловит исключения из downstream (например, внутри `collect`). Для надёжной модели часто сочетают `retry`/`retryWhen` для временных сбоев и `catch` для финальной деградации.

## Q13. Когда вместо исключений лучше использовать sealed-результаты?

Когда ошибка ожидаема и является частью бизнес-потока (валидация, отсутствие данных, отказ внешнего сервиса), sealed-результат часто удобнее исключений. Тип `sealed class` делает все варианты явными в `when` и снижает риск «забыть» обработать важный сценарий.

Исключения лучше оставлять для действительно исключительных ситуаций: баги, проблемы среды, нарушения инвариантов. Такой раздел помогает держать API предсказуемым и уменьшает скрытые control-flow переходы.

## Q14. Как правильно логировать и пробрасывать исключения?

Общая рекомендация: логировать исключение один раз на границе, где принимается решение о реакции (HTTP-ответ, retry, fail-fast). Многократное логирование одного и того же исключения на каждом уровне стека создаёт шум и мешает анализу.

При пробросе сохраняйте первопричину (`throw MyException("...", cause)`). Не теряйте stack trace и не заменяйте его «пустым» сообщением. Для продакшна полезно добавлять контекст (идентификаторы операции), но без утечки чувствительных данных.

## Q15. Какие анти-паттерны обработки исключений встречаются чаще всего?

Типичные анти-паттерны: пустой `catch`, перехват `Exception` без необходимости, проглатывание `CancellationException`, использование исключений как обычной ветки бизнес-логики, и чрезмерно общие сообщения без контекста. Такие практики ухудшают поддержку и маскируют реальные причины сбоев.

Ещё одна частая ошибка — смешивать обработку recoverable и fatal ошибок в одном блоке. Лучше разделять стратегии: retry/fallback для временных сбоев и fail-fast для критичных нарушений инвариантов.
