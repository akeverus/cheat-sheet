# Вопросы на собеседовании: `TypeScript`

`TypeScript` — статически типизированная надстройка над `JavaScript` от Microsoft (с 2012). Добавляет к `JS` систему типов, проверяемую на этапе компиляции, а на выходе даёт обычный `JavaScript`. Главные применения: крупные фронтенд-приложения, `Node.js`-бэкенды, библиотеки и любые кодовые базы, где важна надёжность при росте команды.

## Q1. (!) Что такое TypeScript и зачем он нужен?

`TypeScript` — это язык-надстройка над `JavaScript`, добавляющий статическую систему типов. Любой валидный `JS` — это валидный `TS` (TypeScript — надмножество JavaScript), но компилятор дополнительно проверяет типы и отказывается собирать код с типовыми ошибками. На выходе получается обычный `JavaScript`, который выполняется в браузере или `Node.js`.

Зачем он нужен:

- **Ошибки ловятся на этапе компиляции**, а не в проде — опечатка в имени поля или передача `string` вместо `number` видна сразу в редакторе.
- **Автодополнение и навигация** — IDE знает форму данных, поэтому даёт точные подсказки, refactor-rename и переход к определению.
- **Самодокументируемый код** — сигнатуры функций и типы описывают контракт без отдельной документации.
- **Безопасный рефакторинг** — при изменении типа компилятор показывает все места, которые нужно поправить.
- **Масштабируемость** — на больших кодовых базах и в больших командах типы удерживают сложность под контролем.

**Где применяют:** почти весь современный фронтенд (`Angular` — на `TS` по умолчанию, `React`/`Vue` — массово), `Node.js`-бэкенды (`NestJS`), библиотеки и SDK, которые поставляют типы для удобства потребителей.

## Q2. (!) Чем TypeScript отличается от JavaScript?

`JavaScript` — динамически типизированный интерпретируемый язык: типы проверяются (и часто молча приводятся) во время выполнения. `TypeScript` добавляет слой статической проверки **до** запуска.

| Аспект | JavaScript | TypeScript |
|---|---|---|
| Типизация | динамическая, в рантайме | статическая, на этапе компиляции |
| Когда видны ошибки типов | во время выполнения | при компиляции / в редакторе |
| Запуск | выполняется напрямую | сначала компилируется в `JS` |
| Аннотации типов | нет | `interface`, `type`, generics, и т.д. |
| Инструменты в IDE | ограниченные | богатые (типы → автодополнение, rename) |

Ключевая мысль: `TypeScript` **не меняет поведение программы в рантайме** — типы существуют только во время разработки и компиляции. После сборки остаётся чистый `JavaScript` без какой-либо проверки типов. Поэтому `TS` защищает от ошибок согласованности кода, но не заменяет валидацию данных, пришедших извне (см. [[typescript-interview#Q32]]).

## Q3. (!) Как происходит компиляция и что такое type erasure?

Компилятор `tsc` (или более быстрые транспиляторы — `esbuild`, `swc`, `babel`) превращает `.ts` в `.js`: проверяет типы и **удаляет** все аннотации типов, `interface`, `type`, generic-параметры. Это и называется **type erasure** — типы стирания не оставляют следа в рантайме.

```ts
// Исходный TypeScript
function greet(name: string): string {
  return `Hello, ${name}`;
}

// После компиляции — обычный JavaScript, типов нет
function greet(name) {
  return `Hello, ${name}`;
}
```

Практические следствия:

- В рантайме **нельзя** спросить «какого типа эта переменная по интерфейсу» — интерфейса уже нет. Доступны только нативные проверки `typeof`, `instanceof`, наличие свойств.
- Большинство транспиляторов (`babel`, `esbuild`) вообще **не проверяют типы**, а только вырезают их — это быстро, но проверку (`tsc --noEmit`) приходится запускать отдельно, например в CI.
- Исключения, которые **оставляют** код в рантайме: `enum` (генерирует объект), `namespace`, parameter properties в классах. `const enum` инлайнится в значения.

## Q4. (!) Что такое structural typing?

`TypeScript` использует **структурную типизацию**: совместимость типов определяется их *формой* (набором свойств), а не именем. Если объект имеет все нужные свойства подходящих типов — он подходит, даже если объявлен как другой тип. Это противоположность **номинальной** типизации в `Java`/`C#`, где важно имя класса.

```ts
interface Point {
  x: number;
  y: number;
}

function printPoint(p: Point) {
  console.log(p.x, p.y);
}

const vec = { x: 1, y: 2, z: 3 }; // тип выведен, Point нигде не указан
printPoint(vec); // OK: форма совместима (лишнее поле z не мешает)
```

Это часто называют «duck typing»: «если что-то крякает как утка — это утка». Удобно и гибко, но иногда удивляет: два разных по смыслу типа с одинаковой формой считаются взаимозаменяемыми. Когда нужна номинальность (например, отличать `UserId` от `OrderId`, хоть оба `string`), применяют приём **branding** — добавляют фантомное поле-маркер.

## Q5. (!) Какие базовые типы есть в TypeScript?

- **Примитивы:** `string`, `number`, `boolean`, `bigint`, `symbol`, `null`, `undefined`.
- **Специальные:** `any` (отключает проверку), `unknown` (безопасный «любой»), `never` (нет значений), `void` (отсутствие возвращаемого значения).
- **Объектные:** `object`, массивы (`number[]` или `Array<number>`), кортежи (`[string, number]`), функции.
- **Литеральные:** конкретные значения как тип — `"GET"`, `42`, `true` (см. [[typescript-interview#Q8]]).
- **Композитные:** union (`A | B`), intersection (`A & B`).

```ts
let id: number = 1;
let name: string = "Ann";
let tags: string[] = ["a", "b"];
let pair: [string, number] = ["age", 30]; // кортеж
let flag: boolean = true;
```

Важная деталь: при `strictNullChecks` (см. [[typescript-interview#Q30]]) `null` и `undefined` **не** входят в другие типы автоматически — `string` не может быть `null`, пока вы явно не напишете `string | null`. Это главный механизм защиты от ошибок «обращение к свойству у null».

## Q6. (!) any, unknown и never — в чём разница?

Это три «крайних» типа, и их путают чаще всего.

- **`any`** — полное отключение проверки. Значение `any` можно присваивать куда угодно и вызывать у него что угодно. Удобно как лазейка, но «заражает» код: ошибки перестают ловиться. Использовать по минимуму.
- **`unknown`** — безопасный аналог `any`, верхний тип. В `unknown` можно положить что угодно, но **использовать** значение нельзя, пока не сузишь его тип проверкой. Это заставляет писать безопасный код.
- **`never`** — нижний тип, «значений не бывает». Возникает как результат невозможной ветки или у функции, которая никогда не возвращает управление (бросает исключение или вечный цикл). Полезен для проверки исчерпываемости.

```ts
let a: any = 5;
a.foo.bar;          // компилируется, упадёт в рантайме

let u: unknown = 5;
// u.toFixed();      // ОШИБКА: сначала сузь тип
if (typeof u === "number") u.toFixed(); // OK

function fail(msg: string): never {
  throw new Error(msg); // не возвращает значение
}
```

Кратко: `any` — «доверяю, не проверяй»; `unknown` — «проверь, прежде чем использовать»; `never` — «сюда исполнение не дойдёт».

## Q7. void и чем он отличается от undefined?

`void` — тип возвращаемого значения функции, которая **ничего осмысленного не возвращает**. `undefined` — конкретное значение (и одноимённый тип).

Главная тонкость: тип `void` для callback означает «возвращаемое значение игнорируется», поэтому функцию, которая *что-то* возвращает, можно передать туда, где ждут `() => void`:

```ts
type Logger = () => void;

const log: Logger = () => "ignored"; // OK: возвращаемое значение просто не используется

// Это важно для методов вроде forEach:
const arr: number[] = [];
[1, 2, 3].forEach(x => arr.push(x)); // push возвращает number, но callback ждёт void — ОК
```

Если же объявить переменную типа `void`, в неё (при `strictNullChecks`) можно положить только `undefined`. На практике `void` используют именно как тип возврата, а `undefined` — как реальное значение «ничего нет».

## Q8. Что такое literal types?

**Литеральный тип** — это тип, состоящий из одного конкретного значения: не «любая строка», а именно `"GET"`. В сочетании с union это даёт компактные и безопасные перечисления допустимых значений.

```ts
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE";

function request(method: HttpMethod, url: string) { /* ... */ }

request("GET", "/api");   // OK
request("FETCH", "/api"); // ОШИБКА: "FETCH" не входит в union
```

Тонкость с выводом: переменная, объявленная через `let`, расширяется до базового типа (`"GET"` → `string`), а через `const` — остаётся литералом. Чтобы зафиксировать литералы в объектах и массивах, применяют `as const` (см. [[typescript-interview#Q13]]).

## Q9. Кортежи и чем они отличаются от массивов?

Массив (`number[]`) — это произвольное количество элементов одного типа. **Кортеж** (`[string, number]`) фиксирует длину и тип каждой позиции.

```ts
let scores: number[] = [1, 2, 3];          // массив: сколько угодно number
let entry: [string, number] = ["age", 30]; // кортеж: ровно string, потом number

// entry = [30, "age"]; // ОШИБКА: порядок типов не тот
```

Кортежи поддерживают опциональные и rest-элементы: `[string, number?]`, `[string, ...number[]]`. Их используют для возврата нескольких значений и в типизации React-хуков (`useState` возвращает `[value, setValue]`). С `as const` кортеж становится `readonly`, что защищает от случайной мутации.

## Q10. enum — какие бывают и в чём подвох?

`enum` — именованный набор констант. Бывают числовые и строковые.

```ts
enum Direction { Up, Down }        // числовой: Up=0, Down=1
enum Status { Active = "ACTIVE", Closed = "CLOSED" } // строковый
```

Подводные камни:

- **Числовой `enum` генерирует объект в рантайме** и делает обратное отображение (`Direction[0] === "Up"`). Это значит, что `enum` — одна из немногих конструкций `TS`, оставляющих код после компиляции (нарушает «чистый» type erasure).
- **`const enum`** инлайнится прямо в значения (рантайм-объекта нет), но плохо дружит с `isolatedModules` и отдельными транспиляторами.
- Числовой `enum` допускает присваивание любого `number` (исторически), что снижает безопасность.

Поэтому многие предпочитают **union литеральных типов** (`type Status = "ACTIVE" | "CLOSED"`) или объект с `as const`: они полностью стираются, проще и безопаснее. `enum` оправдан, когда нужна именно рантайм-сущность с обратным отображением.

## Q11. (!) Как работает вывод типов?

`TypeScript` старается вывести типы сам, чтобы не приходилось аннотировать всё подряд. Источники вывода:

- **Инициализатор переменной:** `let x = 3` → `x: number`.
- **Возвращаемое значение функции:** выводится из `return`.
- **Контекстная типизация:** тип ожидаемого callback подсказывает типы его параметров.

```ts
let n = 42;            // number (по значению)
const s = "hi";        // "hi" (const → литеральный тип)

[1, 2, 3].map(x => x * 2); // x выведен как number из типа массива
```

Важное различие **let vs const**: `const` сохраняет узкий литеральный тип, `let` расширяет до базового (`"hi"` → `string`), потому что `let`-переменную можно переприсвоить. Хорошая практика — полагаться на вывод для локальных значений, но **явно аннотировать** публичные сигнатуры функций и границы модулей: так контракт зафиксирован и ошибки локализуются.

## Q12. (!) Что такое type assertion и чем оно опасно?

**Type assertion** (`value as Type`) — это указание компилятору «доверься мне, тип именно такой». Проверки при этом не происходит: вы берёте ответственность на себя.

```ts
const el = document.getElementById("app") as HTMLInputElement;
el.value = "x"; // компилятор верит, что это input

const data = JSON.parse(raw) as User; // НИКТО не проверил, что raw действительно User
```

Опасность: assertion **не делает рантайм-проверку**. Если реальная форма данных не совпала (битый JSON, элемент оказался `div`), ошибка вылезет позже и в другом месте. Поэтому:

- Не используйте `as` для «починки» ошибок типов — обычно это сигнал, что тип описан неверно.
- Для внешних данных вместо `as` делайте настоящую валидацию (type guard или схема, см. [[typescript-interview#Q32]]).
- `as any` и двойное `as unknown as T` — крайняя мера, маркер технического долга.

## Q13. (!) Что делает const assertion?

`as const` превращает выражение в максимально узкий, **неизменяемый** тип: литералы остаются литералами, а объекты и массивы становятся `readonly`.

```ts
const a = { method: "GET" };          // { method: string }
const b = { method: "GET" } as const; // { readonly method: "GET" }

const arr1 = [1, 2];           // number[]
const arr2 = [1, 2] as const;  // readonly [1, 2] (кортеж)
```

Зачем это нужно:

- Зафиксировать допустимые значения как литеральный union (`typeof arr2[number]` → `1 | 2`).
- Передать конфиг туда, где ждут конкретные литералы, а не расширенные `string`/`number`.
- Защитить константы от мутации на уровне типов.

`as const` — частый приём, чтобы из обычного объекта получить «таблицу констант», по которой строят union типов без отдельного `enum`.

## Q14. (!) interface или type — что выбрать?

Обе конструкции описывают форму данных, и для объектов почти взаимозаменяемы. Различия:

| Возможность | `interface` | `type` |
|---|---|---|
| Описать объект/контракт класса | да | да |
| Union / intersection | нет | да (`A \| B`, `A & B`) |
| Кортежи, примитивы, mapped/conditional | нет | да |
| Declaration merging (доп. объявления) | да | нет |
| `extends` / `implements` | да (естественно) | через `&` |

Практическое правило:

- **`interface`** — для публичных контрактов объектов и классов, особенно если их могут расширять (в т.ч. через declaration merging для библиотек).
- **`type`** — когда нужны union, intersection, кортежи, утилитные и условные типы, алиасы примитивов.

```ts
interface User { id: number; name: string; }
type Id = string | number;                 // union — только через type
type Admin = User & { role: "admin" };     // intersection
```

На практике команды часто берут `interface` по умолчанию для объектов и `type` — для всего остального. Разница в производительности компилятора минимальна и в большинстве проектов несущественна.

## Q15. Declaration merging и расширение интерфейсов?

**Declaration merging** — особенность `interface`: несколько объявлений с одним именем сливаются в одно.

```ts
interface Window {
  myGlobal: string;
}
// где-то ещё:
interface Window {
  anotherGlobal: number;
}
// Итог: Window содержит оба поля
```

Это активно используют для **расширения типов библиотек** — например, добавить поле в `Express.Request` или глобальный `Window`, не редактируя чужой код. `type`-алиасы так не умеют: повторное объявление с тем же именем — ошибка.

Обычное наследование интерфейсов делается через `extends`:

```ts
interface Animal { name: string; }
interface Dog extends Animal { breed: string; }
```

## Q16. Опциональные, readonly свойства и index signatures?

- **Опциональные** (`?`) — свойство может отсутствовать; его тип становится `T | undefined`.
- **`readonly`** — свойство нельзя переприсвоить после создания (защита на уровне типов, в рантайме его нет).
- **Index signature** — описывает объект с заранее неизвестными ключами.

```ts
interface Config {
  readonly id: number;     // только чтение
  name?: string;           // может отсутствовать
  [key: string]: unknown;  // любые строковые ключи
}
```

Тонкости: `readonly` — «поверхностный» (вложенные объекты всё ещё мутабельны). Index signature ослабляет проверку (любой ключ становится допустимым), поэтому злоупотреблять им не стоит — часто лучше `Record<K, V>` или `Map`.

## Q17. (!) Union и intersection типы?

- **Union (`A | B`)** — «или»: значение одного из типов. Доступны только **общие** для всех членов свойства, пока тип не сужен.
- **Intersection (`A & B`)** — «и»: значение, удовлетворяющее **обоим** типам одновременно (объединение всех свойств).

```ts
type Id = string | number;        // union: либо строка, либо число

interface Named { name: string; }
interface Aged { age: number; }
type Person = Named & Aged;       // intersection: и name, и age

const p: Person = { name: "Ann", age: 30 };
```

Интуиция, которая многих путает: union *расширяет* множество значений, но *сужает* доступный набор операций (только общее); intersection *сужает* множество значений, но *расширяет* набор свойств. Union — основа моделирования «одно из» (см. discriminated unions, [[typescript-interview#Q19]]).

## Q18. (!) Что такое narrowing и встроенные type guards?

**Narrowing** — это сужение типа внутри ветки кода на основе проверок. Компилятор анализирует поток управления и в каждой ветке знает более точный тип. Встроенные «охранники»:

- **`typeof`** — для примитивов: `typeof x === "string"`.
- **`instanceof`** — для классов: `x instanceof Date`.
- **`in`** — наличие свойства: `"role" in user`.
- **проверка на `null`/`undefined`**, truthiness, сравнение с литералом.

```ts
function format(x: string | number) {
  if (typeof x === "string") {
    return x.toUpperCase(); // здесь x: string
  }
  return x.toFixed(2);      // здесь x: number
}
```

Narrowing — то, что делает union-типы удобными: вы описываете «одно из нескольких», а в коде компилятор сам подсказывает, какие операции доступны после проверки.

## Q19. (!) Что такое discriminated unions?

**Discriminated (tagged) union** — паттерн моделирования «одно из нескольких состояний»: каждый член union имеет общее свойство-**дискриминант** с уникальным литеральным значением. По нему компилятор однозначно сужает тип.

```ts
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.radius ** 2; // s сужен до circle
    case "square": return s.side ** 2;             // s сужен до square
    default:
      const _exhaustive: never = s; // проверка исчерпываемости
      return _exhaustive;
  }
}
```

Бонус — **проверка исчерпываемости**: если позже добавить новый `kind`, присваивание оставшегося значения в `never` перестанет компилироваться, и компилятор укажет на необработанный случай. Это один из самых сильных приёмов `TS` для надёжных state-моделей.

## Q20. (!) Пользовательские type guards и предикаты is?

Когда встроенных проверок мало, пишут **пользовательский type guard** — функцию с возвращаемым типом-предикатом `параметр is Тип`. Если она вернула `true`, компилятор сужает тип в вызывающем коде.

```ts
interface Cat { meow(): void; }
interface Dog { bark(): void; }

function isCat(pet: Cat | Dog): pet is Cat {
  return "meow" in pet;
}

function speak(pet: Cat | Dog) {
  if (isCat(pet)) pet.meow(); // pet сужен до Cat
  else pet.bark();            // pet сужен до Dog
}
```

Родственная конструкция — **assertion functions** (`asserts x is T`): они не возвращают булево, а бросают исключение, если проверка не прошла, и после вызова тип считается суженным.

```ts
function assertString(v: unknown): asserts v is string {
  if (typeof v !== "string") throw new Error("not a string");
}
```

Пользовательские guard-ы — стандартный способ безопасно работать с `unknown` и внешними данными.

## Q21. (!) Что такое generics и зачем они?

**Generics** — параметризация типом: код пишется один раз для «любого `T`», но типобезопасность сохраняется для каждого конкретного применения. Без них пришлось бы либо дублировать код, либо терять типы через `any`.

```ts
function identity<T>(value: T): T {
  return value;
}

const a = identity<string>("hi"); // T = string
const b = identity(42);            // T выведен как number

interface Box<T> { value: T; }
const box: Box<number> = { value: 1 };
```

Зачем: контейнеры (`Array<T>`, `Promise<T>`, `Map<K, V>`), функции-утилиты, которые сохраняют связь между входным и выходным типом. Ключевое отличие от `any`: generic **запоминает** конкретный тип и проносит его через вызов, поэтому результат остаётся типизированным.

## Q22. Generic constraints через extends?

По умолчанию внутри generic-функции о `T` ничего не известно — нельзя обращаться к его свойствам. **Constraint** (`T extends X`) ограничивает `T` подходящими типами и открывает доступ к их членам.

```ts
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

longest("abc", "de");     // OK: у строк есть length
longest([1, 2], [3]);     // OK: у массивов есть length
// longest(1, 2);         // ОШИБКА: у number нет length
```

Частый приём — связать два параметра: `function pick<T, K extends keyof T>(obj: T, key: K): T[K]`. Здесь `K` ограничен ключами `T`, а возвращаемый тип — точный тип значения по этому ключу (см. [[typescript-interview#Q23]]).

## Q23. (!) keyof и indexed access types?

- **`keyof T`** даёт union всех ключей типа `T`.
- **Indexed access** `T[K]` — тип значения по ключу `K`.

```ts
interface User { id: number; name: string; }

type Keys = keyof User;       // "id" | "name"
type NameType = User["name"]; // string

function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const u: User = { id: 1, name: "Ann" };
const n = get(u, "name"); // тип string, не any
get(u, "email");          // ОШИБКА: нет такого ключа
```

Эта пара — фундамент «типобезопасного доступа по ключу» и большинства утилитных типов: `keyof` перечисляет ключи, `T[K]` достаёт типы значений, а вместе они позволяют писать обобщённый код, не теряя точные типы.

## Q24. (!) Какие есть utility types?

Встроенные **utility types** — готовые трансформации типов. Самые ходовые:

- **`Partial<T>`** — все поля опциональны; **`Required<T>`** — все обязательны.
- **`Readonly<T>`** — все поля только для чтения.
- **`Pick<T, K>`** — выбрать подмножество ключей; **`Omit<T, K>`** — исключить ключи.
- **`Record<K, V>`** — объект с ключами `K` и значениями `V`.
- **`Exclude<U, X>` / `Extract<U, X>`** — фильтрация union.
- **`NonNullable<T>`** — убрать `null`/`undefined`.
- **`ReturnType<F>` / `Parameters<F>`** — тип результата и кортеж аргументов функции.
- **`Awaited<T>`** — тип, к которому разрешается `Promise`.

```ts
interface User { id: number; name: string; email: string; }

type UserPatch = Partial<User>;          // все поля опциональны
type PublicUser = Omit<User, "email">;   // без email
type UsersById = Record<number, User>;   // словарь
```

Эти типы выражены через mapped и conditional types (см. [[typescript-interview#Q25]], [[typescript-interview#Q26]]) — их полезно понимать, чтобы при необходимости писать свои.

## Q25. (!) Что такое conditional types?

**Conditional type** выбирает один из двух типов по условию совместимости: `T extends U ? X : Y` — «если `T` присваиваем к `U`, то `X`, иначе `Y`».

```ts
type IsString<T> = T extends string ? "yes" : "no";
type A = IsString<string>; // "yes"
type B = IsString<number>; // "no"
```

Важная особенность — **дистрибутивность** по union: если `T` — это union, условие применяется к каждому члену по отдельности.

```ts
type ToArray<T> = T extends any ? T[] : never;
type R = ToArray<string | number>; // string[] | number[]
```

Условные типы — основа многих утилитных (`Exclude`, `NonNullable`, `ReturnType`) и способ выражать сложные типовые правила. В паре с `infer` (см. [[typescript-interview#Q27]]) они умеют «вытаскивать» типы из других типов.

## Q26. Что такое mapped types?

**Mapped type** строит новый тип, проходя по ключам существующего: `{ [K in keyof T]: ... }`. На этом построены `Partial`, `Readonly`, `Record`.

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] };
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };

interface User { id: number; name: string; }
type OptionalUser = MyPartial<User>; // { id?: number; name?: string }
```

Можно добавлять и снимать модификаторы через `+`/`-` (`-readonly`, `-?`) и переименовывать ключи через `as`:

```ts
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};
// Getters<User> = { getId: () => number; getName: () => string }
```

Mapped types вместе с template literal types дают мощные трансформации форм данных без дублирования.

## Q27. Для чего нужен infer?

`infer` объявляет «типовую переменную» внутри conditional type, чтобы **захватить** часть типа. Компилятор сам подставит в неё подходящий тип.

```ts
type ElementType<T> = T extends (infer U)[] ? U : T;
type A = ElementType<string[]>; // string
type B = ElementType<number>;   // number (не массив — вернулся сам тип)

// Так устроен встроенный ReturnType:
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;
type R = MyReturnType<() => User>; // User
```

`infer` — способ «распаковать» тип: достать тип элемента массива, тип результата функции, тип, к которому разрешается `Promise`, и т.д. Это основной инструмент метапрограммирования на типах.

## Q28. Как работает перегрузка функций?

`TypeScript` позволяет описать несколько **сигнатур** одной функции (overloads), а затем — одну реализацию, совместимую со всеми ними. Вызывающий код видит только сигнатуры-перегрузки, не реализацию.

```ts
function parse(value: string): string[];
function parse(value: number): number[];
function parse(value: string | number): string[] | number[] {
  return typeof value === "string" ? value.split("") : [value];
}

const a = parse("ab"); // string[]
const b = parse(42);   // number[]
```

Тонкости: сигнатура реализации не видна снаружи и должна быть достаточно общей, чтобы покрыть все перегрузки. Часто вместо overloads проще и читаемее обойтись union-типами или generics — перегрузки оправданы, когда связь вход→выход нельзя выразить иначе.

## Q29. Модификаторы доступа и parameter properties?

Классы в `TS` поддерживают модификаторы:

- **`public`** (по умолчанию) — доступно везде.
- **`private`** — только внутри класса (проверка на этапе компиляции; в рантайме поле остаётся доступным).
- **`protected`** — внутри класса и наследников.
- **`readonly`** — присваивается только в конструкторе.

Для настоящей приватности в рантайме есть нативные `#private`-поля (ECMAScript 2022), которые недоступны извне даже в скомпилированном `JS`.

**Parameter properties** — сокращение: модификатор в параметре конструктора сразу объявляет и инициализирует поле.

```ts
class User {
  constructor(
    public readonly id: number,
    private name: string,
  ) {}
  // эквивалент объявления полей + this.id = id; this.name = name;
}
```

Это одна из немногих конструкций, которые **генерируют код** в рантайме (присваивание полей), а не стираются.

## Q30. (!) Что такое strict mode в tsconfig?

Флаг `"strict": true` в `tsconfig.json` включает набор строгих проверок разом. Самые важные из них:

- **`strictNullChecks`** — `null`/`undefined` не входят в другие типы автоматически; их нужно учитывать явно. Это главный защитник от ошибок «cannot read property of undefined».
- **`noImplicitAny`** — запрещает неявный `any`: каждый невыводимый тип нужно аннотировать.
- **`strictFunctionTypes`** — строгая (контравариантная) проверка типов параметров функций.
- **`strictPropertyInitialization`** — поля класса должны быть инициализированы.
- **`strictBindCallApply`**, **`noImplicitThis`**, **`alwaysStrict`**, **`useUnknownInCatchVariables`**.

```jsonc
{
  "compilerOptions": {
    "strict": true,        // включает весь набор
    "target": "ES2022",
    "module": "ESNext"
  }
}
```

Практика: новые проекты всегда стартуют со `strict: true` — без `strictNullChecks` теряется бо́льшая часть пользы `TypeScript`. Полезно добавить и `noUncheckedIndexedAccess` (доступ по индексу даёт `T | undefined`), хотя он не входит в `strict`.

## Q31. Что такое .d.ts и DefinitelyTyped?

**`.d.ts`** (declaration file) — файл, содержащий только объявления типов без реализации. Он описывает форму существующего `JavaScript`-кода, чтобы `TS` знал его типы.

```ts
// math.d.ts
export declare function add(a: number, b: number): number;
```

Зачем нужны:

- Библиотеки на `TS` поставляют `.d.ts` рядом со скомпилированным `JS` — потребитель получает типы из коробки.
- Для библиотек на чистом `JS` типы публикуются отдельно в **DefinitelyTyped** — огромном репозитории, откуда они ставятся как пакеты `@types/имя-пакета` (например, `@types/node`, `@types/lodash`).
- Компилятор сам генерирует `.d.ts` при `"declaration": true`.

Если для пакета нет типов и нет `@types/...`, можно написать локальный `.d.ts` с минимальными объявлениями или временно объявить модуль через `declare module`.

## Q32. (!) Почему типы нельзя проверять в рантайме?

Потому что типы **стираются** при компиляции (type erasure, см. [[typescript-interview#Q3]]): в готовом `JavaScript` нет ни `interface`, ни generic-параметров. Значит, данные, пришедшие извне (HTTP-ответ, `localStorage`, ввод пользователя), `TypeScript` сам по себе **не валидирует** — он лишь верит аннотации.

```ts
const user = await res.json() as User; // компилятор поверил, проверки НЕТ
// если сервер вернул другое — ошибка вылезет позже
```

Как с этим жить:

- **Валидировать на границе** с помощью схемных библиотек (`zod`, `io-ts`, `valibot`): они проверяют данные в рантайме и одновременно выводят `TS`-тип.
- Писать **пользовательские type guards** (см. [[typescript-interview#Q20]]) для ручной проверки.
- Не подменять валидацию `as`-утверждением — оно лишь подавляет ошибку компиляции, но не защищает в рантайме.

```ts
import { z } from "zod";
const UserSchema = z.object({ id: z.number(), name: z.string() });
const user = UserSchema.parse(await res.json()); // упадёт, если форма не та
```

Правило: типы защищают *внутреннюю* согласованность кода; *внешние* данные нужно валидировать явно.

## Q33. (!) Какие минусы и подводные камни у TypeScript?

- **Шаг сборки и инструментарий.** Нужен компилятор/транспилятор, настройка `tsconfig`, отдельная проверка типов в CI. На больших проектах `tsc` может быть медленным.
- **Сложность системы типов.** Conditional/mapped/template-типы мощные, но трудночитаемые; легко переусложнить и получить «type-астрономию», которую никто в команде не понимает.
- **Типы стираются.** Нет рантайм-защиты внешних данных (см. [[typescript-interview#Q32]]) — нужна отдельная валидация.
- **Лазейки `any`.** Один `any` (часто из нетипизированной библиотеки) тихо «разъедает» типобезопасность вокруг.
- **Качество сторонних типов.** `@types/...` могут отставать от версии библиотеки, быть неполными или неверными.
- **Структурная типизация удивляет.** Совместимость по форме иногда пропускает логически разные типы (нужен branding для номинальности).
- **Ложное чувство безопасности.** «Компилируется» не значит «корректно»: типы не ловят логические ошибки и не заменяют тесты.

Итог: для средних и крупных кодовых баз плюсы (надёжность, инструменты, рефакторинг) обычно перевешивают, но `TypeScript` — не бесплатный и не серебряная пуля.
