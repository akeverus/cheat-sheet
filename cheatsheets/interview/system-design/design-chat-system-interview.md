# Вопросы на собеседовании: `Design Chat System`

`Chat System` (WhatsApp, Slack, Telegram, Messenger) — популярная задача на system design. Ключевые темы: **stateful-соединения** (WebSockets), упорядочивание (ordering), гарантии доставки, масштаб. Обсуждаются presence, групповые чаты, шифрование, хранение, push-уведомления.

## Q1. (!) Какие функциональные и нефункциональные требования к чат-системе?

С требований начинается любой system design: они определяют, какие компоненты вообще понадобятся. Для чата важно сразу разделить, *что* система делает (функционал) и *как хорошо* (качества вроде задержки и надёжности) — именно нефункциональные требования диктуют архитектуру.

**Функциональные** (что умеет система):
- Переписка 1:1
- Групповой чат (обычно 10–100 человек, до 500)
- Статус online/offline (presence)
- Доставка сообщений (real-time если получатель online, push если offline)
- Read receipts — отметки о прочтении
- История сообщений
- Индикаторы набора текста (typing indicators)
- Обмен медиа (фото, файлы)

**Нефункциональные** (насколько хорошо) — именно они задают сложность задачи:
- **Низкая задержка** — доставка сообщения < 500 мс, иначе чат ощущается «тормозным»
- **Высокая надёжность** — сообщения не теряются (для мессенджера это критично)
- **Доступность** — 99.99%
- **Масштабируемость** — миллиарды пользователей (у WhatsApp 2B+)
- **Упорядочивание** — собеседники видят сообщения в одной и той же последовательности
- **Шифрование** — E2E для приватности

**Эмпирическое правило:** на собеседовании проговорите требования вслух и зафиксируйте масштаб (число пользователей, сообщений) — от этих цифр зависят все последующие решения.

## Q2. (!) Как оценить нагрузку и ёмкость чат-системы (capacity estimation)?

Оценка ёмкости показывает интервьюеру, что вы умеете переводить требования в конкретные цифры: сколько серверов, какое хранилище, какая пропускная способность. Считать нужно от понятных допущений и держать порядок величин, а не точное число.

**Допущения** (отталкиваемся от масштаба WhatsApp):
- 1B активных пользователей
- В среднем 50 сообщений на пользователя в день
- 500M одновременно online в пике

**Сообщения** (нагрузка на запись):
- 1B × 50 = **50B сообщений/день**
- 50B / 86400 ≈ **580K msg/sec в среднем**
- Пик ~2M msg/sec (трафик неравномерен в течение суток)

**Хранилище** (растёт линейно и накапливается):
- 100B на сообщение (текст + метаданные)
- 50B × 100B = **5 TB/день**
- За 5 лет → ~9 PB
- С учётом медиа — в 10–100 раз больше

**Пропускная способность:**
- Среднее: 580K/s × 100B ≈ 58 MB/s
- Пик: 2M/s × 100B ≈ 200 MB/s — нагрузка по сети скромная (узкое место не здесь)

**Число соединений** — главная особенность чата: соединения постоянные, а не «запрос-ответ»:
- 500M одновременных WebSocket-соединений
- ~1M соединений на сервер (после тюнинга) → 500 серверов на connection-ярус
- Консервативнее: 50K на сервер → 10K серверов

**Память под presence:**
- Карта user_id → server_id: 1B × 16B = 16 GB
- Помещается в Redis

**Вывод:** узкое место чата — не пропускная способность по сети, а удержание сотен миллионов постоянных соединений и объём хранилища. На этом и стоит строить дизайн.

## Q3. (!) Чем WebSockets отличаются от long polling и SSE и что выбрать для чата?

Чату нужен канал, по которому сервер может *сам* пушить сообщение клиенту, не дожидаясь запроса. Обычный HTTP-запрос-ответ для этого не годится. Сравнение сводится к тому, нужна ли двусторонность и какой ценой достигается «серверный push».

**WebSockets** — двунаправленное постоянное TCP-соединение.
- **Лучший выбор** для чата: сообщения идут и туда, и обратно по одному каналу
- Одно TCP-соединение на клиента
- Низкие накладные расходы после установки

**Long polling** — клиент делает запрос, сервер удерживает его открытым до события, затем отвечает.
- Запасной вариант для окружений, где WS заблокирован (старые прокси, корпоративные сети)
- Дороже: HTTP-оверхед на каждое событие

**SSE (Server-Sent Events)** — односторонний канал server → client.
- Не двунаправленный: чтобы отправить сообщение, клиенту нужен отдельный POST
- Работает поверх HTTP/2, что упрощает масштабирование

**Push (mobile)** — APNs (iOS), FCM (Android) для уведомлений, когда приложение закрыто.
- Будят устройство и показывают уведомление
- Само приложение забирает реальные сообщения уже после открытия

**Решение на практике — гибрид:**
- Основной канал — WebSocket, пока приложение активно
- Запасной — long polling там, где WS не проходит
- Offline — push-уведомление, а при следующем открытии происходит синхронизация пропущенного

**Обработка разрывов** (соединение может молча умереть):
- Heartbeat (ping) каждые 30 с
- Обнаружили мёртвое соединение → переподключаемся
- Экспоненциальный backoff, чтобы не добить упавший сервер шквалом реконнектов

## Q4. (!) Как маршрутизировать соединения и балансировать нагрузку при stateful-соединениях?

Главная сложность: WebSockets **stateful** — соединение пользователя живёт на одном конкретном сервере, а не на любом. Чтобы доставить сообщение пользователю X, систему нужно сначала узнать, на каком сервере он сидит, и направить сообщение именно туда. Это и отличает чат от обычного stateless-HTTP-сервиса за балансировщиком.

**Архитектура:**

```
Client → LB → WebSocket server (holds connection)
                    ↓
              Message broker (Kafka/Redis pub-sub)
                    ↑
Other user's WebSocket server publishes message for X
```

**Как идёт маршрутизация:**
- Пользователь X подключается → балансировщик назначает его на WS-сервер S1
- Presence-сервис запоминает: `user_id:X → server:S1` (в Redis)
- Когда Y пишет X:
  1. Сообщение приходит на WS-сервер пользователя Y
  2. По presence находим сервер X (или публикуем в канал X через брокер)
  3. Сервер X пушит сообщение в его WebSocket

**Балансировка нагрузки** — два подхода:
- Consistent hashing (user_id → server): sticky, но масштабируется без полной переразбивки
- Либо round-robin при подключении + центральная маршрутизация сообщений через брокер

**Лимиты соединений:**
- 500K–1M одновременных на сервер (после тюнинга ОС и приложения)
- Горизонтальное масштабирование — добавляем серверы

**Отказоустойчивость:**
- Сервер падает → его WebSockets рвутся
- Клиенты автоматически переподключаются и попадают на новый сервер
- Реестр presence обновляется на актуальное расположение

## Q5. В чём проблема sticky session и как её решают в чате?

**Суть проблемы:** когда пользователь переподключается, должен ли он попасть на *тот же* сервер или подойдёт любой? От ответа зависит, как маршрутизировать его сообщения и как масштабировать кластер. Это компромисс между предсказуемостью и гибкостью.

**Вариант A — sticky (consistent hash):**
- Пользователь привязан к серверу по `hash(user_id) % N`
- При переподключениях попадает на тот же сервер
- **Плюс:** предсказуемо, легко найти соединение пользователя
- **Минус:** при масштабировании (изменении N) часть пользователей переезжает на другие серверы — ребалансировка

**Вариант B — любой сервер + маршрутизация через брокер:**
- Пользователь подключается к любому серверу (round-robin)
- Сообщения для него маршрутизируются через брокер: pub-sub на персональном канале пользователя
- **Плюс:** гибкое масштабирование, серверы взаимозаменяемы
- **Минус:** лишний hop через брокер на каждое сообщение

**Как делают на практике:** вариант B чаще (Slack, Discord) — он гибче, а стоимость лишнего hop окупается простотой эксплуатации.

**Обновление presence при переподключении** (запись о расположении должна следовать за пользователем):
```
On connect: SET user:X server:S2
On disconnect: DEL user:X
```

## Q6. (!) Как выглядит высокоуровневая архитектура чат-системы?

Идея — разделить ответственность по ярусам: отдельный ярус держит постоянные соединения, брокер развязывает серверы между собой, бизнес-сервисы и хранилища стоят за ними. Тогда каждый ярус масштабируется независимо.

```
Clients (mobile/web)
    ↓ WebSocket
[Load Balancer]
    ↓
[WebSocket Service Tier] ← (millions of persistent connections)
    ↓ ↑
[Message Broker (Kafka/Redis pub/sub)]
    ↓ ↑
[Service Tier] — Chat API, Presence, User, Group services
    ↓
[Storage Tier] — Cassandra (messages), Postgres (users), Redis (presence, cache)
    ↓
[Media Store] — S3 для photos/videos
    ↓
[Push Service] — APNs, FCM integration
```

**Компоненты и зачем каждый:**

- **WS Gateway** — терминирует WebSocket и управляет жизненным циклом соединения; единственный stateful-ярус
- **Chat Service** — запись и выборка сообщений
- **Presence Service** — отслеживает статус online и расположение пользователя
- **User Service** — профиль, аутентификация
- **Group Service** — управление группами и составом участников
- **Notification Service** — отправка push offline-пользователям
- **Search Service** — Elasticsearch для поиска по истории

**Ключевая мысль:** stateful только WS-ярус. Все бизнес-сервисы и хранилища stateless/реплицируемы, поэтому масштабируются стандартными приёмами.

## Q7. (!) Как сообщение проходит путь от отправителя до получателя (delivery flow)?

Ключевой принцип — **сначала сохранить, потом доставить**: даже если получатель offline или push не дойдёт, сообщение уже лежит в хранилище и не потеряется. Дальше маршрут зависит от того, online получатель или нет.

**Чат 1:1, оба online:**

```
User A writes → A's WebSocket
    ↓
WS server → Chat service → Persist (Cassandra)
    ↓
WS server → lookup Presence(B) → B on server S3
    ↓
Publish to channel user:B (Kafka/Redis)
    ↓
S3 subscribed → pushes via WebSocket to B
    ↓
B ACKs → read receipt back to A
```

**Задержка:** обычно < 200 мс end-to-end.

**Доставка, когда получатель offline:**
- Presence показывает: B offline → через WS не маршрутизируем
- Кладём сообщение в очередь недоставленных пользователя B (DB / Redis)
- Триггерим push-уведомление (FCM/APNs)
- B открывает приложение → устанавливает WS → забирает накопленные сообщения

**Почему это надёжно:**
- ACK на каждом hop подтверждает, что сообщение принято
- Брокер делает retry при временном сбое
- Персист идёт *до* push: упал push — сообщение всё равно в хранилище и дойдёт при синхронизации

## Q8. Зачем нужен брокер сообщений между серверами и какой выбрать?

Без брокера сервер отправителя должен сам знать, где сидит получатель, и стучаться напрямую — это жёстко связывает серверы и плохо масштабируется. Брокер развязывает их: отправитель просто публикует в канал получателя, а доставит тот сервер, на котором получатель подключён.

**Что даёт брокер:**
- Развязывает сервер отправителя и сервер получателя
- Масштабируемость: публикуем в канал, а не ищем сервер напрямую
- Retry при временном сбое

**Варианты и когда что:**

**Redis pub/sub** — для real-time сигналинга:
- Очень быстро (микросекунды)
- Fire-and-forget, без персистентности
- Хорош для presence и сигналинга
- Доставка не гарантируется: если подписчик на мгновение отвалился, сообщение теряется

**Kafka** — для надёжных асинхронных пайплайнов:
- Durable, возможен replay
- Выше задержка (10–100 мс)
- Лучше для аналитики и уведомлений, где важна сохранность

**NATS** — компромисс: быстро и с at-least-once.

**Гибрид** (типичное решение):
- Redis pub/sub для real-time сигналинга
- Kafka для персистентности и аналитики

**Паттерн «канал на пользователя»:**
```
Each user has a channel: user:{id}
S1 publishes: PUBLISH user:X "msg"
S3 (where X connected) SUBSCRIBE user:X → push to X's WS
```

## Q9. (!) Как спроектировать схему хранения сообщений?

Схему ведёт главный запрос: «отдай последние сообщения беседы». Поэтому беседа становится партицией, а время — ключом сортировки внутри неё. Это даёт быстрые range-запросы по свежим сообщениям без сканирования всей таблицы.

**Сообщения (Cassandra):**

```sql
CREATE TABLE messages (
    conversation_id UUID,
    message_id TIMEUUID,   -- ordered by time
    sender_id UUID,
    content TEXT,
    sent_at TIMESTAMP,
    PRIMARY KEY (conversation_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

- **Партиция** — `conversation_id`: все сообщения беседы лежат на одной node, читаются одним запросом
- **Кластеризация** по времени: эффективные range-запросы за свежими сообщениями
- `TIMEUUID` совмещает сортировку по времени и уникальность

**Беседы (conversations):**
```sql
CREATE TABLE conversations (
    conversation_id UUID,
    participant_ids SET<UUID>,
    type TEXT,  -- 'direct' or 'group'
    created_at TIMESTAMP,
    last_message_id TIMEUUID
);
```

**Индекс «пользователь → беседы»** (отдельная таблица под запрос «список чатов»):
```sql
CREATE TABLE user_conversations (
    user_id UUID,
    last_message_at TIMESTAMP,
    conversation_id UUID,
    PRIMARY KEY (user_id, last_message_at, conversation_id)
) WITH CLUSTERING ORDER BY (last_message_at DESC);
```

Сортировка по `last_message_at DESC` сразу даёт список бесед по недавней активности — как на главном экране мессенджера.

**Подводный камень:** в операционной БД сообщения **не индексируются по content** — полнотекстовый поиск выносят в отдельный Elasticsearch (см. Q21).

## Q10. (!) Что выбрать для чата — SQL или NoSQL?

Универсального ответа нет: разные данные имеют разный профиль доступа, поэтому выбирают БД под каждый тип, а не одну на всё. Главный водораздел — между потоком сообщений (огромный объём, простой паттерн доступа) и данными пользователей (нужна согласованность и связи).

**Сообщения чата** → NoSQL:
- **Write-heavy** — каждое сообщение это запись
- Доступ как к **time-series** — почти всегда читают свежие сообщения
- Идеально **партиционируются по беседе**

Поэтому **Cassandra / DynamoDB** подходят: горизонтальное масштабирование, высокая пропускная способность на запись, низкая задержка под нагрузкой.

**Данные пользователя (профиль, аутентификация)** → SQL:
- Реляционные связи (users, friends)
- Важна строгая согласованность
- Подходит **Postgres**

**Presence** → Redis:
- Эфемерные, маленькие данные, in-memory скорость

**Членство в группах** → SQL или document-БД:
- Небольшие реляционные данные

**Как в реальности** (подтверждает «БД под задачу»):
- WhatsApp — своё решение (Erlang + Mnesia)
- Messenger — HBase
- Slack — MySQL (шардированный)

## Q11. Как шардировать данные чата?

Ключ шардирования выбирают по доминирующему запросу. Для сообщений это «дай беседу», поэтому шардируем по `conversation_id`: вся беседа на одном шарде, чтение и запись бьют в одну node — никаких распределённых джойнов.

**Сообщения — шард по `conversation_id`:**
- Все сообщения одной беседы → 1 partition
- Чтения и записи идут в одну node
- **Подводный камень:** горячая беседа = горячий шард. В обычном чате редкость, но канал знаменитости может перегрузить один шард

**Пользователи и группы — шард по `user_id`.**

**Масштабирование** (Cassandra делает это «из коробки»):
- Token ring перераспределяет данные при добавлении нод
- Virtual nodes сглаживают неравномерность

**Кросс-шардовые запросы** (например, поиск по всем чатам пользователя):
- Fan-out: запрос ко всем релевантным шардам с агрегацией
- Либо заранее посчитанный timeline, чтобы не разлетаться по шардам в рантайме

**Tombstones в Cassandra:**
- Удалённое сообщение помечается tombstone (не стирается сразу)
- Чистка по TTL: например, держим 90 дней, дальше авто-истечение

## Q12. (!) Чем различаются at-most-once, at-least-once и exactly-once и что применяют в чате?

Это три гарантии доставки. Их различие — как система ведёт себя при потере ACK: не повторять (можно потерять сообщение), повторять (можно продублировать) или повторять с дедупликацией (ни потерь, ни дублей). Для чата неприемлемы потери, поэтому базой берут at-least-once и поверх неё убирают дубликаты.

**At-most-once** — отправили и при сбое не повторяем:
- Сообщения могут теряться
- Для чата неприемлемо

**At-least-once** — отправили и повторяем до получения ACK:
- **Возможны дубликаты:** ACK потерялся → клиент повторил, хотя сообщение уже дошло
- Типичная база для чата

**Exactly-once** — каждое сообщение доставляется ровно один раз:
- Достигается идемпотентностью + дедупликацией
- Сложнее, но на практике реализуемо

**Как делают в чате** (at-least-once + дедупликация = фактически exactly-once):
- Доставка идёт **at-least-once**
- Поверх — **идемпотентная обработка** по `message_id`:
  - Клиент генерирует UUID на каждое сообщение
  - Сервер вставляет с `INSERT IF NOT EXISTS` (UUID как ключ идемпотентности)
  - Повторный дубль → no-op, второй копии не появляется

**Итог:** наблюдаемое поведение — exactly-once, без сложной распределённой машинерии.

**End-to-end ACK** (как клиент узнаёт о доставке):
- Клиент → сервер: сообщение с ID
- Сервер сохраняет и отвечает ACK
- Сервер доставляет получателю
- Получатель шлёт ACK → отправитель видит «доставлено»

## Q13. (!) Как устроены отметки о доставке и прочтении (delivery и read receipts)?

Это три статуса жизненного цикла сообщения, которые видит отправитель в виде галочек. Технически каждый статус — отдельное событие, которое получатель отправляет обратно и которое распространяется асинхронно, чтобы не тормозить саму доставку.

**Три события:**
- **Sent** — сообщение дошло до сервера (одна галочка ✓)
- **Delivered** — устройство получателя приняло сообщение (две галочки ✓✓)
- **Read** — получатель открыл чат (синие галочки ✓✓)

**Реализация:**
- На каждое сообщение и каждого получателя — поле статуса
- Обновления статуса возвращаются отправителю

**В группах:**
- Статус хранится на каждого получателя отдельно
- UI отправителя показывает «прочитано N из M»

**Приватность:**
- Read receipts можно отключить, но двусторонне: отключил у себя — не видишь и чужие

**Хранение:**
```
message_status: (message_id, user_id, status, timestamp)
```

**Как распространяются обновления** (чтобы не перегружать систему):
- Асинхронно — не блокируют основную доставку сообщений
- Пакетно — открыл чат, разом прочитал 10 сообщений → одно обновление

**Подводный камень — масштаб:** статусов в разы больше, чем сообщений: сообщения × участники. Группа из 100 человек → 100× записей статуса на каждое сообщение, что становится отдельной нагрузкой на хранилище.

## Q14. Какие гарантии упорядочивания нужны в чате и как их обеспечить?

Достаточно упорядочить сообщения **в рамках одной беседы** — глобальный порядок по всей системе не нужен и был бы запредельно дорогим. Внутри беседы порядок должен быть одинаковым для всех участников, поэтому опираются на серверный timestamp плюс уникальный tiebreaker.

**Упорядочивание внутри беседы:**
- Все участники должны видеть один и тот же порядок
- Сортируем по timestamp + tiebreaker (`message_id` UUID), чтобы развести сообщения с одинаковым временем
- Cassandra `TIMEUUID` удобен: сразу и сортируемый, и уникальный

**Проблема clock skew** — часы на устройствах расходятся:
- Авторитетный timestamp — серверный (момент получения сервером), а не клиентский
- Клиент показывает лишь локальную оценку времени

**Приход не по порядку** (сеть может перемешать сообщения):
- Клиент получил M2 раньше M1
- Клиент пересортировывает по timestamp перед показом

**Глобальное упорядочивание:** не требуется — порядка в рамках беседы достаточно.

**Групповой чат:**
- Партиция по `conversation_id` даёт единую последовательность
- Все участники видят один и тот же порядок

## Q15. (!) Как реализовать online-статус и presence?

Хитрость presence — отслеживать «живость» соединения без явного события «я отключился»: пользователь может просто потерять сеть. Решение — TTL-запись в Redis, которую heartbeat периодически продлевает. Перестали приходить heartbeat → TTL истёк → считаем offline.

**Данные:**
- `user_id → status` (online/away/offline) + `last_seen`

**Хранение — Redis (эфемерно):**
- `SET user:X "online" EX 60`
- TTL 60 с; heartbeat продлевает запись, пока пользователь на связи
- TTL истёк → автоматически считаем offline, отдельного «disconnect» не нужно

**Heartbeat:**
- Клиент шлёт ping каждые 30 с по WebSocket
- Сервер продлевает TTL в Redis

**Уведомления об изменениях** (presence интересен друзьям):
- X стал online/offline → событие в pub/sub
- Подписанные друзья получают апдейт → UI обновляется

**Масштаб:**
- 500M пользователей × несколько байт = несколько GB в Redis
- Шардируется по `user_id`

**Приватность:**
- Статус online можно скрыть
- В WhatsApp — настройка видимости «last seen»

**Статус «away»:**
- Нет активности 5 минут → «away»
- Активность определяет клиент (движение мыши, набор текста)

## Q16. Как сделать индикаторы набора текста (typing indicators)?

Это эфемерные сигналы: их не нужно хранить и не страшно потерять. Поэтому их шлют по самому дешёвому каналу (fire-and-forget pub/sub) и обязательно троттлят, чтобы не слать событие на каждое нажатие клавиши.

**Событие:**
- Пользователь печатает → эфемерное событие участникам беседы
- Не персистится — отбрасывается через несколько секунд

**Реализация:**
- WebSocket-событие `typing`
- Рассылка участникам чата через брокер
- Клиент показывает «John is typing...»
- Таймаут: нет продолжения в течение 5 с → индикатор скрываем

**Ограничение частоты (throttle):**
- Не слать событие на каждое нажатие клавиши
- Максимум одно событие в 3 с

**Брокер:**
- Fire-and-forget (Redis pub/sub)
- Без персистентности — потеря такого события не критична

## Q17. Как спроектировать групповой чат?

Главное отличие от 1:1 — fan-out: одно сообщение нужно доставить десяткам или тысячам получателей. Ключевой выбор — делать fan-out на запись (сразу разослать всем) или на чтение (записать один раз, получатели сами подтянут). Он определяется размером группы.

**Сложности сверх 1:1:**
- 100 получателей → 100-кратный fan-out на каждое сообщение
- Управление списком участников
- Общий порядок сообщений для всех

**Подходы к fan-out:**

**1. Fan-out на запись (write-time):**
- Сервер отправителя публикует во все каналы участников
- Сервер каждого участника пушит сообщение через WS
- Хорошо при < 1000 участников

**2. Fan-out на чтение (read-time, pull):**
- Сообщение записывается один раз (хранилище на уровне группы)
- Получатели подтягивают его при опросе или открытии чата
- Подходит для больших групп (10k+), где push всем был бы слишком дорог

**3. Гибрид** (типичное решение):
- Маленькие группы → push (write-time)
- Большие группы → pull или broadcast-канал

**Как у реальных систем:**
- WhatsApp: маленькие группы (до 256) — сервер делает fan-out; крупнее («broadcast lists») — другая модель
- Slack: канал = topic в брокере, тысячи подписчиков получают fan-out на краю (at edge)

**Членство:**
- Group-сервис управляет добавлением/удалением
- Список участников кэшируется, чтобы не дёргать БД на каждое сообщение

## Q18. Как доставлять push-уведомления offline-пользователям?

Когда получатель offline, WS-канала нет — единственный способ дотянуться до закрытого приложения это системные провайдеры APNs (iOS) и FCM (Android). Сервер не шлёт само сообщение в push, а лишь будит устройство; реальные сообщения приложение забирает по WS после открытия.

**Поток:**
1. Сообщение сохранено в хранилище
2. Запрос presence показывает: получатель offline
3. Notification-сервис → APNs (iOS) / FCM (Android)
4. Провайдер доставляет уведомление на устройство
5. Устройство просыпается и показывает уведомление
6. Пользователь открывает приложение → подключается WebSocket → забирает накопленные сообщения

**Как работают APNs / FCM:**
- Приложение регистрирует device-токен в push-сервисе
- Токен хранится на каждое устройство пользователя
- Сервер шлёт POST в APNs/FCM с токеном + payload

**Дедупликация** (нужна из-за гонки):
- Пользователь переподключился до прихода push → получит и push, и WS-сообщение
- Клиент дедуплицирует по `message_id`

**Содержимое уведомления:**
- Имя отправителя + превью текста
- Приватность: показ превью на lock screen в iOS можно отключить

**Silent push:**
- Фоновое уведомление iOS без баннера
- Ненадолго будит приложение, чтобы подгрузить данные заранее

**Подводный камень — лимиты частоты:**
- APNs/FCM троттлят пуши по приложению
- Поэтому консолидируют: один push «5 новых сообщений» вместо пяти отдельных

## Q19. (!) Как работает сквозное шифрование (end-to-end encryption)?

E2E означает, что прочитать сообщение могут только отправитель и получатель — **сервер видит лишь ciphertext** и не способен расшифровать. Этим оно отличается от шифрования «на сервере», где провайдер технически может прочитать переписку. Стандарт де-факто — Signal Protocol.

**Signal Protocol** (WhatsApp, Signal, опционально Messenger).

**Ключевые понятия:**
- У каждого пользователя долговременный identity key + набор эфемерных ключей
- Каждое сообщение шифруется отдельным **посессионным** ключом
- **Forward secrecy:** ключ ротируется на каждое сообщение, поэтому прошлая переписка остаётся защищённой, даже если текущий ключ скомпрометируют
- **Deniability:** нельзя криптографически доказать, кто отправил сообщение (нет подписи долговременным ключом)

**Поток установки сессии:**
1. Пользователь A при регистрации загружает на сервер публичные ключи (identity + pre-keys)
2. A хочет написать B → забирает публичные ключи B с сервера
3. A выполняет согласование ключей X3DH → получаются сессионные ключи
4. Сообщения шифруются AES-GCM и аутентифицируются
5. Сервер видит только ciphertext, ключей у него нет

**Групповое E2E:**
- Протокол «Sender Keys»: у каждого отправителя свой симметричный ключ, зашифрованный попарно для участников
- При изменении состава группы — rekey

**Компромиссы** (за приватность платят функционалом):
- **Сервер не может** искать по content, считать аналитику по тексту, бэкапить сообщения в открытом виде
- **Бэкап делается на стороне клиента** — зашифрованный blob, ключ держит пользователь
- **Метаданные всё равно видны:** кто кому пишет, когда и какого размера сообщение

**Как у разных систем:**
- **WhatsApp** — E2E по умолчанию с 2016 года
- **Telegram** — E2E только в «секретных чатах»; обычные чаты шифруются на сервере, но провайдер их читает
- **Signal** — всё E2E

## Q20. Как обрабатывать медиа — изображения и видео?

Медиа слишком велики, чтобы гнать их по WS как обычные сообщения: они забили бы пропускную способность чат-серверов. Поэтому файл идёт мимо чат-яруса — напрямую в объектное хранилище (S3) по presigned URL, а в сообщении передаётся только ссылка.

**Не передаётся inline** — слишком большой объём.

**Поток загрузки:**
1. Клиент запрашивает у сервера presigned S3 URL
2. Клиент загружает файл напрямую в S3 (минуя чат-серверы)
3. Клиент шлёт сообщение со ссылкой: `{type: "image", url: "s3://..."}`
4. Получатель скачивает напрямую из S3 (или через CDN перед ним)

**Почему так:**
- Нет проксирования через чат-серверы — они не забивают пропускную способность
- Кэш CDN ускоряет повторные скачивания
- Загрузки и скачивания идут параллельно с перепиской

**Превью (thumbnails):**
- Генерируются на сервере (Lambda, ffmpeg)
- В нескольких размерах (thumb, medium, full)

**Сложность с E2E-шифрованием:**
- Файл шифруется на клиенте перед загрузкой
- Получатель скачивает зашифрованный blob и расшифровывает локально
- CDN кэширует ciphertext — инспектировать содержимое бесполезно

**Видеостриминг:**
- Обычно не как сообщения чата — выносится в отдельный сервис

**Хранение (retention):**
- S3 lifecycle policies автоматически удаляют файлы через N лет

## Q21. Как реализовать поиск по истории сообщений?

Главный фактор — есть ли E2E-шифрование. Без него сервер видит текст и строит полнотекстовый индекс (Elasticsearch). С E2E сервер видит только ciphertext, поэтому поиск приходится делать на клиенте — это фундаментальный компромисс между приватностью и удобством серверного поиска.

**1. Поиск на клиенте** (для E2E-систем):
- Скачиваем сообщения и индексируем локально (SQLite FTS)
- Подходит для небольшой и средней истории
- Медленно для очень длинной истории

**2. На стороне сервера** (системы без E2E):
- Индекс в Elasticsearch
- Шарды на каждого пользователя
- Обновляется в реальном времени из потока сообщений

**3. E2E + зашифрованный поиск:**
- Клиент генерирует зашифрованные поисковые токены, сервер ищет по ним, не видя текста
- Требует сложной криптографии; в Signal полностью не реализовано

**Как у реальных систем:**
- **Slack / Messenger** (по умолчанию не E2E): полнотекстовый поиск через Elasticsearch, шарды по каналам пользователя
- **WhatsApp** (E2E): поиск только на клиенте; функция «Chat backup» кладёт зашифрованный blob в iCloud/Drive, искать можно после скачивания
