# Вопросы на собеседовании: Генератор уникальных ID

В задаче о генераторе ID сначала уточняют область уникальности, допустимый порядок, формат и поведение при отказе. Короткий код URL — отдельная задача представления ID; этот файл посвящён самому выделению идентификаторов.

## Q1. Какие требования определить до выбора генератора ID?

**Уникальность** может требоваться внутри одной таблицы, между шардами, регионами или несколькими независимыми сервисами. Затем уточните: нужен ли строгий порядок создания или достаточно приблизительной сортировки по времени; должен ли ID помещаться в 64 бита; можно ли ждать координатора; допустимы ли пропуски; разрешено ли раскрывать время и скорость создания объектов.

| Требование | Обычно подходящий кандидат | Важная граница |
|---|---|---|
| Один источник записи и ключ таблицы | `IDENTITY`/sequence БД | Порядок выдачи не равен порядку commit; бывают пропуски. |
| Независимая генерация на многих узлах | UUIDv4/v7 | Вероятность коллизии мала, но математической гарантии без общей проверки нет. |
| Компактный числовой ID с приблизительным временем | Snowflake-подобная схема | Нужны уникальные worker ID и политика при сбое часов. |
| Централизованное выделение чисел для шардов | Ticket server или выдача диапазонов | Состояние координатора и failover входят в дизайн. |

Это **маршрут выбора**, а не универсальный рейтинг: сначала определите контракт и лишь затем считайте нагрузку и цену координации. ID не должен служить секретом доступа. У time-based схем может раскрыться время создания; для публичного непредсказуемого токена нужна отдельная модель угроз. [RFC 9562, разделы 6.8–6.9](https://datatracker.ietf.org/doc/html/rfc9562#section-6.8), [Flickr ticket servers](https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/).

## Q2. Когда достаточно sequence или ticket server и что происходит при отказе?

Если запись уже идёт через одну БД, её sequence часто проще отдельного сервиса. В PostgreSQL `nextval` атомарно выдаёт разные значения конкурентным сессиям. Выданное значение **не откатывается** вместе с транзакцией, поэтому rollback, конфликт вставки или кэш sequence оставляют дыры. Нельзя обещать «без пропусков» или восстановить порядок commit по ID. При `CACHE > 1` разные сессии могут вернуть значения не в глобальном порядке вызовов. Для пространства внешних ID используйте `NO CYCLE` и не сдвигайте счётчик назад через `setval` или `RESTART`: циклический переход или сброс назад могут повторно выдать уже использованный номер. Исчерпание диапазона обрабатывайте как отдельную ошибку.

При нескольких независимых БД нужен общий контракт пространства ID. Ticket server может выделять номера отдельными запросами; Flickr использовал два сервера, разделив пространство на чётные и нечётные значения. Альтернатива для высоких нагрузок — выдать узлу непересекающийся **диапазон**, а затем считать локально. Это уменьшает координацию на каждый ID, но при падении узла остаток диапазона теряется; повторно выдавать его без доказательства прекращения старого владельца опасно.

Для отказоустойчивости определите, кто хранит следующий свободный диапазон, как восстанавливается состояние после failover, как исключается двойная выдача и что делает клиент при недоступности координатора. Если ID уходит за пределы БД, завершите транзакцию с `nextval` до внешней публикации номера: PostgreSQL предупреждает, что после аварии состояние sequence из незавершённой транзакции может восстановиться как прежнее. `UNLOGGED` sequence здесь не подходит: после аварийного рестарта она сбрасывается в начальное состояние и не реплицируется на standby. [PostgreSQL `nextval`](https://www.postgresql.org/docs/18/functions-sequence.html), [`CREATE SEQUENCE`/`UNLOGGED`/`CACHE`](https://www.postgresql.org/docs/18/sql-createsequence.html), [Flickr ticket servers](https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/).

## Q3. Какие сбои должен обрабатывать генератор Snowflake-подобных ID?

Одна распространённая 64-битная схема соединяет timestamp, worker ID и счётчик внутри одного миллисекундного интервала. Например, разбиение `41 + 10 + 12` бит даёт **4 096 значений на миллисекунду на один worker** и до 1 024 значений worker ID. Это предел пространства комбинаций, **не измеренная производительность сервиса**. Сначала узлу назначают уникальный worker ID; при нормальной работе каждый ID затем создаётся локально.

```text
[ timestamp | worker ID | sequence within timestamp ]
```

Обработайте три отказа:

1. **Часы пошли назад.** Простое повторное использование прежних `(timestamp, worker, sequence)` может дать дубликаты. Безопасная политика — временно остановить выдачу, вернуть ошибку или использовать явно спроектированное логическое время и сохранённое состояние. NTP уменьшает дрейф, но не заменяет политику.
2. **Счётчик исчерпан в той же миллисекунде.** Дождитесь следующего допустимого времени или откажите; незаметный wrap повторил бы ID.
3. **Worker ID выдан двум живым узлам.** Оба могут сгенерировать одинаковую комбинацию. Назначение и повторное использование worker ID требуют координации, lease/fencing или другого доказательства единственного активного владельца.

Timestamp первым делает ID **приблизительно упорядоченными**, но не доказывает строгий глобальный порядок событий или commit между узлами. Для такой гарантии нужен отдельный сериализующий механизм. [Исходное объяснение Twitter](https://blog.x.com/engineering/en_us/a/2010/announcing-snowflake), [пример битовой схемы](https://github.com/bwmarrin/snowflake).

## Q4. Как сравнить UUIDv4, UUIDv7 и Snowflake для ключа сущности?

UUIDv4 использует случайные биты и не требует координации узлов; вероятность коллизии при качественном генераторе мала, но не равна нулю. UUIDv7 содержит миллисекундный timestamp в старших 48 битах; реализация может дополнительно использовать долю миллисекунды и счётчик вместе со случайными данными. Это улучшает временную локальность ключей относительно случайного UUIDv4, но **не гарантирует строгий порядок всех событий**: в пределах миллисекунды и между узлами порядок зависит от реализации, часов и политики генератора.

Snowflake-подобный ID компактнее (обычно 64 бита против 128 у UUID) и даёт приблизительный временной порядок, но вводит управление worker ID и защиту от clock rollback. UUIDv7 не требует выделять worker ID в варианте с достаточной случайностью, однако хранение 128-битного ключа и выбранное текстовое представление следует учитывать в API и индексах. Не обещайте, что одна схема всегда быстрее другой: измеряйте конкретную БД, тип индекса и характер вставок.

Если ключ создаёт PostgreSQL, с версии 18 есть встроенные `uuidv7()` и `uuidv4()`; `gen_random_uuid()` также создаёт v4. В более ранней версии нужно проверить доступные функции или генерировать v7 в приложении. Наличие `uuidv7()` снимает необходимость отдельного генератора для этого сценария, но не превращает временную сортировку ID в порядок commit. [PostgreSQL 18 UUID functions](https://www.postgresql.org/docs/18/functions-uuid.html), [release notes](https://www.postgresql.org/docs/18/release-18.html).

**Граница гарантии:** уникальный индекс БД остаётся последним контролем дубликатов на записи, если цена коллизии высока. Ни время в UUIDv7, ни предсказуемый счётчик в Snowflake не заменяют авторизацию или случайный токен доступа. [RFC 9562: UUIDv4/v7](https://datatracker.ietf.org/doc/html/rfc9562#section-5.7), [порядок и коллизии](https://datatracker.ietf.org/doc/html/rfc9562#section-6.2).
