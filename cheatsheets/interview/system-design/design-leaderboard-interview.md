## Q1. Как быстро получить top-N и место отдельного игрока?

Для рейтинга, который помещается на один Redis-узел, храните один Sorted Set `leaderboard:<season_id>:<scope>`: `member = player_id`, `score = очки`. `ZADD` меняет score существующего игрока; в Redis 6.2+ `ZRANGE key 0 9 REV WITHSCORES` возвращает десятку лучших, `ZREVRANK key player_id` — позицию с нуля при сортировке по убыванию. Получить публичное место с единицы можно прибавлением 1. Для одного участника `ZADD` и `ZREVRANK` стоят порядка `O(log N)`, индексный `ZRANGE` — `O(log N + M)` для `M` возвращённых игроков. Эти свойства уже частично изложены в [Redis Q11](../databases/redis-interview.md#q11-очки-в-лидерборде-обновляются-верно-но-размер-структуры-застыл-на-числе-игроков-и-не-растёт-с-каждой-новой-отправкой-очков-почему). [Redis Sorted Sets](https://redis.io/docs/latest/develop/data-types/sorted-sets/), [ZRANGE](https://redis.io/docs/latest/commands/zrange/), [ZREVRANK](https://redis.io/docs/latest/commands/zrevrank/).

Уточните требования: глобальный или региональный рейтинг, частота обновлений, допустимая задержка отображения, срок хранения и правило для забаненных игроков. Score в Redis может быть **проекцией**, а авторитетный результат матча и история начисления — в устойчивом хранилище. Redis Cluster использует асинхронную репликацию, поэтому нельзя обещать отсутствие потери подтверждённого изменения при любом failover только за счёт него. Для страницы «вокруг меня» возьмите текущий rank и небольшой индексный диапазон; при частых изменениях между запросами страницы возможны сдвиги, поэтому снимок/версию сезона оговорите отдельно. [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).

## Q2. Что означает место при равных очках?

`ZREVRANK` возвращает **уникальный порядковый индекс**. При одинаковом score Redis упорядочивает участников лексикографически по строке member (в обратном направлении для убывающего списка). Это детерминированный технический порядок, но он не означает, что игрок с тем же количеством очков «лучше». Например, при 100, 90, 90 очках индексы будут 0, 1, 2; спортивный **competition rank** был бы 1, 2, 2, а следующий — 4. [Redis Sorted Sets](https://redis.io/docs/latest/develop/data-types/sorted-sets/), [ZREVRANK](https://redis.io/docs/latest/commands/zrevrank/).

Определите бизнес-правило до выбора структуры: делят ли участники место; побеждает ли тот, кто раньше достиг результата; какой порядок нужен при равных очках и как выдаются награды. Для общего места `1 + число игроков с большим score` можно считать через `ZCOUNT key (score +inf` (нижняя граница исключает равный score); для плотного ранга `1, 2, 2, 3` понадобится число **различных** больших score, чего один `ZREVRANK` не даёт. Если нужен tie-break по времени, отдельно храните надёжное время достижения score и поддерживайте согласованный индекс/проекцию; простое добавление времени к floating-point score без проверки диапазона и точности может изменить порядок. [ZCOUNT](https://redis.io/docs/latest/commands/zcount/).

## Q3. Как принимать повторы и запоздавшие результаты матчей?

Сначала решите, событие несёт **абсолютный итог** или **дельту**. Повтор `ZINCRBY` для одной и той же дельты прибавит очки дважды; `ZADD` с абсолютным score идемпотентен по значению, но старое событие может затереть более новый итог. Сохраняйте `match_id`/`event_id`, версию расчёта и авторитетный результат в долговечном журнале; проекцию рейтинга обновляйте только после проверки уникальности события и порядка версий для `(season, player)`. Повтор должен возвращать уже учтённый итог. Для корректировок после отмены матча публикуйте новое корректирующее событие или пересчитывайте абсолютный результат из авторитетных данных.

Если рейтинг строится из потока, определите время события, допустимое опоздание и момент окончательной фиксации наград. Watermark помогает оценить, до какого event time поток обычно обработан, но не гарантирует, что позже не придёт событие. Для живого рейтинга можно применить позднюю коррекцию и обозначить статус `provisional`; для закрытой призовой таблицы нужен явный deadline, политика ручной корректировки и аудит. Подробная теория watermarks и allowed lateness есть в [stream processing Q5–Q10](../data-engineering/stream-processing-interview.md). [Flink watermarks](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/event-time/generating_watermarks/), [Redis ZADD](https://redis.io/docs/latest/commands/zadd/).

## Q4. Как закрыть сезон без потери старых результатов?

Включайте **season_id в ключ и каждое событие**. Переход на следующий сезон меняет указатель активного сезона в авторитетной конфигурации и направляет новые результаты в новый ключ. Старый рейтинг остаётся доступен для аудита и выдачи наград; снимок победителей формируется после согласованного deadline и сверки с журналом результатов. Не очищайте старый ключ командой массового удаления в момент переключения: это разрушит воспроизводимость и может блокировать узел.

Событие прошлого сезона, пришедшее после переключения, направляют в **его** сезон и применяют по политике поздних корректировок; нельзя автоматически прибавить его к новому сезону. Клиенту и API возвращайте `season_id` вместе с местом, иначе соседние запросы во время переключения могут показать top-N старого сезона и личный rank нового. Если результаты являются призовыми или юридически значимыми, храните неизменяемую итоговую ведомость отдельно от оперативного Redis Sorted Set. Это проектное решение, а не встроенный контракт Redis.

## Q5. Что меняется при шардировании глобального рейтинга?

Один Sorted Set — **один ключ**, а Redis Cluster размещает ключ в одном hash slot. Добавление узлов не распараллелит запись в этот конкретный ключ. Разделение по региону или группе игроков увеличивает ёмкость и пропускную способность, но `ZREVRANK` внутри шарда больше не равен глобальному месту. [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).

Если порядок строго полный (score плюс оговорённый tie-break), точный глобальный top-K можно собрать из top-K **каждого** шарда и затем слить: игрок вне локального top-K не может попасть в глобальный top-K. Точный ранг одного игрока требует посчитать на каждом шарде участников выше него по тому же правилу и сложить результаты; это уже fan-out и цена растёт с числом шардов. Для игры с умеренным числом участников проще оставить один лидерборд; для большой аудитории выбирайте региональные таблицы, периодическую глобальную проекцию или приблизительный ранг, если SLA допускает погрешность. Границу свежести и статус `provisional` показывайте явно; кэшированный top-K и немедленный точный rank могут отражать разные моменты времени.
