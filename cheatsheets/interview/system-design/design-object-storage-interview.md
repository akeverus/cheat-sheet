## Q1. Какой контракт дать PUT, GET, LIST и перезаписи ключа?

Сначала определите **область атомарности и согласованности**. В S3 после успешного `PUT` новый или перезаписанный объект виден последующим `GET` и `LIST`; `DELETE` тоже имеет сильную согласованность. Конкурентный `GET` при замене одного ключа видит старые **или** новые байты, но не их смесь. Это контракт **Amazon S3 для одного ключа**, а не обещание общей транзакции на несколько ключей или всех S3-совместимых продуктов. В собственной реализации публикация нового указателя на готовые байты должна быть атомарной. [S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

**Чтение по диапазонам.** При скачивании большого объекта параллельными запросами `GET` с `Range` каждый запрос сам выбирает текущую версию, если версия не указана. Если объект перезаписали между запросами, клиент может собрать файл из частей разных версий, хотя каждый ответ по отдельности корректен. В бакете с включённым версионированием зафиксируйте конкретный `versionId` и передавайте его во всех запросах, включая повторы. При чтении текущего объекта без закреплённой версии передавайте исходный ETag в `If-Match` для каждого диапазона. При `412 Precondition Failed` начните сборку заново с заново прочитанными метаданными. Проверяйте `Content-Range`, прежде чем записать ответ по нужному смещению. Amazon S3 принимает один диапазон на запрос `GetObject`. [Amazon S3 — GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html).

**Перечисление по страницам.** В Amazon S3 `ListObjectsV2` возвращает до 1000 результатов на запрос. При `IsTruncated=true` передайте `NextContinuationToken` как `ContinuationToken` следующего запроса. Токен непрозрачен. В бакетах общего назначения ключи идут лексикографически, а для directory buckets этот порядок не гарантируется. `Prefix` ограничивает выборку, а `Delimiter` группирует часть ключей в `CommonPrefixes`. [Amazon S3 — ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html).

Сильная согласованность отдельного `LIST` не даёт документированной гарантии общего снимка на весь многостраничный обход. Например, после чтения первой страницы приложение удаляет уже перечисленный объект и создаёт новый объект в ещё не прочитанной части списка. Последующая страница может содержать новый ключ, хотя удалённый ключ остался в накопленном результате. Если продукт обещает выгрузку строго на один момент времени, предусмотрите явный снимок метаданных или неизменяемый манифест, зафиксированный для всей выгрузки. [Amazon S3 — модель согласованности](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

Простой `PUT` того же ключа может затереть предыдущий объект. Для create-only используйте условие `If-None-Match: *`, а для замены при неизменном **текущем ETag** — `If-Match` с ранее прочитанным значением. Это сравнение ETag, а не `versionId` или общая транзакция; при несовпадении S3 возвращает `412 Precondition Failed`. При конфликтующих запросах возможен `409 Conflict`; для `CompleteMultipartUpload` после `409` требуется заново начать multipart через `CreateMultipartUpload` и загрузить части. При `If-Match` отсутствие текущего объекта, в том числе после конкурентного удаления или при текущем delete marker, даёт `404 Not Found`: перечитайте состояние и решите, допустима ли новая запись. Условие проверяется **при записи**, поэтому отдельный `HEAD → PUT` не защищает от гонки. Для multipart оно ставится на `CompleteMultipartUpload`, когда объект публикуют, а не на отдельный `UploadPart`. [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

Версионирование сохраняет прежние версии под `versionId`; обычный `DELETE` в versioned bucket ставит delete marker, а не стирает все старые байты. `If-None-Match: *` смотрит на текущую версию: при текущем delete marker новая запись разрешена, даже если старые версии ещё существуют. При проектировании своего API отдельно решите, что возвращать на `GET` по ключу после удаления, как читать конкретную версию и как окончательно удалять старые версии. Не обещайте атомарное переименование «папки»: ключи с префиксом не являются файловыми директориями, а набор обновлений ключей не получает транзакцию автоматически. [S3 versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html).

## Q2. Как связать метаданные объекта с записанными байтами?

Разделите **namespace/catalog** и **data plane**. Метаданные по `(bucket, key, version)` хранят размер, checksum, состояние, размещение частей, параметры доступа и ссылку на набор неизменяемых blob/chunk. Сами байты живут на storage-узлах. Сервис метаданных обслуживает `HEAD`, `LIST`, авторизацию и выбор версии; storage-узлы обслуживают поток байтов. Это проектная модель, не утверждение о закрытой внутренней архитектуре Amazon S3.

При загрузке сначала запишите части в промежуточное состояние, проверьте их и требуемую устойчивость, **затем атомарно опубликуйте** версию объекта в метаданных. Так читатель либо видит прежнюю опубликованную версию, либо новую целиком. Если байты записались, а публикация сорвалась, останутся неиспользуемые части: их удаляет уборка после безопасного срока. Если метаданные указывают на байты, которые ещё не стали доступными, успешный `GET` может сломаться; порядок публикации должен исключать это состояние. Удаление версии сначала меняет видимое состояние каталога, а физическую очистку частей выполняют отдельно с учётом ссылок, retention и незавершённых чтений.

**Как уборка соревнуется с публикацией.** Допустим, загрузчик записал части и завис перед публикацией. Уборщик увидел старые части без ссылки из каталога и удалил их. Если загрузчик затем опубликует свой указатель, новый объект будет виден, но прочитать его целиком уже не получится.

В этой модели публикация и захват загрузки уборщиком конкурируют за одну запись в каталоге. Публикация атомарно меняет состояние загрузки с `UPLOADING` на `PUBLISHED` и записывает ссылку из версии объекта. Уборщик может перевести в `ABORTED` только просроченную загрузку в состоянии `UPLOADING` и удаляет её части после фиксации перехода. Если первым прошёл abort, позднее завершение отклоняется. Для новой попытки выделяют новый ID. Если часть ещё записывалась во время abort, её учитывают при повторной уборке. В этом примере промежуточные части принадлежат одной загрузке. При дедупликации дополнительно нужно защитить части, которые используют другие версии. Похожий риск есть при удалении файлов, которые ещё не попали в метаданные таблицы. [Apache Iceberg — очистка файлов без ссылок](https://iceberg.apache.org/docs/latest/maintenance/#delete-orphan-files).

**Как удаление соревнуется с чтением.** Допустим, `GET` разрешил ключ в версию V и начал передавать её части. Если конкурентный `DELETE` скроет V в каталоге и сразу освободит её части, поток может оборваться на середине. В этом дизайне каталог выбирает версию и регистрирует временное право чтения одной атомарной операцией. После удаления версии новые чтения по удалённой записи больше не получают это право, а уже начатое чтение может завершиться. Уборка освобождает части, когда истекли сроки хранения, исчезли ссылки других версий и больше нет действующих прав чтения. При использовании аренды продлевайте её до истечения на протяжении передачи. Если продление не удалось, остановите чтение до истечения аренды. Так сбой клиента не удерживает данные бессрочно.

Для масштабирования нужно продумать распределение ключей, горячие префиксы, кэш метаданных и постраничный `LIST`. При этом инвалидация кэша обязана сохранять обещанную видимость после успешного `PUT`. Дизайн этого слоя похож на разделение в [Dropbox Q6](design-dropbox-interview.md#q6-зачем-разделять-metadata-и-blob-postgres--magic-pocket), но здесь он обслуживает bucket/key API и версии вместо пользовательского дерева файлов.

## Q3. Как завершать multipart upload и проверять целостность?

Большой объект загружают как **инициализация → части → завершение**. Инициирование выдаёт `uploadId`; `UploadPart` принимает пронумерованные части, которые можно передавать параллельно и повторять; `CompleteMultipartUpload` получает список частей и делает собранный объект доступным. Незавершённые части занимают место, поэтому клиент или правило очистки должны вызвать `AbortMultipartUpload` для брошенной загрузки. Условие create-only/compare-and-swap для итогового ключа проверяется при `Complete`, когда возможна гонка с другой записью. [S3 multipart](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), [conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

**Конфликт при условном завершении.** В Amazon S3 ответ `412 Precondition Failed` означает, что условие публикации не выполнено. Например, если другой клиент перезаписал ключ, завершение с прежним `If-Match` отклоняется. Приложение решает, допустима ли запись поверх новой версии. Если S3 вернул `409 ConditionalRequestConflict` на условный `CompleteMultipartUpload`, для новой попытки создайте новый `uploadId` и загружайте все части заново. При `If-Match` сначала получите текущий ETag и проверьте, относится ли он к версии, которую действительно можно заменить. [CompleteMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).

**Повтор загрузки части.** В одном `uploadId` новый успешный `UploadPart` с тем же номером заменяет ранее загруженную часть. Например, один воркер загрузил часть 7 и записал её ETag, затем другой воркер ошибочно записал под номером 7 другие байты с новым ETag. Завершение со старым ETag получит `InvalidPart`. Привяжите номер части к одному диапазону исходных байтов, повторяйте загрузку с тем же содержимым и дождитесь завершения запросов перед фиксацией списка частей. Для `CompleteMultipartUpload` передайте свой список номеров и подтверждённых ETag по возрастанию номера. `ListParts` используйте для сверки загруженного с ожидаемым набором. [S3 multipart upload](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), [CompleteMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).

В S3 запросы `UploadPart`, которые уже выполнялись в момент `AbortMultipartUpload`, могут завершиться успешно. Для управляемой отмены остановите отправку новых частей и дождитесь окончания начатых запросов, затем вызовите abort. Если abort уже отправили на фоне активных загрузок, проверьте через `ListParts`, что частей не осталось, и при необходимости повторите abort. [AbortMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_AbortMultipartUpload.html).

Проверяйте checksum при приёме частей и итоговую контрольную сумму по документированному алгоритму. **ETag не является универсальным MD5 всего объекта**: для multipart и некоторых вариантов шифрования это особенно неверно. В S3 можно передать поддерживаемую full-object или составную checksum; при несовпадении предоставленной полной checksum завершение не сохраняет объект. Чтобы гарантировать проверку, задавайте алгоритм и тип checksum (`FULL_OBJECT` или `COMPOSITE`) при `CreateMultipartUpload`: не каждый алгоритм допускает оба типа. Для некоторых алгоритмов checksum, впервые переданная лишь в `CompleteMultipartUpload`, может быть принята **без проверки и сохранения**. Сохраняйте алгоритм и тип вместе со значением, иначе последующая проверка будет двусмысленной. [S3 integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html).

При прямом вызове S3 REST проверяйте **тело ответа** `CompleteMultipartUpload`: сервис может сначала отправить HTTP `200 OK`, а затем вернуть XML-ошибку в этом же ответе. AWS SDK распознаёт такую ошибку. После потери ответа сверяйте состояние объекта/версии с ожидаемым результатом: ошибка сети не доказывает, что публикация не состоялась. [CompleteMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).

В собственной реализации части можно размещать на разных узлах, но объект публикуется только после проверки полного упорядоченного набора; частично загруженный объект нельзя выдавать обычным `GET`.

## Q4. Как пережить потерю диска или узла без повреждения объекта?

Выберите **домен отказа** (диск, узел, стойка, зона) и размещайте копии или erasure-coded фрагменты в разных доменах. Три копии просты для чтения и ремонта, но требуют примерно втрое больше места под байты. Код `k+m` хранит `k` частей данных и `m` избыточных частей: при подходящей схеме восстанавливает объект при потере до `m` частей, платя за вычисление и чтение других частей при ремонте. Числа и устойчивость зависят от политики размещения и размера кластера; хранение всех частей на одной стойке не защищает от потери стойки. Ceph CRUSH — пример политики по host/rack, а не описание внутренностей S3. [Ceph CRUSH](https://docs.ceph.com/en/squid/rados/operations/crush-map/), [Ceph erasure code](https://docs.ceph.com/en/squid/rados/operations/erasure-code/).

После отказа обнаружьте недостающую копию/фрагмент, восстановите его из оставшихся и переразместите без нарушения выбранного домена отказа. Проверка checksum при чтении и фоновый deep scrub помогают обнаружить тихое повреждение. Обнаружение зависит от того, когда соответствующие данные прочитают или проверят. Держите отдельные метрики по недореплицированным объектам, очереди ремонта и времени восстановления. Метаданные, индексы размещения и ключи шифрования требуют собственного резервирования: целые байты бесполезны, если потерян путь к ним. Межрегиональная репликация — отдельная политика с собственной задержкой и правилами конфликта; локальная erasure coding не равна защите от потери региона.

**Сценарий.** Из трёх реплик на разных узлах одна недоступна. Если оставшихся реплик, состояния группы и настроек пула хватает для обслуживания запроса, чтение продолжается в деградированном режиме. Система восстанавливает третью реплику из актуальной копии на подходящем узле. Если для нового размещения не хватает места, избыточность остаётся сниженной. Поэтому доступность чтения и завершение ремонта отслеживают отдельно. В Ceph это разные состояния, например `PG_AVAILABILITY`, `PG_DEGRADED` и `PG_BACKFILL_FULL`. [Ceph Squid — проверки состояния данных](https://docs.ceph.com/en/squid/rados/operations/health-checks/#data-health-pools-placement-groups).

**Отказ региона.** Допустим, клиент получил успешный `PUT`, но регион отказал до копирования новой версии. При переключении на резервный bucket клиент может увидеть прежнюю версию или не найти ключ. Amazon S3 Cross-Region Replication работает асинхронно. Для объектов, которые уже лежали в bucket при настройке live replication, нужен отдельный перенос, например S3 Batch Replication. При современной конфигурации с `Filter` пользовательские delete markers по умолчанию остаются в исходном bucket. Поэтому при переключении ранее удалённый ключ может снова стать видимым. Удаление конкретной версии по `versionId` также не удаляет её реплику. Учитывайте эти различия в плане восстановления и проверяйте готовность резервного bucket по статусам и метрикам репликации. [S3 Cross-Region Replication](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication.html), [Правила репликации удалений](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-what-is-isnot-replicated.html).
