# Вопросы на собеседовании: `mTLS (Mutual TLS)`

`mTLS (Mutual TLS)` — TLS handshake, где **обе стороны** проверяют identity друг друга (в отличие от обычного TLS, где проверяется только сервер). Фундамент для **Zero Trust**-сетей. Применяется в микросервисах (service mesh), B2B API, IoT, банковской сфере. Требует PKI-инфраструктуры для управления сертификатами.

## Q1. (!) Что такое mTLS?

**mTLS (Mutual TLS)** — это TLS handshake, в котором **обе стороны** предъявляют сертификаты и проверяют друг друга, а не только клиент проверяет сервер. Отсюда «mutual» — взаимная аутентификация.

Разница с обычным TLS — в том, кто кого аутентифицирует:

- **Обычный TLS:** сертификат предъявляет только **сервер**, клиент его проверяет. Сам клиент остаётся для сервера анонимным (или аутентифицируется отдельно — паролем, токеном).
- **mTLS:** сертификаты предъявляют **и** сервер, **и** клиент, и **обе** стороны валидируют чужой сертификат по цепочке доверия.

**Зачем это нужно.** В mTLS сервер криптографически **знает**, какой именно клиент к нему подключился. Это надёжнее, чем доверие по IP-адресу (его подделывают) или по учётным данным (их крадут): подделать чужой сертификат без приватного ключа невозможно.

## Q2. (!) Чем mTLS отличается от обычного TLS?

Ключевое отличие одно: **mTLS добавляет аутентификацию клиента по сертификату**. Всё остальное (шифрование, проверка сервера) — то же самое. Но это одно отличие тянет за собой рост сложности: сертификаты нужно выпускать, раздавать и ротировать уже **на обеих** сторонах, а значит — нужен полноценный PKI.

| Аспект | TLS | mTLS |
|--------|-----|------|
| Аутентификация сервера | ✓ | ✓ |
| Аутентификация клиента | ❌ (или другой механизм) | ✓ (через сертификат) |
| Шифрование | ✓ | ✓ |
| Сценарий | Публичный веб | Service-to-service, B2B |
| Управление сертификатами | Только сертификат сервера | Обе стороны |
| Сложность | Низкая | Высокая |
| Нужен PKI | Для CA | Полноценный PKI |

**Пример на пальцах:**
- **TLS:** браузер подключается к `bank.com`. Сертификат есть только у банка, у браузера его нет — банк не знает, кто именно зашёл.
- **mTLS:** `bank-A.com` подключается к `bank-B.com`. Сертификаты есть у обоих, поэтому каждая сторона уверена, с кем разговаривает.

## Q3. (!) Зачем нужен mTLS?

Коротко: mTLS даёт **сильную взаимную аутентификацию без общих секретов**. Каждая сторона доказывает, кто она, владением приватным ключом, а не паролем или API-ключом, который можно украсть или забыть отозвать.

**Что это даёт на практике:**
- **Сильная аутентификация** — криптографическая, а не по паролям, которые подбирают и фишат.
- **Нет общих секретов**, которые можно утечь, — нет API-ключей в конфигах и логах.
- **Подтверждённая identity сервиса** — вы точно знаете, какой сервис на том конце.
- **Шифрование трафика** «в нагрузку» — оно встроено в TLS.
- **Аудит-след** — identity из сертификата попадает в логи, видно кто и куда ходил.

**Где применяют:**
1. **Service-to-service** в микросервисах (Zero Trust).
2. **B2B API** — дорогие партнёрские интеграции.
3. **IoT-устройства** — аутентификация самих устройств.
4. **Внутренние admin-инструменты** — дополнительный слой защиты.
5. **Банки, финансы** — регуляторный комплаенс.
6. **Здравоохранение** — HIPAA.
7. **Госсектор** — требования комплаенса.

## Q4. (!) Как проходит mTLS handshake?

mTLS handshake — это обычный TLS handshake плюс два шага, которыми сервер требует и проверяет сертификат клиента:

```
1. Client → Server: ClientHello (supported ciphers)
2. Server → Client: ServerHello + certificate + CertificateRequest
3. Client → Server: certificate + ClientKeyExchange + CertificateVerify
4. Both: derive session keys
5. Encrypted communication
```

**Что добавилось по сравнению с TLS** (шаги 2–3):
- **CertificateRequest** — сервер явно просит клиента предъявить сертификат.
- **CertificateVerify** — клиент подписывает handshake своим приватным ключом. Это и есть доказательство владения сертификатом: предъявить чужой публичный сертификат мало, нужно подтвердить, что у тебя есть к нему приватный ключ.

После этого **оба сертификата проверяются** по цепочке CA, и стороны выводят общие сессионные ключи.

**Нюанс версии.** В TLS 1.3 handshake короче — 1-RTT против 2-RTT в TLS 1.2, поэтому даже с дополнительными шагами mTLS overhead на установку соединения ниже.

## Q5. Что такое сертификаты X.509?

**X.509** — стандартный формат сертификатов с открытым ключом, на котором стоит весь TLS/mTLS. По сути сертификат — это публичный ключ плюс метаданные о владельце, всё вместе подписанное доверенным CA.

**Что лежит внутри:**
- **Subject** — кому принадлежит сертификат.
- **Issuer** — кто его подписал (CA).
- **Public key** — открытый ключ владельца.
- **Serial number** — серийный номер (нужен для отзыва).
- **Срок действия** — `notBefore` / `notAfter`.
- **Расширения** — `SAN` (Subject Alternative Names — список имён/доменов), `key usage` и т.д.
- **Подпись** — подпись CA, которая связывает всё перечисленное вместе.

**Формат хранения:** PEM (base64-текст с заголовками `BEGIN/END`) или DER (бинарный).

```
-----BEGIN CERTIFICATE-----
MIIDXTCCAkWgAwIBAgIJAK...
-----END CERTIFICATE-----
```

**Как проверяют.** Берут публичный ключ CA и валидируют им подпись сертификата: если подпись сходится, значит содержимое не подменено и CA действительно его выпустил.

## Q6. Как устроена иерархия удостоверяющих центров (CA)?

CA выстроены в **дерево доверия**: один Root наверху, под ним промежуточные CA, а уже они выпускают конечные сертификаты сервисов. Конечные сертификаты подписывает не сам Root, а Intermediate — это сделано ради безопасности.

```
Root CA (self-signed, trust anchor)
  ├── Intermediate CA 1 (signed by Root)
  │   ├── Server cert 1
  │   └── Server cert 2
  └── Intermediate CA 2
      └── Server cert 3
```

**Root CA** — корень доверия:
- **Точка доверия** (trust anchor), предустановлен в браузерах и ОС.
- **Self-signed** — сам подписывает свой сертификат.
- **Хранится офлайн**: если приватный ключ Root утечёт, придётся переустанавливать доверие на всех клиентах планеты, поэтому его берегут максимально.

**Intermediate CA** — промежуточные:
- Подписаны Root и сами подписывают конечные сертификаты.
- **Упрощают отзыв**: при компрометации отзывают Intermediate, а драгоценный Root остаётся нетронутым.

**Как работает цепочка доверия.** Клиент идёт снизу вверх: проверяет конечный сертификат → смотрит Issuer (Intermediate) и проверяет его подпись → убеждается, что Intermediate подписан Root, которому уже доверяет. Дошли до доверенного корня — значит, всей цепочке можно верить.

## Q7. (!) Что такое PKI (Public Key Infrastructure)?

**PKI** — это вся инфраструктура и процессы вокруг сертификатов: как их выпускать, хранить, продлевать и отзывать. Сами сертификаты бесполезны без PKI, который ими управляет на всём жизненном цикле.

**Из чего состоит:**
- **CA (Certificate Authority)** — выпускает сертификаты.
- **Registration Authority (RA)** — проверяет identity заявителя перед выпуском.
- **Certificate Repository** — хранилище выпущенных сертификатов.
- **Validation Authority (VA)** — отвечает на запросы об отзыве (CRL, OCSP).

**За что PKI отвечает на протяжении жизни сертификата:**
- Выпуск.
- Отзыв скомпрометированных.
- Ротация (продление до истечения срока).
- Аудит и логирование.

**Где взять PKI.** Для mTLS внутри компании обычно поднимают **внутренний PKI** (доверяете своему CA, а не публичным):
- HashiCorp Vault PKI engine
- step-ca (smallstep)
- Microsoft AD CS
- Cloudflare PKI Toolkit
- Самописный — скрипты на OpenSSL

**Публичный PKI** (для сертификатов, которым доверяют браузеры из коробки):
- Let's Encrypt — бесплатно
- DigiCert, Sectigo, GoDaddy — платно

## Q8. Чем self-signed сертификат отличается от CA-signed?

Разница — в том, кто подписал сертификат и кто ему за это доверяет. Self-signed подписывает сам себя, поэтому никто заранее ему не доверяет; CA-signed подписан удостоверяющим центром, которому клиенты уже доверяют.

**Self-signed (самоподписанный):**
- Плюс: бесплатно и быстро.
- Минус: браузеры и клиенты по умолчанию ему не доверяют — доверие приходится настраивать руками.
- **Где годится:** dev, внутренние инструменты, где можно вручную добавить сертификат в доверенные.

**CA-signed (подписанный CA):**
- Плюс: доверие работает автоматически, ничего настраивать не нужно.
- Минус: стоит денег (хотя Let's Encrypt бесплатен).
- **Где обязателен:** публично доступные приложения, куда ходят чужие браузеры.

**Что выбирают для mTLS.** Обычно — **внутренний CA** (собственный PKI). Сервисам не нужно доверие публичных браузеров, им нужно доверять только друг другу, поэтому достаточно, чтобы все они доверяли одному вашему CA.

## Q9. Что такое ротация сертификатов и зачем она нужна?

**Ротация** — это замена сертификата на новый до того, как у старого закончится срок действия. Любой сертификат имеет `notAfter`, после которого становится невалидным, поэтому ротация — не опция, а обязательный процесс.

**Чем плоха ручная ротация:**
- Забыли продлить → сертификат истёк → сервис лёг.
- Серверов много → ротировать приходится по очереди.
- Каждая замена — риск даунтайма из-за человеческой ошибки.

**Поэтому ротацию автоматизируют:**
- **Let's Encrypt + cert-manager** — веб-сертификаты.
- **Vault PKI + sidecar** — сертификаты сервисов.
- **Service mesh** — например, Istio авторотирует каждые 24 ч.

**Рекомендации:**
- **Короткие TTL** — часы и дни, а не годы (чем короче, тем меньше окно компрометации).
- **Авторотация** вместо ручной.
- **Алертинг** на приближение срока истечения — как страховка, если автоматика сломалась.

## Q10. Что такое SPIFFE и SPIRE?

**SPIFFE (Secure Production Identity Framework For Everyone)** — открытый стандарт, который отвечает на вопрос «как сервису безопасно получить свою identity». Он стандартизирует формат identity, а конкретную выдачу делает реализация — **SPIRE**.

**SVID (SPIFFE Verifiable Identity Document)** — носитель identity:
- Это X.509-сертификат, в который зашит SPIFFE ID.
- SPIFFE ID имеет вид `spiffe://trust-domain/path/to/service` — глобально уникальное имя сервиса.

**Пример:**
```
spiffe://example.org/ns/payments/sa/payment-service
```

**SPIRE** — эталонная реализация SPIFFE. Главная фишка — **аттестация workload**: прежде чем выдать SVID, SPIRE проверяет, что запрос идёт от настоящего workload (по K8s ServiceAccount, AWS IAM и т.д.), а не от самозванца. Сервису не нужно хранить заранее розданный секрет — identity «зарабатывается» свойствами самого окружения.

**С чем интегрируется:** Istio, Envoy, Vault, AWS, GCP, K8s.

**Итог:** SPIFFE/SPIRE — де-факто стандарт identity сервисов в Zero Trust-архитектурах.

## Q11. (!) Как работает mTLS в service mesh (Istio, Linkerd)?

Главная ценность service mesh для mTLS — он делает его **автоматическим и прозрачным**: разработчику не нужно ни конфигурировать TLS в коде, ни управлять сертификатами вручную. Всю работу берут на себя sidecar-прокси.

**Istio** — mTLS включается политикой:
```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
spec:
  mtls:
    mode: STRICT  # require mTLS
```

**Linkerd** — mTLS работает автоматически и включён по умолчанию, конфигурировать ничего не нужно.

**Что происходит под капотом:**
- Каждый pod получает сертификат, подписанный CA самого меша.
- TTL короткий (≈24 часа) с авторотацией.
- Identity сервиса берётся из его ServiceAccount.
- Весь TLS обрабатывают sidecar-прокси, а не приложение.

**Почему это прозрачно.** Приложение отправляет обычный незашифрованный HTTP на localhost-sidecar; sidecar заворачивает трафик в mTLS, sidecar на той стороне расшифровывает и отдаёт приложению снова обычный HTTP. Код сервиса о mTLS вообще не знает.

**Итог:** аутентификация service-to-service «из коробки», без единой строки в коде.

Подробнее — [Istio](../devops/istio-service-mesh-interview.md), [Linkerd](../devops/linkerd-interview.md).

## Q12. Что такое cert-manager в Kubernetes?

**cert-manager** — это контроллер Kubernetes, который автоматизирует весь жизненный цикл сертификатов: запрашивает, обновляет и хранит их за вас. Вы описываете желаемый сертификат как объект `Certificate`, а контроллер сам приводит кластер к этому состоянию.

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: example-com
spec:
  secretName: example-com-tls
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  dnsNames:
    - example.com
    - www.example.com
```

**Issuer** — это «откуда брать сертификаты». cert-manager умеет работать с разными источниками:
- **Let's Encrypt** — веб-сертификаты, бесплатно.
- **Vault** PKI.
- **Self-signed** — самоподписанные.
- **CA-issued** — выпущенные вашим внутренним CA.
- **Внешние issuer-ы** через плагины.

**Что делает дальше.** Автоматически продлевает сертификат до истечения срока и кладёт его в K8s Secret, откуда его монтируют поды.

**Связь с mTLS.** Интегрируется с Istio: cert-manager может поставлять mesh-у сертификаты для service-to-service mTLS.

## Q13. Как выпускать сертификаты через Vault PKI?

**Vault PKI engine** превращает HashiCorp Vault во внутренний CA: он умеет программно выпускать X.509-сертификаты по запросу. Это удобно, когда нужны короткоживущие сертификаты под mTLS и полная автоматизация без ручной возни с OpenSSL.

```bash
# Setup PKI engine
vault secrets enable pki
vault write pki/root/generate/internal common_name="my-ca" ttl=87600h

# Define role
vault write pki/roles/my-role \
  allowed_domains=example.com \
  allow_subdomains=true \
  max_ttl=24h

# Issue cert
vault write pki/issue/my-role \
  common_name=api.example.com \
  ttl=24h
# Returns cert + key
```

Три шага в примере выше: поднимаем PKI-движок и генерируем корневой CA → описываем роль (что и на какой максимальный TTL разрешено выпускать) → по этой роли выпускаем конкретный сертификат, получая обратно и сертификат, и приватный ключ.

**Где применять:**
- Внутренний CA для mTLS.
- Короткоживущие сертификаты (1–24 часа).
- Программный выпуск по API.
- Удобно встраивать в автоматизацию (CI/CD, sidecar-агенты).

Подробнее — [Vault](../devops/vault-interview.md).

## Q14. Как настроить mTLS в Kafka, Redis и базах данных?

Хорошая новость: **почти все системы хранения данных** поддерживают mTLS из коробки. Принцип везде один — указать серверный сертификат с ключом, CA для проверки клиентов и явно включить требование клиентского сертификата. Отличается только синтаксис конфигов.

**Kafka** (ключевая строка — `ssl.client.auth=required`, она и включает mTLS):
```properties
# server.properties
listeners=SSL://:9093
ssl.client.auth=required
ssl.keystore.location=/path/keystore.jks
ssl.truststore.location=/path/truststore.jks
```

**Redis 6+** (`tls-auth-clients yes` требует от клиента сертификат):
```
tls-port 6379
tls-cert-file /path/cert.pem
tls-key-file /path/key.pem
tls-ca-cert-file /path/ca.pem
tls-auth-clients yes
```

**PostgreSQL:**
```conf
ssl = on
ssl_cert_file = '/path/server.crt'
ssl_key_file = '/path/server.key'
ssl_ca_file = '/path/ca.crt'
```

**MongoDB, Elasticsearch, MySQL** — тоже поддерживают mTLS, принцип настройки тот же.

**Зачем это нужно.** mTLS защищает соединения приложения с хранилищами: к базе физически не подключится клиент без валидного сертификата, даже если он знает адрес и пароль. Это закрывает несанкционированный доступ на транспортном уровне.

## Q15. (!) Когда стоит использовать mTLS, а когда нет?

Эмпирическое правило: mTLS хорош там, где **обе стороны контролируете вы** и можете раздать им сертификаты. Как только на одной стороне неуправляемый клиент (чужой браузер, мобильник пользователя), раздача сертификатов превращается в боль и mTLS уступает место токенам.

**Используйте mTLS, когда:**
- **Service-to-service** в микросервисах (Zero Trust).
- **B2B API** — дорогие партнёрские интеграции.
- **IoT** — аутентификация устройств.
- **Внутренние чувствительные API** — admin-инструменты.
- **Комплаенс** — PCI, HIPAA, банкинг.
- **Межрегиональный** защищённый трафик.

**Не используйте, когда:**
- Публичные потребительские API — берите OAuth или API-ключи.
- Мобильные приложения — раздавать и обновлять сертификаты на устройствах сложно.
- Быстрые прототипы — эксплуатационные накладные расходы не окупятся.

**Современный подход:** комбинируют — **service mesh** даёт внутренний mTLS между сервисами, а OAuth закрывает внешних клиентов.

## Q16. Какие накладные расходы у mTLS на производительность?

Главное, что нужно понимать: **основная цена — это handshake, а не шифрование данных**. Handshake происходит один раз на соединение, поэтому переиспользование соединений почти полностью нивелирует overhead.

**Откуда берутся расходы:**
- TLS handshake: ~50–100 мс, **один раз на соединение**.
- mTLS handshake: ~100–200 мс — дороже за счёт дополнительной проверки клиентского сертификата.
- Шифрование самих байтов: ~5–10% нагрузки на CPU.

**Как снижают накладные расходы:**
- **Пулинг соединений** — переиспользуем установленные TLS-сессии, не платим за handshake на каждый запрос.
- **Возобновление сессий** — TLS 1.3 0-RTT.
- **Мультиплексирование HTTP/2** — одно соединение обслуживает много запросов.
- **Аппаратное ускорение** — AES-NI на CPU удешевляет шифрование.

**Почему в service mesh почти бесплатно.** Sidecar-прокси держат **долгоживущие** соединения между собой, поэтому handshake случается редко. А приложение общается со своим sidecar через localhost без TLS вообще.

**Итог по факту.** В проде overhead обычно ~3–5% к latency — на фоне сетевых задержек практически незаметно.

## Q17. (!) Какие типичные ошибки и подводные камни у mTLS?

Большинство граблей mTLS — не про криптографию, а про **эксплуатацию сертификатов**: истёк, не тот, утёк ключ, рассинхрон часов. Запомнить их полезно, потому что на собеседовании любят спросить «а что может пойти не так».

1. **Нет ротации** — сертификаты истекают, сервис ложится.
2. **Долгоживущие сертификаты** (на годы) — большое окно компрометации.
3. **Self-signed без настройки доверия** — клиенты отклоняют соединение.
4. **Не приложили промежуточные сертификаты** в цепочку — клиент не может достроить путь до Root.
5. **Сертификат не для этого hostname** — несоответствие CN/SAN.
6. **Рассинхрон часов (clock skew)** — сертификат считается «ещё не действительным» из-за `notBefore`.
7. **Нет механизма отзыва** — скомпрометированный сертификат остаётся валидным до истечения срока.
8. **Сложная раздача сертификатов** — мобильным и публичным клиентам её толком не сделать.
9. **Утечка приватного ключа** — закоммитили в git, засветили в логах.
10. **Трудно отлаживать** — TLS-ошибки часто непрозрачны и неинформативны.

**Чем отлаживать:** `openssl s_client`, `curl -v`, Wireshark.

## Q18. Чем mTLS отличается от JWT и когда что выбирать?

Это не конкуренты, а разные уровни. **mTLS аутентифицирует канал** (кто с кем установил соединение) на транспортном уровне, а **JWT аутентифицирует запрос** (от чьего имени он сделан) на прикладном. Поэтому их часто используют вместе, а не вместо друг друга.

| Аспект | mTLS | JWT |
|--------|------|-----|
| Аутентификация | Криптографический сертификат | Bearer-токен |
| Уровень | Транспортный (L4–L5) | Прикладной (L7) |
| Identity | Subject сертификата | Claims в токене |
| Ротация | Продление сертификата | Истечение токена |
| Отзыв | CRL/OCSP (сложно) | Короткий TTL + blocklist |
| Мобильные | Сложно (установка сертификата) | Легко (HTTP-заголовок) |
| Браузер | Сложно (установка сертификата) | Легко (cookie) |
| Service-to-service | **Отлично** | Хорошо |
| Для пользователей | Затруднительно | **Отлично** |

**Как их комбинируют на практике:**
- **mTLS** — для аутентификации сервисов между собой (Zero Trust): сервис A знает, что говорит именно с сервисом B.
- **JWT** — для проброса identity конечного пользователя сквозь цепочку сервисов: внутри защищённого mTLS-канала летит токен, который говорит «этот запрос — от пользователя Иванова».

## Q19. Как отзывают сертификаты (CRL, OCSP)?

Проблема: если приватный ключ **скомпрометирован до истечения срока**, сертификат формально ещё валиден. Значит, нужен механизм сказать клиентам «этому сертификату больше не верьте». Для этого есть два классических подхода — CRL и OCSP.

**CRL (Certificate Revocation List)** — чёрный список:
- CA публикует список серийных номеров отозванных сертификатов.
- Клиенты периодически его скачивают и сверяются.
- **Медленно**: списки большие, обновляются редко — между отзывом и его распространением есть окно.
- Минус приватности: чтобы свериться, клиент обращается к CA.

**OCSP (Online Certificate Status Protocol)** — проверка по запросу:
- Клиент спрашивает у OCSP-респондера статус конкретного сертификата в реальном времени (HTTP-запрос).
- **Быстрее** и актуальнее, чем тянуть весь CRL.
- Минус приватности: CA видит, кто и что проверяет.
- **OCSP Stapling** решает это: сервер сам периодически берёт у CA подписанный OCSP-ответ и прикладывает к сертификату при handshake — клиенту отдельный запрос делать не нужно.

**Современная альтернатива — короткоживущие сертификаты.** Если сертификат живёт часы, отзыв вообще не нужен: скомпрометированный экземпляр сам быстро протухнет. Это убирает всю сложную инфраструктуру отзыва.

## Q20. (!) Что такое короткоживущие сертификаты?

**Короткоживущие сертификаты** — это сертификаты с TTL в **часы или минуты** вместо традиционных лет. Идея в том, что вместо отзыва скомпрометированного сертификата мы просто даём ему очень быстро истечь — а взамен непрерывно автопродлеваем.

**Ключевые свойства:**
- TTL: часы / минуты (против традиционных лет).
- **Автопродление** до истечения срока — без него короткий TTL означал бы постоянные простои.
- **Отзыв не нужен** — сертификат и так быстро протухает.

**Где встречается:**
- **Istio:** TTL 24 ч по умолчанию.
- **SPIRE:** настраивается, часто 1–24 ч.
- **Vault PKI:** любой TTL на ваш выбор.

**Компромисс:**
- Плюс: короткое окно компрометации — часы, а не годы.
- Плюс: не нужна инфраструктура отзыва (CRL/OCSP).
- Минус: высокая нагрузка на выпуск — много операций с сертификатами в секунду.
- Минус: без автоматизации не работает — вручную ротировать сертификаты раз в час невозможно.

**Современный паттерн:** PKI с автоматическим выпуском короткоживущих сертификатов — именно так работают service mesh и SPIRE.

В **2025** mTLS — **стандарт** для production-микросервисов. Service mesh делает его прозрачным.
