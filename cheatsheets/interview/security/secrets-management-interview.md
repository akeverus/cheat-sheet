# Вопросы на собеседовании: `Secrets Management`

Secrets management — безопасная работа с чувствительными учётными данными (пароли, API-ключи, сертификаты). Ключевые понятия: **централизованное хранилище, ротация, динамические секреты, шифрование at rest, аудит, least privilege**. Инструменты: **Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, Doppler**. Критично для безопасности и compliance.

## Q1. (!) Что такое secret и зачем нужно отдельное управление секретами?

**Secret** — любые чувствительные учётные данные, по которым система или человек получает доступ к ресурсам. Если такой секрет утечёт, злоумышленник может выдать себя за легитимного клиента. Типичные примеры:

- Пароли к базам данных
- API-ключи (Stripe, AWS, ...)
- TLS-сертификаты и приватные ключи
- Ключи шифрования
- OAuth-токены
- SSH-ключи

**Зачем для них отдельный инструмент, а не просто `.env` и конфиги.** Секрет отличается от обычной конфигурации тем, что у него есть жизненный цикл (выдача → использование → ротация → отзыв) и требования по безопасности, которые обычные конфиги не покрывают. Централизованный secret manager даёт:

- **Централизацию** — один источник истины вместо паролей, разбросанных по `.env`-файлам, тикетам и головам разработчиков.
- **Аудит** — журнал, кто и когда обращался к секрету (нужен для расследования инцидентов и compliance).
- **Ротацию** — периодическую автоматическую смену, чтобы старые значения не жили вечно.
- **Отзыв** — мгновенное отключение скомпрометированного секрета.
- **Шифрование** — at rest (на диске) и in transit (по сети).
- **Least privilege** — детальный доступ: каждый сервис видит только свои секреты, а не все сразу.
- **Compliance** — выполнение требований SOC2, PCI DSS, HIPAA.

## Q2. (!) Какие практики работы с секретами считаются плохими (что НЕ делать)?

Главная мысль: секрет нельзя класть туда, откуда его легко прочитать или забыть удалить. Типичные анти-паттерны и чем они опасны:

- **Хардкод в исходном коде** — попадает в git, а оттуда в публичную утечку (даже если потом удалить, остаётся в истории).
- **Открытый текст в конфигурационных файлах** — читается любым, у кого есть доступ к файловой системе.
- **Закоммиченные plain `.env`-файлы** — частая причина утечек.
- **Передача через Slack/email** — секрет навсегда остаётся в истории переписки и индексах поиска.
- **Один и тот же секрет в dev / staging / prod** — компрометация менее защищённого dev открывает доступ к prod.
- **Долгоживущие общие секреты без ротации** — окно компрометации не ограничено по времени.
- **Вывод секретов в логи и сообщения об ошибках** — логи часто хранятся дольше и доступнее самих секретов.
- **Секреты в Docker-образах** — видны в слоях образа, даже если файл удалён в более позднем слое.
- **Слишком широкие IAM-права** — один пользователь или сервис имеет доступ ко всему, что превращает любую утечку в катастрофу.
- **Отсутствие журналирования аудита** — после инцидента невозможно понять, что и кем использовалось.

**Почему это не теория.** Реальные инциденты — массовые утечки на GitHub и брутфорс-атаки по закоммиченным секретам. **GitGuardian** ежедневно сканирует GitHub и находит **миллионы** утёкших секретов в год — это показывает масштаб проблемы.

## Q3. Чем статические секреты отличаются от динамических?

Ключевое различие — кто и когда создаёт секрет, и как долго он живёт.

**Статические** хранятся в неизменном виде и используются всеми, кому выдали:
- Ротируются вручную (или редко по расписанию).
- Долгоживущие.
- Примеры: API-ключи, элементы конфигурации.

**Динамические** генерируются по запросу прямо в момент обращения:
- Короткий TTL (минуты-часы).
- Автоматически отзываются по истечении TTL.
- Пример: учётные данные к БД — Vault создаёт временного пользователя на лету и удаляет его, когда срок истёк.

**Когда предпочитать динамические:** доступ к базам данных, облачным API (AWS, GCP), SSH, сторонним сервисам (где поддерживается).

**Почему это безопаснее.** Если динамический секрет утечёт, он бесполезен уже через несколько минут — окно компрометации сведено к TTL. Статический же секрет работает, пока его явно не отзовут, поэтому утечка может оставаться эксплуатируемой месяцами.

## Q4. (!) Что такое HashiCorp Vault и что он умеет?

**Vault** — самое популярное OSS-решение для управления секретами. Это не просто зашифрованное хранилище ключ-значение, а платформа: кроме хранения готовых секретов он умеет генерировать их на лету и выступать как сервис шифрования.

**Ключевые возможности:**
- **KV-хранилище** — статические секреты по путям.
- **Динамические секреты** — выдаёт временные учётные данные для БД, облака, SSH по запросу.
- **PKI** — выступает как внутренний центр сертификации и выпускает TLS-сертификаты.
- **Transit-шифрование** — encryption-as-a-service: приложение шлёт данные на шифрование/расшифровку, ключи не покидают Vault.
- **Multi-tenant** — изоляция через namespaces и политики доступа.
- **Множество методов аутентификации** — Kubernetes, AWS IAM, LDAP, токены и др.

```bash
# Write secret
vault kv put secret/myapp/db password=secret123

# Read
vault kv get secret/myapp/db

# Dynamic DB credentials
vault read database/creds/my-role
# Returns NEW user/password, expires in 1 hour
```

Подробнее — в [Vault](../devops/vault-interview.md).

## Q5. (!) Что такое AWS Secrets Manager?

**AWS Secrets Manager** — полностью управляемое AWS хранилище секретов. Его главное преимущество перед самостоятельным Vault — нулевые операционные расходы: масштабирование, шифрование и интеграция с другими сервисами AWS уже сделаны за вас.

```bash
# Create
aws secretsmanager create-secret --name myapp/db --secret-string '{"username":"admin","password":"secret"}'

# Retrieve
aws secretsmanager get-secret-value --secret-id myapp/db
```

**Возможности:**
- **Авторотация** — встроенная для RDS, Redshift, DocumentDB (Lambda меняет пароль за вас).
- **Шифрование** — через KMS.
- **Репликация между регионами** — для отказоустойчивости и multi-region приложений.
- **Resource-based policies** — тонкое управление доступом через IAM.
- **Аудит** — все обращения логируются в CloudTrail.

**Стоимость:** $0.40 за секрет в месяц + плата за API-вызовы.

**Сценарий применения:** AWS-native приложения, где не хочется поднимать и обслуживать собственный Vault.

## Q6. Чем AWS Parameter Store отличается от Secrets Manager и что когда выбирать?

Оба сервиса AWS хранят значения по ключу и шифруют их через KMS, но Secrets Manager — это «секреты с жизненным циклом», а Parameter Store — «параметры конфигурации». Главное практическое различие: авторотация и цена.

| Критерий | Parameter Store | Secrets Manager |
|-----------|----------------|-----------------|
| Стоимость | **Бесплатно** (Standard) | $0.40 за секрет в месяц |
| Авторотация | Нет | **Да** |
| Репликация между регионами | Нет | Да |
| Макс. размер значения | 4 KB / 8 KB | 64 KB |
| Лимиты API | Ниже | Выше |
| Сценарий | Конфигурация, простые секреты | Чувствительные учётные данные |

**Распространённый паттерн — использовать оба:**
- **Parameter Store** — для конфигурации (URL, feature-флаги, нечувствительные данные), там, где важна экономия.
- **Secrets Manager** — для настоящих учётных данных (пароли БД, API-ключи), где нужны авторотация и репликация.

Оба шифруются через KMS, так что выбор сводится к тому, нужна ли вам встроенная ротация и готовы ли вы за неё платить.

## Q7. Что такое GCP Secret Manager?

**GCP Secret Manager** — управляемое хранилище секретов в Google Cloud, аналог AWS Secrets Manager. Доступ контролируется через тот же IAM, что и остальные ресурсы GCP, а каждое значение версионируется.

```bash
# Create
echo -n "secret_value" | gcloud secrets create my-secret --data-file=-

# Retrieve
gcloud secrets versions access latest --secret="my-secret"
```

**Возможности:**
- **Версионирование** — несколько версий секрета, можно откатиться или явно зафиксировать нужную.
- **Доступ на основе IAM** — те же роли и политики, что и для остальных ресурсов GCP.
- **CMEK** — шифрование ключами, управляемыми клиентом (customer-managed encryption keys).
- **Аудит** — обращения пишутся в Cloud Audit Logs.

**Стоимость:** $0.06 за секрет в месяц + плата за доступ.

## Q8. Что такое Azure Key Vault?

**Azure Key Vault** — управляемое хранилище в Azure, которое объединяет три типа объектов в одном сервисе: секреты, криптографические ключи и TLS-сертификаты. Это его отличительная черта — например, можно держать приватные ключи в HSM и выпускать сертификаты, не выходя за пределы Key Vault.

```bash
az keyvault secret set --vault-name MyVault --name MySecret --value "secretValue"
az keyvault secret show --vault-name MyVault --name MySecret
```

**Возможности:**
- **Три типа объектов** — секреты, **ключи** (с HSM-бэкендом) и **сертификаты**.
- **Soft delete + purge protection** — защита от случайного или злонамеренного удаления: объект сначала помечается удалённым и его можно восстановить.
- **Интеграция с managed identities** — приложения в Azure авторизуются без хранения учётных данных.
- **HSM** — опция аппаратного модуля с сертификацией FIPS 140-2 Level 2/3 для строгих требований.

**Стоимость:** $0.03 за 10K операций + стоимость сертификатов.

**Сценарий применения:** Azure-native приложения и среды с жёсткими требованиями compliance, где нужен HSM.

## Q9. Что такое Doppler, Infisical и 1Password Secrets?

Это developer-friendly альтернативы тяжёлым Vault и облачным менеджерам. Их ниша — команды, которым важна простота настройки и хороший UI, а не максимум возможностей корпоративного уровня.

**Doppler** (SaaS):
- Простой CLI.
- Удобная работа с несколькими окружениями.
- Синхронизация секретов на множество платформ.
- $0–25 за пользователя в месяц.

**Infisical** (open-source + SaaS):
- Можно self-host или взять облако.
- Бесплатная OSS-версия.
- Современный UI.
- Быстро развивается.

**1Password Secrets** (расширение менеджера паролей 1Password):
- Привычный UX 1Password, знакомый многим разработчикам.
- Функции, ориентированные на разработку.
- Интеграция с CLI.

**Сценарий применения:** небольшие команды, которым нужно проще, чем Vault, но богаче, чем голый Parameter Store.

## Q10. (!) Насколько безопасны нативные K8s Secrets?

Короткий ответ: сами по себе — слабо. K8s Secret хранит значение всего лишь в **кодировке Base64** в etcd, а Base64 — это не шифрование, а способ записи, который тривиально декодируется.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-secret
type: Opaque
data:
  password: c2VjcmV0   # base64("secret")
```

**Почему этого недостаточно:**
- **Base64 ≠ шифрование** — любой, у кого есть доступ, мгновенно декодирует значение.
- Секреты лежат в etcd, который **часто не зашифрован** по умолчанию.
- Все администраторы кластера по умолчанию могут их читать.
- Механизм просто не проектировался под высокий уровень безопасности.

**Как усилить защиту:**
1. **Шифровать etcd at rest** через `--encryption-provider-config`.
2. **Ограничить доступ через RBAC** к ресурсам Secret.
3. **Использовать внешний secret manager** (Vault, AWS Secrets Manager) и подтягивать секреты оттуда.
4. **Sealed Secrets** — если секреты нужно хранить в git (GitOps).

**Рекомендация:** не полагайтесь на «голые» K8s Secrets для настоящих секретов. Держите значения во внешнем хранилище и синхронизируйте их в кластер (см. External Secrets Operator).

## Q11. (!) Что такое External Secrets Operator и какую проблему он решает?

**External Secrets Operator (ESO)** — Kubernetes-оператор, который синхронизирует секреты из внешнего хранилища (Vault, AWS, GCP...) в нативные K8s Secrets. Он закрывает разрыв из Q10: настоящий секрет хранится в защищённом менеджере, а в кластер попадает его актуальная копия, которую поды читают привычным способом — без SDK и кода для похода в Vault.

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  secretStoreRef:
    name: vault-store
    kind: SecretStore
  target:
    name: db-secret
  data:
    - secretKey: password
      remoteRef:
        key: secret/myapp/db
        property: password
```

**Как это работает:** ESO периодически забирает данные из Vault (или другого бэкенда) → создаёт и обновляет K8s Secret → поды читают его обычным образом. Когда секрет меняется в источнике, ESO синхронизирует изменение в кластер.

**Поддерживаемые бэкенды:**
- HashiCorp Vault
- AWS Secrets Manager
- AWS Parameter Store
- GCP Secret Manager
- Azure Key Vault
- 1Password
- Doppler
- и другие

Это **самый популярный паттерн** связки Kubernetes с внешним хранилищем секретов в 2025 году.

## Q12. Что такое Sealed Secrets (Bitnami)?

**Проблема:** при GitOps всё хранится в git, но обычный K8s Secret в git класть нельзя — Base64 тривиально декодируется.

**Sealed Secrets** решает это: вы шифруете секрет публичным ключом контроллера, и получившийся `SealedSecret` можно безопасно коммитить в git. Расшифровать его умеет только контроллер внутри кластера своим приватным ключом.

```bash
# Encrypt
echo -n "mysecretpassword" | kubectl create secret generic my-secret \
  --dry-run=client --from-file=password=/dev/stdin -o yaml | \
  kubeseal -o yaml > sealed-secret.yaml

# sealed-secret.yaml содержит encrypted data — safe для git
```

```yaml
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: my-secret
spec:
  encryptedData:
    password: AgBKj9... (encrypted)
```

**Что происходит дальше:** контроллер Sealed Secrets внутри кластера расшифровывает `SealedSecret` → создаёт обычный K8s Secret, который и читают поды.

**Плюсы:** отлично ложится на GitOps — зашифрованный секрет живёт в репозитории рядом с остальными манифестами.

**Минусы:** приватный ключ привязан к конкретному кластеру, поэтому `SealedSecret`, зашифрованный для одного кластера, не расшифруется в другом, а потеря ключа делает все секреты нерасшифровываемыми (важно бэкапить).

## Q13. Как SOPS помогает хранить зашифрованные секреты в git?

**SOPS (Mozilla)** шифрует файлы (YAML, JSON, ENV), но с одной важной особенностью: шифруются только значения, а ключи (имена полей) остаются открытыми. Благодаря этому зашифрованный файл по-прежнему читаемый и diff-friendly в git. Ключ шифрования берётся из разных бэкендов — KMS, PGP или age.

```bash
# Encrypt с AWS KMS
sops --encrypt --kms arn:aws:kms:... secrets.yaml > secrets.enc.yaml

# Decrypt
sops --decrypt secrets.enc.yaml
```

**Результат:** YAML, где значения зашифрованы, а структура видна — такой файл безопасно коммитить в git.

```yaml
db:
  password: ENC[AES256_GCM,data:abc123...,type:str]
```

**Интеграция с инструментами:**
- Helm Secrets
- ArgoCD
- Flux
- Terraform

**Сценарий применения:** GitOps, секреты для IaC, конфигурации с разными значениями для нескольких окружений.

**Отличие от Sealed Secrets:** SOPS не привязан к Kubernetes и работает с любыми файлами и IaC, а Sealed Secrets заточен под K8s-манифесты.

## Q14. (!) Что такое ротация секретов и как её делают?

**Ротация** — это регулярная смена секрета на новое значение. Смысл в том, чтобы ограничить окно компрометации: даже если секрет утёк незаметно, после следующей ротации старое значение перестаёт работать.

**Стратегии ротации:**

**Вручную:**
- Раз в квартал или в год.
- Риск: про ротацию забывают, а сам процесс болезненный и часто откладывается.

**Авторотация:**
- AWS Secrets Manager — автоматически для RDS, Redshift, DocumentDB.
- Динамические секреты Vault — крайний случай ротации: каждый запрос выдаёт новые учётные данные.
- Кастомные Lambda-функции — ротация чего угодно по своей логике.

**Типовой паттерн (без даунтайма):**
1. Создать новые учётные данные.
2. Перевести приложения на новое значение.
3. Проверить, что всё работает.
4. Отозвать старые учётные данные.

**Подводные камни:**
- **Приложение должно уметь перечитывать** секрет — в идеале без перезапуска, иначе ротация = простой.
- **База данных** должна принять новый пароль синхронно со сменой на стороне приложения.
- **Пулы соединений** держат старые учётные данные, поэтому их тоже нужно обновлять, а не только переменную окружения.

## Q15. Как работают динамические секреты на примере Vault DB engine?

Идея: вместо одного общего пароля к базе Vault сам выступает посредником и **выдаёт каждому приложению временного пользователя БД по запросу**. Вы один раз настраиваете подключение и роль с SQL-шаблоном создания пользователя, а дальше Vault создаёт и удаляет пользователей автоматически.

```bash
# Configure
vault write database/config/postgres \
  plugin_name=postgresql-database-plugin \
  connection_url="postgres://vault@host/db" \
  allowed_roles="readonly"

# Define role
vault write database/roles/readonly \
  db_name=postgres \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}';" \
  default_ttl=1h \
  max_ttl=24h

# Get credentials
vault read database/creds/readonly
# Returns username + password, valid 1 hour
```

**Что в итоге:** каждый экземпляр приложения получает свои уникальные учётные данные, а по истечении TTL Vault сам отзывает пользователя в БД.

**Преимущества:**
- **Учётные данные на каждый экземпляр** — в логах БД видно, какой именно инстанс что делал (точный аудит).
- **Автоматический отзыв** — не нужно вручную чистить старых пользователей.
- **Короткое окно компрометации** — утёкший пароль живёт только до конца TTL.

**Поддерживаемые СУБД и платформы:** PostgreSQL, MySQL, MongoDB, Cassandra, Oracle, Redis, AWS, GCP и др.

## Q16. Что такое отзыв секретов (revocation) и как его делают?

**Отзыв** — это немедленное аннулирование секрета, обычно при подозрении на компрометацию. В отличие от плановой ротации, здесь главное — скорость: чем раньше отозван секрет, тем меньше времени у злоумышленника.

**Для статических секретов** отзыв — это, по сути, экстренная ротация:
1. Сгенерировать новое значение.
2. Перевести приложения на него.
3. Удалить старое в хранилище секретов.
4. Пересоздать соединения, чтобы пулы не держали старый пароль.

**Для динамических секретов** всё проще, потому что есть встроенный механизм:
- Vault — API отзыва lease (одной командой убивает выданные учётные данные).
- Cloud IAM — удалить IAM-пользователя или роль.

**После отзыва** проверьте журналы аудита: они показывают, что скомпрометированный секрет больше не используется, и помогают понять, что успели сделать через него.

## Q17. (!) Какими способами приложение получает секреты?

Подходы различаются тем, кто ходит за секретом и куда он попадает — в код, в файл или в переменную окружения.

**1. Прямой вызов API** — приложение само ходит в менеджер секретов через SDK:
```python
import boto3
client = boto3.client('secretsmanager')
secret = client.get_secret_value(SecretId='myapp/db')
```
Просто, но связывает код с конкретным провайдером.

**2. Sidecar (Vault Agent)** — соседний контейнер забирает секреты и пишет в общий volume; приложение просто читает файл. Код не знает про Vault.

**3. Init-контейнер** — забирает секреты на старте пода и монтирует их в основной контейнер. Подходит, если секреты не меняются в рантайме.

**4. Оператор (External Secrets Operator)** — синхронизирует внешний секрет в K8s Secret; приложение читает K8s Secret обычным образом.

**5. Переменные окружения (внедряются при старте)** — K8s Secrets монтируются как env, либо Vault Agent рендерит шаблоны в env.

**Рекомендация:** предпочитайте смонтированные файлы (volume) переменным окружения. Env-переменные утекают в дочерние процессы, дампы и логи, а файл проще ограничить правами и перечитать после ротации без перезапуска.

## Q18. Что делают Vault Agent и Sidecar Injector?

**Vault Agent** — демон-помощник, который снимает с приложения всю работу по общению с Vault. Он запускается рядом с приложением и:
- автоматически аутентифицируется в Vault;
- забирает нужные секреты;
- кэширует их;
- рендерит шаблоны в файлы, которые читает приложение;
- продлевает (обновляет) lease, чтобы секреты не протухали.

**Sidecar Injector (для K8s)** автоматизирует подключение Vault Agent в подах:
- по аннотациям пода сам внедряет sidecar-контейнер с Vault Agent (не нужно править манифест вручную);
- приложение просто читает готовые секреты из каталога `/vault/secrets/`.

```yaml
metadata:
  annotations:
    vault.hashicorp.com/agent-inject: "true"
    vault.hashicorp.com/role: "myapp"
    vault.hashicorp.com/agent-inject-secret-db: "secret/myapp/db"
```

**Главная выгода:** приложению не нужен Vault SDK и код аутентификации — оно просто читает файлы, а всю секретную логику берёт на себя агент.

## Q19. Что такое AWS IRSA (IAM Roles for Service Accounts)?

**IRSA** — механизм EKS, который привязывает **IAM-роль** к Kubernetes ServiceAccount. Это позволяет полностью отказаться от хранения AWS-ключей: под получает доступ к AWS-сервисам по своей роли, а не по секрету в env или файле.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123:role/MyAppRole
```

**Как это работает:** под использует AWS SDK, не имея учётных данных в env или файлах — AWS сам выдаёт временные учётные данные под привязанную роль. Они короткоживущие (около часа) и авторотируются, поэтому даже их перехват малополезен.

Главная идея — **никакого распространения секретов**: доступ выдаётся на основе IAM-роли, а не статического ключа, который надо где-то хранить и ротировать.

**Аналоги в других облаках:**
- **GCP Workload Identity** — для GKE.
- **Azure Workload Identity** — для AKS.

**Рекомендация:** там, где возможно, предпочитайте cloud-native IAM (IRSA / Workload Identity) раздаче статических секретов.

## Q20. (!) Как работать с секретами в GitOps?

**В чём конфликт.** GitOps делает git единственным источником истины — всё, что должно быть в кластере, описано в репозитории. Но секреты в открытом виде в git класть нельзя. Значит, в репозиторий должно попадать либо зашифрованное значение, либо ссылка на внешнее хранилище.

**Решения:**

1. **Sealed Secrets** — секрет зашифрован, можно коммитить; расшифровывает контроллер в кластере.
2. **SOPS** — зашифрованные файлы (значения скрыты, структура видна) в git.
3. **External Secrets Operator** — в git лежит только ссылка на внешнее хранилище (Vault, AWS), сам секрет туда не попадает.
4. **Bitnami Secrets Manager**.
5. **CSI Secrets Store Driver**.

**Пример (подход с External Secrets Operator):**
```yaml
# In git (committed)
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-creds
spec:
  secretStoreRef:
    name: vault-backend
  data:
    - secretKey: password
      remoteRef:
        key: secret/db
```

Здесь сам секрет хранится только в Vault, а в git лежит **ссылка** на него, а не значение. Это и есть ключевой приём: разделить «что подключить» (в git) и «секретное значение» (во внешнем хранилище).

## Q21. (!) Какие best practices в управлении секретами?

Все эти правила сводятся к трём принципам: секрет не должен утечь, должен жить недолго и должен быть отслеживаемым. Чек-лист:

1. **Никогда не коммитьте** секреты в систему контроля версий.
2. **Централизованное хранилище** секретов (Vault, AWS Secrets Manager) вместо разрозненных конфигов.
3. **Авторотация** для долгоживущих секретов.
4. **Динамические секреты** там, где возможно (БД, облако).
5. **Короткие TTL** для учётных данных — меньше окно компрометации.
6. Доступ по принципу **least privilege** — каждому только свои секреты.
7. **Журналирование аудита** всех обращений.
8. **Шифрование at rest + in transit**.
9. **По возможности никаких секретов в env-переменных** — используйте смонтированные файлы.
10. **Cloud IAM вместо распространения секретов** (IRSA, Workload Identity).
11. **Сканирование секретов в CI** (gitleaks, GitGuardian) — ловить утечки до merge.
12. **Немедленная ротация** при подозрении на компрометацию.
13. **Разные секреты для каждого окружения** (dev/staging/prod), чтобы утечка dev не открывала prod.
14. План **disaster recovery** для хранилища секретов.
15. **MFA** для доступа к UI управления секретами.

## Q22. (!) Какие типичные ошибки допускают в управлении секретами?

Это «зеркало» best practices: почти каждый пункт — нарушение одного из принципов из Q21. Самые частые грабли:

1. **Захардкоженные секреты** — утекают через git и логи.
2. **Один секрет на все окружения** — компрометация dev = компрометация prod.
3. **Отсутствие ротации** — старые учётные данные накапливаются и живут вечно.
4. **Слишком широкие права** — сервис имеет доступ ко всем секретам, а не только к своим.
5. **Логирование секретов** — попадают в тела запросов и сообщения об ошибках.
6. **Секреты в слоях Docker-образа** — остаются видны, даже если удалены позже.
7. **Отсутствие аудита** — после инцидента непонятно, скомпрометировано или нет.
8. **Потеря unseal-ключей Vault** — без них Vault невозможно распечатать и восстановить.
9. **Отсутствие бэкапа** хранилища секретов — грозит катастрофической потерей.
10. **Передача через Slack/email** — секрет навсегда остаётся в переписке.
11. **Переиспользование** одного API-ключа между приложениями — нельзя отозвать прицельно.
12. **Отсутствие задокументированной процедуры отзыва** — в момент инцидента нет плана действий.
13. **Секреты в логах CI/CD** — маскируются в выводе, но находимы в артефактах и истории.

**Инструменты для обнаружения:**
- **gitleaks, GitGuardian, TruffleHog** — сканирование git на утёкшие секреты.
- **CodeQL, Semgrep** — статический анализ кода.
- **Trivy, Grype** — сканирование контейнеров.

К **2025 году** управление секретами — это **базовая гигиена безопасности**. Именно из-за пренебрежения этими практиками каждый год случается множество утечек.
