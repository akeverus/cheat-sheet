## Q1. (!) Что такое **Front Controller**?

**Front Controller** — единая точка входа для всех запросов: принимает запрос, по нему решает, какой компонент обработает (диспетчер маршрутизирует по `URL` или параметрам), контроллеры обрабатывают запросы и отдают данные, представления (`View`) рендерят ответ (`HTML`, `JSON` и т.д.). Даёт централизацию логики, переиспользуемость и единую точку для безопасности и логирования. Реализован в `Spring MVC`, `JSF`, `Struts`.

Практическая ценность ответа обычно повышается, если дополнить определение операционным контекстом: как решение ведёт себя под нагрузкой, при сбоях и в процессе сопровождения. На интервью ожидают, что вы назовёте критерии выбора и способ валидации решения через метрики и проверяемый сценарий.

## Q2. (!) Что такое `Spring MVC`?

**Spring MVC** — реализация паттерна `MVC` в `Spring`: **Model** (данные и бизнес-логика), **View** (отображение — `JSP`, `Thymeleaf`, `JSON` и т.д.), **Controller** (обработка запросов, передача данных в модель и выбор представления). Даёт маршрутизацию, связывание данных, валидацию, управление состоянием и интегрируется с `DI` и `AOP Spring`.

## Q3. Как получить `ServletContext` и `ServletConfig` внутри бина?

Обычно достаточно внедрить их через конструктор или поле. `Spring` передаёт в бин те же экземпляры, что и у диспетчера сервлетов, поэтому можно объявить, например, поле с `@Autowired` и типом `ServletContext` или `ServletConfig` — контейнер подставит их при инициализации контроллера или другого бина. Альтернатива — реализовать интерфейсы `ServletContextAware` и `ServletConfigAware`: `Spring` вызовет соответствующие сеттеры и передаст контекст и конфиг. На практике чаще используют внедрение через `@Autowired`, чтобы не раздувать класс лишними интерфейсами.

Практическая ценность ответа обычно повышается, если дополнить определение операционным контекстом: как решение ведёт себя под нагрузкой, при сбоях и в процессе сопровождения. На интервью ожидают, что вы назовёте критерии выбора и способ валидации решения через метрики и проверяемый сценарий.

## Q4. Что такое локализация?

Локализация — адаптация приложения к языку и региону. В `Spring MVC`: файлы сообщений (например, `messages_en.properties`, `messages_fr.properties`), бин **MessageSource** для получения строк по ключу и локали, в шаблоне (`Thymeleaf`) — ключи вместо текста: `th:text="#{`welcome.message`}"`. **LocaleResolver** задаёт текущую локаль (например, из заголовка `Accept-Language`). Итого: ресурсы `.properties` + `MessageSource` + разметка в представлении + `LocaleResolver`.

## Q5. (!) Что такое `Interceptor`?

**Interceptor** (перехватчик) добавляет общую функциональность (логирование, аутентификация, обработка исключений) к запросам и ответам. Срабатывает до и после обработки контроллером.

Класс реализует `HandlerInterceptor` или наследует `HandlerInterceptorAdapter`; переопределяют `preHandle`, `postHandle`, `afterCompletion`. Регистрация — через `WebMvcConfigurer.`addInterceptor()``:

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new MyInterceptor());
    }
}
```

Пути ограничивают через `addPathPatterns()`/`excludePathPatterns()`, порядок — через `order(1)`. Перехватчики отделяют общую логику (логирование, аутентификация) от контроллеров.

## Q6. Что такое `@ModelAttribute`?

Аннотация `@ModelAttribute` — одна из самых важных в `Spring MVC`. Она связывает параметр метода или возвращаемое значение метода с именованным атрибутом модели, а затем предоставляет его веб-представлению.

Если мы используем его на уровне метода, это указывает на то, что целью этого метода является добавление одного или нескольких атрибутов модели.

С другой стороны, при использовании в качестве аргумента метода это указывает на то, что аргумент должен быть получен из модели. Если он отсутствует, мы должны сначала создать его экземпляр, а затем добавить его в модель. После присутствия в модели мы должны заполнить поля аргументов из всех параметров запроса, имеющих совпадающие имена.

## Q7. В чём разница между `Model`, `ModelMap` и `ModelAndView`?

**Model**, **ModelMap** и **ModelAndView** — способы передачи данных между контроллером и представлением в `Spring MVC`.

1. **Model:** интерфейс для передачи данных контроллер → представление; методы добавления атрибутов; принимается параметром метода или возвращается. Пример: `model.addAttribute("attributeName", attributeValue)`.
2. **ModelMap:** реализация `Model` с дополнительными методами (добавить, удалить, извлечь атрибуты); для передачи аргументов в представление.
3. **ModelAndView:** класс, объединяющий модель и имя представления; возвращают из контроллера одним объектом. Пример: `return new ModelAndView("viewName", "modelName", modelObject)`.

`Model` и `ModelMap` проще; `ModelAndView` удобен, когда нужно вернуть и данные, и имя представления сразу.

## Q8. В чем разница между `model.put`() и model.`addAttribute()`?

В `Spring MVC` оба метода добавляют атрибуты в модель.

- **`put(key, value)`** — из интерфейса `Map`, который расширяют `Model` и `ModelMap`; ключ и значение задаются явно. Пример: `model.put("attributeName", attributeValue)`.
- **`addAttribute(name, value)`** — метод интерфейса `Model`; удобнее для добавления атрибутов, поддерживает цепочку вызовов (`method chaining`). Пример: `model.addAttribute("attributeName", attributeValue)`.

Функция одна и та же; `addAttribute()` обычно предпочтительнее из-за абстракции и удобства.

## Q9. Что такое связывание форм?

Связывание форм (форм-биндинг) это процесс автоматического привязывания данных, полученных из формы пользователем, к объекту модели данных. Это позволяет упростить обработку и валидацию данных, полученных от пользователя.

В `Spring MVC` для этого используют `@ModelAttribute` на параметре метода: `Spring` сопоставляет имена полей запроса с полями объекта и вызывает сеттеры; затем объект можно валидировать через `Bean Validation`. Это сокращает код и упрощает валидацию на сервере. Пример: `@PostMapping("/register") String register(@ModelAttribute("user") User user) { ... return "success"; }`

## Q10. Что такое `@PathVariable`?

`@PathVariable` — параметр метода обработчика, в который подставляется значение из шаблона `URI`. Например, для пути `/user/{id}` маппинг `@RequestMapping("/user/{id}")` и параметр `@PathVariable("id")`:

```java
@RequestMapping("/user/{id}")
public String handleRequest(@PathVariable("id") String userId, Model map) {
    // Обработка запроса
}
```

У аннотации есть атрибут `value` (имя переменной в шаблоне `URI`); если не указывать — имя берётся из имени параметра метода. Можно несколько `@PathVariable` в одном методе:

```java
@RequestMapping("/user/{userId}/name/{userName}")
public String handleRequest(@PathVariable String userId,
                            @PathVariable String userName, Model map) {}
```

или собрать все переменные пути в `Map<`String`, `String`>` или `MultiValueMap<`String`, `String`>`:

```java
@RequestMapping("/user/{userId}/name/{userName}")
public String handleRequest(@PathVariable Map<String, String> varsMap, Model map) {}
```

## Q11. (!) Что такое `Validation`?

Валидация в `Spring MVC` — по **Bean Validation** (`JSR 380`): на полях `DTO` аннотации `@NotNull`, `@Size`, `@Email` и т.д., в методе контроллера аргумент с `@Valid`; при ошибках `Spring` кладёт их в **BindingResult** сразу после аргумента. Можно добавить свои аннотации и `ConstraintValidator` или зарегистрировать `Spring Validator` через `@InitBinder`.

## Q12. (!) Что такое `BindingResult`?

**BindingResult** хранит результат привязки и валидации: ошибки полей после вызова валидатора для аргумента с `@Valid`. Параметр с `BindingResult` идёт сразу после проверяемого аргумента (до `Model`). По `result.`hasErrors()`` и `result.`getFieldErrors()`` формируют ответ клиенту или возвращают форму с ошибками. Пример: `public `String` submit(`@Valid NewUserForm` form, `BindingResult` result, `Model` model) { if (result.`hasErrors()`) return "form"; ... }`

## Q13. Что такое аннотации `@RequestBody` и `@ResponseBody`?

Аннотация `@RequestBody`, используемая в качестве параметра метода-обработчика, привязывает тело `HTTP`-запроса к передаче или объекту домена. `Spring` автоматически десериализует входящий `HTTP`-запрос в объект `Java` с помощью преобразователей `HttpMessageConverter`.

Когда мы используем аннотацию `@ResponseBody` для метода-обработчика в контроллере `Spring MVC`, это указывает на то, что мы запишем возвращаемый тип метода непосредственно в тело ответа `HTTP`. Мы не будем помещать его в модель, и `Spring` не будет интерпретировать его как имя представления.

## Q14. (!) В чём разница между `@Controller` и `@RestController`?

`@Controller` помечает класс как `MVC`-контроллер: методы обычно возвращают имя представления (`View`), и `Spring` отдаёт `HTML` через `ViewResolver` (`Thymeleaf`, `JSP`). `@RestController` — это `@Controller` + `@ResponseBody` на уровне класса: методы возвращают объекты, `Spring` сериализует их в `JSON / XML` и пишет в тело ответа. Для веб-страниц с шаблонами — `@Controller`; для `REST API` с `JSON` — `@RestController`.

## Q15. Что такое `@SessionAttributes` и `@SessionAttribute`?

Аннотация `@SessionAttributes` используется для хранения атрибута модели в сеансе пользователя. Мы используем его на уровне класса контроллера, как показано в статье об атрибутах сеанса в `Spring MVC`:

```java
@Controller
@RequestMapping("/sessionattributes")
@SessionAttributes("todos")
public class TodoControllerWithSessionAttributes {

    @GetMapping("/form")
    public String showForm(Model model, @ModelAttribute("todos") TodoList todos) {
        return "sessionattributesform";
    }
}
```

`@SessionAttributes("todos")` сохраняет атрибут модели в сеансе; имя должно совпадать с `@ModelAttribute`. Для получения существующего атрибута из сеанса используют `@SessionAttribute` в параметре метода:

```java
@GetMapping
public String getTodos(@SessionAttribute("todos") TodoList todos) {
    return "todoView";
}
```

## Q16. Что такое `@EnableWebMvc` и когда его включать?

`@EnableWebMvc` включает конфигурацию `Spring MVC` через `Java`-конфиг: по сути это аналог `<mvc:`annotation-driven /  из `XML`. После включения регистрируются обработка `@Controller` и `@RequestMapping`, маппинг запросов, адаптеры, конвертеры сообщений для `JSON / XML` и валидация. В приложении на `Spring Boot` эту аннотацию обычно не ставят: автоконфигурация уже поднимает `MVC`, если в зависимостях есть `spring-`boot-starter`-web`. `@EnableWebMvc` имеет смысл, когда вы полностью отключаете автоконфигурацию и настраиваете веб-слой вручную.

## Q17. (!) Что такое `ViewResolver` и зачем он нужен?

**ViewResolver** по имени представления, которое вернул контроллер (например, строка `"userView"`), находит объект `View` и отдаёт его на рендеринг. Для `JSP` используют `InternalResourceViewResolver`, для `Thymeleaf` — `ThymeleafViewResolver`; `ContentNegotiatingViewResolver` выбирает представление по заголовку `Accept` или расширению `URL`. В чисто `REST`-приложениях с `@RestController` представления обычно не используются: ответ формируется через `HttpMessageConverter` (например, `Jackson` для `JSON`), и `ViewResolver` в цепочке не участвует.

Практическая ценность ответа обычно повышается, если дополнить определение операционным контекстом: как решение ведёт себя под нагрузкой, при сбоях и в процессе сопровождения. На интервью ожидают, что вы назовёте критерии выбора и способ валидации решения через метрики и проверяемый сценарий.

## Q19. Что такое архитектуры модели 1 и модели 2?

## Q20. (!) Что такое `DispatcherServlet` и `ContextLoaderListener`?

**DispatcherServlet** — единая точка входа для `HTTP`: принимает запросы, находит контроллер по маппингу, вызывает его, разрешает `View` и отдаёт ответ. У него свой дочерний контекст (контроллеры, `ViewResolver` и т.д.). **ContextLoaderListener** при старте приложения создаёт корневой контекст `Spring` (сервисы, репозитории, общая инфраструктура) и делает его родительским для контекста `DispatcherServlet`. Сначала поднимается корневой контекст, затем `DispatcherServlet`; бины веб-слоя видят бины из корня.

## Q23. (!) Как происходит обработка исключений в веб-приложениях?

Три подхода. (1) **В самом исключении:** аннотация `@ResponseStatus` на классе исключения — при выбросе `Spring` вернёт указанный `HTTP`-код; обрабатывать исключение вручную не нужно. (3) **Глобально:** класс с `@ControllerAdvice` и методами `@ExceptionHandler` — один набор обработчиков для всех контроллеров. В методах-обработчиках допустимы параметры вроде `HttpServletRequest`, `WebRequest`; объект `Model` напрямую не передают. На практике чаще используют `@ControllerAdvice` + `@ExceptionHandler` для единой обработки ошибок в `API`.

## Q24. (!) Что такое `@ExceptionHandler`?

`@ExceptionHandler` вешает на метод обработку конкретного исключения: при выбросе такого исключения в контроллере `Spring` вызовет этот метод и вернёт его результат клиенту. Обычно класс помечают `@ControllerAdvice`, чтобы один набор обработчиков работал для всех контроллеров. Пример глобального обработчика:

```java
@ControllerAdvice
public class RestExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler({IllegalArgumentException.class, IllegalStateException.class})
    protected ResponseEntity<Object> handleConflict(RuntimeException ex, WebRequest request) {
        return handleExceptionInternal(ex, "Conflict", new HttpHeaders(), HttpStatus.CONFLICT, request);
    }
}
```

Тип исключения в `@ExceptionHandler` должен совпадать с аргументом метода. В одном классе нельзя вешать два обработчика на одно и то же исключение; если таких классов несколько, сработает первый подходящий.

## Q25. (!) Что такое `@ControllerAdvice`?

Область сужают через `basePackages`, `basePackageClasses`, `assignableTypes`, `annotations`. Чаще всего используют вместе с `@ExceptionHandler`: один класс с обработчиками исключений для всего приложения вместо дублирования в каждом контроллере.

## Q26. Как настроить шаблоны (`Thymeleaf`, `JSP`)?

Подключают зависимость движка (например, `spring-boot-starter-thymeleaf`) и настраивают префикс и суффикс для путей к шаблонам. Контроллер возвращает имя представления — фреймворк по нему находит файл. Для `JSP` используют `InternalResourceViewResolver` с префиксом к папке `JSP` и суффиксом `.jsp`. В конфиге (`application.yml` или `properties`) задают префикс и суффикс, например для `Thymeleaf`:

```yaml
spring.thymeleaf.prefix: classpath:/templates/
spring.thymeleaf.suffix: .html
```

Контроллер возвращает, например, `"`userView`"` — резолвер подставит префикс/суффикс, например `userView.html`. В чисто `REST API` с `JSON ViewResolver` не участвует: ответ отдаётся через `HttpMessageConverter`.

## Q27. (!) В чём разница между `@RequestBody` и `@RequestParam`?

`@RequestBody` — тело запроса (обычно `JSON`): `Spring` маппит его в один объект. Используют для `POST / PUT` с телом. `@RequestParam` — параметры из `query` или формы (`?page=0&size=10`). Для части `URL` пути — `@PathVariable`. В коде разница видна по сигнатурам методов:

```java
@PostMapping
public User create(@RequestBody User user) { ... }

@GetMapping
public Page<User> list(@RequestParam int page, @RequestParam int size) { ... }

@GetMapping("/{id}")
public User get(@PathVariable Long id) { ... }
```

Для создания/обновления сущности — тело и `@RequestBody`; для фильтров и пагинации — `@RequestParam`.

## Q28. Как организовать валидацию входных данных?

`Bean Validation` (`JSR 380`): на полях `DTO` — `@NotNull`, `@Size`, `@Email` и т.д., в контроллере аргумент с `@Valid`. При ошибках `Spring` выбрасывает `MethodArgumentNotValidException`. В `@ControllerAdvice` обрабатывают это исключение, достают из него полевые ошибки и отдают клиенту `400` с `JSON`-списком ошибок. Пример: метод создания с `@Valid` и обработчик ошибок валидации в `@ControllerAdvice`:

```java
@PostMapping
public ResponseEntity<User> create(@Valid @RequestBody UserCreateDto dto) { ... }

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<Map<String, String>> handleValidation(MethodArgumentNotValidException ex) {
    // ex.getBindingResult().getFieldErrors() → 400 + JSON
}
```

Свои правила — через `ConstraintValidator` или `@Validated(Group.class)`.

## Q29. Что такое `Content Negotiation` и как его настроить?

**Content Negotiation** — выбор формата ответа (`JSON`, `XML` и т.д.) по запросу клиента. `Spring` может смотреть на заголовок `Accept` или на расширение `URL` (например, `/api/user.json`). За это отвечает `ContentNegotiationManager`; сами форматы обеспечивают `HttpMessageConverter`’ы (`Jackson` для `JSON`, при наличии зависимости — для `XML`). По умолчанию в типичном `REST`-приложении отдаётся `JSON`. Если нужно разрешить выбор формата через параметр запроса (например, `?format=xml`), в конфиге задают стратегию `parameter` и имя параметра; тогда при наличии подходящего конвертера ответ будет в запрошенном формате.

## Q30. Как тестировать контроллеры с помощью `MockMvc`?

**MockMvc** гоняет запросы через `DispatcherServlet` без поднятия сервера. Срез `@WebMvcTest(YourController.class)` поднимает только веб-слой, сервисы подменяют через `@MockBean`. В тесте вызывают `perform(get(...))` или `perform(post(...))` и проверяют статус и тело через `andExpect`. Пример тестового класса:

```java
@WebMvcTest(UserController.class)
class UserControllerTest {
    @Autowired MockMvc mockMvc;
    @MockBean UserService userService;

    @Test
    void getUserId1() throws Exception {
        when(userService.findById(1L)).thenReturn(Optional.of(new User(1, "John")));
        mockMvc.perform(get("/api/users/1"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.name").value("John"));
    }
}
```

Для полного контекста — `@SpringBootTest` + **MockMvc**. Для защищённых эндпоинтов — `@WithMockUser`.
