## Q1. (!) Что такое `Spring Data JPA`?

**Краткий ответ:** подпроект `Spring`, абстракция над **JPA** для работы с БД через `ORM`. Автоматическая реализация репозиториев по интерфейсу, генерация запросов по именам методов (`findBy`...), пагинация, сортировка. Устраняет ручное написание типовых `CRUD` и `JPQL` для простых сценариев. Сущности помечают `@Entity`, репозиторий — интерфейс, наследующий `JpaRepository<`Entity`, Id>`; методы вида `findByUsername`, `findByEmailDomain` с `@Query` генерируют запросы. В сервисе инжектируют репозиторий и вызывают `save`, `findById` и т.д.

Основные преимущества: 1. Устранение необходимости вручную написания многих типовых операций `CRUD` (создание, чтение, обновление, удаление) для работы с сущностями базы данных. Репозитории автоматически создаются на основе интерфейсов, что упрощает и ускоряет разработку.
2. Автоматическая генерация `SQL`-запросов на основе именованных методов в репозитории. `Spring Data JPA` позволяет определить методы с определенным именованием, и соответствующие `SQL`-запросы будут автоматически созданы и выполнятся.
3. Поддержка различных методов запросов, например, поиск по критериям, поиск с использованием спецификаций (`Specifications`), использование `JPQL` (`Java Persistence Query Language`) или нативных `SQL`-запросов.
4. Поддержка пагинации для обработки больших объемов данных, сортировки, кеширования.
5. Использование аннотаций для настройки отображения связей между сущностями базы данных. `Spring Data JPA` является мощным и гибким инструментом для работы с базами данных в `Java`-приложениях на основе `Spring`. Он упрощает и ускоряет разработку, уменьшает количество объемного кода и предоставляет множество функций для эффективного взаимодействия с базой данных.

## Q2. Что такое `Repository`?

Репозиторий в `Spring Data JPA` — интерфейс для операций с БД (`CRUD`). Помечается `@Repository`, расширяет `JpaRepository<`Entity`, Id>` (или `CrudRepository`, `PagingAndSortingRepository`) и наследует готовые методы. Свои запросы задают методами по конвенции имён: `findByFirstName(`String` name)`, `countByStatus(`Status` s)` — `Spring Data` парсит имя и генерирует запрос. Без написания `SQL` и реализации класса.

## Q3. Что такое `JPQL` (`Java Persistence Query Language`)?

**JPQL** — язык запросов `JPA` по сущностям и полям (не по таблицам). В `Spring Data JPA` задаётся аннотацией `@Query("SELECT e FROM YourEntity e WHERE e.name = :name")` на методе репозитория; параметры — `:name` с `@Param("name")` или позиционные `?1`, `?2`. Поддерживаются `ORDER BY`, `JOIN`, агрегаты. Синтаксис близок к `SQL`, но оперирует именами сущностей и атрибутов; для сложных запросов, которые не выразить через `Query Methods`.

На практике этот выбор почти всегда подтверждают измерениями: планом выполнения запросов, профилем нагрузки и latency по p95/p99. В интервью полезно коротко обозначить, как именно вы проверяете гипотезу и какие метрики будут критерием успешности.

## Q4. (!) Что такое `@Transactional`?

Аннотация `@Transactional` в `Spring Data JPA` объявляет метод или класс транзакционным: `Spring` управляет началом, коммитом и откатом транзакции. При исключении транзакция откатывается автоматически.

Можно вешать на метод или на класс — тогда все публичные методы класса выполняются в транзакции. Основные параметры: **propagation** (например, `REQUIRED` — войти в существующую или создать новую, `REQUIRES_NEW` — всегда новая транзакция), **isolation** (уровень изоляции БД: `DEFAULT`, `READ_COMMITTED`, `SERIALIZABLE` и др.), **readOnly** (оптимизация для операций только чтения), **rollbackFor** (типы исключений, при которых делать откат). Для большинства сервисов достаточно `@Transactional` на методе без дополнительных параметров.

## Q5. (!) Можно ли вызвать `@Transactional` метод из другого `@Transactional` метода?

Если в `Spring Boot` один метод с аннотацией `@Transactional` вызывает другой метод, также помеченный аннотацией `@Transactional`, то оба метода будут выполняться в одной транзакции. Поведение транзакций в данном случае зависит от настройки уровня изоляции транзакций. Если уровень изоляции транзакций установлен на уровне по умолчанию (`READ_COMMITTED`), изменения, внесенные в одном методе, станут видимыми для другого метода. Если в методе с аннотацией `@Transactional` возникнет исключение, то обе транзакции будут откатываться и внесенные изменения не будут сохранены. Однако, следует быть осторожным при использовании вложенных транзакций, так как это может привести к проблемам с производительностью и непредсказуемому поведению. Вместо использования вложенных транзакций рекомендуется применять аннотацию `@Transactional` в родительском методе или классе. Также важно учитывать, что аннотация `@Transactional` действует только на публичные методы, вызываемые извне (через `Spring proxy`).

При вызове одного `@Transactional`-метода из другого по умолчанию используется **propagation REQUIRED**: оба выполняются в одной транзакции; при исключении в любом из них откатывается вся транзакция. Если внутреннему методу задать `propagation = Propagation.REQUIRES_NEW` или `@Transactional(isolation = ...)`` и при необходимости наследуется от существующей транзакции.

## Q6. Что такое `Auditing`?

`Auditing` (аудит) — запись и отслеживание изменений данных. В `Spring Data JPA` включается через `@EnableJpaAuditing`; сущности помечают `@EntityListeners(AuditingEntityListener.class)` и полями с `@CreatedBy`, `@CreatedDate`, `@LastModifiedBy`, `@LastModifiedDate` — эти поля заполняются автоматически при создании и обновлении записи. Реализацию «кто изменил» задают через `AuditorAware<T>`.

## Q7. Что такое `Specifications`?

**Specifications** в `Spring Data JPA` — способ динамически собирать условия запроса через `JPA Criteria API`, когда набор фильтров неизвестен заранее. Репозиторий расширяет `JpaSpecificationExecutor<`Entity`>` и принимает `Specification<`Entity`>` в методах вроде `findAll(spec)`. Спецификация — лямбда `(root, `query`, cb) -> `cb.equal`(`root.get`("name"), name)`; несколько условий объединяют через `Specification.where(spec1).and(spec2)`. Удобно для поиска с опциональными параметрами без дублирования методов репозитория.

## Q9. (!) Что такое `@Lock`?

`@Lock` с `LockModeType.PESSIMISTIC_READ`, `PESSIMISTIC_WRITE`, `OPTIMISTIC`. **PESSIMISTIC_WRITE** блокирует строку в БД до конца транзакции; **OPTIMISTIC** — проверка версии при коммите. Используют при конкурентном доступе к одной записи (например, резервирование). Блокировки снижают параллелизм, применять только там, где нужна строгая консистентность.

## Q11. Что такое `@EntityListeners` и `@EntityGraph`?

**@EntityListeners** — привязка слушателей к жизненному циклу сущности (`@PrePersist`, `@PostLoad` и т.д.): аудит, валидация, заполнение полей при событиях. **@EntityGraph** — указание, какие ассоциации загружать одним запросом (избегая N+1): задаётся `attributePaths` на методе репозитория или именованный граф на сущности. Разные цели: listeners — реакция на события; entity graph — контроль загрузки связей.

## Q13. Что такое `Query Methods` и какие ключевые слова поддерживаются?

`Query Methods` — методы репозитория, имена которых `Spring Data JPA` парсит и превращает в запросы. ## Q14. Что такое `Projections` и когда их использовать?

**Projections** позволяют выбирать только нужные поля сущности, уменьшая объём данных и риск N+1. **Интерфейсная проекция** — интерфейс с геттерами по именам полей (`Spring` создаёт прокси). **DTO-проекция** — класс с конструктором, в `JPQL`: `select new com.example.UserDto(u.name, u.email)`.

Используйте при чтении больших сущностей, когда нужны только несколько полей. Закрытая (интерфейс) — поля запрашиваются по мере обращения; открытая (`DTO`) — один запрос с явным списком полей.

**Закрытая vs открытая:** закрытая (интерфейс) — `Spring` создаёт прокси, поля запрашиваются по мере обращения; открытая (`DTO` с конструктором в `JPQL`) — один запрос с явным списком полей. Для `DTO` в нативном запросе — алиасы колонок должны совпадать с именами параметров конструктора или использовать `@SqlResultSetMapping`. Проекции уменьшают объём данных и риск N+1 при отсутствии лишних связей в выборке.

```java
interface UserSummary { String getName(); String getEmail(); }
List<UserSummary> findByStatus(Status s);

record UserDto(String name, String email) {}
@Query("select new com.example.UserDto(u.name, u.email) from User u where u.status = ?1")
List<UserDto> findDtoByStatus(Status s);
```
Закрытая проекция (интерфейс) — `Spring` создаёт прокси; открытая (`DTO`) — явный конструктор в `JPQL`.

## Q15. Как выполнять нативные `SQL`-запросы в `Spring Data JPA`?

Через **`@Query`(`nativeQuery` = `true`)** с `SQL` в атрибуте **value**. Параметры — **?1**, **?2** или именованные **:name** с **`@Param`("name")**. Для `DTO` — **@SqlResultSetMapping** или интерфейсная проекция с алиасами в запросе. Параметры только через `?1` или `:name` — никогда конкатенация строк (безопасность от `SQL`-инъекций).

Нативный запрос привязан к диалекту БД; для переносимости предпочтительнее `JPQL` где возможно. Сортировка и пагинация работают: `Spring Data` подставляет `ORDER BY` и `LIMIT / OFFSET` по диалекту.

**Пример:** `@Query(value = "SELECT * FROM users WHERE status = :status", nativeQuery = true) List<User> findByStatusNative(@Param("status") String status);` Для проекции в `DTO` — в нативном запросе указать алиасы как имена полей `DTO` и использовать интерфейс с геттерами или класс с конструктором; при несовпадении имён — `@SqlResultSetMapping` на сущности или нативный результат через `JdbcTemplate`. Сортировка и пагинация работают: `Spring Data` подставляет `ORDER BY` и `LIMIT`/`OFFSET` по диалекту.

## Q16. Что такое N+1 проблема и как её избежать?

**N+1** — один запрос за список сущностей и N запросов за связанные коллекции (lazy). Решения: `@EntityGraph(attributePaths = "orders")` в методе репозитория; **JOIN FETCH** в `JPQL` (`select u from User u join fetch u.orders`); `@BatchSize` на коллекции; `DTO`/проекции без лишних связей.

Без fetch при обходе `user.getOrders()` будет N запросов. Пример: `@EntityGraph(attributePaths = "orders")` на методе `findById` или `@Query("select u from User u join fetch u.orders where u.id = ?1")`. Правильный `FetchType.LAZY` и загрузка связей одним запросом при необходимости.

## Q17. Что такое `@Modifying` и когда его использовать?

**@Modifying** помечает метод репозитория как изменяющий данные (`UPDATE / DELETE`). Используется вместе с **@Query**. После выполнения сущности в persistence context могут быть устаревшими — часто добавляют **clearAutomatically = true**. Требуется **@Transactional**. Без `@Modifying Spring Data` трактует метод как `SELECT` и может выбросить исключение.

Для bulk delete предпочтительнее один **`@Modifying @Query`("delete from `Entity` e where ...")** — один запрос. `Derived` delete (`deleteByStatus`) в некоторых версиях выполняет `SELECT` + delete по сущностям (N запросов).

## Q18. Как работает batch-обработка (batch insert/update)?

В `Hibernate`: **spring.jpa.properties.hibernate.jdbc.batch_size** (например, 50). Для insert — **`repository.saveAll(batch)`** с батчами; `ID` лучше **SEQUENCE** или табличный генератор — при **IDENTITY** `Hibernate` не может батчить insert (нужен id после каждого insert). Для update — **flush()**, **clear()** по батчам в цикле или bulk **@Modifying** запросы.

В цикле: `saveAll`(batch), flush(), clear() каждые `batch_size` записей — иначе persistence context разрастается и падает по памяти. Для массовой вставки предпочтительнее `SEQUENCE / batch_size` в конфиге.

## Q19. Что такое `FetchType LAZY` vs `EAGER`?

**LAZY** — связь загружается при первом обращении (по умолчанию для **@OneToMany**, **@ManyToMany**). **EAGER** — загружается вместе с владельцем (по умолчанию для **@ManyToOne**, **@OneToOne**). Для производительности предпочтителен `LAZY`; загружайте связи явно через **@EntityGraph** или **JOIN FETCH**, чтобы избежать N+1.

`EAGER` на коллекциях — риск N+1 при запросе списка. Для `@ManyToOne` по умолчанию `EAGER` — часто меняют на `LAZY`. В `Open Session` In `View` lazy может подгружаться в view — при необходимости отключать `OSIV` и загружать явно в сервисе.

## Q20. Что такое `CascadeType` и когда применять каскады?

**CascadeType** распространяет операции с владельцем на связанные сущности: **PERSIST**, **MERGE**, **REMOVE**, **REFRESH**, **DETACH**, **ALL**. Применяйте осторожно: каскад **REMOVE** удалит дочерние записи. Используйте для истинно зависимых сущностей (`Order` → `OrderItem`).

`PERSIST`: при сохранении `Order` сохраняются `OrderItem`. `REMOVE`: при удалении `Order` удаляются `OrderItem`. Не ставить `ALL` на связях «многие» к независимым сущностям (`User` → `Role`) — удаление пользователя не должно удалять роли. Без каскада нужно вручную persist/remove дочерние.

## Q21. Как использовать `@Query` с `SpEL`?

В **@Query** можно использовать **SpEL**: `#{#entityName}` — имя сущности репозитория; `#{#root.args[0]}` — аргументы метода. Пример: `@Query("select e from #{#entityName} e where e.name = ?1")`. Полезно для базовых репозиториев и переиспользуемых запросов.

`#{#entityName}` подставляется из имени сущности репозитория (например, `User` → `"User"`). В абстрактном репозитории один и тот же запрос работает для разных сущностей с полем name. `SpEL` вычисляется при создании запроса.

## Q22. Что такое `Soft Delete` и как реализовать?

**Soft Delete** — запись не удаляется, а помечается (поле **deleted = true** или **deletedAt**). Реализация: поле в сущности + **@Where(clause = "deleted = `false`")** (`Hibernate`) или **@SQLRestriction("`deleted_at` is `null`")** (`Hibernate 6+`). При запросах фильтр применяется автоматически.

Уникальные индексы должны включать `deletedAt` или условный уникальный индекс (`WHERE deleted_at IS NULL`), иначе нельзя создать вторую запись с тем же ключом после удаления первой. При soft delete устанавливать `deletedAt` = now() вместо физического `DELETE`.

## Q23. Как настроить второуровневый кэш (`L2 cache`)?

Подключить провайдер (`Ehcache`, `Hazelcast` и т.д.), в **application.properties**: **spring.jpa.properties.hibernate.cache.use_second_level_cache=true**, **region.factory_class**. Пометить сущности **@Cacheable** и **`@Cache`(usage = `CacheConcurrencyStrategy.READ_WRITE`)**. Для коллекций — **@Cache** на связи. Кэш действует в рамках `SessionFactory`.

Провайдер: `Ehcache` 3 — `hibernate.javax.cache.provider`; `Redis` через `Redisson` или `Hazelcast`. Стратегия READ_WRITE для частых обновлений, READ_ONLY для справочников. Для коллекций кэш хранит id; при загрузке коллекции подгружаются сущности из кэша или БД.

## Q24. Что такое `FlushMode` и когда менять?

**FlushMode** определяет, когда `Hibernate` синхронизирует persistence context с БД. **AUTO** (по умолчанию) — перед запросом и при commit. **COMMIT** — только при commit. При массовых операциях иногда временно выставляют `COMMIT` и вручную вызывают **flush()**, **clear()** по батчам для экономии памяти.

`AUTO` перед каждым запросом синхронизирует контекст — иначе запрос может не увидеть незакоммиченные изменения. Для батч-вставок: `COMMIT` и явный flush по батчам; `MANUAL` не используют в типичных сценариях.

## Q25. Как работать с наследованием сущностей (`JPA Inheritance`)?

Стратегии: **SINGLE_TABLE** (одна таблица, дискриминатор `DTYPE`), **JOINED** (таблица на класс, `JOIN` по `PK`), **TABLE_PER_CLASS** (таблица на конкретный класс). Репозиторий объявляют для базового класса; запросы возвращают подтипы.

SINGLE_TABLE — полиморфные запросы без `JOIN`; nullable колонки подтипов. `JOINED` — нормализация, больше `JOIN` при запросах. TABLE_PER_CLASS — полиморфные запросы через `UNION`. Выбор по частоте полиморфных запросов и объёму общих полей.

## Q26. Что такое `@Embedded` и `@Embeddable`?

**@Embeddable** — класс без собственной идентичности (`Value Object`), встраивается в сущность. **@Embedded** — поле сущности такого типа. Колонки маппятся в таблицу владельца. Используется для адреса, денег, периода и т.п.

Встраиваемый класс не имеет `@Id`. Несколько `@Embedded` одного типа — переименовать колонки через **@AttributeOverrides** (`billing_street`, `shipping_street`). Для неизменяемых value object удобно **record** (`Java 16+`) с `@Embeddable`.

## Q27. Как использовать custom repository implementation?

Создать интерфейс с суффиксом **Custom** (например, **UserRepositoryCustom**) и реализацию с суффиксом **Impl** (например, **UserRepositoryCustomImpl**). Базовый репозиторий расширяет этот интерфейс: **interface `UserRepository` extends `JpaRepository`<`User`, `Long`>, UserRepositoryCustom**. `Spring` находит `Impl` по имени и подмешивает кастомные методы.

Интерфейс: `interface `UserRepositoryCustom` { `List`<`User`> `findWithComplexLogic`(...); }`. Реализация: `class `UserRepositoryCustomImpl` implements UserRepositoryCustom`. Кастомный постфикс: **`@EnableJpaRepositories`(`repositoryImplementationPostfix` = "`CustomImpl`")**.

## Q28. Что такое derived delete и `deleteBy`?

**Derived delete** — методы вида **deleteByStatus(`Status` s)** или **removeByCreatedAtBefore(`LocalDate` date)**. `Spring Data` генерирует `DELETE` или `SELECT` + delete по сущностям (зависит от версии). Возвращать можно **void** или **long** (число удалённых). Транзакция обязательна.

В некоторых версиях derived delete выполняет `SELECT` + delete по сущностям (N запросов). Для bulk delete предпочтительнее **`@Modifying @Query`("delete from `User` u where `u.status` = ?1")** — один запрос. **clearAutomatically = true** очищает persistence context после выполнения.

## Q29. Как тестировать `Spring Data JPA` репозитории?

Использовать **@DataJpaTest** — поднимается слой `JPA` и встроенная БД (**H2**) по умолчанию или **Testcontainers** (`PostgreSQL`). В тестах: **@Autowired** репозиторий, сохранять сущности, вызывать методы и проверять через **assertThat(repository.findAll())**.

Для реальной БД — `@Container` с образом `PostgreSQL` и `@DynamicPropertySource` для подстановки URL БД в конфиг приложения.

## Q30. Какие best practices для производительности `JPA`?

**Краткий ответ:** LAZY, явная загрузка через `JOIN FETCH`/`@EntityGraph`, батчинг, DTO/проекции вместо полных сущностей; индексы на часто запрашиваемые колонки. `L2 cache` для справочников; мониторинг медленных запросов (`spring.jpa.show-sql` в dev, `Hibernate` statistics).

Использовать `LAZY` и загружать связи явно (`EntityGraph`, `JOIN FETCH`). Избегать N+1. Применять пагинацию для больших выборок. Батчить запись и настраивать `batch_size`. Выбирать только нужные поля (проекции). Индексы в БД под частые условия и `JOIN`. Кэш `L2` для редко меняющихся данных. Профилировать запросы (логирование `SQL`, метрики). Включить `spring.jpa.show-sql` (или логирование `org.hibernate.SQL`) для отладки; в prod — метрики `Hibernate` (number of queries, slow queries). Индексы в БД под `WHERE` и `JOIN`; анализировать explain plan. Избегать select * при больших сущностях — проекции. Пагинация: `Pageable` в методе репозитория; не использовать без limit для больших таблиц.
