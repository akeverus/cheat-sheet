## Q1. Что такое Spring Modulith и какую проблему он решает?

Spring Modulith — библиотека для построения **модульных монолитов** на Spring Boot: она даёт коду явные внутренние границы и не позволяет им размываться.

**Какую боль лечит.** В обычном монолите все классы технически видны друг другу. Со временем это вырождается в «большой ком грязи» (Big Ball of Mud): один модуль начинает дёргать внутренние классы другого, появляются циклические зависимости, и сделать это можно случайно — компилятор не возражает. В итоге монолит невозможно ни понять, ни безопасно распилить.

**Что предлагает Spring Modulith.** Модульный монолит — это по-прежнему один деплоируемый артефакт (одна сборка, один процесс; общая база — обычная практика, а не требование библиотеки), но с явными границами между модулями, изоляцией внутренней реализации и зависимостями, которые можно **проверить тестом**. Нарушил границу — упал тест, а не «узнали через год».

**Почему это ценно:**
- Дисциплина границ, как у микросервисов, но без их инфраструктурной цены (сеть, отдельные деплои, распределённые транзакции).
- Архитектура не деградирует незаметно: правила проверяются автоматически.
- Готовый плацдарм для будущей декомпозиции — модуль превращается в кандидата на отдельный сервис.
- Проверкой границ дело не ограничивается: в проекте есть надёжная связь модулей событиями с реестром публикаций (Q6), генерация документации по модулям (Q10) и интеграция с наблюдаемостью.

**Сценарий применения.** Промежуточный шаг между монолитом и микросервисами: когда хочется навести порядок в монолите, не платя сразу за распределённую систему.


## Q2. Как Spring Modulith определяет модуль?

Модуль определяется **по структуре пакетов, без какой-либо аннотации на самом модуле**. Каждый пакет первого уровня (top-level) рядом с классом `@SpringBootApplication` Spring Modulith считает отдельным модулем — по умолчанию границы выводятся из layout-а, а не перечисляются вручную (стратегию обнаружения меняет свойство `spring.modulith.detection-strategy`: при значении `explicitly-annotated` модулями считаются только пакеты, помеченные `@ApplicationModule`).

```
com.example.shop                ← корневой пакет
├── ShopApplication.java       ← класс с @SpringBootApplication
├── order/                     ← модуль Order
│   ├── OrderService.java      ← public API (доступен другим модулям)
│   └── internal/              ← закрытая реализация
│       └── OrderRepository.java
├── inventory/                 ← модуль Inventory
└── notification/              ← модуль Notification
```

**Как устроена видимость:**
- Классы прямо в корне пакета модуля (`order/OrderService.java`) — это его **публичный API**, видимый другим модулям.
- Всё во вложенных пакетах модуля (`order/internal/...`) — закрытая реализация: технически это обычные `public`-классы Java, но Spring Modulith считает их приватными для модуля. Закрыт при этом любой вложенный пакет, а не только названный `internal`: это лишь распространённое соглашение об имени, а открыть отдельный подпакет соседям можно явно, через `@NamedInterface` (см. Q13).

**Почему это важно.** Если из `inventory/` обратиться к `order/internal/OrderRepository`, код скомпилируется (для JVM это публичный класс), но `verify()` распознает это как нарушение границы и завалит проверку. Так модель «публичный API против внутренностей» становится исполняемым правилом, а не договорённостью на словах.


## Q3. Как проверить соблюдение архитектурных правил Spring Modulith в CI?

Правила проверяются **обычным JUnit-тестом** — одной строкой `verify()`. Под капотом Spring Modulith использует ArchUnit, поэтому нарушение архитектуры падает так же, как падает любой unit-тест.

```java
@Test
void modulesAreCompliant() {
    ApplicationModules.of(ShopApplication.class).verify();
}
```

`verify()` проверяет как минимум:
- **Нет обращений к внутренним типам другого модуля** — никто не лезет во внутренности соседа (по умолчанию внутренним считается любой вложенный пакет модуля независимо от имени; `internal` — просто частое имя такого пакета).
- **Нет циклических зависимостей** между модулями — граф зависимостей остаётся ацикличным.
- **Соблюдаются явно объявленные разрешённые зависимости** — если модуль сузил их через `@ApplicationModule(allowedDependencies = ...)`, обращение мимо этого списка тоже роняет проверку.

**Что происходит при нарушении.** Метод выбрасывает исключение с человекочитаемым описанием: какой модуль, какой класс и какую границу нарушает. Тест краснеет, сборка останавливается.

**Почему держать это в CI.** Проверка ловит деградацию архитектуры в момент её появления — в пул-реквесте, а не спустя месяцы. Это дёшево (один тест) и превращает «договорённость о границах» в защиту, которую нельзя обойти по невнимательности.


## Q4. Как модули в Spring Modulith должны взаимодействовать между собой?

Есть два разрешённых способа, и ни один не залезает во внутренности соседа (обращение туда — нарушение, которое падает на `verify()` в тестах, а не блокируется компилятором):

- **Прямой вызов публичного API** — обращение к классу/интерфейсу в корне пакета модуля (не в `internal/`). Синхронно; если у вызывающего открыта транзакция, вызов идёт в ней же. Публичен по умолчанию именно корень пакета; дополнительные точки входа объявляют через `@NamedInterface`, а список разрешённых зависимостей сужают через `@ApplicationModule(allowedDependencies = ...)` (см. Q13). Подходит, когда вызывающему нужен ответ прямо сейчас (например, запросить данные).
- **События приложения** — модуль публикует событие, заинтересованные модули его слушают, без связи по типам реализации. Сама публикация синхронна, но получатель может обработать событие асинхронно и после коммита публикатора — это даёт `@ApplicationModuleListener` (см. Q5). Подходит для уведомления «случилось вот это» — публикатор не знает и не должен знать, кто отреагирует.

**Почему предпочитают события.** Прямой вызов API создаёт жёсткую зависимость «A знает про B». Событие разворачивает связь: `Order` просто сообщает «заказ размещён», а `Inventory` сам решает подписаться. Связанность падает, и впоследствии такой модуль проще вынести в отдельный сервис (событие заменяется на сообщение в брокере).

В примере ниже `Order` публикует факт, а `Inventory` реагирует — ссылок на классы реализации друг друга у них нет, общей остаётся только сам тип события `OrderPlaced`:

```java
// Модуль Order публикует событие
@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final ApplicationEventPublisher events;

    public OrderService(OrderRepository orderRepository, ApplicationEventPublisher events) {
        this.orderRepository = orderRepository;
        this.events = events;
    }

    public void placeOrder(Order order) {
        orderRepository.save(order);
        events.publishEvent(new OrderPlaced(order.getId()));
    }
}

// Событие — простой record
public record OrderPlaced(UUID orderId) {}

// Модуль Inventory подписывается
@Component
public class InventoryListener {
    private final InventoryService inventoryService;

    public InventoryListener(InventoryService inventoryService) {
        this.inventoryService = inventoryService;
    }

    @ApplicationModuleListener
    public void on(OrderPlaced event) {
        inventoryService.decreaseStock(event.orderId());
    }
}
```


## Q5. Что такое @ApplicationModuleListener и чем отличается от @EventListener?

`@ApplicationModuleListener` — это **составная аннотация-«мета»**, которая собирает в себе три настройки, нужные для надёжной связи между модулями. Под ней лежат:

- `@TransactionalEventListener` (фаза по умолчанию — `AFTER_COMMIT`) — обработчик срабатывает **только после успешного коммита** транзакции публикатора.
- `@Async` — обработка идёт в **отдельном потоке**, не блокируя публикатора. Это работает при включённой поддержке асинхронности (`@EnableAsync` или автоконфигурация стартера); без неё обработчик отработает после коммита, но в потоке публикатора.
- `@Transactional(propagation = REQUIRES_NEW)` — обработчик выполняется **в своей транзакции**, а не присоединяется к чужой.

**Зачем такая комбинация.** Она разводит две операции по разным транзакциям. Если бы слушатель работал внутри транзакции `Order` (как делает обычный `@EventListener`), то откат заказа откатил бы и побочный эффект в `Inventory` — модули оказались бы связаны на уровне транзакции. Здесь же `Inventory` реагирует только на **зафиксированный** факт и обрабатывает его независимо; падение слушателя не роняет публикатора.

**Чем отличается от `@EventListener`:**

| | `@EventListener` | `@ApplicationModuleListener` |
|---|---|---|
| Когда срабатывает | сразу при публикации | после коммита (`AFTER_COMMIT`) |
| Поток | тот же (синхронно) | отдельный (`@Async`) |
| Транзакция | та же, что у публикатора, если публикация шла в транзакции | своя |
| Изоляция модулей | низкая | высокая |

**Подводный камень.** Раз обработка асинхронная и после коммита, при падении слушателя или рестарте приложения событие может потеряться — если не включить персистентность событий (см. Q6), которая как раз закрывает этот разрыв.


## Q6. Как работает персистентность событий в Spring Modulith?

Персистентность событий решает главную слабость in-memory событий: если слушатель упал или приложение перезапустилось до обработки, событие теряется. Spring Modulith закрывает этот разрыв, **записывая событие в БД** в той же транзакции, что и доменное изменение: строка появляется на каждую пару «событие — слушатель», если этот слушатель взят библиотекой под персистентность.

Включается стартером (для JPA):

```xml
<dependency>
  <groupId>org.springframework.modulith</groupId>
  <artifactId>spring-modulith-starter-jpa</artifactId>
</dependency>
```

**Как это работает по шагам:**
1. При публикации события Spring Modulith создаёт в таблице `event_publication` по записи на каждого персистентного слушателя — это происходит **в одной транзакции** с доменной операцией (заказ и факт его публикации фиксируются атомарно).
2. После того как слушатель успешно отработал, запись помечается как завершённая — в режиме по умолчанию проставляется дата выполнения (режим настраивается свойством `spring.modulith.events.completion-mode`: обновление даты, удаление строки или перенос в архивную таблицу).
3. Незавершённые записи — это публикации, обработка которых не была доведена до конца: не начиналась, упала с ошибкой или прервалась рестартом.

При рестарте приложения такие «зависшие» события можно переиграть (в актуальных версиях свойство живёт в пространстве `spring.modulith.events.*`; прежнее `spring.modulith.republish-outstanding-events-on-restart` объявлено устаревшим и оставлено для совместимости):

```yaml
spring:
  modulith:
    events:
      republish-outstanding-events-on-restart: true
```

**Что это даёт.** Гарантию доставки **at-least-once** прямо внутри монолита, без внешнего брокера (Kafka/RabbitMQ). По сути это локальный паттерн Transactional Outbox: факт и обещание его обработать сохраняются атомарно, поэтому ничего не теряется.

**Важный нюанс.** Гарантия именно *at-least-once*, не *exactly-once* — после рестарта событие может быть обработано повторно. Поэтому слушатели должны быть **идемпотентными**.


## Q7. Как тестировать отдельный модуль Spring Modulith в изоляции?

Для этого есть аннотация `@ApplicationModuleTest`: она поднимает **только контекст текущего модуля**, а не всё приложение. Тест становится быстрым и по-настоящему изолированным — он проверяет логику одного модуля, не таща за собой соседей.

```java
@ApplicationModuleTest
class OrderModuleTests {

    @Test
    void placingOrderPublishesEvent(
            OrderService orderService,
            PublishedEvents events) {

        orderService.placeOrder(new Order(...));

        assertThat(events.ofType(OrderPlaced.class)).hasSize(1);
    }
}
```

**Что здесь происходит:**
- `@ApplicationModuleTest` сам определяет, в каком модуле лежит тест, и загружает бины только этого модуля.
- Параметр `PublishedEvents` (из Spring Modulith, его подставляет сама `@ApplicationModuleTest`) перехватывает опубликованные события — можно ассертить *что* событие было выпущено, не дёргая реальный модуль-подписчик.
- Зависимости от других модулей не поднимаются: их при необходимости мокируют (в Spring Boot 3.4+ это `@MockitoBean`, прежний `@MockBean` объявлен устаревшим).

**Почему это правильный уровень теста.** Вы проверяете контракт модуля — «при размещении заказа публикуется `OrderPlaced`» — в отрыве от того, как на это событие отреагирует `Inventory`. Реакцию соседнего модуля и сквозной сценарий проверяют отдельно (см. Scenarios API, Q9).

**Объём контекста.** Он регулируется режимом bootstrap (см. Q8): по умолчанию — строго один модуль, а какие именно зависимости к нему добавить, задаёт выбранный режим.


## Q8. Какие режимы bootstrap существуют в @ApplicationModuleTest?

Режим bootstrap управляет тем, **какую часть графа модулей** поднимать для теста. Это компромисс между скоростью/изоляцией и полнотой проверки: чем больше грузим, тем реалистичнее, но медленнее и менее изолированно.

| Режим | Что загружается | Когда выбирать |
|-------|-----------------|----------------|
| `STANDALONE` | Только текущий модуль (по умолчанию) | unit-уровень модуля, максимальная изоляция и скорость |
| `DIRECT_DEPENDENCIES` | Модуль + его прямые зависимости | модулю реально нужны бины соседей, от которых он зависит |
| `ALL_DEPENDENCIES` | Весь транзитивный граф зависимостей | проверка цепочки модулей целиком |

```java
@ApplicationModuleTest(mode = BootstrapMode.DIRECT_DEPENDENCIES)
class OrderIntegrationTests { ... }
```

**Эмпирическое правило.** Начинайте со `STANDALONE` (по умолчанию) и поднимайтесь по уровням только когда тесту не хватает реальных бинов соседних модулей. Чем шире bootstrap — тем медленнее тест и тем меньше остаётся той самой модульной изоляции, ради которой всё затевалось.


## Q9. Что такое Scenarios API и для чего он нужен?

Scenarios API — высокоуровневый **DSL для тестирования событийных сценариев** между модулями. Он решает конкретную проблему: события из `@ApplicationModuleListener` обрабатываются *асинхронно* и *после коммита*, поэтому наивный тест («дёрнули метод — сразу проверили результат») гоняется с реальностью и флакает. Scenarios API умеет **дождаться** нужного события, прежде чем проверять. Параметр `Scenario` (`org.springframework.modulith.test.Scenario`) подставляет расширение `@ApplicationModuleTest`, а сам класс приезжает со стартером `spring-modulith-starter-test` в тестовой области.

Читается как фраза: «**подай** стимул → **дождись** события такого-то типа → **проверь** его»:

```java
@ApplicationModuleTest
class OrderScenarios {

    @Test
    void orderPlacedTriggersNotification(Scenario scenario) {
        scenario
            .stimulate(() -> orderService.placeOrder(order))
            .andWaitForEventOfType(NotificationSent.class)
            .toArriveAndVerify(event ->
                assertThat(event.orderId()).isEqualTo(order.getId()));
    }
}
```

**Чем он лучше ручного теста.** Без него пришлось бы вручную писать `Awaitility` или `Thread.sleep`, ловить таймауты и бороться с флакающими прогонами. Scenarios API инкапсулирует это ожидание: `andWaitForEventOfType(...).toArriveAndVerify(...)` держит тест до прибытия события и только потом выполняет проверку. Ожидание не безымянное: под ним тот же Awaitility, а его предел настраивается у самого сценария — например, `customize(factory -> factory.atMost(Duration.ofSeconds(2)))`. Поэтому он — основной инструмент для сквозной проверки связки «публикация → асинхронный `@ApplicationModuleListener` → результат».


## Q10. Как визуализировать зависимости между модулями?

Spring Modulith умеет **генерировать диаграммы и документацию из самой структуры кода** — модель модулей у него уже есть, нужно лишь её отрисовать. Это держит карту архитектуры в синхроне с реальностью: диаграмма строится по коду, а не рисуется руками и не устаревает.

Простейший вариант — распечатать модель в консоль; полноценный — сгенерировать PlantUML:

```java
// Вывод в консоль
ApplicationModules modules = ApplicationModules.of(ShopApplication.class);
modules.forEach(System.out::println);

// Генерация PlantUML-диаграмм (требует spring-modulith-docs)
new Documenter(modules)
    .writeModulesAsPlantUml()
    .writeIndividualModulesAsPlantUml();
```

`ApplicationModules` — это `Iterable<ApplicationModule>`, поэтому модель можно просто обойти и напечатать; в том же тесте обычно вызывают и `modules.verify()`.

- `writeModulesAsPlantUml()` — общая диаграмма всех модулей и их связей.
- `writeIndividualModulesAsPlantUml()` — по диаграмме на каждый модуль (его зависимости крупным планом).

Для этого нужен отдельный артефакт, и объявляют его с `<scope>test</scope>` — именно область, а не место запуска, держит его вне рантайм-classpath; саму генерацию гоняют из теста или шага CI:

```xml
<dependency>
  <groupId>org.springframework.modulith</groupId>
  <artifactId>spring-modulith-docs</artifactId>
  <scope>test</scope>
</dependency>
```

**Сценарий применения.** Запускать генерацию из теста или в CI — тогда актуальная диаграмма архитектуры всегда лежит в репозитории и обновляется вместе с кодом.


## Q11. Когда использовать Spring Modulith, а когда — микросервисы?

Ключевой вопрос: **нужна ли вам независимость масштабирования, деплоя и данных, или достаточно дисциплины границ внутри одного приложения?** Если хватает второго — модульный монолит даёт почти всю пользу микросервисов без их цены.

**Spring Modulith подходит, если:**
- Команда небольшая (2–10 разработчиков) и работает над одним деплоем — координация дешевле, чем сетевые контракты.
- Нужны явные границы, но не хочется платить за накладные расходы микросервисов: сеть и её отказы, эксплуатация нескольких деплой-пайплайнов, версионирование контрактов, распределённые транзакции.
- Планируется *постепенный* переход к микросервисам — модули станут готовыми линиями реза для будущей декомпозиции.

**Микросервисы нужны, если:**
- Компоненты надо **масштабировать независимо** (один грузит CPU, другой — память).
- Разные команды требуют **независимого цикла деплоя** — не хотят релизиться через общий артефакт.
- Нужна **изоляция данных на уровне БД** (отдельные схемы или базы), а не просто разделение кода.

**Компромисс.** Микросервисы покупают независимость ценой распределённой системы (сеть, согласованность, эксплуатация). Модульный монолит обычно живёт в одном процессе и на одной базе, но это архитектурный выбор команды, а не ограничение библиотеки: за хранилище Spring Modulith не отвечает, он проверяет границы кода. Взамен подход требует дисциплины, чтобы границы не размылись, и поддерживать её помогает `verify()`.


## Q12. Как Spring Modulith облегчает переход к микросервисам?

Главная идея: хорошо изолированный модуль **уже имеет ту же форму, что и сервис** — публичный контракт снаружи, скрытая реализация внутри, явные зависимости. Поэтому декомпозиция превращается из рискованного распутывания клубка в механическую замену механизма связи.

Соответствие «модуль → микросервис»:
- **Публичный API модуля** → REST/gRPC-контракт сервиса (граница для вызова уже определена — её нужно лишь вынести за процесс).
- **События приложения** (`ApplicationEventPublisher` и `@ApplicationModuleListener`) → сообщения в Kafka/RabbitMQ (роли издателя и подписчика сохраняются, но гарантии меняются: внутрипроцессная атомарность события и транзакции уступает место доставке at-least-once, поэтому обработчики делают идемпотентными).
- **Вложенные пакеты модуля** уже скрыты по умолчанию, публичен только корень пакета (имя `internal` — лишь конвенция) — приватную реализацию не придётся выпутывать из чужих обращений.
- **Зависимости между модулями** уже явны и проверены `verify()` — вы заранее знаете весь граф связей и не наткнётесь на скрытую ссылку при распиле. Гарантия действует ровно настолько, насколько тест с `ApplicationModules.of(App.class).verify()` реально гоняется в CI.

**Почему это снимает главный риск.** Самое дорогое при распиле монолита — обнаружить, что модули переплетены сильнее, чем казалось. Spring Modulith не даёт этой запутанности накопиться: границы чёткие с самого начала, поэтому в графе вызовов при декомпозиции сюрпризов нет — при условии, что `verify()` гоняется в CI. Отдельно остаётся то, чего структурная проверка не видит: общая схема БД, транзакции поперёк модулей, циклы через события.


## Q13. Что такое Named Interface в Spring Modulith и зачем он нужен?

Named Interface — это способ **дать модулю несколько именованных точек входа** вместо одной общей.

По умолчанию публичный API модуля — это весь корень его пакета: всё, что лежит прямо в `order/`, видно соседям, а вложенные подпакеты соседям недоступны вовсе. Для маленького модуля это нормально, но у большого появляются разные грани — публичный API, типы событий, конфигурация — и хочется, чтобы соседи зависели только от нужной грани, а не от модуля целиком.

Named Interface объявляется на пакете (через `package-info.java`), и таким объявлением подпакет как раз **открывается** соседям — но уже под собственным именем. Начиная со Spring Modulith 1.2 аннотацию можно ставить и на отдельный тип; тогда в грань попадает именно этот тип, а объявление через `package-info.java` остаётся основным способом:

```java
@org.springframework.modulith.NamedInterface("api")
package com.example.shop.order.api;
```

**Что это даёт:**
- Другой модуль может объявить зависимость от конкретной грани — `@ApplicationModule(allowedDependencies = "order :: api")` на своём пакете, а не от всего `order`.
- Остальные грани модуля для него закрываются, и поверхность зависимости сужается до объявленного контракта. Работает это только для того, кто объявил `allowedDependencies`: соседу без такого объявления по-прежнему видны все грани и корень пакета.

**Зачем это нужно.** Чем уже точка входа, тем меньше способов на неё опереться «не туда» и тем проще потом эволюционировать или выносить модуль. Для крупных модулей с несколькими аспектами (API, events, config) это превращает один большой публичный пакет в набор аккуратных, явно поименованных контрактов.


## Q14. Как включить Spring Modulith в существующий Spring Boot проект?

Внедрять можно **инкрементально** — не нужно переписывать проект, прежде чем получить пользу. Порядок шагов:

1. **Добавить зависимость** `spring-modulith-starter-core`.
2. **Запустить `ApplicationModules.of(App.class).verify()`** в тесте — он упадёт и выдаст агрегированный список уже имеющихся нарушений: обращения к внутренностям, циклы. Просто осмотреть структуру, ничего не роняя, можно печатью самой модели (см. Q10).
3. **Зафиксировать проверку в CI** — сразу после первого прогона, не дожидаясь чистого кода: так новые нарушения перестают появляться.
4. **Параллельно, а не после, чинить накопленные нарушения** — переносить детали реализации в `internal/`, убирать нежелательные зависимости и циклы. Делать это можно по одному модулю за раз, при уже работающей проверке.

**Почему такой порядок ценен.** Даже до того, как вы вычистили *все* старые нарушения, поставленная в CI проверка уже работает как храповик: архитектура перестаёт деградировать дальше. Вы стопорите ухудшение сразу, а долг разгребаете постепенно — это и есть главное преимущество перед «большим переписыванием».


## Q15. Как Spring Modulith соотносится с Hexagonal Architecture и DDD?

Spring Modulith — это **технический механизм для границ**, который сам по себе не диктует стиль, но хорошо ложится и на DDD, и на Hexagonal: он даёт исполняемое воплощение их идей на уровне пакетов Java.

**С DDD.** Модуль естественно отображается на **Bounded Context**: публичный API — это контракт контекста, а вложенные пакеты (по конвенции `internal/`) — его собственная модель, скрытая от остальных. Правило структурное, а не именное: внутренним считается любой вложенный подпакет, а открыть часть его соседям можно только именованным интерфейсом. Разница в том, что у DDD bounded context — концепция на словах, а Spring Modulith делает границу **проверяемой**: `verify()` роняет тест, если один контекст лезет во внутренности другого (компилятору такое обращение по-прежнему безразлично).

**С Hexagonal Architecture (Ports & Adapters).** Аналогия на уровне модуля: публичный API модуля играет роль **входящего порта** — контракта, через который с модулем говорят снаружи. Всё, что скрыто во вложенных пакетах, — внутреннее устройство контекста: и его доменная модель (ядро гексагона), и адаптеры, которыми она ходит наружу.

**Важная оговорка.** Spring Modulith **не навязывает** конкретную внутреннюю структуру модуля — он следит только за границами *между* модулями. Хотите ли вы внутри модуля раскладывать код по гексагональным слоям или нет — ваше дело; библиотека с этим совместима, но не требует.
