# Вопросы на собеседовании: `Cloud-native Patterns`

**Cloud-native** — приложения, спроектированные под облако (а не перенесённые методом lift-and-shift): контейнеризованные, динамически оркестрируемые, построенные на микросервисах. Паттерны: **12-factor**, **sidecar**, **circuit breaker**, **retry**, **bulkhead**, **leader election**, **autoscaling**, **service mesh**. Стандарты: проекты **CNCF** (K8s, Prometheus, Envoy, ...).

## Q1. (!) Что такое cloud-native?

**Cloud-native** — подход, при котором приложение с самого начала проектируют под облако, а не просто переносят туда готовый монолит. Ключевое слово — *проектируют*: приложение рассчитано на динамику облака (инстансы появляются и исчезают, нагрузка скачет, отказ узла — норма), а не борется с ней.

Складывается из набора взаимосвязанных свойств:
- **Containers** — единица упаковки и доставки
- **Microservices** — приложение разбито на независимые сервисы
- **Dynamic orchestration** — Kubernetes управляет жизненным циклом инстансов
- **DevOps-практики** — CI/CD, инфраструктура как код
- **Declarative APIs** — описываем *желаемое* состояние, а не шаги его достижения
- **Loosely coupled** — сервисы слабо связаны и развиваются независимо
- **Resilient** — корректно переживают сбои соседей
- **Observable** — наружу выведены metrics, logs, traces

Эти свойства поддерживают друг друга: микросервисы требуют оркестрации, оркестрация требует контейнеров, динамика инстансов требует resilience и observability.

**Определение CNCF:**
> "Cloud native technologies empower organizations to build and run scalable applications in modern, dynamic environments such as public, private, and hybrid clouds."

**Где проходит граница:** просто перенести монолит в облако методом lift-and-shift — это *не* cloud-native. Монолит, запущенный в EC2, остаётся монолитом: он не масштабируется по частям, не переживает отказ узла без простоя и не пользуется динамикой облака.

## Q2. (!) Каковы принципы 12-factor app?

**12-Factor App** (Heroku, 2012) — свод из 12 правил, как писать приложение, которое легко разворачивать, масштабировать и держать одинаковым во всех окружениях. Общая идея всех факторов одна: вынести всё изменчивое (конфиг, состояние, зависимости) наружу, чтобы сам код оставался переносимым артефактом.

1. **Codebase** — один кодбейз под контролем git, много развёртываний из него
2. **Dependencies** — зависимости объявлены явно и изолированы (package.json, requirements.txt), ничего не берётся «из системы»
3. **Config** — в env-переменных, не в коде (один и тот же образ работает в любом окружении)
4. **Backing services** — БД, очереди — это подключаемые по URL ресурсы; локальную и облачную БД можно поменять без правки кода
5. **Build, release, run** — три строго разделённых этапа; release нельзя менять на лету
6. **Processes** — процессы stateless и share-nothing; всё, что нужно сохранить, идёт во внешнее хранилище
7. **Port binding** — приложение самодостаточно и само отдаёт HTTP через порт (не зависит от внешнего веб-сервера)
8. **Concurrency** — масштабируемся, запуская больше процессов (горизонтально), а не наращивая один
9. **Disposability** — быстрый старт и корректное (graceful) завершение, чтобы инстанс можно было убить в любой момент
10. **Dev/prod parity** — окружения держим максимально похожими, чтобы «у меня работало» не превращалось в баг на проде
11. **Logs** — пишем в stdout как поток событий; сбор и хранение — забота инфраструктуры, не приложения
12. **Admin processes** — разовые задачи (миграции, скрипты) запускаем как отдельные процессы в той же среде

**Современные дополнения** ("Beyond 12-factor", Pivotal):
- API first — контракт API проектируем до реализации
- Telemetry — телеметрия как обязательная часть приложения
- Authentication and authorization — встроены, а не прикручены сбоку

## Q3. (!) Что такое CNCF?

**Cloud Native Computing Foundation** (CNCF) — vendor-нейтральный фонд (часть Linux Foundation), который курирует ключевые cloud-native-проекты с открытым кодом. Смысл его существования — чтобы стандарты облачной инфраструктуры не принадлежали одному вендору: проект живёт в фонде, а не под контролем конкретной компании.

Проекты проходят зрелость по стадиям **Sandbox → Incubating → Graduated**; статус *Graduated* означает, что проект проверен временем и production-ready.

**Известные проекты CNCF (Graduated):**
- **Kubernetes** — оркестрация
- **Prometheus** — мониторинг
- **Envoy** — прокси
- **gRPC** — RPC
- **Helm** — пакетный менеджер K8s
- **Containerd** — container runtime
- **etcd** — распределённое key-value-хранилище
- **Argo** — CI/CD, workflows
- **Linkerd**, **Istio** — service mesh
- **Vitess** — распределённый MySQL
- **Open Policy Agent (OPA)** — политики
- **Flux** — GitOps
- **Cilium** — сеть, eBPF
- **Harbor** — реестр контейнеров

Всего 100+ активных проектов — по сути, de facto стандарты cloud-native-стека.

## Q4. (!) Что такое sidecar pattern?

**Sidecar** — вспомогательный контейнер, который живёт в том же pod, что и приложение, и добавляет ему функциональность, не вмешиваясь в код. Работает за счёт того, что контейнеры одного pod делят сетевое пространство (`localhost`) и volumes — поэтому sidecar видит трафик и файлы приложения как свои.

```
Pod
├── App container (main business logic)
└── Sidecar container (logging, proxy, ...)
   - Shares network namespace
   - Shares volumes
```

**Типичные применения:**
- **Logging sidecar** — собирает логи из приложения
- **Service mesh proxy** (Envoy в Istio) — управляет трафиком
- Sidecar для обновления конфигурации (**config refresh**)
- **TLS termination**
- **Vault Agent** — инъекция секретов
- **Metrics exporter** для Prometheus

**Плюсы:** общая идея — вынести инфраструктурную заботу из приложения:
- Разделение ответственности (приложение занято только бизнес-логикой)
- Переиспользование одного и того же sidecar без правки приложения
- Разные циклы релизов (sidecar обновляют отдельно)
- Разные команды могут владеть приложением и sidecar независимо

**Минус:** каждый sidecar — это дополнительный контейнер на *каждый* pod, то есть лишний CPU/память в масштабе кластера.

## Q5. Что такое ambassador pattern?

**Ambassador** — это частный случай sidecar, который проксирует **исходящие** (outbound) соединения приложения к внешним сервисам. Приложение ходит к `localhost`, а ambassador берёт на себя всю сложность общения с реальной сетью: retry, авторизацию, мониторинг, шифрование.

```
App → Ambassador (handles retry, auth, monitoring) → External service
```

Суть в том, что приложение «думает», что общается с простым локальным сервисом (`localhost:8080`), и остаётся наивным — вся сетевая логика вынесена в ambassador.

**Сценарии применения:**
- Клиентская часть service mesh (Envoy)
- Sidecar для пулинга соединений с БД
- Sidecar-API-gateway для исходящих вызовов

## Q6. Что такое adapter pattern?

**Adapter** — это sidecar, который **приводит вывод приложения к стандартному формату**, ожидаемому внешней системой. Если ambassador стандартизирует *исходящие вызовы*, то adapter стандартизирует *то, что приложение отдаёт наружу* (логи, метрики). Полезен, когда менять само приложение нельзя или дорого (например, legacy).

```
App (custom format) → Adapter → Standardized output
                                   (Prometheus metrics, ELK logs)
```

**Сценарии применения:**
- Legacy-приложение пишет логи в своём формате → adapter преобразует их в JSON для logging-стека
- Приложение отдаёт метрики в своём формате → adapter выставляет их в формате Prometheus

## Q7. Что такое init containers?

**Init containers** — это контейнеры, которые запускаются **до** основного контейнера, выполняют подготовительную работу и завершаются. Основной контейнер не стартует, пока все init-контейнеры не отработают успешно — это гарантирует, что окружение готово.

```yaml
spec:
  initContainers:
    - name: db-migrate
      image: my-app
      command: ["./migrate.sh"]
  containers:
    - name: app
      image: my-app
```

**Сценарии применения:**
- Миграции базы данных
- Ожидание готовности зависимостей
- Подготовка volumes / конфигов
- Загрузка данных

Если init-контейнер падает, pod перезапускается — то есть подготовка надёжно блокирует запуск приложения в неготовом окружении.

## Q8. (!) Что такое circuit breaker?

**Circuit breaker** («предохранитель») защищает от каскадных сбоев: если downstream-сервис начинает стабильно отказывать, бьёт смысл не долбить его и не копить зависшие запросы, а быстро отдавать ошибку (fail fast). По аналогии с электрическим предохранителем — он размыкает цепь, чтобы перегрузка не пошла дальше.

**Три состояния:**
- **Closed** — всё хорошо, вызовы идут как обычно (счётчик ошибок копится)
- **Open** — порог ошибок превышен; все вызовы сразу падают, реального обращения к сервису нет (даём ему время восстановиться)
- **Half-open** — по истечении таймаута пробуем 1-2 вызова: если ОК → возвращаемся в closed, если снова сбой → обратно в open

```python
@circuit_breaker(failure_threshold=5, recovery_timeout=60)
def call_payment_service(order):
    return requests.post(payment_url, json=order)
```

**Инструменты:** Hystrix (legacy), Resilience4j, Polly (.NET), встроенные средства service mesh.

Подробнее — в [Resilience Patterns](../architecture/resilience-patterns-interview.md).

## Q9. (!) Как работает retry с exponential backoff?

**Retry с exponential backoff** — повтор неудачного вызова с *экспоненциально растущей* паузой между попытками (2s, 4s, 8s, ...). Растущая пауза нужна, чтобы не добивать сервис, который и так под нагрузкой: каждая следующая попытка даёт ему больше времени восстановиться.

```python
@retry(
    stop=stop_after_attempt(5),
    wait=wait_exponential(multiplier=1, min=2, max=60)
)
def call_service():
    return requests.get(...)
```

**Схема задержек:** 2s → 4s → 8s → 16s → 60s (рост капается на max).

**Рекомендации:**
- **Jitter** (случайная добавка к паузе) — чтобы клиенты не синхронизировались и не ударили все разом
- Только идемпотентные операции (или с idempotency-ключами) — иначе повтор продублирует эффект (двойное списание и т.п.)
- Повторять только **временные** (transient) ошибки (5xx, таймауты), но не 4xx — клиентскую ошибку повтор не исправит
- Ограничивать общее число попыток / время, иначе ретраи сами станут источником нагрузки

**Подводный камень:** ретраи без jitter дают эффект *thundering herd* — 1000 клиентов одновременно бьются в упавший сервис, и каждая синхронная волна ретраев только усиливает шторм. Именно поэтому jitter — не опция, а необходимость.

## Q10. (!) Что такое bulkhead?

**Bulkhead** («переборка») — изоляция ресурсов, чтобы сбой в одной части системы не съел ресурсы, нужные другим. Название — из судостроения: корпус корабля делят на герметичные отсеки, и пробоина в одном не топит весь корабль.

**Как это работает:** разным downstream-сервисам выделяют отдельные пулы ресурсов (например, потоков). Если один сервис зависнет и исчерпает свой пул, другие останутся с собственными ресурсами и продолжат работать.

```
Service A: thread pool 10 (для users API)
Service B: thread pool 5 (для analytics)

Если analytics dies → users API не affected
```

Без bulkhead зависший analytics мог бы выбрать *все* общие потоки, и users API лёг бы вместе с ним — это и есть тот каскад, который паттерн предотвращает.

**В K8s** роль переборок играют лимиты ресурсов на каждый pod (CPU, memory): один pod не может «съесть» всю ноду.

## Q11. Что такое timeout и deadline propagation?

**Timeout на каждый внешний вызов обязателен.** Без таймаута зависший downstream-вызов держит поток/соединение бесконечно, и эти зависшие запросы копятся, пока не исчерпают ресурсы — отсюда и каскадные отказы.

```python
requests.get(url, timeout=5)
```

**Deadline propagation** — это проброс *оставшегося* времени (дедлайна) вниз по всей цепочке вызовов. Каждый следующий сервис получает не свой произвольный таймаут, а остаток от общего бюджета времени клиента:

```
Client request: 10 sec timeout
  → Service A: пропускает remaining 8 sec timeout
    → Service B: пропускает remaining 5 sec timeout
      → Database: 2 sec timeout
```

Смысл — не тратить ресурсы на работу, результат которой клиент уже не дождётся: если до дедлайна осталось 2 секунды, нет смысла начинать запрос к БД с таймаутом 10. В **gRPC** дедлайны встроены и пробрасываются автоматически; в REST это делают через заголовки (`X-Request-Deadline`).

## Q12. Чем различаются health checks: liveness, readiness, startup?

Kubernetes использует три типа проб, и ключ к ответу — они отвечают на *разные вопросы* и вызывают *разную реакцию*:

- **Liveness** — «процесс жив или завис?» Если проба падает → контейнер **перезапускается**. Лечит зависшие/мёртвые процессы.
- **Readiness** — «готов ли контейнер принимать трафик прямо сейчас?» Если падает → pod **убирают из load balancer** (но НЕ перезапускают). Лечит временную неготовность (БД недоступна, прогрев) без лишних рестартов.
- **Startup** — «завершился ли долгий старт?» Пока startup-проба не прошла, liveness/readiness **приостановлены**. Нужна для медленно стартующих приложений, чтобы liveness не убил их раньше времени.

```yaml
livenessProbe:
  httpGet: { path: /health, port: 8080 }
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
startupProbe:
  httpGet: { path: /startup, port: 8080 }
  failureThreshold: 30  # 5 minutes для startup
```

**Рекомендация:**
- Liveness — держать простым (только «жив ли процесс»); если завязать его на зависимости, упавшая БД вызовет лавину бессмысленных рестартов
- Readiness — наоборот, проверять зависимости (соединение с БД), чтобы трафик не шёл на неготовый инстанс
- Startup — использовать для приложений с долгим прогревом

## Q13. (!) Почему stateless-приложения так важны?

**Stateless-приложение** не хранит состояние локально (в памяти или на диске инстанса) — каждый запрос обрабатывается независимо, и любой инстанс эквивалентен любому другому. Именно эта эквивалентность и делает облачные операции тривиальными:

- **Horizontal scaling** — масштабировать просто, инстансы клонируются без раздумий
- **Простая замена** — инстанс умер → поднимаем новый, ничего не теряя
- **Load balancing** — любой инстанс обслужит любой запрос, балансировщику не нужно помнить, кто кого обслуживал
- **Rolling updates** — заменяем инстансы по одному без простоя
- **Auto-scaling** работает без оговорок

Состояние при этом никуда не исчезает — его просто выносят во внешнее хранилище:
- База данных (PostgreSQL, DynamoDB)
- Кэш (Redis)
- Объектное хранилище (S3)
- Хранилище сессий (Redis, JWT в cookie)

**Подводный камень:** если состояние всё же держать в памяти инстанса, появляются *sticky sessions* (пользователя привязывают к конкретному инстансу), и всё перечисленное выше ломается — масштабирование и замена инстансов становятся болезненными.

## Q14. Что такое session state externalization?

**Session state externalization** — вынос состояния сессии из памяти сервера в общее хранилище, чтобы приложение оставалось stateless (см. Q13). Если сессия лежит в памяти инстанса, обслужить пользователя сможет только этот инстанс — что и порождает sticky sessions. Решение — хранить сессию там, где её видят все инстансы.

Два основных подхода:

```
Option 1: Server-side sessions в Redis
  Cookie: session_id=abc123
  Backend reads Redis: SET session:abc123 {...}

Option 2: Stateless via JWT
  Cookie: jwt=eyJhbGc...
  Backend validates signature, no lookup
```

**Компромисс по JWT:**
- **Плюс** — самодостаточен: бэкенд проверяет подпись, без похода в БД, масштабируется неограниченно
- **Минус** — токен трудно отозвать (revoke) до истечения срока: он валиден, пока не протухнет

Поэтому в **2025** на практике обычно **комбинируют**: JWT как короткоживущий access token (его не нужно отзывать — он быстро протухнет) плюс refresh token + Redis, через который и реализуют отзыв.

## Q15. (!) Что такое leader election?

**Leader election** — механизм, которым несколько одинаковых инстансов сервиса договариваются, кто из них «лидер» и единственный выполняет некую эксклюзивную задачу. Нужен потому, что в stateless-мире инстансы идентичны и масштабируются, но есть работа, которую нельзя делать параллельно (иначе будут дубли или гонки): cron должен сработать один раз, миграция — один раз.

**Сценарии применения:**
- Cron-задачи (запускает только один инстанс)
- Миграции базы данных
- Прогрев кэша
- Координационные задачи

**Инструменты:**
- **Kubernetes leader election** (через ConfigMap / Lease objects)
- Распределённый лок в **etcd**
- **ZooKeeper**
- **Redis Redlock** (с осторожностью)
- **Consul**

```python
# K8s leader election (Python kubernetes client)
from kubernetes.leaderelection import leaderelection

def run_when_leader():
    while True:
        do_cron_job()
        time.sleep(60)

candidate = leaderelection.Candidate(name="my-app")
leader_election = leaderelection.LeaderElection(
    candidate, run_when_leader, ...
)
```

## Q16. Что такое distributed locking?

**Distributed lock** — это мьютекс, действующий не внутри одного процесса, а между несколькими инстансами/машинами: только один владелец лока в каждый момент выполняет защищённый участок. Это более общий механизм, чем leader election (Q15): leader election — частный случай долгоживущего лока на роль лидера.

**Инструменты:**
- **Redis** — `SET NX EX 60` (setNX с TTL) или **Redlock**
- **etcd** — строгая согласованность, на основе lease
- **ZooKeeper** — эфемерные узлы
- **База данных** — `SELECT ... FOR UPDATE`

**Подводный камень:** распределённые локи надёжно реализовать тяжело (часовые рассинхроны, сбои сети, истёкший TTL у ещё работающего владельца). По возможности их избегают — проектируют операции *идемпотентными*, чтобы повтор был безопасен и лок был не нужен.

```python
# Redis simple lock
def acquire_lock(key, timeout=60):
    return redis.set(key, "locked", nx=True, ex=timeout)

if acquire_lock("my-task"):
    try:
        do_task()
    finally:
        redis.delete("my-task")
```

## Q17. (!) Чем горизонтальное масштабирование отличается от вертикального?

Коротко: **vertical** — сделать одну машину мощнее, **horizontal** — добавить больше машин. Разница в том, где упирается потолок и какой ценой даётся рост.

**Vertical (scale-up):**
- Машина мощнее (больше CPU, RAM)
- Есть жёсткий предел — самый крупный доступный тип VM
- Требует перезапуска (то есть простоя при апгрейде)
- **Плюс:** нет проблемы распределения трафика — инстанс по-прежнему один

**Horizontal (scale-out):**
- Больше машин (инстансов)
- Практически без ограничений по росту
- Без простоя — добавление инстансов идёт rolling
- **Условие:** приложение должно быть stateless (см. Q13), иначе клонировать инстансы нельзя

**Вывод для cloud-native:** по умолчанию выбирают **горизонтальное** — оно эластично, без простоя и без потолка; за это платят требованием stateless и наличием балансировки.

```yaml
# K8s HPA (Horizontal Pod Autoscaler)
apiVersion: autoscaling/v2
spec:
  minReplicas: 2
  maxReplicas: 100
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

## Q18. По каким триггерам срабатывает auto-scaling?

Автоскейлинг добавляет/убирает инстансы, когда выбранная метрика выходит за порог. Какую метрику взять — зависит от того, чем именно ограничен сервис (CPU, память или внешняя нагрузка):

- **Загрузка CPU** (> 70%) — классика для CPU-bound сервисов
- **Загрузка памяти** — для memory-bound
- **Кастомные метрики** (глубина очереди, частота запросов) — когда узкое место не в железе, а в обработке
- **Внешние метрики** (Kafka consumer lag, размер очереди SQS) — масштабируемся по объёму невыполненной работы
- **По расписанию** — для заранее известных, предсказуемых паттернов нагрузки

**KEDA (Kubernetes Event-driven Autoscaling)** расширяет это до **30+ источников событий**, позволяя масштабироваться прямо по очередям (вплоть до нуля инстансов, когда работы нет):
- Kafka, Redis, RabbitMQ
- Облачные очереди (SQS, Service Bus, Pub/Sub)
- Кастомный HTTP

## Q19. Чем reactive-масштабирование отличается от predictive?

Разница — в моменте реакции. **Reactive** добавляет инстансы *после* того, как метрика уже достигла порога; **predictive** — *заранее*, опираясь на прогноз нагрузки.

**Reactive** (проще, по факту):
- HPA с порогами по CPU
- KEDA по длине очереди
- Минус — есть лаг (секунды-минуты на старт новых инстансов), и во время этого лага пользователи уже ощущают деградацию

**Predictive** (на упреждение):
- AWS Predictive Scaling (на основе ML)
- Собственное прогнозирование для известных паттернов
- Плюс — мощности готовы *к* всплеску, а не разворачиваются *после* него; минус — сложнее и зависит от точности прогноза

**Что на практике:** в **2025** большинство берёт **reactive** + ручное масштабирование по расписанию для предсказуемых пиков (например, начало рабочего дня) — это покрывает большинство случаев без сложности ML.

## Q20. (!) Что такое три столпа observability: metrics, logs, traces?

Три столпа observability отвечают на разные вопросы о системе, поэтому и дополняют друг друга: метрики говорят *что* сломалось, логи — *почему*, трейсы — *где* в цепочке сервисов.

**Metrics** — числовые агрегаты (counters, gauges, histograms). Отвечают на «что происходит» (растёт ли error rate, какая латентность).
- Prometheus, Datadog, CloudWatch
- Большой объём, низкая кардинальность (дёшево хранить и агрегировать)

**Logs** — дискретные события с контекстом. Отвечают на «почему именно это произошло» (стектрейс, конкретные значения).
- ELK, Loki, CloudWatch Logs, Datadog Logs
- Большой объём, высокая кардинальность

**Traces** — путь одного запроса через все сервисы. Отвечают на «где в распределённой цепочке узкое место/ошибка».
- Jaeger, Zipkin, X-Ray, Datadog APM
- Сэмплируются (хранить трейс каждого запроса слишком дорого)

**Вывод:** ни один столп не заменяет другие — production-системе нужны все три, и сила в их связке (по метрике замечаем аномалию → по трейсу находим виновный сервис → по логам понимаем причину).

Подробнее — в [Observability](../monitoring/observability-interview.md).

## Q21. Что такое OpenTelemetry?

**OpenTelemetry (OTel)** — стандарт CNCF, который задаёт *единый* способ собирать metrics, logs и traces вне зависимости от вендора. Главная боль, которую он решает: раньше инструментация была завязана на конкретный бэкенд (Datadog, New Relic...), и смена вендора означала переписывать код. OTel разрывает эту связь.

```
Apps → OpenTelemetry SDK → OTel Collector → Backend (Datadog, Honeycomb, ...)
```

**Преимущества:**
- **Одна инструментация — много бэкендов**: меняем backend через конфиг Collector, не трогая код приложения
- SDK для **множества языков**
- **Авто-инструментация** для популярных библиотек (HTTP, DB, gRPC) — телеметрия почти без ручной разметки

**Зрелость компонентов** (различается):
- **Tracing** — зрелый
- **Metrics** — стабильны
- **Logs** — новее остальных

В **2025** OTel — **стандарт де-факто** для новых проектов, вытесняющий vendor-специфичную инструментацию.

## Q22. Что такое service mesh (Istio, Linkerd)?

**Service mesh** — инфраструктурный слой, который берёт на себя всё межсервисное взаимодействие, чтобы это не приходилось писать в каждом сервисе. Реализуется через sidecar-прокси (Envoy): прокси встаёт рядом с каждым сервисом и перехватывает весь его трафик, добавляя поверх сетевые возможности прозрачно для кода:

- **Управление трафиком** — маршрутизация, load balancing, circuit breaker
- **Безопасность** — mTLS, авторизация
- **Observability** — metrics, traces, logs

Ключевая идея — эти возможности появляются *без изменения кода сервисов*: их даёт прокси, а не приложение.

**Топология** (две плоскости):
- **Data plane** — рядом с каждым сервисом стоит свой `Sidecar`-прокси: `App A` → `Sidecar` ←→ `Sidecar` → `App B`. Весь трафик между `App A` и `App B` идёт через эту пару прокси, а не напрямую.
- **Control plane** — оба `Sidecar`-прокси подключены к общему `Control Plane` (управляющая связь): он раздаёт им конфигурацию, политики маршрутизации и безопасности, сертификаты для mTLS.

**Инструменты:**
- **Istio** — богатый функционал, сложный
- **Linkerd** — проще, легче
- **Consul Connect** — HashiCorp
- **Cilium Service Mesh** — на eBPF, без sidecar'ов

**Компромисс:** service mesh добавляет сложности (доп. латентность, операционные накладные расходы) в обмен на преимущества.

В **2025** многие берут **только mTLS + телеметрию** (через Linkerd или Cilium), без полной сложности Istio.

## Q23. (!) Что такое blue-green deployment?

**Blue-green deployment** — стратегия выката, при которой одновременно держат две полные среды: **Blue** (текущий production) и **Green** (новая версия). Трафик переключают с blue на green разом, мгновенно. Смысл — сделать релиз бинарным событием (переключил/откатил) и убрать промежуточные состояния.

```
Time 1: Blue serves 100% traffic, Green idle
Time 2: Deploy new version to Green
Time 3: Test Green
Time 4: Switch traffic Blue → Green
Time 5: If issues, instant rollback (switch back)
```

**Компромисс:**
- **Плюс** — мгновенный откат: что-то пошло не так → переключаем трафик обратно на blue (среда никуда не делась)
- **Минус** — на время деплоя нужна **двойная** инфраструктура (обе среды запущены), то есть выше стоимость

**В K8s** реализуется через services: меняем selector, чтобы маршрутизировать трафик на blue- или green-набор подов.

Подробнее — в [Deployment Strategies](../cicd/deployment-strategies-interview.md).

## Q24. (!) Что такое canary deployment?

**Canary deployment** — выкат новой версии *постепенно*: сначала на ней обслуживают крошечную долю трафика, и при отсутствии проблем долю наращивают. Название — от «канарейки в шахте»: маленькая группа пользователей первой принимает на себя риск, и если что-то не так, пострадают единицы, а не все.

```
Day 1: 1% traffic → new version
Day 2: 5%
Day 3: 25%
Day 4: 50%
Day 5: 100%
```

На каждом шаге следят за метриками (error rate, латентность); при ухудшении — откат, не доводя до 100%. В этом и отличие от blue-green: blue-green переключает всех разом, canary ограничивает радиус поражения, жертвуя мгновенностью.

**Инструменты:**
- **Argo Rollouts** — canary, нативный для K8s
- **Flagger** — автоматизированный canary
- **Service mesh** (Istio, Linkerd) — разделение трафика

**Рекомендация:** настроить **авто-откат** по порогам метрик, чтобы деградацию ловил не человек, а сама система.

## Q25. Что такое feature flags?

**Feature flags** — переключатели, которые включают/выключают фичу в рантайме, без передеплоя. Код новой фичи уже задеплоен, но «спит» за флагом — поведением управляют через конфиг, а не через выкат.

```python
if feature_flag("new_checkout_flow", user=current_user):
    return new_checkout()
else:
    return old_checkout()
```

**Сценарии применения:**
- Постепенный раскат (10% → 50% → 100%)
- Kill switch — мгновенно выключить сломанную фичу, не дожидаясь нового деплоя
- A/B-тестирование
- Таргетинг по пользователю / сегменту

**Инструменты:**
- **LaunchDarkly** (популярный SaaS)
- **Unleash** (open-source)
- **Flagsmith**, **GrowthBook**, **Statsig**

**Главная идея:** флаги **развязывают деплой и релиз** — код можно выкатить в любой момент, а *включить* фичу для пользователей отдельным действием (и так же быстро выключить). Это снижает риск релизов и сегодня считается лучшей практикой.

## Q26. Что такое GitOps?

**GitOps** — подход, при котором *желаемое состояние* инфраструктуры описано декларативно и хранится в Git как единственный источник истины, а специальный агент непрерывно приводит кластер к этому состоянию. Развороты происходят не командой «задеплой», а коммитом в Git — Git становится пультом управления инфраструктурой.

```
Developer commits manifest changes к git
  ↓
GitOps tool (Argo CD, Flux) detects change
  ↓
Auto-syncs cluster к desired state в git
```

**Принципы:**
1. Декларативные конфигурации (K8s-манифесты, Helm) — описываем *что* хотим, не *как* достичь
2. Контроль версий (Git) — состояние хранится и версионируется в репозитории
3. Автоматическая синхронизация — агент сам применяет изменения
4. Непрерывный мониторинг — агент ловит *дрейф* (когда реальное состояние разошлось с Git) и возвращает кластер к описанному

**Инструменты:**
- **Argo CD** — самый популярный, с web UI
- **Flux** (CNCF) — упор на автоматизацию

**Что это даёт** (всё вытекает из «Git — источник истины»):
- **Audit trail** — вся история изменений инфраструктуры в git
- Простой откат — `git revert` возвращает прошлое состояние
- Согласование через PR review — изменения инфраструктуры проходят ревью как код
- Самовосстановление — обнаружение дрейфа и авто-возврат к описанному состоянию

## Q27. (!) Как устроен configuration management в cloud-native?

Базовый принцип — из 12-factor (Q2): конфигурация живёт **в окружении (env-переменных), а не в коде**. Цель — чтобы один и тот же образ без пересборки работал в dev, staging и prod, меняя поведение только через подставленный конфиг.

```bash
DATABASE_URL=postgres://...
REDIS_URL=redis://...
LOG_LEVEL=info
```

**В K8s** конфиг отделяют от образа через объекты кластера:
- **ConfigMaps** — несекретная конфигурация
- **Secrets** — чувствительные данные (пароли, токены)
- **External Secrets Operator** — синхронизация секретов из Vault, AWS Secrets Manager

**Разделение по окружениям** (один образ, разный конфиг):
- Свои ConfigMaps на каждое окружение
- Helm values, Kustomize-оверлеи
- Параметры Argo CD

**Жёсткое правило: никогда не коммитьте секреты в git.** Для них — внешнее хранилище (см. Q28).

## Q28. Как устроен secrets management?

**Secrets management** — это хранение, доставка и контроль доступа к чувствительным данным (паролям, токенам, ключам) так, чтобы они никогда не оседали в коде, образах или git. K8s Secrets сами по себе лишь base64, не шифрование — поэтому в продакшене за реальное хранение отвечает выделенное хранилище.

**Инструменты:**
- **HashiCorp Vault** — стандарт уровня enterprise
- **AWS Secrets Manager**
- **Azure Key Vault**
- **GCP Secret Manager**
- **Sealed Secrets** — нативно для K8s, секрет хранится в git в зашифрованном виде
- **External Secrets Operator** — синхронизация внешнего хранилища с K8s Secrets

**Рекомендации:**
- **Ротация** — периодическая авто-смена секретов (украденный секрет недолго остаётся валидным)
- **Аудит-логирование** — фиксировать, кто и когда обращался к секрету
- **Least privilege** — выдавать IAM-доступ только тем, кому он реально нужен
- **Шифрование** — и at rest, и in transit
- **Никаких секретов в открытом виде** — ни в env-переменных Docker-образов, ни в git

## Q29. (!) Какие частые анти-паттерны cloud-native?

Большинство анти-паттернов — это нарушение принципов из вопросов выше: либо сервисы связали слишком сильно (теряем независимость), либо проигнорировали resilience (теряем устойчивость к сбоям), либо нарушили stateless/12-factor (теряем эластичность):

1. **Distributed monolith** — микросервисы с сильной связанностью (худшее от обоих миров: сложность распределённости без её гибкости)
2. **Общая база данных** между сервисами — скрытая связанность через схему
3. **Синхронные цепочки** — A → B → C → D, где сбой одного звена валит всю цепь (каскадные сбои)
4. **Нет circuit breaker'ов** — единичный сбой расходится каскадом (см. Q8)
5. **Stateful-pods** без StatefulSet — состояние теряется при пересоздании
6. **Захардкоженные конфиги** в образах — нарушение 12-factor (Q27)
7. **Логирование в файлы** вместо stdout — инфраструктура не может собрать логи
8. **Нет health checks** — K8s не знает, жив ли и готов ли pod (Q12)
9. **Нет лимитов ресурсов** — один pod съедает всю ноду (нет bulkhead, Q10)
10. **Образы без тегов** (`latest`) — невоспроизводимые деплои
11. **Деплои «всё разом»** без canary/blue-green — нет ограничения радиуса поражения
12. **Нет observability** — production работает как чёрный ящик
13. **Ручные деплои** вместо GitOps — нет аудита и воспроизводимости
14. **Не тестируются бэкапы** — бэкап, который не восстанавливали, нельзя считать рабочим

## Q30. Что описывает cloud-native maturity model?

**Cloud-native maturity model** (CNCF) — шкала зрелости, которая показывает, насколько глубоко организация освоила cloud-native: от «просто упаковали в контейнеры» до «непрерывно улучшаем через chaos engineering и ML». Уровни идут по нарастанию — каждый опирается на предыдущий.

**Level 1 — Build** (научились собирать и доставлять):
- Контейнеризация приложений
- Контроль версий
- Базовый CI/CD

**Level 2 — Operate** (научились надёжно эксплуатировать):
- Оркестрация контейнеров (K8s)
- Централизованное логирование
- Базовый мониторинг

**Level 3 — Scale** (научились масштабировать и наблюдать):
- Авто-масштабирование
- Service mesh
- Продвинутая observability (трейсинг)
- GitOps

**Level 4 — Improve** (научились проактивно улучшать):
- Chaos engineering
- Операции на основе ML
- Полная автоматизация

**Где все находятся:** в **2025** большинство компаний — на Level 1-2, а зрелые игроки (Netflix, Spotify, Airbnb) — на Level 3-4.
