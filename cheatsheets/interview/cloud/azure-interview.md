## Q1. (!) Что такое Azure?

`Microsoft Azure` — публичное облако Microsoft, запущенное в 2010 году. Это провайдер №2 в мире после AWS (~24% рынка в 2025). Главная идея позиционирования: Azure побеждает там, где у компании уже есть инфраструктура Microsoft — его сила не в отдельных сервисах, а в бесшовной связке с тем, что enterprise уже использует.

**Сильные стороны** (и почему именно они):
- **Интеграция с enterprise** — учётки из локального Active Directory синхронизируются в Entra ID, единый вход в Office 365 и облако. Для крупной компании это снимает целый класс задач по управлению идентичностью.
- **Гибридное облако** — Azure Arc и Azure Stack позволяют управлять on-prem-серверами теми же инструментами, что и облаком. Важно тем, кто не может или не хочет уходить из дата-центра полностью.
- **AI** — эксклюзивное партнёрство с OpenAI: модели GPT доступны как Azure OpenAI Service внутри enterprise-периметра.
- **Экосистема .NET** — для C#/Windows-нагрузок Azure исторически лучший дом: SDK, тулинг и интеграция с Visual Studio здесь первоклассные.
- **Compliance** — один из самых широких каталогов сертификаций, что критично для госсектора и здравоохранения.

**Слабые стороны на фоне AWS:**
- UI/UX менее согласован — много legacy-сервисов с разной логикой.
- Документация сложнее в навигации.
- Слабее интегрирована экосистема open-source.
- Надёжность — случались заметные сбои (известные outages, в т. ч. в Entra ID и DNS).

## Q2. (!) Как устроены Subscriptions и Resource Groups?

```
Tenant (Entra ID directory)
  ├── Management Group: Production
  │   ├── Subscription: app-prod
  │   │   └── Resource Group: webapp-rg
  │   │       ├── App Service
  │   │       └── SQL Database
  │   └── Subscription: app-prod-data
  └── Management Group: Development
      └── Subscription: app-dev
```

Azure выстраивает ресурсы в чёткую иерархию из четырёх уровней — снизу вверх: ресурс → Resource Group → Subscription → Management Group, и всё это под одним Tenant (каталогом Entra ID).

- **Subscription** — граница биллинга и квот, аналог отдельного AWS-аккаунта. Счёт выставляется по подписке; в ней же действуют лимиты на количество ресурсов.
- **Resource Group (RG)** — логический контейнер внутри подписки. **Любой** ресурс обязан лежать в какой-то RG; ресурсов «вне группы» не бывает.
- **Management Group** — объединяет подписки в дерево, чтобы применять политики (Azure Policy) и RBAC сразу ко множеству подписок.
- **Tenant** — каталог Entra ID, корень всей иерархии и граница идентичности организации.

**Зачем такая группировка.** Resource Group — это не просто папка: у неё общий жизненный цикл. Удаление RG за одну операцию сносит все ресурсы внутри — удобно для временных окружений (создал стенд → удалил группу). По RG также удобно считать стоимость и навешивать теги.

## Q3. Regions и Availability Zones?

Это три уровня географической отказоустойчивости Azure: зона доступности защищает от отказа одного дата-центра, регион — географическая единица размещения, пара регионов — защита от катастрофы в целом регионе.

- **Region** — географическая зона размещения (East US, West Europe). Регионов более 60 — больше, чем у любого другого облака. Регион выбирают по близости к пользователям, требованиям к резидентности данных и доступности нужных сервисов.
- **Availability Zone (AZ)** — физически отдельный дата-центр (свои питание, охлаждение, сеть) внутри региона. В регионах с поддержкой AZ их минимум 3. Разнося реплики приложения по разным зонам, переживаешь отказ целого ДЦ без даунтайма.
- **Region pair** — Azure заранее связывает регионы в пары (например East US ↔ West US) для disaster recovery: гео-реплицируемые сервисы по умолчанию копируют данные в парный регион, а обновления платформы катятся в паре по очереди.

**Подводный камень.** Не все регионы поддерживают AZ — старые регионы их не имеют. Прежде чем закладывать zone-redundant-архитектуру, проверь, что выбранный регион зоны поддерживает.

## Q4. (!) Что такое Azure VMs и как выбирать серию?

**Azure Virtual Machines** — сервис IaaS: ты получаешь виртуальную машину с полным контролем над ОС, как AWS EC2. Платишь за время работы и берёшь на себя обновления и настройку. На собеседовании важно знать две оси выбора: серию VM (под какой ресурс «затачивать») и модель тарификации (как сэкономить).

**Серии VM — по тому, какой ресурс в дефиците:**
- **B** (Burstable) — копит кредиты CPU в простое и тратит на всплесках; для неравномерной нагрузки и dev-сред.
- **D** (General purpose) — сбалансированная «рабочая лошадка» для большинства приложений.
- **F** (Compute optimized) — больше CPU на единицу памяти; для нагрузок, упирающихся в процессор.
- **E** (Memory optimized) — много RAM; для крупных БД и кэшей в памяти.
- **L** (Storage optimized) — быстрый локальный NVMe/SSD; для нагрузок с интенсивным дисковым I/O.
- **N** (GPU) — ускорители для ML, рендеринга, инференса.
- **H** (HPC) — высокопроизводительные вычисления (моделирование, симуляции).

**Тарификация — от дороже-гибче к дешевле-с-условиями:**
- **Pay-as-you-go** — поминутная оплата без обязательств; максимум гибкости, максимум цена.
- **Reserved Instances** — обязательство на 1–3 года в обмен на скидку до 72%; для стабильной базовой нагрузки.
- **Spot VMs** — свободные мощности со скидкой до 90%, но Azure может забрать их в любой момент; только для прерываемых задач (batch, рендер).
- **Hybrid Benefit** — переносишь уже купленные лицензии Windows/SQL Server в облако, не платя за них повторно.

## Q5. (!) Что даёт AKS (Azure Kubernetes Service)?

**AKS** — управляемый Kubernetes: Azure берёт на себя control plane (API-сервер, etcd, scheduler), а ты отвечаешь только за worker-узлы и сами рабочие нагрузки. Это снимает основную операционную боль Kubernetes — обслуживание мастеров.

**Ключевые особенности:**
- **Бесплатный control plane** — платишь только за worker-узлы (как и в GKE). Управляемые мастера ничего не стоят.
- **Интеграция с Entra ID** — аутентификация в кластере через корпоративные учётки + RBAC Azure поверх Kubernetes RBAC.
- **Автомасштабирование** — Cluster Autoscaler добавляет/убирает узлы под нагрузку.
- **Сеть на выбор** — Azure CNI (поды получают IP прямо из VNet, проще интеграция) или kubenet (экономнее по адресам).
- **Multi-zone-кластеры** — узлы разносятся по зонам доступности ради отказоустойчивости.
- **Windows-контейнеры** — редкая для управляемого Kubernetes возможность, важна для legacy .NET Framework.

**На фоне GKE:** GKE традиционно считают чуть более зрелым (особенно по автомасштабированию и сетям), но AKS его в основном догнал. Для компаний на стеке Microsoft AKS — естественный выбор: единый биллинг, идентичность и тулинг.

## Q6. (!) Как работают Azure Functions?

**Azure Functions** — сервис FaaS (Function-as-a-Service): пишешь функцию, она запускается в ответ на событие, а инфраструктуру (серверы, масштабирование) держит платформа. Прямой аналог AWS Lambda. Модель «событие → функция» избавляет от управления серверами и оплаты простоя.

**Планы хостинга — компромисс «цена против холодного старта»:**
- **Consumption** — платишь только за фактические выполнения, при простое не платишь ничего; настоящий serverless, но есть cold start.
- **Premium** — держит заранее прогретые инстансы, поэтому cold start устранён; за это платишь постоянно. Для нагрузок, где важна предсказуемая задержка.
- **Dedicated** (на App Service Plan) — функции крутятся на уже оплаченных VM; имеет смысл, когда App Service Plan и так есть.

**Триггеры** — что запускает функцию: HTTP-запрос, таймер (Timer), новый блоб в Blob Storage, сообщение в Queue Storage / Service Bus, событие в Event Hubs, изменение документа в Cosmos DB.

**Языки:** C#, JavaScript, Python, Java, PowerShell, плюс Rust/Go через custom handler.

```csharp
[FunctionName("HelloHttp")]
public static IActionResult Run(
    [HttpTrigger(AuthorizationLevel.Anonymous, "get")] HttpRequest req)
{
    return new OkObjectResult("Hello");
}
```

**Durable Functions** — расширение для stateful-воркфлоу: оркестрация цепочек функций, fan-out/fan-in, ожидание человека в процессе. Аналог AWS Step Functions, но логика пишется кодом, а не в JSON.

## Q7. (!) Что такое App Service?

**App Service** — управляемый PaaS для веб-приложений и API: ты деплоишь код или контейнер, а платформа берёт на себя ОС, веб-сервер, патчи и масштабирование. Промежуточный уровень между «голой» VM (всё настраиваешь сам) и Functions (только функция, без долгоживущего процесса). Подходит для классических веб-приложений, которым нужен постоянно работающий сервер.

**Что даёт из коробки:**
- **Автомасштабирование и балансировка** — по метрикам или расписанию.
- **CI/CD** — встроенная интеграция с GitHub Actions и Azure DevOps.
- **Свои домены, SSL, аутентификация** — TLS-сертификаты и вход через Entra ID без своего кода (Easy Auth).
- **Множество языков** — .NET, Node, Java, Python, PHP.
- **Deployment Slots** — отдельные слоты (staging) для blue-green деплоя: прогреваешь новую версию в слоте и мгновенно меняешь его местами с продом, с откатом одним кликом.

**Тарифные уровни** — от Free/Shared (для проб и тестов) через Basic/Standard/Premium до Isolated (выделенное окружение в своей сети для строгого compliance).

**App Service Plan** — это и есть оплачиваемые вычислительные ресурсы (размер и число инстансов). На одном плане можно разместить несколько приложений: они делят его CPU и память — удобно для экономии, но соседи влияют друг на друга.

В **2025** App Service остаётся самым популярным выбором для **классических веб-приложений** на Azure.

## Q8. Чем различаются Container Instances и Container Apps?

Это две точки на спектре «сколько Kubernetes тебе нужно». ACI — минимум абстракции (просто запусти контейнер), Container Apps — serverless-платформа поверх Kubernetes без необходимости его знать, AKS — полный кластер под твоим контролем.

- **Container Instances (ACI)** — запуск одного контейнера без оркестрации. Стартует за секунды, нет накладных расходов на кластер. Хорош для разовых и batch-задач, где не нужны масштабирование, маршрутизация и обновления.
- **Container Apps** (с 2022) — управляемые serverless-контейнеры, «AKS без забот»: под капотом Kubernetes, KEDA (масштабирование по событиям, в т. ч. до нуля) и Dapr (паттерны микросервисов). Ты получаешь автомасштабирование, ingress и revision-деплой, но не видишь и не обслуживаешь сам кластер.

| Сервис | Сценарий применения |
|---------|----------|
| ACI | Один контейнер, batch-задачи |
| Container Apps | Микросервисы, автомасштабирование, управляемый сервис |
| AKS | Полный контроль, сложные конфигурации |

**Эмпирическое правило:** разовый контейнер → ACI; микросервисы со скейлом, но без желания админить Kubernetes → Container Apps (эквивалент GCP Cloud Run); нужен полный контроль над кластером и его экосистемой → AKS.

## Q9. (!) Какие бывают типы Azure Storage account?

**Storage account** в Azure — это не один сервис, а контейнер для нескольких видов хранилища под единым пространством имён и набором настроек (репликация, доступ, шифрование). В отличие от AWS, где Blob (S3), очереди (SQS) и таблицы (DynamoDB) — отдельные сервисы, в Azure они сгруппированы под одним аккаунтом.

**Что входит в Storage account:**
- **Blob Storage** — объектное хранилище для файлов и данных любого типа, аналог S3.
- **File Storage** — файловые шары по SMB/NFS, монтируются как сетевой диск.
- **Queue Storage** — простые очереди сообщений (не путать с более богатым Service Bus).
- **Table Storage** — простой key-value/NoSQL; legacy, тот же API доступен через Cosmos DB Table.
- **Disk Storage** — управляемые диски, подключаемые к VM.

**Типы аккаунтов** определяют, какой это «движок» под капотом:
- **Standard general-purpose v2** — стандартный аккаунт общего назначения на HDD/обычных дисках; выбор по умолчанию для большинства задач.
- **Premium Block Blob** — на SSD, для низкой задержки и высокого числа транзакций (горячие блобы).
- **Premium File Shares** — высокопроизводительные файловые шары на SSD.
- **Premium Page Blobs** — для дисков VM с интенсивным I/O.

**Рекомендация:** начинай со Standard GPv2 — он покрывает почти все случаи; на Premium переходи, только когда упёрся в задержку или IOPS.

## Q10. Какие есть уровни (tiers) Blob Storage?

Tier'ы (уровни доступа) — это компромисс между ценой хранения и ценой доступа. Логика проста: чем реже ты читаешь данные, тем дешевле их хранить, но тем дороже (и медленнее) обходится каждое обращение. Поэтому tier выбирают по ожидаемой частоте доступа.

| Tier | Сценарий применения | Стоимость |
|------|----------|------|
| **Hot** | Частый доступ | Дорогое хранение, дешёвый доступ |
| **Cool** | Редкий (≥30 дней) | Дешевле хранение, дороже доступ |
| **Cold** (с 2023) | Очень редкий (≥90 дней) | Ещё дешевле |
| **Archive** | Почти никогда | Самое дешёвое, извлечение часами |

**Важный нюанс:** Archive — оффлайн-уровень. Данные нельзя прочитать сразу: нужен rehydrate, который занимает часы. Поэтому Archive не подходит для случаев, где данные могут понадобиться срочно.

**Lifecycle management** — правила, которые автоматически перемещают блобы между tier'ами по возрасту (например, через 30 дней Hot→Cool, через 90 →Archive) и удаляют старые. Так экономия достигается без ручного вмешательства.

## Q11. (!) Что такое Azure SQL Database?

**Azure SQL Database** — управляемый (PaaS) Microsoft SQL Server: бэкапы, патчи, отказоустойчивость и масштабирование берёт на себя Azure, а ты работаешь с привычным движком SQL Server. Раз это домашняя СУБД Microsoft, в облаке Azure она интегрирована лучше всего.

**Варианты развёртывания** — по тому, насколько нужна совместимость с «полным» SQL Server:
- **Single Database** — одна изолированная БД со своими ресурсами; самый простой случай.
- **Elastic Pool** — набор БД делит общий пул ресурсов; экономно, когда у тебя много баз с разными пиками (нагрузка не совпадает по времени).
- **Managed Instance** — почти полная совместимость с локальным SQL Server (cross-database-запросы, SQL Agent, CLR); выбор для миграции legacy-приложений «как есть».

**Уровни сервиса** — как считается мощность:
- **DTU-based** (legacy) — единая абстрактная единица, связывающая CPU, память и I/O; проще, но негибко.
- **vCore-based** (рекомендуется) — раздельно платишь за ядра и за хранилище, можно применить Hybrid Benefit. Внутри есть три тира: **General Purpose** (сбалансированный), **Business Critical** (быстрый локальный SSD и in-memory, реплики для HA) и **Hyperscale** (storage scale-out до 100+ ТБ, быстрые бэкапы).

**Итог:** для запуска SQL Server в облаке Azure SQL — без вопросов лучшее место.

## Q12. (!) Что такое Cosmos DB?

**Cosmos DB** — флагманская NoSQL Azure: глобально распределённая, мультимодельная база с гарантиями задержки и доступности на уровне SLA. Главная идея — «база, которая живёт сразу в нескольких регионах»: данные реплицируются по миру, а приложение читает/пишет в ближайший регион с задержкой в единицы миллисекунд.

**Ключевые особенности:**
- **Мультимодельность** — одна СУБД под разные API: Document (Mongo, JSON), Key-Value, Column (Cassandra), Graph (Gremlin). Можно мигрировать существующее приложение, не переписывая код доступа.
- **Глобальная распределённость** — добавление региона в пару кликов, write в несколько регионов сразу (multi-master).
- **5 уровней согласованности** — Strong, Bounded staleness, Session, Consistent prefix, Eventual. Это редкая для NoSQL гибкость: выбираешь точку на шкале «согласованность ↔ задержка/доступность» под конкретный сценарий.
- **SLA 99,999%** на доступность для multi-region-записей — один из самых сильных на рынке.
- **Serverless или provisioned RU** — платишь за фактические операции либо за зарезервированную пропускную способность.

**Тарификация:** мощность измеряется в **Request Units (RU/s)** — абстрактной единице, в которую укладываются CPU, IOPS и память на операцию. Простое чтение по ключу стоит ~1 RU, тяжёлый запрос — десятки.

**Сценарии применения:** IoT, персонализация, рекомендации в реальном времени, глобальные приложения и мобильные бэкенды — везде, где нужны низкая задержка по всему миру и эластичный масштаб.

**Подводный камень по стоимости:** легко случайно зарезервировать слишком много RU/s — и счёт улетает. RU/s нужно подбирать под реальную нагрузку (или брать serverless для непредсказуемого трафика).

## Q13. Что такое Database for PostgreSQL/MySQL?

**Azure Database for PostgreSQL/MySQL** — управляемые версии популярных open-source-СУБД: Azure держит ОС, патчи, бэкапы и HA, а ты получаешь стандартный PostgreSQL или MySQL без vendor lock-in на движок. Выбор для тех, кто хочет open-source-базу, но не хочет администрировать сервер.

**Уровни** — по профилю нагрузки:
- **Burstable** — для небольших и неравномерных нагрузок (dev, малый трафик).
- **General Purpose** — сбалансированный, для большинства продакшен-задач.
- **Memory Optimized** — много RAM для тяжёлых запросов и больших рабочих наборов.
- **Hyperscale (Citus)** — только для PostgreSQL: горизонтально шардирует данные по узлам, позволяя масштабироваться за пределы одного сервера (для очень крупных БД и многоарендных SaaS).

С **2024** основное предложение — **Azure Database for PostgreSQL Flexible Server**: даёт больше контроля над конфигурацией, окнами обслуживания и зональной отказоустойчивостью, чем предыдущая модель Single Server.

## Q14. Azure Cache для Redis?

**Azure Cache for Redis** — управляемый Redis для кэширования, сессий и pub/sub. Снимает заботу о поднятии и обслуживании Redis-кластера. Аналог AWS ElastiCache и GCP Memorystore.

**Уровни** — по мере роста требований к доступности и масштабу:
- **Basic** — один узел, без SLA; только для разработки и тестов (отказ узла = потеря кэша).
- **Standard** — пара узлов с репликой и автоматическим failover; минимум для прода.
- **Premium** — кластеризация (шардинг ради масштаба), персистентность на диск, изоляция в VNet.
- **Enterprise** — фичи Redis Enterprise (модули вроде RediSearch, активная гео-репликация).

С **2024** Microsoft анонсировала **Azure Managed Redis** — preview новой версии сервиса с обновлённой архитектурой.

## Q15. (!) Что такое VNet и NSG?

Это два базовых строительных блока сети в Azure: VNet задаёт изолированное адресное пространство, NSG фильтрует трафик внутри него.

- **VNet (Virtual Network)** — изолированная виртуальная сеть с собственным диапазоном IP, разбитая на подсети. Аналог AWS VPC. Ресурсы внутри VNet общаются приватно, наружу выходят только через явно настроенные шлюзы.
- **NSG (Network Security Group)** — набор allow/deny-правил по IP, порту и протоколу, аналог firewall. Совмещает роли AWS Security Groups и NACLs: применяется и к подсети, и к сетевому интерфейсу VM. В примере ниже подсеть `data` закрыта от интернета именно правилами NSG.

```
VNet (10.0.0.0/16)
  ├── Subnet: web (10.0.1.0/24) + NSG-web
  ├── Subnet: app (10.0.2.0/24) + NSG-app
  └── Subnet: data (10.0.3.0/24) + NSG-data (no internet)
```

**Application Security Groups (ASG)** — позволяют писать правила NSG не по IP-адресам, а по логическим группам VM (например, «web», «db»). Машина включается в ASG — и правила к ней применяются автоматически, без правки IP-списков при масштабировании.

## Q16. Чем различаются Application Gateway и Front Door?

У Azure четыре балансировщика, и выбор между ними сводится к двум вопросам: на каком уровне работаем (L7 HTTP или L4 TCP/UDP) и какой масштаб нужен (один регион или весь мир).

- **Application Gateway** — L7-балансировщик (понимает HTTP) **в пределах одного региона**. Умеет маршрутизацию по URL-пути (path-based routing), терминацию SSL и встроенный WAF. Берут, когда нужно умно распределять HTTP-трафик между сервисами внутри региона.
- **Azure Front Door** — **глобальный** L7-балансировщик плюс CDN. Через anycast направляет пользователя в ближайший здоровый регион, делает multi-region failover при отказе, тоже даёт WAF и терминацию SSL. Берут для глобальных приложений и распределения нагрузки между регионами.
- **Load Balancer** — L4 (TCP/UDP), без понимания HTTP; для не-веб-трафика и высокопроизводительной балансировки на сетевом уровне.
- **Traffic Manager** — балансировка на уровне DNS: отдаёт клиенту разные IP по геолокации/приоритету/весам ещё до установления соединения.

**Эмпирическое правило:** HTTP в одном регионе → Application Gateway; HTTP по всему миру → Front Door; не-HTTP → Load Balancer; маршрутизация на уровне DNS → Traffic Manager.

## Q17. (!) Entra ID (бывший Azure AD)?

**Microsoft Entra ID** (так с 2023 называется Azure Active Directory) — облачный провайдер идентичности: единая система для входа, проверки и авторизации пользователей и сервисов. Это центр всей безопасности Azure — и одновременно ключевое конкурентное преимущество Microsoft, потому что у enterprise учётки сотрудников уже живут здесь (через Office 365).

**Возможности:**
- **SSO** — единый вход в тысячи SaaS-приложений: пользователь логинится один раз корпоративной учёткой.
- **Conditional Access** — гранулярные политики доступа («с неуправляемого устройства из-за рубежа — требовать MFA») — основа Zero Trust.
- **MFA** — многофакторная аутентификация встроена.
- **Passwordless** — вход без пароля по FIDO2-ключам и биометрии.
- **B2B / B2C** — приглашение внешних партнёров (B2B) и идентичность для конечных клиентов приложения (B2C).
- **Identity Governance** — управление жизненным циклом доступа и периодические access reviews (кому что всё ещё нужно).

**Связь с ресурсами Azure:** доступом к ресурсам управляет RBAC, а identities для него берутся именно из Entra ID. Команда ниже назначает пользователю роль на конкретный storage-аккаунт.

```bash
az role assignment create --assignee user@contoso.com \
  --role "Storage Blob Data Reader" --scope /subscriptions/.../my-storage
```

## Q18. Что такое Managed Identities?

**Managed Identity** — это identity в Entra ID, которую Azure автоматически создаёт и обслуживает для ресурса (VM, App Service, Function). Она решает классическую проблему «где хранить пароль к базе/ключ к storage»: вместо секрета в коде или конфиге ресурс получает identity, а платформа сама выдаёт и ротирует токены. Секретов в коде нет вообще — это видно в примере ниже (`DefaultAzureCredential` берёт токен у платформы).

```csharp
// No credentials в коде!
var credential = new DefaultAzureCredential();
var blobClient = new BlobServiceClient(uri, credential);
```

**Два типа — по тому, кому принадлежит identity:**
- **System-assigned** — создаётся для конкретного ресурса и удаляется вместе с ним (1:1). Проще, когда identity нужна только этому ресурсу.
- **User-assigned** — отдельный самостоятельный объект, который можно навесить сразу на несколько ресурсов и переживший их. Удобно, когда группе сервисов нужны одинаковые права.

Эквивалент **AWS IAM Roles for EC2/Lambda** или **GCP Service Accounts**.

## Q19. (!) Что такое Synapse Analytics?

**Azure Synapse Analytics** — единая платформа для аналитики больших данных: объединяет хранилище данных (DWH), big-data-обработку на Spark и интеграцию данных в одном рабочем пространстве. Идея — не собирать аналитический стек из разрозненных сервисов, а получить их связанными «из коробки».

**Что входит:**
- **Synapse SQL** — аналитическое хранилище данных (DWH), конкурент Snowflake.
- **Apache Spark pools** — управляемые кластеры Spark для big-data-трансформаций и ML.
- **Data Explorer** (движок Kusto) — для логов и телеметрии.
- **Pipelines** — интеграция и оркестрация данных (тот же движок, что в Data Factory).

**Synapse SQL бывает двух видов — по модели оплаты и сценарию:**
- **Dedicated SQL pool** — заранее зарезервированное (provisioned) хранилище с предсказуемой производительностью; для постоянной аналитической нагрузки.
- **Serverless SQL pool** — запросы прямо к файлам в Azure Storage без загрузки в DWH, оплата за объём просканированных данных; для разовых исследований и data lake.

В **2025** Synapse — ответ Microsoft на BigQuery и Snowflake, но у него есть проблемы с надёжностью и UX. Поэтому Microsoft активно продвигает **Microsoft Fabric** — новую объединённую платформу, и многие новые проекты выбирают её.

## Q20. Что такое Azure Data Factory?

**Azure Data Factory (ADF)** — управляемый сервис для ETL/ELT: оркестрирует перемещение и трансформацию данных между источниками по расписанию или событию. Его главная фишка — низкий порог входа: pipeline'ы собираются мышкой, без написания кода. Аналог AWS Glue и GCP Cloud Data Fusion.

**Особенности:**
- **Визуальный UI** — pipeline собирается из блоков drag-and-drop.
- **90+ коннекторов** — к облачным и on-prem-источникам (БД, SaaS, файлы).
- **Mapping Data Flows** — трансформации без кода, под капотом исполняются на Spark.
- **Кастомные activities** — где нужно, подключается код на Python/Spark.
- **CI/CD** — pipeline'ы версионируются и деплоятся как код.

В **2025** Microsoft продвигает **Microsoft Fabric** (новую объединённую платформу), но ADF всё ещё широко используется и остаётся движком интеграции данных внутри Synapse и Fabric.

## Q21. Чем различаются Event Hubs и Service Bus?

Оба передают сообщения, но решают разные задачи. Главное различие — модель потребления: Event Hubs это поток событий (читатели двигают свой offset, событие никуда не «исчезает»), а Service Bus это очередь команд (сообщение забрали и обработали).

**Event Hubs** — высокопроизводительный стриминг событий, аналог Apache Kafka.
- Миллионы событий в секунду.
- Партиции и consumer groups: одни и те же данные независимо читают несколько потребителей, каждый со своим offset.
- Совместимость с протоколом Apache Kafka (на уровне Premium) — можно подключать Kafka-клиентов без переписывания.

**Service Bus** — enterprise-обмен сообщениями, аналог RabbitMQ.
- Очереди (Queues, точка-точка) и темы (Topics, pub/sub).
- Богатая семантика: транзакции, сессии (упорядоченная обработка по ключу), dead-letter для проблемных сообщений.
- Протокол AMQP 1.0.
- Пропускная способность ниже, чем у Event Hubs — но он и не про объём, а про надёжную доставку каждого сообщения.

| Сервис | Сценарий применения |
|---------|----------|
| Event Hubs | Стриминг, телеметрия, IoT |
| Service Bus | Бизнес-сообщения, транзакции |

**Эмпирическое правило:** поток телеметрии/событий, где важен объём → Event Hubs; отдельные бизнес-сообщения, где важны гарантии и порядок доставки → Service Bus.

## Q22. (!) Что такое Azure OpenAI Service?

**Azure OpenAI Service** — те же модели OpenAI (GPT-4 и др.), но захостенные внутри инфраструктуры и периметра безопасности Azure. Это эксклюзив Microsoft благодаря партнёрству с OpenAI. Ключевой вопрос на собеседовании — зачем это нужно, если есть публичный API OpenAI: ответ в том, что enterprise не может отправлять чувствительные данные во внешний сервис, а здесь модель работает в его контролируемом окружении.

**Преимущества против прямого OpenAI API:**
- **Enterprise-compliance** — соответствие GDPR, HIPAA, SOC.
- **Доступ через частную сеть** — без выхода данных в публичный интернет.
- **Customer-managed keys (BYOK)** — шифрование своими ключами.
- **Данные не используются для обучения OpenAI** — твои промпты и ответы не утекают в обучающую выборку.
- **SLA и поддержка** — через Microsoft, с корпоративным договором.

**Сценарий:** банк или клиника хочет GPT-4, но по требованиям безопасности не может слать данные в публичный OpenAI API. Azure OpenAI снимает это ограничение.

В **2025** это самый популярный способ для enterprise использовать модели OpenAI.

## Q23. Что такое Azure Machine Learning?

**Azure ML** — управляемая платформа для полного жизненного цикла ML: от обучения и трекинга экспериментов до деплоя и мониторинга моделей в проде (MLOps). Эквивалент AWS SageMaker и GCP Vertex AI. Цель — чтобы дата-сайентисты не собирали инфраструктуру вручную, а работали в одном окружении.

**Возможности:**
- **Workspace** — единое рабочее пространство проекта, где живут данные, эксперименты и модели.
- **Вычислительные кластеры (CPU/GPU)** — эластичные ресурсы под обучение, поднимаются и гасятся по запросу.
- **AutoML** — автоматический подбор модели и гиперпараметров.
- **Реестр моделей** — версионирование и управление обученными моделями.
- **Endpoints** — публикация модели как сервиса: real-time (онлайн-инференс) и batch (пакетный).
- **Интеграция с MLflow** — стандартный трекинг экспериментов.
- **Designer** — визуальная сборка пайплайнов без кода.

В **2025** конкурирует с Vertex AI и SageMaker; сильная сторона — тесная интеграция с Azure DevOps и GitHub для MLOps.

## Q24. (!) В чём сильные и слабые стороны Azure по сравнению с AWS?

Коротко: Azure выигрывает там, где у компании уже есть Microsoft-стек и enterprise-контракт, но проигрывает AWS в зрелости, единообразии и прозрачности.

**Сильные стороны Azure** (и почему):
- **Интеграция с enterprise** — AD/Entra ID и Office 365 уже стоят у большинства корпораций; миграция в Azure естественна.
- **Гибридное облако** — Azure Arc и Azure Stack дают единое управление облаком и on-prem, чего у AWS меньше.
- **AI** — эксклюзивный Azure OpenAI Service: моделей OpenAI в enterprise-периметре больше нигде нет.
- **.NET, Windows, SQL Server** — лучший дом для Microsoft-нагрузок с Hybrid Benefit и первоклассным тулингом.
- **Compliance** — один из самых широких портфелей сертификаций.
- **Контракты Microsoft** — Azure часто входит в корпоративный бандл со скидкой (Enterprise Agreement).

**Слабые стороны Azure** (и почему):
- **Надёжность** — случались заметные сбои (DNS, Entra ID), репутация чуть хуже AWS.
- **Документация** — разрознена по сервисам, сложнее в навигации.
- **UI/UX** — несогласован из-за обилия legacy-сервисов.
- **Экосистема open-source** — интегрирована слабее, чем у AWS/GCP.
- **Тарификация** — запутанные единицы у разных сервисов (DTU, RU и т. п.) усложняют прогноз затрат.

## Q25. (!) Когда выбирать Azure?

Главный критерий выбора Azure — не технический, а контекстный: насколько компания уже завязана на Microsoft. Чем больше существующих инвестиций в AD, Windows и .NET, тем сильнее перевешивает Azure; для «чистого» нового проекта это редко лучший вариант.

**Выбирай Azure, когда:**
- **Уже на стеке Microsoft** (AD, Office 365, Windows-серверы) — миграция дешевле и идентичность уже там.
- Нагрузки на **.NET / SQL Server** — лучший тулинг и Hybrid Benefit на лицензии.
- **Enterprise-закупка** — Microsoft даёт Azure в бандле со скидкой.
- Нужно **гибридное облако** — Azure Arc для управления on-prem.
- Отрасль с **жёстким compliance** (здравоохранение, госсектор).
- Конкретно нужен **Azure OpenAI**.

**Не выбирай, когда:**
- Новый cloud-native проект с нуля — у AWS/GCP часто более зрелые и единообразные сервисы.
- Много Linux / open-source — экосистема лучше у AWS/GCP.
- Сильный фокус на ML/Data — чаще выбирают GCP или AWS.
- Стартап — AWS/GCP удобнее для быстрого старта, а Azure воспринимается как дорогой и «корпоративный».

В **2025** Azure — **№1 для enterprise**, но новые стартапы выбирают его редко.
