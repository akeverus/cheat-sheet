# Вопросы на собеседовании: `Serverless`

**Serverless** — модель вычислений, в которой разработчик не управляет серверами. Включает **FaaS** (Lambda, Functions), **BaaS** (Firebase, Auth0), serverless-контейнеры (Cloud Run, Container Apps), edge computing (Cloudflare Workers, Vercel Edge). На собеседовании спрашивают: когда выбирать, cold starts, стоимость, vendor lock-in.

## Q1. (!) Что такое serverless?

**Serverless** — модель облачных вычислений, при которой вы пишете и деплоите код, а серверы под ним полностью отдаёте провайдеру: их выделение, масштабирование и эксплуатацию. Ключевое слово — не «нет серверов», а «нет управления серверами».

Провайдер берёт на себя четыре вещи, которыми в классической модели занимался ты:
- **Выделение ресурсов** — по запросу (on-demand), инстансы поднимаются под трафик и гасятся в простое.
- **Масштабирование** — автоматически, от нуля до тысяч параллельных вызовов.
- **Эксплуатацию** — runtime, ОС, патчинг, сеть.
- **Биллинг по факту** — платишь за вызовы и время выполнения, а не за арендованный сервер.

Serverless — это не один продукт, а целый спектр сервисов с разной степенью «безсерверности»:
- **FaaS (Function-as-a-Service)** — твой код в виде функций, запускаемых по событиям: AWS Lambda, Azure Functions, GCP Cloud Functions.
- **Serverless-контейнеры** — твой образ, но без управления кластером: Cloud Run, AWS App Runner, Container Apps.
- **BaaS (Backend-as-a-Service)** — готовые сервисы вместо своего кода: Firebase, Auth0, Supabase.
- **Serverless-базы данных** — масштабируются и тарифицируются по нагрузке: DynamoDB, Aurora Serverless, Cosmos DB serverless.
- **Serverless-аналитика** — запрос как функция: Athena, BigQuery.
- **Edge computing** — выполнение у границы сети, близко к пользователю: Cloudflare Workers, Vercel Edge.

## Q2. (!) Serverless ≠ no servers, что это значит?

Серверы есть всегда — код где-то выполняется. «Serverless» — про то, что эти серверы скрыты от тебя: ты их не видишь, не настраиваешь и не платишь за их простой. Сервер становится деталью реализации провайдера, а не объектом твоей эксплуатации.

На практике это означает, что из твоей зоны ответственности уходит целый класс задач:
- Нет SSH в production — некуда и незачем заходить.
- Нет патчинга ОС — версии и обновления держит провайдер.
- Нет планирования ёмкости — масштабирование автоматическое (auto-scale).
- Часто нет «всегда работающих» серверов — в простое не крутится ничего, и платить не за что.

Удобно смотреть на это как на спектр от «serverful» к serverless по тому, чем именно ты управляешь:
- **IaaS** (EC2, GCE) — полный контроль: управляешь всей машиной, ОС и масштабированием.
- **Контейнеры** (ECS, Cloud Run) — управляешь образом и его конфигурацией, не машиной.
- **Serverless** (Lambda) — управляешь только своей функцией; всё остальное — у провайдера.

Чем правее по спектру, тем меньше операционной нагрузки на тебя — но и тем меньше контроля над окружением.

## Q3. Чем FaaS отличается от BaaS?

Разница в том, чей код выполняется. В **FaaS** запускается *твой* код в виде функций, в **BaaS** — *готовый* сервис провайдера, который ты только конфигурируешь. FaaS даёт гибкость и кастомную логику, BaaS — скорость за счёт отказа от собственного кода.

**FaaS (Function-as-a-Service):**
- Свой код, упакованный в функции.
- Запускается по событиям (HTTP-запрос, сообщение в очереди, изменение в БД).
- Примеры: Lambda, Cloud Functions, Azure Functions.

**BaaS (Backend-as-a-Service):**
- Готовые backend-сервисы — аутентификация, БД, файлы, платежи.
- Своего кода нет, только конфигурация и вызовы API.
- Примеры: Firebase, Auth0, Supabase, Stripe.

На практике это не «или-или»: типичное приложение комбинирует оба — BaaS закрывает стандартные куски (auth), FaaS держит уникальную бизнес-логику.

```
Frontend → BaaS auth (Auth0) → FaaS (Lambda business logic) → Database
```

## Q4. (!) Сравнение Lambda vs Functions vs Cloud Run vs Cloud Functions?

Главные оси сравнения — **тип** (чистый FaaS или serverless-контейнер), **таймаут** (сколько может работать один вызов) и **конкурентность** (сколько запросов держит инстанс). По ним и выбирают: короткие event-driven задачи → FaaS, более длинные и тяжёлые → serverless-контейнеры.

| Сервис | Провайдер | Тип | Таймаут | Конкурентность |
|---------|----------|------|---------|-------------|
| **AWS Lambda** | AWS | FaaS | 15 мин | 1000 по умолчанию |
| **Azure Functions** | Azure | FaaS | 10 мин (Consumption) | зависит |
| **GCP Cloud Functions** | GCP | FaaS | 9 мин (gen 1) / 60 мин (gen 2) | зависит |
| **AWS Fargate** | AWS | Serverless-контейнеры | без лимита | на задачу |
| **GCP Cloud Run** | GCP | Serverless-контейнеры | 60 мин | до 1000 на инстанс |
| **Azure Container Apps** | Azure | Serverless-контейнеры | без лимита | зависит |
| **Cloudflare Workers** | Cloudflare | Edge | 30 сек (free) / 5 мин (paid) | очень высокая |

Ключевое различие FaaS и serverless-контейнеров — модель конкурентности. У классического FaaS один инстанс обслуживает **один** запрос за раз, у serverless-контейнеров (Cloud Run, Container Apps) — **несколько** на инстанс, что снижает количество cold start и стоимость.

**Тренд в 2025:** serverless-контейнеры (Cloud Run, Container Apps) обгоняют чистый FaaS за счёт гибкости — более длинные таймауты, больше памяти и несколько запросов на инстанс. Это убирает главные ограничения FaaS, сохраняя pay-per-use и auto-scale.

## Q5. Из чего складывается цена FaaS?

Счёт за FaaS собирается из четырёх слагаемых — и понимать их важно, потому что доминирующее меняется с нагрузкой. На низкой частоте платишь почти только за вызовы, на тяжёлых функциях — за длительность × память.

- **За вызов** — фиксированная цена за каждый запуск ($0.20 за 1M для Lambda).
- **За длительность** — время выполнения × выделенная память (биллинг помегабайтно-посекундно).
- **Хранилище** — размещение пакета деплоя.
- **Сеть** — исходящий трафик.

```
Lambda example:
1M invocations × 100ms × 512 MB = $1.03/month

Always running EC2 t3.medium = $30/month (730 hours)
```

**Точка безубыточности:** примерно ~50K вызовов в день. Ниже — serverless дешевле (не платишь за простой), выше — постоянная VM выгоднее (фиксированная цена размывается на большой объём).

**Подводный камень:** исходящий трафик стоит одинаково и для VM, и для Lambda — на serverless он не дешевеет, и в крупных нагрузках именно он, а не вычисления, способен стать главной статьёй расхода.

## Q6. (!) Cold start — это общая проблема всех FaaS?

Да. **Cold start** — задержка первого вызова, когда инстанса ещё нет и его нужно поднять с нуля. Это неизбежная плата за модель «масштабирование от нуля»: раз в простое не крутится ничего, любой новый инстанс приходится готовить заново. Величина задержки сильно зависит от рантайма.

Подготовка инстанса проходит несколько шагов, и каждый добавляет время:
- Подготовить окружение выполнения.
- Скачать код или образ.
- Инициализировать runtime.
- Выполнить init-код функции.

**Типичные задержки:**
- AWS Lambda Python: 200-500 мс.
- AWS Lambda Java: 1-5 сек (без SnapStart) — JVM прогревается дольше всех.
- GCP Cloud Run (контейнер): 1-3 сек (зависит от размера образа).
- Cloudflare Workers: ~5 мс — V8 isolates вместо полноценного контейнера, реального cold start почти нет.

Cold start срабатывает не только при первом запуске. Он возникает каждый раз, когда провайдеру не хватает тёплых инстансов:
- При самом первом вызове.
- После периода простоя (инстанс был погашен).
- При росте конкурентности (под всплеск поднимают новые инстансы).
- При обновлении кода (старые инстансы сбрасываются).

## Q7. Как бороться с cold start: pre-warming, provisioned concurrency, snapshots?

Способы делятся на два класса: либо держать инстансы тёплыми заранее (за деньги), либо ускорять саму инициализацию. Универсального бесплатного решения нет — выбор зависит от того, насколько критична задержка и сколько готов платить.

**Pre-warming (прогрев):**
- Запланированные вызовы каждые 5-10 мин, чтобы инстанс не успевал погаснуть.
- Хак, а не решение: ненадёжен (не гарантирует тёплый инстанс под всплеск) и не рекомендуется.

**Provisioned Concurrency (Lambda) / Pre-warmed (Functions):**
- Предынициализированные окружения, всегда тёплые — провайдер держит их за тебя.
- Стоит дополнительных денег ($$$): платишь за зарезервированную ёмкость независимо от трафика.
- Лучший выбор для чувствительных к задержке API, где cold start недопустим.

**SnapStart (Lambda Java/Python):**
- Снимок (snapshot) уже инициализированного окружения.
- При вызове окружение восстанавливается из снимка вместо инициализации с нуля — cold start в 5-10x быстрее. Особенно ценно для медленно стартующей JVM.

Помимо этого, cold start уменьшают свойства самой функции:
- **Меньший пакет деплоя** — меньше кода грузить, быстрее старт.
- **Более быстрый runtime** — Node.js, Python, Go стартуют быстрее, чем Java и .NET.
- **Edge-рантаймы** (Cloudflare Workers) — на базе V8 isolates, cold start практически нулевой.

## Q8. (!) Какие преимущества у serverless?

Большинство плюсов вытекают из одного факта: эксплуатацию серверов взял на себя провайдер. Это снимает с команды операционную нагрузку и переводит оплату на модель «по факту».

1. **Нет управления инфраструктурой** — команда фокусируется на бизнес-логике, а не на серверах.
2. **Auto-scaling** — провайдер сам поднимает инстансы под всплеск трафика.
3. **Pay-per-use** — платишь только за реальные вызовы, в простое счёт нулевой.
4. **Быстрее time-to-market** — минимум инфраструктурной обвязки, быстрые прототипы.
5. **Встроенные HA / DR** — отказоустойчивость и резервирование обеспечивает провайдер.
6. **Встроенная безопасность** — патчинг ОС и сетевая изоляция на стороне платформы.
7. **Event-driven** — естественная интеграция с облачными событиями (очереди, изменения в БД, загрузки в хранилище).
8. **Полиглот** — каждую функцию можно писать на своём языке.
9. **Дружелюбность к микросервисам** — функция = сервис, границы прозрачны.

## Q9. (!) Какие недостатки у serverless?

Обратная сторона делегирования серверов провайдеру — потеря контроля: над задержкой, окружением, временем выполнения и переносимостью. Большинство минусов растут именно отсюда.

1. **Cold starts** — задержка первого вызова делает latency нестабильным.
2. **Vendor lock-in** — код завязан на API и события конкретного провайдера.
3. **Ограниченное время выполнения** — у Lambda потолок 15 мин, долгие задачи не помещаются.
4. **Ограниченные память/CPU** — обычно 1-10 GB на инстанс.
5. **Stateless** — локального постоянного состояния нет, всё хранится снаружи.
6. **Сложная отладка** — распределённость и эфемерность функций мешают воспроизводить баги.
7. **Непредсказуемость стоимости** — всплеск трафика → неожиданно крупный счёт.
8. **Лимиты конкурентности** — квоты провайдера могут стать потолком под нагрузкой.
9. **Сетевые накладные расходы** — каждый вызов проходит через облако, добавляя задержку.
10. **Сложнее тестировать** — локальная эмуляция облака несовершенна.

## Q10. (!) Насколько критичен vendor lock-in в serverless?

Lock-in в serverless реальный и более глубокий, чем в контейнерах: ты завязан не только на рантайм, но и на источники событий, SDK и модель прав провайдера. Полностью устранить его нельзя, но можно ограничить зоной адаптеров и спроектировать ядро переносимым.

**Где привязка действительно жёсткая:**
- Lambda runtime API — формат обработчика и контракт вызова.
- Облако-специфичные источники событий — S3, DynamoDB Streams и т.п.
- SDK провайдера, пронизывающий код.
- Модели IAM и сети — права и сетевая конфигурация уникальны для облака.

**Как смягчить:**
- **Гексагональная архитектура** — бизнес-логика в центре, облачные API снаружи, за портами.
- **Adapter pattern** — обёртки над облачными SDK, чтобы замена провайдера касалась только адаптеров.
- **Multi-cloud фреймворки** — Serverless Framework, Pulumi сглаживают различия деплоя.
- **Открытые стандарты** — CloudEvents для переносимого формата событий.

**Реалистичный вывод:** даже со всеми смягчениями миграция между облаками остаётся болезненной. Поэтому основное облако выбирают вдумчиво и надолго, а бизнес-логику с самого начала держат переносимой (portable), не размазывая SDK провайдера по всему коду.

## Q11. (!) Что такое edge computing?

**Edge computing** — выполнение кода не в одном дата-центре, а на граничных локациях (CDN-узлах), физически близких к пользователю. Смысл — срезать сетевую задержку: код отрабатывает в десятках километров от клиента, а не за океаном.

```
Traditional: User → Internet → AWS region (Frankfurt)
Edge:        User → Cloudflare edge (closest, ~10 km) → ...
```

Выигрыш в цифрах: edge даёт ~10-50 мс против ~100-300 мс у обращения в удалённый регион (особенно между континентами). Именно эта разница и определяет, что выносят на edge.

**Сценарии применения** — лёгкая логика, которую выгодно выполнить *до* обращения к origin:
- **Аутентификация** — проверка JWT, чтобы отсечь невалидные запросы у границы.
- **A/B-маршрутизация**.
- **Трансформация изображений**.
- **Гео-таргетинг**.
- **Детект ботов**.
- **Инвалидация кэша**.

**Ограничения** — обратная сторона лёгкости рантайма:
- Очень короткие выполнения (10-50 мс CPU-времени).
- Меньше памяти.
- Урезанные API — нет полноценного Node.js или Python.

## Q12. (!) Чем Cloudflare Workers отличаются от Lambda@Edge?

Корень всех различий — модель рантайма. Workers крутятся на лёгких **V8 isolates**, Lambda@Edge — на полноценной Lambda у границы CloudFront. Отсюда тянется всё остальное: Workers радикально быстрее на старте, но ограниченнее по памяти и API; Lambda@Edge мощнее, но с заметным cold start.

| Критерий | Cloudflare Workers | Lambda@Edge |
|----------|-------------------|-------------|
| Локации | 300+ дата-центров | CloudFront edge (600+) |
| Cold start | **~5 мс** (V8 isolates) | ~200 мс (Lambda) |
| Языки | JS, TS, WASM, Rust, Python (beta) | Node.js, Python |
| Runtime | V8 isolate | полноценная Lambda |
| Память | 128 MB | 128 MB - 10 GB |
| CPU-время | 10-50 мс (free) | 5 сек |
| Цена | $5/10M запросов + длительность | Lambda + CloudFront |
| KV / DB | Workers KV, D1, R2, Durable Objects | ограниченно (через Lambda) |

Как выбирать:
- **Cloudflare Workers** — пионер edge-вычислений с очень зрелой экосистемой (KV, D1, R2, Durable Objects); берут, когда нужен минимальный cold start и edge-нативное хранилище.
- **Lambda@Edge** — для приложений, уже живущих в AWS-стеке; функциональнее по памяти и времени, но ограничен и медленнее на старте.

## Q13. Что предлагают Vercel Edge Functions, Deno Deploy и Fastly Compute@Edge?

Это три альтернативные edge-платформы, и все они строятся на одной идее: лёгкий рантайм (V8 isolates или WebAssembly) ради почти нулевого cold start. Различаются они нишей и технологией изоляции.

- **Vercel Edge Functions** — поверх Cloudflare Workers и инфраструктуры Vercel; ключевая фишка — тесная интеграция с Next.js.
- **Deno Deploy** — JavaScript-рантайм от команды Deno, тоже на V8 isolates.
- **Fastly Compute@Edge** — на базе WebAssembly; поддерживает Rust, AssemblyScript, JS.

**Общий знаменатель:** V8 isolates или WebAssembly вместо контейнеров — отсюда мгновенный старт.

В 2025 edge computing — мейнстрим, особенно для frontend-фреймворков (Next.js, Remix), где рендеринг и логику всё чаще выносят ближе к пользователю.

## Q14. (!) Как строится event-driven архитектура на serverless?

Это естественный для serverless стиль: систему собирают как цепочку функций, реагирующих на события. Событие (загрузка в S3, сообщение в очереди) запускает Lambda, та публикует новое событие — и так дальше. Функции не вызывают друг друга напрямую, а общаются через события.

Поток в этом примере выглядит так:

- `S3 upload` → `Lambda: resize image` — загрузка файла в S3 запускает функцию ресайза.
- `Lambda: resize image` → `SNS topic` — функция публикует событие в SNS-топик.
- `SNS topic` → `Lambda: notify user` — топик веером (fan-out) доставляет событие функции уведомления пользователя.
- `SNS topic` → `Lambda: update analytics` → `DynamoDB` — параллельно тот же топик запускает функцию обновления аналитики, которая пишет в DynamoDB.

То есть одна загрузка файла разворачивается в цепочку: ресайз → уведомление пользователя и обновление аналитики параллельно. Каждый шаг — отдельная Lambda, ничего не знающая о соседях.

**Почему это хорошо ложится на serverless:**
- **Слабая связанность** — потребители не знают о производителях, общаются через события.
- **Независимый auto-scaling** — каждый компонент масштабируется под свою нагрузку.
- **Pay-per-use в чистом виде** — платишь, только когда событие реально происходит.
- **Лёгкая расширяемость** — нового потребителя добавляешь подпиской на событие, не трогая остальных.

**Инструменты:** EventBridge, SNS, SQS, Kinesis, события S3.

Подробнее — в [Event-driven Patterns](../architecture/event-driven-patterns-interview.md).

## Q15. Как применять strangler pattern для миграции legacy на serverless?

Strangler pattern — это постепенное «удушение» монолита: вместо переписывания всё сразу новый функционал по частям выносят в serverless, а старый код снимают с эксплуатации только когда от него ничего не осталось. Это снижает риск — нет момента «большого взрыва».

```
Old monolith handles all routes
  ↓
Add API Gateway in front
  ↓
Route /new-feature → Lambda
  ↓
Gradually move endpoints from monolith to Lambda
  ↓
Eventually decommission monolith
```

Шаги читаются сверху вниз: ставим API Gateway перед монолитом, заворачиваем новые маршруты на Lambda, затем по одному переносим существующие эндпоинты и в конце гасим монолит. Serverless здесь особенно удобен: новую функцию добавляешь как отдельную Lambda, не трогая legacy-код.

## Q16. (!) Как устроен паттерн serverless API gateway?

Это базовая схема serverless-API: перед функциями ставят управляемый API Gateway, который берёт на себя всё, что не относится к бизнес-логике. Так каждая Lambda занимается только своим делом, а сквозные задачи (auth, лимиты, валидация) решаются централизованно в шлюзе.

```
Client → API Gateway → Lambda functions → Database
```

**Что делает API Gateway** (вместо того, чтобы дублировать это в каждой функции):
- Аутентификация — валидация JWT.
- Rate limiting — защита от перегрузки.
- Валидация запросов.
- Кэширование ответов.
- Маршрутизация к нужной Lambda.

**Lambda-функции:**
- По одной на ресурс (REST-стиль) или на сценарий применения.
- Прямой доступ к DynamoDB через IAM — без отдельного слоя.

**Выбор шлюза:** в большинстве случаев хватает **HTTP API** (дешевле и проще); **REST API** берут, когда нужны продвинутые возможности (детальная валидация, кэш, кастомные авторизаторы).

## Q17. Зачем нужны Step Functions / Durable Functions для workflow?

Когда процесс состоит из нескольких шагов с ветвлениями, retry и ожиданием, размазывать оркестрацию по самим функциям больно: теряется наглядность и обработка ошибок. **Step Functions (AWS) / Durable Functions (Azure)** выносят координацию наружу — ты декларативно описываешь граф шагов, а движок управляет переходами, повторами и состоянием.

```json
{
  "States": {
    "Validate": { "Type": "Task", "Resource": "lambda:validate" },
    "ProcessPayment": { "Type": "Task", "Resource": "lambda:payment" },
    "SendEmail": { "Type": "Task", "Resource": "lambda:email" }
  }
}
```

Каждый `State` — шаг workflow, который вызывает свою Lambda; движок прогоняет их по порядку, сам решая, что делать при сбое.

**Что это даёт:**
- Визуальное представление workflow — граф шагов вместо разбросанного кода.
- Встроенные retry и обработка ошибок — не нужно писать их вручную.
- Долгоживущие процессы — до 1 года для Step Functions Standard.
- Параллельные ветки.
- Observability из коробки — видно, на каком шаге что произошло.

**Сценарии:** оформление заказов, согласования, ETL, ML-пайплайны.

По сути это **Saga pattern** в serverless-обёртке. Подробнее — [Saga Pattern](../architecture/saga-pattern-interview.md).

## Q18. (!) Как работать с состоянием в serverless?

Функции **stateless** — между вызовами они ничего не помнят, а инстанс может погаснуть в любой момент. Поэтому любое состояние, которое должно пережить вызов, выносят во внешнее хранилище. Выбор хранилища зависит от того, что именно за состояние.

- **База данных** — DynamoDB, Cosmos DB, Aurora — для основных данных приложения.
- **Кэш** — ElastiCache Redis, Memorystore — для быстрого общего состояния между вызовами.
- **Конечный автомат** — Step Functions / Durable Functions — для состояния многошагового процесса.
- **Event sourcing** — события в Kafka/Kinesis — когда состояние выводится из истории событий.
- **Объектное хранилище** — S3 — для файлов и крупных артефактов.

**Подводный камень:** локальный `/tmp` нельзя использовать для постоянного состояния — он эфемерный и пересоздаётся на каждый cold start. Годится только как временный буфер в пределах одного вызова.

## Q19. Как управлять соединениями с БД в serverless?

**Проблема — connection storm.** В обычном приложении пул соединений общий, но каждый инстанс Lambda изолирован и держит свои соединения. Под нагрузкой это взрывается: 1000 конкурентных Lambda открывают 1000 соединений к БД, и она падает по OOM или упирается в лимит подключений. Реляционные БД к такому не готовы.

Решения сводятся к тому, чтобы либо убрать прямые соединения, либо переиспользовать их:

1. **Пул соединений вне Lambda** — RDS Proxy, PgBouncer: пул живёт отдельно и мультиплексирует тысячи функций на десятки реальных соединений.
2. **Serverless-базы данных** — DynamoDB, Aurora Serverless v2, Cosmos DB: рассчитаны на такую модель доступа изначально.
3. **БД поверх HTTP** — Neon, PlanetScale: работают по HTTP, без долгоживущего соединения вообще.
4. **Переиспользование в init-фазе** — соединение создаётся один раз при инициализации инстанса и переживает несколько вызовов, пока инстанс тёплый.

```python
# Bad — new connection per invocation
def handler(event, context):
    conn = psycopg2.connect(...)  # SLOW + connection storm

# Better — reuse if warm
import psycopg2
conn = psycopg2.connect(...)  # init phase

def handler(event, context):
    cursor = conn.cursor()  # reuse warm connection
```

Идея кода: соединение создаётся вне `handler`, в init-фазе, и переиспользуется тёплым инстансом — вместо открытия нового подключения на каждый вызов (что и порождает шторм).

**RDS Proxy** — управляемый пул соединений как раз для связки Lambda + RDS: снимает проблему без переписывания приложения.

## Q20. (!) Что такое Serverless Framework?

**Serverless Framework** (`serverless.com`) — один из первых и самых популярных multi-cloud инструментов деплоя serverless-приложений. Ты описываешь функции и их триггеры в `serverless.yml`, а фреймворк превращает это в облачные ресурсы и раскатывает их одной командой.

```yaml
# serverless.yml
service: my-app
provider:
  name: aws
  runtime: python3.11

functions:
  hello:
    handler: app.hello
    events:
      - http:
          path: /hello
          method: get
```

```bash
serverless deploy
serverless logs -f hello
serverless remove
```

**Особенности:**
- Multi-cloud — один инструмент для AWS, GCP, Azure.
- Богатая экосистема плагинов.
- Локальная разработка и эмуляция.

**Куда движется:** в 2025 теряет долю в пользу CDK, SST и Terraform, но остаётся популярным выбором именно для AWS Lambda — за низкий порог входа и зрелые плагины.

## Q21. Что выбрать среди SST, Pulumi и CDK?

Все три — IaC-инструменты, описывающие инфраструктуру кодом на настоящих языках программирования (в отличие от YAML-деклараций). Различаются охватом облаков и уровнем абстракции над serverless.

**SST (Serverless Stack)** — современный AWS serverless-фреймворк поверх CDK, с упором на developer experience (быстрый деплой, удобная локальная отладка).

```typescript
new Function(stack, "MyFunction", {
  handler: "src/handler.main",
  events: ["api/users", "api/orders"]
});
```

**AWS CDK** — императивный IaC (Python/TS/Java/.NET/Go), но привязан к AWS.

**Pulumi** — IaC на настоящих языках, но в отличие от CDK — multi-cloud.

**Как выбирать:**
- **Только AWS** — CDK или SST (SST, если нужен фокус на serverless DX).
- **Multi-cloud** — Pulumi или Terraform (последний — декларативный).
- **Быстрый прототип** — Serverless Framework, минимум обвязки.

## Q22. Что дают нативные SAM и Functions Core Tools?

Это официальный serverless-тулинг от самих провайдеров — в отличие от сторонних фреймворков, он глубоко интегрирован с облаком и поддерживается вендором.

- **SAM (AWS Serverless Application Model)** — официальный IaC от AWS для serverless: компактный синтаксис поверх CloudFormation плюс локальный запуск.
- **Azure Functions Core Tools** — локальная разработка и отладка Azure Functions.
- **GCP Functions Framework** — локальный запуск Cloud Functions.

У каждого облака есть свой нативный инструмент; самым зрелым считается SAM. Их берут, когда привязка к одному облаку приемлема и важна тесная интеграция с его сервисами.

## Q23. (!) Когда serverless лучше контейнеров?

Общий критерий: serverless выигрывает там, где нагрузка **неравномерна и непредсказуема**. На рваном трафике pay-per-use и масштабирование от нуля окупаются — не платишь за простаивающие серверы и не настраиваешь capacity заранее.

- **Спорадический трафик** — pay-per-use дешевле постоянной VM, простой бесплатен.
- **Event-driven** — модель «событие → функция» ложится естественно.
- **Быстрые прототипы** — минимум инфраструктурной обвязки.
- **Cron-задачи** — запуск строго по расписанию, без постоянного процесса.
- **Webhooks** — переменная нагрузка, которую трудно прогнозировать.
- **Glue-код** — мелкие интеграции между сервисами.
- **Обработка всплесков** — auto-scale срабатывает мгновенно, без предупреждения.

## Q24. (!) Когда контейнеры лучше serverless?

Зеркальный критерий: контейнеры выигрывают там, где нагрузка **постоянная и предсказуемая** либо где упираешься в лимиты FaaS (время, состояние, задержка). На ровном высоком трафике фиксированная цена за сервер дешевле помиллисекундного биллинга, а отсутствие cold start критично для latency.

- **Высокий постоянный трафик** — на больших объёмах дешевле по вычислениям.
- **Долгие задачи** — дольше 15 мин в FaaS не помещаются.
- **Stateful-приложения** — сессии, локальное кэширование.
- **WebSocket** — длинные постоянные соединения, чуждые модели «вызов-ответ».
- **Тяжёлые фреймворки** — полный Spring Boot слишком долго стартует в FaaS.
- **Критична задержка** — у тёплого контейнера нет cold start.
- **Кастомная сеть / ОС** — нужен контроль над окружением.
- **Предсказуемые нагрузки** — резервирование выходит экономнее.

**Гибрид:** часто компромисс дают serverless-контейнеры (Cloud Run / Container Apps) — «достаточно serverless» (auto-scale, pay-per-use) при гибкости обычных контейнеров.

## Q25. Как обеспечить observability в serverless?

Observability здесь сложнее, чем в монолите, по фундаментальной причине: функции эфемерны и распределены. Привычный подход «поставить агента на сервер» не работает — сервера, на котором он жил бы, нет.

**Что усложняет наблюдаемость:**
- Распределённость — одна операция размазана по множеству функций.
- Короткий жизненный цикл — некуда поставить постоянный агент метрик.
- Изменчивые cold starts — latency скачет, аномалии труднее отличить.
- Асинхронные вызовы — событийные цепочки тяжело связать в один трейс.

**Чем пользуются:**
- **Нативные у провайдера** — CloudWatch + X-Ray, Application Insights, Cloud Logging.
- **Сторонние** — Datadog, New Relic, Lumigo, Thundra (специфичен для Lambda), Honeycomb.

**Lambda Powertools** (open-source от AWS) — библиотеки, дающие единообразное логирование, метрики и трассировку прямо из функции.

**OpenTelemetry** — стандарт для кросс-облачных трейсов, чтобы не привязываться к одному вендору наблюдаемости.

## Q26. Как тестировать serverless?

Тестирование строится пирамидой, но с поправкой на облако: чем выше уровень, тем сильнее тебе нужна сама облачная среда, а её локальная эмуляция всегда неполная.

**Unit-тесты** — обработчик (handler) тестируется как обычная функция, без облачных зависимостей; самый быстрый и надёжный уровень.

**Интеграционные тесты** — проверяют связку с облачными сервисами через локальные эмуляторы:
- **LocalStack** — эмулятор AWS: локальные DynamoDB, S3, SQS, Lambda.
- **SAM Local** — запуск Lambda локально.
- **Functions Core Tools** — для Azure.
- **firebase emulators** — для Firebase.

**End-to-end:**
- Деплой в реальное dev/staging-окружение.
- Прогон сценариев против развёрнутой версии.
- Инструменты: Postman, Cypress, кастомные скрипты.

**Подводный камень:** локальные эмуляторы несовершенны — лимиты, IAM, тайминги и поведение под нагрузкой в production отличаются. Поэтому критичные пути обязательно проверяют end-to-end на реальном окружении, а не только в эмуляторе.

## Q27. (!) Как анализировать стоимость serverless?

Главная мысль: serverless не «дешевле» сам по себе — он дёшев на одном профиле нагрузки и дорог на другом. Граница проходит по тому, постоянный трафик или рваный. И почти всегда счёт раздувают не сами функции, а вспомогательные сервисы вокруг них.

**Дёшево, когда нагрузка неравномерна:**
- Всплески трафика — платишь только за пики (auto-scale).
- Низкая частота (< 100K вызовов в день) — постоянная VM простаивала бы.
- Event-driven workflow.
- Cron и задачи по расписанию.

**Дорого, когда нагрузка ровная и тяжёлая:**
- Высокий постоянный трафик (миллионы в день) — VM с фиксированной ценой выгоднее.
- Долгие задачи — биллинг за длительность растёт линейно.
- Функции с большой памятью — память входит в множитель цены.
- Множество cold starts — лишнее время инициализации тоже оплачивается.

**Скрытые затраты** (часто превышают цену самих функций):
- Запросы API Gateway ($1-3.50 за миллион).
- Приём логов в CloudWatch Logs.
- Исходящий трафик.
- VPC NAT Gateway (если функции внутри VPC).
- Межрегиональные вызовы.

**Эмпирическое правило:** прежде чем выбирать serverless ради экономии, прикинь полную стоимость по формуле:

```
Daily invocations × duration × memory + per-invocation cost + auxiliary services
```

## Q28. Какие частые ошибки в serverless?

Большинство граблей повторяют типовые ловушки модели: игнорирование cold start и лимитов, отсутствие защиты от повторов, недосмотр за стоимостью и безопасностью. Список ниже — концентрат того, на чём обычно горят:

1. **Неожиданные cold start** в production — latency проседает там, где этого не ждали.
2. **Штормы соединений с БД** — отсутствие пулинга кладёт базу.
3. **Нет DLQ** — упавшие сообщения теряются молча.
4. **Жёсткие таймауты** — задача не укладывается в 15 мин у Lambda.
5. **Vendor lock-in без планирования** — миграция потом превращается в переписывание.
6. **Нет идемпотентности** — retry создаёт дубликаты (двойные списания, дубли заказов).
7. **Неконтролируемый рост затрат** — рекурсивный вызов Lambda из Lambda раскручивает счёт.
8. **Захардкоженные секреты** в переменных окружения вместо secrets manager.
9. **Синхронный вызов Lambda из Lambda** — лишняя стоимость и сложенная задержка.
10. **Тяжёлые фреймворки** — Spring Boot без SnapStart превращает каждый cold start в пытку.
11. **Слишком много логов** — CloudWatch Logs дорогой, объём бьёт по счёту.
12. **Нет аутентификации** на эндпоинтах API Gateway — открытый API.
13. **Публичные S3-бакеты** триггерят Lambda → усилитель затрат и вектор атаки.
14. **Упёрлись в лимиты конкурентности** — квота исчерпана, production лежит.

**Как страховаться:** observability и алертинг (чтобы видеть проблему рано), бюджеты (чтобы ловить рост затрат), dead letter queues (чтобы не терять сообщения) и идемпотентность (чтобы retry были безопасны).
