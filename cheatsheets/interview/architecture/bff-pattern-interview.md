# Вопросы на собеседовании: `BFF Pattern`

`BFF (Backend for Frontend)` — паттерн: **отдельный бэкенд под каждый тип клиента** (web, mobile, TV), заточенный под конкретные UX-требования. Агрегирует микросервисы, формирует ответы, прячет сложность. Популяризован SoundCloud/Netflix. Противопоставляется обобщённому API Gateway.

## Q1. (!) Что такое BFF pattern?

**BFF (Backend for Frontend)** — это выделенный API-слой, который пишут и держат **отдельно под каждый тип клиента** (web, iOS, Android, TV). Один клиент — один BFF.

Идея в том, чтобы перевернуть привычную схему. Обычно строят один обобщённый API на всех; BFF же говорит: пусть у каждого фронтенда будет свой бэкенд-сервис, который подгоняет данные именно под его экран. Внутри все BFF ходят в одни и те же доменные микросервисы — отличается только то, **как** они собирают и отдают ответ.

Каждый BFF:
- ходит в те же базовые микросервисы, что и остальные;
- агрегирует и преобразует данные под нужды конкретного клиента;
- оптимизирован под UI-требования именно этого клиента (размер payload, форма ответа, число запросов).

**Схема:**
```
[Web UI] ←→ [Web BFF]      ┐
[iOS App] ←→ [iOS BFF]      │→ [Microservices: User, Product, Order, Inventory, ...]
[Android] ←→ [Android BFF]  │
[Smart TV] ←→ [TV BFF]      ┘
```

**В чём контраст с монолитным API.** Когда один API обслуживает всех, он становится компромиссом ни для кого: клиенты делают много вызовов и отбрасывают данные, которые им не нужны. BFF убирает этот компромисс, давая каждому клиенту ответ ровно той формы, что ему удобна.

**Откуда взялся.** Паттерн придумали инженеры SoundCloud (2015): их Android-приложению нужны были иные формы данных, чем web-фронтенду, и тащить оба требования через один API оказалось неудобно.

## Q2. (!) Зачем нужен BFF — какую проблему он решает?

Коротко: BFF убирает боль обобщённого «one-size-fits-all» API, в котором разные клиенты вынуждены делить один контракт. Когда web, мобайл и TV тянут данные через один и тот же API, каждый из них страдает по-своему. Вот пять типичных проблем такого API и как BFF их закрывает.

**1. Over-fetching — клиент получает лишнее.**
Мобильному экрану нужно 3 поля, а API отдаёт 30. На мобильных и медленных сетях это лишний трафик и батарея на парсинг — то, что особенно дорого.

**2. Under-fetching (N+1) — клиент вынужден делать много вызовов.**
Чтобы собрать один экран, клиенту нужны данные из 5 сервисов, и он делает 5 HTTP-вызовов — 5 round trip. На мобильной сети, где каждый round trip стоит десятки-сотни миллисекунд, это заметно медленно.

**3. Клиент-специфичные требования конфликтуют между собой.**
TV нужна простая навигация и разреженные данные; web хочет богатую интерактивность. Один API не может угодить обоим аккуратно — он либо перегружен ради web, либо обеднён ради TV.

**4. Жёсткая связанность с клиентами (client coupling).**
Любое изменение общего API рискует сломать кого-то из клиентов, поэтому версионирование становится болезненным: каждое поле нужно поддерживать совместимым для всех.

**5. Обобщённый API разрастается под нужды всех.**
Он накапливает каждое поле, которое кто-либо когда-либо просил, и постепенно теряет владельца — непонятно, кто отвечает за этот кусок контракта.

**Что даёт BFF в ответ на это:**
- каждый клиент получает ответ ровно той формы, что ему нужна (нет over-fetching);
- один вызов BFF агрегирует данные нескольких сервисов на стороне сервера, а не клиента (нет N+1);
- изменение под одного клиента = правка только его BFF, остальные не задеты;
- у каждого клиента — чистый, отдельный контракт со своим владельцем.

## Q3. (!) Чем BFF отличается от API Gateway?

Главное различие — в назначении. **API Gateway обобщённый и горизонтальный**: один на всех, занимается сквозными задачами на границе сети. **BFF — клиент-специфичный и вертикальный**: свой на каждого клиента, занимается формой и сборкой ответа под конкретный фронтенд. Это не конкуренты, а слои с разной ответственностью.

**API Gateway** — прокси общего назначения на границе сети (edge):
- auth, rate limit, логирование, маршрутизация;
- обслуживает всех клиентов одинаково;
- решает сквозные задачи (cross-cutting concerns), а не бизнес-логику.

**BFF** — клиент-специфичный слой агрегации:
- заточенные под клиента формы ответов;
- композиция нескольких сервисов в один ответ;
- свой экземпляр на каждого клиента.

**Сравнение:**

| Аспект | API Gateway | BFF |
|--------|-------------|-----|
| Область | Все клиенты | Один тип клиента |
| Логика | Сквозная (auth, rate) | Агрегация, формирование |
| На клиента | Нет | Да |
| Бизнес-логика | Нет | Немного |
| Владелец | Платформенная команда | Клиентская команда |

**Они хорошо сосуществуют** — это типичный production-стек:
```
Client → API Gateway → BFF → Microservices
```

- Gateway снимает общее: auth, WAF, rate limit;
- BFF собирает ответ под конкретного клиента.

**Эмпирическое правило.** Нужна только маршрутизация и auth, ответы у всех одинаковые — хватит API Gateway. Как только клиентам нужны разные формы ответа — добавляй BFF поверх (или вместо) gateway.

## Q4. (!) Как выглядит архитектура с BFF?

Архитектура состоит из трёх слоёв: клиенты, слой BFF (по одному на тип клиента) и доменные микросервисы. Клиент общается только со своим BFF, а тот уже фанаутит запросы во внутренние сервисы и собирает из их ответов один payload.

```
Web browser ─────→ Web BFF (Node.js)
Mobile app (iOS) ─→ iOS BFF (Kotlin/Java) ─→ [Auth]
Mobile app (Android) → Android BFF         ─→ [User Service]
Third party API ──→ Partner BFF            ─→ [Product Service]
                                           ─→ [Order Service]
                                           ─→ [Inventory Service]
                                           ─→ [Recommendation Service]
```

**Что делает каждый BFF:**
- поднимает HTTP-сервер (REST или GraphQL);
- вызывает несколько внутренних сервисов (HTTP/gRPC);
- агрегирует и преобразует их ответы;
- отдаёт результат в форме, удобной именно его клиенту.

**Каким остаётся внутренний слой.** Доменные сервисы сфокусированы на своём домене и **ничего не знают о клиентах** — благодаря этому их может переиспользовать любой BFF. Вся клиентская специфика вынесена в слой BFF, поэтому сервисы не обрастают «костылями под мобайл» или «под TV».

**Пример потока — главный экран мобильного приложения:**
1. Пользователь открывает приложение → один запрос `GET /home` к mobile BFF.
2. BFF **параллельно** дёргает три сервиса:
   - User Service — профиль;
   - Feed Service — топ-20 элементов ленты;
   - Notification Service — число непрочитанных.
3. BFF склеивает ответы в единый payload: `{user, feed, notifications: {unread: 5}}`.
4. Клиент рендерит экран — и всё это за **один** round trip вместо трёх.

## Q5. Сколько BFF нужно?

Главный принцип: считай BFF **по клиентскому опыту (experience), а не по технологии**. Если два клиента дают пользователю один и тот же опыт, им может хватить общего BFF, даже если они написаны на разных стеках. И наоборот — разный UX почти всегда означает разные BFF.

**Типичные разбиения:**
- Web + Mobile — 2 BFF;
- Web + iOS + Android — 3;
- Web + Mobile + TV + Partner API — 4.

**Как решать в спорных случаях:**
- разный UX → отдельный BFF;
- тот же UX, но другая технология (например, iOS и Android на React Native) → возможно, один общий BFF;
- интеграция с бизнес-партнёром → обычно свой BFF, потому что у партнёра другие auth и rate limit.

**Подводные камни (по обе стороны):**
- слишком много — отдельный BFF на каждый экран → раздутая операционная нагрузка;
- слишком мало — один BFF на всё → возвращаемся к той же проблеме обобщённого API.

**Эмпирическое правило.** Начинай с одного BFF и разделяй его только тогда, когда расходящиеся требования клиентов начинают реально мешать друг другу. Преждевременное дробление создаёт операционные издержки на пустом месте.

## Q6. На каком стеке писать BFF?

Два критерия при выборе. Во-первых, стек должен быть хорош в **I/O-bound** работе, потому что BFF почти ничего не считает, а в основном ждёт ответов от сервисов. Во-вторых — это должен быть стек, **близкий клиентской команде**, ведь именно она владеет BFF.

**Подходящие языки:**
- **Node.js** — самый частый выбор: совпадает с навыками web/mobile-команд, отличный async I/O;
- **Kotlin** — типизирован и удобен мобильным командам;
- **Go** — когда важна производительность;
- **TypeScript** — практически везде поверх Node.

**Фреймворки:**
- Node.js — Express, Fastify, NestJS;
- Java/Kotlin — Spring Boot (предпочтительно реактивный);
- GraphQL — Apollo Server, Netflix DGS.

**Почему именно I/O, а не CPU.** BFF в основном проксирует и агрегирует: его время уходит на ожидание сетевых вызовов, а не на вычисления. Поэтому критичен эффективный асинхронный I/O (чтобы один поток обслуживал множество ожидающих запросов), а мощный CPU почти не нужен.

**Почему тот же язык, что у клиентской команды.** Если iOS-команда пишет iOS BFF (обычно на Node или Kotlin), она владеет стеком от UI до бэкенда целиком — без переключения контекста и без зависимости от чужой команды на каждое изменение формы ответа.

## Q7. (!) Что должен делать BFF?

Зона ответственности BFF — это всё, что связано с **адаптацией бэкенда под конкретный клиент**: собрать, переформатировать, подстраховать. Бизнес-логику он не держит (см. Q8). Семь его типичных обязанностей:

**1. Агрегация API.** Собирает ответы из нескольких микросервисов: один запрос к BFF превращается в несколько параллельных вызовов бэкенда — это главное, ради чего BFF и нужен.

**2. Формирование ответа (response shaping).** Подгоняет данные под клиента: убирает ненужные поля, переименовывает их под соглашения клиента, уплощает вложенные структуры.

**3. Трансляция протоколов.** Внутри сети сервисы общаются по gRPC/Protobuf, а наружу клиенту BFF отдаёт привычный REST/JSON или GraphQL.

**4. Клиент-специфичная адаптация.** Mobile — меньшие payload, TV — упрощённая структура навигации, web — богатые метаданные. Одни и те же данные, разная упаковка.

**5. Клиент-специфичная логика.** Feature flags по платформам, прослойки совместимости (compatibility shims) для старых версий приложения.

**6. Устойчивость (resilience).** Fallback при сбое бэкенда, отдача устаревших, но валидных данных вместо ошибки — чтобы экран не падал из-за одного упавшего сервиса.

**7. Кэширование под клиента.** Состояние сессии, настройки под конкретное устройство.

## Q8. (!) Что НЕ должен делать BFF?

Ключевая мысль: **BFF — тонкий оркестратор, а не «умный» слой**. Как только он начинает держать логику или состояние, он превращается в скрытый монолит. Поэтому пять вещей выносим за его границы:

**1. Ключевую бизнес-логику.** Она остаётся в доменных сервисах. BFF — это клей между ними, а не место, где живут правила домена.

**2. Полноценную аутентификацию.** Валидацию токенов обычно делает API Gateway до BFF. BFF может извлечь пользователя из уже проверенного токена, но сам токены не валидирует.

**3. Персистентность данных.** Своей БД у BFF, как правило, нет — всё состояние живёт в доменных сервисах. BFF stateless, чтобы его можно было свободно масштабировать.

**4. Кросс-клиентскую логику.** Код, общий для всех клиентов, идёт в сервисы, а не копируется в каждый BFF. Иначе придётся синхронно править одно и то же в нескольких местах.

**5. Тяжёлые вычисления.** CPU-интенсивная работа выносится в отдельный сервис — она ломает I/O-bound природу BFF и его масштабирование.

**Подводные камни — «жирный BFF» (fat BFF).** Со временем BFF незаметно обрастает бизнес-логикой и превращается в монолит. Это самый частый антипаттерн: лечится только дисциплиной — регулярно рефакторить логику обратно в доменные сервисы.

## Q9. (!) Можно ли использовать GraphQL как BFF?

Да, и это очень естественная пара. GraphQL по своей природе решает ровно те две проблемы, ради которых придуман BFF: клиент сам указывает точную форму данных, которую хочет, поэтому **нет ни over-fetching, ни under-fetching**, и всё это через **единый endpoint** вместо россыпи REST-роутов.

**Как это устроено.** GraphQL-сервер выступает в роли BFF: его схема описывает клиентский взгляд на домен, а резолверы под капотом ходят в микросервисы и собирают ответ. Клиент шлёт один запрос с нужной формой — сервер достаёт ровно эти данные.

**Плюсы:**
- не нужны отдельные endpoint под каждый сценарий — клиент сам комбинирует поля;
- клиенты развивают UI без изменений бэкенда, пока нужные данные уже есть в схеме;
- строгая типизация схемы.

**Минусы:**
- сложность — schema stitching и классическая проблема N+1 в резолверах;
- кэширование труднее: запросы идут POST-ом и динамические, обычный HTTP-кэш по URL не работает;
- ощутимый порог входа для команды.

**Нужен ли тогда отдельный BFF на каждого клиента?** Зависит от расхождения клиентов. Если все они похожи — хватит одного общего GraphQL BFF. Если требования сильно расходятся — заводят отдельную GraphQL-схему на каждого клиента.

**Как лечить кэширование (раз обычный HTTP-кэш не работает):**
- **Persisted queries** — клиент шлёт хэш заранее зарегистрированного запроса, и его можно кэшировать как идентифицированный;
- **DataLoader** — батчит и дедуплицирует вызовы бэкенда внутри одного запроса, снимая ту самую N+1 в резолверах.

## Q10. Что такое GraphQL Federation?

**Federation** — это способ собрать одну большую GraphQL-схему из частей, которыми владеют разные команды. Каждая команда отвечает за свой кусок (subgraph), а gateway склеивает их в единый федеративный граф, по которому клиент ходит как по одной схеме. Так делают, например, Netflix и GitHub.

**Архитектура:**
```
[Client] → [GraphQL Gateway] → [User Subgraph] (User team)
                             → [Product Subgraph] (Product team)
                             → [Order Subgraph] (Order team)
```

**Subgraph** — это самостоятельный GraphQL-сервер: владеет своей частью схемы и деплоится независимо от остальных.

**Gateway** склеивает subgraph-ы в один граф, планирует исполнение запроса по нужным сервисам и проксирует результат. Реализации — Apollo Federation, GraphQL Mesh.

**Чем отличается от монолитного GraphQL.** Монолитную схему пишет и деплоит одна команда — она становится узким местом. Federation распределяет владение и эволюцию схемы по командам, поэтому масштабируется на их большое число без центрального бутылочного горлышка.

**Чем отличается от BFF — это разные оси декомпозиции:**
- BFF режет систему **по клиентам** (client-driven): что нужно конкретному фронтенду;
- Federation режет **по доменам** (domain-driven): кто владеет какой частью данных.

Поэтому они не исключают друг друга: к федеративному графу могут обращаться клиент-специфичные BFF — или клиенты ходят в него напрямую, если их требования достаточно близки.

## Q11. (!) В чём преимущества BFF?

Все плюсы BFF сводятся к одной идее — он разделяет клиентскую специфику и доменную логику, и это разделение выгодно сразу по нескольким осям: производительность, скорость команд, чистота сервисов.

**1. Оптимизация под клиента.** Mobile получает маленькие payload, TV — упрощённую навигацию. Производительность настраивается под каждую платформу отдельно, без компромиссов.

**2. Более быстрая разработка фронтенда.** Клиентская команда владеет своим BFF и итерирует независимо — ей не нужно ждать бэкенд-команду на каждое изменение формы ответа.

**3. Меньше round trips.** Один вызов BFF вместо 10 прямых вызовов сервисов с клиента. На мобильных сетях, где каждый round trip дорогой, это решающий выигрыш.

**4. Чистые доменные сервисы.** Сервисы ничего не знают о клиентах, остаются сфокусированными на домене и легко переиспользуются разными BFF.

**5. Независимая эволюция.** Изменение в BFF одного клиента не задевает остальных, поэтому версионирование API становится проще — нет общего контракта, который страшно трогать.

**6. Устойчивость под каждого клиента.** Fallback и сценарии отказа подбираются под конкретный UX: что показать вместо упавшего блока на мобильном и на TV — решения разные.

**7. Ограничение видимости (security scoping).** BFF фильтрует, что именно уходит клиенту. Внутренние сервисы в доверенной сети могут отдавать больше данных, а наружу пройдёт только разрешённое.

## Q12. (!) В чём недостатки BFF?

Обратная сторона BFF — у вас теперь не один API, а несколько сервисов, и каждый надо писать, деплоить, мониторить и держать согласованным. Большинство минусов вытекает именно из этого «умножения на N».

**1. Дублирование кода.** Несколько BFF делают похожую агрегацию. Опасно не само дублирование, а расхождение: баг чинят в одном BFF и забывают про другой.

**2. Операционная нагрузка.** N сервисов нужно деплоить и мониторить, у каждого свой CI/CD и рантайм. Инфраструктурных забот в N раз больше, чем с одним API.

**3. Путаница во владении.** Кто владеет BFF, когда web- и mobile-команды делят зону ответственности? На стыке команд границы размываются, и BFF рискует стать «ничьим».

**4. Добавочная задержка.** Лишний хоп (client → BFF → services) добавляет 5–20 мс. Обычно это с лихвой окупается выигрышем от агрегации (меньше round trip), но в чистом виде latency BFF добавляет.

**5. Соблазн добавить логику.** Тот самый «жирный BFF»: со временем он разрастается в мини-монолит, если не следить за границами (см. Q8).

**6. Повторяющиеся auth и обработка ошибок.** Один и тот же boilerplate в каждом BFF — приходится выносить его в общие middleware-библиотеки, иначе он расползается копипастой.

**7. Координация при изменениях схемы.** Добавил поле в сервис — нужно обновить все BFF, которые его используют. Сквозное изменение перестаёт быть атомарным.

## Q13. Как бороться с дублированием кода между BFF?

**Проблема:** три BFF делают одинаковый вызов к User Service и одинаково обрабатывают ошибки. Хочется убрать копипасту — но не ценой возврата к единому BFF. Ключ в том, **что именно** выносить (инфраструктурный код — да, агрегацию — нет).

**Что выносить — пять приёмов:**

**1. Общие библиотеки.** Внутренний SDK для вызова User Service: общие обработка ошибок, логирование, retry. Версионируется по semver, чтобы BFF обновлялись по своему графику.

**2. gRPC + сгенерированные клиенты.** Общие `.proto`-определения, из которых кодогенерация выдаёт типизированный клиент. DRY возникает прямо в точке вызова, без ручного дублирования.

**3. Общий middleware.** Auth, логирование, трейсинг как NPM/Maven-пакет, который подключается во все BFF одинаково.

**4. Шаблон / scaffold.** Генератор вроде `create-bff`: новый BFF стартует уже со стандартным набором middleware, а не собирается с нуля.

**5. Вынести общее в gateway.** Если auth, rate limit и логирование одинаковы для всех — делай их в API Gateway, а BFF остаются тонкими.

**А вот что выносить НЕ нужно — бизнес-логику и агрегацию.** Дублировать логику сборки ответа под каждого клиента — это нормально, она для того и разная. Попытка унифицировать агрегацию приводит ровно туда, откуда ушли: к одному общему BFF со всеми проблемами обобщённого API.

## Q14. (!) Кто должен владеть BFF?

**Правильный ответ — клиентская (frontend) команда.** BFF — это её инструмент, продолжение её UI, поэтому и держать его должна она.

**Почему именно она:**
- BFF обслуживает её UI — она лучше всех знает требования к форме данных;
- изменения фронтенда почти всегда тянут за собой изменения BFF, и держать их в одной команде = одно изменение в одной зоне ответственности;
- так снижается межкомандная зависимость.

**Антипаттерн — BFF держит бэкенд-команда.** Тогда фронтенд ждёт чужих изменений на каждую правку формы ответа, бэкенд слабо понимает UX-потребности, и BFF становится узким местом — ровно той зависимостью, которую паттерн должен был убрать.

**Какие навыки нужны команде:**
- знание подходящего стека (Node.js / Kotlin / Go — что ближе);
- понимание I/O, async, работы с HTTP/gRPC-клиентами;
- мониторинг и observability — BFF это полноценный production-сервис.

**Как это ложится на оргструктуру:**
- «full-stack» / «product»-команда владеет связкой UI + BFF;
- доменные команды владеют микросервисами;
- платформенная команда — gateway и общими библиотеками.

## Q15. Как кэшировать в BFF?

Кэш в BFF выстраивают слоями — от внешнего к внутреннему. Чем ближе слой к клиенту, тем дешевле попадание, но тем сложнее держать данные свежими; поэтому персонализированное кэшируют близко и коротко, а публичное — далеко и надолго.

**Три слоя:**

**1. Кэш апстрима (upstream).** BFF вызывает сервисы через кэш (HTTP ETag, Redis), снижая повторную нагрузку на бэкенд.

**2. Кэш на уровне BFF.** Уже агрегированные ответы кладутся в Redis — под пользователя или анонимно. TTL короткий (секунды-минуты), потому что собранные данные быстро устаревают.

**3. CDN-кэш.** Публичный контент без пользовательского контекста кэшируется на CDN с долгим TTL — он одинаков для всех.

**Пример composable-кэширования — главный экран.** Вызов BFF комбинирует feed и user:
- базовый, неперсонализированный feed кэшируется на 30 с (общий для всех);
- персонализация под пользователя накладывается сверху;
- итоговый ответ не кэшируется — он персональный.

Так общую часть переиспользуют, а персональную пересобирают на каждый запрос.

**Инвалидация — два подхода:**
- **событийная** — пользователь запостил → инвалидируем кэш его feed (точно, но сложнее);
- **по TTL** — самый простой вариант: данные сами протухают через заданное время.

**Эмпирическое правило по «температуре» данных:**
- горячие (частые) — in-proc кэш в памяти процесса;
- средние — Redis;
- редкие — кэш не нужен, всегда дёргаем сервис.

## Q16. Что значит BFF на edge (Cloudflare, Vercel)?

Идея: вынести BFF из центрального дата-центра на **edge** — в сотни точек присутствия по миру, чтобы расстояние от клиента до BFF было минимальным. Тренд набрал силу с appearance edge-рантаймов.

**Где это работает:**
- **Vercel Edge Functions** — API-роуты Next.js app router, server components и server actions выполняются на edge;
- **Cloudflare Workers** — BFF крутится в лёгком V8-изоляте на 300+ POP.

**В чём выигрыш — и где он заканчивается.** Вызов клиента до edge BFF — около 20 мс против 100–200 мс до центрального региона. Но сами доменные сервисы остаются в origin, поэтому вызов из edge до них стоит 100–150 мс round trip. То есть edge приближает к пользователю только «первый хоп»; до данных всё равно далеко.

**Отсюда главный компромисс.** Edge-вычисления ограничены (например, 30 с на выполнение, 128 МБ памяти), а холодный путь до origin-сервисов никуда не девается. Поэтому выигрыш реален **только если активно кэшировать на edge** — тогда большинство запросов вообще не доходит до origin.

**Каким должен быть edge BFF, чтобы это окупалось:**
- маленьким и тонким (в рамки лимитов рантайма);
- с агрессивным кэшированием;
- занятым лёгкими задачами — auth, feature flags;
- агрегирующим уже закэшированные данные, а не дёргающим origin на каждый запрос.

**Итоговый паттерн:**
```
Client ←20ms→ Edge BFF (cached) ←150ms→ Services (cold path)
```

## Q17. Как тестировать BFF?

Поскольку BFF — это в основном агрегатор чужих ответов, тестовая пирамида строится вокруг **взаимодействия с сервисами**: чем выше уровень, тем реальнее зависимости. Снизу вверх:

**Unit-тесты.** Проверяют функции резолверов/хендлеров изолированно — клиентов сервисов мокаем. Быстрые, проверяют логику сборки ответа.

**Интеграционные тесты.** Реальный HTTP к тестовым сервисам через TestContainers — либо стабы WireMock / Mock Service Worker. Проверяют, что BFF корректно ходит в сервисы и склеивает ответ.

**Контрактные тесты (Pact).** Фиксируют контракт BFF ↔ бэкенд-сервисы и ловят ломающие изменения до того, как они доедут до прода, — без поднятия всей системы.

**E2E.** Браузерные тесты (Cypress, Playwright) проверяют сквозной поток BFF → клиент целиком, глазами пользователя.

**Smoke-тесты в prod.** Синтетические проверки непрерывно дёргают endpoint BFF и поднимают алерт при росте 5xx — раннее обнаружение проблем на живой системе.

**Chaos-тестирование.** Намеренно вбрасываем задержки и ошибки в бэкенд и проверяем, что fallback BFF действительно срабатывают, — то, ради чего resilience и добавляли (см. Q7).

**Тесты observability.** Проверяют, что трейсинг-span создаются корректно, а метрики экспонируются, — чтобы в инциденте было видно, где встал запрос.
