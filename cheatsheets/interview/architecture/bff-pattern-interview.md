# Вопросы на собеседовании: Паттерн BFF

Backend for Frontend (BFF) — API-слой, который обслуживает потребности конкретного клиентского опыта. Он обращается к внутренним сервисам и возвращает данные в удобной клиенту форме. Отдельный BFF полезен там, где требования клиентов действительно расходятся; разделение по названиям платформ само по себе не цель.

<a id="q1"></a>
## Q1. Что такое BFF pattern?

BFF адаптирует API к клиентскому сценарию. Он может собрать данные нескольких доменных сервисов, преобразовать представление и вернуть ответ, подходящий конкретному интерфейсу. Web и mobile могут иметь разные BFF, если различия в требованиях оправдывают отдельные контракты и эксплуатацию. Для похожих интерфейсов допустим общий слой.

<a id="q2"></a>
## Q2. Зачем нужен BFF — какую проблему он решает?

Общий API может заставлять одних клиентов получать лишние поля, а других — делать несколько обращений ради одного экрана. BFF формирует нужный ответ и может объединить вызовы внутренних сервисов на сервере. Это сокращает число обращений **клиента**, но не гарантирует устранения N+1 внутри самого BFF или GraphQL-резолверов. Добавленный слой тоже имеет стоимость, поэтому эффект оценивают по конкретному пути запроса.

<a id="q3"></a>
## Q3. Чем BFF отличается от API Gateway?

API Gateway обычно решает общие задачи входной границы: маршрутизацию, ограничение частоты и иногда проверку подлинности. BFF отвечает за представление и композицию данных под клиентский сценарий. Эти функции могут находиться в одной технологии или в разных компонентах. Возможная цепочка: `Client → Gateway → BFF → Domain services`.

<a id="q4"></a>
## Q4. Как выглядит архитектура с BFF?

Клиент вызывает подходящий BFF, а тот получает данные из доменных сервисов и собирает ответ. Например, запрос домашнего экрана может объединить профиль, ленту и число уведомлений. Независимые вызовы можно выполнять параллельно, учитывая таймауты и частичный отказ. Доменные правила остаются у владельцев доменов. Число BFF и язык реализации не заданы паттерном.

<a id="q5"></a>
## Q5. Сколько BFF нужно?

Границы проводят по существенным различиям клиентского опыта, контракта и владения. iOS и Android могут разделять BFF, если запрашивают одинаковые данные и развиваются вместе. Разделение оправдано, когда общий API начинает тормозить независимые изменения или обрастает несовместимыми ветками. BFF на каждый экран создаёт лишние развёртывания; один API для сильно разных клиентов возвращает прежнюю проблему компромиссов.

<a id="q6"></a>
## Q6. На каком стеке писать BFF?

Выбирают стек, который команда умеет поддерживать и который подходит для нужных протоколов, библиотек, нагрузки и развёртывания. BFF часто делает несколько сетевых вызовов, поэтому важны таймауты, управление параллелизмом и наблюдаемость. Асинхронный I/O может помочь при большом числе ожидающих запросов. Он не делает Node.js, реактивный Spring или какой-либо язык обязательным.

<a id="q7"></a>
## Q7. Что должен делать BFF?

Типичные задачи: композиция ответов, преобразование формы данных, адаптация протокола и совместимость с версиями клиента. Кэширование и fallback добавляют там, где ясны правила свежести и допустимого частичного ответа. BFF может проверять доступ на своей границе, но доменные сервисы должны защищать собственные операции и данные. Владелец каждого правила должен быть определён явно.

<a id="q8"></a>
## Q8. Что не должен делать BFF?

BFF не должен становиться источником истины для заказов, цен и других доменных данных или копировать доменные решения в клиентский слой. Это ведёт к расхождению правил между клиентами. Техническое состояние, кэш и проверка токена сами по себе не запрещены: важны границы ответственности, корректная передача идентичности и контроль доступа. Доверенная внутренняя сеть не заменяет авторизацию.

<a id="q9"></a>
## Q9. Можно ли использовать GraphQL как BFF?

Да. Схема может отражать клиентский взгляд на данные, а резолверы — собирать их из внутренних сервисов. Клиент выбирает поля из доступной схемы, что помогает уменьшить лишние данные. Это не гарантирует отсутствия недостающих данных в схеме, N+1 на сервере или хорошей задержки. Для резолверов применяют batching/DataLoader, а для кэша учитывают метод запроса, ключ, переменные и пользовательский контекст. GraphQL-запросы могут идти и через GET при подходящих условиях.

<a id="q10"></a>
## Q10. Что такое GraphQL Federation?

Federation собирает единую схему из subgraph, которыми владеют разные доменные команды. Маршрутизатор планирует запрос по нужным subgraph. BFF разделяет API по клиентским потребностям, а federation — владение частями схемы по доменам. Подходы можно сочетать: BFF может обращаться к федеративному графу. Само наличие federation не гарантирует производительность или независимость любых изменений схемы.

<a id="q11"></a>
## Q11. В чём преимущества BFF?

Клиенты получают подходящую форму ответа и могут менять свой контракт с меньшей координацией с другими интерфейсами. Агрегация способна сократить число клиентских сетевых обращений. Доменные сервисы сохраняют фокус на доменных правилах. Фактический выигрыш по задержке зависит от времени внутренних вызовов, дополнительного перехода и кэша; безопасность зависит от реализации авторизации на всех нужных границах.

<a id="q12"></a>
## Q12. В чём недостатки BFF?

Каждый новый BFF нужно разрабатывать, развёртывать, наблюдать и поддерживать. Возможны дублирование интеграционного кода, размытое владение и расхождение контрактов. Дополнительный сетевой переход может увеличить задержку, а изменение доменного API требует координации его потребителей. Пользу от разделения сравнивают с этими затратами для конкретной системы.

<a id="q13"></a>
## Q13. Как бороться с дублированием кода между BFF?

Повторяющиеся контракты, типизированные клиенты и сквозные механизмы можно переиспользовать, если у них действительно общая семантика. Общие задачи входной границы иногда разумно вынести в gateway или платформенную библиотеку. Клиентская композиция должна оставаться понятной владельцу каждого BFF. Если повторяется доменное правило, его место в доменном сервисе, а не в нескольких копиях клиентского кода.

<a id="q14"></a>
## Q14. Кто должен владеть BFF?

Владелец должен понимать клиентский сценарий, принимать решения о контракте и отвечать за работу сервиса в production. Часто это продуктовая команда, объединяющая frontend и backend компетенции. Backend-команда тоже может владеть BFF, если у неё есть ясная ответственность за нужды клиента и быстрый канал изменений. Название команды само по себе не определяет качество границы.

<a id="q15"></a>
## Q15. Как кэшировать в BFF?

Для каждого кэшируемого результата определяют область видимости, ключ, допустимую свежесть и способ инвалидации. Общие данные можно переиспользовать между клиентами, персональные — изолировать по пользователю и другим параметрам доступа. Кэшировать можно ответ целиком или отдельные части, на BFF, в сервисе или CDN, если это соответствует контракту. TTL, событийная инвалидация и проверка актуальности выбираются по свойствам данных; универсальных значений нет.

<a id="q16"></a>
## Q16. Что значит BFF на edge (Cloudflare, Vercel)?

Edge BFF выполняет часть клиентской адаптации ближе к пользователю. Если для ответа всё равно нужен далёкий origin, выигрыш может исчезнуть. Кэш и расположение зависимостей важнее самого слова «edge». Лимиты времени, памяти и доступных API зависят от провайдера и плана; их проверяют перед выбором среды. Сравнивают полную задержку сценария с региональным размещением, включая промахи кэша.

<a id="q17"></a>
## Q17. Как тестировать BFF?

Проверяют форму ответа, ошибки, таймауты и разрешённые частичные результаты. Unit-тесты полезны для преобразований, интеграционные — для взаимодействия с зависимостями, контрактные — для совместимости API. Сквозные проверки оставляют для важных клиентских сценариев. Сбои и нагрузку проверяют там, где они существенно меняют UX. WireMock, Testcontainers, Pact и браузерные инструменты — возможные средства, а не обязательный набор.
