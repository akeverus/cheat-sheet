## Q1. (!) Что такое балансировка нагрузки на уровне L4 и L7?

`L4` (`Transport` layer) — балансировка по `IP` и порту; балансировщик не анализирует содержимое трафика (`HTTP`, `gRPC`). Подходит для любого протокола; низкая задержка; не может маршрутизировать по `URL` или заголовкам. Пример: балансировка `TCP` соединений по `IP` и порту; подходит для не-`HTTP` протоколов (`gRPC`, базы данных); быстрее `L7` из-за отсутствия анализа содержимого.

`L7` (`Application` layer) — балансировка по содержимому запроса (`URL`, заголовки, cookie). Подходит для `HTTP`/`HTTPS`; можно направлять запросы на разные бэкенды по пути; поддержка `TLS` termination и маршрутизации по домену. Пример: маршрутизация `/api/users` → `User Service`, `/api/orders` → `Order Service`; поддержка `path-based` routing; возможность анализа заголовков для маршрутизации.

## Q2. Что такое TLS termination и где его делать?

`TLS` termination — расшифровка `HTTPS` на балансировщике; к бэкендам трафик идёт по `HTTP` (или по внутренней сети). Плюсы: централизованное управление сертификатами; разгрузка бэкендов от шифрования. Минусы: трафик между балансировщиком и бэкендом не зашифрован (допустимо во внутренней сети). Делать на балансировщике (`Nginx`, `AWS ALB`) или на шлюзе; при необходимости `end-to-end` шифрования — `TLS` до бэкенда (без termination на балансировщике). Пример: клиент → `HTTPS` → балансировщик (расшифровка) → `HTTP` → бэкенд; сертификаты управляются на балансировщике; бэкенды не тратят ресурсы на шифрование. Реализация: в `Nginx` через `SSL` сертификаты; в `AWS ALB` через `SSL` сертификаты из `ACM`; в `Kubernetes` через `TLS` секреты в `Ingress`.

## Q3. (!) Что такое health check и зачем он нужен?

`Health` check — периодическая проверка состояния бэкенда (`HTTP`-запрос на `/health`, `TCP`-проверка порта). Нерабочие узлы исключаются из пула; после восстановления — возвращаются. Настраивают: интервал проверки, порог неудач для исключения, порог успехов для возврата; таймаут и ожидаемый код ответа. Пример: проверка каждые 5 секунд; при 3 неудачах подряд узел исключается; при 2 успехах подряд узел возвращается в пул. Типы health check: `HTTP` (`GET` запрос на `/health`), `TCP` (проверка доступности порта), `gRPC` (health check через `gRPC` health service). Важно: health check `endpoint` должен быть быстрым и не зависеть от внешних сервисов; проверять только критичные компоненты приложения.

## Q4. Что такое sticky session (session affinity) и когда его использовать?

`Sticky` session — запросы одного клиента (по cookie или `IP`) направляются на один и тот же бэкенд. Нужен, когда состояние сессии хранится в памяти приложения. Минусы: неравномерное распределение при разной длительности сессий; при падении узла сессии теряются. Предпочтительно: stateless приложение и общее хранилище сессий (`Redis`); sticky session — только при невозможности вынести состояние. Пример: в `Nginx` через `ip_hash` или `sticky` cookie; в `Kubernetes` через `sessionAffinity: ClientIP` для `Service`. Реализация: по `IP` (проще, но не работает за `NAT`); по cookie (надежнее, но требует поддержки cookie); по первому запросу (установка cookie при первом запросе). Рекомендация: избегать sticky session; использовать stateless приложение с общим хранилищем сессий (`Redis`, `Memcached`).

## Q5. Чем отличается активная балансировка от пассивной?

**Активная** — балансировщик сам проверяет бэкенды (health check) и исключает нерабочие. **Пассивная** — балансировщик считает узел нерабочим только после неудачных ответов на реальные запросы.

Активная быстрее выявляет сбои (например, `GET /health` каждые 5 с); пассивная проще, но клиент может получить ошибку до исключения узла. Для критичных сервисов предпочтительна активная проверка с коротким интервалом.

**Практика:** в `Kubernetes` задают активные пробы в `Pod spec`: `livenessProbe` (перезапуск контейнера при провале) и `readinessProbe` (исключение из `Service` при провале). Пример: `httpGet` на `/health`, `initialDelaySeconds: 30`, `periodSeconds: 10`. Так трафик не идёт на неготовые или «мёртвые» поды.

При активной проверке балансировщик периодически шлёт `HTTP`/`HTTPS` или `TCP`-проверку на каждый бэкенд (например, `GET /health`). В `Kubernetes` readiness/liveness — активные пробы; при их провале под не получает трафик. Для критичных сервисов предпочтительна активная проверка с коротким интервалом, чтобы быстрее убирать нерабочие узлы из ротации.

**Примеры:** `Nginx` (активная) — `GET /health`. HAProxy — `option httpchk GET /health` и `http-check expect status 200`. `Kubernetes` — в `Deployment` задают `livenessProbe` и `readinessProbe` (`httpGet` на порт приложения); `kube-proxy` не направляет трафик на под с failed readiness.

**Практика:** для продакшена выбирать активные проверки с интервалом 5–10 с и порогом 2–3 неудачи; для канарейки или A/B — можно пассивную, если допустима кратковременная ошибка до исключения узла. Метрики (число healthy/unhealthy бэкендов) экспортировать в `Prometheus` для алертинга.

## Q6. Что такое Round Robin и когда его применять?

`Round Robin` — запросы распределяются по узлам по очереди (1-й запрос — узел A, 2-й — B, 3-й — C, 4-й — снова A). Подходит для равномерной нагрузки при одинаковой производительности узлов и коротких запросах. Не учитывает текущую загрузку узлов и длительность запросов. Пример: 3 узла (A, B, C); запросы распределяются: 1→A, 2→B, 3→C, 4→A, 5→B, 6→C и т.д. Преимущества: простота реализации; равномерное распределение при одинаковой производительности узлов. Недостатки: не учитывает текущую загрузку; не подходит для длинных запросов (один узел может быть перегружен длинными запросами).

## Q7. Что такое Weighted Round Robin?

`Weighted Round Robin` — каждому узлу задаётся вес; узлы с большим весом получают больше запросов. Используют при разной производительности узлов (мощный сервер — вес 3, слабый — 1) или для постепенного ввода нового узла (малый вес, затем увеличение). Пример: узел A (вес 3), узел B (вес 1), узел C (вес 2); распределение: A получает 3 запроса, B получает 1 запрос, C получает 2 запроса за цикл. Преимущества: учёт разной производительности узлов; возможность постепенного ввода нового узла. Недостатки: не учитывает текущую загрузку; требует настройки весов.

## Q8. Что такое Least Connections и когда его применять?

`Least Connections` — запрос направляется на узел с наименьшим числом активных соединений. Подходит для длинных сессий (долгие запросы, `WebSocket`, потоковая передача), когда `Round Robin` даёт неравномерную нагрузку (один узел перегружен длинными запросами). Балансировщик должен отслеживать число соединений. Пример: узел A (5 соединений), узел B (2 соединения), узел C (8 соединений); новый запрос направляется на узел B. Преимущества: учёт текущей загрузки узлов; подходит для длинных сессий. Недостатки: требует отслеживания числа соединений; может быть сложнее в реализации, чем `Round Robin`.

## Q9. Что такое Least Response Time?

`Least Response Time` — запрос направляется на узел с наименьшей задержкой ответа (или комбинация задержки и числа соединений). Учитывает текущую загрузку узлов; подходит для минимизации латентности. Требует измерения задержки (метрики с бэкендов или пробы). Пример: узел A (latency 50ms), узел B (latency 20ms), узел C (latency 100ms); новый запрос направляется на узел B. Преимущества: минимизация латентности; учёт текущей загрузки узлов. Недостатки: требует измерения задержки; может быть сложнее в реализации; требует метрики с бэкендов или пробы.

## Q10. Как выбрать алгоритм балансировки для микросервисов?

Краткие запросы, stateless — `Round Robin` или `Weighted Round Robin`. Длинные запросы или `WebSocket` — `Least Connections`. Нужна минимальная латентность — `Least Response Time`. Обязательное состояние на узле — `Sticky Session` (лучше избегать, вынести состояние в `Redis`). Пример: краткие `REST` запросы, stateless приложение — `Round Robin` для равномерной нагрузки; длинные запросы или `WebSocket` — `Least Connections` для учёта текущей загрузки; нужна минимальная латентность — `Least Response Time` для минимизации задержки; обязательное состояние на узле — `Sticky Session` (лучше избегать, использовать stateless приложение с общим хранилищем сессий). Рекомендация: избегать `Sticky Session`; использовать stateless приложение с общим хранилищем сессий (`Redis`, `Memcached`); выбирать алгоритм в зависимости от типа запросов и требований к латентности.

В production-реализации важно учитывать не только алгоритм распределения, но и health checks, поведение при частичных отказах и влияние на p95/p99 latency. Сильный ответ обычно включает критерии переключения стратегии и план проверки под пиковыми нагрузками.

## Q11. Что такое клиентская и серверная балансировка?

Серверная — отдельный компонент (`Nginx`, `AWS ALB`) принимает запросы и направляет на бэкенды. Клиент не знает о бэкендах. Клиентская — клиент (приложение, `SDK`) сам выбирает узел из списка (из service discovery, например `Consul`, `Eureka`). Используют в микросервисах (`Spring Cloud LoadBalancer`, `gRPC`-клиент); уменьшается задержка (нет лишнего прыжка через балансировщик). Пример серверной: клиент → `Nginx` → бэкенд; клиент не знает о бэкендах; `Nginx` управляет распределением. Пример клиентской: клиент получает список инстансов из `Consul`/`Eureka` и сам выбирает узел; нет лишнего прыжка через балансировщик; уменьшается задержка. Преимущества серверной: централизованное управление; клиент не знает о бэкендах. Преимущества клиентской: уменьшение задержки; нет single point of failure балансировщика.

В production-реализации важно учитывать не только алгоритм распределения, но и health checks, поведение при частичных отказах и влияние на p95/p99 latency. Сильный ответ обычно включает критерии переключения стратегии и план проверки под пиковыми нагрузками.

## Q12. Что такое blue-green и canary в контексте балансировки?

`Blue-green` — два окружения (blue и green); трафик идёт на одно; при деплое переключают трафик на другое. Переключение мгновенное; откат — обратное переключение. `Canary` — часть трафика направляется на новую версию, остальная — на старую; постепенное увеличение доли нового. Балансировщик или шлюз управляет распределением по версиям. Пример `blue-green`: трафик идёт на blue; при деплое развёртывается green; после проверки трафик переключается на green; при проблемах — обратное переключение на blue. ## Q29. Что такое consistent hashing и когда его использовать для балансировки?

`Consistent` hashing (ключ, например `userId`) определяет узел; при изменении числа узлов перераспределяется только часть запросов. Используют для кэширования (запросы с одним ключом на один узел кэша) и stateful приложений (sharding по ключу). Преимущества: минимальное перераспределение при изменении числа узлов; равномерное распределение при большом числе узлов. Реализация: в `Nginx` через модуль `ngx_http_upstream_consistent_hash`; в `Redis Cluster` для sharding. Пример: запросы с ключом `userId`=123 всегда попадают на один узел; при добавлении нового узла перераспределяется только часть запросов (запросы с ключами, попадающими на новый узел). Преимущества: минимальное перераспределение при изменении числа узлов; равномерное распределение при большом числе узлов; подходит для кэширования и sharding. Недостатки: сложнее в реализации, чем `Round Robin`; требует выбора ключа для хэширования.

В production-реализации важно учитывать не только алгоритм распределения, но и health checks, поведение при частичных отказах и влияние на p95/p99 latency. Сильный ответ обычно включает критерии переключения стратегии и план проверки под пиковыми нагрузками.

## Q30. Как мониторить и анализировать работу балансировщика?

Метрики для мониторинга: Число активных соединений по узлам; Запросы в секунду (`RPS`) по узлам; `Latency` (средняя, p50, p95, p99) по узлам; `Error` rate (4xx, 5xx) по узлам; health check (endpoint). Инструменты: `Prometheus` + `Grafana` для метрик; `Nginx stub_status` или метрики экспортера; `Kubernetes Service` и `Ingress` метрики; `AWS CloudWatch` для `ALB`/`NLB`. Алерты: при исключении узла из пула; при росте error rate; при неравномерном распределении нагрузки; при превышении latency порогов. Пример метрик: число активных соединений по узлам (узел A: 100, узел B: 150, узел C: 80); запросы в секунду по узлам (узел A: 50 RPS, узел B: 75 RPS, узел C: 40 RPS); latency p95 по узлам (узел A: 50ms, узел B: 30ms, узел C: 100ms). Алерты: при исключении узла из пула (health status = unhealthy); при росте error rate выше 5%; при неравномерном распределении нагрузки (разница между узлами > 30%); при превышении latency p95 порога (например, 200ms).

В production-реализации важно учитывать не только алгоритм распределения, но и health checks, поведение при частичных отказах и влияние на p95/p99 latency. Сильный ответ обычно включает критерии переключения стратегии и план проверки под пиковыми нагрузками.
