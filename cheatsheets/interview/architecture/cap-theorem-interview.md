# Вопросы на собеседовании: `CAP`-теорема

Краткое введение: ответы по `CAP`-теореме для собеседований — ограничения распределённых систем, выбор между согласованностью и доступностью. **CAP-теорема** описывает ограничения распределённых систем: нельзя одновременно гарантировать согласованность (`Consistency`), доступность (`Availability`) и устойчивость к разделению (`Partition tolerance`). На интервью часто спрашивают про этот компромисс, модели согласованности, алгоритмы консенсуса и примеры `CP`/`AP`-систем.

## Q1. (!) Что такое CAP-теорема?

**CAP-теорема** утверждает: в распределённой системе нельзя одновременно гарантировать все три свойства — согласованность (`Consistency`), доступность (`Availability`) и устойчивость к разделению сети (`Partition tolerance`). Когда сеть разделяется, одним из свойств приходится жертвовать. Эрик Брюер сформулировал это как гипотезу в 2000 году, а Гилберт и Линч формально доказали в 2002-м.

Важный момент: выбор не между «тремя из трёх», а между двумя. **Partition tolerance** на практике обязателен — сети падают, дата-центры изолируются, и игнорировать это нельзя. Поэтому реальный выбор всегда между **согласованностью** и **доступностью**:

- `CP` — при разделении система блокирует запросы ради согласованных данных (клиент ждёт или получает ошибку, но никогда — устаревшее значение);
- `AP` — при разделении система продолжает отвечать, допуская временную несогласованность (клиент получает ответ, но возможно устаревший).

**CAP-теорема** связывает три свойства — `Consistency` (согласованность), `Availability` (доступность) и `Partition Tolerance` (устойчивость к разделению). Из них любая распределённая система выбирает пару, что даёт три класса:

- **CP-системы** (`Consistency` + `Partition Tolerance`): `ZooKeeper`, `HBase`, `MongoDB` (majority);
- **AP-системы** (`Availability` + `Partition Tolerance`): `Cassandra`, `DynamoDB`, `CouchDB`;
- **CA-системы** (`Consistency` + `Availability`): одиночный `PostgreSQL` (не распределённая система).

**Главное для собеседования:** CAP — это модель для понимания компромиссов, а не жёсткий ярлык на системе. Многие системы (Cassandra, MongoDB, DynamoDB) настраивают поведение на уровне отдельного запроса, поэтому «CP или AP» правильнее задавать про конкретную операцию, а не про продукт целиком.

## Q2. Какие три свойства описывает CAP?

CAP описывает три свойства, из которых при разделении сети одновременно достижимы только два.

- **Consistency** (согласованность) — все узлы видят одни и те же данные в любой момент; чтение после записи возвращает последнее записанное значение. В терминах CAP это `linearizability` — самая строгая модель.
- **Availability** (доступность) — каждый запрос к работающему узлу получает ответ за разумное время (не обязательно с последними данными). Система не зависает и не отдаёт таймаут.
- **Partition tolerance** (устойчивость к разделению) — система продолжает работать, когда сообщения между узлами теряются или задерживаются на произвольное время.

Почему выбор именно между C и A: сетевое разделение в распределённой системе неизбежно, поэтому **Partition tolerance** не отбрасывают. Остаётся пара C/A, и в момент partition обе гарантии разом удержать невозможно — нужно решить, что важнее.

## Q3. Почему на практике выбирают между C и A?

Потому что отказаться от устойчивости к разделению нельзя — а отказаться от C или A можно. Сети ненадёжны, дата-центры изолируются, задержки непредсказуемы. Любая система с репликацией или несколькими узлами обязана пережить partition, иначе она просто перестанет работать при первом же сетевом сбое.

Раз partition обязателен, остаётся выбрать, как вести себя в момент разделения:

- блокировать запросы до восстановления связи с кворумом — жертвуем **Availability**, получаем **CP**;
- продолжать обслуживать запросы и допускать устаревшие данные — жертвуем **Consistency**, получаем **AP**.

При **сетевом разделении** возможны два варианта поведения:

- **CP**: блокировать запросы → данные согласованны → клиент ждёт или получает ошибку;
- **AP**: продолжать отвечать → данные могут быть устаревшими → клиент получает ответ.

Поэтому говорят: «на практике выбор между C и A».

## Q4. (!) Что такое CP-системы, приведите примеры

**CP-системы** жертвуют доступностью ради согласованности: при разделении сети они блокируют запись (и часто чтение), пока не восстановится связь с кворумом реплик. Логика проста — лучше отдать клиенту ошибку, чем устаревшее или неверное значение. Поэтому при partition клиент может получить таймаут или отказ, но никогда — несогласованные данные.

| Система | Механизм CP |
|---------|------------|
| `ZooKeeper` | Алгоритм `ZAB` (Zookeeper Atomic Broadcast), кворум на запись и чтение |
| `etcd` | Алгоритм `Raft`, линеаризуемые чтения через лидера |
| `HBase` | Зависит от `ZooKeeper` для координации, строгая согласованность на уровне строки |
| `MongoDB` (majority) | `writeConcern: majority` + `readConcern: majority` |
| `PostgreSQL` (синхронная репликация) | `synchronous_commit = on`, запись ждёт подтверждения реплики |

**Сценарий применения:** там, где критична строгая согласованность — финансы, учёт, инвентарь, распределённые блокировки, — а кратковременная недоступность допустима. Если выбор стоит между «показать неверный остаток на счёте» и «на пару секунд отказать в записи», CP-система выбирает второе.

## Q5. (!) Что такое AP-системы, приведите примеры

**AP-системы** жертвуют согласованностью ради доступности: при разделении сети они продолжают принимать запросы и всегда отвечают, но могут отдавать устаревшие данные, пока реплики не сойдутся. Репликация обычно асинхронная — узел подтверждает запись, не дожидаясь остальных, поэтому соседние реплики какое-то время отстают.

| Система | Механизм AP |
|---------|------------|
| `Cassandra` (CL=ONE) | Асинхронная репликация, `read repair`, `anti-entropy` |
| `DynamoDB` (eventually consistent reads) | По умолчанию eventual consistency, опционально strongly consistent |
| `CouchDB` | Multi-master репликация, разрешение конфликтов на уровне приложения |
| `Riak` | `Dynamo`-подобная архитектура, `vector clocks` для разрешения конфликтов |

**Сценарий применения:** ленты, счётчики, кэши — всё, где допустима `eventual consistency` и где «устаревший лайк на секунду» никому не вредит. При этом многие AP-системы позволяют усилить согласованность для отдельного запроса, заплатив дополнительной задержкой (например, чтение с кворума вместо одной реплики).

## Q6. Что такое CA-системы и почему они редки?

**CA-системы** дают согласованность и доступность, но не переживают разделение сети — а раз в распределённой среде partition неизбежен, чистый CA на практике почти не встречается.

По сути CA — это одиночный узел или нераспределённая БД без репликации: одна база на одном сервере поверх локальной файловой системы. Пока узел один, разделять нечего — отсюда «и C, и A». Но как только появляются реплики и несколько узлов, partition становится возможным, и приходится выбирать CP или AP.

Логика выбора класса системы:

- **Система распределённая?**
  - **Нет** → **CA** (одиночный `PostgreSQL`, `MySQL` standalone).
  - **Да** → вопрос: при partition что важнее?
    - **Согласованность** → **CP** (`ZooKeeper`, `etcd`, `HBase`).
    - **Доступность** → **AP** (`Cassandra`, `DynamoDB`).

Единственный «CA» — это система, которая при partition просто перестаёт быть распределённой.

## Q7. Что такое сетевое разделение (partition)?

**Partition** (сетевое разделение) — ситуация, когда группа узлов перестаёт получать сообщения от другой группы из-за сетевого сбоя, задержки или потери пакетов. Узлы в каждой группе могут общаться между собой, но не с узлами «по ту сторону» partition.

Пример топологии при разделении пяти узлов:

- **Раздел A**: `Узел 1` ↔ `Узел 2` (связь внутри раздела сохранена).
- **Раздел B**: `Узел 3` ↔ `Узел 4` ↔ `Узел 5` (связь внутри раздела сохранена).
- Между разделами связь `Узел 2` → `Узел 3` разорвана (✕ сеть разорвана) — группы не видят друг друга.

Типичные причины: разрыв кабеля, отказ маршрутизатора, изоляция дата-центра, проблемы у upstream-провайдера. Partition бывает разным:

- **Полным** — полная потеря связи между сегментами;
- **Частичным** (asymmetric) — узел A видит B, но B не видит A; такой случай особенно коварен, потому что узлы по-разному оценивают, кто «жив»;
- **Временным** (секунды) или **длительным** (минуты, часы).

Ключевое: CAP описывает поведение системы именно в момент partition — что она делает с запросами, пока связь разорвана.

## Q8. Почему CAP описывает поведение при partition, а не в норме?

Потому что компромисс между C и A проявляется только при разделении. В нормальных условиях (сеть цела) распределённая система спокойно обеспечивает и согласованность, и доступность одновременно — узлы успевают синхронизироваться, и противоречия не возникает. Дилемма «или C, или A» появляется лишь в тот момент, когда сеть разрывается.

Именно тогда нужно решение: блокировать запросы (CP) или отдавать возможно устаревшие данные (AP). А поскольку большую часть времени система живёт без partition, CAP — это не про «всегда», а про «когда сеть сломалась». Эта узость и привела к появлению **PACELC**, которая добавляет к CAP описание поведения и в нормальном режиме (компромисс latency vs consistency).

## Q9. В чём ограниченность CAP-теоремы?

Коротко: CAP сводит всё к бинарному выбору при partition, а реальность гораздо богаче. Основные упрощения теоремы:

- **Гранулярность.** Система может быть CP для одних операций и AP для других — выбор задаётся уровнем согласованности конкретного запроса, а не продуктом целиком.
- **Задержки.** CAP не учитывает latency: формально «доступная» система, которая отвечает за 30 секунд, для пользователя бесполезна, но по CAP она всё ещё A.
- **Не только partition.** Разделение сети — лишь один тип сбоя; есть отказы узлов, медленные диски, византийские ошибки, которые CAP вообще не охватывает.
- **Спектр согласованности.** CAP знает только про `linearizability` (строгая C) и её отсутствие, тогда как между ними лежит целый ряд промежуточных моделей (causal, read-your-writes и др.).
- **Бинарность.** Реальные системы не «чисто» CP или AP — они выбирают точку на спектре и часто двигаются по нему per-request.

Поэтому на практике опираются на **PACELC**: она достраивает CAP осью latency vs consistency для нормального режима. И помнят главное — большинство систем настраиваются под сценарий, а не жёстко привязаны к CP или AP.

## Q10. (!) Какие модели согласованности существуют и чем отличаются?

Модели согласованности образуют спектр — от самой строгой (всё выглядит как одна машина) до самой слабой (реплики сходятся «когда-нибудь»). Выбор модели — ключевой архитектурный компромисс: чем строже гарантия, тем больше координации между узлами и тем выше задержка.

| Модель | Гарантия | Цена | Пример системы |
|--------|----------|------|---------------|
| `Linearizability` | Операции выглядят мгновенными, глобальный порядок | Максимальная latency, минимальная пропускная способность | `etcd`, `ZooKeeper`, `Spanner` |
| `Sequential consistency` | Глобальный порядок операций, но без привязки к реальному времени | Высокая latency | `ZooKeeper` (для чтений через лидера) |
| `Causal consistency` | Причинно-связанные операции видны в правильном порядке | Умеренная latency | `MongoDB` (causal sessions), `COPS` |
| `Read-your-writes` | Клиент видит свои собственные записи | Низкая latency | Sticky sessions, session tokens |
| `Eventual consistency` | Все реплики сойдутся «когда-нибудь» | Минимальная latency | `Cassandra` (CL=ONE), `DynamoDB` (default) |

Спектр моделей от самой строгой к самой слабой:

`Linearizability` (⬆️ строгая) → `Sequential Consistency` → `Causal Consistency` → `Read-your-writes` → `Eventual Consistency` (⬇️ слабая).

**Эмпирическое правило:** чем строже модель, тем выше задержка и ниже пропускная способность — но тем проще рассуждать о корректности кода. Слабые модели дают скорость ценой того, что приложению приходится самому обрабатывать «странные» порядки чтений.

## Q11. (!) Что такое linearizability и почему это самая строгая модель?

**Linearizability** (линеаризуемость) — самая строгая модель согласованности для одиночного объекта: система ведёт себя так, будто данные лежат на одной машине, а все операции выполняются по очереди. Каждая операция выглядит так, словно произошла мгновенно в некоторый момент между началом и завершением запроса, и все клиенты согласны в одном глобальном порядке, совпадающем с реальным временем.

Самая строгая она потому, что добавляет к порядку операций привязку к реальному времени — это и есть три ключевых свойства:

- **Мгновенность.** Если запись завершилась до начала чтения, чтение обязано увидеть эту запись.
- **Глобальный порядок.** Все наблюдатели согласны в одном и том же порядке операций.
- **Привязка к реальному времени.** Этот порядок совпадает с фактической хронологией событий — нельзя «переставить» операции так, как удобнее системе.

```
Клиент A:  |---write(x=1)---|
Клиент B:           |---read(x)---| → должен вернуть 1
                                      (чтение началось после завершения записи)

Клиент A:  |---write(x=1)---|
Клиент B:      |---read(x)---|      → может вернуть 0 или 1
                                      (операции пересекаются во времени)
```

Линеаризуемость обеспечивается через алгоритмы консенсуса (`Raft`, `Paxos`) или единственного лидера с синхронной репликацией. Системы: `etcd`, `ZooKeeper` (sync reads), Google `Spanner` (с TrueTime).

## Q12. Что такое sequential consistency?

**Sequential consistency** (последовательная согласованность) — модель, где результат выполнения эквивалентен какому-то одному последовательному порядку операций всех процессов, причём внутри каждого процесса операции сохраняют свой порядок. Главное отличие от `linearizability`: этот общий порядок не обязан совпадать с реальным временем — система вправе «переставить» операции разных процессов, лишь бы порядок внутри каждого процесса не нарушился.

```
Процесс A: write(x=1), write(x=2)
Процесс B: write(x=3), write(x=4)

Допустимый sequential order:
  write(x=1) → write(x=3) → write(x=2) → write(x=4)
  (порядок внутри каждого процесса сохранён: 1 до 2, 3 до 4)

Недопустимый:
  write(x=2) → write(x=1) → ...
  (нарушен порядок процесса A)
```

**Почему это дешевле:** раз не нужна синхронизация с реальным временем, `sequential consistency` проще реализовать, чем `linearizability`, — координации между узлами требуется меньше. Например, `ZooKeeper` даёт sequential consistency для обычных чтений и поднимается до линеаризуемости только при явном вызове `sync` перед чтением.

## Q13. (!) Что такое causal consistency и когда она применяется?

**Causal consistency** (причинная согласованность) — модель, которая гарантирует порядок только для причинно-связанных операций. Если операция B зависит от результата A (например, B читает значение, записанное A), то все узлы увидят A перед B. А параллельные операции, между которыми причинной связи нет, могут наблюдаться на разных узлах в разном порядке — и это допустимо.

```
Пример (чат):
  Алиса: "Кто идёт на обед?"     (сообщение 1)
  Боб:   "Я!"                     (сообщение 2, ответ на 1 — причинная связь)

  Causal consistency гарантирует: все видят сообщение 1 перед 2.
  Но сообщение Кати "Привет всем" (не связано) может быть в любом месте.
```

Применяется в:
- **`MongoDB`** (causal consistency sessions) — клиент получает `clusterTime` и `operationTime`, гарантирующие причинный порядок
- **Социальные сети** — комментарии должны отображаться после поста, на который они отвечают
- **Коллаборативные редакторы** — `CRDT` с causal ordering

**Компромисс:** causal consistency — золотая середина. Она сильнее `eventual` (важные причинные связи не нарушатся), но не требует глобальной синхронизации, как `linearizability`, — координируются только связанные операции, а не все подряд. Отсюда умеренная задержка при разумных гарантиях.

## Q14. Что такое eventual consistency и каковы её гарантии?

**Eventual consistency** (согласованность в конечном счёте) — самая слабая из практически полезных моделей. Единственная гарантия: если прекратить запись, то через конечное время все реплики придут к одному состоянию. А вот как быстро это произойдёт и что клиент увидит в промежутке — не оговаривается.

Что **гарантируется**:
- данные не потеряются (durability);
- реплики рано или поздно сойдутся (convergence).

Что **не гарантируется**:
- порядок операций — клиент может увидеть запись B без записи A, хотя A была раньше;
- `read-your-writes` — клиент может не увидеть даже собственную запись сразу после неё;
- время конвергенции — расхождение может длиться миллисекунды, а может минуты.

```java
// Пример: DynamoDB eventually consistent read
GetItemRequest request = GetItemRequest.builder()
    .tableName("Orders")
    .key(Map.of("orderId", AttributeValue.builder().s("123").build()))
    .consistentRead(false)  // eventual consistency (default, в 2 раза дешевле)
    .build();

// Strongly consistent read — гарантирует последние данные, но дороже
GetItemRequest strongRequest = request.toBuilder()
    .consistentRead(true)   // strong consistency (удвоенная стоимость RCU)
    .build();
```

## Q15. Чем отличается strong eventual consistency от eventual consistency?

Главное отличие: **strong eventual consistency** (`SEC`) даёт более сильную гарантию — если два узла получили одинаковый набор обновлений (в любом порядке), они **немедленно** оказываются в одинаковом состоянии, без какой-либо дополнительной координации.

Обычной `eventual consistency` этого мало: ей нужен отдельный этап разрешения конфликтов, который иногда требует общения между узлами. `SEC` снимает этот этап за счёт того, что сами структуры данных спроектированы так, чтобы конфликтов в принципе не возникало, — это **бесконфликтные реплицируемые типы данных** (`CRDT`):

```java
// Пример: G-Counter (grow-only counter) — CRDT
// Каждый узел инкрементирует свой счётчик, конфликтов нет
public class GCounter {
    private final Map<String, Long> counters = new HashMap<>(); // nodeId → count

    public void increment(String nodeId) {
        counters.merge(nodeId, 1L, Long::sum);
    }

    // Merge с другой репликой — просто max по каждому узлу
    public void merge(GCounter other) {
        other.counters.forEach((node, count) ->
            counters.merge(node, count, Math::max)
        );
    }

    public long value() {
        return counters.values().stream().mapToLong(Long::longValue).sum();
    }
}
```

`CRDT` используются в `Riak` (counters, sets, maps), `Redis` (CRDTs в Redis Enterprise), коллаборативных редакторах (Figma, Google Docs).

## Q16. (!) Что такое кворум и как он обеспечивает согласованность?

**Кворум** (quorum) — минимальное число узлов, которые должны подтвердить операцию, чтобы она считалась успешной. Кворумы позволяют добиться согласованности без централизованного координатора: гарантию даёт не главный узел, а пересечение множеств.

Работает это через формулу `W + R > N`, где:
- `N` — общее число реплик;
- `W` — сколько узлов подтверждают запись (write quorum);
- `R` — сколько узлов опрашивают при чтении (read quorum).

**Почему это работает:** если `W + R > N`, множества узлов записи и чтения обязаны **пересекаться** хотя бы в одном узле. А значит, в каждом read-кворуме гарантированно есть как минимум одна реплика с последней записью — её и вернут клиенту.

Пример пересечения кворумов при `N=3` репликах (`Узел 1`, `Узел 2`, `Узел 3`):

- **Write `W=2`** — запись на `Узел 1` и `Узел 2`.
- **Read `R=2`** — чтение с `Узел 2` и `Узел 3`.
- **Пересечение!** `Узел 2` входит и в кворум записи, и в кворум чтения, поэтому содержит последнюю запись.
- Итог: `W + R = 4 > N = 3` → гарантия, что чтение увидит запись.

## Q17. Что такое формула W + R > N и как она работает?

Формула `W + R > N` — это математическое условие того, что кворумы записи и чтения пересекаются. Подкручивая W и R при фиксированном N, мы сдвигаем баланс между скоростью записи, скоростью чтения и отказоустойчивостью:

| Конфигурация | W | R | Характеристика |
|-------------|---|---|----------------|
| `W=N, R=1` | 3 | 1 | Быстрое чтение, медленная запись, нет отказоустойчивости на запись |
| `W=1, R=N` | 1 | 3 | Быстрая запись, медленное чтение, нет отказоустойчивости на чтение |
| `W=2, R=2` (majority) | 2 | 2 | Сбалансированно, переживает отказ 1 узла из 3 |
| `W=1, R=1` | 1 | 1 | Максимальная скорость, но `W+R=2 ≤ N=3` — нет гарантии согласованности |

```
N=5, W=3, R=3:  W+R=6 > 5 ✓  — согласованность, переживает отказ 2 узлов
N=5, W=3, R=2:  W+R=5 = 5 ✗  — формально нет гарантии (нужно строго >)
N=5, W=1, R=1:  W+R=2 < 5 ✗  — eventual consistency, максимальная скорость
```

**Подводный камень:** даже при `W + R > N` кворум сам по себе не даёт `linearizability`. Пересечение гарантирует, что чтение увидит последнюю запись, но не упорядочивает конкурентные записи между собой — для этого нужен дополнительный механизм (version vectors, timestamps).

## Q18. Как настроить кворум в Cassandra?

В `Cassandra` нет глобальной настройки «CP или AP» — вместо этого `consistency level` (CL) задаётся на уровне каждого запроса и определяет фактические W и R. Один и тот же keyspace может обслуживать критичные запросы строго, а некритичные — быстро:

```cql
-- Создание keyspace с replication factor = 3
CREATE KEYSPACE orders WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'dc1': 3,
  'dc2': 3
};

-- Запись с QUORUM: W = ⌊N/2⌋ + 1 = 2 из 3
INSERT INTO orders.items (id, name, price)
VALUES (uuid(), 'Laptop', 999.99)
USING CONSISTENCY QUORUM;

-- Чтение с QUORUM: R = 2 из 3
-- W(2) + R(2) = 4 > N(3) → гарантия согласованности
SELECT * FROM orders.items WHERE id = ?
USING CONSISTENCY QUORUM;

-- Максимальная доступность (AP-режим)
SELECT * FROM orders.items WHERE id = ?
USING CONSISTENCY ONE;  -- R=1, быстро, но может быть устаревшее

-- Максимальная согласованность (CP-режим)
INSERT INTO orders.items (id, name, price)
VALUES (uuid(), 'Laptop', 999.99)
USING CONSISTENCY ALL;  -- W=N=3, все реплики должны ответить
```

Уровни согласованности `Cassandra`:

| CL | Описание | Trade-off |
|----|----------|-----------|
| `ANY` | Запись принята хотя бы одним узлом (включая hinted handoff) | Максимальная доступность, минимальная гарантия |
| `ONE` | 1 реплика | Быстро, AP |
| `QUORUM` | ⌊N/2⌋ + 1 реплик | Баланс, strong consistency при W+R>N |
| `LOCAL_QUORUM` | Кворум в локальном дата-центре | Баланс + низкая latency (без кросс-DC) |
| `EACH_QUORUM` | Кворум в каждом дата-центре | Максимальная кросс-DC согласованность |
| `ALL` | Все реплики | CP, минимальная доступность |

## Q19. (!) Что такое алгоритм консенсуса и зачем он нужен?

**Алгоритм консенсуса** — протокол, который позволяет группе узлов договориться об одном значении, даже если часть узлов отказала. Это фундаментальная задача распределённых систем: теорема `FLP` (1985) доказывает, что в полностью асинхронной системе консенсус в общем случае неразрешим, поэтому реальные алгоритмы опираются на таймауты и предположение, что большинство узлов живо.

Консенсус нужен везде, где узлам важно «договориться» об одном факте:
- **выбор лидера** — кто принимает решения за кластер;
- **репликация журнала** — все реплики должны согласовать единый порядок записей;
- **распределённые блокировки** — кто сейчас владеет ресурсом;
- **атомарные транзакции** — общий вердикт commit или abort;
- **конфигурация кластера** — какие узлы вообще входят в кластер.

Поток репликации записи через консенсус (участники: `Клиент`, `Лидер`, `Follower 1`, `Follower 2`):

1. `Клиент` → `Лидер`: `write(x=42)`.
2. `Лидер` → `Follower 1`: `AppendEntries(x=42)`.
3. `Лидер` → `Follower 2`: `AppendEntries(x=42)`.
4. `Follower 1` → `Лидер`: `ACK`.
5. `Follower 2` → `Лидер`: `ACK`.
6. *Note over `Лидер`*: кворум (2/3) достигнут.
7. `Лидер` фиксирует запись (`Commit`).
8. `Лидер` → `Клиент`: `OK`.
9. `Лидер` → `Follower 1`: commit notification.
10. `Лидер` → `Follower 2`: commit notification.

Основные алгоритмы: `Paxos` (Лэмпорт, 1989), `Raft` (Онгаро и Устерхаут, 2014), `ZAB` (ZooKeeper), `Viewstamped Replication`.

## Q20. (!) Как работает алгоритм Raft?

**Raft** — алгоритм консенсуса, специально спроектированный как понятная альтернатива `Paxos`. Используется в `etcd`, `Consul`, `CockroachDB`, `TiKV`. Главная идея Raft — разбить сложную задачу консенсуса на три независимые и более простые подзадачи:

**1. Выбор лидера (Leader Election)**:
- Узлы в состояниях: `Leader`, `Follower`, `Candidate`
- Если follower не получает heartbeat от лидера в течение election timeout — становится candidate
- Candidate запрашивает голоса у всех узлов; получив большинство — становится лидером
- В каждый момент максимум один лидер на term (эпоху)

**2. Репликация журнала (Log Replication)**:
- Все записи идут через лидера
- Лидер отправляет `AppendEntries` RPC follower'ам
- Запись считается committed, когда реплицирована на большинство

**3. Безопасность (Safety)**:
- Новый лидер обязан содержать все committed записи
- Candidate не получит голос от узла с более полным журналом

Конечный автомат состояний узла Raft (начальное состояние — `Follower`):

- `Follower` → `Candidate`: election timeout, нет heartbeat.
- `Candidate` → `Leader`: получил большинство голосов.
- `Candidate` → `Follower`: получил heartbeat от нового лидера.
- `Candidate` → `Candidate`: таймаут выборов, новый term.
- `Leader` → `Follower`: обнаружил лидера с большим term.

**Итог:** Raft гарантирует `linearizability` для операций, проходящих через лидера. Например, `etcd` по умолчанию направляет чтения через лидера ради строгой гарантии; `serializable`-чтения (с любого узла) быстрее, но слабее по согласованности — это сознательный размен скорости на актуальность.

## Q21. Как работает Paxos и чем отличается от Raft?

**Paxos** (Лэмпорт, 1989) — первый формально доказанный алгоритм консенсуса. Работает в две фазы:

**Фаза 1 (Prepare)**:
- Proposer выбирает номер предложения `n` и отправляет `Prepare(n)` acceptor'ам
- Acceptor отвечает `Promise(n)` — обещает не принимать предложения с номером < n

**Фаза 2 (Accept)**:
- Proposer, получив ответы от кворума, отправляет `Accept(n, value)`
- Acceptor принимает, если не обещал большего номера
- Значение считается выбранным, когда принято кворумом

Сравнение `Paxos` и `Raft`:

| Аспект | `Paxos` | `Raft` |
|--------|---------|--------|
| Роли | Proposer, Acceptor, Learner | Leader, Follower, Candidate |
| Лидер | Необязателен (multi-leader) | Обязателен (single leader) |
| Понятность | Сложный, трудно реализовать | Разработан для понятности |
| Гибкость | Более гибкий (Multi-Paxos, Fast Paxos) | Менее гибкий, но достаточный |
| Реализации | Google Chubby, Spanner | etcd, Consul, CockroachDB |
| Формальное доказательство | Полное | На основе Paxos |

**Вывод:** на практике `Raft` выбирают чаще именно из-за понятности — его проще корректно реализовать, тестировать и отлаживать. `Paxos` мощнее и гибче, но эта гибкость оборачивается сложностью, на которой легко допустить ошибку.

## Q22. Что такое split-brain и как алгоритмы консенсуса его предотвращают?

**Split-brain** («раздвоение мозга») — ситуация, когда при partition несколько сегментов кластера одновременно считают себя «главными» и независимо принимают записи. Это худший сценарий: данные расходятся, и слить их обратно потом бывает невозможно — нет способа узнать, какая из двух версий «правильная».

Иллюстрация split-brain при разделении кластера:

- **Раздел A**: `Бывший лидер` (продолжает писать) и `Follower 1`.
- **Раздел B**: `Follower 2` (избран новым лидером), `Follower 3`, `Follower 4`.
- Между разделами связь `Бывший лидер` → `Follower 2` разорвана (✕ partition) — в итоге оба считают себя лидером.

Алгоритмы консенсуса не дают split-brain возникнуть через три механизма:

1. **Кворум большинства.** Лидер может зафиксировать запись только с подтверждением от `⌊N/2⌋ + 1` узлов. При разделении 5 узлов на 2+3 кворума может достичь лишь раздел с тремя узлами — у меньшинства физически нет большинства, поэтому второго лидера, способного писать, не появится.
2. **Term/epoch.** Каждый лидер работает в своём term (эпохе). Старый лидер, получив сообщение с бо́льшим term, понимает, что его уже сместили, и немедленно становится follower.
3. **Fencing tokens.** При выдаче блокировки возвращается монотонно растущий token; ресурс принимает только запросы с самым свежим token и отклоняет команды старого лидера, даже если тот «не заметил», что его сместили.

```java
// Пример: fencing token в распределённой блокировке
public class FencedLock {
    private final AtomicLong fencingToken = new AtomicLong(0);

    public LockResult tryLock(String clientId) {
        long token = fencingToken.incrementAndGet();
        return new LockResult(clientId, token);
    }

    // Ресурс проверяет: принимать только запросы с максимальным token
    public boolean validateToken(long token, long lastSeenToken) {
        return token > lastSeenToken; // старый лидер будет отклонён
    }
}
```

## Q23. (!) Что такое PACELC и как связано с CAP?

**PACELC** — расширение CAP, предложенное Даниэлем Абади в 2012 году, которое закрывает главную дыру CAP: что система делает, когда partition нет. Формулировка: при **P**artition выбираем между **A** и **C** (как в CAP), а в остальное время — **E**lse — между **L**atency и **C**onsistency. То есть даже при здоровой сети система может жертвовать согласованностью ради меньшей задержки.

Дерево решений PACELC — есть ли partition?

- **Да (`P`)** → выбор: `A` или `C`?
  - `A` → **PA** — доступность при partition.
  - `C` → **PC** — согласованность при partition.
- **Нет (`E`, Else)** → выбор: `L` или `C`?
  - `L` → **EL** — низкая задержка в норме.
  - `C` → **EC** — согласованность в норме.

**Почему PACELC ближе к реальности:**
- CAP описывает только поведение при сбое сети — редкое событие;
- PACELC добавляет повседневный компромисс latency vs consistency, который проявляется в каждом запросе;
- именно поэтому на практике часть EL/EC часто важнее PA/PC: большинство запросов выполняются **без** partition.

## Q24. Как классифицировать реальные системы по PACELC?

| Система | Классификация PACELC | Объяснение |
|---------|---------------------|------------|
| `Cassandra` | PA/EL | При partition — доступность; в норме — низкая latency (async replication) |
| `DynamoDB` (default) | PA/EL | Eventual reads по умолчанию; при partition — доступность |
| `MongoDB` (majority) | PC/EC | При partition — согласованность; в норме — тоже согласованность |
| `ZooKeeper` | PC/EC | Всегда согласованность, даже ценой latency |
| `etcd` | PC/EC | Raft, чтение через лидера, линеаризуемость |
| `CockroachDB` | PC/EC | Строгая сериализуемость, Raft |
| `Riak` | PA/EL | Dynamo-модель, оптимизация latency |
| `PostgreSQL` (async) | PA/EL | Асинхронная репликация → latency важнее |
| `PostgreSQL` (sync) | PC/EC | Синхронная репликация → согласованность важнее |
| Google `Spanner` | PC/EC | TrueTime, внешняя согласованность |

**Важная оговорка:** классификация задаёт поведение *по умолчанию*. `Cassandra` и `DynamoDB` — PA/EL из коробки, но на конкретном запросе превращаются в PC/EC, если включить `QUORUM` или `consistent reads`. То есть PACELC-метка системы — это её настройка по умолчанию, а не приговор.

## Q25. (!) Cassandra и CAP: как работает настраиваемая согласованность?

`Cassandra` — архетипическая AP-система, но её сила в **настраиваемой согласованности** (tunable consistency): клиент выбирает уровень для каждого запроса, поэтому одна и та же база покрывает и быстрые, и строгие сценарии. Это не «AP навсегда», а «AP по умолчанию, CP по требованию»:

```cql
-- AP-режим: быстро, но возможны устаревшие данные
SELECT * FROM users WHERE id = ? CONSISTENCY ONE;

-- Strong consistency: W(QUORUM) + R(QUORUM) > N(RF)
INSERT INTO users (id, name) VALUES (?, ?) CONSISTENCY QUORUM;
SELECT * FROM users WHERE id = ? CONSISTENCY QUORUM;

-- Для мульти-DC: LOCAL_QUORUM не ходит в другие дата-центры
SELECT * FROM users WHERE id = ? CONSISTENCY LOCAL_QUORUM;
```

Раз репликация асинхронная, реплики временно расходятся — поэтому `Cassandra` использует несколько механизмов, чтобы они в итоге сошлись:

- **Read repair** — при чтении с нескольких реплик, если данные расходятся, устаревшие реплики тут же обновляются актуальным значением;
- **Anti-entropy repair** (`nodetool repair`) — фоновый процесс, который сравнивает Merkle trees реплик и докатывает недостающие данные;
- **Hinted handoff** — если реплика недоступна, координатор сохраняет «подсказку» (hint) и доставит данные, когда узел вернётся;
- **Last-write-wins** (LWW) — конфликты разрешаются по timestamp: побеждает запись с большей меткой времени.

```yaml
# cassandra.yaml — ключевые параметры согласованности
hinted_handoff_enabled: true
max_hint_window_in_ms: 10800000  # 3 часа — как долго хранить hints
read_request_timeout_in_ms: 5000
write_request_timeout_in_ms: 2000
```

## Q26. (!) DynamoDB и CAP: какой trade-off?

`DynamoDB` — управляемая NoSQL-БД от AWS, по умолчанию AP с `eventual consistency`. Главный рычаг управления компромиссом — флаг `consistentRead`, который переключает между двумя режимами чтения: дешёвым и устаревающим либо точным и дорогим:

```java
// Eventually consistent read (по умолчанию) — AP
// Дешевле (0.5 RCU за 4KB), может вернуть устаревшие данные
GetItemRequest eventualRead = GetItemRequest.builder()
    .tableName("Orders")
    .key(Map.of("PK", AttributeValue.builder().s("ORDER#123").build()))
    .consistentRead(false) // default
    .build();

// Strongly consistent read — ближе к CP
// Дороже (1 RCU за 4KB), гарантирует последние данные
GetItemRequest strongRead = GetItemRequest.builder()
    .tableName("Orders")
    .key(Map.of("PK", AttributeValue.builder().s("ORDER#123").build()))
    .consistentRead(true)
    .build();
```

Особенности `DynamoDB` в контексте CAP:

| Аспект | Поведение |
|--------|-----------|
| Eventual reads | Данные конвергируют обычно за ~1 секунду |
| Strong reads | Только для `GetItem`/`Query`, не для `Scan` по GSI |
| Global Tables | Multi-region, eventual consistency между регионами (last-writer-wins) |
| Transactions | `TransactWriteItems` — ACID на уровне таблицы, CP-семантика |
| GSI | Всегда eventually consistent (асинхронное обновление индекса) |

`DynamoDB` по PACELC: **PA/EL** (default) или **PC/EC** (при `consistentRead=true` + transactions).

## Q27. (!) Zookeeper и CAP: почему это CP-система?

`ZooKeeper` — классическая **CP-система** для координации кластеров. Он реализует протокол `ZAB` (ZooKeeper Atomic Broadcast), близкий по идее к `Paxos`, и сознательно жертвует доступностью ради того, чтобы координация никогда не была противоречивой.

Почему это CP:
- **все записи идут через лидера** — один leader, остальные follower'ы, никаких независимых записей;
- **запись требует кворума** — лидер не подтвердит её, пока большинство (`⌊N/2⌋ + 1`) follower'ов не зафиксируют её в журнал;
- **при partition** раздел без кворума **отказывается обслуживать запросы** — то есть жертвует availability ради согласованности;
- по умолчанию даёт **sequential consistency**, а `linearizability` — при вызове `sync()` перед чтением.

```
Кластер ZooKeeper (5 узлов):
  При partition 2+3:
    Раздел с 3 узлами: выбирает нового лидера, продолжает работать ✓
    Раздел с 2 узлами: не может достичь кворума, отклоняет запросы ✗
    → Согласованность сохранена, доступность потеряна для меньшинства
```

`ZooKeeper` используется для:
- Распределённых блокировок (`/locks/resource-1`)
- Выбора лидера (`/election/leader`)
- Хранения конфигурации (`/config/service-a`)
- Service discovery (`/services/order-service/instances`)

**Аналоги:** `etcd` и `Consul` (оба на `Raft`) решают ту же задачу координации и тоже являются CP-системами — выбор лидера, блокировки и конфигурация требуют строгой согласованности, доступностью здесь жертвуют осознанно.

## Q28. Redis — CP или AP?

**Redis** в кластерном режиме (`Redis Cluster`) в терминах CAP ближе к **AP**. Причина — асинхронная репликация: мастер подтверждает запись, не дожидаясь реплик, поэтому при partition секции кластера продолжают отвечать, но данные между ними могут разойтись до восстановления связи. Strong consistency при partition Redis не гарантирует.

```
Redis Cluster (6 узлов: 3 master + 3 replica):
  Master A (слоты 0-5460)     → Replica A'
  Master B (слоты 5461-10922) → Replica B'
  Master C (слоты 10923-16383)→ Replica C'

  Репликация: асинхронная (по умолчанию)
  → write на Master A подтверждается ДО репликации на A'
  → при падении Master A возможна потеря последних записей
```

Нюансы по конфигурациям:

- **Одиночный Redis** (standalone) — по сути CA: узел один, разделять между репликами нечего.
- **Redis Sentinel с репликацией** — тоже ближе к AP: репликация асинхронная, и при failover мастера последние неотреплицированные записи могут пропасть.
- **Параметр `WAIT`** позволяет дождаться подтверждения от реплик и тем самым сдвинуть поведение в сторону CP, заплатив задержкой:

```redis
SET order:123 "confirmed"
WAIT 1 5000  -- ждать подтверждения от 1 реплики, таймаут 5 сек
```

## Q29. PostgreSQL с репликацией — CP или AP?

Однозначного ответа нет — всё определяет режим репликации.

**Синхронная репликация** (`synchronous_commit = on`): мастер подтверждает запись только после того, как данные дошли до реплик(и). При partition, когда нужные реплики недоступны, запись блокируется или отказывает — клиент не получит «ОК», пока согласованность не гарантирована. Это **CP**.

```sql
-- Настройка синхронной репликации (postgresql.conf)
-- synchronous_standby_names = 'FIRST 1 (replica1, replica2)'
-- synchronous_commit = on

-- Проверка статуса репликации
SELECT client_addr, state, sync_state, sent_lsn, replay_lsn
FROM pg_stat_replication;

-- sync_state: 'sync' — синхронная (CP), 'async' — асинхронная (AP)
```

**Асинхронная репликация**: мастер подтверждает запись сразу, а реплики догоняют в фоне. При partition мастер продолжает принимать записи — **AP**. Расплата: если мастер упадёт раньше, чем реплика получит изменения, эти записи потеряются.

| Режим | `synchronous_commit` | Поведение | CAP |
|-------|---------------------|-----------|-----|
| `on` | Ждёт WAL flush на реплике | Потеря данных = 0, latency выше | CP |
| `remote_apply` | Ждёт apply на реплике | Чтение с реплики актуально | CP |
| `remote_write` | Ждёт записи в OS cache реплики | Компромисс | CP (слабее) |
| `off` | Не ждёт реплики | Минимальная latency, возможна потеря | AP |

## Q30. Kafka и CAP: какой trade-off?

В терминах CAP `Kafka` — система с настраиваемым поведением, от AP до CP. По умолчанию она ориентирована на **доступность и отказоустойчивость**: брокеры продолжают принимать и отдавать сообщения. Но настройками продьюсера и топика её можно сдвинуть в сторону строгой durability, пожертвовав доступностью записи.

```properties
# Producer: AP-режим (максимальный throughput)
acks=1                    # лидер подтвердил, не ждём реплик
retries=0

# Producer: CP-режим (максимальная durability)
acks=all                  # ждём подтверждения от всех ISR
min.insync.replicas=2     # минимум 2 ISR для записи
retries=2147483647        # бесконечные ретраи
enable.idempotence=true   # exactly-once семантика
```

| Параметр | AP-значение | CP-значение | Влияние |
|----------|------------|-------------|---------|
| `acks` | `0` или `1` | `all` | Подтверждение записи |
| `min.insync.replicas` | `1` | `2+` | Минимум реплик для записи |
| `unclean.leader.election.enable` | `true` | `false` | Разрешить несинхронную реплику стать лидером |

**Ключевой пример CP-поведения:** при `acks=all` и `min.insync.replicas=2`, если живых синхронных реплик меньше двух, продьюсер получит `NotEnoughReplicasException` вместо подтверждения. Kafka сознательно отказывает в записи, чтобы не подтвердить сообщение, которое могло бы потеряться, — то есть жертвует доступностью ради целостности.

## Q31. MongoDB и CAP: как настраивается поведение?

`MongoDB` — система с настраиваемой согласованностью, и управляют ею два параметра: `writeConcern` (сколько узлов подтверждают запись) и `readConcern` (какие данные разрешено читать). База работает на `ReplicaSet` с одним primary и несколькими secondary, а нужный режим — от быстрого AP до строгого CP — задаётся per-operation:

```javascript
// AP-режим: быстрая запись, возможна потеря при failover
db.orders.insertOne(
  { orderId: "123", status: "confirmed" },
  { writeConcern: { w: 1 } }  // только primary подтвердил
);

// CP-режим: запись подтверждена большинством
db.orders.insertOne(
  { orderId: "123", status: "confirmed" },
  { writeConcern: { w: "majority", j: true } }  // majority + journal
);

// Чтение с гарантией causal consistency
const session = db.getMongo().startSession({ causalConsistency: true });
session.getDatabase("shop").orders.find({ orderId: "123" })
  .readConcern("majority")       // читать только committed данные
  .readPreference("secondary");  // можно читать с secondary
```

**Зачем нужны Causal Consistency Sessions:** они дают `causal consistency` через метки `clusterTime` и `operationTime`. Это решает классическую проблему чтения с secondary — клиент может разгрузить primary, читая с реплики, и при этом гарантированно увидеть результаты собственных предыдущих записей в той же сессии (read-your-writes), а не «провалиться в прошлое» из-за отставшей реплики.

## Q32. Можно ли систему переключать между CP и AP?

Да — и это норма, а не исключение. Большинство современных хранилищ не «зашиты» в CP или AP, а позволяют выбирать поведение per-request или per-collection через уровень согласованности:

| Система | CP-настройка | AP-настройка |
|---------|-------------|-------------|
| `Cassandra` | `QUORUM` / `ALL` | `ONE` / `LOCAL_ONE` |
| `DynamoDB` | `consistentRead: true` | `consistentRead: false` (default) |
| `MongoDB` | `w: "majority"`, `readConcern: "majority"` | `w: 1`, `readConcern: "local"` |
| `Kafka` | `acks: all`, `min.insync.replicas: 2` | `acks: 1` |
| `PostgreSQL` | `synchronous_commit: on` | `synchronous_commit: off` |

**Практический вывод:** уровень выбирают под операцию, а не под систему. Критичные операции (платежи, инвентарь) гоняют со строгой согласованностью, некритичные (лента, аналитика) — с упором на доступность и скорость. Поэтому корректная формулировка на собеседовании — не «эта БД CP или AP», а «в каком режиме её настроили для конкретного запроса».

## Q33. Как выбирать CP vs AP для бизнес-системы?

Отталкивайтесь от одного главного вопроса: **допустима ли для этой операции устаревшая информация?** Если нет — нужен CP; если да — почти всегда выгоднее AP. Остальное уточняет, насколько строго.

Дерево выбора — допустимы ли устаревшие данные?

- **Нет** → допустима ли кратковременная недоступность?
  - **Да** → **CP** (банк, инвентарь, бронирование).
  - **Нет** → **Гибрид**: CP для записи, AP для чтения.
- **Да** → как быстро данные должны сойтись?
  - **Секунды** → **AP + read repair** (лента, рекомендации).
  - **Минуты** → **AP + eventual** (аналитика, логи).

Дальше уточняют выбор четыре фактора:

- **Цена устаревших данных.** Банковский баланс, остаток на складе, занятое место в брони — устаревать нельзя, нужен CP. Лента постов, счётчики лайков, рекомендации — eventual consistency вполне допустима, выбираем AP.
- **Влияние недоступности.** Если при partition система «висит» 30 секунд — это терпимо? Для платежа часто да (лучше подождать, чем ошибиться), для real-time чата — нет.
- **Частота partition.** В одной зоне разделения редки; в мульти-регион они куда вероятнее, и там AP обычно предпочтительнее.
- **Что дороже бизнесу** — показать устаревшие данные или не показать ничего? Этот ответ и есть итоговый выбор между AP и CP.

## Q34. (!) Как тестировать partition tolerance?

Суть проста: нельзя верить заявленным гарантиям, пока не сломаешь сеть и не проверишь, что система ведёт себя как обещано. Есть три основных подхода.

**1. Jepsen** — фреймворк Кайла Кингсбери, ставший стандартом проверки согласованности распределённых систем:
- поднимает кластер и искусственно инжектирует сетевые разделения;
- по истории операций проверяет, не нарушились ли заявленные гарантии (linearizability, sequential consistency);
- на практике нашёл реальные баги в `Cassandra`, `MongoDB`, `Redis`, `Kafka`, `CockroachDB` и десятках других систем — то есть «заявлено CP» и «реально CP» совпадают далеко не всегда.

**2. Chaos Engineering** — целенаправленное внесение сбоев в staging или production, чтобы увидеть поведение системы под реальным разделением:

```bash
# Имитация network partition с помощью iptables
# Блокируем трафик между узлами 1 и 3
sudo iptables -A INPUT -s 10.0.0.3 -j DROP
sudo iptables -A OUTPUT -d 10.0.0.3 -j DROP

# Имитация задержки сети (latency injection)
sudo tc qdisc add dev eth0 root netem delay 200ms 50ms

# Имитация потери пакетов (partial partition)
sudo tc qdisc add dev eth0 root netem loss 30%
```

**3. Инструменты Chaos Engineering**:

| Инструмент | Описание |
|-----------|----------|
| `Chaos Monkey` (Netflix) | Случайно убивает инстансы в production |
| `Toxiproxy` (Shopify) | Прокси для имитации сетевых проблем |
| `Pumba` | Chaos testing для Docker контейнеров |
| `Litmus` | Chaos engineering для Kubernetes |
| `tc` / `iptables` | Linux-инструменты для имитации сетевых проблем |

**Что именно проверять** при тестировании:
- система вовремя обнаруживает partition (через таймауты и heartbeat), а не зависает молча;
- не возникает split-brain — двух активных лидеров одновременно;
- данные не теряются при восстановлении связи;
- после устранения partition система сходится автоматически, без ручного вмешательства;
- клиенты получают честные ошибки, а не молчаливое повреждение данных (это худший исход — его сложнее всего заметить).

## Q35. Как проектировать систему с учётом CAP?

Главный принцип: не пытайтесь назначить всей системе один режим. CAP-выбор делается на уровне отдельной операции, а архитектура должна позволять разным частям жить по разным правилам. Конкретные приёмы ниже.

**1. Не проектируйте «глобально CP или AP»** — выбирайте режим на уровне операции:

```
Пример: e-commerce
  - Остаток на складе → CP (нельзя продать товар, которого нет)
  - Каталог товаров → AP (устаревшая цена допустима на секунды)
  - Корзина → AP (синхронизируется при checkout)
  - Платёж → CP (строгая согласованность обязательна)
```

**2. Используйте компенсирующие транзакции** вместо строгой согласованности где возможно:
- Паттерн `Saga` — цепочка локальных транзакций с компенсациями
- Паттерн `Outbox` — гарантированная доставка событий через таблицу outbox
- `Idempotency keys` — безопасные повторные запросы

**3. Разделяйте reads и writes** (`CQRS`):
- Запись через CP-подсистему (один master, синхронная репликация)
- Чтение через AP-подсистему (множество read-реплик, eventual consistency)

**4. Мониторьте replication lag** — разницу между мастером и репликами:

```sql
-- PostgreSQL: проверка задержки репликации
SELECT now() - pg_last_xact_replay_timestamp() AS replication_lag;

-- Если lag > допустимого — алерт, переключение на чтение с мастера
```

**5. Проектируйте для graceful degradation**: при partition система должна деградировать предсказуемо, а не ломаться неожиданно. Клиент должен знать, что получает устаревшие данные (например, через заголовок `X-Data-Staleness`).

## Q36. Что такое PACELC — расширение CAP для нормального состояния?

**PACELC** (Partition-Availability-Consistency-Else-Latency-Consistency) — теорема, предложенная Даниэлем Абади в 2012 году. Она достраивает CAP второй осью компромисса: что система делает, когда разделения **нет**.

В этом и смысл: CAP описывает только поведение при partition, а partition в реальных системах редки. Куда важнее, как система ведёт себя в **нормальном режиме** — а там приходится выбирать между **задержкой** (`Latency`) и **согласованностью** (`Consistency`): ждать подтверждения от реплик ради свежих данных или ответить быстро, рискуя отдать устаревшее.

```
PACELC формулировка:
  Если есть P (Partition):
    выбираем A (Availability) ИЛИ C (Consistency)
  Else (нет Partition):
    выбираем L (Latency) ИЛИ C (Consistency)
```

| Система | При Partition | В норме | Классификация |
|---------|---------------|---------|---------------|
| `DynamoDB` | A | L | PA/EL |
| `Cassandra` (ONE) | A | L | PA/EL |
| `Cassandra` (QUORUM) | A | C | PA/EC |
| `ZooKeeper` | C | C | PC/EC |
| `HBase` | C | C | PC/EC |
| `MongoDB` (default) | C | C | PC/EC |
| `CRDT-системы` | A | L | PA/EL |

**Почему PACELC важнее CAP на практике:**
- в системе с uptime 99.9% partition случается лишь часы в год, а компромисс latency vs consistency проявляется в **каждом** запросе;
- при QUORUM-чтении в Cassandra нужно дождаться ответа большинства реплик — это повышает latency, но возвращает свежие данные;
- при eventual consistency (ONE) latency минимальна, зато данные могут оказаться устаревшими.

```
Пример для собеседования:
  Cassandra с RF=3:
  - CONSISTENCY ONE:   latency ~1ms, может вернуть устаревшие данные (PA/EL)
  - CONSISTENCY QUORUM: latency ~5ms, всегда актуальные данные (PA/EC)
  - CONSISTENCY ALL:   latency ~10ms, максимальная свежесть (PA/EC)
```

## Q37. ZooKeeper и HBase как CP-системы: детали реализации

Оба — CP-системы, и обе опираются на один протокол: HBase делегирует координацию ZooKeeper, а тот реализует строгую CP-семантику через **ZAB** (ZooKeeper Atomic Broadcast). Разберём, как именно это устроено.

**ZooKeeper** — распределённый координатор со строгой CP-семантикой.

**Как ZAB обеспечивает согласованность:**
1. Все операции записи направляются **лидеру**
2. Лидер присваивает **zxid** (монотонно возрастающий идентификатор транзакции)
3. Лидер рассылает `PROPOSE` фолловерам; те отвечают `ACK`
4. После получения кворума ACK лидер отправляет `COMMIT`
5. Операция видна клиентам только после commit

**При network partition:**
- Меньшинство узлов перестаёт принимать запись (блокирует запросы)
- Лидер на меньшинстве уходит в отставку
- Клиенты получают `ConnectionLossException`

```java
// ZooKeeper: создание эфемерного узла (distributed lock)
ZooKeeper zk = new ZooKeeper("localhost:2181", 3000, null);
String path = zk.create("/lock/my-lock-",
    new byte[0],
    ZooDefs.Ids.OPEN_ACL_UNSAFE,
    CreateMode.EPHEMERAL_SEQUENTIAL);
// При потере соединения (partition) — узел исчезает автоматически
// Это гарантирует отсутствие split-brain: два лидера невозможны
```

**HBase** использует ZooKeeper для координации:
- ZooKeeper хранит местоположение region-серверов
- При partition region-сервер не может обновить ZK → считается мёртвым
- RegionMaster назначает регионы на другие серверы
- Запросы к недоступному region-серверу блокируются (CP: лучше ошибка, чем неконсистентные данные)

| Характеристика | ZooKeeper | HBase |
|----------------|-----------|-------|
| Протокол консенсуса | ZAB | ZAB (через ZK) |
| При partition | Блокирует меньшинство | Перемещает регионы |
| Задержка записи | ~1-5ms (синхронная) | ~5-20ms |
| Гарантия | Linearizability | Strong consistency per row |
| Применение | Service discovery, leader election, locks | OLTP с высокой нагрузкой на запись |

## Q38. Cassandra и DynamoDB как AP-системы: детали

Обе — AP-системы, но добиваются доступности по-разному: Cassandra — через архитектуру без лидера, DynamoDB — через управляемый сервис с режимом чтения по выбору. Начнём с Cassandra.

**Cassandra** спроектирована ради максимальной доступности. Её фундамент — архитектура без лидера.

**Архитектура без лидера (leaderless):**
- все узлы равноправны (peer-to-peer), нет «главного»;
- запись приходит на любой узел-координатор, и тот реплицирует её на N узлов по consistent hashing;
- нет единой точки отказа — поэтому partition не останавливает работу целиком, продолжают отвечать доступные узлы.

```
Настройка согласованности Cassandra:
  RF=3, DC=1
  CONSISTENCY ONE:    W=1, R=1 — максимальная доступность, может быть stale read
  CONSISTENCY QUORUM: W=2, R=2 — 2+2>3, всегда читаем свежие данные
  CONSISTENCY LOCAL_QUORUM: кворум в рамках одного датацентра
  CONSISTENCY ALL:    W=3, R=3 — CP-режим (блокирует при недоступности ноды)
```

**Hinted Handoff** — при недоступности реплики координатор сохраняет «подсказку» и доставляет данные позже. Это обеспечивает AP при коротких partition.

**Read Repair** — при чтении с кворумом, если реплики расходятся, Cassandra автоматически обновляет устаревшие реплики.

**DynamoDB** — управляемый сервис AWS, AP по умолчанию, CP по запросу:

```
DynamoDB режимы чтения:
  Eventually Consistent Read (по умолчанию):
    - Запрос идёт на любую реплику из 3
    - Может вернуть данные до 1 секунды устаревшими
    - В 2 раза дешевле (0.5 RCU за 4KB)

  Strongly Consistent Read:
    - Запрос идёт только на leader-реплику
    - Всегда актуальные данные
    - 1 RCU за 4KB, больше latency
    - При partition может вернуть ошибку
```

| Характеристика | Cassandra | DynamoDB |
|----------------|-----------|----------|
| Архитектура | Leaderless ring | Leader-based (Paxos per partition) |
| При partition | Продолжает работу (AP) | Eventually consistent (AP default) |
| CP-режим | CONSISTENCY ALL / QUORUM | Strongly Consistent Reads |
| Конфликты | LWW (Last Write Wins) по timestamp | Условные записи (ConditionalExpression) |
| Anti-entropy | Read Repair, Merkle trees | Managed (прозрачно) |
| Применение | Глобально распределённые данные | AWS-нативные приложения |

## Q39. Network partition на практике: частота и типичные сценарии

Вопреки интуиции, **network partition — не экзотика, а рутина**. Многие думают, что разделение сети случается раз в год при крупной аварии, но в реальных production-системах partition происходят регулярно — и проектировать нужно с этим расчётом.

**Статистика и исследования:**
- Исследование Google (2009): в крупных дата-центрах происходят тысячи сетевых сбоев в месяц
- Исследование Microsoft: 40% инцидентов связаны с сетевыми проблемами
- Jepsen.io: большинство протестированных систем имели проблемы с partition

**Типичные сценарии partition:**

| Сценарий | Причина | Длительность |
|----------|---------|--------------|
| GC pause | Stop-the-world GC на ноде — другие узлы считают её мёртвой | Секунды |
| Сетевое оборудование | Сбой свитча, замена маршрутизатора | Минуты |
| Обновление ОС/приложения | Rolling restart — часть узлов недоступна | Минуты |
| Перегрузка сети | Пакеты теряются при пиковой нагрузке | Секунды–минуты |
| Междатацентровый сбой | Обрыв WAN-канала | Минуты–часы |
| Slow network | Пакеты доходят, но с большой задержкой (partial partition) | Переменно |
| Cloud AZ failure | AWS/GCP зона недоступна | Минуты–часы |

**Partial partition** — самый коварный случай: узлы A и B оба видят узел C, но друг друга не видят. Связность получается «дырявой и асимметричной», и классические алгоритмы консенсуса в такой топологии могут вести себя неожиданно — например, бесконечно переизбирать лидера.

```
Примеры реальных инцидентов (по данным Jepsen):
  - MongoDB 2.4: при partition могла выбрать двух primary → потеря данных
  - Redis Sentinel: split-brain при GC pause у sentinel-узлов
  - Cassandra: при partition с QUORUM возможна запись в меньшинство
  - Kafka: при partition controller мог не освободить лидерство
```

**Как защититься:**
- регулярно тестировать поведение под разделением — Jepsen, Chaos Monkey, Toxiproxy;
- настраивать таймауты с запасом относительно реального времени отказа, чтобы не принять медленный узел за мёртвый;
- применять fencing tokens против split-brain;
- проектировать для предсказуемой деградации, а не в расчёте на идеально стабильную сеть, которой не бывает.

## Q40. CAP и микросервисная архитектура: как выбор БД влияет на дизайн?

В микросервисной архитектуре каждый сервис владеет собственной БД (паттерн Database per Service). Поэтому CAP-выбор делается не один раз на всю систему, а отдельно для каждого сервиса — и именно он задаёт способ взаимодействия между сервисами: синхронный и строгий или асинхронный и устойчивый.

**CP-сервис** (строгая согласованность):
```
Когда выбирать CP:
  - Финансовые транзакции (списание средств)
  - Inventory management (остатки товаров)
  - Уникальность пользователей (регистрация)
  - Права доступа и авторизация

Последствия для дизайна:
  - Синхронные вызовы между сервисами (REST/gRPC)
  - Distributed transactions (Saga с компенсациями)
  - Возможны блокировки при partition
  - Нужен circuit breaker для защиты от каскадных отказов
```

**AP-сервис** (eventual consistency):
```
Когда выбирать AP:
  - Каталог товаров (устаревшая цена 1-2 секунды — OK)
  - Корзина покупок (синхронизируется при checkout)
  - Статистика и аналитика
  - Рекомендации и персонализация

Последствия для дизайна:
  - Асинхронное взаимодействие (события/Kafka)
  - Idempotent операции
  - Версионирование сущностей
  - Логика обработки конфликтов в бизнес-коде
```

**Практическая схема для e-commerce:**

```
Сервис         БД          CAP    Причина
──────────────────────────────────────────────────
Order          PostgreSQL  CP     Финансовая операция
Payment        PostgreSQL  CP     Списание средств
Inventory      PostgreSQL  CP     Нельзя продать дважды
Product        Cassandra   AP     Каталог, устаревание OK
Cart           Redis       AP     Сессионные данные
Search         Elasticsearch AP   Индекс, лаг допустим
Analytics      ClickHouse  AP     Аналитика, eventual OK
Notifications  Cassandra   AP     Доставка best-effort
```

**Паттерны для межсервисной согласованности:**
- **Saga** — цепочка локальных транзакций с компенсациями; заменяет распределённую транзакцию на стыке CP- и AP-сервисов;
- **Outbox + CDC** — атомарная публикация событий из той же транзакции, что и запись в БД, чтобы потребители-downstream ничего не пропустили;
- **API Composition** — агрегация данных нескольких сервисов на стороне чтения (часть подхода CQRS);
- **Read-your-writes** — sticky session или version token, чтобы клиент после своей записи гарантированно прочитал её, а не устаревшую версию.

## Q41. (!) Google Spanner и TrueTime: как Spanner обходит CAP?

Коротко: Spanner CAP не обходит — он остаётся CP-системой, но настолько снижает вероятность partition и так точно синхронизирует время, что на практике ведёт себя почти как «CA». **Google Spanner** — глобально распределённая БД, которую Google маркетингово позиционирует как CA. С точки зрения теоремы это невозможно, и весь фокус — в инженерии, а не в нарушении CAP.

**TrueTime API** — ключевая инновация Spanner:
- каждый дата-центр Google оснащён **атомными часами** и **GPS-приёмниками**;
- TrueTime возвращает не одну точку, а **интервал** `[earliest, latest]`, внутри которого истинное время гарантированно находится — то есть API честно сообщает свою погрешность;
- неопределённость (uncertainty interval) обычно составляет всего **1–7 миллисекунд**.

```
TrueTime API:
  TT.now()   → TTInterval{earliest: t-ε, latest: t+ε}
  TT.after(t) → true, если t точно в прошлом
  TT.before(t) → true, если t точно в будущем

Алгоритм commit wait:
  1. Транзакция получает commit timestamp s = TT.now().latest
  2. Spanner ждёт, пока TT.after(s) станет true (~7ms)
  3. Только после этого транзакция видна другим
  → Это гарантирует, что все узлы "видели" время > s до commit
```

**Почему Spanner не нарушает CAP:**

Spanner — это CP-система. При network partition Spanner блокирует записи (ждёт кворума Paxos). Но Google построил очень надёжную сеть между дата-центрами (выделенные кабели, минимальные потери), поэтому partition практически не происходит.

> Брюер сам прокомментировал: "Spanner — технически CP, но с очень высокой практической доступностью за счёт надёжной инфраструктуры"

**Что даёт TrueTime:**
- **External consistency** (stronger than linearizability): если транзакция T1 завершилась до начала T2 в реальном времени, то T2 увидит все изменения T1 — даже если они на разных континентах
- **Globally consistent snapshots**: чтение с меткой времени даёт согласованный срез всей глобальной БД

| Характеристика | Обычная распределённая БД | Google Spanner |
|----------------|---------------------------|----------------|
| Синхронизация времени | NTP (~100ms погрешность) | Атомные часы + GPS (~7ms) |
| Гарантии | Linearizability per shard | External consistency global |
| Глобальные транзакции | 2PC с высокой latency | Paxos + TrueTime wait |
| Доступность | Зависит от partition | 99.999% (5 nines) |
| Применение | Большинство систем | Google Ads, F1, Cloud Spanner |

## Q42. (!) CAP vs BASE: детальное сравнение

**ACID** и **BASE** — два противоположных подхода к гарантиям транзакций. По сути это те же два полюса CAP, но описанные на языке транзакций: ACID — про строгую согласованность (мир CP), BASE — про доступность ценой временной несогласованности (мир AP).

**ACID** (Atomicity, Consistency, Isolation, Durability) — традиционная модель реляционных БД:
- транзакция выполняется либо полностью, либо никак;
- сильная согласованность: данные всегда в валидном состоянии;
- расплата — дороговизна в распределённой среде: нужны 2PC, блокировки и координация.

**BASE** (Basically Available, Soft state, Eventually consistent) — модель AP-систем:
- **Basically Available** — система всегда отвечает, пусть даже неполными данными;
- **Soft state** — состояние может меняться само по себе (репликация, компакция), без новых запросов;
- **Eventually consistent** — данные сходятся спустя некоторое время.

```
Детальное сравнение ACID vs BASE:

Свойство          ACID                    BASE
─────────────────────────────────────────────────────
Согласованность   Строгая (сразу)         Eventual (через время)
Доступность       Может блокировать       Всегда отвечает
Модель            Pessimistic locking      Optimistic / MVCC
Конфликты         Предотвращаются          Разрешаются post-hoc
Масштабирование   Вертикальное (трудно)    Горизонтальное (легко)
Сложность кода    Простая (БД решает)     Высокая (приложение решает)
Примеры           PostgreSQL, Oracle       Cassandra, DynamoDB, CouchDB
```

**Связь CAP и BASE:**
- CP-системы тяготеют к ACID (ZooKeeper, HBase, PostgreSQL с репликацией);
- AP-системы реализуют BASE (Cassandra, DynamoDB, CouchDB);
- ключевая мысль: BASE — не «плохой ACID», а осознанный размен строгой согласованности на горизонтальную масштабируемость и доступность.

**Когда BASE достаточно — реальные примеры:**

```
1. DNS — классический пример BASE:
   - Запись обновляется у root-сервера
   - Распространяется по миру за минуты-часы
   - Все DNS-серверы eventual consistent
   - Никого не блокирует — всегда доступна

2. Amazon Shopping Cart:
   - При partition cart продолжает работать (AP)
   - Конфликты (два добавления одного товара) разрешаются union-ом
   - Пользователь видит "лишний" товар и может убрать

3. Facebook Timeline:
   - Пост может появиться у разных пользователей в разное время
   - Eventual consistent — через секунды все видят одно
   - Никогда не блокирует публикацию
```

**Практический выбор:**

| Критерий | Выбирай ACID/CP | Выбирай BASE/AP |
|----------|-----------------|-----------------|
| Финансы | ✓ (обязательно) | — |
| Медицинские данные | ✓ | — |
| Inventory | ✓ | — |
| Социальная лента | — | ✓ |
| Аналитика | — | ✓ |
| Кэш / сессии | — | ✓ |
| Корзина | — | ✓ (с merge) |
