## Q1. (!) Что такое event-driven архитектура и чем она отличается от синхронного REST?

`Event-driven` архитектура (`EDA`) — стиль проектирования, при котором компоненты системы обмениваются данными через события, публикуемые в брокер сообщений (`Kafka`, `RabbitMQ`). Производитель (producer) публикует событие и не ждёт немедленной обработки; потребители (consumers) подписываются на топики/очереди и обрабатывают события асинхронно.

Отличия от синхронного `REST`:
- Связность: в `REST` клиент знает адреса сервисов и ждёт ответа; в `EDA` производитель не знает потребителей, связь через брокер.
- Масштабируемость: потребители можно масштабировать независимо; пики нагрузки сглаживаются очередью.
- Отказоустойчивость: при падении потребителя сообщения остаются в брокере; в `REST` нужны retry и circuit breaker.
- Консистентность: в `REST` проще достичь сильной консистентности в одной транзакции; в `EDA` типична eventual consistency и нужны паттерны (`Saga`, компенсирующие транзакции).

## Q2. Что такое событие (event) в контексте EDA? Какие атрибуты у события?

Событие — неизменяемая запись о факте, произошедшем в системе (например, «Заказ создан», «Платёж проведён»). Рекомендуемые атрибуты:
- Идентификатор события — уникальный id для дедупликации и трассировки.
- Тип события — имя/версия для маршрутизации и совместимости.
- Временная метка — когда произошло (часто в `UTC`).
- Агрегат — идентификатор сущности (`orderId`, `userId`).
- Полезная нагрузка (payload) — данные события в формате `JSON`, `Avro` или `Protobuf`.
- Метаданные — источник, correlation id, trace id для распределённой трассировки.

События проектируют неизменяемыми: новые версии — новые типы или поля с обратной совместимостью. Пример структуры события: `{"eventId":"uuid","type":"order.created","timestamp":"2026-01-28T10:00:00Z","aggregateId":"order-123","payload":{},"metadata":{"source":"order-service","correlationId":"corr-456","traceId":"trace-789"}}`. Важно: `eventId` для дедупликации; `type` для маршрутизации; `timestamp` для упорядочивания; `aggregateId` для группировки событий по сущности; `payload` содержит данные события; `metadata` для трассировки и корреляции.

## Q3. (!) Что такое брокер сообщений и чем отличаются Kafka и RabbitMQ для EDA?

Брокер сообщений — промежуточное хранилище, которое принимает сообщения от производителей и доставляет их потребителям. Гарантирует персистентность, доставку и (в зависимости от настроек) порядок.

`Kafka` — распределённый лог: сообщения хранятся в партициях с retention; потребители читают по offset; подходит для высокого throughput, реплея событий, стриминга. `RabbitMQ` — очереди с доставкой до потребителя и удалением; подходит для задач (task queue), `RPC`, когда не нужен длительный лог. Для `EDA` с большим объёмом событий и возможностью «переиграть» историю чаще выбирают `Kafka`; для рабочих очередей и гарантированной доставки до одного потребителя — `RabbitMQ`.

## Q4. Как обеспечить порядок обработки событий в распределённой системе?

Порядок в `Kafka` гарантируется только в пределах одной партиции. Поэтому:
- Используйте ключ партиционирования (например, `orderId`), чтобы все события по одному заказу попадали в одну партицию и обрабатывались одним потребителем по порядку.
- Не увеличивайте число партиций без необходимости — это может изменить распределение ключей.
- Для глобального порядка обычно не стремятся: достаточно порядка по агрегату (по ключу).

В `RabbitMQ` порядок в одной очереди сохраняется при одном потребителе; при нескольких — порядок между сообщениями от разных производителей не гарантирован. Для обеспечения порядка в `RabbitMQ`: использовать одну очередь с одним потребителем; использовать priority queues для приоритизации; использовать message groups для группировки сообщений по ключу; использовать single active consumer для гарантии последовательной обработки.

## Q5. (!) Что такое идемпотентность потребителя и зачем она нужна?

**Практический критерий:** если операция связана с деньгами или резервированием, идемпотентность подтверждают интеграционным тестом с повторной доставкой одного и того же `eventId`.

Идемпотентность — повторная обработка одного и того же сообщения даёт тот же результат, что и однократная. Нужна из-за возможной повторной доставки (retry продюсера, перезапуск потребителя до коммита offset). Способы:
- Хранить обработанные id сообщений в кэше/БД и перед обработкой проверять «уже обработано».
- Использовать бизнес-ключ (например, id платежа): если операция по нему уже выполнена — пропустить или вернуть успех.
- Применять upsert вместо «insert then update», чтобы повторное выполнение не создавало дубликатов. Пример идемпотентности: перед обработкой события проверять в БД или кэше, обработано ли событие с данным `eventId`; если обработано — пропустить или вернуть успех; если не обработано — выполнить операцию и пометить как обработанное. Для бизнес-операций использовать бизнес-ключи (например, id платежа): если операция по данному ключу уже выполнена — пропустить.


## Q6. (!) Что такое Event Sourcing?

`Event Sourcing` — хранение состояния системы как последовательности событий. Текущее состояние получают применением всех событий к «нулевому» состоянию (или к снапшоту + последующие события). Плюсы: полная история изменений, аудит, возможность пересчитать состояние за любой момент; минусы: сложность запросов и миграций схемы событий. Пример: вместо хранения текущего баланса счета хранятся события `AccountOpened`, `MoneyDeposited`, `MoneyWithdrawn`; текущий баланс вычисляется применением всех событий. Преимущества: полная история для аудита; возможность пересчитать состояние при исправлении багов; возможность создать новые проекции из исторических событий.


## Q7. Что такое CQRS и как он сочетается с EDA?

`CQRS` (`Command Query Responsibility Segregation`) — разделение модели на запись (command side) и чтение (`query` side). Запись обновляет хранилище и может публиковать события; чтение обслуживается из отдельного хранилища (часто оптимизированного под запросы), которое обновляется по событиям. С `EDA` события от command side обновляют read-модели (проекции), что даёт масштабирование чтения и записи независимо и возможность разных представлений одних и тех же данных. Пример: команда `CreateOrder` записывает событие `OrderCreated`; проекция обновляет read-модель `OrderView` для быстрых запросов; можно создать несколько проекций для разных представлений (список заказов, статистика, аналитика). Преимущества: независимое масштабирование чтения и записи; оптимизация read-моделей под запросы; возможность разных представлений одних и тех же данных.


## Q8. (!) Что такое Saga и когда её используют?

`Saga` — паттерн для распределённых транзакций: длинная бизнес-операция разбита на шаги в разных сервисах; каждый шаг публикует событие для следующего; при сбое выполняются компенсирующие действия (откат). Бывают оркестрируемые (центральный оркестратор) и хореографические (каждый сервис реагирует на события и решает, что делать дальше). Используют при необходимости согласованности между сервисами без двухфазного коммита (2PC). Пример хореографической `Saga`: `Order Service` публикует `OrderCreated` → `Inventory Service` резервирует товар и публикует `InventoryReserved` → `Payment Service` обрабатывает платёж и публикует `PaymentProcessed` → `Shipping Service` отправляет заказ. При сбое платёжа `Payment Service` публикует `PaymentFailed` → `Inventory Service` откатывает резерв → `Order Service` отменяет заказ. Преимущества: слабая связность сервисов; нет центральной точки отказа; компенсирующие транзакции для отката.

На практике ключевой момент — идемпотентность шагов, корректные компенсирующие действия и наблюдаемость всего потока через `traceId`/метрики. В интервью стоит явно показать, как система ведёт себя при ретраях, сетевых сбоях и дублирующей доставке сообщений.

## Q9. (!) Что такое Outbox pattern?

`Outbox` pattern — запись исходящих событий в таблицу в той же БД, что и бизнес-данные, в одной транзакции; отдельный процесс (polling или `CDC`) читает из этой таблицы и публикует в брокер, затем помечает запись как отправленную. Гарантирует, что событие будет опубликовано при успешной записи бизнес-данных, и избегает потери событий при сбое после commit в БД, но до отправки в брокер. Пример: создание заказа и запись события в таблицу `outbox_events` в одной транзакции; отдельный процесс (scheduler или `CDC` через `Debezium`) читает неопубликованные события и публикует в `Kafka`; после публикации событие помечается как отправленное или удаляется. Реализация: polling (периодический опрос таблицы outbox) или `CDC` (`Change Data Capture` через транзакционный лог БД). Преимущества: гарантия публикации события при успешной записи; избежание потери событий; атомарность записи бизнес-данных и события.


## Q10. (!) Что такое dead letter queue (DLQ) и когда его использовать?

`Dead Letter Queue` (`DLQ`) — очередь для сообщений после N неудачных попыток; чтобы не блокировать основную очередь и позже разобрать проблему (логирование, ручная обработка, исправление и повторная публикация). В `Kafka` часто реализуют отдельным топиком; в `RabbitMQ` — отдельной очередью с `x-dead-letter-exchange`. Пример: после 3 попыток обработки события с ошибкой валидации сообщение отправляется в `DLQ`; оператор анализирует `DLQ`, исправляет данные и повторно публикует событие. Мониторинг: размер `DLQ` — метрика проблемных сообщений; рост `DLQ` указывает на проблемы с обработкой; алерты при превышении порога размера `DLQ`.


## Q11. Что такое Schema Registry и зачем он в EDA?

`Schema Registry` — хранилище схем (например, `Avro`, `JSON Schema`). Пример: Confluent `Schema Registry` для `Kafka`; продюсер регистрирует схему `Avro` для события `OrderCreated`; потребитель получает схему при чтении события и валидирует данные. Преимущества: централизованное управление схемами; проверка совместимости (backward/forward compatible); версионирование схем; контракты между сервисами; предотвращение breaking changes.


## Q12. (!) Как в EDA добиться exactly-once семантики?

**Trade-off:** строгая exactly-once семантика повышает сложность и latency; в большинстве production-сценариев применяют at-least-once + идемпотентный consumer и дедупликацию.

`Exactly-once` — каждое событие обрабатывается ровно один раз. Подходы:
- `Kafka`: транзакции продюсера + идемпотентный продюсер + потребитель с транзакционным коммитом offset (`Kafka Streams`, `Spring Kafka` с правильными настройками). Настройки: `enable.idempotence=true`, `acks=all`, `transactional.id` для продюсера; `isolation.level=read_committed` для потребителя.
- Идемпотентность потребителя: даже при повторной доставке результат не дублируется (дедупликация по id, бизнес-проверки). Проверка «уже обработано» перед обработкой; использование бизнес-ключей для идемпотентности операций.
- Комбинация: транзакционная запись в БД и публикация в `Kafka` через `Outbox` или `Kafka transaction API` с общим транзакционным координатором. `Outbox pattern` гарантирует атомарность записи и публикации; `Kafka transactions` обеспечивают атомарность публикации и коммита offset.


## Q13. Что такое consumer lag и как с ним работать?

`Consumer` lag — отставание потребителя от продюсера (например, 10000 сообщений); при росте lag выше определённой скорости; при lag, приближающемся к retention limit.


## Q14. Чем event-driven отличается от message-driven?

`Event-driven` — фокус на событиях как фактах («что произошло»); потребители подписываются на типы событий; типична eventual consistency. `Message-driven` — фокус на сообщениях-запросах. `Kafka` чаще ассоциируют с `event-driven` (лог событий); `RabbitMQ` — с `message-driven` (очереди задач, `RPC`). Граница размыта: события тоже передаются сообщениями. Примеры событий: `OrderCreated`, `PaymentProcessed`, `InventoryReserved` — факты, которые уже произошли. Примеры сообщений: `CreateOrder`, `ProcessPayment`, `ReserveInventory` — команды для выполнения действий. Преимущества событий: слабая связность; возможность добавления новых потребителей; возможность replay событий; полная история изменений.


## Q15. Как обеспечить обратную совместимость при изменении схемы события?

Рекомендации: добавлять новые поля с значениями по умолчанию (backward compatible); не удалять поля, а помечать deprecated и перестать использовать позже; использовать `Schema Registry` и версионирование типа события (например, `order.created.v2`); потребители должны игнорировать неизвестные поля и обрабатывать отсутствующие опциональные поля. Пример backward compatible: добавление нового опционального поля `discount` в событие `OrderCreated`; старые потребители игнорируют новое поле; новые потребители могут использовать его. Пример forward compatible: новое поле имеет значение по умолчанию; новые потребители работают со старыми событиями, используя значение по умолчанию. `Breaking changes`: удаление поля, изменение типа поля — требуют версионирования типа события или топика.


## Q16. Что такое partition key в Kafka и как он влияет на порядок?

`Partition` key — ключ, по которому `Kafka` определяет партицию для сообщения: `partition = hash(key) % numPartitions`. Все сообщения с одним ключом попадают в одну партицию и обрабатываются одним потребителем в группе в порядке публикации. Для упорядоченности по агрегату (например, по заказу) используют стабильный ключ (`orderId`). `Null`-ключ приводит к `round-robin` по партициям — порядок не гарантируется. Пример: события с ключом `order-123` всегда попадают в одну партицию; потребитель обрабатывает их последовательно в порядке публикации. Выбор ключа: использовать идентификатор агрегата (`orderId`, `userId`) для упорядоченности по агрегату; использовать `null` для `round-robin` распределения (порядок не гарантируется). Влияние на порядок: порядок гарантируется только в пределах партиции; для глобального порядка нужна одна партиция (не масштабируется). Важно: не менять число партиций без необходимости — это может изменить распределение ключей.


## Q17. Когда использовать топик с одной партицией, а когда с несколькими?

Одна партиция — когда нужен глобальный порядок всех сообщений и один потребитель в группе достаточен. Несколько партиций — когда нужна параллельная обработка и throughput; порядок сохраняется только внутри партиции. Число партиций ограничивает максимальное число потребителей в группе (каждый потребитель читает подмножество партиций). Увеличивать число партиций после создания топика сложно (данные не перераспределяются автоматически), поэтому планируют заранее. Пример одной партиции: топик с глобальным порядком всех событий (не масштабируется, но гарантирует порядок). Пример нескольких партиций: топик с событиями по заказам; порядок гарантируется только по заказу (по ключу `orderId`); параллельная обработка разных заказов. Рекомендация: использовать несколько партиций для масштабирования; порядок по агрегату через ключ партиционирования; глобальный порядок обычно не нужен.


## Q18. Что такое consumer group и как распределяются партиции?

`Consumer` group — набор потребителей, совместно обрабатывающих топик. Каждая партиция топика назначается ровно одному потребителю в группе. При добавлении потребителей происходит rebalance: партиции перераспределяются. При количестве потребителей больше числа партиций часть потребителей простаивает. Идентификатор группы задаётся в конфигурации потребителя; offset хранится по группе. Пример: топик с 3 партициями и consumer group с 2 потребителями; каждый потребитель обрабатывает 1-2 партиции; при добавлении третьего потребителя происходит rebalance и каждый получает по 1 партиции. `Rebalance` перераспределяет партиции. Offset хранится по consumer group; при перезапуске потребитель продолжает с последнего коммита offset; при создании новой группы чтение начинается с начала топика (или с latest/earliest).


## Q19. Как в EDA обеспечить мониторинг и наблюдаемость?

Рекомендации: метрики по lag потребителей, throughput продюсера и потребителя, задержки; распределённая трассировка (trace id в заголовках сообщений, передача в `MDC` при обработке); логирование ключевых событий (публикация, обработка, ошибки) без чувствительных данных; алерты при росте lag, падении потребителей, несовместимости схем; дашборды по топикам и группам. Инструменты: `Prometheus` + `Grafana` для метрик; `Jaeger / Zipkin` для распределённой трассировки; `Kafka Manager / Confluent Control Center` для управления `Kafka`; `Schema Registry` для управления схемами. Метрики: consumer lag (отставание потребителя), throughput (число сообщений в секунду), latency (задержка обработки), error rate (частота ошибок), `DLQ` size (размер dead letter queue). Алерты: при превышении порога lag; при падении throughput; при росте error rate; при несовместимости схем; при недоступности брокера.


## Q20. Какие антипаттерны в event-driven архитектуре стоит избегать?

**Антипаттерн:** использовать события как синхронный RPC-заменитель и ждать «мгновенный» ответ от потребителя — это ломает слабую связность и ухудшает отказоустойчивость.

- Большие сообщения — не передавать в событии большие бинарные данные; хранить в объектном хранилище и передавать ссылку.
- Синхронные вызовы внутри потребителя — не блокировать обработку длинными `REST`-запросами; использовать асинхронность или выносить в отдельные воркеры.
- Отсутствие идемпотентности — повторная доставка приводит к дублированию операций.
- Игнорирование схемы — менять формат без версионирования и совместимости ломает потребителей.
- Один гигантский топик на всё — разделять по доменам и по критичности; упрощает retention и мониторинг.


## Q21. Что такое event replay и когда его использовать?

`Event` replay — повторная обработка событий из истории (из топика `Kafka` или event store) для восстановления состояния или пересчёта проекций. Используют при: восстановлении read-модели после сбоя; исправлении багов в обработчиках и пересчёте данных; создании новых проекций из исторических событий; тестировании обработчиков на реальных данных. В `Kafka`: чтение с начала топика или с определённого offset; в event store: применение событий к снапшоту или к «нулевому» состоянию.


## Q22. Как обеспечить транзакционность в event-driven системе?

Транзакционность в `event-driven` системе сложнее, чем в монолите. Подходы: `Outbox` pattern — запись бизнес-данных и события в одну транзакцию БД; отдельный процесс публикует события; `Saga` — компенсирующие транзакции при сбоях; `Transactional` outbox — использование транзакционного лога БД (`CDC`) для публикации событий; `Exactly-once` семантика в `Kafka` (транзакции продюсера, идемпотентность, `read-process-write` с транзакциями). Важно: eventual consistency — норма для `EDA`; сильная консистентность достигается через синхронные вызовы или `Saga`.

На практике ключевой момент — идемпотентность шагов, корректные компенсирующие действия и наблюдаемость всего потока через `traceId`/метрики. В интервью стоит явно показать, как система ведёт себя при ретраях, сетевых сбоях и дублирующей доставке сообщений.

## Q23. Что такое event versioning и как управлять изменениями схемы?

`Event` versioning — управление изменениями схемы событий с сохранением обратной совместимости. Стратегии: backward compatible — новые поля опциональны, старые поля не удаляются; старые потребители работают с новыми событиями; forward compatible — новые потребители работают со старыми событиями (опциональные поля, значения по умолчанию); Версионирование типа события — `order.created.v1`, `order.created.v2`; `Schema Registry` — централизованное управление схемами (`Avro`, `JSON Schema`) с проверкой совместимости. Рекомендация: использовать `Schema Registry` и backward/forward compatible изменения; breaking changes — через версионирование типа или топика.


## Q24. Как обработать события в правильном порядке при параллельной обработке?

Порядок в `Kafka` гарантируется только в пределах партиции. Для параллельной обработки с сохранением порядка: использовать ключ партиционирования (например, `orderId`) — все события по одному заказу попадают в одну партицию; один поток потребителя обрабатывает одну партицию последовательно; для глобального порядка — одна партиция (не масштабируется); для порядка по агрегату — ключ партиционирования. В `Spring Kafka`: `ConcurrentKafkaListenerContainerFactory` с одним потоком на партицию; обработка внутри партиции последовательная.


## Q25. Что такое event store и чем он отличается от обычной БД?

`Event` store — специализированное хранилище для событий в `Event Sourcing`: хранит события как последовательность (`append-only`); события неизменяемы (immutable); поддерживает чтение событий по агрегату и временному диапазону; оптимизирован для записи и чтения последовательностей. Отличия от обычной БД: обычная БД хранит текущее состояние (`CRUD`); event store хранит историю изменений (события); текущее состояние вычисляется применением событий; event store поддерживает версионирование и replay. Примеры: `EventStore`, `Axon Framework Event Store`, `Kafka` как event store (с retention).


## Q26. Как обеспечить мониторинг и алертинг в event-driven системе?

Метрики для мониторинга: `Consumer` lag — отставание потребителя от продюсера (`Kafka` lag); `Throughput` и `Latency` — задержка обработки (`publish-to-consume`, processing time); `Error` rate — частота ошибок обработки; `DLQ` size — размер dead letter queue. Алерты: высокий lag (потребитель не успевает); падение throughput; рост error rate; несовместимость схем (`Schema Registry`); недоступность брокера. Инструменты: `Prometheus` + `Grafana` для метрик; распределённая трассировка (`Jaeger`, `Zipkin`) для trace id в событиях.


## Q27. Что такое event choreography vs orchestration?

`Choreography` (хореография) — децентрализованная координация: каждый сервис реагирует на события и решает, что делать дальше; нет центрального координатора; сервисы слабо связаны; сложнее отладка и мониторинг потока. `Orchestration` (оркестрация) — централизованная координация: центральный оркестратор вызывает сервисы и координирует поток; проще отладка и мониторинг; центральная точка отказа; более жёсткая связность. В `Saga`: хореографическая — каждый сервис публикует события; оркестрируемая — оркестратор вызывает сервисы и управляет компенсацией.


## Q28. Как обработать события с разной скоростью обработки?

Проблема: быстрые события блокируют медленные в одной партиции. Решения: Разделение по скорости — отдельные топики/партиции для быстрых и медленных событий; Приоритетные очереди — `RabbitMQ` priority queues; Отдельные consumer groups — разные группы для разных типов событий; `Backpressure` — замедление продюсера при переполнении очереди; `Rate` limiting — ограничение скорости обработки медленных событий. В `Kafka`: разделение по топикам; настройка `max.poll.records` для контроля батча; использование разных consumer groups.


## Q29. Что такое event sourcing snapshot и зачем он нужен?

`Snapshot` — сохранённое состояние агрегата на определённый момент времени (версия события). Зачем: ускорение восстановления состояния — применение событий к снапшоту быстрее, чем к «нулевому» состоянию; уменьшение нагрузки на event store при частых запросах текущего состояния. Стратегии: периодические снапшоты (каждые N событий или по времени); снапшоты по требованию (при достижении определённого размера); хранение снапшотов отдельно от событий (БД, кэш). При восстановлении: загрузить последний снапшот; применить события после версии снапшота.


## Q30. Как обеспечить безопасность событий в event-driven системе?

Меры безопасности: шифрование в покое и в транзите (`TLS`); аутентификация и авторизация (`SASL`/`SSL` для `Kafka`, `RBAC`); не хранить пароли и `PII` в событиях; проверка схемы через `Schema Registry`; изоляция топиков по окружениям; брокер в приватной сети.
