# Вопросы на собеседовании: `Edge Computing`

`Edge Computing` — выполнение логики **близко к пользователям** (edge-локации CDN, IoT-шлюзы). Cloudflare Workers, AWS Lambda@Edge, Fastly Compute@Edge: latency 10-50 мс (против 100-300 мс у origin), глобальный масштаб, serverless. Роль растёт: API gateway, персонализация, A/B-тестирование, оптимизация изображений, авторизация на edge.

## Q1. (!) Что такое Edge Computing?

**Edge Computing** — выполнение прикладной логики **на краю сети**, физически близко к пользователю, а не в одном центральном дата-центре или облачном регионе. Идея простая: чем короче путь от пользователя до кода, тем меньше задержка.

**Почему это работает.** В классической схеме запрос летит до одного origin (например, `us-east-1`), и пользователю на другом конце планеты это стоит ~150 мс на каждый roundtrip. Edge переносит код в сотни точек по миру, поэтому ближайшая к пользователю отвечает за 10-50 мс.

| | Origin (традиционно) | Edge |
|---|---|---|
| Размещение | 1-2 региона | 100-300+ точек присутствия (POP) |
| RTT до пользователя | ~150 мс по миру | 10-50 мс из любой точки |

**Три типа edge** (различай на собеседовании):
1. **Edge-функции CDN** — Cloudflare Workers, Lambda@Edge. Код выполняется в POP сети доставки контента.
2. **IoT edge** — обработка прямо на устройстве или шлюзе (AWS Greengrass).
3. **Telco edge / MEC** — вычисления на базовой станции оператора 5G.

**Фокус здесь** — edge-функции CDN: именно они чаще всего всплывают на backend-собеседованиях.

**Схема:**
```
User → CDN Edge (runs edge function) → optionally → Origin
         ↓ 10ms                             ↓ 150ms
```

**Ключевая мысль:** edge-функция может ответить сама, вообще не дёргая origin. Тогда дорогой roundtrip до центрального дата-центра исключается — отсюда и весь выигрыш.

## Q2. (!) Чем edge отличается от CDN и обычного serverless?

Коротко: это четыре ступени одной лестницы — от «просто раздаём файлы» до «запускаем код близко к пользователю». Главные оси различия — **где выполняется** (edge или центральный регион) и **что выполняется** (ничего / полный runtime / ограниченный JS).

**CDN** — кэширование статики на edge.
- Хранит готовые объекты: изображения, CSS, JS.
- Своего кода не выполняет — только отдаёт то, что закэшировано.

**Edge compute** — это CDN, который умеет ещё и исполнять код в POP.
- Меняет request/response на лету.
- Динамическая персонализация.
- Авторизация и решения о маршрутизации до origin.

**Serverless (Lambda, Cloud Functions)** — код запускается по требованию, но в централизованных регионах.
- Привязан к региону (`us-east-1` и т.п.) → пользователю издалека всё равно далеко.
- Полноценный runtime в контейнере → можно почти всё.
- Платит за это более долгим cold start и слабой географической распределённостью.

**Edge serverless (Workers, Lambda@Edge)** — тот же serverless, но размазанный по edge.
- V8-изоляты (Workers) стартуют за микросекунды — cold start практически отсутствует.
- Вокруг — целая платформа: KV-хранилище, cron-триггеры, Durable Objects.

**Сравнение:**

| Аспект | CDN | Lambda | Edge Worker |
|--------|-----|--------|-------------|
| Расположение | Edge | Регион | Edge |
| Логика | Нет | Полная | Ограниченная |
| Старт | — | сотни мс | ~0 мс |
| Runtime | — | Полная ОС | Только JS/Wasm |
| Состояние | Статика | Внешнее | KV / DO |

## Q3. (!) Какие у edge преимущества и когда его применять?

Главный выигрыш — **близость к пользователю**, из которой вытекает почти всё остальное: меньше задержка, разгрузка origin, защита от атак на дальних подступах.

**Преимущества:**

1. **Низкая latency.** 10-50 мс вместо 100-300. Напрямую влияет на воспринимаемую скорость сайта (целевой LCP < 2.5 с).
2. **Разгрузка origin.** Edge берёт логику на себя → до центрального сервера доходит меньше трафика → он дешевле и стабильнее.
3. **Мгновенный глобальный масштаб.** Деплоишь один раз — код едет в 300 POP. Не нужно вручную раскатывать мультирегиональную инфраструктуру.
4. **Стоимость (часто ниже).** Платишь за вызовы, за простой — нет. Ориентир: Cloudflare Workers — $5 за 10M запросов.
5. **Поглощение DDoS.** Сеть Cloudflare абсорбирует атаки на 71 Tbps, и твоя edge-функция запускается уже после митигации — грязный трафик до неё не доходит.

**Когда применять** (сценарии, где близость и разгрузка origin реально окупаются):
- Персонализация статичного сайта — подмешать данные под конкретного пользователя.
- Авторизация на edge — отсечь неавторизованных ещё до origin.
- A/B-тестирование и feature-флаги.
- Преобразование изображений/видео.
- Проксирование и агрегация API (BFF на edge).
- Приём данных IoT.

**Когда НЕ стоит** (там, где упираешься в лимиты edge-runtime):
- Тяжёлые вычисления (ML-инференс под нагрузкой) — не хватит CPU.
- Долгие операции (> 30 с) — просто не поддерживаются.
- Stateful-приложения с жёсткой консистентностью — на распределённом edge это сложно.

## Q4. (!) Как устроены Cloudflare Workers?

В основе — **V8-изолят**: лёгкая JavaScript-песочница, тот же механизм, что изолирует вкладки в Chrome. Это и есть причина, почему Workers стартуют за микросекунды: не нужно поднимать контейнер или ОС, достаточно создать новый изолят внутри уже работающего процесса V8.

**Как это работает:**
- Код воркера (JS/TS/Wasm) деплоится сразу на все 300+ POP Cloudflare.
- Первый запрос к конкретному POP → воркер загружается (~1 мс).
- Дальше изолят переиспользуется → последующие запросы обслуживаются за микросекунды.

**Пример:**
```js
export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    if (url.pathname === '/api/hello') {
      return new Response(JSON.stringify({ msg: 'Hello from ' + request.cf.city }));
    }
    return fetch(request);  // passthrough к origin
  }
}
```

**Что доступно из коробки** (не «голый» JS, а целая платформа):
- Fetch API — веб-стандарт для исходящих запросов.
- KV store — key-value с eventual consistency.
- Durable Objects — stateful-хранилище со строгой консистентностью.
- Cron-триггеры.
- D1 — SQLite прямо на edge.
- R2 — S3-совместимое хранилище с нулевым egress.
- Queues, AI.

**Лимиты runtime** (за их пределами edge не лучший выбор):
- CPU-время: 10 мс на бесплатном тарифе / до 30 с на платном.
- Память: 128MB.
- Размер запроса: 100MB.

**Языки:** JS, TS, WASM (Rust, C, Go компилируются в wasm).

## Q5. (!) Чем Lambda@Edge отличается от CloudFront Functions?

У AWS два edge-инструмента, и их легко перепутать. Простое правило: **CloudFront Functions — для лёгких операций над заголовками/URL, Lambda@Edge — для всего, что требует настоящей логики.** Functions быстрее и дешевле, Lambda@Edge мощнее и дороже.

**CloudFront Functions** — лёгкий и сверхбыстрый инструмент:
- Появились позже (2021).
- Только JavaScript.
- Выполнение < 1 мс, запуск мгновенный (cold start нет).
- Срабатывают только на viewer request/response.
- Подходят для простого: манипуляции с заголовками, редиректы.
- Дёшево — $0.10 за миллион.

**Lambda@Edge** — старше, тяжелее, но способен на большее:
- Node.js, Python.
- Выполнение до 5 с (viewer) / 30 с (origin).
- Полноценная Lambda — может звать внешние сервисы и работать дольше.
- Срабатывает в **4 точках** жизненного цикла запроса:
  - Viewer request — до кэша.
  - Origin request — после промаха кэша.
  - Origin response — до записи в кэш.
  - Viewer response — после кэша.
- Дороже — $0.6 за миллион.
- Cold start: 50-200 мс на холодную (у Functions его нет вовсе).

**Что куда:**
- CloudFront Functions: переписывание URL, заголовки, простая авторизация.
- Lambda@Edge: персонализация, сложная маршрутизация, ресайз изображений.

**Распространение деплоя:** Lambda@Edge раскатывается по миру за 2-5 мин, CloudFront Functions — быстрее.

## Q6. Чем V8-изоляты отличаются от контейнеров?

Это про **цену изоляции**. Изолят разделяет тенантов внутри одного процесса (дёшево, но граница тоньше), контейнер — на уровне VM (дорого, но граница жёсткая). Отсюда вытекают скорость старта, плотность и модель безопасности.

**V8-изолят (Workers):**
- Лёгкая песочница внутри движка V8.
- Изоляция по памяти, а не по процессам — несколько изолятов живут в одном V8-процессе.
- Старт за микросекунды.
- Только короткий JS/WASM-код.

**Контейнер (Lambda):**
- Полноценная ОС/runtime.
- Изоляция процессов и разделение на уровне VM (Firecracker).
- Старт от 100 мс до нескольких секунд.
- Любой язык или бинарь.

**Компромиссы:**

| Аспект | Изолят | Контейнер |
|--------|---------|-----------|
| Старт | мкс | 100 мс+ |
| Плотность | тысячи на машину | десятки |
| Безопасность | Общий процесс (V8) | Уровень VM |
| Языки | JS, WASM | Любые |
| Runtime | Ограниченный | Полный |

**Про безопасность.** Изоляты держатся на корректности V8: уязвимость в движке теоретически даёт утечку между тенантами. Случается редко, но эту цену за плотность стоит держать в голове.

**Куда движется индустрия:** гибрид — Workers на горячих путях, где важна скорость, Lambda — для тяжёлой и сложной логики.

## Q7. (!) Какие типичные сценарии для edge?

Объединяет их одно: **выгоднее обработать запрос на edge, чем гнать его до origin** — либо ради скорости, либо чтобы отсечь лишний трафик пораньше.

1. **Авторизация / валидация JWT.** Отклонять неавторизованные запросы прямо на edge — origin не тратит вычисления на ответы 401.
2. **Переписывание URL / маршрутизация.** A/B-тест (50% пользователей → backend v2) или гео-маршрутизация (пользователи из EU → EU-origin).
3. **Персонализация.** Закэшированная базовая страница + динамическая вставка пользовательских сниппетов в HTML на edge.
4. **Оптимизация изображений.** Ресайз на лету под устройство/экран и конвертация в WebP/AVIF (Cloudflare Image Resizing, AWS Lambda@Edge).
5. **Детектирование ботов / WAF.** Анализ паттернов запросов и блокировка ботов, не доходя до origin.
6. **API gateway / BFF на edge.** Агрегация нескольких бэкендов и преобразование ответов под клиента (см. [паттерн BFF](bff-pattern-interview.md)).
7. **Гео-блокировка / комплаенс.** Блокировка конкретных стран; показ GDPR-баннеров согласия только в EU.
8. **Кэширование с кастомной логикой.** Свой ключ кэша, stale-while-revalidate, edge-purge по требованию.
9. **Real-time-функции.** Терминация WebSocket на edge, pub/sub (Cloudflare Realtime).
10. **AI-инференс.** Лёгкие модели прямо на edge (Cloudflare AI, Vercel AI) для генерации с низкой задержкой.

## Q8. Как проверять JWT и авторизацию на edge?

Идея: **edge выступает «вышибалой» перед origin** — проверяет токен и пропускает дальше только уже аутентифицированные запросы. Невалидный трафик отсекается на ближайшем POP и до бэкенда не доходит.

**Поток:**
```
Request → Edge Worker
  ├─ No token → 401
  ├─ Invalid token → 401
  ├─ Valid → forward to origin with verified claims
```

**Код (Cloudflare Workers):**
```js
export default {
  async fetch(request, env) {
    const token = request.headers.get('Authorization')?.replace('Bearer ', '');
    if (!token) return new Response('Unauthorized', { status: 401 });
    
    try {
      const payload = await verifyJWT(token, env.JWT_SECRET);
      const headers = new Headers(request.headers);
      headers.set('X-User-ID', payload.sub);
      return fetch(new Request(request.url, { method: request.method, headers, body: request.body }));
    } catch (e) {
      return new Response('Invalid token', { status: 401 });
    }
  }
};
```

**Плюсы:**
- Origin всегда получает уже аутентифицированные запросы.
- Атакующий трафик не доходит до origin.
- Backend упрощается — доверяет заголовку от edge вместо собственной проверки токена.

**Подводные камни:**
- **Секреты.** Ключ для проверки JWT надо безопасно раздать на сотни POP — для этого Cloudflare Secrets.
- **Отзыв токенов.** Сложен: решение кэшируется на каждом edge, поэтому отзыв не моментальный → спасают короткие TTL.
- **Ротация ключей.** Её приходится координировать по всей сети, а не на одном сервере.

## Q9. Как делать оптимизацию и ресайз изображений на edge?

**Задача:** отдавать каждому клиенту изображение нужного размера и формата под его устройство и соединение, а не один тяжёлый файл на всех.

**Без edge** клиент скачивает крупный оригинал и сам ужимает его в браузере — лишний трафик и потерянное время. **На edge** картинку преобразуют один раз ближе к пользователю и кэшируют результат.

**С edge:**
```
Request /image.jpg?w=500&format=webp
  ↓
Edge worker:
  - Fetch original from origin
  - Resize to 500px width
  - Convert to WebP
  - Cache result at edge
  - Return
```

**Инструменты:**
- Cloudflare Image Resizing (managed)
- AWS Lambda@Edge + Sharp
- Fastly Image Optimizer
- Vercel Image Optimization

**Плюсы:**
- Экономия трафика (на 10-50% меньше).
- Быстрее загрузка страниц.
- Изображение под устройство (retina против 1x).

**Кэширование:**
- Свой кэш на каждый вариант (параметры размера/формата в URL).
- За hit ratio отвечает CDN-кэш.

**Согласование формата** — edge сам выбирает формат по заголовку `Accept` клиента:
- `Accept: image/webp` → отдаёт WebP.
- `Accept: image/avif` → AVIF (ещё меньше).
- Старые браузеры → откат на JPEG.

## Q10. Как делать A/B-тесты и персонализацию на edge?

**Конфликт, который решает edge:** A/B-тесты требуют разного контента для разных людей, а кэширование держит на всех одну версию. Edge примиряет одно с другим — кэширует общий каркас, но подменяет вариативную часть на лету.

**Подход на edge:**
1. Кэшировать на edge базовый HTML.
2. Edge-функция выбирает вариант для пользователя (по cookie или случайно при первом визите).
3. Подставляет в ответ контент именно этого варианта.
4. Возвращает изменённый HTML.

**Код:**
```js
export default {
  async fetch(request, env) {
    let variant = getCookie(request, 'ab_variant');
    if (!variant) {
      variant = Math.random() < 0.5 ? 'A' : 'B';
    }
    
    const origResp = await fetch(request);
    const html = await origResp.text();
    const modified = html.replace('__CTA__', variant === 'A' ? 'Buy Now' : 'Get Started');
    
    const resp = new Response(modified, origResp);
    resp.headers.append('Set-Cookie', `ab_variant=${variant}; Max-Age=86400`);
    return resp;
  }
};
```

**HTMLRewriter** (Cloudflare): потоковый API в стиле DOM. Производительнее, чем `replace` по строке, потому что разбирает HTML на лету, не загружая его целиком в память.

**Feature-флаги:** edge опрашивает сервис флагов (с кэшированием) и включает фичи по пользователю или региону.

**Персонализация без мерцания.** Контент готов уже в момент доставки, поэтому не нужен клиентский fetch после загрузки — и нет FOUC (flash of unstyled content), когда страница на миг показывается «неправильной».

## Q11. (!) Как работать с состоянием на edge?

**Корень проблемы:** edge-узлы по умолчанию stateless, а POP их 300+. Состояние, записанное в одном POP, по умолчанию не видно остальным — поэтому выбор сводится к компромиссу между скоростью, консистентностью и тем, насколько глобально нужны данные.

**Варианты — от простого к сложному:**

1. **Без состояния.** Всё гонится через origin. Проще некуда, но теряется весь смысл edge для динамики.
2. **Кэш (эфемерный).** Edge-кэш уровня CDN, по TTL. У каждого POP свой кэш → данные дублируются, зато читаются мгновенно.
3. **KV store (eventually consistent).** Cloudflare Workers KV, DynamoDB Global Tables. Запись со временем реплицируется на все POP. Чтение ~1 мс, но запись медленная и с лимитом на ключ — это хранилище заточено под чтение.
4. **Durable Objects (strongly consistent).** Один инстанс на объект на всю сеть, привязанный к конкретному POP. Все записи идут в одну точку → строгая консистентность. Для координации: чат-комната, счётчик.
5. **Внешняя БД.** Вызов Postgres или DynamoDB прямо из воркера. Даёт полноценную БД, но добавляет round-trip edge → БД и съедает выигрыш по latency.

**Как выбрать под сценарий:**
- Токены сессий: **KV** — много чтения, eventual consistency допустима.
- Состояние чат-комнаты: **Durable Objects** — нужна строгая консистентность.
- Глобальный счётчик: **Durable Objects** или атомарный Redis.

## Q12. Что такое Cloudflare Durable Objects?

**Durable Object** — stateful-сервис, который существует ровно в одном инстансе на всю сеть и привязан к одному POP. Это и есть способ получить на edge строгую консистентность: раз инстанс один, все записи проходят через одну точку, и гонок между POP быть не может.

**Модель:**
- Объект адресуется по имени: `getDurableObject("chat-room-123")`.
- Глобально живёт один инстанс — все записи идут именно в него.
- Состояние сохраняется в транзакционном key-value storage.
- Есть поддержка WebSocket.

**Сценарии** (везде нужно общее состояние без гонок):
- Чат-комнаты — общее состояние участников.
- Real-time-совместная работа (как Google Docs).
- Атомарные счётчики.
- Координация — например, выбор лидера.

**Код:**
```js
export class ChatRoom {
  constructor(state, env) {
    this.state = state;
    this.sessions = [];
  }
  
  async fetch(request) {
    // WebSocket upgrade
    const [client, server] = Object.values(new WebSocketPair());
    this.sessions.push(server);
    server.accept();
    server.addEventListener('message', (e) => {
      for (const s of this.sessions) s.send(e.data);
    });
    return new Response(null, { status: 101, webSocket: client });
  }
}
```

**Компромисс:** ровно за строгую консистентность платишь latency — DO живёт в одном POP, поэтому пользователям из других регионов до него дальше.

**Стоимость:** $0.20 за миллион запросов.

## Q13. Какие KV-хранилища есть на edge (Workers KV, DynamoDB Global)?

Общая черта всех edge-KV: они **жертвуют моментальной консистентностью ради быстрого глобального чтения**. Запись распространяется по миру не мгновенно — поэтому они хороши там, где данные читают часто, а пишут редко.

**Workers KV:**
- Eventually consistent key-value.
- Чтение ~1 мс (кэшируется на edge).
- Запись распространяется по миру до ~1 минуты.
- Заточен под чтение и терпит устаревшие данные.
- Лимит 100 записей/сек на ключ.

**Сценарии** (всё, что часто читается и редко меняется):
- Feature-флаги.
- Конфигурация.
- Статический контент.
- Маппинги маршрутов.

**DynamoDB Global Tables:**
- Мультирегиональная репликация, eventual consistency между регионами.
- API тяжелее и медленнее, чем у KV.
- Применяется из Lambda@Edge.

**FaunaDB, PlanetScale** — глобальные SQL-базы: строгая консистентность внутри региона, eventual между регионами.

**Как выбирать** — три вопроса:
- Нужна ли строгая консистентность?
- Насколько часто пишем?
- Хватит ли KV или нужен полноценный SQL?

## Q14. (!) Какие ограничения у edge-runtime?

Edge меняет цену изоляции на урезанный runtime: ради микросекундного старта и огромной плотности приходится отказаться от полноценной ОС. Отсюда все лимиты ниже — короткий CPU-бюджет, мало памяти, нет диска и нет произвольных системных вызовов.

**Cloudflare Workers:**
- CPU: 10-30 с (зависит от тарифа).
- Память: 128MB.
- Нет файловой системы (только ассеты, вшитые в бандл).
- Нет нативных Node-API — workerd реализует лишь подмножество.
- Часть npm-пакетов не работает.

**Lambda@Edge:**
- CPU: 5-30 с.
- Память: 128MB-10GB.
- Viewer request/response: лимит 5 с и тело до 1MB.

**Что есть и чего нет в runtime Workers:**
- Fetch API ✅
- Web Streams ✅
- Crypto (SubtleCrypto) ✅
- TextEncoder/Decoder ✅
- Нет `fs`, нет прямого TCP — только fetch.
- Нет дочерних процессов.

**Языки:**
- В основном JS/TS.
- WASM (Rust, Go, C++), но с ограниченными bindings.
- Python — новее, через Pyodide в Workers.

**Размер деплоя:**
- Workers: 10MB в сжатом виде.
- Lambda@Edge: 50MB.

**О чём ещё помнить:**
- Нет long-polling и долгоживущего HTTP — максимум 30 с.
- Нет диска → состояние только через KV/DO/R2.
- Региональный комплаенс — резидентность данных.

## Q15. Что с cold start на edge?

Главное различие здесь — снова про модель изоляции. У Workers cold start практически отсутствует (изолят создаётся за микросекунды), у Lambda@Edge он реальный, потому что нужно поднять контейнер.

**Workers:**
- Практически нулевой — V8-изолят стартует за микросекунды.
- Первый запрос к POP может стоить ~1-5 мс на загрузку кода.

**Lambda@Edge:**
- Cold start 50-500 мс.
- Node.js прогревается быстрее, чем Java/.NET.
- Снизить: меньше пакет, Provisioned Concurrency.

**Как бороться:**
- Держать пакеты маленькими.
- Переиспользовать runtime — не импортировать крупные модули динамически.
- Для Workers это вообще не проблема.

**Тёплый инстанс.** После первого запроса POP держит изолят/контейнер тёплым ~5-15 минут, поэтому при стабильном трафике он всегда прогрет — cold start почти не встречается.

## Q16. Дороже ли edge по сравнению с традиционным compute?

Зависит от профиля нагрузки. Edge тарифицируется **за вызовы и масштабируется до нуля**, поэтому выигрывает на «рваном» глобальном трафике с высокой кэшируемостью и проигрывает на постоянных тяжёлых вычислениях, где дешевле арендованный сервер.

**Cloudflare Workers (2024):**
- Платный тариф: $5/мес, 10M запросов включено.
- Сверх лимита: $0.50 за миллион.
- CPU: максимум 30 с, медианно тарифицируется около 50 мс.

**AWS Lambda@Edge:**
- $0.60 за миллион запросов.
- Плюс $0.0000125128 за GB-секунду.

**Сравнение (100M запросов/мес):**
- Workers: ~$50.
- Lambda@Edge: ~$60 + вычисления.
- EC2 (always-on): зависит от размера, от сотен до тысяч $.

**Edge дешевле, когда:**
- 90%+ трафика кэшируется на edge.
- Нагрузка пиковая — масштаб до нуля экономит на простое.
- Нужна глобальная распределённость без мультирегионального EC2.

**Edge дорог, когда:**
- Тяжёлые CPU-bound вычисления.
- Долгие запросы.
- Stateful-приложения.

## Q17. (!) Как отлаживать edge и строить observability?

Главная сложность здесь — **распределённость**: код выполняется в сотнях POP, поэтому нет одного места, куда «сходить за логами». Особенно у Lambda@Edge, где логи разбросаны по CloudWatch множества регионов. Это делает трассировку сложнее, чем в обычном монолите.

**Логи:**
- Cloudflare: live-стрим через `wrangler tail`.
- Lambda@Edge: CloudWatch в том регионе, где выполнялось — а их может быть много.

**Метрики:**
- Дашборд Cloudflare: запросы, ошибки, CPU-время на воркер.
- Метрики CloudFront: cache hit ratio, ошибки.

**Трассировка:**
- Сложнее обычного из-за кросс-региональности.
- Экспорт OpenTelemetry в Honeycomb или Datadog.
- Workers Trace Events API.

**Локальная разработка:**
- `wrangler dev` — запускает воркер локально на miniflare (эмулятор workerd).
- `sam local` для Lambda@Edge, но возможности ограничены.

**Тестирование:**
- Unit: мокать Fetch и KV.
- Integration: деплой на staging-воркер.

**Обработка ошибок:**
- Try/catch в воркере, репорт в Sentry.
- Возвращать осмысленный ответ об ошибке, а не голый 5xx.

## Q18. Какие стратегии деплоя на edge?

Ключевое отличие от обычного деплоя: код едет сразу на все POP мира одной командой, поэтому особенно важны **постепенная раскатка** (чтобы баг не накрыл всех сразу) и **быстрый откат**.

**Cloudflare Workers:**
- `wrangler deploy` — мгновенно и глобально (распространение 5-30 с).
- Canary через процентную маршрутизацию — пускаем новую версию на часть трафика:
```
routes: [
  { pattern: "example.com/*", script: "worker-v2", percent: 10 }
]
```
- Откат быстрый — передеплой предыдущей версии.

**Lambda@Edge:**
- Пиннинг версии — одна версия на путь дистрибуции.
- Распространение 2-5 мин по миру.
- Откат — переключить CloudFront на прежнюю версию.

**CI/CD:**
- GitHub Actions → `wrangler deploy`.
- Сначала прогон тестов в preview-окружении.

**Переменные окружения и секреты:**
- Свои конфиги под каждое окружение.
- `wrangler secret put` — зашифрованное хранилище.

**A/B-деплой через feature-флаг.** Тот же воркер ветвится по флагу из KV — переключение мгновенное, без нового деплоя.
