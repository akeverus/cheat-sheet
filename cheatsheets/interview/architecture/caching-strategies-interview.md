## Q1. Что такое локальный кэш и распределённый кэш?

Локальный кэш — кэш в памяти процесса приложения (`Caffeine`, `Guava Cache`, `Ehcache`). Плюсы: минимальная латентность, нет сетевых вызовов. Минусы: не разделяется между инстансами; при масштабировании каждый инстанс имеет свой кэш; инвалидация на других узлах сложнее.

Распределённый кэш — кэш на отдельных узлах (`Redis`, `Memcached`). Плюсы: общий кэш для всех инстансов; централизованная инвалидация. Минусы: сетевая задержка, зависимость от доступности кэш-сервера.

## Q2. Что такое многоуровневый кэш (L1/L2)?

**Многоуровневый кэш** — комбинация уровней: **L1** — локальный (`in-memory`, `Caffeine`), **L2** — распределённый (`Redis`). Запрос сначала проверяет `L1`; при промахе — `L2`; при промахе в `L2` — источник данных (БД). Результат записывается в оба уровня.

Согласованная инвалидация: при обновлении инвалидировать оба уровня (например, `Redis / TTL` в `L1` обычно короче, чем в `L2`.

Плюсы: горячие данные обслуживаются из `L1` с минимальной задержкой; `L2` снижает нагрузку на БД. Важно: согласованная инвалидация (при обновлении инвалидировать оба уровня).

В `Spring` можно комбинировать `Caffeine` (`L1`) и `Redis` (`L2`) через кастомный `CacheManager` или два уровня с разными именами кэшей: сначала lookup в `L1`, при промахе — в `L2`, при промахе в `L2` — загрузка из БД и запись в оба. `TTL` в `L1` обычно короче, чем в `L2`, чтобы быстрее подхватывать инвалидацию; при публикации события инвалидации нужно очищать и `L1` во всех инстансах (например, через `Redis` Pub/Sub или общий канал).

**Пример двухуровневого доступа (псевдокод):**

```java
public User getUser(Long id) {
    String key = "user:" + id;
    User u = localCache.get(key);           // L1
    if (u != null) return u;
    u = redis.get(key);                    // L2
    if (u != null) { localCache.put(key, u); return u; }
    u = userRepository.findById(id);       // БД
    if (u != null) { redis.set(key, u); localCache.put(key, u); }
    return u;
}
```

## Q3. Что такое HTTP-кэш (браузерный и прокси)?

**HTTP-кэш** — кэширование ответов по заголовкам **Cache-Control**, **ETag**, **Last-Modified**. Браузер и прокси (`CDN`, `Nginx`) хранят ответ и не запрашивают сервер при повторном запросе. Для персональных данных используют `private` или `no-store`.

Сервер отдаёт ETag; клиент при повторном запросе шлёт **If-None-Match**; при неизменных данных — **304 Not Modified** без тела. **Практика:** **Cache-Control**: `max-age`=3600 — кэш на 1 час; для статики — `public, max-age=31536000` с версией в имени файла.

Сервер отдаёт ETag (хеш тела или версии); клиент при повторном запросе шлёт `If-None-Match: etag`; при неизменных данных сервер отвечает **304 Not Modified** без тела — экономия трафика. Для персональных данных используют `private` (кэш только в браузере) или `no-store`. `CDN` кэширует по пути и заголовкам; для инвалидации — purge по `URL` или по тегу (`CloudFront`, `Fastly`). В `Spring`: `CacheControl.maxAge(1, HOUR).cachePublic()` для статики; для `REST API` с ETag — `ShallowEtagHeaderFilter` или ручная установка ETag в ответе.

**Практика:** для статики (`JS / CSS`) — **Cache-Control**: public, `max-age`=31536000 (год) с версией в имени файла; для `API` с редкими обновлениями — ETag по хешу тела; для персональных данных — **Cache-Control**: private, no-store.

## Q4. Что такое hit ratio и miss ratio?

**Hit ratio** — доля запросов, обслуженных из кэша: **hit_ratio = hits / (hits + misses)**. **Miss ratio** = 1 − `hit_ratio` — доля запросов, при которых данные загружались из источника.

Целевые значения: 80–95% для горячих справочников. Метрики: `Redis INFO stats` (`keyspace_hits`, `keyspace_misses`) или `Micrometer CacheMetrics`. Низкий hit ratio — проверить дизайн ключей, `TTL` и размер кэша.

Типичные целевые значения: 80–95% для горячих справочников; для персональных данных hit ratio может быть ниже из-за высокой кардинальности ключей. Метрики снимают с кэша (`Redis INFO stats`: `keyspace_hits`, `keyspace_misses`) или через `Micrometer CacheMetrics`. Если hit ratio низкий при стабильных данных — проверить дизайн ключей (избегать уникальных id в ключе без ограничения набора), `TTL` и размер кэша. В `Prometheus`/`Grafana` hit ratio считают как `rate(keyspace_hits)/(rate(keyspace_hits)+rate(keyspace_misses))` или по метрикам кэша.

**Практика:** алерт при hit ratio &lt; 70% в течение 15 минут; дашборд с трендом hit ratio по кэшам; при падении после деплоя — ожидаемо (холодный кэш), дать время на прогрев.

## Q5. Что такое eviction policy и какие бывают?

**Eviction policy** — политика вытеснения записей при переполнении кэша. **LRU** (`Least Recently Used`) — вытесняются наименее недавно использованные. **LFU** (`Least Frequently Used`) — наименее часто используемые. **TTL** — удаление по истечении времени. **FIFO** — первым пришёл — первым вытеснен.

`Caffeine` по умолчанию — `Window TinyLFU`. В `Redis` по умолчанию `noeviction`; настраивают `allkeys-lru`, `volatile-ttl` и др. `LRU` подходит для большинства сценариев; `LFU` — когда важна частота обращений.

`LRU` подходит для большинства сценариев (горячие данные остаются). `LFU` — когда важна частота обращений, а не давность (например, топ популярных ключей). `volatile-ttl` в `Redis` вытесняет записи с истекающим `TTL`. В `Java Caffeine` по умолчанию использует `Window TinyLFU` — комбинация `LRU` и `LFU` для лучшего hit ratio при ограниченном размере.

**Redis — выбор политики в конфиге:**
```conf
maxmemory 256mb
maxmemory-policy allkeys-lru
```
Варианты: `allkeys-lru`, `volatile-lru`, `allkeys-lfu`, `volatile-ttl`, `noeviction`.

## Q6. Что такое Cache-Aside (Lazy Loading)?

`Cache-Aside` — приложение само управляет кэшем: при чтении сначала проверяет кэш; при промахе загружает из БД и записывает в кэш. При записи приложение обновляет БД и инвалидирует кэш (удаляет ключ). Плюсы: простота; кэш содержит только запрашиваемые данные. Минусы: при промахе два запроса (чтение + запись в кэш); возможна гонка при одновременной записи и чтении (stale data). В `Spring` реализуется через `@Cacheable` (чтение) и `@CacheEvict` (инвалидация при обновлении); порядок операций при записи — сначала БД, затем удаление ключа в кэше, чтобы не оставлять устаревшее значение.


## Q7. Что такое Write-Through?

**Write-Through** — при записи приложение пишет и в кэш, и в БД синхронно. Порядок: сначала БД, потом кэш — при сбое данные не расходятся. Плюсы: кэш и БД согласованы. Минусы: повышенная латентность записи. Подходит, когда консистентность важнее скорости записи.

При чтении данные берутся из кэша; при промахе загружаются из БД и записываются в кэш. При падении кэша после записи данные уже в БД и при следующем чтении подтянутся в кэш.

Порядок операций: сначала запись в БД, затем обновление кэша (или наоборот при использовании кэша как write buffer — тогда кэш пишет в БД). При сбое после записи в кэш, но до БД — данные в кэше не совпадают с БД; поэтому часто выбирают «сначала БД, потом кэш».

**Пример (`Spring`):** при обновлении сущности сначала сохраняем в БД, затем кладём в кэш и/или инвалидируем ключ.
```java
@CacheEvict(value = "users", key = "#user.id")
@Transactional
public User update(User user) {
    User saved = userRepository.save(user);  // сначала БД
    cache.put("user:" + saved.getId(), saved); // затем кэш при write-through
    return saved;
}
```

## Q8. Что такое Write-Behind (Write-Back)?

**Write-Behind (Write-Back)** — при записи приложение пишет в кэш и сразу возвращает успех; запись в БД выполняется асинхронно (батчами или по расписанию). Плюсы: низкая латентность, разгрузка БД. Минусы: риск потери данных при падении до сброса в БД; сложность консистентности.

Подходит для логов, метрик, счётчиков; для платежей — `Write-Through`. Требует надёжной очереди (`Kafka`, `RabbitMQ`) или `WAL` и идемпотентности записи в БД при повторной доставке.

Реализация: при put в кэш запись также ставится в очередь (`Kafka`, `RabbitMQ`) или в `WAL`; воркер батчами пишет в БД. При падении воркера очередь сохраняет записи; при перезапуске обработка продолжается. Идемпотентность по ключу (например, `order_id`) позволяет безопасно повторять запись при повторной доставке. Подходит для логов, метрик, счётчиков; для критичных финансовых операций предпочтительнее `Write-Through`.

**Практика:** в коде при обновлении счётчика или события — `cache.put(key, value)` и отправка сообщения в `Kafka` с тем же ключом; consumer батчами пишет в БД (по ключу — последнее значение или merge). При повторной доставке сообщения запись по ключу идемпотентна (перезапись тем же или новым значением). Не использовать `Write-Behind` для платежей и критичных к консистентности данных без явного согласования рисков.

## Q9. Когда использовать TTL, а когда инвалидацию по событию?

**TTL** — запись живёт заданное время; подходит для справочников и редко меняющихся данных. **Инвалидация по событию** — при изменении в БД приложение удаляет/обновляет ключ в кэше; подходит для часто меняющихся данных, когда нужна актуальность сразу после записи.

Для персональных данных (профиль, корзина) — инвалидация по событию; для справочников — `TTL` с jitter. Комбинированный подход: `TTL` как страховка (например, 1 час) плюс инвалидация при обновлении — при пропуске события кэш обновится по истечении `TTL`.

**Пример комбинации в коде:** при обновлении сущности вызываем `@CacheEvict`, а у кэша задан `TTL` (например, `Caffeine.expireAfterWrite(1, HOUR)`) — при пропуске события кэш всё равно обновится через час.

## Q10. Что такое cache stampede (thundering herd) и как его избежать?

**Практический приём:** для горячих ключей объединяйте конкурентные запросы (singleflight/request coalescing), иначе при истечении `TTL` БД получает лавину одинаковых чтений.

`Cache` stampede — при истечении популярного ключа множество потоков одновременно обнаруживают промах и все идут в БД, создавая всплеск нагрузки. Решения: блокировка (один поток загружает, остальные ждут); вероятностное раннее обновление (обновлять до истечения `TTL` с вероятностью); предзагрузка до истечения `TTL`. В `Java` часто используют блокировку по ключу (например, `ConcurrentHashMap` + `computeIfAbsent` или отдельный lock per key); при распределённом кэше — distributed lock (`Redis SET NX`) или singleflight-подобный паттерн.


## Q11. Как кэшировать результаты с разными ключами (списки, фильтры)?

Списки и фильтры дают высокую кардинальность ключей и низкий hit ratio. Подходы: кэшировать сущности по **id** и собирать список из кэша; кэшировать только популярные комбинации (первая страница, топ-фильтры); короткий `TTL`; инвалидация по тегу (при изменении сущности — инвалидировать ключи с этим тегом).

Ключ вида `list:filter1=val1:page=1` даёт много комбинаций. Лучше кэшировать по id (`entity:123`); при запросе списка получать id из БД или из кэша списка id (короткий `TTL`), затем загружать сущности из кэша по id.

**Практика:** в `Spring`: `@Cacheable` с ключом по параметрам для популярных комбинаций; `@CacheEvict(cacheNames = "users", allEntries = true)` при обновлении сущности — инвалидация всего кэша списков по тегу. Первую страницу и топ-фильтры кэшировать отдельно с коротким `TTL`.

Ключ вида `list:filter1=val1:filter2=val2:page=1` даёт огромное число комбинаций. Лучше кэшировать сущности по id (`entity:123`); при запросе списка получать id из БД или из кэша списка id (короткий `TTL`), затем загружать сущности из кэша по id — промахи подгружать из БД. Первую страницу и топ-фильтры можно кэшировать отдельно с коротким `TTL`. Инвалидация по тегу: при обновлении entity:123 удалять все ключи с тегом `entity:123`.

**Пример ключей:** кэш по id — `product:42`, `product:99`; список id первой страницы — `products:page:1:ttl:60` (короткий `TTL`). При запросе «страница 1» сначала берём id из кэша или БД, затем `product:42`, `product:99` из кэша; промахи — из БД с записью в кэш.

## Q12. Что такое cache penetration, cache avalanche?

`Cache / TTL`, чтобы повторные запросы по тому же ключу не били в БД. Дополнительно: блум-фильтр для отсечения заведомо несуществующих ключей; лимит запросов по одному ключу.

`Cache` avalanche — массовое истечение `TTL` многих ключей одновременно (например, кэш заполнялся в один момент); всплеск запросов к БД. Решение: разброс `TTL` (базовый `TTL` + случайное отклонение); высокая доступность кэша; ограничение нагрузки на БД. При холодном старте кэша предпочтительнее постепенная загрузка (`cache` warming по приоритету) или ленивая загрузка с jitter по `TTL`.

## Q13. Как обеспечить консистентность кэша и БД?

Подходы: `Write-Through` — запись в кэш и БД синхронно. `Cache-Aside` с инвалидацией — при записи в БД удалять ключ в кэше (или обновлять кэш после успешной записи). Короткий `TTL` — приемлемая задержка консистентности для редко меняющихся данных. События — при изменении данных публиковать событие; потребители инвалидируют кэш. При распределённом кэше единая стратегия для всех писателей; иначе один сервис может инвалидировать ключ, а другой — перезаписать устаревшим значением. Порядок операций при `Cache-Aside`: сначала обновить БД, затем инвалидировать кэш; при обратном порядке возможна гонка (чтение после инвалидации, но до записи в БД — устаревшие данные).


## Q14. Как кэшировать в микросервисной архитектуре?

Локальный кэш в каждом сервисе — быстрый, но инвалидация при изменении в другом сервисе сложна (события, сообщения). Распределённый кэш (`Redis`) — общий для инстансов одного сервиса; при изменении данных сервис инвалидирует свои ключи. При изменении в другом сервисе — событие или `API` для инвалидации; избегать кэширования чужих данных без контракта на инвалидацию. Часто комбинируют `L1` (локальный, короткий `TTL`) и `L2` (`Redis`); при публикации события подписчики инвалидируют свой `L1` и соответствующие ключи в `L2`; важна идемпотентность обработки инвалидации.


## Q15. Что такое Near Cache и когда его использовать?

**Near Cache** — локальный кэш рядом с клиентом распределённого кэша (`Hazelcast Near Cache`, клиент `Redis` с локальным кэшем). Горячие ключи обслуживаются из локальной памяти; уменьшается нагрузка на сеть и распределённый кэш.

Используют при высокой частоте обращения к одному набору ключей. Важно: согласованная инвалидация — при обновлении в распределённом кэше локальный кэш должен инвалидироваться (события, `TTL`).

Обычно `Near Cache` имеет ограниченный размер (max entries) и `TTL` или invalidation при обновлении в кластере (`Hazelcast` рассылает инвалидацию при изменении записи). Подходит для `read-heavy` с повторяющимся набором ключей (например, топ товаров, конфигурация). **Не подходит:** высокая кардинальность ключей (много уникальных ключей — локальный кэш раздувается, hit ratio низкий); частые обновления (инвалидация между клиентами усложняется); данные, требующие строгой консистентности между всеми узлами.

**Практика:** в `Hazelcast` — включить `Near Cache` для map с `invalidate-on-change: true`, задать `max-size` и `TTL`. В клиенте `Redis` (`Lettuce`, `Jedis`) можно держать локальный `Caffeine` поверх `Redis` для горячих ключей; при обновлении ключа публиковать событие инвалидации (`Redis / Near Cache`: при низком — уменьшить кардинальность или увеличить размер.

## Q16. Что такое cache warming и когда его применять?

`Cache` warming — предзаполнение кэша при старте приложения или по расписанию (популярные ключи загружаются до первых запросов). Применяют чтобы избежать всплеска промахов и нагрузки на БД после деплоя или перезапуска. Реализация: при старте загрузить топ-N ключей; или фоновый процесс периодически обновляет горячие ключи. Важно не блокировать старт приложения долгим warming: загружать ключи асинхронно или с ограничением по времени; при большом объёме — приоритизировать самые горячие ключи.


## Q17. Как выбрать TTL для кэша?

Зависит от требований к консистентности: строгая консистентность — короткий `TTL` или инвалидация по событию; допустима задержка (например, справочники) — длинный `TTL` (минуты–часы). Рекомендуют разброс `TTL` (базовый + случайное отклонение), чтобы избежать массового истечения (`cache` avalanche). Типичные ориентиры: справочники и редко меняющиеся данные — 10–60 минут или часы; пользовательские сессии — минуты; часто обновляемые сущности — секунды или инвалидация по событию. Метрики hit ratio и latency помогают подобрать `TTL`: при низком hit ratio и стабильных данных — увеличить `TTL`; при жалобах на устаревшие данные — уменьшить или перейти на инвалидацию по событию.


## Q18. Что такое write-through vs write-behind в контексте консистентности?

**Write-Through** — запись в кэш и БД синхронно; после успешной записи кэш и БД согласованы. **Write-Behind** — запись в кэш сразу, в БД асинхронно; возможна потеря данных при сбое до сброса в БД; консистентность ослаблена.

`Write-Through` предпочтителен, когда консистентность важна (платежи, профиль); `Write-Behind` — когда приоритет низкая латентность записи (логи, метрики, счётчики).

При `Write-Behind` читатель может прочитать из кэша значение, которое ещё не попало в БД; при падении кэша эти данные теряются. Для аудита и финансовых операций обычно выбирают `Write-Through` или синхронную запись в БД с последующей инвалидацией кэша. `Write-Behind` уместен для счётчиков, логов, аналитики — где допустима небольшая потеря или задержка консистентности. В `Spring` при `Cache-Aside` инвалидация при записи (`@CacheEvict`) даёт эффект «сначала БД, потом кэш» — близко к `write-through` по консистентности.

## Q19. Как мониторить кэш в production?

Метрики: **hit ratio**, **miss ratio**, **latency** (get/set), размер кэша, число ключей, **eviction rate**; алерты при падении hit ratio, росте latency, переполнении.

В `Redis` — `INFO stats`, `INFO memory`; в приложении — `Micrometer` по `Cache` (`cache.gets`, `cache.puts`, `cache.evictions`). Дашборды для трендов; при деплое отслеживать всплеск промахов и время до стабилизации hit ratio. Алерты: hit ratio &lt; 70%, p99 latency выше порога, память `Redis` &gt; 80%.

Алерты: hit ratio ниже порога (например, &lt; 70%) в течение N минут; p99 latency get выше порога; использование памяти `Redis` выше 80%; `eviction` rate резко вырос. После деплоя или перезапуска ожидаем временный всплеск miss ratio — не алертить сразу, дать время на прогрев. `Redis EXPORTER` для `Prometheus` собирает метрики; `Grafana` и `spring-boot-starter-cache` с `Caffeine`/`Redis` метрики автоматически экспортируются в `Actuator` и `Prometheus` при наличии `micrometer-registry-prometheus`.

## Q20. Что такое cache coherence в распределённом кэше?

**Cache coherence** — согласованность кэша между узлами. В распределённом кэше (`Redis Cluster`) данные реплицируются или шардируются; при записи в один узел другие узлы могут видеть старую версию до репликации.

Стратегии: инвалидация по событию (публикация «удалить ключ» при изменении); короткий `TTL`; использование одного узла для записи по ключу (`Redis` — один шард по ключу). Для критичной консистентности — `write-through` и инвалидация по событию.

В `Redis Cluster` каждый ключ принадлежит одному шарду по хешу слота; реплики шарда получают копию асинхронно. Чтение с реплики может вернуть устаревшие данные. Для строгой консистентности читать с primary по ключу или использовать инвалидацию: при обновлении публиковать сообщение (`Redis / Kafka`), подписчики удаляют ключ в своём локальном кэше или в `Redis`. `Near Cache` усложняет coherence — при обновлении нужно инвалидировать `Near Cache` во всех клиентах. **Практика:** при обновлении сущности публиковать событие `CacheInvalidateEvent(key)` или через `Redis` Pub/Sub.

## Q21. Что такое cache key design и какие ошибки избегать?

`Cache` key design — проектирование ключей кэша. Ошибки: высококардинальные ключи (уникальный id в ключе для каждого пользователя — много ключей, низкий hit ratio); слишком длинные ключи (ограничения размера в `Redis`); неоднозначные ключи (разные данные под одним ключом при разных версиях). Рекомендации: осмысленный префикс (домен:версия); ограничение кардинальности; короткие стабильные ключи. При смене формата сериализации или полей — версия в ключе (`user:v2:123`) или короткий `TTL` при миграции, чтобы старые записи не ломали десериализацию.


## Q22. Как кэшировать списки и пагинированные результаты?

Списки кэшируют по комбинации параметров (фильтры, страница, сортировка) — высокая кардинальность. Подходы: кэшировать отдельные сущности по id и собирать список из кэша; кэшировать только первую страницу и популярные фильтры; короткий `TTL`; инвалидация по тегу при изменении любой сущности в наборе. Для пагинации кэшируют страницы по ключу `list:hash(params):page:N` с коротким `TTL` или инвалидируют по тегу при изменении данных; кэширование только id списка + загрузка сущностей из кэша по id снижает дублирование и упрощает инвалидацию.


## Q23. Что такое read-through и write-through cache в терминологии провайдеров?

**Read-through** — кэш сам загружает данные из источника при промахе (прозрачно для приложения). **Write-through** — приложение пишет в кэш, кэш синхронно пишет в источник.

В `Spring CacheManager` + `@Cacheable` реализуют паттерн, близкий к **cache-aside** (приложение управляет загрузкой при промахе); провайдеры вроде `Hazelcast` могут предлагать `read-through / write-through` из коробки.

В `read-through` приложение вызывает только `cache.get(key)`; кэш при промахе сам вызывает `Loader` (например, загрузку из БД) и кладёт результат в кэш. В `write-through` приложение вызывает `cache.put(key, value)`; кэш синхронно пишет в `MapStore` (БД). Приложение не знает об источнике данных — логика инкапсулирована в провайдере. В `Spring` при промахе `@Cacheable` вызывается метод с логикой загрузки (например, `repository.findById`) — это **cache-aside**, а не `read-through`; для настоящего `read-through` нужен провайдер с поддержкой `CacheLoader` (например, `Caffeine.build(CacheLoader)` или `Hazelcast MapLoader`).

## Q24. Как обеспечить безопасность кэша (Redis)?

Рекомендации: ограничить доступ по сети (firewall, `VPC`); аутентификация (**AUTH** в `Redis`); шифрование в transit (**TLS**); не хранить чувствительные данные в открытом виде; ограничить команды (отключить `FLUSHALL` и т.п.); мониторинг доступа.

В production `Redis` в приватной сети; пароль и `TLS` в `redis.conf`; секреты из `Vault`. В `Spring`: `spring.data.redis.password` из переменной окружения; для `TLS` — `spring.data.redis.ssl=true` и настройка `SSL`.

В production `Redis` должен быть в приватной сети; доступ только с хостов приложения. В `redis.conf`: `requirepass`, `rename-command FLUSHALL ""`, `tls-port 6380` при использовании `TLS`. Секрет пароля — из `Vault` или переменных окружения, не в коде. Для чувствительных полей (`PII`) — шифрование на уровне приложения перед записью в кэш; ключ шифрования в секретном хранилище. Аудит: логирование доступа, алерты на подозрительную активность (массовый `KEYS`, резкий рост трафика). В `Spring` подключать `Redis` с `TLS` и паролем через `spring.data.redis.password` и `spring.data.redis.ssl=true`; не логировать значения кэша с `PII`.

**Пример `redis.conf` (фрагмент):**
```conf
requirepass ${REDIS_PASSWORD}
rename-command FLUSHALL ""
rename-command CONFIG ""
tls-port 6380
port 0
bind 127.0.0.1
```
Подключение из приложения: `redis://host:6379` или через `Spring` (`spring.data.redis.password` из переменной окружения); для `TLS` — `spring.data.redis.ssl=true` и настройка `SSL`.

## Q25. Что такое cache aside vs lazy loading — одно и то же?

**Cache-Aside** и **Lazy Loading** часто используют как синонимы: приложение при промахе загружает из источника и кладёт в кэш. `Lazy Loading` подчёркивает «загрузка по требованию»; `Cache-Aside` — явное управление кэшем приложением (включая инвалидацию при записи).

По сути один паттерн. В `Spring @Cacheable` + метод с repository — это `cache-aside` (lazy loading). При записи — сначала БД, затем `@CacheEvict` для инвалидации ключа.

Отличие от `read-through`: в `cache-aside` приложение явно проверяет кэш, при промахе загружает из БД и кладёт в кэш; при записи приложение обновляет БД и инвалидирует кэш. В `read-through / Spring @Cacheable` + метод с вызовом repository — это `cache-aside` (lazy loading по требованию); инвалидация при записи — через `@CacheEvict` в методе обновления.

**Практика:** при описании архитектуры говорить «`cache-aside` (lazy loading)» — тогда ясно, что кэш заполняется по первому запросу и приложением управляется логика загрузки и инвалидации. Для справочников с редким обновлением этого достаточно; для часто меняющихся данных — инвалидация по событию после записи.

**Пример (`Spring`):**
```java
@Cacheable(value = "users", key = "#id")
public User findById(Long id) { return userRepository.findById(id).orElseThrow(); }

@CacheEvict(value = "users", key = "#user.id")
public User update(User user) { return userRepository.save(user); }
```
Чтение: при промахе вызывается `findById`, результат кладётся в кэш. Запись: после сохранения в БД ключ удаляется из кэша — следующее чтение подтянет свежие данные.

## Q26. Что такое cache invalidation по тегу и когда применять?

Инвалидация по тегу — группировка ключей по тегу (например, «user:123» для всех ключей, связанных с пользователем `123`); при изменении сущности инвалидируют все ключи с этим тегом. Применяют когда данные связаны (список заказов пользователя, профиль + настройки) и при обновлении одной сущности нужно сбросить несколько ключей. Реализация: хранить маппинг тег → ключи в `Redis` (Set или отдельный ключ со списком); при инвалидации по тегу удалять все ключи из набора. Альтернатива — версия в ключе (user:123:v2); при изменении увеличивать версию, старые ключи вымирают по `TTL`.


## Q27. Как кэшировать графы данных и связанные сущности?

Графы и связанные сущности кэшируют по узлам: каждая сущность по своему id (user:123, order:456); при запросе «пользователь с заказами» загружают user:123 из кэша, затем ключи order:*. Если заказы кэшируются по id — получают список id заказов пользователя (отдельный ключ user:123:`orderIds` или из БД) и загружают каждый order:id из кэша; промахи подгружают из БД и кладут в кэш. Избегать кэширования всего графа одним ключом (огромные значения, сложная инвалидация). Инвалидация по событию: при изменении заказа инвалидировать order:id и при необходимости user:123:`orderIds`.


## Q28. Что такое write-around и когда его использовать?

`Write-Around` — при записи приложение пишет только в источник данных (БД); кэш не обновляется и не инвалидируется при записи. При чтении при промахе данные загружаются из источника и кладутся в кэш. Плюсы: запись не нагружает кэш; подходит для редко перечитываемых после записи данных. Минусы: после записи следующее чтение даёт промах и идёт в БД; возможны устаревшие данные в кэше, если запись делается в обход приложения (миграции, другие сервисы). Используют когда записей много, а повторные чтения тех же данных редки, или когда допустима задержка консистентности до `TTL`.


## Q29. Как кэш влияет на латентность и throughput приложения?

Латентность: при hit запрос обслуживается из кэша (локальный кэш — доли миллисекунды, `Redis` — 1–5 ms по сети), без обращения к БД (десятки–сотни ms). Снижение средней латентности тем выше, чем выше hit ratio. `Throughput`: кэш снижает нагрузку на БД; приложение может обслуживать больше запросов в секунду при той же БД. Риски: при промахах добавляется обращение к кэшу (сеть, сериализация); при переполнении или `eviction` — дополнительная нагрузка; неправильный размер или `TTL` может не дать выигрыша или ухудшить консистентность.


## Q30. Как тестировать кэширование (unit, integration)?

`Unit`: подменять `Cache / CacheManager` моком или `in-memory` реализацией; проверять, что при вызове метода с `@Cacheable` второй вызов с тем же ключом не вызывает репозиторий (verify `mock`). Проверять инвалидацию: после update вызывается `@CacheEvict` и следующий get идёт в репозиторий. `Integration`: тест с реальным `Redis` (`Testcontainers`) или встроенным; проверить запись и чтение, `TTL`, инвалидацию; при необходимости проверить `cache` stampede (много потоков одновременно по одному ключу — один запрос к БД). Проверять метрики hit/miss в тестах, если приложение их экспортирует.


## Q31. Что такое cache serialization и какие форматы предпочтительны?

Сериализация кэша — преобразование объектов в байты для хранения в распределённом кэше (`Redis`, `Memcached`). Форматы: `JSON` — читаемость, межъязыковость; `MessagePack / Protobuf` — компактность и скорость; `Java Serialization` — не рекомендуется (медленно, небезопасно, привязка к `JVM`). Для `Redis` с `Java` часто используют `Jackson` (`JSON`) или `Redis Serializer` с `GenericJackson2JsonRedisSerializer`; для высоконагруженных сценариев — `Kryo` или `FST`. Важно: версионирование схемы при изменении полей объектов. При смене формата или полей старые записи в кэше могут не десериализоваться — используют версию в ключе (например, `user:v2:123`) или короткий `TTL` при миграции.


## Q32. Как кэшировать результаты тяжёлых вычислений (CPU-bound)?

Результаты тяжёлых вычислений (агрегации, машинное обучение, генерация отчётов) кэшируют по ключу, зависящему от входных параметров. При первом запросе — вычисление и запись в кэш с `TTL`; при повторных — чтение из кэша. Для длительных вычислений используют асинхронное кэширование: запрос триггерит вычисление в фоне и возвращает «в процессе» или старые данные; по завершении результат кладётся в кэш. Важно: ограничить параллельные вычисления одного и того же ключа (lock или singleflight), чтобы избежать stampede. Локальный кэш (`Caffeine`) подходит для `CPU-bound`: нет сетевой задержки, быстрый доступ; при распределённой системе — общий ключ и `TTL`, чтобы все инстансы использовали один результат.


## Q33. Что такое cache partitioning и зачем оно нужно?

`Partitioning` (шардирование) кэша — распределение ключей по нескольким узлам (нодам `Redis` или экземплярам) по хешу ключа. Нужно для: горизонтального масштабирования объёма кэша; распределения нагрузки; увеличения пропускной способности. В `Redis Cluster / {user}:123` и `{user}:456` попадают в один слот и могут участвовать в одной транзакции.


## Q34. Как обрабатывать сбои кэша (Redis unavailable)?

**Антипаттерн:** при падении `Redis` без ограничений переключаться на БД и одновременно запускать агрессивные retry — это быстро приводит к каскадному сбою уже на уровне БД.

Стратегии: **Circuit breaker** — при серии ошибок перестаём обращаться к кэшу на время, идём в БД; **Fallback to DB** — при недоступности кэша все запросы обслуживаются из источника данных (с возможным деградацией по latency); **Local fallback cache** — кратковременный локальный кэш (`Caffeine`) с коротким `TTL` при падении `Redis`; **Graceful degradation** — возврат устаревших данных из резервного хранилища, если есть. Важно: мониторинг доступности кэша и алерты; тесты на отказ (chaos engineering). При восстановлении `Redis` не заполнять кэш одним батчем — возможна перегрузка; предпочтительнее ленивая загрузка (`Cache-Aside`) или постепенный `cache` warming.


## Q35. Что такое stale-while-revalidate и когда применять?

`Stale-while-revalidate` (`SWR`) — стратегия: клиенту сразу возвращают закэшированное (возможно устаревшее) значение, а в фоне обновляют кэш для следующего запроса. Применяют в `HTTP` (заголовок **Cache-Control**: `stale-while-revalidate`=<seconds>) и в серверном кэше. Плюсы: низкая латентность для пользователя, фоновая актуализация. Минусы: один запрос может получить устаревшие данные. Уместно для контента, где небольшая задержка актуализации допустима (ленты, каталоги, статика). В серверном кэше реализуют так: при запросе возвращают значение из кэша (если есть), а в фоновом потоке проверяют `TTL` и при необходимости обновляют кэш из источника.


## Q36. Как кэшировать графы и связанные сущности без дублирования?

Кэшировать отдельные сущности по id (user:123, order:456), а не целые графы: при запросе «пользователь с заказами» читают user:123 из кэша, затем ключи заказов (user:123:`orderIds`) или запрос к БД по связи; заказы подтягивают по id из кэша или БД. Дублирования нет: каждая сущность хранится один раз. При изменении заказа инвалидируют order:456; при изменении пользователя — user:123 и при необходимости user:123:`orderIds`. Альтернатива — инвалидация по тегу: ключи регистрируют в Set по тегу (например, «user:123»); при инвалидации по тегу удаляют все ключи набора. Для глубоких графов (дерево категорий, оргструктура) кэшируют узлы по id и ссылки на детей; при изменении узла инвалидируют его ключ и при необходимости ключ родителя (список детей).


## Q37. Что такое cache coherence в мультидатацентровой среде?

`Cache` coherence — согласованность копий данных между кэшами в разных датацентрах. В мультидатацентровой среде каждый `DC` может иметь свой кэш (локальный или реплика `Redis`); при обновлении в одном `DC` кэши в других могут содержать устаревшие данные. Подходы: инвалидация по событию — при записи в `DC1` публикуется событие (`Kafka`, `RabbitMQ / TTL` — короткий `TTL` уменьшает окно несогласованности, но не устраняет её полностью; синхронная запись — запись в кэш всех `DC` (выше latency); версионирование — версия в ключе или в значении, клиент сравнивает версии. Выбор зависит от требований к консистентности и допустимой задержки. Для строгой консистентности между `DC` часто используют централизованный кэш (один `Redis Cluster` с репликами в `DC`) или отказ от кэша для критичных данных.


## Q38. Как выбирать между Caffeine, Redis и Hazelcast?

**Trade-off:** выбор обычно не «или/или» — для production-путей часто эффективнее гибрид `L1 Caffeine` + `L2 Redis`, чем ставка только на один слой.

`Caffeine` — локальный `in-memory` кэш в процессе `JVM`. Плюсы: минимальная латентность, нет сети, простой `API`. Минусы: не разделяется между инстансами, при рестарте кэш пуст. Уместно: горячие справочники, результаты тяжёлых вычислений, один инстанс или не критична консистентность между инстансами. `Redis` — распределённый кэш. Плюсы: общий кэш для всех инстансов, персистентность (`RDB / AOF`), богатый `API`. Минусы: сетевая задержка, зависимость от доступности сервера. Уместно: сессии, общие справочники, кэш между микросервисами. `Hazelcast` — распределённый кэш и структуры данных в кластере `JVM`. Плюсы: `read-through / write-through` из коробки, распределённые структуры (Map, `Queue`), встроенная репликация. Минусы: сложнее эксплуатация кластера, потребность в `JVM` на всех узлах. Уместно: когда нужны `read-through / write-through` или тесная интеграция с `Java` без отдельного сервера кэша. Часто комбинируют: `L1` — `Caffeine`, `L2` — `Redis`.


## Q39. Что такое cache stampede на уровне ключа и как его подавить?

`Cache / TTL`, уменьшая вероятность массового истечения; `stale-while-revalidate` — возвращать устаревшее значение и в фоне обновлять кэш; `request` coalescing — объединять одновременные запросы по одному ключу в один вызов к источнику. В `Java` часто реализуют через `LoadingCache` (`Caffeine`, `Guava`) — при промахе один поток вычисляет, остальные блокируются на get и получают результат после записи в кэш. Для `Redis` аналогичный эффект даёт singleflight-паттерн на стороне приложения или блокировка по ключу (`Redis SETNX` с коротким `TTL`).


## Q40. Как измерять и интерпретировать метрики кэша в production?

Собирать: hit ratio (hits / (hits + misses)) — цель 80–95% для горячих ключей; низкий hit ratio указывает на плохой дизайн ключей, короткий `TTL` или неподходящие данные. `Latency / Eviction` rate — частые evictions снижают hit ratio. Ошибки (timeout, connection refused) — доступность кэша. Инструменты: `Micrometer` + `Prometheus / Grafana` для метрик приложения; `Redis INFO` stats (`keyspace_hits`, `keyspace_misses`), latency; алерты при падении hit ratio ниже порога (например 70%), росте p99 выше порога, открытии circuit breaker. Интерпретация: резкое падение hit ratio после деплоя — возможно смена ключей или `TTL`; рост `eviction` rate — увеличить память или сократить `TTL`. Для Caffeine метрики экспортируют через `Caffeine.stats()` (`hitCount`, `missCount`, `loadSuccessCount`) и прокидывают в `Micrometer`; дашборды строят по тем же метрикам, что и для `Redis`.
