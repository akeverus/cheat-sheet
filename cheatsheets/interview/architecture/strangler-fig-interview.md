# Вопросы на собеседовании: `Strangler Fig Pattern`

`Strangler Fig` — паттерн **постепенной миграции** монолита → microservices (или legacy → modern). Вместо "big bang rewrite" новая функциональность оборачивает старую и постепенно её замещает. Название придумал Martin Fowler (2004), вдохновившись деревьями-душителями (strangler fig). Индустриальный стандарт для модернизации с управляемым риском.

## Q1. (!) Что такое Strangler Fig pattern?

**Strangler Fig** (Martin Fowler, 2004) — паттерн **инкрементальной миграции**: новая система постепенно, кусок за куском, замещает старую, пока та не окажется полностью «задушена» (strangled). Ключевая идея — никакого «big bang»-переключения: старое и новое работают бок о бок, а трафик перетекает на новое по мере готовности.

**Откуда название.** В тропическом лесу есть деревья-душители (strangler fig): семя прорастает на ветке дерева-хозяина, фикус разрастается вокруг ствола вниз к земле и в итоге хозяин гибнет внутри, а на его месте остаётся самостоятельный фикус. Та же траектория в миграции:
- Новые сервисы «обвивают» legacy-монолит снаружи
- За один шаг заменяется ровно один кусок функциональности
- Монолит постепенно выводится из эксплуатации, а не отключается разом

**Конечное состояние:** legacy полностью заменён и удалён, новая система работает самостоятельно.

**Почему это работает.** Замена идёт мелкими обратимыми шагами, поэтому на каждом шаге риск минимален, а ценность поставляется непрерывно — не нужно ждать «100% готово», чтобы что-то выкатить.

**Диаграмма (прогрессия):**
```
Stage 1: [Monolith 100%]
Stage 2: [New Service A | Monolith 80%]
Stage 3: [Service A | Service B | Monolith 60%]
...
Stage N: [Service A | Service B | Service C | Service D]  (monolith gone)
```

## Q2. (!) Зачем Strangler вместо big bang rewrite?

Коротко: **big bang rewrite (переписать всё с нуля и переключиться разом) — это ставка ва-банк**, а strangler разбивает её на серию мелких безопасных ставок. Главная разница — в распределении риска во времени.

**Чем плох big bang:**

- **Огромный риск, отложенный к самому концу.** Месяцы или годы работы, прежде чем появится хоть какая-то ценность; часто проект так и не доходит до прода (классический пример — «Netscape rewrite»). Доля провалов крупных переписываний — 50%+.
- **Гонка за паритетом по фичам.** Новое должно повторить *все* старые функции до переключения, но старое всё это время продолжает развиваться — цель движется, и догнать её тяжело.
- **Ноль инкрементальной ценности.** Пока не готово на 100%, выгоды нет: нельзя учиться на реальном трафике и корректировать курс по дороге.
- **Падает боевой дух.** Длинный туннель без промежуточных побед изматывает команду, а бизнес теряет терпение.
- **Тяжело тестировать.** Пока система не заменена целиком, не прогнать сквозные integration-тесты — и реальность тихо расходится со спецификацией.

**Что даёт strangler взамен:**
- Инкрементальная поставка ценности — польза идёт с первого же мигрированного куска
- Риск на каждый кусок мал, и проблемы локализованы
- Ранняя обратная связь и обучение на живом трафике
- Rollback возможен по отдельным кускам, без отката всего проекта
- Бизнес видит прогресс, а команда сохраняет темп

**Консенсус индустрии (Sam Newman, Fowler, блог Netflix):** strangler выигрывает у big bang в 95%+ случаев.

## Q3. (!) Как работает механика?

Механика держится на одном элементе — **прокси/фасаде перед обеими системами**, который для каждого запроса решает, куда его отправить. Пока маршрут не мигрирован, прокси шлёт запрос в монолит; как только готов новый сервис — перенаправляет на него. Это и позволяет менять систему по кускам, не трогая клиента.

**Три компонента:**

- **Proxy / Facade layer** — единая точка входа для трафика. Маршрутизирует каждый запрос в старую или новую систему по URL, feature flag или сегменту пользователя.
- **Новый сервис** — реализует часть старой функциональности и деплоится независимо от монолита.
- **Старый монолит** — всё ещё работает и обслуживает все ещё не мигрированные пути.

**Поток:**
```
Client → Proxy
         ├─ /users (migrated) → [New User Service]
         ├─ /orders (in progress) → [Shadow: both]
         └─ /rest → [Old Monolith]
```

**Пошаговая прогрессия (цикл повторяется для каждого среза):**
1. Задеплоить proxy — поначалу прозрачный, весь трафик идёт в монолит
2. Построить новый сервис для одного среза (например, endpoint профиля пользователя)
3. Направить небольшой % трафика на новый сервис
4. Мониторить и чинить проблемы на малом проценте
5. Постепенно нарастить долю до 100%
6. Удалить замещённый код из монолита
7. Повторить для следующего среза

## Q4. (!) С чего начинать strangling?

Главный принцип — **первым выносить то, что легко отделить и не страшно сломать**. Первый срез нужен не столько ради бизнес-эффекта, сколько чтобы команда отработала на нём весь процесс миграции при минимальном риске.

**По каким критериям выбирать срез:**

- **Слабая связанность** — мало зависимостей, чистый интерфейс, который можно обернуть за API.
- **Высокая ценность или высокая боль** — там, где в монолите уже есть баги или проблемы масштабируемости, либо это приоритет для бизнеса.
- **Изолированные данные** — свои таблицы, минимум join к другим доменам; миграцию БД проще выполнить.
- **Хорошее покрытие тестами** — легче проверить, что новый сервис ведёт себя эквивалентно старому.

**Типичные первые кандидаты** (и почему они удобны):
- **Read-heavy endpoints** — низкий риск, читающую реплику легко поднять
- **Краевые endpoints** — не лежат на основном transaction path
- **Аутентификация** — хорошо ограничена и имеет чёткий контракт
- **Уведомления** — асинхронные и восстановимые, ошибка не критична
- **Отчётность** — обычно работает на отдельном хранилище данных

**Чего избегать на старте:**
- Основные бизнес-транзакции
- Сильно связанное (тянет за собой половину БД монолита)
- Критичное для комплаенса (платежи, identity — слишком высокий риск, пока процесс не отлажен)

**Стратегия:** взять небольшую раннюю победу → нарастить уверенность команды и обкатать паттерн, прежде чем браться за ядро.

## Q5. (!) Какие функции выделять первыми?

Двигайся **от периферии к ядру** — сначала то, что слабо связано с остальным, в конце то, что завязано на всё. Связанность здесь — главный сортировочный признак.

**Шкала связанности (на примерах):**
- **Низкая** — внешний поиск: легко вынести в отдельный сервис
- **Средняя** — профиль пользователя: используется многими частями системы, но данные обособлены
- **Высокая** — обработка заказов: затрагивает платежи, склад, доставку одновременно

**Как находить границы — bounded contexts (DDD):**
- Выявить естественные границы в домене
- Каждый bounded context — кандидат на отдельный сервис
- Воркшоп Event Storming помогает эти границы разметить

**Порядок декомпозиции:**
1. **Периферийное** — уведомления, отчёты, поиск
2. **Вспомогательное** — auth, управление пользователями
3. **Ядро домена** — когда команда уже набралась опыта

**Совет:** начинай там, где цена ошибки для бизнеса наименьшая, то есть с *менее* критичных вещей. Сначала отточи процесс миграции на них, а уже отлаженный применяй к ядру.

## Q6. Как мигрировать данные при общей БД (shared DB)?

Данные — **самая сложная часть миграции**, потому что общая база (shared DB) означает тесную связанность: пока монолит и новый сервис ходят в одни таблицы, по-настоящему независимыми они не станут. Поэтому переход обычно идёт от «общей БД» к «у каждого своя БД» постепенно.

**Стратегии (от самой связанной к самой чистой):**

- **Временная фаза shared DB** — и монолит, и новый сервис читают/пишут в одну БД. Быстрый старт, но связанность сохраняется, и схему приходится развивать осторожно, чтобы не сломать обе стороны.
- **Изоляция через database views / API** — новый сервис читает данные монолита не напрямую из таблиц, а через view (или API). Это прячет реальную схему и упрощает последующее разделение.
- **Дублирование данных с синхронизацией** — у нового сервиса своя БД, а записи монолита реплицируются в неё через CDC или события. Результат — eventually consistent.
- **Полная миграция владения** — новый сервис становится authoritative-источником данных, а монолит читает их через API или event stream. Больше всего работы, но конечное состояние самое чистое.

**Паттерн expand-contract** (как безопасно эволюционировать схему):
- **Expand** — добавить новые колонки/таблицы для нового сервиса; читают пока оба
- **Move writes** — новый сервис начинает писать, монолит подхватывает изменения через события
- **Migrate reads** — монолит перестаёт читать по старому пути и читает из нового
- **Contract** — удалить старые колонки/таблицы, ставшие ненужными

**Инструменты:** Debezium (CDC), Kafka Connect, кастомный ETL.

## Q7. Dual-write и проблема согласованности данных

**Dual-write — это запись в оба хранилища (старое и новое) во время миграции.** Звучит просто, но это известный антипаттерн: атомарной транзакции через две независимые БД нет, поэтому почти всегда лучше выбрать один из паттернов ниже, а не писать в обе руками.

**Почему наивный dual-write опасен:**
- **Порядок** — запись в A прошла, а в B упала → данные разъехались
- **Задержка** — теперь на каждый запрос две записи вместо одной
- **Сложность retry** — если одна сторона упала, непонятно, где и как повторять, чтобы не задвоить

**Паттерны (как сделать правильно):**

- **Запись в старое, CDC в новое** — старая БД остаётся source of truth, изменения стримятся в новое через Debezium. Eventually consistent.
- **Запись в новое, репликация в старое** — новая БД становится authoritative, монолит читает новое через API или реплику; когда монолиту данные больше не нужны — репликацию останавливают.
- **Transactional outbox** — запись в основную БД и в таблицу outbox идут в *одной* транзакции, отдельный publisher читает outbox и публикует события, которые забирает другая сторона. Это и убирает проблему «записал в A, упал на B».
- **Saga / 2PC** — распределённая транзакция, дорого и хрупко; применять редко и осознанно.

**Сверка (reconciliation):** периодический аудит сравнивает записи в старом и новом хранилище — drift автоматически чинится там, где это безопасно, о значимых расхождениях идёт алерт.

**Какой уровень согласованности выбрать:**
- **Eventual** подходит для большинства случаев
- **Strong** нужна только там, где речь о деньгах или складских остатках — и там применяют аккуратные транзакционные паттерны

## Q8. (!) Что такое proxy / facade layer и какой выбрать?

**Proxy (router) стоит перед обеими системами и для каждого запроса решает, куда его направить** — в монолит или в новый сервис. Это «сердце» strangler: именно он позволяет переключать трафик по кускам, не трогая клиента. Выбор конкретного типа — компромисс между простотой и гибкостью маршрутизации.

**Типы (от простого к гибкому):**

- **Reverse proxy** (Nginx, Envoy, HAProxy) — маршрутизация по URL/path, всё управляется конфигом, низкая нагрузка на CPU. Хорош для простого разделения по путям.
- **API Gateway** (Kong, AWS API Gateway) — то же плюс auth, rate limiting, трансформации; логика навешивается плагинами на каждый маршрут.
- **Application-level** (Spring Gateway, кастомный) — маршрутизация прямо в коде. Нужен, когда логика сложная: по заголовкам, A/B-сегментам и т.п.
- **Service mesh** (Istio, Linkerd) — sidecar-прокси рядом с каждым сервисом; лучший вариант для трафика microservice-to-microservice внутри кластера.

**Пример конфигурации (Envoy):**
```yaml
routes:
  - match: { prefix: "/api/v2/users" }
    route: { cluster: new_user_service }
  - match: { prefix: "/" }
    route: { cluster: old_monolith }
```

**Подводные камни:**
- **Session affinity** — если у монолита есть серверные сессии, запросы пользователя должны липнуть к нужной системе
- **Совместимость auth-токенов** — обе системы должны понимать один и тот же токен
- **Сквозная трассировка** — один пользователь ходит в разные системы, и trace нужно пробросить через прокси, иначе картина запроса распадётся

## Q9. Где разместить proxy в инфраструктуре?

Чем ближе прокси к пользователю, тем раньше можно отсечь или перенаправить запрос, но тем меньше доступно сложной логики; чем ближе к сервисам — тем гибче маршрутизация. Отсюда несколько уровней, на каждом из которых может жить strangler-маршрутизация.

**Варианты (от края к ядру):**

- **Edge proxy** (Cloudflare, AWS CloudFront) — ближе всего к пользователю, ранний reject и маршрутизация, но логика ограничена.
- **API Gateway** (AWS API Gateway, Kong) — централизованные политики, конфиг на каждый маршрут. Типичное место для strangler-маршрутизации.
- **Load balancer** (NGINX, HAProxy) — простая и быстрая маршрутизация по путям, минимум возможностей.
- **Application** (кастомный Node.js / Spring) — максимальная гибкость, маршрутизация по бизнес-логике.
- **Service mesh** (Istio) — внутренний трафик внутри кластера; постепенное смещение трафика через VirtualService.

**Типичная схема:** API Gateway для публичного трафика и service mesh для внутреннего.

## Q10. Зачем feature flags для маршрутизации?

**Feature flag позволяет решать, в монолит или в новый сервис идёт запрос, в рантайме — без передеплоя.** Главная ценность для strangler в том, что флаг даёт мгновенный rollback и тонкую раскатку (по пользователю, региону, проценту), чего конфиг-перезагрузка прокси не всегда даёт так быстро.

```javascript
if (featureFlag('new-user-service', user)) {
  return callNewService(req);
} else {
  return callMonolith(req);
}
```

**Что это даёт:**
- Мгновенный rollback — достаточно переключить флаг
- Раскатка по пользователю / по региону
- A/B-тестирование старой и новой реализации
- Kill switch на случай инцидента

**Инструменты:** LaunchDarkly, Split, Unleash, Statsig; Flagsmith (OSS).

**Стратегия раскатки:**
1. Флаг OFF — 0% трафика на новый сервис
2. Canary — 1% избранных пользователей
3. Раскатка — 10% → 50% → 100%
4. На каждом шаге мониторить ошибки, latency и бизнес-метрики
5. Любая регрессия → мгновенно переключить флаг OFF

**Гигиена флагов:**
- Config UI — переключать могут и неинженеры
- Audit log — видно, кто и что менял
- Плановое удаление — флаг временный; по политике очистки его убирают, чтобы не накапливать «мусорные» ветвления в коде

## Q11. (!) Преимущества Strangler Fig?

Почти все плюсы вытекают из одного свойства — **миграция идёт мелкими обратимыми шагами**, а не одним прыжком. Отсюда и низкий риск, и непрерывная ценность, и возможность учиться по дороге.

- **Инкрементальный прогресс** — ценность поставляется непрерывно, бизнес видит конкретные победы и продолжает поддерживать проект.
- **Низкий риск на каждом шаге** — небольшие куски легко валидировать, а проблемы локализованы одним срезом.
- **Лёгкий rollback** — достаточно перенаправить трафик обратно; нет «точки невозврата».
- **Обучение команды** — экспертиза в микросервисах нарастает постепенно, а ранние ошибки обходятся дёшево.
- **Параллельная разработка** — новая команда строит сервисы, пока старая поддерживает монолит; merge-конфликтов меньше.
- **Непрерывность бизнеса** — монолит продолжает обслуживать запросы, переключение идёт без downtime, выручка не прерывается.
- **Погашение технического долга** — замещённый код удаляется по мере миграции, и со временем кодовая база становится чище.

## Q12. (!) Недостатки и риски Strangler Fig?

Обратная сторона безопасности — **долгий период, когда система живёт в «двойном» состоянии**: одновременно работают и старое, и новое. Большинство рисков — про сложность и стоимость этого переходного периода.

- **Долгие сроки** — обычно годы, а не месяцы; нужна устойчивая приверженность со стороны бизнеса.
- **Двойная поддержка** — старое и новое работают одновременно, и багфиксы нередко приходится делать в двух местах.
- **Сложность интеграции** — сервисы зовут монолит, монолит зовёт сервисы; интерфейсы нужно проектировать аккуратно.
- **Согласованность данных** — dual-write и CDC сложны, а баги здесь напрямую ведут к порче данных.
- **Узкое место в proxy** — весь трафик идёт через прокси, и если он не в HA-конфигурации, это single point of failure.
- **Клубки зависимостей** — срез B нельзя вынести, пока не мигрирован A; порядок декомпозиции важен.
- **Сопротивление feature freeze** — добавлять фичи в монолит не поощряется, что создаёт напряжение в команде, а бизнес может противиться заморозке.
- **Риск «никогда не закончить»** — последние 20% застревают, потому что остаток монолита — это ядро домена, самое связанное и сложное.
- **Смена культуры** — команде нужно перенять микросервисный mindset, и операционная сложность системы растёт.

## Q13. (!) Как откатиться (rollback), если новый сервис не работает?

Главное преимущество strangler здесь — **откат идёт по одному срезу, а не по всему проекту**: достаточно вернуть проблемный кусок трафика на монолит, остальное продолжает работать. Сложность не в маршрутизации, а в данных — их нужно уметь вернуть в согласованное состояние.

**Откат трафика (быстрый):**
- **Изменение конфига proxy** — переключить маршрутизацию обратно на монолит; деплой за секунды-минуты.
- **Feature flag** — переключить OFF; мгновенно и без деплоя.

**Откат данных (сложный):**
- Если новый сервис уже писал данные, их нужно реплицировать обратно в монолит — либо включить dual-read (монолит читает свои данные плюс новые).
- Если переключение было полным, откат превращается в обратную миграцию данных.
- Dual-write обратим легко, пока обе БД держатся в синхроне.

**Подводные камни:**
- Как только монолит перестал писать, его данные начинают устаревать — это нужно планировать заранее.
- Не сжигай мосты слишком рано.

**Рекомендация:**
- Держи код монолита рабочим ещё несколько недель после переключения (cutover).
- Удаляй старый путь только после того, как появится уверенность.

**Аварийный план должен быть:**
- Расписан по шагам
- Протестирован вхолостую (chaos game days)
- Отработан дежурными (on-call)

## Q14. Как тестировать новый сервис параллельным прогоном (shadow)?

**Shadow mode — это когда запрос идёт и в старую, и в новую систему, ответы сравниваются, но пользователь видит только ответ монолита.** Идея в том, чтобы прогнать новый сервис на реальном боевом трафике и найти расхождения, ничем не рискуя для пользователя.

**Как это работает:**
1. Запрос приходит на proxy
2. Прокси шлёт его в монолит — это основной путь, он и возвращает ответ
3. Тот же запрос дублируется в новый сервис (shadow), его ответ только логируется
4. Ответы сравниваются, различия фиксируются
5. Реальный пользователь видит ответ монолита — безопасно

**Что это даёт:**
- Тестирование нового сервиса на реальном трафике, а не на синтетике
- Поиск расхождений без влияния на пользователей
- Уверенность перед cutover

**Инструменты:** Scientist (GitHub) — библиотека для Ruby/Python/Java; Diffy (Twitter, заархивирован); shadow-routing в Envoy; кастомный middleware.

**Подводные камни:**
- **Дублирование побочных эффектов** — операции записи в shadow выполнятся дважды!
- В shadow гонять **только чтения или идемпотентные записи**.
- Неидемпотентные операции — направлять на тестовый tenant или санитизировать.

**Что сравнивать в анализе различий:** тело ответа (diff), latency, error rate.

## Q15. Сколько времени занимает миграция?

Честный ответ — **долго, и разброс огромный**: от полугода для маленького приложения до многих лет для крупного. На собеседовании важно не назвать конкретное число, а показать, что время определяется масштабом и сложностью данных.

**Ориентиры по масштабу:**
- **Малый** (команда ~10 человек, простое приложение) — 6–12 месяцев
- **Средний** (50+ инженеров, средний монолит) — 1–2 года
- **Крупный** (Netflix, Amazon) — 5+ лет. Amazon потратил 5+ лет на переход монолит → microservices в начале 2000-х; Netflix — около 7 лет (завершил примерно к 2015).

**От чего зависит срок:** сложность домена, размер выделенной команды, сложность данных, регуляторные ограничения, срочность для бизнеса.

**Чего реалистично ждать:**
- 80% мигрируется за 1–2 года
- Последние 20% могут занять столько же, сколько первые 80% — это ядро домена
- «Готово на 90%» — частая ловушка: оставшиеся проценты держат проект годами

**Рекомендация:** начинай с самого чистого куска, на нём учись, документируй и шлифуй процесс, а уже отлаженный — применяй к остальному заметно быстрее.

## Q16. Когда считать миграцию завершённой?

Ключевая мысль: **«завершено» — это не обязательно «монолита больше нет».** Часто экономически разумнее остановиться на 95%, чем добивать последний дорогой и связанный остаток. Сначала смотрят на сигналы готовности, потом сознательно выбирают одну из стратегий финала.

**Сигналы, что миграция близка к концу:**
- Монолит обслуживает < 5% трафика
- Оставшаяся функциональность меняется редко
- Команда деплоит монолит нечасто
- Инфраструктура монолита почти ничего не стоит

**Три стратегии финала:**

- **Задушить остаток** — продолжить миграцию и полностью вывести монолит из эксплуатации.
- **Заморозить монолит** — оставить его работать для редких краевых случаев, прекратить активную разработку, со временем погасить (решение за бизнесом).
- **Вынести остаток в «legacy service»** — обернуть монолит сервисом, но дальше не декомпозировать. Прагматично для low-traffic admin-инструментов, ради которых не стоит затевать полную декомпозицию.

**При выводе из эксплуатации:** финальные планы по архивации данных, коммуникация с клиентами (если меняются интерфейсы), отключение и удаление инфраструктуры.

**После миграции:** зафиксировать извлечённые уроки, честно оценить декомпозицию (были ли микросервисы правильным выбором?) и не скатиться в чрезмерное дробление — иначе вместо монолита получится распределённый монолит.

## Q17. Что такое anti-corruption layer (ACL)?

**Anti-corruption layer (ACL, термин из DDD) — слой-переводчик между новым сервисом и legacy, который не даёт «кривой» модели старой системы протечь в чистую модель новой.** Без него странные формы данных и несогласованности legacy впитываются в новый код, и весь смысл миграции теряется.

**Где стоит ACL:**
```
New Service ←→ ACL (translator) ←→ Legacy API / DB
```

Что делает ACL:
- Маппит типы legacy в типы нового домена
- Скрывает именование и схемы legacy за чистым интерфейсом
- Даёт единую точку, которую правишь, когда legacy меняется

**Пример трансляции:**
- Legacy: `CUST_RECORD` с полями `CUST_NM`, `CUST_BRTH_DT_YR`
- New: `Customer` с `name`, `birthYear`
- ACL переводит одно в другое, и новый сервис никогда не видит legacy-нейминг

**Что это даёт:**
- Новый сервис остаётся чистым
- Дальнейшая миграция legacy не ломает его внутренности
- Зависимость от старой модели развязана

**Когда не нужен:** ACL — это лишний слой, поэтому вводить его стоит только там, где legacy-модель действительно уродлива; для аккуратного legacy он избыточен.

## Q18. Что такое branch by abstraction?

**Branch by abstraction — это «strangler внутри кода»:** вместо HTTP-прокси снаружи ты вводишь абстракцию (интерфейс) внутри монолита, держишь под ней старую и новую реализации одновременно и переключаешься между ними feature flag'ом. Когда новая реализация доказала себя — старую удаляешь.

**Как идёт переключение:**
- Внутри кода ввести абстракцию (интерфейс)
- Под ней живут обе реализации — старая и новая
- Feature flag выбирает, какую использовать
- После переключения старую реализацию удаляют

**Чем отличается от Strangler:**
- **Strangler** — внешнее разделение: маршруты HTTP-прокси перед системами
- **Branch by abstraction** — внутреннее разделение: ветвление прямо в коде

**Когда применять:**
- Снаружи декомпозировать нельзя из-за тесной связанности
- Хочется сначала отрефакторить внутренности монолита, а уже потом выносить кусок наружу

**Пример:**
```java
interface PaymentProvider {
    void charge(...);
}

class LegacyPaymentProvider implements ... { ... }  // old code
class StripePaymentProvider implements ... { ... }  // new

@Autowired PaymentProvider provider;  // flag-selected
```

**Переход:**
1. Ввести интерфейс (без изменения поведения)
2. Реализовать новое
3. Переключить флаг
4. Удалить старую реализацию

**Часто это предусловие для strangler** — сначала отрефакторить внутренности, затем выносить.
