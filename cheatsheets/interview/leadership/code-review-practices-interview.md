## Шаблон leadership-ответа

Для вопросов уровня lead лучше отвечать через операционную рамку:

1. **Процесс:** правила и SLA команды.
2. **Люди:** как обучаете и распределяете нагрузку.
3. **Измерение:** по каким метрикам видно, что практика работает.

## Q1. Какие практики делают code review эффективным?

Практики: малый объём `PR` (200–400 строк диффа); чёткое описание (что и зачем сделано); автоматизация стиля и тестов в `CI`; `SLA` на первое реагирование (например, 4 часа); фокус ревьюера на логике, тестах, безопасности; конструктивная обратная связь (тон, формулировки). Эффективность — меньше дефектов в проде при приемлемом времени ревью.

**Измеримые результаты:** cycle time (время от открытия `PR` до merge) и доля `PR` с регрессиями после merge — ключевые метрики. Чек-лист по приоритетам (корректность → тесты → безопасность → архитектура → читаемость) уменьшает пропуски; стиль делегируют линтерам. Ретро по «пропущенным багам» помогает скорректировать чек-лист и объём `PR`.

**Практика:** зафиксировать в `README` или `Confluence`: максимальный размер `PR / SLA` «первый ответ за 4 часа», чек-лист для ревьюера. В branch protection — обязательный 1 approve и зелёный `CI` перед merge.

## Q2. Какой чек-лист использовать при ревью?

Чек-лист по приоритетам: (1) Корректность — логика, граничные случаи, `NPE`, ошибки. (2) Тесты — покрытие изменений, качество тестов. (3) Безопасность — инъекции, утечка данных, небезопасные `API`. (4) Архитектура — границы модулей, зависимости. (5) Читаемость — имена, сложность. Стиль делегировать линтерам. Чек-лист можно хранить в wiki или в шаблоне `PR`; команда согласовывает пункты.

**Практика:** в шаблоне `PR` (`GitHub`, `GitLab`) указать чек-лист по OWASP или внутренним правилам.

## Q3. Как организовать процесс ревью в команде?

Соглашения: кто утверждает (один/два ревьюера); критерии approve (зелёный `CI`, нет критичных замечаний); `SLA` на ревью; объём `PR`; обязательность тестов. Процесс зафиксировать в документации (`Confluence`, `README`). Защита веток в `GitHub / GitLab`: merge только после approve и зелёного `CI`. На ретро обсуждать узкие места (очередь ревью, задержки) и улучшать процесс.

**Практика:** в branch protection rules задать: 1 required approval, статус `CI` должен быть success. В `README` или `Confluence` описать: «Ревьюер — любой из команды по ротации; первый ответ в течение 4 часов; объём `PR` до `400` строк». На планировании напоминать про `SLA`; на ретро смотреть метрики cycle time и перегруженных ревьюеров.

## Q4. Роль автоматизации в практиках ревью?

Автоматизация снимает с ревьюера рутину: стиль — `Checkstyle`, `Spotless`, `EditorConfig`; тесты — JUnit, сборка в `CI`; безопасность — `SAST`, проверка зависимостей (`Dependabot`, `Snyk`); качество кода — `SonarQube`, `SpotBugs`. Ревьюер смотрит то, что машина не проверяет: логику, дизайн, контекст. Красный `CI` блокирует merge; ревью не тратится на то, что уже падает в пайплайне.

**Практика:** в `pipeline` этапы: lint (`Checkstyle / Spotless`), `unit` tests, `SonarQube` (quality gate), dependency check. `Merge` только при зелёном `CI`. Ревьюер не комментирует форматирование — только логику, тесты, безопасность и архитектуру. При новом правиле в линтере — добавить в `CI` и убрать из ручного чек-листа ревью.

## Q5. Как практиковать асинхронное ревью?

Асинхронное ревью — норма для распределённых команд. Практики: ясное описание `PR` и контекст; ревьюер смотрит в своё время и оставляет комментарии; автор отвечает в течение рабочего дня; при срочности — явно помечать и синхронизироваться по времени (созвон). Соглашения по времени первого ответа (например, 4 часа) и по количеству итераций уменьшают неопределённость.

**Практика:** в описании `PR` указывать контекст и ссылку на тикет; ревьюер выделяет блоки (например, утро и после обеда) на ревью. При срочном `PR` — пометить в заголовке [`URGENT`] и написать в чат команды; ревьюер приоритизирует. Ответы на комментарии — в тот же день; при несогласии короткий созвон вместо длинной переписки. Метрика «time to first review» — следить за `SLA`.

## Q6. Какие инструменты использовать для ревью (`GitHub`, `GitLab`, `Gerrit`)?

`GitHub / GitLab`: встроенный `UI` для `PR / MR`, комментарии по строкам, approve, защита веток, интеграция с `CI`. Удобно для большинства команд. `Gerrit`: патч-сеты, строгий workflow (submit только после +2), удобен для больших open source и строгого compliance. Выбор по экосистеме (уже используете `GitHub / GitLab`) и по требованиям (compliance, трассируемость). Инструмент должен поддерживать approve, комментарии и блокировку merge до критериев.

**Практика:** в `GitHub / GitLab` включить branch protection: `require 1` approval, require status checks (`CI`), no force push. Шаблон `PR / Gerrit` даёт детальную историю голосов и комментариев; для обычной команды достаточно `GitHub / GitLab` с настроенной защитой веток и `CI`.

## Q7. Как ввести ревью в команду, где его не было?

Начать с пилота: один ревьюер, малые `PR`, фокус на пользе (меньше багов, обмен знаниями). Зафиксировать правила (кто ревьюит, критерии approve) и обсудить на ретро. Не требовать идеального ревью с первого дня; наращивать ожидания по мере привыкания. Показать примеры хороших комментариев и быстрых циклов. Тимлид и старшие — первые ревьюеры и образец тона.

**Практика:** пилот на 2–4 недели: обязательный 1 approve для ветки main, макс. размер `PR 300` строк. В `README` добавить раздел «`Code` review» с правилами и примером хорошего описания `PR / SLA` (первый ответ за 4 часа) и чек-лист; при сопротивлении — объяснить выгоды (меньше багов в проде, обмен контекстом) и начать с тимлида как ревьюера.

## Q8. Практики ревью для распределённой команды?

Асинхронное ревью; ясное описание `PR` (контекст, ссылки на тикеты); `SLA` на ответ; при сложных спорах — короткий созвон вместо длинной переписки. Ротация ревьюеров по часовым поясам для быстрого первого ответа. Документация по стандартам кода и архитектуре уменьшает необходимость «угадывать» ожидания. Видео-разбор сложных `PR` по запросу ускоряет обратную связь.

**Практика:** в шаблоне `PR` обязательные поля: ссылка на тикет, что сделано, как тестировали. Ревьюеры по ротации (`round-robin`) или по владению модулем; при перекрытии часовых поясов хотя бы один ревьюер в доступности в течение 4 часов. Сложные `PR` (архитектура, спорные решения) — 15-минутный созвон после первого раунда комментариев вместо 10 сообщений в треде. `ADR` и архитектурные гайды в `Confluence` снижают вопросы «а почему так?».

## Q9. Как совмещать ревью с другими обязанностями?

Выделять блоки времени на ревью (например, утро и после обеда); не откладывать ревью «на потом» — очередь растёт. Малые `PR` ревьюить быстрее. Ротация ревьюеров и несколько людей, способных ревьюить, снимают узкое место «один эксперт». Метрики (время в очереди) помогают заметить перегрузку и перераспределить. Культура «ревью — часть работы» снижает конкуренцию с «своими задачами».

**Практика:** в календаре блоки «`Code` review» по 30–60 минут 2 раза в день; не сливать их с глубокой работой. При очереди > 5 `PR` на человека — тимлид перераспределяет или временно подключает второго ревьюера. На ретро смотреть метрику «`PR` в ожидании ревью > 24 ч» и обсуждать причины; при хронической перегрузке — уменьшить размер `PR` или увеличить число ревьюеров в ротации.

## Q10. Ревью по слоям (архитектор, тимлид, разработчик)?

Для критичных изменений (архитектура, безопасность, публичный `API`) можно ввести многоуровневое ревью: сначала разработчик (логика, тесты), затем архитектор или тимлид (дизайн, границы). Не обязательно для каждого `PR`; только для областей по соглашению. Избегать избыточных слоев: два ревьюера часто достаточно; третий — только при явной необходимости (например, security).

При обсуждении архитектуры важно дополнить ответ явными trade-offs: что выигрываем, чем платим и как контролируем риски в production. Хорошей практикой считается привязка решения к измеримым SLO/SLI и плану эволюции при росте нагрузки.

## Q11. Практики ревью безопасности (security review)?

Для областей с повышенными рисками (аутентификация, платежи, персональные данные): чек-лист по `OWASP` или внутренним правилам; при необходимости привлечение security-специалиста; автоматизация (`SAST`, проверка зависимостей). Ревьюер проверяет: инъекции, утечка секретов, небезопасная десериализация, недостаточная валидация. Результат ревью и критерии зафиксировать в процессе; при критичных находках — блокировать merge до исправления.

Для production-систем дополнительно стоит описать модель угроз, контроль доступа по принципу least privilege и процесс реагирования на инциденты. На собеседовании обычно ожидают, что вы свяжете техническую меру с риском для бизнеса и с проверяемыми контрольными точками в CI/CD.

## Q12. Как ревьюить конфигурацию и инфраструктуру?

Конфигурация (`YAML`, properties, `Terraform`) и инфраструктура тоже проходят ревью: актуальность, отсутствие секретов в репозитории, влияние на окружения. Линтеры для конфигов (`YAML`, `Terraform`) и проверка секретов в `CI` дополняют ручную проверку. Изменения в продакшен-конфигурации особенно важны — проверять откат и влияние. Ревьюер не обязательно инфраструктурный эксперт; достаточно базовой проверки и эскалации при сомнениях.


## Q13. Ревью документации и `API`-контрактов?

Документация (`README`, `API` docs, runbooks) и контракты (`OpenAPI`, `gRPC`) ревьюятся на актуальность, ясность и соответствие коду. Изменения контрактов — на обратную совместимость и версионирование. Контрактное тестирование (`Pact`, `Spring Cloud Contract`) автоматизирует часть проверок. В `PR` с изменением `API` обязательно обновление документации; ревьюер проверяет полноту и корректность описаний.


## Q14. Как измерять эффективность практик ревью?

Метрики: время от открытия `PR` до merge (cycle time); количество итераций (раундов замечаний); доля `PR` с регрессиями после merge; покрытие ревью (доля `PR` с хотя бы одним ревью). Цель — не «больше замечаний», а меньше дефектов в проде и приемлемое время ревью. Метрики обсуждать на ретро и использовать для улучшения процесса (например, уменьшение размера `PR`, ускорение первого ответа).


## Q15. Практики ревью для срочных hotfix?

Соглашение: hotfix до N строк может идти с упрощённым ревью (один быстрый взгляд) или постфактум ревью в течение 24 часов. Критичные области (безопасность, деньги) — минимум один быстрый approve до merge. Документировать исключения и не злоупотреблять; после инцидента провести постмортем и при необходимости ужесточить правила для hotfix.


## Q16. Как избежать «ревью ради галочки»?

Критерии approve должны быть содержательными: не «посмотрел», а «проверил логику, тесты, безопасность в рамках чек-листа». Автоматизация снимает рутину; ревьюер тратит время на то, что важно. Культура: ревью — часть качества продукта, а не формальность. На ретро обсуждать примеры пропущенных багов и улучшать чек-лист и процесс. Тимлид не давить на «быстрее approve», а на «проверять по делу».


## Q17. Ротация ревьюеров и нагрузка?

Ротация: не закреплять ревью за одним человеком; распределять по команде (`round-robin` или по владению модулем). Нагрузка: следить за очередью ревью; при перегрузке перераспределять или временно добавлять ревьюеров. Несколько людей, способных ревьюить каждый модуль, снимают узкое место. Метрики «кто сколько ревьюит» помогают балансировать; избегать перегрузки отдельных людей.


## Q18. Практики ревью для джуниоров (как ревьюить, как получать ревью)?

Получать ревью: малые `PR`, ясное описание; не воспринимать замечания как личную критику; задавать вопросы, если комментарий непонятен. Ревьюить: джуниор может ревьюить код коллег с фокусом на читаемости и простых проверках; сложную логику и архитектуру проверяет сеньор. Парное ревью (джуниор + сеньор) — способ обучения. Обратная связь по качеству ревью (как ревьюеру) помогает развиваться.


## Q19. `Pair` programming vs code review?

`Pair` programming — два человека пишут код вместе; обсуждение в реальном времени, меньше замечаний постфактум. `Code` review — асинхронная проверка после написания кода. Оба улучшают качество; выбор по контексту. Парное программирование подходит для сложных задач и онбординга; ревью — для распределённых команд и гибкости времени. Можно комбинировать: парная работа над ядром, ревью остального.


## Q20. Как практиковать ревью без блокировки разработки?

Малые `PR` (быстрее ревьюить); несколько ревьюеров (нет узкого места); `SLA` на первое реагирование; автор может переключаться на другую задачу, пока ждёт ревью. Автоматизация (`CI`) не блокирует ревьюера на рутине. При блокировке — эскалировать: «ждём ревью 2 дня, нужен второй ревьюер или приоритет». Культура «ревью в приоритете» уменьшает время ожидания.
