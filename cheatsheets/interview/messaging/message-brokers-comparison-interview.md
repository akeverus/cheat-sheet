## Q1. (!) Чем отличаются Pub/Sub, Queue и Stream?

Это три базовые модели доставки сообщений, и различаются они по двум вопросам: **сколько потребителей получают сообщение** и **что происходит с сообщением после прочтения**. Понимание этих различий — фундамент выбора брокера: каждый продукт изначально заточен под одну из моделей.

**Queue (очередь, точка-точка):**
- Один producer → один consumer (или один из группы)
- Сообщение **удаляется** после обработки
- Обычно FIFO
- **Примеры:** очереди RabbitMQ, SQS, ActiveMQ

**Pub/Sub (публикация-подписка):**
- Один producer → **несколько подписчиков** (broadcast)
- Каждый подписчик получает **свою копию** сообщения
- **Примеры:** topic exchanges в RabbitMQ, SNS, NATS Core

**Stream (поток, лог):**
- Append-only лог: сообщения дописываются в конец и читаются по позиции (offset)
- **Несколько consumer-ов** читают **независимо**, каждый со своим offset — продвижение одного не влияет на других
- Сообщения **НЕ удаляются** после прочтения, а живут по политике хранения (retention)
- Поэтому поток **воспроизводим** (replay): любой consumer может вернуться назад и перечитать историю
- **Примеры:** Kafka, Pulsar, Kinesis, Redpanda

| Паттерн | Кто получает | Хранение |
|---------|-------------|-------------|
| Queue | Один (с балансировкой) | До обработки |
| Pub/Sub | Все подписчики | На подписчика или без хранения |
| Stream | Все consumer-ы (независимо) | По retention |

**Ключевое отличие Stream от двух остальных:** сообщение не «съедается» при чтении. Это и даёт replay, и позволяет подключить нового потребителя «задним числом» — он прочитает всю историю с начала лога.

## Q2. (!) Чем message broker отличается от streaming-платформы?

Главное различие — в том, **что система делает с сообщением после доставки**. Message broker заточен на транспорт «доставил — забыл», streaming-платформа хранит сообщения как лог и позволяет перечитывать их. Из этой одной разницы вытекают все остальные свойства.

**Message broker** (RabbitMQ, ActiveMQ, NATS Core):
- Рассчитан на **обмен сообщениями без долгого хранения** — доставил подписчику и удалил
- Оптимизирован под **гибкость маршрутизации** (по теме, заголовку, паттерну)
- Обычно ниже throughput — платит за богатую семантику доставки
- Часто **at-most-once** или **at-least-once**

**Streaming-платформа** (Kafka, Pulsar, Redpanda):
- Рассчитана на **persistent-лог** — сообщения хранятся и читаются по offset
- Высокий throughput за счёт простой append-only модели и последовательной записи на диск
- **Возможность replay** — прямое следствие того, что лог не удаляется
- **At-least-once** по умолчанию, **exactly-once** достижима
- Интеграция со stream processing (Kafka Streams, Flink)

**Гибрид** (NATS + JetStream, RabbitMQ Streams) — добавляют persistent-лог поверх классического брокера, давая оба мира сразу: и гибкую маршрутизацию, и хранение с replay.

## Q3. (!) Каковы ключевые характеристики Apache Kafka?

Kafka — это распределённый append-only лог, фактический промышленный стандарт для event streaming. Его сила — в сочетании очень высокого throughput, надёжного хранения с replay и огромной экосистемы (Connect, Streams, Schema Registry). Плата за это — высокая сложность эксплуатации и латентность не из самых низких.

| Критерий | Apache Kafka |
|-----------|--------------|
| Тип | Streaming-платформа |
| Язык | Java (JVM) |
| Throughput | Очень высокий (миллионы msg/sec) |
| Latency | Средняя (10–100 мс) |
| Хранение | Всегда (на основе лога) |
| Упорядоченность | На партицию |
| Replay | Отличный |
| Multi-region | MirrorMaker (отдельный инструмент) |
| Экосистема | **Огромная** (Connect, Streams, registry) |
| Зрелость | Самая зрелая (с 2011) |
| Распространённость | **Промышленный стандарт** |
| Сложность эксплуатации | Высокая (ZK/KRaft, брокеры, Connect) |

**Лучше всего для:** event streaming, big data-конвейеров, агрегации логов, event sourcing.

Подробнее — в [Apache Kafka](kafka-interview.md).

## Q4. (!) Каковы ключевые характеристики RabbitMQ?

RabbitMQ — классический message broker с богатейшей маршрутизацией: exchanges и bindings позволяют гонять сообщения по теме, заголовку или паттерну. Берут его за гибкость доставки, низкую латентность и зрелость, а не за throughput — он средний. Replay исторически слабое место (появился позже через плагин Streams).

| Критерий | RabbitMQ |
|-----------|----------|
| Тип | Message broker |
| Язык | Erlang |
| Throughput | Средний (десятки тысяч msg/sec) |
| Latency | Низкая (мс) |
| Хранение | Опционально |
| Упорядоченность | На очередь |
| Replay | Ограниченный (плагин Streams, появился позднее) |
| Маршрутизация | **Отличная** (exchanges, bindings, topics) |
| Протоколы | AMQP, MQTT, STOMP |
| Зрелость | Очень зрелый (с 2007) |
| Распространённость | Широкая |
| Сложность эксплуатации | Средняя |

**Лучше всего для:** enterprise-обмена сообщениями, сложной маршрутизации, RPC, транзакционных нагрузок.

Подробнее — в [RabbitMQ](rabbitmq-interview.md).

## Q5. (!) Каковы ключевые характеристики NATS?

NATS — лёгкий брокер на Go, главный козырь которого — латентность в микросекундах и крайне низкое потребление ресурсов. Базовый NATS Core работает без хранения (at-most-once), а persistent-лог с replay добавляет опциональный модуль JetStream. Эксплуатация максимально простая (один бинарник), есть нативный multi-region через super-cluster и leaf nodes.

| Критерий | NATS |
|----------|------|
| Тип | Обмен сообщениями + streaming (JetStream) |
| Язык | Go |
| Throughput | Очень высокий (миллионы msg/sec) |
| Latency | **Микросекунды** (самая низкая) |
| Хранение | Опционально через JetStream |
| Упорядоченность | На subject |
| Multi-region | Нативный (super-cluster, leaf nodes) |
| Потребление ресурсов | **Очень низкое** |
| Настройка | **Очень простая** |
| Зрелость | Зрелый, растущий (с 2014) |
| Распространённость | Нишевый, но растущий |

**Лучше всего для:** микросервисов, IoT, edge computing, низколатентного обмена сообщениями.

Подробнее — в [NATS](nats-interview.md).

## Q6. (!) Каковы ключевые характеристики Apache Pulsar?

Pulsar — streaming-платформа уровня Kafka, но с двумя архитектурными отличиями: **хранилище и вычисления разделены** (брокеры обрабатывают, данные лежат в Apache BookKeeper), а multi-tenancy и geo-репликация встроены изначально. Это даёт раздельное масштабирование и удобство для multi-tenant SaaS. Цена — самая высокая операционная сложность (брокеры + bookies + ZooKeeper).

| Критерий | Apache Pulsar |
|----------|---------------|
| Тип | Streaming + обмен сообщениями |
| Язык | Java |
| Throughput | Очень высокий |
| Latency | Средняя |
| Архитектура | **Вычисления и хранилище разделены** (BookKeeper) |
| Multi-tenancy | **Встроенная** |
| Multi-region | **Нативная** geo-репликация |
| Типы подписок | 4 (Exclusive, Shared, Failover, Key_Shared) |
| Tiered storage | Встроенный |
| Распространённость | Нишевый |
| Сложность эксплуатации | Высокая |

**Лучше всего для:** multi-tenant SaaS, multi-region, cloud-native-архитектур.

Подробнее — в [Apache Pulsar](pulsar-interview.md).

## Q7. (!) Каковы ключевые характеристики Redpanda?

Redpanda — это переписанная на C++ замена Kafka, совместимая по Kafka API: существующие клиенты Kafka работают без изменений. Отсутствие JVM (нет пауз GC) и архитектура shard-per-core на фреймворке Seastar дают латентность ниже, чем у Kafka. Свой Raft вместо ZooKeeper и один бинарник делают эксплуатацию заметно проще.

| Критерий | Redpanda |
|----------|----------|
| Тип | Streaming (совместим с Kafka) |
| Язык | C++ |
| Throughput | Очень высокий |
| Latency | Ниже, чем у Kafka (нет GC) |
| Совместимость | **Kafka API** |
| ZooKeeper | Нет (собственный Raft) |
| Архитектура | Shard-per-core (Seastar) |
| Настройка | **Один бинарник** |
| Распространённость | Растёт |

**Лучше всего для:** пользователей Kafka, которым нужна более высокая производительность и проще эксплуатация.

Подробнее — в [Redpanda](redpanda-interview.md).

## Q8. Чем различаются AWS SQS, SNS и EventBridge?

Это три полностью управляемых messaging-сервиса AWS, и каждый закрывает свою из трёх базовых моделей из Q1 — очередь, pub/sub и шину с маршрутизацией:

- **SQS** — управляемая очередь (точка-точка): сообщение читает один consumer и удаляет.
- **SNS** — управляемый pub/sub: одно сообщение веером (fan-out) рассылается всем подписчикам.
- **EventBridge** — шина событий со сложной маршрутизацией по правилам (event patterns) и готовыми интеграциями с SaaS (Stripe, Auth0 и др.).

Классическая связка — **SNS → несколько SQS**: SNS делает fan-out, а каждая SQS-очередь обслуживает своего потребителя с независимыми повторами.

**Лучше всего для:** AWS-native-приложений, serverless, развязки микросервисов.

Подробнее — в [AWS SQS/SNS](aws-sqs-sns-interview.md).

## Q9. Что такое Apache ActiveMQ и где он применяется?

ActiveMQ — зрелый Java-брокер с акцентом на JMS, де-факто стандарт обмена сообщениями в старых Java-enterprise-системах. Сегодня это в основном legacy-выбор: throughput ниже современных брокеров, новые проекты уходят на Kafka и RabbitMQ.

| Критерий | Apache ActiveMQ |
|----------|-----------------|
| Тип | Message broker (JMS) |
| Язык | Java |
| Throughput | Ниже |
| Протоколы | JMS, AMQP, MQTT, STOMP |
| Зрелость | Очень зрелый (с 2004) |
| Распространённость | В основном legacy |

**Две разновидности:**
- **ActiveMQ Classic** — старая, менее популярная
- **Artemis** — новее, выше производительность

**Лучше всего для:** legacy Java enterprise-систем, где требуется совместимость с JMS.

В **2025** — на спаде, вытесняется Kafka и RabbitMQ.

## Q10. (!) Как брокеры сравниваются по throughput?

Короткий ответ: NATS Core и Redpanda — лидеры (миллионы сообщений в секунду), Kafka на следующей ступени, классические брокеры (RabbitMQ, ActiveMQ) — на порядок ниже. Но цифры ниже — ориентир, а не приговор: реальный throughput сильно зависит от размера сообщения, железа и настроек.

**Примерный throughput на узел** (один брокер):

```
NATS Core:        10M+ msg/sec (small messages)
Redpanda:         5M+ msg/sec
Kafka:            1-2M msg/sec
NATS JetStream:   500K msg/sec
Pulsar:           500K-1M msg/sec
RabbitMQ:         50K-100K msg/sec
ActiveMQ:         20K msg/sec
SQS:              No limit (managed scale)
```

**Оговорки:**
- Сильно **зависит от размера сообщения**
- **Важно железо** (NIC, диск, CPU)
- Настройки, replication factor

**Для большинства приложений** RabbitMQ / Kafka / NATS — избыточны по throughput. **Выбирай по фичам**, а не по сырому throughput.

## Q11. (!) Как брокеры сравниваются по latency?

По задержке доставки картина похожа на throughput: NATS — недосягаемый лидер (sub-миллисекунда), Redpanda быстрее Kafka за счёт отсутствия пауз GC, классические брокеры и SQS — медленнее. Важный нюанс: у Kafka latency регулируется батчингом и обменивается на throughput.

**Типичная p99 latency** (без батчинга):

```
NATS Core:        < 1 ms
NATS JetStream:   2-5 ms
Redpanda:         5-10 ms
RabbitMQ:         10-50 ms
Pulsar:           10-50 ms
Kafka:            10-100 ms
SQS:              50-200 ms
```

**Latency Kafka** зависит от настроек батчинга: `linger.ms` задаёт, сколько producer ждёт, набирая батч. Больше задержка — больше пропускная способность, и наоборот. То есть числа выше для Kafka можно сдвинуть, выбрав точку на этом компромиссе.

**Для низколатентных** требований (gaming, trading) предпочтительнее NATS / Redpanda.

## Q12. (!) Какие гарантии упорядоченности дают брокеры?

Ни один распределённый брокер не гарантирует глобальный порядок по всем сообщениям — это убило бы параллелизм. Вместо этого порядок держится в пределах **единицы параллелизма**: партиции у Kafka/Pulsar/Redpanda, очереди у RabbitMQ, message-group у SQS FIFO. NATS Core порядка не даёт вовсе (доставка параллельная).

| Система | Упорядоченность |
|--------|----------|
| Kafka | На партицию |
| RabbitMQ | На очередь (один потребитель) |
| NATS Core | Нет (параллельная доставка) |
| NATS JetStream | На stream |
| Pulsar | На партицию или через подписку Key_Shared |
| Redpanda | На партицию |
| SQS Standard | По возможности (возможна перестановка) |
| SQS FIFO | **Строгая в пределах message-group** |
| EventBridge | По возможности |

**Строгая упорядоченность** обычно требует **одного consumer-а на партицию/очередь** — иначе несколько обработчиков читают параллельно и порядок теряется.

**Для частичной упорядоченности** (по ключу) → используй **ключи партиционирования** (Kafka, Pulsar) или **message groups** (SQS FIFO): сообщения с одним ключом гарантированно попадают в одну партицию/группу и читаются по порядку, а разные ключи обрабатываются параллельно. Это типичный компромисс — порядок там, где он нужен (например, по `customer_id`), и масштабирование между ключами.

## Q13. (!) Какие гарантии доставки (at-least-once, exactly-once) дают брокеры?

Есть три уровня: **at-most-once** (может потеряться, но не дублируется), **at-least-once** (не потеряется, но возможны дубли) и **exactly-once** (ровно один раз). Большинство streaming-платформ по умолчанию дают at-least-once и опционально — exactly-once; классический NATS Core — at-most-once; SQS FIFO — единственный из списка с exactly-once «из коробки».

| Система | По умолчанию | Возможно |
|--------|---------|----------|
| Kafka | At-least-once | Exactly-once (транзакционно) |
| RabbitMQ | At-most-once | At-least-once (с acks) |
| NATS Core | **At-most-once** | — |
| NATS JetStream | At-least-once | Exactly-once |
| Pulsar | At-least-once | Exactly-once |
| Redpanda | At-least-once | Exactly-once |
| SQS Standard | At-least-once | — |
| SQS FIFO | **Exactly-once** | — |

**Exactly-once** в распределённых системах — сложно: повторы и сбои почти всегда порождают дубли. Обычно его собирают из трёх частей:
- Идемпотентные producer-ы — повторная отправка не создаёт дубль в логе
- Транзакционные записи — запись в несколько партиций атомарна (всё или ничего)
- Идемпотентные consumer-ы — повторная обработка одного сообщения не меняет результат

**Эмпирическое правило:** на практике вместо честного exactly-once берут **at-least-once + идемпотентные consumer-ы** — это проще, дешевле и даёт тот же эффект «ровно один раз» с точки зрения результата.

## Q14. Как брокеры хранят сообщения (persistence)?

Persistence определяет, переживут ли сообщения рестарт брокера. Streaming-платформы (Kafka, Pulsar, Redpanda) хранят всегда — это часть их природы как лога. У классических брокеров и NATS хранение опционально: NATS Core вообще без него (всё в памяти), JetStream добавляет durable-хранилище.

| Система | Хранение |
|--------|-------------|
| Kafka | Всегда (на основе лога) |
| RabbitMQ | Опционально (durable-очереди + persistent-сообщения) |
| NATS Core | Нет (без хранения) |
| NATS JetStream | Да |
| Pulsar | Всегда (BookKeeper) |
| Redpanda | Всегда |
| SQS | Да (управляемое) |
| ActiveMQ | Опционально |

**Компромисс:**
- **Хранимое (persistent)** — переживает рестарт брокера, но дороже по latency (запись на диск).
- **Нехранимое (non-persistent)** — быстрее (всё в памяти), но теряется при рестарте.

## Q15. Кто умеет replay (перечитывать исторические сообщения)?

Replay напрямую следует из persistence (Q14): если сообщения не удаляются при чтении, их можно перечитать. Поэтому отличный replay у лог-платформ (Kafka, Pulsar, Redpanda) — любой consumer возвращается на любой offset. У RabbitMQ replay ограничен (только через плагин Streams), а у SQS его нет вовсе: сообщение удаляется после обработки.

| Система | Replay |
|--------|--------|
| Kafka | **Отличный** (любой consumer, любой offset) |
| Pulsar | **Отличный** |
| Redpanda | **Отличный** |
| NATS JetStream | Да (ограничен по времени/размеру) |
| RabbitMQ | Ограниченный (плагин Streams) |
| SQS | **Нет** (удаляется после обработки) |
| EventBridge | Поддерживаются архив и replay |

**Replay** — ключевая фича для:
- Восстановления после бага
- Подключения новых consumer-ов
- A/B-тестирования на исторических данных
- Event sourcing

**Если replay критичен** → streaming-платформа (Kafka, Pulsar).

## Q16. Насколько сложна эксплуатация (operational complexity)?

Закономерность простая: чем больше движущихся частей, тем сложнее эксплуатация. NATS и Redpanda — один бинарник без внешних зависимостей; на другом полюсе Pulsar с тремя слоями (брокеры + bookies + ZooKeeper). Управляемые сервисы убирают эту сложность целиком, перекладывая её на провайдера.

**От самого простого к самому сложному:**

1. **NATS** — один бинарник, без зависимостей
2. **Redpanda** — один бинарник, без ZK
3. **AWS SQS/SNS/EventBridge** — полностью управляемые
4. **RabbitMQ** — умеренно (кластеры, плагины)
5. **Kafka** — высокая (брокеры, ZK/KRaft, Connect, Schema Registry)
6. **Pulsar** — самая высокая (брокеры + bookies + ZK)

**Управляемые сервисы** убирают сложность:
- **Confluent Cloud** (управляемая Kafka)
- **MSK** (управляемая Kafka от AWS)
- **CloudAMQP** (управляемый RabbitMQ)
- **Synadia** (управляемый NATS)
- **StreamNative** (управляемый Pulsar)
- **Redpanda Cloud**

## Q17. Как брокеры работают в режиме multi-region?

Здесь важно, встроена ли geo-репликация или это отдельный навесной инструмент. У Pulsar и NATS multi-region нативный (geo-репликация и super-cluster соответственно), поэтому он надёжнее и проще. У Kafka репликация между регионами делается внешним MirrorMaker 2 — работает, но сложен в эксплуатации.

| Система | Multi-region |
|--------|--------------|
| Kafka | MirrorMaker 2 (отдельный инструмент) |
| Pulsar | **Нативная** geo-репликация |
| NATS | **Нативный** super-cluster |
| RabbitMQ | Плагины Federation, Shovel |
| Redpanda | Cluster linking (появился позднее) |
| SQS | Один регион (требуется настройка межрегиональной репликации) |

**Pulsar и NATS** — лучший встроенный multi-region.

**Kafka** — возможен, но MirrorMaker сложен в эксплуатации.

## Q18. (!) Когда выбрать Kafka?

Короткий ответ: Kafka — выбор по умолчанию для event streaming и больших данных, когда нужны высокий throughput, долгое хранение с replay и зрелая экосистема, а сложность эксплуатации — приемлемая цена.

**Выбирай Kafka когда:**
- **Event streaming** — основной сценарий
- **Big data-конвейеры** (интеграция со Spark, Flink)
- **Event sourcing** + replay
- **Уже вложились** в экосистему Kafka
- Нужна **огромная экосистема** (Kafka Connect, Streams, registry)
- Требуется **долгое хранение**
- Промышленный стандарт, легко нанимать специалистов

**Не выбирай когда:**
- Нужна очень низкая latency (< 5 мс) — NATS / Redpanda
- Только простая очередь — RabbitMQ
- AWS-native serverless — SQS/EventBridge
- Multi-tenancy — Pulsar
- Не хочешь сложности эксплуатации — управляемые альтернативы

## Q19. (!) Когда выбрать RabbitMQ?

Короткий ответ: RabbitMQ берут, когда главное — гибкая маршрутизация и enterprise-паттерны обмена сообщениями (RPC, рабочие очереди, DLQ, приоритеты), а умеренного throughput хватает.

**Выбирай RabbitMQ когда:**
- **Сложная маршрутизация** (по exchange, по topic, по header)
- **Enterprise-паттерны обмена сообщениями** (RPC, рабочие очереди)
- **Несколько протоколов** (AMQP, MQTT, STOMP)
- Приемлем **более низкий throughput** (< 100K msg/sec)
- Java enterprise (JMS-подобные паттерны)
- Нужен **зрелый, проверенный в бою** брокер
- Dead letter exchanges, очереди приоритетов, TTL

**Не выбирай когда:**
- Высоконагруженный streaming — Kafka
- Долгое хранение / replay — Kafka
- Внутренняя коммуникация микросервисов — NATS часто лучше

## Q20. (!) Когда выбрать NATS?

Короткий ответ: NATS — выбор для внутренней коммуникации микросервисов, IoT и edge, где критичны низкая латентность, простая эксплуатация и малое потребление ресурсов.

**Выбирай NATS когда:**
- **Внутренняя коммуникация микросервисов**
- Критична **низкая latency** (< 5 мс)
- **IoT** — миллионы устройств
- **Edge computing** — leaf nodes
- Нужен нативный **multi-region**
- Хочешь **простую эксплуатацию** (один бинарник)
- Среды с ограниченными ресурсами

**Не выбирай когда:**
- Нужна огромная экосистема (Kafka)
- Сложный stream processing (Kafka Streams, Flink)
- Долгосрочное хранение (у Kafka дешевле)

## Q21. (!) Когда выбрать Pulsar?

Короткий ответ: Pulsar выбирают, когда нужны его фишки — встроенные multi-tenancy и geo-репликация, раздельное масштабирование хранилища и вычислений, tiered storage в S3, и команда готова к высокой операционной сложности.

**Выбирай Pulsar когда:**
- **Multi-tenant SaaS**-платформа
- Нужен нативный **multi-region**
- **Хранилище и вычисления** масштабируются раздельно
- **Долгое хранение** с tiered storage (S3)
- Нужны **разные паттерны подписок**
- Современная cloud-native-архитектура

**Не выбирай когда:**
- Нужна максимальная простота (Kafka или NATS проще)
- Уже глубоко в экосистеме Kafka
- Небольшая команда не справится со сложностью

## Q22. (!) Когда выбрать SQS/EventBridge?

Короткий ответ: эти управляемые сервисы — естественный выбор для AWS-native и serverless-приложений, когда нужна оплата по факту использования и не хочется самому держать инфраструктуру брокера.

**Выбирай SQS/SNS/EventBridge когда:**
- **AWS-native**-приложение
- **Serverless**-стек (много Lambda)
- Не хочешь **эксплуатировать инфраструктуру**
- Предпочтительна модель **pay-per-use**
- Интеграция **между AWS-сервисами**
- **SaaS-интеграции** (EventBridge для Stripe, Auth0, ...)

**Не выбирай когда:**
- Multi-cloud / on-prem
- Очень высокий throughput на постоянной основе (стоимость накапливается)
- Нужен streaming с replay
- Сложные требования к упорядоченности за пределами ограничений SQS FIFO

## Q23. (!) Какой брокер выбрать для конвейера обработки заказов?

Здесь нужен брокер с упорядоченностью по клиенту, надёжной обработкой несколькими независимыми consumer-ами и replay для восстановления. Под эти три требования идеально ложится Kafka.

**Требования:**
- Заказ оформлен → несколько последующих действий (списать оплату, собрать заказ, уведомить)
- Надёжная обработка
- Replay для восстановления

**Лучший выбор:** **Kafka** + **Kafka Streams** (или **Pulsar**).

```
Order Service → Kafka (orders topic) → 
  ├─ Charge Service (consumer)
  ├─ Fulfillment Service (consumer)
  ├─ Notification Service (consumer)
  └─ Analytics (Kafka Streams aggregate)
```

**Почему Kafka:** упорядоченность на партицию (партиционируем по `customer_id`, чтобы события одного клиента шли строго по порядку), replay для восстановления после бага и несколько независимых consumer-ов на один topic — каждый сервис читает поток сам по себе.

**Альтернатива:** Pulsar (та же модель), AWS EventBridge (управляемый, AWS-native).

## Q24. Какой брокер выбрать для системы уведомлений?

Задача — разослать одно событие по нескольким каналам (email/SMS/push) с независимыми повторами на канал. Это классический fan-out, под который идеально ложится SNS → несколько SQS (или RabbitMQ с worker-очередями).

**Требования:**
- Отправка email/SMS/push пользователям
- Несколько каналов на уведомление
- Повторная отправка при сбое

**Лучший выбор:** **SNS** (AWS) или **RabbitMQ** + worker-очереди.

```
Trigger → SNS notification topic →
  ├─ SQS email queue → Email service
  ├─ SQS SMS queue → SMS service
  └─ SQS push queue → Push service
```

**Почему так:** SNS делает fan-out одного события во все каналы, а отдельная SQS-очередь на канал изолирует его обработку — у каждого worker-а своя DLQ (dead letter queue) и своя стратегия повторов. Сбой в SMS-канале не задерживает email и push.

## Q25. Какой брокер выбрать для clickstream-аналитики?

Здесь сходятся три требования: огромный поток событий (миллионы/сек), потребление одним потоком и в real-time, и батчем, и долгое хранение. Под этот набор — Kafka (или Kinesis на AWS): один topic читают независимо несколько пайплайнов, а лог хранит историю для аналитики.

**Требования:**
- События web/приложений (миллионы/сек)
- Обработка в реальном времени + пакетная (batch)
- Долгое хранение для аналитики

**Лучший выбор:** **Kafka** или **Kinesis**.

```
Web/App → Kafka clickstream topic →
  ├─ Real-time: Flink processing → dashboards
  ├─ Batch: Spark ETL → DWH (BigQuery, Snowflake)
  └─ Storage: tiered к S3 (cold)
```

**Почему Kafka:** один топик одновременно питает real-time-обработку (Flink), batch-ETL (Spark) и долгое хранение — каждый потребитель идёт по своему offset, не мешая другим. Tiered storage сбрасывает старые данные в S3, удешевляя хранение.

**Pulsar** — альтернатива для multi-region.

## Q26. Какой брокер выбрать для IoT с миллионами устройств?

Ключевые ограничения IoT — слабые устройства, обработка на границе сети (edge) и стандартный протокол. Поэтому здесь правят MQTT-брокеры (HiveMQ, EMQX, AWS IoT Core) и NATS с leaf nodes, а не Kafka — она для edge тяжеловесна.

**Требования:**
- Миллионы устройств шлют данные с датчиков
- Низкое потребление ресурсов на устройствах
- Обработка на границе сети (edge)

**Лучший выбор:** **MQTT-брокер** (HiveMQ, EMQX, AWS IoT Core) или **NATS** (с leaf nodes).

```
IoT devices → MQTT broker / NATS leaf → Central NATS / Kafka
                                          ↓
                                  Stream processing
```

**MQTT** — стандартный протокол для IoT: лёгкий, рассчитан на ненадёжную сеть и слабые устройства.
**NATS** — современная альтернатива, более гибкая, с нативными leaf nodes для edge.

**Kafka** не идеален для IoT — тяжеловесен для устройств и не имеет поддержки граничных узлов (edge), поэтому её обычно ставят уже в центре, за MQTT/NATS-слоем.
