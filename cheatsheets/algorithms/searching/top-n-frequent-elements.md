# Топ-N наиболее частых элементов (`Top N Frequent Elements`)

**Дата последнего обновления:** 2026-02-06

Поиск `n` самых часто встречающихся элементов в массиве — распространённая задача в анализе данных и алгоритмике. Рассматриваются три основных подхода: использование `HashMap` в сочетании с `PriorityQueue` для эффективного извлечения топ-элементов, применение `Stream API` для функционального стиля программирования, и использование `TreeMap` для случаев, когда требуется дополнительная сортировка. Каждый подход имеет свои преимущества и ограничения в зависимости от размера данных, требований к производительности и стиля кода. В этом документе рассматриваются принципы работы каждого подхода, их реализация на `Java` и `Kotlin`, анализ сложности и практические рекомендации по выбору подходящего решения.

## Описание алгоритма

В этом руководстве мы рассмотрим, как найти `n` наиболее часто встречающихся элементов в массиве на `Java` и `Kotlin`. Задача возникает в различных контекстах: от анализа логов и поиска наиболее частых ошибок до построения рекомендательных систем и анализа текстовых данных.

Основная идея всех подходов заключается в том, что сначала необходимо подсчитать частоту появления каждого элемента в массиве, а затем выбрать `n` элементов с наибольшей частотой. Различия между подходами заключаются в способе подсчёта частот и в методе выбора топ-элементов.

Мы можем использовать `HashMap` для подсчёта вхождений каждого элемента и `PriorityQueue` для определения приоритетов элементов на основе их количества. Этот подход обеспечивает хороший баланс между производительностью и простотой реализации, что делает его предпочтительным выбором для большинства практических случаев.

## Подход 1: HashMap + PriorityQueue

Этот подход позволяет эффективно находить `n` наиболее часто встречающихся элементов в массиве, используя комбинацию `HashMap` для подсчёта частот и `PriorityQueue` для извлечения элементов с наибольшей частотой:

```java
// Подсчёт частот в HashMap, приоритет по частоте в PriorityQueue, топ-n из кучи
public static List<Integer> findByHashMapAndPriorityQueue(Integer[] array, int n) {
    // Шаг 1: Подсчитываем частоту появления каждого элемента
    Map<Integer, Integer> countMap = new HashMap<>();
    
    // Проходим по массиву и увеличиваем счётчик для каждого элемента
    for (Integer i : array) {
        countMap.put(i, countMap.getOrDefault(i, 0) + 1);
    }
    
    // Шаг 2: Создаём приоритетную очередь (максимальная куча) по частоте
    // Компаратор сравнивает элементы по их частоте в убывающем порядке
    PriorityQueue<Integer> heap = new PriorityQueue<>((a, b) -> countMap.get(b) - countMap.get(a));
    // Добавляем все уникальные элементы в кучу
    heap.addAll(countMap.keySet());
    
    // Шаг 3: Извлекаем n элементов с наибольшей частотой
    List<Integer> result = new ArrayList<>();
    for (int i = 0; i < n && !heap.isEmpty(); i++) {
        result.add(heap.poll()); // poll() извлекает элемент с максимальной частотой
    }
    
    return result;
}
```

### Объяснение алгоритма (HashMap + PriorityQueue)

1. **Подсчет частоты:** Используем **HashMap** для подсчета вхождений каждого элемента
2. **Создание кучи:** Создаем **PriorityQueue** с компаратором, который сравнивает элементы по частоте (**убывание**)
3. **Извлечение топ-n:** Извлекаем n элементов с наибольшей частотой

### Тестирование

**Проверим наши методы:**

```java
Integer[] inputArray = {1, 2, 3, 2, 2, 1, 4, 5, 6, 1, 2, 3};
Integer[] outputArray = {2, 1, 3};

assertThat(findByHashMapAndPriorityQueue(inputArray, 3)).containsExactly(outputArray);
```

## Подход 2: Stream API

Мы также можем использовать `Stream API` для создания карты подсчёта вхождений каждого элемента, сортировки записей на карте по частоте в порядке убывания, а затем извлечения `n` наиболее часто встречающихся элементов. Этот подход отличается высокой читаемостью и идиоматичностью для функционального стиля программирования:

```java
// Функциональный подход с использованием Stream API
public static List<Integer> findByStream(Integer[] arr, int n) {
    return Arrays.stream(arr)
        // Группируем элементы и подсчитываем частоту каждого элемента
        .collect(Collectors.groupingBy(i -> i, Collectors.counting()))
        // Преобразуем Map в Stream записей
        .entrySet()
        .stream()
        // Сортируем записи по значению (частоте) в убывающем порядке
        .sorted(Collections.reverseOrder(Map.Entry.comparingByValue()))
        // Извлекаем ключи (сами элементы)
        .map(Map.Entry::getKey)
        // Ограничиваем результат n элементами
        .limit(n)
        // Собираем результат в список
        .collect(Collectors.toList());
}
```

### Объяснение алгоритма (Stream API)

Алгоритм использует декларативный стиль программирования через `Stream API`. На этапе группировки метод `groupingBy` группирует элементы и подсчитывает их частоту, создавая `Map<Integer, Long>`, где ключ — элемент, а значение — количество его вхождений. Это эквивалентно первому этапу предыдущего подхода, но выполняется в функциональном стиле.

На этапе сортировки мы преобразуем `Map` в `Stream` записей и сортируем их по значению (частоте) в убывающем порядке. Это позволяет нам получить элементы, отсортированные по частоте появления. Временная сложность сортировки составляет `O(n log n)`.

На этапе извлечения мы берём ключи (сами элементы) из отсортированных записей и ограничиваем результат `n` элементами с помощью `limit(n)`. Итоговая временная сложность алгоритма составляет `O(m + n log n)`, что аналогично предыдущему подходу, но код более читаемый и декларативный.

### Пример использования (Stream API)

Пример использования функционального подхода:

```java
// Пример поиска топ-3 наиболее частых элементов с использованием Stream API
Integer[] arr = {1, 2, 3, 2, 2, 1, 4, 5, 6, 1, 2, 3};
List<Integer> top3 = findByStream(arr, 3);
// Результат: [2, 1, 3] — элементы отсортированы по частоте появления
```

## Подход 3: TreeMap

В качестве альтернативы мы можем использовать `TreeMap` для хранения частот элементов. Однако важно понимать, что `TreeMap` сортирует элементы по ключам, а не по значениям, поэтому нам всё равно потребуется дополнительная сортировка по частоте (значениям):

```java
// Подход с использованием TreeMap (менее эффективен, но полезен для демонстрации)
public static List<Integer> findByTreeMap(Integer[] arr, int n) {
    // Создаём TreeMap с обратным порядком сортировки по ключам
    // Внимание: это сортирует по ключам, а не по частоте!
    Map<Integer, Integer> countMap = new TreeMap<>(Collections.reverseOrder());
    
    // Подсчитываем частоту каждого элемента
    for (int i : arr) {
        countMap.put(i, countMap.getOrDefault(i, 0) + 1);
    }
    
    // Преобразуем записи в список для сортировки по значениям (частоте)
    List<Map.Entry<Integer, Integer>> sortedEntries = new ArrayList<>(countMap.entrySet());
    // Сортируем по частоте в убывающем порядке
    sortedEntries.sort((e1, e2) -> e2.getValue().compareTo(e1.getValue()));
    
    // Извлекаем первые n элементов
    List<Integer> result = new ArrayList<>();
    for (int i = 0; i < n && i < sortedEntries.size(); i++) {
        result.add(sortedEntries.get(i).getKey());
    }
    
    return result;
}
```

### Объяснение алгоритма (TreeMap)

Алгоритм начинается с создания `TreeMap` с обратным порядком сортировки по ключам. Это означает, что ключи будут отсортированы в убывающем порядке, но это не то, что нам нужно — нам нужна сортировка по частоте (значениям), а не по самим элементам.

На этапе подсчёта мы проходим по массиву и увеличиваем счётчик для каждого элемента. `TreeMap` автоматически поддерживает отсортированный порядок ключей, но это не помогает нам в решении задачи, так как нам нужна сортировка по частоте.

На этапе сортировки мы преобразуем записи `Map` в список и сортируем их по значениям (частоте) в убывающем порядке. Это дополнительный шаг, который делает этот подход менее эффективным по сравнению с предыдущими. Затем мы извлекаем первые `n` элементов из отсортированного списка.

### Примечание

Важно понимать, что `TreeMap` в данном случае сортирует по ключам (самим элементам), а не по значениям (частоте). Поэтому нам всё равно нужна дополнительная сортировка по значениям, что делает этот подход менее эффективным. `TreeMap` полезен, когда требуется дополнительная сортировка по ключам, но для задачи поиска топ-элементов по частоте он не является оптимальным выбором.

## Сравнение подходов

| Характеристика | **HashMap** + **PriorityQueue** | **Stream API** | **TreeMap** |
|----------------|-------------------------|------------|---------|
| Временная сложность | `O(**n**log(**m**)`) | `O(**m**log(**m**)`) | `O(**m**log**(m**)`) |
| Пространственная сложность | `O(m)` | `O(m)` | `O(m)` |
| Читаемость | Средняя | Высокая | Средняя |
| Производительность | Высокая | Средняя | Средняя |
| Применение | Общий случай | Функциональный стиль | Когда нужна сортировка |

**где:**
- n - количество уникальных элементов
- m - размер входного массива

## Реализация на Kotlin

Реализация на `Kotlin` демонстрирует более лаконичный и идиоматичный синтаксис по сравнению с `Java`. Рассмотрим все три подхода:

### HashMap + PriorityQueue (Kotlin)

```kotlin
// Реализация с использованием HashMap и PriorityQueue на Kotlin
fun findByHashMapAndPriorityQueueK(array: Array<Int>, n: Int): List<Int> {
    // Используем встроенную функцию groupingBy для подсчёта частот
    val countMap = array.groupingBy { it }.eachCount()
    
    // Создаём приоритетную очередь с компаратором по частоте (убывание)
    val heap = PriorityQueue<Int> { a, b -> 
        (countMap[b] ?: 0).compareTo(countMap[a] ?: 0)
    }
    // Добавляем все уникальные элементы в кучу
    heap.addAll(countMap.keys)
    
    // Используем generateSequence для извлечения n элементов
    return generateSequence { if (heap.isNotEmpty()) heap.poll() else null }
        .take(n)
        .toList()
}
```

### Stream API (Kotlin)

```kotlin
// Функциональный подход с использованием встроенных функций Kotlin
fun findByStreamK(arr: Array<Int>, n: Int): List<Int> {
    return arr.groupingBy { it }.eachCount() // Подсчитываем частоты
        .entries // Преобразуем в коллекцию записей
        .sortedByDescending { it.value } // Сортируем по частоте в убывающем порядке
        .take(n) // Берём первые n элементов
        .map { it.key } // Извлекаем ключи (сами элементы)
}
```

### TreeMap (Kotlin)

```kotlin
// Подход с TreeMap (менее эффективен из-за дополнительной сортировки)
fun findByTreeMapK(arr: Array<Int>, n: Int): List<Int> {
    // Подсчитываем частоты с помощью groupingBy
    val countMap = arr.groupingBy { it }.eachCount().toMutableMap()
    
    // Сортируем записи по частоте в убывающем порядке
    val sortedEntries = countMap.entries.sortedByDescending { it.value }
    
    // Извлекаем первые n элементов
    return sortedEntries.take(n).map { it.key }
}
```

### Пример использования (Kotlin)

Пример использования всех трёх подходов:

```kotlin
// Демонстрация работы всех трёх подходов
fun main() {
    val inputArray = arrayOf(1, 2, 3, 2, 2, 1, 4, 5, 6, 1, 2, 3)
    
    // Подход 1: HashMap + PriorityQueue
    val top3a = findByHashMapAndPriorityQueueK(inputArray, 3)
    println("Top 3 (PriorityQueue): $top3a") // [2, 1, 3]
    
    // Подход 2: Stream API
    val top3b = findByStreamK(inputArray, 3)
    println("Top 3 (Stream): $top3b") // [2, 1, 3]
    
    // Подход 3: TreeMap
    val top3c = findByTreeMapK(inputArray, 3)
    println("Top 3 (TreeMap): $top3c") // [2, 1, 3]
}
```

## Сложность

Анализ сложности показывает, что все три подхода имеют схожую временную сложность, но различаются в деталях реализации и эффективности.

### Сложность HashMap + PriorityQueue

Временная сложность составляет `O(m + n log n)`, где `m` — размер массива, `n` — количество уникальных элементов. Подсчёт частоты занимает `O(m)` времени, так как мы проходим по массиву один раз. Построение кучи требует `O(n log n)` времени, так как мы добавляем `n` элементов в приоритетную очередь. Извлечение топ-`n` элементов также занимает `O(n log n)` времени, так как каждая операция `poll()` требует `O(log n)` времени. Пространственная сложность составляет `O(n)` для хранения `HashMap` и `PriorityQueue`.

### Сложность Stream API

Временная сложность также составляет `O(m + n log n)`. Группировка элементов занимает `O(m)` времени, так как мы проходим по массиву один раз. Сортировка записей по частоте требует `O(n log n)` времени. Пространственная сложность составляет `O(n)` для хранения `Map` и промежуточных коллекций, создаваемых в процессе работы `Stream API`.

### Сложность TreeMap

Временная сложность составляет `O(m log n + n log n)`. Подсчёт частоты с использованием `TreeMap` требует `O(m log n)` времени, так как каждая операция `put()` занимает `O(log n)` времени. Дополнительная сортировка по значениям требует `O(n log n)` времени. Пространственная сложность составляет `O(n)` для хранения `TreeMap` и списка отсортированных записей.

## Особенности

Все три подхода обладают определёнными особенностями, которые делают их подходящими для различных сценариев. Гибкость всех подходов заключается в том, что они работают с любыми типами данных, не только с целыми числами. Для работы с другими типами достаточно изменить типы в сигнатурах методов и, при необходимости, предоставить компаратор.

Эффективность `PriorityQueue` делает его оптимальным выбором для больших массивов, так как он использует эффективную структуру данных для извлечения топ-элементов без необходимости полной сортировки всех элементов. Это особенно важно, когда `n` значительно меньше количества уникальных элементов.

Читаемость `Stream API` делает его наиболее предпочтительным для функционального стиля программирования. Декларативный синтаксис позволяет легко понять логику алгоритма, что упрощает поддержку и модификацию кода.

## Применение

Поиск `n` самых частых элементов используется в различных областях. В анализе данных эта задача возникает при поиске наиболее распространённых паттернов или значений в наборах данных. В обработке текста поиск топ-слов позволяет определить ключевые темы и термины в документах.

В рекомендательных системах поиск наиболее частых элементов помогает определить предпочтения пользователей и предложить релевантные рекомендации. В логировании поиск топ-ошибок позволяет быстро выявить наиболее критичные проблемы в системе. В аналитике веб-сайтов поиск наиболее частых страниц или источников трафика помогает понять поведение пользователей и оптимизировать контент.

## Оптимизация

Для оптимизации производительности можно использовать различные техники в зависимости от соотношения между `n` и количеством уникальных элементов.

### Минимальная куча для больших n

Если `n` близко к количеству уникальных элементов, можно использовать минимальную кучу размером `n` вместо максимальной кучи размером `u` (где `u` — количество уникальных элементов). Это позволяет уменьшить использование памяти и улучшить производительность:

```java
// Оптимизированная версия с минимальной кучей размером n
// Эффективна, когда n значительно меньше количества уникальных элементов
public static List<Integer> findByMinHeap(Integer[] arr, int n) {
    // Шаг 1: Подсчитываем частоту каждого элемента
    Map<Integer, Integer> countMap = new HashMap<>();
    for (int i : arr) {
        countMap.put(i, countMap.getOrDefault(i, 0) + 1);
    }
    
    // Шаг 2: Создаём минимальную кучу размером n (храним только топ-n элементов)
    // Компаратор сравнивает элементы по частоте в возрастающем порядке
    PriorityQueue<Map.Entry<Integer, Integer>> minHeap = 
        new PriorityQueue<>((a, b) -> a.getValue() - b.getValue());
    
    // Шаг 3: Проходим по всем записям и поддерживаем кучу размером n
    for (Map.Entry<Integer, Integer> entry : countMap.entrySet()) {
        minHeap.offer(entry); // Добавляем элемент в кучу
        // Если размер кучи превышает n, удаляем элемент с минимальной частотой
        // Это гарантирует, что в куче остаются только элементы с наибольшей частотой
        if (minHeap.size() > n) {
            minHeap.poll(); // Удаляем элемент с наименьшей частотой
        }
    }
    
    // Шаг 4: Извлекаем элементы из кучи и преобразуем в список
    return minHeap.stream()
        .map(Map.Entry::getKey) // Извлекаем ключи (сами элементы)
        .collect(Collectors.toList());
}
```

Эта оптимизация особенно эффективна, когда `n` значительно меньше количества уникальных элементов, так как мы поддерживаем кучу размером `n` вместо `u`, что уменьшает использование памяти и улучшает производительность операций с кучей.

## Когда использовать

Выбор подходящего подхода зависит от конкретных требований приложения, размера данных и стиля программирования.

Используйте `HashMap` + `PriorityQueue`, когда нужна максимальная производительность, массив большой, и `n` относительно мало. Этот подход обеспечивает наилучшую производительность для большинства практических случаев, особенно когда количество уникальных элементов велико, а `n` мало.

Используйте `Stream API`, когда нужна читаемость кода, вы работаете в функциональном стиле, и массив среднего размера. Декларативный синтаксис делает код более понятным и легким для поддержки, что особенно важно в командах, использующих функциональный стиль программирования.

Используйте `TreeMap`, когда нужна дополнительная сортировка по ключам, и вы работаете с отсортированными данными. Хотя этот подход менее эффективен для задачи поиска топ-элементов по частоте, он может быть полезен, когда требуется дополнительная обработка данных, связанная с сортировкой по ключам.

## Решение проблем

При работе с поиском топ-`n` наиболее частых элементов могут возникать различные проблемы. Если алгоритм работает медленнее, чем ожидалось, проверьте соотношение между `n` и количеством уникальных элементов. Если `n` близко к количеству уникальных элементов, рассмотрите возможность использования минимальной кучи размером `n` вместо максимальной кучи размером `u`.

Если возникают проблемы с памятью, убедитесь, что вы используете оптимальный подход для вашего случая. Минимальная куча размером `n` использует меньше памяти, чем максимальная куча размером `u`, когда `n` значительно меньше `u`. Это особенно важно для больших массивов с большим количеством уникальных элементов.

Если результаты не соответствуют ожиданиям, проверьте обработку граничных случаев. Убедитесь, что ваш код корректно обрабатывает случаи, когда `n` больше количества уникальных элементов, `n` равно нулю или отрицательно, массив пуст, или все элементы одинаковы. Также проверьте корректность компаратора в `PriorityQueue` — он должен правильно сравнивать элементы по частоте, а не по их значениям.

Если возникают проблемы с производительностью на больших данных, рассмотрите возможность использования параллельной обработки. `Stream API` поддерживает параллельное выполнение через `parallelStream()`, что может улучшить производительность для больших массивов на многопроцессорных системах. Однако важно понимать, что параллелизация добавляет накладные расходы и эффективна только для достаточно больших объёмов данных.

## Частые вопросы

**Вопрос:** Почему `HashMap` + `PriorityQueue` предпочтительнее других подходов?

**Ответ:** `HashMap` + `PriorityQueue` обеспечивает наилучший баланс между производительностью и простотой реализации. Он эффективно использует память и обеспечивает хорошую производительность для большинства практических случаев, особенно когда `n` значительно меньше количества уникальных элементов.

**Вопрос:** Можно ли использовать `Stream API` для больших массивов?

**Ответ:** Да, `Stream API` может использоваться для больших массивов, но его производительность может быть немного ниже, чем у подхода с `PriorityQueue`. Однако для большинства практических случаев разница в производительности незначительна, и преимущества читаемости кода могут перевесить небольшое снижение производительности.

**Вопрос:** Когда следует использовать минимальную кучу вместо максимальной?

**Ответ:** Минимальную кучу размером `n` следует использовать, когда `n` значительно меньше количества уникальных элементов. Это позволяет уменьшить использование памяти и улучшить производительность операций с кучей, так как мы поддерживаем кучу меньшего размера.

**Вопрос:** Как обрабатывать равенство частот?

**Ответ:** При равенстве частот порядок элементов не определён. Если требуется определённый порядок (например, лексикографический по значению элемента), необходимо модифицировать компаратор, чтобы он учитывал и значение элемента, и частоту.

**Вопрос:** Можно ли использовать эти подходы для других типов данных?

**Ответ:** Да, все подходы могут быть легко адаптированы для работы с другими типами данных. Достаточно изменить типы в сигнатурах методов и, при необходимости, предоставить компаратор для сравнения элементов. Например, для работы со строками можно использовать `Map<String, Integer>`, а для работы с объектами — `Map<MyClass, Integer>` с соответствующим компаратором.

**Вопрос:** Как обрабатывать поток данных в реальном времени?

**Ответ:** Для обработки потока данных в реальном времени можно использовать инкрементальный подход: поддерживать `HashMap` с частотами и `PriorityQueue`, обновляя их при поступлении новых элементов. Однако это требует более сложной реализации с поддержанием актуального состояния структур данных.

**Вопрос:** Можно ли использовать эти подходы для распределённых систем?

**Ответ:** Да, но требуется модификация алгоритма. Можно использовать подход MapReduce: на каждом узле подсчитывать локальные частоты, затем агрегировать результаты на центральном узле и извлекать топ-`n` элементов из агрегированных данных. Это позволяет обрабатывать большие объёмы данных, распределённые по нескольким узлам.

## Глоссарий терминов

`Top N Frequent Elements` — задача поиска `n` наиболее часто встречающихся элементов в массиве или коллекции.

`HashMap` — структура данных, которая хранит пары ключ-значение и обеспечивает быстрый доступ к значениям по ключу. Используется для подсчёта частоты элементов.

`PriorityQueue` — структура данных, которая хранит элементы в порядке приоритета, определяемом компаратором. Используется для извлечения элементов с наибольшей частотой.

`Stream API` — набор функций в `Java` 8+ для функциональной обработки коллекций. Позволяет писать декларативный код для обработки данных.

`TreeMap` — структура данных, которая хранит пары ключ-значение в отсортированном порядке по ключам. Менее эффективен для задачи поиска топ-элементов по частоте.

`Минимальная куча` — приоритетная очередь, где элемент с минимальным значением имеет наивысший приоритет. Используется для оптимизации, когда `n` мало по сравнению с количеством уникальных элементов.

`Максимальная куча` — приоритетная очередь, где элемент с максимальным значением имеет наивысший приоритет. Используется для извлечения элементов с наибольшей частотой.

`Частота элемента` — количество раз, которое элемент встречается в массиве или коллекции.

`Компаратор` — функция сравнения, определяющая порядок элементов в структурах данных, таких как `PriorityQueue` или при сортировке.

`Группировка` — операция объединения элементов с одинаковыми значениями для подсчёта их частоты.

`Инкрементальное обновление` — техника обновления структур данных при поступлении новых элементов без полного пересчёта всех данных.

`Распределённая обработка` — техника обработки данных, распределённых по нескольким узлам, с последующей агрегацией результатов.

### Пример 1: Поиск наиболее частых слов в тексте

```java
// Поиск топ-n наиболее частых слов в тексте
// Практический пример применения алгоритма поиска наиболее частых элементов
public static List<String> findTopWords(String text, int n) {
    // Шаг 1: Разбиваем текст на слова и приводим к нижнему регистру
    // Регулярное выражение \\W+ разделяет по не-словесным символам
    String[] words = text.toLowerCase().split("\\W+");
    
    // Шаг 2: Подсчитываем частоту каждого слова
    Map<String, Integer> wordCount = new HashMap<>();
    
    for (String word : words) {
        // Пропускаем пустые строки, которые могут появиться после split
        if (!word.isEmpty()) {
            wordCount.put(word, wordCount.getOrDefault(word, 0) + 1);
        }
    }
    
    // Шаг 3: Создаём приоритетную очередь по частоте (максимальная куча)
    // Компаратор сравнивает слова по их частоте в убывающем порядке
    PriorityQueue<String> heap = new PriorityQueue<>(
        (a, b) -> wordCount.get(b) - wordCount.get(a)
    );
    // Добавляем все уникальные слова в кучу
    heap.addAll(wordCount.keySet());
    
    // Шаг 4: Извлекаем топ-n слов с наибольшей частотой
    List<String> result = new ArrayList<>();
    for (int i = 0; i < n && !heap.isEmpty(); i++) {
        result.add(heap.poll()); // poll() извлекает слово с максимальной частотой
    }
    
    return result;
}
```

```java
    // Фильтруем только записи уровня ERROR

        // Проверяем уровень логирования
        if (log.getLevel().equals("ERROR")) {
            String errorMessage = log.getMessage();

            errorCount.put(errorMessage, errorCount.getOrDefault(errorMessage, 0) + 1);

    }
```

```java
// Безопасная реализация с обработкой всех граничных случаев
public static List<Integer> findTopNFrequentSafe(Integer[] arr, int n) {
    // Проверка на null и пустой массив
    if (arr == null || arr.length == 0) {
        return new ArrayList<>();
    }
    
    // Проверка на невалидное n
    if (n <= 0) {
        return new ArrayList<>();
    }
    
    // Подсчитываем частоты
    Map<Integer, Integer> countMap = new HashMap<>();
    for (Integer i : arr) {
        countMap.put(i, countMap.getOrDefault(i, 0) + 1);
    }
    
    // Если n больше количества уникальных элементов, возвращаем все
    if (n >= countMap.size()) {
        return new ArrayList<>(countMap.keySet());
    }
    
    // Используем PriorityQueue для извлечения топ-n
    PriorityQueue<Integer> heap = new PriorityQueue<>(
        (a, b) -> countMap.get(b) - countMap.get(a)
    );
    heap.addAll(countMap.keySet());
    
    List<Integer> result = new ArrayList<>();
    for (int i = 0; i < n && !heap.isEmpty(); i++) {
        result.add(heap.poll());
    }
    
    return result;
}
```

## Лучшие практики

При реализации поиска топ-`n` наиболее частых элементов важно следовать нескольким лучшим практикам. Выбор подхода зависит от соотношения между `n` и количеством уникальных элементов. `HashMap` + `min-heap` по частоте размером `k` даёт `O(n log k)` временную сложность, что эффективнее полной сортировки записей по частоте `O(n log n)` для одного запроса «топ-n». Для одного запроса достаточно подсчёта + сортировки записей или кучи.

При равенстве частот уточните порядок элементов (например, лексикографический по значению элемента). Компаратор должен быть согласован и учитывать и значение, и частоту, чтобы обеспечить детерминированный порядок результатов.

Граничные случаи требуют особого внимания. Если `n` больше количества уникальных элементов, верните все уникальные элементы. Если `n` ≤ 0, верните пустой список. Если массив пуст, верните пустой список. Если массив содержит один элемент, верните список из одного элемента.

Память также важна для оптимизации. Подсчёт частот требует `O(u)` памяти, где `u` — число уникальных элементов. Куча размером `n` требует `O(n)` памяти. При очень большом `u` и малом `n` `min-heap` по частоте эффективнее полной сортировки.

При тестировании проверьте случаи: `n = 1`, `n` = количество уникальных элементов, все элементы равны, все элементы разные, порядок при равенстве частот. Это поможет убедиться, что реализация корректно обрабатывает все граничные случаи и различные состояния входных данных.

## Заключение

В этом руководстве мы рассмотрели три подхода к поиску `n` самых частых элементов в массиве. `HashMap` + `PriorityQueue` является наиболее эффективным решением для большинства случаев, обеспечивая хороший баланс между производительностью и простотой реализации. `Stream API` предлагает более читаемый и декларативный код, что делает его предпочтительным для функционального стиля программирования. `TreeMap` менее эффективен для этой задачи, но может быть полезен, когда требуется дополнительная сортировка по ключам.

Выбор подходящего подхода зависит от конкретных требований приложения, размера данных и стиля программирования. Для большинства практических случаев рекомендуется использовать `HashMap` + `PriorityQueue` или его оптимизированную версию с минимальной кучей размером `n`, когда `n` значительно меньше количества уникальных элементов.
