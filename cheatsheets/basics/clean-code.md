# Принципы чистого кода

## Именование

- **Осмысленные имена**: переменные, методы и классы должны отражать назначение.
- **Избегать сокращений**: `userRepository`, а не `usrRepo`, если контекст не общепринятый (id, url, dto).
- **Имена не должны вводить в заблуждение**: не хранить список в переменной `userList`, если это не `List`.
- **Константы**: `UPPER_SNAKE_CASE` для констант.

```java
// Плохо
int d;
List<int[]> list1;

// Хорошо
int daysSinceCreation;
List<Order> pendingOrders;
```


## Функции и методы

- **Маленькие**: одна задача на метод; если метод длинный — разбить.
- **Один уровень абстракции**: внутри метода не смешивать высокоуровневую логику и детали реализации.
- **Мало аргументов**: 0–2 предпочтительно; больше — рассмотреть объект-параметр или билдер.
- **Без побочных эффектов**: метод не должен делать скрытых изменений состояния, не отражённых в имени.
- **Command/`Query` разделение**: метод либо меняет состояние (command), либо возвращает данные (query), но не оба.

```java
// Плохо
public boolean set(String attr, String value) {
    if ("name".equals(attr)) { name = value; return true; }
    if ("email".equals(attr)) { email = value; return true; }
    return false;
}

// Лучше: отдельно проверка и изменение
public boolean isValidAttribute(String attr) { ... }
public void setAttribute(String attr, String value) { ... }
```


## Комментарии

- **Код должен быть самодокументируемым**: имена и структура объясняют «что» и «зачем».
- **Комментарии — когда нужно объяснить «почему»**: неочевидное решение, обход бага, бизнес-правило.
- **Избегать закомментированного кода**: удалять или переносить в историю (git).
- **Javadoc для публичного API**: описание контракта, параметров, возвращаемого значения, исключений.

```java
// Хорошо: объясняет причину
// Retry из-за временных сбоев БД при миграции (тикет PROJ-123)
repository.save(entity);
```


## Структура и форматирование

- **Вертикальное форматирование**: связанный код — рядом; пустые строки разделяют логические блоки.
- **Размер файла**: предпочитайте классы и файлы умеренного размера; большие — признак нарушения **SRP**.
- **Зависимости**: направление зависимостей вниз (от высокоуровневых модулей к низкоуровневым); избегать циклических зависимостей.
- **Отступы и стиль**: единый стиль (например, Google Java Style); автоформатирование в **IDE**.


## Обработка ошибок

- **Использовать исключения, а не коды возврата**: не смешивать нормальный результат и ошибку в одном возвращаемом значении.
- **Не игнорировать исключения**: пустой **catch** — только с явным обоснованием и логированием.
- **Контекст при броске**: оборачивать в исключение с понятным сообщением или **cause**.
- **Границы контракта**: проверять входные параметры (IllegalArgumentException); не допускать неконсистентного состояния объекта.

```java
// Плохо
try {
    doSomething();
} catch (Exception e) {}

// Лучше
try {
    doSomething();
} catch (SpecificException e) {
    log.warn("Expected situation: {}", e.getMessage());
    throw new DomainException("Cannot doSomething", e);
}
```


## Лучшие практики

- Регулярный рефакторинг: не накапливать «временные» решения.
- Тесты защищают рефакторинг и документируют поведение.
- **Code review** и единые стандарты (checkstyle, spotbugs) помогают держать код чистым.
- Избегать магических чисел и строк: выносить в константы или конфигурацию.


## Именование: детали

**Осмысленные имена** — переменные, методы и классы должны отражать назначение без необходимости смотреть в реализацию. **Избегать сокращений** — `userRepository`, а не `usrRepo`, кроме общепринятых (id, url, dto). **Имена не должны вводить в заблуждение** — не хранить список в переменной `userList`, если это не `List`; не использовать `getData()` если метод возвращает не данные, а что-то иное. **Константы** — `UPPER_SNAKE_CASE` для констант. **Параметры и локальные переменные** — **camelCase**; короткие имена допустимы в узкой области видимости (цикл: i, j).


## Функции и методы: детали

**Маленькие** — одна задача на метод; если метод длинный — разбить на подметоды. **Один уровень абстракции** — внутри метода не смешивать высокоуровневую логику и детали реализации (например, вызов сервиса и парсинг байтов). **Мало аргументов** — 0–2 предпочтительно; больше — рассмотреть объект-параметр или билдер. **Без побочных эффектов** — метод не должен делать скрытых изменений состояния, не отражённых в имени. **Command/`Query` разделение** — метод либо меняет состояние (command), либо возвращает данные (query), но не оба.


## Комментарии: детали

**Код должен быть самодокументируемым** — имена и структура объясняют «что» и «зачем». **Комментарии — когда нужно объяснить «почему»** — неочевидное решение, обход бага, бизнес-правило. **Избегать закомментированного кода** — удалять или переносить в историю (git). **Javadoc для публичного API** — описание контракта, параметров, возвращаемого значения, исключений. **Не дублировать код в комментариях** — комментарий не должен повторять то, что видно из кода.


## Структура и форматирование: детали

**Вертикальное форматирование** — связанный код — рядом; пустые строки разделяют логические блоки. **Размер файла** — предпочитайте классы и файлы умеренного размера; большие — признак нарушения **SRP**. **Зависимости** — направление зависимостей вниз (от высокоуровневых модулей к низкоуровневым); избегать циклических зависимостей. **Отступы и стиль** — единый стиль (например, Google Java Style); автоформатирование в **IDE**.


## Обработка ошибок: детали

**Использовать исключения, а не коды возврата** — не смешивать нормальный результат и ошибку в одном возвращаемом значении. **Не игнорировать исключения** — пустой **catch** — только с явным обоснованием и логированием. **Контекст при броске** — оборачивать в исключение с понятным сообщением или **cause**. **Границы контракта** — проверять входные параметры (IllegalArgumentException); не допускать неконсистентного состояния объекта. **Checked vs unchecked** — проверяемые исключения для ожидаемых ошибок (IO, парсинг); непроверяемые для ошибок программирования (NPE, IllegalArgumentException).


## Связь с SOLID и паттернами

Чистый код поддерживает **SOLID**: **SRP** — один класс одна ответственность, маленькие методы. **OCP** — расширение без модификации через полиморфизм и стратегии. **LSP** — подтипы подставляемы; контракты соблюдаются. **ISP** — узкие интерфейсы; код не зависит от неиспользуемого. **DIP** — зависимости от абстракций; внедрение через конструктор. Паттерны (Strategy, `Factory`, Builder) помогают сохранять чистоту кода.


## Частые вопросы по чистому коду

**Когда комментарий уместен?** Когда нужно объяснить «почему», а не «что»: неочевидное решение, обход бага, бизнес-правило. **Как определить, что метод слишком длинный?** Если метод делает больше одной логической вещи или смешивает уровни абстракции — разбить. **Что делать с магическими числами?** Выносить в константы с осмысленными именами или в конфигурацию. **Как обрабатывать ошибки в чистом коде?** Использовать исключения; не смешивать результат и ошибку в одном возвращаемом значении; проверять входные параметры.

```java
// Хорошо
```

## Функции: расширенные примеры

```java
// Плохо: метод делает несколько вещей и возвращает результат + флаг
public boolean processAndNotify(User u) {
    validate(u);
    save(u);
    sendEmail(u);
    return true;
}

// Лучше: разделение на методы с одной задачей
public void process(User u) {
    validator.validate(u);
    repository.save(u);
    notifier.sendWelcome(u);
}
```


## Комментарии: когда писать и когда не писать

**Писать:** неочевидное решение (обход бага, бизнес-правило), предупреждение о последствиях, **TODO** с контекстом, **Javadoc** для публичного **API**. **Не писать:** дублирование кода в комментарии, закомментированный код (удалять или в git), комментарии «что» когда имя метода/переменной уже объясняет.


## Структура: направление зависимостей

Зависимости должны быть направлены вниз: высокоуровневые модули (сервисы, оркестрация) зависят от низкоуровневых (репозитории, утилиты) через интерфейсы. Избегать циклических зависимостей (A B C A). Большие файлы и классы — признак нарушения **SRP**; разбивать на меньшие модули.


## Обработка ошибок: примеры

```java
// Плохо: пустой catch
try {
    doSomething();
} catch (Exception e) {}

// Лучше: логирование и проброс с контекстом
try {
    doSomething();
} catch (SpecificException e) {
    log.warn("Expected situation: {}", e.getMessage());
    throw new DomainException("Cannot doSomething", e);
}
```

## Резюме для быстрого повторения (чистый код)

**Именование:** осмысленные имена, избегать сокращений, константы **UPPER_SNAKE_CASE**. **Функции:** маленькие, один уровень абстракции, мало аргументов, **Command**/**Query** разделение. **Комментарии:** объяснять «почему»; **Javadoc** для публичного **API**. **Структура:** связанный код рядом; зависимости вниз; избегать циклов. **Ошибки:** исключения вместо кодов возврата; контекст при броске; проверка входных параметров. **SOLID и паттерны** поддерживают чистый код.

## Code Smells: определение и примеры

**Code smell** — признак возможной проблемы в коде, не обязательно баг, но сигнал к рефакторингу.

| Запах | Описание | Действие |
|-------|----------|----------|
| Длинный метод | Метод > 20–30 строк, несколько уровней абстракции | Разбить на подметоды |
| Большой класс | Класс делает слишком много | Выделить ответственности (SRP) |
| Длинный список параметров | 4+ параметров | Объект-параметр, билдер |
| Дублирование | Одинаковая логика в нескольких местах | Вынести в общий метод/класс |
| Магические числа/строки | Литералы без имени | Константы с осмысленными именами |
| Имена вводят в заблуждение | Имя не соответствует типу или поведению | Переименовать |
| Мёртвый код | Неиспользуемый код, закомментированные блоки | Удалить |
| Глубокая вложенность | Много уровней if/**for** | Ранний **return**, полиморфизм |
| Избыточные комментарии | Комментарий повторяет код | Удалить или объяснить «почему» |
| Специфика класса в имени | **OrderManager** в имени класса | Убрать суффикс, имя = ответственность |


## Code Smells: примеры на Java

```java
// Длинный список параметров — плохо
public void createOrder(String user, String item, int qty, String addr, String payment) { ... }

// Объект-параметр — хорошо
public void createOrder(CreateOrderRequest request) { ... }
```

```java
// Магические числа — плохо
if (status == 3) { ... }
Thread.sleep(5000);

// Константы — хорошо
if (status == OrderStatus.SHIPPED.getCode()) { ... }
Thread.sleep(MAX_RETRY_DELAY_MS);
```

```java
// Глубокая вложенность — плохо
if (user != null) {
    if (user.isActive()) {
        if (order != null) {
            if (order.isPaid()) { ... }
        }
    }
}

// Ранний return — хорошо
if (user == null || !user.isActive()) return;
if (order == null || !order.isPaid()) return;
// основная логика
```


## Антипаттерны именования

- **Шумовые слова**: `UserData`, **OrderInfo** **User**, **Order** если контекст ясен.
- **Сокращения кроме общепринятых**: `usrRepo` вместо `userRepository` усложняет чтение; допустимы id, **url**, **dto**, **api**.
- **Префиксы типов в именах**: `strName`, `listUsers` — тип меняется, имя остаётся; убрать префикс.
- **Слишком общие имена**: `data`, `result`, `handler` — уточнить по контексту (e.g. `orderTotal`, `paymentResult`).
- **Разные понятия — одно имя**: не использовать `get` для метода, который что-то вычисляет и кэширует; лучше `compute` или явное имя.


## Рефакторинг: чек-лист перед изменением

1. Покрыть тестами зону изменения (если тестов нет — добавить ключевые сценарии).
2. Выполнять маленькие шаги: один приём рефакторинга за раз (Rename, `Extract Method`, Move).
3. После каждого шага запускать тесты.
4. Не смешивать рефакторинг и новую функциональность в одном коммите.
5. Использовать поиск по проекту, чтобы не сломать вызовы (переименование, смена сигнатуры).

## TDD и чистый код

**TDD** (Test-`Driven` Development) поддерживает чистый код: тест задаёт контракт и использование **API**; код пишется так, чтобы тест прошёл, что естественно ведёт к меньшим методам, меньшему числу зависимостей и явным входным/выходным данным. Рефакторинг после «зелёного» теста выполняется с уверенностью. Чистый код и **TDD** усиливают друг друга: тесты остаются простыми, когда код простой.


## Документирование публичного API

- **Javadoc** для публичных классов и методов: что делает, параметры, возвращаемое значение, исключения, пример использования при необходимости.
- Не документировать очевидное (геттеры/сеттеры без особых контрактов).
- В комментариях указывать инварианты и пред-/постусловия, если они есть (например, «id не `null`», «возвращает неизменяемый список»).
- Для сложных алгоритмов — краткое описание подхода или ссылка на спецификацию.


## Границы и контракты

- **Входные параметры**: проверять на **null** и допустимые значения на границе модуля (публичный API); бросать `IllegalArgumentException` с понятным сообщением.
- **Возвращаемые значения**: не возвращать **null** вместо коллекции; предпочитать пустую коллекцию или `Optional` для одного значения.
- **Инварианты объекта**: конструктор и сеттеры не должны оставлять объект в неконсистентном состоянии; при необходимости делать объект неизменяемым.


## Таблица: типичные нарушения и исправления

| Нарушение | Исправление |
|-----------|-------------|
| Метод возвращает и результат, и флаг ошибки | Исключение или **Optional**/**Result**-тип |
| Пустой **catch** | Логирование и/или проброс с контекстом |
| Код в нескольких копиях | **Extract Method**, общий сервис |
| Класс знает о деталях другого класса | Скрыть за интерфейсом, **Dependency Injection** |
| Жёстко заданные зависимости | Конструктор/сеттер для внедрения зависимостей |
| Смешение уровней абстракции в методе | Разбить на методы одного уровня |


## Глоссарий (чистый код)

- **Command/`Query` separation** — метод либо меняет состояние (command), либо возвращает значение (query), но не оба.
- **Code smell** — признак возможной проблемы, требующий рефакторинга.
- **Self-documenting code** — код, понятный по именам и структуре без избыточных комментариев.
- **Single level of abstraction** — внутри одного метода операции одного уровня абстракции (например, только вызовы сервисов или только работа с коллекциями).
- **Dependency rule** — зависимости направлены от высокоуровневых модулей к низкоуровневым; низкоуровневые не зависят от высокоуровневых.


## Примеры рефакторинга: до и после

**До:** метод с побочным эффектом и смешанными уровнями абстракции.

```java
public boolean process(User u) {
    if (u == null) return false;
    u.setLastLogin(LocalDateTime.now());
    repository.save(u);
    byte[] raw = serializer.serialize(u);
    messageQueue.send("user.updated", raw);
    return true;
}
```

**После:** разделение на команды и запросы, один уровень абстракции.

```java
public void updateLastLogin(User u) {
    Objects.requireNonNull(u, "user");
    u.setLastLogin(LocalDateTime.now());
    repository.save(u);
    eventPublisher.publish(new UserUpdatedEvent(u));
}
```


## Чистый код и производительность

Чистый код не противоречит производительности: сначала писать читаемо и правильно, затем измерять и при необходимости оптимизировать узкие места. Избегать преждевременной оптимизации (усложнение кода без измерений). Оптимизированный код тоже должен быть по возможности чистым: вынести сложную логику в отдельные методы с понятными именами.


## Соглашения команды

- Единый стиль (Google `Java Style`, или внутренний гайд) и автоматическое форматирование при коммите.
- Правила именования пакетов, классов, методов (например, сервисы — `Service`, репозитории — `Repository`).
- Когда писать **Javadoc** (публичный `API`, библиотеки), когда достаточно комментария «почему».
- Как обрабатывать исключения (обёртка в доменное исключение, логирование на границах).
- Регулярный рефакторинг в рамках задач, а не накопление долга.


## Краткие формулировки для запоминания

- Имена должны отвечать на «что» и «зачем», не заставлять смотреть в реализацию.
- Метод: одна задача, один уровень абстракции, мало аргументов.
- Комментарий объясняет «почему», код — «что» и «как».
- Ошибки — через исключения, с контекстом; не игнорировать.
- Зависимости вниз; без циклов; большие классы/методы — кандидаты на разбиение.

## Связь с тестируемостью

Чистый код легче тестировать: маленькие методы и один уровень абстракции упрощают **unit**-тесты; зависимости через интерфейсы позволяют подставлять **mock**; отсутствие скрытых побочных эффектов делает поведение предсказуемым. Если код сложно покрыть тестами — часто это сигнал к упрощению и уменьшению связей.

## Java-специфика: Optional и null-safety

- **Optional** — использовать для возвращаемого значения «может отсутствовать»; не использовать для полей коллекций или параметров (предпочитать перегрузки или объект-параметр).
- **Не возвращать null** вместо коллекции; возвращать `Collections.emptyList()` или пустой список.
- **Проверка на null** на границах (входные параметры публичного API); внутри модуля по контракту можно не проверять, если контракт гарантирует **non-null**.
- **`@Nullable` / `@NonNull`** (JSR-305, JetBrains) — аннотации для документирования контракта; инструменты (IDE, SpotBugs) могут предупреждать о нарушениях.

```java
// Плохо: возврат null
public User findById(Long id) {
    return repository.findById(id).orElse(null);
}

// Лучше: Optional
public Optional<User> findById(Long id) {
    return repository.findById(id);
}
```


## Java: лямбды и стримы

- **Читаемость стримов**: если цепочка длинная или логика сложная — вынести в метод с осмысленным именем или разбить на шаги.
- **Избегать побочных эффектов** внутри **forEach** и других терминальных операций; предпочитать чистые функции.
- **Именование переменных в лямбдах**: при одной букве (x, y) допустимо в простых случаях; при сложной логике — осмысленное имя (user, order).

```java
// Плохо: длинная цепочка без имени
list.stream().filter(x -> x.getStatus() == 1 && x.getAmount() > 0).map(x -> x.getId()).collect(Collectors.toList());

// Лучше: вынести предикат
list.stream().filter(this::isActiveOrder).map(Order::getId).toList();
```


## Логирование в контексте чистого кода

- **Не логировать в «глубине»** бизнес-логики без необходимости; логировать на границах (вход в сервис, выход, ошибки).
- **Уровни логирования**: **ERROR** — ошибки, требующие внимания; **WARN** — ожидаемые аномалии (retry, fallback); **INFO** — ключевые события (старт/стоп, важные операции); **DEBUG** — детали для отладки.
- **Структурированное логирование**: передавать параметры как аргументы (**log.info("`User` {} created", id)), не конкатенировать строки (избежать лишних аллокаций и улучшить парсинг логов).
- **Не логировать чувствительные данные** (пароли, токены, персональные данные) в открытом виде.


## Конфигурация и магические значения

- **Выносить в конфигурацию** (файл, переменные окружения) всё, что может меняться между средами или без пересборки: **URL**, таймауты, лимиты, флаги.
- **Константы в коде** — только для значений, действительно фиксированных в коде (математические константы, коды состояний из контракта API).
- **Именование констант**: осмысленное имя (MAX_RETRY_ATTEMPTS), не аббревиатура без контекста.


## Версионирование и обратная совместимость API

- **Публичный API** (REST, библиотека) — не ломать обратную совместимость без явного мажорного обновления версии.
- **Устаревшие методы**: помечать @**Deprecated** с указанием замены и срока удаления; не удалять сразу.
- **Добавление полей/параметров** — обычно обратно совместимо; удаление или смена типа — нет. Для **REST** — версионирование **URL** или заголовок версии.


## Код-ревью: чек-лист по чистому коду

- [ ] Имена отражают назначение; нет вводящих в заблуждение имён.
- [ ] Методы короткие, один уровень абстракции, мало аргументов.
- [ ] Нет магических чисел/строк; константы или конфигурация.
- [ ] Комментарии объясняют «почему»; нет закомментированного кода.
- [ ] Ошибки обрабатываются; нет пустого **catch** без обоснования.
- [ ] Нет дублирования; зависимости направлены вниз.
- [ ] Публичный **API** документирован (Javadoc); контракты ясны.


## `CI` и качество кода

- **Автоматические проверки**: форматирование (Checkstyle, Spotless), статический анализ (SpotBugs, PMD); запускать в **CI** и при **PR**.
- **Пороги качества**: не допускать падения тестов; при необходимости блокировать мерж при снижении покрытия или росте количества замечаний **Sonar**.
- **Регулярный рефакторинг**: выделять время на уменьшение долга в рамках спринта; не накапливать «временные» решения.


## Технический долг и рефакторинг

- **Технический долг** — осознанные компромиссы (быстрая доставка vs идеальная архитектура); фиксировать в тикетах и планировать погашение.
- **Рефакторинг** — менять структуру кода без изменения наблюдаемого поведения; тесты обязательны.
- **Когда рефакторить**: при добавлении новой функциональности в зоне долга (рефакторинг + фича в одном `PR` при возможности); отдельные тикеты на крупный рефакторинг.


## Именование тестов и чистый код

- Тесты — тоже код; имена тестов должны быть осмысленными: `methodName_scenario_expectedResult` или `should_expectedResult_when_scenario`.
- Один сценарий на тест; **Arrange**–**Act**–**Assert**; при необходимости вынести подготовку в методы с понятными именами (**givenUserWithOrder(), **whenPaymentSucceeds**()).
- Чистый код в тестах упрощает поддержку и понимание падающих тестов.

## Принципы именования: полный чек-лист

- [ ] Класс, интерфейс — **PascalCase**; метод, переменная — **camelCase**; константа — **UPPER_SNAKE_CASE**; пакет — **lowercase**.
- [ ] Имя отражает назначение; не вводит в заблуждение (тип, поведение).
- [ ] Избегать сокращений кроме общепринятых (id, url, dto, api).
- [ ] Не использовать шумовые слова (Data, Info) без необходимости.
- [ ] Не использовать префиксы типов в именах (strName, listUsers).
- [ ] Имена методов: глагол или глагол+существительное (getUserById, `saveOrder`, isValid).


## Принципы функций: полный чек-лист

- [ ] Метод делает одну вещь; один уровень абстракции внутри метода.
- [ ] Длина метода: предпочтительно до 20–30 строк; при необходимости разбить.
- [ ] Количество аргументов: 0–2 предпочтительно; больше — объект-параметр или билдер.
- [ ] **Command**/**Query** разделение: метод либо меняет состояние, либо возвращает значение, но не оба.
- [ ] Нет скрытых побочных эффектов; имя метода отражает действие.
- [ ] Ранний **return** вместо глубокой вложенности; избегать вложенности > 2–3 уровней.


## Принципы комментариев: полный чек-лист

- [ ] Код самодокументируемый; комментарий объясняет «почему», не «что».
- [ ] Нет закомментированного кода; удалить или перенести в **git**.
- [ ] **Javadoc** для публичного **API**: описание, параметры, возврат, исключения.
- [ ] **TODO**/**FIXME** с контекстом и тикетом.
- [ ] Нет дублирования кода в комментарии.


## Принципы структуры: полный чек-лист

- [ ] Связанный код рядом; пустые строки разделяют логические блоки.
- [ ] Размер файла/класса умеренный; большой класс — признак нарушения **SRP**.
- [ ] Зависимости направлены вниз (высокий уровень низкий через интерфейсы).
- [ ] Нет циклических зависимостей (A B C A).
- [ ] Единый стиль (Google `Java Style` или внутренний гайд); автоформатирование в **IDE**.


## Принципы обработки ошибок: полный чек-лист

- [ ] Исключения вместо кодов возврата; не смешивать результат и ошибку в одном возвращаемом значении.
- [ ] Не игнорировать исключения; пустой **catch** только с явным обоснованием и логированием.
- [ ] Контекст при броске: оборачивать в исключение с понятным сообщением или **cause**.
- [ ] Проверка входных параметров на границах (IllegalArgumentException); не допускать неконсистентного состояния объекта.
- [ ] **Checked** vs **unchecked**: проверяемые для ожидаемых ошибок (IO, парсинг); непроверяемые для ошибок программирования (NPE, IllegalArgumentException).

## Глоссарий (расширенный)

- **Command** — метод, меняющий состояние объекта или системы (void или побочный эффект).
- **Query** — метод, возвращающий значение без изменения наблюдаемого состояния.
- **Code smell** — признак возможной проблемы в коде, требующий рефакторинга.
- **Self-documenting code** — код, понятный по именам и структуре без избыточных комментариев.
- **Single level of abstraction** — внутри одного метода операции одного уровня абстракции.
- **Dependency rule** — зависимости направлены от высокоуровневых модулей к низкоуровневым.
- **DRY** (Don't `Repeat` Yourself) — не дублировать логику; выносить в общее место.
- **KISS** (Keep `It Simple`, Stupid) — предпочитать простое решение сложному.
- **YAGNI** (You `Aren`'t `Gonna Need` It) — не добавлять функциональность «на будущее».
- **Technical debt** — осознанный компромисс (быстрая доставка vs идеальная архитектура).

## Краткие формулировки для запоминания (полный список)

- Имена должны отвечать на «что» и «зачем», не заставлять смотреть в реализацию.
- Метод: одна задача, один уровень абстракции, мало аргументов (0–2).
- Комментарий объясняет «почему», код — «что» и «как».
- Ошибки — через исключения, с контекстом; не игнорировать.
- Зависимости вниз; без циклов; большие классы/методы — кандидаты на разбиение.
- **Code smell** — сигнал к рефакторингу; не обязательно баг.
- **DRY** — не дублировать; **KISS** — проще лучше; **YAGNI** — не добавлять «на будущее».
- **Optional** для «может отсутствовать»; не возвращать **null** вместо коллекции.
- Логировать на границах; не логировать чувствительные данные.
- Рефакторинг — маленькими шагами; тесты обязательны.

## Дополнительные примеры: Command/Query разделение

```java
// Плохо: метод и меняет состояние, и возвращает результат
public boolean setAttribute(String attr, String value) {
    if ("name".equals(attr)) { name = value; return true; }
    if ("email".equals(attr)) { email = value; return true; }
    return false;
}

// Лучше: разделение на command и query
public void setAttribute(String attr, String value) {
    if (!isValidAttribute(attr)) throw new IllegalArgumentException("Invalid attr: " + attr);
    if ("name".equals(attr)) name = value;
    else if ("email".equals(attr)) email = value;
}
public boolean isValidAttribute(String attr) {
    return "name".equals(attr) || "email".equals(attr);
}
```

## Связь с SOLID: детали

- **SRP** — один класс одна ответственность; маленькие классы и методы; чистый код поддерживает **SRP** через разбиение длинных методов и больших классов.
- **OCP** — расширение без модификации; полиморфизм и стратегии; чистый код поддерживает **OCP** через явные интерфейсы и отсутствие дублирования.
- **LSP** — подтипы подставляемы; контракты соблюдаются; чистый код поддерживает **LSP** через предсказуемое поведение и явные контракты в **Javadoc**.
- **ISP** — узкие интерфейсы; код не зависит от неиспользуемого; чистый код поддерживает **ISP** через осмысленные имена методов и отсутствие «толстых» интерфейсов.
- **DIP** — зависимости от абстракций; внедрение через конструктор; чистый код поддерживает **DIP** через направление зависимостей вниз и тестируемость.


## Связь с тестируемостью: детали

Чистый код легче тестировать: маленькие методы и один уровень абстракции упрощают **unit**-тесты; зависимости через интерфейсы позволяют подставлять **mock**; отсутствие скрытых побочных эффектов делает поведение предсказуемым. Если код сложно покрыть тестами — часто это сигнал к упрощению и уменьшению связей. Тесты защищают рефакторинг и документируют поведение; чистый код в тестах (имена, AAA) упрощает поддержку.

## Глоссарий (полный список)

- **Command** — метод, меняющий состояние объекта или системы.
- **Query** — метод, возвращающий значение без изменения наблюдаемого состояния.
- **Code smell** — признак возможной проблемы в коде, требующий рефакторинга.
- **Self-documenting code** — код, понятный по именам и структуре без избыточных комментариев.
- **Single level of abstraction** — внутри одного метода операции одного уровня абстракции.
- **Dependency rule** — зависимости направлены от высокоуровневых модулей к низкоуровневым.
- **DRY** (Don't `Repeat` Yourself) — не дублировать логику; выносить в общее место.
- **KISS** (Keep `It Simple`, Stupid) — предпочитать простое решение сложному.
- **YAGNI** (You `Aren`'t `Gonna Need` It) — не добавлять функциональность «на будущее».
- **Technical debt** — осознанный компромисс (быстрая доставка vs идеальная архитектура).
- **Refactoring** — изменение структуры кода без изменения наблюдаемого поведения.
- **Extract Method** — приём рефакторинга: выделение фрагмента кода в отдельный метод.
- **Early return** — выход из метода в начале при невыполнении условий; уменьшает вложенность.
- **Guard clause** — проверка в начале метода с ранним **return** при невыполнении условия.


## Резюме для быстрого повторения (полное)

**Именование:** осмысленные имена, избегать сокращений (кроме id, url, dto), константы **UPPER_SNAKE_CASE**, не вводить в заблуждение, стили в **Java** (PascalCase для классов, camelCase для методов). **SOLID и паттерны** поддерживают чистый код; тестируемость и читаемость идут вместе. **Java-специфика: Optional** для «может отсутствовать», стримы читаемо, логирование на границах, конфигурация вместо магических значений.

```java
/**
 * Сохраняет заказ и публикует событие создания.
 *
 * @param order заказ для сохранения; не null, id может быть null (новый заказ)
 * @throws IllegalArgumentException если order невалиден (пустые обязательные поля)
 * @throws DuplicateEntityException если заказ с таким id уже существует
 */
public void saveOrder(Order order) {
    Objects.requireNonNull(order, "order");
    validateOrder(order);
    if (order.getId() != null && repository.exists(order.getId())) {
        throw new DuplicateEntityException("Order already exists: " + order.getId());
    }
    repository.save(order);
    eventPublisher.publish(new OrderCreatedEvent(order));
}
```

## Связь с SOLID и паттернами: краткая сводка

## Дополнительные примеры: Optional вместо null

```java
// Плохо: возврат null
public User findUserById(Long id) {
    return repository.findById(id).orElse(null);
}
// вызывающий код вынужден проверять null

if (u != null) { ... }

// Лучше: Optional
public Optional<User> findUserById(Long id) {

}
// вызывающий код явно обрабатывает отсутствие
findUserById(1L).ifPresent(u -> ...);
User u = findUserById(1L).orElseThrow(() -> new EntityNotFoundException("User not found: 1"));
```


## Дополнительные примеры: стримы и читаемость

```java
// Плохо: длинная цепочка без имени

    .filter(o -> o.getStatus() == OrderStatus.ACTIVE && o.getTotal().compareTo(BigDecimal.ZERO) > 0)
    .map(Order::getId)
    .collect(Collectors.toList());

List<Long> ids = orders.stream()
    .filter(this::isActiveOrderWithPositiveTotal)
    .map(Order::getId)

    return o.getStatus() == OrderStatus.ACTIVE && o.getTotal().compareTo(BigDecimal.ZERO) > 0;
}
```

## Дополнительные примеры: логирование на границах

```java
// Плохо: логирование в глубине бизнес-логики
public void processOrder(Order order) {

    order.setStatus(OrderStatus.PROCESSING);
    repository.save(order);
    log.debug("Saved order {}", order.getId());
    eventPublisher.publish(new OrderProcessedEvent(order));
    log.debug("Published event for order {}", order.getId());
}

// Лучше: логирование на границе (вход/выход/ошибка)
public void processOrder(Order order) {
    log.info("Processing order {}", order.getId());
    try {
        markOrderAsProcessing(order);
        repository.save(order);
        eventPublisher.publish(new OrderProcessedEvent(order));
        log.info("Order {} processed successfully", order.getId());
    } catch (Exception e) {
        log.error("Failed to process order {}", order.getId(), e);
        throw new OrderProcessingException("Failed to process order: " + order.getId(), e);
    }
}
```

## Решение проблем

- **Сложно читать код** — применить правила именования и короткие функции из раздела «Лучшие практики»; разбить длинные методы.
- **Дублирование** — вынести общую логику в отдельный метод или утилитный класс; проверить связь с SOLID.
- **Сложно тестировать** — уменьшить связность, внедрять зависимости через конструктор; см. раздел по обработке ошибок.

## Частые вопросы

- **Когда писать комментарий?** Когда объясняете «почему», а не «что»; для публичного API — **Javadoc**.
- **Какой длины должны быть функции?** Короче лучше; один уровень абстракции внутри функции; при необходимости — разбить на подфункции.
- **См. также:** разделы «Именование», «Функции», «Комментарии» и «Лучшие практики» в документе.
