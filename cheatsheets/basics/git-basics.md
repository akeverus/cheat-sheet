## Основные команды

- **Инициализация и клонирование**
  - `**git init**` — создать репозиторий.
  - `**git clone** <**url**>` — клонировать удалённый репозиторий.

- **Состояние и коммиты**
  - `**git status**` — текущее состояние (**ветка, изменения**).
  - `**git add** <**file**>` / `**git add** .` — добавить файлы в индекс.
  - `**git commit** -m "**message**"` — зафиксировать коммит.
  - `**git log** --**oneline**` — краткая история коммитов.

- **Удалённый репозиторий**
  - `**git remote** -v` — список **remote**.
  - `**git fetch origin**` — забрать изменения без слияния.
  - `**git pull origin main**` — **fetch** + **merge** в текущую ветку.
  - `**git push origin main**` — отправить коммиты в **origin**.


## Ветки и слияние

- **Создание и переключение**
  - `**git branch feature-x**` — создать ветку.
  - `**git checkout feature-x**` / `**git switch feature-x**` — переключиться.
  - `**git checkout** -b **feature-x**` / `**git switch** -c **feature-x**` — создать и переключиться.

- **Слияние**
  - `**git merge other-branch**` — влить другую ветку в текущую.
  - Обычно создаётся **merge**-коммит (**если не fast-forward**).


## **Merge** и **Rebase**

- **Merge** — сохраняет историю «как было»: создаётся коммит слияния, ветки не переписываются.
- **Rebase** — переносит коммиты текущей ветки «поверх» другой, история линейная, но хеши меняются.

```bash
# Текущая ветка feature, хотим подтянуть main
git checkout feature
git rebase main   # коммиты feature переиграются поверх main
# После rebase: git push --force-with-lease (если feature уже пушили)
```

- **Rebase на общую ветку** переписывает историю; в общих ветках (**main, develop**) обычно используют **merge**. **Rebase** — для локальной очистки истории перед **merge**.


## Конфликты и отмена

- **Конфликты при merge/rebase**
  - В файлах появятся маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
  - Исправить вручную, затем `**git add**` и `**git commit**` (**merge**) или `**git rebase** --**continue**` (**rebase**).
  - Отмена **merge**: `**git merge** --**abort**`. Отмена **rebase**: `**git rebase** --**abort**`.

- **Отмена изменений**
  - `**git checkout** -- <**file**>` / `**git restore** <**file**>` — откатить изменения в файле (**до последнего коммита**).
  - `**git reset** --**soft HEAD**~1` — убрать последний коммит, оставив изменения в индексе.
  - `**git reset** --**hard HEAD**~1` — убрать последний коммит и изменения (**осторожно**).


## Типовой **workflow**

1. Обновить основную ветку: `**git checkout main** && **git pull**`.
2. Создать ветку для задачи: `git checkout -b feature-xxx`.
3. Делать коммиты: `**git add**`, `**git commit** -m "описание"`.
4. Периодически подтягивать **main**: `git merge main` или `git rebase main`.
5. Отправить ветку: `git push -u origin feature-xxx`.
6. Создать **Pull Request** / **Merge Request**, пройти ревью, смержить в **main**.
7. После **merge** удалить ветку: локально `git branch -d feature-xxx`, на сервере — через интерфейс или `git push origin --delete feature-xxx`.


## Лучшие практики

- Осмысленные сообщения коммитов: что и зачем изменено.
- Маленькие атомарные коммиты: проще ревью и откат.
- Не коммитить лишнее: использовать `.**gitignore**`; секреты — в переменных окружения или **vault**.
- В общих ветках не делать **force-push**; в личных ветках — при необходимости `**git push** --**force-with-lease**`.


## Рабочая директория, индекс и репозиторий

**Git** хранит три уровня состояния файлов:

1. **Working directory** — файлы на диске, которые вы редактируете.
2. **Staging area (**index**)** — то, что попало в `**git add**` и будет в следующем коммите.
3. **Repository (**HEAD**)** — зафиксированные коммиты.

```bash
# Посмотреть разницу между рабочей директорией и индексом
git diff

# Разница между индексом и последним коммитом
git diff --staged

# Разница между двумя коммитами
git diff commit1 commit2
```


## .gitignore

Файл `.gitignore` задаёт шаблоны файлов и каталогов, которые **Git** не отслеживает. Синтаксис: одна строка — один шаблон; `#` — комментарий; `*` — любое количество символов; `?` — один символ; `**/` — любой уровень вложенности.

```gitignore
# Сборки и артефакты
target/
build/
*.class
*.jar
*.war

# IDE
.idea/
*.iml
.vscode/

# Логи и временные файлы
*.log
tmp/
temp/

# Секреты (никогда не коммитить)
.env
*.pem
secrets/
```

После добавления правил в `.**gitignore**` уже отслеживаемые файлы нужно убрать из индекса: `**git** rm --**cached** <**file**>` (**файл останется на диске**).


## Просмотр истории и различий

```bash
# Краткий лог (одна строка на коммит)
git log --oneline

# Лог с графом веток
git log --oneline --graph --all

# Лог с патчем (diff) последнего коммита
git show HEAD

# Лог по файлу
git log --follow -- path/to/file

# Кто последний менял каждую строку файла
git blame path/to/file
```


## Теги (**tags**)

Теги фиксируют точку в истории (**например, релиз**). Теги бывают **lightweight** (**просто указатель на коммит**) и **annotated** (**с сообщением и метаданными**).

```bash
# Создать lightweight тег
git tag v1.0.0

# Создать annotated тег (рекомендуется для релизов)
git tag -a v1.0.0 -m "Release 1.0.0"

# Список тегов
git tag -l

# Переключиться на тег (detached HEAD)
git checkout v1.0.0

# Отправить теги на remote
git push origin v1.0.0
git push origin --tags
```


## **Stash** (**временное сохранение изменений**)

Когда нужно переключиться на другую ветку, но не коммитить текущие изменения, используют **stash**.

```bash
# Сохранить изменения в stash (включая неотслеживаемые опционально)
git stash
git stash push -m "WIP: feature X"

# Список stash
git stash list

# Применить последний stash и удалить его из списка
git stash pop

# Применить stash, но оставить в списке
git stash apply

# Применить конкретный stash
git stash apply stash@{1}

# Удалить stash
git stash drop stash@{0}
git stash clear
```


## **Cherry-pick**

Перенос одного или нескольких коммитов из одной ветки в другую без слияния всей ветки.

```bash
# Взять коммит по хешу и применить к текущей ветке
git cherry-pick <commit-hash>

# Взять несколько коммитов
git cherry-pick commit1 commit2

# Cherry-pick без автоматического коммита (оставить изменения в индексе)
git cherry-pick -n <commit-hash>
git cherry-pick --no-commit <commit-hash>

# При конфликте: разрешить, затем
git add .
git cherry-pick --continue
# Или отменить: git cherry-pick --abort
```


## **Revert** (**отмена коммита новым коммитом**)

**Revert** создаёт новый коммит, который отменяет изменения указанного коммита. История не переписывается — безопасно для общих веток.

```bash
# Отменить последний коммит
git revert HEAD

# Отменить конкретный коммит
git revert <commit-hash>

# Revert без автоматического коммита (оставить изменения в индексе)
git revert -n <commit-hash>
```


## **Reflog**

**Reflog** хранит историю перемещений **HEAD** и ссылок (**checkout, reset, merge, rebase**). Полезно для восстановления «потерянных» коммитов после ошибочного **reset** или удаления ветки.

```bash
# Показать reflog для HEAD
git reflog

# Показать reflog для ветки
git reflog feature-branch

# Восстановить ветку на коммит из reflog
git reset --hard HEAD@{1}
```


## **Reset**: **soft**, **mixed**, **hard**

- **git reset --soft `HEAD`~1** — убрать последний коммит; изменения остаются в индексе (**staged**). Можно сразу закоммитить заново с другим сообщением.
- **git reset --mixed `HEAD`~1** (**по умолчанию**) — убрать последний коммит; изменения остаются в рабочей директории, но не в индексе.
- **git reset --hard `HEAD`~1** — убрать последний коммит и все изменения; рабочая директория и индекс приводятся к состоянию предыдущего коммита. **Опасно:** непоправимо удаляет незакоммиченные изменения.

```bash
# Откатить последний коммит, оставив изменения в индексе
git reset --soft HEAD~1

# Откатить последний коммит, оставив изменения в рабочей директории
git reset HEAD~1

# Полностью откатить к коммиту (осторожно)
git reset --hard <commit-hash>
```


## **Amend** (**исправить последний коммит**)

Добавить забытые файлы в последний коммит или изменить сообщение коммита.

```bash
# Добавить изменения в индекс и «дописать» в последний коммит
git add forgotten-file.txt
git commit --amend --no-edit

# Изменить только сообщение последнего коммита
git commit --amend -m "New message"

# После amend уже пушили? Нужен force-push (только в личной ветке)
git push --force-with-lease
```


## Интерактивный **rebase** (**rebase -i**)

Позволяет переписать историю: объединить коммиты, изменить порядок, изменить сообщения, удалить коммиты.

```bash
# Редактировать последние 3 коммита
git rebase -i HEAD~3
```

**В редакторе для каждого коммита можно указать действие:**
- **pick** — оставить как есть
- **reword** — оставить коммит, но изменить сообщение
- **edit** — остановиться для правок (**можно изменить файлы и сделать amend**)
- **squash** — объединить с предыдущим коммитом, сообщения объединятся
- **fixup** — объединить с предыдущим, сообщение предыдущего сохранится
- **drop** — удалить коммит

После сохранения **Git** применяет коммиты по порядку. При конфликтах: разрешить, `**git add**`, затем `**git rebase** --**continue**`. Отмена: `**git rebase** --**abort**`.


## Удалённые репозитории (**remote**)

```bash
# Список remote
git remote -v

# Добавить remote
git remote add origin https://github.com/user/repo.git

# Изменить URL remote
git remote set-url origin https://github.com/user/repo.git

# Забрать изменения без слияния
git fetch origin

# Забрать и смержить в текущую ветку
git pull origin main

# Отправить ветку и установить upstream
git push -u origin feature-branch

# Удалить удалённую ветку
git push origin --delete feature-branch
```


## Стратегии ветвления

**Git `Flow`:** ветки `**main**` (**продакшен**), `**develop**` (**интеграция**), фичи — от `**develop**`, релизы — от `**develop**`, хотфиксы — от `**main**`. Сложнее, подходит для релизов по версиям.

**GitHub `Flow`:** одна основная ветка `**main**`, фичи — в отдельных ветках, **merge** через **Pull Request**. Проще, подходит для непрерывного деплоя.

**Trunk-`Based Development`:** минимум веток, короткоживущие фичи, частые коммиты в **main**. Требует сильной культуры тестов и **feature flags**.


## Разрешение конфликтов при **merge**

**При конфликте **Git** помечает файлы маркерами:**

```text
<<<<<<< HEAD
код из текущей ветки
=======
код из вливаемой ветки
>>>>>>> branch-name
```

Действия: открыть файл, оставить нужный вариант (**или объединить вручную**), удалить маркеры, затем:

```bash
git add conflicted-file.txt
git commit -m "Resolve merge conflict"
```


## Разрешение конфликтов при **rebase**

**Во время **rebase** конфликты разрешаются для каждого коммита по очереди:**

```bash
# После правки файлов
git add .
git rebase --continue

# Пропустить коммит (если решите его убрать)
git rebase --skip

# Отменить rebase полностью
git rebase --abort
```


## **Bisect** (**поиск коммита, внесшего баг**)

Бинарный поиск по истории: помечаете коммит как «хороший» и «плохой», **Git** переключает на средний коммит; вы тестируете и помечаете **good**/**bad**, пока не найдёте первый плохой коммит.

```bash
git bisect start
git bisect bad HEAD
git bisect good <known-good-commit>

# После переключения: проверить, есть ли баг
git bisect good   # или git bisect bad

# В конце
git bisect reset
```

Можно автоматизировать: `git bisect run <test-script>`.


## **Hooks** (**перехватчики событий**)

Скрипты в `.git/hooks/`, выполняемые при определённых событиях. Примеры: `**pre-commit**` (**проверка перед коммитом**), `**commit-msg**` (**проверка формата сообщения**), `**pre-push**` (**проверки перед push**). Имена без расширения; файл должен быть исполняемым.

```bash
# Пример pre-commit: запуск линтера
#!/bin/sh
npm run lint
```

Управление через инструменты (**Husky, pre-commit**) позволяет хранить скрипты в репозитории и устанавливать их при клонировании.

## Часто задаваемые вопросы

**Чем отличаются merge и rebase?**
**Merge** создаёт коммит слияния и сохраняет историю обеих веток. **Rebase** переносит коммиты одной ветки поверх другой, история становится линейной, но хеши коммитов меняются. **Rebase** не используют для общих веток (**main, develop**), чтобы не переписывать историю для всех.

**Когда использовать `force-push`?**
Только в своей личной ветке после **rebase** или **amend**. Предпочтительно `**git push** --**force-with-lease**`, чтобы не перезаписать чужие коммиты, если кто-то успел запушить в ту же ветку.

**Как откатить уже запушенный коммит?**
Если коммит ещё не в общей ветке — можно сделать **reset** и **force-push** (**в личной ветке**). Если уже в **main** — безопаснее `**git revert**`, создав новый коммит, отменяющий изменения.

**Что делать при конфликте при pull?**
Разрешить конфликты в файлах, затем `**git add**` и `**git commit**` (**pull уже создал merge-коммит при конфликте**) или при **pull** с **rebase** — `**git add**` и `**git rebase** --**continue**`.

**Как удалить ветку локально и на remote?**
Локально: `**git branch** -d **branch-name**` (**или `-D` для принудительного удаления**). На **remote**: `**git push origin** --**delete branch-name**`.

## Сообщения коммитов (**соглашения**)

Распространённый формат: краткий заголовок (**до 50 символов**) + при необходимости тело коммита.

- **Conventional `Commits`:** тип(**область**): описание. Типы: **feat**, **fix**, **docs**, **style**, **refactor**, **test**, **chore**. Пример: `**feat(**auth**): **add OAuth2 login**`.
- **Imperative mood:** «**Add feature**» вместо «**Added feature**».
- В теле коммита — зачем сделано изменение, а не что именно изменено (**что видно в diff**).


## Безопасность и секреты

- Никогда не коммитить пароли, ключи **API**, токены. Использовать переменные окружения или секрет-хранилища (**Vault, `AWS Secrets` Manager**).
- Проверять `.**gitignore**` перед первым коммитом; при утечке — ротировать секреты и при необходимости очистить историю (**git `filter-branch` или `BFG Repo-Cleaner`; осторожно, переписывает историю**).

## Сравнение с другими системами контроля версий

**Централизованные (**SVN**, **Perforce**):** один сервер, клиенты получают только последние версии файлов. Коммит требует доступа к серверу. В **Git** каждый клон — полная копия истории; работа офлайн возможна; коммиты локальные, синхронизация через **push**/**pull**.

**Распределённость Git:** при падении сервера любой клон может стать новым «источником правды». Ветвление и слияние — быстрые локальные операции.


## **Pull Request** / **Merge Request** (**workflow**)

1. Разработчик пушит ветку в свой **fork** или в общий репозиторий.
2. Создаётся **Pull Request** (**GitHub**) или **Merge Request** (**GitLab**) из ветки в целевую (**например main**).
3. `CI` запускает проверки (**сборка, тесты, линтеры**).
4. Ревьюеры оставляют комментарии; автор вносит правки и пушит в ту же ветку.
5. После одобрения и прохождения `CI` выполняется **merge** (**squash, merge commit или rebase — по настройкам репозитория**).
6. Ветка удаляется; при необходимости основная ветка обновляется у всех через **pull**.


## **Merge strategies**

- **Fast-forward:** если целевая ветка не ушла вперёд, указатель просто перемещается на конец вливаемой ветки. История линейная.
- **Merge commit:** создаётся коммит слияния с двумя родителями. Сохраняется полная история веток.
- **Squash merge:** все коммиты вливаемой ветки объединяются в один коммит при **merge**. История проще, но теряется детализация коммитов ветки.

```bash
# Запретить fast-forward (всегда создавать merge-коммит)
git merge --no-ff feature-branch

# Создать squash merge
git merge --squash feature-branch
git commit -m "Squash merge feature X"
```


## Восстановление после ошибок

**Случайно закоммитили в не ту ветку:**
Создать правильную ветку от текущего состояния: `**git branch correct-branch**`. Откатить текущую ветку: `git reset --hard HEAD~1`. Переключиться на **correct-branch** и продолжить работу.

**Случайно сделали commit в main вместо feature:**
`**git branch feature-branch**` (**создать ветку от текущего main**). `git reset --hard origin/main` (**откатить main к состоянию на сервере**). `**git checkout feature-branch**` — коммит останется в **feature-branch**.

**Потеряли коммиты после reset:**
`**git reflog**` — найти хеш нужного коммита. `**git checkout** -b **recovered-branch** <**hash**>` или `**git reset** --**hard** <**hash**>`.

## Ограничения и хорошие практики

- **Не коммитить большие бинарные файлы** (**артефакты сборки, медиа**) — использовать **LFS** или внешнее хранилище.
- **Не переписывать историю общих веток** — не делать **force-push** в **main**/**develop**.
- **Делать атомарные коммиты** — один коммит = одна логическая правка; проще ревью и откат.
- **Проверять статус перед коммитом** — `**git status**`, `**git diff**` чтобы не закоммитить лишнее.


## Интеграция с CI/CD

Типичный сценарий: при **push** в ветку или при создании `PR` запускается пайплайн (**сборка, тесты, деплой в тест**). **Merge** в **main** запускает деплой в прод. В **Git** хранятся только исходники; секреты и переменные окружения задаются в `CI`, не в репозитории.

## Конфликтные маркеры и стратегия **diff3**

При конфликте по умолчанию в файле показываются две версии (**текущая и вливаемая**). Опция `**merge.conflictStyle diff3**` добавляет третью версию — общий предок, что упрощает понимание конфликта.

```bash
git config merge.conflictStyle diff3
```

**В файле появятся маркеры:**
```text
<<<<<<< HEAD
текущая версия
||||||| merged common ancestors
общий предок
=======
вливаемая версия
>>>>>>> branch-name
```


## Подпись коммитов (**GPG**)

Проверка подлинности автора коммита. Настраивается ключ **GPG**, в **Git** указывается **key** `ID`; при коммите с опцией `-S` коммит подписывается.

```bash
# Указать ключ для подписи
git config --global user.signingkey <key-id>

# Подписать последний коммит
git commit --amend -S --no-edit

# Требовать подпись коммитов
git config commit.gpgsign true
```

- `**git status**` — что именно попадает в коммит.

## Отмена **merge** (**до push**)

**Если **merge** сделали по ошибке и ещё не пушили:**

```bash
git reset --hard HEAD~1
```

Внимание: это удалит **merge**-коммит и вернёт ветку к состоянию до **merge**. Если уже запушили — безопаснее откатывать через **revert merge**-коммита.


## **Revert merge**-коммита

**У **merge**-коммита два родителя. При **revert** нужно указать, какую линию сохранять (**обычно основную ветку**):**

```bash
git revert -m 1 <merge-commit-hash>
```

`-m 1` означает «оставить первого родителя» (**обычно main**). Создаётся новый коммит, отменяющий изменения, привнесённые **merge**.

## Очистка устаревших ссылок на удалённые ветки

**После удаления веток на сервере локальные ссылки `origin/branch-name` остаются до следующего **fetch** с опцией **prune**:**

```bash
git fetch origin --prune
# или
git remote prune origin
```


## Создание «пустой» ветки (**без истории**)

**Иногда нужна ветка без общей истории (**например, для документации или статического сайта**):**

```bash
git checkout --orphan new-branch
git rm -rf .
# Добавить нужные файлы и закоммитить
git add .
git commit -m "Initial commit"
```


## Слияние без автоматического коммита

**Чтобы смержить ветку, но оставить изменения в индексе (**например, для доработки перед одним общим коммитом**):**

```bash
git merge --no-commit --no-ff feature-branch
# Проверить, доработать, затем
git commit -m "Merge feature X"
```

## Дополнительные вопросы для собеседования

**Что такое detached `HEAD`?**
Состояние, когда **HEAD** указывает на конкретный коммит, а не на ветку. Коммиты, сделанные в этом состоянии, не будут привязаны к ветке и могут «потеряться», если переключиться на ветку без создания новой ветки от этого коммита.

**Чем отличается git pull от git fetch + merge?**
`**git pull**` = `**git fetch**` + `**git merge**` (**или rebase, если настроено**). То есть **pull** забирает изменения и сразу сливает их в текущую ветку.

**Что такое origin?**
Имя удалённого репозитория по умолчанию, которое **Git** присваивает при клонировании. Можно добавить другие **remote** (**например upstream для fork**).

**Как откатить один файл к состоянию из другого коммита?**
`git checkout <commit-hash> -- <file>` или `git restore --source=<commit-hash> <file>`. Файл будет в рабочей директории и в индексе.

## Дополнительные сценарии (**продолжение**)

**Восстановить файл из stash:**
`git stash show -p stash@{0} | git apply` — применить патч из **stash** без удаления **stash**. Или `git checkout stash@{0} -- path/to/file` — восстановить только один файл из **stash**.

**Переименовать ветку на remote:**
Локально: `**git branch** -m **old-name new-name**`. Удалить старую на **remote**: `**git push origin** --**delete old-name**`. Запушить новую: `**git push** -u **origin new-name**`.

**Сравнить два коммита по файлам:**
`**git diff** --**name-status commit1 commit2**` — список файлов с статусом (**A/M/D и т.д.**).

**Показать, кто изменил каждую строку файла (**с датой**):**

**Найти ветку, содержащую коммит:**
`**git branch** -a --**contains** <**commit-hash**>`.

**Удалить все локальные ветки, кроме текущей и main:**
`**git branch** | **grep** -v "**main**\|*" | **xargs git branch** -D` (**осторожно: удалит все перечисленные ветки**).

**Показать разницу между рабочим деревом и конкретным коммитом:**
`git diff <commit-hash>`.

**Сбросить один файл к состоянию из другого коммита:**
`git checkout <commit-hash> -- <file>` или `git restore --source=<commit-hash> <file>`.

## Дополнительные вопросы для собеседования

**Что такое `HEAD`?**
**HEAD** — указатель на текущий коммит (**или на ветку, которая указывает на коммит**). В **detached HEAD HEAD** указывает напрямую на коммит.

**Что такое `fast-forward` merge?**
Когда целевая ветка не получила новых коммитов после ответвления, указатель ветки просто перемещается вперёд на конец вливаемой ветки. **Merge**-коммит не создаётся.

**Зачем нужен git fetch?**
**Fetch** забирает изменения с **remote** в локальные ссылки (**origin/main и т.д.**), но не меняет рабочую директорию и текущую ветку. Позволяет посмотреть изменения перед **merge**/**rebase**.

**Что такое upstream?**
**Upstream** — удалённая ветка, с которой связана локальная (**при push/pull**). Устанавливается при первом **push** с `-u`: `**git push** -u **origin feature**`.

**Как откатить push (**если коммит уже в **remote**)?**
В общих ветках — только через **revert** (**создать новый коммит, отменяющий изменения**). В личной ветке — **reset** и **force-push**, если никто не успел подтянуть ветку.

**Что такое squash при merge?**
Все коммиты вливаемой ветки объединяются в один коммит. История упрощается, но теряется детализация коммитов ветки. Часто используется в **PR/MR**.

## Дополнительные сценарии: конфликты

**Конфликт при merge:**
Открыть файл, найти маркеры `<<<<<<<`, `=======`, `>>>>>>>`, оставить нужный код или объединить вручную, удалить маркеры. Затем `**git add file**` и `**git commit**`.

**Конфликт при rebase:**
Разрешить конфликт в файлах, `**git add**`, затем `**git rebase** --**continue**`. Если нужно пропустить коммит — `**git rebase** --**skip**`. Отменить весь **rebase** — `**git rebase** --**abort**`.

**Конфликт при `cherry-pick`:**
Разрешить конфликт, `**git add**`, затем `**git cherry-pick** --**continue**`. Отменить — `**git cherry-pick** --**abort**`.

## Решение проблем

- **Конфликты при merge/rebase** — разрешить вручную в указанных файлах, затем `git add` и продолжить (`git merge --continue` / `git rebase --continue`); см. раздел «Конфликты и отмена».
- **Потерянный коммит** — найти хеш через `git reflog`, затем `git checkout <hash>` или `git reset --hard <hash>`; см. «reflog» и «Восстановление».
- **Случайный коммит не в ту ветку** — перенести коммит через `git cherry-pick` или откатить и закоммитить в нужной ветке; см. «Типовой workflow».

## Частые вопросы

- **Когда использовать merge, а когда rebase?** Merge сохраняет историю веток; rebase даёт линейную историю (предпочтительно для локальных веток перед push).
- **Как отменить последний коммит?** `git reset --soft HEAD~1` — оставить изменения в индексе; `--mixed` — оставить в рабочей директории; `--hard` — отбросить.
