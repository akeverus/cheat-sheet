## Введение

Лучшие практики логирования помогают строить эффективную систему логирования для отладки, наблюдаемости и соответствия требованиям.

### Основные принципы

1. **Логи для людей и машин** — понятные сообщения плюс структурированные поля (key-value, JSON) для парсинга.
2. **Уровни по назначению** — ERROR для сбоев, WARN для рисков, INFO для важных событий, DEBUG/TRACE только для отладки.
3. **Консистентность формата** — единые шаблоны сообщений и полей в рамках проекта.

Пример:

```java
// Плохо
logger.error("Error occurred");

// Хорошо
logger.error("Failed to process payment for user {}: payment method {} invalid",
             userId, paymentMethod, exception);

// Структурированно (если используется API с key-value)
logger.error("Payment processing failed", kv("userId", userId), kv("paymentMethod", paymentMethod), kv("errorCode", e.getCode()));
```

## Принципы эффективного логирования

### Читаемость

Избегать голого техжаргона; формулировать так, чтобы по сообщению можно было понять, что произошло и в каком контексте.

```java
// Плохо
logger.info("HTTP POST /api/v1/users with payload size 2048 bytes returned 201");

// Хорошо
logger.info("New user registration completed", kv("endpoint", "/api/v1/users"), kv("responseCode", 201));
```

### Полнота

Включать идентификаторы запроса, пользователя, сущности (requestId, userId, orderId и т.д.), чтобы можно было связать логи одной операции.

```java
logger.info("Creating order", kv("userId", userId), kv("requestId", requestId), kv("itemCount", request.getItems().size()));
```

### Эффективность

Не засорять INFO лишними деталями; детали — в DEBUG. Не выполнять тяжёлые операции ради лога, если уровень отключён.

## Уровни логирования

### ERROR

Использовать для: сбоев системы, ошибок целостности данных, отказов внешних сервисов, критических ошибок конфигурации. Всегда передавать исключение последним аргументом: `logger.error("...", e)`.

### WARN

Использовать для: деградации (retry, fallback), устаревшего API, необычных, но обработанных ситуаций (например, устаревшие данные в кеше).

### INFO

Использовать для: важных бизнес-событий (регистрация, заказ, платёж), смены состояния системы, старта/остановки компонентов. Не дублировать каждый мелкий шаг.

### DEBUG и TRACE

Только для отладки. В production обычно отключены. TRACE — максимальная детализация (например, вход/выход методов, параметры).

## Форматирование и структура

### Консистентные шаблоны

Определить в проекте шаблоны для типов событий (например: "User {} performed {}", "Order {} created for user {}") и придерживаться их.

### Структурированное логирование (JSON / key-value)

В микросервисах и при сборе в централизованные системы удобен JSON или key-value: удобный поиск и метрики по полям.

```java
logger.info("Business event", kv("eventId", event.getId()), kv("eventType", event.getType()), kv("userId", event.getUserId()));
```

### MDC (Mapped Diagnostic Context)

Использовать MDC для requestId, userId, correlationId и т.д.; очищать в finally или в фильтре после обработки запроса, чтобы не утекал контекст в thread pool.

```java
        MDC.put("requestId", requestId);
        MDC.put("userId", userId);
try {
    // ...
        } finally {
    MDC.clear();
}
```

## Контекст и корреляция

- **Request-scoped:** в веб-приложении устанавливать requestId (из заголовка или сгенерировать) и при необходимости userId/sessionId в начале цепочки и очищать в конце.
- **Distributed tracing:** интегрировать traceId/spanId (например, OpenTelemetry) и при необходимости прокидывать их в MDC, чтобы логи связывались со span’ами.

## Производительность

- **Guard clauses:** для тяжёлой подготовки аргументов использовать `if (logger.isDebugEnabled()) { logger.debug("...", expensive()); }` или параметризованный вызов (SLF4J не вычисляет аргументы при отключённом уровне).
- **Async logging:** в нагруженных приложениях использовать AsyncAppender (Logback) или аналог, чтобы не блокировать поток приложения.
- **Сэмплирование:** при очень частых логах одного типа можно логировать каждый N-й или по времени, сохраняя ERROR/WARN без сэмплирования.

Пример AsyncAppender (Logback):

```xml
    <appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
        <discardingThreshold>20</discardingThreshold>
        <queueSize>512</queueSize>
    <appender-ref ref="FILE"/>
    </appender>
```

## Безопасность

### Защита чувствительных данных

Не логировать пароли, токены, полные номера карт, PII в открытом виде. Маскировать (например, последние 4 цифры карты), логировать только длину или хеш там, где нужно.

```java
logger.info("Payment processed", kv("amount", amount), kv("maskedCard", "***" + cardLast4));
```

### Защита от log injection

Санитизировать пользовательский ввод перед записью в лог: удалять переводы строк (`\n`, `\r`) и управляющие символы, чтобы злоумышленник не подменял строки в логе.

```java
String safe = message.replaceAll("[\\r\\n\\x00-\\x1F]", " ");
logger.info(safe, args);
```

## Тестирование и мониторинг

- **Unit-тесты логов:** при необходимости проверять, что при определённых действиях пишется ожидаемый уровень и сообщение (например, через ListAppender в Logback).
- **Метрики по логам:** считать количество ERROR/WARN по логгерам или тегам и строить алерты при превышении порога.
- **Алертинг:** настраивать алерты на паттерны в логах (например, "Database connection failed", серия "Authentication failed") и на рост частоты ошибок.

## Антипаттерны

1. **Неинформативные сообщения** — "Error!", "Done". Нужны контекст и идентификаторы.
2. **Логирование чувствительных данных** — пароли, токены, полные карты.
3. **Производительность** — конкатенация строк в цикле, тяжёлые операции в аргументах без проверки уровня.
4. **Неправильные уровни** — ERROR для "user not found" (ожидаемая ситуация WARN или INFO); INFO для исключений.
5. **Отсутствие контекста** — сообщение без requestId, userId, orderId и т.д.
6. **Log injection** — запись в лог непроверенного пользовательского ввода с переводами строк.
7. **Синхронное логирование под нагрузкой** — без async appender и без сэмплирования при высокой частоте.
8. **Отсутствие ротации** — один файл без maxHistory/maxFileSize; риск заполнения диска.

Краткие примеры исправлений:

```java
// Плохо
logger.error("Error!");
logger.info("User login", kv("password", password));
logger.debug("User: " + user.toString());

// Хорошо
logger.error("Failed to connect to DB", kv("host", host), exception);
logger.info("User authentication", kv("userId", userId));
if (logger.isDebugEnabled()) logger.debug("User: {}", user.getId());
```

Ротация в Logback:

```xml
    <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
        <fileNamePattern>app.%d{yyyy-MM-dd}.%i.log</fileNamePattern>
        <maxFileSize>100MB</maxFileSize>
        <maxHistory>30</maxHistory>
    </rollingPolicy>
```

## Решение проблем

| Проблема | Причина | Решение |
|----------|---------|---------|
| Слишком много логов в production, сложно искать ошибки | Включен DEBUG/TRACE или избыточный INFO | Поднять уровень для пакетов приложения до INFO; оставить DEBUG только для нужных пакетов; сократить количество INFO-сообщений до ключевых событий |
| Логи из разных запросов перемешаны | Нет requestId/correlationId в логах | Внедрить фильтр/интерцептор: генерировать или брать X-Request-ID, класть в MDC, использовать в pattern (%X{requestId}); очищать MDC после запроса |
| Логи тормозят приложение | Синхронная запись, тяжёлое форматирование | Включить AsyncAppender; убрать конкатенацию и дорогие вызовы в аргументах; проверить, что уровень не слишком низкий (например, не TRACE в prod) |

## Частые вопросы

**Как решить, логировать ли на WARN или ERROR?** ERROR — когда операция не удалась и последствия значимы (сбой платежа, потеря данных, недоступность сервиса). WARN — когда есть fallback, retry или ситуация необычна, но обработана (повторная попытка, устаревшие данные, deprecated API).

**Нужно ли в Java переходить на структурированные (JSON) логи?** Да, если логи собираются в централизованную систему (ELK, Loki, CloudWatch и т.д.) и по ним строят дашборды и алерты. В простых приложениях с просмотром только по файлу достаточно читаемого текстового формата с единым pattern и MDC.

**Как не забыть очищать MDC в асинхронном коде?** В веб-приложении — в фильтре или интерцепторе в блоке finally после chain.doFilter() / выполнения запроса. При ручном использовании — try/finally с MDC.clear(). При передаче задачи в другой поток — копировать нужные ключи MDC в контекст задачи и устанавливать их в целевом потоке, затем очищать после выполнения.
