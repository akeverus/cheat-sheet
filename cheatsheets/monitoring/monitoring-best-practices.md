# Лучшие практики мониторинга

Принципы построения эффективного мониторинга: метрики, алерты, наблюдаемость.

## Введение

Качественный мониторинг позволяет быстро обнаруживать инциденты, анализировать производительность и планировать ресурсы. Ниже — сжатые практики по метрикам, алертингу и организации observability.

## Золотые сигналы

Четыре типа сигналов для мониторинга сервисов:

1. **Latency** — время ответа (медиана, перцентили 95/99).
2. **Traffic** — нагрузка (RPS, запросы в секунду).
3. **Errors** — доля ошибок (4xx, 5xx, исключения).
4. **Saturation** — загрузка ресурсов (CPU, память, диск, очереди).

Дополнительно: availability (доступность) и capacity (насколько далеко до лимитов).


## Метрики и именование

- **Именование**: единый стиль (например, `snake_case`), префикс по домену/сервису.
- **Лейблы**: использовать для размерностей (env, service, instance), не хранить в имени метрики высококардинальные значения (user_id).
- **Типы**: counter (только рост), gauge (текущее значение), histogram/summary (распределение).
- **Избегать**: дублирования метрик, избыточных лейблов, метрик «на каждый запрос» без агрегации.


## Алертинг

- **Алертить на симптомы для пользователя**: недоступность, высокая latency, рост ошибок.
- **Избегать алертов на причины**, которые не требуют немедленного действия (например, «CPU 80%» без контекста).
- **Пороги**: настраивать на основе перцентилей и трендов; использовать дебаунс/окно, чтобы снизить шум.
- **Эскалация**: чёткие владельцы, каналы (Slack, PagerDuty), runbooks для типовых инцидентов.
- **Проверять алерты**: периодически убеждаться, что они срабатывают когда нужно и не дают ложных срабатываний.


## Логи и трейсы

- **Логи**: структурированный формат (JSON), единые поля (timestamp, level, message, trace_id).
- **Не логировать чувствительные данные**: пароли, токены, персональные данные в маске.
- **Трейсы**: единый trace_id по цепочке запросов; связывать логи с трейсами для отладки.
- **Хранение**: политики retention, индексация по полям для быстрого поиска.


## Организация и документация

- **Дашборды**: один дашборд на сервис/домен; верхний уровень — обзор, детали — по клику.
- **Runbooks**: для каждого алерта — что проверить, как эскалировать, типовые решения.
- **Онбординг**: где смотреть метрики, логи, трейсы; кого звать при инциденте.
- **Регулярный пересмотр**: убирать неиспользуемые метрики и алерты, обновлять пороги и документацию.


## Лучшие практики

- Начинать с золотых сигналов и минимального набора алертов; расширять по мере необходимости.
- Хранить конфигурацию мониторинга в коде (IaC) и в репозитории.
- Использовать единый стек (метрики + логи + трейсы) для упрощения расследований.
- Проводить постмортемы после инцидентов и обновлять мониторинг и runbooks.


## Решение проблем

| Симптом | Возможная причина | Решение |
|--------|-------------------|---------|
| Алерты срабатывают слишком часто (alert fatigue) | Слишком жёсткие пороги или алерты на причины, а не симптомы | Пересмотреть пороги; перейти к алертам на симптомы; добавить debounce/окна |
| Дашборды не отображают данные после деплоя | Изменились имена метрик или лейблы | Проверить именование метрик; обновить PromQL-запросы; использовать recording rules |
| Логи занимают слишком много места в хранилище | Избыточный уровень логирования (DEBUG в production) | Настроить уровни логирования; добавить политики retention и ротации |

## Частые вопросы

**С чего начать построение мониторинга с нуля?**
Начните с четырёх золотых сигналов (latency, traffic, errors, saturation) для критичных сервисов. Добавьте структурированные логи и один обзорный дашборд. Расширяйте по мере роста системы.

**Как часто пересматривать алерты?**
После каждого инцидента и раз в квартал. Проверяйте: срабатывают ли алерты вовремя, нет ли ложных срабатываний, актуальны ли пороги и runbooks.

**Нужен ли отдельный мониторинг для инфраструктуры и приложений?**
Да. Инфраструктурные метрики (CPU, память, диск) показывают состояние ресурсов, а метрики приложения (latency, errors) — поведение с точки зрения пользователя. Оба уровня нужны для полной картины.
