# Zipkin

**Zipkin** — открытая распределённая система трейсинга (**distributed tracing**), позволяющая собирать и визуализировать цепочки вызовов между сервисами. Используется для отладки задержек и сбоев в микросервисной и распределённой архитектуре.

## Введение

**Zipkin** — одна из первых открытых систем распределённого трейсинга, изначально разработанная в **Twitter** и переданная в открытую разработку. Система принимает данные о **span**'ах (операциях) и **trace**'ах (цепочках вызовов), хранит их и предоставляет веб-интерфейс для поиска и анализа.

Зачем использовать **Zipkin**: понимание потока запроса между сервисами, поиск узких мест по задержкам, анализ ошибок в распределённых сценариях. **Zipkin** поддерживает несколько форматов приёма данных (**HTTP**, **Kafka**, **Scribe**), что упрощает интеграцию с разными стеками. Современный подход — отправлять трейсы через **OpenTelemetry** или **Micrometer Tracing**, а **Zipkin** использовать как бэкенд хранения и визуализации.


## Архитектура Zipkin

**Zipkin** состоит из нескольких компонентов, которые в минимальной конфигурации могут быть объединены в один процесс (**all-in-one**), а в production — разнесены для масштабирования.

**Reporter** (в приложении) отправляет **span**'ы в **Zipkin** по **HTTP** или через **Kafka**. **Zipkin Server** принимает трейсы, по умолчанию хранит их в памяти (подходит только для разработки) или в внешнем хранилище: **Elasticsearch**, **Cassandra**, **MySQL**. **Zipkin UI** встроен в тот же сервер и позволяет искать трейсы по имени сервиса, длительности, тегам и просматривать дерево **span**'ов.

Ключевые понятия: **trace** — целый запрос, проходящий через несколько сервисов; **span** — одна операция (например, HTTP-вызов или запрос к БД) с временем начала и окончания, именем и тегами; **trace ID** и **span ID** связывают **span**'ы в одну цепочку. Контекст (**trace ID**, **span ID**) передаётся между сервисами через заголовки (**B3**, **W3C Trace Context**), чтобы дочерние вызовы могли быть привязаны к родительскому **span**'у.


## Установка и запуск

Самый простой способ — запустить **Zipkin** в режиме **all-in-one** с хранением в памяти. Через **Java**:

```bash
curl -sSL https://zipkin.io/quickstart.sh | bash -s
java -jar zipkin.jar
```

Через **Docker**:

```bash
docker run -d -p 9411:9411 openzipkin/zipkin
```

После запуска веб-интерфейс доступен по адресу `http://localhost:9411`. Для production рекомендуется настроить постоянное хранилище (**Elasticsearch** или **Cassandra**) и при необходимости разнести компоненты (приём, хранение, **UI**).


## Инструментация приложений

Приложение должно создавать **span**'ы для ключевых операций (входящий HTTP, вызовы к БД, вызовы других сервисов) и отправлять их в **Zipkin**. Идентификаторы **trace** и **span** передаются по цепочке вызовов (заголовки **B3** или **W3C Trace Context**), чтобы **Zipkin** мог собрать единый трейс.

Ручная инструментация возможна через библиотеки **Brave** (оригинальный клиент **Zipkin**) или через **OpenTelemetry** **API** с экспортером в **Zipkin**. Предпочтительный современный путь — использовать **OpenTelemetry** или **Micrometer Tracing**, а в **Zipkin** отправлять данные через соответствующий экспортёр, чтобы не привязываться к конкретному бэкенду.


## OpenTelemetry и Zipkin

**OpenTelemetry** предоставляет единый **API** и **SDK** для создания трейсов; экспортер **Zipkin** отправляет **span**'ы в **Zipkin** в нужном формате. Таким образом, приложение инструментируется один раз (**OpenTelemetry**), а бэкендом может быть **Zipkin**, **Jaeger** или другой коллектор.

Пример настройки экспортера **Zipkin** для **OpenTelemetry Java**: указать endpoint **Zipkin** (например, `http://localhost:9411/api/v2/spans`) в конфигурации **OTLP** или использовать **Zipkin** exporter напрямую. **OpenTelemetry Collector** также может принимать **OTLP** и пересылать данные в **Zipkin**, что даёт гибкость в маршрутизации и буферизации.


## Spring Boot и Zipkin

В **Spring Boot 2** часто использовался **Spring Cloud Sleuth** с экспортом в **Zipkin** (зависимости `spring-cloud-starter-sleuth`, `spring-cloud-sleuth-zipkin`). В **Spring Boot 3** рекомендуется **Micrometer Tracing** с bridge в **OpenTelemetry** или прямой экспорт в **Zipkin** через **Micrometer** **Zipkin** reporter.

Настройка сводится к добавлению зависимостей (`micrometer-tracing-bridge-brave`, `micrometer-registry-prometheus` при необходимости) и указанию в `application.yml` адреса **Zipkin** (`management.zipkin.tracing.endpoint` или аналог для **Brave**). После этого входящие HTTP-запросы и вызовы через типичные клиенты (**RestTemplate**, **WebClient**, **JPA**) автоматически попадают в трейсы при наличии соответствующих автоинструментаций.


## Zipkin UI и анализ трейсов

В веб-интерфейсе **Zipkin** можно искать трейсы по имени сервиса, длительности, времени, тегам и **trace ID**. Выбрав трейс, пользователь видит временную шкалу и дерево **span**'ов: какой сервис сколько времени занял, какие вызовы были выполнены. Это помогает находить медленные операции и узкие места. Поддержка **dependency graph** (граф зависимостей сервисов) доступна при использовании соответствующего хранилища или дополнительных компонентов.


## Лучшие практики

Используйте единое именование сервисов и операций, чтобы удобно фильтровать трейсы. Не передавайте чувствительные данные в тегах **span**'ов. В production настраивайте сэмплирование, чтобы не перегружать **Zipkin** и хранилище. Для высокой доступности используйте постоянное хранилище (**Elasticsearch**, **Cassandra**) и при необходимости несколько экземпляров приёмной части. Предпочтительно инструментировать приложения через **OpenTelemetry** или **Micrometer Tracing**, оставляя **Zipkin** в роли бэкенда — так проще в будущем сменить или дополнить систему трейсинга.


## Решение проблем

| Симптом | Возможная причина | Что делать |
|--------|-------------------|------------|
| Трейсы не появляются в **Zipkin** | Неверный endpoint, сеть, формат | Проверить URL репортера, логи приложения и **Zipkin**; убедиться, что используется правильный формат (**B3**, **Zipkin** **v2** и т.д.) |
| Высокая задержка отображения | Очередь или медленное хранилище | Увеличить ресурсы **Zipkin** или хранилища; проверить сэмплирование и объём данных |
| Ошибки при отправке **span**'ов | Таймаут, отказ **Zipkin** | Настроить retry и буферизацию на стороне клиента; проверить доступность **Zipkin** |
| Неполные трейсы (нет дочерних **span**'ов) | Контекст не передаётся между сервисами | Проверить передачу заголовков **B3** или **W3C Trace Context** в HTTP-клиентах и между сервисами |


## Частые вопросы

**Чем **Zipkin** отличается от **Jaeger**?** Обе системы решают задачу распределённого трейсинга. **Zipkin** проще в развёртывании и исторически тесно связан с экосистемой **Java** (**Brave**, **Sleuth**). **Jaeger** предлагает расширенные возможности сэмплирования и интеграцию с **Kubernetes**. Для новых проектов часто выбирают **OpenTelemetry** с бэкендом **Zipkin** или **Jaeger** по предпочтениям команды.

**Нужно ли писать инструментацию вручную?** Нет, при использовании **OpenTelemetry** **Java Agent** или **Spring** с **Micrometer Tracing** многие вызовы (HTTP, **JDBC**, **Kafka** и т.д.) инструментируются автоматически. Ручные **span**'ы добавляют для важных бизнес-операций.

**Как хранить трейсы в production?** Встроенное хранение в памяти подходит только для разработки. Для production настраивают **Elasticsearch** или **Cassandra** в качестве хранилища **Zipkin** согласно официальной документации.

**Поддерживает ли **Zipkin** **W3C Trace Context**?** Да, современные версии **Zipkin** и клиенты поддерживают передачу контекста в формате **W3C**, что обеспечивает совместимость с **OpenTelemetry** и другими системами.


## Глоссарий

- **B3** — формат заголовков распространения контекста трейса, изначально использовавшийся **Zipkin**.
- **Span** — одна операция в трейсе с именем, временем начала/окончания и тегами.
- **Trace** — цепочка связанных **span**'ов, представляющая один запрос или сценарий.
- **Trace ID** — идентификатор всего трейса, общий для всех **span**'ов в цепочке.
- **Span ID** — идентификатор отдельного **span**'а.
- **Reporter** — компонент в приложении, отправляющий **span**'ы в **Zipkin**.
- **W3C Trace Context** — стандарт заголовков для передачи контекста трейса между сервисами.


## Заключение

**Zipkin** — проверенная открытая система распределённого трейсинга, удобная для сбора и просмотра цепочек вызовов между сервисами. Современная интеграция строится вокруг **OpenTelemetry** или **Micrometer Tracing** с **Zipkin** в роли бэкенда, что сохраняет гибкость при смене или дополнении стека мониторинга. Для углублённого изучения смотрите [OpenTelemetry](opentelemetry.md) и [Jaeger](jaeger.md).
