## Введение в API тестирование

**API тестирование** — проверка функциональности, производительности и надежности **API**.

### Основные аспекты

- Функциональное тестирование
- Тестирование производительности
- Тестирование безопасности
- Тестирование интеграции

## Типы тестов

1. **Unit тесты** — тестирование отдельных **endpoints**
2. **Integration тесты** — тестирование взаимодействия компонентов
3. **E2E тесты** — тестирование полных сценариев
4. **Performance тесты** — тестирование производительности

## Инструменты

| Инструмент | Назначение |
|------------|------------|
| **REST Assured** | **Java** — декларативные тесты **REST API** |
| **Postman** / **Newman** | Ручные и автоматические запросы, **CI** |
| **Insomnia** | Разработка и тестирование **API** |
| **curl** / **httpie** | Быстрые проверки из терминала |
| **WireMock** | Моки **HTTP** для изоляции тестов |

## Лучшие практики

1. **Автоматизация:** тесты в **CI/CD** (например, JUnit + REST Assured, Newman в пайплайне); проверка кодов ответа, тела и заголовков.
2. **Граничные случаи:** пустые и невалидные входы, таймауты, большие ответы; негативные сценарии (4xx, 5xx).
3. **Валидация:** схема ответа (JSON Schema), обязательные поля, типы; контрактное тестирование при микросервисах.
4. **Изоляция:** моки зависимостей и внешних **API**; использование **Testcontainers** для реальных БД при необходимости.

## Решение проблем

| Симптом | Частая причина | Что проверить |
|---|---|---|
| Тесты периодически падают по timeout | нестабильная сеть/слишком жёсткий timeout | увеличить timeout, отделить network flakiness от функциональных проверок |
| `401/403` в автотестах | токен истёк или не обновляется перед тестом | добавить явный шаг получения/обновления токена, проверить test credentials |
| CORS/Preflight ошибки | неверные заголовки `Origin`/`Access-Control-*` | добавить отдельные тесты preflight (`OPTIONS`) и проверить gateway policy |
| Контракт «сломался» после деплоя | изменили поле/тип без согласования схемы | ввести contract tests и schema validation в CI |
| Нестабильные проверки данных | окружение не детерминировано, грязные test data | фиксировать тестовые данные, использовать isolated fixtures/Testcontainers |

## Чек-лист проверки API перед релизом

1. Проверены позитивные и негативные сценарии для критичных endpoint-ов.
2. Все коды ответов (`2xx/4xx/5xx`) соответствуют контракту и документации.
3. Пройдена проверка аутентификации/авторизации (включая истёкший и невалидный токен).
4. Проверены backward-совместимость и schema validation для ключевых ответов.
5. Пройдены smoke-тесты на staging после деплоя.
6. Зафиксированы p95/p99 latency и error-rate для основных маршрутов.
7. Обновлена документация API (OpenAPI/Swagger) при изменениях контракта.
