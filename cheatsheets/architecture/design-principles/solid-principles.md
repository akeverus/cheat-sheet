# Принципы SOLID

Пять принципов объектно-ориентированного проектирования с примерами на `Java`.

## Введение

**SOLID** — аббревиатура пяти принципов, которые помогают проектировать понятный, расширяемый и устойчивый к изменениям код.

## S — Single Responsibility

**Один класс — одна причина для изменения.**

Класс должен иметь одну зону ответственности. Если меняется бизнес-логика, формат отчёта или способ сохранения — меняться должен один модуль, а не один «бог-класс».

### Плохо

```java
public class UserService {
    public void register(User u) { /* валидация + сохранение + отправка email + логирование */ }
}
```

### Хорошо

```java
public class UserValidator { boolean validate(User u) { return true; } }
public class UserRepository { void save(User u) { } }
public class EmailSender { void sendWelcome(User u) { } }
public class UserService {
    private final UserValidator validator;
    private final UserRepository repo;
    private final EmailSender email;
    public UserService(UserValidator v, UserRepository r, EmailSender e) {
        validator = v; repo = r; email = e;
    }
    public void register(User u) {
        if (!validator.validate(u)) throw new IllegalArgumentException();
        repo.save(u);
        email.sendWelcome(u);
    }
}
```


## O — Open/Closed

**Открыт для расширения, закрыт для модификации.**

Новое поведение добавляется через новые классы/реализации, а не через правки существующего кода.

### Плохо

```java
public double area(Shape s) {
    if (s instanceof Circle) return Math.PI * ((Circle) s).getR() * ((Circle) s).getR();
    if (s instanceof Rectangle) return ((Rectangle) s).getW() * ((Rectangle) s).getH();
    return 0;
}
```

### Хорошо

```java
public interface Shape { double area(); }
public class Circle implements Shape {
    private final double r;
    public Circle(double r) { this.r = r; }
    @Override public double area() { return Math.PI * r * r; }
}
public class Rectangle implements Shape {
    private final double w, h;
    public Rectangle(double w, double h) { this.w = w; this.h = h; }
    @Override public double area() { return w * h; }
}
```


## L — Liskov Substitution

**Подтипы должны быть подставляемы вместо базового типа без нарушения контракта.**

Поведение подкласса не должно «ломать» ожидания клиента, работающего с базовым типом (не уже контракт, не бросать неожиданные исключения).

### Плохо

```java
public class Rectangle { void setW(double w); void setH(double h); }
public class Square extends Rectangle {
    @Override void setW(double w) { super.setW(w); super.setH(w); }
    @Override void setH(double h) { super.setH(h); super.setW(h); }
}
// Клиент ожидает: setW(5); setH(4); area() == 20. У Square после setW(5); setH(4) area() == 16.
```

### Хорошо

Подтип не сужает предусловия и не ослабляет постусловия; не бросает новых исключений для клиента базового типа. Квадрат не наследуют от прямоугольника с сеттерами сторон, если контракт «независимые стороны» важен.


## I — Interface Segregation

**Клиенты не должны зависеть от интерфейсов, которые не используют.**

Вместо одного «толстого» интерфейса — несколько узких. Класс реализует только то, что ему нужно.

### Плохо

```java
public interface Worker {
    void work();
    void eat();
    void sleep();
}
// Офисный работник — work, eat, sleep. Робот — только work. Робот вынужден реализовывать eat/sleep пустыми.
```

### Хорошо

```java
public interface Workable { void work(); }
public interface Eatable { void eat(); }
public class Human implements Workable, Eatable { /* work, eat */ }
public class Robot implements Workable { /* work */ }
```


## D — Dependency Inversion

**Зависимости должны быть от абстракций, а не от конкретных реализаций.**

Модули верхнего уровня не зависят от модулей нижнего уровня; оба зависят от абстракций (интерфейсов). Внедрение зависимостей (DI) — способ соблюдения принципа.

### Плохо

```java
public class OrderService {
    private final MySqlRepository repo = new MySqlRepository();
    public void save(Order o) { repo.save(o); }
}
```

### Хорошо

```java
public interface OrderRepository { void save(Order o); }
public class OrderService {
    private final OrderRepository repo;
    public OrderService(OrderRepository repo) { this.repo = repo; }
    public void save(Order o) { repo.save(o); }
}
// Конкретная реализация (MySQL, Mongo, in-memory) передаётся снаружи (конструктор, DI-контейнер).
```


## Лучшие практики

Краткие рекомендации по применению каждого принципа **SOLID** в коде:

- **SRP**: разбивайте большие классы по зонам ответственности (валидация, персистентность, уведомления).
- **OCP**: полиморфизм, стратегии, плагины вместо длинных if/**switch** по типам.
- **LSP**: подклассы не должны уже контракт и не бросать неожиданных исключений для клиента базового типа.
- **ISP**: маленькие интерфейсы под конкретные роли.
- **DIP**: зависимости от интерфейсов и внедрение через конструктор/сеттер; в **Spring** — автоматический `DI`.


## SRP: детали и примеры

**Одна причина для изменения** означает: класс меняется только когда меняется одна область требований (бизнес-правило, формат отчёта, способ хранения, протокол уведомления и т.д.). Если один класс отвечает за валидацию, сохранение в БД и отправку **email** — при смене формата **email** или добавлении поля в БД придётся трогать один и тот же класс. Разделение на **UserValidator**, **UserRepository**, **EmailSender** позволяет менять каждый аспект независимо.

### Пример нарушения SRP

```java
public class OrderProcessor {
    public void process(Order o) {
        validate(o);
        saveToDb(o);
        sendToWarehouse(o);
        sendInvoice(o);
        logAudit(o);
    }
    private void validate(Order o) { /* ... */ }
    private void saveToDb(Order o) { /* ... */ }
    private void sendToWarehouse(Order o) { /* ... */ }
    private void sendInvoice(Order o) { /* ... */ }
    private void logAudit(Order o) { /* ... */ }
}
```

Один класс отвечает за валидацию, персистентность, интеграцию со складом, выставление счёта и аудит. Любое изменение в одном из аспектов затрагивает **OrderProcessor**.

### Пример соблюдения SRP

```java
public class OrderService {
    private final OrderValidator validator;
    private final OrderRepository repository;
    private final WarehouseClient warehouse;
    private final InvoiceSender invoiceSender;
    private final AuditLogger auditLogger;

    public OrderService(OrderValidator v, OrderRepository r, WarehouseClient w,
                        InvoiceSender i, AuditLogger a) {
        validator = v; repository = r; warehouse = w; invoiceSender = i; auditLogger = a;
    }
    public void process(Order o) {
        validator.validate(o);
        repository.save(o);
        warehouse.send(o);
        invoiceSender.send(o);
        auditLogger.log(o);
    }
}
```

Каждая зависимость — отдельная зона ответственности; замена реализации (например другой WarehouseClient) не затрагивает остальной код.


## OCP: детали и примеры

**Открыт для расширения** — можно добавлять новое поведение (новые типы фигур, новые стратегии). **Закрыт для модификации** — существующий код не меняется (не добавляются новые case в switch/if). Достигается через полиморфизм, стратегии, плагины.

### Пример нарушения OCP

```java
public double area(Shape s) {
    if (s instanceof Circle) return Math.PI * ((Circle) s).getR() * ((Circle) s).getR();
    if (s instanceof Rectangle) return ((Rectangle) s).getW() * ((Rectangle) s).getH();
    if (s instanceof Triangle) return /* ... */;
    return 0;
}
```

Добавление нового типа (Triangle, Polygon) требует изменения этого метода и перекомпиляции модуля.

### Пример соблюдения OCP

Каждый тип фигуры реализует интерфейс **Shape** с методом **area**(). Добавление нового типа — новый класс, реализующий **Shape**; метод **area(Shape) не меняется.


## LSP: детали и контракты

**Контракт** — предусловия (что должно быть истинно до вызова), постусловия (что гарантируется после вызова), инварианты (что сохраняется всегда). Подтип не должен уже предусловия (требовать больше от клиента) и не должен ослаблять постусловия (гарантировать меньше). Подтип не должен бросать исключения, которые клиент базового типа не ожидает.

### Пример: квадрат и прямоугольник

Если **Rectangle** допускает независимую установку ширины и высоты, то **Square** не может быть подтипом **Rectangle** с тем же контрактом: после **setW**(5); **setH**(4) клиент ожидает **area**() == 20, у **Square area**() == 16. Решение: не наследовать **Square** от **Rectangle**; общий интерфейс **Shape** с методом **area**(); или отдельная иерархия без сеттеров сторон.

### Пример: исключения

Если базовый метод не бросает исключений, подтип не должен бросать проверяемые исключения (или только подтипы существующих). Иначе клиент, работающий с базовым типом, не сможет подставить подтип без изменения кода (добавление try-catch).


## ISP: детали и примеры

**Толстый интерфейс** заставляет класс реализовывать методы, которые он не использует (пустые реализации или выброс UnsupportedOperationException). Это создаёт шум и нестабильный контракт (клиент может вызвать нерелевантный метод). **Узкие интерфейсы** — клиент зависит только от того, что реально использует.

### Пример: разделение интерфейсов

Вместо **Worker** { **work**(), **eat**(), **sleep**() } — **Workable** { **work**() }, **Eatable** { **eat**() }, **Sleepable** { **sleep**() }. **Human** реализует **Workable**, **Eatable**, **Sleepable**; **Robot** — только **Workable**. Клиент, которому нужен только **work**(), зависит от **Workable**, а не от **Worker**.


## DIP: детали и `DI`

**Модули верхнего уровня** — бизнес-логика, оркестрация. **Модули нижнего уровня** — БД, внешние **API**, файловая система. Оба должны зависеть от абстракций (интерфейсов). Конкретные реализации (MySqlRepository, MongoRepository) внедряются снаружи (конструктор, setter, `DI`-контейнер). Это упрощает тестирование (подстановка mock) и замену реализации без изменения бизнес-логики.

### Spring и DIP

В **Spring** зависимости объявляются через конструктор или поле с @**Autowired**; контейнер создаёт бин и подставляет реализацию по типу интерфейса. @**Repository**, @**Service** — стереотипы; интерфейс **OrderRepository** и реализация **JpaOrderRepository**; **OrderService** зависит от **OrderRepository**, а не от **JpaOrderRepository**.

| Принцип | Паттерны, поддерживающие принцип |
|---------|-----------------------------------|
| **SRP** | **Facade** (разделение подсистем), разбиение на сервисы |
| **OCP** | **Strategy**, **Template Method**, **Observer**, **Factory Method** |
| **LSP** | Правильная иерархия наследования, контракты |
| **ISP** | Разделение интерфейсов (многие мелкие интерфейсы) |
| **DIP** | **Dependency Injection**, **Factory**, **Abstract Factory** |


## Частые вопросы по SOLID

**Как определить, что класс нарушает `SRP`?** Спросите: «Сколько причин для изменения у этого класса?» Если больше одной (меняется при смене БД и при смене формата отчёта) — нарушение.

**Когда можно нарушить `OCP`?** При прототипировании или когда изменение маловероятно; в долгосрочном коде предпочтительно расширение без модификации.

**Что такое «контракт» в `LSP`?** Предусловия (условия на вход), постусловия (гарантии на выход), инварианты (условия, сохраняемые объектом). Подтип не должен уже предусловия и не ослаблять постусловия.

**Как применить `ISP` к существующему толстому интерфейсу?** Выделить группы методов в отдельные интерфейсы; классы реализуют только нужные интерфейсы; клиенты зависят от узких интерфейсов.

**Чем `DIP` отличается от простого «зависить от интерфейса»? DIP** явно требует: модули верхнего уровня не зависят от модулей нижнего уровня; оба зависят от абстракций. Создание конкретной реализации (**new `MySqlRepository`()) внутри сервиса нарушает **DIP**; реализация должна внедряться снаружи.

## SRP: признаки нарушения и рефакторинг

**Признаки нарушения `SRP`:** класс меняется по разным причинам (смена БД, смена формата отчёта, смена протокола уведомлений); класс содержит много методов из разных областей (валидация, персистентность, уведомления); класс трудно тестировать изолированно. **Рефакторинг:** выделить группы методов в отдельные классы; внедрить их через конструктор; оставить в исходном классе только оркестрацию.


## OCP: стратегии и плагины

**Стратегии:** вместо **switch** по типу — интерфейс **Strategy** и реализации; клиент получает стратегию снаружи (DI). **Плагины:** новое поведение подключается как отдельный модуль (класс, реализующий интерфейс); основной код не меняется. **Полиморфизм:** базовый тип с методом; подтипы переопределяют метод; добавление нового поведения — новый подтип.


## LSP: предусловия и постусловия

**Предусловия** — условия на входные параметры; подтип не должен их ужечить (требовать больше от клиента). **Постусловия** — гарантии на выход; подтип не должен их ослаблять (гарантировать меньше). **Инварианты** — условия, сохраняемые объектом; подтип не должен их нарушать. Пример: если базовый метод гарантирует «не **null**», подтип не может возвращать **null**.


## ISP: примеры из Java и Spring

В **Java**: вместо одного интерфейса с десятками методов — несколько интерфейсов (Readable, `Writable`, `Closeable` и т.д.). В **Spring**: клиент зависит от узкого интерфейса (JpaRepository для чтения/записи сущности), а не от всего контекста. При добавлении нового клиента с другими потребностями создаётся новый интерфейс, а не расширение существующего.


## DIP: внедрение зависимостей (конструктор vs сеттер)

**Конструктор:** зависимости обязательны при создании; объект в консистентном состоянии сразу. **Сеттер:** зависимости опциональны или могут меняться; гибче, но объект может быть в неконсистентном состоянии до вызова сеттеров. В **Spring** предпочитают внедрение через конструктор (явные зависимости, неизменяемость полей).


## Таблица: SOLID и типичные нарушения

| Принцип | Типичное нарушение | Решение |
|---------|---------------------|---------|
| **SRP** | Один класс делает валидацию, сохранение, уведомления | Разделить на **Validator**, **Repository**, **Notifier** |
| **OCP** | Длинный **switch**/if по типу при добавлении нового типа | Полиморфизм, **Strategy**, плагины |
| **LSP** | Подтип сужает контракт (Square extends `Rectangle` с сеттерами) | Не наследовать; общий интерфейс без сеттеров |
| **ISP** | Толстый интерфейс; класс реализует пустые методы | Разделить на узкие интерфейсы |
| **DIP** | **new ConcreteRepository**() внутри сервиса | Зависимость от интерфейса; `DI` через конструктор |


## Таблица: SOLID и тестируемость

| Принцип | Влияние на тесты |
|---------|-------------------|
| **SRP** | Класс с одной ответственностью проще тестировать изолированно |
| **OCP** | Новое поведение — новый класс; тесты не трогают старый код |
| **LSP** | Подтипы подставляемы; тесты базового типа применимы к подтипам |
| **ISP** | Узкие интерфейсы упрощают создание **mock**/**stub** |
| **DIP** | Зависимости от интерфейсов позволяют подставлять **mock** в тестах |


## Дополнительные примеры: SRP (разделение отчёта и сохранения)

```java
public interface ReportGenerator { String generate(Data data); }
public interface ReportPublisher { void publish(String report); }

public class ReportService {
    private final ReportGenerator generator;
    private final ReportPublisher publisher;
    public ReportService(ReportGenerator g, ReportPublisher p) {
        generator = g; publisher = p;
    }
    public void createAndPublish(Data data) {
        String report = generator.generate(data);
        publisher.publish(report);
    }
}
```


## Дополнительные примеры: OCP (стратегия расчёта скидки)

```java
public interface DiscountStrategy { double apply(double price); }

public class NoDiscount implements DiscountStrategy {
    @Override public double apply(double price) { return price; }
}

public class PercentDiscount implements DiscountStrategy {
    private final double rate;
    public PercentDiscount(double rate) { this.rate = rate; }
    @Override public double apply(double price) { return price * (1 - rate); }
}

public class OrderService {
    private final DiscountStrategy discount;
    public OrderService(DiscountStrategy d) { this.discount = d; }
    public double total(double price) { return discount.apply(price); }
}
```

Добавление нового типа скидки — новый класс, реализующий **DiscountStrategy**; **OrderService** не меняется.

## Резюме для быстрого повторения (SOLID)

**SRP:** один класс — одна причина для изменения; разбивать по зонам ответственности. **OCP:** открыт для расширения, закрыт для модификации; полиморфизм, стратегии. **LSP:** подтипы подставляемы; не ужечить предусловия, не ослаблять постусловия. **ISP:** узкие интерфейсы; клиент не зависит от неиспользуемых методов. **DIP:** зависимости от абстракций; внедрение через конструктор; в **Spring** — `DI`.

## Дополнительные детали: SRP и размер класса

Класс с одной ответственностью обычно имеет ограниченный размер (условно до нескольких сотен строк). Очень большой класс — признак множества ответственностей. Разбиение по **SRP** не означает «один метод на класс»; группа связанных методов, относящихся к одной зоне ответственности, может оставаться в одном классе.


## Дополнительные детали: OCP и конфигурация

Новое поведение можно добавлять через конфигурацию (например, плагины, загружаемые по имени класса) без перекомпиляции основного кода. **OCP** поддерживается, если основной код зависит от абстракции (интерфейса), а конкретная реализация задаётся конфигурацией или `DI`.


## Дополнительные детали: LSP и исключения

Подтип не должен бросать проверяемые исключения, которые базовый метод не объявляет. Иначе клиент, работающий с базовым типом, не сможет подставить подтип без добавления **try-catch**. Подтип может бросать подтипы исключений базового метода (если базовый метод объявляет throws `Exception`, подтип может бросать IOException).


## Дополнительные детали: ISP и адаптеры

Если клиенту нужен только часть методов толстого интерфейса, можно создать адаптер (класс, реализующий узкий интерфейс и делегирующий толстому объекту только нужные вызовы). Так клиент зависит от узкого интерфейса, а адаптер — от толстого. Альтернатива — разделить толстый интерфейс на несколько узких; объект реализует несколько интерфейсов.


## Дополнительные детали: DIP и слои архитектуры

В многослойной архитектуре (presentation, business, data) зависимости направлены внутрь: слой бизнес-логики не зависит от слоя данных напрямую; оба зависят от интерфейсов (репозитории, сервисы). Слой данных реализует интерфейсы репозиториев; бизнес-слой получает репозитории через `DI`. Это позволяет подменять слой данных (например, `in-memory` для тестов) без изменения бизнес-логики.


## Таблица: SOLID и рефакторинг

| Принцип | Рефакторинг при нарушении |
|---------|---------------------------|
| **SRP** | Выделить классы по ответственности; внедрить через конструктор |
| **OCP** | Заменить **switch**/if на полиморфизм или стратегии |
| **LSP** | Не наследовать несовместимые контракты; общий интерфейс без нарушающих методов |
| **ISP** | Разделить интерфейс на узкие; классы реализуют только нужные |
| **DIP** | Ввести интерфейс; внедрять реализацию снаружи (конструктор, DI) |


## Таблица: SOLID в Spring

| Принцип | Как соблюдается в **Spring** |
|---------|---------------------------|
| **SRP** | Сервисы, репозитории, контроллеры разделены по ответственности |
| **OCP** | Новые бины добавляются без изменения существующего кода |
| **LSP** | Подтипы бинов подставляемы при внедрении по интерфейсу |
| **ISP** | Узкие интерфейсы (JpaRepository, `ApplicationListener` и т.д.) |
| **DIP** | @**Autowired** по интерфейсу; контейнер подставляет реализацию |


## Пример: нарушение SRP (класс с валидацией, сохранением и уведомлением)

```java
public class UserRegistration {
    public void register(User u) {
        if (u.getEmail() == null || !u.getEmail().contains("@")) throw new IllegalArgumentException();
        jdbcTemplate.update("INSERT INTO users ...", u.getName(), u.getEmail());
        emailSender.send(u.getEmail(), "Welcome", "Welcome!");
    }
}
```

Один класс отвечает за валидацию, персистентность и уведомление. При смене формата **email** или способа сохранения придётся менять **UserRegistration**.


## Пример: соблюдение SRP (разделение на `Validator`, `Repository`, Notifier)

```java
public class UserValidator { boolean validate(User u) { /* ... */ return true; } }
public interface UserRepository { void save(User u); }
public interface EmailNotifier { void sendWelcome(User u); }

public class UserRegistration {
    private final UserValidator validator;
    private final UserRepository repo;
    private final EmailNotifier notifier;
    public UserRegistration(UserValidator v, UserRepository r, EmailNotifier n) {
        validator = v; repo = r; notifier = n;
    }
    public void register(User u) {
        if (!validator.validate(u)) throw new IllegalArgumentException();
        repo.save(u);
        notifier.sendWelcome(u);
    }
}
```


## Пример: нарушение OCP (добавление типа требует изменения метода)

```java
public double area(Shape s) {
    if (s instanceof Circle) return Math.PI * ((Circle) s).getR() * ((Circle) s).getR();
    if (s instanceof Rectangle) return ((Rectangle) s).getW() * ((Rectangle) s).getH();
    if (s instanceof Triangle) { Triangle t = (Triangle) s; return 0.5 * t.getBase() * t.getHeight(); }
    return 0;
}
```

Добавление **Polygon** потребует изменения этого метода.


## Пример: соблюдение OCP (новый тип — новый класс)

```java
public interface Shape { double area(); }
public class Polygon implements Shape {
    private final List<Point> vertices;
    public Polygon(List<Point> v) { this.vertices = v; }
    @Override public double area() { /* формула по вершинам */ return 0; }
}
```

Метод **area(Shape s) { **return s.area**(); } не меняется при добавлении **Polygon**.


## Пример: нарушение LSP (Square и Rectangle)

Клиент ожидает: **rectangle.setWidth**(5); **rectangle.setHeight**(4); **rectangle.getArea**() == 20. Если **Square extends Rectangle** и переопределяет **setWidth**/**setHeight** так, что обе стороны равны, то после **setWidth**(5); **setHeight**(4) у **Square area**() == 16. Ожидание клиента нарушено.


## Пример: соблюдение LSP (общий интерфейс без сеттеров сторон)

```java
public interface Shape { double area(); }
public class Rectangle implements Shape {
    private final double w, h;
    public Rectangle(double w, double h) { this.w = w; this.h = h; }
    @Override public double area() { return w * h; }
}
public class Square implements Shape {
    private final double side;
    public Square(double side) { this.side = side; }
    @Override public double area() { return side * side; }
}
```

Клиент работает с **Shape**; подстановка **Rectangle** или **Square** не нарушает контракт **area**().


## Пример: нарушение ISP (толстый интерфейс)

```java
public interface Worker { void work(); void eat(); void sleep(); }
public class Robot implements Worker {
    @Override public void work() { /* ... */ }
    @Override public void eat() { throw new UnsupportedOperationException(); }
    @Override public void sleep() { throw new UnsupportedOperationException(); }
}
```

Робот вынужден реализовывать **eat**/**sleep**; клиент может случайно вызвать их.


## Пример: соблюдение ISP (узкие интерфейсы)

```java
public interface Workable { void work(); }
public interface Eatable { void eat(); }
public class Robot implements Workable { @Override public void work() { /* ... */ } }
public class Human implements Workable, Eatable { /* work, eat */ }
```

Клиент, которому нужен только **work**(), зависит от **Workable**; **Robot** реализует только **Workable**.


## Пример: нарушение DIP (создание зависимости внутри класса)

```java
public class OrderService {
    private final MySqlOrderRepository repo = new MySqlOrderRepository();
    public void save(Order o) { repo.save(o); }
}
```

**OrderService** зависит от конкретной реализации **MySqlOrderRepository**; замена на **Mongo** или **in-memory** требует изменения **OrderService**.


## Пример: соблюдение DIP (внедрение через конструктор)

```java
public interface OrderRepository { void save(Order o); }
public class OrderService {
    private final OrderRepository repo;
    public OrderService(OrderRepository repo) { this.repo = repo; }
    public void save(Order o) { repo.save(o); }
}
```

Конкретная реализация (MySqlOrderRepository, `MongoOrderRepository`, InMemoryOrderRepository) передаётся снаружи; **OrderService** не меняется.


## Частые вопросы: ещё вопросы по SOLID

**Как `SRP` связан с размером класса?** Класс с одной ответственностью обычно компактен; большой класс часто указывает на несколько ответственностей. Но «одна ответственность» не означает «один метод»; группа связанных методов может образовывать одну ответственность.

**Когда можно не соблюдать `OCP`?** В прототипах, при маловероятном изменении или когда полиморфизм избыточен (например, два типа, не ожидается рост). В долгосрочном коде предпочтительно **OCP**.

**Что такое «ужечить предусловие»?** Базовый метод принимает любую строку; подтип требует непустую строку. Клиент, передающий пустую строку в базовый тип, сломается при подстановке подтипа.

**Как разделить толстый интерфейс (ISP)?** Выделить группы методов по клиентам; создать отдельные интерфейсы; классы реализуют только нужные интерфейсы. Клиенты зависят от узких интерфейсов.

**Зачем предпочитать внедрение через конструктор (DIP)?** Зависимости явны и обязательны; объект в консистентном состоянии после конструктора; поля можно сделать **final**. В **Spring** — рекомендация для обязательных зависимостей.

- **O** — открыт для расширения, закрыт для модификации; полиморфизм, стратегии.
- **L** — подтипы подставляемы; не ужечить предусловия, не ослаблять постусловия.
- **I** — узкие интерфейсы; клиент не зависит от неиспользуемых методов.
- **D** — зависимости от абстракций; внедрение через конструктор; `DI`.

## Дополнительные примеры: SRP (разделение валидации и сохранения)

```java
public interface UserValidator { boolean validate(User u); }
public interface UserRepository { void save(User u); }

public class UserService {
    private final UserValidator validator;
    private final UserRepository repo;
    public UserService(UserValidator v, UserRepository r) { validator = v; repo = r; }
    public void register(User u) {
        if (!validator.validate(u)) throw new IllegalArgumentException("Invalid user");
        repo.save(u);
    }
}
```

## Дополнительные примеры: OCP (стратегия валидации)

```java
public interface ValidationRule<T> { boolean validate(T entity); }

public class EmailRequired implements ValidationRule<User> {
    @Override public boolean validate(User u) { return u.getEmail() != null && !u.getEmail().isBlank(); }
}

public class UserValidator {
    private final List<ValidationRule<User>> rules;
    public UserValidator(List<ValidationRule<User>> rules) { this.rules = rules; }
    public boolean validate(User u) { return rules.stream().allMatch(r -> r.validate(u)); }
}
```

Добавление нового правила — новый класс **ValidationRule**<**User**>; **UserValidator** не меняется.


## Дополнительные примеры: LSP (контракт возвращаемого значения)

Базовый метод **getConfig**() возвращает **non-null Config**. Подтип не должен возвращать **null** (ослабление постусловия). Если подтип может не иметь конфига, контракт базового типа должен это допускать (Optional<`Config`>) или подтип не должен быть подставляем в контекст, где ожидается **non-null**.


## Дополнительные примеры: ISP (разделение интерфейса репозитория)

Вместо **UserRepository** { **findById**, **findAll**, **save**, **delete**, **findByEmail**, **findByStatus**, ... } — **Readable**<**User**> { **findById**, **findAll** }, **Writable**<**User**> { **save**, **delete** }, **UserQuery** { **findByEmail**, **findByStatus** }. Сервис, которому нужны только чтение и сохранение, зависит от **Readable** и **Writable**; не от **UserQuery**.


## Дополнительные примеры: DIP (слой данных и бизнес-логика)

Слой бизнес-логики определяет интерфейсы **OrderRepository**, **PaymentGateway**. Слой данных реализует **JpaOrderRepository**, **StripePaymentGateway**. Конфигурация (Spring) связывает интерфейсы с реализациями. Бизнес-слой не зависит от **JPA** или **Stripe**; при замене БД или платёжной системы меняется только слой данных.

## Резюме для быстрого повторения (SOLID, часть 3)

**SRP:** один класс — одна причина для изменения; разбиение по валидации, персистентности, уведомлениям, логированию. **OCP:** открыт для расширения, закрыт для модификации; полиморфизм, стратегии, плагины. **LSP:** подтипы подставляемы; не ужечить предусловия, не ослаблять постусловия. **ISP:** узкие интерфейсы; клиент не зависит от неиспользуемых методов. **DIP:** зависимости от абстракций; внедрение через конструктор; в **Spring** — `DI`.

## SRP: критерии «одной ответственности»

Одна ответственность — одна причина для изменения. Если класс меняется при смене формата отчёта и при смене БД — две ответственности. Критерий: можно ли описать ответственность класса одним коротким предложением без «и»? «Класс валидирует пользователя» — одна; «Класс валидирует пользователя и сохраняет в БД» — две.


## OCP: расширение без модификации на практике

На практике: новые типы (новые фигуры, новые стратегии скидки) добавляются как новые классы, реализующие интерфейс. Существующий код (**метод area(`Shape` s) { **return s.area**(); }, **OrderService** с **DiscountStrategy**) не меняется. Конфигурация или `DI` связывает новые классы с клиентом.


## LSP: инварианты

Инварианты — условия, сохраняемые объектом на протяжении жизни. Например: «ширина и высота прямоугольника положительны». Подтип не должен нарушать инварианты базового типа. **Square** нарушает инвариант **Rectangle** «ширина и высота могут меняться независимо», если **Square** принудительно делает их равными.


## ISP: адаптер как альтернатива разделению интерфейса

Если толстый интерфейс менять нельзя (внешняя библиотека), можно создать адаптер: класс, реализующий узкий интерфейс и делегирующий толстому объекту только нужные вызовы. Клиент зависит от узкого интерфейса; адаптер зависит от толстого. Так клиент изолирован от неиспользуемых методов.


## DIP: высокоуровневый и низкоуровневый модули

Высокоуровневый модуль — бизнес-логика (OrderService). Низкоуровневый — детали реализации (JpaOrderRepository, StripePaymentGateway). Оба должны зависеть от абстракций (OrderRepository, PaymentGateway). Абстракции определяются высокоуровневым модулем (интерфейс в пакете домена или сервиса); низкоуровневый модуль реализует интерфейс.


## Таблица: SOLID — краткие формулировки для запоминания

| Буква | Принцип | Краткая формулировка |
|-------|---------|------------------------|
| S | **Single Responsibility** | Один класс — одна причина для изменения |
| O | **Open**/**Closed** | Открыт для расширения, закрыт для модификации |
| L | **Liskov Substitution** | Подтипы подставляемы без нарушения контракта |
| I | **Interface Segregation** | Узкие интерфейсы; не зависеть от неиспользуемого |

## Частые вопросы: SOLID и рефакторинг

**Как начать применять `SOLID` в существующем коде?** Выделить наиболее очевидные нарушения **SRP** (классы с множеством обязанностей); разбить на сервисы/репозитории; внедрить через конструктор (DIP). Затем заменить **switch**/if на полиморфизм (OCP) там, где добавляются новые типы.

**Нужно ли всегда соблюдать все пять принципов?** В долгосрочном коде — да; в прототипах или скриптах допустимы упрощения. **SRP** и **DIP** наиболее важны для тестируемости и поддержки.

**Как `SOLID` связан с микросервисами? SRP** и границы сервисов (один сервис — одна зона ответственности); **DIP** и взаимодействие через **API**/события (зависимость от контракта, а не от реализации); **OCP** и добавление новых сервисов без изменения существующих.
