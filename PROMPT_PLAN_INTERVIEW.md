# Полный промпт проверки и улучшения MCQ для любой LLM

Этот документ можно целиком передать другой LLM, работающей с репозиторием.
Он описывает поручение на выполнение, правила приёмки, экономию ресурсов, реальные
инструменты и продолжение работы. Состояние корпуса берётся из текущего дерева и
доказательств, а не из чисел в этом документе или из истории предыдущего чата.

## 1. Твоя задача и ожидаемый результат

Ты работаешь в репозитории **cheat-sheet**. Последовательно проверь, исправь и улучши
весь production-корпус MCQ и связанную с ним теорию. Доведи его до подтверждённой
приёмки по каждому файлу, вопросу, блоку и обязательной проверке. Поддерживай актуальные
план, доказательства, таблицу и точку продолжения для следующего исполнителя.

Главные требования, действующие одновременно:

1. Экономить недельный лимит пользователя и суммарные токены всех участников.
2. Выполнить работу полностью: выборка, отсутствие сигналов и удачный пилот не заменяют
   проверки оставшегося корпуса.
3. Сохранять проверяемый прогресс, чтобы продолжение не требовало повторного чтения
   неизменённых принятых блоков.
4. Обеспечивать одинаковые критерии для текущей модели, другой LLM и человека.
5. Проверять естественность русского языка, полноту каждого ответа и отсутствие
   подсказок, по которым правильный ответ выделяется без знания темы.
6. Сохранять честные незавершённые статусы, когда доказательств недостаточно.

Экономия достигается короткими пакетами, локальными инструментами, точечными правками
и повторным использованием действительных результатов. Пропуск вариантов, sections,
второго блока вопроса или обязательной проверки недопустим.

Результат работы — улучшенный корпус и воспроизводимая приёмка. Не ограничивайся
отчётом о проблемах, предложением плана или одним удачным пакетом. Если исполнение
прерывается, сохрани точный checkpoint; прерывание не означает завершения задачи.

Отвечай и веди рабочую документацию на русском языке. Не запрашивай повторное
формальное разрешение на каждый пакет уже порученной локальной работы.

## 2. Скоуп и полномочия

Production seeds находятся в `modules/quiz-app/src/main/resources/seed/mcq/`.
Парная теория — в `cheatsheets/interview/`, с тем же относительным путём и расширением
`.md`. Тестовые fixtures и архивные экспорты не являются production-корпусом.

Разрешено:

- читать применимые инструкции, код, данные, историю Git и первичные источники;
- выполнять локальную диагностику и подходящие тесты;
- исправлять MCQ, видимые вопросы и соответствующую теорию;
- исправлять конкретные дефекты валидаторов и учёта, необходимые для корректной приёмки;
- обновлять действующий план, таблицу, evidence и checkpoint;
- использовать дополнительных агентов только при явно выбранной дешёвой модели;
- удалять подтверждённо устаревшие планы, приложения к ним и сценарии после проверки
  потребителей и наличия восстанавливаемой версии в Git.

Не выполняй commit, push, публикацию, покупку ресурсов, расход reset-кредитов,
подключение платного API или изменение удалённых систем без отдельного поручения.
Никакие инструменты этого workflow не требуют перечисленных действий.

Сохраняй существующие staged, unstaged и untracked изменения. Не используй массовые
reset/clean/restore. Не меняй несвязанные UI, архитектуру приложения и бизнес-правила.
Если runtime-дефект влияет на MCQ, зафиксируй его и заблокируй FINAL затронутого скоупа.
Продуктовое решение нельзя выдумывать ради зелёного отчёта.

Один файл одновременно изменяет один автор. При другой машине или ветке сначала
синхронизируй состояние и распределение работы. Координатор сериализует импорт evidence.

## 3. Начало без повторного аудита всего репозитория

Прочитай применимые `AGENTS.md`, `RTK.md` и локальные инструкции. Выполни их реальные
требования; не предполагая наличие инструментов другой LLM или другой среды.

Зафиксируй корень, ветку, HEAD и исходные изменения. Для затрагиваемых файлов сохрани
исходные хеши. Проверь, не работают ли другие авторы с тем же пакетом.
Для передачи между машинами нужен текущий рабочий каталог со staged, unstaged и
untracked файлами. Чистый clone на одном HEAD может не содержать новые инструменты,
evidence и артефакты run. Не объявляй исчезнувшие при копировании результаты
«непроверенными» до сверки переданного дерева. Если run прерван, определи его
сохранённую фазу и не повторяй слепой проход в уже раскрытом контексте.

Действующие входные точки:

- `PLAN_INTERVIEW.md` — единый план работ;
- `PROMPT_PLAN_INTERVIEW.md` — этот промпт;
- `docs/mcq-quality/workflow.md` — команды, передача и ограничения инфраструктуры;
- `docs/mcq-quality-standard.md` — критерии MCQ;

- `docs/mcq-quality/file-checklist.md` — производная таблица каждого файла;
- `docs/mcq-quality/reviews/README.md` — контракт evidence;
- `docs/mcq-quality/reviews/checks/*.json` — действующие результаты по пакетам;
- `docs/mcq-quality/runs/` — артефакты новых двухфазных проходов;
- `docs/mcq-quality/reviews/blind/` — сохранённые предыдущие проходы;

Не создавай второй конкурирующий план. Не загружай многомегабайтный audit-state
целиком в контекст. Для работы используй компактный CLI, отдельную тему и точные Q/B.

Начальные команды из корня репозитория:

```bash
python3 scripts/mcq-workflow.py doctor
python3 scripts/mcq-workflow.py status
python3 scripts/mcq-workflow.py next --size 4
```

Если отсутствуют зависимости, используй существующее подходящее окружение или создай
локальное окружение по `workflow.md`. Нужны Python 3.10+, Git, jsonschema из
`scripts/requirements-mcq.txt`, Bash для shell gates. Сам workflow не вызывает LLM.

Не начинай с переустановки всех инструментов или нового широкого исследования архитектуры.
Читайте код инфраструктуры повторно только для конкретного дефекта или непонятного контракта.

Три ранее принятые темы: Java functional interfaces, Spring transactions, Hibernate

записи, их нельзя складывать в 88 проверенных блоков.

Порядок: сначала незавершённые проверки исторически обновлённых тем, затем TODO.
Пакет выбирается по `next`, а не по списку, запомненному другой моделью. На момент

Известная runtime-находка: второй блок в CompletableFuture Q3/Q8 может смешиваться
с первым при показе/выборе правильного ответа. Доказательство и затронутый скоуп
хранятся в audit-evidence; до исправления или обоснованного закрытия FINAL блокируется.
Наличие этого блокера не останавливает независимую работу по остальному корпусу.

## 5. Единственный источник статусов

Статусы вычисляются из текущего содержимого, правил и проверяемых evidence.
Не редактируй галочки Markdown-таблицы или audit-state вручную.

Существующая инфраструктура уже умеет:

- хранить отдельные результаты каждой проверки по Q/B;
- связывать их с JSON-блоком, видимым вопросом, теорией и общим прологом;
- проверять дополнительные объявленные зависимости и связанные артефакты;
- различать историческое чтение, автоматические сигналы и текущую приёмку;
- сохранять открытые findings до явного разрешения;
- учитывать B1 отдельно от B0;
- сохранять две фазы независимого ревью;
- убирать из очереди только проверки с актуальным PASS;
- пересчитывать общие таблицу, снимок и checkpoint.

Не переписывай эту систему заново перед обработкой корпуса. Если обнаружишь конкретную
ошибку зачёта, воспроизведи её небольшим тестом, исправь минимально и проверь регрессию.
Не добавляй новые колонки, которые всегда UNVERIFIED, вместо рабочего сохранения результата.

## 6. Обязательные проверки по каждому файлу и блоку

| Название | Поле evidence / снимка | Что подтверждает |
|---|---|---|
| SCHEMA | `schema_structure`, вычисляется инструментом | Схема, межполевые инварианты, последовательность Q/B, связь заголовков |
| CONTENT | `content_review` | Все четыре варианта, единственность ключа, отсутствие двусмысленности |
| FACTS | `factual_correctness` | Факты и условия применимости сверены с источниками и версиями |
| LINKAGE | `source_linkage` | Ответы соответствуют видимому вопросу и связанной теории |
| SECTIONS | `sections_consistency` | Объяснения верны и относятся к текущему тексту каждой опции |
| SFPL | `sfpl` | Сопоставимы форма, смысловой каркас и детализация A/B/C/D |
| ANSC | `ansc` | Каждый вариант полноценно отвечает на все части видимого вопроса |
| RU | `russian_readability` | Вопрос, теория, варианты и объяснения естественно читаются по-русски |
| INDEPENDENT | `independent_review` | Проверка выполнена участником, отличным от автора |
| BLIND | `blind_review` | Выбор и наблюдения зафиксированы до раскрытия ключа и теории |
| FINAL | `final_acceptance` | Явная итоговая приёмка при закрытых зависимых проверках и находках |

SCHEMA не записывается вручную в coverage[].checks. Его выполняет валидатор.
Остальные десять полей могут присутствовать в одном результате, но каждое получает
собственный вердикт и краткое обоснование. Один общий REVIEWED их не заменяет.

Для каждой пары файлов должны быть доступны относительные пути, этап, количество Q/B,
хеши, покрытие каждой проверки, остаток, находки, evidence и следующее действие.
Один дефектный блок не скрывается средним значением или высоким процентом по файлу.

## 7. Семантика статусов

- `NOT_RUN`: проверка не выполнялась; отсутствие evidence не равно дефекту и не равно PASS.
- `IN_PROGRESS`: выполняется; есть реальное текущее задание.
- `PARTIAL`: часть заявленного скоупа подтверждена, остальная ещё не принята.
- `PASS`: критерий подтверждён на всём заявленном скоупе текущей версии.
- `FAIL`: есть подтверждённый незакрытый дефект.
- `STALE`: доказательство не подходит к изменившемуся содержимому/правилам/зависимостям.
- `BLOCKED`: указан конкретный блокер; для результата обязательно поле `blocker`.
- `UNVERIFIED`: доказательств недостаточно для заявленного вывода.

REVIEWED в старых записях означает чтение, а не приёмку. SIGNALS/NO_SIGNALS относятся
к автоматической диагностике и не являются статусами ручного редакторского ревью.

Файл получает FINAL PASS только при актуальном PASS всех обязательных проверок всех
его блоков, явном FINAL и отсутствии блокирующих находок. Нельзя закрывать FILE целиком
после удачной проверки одного Q или одной версии API.

## 8. Экономия общего расхода

Считай полезной единицей **принятый неизменённый блок**, а не количество агентов или
объём сгенерированного текста. Учитывай контекст, генерацию, исправление ошибок,
повторные проходы и затраты координатора.

Рабочие правила:

1. Сначала локальная диагностика, затем конкретное LLM-задание.
2. Правила читаются один раз за контекст; перечитывание — при изменении или необходимости.
3. Координатор читает большой промпт; исполнителям передаются короткие задания и нужные
   части правил, без всей истории и многомегабайтных отчётов.
4. Не выводи в чат весь JSON, сотни успешных строк, полный diff корпуса и чужие отчёты целиком.
5. CONTENT/FACTS/LINKAGE/SECTIONS/SFPL/ANSC/RU можно проверять одним чтением раскрытого пакета,
   сохраняя отдельные вердикты.
6. Независимое ревью объединяет blind-фазу A и раскрытую фазу B в одном контексте ревьюера.
7. Повторный проход нужен только для изменённых блоков и зависимых проверок.
8. Не переписывай хорошие тексты ради одинакового количества слов или личного вкуса.
9. Полный audit запускай на контрольных точках, а не после каждой опции.
10. Переиспользуй первичный источник для связанных утверждений одной темы с точной областью.
11. Для PASS достаточно компактного проверяемого вывода; длинный пересказ теории не нужен.
12. Не организуй бесконечные круги независимого ревью «на всякий случай».

У текущего консервативного контракта изменение любой части JSON-блока или его Q-текста
инвалидирует результаты блока целиком. Не планируй экономию на ещё не реализованной
инвалидации отдельных полей. Изменение соседнего независимого блока не обнуляет тему.

Перед новым масштабом работы можно сделать небольшой пилот 2–4 блока; первоначальный
пилот на 5 блоках уже проведён. Не повторяй пилот только из-за смены чата. При смене
провайдера проверь качество на одном небольшом пакете и затем продолжай общий план.

Фиксируй размер входа, принятые блоки, возвраты и расход, если он реально доступен.
Размер JSON в байтах не называй количеством токенов. Дешёвая цена модели не доказывает
меньший расход недельного лимита. Не выдумывай остаток лимита и время его восстановления.

## 9. Дополнительные агенты: только экономный режим

Агенты разрешены, но только если инструмент позволяет явно выбрать дешёвую модель.
Проверь реально доступные модели и настройки; не переноси названия из другой среды.
Если выбор недоступен или стоимость неизвестна, не наследуй дорогую модель автоматически.
Продолжай последовательную работу и честно оставь независимое ревью незавершённым,
если получить отдельного исполнителя нельзя.

Начинай максимум с двух дополнительных агентов одновременно. Используй минимально
достаточный reasoning. Не создавай дерево субагентов и отдельные пользовательские задачи
вместо внутренних исполнителей. Не увеличивай параллельность без измеримой пользы.

Предпочтительная схема: автор делает небольшой пакет, отдельный дешёвый ревьюер проходит
фазы A/B. Координатор распределяет темы, проверяет артефакты и конкретные спорные места.
Он не обязан заново читать весь контент за каждым агентом.

Предыдущие большие авторские пакеты дешёвой модели вызывали дорогие возвраты: пропущенную
полноту ответа, инверсию ключа и появление второго истинного варианта. Не повторяй эту
схему механически. Начни с 2–4 блоков ревьюеру, с явной защитой каждого wrong.

Сложный вопрос поднимай на конкретном фрагменте, а не отправкой всей темы дорогой модели.
При повторяющейся ошибке уточни контракт или сократи пакет; не оплачивай повтор того же
неверного рассуждения. Эскалация сверх разрешённого бюджетного режима требует отдельного решения.

## 10. Выбор пакета и подготовка авторского контекста

```bash
python3 scripts/mcq-workflow.py next --size 4
```

Вывод содержит topic, точные blocks, незакрытые checks и отдельно отложенные BLOCKED-темы.
Команда учитывает весь корпус; обновлённое множество идёт перед TODO. Полностью принятые
блоки не попадают в next. Если остались только блокеры, `complete` остаётся false.

Подставь реальные значения. Пример команд:

```bash
MCQ_TOPIC='ai-ml/agentic-patterns-interview.json'
MCQ_BLOCKS='Q1:B0,Q2:B0,Q3:B0,Q4:B0'
python3 scripts/mcq-workflow.py packet --topic "$MCQ_TOPIC" --blocks "$MCQ_BLOCKS" --output work/mcq-author-packet.json
```

`packet` содержит ключ, все варианты и sections выбранных блоков, соответствующую теорию,
пролог, хеши, статусы и открытые находки. Не передавай этот файл в слепую фазу.
Выходной файл не перезаписывается: для нового пакета используй новое имя.

В список blocks входят устойчивые Qn:Bn через запятую. Диапазоны и просто Qn не подходят.
Нельзя забыть B1 только потому, что большинство вопросов имеет B0.

Перед изменением прочитай существующую опцию целиком, её sections, вопрос и нужную теорию.
Пакет не освобождает от чтения дополнительных объявленных смысловых зависимостей.

## 11. CONTENT: четыре варианта и единственность ключа

Для каждого блока:

1. Установи, какой вопрос реально видит пользователь.
2. Выдели все части вопроса и существенные условия.
3. Прочитай каждый A/B/C/D без предположения, что существующий correct верен.
4. Проверь правильный ответ и его границы применимости.
5. Попробуй защитить каждый wrong: нет ли версии, режима или допустимого прочтения,
   в котором он тоже отвечает на вопрос верно.
6. Если два варианта истинны, уточни условие или исправь конкретный вариант.
7. Проверь, что осталось ровно одно правильное решение.
8. Сверь все объяснения после изменения ключа, опции или условий.

False у wrong — ожидаемое свойство. Нельзя превращать дистрактор в истину ради исправления
«фактической ошибки». Исправляй дефект задания или объяснения, сохраняя правдоподобную
ошибочную модель неверного ответа.

Не объявляй wrong дефектом только потому, что он ложен. Находка должна объяснять,
почему нарушены критерии MCQ: второй правильный, неподходящий вопрос, нелепый дистрактор,
слишком очевидная подсказка, неработающее опровержение, плохой язык и т. п.

## 12. FACTS: источники, версии и неопределённость

Первичные источники предпочтительны: спецификации, официальная документация,
исходный код соответствующей версии, release notes, стандарты и оригинальные публикации.
Версионные утверждения, defaults, API, ограничения, числа, лицензии и рекомендации
обязательно сверяй с применимой версией, а не только с памятью модели.

Сохраняй для источника:

- URL;
- `used_for`: какое конкретное утверждение проверено, для каких Q/B;
- `version`: версия/редакция и существенные условия;
- `checked_at`: реальная дата проверки.

Наличие URL или заполненного sidecar не означает fact-check. Поле used_for не должно
быть общим «вся тема», если проверен один API. Чтение источника можно переиспользовать
для нескольких блоков только при действительно общей проверенной предпосылке.

Факт в обучающей теории должен быть корректен даже при наличии ложных вариантов.
Если теория ошибочна, исправь её и зависимые объяснения. Не объявляй wrong правильным
только потому, что он повторяет ошибку устаревшего Markdown.

Без доступного источника сохраняй конкретное UNVERIFIED/BLOCKED и продолжай независимые
блоки. Не подставляй правдоподобную ссылку и не принимай весь файл по одному источнику.

## 13. LINKAGE: видимый вопрос и теория

Реальный вопрос берётся из Markdown. Скрытый `question_text` JSON не должен содержать
единственное условие, оправдывающее ключ. Структурная синхронизация заголовков не заменяет
проверки того, что ответы действительно отвечают на вопрос.

Если заголовок спрашивает определение и пример, все варианты должны предлагать определение
и пример. Если нужен механизм и следствие, один correct не должен быть единственным,
кто раскрывает оба. Нельзя незаметно сузить вопрос до одного удобного тезиса.

Теория должна позволять понять правильный ответ и опровергнуть конкретные wrong.
Ссылка на соседний Q или внешний документ не заменяет отсутствующее существенное условие.
Если общая предпосылка вынесена в пролог, включи её в чтение и зависимости.

Не расширяй вопрос до всей темы ради одного блока и не превращай варианты в мини-конспекты.
Размер исправления должен соответствовать дефекту.

## 14. SECTIONS: обучающие объяснения

У correct проверяются `explanation`, `example`, `when_to_apply`, `edge_cases`, `related`.
У каждого wrong — `what_actually`, `source_of_confusion`, `if_it_were_true`, `how_it_should_be`.
Проверяй также любые дополнительные пользовательские поля, предусмотренные схемой.

Объяснение должно относиться к текущему тексту именно этой опции. После перестановки
вариантов или изменения correct проверь соответствие роли, всех sections и примеров.
Недостаточно поменять только boolean или label.

Проверь факты, выводы, код, версии, внутреннюю непротиворечивость и полезность объяснения.
Контрфакт у wrong показывает следствие ошибочной модели, а не повторяет её другими словами.
Related должен помогать обучению, а не добавлять неподтверждённый факт для объёма.

Хорошие sections не компенсируют неполные или выделяющиеся тексты вариантов до выбора.
SFPL и ANSC сравнивают прежде всего те ответы, которые видит решающий пользователь.

## 15. SFPL: правильный ответ не выделяется формой

Сравни A/B/C/D по нескольким признакам вместе:

- тип ответа: определение, механизм, сравнение, список, условие, результат;
- смысловой каркас: например «условие → действие → следствие»;
- степень конкретности и число существенных тезисов;
- глубина объяснения механизма;
- оговорки, условия и ограничения;
- наличие примеров, кода, API, чисел;
- длина, оформление, списки и пунктуация;
- естественность и профессиональность языка.

Ищи особенно:

- содержательный профессиональный correct против трёх поверхностных wrong;
- механизм или обоснование только в correct;
- единственный полный ответ на многосоставной вопрос;
- полный список только у правильного варианта;
- уникальную оговорку, пример, API или условие, выдающее ключ;
- короткий точный correct на фоне искусственно раздутых wrong;
- хороший русский correct на фоне неестественных дистракторов.

Одинаковое число слов, запятых или предложений не подтверждает SFPL. Не назначай correct
обязательную вторую/третью позицию в рейтинге длины. Не выкидывай API ради regex.
Не добирай символы пустыми оборотами и не клонируй один шаблон четырежды.

Слабые дистракторы улучшаются содержательно: полноценный ответ того же типа с правдоподобной
ошибкой. Избыточную лекцию из correct можно перенести в sections, но необходимые условия
и части ответа остаются в опции.

Вердикт содержит конкретное сравнительное наблюдение. «Длины похожи» недостаточно.

## 16. ANSC: полнота каждого ответа

Разложи видимый вопрос на необходимые части и проверь каждую для всех четырёх вариантов.
Неверный вариант тоже обязан быть законченным ответом на этот вопрос; его ошибка лежит
в содержании, а не в отсутствии половины задания.

Примеры дефектов:

- вопрос просит «что это и когда использовать», три wrong отвечают только «что это»;
- вопрос просит сравнить X/Y, дистрактор описывает только X;
- вопрос просит перечислить виды и различия, correct содержит классификацию,
  а остальные — отдельные элементы без принципа;
- вопрос о результате кода, один ответ предлагает совет по стилю вместо результата.

Полнота не означает длину учебной главы. Нужен достаточный ответ в заявленном объёме
вопроса. Не закрывай ANSC ссылкой на sections: пользователь выбирает текст опции.

SFPL и ANSC получают разные результаты: варианты могут одинаково выглядеть и быть
одинаково неполными, либо быть полными, но сильно различаться формой.

## 17. RU: человекочитаемость на русском языке

Проверка RU обязательна независимо от автоматических сигналов. Прочитай:

- видимый вопрос;
- нужную теорию и общий пролог;
- все A/B/C/D;
- все sections, включая example и related;
- русскую прозу вокруг кода, подписи ссылок, комментарии и пояснения примеров;
- текст в таблицах и диаграммах, если он относится к проверяемому материалу.

Критерии: понятность при первом последовательном чтении, естественная техническая
терминология, грамматика, однозначные местоименные отсылки, логические связи,
завершённые предложения, отсутствие пустых оборотов, канцелярита и искусственных метафор.

Не используй выражения вроде «поле-голое значение», «родится пустотою» или неопределённого
«тела» вместо конкретного объекта. Не заменяй общепринятые термины неестественными кальками.
Имена API, идентификаторы и обычные технические термины сохраняются.

Проверь одинаковое качество языка correct и wrong. Нельзя сделать правильный вариант
единственным понятным и грамматически аккуратным.

Редакторская правка сохраняет технический смысл и конкретную ошибочную модель wrong.
После существенного изменения формулировки повтори связанные CONTENT/FACTS/SECTIONS.
Процент кириллицы, длина фразы и отсутствие regex-предупреждений не дают RU PASS.

## 18. Точечные правки и проверки автора

Вноси минимальные обоснованные изменения. Не меняй порядок и ID без необходимости.
Сохраняй все существующие блоки; не удаляй сложный B1, чтобы снять runtime или audit FAIL.
При изменении порядка следи, чтобы текст, correct и sections перемещались вместе.

После правок выбранной темы:

```bash
bash scripts/verify-mcq-json.sh "modules/quiz-app/src/main/resources/seed/mcq/$MCQ_TOPIC"
bash scripts/mcq-tools/gates.sh "modules/quiz-app/src/main/resources/seed/mcq/$MCQ_TOPIC"
```

Если изменён Markdown:

```bash
bash scripts/verify-md-no-mcq.sh "cheatsheets/interview/${MCQ_TOPIC%.json}.md"
```

Сохраняй exit code и существенную диагностику. Code 1 эвристического gate — повод для
разбора, а не автоматическое доказательство плохого MCQ. Code 2 — ошибка исполнения,
её нельзя переклассифицировать в содержательный finding или игнорировать.

Не снижай пороги ради PASS. Обоснованное ложное срабатывание сохраняется с конкретным
Q/B, названием сигнала и объяснением. Структурный дефект исключением не закрывается.

## 19. Создание зафиксированного слепого пакета

После завершения авторских правок:

```bash
MCQ_RUN="$(date -u +%Y%m%dT%H%M%SZ)-agentic-q1-q4-r1"
python3 scripts/mcq-workflow.py prepare --topic "$MCQ_TOPIC" --blocks "$MCQ_BLOCKS" --run "$MCQ_RUN"
```

Идентификатор должен быть новым; дата и тема в примере заменяются реальными.
Команда создаёт `docs/mcq-quality/runs/<run>/manifest.json` и `blind-input.jsonl`.
В blind-input только путь темы, Q/B, видимый вопрос и label/text вариантов.
Ключ, sections, теория, прежние выборы и объяснения туда не попадают.

Ревьюер должен получить свежий контекст. Если он уже видел ключ, попросить его «забыть»
недостаточно. Контекст автора или общей переписки не является слепым.

Сам факт доступа агента к общему репозиторию не гарантирует слепоту. Передай только
разрешённый файл и запрети чтение остальных источников до фиксации A.

## 20. Короткое задание независимому ревьюеру: фаза A

Передай следующее, подставив путь и реальное имя контекста:

> Ты независимый решающий MCQ. Сейчас фаза A до раскрытия ключа. Прочитай только
> указанный blind-input.jsonl. Не читай seed, Markdown-теорию, авторский пакет,
> evidence, прошлые ответы и историю координатора. Не изменяй файлы корпуса.
> Для каждого Q/B выбери ответ и дай короткую проверяемую причину. При неоднозначности
> используй AMBIGUOUS, при отсутствии верного — NO_VALID_OPTION, при недостатке знания —
> UNSURE. Отдельно назови конкретные признаки, по которым один вариант выделяется формой
> или полнотой. Верный выбор по знанию темы сам по себе не доказывает подсказку формы.
> Верни JSON-массив с q_number, block_idx, choice, reason, form_signals. Ровно один
> элемент на каждый блок экспорта. Не создавай субагентов. Дождись раскрытия от координатора.

Формат ответа:

```json
[
  {
    "q_number": 1,
    "block_idx": 0,
    "choice": "B",
    "reason": "Краткая проверяемая причина.",
    "form_signals": []
  }
]
```

Список form_signals пустой только если не обнаружены конкретные признаки. Не требуй
от исполнителя скрытой внутренней цепочки рассуждений; нужны вывод и проверяемое основание.

## 21. Фиксация A и раскрытие B

Сохрани массив ответа, затем выполни:

```bash
python3 scripts/mcq-workflow.py phase-a --run "$MCQ_RUN" --answers work/mcq-phase-a-answers.json --reviewer reviewer-context-01
python3 scripts/mcq-workflow.py reveal --run "$MCQ_RUN" --author author-context-01 --reviewer reviewer-context-01
```

Имена отражают действительных автора и независимого участника. `--model`, если указан,
фиксирует реально использованную модель; этот флаг её не запускает и не выбирает.

Phase A и её квитанция сохраняются до раскрытия. Повторная запись запрещена. Reveal
проверяет актуальность снимка и публикует каталог `disclosure/` с `review-input.json`,
`reveal.json`, `evidence-draft.json`. Публикация атомарна: неполный каталог не считается
раскрытием. При ошибке не придумывай новый timestamp вручную; исправь причину и повтори
разрешённую операцию либо создай новый run.

После reveal этот контекст никогда больше не считается слепым по раскрытым блокам.
Ошибочный выбор фазы A не исправляется задним числом. В фазе B объясняется причина
расхождения: незнание версии, неоднозначность задания, ошибка ключа или другое.

## 22. Короткое задание независимому ревьюеру: фаза B

Передай тому же ревьюеру раскрытый пакет:

> Фаза A уже сохранена. Прочитай review-input.json, нужные правила и первичные источники.
> Сопоставь свой выбор с ключом без изменения исходного ответа A. Проверь все четыре
> опции; попробуй защитить каждый wrong и исключи второй правильный ответ. Проверь
> факты/версии, видимый вопрос и теорию, каждое section, SFPL, ANSC и RU отдельно.
> При SFPL/ANSC оценивай тексты опций до выбора; хорошие sections не компенсируют их
> неполноту. Ложность wrong ожидается и сама по себе не является finding.
> Верни для каждого Q/B отдельные статусы и краткие конкретные причины. Для дефекта
> укажи поле/label, короткую цитату, последствие, источник и предлагаемую правку.
> Сохрани проверенные claims/версии/URL и ограничения. Не изменяй корпус и phase A,
> не создавай субагентов. Не проставляй FINAL за координатора без проверки всех
> предусловий и не объявляй весь файл принятым по части пакета.

Один независимый проход может закрывать несколько проверок; отдельный агент на каждую
колонку не нужен. Совпадение модели автора и ревьюера допустимо при разных реальных
контекстах; смена модели в том же контексте не создаёт независимость автоматически.

## 23. Evidence: что сохранять и как импортировать

Черновик расположен в:
`docs/mcq-quality/runs/<run>/disclosure/evidence-draft.json`.

В нём заранее заполнены пути, полные/блочные хеши, правила и ссылки на две фазы.
`checks` пустые: это намеренно не готовая запись. Заполни только выполненные проверки.
Каждый результат — объект `{ "status": "PASS|FAIL|...", "reason": "конкретное основание" }`.
Для BLOCKED добавь `blocker`. Обнови date на фактическое завершение с часовым поясом.

Обязательные поля записи:

- review_id, reviewer, author, model (либо null), date, kind;
- paths.mcq/theory и исходные sha256;
- rules_sha256;
- coverage каждого Q/B с его sha256 и отдельными checks;
- findings, sources, limitations;
- для двух фаз — phase_a, revealed_at, workflow_run и реальные сохранённые артефакты.

Для полного независимого разбора допускается отдельный `review_artifact: {path, sha256}`.
Сохраняй его внутри репозитория, чтобы он не исчез при передаче. Не привязывай обязательное
доказательство только к игнорируемому work/ или истории инструмента другой платформы.

Источники — объекты с url, used_for, version, checked_at. Поле used_for связывает источник
с конкретными проверенными фактами. В `limitations` укажи существенные границы;
ограничение, противоречащее PASS, требует другого статуса, а не мелкого примечания.

Невыполненные проверки не вставляй как NOT_RUN поверх старого результата. Просто опусти
их: они останутся прежними либо NOT_RUN при отсутствии доказательств.

Импорт:

```bash
python3 scripts/mcq-workflow.py record --input "docs/mcq-quality/runs/$MCQ_RUN/disclosure/evidence-draft.json"
python3 scripts/mcq-workflow.py status --topic "$MCQ_TOPIC"
```

Record не переписывает существующий review_id, проверяет текущие полные и блочные хеши,
правила, артефакты, две фазы и действительность PASS. Новые двухфазные результаты требуют
квитанции workflow; прежние валидные evidence остаются читаемыми без миграции.

Проверка полей и SHA не доказывает, что человек или LLM действительно прочитали источник.
Не фабрикуй evidence. Инструмент проверяет воспроизводимость привязки, а ты отвечаешь
за обоснованность содержательного вывода и честность происхождения.

## 24. Находки, исправления и разрешение противоречий

Подтверждённый дефект сохраняется как finding:

```json
{
  "id": "topic-q1-b0-sfpl-01",
  "check": "sfpl",
  "blocks": ["Q1:B0"],
  "status": "OPEN",
  "reason": "Конкретный отличающий признак и его последствие."
}
```

Открытый finding имеет приоритет над старым и новым PASS. Для закрытия нужна новая запись
с тем же id/check/blocks, status RESOLVED, причиной и актуальным PASS той же проверки
на затронутых блоках. Простой повтор PASS без resolution ничего не закрывает.

Не переиспользуй идентификатор для другого дефекта, другой проверки или других блоков.
При сомнении сохраняй вопрос для разбирательства, а не подтверждённый FAIL без основания.
Разногласие автора и ревьюера разрешается конкретным условием, источником или примером.

Сначала сохрани результат неудачного ревью, затем исправляй. Старые FAIL/STALE и слепые
ответы не удаляются для красивой истории. Новая попытка получает новый run/review_id.

Если исправление затронуло текст опции или видимый вопрос, новый blind-проход делается
в свежем контексте по изменённому пакету. Если контекст видел ключ, слепота не восстанавливается.

## 25. Актуальность и дополнительные зависимости

Устойчивый идентификатор: относительный путь production seed + q_number + block_idx.
Имя файла без каталога, номер вопроса без B и Git commit без содержимого недостаточны.

Текущий блочный контракт учитывает:

- JSON всего блока, topic_slug и q_number;
- нормализованный видимый заголовок и тело соответствующего Q;
- общий пролог Markdown;
- три файла применимых правил;
- дополнительные явно объявленные `coverage[].dependencies`;
- связанные review_artifact и blind-артефакты.

Изменение постороннего файла не обнуляет блок. Изменение общего определения может
инвалидировать несколько блоков или всю тему. Хеширование не обнаруживает само, что
Q7 зависит от утверждения Q2: объяви такую зависимость и прочитай источник.

Перед импортом новых результатов полные хеши пары должны совпадать с текущими.
Если другой автор поменял непересекающийся фрагмент, сверка и обновление metadata должны
быть осмысленными, а не заменой SHA для подавления STALE. Уже зарегистрированная
приёмка сохраняется для неизменённых блоков по блочным хешам.

Не редактируй правила без конкретной необходимости: их изменение затронет применимость
всех связанных evidence. Изменения оперативных инструкций делай в workflow/промпте,
если критерии качества действительно не меняются.

## 26. Полные проверки и частота запуска

После изменения валидаторов, evidence или workflow:

```bash
python3 -m unittest discover -s scripts/tests -p 'test_mcq*.py'
bash scripts/verify-mcq-json.sh --all
```

Тесты включают частичное покрытие, B1, STALE, посторонние изменения, сохранность findings,
неполный FINAL, отсутствие источников, blind-экспорт, две фазы, запрет перезаписи,
неполное раскрытие и возобновление после сбоя. Добавляй тест на реальный найденный дефект,
а не зеркальный тест, повторяющий реализацию без проверки поведения.

При изменении Java-импортера или runtime запускай относящиеся к ним тесты. После обычной
редакторской правки не запускай весь проект и все браузерные тесты без причины.

Полная контрольная точка:

```bash
python3 scripts/mcq-workflow.py sync
```

Sync вызывает полный audit и обновляет JSON, Markdown-таблицу и checkpoint. Он не требует
закрытого корпуса, поэтому exit 0 означает успешную генерацию, а не FINAL для всех файлов.

Для проверки заявленного завершения:

```bash
python3 scripts/mcq-workflow.py sync --require-complete
```

При незавершённых файлах команда возвращает 1 и сохраняет точный остаток.
Не меняй этот режим на обычный sync только ради успешного exit code.

## 27. Рабочий цикл до завершения

Повторяй:

1. Получить следующий незакрытый пакет и проверить владельца темы.
2. Прочитать нужный контекст и действующие доказательства.
3. Получить точечные автоматические сигналы.
4. Проверить и исправить конкретные дефекты автора.
5. Проверить изменённую пару и зафиксировать снимок prepare.
6. Провести независимые A/B с реальным разделением времени и контекста.
7. Сохранить findings, исправить подтверждённые дефекты, повторить зависимые проверки.
8. Импортировать действительный результат; проверить вычисленный topic status.
9. На контрольной точке выполнить sync, затем сохранить checkpoint с конкретным
   `--next-action`, если нужно передать незавершённый пакет; обычный sync сам
   перезаписывает checkpoint стандартным следующим действием.
10. Перейти к следующему пакету.

Не останавливайся после первого зелёного файла. BLOCKED не исключается из общего плана,
но позволяет переключиться на независимые темы. Полностью проверить весь корпус и
уместить его в произвольный оставшийся недельный лимит заранее обещать нельзя.

## 28. Checkpoint без истории чата

После законченного пакета:

```bash
python3 scripts/mcq-workflow.py checkpoint --next-action 'Точная следующая работа и существенный незакрытый вопрос.'
```

Если в этой точке нужен полный `sync`, выполни его **до** команды с `--next-action`:
он обновляет checkpoint и заменяет пользовательское следующее действие стандартным.

Checkpoint сохраняет время, HEAD, актуальные количества и статусы, следующий пакет,
пути источников истины и ограничения измерения расхода. Он не является новой базой
доказательств и не хранит копию всего корпуса.

В evidence/run дополнительно должны остаться исходные хеши, реальный Q/B-скоуп,
изменения и находки, проверенные claims/источники, причины повторного ревью.
Если пакет ещё выполняется, допиши next_action с его run и незавершённой фазой.

При продолжении прочитай checkpoint, выполни doctor и next/status, проверь изменения.
Не начинай новый полный смысловой аудит только потому, что отсутствует история чата.
Не обещай фоновое продолжение, автоматическое пробуждение или восстановление лимита
без реально настроенного механизма и полномочий.

## 29. Уборка старых планов и скриптов

Старый возраст файла не является доказательством ненужности. Перед удалением установи:

- относится ли он к этому процессу;
- заменён ли действующей командой/правилом;
- кто его вызывает: CI, hooks, Gradle, другие скрипты, локальные адаптеры;
- содержит ли он уникальные источники, решения или evidence;
- есть ли нужная версия в Git, включая текущие незакоммиченные изменения.

Tracked-файл, совпадающий с версией в Git, можно удалить локально с указанием commit/path
для восстановления. Не удаляй untracked уникальный материал, называя Git страховкой:
его ещё нет в истории. Не создавай commit без отдельного поручения.

Сохраняй реальные evidence, включая неудачные проходы. Удаляй конкурирующие инструкции,
заведомо устаревшие runtime-адаптеры и повторяющиеся планы после проверки замены.
Исторические ссылки в evidence можно оставить как происхождение; это не активные команды.

Шесть противоречивых старых JS workflow уже удалены при подготовке инфраструктуры.
Причины и commit восстановления приведены в workflow.md. Не восстанавливай их ради
автоматической генерации одинаковых запятых или обхода новых критериев.

## 30. Что нельзя принимать за успех

Запрещены следующие подмены:

- JSON PASS вместо CONTENT/FACTS/RU;
- NO_SIGNALS вместо SFPL/ANSC/RU PASS;
- старый AUDITED или совпавший commit вместо текущего доказательства;
- наличие URL вместо прочитанного источника;
- один правильный выбор ревьюера вместо отсутствия подсказок формы;
- самопроверка автора вместо INDEPENDENT;
- «забыл ключ» вместо нового слепого контекста;
- общий процент успешности вместо незакрытого второго блока;
- качественные sections вместо полноценности самих вариантов;
- высокий средний балл вместо открытого FAIL;
- ручная зелёная галочка в таблице вместо evidence;
- достигнутый лимит вместо завершения корпуса.

Отдельно не исправляй опции исключительно под метрики: одинаковая пунктуация может
скрывать разную смысловую полноту, а буквальные клоны ухудшают задания.

## 31. Критерии завершения всего поручения

Работа завершена только когда:

- все production-пары представлены в плане и вычисленном снимке;
- учтены каждый Q и каждый B;
- все обязательные проверки каждого блока имеют актуальные доказательства;
- проверены и блоки без автоматических сигналов;
- подтверждённые дефекты исправлены, findings явно закрыты;
- ни один correct не выдаётся качеством языка, каркасом или полнотой относительно wrong;
- вопросы, теория, варианты и sections читаются как естественный русский технический текст;
- структурные проверки проходят, эвристические сигналы разобраны по существу;
- независимость и две фазы подтверждены сохранёнными артефактами;
- никакие FAIL, STALE, BLOCKED, UNVERIFIED или NOT_RUN не спрятаны под общим DONE;
- выполнены итоговые проверки и `sync --require-complete`;
- сохранён переносимый итог и короткий отчёт.

Если лимит, отсутствие источника или доступного независимого контекста мешает закончить,
оставь точное незавершённое покрытие и следующий шаг. Не выдумывай PASS и не обещай
автоматическое продолжение. Накопленный результат должен сохраняться между запусками.

## 32. Общение и финальный отчёт

Во время работы сообщай кратко: текущий пакет, реально завершённое покрытие, существенные
дефекты, внесённые исправления и конкретный блокер. Не пересказывай каждый успешный тест
и не публикуй отчёты всех агентов целиком.

В финальном сообщении укажи:

- файлов и блоков всего / принято / осталось;
- покрытие обязательных проверок;
- основные исправленные классы дефектов;
- оставшиеся блокеры и неопределённость;
- что проверено инструментами;
- расход только в доступной достоверной мере;
- ссылки на план, таблицу, checkpoint и evidence;
- следующий конкретный пакет, если работа прервана.

Начинай с doctor, актуального status и next. Используй подготовленную инфраструктуру,
сохраняй действующие результаты и продолжай полный цикл корпуса без повторных формальных
подтверждений после каждого пакета.
