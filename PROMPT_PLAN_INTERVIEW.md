# Переносимый процесс MCQ

Точка входа для автора, ревьюера и следующей LLM. Провайдер, IDE и личные каталоги
не являются частью контракта. Единственный стандарт: [docs/mcq-quality-standard.md](docs/mcq-quality-standard.md).
Состояние: [docs/mcq-refactoring-state.md](docs/mcq-refactoring-state.md).

## Начало работы

1. Прочитать применимые AGENTS.md и стандарт. Проверить git status, HEAD и чужие изменения.
2. Выполнить `python3 scripts/mcq-audit.py --output work/mcq-audit/inventory.json`.
3. Взять одну тему или ограниченный набор её блоков из `review_queue`. Не брать файл,
   который одновременно изменяет другой исполнитель, без согласования владения.
4. Зафиксировать относительный путь, Q/B, SHA-256 JSON и Markdown, хеш стандарта,
   разрешённый скоуп, открытые находки и следующий этап.
5. Перед применением результата проверить исходные хеши. При расхождении перечитать
   изменения и согласовать patch; не перезаписывать новый контент старым пакетом.

Зависимость для локальных проверок: `python3 -m pip install -r scripts/requirements-mcq.txt`.
Все команды выполняются из корня репозитория, если не указан абсолютный путь.
Никаких reset раунда, commit/push, платных API или фоновых циклов по умолчанию.

## Пакет автору

Передай файл JSON, парный Markdown (либо полный текст затронутых Q), стандарт,
идентификаторы блоков, хеши, открытые находки и ограничения версии. Стем — видимый
заголовок Markdown. Локальная теория должна быть фактически корректной.

Задание автору:

> Исправь только указанные дефекты и зависимые sections. Сначала проверь единственность
> ответа и модель каждого wrong. Сохрани Q/B и смысл вопроса. Не исправляй неверный
> дистрактор в истинный. Не подгоняй фразы под regex. Верни patch, список Q/B,
> краткое обоснование, источники, результаты проверок и незакрытые вопросы.

Разрешённые режимы: audit, targeted repair, fact refresh, schema repair, full rewrite
по отдельному явно заданному скоупу. Старый режим «перепиши весь файл за тик» не обязателен.

## Пакет содержательному ревьюеру

Отдельный контекст получает итоговую пару и стандарт. Это ревью с доступным ключом.

> Для каждого Q/B прочитай видимый вопрос, тело, все четыре варианта и sections.
> Попытайся защитить каждый wrong. Проверь ключ, условия, факты, обучающую связь,
> естественный язык и одинаковый скелет опций. Ложность wrong — ожидаемое свойство,
> а не finding. Для находки укажи Q/B/label/field, точный фрагмент, последствие,
> источник и предлагаемую правку. Для каждого блока верни краткий вердикт.
> Не объявляй fact freshness всего файла, если проверена только часть фактов.

Сохрани identity ревьюера, kind=independent_nonblind, хеши пары, покрытие, findings,
проверенные источники и ограничения. Не объявляй такой проход слепым.

## Отдельный пакет проверки формы и полноты

Использовать [протокол SFPL/ANSC](docs/mcq-quality/surface-parity-rules.md).
Для каждого A/B/C/D вернуть тип ответа, смысловой каркас, покрытие частей вопроса,
конкретность и заметные особенности формы; затем два вердикта SFPL и ANSC с причинами.
Выделить случай «полный профессиональный correct против трёх поверхностных wrong»,
даже если длины, предложения и пунктуация похожи. До раскрытия ключа фиксировать
наблюдения о выделяющихся вариантах; после — проверять правдоподобие заблуждений
и корректность объяснений. Успешное решение вопроса по знанию темы не считать утечкой формы.

Автор получает конкретные отличия и чинит только соответствующий пакет. После правки
проверяются все четыре опции/sections и повторяется зависимое ревью. Не раздувать текст
ради метрик. Размер пакета и стоимость дополнительных ревью ограничены бюджетом пользователя.

## Отдельный пакет редакторской проверки русского языка

Прочитать [RU-протокол](docs/mcq-quality/russian-readability-rules.md), видимые вопросы,
тела Q, все A/B/C/D и все sections, включая прозу примеров и пояснения ссылок.
Проверить понятность при первом чтении, грамматику, связность, естественность терминов,
пустые обороты и машинный стиль. Проверять одинаково строго correct и wrong.
Не переводить имена API/код в искусственные русские метафоры.

Вернуть отдельный RU PASS/FAIL/UNVERIFIED по каждому Q/B, проверенные поля, точные цитаты
дефектов, краткую причину и предлагаемую редакцию. Отсутствие автосигналов не даёт PASS.
Редакция должна сохранить технический смысл и ошибочную модель wrong; после правок
перепроверяются единственность ключа, sections и сравнительная форма. Хеши и покрытия
передаются по общему контракту; RU не зачтён только потому, что уже было общее ревью.

## Пакет слепому ревьюеру

Экспорт для нового контекста:

```bash
python3 scripts/mcq-answer-parity-gate.py <seed.json> --blind-export <outside-repo-output.jsonl>
```

В экспорт входят видимый вопрос, A/B/C/D и идентификатор; correct, sections и скрытый
question_text отсутствуют. Метки сохраняются для последующего сопоставления.
Не передавать исходники, sidecars, историю исправлений и ключ рядом с экспортом.

> Реши каждый вопрос. Укажи выбранную метку, альтернативные защитимые ответы,
> неоднозначность или недостаток условий. Сначала зафиксируй ответы; ключ будет
> открыт принимающей стороной после этого. Не имитируй незнание технологии.

Это проверяет содержательное решение. Проверку формы проводить отдельно по стандарту;
ни один фиксированный процент сам по себе не закрывает приёмку.
Если отдельный контекст недоступен, сохранить NOT_RUN и передать пакет внешней LLM.

## Проверки после правки

```bash
bash scripts/verify-mcq-json.sh <seed.json>
bash scripts/mcq-tools/gates.sh <seed.json>
python3 -m unittest discover -s scripts/tests -p 'test_mcq*.py' -v
```

Тесты валидаторов нужны при изменении инструментария, а не после каждой запятой.
Полный structural gate: `bash scripts/verify-mcq-json.sh --all`.
При изменении Markdown дополнительно `bash scripts/verify-md-no-mcq.sh <theory.md>`.
При изменении импортера — связанные Java-тесты. Структурный PASS не заменяет ревью.

## Состояние и передача работы

`linkage-reset-manifest.json` и topic-sidecars сохраняют исторические заявления.
Текущее состояние выводится из содержимого и проверяемых evidence, не из галочек плана.
Снимок `docs/mcq-quality/audit-state.json` воспроизводится командой:

```bash
python3 scripts/mcq-audit.py --output docs/mcq-quality/audit-state.json --checklist-output docs/mcq-quality/file-checklist.md
```

Это производный снимок; вручную его статусы не редактировать. Источник новых проверок
текущей задачи — `docs/mcq-quality/audit-evidence.json`. Запись содержит paths/sha256,
coverage всех Q/B, вид ревью, источники, ограничения и отдельное resolution после правок.
Начальное ревью после правки не становится автоматически актуальным.

В `review_queue` находятся ещё не прочитанные и STALE-блоки обновлённого множества.
`issue_queue` хранит незакрытые замечания, включая уже прочитанные блоки;
`runtime_findings` — отдельные проблемы приложения. Эти очереди не заменяют друг друга.
`readability_review_queue` — отдельный скоуп RU. Обязательные проверки каждого файла
указаны в `files[].checks` и [читаемой таблице](docs/mcq-quality/file-checklist.md).
`form_review_queue` — отдельный скоуп SFPL/ANSC всех обновлённых блоков: сначала с
автосигналами, затем без них. Его не сокращает содержательная вычитка. Пока отдельные
формальные ревью не подключены как проверяемый источник coverage, статус UNVERIFIED.
Блочные SHA-256 позволяют сохранить проверку неизменённых Q; общий пролог и смысловые
зависимости тоже входят в оценку применимости. `CURRENT` означает совпадение проверенного
содержимого, а не автоматическую приёмку по всем правилам.

Минимальная запись передачи для одного блока (значения в угловых скобках заполнить):

```json
{
  "paths": {"mcq": "<relative seed path>", "theory": "<relative Markdown path>"},
  "sha256": {"mcq": "<input SHA-256>", "theory": "<input SHA-256>"},
  "standard_sha256": "<standard SHA-256>",
  "scope": [{"q_number": 1, "block_idx": 0}],
  "stage": "INDEPENDENT_REVIEW_PENDING",
  "checks": {
    "structure": "PASS",
    "fact_check": "PARTIAL",
    "sfpl": "UNVERIFIED",
    "ansc": "UNVERIFIED",
    "russian_readability": "UNVERIFIED",
    "blind": "NOT_RUN"
  },
  "evidence": "<path to review record with coverage and sources>",
  "open_findings": ["<finding ID>"],
  "next_action": "<specific check or repair>"
}
```

Это шаблон handoff, не готовый sidecar и не основание проставить AUDITED.

Следующему исполнителю передать:
- точный файл и блоки, исходные хеши и текущую версию стандарта;
- что действительно сделано и где лежит доказательство;
- открытые findings, NOT_RUN и STALE;
- команды проверки и оставшиеся этапы;
- конкретное следующее действие.

Провайдер может быть тем же или другим. При параллельной работе один автор владеет
одной единицей; рецензент читает отдельный снимок. Число агентов и размер пакета
ограничиваются бюджетом пользователя. Никаких автоматических бесконечных ревью-кругов.
