# Auto-Improve: автономный цикл улучшения проекта

Бесконечный цикл: анализ проекта → выбор приоритетов → внесение изменений → тестирование → отчёт → коммит → повтор. Пользователь участвует минимально — только подтверждает чекпоинты ("ок").

## Области работы

Скилл работает по ВСЕМ направлениям одновременно, выбирая самое слабое место:

1. **Контент** — шпаргалки в `cheatsheets/` (глубина, покрытие тем, актуальность для backend-разработчика)
2. **Код** — качество кода quiz-app (рефакторинг, баги, новый функционал)
3. **UI/UX** — интерфейс приложения (Thymeleaf + app.js)
4. **Тесты** — покрытие, качество тестов, новые тест-кейсы

## Главный цикл

```
┌─────────────────────────────────────────┐
│            ФАЗА 1: АНАЛИЗ               │
│  Сканировать проект, найти слабые места │
└──────────────┬──────────────────────────┘
               ▼
┌─────────────────────────────────────────┐
│         ФАЗА 2: ПРИОРИТИЗАЦИЯ           │
│  Выбрать одну задачу с макс. импактом   │
└──────────────┬──────────────────────────┘
               ▼
┌─────────────────────────────────────────┐
│          ФАЗА 3: РЕАЛИЗАЦИЯ             │
│  Внести изменения (код/контент/UI)      │
└──────────────┬──────────────────────────┘
               ▼
┌─────────────────────────────────────────┐
│        ФАЗА 4: ТЕСТИРОВАНИЕ             │
│  Билд, тесты, браузерное QA             │
└──────────────┬──────────────────────────┘
               ▼
┌─────────────────────────────────────────┐
│          ФАЗА 5: ЧЕКПОИНТ              │
│  Показать отчёт, ждать "ок"            │
└──────────────┬──────────────────────────┘
               ▼
┌─────────────────────────────────────────┐
│           ФАЗА 6: КОММИТ               │
│  git add + commit с описанием           │
└──────────────┬──────────────────────────┘
               ▼
          (вернуться к Фазе 1)
```

## Детали каждой фазы

### Фаза 1: Анализ

Собрать сигналы из всех областей, чтобы выбрать следующую задачу:

**Сперва — git состояние** (кричащий сигнал):
- `git status --porcelain` — посмотреть текущие незакоммиченные изменения
- Это **WIP пользователя**, не моё. Не коммитить, не путать с моими изменениями.
- Если файлов много (>5 modified) — пользователь активно редактирует. Избегать
  коллизий: не трогать те же файлы.

**Контент (`cheatsheets/`)**:
- Прочитать `cheatsheets/CHEATSHEETS_ARCHITECTURE_AND_RULES.md` — это единый стандарт
- Прочитать `references/backend-topics.md` (файл в директории скилла) — целевой список тем для backend-разработчика
- **Проверить README целевой папки** перед созданием/расширением файла —
  папка может быть помечена как **legacy/freeze**. Если README содержит фразы
  типа «новые документы сюда не добавляем», «legacy-папка», «заморожена» —
  искать каноничную папку (она указана в legacy-README).
- **Проверить отсутствие дубликата** — `find cheatsheets -name "*тема*.md"` перед
  созданием нового файла. Часто файл уже есть в соседней папке.
- Сканировать случайные 5-10 файлов из разных разделов cheatsheets на качество:
  - Есть ли frontmatter? Корректен ли формат?
  - Есть ли TOC и совпадает ли с заголовками?
  - Глубина контента (поверхностный обзор vs практическая шпаргалка)?
  - Актуальность (устаревшие версии, deprecated API)?
  - Битые внутренние ссылки?
- Проверить покрытие тем: какие разделы из `references/backend-topics.md` отсутствуют или пусты?

**Код**:
- `./gradlew build -x test` — проверить компиляцию
- `./gradlew test` — запустить тесты, найти падающие
- **`./gradlew check`** — проверить ВСЕ gates (тесты + coverage + ArchUnit).
  Это главное: `test` пропускает coverage-gates, которые тоже валят CI.
  Цикл 2 в истории родился именно из coverage-gate, незамеченного на этапе `test`.
- `./gradlew jacocoTestReport` — генерация HTML-отчёта (для анализа per-package coverage)
- Поискать TODO/FIXME/HACK в коде
- Проверить наличие дизайн-спеков в `docs/superpowers/specs/` — есть ли нереализованные фичи?
- Если падают тесты или гейты — **сразу разобраться в корневой причине** через
  `--info` или `build/test-results/test/*.xml`. Stack trace часто скрыт под
  «Failed to load ApplicationContext» — копать до `Caused by:`.

**UI/UX**:
- Запустить приложение (`./gradlew bootRun` в фоне)
- Дождаться старта на порту 8080
- Сделать скриншоты ключевых страниц через Chrome DevTools MCP
- Визуально оценить: вёрстка, отзывчивость, UX-проблемы

**Тесты**:
- Посмотреть текущее покрытие (JaCoCo HTML-отчёт)
- Найти классы/методы без тестов
- Оценить качество существующих тестов (моки vs интеграция, edge cases)

### Фаза 2: Приоритизация

Автономно выбрать ОДНУ задачу на этот цикл. Критерии:

1. **Сломанное важнее нового** — падающие тесты, ошибки компиляции, баги
2. **Высокий импакт** — что принесёт максимум пользы для обучения backend-разработчика
3. **Быстрый результат** — предпочитать задачи, которые можно завершить за один цикл
4. **Ротация областей** — не зацикливаться на одной области, чередовать контент/код/UI/тесты

Задача должна быть конкретной и завершаемой. Примеры хороших задач:
- "Углубить cheatsheets/databases/relational/postgresql/postgres-indexes.md — добавить практические примеры B-tree vs GIN vs GiST"
- "Добавить unit-тесты для SpacedRepetitionService — покрыть граничные случаи SM-2"
- "Исправить: hint-панель не рендерит markdown при первом показе"
- "Создать cheatsheets для Spring Security (отсутствует в покрытии)"

### Фаза 3: Реализация

Выполнить задачу. Конкретные правила по областям:

**Для контента**:
- Следовать правилам из `CHEATSHEETS_ARCHITECTURE_AND_RULES.md` строго
- Обязательный frontmatter: title, description, tags, updated
- Обязательный TOC в формате `- [Раздел](#якорь)`
- Язык контента — русский (кроме кода и терминов)
- Плотность пользы: каждый абзац = одна мысль, без воды
- Код-блоки с указанием языка
- Практичность: примеры, сравнения, когда-что-использовать
- **Относительные пути в ссылках — типовая ошибка.** От `cheatsheets/X/Y/file.md`
  до `cheatsheets/interview/...` — это `../../interview/...`, НЕ `../../../`.
  Третий `..` уведёт за корень репо. Всегда проверяй через `python3` тестом
  существования файлов (см. шаблон в Фазе 4).
- **Не дублировать секцию «См. также»**: если уже есть `### См. также`
  под `## Полезные ссылки`, то не добавляй второй `## См. также` в конце —
  GitHub присвоит anchor `см-также-1`, и в TOC надо это учесть. Лучше один
  раз в конце.
- **Перед созданием НОВОГО файла**: убедись, что:
  1. Папка не помечена legacy/freeze в её README.
  2. Нет уже файла с такой же темой в каноничной папке.
  3. Если есть похожий файл — РАСШИРЯТЬ его, а не создавать новый.

**Для кода**:
- Следовать архитектуре из CLAUDE.md (модули, слои, пакеты)
- ArchUnit правила не нарушать
- Существующие паттерны (Strategy, Observer, Builder) — использовать как есть
- Не добавлять лишнего: YAGNI

**Для UI**:
- Vanilla JS (app.js), Thymeleaf шаблоны
- Стили в styles.css
- Не добавлять новых JS-библиотек без причины

**Для тестов**:
- TestQuestionBuilder для фикстур
- Стандартная структура: given-when-then
- Моки для AI-клиентов, реальная БД для persistence

### Фаза 4: Тестирование

Обязательные проверки после каждого изменения:

**Всегда**:
- `./gradlew check` (НЕ просто `test`) — компиляция + тесты + coverage gates +
  ArchUnit. Это полный сквозной gate, как в CI.
- Если тесты упали — `./gradlew test --info` или прочитать
  `build/test-results/test/*.xml`. ApplicationContext failures обычно
  скрывают real cause под несколькими caused-by — копать до настоящей причины.
- Если coverage gate упал — `./gradlew jacocoTestReport`, открыть
  `build/reports/jacoco/test/html/index.html`, найти классы с низким покрытием,
  добавить тесты.

**Шаблон валидации внутренних ссылок в .md**:

```python
# Запускать перед коммитом любого markdown с относительными ссылками
import re, os
base = '/абсолютный/путь/к/папке/файла/'
with open(base + 'имя-файла.md') as f:
    text = f.read()
links = re.findall(r'\]\(((?:\.\.|\.|[^\)#h][^\)]*?))\.md(?:#[^)]+)?\)', text)
for path in set(links):
    full = path + '.md'
    abs_path = os.path.normpath(os.path.join(base, full))
    if not os.path.exists(abs_path):
        print(f'BROKEN: {full}')
```

**Для UI-изменений (браузерное QA)**:
1. Убедиться что приложение запущено (или запустить `./gradlew bootRun`)
2. Через Chrome DevTools MCP:
   - Открыть целевую страницу
   - Сделать скриншот
   - Проверить: рендеринг корректен, нет визуальных артефактов
   - Прокликать интерактивные элементы (кнопки, панели)
   - Проверить консоль на JS-ошибки
3. Если есть проблемы — исправить и повторить QA

**Для контента**:
- Проверить что все внутренние ссылки рабочие
- Проверить TOC на соответствие заголовкам
- Проверить frontmatter

### Фаза 5: Чекпоинт

Показать пользователю отчёт в формате:

```
═══════════════════════════════════════
  ЦИКЛ #N — ЧЕКПОИНТ
═══════════════════════════════════════

📋 Область: [контент / код / UI / тесты]
📝 Задача: [конкретное описание]

✅ Что сделано:
  - [список конкретных изменений]

🧪 Тестирование:
  - Билд: ✅ / ❌
  - Тесты: ✅ (N passed) / ❌ (описание)
  - Браузер QA: ✅ / ⏭️ (не требовалось)

📁 Изменённые файлы:
  - path/to/file1.md (создан / изменён)
  - path/to/file2.java (изменён)

🔮 Следующий цикл (предварительно):
  - [что планируется дальше]

═══════════════════════════════════════
  Ответь "ок" для коммита и продолжения
═══════════════════════════════════════
```

Ждать ответа пользователя. Если пользователь:
- "ок" / "ok" / "да" / "+" → коммит и следующий цикл
- Даёт замечания → исправить, показать обновлённый чекпоинт
- "стоп" / "stop" → завершить цикл

### Фаза 6: Коммит

После подтверждения пользователя:
- `git add <конкретные файлы>` — **ТОЛЬКО мои файлы этого цикла**.
  Никогда `git add .` или `git add -A` — в working tree часто WIP пользователя.
- В чекпоинте 5-й фазы заранее перечисли «Изменённые файлы» и «НЕ моё».
  В Фазе 6 добавляй только из «Изменённые файлы».
- `git commit` с описательным сообщением:
  - Для контента: `docs([раздел]): улучшить [тема] — [детали]`
  - Для кода: `refactor/feat/fix([модуль]): [описание]`
  - Для UI: `ui: [описание]`
  - Для тестов: `test([модуль]): [описание]`

После коммита — сразу начать Фазу 1 следующего цикла.

## Правила автономности

- Решения о приоритетах принимаются самостоятельно — пользователь НЕ выбирает задачу
- Единственная точка взаимодействия — чекпоинт (Фаза 5)
- Если задача оказалась слишком большой — разбить на части, завершить первую часть как один цикл
- Если что-то сломалось и не починить за 3 попытки — откатить изменения, выбрать другую задачу
- Не спрашивать разрешения на чтение файлов, запуск тестов, создание контента

## Состояние между циклами

Вести мысленный счёт:
- Номер текущего цикла
- Какие области уже покрыты (для ротации)
- Какие проблемы обнаружены но отложены (бэклог)

## Запуск

При вызове скилла:
1. Прочитать `references/backend-topics.md` для понимания целевого покрытия тем
2. Начать с Фазы 1 (Анализ) — первый цикл
3. Продолжать бесконечно до команды "стоп"

## Уроки из реальных циклов

Эти ошибки стоит избегать — все были сделаны и стоили времени:

- **Не создавай файл, не проверив README папки.** Папка может быть legacy
  с фразой «новые файлы сюда не добавляем». Канонический файл уже есть в
  соседней папке — её путь указан в legacy-README.
- **`./gradlew test` не равно `./gradlew check`.** Coverage gates и ArchUnit
  правила не запускаются при `test`. Если CI зелёный локально на тестах,
  но красный в pipeline — почти всегда дело в этом.
- **Падение «Failed to load ApplicationContext» — это не root cause.**
  Реальная причина в нескольких caused-by ниже. Прокручивай в HTML-отчёте
  или через `--info` до настоящего исключения.
- **Относительные пути ../X легко промахнуться на один уровень.** От
  `cheatsheets/A/B/file.md` к `cheatsheets/C/...` — это `../../C/...`, а не
  `../../../C/...`. Прогоняй python-скрипт валидации перед коммитом.
- **WIP пользователя в working tree — норма.** Если git status показывает
  файлы, которые ты не трогал — это работа пользователя, не ошибка. Никогда
  не добавляй их в свой коммит.
- **Большая задача (например, чистка 303 вопросов) — это не один цикл.**
  Разбивай: первый цикл → диагностика и сообщение, чтобы автор мог найти
  все случаи. Цикл реальной правки — отдельно.
- **Прежде чем создать «новую шпаргалку по X», поищи `find ... -name '*X*.md'`.**
  В 9 из 10 случаев файл уже есть в каноничной папке.
