# Cheatsheet Writer

Скилл для создания и улучшения технических шпаргалок в каталоге `cheatsheets/`.

## Область действия

- **Рабочая директория**: `cheatsheets/` в корне проекта
- **Исключение**: папка `cheatsheets/interview/` — её не трогаем, у неё свой формат
- **Правила оформления**: файл `cheatsheets/CHEATSHEETS_ARCHITECTURE_AND_RULES.md` — единственный источник правды по стандартам

## Workflow

### 1. Определи задачу

Пользователь может попросить:
- **Создать новую шпаргалку** — файл не существует, нужно написать с нуля
- **Улучшить существующую** — файл есть, но неполный, устарел, или плохо структурирован
- **Дополнить конкретный раздел** — добавить информацию в конкретную секцию

### 2. Изучи текущее состояние

Перед любыми изменениями:

1. **Прочитай правила** — `cheatsheets/CHEATSHEETS_ARCHITECTURE_AND_RULES.md` (если ещё не читал в этой сессии)
2. **Прочитай существующий файл** целиком (если обновляешь)
3. **Посмотри соседние файлы** в той же папке — чтобы понять контекст, избежать дублирования, и найти возможности для перекрёстных ссылок
4. **Оцени текущее качество**: какие разделы полные, какие поверхностные, чего не хватает

### 3. Исследуй тему

Шпаргалка должна **полностью покрывать тему**. Для этого нужны актуальные источники.

**Стратегия поиска информации:**

- Используй `WebSearch` для поиска актуальной информации по теме
- Используй `WebFetch` для извлечения контента с найденных страниц
- **Приоритет источников** (от высшего к низшему):
  1. Официальная документация технологии (docs.oracle.com, spring.io, postgresql.org и т.д.)
  2. Качественные обучающие ресурсы (baeldung.com, digitalocean.com/community, docs.microsoft.com)
  3. Авторитетные блоги и статьи (martinfowler.com, blog.cleancoder.com)
  4. Спецификации и RFC (если тема про протоколы/стандарты)

- **Что искать:**
  - Полный список возможностей/API/команд по теме — шпаргалка не должна упускать важные аспекты
  - Лучшие практики и антипаттерны
  - Типичные проблемы и их решения
  - Свежие изменения в последних версиях (если тема про конкретную технологию)

- **Не нужно искать**, если тема фундаментальная и хорошо тебе известна (алгоритмы, паттерны GoF, базовый SQL). Но даже тогда сверься с парой источников, чтобы ничего не упустить.

### 4. Напиши или перепиши файл

#### Обязательная структура документа

```markdown
---
title: "Название темы"
description: "Краткое описание — для чего эта шпаргалка."
tags:
  - раздел
  - тема
  - подтема
difficulty: "beginner|intermediate|advanced"
prerequisites: ["путь/к/зависимости.md"]
next: ["путь/к/следующей-теме.md"]
updated: "YYYY-MM-DD"
related: ["путь/к/связанной-теме.md"]
---

# Название темы

Краткое введение: что это, зачем нужно, когда применяется. 1-3 абзаца.

## Полезные ссылки

### Официальная документация
- [Название](URL) — краткое описание

### См. также
- [[название-файла]] — что найдёт читатель

## Содержание

- [Раздел](#якорь)
  - [Подраздел](#якорь)

## Основные разделы

... тематический контент ...

## Лучшие практики

... для крупных тем ...

## Решение проблем

... для крупных тем ...
```

#### Obsidian-совместимость и граф связей

Каждый файл — это узел в графе знаний Obsidian. Чтобы граф был полезным:

**Frontmatter (YAML):**
- Поле `tags` — используй формат списка YAML (`- тег`), не JSON-массив. Obsidian парсит оба, но список чище
- Все поля frontmatter должны быть валидным YAML — Obsidian использует его для фильтрации и Dataview-запросов

**Wikilinks для внутренних связей:**
- Для ссылок на соседние файлы в папке cheatsheets/ используй формат `[[имя-файла]]` (Obsidian wikilink), а НЕ `[текст](путь.md)`
- Wikilinks формируют рёбра графа в Obsidian — обычные markdown-ссылки этого не делают
- В секции "См. также" — только wikilinks: `[[java-concurrency-basics]]`, `[[postgres-indexes]]`
- В тексте шпаргалки, когда упоминаешь тему, покрытую другим файлом — ставь wikilink: "подробнее в [[java-collections-map]]"
- Для ссылок с кастомным текстом: `[[имя-файла|отображаемый текст]]`

**Минимум связей — это жёсткое требование:**
- Каждый файл должен иметь **минимум 5 wikilinks** на другие файлы в каталоге cheatsheets/
- Распределяй wikilinks по всему файлу, а не только в "См. также":
  - 2-3 в секции "См. также"
  - 2-3 inline в тексте, когда упоминаешь связанную тему
- Изолированные узлы бесполезны в графе — каждая шпаргалка должна быть частью сети знаний
- Перед добавлением wikilink — проверь через Glob, что целевой файл существует

**Как находить кандидатов для wikilinks:**
1. Запусти `Glob` по `cheatsheets/**/*.md` чтобы увидеть все файлы
2. Для каждого ключевого термина в шпаргалке проверь: есть ли отдельный файл на эту тему?
3. Если да — ставь wikilink при первом упоминании термина в тексте

**Пример inline wikilinks в тексте:**
```markdown
Виртуальные потоки блокируют carrier thread при использовании `synchronized` — 
это называется pinning. Подробнее о механизмах синхронизации см. в [[java-concurrency-basics]].
Для понимания видимости между потоками важно знать [[java-memory-model|Java Memory Model]].
```

**README.md как хаб:**
- Каждый README.md в папке — хаб-узел, связывающий все дочерние файлы через wikilinks
- Если создаёшь новый файл, добавь wikilink на него в README папки

#### Правила контента

**Полнота покрытия** — это главный приоритет:
- Шпаргалка должна быть **исчерпывающим справочником** по теме, а не кратким обзором
- Если тема имеет 15 подтем, все 15 должны быть раскрыты
- Каждый раздел должен содержать достаточно информации для практического применения: объяснение + пример кода/команды
- Лучше одна полная шпаргалка, чем десять поверхностных

**Читаемость (ОБЯЗАТЕЛЬНО):**

Шпаргалки читают живые инженеры перед собеседованием / в работе — они должны восприниматься легко. Это жёсткое требование, нарушение считается критическим дефектом.

- **Короткие абзацы** — 2-4 предложения максимум. Длинный абзац = разбить на два или список.
- **Bullet-списки вместо стен текста** — если перечисляешь 3+ пункта, используй `-` список.
- **Таблицы для сравнений** — любые `vs` / выбор / "когда что использовать" = markdown таблица с колонками.
- **Код-блоки** — обязательно указание языка (`java`, `sql`, `bash`, `yaml`, `json`, `text`, `kotlin`, `python`, `go`).
- **Один абзац = одна мысль** — не склеивай несвязанные идеи.
- **Без воды и academic-tone** — запрещены фразы "важно отметить что", "стоит упомянуть", "необходимо понимать", "следует иметь в виду", "в этом разделе мы рассмотрим". Сразу суть.
- **Без маркетинга** — никаких "мощный инструмент", "гибкое решение", "надёжная система".
- **Без повторов очевидного** — не пиши "PostgreSQL — это реляционная БД" в шпаргалке по PostgreSQL; не пиши "Spring — это Java-фреймворк" в Spring-шпаргалке.
- **Примеры обязательны** — каждая концепция подкрепляется примером (код / команда / сценарий / цифры).
- **Явные выводы** — для нетривиальных сравнений / выборов добавляй в конце ответа строку `**Итог:**` / `**Вывод:**` / `**Когда использовать:**`.
- **Mermaid диаграммы** — для flow / архитектуры / последовательностей, 1-3 на крупный файл.
- **Жирным** — ключевые термины и выводы, не более 1-2 раз на абзац.

**Язык (СТРОГО):**
- Весь прозаический контент — **только на русском**. Английский допустим только для:
  1. Технических терминов в `backticks` (`HashMap`, `CompletableFuture`, `pg_stat_statements`)
  2. Кода внутри code-блоков
  3. Имён файлов / путей (`kebab-case.md`)
  4. Имён продуктов и технологий (Kubernetes, Docker, Spring Boot, Git)
- Заголовки разделов — на русском (кроме технических названий в `backticks` типа `## Работа с HashMap`).
- Описания в frontmatter (`title`, `description`) — на русском.

**TOC (содержание):**
- Заголовок: `## Содержание`
- Формат H2: `- [Раздел](#якорь)`
- Формат H3: `  - [Подраздел](#якорь)` (2 пробела)
- Формат H4: `    - [Подподраздел](#якорь)` (4 пробела)
- Маркер — только тире (`-`)
- TOC должен точно соответствовать реальным заголовкам в файле

**Ссылки:**
- Внутренние ссылки — только относительные
- Внешние ссылки — в секции "Полезные ссылки"
- Никаких битых ссылок — проверяй, что целевые файлы существуют

**Размер:**
- Документ > 1200 строк — подумай о декомпозиции на дочерние файлы
- Но лучше один файл на 800 строк, чем 3 по 100 — не дроби без необходимости

**Язык:**
- Весь контент на русском
- Английские термины, команды и идентификаторы — в обратных кавычках
- Имена файлов — на английском (kebab-case)

### 5. Валидация

После написания проверь:

1. **Frontmatter** — все обязательные поля заполнены, `updated` = сегодняшняя дата, `tags` в формате YAML-списка
2. **TOC** — якоря совпадают с реальными заголовками
3. **Код-блоки** — у каждого указан язык
4. **Внутренние ссылки** — файлы, на которые ведут wikilinks, существуют (проверь через Glob)
5. **Wikilinks >= 5** — посчитай количество `[[...]]` в файле. Если меньше 5 — найди ещё связанные файлы и добавь inline wikilinks в текст
6. **Полнота** — пройдись по оглавлению и спроси себя: "если бы я готовился к собеседованию/работе по этой теме, чего бы мне не хватило?"
7. **Нет дублей** — контент не повторяет соседние файлы в той же папке
8. **Чек-лист читаемости** (каждый пункт обязателен):
   - [ ] Весь прозаический текст на русском (английский только в `backticks` / коде / путях / именах продуктов)
   - [ ] Нет абзацев длиннее 4 предложений
   - [ ] Любое перечисление от 3 пунктов — bullet-лист
   - [ ] Любое сравнение / выбор между опциями — markdown таблица
   - [ ] Каждый код-блок имеет language tag
   - [ ] Нет фраз-заполнителей ("важно отметить", "стоит упомянуть", "в этом разделе мы рассмотрим")
   - [ ] Нет маркетинга ("мощный", "гибкий", "надёжный")
   - [ ] Нет повторов очевидного про саму технологию
   - [ ] Концептуальные ответы имеют пример кода или конкретного сценария
   - [ ] Для сравнений / выборов есть явный `**Итог:**` / `**Когда использовать:**`

### 6. Обнови README

Если создал новый файл, добавь ссылку на него в `README.md` родительской папки (если README существует).

## Типы контента и их особенности

| Тип | Фокус | Пример |
|-----|-------|--------|
| `overview` | Карта темы, связи между подтемами | `postgres-basics.md` |
| `reference` | Полный справочник команд/API | `postgres-queries.md` |
| `how-to` | Пошаговая инструкция | `postgres-backup-restore.md` |
| `troubleshooting` | Симптомы → диагностика → решение | `postgres-troubleshooting.md` |

Если файл пытается быть всем сразу — разбей его.

## Примеры хороших практик

**Хорошо** — конкретный пример с объяснением:
```markdown
### Индексы в PostgreSQL

Индекс ускоряет выборку, но замедляет вставку. Используй, когда столбец часто в `WHERE` или `JOIN`.

\```sql
-- B-Tree (по умолчанию) — для =, <, >, BETWEEN
CREATE INDEX idx_users_email ON users(email);

-- GIN — для массивов, JSONB, полнотекстового поиска
CREATE INDEX idx_docs_tags ON documents USING GIN(tags);
\```
```

**Плохо** — общие слова без практической пользы:
```markdown
### Индексы

Индексы — важная часть базы данных. Они помогают ускорить запросы.
Существуют разные типы индексов.
```
