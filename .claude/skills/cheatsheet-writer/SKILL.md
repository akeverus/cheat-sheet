# Cheatsheet Writer

Скилл для создания и улучшения технических шпаргалок в каталоге `cheatsheets/`.

## Область действия

- Рабочая директория: `cheatsheets/` в корне проекта.
- Исключение: папка `cheatsheets/interview/` — её не трогаем, у неё свой формат.
- Источник правды: `cheatsheets/CHEATSHEETS_ARCHITECTURE_AND_RULES.md`. Если в этом скилле и в правилах есть расхождение — правила репозитория важнее.

## Workflow

### 1. Определи задачу

Пользователь может попросить:
- Создать новую шпаргалку — файл не существует.
- Улучшить существующую — есть, но неполная, устарела или плохо структурирована.
- Дополнить раздел — добавить блок в существующий файл.
- «Всё вместе» — переписать слабые файлы и закрыть пробелы. Тогда: сканируй структуру `find cheatsheets -name '*.md' -not -path '*/interview/*' | xargs wc -l | sort -n | head -30`, ищи короткие топические файлы (под 200 строк), стандартные пробелы (нет файла на крупную тему).

### 2. Изучи текущее состояние

Перед любыми изменениями:

1. Прочитай правила — `cheatsheets/CHEATSHEETS_ARCHITECTURE_AND_RULES.md` (один раз в сессии).
2. Прочитай существующий файл целиком, если обновляешь.
3. Проверь соседние файлы в той же папке — для контекста, чтобы избежать дублирования и найти кандидатов на перекрёстные ссылки. Используй `Glob` с маской вида `cheatsheets/<раздел>/**/*.md`.
4. Оцени текущее качество: какие разделы полные, какие поверхностные, чего не хватает.

### 3. Исследуй тему

Шпаргалка должна полностью покрывать тему. Для этого нужны актуальные источники.

**Стратегия поиска информации:**

- `WebSearch` — для поиска актуальной информации.
- `WebFetch` — для извлечения контента с найденных страниц.
- Приоритет источников (от высшего к низшему):
  1. Официальная документация технологии (docs.oracle.com, spring.io, postgresql.org, kubernetes.io).
  2. Качественные обучающие ресурсы (baeldung.com, digitalocean.com/community, docs.microsoft.com, sre.google).
  3. Авторитетные блоги (martinfowler.com, blog.cleancoder.com, microservices.io).
  4. Спецификации и RFC (если тема про протоколы или стандарты).
- Что искать:
  - Полный список возможностей или API по теме.
  - Лучшие практики и антипаттерны.
  - Типичные проблемы и решения.
  - Свежие изменения в последних версиях.

Не нужно искать, если тема фундаментальная и хорошо известна (алгоритмы, паттерны GoF, базовый SQL). Но даже тогда сверься с парой источников.

### 4. Напиши или перепиши файл

#### Обязательная структура документа

```markdown
---
title: "Название темы"
description: "Краткое описание, для чего эта шпаргалка."
tags:
  - раздел
  - тема
  - подтема
type: "overview|reference|how-to|troubleshooting|index"
difficulty: "beginner|intermediate|advanced"
aliases:
  - "Альтернативное название"
  - "Synonym"
prerequisites:
  - "[[имя-файла-зависимости]]"
related:
  - "[[имя-связанного-файла]]"
updated: "YYYY-MM-DD"
---

# Название темы

Краткое введение: что это, зачем нужно, когда применяется. 1-3 абзаца. Без воды.

## Полезные ссылки

### Официальная документация

- [Название](URL) — что найдёт читатель

### Обучающие материалы

- [Название](URL) — короткое пояснение

### См. также

- [Название](относительный/путь.md) — что найдёт читатель

## Содержание

- [Раздел](#якорь)
  - [Подраздел](#якорь)

## Тематические разделы

... контент ...

## Лучшие практики

... для крупных тем ...

## Решение проблем

... для крупных тем ...
```

Обязательные поля frontmatter: `title`, `description`, `tags`, `type`, `updated`.
Рекомендуемые: `aliases`, `difficulty`, `prerequisites`, `related`, `next`.
`updated` — сегодняшняя дата на момент правки.

Полный контракт frontmatter и Obsidian-семантика описаны в скилле `obsidian-metadata`
(`.claude/skills/obsidian-metadata/SKILL.md`). Если правила репозитория и этого скилла
расходятся по полям frontmatter — `obsidian-metadata` важнее.

После написания нового файла прогони:

```bash
python3 .claude/skills/obsidian-metadata/scripts/normalize_frontmatter.py --apply
```

Скрипт идемпотентен и достроит `type`, `aliases`, и нормализует значения, если что-то
было упущено или сделано не по форме.

#### Внутренние ссылки: markdown в теле, wikilinks в frontmatter

- В **теле** документа — стандартные markdown-ссылки с относительными путями. Это закон
  репозитория. Wikilinks `[[file]]` в теле — устаревший формат.
- В **frontmatter-list-полях** (`related`, `prerequisites`, `next`) — wikilink-форма
  `"[[имя-файла-без-md]]"`. Это нужно, чтобы Obsidian создавал рёбра графа из метаданных.
  Без wikilink-формы значения остаются обычными строками и в граф не попадают.

Почему markdown:
- Кликабельны в GitHub, VS Code preview, IntelliJ, любом редакторе.
- Wikilinks работают только в Obsidian/Foam.
- Совместимы с CI-проверками валидности ссылок.

Формат:
- `[Название темы](относительный/путь.md)` — относительно текущего файла, всегда с `.md`.
- В «См. также»: `- [Название](path.md) — короткое пояснение`.
- Inline в тексте: «подробнее в [Java Memory Model](java-memory-model.md)».

**Минимум 5 внутренних ссылок** — жёсткое требование. Распределяй:
- 2–4 в секции «См. также».
- 2–3 inline в тексте при первом упоминании родственной темы.

Перед добавлением ссылки обязательно проверь существование цели:

```bash
ls cheatsheets/<путь>/<имя>.md     # или через Glob
```

#### README.md как хаб

Если создаёшь новый файл, добавь ссылку на него в README родительской папки.
Если родительский README — статический индекс, обнови раздел «Содержание»
или таблицу карты тем.

#### Правила контента

**Полнота покрытия — главный приоритет:**
- Шпаргалка должна быть исчерпывающим справочником, не кратким обзором.
- Если тема имеет 15 подтем, все 15 раскрыты.
- Каждый раздел: объяснение плюс пример (код, команда, сценарий).
- Лучше одна полная шпаргалка на 600 строк, чем десять поверхностных по 60.

**Читаемость (жёсткое требование):**

- Короткие абзацы — 2–4 предложения. Длинный = разбить.
- Bullet-списки от 3 пунктов.
- Таблицы для сравнений (любое «vs», «когда что», «выбор»).
- Код-блоки с указанием языка: `java`, `sql`, `bash`, `yaml`, `json`, `text`, `kotlin`, `python`, `go`, `xml`, `hcl`, `dockerfile`.
- Один абзац — одна мысль.
- Без воды и academic-tone. Запрещены: «важно отметить», «стоит упомянуть», «необходимо понимать», «следует иметь в виду», «в этом разделе мы рассмотрим», «обратите внимание», «важно понимать что», «стоит обратить внимание».
- Без маркетинга: «мощный», «гибкий», «надёжный», «универсальный», «передовой».
- Без повторов очевидного про саму технологию: не пиши «PostgreSQL — реляционная БД» в шпаргалке по PostgreSQL.
- Примеры обязательны: каждая концепция подкрепляется кодом, командой или цифрами.
- Явные выводы для нетривиальных сравнений: лейбл-маркер `**Итог:**` / `**Когда использовать:**`.
- Диаграммы — ASCII/текст, 0–3 на крупный файл (для flow, архитектуры, последовательностей). Mermaid в проекте отменён — не использовать.
- Жирный — ключевые термины и выводы, максимум 1–2 раза на абзац.

#### Инлайн-форматирование

Полный стандарт — в `cheatsheets/CHEATSHEETS_ARCHITECTURE_AND_RULES.md`, раздел «Инлайн-форматирование — единые правила». Ключевые запреты:

- Никакого жирного в заголовках (`# **Title**`, `## **Section**`).
- Никаких backticks на названиях технологий в потоке текста: `PostgreSQL`, `Spring`, `Kafka`, `Docker` — без `` ` `` и без `**`.
- Не дублировать выделения: запрещены `` `**CREATE INDEX**` ``, `**`HashMap`**`, `**[text](url)**`, `[`name`](file.md)`.
- Не выделять часть фразы в скобках: `(**только PostgreSQL**)` — нельзя; вынеси в `**Исключение:**` или цитату `> `.
- Внутренние ссылки между файлами `cheatsheets/` — обычные markdown-ссылки `[Текст](path.md)`, не wikilinks `[[file]]`.
- Секция «См. также» — bullet-список `-`, не фраза через тире.
- Курсив через `*текст*`, не `_текст_` (underscore ломается в идентификаторах).
- Блочные цитаты `> ` — максимум 1–2 на файл.
- Лейблы-маркеры (`**Итог:**`, `**Когда использовать:**`, `**Исключение:**`, `**Внимание:**`) — поощряются, без эмодзи.
- Разделы в «Полезные ссылки» — по роли ресурса (`Официальная документация`, `Обучающие материалы`, `Книги`, `См. также`), не по имени сайта (`Baeldung`, `Oracle`).

#### Типографика и спец-символы

- Тире: длинное `—` с пробелами в прозе (`Postgres — БД`); короткое `–` в диапазонах (`Java 11–21`); дефис `-` только в словах (`B-Tree`) и коде. Запрещены `--` и `слово - слово`.
- Кавычки: «ёлочки» в русской прозе; `"..."` только в коде/путях/JSON; `„лапки"` для вложенных цитат.
- Многоточие — `...`, не символ `…`.
- Эмодзи и декоративные символы запрещены везде в контенте: `🚀 ✅ ❌ ⚠️ 💡 ✓ ✔ ➤ ★ ● → ⇒` и подобные. Исключение — внутри кода, если часть синтаксиса. Лейблы — текстом: `**Внимание:**`, не `⚠️ Внимание!`.
- Диаграммы — ASCII/текст в обычном fenced-блоке (` ```text `), не Mermaid (проект отказался от mermaid — рендера нет). Flow — стрелками `A -> B -> C`; иерархии — отступами/деревом. Схемы компактные, читаемые моноширинно, ширина ≤ 80 символов.
- Длина строки: мягкий лимит 120 символов. Прозаические абзацы — на 100. URL, таблицы, код — без ограничений.
- Пробелы: нет trailing whitespace, нет двух пробелов в конце для `<br>`, нет тройных пустых строк.
- Горизонтальные `---` между секциями не использовать (заголовки `##` уже разделяют). Допустимо только в `interview/`.
- Изображения: в `cheatsheets/assets/<раздел>/`, не рядом с `.md`. Обязательный alt-текст. Ширина не больше 1200 px.

**ASCII/текстовые диаграммы: как делать хорошо**

- Обычный fenced-блок ` ```text ` (или без языка) — рендерится моноширинно, без внешних библиотек.
- Flow — горизонтальными стрелками: `Client -> LB -> Service -> DB`. Ветвление — на отдельных строках с отступом.
- Иерархии/деревья — отступами по 2 пробела; последовательности — нумерованным списком шагов.
- Ширина ≤ 80 символов, чтобы схема читалась на мобильном без горизонтального скролла.
- Если схема не умещается в 5–7 строк ASCII — замени её таблицей или 2–3 буллетами прозы.

#### Язык (строго)

- Весь прозаический контент — на русском.
- Английский допустим только в:
  1. Технических идентификаторах в `backticks` (`HashMap`, `pg_stat_statements`).
  2. Коде внутри code-блоков.
  3. Именах файлов и путях (`kebab-case.md`).
  4. Именах продуктов и технологий (Kubernetes, Docker, Spring Boot, Git).
- Заголовки — на русском (кроме технических названий: `## Работа с HashMap`).
- Frontmatter `title` и `description` — на русском.

#### TOC (содержание)

- Заголовок: строго `## Содержание`.
- H2: `- [Раздел](#якорь)`.
- H3: `  - [Подраздел](#якорь)` (2 пробела).
- H4: `    - [Подподраздел](#якорь)` (4 пробела).
- Маркер — только тире `-`.
- TOC должен точно соответствовать реальным заголовкам.

#### Размер

- Документ > 1200 строк — подумай о декомпозиции.
- Один файл на 800 строк лучше, чем три по 100. Не дроби без необходимости.
- Цель для топовой шпаргалки — 400–700 строк рабочего контента.

### 5. Валидация

После написания обязательно прогони механическую проверку. Команды ниже работают из корня репо:

```bash
F="cheatsheets/<path>/<file>.md"

# 1. Frontmatter дата свежая
head -15 "$F" | grep updated

# 2. Жирного в заголовках быть не должно
grep -E "^#+.*\*\*" "$F"

# 3. Запрещённые комбинации жирного и backticks
grep -E "\`[^\`]*\`\*\*|\*\*\`" "$F"

# 4. Эмодзи в контенте
grep -oE "[🚀✅❌⚠️💡📌🔥⭐✓✔➤★●→⇒]" "$F"

# 5. Untagged code blocks (опенер без языка)
awk '/^```/{n++; if (n%2==1 && length($0)<=3) print FILENAME":"NR": untagged opener"}' "$F"

# 6. Количество внутренних ссылок (должно быть ≥ 5)
grep -oE '\]\([^)]+\.md[^)]*\)' "$F" | wc -l

# 7. Битые внутренние ссылки
grep -oE '\]\(([^)]+\.md)\)' "$F" | sed -E 's/^\]\(//; s/\)$//' | while read link; do
  case "$link" in http*|https*) continue ;; esac
  target=$(cd "$(dirname "$F")" && realpath -m "$link" 2>/dev/null)
  if [ -n "$target" ] && [ ! -f "$target" ]; then
    echo "BROKEN: $link"
  fi
done
```

Дополнительные ручные проверки:

1. TOC — якоря совпадают с заголовками.
2. Полнота — пройдись по оглавлению: «если бы я готовился к собеседованию по этой теме, чего бы мне не хватило?»
3. Нет дублей с соседними файлами в той же папке.

**Чек-лист читаемости** (каждый пункт обязателен):

- [ ] Концептуальные ответы имеют пример кода или сценария.

**Чек-лист инлайн-форматирования:**

- [ ] Жирный в абзаце — 0–2 раза.

### 6. Обнови README

Если создал новый файл, добавь markdown-ссылку в README родительской папки. Не забывай — это часто пропускают.

## Типы контента

| Тип | Фокус | Пример |
|-----|-------|--------|
| `overview` | Карта темы, связи между подтемами | `postgres-basics.md` |
| `reference` | Полный справочник команд/API | `postgres-queries.md` |
| `how-to` | Пошаговая инструкция | `postgres-backup-restore.md` |
| `troubleshooting` | Симптомы, диагностика, решение | `postgres-troubleshooting.md` |

Если файл пытается быть всем сразу — разбей.

## Антипаттерны и уроки

Накопленные ошибки, которых стоит избегать:

- **Битые ссылки в новом файле.** Всегда проверь через `ls` или `Glob` существование цели до записи. Если цели нет, исправь путь или поставь ссылку на README раздела.
- **Дублирование с advanced-файлом.** Если есть `topic.md` и `topic-advanced.md`, разделяй: основы в первом, продвинутое во втором. Не повторяй.
- **«Заполнитель» в overview-файле.** Однострочные секции вроде «См. документацию» — это не контент. Либо раскрывай, либо убирай раздел.
- **Pre-existing нарушения правил.** Когда улучшаешь файл, заодно почини нарушения формата (жирный в заголовках, оставшиеся Mermaid-блоки, прямые кавычки), а не оставляй «как было».
- **Кросс-ссылки только в `См. также`.** Это формализм. Лучшие шпаргалки имеют 2–3 inline-ссылки в теле текста, ведущие к подробностям.
- **Сравнения без явного итога.** Таблица «X vs Y» без вывода «Когда X, когда Y» — половина работы.
- **Нет негативных кейсов.** Хорошая шпаргалка отвечает не только «как делать», но и «когда не делать», «антипаттерны».
- **Wikilinks в новом файле.** Архитектурные правила прошли несколько ревизий. Текущий стандарт — markdown-ссылки. Обнови старый файл при правке.
- **Перегруженные диаграммы.** ASCII-схема шире 80 символов или глубже 7 строк не читается на мобильном — упрости до стрелочного flow или таблицы.
- **Frontmatter `description` с маркдауном.** Описание — простая строка, без `**bold**`, ссылок и backticks. Иначе ломает Obsidian Properties.

## Примеры хороших практик

**Хорошо** — конкретный пример с пояснением:

```markdown
### Индексы в PostgreSQL

Индекс ускоряет выборку, замедляет вставку. Используй, когда столбец часто
в `WHERE` или `JOIN`.

\```sql
-- B-Tree (по умолчанию) — для =, <, >, BETWEEN
CREATE INDEX idx_users_email ON users(email);

-- GIN — для массивов, JSONB, полнотекстового поиска
CREATE INDEX idx_docs_tags ON documents USING GIN(tags);
\```
```

**Плохо** — общие слова без пользы:

```markdown
### Индексы

Индексы — важная часть базы данных. Они помогают ускорить запросы.
Существуют разные типы индексов.
```

## Когда применять «всё вместе»

Если пользователь говорит «улучши все», «закрой пробелы», «продолжай»:

1. Сканируй короткие топические файлы:
   ```bash
   find cheatsheets -name '*.md' -not -path '*/interview/*' -not -path '*/sheets-pdf/*' \
        -not -name 'README.md' | xargs wc -l | sort -n | head -30
   ```
2. Смотри топ — это или редиректы (которые нечего улучшать), или реально слабые файлы.
3. Параллельно ищи топические пробелы — крупные технологии, которых нет в репо:
   ```bash
   find cheatsheets -iname '*kafka*'    # пример
   ```
4. Делай партиями по 3–6 файлов: 2–3 переписать, 1–3 создать с нуля.
5. После каждой партии — валидация (см. секцию 5) и обновление README.
6. Сводка пользователю: что сделано, какие темы покрыты, размеры файлов.
