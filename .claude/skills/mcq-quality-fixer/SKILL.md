# MCQ Quality Fixer v4

## 0. Назначение

Этот скилл является **единственным владельцем JSON MCQ-контента** проекта:

- создаёт MCQ-сидеры с нуля;
- добавляет новые MCQ-блоки к существующим вопросам;
- исправляет схему и структуру JSON;
- переписывает слабые варианты ответа;
- улучшает объясняющие секции;
- устраняет угадываемость correct по форме;
- проверяет единственность правильного ответа;
- синхронизирует MCQ с параллельной теорией;
- выполняет точечный или корпусный аудит качества;
- запускает обязательные валидаторы и сообщает остаточные риски.

MCQ и теория являются двумя разными поверхностями одной темы:

```text
Теория:
cheatsheets/interview/<category>/<topic>-interview.md

MCQ:
modules/quiz-app/src/main/resources/seed/mcq/<category>/<topic>-interview.json
```

В `.md` находится теория. В JSON находится проверка понимания. Новые inline-блоки
`> [!mcq]` в `.md` запрещены.

---

# 1. Главная формула качества

Качественный MCQ-блок строится так:

```text
ясный вопрос
+ ровно один защитимый правильный ответ
+ три реальные ошибочные модели мышления
+ одна основная ошибка в каждом дистракторе
+ естественный русский язык
+ визуально неотличимая форма всех четырёх вариантов
+ содержательные sections
+ проверенные факты
= обучающий MCQ, а не угадайка
```

Главное правило:

> **Correct должен отличаться только истинностью, а не внешним видом.**

Контрольный вопрос:

> Если скрыть `question_text`, поле `correct` и порядок вариантов, можно ли
> стабильно выбрать correct по длине, стилю, пунктуации, `backticks`, структуре,
> уверенности тона или качеству редактуры?

Если да, блок не готов.

---

# 2. Иерархия приоритетов

При конфликте правил применять следующий порядок. Более высокий пункт нельзя
нарушать ради более низкого.

1. **Фактическая корректность.**
2. **Ровно один защитимый правильный ответ.**
3. **Соответствие вопросу и теории.**
4. **Согласованность option text с его sections.**
5. **Правдоподобность дистракторов.**
6. **Естественный и человекочитаемый русский язык.**
7. **Visual Format / Option / Structure Parity.**
8. **Числовые метрики и автоматические эвристики.**
9. **Косметическая симметрия.**

Нельзя сделать утверждение спорным или фактически неверным только ради
`OPTION_LENGTH_RATIO`. Нельзя превращать живые ответы в карбон-копии ради
`structure-tell = 0`.

Если hard gate и естественный текст невозможно совместить в рамках разрешённой
поверхности изменений, остановиться и пометить блок как `manual review`, а не
ломать факты или запрещённые поля.

# 3. Авторитетные источники и порядок чтения

## 3.1 Golden examples

Перед любой генерацией или содержательной правкой MCQ обязательно найти и
прочитать golden examples в таком порядке:

```text
1. docs/golden-examples.md
2. docs/mcq-quality/golden-examples.md
3. golden-examples.md
```

Использовать первый найденный файл. Если не найден ни один, не выдумывать его
содержание: продолжить по этому скиллу и явно указать отсутствие golden examples
в финальном отчёте.

Golden examples задают:

- вкус и тон;
- плотность вариантов;
- уровень русского языка;
- допустимую естественную вариативность;
- модели дистракторов;
- anti-golden примеры;
- глаз-тест «убери `correct`».

Golden examples важнее механического копирования старых сидеров. Старый JSON не
является эталоном только потому, что уже лежит в репозитории.

## 3.2 Теория по теме

Перед работой прочитать соответствующий `.md` целиком или минимум:

- заголовок `## Q<N>`;
- ответ на вопрос;
- примеры;
- edge cases;
- соседние связанные вопросы.

MCQ не должен вводить факты, противоречащие теории. Если теория устарела или
ошибочна, не маскировать проблему в JSON. Сообщить, что требуется
`interview-writer`.

## 3.3 Схема и спецификация

Проверить актуальные файлы:

```text
modules/quiz-app/src/main/resources/seed/mcq-schema.json
docs/superpowers/specs/2026-05-20-mcq-v3-design.md
scripts/verify-mcq-json.sh
```

Схема на диске является источником истины по ключам и типам.

## 3.4 Факты, зависящие от версии

Для версий, CLI, лицензий, API-политик, дефолтов, benchmark-чисел и поведения,
которое могло измениться:

1. использовать `context7 MCP`:
   - `resolve-library-id`;
   - `query-docs`;
2. при недостатке данных использовать официальную документацию через WebFetch;
3. не опираться на блоги как единственный источник;
4. создать или обновить sidecar:

```text
docs/mcq-quality/fact-freshness/<topic_slug>.json
```

Пример:

```json
{
  "topic_slug": "spring-security-interview",
  "version_sensitive": true,
  "product_version": "Spring Security 6.5",
  "checked_date": "2026-07-11",
  "sources": [
    "https://docs.spring.io/..."
  ],
  "version_sensitive_claims": [
    "Поведение SecurityFilterChain по умолчанию"
  ]
}
```

Запрещены расплывчатые формулировки `current`, `latest`, «на данный момент»,
«сейчас по умолчанию» без версии и источника.

# 4. Когда использовать и когда не использовать

## Использовать

- создать JSON MCQ для существующей теоретической темы;
- добавить блоки к существующим `q_number`;
- переписать correct и distractors в рамках полного редакторского прохода;
- переписать только distractor text в ограниченном ROUND/loop-режиме;
- улучшить `sections`;
- исправить схему;
- сбалансировать позиции correct;
- провести аудит файла или всего корпуса;
- обновить fact-freshness sidecar;
- устранить нарушения golden/parity/readability.

## Не использовать

- для написания или расширения теоретических `## Q<N>` в `.md`;
- для изменения структуры cheatsheet;
- для возврата inline `> [!mcq]`;
- для legacy SQLite `answer_options`, если задача явно требует старый pipeline;
- для UI/UX quiz-app;
- для изменения backend-логики импорта.

Смежные владельцы:

- `/interview-writer` — теория и набор вопросов в `.md`;
- `/mcq-quality-fixer` — JSON MCQ;
- `/interview-options-writer` — deprecated, не использовать для нового JSON.

# 5. Определение режима работы

Перед изменениями явно определить один режим. От режима зависит допустимая
поверхность изменений.

## MODE A — `CREATE`

Создание нового JSON или новых блоков.

Можно менять:

- `question_text` нового блока;
- все 4 option text;
- correct position;
- все sections;
- `block_idx` новых блоков.

Нельзя:

- создавать `q_number`, отсутствующий в теории;
- выдумывать факты;
- добавлять неразрешённые ключи.

## MODE B — `FULL_REWRITE`

Полный редакторский проход существующего блока/файла.

Можно менять:

- `question_text`, если он двусмысленный;
- correct text;
- distractor text;
- sections;
- correct position, сохраняя единственность;
- формулировки для устранения скрытого условия.

Обязательно:

- сохранить смысл теории;
- сохранить `q_number` и `block_idx`, если нет отдельной миграции;
- повторно проверить все facts и links.

## MODE C — `DISTRACTOR_ONLY`

Ограниченный проход по визуальному/структурному паритету, включая loop ROUND-6/
ROUND-7.

Можно менять только:

- `text` у options с `correct: false`.

Байт-в-байт неизменны относительно HEAD:

- correct text;
- `correct`;
- `label`;
- `order`;
- `q_number`;
- `block_idx`;
- `question_text`;
- все `sections`;
- `topic_slug`.

Каждый новый distractor text обязан оставаться согласованным с неизменёнными
`what_actually`, `source_of_confusion`, `if_it_were_true`, `how_it_should_be`.

Если это невозможно, не менять блок и пометить его для `FULL_REWRITE`.

## MODE D — `SCHEMA_REPAIR`

Исправление только структурной валидности.

Можно менять:

- отсутствующие/лишние ключи;
- типы значений;
- `order`/`label`, если они неконсистентны;
- число options;
- секции по схеме.

Нельзя тихо переписывать содержание без необходимости. Если содержательная
ошибка обнаружена, вынести отдельно.

## MODE E — `AUDIT_ONLY`

Ничего не менять. Собрать:

- schema errors;
- factual risks;
- answer uniqueness risks;
- parity tells;
- caricature/stamp/readability issues;
- приоритет исправлений.

## MODE F — `FACT_REFRESH`

Проверка version-sensitive claims и sidecar. Менять только подтверждённые факты и
зависимые sections/options.

## MODE G — `CORPUS_SWEEP`

Последовательная обработка нескольких файлов. Работать worst-first, но один
атомарный файл или один чанк giant-файла за итерацию. Соблюдать collision guard и
не трогать dirty/off-limits файлы.

# 6. Структурные инварианты JSON

Каждый файл обязан соответствовать схеме.

## На уровне файла

- `topic_slug` совпадает с basename JSON без `.json`;
- `questions` является массивом;
- JSON валиден;
- кодировка UTF-8;
- русские символы не экранируются без необходимости;
- форматирование сохраняет репозиторный стиль;
- не форматировать весь файл, если меняется один блок.

Каноническая запись при создании файла:

```python
json.dumps(data, ensure_ascii=False, indent=2)
```

Если репозиторий требует отсутствие хвостового перевода строки, сохранять без
него. При точечной правке сохранять существующее соглашение файла.

## На уровне question

- `q_number` существует как `## Q<N>` в параллельном `.md`;
- `q_number` уникален в файле;
- `blocks` содержит минимум один блок;
- вопросы отсортированы по `q_number`, если репозиторный стиль не говорит иное.

## На уровне block

- `block_idx` начинается с 0;
- внутри одного `q_number` `block_idx` уникален и последователен;
- `question_text` непустой;
- `options` содержит ровно 4 элемента.

## На уровне option

- `order`: 0, 1, 2, 3;
- `label`: A, B, C, D и соответствует `order`;
- ровно одна option имеет `correct: true`;
- `text` непустой;
- в `text` нет `**bold**`;
- correct имеет ровно 5 секций;
- wrong имеет ровно 4 секции;
- нет лишних section keys.

Correct sections:

```text
explanation
example
when_to_apply
edge_cases
related
```

Wrong sections:

```text
what_actually
source_of_confusion
if_it_were_true
how_it_should_be
```

# 7. Качество question_text

Хороший stem:

- задаёт один ясный вопрос;
- проверяет одно основное знание или решение;
- имеет ровно один защитимый ответ;
- написан естественно на русском;
- не содержит подсказку через повтор уникальных слов correct;
- не зависит от скрытого контекста;
- завершён `?` либо является корректной инструкцией «Выберите…»;
- не содержит лишней вводной воды;
- не смешивает две независимые проверки через «и/или»;
- соответствует уровню темы.

Плохо:

```text
Что такое LAZY и когда его использовать и почему EAGER плохой?
```

Лучше разделить на блоки:

```text
Чем `FetchType.LAZY` отличается от `FetchType.EAGER`?
```

и отдельно:

```text
Какую стратегию загрузки безопаснее выбирать по умолчанию для связей?
```

## Проверка скрытых условий

Перед сохранением спросить:

- зависит ли ответ от версии;
- зависит ли от ORM/provider;
- зависит ли от конфигурации;
- зависит ли от типа связи;
- зависит ли от режима транзакции;
- зависит ли от организационного контекста;
- для soft skills: является ли ответ «наиболее уместным», а не универсальным законом.

Если зависит, контекст должен быть в `question_text`.

# 8. Mental-model-first workflow

Нельзя начинать с механического написания A/B/C/D.

Для каждого блока сначала сформулировать внутренний design card:

```text
Question intent:
Что именно проверяет вопрос?

Correct mental model:
Какая модель полностью верна?

Wrong mental model 1:
Какое близкое понятие путают?

Wrong mental model 2:
Какое верное правило чрезмерно обобщают или переносят?

Wrong mental model 3:
Какой разумный trade-off выбирают, игнорируя ограничение?

Single defensible answer:
Почему только correct верен при формулировке стема?
```

Только после этого превращать модели в option text.

Для технических вопросов типовые модели:

- confusion of adjacent APIs;
- wrong scope;
- wrong lifecycle;
- wrong cardinality;
- wrong direction;
- wrong default;
- wrong failure cause;
- wrong trade-off;
- version transfer;
- API-shape confusion;
- concurrency/transaction boundary confusion.

Для soft-skill вопросов:

- смешение двух форматов работы;
- правильный инструмент в неправильном контексте;
- оптимизация краткосрочного результата за счёт долгосрочного;
- чрезмерное обобщение;
- игнорирование психологической безопасности;
- путаница между поддержкой и контролем;
- неверная диагностика причины;
- решение симптома вместо причины.

# 9. Канон дистрактора

## 9.1 Формула

```text
реальное понятие
+ зёрно правды
+ правдоподобное рассуждение
+ одна основная смысловая ошибка
+ тот же уровень редакторского качества
= хороший distractor
```

Wrong option должен быть **ошибочным, но не глупым**.

## 9.2 Одна основная ошибка

Каждый distractor содержит ровно одну основную поломку:

- перепутаны роли;
- неверная область действия;
- неверная кардинальность;
- неправильный порядок;
- неверное условие применения;
- неправильный дефолт;
- одна неверная характеристика;
- ошибочная причинно-следственная связь;
- частное правило обобщено;
- свойство соседнего API перенесено сюда.

Нельзя делать три независимые ошибки в одной option.

Плохо:

```text
`Flowable` не поддерживает backpressure, всегда синхронен и существует только в RxJava 1.
```

Лучше:

```text
`Flowable` ограничивает скорость внутренним буфером, но не использует запросы `request(n)` от потребителя.
```

## 9.3 Реальная терминология

Даже wrong option использует реальные:

- классы;
- методы;
- аннотации;
- интерфейсы;
- исключения;
- протоколы;
- процессы.

Не выдумывать API, если вопрос не проверяет существование API.

## 9.4 Разные ошибки внутри блока

Три distractor-а должны проверять разные misconceptions. Нельзя трижды повторять
одну ошибку разными словами.

Пример для `LAZY/EAGER`:

- B: путает момент SQL и момент материализации объекта;
- C: переворачивает дефолты `*ToMany`/`*ToOne`;
- D: считает `EAGER` универсальным лечением N+1.

## 9.5 Не повторять correct с отрицанием

Плохо:

```text
Correct: `Flowable` поддерживает backpressure.
Wrong: `Flowable` не поддерживает backpressure.
```

Лучше:

```text
Wrong: `Flowable` регулирует нагрузку только размером буфера и не использует downstream-запросы `request(n)`.
```

## 9.6 Не создавать частично правильный distractor

Wrong option должен быть однозначно неверен при разумной интерпретации стема.

Проверить:

- не верен ли он в другой версии;
- не верен ли для другого типа;
- не верен ли при другой конфигурации;
- не становится ли верным из-за слова «может», «обычно», «иногда»;
- не содержит ли более точную формулировку, чем correct.

Если можно защитить, переписать либо уточнить stem.

# 10. Single-Delta

Single-Delta означает, что варианты отличаются одним проверяемым элементом:

- методом;
- классом;
- параметром;
- числом;
- условием;
- порядком шага;
- направлением связи;
- областью действия.

Применять, когда вопрос действительно проверяет точное различие.

Подходит:

- API signature;
- default value;
- cardinality;
- lifecycle sequence;
- exact annotation semantics;
- method behavior.

Не применять механически:

- сложные decision-вопросы;
- архитектурные trade-offs;
- soft skills;
- вопросы с несколькими независимыми критериями.

В сложном вопросе «одна ошибка» означает одну основную ошибочную модель, а не
буквальную замену одного слова.

---

# 11. Option Parity

Все 4 варианта должны быть сопоставимы по форме и содержательной плотности.

Проверять:

- длину;
- количество слов;
- количество предложений;
- число claims;
- число технических терминов;
- число условий;
- наличие примеров;
- количество code spans;
- конкретность;
- уровень уверенности;
- причинно-следственную структуру.

Целевой ориентир:

- longest/shortest по словам не более 1.35;
- correct не является одиночным самым длинным;
- correct/average wrong по файлу 0.90–1.10;
- разница в числе предложений внутри блока не более 1.

Ориентир не заменяет редакторское решение. Варианты на 24/27/29/31 слово могут
быть естественнее вариантов ровно по 28 слов.

## Направление исправления

При коротких заглушках:

1. поднять distractors до уровня correct через правдоподобные детали;
2. перенести лишнее обучающее объяснение из option text в sections;
3. не уничтожать полезность correct;
4. не набивать distractor пустыми словами.

---

# 12. Plausibility Parity

Все 4 варианта должны звучать как реальные ответы людей одного уровня.

Для каждого wrong спросить:

1. Мог бы компетентный middle/senior искренне так ответить?
2. Есть ли зёрно правды?
3. Понятен ли источник заблуждения?
4. Есть ли ровно одна основная ошибка?
5. Не звучит ли это как карикатура?
6. Не можно ли отбросить вариант без знания темы?
7. Не является ли вариант токсичным strawman?

## Категоричные слова

`всегда`, `никогда`, `полностью`, `только` не запрещены автоматически. Они
допустимы, если являются сутью правдоподобного заблуждения.

Проблема — асимметрия:

- все wrong категоричны;
- correct осторожный и нюансированный;
- тон выдаёт ответ.

## Запрещённая карикатура

Сильные маркеры soft-skill strawman:

```text
любой ценой
не спрашивая
публично и жёстко
заставить
угрожать
оставить в покое
записать в «без амбиций»
якобы
```

Они допустимы только если вопрос прямо тестирует такое поведение и остальные
варианты имеют сопоставимый тон. В обычном distractor-е заменить зрелой, но
ошибочной моделью.

---

# 13. Russian Readability Parity

Все варианты и sections должны быть естественными и человекочитаемыми на
русском языке.

## Приоритет

```text
1. Фактическая точность
2. Однозначность
3. Правдоподобность
4. Естественный русский язык
5. Паритет формы
6. Числовая симметрия
```

## Требования

- короткие и ясные предложения;
- нормальный порядок слов;
- без канцелярита;
- без кальки с английского, если есть устоявшийся русский вариант;
- технические термины оставлять на английском в `backticks`, если так принято;
- не злоупотреблять скобками;
- не строить машинные цепочки `A → B → C` без реального алгоритма;
- не использовать длинные искусственные перечисления ради parity;
- не повторять один тезис разными словами;
- не использовать «а также», «при этом», «соответственно» как наполнитель;
- не делать option похожей на сгенерированный нормативный документ.

## Признаки машинного текста

- одно предложение длиннее 220–250 символов с 4+ клаузами;
- 3+ стрелки в обычной прозе;
- 3+ точки с запятой без необходимости;
- цепочка «сделать → проверить → заставить → закрыть»;
- искусственное повторение подлежащего;
- одинаковые ритмические штампы во всех четырёх options;
- фраза не произносится вслух без спотыкания.

Правило:

> Лучше немного различаться по длине, но звучать живо, чем быть одинаковыми до
> символа и деревянными.

---

# 14. Visual Format Parity

Правильные и неправильные ответы должны быть визуально неотличимы по качеству
оформления.

## Проверяемые признаки

- количество предложений;
- общий синтаксический шаблон;
- зачин;
- число и порядок клауз;
- форма сказуемого;
- двоеточия;
- точки с запятой;
- тире;
- запятые;
- скобки;
- кавычки;
- code spans;
- перечисления;
- нумерация;
- причинно-следственные связки;
- пример;
- техническая плотность;
- терминальная пунктуация.

## Единый формат блока

Перед написанием options выбрать surface template.

Примеры:

```text
<тезис>. <уточнение или следствие>.
```

```text
`<термин>` — <определение>; <ограничение>.
```

```text
<подход> работает через <механизм>, поэтому <следствие>.
```

```text
<понятие A> отличается от <понятия B> тем, что <критерий>. <практический вывод>.
```

Все варианты используют близкий шаблон, но не обязаны быть буквальными клонами.

## Пунктуационная дисциплина

- если варианты полные предложения, все заканчиваются точкой;
- не смешивать `—`, `–` и `-` в одной роли;
- если correct начинается с backticked identifier, wrong не должны начинаться
  случайной разговорной фразой;
- одинаковые типы терминов оформляются одинаково;
- использовать русские кавычки `«»` для обычной речи;
- не давать только correct скобочное пояснение;
- не давать только correct двоеточие и аккуратный список.

## Глаз-тест

Скрыть:

- `question_text`;
- `correct`;
- labels A/B/C/D.

Посмотреть только на четыре текста. Correct не должен выделяться как:

- самый длинный;
- самый аккуратный;
- самый технический;
- единственный двухпредложный;
- единственный с backticks;
- единственный с примером;
- единственный с причинно-следственной связью;
- единственный без карикатурного тона.

# 15. Structural Parity без stamped-clone

`structure-tell` является диагностикой, а не конечной целью.

Команды:

```bash
python3 scripts/mcq-structure-parity.py --rank
python3 scripts/mcq-structure-parity.py --file <path>
python3 scripts/mcq-structure-parity.py --block <path> <q_number>
```

Метрика сравнивает:

- предложения;
- `;`;
- `:`;
- `(`;
- code spans;
- нумерацию;
- `—`;
- `,`.

Правила интерпретации:

- высокий tell часто означает плоские distractors;
- снижение относительно HEAD желательно;
- около 9 считается near-gold ориентиром для насыщенных блоков;
- **0 не является целью**;
- tell нельзя снижать пустым клонированием пунктуации;
- после снижения tell обязательно запустить stamp/readability review.

## Semantic skeleton, не literal clone

Клонировать нужно **тип ответа**, а не символы:

- определение → определения;
- сравнение → сравнения;
- алгоритм → алгоритмы;
- decision rationale → decision rationales.

Не нужно искусственно добавлять три скобки только потому, что они есть в correct.
Нужно дать distractor-у сопоставимую содержательную насыщенность естественным
способом.

---

# 16. Anti-pattern: Stamped-clone over-correction

Признаки:

- все четыре options почти одной длины до символа;
- одинаковые 10-граммы;
- одинаковые фразы с заменой одного слова, хотя вопрос не Single-Delta;
- искусственные скобки и двоеточия;
- один и тот же ритм, неестественный для русского;
- wrong option формально отличается одной деталью, но не представляет реальную
  mental model;
- `structure-tell` близок к 0, а текст выглядит сгенерированным штампом.

Проверка:

```bash
python3 scripts/mcq-stamp-audit.py --file <path>
```

Исправление:

- сохранить общий тип ответа;
- переписать каждую mental model своими естественными словами;
- убрать пустой наполнитель;
- сохранить одну основную ошибку;
- допустить умеренный естественный разброс длины и пунктуации.

# 17. Согласованность option text и sections

Это hard gate.

## Для correct

`explanation`, `example`, `when_to_apply`, `edge_cases`, `related` должны
поддерживать именно текущий correct text.

## Для wrong

Sections должны объяснять конкретную ошибку текущего distractor text:

- `what_actually` исправляет основную ошибку;
- `source_of_confusion` объясняет, почему так можно подумать;
- `if_it_were_true` показывает наблюдаемое следствие;
- `how_it_should_be` кратко формулирует правильную модель.

После переписывания wrong text спросить:

```text
Осталась ли та же misconception?
Исправляет ли what_actually именно её?
Объясняет ли source_of_confusion именно её?
Следует ли if_it_were_true из нового текста?
Не противоречит ли how_it_should_be correct?
```

В `DISTRACTOR_ONLY` sections нельзя менять, поэтому несогласованность означает
manual review.

---

# 18. Качество sections

## `explanation`

- 3–7 предложений;
- объясняет механизм;
- не повторяет option text;
- содержит ключевое различие;
- без лишней истории вопроса;
- версия указана, если важна.

## `example`

- конкретный сценарий;
- корректный inline code;
- один связный абзац;
- не выдумывать компании/инциденты как факт;
- production numbers только с источником.

## `when_to_apply`

- конкретные условия;
- trade-offs;
- не универсальная рекомендация без контекста.

## `edge_cases`

- edge cases при корректном применении;
- не повторять misconceptions из wrong options;
- не добавлять новую основную тему.

## `related`

- 2–3 ссылки;
- формат `[[<file>#Q<N>]] пояснение`;
- только существующие вопросы;
- связи действительно полезны.

## `what_actually`

- 2–4 предложения;
- исправляет одну основную ошибку;
- не пересказывает весь correct.

## `source_of_confusion`

- реальный источник ошибки;
- похожее имя/API;
- перенос свойства;
- устаревшая практика;
- неверная аналогия;
- не фраза «пользователь просто не знает тему».

## `if_it_were_true`

- конкретное наблюдаемое последствие;
- компиляция, SQL, thread, lifecycle, данные, UX или организационный эффект;
- не выдумывать громкий post-mortem;
- причинная связь должна быть доказуема.

## `how_it_should_be`

- одно ясное исправление;
- мост к correct;
- без нового длинного объяснения.

---

# 19. Распределение correct

Позиция correct не должна быть подсказкой.

Требования по файлу:

- A/B/C/D распределены максимально равномерно;
- `max/min ≤ 2.0`, если вопросов достаточно;
- не строить очевидный цикл A→B→C→D;
- максимальная серия одной позиции ≤ 5;
- при малом количестве вопросов использовать разумную случайность.

Перемещение correct требует перестановки целой option с её sections, а не только
переключения boolean.

В `DISTRACTOR_ONLY` позиции не менять.

# 20. Автоматические проверки

## 20.1 Schema validator — hard gate


Требование: exit code 0.

Ожидаемые пороги:

| Проверка | Порог |
|---|---:|

# 21. Полный workflow создания блока

## Шаг 1. Определить режим

Зафиксировать `CREATE`, `FULL_REWRITE` и т. д.

## Шаг 2. Прочитать golden examples

Не только открыть, а выбрать 1–2 наиболее близких примера по типу вопроса.

## Шаг 3. Прочитать теорию

Проверить `q_number`, факты и соседние темы.

## Шаг 4. Сформулировать intent

Одним предложением:

```text
Этот блок проверяет понимание <конкретного различия>.
```

## Шаг 5. Сформулировать 4 mental models

- correct;
- confusion;
- overgeneralization/wrong scope;
- wrong trade-off/lifecycle/failure model.

## Шаг 6. Проверить uniqueness до написания options

Обосновать:

- почему correct верен;
- почему каждая wrong model неверна;
- какие скрытые условия могли бы сделать wrong верной.

## Шаг 7. Выбрать единый surface template

Например «тезис + уточнение» или «сравнение + практический вывод».

## Шаг 8. Написать options

- 1–2 предложения;
- естественный русский;
- сопоставимая плотность;
- реальные термины;
- без bold;
- одна ошибка на wrong.

## Шаг 9. Написать sections

Sections добавляют знание и объясняют именно текущий text.

## Шаг 10. Провести редакторский self-review

Прочитать все 4 options вслух. Исправить машинность и карикатуру.

## Шаг 11. Провести blind visual review

Убрать metadata и найти form-tells.

## Шаг 12. Вставить в JSON минимальным diff

Не менять unrelated blocks.

## Шаг 13. Запустить проверки

Schema → parity → structure → stamp → blind → tests.

## Шаг 14. Повторно открыть итоговый JSON

Убедиться, что сериализация не повредила текст и ключи.

# 22. Workflow исправления существующего блока

1. Снять baseline всех валидаторов.
2. Зафиксировать, что именно плохо:
   - length tell;
   - structure tell;
   - format tell;
   - style tell;
   - caricature;
   - duplicate misconception;
   - multiple plausible answers;
   - unreadable Russian;
   - sections drift;
   - stale fact.
3. Не переписывать всё без необходимости.
4. Сначала сформулировать текущие mental models.
5. Сохранить полезную misconception каждого wrong.
6. Переписать только слабые элементы.
7. Проверить, что wrong не стал true.
8. Проверить sections consistency.
9. Сравнить CUR с HEAD по разрешённым полям.
10. Запустить весь gate stack.

# 23. Безопасный corpus/loop workflow

Применять в `CORPUS_SWEEP` или `/loop`.

## В начале каждого тика

Прочитать с диска:

- план;
- progress table;
- golden examples;
- текущий skill;
- статус git.

Loop не имеет памяти между тиками.

## Выбор файла

- worst-first;
- сначала tractable;
- giants обрабатывать чанками;
- один тик = один файл или один чанк;
- block-level gate, не среднее файла.

## Collision guard

```bash
git status --porcelain <file>
```

Если dirty, off-limits или параллельно изменяется другим агентом — пропустить.

## Mutation safety

Для ограниченного режима использовать идемпотентный harness и проверять diff
относительно HEAD:

- изменены только разрешённые поля;
- correct byte-for-byte сохранён, если режим этого требует;
- sections не дрейфовали;
- сериализация стабильна;
- повторный запуск не создаёт новый diff.

## Коммиты

Коммитить только если пользователь/loop явно требует.

- explicit pathspec;
- не `git add -A`;
- не коммитить чужие изменения;
- не откатывать чужие коммиты;
- не push;
- не массовый reformat.

# 24. Hard stop conditions

Остановиться и сообщить проблему, если:

- нет теоретического `Q<N>`;
- source of truth противоречив;
- нельзя получить ровно один правильный ответ;
- version-sensitive факт нельзя подтвердить;
- исправление требует запрещённого поля в текущем режиме;
- sections невозможно согласовать с новым text без их изменения;
- файл dirty/off-limits;
- валидатор не доступен и нельзя честно проверить результат;
- gate конфликтует с фактической корректностью;
- пользовательский эталон отсутствует, а задача требует строгого style match.

Не придумывать обход и не заявлять `DONE`.

# 25. Анти-паттерны

## Schema/format

- inline `> [!mcq]` в `.md`;
- emoji-маркеры legacy;
- bold в option text;
- несуществующие section keys;
- меньше/больше 4 options;
- несколько correct;
- `[[Q<N>]]` без имени файла;
- массовая пересериализация unrelated JSON.

## Content

- distractor-абсурд;
- выдуманный API;
- три ошибки в одной option;
- три distractor-а с одной misconception;
- echo-negation correct;
- partially correct option;
- спорное слово «обычно» делает option защитимой;
- wrong не отвечает на stem;
- section просто повторяет option;
- несуществующий post-mortem;
- устаревший version claim без sidecar.

## Parity

- correct — мини-конспект, wrong — заглушки;
- correct единственный с backticks;
- correct единственный с примером;
- correct единственный двухпредложный;
- wrong карикатурно токсичны;
- все wrong категоричны, correct осторожный;
- механическое клонирование пунктуации;
- гонка structure-tell к 0;
- одинаковые 10-граммы;
- искусственная длина ради gate;
- одинаковый жёсткий ритм у всех вариантов.

# 26. Мини-примеры

## 26.1 Технический вопрос

Вопрос:

```text
Чем `Consumer<T>` отличается от `Supplier<T>`?
```

Хороший общий формат:

```text
`<Interface>` принимает/не принимает вход и возвращает/не возвращает результат;
<типичный сценарий>.
```

Correct:

```text
`Consumer<T>` принимает значение `T` и ничего не возвращает через `void accept(T)`;
его используют для побочного эффекта, например в `forEach`.
```

Plausible wrong:

```text
`Consumer<T>` принимает значение `T` и возвращает преобразованный `T` через
`T accept(T)`; его используют для преобразования элементов в `map`.
```

Ошибка одна: Consumer перепутан с Function. Термины реальные, форма сопоставима.

## 26.2 Soft-skill вопрос

Вопрос:

```text
Как использовать 1:1 с разработчиком?
```

Плохой wrong:

```text
Всегда публично и жёстко контролировать задачи.
```

Хороший plausible wrong:

```text
1:1 можно использовать как регулярный статус-синк по задачам, чтобы быстрее
находить блокеры. Ошибка в том, что такой формат дублирует стендап и вытесняет
разговор о росте, мотивации и долгосрочных проблемах.
```

Это зрелая, но неверная модель: полезная цель выбрана, формат перепутан.

# 27. Финальный self-review блока

Перед сохранением ответить `да` на каждый пункт.

## Факты и уникальность

1. Correct фактически верен?
2. Ровно один вариант защитим?
3. Stem содержит весь необходимый контекст?
4. Wrong не становится верным в другой разумной интерпретации?
5. Version-sensitive claims проверены?

## Mental models

6. В каждом wrong одна основная ошибка?
7. Все три ошибки различаются?
8. Каждый wrong содержит зёрно правды?
9. Каждый wrong мог бы выбрать реальный middle/senior?
10. Нет карикатуры или очевидного абсурда?

## Русский язык

11. Все варианты звучат естественно вслух?
12. Нет канцелярита и машинных цепочек?
13. Нет искусственного наполнителя?
14. Термины оформлены последовательно?
15. Пунктуация корректна?

## Visual parity

16. Correct нельзя угадать по длине?
17. Correct нельзя угадать по числу предложений?
18. Correct не единственный с backticks/скобками/двоеточием?
19. Correct не единственный с примером или cause-effect?
20. Wrong выглядят так же хорошо отредактированными?
21. При скрытом `correct` ответ не угадывается глазами?
22. При этом options не выглядят stamped clones?

## Sections

23. Sections соответствуют текущему text?
24. Sections добавляют знание, а не повторяют option?
25. Related links существуют?

Если хотя бы один ответ `нет`, блок не готов.
